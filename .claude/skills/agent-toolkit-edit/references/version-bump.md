# バージョン更新の詳細手順

本書は、`.claude/skills/agent-toolkit-edit/SKILL.md`の「バージョン更新」節で扱う詳細手順をまとめた資料である。
`.chezmoi-source/`配下のchezmoi配布物、`bin/`配下のCLIラッパー、`scripts/`配下のヘルパースクリプトのみを変更する場合は対象外とし、バージョン番号を据え置く。

## 判定基準

エンドユーザーに届く振る舞いが変化する変更では、必ずバージョン番号を更新（バンプ）する。更新要否の判断に迷う場合も更新する。
コメントやdocstringの修正のみ、`*_test.py`の修正のみ、入出力の挙動が変わらないリファクタリング、誤字修正やスタイル調整にとどまる場合は、バージョン番号を据え置く。

- PATCH（`+0.0.1`）: 軽微な修正（不具合修正、フック処理の改善、検出処理の調整、文言の修正、既存見出し内における規範の補強など）
- MINOR（`+0.1.0`）: 機能の追加、検出範囲の大幅な拡大、descriptionの変更、節の新設など、規模の大きい変更
- MAJOR（`+1.0.0`）: ユーザーからの明示的な指示がある場合に限定して適用する（詳細な規定は`agent-toolkit:commit`の`references/publish.md`「版数と生成物」を参照する）
- 現行のバージョンが`major.minor.patch`という3つの数値要素で表せない場合は、プロジェクト固有の対応表またはユーザーからの明示的な指定がある場合にのみ区分を適用する。指定がない場合はバージョン更新せず、判定不能として報告する

## 競合解決と統合後の確認

rebaseやmergeの際に`version`の競合が発生した場合は、`(major, minor, patch)`の数値タプルを比較して値が大きい方を採用する。採用した値は、定義元となる2つのファイル（`agent-toolkit/.claude-plugin/plugin.json`および`.claude-plugin/marketplace.json`）へ反映する。続けて`scripts/sync_codex_plugin_manifests.py`を実行し、派生マニフェストを同期する。バージョンの整合性は`scripts/sync_codex_plugin_manifests.py --check`（最新なら終了コード0、不整合なら1、引数の誤用なら2）を実行して確認し、同スクリプトによる判定結果を採用する。

rebaseやmergeを完了した後は、競合の有無にかかわらず、公開済みの統合先と定義元の`version`を比較する。未公開のコミットにエンドユーザー向けの振る舞いを変える変更が含まれており、かつバージョン番号が同じである場合は、統合後のバージョンを基準として再度バージョン番号を更新する（別の作業が先に同一バージョンへ更新し、競合せずに統合された場合に更新が配信されなくなる事態を防ぐためである）。

## 未プッシュ範囲での統合

`scripts/agent_toolkit_bump.py`は、未プッシュのコミット範囲にすでに存在する更新以下の種別が指定された場合、処理を行わずスキップ（no-op）する。そのため、後続の編集ごとに毎回追加で更新を実行する必要はなく、更新種別の引き上げ（格上げ）が必要な場合にのみ上位の種別を指定して実行する。なお、`git push`を実行した後の追加コミットは、新たな未プッシュ範囲として扱う。

## Codex導入後のrootの再確認

Codexプラグインの導入バージョンが変更された場合は、保持しているplugin rootの情報を破棄して再解決する。
プログラム内で`codex plugin list --json`を実行して結果を取得する。`installed`の一覧から`pluginId == "agent-toolkit@ak110-dotfiles"`となるエントリを一意に抽出し、識別子、marketplace、version、有効状態、ならびにrootの解決結果のみをモデルへ返却する。
取得の失敗、対象エントリの不在、対象が一意に定まらない状態、無効化状態、実体パスの欠落をそれぞれ区別して診断し、全一覧をそのまま返すことは避ける。
plugin cache directory配下にある新バージョンのrootパスを解決し、そのroot内の`skills/`ディレクトリの存在、plugin manifestに記載された`version`と導入バージョンの一致、および実行対象スクリプトの実在を確認した上で使用する。
これらを確認できない場合は処理を未完了として扱い、古いrootへ戻す操作は行わない（`source.path`は配布元を示す値であり、cache rootの解決には新バージョンのrootを使用する）。
なお、起動時の通知に示された変更前のplugin rootは、導入バージョンを変更する前の処理に用いる。

## plan modeでの取り扱い

- 計画ファイルの`## 要件・外部仕様`に、更新種別（PATCH／MINOR／MAJORまたは`bump不要`）と、「判定基準」に基づく判断根拠を記述する。具体的なバージョン番号の決定や既存の更新コミットとの統合処理は、`scripts/agent_toolkit_bump.py`に委ねる。バージョン更新する実装では、検証を実行する前に`scripts/agent_toolkit_bump.py {種別}`を実行する。
- バージョン更新を伴う計画では、差分の有無にかかわらず定義元の2ファイルを変更対象の説明に含める。ジェネレーターが整合性を保証する派生ファイル（派生マニフェストや、`agent-toolkit/rules/`から生成される`.chezmoi-source/dot_codex/AGENTS.md`など）は変更対象の説明に列挙せず、正式な生成コマンドの実行と生成結果の一致確認手順を`## 検証`に記述する。派生マニフェストは、定義元の更新後に`scripts/sync_codex_plugin_manifests.py`を実行して反映し、`--check`オプションで整合性を確認する。
- バージョン更新の完了条件は、公開済みの基準（`git push`済みの最新のplugin manifest）に対して要求された種別以上の更新が含まれており、定義元の2ファイルと派生マニフェストの`version`が一致していることとする。既存の未プッシュの更新内容で条件を満たしており、`scripts/agent_toolkit_bump.py`がファイル変更なし・終了コード0で終了した場合も完了とみなす。

`agent-toolkit:process-wi`における特則:

- 各レーンは、更新種別（`bump不要`を含む）とその根拠、ならびにMAJORの場合は認可の根拠を計画ファイルに記録し、レーン内ではバージョン更新コマンドを実行しない。
- AWI本文に記載されたバージョン区分は、起草時点でその要求単体を評価した判定である。メインエージェントは、同一の実行サイクルで統合された変更全体に対して「判定基準」を適用し、より上位の区分が存在する場合はそれを`bump種別`として終端担当へ引き渡す。終端担当は、すべてのレーンのマージが完了した後に`scripts/agent_toolkit_bump.py`を1回実行する。
- バージョン更新を完了条件に含むAWIは、`agent-toolkit/share/lane-integration.subagent.md`の延期`adopt`の手順に従い、終端担当がバージョン番号、派生マニフェスト、および公開結果を検収した後に完了（終端）とする。
- 統合ブランチをpushする前に上流ブランチの進捗を取り込むためrebaseを行った場合は、「競合解決と統合後の確認」の基準に基づいて再度比較し、必要に応じて終端担当が再度のバージョン更新とマニフェスト同期を実施する。

## 新規CLI公開時の疎通確認

配布用プラグインにおいて新しいCLI、コマンド、またはラッパースクリプトを公開する計画を立てる際は、エンドユーザー環境で正常に起動できるようになるまでの導入手順を`## 要件・外部仕様`に明記する。対象はインストールスクリプト、post-apply処理、PATHの通し方、bash補完の登録、Windows用ペアファイルの作成である。プラグイン単体を利用するエンドユーザーが、PATHの追加や環境変数の設定以外の特別な設定なしにコマンドを実行できる状態を目標基準とする。
プラグインの`bin/`ディレクトリの実配置先は、バージョン番号付きのキャッシュディレクトリとなる。dotfilesを利用するエンドユーザーは`.bashrc`でのPATH追加によって、またプラグイン単体を利用するエンドユーザーは`install-claude.sh`や`install-claude.ps1`が配置する動的解決ラッパーによって、このパス構造を意識せずにコマンドを実行できるようにする。
