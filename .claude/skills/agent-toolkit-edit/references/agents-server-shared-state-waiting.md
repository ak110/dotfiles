MCPツールの呼び出し記録（セッション状態`agents_server_sessions`）は`session-state-and-flags-agents-server.md`が保持先と更新主体を定める。

子の追跡は、登録簿の不在・解放済み・読取不能でも維持する。
共有された終了時の結果も得られなければ、同じ識別子を保持して終了の観測まで再解決する。
回収済みの終了は既存のwait出力追跡で集合から除き、未回収の子の終了を継続の判定に用いる。
過去の継続を消費した後やCLIのidle時も、未回収の子の観測を保持する。
Managerは配送成功した完了IDだけを終了待ち集合から除き、回収済み・未追跡の子の終了応答を集合外として扱う。

Codexバックエンドは、子セッションを起動した委譲先から`atk agents wait`の実行に成功した`commandExecution`を受け取る。
回収済みの終了セッション識別子は、`_agents_server/wait_output_tracking.py`の`consume_agents_wait_output`によって追跡対象の集合から除外される。
読み取りの対象となるのは、ターミナル等の標準出力に出力されたJSON Lines、エージェント環境で標準出力に直接書き込まれた要約の`終了行:`、ならびに要約が長文となって`atk`の自動保存機能により保存された場合の`保存先:`が示すファイル内容である。
標準エラー出力の保存先は別のラベルで返されるため、待機処理のJSON Linesとしては読み取らない。
保存先ファイルは結果の回収処理を行う前にあらかじめ開き、準備が整わない限り結果データを消費しない。
待機に失敗した場合や内容が読み取れなかった結果については、追跡対象の集合に残したまま保持する。

子セッションやバックグラウンドタスクの完了を待っている保留中の状態に対してプロンプトの追送が行われた場合でも、待機対象の識別子と保存済み出力との対応関係は維持する。
子セッション、Codexの子スレッド、Claudeの`local_agent`など、明確な終了上限時間が存在しない対象を含む保留状態では、`auto_resume_deadline=None`とする。
名目上の7800秒といった制限で強制的に最終化することはせず、対象の終了と再開ターンが実際に観測されるまで待機状態を維持する。
一方で、明確な制限時間を持つバックグラウンドコマンドの通知欠落に対しては、既存のタイムアウト期限を適用する。
過去ターンの保留結果は外部へ公開せず、新規ターンと未完了の作業の生存期間を適切に分離する。
配送に失敗した場合でも観測対象を維持し、再試行可能な状態を保つ。
終了を観測した対象と回収済みの対象を追跡集合から除き、同一の完了イベントによる自動再開処理は1回のみに制限する。
kill、期限切れ、ストリーム終了による明示的な完了確定と、利用上限や過負荷による継続待機は、異なる処理境界として区別して扱う。
期限を持たない利用上限や過負荷による保留状態に対してプロンプトが追送された場合は、従来通り保留結果を確定し、待機対象が残っていれば`heldResultFinalized`フラグを付与する。

- 新しい状態を設計する際は、状態の表現形式を1つに集約する。
  未回収の終了結果は、結果ファイルを書き込んだ主体の公開台帳とファイルの存在有無から、`published`、`consumed`、`unpublished`のいずれかに分類する。
  CLIによる回収途中の結果については、run別退避ディレクトリのデータを再開時の基準とし、原本が残っている中断ポイントであっても同一のメッセージ本文を重複して配信しないようにする。
  なお、`SessionState.result_delivered`はファイルを削除するタイミングを管理するための内部フラグであり、ファイルを持たない処理でのみ使用する。
- MCP側の待機処理とCLI側の待機処理は、いずれも`_agents_server/retained_results.py`の`take_result`を用いて、所有者確認、排他ロックの取得、本文の読み取り、およびファイルの削除を一連のアトミックな区間として実行する。
  CLI待機では同一の排他区間内でrun別退避ディレクトリへの保存を確定させてから原本ファイルを削除する。
  MCP待機では退避先を指定せず、従来の結果回収フローを使用する。
- 待機処理の所有権と待機対象セッションの登録は、いずれも書込主体を単位とする名前空間で管理する。
  読み取り側も同じ書込主体単位で探索し、対象のロックファイルや登録情報を特定する。
- `atk agents wait`の実行（フォアグラウンド実行およびバックグラウンド実行）は、書込主体ごとに同時に最大1つとする。
  ロック競合を検知した後発プロセスは、`current.json`に記録されたrun IDを固定し、ロック取得後にその固定したrunの状態を再読み込みする。
  その状態が`published`であれば保存済みの本文と終了コードを返し、返却完了後に`consumed`へ遷移させる。
  `foreground-delivered`または`consumed`なら本文を再出力せず、終了コード8と保存runの回復情報を返す。
  状態が`running`の場合は、保存対象およびrun別退避ディレクトリの対象を引き継ぎ、ロック待機中に追加された対象セッションも含めて同一runの待機処理を再開する。
  競合せずにロックを取得できた後続のwaitプロセスも、現在の対象セッション集合が残存する`running`状態のrunと一致していれば、退避データを引き継いで待機を再開する。
  この対象集合の一致確認には、原本の回収後にrun別退避ディレクトリにのみ残っているセッションも含める。
  対象集合が一致し、かつ`continuable`がfalseの`published` runについては、結果を1回のみ返却する。
  対象集合が変化したrunや、継続可能な公開状態（`continuable`がtrue）のrunについては新規待機を開始する。
  `consumed`に遷移済みのrunは再利用せず、常に新規runを開始する。
  待機時間の上限に達した場合や通知のみを返却したrunは`continuable`をtrueとし、次回実行時には新規runを開始する。
  なお、run情報の記録がない旧形式のロックファイルのみが存在する場合は、旧形式との競合を示すエラー診断を出力して終了する。
  ロックの取得単位は書込主体ごととし、対象セッション個別のロックは使用対象から除く。

`wait_run.py`は、`status`で判別する`running`、`published`、`foreground-delivered`、`consumed`の型でrun本体を読み、`current.json`はrun参照として別に検証する。
run本体の`run_id`と`targets`を検証し、`published`以後では文字列の`output`と整数の`exit_code`を必須とする。
対象追加と公開・配送の遷移は同モジュールの操作へ集約し、`agents_wait.py`が書込主体のロック内で保存する。
不在は`None`、不正記録は既存の読取異常として扱い、上書きしない。
`shared_sweep.py`も同じ型で未回収runを判定し、読取不能・不正なrun本体や参照があればルートを保持する。

CLI待機における結果配信は、結果や通知の取りこぼしを防ぐことを最優先とする。
具体的には、runディレクトリへ本文を保存してから標準出力（stdout）または標準エラー出力（stderr）へフラッシュ（flush）し、その後に配信完了状態を保存する。
後続のwaitプロセスが保存済みの本文を再配信する場合も、フラッシュ完了後に`consumed`状態を保存する。
いずれのケースでも、フラッシュ後かつ状態保存前にプロセスが異常停止した場合は、次回のwait実行時に保存済み本文が1回再出力されることを許容する。
プロセスの強制終了を伴わない通常の合流処理では同一runを1回のみ回収し、1回の再開処理の中で同一セッションの結果が重複して出力されるのを防ぐ。
フラッシュと状態ファイルの更新は受信確認（ACK）の仕組みなしに完全アトミック化できないため、この停止点における安全側の再出力を許容する設計としている。

`foreground-delivered`や`consumed`の状態は、標準出力への配信が行われたこと、および後続のwaitによる再演が完了したことのみを示しており、受け取った側（エージェント）が実際に内容を読み取ったかどうかまでは保証しない。
待機対象が0件で終了した場合（終了コード10）や、すでに消費済み（`consumed`）で終了した場合（終了コード8）の対応を定める。
`atk agents wait`は同一ルートと書込主体の`current.json`に記録された配信済みrunを読み取り、`run_path`、対象の`session_ids`、ならびに実在する`agent_message_paths`を診断情報に追加する。
結果を受け取ったコンポーネントは`run_path`を参照することで、`output`内に保存されている終了結果本文を再取得できる。
これにより、個別のメッセージ本文ファイルがすでに削除されていても`output`から内容を復元できる。
runファイルが存在しない、読み取れない、または結果データを含んでいない場合は、`status`をそれぞれ`missing`、`unreadable`、`no-results`として区別して報告する。
復旧対象として参照できるのは同一所有者のrunに限られる。
保存されたrunデータは受取側が直接読み取る運用とし、`atk agents wait`側では結果を再配信せず1回限りの回収とする契約を保つ。

共有領域である`results`配下の結果ファイルを削除できるのは、委譲元への配送完了後、CLIのrun別退避ディレクトリへの保存完了後、または`stop`による明示的な破棄要求の受領後に限られる。
単なる経過時間の長さだけを理由として結果ファイルを削除することはない。
再開した親のManagerは、登録簿が示す元のrootから結果を読み、`_RegistryResumeState`に原本のrootと所有ファイル名だけを保持する。
結果本文の複製は増やさず、元turn番号を確認した同じ排他回収で一度だけ消費する。
元rootに別の生存sessionがある場合も、登録された同じ子の結果を回収できる。
通知の宛先は元の投影の親IDと、投影が無い場合の登録簿の起動主体から確認し、同じ直接親へ返す。
再開予約中の元turn結果を現在turnの終了として返さず、旧結果の回収・削除は新turnの開始前に終える。

`atk agents notify`は、委譲先から環境変数`AGENT_TOOLKIT_OWNER_SESSION`を通じて所有者セッションを直接特定できるため、索引の参照を省略する。
子エージェントから親エージェントへ通知を送る際は、宛先を所有者セッションから解決する。
現在のセッション識別子から解決してしまうと、自分自身を宛先として誤認してしまうためである。
