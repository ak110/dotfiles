| 記録済み実行の停止で回収できなかった所有対象と回収（親による待機）を確認できなかった直接の子（それぞれPIDと起動時刻）、生成停止を確認できなかった理由 | `<状態ディレクトリ>/recorded-process-reclaim/<起点のpid>-<起点の起動時刻>.json` | `recorded_process.stop_recorded_executor`（同じ起点の再停止で回収を再試行）、`session_registry.resolve`（記録した対象が残る委譲先CLIか未確認の理由を持つ記録を生存中として扱い、終了の推定を止める。回収待ちの直接の子はzombie表示でも同じPID世代が残る間は残るとみなす）、`run_skill_state.RecordWriter.finish`（回収待ちが残る間は実行記録のPID世代を消さず、`atk run-skill --resume`の再試行へ渡す） | `recorded_process.stop_recorded_executor`が残存・未確認の時に保存し、`atk run-skill`が起動した子を直接停止して回収できなかった時は`recorded_process.retain_unreclaimed`が同じ形式で保存する。残存は回収を確認した時と記録した対象が全て終了していた時に削除する。回収待ちの直接の子は、強制終了の後に同じPID世代の消滅を確かめるまで残す。生成停止を確認できなかった理由は再試行で解消しないため、運用者がこの実行の残存プロセスが無いことを確かめてから記録を削除するまで残す。書込は`reclaim_records`が原子的に行う |
| 終了済み委譲sessionの解放要求と応答 | `<状態ディレクトリ>/sessions/<uuid>.release-request`および同名の`.release-response` | レーン回収CLI、および対象セッションを所有するMCPサーバー | CLIが解放要求を作成し、所有MCPサーバーが終了状態と所有関係を再確認した上で結果保持付きの停止（stop）を実行し、応答を書き込む。CLIの処理完了時に両ファイルとも削除・回収される |

task返却の形式回復を消費した状態は`SessionState.result_contract_recovery_consumed`が保持し、`state.py`の登録処理から`session_registry.py`の共有登録簿へ保存する。
同一sessionで真になった値は後続の公開でも保持する。
`manager_registry.py`が別所有者へ復元し、`SessionResumeState`と`manager_resume.py`を通して新しいturnへ引き継ぐ。
回復待ちと診断はturn単位で初期化し、消費状態は初期化しない。

メモリー上の保留は`SessionState.hold`の理由別データ、開始受理は`turn_start`、終了は`turn_end`で保持する。
型は`_agents_server/turn_state.py`、開始・解除・記録の操作は`state.py`が所有し、backend・resume_waits・result_contract・Managerが消費する。
保留述語と予定時刻は、この状態から得るreadonlyの射影とする。
連鎖履歴と形式回復の消費は別の寿命を保つ。
登録簿の書込入力は`PublicationState`とし、terminal/statusの許容組から保存値を導出する。
読取の解決とv1〜v3の保存・復元契約は維持する。
reader-fitの入力成果物と対象別完了の形式検査はresult_contractが既存の回復を用いて行う。
本文・比較資料・判定範囲の確認が済んだかの意味判断と証拠は、レビュー担当が所有する。

session登録簿の公開・解放・中断履歴更新・掃引と再開予約は、`sessions/.locks/<session_id>.lock`の共有ファイルロック内で読み取りと更新を実行する。
ロックファイルは保持する。
所有者による解放は、取得した`server_instance`と`turn_seq`が現在の記録と一致するときだけ更新し、旧turnの公開時は新turnと再開予約の記録を保持する。
時間のかかるバックエンド接続中はファイルロックを保持せず、PID世代付きの予約を同一会話の二重再開防止に使う。

Codex App Serverの管理・所有単位は委譲セッションごとである。
Codexバックエンドはセッション単位で個別にApp Serverを起動し、そのセッションの開始・継続・再開・中断のリクエストを該当の接続へ送信する。
サーバーからのリクエストに対する応答や接続エラーの通知も、その接続を所有するセッションのみを対象として処理する。
App Serverはthreadごとのstdio MCPサーバーを子孫プロセスとして起動するが、`thread/unsubscribe`のレスポンスを返した後もしばらくの間プロセスを存続させる挙動がある（2026年10月16日にCodex CLI 0.163.0で確認）。
そのため、購読解除の応答が返ったことだけではリソースの解放完了とはみなせず、完了判定にはApp Serverおよびその子孫プロセスの実際の終了確認を用いる。
セッションのリソース解放（`stop`の実行、保持期限切れ、起動候補の取り下げ、MCPサーバー停止など）を行う際は、所有するApp Serverと、そのApp Serverへの終了要求の直前に取得した子孫プロセスの一覧がOS上で実際に終了したことを確認して完了とする。
App Serverが先に終了してしまうと、子孫プロセスの親PIDが変わり、追跡できなくなるためである。
終了が確認できないプロセスが残っている場合は、接続の所有関係を維持したまま再試行可能なエラーを返し、セッション登録簿も解放前の状態を保持する。
リソース解放後に`send_message`が呼び出された場合は、新たなApp Serverを起動して`thread/resume`を実行し、同一の会話を再開する。
モデル一覧の取得や`thread/read`で参照する際は、専用のApp Serverを一時的に起動し、応答を受け取った後に終了させる。

新規セッションの識別子は、各バックエンドが共有セッション一覧に登録する前に、`session_identity.identity_validator`を使って重複の有無を検証する。
ルート識別子、稼働中・保持中の他のセッション識別子、ならびに共有登録簿上で実行中または終了状態として解決されるセッション識別子との重複が検出された場合は、原因と対処手順を示す起動エラーとする。
重複した値は、登録簿、状態・結果ファイル、待機対象リスト、イベントログなどの永続化処理には渡さない。
同一の識別子を再利用して再開する場合は、指定された`expected_session_id`と完全に一致していることを確認した上で許可する。

セッションの`created_at`は初回の開始時刻を表し、ターンごとに更新される`started_at`とは区別して保持する。
また、`label`と`prompt`も初回の`start`時点で確定する。
これら3つの項目は、セッションの再開や再起動をまたいで保持される基本起動情報であり、その定義は`agent-toolkit/agent_toolkit/_common/session_registry.py`の`LaunchInfo`で一元管理されている。
MCPサーバーのメモリー上の値を正とし、状態ファイルやセッション登録簿（フォーマットバージョン2のオプショナル項目）へ反映（射影）される。
再開されたセッションは、登録簿または退避済みの再開情報から各項目を引き継ぐ。
これらの項目を持たない旧形式の登録簿から再開された場合は、`label`と`prompt`を空文字列とし、`created_at`は再開時刻を起点として扱い直す。
`start`および`send_message`の公開レスポンスには、起動したセッションや送信先セッションがメモリー内に保持している`label`を含めて返す。
これにより、委譲元エージェントが起動時やプロンプト追送時のレスポンスを確認するだけで、`session_id`と担当エージェント名を正確に対応付け、送り先を確認できるようにしている。
また、`LaunchInfo`は送信済みの追送プロンプト一覧である`followup_prompts`、ターン番号と最終応答全文を記録する`final_responses`、および`terminal_error`も管理する。
これらの項目は、所有側が起動時・追送時・終了時の各タイミングで更新し、同一セッションの再開や前任エージェントからの引き継ぎ時に活用される。
プロンプト送信前の事前確認処理や委譲プロンプト生成CLIも、既存の`prompt`や`followup_prompts`を参照して、今回の入力がエージェントの役割宣言に沿っているかを検証する。
CLIは登録済みのセッション情報や既存の起動・ログ記録への参照を利用し、既存の保存先へ情報を集約する。
参照先のパスの内容が更新された場合でも、その時点で必要な入力を保持する。
`handoff_from`を指定して起動した場合は、前任エージェントの作業ディレクトリ（cwd）とモデル種別（model_type）を復元してレスポンスに含める。
PostToolUseフックはこの引き継ぎ起動時に限りレスポンスから両方の値を取得し、後任エージェントの待機対象とタスク種別を記録する。
通常の起動時には、指定された入力のcwdとmodel_typeを検証して受け付ける。
引き継ぎに必要な会話ログの抽出には、`atk run-script session-review-prepare`の`--conversation-only`オプションを使用する。
指定した記録から会話のbundleを生成し、候補文書、比較資料、統計データの生成とfailure ledgerの更新を省く。
少量表示と保存済みbundleからの継続取得は、`agent-toolkit:review-session/references/session-records-conversation.md`「会話の少量取得」に従う。
生成されたログデータの保存期間は、managed-tempの保持期限に従う。

- 外部所有の復元状態は`ManagerRegistry`の`_RegistryResumeState`として管理し、各利用側は共通の`_refresh_resume_state`を呼び出して共有登録情報の最新ターンと状態を再確認する。
- 外部の復元状態を読み取る`show`や`list`、停止済み・期限切れの判定、ならびに停止実行や結果取得の処理は、再確認した最新の状態に基づいて行う。
  新しいターンが進行中である場合は、過去ターンの終了状態を現在の完了状態として流用してはならず、過去の未回収結果は結果ファイルのルールに従って保持する。

`sessions`配下の登録簿を「解放済み」レコードへ更新できるのは、そのセッションを所有するMCPサーバー自身のみである。
自プロセスが所有していないセッションに対する`stop`要求に対しては、記録されたプロセスがOS上に存在する限り、登録簿と結果ファイルを保持したまま拒否レスポンスを返す。
`stop`の実行または保持期限の経過によってリソース解放が完了した段階で、解放の理由、完了時刻、および内部再開情報を記録した「解放済み」レコードへと置き換える。
Codexにおけるリソース解放の完了は、所有するApp Serverおよびその子孫プロセスの終了をOS上で確認できた時点とする。
API接続へ移行した会話については、Codexでは利用プロバイダー名、Claudeでは`claude_resume_info`に含まれるenvファイルのパスを保持する。
セッションの終了を観測した待機側プロセスは、登録簿を削除せず保持する。
解放済みレコードを意図して残すことにより、他のMCPサーバーが「所有側によって正常に解放された状態」と「そもそも記録が存在しない状態」とを明確に判別できるようにしている。
委譲元に関する情報はセッション作成時に書き込まれ、その後の状態更新や解放済みレコードへの移行時にも一貫して引き継がれる。

レーン回収時のリソース解放要求は、`session_release.py`が登録簿の終了状態、作業ディレクトリ（cwd）、および所有プロセスを確認した上で作成する。
所有MCPサーバーの常駐監視処理がこの要求を読み取り、現在の登録情報と所有関係を再確認した上で`stop(retain_result=True)`を実行する。
ユーザー等から明示的に実行された`atk lane delete`は、メイン側の待機タイムアウトから算出した共通の期限（deadline）内で応答とリソースの終了を待ち、リソースが使用中かどうかの判定を再度行う。
一方、バックグラウンド等による自動回収処理は解放完了をブロッキングして待つことはせず、その時点の登録簿と使用状況の判定結果に基づいて、即座に回収可能なリソースのみを回収する。
未解放、使用中、または状態確認が取れないリソースについては、回収できなかった理由と再開手順を提示した上でそのまま保持する。
CLI自身が生成した要求ファイルや応答ファイルは、CLI処理の完了時に自身で削除・回収する。
プロセスの異常終了によって残されたファイルについては、既存のセッションファイルと同様に7日間の定期掃引処理に委ねる。

サーバー停止処理は、再開処理と同じ`turn_control_lock`を取得して直列に実行され、管理対象のSDKタスク、CLIのルートプロセス、およびその子孫プロセスのクリーンアップが完了した後に、未終了ターンを`interrupted`として外部へ公開する。
クリーンアップ後も委譲先CLIのプロセスが依然として生存しているターンについては中断を公開せず、登録簿上は実行中（`running`）のまま保持する。
クリーンアップ処理が失敗した場合は、プロセスハンドルや未解放のリソース記録をそのまま維持し、同一対象に対して停止処理を再試行できるようにする。

起動済みとしてセッション登録簿に登録するのはバックエンドの起動に成功したセッションのみであり、入力パラメーターの検証エラー、候補モデルの解決失敗、バックエンド起動エラーなどの理由で起動に至らなかったものは、起動前の失敗として返却する。
親のMCP起動時は`manager_recovery.py`が登録簿の直接の親子関係から元の子IDを待機対象へ戻す。
生存する所有者は観測し、所有者喪失時の実行プロセスだけをPID・作成時刻で確認して停止する。
終了を確認した未完了の会話は、保存した接続・モデル・cwd・起動情報で同一IDから再開する。
子のMCPが同じ処理を行うことで孫以降を復旧する。
完了未回収は元結果だけを返し、明示中止と回収済みの仕事は再実行しない。
復旧失敗はMCP待機の診断と、作成主体をserverとする既存形式の上り通知で親へ伝える。
通知の保存失敗は元の例外へ追加し、独立した他の子の復旧を続ける。

次の箇条書きは個別照会・追送による引き継ぎの条件であり、親MCP起動時の自動復旧は上記の処理を使う。

- プロセスの再起動をまたぐセッション状態の解決は、セッション登録簿の記録に従って行う。
  statusline向けの状態ファイルは書込主体を特定できる処理でのみ作成されるため、この解決処理の入力としては使用しない。
  登録簿上で終了状態が示されていないセッションについては、別のプロセスが現在ターンを実行している可能性を否定できないため、自動再開は行わない。
  所有サーバー側は自身の停止時に、バックエンド停止に伴って終了した未完了ターンを`interrupted`として登録簿および結果ファイルへ書き込み、セッションを終了状態へ進める。
  それでもなお`running`のまま残されている記録については、`session_registry.resolve`が記録済みのプロセス識別情報を検証して状態を判定する。
  記録されたすべてのプロセスが存在しない（PIDが存在しない、または同一PIDでもプロセスの起動時刻が異なる）場合は、登録簿のファイル自体を書き換えることなく`interrupted`による終了および中断理由として解決し、すべての参照元が終了状態として扱う。
  プロセスが1つでも生存している場合や、プロセス識別情報を持たない記録（識別機能が導入される前の古い記録）については、実行中（running）として扱う。
  問い合わせたMCPサーバーは、有効なハートビートを持つ状態ファイルのいずれにもそのセッションが含まれていない場合に限り、エンジンの種類に関わらずこの中断情報を登録簿へ正式に書き込んで復元処理を進める。
  Codexのセッション記録については、上記の条件に加えて、プロセス識別情報を持たない旧形式の記録であるか、あるいは委譲先CLIプロセスが実在しない場合に、`thread/read`による終了状態の確認結果も登録簿へ公開する。
  公開するのは、自身のCodex App Serverに対して実行した`thread/read`が、登録簿に記録された`turn_id`のターン（ターンIDが記録されていない場合は全ターン）の終了を示しており、かつ後続に進行中のターンが存在しない場合である。
  所有MCPサーバーのプロセスのみが無応答で残存している記録についても、この引き継ぎ処理の対象となる。
  なお、引き継ぎ側のMCPサーバーが行うのは終了状態の公開のみであり、「解放済み」レコードへの書き換えは元の所有サーバー側の担当として残す。
- 有効なハートビートを持つ状態ファイルにセッションが存在せず、かつ記録されたプロセスのうち委譲先CLIプロセスが現在も生存しているセッションは、「所有サーバーを失った実行中セッション」として扱う。
  このセッションは`thread/read`の結果に関わらず実行中として維持する。
  この判定ロジックは`session_registry.running_ownership`に集約されている。
  MCPツールの`show`と`atk agents show`は、状態が`running`の場合に`ownership`、`recorded_processes`、`owner_root_session_id`、`stranded_notice_count`を付与して返す。
  また`next_action`には、自然終了を待つ操作、ならびに`kill`を実行した後に同一セッションへ`send_message`を送る操作を案内として提示する。
  この状態のセッションに対して`send_message`が呼び出された場合は、再開を試みずに同様の案内を含むエラーを返し、`atk agents wait`は実行中セッションとして待機を継続する。
  MCPツールの`kill`は、登録簿に記録されたPIDおよび起動時刻と完全に一致する委譲先CLIプロセスのみをその子孫プロセスごと停止させ、プロセスの終了を確認した上で`interrupted`を公開する（所有サーバーのプロセスは稼働させたまま残す）。
  この実装は`_agents_server/owner_lost.py`と`manager_registry.py`が担当する。
- 登録簿上にレコードが存在しない場合、すでに「解放済み」になっている場合、またはファイルが読み取れない場合は、同一識別子を持つ終了結果ファイルの有無を確認し、そのファイルが終了を示していれば終了状態として扱う。
  「解放済み」状態や「レコード不在」の状態は、所有サーバーによる明示的な解放だけでなく、7日間の定期掃引処理によっても発生し、終了結果ファイルの存在とは独立しているため、結果の有無の判定には常に結果ファイル自身を用いる。
  解放済みレコードに対する公開判定や、待機対象の解放判定・実行中判定は、レコードが存在しない場合と同様に扱う。
  明示的なモデル候補リストから選択されたAPI会話の復元に限っては、解放済みレコード内に保存されている内部再開情報を取得して同一のプロバイダーをバックエンドへ引き渡す。
  古い記録形式や他のエンジンにおける復元条件は従来通りの動作を維持する。

## effort操作

相対effortの要求は`<状態ディレクトリ>/sessions/<uuid>.effort-request`、応答は同名の`.effort-response`で受け渡す。
会話IDを環境へ渡さないAntigravity・OpenCodeのCLI呼出元は、所有ルート内の状態ファイルにあるsessionと登録簿を読む。
登録済み実行プロセスのPID世代が呼出元の最も近い祖先に一致するsessionだけを本人とし、同距離の複数候補や不一致では操作を拒否する。
起動の可用性確認中でsessionが表示前の場合は、同じ要求の30秒期限内で表示を待つ。
全ルートの走査や新しい索引は加えない。
CLIが自身の会話ID・対象・方向と所有プロセス・有限期限を渡す。
所有MCPの既存監視loopが登録簿の直接親子関係と起動区分を再検査し、受理段を確認して現在値・変更履歴を公開した後に応答する。
CLI終了時に両ファイルを除き、異常終了時は既存の保持・掃引へ渡す。

effortの希望値は`SessionState.effort`から既存の状態・登録簿へ射影する。
`LaunchInfo.effort_history`は時刻・前値・後値・操作主体の4文字列組、`effort_levels`は確認済み受理段を保持し、再開・解放時も起動情報とともに保存する。
`SessionState.effort_resume_turn`は自身で変更したturn番号を保持し、監視loopがそのturnの終了後に1回消費する。
別経路で次turnが始まった場合は予約を除き、重複再開しない。
Claudeの接続済みeffortは`claude_applied_effort`で希望値と区別し、同じ会話の次turn設定を所有タスクへ渡す。
Codexは既存のturn/start、OpenCodeとAntigravityは既存のturn別引数を使う。
