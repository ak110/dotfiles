## 状態ファイルの設計

Claude Code・Codexのhookは呼び出しごとに別プロセスで起動するため、セッション単位の状態ファイルで情報を共有する。

- パス規則: 本書の冒頭に示したパスを、`_common/state_paths.py`の`state_dir()`と`payload["session_id"]`から組み立てる
- 置き場所の選定: 生存期間と共有範囲で選ぶ。
  セッション再開・ホスト再起動後に使う記録と排他ロックは同じ状態ディレクトリへ置く。
  一時ディレクトリへ置けるのは、消失しても判定情報を失わない診断ログや再生成可能なキャッシュに限る
- 旧位置からの移行: 新位置に状態ファイルが無い場合だけ、排他ロック下で同じ`session_id`の旧位置（`tempfile.gettempdir()`配下）のJSONを移す。
  読み取り・更新・期限切れ回収・前身状態の継承には新位置を使う
- データ形式: 単一JSONオブジェクト。
  新規フラグのキーはsnake_case、既存名は読取側の契約として維持する
- 読み書きの契機: スキル呼出・バックグラウンドタスク起動などのPostToolUseイベントで書き込み、PreToolUse・UserPromptSubmit・Stopの判定時に読み取る
- 破損・不在時の扱い: 空の辞書として扱い、安全側に判定する
- `session_id`の切り替え: 現行の状態ファイルが存在しない場合に限り、transcriptを先頭から走査し、状態ファイルを持つ別の`session_id`が一意に特定できるなら、その全キーを継承して継承元を記録する。
  現行の状態ファイルがある通常時は、存在確認だけで終える
- フックイベント間の同期: 主体・文脈・受信版と、実際に発生した出来事を区別して必要な記録だけを共有する。
  資料取得では既知範囲のdigestと配送後の本文を対応付け、実際の受信だけを根拠にする。
  保存内容は本文を除く識別情報に限定する
- フラグ仕様の文書化: 新規フラグや同じ状態ファイルを共有する個人フックのフラグも含め、用途、書き込み元、読み取り元、寿命、リセット処理を後掲の各節に記す（努力目標）
- 状態JSONの削除契機: 状態ファイルを削除するのは、期限切れの定期回収と、終了理由が`clear`のSessionEndだけとする。
  SessionEndは`--continue`、`--resume`、`/resume`で同一の`session_id`に復帰する場合にも発火するため、他の理由で削除すると再開後の記録が失われる。
  期限切れ回収の対象は最終更新から一定期間が経過した通常の状態ファイルとし、`clear`時は排他ロック下で、対象セッションの新旧両方の配置場所にある状態ファイルを削除する
- 出来事と更新の対応: 時刻や消費済みの記録を持つ状態は、記録が証明する出来事（通知の採用、資料の取得など）と更新を許す出来事を対応付け、予約（生成・試算）と確定（採用・配送）、周期の上限、最小間隔の抑止、活動後のデバウンスを区別する。
  別種のイベント列を反復しても要求した出来事へ到達するかは、生成・採用・出力を接続した試験で確かめる
- サブエージェント起動の判定: `tool_name in ("Agent", "Task")`をSSOTとする。
  子の状態は委譲元へ自動伝播しないため、親が必要な値は完了報告の構造化フィールドから厳密に解析する

### 並行書き込みの排他制御

Claude Codeはツールの並列呼び出しでhookを同時に発火させるため、同じ状態ファイルへの書き込みが競合する。

- 状態の更新処理は、排他ロックを備えた`update_state`関数へ集約し、セッション命名用の種別や自動設定されたセッション名も同一のAPI経由で保存する
- 通常のロックファイルは`{state_dir}/hook-sessions/.state.lock`の固定1個とし、`TMPDIR`が異なるプロセスも同じロックで排他する
- ロックは状態の読み取り・変更・書き込みの短い区間だけ保持し、時間のかかるtranscriptの読み取りや継承候補の準備はロックの外で行う
- 前身状態を継承する際は、継承候補を準備した後に同一の共有ロック下で現行状態が不在であることを再確認し、二重継承を防ぐ
- `clear`による削除や期限切れ回収の処理は、同一の共有ロック下でJSONファイルを削除し、固定ロックファイル自体は保持する
- 旧一時ディレクトリのロックは、旧JSONファイルの移行処理に必要な範囲に限定して使用する
- 並行書き込みに関する回帰テストを継続して維持する

## 状態の継承

- `inherited_from_session_id`: 現行の`session_id`に対応する状態が存在しない場合に、一意に特定された前身の`session_id`を記録する。
  共通hookの起動処理が、前身の全状態キーの引き継ぎと同時に1回だけ書き込みを行う
