# dotfilesの規範の改訂

本リポジトリのエージェント向け文書を変える担当が、過去の決定との照合、変更した規範の自セッションへの適用、削除と縮小、仕組みの追加と撤去で守ることを定める。
`agent-toolkit/`配下の配置、版数、配布の手順は`.claude/skills/agent-toolkit-edit/SKILL.md`の表から選ぶ。

| 作業・条件 | 読む資料 |
| --- | --- |
| 規範を追記・新設・移動する置き場所を選ぶ、置き場所を実行レビューで判定する | `references/norm-layer-map.md`と`agent-basics:writing-standards/references/agent-documents-basics.md`「置き場所の選定」 |
| 不具合の原因が過去の対策と同じかを分類する、同じ原因と判定して記録する | `references/recurrence-record.md` |
| 規範を編集する作業を始める（モデルIDとホストの版の点検） | `references/model-host-audit.md` |
| `agent-toolkit:atk-mode`の作業`process-wi`の選定工程でAWIごとの`プロジェクト規範の指定`を書く | `references/project-norm-designation.md` |
| 確認するかを決める | `agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」 |

## 読込表

| 時点または条件 | 全文読む資料 |
| --- | --- |
| エージェント向け文書を編集する前 | `docs/development/concepts.md`。編集する担当自身が全文を読む（要約、見出し一覧、部分読み取り、他の担当の読み取り結果では代えない）。方針の本文と障害の経緯は次節の手順で選ぶ |

## 既存の方針との照合

ユーザーが確定した決定を、後の是正が気付かずに覆す再発を防ぐ。

1. 上の読込表のとおり`docs/development/concepts.md`を自分で全文読み、全ての決定の要旨と今回の変更を比べる。
   関係する決定は見出しから本文へ進む。
   障害の経緯は、変更対象の名前・工程・機能を表す語で`git log -i -E --grep=<語>`を検索し、同じ害の再発を防ぐ条件をcommit本文から読む。
   2026年11月22日より前の障害は、削除前の障害事例集にもある。
   削除したcommitを`git log -1 --format=%H --diff-filter=D -- docs/development/incidents.md`で得て、その親から`git show`で区分と分割ファイルを読む。
2. 採否を決める担当は、選んだ方針とcommit本文から守る条件を今回の判断へ対応付け、結論を計画の判断の根拠（計画が無ければ引き継ぎ記録）へ残す。
3. エージェント向け文書、hook、CLIの変更を実装する担当と実行レビュー担当は、`concepts.md`の決定の要旨を全件読み、変更対象の名前で選んだ節以外も含めて、今回の差分が各決定を覆していないか確かめる（話題の違う決定は話題別の選択では届かないため）。
   決定を覆す差分は、その決定を変えるユーザーの判断が無い限り、実行レビューの指摘（既存の契約を破っている）とする。
4. 規範を追記・新設・移動する時は、過去の決定を覆さないかを先に確かめてから置き場所を選ぶ。
5. 衝突した決定と、近いと判断して衝突なしとした決定だけを、決定と差分を比べた結果とともに計画の記録（実行レビューでは走査記録）へ残す。
6. 規範の節の内容を変える時は、ファイル名と節名を個別の固定文字列で`docs/development/`から検索し、その節を現行規定の所在として挙げる記録も同じ変更で直す。
   編集の過程で新たな障害が起きたか方針が確定した場合は、対応する記録を直す。
7. 工程の担当（その工程を実行する主体）を移す時は、工程名（`実行レビュー`、`実装完了`など）を固定文字列で`agent-toolkit/`、`agent-basics/`、`.claude/skills/`から全件検索し、主体を述べる全ての箇所（例示、別の役割の手順、受領の手順を含む）を新しい担当へそろえる。
   旧来の担当が例示に1か所残っただけで、レーン担当が実行レビューを統括の担当と読んで約1時間待った事例がある（WI `20261116-145542-001`）。

## 変更した規範の自セッション適用

対象となる規範は、`AGENTS.md`、`agent-toolkit/skills/`、`agent-basics/skills/`配下、および`.claude/skills/`配下の各ファイルである。
稼働中の仕組みはセッション開始時や配布時の版で動き、作業ツリーで改訂した条文とは版が違う。
どの版をいつから適用するかを取り違えないことが要点である。

1. 着手前に、依頼やAWIが引用する条文を作業ツリーの現行本文から固定文字列で探し、反映先を特定する。
   一致しなければ同じ目的の現行条文を選ぶ。
   編集するのは作業ツリーの原本であり、配布先の`~/.claude/`と`~/.codex/`は対象外とする。
2. 変更が確定した時点から、作業ツリーの最新内容を自分の判断に適用する。
   `Skill`ツールと`${CLAUDE_PLUGIN_ROOT}`配下の文書はセッション開始時の版を返す（変更したスキルは古い内容を返し、新設したスキルは`Unknown skill`になる）ため、適用する文書は作業ツリー版を絶対パスで読む。
   会話の圧縮の後も、以降の工程を定める変更済みの文書を作業ツリー版で読み直す。
3. 影響を受ける委譲先へ、原本の絶対パス、適用する節、版（commit。未commitならその旨と確定時刻）を伝え、委譲先自身が判断の前に読む。
   未配布の採用版がメインや配下の判断を変える場合は、`agent-toolkit:atk-mode/references/work-contract.md`「記録する内容」に従い、従う版、適用対象、解除条件を全体の作業契約の暫定規則へ残す。
   委譲先は全体の記録を編集せず、同じ情報を委譲元へ渡して自分の引き継ぎ記録に保つ。
4. 呼び出し元の起動・受領契約と、その`起動対象:`に指定した`<役割名>.subagent.md`は、同じplugin rootから対で適用する。
   入力宣言と起動設定が呼び出し元の値の確定・検収と整合する版だけを使い、確かめられなければセッション開始時の版を使い続ける（入力名や起動設定の違う版の混在を防ぐため）。
5. hook、会話イベントを処理するFunction hooks module、プラグインMCPの変更は、配布の後にメインが`mcp__plugin_agent-toolkit_agents_server__apply_runtime_changes`で反映を予約する。
   `targets`へ`plugins`、`agents_server`、`pyfltr`から必要なものを指定し、ターン終了後の反映結果を確かめてから新しい動作を使う。
   agents_serverの再接続は実行中の委譲先のturnを中断し、既存の復旧で同じ会話を再開する。
   権限設定と、この操作の反映対象に無いスクリプトは、この操作だけで反映済みと扱わない。
   委譲先が現行のplugin rootから解決して実行する資源の不具合を直した場合は、`agent-toolkit:atk-mode/references/delegation-prompt.md`の`是正済み資源:`の行で作業ツリー側の絶対パスを渡す。
6. 変更後の規範に従うと作業を完遂できないと分かったら、その変更の設計の見直しを優先する。
   見直しの間も確定済みの採用版を保ち、修正版を確定してから作業契約の指定と配下への案内を直す。

## 規範を削除・縮小するときの消失確認

エージェント向け文書の削除・縮小では、編集目的によらず以下を実施する。
`norm_size_budget_invariant_test.py`で基点からの上限超過を見つけた担当は、無関係なレーンで削減せず、統合先の所有者へ返す。
統合先の所有者は基点の引き渡し・公開の前にこの手順で削減し、検査を通す。
予定済みの並行変更にも余裕を持たせる。
削減量と整理後の上限は、品質に必要な注意事項を残し、読み込み・保守の費用と作業時間を踏まえて、dotfilesの価値を最大化するようにエージェントが決める。
経緯は`docs/development/concepts-document-writing.md`にある。
変えてよいのは構成、置き場所、表現、量であり、各規範が守ろうとしている結果は保つ。

1. 必ず残す4種を、編集の前後で照合する。
   - 硬い制約: データの破損、セキュリティ上の欠陥、取り消しの難しい操作、意図しない外部公開を防ぐ条件。
   - ユーザーが決めた方針: `docs/development/concepts.md`の決定の要旨とその本文、WIの逐語の要求。
   - 公開契約: スキルと作業の名前、`atk`のコマンドと出力、MCPのツール名、WIの本文形式とfrontmatter、役割文書の入力名と返却形式。
   - 文書の目的: 各文書の冒頭で、主体とユーザーにとって守る結果を述べた目的文（`agent-basics:writing-standards/references/agent-documents-basics.md`「冒頭の責務と目的」）。
     重複を圧縮しても意味を残す。
2. 4種以外の削除・縮小は、記述の由来にかかわらず、失われる価値と読み込み・保守の費用を目的とQCDで比べてエージェントが確定する。
   上位の原則（`agent-basics:writing-standards/references/quality-principles.md`）から導ける細則、同じ規則の再掲、検査・CLI・hookが強制している規則の文章は削り、削ると過去の誤りの再発が見込まれる保護は短く残す。
   条文ごとの由来の調査、統合先との対応付け、削除理由の記録は行わない。
3. 削除・縮小の方針と理由は、領域（スキル、手順書のまとまり）の単位でcommit本文に書く。
   失効（対象の実装、機能、工程、ファイルが現行リポジトリに無いこと）を理由にする場合は、識別子の固定文字列検索で実在しないことを確かめる。
4. 意味が保たれたことは、1の照合と、過去の誤りの実例と正常な例を作り替え後の文面へ文書の上で当てはめる確認で確かめる。
   作成者と実行レビュー担当の両方が、縮小前の各文（削除した文、他の文へ一部を統合した文、短く言い換えた文）ごとに、旧文の限定、条件、例外、区別、列挙の要素を1つずつ数え、新文か移動先に残ったか、2で削ると決めたかを確かめる。
   行や文が対応することは、意味が残った根拠にしない（旧文と新文を行で対応付けて検収した圧縮で、対象の限定、追加の認可がある時だけの確認、見立ての分類が落ち、後から戻した）。
   委譲先やセッションを起動して挙動を試す確認は完成条件に置かず、効果は公開後の効果確認で見る。
   テストを足す対象は構造に関わる変更（参照の実在、frontmatter、読込表、役割文書の宣言、表の列など）に限り、文体だけの変更は文書の上の確認で済ませる。
5. 規定を別の資料へ移す時（常に読む資料から条件付きで読む資料へ移す時を含む）は、移設先の読込条件が、その規定を適用する時点で成立するかを確かめる。
   2026年11月20日の作り替え（commit `bc4d3d889`）で、hook通知の処置規則が「方針の衝突時」に読む資料へ移り、通知を受けた時点で読まれずに無視が再発した。
6. 編集前に確認するのは、ユーザーの決定や明示した要求を失う場合と、エンドユーザーが観測する結果や認可・安全性の境界を変える場合だけとする。
   ユーザーの要求を保ったまま、エージェントが要求を広げて足した手段を削る場合は確認しない。
   確認の要否と手段は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
7. 削った規範に起因する誤りが再発した場合は、検査や型へ移す。
   判断が必要なものだけ、失敗例を添えた短文で戻す。

## 撤去した仕組みの照合

新しい仕組み（hook、自動チェック、永続状態、配送の仕組み、規範の条文など）を加える計画を起草する担当と、その変更を実行レビューする担当は、提案が過去に撤去した仕組みと同じ働きをしないか確かめる。

1. 仕組みの働き（何を補う・何を代替するか）を表す語で`git log -i -E --grep=<語>`を検索し、撤去を記したcommit本文を探す（名前や名目は導入のたびに変わるため）。
   2026年11月22日より前の撤去は、削除前の台帳にもある（`git log -1 --format=%H --diff-filter=D -- docs/development/removed-mechanisms.md`で得たcommitの親から`git show`で、索引と主題別の分割先を読む）。
   導入前に検討して却下しただけの案は撤去の記録に載らないため、同じ語で`docs/development/design*.md`の却下案の記述も検索する。
2. 一致する項目があれば、過去の状態へ戻す提案として扱う（`agent-toolkit:atk-mode/references/awi-body.md`「配置規約と導入目的の調査」と同じ扱い）。
   一致した記録が示す方針の所在の本文と比べ、撤去の理由を新しい案で満たせるかを確定してから進める。
3. 検索に使った語、一致した項目、判断を計画の記録（実行レビューでは走査記録）へ残す。
4. 仕組みを撤去する変更では、そのcommit本文に`撤去:`で始まる行で働きを書き、理由の要約、方針の所在、再導入の条件を続ける。
   働きを表す語が手順1の検索で一致するように書く。
