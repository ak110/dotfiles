# dotfilesの規範の改訂

このスキルは、本リポジトリのエージェント向け文書を改訂するエージェントに向けて、次の事項をまとめたものである。
編集前に参照すべき記録、変更した規範を自身のセッションへ適用する手順、メインエージェントが記述する`プロジェクト規範の指定`を扱う。
規範の配置、削除・縮小時の消失確認、モデルとホストの更新時の点検、撤去した仕組みとの一致確認と再発の記録も扱う。
`agent-toolkit/`配下の配置やバージョン更新、配布の手順は、`agent-toolkit-edit`の読込表から作業に合う資料を選ぶ。

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

編集を始める前に、読込表の1行目にある方針や障害対策の記録と、今回の変更内容に矛盾がないことを確認する。
採否を決める担当は、選んだ方針と障害の本文から守る条件を今回の判断へ対応付け、その結論を計画の判断の根拠（計画が無ければ引き継ぎ記録）へ残す。
エージェント向け文書・hook・CLIの変更を実装する担当と実行レビュー担当は、`concepts.md`の決定の要旨を全件読み、今回の差分が各決定を守っているか確かめる。
変更対象のファイル名・工程名で選んだ節以外も、今回の差分が過去の決定を覆していないか確かめる。
話題の違う決定を後の是正が覆す再発は、話題別の選択では決定へ届かないためである。
決定を覆す差分は、その決定を変えるユーザーの判断が無い限り、実行レビューの指摘（既存の契約を破っている）とする。
規範を追記・新設・移動する場合は、追記内容が過去の決定を覆さないかを先に確かめる。
その後、読込表の「規範を追記・新設・移動する置き場所を選ぶ前」が指定する資料で置き場所を選定する。
衝突した決定と、近いと判断して衝突なしとした決定だけを計画の記録（実行レビューでは走査記録）へ残す。
記録には索引の名前や「取得済み」だけでなく、決定と差分を比べた結果を書く。
既存の記録形式を使う。
規範の節の内容を変えるときは、ファイル名と節名を個別の固定文字列で`docs/development/`から検索し、その節を現行規定の所在として挙げる記録も同じ変更で現行に合わせる。
編集の過程で新たな障害が発生したり方針が確定したりした場合は、対応する記録文書を更新する。

## 変更した規範の自セッション適用

1. 更新済み条文との競合を防ぐため、着手前に依頼やAWIの引用を作業ツリーの現行本文から固定文字列で検索し、反映先を特定する。
   一致しなければ同じ目的の現行条文を選ぶ。
   配布先の`~/.claude/`や`~/.codex/`は編集対象としない。

2. 対象となる規範は、`AGENTS.md`、`agent-toolkit/skills/`、`agent-toolkit/share/`（規範原本を含む）、`agent-basics/skills/`配下、および`.claude/skills/`配下の各ファイルである。
   これらを変更したエージェントは、変更が確定した時点から作業ツリーの最新内容を自身のその後の判断に適用する。
   影響を受ける委譲先には原本の絶対パス、適用する節、版（commitハッシュ。未commitの場合はその旨と変更確定時刻）を伝え、委譲先自身が判断前に読み込む。
   セッション開始時の版と作業ツリーの版を明確に区別し、各担当者が同じ原本を参照できるようにする。
   未配布の採用版がメインや配下の判断を変える場合は、`agent-toolkit/share/work-contract.md`「記録する内容」に従い、従う版・適用対象・解除条件を既存の全体作業契約の暫定規則へ残す。
   委譲先は全体記録を編集せず、同じ情報を委譲元へ渡し、自身の引き継ぎ記録にも保持する。

   - `Skill`ツールや`${CLAUDE_PLUGIN_ROOT}`配下の文書は、セッション開始時に読み込まれた版を返す（変更したスキルは古い内容のまま返り、新設したスキルは`Unknown skill`となる）。
     以降の判断に適用すると選んだ文書は、作業ツリー版を絶対パスで直接読み込む。
     読込支援hookは、作業ツリー版の文書が名指す資料と役割契約を同じ作業ツリーから案内する。
     案内が稼働版の資料の欠落を示す場合は、案内の宣言元と解決先がどちらの版かを確かめ、作業ツリー版の資料を取得済みなら作業を続ける。
   - 会話圧縮後は、以降の工程を定める変更済み文書を選び、作業ツリー版を直接読み込む。
   - 呼び出し元の起動・受領契約と、その`起動対象:`に指定された`<役割名>.subagent.md`は、同一のplugin rootからペアとして適用する。
     契約は共有の`<役割名>.parent.md`、または単一の呼び出し元へ統合した節に記述する。
     入力宣言や起動設定と、呼び出し元での値の確定・検収が整合している版だけを後続の処理に使い、整合性を確認できない場合はセッション開始時の版を使い続ける（入力名や起動設定が異なる版の混在を防ぐためである）。
   - フック・会話イベントを処理するFunction hooks module・プラグインMCPの変更は、配布後にメインが`mcp__plugin_agent-toolkit_agents_server__apply_runtime_changes`で反映を予約できる。
     `targets`へ`plugins`、`agents_server`、`pyfltr`から必要な対象を指定し、ターン終了後の反映結果を確認してから新しい動作を使う。
     agents_serverを再接続すると実行中の委譲先turnが中断され、既存の復旧で同じ会話を再開する。
     権限設定と、同ツールの反映対象にないスクリプトは、この操作だけで反映済みと扱わない。
     委譲先が現行のplugin rootから自律的に解決して実行するリソースの不具合を修正した場合は、`agent-toolkit:delegation`の`references/base-contract.md`にある`是正済み資源:`の行で作業ツリー側の絶対パスを渡す。
   - 変更後の規範に従うと作業を完遂できないと判明した場合は、その変更自体の設計見直しを優先して進める。
     見直し中も確定済みの採用版を維持し、修正版を確定してから、前述の作業契約の指定と配下への案内を更新する。

## 規範を削除・縮小するときの消失確認

エージェント向け文書の削除・縮小では、編集目的によらず以下を実施する。
経緯は`docs/development/incidents-norms.md`「規範の消失と陳腐化」と`docs/development/concepts-document-writing.md`にある。
変えてよいのは構成、置き場所、表現、量であり、各規範が守ろうとしている結果は保つ。

1. 必ず残す3種を、編集の前後で照合する。
   - 硬い制約: データの破損、セキュリティ上の欠陥、取り消しの難しい操作、意図しない外部公開を防ぐ条件。
   - ユーザーが決めた方針: `docs/development/concepts.md`の決定の要旨とその本文、WIの逐語の要求。
   - 公開契約: スキルと作業の名前、`atk`のコマンドと出力、MCPのツール名、WIの本文形式とfrontmatter、役割文書の入力名と返却形式。
2. 3種以外の削除・縮小は、記述の由来にかかわらず、失われる価値と読込・保守の費用を目的とQCDで比べてエージェントが確定する。
   上位の原則（`agent-basics:writing-standards/references/quality-principles.md`）から導ける細則、同じ規則の再掲、検査・CLI・hookが強制している規則の文章は削り、削ると過去の誤りの再発が見込まれる保護は短く残す。
   条文ごとの由来の調査、統合先との対応付け、削除理由の記録は行わない。
3. 削除・縮小の方針と理由は、領域（スキル、手順書のまとまり）の単位でcommit本文に書く。
   失効（対象の実装、機能、工程、ファイルが現行リポジトリに無いこと）を理由にする場合は、識別子の固定文字列検索で実在しないことを確かめる。
4. 意味が保たれたことは、1の照合と、過去の誤りの実例と正常な例を作り替え後の文面へ文書の上で当てはめる確認で確かめる。
   委譲先やセッションを起動して挙動を試す確認は完成条件に置かず、効果は公開後の効果確認で見る。
5. 編集前に確認するのは、ユーザーの決定や明示した要求を失う場合と、エンドユーザーが観測する結果や認可・安全性の境界を変える場合だけとする。
   ユーザーの要求を保ったまま、エージェントが要求を広げて足した手段を削る場合は確認しない。
   確認の要否と手段は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
6. 削った規範に起因する誤りが再発した場合は、検査や型へ移す。
   判断が要るものだけ、失敗例を添えた短文で戻す。

## 撤去した仕組みの照合

新しい仕組み（hook、自動チェック、永続状態、配送の仕組み、規範の条文など）を加える計画を起草する担当と、その変更を実行レビューする担当は、提案が`docs/development/removed-mechanisms.md`の撤去済み機構と同じ働きをするか確かめる。
名前や名目は導入のたびに変わるため、仕組みの働き（何を補う・何を代替するか）を表す語で検索する。
導入前に検討して却下しただけの案は台帳に載らないため、同じ時点で`docs/development/design*.md`の却下案の記述も働きの語で検索する。

- 一致する項目があれば、`agent-toolkit:atk-mode/references/awi-body.md`「配置規約と導入目的の調査」と同じく過去の状態へ戻す提案として扱い、台帳の方針の所在の本文と比べて撤去理由を新しい案で満たせるかを確定してから進める
- 撤去済み機構の検索に使った語、一致した項目、判断を計画の記録（実行レビューでは走査記録）へ残す
- 仕組みを撤去する変更では、同じcommitで台帳へ項目（働き、撤去日とcommit、理由の要約、方針の所在、再導入の条件）を追加する
