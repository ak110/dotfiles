# 品質基準を変えた時の規範の追従

dotfilesで成果物の品質基準を新設・強化する担当は、条文の改訂と同じ作業で、既存成果物にも新しい基準を適用する。
WI投入担当、実装担当、実行レビュー担当、採用する公開担当が同じ判定と記録を使う。

## 対象の判定

`AGENTS.md`やスキルの規範など、エージェント向け文書の改訂のうち、成果物（コード、テスト、文書、コメント、UI、設定、CI、commitメッセージなど）が満たす基準を新設・強化する変更である。
エージェントの作業手順、報告、委譲、WI運用だけの変更と、誤字、移動、意味を変えない言い換えは対象外とし、その理由だけを記録する。

## 3つの追従

1. **dotfiles自身**: 原則9（`agent-basics:writing-standards/references/quality-principles-subtraction.md`）を既存成果物全体に当てる。
   検索式、検索結果の件数、判定と処置を記録し、読める候補は全件判定して違反を同じ変更で直す。
   同じ変更に収まらない場合は、検索式、該当一覧、判定基準を添えてdotfiles宛てのAWIへ渡し、そのファイル名を記録する。
   遡らず新規作成・改稿だけに当てるのは、本人の決定か、遡る費用と防ぐ害をQCDで比べた理由を記録した場合に限る。
2. **追従台帳**: `operate-ak110-projects` の `references/project-synchronization.md`「台帳への追記」が定める条件と様式に従う。
   記録対象なら同じ変更で既存台帳へ追記する。
   不要なら理由を残す。
   届かない環境などで手動適用するための記録であり、届く姉妹への追従AWIに代えない。
3. **姉妹プロジェクト**: `atk config repos` の登録からdotfiles以外を全て候補にする。
   先に、起点のcommit、条文の所在、元AWI名を手掛かりに `atk wi grep --state all --target-repo all` で既存のWIを探す。
   宛先と改訂が同じ活動中か採用済みのWIを本文で確かめた候補は「既存のWIで被覆」とし、現物の再調査から外す。
   残る候補は `project-synchronization.md`「同期の手順」5のとおり、`agents_server` の `explore` で現物を読み取り専用で並列に調べる。
   リポジトリごとに次のいずれかと根拠を記録する。
   - 該当: 新基準が適用され、対処が必要な現物を示す。
   - 非該当: 適用先が無いか、基準に準拠済みで対処が不要なことを、現物を挙げて区別する。
   - 既存のWIで被覆: 同じ宛先で同じ改訂を扱うことを確かめたWIを示す。
   - 未確認: 到達できない理由と再開条件を示す。
     非該当や適用済みとは扱わない。

## 工程と担当

- **起草**: 3つの追従と遡るかどうかをAWIの「反映内容と反映先」「完成条件」に書く。
  姉妹ごとの判定は統合前に処理担当が行うと書けばよく、起草時に全候補の調査は求めない。
- **選定**: 選定メインが `project-norm-designation.md`「メインが書くプロジェクト規範の指定」の工程で対象を判定する。
  対象か未判断なら `プロジェクト固有の公開後の操作の順序` に「姉妹の追従AWIの登録の後にadopt」を指定する。
  未判断だった変更が統合前に対象外と分かったら、登録0件でこの操作を終える。
- **統合前**: 実装担当が対象の判定、ローカルの検索・修正、台帳、姉妹ごとの判定、登録予定の宛先・要旨を揃える。
  AWIに書かれていない追従も補う。
  実行レビュー担当は「規範の追従:」の記録を候補版での検索の再実行、台帳、姉妹ごとの根拠と照合する。
  必要な処置や根拠が欠けていれば「既存の契約を破っている」指摘とする。
- **統合後**: 公開担当が、既存の公開後の操作として、起点のcommitと公開状態を確かめてから「該当」の宛先へだけ追従AWIを登録する。
  `project-synchronization.md`「同期の手順」7に従い、起点のcommit、変えた条文の所在、該当する台帳項目IDを追従AWIに書く。
  登録の直前にも起点のcommitで再検索し、同じ宛先で同じ改訂の追従を扱う登録済みAWIを本文で確認できた場合だけ、その宛先を除く。
  同じ起点への言及だけでは被覆とせず、別の改訂を扱うAWIは除外の根拠にしない。
  追従AWIを扱う担当は、取得する配布物に条文が含まれることを確かめてから適用する。
  公開担当は登録したAWIの実在を確かめてから延期 `adopt` する。
  登録に失敗した時は採用せず、次回も同じ起点と公開状態を検収し、未登録の分だけを再開する。
- **協調モード**: 変更の作成者が、認可済みのpushの後に同じ登録と結果の確認を終えてから作業を終える。
  pushが認可されていない場合は登録せず、候補の判定と未登録の宛先、再開に必要な公開の認可を既存の作業記録か引き継ぎに残す。
  push後に登録の失敗があれば、統合後の手順と同じく未登録分だけを再開する。

公開後の操作の指定は `agent-toolkit:atk-mode/references/process-wi-selection-format.md` の選定欄に従う。
延期する時は `agent-toolkit:atk-mode/references/lane-integration-format.md`「AWI行の終了」を使う。
公開後は `agent-toolkit:atk-mode/playbooks/process-wi-observation.md`「延期adoptと反映後の観測」を使う。
この手順の配布より前に選定したAWIには遡って適用せず、延期 `adopt` も付けない。
以前の採用分を別途見直す際は、採用記録に「規範の追従:」行が無いことを境界とする。

## 記録

`規範の追従:` で始め、その行と続く記録に次を書く。

- dotfiles自身の検索式、件数、処置（遡らない場合は理由）。
- 追従台帳の項目ID、または「台帳不要」とその理由。
- リポジトリ別の判定、登録した追従AWIのファイル名、非該当の理由、被覆するWIのファイル名、未確認の理由と再開条件。
  統合前は登録予定の宛先と要旨までとする。

対象外は「規範の追従: 対象外」に理由だけを添える。
この手順を使ったAWIは、対象外の場合も同じ行を残す。
`process-wi` では採用記録に、延期した場合は公開後の操作を終えた採用記録に残す。

協調モードでは、起点のcommit本文にその時点で確定した公開可能な判定を書く。
push後に確定した登録結果と非公開のWI名は、同じ起点commitに対応付け、認可済みの非公開の計画バンドルか作業記録にこの行を残す。
元AWIへ記録できる場合は `agent-toolkit:atk-mode/playbooks/wi-saving.md`「追記」の保存手順を使う。
非公開commit本文にこの行を残せる既存の保存経路があれば同じ記録に使う。
使える非公開記録が無ければ、確認済みの登録結果と非公開保存が未完了であることを、非公開で受け取れる委譲元へ分けて渡す。
非公開で渡せない場合は、私的なWI名は送らず、保存の再開に必要な非公開の経路を示す。
起点のcommitの書き換え、非公開のWI名の公開、推定した番号の記載は行わない。
