# 実装担当の起動と受領

メインが計画の実装単位を実行する際、本書に従ってfast担当・fix担当を起動し、エスカレーションを受領する。本書は実装担当自身が行う手順を定義しない。

## 入力

起動文の1行目で`${CLAUDE_PLUGIN_ROOT}/share/implementation.subagent.md`を指し、次を名前付き入力とする。

- 1組の計画ファイルの絶対パス。新書式は計画ファイル（メイン）と計画ファイル（詳細）の組、旧形式は単一パスとする
- 作業種別が`バグ対応`の計画では計画ファイル（バグ）の絶対パス。計画本文が参照する素材がある場合はその絶対パス
- 用途、絶対パス、管理対象領域の絶対パス、完全OID、作成主体、所有主体及び回収対象を持つ専用worktree
- AWI起因の場合は受領順を保持したAWIファイル名一覧
- 複製元と対象外worktree

実装レビュー指摘管理表の絶対パスは、受領した計画ファイル（メイン）と`agent-toolkit:plan-mode`の計画ファイル基準が定めるファイル名・配置から確定する。
計画レビューの指摘管理表は実装担当へ渡さず、実装レビューにも用いない。同表は計画の確定までに用いる記録であり、実装担当の入力ではない。
計画レビューの経緯が必要になる事象が生じた場合だけ、当該事象を示して同表の絶対パスを追送する。
確定した絶対パスと`implementation-review`の`track`を実装担当及び実装レビュー担当へ渡す。

新旧の判別は対応するdetailファイルの実在で行う。新規計画メインの固定H2順と旧見出しの読み取り互換は同基準が定める。
1つのレーンへ複数の計画ファイルをまとめず、現在worktreeを実装対象にしない。

実装担当を起動する前に、`${CLAUDE_PLUGIN_ROOT}/share/implementation.subagent.md`の`## 入力`が列挙する必須入力が、当該起動の担当種別についてすべて起動文にそろっていることを確認する。`fix担当`では元の実装入力、同じworktreeの現行状態とエスカレーション内容を確認の対象へ含める。`CI修正担当`では、起動文へ直接記載するCI記録又は統合後検証失敗記録に、原因分析結果、修正認可根拠、対象の検証結果、変更目的、対象、公開契約及び入力計画の7項目がそろっていることを確認する。記録自体を絶対パスとして扱わず、絶対パスで示す他の入力だけの実在を同じ時点で確認する。いずれかが欠ける場合は実装担当を起動せず、欠けていた入力項目を呼び出し元へ返す。

## 実装単位の実行

計画の実装単位表から、説明的な実装単位名、目的、先行依存、統合順及び近接検証を取得する。ベースコミットは表示だけに用い、レーン割当又は着手可否の条件にしない。同じ計画ファイルに属する実装単位は、同じ専用worktreeで依存順に実装し、同時に1つの実装担当だけを置く。実装単位の分割規則は`agent-toolkit:plan-mode`の計画ファイル基準が定める。

各単位の起動前に、変更する定義、その直接消費側、契約テスト及び生成・配布物のうち当該commitの正式な近接検証に必要な対象が同じ単位へ含まれることを照合する。
先行するcommitだけで後続単位の着手前に正式な近接検証が成功しない分割は受理せず、計画担当へ差し戻して実装単位を再分割する。

レーンへ割り当てた専用worktreeを計画の実装単位と統合順に照合する。作成主体、所有主体、管理対象領域の絶対パス及び回収対象の記録がそろわない場合は受理せず、一覧にないworktreeを作成又は補完しない。

最初の単位へ着手する直前に、計画ファイル（詳細）の`### 実装担当のモデル区分`の`判定`を読み、次の表のとおり`agents_server.start`へ渡す`model_type`を確定する。本表を当該対応の正本とする。

| `判定`の値 | 渡す`model_type` |
| --- | --- |
| `可` | `execute_fast` |
| `不可` | `execute` |
| 見出しが無い、又は`判定`の行が無い | `execute_fast` |

`判定`が`可`と`不可`のいずれでもない値を持つ場合は、担当を起動せず計画担当へ差し戻す。
`判定`が`不可`の場合は同節の`根拠`も読み、不成立の条件が対象ファイル若しくは内部識別子の追加探索、
実装内部の設計判断又は近接検証の合否を確定する追加調査のいずれかに限られることを確認する。
当該不足が対象の追加探索である場合は、探索範囲が確定済みの目的と適用範囲に属する直接影響範囲へ限定され、
探索で特定した対象を変更対象へ加えてよいことが同じ`根拠`に記載されていることも確認する。
利用者が観測する契約、認可又は計画の適用範囲の不足を根拠とする場合は、担当を起動せず計画担当へ差し戻す。
確定した`model_type`を保持して担当を新規起動し、担当種別は`fast担当`とする。
以降の単位は、現在担当がfast担当なら同じthreadへ継続して指示する。継続の可否及び継続不能時に渡す検収済み状態の範囲は`agent-toolkit:delegation`の経路選択契約に従う。

起動文の構成と列挙形式は`agent-toolkit:delegation`のSKILL.mdの`## 送信`が定める。
必須入力の項目は本書の`## 入力`と`${CLAUDE_PLUGIN_ROOT}/share/implementation.subagent.md`の`## 入力`が列挙するものとし、両節の記述を起動文へ転記しない。
両節が列挙しない次の2項目を同じ形式で加える。

- `権限`: commit可、ffマージ可、所有資源の回収可、作業対象リポジトリへのpush不可。`agent-toolkit/rules/02-agent-operations.md`の`対象リポジトリとキュー管理リポジトリの区別`節のとおり、`atk`がキュー管理リポジトリへ行う反映は当該権限の対象外とする
- `git操作の制約`: 当該起動で許すgit操作の範囲

対象ファイル集合と近接検証が独立する連続単位だけは1回へまとめてもよいが、commitと単位IDの対応を維持する。
起動前に、追加指示へ含める検証コマンドを計画ファイル（詳細）の実装単位表にある当該単位の近接検証へ照合する。追加指示は近接検証コマンドの実行方法と環境固有の回避手順だけを補足でき、計画全体の完了条件と後続の実装単位の成果に依存する検証を当該単位の近接検証へ追加しない。fast担当、fix担当又はレビュー修正担当を起動する場合は、いずれも追加指示と実装単位表を照合する。両者が異なる検証範囲を指す場合は、起動前に近接検証の範囲を確定する。

fast担当からエスカレーションを受領した場合は、`model_type="execute"`での起動を選ぶ。`agent-toolkit:delegation`の経路選択契約が定める継続条件で、継続か新規起動のいずれかを確定する。同一threadを継続する場合は、担当種別を`fix担当`へ切り替える旨とエスカレーション内容を継続本文へ含める。新規起動する場合はfast担当の終端を確認し、新規threadとして同じworktreeへfix担当を1件だけ起動する。元の実装入力、同じworktreeの現行状態、エスカレーション内容及びfast担当の終端確認を渡し、担当種別を`fix担当`として明示する。いずれの場合も同じworktreeの書込主体は1つに保つ。fast担当以外のエスカレーションとfix担当の続行不能では、メインが内容を確認して回答だけを同じthreadへ返し、ユーザーの判断を要する事項は確認経路へ送る。

fix担当が実装単位を完了した後に残りの単位がある場合は、最初の単位の開始前に保持した`model_type`と現在のthreadの`model_type`を比較する。一致する場合は同じthreadの担当種別を`fast担当`へ戻して次の単位を指示する。一致しない場合はfix担当の終端を確認し、検収済みの先行commitと残りの実装単位を新規fast担当へ渡す。

各単位の現在担当を保持し、全単位の完了後に生成同期と最終検証を最後の担当へ指示する。同worktreeのHEADをレビュー対象とし、`${CLAUDE_PLUGIN_ROOT}/share/implementation-review.parent.md`に従って`review_contract`を生成してから、単一の実装レビューへ進む。
