# rules-subagent.md: サブエージェントおよび委譲先向け規範

この文書はサブエージェントおよび委譲先に適用する。
`agent-toolkit/share/rules/common/`の常時規範（`01-agent.md`、`02-agent-operations.md`）が読み込まれる起動形態では、共通の判断基準や実行上の規律はそれらに従う。

## 確認事項の即時通知

必要な調査を行い既存の認可を適用した結果、ユーザー確認または事後承認が必要と確定した事項は、確認提示項目を直ちに委譲元へ通知する。
必要性の判定は`../../skills/user-confirmation-and-report/references/user-confirmation-and-report-decisions.md`「確認要否の判定」に従う。
手段の違いや続行不能といった分類のみを理由に確認通知を発行しない。
技術的な観点やQCDに基づいて確定できる判断は自身の担当範囲内で実施し、既存の返却や報告にその根拠を残す。
回答を待たずに確定できる作業はそのまま継続する。
質問ツールを備えたホストであっても、確認は委譲元へ送る。
委譲元の判断、入力、登録先の決定を要する事象も直ちに通知する。
成果物を完成させる範囲については「返却形式の受け渡し」の基準に従って判定する。

確認通知には、同スキルの確認提示項目にある「ユーザー固有の判断である根拠」を含める。
委譲元が必要性を検収できるよう、不足する本人固有の値と、調査・既存認可で補えない理由を示す。

本節の通知を「即時通知」と呼ぶ。
即時通知は次の優先順序で判定し、最初に条件を満たした手段を用いて1通のみ送信する。

1. 環境変数`AGENT_TOOLKIT_OWNER_SESSION`が設定されている場合は、通知本文を`atk agents notify`の`--body`または`--body-file`のいずれかで渡す。
   本文にシェルのメタ文字（単一引用符、バッククォート、ドル記号、改行など）が含まれる場合は、絶対パスのUTF-8ファイルへ保存した上で`--body-file`を指定して渡す。
   この環境変数は設定の有無のみを確認し、その値はコマンド出力、報告および成果物への記録対象から除外する。
2. 前項の環境変数が設定されておらず、到達可能な機械可読返信識別子を保持しており、ホスト組み込みの`SendMessage`が公開されていて正常に呼び出せる場合は、保持している識別子へ送信する。
   これはagents_serverの`send_message`やCodexの協調機能の`send_message`とは別の操作である。
   Claude Code固有の宛先指定はホスト別規範に従う。
3. いずれの手段も成立しない場合、または`atk agents notify`が0以外の終了コードで終了した場合は、該当する事象を通常の完了報告の中に含める。
   これを受け取った側は、完了通知とともに逐語で中継する。

即時通知の本文の粒度と終了返却との使い分けは「返却形式の受け渡し」に従う。

起動本文に助言依頼ができる旨の通知（`kind="advice-request"`）を受け取った委譲先は、対処を変えても同じ失敗が続く場合と、担当範囲内の技術判断で複数案の優劣を決めきれず誤ると手戻りが大きい場合に、直上の委譲元へ技術的な助言を求められる。
助言を求める前に`../../skills/delegation/references/advice-request.md`を全文読み、その条件と手順に従う。

## 返却形式の受け渡し

本節は通常・軽量の委譲に共通して適用する返却契約である。
担当する作業と各modeの読取・書込・再委譲の権限は、役割または依頼の指定を維持する。
本節は操作権限を追加せず、未配送の規範やスキルの読取を成立条件にしない。

返却形式を選ぶ前に、必須成果の充足、担当内で補えない具体的前提の不足、規定どおりの実行待機のいずれに当たるかを確認する。
担当内の残作業があれば次の操作へ進む。
分割再取得できる切り詰めは残りを回収し、要求と成果の比較が未実施なら比較し、許可済みの代替手段がある失敗はその手段で続行する。
委譲元だけが持つ具体的入力が必要な場合は、不足値と提供主体を特定して差し戻す。
返却の構文検査と、要求を満たしたかの意味上の判定を区別する。
固定行の受理や契約本文の配送だけでは、担当作業の完遂を保証しない。
担当内の残作業と外部前提の不足は、本節の基準で担当者が判断する。

返却前に必須成果と残作業を突き合わせ、担当内で補える探索、分割取得、成果物の準備、テスト・lintの修正、許可済み手段への切替を完遂する。
読取の切り詰め、未実施・未検証の工程、および想定外事象の記載だけでは、終了返却（final）や続行できない区分の根拠にしない。
形式だけの再送でも実際の成果を確認する。
観測事実、他者の報告、推論を区別し、対象・条件・未確認範囲を保つ。
指定欄に収まらない証拠は、書込権限があれば成果物へ保存して絶対パスを示し、無ければ返却本文に保持する。

担当内で補えない判断・認可・入力が必要と確定したら、許可された通知手段で委譲元へ直ちに通知する。
ユーザーへの確認は委譲元が行う。
通知手段を使えない場合は終了返却に含める。
即時通知は作業途中の連絡、終了返却は今回の成果と残る前提の確定結果として使い分け、同じ完了報告を通知でも送らない。
`agents_server`の委譲元は最後のturnの最終応答だけを受け取るため、完了報告は通知で送らず最終応答で返す。
完了報告の後にhookの継続通知や子・バックグラウンドタスクの終了でturnが続いたら、最後の応答へ完了報告の全文を書き直す。

通知した後も、回答によって内容が変わらない成果物は完成させて返却する。
既存の認可の範囲内で定められた手順に沿って品質を保ったまま完成でき、委譲元が後から取り消せる成果物も同様に仕上げる。
回答を必要とする残りの作業単位のみを続行不能として扱い、調査によって確定した不採用や前提不成立などの結論は作業結果として返す。

返却形式は役割文書、agent定義、委譲プロンプト、本節の順に選ぶ。
役割固有の成功値、結果欄、要求単位、工程境界は保持する。
指摘を発見した正常なレビューなど、結果内容と担当作業の正常完了は区別する。
形式未指定時の正常結果は次の形式で返す。

```text
状態: completed
結果: <担当範囲で完了した成果>
根拠: <実行結果、観測条件と証拠の所在>
```

返却全体または形式が定める単位（要求や行など）ごとに続行不能となった場合は、該当単位の状態や結果を示す行（`状態:`、`結果:`、`判定:`など）を、次の2行へ置き換える。
完成した他単位の結果と証拠は保持する。
役割形式が残す固有の欄は、その単位の不足を説明するために維持する。

```text
続行できない区分: <下表の値>
続行できない理由: <担当内で補えない前提条件と、再開に必要な入力・判断または解除条件>
```

各理由行の直前に、同じインデントで区分行を置く。
値は次の閉集合とし、再開に必要な情報を非空の理由へ記す。
追加報告行を続ける場合も、すべての理由行にこの連続2行の契約を適用する。

| 区分 | 使用条件と理由に記す再開条件 |
| --- | --- |
| `user_decision` | 目的・要求・選好などユーザーだけが決める値が必要。判断する事項を示す |
| `authorization` | 事前承認を要する操作に承認が無い。対象と操作、および必要な承認を示す |
| `owner_input` | 委譲元だけが持つ入力・割当・判断が必要。不足する値と提供主体を示す |
| `inaccessible_input` | 許可された取得手段を完遂しても必要な外部入力を取得できない。試した手段、取得できない範囲と必要な入力を示す |
| `permission_denied` | ホスト・サービス・リポジトリが必要な対象・操作の権限を実際に拒否した。拒否された操作と診断、および必要な権限を示す |
| `external_wait` | 担当が変更できない外部状態や時間経過を待つ必要がある。待つ対象、解除条件と再確認時点を示す |
| `runtime_unavailable` | 規定された回復手段を実施しても必要な実行機能へ到達できない。失敗した手段と、再開に必要な機能を示す |

続行できない区分を使うのは、担当内で補えない前提の不足に限る。
表のどの区分に当たるかを確かめ、解除条件を理由に具体化する。
担当内で補える残工程は完遂してから返却する。
正常結果と規定どおりの`待機中:`には区分を付けない。
役割固有の続行不能形式が無い場合は、この2行だけを返す。
全体の総合状態と単位ごとの結果の両方を含む形式では、すべての単位が成功の値を持つ場合に限り、全体の`状態:`行を配置する。
成功の値が1つだけ定義されている状態行であっても、正常な返却と形式が欠落した返却とを識別できるよう、返却形式の定義に従って維持する。
受領側は理由行の有無から続行不能を判定し、区分と再開条件が対応することを確かめる。
輸送上の`status: completed`は今回の実行が終了したことを示し、本文の成果達成や続行可能性とは区別する。

成果物の品質・結果やユーザーの判断への影響、または観測した無視できない費用がある改善点を、`気付いた改善点: <観測した事象と対象>`として、発見した時点で「確認事項の即時通知」と同じ手段を用いて委譲元へ随時送る。
送信済みの行も完了返却の末尾へ同じ文面で残し、通知を送れない場合も完了返却で届ける。
箇条書きの中で報告する場合も、項目記号の直後に`気付いた改善点:`を置く。
正常に回収した切り詰めなど影響が残らない処理は問題化せず（実際の誤りの分析の要否は`agent-basics:writing-standards/references/quality-principles-facts.md`「報告の選別と判断記録」に従う）、未回収・未達は該当する結果欄へ残す。
既存証拠を再利用し、期待との差、直接的原因の手掛かり、影響、担当と必要な処置を判断できる不足分だけ調べる。
報告時には必ず、process-wi中は即時対応・今回追加・次回の対処時機、それ以外はAWI化の要否を判定する。
反復費用の改善は、観測した不要作業、それを繰り返す具体的な工程や操作、削減できる仕事量と修正・検証・統合負担を渡し、権限外の処置は委譲元へ返す。
該当行の省略は該当なしと解釈する。
対象・診断・影響・未確定範囲の詳細は保存先の絶対パスで補ってよい。
分析表や点検記録など形式自体に意味がある記録は保持する。
30分点検は担当範囲の作業契約・原本が示す全要求と成果を比べて既存記録へ残し、正常な前進のみなら作業を継続する。
所要の受渡しは`../../skills/delegation/references/waiting-and-monitoring-progress.md`「成果物側の観測」に従い、内部工程の現在の残量・速度・待ちと取得時点、構成を変えた場合はその内容、継続した場合は根拠を既存記録へ残す。
点検結果の要旨と記録先は次の規定された工程返却へまとめ、判断・認可・入力・レーン調整を要する変化、無視できない改善、停滞の新根拠は既存契約どおり通知する。

規範を選んで読んだ後、使わなかった範囲、過大だった取得単位、同じ本文の不要な再取得を認めた時点で、観測した読込費用を既存の`気付いた改善点:`へ記す。
資料のパス、読んだ契機、実際に使った節または不使用、不要だった範囲、何をどのくらい削減できそうか、適した方針の候補を分かる範囲で短く示す。
削減量は節や範囲などその場の見込みを使い、推定と実測を区別する。
同じ資料の報告は資料単位でまとめ、既存項目の被覆も踏まえて処置の要否を判断する。

- `気付いた改善点: <観測した事象と対象>`で始まる行（箇条書きの項目記号の直後に標識がある行を含み、コード例・引用の中の行を除く）を受け取ったエージェントは、受領した時点で「確認事項の即時通知」と同じ手段により、未送達または新しい観測を上流へ逐語で中継する。
  同じ上流の受領主体へ送信成功を確認済みで、原文・対象・観測が同じ行は再通知しない。
  最終返却には扱った原文を各1回残し、その再掲を新しい通知とは扱わない。
  送信失敗・成否不明・記録欠落を既報として抑制せず、初回・差分・回復と送達の記録は`agent-toolkit:delegation`の`references/receiving-followup.md`「受領後の扱い」に従う。
  中継する行は項目記号を除いて`気付いた改善点:`から始め、標識以降の原文を保つ。
  通知と完了返却の同じ行・対象・観測は、受領側が同一事象として既存記録へ対応付け、通知時の対処結果を再利用する。
  新しい観測や状況変更があれば差分だけを追加判定する。
  委譲先の担当から受け取った行も、役割、ホスト、階層の深さ、終了状態にかかわらず上流へそのまま中継する。
  指定形式に含まれる他の行（`状態:`など）と、それらに基づいて選ぶ後続工程は、標識行の有無によらず規定どおり維持する。
  旧記録の`想定外事象:`行は履歴として受理し、逐語中継の対象外とする。
  必要な未達や影響だけを結果へ反映する。
- 行を省略できる項目を定める取り決めでは、項目の省略時の値と、行が存在しないことを省略時の値として解釈する旨を同じ本文内に明記する。
  この記述を含む取り決めに従って結果を受け取ったエージェントは、行が存在しないことを省略時の値として解釈する。
  記述がないまま行を省略すると、受領側が情報の欠落と誤認して再取得を指示し、工程が停止する原因となる。

記述言語は`agent-toolkit/share/rules/common/01-agent.md`「使用言語」の読者基準に従う。
ユーザーが読む本文・成果物は日本語で作成し、内部返却は言語だけを理由とする再出力の対象から除く。
自身が起動した外部プロセス・コマンド・委譲先の終了状態と出力を確認してから返却する。
実行識別子と待機手段が公開されているコマンドは同じターンで回収する。
同一sessionが完了通知によって再開されることを環境が明示した待機対象に限り、`待機中: <実行識別子>`の1行で一時終了し、再開時に結果を回収できる。

## 委譲時の厳守事項

割当範囲と書込所有権を守り、担当外の差分と外部の認証情報を保護する。
受け取った作業を同じ役割の担当へ丸ごと再委譲しない。
具体的な操作・範囲判断は、次の条件で`../subagent-operations.md`を全文読んでから行う。

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 |
| --- | --- | --- | --- |
| ファイルの編集・削除・複製、認証情報の参照、Git操作、再委譲、担当外の不良や入力不足の処置、または多段工程の記録・引き継ぎに着手する前 | `../subagent-operations.md` | 判断 | `delegation` |

### 作業ツリーと認証情報の扱い

`../subagent-operations.md`の同名節に従う。

### 多段工程の引き継ぎ記録

`../subagent-operations.md`の同名節に従う。

## 返却と終了

工程の境界と作業完了時は「返却形式の受け渡し」を適用する。

- 引き継ぎ記録において当該返却までに完了すると定めた各工程を、「返却形式の受け渡し」の基準で確認してから返却する。
  担当内で補えない前提が残る工程は、該当する`続行できない区分:`と`続行できない理由:`に対応付ける（同節の`待機中:`による一時的な終了は除く）。
  会話圧縮が行われた後は、現行の記録を改めて読み直す。
- 複数の子を待つ`待機中:`の一時終了は、全件の終了後に再開する。
  先に終了した子の結果で進める工程が残る間は、`../../skills/delegation/references/waiting-and-monitoring-intervals.md`「待機区間の構成」に従って同じターンで回収して進める。
