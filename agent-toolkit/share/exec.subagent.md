# レーン実行タスク

`agent-toolkit:process-wi`の1レーンを、必要な計画の起草から統合まで同じthreadで担当する。担当種別は`レーン担当`、`レビュー修正担当`または`CI修正担当`とする。
計画と実行工程の責務と出口は`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`に従う。
本タスクの完了報告と成果物は日本語で書く。返却値は指定どおりに返す。

## 読込表

次の時点または条件が成立したら、対象の操作の前に同じ行の資料を全文読む。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 計画の起草前、計画なしで実装へ着手する直前、レビュー修正担当とCI修正担当が修正へ着手する直前 | `agent-toolkit:delegation`の`references/routing.md` |
| 計画を起草するか既存計画から再開する直前 | `agent-toolkit:process-wi`の[references/lane-planning.md](../skills/process-wi/references/lane-planning.md) |
| 初回実装（`CI修正担当`では修正）に着手する直前と、変更範囲の検証（履歴統合後の再検証を含む）を実行した後 | `agent-toolkit:check-execution`の`references/diagnostics.md` |
| 変更範囲の検証が失敗したとき | `agent-toolkit:process-wi`の[references/lane-verification-failure.md](../skills/process-wi/references/lane-verification-failure.md) |
| `実装なし`またはレビュー収束後にメインから統合指示を受領したとき | `${CLAUDE_PLUGIN_ROOT}/share/lane-integration.subagent.md` |

## 入力

```text
必須入力名: 担当種別,引き継ぎ記録先
任意入力名: 選定結果の出力先ファイル,レーン識別子,固有指示,上流投入結果,再開位置,レビュー指摘管理表,CI記録,環境構築
```

`レーン担当`は`選定結果の出力先ファイル`から`レーン`が`レーン識別子`と一致する`選定`の項目だけを読み、AWIファイル名、順序、`鮮度`、`担当モデル`、`プロジェクト規範の指定`、上流投入の3行、`プロジェクト固有の公開後の操作の順序`を入力とする。書式と省略時の値は`${CLAUDE_PLUGIN_ROOT}/skills/process-wi/references/selection-format.md`の`## 選定結果の書式`に従い、省略された行は省略時の値として扱う。該当項目が無い、同じAWIが重複する、必須フィールドが形式外の場合は推測せず続行できない理由を返す。

計画作成と実装の前（計画なしでは本文を読んだ時点）に、AWI本文が明示した担当とモデルの組を選定結果の`担当モデル`と比べ、一致しなければ下位担当の起動で補わず、WIファイル名、本文の組、選定結果の値を`続行できない理由`で返す。
`担当モデル.実装担当`の値は自身の担当範囲の一部を任せる下位実装担当（「操作区分」の内部群など）の`model_type`へ渡す。比較と記録は`agent-toolkit:delegation`の`references/runtime-routing.md`「工程別モデル設定」の担当モデルの段落に従う。自身のレーン全体は自分のthreadで担い続ける（別の`レーン担当`へ任せない）。実行レビュー担当の起動と`統合開始`の送付はメインが行う。

要求単位の由来は`agent-toolkit:wi-standards`の`## 由来と承認`に従い、計画の起草時に`atk wi show`のAWI本文とfrontmatterから判定する。判定結果は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`の書式で計画の`由来`欄へ書く。計画の確定後は実装と統合で由来を再判定しない。その後は計画で確定した採否と終端区分を用いる（由来の確定時点）。
計画を省くレーンは同じ判定の結果を引き継ぎ記録へ残す。ユーザーが報告した不具合を既存実装で充足済みとする場合は、`plan-file-standards.md`「実施内容」が定める調査（呼び出し手段、操作順、結果、報告時点との差）を行い、操作、観測結果、相違、未特定の範囲を同じ記録へ残す。

`レビュー修正担当`は同じthreadの継続なら保持する選定結果を引き継ぐ。新しいthreadでは`再開位置`の計画ファイル（`計画なし`なら引き継ぎ記録）と引き継ぎ記録の全計画の進捗、`レビュー指摘管理表`を読み、両者が同じ計画に属することを確かめる。
`環境構築`が`レーン担当が実行`なら、対象リポジトリの開発手順が定める環境構築を実装の前に行う。その他の値と不在では準備済みとして扱い、併記された判定をそのまま用いる。
`CI修正担当`は代わりに、原因分析結果、修正認可根拠、対象の検証結果、変更目的、対象、公開契約、入力計画の7項目を持つ`CI記録`を受領する。

対象worktreeは`cwd`、複製元と対象外worktreeはGit共通ディレクトリとlinked worktree、プロジェクト規範は`cwd`で実行ホストがロードする指示ファイルから解決する。対象リポジトリではcommitとffマージを行うが直接pushは行わない（委譲元が別工程で行う）。書き込み先は対象worktreeに限り、対象外worktreeと複製元は読み取り専用とする。private-notesでの計画保存とWIの状態変更は`atk`の通常の公開を用いる。委譲プロンプトの操作禁止がこの通常公開に及ぶか確定できない場合は委譲元へ確認する。

## 操作の直前に判定する前提

次の前提は対象の操作の直前に判定する。着手時に読んだだけでは、満たさないまま操作して遮断される。

- 既存ファイルの全体上書きと文字列置換の直前: 対象の現行本文を取得する（自ら書いたファイルも含む）
- 編集の直前: プロジェクト規範が定める、編集対象のパスに対応する必須スキルを起動する
- 変更範囲の検証の直前: 計画の`## 検証`の`変更範囲の検証`行（計画なしでは引き継ぎ記録の検証コマンド）から取得する
- 受入シナリオか完成条件を手動で観測する直前: 受入シナリオ検証（`agent-toolkit:check-execution`の`references/acceptance-scenarios.md`）の起動条件で対象を起動する。MCPで記録を取得できない有限終了のコマンドは、対象worktreeで`atk run-command [--cwd DIR] [--timeout SECONDS] -- COMMAND [ARG...]`で実行する。返却の`record_path`はcwd・argv・`git_head`・`git_status`・終了状態・両出力パスを保持するため、その絶対パスと出力の保存先を検証結果と未判定検証記録の`evidence`へ渡す。保存失敗の非0を確かめ、記録の無い観測は保存する形でやり直す（実行レビュー担当は未保存の観測を補えない）。PATH上のコマンドなどインストール済みの別実体を実行した観測は、その実体の版を記録する

## 操作区分

| 担当種別 | 計画起草 | 実装・修正 | commit | 統合 |
| --- | --- | --- | --- | --- |
| レーン担当 | 再開位置が`なし`の場合に作成要否を判定する | メインの判断を待つ場合は`実装開始`受領後、待たない場合は通知後に実施 | 可 | 統合指示の受領後に実施し、統合を完了するまで同じthreadが担当する |
| レビュー修正担当 | 実施しない | 受領した指摘だけを修正 | fixup commit可 | 実施しない |
| CI修正担当 | 実施しない | CI記録が認可する失敗だけを修正 | 可 | 実施しない |

この許可は委譲プロンプトや追送を受けた後もそのまま保つ。レビュー修正の`autosquash`と`lane-integration.subagent.md`「マージありの統合」の統合先HEADへのrebaseは別の操作であり、一方への禁止はその操作だけに適用する。担当種別に必須の操作を委譲プロンプトか追送が禁止する場合は着手せず、制限の文面と必須の操作を続行できない理由として返す。
`レビュー修正担当`として起動された担当が統合指示を受領した場合は、`レーン担当`へ戻って統合を実施する。

統合指示の受領後は`lane-integration.subagent.md`「公開統合操作」の`atk lane integrate`へ所有登録、レビュー対象HEAD、今回の全計画・WIと検収済み採否を渡す。資源、Git統合、最終化と選定状態の定型操作は同じCLIへ集約し、担当は独立文脈レビューの受理、完成条件判定、診断と延期の判断を持つ。失敗後は保存済み進行と同じ入力で再開する。

同じ専用worktreeで書込を分担する場合は、`agent-toolkit:delegation`の`references/mandatory-rules.md`「作業ツリーの保護」に従う。書込先が交わらない担当を並列に、または1つの担当を直列に置き、commitと作業ツリー全体へ作用する操作はレーン担当が全担当の終端後に行う。担当種別の切替は同じthreadの継続であり、書込の所有者は変わらない。
担当ごとのcommitや書き換えを伴う検証が要る場合と、書込先を事前に確定できない場合は、別branch・別worktreeの一時的な内部群を使う。レーン担当がファイルの所有表を確定し、レーンbranchの確定済みcommitから群ごとの別branch・別worktreeを作成する（各worktreeの書込担当は1つ）。群の粒度と同時起動数は固定の分割数や上限を置かず`agent-toolkit:delegation`の`references/routing.md`「委譲単位の確定」で選び、契約で結び付く出力元とテスト期待値は同じ群へ置く。レーン担当は各担当の終端、clean状態、群のcommit・差分・検証（実行した版とともに）を確かめ、レーンbranchへ順に統合し、取り込みごとに前後のHEADを`agent-toolkit:commit`の`SKILL.md`「WI実装commitの対応」の手段で記録する。統合後に対象語の残存、生成物と直接影響範囲の同期、変更範囲を検証してから一時worktreeとbranchを回収する。群の検証記録はOIDが変わっただけでは破棄せず、統合で結果が変わり得る行と統合で初めて成立する観測だけを取り直す。内部群は別レーンや別要求の担当にせず、計画、検収、commitの対応記録、統合とメインへの返却はレーン担当が所有する。

## 処理中の処理対象WIの追加の指示

処理中に追加WIを割り当てられても、現在工程を完了させてから、turnを終えずに追加WIの計画作成要否の判定へ進む。現在工程の境界の固定形式の各行は、追加WIの最初の工程境界の本文の先頭へ置く。ただし現在工程の結果がメインの後続工程の入力になる場合（`実装完了`の後の実行レビューなど）は、追加WIへ進む前にその固定形式を`atk agents notify`で送る。
メインの判断を待つ`計画作成完了`と`計画なし準備完了`は返却として届けて待つ。非待機の`計画検査完了`は`atk agents notify`で送ってturnを終えずに`## 実装`へ進む（`マージなし`では統合指示を待つ）。`agents_server`の委譲先では返却がturnの終端になるため、非待機の境界を返却すると実装が止まる。
確定済みの計画は凍結したまま保ち、指示は受領順に扱う。計画を作成した境界ごとに、その計画の絶対パス、対応AWI集合、保存状態を引き継ぎ記録へ累積し、統合入力には全計画を順序付きで渡す。

## 実装

`実装開始`を受領した`レーン担当`、非待機の`計画検査完了`を通知した`レーン担当`、修正入力を受領した他の担当種別が実施する。本節が計画の進捗ログへ記録する内容は、計画なしでは引き継ぎ記録へ記録する。

- 初回実装（CI修正では修正）の直前に、`agent-toolkit:check-execution`の`references/diagnostics.md`が定める基準版の完全OIDを記録し、レビュー修正と履歴統合の後も同じ基準版を使う。各検証の後は同書の共通基準で診断と警告を判定し、比較した版と、残す診断の意味・影響・帰属・理由を検証結果と進捗ログへ残す
- 実装契約: 計画を持つレーンは`## 要件・外部仕様`を契約とし、`## 実施内容`と`## 変更履歴`の対象・範囲・外部可視の結果を認可範囲の上限とする。計画なしのレーンはAWIの要求と完成条件を契約とし、引き継ぎ記録で確定した採否と対象の内側だけを変更する。計画ファイルの扱いは計画凍結（`plan-file-standards.md`）に従う
- 変更前に作成規範を読み、担当ファイルと直接影響範囲だけを変更する。生成元を変更したら生成・配布手段を追随させる
- `レーン担当`は版数更新コマンドを実行せず、bump種別と根拠を計画か引き継ぎ記録で公開工程へ渡す
- 初回実装では、`lane-planning.md`「計画の起草」で選んだ最も近い既存実装との契約・構造の一致と、入力値・時間経過・操作順・保持状態・反復の境界を確かめる。採用案を`前提を疑う観点`から反証し、責務の移動、既存機構や上流への統合、削除・簡素化で満たせるなら恒常的な複雑性が小さい案を採用する。不具合対策では`agent-toolkit:review-standards`の`references/reviewer.md`「初回レビュー」の`前提を疑う観点`に従い、観測した害の消滅と呼び出す側の修正案も比べる
- エージェント向け文書は、メインが`実装開始`で名指ししたパス（新規作成先・移動先を含む）だけを編集する。追加が要る場合は編集前に追加するファイル名だけをメインへ返し、追送を受けてから編集する
- 実装中に要件・外部仕様水準の判断が新たに生じたら実装を止め、現在の結論を計画があればレビュー指摘管理表へ、なければ引き継ぎ記録へ記録する。ユーザー選好か認可範囲の変更を要する場合は`agent-toolkit/share/rules-subagent.md`「確認事項の即時通知」に従う
- 完成条件を変更・除外して残りをadoptする判断が要る場合は、対象条件、外す技術的根拠、否定したユーザー判断（`agent-toolkit:review-standards`の`references/exec-review-recording.md`「失効の根拠」）の有無・所在をメインへ通知する。返された判断から再開し、エージェント由来であることだけを失効の根拠にはしない。メインの技術判断を受けたら、その完成条件を扱うレビュー指摘管理表の行（無ければ`atk review-table add`で加える）へ`atk review-table respond`の`--no-response-reason-file`で記録する。記録には`根拠の所在:`ラベルの行へ`メインの技術判断`、対象AWIのファイル名と完成条件、外す根拠を書く
- 最後の実装commitの前に、差分を`agent-toolkit:writing-standards`の`references/design-heuristics.md`「設計品質の劣化確認」で評価して観点ごとの結論を検証結果へ残し、認可内の劣化は同じcommitで構造を整理する。書込対象の追加が要る場合は対象と理由をメインへ返す
- 計画の`### 受入シナリオ`は受入シナリオ検証（`workflow-phases.md`）で検証し、計画なしでもWIの完成条件を公開された呼び出し手段で検証する。新規テストは各シナリオへ対応させ、`検証結果`にテスト名と合否を記す
- 完成条件か受入シナリオが名指しした観測手段（コマンドの出力、画面、hookの通知など）を実装が生まない場合は、代替観測で埋めず実装の不足として是正する。完成条件自体の変更が要るなら採否の変更として「確認事項の即時通知」に従う。環境の不在など実装が決めない理由で観測できない場合は、実施できた範囲と観測に要る後続工程を記し、残存する状態が観測を妨げるなら、その状態の生成主体・起動元・起動契機も調べて未確定範囲とともに記す
- 公開された呼び出し手段を置換・廃止した場合の完遂は`agent-toolkit/rules/01-agent.md`「QCDと3段判定」に従う。存在確認、mock、部分的なprobe、旧手段を併用した成功は検証結果に使わない
- Git管理外のファイルは、各ファイルの最初の変更の直前に現行本文をmanaged-temp（`agent-toolkit:managed-temp`）へ複製し、元と複製の絶対パスの対を引き継ぎ記録へ残す（実行レビュー担当が変更前後を比べるため）
- 変更範囲を検証する前に（計画なし、レビュー修正、CI修正も）直接影響範囲を確定する
  1. 外部から観測できる文言か挙動を変えた場合は、`plan-file-standards.md`「要件・外部仕様」の直接影響範囲の段落が定める検索語を固定文字列で個別に検索する。値を組み立てる生成コードでは、変更前の実行結果から旧値を列挙するか、生成元を使う全テストを実行する
  2. 検出した直接影響範囲の実装ファイルに対応するテストを変更範囲の検証へ加える。加えない場合は理由を残す
  3. 計画の起草で確定した検証対象を実装の現物と比べ、`agent-toolkit:check-execution`の`references/verification-scope.md`の類型で外れていた対象を加える
  4. 検索語、検出結果、採否、テスト実行の採否、検証対象ごとの結果と除外理由をmanaged-tempへ保存し、`検証結果`から参照する

  検索は語ごとに`atk run-command --cwd <対象worktreeの絶対パス> --timeout <有限秒数> -- git grep -n -F -e '<検索語>' -- .`（Git追跡外は子argvを`rg -n -F -- '<検索語>' <対象の絶対パス>`）で保存する。exit 1は不一致、起動失敗・timeout・保存失敗・その他の非0は検索失敗であり、不在の根拠にしない
- ユーザーがAWIの`## ユーザーコメント`かUWIの`## 回答`へ処理側に宛てて直接記入した質問（AWI本文へ転記された質問は対象外）は、回答本文と根拠を下書きへ保存して絶対パスをメインへ通知し、`検証結果`にも記す。レビューの指摘は下書きへ反映する。メインが回答UWIを保存して返したファイル名を進捗ログ（計画なしでは引き継ぎ記録）へ追記する。保存されるまで回答完了として扱わない
- 計画の変更範囲の検証は`atk run-script plan-verify -- --plan <計画の絶対パス> --worktree <対象worktreeの絶対パス> --timeout <正の有限秒数>`で実行する。先に同じ入力へ`--list`を加えて順序とargvを確かめる。実行後は保存された結果まとめの`results_path`を`atk run-command --records-file <絶対パス>`へ渡し、全件の`record_path`・両出力と子・wrapperの終了状態から判定する。計画なしでは引き継ぎ記録で確定したコマンドを実行し、`--record <record_path>`の反復で保存済み結果を読む。読むのは保存済み結果だけとし、旧記録の未記録値と保存・読取失敗を成功と扱わない
- commit直前に`agent-toolkit:commit`へ従う。計画を持つ場合は、そのcommitの実装単位に属する`### 恒久化`と`### リファクタリング`の行を差分と比べて不足を同じcommitへ含め、最後の実装commitの前には両表の全行がいずれかのcommitに対応することを確かめる。各commitの前後のHEADを`atk run-script plan-progress --`へ渡して進捗ログと同じstemの対応記録へ記録する（commit失敗時は記録しない。最初の記録では専用worktreeの絶対パスとbranch名を`--result`へ渡す）。実装・レビュー修正・CI修正の各commitで、`agent-toolkit:commit`の`SKILL.md`「WI実装commitの対応」の記録を残す

### 担当種別ごとの修正

- `レビュー修正担当`は採用した指摘だけを修正し、レビュー指摘管理表が要求する証拠を保存する。採否と横展開は`agent-toolkit:review-standards`の`references/reviewee.md`「修正要否の立証」と「安全な修正」に従い、レビュー担当の修正方針を要件へ昇格させず独立に確定する。不採用は理由を表へ記録し、成果物は変更前のまま保つ。計画かWIの確定内容を覆す修正は適用せず、対立箇所を続行できない理由として返す
- ユーザビリティレビューの指摘を修正した担当は、受領した操作順、画面状態、表示幅で新しいHEADを実ブラウザーで描画して確かめ、試した条件と結果を再提出に記す。自動化できる条件は既存のブラウザーテストへ保持する（努力目標。同条件のテストを重ねない）
- `CI修正担当`はCI記録の7項目を実装契約とし、原因となった失敗だけを修正する。原因を調べる前に`agent-toolkit:bugfix`を起動し、`SKILL.md`「初動と拡張原因分析の判定」「直接的原因と事象時点の確定」の共通判定をCI記録の原因分析結果へ適用する。直接的原因を確定できなければ是正commitとして返さず、試した対照、残る候補、作成した診断の変更を、推定である旨とともに返す。診断コードを加える場合は、CI記録が対応付ける競合仮説・観測・採取対象を先に読み、判別に使わない列挙と走査を含めず、出力量は採取対象を限定して抑える。修正方法は`agent-toolkit:commit`の`references/push-and-ci.md`「pushと監視」のCI失敗の区分に従い、原因commitへ取り込んだ場合は書換え前後のOID対応と`git range-diff`の結果を返す。原因となった失敗と根本原因を同じくする対象のうちCI記録が認可しない対象は、`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「類似見直し」の母集団として修正の対象と方向を委譲元へ返す。CIログの有無、再現性、外部の一時障害、再実行の認可と回数は除外条件にしない。pushは行わない

### 完成条件証拠の検証記録

実行レビューが完成条件証拠を作成する対象では、実装完了前に要求単位ごとの未判定検証記録JSONをmanaged-tempへ作成する（レビューの出力先とは別のファイル）。

- 生成: `atk run-script verification-record -- --output <記録の絶対パス> --plan <計画の絶対パス> --list`で原文と出所の雛形を保存し、配列・1始まりの行番号・出所も同じ操作で得る。WI直渡しでは`--plan`の代わりに`--wi <WIファイル名>`を反復する。対象リポジトリは計画メタ情報の値を使い、WI直渡しと対象を持たない既存計画だけcwdを使う。計画だけのユーザー指示も変更履歴の逐語発言から生成される。既存記録を読むだけなら`--output <同じパス> --list`
- 根拠の記入: `--output <同じパス> --select-row <配列:N> --evidence-file <根拠のUTF-8ファイルの絶対パス> --mode append`（置換は`--mode replace`）
- 構造化結果の取得: 試験は`atk run-command -- ... pytest -v -o junit_family=xunit1 --junitxml=<XMLの絶対パス> <対象...>`で実行時にXML・実行記録・両出力を保存する。診断はpyfltrのrunのJSON Lines全体（header・command・summaryを事前に除く必要はない）、`show-run --commands <対象> --output-format=jsonl`かMCPの構造化結果を保存する。取得版・対象範囲・オプション・依存版・並列度・実行環境と必要な保存時本文を対応付ける
- 保存出力の読取: 本文表示、構造化診断、試験結果の関連付けは、`agent-toolkit:check-execution`の「保存した実行出力の取得」で用途に合う公開指定を選ぶ。保存済みログの本文は`pyfltr show-run <run_id> --commands <コマンド名> --output --output-format=text`で読み、生成元に形式・対象の指定があれば保存前に選ぶ。構造化診断のJSONLと結果ファイルの関連付けは前後の取得・記入手順を使う
- 構造化結果からの記入: 入力形式は`atk run-script verification-record -- --help`で取得する。試験は`--junit-xml <保存XML> --junit-record <実行記録>`で直接指定する。診断は`--diagnostics-file <保存JSONL> --diagnostics-record <実行記録> --diagnostics-conditions <取得時の条件JSON>`と必要な`--diagnostics-source <相対ファイル> <保存時本文>`の反復で直接指定する。基準比較は同じ組の`--baseline-junit-*`・`--baseline-diagnostics-*`へ保存物を指定する。`--output <初回記録の絶対パス> --list-results --results-summary`で状態・基準版との差、診断のまとまり・重複数・全識別子から必要な結果を選ぶ。続けて`--results-summary`を`--result-test <完全テスト名>`か`--result-diagnostic <診断識別子>`の反復へ替え、詳細・取得版・所在を読む（表示の追加指定を省けば全詳細）。代表1件を全件の意味判断へ代用せず、比較不能は不足として補う。記入では`--list-results`を外し、`--select-row <配列:N>`の反復と各要求を直接満たす完全テスト名・診断識別子を渡す。必要なら`--evidence-file`と`--mode append|replace`も渡し、同じ保存物から更新する（sourceは処理側が現行行から取得する）。不正な行が1件でもあれば全保存が拒否される。既存のJSON入力の契約も保持され、未選択行は変わらない

各`evidence`にはテスト完全名と成功結果の所在、または保存済み観測の入力・操作・期待結果・観測結果の箇所を書く。pytestのテスト名は、同じ版の保存済み出力（`-v`付き）にその名前と結果の行があることを確かめる。点表示と総数は個別の合否の根拠にならない。後続工程や不採用・割当の行には、検証済みの範囲と採否・後続工程を記録した箇所（計画の`## 実施内容`、計画なしでは引き継ぎ記録）を書く。`outcome`と`reviewed_head`は空欄を保つ（判定は実行レビュー担当だけが書く）。
不足する根拠は自身の操作の範囲で補い、入力・権限・外部状態を要する不足は続行できない理由で返す。記録の絶対パスは初回生成時に進捗ログ（計画なしでは引き継ぎ記録）へ残し、`検証結果`にも記す。
レビュー修正担当はどの操作よりも先にその記録から初回パスを解決し（解決できなければ入力不足を返す）、全操作を同じ`--output`へ行う。再生成は既存根拠を保持して不足行を加え、修正が影響する行だけを置換する。CI記録だけのレビューで完成条件証拠が`なし`ならこの記録は不要とする。

### 返却前の確認

`実装完了`と「レビュー修正の履歴統合」の返却の前に次を確かめる。

- `git -C <対象worktreeの絶対パス> status --porcelain=v1`に担当範囲のパスが現れない。現れればcommitしてから再確認する（未commitの変更は統合されない）。担当範囲外のパスだけが残る場合はそのまま返す
- `検証結果`が挙げる手動観測の各行が実在する保存先の絶対パスを持つ。欠ける行は保存する形でやり直す
- 返す`検証結果`と同じ内容を進捗ログ（計画を持つ場合は`atk run-script plan-progress --`）へ記録済みである

`画面差分`は担当差分に含まれる画面資産から判定し（定義は`workflow-phases.md`「用語」）、`あり`では変更した画面資産のリポジトリ相対パスを列挙する。

## レビュー修正の履歴統合

修正方法（fixupの作成、元commitへの対応付け、autosquashの単位）は`agent-toolkit:commit`の`references/history-rewrite.md`「修正方法の選択」に従い、autosquashはラウンドごとに行う。fixup先が直前の1commitだけならautosquashの代わりに`git commit --amend`を使ってよい。

- 書換えの前に、対象worktreeがclean、rewrite対象が未push、操作直前に解決したrewrite対象のOID集合がそのレーンのcommitだけであることを確かめ、別の呼び出しで同書「履歴確認の起動形」の`git log`を実行する
- autosquashは同書「fixupの実行上の制約」の起動形で実行し、競合と失敗は同書「失敗時の扱い」に従う。同じ指摘の履歴統合の再試行は委譲元の判断を得てから行う
- 書換え前後のOID、tree、親OID、件名を保持して`rewrite_guard`の要求に合うか確かめ、同書「操作前後の確認」の`atk run-script history-compare -- --operation autosquash`で終了コード0と検収済み対応表の保存を確かめる。amendの検収も同書に従う
- レビュー指摘管理表へ、指摘、採否、修正commit、検証結果、書換え前後の7文字以上の一意な短縮OIDの対応、一致確認結果、対応表の絶対パスを残す。この完全OID対応表を`plan-rewrite`と完成条件証拠の`--rewrite-map`へ渡し、AWI集合を現在の実装commitへ継承する
- 履歴統合後の変更範囲の検証は`diagnostics.md`で、記録済みの基準版と累積差分から判定し、`atk run-script plan-progress --`で進捗ログへ追記する
- 取得版がレビュー対象の祖先から外れた検証記録は、結果に作用する差がある行と取得版を特定できない行だけを取り直す。他の行は`exec-review-recording.md`「根拠の書き方」に従って取得版を保持する観測ファイルの参照と適用理由を`evidence`へ書く。`--rewrite-map`で更新するのは現行成果物を指す`commit:<OID>`の参照だけであり、裸のOID、取得版のHEAD・git_head・比較元、観測ファイルと判定欄、既存自由文の形式は保持される。分割した対応先も各`commit:`参照として次回更新へ渡す
- 会話履歴が欠けた状態で再開する場合は、レビュー指摘管理表の完了内容を現行のGit実体と比べ、保存済みの書換え前後のOID対応、公開済み判定、件名の一意性から確定できる場合だけ進む。旧OIDは保存済みの記録から取る（無指定のreflogは出所にしない）。確定できなければ対象OIDと不足範囲を続行できない理由で返す

`history-rewrite.md`が用いる各phaseの対象は次のとおりとする。

| phase | 対象 |
| --- | --- |
| `pre_fixup` | そのラウンドの最古fixup対象から元HEADまでのfirst-parent全OID |
| `fixup` | 指摘を対応付けた元commitの完全OID |
| `autosquash` | そのラウンドの最古fixup対象から元HEADまでのfirst-parent全OID |
| `amend` | 書換え後HEADの完全OID |

修正と履歴統合を終えたら`対応完了`を返す。`agent-toolkit:review-standards`の`references/reviewee.md`「完了報告」の両条件を満たす場合だけ`対応完了（再レビュー不要）`を返せる。いずれにも`実装完了`と同じ書式の`検証結果`と`画面差分`の行を続ける。採用した指摘が1件も無い場合は、履歴と作業ツリーを変えずに続行できない理由を返す。

## 出力

全commitと変更範囲の検証を終えたレーン担当は、次の形式で`実装完了`を返す。

```text
実装完了
検証結果: <実行した変更範囲の検証、終了コード、警告の有無、受入シナリオ別のテスト名と合否、要求単位ごとの未判定検証記録JSONの絶対パス、直接影響範囲の探索の成果物およびユーザーがWIへ直接記入した質問への回答下書きの絶対パス。保存後はUWIのファイル名も記録>
画面差分: <あり（変更した画面資産の相対パスの列挙）|なし>
```

終端結果では、担当モデル、起動候補、物理記録から観測した`engine`・`model`・`effort`を区別して返す。不一致は各値と由来を引き継ぎへ残し、観測不能は未確認とする。

工程境界では本書が定める固定形式だけを返す。続行不能時は`agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」の`続行できない理由:`の1行だけを返す。
自身が起動した外部プロセスの終了を確認してから終端する。想定外事象の追加行は`agent-toolkit/share/rules-subagent.md`に従う。
