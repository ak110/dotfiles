# pickerの起動と受領

```text
起動対象: pick-wi.subagent.md
```

process-wiのメインが、処理対象の選定と処理開始へ適用する。

## 読込表

次の時点または条件が成立したら、対象の操作の前に同じ行の資料を全文読む。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 処理対象WIについて、包含、除外または構成の理由をユーザーが尋ねたとき | `${CLAUDE_PLUGIN_ROOT}/share/pick-wi-explain.parent.md` |

## 起動

メインはキュー一覧とAWI本文の取得をpickerへ委ね、pickerを1件起動する。

`start`の前に、対象リポジトリがmiseの設定ファイルを持ち、対象リポジトリで実行した`mise trust --show`が`untrusted`を示す場合は`mise trust <対象リポジトリの絶対パス>`を実行する。
未trustの設定があると委譲先がプラグインのMCPサーバーとhookを起動できず、`agents_server`は事前確認の失敗としてpickerを起動しない。準備の範囲は`agent-toolkit/skills/process-wi/references/run-lanes.md`「レーンと資源」が専用worktreeへ行うmise trustと同じとする。

`agents_server`の`start`を次の引数で呼ぶ。

| 引数 | 値 |
| --- | --- |
| `cwd` | 対象リポジトリの絶対パス |
| `subagent_md_path` | `pick-wi` |
| `extra_params` | 次の名前付き入力 |

セッションのmanaged-temp（`agent-toolkit:managed-temp`）の直下の`pick-wi.yaml`を出力先とする。

- `選定結果の出力先ファイル`: 絶対パス
- `引き継ぎ記録先`: 省略と継続の扱いは`agent-toolkit:delegation`の`references/base-contract.md`「引き継ぎ記録先」に従う
- `WIファイル名一覧`: 「処理対象WIの追加」の候補差分のWIファイル名（AWIと回答済みUWI）の一覧。指定が無い場合は送らない

ユーザー指定がある場合もpickerを起動する。本文取得、依存順、レーン分けおよび再開位置はpickerが担う。

## 出力の受領

pickerから4行の返却を受領する。欄は`状態`、`出力先`、`行数`、`書込対象の検査`であり、続行不能時は`状態`の行に代えて末尾に`続行できない理由`の行を持つ。
出力先が起動時の絶対パスと一致することを確認する。
追加選定の受領では、追加側の全レーンから検収用の最終レーンへの対応をJSONオブジェクトとしてmanaged-tempへ保存する。
次の統合操作を単独で実行し、全追加WIへ`--body-wi`を反復する。

```sh
atk run-script pick-wi-check -- <既存選定YAML> --merge <追加選定YAML> --lane-map <対応JSON> --output <一時全体YAML> --work-dir <対象リポジトリの絶対パス> --body-wi <追加WI名>...
```

対応の意味判断は受領側が行い、保存成功と全体チェックの終了コード0を確認する。
メインが合流後の時間と根拠を再確定した場合は、最終レーン識別子から`実装秒数`・`統合秒数`・`根拠`の3欄への写像をJSONへ保存し、同じ操作へ`--lane-cost-updates <費用更新JSON>`を加える。対象は今回追加の合流先だけとする。省略時は従来の秒数の加算と根拠の結合を使う。指定値は段階と先行参照を変えず、合流後の3欄へ反映される。
追加YAMLの比較欄は追加分だけの見込みから全体配分に対する値へ確定して渡す。検収用の割当と最終割当で全体配分が変われば比較値も再確定する。
既存と追加の原本を保持し、この場合に限り以下の出力先を確かめるコマンドへ一時全体YAMLを渡す。
続けて返却欄の値にかかわらず、受領側自身が最新の出力先へ`atk run-script pick-wi-check -- --work-dir <対象リポジトリの絶対パス> <出力先の絶対パス>`を単独で実行し、終了コードと出力行を得る。このコマンドは最初に出力先をYAMLとして読み、pickerの出力契約が定める項目名、必ず持つ行と値の型を確かめる。続けて`書込対象`、`公開工程の書込対象`および`書き込まない反映先`の和がAWI本文の反映先とUWIの本文に明示されたパス（配下の個別パスと並べて挙げたディレクトリ範囲を除く）を覆い、3区分が重複しないことを確かめ、受領の可否を判定する。`書き込まない反映先`の範囲が配下の書込区分のパスを含む組は、変更しない上位ディレクトリの配下で個別のファイルを書く選定として重複に数えない。ほかに別レーンの`書込対象`の重なりと`レーン間の重なり`の構造化した記録、同じレーンの`担当モデル.実装担当`の両立、`公開工程の書込対象`の根拠、同じ再開計画を指す項目のレーン、後段の先行指定の形式も判定する。対象リポジトリの`pyproject.toml`の`[tool.agent-toolkit.pick-wi-check]`が条件を定める場合は、`プロジェクト規範の指定`の記載の有無も確かめる。
`単一段階案の完了見込み秒数`の有無も判定項目に含む。段階2以上での欠落は終了コード1、不正な型は終了コード2となる。欄を持つ成功時の要約には同名の値行が出る。
終了コード0の標準出力は、WI総数、通常レーン数、レーンごとのWI件数・段階・先行レーン・実装秒数・統合秒数・全WIファイル名と`レーン: なし`の項目を示す要約である。レーン構成と件数はこの要約で把握し、根拠・分類・変更する定義の独立性の検収は選定結果の本文を読んで行う。
コマンドの結果を得てから返却欄との整合を判定する。`書込対象の検査`の欄は`状態: completed`の返却では最新の出力先に対する`終了コード0`、`続行できない理由`の行を持つ返却では観測した非0の終了コードか実行できなかった理由を示す。

- 終了コード1と、`次の操作:`が選定結果の修正を示す終了コード2（YAML構文、項目名、必ず持つ行または値の型の誤り）は、返却欄の値にかかわらずその出力行を観測値として添えて後述の手順で同じpicker threadへ再取得を指示する
- `次の操作:`が引数、パスまたはprivate-notesの確認を示す終了コード2は、受領側の実行の誤りか環境の問題である。案内に従って引数か場所を直して同じコマンドを再実行し、pickerへの再取得には送らない。出力先が実在しない場合は返却の欠落として同じpicker threadへ再取得を指示する
- 終了コード0でも、返却欄の`状態`や`書込対象の検査`がこの結果と合わない場合は、観測値を添えて同じpickerへ欄の訂正を求める
- `書込対象の検査`の欄を持たない3行の返却は結果不明として扱い、欄の省略を合格へ補完せず、このコマンドの結果で判定する

終了コード0で欄が整合した出力の本文を読む。
AWIも`atk wi show`で元本文を取得し、変更要求から既存・新設・参照・除外・公開工程所有の分類と、限定調査で確定した変更領域を検収する。抽出パス、存在、名前順、一定件数だけによる配分と独立性の一律宣言は受理せず、一致しないWIと観測箇所を同じpickerへ返す。初回・再取得・追加選定で同じ意味検収を行う。根拠には配分比較と不可分条件を求め、共通パスと定義の独立性は`レーン間の重なり`から検収する。同一レーンの全書込集合の再掲は求めない。
`プロジェクト規範の指定`の欠落による非0も他の内容違反と同じく同じpicker threadへ修正と再取得を指示し、終了コード0を得てからレーンを開始する。指定が求める資料を実際に読んだかは、レーン担当が指定を消費する工程で確かめる。分類と変更する定義の独立性はpickerの本文読解と、後段のメインの検収で確かめる。終了コード0が示す範囲と、読解で確かめる意味の範囲を分けて判定する。
作業を求める回答済みUWIの項目では、回答に起因する3区分の分類を、UWIの質問・判断材料・回答を読んで検収する。回答がパスを明示しない場合は`pick-wi-check`が比べるパスが無く、終了コード0はUWIの書込範囲を確かめた結果にならない。pickerが限定調査で導いた範囲と、そのレーンの`根拠`の記述が回答の作業内容と合うかを確かめ、欠けや食い違いは後述の不一致として扱う。
`選定`の各項目を`${CLAUDE_PLUGIN_ROOT}/share/pick-wi.subagent.md`の`## 出力`が定める項目、省略時の値、省略規則と比べて検収する。
`導出した新設先`の要求と配置根拠を元本文と限定調査の現物へ対応付け、要求範囲を満たす具体化か、未具体化の残りを保守的な書込範囲で持つかを検収する。構造上の受理に加え、親が要求と配置の意味を確定する。共有定義と接続先、実依存、同じ再開計画の不可分性を保持し、計画で名前と範囲を変えた場合は実際の競合を再確認する。
段階案の比較では最上位の`単一段階案の完了見込み秒数`を読み、`レーンの所要時間`から求めた段階側の和と比べる。配分と補正の妥当性、採った理由は`根拠`と元本文で検収する。比較欄の書式・省略・算出の定義はpickerの出力契約に従う。
書込の推移的な重なりだけで6000秒超過を不可避としていないことを確認する。実依存と同じ再開計画の不可分性を保ち、レーン数上限内で独立群を並行する段階案と単一段階案を比較した根拠を読む。完了見込みは各段階の最長実装時間と直列統合時間の和を全段階で合計し、短い単一段階案を採用する場合にも比較理由を確かめる。段階化した結果はその比較と後段の先行統合条件が各レーンの`根拠`で一致するか確認する。
`プロジェクト規範の指定`が指すファイルは実在して読み取れることを確認する。上流投入の3行は`上流投入`の値に応じた必須性と省略規則を確認する。`レーンの所要時間`は`なし`でないレーンとの集合一致、重複の不在、非負の2つの秒数を確認する。根拠も空でないことを確かめる。レーン数は`選定`の件数を`WI数`とした`floor((WI数+9)/10)`と比べ、上限を超える場合は、超過の根拠を超過分のレーンの`根拠`が示すか確かめる。認める根拠は、分割不能条件だけで6000秒を超える連結成分から他の連結成分を分けたこととし、示さない場合は後述の不一致として扱う。pickerの文書の上限規則だけでは超過を防げないため、受領側でも比べる。
予測の根拠は`pick-wi.subagent.md`「調査とレーン分け」が定める過去記録による補正と比べる。対象リポジトリ・process-wiの1回の実行・レーンの対応、補正前の2値、係数、除外理由と取得先から、YAMLの2値が双方とも補正後であり、観測した総経過秒を別に加算していないことを検収する。過去記録が不足する場合も、遡った結果と係数1の理由を読む。6000秒と段階案の比較には補正後の値を使い、レーン数上限と品質確認を同じ基準で維持する。
`選定`と`レーンの所要時間`が空の選定結果も正常な選定結果として受領し、レーンを起動せずに自動コードレビュー監査と公開工程へ進む。

`pick-wi-check`が判定した別レーンの`書込対象`の重なりについて、`レーン間の重なり`の`共通パス`、`レーン1の定義`、`レーン2の定義`と`判定`が本文と一致するか読む。`交わらない`とした定義の意味が交わる場合、同段階で交わる場合、後段の先行指定が交わる記録の連鎖と合わない場合は不一致とし、観測した重なりと2つのAWIを添えて同じpickerへ再取得を指示する。受理には自由文のパス再掲の有無によらず、構造化した記録を要する。

メインは候補内の同一リポジトリの依存を、正規化した`target_repo`と`depends_on`から推移的にたどる。起動前に、依存の両端が同じレーンにあり依存先が先行することを検収する。書込競合の順序は`depends_on`とは分ける。別レーンの開始順だけで候補内依存を満たす割当は受理しない。

上流投入の3行の省略時の値と省略を解決した`選定`の各項目について、「出力」の`上流投入`と`レーン`の組合せ条件も検収する。`上流投入`の行を省略した`レーン: なし`などの不一致は、後段の同一pickerへの再取得へ戻す。通常レーンがある外部操作だけの項目は、ファイル変更が無いことを理由に再取得しない。

固定形式に適合する出力を受領した時点で選定結果を検証し、監査の終端を待たずに選定工程の完了とレーン起動へ進む。受領済みのpickerを再び待機または起動せず、そのまま終端させる。

再開位置が`反映後の観測だけが残る`で始まらない項目では、`~/.claude/plans`内の計画ファイルの絶対パスであり、計画の`関連WI`が対象AWIを含むことを確認する。
`agent-toolkit:process-wi`の`references/finish-session.md`「延期adoptと反映後の観測」はAWI本文へ再開記録（最後の`## 反映後の観測の再開記録`の節）を追記する。pickerは最後の同名節の`再開区分`が`反映後の観測だけが残る`の項目だけ、その記録から`反映後の観測だけが残る`で始まる観測のみの再開位置を返す。この値では前文の計画ファイルの確認に代えて、AWI本文の最後の同名節が持つ`計画`の値と再開位置の`計画:`の値が一致することを確かめる。値が`private-notes/plans/`からの相対パスの場合は、`atk config get private_notes`が返す場所の`plans/`配下にその計画が実在し、計画の`関連WI`が対象AWIを含むことも確かめる。値が`計画なし`の場合は計画の確認を省く。
再開位置が無い項目は新しい計画を起草する対象とする。省略時の値との一致により省略された行は、pickerの出力契約が定める省略時の値として解釈する。

欠落、重複、形式外の値または不一致を検出した場合だけ、観測値を添えて同じpicker threadへ再取得を指示する。`続行できない理由`の返却も根拠を検収し、内側で補える入力・技術的不足は同じpickerへ結果か続行指示を返す。`agent-toolkit:user-confirmation-and-report`「確認要否の判定」でユーザーだけの値が残る事項だけを確認する。必要な回答を得られない場合はUWIを登録し、回答依存の項目を`atk wi hold`で保留する。`processing`の項目は`atk wi hold --state=processing <ファイル名>`で保留する。

メインはpickerの出力へ不採用と既存実装による充足の確定が含まれないことを検収する。選定工程ではメインがAWIを直接`reject`または`adopt`せず、採否と通常の終端はレーン担当が行う。反映後の観測だけが残る延期`adopt`は`agent-toolkit:process-wi`の`references/finish-session.md`「延期adoptと反映後の観測」に従う。採否の確定はレーン担当の職務であり、その職務境界は`${CLAUDE_PLUGIN_ROOT}/share/pick-wi.subagent.md`が定める。

## 選定工程の完了

処理開始はpickerが行う。メインは`atk wi list --target-repo=<対象リポジトリの絶対パス> --skip-pull`を1回実行し、選定された全項目が`processing`にあり、対象外の回答済みUWIが`processing`にないことを確認する。回答済みUWIの本文が指し、pickerが同じ工程で`unhold`した元項目も選定された全項目に含め、同じ確認の対象とする。不一致ではレーン工程へ進まず、状態と理由を記録する。

対象リポジトリのプロジェクト規範が選定工程の完了時点での評価と記録を求める条件を定める場合は、同じ工程でその条件を評価し、規範が定める記録先へ判定結果を保存する。記録は選定工程の内側で完了させる。条件の内容と記録先はプロジェクト規範に従い、本書への再掲を省く（努力目標。定義を持つ文書を1つに保つ）。

処理対象は受領した選定結果の`選定`の集合を基準とする。追加した処理対象WIは次節で検収してから同じ`選定結果の出力先ファイル`へ追記する。

## 処理対象WIの追加

追記後の全体YAMLが段階2以上の行を持つ場合は、全体配分の`単一段階案の完了見込み秒数`を追加YAMLで再確定して統合へ渡す。
時間と根拠を再見積りした場合も「出力の受領」の費用更新JSONを使い、保存前の全体チェックへ渡す。

ユーザーが処理中のセッションへキュー操作（UWIへの回答、AWIの投入）を告げた発話は、その項目を同じ実行の処理対象へ加える明示指示として扱い、追加の可否を問い返さない。ユーザーが対象へ加えるよう明示した項目と告げた項目を候補差分とする。即時対応で投入または再利用するAWIが確定した場合も、そのファイル名を候補差分とする。告げられたUWIは投入元のセッションによらず候補差分に含める。ユーザーがUWIを名指ししない場合は、回答済みで未終端のUWIのうち処理対象WIに含まれない全件を候補差分とする。取得には`atk wi list --type=uwi --answered=yes --status=processable --source=!run-skill --target-repo=<対象リポジトリの絶対パス> --skip-pull`を使う。メインは通常の新着を探すためにready一覧を再取得せず、告げられていない新着はprocess-wiの次の実行へ残す。ユーザーが告げた発話を明示指示とする判断は本節だけが定め、他の文書は本節を参照する。

候補差分を確定した時点で初期pickerが返却前なら、メインは既存の`send_message`で`WIファイル名一覧`を同じpicker threadへ追送する。候補差分だけで初期集合を置き換えず、同じ出力先へ合流するよう伝える。別pickerを起動せず、追送分を含む最新の返却を「出力の受領」と「選定工程の完了」で検収してからレーンを起動する。状態変更済みの初期項目を再遷移させず、未遷移の追加項目と回答済みUWIの元項目を既存手順で扱ったことも確かめる。

初期pickerの返却後に候補差分がある場合、メインは元の選定結果とは別の出力先ファイルと引き継ぎ記録先を確保する。`WIファイル名一覧`へ候補差分を渡してpickerを起動し、`既存レーンの選定結果の出力先ファイル`へ元の`選定結果の出力先ファイル`の絶対パスを渡す。pickerは指定項目だけを処理開始し、各項目の`プロジェクト規範の指定`、既存レーンとの書き込むファイルと節（`書込対象`）の重なり、同じ再開計画を持つ既存レーンを出力する。メインは追加出力の`選定`、`レーンの所要時間`、処理開始状態および候補差分との集合一致を「出力の受領」と同じ基準で検収する。同じ再開計画を持つ既存レーンが根拠に記録されている追加項目は、その既存レーンへの割当を費用比較より先に確定する。

メインは`agent-toolkit:process-wi`の`references/run-lanes.md`「処理中に確定した必須是正レーン」の割当基準で、追加出力のレーン識別子を既存または新規のレーン識別子へ対応付ける。最終割当の対応JSONを確定し、受領時と同じ統合操作へ`--output <元の選定結果の出力先ファイル>`を渡して保存する。対応JSONは追加側の全レーン識別子をキー、最終レーン識別子を値とする。統合操作が既存の選定を保持し、追加項目のレーン・先行レーン・重なり両側を変換し、所要時間と根拠を合流する。自己レーン組は除き、同じ組と共通パスの定義は両側を統合する。全体検査が成功するまで元ファイルは変わらない。独自の合流スクリプトで3列を別々に書き換えない。
`--body-wi <追加WI名>`を全件分反復して本文検査だけを追加分へ限定し、構造・担当モデル・同じ再開計画・段階・重複・公開工程所有の根拠は全体検査を保つ。省略すれば全件の本文検査となる。終了コード0の本文検査対象が追加した通常レーンの全件と一致することを確かめ、保存先と全体の検査結果を保持する。
同じ再開計画の別レーン割当を含む非0では割当を直す。本文検査の違反では元本文と限定調査から分類を判断し直し、規範指定の不足は追加出力のpickerへ修正と再取得を指示する。追記後の全体が終了コード0になり、元本文による意味検収を通ってからレーン担当へ追加分を渡す。あわせて`選定`と`レーンの所要時間`の集合、AWI名の重複、依存順を再検収する。`選定結果の出力先ファイル`へ追記する前に別出力を直接レーンへ渡すと、実行レビューと終端の対象集合に追加分が含まれなくなる。
