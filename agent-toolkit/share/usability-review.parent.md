# ユーザビリティレビューの起動と検収

```text
起動対象: usability-review.subagent.md
```

画面差分が存在する場合に実施する並列画面レビュー（定義はいずれも`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`「用語」に準拠）において、メインエージェントがユーザビリティレビュー担当を起動し、その返却結果を検収する手順を定める。

## 起動

起動に先立ち、対象worktreeの書き込み主体（レーン工程ではレーン担当者）へ、対象リポジトリの手順に沿って対象HEADの再配備または起動を実行させ、その完了を確認する。実装途中に配備済みの環境についても対象HEADへ更新し、修正後に再判定する際も新しい対象HEADを用いて同様に準備する。

`agents_server`の`start`を次の引数で呼び出す。

| 引数 | 値 |
| --- | --- |
| `cwd` | 対象worktreeの絶対パス |
| `subagent_md_path` | `usability-review` |
| `extra_params` | 次の名前付き入力 |

- 対象worktree: `cwd`と同一の絶対パスを指定する。
- 変更画面: 変更が加えられた画面のパスまたはURLと、該当する表示状態へ到達するための操作手順を指定する。
- 主要シナリオ: 計画またはWIで指定されたエンドユーザーの作業の流れと、そこで確認すべきUX上の観点を指定する。期待結果との一致、データの反映、操作の成否といった機能的な正しさは、判定基準として渡さない。
  観点は変更画面ごとに、その画面に対するWIの完成条件および計画の受入シナリオが求める範囲に限定し、完成条件が異なる画面についてはシナリオの記述を分ける（計画の要約文が完成条件より広い結果を述べている場合でも、WIの完成条件に合わせる）。
  `agent-basics:writing-standards/references/ui-ux.md`「完了前の実描画確認」において実データから切り離した環境でのみ実施すると定められた操作を必要とする観点については、切り離された`検証環境`と許可される操作を明記するか、観点自体から除外する。`検証環境`で禁止されている操作を必要とする観点は記載しない。
- 検証環境: 対象プロジェクトの手順から確定したローカル起動コマンド、または127.0.0.1で稼働中のURLを指定する。
- 引き継ぎ記録先: 省略時や継続時の扱いは、`agent-toolkit:delegation`の`references/base-contract.md`「引き継ぎ記録先」に従う。
- round: 初回起動時は1を指定し、同一担当への再判定時には直前の番号に1を加えた値を指定する。
- レーン識別子: レーンの作業を対象とする起動に限り、該当するレーンの識別子を指定する。session識別名は`<レーン識別子>-usability-review`とする。

## 返却後

返却された記録に対象HEADと`判定の回数`が正しく示されているかを確認する。判定が`合格`または`不合格`の場合は、完遂を試みたシナリオ、観測された状態、およびキャプチャーの実在を確認する。判定が`未確定`の場合は、`E2E環境`、`Playwrightのライブラリ`、`ブラウザー操作ツール`の3つの`試行:`行が揃っているかを確認し、不足がある場合は受理せず、同一threadに対して不足している手段の試行と再判定を要求する。

判定が`不合格`となった場合は、その根拠が該当画面に対するWIの完成条件の範囲内にあるかどうかに応じて扱いを分ける。

- 範囲外の観察結果: 判定の根拠から除外した上で、適用範囲を示して同一threadへ再判定を依頼する。その観察結果がエンドユーザーの作業停止や誤った結果を示す欠落である場合は、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「認可を要する操作」に定める範囲外の不足区分に沿って判定する。バグの修正はprocess-wiの同一実行内で是正し、新たな挙動の追加は同書の「確認を要する事項」に従って確認へ送る。それ以外の事項は参考記録として扱う。
- 範囲内の根拠: 指摘された問題の機構、対象範囲、画面状態、操作手順、表示幅、および観測結果を修正条件として整理し、同一の実装担当者（レーン工程では同一のレーン担当者）へ返却する。実装担当者は指摘箇所に加えて同一の機構を持つ依頼対象全体を確認し、新しい対象HEADを実ブラウザで描画して確認する。対象全体に対して試行した条件と実際の表示結果を再提示させ、同一機構の該当箇所へ修正が反映されたことを確認した上で、同一のユーザビリティレビュー担当threadへの再判定と、実行レビュー担当への再レビューを同一HEADに対して並列で依頼する。

統合処理へ進む前に、同一の対象HEADについてユーザビリティレビューの判定が`合格`または`未確定`であること、および実行レビューの未解決指摘が0件であることを確認し、ユーザビリティレビューの記録を計画の検証結果へ追加する。`未確定`の場合は、利用できなかった描画手段と未確認となった画面状態を完了報告に明記する。
