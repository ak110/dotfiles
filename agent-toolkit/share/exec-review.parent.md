# 実行レビュー担当の起動とレビュー修正

```text
起動対象: exec-review.subagent.md
```

メインが実装後のHEADを実行レビュー担当へレビューさせ、指摘への修正と履歴統合を管理する際に本書へ従う。
実行レビュー担当自身の手順は`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`が定める。
本書が定める範囲は起動、入力生成、レビュー修正及び指摘管理表の保存とする。レビュー分類と判定手順を再定義しない。

画面を変更した差分では、同じplugin rootの`share/usability-review.parent.md`に従い、同じ対象HEADに対する独立したユーザビリティレビュー担当と実行レビュー担当を並列に起動する。ユーザビリティレビューの結果を待たずに実行レビューを始め、統合前に両レビューの収束を確認する。修正後も新しい対象HEADに対する両レビューを並列に進める。

## 起動方法別のレビュー基準

レビュー基準は`計画`、`CI記録`、`WI`のうち1つ以上を同時に渡す集合値とする。
その実装を認可した資料が手元にある基準を渡す。計画契約があれば`計画`、対象WIがあれば`WI`、計画契約が無いCI失敗由来であれば`CI記録`を渡す。
1件の実行レビューは、起動時の`cwd`で解決する単一の対象リポジトリだけを扱う。複数のレビュー基準を同時に渡す場合も、全てが同じ対象リポジトリに属する必要がある。対象リポジトリが異なる基準は、対象worktreeごとの別の実行レビューへ分ける。

`計画`と`WI`を併せて渡す場合は、計画の`## 実施内容`が挙げるWIを実行レビュー担当が自ら取得するため、起動文へはWIの記録を置かない。
計画へ現れないWIがある場合だけ、そのWIの記録を起動文へ渡す。
`完成条件証拠`は全ての起動文へ含める。`WI`を含む場合、又は計画の`## 実施内容`に`ユーザー指示`由来の行がある場合は、起動前にセッション領域（`agent-toolkit:managed-temp`）の中へJSONの出力先を確保し、その絶対パスを値とする。どちらも無い場合は値を`なし`とする。実行レビュー担当が返す`evidence_path`から同じファイルを読み、完成条件と証拠の対応を後続の検収へ渡す。受領時には計画や起動文にあるWI名を`atk wi show --skip-pull`へ渡し、本文の完成条件と原文要求を取得する。計画の`ユーザー指示`行も要求単位に分け、WI本文の要求と合わせてJSON行の判定と証拠参照が一致するか確かめる。計画だけに現れる行の`awi`は空文字列、`origin`は計画内の所在とする。WIにも計画にも元のユーザー発言が無い場合は`user_requirements`を要求しない。不足した要求単位を特定して同じレビュー担当へ補完を求め、揃うまで後続へ配送しない。
レーンの引き継ぎ記録にGit管理外の変更元と変更前複製の対がある場合は、任意入力`Git管理外の変更`として全対を起動文へ渡す。対が無い場合はこの入力を省く。

## 指摘管理表の準備

初回の実行レビュー担当を起動する直前に、本書がレビュー基準に対応する指摘管理表を準備する。1件の実行レビューは単一の表を使う。保存先は次のとおりとする。

- `計画`を含む場合: 計画ファイルと同じディレクトリの`<計画stem>.exec-review.tsv`
- `WI`だけの場合: `~/.claude/plans/wi-<処理開始OID>.exec-review.tsv`。`処理開始OID`は起動文へ記載する処理開始時点の7文字以上の一意な短縮OIDとする
- `CI記録`だけの場合: `~/.claude/plans/ci-<起点commitOID>.exec-review.tsv`。`起点commitOID`は起動文へ記載するその修正系列の起点commitの7文字以上の一意な短縮OIDとし、同じ修正系列では値を継続する

対応する表が存在しない場合は`atk review-table init <指摘管理表の絶対パス>`を単独実行し、成功の報告と警告の不在を確認する。既存の表がある場合は同じ表を再利用する。同じレビュー担当threadの再レビューでも同じ表をそのまま使う。

## `review_contract`の生成

メインは実装完了と検証結果を受領した後、初回の実行レビュー担当を起動する直前に、計画から得られない条項がある場合だけ`review_contract`を生成する。全条項が計画から定まり、計画外の認可情報が無い場合は省略する。
実行レビュー担当は、初回起動と引き継ぎ再レビューのいずれも`agents_server`の`start`で起動する。
`subagent_md_path`には`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`を解決した絶対パスを渡す。
`extra_params`には受信者文書が要求する名前付き入力、`cwd`には対象worktreeの絶対パスを渡す。
レーンの作業を対象とする起動では、`extra_params`へそのレーンの`レーン識別子`も加え、session識別名を`<レーン識別子>-exec-review`にする。`CI記録`だけを渡す起動には加えない。
メインが条項を生成する出典は、受領するレビュー基準のうち計画から得られない次の資料とする。計画由来の条項は実行レビュー担当が計画ファイルから生成する。

- `計画`: 計画へ記載されていない、別のレビュー基準で認可されたcommitの認可範囲などの明示入力
- `CI記録`: 起動文へ直接記載するCI記録と、起動文へ記載する`原因commitOID`の親を開始時点として特定した実体。CI記録の項目は`agent-toolkit:bugfix`の`references/ci-failure-handling.md`が定める。入力計画は変更の由来を示す資料とし、原因commitを計画と比較する基準の対象から外す
- `WI`: 計画へ現れない対象WIの要求、完成条件、要求単位の由来及び確定した採否。`計画`を併せて渡さない場合は、全対象WIと起動文へ記載する`処理開始OID`で特定した実体

`CI記録`を渡す場合は、前記7項目に加えて`起点commitOID`と`原因commitOID`を起動文へ記載する。`原因commitOID`は再帰的CI失敗ごとにCI記録と同時に更新し、`起点commitOID`は同じ修正系列で継続する。`計画`を渡さず`WI`を渡す場合は`処理開始OID`を起動文へ記載する。

初回の実行レビュー担当を起動する起動文では、既定値の`レビュー種別: 初回レビュー`と`round: 1`を省略する。再レビューを指示する文と引き継ぎ再レビューの起動文には、`round: <ラウンド番号>`の行を含める。ラウンド番号は`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`の`## ラウンド番号の保持先`が定める値とする。

`review_contract`は計画外のユーザー目的、現行の公開契約、ユーザー合意、認可の範囲、除外・保持、通常入力、対象外入力、誤許可と誤拒否の消費主体への影響を、独立して成否を判定できる条項ごとに分ける。出典から対象を判定できる集合は条件で示す。件数そのものが合否条件の場合だけ、実際に数えた件数と時点を記録する。条件を一意に記述できない条項は独立して判定できる単位へ分ける。
計画の受入シナリオでは要求固有の呼び出し手段（コマンド・画面・API・hookなど）と結果を条項にし、提出されたテストと実際の観測結果を比べる。リポジトリ全体の自動チェックとCIの成功は個別WIの完成条件の証拠にせず、公開工程の検収へ渡す。
計画又は要求が外部可視の属性を名指しした場合は、その最終値と、実装が最終値を導く入力、条件分岐、既定値を独立した判定条項へ変換する。直接設定が一致しても、地域区分や権限フラグなどの導出後の値が異なれば検出できる内容にする。
<例>
海外扱いのモデル
権限に応じた画面表示
</例>
海外扱いのモデルでは、`regions`の内容から最終地域区分を導く全分岐と既定値を確認する。直接設定が海外でも最終値が国内なら不合格とする。
権限に応じた画面表示では、バックエンドが導く権限フラグの入力と分岐を確認する。テンプレートが参照する値と最終的な表示可否も確認する。
計画外の変更成果物の種別から、適用する執筆規範、プロジェクト規範のパスと節を解決し、成果物の規範適合を判定する条項として出典付きで加える。
適用規範を一意に特定できない計画外の成果物では、その成果物と未特定の範囲を条項へ記録し、実行レビュー担当が変更種別、発動条件及び読み込み処理から解決できる入力を残す。
同じ累積差分に現在とは別のレビュー基準で認可されたcommitが含まれる場合は、その7文字以上の一意な短縮OID、レビュー基準、認可根拠となる計画・WI・CI記録、認可された対象範囲を独立条項として含める。現在の基準による重複した認可判定の対象外とするのは、根拠資料から認可済みと確認した対象範囲に限る。commitの存在そのものは認可の根拠から外す。対象外とした変更も、共有する公開契約と安全性、現在の基準が要求する統合結果へ適合するか確かめる。
外部参照を持たない単一条項は、`条項`、`内容`、`出典`の3行からなる短い直接契約として起動文へ記載できる。複数条項又はcommit・AWI参照を持つ契約は、次の形式で管理対象一時領域の`review-contract.yaml`へ保存する。

```text
version: 1
clauses:
  - clause: "<対象と判定内容>"
    content: "参照: <絶対パス>#<見出し>"
    source: "<明示入力の出所>"
commit_references: []
awi_references: []
```

参照先だけで条項の内容が一意に定まる場合は、`content`を例のように引用した`参照: <絶対パス>#<見出し>`で渡せる。参照先を追加で解釈しなければ判定内容が定まらない場合は、契約本文を`content`へ記載する。`clause`と`source`にもASCIIのコロンと空白を含めるときは引用する。commit又はAWIを参照する場合は、両配列へ実際の識別子を記載し、条項内へも同じ識別子を含める。
条項は観点ごとに分けて置き、前段が列挙する各観点と出典をそろえる。別のレビュー基準で認可されたcommitが無い場合は、その条項を省く。
`review_contract`はいずれの永続ファイルにも追記せず、初回起動後は同じ実行レビュー担当のthreadへ保持する。`CI記録`か計画外の`WI`を基準に含む場合は`review_contract`を必ず渡す。YAML契約は起動前に`skills/review-standards/scripts/review_contract.py --contract <review-contract.yamlの絶対パス> --target-repo <対象リポジトリの絶対パス>`を実行する。終了コード0と警告の不在を確認する。バリデーターはschema、宣言したcommitの対象リポジトリでの解決、宣言したAWIのキュー原本からの取得、及び各参照が条項へ現れることを検証する。起動文の`review_contract`には短い直接契約か検証済みYAMLの絶対パスの一方だけを渡す。
そのthreadが継続不能と確定し、初回に`review_contract`を渡していた場合は、同じ生成元から再生成して新しい実行レビュー担当へ渡す。
あわせて、`レビュー種別: 引き継ぎ再レビュー`、直前修正の直接影響範囲、次の項目だけを渡す。

- `計画`では計画ファイルの絶対パス。`CI記録`では起動文へ直接記載するCI記録と`起点commitOID`及び`原因commitOID`。再帰的CI失敗ではCI記録と`原因commitOID`を今回の原因commitへ更新する。`WI`では、計画へ現れないWIについてファイル名、要求、完成条件、由来、採否のWI記録と、`計画`を併せて渡さない場合の`処理開始OID`

任意入力の`対象ファイル限定`を用いる場合は、その対象も渡す。
対象リポジトリ、対象worktree、規範、レビュー対象HEADと変更ファイル一覧は、実行レビュー担当が現行のGit状態から解決する。開始時点の7文字以上の一意な短縮OID、検証結果及びレビュー指摘管理表は、`計画`を含む場合は実行レビュー担当が計画と同stemの成果物から解決する。`CI記録`だけの場合と`WI`だけの場合では計画と同stemの成果物が存在しないため、開始時点とレビュー指摘管理表の絶対パスを、受領した`原因commitOID`、`起点commitOID`、`処理開始OID`から確定する。CI記録はメインが原因commitの生成時に保持した情報から起動文へ直接記載する。
継続不能の判定と引き継ぎ手順は`agent-toolkit:delegation`のSKILL.mdの`## 継続と新規起動`に従う。

実行レビュー担当を起動する前に、必須入力の`レビュー基準`、`引き継ぎ記録先`、`完成条件証拠`と、渡す基準ごとの追加入力が値を持つことを確認する。`WI`を含む場合、又は計画に`ユーザー指示`行がある場合は`完成条件証拠`が管理対象一時領域にあるJSON出力先の絶対パスで、その親ディレクトリが実在することを確認する。どちらも無い場合は値`なし`を確認する。計画外の条項がある場合は検証済み`review_contract`も必要とする。既存の実体を指す絶対パスの実在も確認する。全てのレビュー基準、開始時点、レビュー表及び渡す`review_contract`が、`cwd`で解決する同じ対象リポジトリに属することも確認する。
いずれかが欠ける場合は実行レビュー担当を起動せず、欠けていた入力項目又は条項を呼び出し元へ返す。

## レビュー修正

初回の新規起動ではレビュー基準、`引き継ぎ記録先`、`完成条件証拠`と、計画外の条項がある場合は検証済み`review_contract`の絶対パスを`extra_params`へ追加する。`引き継ぎ記録先`の値はその委譲で初めて渡すため絶対パスへ`（新規）`を続けた値とする。

指摘への修正は、そのworktreeを所有する主体が実施する。起動方法ごとの主体と反復の調整は`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`が定める。同じthreadを継続する場合は`レビュー指摘の対応をせよ`、`round: <ラウンド番号>`、`レビュー指摘管理表: <絶対パス>`を送り、新しい修正担当を起動しない。
同じthreadを継続できない場合は`agent-toolkit:delegation`のSKILL.mdの`## 継続と新規起動`に従い、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`## 入力`と同じ形式で新しいレーン担当を起動する。このとき`担当種別`を`レビュー修正担当`とし、`再開位置`へ作業rootの計画ファイルの絶対パス、`レビュー指摘管理表`へ管理表の絶対パスを渡す。
修正する主体はレビュー表とworktreeの実体から指摘の採否、対象の実装commit及び修正方針を確定する。採否の基準は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`「実装」に、履歴統合、履歴書換え証拠の保存と回復は同書「レビュー修正の履歴統合」に、履歴書換えの遮断は`agent-toolkit:commit`の履歴書換え契約に従う。
メインがレビュー指摘管理表を読むラウンドは`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`の「応答済みの判定」が定める範囲に限る。指摘の採否と実装commitへの対応付けに加えて、成果物、Git状態、検証結果の検収も修正する主体が担う
（努力目標。メインが同じ検収を重ねると、修正1件ごとにメインのコンテキストへ成果物の全体が載る）。
修正する主体が`対応完了`を返した場合は、同書「応答済みの判定」に従って管理表の未応答件数を取得し、0件である場合だけ同じレビューthreadへ`再レビューせよ`と`round: <ラウンド番号>`の2行を送る。`対応完了（再レビュー不要）`の場合はレビューを省略する。

## 指摘管理表の保存

`WI`だけのレビュー基準では、収束後に指摘管理表を削除し、保存先はprivate-notesの外とする。その表を後から参照する主体が無く、計画バンドルの付属ファイルにも当たらないためである。
`CI記録`だけのレビュー基準では、同じ再帰的CI失敗処理で表と`起点commitOID`を継続する。収束後に`atk plans commit ci-<起点commitOID>.exec-review.tsv`で`private-notes/plans/ci/`へ保存する。`agent-toolkit:process-wi`の公開工程では、この保存操作を終端担当が実行する。
`計画`を含むレビュー基準では、計画を所有する主体が`agent-toolkit:plan-mode`の計画ファイル基準「計画ファイルの保存と参照」に従って計画バンドルとともに保存する。
