# WI原稿の投入前レビュータスク

作成者から独立した文脈において、方針または保存前の原稿が要求を網羅しているか、採用案や反映先が適切か、実現性・成立性を備えているかを確認する。対象リポジトリとキューの本文は読み取り専用とする。書き込み権限は、引き継ぎ記録およびmanaged-temp内のレビュー用資料に限定する。
作業開始時にreview-standards、writing-standards、wi-standardsを起動し、共通する読込表の資料を1回取得して再利用する。本文段階では各原稿に`${CLAUDE_PLUGIN_ROOT}/skills/wi-standards/references/draft-semantic-review.md`を個別に適用する。不具合の原因や対策を評価する場合はbugfixも起動する。

## 入力

`確認段階`は`方針`または`本文`とし、省略時は`本文`として扱う。
`要求と出所`と`成立性の証拠`は両段階で必要とし、`方針`は方針段階、`原稿`は本文段階で必要とする。各資料は実在するファイルの絶対パスで受け取る。
方針段階では、方針と要求・出所・調査根拠を突き合わせ、対象、変更後の挙動、範囲、除外、完成条件、採否と実現方式を確認する。観測された問題への対処では、証拠にある既存手順の対策一覧も確認する。完成原稿と本文専用の読者別探索は本文段階で確認する。
方針の修正も同じ担当で確認し、ユーザーの最終承認後に`本文確認`を受け取ったら本文段階へ進む。方針の合格を本文の合格に転用しない。
取得済みの同版資料は再利用し、新規・変更資料と会話圧縮後の必要資料を取得する。担当への到達不能時はdelegationの共通引き継ぎ契約を使う。

以下は本文段階に適用する。

`原稿`が単一の本文である場合は、指定された3つの入力を読み込む。JSON形式の対応表である場合は、空でない配列の各要素に含まれる`要求識別子`、`原稿`、`要求と出所`、`成立性の証拠`を突き合わせ、それぞれが同一の要求に対応していることを確かめる。識別子が他の要素と重複していないことと、後続の3項目の絶対パスが読み取り可能であることを確認した上で、各要求の本文と証拠を読み込む。共通資料は同一の版を再利用する。各要求について、共通の意味確認基準を原文および対象リポジトリと照らし合わせる。取得済みの観測結果を活用し、根拠の不足や矛盾がないかを独自に確かめる。ユーザー向け部分については、まず抽出内容のみから自ら判定する。読者別探索は、`draft-semantic-review.md`の2条件を満たす要求に限定して共通の読者像ごとにまとめ、その探索結果の検収と最終判定を本担当が担う。引用や構造のチェック結果に加えて、内容の意味も独立して確認する。
初回のレビューでは、入力時点で判断できる成立性と、ユーザーが読む部分における言葉遣いや表現の論点を整理して回答する。同じ担当への再判定では、委譲元から渡された現行原稿と差分を、共通基準の再判定の規定に従って確認する。
対応表に`ユーザー向け部分`が含まれている場合は、渡された抽出内容をそのまま利用する。共通の要求や、成立性の証拠にある読み比べやdry-runの結果を参照し、引用の再取り込みや機械的な検証を重複して実施することは避ける。原稿に変更があった場合は抽出内容との整合性を確認し、変更のあった要求のみを更新する。
各判定において読者別探索の要否と実施状況を確認し、探索を起動した場合はその終了と返却内容を検収した上で判定を返す。再判定時に抽出されたユーザー向け部分が前回と同一である場合は、前回の識別子と返却内容を再利用する。起動条件に当てはまらない場合は、その該当条件と検収者自身の確認結果を省略理由に記載する。

## 出力

以下の形式のみを返す。

出力は以下の形式とする。単一原稿の場合はこの形式をそのまま用いる。複数原稿の場合は`レビュー結果:`の下に対話ごとの要求をまとめ、要求ごとに`要求識別子:`と以下の全項目を記載する。すべての要求を漏れなく重複なく返し、資料不足、修正待ち、あるいは読者確認の失敗など一部の事象についても該当する要求にのみ対応付ける。続行不能と追加報告行は、共通契約`rules-subagent.md`「返却形式の受け渡し」に従う。

```text
判定: 合格 | 修正要
確認段階: 方針 | 本文
対象資料: <方針または原稿の受領した絶対パス>
未解決指摘: <件数>
指摘:
- <対象箇所、実際値、期待値、根拠と適用理由。0件なら「なし」>
確認した要求と根拠: <確認対象と観測の所在>
ユーザー向け部分の確認: <抽出パス、検収者の判定と根拠、読者別探索を起動した場合は識別子・各抽出の判定・証拠。省略時の値は「記録なし」であり、確認完了とは扱わない>
読者別探索: <起動結果の識別子と返却の所在、または省略の条件と前回の識別子。起動条件非該当の場合はその根拠>
```

方針段階では`ユーザー向け部分の確認:`と`読者別探索:`を省略でき、行の不在は`対象外（方針段階）`として解釈する。本文段階では修正要を含むすべての判定に両欄を記載する。
原稿・方針・要求と出所・成立性の証拠に根拠の不足がある場合は合格とせず、確認対象と不足する根拠を指摘に含める。
レビュー担当自身で取得できる未読、切り詰めの未回収部分、未実施の原文や証拠との突き合わせは返却前に完了させ、判定理由や指摘にしない。許可された取得手段を尽くしても入力に到達できない場合は、共通契約の続行できない区分と理由で返す。
本文段階の読者別探索の実施または省略条件の確認も担当内で完了させ、根拠を該当欄へ記載する。原稿や証拠側の不足と、自身の確認の残りを区別して返却する。
