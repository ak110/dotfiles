# 単一担当の実行契約

処理対象のWIを持つ1人の担当者が、計画、実装、独立した実行レビューの調整、修正および最終化を一貫して同じthread内で進める。レーン専用の作業資源を渡す呼出側では、レーン数にかかわらず各レーンのworktreeを担当するレーン担当者へこの契約を適用する。これは、メインエージェントとレーン担当者が同じ計画やレビュー結果を重複して読み込み、同一の判断を繰り返す定型的な往復処理を省くためである。対象worktreeへ直接実装する呼出側では、そのworktreeへの書き込みを担当するメインエージェント自身へ適用する。

初期選定で複数レーンが立ち上がっている場合は、メインエージェントが処理対象の選定、レーン間の書き込み競合と依存関係の調停、ユーザー判断の中継、主作業ツリーへの直列統合の許可、および最終結果の検収を担う。レーン担当者は、独立した実行レビュー担当の起動、指摘への対応、再レビューの調整、完成条件証拠の受領確認を担う。

## 入力と書込所有

呼出側が固定したWIの集合、対象worktree、開始HEAD、引き継ぎ記録、既存の認可を使用する。process-wiのメインエージェントは、準備済みの資源記録、選定原本、統合先worktreeおよびブランチを初回起動時に渡す。レーン開始時刻は初回起動直後に1回通知し、以後はその値を保持する。編集対象の境界はWIの要求とし、計画に含まれないファイルの取り扱いは「継続する工程」に従う。
書き込み担当者の一覧は、`exec.parent.md`の同名入力として初回に受領し、担当の交代、再開、追送のタイミングで更新する。
単一の書き込み担当者（単一writer）と、独立した実行レビュー体制を維持する。process-wiにおける専用資源の作成、統合、回収には既存のlane CLIを使用し、主作業ツリーへの書き込みは統合時にのみ行う。

## 継続する工程

1. 計画の要否を判定し、必要な計画の起草、自己監査、および計画構造の自動チェックを完了する。採否の判定と既存認可への適合は自身で検収する。ユーザー固有の判断が必要な事項が残る場合は、委譲されたレーン担当者がメインエージェントへ直ちに通知し、直接実装を担当するメインエージェントは呼出側の確認手段を用いてユーザーへ確認する。計画を作成しない場合も同様の判定手順に従う。実装を伴う項目は手順2〜4へ進み、実装やマージを伴わない項目は採否を確定した上で手順5へ進む。
2. 計画またはWIの要求に基づき、実装に着手する前に受入シナリオにおける公開された呼び出し手段、入力と初期状態、有効な期待結果、検出対象の失敗条件を具体化する。通常の変更範囲検証と受入確認について、対象、入力・環境条件、期待結果およびレビューで必要な出力を比較し、両方を観測できる実行を初回から選ぶ。両立しない条件、先行結果を失効させる差分、または別の結果そのものを要求する条件は別実行として残す。対象プロジェクトの定義と公開入力から起動形を選ぶ`agent-basics:check-execution/references/verification-scope.md`に従って適切なテストを選択し、実装、自己検収、commit、`検証結果`の作成を完了させる。計画を作成しない場合やレビュー指摘に基づく修正時にも同様に対応し、不具合は該当する入力を用いて再現させた上で修正する。呼び出し手段、入力、期待結果と実際の結果の対応関係、未実施や条件変更の判断、残る工程の担当と再開先を、既存の引き継ぎ記録および進捗ログの`検証結果`へ記録する。計画準備、実装開始、実装完了の各状態を保存し、同一の担当者が処理を継続する。
3. 読込表に定める起動契約に従い、実装を担当していない独立した実行レビュー担当者を起動する。起動前に`verification-evidence.md`に従い、取得版、入力条件および要求別の観測箇所を同じ検証記録へ対応付ける。レビュー担当はその記録を独立に読み、保存済み成功の適用可否と、不足または影響差分に限った追加観測を判断する。レビュー指摘管理表の作成や完成条件証拠の受領確認は同書の規定に従う。画面差分が存在する場合は、読込表のユーザビリティレビュー契約に従ってレビュー担当者を起動する。各計画のレビュー基準および開始HEADは保持する。
4. `${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`の手順に従って指摘事項を収束させ、修正作業とGit履歴の統合は自身で実施する。要件や認可の変更、事後承認の確認が必要な場合は、手順1に定める主体分担に従って対応する。事後承認はレビュー収束後かつ統合前の内容に基づいて発行し、レーン担当者はメインエージェントから保存結果を受け取る。作業中に生じる通常の問い合わせや状況確認には次の応答で回答し、元の作業工程へ復帰する。WIへ直接記入された質問に対する回答用UWIの保存は、呼出側のレビュー収束後の保存手順に従う。
5. レーン専用の資源を使用している場合は、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に定める検収を自ら実施する。読込表に記載されたレーン担当の契約に従い、検収済みHEAD、全計画、WI、採否、および受理した返却ファイルと`レビューHEAD`の組み合わせに基づいて統合入力を確定する。初期選定が複数レーンである場合は、統合入力を確定した後に`exec.subagent.md`「出力」の`統合準備完了`を返し、メインエージェントから`統合許可`を受け取ってから統合を進める（主作業ツリーへ統合するレーンを常に1つに制限するため）。`atk lane integrate`を実行して統合、計画保存、WIの終端処理を最終化し、`phase: finalized`を確認した上で通常の`統合完了`形式のみをメインエージェントへ返す。対象worktreeへ直接実装している場合は、既存の受領確認を完了した後に呼出側の計画保存、WI終端、公開工程へ戻る。実装を伴う対象は独立した実行レビューを受理した後に、実装やマージを伴わない対象は採否を確定した後に、それぞれ本手順を実施する。

本契約の対象となる作業では、exec.parent.md、exec.subagent.md、lane-planning.mdに定める定型的な準備通知、実装開始、実装完了、レビュー修正、統合開始の往復処理や、応答を待つ指示を省く。本節に定める同一担当者による継続実行を優先する。ただし、計画の自己監査、計画構造の自動チェック、採否や認可の検収、計画の凍結、独立した実行レビューの実施、統合時の検収条件は維持する。エージェント向け文書を含む書き込み認可の境界はWIの要求とし、その境界の内側で計画に含まれていないファイルを作成・編集する場合や、WIの要求を超える変更が生じる場合の扱いは、exec.subagent.md「実装」に従う。ユーザー判断の即時通知、必要な回答の待機、最終結果の検収は維持する。実装やマージを行わない場合であっても、採否の確定、計画の保存、WIの終端処理は完了させる。

## 追加と再開

同一レーンへWIを追加する場合は、選定原本へ反映された集合のみを受け取り、すでに凍結された計画を維持した上で追加計画から作業を再開する。レビューや再統合の調整も同一の担当者が担う。作業が中断された場合は、資源記録と引き継ぎ記録に基づいて未完了の工程へ復帰し、完了済みの最終化処理を重複して実行しないようにする。メインエージェントは、作業の追加や中断からの再開時においても、定型的な工程調整を引き取ることはしない。
手動起動、process-loop、all-reposのリポジトリ担当エージェントに対しても同一の契約を適用する。複数レーンで開始した実行は、途中で稼働中のレーンが1つになった場合であっても、必ず`統合許可`を得てから統合を実行する。資源はセッション終了時の回収まで保持し、未統合の差分、dirtyな状態、稼働中の状態、所有主体が不明な成果物を確実に保持する。
