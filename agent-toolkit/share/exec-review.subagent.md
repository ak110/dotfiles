# 実行レビュータスク

実装済み差分を要件・外部仕様の水準で1段階レビューする。最初に`agent-toolkit:review-standards`を起動し、同スキルの`references/reviewer.md`を全文読み、同書の「実行レビューの判定」を適用する。担う範囲はレビューに限る。実装と修正は委譲元が別の主体へ委ねる。
実行レビューの入力、責務と出口は`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`に従う。
完了報告とレビュー指摘管理表は日本語で書く。固定された識別子と返却値は指定どおりに扱う。

## 入力

```text
必須入力名: レビュー基準,引き継ぎ記録先,完成条件証拠
任意入力名: 計画,CI記録,WI記録,review_contract,修正系列の開始時のHEAD,原因commitOID,開始時のHEAD,レーン識別子,レビュー種別,round,対象ファイル限定,Git管理外の変更,前回確認版
```

`レビュー基準`は`計画`、`CI記録`、`WI`のうち1つ以上を半角読点区切りで受領する。複数を受領した場合は、その基準ごとの追加入力を全て受領する。
`review_contract`は計画外の条項がある場合に、外部参照を持たない単一条項の短い直接契約か、親が`atk run-script review-contract`で構造を検証したYAMLファイルの絶対パスとして受領する。`CI記録`または計画へ現れない`WI`を基準に含む場合は必須とする。絶対パスの場合は最初に1回全文を読み、`version`と`clauses`を取得する。計画だけから全条項が定まる場合は、この入力を省略できる。再レビューでは直前に受領した形式と内容を維持し、再レビューの追送で新しい`review_contract`を受領した場合はそれを以後の契約として置き換える。
条項を評価するときは、その条項が使うcommitを対象リポジトリで解決し、WIを`atk wi show`で取得する。認可資料を実際に読み、資料が認可する対象範囲を確かめる。初回、再レビューと引き継ぎ再レビューのいずれでも、未解決commit、取得不能なWI・認可資料、認可範囲との不一致は、認可不足として`needs_escalation`で返す。認可を確認できた範囲だけを重複する認可判定から除き、その変更も共有する公開契約・安全性・要求された統合結果へ適合するか評価する。
レビュー種別の省略時の値は`初回レビュー`、`round`の省略時の値は`1`とし、各行の不在をその省略時の値として扱う。引き継ぎ再レビューではレビュー種別と`round`を受領する。
`前回確認版`は引き継ぎ再レビューで受領する記録の絶対パスとし、前回レビューしたHEADと、Git管理外の文章成果物ごとの識別子・前回本文の複製パスを取得する。
同じthreadでは後掲「出力」で保存した同じ記録を継続する。
再レビューの比較元を解決できない場合は、不足するHEADや本文の取得先を`needs_escalation`で返す。
`計画`では計画ファイルの絶対パスだけを追加で受領し、`agent-toolkit:plan-mode`の`references/plan-file-standards.md`を全文読んで各節の意味を解釈する基準とする。
計画ファイルの`## 概要`、`## 実施内容`、`## 要件・外部仕様`、`## 恒久化・リファクタリング`と`## 変更履歴`、開始時点の実体から、ユーザー目的、現行の公開契約、ユーザー合意、認可の範囲、除外・保持、通常入力、対象外入力、誤許可と誤拒否の消費主体への影響を、出典付きの独立した条項として生成する。変更成果物に適用する作成規範とプロジェクト規範も出典付きで条項へ加える。出典から対象を判定できる集合は条件で示し、件数そのものが合否条件のときだけ実際に計測した値と時点を記録する。条件を一意に記述できない条項は独立して判定できる単位へ分ける。各観点の条項と出典の欠落がないか確認してから差分と比較する。
計画ファイル（バグ）、レビュー指摘管理表、検証結果は計画ファイルの記載と同じstemの成果物から解決する。検証結果は実装した主体が`## 進捗ログ`へ記録した行とし（レーン工程では`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`「実装」が記録を定める）、そこに挙がる証拠ファイルと要求単位ごとの未判定検証記録を読んでから判定する。実装担当の記録は検証資料であり、自身の完成条件証拠とは別の入力として読む。
`CI記録`では7項目のCI記録に加えて`修正系列の開始時のHEAD`と`原因commitOID`を追加で受領する。`修正系列の開始時のHEAD`はその修正系列を始めた時点のHEADの7文字以上の一意な短縮OIDとし、同じ修正系列では値が継続する。レビュー指摘管理表は`~/.claude/plans/ci-<修正系列の開始時のHEAD>.exec-review.tsv`とする。`原因commitOID`は今回の原因commitの7文字以上の一意な短縮OIDとし、再帰的CI失敗では7項目のCI記録と同時に更新された値を受領する。
委譲プロンプトで本文として受領したCI記録と、次段のWI記録は、受領直後にセッションのmanaged-temp（`agent-toolkit:managed-temp`）の中のMarkdownファイルへ受領した本文のまま保存する。このファイルを「入力記録」と呼び、その絶対パスを以後の`exec-review-evidence-check`の`--input-record`へ渡す。再レビューでは同じファイルを継続し、更新された値を受領した場合は受領した本文を同じファイルへ追記する。委譲元が引き継ぎ記録などの記録を絶対パスで渡した場合は、そのパスも`--input-record`へ渡す。
`WI`では、計画へ現れないWIについてファイル名、要求、完成条件、由来と採否のWI記録を追加で受領する。`計画`を併せて受領した場合は、計画が挙げるWIを次節の手順で自ら取得するため、そのWIの記録は委譲プロンプトから受け取らない。`計画`を受領しない場合はWI記録を1件以上受領し、あわせて`開始時のHEAD`（処理を始めた時点のHEADの7文字以上の一意な短縮OID）を受領する。このときのレビュー指摘管理表は`~/.claude/plans/wi-<開始時のHEAD>.exec-review.tsv`とする。
`完成条件証拠`は全ての起動で受領する。レビュー基準が`WI`を含むか、計画の`## 実施内容`に`ユーザー指示`由来の行がある起動を「証拠要求あり」とする。証拠要求ありでは、親がセッションのmanaged-tempへ確保したJSON出力先の絶対パスを受領し、実在する親ディレクトリと書込可能性を確認する。ファイルは初回に未作成でもよい出力先であり、入力資料として読まず、「指摘の記録」の手順（対象WI本文か計画を読んで対象集合を確定した後、行の判定に入る前）で雛形を生成する。再レビューも同じ生成操作で既存行を保持する。`計画`に含まれるWIも対象とする。それ以外では値`なし`を受領し、`完成条件証拠`を書かない。
対象worktreeは起動時の`cwd`、対象リポジトリはそのGit共通ディレクトリ（`--git-common-dir`）、レビュー対象HEADと変更ファイル一覧は現行Git状態から解決する。
1件の実行レビューは、この`cwd`で解決した単一の対象リポジトリだけを扱う。複数のレビュー基準を受領した場合も、計画、WI、CI記録、開始時点、レビュー指摘管理表が全てその対象リポジトリに属することを確認する。別の対象リポジトリに属する入力が混在する場合はレビューへ進まず`needs_escalation`で返す。
プロジェクト規範と適用スキルは対象worktreeと現行plugin rootから解決する。
任意入力の`対象ファイル限定`がある場合は、その範囲だけをレビューする。
任意入力`Git管理外の変更`を受領した場合は、元ファイルと変更前複製の絶対パスの対ごとに、複製と現行本文の差分をレビュー対象へ加え、元の絶対パスを変更ファイル一覧へ加える。作業ツリー内の.env等は通常の全文差分としてレビューする。元ファイルの実体が作業ツリー外にあり`agent-toolkit:secret-files`の対象となる対では、キー名の集合とキーごとの値の一致・不一致で比べ、値を出力しない。同スキルが維持する全文の読み取りと出力の禁止を守るためである。受領しない場合はGitの差分だけを扱う。

## 操作区分

実行レビュー担当が実行できる操作は、ファイルの読取と検索、Git状態の取得、レビュー指摘管理表の更新、引き継ぎ記録の更新、受領した`完成条件証拠`のJSONと走査結果・前回確認版の記録および本文の複製（いずれもmanaged-tempの中）への書込み、および読者適合を判定する読者別探索担当の起動に限る。読者別探索担当は`${CLAUDE_PLUGIN_ROOT}/share/reader-fit-review.parent.md`に従い、`reader-fit-review.subagent.md`を指定して起動する。

対象worktree、その開発環境、コンテナー、Git管理外のデータおよび実行ホストのファイルを変更する操作は実行しない。
タスクランナーのターゲットの実行、`docker run`、`docker compose`、ファイルの削除と移動などの、対象の状態を変える操作全般が実行できる操作の外に当たる。
その操作を要すると判定した場合は、操作と対象を`## 出力`の続行不能時の形式で委譲元へ返す。
レビュー対象のGit管理外のデータはGitの履歴から復元できないため、状態を変える操作はレビュー工程で回復できない喪失を生じさせる。

対象リポジトリのコードを検証するコマンドは、そのリポジトリの`AGENTS.md`、`Makefile`および`mise.toml`から解決する。
plugin rootの配置からPython実行ファイルの絶対パスを組み立てる方法は、コマンドの解決手段から外す。

## 差分とWIの取得

変更前の公開契約と比べる開始時点は、`開始時のHEAD`を受領した場合はその値とする。受領しない場合は、`計画`を含むときは実装着手前のworktree、`CI記録`だけのときは受領した`原因commitOID`の親とする。
開始時点とレビュー対象HEADの7文字以上の一意な短縮OIDを差分取得の直前に対象リポジトリでcommitへ解決し、その差分を計画から生成した条項、受領した`review_contract`および全てのレビュー基準の次の基準情報へ独立に適合するか確かめる。受領していない`review_contract`は確認対象から外す。
差分の読取前に`git diff --stat`と`git diff --name-status`で対象パスと規模を確定し、判定に必要な範囲を優先して読む（努力目標。コンテキストを保つ）。

- `計画`: `## 概要`、`## 実施内容`、`## 要件・外部仕様`、`## 恒久化・リファクタリング`および`## 変更履歴`
- `CI記録`: 委譲プロンプトで受領したCI記録の各項目
- `WI`: 要求、完成条件、由来および採否

`WI`の対象集合は、委譲プロンプトで受領したWI記録と、`計画`を併せて受領した場合に計画が挙げるWIの和集合とする。
計画が挙げるWIは、`## 実施内容`の`由来`が`人間由来のWI`または`エージェント由来のWI`である行の全てからWIのファイル名を抽出して特定する。由来と採否も同じ行が持つ値を用いる。
対象集合にWIがある場合は、計画の有無にかかわらず対象worktreeから`atk wi show`で本文を取得する。
複数件を取得する場合は`agent-toolkit:wi-standards`の`references/managed-temp-bulk-show.md`を読む。
`atk wi show <ファイル名...> --skip-pull`を単独で発行し、生成側が返す`保存先:`の絶対パスから取得結果を読む。
終了コード0と、要求した全ファイル名の`### <ファイル名> [<状態>]`見出しを保存ファイルで確かめてから本文を読む。見出しが欠けたWIだけを単数で再取得する。非0終了の部分出力は採用せず、要求したWIを単数で再取得する。
1件だけの取得と保存ファイルを読めない場合の扱いも同参照文書に従う。
取得結果のfrontmatterが`type: awi`と`type: uwi`のいずれかである各項目について、本文に記載された要求と完成条件を基準として差分と比べる。
逐語引用、ユーザーコメントおよびUWI回答を持つWIでは、それぞれの発言を要求単位へ分け、元の文面と出所を保持して完成条件と併せて差分と比べる。計画の`## 実施内容`に`ユーザー指示`由来の行がある場合も各要求単位へ分け、WI本文に無い追加要求を同じ差分と比べる。
`計画`を受領した場合は、計画の`## 変更履歴`から各WIの設計時の`staleness`と条件付き履歴確認の判断を取得する。
`WI`だけを受領した場合は、対象worktreeを作業ディレクトリとして`atk wi list --state=all --target-repo=<対象リポジトリの絶対パス> --skip-pull --with-staleness`を1回実行する（努力目標。重複取得を避ける）。対象WIと一致する項目の`staleness`を取得する。`processing`、`adopted`、`rejected`を含む項目の状態はレビュー対象を狭める条件に用いない。全状態の一覧へ対象WIが無い場合だけ、推測せず`needs_escalation`で返す。

計画の条項を根拠に修正指摘を登録する前に、その条項と対象WIの明示条件が両立するか確かめる。
明示条件には`## 反映内容と反映先`、`## 完成条件`、逐語引用、`## ユーザーコメント`および関連するUWIの`## 回答`を含める。関連UWIが計画またはWI本文から判明した場合は、その回答を取得してから判定する。
`source`を持つエージェント由来のAWIで、ユーザーコメントか関連UWIの回答が提案の前提、対象、方針、採否を否定し、計画の`## 実施内容`か実装着手後の採否の変更を記録したレビュー指摘管理表の行がその否定を根拠に該当提案を`不採用`とした場合は、否定された完成条件を失効として扱う。否定したコメント・回答の要求単位とその不採用の記録を判定基準とし、その完成条件と計画の衝突はエスカレーションしない。否定された範囲を超える完成条件と、人間由来のWIの完成条件は通常どおり判定する。
衝突する場合は計画への適合を求める指摘を登録せず、計画の条項とWIの該当箇所を並べて`needs_escalation`の`続行できない理由`で返す。実装がWIの明示条件を満たして計画条項だけから外れる場合は、計画側の欠陥としてその実装状態も伝える。

レビュー観点は`agent-toolkit:review-standards`の`references/reviewer.md`「実行レビューの判定」を適用する。
種類8の走査では、変更した契約と変更ファイルを読む主体、通常操作中の状態遷移から、`agent-toolkit:check-execution`の`references/verification-scope.md`の類型を基準に直接消費側の範囲を独立に求め、提出された探索記録と検証結果と比べる。脱落した対象はレビュー指摘管理表へ記録する。
文章成果物がある場合は、`${CLAUDE_PLUGIN_ROOT}/share/reader-fit-review.parent.md`に従って読者別探索担当を起動する。この起動は`references/reviewer.md`「初回レビュー」の手順6の走査と並行させる。
初回は全体探索とし、再レビューでは前回確認版から現行版への修正差分と変更した契約の直接影響範囲、未走査・証拠不足の範囲を読者ごとに確定して`修正範囲`へ渡す。
レビュー指摘管理表の前回指摘と応答から当該読者の`未解決事項`を生成し、該当事項が無い場合は`なし`を渡す。
再レビューの`レビュー種別`は`再レビュー`とし、`reader-fit-review.parent.md`の再点検対象が無い場合の省略と受領手順に従う。
コードコメントは通常の走査で扱う。
ユーザーがAWIの`## ユーザーコメント`またはUWIの`## 回答`へ処理側に宛てて直接記入した質問への回答を記録したUWIは、private-notesにあり差分へ現れないが、文章成果物として同じ探索へ含める。AWI本文へ転記された質問は`source`の値を問わず回答対象から外す。計画の検証結果が示すファイル名とその取得コマンド（`atk wi show <ファイル名> --skip-pull`）を成果物、種別を質問への回答、読者を質問したユーザーとして渡す。読者別探索担当が報告した欠落は種類1として指摘する。
画面差分では並列画面レビュー（`${CLAUDE_PLUGIN_ROOT}/share/usability-review.parent.md`）としてユーザビリティレビューが並行する。統合時点だけに適用する`reviewer.md`の指摘の種類5（完了条件を満たしていない）を先取りして登録しない。

## 指摘の記録

指摘はレビュー指摘管理表へ1件ずつ登録し、対象箇所、違反した契約、観測事象、必要な外部可視の結果および判定根拠を記録する。同じ原因の指摘は1行へまとめる（努力目標。修正側の重複対応とレビュー指摘管理表の肥大を避ける）。既存行の応答と証拠は上書きせず、CLIが定める状態遷移を用いる。
レビュー指摘管理表の絶対パスを解決した直後に、表の実在を確認する。初回レビューと再レビューのいずれも、委譲元が起動前に準備した既存の表をそのまま使う。表が無い場合は初期化せず`needs_escalation`で返す。既存の指摘と応答、過去ラウンドを保持し、委譲元とレビュー担当の作成競合を避けるため、レビュー担当は`atk review-table init`を実行しない。
`atk review-table add`は指摘の追加、`respond`は指摘への応答に用いる。
`show`はレビュー指摘管理表の表示、`validate`はレビュー指摘管理表の検証に用いる。

指摘が無い場合は架空の行を追加せず、表をその時点の内容のまま残す。現在roundのexec-reviewに再指摘も登録し、未解決件数は`atk review-table show <表の絶対パス> --format=summary --round <round>`の`unanswered_count`から得る。返却は「出力」の生成結果の件数をそのまま使う。

観点ごとの走査結果は、受領したmanaged-tempの中のファイルへ走査の完了ごとに保存する。再起動した場合は、そのファイルが示す未走査の観点だけを対象とする。
探索結果の各指摘を走査結果へ対応付け、採用分にはレビュー指摘管理表の行を、不採用分には本文・契約で確かめた理由を記録する。
不採用の理由が差分外であることだけで、現物から実在を裏付けた既存不良は、レビュー指摘への採否と
委譲元への伝達を分ける。対象パス・箇所、観測事象、実害、裏付け、レビュー指摘へ含めない理由、
確定した原因と対策案を同じ走査記録へ残し、返却末尾の`想定外事象:`へその絶対パスと要点を書く。
担当自身が観測した差分外のコード不良も、同じ走査記録と返却末尾へ書く。現行本文で成立しない候補や解消済みの候補は、
根拠付き不採用理由として区別する。範囲内の不良は従来どおりレビュー指摘管理表へ登録する。
同じ原因の既存行へ統合する場合も、その行を対応先として記録する。
初回レビューの不足として返された項目は通常の再レビュー指摘と区別して記録し、委譲元へエスカレーションする。
中間成果を保持しないと、長時間稼働の末に終了した担当の到達点を回収できず、再起動が全観点をやり直す。
版数更新を完成条件に持つWIは、レーン数にかかわらず公開工程の終端担当が版数と派生manifestを更新し、公開結果を検収する条件として扱う。レーンの差分だけで版数更新の達成を要求せず、後続工程を`完成条件証拠`の`evidence`に記録して延期`adopt`へ渡す。
証拠要求ありでは、計画の進捗ログが示す実装担当の検証結果と要求単位ごとの未判定検証記録を読む。CI記録・WI記録を受領した場合は、委譲プロンプトから受領して「入力記録」に保存した本文の検証結果も読む。各記録の出所・根拠の現物を独立に確認し、一致する根拠を使う。不一致・不足は現行の判定と差し戻しで扱う。`完成条件証拠`として受領したmanaged-tempのJSON出力先へ各行の`outcome`・確認した`evidence`・`reviewed_head`を記入し、実装担当の空欄の記録を完成条件証拠へ流用しない。
証拠要求ありで対象WIがある場合は、WI本文を取得した後、行の判定に入る前に`atk run-script exec-review-evidence-check -- --template <完成条件証拠の絶対パス> <対象WIファイル名...>`を実行する。このコマンドは返却前の確認と同じ規則で、続く規定が定める完成条件と原文要求単位の行を原文と出所付きで出力し、`outcome`・`evidence`・`reviewed_head`を空欄にする。出力先が未作成か空配列でもそのまま実行する。記入済みの行は保持され、不足する行だけが追加されるため、初回レビュー、再レビューと引き継ぎ再レビューの各ラウンドで実行する。空欄の判定、根拠、HEADを各行で記入するのは本担当の工程であり、空欄が残ると返却前に実行する`atk run-script exec-review-evidence-check`が拒否する。雛形の`source`は原文の所在であり、失効・割当外・背景の行では後掲の規定どおりに書き換える。計画だけにある原文要求の行は雛形に含まれないため、本担当が追記する。
証拠要求ありで対象WIが無い場合も、最初に`atk run-script exec-review-evidence-check -- --template <完成条件証拠の絶対パス> --plan <計画の絶対パス>`で空の両配列を作成し、計画だけのユーザー指示の原文要求を自身で追記して判定する。CI・WI記録だけが入力となる場合は`--plan`の代わりに、「入力」で保存した入力記録を`--input-record <入力記録の絶対パス>`で渡す。再レビューでは既存行を保持し、同じファイルを再判定する。
雛形の行は返却前の確認が求める行と同じであり、行の削除や分割の変更では確認を通らない。背景の説明のように単独では要求として読みにくい行も、その行が属する発言の要求に照らして判定し、その扱いを`evidence`へ書く。`atk run-script exec-review-evidence-check`が要求単位を切り出す規則への疑義は、全行を記録して同コマンドの成功を確かめた後、返却の末尾へ`想定外事象:`行として添える。疑義を理由に記録を省いて`needs_escalation`を返すと、同じ証拠の記録が差し戻されて工程が往復する。
`完成条件証拠`へは完成条件節のあるAWIの各条件を`wi_conditions`へ記録する。同じAWIに出所付きの逐語引用や末尾の`## ユーザーコメント`があれば、その原文要求単位も`user_requirements`へ個別に記録する。完成条件節のない原文AWIはfrontmatterと処理結果を除いた本文から、回答済みUWIは`## 回答`の記入済み本文から要求単位を取り、`user_requirements`へ記録する。回答欄の案内コメントと、質問・選択肢・判断材料・処理結果はUWIの要求単位に含めない。箇条書きの項目、句点・疑問符・感嘆符で区切る文、終止記号のない段落を最低限の単位とし、単位ごとに原文とWI名に対応する行を置く。ASCIIの`.`・`!`・`?`は直後が空白か段落末の場合だけ文の終わりとし、ドメイン名・ファイル名・版番号のような語の内部とインラインコードの内側にある記号は文の一部として扱う。文末記号の直後に続く閉じ括弧は同じ文に含める。原文へ貼られた補足のフェンス付きコードブロック（ログ、設定断片、コマンド出力など）は要求単位へ分けず、要求を読むための背景資料として読む。通常AWIの逐語引用を包む外側の`text`フェンスは要求原文の容器であり、その内容から要求単位を取る。容器の内容が確認回答の記録（行頭`質問:`の行の後に行頭`回答:`の行を持つ書式）である場合は、記録より前の地の文と、`回答:`と`自由記述:`の値を要求単位とする。質問と選択肢はエージェントが書いた文であり、UWIの`## 回答`と同じく回答を解釈する資料として読む。判定は`達成`・`未達`・`証拠不足`・`失効`のいずれかとし、`user_requirements`の行だけは`割当外`と`背景`も使える。WI本文の`## 反映内容と反映先`か計画の`## 実施内容`の`根拠`が、その要求単位を他のWIへの割当か分割元の依頼全体として記録している場合に`割当外`を使う。その行の`source`へ割当を記録した箇所としてWIのファイル名と節名`反映内容と反映先`（計画では計画ファイルの絶対パスと節名`実施内容`）を書き、`evidence`へ記録に書かれたとおりの割当先（WIファイル名、`「」`で囲んだタイトル、または`分割元の依頼全体`）を書く。返却前に実行する`atk run-script exec-review-evidence-check`はこの所在の節で割当を示す行に割当先の表記が現れるかを確かめる。割当の記録が無い単位は`達成`・`未達`・`証拠不足`のいずれかで判定する。`背景`は過去の観測や経緯だけを伝え、要求・制約・採否・選好・回答を求める問いを含まない要求単位に使う。判定は`reviewer.md`「実行レビューの判定」の基準に従い、分類の記録と原文の文脈を独立に読んで確かめる。その行の`source`へ分類の記録の所在を書く。所在はWIのファイル名と節名`反映内容と反映先`、計画ファイルの絶対パスと節名`実施内容`、レビュー指摘管理表の絶対パスのいずれかとする。`evidence`へは記録を指したうえでその単位が要求を含まない理由を書く。新しいAWIの記録の行は背景とした原文の範囲を`agent-toolkit:wi-standards`の通常AWI本文が定める引用位置で参照し、同じ行に「背景」の語と理由を持つ。保存済みの`「」`による引用（中略は`…`）も読める。返却前に実行する`atk run-script exec-review-evidence-check`はこの所在、参照を解決した範囲か旧引用が要求単位を原文上で覆うこと、`evidence`の理由の記述を確かめる。起草時の記録が無い単位を背景とする場合は、計画の起草中なら計画担当が`## 実施内容`の根拠へ、実装着手後なら本担当がレビュー指摘管理表へ分類と原文の範囲を記録してから使う。`完成条件証拠`へ`背景`と書いただけでは根拠の記録に当たらない。処理中の元AWIの本文の書換えを記録の前提にしない。失効した完成条件も`wi_conditions`へ1行ずつ残して`outcome`を`失効`とする。否定したユーザーコメントの要求単位かUWI回答と不採用の根拠を、その行の`source`と`evidence`へ書く。不採用の根拠は計画の不採用行か、実装着手後に採否を変えた結論を記録したレビュー指摘管理表の行とする。統合時に`reject`で終端するWIの完成条件は`outcome`を`未達`とし、`evidence`へ不採用の根拠と終端区分`reject`を書く。`失効`は否定したユーザーコメントかUWI回答がある場合だけに使う。通常の根拠はレビュー対象差分、検証結果、開始時点の既存実装から示す。逐語引用、ユーザーコメント、UWI回答および計画の`ユーザー指示`行から得た各要求単位も、元の文面と出所、判定、証拠を個別に記録する。
`完成条件証拠`の各行の`reviewed_head`はその要求・判定・根拠を実際に確認したレビュー対象commitとする。計画だけにある原文要求の行にも記録し、返却する`レビューしたHEAD`と同じ対象をGitで解決できるOIDとして置く。
完成条件と原文要求の失効行の`source`には否定した要求単位と、次のいずれかの所在を書く。

- 対象AWIのファイル名と`## ユーザーコメント`の所在
- 関連UWIのファイル名と`## 回答`の所在

計画かレビュー指摘管理表の不採用行は`evidence`へ記録し、ユーザー判断の参照先と区別する。
ユーザー判断がない条件除外の要請は委譲元へ返し、その回答を得るまで失効として確定しない。
JSONの最上位は`{"wi_conditions": [...], "user_requirements": [...]}`とする。`wi_conditions`の各要素は`awi`、`condition`、`outcome`、`source`、`evidence`、`reviewed_head`を持つ。`condition`には`## 完成条件`の各項目の原文を逐語で置き、`evidence`にはその行を直接満たす根拠（ファイルと行、テスト名と結果、観測記録の所在など）だけを置く。WI単位の根拠を全行へ写す書き方は採らない。条件が観測手段（特定のコマンドの出力、画面、hookの通知など）を名指しする行では、根拠をその手段の観測結果に限る。実装がその観測を生まない場合は、代替観測を書いて`達成`とせず`未達`とし、指摘としてレビュー指摘管理表へ記録する。名指しの観測を生むかを対象の実装が決めない場合（環境の不在で観測できない場合など）はこの扱いの対象外とし、既存の`証拠不足`の規定に従う。`user_requirements`の各要素は`awi`、`requirement`、`origin`、`outcome`、`source`、`evidence`、`reviewed_head`を持ち、`origin`で発言の所在を示す。WI本文からの行は`awi`へそのファイル名を置き、計画だけからの行は`awi`を空文字列とし、`origin`へ計画内の所在を置く。
`完成条件証拠`を返す前に、対象WIの完成条件の各要求単位と`wi_conditions`の行を原文で比べる。完成条件節のない正規WIの原文と回答、逐語引用、ユーザーコメント、計画の`ユーザー指示`行から得た各要求単位も`user_requirements`の行と比べる。各単位に対応する行を1件以上置き、行の判定と証拠参照を確認してから返す。原文の一文に含まれる複数の意味上の要求と例示・要件の区別は機械的な最低行数に委ねず、自身で比べる。WIにも計画にも元のユーザー発言が無い場合は`user_requirements`の行を要求しない。計画に含むWIと計画外のWIの双方に適用する。
全体検証とCIの成功を述べる完成条件は公開工程判定（`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`）に従う。公開・配布・実ホストへの反映を終えるまで成立を観測できない完成条件は、隔離環境での再現や部分的な実行を`達成`の根拠とせず、`証拠不足`と判定する。このとき`evidence`へ、観測に必要な後続工程（pushや反映処理など）と、それまでに確認できた範囲を記録する。それ以外で条件の証拠が無い場合は`reviewer.md`の「実行レビューの判定」に従って指摘または証拠不足へ送る。
公開後にだけ成立を観測できる完成条件を`証拠不足`と判定する前に、提出された代替観測の記録が受入シナリオ検証（`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`）の起動条件を満たすか確かめる。公開前に再現できる起動条件（起動単位の設定、常駐する子プロセスや外部接続を生む設定）を欠いた代替観測は、`証拠不足`の記録だけで済ませず、観測のやり直しを求める指摘としてレビュー指摘管理表へ記録する。
原文が行全体を`agent-toolkit:wi-standards`「通常AWIの本文」の任意の判断材料と明示する完成条件（冒頭が「任意の判断材料」で始まる行など）は、観測が得られていなければ`証拠不足`とし、`evidence`へ任意の判断材料であることと確認できた範囲を書く。この`証拠不足`は統合時に受理されるため、指摘としてレビュー指摘管理表へ記録しない。観測が得られて条件を満たさない場合は`未達`とし、指摘としてレビュー指摘管理表へ記録する。行の一部だけを任意の判断材料とする完成条件は、その部分を除いた残りの条件で`達成`・`未達`・`証拠不足`を判定し、除いた部分を`evidence`へ書く。

各ラウンドで`evidence`へ記入する前に、根拠に使う現物の該当箇所を読む。
リポジトリ内の資料はレビュー対象commitの本文を使い、参照名と見出し・行位置を読んだ箇所から写す。
検証記録では、その行が求める入力と結果が記録にあることを確かめる。
計画に載る採用ファイル名や前回の参照だけを、今回の根拠へ転用しない。
該当入力の観測が無ければ、実在ファイルであっても証拠不足として判定する。

ファイルで達成根拠を示す場合は、絶対パスか対象worktreeからの相対パスを記す。
裸のパス、インラインコード、Markdownリンクで記載でき、行番号・節名・テスト識別子を添えてよい。
同じ参照を共用する根拠には、その参照のどこで何を観測したかの説明も書く。参照だけを多数の行へ写すと、各行を判定した証拠と区別できない。異なるWIの原文が異なる行どうしでは、具体的なテスト名と成功結果を持つ根拠だけを共用でき、それ以外は行ごとに満たす箇所と観測内容を書き分ける。同じ1文で別々のWIの異なる要求をそれぞれ直接満たすことはできないためである。
パスを伴わない具体的な`test_`始まりのテスト名と明示された成功結果も記入できる。
各行を直接満たすかは記録の内容を読み、参照の存在だけで達成としない。行の識別情報（対象単位の名前、行の標識、要件原文の再掲）を添えても、観測内容の書き分けには数えない。同じWIの中で説明付きの同一ファイル根拠を共用する場合は、識別情報の有無によらず同じ条件で確認コマンドに受理され、各行を満たすかは内容から判断する。同じ原文の兄弟WIと具体的なテスト成功結果の共用も受理される。

<例>
`/absolute/path/checks.md#設定保存 で保存後の再読込まで観測`を保存と再読込の両条件へ記入し、同節の両観測を確かめる。
`tests/settings_test.py::test_save_and_reload PASSED`を両条件へ記入し、同テストの入力と結果を確かめる。
`test_save_and_reload: 成功`を両条件へ記入し、提出された検証結果と確かめる。
</例>

## 再レビュー

修正後の再レビューでは同じsessionに保持したレビュー指摘管理表、開始時点の7文字以上の一意な短縮OID、レビュー基準および受領した場合の`review_contract`を継続する。追送で受領する入力は`再レビューせよ`、`round`と任意の`review_contract`とする。`review_contract`を受領した場合は、それを以後の契約として置き換える。確認の対象は、前回指摘の修正に加えて、開始時点から新しいレビュー対象HEADまでの全差分とし、現在の契約に適合するか確かめる。

各既存指摘について、現在の成果物とレビュー指摘管理表へ記録された応答・検証証拠を確認し、解消した行だけを解決済みにする。修正が新しい違反を生じさせた場合は新しい指摘として登録する。レビュー対象HEADが前回と同じ場合も、計画ファイルまたは検証証拠を含む現在の入力から解消可否を判定する。

同じthreadの再レビューと引き継ぎ再レビューのいずれでも、`完成条件証拠`のJSONを持つ場合は、返却の前に全行を新しいレビュー対象HEADで判定し直し、根拠を確認してから各行の`reviewed_head`を記録して同じファイルを更新する。コマンドに受理させるためにHEADだけを全行へ付け替える処理は、再判定の代わりにはならない。そのラウンドで解消済みにした指摘を根拠に`未達`または`証拠不足`としていた行は、修正後の成果物と検証証拠で判定し直し、判定を変えない場合はその根拠を`evidence`へ書く。指摘の解消は証拠の行へ自動では反映されないため、行を残すとメインが統合前に証拠を確認するときに差し戻しが生じる。`完成条件証拠: なし`の起動には適用しない。

## 出力

返却前に探索結果の全指摘を走査結果と比較し、レビュー指摘管理表の対応行または根拠付き不採用理由の欠落が0件であることを確認する。
欠落があれば採否と対応先を補完してから返す。
裏付けた差分外の既存不良には、走査記録だけでなく`想定外事象:`への返却先もあることを確かめる。
再レビューと引き継ぎ再レビューでは、走査記録・引き継ぎ記録から残る報告事項を回収し、
委譲元が処置を決めた記録へ対応付ける。未処置の不良は`想定外事象:`へ所在と要点を返す。
差分外の不良はレビューの未解決件数へ加えず、その報告だけで正常なレビューを`needs_escalation`へ変えない。
各ラウンドでレビューしたHEADと、Git管理外の文章成果物ごとの識別子・そのラウンドで読んだ本文の複製パスをセッションのmanaged-temp内の記録へ保存する。
記録の絶対パスを引き継ぎ記録へ`前回確認版`として残し、次の再レビューの比較元にする。
質問への回答を記録したUWIの識別子はWIファイル名、その他のGit管理外文書は元の絶対パスとする。
前回本文の複製は上書きせず、現在のレビューが終了してから次の比較元へ切り替える。

返却前の工程は次の順序で完了する。

1. `完成条件証拠`の未記入行を本担当が原文と検証資料から判定し、`outcome`・`evidence`・`reviewed_head`を記入する。空欄と参照の不整合は本担当の証拠として補い、レビューイーへの指摘に置き換えない
2. 実装差分について裏付けた指摘だけをレビュー指摘管理表へ登録し、表の構造を確認する。証拠の記入と指摘の登録は別の工程として扱う。レビューイーが記入する応答を待つために工程を止めず、表の構造確認は`atk review-table validate <表の絶対パス> --allow-unanswered`で行う
3. 次のコマンドで証拠を確かめて返却本文を生成し、標準出力、標準エラーと終了状態を確認する。継続セッションを返した場合は終端まで観測し、終了コード0で生成された返却本文だけをそのまま返す。非0なら診断箇所を本担当が直して再実行する

```bash
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス|なし> <対象WIファイル名...> --expected-head <レビュー対象HEAD> --review-table <表の絶対パス> --round <round> --return-result
```

計画を受領した場合は全計画を`--plan <絶対パス>`で反復指定する。WI・CI記録にある採否と後続工程を使う場合は「入力」で保存した入力記録を、委譲元から絶対パスで受領した引き継ぎ記録を使う場合はそのパスを、`--input-record <絶対パス>`で渡す。証拠要求なしでも同じ操作で表から件数を生成する。指摘のある正常なレビューもcompletedとして返せる。

同じコマンドは、両配列の全達成行（指定WI集合外の行と計画由来の行を含む）について、明示されたファイル・見出し・行の所在と、異なる要求単位での達成根拠の共用を確かめる。リポジトリ内は最後に実レビューしたcommit、リポジトリ外の絶対パスは現在の実ファイルを使う。失効行の`source`が記入済みユーザーコメントか回答済みUWIを指すこと、背景行の`source`が分類の記録を指し、その参照を解決した範囲か旧引用が要求単位を覆うことも確かめる。
拒否された行は、その行の条件を満たす具体的な所在・観測内容・結果を記入するか、観測が不足する条件を証拠不足へ再判定してから再実行する。根拠の書き方は「指摘の記録」に従い、行ごとに観測した箇所と内容を記す。
コマンドの成功だけで内容の適合を判断しない。各行の根拠が条件を直接満たすか、背景行が要求を含まないか、意味上の否定範囲と不採用根拠が十分かは「指摘の記録」で確かめる。

現在roundに未応答が1件以上ある場合は、証拠の形式・原文・HEADを確認した後、指摘ありのcompletedを生成してレビューイーへ渡す。応答の記入はレビューイーが後で行うため、レビュー担当はその応答を待たず返す。未応答0件の場合に限り、達成を要する未達・証拠不足が残る組合せを拒否する。0件は収束の候補、1件以上は修正へ渡す正常な出口であり、どちらも本担当のcompletedである。
形式だけを確かめる従来の呼び出しの成功を収束の代わりに使わず、生成操作の対象を確認する。
許容する非達成の意味と範囲は「指摘の記録」の基準で判定し、その判断を持つ入力記録の箇所をsourceとevidenceへ書く。rejectは計画の実施内容の不採用行と根拠を使う。延期対象と後続の判定は、既存の引き継ぎ記録の同じ段落へ`AWI: <awi欄の値|計画由来>`、`判定対象: <conditionかrequirementの原文>`を置き、延期adoptでは`終端区分: 延期adopt`、`後続工程:`、`検収時機:`へ実際の結論を書く。公開工程が判定する条件は`判定工程: 公開工程`、並行中の画面レビューの条件は`判定工程: ユーザビリティレビュー`と`進行状態: 並行中`を同じ箇所へ書く。別の証拠台帳へ結論を複製せず、元の判断と対応する記録だけを渡す。記録の実在と対象の対応の成功は、判断そのものの十分性を代替しない。
判断・認可・入力・外部状態が不足し、本担当では補えない場合だけ、その不足と再開位置を続行不能の理由へ記す。

生成する返却は次の3行とし、証拠要求ありでは4行目へ`完成条件証拠のパス: <完成条件証拠の絶対パス>`が加わる。

```text
状態: completed | needs_escalation
レビューしたHEAD: <レビューした対象HEADの7文字以上の一意な短縮OID>
未解決の指摘数: <未解決指摘数>
```

複数のレビュー基準を受領した場合の`未解決の指摘数`は全ての基準について登録した未解決指摘の合算値とする。
続行不能時も同じ形式を使い、末尾に`続行できない理由: <続行できない理由>`を加える。完了報告はツール戻り値で1回返す。委譲元への`SendMessage`での送信は行わない。想定外事象の追加行は`agent-toolkit/share/rules-subagent.md`に従う。
