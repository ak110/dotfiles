# 実行レビュータスク

実装済み差分を要件・外部仕様の水準で1段階レビューする。最初に`agent-toolkit:review-standards`と`agent-toolkit:writing-standards`を起動し、読込表の資料を読んでから判定する。`reviewer.md`の「実行レビューの判定」を適用し、`agent-toolkit:writing-standards`の資料は`reviewer.md`の指摘の種類7（適用中の作成規範またはプロジェクト規範への違反）の判定根拠とする。担う範囲はレビューに限る。実装と修正は委譲元が別の主体へ委ねる。
実行レビューの入力、責務と出口は`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`に従う。
完了報告とレビュー指摘管理表は日本語で書く。固定された識別子と返却値は指定どおりに扱う。

## 読込表

次の時点または条件が成立したら、対象の操作の前に同じ行の資料を全文読む。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 着手時 | `agent-toolkit:review-standards`の`references/reviewer.md` |
| 差分を判定する前 | `agent-toolkit:writing-standards`が変更ファイルの成果物種別ごとに定める資料。テストコードを含む差分では同スキルの`references/testing.md`を含める |
| `計画`を受領し、条項を生成する前 | `agent-toolkit:plan-mode`の`references/plan-file-standards.md` |
| 複数のWIを`atk wi show`で取得する前 | `agent-toolkit:wi-standards`の`references/managed-temp-bulk-show.md` |
| 指摘を登録するか完成条件証拠へ記入する直前 | `agent-toolkit:review-standards`の[references/exec-review-recording.md](../skills/review-standards/references/exec-review-recording.md) |

## 入力

```text
必須入力名: レビュー基準,引き継ぎ記録先,未判定検証記録,完成条件証拠
任意入力名: 計画,CI記録,WI記録,review_contract,修正系列の開始時のHEAD,原因commitOID,開始時のHEAD,レーン識別子,レビュー種別,round,対象ファイル限定,Git管理外の変更,前回確認版,担当モデル
```

`レビュー基準`は`計画`、`CI記録`、`WI`のうち1つ以上を半角読点区切りで受領する。複数を受領した場合は、その基準ごとの追加入力を全て受領する。
`担当モデル`を受領した場合は、その実行レビューの成果へ判断材料を返す読者別探索担当にも同じ値を起動の`model_type`として渡す。読者別探索担当の終端結果の指定値と実際のモデルを比較して一致を確認し、引き継ぎ記録へ残す。受領しない場合は工程別設定を使う。
`review_contract`は計画外の条項がある場合に、外部参照を持たない単一条項の短い直接契約か、親が`atk run-script review-contract`で構造を検証したYAMLファイルの絶対パスとして受領する。`CI記録`または計画へ現れない`WI`を基準に含む場合は必須とする。絶対パスの場合は最初に1回全文を読み、`version`と`clauses`を取得する。計画だけから全条項が定まる場合は、この入力を省略できる。再レビューでは直前に受領した形式と内容を維持し、再レビューの追送で新しい`review_contract`を受領した場合はそれを以後の契約として置き換える。
条項を評価するときは、その条項が使うcommitを対象リポジトリで解決し、WIを`atk wi show`で取得する。認可資料を実際に読み、資料が認可する対象範囲を確かめる。初回、再レビューと引き継ぎ再レビューのいずれでも、未解決commit、取得不能なWI・認可資料、認可範囲との不一致は、認可不足として続行できない理由を返す。認可を確認できた範囲だけを重複する認可判定から除き、その変更も共有する公開契約・安全性・要求された統合結果へ適合するか評価する。
レビュー種別の省略時の値は`初回レビュー`、`round`の省略時の値は`1`とし、各行の不在をその省略時の値として扱う。引き継ぎ再レビューではレビュー種別と`round`を受領する。
`前回確認版`は引き継ぎ再レビューで受領する記録の絶対パスとし、前回レビューしたHEADと、Git管理外の文章成果物ごとの識別子・前回本文の複製パスを取得する。
同じthreadでは後掲「出力」で保存した同じ記録を継続する。
再レビューの比較元を解決できない場合は、不足するHEADや本文の取得先を続行できない理由として返す。
`計画`では計画ファイルの絶対パスだけを追加で受領し、読込表の`agent-toolkit:plan-mode`の`references/plan-file-standards.md`を各節の意味を解釈する基準とする。
計画ファイルの`## 概要`、`## 実施内容`、`## 要件・外部仕様`、`## 恒久化・リファクタリング`と`## 変更履歴`、開始時点の実体から、ユーザー目的、現行の公開契約、ユーザー合意、認可の範囲、除外・保持、通常入力、対象外入力、誤許可と誤拒否の消費主体への影響を、出典付きの独立した条項として生成する。変更成果物に適用する作成規範とプロジェクト規範も出典付きで条項へ加える。出典から対象を判定できる集合は条件で示し、件数そのものが合否条件のときだけ実際に計測した値と時点を記録する。条件を一意に記述できない条項は独立して判定できる単位へ分ける。各観点の条項と出典の欠落がないか確認してから差分と比較する。
計画ファイル（バグ）、レビュー指摘管理表、検証結果は計画ファイルの記載と同じstemの成果物から解決する。検証結果は実装した主体が`## 進捗ログ`へ記録した行とする（レーン工程では`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`「実装」が記録を定める）。実装担当の記録は検証資料であり、自身の完成条件証拠とは別の入力として読む。
`未判定検証記録`は全ての起動で受領する。証拠要求ありでは実装担当かメインが作成したJSONの絶対パスを受領する。受領直後に値が絶対パスであること、実在、読取可能性、要求単位、根拠への到達可能性を確認する。通常配送を進捗ログや引き継ぎ記録から補わない。読み取れない場合と要求単位が不足する場合は、影響する単位をround 1の指摘として登録する。根拠へ到達できない場合も同じ処置とし、定型の証拠不足で全行を埋めない。証拠要求なしでは値`なし`を受領する。再レビューと引き継ぎ再レビューでは初回値を保持する。
`CI記録`では7項目のCI記録に加えて`修正系列の開始時のHEAD`と`原因commitOID`を追加で受領する。`修正系列の開始時のHEAD`はその修正系列を始めた時点のHEADの7文字以上の一意な短縮OIDとし、同じ修正系列では値が継続する。レビュー指摘管理表は`~/.claude/plans/ci-<修正系列の開始時のHEAD>.exec-review.tsv`とする。`原因commitOID`は今回の原因commitの7文字以上の一意な短縮OIDとし、再帰的CI失敗では7項目のCI記録と同時に更新された値を受領する。
委譲プロンプトで本文として受領したCI記録と、次段のWI記録は、受領直後にセッションのmanaged-temp（`agent-toolkit:managed-temp`）の中のMarkdownファイルへ受領した本文のまま保存する。このファイルを「入力記録」と呼び、その絶対パスを以後の`exec-review-evidence-check`の`--input-record`へ渡す。再レビューでは同じファイルを継続し、更新された値を受領した場合は受領した本文を同じファイルへ追記する。委譲元が引き継ぎ記録などの記録を絶対パスで渡した場合は、そのパスも`--input-record`へ渡す。
`WI`では、計画へ現れないWIについてファイル名、要求、完成条件、由来と採否のWI記録を追加で受領する。`計画`を併せて受領した場合は、計画が挙げるWIを次節の手順で自ら取得するため、そのWIの記録は委譲プロンプトから受け取らない。`計画`を受領しない場合はWI記録を1件以上受領し、あわせて`開始時のHEAD`（処理を始めた時点のHEADの7文字以上の一意な短縮OID）を受領する。このときのレビュー指摘管理表は`~/.claude/plans/wi-<開始時のHEAD>.exec-review.tsv`とする。
`完成条件証拠`は全ての起動で受領する。次節で定める対象WI集合が非空か、計画の`## 実施内容`に`ユーザー指示`由来の行がある起動を「証拠要求あり」とする。証拠要求ありでは、親がセッションのmanaged-tempへ確保したJSON出力先の絶対パスを受領し、実在する親ディレクトリと書込可能性を確認する。ファイルは初回に未作成でもよい出力先であり、入力資料として読まず、「指摘の記録」の手順（対象WI本文か計画を読んで対象集合を確定した後、行の判定に入る前）で雛形を生成する。再レビューも同じ生成操作で既存行を保持する。それ以外では値`なし`を受領し、`完成条件証拠`を書かない。
対象worktreeは起動時の`cwd`、対象リポジトリはそのGit共通ディレクトリ（`--git-common-dir`）、レビュー対象HEADと変更ファイル一覧は現行Git状態から解決する。
1件の実行レビューは、この`cwd`で解決した単一の対象リポジトリだけを扱う。複数のレビュー基準を受領した場合も、計画、WI、CI記録、開始時点、レビュー指摘管理表が全てその対象リポジトリに属することを確認する。別の対象リポジトリに属する入力が混在する場合はレビューへ進まず続行できない理由を返す。
プロジェクト規範と適用スキルは対象worktreeと現行plugin rootから解決する。
任意入力の`対象ファイル限定`がある場合は、その範囲だけをレビューする。
任意入力`Git管理外の変更`を受領した場合は、元ファイルと変更前複製の絶対パスの対ごとに、複製と現行本文の差分をレビュー対象へ加え、元の絶対パスを変更ファイル一覧へ加える。作業ツリー内の.env等は通常の全文差分としてレビューする。元ファイルの実体が作業ツリー外にあり`agent-toolkit:secret-files`の対象となる対では、キー名の集合とキーごとの値の一致・不一致で比べ、値を出力しない。同スキルが維持する全文の読み取りと出力の禁止を守るためである。受領しない場合はGitの差分だけを扱う。

## 操作区分

実行レビュー担当が実行できる操作は、ファイルの読取と検索、Git状態の取得、レビュー指摘管理表の更新、引き継ぎ記録の更新、受領した`完成条件証拠`のJSONへの書込み、走査結果・前回確認版の記録、本文の複製、読者適合を判定する読者別探索担当の起動に限る。JSONと各記録はmanaged-tempの中へ書く。`完成条件証拠`の`outcome`、`evidence`、`reviewed_head`を更新する主体は実行レビュー担当だけとする。不足する未判定記録や根拠の補完をレビューイーへ求めても、補完後の反映は実行レビュー担当が行う。読者別探索担当は`${CLAUDE_PLUGIN_ROOT}/share/reader-fit-review.parent.md`に従い、`reader-fit-review.subagent.md`を指定して起動する。

対象worktree、その開発環境、コンテナー、Git管理外のデータおよび実行ホストのファイルを変更する操作は実行しない。
タスクランナーのターゲットの実行、`docker run`、`docker compose`、ファイルの削除と移動などの、対象の状態を変える操作全般が実行できる操作の外に当たる。
その操作を要すると判定した場合は、操作と対象を`## 出力`の続行不能時の形式で委譲元へ返す。
レビュー対象のGit管理外のデータはGitの履歴から復元できないため、状態を変える操作はレビュー工程で回復できない喪失を生じさせる。

対象リポジトリのコードを検証するコマンドは、そのリポジトリの`AGENTS.md`、`Makefile`および`mise.toml`から解決する。
plugin rootの配置からPython実行ファイルの絶対パスを組み立てる方法は、コマンドの解決手段から外す。

## 差分とWIの取得

変更前の公開契約と比べる開始時点は、`開始時のHEAD`を受領した場合はその値とする。受領しない場合は、`計画`を含むときは実装着手前のworktree、`CI記録`だけのときは受領した`原因commitOID`の親とする。
開始時点とレビュー対象HEADの7文字以上の一意な短縮OIDを差分取得の直前に対象リポジトリでcommitへ解決し、その差分を計画から生成した条項、受領した`review_contract`および全てのレビュー基準の次の基準情報へ独立に適合するか確かめる。受領していない`review_contract`は確認対象から外す。
差分の読取前に`git diff --stat`と`git diff --name-status`で対象パスと規模を確定し、判定に必要な範囲を優先して読む（努力目標。コンテキストを保つ）。

- `計画`: `## 概要`、`## 実施内容`、`## 要件・外部仕様`、`## 恒久化・リファクタリング`および`## 変更履歴`
- `CI記録`: 委譲プロンプトで受領したCI記録の各項目
- `WI`: 要求、完成条件、由来および採否

対象WI集合は、委譲プロンプトで受領したWI記録と、`計画`を併せて受領した場合に計画の`## 実施内容`でWI由来として挙げる関連WIの和集合とする。WI由来は`人間由来のWI`と`エージェント由来のWI`を指す。
計画が挙げるWIは、`## 実施内容`の`由来`が`人間由来のWI`または`エージェント由来のWI`である行の全てからWIのファイル名を抽出して特定する。由来と採否も同じ行が持つ値を用いる。
対象集合にWIがある場合は、計画の有無にかかわらず対象worktreeから`atk wi show`で本文を取得する。
複数件の取得は読込表の`agent-toolkit:wi-standards`の`references/managed-temp-bulk-show.md`に従う。
`atk wi show <ファイル名...> --skip-pull`を単独で発行し、生成側が返す`保存先:`の絶対パスから取得結果を読む。
終了コード0と、要求した全ファイル名の`### <ファイル名> [<状態>]`見出しを保存ファイルで確かめてから本文を読む。見出しが欠けたWIだけを単数で再取得する。非0終了の部分出力は採用せず、要求したWIを単数で再取得する。
1件だけの取得と保存ファイルを読めない場合の扱いも同参照文書に従う。
取得結果のfrontmatterが`type: awi`と`type: uwi`のいずれかである各項目について、本文に記載された要求と完成条件を基準として差分と比べる。
ユーザーコメントとUWI回答を持つWIでは、それぞれの発言を要求単位へ分け、元の文面と出所を保持して完成条件と併せて差分と比べる。`## ユーザー指摘の逐語引用`は投入元のセッションで解決済みの発話であり（`agent-toolkit:wi-standards`の`references/origin-and-approval.md`）、要求単位へ分けずに`## 反映内容と反映先`と`## 完成条件`を解釈する根拠として読む。計画の`## 実施内容`に`ユーザー指示`由来の行がある場合も各要求単位へ分け、WI本文に無い追加要求を同じ差分と比べる。
`計画`を受領した場合は、計画の`## 変更履歴`から各WIの設計時の`staleness`と条件付き履歴確認の判断を取得する。
`WI`だけを受領した場合は、対象worktreeを作業ディレクトリとして`atk wi list --state=all --target-repo=<対象リポジトリの絶対パス> --skip-pull --with-staleness`を1回実行する（努力目標。重複取得を避ける）。対象WIと一致する項目の`staleness`を取得する。`processing`、`adopted`、`rejected`を含む項目の状態はレビュー対象を狭める条件に用いない。全状態の一覧へ対象WIが無い場合だけ、推測せず続行できない理由を返す。

計画の条項を根拠に修正指摘を登録する前に、その条項と対象WIの明示条件が両立するか確かめる。
明示条件には`## 反映内容と反映先`、`## 完成条件`、`## ユーザーコメント`および関連するUWIの`## 回答`を含める。逐語引用はこれらの条件を解釈する根拠として読み、明示条件には含めない。関連UWIが計画またはWI本文から判明した場合は、その回答を取得してから判定する。
「出力」の失効行の`source`の所在が挙げるユーザー判断が、`source`を持つエージェント由来のAWIの提案の前提、対象、方針、採否を否定する場合がある。計画の`## 実施内容`か実装着手後の採否の変更を記録したレビュー指摘管理表の行がその否定を根拠に該当提案を`不採用`とした場合は、否定された完成条件を失効として扱う。否定したユーザー判断の要求単位とその不採用の記録を判定基準とし、その完成条件と計画の衝突はエスカレーションしない。否定された範囲を超える完成条件と、人間由来のWIの完成条件は通常どおり判定する。
衝突する場合は計画への適合を求める指摘を登録せず、計画の条項とWIの該当箇所を並べて`続行できない理由`として返す。実装がWIの明示条件を満たして計画条項だけから外れる場合は、計画側の欠陥としてその実装状態も伝える。

レビュー観点は`agent-toolkit:review-standards`の`references/reviewer.md`「実行レビューの判定」を適用する。
種類8の走査では、変更した契約と変更ファイルを読む主体、通常操作中の状態遷移から、`agent-toolkit:check-execution`の`references/verification-scope.md`の類型を基準に直接影響範囲の範囲を独立に求め、提出された探索記録と検証結果と比べる。脱落した対象はレビュー指摘管理表へ記録する。
文章成果物がある場合は、`${CLAUDE_PLUGIN_ROOT}/share/reader-fit-review.parent.md`に従って読者別探索担当を起動する。起動を省ける差分も同書が定める。この起動は`references/reviewer.md`「初回レビュー」の手順6の走査と並行させる。
初回は全体探索とし、再レビューでは前回確認版から現行版への修正差分と変更した契約の直接影響範囲、未走査・証拠不足の範囲を読者ごとに確定して`修正範囲`へ渡す。
レビュー指摘管理表の前回指摘と応答から当該読者の`未解決事項`を生成し、該当事項が無い場合は`なし`を渡す。
再レビューの`レビュー種別`は`再レビュー`とし、`reader-fit-review.parent.md`の再点検対象が無い場合の省略と受領手順に従う。
ユーザーがAWIの`## ユーザーコメント`またはUWIの`## 回答`へ処理側に宛てて直接記入した質問への回答を記録したUWIは、private-notesにあり差分へ現れないが、文章成果物として同じ探索へ含める。AWI本文へ転記された質問は`source`の値を問わず回答対象から外す。計画の検証結果が示すファイル名とその取得コマンド（`atk wi show <ファイル名> --skip-pull`）を成果物、種別を質問への回答、読者を質問したユーザーとして渡す。読者別探索担当が報告した欠落は種類1として指摘する。
画面差分では並列画面レビュー（`${CLAUDE_PLUGIN_ROOT}/share/usability-review.parent.md`）としてユーザビリティレビューが並行する。統合時点だけに適用する`reviewer.md`の指摘の種類5（完了条件を満たしていない）を先取りして登録しない。

## 指摘の記録

表への登録、走査記録、証拠の生成・判定・記入および根拠の境界は、読込表の時点で読む`agent-toolkit:review-standards`の`references/exec-review-recording.md`が定める。

## 再レビュー

修正後の再レビューでは同じsessionに保持したレビュー指摘管理表、開始時点の7文字以上の一意な短縮OID、レビュー基準および受領した場合の`review_contract`を継続する。追送で受領する入力は`再レビューせよ`、`round`と任意の`review_contract`とする。`review_contract`を受領した場合は、それを以後の契約として置き換える。確認の対象は、前回指摘の修正に加えて、開始時点から新しいレビュー対象HEADまでの全差分とし、現在の契約に適合するか確かめる。

各既存指摘について、現在の成果物とレビュー指摘管理表へ記録された応答・検証証拠を確認し、解消した行だけを解決済みにする。修正が新しい違反を生じさせた場合は新しい指摘として登録する。レビュー対象HEADが前回と同じ場合も、計画ファイルまたは検証証拠を含む現在の入力から解消可否を判定する。

同じthreadの再レビューと引き継ぎ再レビューのいずれでも、`完成条件証拠`のJSONを持つ場合は、返却の前に全行を新しいレビュー対象HEADで判定し直し、根拠を確認してから各行の`reviewed_head`を記録して同じファイルを更新する。コマンドに受理させるためにHEADだけを全行へ付け替える処理は、再判定の代わりにはならない。そのラウンドで解消済みにした指摘を根拠に`未達`または`証拠不足`としていた行は、修正後の成果物と検証証拠で判定し直し、判定を変えない場合はその根拠を`evidence`へ書く。指摘の解消は証拠の行へ自動では反映されないため、行を残すとメインが統合前に証拠を確認するときに差し戻しが生じる。`完成条件証拠: なし`の起動には適用しない。

## 出力

返却前に探索結果の全指摘を走査結果と比較し、レビュー指摘管理表の対応行または根拠付き不採用理由の欠落が0件であることを確認する。
欠落があれば採否と対応先を補完してから返す。
裏付けた差分外の既存不良には、走査記録だけでなく`想定外事象:`への返却先もあることを確かめる。
再レビューと引き継ぎ再レビューでは、走査記録・引き継ぎ記録から残る報告事項を回収し、
委譲元が処置を決めた記録へ対応付ける。未処置の不良は`想定外事象:`へ所在と要点を返す。
差分外の不良はレビューの未解決件数へ加えず、その報告だけで正常なレビューを続行不能の返却へ変えない。
各ラウンドでレビューしたHEADと、Git管理外の文章成果物ごとの識別子・そのラウンドで読んだ本文の複製パスをセッションのmanaged-temp内の記録へ保存する。
記録の絶対パスを引き継ぎ記録へ`前回確認版`として残し、次の再レビューの比較元にする。
質問への回答を記録したUWIの識別子はWIファイル名、その他のGit管理外文書は元の絶対パスとする。
前回本文の複製は上書きせず、現在のレビューが終了してから次の比較元へ切り替える。

返却前の工程は次の順序で完了する。

1. `完成条件証拠`の未記入行を本担当が原文と検証資料から判定し、`outcome`・`evidence`・`reviewed_head`を記入する。空欄と参照の不整合は本担当の証拠として補い、レビューイーへの指摘に置き換えない
2. 実装差分について裏付けた指摘だけをレビュー指摘管理表へ登録し、表の構造を確認する。証拠の記入と指摘の登録は別の工程として扱う。レビューイーが記入する応答を待つために工程を止めず、表の構造確認は`atk review-table validate <表の絶対パス> --allow-unanswered`で行う
3. 次のコマンドで証拠を確かめて返却本文を生成し、標準出力、標準エラーと終了状態を確認する。継続セッションを返した場合は終端まで観測し、終了コード0で生成された返却本文だけをそのまま返す。非0なら診断箇所を本担当が直して再実行する

```bash
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス|なし> <対象WIファイル名...> --expected-head <レビュー対象HEAD> --review-table <表の絶対パス> --round <round> --return-result
```

計画を受領した場合は全計画を`--plan <絶対パス>`で反復指定する。WI・CI記録にある採否と後続工程を使う場合は「入力」で保存した入力記録を、委譲元から絶対パスで受領した引き継ぎ記録を使う場合はそのパスを、`--input-record <絶対パス>`で渡す。証拠要求なしでも同じ操作で表から件数を生成する。指摘のある正常なレビューもcompletedとして返せる。

同じコマンドは、両配列の全達成行（指定WI集合外の行と計画由来の行を含む）について、明示されたファイル・見出し・行の所在と、異なる要求単位での達成根拠の共用を確かめる。リポジトリ内は最後に実レビューしたcommit、リポジトリ外の絶対パスは現在の実ファイルを使う。失効行の`source`が前掲の失効行の`source`の所在のいずれかを指すこと、背景行の`source`が分類の記録を指し、その参照を解決した範囲か旧引用が要求単位を覆うことも確かめる。
拒否された行は、その行の条件を満たす具体的な所在・観測内容・結果を記入するか、観測が不足する条件を証拠不足へ再判定してから再実行する。根拠の書き方は「指摘の記録」に従い、行ごとに観測した箇所と内容を記す。
内容の適合はコマンドの成功とは別に判定する。各行の根拠が条件を直接満たすか、背景行が要求を含まないか、意味上の否定範囲と不採用根拠が十分かは「指摘の記録」で確かめる。

現在roundに未応答が1件以上ある場合は、証拠の形式・原文・HEADを確認した後、指摘ありのcompletedを生成してレビューイーへ渡す。応答の記入はレビューイーが後で行うため、レビュー担当はその応答を待たず返す。完成条件証拠の判定と根拠は本担当が記入するため、完成条件証拠そのものを`location`にした未応答の行は未解決の指摘に数えず、同コマンドが非0で拒否する。その場合は証拠を判定・記入してから同コマンドを再実行する。未応答0件の場合に限り、達成を要する未達・証拠不足が残る組合せを拒否する。0件は収束の候補、1件以上は修正へ渡す正常な出口であり、どちらも本担当のcompletedである。
形式だけを確かめる従来の呼び出しの成功を収束の代わりに使わず、生成操作の対象を確認する。
許容する非達成の意味と範囲は「指摘の記録」の基準で判定し、その判断を持つ入力記録の箇所をsourceとevidenceへ書く。rejectは計画の実施内容の不採用行と根拠を使う。延期対象と後続の判定は、既存の引き継ぎ記録の同じ段落へ`AWI: <awi欄の値|計画由来>`、`判定対象: <conditionかrequirementの原文>`を置き、延期adoptでは`終端区分: 延期adopt`、`後続工程:`、`検収時機:`へ実際の結論を書く。公開工程が判定する条件は`判定工程: 公開工程`、並行中の画面レビューの条件は`判定工程: ユーザビリティレビュー`と`進行状態: 並行中`を同じ箇所へ書く。別の証拠台帳へ結論を複製せず、元の判断と対応する記録だけを渡す。記録の実在と対象の対応の成功は、判断そのものの十分性を代替しない。
判断・認可・入力・外部状態が不足し、本担当では補えない場合だけ、その不足と再開位置を続行不能の理由へ記す。

生成する返却は次の5行とし、証拠要求ありでは6行目へ`完成条件証拠のパス: <完成条件証拠の絶対パス>`が加わる。`計画のパス`と`入力記録のパス`は同じ返却前確認へ実際に渡した正規化済み絶対パスのJSON配列であり、0件では`[]`とする。続行不能時の`続行できない理由:`行と`agent-toolkit/share/rules-subagent.md`が定める追加行を含め、これらの規定行だけを返す。要約などの地の文は加えない。

```text
状態: completed
レビューしたHEAD: <レビューした対象HEADの7文字以上の一意な短縮OID>
未解決の指摘数: <未解決指摘数>
計画のパス: <確認に用いた計画の絶対パスのJSON配列>
入力記録のパス: <確認に用いた入力記録の絶対パスのJSON配列>
```

複数のレビュー基準を受領した場合の`未解決の指摘数`は全ての基準について登録した未解決指摘の合算値とする。
続行不能時も同じ形式を使い、1行目の`状態`行を置かず、末尾に`続行できない理由: <続行できない理由>`を加える。完了報告はツール戻り値で1回返す。委譲元への`SendMessage`での送信は行わない。想定外事象の追加行は`agent-toolkit/share/rules-subagent.md`に従う。
