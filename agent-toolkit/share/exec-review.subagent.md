# 実行レビュータスク

実装済み差分を要件・外部仕様の水準で1段階レビューする。最初に`agent-toolkit:review-standards`と`agent-toolkit:writing-standards`を起動し、読込表の資料を読んでから判定する。`reviewer.md`の「実行レビューの判定」を適用し、`agent-toolkit:writing-standards`の資料は`reviewer.md`の指摘の種類7（適用中の作成規範またはプロジェクト規範への違反）の判定根拠とする。担う範囲はレビューに限り、実装と修正は委譲元が別のエージェントへ委ねる。
実行レビューの入力、責務と出口は`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`に従う。
完了報告とレビュー指摘管理表は日本語で書く。固定された識別子と返却値は指定どおりに扱う。

## 読込表

次の時点または条件が成立したら、対象の操作の前に同じ行の資料を全文読む。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 着手時 | `agent-toolkit:review-standards`の`references/reviewer.md` |
| 文章成果物の初回レビュー・再レビュー・引き継ぎ再レビューで、読者別探索の起動または省略を判断する前 | `${CLAUDE_PLUGIN_ROOT}/share/reader-fit-review.parent.md` |
| 差分を判定する前 | `agent-toolkit:writing-standards`が変更ファイルの成果物種別ごとに定める資料。テストコードを含む差分では同スキルの`references/testing.md`を含める |
| `計画`を受領し、条項を生成する前 | `agent-toolkit:plan-mode`の`references/plan-file-standards.md` |
| `計画`を受領し、計画が過去の契約へ戻す変更、過去の契約を撤去する変更、または保持・不変性・完全復元の契約を含む場合 | `agent-toolkit:plan-mode`の`references/plan-restoration-contracts.md` |
| 複数のWIを`atk wi show`で取得する前 | `agent-toolkit:wi-standards`の`references/wi-show-bulk.md` |
| 指摘を登録するか完成条件証拠へ記入する直前 | `agent-toolkit:review-standards`の[references/exec-review-recording.md](../skills/review-standards/references/exec-review-recording.md) |

## 入力

```text
必須入力名: レビュー基準,引き継ぎ記録先,未判定検証記録,完成条件証拠
任意入力名: 計画,CI記録,WI記録,review_contract,修正系列の開始時のHEAD,原因commitOID,開始時のHEAD,レーン識別子,レビュー種別,round,対象ファイル限定,Git管理外の変更,前回確認版,担当モデル,rewrite_map,受理済みの完成条件証拠
```

- `レビュー基準`: `計画`、`CI記録`、`WI`のうち1つ以上を半角読点区切りで受領し、基準ごとの追加入力を全て受領する
- `計画`: 計画ファイルの絶対パス。各節の意味は読込表の`plan-file-standards.md`で解釈する。レビュー指摘管理表と検証結果は同じstemの成果物から解決する。検証結果は実装したエージェントが`## 進捗ログ`へ記録した行（レーン工程では`exec.subagent.md`「実装」）であり、自身の完成条件証拠とは別の検証資料として読む
- `CI記録`: 7項目のCI記録と`修正系列の開始時のHEAD`（同じ修正系列で継続する短縮OID）、`原因commitOID`（今回の原因commitの短縮OID。再帰的CI失敗ではCI記録と同時に更新される）を受領する。表は`~/.claude/plans/ci-<修正系列の開始時のHEAD>.exec-review.tsv`
- `WI`: 計画へ現れないWIのファイル名、要求、完成条件、由来と採否の`WI記録`を受領する（計画が挙げるWIは自ら取得する）。`計画`が無い場合はWI記録1件以上と`開始時のHEAD`を受領し、表は`~/.claude/plans/wi-<開始時のHEAD>.exec-review.tsv`とする
- `未判定検証記録`: 証拠要求ありでは実装担当かメインが作成したJSONの絶対パス、なしでは`なし`。受領直後に絶対パスであること、実在、読取可能性、要求単位、根拠への到達可能性を確かめる。欠けた値を進捗ログや引き継ぎ記録から補うことはしない。読めない、要求単位が不足する、根拠へ到達できない場合は、影響する単位をround 1の指摘として登録する（定型の証拠不足で全行を埋めることはしない）。再レビューでは初回値を保持する
- `完成条件証拠`: 対象WI集合（「差分とWIの取得」）が非空か、計画の`## 実施内容`に`ユーザー指示`由来の行がある起動を「証拠要求あり」とし、親がmanaged-tempへ確保したJSON出力先の絶対パスを受領する。親ディレクトリの実在と書込可能性を確かめる。初回は未作成でよく、入力資料として読まず、`exec-review-recording.md`「完成条件証拠の生成」の手順（対象集合の確定後、行の判定に入る前）で雛形を生成する。再レビューも同じ生成操作で既存行を保持する。それ以外は`なし`を受領し、書かない
- `review_contract`: 計画外の条項がある場合に、単一条項の直接契約か、親が`atk run-script review-contract`で構造を検証したYAMLの絶対パス。`CI記録`か計画へ現れない`WI`を基準に含む場合は必須。パスなら最初に全文を読んで`version`と`clauses`を取得する。再レビューでは維持し、追送で新しい契約を受けたら置き換える
- `担当モデル`: 受領した場合は読者別探索担当の起動の`model_type`へ渡し、終端結果の実際のモデルとの一致を引き継ぎ記録へ残す。受領しない場合は工程別設定を使う
- `レビュー種別`と`round`: 省略時の値は`初回レビュー`と`1`。引き継ぎ再レビューでは両方を受領する
- `rewrite_map`: 前回のレビュー後に履歴書換えかcommit分割でOIDが変わった再レビューで受領する旧OIDから新OIDへの対応表の絶対パス。形式は`agent-toolkit:commit`の`references/history-rewrite.md`「WI実装commitの対応の継承」、扱いは「再レビュー」に従う
- `前回確認版`: 引き継ぎ再レビューで受領する記録の絶対パス。前回の開始時点とレビューしたHEADの組（差分の比較に使う）と、Git管理外の文章成果物ごとの識別子・前回本文の複製パスを持つ。同じthreadでは「出力」で保存した記録を継続する。比較元を解決できなければ、不足するHEADや本文の取得先を続行できない理由で返す
- `受理済みの完成条件証拠`: 後続レビューが参照できる判定済みJSONの絶対パス。省略時と行が無い場合は`なし`。未判定検証記録の継承入力へ混ぜず、`exec-review-recording.md`「受理済み判定への参照」の条件を満たす行だけを参照する
- `対象ファイル限定`: ある場合はその範囲だけをレビューする
- `Git管理外の変更`: 元ファイルと変更前複製の絶対パスの対ごとに、複製と現行本文の差分をレビュー対象へ、元の絶対パスを変更ファイル一覧へ加える。作業ツリー内の.env等は通常の全文差分とする。元ファイルが作業ツリー外にあり`agent-toolkit:secret-files`の対象となる対では、キー名の集合とキーごとの値の一致・不一致だけを比べ、値は出力対象から除く

委譲プロンプトで本文として受領したCI記録とWI記録は、受領直後にmanaged-temp（`agent-toolkit:managed-temp`）内のMarkdownファイルへ受領したまま保存する（「入力記録」）。その絶対パスを以後の`exec-review-evidence-check`の`--input-record`へ渡し、再レビューで更新値を受けたら同じファイルへ追記する。委譲元が絶対パスで渡した記録もそのまま`--input-record`へ渡す。
計画なしでWI全体を不採用とする場合は、入力記録へ`## 実施内容`の表を置く。表は`実施内容`・`採否`・`根拠`の列を持ち、対象WIごとにファイル名を含む行を1行以上置く。その全行の`採否`を`不採用`とし、各行に空でない根拠を記録する。

対象worktreeは`cwd`、対象リポジトリはそのGit共通ディレクトリ、レビュー対象HEADと変更ファイル一覧は現行Git状態から解決する。計画、WI、CI記録、開始時点、レビュー指摘管理表のいずれかが別の対象リポジトリに属する場合は続行できない理由を返す。プロジェクト規範と適用スキルは対象worktreeと現行plugin rootから解決する。

レビュー指摘管理表は最初の読取前に存在を確かめる。初回レビューで不在の場合だけ`atk review-table init <表の絶対パス>`を単独実行し、成功を確かめてから読む。既存表は初期化せずに使う。再レビューと引き継ぎ再レビューで不在の場合は空表を作成せず、欠けた表と再開に要る記録を続行できない理由で返す。

## 操作区分

実行できる操作は、ファイルの読取と検索、Git状態の取得、レビュー指摘管理表の更新（初回で不在の表の初期化を含む）、引き継ぎ記録の更新、受領した`完成条件証拠`への書込み、走査結果・前回確認版の記録、本文の複製、読者別探索担当の起動（`reader-fit-review.parent.md`に従う）に限る。JSONと記録はmanaged-temp内へ書く。`完成条件証拠`の`outcome`、`evidence`、`reviewed_head`を更新するのは実行レビュー担当だけであり、レビューイーに根拠の補完を求めた場合も反映は本担当が行う。

対象worktree、その開発環境、コンテナー、Git管理外のデータ、実行ホストのファイルを変更する操作（タスクランナーのターゲット、`docker run`、`docker compose`、ファイルの削除と移動など）は実行しない。Git管理外のデータはGitから復元できず、レビュー工程で回復できない喪失になる。そうした操作が必要と判定した場合は、操作と対象を続行不能の形式で委譲元へ返す。

検証コマンドは対象リポジトリの`AGENTS.md`、`Makefile`、`mise.toml`から解決する（plugin rootの配置からPython実行ファイルのパスを組み立てる方法は使わない）。

## 差分とWIの取得

変更前の公開契約と比べる開始時点は、`開始時のHEAD`があればその値、無ければ`計画`を含む場合は実装着手前のworktree、`CI記録`だけなら`原因commitOID`の親とする。開始時点とレビュー対象HEADを差分取得の直前にcommitへ解決し、差分が計画から生成した条項、受領した`review_contract`、各基準の次の情報へ独立に適合するか確かめる。差分は`git diff --stat`と`git diff --name-status`で規模を把握してから、判定に要る範囲を優先して読む（努力目標。コンテキストを保つ）。

- `計画`: `## 概要`、`## 実施内容`、`## 要件・外部仕様`、`## 恒久化・リファクタリング`、`## 変更履歴`
- `CI記録`: 受領したCI記録の各項目
- `WI`: 要求、完成条件、由来、採否

対象WI集合は、受領したWI記録と、計画の`## 実施内容`で`由来`が`人間由来のWI`か`エージェント由来のWI`の行が挙げるWIの和集合とする（計画の行の由来と採否を用いる）。対象WIは計画の有無にかかわらず対象worktreeで`atk wi show`により取得し、frontmatterが`type: awi`か`type: uwi`の項目の要求と完成条件を差分と比べる。
ユーザーコメントとUWI回答は要求単位へ分け、元の文面と出所を保持して比べる。`## ユーザー指摘の逐語引用`は投入元で解決済みの発話であり（`agent-toolkit:wi-standards`の`references/origin-and-approval.md`）、要求単位にせず`## 反映内容と反映先`と`## 完成条件`を解釈する根拠として読む。計画の`ユーザー指示`由来の行も要求単位に分け、WI本文に無い追加要求として比べる。
WI鮮度は`計画`があれば`## 変更履歴`の設計時の`staleness`と条件付き履歴確認の判断を使う。`WI`だけの場合は対象worktreeで`atk wi list --state=all --target-repo=<対象リポジトリの絶対パス> --skip-pull --with-staleness`を1回実行して対象WIの`staleness`を得る。レビュー対象には全状態（`processing`、`adopted`、`rejected`など）の対象WIを含める。全状態の一覧に対象WIが無い場合だけ続行できない理由を返す。

計画の条項を根拠に指摘を登録する前に、その条項が対象WIの明示条件（`## 反映内容と反映先`、`## 完成条件`、`## ユーザーコメント`、関連UWIの`## 回答`）と両立するか確かめる。関連UWIが判明したら回答を取得してから判定する。衝突する場合は指摘を登録せず、計画の条項とWIの該当箇所を並べて続行できない理由で返す。実装がWIを満たして計画条項だけから外れる場合は、計画側の欠陥としてその実装状態も伝える。
`exec-review-recording.md`「失効の根拠」が挙げるユーザー判断が、`source`を持つエージェント由来AWIの提案（前提・対象・方針・採否）を否定する場合がある。計画の`## 実施内容`か採否の変更を記録したレビュー指摘管理表の行がそれを根拠に提案を`不採用`とした場合は、否定された完成条件を失効として扱い、計画との衝突とは扱わない。否定された範囲を超える完成条件と人間由来のWIの完成条件は通常どおり判定する。メインの技術判断を根拠にできる範囲も同節が定め、計画確定前の判断は計画の実施内容の根拠欄から、着手後の判断は表の行から読む。全体不採用の条件は部分失効にせず、初回から未達とし、evidenceへreject終端と、計画または入力記録の`実施内容`の不採用根拠の所在を書く。

## 条項の生成

`計画`を受領した場合は、計画の`## 概要`・`## 実施内容`・`## 要件・外部仕様`・`## 恒久化・リファクタリング`・`## 変更履歴`と開始時点の実体から条項を生成する。条項はユーザー目的、現行の公開契約、ユーザー合意、認可の範囲、除外・保持、通常入力、対象外入力、誤許可と誤拒否の消費主体への影響について、出典付きの独立した単位で書く。変更成果物に適用する作成規範とプロジェクト規範も条項へ加える。集合は条件で示し、件数そのものが合否条件の場合だけ、実際に数えた値と時点を記録する。`reviewer.md`の種類9（設計品質の劣化）は計画の結論に依らず差分と変更後のファイル全体から判定する。

条項が使うcommitは対象リポジトリで解決し、WIは`atk wi show`で取得し、認可資料を実際に読んで認可する範囲を確かめる。未解決commit、取得できないWI・認可資料、認可範囲との不一致は、どのラウンドでも認可不足として続行できない理由で返す。認可を確かめた範囲だけを重複する認可判定から除き、その変更も共有する公開契約・安全性・要求された統合結果への適合は評価する。

## 判定の観点と並行する探索

レビュー観点は`reviewer.md`「実行レビューの判定」を適用する。種類8の走査では、変更した契約と変更ファイルを読む主体と通常操作中の状態遷移から、`agent-toolkit:check-execution`の`references/verification-scope.md`の類型を基準に直接影響範囲を独立に求める。それを提出された探索記録と検証結果と比べ、脱落を表へ記録する。

文章成果物がある場合は`reader-fit-review.parent.md`に従って読者別探索担当を起動し、`reviewer.md`「初回レビュー」の走査と並行させる。起動を省ける差分も同書が定める。

- Git管理下の比較資料は、次の公開操作の1回の実行で準備する。再レビューは`--previous-review-start <前回の開始時点> --previous-review-head <前回のレビューHEAD>`、YAMLの`review_contract`があれば`--review-contract <絶対パス>`も渡す。対象を限定する場合は`--markdown <リポジトリ相対パス>`を反復する

```text
atk run-script reader-fit-prepare -- --repository <対象worktree> --review-start <今回の開始時点> --review-head <レビュー対象HEAD> --output-dir <managed-temp内の出力先>
```

- 出力の`files`にある`path`・`before`・`patch`を、変更前（再レビューは前回HEAD）の本文と今回差分の保存先として使い、現行本文と直接影響範囲を読者ごとの`修正範囲`へ対応付ける。新規文書・新規回答は全文が差分である。再レビューでは未走査・証拠不足の範囲も渡し、`レビュー種別`は`再レビュー`とする。Git管理外は保存済みの前回本文の複製と現行本文を使う
- 表の前回指摘と応答から当該読者の`未解決事項`を作成し、無ければ`なし`を渡す
- 差分外の既存不良は想定外事象として、新しい要件はその旨を委譲元へ返し、未達指摘や未解決件数の集計対象から除く
- ユーザーがAWIの`## ユーザーコメント`かUWIの`## 回答`へ処理側に宛てて直接記入した質問への回答下書きは、Git差分に無くても文章成果物として含める（AWI本文へ転記された質問は対象外）。検証結果が示す下書きの絶対パスを成果物、種別を質問への回答、読者を質問したユーザーとして渡す。本担当は言い切りの事実主張を根拠と現物で確かめ、欠落は種類1として指摘し、修正は下書きへ返す。回答UWIの保存はレビュー収束後にメインが行う

画面差分ではユーザビリティレビューが並行するため、統合時点だけに適用する`reviewer.md`の指摘の種類5（完了条件を満たしていない）の登録は統合時点まで待つ。

## 再レビュー

再レビューでは同じsessionの表、開始時点の短縮OID、レビュー基準、`review_contract`を継続する。追送で受けるのは`再レビューせよ`、`round`と任意の`review_contract`、`rewrite_map`である。確認対象は前回指摘の修正に加え、開始時点から新しいレビュー対象HEADまでの全差分とする。
各既存指摘は現在の成果物と表の応答・検証証拠から判定し、解消した行だけを解決済みにする。修正が生んだ新しい違反は新しい指摘として登録する。HEADが前回と同じでも現在の入力から判定する。

`rewrite_map`を受領したら、行の判定の前に証拠の`evidence`にある現行成果物への`commit:<OID>`参照だけを新OIDへ更新する。コマンドは`atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス> --rewrite-map <rewrite_mapの絶対パス>`とし、両配列へ同じ規則で適用され、判定と`reviewed_head`は保たれる。裸のOID、取得版のHEAD・git_head・比較元、観測ファイル、既存自由文の形式は保持され、曖昧・不正な対応では部分保存されない。分割形式の対応表では旧`commit:`参照が全対応先の`commit:`参照へ更新され、次回も解決できる（根拠共用比較のCOMMIT_REFERENCEは別責務として維持される）。取得版と異なる版で判定し直す行は`exec-review-recording.md`「根拠の書き方」に従って既存の記録を使えるかを決める。
`完成条件証拠`のJSONを持つ場合は、返却の前に全行を新しいHEADで判定し直し、根拠を確かめてから各行の`reviewed_head`を記録する。HEADだけの付け替えと参照の更新は再判定の代わりにはならない。解消した指摘を根拠に`未達`か`証拠不足`としていた行も判定し直し、判定を変えない場合はその根拠を`evidence`へ書く。`対応完了（再レビュー不要）`で収束する場合は、証拠を最後に実際にレビューしたHEADの`reviewed_head`と参照のまま保つ。

## 出力

保存済みのplan-verifyの結果は、`verification_plan_path`が引き継いだ検証条件を指すか確かめ、各行の`state`と`failure`を両出力・子の終了状態とともに判定する。pyfltrの子が終了0でも、対象未到達・未完了を示す結果は合格にしない。訂正表の書式・保持・引き継ぎは`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「検証と終端工程」に従う。

返却の前に次を終える。

- 探索結果の全指摘について、表の対応行か根拠付きの不採用理由があることを確かめ、欠落を補う
- 差分外・範囲外として表から外す候補は、`exec-review-recording.md`「走査記録と差分外の不良」の分類と受渡しを終える。再レビューでは走査記録・引き継ぎ記録から残る報告事項を回収して委譲元の処置の記録へ対応付け、未処置の不良を`想定外事象:`へ返す。差分外の不良だけで正常なレビューを続行不能へ変えない
- 各ラウンドの開始時点とレビューしたHEAD、Git管理外の文章成果物ごとの識別子（回答下書きは元の絶対パス）・読んだ本文の複製パスをmanaged-temp内の記録へ保存し、その絶対パスを引き継ぎ記録へ`前回確認版`として残す。前回本文の複製は上書きせず、現在のレビューの終了後に次の比較元へ切り替える
- 読者別探索の申告を`{"files":{"<相対パス>":{"sessions":["<sessionのUUID>"]}},"external":{"<絶対パス>":{"sessions":["<sessionのUUID>"]}}}`のJSON1行で作成する。同じファイルの読者ごとのUUIDは配列へまとめる。Git管理外の対象が無い場合の`external`は`{}`とする
- Git管理下の対象は、削除を除く変更`.md`・`.md.tmpl`のうち、このレビューの判定対象commitが変更した範囲とし、改名は新パスで記す。`review_contract`の`別計画の認可`が挙げる他計画のcommitだけの変更は外し、どの計画にも属さないcommitは対象に残す。2回目以降で前回と今回のファイル別差分が同一のファイルだけ、値を`{"omission":"再点検対象なし"}`にできる
- Git管理外の対象集合は、回答下書きの絶対パスと、`Git管理外の変更`の元ファイルのうち`.md`・`.md.tmpl`の絶対パスとし、各パスを`--external-artifact`で反復指定する。roundが2以上で前回本文の複製と現行本文のバイト列が一致する場合だけ、`external`の値を`{"omission":"再点検対象なし","previous":"<前回本文の複製の絶対パス>"}`にできる
- 初回は意味による省略をせず、Git管理下と管理外の対象集合がともに空の場合だけ`文章成果物なし`とする。証拠要求なしでも同じ申告と対象集合を返却前確認へ渡す

続けて次の順で返却を生成する。

複数行の根拠更新では、`--evidence-file`・`--result-test`・`--result-diagnostic`を全選択行への共通指定に使う。
行ごとに異なる値は`--row-evidence-file <配列:N> <根拠の絶対パス>`・`--row-result-test <配列:N> <完全テスト名>`・`--row-result-diagnostic <配列:N> <診断識別子>`を反復して対応付ける。
同じ種類の共通指定と行別指定は分けて使い、詳しい行別入力は`--updates-file`でも渡せる。
単一値の入力を異なる値で反復すると拒否されるため、モード・レビュー対象HEADなどが異なる更新は呼び出しを分割する。

1. `完成条件証拠`を`exec-review-recording.md`「JSONの形式と返却前の確認」の`--list`で読み、未記入行（再レビューでは全行）を原文と検証資料から本担当が判定する。記入は同節の`--select-row`と保存物の直接指定、`--row-outcome`・`--reviewed-head`・`--mode`で行う（構造化結果でも説明ファイルだけでも同じ公開操作を使う）。更新配列を直接記入する場合は同節のJSON例と`--updates-file`を使い、一覧の現行`source`で選択し、新しい所在は許された判定に限り`new_source`へ置く。結果ファイルを要しない手動観測では結果指定を省略でき、訂正・再レビューも同じ操作で更新する。`--select-row`ではsourceは処理側が取得し、失効・割当外・背景の判断根拠の所在へ変える場合だけ`--row-source`を明示する。未判定記録からは同じ要求単位の行だけを`--verification-row`で選ぶ。保存済みの実行は`atk run-command --record <record_path>`の反復か`--records-file <plan-verifyの結果まとめ>`で子を再実行せずに読み、取得版・Git状態・子とwrapperの終了状態・両出力を判定する。未記録・破損・読取失敗を成功と扱わず、取得版・条件・原文の対応を確かめ、達成は結果から自動生成しない。保存先は未判定記録と別ファイルとし、未選択行を保ったまま更新後の証拠を再読取する。空欄と参照の不整合は本担当が補い、レビューイーへの指摘に置き換えない
2. 実装差分について裏付けた指摘だけを表へ登録し、`atk review-table validate <表の絶対パス> --allow-unanswered`で構造を確かめる（レビューイーの応答は待たない）
3. 次のコマンドで証拠を確かめて返却本文を生成する。終了コード0で生成された本文だけをそのまま返す。非0では診断の回復操作を「操作区分」と比べ、担当内で実施できる処理を終えて再実行する

```bash
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス|なし> <対象WIファイル名...> --expected-head <レビュー対象HEAD> --review-start <今回の開始時点> --review-table <表の絶対パス> --round <round> --return-result --reader-fit-review '<読者別探索の申告>'
```

全計画を`--plan <絶対パス>`で反復指定し、WI・CI記録の採否と後続工程を使う場合は入力記録を、委譲元から受領した引き継ぎ記録を使う場合はそのパスを`--input-record <絶対パス>`で渡す。証拠要求なしでも同じ操作で表から件数を生成する。
Git管理外の各対象を`--external-artifact <絶対パス>`で反復指定し、YAMLの`review_contract`を受領していれば`--review-contract <その絶対パス>`も渡す。
返却生成は検査へ渡した値を既存の`version: 1`・`reviews`形式でmanaged-tempへ保存し、`受領確認入力のパス`として返す。
この生成済み入力を受領と統合へそのまま渡す。
保存に失敗した場合は非0の診断を解消してから返却する。
2回目以降は`--previous-review-start <前回の開始時点> --previous-review-head <前回のレビューHEAD>`を加え、rebase後も前回の組を保ってファイル別差分の比較に使う。申告の不足や不正では返却が生成されないため、診断が示すファイルの読者別探索を済ませてから再実行する。

同じコマンドは、両配列の全達成行（指定WI集合外の行と計画由来の行を含む）について、明示されたファイル・見出し・行の所在（リポジトリ内は最後に実レビューしたcommit、リポジトリ外は現在の実ファイル）と、異なる要求単位での達成根拠の共用を確かめる。失効行の`source`が同節の所在のいずれかを指すこと、背景行の`source`が分類の記録を指し、その記録が「」で引用した範囲が要求単位を覆うことも確かめる。拒否された行は、条件を満たす具体的な所在・観測内容・結果を記入するか証拠不足へ再判定してから再実行する。コマンドの成功は内容の適合を意味せず、根拠が条件を直接満たすか、背景行が要求を含まないか、否定範囲と不採用根拠が十分かは`exec-review-recording.md`の基準で判定する。

現在roundに未応答が1件以上ある場合は、指摘ありのcompletedを生成して返す（応答はレビューイーが後で記入する）。完成条件証拠そのものを`location`にした未応答の行は同コマンドが拒否するため、証拠を判定・記入して再実行する。未応答0件の場合に限り、達成を要する未達・証拠不足が残る組合せが拒否される。0件は収束の候補、1件以上は修正へ渡す正常な出口であり、どちらもcompletedである。

許容する非達成の意味と範囲は`exec-review-recording.md`の基準で判定し、その判断を持つ入力記録の絶対パスと位置をsourceかevidenceの一方で指す。
延期・終端しない行はsourceを保ち、`--select-row`・`--evidence-file`・`--mode replace`でevidenceへ所在を書けばよい。
rejectは計画または入力記録の`実施内容`の不採用行と根拠を使う。延期対象と本実行で終端しない項目は、既存の引き継ぎ記録の段落へ条件1件ごとに次を書く（複数の条件をまとめた言い換えは拒否される）。

- `AWI: <awi欄の値|計画由来>`、`判定対象: <conditionかrequirementの原文を逐語>`
- `終端区分: 延期adopt`か`終端区分: 終端しない`（`exec.parent.md`「統合の指示と受領」の`AWI終端区分`のうち統合時に`adopt`しない値）と、実際の結論を書いた`後続工程:`、`検収時機:`
- 公開工程が判定する条件は`判定工程: 公開工程`、並行中の画面レビューの条件は`判定工程: ユーザビリティレビュー`と`進行状態: 並行中`

この記録で許容される非達成は、表への登録も別の台帳への複製もしない。記録の実在と対応の成功とは別に、判断の十分性を確かめる。
返却の分類は、残る処理の所有者と不足する判断・入力・権限から決める。
証拠の記入修復、読者別探索の起動・回復・受領と申告の修復、新しいHEADでの全行再判定など、担当の操作区分で補える処理は同じ担当が返却前確認まで終える。
返却前確認の非0や未完了処理の残存だけを続行不能の理由にしない。
委譲元の終端判断・認可、取得不能な入力、権限・外部状態など、本担当では補えない不足が残る場合だけ、その不足と再開位置を続行不能の理由へ書く。

返却は次の行とし、証拠要求ありでは`入力記録のパス`の次へ`完成条件証拠のパス: <完成条件証拠の絶対パス>`が加わる。`計画のパス`と`入力記録のパス`は返却前確認へ渡した正規化済み絶対パスのJSON配列（0件は`[]`）である。`<配列>の判定内訳`は証拠の全行の総行数と判定値別の件数のJSONで、証拠要求なしでは`{"総数": 0}`とする。`達成以外の行`は`達成`以外の行ごとに1行ずつ、配列名、0始まりの添字、WI、判定、`condition`か`requirement`、`source`と根拠をJSONで持つ。
根拠は`evidence`の全文とし、同じ出力で先に示した`達成以外の行`と同一の空でない根拠は、`evidence`の代わりに`evidence_reference`（表示名の`display`、配列名の`section`、1始まりの`row`）で先行行を指す。
`atk`が保存先と行数を返した場合は保存先から全量を読んで写す。続行不能時の`続行できない理由:`行と`agent-toolkit/share/rules-subagent.md`が定める追加行を含め、要約などの地の文は加えず、これらの規定行だけを返す。

```text
状態: completed
レビューしたHEAD: <レビューした対象HEADの7文字以上の一意な短縮OID>
未解決の指摘数: <未解決指摘数>
読者別探索: <ファイル別JSON申告、または文章成果物なし>
レビュー開始時点: <今回の開始時点の完全OID>
前回確認版の開始時点: <前回の開始時点の完全OID|なし>
前回確認版HEAD: <前回のレビューHEADの完全OID|なし>
計画のパス: <確認に用いた計画の絶対パスのJSON配列>
入力記録のパス: <確認に用いた入力記録の絶対パスのJSON配列>
受領確認入力のパス: <返却生成が保存した入力JSONの絶対パス>
wi_conditionsの判定内訳: <総数と判定値別の件数のJSON>
user_requirementsの判定内訳: <総数と判定値別の件数のJSON>
達成以外の行: <達成以外の1行の位置と項目のJSON（該当する行の数だけ繰り返す）>
```

複数のレビュー基準を受領した場合の`未解決の指摘数`は全基準の合算とする。
続行不能時も同じ形式を使い、1行目の`状態`行を置かず、末尾に`続行できない理由: <続行できない理由>`を加える。完了報告はツール戻り値で1回返す（委譲元へ`SendMessage`で送ることはしない）。想定外事象の追加行は`agent-toolkit/share/rules-subagent.md`に従う。
