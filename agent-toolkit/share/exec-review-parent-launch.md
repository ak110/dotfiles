## 起動方法別のレビュー基準

**2.** 要求と認可に合うレビュー単位・基準・担当モデルを確定する。

原要求・回答・公開契約から派生計画・review_contractの必要性も検収させる。
内部方式・検証手段は必要結果・品質・認可・制約を保って変更できる。

レビュー基準には、その実装を認可した手元の資料に応じて`計画`、`CI記録`、`WI`を組み合わせて指定する（対応する計画があれば`計画`、対象WIがあれば`WI`、計画がなくCI失敗に対応した実装なら`CI記録`）。
1回の実行レビューは`cwd`から解決する単一のリポジトリだけを対象とし、リポジトリが異なる基準はレビューを分ける。

別branch・worktreeの内部群は、レーン担当が、群ごとの実装・焦点検証・保存が完了した順にレビュー単位として起動する。
他群が編集中でも、対象群の書込担当はレビュー中にそのworktreeの編集・履歴更新を止める。
レーン担当は保存HEAD、割当要求と元WIの条件との対応、直接影響集合、検証の成功証拠を引き継ぎ記録で固定する。
起動には既存の`計画`、`対象ファイル限定`、`review_contract`と検証記録を使い、割当外の未達条件も元WIとの対応を保って渡す。
条件表では`exec-review-recording-contract.md`「記録する行と要求単位」の他項目への割当と除外理由の行を使い、群の割当外条件を除外理由の一致として検収させる。
同じ計画を複数群で使う場合は、原本と割当の対応を記した群ごとの計画とcommit対応記録の複製を独立した保存先へ置く。
その複製を`計画`として渡して指摘管理表と契約を群別に保持する。
群の判定範囲と完成条件証拠は`exec-review-recording.md`に従い、元WI全体の合格とは区別する。

対象WIに`担当モデル.実行レビュー担当`の指定があれば、そのモデル名を起動時の`model_type`と委譲入力の`担当モデル`へ渡す（読者別探索担当にも引き継がれる）。
モデルの比較と記録は`agent-toolkit:delegation`の`references/process-model-settings.md`「工程別モデル設定」に従い、対象WIごとにモデル指定が異なればレビューの実行単位を分ける。

同じレーンに複数の計画（初回分割時の複数計画、または凍結済みの先行計画と追加計画）がある場合は、レビューの単位（以下、レビュー単位）を計画の境界ではなく共有する変更で決める。
同じ最終実装HEADで判定対象commitの変更ファイルが重なる計画と、同じ変更範囲の検証を共有する計画は、1つのレビュー単位にまとめて1回だけ起動する。
計画を分けた理由（行数の警告、凍結済み計画への追加）だけではレビュー単位を分けない。
同じ準備・起動・読込を計画の数だけ繰り返すと、独立した判定を増やさずに所要だけが増えるためである。
レビュー済みの計画は、後述の「影響を受ける計画」に当たる場合だけ新しいレビュー単位へ含める。
1つのレビュー単位に複数の計画を含める場合は、`計画`へ全計画の絶対パスをJSON配列で渡し、1つの`review_contract`の中に計画名とAWIごとの要求行を残して、1つのレビュー指摘管理表と1つの返却を受け取る。
変更ファイルも検証も共有しない計画は別のレビュー単位とし、各単位にはその単位の計画に対応するAWIだけを割り当てる。
独立した保存HEADで先行レビューする内部群には群別の単位を適用し、共通の検証を要する組合せは最終レビュー単位へ含める。
レビュー単位ごとの成果物は、レビュー指摘管理表、完成条件証拠を含む返却メッセージ、`review_contract`である。
レーン全体を管理する担当には全レビュー単位の分を計画との対応を保って1回で渡し、各レビューthreadにはその単位の分を渡す。
契約ファイルは、初回・再レビューを問わず`exec-review-contract-generation.md`「`review_contract`の生成」に従ってレビュー単位ごとに作る。

レビュー修正やrebaseの競合解消でHEADが変わったら、影響する計画を含むレビュー単位だけを再レビューする。
前回レビューHEADを`R`、最新HEADを`H`、`<基点>`を開始時のHEAD（rebase後はrebase先OID）とし、次のどちらかに当たる計画を「影響を受ける計画」とする。

- `git range-diff <開始時のHEAD>..<R> <基点>..<H>`の結果で、その計画の判定対象コミット（`review_contract`で判定対象外としたコミットを除く）のいずれかが`=`以外で対応している
- `git diff --name-only <R> <H>`の変更ファイル一覧が、その計画の判定対象コミットで変更されたファイルと重なる

対象worktreeで上記コマンドを直接実行する。
判定対象コミットは`atk run-script plan-commits -- <計画の絶対パス> --worktree <対象worktreeの絶対パス>`が返すレビュー時点の一覧から判定対象外を除く。
変更ファイルは`git show --name-only --format= <commit>`で確認する。
終了が非0なら原因を解消して判定し直す。
影響を受けない計画は再レビューを省き、計画名、`R`と`H`の完全なコミットOID、実行したコマンド、対応行の要点、省略理由をレーンの引き継ぎ記録に残す。
rebaseでコミットOIDだけが変わった場合は再レビュー不要である。
影響を受ける計画でも、その差分が`agent-basics:review-standards/references/reviewee-verification.md`「方式見直しと再レビュー」の省略条件を満たす場合は、同節に従って再レビューを省く。
省略条件には、意味・動作・契約を変えない機械的な修正などがある。
省いた理由は同じ引き継ぎ記録に残す。
内部群の取り込み後は、受理済みレビューの本文・環境・契約との一致を確認し、元WI全条件への被覆と群間の契約、共有生成物、組合せ差分、未達条件を最終レビュー単位で検収する。
同じ条件で受理した群の本文を一律に再レビューせず、影響する範囲だけを上記の比較で選ぶ。
統合は、全レビュー単位のレビューが最終HEADで完了しているか、最後のレビュー以降の差分が前記の比較で影響しない修正だけであり、かつ元WI全体の条件別判定が統合時の受理条件を満たした場合に始める。
各指摘管理表の未解決指摘が0件であることも条件とする。

基準の`計画`には計画ファイルの絶対パスを書く。
計画の`## 実施内容`に挙がったWIはレビュー担当が自ら取得するので、委譲プロンプトには計画にないWIだけを書く。
プロンプトで渡すWIと、計画の`## 実施内容`に「人間由来のWI」「エージェント由来のWI」として挙がった関連WIを合わせた集合（対象WI集合）が空でない場合と、`ユーザー指示`由来の行がある場合を「証拠要求あり」と呼ぶ。
証拠要求があるレビューの返却には条件別の判定行を出す。
受理した返却の保存先（`agent_message_path`。`atk agents wait`の結果が示すファイルパス）は、計画名と対象WI集合に対応付けて後続の検収へ渡す。

## レビュー指摘管理表のパス

**3.** 既存のレビュー履歴を保持できる管理表を特定する。

1回の実行レビューでは単一の指摘管理表を使う。
レビュー担当は次の規則で保存先を決める。

- 基準に`計画`を含む場合: 計画ファイルと同じディレクトリの`<計画stem>.exec-review.tsv`（複数の計画を含むレビュー単位では、作成順で最初の計画のstem）
- 基準が`WI`のみの場合: `~/.claude/plans/wi-<開始時のHEAD>.exec-review.tsv`（`開始時のHEAD`は、委譲プロンプトに書く処理開始時のHEADの7文字以上の一意な短縮OID）
- 基準が`CI記録`のみの場合: `~/.claude/plans/ci-<修正系列の開始時のHEAD>.exec-review.tsv`（`修正系列の開始時のHEAD`は、委譲プロンプトに書く一連の修正の開始時のHEADの7文字以上の一意な短縮OIDで、同じ修正系列では引き継ぐ）

初回レビューで管理表が無い場合はレビュー担当が初回の読み取り前に作るので、メインエージェントは事前に初期化せず、表が無いことを理由に起動を拒まない。
既存の管理表や再レビュー用の管理表はそのまま使い続ける。
履歴を引き継ぐ場面で管理表が見つからない場合は、無い原因を調べ、空の表で代替しない。

## 入力

**4.** 基準ごとの不足を防ぐため、以下の入力を確定する。

- 必須入力名: `レビュー基準`、`引き継ぎ記録先`

必須の`レビュー基準`には「起動方法別のレビュー基準」で決めた基準を指定する。
必須の`引き継ぎ記録先`は`../skills/delegation/references/base-contract-handoff.md`「引き継ぎ記録先」に従って決める。
`計画`は対応する計画ファイルの絶対パスを渡す。
`CI記録`はCI失敗に対応する場合に記録項目を渡す。
`WI記録`は計画にない対象WIのファイル名、要求、完成条件、由来、採否を渡し、計画がない場合は全対象を含める。
基準ごとの要否と関連する開始時点は「起動方法別のレビュー基準」、`review_contract`の要否と値は`exec-review-contract-generation.md`「`review_contract`の生成」に従う。
`修正系列の開始時のHEAD`、`原因commitOID`、`開始時のHEAD`、`レーン識別子`、`レビュー種別`、`round`、`対象ファイル限定`、`Git管理外の変更`、`前回確認版`の要否と値は「起動」の説明に従って決める。
`担当モデル`は「起動方法別のレビュー基準」、`rewrite_map`は「レビュー修正」、`受理済みの完成条件証拠`は本書冒頭の規則に従う。

## 起動

**5.** 入力と所属を点検してから、確定した単位でレビューを起動する。

証拠の引渡しは`verification-evidence-records.md`「完成条件証拠の検証記録」に従う。
起動した後もレーンは同じ作業ツリーで別の修正を続けてよい。
その間のレビュー担当の検証の場所は、`exec-review-operations.md`「操作区分」の手順で対象worktreeの未commitの変更の有無から決まる。

次の引数で`agents_server`の`start`を呼ぶ。

| 引数 | 値 |
| --- | --- |
| `cwd` | 対象worktreeの絶対パス |
| `subagent_md_path` | `exec-review` |
| `extra_params` | 「入力」に示す入力パラメーター |
| `model_type` | `担当モデル.実行レビュー担当`の指定があればその値。なければ省略する |

初回起動の`extra_params`には、レビュー基準と、複数計画、計画外の条項または新形式AWIにより作った`review_contract`を含める。
`引き継ぎ記録先`の扱い（引き継ぎ再レビューでの`（継続）`表記を含む）は、`../skills/delegation/references/base-contract-handoff.md`「引き継ぎ記録先」に従う。
特定レーンの作業を対象に起動する場合は`レーン識別子`も指定し、セッション識別名を`<レーン識別子>-exec-review`とする（`CI記録`のみによる起動を除く）。
起動直前に`git merge-base <専用branch> <ベースbranch>`で分岐元コミットを解決し、計画の有無にかかわらず`開始時のHEAD`としてプロンプトに書く。
それ以外で`WI`だけを渡す場合は、作業開始時のHEADを`開始時のHEAD`とする。
`CI記録`を渡す場合は、`agent-toolkit:process-wi/references/ci-fix-series.md`の項目に加えて`修正系列の開始時のHEAD`と`原因commitOID`を書く。
`原因commitOID`はCI失敗が再帰するたびにCI記録と一緒に更新し、`修正系列の開始時のHEAD`は同じ修正系列で引き継ぐ。
CI記録には、メインエージェントが原因コミットを作ったときに持っていた情報を直接書く。
初回レビューでは、デフォルト値の`レビュー種別: 初回レビュー`と`round: 1`を省く。
再レビューの指示と引き継ぎ再レビューでは、`review-loop-coordination-rounds.md`「ラウンド番号の保持先」に記録した値で`round: <ラウンド番号>`を含める。
`対象ファイル限定`は対象ファイルを示す。
リポジトリ、レビューHEAD、変更ファイル、検証結果、指摘管理表は担当が解決する。
内部群では起動元が固定した保存HEADとの一致も確認し、未保存の本文や他群の未完了結果を判定根拠に含めない。
メインエージェントが読者別探索を起動する場合も、Git管理下の比較対象資料は`reader-fit-review.parent.md`「入力」のGit参照形式で渡す。
再レビューの比較元には前回のレビューHEADを指定し、レビュー単位ごとの判定範囲は同節の`判定範囲差分`で渡す。

Git管理外ファイルの変更前後の複製のペアがあれば、レーンの引き継ぎ記録にある全ペアを任意入力`Git管理外の変更`で渡し、無ければ省く。
メインエージェント自身が実装した場合は、`exec-subagent-implementation.md`「実装」のGit管理外ファイルの手順に従って最初の変更の前に複製を作り、そのペアを計画の`## 進捗ログ`（計画がなければ直接実装の引き継ぎ記録）に残す。
作業ツリー内の`.env`などの設定ファイルは通常の全文差分として扱う。
作業ツリー外で`agent-basics:secret-files`の対象となるファイルのペアは、キー名の一覧とキーごとの値の一致だけを比べる（同スキルの全文読み取りと出力の禁止を守るため）。

引き継ぎ再レビューは`レビュー種別: 引き継ぎ再レビュー`と次の情報を渡す。
契約の再作成は`exec-review-contract-generation.md`「`review_contract`の生成」、継続不能の判定と引き継ぎは`agent-toolkit:delegation`のSKILL.md「継続と新規起動」に従う。

- `前回確認版`: 前担当の引き継ぎ記録に保存された記録ファイルの絶対パス。
  前回レビューしたHEADのほか、Git管理外の文章成果物ごとの識別子と前回本文の複製パスを含む。
  記録ファイルと比較元の実在を確かめてから起動し、取得できない情報があれば、欠けたHEADや本文の取得元を委譲元へ報告する
- 基準ごとの追加入力: 「起動方法別のレビュー基準」と本節の`CI記録`・`開始時のHEAD`の説明で定めた各値

`agents_server`は必須入力の欠落を拒否する。
`レビュー基準`は基準名だけの値か、選んだ基準の追加入力（「起動方法別のレビュー基準」と本節の各入力）が揃っているかを起動時に検査し、基準名へ資料のパスや説明を連結した値も拒否する。
その後、新形式AWIでは初回・引き継ぎ再レビューとも、条件表の有無、列、主要完成状態、反映内容の全項目と出典の`反映内容N`の対応、補足条件数、AWI内の条件番号の一意性を起動時に検査する。
対象は計画の関連WIと`WI記録`の和集合とし、項目内の具体的な成果が条件から欠けていないかは、レビュー担当が`exec-review-recording-contract.md`「記録する行と要求単位」に従い原文と読み比べる。
起動前に追加入力、既存パスの実在、全基準・開始時点・管理表・`review_contract`の所属リポジトリの一致を確認する。
不足時は起動せず、不足入力・条項を委譲元へ返す。
