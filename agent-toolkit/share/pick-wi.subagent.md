# AWI選定とレーン分けタスク

対象リポジトリのWIキューを取得し、1処理回の対象、依存順、レーン、中断項目の再開位置を確定する。回答済みUWIを処理し、新規選定AWIを`processing`へ移す。計画、実装、`reject`、AWIの`adopt`は後続の担当が行う。
完了報告と成果物は日本語で書き、固定された返却値は指定どおりに返す。

## 入力

```text
必須入力名: 選定結果の出力先ファイル,引き継ぎ記録先
任意入力名: AWIファイル名一覧,既存レーンの選定結果ファイル
```

対象リポジトリは起動時の`cwd`が属するGit worktreeのroot、プロジェクト規範はその`cwd`で実行ホストがロードするプロジェクト指示として解決する。
`AWIファイル名一覧`の既定値は`なし`とし、行の不在を利用者指定なしとして扱う。利用者指定がある場合だけAWIファイル名一覧を受領する。
`既存レーンの選定結果ファイル`の既定値は`なし`とする。処理中の追加集合を選ぶ場合は、メインから元の固定出力の絶対パスを受領して既存レーンのAWIと書込領域を読む。この場合は`AWIファイル名一覧`の指定を必須とし、状態変更対象は明示一覧のWIに限る。

## 処理対象の決定

`atk wi list --status=processable --target-repo=<対象リポジトリの絶対パス> --skip-pull --with-staleness`を実行する。明示一覧がある場合は出力に現れる指定項目だけを対象とし、現れない名前を`needs_escalation`へ返す。指定が無い場合は`processing`の全項目と、次の除外条件に当たらない`inbox`項目を候補とする。鮮度情報は選定結果へそのまま保存し、`notice`だけを理由とする履歴調査は省く（努力目標。選定時間を短く保つ）。内容不一致、充足済みまたは巻戻しの危険を観測した項目だけ履歴を確認する。

- `ready`が偽であり、`blocked_reason`が`dependency-unmet-internal`以外である。依存の未充足を理由とする除外は`dependency-unmet-external`だけが該当する

一覧に現れた各項目の`depends_on`は候補選定の前に依存先ごとに状態と所有リポジトリを解決する。`atk wi show <依存ファイル名> --skip-pull`で全状態と全対象リポジトリを1回照会する。結果に現在の対象リポジトリの項目があればその項目に従う。現在の対象リポジトリに無く候補が1件ならfrontmatterの`target_repo`と状態に従い、複数の`target_repo`に同名項目がある場合は自動選択せず`needs_escalation`へ返す。別リポジトリの依存先が終端済みなら充足済み、未終端なら外部依存未達とする。別リポジトリの依存先の存在と状態は、明示照会の結果から判定する。

候補内の先行項目だけへ依存するAWIは、書込対象の包含関係がある場合も候補へ残し、推移的な依存先を含む同じレーンの依存順で扱う。依存先が開始時候補外、`hold`、別セッションで処理中などで着手不能なら、後続だけを開始せず依存待ちを維持する。初回選定の候補は処理回の開始時点の集合とする。追加選定では明示一覧にある新着項目だけを候補とする。`hold`の項目も初期候補には含めないが、回答を保存したUWIの本文が指す元項目は次段で保存状態を確かめ、`hold`なら候補へ加える。既に`inbox`で`ready=true`なら開始時候補へ含まれている。

初回選定では回答済みUWIを`atk wi list --type=uwi --answered=yes --status=processable --target-repo=<対象リポジトリの絶対パス> --skip-pull`で取得する。回答が作業を求めないUWIは「処理開始」で終端する対象とし、是正または保留中の元項目での作業を求めるUWIは回答を作業要求としてdecisionへ含める。追加選定の処理対象は明示一覧のAWIに限る。
回答済みUWIの本文が元項目のファイル名を示す場合は、その項目の保存状態と`ready`を確認する。元項目が`hold`にあるか`inbox`で`ready=true`であれば、開始時候補との集合和を取って固定集合へ一度だけ含める。状態の変更は「処理開始」で行う。そのUWIをdecisionへ含める場合は、UWIと元項目を同じレーンへ割り当てる。その他の保存状態と回答未保存の項目は`inbox/ready`と同一視せず、不足する状態条件を示して`needs_escalation`へ返す。

`processing`のまま残った項目では`atk plans list`を実行し、作業root内にある計画の`関連WI`が候補AWIを含むか確かめる。一意に対応する計画ファイルの絶対パスと`## 進捗ログ`の最終行から、残る最初の工程を`再開位置`へ返す。対応が無い場合または複数ある場合は推測せず`needs_escalation`へ返す。再開位置の記録先は選定結果の出力先ファイルとし、キュー項目は受領時の状態のまま残す。
進捗ログの最終行が「反映後の観測だけが残る」と示す場合も、その値を`再開位置`へ記す。実装済みの項目は既存計画の観測工程から再開する。

## 調査とレーン分け

各AWI本文を`atk wi show`で取得する。処理区分、依存順、変更対象の重なりまたは規模を本文だけから確定できない場合に限り、必要な定義、参照元および既存実装を調査する。`source`のない人間が手動投入したAWIは、症状、先行項目および端末出力などの手掛かりから作業要求を読み取る。反映先が未特定なら前段の限定調査で書込範囲と規模を見積もり、原因と実装方式の確定はレーン担当の計画へ渡す。通常AWIの見出し不足だけを`needs_escalation`の理由とせず、本文と調査からも作業要求を一意に解決できない場合は不足内容を示して返す。AWI本文に規模見込みが任意で記載されている場合はレーン分けの入力に加えるが、実際の計測値と矛盾する見込みは計測結果へ補正する。

レーン分けが満たす価値は、所要時間の均衡、依存の連結成分を割らないこと、およびレーン数を最小にすることの3つとする。レーン工程の完了は最も遅いレーンの完了で決まり、他のレーンが早く終わった分は待ち時間として残る。レーン数が増えるほど起動の固定コストも増える。

レーン数は`floor((WI数+9)/10)`を上限とし、前段の3つの価値を満たす最小の数を選ぶ。`WI数`は開始時候補のうち通常の除外条件に当たらない全件で数え、包含は差し引きの対象から外す。利用者の明示指示または必須是正で処理中に追加された項目は初回件数式の対象から外す。追加時の割当は`agent-toolkit:process-wi`の`references/run-lanes.md`「処理中に確定した必須是正レーン」で合計件数と既存レーンの受領可能性を判定する。
追加選定では受領した既存レーンのAWIと、追加候補の書込領域を比較する。各追加AWIと重なる既存レーンの識別子、重なる節・定義、重ならない場合はその結果を`lane_costs.rationale`へ記す。追加出力のレーン識別子は追加候補の内部で一意に割り当て、既存レーンへの最終割当と固定出力への追記はメインが行う。

各項目の所要時間の見込みは、既存方針から変更を一意に導ける軽量な項目か設計判断を要する項目かの区分と、AWI本文が示す変更対象の範囲から置く。
過去の処理回の計画ファイルの`## 進捗ログ`がレーンの稼働時間を保持する場合は、その実際の稼働記録も同じ導出の入力へ加える。
1つのレーンが担う見込みの合計は6000秒を上限とする。上限を超える配分では、レーン数の上限に達するまでの範囲で、依存の連結成分を割らずにレーンを増やす。この値はレーン別の稼働時間が2298秒から6708秒まで広がり、単独稼働が9482.3秒に達した処理回の計測結果を根拠とする。

レーン分割の前に、各項目の書込対象ファイルと変更する節・定義を対応付ける。候補内の同一リポジトリの`depends_on`と、同じファイルの同じ節または定義を書き換える項目を分割不能な連結成分の辺とし、各成分を同じレーンへ割り当てる。同一ファイルでも変更領域を一意に特定でき、書込集合が交わらない独立項目は別レーンへ分けられる。本文と必要な実装調査から変更領域を一意に特定できない同一ファイルの項目は、ファイル単位で重複すると判定する。書込の直列化は同じレーンの実装順で扱い、そのための保存依存と別処理回への延期は設けない。
あるAWIの書込対象ファイルと変更領域の集合が別の候補の集合を真に包含する場合は、必要な先行成果の依存順を守ったうえで包含するAWIを先行させ、重なる候補を同じレーンの分割不能な連結成分へ含める。包含だけを理由に`depends_on`を設定せず、候補とdecisionへ全項目を残す。書込対象が同じ広さで包含する側を一意に決められない組は、通常の重複規則で扱う。依存設定の必要性は`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`が定める。
書込領域の重複は直列統合時間ではなく、所要時間の比較より先に適用する分割不能条件とする。重複しない連結成分の割当では、実装時間の最大値と、待機、rebase、自動チェックの再実行の直列統合時間の合計が短い案を選ぶ。
書込領域の分割不能条件をレーン数の上限および6000秒の上限より優先する。分割不能条件は項目を同じレーンへまとめる制約であり、その成分を同じレーンへ保つ。分割不能条件だけで見込みが6000秒を超える連結成分がある場合は、そのレーンへ他の連結成分を加えず、他の成分を別レーンへ置くためにレーン数の上限を超えてよい。上限を守るための合流は、完了時刻を決める最も遅いレーンをさらに延ばすためである。上位の制約により6000秒の上限を守れない場合は、上限を超えたまま割当を確定し、超過した見込み値と超過が不可避である根拠を`lane_costs`の`rationale`へ書く。レーン数の上限を超えた場合は、超過の根拠となる連結成分と所要時間を同じ`rationale`へ書く。この競合は技術的に割当を確定できるため、`needs_escalation`へ送らない。
必要な依存にも前段の分割不能条件の優先順位を適用し、上限に合わせるために依存成分を割ったり次回へ送ったりせず、超過根拠を`rationale`へ残す。依存成分内は依存先を先にする。分割の根拠は依存と見込みに限り、主題とファイルの違いはこの根拠から外す。1件専用レーンを置くかは、前掲の3つの価値（所要時間の均衡、依存の連結成分を割らないこと、レーン数の最小化）の比較で決める。1つのAWIが複数要求を持つ場合も全要求を同じ処理回へ含める。

## 反映先と上流投入

AWIが指定する反映先を現物で確かめる作業はレーン担当が計画起草時に行い、picker側では省く（努力目標。計画起草時の確認と重複する）。picker側では不採用と既存実装による充足を確定しない。

対象リポジトリだけでは成立せず上流改訂を要する場合は、`upstream_submission`を上流要求の範囲に応じて記録する。投入先と要求は`upstream_target_repo`と`upstream_request`へ記録する。レーンの割当は「出力」の組合せ条件に従い、外部操作だけの項目もその条件で通常レーンへ渡す。レーン担当が採否と計画の作成要否、実施および終端を判断する。

選定結果を書き込む前に、起動時に読み込まれたプロジェクト指示のスキル表から、pickerまたは`project_notes`の記載を扱うスキルを特定して起動する。スキルを起動できない環境では、その参照先と必読資料を読んで同じように判定する。各AWIの反映先へ指定を当てはめ、`project_notes`を省略する判断の直前にも該当スキルの指定を確認する。

`project_notes`はプロジェクト規範が選定結果への記載を明示した場合だけ、その規範が指定する値を解決して記録する。値がファイルパスを含む場合は、選定時点で実在し読み取れることを確認する。指定の無い内容を推測して補わない。`upstream_submission`が`上流要求だけ`または`混在`の場合は`upstream_target_repo`を1件以上の空でない文字列、`upstream_request`を空でない文字列として出力前に確認する。`upstream_submission`が`なし`の場合は3つの上流投入行を全て省く。

`needs_escalation`はキュー入力の不整合、本文だけから明白なユーザー選好または外部待ちに限定する。公開契約変更の要否と採否はレーン担当が計画で確定する。

## 処理開始

開始時の処理可能候補とdecisionのファイル名集合が一致し、包含された項目を含めて各ファイル名が1回だけ現れ、複数レーンへ重複しないことを確かめる。合格後は同じ集合のまま以降の工程へ進む。

初回選定では、作業を求めない回答済みUWIを`atk wi adopt <filename>... --target-repo=<対象リポジトリの絶対パス>`で終端する。続けて、回答済みUWIの本文が指す元項目のうち`hold`にある項目だけを`atk wi unhold <filename>... --target-repo=<対象リポジトリの絶対パス>`で`inbox`へ戻す。選定時点が`inbox`のdecisionと`unhold`した元項目の集合和を取り、各項目を一度だけ`atk wi start-processing <filename>... --target-repo=<対象リポジトリの絶対パス>`で移す。追加選定では明示一覧にあるinboxのAWIだけを同コマンドで処理開始する。引数は`processing`にまだ無い項目に限る。各状態変更は成功報告と警告の不在を確認し、部分状態または原因不明ではAWIを追加遷移させず`needs_escalation`へ返す。

## 出力

次の本文を出力先ファイルへ書く。書き込み前に、各decisionの上流投入情報の既定値と省略を解決し、次の組合せを確認する。

| `upstream_submission`の解決値 | `lane` | 担当 |
| --- | --- | --- |
| `なし`（行の省略を含む） | 通常の`lane-NN` | ファイル変更の有無によらずレーン担当が採否・実施・終端を扱う |
| `上流要求だけ` | `なし` | メインが既存の上流投入工程を実施する |
| `混在` | 通常の`lane-NN` | メインの上流投入後、対象側の作業をレーン担当へ渡す |

この条件は作業を求める回答済みUWIにも適用する。外部待ちで処理不能な項目は「処理対象の決定」と既存の`needs_escalation`の判断を用いる。ファイル変更が無いことだけでは待機としない。通常レーンへの割当は外部操作の承認を追加せず、操作の確認とAWI終端は既存の担当手順で判断する。

```yaml
decisions:
- awi: <AWIまたは作業を求める回答が保存されたUWIのファイル名>
  lane: <`lane-NN`形式のレーン識別子(`NN`は2桁のレーン番号)または「なし」>
  staleness: <`atk wi list --with-staleness`が返した鮮度情報のYAMLフロー写像>
  再開位置: <作業root内の計画ファイル絶対パスと残る工程。既定値は「なし」>
  terminal_order: <固有の終端順序。既定値は「既定」>
  project_notes: <プロジェクト規範が指定した内容。既定値は「なし」>
  upstream_submission: <上流要求だけまたは混在。既定値は「なし」>
  upstream_target_repo: <投入先のYAMLフロー列。既定値は「なし」>
  upstream_request: <上流要求と対象側の後続作業。既定値は「なし」>
lane_costs:
- lane: <`lane-NN`形式のレーン識別子>
  implementation_seconds: <0以上の数値>
  integration_seconds: <0以上の数値>
  rationale: <同一レーン案と分割案の比較根拠を示す空でない文字列>
  after_lanes: <開始前に統合完了を待つ先行レーンの識別子のYAMLフロー列。既定値は「[]」>
阻害要因:
- <確認事項。完了時は「なし」>
```

処理可能な候補が0件の場合は、`decisions`と`lane_costs`を空の列（`[]`）とし、`status: completed`で返す。

既定値のとき省略する行は`再開位置`、`terminal_order`、`project_notes`、3つの上流投入行および`lane_costs`の`after_lanes`とする。行の不在は記載した既定値として解釈する。各decisionが必ず持つ行は`awi`、`lane`、`staleness`とする。`staleness`は一覧JSONの写像を値と型を変えずに転記する。

`lane_costs`は`なし`でないレーンを重複なく全て1件ずつ含める。秒数は実装時間と直列統合時間を分けて保持し、同じ値へ重複計上しない。同一候補の同一リポジトリ内依存は同じレーンへ置き、依存先を先にする。`after_lanes`は既存出力の読取互換のため形式と空列の既定値を残し、新しい選定では省略または空列とする。

選定結果を読む全ての主体は、本節が定める項目名、既定値および省略規則に従う。消費側の文書は本節を参照し、項目の再掲を省く（努力目標。正本を一意に保つ）。

書き込み後にdecision件数および候補件数が一致するか確かめ、次の3行だけを返す。

```text
status: completed | needs_escalation
output_file: <出力先の絶対パス>
lines: <行数>
```

完了報告はツール戻り値で1回返す。呼び出し元への能動送付はこの返却に含めない。想定外事象の追加行は`agent-toolkit/share/rules-subagent.md`に従う。
