# AWI選定とレーン分けタスク

対象リポジトリのWIキューを取得し、1処理回の対象、依存順、レーン、中断項目の再開位置を確定する。回答済みUWIを処理し、新規選定AWIを`processing`へ移す。計画、実装、`reject`、AWIの`adopt`は担当しない。
完了報告と成果物は日本語で書き、固定された返却値は指定どおりに返す。

## 入力

```text
必須入力名: 選定結果の出力先ファイル,引き継ぎ記録先
```

対象リポジトリは起動時の`cwd`が属するGit worktreeのroot、プロジェクト規範は当該`cwd`で実行ホストがロードするプロジェクト指示として解決する。
`AWIファイル名一覧`の既定値は`なし`とし、行の不在を利用者指定なしとして扱う。利用者指定がある場合だけAWIファイル名一覧を受領する。

## 処理対象の決定

`atk wi list --status=processable --target-repo=<repo-path> --skip-pull`を実行する。明示一覧がある場合は出力に現れる指定項目だけを対象とし、現れない名前を`needs_escalation`へ返す。指定が無い場合は`processing`の全項目と、次の除外条件に当たらない`inbox`項目を候補とする。

- `cooldown-until`、frontmatter不備又は依存不備でblockedである
- 候補に含まれない項目へ依存する

候補内の先行項目だけへ依存するAWIは除外せず、同じレーンの依存順で扱う。処理回の進行中に追加された項目は含めない。`hold`の項目も含めないが、回答を保存したUWIの本文が指す保留中の元項目は次段の手順で候補へ加える。

回答済みUWIは`atk wi list --type=uwi --answered=yes --status=processable --target-repo=<repo> --skip-pull`で取得する。回答が作業を求めないUWIは処理開始前に終端し、是正又は保留中の元項目での作業を求めるUWIは回答を作業要求としてdecisionへ含める。
回答済みUWIの本文が保留中の元項目のファイル名を示す場合は、当該元項目を`atk wi unhold`で`inbox`へ戻してdecisionへ含める。当該UWIをdecisionへ含める場合は、当該UWIと元項目を同じレーンへ割り当てる。

`processing`のまま残った項目では`atk plans list`を実行し、作業root内にある計画の`関連WI`を候補AWIへ照合する。一意に対応する計画ファイルの絶対パスと`## 進捗ログ`の最終行から、残る最初の工程を`再開位置`へ返す。対応が無い場合又は複数ある場合は推測せず`needs_escalation`へ返す。再開位置をキュー項目へ追記しない。

## 調査とレーン分け

各AWI本文を`atk wi show`で取得する。処理区分、依存順、変更対象の重なり又は規模を本文だけから確定できない場合に限り、必要な定義、参照元及び既存実装を調査する。AWI本文に規模見込みが任意で記載されている場合はレーン分けの入力に加えるが、実測と矛盾する見込みは実測へ補正する。

レーンへの配分は所要時間の見込みで均衡させる。レーン工程の完了は最も遅いレーンの完了で決まり、他のレーンが早く終わった分は待ち時間として残るためである。所要時間の見込みは本節の冒頭で取得済みのAWI本文から導き、当該処理回へ新しい取得工程を加えない。

レーン数は最小とし、`floor((WI数+7)/8)`を上限とする。`WI数`は当該処理回で固定した候補集合の件数とし、`## 処理対象の決定`が候補から除くと定める、処理回の進行中に追加された項目を含めない。上限未満のレーン数を選んでよい。レーン数が少ないほどコストの面で望ましいため、目安を満たす最小のレーン数を選ぶ。
処理対象が1件、又は依存の連結成分が1つで目安以内なら1レーンとする。その他は次の順で決める。

1. 既存方針から変更を一意に導ける軽量な項目と、設計判断又は既存契約変更を要する項目へ分ける。
2. 各項目の所要時間の見込みを置く。見込みは手順1の区分と、AWI本文が示す変更対象の範囲及び任意の規模見込みから導く。全項目の見込みの合計をレーン数の上限で割った値を、1レーンが担う見込みの目安とする。
3. 候補内の`depends_on`と、変更対象ファイル又は同じ公開定義が重なる組を無向辺とし、連結成分を分割しない。推測した対象で辺を設けない。
4. 目安を超える単一成分は1レーンへ置き、残る成分を各レーンが目安以内となる最小レーン数へ分ける。
5. 上限の内側で、同数の案では各レーンの見込みの合計の差が最小の案、さらに同じなら内容が近い項目を同じレーンに置く案を選ぶ。

依存成分内は依存先を先にする。独立項目は見込みの合計が最少のレーンへ置く。主題又はファイルの違いだけで分割せず、1件専用レーンは他項目と同じ計画では成立しない場合に限る。1つのAWIが複数要求を持つ場合も全要求を同じ処理回へ含める。

## 反映先と上流投入

AWIが指定する反映先の実測はレーン担当が計画起草時に行う。picker側では実測しない。不採用と既存実装による充足も確定しない。

対象リポジトリだけでは成立せず上流改訂を要する場合は、上流だけなら`lane`を`なし`にして`upstream_submission`を`上流要求だけ`とし、対象側の実装もあれば通常のレーンを割り当てて`upstream_submission`を`混在`とする。投入先と要求は`upstream_target_repo`と`upstream_request`へ記録する。外部操作又は待機だけの項目へレーンを割り当てない。実装を伴う全項目は通常のレーンへ割り当て、レーン担当が計画を起草する。

`needs_escalation`はキュー入力の不整合、本文だけから明白なユーザー選好又は外部待ちに限定する。公開契約変更の要否と採否はレーン担当が計画で確定する。

## 処理開始

候補集合とdecisionのファイル名集合が一致し、各ファイル名が1回だけ現れ、複数レーンへ重複しないことを検査する。合格後は集合を変更しない。

作業を求めない回答済みUWIを`atk wi adopt <filename>... --target-repo=<repo-path>`で終端する。続けて、回答済みUWIの本文が指す保留中の元項目を`atk wi unhold <filename>... --target-repo=<repo-path>`で`inbox`へ戻す。続けて選定時点が`inbox`のdecisionと当該`unhold`した元項目を`atk wi start-processing <filename>... --target-repo=<repo-path>`で移す。既に`processing`の項目を引数へ含めない。各状態変更は成功報告と警告の不在を確認し、部分状態又は原因不明ではAWIを追加遷移させず`needs_escalation`へ返す。

## 出力

次の本文を出力先ファイルへ書く。

```yaml
decisions:
- awi: <AWI又は作業を求める回答が保存されたUWIのファイル名>
  lane: <`lane-NN`形式のレーン識別子(`NN`は2桁のレーン番号)又は「なし」>
  再開位置: <作業root内の計画ファイル絶対パスと残る工程。既定値は「なし」>
  terminal_order: <固有の終端順序。既定値は「既定」>
  project_notes: <プロジェクト規範が指定した内容。既定値は「なし」>
  upstream_submission: <上流要求だけ又は混在。既定値は「なし」>
  upstream_target_repo: <投入先のYAMLフロー列。既定値は「なし」>
  upstream_request: <上流要求と対象側の後続作業。既定値は「なし」>
阻害要因:
- <確認事項。完了時は「なし」>
```

既定値のとき省略する行は`再開位置`、`terminal_order`、`project_notes`及び3つの上流投入行とする。行の不在は記載した既定値として解釈する。

書き込み後にdecision件数及び候補件数を照合し、次の3行だけを返す。

```text
status: completed | needs_escalation
output_file: <出力先の絶対パス>
lines: <行数>
```

完了報告はツール戻り値で1回返し、能動送付しない。想定外事象の追加行は`agent-toolkit/share/rules-subagent.md`に従う。
