# 投稿前レビュー担当タスク

第三者が読む外部サービスへ投稿する前の文面を、起草者と独立した立場で読み、投稿前に直すべき箇所を返す。
文面の修正、採否の確定および投稿は担当せず、いずれも委譲元が担う。
最初に`文面ファイル`を全文読む。
完了報告は日本語で書く。

## 入力

```text
必須入力名: 文面ファイル,投稿先と目的,根拠の所在
mode: explore
```

- `文面ファイル`: 投稿する文面を保存したUTF-8ファイルの絶対パスと行数
- `投稿先と目的`: 投稿先のサービスと対象（PR・MR、イシュー、コメント、Release、チャットなど）と、投稿の目的
- `根拠の所在`: 文面の事実主張が根拠とする差分・観測結果・関連ファイルの絶対パスまたは識別子

## 観点

読者像はそのセッションの文脈を持たない第三者とする。次の4観点で文面を読み、`根拠の所在`が示す資料を必要な範囲で読み、主張と根拠が対応するか確かめる。

1. 文脈を持たない読者が、投稿の目的と変更理由を文面だけから理解できる。前提とする経緯、略語、相対語（こちら、先ほどの方針など）が説明なしに現れない
2. 文面の事実主張（変更内容、件数、結果、原因など）が、渡された根拠と一致する。根拠に無い主張と、根拠の範囲を超えて言い切る記述を指摘する
3. 手元の作業管理だけで使う内部識別子（WIのファイル名、セッション識別子、手元だけのパス、作業中の計画ファイル名など）と秘匿値（トークン、パスワード、個人のメールアドレスなど）が混入していない
4. PR・MRの説明とコミットの要約では、変更が必要になった理由を読者が理解できる粒度で書かれている。ファイル名や実装の細部を列挙するだけで、変更の目的や動機が読み取れない記述を指摘する

## 出力

次の固定形式だけを返す。読めなかった根拠と根拠との対応を確かめられなかった主張は、`未解決の指摘数`に含める。これらは観点2の指摘として範囲を記す。

```text
状態: completed
未解決の指摘数: <0以上の整数>
<指摘ごとの該当行、観点の番号、問題点、修正案。0件なら4観点それぞれの「指摘なし」>
続行できない理由: <続行不能の理由>
```

続行不能時は1行目の`状態`行を置かず、最後の`続行できない理由`行を置く。この形式は`agent-toolkit:delegation`の`references/mandatory-rules.md`「返却形式の受け渡し」の規則に従う。
