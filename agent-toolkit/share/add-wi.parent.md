# WI投入担当の起動と受領

```text
起動対象: add-wi.subagent.md
```

AWI・UWIの作成・更新で成立性調査と起草をWI投入担当へ委ねるエージェントは、本書を全文読み、起動、入力の受け渡しおよび返却の検収へ適用する。`agent-toolkit:process-wi`のレーン工程で上流リポジトリへの投入を要する項目も同じ委譲で扱う。委譲先の手順と返却形式は`${CLAUDE_PLUGIN_ROOT}/share/add-wi.subagent.md`が定める。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 対象集合の見直し・存廃・要否・仕分けを求める依頼（先行成果物から登録項目を選ぶ依頼を含む）を渡す前 | `agent-toolkit:wi-standards`の`references/drafting-completion.md` |

## 起動前の前提

未終端の既存WIを更新・修復する必要が分かった時点と、既存WIへ対象と根拠のある具体的な懸念を受けた時点で、認識合わせや調査より先に`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`の手順で対象を保留する。`processing`の項目は同書「保留と本文修正」の処理中の項目の扱いに従い、書き換えたい内容を新規投入の要求として渡す。

要求ごとに投入先の対象リポジトリと種別を確定してから渡し、複数の投入先を持つ要求は要求と投入先の組へ展開する。
観測した問題（失敗、不具合、未対応など）を起点とする要求では、委譲元が`agent-toolkit:bugfix`の`SKILL.md`「直接的原因と事象時点の確定」で直接的原因と類似範囲を把握する。そのうえで症状が出た成果物、原因を生成する定義、機構を共有する成果物とそれぞれの所有リポジトリを分けて投入先を決める。担当は受領した投入先の中だけを扱うため、症状の出た成果物だけで投入先を決めると、機構を共有する他の成果物とリポジトリが是正から漏れる。把握した範囲の未走査部分は`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従って走査を続け、集合を名指しの例へ狭める案は`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文からの具体化を要する軸」で確認する。根本原因と対策の確定は担当へ残す。
原因調査に必須でユーザーだけが提供できる資料・実例は、同スキルの`SKILL.md`「未確定判断の保留と暫定判断」に従い、担当の返却を待たずに提供を依頼して該当する要求を保留する。この依頼は対処の選択を問う確認と分けて送り、原因の説明は資料で確定してから伝える。資料なしで進められる要求はそのまま渡す。
認識の違いで要件や結果が変わる未確定事項を含む要求は、回答を得てから渡す。
対象集合の見直し・存廃・要否・仕分けを求める依頼では、レビューや見直し自体が依頼された作業であっても対象の採否は投入前に確定する。判定済みの対象は結論を`委譲元の判断`へ、未調査の対象は`投入前に確定すべき事項`へ対象ごとに書いて渡す。

## 渡す入力

`投入する要求`の内容はmanaged-temp内のUTF-8ファイルへ全量を保存し、その絶対パスを渡す。起動引数へ埋め込むと引用符と改行の解釈が変わる（`docs/development/audit-records.md`「agent-toolkit/share/add-wi.parent.md：渡す入力：2026年10月7日」）。共通入力を別ファイルに置く場合は要求ファイルから絶対パスで参照する。直接本文を渡す入力も互換として受理される。

- `投入する要求`: 要求ごとの識別子、`質問への回答の扱い`、投入先の対象リポジトリ、種別、要求の趣旨、`確定した要件`、`委譲元の判断`、`投入前に確定すべき事項`、`source`、保持している場合のユーザー発話の逐語本文と出所、`他の要求単位の割当`、`確定済みの観測`
  - `質問への回答の扱い`: 逐語本文の質問ごとに、送達済みの回答内容と送達済みであること、または担当の調査で確定する回答の対象。後者の回答済み注記は回答の送達後に指定する。質問が無ければ`なし`
  - 要求の趣旨: 委譲元が確定した結論（対象、観測した事象、確定していれば原因と対策の1案、要求間の依存）だけを書く。調査の経緯と裏付けの無い推定（行番号、件数、見積もり、発話にも観測にも無い結果や影響の言い換えなど）は書かず、事象は発話か観測が示す範囲の語で書く。担当が投入先を独立に調べる目的を委譲元の推論で狭めないためである。原因が未確定なら`投入前に確定すべき事項`として渡す（担当は原因を確定できなければ投入せず返すため、原因調査を後続の要求へ分けさせない）
  - `確定した要件`: ユーザーが明示した要件と、確認への回答などで合意した要件だけを置く。回答として扱う範囲は`agent-toolkit:wi-standards`「由来と承認」に従い、質問本文や`共通前提:`行に置いたエージェントの判断は`委譲元の判断`へ回す。後続工程（計画・実行・実行レビュー）のモデル、ツール、担当エージェント、操作方法は、その工程への適用を示す発話か独立した確認回答に対応する場合だけ置く。置くのは`agent-toolkit:wi-standards`冒頭のAWIの粒度でその要求の具体化・変更と判定した要件に限る。別目的で単独の採否・実装・完成判定が成立する要件は、反映先が部分的に重なっても別の要求として「起動方法」で新しい担当へ渡す。同じ発話内の要件、途中の書き方への注文、振る舞いの是正（再発防止の要求を含む）も要求単位ごとに判定する
  - `委譲元の判断`: 委譲元が技術判断で決めた前提を理由とともに置く。範囲の判断、選んだ対策の方向、委譲元が選んだ比較・検収の手段（ユーザーの指定を除く）を含む。起草者は調査で得た事実でこれを覆せ、観測事象を契機とする要求の対策の方向は候補の1つとして扱われる。`確定した要件`へ混ぜると覆せない制約として扱われ、品質の退行を伴う案が選ばれる。該当が無ければ`なし`
  - 原文の対象集合を判定する基準や対策の範囲を委譲元の語で書く判断は、置く前に`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」で原文と比べ、比較結果（広い場合は根拠も）を理由へ書く。原文より狭い判断は渡さず、狭める必要があれば同スキル「原文からの具体化を要する軸」で確認して合意した範囲を`確定した要件`へ置く。作成した基準を原文の対象の該当例の1つとして渡すこともできる。字面で名指しされていないことを理由に原文の集合の対象を除く判断も、この比較の対象とする
  - 判断の理由へ使う事実は、渡す直前に同じセッションで確かめた観測（`確定済みの観測`の形式）か、ユーザーの方針の記録の所在へ対応付ける。未確認の前提は`agent-toolkit:delegation`の`references/sending.md`「未検証情報の取り扱い」に従って未検証とし、`投入前に確定すべき事項`へ対応付ける。変更量や改訂費用だけを不採用の理由にしない
  - `投入前に確定すべき事項`: 確定すべき項目だけを書き、委譲元が想定する答えや案は書かない
  - `他の要求単位の割当`: 渡す逐語本文のうちその要求が扱わない単位ごとの割当先。値は投入済みAWIのファイル名とH1タイトル、同じ委譲で別の担当へ渡した要求を特定する「」で囲む説明、`分割元の依頼全体`のいずれかとし、割当先を決めた単位だけを渡す。該当が無ければ`なし`
  - 要求間の依存は、`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`の先行成果の必要性の根拠とともに渡す
  - `source`: 委譲元が`agent-toolkit:wi-standards`「由来と承認」で決めた値（`add-awi-by-user`、`session-review`、`process-wi`、`agent`など）
  - ユーザー発話: 対象の逐語内容と、委譲元自身の記録を指定できる識別子（Claude CodeではセッションID、Codexでは`session-review-evidence --codex-thread-id`へ渡せるthread ID）。同文の反復があれば時点や前後の文脈も添えて対象を選べるようにし、構造化確認は質問・全選択肢・選択回答・自由記述の対応を保つ。委譲元は出所の抽出を待たずに回答・調査・追送へ進み、担当が証拠を使う時に既存の抽出CLIで出所を確定する
  - 取得済みの出所があれば、元の出力ファイルの絶対パスとそのJSONレコードの`record`欄・`line`欄の値を渡し、担当はそれを再利用する。`line`は元のセッション記録の行位置であり、出力ファイルの物理行番号とは別の値である。`session-review-prepare`の`conversation.md`も抽出CLI由来の原文として使える
  - `確定済みの観測`: 観測ごとの内容、手段（実行したコマンドと入力）、時点と、取得済みの記録位置（元の記録での`<記録>:<行番号>`）または保存出力の絶対パス。位置が未取得なら、委譲元自身のtranscriptの絶対パスと観測の入力の特徴・時点を渡せばよく、位置を得るためだけの事前照会は要らない。「起動前の前提」で確かめた直接的原因と類似範囲もこの形式で渡す。再実行の要否は担当が判定するため、再確認を促す指定は加えない
  - 範囲語か開放列挙と、例示か理由を併せ持つ依頼では、例示の近傍を起点に検索した観測はそうと明記し、集合全体の観測と区別して渡す。集合全体の観測には、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」の該当項が定める独立した調査の結果を、受け渡し前に委譲元が済ませて含める
  - 投入済みAWIの更新と失敗後の再開では、保留を終えた対象の`ファイル名`も渡す
- 上流投入の要求では`元項目`（元項目のAWIファイル名）と`投入条件`も渡す。複数の投入先は元項目と投入先の組へ展開する
- `引き継ぎ記録先`: `agent-toolkit:delegation`の`references/base-contract.md`「引き継ぎ記録先」に従う

## 起動方法

委譲の目的は、起草を作業文脈の少ない担当へ移すことである。独立した要求を同じ担当へ足すと、先の要求の調査と判断が後の起草へ入り込む。

- `agent-toolkit:wi-standards`冒頭の粒度で独立と判定した要求は、要求ごとに別の担当を起動する（並行起動してよい）。反映先の部分重複は独立性の否定に使わず、書込競合として扱う
- 1つの要求を投入先へ展開した全ての組（上流投入では同じ`元項目`の組）、`agent-toolkit:wi-standards`の`references/cross-repository-submission.md`の整合を要する組、依存で結ばれた要求は同じ担当へ渡す
- 担当は他の担当の成果を知らないため、担当をまたぐ事実（割当先、1つの判断を展開した本文の集合、依存先の正式名など）は委譲元が保持して各担当へ渡し、「受領と検収」で原稿の集合と比べる
- 起動後に生じた独立した要求は新しい担当へ渡し、稼働中・終端済みの担当へ`send_message`で足さない
- 同じ担当への追送は、渡した要求の要件更新と「受領と検収」の修正と再開に限る。追送の前に追加の発話を要求単位へ分け、`確定した要件`の帰属の条件を単位ごとに判定する。一部が要件更新に当たることを残りの単位を含める理由にしない

`agents_server`の`start`を次の引数で呼ぶ。

| 引数 | 値 |
| --- | --- |
| `cwd` | 委譲元の作業ディレクトリの絶対パス。上流投入では元項目を保持する対象リポジトリの絶対パス |
| `subagent_md_path` | `add-wi` |
| `extra_params` | `投入する要求`には要求ファイルの絶対パス、`引き継ぎ記録先`には記録先を渡す |

```json
{"投入する要求":"/absolute/managed-temp/requirements.md","引き継ぎ記録先":"/absolute/managed-temp/handoff.md（新規）"}
```

## 受領と検収

### 原稿の検収

返却の形式と省略規則は`add-wi.subagent.md`の`## 出力`が定める。原稿の返却を受けたら保存前に次を検収し、合格した要求識別子を`保存開始`として同じ担当へ直ちに送る。他の担当の返却や別のAWIの確定とは独立に送り、同じ担当内の依存順だけを保つ。不合格の要求は「修正と再開」に従う。起草者と別のエージェントによる確認は、案を確定した委譲元のこの検収が担う。

- `起草結果`の要求識別子が重複せず、渡した要求の集合と一致する。全体の`状態`行の有無が要求ごとの`結果`行と`続行できない理由`行から規則どおり導かれている
- `drafted`の要求は、`既存項目の扱い`が再利用の場合を除き、原稿と成立性の証拠の絶対パスが実在して読める。原稿は`agent-toolkit:wi-standards`「通常AWIの本文」（UWIは`references/uwi-format.md`）を満たし、委譲元の会話や元項目に依存せず本文だけで理解できる。全節が`references/drafting-completion.md`「投入前の読み直し」の要求固有性の点検を満たす
- `既存項目の扱い`を返した要求は、既存項目の本文を読んで`drafting-completion.md`「重複判定」が成立することを確かめる。再利用は`保存開始`を送らず既存ファイル名を投入結果とし、部分被覆は原稿が未被覆部分だけを扱うことを確かめる
- AWIの反映内容・完成条件、UWIの問い・判断材料・回答による結果が、渡した要求（確定した要件と逐語本文）と一致し、「他AWIへ割当」の割当先が渡した`他の要求単位の割当`の値だけである
- 説明追記は、完成条件と一致していても`agent-toolkit:writing-standards`の`references/writing.md`「人間向け文章の共通規定」の必要性判定を満たす場合だけ受理し、満たさなければ採否の再選定を返す
- 仕分け・要約・統合を経た原稿は、成立性の証拠の元の調査結果へ個別の採否、変更箇所、保持条件、根拠を対応付けられる（`drafting-completion.md`「対象集合の仕分け」）
- 観測した欠陥を起点とするAWIは、`drafting-completion.md`「投入前の読み直し」の原因分析の項を委譲元が原稿と証拠の読取で独立に確かめる。直接的原因の根拠の値ごとに生成元と比較があり、主張の対象を表すと読み取れなければ不合格とする（委譲元は同じ調査をやり直さない）
- 既存の値や設定を変える反映内容・選択肢には、`drafting-completion.md`「方針と判断の記録との比較」の結果が成立性の証拠（AWIではH1直下も）にある
- 原稿が必須とする手段と条件が次の根拠に対応する。委譲元自身の追送やWIに書かれていることは根拠にしない
  - 完成条件が必須とする比較・検収・工程の指定: 原要求か、品質判定に必要な理由
  - 後続工程のモデル、ツール、担当エージェント、操作方法: その工程への適用を示すユーザー発話か独立した確認回答。渡した`確定した要件`が含めていた場合は要件から外して渡し直す
  - 処理を実施しない・延期する保護条件: `## 実現性`にある確定した要件、規範的制約、観測済みの欠陥のいずれか。外部文書が記す可能性や安全側であることだけでは対応先にならず、同じ担当へ戻す
- 依存が`states-and-dependencies.md`の基準に従い、後続本文の先行成果の必要性と対応する
- 逐語本文の範囲語か開放列挙が示す集合に未走査・後送りの範囲があれば不合格とし、残りの調査と反映を指示する。分割読取で読める未読や未調査を委譲元の調査へ引き取らない
- 原稿、証拠、返却（`想定外事象:`を含む）の未確認範囲は、担当が確かめる手段を持つ間は不合格とし、手段のある範囲は担当へ戻すか委譲元が確かめて渡す。「失敗しても記録される設計にした」「完成条件の判定を変えない」は受理の理由から外す。手段の無い範囲は、根拠が`## 実現性`にあり`agent-toolkit:wi-standards`の`references/awi-body.md`「原因分析・適用範囲・実現性」の条件を満たす場合だけ受理する
- `判断の変更`を返した要求は、採った案が`確定した要件`の対象、範囲、外部可視の結果と両立することを確かめ、手段や条件を加える場合は前掲の根拠も確かめる
- `condition_not_met`の要求は`条件判定`が不成立の条件、調査対象、確認結果を示している。その要求は投入先のファイル名を使う後続工程から除く

### 続行できない理由の扱い

`保存開始`を送るのは続行できない理由が解消した要求に限る。上流投入では、解消までその元項目のレーンの起動と状態の変更を保留する。

- 認識の違いで要件や結果を変える未確定事項: `agent-toolkit:user-confirmation-and-report`「確認要否の判定」で根拠と既存認可を検収し、ユーザーだけの値が残る部分を確認する。技術的に確定できる不足は同じ担当へ返す。担当の直接的原因を確認の前提や選択肢に使う場合は、原因分析の項と同じ確かめを先に行う
- `確定した要件`が別の要求に当たる（帰属の判定）: その要件を同じ担当から外し、別の要求として新しい担当へ渡す
- 規範の投入前条件が未完了: 指摘された条文と未判定の対象を読み、調査で進められるなら同じ担当へ続行を指示する
- 到達・権限不足で担当の調査が成立しない: 照会結果を確かめ、委譲元側で成立する調査は同じWI作成工程で行って結果を渡す。こちらでも成立しなければ`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従って報告し、共通判定で残るユーザー依存事項だけを確認する

### 保存の検収

保存の返却では、指示した集合との一致、`completed`の実際のファイル名、CLIの終了コード0、成功報告と警告の判定を確かめる。CLIが保存本文の一致を確かめるため、意味の検収は原稿の検収結果を使う。新しい成立性の論点が要る場合はその必要性を具体化し、計画・実行に属する検証はそれらの工程へ渡す。

- 分割起票した組では、保存済みのAWIが他AWIへ割り当てた単位の受渡し先が全て`completed`になったことを確かめる。受渡し先が`condition_not_met`か投入しないと決めた場合は、その単位を新しい要求か割当元AWIの更新として渡す
- 「起動前の前提」で保留した既存AWIは、保存本文の検収が成立してから`atk wi unhold`で戻す

### 修正と再開

検収に失敗した場合は、同じWI投入担当へ不一致の修正を指示する。続行できない理由を解消した後は、失敗した要求だけを同じ担当へ渡して再開し、`completed`か`condition_not_met`になった要求はその結果を保持する。保存済みの`ファイル名`がある失敗要求はその値も渡して既存の保存先を修復させる。再開後の返却は再開時の集合に対して同じ規則で検収する。

## 受領後の報告

担当の調査に依存する事項（原因、対象範囲など）への回答は、返却を検収してから、確定した結論か確定できない限界を根拠に送る。返却前は観測済みの事象と調査中であることを伝える。確定済みの事実への回答は先に送ってよい。回答済みとして扱うのは送達の完了後とする。

返却前にユーザーへ伝えた回答や説明のうち担当の調査対象（原因、対象範囲など）に依存する記述を、返却で確定した内容と比べ、異なれば次の報告で誤っていた記述と確定した内容を明示して訂正する。
