# WI投入担当の起動と受領

```text
起動対象: add-wi.subagent.md
```

エージェントが通常AWIを投入する場合と、投入済みAWIの内容（対象、範囲、完成条件などの本文）を更新する場合に、本書を全文読み、WI投入担当の起動、入力の受け渡しおよび返却値の検収へ適用する。
`agent-toolkit:process-wi`のレーン工程で上流リポジトリへの投入を要する項目も、同じ委譲で扱う。
呼び先の作業手順と返却形式は`${CLAUDE_PLUGIN_ROOT}/share/add-wi.subagent.md`が定め、本書の記載対象から外す。

## 起動方法

WI投入担当はタスク文書起動（`agent-toolkit:delegation`の`references/base-contract.md`「タスク文書起動」）で起動し、次の単位で分ける。
委譲の目的は、起草を作業文脈の少ない担当へ移すことである。独立した要求を同じ担当へ足すと、先に扱った要求の調査結果と判断がその担当の文脈に残り、後の起草へ入り込む。

- 反映先と完成条件が他の要求と重ならず、単独で採否と実装を判断できる要求は、要求ごとに別の担当を起動する。互いに独立した担当は並行して起動してよい
- 次の要求の組は同じ担当へ渡す。1つの要求を投入先の組へ展開した全ての組（上流投入では同じ`元項目`の組）、`agent-toolkit:wi-standards`の`references/cross-repository-submission.md`が扱う同じ成果の整合を要する組、依存で結ばれた要求（先行項目の正式名を待つ後続を含む）
- 起動後に独立した要求が生じた場合は、新しい担当を起動する。稼働中の担当と終端済みの担当のどちらへも`send_message`で追加しない
- 同じ担当へ追送するのは、その担当へ渡した要求の要件更新と、「受領と検収」が定める修正と再開に限る

`cwd`は呼び出し元の作業ディレクトリの絶対パスとし、上流投入では元項目を保持する対象リポジトリの絶対パスとする。

## 起動前の前提

要求ごとに、投入先の対象リポジトリと種別を確定していることを確認する。1つの要求が複数の投入先を持つ場合は、要求と投入先の組へ展開してから渡す。
投入先または種別が欠ける要求は起動文へ含めず、確定してから渡す。
認識の違いで要件や結果が変わる未確定事項は、回答を得てからその要求を渡す。回答を得られない事項を含む要求は起動文へ含めず、回答の受領まで保留する。

## 渡す入力

- `投入する要求`: 要求ごとの識別子、投入先の対象リポジトリ、種別、要求の趣旨、`確定した要件`、`呼び出し元の判断`、投入前に確定すべき事項、`source`、保持している場合のユーザー発話の逐語本文と出所、および呼び出し元が同じセッションで実行して確かめた`確定済みの観測`
  - 要求の趣旨へ書く値は、呼び出し元が確定した結論に限る。確定した結論とは、対象、観測した事象、原因と対策の1案、要求間の依存である。原因と対策は呼び出し元が確定している場合だけ書く。呼び出し元が原因を確定していない要求は、その確定を投入前に確定すべき事項として渡す。WI投入担当が投入前に原因を確定できなければ投入されず返るため、原因の調査を後続の要求へ分けて投入させない（`agent-toolkit:wi-standards`の`references/drafting-completion.md`）
  - `確定した要件`にはユーザーが明示した要件と、確認への回答などでユーザーと合意済みの要件だけを置く
  - `呼び出し元の判断`には呼び出し元が技術判断で決めた前提を、判断ごとに理由を添えて置く。名指しされていない対象を変えないなどの範囲の判断と、対策の案のうち呼び出し元が選んだ方向（反映先の候補など）もここへ置く。初回入力と追送で呼び出し元が選んだ比較・検収の手段も、ユーザーが指定した場合を除きここへ置く。起草者は調査で得た事実によってこれを覆せる。観測事象を契機とする要求の対策の方向は、起草者が自ら原因分析で導いた案と比べる候補として扱われる。該当が無い場合の省略時の値は`なし`とする。呼び出し元の判断を`確定した要件`へ混ぜると、起草者はそれを覆せない制約として扱い、前提を守るために品質の退行を伴う案を選ぶ
  - ユーザー要求の対象（原文の語が指す集合）を判定する基準、定義または対策が扱う範囲を呼び出し元の語で書く判断はユーザー発話から導いた結論に当たる。置く前に`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`の比較の項で原文と比べる。理由へは、原文の集合と一致するか、原文より狭いか広いかの比較結果を書き、異なる場合はその根拠も書く。原文より狭い判断は`呼び出し元の判断`として渡さない。狭める必要がある場合は同スキルの`references/judgment.md`「原文からの具体化を要する軸」に従ってユーザー確認し、合意を得た範囲を`確定した要件`へ置く。原文の語を対象のまま保ち、作成した基準を原文の対象に含まれる該当例の1つとして渡すこともできる。狭い基準を技術判断の欄へ置くと、比較を経ずに要求の対象が縮んだまま起草される
  - 要求の趣旨へは、原因に至った調査の経緯、判定に至る過程、裏付けを取っていない推定値（行番号、件数、費用の見積もりなど）を書かない。担当が投入先を独立に調べて起草するという委譲の目的を、呼び出し元の推論で先回りして狭めないためである
  - 判断を渡す直前に、理由へ事実として使う内容を同じセッションで確かめた観測へ、利用者が確定した方針をその記録の所在と該当箇所へ対応付ける。観測は後述の`確定済みの観測`の形式で渡す。未確認の前提は`agent-toolkit:delegation`「未検証情報の取り扱い」に従って未検証とし、投入前に確定すべき事項へ対応付ける。採否は守る要件と品質への影響を比べて決め、変更量や改訂費用だけを既存側の維持や不採用の理由にしない
  - 投入前に確定すべき事項には確定すべき項目だけを書き、呼び出し元が想定する答えや案を書かない
  - 要求間の依存を渡す場合は、`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`に従い、先行成果の必要性の根拠を要求へ含める
  - `source`は呼び出し元が`agent-toolkit:wi-standards`「由来と承認」に従って決めた値（`add-awi-by-user`、`session-review`、`process-wi`、対応するスキルを持たない起票では`agent`など）とする
  - 出所は呼び出し元が自身のトランスクリプトから抽出器で取り出した出力ファイルの絶対パスと、引用する発話・確認回答の記録位置（出力の`record`と`line`）とする。抽出は呼び出し元が次のコマンドで行う。Codexでは`--claude-session-id "$CLAUDE_CODE_SESSION_ID"`の代わりに`--codex-thread-id "$CODEX_THREAD_ID"`を使う

    ```sh
    atk run-script session-review-evidence -- --claude-session-id "$CLAUDE_CODE_SESSION_ID" --user-events --since <引用する最初の発話より前の時刻> --output-file <管理対象一時領域の絶対パス>
    ```

    この出力は本文を切り詰めず、確認回答には質問、提示した全選択肢、選ばれた選択肢および自由記述が入る。`agent-toolkit:session-review`の`session-review-prepare`が出力する`conversation.md`も抽出器由来の原文であり、そのまま出所に使える
  - `確定済みの観測`は観測ごとの内容、手段（実行したコマンドと入力）、時点および記録位置（transcriptの絶対パスと`<記録>:<行番号>`、または出力を保存したファイルの絶対パス）とする。再実行の要否は受信側が判定するため、起動文で再確認を促さない
  - 範囲語か開放列挙と、例示か理由を併せ持つユーザーの依頼を起点とする要求では、例示の語形やその近傍を起点に検索した観測にそのことを書き、対象集合の全体を表す観測として渡さない。WI投入担当は例示を含む逐語本文を受け取るため、例示を伏せた調査を担えない。対象集合の観測には、`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`の同じ依頼を扱う項が定める独立した調査の結果を含める。対象集合の確定を投入前に確定すべき事項として渡す場合も、その調査は呼び出し元が受け渡しの前に済ませる。調査せずに渡す場合は、観測が例示の近傍に限られることを`確定済みの観測`へ書く
  - 投入済みAWIを更新する要求と失敗後に再開する要求では、更新または修復する項目の`filename`も渡す。既存AWIの更新では、呼び出し元が`atk wi hold`で保留してから渡し、保存本文の検収後に`atk wi unhold`を実行する
- 上流投入の要求では、`元項目`（元項目のAWIファイル名）と`投入条件`も渡す。`upstream_target_repo`が複数の投入先を含む場合は、元項目と投入先の組へ展開する
- `引き継ぎ記録先`: 値は`agent-toolkit:delegation`の`references/base-contract.md`「タスク文書起動」が指す`引き継ぎ記録先`の書式に従う

## 受領と検収

返却の形式、省略時の値および省略規則は`${CLAUDE_PLUGIN_ROOT}/share/add-wi.subagent.md`の`## 出力`が定める。呼び出し元は次を確認する。

- `submissions`が挙げる要求の識別子が重複せず、その集合が起動文へ渡した要求の集合と過不足なく一致する
- 全体の`status`が、要求ごとの`result`から同書の規則どおり導かれている
- `result`が`completed`の要求は`filename`が値を持ち、投入先を絶対パスまたは正規化リモートURLで渡した`atk wi show <filename> --target-repo=<その要求の投入先> --skip-pull`が終了コード0でその項目を返す。保存本文が`agent-toolkit:wi-standards`の本文契約を満たし、呼び出し元の会話文脈と元項目を参照せずに反映内容、反映先および完成条件を判断できる
- 同じ保存本文の反映内容と完成条件が、渡した要求（確定した要件と逐語本文）と一致する。案を確定した呼び出し元が起草者の成果を確かめる工程であり、起草者と別の主体による確認をこの検収が担う
- 完成条件が必須とする比較・検収・工程の指定が、原要求か品質判定に必要な理由のどちらかへ対応する。呼び出し元が選んだ手段が必須の完成条件へ昇格している場合は、その根拠を本文から読み取る。呼び出し元自身の追送と、WIに書かれているという事実は根拠にしない
- 保存された依存が`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`の基準に従い、後続本文の先行成果の必要性と対応する
- `判断の変更`を返した要求では、覆された呼び出し元の判断と理由を読み、採った案が`確定した要件`の対象、範囲および外部可視の結果と両立することを確かめる
- 返却より前にユーザーへ伝えた回答や説明のうち、担当の調査対象（原因、対象範囲など）に依存する記述を、返却で確定した内容と比べる。異なる記述があれば、次のユーザーへの報告（作業完了報告など）で、先の回答のどの記述が誤りだったかと確定した内容を明示して訂正する
- `result`が`condition_not_met`の要求は`条件判定`が不成立の条件、調査対象および実際の確認結果を示す。その要求を投入先のファイル名を用いる後続工程から除く
- `result`が`needs_escalation`の要求は`阻害要因`が値を持つ。阻害条件が認識の違いで要件または結果を変える未確定事項である場合は、呼び出し元がユーザー確認して回答を得る。上流投入では、その要求を含む元項目のレーンを起動せず、元項目の状態も変更せずに阻害条件の解消まで保留する

いずれかの検収に失敗した場合は、同じWI投入担当へ不一致の修正を指示する。
阻害条件を解消した後は、失敗した要求だけを同じ担当へ渡して再開する。先に`completed`か`condition_not_met`となった要求は再投入せず、その結果を保持する。
保存済みの`filename`がある失敗要求はその値も渡し、既存の保存先を同じ投入手順で修復させる。既存AWIの更新と同じ入力の形である。
再開後の返却は、再開時に渡した要求の集合に対して同じ規則で検収する。
