# 実行レビュー反復の調整

実行レビューの委譲元が、指摘の受領、修正、再レビューおよびエスカレーションを収束まで調整する。
レビューイーは、`agent-toolkit:process-wi`ではそのレーンのレーン担当、`agent-toolkit:plan-mode`のメインによる起動ではメイン、公開工程のCI失敗修正では終端担当が起動する`CI修正担当`とする。

## ラウンドの遷移

1. レビュー担当が対象HEADをレビューし、指摘をレビュー指摘管理表へ登録する。
2. `${CLAUDE_PLUGIN_ROOT}/share/exec-review.parent.md`の受領手順で、表と完成条件証拠から生成した未解決件数0件と、達成を要する行の証拠が揃うことを確認したら収束とする。指摘がある正常なレビューはcompletedとして修正へ渡す。
3. 指摘がある場合は、レビューイーが現物と比べて採否を確定する。採用した指摘に必要な成果物修正、変更範囲の検証およびレビュー指摘管理表への証拠記録を完了し、対象worktreeにcommit対象の差分が生じた場合だけcommitする。計画ファイルだけの修正はcommitを要しない。
4. 同じレビュー担当へ、同じ`開始時のHEAD`（CI記録では`修正系列の開始時のHEAD`）、レビュー基準、初回に受領した`review_contract`があればその短い直接契約または検証済みYAMLの絶対パス、およびレビュー指摘管理表を渡して再レビューさせる。計画だけから条項を生成した場合は、初回に読んだ計画を継続する。
5. 未解決指摘が0件になるか、本書のエスカレーション条件に達するまで反復する。

前ラウンドの指摘は解決状態と証拠を伴ってレビュー指摘管理表に残す。再レビューでは`開始時のHEAD`から新しい対象HEADまでの全差分を対象とする。
複数計画の反復では、計画ごとの最後のレビューHEAD・round・表・証拠・返却入力配列を保持する。
`${CLAUDE_PLUGIN_ROOT}/share/exec-review.parent.md`の入力契約に従い、別計画の認可は`review-contract --generate`で現在OIDへ再生成し、変更後の再レビュー対象は`review-impact`で判定する。
受領確認は`exec-review-evidence-check --batch`へ各組をそのまま渡せる。読者別探索の申告も各組の`reader_fit_review`へ保持し、同書の起動条件と省略根拠を確認する。CLIの成功だけで収束とせず、同書の意味判定と未解決0件の条件を満たすことを確かめる。

## ラウンド番号の保持先

レビュー指摘管理表に同じ系統で記録された最大ラウンド番号に従う。初回は1、再レビューは最大値+1とし、値の出所はレビュー指摘管理表の記録に限る。同じラウンドは1つの表の1つの番号で表す。

## 応答済みの判定

レビューイーは`agent-toolkit:review-standards`の`references/reviewee.md`「実行レビュー反復での記録」に従って全指摘への応答を記録する。委譲元は`atk review-table show <表の絶対パス> --format=summary --round <対応したround>`の`unanswered_count`を取得し、0件の場合だけ再レビューへ進む。判定の入力は同じroundのexec-reviewの登録済み行とし、返却文の「対応済み」はその代わりから外す。

## 反復原因の判定

同じ論点が再発した場合は、`agent-toolkit:bugfix`を起動し、`references/root-cause-analysis.md`「反復した指摘の原因判定」で原因を確定する。新しい要件または認可範囲の変更に当たる結果は修正せず、エスカレーションへ送る。

## エスカレーションの事由別の扱い

| 事由 | 委譲元の処置 | 再開位置の記録 |
| --- | --- | --- |
| 計画の条項とWIの明示条件の衝突 | WIの明示条件から契約が一意に定まる場合はWIを優先して確定し、同じレビューイーへ返す。人間由来の要求の解釈が分かれる場合はユーザー確認で確定してから返す | 不要 |
| 選定結果の`担当モデル`とAWI本文のモデル指定の不一致 | AWI本文の記述を確かめ、選定結果の出力先ファイルの当該項目の`担当モデル`を本文の組へ直し、`pick-wi-check`の終了コード0を確かめる。`実装担当`の値が変わった場合は返却したレーン担当のsessionを破棄し、`agent-toolkit:process-wi`の`references/run-lanes.md`の手順で、直した値を`model_type`としてレーン担当を起動し直す。`実行レビュー担当`の値だけが変わった場合は同じthreadへ続行を返す | 不要 |
| 完成条件を外して残りをadoptする判断要請 | 冒頭で、対象の完成条件が後掲の「技術判断で外せる完成条件」に当たるかを判定する。当たる場合は、メインが技術判断で採否を確定し、判断と外す根拠を同じ担当へ返し、計画確定前は計画の実施内容の根拠、実装着手後はレビュー指摘管理表へ記録を求める。前者の形は後掲の「技術判断で外せる完成条件」、後者の形は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`の完成条件を変更・除外する判断の通知の箇条が定める。当たらない場合は、`agent-toolkit:review-standards`の`references/exec-review-recording.md`「統合時の完成条件判定」の失効を受理できる条件に当てはまるか確かめる。否定したユーザー判断（同書「失効の根拠」）がある場合は、否定された要求単位に不採用の根拠が対応するか確かめて同じ担当へ返す。メイン自身の会話に対象の完成条件を否定する発話がある場合は、対象の逐語内容とメインのセッションIDまたはthread ID、必要な時点・文脈を同じ担当へ返す。出所は担当が証拠を使う時に後掲の取得契約で確定し、取得済みの証拠も再利用する。どちらも無い場合は、`agent-toolkit:user-confirmation-and-report`「手段の選択」に従ってユーザー確認する | 必要 |
| ユーザーの選好、要件または認可範囲の変更 | ユーザー確認で回答を得て同じレビューイーへ返す | 不要 |
| 外部状態または権限の不足 | 回復手段を確認し、ユーザー操作が必要ならユーザー確認する | 必要 |
| 同じ論点の2回目以降の差し替え | 指摘と現物を比べて意図と変更範囲を確かめ、なお確定できない場合だけユーザー確認してから修正する。回数だけを確認の条件にしない（`agent-toolkit:review-standards`の`references/reviewee.md`「同じ指摘の反復」） | 必要 |
| 技術的に解消できる実装欠陥 | レビューイーが同じ工程で修正する | 不要 |
| 同じthreadを継続できない | 後続担当へ同じ計画（`~/.claude/plans`内）、レビュー指摘管理表および確定済み判断を渡す | 必要 |

`再開位置の記録`が`必要`の行では計画ファイルを`~/.claude/plans`へ残し、`atk run-script plan-progress --`でその`## 進捗ログ`へ完了工程、続行できない理由および再開位置を書く。キュー項目は変更しない。

完成条件の判断をUWIで待つ場合は、`agent-toolkit:wi-standards`「状態と依存」に従い元AWI全体を保留する。
UWIへ元項目のファイル名と対象の説明、必要な回答と回答で変わる結果を記録し、回答済みUWIの取り込みへ接続する。解除条件と再開工程は計画の進捗ログか引き継ぎ記録へ残す。
回答前は失効を承認して統合へ渡さず、依存しない他項目の作業を続ける。
この保留は前段のキュー項目を変更しない再開記録とは区別する。全要求を不採用にしてrejectする判断も、失効とは別に扱う。

エスカレーションへの回答後は、既存のレビュー指摘管理表とラウンド番号を継続する。同じ表を使い続け、解決済み指摘は解決済みのまま保つ。
担当内で残った表登録、証拠記入と確認の失敗は、同じ担当へ自己修正と続行を求める。未作成の完成条件証拠は担当が生成する出力先として扱い、既存の指摘表や認可資料の不足と区別する。本担当では補えない判断・認可・入力・外部状態の不足だけを、その具体的な不足と再開位置に対応付けてエスカレーションとして扱う。

## 技術判断で外せる完成条件

技術判断で外せる完成条件は、frontmatterに`source`を持つエージェント由来のWIの完成条件のうち、次の全てを満たすものとする。満たさない条件は、ユーザー判断の記録を探し、無ければユーザー確認する。

- 条件が`agent-toolkit:wi-standards`「由来と承認」の明示由来（逐語引用、ユーザーコメント、UWI回答、出所付き対話回答）の要求単位に対応しない
- 外すことが`agent-toolkit/rules/01-agent.md`「協調と自律」のユーザーが確定した判断の変更に当たらない
- 外すかどうかが`agent-toolkit:user-confirmation-and-report`「確認要否の判定」の3のユーザーだけが持つ値（選好、認可、外部の状態、手元に無い資料）に依存しない

境界の判定は条件の意味の判断であり、判断要請を受けたメインと、統合時の完成条件判定で記録を読むメインが行う。エージェント由来であることだけを外す理由にしない。

技術判断の記録先は判断時点で選ぶ。計画確定前は、対象AWIの実施内容の根拠欄へ対象AWI・対象条件・`メインの技術判断`・外す根拠を記録する。初回レビューと統合は同じ計画の記録をそのまま受理する。実装着手後は計画凍結を保ち、上表のとおりレビュー指摘管理表へ記録する。
会話中の判断は、対象発話の逐語内容とメイン自身のセッションIDまたはthread ID、反復を区別する時点・文脈を、その証拠を使う担当へ渡す。メインは出所の抽出を待たずに回答し、担当が証拠を使う時に`session-review-evidence --user-events`で元の出所を確定する。取得済みの出所ファイルとrecord・lineも渡せ、担当は同じ証拠を再利用する。
保存済みの指定組は`atk run-script session-review-evidence -- --user-events-file <元の出力の絶対パス> --user-event-at <record>:<line>`で読む。根拠は元ファイルと元のrecord・lineを使い、照会出力の物理行番号と区別する。失効の根拠の書式とユーザー由来の受理条件は`agent-toolkit:review-standards`の`references/exec-review-recording.md`「失効の根拠」に従う。
