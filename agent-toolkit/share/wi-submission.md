# 独立したWI投入

投入元は確定した要求を`atk wi submit --request-file <JSON>`へ渡す。
投入セッションは保存入力を取得し、`agent-toolkit:wi-standards`の通常の投入手順で意味確認・保存・検収を完遂する。
受付票は永続入力と独立監督への所有移管を示す。
投入済みの判断には要求ごとの結果と報告同期を使う。
公開launcherで準備された共有依存環境のPythonを使い、投入ごとの配布物を保持してから監督へ移管する。
元の製品worktreeや版付きplugin rootを回収しても、監督と実行子は保持したrootと自身のleaseを使う。
保持に失敗した受付は未成立として記録する。

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 独立投入の起動と保存を検収する前 | `../skills/wi-standards/SKILL.md` |

## 入力と受付票

入力はUTF-8のJSON object、または同一対象の要求objectを持つ非空の配列とする。
同時に確定した同一対象の要求は1つの配列で渡し、各要求の識別子と原文・処置を保つ。
配列内の`request_id`は一意、`target_repo`は同じ値とし、全件の入力を検証してから同じロック内で保存する。
これにより新規要求の集合を監督が一度に取得できる。
単一入力の応答はobject、配列入力の応答は要求ごとの同じ形式のobjectを入力順に並べた配列となる。
既存IDの再送は元の作業へ対応付け、過去に別々に受付した要求を再実行してまとめ直すことはしない。
各要求objectに次の項目を全て含め、文字列は空白以外の文字を含む値にする。

| 項目 | 形式・意味 |
| --- | --- |
| `request_id` | 英数字で始まる英数字・`_`・`-`の128文字以内のID |
| `target_repo` | 正規化したリポジトリURL（`github.com/example/repository`の形式） |
| `source` | 投入元の識別子。登録時もこの由来を維持する |
| `origin` | `kind`が`human`または`agent`、`text`が逐語原文であるobject |
| `requirements` | 確定要件の非空文字列配列。1件以上 |
| `observations` | 観測した事象の文字列配列。観測なしは空配列 |
| `evidence` | 証拠本文を含む文字列配列。1件以上 |
| `update_targets` | 更新対象と保留の扱いを明記した文字列配列。新規だけの場合もその旨を1件以上記す |

原文・証拠本文を入力へ直接含める。
親の一時ファイルや撤去するworktreeの所在は、保存入力に含めた原文・証拠本文への補足として使う。
同じIDの同じ入力は同じ受付へ対応し、異なる入力は拒否される。
各要求の同一性はJSON解析後の全項目の値で比較し、objectのキー順・JSONの空白は比較に含めず、その要求内の文字列内容と配列の順序を保持する。

公開応答の`ticket`は`request_id`、`target_repo`、`accepted_at`、`owner`を持つ。
配列入力では各応答の票を確認し、全件の所有移管が成立した場合に限り、投入元の待機集合から全件を外す。
`owner`は監督の`pid`と`create_time`を持つPID世代である。
製品側の待機集合から外す主体は、`atk wi submit --show <request_id>`を同じホストで実行する。
終了0、`ticket_verified: true`、応答の`ticket`と受領済み票の一致を確認した受付だけを待機集合から外す。
非0・票なし・不一致の場合は投入元の待機対象に残し、保存された失敗と次の操作を確認する。
監督の正常終了後も所有移管の記録は有効である。
`atk wi submit --show <request_id>`は票、保存入力、処置、ログを持つ実行ディレクトリと未報告の所在を返す。

## 投入セッション契約

起動と保存の検収の前に、`add-wi.parent.md`を全文読み、専念型の契約を適用する。
run-skillの起動入力にある独立WI受付の`run.json`を読み、`requests`の全件を対象にする。
対象リポジトリのコードを恒久変更する権限は持たない。
元の`source`、`origin`の由来と逐語原文、確定要件、証拠を維持し、既存WIとの意味上の重複を確かめる。
同時に受付済みの同一対象の要求は1回の実行へまとめられる。
`add-wi.parent.md`の起動・入力・受領契約に従い、`add-wi`担当へ`投入経路: 専念型`で渡す。
要求ファイルには各request ID、対象repo・種別、原文と由来、確定要件、技術判断、観測・証拠、更新対象と保留の扱いを分けて記す。
エージェントが確定した事項は`委譲元の判断`へ、人間が明示・承認した要件は`確定した要件`へ対応付ける。
sourceは受付値を保持する。
専念型の担当が独立した投入前レビューと保存まで完遂し、投入元の実行は全要求の結果・保存・保留解除を検収する。
各WIの保存・更新と同じ操作で、frontmatterの`wi_submit_bindings`へ`run_id`をキー、対応する`request_id`配列を値として保存する。
既存WIの他実行の対応は保持する。
保存後・finish前に中断しても、公開showの`saved_wi_bindings`から要求に対応する正式WIを取得できる。
保存応答が不明な要求は、この対応と`atk wi show <ファイル名>`の現行本文を取得し、必要な同期を完了してからfinishへ進む。
`saved_wi_bindings`が元の`requirements`・`update_targets`を満たす範囲を確かめ、保存済みのWIを再利用して残る処置を進める。
要求全体の完了は、対応するWIの本文が要件を全て満たすことから判断する。
この入力は確定契約の引継ぎであり、手動入力向けの協調モードから自律モードへ読み替える。
ユーザー固有の判断が不足する要求は確認UWIを保存し、未完了として保持する。

処置後、次の構造のJSONを作り、`atk wi submit --finish <result-file>`で保存する。
`run_id`には起動入力の同じ実行IDを、`results`には受付の全`request_id`を1回ずつ含める。

```json
{
  "run_id": "0123456789abcdef0123456789abcdef",
  "results": [
    {
      "request_id": "request-1",
      "status": "registered",
      "files": ["20261106-120000-001.md"],
      "reason": "確定要件を新規AWIとして保存した"
    }
  ]
}
```

`status`は`registered`（登録）、`reused`（既存WIの再利用）、`unnecessary`（不要）、`incomplete`（未完了）のいずれかとする。
`reason`に判断根拠を記す。
登録・再利用の`files`には同じ対象リポジトリに実在する正式WIのファイル名を1件以上指定する。
不要の`files`は空配列にできる。
未完了では保存した確認UWIを指定し、技術的に保存できない場合は空配列と理由を残す。
完了済みの処置は保持し、同じ実行の再開では未完了の処置だけを更新できる。

finishの保存後、同じrun IDの作業完了報告を`agent-toolkit:report-completion`で1件だけ同期する。
未完了を含む場合も、今回の処置結果と残る確認UWI・解除条件を同じ実行の報告へ記す。
再開時は公開showの`report_files`で既存報告を取得し、`atk wi edit`で同じ報告を更新する。
報告は`source: run-skill`、`scope: agent-toolkit:wi-standards`、`run_skill_report: true`、自動取得の`run_skill_run_id`で識別する。
保存応答を失った場合も、`report_files`が示す既存報告の同期を再開し、報告を新規登録し直さない。
監督が正式WIの実在、全要求の処置と報告同期を確認して初めて完了となる。

## 失敗・再開・保持

監督は起動前失敗、子の異常終了、timeout、finish欠落、報告未同期を検出する。
排他競合は未実行として最大1時間待ち、解放後に同じ監督が実行する。
可用性判定を含む子実行全体の時間上限は6時間とする。
監督の消失は保存したPID世代をSessionStart・SessionEndと照会時に再観測する。
起動した子の終了を確認し、保存済みWIと同じrun IDの結果を先に照会する。
監督が失敗報告用UWIを1実行1件で同期し、同期できない場合は同じ報告の同期だけを後の契機で再開する。
監督の報告同期はGit呼出全体に120秒の予算を適用し、既存の短いtimeoutを保つ。
時間上限に達した場合も未報告を保存し、次の契機で同じrunの照会・同期へ戻る。

成否不明の要求を新規実行へ無条件に再送しない。
再開を担当するエージェントは、失敗報告UWIを受領した時点で`atk wi submit --show <request_id>`を照会する。
モデル起動前でセッション記録が無い場合は`atk wi submit --resume <request_id>`で同じ受付とrun IDを再移管する。
元の会話がある場合も同操作を使い、監督が既存の`atk run-skill --resume <RUN_ID>`へ接続する。
確認UWIが未回答の要求は回答・解除条件を満たしてから再開する。
元の会話・残時間が不足する場合は、報告UWIを担当するエージェントが未完了要求・保存済みWI・必要な判断を確認UWIへ引き継ぐ。
その回答を得た担当者が、元の受付とWIへの対応を保持して後続処理を起動する。
未完了・未報告の受付は保持する。
完了して報告同期済みの受付・実行ログは、最終更新から30日後の再観測で回収する。
