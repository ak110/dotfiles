# 読者別探索担当の起動と受領

```text
起動対象: reader-fit-review.subagent.md
```

文章成果物を含むレビューにおいて、レビュー担当は本書に従って読者別探索担当を起動し、その結果を受領する。
読者別探索担当の確認観点と返却形式は、`${CLAUDE_PLUGIN_ROOT}/share/reader-fit-review.subagent.md`に定める（所在参照）。

## 名指し参照の読込方法

名指し参照は`read-trigger-contract.md`「名指し参照の読込方法」に従う。

## 起動

初回レビューでは、レビュー開始時点からレビューHEADまでに追加・変更されたすべての`.md`および`.md.tmpl`を対象とする（削除されたファイルは除外し、改名されたファイルは変更後のパスで扱う）。誤字修正や整形のみの差分であっても、内容による選別は行わずにすべて対象に含める。文章の品質に影響する対象の除外や縮小と、検出された問題の対処要否は、`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「QとC・Dの区別」に基づいて判定し、作業費用や所要時間のみを理由とした除外は行わない。
コードコメントの確認は通常のコードレビューで扱う。Git管理外の文章成果物や回答下書きは、新規作成または修正された範囲を入力として起動する。
同一レーンに複数の計画が存在する場合は、当該レビューの`review_contract`内の「別計画の認可」条項に記載された他計画のコミットを除外し、判定対象コミットによって変更された範囲を対象とする。いずれの計画にも属さないコミットも対象に含める。他計画のコミットのみで変更された文書は対象から外し、双方の計画で変更された文書の「修正範囲」には自計画の差分のみを渡す。同一の行を複数の計画が変更した場合は、最終変更コミットの計画に帰属させる。他計画の記述の前提を自計画が変更した場合は、自計画の差分の直接影響範囲として扱う。

起動単位の決定権は本書が保持する。通常のリスクを含め、同一の読者像で確認できる準備済みの文書群は、既存の「成果物」配列とファイルごとに1対1で対応する「比較資料」を用いて集約して起動する。読取量、共通文脈、読者像の違い、および確認品質を考慮して対象集合を分割し、全対象および各読者における独立した判定を維持する。この同一の契約を、初回レビュー、再レビュー、引き継ぎ再レビュー、ならびにGit管理下・管理外の文書および回答下書きへ適用する。対象ごとに比較元、現行本文、完全差分、判定、指摘、証拠を保持し、集約起動の識別子を各ファイルの申告へ対応付ける。再点検の省略可否は、後述する条件に従ってファイル単位で判定する。
起動と終端観測の手順は、`agent-toolkit:delegation`の`references/runtime-routing.md`「実行手段」に従う。
`agents_server`を利用できない環境におけるCodex組み込み機能の代替手順としては、`spawn_agent`に`fork_turns: "none"`を指定して独立した文脈で起動する。
`agents_server`を使用する場合は、以下の引数を指定して`start`を呼び出す。

| 引数 | 値 |
| --- | --- |
| `cwd` | 検証対象とする作業ツリーの絶対パス（保存された本文であっても参照先を判定する対象の版） |
| `subagent_md_path` | `reader-fit-review` |
| `extra_params` | 次に示す名前付きパラメーターのみ |
| `model_type` | 実行レビュー担当が対象WIから`担当モデル.実行レビュー担当`を受け取っている場合はその値（比較と記録は`agent-toolkit:delegation`の`references/runtime-routing.md`「工程別モデル設定」の担当モデルの段落に従う）。受け取っていない場合は省略する |

- `成果物`: 成果物の単一の絶対パス、または空でない絶対パスのJSON配列を指定する。成果物がWIである場合、担当自身がそのファイル名を指定して`atk wi show --skip-pull <ファイル名>`を実行し、リモートと同期せずに取得できる。特定の版を固定する必要がある成果物は、委譲元が保存した本文の絶対パスを渡す
- `種別`: 成果物の種別を指定する
- `読者像`: その成果物を読む主体と、その主体が前提として把握している事柄を指定する
- `修正範囲`: 比較元と現行版の識別子（Git管理下のファイルはOID、Git管理外のファイルは旧本文の複製と現行本文の絶対パス）、および変更された識別子や契約の直接影響範囲を指定する。新規作成された文書や回答の場合は、新規である旨と全文を差分として示す。`atk`でのみ取得可能な本文のうち版を固定する必要があるものは、委譲元が`atk wi show`などで取得したうえで、自身のセッションのmanaged-tempへ保存して渡す
- `比較資料`: Git管理下の成果物の場合は`{"repository":"/repo","base":"<比較元OID>","head":"<レビューHEAD>","paths":["文書.md"]}`を渡す。`paths`には全成果物のリポジトリ相対パスを設定する。担当は同一OIDの本文と差分を`git show`や`git diff`で読み込む。起動側は、全成果物の集合と対象HEADの本文が現行本文と一致することを起動前に確認する。計画別の判定範囲が存在する場合は、同一オブジェクトに「判定範囲差分」を追加し、`paths`の各パスに対して判定範囲の差分のみを保存したファイルの絶対パスをマッピングする。Git管理外の文書や回答下書きの場合は、`{"比較元本文":"/保存先/before.md","今回差分":"/保存先/change.patch","現行本文":"/成果物.md"}`、または同一の3項目を持つオブジェクト配列を渡す。複数の成果物を扱う場合は配列を渡し、各成果物に対して現行本文が1対1で対応するように設定する（項目の欠落、余剰、重複がある指定は拒否される）。3項目には読み取り可能なUTF-8形式の通常ファイルの絶対パスを指定し、現行本文は「成果物」と同一のパスとする。今回差分には比較元本文と現行本文の間の完全な差分を指定し、起動側は比較元本文へ差分を適用した結果が現行本文と一致しない資料を拒否する。初回レビューの新規成果物に限り、`{"比較元本文":"新規","今回差分":"全文","現行本文":"/成果物.md"}`の指定を許可する。再レビューおよび引き継ぎ再レビューにおける比較元には、前回確認時の版（Git管理下では前回レビュー時のHEAD、Git管理外では前回の本文複製）を指定する

集約起動を行う場合は、「修正範囲」にもファイルごとの比較元、現行本文、今回差分を対応付けたうえで全対象を渡す。
成果物、および成果物が参照する実装・文書・CLIの存在と挙動は、受け取った絶対パスと対象の作業ツリーまたは保存された版に基づいて判定する。
担当自身が使用するスキルや実行基盤（agent-toolkitの配布物）の配置場所は対象版の判定対象外とし、そこでの不在を対象版における不在の根拠としては扱わない。

Git管理下の対象ファイルは、`git diff --name-only --diff-filter=d <今回の開始時点> <レビュー対象HEAD> -- '*.md' '*.md.tmpl'`によって特定する。起動前に、レビュー対象HEADをチェックアウトした作業ツリーにおいて、各対象の本文がHEADと一致していること（`git diff --quiet <レビュー対象HEAD> -- <パス>`の終了コードが0であること）を確認する。`review_contract`に判定対象外のコミットが含まれている場合は、パスごとに自計画の判定対象コミットについて`git show --format= <commit> -- <パス>`を実行した結果を順次保存し、「判定範囲差分」とする。判定範囲内の差分が空であるファイル（計画外の変更のみを含むファイル）であっても、省略条件を満たさない限り起動対象とする。読者別探索の申告には`paths`に設定したリポジトリ相対パスを使用する。
起動側は指定形式と保存された資料の可読性、複数成果物の対応、完全差分の適用結果を確認し、不足や参照不可がある場合は入力の補完と`start`の再発行を案内する。保存資料を受け取る担当は本文、差分、判定範囲および未解決事項の意味上の対応を読む。起動側が保証した形式、読取可能性、完全差分の適用結果を担当ごとに再計算させない。Git識別子だけを渡す経路では、担当による指定版の本文と差分の取得を維持する。

再レビューでは、前回および今回の各開始時点からそれぞれのレビューHEADまでのファイル単位の差分を、各`review_contract`の判定範囲に基づいて比較する。
差分と契約境界の双方が完全に一致するファイルに限り、「再点検対象なし」として再起動を省略できる。
前回契約が存在しない旧形式の入力では従来の比較方式を適用し、契約境界が変化した箇所は再点検を実施する。
rebaseによって開始時点が変更された場合も双方の差分を比較し、空白の変更を含むファイルは起動対象とする。再点検の対象が存在する読者に対しては、以下の項目も追加で渡す。

- `レビュー種別`: `再レビュー`
- `修正範囲`: 前回確認時の版（Git管理下では前回レビューしたコミット、Git管理外では自身のセッションのmanaged-tempへ複製した前回の本文）と現行版との比較に更新し、前回の未走査範囲や証拠不足だった範囲も含めて明示する。Git管理下の場合は「比較資料」の`base`を前回レビューしたコミットに変更する
- `未解決事項`: 当該読者に関連する前回の指摘箇所、違反した規定、発生条件、根本原因、要求した検収手段、前回指摘への応答（採否と不採用理由、範囲外とした場合の割り当て先）、検証証拠を記載したファイルの絶対パスを指定する。コマンド実行によって得られた証拠は、出力を自身のセッションのmanaged-tempへ保存して渡す。複数のファイルがある場合は絶対パスのJSON配列とし、説明内容は保存ファイル内に記述してパラメーターにはパスのみを設定する（パスと説明文を連結した値は起動前に拒否される）。該当項目がない場合は`なし`を指定する

行数は読み込みを担当する側が実体から取得する。入力パラメーターや比較元の情報が不足している場合は、補完したうえで起動する。
実行レビューの返却時には、ファイルごとに起動結果の識別子配列、または再点検の省略をJSON形式で申告する。
識別子としては、`agents_server`の`session_id`（UUID）を受け付ける。またClaude Codeの`Agent`ツールのエージェントID（16進文字列や`agent-`接頭辞付き16進文字列）、Codexの組み込み委譲`spawn_agent`が返す`task_name`（`/root/<名前>`形式のエージェントパス）も受け付ける。組み込み委譲で起動した場合は、返却された`task_name`をそのまま申告する。集約起動した場合は、対象となる各ファイルに同一の起動結果識別子を記録する。
申告の形式と対象集合は実行レビュー担当の返却契約で規定する。Git差分の対象集合は、今回の開始時点からレビューHEADまでの変更差分に含まれる`.md`および`.md.tmpl`から、`review_contract`の判定対象外コミットのみで変更されたファイルを除外した集合とする。
Git管理外の対象集合は、回答下書きの絶対パス、ならびに「Git管理外の変更」の元ファイルのうち`.md`・`.md.tmpl`であるものの絶対パスとする。申告内の`external`には、対象集合の絶対パスごとに`{"sessions":["<起動結果の識別子>"]}`または`{"omission":"再点検対象なし","previous":"/前回本文の複製.md"}`を格納したオブジェクトを設定する。後者は第2ラウンド以降において、前回本文の複製と現行本文のバイト列が完全に一致する場合にのみ使用できる。対象集合や申告内容に不足や過剰がある場合は、委譲元の受領確認において差し戻しの対象となる。「文章成果物なし」の申告は、Git差分の対象集合とGit管理外の対象集合がともに空である場合にのみ許可する。

## 受領

レビュー結果は、選択した起動手段の終端観測によって受け取り、読者ごとに終端ステータスと返却本文の内容を確認する。
`agents_server`を利用する場合は、引数なしの`atk agents wait`を実行する。
`Agent`ツールの起動と終端観測は、`agent-toolkit:delegation`の`references/runtime-routing.md`「実行手段」に従う。
一部の資料不足、実行失敗、または本文の欠落が生じた場合は、該当する対象および読者の結果を「未取得」として扱い、起動手段が提示する後続操作と本書の回復手順に従って同一読者の結果を再回収する。
回復手順を実施しても結果が揃わない場合は、欠落している読者と再開に必要な事項を「続行できない理由」に明記したうえで工程を中断する。
起動前に再点検不要と判定した読者は、欠落の対象外として扱う。
入力の不足や資料の対応不備によって中断した探索は、資料を補完したうえで同一読者の探索を再起動する。確認範囲を確定できなかった探索結果は、今回の完了判定には利用しない。資料を補完できない場合は、必要な資料とその理由を「続行できない理由」に記録して委譲元へ返却する。前回の探索結果と現行差分を直接目視で確認したのみでは、今回の独立した探索の完了とはみなさない。再点検の省略は前述したファイル別差分の一致のみに基づいて判定し、資料の不足を省略の理由に含めない。

各指摘の裏付けは、成果物の本文および適用対象の契約と照らし合わせて確認し、採否、採否の根拠、採用分の記録先、または不採用理由（同一原因の既存指摘へ統合する場合は統合先）を自身のレビュー記録へ残す。`未解決の指摘数: 0`という返却内容についても、対応付ける指摘が存在しない事実を明記する。
指摘の採否は、指摘が根拠とする作成規範の条文に本文が反しているか、あるいは読者像の観点から本文のみを根拠として行為者・対象・条件・結果を一意に読み取れず、判断・操作・検証を誤るか中断せざるを得ないかによって判定する。文章成果物の実害判定は、`agent-toolkit:review-standards`の両役割に共通する規定に従う。計画やWIの完成条件を満たしていること、機能的な実害がないこと、または説明の追加のみを求める指摘であることを、不採用の根拠にしない。説明の追加が必要であるかの判定は、`agent-basics:writing-standards`の`references/writing.md`「文章の共通規定」における情報を追加する前の判定基準に従う。作成規範への違反は既存要件に対する指摘として扱う。不採用理由を記録する際は、指摘ごとに「条文への非該当」「範囲外」「事実誤認」のいずれであるかを特定し、その根拠を記録する。
未解決件数として計上する対象は、差分および直接影響範囲に存在する既存要件への指摘に限定する。範囲外の既存不良は想定外の事象として扱い、新規要件はその旨を明記し、再レビュー時に検出された初回レビューの確認不足は通常の指摘と区別したうえで、それぞれ委譲元へ伝達する。
