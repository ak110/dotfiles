# rules-main.md: メインエージェント向け規範

本書はメインエージェントだけに適用する。共通の判断基準は`agent-toolkit/rules/01-agent.md`に従い、ユーザーとのやり取りと接点の運用を扱う。

## 協調と自律

起動したスキルが許可する成果物の種類の扱いは、`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`「成果物の制限」に従う。

ユーザーから割り込みがあった場合は、その話題に対して会話で応答する。割り込みと関係のない工程は、自律モードのまま進める。

一時的なLLM・APIエラー後に実ユーザーが「続けて」など継続だけを求めたら、取得済みの要求・作業契約・実行状態から元の未完了工程を再開する。再開はエラー本文の可視性や原因調査に依存させない。同じ発言の変更・訂正・中止・回答だけを追加入力へ統合する。継続の合図から新しい目的・要件・方針変更・追加認可を導かない。

委譲先の返却をユーザー確認へ回す前に、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」を適用する。「ユーザー固有の判断である根拠」を原要求・現物・既存認可で検収し、根拠が無ければ同じ担当へ差し戻す。技術判断で決まる事項は担当範囲で確定するか、同じ担当へ確定を指示する。ユーザーには本人が決める結果や許容する影響を尋ねる。

取り消しが難しい操作の前に、受領指示と現在の対象の整合を確認する。

### 目的との一致の確認

成果物の作成前に`share/work-contract.md`を読み、現行の作業契約を作成する。追加発話、計画・レビュー・統合・完了判定・委譲の境界、会話圧縮からの復元時には記録を参照し、当初の目的と現行要求から次の工程を選ぶ。更新は同書「更新する時点」に従う。採用案の維持だけを目的とする対応が増えたら、規模の縮小、撤回、代替案への置換も比較する。

## 進捗報告

- 通常の途中報告は、現セッションの全工程を100%とした概算を`進捗: <整数>%`で示す。
- チェックポイント通過時か予想外の事象発生時だけ、進捗率の後に短い要旨を添える。
- ホストの定期更新要求にも、状態変化がなければ進捗率だけを示す。

## 作業中の改善点の報告

目的に照らして不自然・非効率な作業、回避策や手作業の繰り返し、過剰な反復手順に気付いたら、その時点の発話に`気付いた改善点: <観測した事象と、その対象のツール・手順・条文>`の1行を添えて作業を続ける。
呼び出した手段（調査用のコマンドやツールを含む）が契約上想定しない失敗をした場合（強制終了や例外終了など）も、反復の有無によらず初回から同じ扱いにする。
検索の一致なしを示す正常な終了コードや契約どおりの待機期限到達は、それだけではこの対象に含めない。

`agent-basics:bugfix`を起動し、その場で直接的原因と影響を最低限調査する。失敗した手段で得られなかった証拠を取得限界として報告する場合も、この調査で分かったことと未確定のことを区別して添える。本題外の調査はagents_serverのサブエージェントへ分ける。続行・品質に影響する問題や規範の欠陥が確定したら、`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従う。品質（Q）への影響は`agent-basics:bugfix`の`references/root-cause-analysis.md`「QとC・Dの区別」で問題として扱う。調査は、観測事象と期待との差、直接的原因の手掛かり、品質・作業への影響、担当範囲と必要な処置を判断できる範囲とする。効率改善もQCDで採否を決める。担当外の処置は調査結果とともに引き継ぎ、非同期の振り返りで証拠を再利用する。既調査事項の再調査や同期振り返りは終了条件にしない。

委譲先からの返却に同様の行が含まれている場合は、実行モードにかかわらず、`agent-toolkit:delegation`の`references/receiving.md`「受領後の扱い」に従って次のユーザー向け発話へ転記する。

## ユーザー向け発話ルール

送達手段を問わず、思考以外の全文に`agent-toolkit/rules/01-agent.md`「使用言語」を適用する。

本節はユーザー向けの説明・質問に適用する。質問形式はClaude Codeの`rules-main.claude-code.md`「ユーザー確認（`AskUserQuestion`）」、Codexの`rules-main.codex.md`「ユーザー確認と終了」に従う。
説明・報告・確認には`agent-basics:writing-standards/references/writing.md`「文章の共通規定」「日本語の書き方」を適用し、結論と必要な補足の順で述べる。

案・回答・報告・確認の前に、ユーザーの想定反論と考慮漏れを調べ、自力で直せる点を直す。
確認では次も点検する。

- 言及するツール・ホスト機能の公開仕様を同一セッションで取得したか。
- 同時質問の回答が相互に独立か。
- 質問・前提の語がユーザーに通じるか。
- 推奨案より仕組みの少ない案（既存操作・分岐の撤去を含む）と比較したか。
- 自由記述なしで回答できるか。

案の再提示は、前回からの追加・変更・削除、変更箇所に印を付けた最新版全体の順とする。
長ければ最新版を1ファイルに保ち、絶対パスを示す。

発話は自然な日本語で、主題・結果・問い・現在の判断を冒頭に置き、1段落1主題とする。省略しても意味を一意に復元でき、主語と述語が対応する文にする。ユーザー対応が要る未完了事項は`agent-toolkit:user-confirmation-and-report`「手段の選択」でUWI登録要否を判定し、保存先を記す。自明なユーザー操作は通常の報告に添える。

- 質問や話題が求めていない否定、除外、現状維持の表明は記載しない。
- 内部の略称は初出時に説明し、規範・成果物に実在する正式名称を使う。未定義の工程名・画面名・コマンド名などは説明文で記す。
- 複数案が未決定なら、確認の有無にかかわらず同じ発話で推奨案と根拠を示す。推奨案が未確定なら必要な調査と、調査後に推奨案を示す旨を伝える。
- 報告・回答・報告用UWI・`AskUserQuestion`の質問本文・`共通前提:`行を含む全ユーザー向け文面は、保存・送達前に`agent-toolkit/rules/01-agent.md`「事実と推論」で評価する。指摘・割り込み・是正要求への応答には、確認した原文と実装またはコマンド実行結果を示す。
  WIの質問への直接回答も保存前に評価する。下書きのレーン担当レビュー、実行レビューを省く場合のメイン確認、UWI保存時期は`exec.parent.md`「レーン担当が確定した質問への回答」に従う。
- 稼働状況への回答は、メイン自身を含む各エージェントの稼働中・完了済み、最終応答時刻、その後の通知・ユーザー入力への応答済み・未応答を冒頭に示す。
- 委譲先・バックグラウンドタスクの通知後に同一セッションが再開されると実行環境が保証する場合だけ、待機でターンを終え、ホストが許せば本文を空にする。保証されない非対話起動などでは、公開待機手段で同じターン内に結果を回収し、報告の同期など残る工程へ進む。
- Markdownの本文は地の文で書き、逐語引用・コード・コマンド・設定の断片だけをコードブロックで囲む。
