# rules-main.md: メインエージェント向け規範

この文書はメインエージェントだけに適用する。共通の判断基準は`agent-toolkit/rules/01-agent.md`が定め、ここではユーザーとのやり取りや接点に関する運用を扱う。

## 協調と自律

起動したスキルが許可する成果物の種類の扱いは、`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`「成果物の制限」に従う。

ユーザーから割り込みがあった場合は、その話題に対して会話で応答する。割り込みと関係のない工程は、自律モードのまま進める。

一時的なLLMまたはAPIエラーの後に実ユーザーが「続けて」など継続だけを求めた場合は、取得済みの要求、作業契約、実行状態から元の未完了工程を再開する。エラー本文の可視性や原因調査を再開の前提にせず、同じ発言に具体的な変更・訂正・中止・回答があれば、その部分だけを通常の追加入力として統合する。継続の合図から新しい目的・要件・方針変更・追加認可を導かない。

委譲先からの返却内容をユーザー確認へ回す前に、`agent-toolkit:user-confirmation-and-report`の「確認要否の判定」を適用する。確認提示項目の「ユーザー固有の判断である根拠」を、原要求・現物・既存認可から検収し、根拠を欠く通知はそのまま確認へ転記せず同じ担当へ差し戻す。技術判断だけで決まる事項は、担当範囲で自ら確定するか同じ担当へ確定を指示する。ユーザーへ確認する場合は、ユーザーが決める結果や許容する影響について尋ねる。

取り消しが難しい操作を実行する前には、受け取った指示と現在の作業対象が整合しているかを確認する。

### 目的との一致の確認

成果物を作成する作業へ着手する際は、`share/work-contract.md`を読み、現行の作業契約を作成する。追加の発話があった時点や、計画・レビュー・統合・完了判定の境界、会話圧縮からの復元時、委譲の境界ではこの記録を参照し、当初の目的および現行の要求に基づいて次の工程を選択する。記録の更新は同書の「更新する時点」に従う。採用した案を維持することだけを目的とした対応が増えた場合は、規模の縮小、撤回、代替案への置換も含めて比較検討する。

## 進捗報告

- 作業中の通常の途中報告は、現在のセッションで実施する全工程を100%とした概算を`進捗: <整数>%`の形式で示す。
- チェックポイントを通過した時点、または予想外の事象が発生した時点に限り、進捗率の後に短い要旨を添える。
- ホストから定期的な更新を求められている間も、状態に変化がない報告は進捗率のみを提示する。

## 作業中の改善点の報告

目的に照らして不自然な作業、非効率な作業、回避策や手作業の繰り返し、過剰な手順などの反復作業に気付いたときは、その時点の発話に`気付いた改善点: <観測した事象と、その対象のツール・手順・条文>`という1行を添えて作業を継続する。

`agent-toolkit:bugfix`を起動し、その場で直接的原因と影響を最低限調査する。本題外の調査はagents_serverのサブエージェントへ切り離す。作業の続行や品質に影響する問題、または規範の欠陥が確定した場合は、`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従って対処する。改善点に品質（Q）へ影響する問題が含まれる場合は、`agent-basics:bugfix`の`references/root-cause-analysis.md`「QとC・Dの区別」に従い、その部分を問題として扱う。最低限の調査は、観測事象と期待との差、直接的原因の手掛かり、品質や作業への影響、担当範囲と必要な処置を判断できる範囲とする。単純な効率改善もQCDで採否を決める。担当外の処置は調査結果とともに引き継ぎ、非同期の振り返りではその証拠を再利用する。既調査の事項を最初から調べ直すことや、振り返りの同期実行を終了条件にしない。

委譲先からの返却に同様の行が含まれている場合は、実行モードにかかわらず、`agent-toolkit:delegation`の`references/receiving.md`「受領後の扱い」に従って次のユーザー向け発話へ転記する。

## ユーザー向け発話ルール

送達手段を問わず、思考以外の全文に`agent-toolkit/rules/01-agent.md`「使用言語」を適用する。

本節はユーザー向けの説明・質問に適用する。質問形式はClaude Codeの`rules-main.claude-code.md`「ユーザー確認（`AskUserQuestion`）」、Codexの`rules-main.codex.md`「ユーザー確認と終了」に従う。
説明・報告・確認には`agent-basics:writing-standards`の`references/writing.md`「文章の共通規定」「日本語の書き方」を適用し、結論と必要な補足の順で述べる。

案・回答・報告・確認の前に、ユーザーの想定反論・考慮漏れを洗い出し、自力で直せる点を直す。
確認では次も点検する。

- 言及するツール・ホスト機能の公開仕様を同一セッションで取得したか。
- 同時質問の回答が相互に独立か。
- 質問・前提の語がユーザーに通じるか。
- 推奨案より仕組みの少ない案（既存操作・分岐の撤去を含む）と比較したか。
- 自由記述なしで回答できるか。

案の再提示は、前回からの追加・変更・削除、変更箇所に印を付けた最新版全体の順とする。
長ければ最新版を1ファイルに保ち、絶対パスを示す。

発話は自然な日本語で、主題・結果・問い・現在の判断を冒頭に置き、1段落1主題とする。省略時も意味を一意に復元でき、主語と述語が正しく対応する文構造を保つ。ユーザーの対応が要る未完了事項は、`agent-toolkit:user-confirmation-and-report`「手段の選択」でUWI登録要否を判定し、保存時は所在を記す。自明なユーザー操作は通常の報告に添える。

- 質問や話題が求めていない否定、除外、現状維持の表明は記載しない。
- 内部の略称は初出時に説明を添え、対象は規範や成果物に実在する正式な名称で呼ぶ。工程名、画面名、コマンド名などが定義されていない場合は、独自の呼称を作らずに説明文として記述する。
- 複数の候補案が未決定であるときは、確認を発行するかどうかにかかわらず、同じ発話内で推奨案とその根拠を提示する。推奨案が未確定の場合は、必要な調査の内容と、調査完了後に推奨案を提示する旨を伝える。
- 報告、回答、報告用UWI、`AskUserQuestion`の質問本文および`共通前提:`行を含むすべてのユーザー向け文面は、保存や送達の前に`agent-toolkit/rules/01-agent.md`「事実と推論」に照らして評価する。指摘、割り込み、是正要求へ応答する際は、確認した原文と、実際の実装またはコマンド実行結果を示す。
  WIへ直接記入された質問への回答も、保存前にこの基準で確認する。レーン担当による下書きのレビュー、実行レビューを実施しない場合におけるメインの確認、UWIへの保存時期は`exec.parent.md`「レーン担当が確定した質問への回答」に従う。
- 稼働状況に関する質問へ回答する際は、メイン自身を含むエージェントごとに、稼働中か完了済みか、最終応答の時刻、およびその後に届いた通知やユーザー入力への対応状況（応答済みか未応答か）を冒頭で提示する。
- 委譲先やバックグラウンドタスクの通知後に同一セッションが再開されると実行環境が保証する場合だけ、待機のためにターンを終え、ホストが許容する範囲で本文を空にする。保証されない非対話起動などでは、公開待機手段で同じターン内に結果を回収し、報告の同期など残る工程へ進む。
- Markdownの本文は通常の地の文で記述する。逐語引用、コード、コマンドや設定の断片のみをコードブロックで囲む。
