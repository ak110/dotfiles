# 計画ファイルレビュータスク

## 入力

本節を総合レビュー系へ渡す資料契約の正本とする。

- `plan-review-delegation.md`、`plan-codex-review.md`、本ファイル、正規計画の絶対パスを受け取り、着手時に全文を読む
- 適用する品質規範はスキル名で受け取り、各スキルのトリガー規則に従って着手時に全文を読む
- `agent-toolkit:plan-mode`のSKILL.mdとプロジェクト規範の絶対パスを受け取り、着手時に全文を読む
- 対象リポジトリの絶対パス、初回または限定再レビューの別、限定再レビュー時の差分一式を受け取る
- 入力が欠ける場合は欠落項目を返し、推測で補わない

## レビュー

- 着手時に正規計画全文とレビューに必要な対象ファイルを直接読む
- 計画内部の整合性、実装可能性、現行実装との一致、規範適合を点検する
- 初回レビューでは計画全体を点検し、指摘候補を初版内補正、スコープ拡大、独立問題へ区分する
- スコープ拡大は、計画した変更から不具合へ至る実行結果または静的な呼び出し・参照経路を根拠として示す
- 独立問題は、初版の成立性へ影響しないことを確認して指摘候補から除外する
- バグ計画の分類には、`## 背景`直下にある`### 計画メタ情報`の固定値`作業種別`だけを用いる。
  作業種別が欠落・未知値・複数値の場合は分類契約の不成立として指摘する。
  タイトル、依頼内容、背景、提示素材の自然言語から分類を推測しない
- 作業種別が単一の`バグ対応`の場合だけ、受領した`plan-mode/SKILL.md`から
  `skills/bugfix/references/root-cause-analysis.md`を解決して全文を読む。
  名前付きの全`### バグ調査結果: <事象名>`について、
  事象名、親H2、重複、必須14行、原因区分、類似見直し、3処置を点検する。
  提示素材に現れる利用者可視の各バグがいずれかの表へ対応することを確認し、
  機械検査では判定できない表の抜けを指摘する
- 同じ根本原因でも直接的原因または是正処置の変更単位が異なる事象が別表になり、
  直接的原因と是正処置の変更単位がともに同じ事象だけが統合されていることを点検する
- 根本原因が直接的原因の言い換えに留まる場合、類似母集団が識別子やコード形状だけで定義される場合、
  再発防止処置が是正テストだけで同じ原因の混入や見逃しを防がない場合は指摘する
- 提示素材と`### ユーザー合意済み事項`を、`### 実施内容`、`## 変更内容`、`### エージェント判断`へ突合する。
  計画が用いる分類名にかかわらず、明示された外部可視のコマンド、引数、操作順序、入出力、
  公開インターフェースの変更を検出し、
  変更がある場合はユーザー合意の根拠を要求する
- 計画が新たに追加する拒否条件、受理する入力値の縮小、容量・件数制限、ネットワーク遮断、権限強化、
  既存コマンドや導入済み機能の利用不可化を列挙する
- 各制約について、現行実装で成功する利用シナリオを確認する
- 成功経路を失う場合は、公開契約変更として扱い、ユーザー合意の根拠を要求する
- 再レビューでは前回の採用指摘、反映結果、反映差分を点検する
- 再レビューの新規指摘は、反映差分との因果関係と再現根拠を示す
- 認証・認可に関する主張は、共通ミドルウェアまたは認証フックから
  ルーターやコントローラーを経て最終ハンドラーまでの実行経路を追跡する。
  局所実装だけを根拠に公開契約を確定しない
- 非Webアプリケーションでは、共通の認証・認可入口から
  コマンドまたはイベントのディスパッチを経て最終処理までを同じ観点で追跡する
- 応答フィールドに関する主張は、内部オブジェクトの生成箇所から
  シリアライズやフィルターを経て利用者が観測できる値まで追跡する
- 正規計画と対象リポジトリを読み取り専用として扱い、変更しない
- 共有作業ツリーの変化だけを理由にレビュー結果を破棄または再実行しない
- 外部ツールまたは外部実行系の挙動を根拠とする指摘は、実行したコマンド、主要な環境条件、
  終了コード、標準出力、標準エラーを根拠へ含める
- 裏付けられない主張は`未検証`と明記して指摘候補から除外する
- 指摘ごとに重大度、対象箇所、根拠、修正方針を示す

## 出力

- 重大度は`重大`または`中程度`から選ぶ
- 指摘がある場合は、重大度、区分、対象箇所、根拠、修正方針を全件返す
- 指摘がない場合は「指摘なし」と明記する
- 指摘ごとに裏付けへ用いた実行結果、公式資料の該当記述、実装箇所のいずれかを示す
- 裏付けられない指摘候補は`未検証`として指摘とは分けて記載する
- 正規計画と対象リポジトリを変更していないことを`write_status: unchanged`として記載する
- 外部実行を保持した場合は`external_execution`へ所有主体、安定した実行識別子、開始時刻、
  直近の生存確認時刻と結果を記載する。保持しなかった場合は`not_applicable`とする
