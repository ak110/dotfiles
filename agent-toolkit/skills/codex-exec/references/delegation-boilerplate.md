# 委譲プロンプトと受領の共通契約

`agent-toolkit:codex-exec`を利用する送信側が、用途別referenceと重複させずに
委譲プロンプトを構成し、完了報告を受領するための共通契約を定める。

## 共通入力

送信側は用途別の実行手順referenceとtask referenceを1件ずつ選ぶ。
受信側task referenceの`## 入力`が要求する資料を絶対パスで渡す。
起動文は作業ディレクトリ、対象、完了条件、実行時に確定した値、呼び出し元が許可した追加指示だけで構成する。
恒常的な手順、品質規範本文、task referenceが列挙する資料を起動文へ転記しない。

作業ディレクトリは受領した絶対パスをそのまま使う。
委譲先は`git rev-parse --show-toplevel`やホームディレクトリから作業ディレクトリを再解決しない。
作業用複製では複製元の絶対パスまたは`対象外`も明示する。

## codex委譲

初回は用途別の系統へ新しい`threadId`を割り当て、継続時は同じ系統の`threadId`だけを使う。
計画レビュー系、計画準拠実装レビュー系、独立実装レビュー系、実装・修正系の履歴を混在させない。
同じ`threadId`へは先行応答を受領してから次の指示を送る。
応答の`threadId`と本文を保持し、実行結果に基づくrouteを1回だけ記録する。

## 汎用Agent委譲

codex MCPを解決できない場合または利用上限を応答で確認した場合だけ、
専用定義を持たない汎用Agentへ切り替える。
初回起動は`name`と`run_in_background`を省略し、実際の受領経路を起動結果から判定する。
設計判断や重大指摘の採否を含む作業はOpusを使う。
確定済みの実装や機械修正にはSonnetを使う。

Agent識別子は直接起動した主体が所有する。
稼働中の同じAgentへ追加指示を送る場合だけ`SendMessage`を使う。
完了済みAgentへ追加作業を依頼し、完了通知だけが受領経路になる場合は、
前回応答全文と未完了事項を渡して新規起動する。
`completion.md`またはセッションJSONLなど、再開後の完了を確実に照会できる記録がある場合だけ、
完了済みの同じAgentを再開できる。

## 完了報告の受領と継続

通常のツール戻り値または完了通知を第一の受領経路とする。
通常配送でtask referenceの必須欄を含む完了報告を受領した場合は、記録ファイルの生成を要求しない。
配送不能を実測した場合だけ、`completion.md`や確実に照会できるセッション記録を使う。

受領した完了報告はtask referenceの必須欄、成果物実体、route、thread、Agent識別子、
作業ディレクトリの非変更条件と照合する。
待機表明だけの応答、必須欄不足、実体との不一致は未完遂として扱う。
同じ系統へ継続する場合は、未完了事項と新しい判断材料だけを送り、完了済み工程を再送しない。

記録経路を使った場合は、記録を生成した主体の終端と内容検収を確認した後に、
当該試行用の管理対象一時ディレクトリだけをcleanupする。
記録失敗または書き込み主体の生存が未確定の場合はcleanupせず、絶対パスを未解決事項へ含める。
