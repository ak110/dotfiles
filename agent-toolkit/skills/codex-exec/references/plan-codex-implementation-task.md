# 計画実装タスク

## 入力

- `plan-codex-implementation.md`、`plan-codex-implementation-task.md`、
  `plan-codex-implementation-review.md`の絶対パスを受け取り、着手時に各ファイルの全文を読む
- 計画ファイル、品質規範、プロジェクト規範の絶対パスを受け取り、
  着手時に各ファイルの全文を読む
- 作業ディレクトリの絶対パスは、対象リポジトリを実装する基点として使う
- 入力が欠ける場合は欠落項目を返し、推測で補わない
- レビュー指摘修正では`review_findings`として、`P-*`または`I-*`の指摘ID、
  指摘原文、重大度、観点を受け取る。箇所と再現根拠も受け取り、区分欄は未判定の空欄とする

## レビュー指摘の妥当性検討

レビュー指摘の妥当性は本系統が検討し、採否と根拠を`review_resolution`へ記載する。
委譲窓口は採否を判断せず、本系統が返した結果を検収する。

- 採用を確定する前に、指摘が挙げる事実を実測で確認する。
  確認手段は対象コマンドの実行、公式仕様の該当記述、既存実装と履歴の調査とする
- 指摘が計画の確定事項、計画が転記する要求元の原文、ユーザーの明示指示と
  衝突しないかを確認する。衝突する場合は不採用とし、衝突する箇所を根拠へ記す
- 指摘が実行環境の前提（OS・ランタイムの版・外部ツールの要求仕様）に依存し、
  かつ根拠が文書上の整合のみで実行環境の要求仕様に触れていない場合は、
  採用の確定前に対象環境での成立を確認する。
  確認できない場合は既存実装の前提を維持し、指摘が挙げる懸念に対処する形へ修正方針を組み替える
- 実測で確認できない主張を含む指摘は、確認できなかった範囲を根拠へ明示して不採用とする
- 採用する指摘へ`plan-codex-implementation-review.md`「初回レビュー」節が定める区分
  （計画対応・独立提案）を割り当て、根拠を`review_resolution`へ記す
- 独立提案と判定した指摘のうち、`plan-codex-implementation-review.md`「初回レビュー」節が
  登録対象と定めるものは当該セッションで実装せず、事象、根拠、想定する対応案を含む本文で
  `atk mq add`へ登録し、登録した識別子を`review_resolution`へ記す。
  同節が破棄と定める指摘は登録せず、不採用として`review_resolution`へ残す
- 指摘が例示した箇所を是正する前に、当該指摘が成立する判定軸を言語化し、
  同じ判定軸に該当する箇所を検索または機械照合で洗い出す。
  同一の判定軸による指摘が2ラウンド連続で発生した場合は、目視の個別照合を継続せず、
  機械的な網羅照合手段を用いる

全採用指摘を反映した後は、一括修正による影響を監査する。
個別指摘の再現確認に加えて次を実施してから完了とする。

- 各修正が変更した条件、順序、所有責務、資源のライフサイクルを抽出する
- 抽出した各要素について、同じ原因が及ぶ箇所と、隣接する正常・失敗・取消・再試行の経路を点検する
- 複数の指摘を同一ラウンドで是正した場合は、是正どうしが同じ処理、規定、記述を
  逆方向へ変えていないかを点検する。実装と文書の組み合わせも対象とし、
  一方が仕様を緩め、他方が同じ仕様を厳格化する状態を残さない
- 点検で見つけた欠陥は同じ修正単位で解消し、再検証する
- 点検対象と結果を`review_impact_audit`として出力へ含める

## 実装

- 現行実装と計画の相違を確認し、計画の意図に沿って
  実装、検証、進捗ログ更新、指定されたコミットまで完遂する
- 計画と現行実装が一致しない場合は、採用した判断と根拠を進捗ログへ記録する
- `git push`、タグ作成、リモートref変更は実行しない
- 承認済み計画の`## 実行方法`が対象リポジトリ外への操作と対象を明記する場合は、
  記載された操作と対象範囲に限って実施する。この許可は`git push`、タグ作成、
  リモートref変更に対する既存の禁止を解除しない
- 計画記載の操作への許可とは別に、適用中の規範が義務づける登録操作
  （`plan-codex-implementation-review.md`「初回レビュー」節が登録対象と定める独立提案の
  `atk mq add`登録など）は、計画への記載を要さず実施する
- 対象リポジトリ外の既存内容の削除・改変を伴う操作は、計画記載の操作と規範義務の登録操作の
  いずれの許可にも含めず、当該項目の`result`を`needs_escalation`として呼び出し元の確認へ回す
- 計画記載の操作と規範義務の登録操作を除き、指定された作業ディレクトリ外では、
  受領した計画ファイルの絶対パスだけをファイル全体の書き込み許可先とする
- 計画ファイルの更新内容は`plan-codex-implementation.md`の計画同期規定に従う

## 出力

```text
status: completed | needs_escalation
summary: <結果>
changed:
- <変更内容>
external_operations:
- operation: <実施または実施不可と判定した対象リポジトリ外操作と認可根拠（承認済み計画の`## 実行方法`に
    記載された操作は`計画記載`、規範が義務づける登録操作は`規範義務`）。該当する操作が無い場合は「なし」>
  target: <対象リポジトリ、外部サービス、登録先など。該当する操作が無い場合は「なし」>
  result: completed（実施した） | needs_escalation（実施せず呼び出し元の確認へ回した） | not_applicable（該当する操作が無い）
  evidence: <対象側の識別子、応答、または実物照合に使う値。該当する操作が無い場合は「なし」>
verification:
- <コマンド、終了コード、警告>
- <`git status --short`の生の出力。空の場合も空であることを明示する>
- <`git diff --stat <計画着手前SHA>..<commit_sha>`の生の出力>
commit_sha: <最終コミット。コミット不要時は「なし」>
review_resolution: <レビュー指摘修正時だけ出力する>
| 通番 | 重大度／観点 | 区分 | 箇所 | 内容 | 対応方針 |
| <P-*またはI-*> | ... | 採用（計画対応）・採用（独立提案）・不採用・重複 | ... | ... | 根拠、登録先、重複先、修正・再検証結果 |
review_impact_audit: <点検対象と結果。レビュー指摘修正時だけ出力する>
unplanned:
- <計画外事項。無ければ「なし」>
blockers:
- <未解決事項。無ければ「なし」>
```

`external_operations`のいずれかの`result`が`needs_escalation`の場合は、
全体の`status`も`needs_escalation`とする。
当該項目は`operation`と`target`を含む形で`blockers`へ記載する。
呼び出し元はこの欄で未実施の操作を特定する。
`git status --short`と`git diff --stat`は要約へ置き換えず、生の出力を記載する。
前者は未コミット変更の残存を示し、後者は計画着手前からの変更規模を示す。
