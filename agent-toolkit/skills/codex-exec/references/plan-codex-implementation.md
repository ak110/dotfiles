# 計画の実装と修正

`plan-impl-executor`が計画全体の実装・検証・コミットと、レビュー指摘の修正を
単一の実装・修正系へ委譲し、応答と実体を検収するための手順を定める。

`## 変更内容`に列挙された全項目は、現在のコミット単位に属する分を当該単位の初回実装で完遂する。
段階化ラベルによる先送りや、全単位を先に実装してから部分ステージでコミット境界を再構成する運用は行わない。

## 初回委譲

委譲先へ次の絶対パスを渡し、着手時に全文をReadさせる。

- 本ファイル
- `plan-codex-implementation-task.md`
- `plan-codex-implementation-review.md`（採用指摘へ割り当てる区分の定義元）
- 計画ファイル
- 対象文書に適用する品質スキル
- プロジェクト規範

対象文書種別に対応する品質スキルを必ず含める。
コード・テストコードには`agent-toolkit:coding-standards`を用いる。
Markdownなどの文書には`agent-toolkit:writing-standards`を用いる。
コーディングエージェント向け文書には`agent-toolkit:agent-standards`を用いる。
タスク本文は作業ディレクトリ、対象、完了条件だけに限定し、計画や規範の本文を転記しない。

初回委譲の前に、計画の`## 実行方法`の本文を委譲前スナップショットとして保存する。
実装・修正系はレビュー指摘の採用に伴い計画本文を改訂するため、対象リポジトリ外操作の認可判定を
改訂後の内容で行うと、委譲先が自身で追記した記載により当該操作を自己承認できる。
保存したスナップショットは、レビュー指摘の反映を含む全ラウンドを通じて更新しない。

実装をファイル・言語・工程別の複数担当へ分割しない。
同じ実装・修正系を完了まで継続する。Codex経路は`threadId`を保持する。
Claude代替はAgent識別子を保持し、利用可能な`SendMessage`で同じAgentを再開する。
再開できない場合だけ、同じreference群と前回応答全文を渡して新規起動する。

## 実装順序

1. 計画着手前の`HEAD`を記録し、計画を想定コミット単位へ分解する
2. 現在の単位だけを実装する
3. 応答の受領直後に、応答と作業ツリーを照合する
4. 現在の単位に最も近い範囲を検証する
5. 差分と検証結果を確認し、現在の単位だけをコミットする
6. 未処理の単位があれば手順2へ戻る
7. 全単位の完了後に計画全体を最終検証する

対象ファイル数が5以上の場合は、実装前に対象ファイルごとのコミット履歴を確認する。
並行セッション由来の重複実装を検出した場合は、既存対応との統合結果を計画本文へ反映してから続行する。

計画は作成時点の実装を基にしている。着手時の実装と計画が一致しない場合は、
計画の記述を機械的に適用せず、計画の意図と現行実装を照合して妥当な実装を選ぶ。
判断内容と根拠は計画の`## 進捗ログ`と完了報告の`unplanned`へ記録する。

各タスク、コミット、レビュー指摘反映の節目で、計画ファイルの`## 進捗ログ`へ結果を追記する。
計画本文と異なる確定形を採用した場合は、進捗ログだけでなく`## 変更内容`などの本文も更新する。
対象ファイルの追加・除外・改名では、チェックボックス項目と対応するH3節を同時に更新する。
当該チェックボックスは対象パス抽出用の固定記法であり、実装の完了状態を示す目的で書き換えない。

実行中のユーザー指摘は、適用中のプロジェクト規範に従って同じ実装・修正系へ追加指示として渡す。
指摘から確定した恒久化内容は計画本文へ反映し、未処理のまま先送りしない。

## 応答の即時検収

実装・修正系の応答を受領するたび、次のレビュー工程まで保留せず検収する。

- `changed`と計画の独立変更項目を`git diff`の実体で照合する
- `external_operations`の各項目のうち認可根拠が`計画記載`のものを、「初回委譲」節で保存した
  `## 実行方法`のスナップショットが列挙する操作・対象と照合する。認可根拠が`規範義務`のものは、
  適用中の規範が当該登録を義務づけることを確認する。
  いずれも対象側を直接照会して実施結果を確認する。実装・修正系は計画本文を改訂できるため、
  応答受領後の計画本文を認可根拠に用いない
- `verification`のコマンド、終了コード、警告を実測と照合する
- 応答が変更なしを示す一方で作業ツリーに変更があるなどの矛盾を検出する
- `unplanned`を計画方針へ照らして採否判定し、保留事項は`pending_confirmations`へ記録する
- 計画と異なるファイル、識別子、命名規約を採用した場合は計画本文を即時同期する
- 修正再実装では、修正差分が別の不具合を混入させていないことを確認する

技術的に解消できる失敗は、失敗事象と期待結果を同じ実装・修正系へ渡して継続する。
必須項目不足、実測との不一致、または同じ委譲失敗には、
確定済み事実と期待する出力に限定して1回再依頼する。
同じ失敗が2回続いた場合は応答全文と実測結果を残し、呼び出し元へエスカレーションする。

## 検証

現在のコミット単位を実装した後、その単位に最も近い範囲を検証する。
単位外の未コミット変更が検証へ影響する場合は、単位外の変更を含まない一時worktreeで検証する。
独立して検証できない変更は同一コミット単位へまとめる。

全コミットの完了後は、計画ファイルの`## 実行方法`に記載された内容で最終検証する。
最終検証には次を含める。

```text
uv run --script ${CLAUDE_PLUGIN_ROOT}/skills/plan-mode/scripts/check_plan_file.py \
  --work-dir <対象リポジトリの絶対パス> \
  <計画ファイルパス>
```

終了コード1は計画形式の違反として是正する。
終了コード2は引数、対象パス、読み取り条件を是正して再実行する。
warningも内容を確認し、解消または許容理由の記録を完了する。

## コミット

計画の想定コミット単位に従い、現在の単位だけをステージする。
コミット直前に`agent-toolkit:commit`の手順でstaged差分とunstaged差分を検収する。
各中間`HEAD`がその時点の公開契約とテストを満たすことを確認する。
実差分に応じてコミット境界を変更する場合は、コミット前に計画本文と進捗ログを同期する。

レビュー指摘をコミット済み差分へ反映する場合は、再検証後に`git commit --amend`で統合する。
`git push`、タグ作成、リモートref変更は実行しない。

## 指摘修正

レビュー指摘の修正では次を同じ実装・修正系へ渡す。

- 計画準拠系を`P-<通番>`、独立系を`I-<通番>`とした指摘ID
- 指摘原文、重大度、観点、区分、対象箇所、再現根拠
- 前回実装・検証結果
- 必要な再検証
- コミット済み差分へ統合する場合の`git commit --amend`条件

全指摘へ採用、不採用、他指摘との重複のいずれかを割り当てる。
不採用には実測根拠、重複には対応先IDを記録する。
採用指摘は修正、再検証、`git commit --amend`まで完遂し、
元の系統と指摘IDごとに反映結果を返す。
公開契約または利用者判断を要する未解決事項には暫定採否を設けず、
元の系統、指摘ID、判断材料を`blockers`へ返す。

修正後は`git status --short`・`git diff --stat`と検証結果を実測させる。
修正対象外の計画変更を発見した場合は、変更せず計画外事項として返させる。

## 検収結果

委譲先の完了報告形式は`plan-codex-implementation-task.md`を正とする。
`git status --short`と`git diff --stat`は要約へ置き換えず、生の出力であることを確認する。
前者は未コミット変更の残存を示し、後者は計画着手前からの変更規模を示す。

呼び出し元は応答とリポジトリ実体を照合し、最終完了報告を自身で作成する。
