# 計画の実装と修正

`plan-impl-executor`が計画全体の実装・検証・コミットと、レビュー指摘の修正を
単一の実装・修正系へ委譲するための手順を定める。

`## 変更内容`に列挙された全項目は、現在のコミット単位に属する分を当該単位の初回実装で完遂する。
段階化ラベルによる先送りや、全単位を先に実装してから部分ステージでコミット境界を再構成する運用は行わない。

## 初回プロンプト

初回プロンプトへ次を含める。

- 計画ファイルと対象リポジトリの絶対パス
- 計画着手前の`HEAD`
- 計画の対象ファイル、変更内容、想定コミット単位、実行順、完了条件
- 作業ディレクトリ外へ書き込まない制約
- 適用する品質スキルとプロジェクト規範の絶対パス
- 既存実装の移設または既存APIの呼び出しを含む場合は、対象実装本体の引用
- 実装、近接検証、計画の進捗ログ更新、計画記載のコミットまで完遂する指示
- `git push`・タグ作成などの公開操作を実行しない指示

実装をファイル・言語・工程別の複数担当へ分割しない。
codex経路では同じ実装・修正系`threadId`を完了まで継続する。
Claude代替では前回応答全文とリポジトリの実体をプロンプトへ含めて毎回新規起動する。
Claude代替では、初回プロンプトで指定した品質スキルとプロジェクト規範から
計画実装・修正へ適用する節本文を起動プロンプトへ引用転記する。
スキル名・節名・絶対パスの列挙を引用転記に代用しない。

## 実装順序

1. 計画着手前の`HEAD`を記録し、計画を想定コミット単位へ分解する
2. 現在の単位だけを実装する
3. 応答の受領直後に、応答と作業ツリーを照合する
4. 現在の単位に最も近い範囲を検証する
5. 差分と検証結果を確認し、現在の単位だけをコミットする
6. 未処理の単位があれば手順2へ戻る
7. 全単位の完了後に計画全体を最終検証する

対象ファイル数が5以上の場合は、実装前に対象ファイルごとのコミット履歴を確認する。
並行セッション由来の重複実装を検出した場合は、既存対応との統合結果を計画本文へ反映してから続行する。

各タスク、コミット、レビュー指摘反映の節目で、計画ファイルの`## 進捗ログ`へ結果を追記する。
計画本文と異なる確定形を採用した場合は、進捗ログだけでなく`## 変更内容`などの本文も更新する。
対象ファイルの追加・除外・改名では、チェックボックス項目と対応するH3節を同時に更新する。

実行中のユーザー指摘は、適用中のプロジェクト規範に従って同じ実装・修正系へ追加指示として渡す。
指摘から確定した恒久化内容は計画本文へ反映し、未処理のまま先送りしない。

## 応答の即時検収

実装・修正系の応答を受領するたび、次のレビュー工程まで保留せず検収する。

- `changed`と計画の独立変更項目を`git diff`の実体で照合する
- `verification`のコマンド、終了コード、警告を実測と照合する
- 応答が変更なしを示す一方で作業ツリーに変更があるなどの矛盾を検出する
- `unplanned`を計画方針へ照らして採否判定し、保留事項は`pending_confirmations`へ記録する
- 計画と異なるファイル、識別子、命名規約を採用した場合は計画本文を即時同期する
- 修正再実装では、修正差分が別の不具合を混入させていないことを確認する

技術的に解消できる失敗は、失敗事象と期待結果を同じ実装・修正系へ渡して継続する。
計画方針の見直しやユーザー判断が必要な場合だけ、`needs_escalation`として呼び出し元へ返す。

## 検証

現在のコミット単位を実装した後、その単位に最も近い範囲を検証する。
単位外の未コミット変更が検証へ影響する場合は、単位外の変更を含まない一時worktreeで検証する。
独立して検証できない変更は同一コミット単位へまとめる。

全コミットの完了後は、計画ファイルの`## 実行方法`に記載された内容で最終検証する。
最終検証には次を含める。

```text
uv run --script ${CLAUDE_PLUGIN_ROOT}/skills/plan-mode/scripts/check_plan_file.py <計画ファイルパス>
```

終了コード1は計画形式の違反として是正する。
終了コード2は引数、対象パス、読み取り条件を是正して再実行する。
warningも内容を確認し、解消または許容理由の記録を完了する。

## コミット

計画の想定コミット単位に従い、現在の単位だけをステージする。
コミット直前に`agent-toolkit:commit`の手順でstaged差分とunstaged差分を検収する。
各中間`HEAD`がその時点の公開契約とテストを満たすことを確認する。
実差分に応じてコミット境界を変更する場合は、コミット前に計画本文と進捗ログを同期する。

レビュー指摘をコミット済み差分へ反映する場合は、再検証後に`git commit --amend`で統合する。
`git push`、タグ作成、リモートref変更は実行しない。

## 指摘修正

レビュー指摘の修正では次を同じ実装・修正系へ渡す。

- 指摘原文、重大度、採否、対象箇所
- 前回実装・検証結果
- 必要な再検証
- コミット済み差分へ統合する場合の`git commit --amend`条件

修正後は`git status --short`・`git diff --stat`と検証結果を実測させる。
修正対象外の計画変更を発見した場合は、変更せず計画外事項として返させる。

## 実装担当の応答

```text
status: completed | needs_escalation
summary: <結果>
changed:
- <変更内容>
verification:
- <コマンド、終了コード、警告>
commit_sha: <最終コミット。コミット不要時は「なし」>
unplanned:
- <計画外事項。無ければ「なし」>
blockers:
- <未解決事項。無ければ「なし」>
```

呼び出し元は応答とリポジトリ実体を照合し、最終完了報告を自身で作成する。
