# 設計時のコーディング品質

本書は、計画ファイルを作成する時点で確定する実装方針、エンドユーザーデータの移行方針及びエンドユーザー接点の規範を扱う。
コードを編集する時点の規範は`implementation-time.md`が扱う。

## 実装方針の選択

- 実装に着手する前に、以下の順で検討する実装ラダーを適用する
  - 上位で成立する選択肢が見つかった時点で下位の検討は打ち切る
  - 検討順序:
    1. そもそも必要か（YAGNI）
    2. 標準ライブラリで実現できるか
    3. プラットフォーム標準機能（ブラウザAPI・OS提供機能等）で実現できるか
    4. インストール済みの依存で実現できるか
    5. 1行で書くか
    6. 上記いずれも成立しない場合のみ最小限の独自実装
  - ラダー対象外: 信頼境界検証・データ損失防止・セキュリティ・アクセシビリティ・
    ハードウェア較正に関わる実装はラダーで省略せず必要な堅牢性を確保する
- hashを採用する前に、識別・改ざん検知・cache invalidation等の目的、非hashの代替、衝突時の影響を確定する。
  目的に必要な性質を満たす最小の手段を選び、直接比較で十分な場合はhashを使わない（努力目標）
  - 複数の可変長値を入力にする場合は、長さ接頭辞または仕様で一意な正規形式により境界を一意にし、
    異なる値の分割が同じhash入力列にならない反証ケースをテストする（厳守規定）
- 品質要件を満たす実装案は、保守、実行時間、状態・工程、障害影響を含む総ライフサイクルコストで比較する。
  再発防止の便益は評価へ含めるが、既存契約の修正や削除・統合で同じ便益を得られる案を優先する
- 標準仕様のある形式（YAML・JSON・TOML等）を読み書きする実装は、形式のサブセットを自前パースせず正規のパーサーを使う
  （サブセット実装は仕様準拠を保証できず、正当な入力（複数行・入れ子の値など）を静かに誤読・欠落させるため）
- 入力形態の網羅: 集計値の判別条件と、入力形態が複数あり得る解析処理（正規表現・パーサー・突合条件）は、
  対象の命名規則・出力仕様が生成し得る形態を列挙してから確定する。
  構造化データ（frontmatter・JSON等）を対象とする集計では当該構造を解析した結果を根拠とし、
  条件へ合致しなかった対象を個別に確認して該当と非該当を区分する
  （条件の不備による取りこぼしと、構造外の記述への一致による過大計上の双方を防ぐ）。
  既存の解析処理を変更する場合は変更前後の双方を全形態へ適用して差分を比較し、
  変更前に取れていた情報が取れなくなる形態が1件でもあれば当該案を採用しない
- 公開仕様に準拠する解析処理（マークアップ・データ形式・識別子形式などの構文解析）を実装または
  変更する場合、当該仕様の参照実装が利用可能であれば、それを正解として突合し列挙の網羅性を検証する
  （努力目標。自力の列挙は仕様の見落としを検出できないため）
- 自動承認またはポリシー判定に用いる解析処理を新規作成・変更する前に、入力生成主体、信頼境界、
  通常入力、対象外入力、誤許可と誤拒否が消費主体へ与える影響を明示する。実装とテストの入力集合は
  この宣言へ合わせ、宣言外の脅威モデルを暗黙の要件として追加しない

## エンドユーザーデータの移行

- エンドユーザーが蓄積したデータ（ファイル配置・ファイル形式・スキーマ・設定形式）を変更する場合、
  旧形式から新形式への移行処理を同一の変更へ含める
  - 移行をエンドユーザーの手作業へ委ねる設計は採用しない
  - 移行処理を含められない技術的制約がある場合に限り、拒否時の案内文へエンドユーザーが単独で完遂できる手順を書く
  - 案内文で外部の状態変更を要求する場合は、その状態を当該変更の実装者が用意したうえで書く
- 移行処理と案内出力が同じ対象を扱う場合は判定関数を共有し、移行成立後に案内が自動的に無効化される条件を持たせる

## エンドユーザー接点と公開インターフェース

- CLIメッセージ設計: エンドユーザー向けエラーメッセージ・案内文は現行仕様のみで理解できる文面とし、
  metavar・内部識別子ではなくエンドユーザーの操作に即した平易な語を使う
  - 入力を拒否するメッセージには、拒否された値と、その値が違反した条件を書く。
    受理条件が複数の独立した制約から成る場合は、違反した制約を特定できる文面にする
  - 受理条件の定義と、それをエンドユーザーへ説明する文面は同じ場所へ置き、条件から文面を導く。
    同じ固定文言を複数の呼び出し箇所へ複製しない
- モジュール内および隣接モジュール（同ディレクトリ配下、または共通の公開インターフェースを介する
  呼び出し関係にあるモジュール群）の命名規約・エラー処理方針・返却値構造の一貫性を保つ
- 公開インターフェースを変更する場合、連動追従が必要な次の対象を、
  変更した識別子・出力文字列の全文検索（`grep`等）で全件洗い出す。
  公開インターフェースとはAPI・UI、CLIオプション・設定形式・出力形式、ライブラリの公開関数・
  公開クラス・データ形式など配布物のエンドユーザーが直接触れる面を指す
  （リポジトリ内部のモジュール・関数・クラスはpublic修飾の有無を問わず内部実装として扱う）
  - 対応する単体テスト・統合テスト・スナップショット
  - 対応するドキュメント（エンドユーザー向け・開発者向け）・サンプルコード・出力例
  - 対応する利用元（配布物を利用する側のコード・スクリプト、または内部で公開インターフェースを呼び出すモジュール群）
  - エンドユーザー向けエラーメッセージ・案内文
