# 待機と観測

委譲先または背景ジョブの完了を待つ際の観測、停滞判定、巻き取りを定める。

委譲先の完了を待つ場合と、委譲を伴わない背景ジョブの完了を待つ場合の双方へ適用する。
プロセスを終了させる操作の所有権規定は
`agent-toolkit/rules/02-agent-operations.md`「プロセス終了の安全規定」節を正本とする。

## 待機手段の選択

本表は待機対象から詳細規範へ進むための索引とし、各手段の規範本文は詳細節を正本とする。

| 待機対象 | 待機手段 | 終端の受領方法 | 除外する操作 | 詳細節 |
| --- | --- | --- | --- | --- |
| `agents_server`の委譲先 | `atk agents wait` | 対象の`session_id`を持つ終端statusと結果本文 | 対象又は待機上限の指定、未終端件数による遮断、同じ書込主体での併走 | 「待機区間の構成」「待機の起動条件」 |
| ホストの`Agent`ツールによるサブエージェント | ホストの完了通知と委譲一覧 | 完了通知又は戻り値と、起動文で指定した成果物 | `atk agents wait`、完了通知を待たない同じ処理の再委譲 | 「待機区間の構成」「待機の起動条件」 |
| ホストの背景ジョブ | ホストの背景実行と完了通知 | 保持した実行識別子の終端状態と、出力ファイルの終了状態行 | 同じ処理の重複起動、実行中の所有対象の停止 | 「背景ジョブの起動形（Claude Code）」「完了通知を待ってターンを終える場合」 |
| 外部サービスの状態変化 | 終了条件付きの待機又は背景実行した終了条件ループ | 終了条件が成立したコマンドの終端結果 | 前景の固定時間待機、固定時間待機と状態確認の反復 | 「外部サービスの状態変化を待つ場合」 |
| 人間の入力 | 定時起動による保存済みUWIの回答照会 | `atk wi list --type=uwi --answered=yes`に待機対象が現れた結果 | 前景の固定時間待機、回答前の元工程の再開 | 「外部サービスの状態変化を待つ場合」「完了通知を待ってターンを終える場合」 |

## 待機区間の構成

- 機械的な完了通知の受領を待機解除の既定手段とし、シェルコマンドによる能動的な時間待ちに代えてこの手段を使う
- `agents_server`を使う待機は`atk agents wait`だけで発行し、待機対象と待機上限を指定する引数は渡さない。前景待機と背景待機の選び方は、同CLIの公開説明と後述の目標評価の条項を正本とする。待機の対象は全ルートの起動中sessionと未回収結果の固定集合であり、稼働中の委譲先の件数から待機手段を選ぶ工程は無い
- 回収した終端結果が小さく、同じターンで1回だけ消費する場合は標準出力を直接受け取る。後続ターンで読む、再読する、監査証跡として保持する、又は出力量が大きい場合は`atk agents wait --output-file <管理対象一時領域の絶対パス>`で保存する。保存形を選ぶ前に`atk agents wait --help`を読み、必要な情報を失わない公開の要約指定があればそれを優先する。回収は結果ファイルと通知ファイルの削除を伴うため、背景移行後を含め、同じ結果を得る目的で待機を再発行しない
- 観測手段が終端statusを返さずに制御を戻した場合は、戻り方で継続と終端を分ける。
  実行環境がその観測を背景処理へ移し、完了時に通知すると戻り値が示す場合は、待機表明でターンを終え、通知の受領で再開する。
  この場合の同じ観測の再発行は控える。
  待機表明でターンを終えるセッションに`/goal`が設定され、かつそのセッションの未完了の背景タスクがこの背景移行だけである場合は、本項に代えて後述の目標評価の条項を適用する。
  背景処理への移行は待機の上限を意味せず、待機の上限は`atk agents wait`が導出する
- 完了通知の経路が確立しない戻り方では、同じターン内で同じ観測を再発行してよい。
  観測が自身の待機上限に達して終端statusを返さずに戻り、実行環境が背景処理への移行を示さない場合が該当する。
  再発行は、次項が定める`待機中の先行実施`の対象工程が尽きるまで続ける
- 再発行の前に`待機中の先行実施`の対象工程があれば実施する。
  先行して実施できる工程が尽き、かつ再発行した観測も終端statusを返さない場合は、待機表明でターンを終えて完了通知と定期再確認の経路へ委ねる
- 再発行できるのは、1回の呼び出しが待機時間を消費する観測手段に限る。
  待機時間を消費しない状態照会の反復は、補助観測だけを更新する同一turn内のポーリングに当たるため、再発行の対象の外に置く
- 自身が起動していない子孫の完了通知を受け取った場合は、直接の子へ中継した時点でその工程が再開する。
  中継の要否と手順は実行ホストの経路契約に従う（Claude Codeでは`references/claude-code-runtime.md`の
  「完了通知と中継の実行順」を正本とする）
- 生存状態と対象の判定には、プロセス名の一致を用いない。起動結果が返した識別子、完了通知、成果物側の状態確認手段のいずれかを照合する。
  照会手段と停止手段が公開されない実行環境でも同じ照合を用い、成果物の更新時刻と末尾標識は補助の材料に留める
- `atk agents wait`は、待機対象、待機上限、呼び出し元の区分及び応答後の破棄指定のいずれも受け取らない。対象は呼び出し元が保持する起動中のsessionと未回収結果の固定集合とする。待機上限はCLIが導出する。未終端sessionの件数を根拠として待機を遮断する検査は無い
- `atk agents wait`は、1回の巡回で回収できた終端結果と通知を全件、1件1行のJSON Linesで返す。各行は`session_id`を持ち、行は識別子の昇順に並ぶ。待機の成立は、いずれかの行が待機対象の`session_id`を持ち終端statusであることで判定する。待機対象の行が現れない応答は、その対象が未終端であることを示す。待機対象を指定する引数と残り件数の応答項目は、呼び出し元が保持する状態と判定を増やすため設けない
- 同じ書込主体の`atk agents wait`が既に稼働している場合、後発は`current.json`が示すrun識別子を固定し、先行待機のlock解放後に当該runが保存した本文と終了コードを返す。先行待機と後発待機は同じ結果を各1回受け取る
- `atk agents wait`が返す終了コード8は、run記録を持たない旧形式の待機との競合、先行run記録の読取不能、未公開又は回収済みを示す。待機対象の異常とは別の事象として、診断本文を呼び出し元へ返す
- 目標評価の発動条件は`agent-toolkit/share/rules-main.claude-code.md`の`/goal`の条項を正本とする。
  `agents_server`の`start`で起動した委譲先は独立したセッションとして動くため、委譲先の判定には委譲先が起動したタスクだけが入り、呼び出し元の判定には呼び出し元が起動したタスクだけが入る。
  そのセッションのAgent委譲とBash背景ジョブのいずれかの完了を待つ場合は、待機表明でターンを終える手順をそのまま用いる。
  そのセッションの未完了タスクが`agents_server`のsessionだけである場合は、`atk agents wait`を背景ジョブとして起動し、待機表明でターンを終える。
  このCLIは`agents_server`の状態ディレクトリを解決できる実行主体でだけ成立する。解決できない主体では終了コード4で終わるため、その事象と実行環境を呼び出し元へ返す。このCLIは書込主体単位の待機所有権を取得し、同じ書込主体による後発の起動を先行runの結果回収へ合流させる。
  このCLIは待機対象の指定と待機するturnの番号のいずれも受け取らず、対象は呼び出し元が保持する起動中のsession全体とする。`agents_server`は新しいturnの開始で前のturnの終端結果を削除するためである。
  この背景ジョブの完了通知が返した結果本文を受け取り、その受領で待機を終える。
  背景ジョブの起動を指定できない実行ホストでは、`atk agents wait`を前景で実行する。
  発動条件は`agent-toolkit/share/rules-main.claude-code.md`の`/goal`の条項を正本とする
- 待機表明で終端した委譲先が再開する契機は、その委譲先の起動経路で異なる。
  実行環境の`Agent`ツールで起動したサブエージェントは、背景ジョブの完了通知で再開する。
  `agents_server`の`start`、`start_explore`及び`start_shell`で起動した委譲先は、呼び出し元のサブエージェントではなく独立したセッションとして動く。
  そのセッションが`agents_server`の`start`、`start_explore`又は`start_shell`で別のsessionを起動した場合は、ClaudeとCodexの両backendがツール結果の`session_id`を追跡する。
  managerの常駐監視は全ての追跡対象が終端するまで最初の結果を保留し、終端した識別子を示す継続指示で同じsessionをそのターンにつき一度だけ自動的に再開する。
  Claude backendでは、背景実行したシェルのコマンド、背景で起動したAgent委譲、及び背景へ移行したMCPツールの呼び出しも、Claude Codeの完了通知による自動再開の対象になる。
  自動再開が働くのは背景タスクを起動した場合に限る。背景タスクを起動せずに待機を表明した場合の待機対象の完了確認と再開指示は、呼び出し元が行う
- 呼び出し元は、前項の自動再開について再開の要否を判断せず、再開の実行を自動再開へ委ねる。
  `atk agents wait`は再開したturnの終端まで待ち、その結果を返す。
  待機表明かどうかの判別にも、委譲先の最終メッセージの文面に代えてこのCLIの応答を用いる。
  同じ文面が作業の完了報告としても現れるため、文面による判別は誤った再開と再開漏れの双方を生む
- `atk agents wait`の待機上限と、その上限へ達した応答の扱いは、同CLIの公開説明を正本とする
- `agents_server`で起動したsessionの結果待機には`atk agents wait`を使う。
  待機上限を引数で指定せず、サーバーと待機CLIが導出する値を用いる。
  その上限へ達すると終了コード3で終わるため、この場合も`status`が`running`の応答と同じく同じコマンドを再発行して待機を継続する
- `atk agents wait`の終了コード10は、呼び出し元の状態へ待機対象が登録されていないことを示し、委譲先の実行失敗を示さない。
  起動側の応答と`atk agents list`で`agents_server`のsessionが存在するかを確認し、実行ホストの組み込み委譲として起動した対象はそのホストの委譲一覧と指定成果物で終端を観測する
- 実行ホストの上限により`atk agents wait`の呼び出し自体が失敗した場合も、待機対象のsessionは終端せず実行を続ける。
  `atk agents list`でそのsessionの`status`を確認し、CLIを再実行して待機を継続する。
  停滞、中断及び再起動の判定は、この`status`の確認で行う
- 委譲先と自身のツール呼び出しが、実行環境のアイドル上限によるアボート、待機上限の超過、無応答のままの中断のいずれかで終端statusを返さずに終了した場合を対象とする。
  この事象は実行基盤の欠陥の観測として扱い、`agent-toolkit:bugfix`の`references/response.md`の経路へ送る。
  待機の継続判定はこの事象と切り離して行い、欠陥の処置の確定と待機の継続判定の両方を実行する。
  異常終了の通知を待機の続行判断だけで消費すると、同じ欠陥が別のセッションで繰り返し発生する
- 保持中のsessionの活動時刻からの経過秒数`seconds_since_activity`、最新テキスト出力からの経過秒数`seconds_since_output`、未完了のツール呼び出し`active_tool_uses`及び稼働中の子`live_child_session_ids`は`show`の応答が返す。項目の名称と型はMCPツールのスキーマを正本とする。
  停滞の疑いは`seconds_since_activity`から判定する。テキスト出力だけが止まり活動が続いている状態は長時間のコマンドの実行中であり、催促と巻き取りのどちらも保留する。
  この判定は停滞の確定ではなく、呼び出し元がその委譲先の状況を調べる契機として扱う。該当した場合は同じ待機手段を再発行し、停滞の確定と巻き取りは「停滞の検知と巻き取り」節に従う
- `send_message`が返す`delivery: steered`は、その指示を配送キューへ投入した事実だけを示す。委譲先がその指示を読むかどうかは、この値の外にある。
  委譲先が単一の長時間コマンドを実行している間はターン境界へ達しないため、その指示はキューに滞留したままとなる。
  催促の到達は、そのsessionの`seconds_since_activity`と`active_tool_uses`の変化で判定する
- `agents_server`は終端結果を経過時間で解放せず、`atk agents wait`が結果本文を受け取るまで保持する。完了通知の受領から時間が経った後もCLIは終端状態と結果本文を返す。保持の解放は結果本文の配送後と`stop`による明示的な破棄の後だけとする
- 待機の続行の判断は、`atk agents wait`の終了コードと応答だけで行う。待機対象登録簿の内部仕様は同CLIの公開説明を正本とする。
  `status: running`を返した場合は、同じコマンドを再発行して待機を継続する。
  待機対象の登録と`starting`を含む保持中sessionがともに0件で非0終了した場合は、回収対象が存在しないため、再発行に代えて起動側の応答を確認する。保持中sessionがある場合は通常の待機上限まで待つ
- `atk agents wait`の応答の行が`notices`を含む場合は、その本文をその行の`session_id`の委譲先による実行中の即時報告として受け取る。待機を継続するかは`notices`の有無ではなく行の`status`で判定する。`status`が`running`の行は終端待機の完了ではないため、待機対象の終端行が無い応答では同じターン内で同じ待機手段を再発行する。終端statusの行は完了報告とともに受け取り、その行の`session_id`のsessionを未終端の集合から除く。回収した通知は再び返らないため、受け取った本文を保持する
- `agents_server`のMCPサーバーが再起動した場合、同じ`session_id`はsession登録簿から遅延解決する。終端が確定している記録だけを同じ識別子の結果観測と会話再開へ用いる。終端が確定していない場合は`error.recovery=turn_unobserved`を受け取り、同じ作業を新しい`start`でやり直さず、そのsessionが実行中である可能性を添えて呼び出し元へ返す。`missing`、`unreadable`、`no_resume_info`はそのsessionを失われたものとして扱ってよい

## 外部サービスの状態変化を待つ場合

待機を起動する前に、待機から得る結果、既に得た証拠及び次の必須工程が判定する結果を照合する。
同じ結果が既に得られている場合は待機を起動せず、`agent-toolkit/rules/01-agent.md`「手順の目的照合」の省略と報告の経路へ進む。
必要な結果が残る場合に、以下の終了条件付きの起動形を選ぶ。

CIの完了、デプロイの反映など、外部サービスの状態が変わるまで待つ場合は、終了条件の成立で終端し、その時点で1回だけ結果を返す起動形を選ぶ。
用いる起動形はこれだけとし、固定時間の`sleep`と、`sleep`へ状態確認コマンドを連結した反復は候補の外に置く。

- CIの完了は、`agent-toolkit:commit`の`references/push-and-ci.md`が定めるbaseline作成と監視の手順で待つ。同書が起動形、引数及び終了コードの意味の正本である
- 対象サービスのCLIが終了条件付きの待機を提供する場合はその手段を使う
- いずれも利用できない場合は、`until <終了条件のコマンド>; do sleep <秒数>; done`の形で終了条件により終端するループを構成し、実行ホストが提供する背景実行の指定で起動して、その完了通知で待機を解除する。`sleep`はループ本体の内側だけに置く
- 待機の解除条件が人間の入力又は外部インフラの復旧である区間には、終了条件の成立で終端する起動形が存在しないため、定時起動の各回でその条件の成立を照会する。
  保存済みUWIの回答は`atk wi list --type=uwi --answered=yes`の出力へ待機対象のファイル名が現れるかで判定する。
  外部インフラの復旧は、そのインフラが公開する状態照会と待機対象のジョブの再照会のいずれかで判定する。
  照会は委譲先の稼働確認と同じ回で行い、成立を検知した時点でその待機を終える
- 定時照会の間隔は、現在残る解除条件の種類から選ぶ。人間の入力は利用者が応答できる時間幅、外部インフラの復旧は公開された復旧見込みと状態照会の負荷、外部サービスの処理完了は通常の完了時間とサービス側のrate limitを入力にする。
  複数の解除条件が残る場合は、条件ごとに必要な照会契機を満たす最短の間隔を用いる。解除条件の成立又は追加により残る種類が変わった時点で間隔を再計算し、開始時に選んだ間隔を持ち越さない

## 背景ジョブの起動形（Claude Code）

- `run_in_background=true`の長時間ジョブは`Monitor`で全行取得するか完了マーカーを`grep -q`で待つ。
  `Monitor`を起動するのは、全行取得と完了マーカーの待機の2つに限る。
  ツール側で背景実行を指定したコマンドはシェル側を前景のまま保ち、末尾の`&`や`nohup`を重ねない。
  二重に背景化するとシェルの終了が完了通知となり、実ジョブの完了を検知できない
- 完了までに時間を要するコマンドは、Bashツールのタイムアウト引数を上限まで引き上げた前景実行を既定とする。
  上限時間内に収まらない場合は、実行対象を限定して複数回の前景実行へ分ける
- 遠隔ホスト側で`nohup`又は`setsid`により切り離した起動は完了通知経路を持たないため、実行主体自身が応答不能になる工程だけに用いる。
  それ以外の遠隔ホストの長時間コマンドは、`run_in_background=true`でSSH接続を保持するか、対象を限定した前景実行とする
- 完了と失敗の判定は、保持した実行識別子による生存の照会と出力ファイルの終了状態行で行い、空の出力ファイルは判定を保留する材料として扱う。
  Claude Codeで実測した完了通知と実プロセスの終了順は`references/claude-code-runtime.md`「背景ジョブ完了通知と実プロセスの終了順」を参照する。
  自己所有の背景ジョブも、再起動・巻き取りの前に保持した実行識別子で生存を照会し、生存中は同じ処理を重複起動しない。
  実行中の背景ジョブを空出力だけで終端と誤認する経路を閉じるためである
- 背景ジョブの終了状態と出力は、起動結果が返す出力ファイルの絶対パスから取得する。
  そのファイルは実行識別子から独立して残り、出力の全量と`[exited with code <整数>]`形式の終了状態行を保持する。
  観測手段には、実行識別子を入力とするものに加えて、この絶対パスからの取得を含める。
  待機が別のセッション又は別の実行主体へ渡る場合は、その絶対パスを引き継ぐ対象へ含める。
  実行識別子は実行環境の再起動で失効し、失効後はその識別子から終了状態と出力を取得できなくなる

## 待機の起動条件

- 委譲の起動前に、起動経路とその経路が提供する終端観測手段を組として選ぶ。要求する機能と権限が同等なら、`atk agents wait`で機械的に終端を観測できる`agents_server`を選ぶ。
  実行ホストの組み込み委譲を選んだ場合は、そのホストの委譲一覧が返すstatusと起動文で指定した成果物を観測し、終端観測をこの経路へ限定する。
- 完了通知を受け取れる経路が実在し、通知後に再開できることを待機開始前に確認する。
  受け取れない条件が確定した対象は待機対象に含めず、検収済み状態を渡して新規起動する。
  Codexでは、`references/runtime-routing.md`「Codex後続操作の共通先行条件」を適用してから新規起動する。
- 観測が終端statusを返しながら、タスク契約が受領を定める返却値を伴わない場合は、その終端を待機の対象の外に置く。
  完了通知を待たず、保持済みの識別子で同じsessionへ継続を要求してその返却値を得る。
  継続の要求は既存sessionの継続で行う。
  終端したturnは以降の通知を発しないため、待ち直しではその返却値が到達しない。
- 委譲先が自身の起動した委譲先の終端を待たずに自身のturnを終えた場合、その子の完了は呼び出し元へ通知されない。
  終端したturnは子の完了後に新しいturnを開始しないためであり、呼び出し元は前項に従って継続を要求する。
  本項は自動再開を持たない実行経路へ適用する。`agents_server`の両backendは、同じsessionが`agents_server`で起動した子の生存中はそのsessionの終端結果を保留するため、この経路では終端statusが返らない。
- 完了通知が到達しない場合は、単純に待ち直さず`停滞の検知と巻き取り`へ進む。
  調査は対象の実体を直接照会するコマンド（`ps -p <PID>`・`gh run list --commit <SHA>`等）で行う。

### Codex互換実行の稼働中turn

Codexで元担当の回復、置換、再起動、代替起動又は役割引継ぎを行う場合は、`references/runtime-routing.md`「Codex後続操作の共通先行条件」を先に適用する。
`running`のstatusと補助観測の優先順位、及び中断を確定できる根拠は、同節を正本とする。
後続主体を起動できるのは、同節が中断の根拠と認める事実を確認した後、元担当の終端と書込所有権の解放を確認した場合だけである。

- 同じ結果の再取得へコンテキストを消費しない。前回と同じ値が返ると見込まれる状態照会は反復せず、完了通知の不着、終端statusの確認、定時起動の各回など、値が変わり得る契機で照会する
- 待機中は対象外の独立した実装・検証・履歴整理・CI確認を進める。
  広範な未完了調査を1つの委譲先へ再委譲せず、独立した作業単位の完了を個別に受け取って統合する

## 完了通知を待ってターンを終える場合

- blocking waitとその背景ジョブのいずれかが対象sessionを所有している間は、定期再確認の各回でそのsessionの観測をblocking waitへ委ねる。
  所有の判定は、`atk agents wait`又はこれを起動した背景ジョブが終端の`status`を返していないことで行う。1回の待機は、その待機を発行した時点で呼び出し元が保持していた起動中のsession全体を所有する。
  定期再確認は、所有されていない待機対象の正本状態と完了通知、及び経過時間起動の義務だけを再確認する。
  blocking waitが自身の上限へ達して`running`を返した場合の再発行は、本項の対象の外に置き、「待機区間の構成」に従って発行する。
  完了通知の不着を検出した場合と、待機手段が終端の`status`を返さないまま失敗した場合は、そのsessionを所有されていない対象として扱う。
  同じsessionの終端観測をblocking waitと定期再確認の2経路が同時に所有すると、終端の検出を早めないまま照会だけが重複する

- 待機対象の完了通知から独立した定期再確認は、Claude Codeでは
  `agent-toolkit/skills/delegation/references/claude-code-runtime.md`「Cronによる定期再確認」節の作成・再利用・resume又はcompaction後の照合・削除の順序に従う。
  `CronCreate`、`CronList`及び`CronDelete`が現在の実行主体へ公開される場合だけ併用し、一般の委譲待機で`ScheduleWakeup`を使用しない
- 装着の時点、`atk wait-schedule`の起動形、定期promptへ含める内容、経過時間起動の義務の列挙及びtaskの再利用と削除は、前項が挙げる正本を適用する。
  装着するのは、起動する委譲先と背景ジョブのいずれかがあるセッションに限る。
  そのセッションが投入済みで未回答のUWIを保持している場合は、経過時間起動の各回で`atk wi`によりそのUWIの回答の有無を確認し、回答済みであれば同じターンで元の作業へ反映する。保持していないセッションではこの確認をしない。
  回答の到達を検知する契機が無いと、ユーザーが会話で通知するまで元の工程が再開しない。
  委譲先の起動から定期再確認の開始までの区間は、稼働中の委譲先の停滞と外部ジョブの終了を検出する主体が存在しない
- 実行環境が地の文の無い応答を可視出力の欠落として扱い、応答の再生成を要求する場合だけ、記号1文字など内容を持たない最小限の出力でその要求を満たす
- 定期再確認機構又は`atk wait-schedule`が利用できない場合も、シェルの`sleep`や背景タイマーへ切り替えず待機表明でターンを終える。
  外部事象の到達だけに依存する待機は、その事象が到達しない障害時に打ち切る契機を失う
- 背景委譲を起動した実行主体は、その委譲の完了通知の受領をもって待機解除としてよい
- 子孫の完了通知を直接の呼出元ではない主体が受け取った場合の中継と、中継不能時の巻き取りは`references/claude-code-runtime.md`「完了通知と中継の実行順」を正本とする。
  中継先への送信の受理は送信側の受理だけを示すため、完了通知か戻り値を対応付けて受信処理を確認するまで再送を控える。
  担当範囲又は権限の外にある場合は、保持した通知、送信先ID、送信結果及び未観測の結果を`needs_escalation`として呼出元へ返す。
  Codexで未完了工程を巻き取る場合は、`references/runtime-routing.md`「Codex後続操作の共通先行条件」を適用してから行う
- 完了通知が到達しない場合は`停滞の検知と巻き取り`へ進む。
  成果物ファイル、孫のtranscript及び委譲先自身のtranscriptの最終更新時刻を停滞の判定材料として実測する。
  終了の判定には更新時刻に加えて実行識別子の直接照会を用い、実行中の孫を終了済みと誤認して同じ工程へ複数の主体を接続する経路を閉じる
- 出力ファイルの末尾標識照会は取得時点が中間ターン境界へ一致し得るため、完了判定では他の観測と併用する
- 定時起動の依頼文へは、現在の作業状態を正本となるファイル（計画ファイル・引き継ぎ記録・作業ツリー・
  課題管理の一覧など）から読み直して判定する手段だけを書く。
  待機対象ID、成果物の絶対パス、コミット識別子、残工程の列挙及び完了済み工程の記述は依頼文の外へ置く。
  依頼文が可変状態の写しを保持すると、工程が進むたびに内容が事実と相違する（努力目標）
- 定時起動の発火は停滞時間の起点を更新せず、完了と停滞の判定は次の観測で行う。
  変化が無い場合も、既存の`ListAgents`、完了通知、`atk watch`及び保持済み識別子による直接観測で停滞の検知条件を満たした場合だけ巻き取りへ進む
- ターンを終える直前の実測は、成果物側の観測を1回だけ行い、前回から値が変わった場合は、変化した値と待機を続ける理由をユーザーへ簡潔に示す。
  稼働状態の照会は、停滞の検知条件を満たしたかを判定する回と、催促又は巻き取りの要否と宛先を確定する回で発行する。
  同一turn内で補助観測を更新するために同じ状態確認コマンドを反復発行すると、同一結果の再取得へコンテキストを消費する

## 待機中の先行実施

待機中は、後続工程のうち委譲先の対象範囲と競合せず、
かつ着手条件と入力が待機対象の結果に依存しない全ての工程を先行して実施する（努力目標）。
競合の有無は委譲先の変更説明と実差分の突合で判定し、読み取りのみの調査は競合しないものとして扱う。
別リポジトリへの操作もファイル競合は生じないが、入力が待機対象の結果に依存する場合は先行しない。

## 停滞の検知と巻き取り

- 停滞を疑った時点で`show`を1回発行し、`active_tool_uses`を確認する。
  この項目が存在し、前回の観測と同じツール呼び出しが同じ開始時刻で続いている場合は、委譲先が長時間のコマンドを実行中であるため、催促と巻き取りのどちらも保留する。
  この項目が無く`seconds_since_activity`が停滞を疑う長さに達している場合だけ、以降の停滞の確定の手順へ進む
- 委譲先が所有する外部プロセスまたは背景ジョブの実行中は、停滞の判定に成果物差分と実行識別子の直接照会の両方を用いる。
  所有主体が返した安定した実行識別子を直接照会し、生存中、識別子消失、終了後の結果未回収を区別する。
  外部実行を終了できるのは所有主体だけとし、委譲元は生存中の処理を重複起動しない
- 別turn又は次の定時起動で間隔を空けた複数回の観測に差が無ければ継続を1回促す。
  Codexの`list_agents`が対象を`running`として返している間は、`Codex互換実行の稼働中turn`節の禁止及び起動条件を適用し、巻取り、新規起動及び役割引継ぎを保留する。補助観測と催促は、これらを開始する根拠の外に置く。
  Codex以外の対象でその後も応答が無ければ、未完了工程を巻き取るか、縮減した新規サブエージェントを起動する。観測結果はユーザーへ短く提示する。
  ただし成果物ファイルの更新が続いている間と、更新元を別主体（CI・formatter・並行セッション等）と
  区別できない間は、停止・巻き取りの判断を保留して催促にとどめる。
  観測値の無変化が続いた場合は、この保留を解いて催促へ進む
  （努力目標。保留を解く間隔は対象の性質で選ぶ）
- 稼働中の同一委譲先へ、先に送った方針と矛盾する差し替えを繰り返す状況になった時点で作業の保留を指示し、
  委譲元で方針を確定してから旧方針との差分を統合した指示を1回で送付して再開させる
- 起動文へ明示した同一の制約への違反が繰り返される場合は、同じ制約を伝え直す起動を繰り返さず、
  Codexでは`references/runtime-routing.md`「Codex後続操作の共通先行条件」を適用した後にその工程の巻取り、別の経路への切替え又は役割の引継ぎを行う。
  Codex以外では、呼び出し元がその工程を巻き取るか別の経路へ切り替える。切り替えの前に、違反が委譲先の出力形式と
  受信側の判定条件のどちらに起因するかを実装で確認し、受信側に起因する場合は判定条件を是正する
- 停滞を確定して巻き取る場合、再実装を決める前に委譲先自身のtranscript、委譲先が起動した子孫の記録及び
  外部実行系のログを末尾に限定して確認する。
  完了報告を取得できた場合は再実装せず、その報告を検収して、実行時に公開され呼び出しが成功した`SendMessage`と保持済みIDで再開する。
  完了報告を取得できない場合は未完了の工程だけを巻き取り、担当範囲又は権限の外にある場合は`needs_escalation`で返す
  Codexで未完了工程を巻き取るか新規起動する場合は、`references/runtime-routing.md`「Codex後続操作の共通先行条件」を適用してから行う
- 停滞検知を完了して委譲先を停止する場合は、停止の根拠を対象ごとに残してから停止する。
  Claude Codeでは`atk run-script record-stall-detection --`がその記録を作成し、終了コード0を返した対象だけが停止の対象となる
- Codexの二層待機では、停滞の判定材料に内側の`atk agents wait`の状態を用いる。外側の実行セルのyieldが続く間は、巻き取り、代替起動及び新規起動へ進まず、`codex-runtime.md`「agents_serverの二層待機」節が定める手順で外側の実行セルを再開する

## 成果物側の観測

委譲先が新規作成する成果物のパスは、委譲元が起動文で指定した値又は委譲先が報告した値から確定する。
対象の確定にはこの2つの値を用い、共有出力ディレクトリの一覧と更新時刻は推定の材料から外す。
対象パスが未確定の間は成果物を観測せず、委譲先の生存確認と完了通知を待つ。

委譲先・背景ジョブの成果物側の状況は、実行環境向けに配布されたagent-toolkitの管理CLIが提供する状態確認手段で、
作業ツリーの差分件数・HEAD・成果物ファイルの行数と最終更新からの経過時間を1回の呼び出しでまとめて得る。
同一の観測へ複数のコマンドを個別に発行しない（努力目標）。この手段が返すのは成果物側の値だけであり、
生存中・識別子消失・終了後の結果未回収の区別には、引き続き実行識別子の直接照会を用いる。

- 待機中の報告へ載せる観測値は、その実行主体が書き込む対象の値に限る。非担当対象の値を載せる場合は、その値が判断を変える理由と、実際に書き込んだ実行主体を併記する。
- `atk watch`が返す作業ツリーの差分件数とHEADは、並行セッション、CI、formatterその他の主体を含む作業ツリー全体の値であり、生存と進捗の判定には他の観測と併用する。指定artifactの行数・更新時刻・経過秒も、そのartifactの書込主体へ帰属させて補助観測として扱う。

## 委譲先からの即時報告

本節は`agent-toolkit/share/rules-subagent.md`「委譲時の厳守事項」が定める即時報告の判定順序と本文要件の正本である。

即時報告は、次の順に判定し、最初に成立した手段だけで1通送る。
判定の前に環境変数`AGENT_TOOLKIT_OWNER_SESSION`の設定有無だけを検査する。この環境変数の値は、コマンド出力、報告及び成果物のいずれの記録対象からも外す。
第1に、この環境変数を保持する実行主体は、本文を`atk agents notify`の`--body`又は`--body-file`のいずれか一方で渡す。
本文がシェルメタ文字（単一引用符・逆引用符・ドル記号・改行など）を含む場合は、絶対パスのUTF-8ファイルへ保存し、`--body-file`で渡す。
引数の引用の組み立ては`agent-toolkit/rules/02-agent-operations.md`「ツール・コマンド運用」に従う。
第2に、`AGENT_TOOLKIT_OWNER_SESSION`を保持しない実行主体が到達可能な機械可読返信識別子を保持し、現在の実行主体へ`SendMessage`が公開され呼び出しに成功する場合は、保持した識別子へ送る。
いずれの手段も成立しない場合と、`atk agents notify`が非0で終了した場合は、同じ事象を通常の完了報告へ含め、受け取った側が完了通知とともに逐語で中継する。`agents_server`の委譲先は、`SendMessage`を完了報告の送信手段に用いず、通常の完了報告を起動経路の返却値へ返す。
返信先には保持した機械可読識別子だけを用い、即時報告は`atk agents notify`と`SendMessage`のどちらか1つで送る。
即時報告と完了報告の`想定外事象:`及び続行不能時の返却形式の`reason`には、事象、実行経路又はコマンド、エラー原文、影響範囲、
直接原因が確定済みか未確定か、対象ホスト又はパスを含める。
これらを1行へ収められない場合は、全項目を記録した成果物の絶対パスをその行へ示す。
受け取った主体が追加の照会をせずに、その事象の判断とAWIの起草を確定できる粒度とする。

本書の条文が根拠とする実測の日付、版数及び再検証手段は、`docs/development/audit-records.md`の本書に対応する各記録が持つ。
