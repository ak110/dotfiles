# 待機と観測

委譲先と、委譲を伴わないバックグラウンドタスクの完了を待つ際の観測、停滞判定、巻き取りを定める。プロセスを終了させる操作の所有権は`agent-toolkit/rules/02-agent-operations.md`「プロセス終了の安全規定」に従う。

## 待機手段の選択

| 待機対象 | 待機手段 | 終端の受領方法 | 除外する操作 | 詳細節 |
| --- | --- | --- | --- | --- |
| `agents_server`の委譲先 | `atk agents wait` | 対象の`session_id`を持つ終端statusと結果本文 | 対象または待機上限の指定、未終端件数による遮断、同じ書込主体での併走 | 「待機区間の構成」「`atk agents wait`の応答の扱い」「待機の起動条件」 |
| ホストの`Agent`ツールによるサブエージェント | ホストの完了通知と委譲一覧 | 完了通知または戻り値と、委譲プロンプトで指定した成果物 | `atk agents wait`、完了通知を待たない同じ処理の再委譲 | 「待機区間の構成」「待機の起動条件」 |
| ホストのバックグラウンドタスク | ホストの背景実行と完了通知 | 保持した実行識別子の終端状態と、出力ファイルの終了状態行 | 同じ処理の重複起動、実行中の所有対象の停止 | 「背景ジョブの起動形（Claude Code）」「完了通知を待ってターンを終える場合」 |
| Codexの`functions.exec`のcell ID | 公開されている`functions.wait` | 同一ターンで出力と完了結果を回収 | 環境全体の自動再開通知を理由にしたターン終了 | 「待機区間の構成」 |
| Codexの`exec_command`のsession ID | 公開されている`write_stdin` | 同一ターンで出力と終了コードを回収 | 前掲と同じ | 「待機区間の構成」 |
| 外部サービスの状態変化 | 終了条件付きの待機または背景実行した終了条件ループ | 終了条件が成立したコマンドの終端結果 | 前景の固定時間待機、固定時間待機と状態確認の反復 | 「外部サービスの状態変化を待つ場合」 |
| ユーザーの入力 | 定時起動による保存済みUWIの回答照会 | `atk wi list --type=uwi --answered=yes`に待機対象が現れた結果 | 前景の固定時間待機、回答前の元工程の再開 | 「外部サービスの状態変化を待つ場合」「完了通知を待ってターンを終える場合」 |

## 待機区間の構成

機械的な完了通知を待機の解除手段とし、シェルによる能動的な時間待ちを禁じる。

完了通知で同じセッションを再開できる待機は、対象の種類・件数・既存のバックグラウンドタスク・goalの有無によらず、常にホストの背景実行で開始する。
Claude Codeでは`atk agents wait`、CI・配備状態の監視、終了条件ループをBashの`run_in_background=true`で起動し、先に届いた独立待機の通知から保存出力と終了状態を回収する。
起動済みの待機の結果を受け取り、先に届いた通知に対応する工程へ進む。
各待機・監視は1つの実行を保ち、前景やMonitorを別の待機の終端まで占有する操作は対象外とする。
通知による再開が無い環境は公開待機手段で終端を確定し、Codexのcell ID・コマンドsession IDは前表の公開回収機能で同じターンに回収する。

- `agents_server`の待機は`atk agents wait`だけで発行する
  - 待機対象、待機上限、委譲元の区分、応答後の破棄指定は渡す引数から外す。対象は発行時点の全ルートの起動中sessionと未回収結果の全体で、上限はCLIが導出する
  - 外側の`timeout`、パイプ、`wc`などを連結しない引数なしの単独コマンドとする。ホストのツールの時間上限（Claude CodeのBashツールの`timeout`引数など）も外側の上限に当たり、背景実行での扱いは`agent-toolkit/rules/02-agent-operations.md`「待機と背景実行」に従う。連結や短い外側の上限は待機を先に打ち切るか終了コードを覆い隠す
  - 続行の判断は終了コードと応答だけで行い、`status: running`なら同じコマンドを再発行する。起動方法は本節の通知による再開の規則に従う
  - 回収結果はエージェント環境では新規managed-tempへ保存され、保存先・行数と終端・通知の内訳が返る。保存先から全量を読み、後続ターンの再読と引き渡しにも同じファイルを使う
  - 回収は結果と通知の削除を伴うため、背景へ移った後も含め、同じ結果を得る目的の操作は再発行対象から除く
- 観測が終端statusを返さずに戻った場合は、戻り方で分ける
  - 実行環境が観測を背景処理へ移し、その完了通知が同じsessionを再開すると示す場合だけ、同じ観測を再発行せず待機表明でターンを終える。背景への移行は待機の上限とは無関係である。Codexのcell IDとexec_commandのsession IDは環境全体の能力通知だけでは自動再開されないため、前表の公開手段で同じターンに回収する
  - 観測が自身の待機上限で戻り背景への移行も示されない場合は、同じターン内で再発行してよい。再発行の前に「待機中の先行実施」の工程を進め、それが尽きても終端しない場合は、通知で再開できることを確かめてから完了通知と定期再確認へ委ねる
  - 再発行してよいのは1回の呼び出しが待機時間を消費する観測手段に限る。待機時間を消費しない状態照会の反復は、補助観測だけを更新するポーリングとして避ける
- 自身が起動していない子孫の完了通知は、直接の子へ中継した時点でその工程が再開する。中継はホストの委譲契約（Claude Codeでは`references/claude-code-runtime.md`「完了通知と中継の実行順」）に従う
- 生存状態と対象は、起動結果の識別子、完了通知、成果物側の状態確認手段で判定し、更新時刻、末尾標識、`git log`、`git status`は補助材料にとどめる
- 目標評価（`/goal`）の発動条件は`agent-toolkit/share/rules-main.claude-code.md`に従う。`agents_server`の委譲先は独立したセッションであり、各セッションの判定には自身が起動したタスクだけが入る。待機の起動と回収はgoal条件で分岐させず、本節の共通規則を使う。異常終了は`references/wait-anomalies.md`に従う
- 待機表明で終端した委譲先が再開する契機は起動形態で異なる。`Agent`ツールのサブエージェントはバックグラウンドタスクの完了通知で再開する。`agents_server`の委譲先が起動した別の`agents_server` sessionは両backendが追跡し、全ての追跡対象が終端するまで最初の結果を保留して、そのturnにつき一度だけ同じsessionを自動再開する。Claude backendでは背景実行したシェル、背景のAgent委譲、背景へ移ったMCPツール呼び出しも自動再開の対象になる。自動再開はバックグラウンドタスクを起動した場合に限り、起動せずに待機を表明した場合は委譲元が完了を確かめて再開を指示する。監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：待機区間の構成：2026年9月3日」にある
- 委譲元は自動再開の要否を判断せず、自動再開へ委ねる。`atk agents wait`は再開したturnの終端まで待って結果を返す。待機表明かどうかはこのCLIの応答で判別する（同じ文面が完了報告にも現れる）。`終端行:`に`unfinished_waits`を持つ結果（`error`の`heldResultFinalized`が真）は、待機対象が残ったまま保留を打ち切った待機表明であり、再開したturnの最終返却として扱わず、残った対象の状態を確かめてから同じsessionへ続きを依頼する。`unobservedSessions`だけでは判別しない
- `show`が返す停滞診断と子sessionの一覧、`send_message`が返す`delivery`の意味は各MCPツールの説明が定める。長時間のコマンドの実行中なら催促も巻き取りも保留する。停滞の可能性は委譲先の状況を調べる契機であり、確定と巻き取りは「停滞の検知と巻き取り」に従う

## 長時間待機前の会話圧縮

Claude Codeのメインが、他の担当かCI監視の結果を次の工程の入力として待つ時点の共通手順である。予約する時点と保存する工程状態は、呼び出す工程の手順が定める。
独立した先行工程を先に開始し、工程状態をセッションのmanaged-temp直下の`parent-handoff.md`へ保存してから進む。圧縮後はmanaged-tempの通知からこの固定名を見つけ、担当別記録、選定、監視、保存出力はそこに書いた参照から取得する。

1. `mcp__agent-toolkit__compact_conversation`が無い環境は前提不成立を引き継ぎ記録へ残して通常の待機へ進む。Codexは適用範囲外とする
2. ツールを引数なしで1回呼ぶ。受付は圧縮完了と区別し、未完了の予約へ追加予約を重ねない。Claude CodeのFunction hooks moduleは追加指示のない`/compact`を実行するため、工程状態を予約入力へ転記しない
3. agents_serverの結果を待つ区間は、引数なしの単独`atk agents wait`をBashバックグラウンドタスクで起動する（session_idは結果との対応付けに使い、待機コマンドへ渡さない）。CI監視を待つ区間は、起動済みの`wait_ci.py`のバックグラウンドタスクを保ち、新しい監視を起動しない
4. Monitorで前景を占有せずに現在ターンを終え、完了通知と保存した全出力から待機の終了状態を回収する
5. 通知後は`parent-handoff.md`を読み、保存した現物と受領結果を比べて同じ工程から続ける。圧縮が失敗してもこの記録から復元し、既存の担当と監視を継続する。予約の失敗、圧縮成功、待機結果は別々に記録する

## `atk agents wait`の応答の扱い

バックグラウンドタスクの`atk agents wait`が未完了の間の進捗はlist/showの活動情報で確かめ、途中の出力は進捗として扱う。終端結果は完了通知を受け取ってから出力を全量読み直して回収し、同じ結果のためにwaitを併走させない。Codexのcell IDとsession IDは前掲の同ターン回収に従う。
公式資料と元ホストの観測は、`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：進捗照会と結果回収：2026年10月10日」にある。

- 応答の行の形式（JSON Lines、`session_id`と`label`、`agent_message_path`、`終端行:`の要約行）と待機の成立の判定は同CLIの`--help`に従う。依頼の判別には`label`を使い、失敗で終端した行は要約行の`error`で原因を確かめ`next_action`に従う。結果を回収できなかった終端sessionの原因は`show`の`error`で確かめる
- 同じ書込主体の`atk agents wait`が既に稼働している場合、後発は`current.json`が示すrun識別子を固定し、先行待機のlock解放後にそのrunが保存した本文と終了コードを返す。前景のCLIが本文を返した後の逐次待機は新しいrunへ進み、先行CLIが稼働中にlock競合した後発待機だけが先行runの本文を1回回収する。バックグラウンドタスクの完了通知の後も先行の実プロセスが残ることがあり、その間に起動した後続の待機も同じく先行runを回収する
- 待機上限の終了コード3は`status`が`running`の応答と同じく、同じコマンドを再発行して続ける
- 行が`notices`を含む場合は、その`session_id`の委譲先からの実行中の即時通知として受け取り、本文を保持する（同じ通知が返るのは一度だけである）。待機の継続は行の`status`で判定し、終端行が無ければ同じターン内で再発行する。終端statusの行は完了報告とともに受け取り、そのsessionを未終端の集合から除く
- `agents_server`は終端結果を経過時間で解放せず、結果本文の配送後と`stop`による破棄の後にだけ解放する。完了通知から時間が経っても終端状態と本文を回収できる

## 外部サービスの状態変化を待つ場合

待機を起動する前に、待機で得る結果が既に得た証拠や次の必須工程の判定で足りないかを比べ、足りるなら待機せず`agent-toolkit/rules/01-agent.md`「行動と手順の目的」の省略と報告へ進む。

CIの完了、デプロイの反映などは、終了条件の成立で終端してその時点で1回だけ結果を返す起動形で待つ。固定時間の待機は所要時間が確定した短い待ち（数秒のレート制限など）に限り、`sleep`へ状態確認を連結した反復は使わない（待ち時間を浪費し、打ち切りの契機も失う）。

- CIの完了は`agent-toolkit:commit`の`references/push-and-ci.md`のbaseline作成と監視の手順で待つ
- 対象サービスのCLIが終了条件付きの待機を提供すればそれを使う
- どちらも無ければ、`agent-toolkit/rules/02-agent-operations.md`「待機と背景実行」の`timeout`付き終了条件ループを、同節の時間上限でホストの背景実行として起動し、完了通知で解除する。上限で終わったら終了条件を照会し、未成立なら起動し直す
- 解除条件がユーザーの入力か外部インフラの復旧である区間は、定時起動の各回で成立を照会する。保存済みUWIの回答は`atk wi list --type=uwi --answered=yes`の出力に待機対象のファイル名が現れるかで、インフラの復旧は公開された状態照会か対象ジョブの再照会で判定する
- 照会の間隔は残る解除条件の種類（ユーザーが応答できる時間幅、公開された復旧見込みと照会の負荷、通常の完了時間とrate limit）から選び、残る種類が変わったら選び直す

## 背景ジョブの起動形（Claude Code）

- 待機の起動方法は「待機区間の構成」に従う。待機以外の検証・ビルドなど時間を要するコマンドは、Bashツールのタイムアウト引数を上限まで上げた前景実行を通常とし、収まらなければ対象を限定して複数回の前景実行へ分ける
- 待機は完了通知と定期再確認で扱い、Monitorや完了マーカーの前景ループへ戻さない。待機以外のバックグラウンドタスクの全行取得にはMonitorを使える。ツール側で背景実行を指定したコマンドに`&`や`nohup`を重ねない（シェルの終了が先に完了通知として届く）
- 遠隔ホストで`nohup`か`setsid`により切り離す起動は完了通知を持たないため、エージェント自身が応答不能になる工程だけに使う。それ以外は`run_in_background=true`でSSH接続を保持するか、対象を限定した前景実行とする
- 終了状態と出力は、起動結果が返す出力ファイルの絶対パスから取得する。このファイルは実行識別子と独立して残り、出力の全量と`[exited with code <整数>]`形式の終了状態行を持つ（実行識別子は実行環境の再起動で失効する）。待機を別のセッションかエージェントへ渡す場合はこのパスも引き継ぐ。監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」にある。同じ文の記録は「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月4日」にもある
- 完了と失敗は、保持した実行識別子による生存の照会と出力ファイルの終了状態行で判定し、空の出力ファイルは判定の保留にとどめる。自己所有のタスクも、再起動や巻き取りの前に生存を照会し、生存中は同じ処理を重複起動しない。完了通知と実プロセスの終了順は`references/claude-code-runtime.md`「背景ジョブ完了通知と実プロセスの終了順」を参照する。ホストの停止通知を受けた場合は`references/wait-anomalies.md`「ホストによる背景待機の停止後」に従い、元の待機と出力を回収する

## 待機の起動条件

- 起動手段と終端観測手段の組は`references/runtime-routing.md`「実行手段」に従って起動前に選ぶ
- 完了通知を受け取る手段が実在し、通知後に再開できることを待機開始前に確かめる。受け取れない対象は待機対象に含めず、検収済み状態を渡して新規起動する（Codexでは`references/codex-runtime.md`「後続操作の共通先行条件」を先に適用する）
- 終端statusを返しながらタスク契約の返却値を伴わない終端は未完了として扱う。終端したturnは以後通知を発しないため、待ち直さず、保持済みの識別子で同じsessionへ継続を要求して返却値を得る。委譲先が自身の子の終端を待たずにturnを終えた場合も同じとする（`agents_server`の両backendは子の生存中は終端結果を保留するため、この起動形態では生じない）
- 完了通知が到達しない場合は待ち直さず「停滞の検知と巻き取り」へ進み、保持した識別子で対象を直接照会する

### 再照会の抑制と待機中の作業

- 前回と同じ値が返ると見込まれる状態照会は反復せず、完了通知の不着、終端statusの確認、定時起動の各回など値が変わり得る契機で照会する
- 待機中は対象外の独立した作業を進める。広範な未完了調査を1つの委譲先へ再委譲せず、独立した作業単位の完了を個別に受け取って統合する

## 完了通知を待ってターンを終える場合

- 1回のblocking wait（`atk agents wait`かそれを起動したバックグラウンドタスク）は、発行時点で委譲元が保持していた起動中のsession全体を、終端の`status`を返すまで所有する。定期再確認は所有された対象の観測をblocking waitへ委ね、所有されていない対象の記録側の状態と完了通知、および経過時間起動の義務だけを確かめる。完了通知の不着を検出した対象と、待機手段が終端の`status`を返さず失敗した対象は所有されていないものとして扱う。上限で`running`を返したblocking waitの再発行は「待機区間の構成」に従う
- 定期再確認は、Claude Codeでは`references/claude-code-runtime.md`「待機中の定期再確認と背景転換」に従い、委譲先かバックグラウンドタスクを起動したセッションにだけ装着する。`start`の結果を受け取った時点でFunction hooks moduleによる定期再確認の装着は済んでおり、自ら装着する場合も起動の直前か通知を受けた直後に装着する（起動から装着までが延びると停滞や外部ジョブの終了を検出する主体が欠ける）
- 投入済みで未回答のUWIを保持するセッションは、経過時間起動の各回で`atk wi`によりその回答の有無を確かめ、回答済みなら同じターンで元の作業へ反映する（契機が無いとユーザーが会話で通知するまで工程が止まる）
- 子孫の完了通知を直接の委譲元以外が受け取った場合の中継、再送、巻き取りは`references/claude-code-runtime.md`「完了通知と中継の実行順」に従う
- 完了通知が届かない場合は「停滞の検知と巻き取り」へ進み、成果物ファイル、委譲先が起動した委譲先のtranscriptと委譲先自身のtranscriptの最終更新時刻を実際に取得する。終了の判定には実行識別子の直接照会も使い、委譲先が起動した主体を終了済みと誤認して同じ工程へ複数のエージェントを接続しない
- 定時起動の依頼文には、現在の作業状態を正とする記録（計画ファイル、引き継ぎ記録、作業ツリー、課題管理の一覧など）から読み直す手段だけを書き、待機対象ID、成果物の絶対パス、コミット識別子、残工程と完了済み工程は書かない（努力目標）
- 定時起動の発火は停滞時間の起点を更新せず、判定は次の観測で行う
- ターンを終える直前に成果物側を観測し、前回から変わった値があれば、その値と待機を続ける理由をユーザーへ簡潔に示す（努力目標）。稼働状態の照会は、停滞を判定する回と、催促か巻き取りの要否と宛先を確定する回にだけ発行する

Claude CodeのStopで未配送の完了通知があり、他のagent-toolkitの判定がblockを返していない場合は、現在ターンを終えて通知の配送による次ターンで保存出力と終了状態を受け取る。他のblockが残る場合だけ、その理由を解消しながら結果受領の警告に従う。同じ結果のために待機コマンドを再発行しない。

待機だけでターンを終えるときの出力は次のとおりとする。自動再開の対象には、自身が`agents_server`で起動した委譲先のsessionとClaude Codeの通知付きバックグラウンドタスクを含み、Codexのcell IDとexec_commandのsession IDは対象外とする。本表を変える場合は、各エージェントへ届く文書（表中の参照先）も合わせる。

| エージェント | 同じsessionの自動再開あり | 自動再開なし |
| --- | --- | --- |
| メイン | 本文を空にする。空の応答をホストが再生成させる場合（Claude Code）は`…`だけを出力する（`share/rules-main.md`「ユーザー向け発話ルール」、`share/rules-main.claude-code.md`） | 同左（メインは完了通知で再開する） |
| `agents_server`の委譲先 | `待機中: <実行識別子>`の1行（`share/agents-server-auto-resume.md`、`share/rules-subagent.md`「返却と終端」） | 待機でターンを終えず、`agent-toolkit/rules/02-agent-operations.md`「待機と背景実行」の前景待機で終端を確定してから返却形式を返す |
| `Agent`ツールのサブエージェント | 完了通知で再開する起動形態では`待機中: <実行識別子>`の1行 | 同上の前景待機 |

## 待機中の先行実施

待機中は、委譲先の対象範囲と競合せず、着手条件と入力が待機対象の結果に依存しない後続工程を全て先に実施する（努力目標）。競合は委譲先の変更説明と実差分の突合で判定し、読み取りだけの調査は競合しないものとする。別リポジトリへの操作も、入力が待機対象の結果に依存する場合は先行しない。

## 停滞の検知と巻き取り

- 委譲先とバックグラウンドタスクを停止するのは、ユーザーが即時の停止を明示的に求めた場合か、本節の手順で停滞を確定した場合に限る。進行が遅いことや手順が非効率なことは根拠にならない。停止を求める発話の解釈が複数残る場合は停止の前にユーザーへ確かめる（停止した作業は再開できず、途中の成果と観測を失う）
- 停滞を確定して停止する場合は、対象ごとに根拠を残してから停止する。Claude Codeでは`atk run-script record-stall-detection --`がその記録を作成し、終了コード0を返した対象だけを停止できる
- `show`か`list`が`status: running`とともに`api_error`を返す場合は、サーバーが同じsessionで作業を続けるため、催促、巻き取り、別engineへの再委譲をせず終端まで待つ。`api_error`が消えるか終端したら通常の判定へ戻る
  - Claudeの429の`rate_limit_error`: API失敗の合成メッセージはモデル活動時刻を進めないため、`seconds_since_activity`の増大は停滞の根拠から除く
  - Claudeの種別`usage_limit`: Weekly limitか5時間の利用上限の解除待ちであり、`resets_at`の後に同じsessionで続く。活動停止の長さを理由にCodexへ再委譲しない（ユーザー指示）。解除待ちの作業が不要になった場合だけ`kill`で保留中の結果を受け取る
  - Codexの種別`serverOverloaded`: 継続の`send_message`を控える。自動継続の上限に達すると失敗の終端結果が届くため、その時点で候補を変えて起動し直す
- 停滞の可能性に気付いたら`show`を1回発行する。`active_tool_uses`があり、前回と同じ呼び出しが同じ開始時刻で続いていれば長時間のコマンドの実行中として催促も巻き取りも保留する。`result_held`が真なら、委譲先はturnを終え、バックグラウンドタスクか子sessionの終端、または利用上限の解除を待って結果を保留している。この場合は`live_background_tasks`の`seconds_since_start`と`live_child_sessions`から待機を続けるかを判断し、後の結果が不要なら`kill`で保留中の結果を受け取る。保留中のsessionの確認には`show`を使う（新しいturnが始まる）。`active_tool_uses`が無く`seconds_since_activity`が停滞の可能性がある長さに達している場合だけ次へ進む
- 委譲先が所有する外部プロセスかバックグラウンドタスクの実行中は、成果物差分と実行識別子の直接照会の両方で判定し、生存中、識別子消失、終了後の結果未回収を区別する。外部実行を終了できるのは所有主体だけで、委譲元は生存中の処理を重複起動しない
- 間隔を空けた複数回の観測（別turnか次の定時起動）に差が無ければ継続を促し、それでも応答が無ければ未完了工程を巻き取るか、担当範囲を縮めた新規サブエージェントを起動し、観測結果をユーザーへ短く示す。成果物の更新が続く間と、更新元を別主体（CI、formatter、並行セッション等）と区別できない間は催促にとどめ、無変化が続いたら保留を解く（努力目標。回数と間隔は対象の性質で選ぶ）。Codexで`list_agents`が`running`を返す間は`references/codex-runtime.md`「後続操作の共通先行条件」に従い、巻き取り、新規起動、役割引継ぎを保留する
- 稼働中の同じ委譲先へ矛盾する差し替えを重ねそうになったら作業の保留を指示し、方針を確定してから旧方針との差分を統合した指示を1回で送る
- 明示した同じ制約への違反が繰り返される場合は、伝え直しの起動を繰り返さず、工程を巻き取るか別の手段へ切り替える（Codexでは`references/codex-runtime.md`「後続操作の共通先行条件」を先に適用する）。切り替える前に、違反が委譲先の出力と委譲元の判定条件のどちらに起因するかを実装で確かめ、委譲元に起因すれば判定条件を直す
- 巻き取る前に、委譲先自身のtranscript、委譲先が起動した子孫の記録、外部実行系のログを末尾に限って確かめる。完了報告を取得できれば再実装せずに検収し、公開され呼び出しが成功する`SendMessage`と保持済みIDで再開する。取得できなければ未完了の工程だけを巻き取り、担当範囲か権限の外なら続行できない理由を返す（Codexでは`references/codex-runtime.md`「後続操作の共通先行条件」を先に適用する）
- Codexの二層待機では、停滞の判定に内側の`atk agents wait`の状態を使う。外側の実行セルのyieldが続く間は巻き取り、代替起動、新規起動へ進まず、`codex-runtime.md`「agents_serverの二層待機」の手順で外側を再開する

## 成果物側の観測

委譲先が新規作成する成果物のパスは、委譲プロンプトで指定した値か委譲先が報告した値で確定し、共有出力ディレクトリの一覧と更新時刻はパス確定の根拠から除く。パスが未確定の間は成果物を観測せず、生存確認と完了通知を待つ。

成果物側の状況（作業ツリーの差分件数、HEAD、成果物ファイルの行数と最終更新からの経過時間）は`atk watch`の1回の呼び出しでまとめて得る（努力目標）。返るのは成果物側の値だけであり、生存中、識別子消失、結果未回収の区別には実行識別子の直接照会を使う。

- `atk watch`の差分件数とHEADは、並行セッション、CI、formatterなどを含む作業ツリー全体の値であり、生存や進捗の判定では他の観測と併用する。指定artifactの値もその書込主体に帰属させて補助観測として扱う
- 待機中の報告へ載せる観測値は、報告するエージェントが書き込む対象の値に限る。非担当対象の値を載せる場合は、それが判断を変える理由と実際の書込主体を併記する
