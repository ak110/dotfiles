# 待機と観測

委譲先の処理や、委譲を伴わないバックグラウンドタスクの完了を待つ際の観測手順、停滞の判定基準、および巻き取りの手順を定める。プロセスを終了させる操作の所有権については、`agent-toolkit/rules/02-agent-operations.md`の「プロセス終了の安全規定」に従う。

## 待機区間の構成

機械的な完了通知を待機の解除手段とし、シェルによる能動的な時間待ち（sleepなど）を禁止する。

完了通知によって同じセッションを再開できる待機は、対象の種類や件数、既存バックグラウンドタスクの有無、goalの有無にかかわらず、常にホストの背景実行機能を使って開始する。
Claude Codeでは`atk agents wait`、CIやデプロイ状態の監視、および終了条件ループをBashツールの`run_in_background=true`で起動し、先に届いた独立待機の通知から順に保存出力と終了状態を回収する。
起動済みの待機結果を受け取り、先に届いた通知に対応する工程から順次進める。
各待機や監視は単一の実行として管理し、別の待機が終わるまで前景やMonitorを占有し続けるような操作は避ける。
通知による自動再開に対応していない環境では、公開されている待機手段を用いて終端を確定させる。Codexのcell IDやコマンドsession IDは、前掲の表に示した回収手段を用いて同じターン内で回収する。

- `agents_server`の待機は`atk agents wait`だけで発行する
  - 待機対象、待機上限、委譲元の区分、応答後の破棄指定などの引数指定は避ける。対象は発行時点で全ルートに存在する起動中セッションと未回収結果の全体となり、上限はCLI側が自動で算出する
  - 外側の`timeout`コマンド、パイプ、`wc`などを連結せず、引数なしの単独コマンドとする。ホスト側ツールが持つ実行時間上限（Claude CodeのBashツールにある`timeout`引数など）も外側の上限に該当するため、背景実行時の扱いについては`agent-toolkit/rules/02-agent-operations.md`の「待機と背景実行」に従う。コマンドの連結や短すぎる外側の上限設定は、待機を途中で打ち切ってしまったり、終了コードを覆い隠してしまったりする原因になる
  - 続行の判断は終了コードと応答のみに基づいて行い、`status: running`が返ってきた場合は同じコマンドを再発行する。起動方法は本節に定める通知による再開のルールに従う
  - エージェント環境では、終端や通知の内訳と、上限サイズ内に収まる本文の要約が標準出力へ直接返される。各終端の結果本文は個別のファイルへ保存され、終端行の`agent_message_path`がその絶対パスを示す。要約に本文が含まれていない場合や、後続ターンでの再読・他者への引き渡しを行う場合は、そのファイルを直接参照する
  - 結果の回収処理は結果データや通知の削除を伴うため、背景処理へ移行した後も含めて、同一の結果を得るためのコマンドの重複再発行は避ける
- 観測処理が終端ステータスを返さずに戻った場合は、戻り方で分類する
  - 実行環境が観測を背景処理へ移行させ、その完了通知によって同じセッションが自動再開されると示されている場合に限り、同じ観測コマンドを再発行せずに待機状態を表明してそのターンを終える。背景処理への移行は、コマンド本来の待機上限とは独立して扱われる。なお、Codexのcell IDや`exec_command`のsession IDは環境全体の機能通知だけでは自動再開されないため、前掲の表に示した手段で同じターン内に回収する
  - 観測処理が自身の待機上限に達して戻り、背景処理への移行も示されていない場合は、同じターン内で再発行してよい。再発行する前に「待機中の先行実施」に該当する工程を先に進め、進められる工程がなくなった後も終端しない場合は、通知によって再開できることを確認したうえで完了通知や定期的な再確認に処理を委ねる
  - 同じターン内で再発行してよいのは、1回の呼び出し自体が待機時間を消費する観測手段に限られる。待機時間を消費しない状態照会を何度も繰り返す行為は、単に補助的な観測値を更新し続けるだけのポーリングとなってしまうため避ける
- 自身が直接起動していない子孫プロセスの完了通知は、直接の子プロセスへ中継した時点でその工程が再開される。中継処理はホストごとの委譲契約（Claude Codeでは`references/claude-code-runtime.md`の「完了通知と中継の実行順」）に従う
- プロセスの生存状態や対象の判別は、起動時に得られた識別子、完了通知、および成果物側の状態確認手段を用いて判定する。更新時刻、末尾の標識、`git log`、`git status`などはあくまで補助的な情報として扱う
- 目標評価（`/goal`）の発動条件は`agent-toolkit/share/rules-main.claude-code.md`に従う。`agents_server`の委譲先はそれぞれ独立したセッションであり、各セッションの判定対象には自身が起動したタスクのみが含まれる。待機の起動や結果回収の処理をgoalの有無で分岐させず、本節の共通ルールに従って進める。異常終了が発生した場合は`references/wait-anomalies.md`に従う
- 待機表明してターンを終えた委譲先が再開される契機は、起動形態によって異なる。`Agent`ツールによるサブエージェントは、バックグラウンドタスクの完了通知によって再開される。`agents_server`の委譲先が起動した別の`agents_server`セッションは両バックエンドによって追跡され、追跡対象がすべて終端するまで最初の結果が保留され、そのターンにつき1回だけ同じセッションが自動再開される。Codexバックエンドでは、組み込み委譲で起動した子スレッドも同様に保留と自動再開の対象となる。Claudeバックエンドでは、背景実行されたシェル、背景のAgent委譲、背景へ移行したMCPツール呼び出しも自動再開の対象に含まれる。自動再開が行われるのは、対象となる子セッション、子スレッド、バックグラウンドタスクを実際に起動した場合に限られる。これらを起動せずに待機表明だけを行った場合は、委譲元が完了を確認して再開を指示する。監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：待機区間の構成：2026年9月3日」を参照する
- 委譲元は自動再開の要否を独自に判断せず、自動再開の仕組みに委ねる。`atk agents wait`は、再開されたターンの終了まで待機してから結果を返す。応答が待機表明であるかどうかは、CLIの応答内容から判別できる（同様の文面が完了報告にも現れる）。`終端行:`に`unfinished_waits`が含まれる結果（`error`の`heldResultFinalized`が真）は、待機対象が残っている状態で保留を打ち切った待機表明であるため、再開したターンの最終的な返却値から除外する。残っている対象の状態を確認したうえで、同じセッションへ続きの処理を依頼する。判別には`unobservedSessions`の有無以外の情報も併用する
- `show`が返す停滞診断や子セッション一覧、`send_message`が返す`delivery`の意味は、各MCPツールの仕様に従う。実行時間の長いコマンドを実行中である場合は、催促や巻き取りの判断を保留する。停滞の兆候は委譲先の状況を調査する契機として扱い、実際の確定と巻き取りの手順は「停滞の検知と巻き取り」に従う

子セッション、子スレッド、背景エージェントが生存している間は、待機表明の保留と終端後の自動再開が維持される。利用上限の解除を待機している子プロセスにも同様の扱いを適用する。実行時間の上限が保証されている背景コマンドについては、その上限に基づいて通知喪失を診断し、明示的な中断や追跡先の喪失、再開失敗が発生した場合はそれぞれの診断手順から回復を図る。

## 長時間待機前の会話圧縮

Claude Codeのメインエージェントが、他の担当者やCI監視の結果を後続工程の入力として待つ際の共通手順である。圧縮を予約するタイミングと保存すべき工程状態は、呼び出し元の工程手順に従う。
独立して実行できる先行工程を先に開始し、工程の状態をセッションのmanaged-temp直下にある`parent-handoff.md`へ保存してから待機へ進む。圧縮が行われた後は、managed-tempの通知からこの固定ファイル名を探し出し、担当別の記録、選定内容、監視状況、保存出力などをそこに記載された参照先から取得する。

1. `mcp__agent-toolkit__compact_conversation`が存在しない環境では、前提が成立しなかった旨を引き継ぎ記録に残したうえで通常の待機へ進む。なお、Codexは本手順の対象外とする
2. 対象ツールを引数なしで1回呼び出す。予約の受付と圧縮の完了を区別し、圧縮が完了するまで予約は1件のみに維持する。Claude CodeのFunction hooks moduleは追加の指示を与えずにターン間で`session.compact()`を実行するため、予約入力は空のまま保持する
3. `agents_server`の結果を待つ区間では、引数を指定せずに単独の`atk agents wait`をBashのバックグラウンドタスクとして起動する（`session_id`は結果の突き合わせにのみ使用し、待機コマンドの引数からは除外する）。CI監視を待つ区間では、すでに起動している`wait_ci.py`のバックグラウンドタスクをそのまま維持し、新たな監視タスクの追加は避ける
4. Monitorツールで前景を占有することなく現在のターンを終了し、届いた完了通知と保存された全出力から待機の終了状態を回収する
5. 完了通知を受け取った後は`parent-handoff.md`を読み込み、保存されていた内容と受け取った結果を突き合わせて同じ工程から作業を再開する。会話圧縮が失敗した場合でもこの記録から状態を復元し、既存の担当作業や監視を継続する。予約の失敗、圧縮の成功、待機結果はそれぞれ個別に記録する

Claude Codeのメインエージェントが背景のBashで単独の`atk agents wait`を起動した場合は、フックモジュールが同じ圧縮予約に接続する。
バックグラウンドタスクが5秒以上継続しており、コンテキスト利用率が50%以上で、ターン間であり、かつ現在のターンの状態が`parent-handoff.md`へ保存されている場合に限り、自動圧縮が実行される。
あわせて、待機所有の登録状況と起動区分を確認し、自身が待機しているexploreやshell以外の担当タスクが残っていることも確かめる。これらの状態確認は、既存の記録を一度読み取る`atk run-script wait-compaction-context`が担当する。
同一の背景待機における圧縮は1回までに制限し、圧縮が成功した後にコンテキスト利用率が高いまま推移しても、その待機中に再圧縮することは避ける。利用率が閾値未満に下がったことを確認した後の新たな作業であれば、再び圧縮の対象とできる。
スキップや失敗が発生した場合は予約を解除して通常の結果回収を継続し、同一の背景待機に対する自動再試行は除外される。
単発タイマーやターン完了通知を活用し、不要な継続ポーリングや圧縮のためだけのLLMターンを追加しないようにする。Codex環境では、ホスト標準の圧縮機能と同じ状態復元手順を利用する。

## `atk agents wait`の応答の扱い

バックグラウンドタスクとして実行中の`atk agents wait`が完了していない間の進捗状況は、listやshowによる活動情報で確認し、出力途中の内容は進捗情報として扱う。最終的な終端結果は完了通知を受け取った後に出力全体を改めて読み取って回収し、同じ結果を得るためのwaitコマンドの並行重複実行は避ける。Codexのcell IDやsession IDについては、前述のとおり同一ターン内での回収手順に従う。
公式資料と開発元ホストでの観測記録は、`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：進捗照会と結果回収：2026年10月10日」にある。

- 応答各行の形式（JSON Lines、`session_id`、`label`、`agent_message_path`、`終端行:`の要約行）や待機が成立したかどうかの判定基準は、CLIの`--help`に従う。どの依頼に対応するかは`label`で判別し、失敗で終了した行については要約行の`error`で原因を確認して`next_action`の指示に従う。結果を正常に回収できなかった終端セッションの原因は、`show`の`error`情報で確認する
- 同一の書き込み主体による`atk agents wait`がすでに稼働している場合、後発のプロセスは`current.json`に示されるrun識別子を固定して保持し、先行する待機のロックが解放された後にそのrunが保存した本文と終了コードを返す。ロックを取得する前にCLIが算出する1回分の待機期限が開始され、この期限はロック取得待ちと取得後の結果待ちの双方で共有される。正常な長時間待機、ホストセッション識別子の別名、対象セッションの追加に伴う合流にも同一の期限が適用され、ロック競合が期限まで解消しなかった場合は終了コード8と固定runの診断情報を返す。前景のCLIが本文を返した後の逐次待機は新しいrunへ進み、先行CLIが稼働中にlock競合した後発待機だけが先行runの本文を1回回収する。バックグラウンドタスクの完了通知が届いた後も先行する実プロセスが一時的に残存することがあり、その間に起動した後続の待機も同様に先行runの結果を回収する。期限に達した際の復旧手順は、`references/wait-anomalies.md`の「終了コードと呼び出しの失敗」に従う
- 待機上限に達したことを示す終了コード3が返された場合は、`status`が`running`である応答と同様に扱い、同じコマンドを再発行して待機を継続する
- 取得した行に`notices`が含まれている場合は、その`session_id`を持つ委譲先から実行中に届いた即時通知として受け取り、本文を保持する（同一の通知が返されるのは1度だけである）。待機を継続すべきかどうかは行の`status`で判定し、終端行が含まれていない場合は同一ターン内でコマンドを再発行する。終端ステータスを示す行を受け取った場合は完了報告として扱い、そのセッションを未終端の対象一覧から除外する
- `agents_server`は終端結果を経過時間だけで破棄することはなく、結果本文を配送した後、または`stop`によって明示的に破棄された後にのみ解放する。そのため、完了通知を受け取ってから時間が経過していたとしても、終端状態と結果本文を確実に回収できる

## 外部サービスの状態変化を待つ場合

待機を開始する前に、待機によって得られる結果がすでに収集した証拠や次の必須工程の判定に対して不足しているかどうかを比較する。既存の情報で十分に判断できる場合は待機せず、`agent-toolkit/rules/01-agent.md`の「行動と手順の目的」に従って工程を省略し、その旨を報告する。

CIの完了やデプロイの反映などを待つ際は、終了条件が満たされた時点で終了し、その際に一度だけ結果を返す起動形態で待機する。固定時間で待機するのは、所要時間が確定しているごく短い待ち時間（数秒程度のレート制限など）に限るものとし、`sleep`コマンドに状態確認を連結して繰り返すような待機方法は用いない（待ち時間を浪費するうえ、適切な中断契機を失ってしまうためである）。

- CIやReleaseワークフローの完了待機は、`agent-toolkit:commit`の`references/push-and-ci.md`の「pushと監視」に定める手順に従って実施する。ベースラインが存在しない公開後のRelease確認などでは、同節で説明されている完全長SHAによる`--wait-sha`オプションを使用する
- 対象サービスのCLIに終了条件付きの待機機能が用意されている場合は、その機能を優先して使用する
- いずれの機能も提供されていない場合は、`agent-toolkit/rules/02-agent-operations.md`「待機と背景実行」の終了条件ループを用いる。照会成功による未完了、照会失敗、時間上限到達を区別する構成とし、同節の時間上限を設けてホストの背景実行として起動し、完了通知によって待機を解除する。時間上限に達して終了し、かつ状態照会には成功して処理が未完了であることが示されている場合に限ってループを再起動する。照会自体が失敗して終了した場合は、保持されている診断情報から原因を確認したうえで、待機手段を選び直す
- 待機の解除条件がユーザーからの入力や外部インフラの復旧である場合は、定期起動のタイミングごとに条件の成立を確認する。保存済みUWIへの回答が得られたかどうかは`atk wi list --type=uwi --answered=yes`の出力に対象のファイル名が含まれているかで判断し、インフラの復旧については公開されている状態照会機能や対象ジョブの再確認によって判定する
- 状態照会の間隔は、残っている解除条件の種類（ユーザーが応答可能な時間帯や頻度、公開された復旧見込みと照会に伴う負荷、通常の完了までの所要時間とAPIのレート制限など）を考慮して設定し、条件の種類が変化した場合は設定を見直す

## 背景ジョブの起動形（Claude Code）

- 待機処理の起動方法は「待機区間の構成」に従う。待機以外の検証やビルドなど、実行に時間を要する通常のコマンドは、Bashツールのタイムアウト引数を上限まで引き上げたうえで前景実行するのが基本であり、その時間内に収まらない場合は対象を絞り込んで複数回の前景実行に分割する
- 待機は完了通知や定期的な再確認を通じて処理し、Monitorや完了マーカーを用いた前景でのループ処理への回帰は避ける。待機以外のバックグラウンドタスクで全出力を取得する用途にはMonitorを利用できる。また、ツール側で背景実行を指定したコマンドに対して、さらにシェル上で`&`や`nohup`を重ねない（シェルの終了が先に完了通知として届いてしまうためである）
- リモートホスト上で`nohup`や`setsid`を使ってプロセスを切り離す起動方法は、完了通知を受け取れないため、エージェント自身が一時的に応答不能となる工程に限って使用する。それ以外の処理では、`run_in_background=true`でSSH接続を維持するか、対象を絞り込んだ前景実行とする
- コマンドの終了状態と出力内容は、起動時の結果に含まれる出力ファイルの絶対パスから取得する。このファイルは実行識別子とは独立してディスク上に残り、出力の全量と`[exited with code <整数>]`という形式の終了状態行を含んでいる（実行識別子自体は実行環境の再起動によって失効する）。監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」にある。同じ文の記録は「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月4日」にもある。待機タスクを別のセッションやエージェントへ引き継ぐ場合は、このファイルパスもあわせて引き継ぐ。監査記録は`docs/development/audit-records.md`に記載されている。対象見出しは「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」および「2026年9月4日」である
- 処理が完了したか失敗したかは、保持している実行識別子によるプロセスの生存確認と、出力ファイル末尾の終了状態行によって判定する。出力ファイルが空の場合は判定を保留する。自身が所有するタスクであっても、再起動や巻き取りを行う前に生存状態を確認し、プロセスが生存している間における同一処理の重複起動は避ける。完了通知と実際のプロセス終了の順序関係については、`references/claude-code-runtime.md`の「背景ジョブ完了通知と実プロセスの終了順」を参照する。ホストからの停止通知を受けた場合は、`references/wait-anomalies.md`の「ホストによる背景待機の停止後」に従って元の待機状態と出力を回収する

## 待機の起動条件

- 起動手段と終端観測手段の組み合わせは、起動前に`references/runtime-routing.md`の「実行手段」に従って決定する
- 完了通知を受け取る手段が実際に存在し、通知を受けた後に処理を再開できることを待機開始前に確認する。通知を受け取れない対象は待機対象に含めず、検収済みの状態を引き渡したうえで新規起動する（Codex環境では`references/codex-runtime.md`の「後続操作の共通先行条件」を事前に適用する）
- 終端ステータスを返しながらもタスク契約で定められた返却値が含まれていない終了は、未完了として扱う。終了したターンはそれ以降通知を発しないため、そのまま待ち続けることはせず、保持している識別子を使って同じセッションへ継続処理を要求し、返却値を取得する。委譲先が自身の子プロセスの終了を待たずにターンを終えてしまった場合も同様に扱う（なお、`agents_server`の両バックエンドは子プロセスの生存中は終端結果を保留するため、この起動形態ではその事象の発生を防止できる）
- 完了通知が届かない場合は待ち直さず「停滞の検知と巻き取り」へ進み、保持している識別子を使って対象の状態を直接照会する

### 再照会の抑制と待機中の作業

- 前回と同じ結果が返ると見込まれる状態照会を無駄に繰り返すことは避け、完了通知が届かない場合や、終端ステータスを確認する場合、定時起動の各回など、状態が変化する可能性のある契機に限って照会する
- 待機中には、待機対象とは独立した別の作業を進める。広範囲にわたる未完了の調査を単一の委譲先へまとめて再委譲するのではなく、独立した作業単位ごとに完了結果を個別に受け取って統合する

## 完了通知を待ってターンを終える場合

- 1回のブロッキング待機（`atk agents wait`またはそれを起動したバックグラウンドタスク）は、発行時点で委譲元が保持していた起動中セッション全体を、終端ステータスを返すまで所有して管理する。定期再確認では、所有されている対象の観測をブロッキング待機に委ね、所有されていない対象については記録側の状態や完了通知、および経過時間起動の義務のみを確認する。完了通知の不着が検出された対象や、待機手段が終端ステータスを返さずに失敗した対象は、所有されていないものとして扱う。上限到達により`running`を返したブロッキング待機の再発行は「待機区間の構成」に従う
- 定期再確認は、Claude Codeでは`references/claude-code-runtime.md`「待機中の定期再確認と背景転換」に従い、委譲先やバックグラウンドタスクを実際に起動したセッションにのみ設定する。`start`の結果を受け取った時点でFunction hooks moduleによる定期再確認の設定は完了している。自身で明示的に設定する場合も、起動の直前または通知を受け取った直後に設定する（設定までの間隔が空くと、停滞や外部ジョブの終了を検出する主体が存在しない期間が生じるためである）
- 作成済みで未回答のUWIを保持しているセッションは、経過時間起動の各回で`atk wi`を使って回答の有無を確認し、回答が得られている場合は同じターン内で元の作業へ反映する（この契機がないと、ユーザーが会話を通じて通知するまで作業工程が停止してしまう）
- 子孫プロセスの完了通知を直接の委譲元以外のエージェントが受け取った場合の中継、再送、巻き取りの手順は、`references/claude-code-runtime.md`の「完了通知と中継の実行順」に従う
- 完了通知が届かない場合は「停滞の検知と巻き取り」へ進み、成果物ファイル、委譲先が起動した子プロセスのトランスクリプト、および委譲先自身のトランスクリプトの最終更新時刻を実際に取得して確認する。終了の判定には実行識別子の直接照会も併用し、委譲先が起動したプロセスがすでに終了していると誤認して、同じ工程に複数のエージェントを誤って接続しないようにする
- 定時起動の依頼文には、現在の作業状態を正しく記録している情報源（計画ファイル、引き継ぎ記録、作業ツリー、タスク一覧など）から状態を読み直す手段のみを記載し、待機対象ID、成果物の絶対パス、コミット識別子、残工程や完了済み工程そのものは書き込まないようにする（努力目標）
- 定時起動が発火しても停滞時間の起点は更新されず、停滞判定は実際の観測値に基づいて行う
- ターンを終了する直前には成果物側の状態を観測し、前回から値が変化していれば、その値と待機を継続する理由をユーザーへ簡潔に説明する（努力目標）。稼働状態の照会は、停滞を判定する回と、催促や巻き取りの要否および宛先を確定する回に限って発行する

Claude CodeのStop時に未配信の完了通知が存在し、他のagent-toolkitのチェックがブロックを返していない場合は、現在のターンを終了し、通知の配信に伴う次のターンで保存出力と終了状態を受け取る。他のブロックが残っている場合に限ってその要因を解消しつつ、結果受け取りに関する警告に従う。同一の結果を得るための待機コマンドの重複再発行は避ける。

待機のみを理由としてターンを終了する際の出力内容は以下のとおりとする。自動再開の対象には、自身が`agents_server`で起動した委譲先セッション、Codexの組み込み委譲で起動した子スレッド、およびClaude Codeの通知付きバックグラウンドタスクが含まれ、Codexのcell IDや`exec_command`のsession IDは対象外となる。本表の内容を変更する場合は、各エージェントに届くエージェント向け文書（表中の参照先）もあわせて更新する。

| エージェント | 同じセッションの自動再開あり | 自動再開なし |
| --- | --- | --- |
| メイン | 本文を空にする。空の応答をホストが再生成させる場合（Claude Code）は`…`のみを出力する（`share/rules-main.md`「ユーザー向け発話ルール」、`share/rules-main.claude-code.md`） | 同左（メインは完了通知によって再開される） |

## 待機中の先行実施

待機中には、委譲先の担当範囲と競合せず、かつ待機対象の結果を着手条件や入力として必要としない後続工程をすべて先行して実施する（努力目標）。競合するかどうかは、委譲先の変更説明と実際の差分を突き合わせて判定し、読み取り専用の調査作業は競合しないものとして扱う。別リポジトリに対する操作であっても、待機対象の結果を入力として利用する場合は先行実施の対象外とする。

## 停滞の検知と巻き取り

- 委譲先やバックグラウンドタスクを停止するのは、ユーザーが即時停止を明示的に求めた場合、または本節の手順によって停滞が確定した場合に限る。単に処理の進みが遅いことや手順が非効率であることは停止の根拠から除外される。停止を求めるユーザー発話に複数の解釈が成り立つ場合は、停止を実行する前にユーザーへ確認する（停止した作業は再開できず、そこまでの成果や観測情報が失われてしまうためである）
- 停滞を確定して停止する場合は、対象ごとにその根拠を記録してから停止する。Claude Codeでは`atk run-script record-stall-detection --`がその記録を作成し、終了コード0を返した対象のみを停止できる
- `show`や`list`の出力で`status: running`とともに`api_error`が返されている場合は、サーバー側が同一セッションで作業を継続するため、催促や巻き取り、別エンジンへの再委譲をせずに終端まで待機する。`api_error`が解消されるか終端に達した段階で、通常の判定手順へ戻る
  - ClaudeのAPI再試行: 合成assistantメッセージや`api_retry`はモデルの活動時刻を進めないため、`seconds_since_activity`の増加は停滞の根拠から除外する。`retry_at`に示される次回の再試行予定時刻を確認し、HTTP 429以外のエラーであっても同じセッションの終端まで待機する
  - Claudeの`usage_limit`: Weekly limitまたは5時間の利用上限に達したことを示す。`claude_usage_limit_wait`の設定に従い、同じ会話内で後続のAPIへ切り替えるか、`resets_at`の時刻が経過した後に同じセッションで再開する。設定が省略されている場合は、5時間の上限解除を待つ。活動停止期間が長いことだけを理由にしてCodexへ再委譲しない（ユーザー指示による）。作業自体が不要になった場合に限り、`kill`を発行して停止結果を受け取る
  - Codexのターン内再試行: `willRetry: true`の通知に含まれる種別とHTTPステータスを確認する。追加のメッセージ送信は控え、モデルの活動によって`api_error`が解消されるかターンが終了するまで待機する
  - Codexの`serverOverloaded`によるターン終了後の自動継続: 継続を促す`send_message`の送信は控える。自動継続の上限回数に達すると失敗の終端結果が届くため、その時点で別の候補へ切り替えて再起動する
- 停滞の兆候が見られた場合は、まず`show`を1回実行する。`active_tool_uses`が存在し、前回と同じツール呼び出しが同一の開始時刻のまま継続している場合は、長時間のコマンドを実行中であると判断し、催促や巻き取りを保留する。`result_held`が真である場合は、委譲先がターンを終えており、バックグラウンドタスクや子セッションの終了、または利用上限の解除を待って結果を保留している状態である。この場合は`live_background_tasks`の`seconds_since_start`や`live_child_sessions`を確認して待機を継続するか判断し、後続の結果が不要であれば`kill`を発行して保留中の結果を受け取る。なお、保留中のセッション状態を確認する際は`show`を使用する（新規のターンが開始されるのを防ぐため）。`active_tool_uses`がなく、かつ`seconds_since_activity`が停滞を疑うに足る時間に達している場合に限って、次の手順へ進む
- 委譲先が所有している外部プロセスやバックグラウンドタスクが実行中であるかどうかは、成果物の差分確認と実行識別子の直接照会の双方を用いて判定し、生存中、識別子の消失、終了後の結果未回収の各状態を明確に区別する。外部実行プロセスを終了できるのはその所有主体に限られるため、委譲元による生存中の処理の重複起動は避ける
- 時間間隔を空けた複数回の観測（別ターンや次回の定時起動）を行っても状況に変化が見られない場合は継続を促し、それでも応答が得られない場合は未完了の工程を巻き取るか、担当範囲を絞り込んだ新規サブエージェントを起動して、観測結果をユーザーへ簡潔に報告する。成果物の更新が続いている間や、更新元が他の主体（CI、フォーマッター、並行セッションなど）と区別できない間は催促にとどめ、変化がない状態が続いた段階で保留を解除する（努力目標。確認回数や間隔は対象の特性に応じて調整する）。Codex環境で`list_agents`が`running`を返している間は、`references/codex-runtime.md`の「後続操作の共通先行条件」に従い、巻き取り、新規起動、および役割の引き継ぎを保留する

更新元を別主体と区別できないことだけを理由とした保留は、観測値が30分間にわたって変化しなかった場合に解除し、催促へ進む。この基準はあくまで催促する契機であり、プロセス停止や巻き取りを自動的に行う期限とは区別される。API再試行や利用上限の解除待ち、実行中のツール、保留中の結果、および所有する外部処理の実行中に対する既存の保留条件や、Codex固有の終端・後続操作条件は、引き続き優先して適用する。

- 稼働中の同一の委譲先に対して矛盾する指示の差し替えを重ねそうになった場合は、いったん作業の保留を指示し、方針を確定させたうえで、旧方針との差分を統合した指示を一度にまとめて送信する
- 明示した制約への違反が同一の委譲先で繰り返される場合は、指示を何度も再送して起動を繰り返すのではなく、その工程を巻き取るか別の手段へ切り替える（Codex環境では`references/codex-runtime.md`の「後続操作の共通先行条件」を事前に適用する）。切り替える前に、違反の原因が委譲先側の出力にあるのか、それとも委譲元側の判定条件にあるのかを実装コード等で確認し、委譲元に起因する場合は判定条件を修正する
- 巻き取りを行う前には、委譲先自身のトランスクリプト、委譲先が起動した子孫タスクの記録、および外部実行系のログについて、末尾の最新部分を必ず確認する。完了報告がすでに取得できる状態であれば再実装せずにそのまま検収し、公式に提供され呼び出しが成功する`SendMessage`と保持しているIDを用いて処理を再開する。完了報告を取得できない場合は未完了の工程のみを巻き取り、担当範囲や権限の外にある作業であれば続行できない理由を委譲元へ報告する（Codex環境では`references/codex-runtime.md`の「後続操作の共通先行条件」を事前に適用する）
- Codexにおける二層待機の識別子保持、外側セルと内側の`exec_command`のyield処理中における結果回収、巻き取り・代替起動・新規起動の扱いについては、`codex-runtime.md`の「agents_serverの二層待機」に従う

## 成果物側の観測

委譲先が新規作成する成果物のパスは、委譲プロンプトで指定した値、または委譲先が明示的に報告した値に基づいて確定する。共有出力ディレクトリの一覧や更新時刻はパス確定の根拠から除外する。パスが確定していない間は成果物を直接観測せず、プロセスの生存確認と完了通知の到着を待つ。

成果物側の状況を確認するコマンドとして、作業ツリーの差分取得には`git -C <worktree> status --porcelain=v1`、HEADの取得には`git -C <worktree> rev-parse --short HEAD`を用いる。成果物ファイルの行数は`wc -l -- <file>`、最終更新日時は`stat -L -c %Y -- <file>`（macOSでは`stat -L -f %m -- <file>`。エポック秒）で取得する。これらのコマンドは成果物側の静的な状態値のみを返すため、対象が生存中なのか、識別子が消失したのか、あるいは終了後の結果が未回収なのかを区別するには、実行識別子の直接照会を併用する。

- 差分やHEADの値は、並行セッションやCI、フォーマッターなどによる変更も含めた作業ツリー全体の状態を反映しているため、生存確認や進捗判定においては他の観測手段と組み合わせて判断する。指定された成果物（アーティファクト）の値についても、実際の書き込み主体に対応付けて補助的な観測情報として扱う
- 待機中の報告に記載する観測値は、報告するエージェント自身が書き込みを担当している対象の値に限定する。担当外の対象に関する値を記載する場合は、その値が判断に影響を与える理由と、実際の書き込み主体をあわせて明記する
