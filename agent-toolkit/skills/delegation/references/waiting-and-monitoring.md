# 待機と観測

委譲先または背景ジョブの完了を待つ際の観測、停滞判定、巻き取りを定める。

委譲先の完了を待つ場合と、委譲を伴わない背景ジョブの完了を待つ場合の双方へ適用する。
プロセスを終了させる操作の所有権規定は
`agent-toolkit/rules/02-agent-operations.md`「プロセス終了の安全規定」節を正本とする。

## 待機区間の構成

- 機械的な完了通知の受領を待機解除の既定手段とする。シェルコマンドによる能動的な時間待ちは行わない
- 観測手段が終端statusを返さずに制御を戻した場合は、戻り方で継続と終端を分ける。
  実行環境が当該観測を背景処理へ移し、完了時に通知すると戻り値が示す場合は、同じ観測を再発行しない。
  待機表明でターンを終え、当該通知の受領で再開する。
  待機表明でターンを終えるセッションに`/goal`が設定され、かつ当該セッションの未完了の背景タスクが当該観測の背景移行だけである場合は、本項に代えて後述の目標評価の条項を適用する。
  2026年9月、Claude Codeで`agents_server`の`wait`が発行から120秒で背景タスクへ移り、完了時に当該タスクの通知として結果本文が届くことを実測した。120秒は背景タスクへ移行する閾値であり、待機の上限ではない。
  再検証は`wait`を発行し、背景移行の通知を受領した後に完了通知の到達を確認する
- 完了通知の経路が確立しない戻り方では、同じターン内で当該観測を再発行してよい。
  観測が自身の待機上限に達して終端statusを返さずに戻り、実行環境が背景処理への移行を示さない場合が該当する。
  再発行の回数に上限は設けない
- 再発行の前に`待機中の先行実施`の対象工程があれば実施する。
  先行して実施できる工程が尽き、かつ再発行した観測も終端statusを返さない場合は、待機表明でターンを終えて完了通知と定期再確認の経路へ委ねる
- 再発行できるのは、1回の呼び出しが待機時間を消費する観測手段に限る。
  待機時間を消費しない状態照会の反復は、補助観測だけを更新する同一turn内のポーリングに当たるため行わない
- 自身が起動していない子孫の完了通知を受領した場合は、直接の子へ中継しなければ当該工程は再開しない。
  中継の要否と手順は実行ホストの経路契約に従う（Claude Codeでは`references/claude-code-runtime.md`の
  「完了通知と中継の実行順」を正本とする）
- 起動前に、自身のツール一覧で稼働状態の照会手段と停止手段の可用性を確認する。
  Claude Codeでは`ListAgents`と`TaskStop`が実行主体へ公開され、呼び出しに成功する場合だけ後続手順へ用いる
- 稼働状態の照会手段と停止手段のいずれかが公開されないか呼び出しを拒否された場合は、起動結果が返した識別子を保持する。
  完了通知、成果物側の状態確認手段及び自身が起動して識別子を保持したプロセスの生存を照合する。
  プロセス名の一致だけから生存状態又は対象を推定しない。
  成果物側の状態確認手段で回数上限付きで観測し、上限到達後は取得できた実測を添えて継続か停止かを判断する。
  成果物の更新時刻や末尾標識だけで完了を判定しない
- `agents_server`の`wait`では、委譲先の終端を待つ場合に`timeout`を省略し、サブエージェントは`request_bucket`へ`subagent`を渡す。所要時間の見込みを自ら見積もって値を渡さない。次項の目標評価の条項が前景の待機を求める場合だけ、背景移行の閾値より短い値を`timeout`へ渡す
- 目標評価の発動は、`/goal`が設定されたセッションごとに、当該セッション自身が起動した未完了のタスクだけを入力として判定する。
  別のセッションが起動したタスクは当該セッションの判定へ入らない。
  `agents_server`の`start`で起動した委譲先は独立したセッションとして動くため、委譲先の判定には委譲先が起動したタスクだけが入り、呼び出し元の判定には呼び出し元が起動したタスクだけが入る。
  `/goal`が設定されたセッションでターンを終えた時点で、当該セッションが起動した未完了のAgent系タスク又はBash背景ジョブが1件も無い場合に目標評価が発動する。
  当該セッションのAgent委譲とBash背景ジョブのいずれかの完了を待つ場合は、待機表明でターンを終える手順をそのまま用いる。
  当該セッションの未完了の背景タスクがMCPツールの背景移行だけである場合は、背景移行の閾値より短い`timeout`を渡した`wait`を同じターン内で再発行し、前景の待機として繰り返す。
  発動条件は`agent-toolkit/rules/99-claude-code.md`の`/goal`の条項を正本とする
- 待機表明で終端した委譲先が再開する契機は、当該委譲先の起動経路で異なる。
  実行環境の`Agent`ツールで起動したサブエージェントは、背景ジョブの完了通知で再開する。
  `agents_server`の`start`、`start_explore`及び`start_shell`で起動した委譲先は、呼び出し元のサブエージェントではなく独立したセッションとして動く。
  当該セッションが背景タスクを起動して待機を表明した場合は、当該タスクの完了で同じsessionが一度だけ自動的に再開し、`wait`が再開したturnの結果を返す。
  背景タスクに当たるのは、背景実行したシェルのコマンド、背景で起動したAgent委譲、及び背景へ移行したMCPツールの呼び出しである。
  背景タスクを起動せずに待機を表明した場合は再開しない。この場合の待機対象の完了確認と再開指示は呼び出し元が行う。
  2026年9月3日から9月4日にかけて、`agents_server`の`start`で起動した委譲先が外部コマンドの完了待ちを表明して`status: completed`で終端し、当該コマンドの終了後も再開しない事象を実測した。
  2026年9月4日には、同じ経路で起動した委譲先が自ら起動した委譲先の終端を待たずに待機表明で終端し、呼び出し元が保持した`session_id`へ`send_message`を送って再開させた事象を実測した。
  再検証は`agents_server`で委譲先を起動し、待機表明で終端させたうえで、完了通知の到達を確認する
- 呼び出し元は、前項の自動再開について再開の要否を判断せず、`send_message`による再開指示も送らない。
  `wait`は再開したturnの終端まで待ち、その結果を返す。
  委譲先の最終メッセージの文面から待機表明を読み取って判別しない。
  同じ文面が作業の完了報告としても現れるため、文面による判別は誤った再開と再開漏れの双方を生む
- 1回の`wait`が待てる長さには、実行環境がMCPサーバーへ課すアイドル上限が別に働く。Claude Codeのstdioサーバーの既定は30分であり、`timeout`の省略時にサーバーが導出する上限はこれより短い。終端前に`status: running`が返った場合は、同じ`session_id`へ`wait`を再発行して待機を継続する。1回の待機で終端まで待てない所要時間の委譲先は、この再発行を繰り返して待つ

## 外部サービスの状態変化を待つ場合

CIの完了、デプロイの反映など、外部サービスの状態が変わるまで待つ場合は、終了条件の成立で終端し、その時点で1回だけ結果を返す起動形を選ぶ。
固定時間の`sleep`と、`sleep`へ状態確認コマンドを連結した反復のいずれも用いない。

- CIの完了は、`agent-toolkit:commit`の`references/push-and-ci.md`が定めるbaseline作成と監視の手順で待つ。同書が起動形、引数及び終了コードの意味の正本である
- 対象サービスのCLIが終了条件付きの待機を提供する場合は当該手段を使う
- いずれも利用できない場合は、`until <終了条件のコマンド>; do sleep <秒数>; done`の形で終了条件により終端するループを構成し、実行ホストが提供する背景実行の指定で起動して、その完了通知で待機を解除する。ループ本体の外へ`sleep`を置かない

## 背景ジョブの起動形（Claude Code）

- `run_in_background=true`の長時間ジョブは`Monitor`で全行取得するか完了マーカーを`grep -q`で待つ。
  マーカー未生成の背景タスク完了検出目的では`Monitor`を起動しない。
  ツール側で背景実行を指定したコマンドはシェル側を前景のまま保ち、末尾の`&`や`nohup`を重ねない。
  二重に背景化するとシェルの終了が完了通知となり、実ジョブの完了を検知できない
- 完了までに時間を要するコマンドは、Bashツールのタイムアウト引数を上限まで引き上げた前景実行を既定とする。
  上限時間内に収まらない場合は、実行対象を限定して複数回の前景実行へ分ける
- 遠隔ホスト側で`nohup`又は`setsid`により切り離した起動は完了通知経路を持たないため、実行主体自身が応答不能になる工程だけに用いる。
  それ以外の遠隔ホストの長時間コマンドは、`run_in_background=true`でSSH接続を保持するか、対象を限定した前景実行とする
- 空の出力ファイルは完了・失敗の根拠にしない。自己所有の背景ジョブも、再起動・巻き取りの前に
  保持した実行識別子で生存を照会し、生存中は同じ処理を重複起動しない
  （厳守規定。実行中の背景ジョブを空出力だけで終端と誤認しないため）
- 背景ジョブの終了状態と出力は、起動結果が返す出力ファイルの絶対パスから取得する。
  当該ファイルは実行識別子から独立して残り、出力の全量と`[exited with code <整数>]`形式の終了状態行を保持する。
  実行識別子を入力とする観測手段だけに依存しない。
  待機が別のセッション又は別の実行主体へ渡る場合は、当該絶対パスを引き継ぐ対象へ含める
  （厳守規定。実行識別子は実行環境の再起動で失効し、失効後は当該識別子から終了状態と出力を取得できない）。
  2026年9月4日、Claude Code 2.1.260で次の2点を実測した。
  終了コード7で終わる`run_in_background=true`のBashについて、起動結果が返した出力ファイルは出力の全量と`[exited with code 7]`を保持した。
  2026年9月2日に別のセッションが起動した背景ジョブの実行識別子は`TaskOutput`が`No task found with ID`で拒否し、
  当該ジョブの出力ファイルは絶対パスのまま全出力と`[exited with code 0]`を保持していた。
  再検証は同じ形で背景実行して当該ファイルを読み、終了済みセッションが残した出力ファイルの絶対パスの読み取りと、
  同じ実行識別子が解決しないことを対にして確認する

## 待機の起動条件

- 完了通知を受領できる経路が実在し、通知後に再開できることを待機開始前に確認する。
  受領できない条件が確定した対象は待機対象に含めず、検収済み状態を渡して新規起動する。
  Codexでは、`agent-toolkit:delegation`の「Codex後続操作の共通先行条件」を適用してから新規起動する。
- 観測が終端statusを返しながら、タスク契約が受領を定める返却値を伴わない場合は、当該終端を待機の対象に含めない。
  完了通知を待たず、保持済みの識別子で同じsessionへ継続を要求して当該返却値を得る。
  継続の要求は既存sessionの継続とし、新規起動へ切り替えない
  （厳守規定。終端したturnは以降の通知を発しないため、待ち直しでは当該返却値が到達しない）。
- 委譲先が自身の起動した委譲先の終端を待たずに自身のturnを終えた場合、当該子の完了は呼び出し元へ通知されない。
  終端したturnは子の完了後に新しいturnを開始しないためであり、呼び出し元は前項に従って継続を要求する。
  本項は自動再開を持たない実行経路へ適用する。`agents_server`のClaude backendは子の生存中はsessionを実行中として保つため、当該経路では終端statusが返らない。
- 完了通知が到達しない場合は、単純に待ち直さず`停滞の検知と巻き取り`へ進む。
  調査は対象の実体を直接照会するコマンド（`ps -p <PID>`・`gh run list --commit <SHA>`等）で行う。

### Codex互換実行の稼働中turn

Codexで元担当の回復、置換、再起動、代替起動又は役割引継ぎを行う場合は、`agent-toolkit:delegation`の「Codex後続操作の共通先行条件」を先に適用する。
Codexの`list_agents`が対象を`running`として返している間は、`running`のstatusを補助観測より優先する。
Codexの`list_agents`が対象を`running`として返している間は、補助観測や催促だけを根拠とする巻取り、新規起動、役割引継ぎを行わない。
後続主体を起動できるのは、ユーザーの明示要求、終端・失敗status、タスク契約上のキャンセルのいずれかを確認した後、
元担当の終端と書込所有権の解放を確認した場合だけである。
補助観測から停滞を推定して`interrupt_agent`を実行しない。
Git差分、HEAD、成果物の更新時刻・行数、無応答、経過時間やこれらの組合せは、`running`を覆す中断根拠にならない。
中断は、ユーザーの明示要求、終端・失敗status、タスク契約でキャンセルが指定された場合のいずれかだけで確定する。

- 同一turn内では、補助観測の更新だけを理由に同じ対象の状態照会を反復するポーリングを行わない
- 完了通知の不着を検出した時点では、同一turn内でも対象を直接照会してよい
  これは通知不着を契機とする受領経路の検証であり、補助観測だけを更新するポーリングではない
- 通知不着後の次の定時turn（定時起動）では、対象の状態を直接照会してよい
- 終端statusを確認する工程では、必要な再照会を実施してよい
- ターン終了前の稼働状況の1回測定は、同一turn内のポーリングに当たらない
- 別turn又は次の定時turnで間隔を空けた複数回の観測は、同一turn内のポーリングに当たらない
- 対象外の独立した実装・検証・履歴整理・CI確認を進める
  広範な未完了調査を1つの委譲先へ再委譲せず、独立した作業単位の完了を個別に受領して統合する

## 完了通知を待ってターンを終える場合

- 待機対象の完了通知から独立した定期再確認は、Claude Codeでは
  `agent-toolkit/skills/delegation/references/claude-code-runtime.md`「Cronによる定期再確認」節の作成・再利用・resume又はcompaction後の照合・削除の順序に従う。
  `CronCreate`、`CronList`及び`CronDelete`が現在の実行主体へ公開される場合だけ併用し、一般の委譲待機で`ScheduleWakeup`を使用しない
- 定期再確認を開始する直前に、メインは`atk wait-schedule --request-bucket main`、サブエージェントは`atk wait-schedule --request-bucket subagent`を1回実行し、標準出力のcron式を変更せず`CronCreate`へ渡す。
  待機対象を一意に識別できる保持済みIDをpromptへ含め、`recur=true`で1件だけ作成する
- 定期promptは正本状態と完了通知を再確認し、完了対象があれば既存の受領手順へ進む。
  全対象が未完了なら、実測で判定閾値へ到達した経過時間起動の義務を実行し、到達した義務が無ければ利用者向け報告を出力せず待機を継続する。
  実行環境が地の文の無い応答を可視出力の欠落として扱い、応答の再生成を要求する場合だけ、記号1文字など内容を持たない最小限の出力で当該要求を満たす。
  定期起動だけを完了又は停滞の証拠にしない
- 定時起動を装着する時点で、当該セッションに適用される定期報告、cooldown解除、期限監視などの経過時間起動の義務を列挙し、各義務の経過を実測するコマンドと判定閾値を定期promptへ含める。
  該当する義務が無い場合は含めない
- 定期再確認機構又は`atk wait-schedule`が利用できない場合も、シェルの`sleep`や背景タイマーへ切り替えず待機表明でターンを終える。
  外部事象の到達だけに依存する待機は、当該事象が到達しない障害時に打ち切る契機を失う
- 背景委譲を起動した実行主体は、当該委譲の完了通知の受領をもって待機解除としてよい
- 直接の呼出元ではない主体が子孫の完了通知を受領した場合は、通知の`status`と`result`を保持し、
  `agent-toolkit:delegation`の完了通知と中継の実行順を正本として、保持した直接の子のagent IDへ逐語中継する
  完了通知の受領主体を最上位と直接の親のいずれにも固定せず、providerと実行時のtool公開を実測して判定する
- `ListAgents`が不在か、呼び出しを拒否された場合は、保持済みのID、完了通知、`atk watch`による成果物観測及び自身が起動して識別子を保持したプロセスの生存を照合する。
  プロセス名の一致だけから生存状態又は対象を推定せず、agent定義の許可単独や環境変数単独から機能を推測しない
- `SendMessage`のsuccess又はqueuedは送信側の受理だけを示す。
  中継先IDと送信後の完了通知か戻り値を対応付けて受信処理を確認し、未確認の反映を理由に再送しない
- 中継不能時は、未完了の工程だけを巻き取る。
  担当範囲又は権限の外にある場合は、保持した通知、送信先ID、送信結果及び未観測の結果を`needs_escalation`として呼出元へ返す
  Codexで未完了工程を巻き取る場合は、`agent-toolkit:delegation`の「Codex後続操作の共通先行条件」を適用してから行う
- 完了通知が到達しない場合は`停滞の検知と巻き取り`へ進む。
  成果物ファイル、孫のtranscript及び委譲先自身のtranscriptの最終更新時刻を停滞の判定材料として実測する。
  更新時刻だけで終了を判定せず、実行中の孫を終了済みと誤認して同じ工程へ複数の主体を接続しない（厳守規定）
- 出力ファイルの末尾標識照会は取得時点が中間ターン境界へ一致し得るため、単独で完了判定に用いない
- 定時起動の依頼文へは、現在の作業状態を正本となるファイル（計画ファイル・作業ツリー・
  課題管理の一覧など）から読み直して判定する旨だけを書き、
  コミット識別子・残工程の列挙・完了済み工程の記述を埋め込まない。
  依頼文が可変状態の写しを保持すると、工程が進むたびに内容が事実と相違する（努力目標）
- 定時起動の発火は停滞時間の起点を更新せず、定期起動だけを完了又は停滞の証拠にしない。
  変化が無い場合も、既存の`ListAgents`、完了通知、`atk watch`及び保持済み識別子による直接観測で停滞の検知条件を満たした場合だけ巻き取りへ進む
- ターンを終える直前に、観測対象の成果物パスが確定している場合は成果物の更新時刻と分量を、
  自身が起動して識別子を保持したプロセスがある場合は当該プロセスの生存を1回だけ実測する。
  前回の実測から値が変わった場合だけ、ユーザーへ1行で示す。値が変わらない回と、どちらの観測対象も無い場合は、実測結果の報告を省略して完了通知を待ってターンを終える。
  進捗の有無だけを確認するこの回は`ListAgents`を発行せず、成果物パスが確定している場合だけ成果物側の観測で判定する。同toolは、停滞の検知条件を満たしたかを判定する回、催促又は巻き取りの要否と宛先を確定する回、及び実行ホストの経路契約が終端の観測手段として指定する回で発行する。
  同一turn内で補助観測を更新するために同じ状態確認コマンドを反復発行すると、同一結果の再取得へコンテキストを消費する

## 待機中の先行実施

待機中は、後続工程のうち委譲先の対象範囲と競合せず、
かつ着手条件と入力が待機対象の結果に依存しない全ての工程を先行して実施する（努力目標）。
競合の有無は委譲先の変更説明と実差分の突合で判定し、読み取りのみの調査は競合しないものとして扱う。
別リポジトリへの操作もファイル競合は生じないが、入力が待機対象の結果に依存する場合は先行しない。

## 停滞の検知と巻き取り

- 委譲先が所有する外部プロセスまたは背景ジョブの実行中は、成果物差分だけで停滞を判定しない。
  所有主体が返した安定した実行識別子を直接照会し、生存中、識別子消失、終了後の結果未回収を区別する。
  外部実行を終了できるのは所有主体だけとし、委譲元は生存中の処理を重複起動しない
- 別turn又は次の定時起動で間隔を空けた複数回の観測に差が無ければ継続を1回促す。
  Codexの`list_agents`が対象を`running`として返している間は、`Codex互換実行の稼働中turn`節の禁止及び起動条件を適用し、補助観測や催促だけを根拠とする巻取り、新規起動、役割引継ぎを行わない。
  Codex以外の対象でその後も応答が無ければ、未完了工程を巻き取るか、縮減した新規サブエージェントを起動する。観測結果はユーザーへ短く提示する。
  ただし成果物ファイルの更新が続いている間と、更新元を別主体（CI・formatter・並行セッション等）と
  区別できない間は、停止・巻き取りの判断を保留して催促にとどめる
- 稼働中の同一委譲先へ、先に送った方針と矛盾する差し替えを繰り返す状況になった時点で作業の保留を指示し、
  委譲元で方針を確定してから旧方針との差分を統合した指示を1回で送付して再開させる
- 起動文へ明示した同一の制約への違反が繰り返される場合は、同じ制約を伝え直す起動を繰り返さず、
  Codexでは`agent-toolkit:delegation`の「Codex後続操作の共通先行条件」を適用した後に当該工程の巻取り、別の経路への切替え又は役割の引継ぎを行う。
  Codex以外では、呼び出し元が当該工程を巻き取るか別の経路へ切り替える。切り替えの前に、違反が委譲先の出力形式と
  受信側の判定条件のどちらに起因するかを実装で確認し、受信側に起因する場合は判定条件を是正する
- 停滞を確定して巻き取る場合、再実装を決める前に委譲先自身のtranscript、委譲先が起動した子孫の記録及び
  外部実行系のログを末尾に限定して確認する。
  完了報告を取得できた場合は再実装せず、当該報告を検収して、実行時に公開され呼び出しが成功した`SendMessage`と保持済みIDで再開する。
  完了報告を取得できない場合は未完了の工程だけを巻き取り、担当範囲又は権限の外にある場合は`needs_escalation`で返す
  Codexで未完了工程を巻き取るか新規起動する場合は、`agent-toolkit:delegation`の「Codex後続操作の共通先行条件」を適用してから行う
- Codexの二層待機では、外側の実行セルのyieldを停滞の判定材料に用いない。内側の`agents_server.wait`が継続している間は、巻き取り、代替起動及び新規起動へ進まず、`${CLAUDE_PLUGIN_ROOT}/share/codex-agents-base.md`「agents_serverの二層待機」節が定める手順で外側の実行セルを再開する

## 成果物側の観測

委譲先が新規作成する成果物のパスは、委譲元が起動文で指定した値又は委譲先が報告した値から確定する。
共有出力ディレクトリの一覧や更新時刻から対象を推定しない。
対象パスが未確定の間は成果物を観測せず、委譲先の生存確認と完了通知を待つ。

委譲先・背景ジョブの成果物側の状況は、実行環境向けに配布されたagent-toolkitの管理CLIが提供する状態確認手段で、
作業ツリーの差分件数・HEAD・成果物ファイルの行数と最終更新からの経過時間を1回の呼び出しでまとめて得る。
同一の観測へ複数のコマンドを個別に発行しない（努力目標）。当該手段が返すのは成果物側の値だけであり、
実行識別子の直接照会と、生存中・識別子消失・終了後の結果未回収の区別を置き換えない。

- 待機中の報告へ載せる観測値は、当該実行主体が書き込む対象の値に限る。非担当対象の値を載せる場合は、その値が判断を変える理由と、実際に書き込んだ実行主体を併記する。
- `atk watch`が返す作業ツリーの差分件数とHEADは、並行セッション、CI、formatterその他の主体を含む作業ツリー全体の値であり、当該実行主体の生存又は進捗を単独で示さない。指定artifactの行数・更新時刻・経過秒も、当該artifactの書込主体へ帰属させて補助観測として扱う。
