# Claude Codeでの委譲の実装：検証コマンドの実行と待機中の定期再確認

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 検証コマンドの実行形態

待機の起動と結果回収は`waiting-and-monitoring-intervals.md`「待機区間の構成」に従い、待機以外の検証・ビルドやリモートホストでの長時間コマンドは同書「背景ジョブの起動形（Claude Code）」に従う。
バックグラウンド移行したコマンドの終了状態を確認して終了報告を返す規定は、`agent-toolkit/share/agents-server-delegate-notice.md`で定める。
同じ規定の共通部分は`agent-toolkit/share/rules/common/02-agent-operations.md`「ツール・コマンド運用」にある。
バックグラウンドで実行中のBashコマンド（`run_in_background=true`の指定、または実行環境の判断で移行したもの）を停止する場合は、起動結果や移行通知で返されたタスクIDのみを`TaskStop`へ渡す。
遅延して提示される環境では、ツールのスキーマを取得してから呼び出す。

## 待機中の定期再確認と背景転換

未完了の委譲タスクやバックグラウンド処理の完了を待機するメインエージェントは、完了通知を主な待機解除手段としつつ、`CronCreate`、`CronList`、`CronDelete`が公開されている場合に限り定期再確認タスクを併用する。
なお、`ScheduleWakeup`は`/loop`コマンド専用として扱う。
定期再確認タスクを設定するのはメインエージェントのみとする。
`Agent`ツールのサブエージェントには設定しない（`CronList`はメインエージェントと共有されるため、サブエージェント用に作成したタスクのプロンプトが親エージェントの会話へ届いてしまう）。
`agents_server`によって起動された委譲先は、独立したセッションのメインエージェントとして扱う。

1. 所有するタスクを設定するため、`agents_server`の`start`処理では、agent-toolkitのmodが自身の`CronList`・`CronCreate`・`CronDelete`の実行権限を確認し、メインエージェントの初回の`start`処理の中でタスクを設定する。
   設定されたタスクID、または設定できなかった事実と理由が、該当する`start`の結果の後に会話へ通知される。
   すでにタスクを保持しているメインエージェントや、サブエージェントによる`start`では作成および通知を省略する。
   mod自身に削除権限がない場合はタスクの作成を見送り、完了通知による待機を維持する。
   設定失敗の通知を受け取ったメインエージェントは、通知された理由と指示に従って対処する。
   メインエージェント自身がタスクを設定するのは、必要なCronツールがすべて利用可能であり、かつ次のいずれかに該当する場合に限る。

   - `start`の実行結果の後に設定通知がなく、`CronList`にも後述の標識を1行目に持つタスクが存在しない場合（modが読み込まれていない環境など）。
   - `Agent`ツールの委譲先またはバックグラウンドタスクを、そのセッションで初めて起動する直前。
   自身でタスクを設定する場合は、`atk wait-schedule`を1回実行し、出力された`cron`と`prompt`を変更せずにそのまま`CronCreate`へ渡し、`recurring: true`で1件のみタスクを作成する（`prompt`はmodが設定するものと同一の共通本文である）。
     プロンプトの1行目は`<atk-auto source="periodic-recheck" kind="periodic-recheck">`のみで構成された行とする。
     UserPromptSubmitフックはこの行によって自動挿入ターンを判別し、セッション再開後の所有タスク確認もこの標識の完全一致に基づいて行う。
   監査記録は`docs/development/audit-records-delegation-waiting.md`にある。
   該当節は「agent-toolkit/skills/delegation/references/claude-code-runtime.md：待機中の定期再確認と背景転換：2026年10月4日」である。

2. 必要な再確認のため、定期プロンプトに含める内容は、待機対象を記録側から列挙する手段、対象ごとの成果物パスを特定する方法、動的に解決したパスを引き渡すコマンド形式のみとする。
   作業ツリーに対する確認コマンドは`git -C "$worktree_path" status --porcelain=v1`と`git -C "$worktree_path" rev-parse --short HEAD`である。
   成果物ファイルに対する確認コマンドは`wc -l -- "$artifact_path"`および`stat -L -c %Y -- "$artifact_path"`（macOSでは`stat -L -f %m -- "$artifact_path"`）である。
   待機対象ID、成果物の絶対パス、コミット識別子、残工程、完了済み工程は、プロンプト発火の都度、記録側から最新情報を読み直させる（可変状態の静的なコピーを保持すると、作業の進行に伴って実態と乖離するため）。
   セッション固有の経過時間に応じた起動義務（定期報告、クールダウンの解除、期限監視など）は共通本文の対象から除く。
   こうした義務が存在する場合は、義務ごとに経過時間を測定するコマンドと判定閾値を1行ずつ共通本文の終了タグ（`</atk-auto>`）の前に追加する。
   保持しているタスクIDを`CronDelete`で削除した上で、同一の標識を持つプロンプトで`CronCreate`を再実行し、新しく発行されたIDを以後の管理対象とする。
   義務が後から確定した場合も、その時点で再作成する。
   cron式は壁時計基準で設定され、REPLがアイドル状態のときにのみ発火する。
   繰り返しタスクは7日間で失効し、実際の発火時刻にはジッターが加わる場合がある（詳細は`CronCreate`のツール定義で確認する）。

3. 重複を防ぐため、タスクIDはプロンプトの外部で保持し、未完了の対象が存在する間は同一のタスクを再利用する（modの通知によって受け取ったIDも同様に扱う）。
   セッション再開時や会話圧縮後は、保持しているIDを`CronList`に存在する実タスクと突き合わせ、IDを喪失している場合は標識の完全一致によって所有タスクを一意に特定できる場合に限り、再利用または削除へ進む。
   一意に特定できないタスクへの操作や重複した作成は避ける。

4. 待機中の変化を受け取るため、定期プロンプトは、blocking waitおよびそのバックグラウンドタスクに所有されていない待機対象について、記録側の状態と完了通知を再確認し、完了した対象があれば受領手順へ移行させる。
   すでに所有されている対象への照会は省略する（所有関係の判定は`waiting-and-monitoring-auto-resume.md`「完了通知を待ってターンを終える場合」に従う）。
   すべての対象が未完了である場合は、判定閾値に達した経過時間起動の義務のみを実行し、該当するものがなければ報告を出力せずに待機を継続する。
   プロンプトの発火自体は、完了や停滞を判定するための入力情報としては扱わない。
   `run_in_background`を指定していないBashコマンドが実行環境の判断によってバックグラウンドへ移行した場合も、定期再確認の対象とする。
   バックグラウンド移行時の起動結果として返された出力ファイルの絶対パスに対し、コマンド完了時に同一パスを含む完了通知が届く。
   コマンドの実行結果は、その出力ファイルを`Read`ツールで読み取って確認する。
   なお、サブエージェントの出力ファイルはセッションログ全文であり、読み込むとコンテキストを過度に圧迫するため、結果は起動形態の終了応答から取得する。
   通知によって同一セッションを再開可能な待機処理は、「待機区間の構成」に定めるバックグラウンド起動および通知後の回収手順へ統一する。
   通知機構を持たず同一ターン内での回収が必要な場合は、保持している出力ファイルパスの末尾にある終了標識を回数上限付きで確認し、標識が得られない場合は`ListAgents`または代替稼働観測によって状態を確認する。
   稼働状態を確定できない場合は書込権限を移行させず、続行不能の理由として報告する。
   `sleep`コマンドの直接実行、初回から条件が成立するビジーループ、独自の待機機構の新設によって待機処理を代替しない。

5. 所有タスクを適切に回収するため、modはすべての待機対象が終了して結果を回収した後に、共通プロンプトと一致する非durableな所有タスクを自動回収する。
   `/goal`を設定したセッションでは、メインエージェントが同じ時点で、最終ターンを閉じる前に同じ範囲のタスクを`CronList`で特定して`CronDelete`で削除する。
   目標の評価はターン終了時に残るタスクを未完了と判定し、modの自動回収はその評価より後にしか動かないためである。
   手順は`agent-toolkit/share/rules/rules-main.claude-code.md`「ターンの終え方」が定める。
   複数対象の一部のみが終了した場合、バックグラウンド処理が継続中の場合、未配送の完了通知がある場合、`agents_server`の未回収結果が残っている間はタスクを保持する。
   モデルに対して`CronDelete`が公開されているかどうかは、自動回収の条件には含めない。
   経過時間に応じた起動義務を追加したタスクは通常の自動回収では保持し、既存のセッション終了時自動回収処理に委ねる。
   無関係なcronタスクやdurableなタスクは通常回収の対象外とする。
   回収可否の判定が得られない場合や、自動回収が拒否・失敗した際もタスクをそのまま保持する。
   失敗通知を受信したメインエージェントは理由と指示を確認し、modは次回の有効な終了判定時に再評価する。
   modが存在しない環境で自身が設定したタスクは、すべての対象の終了を確認した時点で`CronDelete`を実行し、削除が完了したことを確認する。
   `CronCreate`、`CronList`、`CronDelete`が利用できない場合や、`atk wait-schedule`の実行が失敗した場合は、`sleep`コマンドやバックグラウンドタイマーへの代替は行わない。
   同一セッションの再開が保証される場合は完了通知を待つためにターンを終了し、それ以外は公開待機手段で同じターン内に結果を回収する。
   `sleep`で外部事象のみを待機すると、事象が届かない障害時に処理を打ち切る契機を失うためである。
