# 委譲の要否判定と委譲単位の確定

本書は`agent-toolkit/rules/01-agent.md`が定める委譲の要否判定と委譲単位の確定、および読み取り専用の探索委譲の選定の正本である。
委譲先を起動、観測、継続又は巻き取る場面で全文読む。

## 要否判定

基本的な委譲では`references/base-contract.md`を適用する。
工程別モデル設定、複数主体調整、継続、停滞検知又は巻き取りが必要な場合は
`agent-toolkit:delegation`を適用して経路固有の契約を確定する。

委譲先を指定する手順が無い場面でも、独立コンテキストによる先入観のない評価、モデルの使い分け、
並列実行の3つの利益に照らして委譲の要否を自ら判定する（努力目標）。
同一の対処を繰り返しても事象が解消しない場合、相互に依存しない作業が複数ある場合、
内容が確定済みで判断を要さない作業が残っている場合は、判定の好機とする。
ユーザーの割り込み・是正要求により稼働中の作業と対象が独立した調査・是正が生じた場合、
または未処理のレビュー指摘・是正項目が対象ファイルの重複しない組へ分かれる場合も、判定の好機とする。
所在の特定、横断的な該当箇所の列挙、命名規則の探索など、結論だけで後続の判断が成立する調査も判定の好機とする。
この場面では読み取り専用の探索委譲を選択肢へ含める。
対象が特定済みで読む範囲が少量の場合は、起動の固定コストを踏まえて自ら実施してよい。
判定の結果として自ら実施する選択も採用できる。

## 委譲単位の確定

委譲対象と判定した作業が複数ある場合は、起動前に同じ委譲先へまとめられるかを判定する。
同じ作業ディレクトリで実行でき、同じ権限区分で足り、書込所有権が競合しない作業は、1件の委譲へまとめる。
先行作業の結果を後続作業の入力にする依存関係がある作業も1件の委譲へまとめ、実行順を起動文へ示して同じ委譲先が順に実行する。
まとめられない場合は理由を記録する。分割理由として認めるのは、書込所有権の競合、読み取り専用と書込可のような権限区分の相違、
又は規範が実行時機若しくは他工程との同時実行を制限する場合に限る。
同じ種別かつ同じ実行時機の作業は、規範が委譲の種別を指定している場合も1件の委譲へまとめる。

確定した委譲単位の構成（件数、各単位の担当範囲、起動順）は、構成を確定した工程の判断基準を正本として維持する。
稼働中に構成を変更できる条件は、依存関係又は書込所有権の変化により構成が成立しなくなったことに限る。
変更する場合は、稼働中の担当を停止する前に、確定時と同じ判断基準で構成を再計算する。
変更の理由と、維持する進捗済みの成果を確定してから移行する。
作業量、対象件数、目標時間、一般的な並列化の利点を理由に構成を置き換えると、起動済みの担当の停止と再起動が生じ、進行中の成果が失われる。

実装を委譲する際の書込主体とworktreeの対応は`references/mandatory-rules.md`に従う。

## コンテキスト消費が大きい調査の切り出し

コンテキスト消費が大きい調査は、読み取り専用の探索委譲へ積極的に切り出す。
所在の特定、横断的な該当箇所の列挙、命名規則の探索など、結論だけで後続の判断が成立する調査を対象とする。
`agents_server`が`start_explore`を提供する場合は、通常の委譲起動より`start_explore`を優先する。
軽量起動の委譲先が受け取る取り決めと`fast`の扱いは`references/runtime-routing.md`「経路」を正本とする。
委譲と直接実行の分岐は、`start_explore`の説明が示す採算の目安で判定する（努力目標）。
