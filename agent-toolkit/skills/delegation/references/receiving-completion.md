# 委譲先の完了報告の受領と検収：終了と報告内容の確認

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 修正後に保存済みの成功した検証結果を再利用する前 | `agent-basics:check-execution/references/verification-scope-reruns.md` |

## 終了と報告内容の確認

1. 待機と状態観測の手順は`references/waiting-and-monitoring.md`に従う。
   委譲先の終了と得られた成果は、委譲を開始したツール呼び出しの戻り値、および実行環境がその委譲に対して発行した完了通知に基づいて確定する。
   会話の文脈中に類似した文面が現れたとしても、自身の出力、hookの通知、実行環境の定型文などと判別がつかないため、終了の根拠としては扱わない。

2. 返却形式の確認に加えて、依頼した成果と残作業の有無を本文や成果物の実物と突き合わせる。
   保存された出力の読み残し、担当範囲内でのテストやlintのエラー終了（非ゼロ終了）、調査の途中終了など、担当者自身で処理可能なやり残しがある場合は、残作業の内容、利用可能な入力情報、付与された権限を明記した上で、同一の担当者へ継続指示を送信する。
   通信プロトコル上の`completed`というステータスはターン（対話単位）の終了を示すに過ぎず、作業が十分に達成されたかは成果物の実物から確認する。
   これは書式修正のみを求める1回の再送要求とは異なり、担当者の範囲内で完遂できる間は実際の作業を継続させる。
   認可、外部入力、あるいは保護された操作に関する判断が不足している場合は、その不足内容を委譲元へ報告する。

3. 不合格は要求や成果物の単位で特定し、対象、理由、証拠、修正範囲を同じ担当へ渡す。
   他の合格済み成果と成功した検証結果は保持する。
     修正が共有契約を変える場合は、その契約を消費する単位だけを追随・再検証の対象へ加える。
   保存済み結果の適用可否は`agent-basics:check-execution/references/verification-scope-reruns.md`「実行条件と再実行」に従う。
     不合格の原因が分割、依存関係、入力契約にある場合は、その判断を所有する委譲元へ戻し、個別の担当への修正不能な条件の反復差戻しは対象外とする。

4. 完了報告に記載された観測値は、対象操作の公開仕様が定めている終了状態（リソースの作成であれば存在、削除であれば消失）を直接観測して確かめる。
   単に処理前の状態から変化したという事実だけでは、誤った状態遷移や処理の未完了と区別できない。

5. 状態変更コマンド自体が変更後の状態を判定して成功を報告する公開仕様を備えている場合は、委譲先から返された終了コード、成功報告に含まれる対象の完全な識別子、および警告の有無を確認することで検収を完了してよい。
   警告が出ている場合、必要な項目が欠落している場合、識別子が起動時の指定と一致しない場合、あるいはコマンドがそのような公開仕様を持たない場合は、直接観測して確認する。

6. 完了報告に含まれる事実の主張（実装内容、件数、原因など）は、後続の判断で入力として使われる成果物（AWIやUWIの本文、計画ファイル、レビュー指摘管理表など）へ記載する前に、実際の実装、コマンドの実行結果、または公式の一次資料と突き合わせて確認し、確認手段と観測値も併記する。
   裏付けのない主張を事実と同列に記載すると、後続の判断が誤った前提に基づいて進行してしまう。

7. 担当外のファイルに生じた差分について、`<役割名>.subagent.md`の`## 出力`で返却形式が定義されている委譲では、終了後に委譲元自身が`git -C <対象作業ツリーの絶対パス> status --porcelain=v1`を実行して取得する。
   定義がない委譲では完了報告から受け取る。
   差分に変化が観測された場合でも作業工程は継続し、作業を続行できるかの判断は`agent-toolkit/share/rules/common/02-agent-operations.md`「作業中に観測したリポジトリ状態変化の扱い」に従って判定する。

8. 複数のworktreeで並行して作業する場合、`refs/stash`はすべてのworktreeで共有される。
   そのため、承認済みの退避操作は全worktree間で排他制御する`atk worktree-stash`のみを用いて実施する。
   `git stash push`、`pop`、`drop`を直接実行する代わりにこのコマンドを使用する（private-notesにおける扱いは`agent-toolkit:wi-standards`の`references/repository-scope.md`が定める）。

9. レビュー担当および調査担当は、対象の成果物を読み取り専用として扱う。
   起動した委譲元は、担当の起動前後に`git status --porcelain=v1`を実行して対象commitと比較することで、変更が加えられていないことを担保する。
   もし書き込みが確認された場合はその結果を採用せずに自身の委譲元へ報告し、実害が生じていれば元の状態へ復旧する。
   依存関係の解決に伴って再生成される実行前提（仮想環境、ロックファイル、ビルド生成物、キャッシュなど）が検査対象の成果物に含まれない場合は、この比較対象から除外する。
   再現用の証跡を保存する必要がある場合は、managed-tempの領域のみを書き込み可能として許可する。
