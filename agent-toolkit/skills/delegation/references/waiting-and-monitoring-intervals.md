## 待機区間の構成

機械的な完了通知を待機の解除手段とし、シェルのsleepやCodexの`sleep`ツールによる能動的な時間待ちを禁止する。

1. 結果を回収できる起動形を選ぶ。
   完了通知によって同じセッションを再開でき、ホストが背景実行機能を公開する待機は、対象の種類や件数、既存バックグラウンドタスクの有無、goalの有無にかかわらず、背景実行で開始する。
   同一セッションの再開が保証され、Bashの背景実行が有効なClaude Codeでは、`atk agents wait`、CIやデプロイ状態の監視、および終了条件ループを`run_in_background=true`で起動する。
   通知による再開保証が無い場合と、Bashの背景機能が公開されていない場合は、非対話起動のメインも公開待機手段で同じターン内に結果を回収する。
   前景待機では、ホスト側の実行時間上限を待機コマンド自身の上限以上に設定する。
   Bashの背景実行が無効なClaude Code（`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`）では、単独の`atk agents wait`へBashの`timeout=600000`を指定する。
   この条件はSessionStartの通知と、Bashの公開入力に`run_in_background`が無いことで判別し、未知引数として拒否される背景指定を試さない。
   CLI自身はTTL由来の上限と540秒の小さい方で終了3を返すため、結果と終了コードを回収し、未終了なら同じコマンドを再発行する。
   MCP内部とlane資源回収の待機期限は、このCLI専用の短縮の対象外とする。
   背景無効時の前景上限と公開引数の再検証は、`docs/development/audit-records-delegation-waiting.md`にある。
   該当節は「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：待機区間の構成：2026年11月2日」である。
   Codexのcell IDやコマンドsession IDは、前掲の表に示した回収手段を用いて同じターン内で回収する。
   独立して進められる作業と受信済み通知の処理を先に行い、それらが尽きた長い終了待ちでは、`share/rules/rules-common.codex.md`「Codex固有の入出力」の長めの回収時間の目安を適用する。
   制御が戻るたびに追加入力と通知を処理する。
   待機を開始できなかった場合は、未回収対象の識別子と起動状態を保持して`wait-anomalies-refusal.md`「待機を開始できない場合」に従う。
   待機の起動失敗と、対象の終了・観測責任の解消を区別する。
   目標評価（`/goal`）の発動条件は`agent-toolkit/share/rules/rules-main.claude-code.md`に従う。
   `agents_server`の委譲先はそれぞれ独立したセッションであり、各セッションの判定対象には自身が起動したタスクのみが含まれる。
   待機の起動や結果回収の処理をgoalの有無で分岐させず、本節の共通ルールに従って進める。
   異常終了が発生した場合は`references/wait-anomalies.md`に従う

2. 単一の待機を開始するため、`agents_server`の待機は`atk agents wait`だけで発行する
   - 待機対象、待機上限、委譲元の区分、応答後の破棄指定などの引数指定は避ける。
     対象は発行時点で全ルートに存在する起動中セッションと未回収結果の全体となり、上限はCLI側が自動で算出する
   - 外側の`timeout`コマンド、パイプ、`wc`などを連結せず、引数なしの単独コマンドとする。
     ホスト側ツールが持つ実行時間上限（Claude CodeのBashツールにある`timeout`引数など）も外側の上限に該当するため、背景実行時の扱いについては`agent-toolkit/share/rules/common/02-agent-operations.md`の「待機と背景実行」に従う。
     コマンドの連結や短すぎる外側の上限設定は、待機を途中で打ち切ってしまったり、終了コードを覆い隠してしまったりする原因になる
   - 続行の判断は終了コードと応答のみに基づいて行い、`status: running`が返ってきた場合は同じコマンドを再発行する。
     起動方法は本節に定める通知による再開のルールに従う
   - エージェント環境では、終了や通知の内訳と、上限サイズ内に収まる本文の要約が標準出力へ直接返される。
     各終了の結果本文は個別のファイルへ保存され、終了行の`agent_message_path`がその絶対パスを示す。
     要約に本文が含まれていない場合や、後続ターンでの再読・他者への引き渡しを行う場合は、そのファイルを直接参照する
   - 結果の回収処理は結果データや通知の削除を伴うため、背景処理へ移行した後も含めて、同一の結果を得るためのコマンドの重複再発行は避ける
   プロセスの生存状態や対象の判別は、起動時に得られた識別子、完了通知、および成果物側の状態確認手段を用いて判定する。
     更新時刻、末尾の標識、`git log`、`git status`などはあくまで補助的な情報として扱う

3. 待機中の工程と観測を保つため、待機表明してターンを終えた委譲先が再開される契機は、起動形態によって異なる。
   `Agent`ツールによるサブエージェントは、バックグラウンドタスクの完了通知によって再開される。
   `agents_server`の委譲先が起動した別の`agents_server`セッションは両バックエンドによって追跡され、追跡対象がすべて終了するまで最初の結果が保留され、そのターンにつき1回だけ同じセッションが自動再開される。
   Codexバックエンドでは、組み込み委譲で起動した子スレッドも同様に保留と自動再開の対象となる。
   Claudeバックエンドでは、背景実行されたシェル、背景のAgent委譲、背景へ移行したMCPツール呼び出しも自動再開の対象に含まれる。
   自動再開が行われるのは、対象となる子セッション、子スレッド、バックグラウンドタスクを実際に起動した場合に限られる。
   これらを起動せずに待機表明だけを行った場合は、委譲元が完了を確認して再開を指示する。
   監査記録は`docs/development/audit-records-delegation-waiting.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：待機区間の構成：2026年9月3日」を参照する。
   複数の子を待つ委譲先では、待機表明による自動再開は追跡対象の全件終了後に1回だけ起こる。
   先に終了した子の結果を残る工程の入力に使う場合は、待機表明でターンを終えず、同じターンの`atk agents wait`（本節の起動形に従う）で終了した分から回収して、その工程を進める。
   待機表明でターンを終えるのは、全件の結果がそろうまで進める工程が無い場合に限る。
   `atk agents wait`で回収した子は追跡から外れ、残る子の終了で再開したターンへは回収済みの子を再び示さない
   未回収の子セッション、子スレッド、背景エージェントを追跡している間は、待機表明の保留と終了後の必要な継続を維持する。
   過去の自動継続の消費済み状態やCLIのidle状態だけで、その観測責任を終えない。
   回収済みの対象は再追跡せず、同じ終了通知による重複再開を行わない。
   利用上限の解除を待機している子プロセスにも同様の扱いを適用する。
   実行時間の上限が保証されている背景コマンドについては、その上限に基づいて通知喪失を診断し、明示的な中断や追跡先の喪失、再開失敗が発生した場合はそれぞれの診断手順から回復を図る

4. 制御が戻ったら次の観測を選ぶため、観測処理が終了ステータスを返さずに戻った場合は、戻り方で分類する
   - 実行環境が観測を背景処理へ移行させ、その完了通知によって同じセッションが自動再開されると示されている場合に限り、同じ観測コマンドを再発行せずに待機状態を表明してそのターンを終える。
     背景処理への移行は、コマンド本来の待機上限とは独立して扱われる。
     なお、Codexのcell IDや`exec_command`のsession IDは環境全体の機能通知だけでは自動再開されないため、前掲の表に示した手段で同じターン内に回収する
   - 観測処理が自身の待機上限に達して戻り、背景処理への移行も示されていない場合は、同じターン内で再発行してよい。
     再発行する前に`waiting-and-monitoring-independent-work.md`「待機中の先行実施」に該当する工程を先に進める。
     通知による再開と背景機能が使える場合に限り、進められる工程がなくなった後の待機を完了通知や定期的な再確認に委ねる
   - 同じターン内で再発行してよいのは、1回の呼び出し自体が待機時間を消費する観測手段に限られる。
     待機時間を消費しない状態照会を何度も繰り返す行為は、単に補助的な観測値を更新し続けるだけのポーリングとなってしまうため避ける
   `show`が返す停滞診断や子セッション一覧、`send_message`が返す`delivery`の意味は、各MCPツールの仕様に従う。
     実行時間の長いコマンドを実行中である場合は、催促や巻き取りの判断を保留する。
     停滞の兆候は委譲先の状況を調査する契機として扱い、実際の確定と巻き取りの手順は`waiting-stalls.md`「停滞の検知と巻き取り」に従う

5. 届いた結果から工程を再開するため、先に届いた独立待機の通知から順に保存出力と終了状態を回収する。
   起動済みの待機結果を受け取り、先に届いた通知に対応する工程から順次進める。
   各待機や監視は単一の実行として管理し、別の待機が終わるまで前景やMonitorを占有し続けるような操作は避ける。
   自身が直接起動していない子孫プロセスの完了通知は、直接の子プロセスへ中継した時点でその工程が再開される。
   中継処理はホストごとの委譲契約（Claude Codeでは`claude-code-runtime-receiving.md`「完了通知と中継の実行順」）に従う
   委譲元は自動再開の要否を独自に判断せず、自動再開の仕組みに委ねる。
   `atk agents wait`は、再開されたターンの終了まで待機してから結果を返す。
   応答が待機表明であるかどうかは、CLIの応答内容から判別できる（同様の文面が完了報告にも現れる）。
   `終了行:`に`unfinished_waits`が含まれる結果（`error`の`heldResultFinalized`が真）は、待機対象が残っている状態で保留を打ち切った待機表明であるため、再開したターンの最終的な返却値から除外する。
   残っている対象の状態を確認したうえで、同じセッションへ続きの処理を依頼する。
   判別には`unobservedSessions`の有無以外の情報も併用する

## 完了通知で始まったターンの対処

`Claude Code`のバックグラウンドタスク完了の自動通知で始まったターンは、ユーザーの発話ではない。
通知配送のための前ターンの`Stop`終了は、現在ターンのツール操作の禁止を意味しない。
通知の保存出力と終了状態を回収する。
未終了の担当には、有効な待機または同じセッションの自動再開を維持する。
ホストが実際に操作を拒否した場合は、その拒否に従う。

## ホストが待機コマンドを停止した場合

ホストが`atk agents wait`などの待機コマンドを停止し、再開にユーザーの指示を要する場合は、取得済みの結果を保持する。
再開の可否は`agent-toolkit:user-confirmation-and-report`に従ってユーザーへ確認する。
