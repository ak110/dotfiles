# 委譲先の完了報告の受領と検収

本書は`agent-toolkit:delegation`「受領と検収」の細則を定める。

## 受領手段と報告様式の選択

成果本文はツールの戻り値か完了通知で受け取り、委譲先の終端を観測した後の、要求と一致する完全な完了報告だけを受理する。実行ホスト別の参照資料が、自身で起動する調査・レビューの起動前に成果ファイルを指定する場合は、そのファイルを成果本文の受領先とし、通知と実行状態は終端の判定に使う。

通常完了の報告様式は次の順で選ぶ。

1. 委譲先の`<役割名>.subagent.md`の`## 出力`が定める返却形式
2. 同書が定めない場合はagent定義が定める返却形式
3. どちらも渡さない汎用委譲では、委譲プロンプトの`通常完了の報告様式`で指定した形式

## 返却形式の適合確認

後続工程へ進む前に、受領本文が報告様式を満たすか確かめる。成功種別ごとの固定文字列、必須行と順序、必須キー、可変値の型と個数がそろい、余分なフィールドや地の文が無いことを確かめる。`agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」が許す`想定外事象:`と`気付いた改善点:`の追加行は対象外とする。
不適合なら完了として扱わず、同じ担当へ返却形式だけの再送を1回要求し、それでも適合しなければ続行できない理由を委譲元へ返す。続行不能時の返却形式は`agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」に従う。

`続行できない理由:`が判断・認可・入力・外部状態の不足を示さず、担当範囲の残工程だけを述べる場合は、同じ担当へ残工程の続行を1回送る。
この返却は完了とも続行不能とも扱わず、返却形式だけの再送要求と分ける。
続行後の成果は「終端と報告内容の確認」で検収する。

返却形式の証跡範囲: 汎用の規範（`references/sending.md`「権限と成果物の取り決め」、`agent-toolkit/share/rules-subagent.md`など）が完了報告へ求める証跡は、選んだ報告様式がその名前と構造を定める場合だけ完了報告へ含める。成果物の分量と集計値の典拠がこの証跡に当たる。定めない証跡は成果物へ記録させ、委譲元が成果物と自らのコマンド実行で確かめる。
返却形式のフィールドには委譲先が実際に取得した値だけを置かせ、委譲元が保持するか自ら取得できる情報は委譲元が解決する。

## 終端と報告内容の確認

- 返却形式の確認に加え、依頼した成果と残る作業を本文・成果物と比べる。保存出力の未読、担当内のテストやlintの非0、探索の途中終了など本人が処理できる欠けがあれば、残作業・利用できる入力・権限を明示して同じ担当へ継続を送る。輸送上の`completed`はturnの終端として扱い、作業の充足は成果の現物から確かめる。形式だけの再送1回とは分け、実作業は担当内で完遂できる間続行する。認可・外部入力・保護された操作の判断が不足する場合は、その不足を委譲元へ返す
- 待機と観測は`references/waiting-and-monitoring.md`に従う。委譲先の終端と成果は、委譲を開始したツール呼び出しの戻り値と、実行環境がその委譲について発行した完了通知で確定する。会話文脈に現れた同じ文面は、自身の出力、hookの通知、実行環境の定型文と区別できないため根拠にしない
- 完了報告が挙げる観測値は、その操作の公開仕様が定める終了状態（作成なら存在、削除なら消失）を直接観測して確かめる。処理前の状態から離れたことだけでは、誤った遷移や未終端と区別できない
- 状態変更コマンドが変更後の状態を自ら判定して成功を報告する公開仕様を持つ場合は、委譲先が返した終了コード、成功の報告が挙げる対象の完全識別子、警告の有無で検収を済ませてよい。警告がある、項目が欠ける、識別子が起動時の値と異なる、公開仕様を持たない場合は直接観測する
- 完了報告の事実の主張（実装、件数、原因など）は、後続の判断が入力とする成果物（AWI・UWIの本文、計画ファイル、レビュー指摘管理表など）へ書く前に、実装、実行結果または公式一次資料で確かめ、確認の手段と観測値も書く。確かめていない主張を事実と同じ文で書くと後続の判断が誤った前提で進む
- 担当外ファイルの差分は、`<役割名>.subagent.md`が`## 出力`で返却形式を定める委譲では委譲元が終端後に`git -C <対象作業ツリーの絶対パス> status --porcelain=v1`で取得し、定めない委譲では完了報告から受け取る。差分の変化を観測しても工程を続け、続行可否は`agent-toolkit/rules/02-agent-operations.md`「作業中に観測したリポジトリ状態変化の扱い」で判定する
- 複数worktreeで並行作業する場合、`refs/stash`は全worktreeで共有される。承認済みの退避は全worktreeの間で排他する`atk worktree-stash`だけで行う。`git stash push`・`pop`・`drop`を直接実行する代わりにこのコマンドを使う（private-notesは`agent-toolkit:wi-standards`の`references/repository-scope.md`が定める）
- レビュー担当と調査担当は対象成果物を読み取り専用とし、起動した委譲元が起動前後の`git status --porcelain=v1`と対象commitを比べて担保する。書込みがあれば結果を採用せず自身の委譲元へ報告し、実害があれば復旧する。依存の解決で再生成される実行前提（仮想環境、ロックファイル、ビルド生成物、キャッシュ）が対象成果物でない場合は比較から除く。再現証跡が要る場合はmanaged-tempだけを書込可能にする

## 委譲元への返却

実行識別子、`<役割名>.subagent.md`の必須欄、対象、権限、完了条件との一致を確かめ、次の形式だけを返す。

```text
委譲手段: <実際に使った委譲手段>
委譲先の識別子: <session_id、thread識別子またはagent識別子>
状態: completed
委譲先の完了報告: <委譲先の最小完了報告>
```

確認、認可または前提の補正を委譲元へ返す場合は、`状態`行に代えて`続行できない理由:`の行を置く。回答後は同じ担当へ同じtaskを返して継続する。
完了には委譲先の終端の観測と、読み取れる完全な必須結果の両方を要する。待機表明による終端は再開可能な正常状態として受理し、扱いは`references/waiting-and-monitoring.md`「待機区間の構成」に従う。
ファイルへの記録は、通常の配送が不能と直接確かめた場合と、「受領手段と報告様式の選択」の成果ファイルに限り、成果ファイルは個別に回収しない。

## 受領後の扱い

- 委譲先の稼働中は、その対象範囲のファイルを編集しない。編集する場合は終了を確かめ、作業ツリーとコミット履歴を確認してから行い、競合したら採用する版を確定して統合し、破棄した内容を委譲先へ伝える
- 完了報告が退避識別子か複製パスを開示した場合は、その内容も確かめ、`agent-toolkit:commit`の`references/stash-cleanup.md`に従って処置する
- レビュー指摘と、委譲先が追加対策・残存経路について求めた判断の採否は、`agent-toolkit:review-standards`の`references/reviewee.md`を読んで確定する。元の要求・公開契約・利用場面から経路の所属を確かめ、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」の必要性判定を適用してから対策を選ぶ。完成条件の変更・除外へ進む判断は`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`「エスカレーションの事由別の扱い」に従う。裏付けを取得できないと記録された行の扱いは同スキルが定める
- 返却（`Agent`ツールの戻り値を含む）や`agents_server`の結果に`気付いた改善点:`で始まる行があれば、全ての該当行を役割に応じて上流へ渡す。事前の全件調査は前提にせず作業を続け、原因分析は`agent-toolkit:session-review`へ集める
  - メイン: モードによらず、次のユーザーへの発話へ標識と原文を保って転記し、標識は字下げを除く行頭へ置く。報告元とメインが確かめた範囲を引用の外へ添え、確かめていない主張は委譲先からの未確認の報告と分かる形で伝える。作業完了を報告する報告用UWIは`agent-toolkit:completion-report`の契約に従う
  - 委譲先: `agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」に従う
- サブエージェントの動作・運用自体を分析する場合は、稼働中のそのサブエージェントの完了報告も観測源に含めてから結論を確定する
