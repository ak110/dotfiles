## 受領手段と報告様式の選択

成果物の本文はツールの戻り値または完了通知から受け取り、委譲先の終了を確認した上で、要求内容と合致する完全な完了報告のみを受理する。実行ホスト別の参照資料において、自身で起動する調査やレビューの着手前に成果ファイルの保存先を指定する規定がある場合は、そのファイルを成果本文の受け取り先とし、完了通知や実行ステータスは終了判定の用途に用いる。
役割の公開操作によって生成された完全な固定形式の原本が保存されており、担当者、対象、工程、取得した版の対応付けが確認でき、かつ本文自体が必須の書式を満たしている場合は、手作業による報告文に代えて原本を一次返却として受領できる。この場合、委譲元は手作業の報告文との差異や代用した原本の情報を記録する。生成元の由来、原本の完全性、対応関係、書式のいずれかの確認が不足している場合は、原本を一次返却として受領することは認められない。

通常完了時の報告様式は、次の優先順位で決定する。

1. 委譲先が参照する`<役割名>.subagent.md`の`## 出力`に定義された返却形式
2. 同文書に定義がない場合は、agent定義に定められた返却形式
3. いずれも指定がない汎用的な委譲では、委譲プロンプト内の`通常完了の報告様式`で指定した形式
4. 指定が無ければ、`rules-subagent.md`「返却形式の受け渡し」の正常結果の形式

共通の続行不能区分、部分成果、末尾標識行と省略値の契約は同節を使用し、呼出元は役割固有の入力と結果のみを補う。自由本文の軽量起動にも共通契約が自動配送されるため、依頼へ再掲しない。

## 返却形式の適合確認

後続の工程へ進む前に、受領した本文が指定の報告様式を満たしているか検証する。成功種別ごとの固定文字列、必須の行構成と順序、必須キー、可変値の型や個数がすべて一致し、規定外のフィールドや余計な地の文が含まれていないことを確認する。なお、`agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」で認められている`想定外事象:`および`気付いた改善点:`の追加行はこの制限の対象外とする。
続行不能では、該当単位の結果を区分と理由の2行へ置換した共通形式も受理する。正常な他単位の結果は維持し、理由の直前に同じインデントの有効区分があることと、その区分が実際の不足に合うことを確認する。輸送上の`status: completed`と、本文の成果・続行不能の判定を区別する。

agents_serverの役割文書によるtaskは、backendが正常終了本文を公開する前に区分の構造を検査する。欠落・集合外・インデント違反は結果を保留して同一sessionへ1回だけ自動継続する。役割のmodeと4 backendに共通し、自由本文のdelegate・explore・shell・writeは自動回復の対象外とする。再違反または継続配送失敗では保留本文と診断が公開されるため、委譲元が必要な入力または手動のsend_messageを判断する。自然言語の理由を自動分類せず、保存・復元後も1session1回の上限を保つ。以下の手動差戻しと、サーバーによるこの構造回復を区別して受領する。
書式に不備がある場合は、前節に定めた原本による受領条件を満たすか確認する。条件を満たさない場合は完了として処理せず、同一の担当者へ返却形式の修正のみを求めて1回再送を要求する。それでも適合しない場合は、作業を続行できない理由を委譲元へ報告する。続行不能時の返却形式は`agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」に従う。

報告内の`続行できない理由:`が判断、認可、入力、外部状態などの不足を示しておらず、単に担当範囲内の残作業を述べているに過ぎない場合は、同一の担当者へ残作業の継続を1回指示する。
この返却は完了としても続行不能としても処理せず、返却形式のみの再送要求とは明確に区別して扱う。
継続後の成果物については、後述の「終了と報告内容の確認」に従って検収する。

返却形式の証跡範囲: 汎用的な規範（`references/sending.md`「権限と成果物の取り決め」や`agent-toolkit/share/rules-subagent.md`など）が完了報告に求める証跡は、選択した報告様式にその項目名とデータ構造が明記されている場合に限って完了報告に含める。成果物の分量や集計値の典拠などがこの証跡に該当する。報告様式に定められていない証跡は成果物ファイル側へ記録させ、委譲元がその成果物や自身のコマンド実行結果を通じて直接確認する。
また、返却形式の各フィールドには委譲先が実際に取得した値のみを記入させ、委譲元がすでに保持している情報や自ら取得できる情報については委譲元自身が解決する。

## 終了と報告内容の確認

- 返却形式の確認に加えて、依頼した成果と残作業の有無を本文や成果物の実物と突き合わせる。保存された出力の読み残し、担当範囲内でのテストやlintのエラー終了（非ゼロ終了）、調査の途中終了など、担当者自身で処理可能なやり残しがある場合は、残作業の内容、利用可能な入力情報、付与された権限を明記した上で、同一の担当者へ継続指示を送信する。通信プロトコル上の`completed`というステータスはターン（対話単位）の終了を示すに過ぎず、作業が十分に達成されたかは成果物の実物から確認する。これは書式修正のみを求める1回の再送要求とは異なり、担当者の範囲内で完遂できる間は実際の作業を継続させる。認可、外部入力、あるいは保護された操作に関する判断が不足している場合は、その不足内容を委譲元へ報告する。
- 待機と状態観測の手順は`references/waiting-and-monitoring.md`に従う。委譲先の終了と得られた成果は、委譲を開始したツール呼び出しの戻り値、および実行環境がその委譲に対して発行した完了通知に基づいて確定する。会話の文脈中に類似した文面が現れたとしても、自身の出力、hookの通知、実行環境の定型文などと判別がつかないため、終了の根拠としては扱わない。
- 完了報告に記載された観測値は、対象操作の公開仕様が定めている終了状態（リソースの作成であれば存在、削除であれば消失）を直接観測して確かめる。単に処理前の状態から変化したという事実だけでは、誤った状態遷移や処理の未完了と区別できない。
- 状態変更コマンド自体が変更後の状態を判定して成功を報告する公開仕様を備えている場合は、委譲先から返された終了コード、成功報告に含まれる対象の完全な識別子、および警告の有無を確認することで検収を完了してよい。警告が出ている場合、必要な項目が欠落している場合、識別子が起動時の指定と一致しない場合、あるいはコマンドがそのような公開仕様を持たない場合は、直接観測して確認する。
- 完了報告に含まれる事実の主張（実装内容、件数、原因など）は、後続の判断で入力として使われる成果物（AWIやUWIの本文、計画ファイル、レビュー指摘管理表など）へ記載する前に、実際の実装、コマンドの実行結果、または公式の一次資料と突き合わせて確認し、確認手段と観測値も併記する。裏付けのない主張を事実と同列に記載すると、後続の判断が誤った前提に基づいて進行してしまう。
- 担当外のファイルに生じた差分について、`<役割名>.subagent.md`の`## 出力`で返却形式が定義されている委譲では、終了後に委譲元自身が`git -C <対象作業ツリーの絶対パス> status --porcelain=v1`を実行して取得する。定義がない委譲では完了報告から受け取る。差分に変化が観測された場合でも作業工程は継続し、作業を続行できるかの判断は`agent-toolkit/rules/02-agent-operations.md`「作業中に観測したリポジトリ状態変化の扱い」に従って判定する。
- 複数のworktreeで並行して作業する場合、`refs/stash`はすべてのworktreeで共有される。そのため、承認済みの退避操作は全worktree間で排他制御する`atk worktree-stash`のみを用いて実施する。`git stash push`、`pop`、`drop`を直接実行する代わりにこのコマンドを使用する（private-notesにおける扱いは`agent-toolkit:wi-standards`の`references/repository-scope.md`が定める）。
- レビュー担当および調査担当は、対象の成果物を読み取り専用として扱う。起動した委譲元は、担当の起動前後に`git status --porcelain=v1`を実行して対象commitと比較することで、変更が加えられていないことを担保する。もし書き込みが確認された場合はその結果を採用せずに自身の委譲元へ報告し、実害が生じていれば元の状態へ復旧する。依存関係の解決に伴って再生成される実行前提（仮想環境、ロックファイル、ビルド生成物、キャッシュなど）が検査対象の成果物に含まれない場合は、この比較対象から除外する。再現用の証跡を保存する必要がある場合は、managed-tempの領域のみを書き込み可能として許可する。

## 委譲元への返却

実行識別子、`<役割名>.subagent.md`の必須項目、対象リソース、付与された権限、および完了条件との整合性を確認した上で、次の書式のみを用いて結果を返却する。

```text
委譲手段: <実際に使った委譲手段>
委譲先の識別子: <session_id、thread識別子またはagent識別子>
状態: completed
委譲先の完了報告: <委譲先の最小完了報告>
```

確認事項、認可の要求、または前提条件の修正を委譲元へ返す場合は、`rules-subagent.md`「返却形式の受け渡し」の区分と理由で返す。委譲元から回答を得た後は、同一の担当者へ同じタスクを返送して作業を継続する。
完了の判定には、委譲先が終了したことの確認と、内容を正しく読み取れる完全な必須結果の両方が揃っている必要がある。待機表明によってターンが終了した場合は、再開可能な正常状態として受理し、その扱いは`references/waiting-and-monitoring.md`「待機区間の構成」に従う。
ファイルへ記録するのは、通常の通信による配送が不可能であることを直接確認した場合、「受領手段と報告様式の選択」で指定された成果ファイルを用いる場合、および同節に従って原本を一次返却として受理する際に手作業の報告文との差異や代用原本を明記する場合に限る。なお、成果ファイルは個別に回収しない。

## 受領後の扱い

- 保存済みの実行結果（`atk agents wait`の`agent_message_path`、CLIの出力保存先、MCPの結果を保存したファイル、`session-review-evidence`の出力など）を後続の担当者、検査処理、またはCLIへ引き渡す場合は、そのファイルのパスを直接渡す。モデルが本文を別ファイルや次のプロンプトへ書き写すと、同一の文章がコンテキスト内へ重複して取り込まれ、書き写しの誤りも発生しやすくなるためである。受け取り側は判断に必要な部分のみを読み込み、原本ファイルは後続の参照が終わった後に回収する。
- 委譲先が稼働している間は、その担当範囲に含まれるファイルを編集しない（並行して編集できる条件は`references/mandatory-rules.md`「作業ツリーの保護」に従う。worktree全体を任せた担当の稼働中は、そのworktreeへ書き込まない）。どうしても編集する必要がある場合は、委譲先が終了したことを確認した上で作業ツリーとコミット履歴を点検してから実施する。万一競合が発生した場合は、採用する版を確定して統合し、破棄した内容を委譲先へ伝達する。
- 受け取った返却や通知の`想定外事象:`のうち、ツールや実行基盤の異常を示すもの（turnの中断、接続失敗、hookの警告、同じ操作の再実行など）が同じ種類で2回現れたら、その時点で原因の調査に着手する（調査は委譲してよい）。`agent-toolkit:session-review`への先送りでは調査を始めるのが遅れ、同じ異常が反復し続けるためである。通知機構自体の欠陥を示す場合の処置は`agent-toolkit:bugfix`の`SKILL.md`「問題を見つけたときの対処」に従う。
- 完了報告において退避識別子やバックアップ用の複製パスが開示された場合は、その内容も点検し、`agent-toolkit:commit`の`references/stash-cleanup.md`に従って適切に処置する。
- レビューの指摘事項と、委譲先から追加の対策や残作業について判断を求められた内容の採否は、`agent-toolkit:review-standards`の`references/reviewee.md`を読み込んで確定する。元の要求、公開契約、および利用場面からその処理が属する契約上の位置付けを確認し、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」の必要性判定を適用した上で対策を選定する。完成条件の変更や除外へ進むかどうかの判断は、`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`「エスカレーションの事由別の扱い」に従う。裏付けを取得できなかった旨が記録されている行の扱いについては同スキルが定める。
- 返却内容（`Agent`ツールの戻り値を含む）や`agents_server`の実行結果に`気付いた改善点:`で始まる行が存在する場合は、該当するすべての行を役割に応じて上位のエージェントへ引き渡す。調査結果と必要な処置を受け取り、観測事象と期待との差、直接的原因の手掛かり、品質や作業への影響、担当範囲の判断に不足する部分だけを補う。取得済みの調査は再利用し、追加調査の要求は不足分に限る。本題外の調査はagents_serverのサブエージェントへ切り離す。作業の続行や品質に影響する問題、または規範の欠陥が確定した場合は、`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従って対処する。担当外の処置は調査結果とともに委譲元へ返す。単純な効率改善もQCDで採否を判断する。残る分析は証拠とともに非同期の振り返りへ引き継ぎ、元作業の終了とは独立して進める。
  - メインエージェント: 動作モードにかかわらず、次回のユーザー向け発話へ識別子と原文を保持したまま転記し、識別子はインデントを除いた行頭に配置する。報告元の情報とメインエージェントが確認できた範囲を引用の外側に補足し、未確認の主張については委譲先からの未検証報告であることが分かる形で明示する。作業完了を報告するための報告用UWIは、`agent-toolkit:completion-report`の規約に従って作成する。
  - 委譲先: `agent-toolkit/share/rules-subagent.md`「返却形式の受け渡し」に従って処理する。
- サブエージェントの動作や運用そのものを分析する場合は、現在稼働しているそのサブエージェントの完了報告も観測対象に含めた上で結論を確定する。
