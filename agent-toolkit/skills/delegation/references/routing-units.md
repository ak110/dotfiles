## 委譲単位の確定

作業の独立性、必要な権限、書込所有権、依存関係、文脈の共有度合い、および統合にかかるコストを総合的に考慮して委譲単位を決定する。
調査を依頼された担当が似た対象から順に調べ、知見を再利用する構成を通常の進め方とする。
広い所在探索は`explore`へ分けてよい。
委譲は`routing-decisions.md`「要否判定」の総費用比較で有利な場合に限り、似た対象をまとめる。

- 実行タイミング、作業ディレクトリ、権限区分が共通しており、書込所有権が競合しない作業は、1件の委譲へまとめる候補とし、作業量と難易度を踏まえてQCDの観点から比較検討する。
  独立した単純作業が1つの担当に集中して直列化することや、難度の高い作業で背景情報の読み込み、判断、統合の重複が発生することを共に防ぐ。
  担当者の人数や作業の粒度もこの比較に基づいて決定する。
- 判断の所有は`routing-decisions.md`「要否判定」に従う。
  役割の内部で切り出すのは、5工程で処理できる確定済みの作業に限る。
  独立した文脈でのレビューと、役割文書が定める担当の起動は、それぞれの契約を維持する。
- 先行作業の出力結果を後続作業の入力として利用する一連の処理も1件の委譲にまとめ、実行手順を明示して同一の委譲先に順番に実行させる。
  計画ファイルなどの反復的な修正作業では、整合性の確認と修正を同一の委譲先へ集約する。
  なお、この方針は委譲された単位の内部における作業順序を規定するものであり、判断工程とその結果を入力とする確定済みの作業とを同一の委譲先へまとめる根拠としては用いない。
- 作業をまとめずに分割する場合は、まとめるための条件のうちどれが満たされなかったのかを理由として記録する。
  ただし、規範が委譲の種別を指定していること自体は理由としない。
- 独立文脈レビューは作成側から分離する。
  調査や起草の担当数は対象の件数や独立性だけで決めず、同じ担当が順に処理する案と総費用を比較する。
  起動後の追加対象も同じ基準で割り当て、同じ担当へ渡す場合は対象ごとの要求・原稿・根拠を区別する。

一度確定した構成（エージェント数、担当範囲、起動順序）は、依存関係や書込所有権に変化が生じて作業が成立しなくなった場合に限って変更する（努力目標。途中で停止して再起動すると進行中の成果が失われるため）。
構成を変更する場合は、稼働中の担当者を停止する前に同一の基準で構成を再計算し、維持すべき成果物を確定してから移行する。

実行順序は先行処理の出力を後続入力として使うデータ依存と、共有資源・同一ファイルの書込・認可による順序制約を分けて判定する。
先行出力が必要な処理は、その出力と終了状態を確かめてから開始する。
資料の内容で操作条件が決まる場合も、読取を終えて条件を確定してから操作する。
依存も資源の競合もない読取や作業は並行できる。

書き込み主体とworktreeの対応関係は`references/mandatory-rules.md`に従う。
レーン内で書き込み作業を分担する場合は、書込先を確定させた上で同一の専用worktreeへ担当者を配置する方法と、別branchおよび別worktreeへ一時的に分離した担当群（以下「内部群」）を設ける方法とを比較検討する。
どちらを選ぶかの条件と、同一worktree内での分担で守る事項は`references/mandatory-rules.md`「作業ツリーの保護」に従う。
内部群を運用する際は次のルールを遵守する。

- レーン担当者は、各ファイルと契約で結び付いているテストコードを群ごとに対応付けた所有表を作成し、書込所有権を明確に固定する。
  出力元のコードと完全一致を期待するテストのように契約で一体となっているファイルは、同一の群へ配置する。
- レーンbranchの確定済みcommitを分岐の起点とし、群同士で未解決の先行成果への依存が存在しない範囲に限って、群ごとの別branchと別worktreeへ分割する。
  各worktreeで書き込みを行う担当者は1名とし、1つのbranchに対してcommitやamendを実行する主体も1名に限定する。
  各群の担当者は自身のworktreeにおけるcommitおよびGit hookの処理を所有し、hookによって更新された生成物も同一のcommitに含める。
- 群の粒度と総数は、同時に稼働させる担当者の数と分けて、前述の比較検討に基づいて決定する。
  process-wiでは巡回全体の同時数Cを`../../process-wi/references/selection-procedure-allocation.md`「内部担当の同時数と巨大WIの判定」で選び、内部群を増やしてもレーン数上限と共有2枠の検証は維持する。
  粒度の選定を誤った場合の不利益は作業速度の低下にとどまり、品質自体は各群の検収によって担保する。
- 実装・焦点検証・commitが完了した群から、作成側と独立したレビューへ渡す。
  対象のHEAD・要求・直接影響集合・成功証拠を固定し、他群の編集中の本文を保存HEADのレビューへ混ぜない。
  起動と受理は`../../../share/exec-review-parent-launch.md`と`../../../share/exec-review-recording.md`に従い、全群の完了を待たずに進める。
- 検収、レーンbranchへの統合、および競合の解消はレーン担当者のみが実施する。
  群間の契約・共有生成物・組合せ差分・未達条件を確認し、同条件の受理済みレビューと検証結果を再利用する。
  統合後は、群の間で重複する生成物の差異を原本から同期し、すべての追跡対象ファイルにおける対象文字列、直接影響範囲、変更範囲のテストを確認した上で、一時的なworktreeとbranchを回収する。
  なお、内部群は同一要求の実装の一部として取り扱う。
