# 基本委譲契約：入力の適格性と追送

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 入力の適格性と追送

エージェント向け文書の修正を指示する場合は、同一の論点を修正するために必要なファイルを一度にすべて指定し、節名は該当箇所の所在の手掛かりとして提示する。
指定したファイル内で同一の論点に関連する別の節も、整合性を保つ修正範囲に含める。
新たな論点、指定されていないファイル、またはユーザーが明示的に限定した節の変更については、委譲元へ判断を差し戻す。
process-wiにおけるWI要求を境界とする書き込み判断は`../../../share/exec-subagent-implementation.md`「実装」に従うため、メインエージェントがファイルを個別に名指しする工程は追加しない。
現行の作業契約を保持している委譲元は、起動や追送の前、および結果の受領時に自身の記録を参照し、`share/work-contract.md`に基づいて作業の割り当てと当初の目的・現行要求を突き合わせる。
保持すべき対象と残存する完了条件を担当者へ引き渡し、通常の`task`や`delegate`が終了時に返却する`handoff_record_path`を読み込んで検収する。
自身の記録を更新するのは、要求内容や元の未完了作業への復帰先が変更された場合に限る。
自身の作業契約を持たない軽量起動の委譲先は、起動時のプロンプトと、そのプロンプトが参照を指示する資料を作業基準とする。

役割指定の`task`および`delegate`では、初回起動時も含めて`start`ツールの`whole_contract_path`引数に、委譲元が保持する現行の全体作業契約の絶対パスを渡す。
役割内部の起動設定の判別はサーバーに任せ、通常起動の場合だけ参照を検証・配送する。
軽量役割の`task`では指定値を参照せず、全体作業契約の本文と専用の引き継ぎ記録を追加しない。
自由本文の`explore`・`write`・`shell`と`handoff_from`はこの引数を渡す対象から除く。
通常起動の委譲先がさらに委譲する場合も、受け取った参照がそのまま継承される。
通常起動で`whole_contract_path`を省略した既存の起動は、互換性維持のため、直接の委譲元が起動時に受け取った参照、委譲元の会話のmanaged-temp配下にある`work-contract.md`の順で自動解決される。
明示的に指定された参照は、この自動解決よりも優先される。
次の2つのケースでは起動が拒否されるため、委譲元はそれぞれ適切に対処する。
委譲元の会話を特定できず解決元が存在しないことによる拒否では、正しい全体作業契約の絶対パスを指定して再実行する。
期待されるパスは特定できたもののファイルが未作成であることによる拒否では、`share/work-contract.md`に従って期待パスに記録を作成した上で同一入力を用いて再実行する。
未作成のまま期待パスを`whole_contract_path`に指定して再実行しても、ファイル不在として同様に拒否される。

初回の委譲プロンプトおよび稼働中の委譲先への追送指示に含める要素は、本節の基準に基づいて個別に判定する。
`delegation-sending.md`「送信」、`references/sending.md`、ならびに追送を中継する各工程の文書は、入力として許可する項目を本節に委ねている。
プロンプトに含めてよい内容は、委譲先が他の入力から取得できない次の要素に限定する。
`<役割名>.subagent.md`、agent定義、基準となる記録にすでに記載されている内容は、転記せずに該当する記録を参照させる。

- ユーザーの発話の逐語テキスト
- 作業の対象、ならびに参照すべき基準記録の絶対パスと対象ID
- 基準記録に含まれていない目的、要件、制約、完了条件
- 委譲元自身が実物で確認した事実、および実行時に確定した値
- 委譲先の`<役割名>.subagent.md`、プロジェクト規範、適用スキルで規定されていない権限と対象範囲
- 既存の規範が委譲プロンプトや追送に含めるよう定めている項目（前提を覆す追送において維持すべき成果と破棄すべき成果の範囲、`引き継ぎ記録先`、応答言語など）

委譲先の`<役割名>.subagent.md`、プロジェクト規範、適用スキルによってすでに決定されている実施手段は、初回のプロンプトにも追送指示にも追記しない。
重複して指示すると、委譲先はどちらを優先すべきか判断できず、委譲元による不適切な指示がそのまま成果物に反映される原因となる。

<例>
コミットをまとめるか分割するか
fixupとautosquashを使用するかどうか
検証方法の選択
pushを行ってよいかどうか
必須スキルの起動
</例>

具体的な手段をプロンプトに記述できるのは、ユーザー自身が手段を指定した場合、または目的・要件・制約を達成するためにその手段が不可欠であることが実装コード、公式仕様、実機での検証結果から裏付けられている場合（その根拠を併記する）に限る。
委譲元自身が選んだにすぎない実装手段を指示として固定すると、委譲先による調査や最適な設計の選択肢を狭めてしまう。
記述の粒度については、`agent-basics:writing-standards/references/writing-readers.md`「読み手別の追加注意点」のエージェント向け文書の項に従う。
必須入力の形式やユーザーが明示的に指定した手段は、省略せずに確実に引き渡す。

操作の許可や禁止を指定する場合は、対象リポジトリと操作内容をペアにして明示する。
対象リポジトリと、WIや計画ファイルを保存するprivate-notesリポジトリは、別個の対象として区別して扱う。
ユーザーからの要求を引き渡す際は、採用した要求の原文と出所を`forwarded-user-input`標識の内側に配置し、起動前に原文と標識が整合していることを確認する。
自然言語による単なる引用にとどまると、委譲先が出所を判別できなくなる。

追送する要件は内容を確定させてから送信する。
確定した要件であれば、委譲プロンプトの前提（対象、範囲、外部から観測可能な結果、判断基準）を覆す内容であっても先行タスクの応答を待たずに直ちに追送し、維持すべき成果と破棄すべき成果の範囲を追送文の中で明確に示す。
追送によって既存の成果を引き継ぐことが不可能な場合に限り、実行中のタスクを終了させて新しい委譲先を起動する。
稼働中の委譲先の強制停止は最終手段とし、停止によって失われる書き込み内容、未着の報告、コンテキストを確認し、回収可能な成果物をすべて回収してから停止を実行する。
