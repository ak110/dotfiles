## 長時間待機前の会話圧縮

Claude Codeのメインエージェントが、他の担当者やCI監視の結果を後続工程の入力として待つ際の共通手順である。圧縮を予約するタイミングと保存すべき工程状態は、呼び出し元の工程手順に従う。
独立して実行できる先行工程を先に開始してから待機へ進む。圧縮が行われた後は、注入された要約を起点にし、不足する情報だけを担当別の記録、選定原本、監視状況、保存出力、`atk agents list --include-terminated`、`atk agents show <session_id>`、会話原文から取得する。

1. `mcp__agent-toolkit__compact_conversation`が存在しない環境では、前提が成立しなかった旨を引き継ぎ記録に残したうえで通常の待機へ進む。なお、Codexは本手順の対象外とする
2. 対象ツールを引数なしで1回呼び出す。予約の受付と圧縮の完了を区別し、圧縮が完了するまで予約は1件のみに維持する。Claude CodeのFunction hooks moduleは追加の指示を与えずにターン間で`session.compact()`を実行するため、予約入力は空のまま保持する
3. `agents_server`の結果を待つ区間では、引数を指定せずに単独の`atk agents wait`をBashのバックグラウンドタスクとして起動する（`session_id`は結果の突き合わせにのみ使用し、待機コマンドの引数からは除外する）。CI監視を待つ区間では、すでに起動している`wait_ci.py`のバックグラウンドタスクをそのまま維持し、新たな監視タスクの追加は避ける
4. Monitorツールで前景を占有することなく現在のターンを終了し、届いた完了通知と保存された全出力から待機の終了状態を回収する
5. 完了通知を受け取った後は、注入された要約と受け取った結果を突き合わせ、必要に応じて既存記録を読んで同じ工程から作業を再開する。会話圧縮が失敗した場合も既存の担当作業や監視を継続する。予約の失敗、圧縮の成功、待機結果はそれぞれの既存記録へ残す

Claude Codeのメインエージェントが背景のBashで単独の`atk agents wait`を起動した場合は、フックモジュールが同じ圧縮予約に接続する。
バックグラウンドタスクが5秒以上継続しており、コンテキスト利用率が50%以上で、ターン間である場合に限り、自動圧縮が実行される。
あわせて、待機所有の登録状況と起動区分を確認し、自身が待機しているexploreやshell以外の担当タスクが残っていることも確かめる。これらの状態確認は、既存の記録を一度読み取る`atk run-script wait-compaction-context`が担当する。
同一の背景待機における圧縮は1回までに制限し、圧縮が成功した後にコンテキスト利用率が高いまま推移しても、その待機中に再圧縮することは避ける。利用率が閾値未満に下がったことを確認した後の新たな作業であれば、再び圧縮の対象とできる。
スキップや失敗が発生した場合は予約を解除して通常の結果回収を継続し、同一の背景待機に対する自動再試行は除外される。
単発タイマーやターン完了通知を活用し、不要な継続ポーリングや圧縮のためだけのLLMターンを追加しないようにする。Codex環境では、ホスト標準の圧縮機能と同じ状態復元手順を利用する。

## 背景ジョブの起動形（Claude Code）

- 待機処理の起動方法は「待機区間の構成」に従う。待機以外の検証やビルドなど、実行に時間を要する通常のコマンドは、Bashツールのタイムアウト引数を上限まで引き上げたうえで前景実行するのが基本であり、その時間内に収まらない場合は対象を絞り込んで複数回の前景実行に分割する
- 待機は完了通知や定期的な再確認を通じて処理し、Monitorや完了マーカーを用いた前景でのループ処理への回帰は避ける。待機以外のバックグラウンドタスクで全出力を取得する用途にはMonitorを利用できる。また、ツール側で背景実行を指定したコマンドに対して、さらにシェル上で`&`や`nohup`を重ねない（シェルの終了が先に完了通知として届いてしまうためである）
- リモートホスト上で`nohup`や`setsid`を使ってプロセスを切り離す起動方法は、完了通知を受け取れないため、エージェント自身が一時的に応答不能となる工程に限って使用する。それ以外の処理では、`run_in_background=true`でSSH接続を維持するか、対象を絞り込んだ前景実行とする
- コマンドの終了状態と出力内容は、起動時の結果に含まれる出力ファイルの絶対パスから取得する。このファイルは実行識別子とは独立してディスク上に残り、出力の全量と`[exited with code <整数>]`という形式の終了状態行を含んでいる（実行識別子自体は実行環境の再起動によって失効する）。監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」にある。同じ文の記録は「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月4日」にもある。待機タスクを別のセッションやエージェントへ引き継ぐ場合は、このファイルパスもあわせて引き継ぐ。監査記録は`docs/development/audit-records.md`に記載されている。対象見出しは「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」および「2026年9月4日」である
- 処理が完了したか失敗したかは、保持している実行識別子によるプロセスの生存確認と、出力ファイル末尾の終了状態行によって判定する。出力ファイルが空の場合は判定を保留する。自身が所有するタスクであっても、再起動や巻き取りを行う前に生存状態を確認し、プロセスが生存している間における同一処理の重複起動は避ける。完了通知と実際のプロセス終了の順序関係については、`references/claude-code-runtime.md`の「背景ジョブ完了通知と実プロセスの終了順」を参照する。ホストからの停止通知を受けた場合は、`references/wait-anomalies.md`の「ホストによる背景待機の停止後」に従って元の待機状態と出力を回収する
