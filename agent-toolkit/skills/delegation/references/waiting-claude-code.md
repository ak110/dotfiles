## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 長時間待機前の会話圧縮

Claude Codeが、他の担当者やCI監視の結果を後続工程の入力として待つ際の共通手順である。
手動予約は対象ツールがある対話セッションで使い、agents_serverの委譲先は後述する所有バックエンドの自動予約を使う。
予約の時機と工程状態は呼び出し元の手順に従う。
独立して実行できる先行工程を先に開始してから待機へ進む。
圧縮後は原本ログと、担当別の記録、選定原本、監視状況、保存出力から目的・最新の訂正・認可・未完了の操作を復元する。
要約が渡されるホストでも、要求と認可の確定には原本を使う。
原本は発話順・主体・参照位置を保ち、必要な本文を範囲指定で取得する。

1. `mcp__agent-toolkit__compact_conversation`が存在しない環境では、前提が成立しなかった旨を引き継ぎ記録に残したうえで通常の待機へ進む。
   なお、Codexは本手順の対象外とする
2. 対象ツールを引数なしで1回呼び出す。
   予約の受付と圧縮の完了を区別し、圧縮が完了するまで予約は1件のみに維持する。
   Claude CodeのFunction hooks moduleは追加の指示を与えずにターン間で`session.compact()`を実行するため、予約入力は空のまま保持する
3. `agents_server`の結果はBashの背景機能が公開されている場合に、引数なしの単独の`atk agents wait`を背景で起動して待つ（`session_id`は結果の突き合わせにのみ使う）。
   背景機能が無い場合（SessionStartが背景実行の無効を通知し、Bashの公開入力に`run_in_background`が無い場合）は「待機区間の構成」に従い、前景のBashへ`timeout=600000`を指定して同一ターン内に結果を回収する。
   CI監視では、すでに起動している`wait_ci.py`のタスクを維持する
4. 背景待機では現在のターンを終了し、届いた完了通知と保存された全出力から終了状態を回収する。
   前景待機はCLI自身の期限で返る終了コードを回収し、未終了なら同じコマンドで待機を続ける
5. 完了通知を受け取った後は、復元した要求と受け取った結果を突き合わせ、同じ工程から作業を再開する。
   会話圧縮が失敗した場合も既存の担当作業や監視を継続する。
   予約の失敗、圧縮の成功、待機結果はそれぞれの既存記録へ残す

   Claude Codeの直接の`/compact`入力とホスト標準の自動圧縮では、原本ログの所在へ置き換えられる場合に要約の生成を省く。
   同じプラグインからの`session.compact()`予約は自身の置換フックが再入除外されるため、標準の要約生成を使う。
   この経路でも復元時には原本を確認する。
   原本置換の適用範囲と再検証は`docs/development/audit-records-compaction.md`「agent-toolkit/hooks/compact_conversation.ts：原本参照圧縮：2026年11月2日」にある。

   Claude Codeのメインエージェントが背景Bashで結果を待つ場合は、フックモジュールが同じ圧縮予約に接続する。
   CI監視も対象とする。
   バックグラウンドタスクが60秒以上継続し、使用量が400,000トークンと文脈上限の40%の大きい方以上で、ターン間である場合に自動圧縮する。
   `atk agents wait`では、既存の記録を読む`atk run-script wait-compaction-context`が待機の所有と未完了の担当を確認する。
   delegate・write・explore・shellの全起動区分を対象とする。
   agents_serverが起動したClaude委譲先では、所有バックエンドがバックグラウンドタスクの完了待ちを確認し、同じ時間・使用量条件で公開`/compact`入力を1回予約する。
   SDKはターン間の`session.compact()`を受け付けないため、所有する入力キューで通常の追送と直列化する。
   配送直前に同じ待機が続くことを再確認し、圧縮のturnが終わった後も結果を待つ保留を維持する。
   圧縮の受付・完了は担当作業の完了とは区別する。
   同一の背景待機における圧縮は1回までに制限し、圧縮が成功した後にコンテキスト利用率が高いまま推移しても、その待機中に再圧縮することは避ける。
   利用率が閾値未満に下がったことを確認した後の新たな作業であれば、再び圧縮の対象とできる。
   スキップや失敗が発生した場合は予約を解除して通常の結果回収を継続し、同一の背景待機に対する自動再試行は除外される。
   Codexの委譲先でも、所有バックエンドが結果保留と未完了の子・バックグラウンドタスクを確認し、同じ時間・使用量条件で公開`thread/compact/start`を1回実行する。
   Claude・Codexとも全起動区分の委譲先に適用する。
   圧縮は別turnとして完了を観測し、担当の応答・turn ID・待機対象を保持する。
   通常の追送は圧縮の完了後に配送する。
   受付後に時間上限を超えても完了とは扱わず、後着の完了または接続終了まで実行状態を保持する。
   セルやコマンドの実行識別子を同じturn内に回収するCodex最上位の待機は、ターン間の背景待機条件を満たさないため、この自動予約を起動しない。
   ホスト標準の圧縮と文脈上限設定を保持する。
   確認した公開入力と再検証は`docs/development/audit-records-delegation-waiting.md`「agent-toolkit/skills/delegation/references/waiting-claude-code.md：Codex最上位の待機条件：2026年11月2日」にある。
   単発タイマーやターン完了通知を活用し、不要な継続ポーリングや圧縮のためだけのLLMターンを追加しないようにする

## 背景ジョブの起動形（Claude Code）

1. 待機処理の起動方法は「待機区間の構成」に従う。
   待機以外の検証やビルドなど、実行に時間を要する通常のコマンドは、Bashツールのタイムアウト引数を上限まで引き上げたうえで前景実行するのが基本であり、その時間内に収まらない場合は対象を絞り込んで複数回の前景実行に分割する

2. Bashの背景機能が公開されている場合は、待機を完了通知や定期的な再確認で処理する。
   背景機能が無い場合は「待機区間の構成」の前景回収を使う。
   待機以外のバックグラウンドタスクで全出力を取得する用途にはMonitorを利用できる。
   ツール側で背景実行を指定したコマンドに、シェル上の`&`や`nohup`を重ねない（シェルの終了が先に完了通知として届くため）

3. リモートホスト上で`nohup`や`setsid`を使ってプロセスを切り離す起動方法は、完了通知を受け取れないため、エージェント自身が一時的に応答不能となる工程に限って使用する。
   それ以外の処理では、Bashが背景機能を公開していれば`run_in_background=true`でSSH接続を維持するか、対象を絞り込んだ前景実行とする

4. コマンドの終了状態と出力内容は、起動時の結果に含まれる出力ファイルの絶対パスから取得する。
   このファイルは実行識別子とは独立してディスク上に残り、出力の全量と`[exited with code <整数>]`という形式の終了状態行を含んでいる（実行識別子自体は実行環境の再起動によって失効する）。
   監査記録は`docs/development/audit-records-delegation-waiting.md`にある。
   該当節は「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」である。
   同じ文の記録は「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月4日」にもある。
   待機タスクを別のセッションやエージェントへ引き継ぐ場合は、このファイルパスもあわせて引き継ぐ。
   監査記録は`docs/development/audit-records.md`に記載されている。
   対象見出しは「agent-toolkit/skills/delegation/references/waiting-and-monitoring.md：背景ジョブの起動形（Claude Code）：2026年9月2日」および「2026年9月4日」である

5. 処理が完了したか失敗したかは、保持している実行識別子によるプロセスの生存確認と、出力ファイル末尾の終了状態行によって判定する。
   出力ファイルが空の場合は判定を保留する。
   自身が所有するタスクであっても、再起動や巻き取りを行う前に生存状態を確認し、プロセスが生存している間における同一処理の重複起動は避ける。
   完了通知と実際のプロセス終了の順序関係については、`claude-code-runtime-receiving.md`「背景ジョブ完了通知と実プロセスの終了順」を参照する。
   ホストからの停止通知を受けた場合は、`wait-anomalies-stopped.md`「ホストによる背景待機の停止後」に従って元の待機状態と出力を回収する
