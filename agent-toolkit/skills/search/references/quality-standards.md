# 日本語の書き方

伝える内容を肯定文で直接書き、主張を際立たせるために否定する側を並べる対比フレーミングを禁止する。否定は肯定文から読み取れず読み手の判断に要る実在の制約、選択肢または誤解に限り、独立した事実の文で示す。

行為者、対象、動作、条件と結果を文と前後の文脈から読み取れる形で書く。省略した要素の補い方が一意に定まり、動詞の意味が読み手と共有され、主題と述語の関係が成立することを確かめる。参照先が曖昧な代名詞は対象名へ戻し、同じ段落で一意に分かる指示語は残す。主語の文頭配置や受動文の排除を一律に求めず、自然な語順を保つ（努力目標）。

操作や状態が分からない比喩、漢語と名詞の過剰な連結は、動詞と助詞を補って文全体を組み直す。表現の不自然さを指摘するときは、その文や句から成立しない関係を説明し、別の箇所や専門知識との不一致から判断する内容の誤りと区別する。定着した専門用語、字義通りの動作、文脈から一意に復元できる省略、見出しと必要な一覧、規範の体言止めは保つ（努力目標）。

機械の処理へ、人や物の動きを当てはめた動詞の使用を禁止する。`拾う`・`引く`・`通る`・`効く`・`響く`・`足す`などは実際の処理を示す語へ書き換える。書換えには取得する・読み取る・抽出する・成立する・許可される・作用する・追加するなどの語を使う。

仕組みを場所にたとえる名詞の使用を禁止する。`入口`、`受け口`、`口`、`依存先`などは公開エンドポイント、起動コマンド、呼び出し元、接続先URLなど、指す構成要素の名称へ書き換える。WI間の`depends_on`、ソフトウェア、パッケージまたはモジュールのdependencyを示す`依存`と`依存先`は技術用語として使える。
一般の文章の成立条件や、単なる通信相手・接続先には、この技術用語を使わず、前提条件や接続先を具体的に書く。

英語の定型句を語ごとに訳した表現の使用を禁止する。`足すものがない`は「得られるものがない」、`失効が効く`は「次のリクエストから拒否される」など、日本語として処理結果が直接分かる文へ書き換える。

物の呼び名は、読み手がその分野で自分で書くときの呼び名にそろえる。文が長くなっても、仕組みや物を書き手が思いついた短い1語のたとえや言い換えで済ませず、分野の名称で書く（リクエストを`要求`、夜間バッチを`夜間の処理`と書き換えない）。図の箱や表の列名のように短く書く場所ほど置き換えが起きやすいため、同じ基準を適用する。
動詞も、`届く`・`動く`・`入れる`・`受ける`のような抽象的な短い語で済ませず、読み手の分野の言葉で何がどうなるかを書く（インフラ担当者向けに`社内VPNからしか入れない`を「社内VPNからしかアクセスできない」、デザイナー向けに`Figmaの値がボタンに届く`を「Figmaの値がボタンに反映される」と書く）。

素材やメモに出てくる作業用の名前（実験の条件名、ブランチ名、集計で付けた区分の名前など）は読み手が知らないため、そのまま書かず、何を指すかを言葉で書く。
文書の中で新しく短い呼び名や略称を定義して読み手に覚えさせる書き方（`以下「高」と呼ぶ`など）を避け、言葉で書けば済むなら言葉で書く。呼び名を導入する場合は、名前だけで中身が分かる語にし（住所と支払いを1画面にまとめた案を「1画面案」と呼ぶなど）、同じ文書の中では最後まで同じ名前で統一する。

システムの動作は、その主体で説明する。意志や感情を仮託する擬人化や、判断した主体と根拠を隠す推量は、動作または判断と根拠を対応付けて書く。文長や文末の指標だけを満たすための分割や言い換えはせず、条件と結果の関係、時制と確実性を保つ（努力目標）。

```text
例文: 設定ファイルが存在する場合、CLIは指定された保存先へ結果を書き込む。
説明: 条件はファイルの存在、動作の主体はCLI、対象は指定された保存先であり、書き込まれる結果との関係が読み取れる。
```
