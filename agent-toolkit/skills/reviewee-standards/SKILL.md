# レビューイー側心得

本スキルは、レビューイーが指摘を検証し、採否と修正を確定する際の知識を提供する。
指摘の根拠となる原文と対象への適用条件を最初に確認せよ。
レビューを実施する主体は、`agent-toolkit:review-standards`の`SKILL.md`を全文読む。

## 指摘の検証

指摘が根拠とする原文と対象への適用条件を確認し、指摘の成立性と修正方法を別々に確定する。
各指摘の事実と違反契約を自身でも実測する。
外部実行環境の挙動、既存実装の挙動又は既存契約を根拠とする指摘では、採否確定前に対象実装と契約本文を実読するか、公式一次資料若しくは実機再現で成立性を裏付ける。裏付けを取得できず採否を確定できない場合は、取得できない理由を明記して呼び出し元へ返す。
根拠や適用条件が不足する指摘は再取得するか`未検証`へ分離する。
好み、将来仮定、目的外改善、裏付けの無い候補は採用しない。

レビュー担当の指摘は、レビュー担当が立証済みの事実として扱わない。
レビューイーは指摘の原文、適用条件、通常運用での再現経路及び利用者影響を独立に測定し、
実在する欠陥かを確定する。採用する場合も、レビュー担当の修正案を複写せず、
確認した欠陥を解消する必要十分な対策だけを選ぶ。

重大度ラベル付きの指摘では、受領した指摘が持つ値をそのまま用い、重大又は中程度の実在欠陥だけを採用する。
重大度を持たない指摘や改善提案では、観測事実、違反する契約、利用者影響への対応から採否を確定する。
重大度の定義を照会する目的でレビュー担当側スキルを読み込まない。

## 採否の独立確定

採否確定前に、指摘を通常運用の再現経路と入力主体へ照合し、問題と手段の比例性を独立に再判定する。
対象外の入力前提又は異なる脅威モデルだけで成立する候補は不採用とする。
レビュー担当の修正方針を新しい要件として扱わず、複写するだけで採用しない。
修正に永続状態、所有権、期限、復旧経路、互換経路の新設が必要な場合は、元の目的と非目標へ差し戻す。
比較階層と比例性の判定は、`../review-standards/references/judgment-details.md`を解決して正本とする。

## 修正の実施

成果物に責任を持つ最上位の主体が確定した範囲内で最小限に修正する。
採用指摘と同じ混入要因、動機的要因、見逃し原因が及ぶ箇所を確認し、成立する欠陥を同じ修正回で一括修正する。
横展開の単位は採用指摘が示す違反契約または新設・変更機構とする。対象実装の該当箇所だけでなく、実装コード、テスト、規範文書と計画本文の全出現箇所を`grep -n`で列挙する。検索コマンド、一致件数、各一致箇所と修正の対応を成果物へ記録してから再レビューへ送る。残存が引用・変更履歴だけである場合は、その範囲を記録する。
新設・変更機構を単位とする場合は、受け渡し文書、status一覧、担当種別定義、機械検査、完了条件と同期テストを含む全接続先契約面の対応表を作成し、同じ修正回で照合する。
直前ラウンドで自身が追加又は変更した箇所への再指摘では局所修正を止め、再設計・簡素化・撤去を同じラウンド内で比較し、採用した結果と不採用理由を記録する。
同一箇所、同一の違反契約、同一の新設・変更機構のいずれかへの指摘が2ラウンド連続して成立した場合も同じ比較をする。
比較の対象には、計画と既存の設計のいずれかが指定した方式そのものを撤去する案を必ず含める。
当該方式の枠内で条件を追加する案だけを比較対象にしない。

計画又は上位の設計が指定した方式の枠内では契約を満たせないと判明した場合は、当該方式を保ったまま条件を追加せず、
当該指定が不成立であることを、成立しない理由と実測の根拠を添えて呼び出し元へ差し戻す。

前記の比較を経てもなお同じ単位へ指摘が成立し、連続3ラウンドへ達した場合は、当該単位の処置を自ら確定せず呼び出し元へ返す。
いったん採用した変更の撤去と同一内容の復元をともに観測した場合も同じ扱いとする。
返却内容には対象の単位、各ラウンドの指摘と期待値、比較した案と不採用理由、確定できない理由を含める。
呼び出し元が当該単位の処置を確定して指示した場合は、当該指示のとおり反映し、当該単位へ追加のレビューラウンドを求めない
（厳守規定。確定経路が無いと、同一単位の修正が往復し続けて収束しない）。

初回と第2回での収束を目標とする。第3回へ入る場合は、直前ラウンドの各指摘を「起草時又は実装時に判断可能」
「初回レビューの見逃し」「直前修正による混入」へ分類し、レビュー担当側と自身のいずれに帰属するかを判定して成果物へ記録する。
見逃しが主である場合は次ラウンドのレビュー担当へ契約単位の全走査を求め、直前修正による混入が主である場合は
提出前に修正自体を検証する工程を追加する。

## 修正後の自己点検

レビュー指摘管理表はラウンド、重大度、指摘箇所、指摘内容、対応要否、対応内容、対応不要理由の固定7列TSVとする。
表が指定されている場合は系統ごとに別の表を使い、初回strict検証の前に調整主体が`atk review-table init <レビュー表>`を実行する。
レビューイーは各ラウンドの開始時に`atk review-table validate --allow-unanswered <レビュー表>`を実行して自身へ渡された表の構造を検証する。
検証後に表を全文読み、
行を一意に特定できる列だけを指定して`atk review-table respond`で対応要否・対応内容・対応不要理由だけを更新する。
先頭4列は変更せず、応答更新後は同じ構造検証を再実行する。全行への応答を終えたら
`atk review-table validate <レビュー表>`で全件応答済みを検証する。
各レビュー担当は新規起動でも同一thread継続でも同じ系統表を検証・全文読取し、今回のラウンドとして同じ表へ指摘を追加する。
両系統の担当が終端した後に、レビューイーは修正対象となる全系統表を全文読取する。
その後、調整主体が系統の帰属を保ったまま各表を統合する。盲検系のレビュー担当へ準拠系の表を渡す境界は維持する。

採用した各指摘について、指摘が引用した違反契約の原文を修正後の成果物へ再適用する。
当該箇所で違反が成立しないことを確認する。
保持契約と合意済みの除外・保持が維持されていることを確認する。
呼び出し文脈が定める検証の再実行を完了する。

修正で新たに書いた文は、採用指摘が引用した契約に加えて確度、因果、出所を点検する。
確度は提示素材・観測が推量に留まる事項を断定へ変えないこと、
因果は実測で裏付けていない一律帰属を書かないこと、
出所はエージェントが導出した理由を利用者由来と解釈され得る形で並置しないこととする。
確度を弱める場合は、根拠となる観測範囲を同じ文へ残す。
修正で対象の選択・解決条件を新設又は変更した場合は、判定に用いる入力（外部コマンド出力の全項目、実装の分岐、設定の全経路）を実読し、選択条件が対象集合を過不足なく定めることを確認する。
