# レビューイー側心得

本スキルは、レビュー指摘、改善提案、ユーザーの割り込みや是正要求、作業中の想定外の発見を受領した主体が、修正の必要性を立証し、安全な修正と検証を完了するための知識を提供する。
以下では、これらを是正要求等と呼ぶ。
是正要求等の根拠となる原文、対象への適用条件及び現在の成果物を最初に確認せよ。

## ユーザー指摘の受領

ユーザーの指摘・割り込み・是正要求は、`agent-toolkit/rules/01-agent.md`「問題を見つけたときの対処」に従って扱う。

- 対処に着手する前に、指摘が示す事象の解釈候補を列挙し、指摘の根拠となる原文・実装・規範を読んで
  観測事実と照合する。照合後も解釈候補が2つ以上残る場合は`AskUserQuestion`で意図を確認する
- 是正内容が確定するまで、稼働中の委譲先へ当該指摘に基づく追加指示を送らない
- 同一トピックでの即時差し替えが2回以上（目安）発生した時点で`AskUserQuestion`へ切り替える
- 指摘は当該判断の是正のみを求めるものであり、以降の自律実行義務は変わらない

## 修正要否の立証

指摘は、観測事実、違反する目的又は契約、対象への適用条件、通常運用で生じる実害及び裏付けを照合して採否を確定する。
いずれかの根拠が不足する行は採否を確定せず、証拠不足の範囲と必要な検証をレビュー工程へ返す。

レビュー担当の指摘は、レビュー担当が立証済みの事実として扱わない。
各指摘の事実と違反契約を自身でも実測する。
対象実装と契約本文の実読、公式一次資料又は実機再現により、通常運用での再現経路及び消費主体への影響を独立に測定する。
裏付けを取得できない是正要求等は修正対象から分離し、証拠不足の範囲と必要な検証をレビュー工程へ返す。
好み、将来仮定、目的外改善、対象外の入力前提か異なる脅威モデルだけで成立する候補は採用しない。

採否確定前に、問題と手段の比例性を独立に再判定する。
レビュー担当の修正方針を新しい要件として扱わず、複写するだけで採用しない。
何も変更しない案を含め、残置した場合の実害と認知・保守費用、修正・検証・再レビューの費用、変更が増やす複雑性を同じライフサイクルで比較する。
実害がなく意味も変えない単独の誤記は、独立した修正と再レビューを起こさない。
同じ成果物に重大な修正があり再レビューする場合は、追加費用が小さい誤記も同時に是正する。
エンドユーザー向け文書の誤記と適用対象のスタイル違反、重大な実害、明示要件違反、公開契約違反及びセキュリティ欠陥は、費用だけを理由に残置しない。
比較階層と比例性の判定は、`../review-standards/references/judgment-details.md`を解決して正本とする。

ロック、書込所有権、排他、復旧又は移行を根拠とする指摘では、要件の出所、対象操作、操作主体、競合主体及び両操作が同時に成立する条件を原文、対象実装及び通常運用から独立に照合する。

別操作の要件又はレビュー中に追加した機構を元のユーザー要求へ帰属させない。

ユーザーの是正又は実測により指摘の前提が失効した場合は、次回レビュー前に、その前提だけへ依存する指摘、修正方針及び追加機構を修正対象と成果物から撤去する。前提に依存しない是正要求等は、同じ採否契約で個別に再判定する。

計画ファイルの章構成、段落構成、表現選択、書き方又は情報配置だけを変える指摘は採用しない。
記述間の矛盾は、実装時の判断で解消できず、計画の実施可能性か公開契約を損なう場合だけ採用する。
いったん不採用とした案を再採用する場合は、不採用時の原文と根拠を読み直し、当時の理由が失効したことを現行の実測で確認する。
理由の失効を確認できない場合は再採用せず、必要な判断を呼び出し元へ返す。

## 安全な修正

修正が必要だと立証できた場合だけ、確認した欠陥を解消する必要十分な対策だけを選ぶ。
最小差分ではなく、元の目的、公開契約及び原因に対して必要十分な変更範囲を採用する。
同じ違反契約が通常運用で再現する範囲を実装コード、テスト、規範文書と計画本文から検索し、成立する欠陥を同じ修正回で一括修正する。
文字列、見出し、目的語又は接続関係だけが似る箇所は修正範囲へ含めない。
検索方法、確認した範囲、各箇所の採否及び修正との対応を、呼び出し文脈が指定する成果物へ記録する。

修正前に、同じ対象の過去の指摘、採否、ユーザー合意、設計理由及び事故対策を確認する。
過去の不採用理由が失効していない案、保持対象、除外範囲か既存の成功経路を、局所修正の都合で変更しない。
修正に永続状態、所有権、期限、復旧経路か互換経路の新設が必要な場合は、元の目的と非目標へ差し戻す。
計画又は上位設計が指定した方式で契約を満たせない場合は条件追加を重ねず、不成立の理由と実測を呼び出し元へ返す。
`対応要否`を`yes`とする行では、対応内容の先頭へ、確認した違反契約、採用する修正範囲、及び採用しない修正方針又は対象範囲を記録する。
指摘が示す手段は候補として扱い、待機、同期、状態、完了条件又は対象ファイルを新設又は変更する場合は、当該変更が違反契約を解消する理由と、変更しない既存経路を同じ対応内容へ記録する。
修正方針が新しい実機検証、待機、同期、復旧・完了条件を要求する場合は、修正差分を適用する前に、その経路を一度成立させる。現行の許可ツール、実行主体、入力及び終了条件を用いる。
成立しない場合は、当該経路が成立するとは記述しない。要求された検収を文面照合その他の代替手段へ置換せず、`対応要否`を`no`とする。探索した実行経路と各経路が成立しない観測を`対応不要理由`へ記録する。到達可能性の判定は`../review-standards/references/judgment-details.md`「検収経路の到達可能性」を正本とする。

承認済みの計画に基づく実装工程（実装担当、レビュー修正担当、CI修正担当及びこれらを統括する主体）では、修正を確定する前に計画ファイル（メイン）の`## 実施内容`、`## エージェント判断`及び`## 変更履歴（計画時）`を読む。既存実装との不整合、規範との不整合、実装上の都合のいずれかを理由に、計画が確定した目的、方針、採否、対象範囲又は除外・保持を覆す修正を確定しない（厳守規定。承認済み計画を実装工程の判断だけで反転させると、ユーザーが合意していない成果物が確定する）。計画自体を更新する計画レビュー工程は本規定の対象外とする。
計画の確定内容と既存実装若しくは規範が矛盾する場合は、`## 実施内容`の`由来`列と`## 変更履歴（計画時）`から計画側の由来を確認し、対立する既存実装又は規範を導入した変更の由来も調べたうえで、`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」を適用する。計画側が上位となる場合と、いずれかの由来を確定できない場合は、修正を適用せず、矛盾する計画の記述、対立箇所の位置及び調べた由来を呼び出し元へ返す。ユーザー接点を持つ主体は、この差し戻しを確認経路へ送り、回答を得てから計画と成果物へ反映する。

直前の修正後に同じ問題が再発した場合、又は前回の是正と同じ違反契約若しくは同じ根本原因を示す指摘を同じ成果物・責任範囲で再び受領した場合は、局所修正を止める。
修正へ着手する前に`agent-toolkit:bugfix`をSkill機能で起動して拡張原因分析の要否判定を適用し、変更した契約とその判断を直接消費する箇所を影響範囲の母集団として列挙する。識別子と文言の検索一致は母集団を抽出する補助に限り、母集団の定義に用いない。
母集団の各箇所について既存欠陥と予防対象を確定したうえで、現在の設計の維持、再設計、簡素化及び撤去を比較する。
欠陥を解消し、新たな問題を作成しない案を立証できない場合は、追加修正を確定せず、比較した案と確定できない理由を呼び出し元へ返す。
ラウンド数、指摘の分類、記録と収束判定は、呼び出し文脈が指定するレビュー調整側の正本へ委ねる。

## 公開可能性の検証

採用した各是正要求等について、違反契約の原文を修正後の成果物へ再適用し、違反が解消したことを確認する。
変更全体を通読又はレビューし、元の目的、明示要件、公開契約、保持・除外対象及び既存の成功経路を維持していることを確認する。
修正で新たに書いた内容は、確度、因果及び出所を点検し、推量の断定、未実測の一律帰属及びエージェント判断のユーザー由来化を除く。
対象の選択条件又は解決条件を変更した場合は、判定に用いる全入力と全分岐を実読し、対象集合の過不足と変更しない入力の結果を確認する。

変更に最も近いテスト、lint、format、型検査、生成物同期と、呼び出し文脈が定める全体検査のうち該当するものを実行する。
失敗、警告、検証不足の範囲と修正による新たな問題を残したまま完了しない。
成果物が修正直後の状態で公開されても事故を起こさないと、実測結果と自己点検から説明できる状態だけを修正完了とする。
説明できない場合は修正を確定せず、不足する検証又は判断を呼び出し元へ返す。

レビュー表が指定された場合は、渡された修正対象の`track`集合だけを扱う。
渡された集合の外に属する`track`の行を採否判断と更新の対象にせず、`atk review-table`の公開CLI契約に従って応答と検証を完了する。
実装レビューでは、修正対象を`implementation-review`の単一trackに限定する。
実装レビュー担当へ渡す情報は、調整主体が指定した`review_contract`と直接影響範囲を超えて自ら拡張しない。

## 完了報告

採否、修正方針、対応結果及び検証結果は、指定されたレビュー指摘管理表と成果物へ記録する。
修正完了時は`対応完了`だけを返す。

全修正が誤記、空白、Markdown整形又は意味が一意な参照訂正など、意味・動作・契約を変えない機械的修正だけの場合は、
`対応完了（再レビュー不要）`を返せる。コード、設定値、制御フロー、公開契約、テスト期待値か計画の実装方針を変える修正と、判断に迷う修正は`対応完了`を返して再レビューへ進む。
続行不能時はエスカレーション内容だけを返す。
