# プロンプトの改善案の検討

本スキルはエージェントへの指示文を前提知識の無いプロンプト評価担当に読ませて指摘を集め、メインが改善案と採否を確定して反映する手順を提供する。採否の判断主体は起動の目的に従う。プロンプト評価担当の入力・手順・出力は`${CLAUDE_PLUGIN_ROOT}/share/refine-prompt.subagent.md`が、起動と受領は`${CLAUDE_PLUGIN_ROOT}/share/refine-prompt.parent.md`が定める。本スキルは起動の契機、指摘の集約と採否の工程を持つ。

## 読込表

次の時点または条件が成立したら、その操作の前に同じ行の資料を全文読む。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 改善案を作成する前（エージェント向け文書が対象の場合） | `agent-toolkit:writing-standards`の「エージェント向け文書の編集時に読む資料」 |
| プロンプト評価担当を起動する前 | `${CLAUDE_PLUGIN_ROOT}/share/refine-prompt.parent.md` |

## 使用条件

frontmatterの発火条件に加えて、頻繁に使うskillや自動化の中核プロンプトを堅牢化したい場合にも使う。
挙動の不一致を起点にする場合は、指示文の追記へ進む前に`agent-toolkit:writing-standards`の`references/agent-documents-additions.md`「規範追記時の判定」に従い、工程の変更と機械化を評価する。

## 使用しない条件

- 単発利用のプロンプト（プロンプト評価担当の起動コストに見合わない）
- 再現可能な品質改善ではなく、書き手の主観的選好を反映したい場合

委譲手段を利用できない環境での扱いは「環境制約」節に従う。

## ワークフロー

本スキルはPlan modeの外で実行する。実行環境がPlan modeを提供する場合はPlan modeを抜けてから開始する。Claude Codeでは`ExitPlanMode`を使う。
`agent-toolkit:plan-mode`スキルは呼び出さない
（本スキルは評価と改善案の反映を扱い、元の依頼にある計画の作成要否を変更しないため）。

1. メインは`agent-toolkit:writing-standards`スキルを呼び出す。
2. 対象を確定し、シナリオに従う実行評価か、シナリオなしの批判的通読かを選ぶ。解釈・裁量による補完、不明瞭・冗長・不足・誤り・過剰指定を評価する。
   シナリオは初回に決めた内容を反復の間も保ち、反映に合わせて容易にしない。
3. 対象の分量と論点数に応じてプロンプト評価担当の起動数を1体以上として決め、読込表の行の`refine-prompt.parent.md`に従って起動し、指摘を受領する。
4. 各プロンプト評価担当から戻った指摘を集約し、改善案を作成する。提示と採否の確定は「指摘の集約と改善案作成」節に従う。
5. ユーザーが対話による採否・反復を求めた起動では、続行か終了かをユーザーに確認する。品質確認のためエージェントが起動した場合は、必要な評価と反映を終えて元の依頼の残工程へ進む。工程の終了だけを確認理由にしない。
   - 続行する場合は新しいプロンプト評価担当を起動して再評価する。前回のプロンプト評価担当は継続しない
   - ユーザーが終了を告げた時点で評価の反復を終える。反映後は対象の編集手順を定めるスキル（`agent-toolkit:writing-standards`など）、`agent-toolkit:check-execution`および`agent-toolkit:completion-report`の工程へ進む

## 指摘の集約と改善案作成

メインだけが指摘を統廃合し、意図を保って重複・近接をまとめる。`agent-toolkit:review-standards`と`references/reviewee.md`で採否を判定し、些末・的外れ・目的やスコープ外の指摘を除外する。定義元の転記要求は、読込表で読む`agent-toolkit:writing-standards`の`references/agent-documents-basics.md`「定義の所有者」で判定する。
採用する指摘には作成規範に沿う改善案のdiffを作成する。ユーザーとの対話による採否を求められた場合は、後掲書式で指摘と改善案を区別して提示する。評価担当の出力は直接表示されないため、指摘は原文に近い形で残す。

- 採否の確定: ユーザーが対話による採否を求めた起動では、提案を回答可能な件数ずつまとめて確認する。品質確認のためエージェントが起動した場合は、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」で技術指摘の採否を自ら確定し、目的・結果の変更やユーザーだけの選好・認可が残る部分だけを問う。Claude Codeの対話では`AskUserQuestion`の`multiSelect`で最大4件ずつ1質問にまとめる
  - 片方だけの採用で本文が矛盾する提案は同じ選択肢にまとめる
  - 質問本文と選択肢の組み方は`agent-toolkit:user-confirmation-and-report`「確認の選択肢を組む手順」に従う。本スキルでは、各`description`へ変更前後の要点を書き、各オプションの`label`を「提案N: <変更対象>」とする（努力目標。質問だけで採否を判断できるようにする）
  - チェックされた提案を採用、未チェックを却下として扱う
  - 修正したい改善案がある場合は自動付与の「Other」欄に番号と修正内容を書くよう、質問本文で案内する
- 反映: 採用が確定した改善案を対象プロンプトに反映する
  - 「Other」欄に修正指示があれば、その内容に沿って反映する

### ユーザー提示フォーマット（1件ごとに繰り返す）

````text
### 提案 N: <変更対象を1行で>
- 指摘元: <プロンプト評価担当が報告した該当箇所と問題内容を1〜2文で>
- 変更理由: <なぜ変更すべきか1〜2文>
- 変更内容: 以下のdiff形式で示す。新規追加なら`+`のみ、削除なら`-`のみでよい

  ```diff
  - <現在の文言>
  + <変更後の文言>
  ```

- 期待効果: <この変更で何が改善するか1文>
- 追随対象: <採用時に追随する他の文書・記述。無い場合は「なし」>
- 種別: 加筆 / 書き換え / 削除
````

## 環境制約

`agent-toolkit:delegation`が定める委譲手段を利用できない環境では、
同一セッション内で直接評価を実施し、結果提示時に「プロンプト評価担当を起動できないため直接評価」と明記する。
