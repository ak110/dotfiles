# 固定課題による多ターン試行

<!-- 節をまたぐ手順を通し番号で示す。 -->
<!-- markdownlint-disable MD029 -->

多ターン試行は、独立したユーザー役エージェントが質問に応じて段階的に情報を開示し、評価対象エージェントが対話を重ねて提出した成果物を採点する手動検証である。
進行を担当する仲介エージェントが両者のやりとりを中継し、対話履歴全体と提出された成果物をもとに採点する。
目的に応じ、批判的通読、単ターンのシナリオ評価、読み取り専用文書の判定試行も選べる。

## 名指し参照の読込方法

名指し参照は`../SKILL.md`「名指し参照の読込方法」に従う。

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 |
| --- | --- | --- | --- |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `../../delegation/SKILL.md` | 判断 | `read:agent-toolkit:*/skills/delegation/SKILL.md` |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `../../managed-temp/SKILL.md` | 判断 | `read:agent-toolkit:*/skills/managed-temp/SKILL.md` |

## 素材と準備

1. 比較する課題と開示条件を選ぶため、`atk run-script multi-turn-trials -- --list`で課題名、種別`kind`と条件を取得する。
固定素材は`${CLAUDE_PLUGIN_ROOT}/skills/refine-prompt/fixtures/multi-turn/`に配置されている。

| 課題 | 開示条件 | 成果物で確かめる結果 | 原型の節 |
| --- | --- | --- | --- |
| `attachment-paths` | `questions-only` | 添付の参照・関連付け・削除のパスと従来API | C.2.1 A1 |
| `weekday-queries` | `questions-only` | Sunday=1の維持と別の公開ISO問い合わせ | C.3.1 F1 |
| `batch-conditions` | `questions-only` | 異なる条件の複数要素、順序、空入力と単体API | C.3.2 F2 |
| `display-spaces` | `no-followup`、`observations-only` | 空白を含む表示の回復と正常表示の維持 | C.1 |
| `verification-status` | `no-dialogue` | 未実行と実行済みの期待失敗の分類 | 合成素材 |
| `skill-selection` | `no-dialogue` | 依頼と説明による初期選択と、本文を読んだ後の追加選択 | 合成素材 |
| `test-selection` | `no-dialogue` | 隠れた依存を含む変更から実行すべきテストの選択 | 合成素材 |
| `goal-discovery` | `no-dialogue` | 目標から注文集計CLIを完成させ、既存APIを保つ | 独自素材 |
| `strategy-update` | `no-dialogue` | 単位の異なる明細と担当間の矛盾を整合させ、既存結果を保つ | 独自素材 |
| `purpose-boundary` | `questions-only` | 目的の確認後に、確定した改善領域を要求へ反映する | 独自素材 |

上表の`attachment-paths`、`weekday-queries`、`batch-conditions`、`display-spaces`の原型は、[SWE-Journey v1 Appendix C](https://arxiv.org/html/2610.11559v1)で報告された失敗パターンを、扱いやすい小規模な課題として具体化したものである。
`private/trial.json`には、出典情報、非公開の要件、開示条件、対話の評価基準、終了条件、および参考となる成功例・失敗例が記録されている。
なお、表示課題に含まれる第三者テスターの存在や回答制約は原型論文には含まれておらず、本試行の要件に合わせて独自に追加した条件である。
`kind`が`dialogue`の課題では、以下のユーザー役との仲介手順と対話JSONを使う。
`kind`が`single`の課題では、評価対象だけを起動して提出までの終了を観測し、「単独作業の採点」の実施情報を保存する。
単独課題`verification-status`は、未実行と実行済みの期待失敗の分類を扱う保存形式の検証用合成素材であり、実モデルの比較実績ではない。
単独課題`skill-selection`と`test-selection`の保存例も採点契約を確かめる合成素材であり、実モデルの改善実績や選択精度の記録ではない。
両課題で採点するのは提出した識別子による選択判断であり、本文を実際に読んだことや依存を探索したことの証拠にはしない。
実モデルで比較する場合は、session記録から開いた本文、実行した検索と読取の順序を確かめ、取得できた入力・出力トークン、所要時間、費用を併記し、取得できない値は「未取得」とする。
`test-selection`の手動比較では、最初に与えた情報だけで選ぶ方式と、検索・読取の結果を次の判断へ反映する方式を区別して記録し、結果を実行するテストの縮小へ反映しない。

2. 試行間の素材を分離するため、managed-temp直下に版・課題ごとの作業ディレクトリを用意し、次のコマンドで公開素材を準備する。
コマンド例における`<公開素材の新規絶対パス>`には、まだ存在しない新規パスを指定する。

```sh
atk run-script multi-turn-trials -- prepare --case attachment-paths --output <公開素材の新規絶対パス>
```

準備コマンドを実行すると、課題の`public/`配下の公開素材（`request.md`、`task.py`と課題の素材ファイル）だけが指定先に複製される。
評価対象エージェントの読み書き権限はこの公開素材と評価対象文書の複製のみに限定し、課題専用のコードのみを変更させる。
変更の適用対象は課題専用コードに限定する。
`private/`ディレクトリ、採点用テスト、正解データ、ユーザー役の入力内容およびその配置場所は、仲介担当が評価対象から隠蔽して管理する。
同一OS上のディレクトリ分離はセキュリティ上の完全なサンドボックスではないため、意図しないアクセスが行われていないかを仲介担当が確認する。

## 両役の入力と返却

3. 非公開情報の事前把握を防ぐため、以下の契約で入力を準備し、入力・返却形式を本文で指定して、`agent-toolkit:delegation`の`agents_server`自由文委譲で両役を独立した新規セッションとして起動する。`single`は評価対象のみとする。スキーマで起動オプションを確認し、モデル名と設定を保存する。

| 役割 | 渡す入力 | 返却 |
| --- | --- | --- |
| 評価対象 | 適用する文書の本文と版、公開素材、公開依頼、公開素材だけの書込範囲、課題固有の終了条件 | 応答全文、質問または変更の説明、提出`task.py`の絶対パス、完了宣言、実行した検証の記録 |
| ユーザー役 | 公開依頼、選んだ条件、`trial.json`の要件と質問による開示条件だけ、以下の開示制約 | 応答全文と開示した要件の識別子、対応質問の引用、情報源 |

`trial.json`に記載された成功・失敗例、採点テスト、対話判定基準、および正解コードは、仲介担当のみが参照する。
仲介担当は、必要な要件と開示条件のみを抽出した入力データを作成して保存する。
最初の依頼メッセージとしては、`public/request.md`の内容をそのまま転送する。
ユーザー役が回答する範囲は、評価対象から適切な質問があった要件のみに限定する。
把握していない内容や答えられない質問を受けた場合は、情報を持っていない事実をそのまま伝える。
採点結果は仲介担当のみが管理・保持する。

表示課題において`no-followup`条件を適用する場合、ユーザー役は追加の回答が得られない旨のみを返答する。
`observations-only`条件を適用する場合は、質問に関連する画面表示・入力内容・操作結果といった客観的な観測情報のみを回答する。
内部実装の詳細や「空白が消失している」という根本原因の正解は、ユーザー役に対しても伏せておく。
評価対象は、追加回答の有無にかかわらず、初期報告にある再現手順や課題コードを自身で調査して原因を特定する。

## 仲介と終了

4. 開示範囲と対話の連続性を守るため、同一課題では双方のセッションを維持し、評価対象の応答全文をユーザー役へ、ユーザー役の応答本文のみを評価対象へ転送する。`single`では仲介を省く。
開示要件の識別子など、ユーザー役から返された管理用データは仲介担当側で保持する。
メッセージの送信受付と応答の完了を明確に区別し、`atk agents wait`で返却内容と終了状態を確認した上で次のメッセージを送信する。
応答が完了したセッションへ追加メッセージを送信することで、同一対話の次ターンを開始する。
待機・状態観測・中断の制御は、`agent-toolkit:delegation`に定めるホスト別の契約に従う。

5. 終了と未達を区別するため、`dialogue`は提出物を伴う完了宣言または評価対象の応答6回、`single`は課題固有の終了条件で終了を観測する。
この6回という上限は、固定課題を同一のコストと条件下で公平に比較するために設けた本試行専用の制約である。
完了宣言の有無とあわせて、終了に至る全対話履歴、提出物、および検証記録を回収して判定の根拠とする。
往復回数の上限に達した時点で未解決の要件は未達成として扱い、起動失敗や実行エラー、開示ルール違反が生じた場合は試行不成立とする。
起動したすべてのターンの終了状態を確実に確認してから、試行結果を返却する。

## 保存対話と採点

6. 対話を証拠で判定するため、`dialogue`では仲介担当が履歴全体を読み、開示ルール違反と`trial.json`の対話基準への合致、質問と回答の論理的関係を、各役の自己評価とは独立して採点する。`single`は「単独作業の採点」の実施情報を保存する。
採点用CLIは対話の意味的な妥当性までは自動判定しないため、判定項目の網羅性、引用されたターン番号、および開示条件の適合性を検証する。

保存する対話JSONは次の項目を持つ。
配列のターン番号は1始まりとする。

| 項目 | 値 |
| --- | --- |
| `case`、`condition` | 課題名と開示条件 |
| `document_version` | commitと対象パス、または保存した文書本文の絶対パス |
| `model`、`settings` | 実際のモデル名と起動設定のオブジェクト |
| `sessions` | `candidate`と`user`の別々の実session識別子 |
| `termination` | `submitted`、`turn-limit`、`error` |
| `execution_errors` | 起動・実行障害の配列。無ければ空配列 |
| `turns` | 初期依頼から交互の`role`（`user`、`candidate`）と応答全文`text` |
| `disclosures` | 開示ごとの`requirement`、`question`、`answer`、`matched`、`source` |
| `disclosure_audit` | 全userターン番号の`reviewed_user_turns`と、意味で判定した違反の`violations`配列 |
| `behavior` | 基準ごとの`criterion`、`verdict`、`reason`、`evidence` |

`question`と`answer`の各項目には、ターン番号を表す`turn`と、発言の逐語引用である`quote`を記録する。
`matched`は、仲介担当が質問と回答の対応関係を妥当と認めた場合に`true`を設定する。`source`には要件を表す`requirements`か、観測情報を表す`observations`を指定する。
`behavior`の判定結果には「適合」「不適合」「未判定」のいずれかを記録し、判定根拠には発言者を示す`role`、ターン番号の`turn`、および該当箇所の引用である`quote`を含める。
試行が不成立となった場合でも取得済みの対話履歴は保存し、取得できなかったセッションや根拠情報については未取得である旨を明記する。
入力の検証段階で拒否された場合は、終了コードとエラー診断情報を保存し、試行不成立として分類する。

7. 成果物と対話の評価軸を分けて確かめるため、保存した情報で採点する。`single`は「単独作業の採点」の引数を使う。

   ```sh
   atk run-script multi-turn-trials -- grade --case attachment-paths --candidate <提出task.pyの絶対パス> --dialogue <対話JSONの絶対パス> --output <結果JSONの絶対パス>
   ```

表示課題を採点する場合は、`--condition no-followup`または`--condition observations-only`のいずれかを指定する。
`--timeout`には成果物テストのタイムアウト時間を正の有限秒数で指定する（省略時は10秒）。
採点コマンドは、提出された成果物を専用の作業領域へコピーした上で、あらかじめ定義された公開操作テストを明示的に実行する。
採点結果は、`functional`（機能テストの合否）、`requirements`（要件ごとの達成・未達）、`behavior`（対話基準の判定）の各項目に分けて出力される。
各機能テストの結果には期待値、実際の結果、あるいは発生した例外が記録され、各要件の達成状況はテスト識別子を通じて判定根拠と紐付けられる。
`test_run`には、テスト実行時の引数、終了コード、標準出力、および標準エラー出力を記録する。
終了コード0は成果物が正常に機能テストに合格した状態、1は成果物として成立しているものの機能要件を満たしていない状態、2は実行不成立または入力不正を表す。
対話基準における不適合と、機能要件の未達は、互いに独立した評価軸として確認できる。

### 単独作業の採点

`single`課題では、`--dialogue`の代わりに`--execution`へ実施情報JSONを渡す。
両引数は排他であり、課題種別と異なる入力は終了コード2で拒否する。
実施情報は、`case`、`condition`、`document_version`、`engine`、解決後のモデルIDである`model`、`settings`、`sessions.candidate`、`termination`を持つ。
`settings.effort`と各文字列には実際の起動記録を記入し、課題と条件は一覧の値に合わせる。
`termination`は提出を観測した`submitted`か、障害で終わった`error`とし、起動・実行障害の文字列配列`execution_errors`は省略時に空配列として扱う。
ユーザー役のsession、`turns`、開示記録と監査は要求しない。

```sh
atk run-script multi-turn-trials -- grade --case verification-status --candidate <提出task.pyの絶対パス> --execution <実施情報JSONの絶対パス> --output <結果JSONの絶対パス>
```

成果物の機能テストと要件別判定、終了コード0・1・2の意味は対話課題と共通である。
結果の`execution_path`は実施情報の絶対パスを示し、`provenance`にはengineを含む起動記録を保存する。
単独作業の`behavior`は空配列であり、判断内容は作業記録から評価担当が判定して比較要約へ残す。

### 作業構成・方針更新・目的確認の3課題

`goal-discovery`と`strategy-update`は`single`、`purpose-boundary`は`dialogue`である。
各課題の公開APIと入力契約は`public/README.md`、行動判定基準と固定期待値は`private/`にある。
成功例と機能未達例は保存形式検証用の合成素材であり、実モデル試行の実績には含めない。

- `goal-discovery`: 依頼に解法を加えず公開素材を渡し、必要作業の発見、公開CLIによる検証、目的と局所判断の区別、不要な指示待ちを履歴から判定する
- `strategy-update`: 実入力による初期仮説の反証、整数セントの維持、担当A/Bの矛盾の統合、採らなかった案と再検討条件を履歴から判定する
- `purpose-boundary`: 目的に関する回答前の質問、候補と推奨、例示の開放性、回答後の技術手段の不要確認を対話から判定する

単独2課題は追加回答を行わず、初期依頼から提出までの応答とツール操作・出力を保存する。
提出コードだけから行動の適否を推定しない。
行動基準ごとの適合・不適合・未判定、理由、根拠となる履歴の保存先と引用を比較要約に記す。
`strategy-update`の再開試行では、評価対象が一度応答を終えた時点で、目標・観測・未完了作業を作業領域へ保存させる。
同じ担当へ「保存した目標・観測・未完了作業を確認して続けて」と追送し、再開前後の入力、終了状態、復元に使用した証拠を保存する。
新しい正解や追加要件は渡さず、再開を実施しなかった比較では該当基準を未判定とする。

`purpose-boundary`のユーザー役へは、`trial.json`の目的・範囲に関する回答と開示条件だけを渡す。
機能採点はその回答で確定した要件を検査する。
回答前に選べる目的一般について、1つの目的を正解として扱わない。
同じ公開素材を使う手動対照として、目指す状態を最初から明記した依頼と、性能などを例示する広い依頼を別々の新規文脈で試す。
前者は目的内の技術判断を継続できるか、後者は例示を閉じた範囲へ変えず必要な目的確認ができるかを観測し、固定課題の結果とは入力条件を分けて保存する。

## 改訂前後の比較と受領

8. 公平な比較と追跡を保証するため、同じ素材、モデル、起動設定、開示・終了条件、採点基準で版ごとに手順2〜7を繰り返す。各役は新規セッションとし、固定の初期入力だけを渡す。以前の履歴、正解データ、指摘、採点結果などは遮断する。
上表の対話課題は、表示課題の2条件を含む全条件の結果を事例と条件ごとに整理し、版の改訂によって変化した判定結果とその根拠を精査する。

受領すべき成果物は、評価対象となった文書の本文と版情報、起動パラメーターの記録、各エージェントへの入力データ、および対話履歴全体である。
あわせて、各ターンの終了状態、提出された成果物、結果のJSONファイルとテスト実行ログも回収する。
比較結果をまとめた記録からすべての保存ファイルへ絶対パスでアクセスできるように構成し、実行レビュー担当者が判定根拠を直接確認できる状態を維持する。
記録された保存例は、採点用CLIやテスト環境の入力データとして活用する。
少数の固定事例から得られた差異は、あくまでその検証事例における観測結果として報告する。
素材や検証結果の保存および不要になったファイルの回収は、`agent-toolkit:managed-temp`に従って実施する。

## 実セッション由来の小課題による比較

規範の条文がエージェントの誤誘導や不要な作業の要因になっていないかを検証したい場合に選択する、任意の検証手法である。
既存の固定課題や単発の評価で採否を十分に判断できる場合は、そちらの手法を優先する。
本手法は、[OpenAIのソフトウェア保守事例](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)で紹介された、元の依頼内容、初期状態、使用モデルを完全に揃えた上で1文のみを変更して比較するアプローチを参考にしている。
このアプローチを本スキルの試行環境へ適用する具体的な手順を以下に示す。

実際の依頼内容、入力データ、初期状態の成果物、および実際に観測された誤誘導や余分な作業の記録をもとに、独立して完結する小規模な課題を作成する。
エージェントへ提示する公開依頼や素材と、仲介担当のみが保持する要件や評価基準とを明確に分離する。
元の会話から独立した新規セッションを作成し、実際の環境に影響を与える操作対象は課題専用の素材へ置き換える。
評価対象へ許可する読み書き範囲の制限や、実行後のアクセス確認は、「素材と準備」の規定に従って仲介担当が実施する。
保存形式へ整える前の独自課題は、その課題の公開操作を実行して要件の充足状況を確認する。
比較後の保存と採点CLIへの登録は、次節の手順に従う。

同一の依頼内容、初期状態の成果物、モデル、effort設定、起動パラメーター、開示条件、終了条件、および評価基準を用意し、現行版の規範と1文のみを変更した改訂版の規範を、それぞれまっさらな新しい文脈で実行する。
モデルやeffortの違いを比較する場合は、文書内容を固定した別の検証として実施する。
確率的な出力の比較では、課題・初期状態・モデル・設定、採点基準と候補の固定時点、実行順の偏りをそろえ、判断に必要な独立反復を選ぶ。
要件別達成、成功率、時間・トークン・費用の代表値と分布、不成立と良好な試行だけの選別を区別し、既存の`comparisons.jsonl`へ全試行を対応付ける。
反復回数の一律指定やCIでのLLM自動試行は追加しない。
評価対象へ渡す情報は、指定された入力のみに限定する。
対話の発生しない単独作業の課題であれば評価対象のみで試行し、対話を必要とする課題については前述の仲介手順を適用する。

提出された成果物の機能や維持すべき要件が満たされているかを第一に判定し、その上でエージェントの判断内容、ツール操作の回数、消費トークン数、所要時間、推定費用などの指標を比較する。各数値にはその根拠となるログを紐付けて記録する。
要件の未達成と、起動失敗や環境エラーによる試行の不成立は明確に区別する。
計測できなかった指標は無理に推測せず「未取得」として記録し、少数の試行から得られた差は、あくまでその検証事例における観測結果として扱う。
比較記録には、両版の文書内容、初期状態、使用したモデルと設定、対話履歴全体、提出物、検証結果、および各指標の算出根拠を漏れなく対応付けて保存する。

| 結果の例 | 判定 |
| --- | --- |
| 同一課題で全要件を満たした上で、不要な読み取りや操作が減少した | その事例において品質を維持したまま改善されたと判定する |
| 所要時間や消費トークンは減少したが、維持すべき公開機能が損なわれた | 機能未達と判定する |
| 両版の間で使用モデルや初期状態が異なっている | 条文変更の効果を示す根拠としては採用しない |
| 起動エラーなどの障害により成果物が得られなかった | 試行不成立として扱い、機能の未達とは区別する |

### 調整用課題と検収用課題

規範案を事例に合わせて直した効果を一般的な改善と取り違えないよう、任意で課題を用途で分ける。

- 調整用課題: 規範案の作成・修正に使った課題
- 検収用課題: 案を固定した後に初めて実行する課題

両版で入力、モデル、設定、採点基準をそろえる。
検収用課題の結果を見て案を直した場合、その課題は以後調整用として扱う。
案の作成・選定に渡す実行記録から、検収用課題とその採点結果を外す。
ネットワークを含むアクセス範囲で分離を保証できない場合は、その限界を比較結果へ残し、未使用の課題での検収として扱わない。
検収用課題を用意しない比較も使えるが、結論は試した事例での改善に限る。

| 結果の例 | 判定 |
| --- | --- |
| 調整用課題だけで改善した | 試した事例での改善に限って報告する |
| 調整用課題と検収用課題の両方で改善した | 未使用の課題でも改善を観測したと報告する |
| 検収用課題の結果を見て案を直した | その課題を調整用へ移し、別の未使用課題で検収するまで未使用の課題での結論を出さない |
| 検収用課題や採点結果が案の作成側へ渡った | 未使用の課題での検収として扱わない |

### 課題の選別と保存

比較を担当したエージェントは、現行の規範とモデルでも対象の誤りや判断の差が実際に生じうることを試行記録から確かめ、再比較に使う小課題を保存する。
差が出ないほど容易な課題は保存せず、再実行で比較価値を失った課題は保守時に整理する。
単独課題の合成保存例は採点形式の動作確認に使い、実際のモデル間の差を示す評価課題とは区別する。

1. 比較に使った依頼、初期状態、判断差を生む条件を小課題へ残し、個人名、実パス、業務データなどは課題専用の値へ置き換える。
2. `fixtures/multi-turn/<課題名のアンダースコア表記>/`へ、`public/request.md`、`public/task.py`、`private/trial.json`と`private/grade.py`を保存する。
3. `trial.json`に`case`、`kind`（`dialogue`または`single`）、`source`、`conditions`、`termination`、要件とテストIDの対応`requirements`、判断基準`behavior_criteria`、成功・失敗の保存例`examples`を記す。
4. 対話課題には既存課題と同じ`max_rounds`、要件の開示条件、対話と引用根拠を記す。単独課題には対話の代わりに実施情報の保存例を用意する。
5. 課題専用の`grade.py`で公開操作と期待値を共通の`grade_fixture`へ渡し、`scripts/multi_turn_trials.py`の`CASES`へハイフン表記の課題名を登録する。
6. 一覧、`prepare`、採点を公開CLIから実施し、公開素材だけの複製、成功・未達・不成立の区別と既存課題の採点結果を確認する。

### 比較要約と手動再実行

後から再比較する評価担当が条件と結果を確認できるよう、課題ごとの`private/comparisons.jsonl`に1試行1行の要約を保存し、素材とともに版管理する。
比較を担当するエージェントが比較時に記録を追加・更新し、初回の比較元も同じ形式で残す。
実施日、engine、解決後のモデルID、effort、文書の版、課題素材と条件・起動設定、課題の用途（調整用・検収用）と候補を固定した時点、要件ごとの結果、判断過程の要点、取得できた指標と単位・算出根拠を記す。
未取得の指標は「未取得」とし、不成立の試行は理由を記録して機能未達と区別する。
対話全文や大量のログは版管理へ含めず、受領に必要な全記録はmanaged-tempに保持し、要約へ条件と判断根拠を転記する。
既存の`trial.json`の合成保存例を実モデルの検証記録として転記しない。

評価に使うengineまたは解決後のモデルIDが要約の値から変わったことを確認した時は、文書を固定して保存課題を手動で再実行する。
設定名が同じ場合も、実際に解決されたモデルIDで変化を判断する。
大きな規範削減時は次節に従い、モデルを固定して再実行する。
両場面とも初期素材、開示条件、終了条件、評価基準と比較対象以外の起動設定をそろえ、要件充足、判断内容、取得できた指標の順で前回と比較する。
LLM試行をCIで自動実行したり、その合否を後続処理の実行条件にしたり、セッション記録から課題を自動生成したりしない。

## 大きな削減の3条件比較

複数の記述をまとめて削る場合は、任意の検証として、削る前の版、削った後の版、対象文書を読み込まない構成を比較できる。
同じ課題、初期状態、モデル、effort、起動パラメーター、開示条件、終了条件、評価基準を使い、各条件を新しい文脈で実行する。
削った後の版が要件の充足と判断内容の両方で削る前と同等以上の場合に採用し、劣った判断に対応する記述は戻す。
文書なしでも同等の結果になった記述は削除の候補にできる。
削除を確定する前に、課題がその記述の対象状況を含むことを確かめ、含まない状況のための記述は残す。
指標と記録方法は「実セッション由来の小課題による比較」に従い、3条件の本文と構成、結果、根拠を対応付ける。
保存済み課題を使った比較要約は、前節の`private/comparisons.jsonl`へ3条件を区別して記録する。
観測結果は試した課題の範囲に限定する。
