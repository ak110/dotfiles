# 固定課題による多ターン試行

多ターン試行は、独立したユーザー役が質問に応じて情報を開示し、評価対象が対話を継続して提出した成果物を採点する手動検証である。
試行を進めるエージェントは両役を仲介し、全対話と成果物から採点する。
最初に固定課題と開示条件を選び、公開素材を準備する。
批判的通読、単ターンのシナリオ評価、読み取り専用の文書の判定試行も目的に合わせて選べる。

## 名指し参照の読込方法

名指し参照は`../SKILL.md`「名指し参照の読込方法」に従う。

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 |
| --- | --- | --- | --- |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `../../delegation/SKILL.md` | 判断 | `read:agent-toolkit:*/skills/delegation/SKILL.md` |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `../../managed-temp/SKILL.md` | 判断 | `read:agent-toolkit:*/skills/managed-temp/SKILL.md` |

## 素材と準備

`atk run-script multi-turn-trials -- --list`で課題名と開示条件を取得する。
固定素材は`${CLAUDE_PLUGIN_ROOT}/skills/refine-prompt/fixtures/multi-turn/`にある。

| 課題 | 開示条件 | 成果物で確かめる結果 | 原型の節 |
| --- | --- | --- | --- |
| `attachment-paths` | `questions-only` | 添付の参照・関連付け・削除のパスと従来API | C.2.1 A1 |
| `weekday-queries` | `questions-only` | Sunday=1の維持と別の公開ISO問い合わせ | C.3.1 F1 |
| `batch-conditions` | `questions-only` | 異なる条件の複数要素、順序、空入力と単体API | C.3.2 F2 |
| `display-spaces` | `no-followup`、`observations-only` | 空白を含む表示の回復と正常表示の維持 | C.1 |

原型は[SWE-Journey v1 Appendix C](https://arxiv.org/html/2610.11559v1)の失敗機構を小規模課題へ具体化したものである。
各`private/trial.json`は出典、隠した要件、開示条件、対話基準、終了条件と保存成功例・失敗例を持つ。
表示課題の第三者テスターと回答制約は原型に無く、追加の要求に基づいてこの試行の条件として加えたものである。

セッションのmanaged-temp直下に、版と課題ごとに独立した領域を選ぶ。
次の`<公開素材の新規絶対パス>`はまだ存在しないパスとする。

```sh
atk run-script multi-turn-trials -- prepare --case attachment-paths --output <公開素材の新規絶対パス>
```

準備コマンドは`public/request.md`と`public/task.py`だけを複製する。
評価対象の読取・書込をこの公開素材と評価する文書の複製に限定し、課題専用コードだけを変更させる。
変更の適用先は課題専用コードに限る。
`private/`、採点テスト、正解、ユーザー役の入力とその所在は仲介担当が評価対象から伏せて保持する。
同じOS上のファイル分離はセキュリティのsandboxを意味しないため、読取制約と実際のアクセスを仲介担当が検収する。

## 両役の入力と返却

両役は`agent-toolkit:delegation`が定める既存の`agents_server`の自由本文の委譲で新規起動する。
特定の名前付き担当の手順を実行させる起動にはせず、以下の役割の入力と返却を本文へ渡す。
既存の指摘収集の担当に両役を兼任させると隠した情報を評価対象も知るため、両役を分ける。
実際のツールスキーマで起動設定を確かめ、起動に使ったモデルと設定を保存する。

| 役割 | 渡す入力 | 返却 |
| --- | --- | --- |
| 評価対象 | 適用する文書の本文と版、公開素材、公開依頼、公開素材だけの書込範囲、課題固有の終了条件 | 応答全文、質問または変更の説明、提出`task.py`の絶対パス、完了宣言、実行した検証の記録 |
| ユーザー役 | 公開依頼、選んだ条件、`trial.json`の要件と質問による開示条件だけ、以下の開示制約 | 応答全文と開示した要件の識別子、対応質問の引用、情報源 |

`trial.json`の保存例、採点テスト、対話判定と正解コードは仲介担当だけが読む。
仲介担当が必要な要件と開示条件だけを切り出した入力を保存する。
初期依頼は`public/request.md`の本文をそのまま配送する。
ユーザー役が回答できる範囲は、対応する質問があった一覧内の要件に限る。
回答できない質問には、その情報を持たないことを伝える。
採点結果は仲介担当だけが保持する。

表示課題の`no-followup`では、ユーザー役は追加回答を得られないことだけを返す。
`observations-only`では質問に対応する表示・入力・操作の観測情報だけを返す。
内部実装や空白消失という原因の正解はユーザー役にも伏せる。
評価対象は回答の有無にかかわらず、初期報告の再現入力と課題コードから調査する。

## 仲介と終端

同じ課題内は両sessionを維持し、評価対象の応答全文をユーザー役へ送り、ユーザー役の応答本文だけを評価対象へ送る。
開示識別子などユーザー役の管理用返却は仲介担当が保持する。
`send_message`の配送受理と応答の終端を区別し、`atk agents wait`で返却と終了状態を観測してから次を配送する。
終端済みsessionへの追送で同じ会話の次のturnを開始する。
待機・観測・中断は`agent-toolkit:delegation`のホスト別契約に従う。

終了条件は提出物を伴う完了宣言、または評価対象の応答6回への到達である。
6回の上限は、固定課題を同じ費用と条件で比べるための試行素材だけに適用する。
完了宣言だけを合格とせず、終端までの全文、提出物、検証記録を回収する。
往復数の上限に達して残った要件は未達、起動・実行障害と開示違反は試行不成立とする。
全ての起動したturnの終了状態を観測してから試行を返す。

## 保存対話と採点

仲介担当は全対話を読み、開示違反と`trial.json`の対話基準を意味で判定する。
質問の内容と応答の関係を判定し、質問数や語の一致だけによる採点を避ける。
評価対象やユーザー役の自己評価にかかわらず、仲介担当が根拠から判定する。
CLIは意味の正しさを自動判定せず、判定の網羅性、引用ターンと開示条件を確認する。

保存する対話JSONは次の項目を持つ。
配列のターン番号は1始まりである。

| 項目 | 値 |
| --- | --- |
| `case`、`condition` | 課題名と開示条件 |
| `document_version` | commitと対象パス、または保存した文書本文の絶対パス |
| `model`、`settings` | 実際のモデル名と起動設定のオブジェクト |
| `sessions` | `candidate`と`user`の別々の実session識別子 |
| `termination` | `submitted`、`turn-limit`、`error` |
| `execution_errors` | 起動・実行障害の配列。無ければ空配列 |
| `turns` | 初期依頼から交互の`role`（`user`、`candidate`）と応答全文`text` |
| `disclosures` | 開示ごとの`requirement`、`question`、`answer`、`matched`、`source` |
| `disclosure_audit` | 全userターン番号の`reviewed_user_turns`と、意味で判定した違反の`violations`配列 |
| `behavior` | 基準ごとの`criterion`、`verdict`、`reason`、`evidence` |

`question`と`answer`はそれぞれ`turn`と逐語引用`quote`を持つ。
`matched`は仲介担当が対応する質問と判定した場合に`true`とし、`source`は要件の`requirements`か観測の`observations`とする。
`behavior`の判定値は適合、不適合、未判定であり、根拠の配列は`role`、`turn`、`quote`を持つ。
不成立時も取得できた対話を保存し、欠けたsessionや根拠は未取得と記す。
入力検証で拒否された場合は終了コードと診断を保存し、試行不成立へ分類する。

```sh
atk run-script multi-turn-trials -- grade --case attachment-paths --candidate <提出task.pyの絶対パス> --dialogue <対話JSONの絶対パス> --output <結果JSONの絶対パス>
```

表示課題には`--condition no-followup`か`--condition observations-only`を指定する。
`--timeout`は成果物テストの正の有限秒数で、省略時は10秒である。
採点コマンドは提出物を結果保存先の専用複製へコピーし、固定した公開操作のテストを明示実行する。
結果は`functional`の機能合否、`requirements`の要件ごとの達成・未達、`behavior`の対話判定に分かれる。
各機能テストは期待値と実際の値か例外を持ち、要件はテストの識別子から根拠へ届く。
`test_run`へ実行引数、終了コード、標準出力と標準エラーを保存する。
終了コード0は成立した成果物の機能合格、1は成立した成果物の機能未達、2は不成立か入力不正を表す。
対話上の不適合と機能未達は独立して読める。

## 改訂前後の比較と受領

同じ素材、モデル、起動設定、開示条件、終了条件と採点基準で、版ごとに両役を新規起動する。
次の版へ渡すのは固定した初期入力だけとし、以前の会話や正解、指摘と採点結果を伏せる。
表示の2条件を含む5条件の結果は事例と条件ごとに並べ、変わった判定と根拠を読む。

受領物は文書の本文と版、起動記録、各役への入力と全対話である。
各turnの終端、成果物、結果JSONと実行記録も受領する。
比較記録から全保存物の絶対パスへ到達できるようにし、実行レビュー担当が根拠を確認できる状態へ保つ。
保存例はCLIと採点のテスト入力として扱う。
少数の固定事例の差は、その事例での観測に限って報告する。
素材と結果の保持・回収は`agent-toolkit:managed-temp`に従う。

## 実セッション由来の小課題による比較

条文が誤誘導や余分な作業へ作用したかを判断する必要がある場合に選ぶ任意の試行である。
既存の固定課題や単発評価で採否を判断できる場合は、その方法を使う。
参考は[OpenAIのソフトウェア保守事例](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)の、元の依頼・開始状態・モデルをそろえて一条文だけを変える比較である。
以下は同じ考え方を本スキルの試行へ適用する方法とする。

実際の依頼と入力、開始時の成果物、観測した誤誘導や余分な作業から、小さく完結する課題を作る。
公開する依頼・素材と、仲介担当だけが持つ要件・評価基準を分ける。
元の会話を再開・分岐せず、実環境へ作用する対象を課題専用の素材へ置き換える。
評価対象へ渡す読取・書込範囲と取得後の検収は「素材と準備」に従う。
固定課題専用の採点CLIへ独自課題をそのまま渡さず、その課題の公開操作で要件を観測する。

同じ依頼、開始時の成果物、モデル、effort、起動設定、開示・終了条件と評価基準を使い、現行版と一条文だけを変更した版を新しい文脈で実行する。
モデルやeffortを比較する場合は、文書を固定した別の比較にする。
過去の対話、指摘、正解と採点結果は評価対象へ渡さない。
両役を必要としない課題は評価対象だけで試行し、対話を要する課題は既存の仲介を使う。

成果物の機能と保持すべき要件を先に判定し、判断・ツール操作・token・所要時間・取得できる推定費用を、その根拠へ対応付けて比べる。
要件の未達と起動・環境による試行不成立を区別する。
取得できない指標は未取得とし、少数試行の差はその事例での観測として残す。
比較記録には両版の文書、開始状態、実際のモデルと設定、全対話、提出物、検証結果と指標の取得元を対応付ける。

| 結果例 | 判定 |
| --- | --- |
| 同じ課題で全要件を満たし、不要な読取と操作が減った | その事例で品質を保った改善と判定する |
| 所要とtokenは減ったが、保持すべき公開操作が失われた | 機能未達と判定する |
| 両版でモデルや開始状態が異なる | 条文変更の効果の根拠には使わない |
| 起動失敗で成果物を得られなかった | 試行不成立とし、機能の未達と分ける |
