# 固定課題による多ターン試行：両役の入力と返却

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 両役の入力と返却

**3.** 非公開情報の事前把握を防ぐため、以下の契約で入力を準備し、入力・返却形式を本文で指定して、`agent-toolkit:delegation`の`agents_server`自由文委譲で両役を独立した新規セッションとして起動する。
   `single`は評価対象のみとする。
   スキーマで起動オプションを確認し、モデル名と設定を保存する。

| 役割 | 渡す入力 | 返却 |
| --- | --- | --- |
| 評価対象 | 適用する文書の本文と版、公開素材、公開依頼、公開素材だけの書込範囲、課題固有の終了条件 | 応答全文、質問または変更の説明、提出`task.py`の絶対パス、完了宣言、実行した検証の記録 |
| ユーザー役 | 公開依頼、選んだ条件、`trial.json`の要件と質問による開示条件だけ、以下の開示制約 | 応答全文と開示した要件の識別子、対応質問の引用、情報源 |

`trial.json`に記載された成功・失敗例、採点テスト、対話判定基準、および正解コードは、仲介担当のみが参照する。
仲介担当は、必要な要件と開示条件のみを抽出した入力データを作成して保存する。
最初の依頼メッセージとしては、`public/request.md`の内容をそのまま転送する。
ユーザー役が回答する範囲は、評価対象から適切な質問があった要件のみに限定する。
把握していない内容や答えられない質問を受けた場合は、情報を持っていない事実をそのまま伝える。
採点結果は仲介担当のみが管理・保持する。

表示課題において`no-followup`条件を適用する場合、ユーザー役は追加の回答が得られない旨のみを返答する。
`observations-only`条件を適用する場合は、質問に関連する画面表示・入力内容・操作結果といった客観的な観測情報のみを回答する。
内部実装の詳細や「空白が消失している」という根本原因の正解は、ユーザー役に対しても伏せておく。
評価対象は、追加回答の有無にかかわらず、初期報告にある再現手順や課題コードを自身で調査して原因を特定する。

## 仲介と終了

**4.** 開示範囲と対話の連続性を守るため、同一課題では双方のセッションを維持し、評価対象の応答全文をユーザー役へ、ユーザー役の応答本文のみを評価対象へ転送する。
   `single`では仲介を省く。
開示要件の識別子など、ユーザー役から返された管理用データは仲介担当側で保持する。
メッセージの送信受付と応答の完了を明確に区別し、`atk agents wait`で返却内容と終了状態を確認した上で次のメッセージを送信する。
応答が完了したセッションへ追加メッセージを送信することで、同一対話の次ターンを開始する。
待機・状態観測・中断の制御は、`agent-toolkit:delegation`に定めるホスト別の契約に従う。

**5.** 終了と未達を区別するため、`dialogue`は提出物を伴う完了宣言または評価対象の応答6回、`single`は課題固有の終了条件で終了を観測する。
この6回という上限は、固定課題を同一のコストと条件下で公平に比較するために設けた本試行専用の制約である。
完了宣言の有無とあわせて、終了に至る全対話履歴、提出物、および検証記録を回収して判定の根拠とする。
往復回数の上限に達した時点で未解決の要件は未達成として扱い、起動失敗や実行エラー、開示ルール違反が生じた場合は試行不成立とする。
起動したすべてのターンの終了状態を確実に確認してから、試行結果を返却する。
