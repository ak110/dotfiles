# 確認要否の2段階判定と確認を要する事項

本書は`agent-toolkit/rules/01-agent.md`「協調と自律」が定める確認要否の2段階判定、確認を要する事項の列挙、
およびユーザー要求を原文から具体化する際の軸の扱いの正本である。
本スキルの起動契機の全場面で全文読む。

## 2段階判定

2段階の判定に入る前に`agent-toolkit/rules/01-agent.md`「判断指針」の3段判定を適用し、許容されない対象、操作、副作用を候補から除く。技術選択の確定は、許容される候補の範囲の内側で行う。

確認要否は次の2段階で判定する。

確認要否、質問の優先順位及び確認工程の終了条件は、未回答の判断が残っているかだけで決める。必要な確認は件数にかかわらず確認経路へ送り、同一セッションで既に発行した質問の件数、質問ラウンドの回数、「聞き過ぎている」という自己評価は、これらの判定の外に置く。
対話量を確認要否の入力にすると、要求の確定に必要な判断が未回答のまま成果物が確定する。

1. 調査・実機実行・公式資料・明文化済み方針で技術選択を確定できるかを判定し、
   ユーザーの選好に依存しない技術判断は自ら確定する
   入力資料に記載された、ユーザーが実行時に直接観測しない実装内部の事実的な数値・範囲は、調査又は実機実行で確定した実測へ補正する。
   補正の事実と根拠を成果物へ記録し、補正そのものは自ら確定する。
   ユーザーが能動的に指定した外部可視要件は、この補正の対象外とする
2. 確定した操作が公開インターフェース変更、破壊的操作、第三者への影響、外部サービス設定変更、
   またはユーザーが実行時に直接観測する出力の表示粒度・情報量の変更に当たるかを判定する。
   ここでいう第三者は、`agent-toolkit/rules/01-agent.md`「役割分担」が定めるユーザーと、その指示で動く実行主体の外側にある主体とする。
   開発環境、検証用の環境その他のユーザーの側が使う資源を使う主体は、この範囲の外に置く

要求が対象の主題又は責務で範囲を述べた場合は、前記の判定へ入る前に、対象成果物の内側に主題の宣言が実在するかを調べる。
実在する場合はその宣言から範囲を確定し、確認経路へ送らない。主題の宣言は、文書では表題の要素と最上位の見出し、コードではそのモジュールの責務の記述を指す。

ユーザーの明示指示と異なる判断を確定する場合は、その判断と差異の理由を記録対象とする。

## 原文からの具体化を要する軸

ユーザー要求の対象、適用範囲、外部可視の結果ならびに除外内容を原文から新たに具体化する場合と、原文が示す対象集合を縮小、置換、細分化する場合は、具体化を要する軸を先に列挙する。
対象、範囲、実行時点、区分のうち、変更により実行時の結果又は要求を実施する範囲が変わる箇所から軸を求める。
依頼文が操作の対象を示す主語と目的語のいずれかを省略し、その省略により操作対象の種類（機能そのものと、その機能の特定の利用）が複数に解釈できる場合は、種類の相違も軸へ加える。
原文が定めた対象集合を変える軸は、拡大と縮小のいずれも同じ確認経路で扱う
（努力目標。対象を狭める判断も要求の一部を実施しない結果を生む）。
その対応の反映先が、全ての利用者へ配布する規範と特定の実行環境だけに適用する記録のいずれになるかも軸として列挙する。
反映先は、実行時の外部可視の結果が同じでも対応が適用される環境の範囲を変えるためである。
列挙した軸ごとに、原文が定めているか、本書の2段階の判定で自ら確定できるか、確認経路へ送るかを判定する。
確認経路へ送ると判定した軸のうち、対象集合の範囲の広さを扱う軸は、調査を完了して推奨案と観測根拠を示し、成果物を確定する前に送る。
操作対象の種類を扱う軸は、調査の前提を固定する前に送る。
前提の固定には、委譲先の起動文へ書く対象の想定、確認の選択肢と推奨案の構成、計画の対象集合を含める。
判定した結果は、軸ごとに、成果物の種別に対応する記録先へ残す。
ユーザーが対象、範囲及び結果を明示した提案を同じ内容で採用する場合、コードベースから確定できる事実、実測による内部値の補正、ファイル配置、関数分割及びテスト手段は自ら確定する。

## 確認を要する事項

本書の第1段階でユーザーの選好に依存する事項、第2段階の承認対象に該当する場合、
および次の各項に該当する場合は確認経路へ送る。
確認経路は、メインエージェントでは実行環境の構造化質問（Claude Codeでは`AskUserQuestion`）とし、この機能を利用できない実行環境では`references/codex-format.md`の固定形式で提示する。サブエージェント及び委譲先では呼び出し元への差し戻しとする。

- 複数の対応層（実装変更・ドキュメント追記・規範改訂など）が候補となり既存の方針では確定できない
- 指示の文言が複数の解釈を許し、解釈により成果物が大きく変わる
- 受け取った発話が単体では実施すべき工程を定めず、直前の要求との補い方が複数成立して実施する工程が変わる（補った関係を確定してから、その解釈に基づく成果物の変更と委譲へ着手する）
- 破壊的操作を含む委譲先が、意図せず外部公開状態を除去した
