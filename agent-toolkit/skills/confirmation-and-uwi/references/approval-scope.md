# 承認範囲の判定

第2段階の判定は、操作が残す副作用だけを入力として行う。操作の目的は判定の入力から外れる。
既存の環境、成果物又は依存関係を置換、再作成又は削除する操作は、調査、原因特定又は動作確認を目的とする実行でも
破壊的操作として承認対象とする。
調査という目的が承認要否の判定を上書きすると、合意していない置換が確定する。

第2段階に該当する操作は技術選択が一意でも確認経路へ送る。
ただしユーザーが提案として指定した操作は、その提案の範囲では合意済みとして扱い、そのまま実施する。
承認源はユーザーの指示、規範、手順、承認済みの計画並びに人間由来のWIとする。人間由来のWIから承認が成立する条件は`agent-toolkit:wi-standards`を正本とし、他の承認源では、その指示、規範、手順又は計画が定める範囲を承認の範囲とする。
成立した承認は、承認源を問わず、操作、対象、影響範囲及び成立条件が同じ範囲へそのまま適用する。
適用範囲を限定して受け取った指示は、その限定が成立している間の、同じ対象への操作にだけ適用する。

成立した承認が無く第2段階に該当する操作は、事前承認と事後承認へ分ける。
ユーザー要件・運用方針の選択を伴う変更のうち、可逆であり、第三者への影響、外部サービスの状態変更及び復元に追加の外部操作を要する副作用のいずれも伴わない操作を事後承認とする。
技術資料又は実測で確定する実装上の選択は事後承認の対象から外す。
事後承認の操作は、最善と判断する対応を実施したうえで確認経路へ送り、回答を待たずに元の作業を続ける。
事後承認の操作を事後承認型UWIとして記録するのは自律モードに限る。協調モードでは、その操作の可否をその場の確認経路で確定する。
ただし、「判断指針」が定める、指定された手段と明らかに異なる手段の採用を記録する事後承認型UWIは、協調モードでも投入する。
いずれかの副作用を伴う操作は事前承認とし、合意を得てから着手する。
成果の適否をユーザーだけが観測でき、実行主体がいずれの手段でも観測できない変更は、第2段階の該当の有無にかかわらず事後承認として扱う。
この変更では、最善と判断する対応を実施して元の要求を終端し、適否を事後承認型UWIで問う。
画面表示の見え方や操作の感触など、実行主体が再現できない環境でだけ現れる結果が該当する。
前段が事前承認と定める副作用を伴う操作は、事前承認のまま扱う。
ユーザーが実行時に直接観測する出力の変更を理由に確認経路へ送る場合は、その変更がエンドユーザーの運用へ影響するかを先に判定し、影響する変更を理由として元の作業を止める。

事前承認を求める時点までに、既に許容されている範囲で実行でき、かつ未回答の確認事項に依存しない準備を完了する。
承認を求める本文には、その準備で得た成果と、承認後に実行する操作を示し、ユーザーが可否を判断できる状態にする。
未承認の操作へ進む根拠は、承認の成立だけとする。
準備自体が確認を要する場合は、その確認を先に送る。

第2段階で公開インターフェース変更に当たるかを判定する前に、そのインターフェースの消費主体を確定する。
消費主体は、そのインターフェースを実行時に呼び出す主体と、その出力を読む主体で判定する。
成果物の配布元、置き場所及び名称は、この判定の外に置く。
消費主体がコーディングエージェントだけであるインターフェースは、公開インターフェース変更の対象から外れる。
受理形式・オプション・公開名・説明・入出力の形式・スキーマ・返却形式のいずれの変更も同じ扱いとする。
該当の例は次のとおりとする。
agent-toolkitが配布するコマンドライン群（`atk`コマンドとスキル配下のスクリプト）。
MCPサーバーが公開するツール（対象プロジェクトが提供するものを含む）。
コーディングエージェント向け文書が定める起動契約と返却形式。
フックがコーディングエージェントへ返す通知の本文。
これらを含む各対象についても、前段の消費主体の判定を実施して該当を確定する。
ブラウザーUIの画面・エンドユーザー向け文書・ユーザーへの通知は、エンドユーザー又はユーザーが直接読むため、公開インターフェースとして第2段階の対象に残る。
これらの出力の変更には、第2段階の判定を通常どおり適用する。
消費主体がコーディングエージェントだけである変更は、第1段階の技術判断で確定し、確定内容を成果物へ記録する。
そのインターフェースが実行する操作自体が第2段階の他の区分に当たる場合と、ユーザーの明示要件を変更する場合は確認経路へ送る。
破壊的操作では、実行内容・影響範囲・復元方法の事前説明を維持する
（`agent-toolkit/share/rules-main.md`「ユーザー発話の解釈」の提案的表現の規定に従う）。
パターン、ワイルドカード、状態指定などで対象を一括選択する破壊的コマンドでは、同じ指定で対象の一覧と削除時の副作用を実測してから影響範囲を示し、依頼の範囲外の対象を除いたコマンドにする。
利用者へ実行を求めるコマンドを案内する場合も同じとする。集合指定の評価結果は起草時の想定より広がり得るため、実測前の案内は依頼していない対象の削除を招く。
第1段階で認識の違いにより要件や結果が変わる未確定事項は、第2段階に該当しない場合も同じ確認経路へ送る。既に明示された要件と合意済みの要件は再確認の対象外とする。その内側で技術資料や実測から確定する実装判断も同様に扱う。
