# ユーザー確認とユーザーへの報告

本スキルは確認要否の判定から手段の選択、回答後の作業再開までを一続きに扱う手順を提供する。
UWIの本文、投入、状態および依存関係の形式は`agent-toolkit:wi-standards`を起動して適用する。

## 起動契機

起動契機はfrontmatterの`description`が定める。同所が起動契機から除く自動的なプロンプトは、機械が生成してユーザー入力欄へ入る本文とする。
`atk wi process-loop`が子セッションの最初の入力として渡す起動時プロンプトと、モデルの可用性を確認するプロンプトがこれに当たる。
生成側は新しい本文を`atk-auto`要素で囲む。機械が生成した本文の境界とユーザー発話の証拠は`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」が定め、その境界の内側の本文は自動挿入として起動契機から除く。
委譲先として起動されたターンも、受け取る委譲プロンプトがユーザーの発話ではないため対象から外す。

Claude Codeメインが利用上限の猶予通知を受けた場合は、ユーザー発話への応答とは別の起動契機として本スキルを起動し、`references/usage-limit.md`「利用上限の猶予通知を受けたときの続行と再開」へ進む。
規範どうしが矛盾する場合、手順どおりに進められない場合、権限拒否を観測した場合は、読込表の各行の資料の手順に従う。

## 確認要否の判定

判定の前に、選択肢を依頼の目的と要件、そのセッションでユーザーが示した判断基準、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」、明文化された方針の順で順位付ける。明文化された方針はQCDを達成するための手段であり、QCDが明らかに悪化する場面での扱いは同節に従う。ユーザーが示した判断基準には、その場で示した手段と作業の進め方への指示を含めず、それらは`agent-toolkit/rules/01-agent.md`「QCDと3段判定」のユーザーが示した手段の評価で扱う。
そのうえで、確認を発行するかは目的・期待結果・認可の確定と、その範囲内の手段の選択を分けて判定する。

要件・意図の曖昧さは、原文・先行発話・現物を調べても、ユーザーしか答えを持たず解釈が定まらない状態とする。
答えによってエンドユーザーが観測する結果、対象・範囲、要件の充足が変わるかで、実現の仕方だけを選ぶ技術選択と区別する。
この基準は`references/judgment.md`「認可を要する操作」の目的側と手段側の判別と同じである。

調査や変更へ着手する前に、目的・範囲・期待結果・制約・外部可視の挙動・境界・例外・除外の各軸で曖昧さを全件列挙し、各件へ次の1〜4を適用する。2で解消できず3に当たる事項は全て確認し、残りを推測で埋めない。

1. 依頼の目的、期待結果と認可が確定しているかを判定する。ユーザーがその結果で何を判断し何を行うかを利用場面から導き、明示された要件に加えて、利用場面で必要な表現されていない要求も目的の評価へ含める。既存仕様と整合することや算術・実装として正しいことは、目的への適合とは別に判定する。目的への適合と認可の確定は、推奨案を持てることとは別に確かめる。
2. 不確実性が残る場合は、先に手元の情報で解消を試みる。調査、現物の観測、公式資料、明文化された方針、成立済みの承認、そのセッションでのユーザー発話と、起動中のスキル・規範・ユーザー指示が定めた工程と対象集合は、手元の情報に含める。定めを変える根拠は、現物を観測して得た事実に限る。調べれば確定できる未知は調べて確定し、調べていない未知は確認不要と判定する前に調べる。元の要求と、関わるユーザーが確定した判断の目的（判断の記録、当時の確認本文、提示した選択肢と回答から読み取る）も手元の情報に含める。解釈、区分（目的側か手段側か、バグの修正か新しい挙動の追加か、条文の失効かなど）または適用範囲を決めかねる場合は、その目的に照らして結論を確定する。確定した結論は4の自ら確定した判断として報告する。規範の区分を決めかねることは、それだけでは3の確認理由から外れる。判断の目的を記録からも当時の確認本文からも特定できない場合は、ユーザーだけが持つ値の不足として3へ送る。
3. 調べた後も、要件・意図の曖昧さのうちどの解釈を採用するかでエンドユーザーが観測する結果が少しでも変わるものか、ユーザーだけが持つ値（選好、認可、外部の状態、手元に無い資料）の不足が残る場合は確認を発行する。結果の違いの大きさは判定の入力から外す。各質問の本文へ、回答によって分岐する外部可視の結果、根拠と推奨案を書く。質問として発行するのは、回答ごとに分岐する結果を書ける問いに限る。回答で結果が変わらない問いと技術選択の問いは、手元の判断で確定する。結果を左右する点を問わずに周辺の点だけを問う確認では、前段の全件の確認を満たしたことにならない。推奨案を持つ場合も同じく確認する。成立済みの認可は再利用する。所要時間と費用の許容範囲もユーザーだけが持つ値に含める。費用と所要時間の見込みは観測から求めて案の影響として書き、許容するかは自ら決めない。ユーザーが範囲語か開放列挙で求めた対象（ツールや手順、確認の工程など）を費用や所要時間、手間を理由に省く判断は、対象集合の縮小に当たる。任意にする判断と求められた場合だけ実施する判断も同じく縮小に当たり、いずれも4の技術手段の選択としてではなく`references/judgment.md`「原文からの具体化を要する軸」に従って確認する。
4. 目的と認可が確定し、その範囲の内側の技術手段だけが残る場合は、自ら確定して実施する。別の合理的なエージェントなら異なる判断をし得るものは、`agent-toolkit:completion-report`の読込表で報告の本文を書く前に読む`references/report-formats.md`「作業完了報告のフォーマット」の`### 自ら確定した判断`へ書く。自律モードでは同書「報告用UWIのフォーマット」の`### 自ら確定した判断`へも1件1行の形式で書く。先行発話や定めから確定した事項は、根拠となった発話または定めを理由へ書く。

目的に適した実装を選ぶための推論は、目的と認可の範囲の内側の選択へ作用させる。明示された要件の上書き、未合意の目的側の変更、依頼に無い挙動や機能の追加は推論だけで確定せず、3に当たるものとして確認する。
委譲先から差し戻された論点と、委譲先へ調査や選択を回そうとする技術的な選択肢にも同じ判定を適用する。手元の情報で決まる選択は、委譲の前に確定して委譲先へ渡す。工程やスキルの手順が条件付きでユーザー確認を定めている場合も、その条件が成立した事項へこの判定を適用し、技術的に決まる事項は自ら確定する。
他の規範が用いる「認識の違いで要件や結果が変わる未確定事項」は、この判定の3で確認を要する事項を指す。

- 認可または選好がユーザーだけが持つ値に当たる操作と、その事前承認・事後承認の区分は`references/judgment.md`「認可を要する操作」と`references/approval-scope.md`が定める。この区分は推奨の順位にかかわらず適用する。
- 規範・文書・設定の記述を置くファイルと節、関数分割、内部データ表現、検証手段その他の技術選択は、目的と認可が確定していれば手元の情報で決まる事項として自ら確定し、事後承認の対象から外す。依頼がもともと求める変更の実施方法、範囲語が定める対象集合の適用、仕組みの要否も同じく自ら確定する。
  ユーザーが適用する水準や分類を示した場合も、その記述を必要とする工程で各候補が読まれるかを、読込を定めるスキルや規範の現行条文で確かめて配置先を決める。

複数案、変更の広さ・波及、観測結果の変化、明示規定の不在などの表面属性だけでは確認要否を決めず、前段の判定を使う。

質問の件数・回数、推奨案の有無、規範上の自律度は判定の入力から外す。必要な確認で意図の違いを防ぎ、技術的に決まる事項は自ら確定する。自律遂行と質問の削減は目的・要件とQCDを守るための手段である。

ユーザーの判断を求める確認本文と、委譲先が委譲元へ送る確認通知が含む項目を「確認提示項目」と呼ぶ。確認提示項目は判断対象、推奨案、代替案、根拠、影響範囲およびユーザーが観測する結果とし、協調モードの確認本文では回答後に実施する操作を加える。
根拠、`共通前提:`行、選択肢の説明のいずれかで既存の規範・手順・仕様を挙げる場合は、名前や所在に加えて、それに従うことで防ぐ事象か確保する結果（従わない場合に誰に何が起きるか）を書く。
名前や所在だけでは、ユーザーはその規範を保つ案と外す案の得失を比べられず、理由を問い返すまで判断できない。
選択肢が対処法、操作または回避手段を示す場合は、その手段がユーザーの試みる操作を可能にするかを書く。
可能にしない手段では、達成する別の目的と、元の操作が成立しない条件を併記する。
別目的の手段を成立手段として示すと、ユーザーは元の操作を完遂できる案として選択する。

確認を発行する応答の地の文へ、確認を発行することだけを書かない。推奨案とその根拠の要旨を確認の本文へ同梱し、地の文を置く場合は同じ要旨を含める。
確認を発行しない応答で未確定の選択肢を示す場合と、推奨案を確定できない場合の扱いは`${CLAUDE_PLUGIN_ROOT}/share/rules-main.md`「ユーザー向け発話ルール」の推奨案の箇条に従う。同梱するのは要旨とし、分量は確認の本文より短くてよい。
確認の本文は描画されるまでユーザーへ到達しないため、先に到達する地の文が判断を委ねるだけの内容であると、ユーザーが応答を中断して推奨の提示を求める。

## 確認の選択肢を組む手順

確認は検証済みの前提に基づき本文だけで判断でき、合意した範囲がそのまま成果物になるように組む。
確認本文と選択肢は`references/choice-construction.md`に従って起草する。前提と各案の影響の根拠を同書「根拠の確定」で確かめ、同書「候補の構成」で選択肢を組む。続けて副次的影響と回答単位を同書「影響と回答単位」で確かめ、本文の語を同書「本文の語」で確かめる。

## 手段の選択

両工程の定義は`agent-toolkit/rules/01-agent.md`「役割分担」が定め、手段は次の表で選ぶ。表の後に挙げる、モードによらず個別のUWIを使う場合は、表の行より優先する。権限拒否の偽陽性の確認の手段は`references/permission-denial.md`「偽陽性と判断できる拒否への対応」が定め、表の行より優先する。
ユーザーへの報告では、発話本文と報告用UWIのどちらでも、作業の結果を都合の悪い結果も含めて正直に報告する。

| 工程 | 協調モード | 自律モード |
| --- | --- | --- |
| ユーザー確認（事前承認） | 実行環境の構造化質問。Claude Codeは`AskUserQuestion`（制約は`agent-toolkit/share/rules-main.claude-code.md`）、Codexは`agent-toolkit/share/rules-main.codex.md`の手段を使い、適合するものが無ければ`references/codex-format.md`の固定形式で提示する | 実行環境が実際に働く回答期限を持ち、ホスト契約に適合する構造化質問を発行できるメインだけが、その場で質問する。期限を超えて回答が無い場合は`references/main-behavior.md`「未確定判断の保留と暫定判断」へ進む。期限が無い実行環境と、期限の設定値があっても期限を無効化する条件が成立する実行環境では、質問を発行せず最初から事前承認型UWIへ記録し、回答を要する元項目だけを保留する。回答期限を持たないCodex Default modeもこの実行環境に含める |
| ユーザー確認（事前承認以外の、回答を待つ通常の確認） | 事前承認の行と同じ手段を使う | 回答期限の有無によらずその場の質問を発行せず、事前承認型UWIへ記録して`references/main-behavior.md`「未確定判断の保留と暫定判断」に従う |
| ユーザー確認（事後承認） | その場で構造化質問を使う | 回答を待たずに事後承認型UWIへ記録し、元の作業を続ける |
| ユーザー確認（認識合わせ） | 「認識合わせ」の手順で、事前承認の行と同じ手段によりその場で質問して回答を待つ | その場で質問する。実行環境が回答期限を与える場合（`atk wi process-loop`から起動したセッションなど）は、期限を超えて回答が無ければ`references/main-behavior.md`「未確定判断の保留と暫定判断」へ進む。回答期限の無い実行環境（手動で起動したClaude Codeなど）でもその場で質問して回答を待つ。構造化質問を発行できないCodex Default modeでは、`agent-toolkit/share/rules-main.codex.md`の自律モードの例外に従う。この場合は提示する理解と問いをUWIへ記録し、回答を要する元項目だけを保留する |
| ユーザーへの報告 | 発話本文。作業完了報告は`agent-toolkit:completion-report`の書式に従う | `agent-toolkit:completion-report`の報告用UWI（セッションに1件） |

自律モードで実際に働く回答期限を持つのは、`atk wi process-loop`のように起動時に有限の期限を与える実行環境である。回答期限を無期限とする設定で起動したセッションと、`askUserQuestionTimeout`のような回答期限を提供しない実行環境は、期限を持たない実行環境として扱う。
認識合わせの質問を自律モードでも回答期限の有無によらずその場で発行するのは、認識合わせがユーザーの割り込みや是正の直後に起動され、理解を確かめる回答を得ることがその目的だからである。
回答なしで終わった確認のUWIへの切替は`references/main-behavior.md`「未確定判断の保留と暫定判断」が定める。
有効な回答期限の超過、回答なしで終了した後の同一セッションの確認、事前承認を要する元項目の保留は同節へ接続する。
実際の回答を得た場合は、その合意に沿って続行する。ユーザー接点を持たない委譲先は、後段の確認通知の手段で委譲元へ返す。

次の場合はモードによらず個別のUWIを使う。

- 成果の適否をユーザーだけが観測できる変更は、元の要求を終端して事後承認型UWIで適否を問う
- AWIの`## ユーザーコメント`またはUWIの`## 回答`へ直接記入された質問への回答は、ユーザーへの報告として個別のUWIで届ける。自律モードの報告用UWIへの記載は`agent-toolkit:completion-report`の書式に従い、個別のUWIの投入を代えない

自律モードでユーザーが指定した手段と明らかに異なる手段を採用した記録は、個別の事後承認型UWIで確認する。協調モードでは採用の前に確認するため、記録のUWIは自律モードに限る。

自律モードでは次の実施を個別の事後承認型UWIにせず、報告用UWIへ含める。事前承認の対象は事前承認のまま扱う。

- 起動中のスキル、適用中の規範、ユーザー指示または計画が記録した回答が工程・対象集合・副作用を定めた範囲の実施
- 調査の結果で解釈が1つに定まった要求を解釈して実施した記録
- 規範からの逸脱（`references/approval-scope.md`の逸脱の扱い）
- エージェントが起草した完成条件を技術的理由で改めた判断
- 採用する再発防止策なしで終えた判断。`agent-toolkit:session-review`が扱う問題では振り返り結果報告が兼ねる

事後承認は実施した対応の可否がユーザーだけが持つ情報（選好、認可、成果の見え方）で決まる場合にその可否を問う。回答ごとに分岐するエンドユーザーが観測する結果か実施する操作を書けない対応は、個別の事後承認型UWIにせず報告へ含める。「確認要否の判定」の3が質問を回答ごとに分岐する結果を書ける問いに限るのと同じ基準である。問いと判断材料をエンドユーザーの語で書けず、規範の工程名や内部の作業の状態でしか書けないことは、その判断がユーザーの判断ではない徴候として扱う。
ユーザーへの報告は判断を求めない内容を届ける。
報告用UWIが事後承認型UWIの2択書式を使うのは是正を返せる回答欄を置くためで、工程はユーザーへの報告のままとする。

非同期の構造化質問では、発行の成功と初期選択を回答または承認として扱わない。後続の実回答を元の質問へ対応付け、その回答に依存する操作は受領まで確定しない。
委譲先が委譲元へ確認事項を通知する手段は`agent-toolkit/share/rules-subagent.md`「確認事項の即時通知」に従う。

確認を発行したエージェントは、ユーザーがその確認を棄却したか、承認要求を取り下げたことを観測した場合、同じ論点を`## 確認要否の判定`で判定し直す。認識の違いで要件や結果が変わる未確定事項が残る場合は、その論点の解決を要する元項目を`hold`で保留したまま事前承認型UWIへ記録し、確認を要しない範囲に収まる場合は自ら確定して続行する。棄却と取り下げの観測は回答なしに当たらないため、以降の確認を同期的に発行しない切替の条件からは外れる。

事後承認の確認本文と記録する範囲は`references/approval-scope.md`の事前・事後承認の区分に従う。

## 認識合わせ

ユーザーと自分の認識が一致していない可能性があるとき、行動を繰り返し咎められるとき、および実ユーザー発話の全角`！！`を契機とするUserPromptSubmitフックの注記を受けたときは、ユーザーの目標と解決したい問題の理解を次の手順で確かめる。

1. 現在の依頼とユーザーの発話を読み、ユーザーが達成したい目標と解決しようとしている問題を、それぞれ自分の言葉で提示する。ユーザーの発話から得た理解と、エージェントが補った前提を区別する。
2. その理解が合っているかを「手段の選択」の表の認識合わせの行の手段でその場で確かめる。問う対象は目標と問題の理解とし、採用案の承認へ置き換えない。質問は「確認要否の判定」と「確認の選択肢を組む手順」に従って構成し、実際の回答を受け取る。
3. 回答を元の依頼の目的・要件と自分の理解に照らして、次に行う処置を確定する。処置には採用済み案の縮小・撤回・置換を含め、`agent-toolkit/share/rules-main.md`「目的との一致の確認」と`agent-toolkit:review-standards`の`references/reviewee.md`「ユーザー指摘の受領」に従う。

ユーザー割り込みの扱いは`agent-toolkit/share/rules-main.md`「協調と自律」に従い、関係のない工程の実行モードは保持する。
質問の発行成功や初期選択を回答として扱わず、回答に依存する処置は実回答まで確定しない。
委譲先で認識合わせが必要と分かった場合は、確認事項を委譲元へ返す。
