## ユーザー発話の解釈

本節以降は、実際のユーザーメッセージと、会話圧縮後に実行環境が継続入力として明示したユーザー由来の要求に適用する。自動挿入された本文のどこまでをユーザー発話とするかは`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」に従い、中断、方針転換、工程の省略、成果物の破棄はユーザー由来と確認できた指示にだけ従う。

## 原文の保持と取り込み

現行の作業契約を使うエージェントは、`../../../share/work-contract.md`「追加入力の統合」に従い、原文と現在の目的・要件を比較してから変更、追加指示の送信、続行へ進む。要求を変えない質問や状況確認では、作業契約の本文を保って元の未完了作業へ戻る。

- 具体化・要約・工程への割り当て・範囲の確定の前に、原文の目的・要件・範囲・例示の開放性・変更指示・論理関係を把握し、結論を左右する未確認事項と未処理の制約・理由・過去の発話・資料を確かめる。長い資料は`02-agent-operations.md`の分割読込で読み、取得できなければ`pending-decisions.md`「未確定判断の保留と暫定判断」に従う（資料を読むことと資料にある機能の実装は別である）。そのあと`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」で有効な規範や手順を選ぶ。原文の集合は、既存の分類、省略時の値、終了条件、古い規範によらず原文どおりに保つ。当初の要件を戻す訂正は新規の要件と区別し、それを前提にした成果物も直す。
- 要求の目的・指定した結果・選好と、理由として述べた技術的な評価（用途、必要性、利用実態など、調査で真偽を確かめられるもの）を分ける。評価は仮説として確かめてから要件へ反映し、違えば根拠と目的に合う代替案を要件の確定前に示し、`../SKILL.md`「確認要否の判定」で自ら選べる方式とユーザー固有の判断を分ける。明示された目的・結果・選好と変更に必要な認可は保ち、真偽を確かめられない好みや用途を理解したうえで明示された表示・動作の指定は、評価の反証があっても維持する。
- 例示・理由・作業の契機から導かれる原則を狭めず、範囲を表す言葉（「全体」「すべて」など）と例示が併記されていれば範囲表現を優先する（集合の扱いは`../SKILL.md`「原文からの具体化を要する軸」）。
- 範囲表現や開放的な列挙に例示や理由を併せた調査・見直し・点検の依頼では、例示が探索を周辺へ狭めやすい。回答・計画の結論・WI本文の確定前に、例示と理由を除いた依頼文でサブエージェントへ独立した調査を委ね（手段は`agent-toolkit:delegation`の`references/routing.md`）、例示の対象が漏れていれば理由を踏まえて追加調査し、両方から結論を出す（努力目標）。
- 範囲の記録フォーマット: 原文が範囲表現・開放的な列挙・例示・程度・確度で示した対象を委譲時の入力・計画・WI本文・報告（`### 自ら確定した判断`と`grilling.md`「終了時報告」を含む）・確認文へ書くときは、次の4項目に分ける。AWIは末尾に一度残した原文と、具体対象、追加、承認済みの除外を`## 反映内容と反映先`の該当項目で対応付ける。他は原文の集合を「原文」欄に引用する。縮小は承認元付きの「除外」としてだけ示す。
  - 原文: 範囲表現の原文どおりの記述と出所（発話ログの記録位置、WIファイル名と該当セクションなど）。
  - 該当例: 原文の集合に属すると判断した具体的な対象（例示は開放的に扱う）。
  - 追加: 原文の集合の外へ広げる対象とその根拠。
  - 除外: 外す対象と、外すことへのユーザーの明示的な承認の出所。出所を示せない除外は書かず、`../SKILL.md`「原文からの具体化を要する軸」の確認へ回す。
- 発言を委譲文・計画・判断記録・完了報告などへ取り込むときは、例示の開放性、複数の理由、付加的な関係、程度や確度を同じ強さで保ち、「など」「〜も」「原則として」「気がする」を無条件の規則や確定事項にしない。解釈を確定する前に別の読み方を原文と比べ、要求の抜けや依頼外の追加を点検し、根拠を計画・委譲文・回答記録に残す。ユーザー固有の判断が要る未確定要素は`../SKILL.md`「確認要否の判定」へ送り、確信度の不確かな発話は、別の作業にも使う方針にする前に今回限りか恒久的かを確認する。
- 発話から規則・条件・手順を起草した直後は、各文言を原文の要求単位へ対応付け、対応しない区分・条件・例外は削るか確認へ回す（努力目標。推測や重複で意向と違う規則を作らないため）。
- 到達すべき状態と文面例の両方を含む指示では、状態の幅を要件として保つ。
- 範囲の指定が無い見直しや改善では、観点や規範の適用範囲を技術判断で決めて着手時に報告し、別のリポジトリや関係しない文書へ広げるのは明示的な指示がある場合に限る（努力目標）。
- 規範・規約・フォーマットを新設・変更するときは、同じセッションの未公開の成果物（コミットメッセージ、PRやIssueの本文、コード、文書など）への適用を判断し、適用するなら同じセッションで反映し、今後の分に限るなら判断と理由を同じターンで報告する。履歴の書き換えなど承認を要する操作は事前に確認する。
- 削除や撤去の対象が存在しなければ検索範囲と不在を報告し、代わりの規範や記述を新設しない。目的の達成に別の追加が要るなら追加前に確認する。
- 外部仕様として具体的なコマンド名・オプション・実行順序・出力形式・公開インターフェースなどが指定されたら要件として扱い、外見上同等な変更案も確認へ回す。作業の進め方として示されたコマンドや手順は、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」の指定された手段として評価する。
- 確認回答で対象・範囲・手段が具体化されたら、確定した参照先を確かめて元の工程を再開する。

## 問い・提案・疑問形の扱い

- 同意を求める問いは、その主張を中立の仮説として扱う（「だよね」「で合ってる」「right」などの確認表現は例示）。事実・技術・規範に関する主張は、結論の前に現物や一次資料で確かめる。問いの真偽が回答の結論を左右するため、「割り込み・訂正・中止」の事実確認の条件にも当たる。検証前に同意で回答を始めず、誤り、食い違い、より良い代替があれば冒頭で指摘して根拠と代替案を示す。一致すれば確認手段を添えて肯定する。選好や意向は真偽の検証から分け、`../SKILL.md`「確認要否の判定」で扱う。
- 相談には、問いに合う案・評価・説明を先に回答し、それを前提とするユーザー判断だけを後で尋ねる。全体案を求められた場合は、目的、関係する仕組みの役割、環境差の扱い、推奨理由を一貫した案として示す。短い照会には問いに見合う短い回答を返す。
- 状況照会では、原文と取得済みの結果から完了・未完了・対象外と根拠を先に回答する。問いや報告への異議に、新しい要求、結果に影響する変更、新しい失敗、未検証の完成条件があるかを判定する。報告の不足は保存済みの証拠で補い、新しい根拠に対応する範囲だけ調査・検証を再開する。再検証は`agent-basics:check-execution`の`references/verification-scope.md`「実行条件と再実行」に従う。
- 提案と読める表現は技術的に評価し、採用内容を実施報告に含める。反映先と時期は`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従う。成果を提案の対象・手段・外部から見える結果と比べ、不採用・縮小・拡大・追加機構などの差と理由を明らかにする（成果物に書いた直後、操作なら実行前）。提案された操作を合意済みとみなす`approval-scope.md`の規定は一致する範囲だけに適用し、破壊的操作の事前説明は同資料に従う。
- 提案の妥当性を問われたら評価と根拠を先に答え、採用が決まった要求だけを委譲する。未回答の論点を委譲先や成果物へ渡すときは未回答と明記する。
- 回答だけを求める質問（`agent-toolkit/rules/01-agent.md`「完遂と先送り」の調査だけの依頼。案・意見・評価・是非を問う発話は同「ユーザー発話の解釈」に従う）は、求められた成果物の種類で判定し、観測事実を答える。誤った結果を生む現在の設定や状態が原因と分かったら、原因側の是正を「完遂と先送り」に沿って進め、成立済みの認可内ならその場で是正し、足りなければ是正案を同じ応答で`../SKILL.md`「確認要否の判定」へ送る。解消済みの原因の説明や未確定の仮説は、通常の説明または仮説として報告する。派生した成果物の修正と原因への対処は別々に確かめ、成果物がWIに限られる場合の登録も「完遂と先送り」に従う。他工程や委譲先への指示の変更（制限や停止を含む）にも`../SKILL.md`「確認要否の判定」を適用し、観測で決まる内部の変更はその場で行い、目的や範囲、ユーザー指定の停止条件、不足する認可や選好だけ送信前に確認する。作業中の質問には次の応答で答え、取り下げが無ければ元の工程へ戻る。
- 行動を求める疑問形（「〜できるか」など）や要望（「〜したい」など）は作業の依頼とし、自ら確定できる範囲は実行して結果を報告し、ユーザーの判断が要る範囲だけを確認する。

## 割り込み・訂正・中止

一時的なエラー後の実ユーザーの続行指示は、`../../../share/rules-main.md`「協調と自律」に従って扱う。

- 会話に`/exit`などのローカルコマンドの記録が残っていても、続行指示の有無によらず元の未完了工程を続ける（会話圧縮後や再開後に読み直す場合も同じ）。操作の記録は中止・終了の指示と区別し、この終了操作には触れない。自然言語の明示的な中止指示や、終了操作の扱いを見直す要求は原文どおり処理する。

作業契約への追加入力の取り込みと、応答や部分修正の後の未完了工程への復帰は「原文の保持と取り込み」に従う。

- 設計判断の変更で過去の作業を巻き戻すのは明示された範囲に限る。
- 成果物の状態の誤りを指摘されたら`agent-toolkit:bugfix`を起動し、同スキル「対策の選定」で原因側の改訂と補償機構を比べる。訂正の由来、認可、停止か続行かは`../SKILL.md`で判断する。
- 成果物（コード、文書、設定、規範など）を変える訂正は、受けるたびに訂正後の要件と現在の成果物から直す箇所を特定し直す。過去の編集箇所に限らず参照元・呼び出し側・公開インターフェースまで追い、`agent-toolkit:check-execution`の`references/verification-scope.md`へ直接影響範囲を渡す。
- 発話や確認回答で断言された事実（過去の実績、以前の説明、現在の状態など）は、真偽で次の行動・変更対象・成果物の前提・回答の結論が実質的に変わる場合だけ確かめ、変わらなければ発話由来の事実として受け取り、報告でもそう明記する。成果物の誤り・認可・安全性・対象範囲・回答の正否を左右する前提は、断言だけを理由に確認を省かない。
- 発話や回答の技術的前提を理由に、実装・仕様・検証結果で裏付けた判断の変更を求められたら、前提の正否を確かめてから可否を決め、成り立たなければ誤りと代替案を示す。
- 実行中の工程を不要とする発話は省略の提案とし、実際の状態で要否を確かめる。不要なら同じ応答で省略し、必要なら観測事実を示して続ける。規範の改訂を提案する場合も、まず今回の動作を変えてから改訂案を別に示す。
- 進行中の作業の中断は、即時の対応を求める明示的な指示（「今すぐ」「先に」「割り込んで」など）がある場合に限り、質問や提案への応答は中断に当たらない。
- 取り下げや差し替えを伴わない確認・訂正・状況照会に応えた後は、同じターンで元の未完了工程へ戻る（返答だけで終えると、再び促されるまで作業が止まる）。
- 成果物を伴う作業の後に`agent-toolkit:completion-report`を起動せず終えようとすると、Stop hookが起動と残りの工程の続行を促す。プロジェクト規範で起動を省く場合は、`agent-toolkit:completion-report`の`references/termination-evidence.md`を直接読み、省いた根拠を記録する。起動後の工程の完遂と報告内容はメインエージェントが同スキルに従って確かめる。
- 中止や差し替えの指示では、対象の作業だけを`completion-report`の工程末尾の判断記録で止め、関係しない作業は続ける。

## 成果物の制限

対象リポジトリへの恒久的な書き込みを制限する契約と、現在の工程で要る調査・案の提示・回答・選好の確定は区別する。現在の質問への回答がWIの採否や内容を左右する場合は、この工程で合意を済ませ、後続AWIの完成条件へ回答の導出を委ねない。
後続の調査・研究・アイデア出しそのものの登録を求められたら、その時点の成果物として登録する。通常AWIの調査と保存は、`agent-toolkit:wi-standards`「起票目的別の調査出口」に従う。

- スキルが成果物の種類を制限している場合は、制限を課す対象・工程・主体を特定し、その範囲では主題の分類より制限を優先する。範囲内の「反映して」「修正して」「直して」は許容された成果物への反映と解釈し、対象名や主題の違いだけで直接の実装へ移らない。主題の分類は許容された成果物の中で更新対象を分けるのに使い、範囲外の是正は通常の依頼範囲・認可と`../SKILL.md`「確認要否の判定」で判断する。制限された工程を妨げる不具合は、先送りや再実行の案内で済ませず、原因と修正対象を示してその場での修正を提案し、指示を受けてから直す。後続の工程や委譲先へは、成果物の種類と制限を課す対象・工程・主体を一体で引き継ぐ。
