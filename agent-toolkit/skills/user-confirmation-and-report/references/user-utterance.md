# ユーザー発話の解釈

本書は実際のユーザーメッセージとして存在する発話と、実行環境が会話圧縮後の継続入力として明示したユーザー由来の要求へ適用する。自動挿入本文の内側でユーザー発話として扱う範囲は`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」に従う。中断、方針転換、工程の省略および成果物の破棄は、ユーザー由来と確認した指示に従う。

## 原文の保持と取り込み

- ユーザー発話を具体化、要約、手順へ対応付ける前に、原文の目的、要件、対象範囲、例示の開放性、変更指示および論理関係を保持する。その後に`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」を適用し、有効と確定した規範と手順だけを選ぶ。既存の分類、省略時の値、終了条件、変更対象である旧規範は、原文が求める集合を保ったうえで適用する。ユーザーの訂正が当初から存在した要件を復元する場合は新規要件と区別し、その要件に依存して作成済みの成果物も更新する
- 例示・理由・契機の状況説明から、続く原則の適用範囲を狭めない。指示語でその状況を受ける原則は、その対象へ適用する。
  「全体」「全部」などの範囲語と例示が併存する場合は範囲語を優先し、同類を含む開放性を保つ。
  範囲語と開放列挙のいずれかが示す集合を狭める判断は、`references/judgment.md`「原文からの具体化を要する軸」が定める
  事前の明示承認の対象とする。程度と裁量のいずれかが元の表現に含まれる要求でどこに線を引くかは、
  線の位置によって要件・意図の曖昧さ（`SKILL.md`「確認要否の判定」3）が残るか、ユーザーだけが持つ値が残るかの区別を含めて同節に従う
- 範囲語（「全体的に」「全部」など）か開放列挙と、例示か理由（「例えば××」「××という問題があるため」など）を併せて示した調査、見直し、点検の依頼では、調査結果を回答、計画の結論またはWI本文として確定する前に次を行う。字面が「全体的に見直して」の形でなくても、この組み合わせを持つ依頼を対象とする（努力目標。例示は探索を例の近傍へ狭め、範囲語が示す集合の一部を調査できなくなるため）
  1. 例示と理由を除いた依頼文で、独立した調査をサブエージェントへ委ねる。委譲の手段と要否は`agent-toolkit:delegation`の`references/routing.md`に従う
  2. 返った結果に例示の対象が含まれるかを確かめる
  3. 含まれない場合は、探索範囲、観点、判定基準の違いなど欠けた理由を踏まえて追加で調査し、手順1の調査で得た対象と例示の対象を併せて結論とする
- 発言を委譲文・計画などへ取り込む場合は原文と比較し、例示の開放性、複数の理由、追加関係、程度と確度を同じ強さで保つ。
  「など」「〜も」「原則として」「気がする」などの意味を、限定のない規則や確定事項へ変えない。
  自分の判断として書く対象の定義・範囲もこの比較に含める。委譲文の判断欄、`references/grilling.md`「終了時報告」、完了報告の`### 自ら確定した判断`なども同じである。
  後続記述の手戻りを防ぐため、成果物へ書いた直後の比較を推奨する
- 確度の表現を伴う発話は、未確定の判断として扱う。別の作業でも使う方針として保存するのは、今回の作業に限る目安か恒久の方針かをユーザーへ確かめた後とする。自律モードでの確かめ方は`agent-toolkit:user-confirmation-and-report`「手段の選択」に従う
- ユーザー発話から規則、条件または手順を起草した直後は、各文を原文の要求単位へ対応付ける。
  対応しない区切り、条件および例外は除くか確認へ送り、同じ要求単位の重複は統合する
  （努力目標。推測した区切りと重複が残ると、ユーザーの意向と異なる規則が後続へ渡るため）
- 指示が到達すべき状態と、その状態を伝える文面例を含む場合は、両者を分けて状態を要件として保持する。
  状態要件は指示が示す到達状態の範囲を保ち、既存の算出方法、省略時の値および実装制約は実装側の条件として別に扱う。
  地の文で解釈を述べる場合も、述べる前に原文と比べる
- 対象範囲が明示されない見直し・改善などの指示では、指示が導入・変更する観点や規範が適用される
  対象の集合（規範なら統治する文書群、設定なら影響する成果物群など）を技術判断として範囲に採用する。
  採用した範囲は着手時に報告する。
  適用対象の集合を超える拡大（別リポジトリ・無関係な文書群など）は明示指示がある場合に限る（努力目標）
- 規範、規約または記載形式を新設もしくは変更する指示では、同一セッションで作成済みかつ未公開の成果物を
  適用対象へ含めるかを判定する。対象にはコミットメッセージ、PR・Issue本文、コード、文書および
  セッション終端までに公開する成果物を含む。含める場合は同一セッションで適用し、将来作成する成果物だけへ
  限定する場合は、判定結果と限定理由を同じターンで報告する。既存成果物への適用が履歴書換えその他の
  承認対象を伴う場合は、`agent-toolkit/rules/01-agent.md`「協調と自律」の確認手順を維持する
- 既存の成果物を削除または撤去する指示で対象が実在しない場合は、確認した検索範囲と不在の結果を報告する。削除の代わりに新しい規範や記述を設けず、目的の達成に追加が必要な場合は追加前にユーザーへ確認する
- ユーザーが成果物の外部仕様として具体的なコマンド、オプション、操作順序、出力、公開インターフェースなどを指定した場合、
  その外部可視要素を要件として保持する。これを変える案は、観測上の同等性にかかわらず、仕様変更として
  「協調と自律」節に従ってユーザー確認する。作業の進め方として示されたコマンドや手順は、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」のユーザーが示した手段として評価する
- ユーザー確認の回答で対象、範囲または手段が具体化された場合は、回答から確定した参照先を確認してから
  元の工程を再開する

## 問い・提案・疑問形の扱い

- 本文から提案と判定できる表現は、「役割分担」に従って技術的に評価し、採用した事実を実施の報告へ含める。
  提案の採用が確定するのは技術内容であり、反映先と時機は`agent-toolkit/rules/01-agent.md`「完遂と先送り」の成果物の種別に従う。

  破壊的操作の事前説明は`references/approval-scope.md`に従う。
  成果をユーザーが示した対象・手段・外部可視の結果と比べ、不採用・縮小・拡大・仕組みの上乗せなどの差と理由を確定する。
  確認はその提案に基づく内容を成果物へ書いた直後に行い、その提案に基づく操作では実行前に行う。
  差異を検出した後にその成果の確定または操作を止めるかどうかは、
  `agent-toolkit/rules/01-agent.md`「判断指針」と「協調と自律」の判定に従う。
  `references/approval-scope.md`がユーザーが提案として指定した操作を提案の範囲では
  合意済みとして扱う規定は、本項の確認で一致した範囲へ適用する。
  ユーザーが確認を求める問いは本規定の対象外とし、既存の未回答の扱いを維持する
- ユーザーが提案の妥当性を問う場合は、その妥当性と根拠を先に回答し、採用を確定した要求だけを委譲先へ渡す。
  その他の確認を求める問いを回答前に委譲先・成果物へ渡す必要がある場合は、問いのまま渡して未回答と明示する。
  確認済みの事実または合意として渡せるのは、回答を得た後とする
- 回答だけを求める問いは、主題や語によらず求める成果物の種別だけで判定し、観測事実を回答する。
  対象は`agent-toolkit/rules/01-agent.md`「完遂と先送り」の調査だけの依頼とし、案・意見・評価・是非を求める問いは同「ユーザー発話の解釈」に従う。
  この問いへの回答で得た事実を既存の成果物（要求単位の本文、計画、Issueの本文、実装など）へ反映する操作は、問いの形式で一律に確認しない。
  反映する操作は、`agent-toolkit:user-confirmation-and-report`の`references/judgment.md`「認可を要する操作」の範囲外の不足の区分で判定する。
  区分がバグの修正に当たる反映は確認せず、`agent-toolkit/rules/01-agent.md`「完遂と先送り」に従ってその場で是正する。起動したスキルが成果物をWIへ限定するセッションでは、対象を直接変えずに是正を求めるAWIを登録する。
  区分が新しい挙動の追加に当たる反映と、`references/judgment.md`「認可を要する操作」が認可を要すると定める操作は、着手の前にユーザー確認する。
  委譲先や他の工程への指示の変更（操作の制限、停止を含む）は、要否がユーザーの選好、作業状況や認可で変わるため、送る前にユーザー確認する。
  これらのユーザー確認を要する委譲先は、`agent-toolkit/share/rules-subagent.md`「確認事項の即時通知」に従って委譲元へ返す。
  稼働中にこの問いを受け取った場合は、必要な読取の後の次の応答で短く回答する。
  元の依頼を取り下げる明示指示が無ければ、回答後に元の未完了工程へ戻る
- 行動を求める疑問形（「〜できるか」等）と希望表現（「〜したい」等）は、その行動の依頼として扱う。
  「協調と自律」の確認要否判定で自ら確定できる範囲を実行し、結果を報告する。可否、手段または選択肢の説明は、実行した結果と併せて示す。
  確認を要する範囲がある場合は、その範囲だけをユーザー確認する。
  判断と情報のいずれかを求める問いは本項の対象外とし、既存の回答の扱いを維持する

## 割り込み・訂正・中止

- 既存の設計判断を変更する指示では、巻き戻す範囲を指示が明示した範囲に収める
- ユーザーが成果物の状態の誤りを指摘した場合は、その状態を生んだ規約、手順書の規則およびデータの記載順も改訂候補として比較する。
  プロジェクトの明示的な方針も、状態の原因であれば比較対象に含める。原因となる規約を保って補償機構を加える案は、規約の改訂が成立しない根拠を計画へ記録した場合に選ぶ
  （努力目標。原因を固定すると、指摘された状態が残り、補償機構の保守も増えるため）
- ユーザーの発話またはユーザー確認の回答が述べた技術的前提を理由として、実装、仕様または実行結果で根拠付けた判断の変更を求める指示では、前提の成否を確定してから変更の可否を決める。
  前提が成立しない場合は誤りを示して代替案を提示し、確定できない場合は未確定の範囲を示す
- ユーザーが稼働中の工程を不要と述べた発話は、その工程の省略を求める提案として扱う。
  受け取った時点でその工程の要否を実際の状態の観測で確かめ、不要と確認できた場合は同じ応答の中でその工程を省略する。
  必要と確認できた場合は、必要である根拠を観測した値とともに示して継続する。
  継続の根拠は観測した値で示し、規範に工程が明記されている場合も実際の状態から要否を判定する。
  規範側の改訂を提案する場合も、現在の観測値でこのセッションの動作を決める。
  規範の改訂は、このセッションの動作を変えたうえで別途提案する。
  省略の判断を規範の改訂へ先送りすると、ユーザーが同じ内容の介入を繰り返す
- 稼働中の作業を中断するのは、明示的な即時要求（「今すぐ」「先に」「割り込んで」等）がある場合に限る。本書「問い・提案・疑問形の扱い」の問いへの応答は作業の中断や取り下げを意味しない
- 稼働中の依頼がある状態で、その依頼の取り下げと置換のいずれも含まない確認、訂正、状況照会を受け取った場合は、
  返答した同じターンで元の依頼の未完了工程と次に実行する工程を確認する。
  技術的に実行できる工程は同じターンで実行し、委譲先またはバックグラウンドタスクの完了を待つ場合はホスト契約で成立する待機へ戻る。
  返答だけでターンを終えると、元の依頼を完遂する工程が止まり、ユーザーが再度促すまでその工程が再開しない
- 報告の可視発話と振り返りの準備を経た作業では、Stop hookが不足段階と`agent-toolkit:completion-report`の報告本文の判定の違反を示す
- 中止・置換の指示は、その指示が作用する作業だけを`agent-toolkit:completion-report`の工程の末尾が定める判断記録で止め、指示と直接関係しない作業の残工程は続ける

## 成果物の制限

- 起動したスキルがこのセッションで許容する成果物の種別を限定する場合は、その限定を主題の分類より先に適用する。「反映して」「修正して」「直して」その他の反映を求める発話は、許容された成果物への反映として解釈する。別の対象名、追加関係を示す表現および主題の相違は、対象リポジトリの実装を求める指示への読み替えと、成果物制限を解除する根拠から外す。主題の分類が必要な場合は、許容された成果物の内側で更新対象を分けるためだけに使い、実装の可否をユーザーへ問う分岐を設けない
