# 確認要否の判定の細則と確認を要する事項

本書は`agent-toolkit:user-confirmation-and-report`「確認要否の判定」が定める判定の細則、認可を要する操作、確認を要する事項の例、
およびユーザー要求を原文から具体化する際の軸の扱いを定める。

## 判定の細則

ユーザー要求を具体化する前の原文の保持と優先順位の適用は、`references/user-utterance.md`冒頭の項に従う。

確認要否と質問の優先順位は`SKILL.md`「確認要否の判定」3で決め、確認工程の終了条件は`references/grilling.md`「終了条件」に従う。

目的、スコープ、機能、実現方式、望む結果、制約および優先順位は、未確定事項を点検する代表例とし、各事項へ`SKILL.md`「確認要否の判定」を適用する。実現方式や結果の差だけで確認対象とせず、目的・要件・認可の範囲で技術とQCDにより確定できる事項は自ら選ぶ。
技術的に実現可能な案が1つだけであることと推奨案を示せることは、その案が満たす要件への合意の代わりから外す。`SKILL.md`「確認要否の判定」3に当たる要件・意図の曖昧さが残ったまま推奨案で進めない。
入力資料に記載された、ユーザーが実行時に直接観測しない実装内部の事実的な数値・範囲は、調査または実機実行で確定した観測値へ補正する。
補正の事実と根拠を成果物へ記録し、補正そのものは自ら確定する。ユーザーが能動的に指定した外部可視要件は、この補正の対象外とする。

確定済みの回答を変更する可能性がある場合は、目的・回答原文・既存の観測と追加資料を同じ条件で比べ、実施可能な観測を質問前に終える。
公開仕様との相違が残れば、その差と未確定事項を質問へ示す。

要求が対象の主題または責務で範囲を述べた場合は、対象成果物の内側に主題の宣言が実在するかを調べる。
実在する場合はその宣言から範囲を確定し、ユーザー確認しない。主題の宣言は、文書では表題の要素と最上位の見出し、コードではそのモジュールの責務の記述を指す。
同じセッションでエージェント自身が出力した先行成果物の提案、所見、候補などを依頼が指す場合は、その成果物が提案として列挙した集合を範囲に採る。範囲を表す語がない依頼も、直前の先行成果物だけが提案や所見の集合を列挙している場合は同じ扱いとする。
編集提案のない項目、flag、見送りとした項目など、報告だけに留めた項目は提案集合に含めない。それらを加える判断は「原文からの具体化を要する軸」の範囲変更として扱い、その追加判断だけを確認する。

ユーザーの明示指示と異なる判断を確定する場合は、その判断と差異の理由を記録対象とする。

## 認可を要する操作

次の操作は技術選択が一意でも、認可がユーザーだけが持つ情報に当たるものとしてユーザー確認する。事前承認と事後承認の区分と、成立済みの承認の適用は`references/approval-scope.md`が定める。

- 公開インターフェース変更
- 破壊的操作
- 第三者への影響
- 外部サービス設定変更
- 依頼に含まれないエンドユーザー向け画面・文書・通知の変更
- ユーザーが確定した判断のうち、目的・要件・ユーザーが観測する結果に関する判断の変更

公開インターフェース変更に当たるかを判定する前に、そのインターフェースの消費主体を確定する。
消費主体はそのインターフェースを実行時に呼び出す主体と、その出力を読む主体で判定する。
成果物の配布元、置き場所および名称は、この判定の対象外とする。
消費主体がエージェントだけであるインターフェースは、公開インターフェース変更の対象から外れる。
受理形式・オプション・公開名・説明・入出力の形式・スキーマ・返却形式のいずれの変更も同じ扱いとする。
該当の例は次のとおりとする。
agent-toolkitが配布するコマンドライン群（`atk`コマンドとスキル配下のスクリプト）。
MCPサーバーが公開するツール（対象プロジェクトが提供するものを含む）。
エージェント向け文書が定める起動契約と返却形式。
フックがエージェントへ返す通知の本文。
これらを含む各対象についても、前段の消費主体の判定を実施して該当を確定する。
ブラウザーUIの画面・エンドユーザー向け文書・ユーザーへの通知は、エンドユーザーまたはユーザーが直接読むため、公開インターフェースとして本節の対象に残る。
消費主体がエージェントだけである変更は、手元の情報で決まる技術判断として確定し、確定内容を成果物へ記録する。
そのインターフェースが実行する操作自体が本節の他の区分に当たる場合と、ユーザーの明示要件を変更する場合はユーザー確認する。

実行中の依頼・WI・確定済み要件を実現するために必要なCI関連の外部サービス設定変更には、全agent-toolkitユーザーと全リポジトリに適用する包括的な認可が成立済みである。この認可により、個別のユーザー確認を省く。CI関連とは、workflow、pipelineまたはjobの選択・起動・入力・権限・認証情報・実行前の保護・結果報告・合否判定へ直接作用する設定を指し、CI用secretsの作成・変更も含む。操作がCIへ直接作用するかで判定する。

同じサービスや設定画面にあっても、リポジトリの公開範囲、CIと独立した配信・公開、CI以外を目的とするwebhook・app、CIの実行や合否判定と独立した保護規則は前段の認可の外に置く。複合的な変更では、CIと独立した副作用だけを従来の基準で判定する。目的・要件そのものの変更と、実行環境の権限拒否には従来の確認基準を適用する。

WIの完成条件と依頼の範囲の外で見つけたエンドユーザー向けの不足を是正する場合は、依頼に含まれないエンドユーザー向け画面・文書・通知の変更に当たるかを、次の基準（範囲外の不足の区分）で判定する。ここでいうエンドユーザーはユーザーを含む。消費主体がエージェントだけのインターフェースは本節の公開インターフェース変更の消費主体の判定に従う。

- バグの修正: 文書・テスト・表示・実装意図などの既存仕様が示す結果へ戻し、新たに覚える操作・設定・表示要素を加えない是正。データの誤り、表示崩れ、動かない操作、文書と実装の不一致などを含み、認可を要する変更の区分に当たらないため確認せず直す
- 新しい挙動の追加: エンドユーザーが観測する挙動・操作・設定・画面要素・通知の追加、または既存仕様の挙動変更を要する是正。新しい操作手段や初期値の変更などは、認可を要する変更の区分に当たる

文書、ヘルプ、スキル本文、システムプロンプト、エラーや案内の文言を、製品の機能やツールが持たない操作へ合わせて書き換える是正（文書を機能の制約へ合わせる是正）では、文書の書き換えを「実装と一致しない文書の記述」のバグの修正として扱うことと別に、欠如した機能そのものを本区分で判定する。欠如によりエンドユーザーが案内された目的の操作を製品の中で完了できず、手作業の回避策や別の画面での操作へ案内される場合は、エンドユーザーの停止場面として扱い、機能を加える案を新しい挙動の追加として「確認を要する事項」の確認へ送る。元の文書がその機能を前提に書かれていた場合は、文書の是正と機能の追加の両方に当たる。この判定は追加に認可が要るかを決めるものであり、機能を加える案と文書だけを是正する案のどちらを推奨案にするかは、`references/choice-construction.md`「候補の構成」の推奨案を決める手順で別に決める。

両方に当たる場合は新しい挙動の追加として扱う。確認の費用は、ユーザーが把握しない機能がリリースされる不利益より小さいためである。どちらに当たるかを決めかねる場合は、この区分の目的（ユーザーが把握しない機能を確認なしに公開しないことと、仕様の範囲に収まる是正は確認せずに直すこと）に照らして`SKILL.md`「確認要否の判定」の2に従って確定し、区分と根拠を自ら確定した判断として報告する。
範囲外の不足の区分の対象は、エンドユーザーの停止場面か誤った結果として観測した不足とする。停止場面を観測していない改善案（好み、将来の仮定）は`agent-toolkit:review-standards`の`references/reviewee.md`「レビュー指摘の位置付け」の扱いのままとする。

ユーザーが確定した判断の変更は、`agent-toolkit/rules/01-agent.md`「協調と自律」が定めるユーザーが確定した判断（別の作業でも使う方針や将来の案を制約する要件）について、次のいずれかを行う操作を指す。

- その判断が達成しようとした目的を変える操作
- その判断が退けた案（当時の選択肢のうち選ばれなかった案と、記録が除外した対象）を採用する操作
- ユーザーが選んだ結果を取り消す操作

記録の文言が名指ししない対象や処理へ同じ判断を当てはめる操作は、その目的に資し、退けた案を採用せず、そのセッションでユーザーが求めた結果と矛盾しない場合に判断の適用として扱う。判断の適用はエージェントが確定し、自ら確定した判断として報告する。導入時の処理に限って決めた対処を、同じ目的と同じ失敗を持つ更新の処理へ当てはめる場合がこれに当たる。
認可を要するのは目的側の判断の変更に限る。ユーザーが確定した目的・要件・対象範囲や期待結果を変える場合は目的側の判断とする。それらを保って実現の仕方（hookの範囲、書式、工程の手順、ツールや担当の段位の選択など）を選ぶ場合は、表示や結果に差があっても手段側の方針とし、`references/approval-scope.md`の逸脱の事後承認に従う（区分の詳細は`references/approval-scope.md`）。目的側か手段側かを決めかねる場合は、`SKILL.md`「確認要否の判定」の2に従い、判断の目的に照らして確定する。判断の所在は、`agent-toolkit:wi-standards`の`references/drafting-completion.md`「方針と判断の記録との比較」が導入目的と由来の調査先として挙げる、ユーザーが確定した方針と判断の記録で調べる。
観測した問題を解消する目的でその変更を問う場合は、確認を組む前に、`SKILL.md`の読込表に従って読む`references/choice-construction.md`「候補の構成」の観測した問題への対処を選ばせる確認の段落を適用する。
これらの区分に当たる操作でも、依頼がその操作自体を求める場合は依頼が承認源となり、`references/approval-scope.md`冒頭のユーザーが指定した操作を合意済みとする規定に従う。
ここでいう第三者は、`agent-toolkit/rules/01-agent.md`「役割分担」が定めるユーザーと、その指示で動くエージェントの外側にある主体とする。
ここでいう第三者の範囲から、開発環境、検証用の環境その他のユーザーの側が使う資源を使う主体を除外する。

## 原文からの具体化を要する軸

同じ対象の表示や同じ目的の操作が複数ある相談では、操作から結果までをたどり、表示状態・作用・仕様上の使い分けを比べる。
選択肢は内部フラグ名だけで示さず、エンドユーザーが行う操作と観測する状態の差で説明する。

ユーザー要求の対象、適用範囲、外部可視の結果ならびに除外内容を原文から新たに具体化する場合と、原文が示す対象集合を縮小、置換、細分化する場合は、具体化を要する軸を先に列挙する。ユーザー要求に基づいて既存の条文を置き換えまたは改訂するとき、その条文が原文で名指しされない対象も扱い、新しい扱いをその対象へ及ぼす場合も同じ具体化として扱う。
対象、範囲、実行時点、区分のうち、変更により実行時の結果や要求を実施する範囲が変わる箇所から軸を求める。
依頼文が操作の対象を示す主語と目的語のいずれかを省略し、その省略により操作対象の種類（機能そのものと、その機能の特定の利用）が複数に解釈できる場合は、種類の相違も軸へ加える。
原文が範囲語や開放列挙で定めた対象集合を変える軸は、拡大と縮小のいずれも同じユーザー確認で扱う。対象を狭める判断は要求の一部を実施しない結果を生む。
「全部」「AやBなど」「〜とか」「例えば〜」など、範囲語や開放列挙が示す集合を狭める場合は、事前の明示承認を得てから実施する。

その判定に用いる集合を定める前に`references/user-utterance.md`を適用する。要求の理由が当てはまる対象を候補へ含め、明示された範囲、例示性、理由と結論の関係から所属を判定する。集合に属する対象を除く判断は前掲の明示承認へ接続する。名指し語の一覧だけで集合を閉じず、原文の範囲と論理関係を用いる。
範囲語が定める集合をそのまま適用する判断は、原文が定めている軸として自ら確定する。
集合への所属は、その語が指す概念（サブエージェントであるかなど）で判定し、現行の実装や仕組みがその対象を扱えるか（親を結べるかなど）を判定条件に使わない。所属するが現行の仕組みで扱えない対象は集合に残し、新しい仕組みへの要件とする。新しい仕組みでも扱えないと観測で確かめた対象を範囲から外す判断は、技術的不成立の形をとっていても集合の縮小として同じユーザー確認で扱い、確認本文に成立しない根拠となる観測を示す。仕組みの処理能力で所属を選び直すと、集合の縮小が技術判断として記録され、確認を経ずに要求の一部が落ちる。程度や裁量を含む表現の軸は`agent-toolkit:wi-standards`「由来と承認」に従う。
その対応の反映先が、全てのエンドユーザーへ配布する規範と特定の実行環境だけに適用する記録のいずれになるかも軸として列挙する。
反映先を軸に含めるのは、実行時の外部可視の結果が同じでも対応が適用される環境の範囲が変わるためである。
列挙した軸ごとに、原文が定めているか、`SKILL.md`「確認要否の判定」で自ら確定できるか、ユーザー確認するかを判定する。
回答済みの軸の値は、その質問と回答が対象とした要求へだけ適用する。同じセッションで別の要求を受領した時点で、先行回答をその要求の省略時の値とせず、軸を列挙し直して判定する。質問と回答から適用先を確定できない軸はユーザー確認する。先行要求の値を流用すると、新しい要求の対象や範囲が回答を経ずに変わる。
ユーザー確認すると判定した軸のうち、対象集合の範囲の広さを扱う軸は、調査を完了して推奨案と観測根拠を示し、成果物を確定する前に確認する。
操作対象の種類を扱う軸は、調査の前提を固定する前に送る。
前提の固定には、委譲先の委譲プロンプトへ書く対象の想定、確認の選択肢と推奨案の構成、計画の対象集合を含める。
判定した結果は、軸ごとに、成果物の種別に対応する記録先へ残す。
ユーザーが対象、範囲および結果を明示した提案を同じ内容で採用する場合、コードベースから確定できる事実、観測による内部値の補正、ファイル配置、関数分割およびテスト手段は自ら確定する。

## 確認を要する事項

`SKILL.md`「確認要否の判定」でユーザー確認する事項の代表例を次に挙げる。
確認本文の対象をユーザー要件・運用方針の未確定部分に限定する。実装過程の技術選択と調査経緯は対象から外す。
ユーザー確認の手段は`SKILL.md`「手段の選択」が定める。

- 指示の文言が複数の解釈を許し、原文、そのセッションの先行発話、依頼の目的と照らしても解釈を1つに定められず、解釈によりエンドユーザーが観測する結果が変わる
- 受け取った発話が単体では実施すべき工程を定めず、直前の要求との補い方が複数成立して実施する工程が変わる（補った関係を確定してから、その解釈に基づく成果物の変更と委譲へ着手する）
- 破壊的操作を含む委譲先が、意図せず外部公開状態を除去した
- WIの完成条件の範囲外で見つけたエンドユーザー向けの不足のうち、是正が新しい挙動の追加（「認可を要する操作」の範囲外の不足の区分）に当たるものを、今回の作業へ含めるか別の作業へ回すか

範囲外の不足を新しい挙動の追加と区分した時点で、公開工程中でも確認を発行し、回答に依存しない工程を続ける。
本文には観測した停止場面、今回の変更で直面しやすくなるか、含める場合と別に回す場合のリリース内容の差を書く。
「含める」の回答を得た場合は、実行中のスキル（`agent-toolkit:process-wi`など）が定めるユーザーの追加指示と即時対応の手順で同じ実行の処理対象へ加え、元の変更と一緒に公開・リリースする。公開工程の開始後に得た回答は、同じスキルが公開後に届いたユーザー指示へ定める扱いに従う。
回答を得られない場合は`references/main-behavior.md`「未確定判断の保留と暫定判断」に従い、新しい挙動を実装しない。新しい挙動の作業はWI投入担当へ委譲してAWIとして投入し、`atk wi hold`で保留したうえで、そのAWIを実施するかを問う事前承認型のUWIを記録する。
元の認可済みの変更は新しい挙動を含めず、通常どおり公開とリリース判定へ進める。
