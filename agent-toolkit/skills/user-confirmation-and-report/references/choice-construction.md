# 確認の選択肢を組む細則

`user-confirmation-and-report-questions.md`「確認の選択肢を組む手順」の根拠・構成・影響・回答単位・用語の確認を定める。
ユーザーが確認文だけで判断でき、選択肢の再提示や事実確認の往復を防ぐ。

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `../../write-plan/references/plan-file-standards-requirements.md` |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `../../wi-standards/references/drafting-completion-policies.md` |

## 根拠の確定

1. 確認の前提を裏付ける。

   - 前提・影響・副作用は、推測・未確認の注記を付ける場合もコード・規範・実行結果で確認する。
     既存の機能や経路を使う案では、その存在に加え、案が使う起動形、終了時の動き、状態、権限などの条件でも成立することを実装か実行結果で確かめる。
     他者の報告や文書も一次資料で確かめ、裏付けの無い内容は確認文から外す。
     共通の仕組みを変更する時は、手元の実行例だけで影響を判断せず、`../../write-plan/references/plan-file-standards-requirements.md`「要件・外部仕様」に従って、従来の動作を前提とする指定を網羅して確認する。
   - 実行環境が会話を自動で圧縮して作業を継続するため、作業を完遂できるかやコンテキスト容量の不足は前提から外す。
     所要時間やコストの許容範囲の扱いは、`user-confirmation-and-report-decisions.md`「確認要否の判定」の項目4に従う。
   - 既存の値や設定、規範の規定を変更する案を提示する時は、`../../wi-standards/references/drafting-completion-policies.md`「方針と判断の記録との比較」に従い、その値を明記している記録や規範と照らし合わせる。
     その上で、従来の判断を維持する案と、変更の承認を必要とする案を明確に区別する。
     現状を維持する案を選択肢に含めるか、あるいは確認自体するかどうかは、同節の既存の保護の必要性の比較と`user-confirmation-and-report-decisions.md`「確認要否の判定」に基づいて決定する。
   - 本文や選択肢で言及するコマンド、ツール、設定項目は、現在のセッションで公開仕様（ヘルプ出力、入力スキーマ、公式仕様など）を取得してから選択肢を作成する。
     仕様によって一意に定まる事項はエージェント自身で確定させる。
     操作や設定、回避策の各案は、入力値の補正やデフォルト値、権限チェックなどを経た後に実際に適用される状態を基準として効果を評価する。
   - 指定した集合の外側に対象が存在しないことを示す主張や、利用箇所を列挙する時は、母集団の総数、除外した分類ごとの件数、およびその判定条件を併記する。
     対象の包含条件をユーザーに選択させる場合は、各案によって扱いが異なる実データの行を比較表として提示する。
     状態は発生元と参照元を出力行と対応付けて確定させ、空欄や欠損から推測しない。
   - 複数の仕組みや手段、案の違いやメリットについて「違いは〜のみ」「残る利点は〜だけ」のように限定して説明する場合も、提示した差以外に違いが存在しないと主張しているものとする。
     実際の仕様を、対象範囲、入力、実行主体、使用リソース、出力、終了状態などの観点（これらは例示であり、比較に必要な仕様上の差異も確認する）から比較し、その根拠に基づいて説明する。
   - 同じ実装構造を共有する対象の一部を適用範囲から外す場合は、その構造がもたらす外部から観測可能な結果に基づいて判断する。
     単に観測済みの症状が再現しないことだけを除外の理由にすることは避ける。
   - エンドユーザーが目にする表示、通知、帳票などの文面案を提示する時は、その文面が示す内容と表示判定の実装条件を比較する。
     両者が一致しない場合は、文面と判定条件のどちらを修正するかも同じ回答単位に含めて確認する。

## 候補の構成

1. ユーザーの判断に必要な案をそろえる。

   質問本文・選択肢・`共通前提:`には、原文や回答に由来する内容と、エージェントの案・推論を区別して示す。
   原文で述べられた目的、背景理由、提案された手段を区別し、背景理由から補った目的を合意済みとみなさない。
   原文と異なる対象・契機・結果・適用期間を提案する時は、その差と根拠を明示し、全選択肢で合意済みの前提として扱わない。
   整理案を次の質問へ転記する際も、原文と現行の回答へ照らし合わせる。

   候補を組む前に、ユーザーが決める方針・基準・考え方と、その結果からエージェントが決める技術的詳細を分ける。
   問いと選択肢の主題はユーザーだけが判断できる方針や基準に置き、恒久的な成果物へ残せる粒度にする。
   実装内部の値や手段を選ばせる問いでは、ユーザーが判断材料を持たないため、同じ確認が繰り返される。
   実装手段そのものは、`user-confirmation-and-report-decisions.md`「確認要否の判定」でユーザー固有の判断が必要と判定した場合に限り問い、不足している判断材料を明示する。
   確認文には、対象の識別子、回答ごとに変わる外部から観測可能な結果、および採用時に実行する操作の要約を記載する。
   判断に使う経緯、調査結果、案の詳しい比較は、ユーザー向け本文の送達ツールを使えるホストでは質問より先に送り、質問には問いと最小限の前提を残す。
   Claude Codeでの扱いは`agent-toolkit/share/rules/rules-main.claude-code.md`「ユーザー確認（`AskUserQuestion`）」が定める。
   送達ツールが無いホストとCodexでは、判断材料も質問本文へ書く。

   主題はユーザーが決める結果・許容する影響とする。
   実装手段への本人の指定が必要なら、理由と観測結果を「ユーザー固有の判断である根拠」へ対応付ける。

   各質問の本文には`共通前提:`で始まる1行を置き、すべての選択肢が共有する前提、その前提を外した案を含めたか（または含めない根拠）、選択肢の評価を左右する技術的事実（対象を作成する主体、その時点でそろう情報や状態など）を記載する。
   共有する前提も技術的事実も無ければ、`共通前提: なし`と記載することを推奨する。
   前提は次のような観点から確認する。

   - 判断のタイミング、実施の主体、対象の範囲、工程の順序
   - 工程の完了と結果の届け方
   - すべての案で共通となるエンドユーザーの観測結果（既存の表示を残して追加するか、置き換えるかなど）
   - 論点に関わる既存の機能、手段、分岐、設定の存続、および論点となるケースを別扱いとしている既存の規則
   - ユーザーの発言から引用した語句（範囲を示す語句や例示を含む）

   推奨案と前提を共有する案だけを並べると、ユーザーが欠けた案を自ら挙げ直す負担が生じる。
   すべての選択肢が共通して前提とする事項は、その由来を問わず、その前提で達成しようとした上位目的の観点から、前提を外した案を検討する。
   掲載する対案はユーザーの判断が要るものに限り、該当する案を1件以上掲載するか、掲載しない根拠を記載する。
   技術とQCDで決まる判断は自分で確定して報告する。
   検討する対案には、元の要求に対して不要な分岐、条件、確認や対象そのものを撤去して目的を達成する案、既存の名称や語句を用いる案、既存側を変更しない案、先行するユーザーの判断を反映する案を含める。
   手元の調査で目的の前提がすでに満たされている場合は、後続の工程を前倒しする案も同じ基準で扱う。
   実装量、工数、変更範囲、所要時間は、各案の影響として記載する。

   <例>
   「小さいリポジトリで試してから全体へ広げたい」と述べた後、試行の結果が出た時点で質問する: 同じ回で全体へ展開する案も並べる。
   新しい方針を、既存の規則が別扱いにしている場合へ広げるかを問う: 規則を残す案と規則の内側で当てはめる案に加え、その規則を外す案を載せる。
   依頼が範囲語で対象を定めながら、例示や問いで特定の対象を知りたい目的を示している: 範囲語どおりの案に加え、例示と問いが示す対象へ限定する案を載せる。
   </例>

   - 名称、識別子、用語の候補は、`agent-basics:writing-standards/references/defined-names.md`「命名の方針」に従って作成し、既存の成果物で同じ対象を指している語句を採用しない場合はその理由を記載する。
     該当セッションでユーザーが挙げた例示や、同じ適用区分で先行するユーザーの判断も候補へ反映し、反映しない場合はその理由を記載する。
     ユーザーが確定した再利用可能な判断は、成果物名に加えて、読み手、公開範囲、主題などの適用区分と対応付ける。
     画面に表示する名称の記法を既存ラベルに合わせて統一する案は、設計意図の記録が見当たらなければ現状維持を推奨案とし、統一する案には記録が無いことを明記して選択肢に示す。
   - 既存の成果物と新しい成果物の関係を変更する確認では、変更する側と参照・利用の向きを比較の観点に含め、既存側を変更しない案も提示する。
   - 工程の一部を後で実施する案（後続のセッション、`atk wi process-loop`、別の担当へ引き継ぐ案や、回答や外部状態を待って保留する案を含む）では、その工程を完了する主体とタイミング、ユーザーへ結果が届く報告先、粒度およびタイミングを同じ案の中に記載する。
     また、完了を委ねる既存の仕組みがその実行形態でも正しく機能するかを確認する。

   選択肢は候補を一覧形式で提示し、技術的に最適な案を次の手順に従って第1選択肢（推奨案）に配置する。
   判断の根拠は`agent-toolkit/share/rules/common/01-agent.md`「QCDと3段判定」に従い、選択の判断自体をユーザーへ丸投げしない。

   1. 変更の利用主体（変更後の成果物を使う人とその役割、または人以外の利用主体）と、その利用主体にとって理想的な動作を整理して確認文に示す。
      確認に使用する情報ごとに、利用主体と、その情報を用いる判断や操作の目的を対応付ける。
      技術判断にのみ用いる情報はエージェント側で処理し、ユーザーが選択する上で必要な結果、コスト、影響を確認文に残す。
      判断にも操作にも使用しない内部の詳細は記載しない。
      許容できる不便の範囲は利用主体の役割によって異なるため、これを明示してユーザーに必要な判断材料を提供する。
   2. 確定した達成目標と受入れ条件を満たす案の中から、手順1の結論を反映した案を選ぶ。
      エージェントが実施できる作業は、`../../../share/rules/common/01-agent.md`「確認を要する事項」に従い、エージェントが行う案を推奨し、選択肢の初期選択にする。
      候補が複数ある場合は、追加または維持する仕組み（上限、分岐、集約、専用の状態、書き込み主体や不変条件の変更、エンドユーザー向けの機能・操作・設定の追加、維持する既存の保護とそれを補う機構など）が最も少ない案を選択する。
   3. 選択した案よりも仕組みが少ない各案について、満たせない受入れ条件を説明文に記載できるか確認する。
      記載できない案があれば、その案に切り替える。
   4. 仕組みを追加する案や、既存の保護を維持・補完する機構を加える案を推奨するのは、その仕組みがないと要件を満たせないことを実際の観測事象（保護対象となる事象の観測頻度や最大の影響度を含む）で示せる場合に限る。
      その対応関係を説明文に記載する。
      対策を追加する案を選択肢に含める場合は、防止対象とする事象の発生条件、確認できた発生頻度、想定される最大影響を確認文に明記し、これらを具体的に特定できなければ対策を追加しない案を推奨案とする。
      ドキュメントと実装が一致しない場合、合意済みの目的へ既存の手段で到達できるのであれば、ドキュメント側の修正を推奨する。
      機能を追加する案を推奨する時は、ドキュメントの修正だけでは解決しない停止事例を説明文に記載する。
      過去にドキュメントで案内されていたことだけを機能追加の根拠とはしない。
   5. 仕組みを追加しない案の影響も、その影響に至る処理プロセスを確認して記載する。
      受入れ条件を満たさない案を提示する時は、満たせない条件を説明文に明記する。

   実装方式やアルゴリズム、データ構造などの手段の比較を選択肢として提示する前に、その手段が満たすべき達成目標と受入れ条件を確定させる。
   確定できない場合は、達成目標や受入れ条件そのものを確認の対象とする。

   観測された問題への対処をユーザーに選択させる確認（方針や初期設定の変更承認、適用範囲の選択など、別の形で対処を問う確認を含む）では、選択肢を作成する前に`agent-basics:bugfix`を起動し、「初動と拡張原因分析の判定」に従って直接的な原因を実際の観測から確定する。
   委譲先から返された直接的原因は、実際の観測結果と突き合わせ、`agent-basics:bugfix/references/root-cause-analysis-evidence.md`「直接的原因と事象時点の確定」の推測の条件に該当しないことを確認した上で、確定済みとする。
   対策の選定は同スキルの「対策の選定」に従い、比較検討した原因側・構造側の成立案を選択肢に含めるか、成立しない根拠を観測結果に基づいて示す。
   選んだ対策の組は、`agent-basics:bugfix/references/root-cause-actions-selection.md`「対策の選定」の一覧（要因ごとの処置、階層、重大度との比例性、適用範囲）で点検してから確認文に使い、その一覧を確認文の根拠に含める。
   原因を特定できない場合は、原因特定に必要な調査とその実施条件を確認の主題とする。

## 影響と回答単位

1. 影響と合意の単位を確定する。

   - 第1選択肢（推奨案）は、技術的な観点と、ユーザーが気付きにくい・取り消しにくい副次的な影響（機密情報の残留、可逆性、第三者からの観測、監査や通知、管理外の複製やリンクの不整合など）を比較考量して決定する。
     案ごとの差異や他案のメリットも推奨理由に記載する。
   - 確認文には、外部から観測可能な差異（入出力、応答時間、画面表示、情報量、通知頻度など）と、値・文言・動作の変更に伴って修正が必要な成果物（設計書、運用手順書、ヘルプ、テストコード、公開ドキュメントなど）を記載する。
     修正対象が存在しない案では、対象が0件であることを明示する（努力目標。追随の検討を済ませたことを示す）。
   - 同じ論点を繰り返し問わずに確定できるよう、必要事項を1つの回答単位にまとめる。
     回答の結果として値の登録、保存、作成、変更を伴う質問は、主題が主体や手順、タイミングであっても保持先に関する論点を含める。
     保持先に登録済みの項目を実物で列挙し、流用と新規作成の件数や形式を記載する。
     値の指定をユーザーに委ねる論点では、候補となる値を1件以上提示する。
   - 既存のフラグ、カラム、設定項目、状態の値を変更する論点では、その値を参照している箇所と、各箇所の意味の整合性が保たれることを確認文と計画書に記載する。
   - いずれの選択肢を選んでも残る外部から観測可能な結果は、今回の作業で許容するか、別の要求単位として扱うかを同じ確認文の中で明示する。
   - ユーザー固有の判断が必要な事項が複数ある場合、一方を除外しても他方の技術的な成立性に影響しなければ、別の質問に分割して個別の回答から合意を判定する（構造化質問ツールでは同一の呼び出しに並べてよい）。
     UWIに記録する確認では質問ごとに個別のUWIを作成し、書式は`agent-toolkit:wi-standards`の`references/uwi-format.md`に従う。
     提案全体に対する大まかな賛同は、各項目の個別合意の根拠としない。
     相互の回答が依存し合う事項は、同一の確認単位にまとめる。

## 本文の語

1. 発行前に用語を点検する。

   内部ツール名や実装候補名は、回答の影響を理解するために必要な場合だけ補足する。
   質問の主題を内部名の選択へ置き換えず、`user-confirmation-and-report-decisions.md`「確認要否の判定」の確認提示項目で、不足する本人固有の値を説明する。

   発行前に本文・選択肢の名詞を点検する。
   ユーザー発言の語、一般に意味が一意な語、本文内で説明済みの語に該当しなければ、説明を付けるか平易な語へ直す。
   規範で定義されている工程、レビュー、検証、判定、担当の名称は変更せずにそのまま使用し、指し示す対象を同じ本文内で説明する。
   対象、機能、検証手段の有無は、それぞれ独立した事実として書き分ける。
   表現の基準は`${CLAUDE_PLUGIN_ROOT}/share/rules/rules-main.md`「ユーザー向け発話ルール」に従う。
