# 確認の選択肢を組む細則

本書は`agent-toolkit:user-confirmation-and-report`「確認の選択肢を組む手順」の細則として、確認本文と選択肢の根拠、構成、影響と回答単位、本文の語の確かめ方を定める。目的はユーザーが本文だけで判断でき、欠けた案の挙げ直しや事実の問い返しが起きない確認にすることである。

## 根拠の確定

- 確認の前提・影響・副作用は、推測や未確認の注記を付ける場合も、現物の実装・規範・実行結果で確かめる。別のエージェントの報告や既存文書の主張も一次資料の該当箇所へ対応付け、裏付けられない主張は本文から外す。共通機構の変更は手元の実行例だけで影響を判定せず、`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」に従って旧動作を前提とする指定を列挙して確かめる
- 完遂の可否と容量の不足は前提から外す（実行環境が会話を自動で圧縮して継続するため）。所要時間とコストの許容範囲の扱いは`SKILL.md`「確認要否の判定」の3に従う
- 既存の値、設定、規範の定めを変える案は、`agent-toolkit:wi-standards`の`references/drafting-completion.md`「方針と判断の記録との比較」に従ってその値を名指しする記録と規範に照らし、判断を維持する案と変更の認可を要する案を区別する。現況を維持する案を選択肢へ含めるか、確認自体を発行するかは、同節の既存の保護の必要性の比較と`SKILL.md`「確認要否の判定」で決める
- 本文と選択肢が名指しするコマンド、ツール、設定項目は、そのセッションで公開契約（ヘルプ出力、入力スキーマ、公式仕様）を取得してから選択肢を組み、契約で一意に定まる対象は自ら確定する。操作、設定または回避策の案は、入力補正、省略時の値、権限判定を経た後に到達する状態で効力を判定する
- 集合の外側に該当が無いことを含意する主張と利用先の列挙には、母集団の総数、除外した分類ごとの件数と判定条件を併記する。対象の包含条件を選ばせる場合は、各案で扱いが分かれる実データの行を比較表にする。状態は発生元と参照元を出力行へ対応付けて確定し、空欄や欠損から推定しない
- 複数の機構・手段・案の差や利点を「違いは〜だけ」「残る利点は〜だけ」と限定する説明も、挙げた差以外の差の不在を含意する主張として扱う。両者の現物の契約を対象範囲・入力・実施主体・使用資源・出力・終端などの軸（例示であり、比較に必要な契約上の差も確かめる）で比べた根拠から説明する
- 同じ実装構造を共有する対象の一部を範囲から除外する場合は、その構造が生む外部可視の結果で判定し、観測済みの症状が再現しないことだけの根拠は除外理由から外す
- エンドユーザーが観測する表示、通知または帳票の文面案は、文面が主張する事象を表示実装の判定条件と比べ、一致しない場合は文面と判定条件のどちらを変えるかを同じ回答単位へ含める

## 候補の構成

候補を組む前に、ユーザーが決める方針・基準・考え方と、その結果からエージェントが決める技術的詳細を分ける。問いと選択肢の主題はユーザーだけが判断できる方針・基準に置き、恒久的な成果物へ残せる粒度にする。実装内部の値と手段を選ばせる問いでは、ユーザーが判断材料を持たないため、同じ確認が繰り返される。実装手段そのものは`SKILL.md`「確認要否の判定」でユーザーだけの値を要すると判定した場合だけ問い、その不足値を明示する。確認本文には対象の識別子、回答ごとに変わる外部可視の結果、採用時に実行する操作の要約を示す。

各質問の本文へ`共通前提:`で始まる1行を置き、全ての選択肢が共有する前提と、その前提を外した案を含めたか含めない根拠、選択肢の評価を左右する技術的事実（対象を作成する主体、その時点でそろう情報や状態など）を書く。共有する前提も技術的事実も無い場合は`共通前提: なし`と書くことを推奨する。前提は次のような軸で確かめる。

- 判断の時機、実施の主体、対象の範囲、工程の順序
- 工程の終端と結果の届け方
- 全ての案で同じになるエンドユーザーの観測結果（既存の表示を残して追加するか置き換えるかなど）
- 論点に関わる既存の機能・手段・分岐・設定の存続と、論点の場合を別扱いにしている既存の規則
- ユーザーの発言から写した語（範囲語や例示を含む）

推奨案と前提を共有する案だけを並べると、ユーザーが欠けた案を自ら挙げ直す。全ての選択肢が共通して前提とする事項は、由来を問わず、その前提で達成しようとした上位の目的の水準で前提を外した案を1件以上載せるか、載せない根拠を書く。前提を外した案には、元の要求に不要な分岐・条件・確認や対象そのものを撤去して目的が成立する案、既存の名称や語を使う案、既存側を変更しない案、先行するユーザーの判断を反映する案を含める。手元の観測で目的の前提が既に満たされている場合は、後段の工程を前倒しする案を載せる。実装量、工数、変更範囲および所要時間は案の影響として書く。

<例>
「小さいリポジトリで試してから全体へ広げたい」と述べた後、試行の結果が出た時点で質問する: 同じ回で全体へ展開する案も並べる。
新しい方針を、既存の規則が別扱いにしている場合へ広げるかを問う: 規則を残す案と規則の内側で当てはめる案に加え、その規則を外す案を載せる。
依頼が範囲語で対象を定めながら、例示や問いで特定の対象を知りたい目的を示している: 範囲語どおりの案に加え、例示と問いが示す対象へ限定する案を載せる。
</例>

- 名称・識別子・用語の候補は`agent-basics:writing-standards/references/defined-names.md`「命名の方針」に従って作成し、既存成果物が同じ対象を呼んでいる語を載せない場合は理由を書く。そのセッションのユーザーの発言が挙げた例示と、同じ適用区分の先行するユーザーの判断も候補へ反映し、反映しない場合は理由を書く。ユーザーが確定した再利用可能な判断は、成果物名に加えて読み手、公開範囲または主題などの適用区分へ対応付ける
- 既存成果物と新しい成果物の関係を変える確認では、変更する側と参照・利用の向きを比較軸に含め、既存側を変更しない案を含める
- 工程の一部を後で実施する案（後続のセッション、`atk wi process-loop`、別の担当へ移す案や、回答・外部状態を待って保留する案を含む）では、その工程を終える主体と時機、結果がユーザーへ届く報告先、粒度と時機を同じ案へ書き、終端を任せる既存の仕組みがその実行形態でも働くかを確かめる

選択肢は候補を一覧で示し、技術的な最適案を次の手順で第1選択肢（推奨案）に置く。判断の根拠は`agent-toolkit/rules/01-agent.md`「QCDと3段判定」に従い、選択の判断そのものをユーザーへ委ねない。

1. 変更の消費主体（変更後の成果物を使う人とその役割、または人以外の消費主体）と、その消費主体にとっての理想的な動作を整理し、確認本文へ示す。確認に使う情報ごとにも、消費主体とその情報を使う判断・操作の用途を対応付ける。技術判断にだけ使う情報はエージェントが処理し、ユーザーの選択に必要な結果・費用・影響は本文へ残す。判断にも操作にも使わない内部詳細は載せない。許容できる不便の範囲は消費主体の役割で変わるため、示さないとユーザーが判断材料を持たない
2. 確定した達成目標と受入条件を満たす案から、手順1の結論を反映した案を選ぶ。複数ある場合は、追加または維持する仕組み（上限、分岐、集約、専用の状態、書込主体や不変条件の変更、エンドユーザー向けの機能・操作・設定の追加、維持する既存の保護とそれを補う機構など）が最も少ない案を選ぶ
3. 選んだ案より仕組みの少ない各案について満たさない受入条件を説明へ書けるかを確かめ、書けない案があればその案へ替える
4. 仕組みを加える案と、既存の保護を維持するか補う機構を加える案を推奨するのは、それが無いと満たせない要件を観測事象（保護する事象の観測した頻度と最大影響を含む）で示せる場合に限り、その対応を説明へ書く。文書と実装が一致しない場合は、既存の手段で合意した目的へ到達できるなら文書の是正を推奨する。機能を加える案を推奨する場合は、文書の修正だけでは解消しない停止場面を説明へ書く。文書が過去に案内していたことだけでは追加の理由にならない
5. 仕組みを加えない案の影響も、影響へ至る処理を確かめて書く。受入条件を満たさない案を載せる場合は、満たさない受入条件を説明へ書く

実装方式、アルゴリズム、データ構造など手段の比較を選択肢にする前に、その手段が満たすべき達成目標と受入条件を確定する。確定できない場合は、達成目標と受入条件そのものを確認対象とする。

観測した問題への対処を選ばせる確認（方針や初期設定の変更の認可、適用範囲の選択など、別の形で対処を問う確認を含む）では、選択肢を組む前に`agent-toolkit:bugfix`を起動し、「初動と拡張原因分析の判定」に従って直接的原因を観測で確定する。委譲先が返した直接的原因は、観測を現物と比べ、`agent-toolkit:bugfix`の`SKILL.md`「直接的原因と事象時点の確定」の推定の条件に当たらないことを確かめてから確定済みとして扱う。対策の選定は同スキル「対策の選定」に従い、比較した原因側・構造側の成立案を選択肢へ含めるか、成立しない根拠を観測結果で示す。原因を確かめられない場合は、原因の確定に必要な調査とその実施条件を確認の主題にする。

## 影響と回答単位

- 第1選択肢は、技術面と、ユーザーが気付きにくいか取り消しにくい副次的影響（機密情報の残存、可逆性、第三者の観測、監査・通知、管理外の複製やリンクの不一致など）を比べて決め、案ごとの差と他案の利点も推奨理由へ書く
- 確認本文へ、外部可視の差（入出力・応答時間・表示・情報量・通知頻度など）と、値・文言・挙動の変更に追随する成果物（設計書、運用手順、ヘルプ、テスト、公開資料など）を書く。追随対象が無い案では0件であることを明示する（努力目標。追随の検討を済ませたことを示す）
- 回答後に同じ論点の確認が残らないよう、論点の確定に必要な事項を回答単位へ含める。回答の結果として値の登録、保存、作成、変更を伴う問いは、主題が主体や手順、時機であっても保持先の論点を含み、保持先に登録済みの項目を実物で列挙して流用と新設の数と形を書く。値の指定をユーザーへ委ねる論点では候補値を1件以上示す
- 既存のフラグ、列、設定項目または状態の値を変える論点では、その値を読む箇所と各箇所での意味の両立を確認本文と計画へ書く
- いずれの選択肢でも残る外部可視の結果は、本件で許容するか別の要求単位とするかを同じ本文で示す
- 複数のユーザーだけが決められる事項は、一方を除いても他方の技術的成立性が変わらなければ別の質問に分け（構造化質問では同じ呼び出しへ並べてよい）、個別の回答で合意を判定する。UWIへ記録する確認では質問ごとに個別のUWIとし、書式は`agent-toolkit:wi-standards`の`references/uwi-format.md`に従う。提案全体への肯定は個別合意の判定材料にしない。互いの回答を必要とする事項は同じ確認単位に保つ

## 本文の語

発行前に、問い本文と選択肢の名詞がユーザーの発言に現れた語、一般に意味が一意な語、同じ本文で説明した語のいずれかであることを確かめる。該当しない語は説明するか置き換える。規範が定義した工程・レビュー・検証・判定・担当の名前は置き換えずに使い、指す対象を同じ本文で説明する。対象、機能および検証手段の有無は別の事実として書き分ける。基準は`${CLAUDE_PLUGIN_ROOT}/share/rules-main.md`「ユーザー向け発話ルール」とする。
