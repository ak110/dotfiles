# 権限拒否への対応

ツール呼び出しが権限設定またはauto mode classifierに拒否された場面の手順を定める。
auto modeのカスタムルールを追加・編集する手順は`agent-toolkit:writing-standards`の`references/auto-mode.md`が定める。

## 拒否の確認手順

拒否を観測したら、別の手段で迂回する前に有効な設定ファイルを`Read`して許可・拒否のルールを確認する。
対象は`/etc/claude-code/managed-settings.json`、`~/.claude/settings.json`、リポジトリ直下の`.claude/settings.json`および`.claude/settings.local.json`とする。
拒否本文が同じ結果の追求を禁じている場合は、設定ファイルの読み取りも同じ結果の追求とみなされて拒否され得るため、読み取りを省いて「偽陽性と判断できる拒否への対応」の確認へ進む。

拒否された操作を、有効な`autoMode.allow`の各規則について、対象操作、適用条件および信頼境界の包含関係で確認する。
対応するallow規則がある場合は、拒否本文の分類名または意味上の一致とは独立に偽陽性の可能性が高い条件として扱う。
分類名との意味上の一致を理由にallow規則との確認を省かない。`hard_deny`に属する操作は偽陽性フローの対象から外す。

権限評価はpermissionsルール（deny→ask→allowの順で最初の一致が確定）、作業ディレクトリ内編集等の自動承認、auto mode classifierの順に進む。
PreToolUseフックの`permissionDecision: "allow"`より前にpermissions評価が確定する。
このため、拒否ルールに該当する対象は、許可の追加ではなく拒否ルール自体の見直しで解消する。

permissions設定による確認ダイアログが対象の場合は本書の範囲の外とし、`agent-toolkit:writing-standards`の`references/claude-hooks.md`の「PermissionRequest」に従う。

アクセス制御、認証、公開範囲などのセキュリティ設定をマージする操作が拒否された場合は、変更候補の作成、現行の実効値と候補の読み取り比較、候補の適用のうち、拒否された操作を特定する。
1つの呼び出しが複数の操作を含んでいた場合は、拒否された操作を区別できないため、候補の作成が拒否されたものとして扱う。
候補の作成が拒否された場合は、別の手段で同じ候補を生成せず、比較を未実施と明示して、拒否された操作の承認をユーザー確認で求める。委譲先は確認事項を委譲元へ返す。承認を得るまでセキュリティ設定を変更しない。
候補があっても比較手段が成立しない場合は、実効値が保たれると言い切らず、未確認の範囲として示す。
ユーザー確認の本文には、比較できた値と、比較不能または未実施の範囲を分けて示す。

## 既知の誤拒否パターンと対応

次の表はdotfilesの管理設定`claude_settings_json_managed.json`を導入した環境で拒否に遭遇した場合に適用を検討する対応の対応付けとする。
観測日付と対象版数の記録を持たないため、適用の前に実行中の環境で拒否メッセージ本文と分類名を取得して該当を確認する。
分類名は`claude auto-mode defaults`の出力で確認できる区分を指す。

| 拒否される操作 | 分類名 | 対応 |
| --- | --- | --- |
| 自身が作成したHEADへの`git commit --amend` | Git Destructive | 許可ルール`Personal Repository Operations`が対象に含む。拒否が残る場合は後掲の偽陽性フローへ進む |
| MR/PRのマージ（`glab mr merge`・`gh pr merge`等） | Merge Without Review | 同じルールが対象に含む。remoteのホストによる限定は置いていない |
| リリースワークフローの起動 | `Production Deploy`が有力候補（拒否本文では未取得） | 同じルールが起動と結果確認を対象に含む |
| コンテナーまたはサービスの再作成 | Interfere With Workloads等 | 許可ルール`Reversible Change Approval`が、ユーザー本人の環境で変更前の構成を復元できる再作成を対象に含む |
| 承認条件の緩和・規範改訂・設定原本変更を含むコミット | Self Modification | 許可ルール`Agent Workspace Writes`が対象に含む |
| `atk agents-exit-session`による本人確認済みPIDの停止 | Interfere With Workloads | 許可ルール`Session And Delegation Control`が対象に含む |
| 委譲先の状態・終端・通知・結果の観測と受領（`atk agents wait`・`list`・`show`等） | Self Modification | 許可ルール`Session And Delegation Control`が、委譲内容にかかわらず受領済み化と結果・通知ファイルの削除を含めて対象にする |
| 自ら新規に作成したtmuxセッションでの対話CLIの起動し直し、キー入力の送信、画面の取得 | Tmux Self Drive | 許可ルール`Session And Delegation Control`が対象に含む。拒否が残る場合は後掲の偽陽性フローへ進む |
| UWIの回答でエージェントに実行を任せたシステムへの永続的な変更（sudoによるパッケージ導入など） | Unauthorized Persistence | UWIの回答は判定器が読む会話上のユーザー発言に現れない。実行前には確認せずに実行し、拒否された場合は設定ファイルの読み取りを省いて後掲の偽陽性フローの`AskUserQuestion`へ進む |
| ユーザーの指示を反映しない拒否後の再発行 | Auto-Mode Bypass等 | 許可ルール`Reconsidered Retry Approval`により、拒否本文とユーザーメッセージを比べて同一のコマンド・引数・ツールを1回だけ再発行する |
| 常時読み込む規範ファイル（`~/.claude/rules/`配下など）の編集 | Self Modification | 許可ルール`Agent Workspace Writes`が対象に含む |
| エージェントの誤操作で変わった状態（リポジトリ共通のGit設定など）を変更前の値へ戻す操作 | Modify Shared Resources等 | 許可ルール`Agent Mistake Recovery`が対象に含む。拒否が残る場合は後掲の偽陽性フローへ進む |
| 規範の配布元となるユーザー本人のリポジトリへの読み取り | Self Modification | 同じルールが値を変更しない参照を対象に含む |

- 許可ルールはremoteのホスト、由来および所有者による限定を置かず、操作の種別と除外条件で対象を決める
- 必須レビュー・必須チェックの迂回形態（`--admin`・`--force`等）と、リポジトリまたは組織のチェック設定を変える操作は許可の範囲の外にあり、CI Bypass領域のまま残る
- リリースワークフロー起動の拒否本文には分類名が現れないため、`Production Deploy`は初期設定の`soft_deny`との対応から見た有力候補に留まる

## 偽陽性と判断できる拒否への対応

auto mode classifierによる拒否は対象操作の実行自体を妨げる技術的ブロックであり、UWIの記録では解消できない。
このため、自律モードと協調モードのいずれでも本フローの`AskUserQuestion`を発行する。
判定器が拒否するかは実行する前に予測しにくいため、実行前には確認せず、拒否を観測した時点で本フローの確認へ進む。確認の往復はユーザーの手間になり、エージェントの再実行より避ける対象である。
拒否理由がtranscript内のユーザーによるその操作の明示指示または承認を反映していない場合は、`Reconsidered Retry Approval`を同一操作につき1回だけ適用する。
本フローはその1回の再発行の後も拒否が残る場合に適用する。`clears`が成立するのは、ユーザーが拒否を偽陽性と明示した回答に限る。進行への同意は対象外とする。

メイン・サブエージェントのいずれが発行した操作にも適用する。
委譲先は本フローの`AskUserQuestion`を自ら発行せず、拒否本文、分類名、拒否された操作と対象を、`agent-toolkit/share/rules-subagent.md`「確認事項の即時通知」の確認事項として委譲元へ返す。代替手段で工程を進めた場合も同じく返す。
委譲元は返却から受け取った拒否を自ら発行した操作の拒否と同じく本フローで扱う。「拒否の確認手順」の設定ファイルの読み取りとallow規則の確認も委譲元が行う。手順3で承認を得た後の実行も手順3に従い、委譲先が継続中か終端済みかを問わずメイン側が該当操作を直接実行する。
対象操作は`git commit`、`git commit --amend`、`Write`／`Edit`／`MultiEdit`によるファイル編集、GitHubリポジトリ設定変更等の外部サービスの設定変更コマンドを含む（代表例であり、同種の操作を含む開放集合とする）。
適用条件はユーザーまたは処理中のAWIでその操作が承認済みであると実体確認でき、拒否理由がその承認を反映していないと判断できる場合、または「拒否の確認手順」のallow規則の確認で対応する規則がある場合とする。両条件は独立に判定し、いずれかが成立した操作を偽陽性の可能性が高い対象として扱う。適用範囲は`hard_deny`領域の外とする。

1. 拒否理由をメッセージ本文で確認する。分類名を取得できる場合は分類名と本文を記録する。`claude auto-mode defaults`自体が拒否されて分類名を取得できない場合は、拒否メッセージ本文を根拠として手順2へ進む
2. 偽陽性の可能性が高い場合、`AskUserQuestion`で次の選択肢を提示する。拒否経緯の説明と選択肢の説明文は要点を中心に書き、判断材料の詳細はターン内のテキスト出力側へ置く（努力目標。auto mode classifierの拒否はほとんどが偽陽性であり、確認を簡潔に保つため）
   - 偽陽性として実行を承認する
   - 該当操作を撤回する
   - サブエージェント側でレビューを完了してから判断する
3. ユーザーの選択に応じて後続動作を実行する
   - 承認を選んだ場合はメイン側で該当操作を直接実行する
   - 撤回を選んだ場合は該当操作を破棄する。委譲により発行された操作では、該当操作を撤回したことと再開時の条件をサブエージェントへ返却する
   - レビュー完了待ちを選んだ場合はサブエージェント側のレビューを起動し、完了報告の受領後に手順1へ戻って拒否の再現の有無を確認する
4. `AskUserQuestion`が無応答のまま期限を迎えた場合は対象操作を保留する。回答を待つためのUWIを記録し、解除条件を満たすまで代替手段だけを継続する
5. 無応答の後にUWIへ回答が保存された場合も、classifierが観測する承認はtranscript内の確認で成立する。transcript内で同じ操作への再確認を発行し、ユーザーの回答を受領してから手順1へ戻って拒否の有無を再確認する
6. 手順3または手順5で偽陽性として承認を得て該当操作を実行した後に、同じ種別の拒否を以後のセッションで繰り返さないよう、許可規則の追記を検討する。検討と追記はメイン側が行い、委譲先から返った拒否でも委譲先は検討と追記をしない
   - 追記しない場合: 一度限りの操作で同じ種別の再発が見込めない場合、拒否された操作が`hard_deny`の領域に属する場合（カスタム規則で上書きするのは`soft_deny`までとする）、「拒否の確認手順」で既存の許可規則が対象を全て含んでいた場合。最後の場合に既存規則の文面を変えて範囲を広げるときは、次の提案と確認の対象とする
   - 抽象化と既存規則との比較: 追記する規則は拒否された個別の識別子（パス、リポジトリ名、ブランチ名、引数）ではなく操作の種別で書く。文面の書き方と既存規則との包含関係の確認は`agent-toolkit:writing-standards`の`references/auto-mode.md`「カスタムルール追加のワークフロー」と「カスタムルール記述の注意点」に従う
   - 直接追記する場合: 抽象化した規則の対象が、ユーザーが偽陽性と回答した操作と同じ操作種別と副作用の区分に収まり、一般化が個別の識別子を操作の種別へ置き換えるだけの場合。偽陽性の回答はその操作種別への承認として扱える（`references/approval-scope.md`の成立した承認を同じ範囲へ適用する規定）。追記後に、規則の本文、追記先、取り消し方法をユーザーへの報告に含める
   - 提案してユーザー確認する場合（事前承認）: 抽象化で対象が回答の対象外の操作種別、別の拒否区分、または破壊的操作・外部公開・セキュリティ設定の変更などの副作用の区分へ広がる場合と、既存規則の文面を変えて範囲を広げる場合。確認の手段は`agent-toolkit:user-confirmation-and-report`「手段の選択」に従い、規則の文面案、追記先、広がる範囲を本文へ書く
   - 追記先: `agent-toolkit:writing-standards`の`references/auto-mode.md`のワークフロー手順3の判定に従い、配布側の設定ファイルがある場合はそのsource、無い場合は`~/.claude/settings.json`とする。dotfilesの管理設定を導入した環境では、sourceはdotfilesリポジトリの`share/claude_settings_json_managed.json`である。sourceが現在のセッションの作業リポジトリにある場合は、その変更としてsourceを編集し、作業リポジトリの公開手順に含める。sourceが別のリポジトリにある場合は、その作業ツリーを直接編集せず、規則の文面と追記先を書いたAWIをsourceのリポジトリへ投入する（`agent-toolkit:wi-standards`に従う）。直接追記と判定した場合もこの投入を追記の実施として扱う
   - 反映: sourceを編集した場合のユーザー環境への反映は配布側の通常の反映手順に委ね、セッション内で反映する工程を設けない。反映されるまで規則が有効にならないことをユーザーへの報告に含める
