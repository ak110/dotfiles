# 承認範囲の判定

## 承認源と適用範囲

`SKILL.md`「認可を要する操作」への該当は、操作が残す副作用で判定し、操作の目的はその判定対象から外す。既存の環境、成果物または依存関係を置換、再作成または削除する操作は、調査、原因特定または動作確認のための実行でも破壊的操作として承認対象とする。
`agent-toolkit/rules/02-agent-operations.md`「プロセス終了の安全規定」の条件で作成元の作業単位が回収済みと確定したエージェント由来の残存資源の停止と、その資源が再作成した空のパスの削除は、作業単位の回収の完了に当たるため承認対象の破壊的操作から外す。

ユーザーが提案として指定した操作は、その提案の範囲では合意済みとしてそのまま実施する。
承認源はユーザーの指示、規範、手順ならびに人間由来のWIとする。人間由来のWIから承認が成立する条件は`agent-toolkit:wi-standards`が定め、他の承認源では、その指示、規範または手順が定める範囲を承認の範囲とする。計画が記録したユーザー確認の回答も承認源とする。
成立した承認は、承認源を問わず、操作、対象、影響範囲および成立条件が同じ範囲へそのまま適用する。適用範囲を限定して受け取った指示は、その限定が成立している間の、同じ対象への操作にだけ適用する。

`SKILL.md`「認可を要する操作」が定めるCI関連の外部サービス設定の包括認可には、外部サービスの状態変更、第三者への影響、既存設定の置換・無効化、CI用secretsの作成・変更を含める。破壊的操作では安全な対象解決と、影響範囲・復元方法の実行前の説明を維持し、操作結果はユーザーへの報告とする。CIと独立した副作用、目的・要件の変更ならびに実行環境の権限拒否には従来の確認基準を適用する。

## 事前承認と事後承認

成立した承認が無い承認対象（「認可を要する操作」と、`SKILL.md`「確認要否の判定」で確認を要すると判定した変更）は、事前承認と事後承認へ分ける。

- 事後承認: 可逆であり、第三者への影響、外部サービスの状態変更および復元に追加の外部操作を要する副作用のいずれも伴わない変更。最善と判断する対応を実施してからユーザー確認し、回答を待たずに元の作業を続ける。確認本文へ実施内容、根拠と影響を書き、対話の確認では復元方法も書く。UWIでは`agent-toolkit:wi-standards`の`references/uwi-format.md`の情報の選び方に従う
- 事前承認: 前項の副作用のいずれかを伴う操作。合意を得てから着手する
- 成果の適否をユーザーだけが観測でき、エージェントがいずれの手段でも観測できない変更（画面表示の見え方、操作の感触など）は、事前承認の副作用を伴わない限り事後承認とし、元の要求を終端してから適否を問う

起動中のスキル・適用中の規範・ユーザー指示・計画が記録した元の要求または確認回答が工程・対象集合・副作用を定める場合、その範囲の実施はユーザーへの報告へ含める。その内側で、規範から一意に導けない判断、ユーザーの選好に依存する代替、定められた範囲を変える操作を追加した場合は、その追加部分だけを`SKILL.md`「確認要否の判定」へ送る。

ユーザーが確定した目的・要件・ユーザーが観測する結果に関する判断の変更（`SKILL.md`「認可を要する操作」）は、可逆性、外部影響の有無、観測可能性によらず事前承認とし、この規定は本書の事後承認の各条件より優先する。事後承認ではユーザーが知らないまま目的側の判断が変わるためである。判断の記録自身が変更時の承認方式を定める場合は、その定めに従う。

破壊的操作では、実行内容・影響範囲・復元方法を事前に説明する。ユーザーが提案した破壊的操作にも同じ説明を適用する。パターン、ワイルドカード、状態指定などで対象を一括選択する破壊的コマンドは、同じ指定で実際に対象の一覧と副作用を取得してから影響範囲を示し、依頼の範囲外の対象を除く。ユーザーへ実行を求めるコマンドを案内する場合も同じとする。集合指定の評価結果は起草時の想定より広がり得る。

## 逸脱

規範からの逸脱と、ユーザーが確定した手段に関する方針（`SKILL.md`「認可を要する操作」の判別基準で手段側と判定したもの）からの逸脱は、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」の条件を満たす場合に実施する。

- 逸脱1件は外れた規範条文または手段の方針の記録と、外れた場面の組とする
- 規範からの逸脱は承認の対象から外し、逸脱1件ごとに外れた規範の所在、場面、両案のQCDを比べた観測根拠を作業完了報告の`### 自ら確定した判断`へ1行で書き、自律モードでは報告用UWIの同じH3へも書く。ユーザーは報告から個々の逸脱を見直し、是正を返せる
- 手段の方針からの逸脱も先に`SKILL.md`「確認要否の判定」を適用し、目的・要件・認可と要求された結果を保って技術とQCDで選べる場合は自ら確定して規範逸脱と同じ項目を報告する。手段の差だけでは確認を発行しない
- 調査と既存認可の適用後もユーザーだけの選好・認可・適否が残る逸脱は、必要な判断ごとに確認する。確認本文には外れた方針の所在、場面、両案のQCDの観測根拠と実施内容を書き、対話の確認では復元方法も書く
- 事前承認の副作用（第三者への影響、外部サービスの状態変更、復元に追加の外部操作を要する副作用、破壊的操作）を伴う逸脱は事前承認のまま扱う
- ユーザーの目的・要件と硬い制約が両立しない場合は、事前承認の対象とする
- 規範どうしが両立しない場合と手順の文言が状況を想定していない場合に、各規範の目的から次の工程を一意に導けるときは、その選択を事後承認の対象にせず`references/procedure-conflict.md`の判定順3と報告に従う

## 新しい挙動と準備の提示

依頼に含まれない新しい挙動の追加（`SKILL.md`「認可を要する操作」の範囲外の不足の区分）は、可逆で外部影響が無い場合も事前承認とし、合意まではリリースの対象へ含めない。この規定も事後承認の各条件より優先する。事後承認で実施すると、ユーザーが把握しない機能が回答より先に公開されるためである。
ユーザーが直接観測する出力の変更のうち承認対象に残すのは、依頼に含まれないエンドユーザー向け画面・文書・通知の変更だけとする。依頼が求める表示変更の実施方法と、表示の粒度や情報量の変更は、それ単独では確認理由にしない。

事前承認を求める前に、許容済みの範囲で実行でき未回答の確認に依存しない準備を完了し、承認を求める本文にはその成果と承認後に実行する操作を示す。未承認の操作へ進む根拠は承認の成立だけとする。準備自体が確認を要する場合は、その確認を先に送る。
