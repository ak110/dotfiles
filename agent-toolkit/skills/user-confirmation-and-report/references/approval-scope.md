# 承認範囲の判定

`references/judgment.md`「認可を要する操作」への該当は、操作が残す副作用だけを入力として判定する。操作の目的は判定の入力から外れる。
既存の環境、成果物または依存関係を置換、再作成または削除する操作は、調査、原因特定または動作確認を目的とする実行でも
破壊的操作として承認対象とする。
調査という目的が承認要否の判定を上書きすると、合意していない置換が確定する。
`agent-toolkit/rules/02-agent-operations.md`「プロセス終了の安全規定」の条件で作成元の作業単位が回収済みと確定したエージェント由来の残存資源の停止と、その資源が再作成した空のパスの削除は、承認対象の破壊的操作から外す。作成元の作業単位の回収は既に成立した工程であり、残存資源の回収はその回収の完了に当たり、その資源を使う主体も残っていないためである。

ユーザーが提案として指定した操作は、その提案の範囲では合意済みとして扱い、そのまま実施する。
承認源はユーザーの指示、規範、手順ならびに人間由来のWIとする。人間由来のWIから承認が成立する条件は`agent-toolkit:wi-standards`が定め、他の承認源では、その指示、規範または手順が定める範囲を承認の範囲とする。計画が記録したユーザー確認の回答は、その回答を承認源として扱う。
成立した承認は、承認源を問わず、操作、対象、影響範囲および成立条件が同じ範囲へそのまま適用する。
適用範囲を限定して受け取った指示は、その限定が成立している間の、同じ対象への操作にだけ適用する。

成立した承認が無い承認対象（「認可を要する操作」と、`SKILL.md`「確認要否の判定」で確認を要すると判定した変更）は、事前承認と事後承認へ分ける。
後者の変更のうち、可逆であり、第三者への影響、外部サービスの状態変更および復元に追加の外部操作を要する副作用のいずれも伴わない操作を事後承認とする。
事後承認の操作は、最善と判断する対応を実施したうえでユーザー確認し、回答を待たずに元の作業を続ける。実施した変更はそのまま保ち、確認本文へ実施内容、根拠、影響、復元方法を書く。
起動中のスキル・適用中の規範・ユーザー指示が工程・対象集合・副作用を定める場合は、その範囲の実施はユーザーへの報告へ含める。計画が記録した元の要求または確認回答も、その範囲で同じく扱う。
定められた工程の内側で、規範から一意に導けない判断、ユーザーの選好に依存する代替、定められた範囲を変える操作を追加した場合は、その追加部分だけを`SKILL.md`「確認要否の判定」へ送る。
いずれかの副作用を伴う操作は事前承認とし、合意を得てから着手する。
成果の適否をユーザーだけが観測でき、実行主体がいずれの手段でも観測できない変更は、「認可を要する操作」への該当の有無にかかわらず事後承認として扱う。
この変更では、最善と判断する対応を実施して元の要求を終端し、適否を事後承認のユーザー確認で問う。
画面表示の見え方や操作の感触など、実行主体が再現できない環境でだけ現れる結果が該当する。
前段が事前承認と定める副作用を伴う操作は、事前承認のまま扱う。
人間が確定した判断のうち、目的・要件・ユーザーが観測する結果に関する判断の変更（`references/judgment.md`「認可を要する操作」）は、可逆であること、第三者・外部サービスへの影響が無いこと、成果の適否をユーザーだけが観測できることのいずれによっても事後承認とせず、事前承認とする。この規定は本書の事後承認の各条件より優先する。事後承認は新しい人間の判断を得る前にエージェントの判断だけで変更を実施するため、ユーザーが知らないまま目的側の判断が変わる結果を招く。判断の記録自身が変更時の承認方式を定める場合（事後承認型UWIでの報告を定める記録など）は、その定めに従う。
規範からの逸脱と、人間が確定した手段に関する方針（`references/judgment.md`の判別基準で手段側と判定したもの）からの逸脱は、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」の条件を満たす場合に事後承認とする。逸脱の扱いは次のとおりとする。

- 逸脱1件は外れた規範条文または手段の方針の記録と、外れた場面の組とする。確認は逸脱1件ごとに発行し、報告用UWIや完了報告へまとめて済ませない。まとめると、ユーザーは個々の逸脱の可否を判断できない
- 確認本文には、外れた規範の所在、場面、両案のQCDを比べた観測根拠、実施内容および復元方法を書く。手段は`SKILL.md`「手段の選択」に従い、自律モードでは事後承認型UWIとする
- 逸脱する操作が本書の事前承認の副作用（第三者への影響、外部サービスの状態変更、復元に追加の外部操作を要する副作用、破壊的操作）を伴う場合は、事前承認のまま扱う
- ユーザーの目的・要件と硬い制約が両立しない場合は、逸脱ではなく事前承認の対象とする

依頼に含まれない新しい挙動の追加（`references/judgment.md`「認可を要する操作」の範囲外の不足の区分）も、可逆で第三者・外部サービスへの影響が無い場合を含めて事前承認とし、合意を得るまでリリースの対象へ含めない。この規定も本書の事後承認の各条件より優先する。事後承認で実施すると、ユーザーが把握しない機能が回答より先に公開されるためである。
ユーザーが実行時に直接観測する出力の変更のうち、承認対象に残すのは依頼に含まれないエンドユーザー向け画面・文書・通知の変更だけとする。依頼が求める表示変更の実施方法は`SKILL.md`「確認要否の判定」で決める。表示の粒度や情報量の変更は、それ単独では確認理由にしない。

事前承認を求める時点までに、既に許容されている範囲で実行でき、かつ未回答の確認事項に依存しない準備を完了する。
承認を求める本文には、その準備で得た成果と、承認後に実行する操作を示し、ユーザーが可否を判断できる状態にする。
未承認の操作へ進む根拠は、承認の成立だけとする。
準備自体が確認を要する場合は、その確認を先に送る。

公開インターフェース変更に当たるかを判定する前に、そのインターフェースの消費主体を確定する。
消費主体はそのインターフェースを実行時に呼び出す主体と、その出力を読む主体で判定する。
成果物の配布元、置き場所および名称は、この判定の対象外とする。
消費主体がコーディングエージェントだけであるインターフェースは、公開インターフェース変更の対象から外れる。
受理形式・オプション・公開名・説明・入出力の形式・スキーマ・返却形式のいずれの変更も同じ扱いとする。
該当の例は次のとおりとする。
agent-toolkitが配布するコマンドライン群（`atk`コマンドとスキル配下のスクリプト）。
MCPサーバーが公開するツール（対象プロジェクトが提供するものを含む）。
エージェント向け文書が定める起動契約と返却形式。
フックがコーディングエージェントへ返す通知の本文。
これらを含む各対象についても、前段の消費主体の判定を実施して該当を確定する。
ブラウザーUIの画面・エンドユーザー向け文書・ユーザーへの通知は、エンドユーザーまたはユーザーが直接読むため、公開インターフェースとして「認可を要する操作」の対象に残る。
消費主体がコーディングエージェントだけである変更は、手元の情報で決まる技術判断として確定し、確定内容を成果物へ記録する。
そのインターフェースが実行する操作自体が「認可を要する操作」の他の区分に当たる場合と、ユーザーの明示要件を変更する場合はユーザー確認する。
破壊的操作では、実行内容・影響範囲・復元方法の事前説明を維持する。
ユーザーが提案として指定した破壊的操作（`references/user-utterance.md`の提案的表現の項）にも同じ事前説明を適用する。
パターン、ワイルドカード、状態指定などで対象を一括選択する破壊的コマンドでは、同じ指定で実際に対象の一覧と削除時の副作用を取得してから影響範囲を示し、依頼の範囲外の対象を除いたコマンドにする。
利用者へ実行を求めるコマンドを案内する場合も同じとする。集合指定の評価結果は起草時の想定より広がり得るため、評価結果を実際に確かめる前の案内は依頼していない対象の削除を招く。
