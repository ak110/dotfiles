# 実行レビューの指摘と完成条件証拠の記録

本書は実行レビュー担当が、指摘をレビュー指摘管理表へ登録し、完成条件証拠を作成する方法と、判定の値と根拠の記録の仕方を定める。判定の基準は`agent-basics:review-standards`の`references/reviewer.md`「実行レビューの判定」、返却前の工程は`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`「出力」が定める。

未判定検証記録は実装担当またはメインが`atk run-script verification-record --`で作成する入力であり、操作は`${CLAUDE_PLUGIN_ROOT}/share/verification-evidence.md`「完成条件証拠の検証記録」が定める。初回は計画かWIと`--list`を渡し、保存と原文・出所・行番号の取得を同時に行う。入力なしの一覧は既存記録の読取だけに使う。完成条件証拠は実行レビュー担当が作成する判定結果である。完成条件証拠の`outcome`、`evidence`および`reviewed_head`は実行レビュー担当だけが更新し、レビューイーへ補完を求めた場合も補完後の判定と記入は本担当が行う。証拠そのものを`location`にした指摘は、`atk run-script exec-review-evidence-check`が未応答の行として拒否する。

## 名指し参照の読込方法

本文の各参照の適用条件を保ち、選んだ資料の指定範囲を取得してから、その基準を使う具体的な判断へ進む。起動時の行の資料は起動本文とともに届く。

## レビュー指摘管理表への登録

- 表の絶対パスを解決した直後、最初の読取前に`exec-review.subagent.md`「入力」の初回準備に従う。初回で不在の表だけを本担当が作成し、既存表と再レビュー・引き継ぎ再レビューの表は保持する。履歴継続時に表が不在なら新規の空表で補わず、不在として扱う
- 指摘には対象箇所、違反した契約、観測事象、必要な外部可視の結果および判定根拠を書く。同じ原因の指摘は1行へまとめる（努力目標）。既存行の応答と証拠は保持する
- 同じround・trackで確定した複数指摘は、`atk review-table add <表の絶対パス> --round <round> --track exec-review --items-file <JSONの絶対パス>`で一括登録する。JSONはUTF-8の非空配列とし、各要素には文字列の`location`・`issue`・`level`の3キーだけを置く。`level`は`要件`・`仕様`・`詳細`・`実装`から選ぶ。単独指摘は従来の`--level`・`--location-file`・`--issue-file`でも登録でき、これらと`--items-file`は併用しない。どちらの形でも、終了コード0と標準成功文で、同じ操作が行う既存行を含む全行の保存一致確認の成功を受け取る
- 指摘が無ければ表をそのまま残す。再指摘も現在roundへ登録し、未解決件数は`atk review-table show <表の絶対パス> --format=summary --round <round>`の`unanswered_count`から得る

## 走査記録と差分外の不良

観点ごとの走査結果は、受領したmanaged-temp内のファイルへ走査の完了ごとに保存し、再起動時はそのファイルが示す未走査の観点だけを扱う（長時間稼働の末に終了した担当の到達点を回収するため）。

- 探索結果の各指摘を走査結果へ対応付け、採用分は表の行を、不採用分は本文・契約で確かめた理由を記録する
- 差分外・範囲外として表から外した候補は、実在する不良、未裏付けの候補、現物上成立しない候補へ分けて走査記録へ残す
- 実在する不良には対象箇所・条件・観測事象・実害・裏付け・表から外す理由・原因と対策案を記録する。裏付けには、報告する入力・呼び出し元・設定で使われる定義（囲む関数とクラス、派生クラスの上書き、呼び出し元）を読み、対象箇所への到達を確かめた所在を書く。判定は`agent-basics:writing-standards`の`references/investigation.md`「根拠と主張の一致」に従う。返却末尾の`想定外事象:`へ記録の絶対パスと要点、到達を確認した定義と呼び出し元のファイルと名前を書く。担当自身が観測した差分外の不良も同じ内容を委譲元へ渡す
- 未裏付けの候補には不足する根拠と取得手段を記録し、操作区分で補える不足を補ってから分類する。検索の一致行や差分の断片だけを根拠にした候補はこの区分とし、定義と呼び出し元の読取で到達を確かめてから分類し直す。担当で補えない不足は対象と不足内容を委譲元へ渡す
- 現物上成立しない候補には、確認した本文・契約と非該当の根拠を記録する。範囲内の不良は表へ登録する
- 初回レビューの不足として返された項目は通常の再レビュー指摘と区別して記録し、委譲元へエスカレーションする

## 完成条件証拠の生成

ラッパー・コンテナー経由の試験結果は、`atk run-command`の`--result-file`と必要な`--path-map`による宣言から取り込める。
宣言したファイルの起動前後の有無かSHA-256の変化と、取込時のSHA-256が終了直後と一致することを確かめる。
結果中のパスは最長一致の接頭辞対応でホストへ変換し、worktree内に限定する。
宣言のない記録はrunnerの出力指定をargvから確認する。

証拠要求ありの場合は次の順で作成する。

1. 計画の進捗ログが示す検証結果、要求単位ごとの未判定検証記録、受領したCI記録・WI記録（`exec-review.subagent.md`「入力」で保存した入力記録）を読み、各記録の出所と根拠の現物を独立に確かめる。不一致・不足は`証拠不足`と指摘の登録で扱う
2. 雛形を出力する。`atk run-script exec-review-evidence-check -- --template <完成条件証拠の絶対パス> <計画外の対象WIファイル名...> --plan <計画の絶対パス...>`を、行の判定の前に実行する。計画が無ければ`--plan`を省き、CI・WI記録だけが入力なら`--plan`の代わりに`--input-record <入力記録の絶対パス>`を渡す。計画の関連WIと計画だけの要求（`## 変更履歴`の`### ユーザー発言N`直下の`text`ブロックの逐語発言）の行も生成される。記入済みの行は保持され不足行だけが加わるため、各ラウンドで実行する
3. 次節の`--list`で行を読み、同じ更新で確定できる複数行は更新配列へまとめ、同節の`--updates-file`で各行の`outcome`・`evidence`・`reviewed_head`を記入する。単独行は行選択と公開引数でも記入できる。保存結果で期待する更新内容との一致を確認し、内容の判定に追加本文が必要な場合は`--list`で対象行を取得する。実装担当の空欄の記録は流用せず本担当が判定する
4. 再レビューでは既存行を保持し、同じファイルを再判定する。各行の根拠を現在の要求単位へそろえ、失効した説明と別要求の経緯を置換する

雛形の行は返却前の確認が求める行と同じであり、削除や分割をすると確認で拒否される。単独では要求として読みにくい行も、属する発言の要求に照らして判定し、その扱いを`evidence`へ書く。要求単位の切り出し規則への疑義があっても全行を記録し、確認の成功を確かめた後に`想定外事象:`へ添える。

## JSONの形式と返却前の確認

次は読取の操作であり、JSONを変更しない。全行表示と`--section`（配列の指定）だけの指定では、先に根拠を除いた`証拠の行一覧`（配列名・行番号・WI・判定・source・原文）を全行分並べ、続く`証拠の全行`に根拠を含む各行を並べる。`--row`は`--section`と組で1始まりの行番号を反復して指定し、指定した行だけを返す。
複数行を返す全ての表示では、先行行と同一の空でない根拠を`evidence_reference`の`display`・`section`・1始まりの`row`で示す。
同じ出力の先行行をたどると全行の根拠を読め、1行だけの`--row`指定でも同じ出力から根拠全文に到達できる。`--list --rows-only`は根拠を除いた行一覧だけを返す。
通常返却・全行表示・配列表示・選択読取とbatchの各組では、共通段落を同じ出力の`証拠の根拠辞書`にまとめ、各行の`evidence_parts`から順序・反復を保って読む。各IDの本文断片を順に連結すると原本の根拠全文へ完全一致する。保存JSONの配列・1始まりの行番号と表示行を対応付け、全欄と直接根拠の意味を全対象について確認する。辞書は表示ごとの参照先であり、保存原本と判定・実行終了状態を保持する。

```text
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス> --list
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス> --list --rows-only
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス> --list --section user_requirements --row 1 --row 3
```

記入は表示された配列名と1始まりの行番号を`--select-row <配列:N>`へ渡して行う（sourceは処理側が現行行から取る）。`--select-row`を省略した場合は、`--row-outcome`などの行別指定に書いた行（`--verification-row`と`--accepted-row`では第1要素の行）が選択行になる。各選択行へ`--row-outcome`を明示し、`--reviewed-head`へ本担当が判定した完全OID、`--evidence-file`へその行を直接満たす説明を渡し、`--mode`のappendかreplaceで根拠を追記・置換する。失効・割当外・背景で判断根拠の所在へsourceを変える場合だけ`--row-source <配列:N> <所在>`も渡す（受理条件は本書の各判定値の規定による）。

```text
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス> --select-row user_requirements:1 --row-outcome user_requirements:1 達成 --reviewed-head <レビューした完全OID> --evidence-file <説明の絶対パス> --mode replace --output <同じ完成条件証拠の絶対パス>
```

構造化試験は`--junit-xml <保存XML> --junit-record <実行記録>`で指定する。診断は`--diagnostics-file <保存JSONL> --diagnostics-record <実行記録> --diagnostics-conditions <取得時の条件JSON>`と必要な`--diagnostics-source <相対ファイル> <保存時本文>`の反復で指定する。相対ファイルはworktreeのルートを起点とする。基準比較は同じ組の`--baseline-junit-*`・`--baseline-diagnostics-*`へ保存物を渡す。pyfltrのrun JSON Linesはheader・command・summaryを含む全体を使う。形式は`atk run-script exec-review-evidence-check -- --help`で読む。
pytest以外の試験は、`--test-format <vitest|playwright|trx> --test-file <保存結果> --test-record <実行記録>`で形式と対応する保存物を渡す。同じ完全名が複数ある結果は出現順の1始まりの`#<番号>`を完全名へ付けて区別する。
基準版は`--baseline-test-format`・`--baseline-test-file`・`--baseline-test-record`へ同じ組で渡す。
各runnerの取得は、対象プロジェクトの起動形へ次の指定を加えて`atk run-command`で実行し、結果ファイルと実行記録を保存する。

| runner | 結果を保存する指定 |
| --- | --- |
| pytest | `-v -o junit_family=xunit1 --junitxml=<XMLの絶対パス>` |
| vitest | `run --reporter=json --outputFile=<結果の絶対パス>` |
| Playwright | `env PLAYWRIGHT_JSON_OUTPUT_NAME=<結果の絶対パス> <Playwrightの起動形> test --reporter=json` |
| dotnet test | `--logger "trx;LogFileName=<結果の絶対パス>"` |

形式ごとの状態と完全名は保存結果から読み取られ、一覧・詳細・要求行への記入・基準版との差の確認は共通の公開操作を使う。
結果と実行記録の対応を確認できない入力は、診断の示す不足を補ってから再指定する。
これらへ`--list-results --results-counts`を加えて状態・基準差・診断群の件数を読む。続けて`--results-counts`を`--result-status <状態>`・`--result-change <差の種類>`・`--result-diagnostic-group <群番号>`の必要な選択へ替え、`--results-identifiers`で選択群の全識別子を取得する。識別子表示を外せば選択群の詳細を取得でき、完全名の`--result-test <完全テスト名>`と`--result-diagnostic <診断識別子>`の反復でも詳細・取得版・所在を読める。全詳細と全識別子付き要約の`--results-summary`も使える。代表1件で全件の意味を判断せず、比較不能を一致と扱わず、成功件数だけから達成を生成しない。取得版と条件が行を直接満たすかは本担当が判定する。
記入時は`--list-results`を外し、同じ保存物と識別子を`--select-row`・`--mode`・選択行ごとの`--row-outcome`と`--reviewed-head`へつなぐ。既存の`--results-file`・`--updates-file`も受理され、JSON入力のsource不一致は拒否される。

更新配列を直接ファイルへ記入する場合は、一覧の配列名・1始まりの行番号・現行`source`を使う。例えば、`user_requirements`の1行目を手動観測で判定する更新JSONは次の形で保存する。`source`は一覧の値へ、`reviewed_head`は実際にレビューした完全OIDへ、`evidence_file`は行を直接満たす説明のUTF-8ファイルの絶対パスへ置き換える。

```json
[
  {
    "section": "user_requirements",
    "row": 1,
    "source": "一覧に表示された現行source",
    "outcome": "達成",
    "reviewed_head": "レビューした完全OID",
    "evidence_file": "/absolute/path/observation.txt",
    "mode": "replace"
  }
]
```

```text
atk run-script exec-review-evidence-check -- <完成条件証拠の絶対パス> --updates-file <更新配列JSONの絶対パス> --output <同じ完成条件証拠の絶対パス>
```

更新の終了0と、返却の`保存結果`にある`readback_matches: true`、出力先・更新対象・件数を確認する。同じ公開更新操作が保存済みJSONの全文を読み直し、更新後の期待本文と一致することを確認する。この比較にはappend・replaceによる更新、原文・出所・判定・取得版と未選択行の保持を含む。保存結果が一致しない場合と読取不能の場合は非0で終了する。

説明ファイルだけで記入する場合は`tests`・`diagnostics`、`--results-file`と構造化結果の指定を省略できる。初回更新後、根拠を訂正するときは説明ファイルを書き直して`mode: replace`で同じコマンドを実行する。再レビューも同じ証拠を一覧で読み、今回の判定と完全OIDを明示して更新する。追記する場合は`mode: append`を使う。
出所変更では同じ更新行の`source`に変更前の一覧の値を保ち、`new_source`へ判断根拠の新しい所在を追加する。`outcome`は`wi_conditions`では`失効`、`user_requirements`では`失効`・`割当外`・`背景`のいずれかとし、所在と説明は「判定の値」「失効の根拠」に従う。例えば、ユーザー判断で要求が失効した場合は次の更新配列を直接記入し、前記の`--updates-file`のコマンドで保存する。例の各値を一覧、実際の判断の所在、レビューした完全OIDと不採用の説明ファイルへ置き換える。

```json
[
  {
    "section": "user_requirements",
    "row": 1,
    "source": "一覧に表示された変更前のsource",
    "new_source": "関連UWIのファイル名と回答節、否定した要求単位",
    "outcome": "失効",
    "reviewed_head": "レビューした完全OID",
    "evidence_file": "/absolute/path/rejection-reason.txt",
    "mode": "replace"
  }
]
```

更新後の一覧にある新しい`source`を次の更新の選択値に使う。
通常の判定の更新では原文と出所が保持され、どの更新でも未選択行の値が保持される。配列に不正な行指定や組合せが1件でもあれば、入力も出力も変更しない。保存時のJSONの再直列化による空白・改行の変化と、値の変更を区別する。
未判定根拠を使う場合は`--verification-record <未判定記録の絶対パス> --verification-row <選択行の配列:N> <未判定行の配列:N>`を指定する。同じ原文・WI・出所の要求単位からだけ継承でき、説明と手動観測は`--evidence-file`で補う。保存先は未判定記録と別の完成条件証拠とし（同じ証拠のパスへ原子的に更新でき、別出力も指定できる）、不正な行が1件でもあれば全保存が拒否される。原文・未選択行・未判定記録は保持される。
継承する未判定根拠も、その要求単位の現在の判定に直接必要な観測と適用理由を確かめてから使う。
更新は`--mode replace`で現在の根拠へそろえ、`--mode append`は同じ要求単位の現在の根拠に不足する観測を補う場合に使う。
更新後は同じ操作の保存結果で期待する更新内容との一致を確認し、本書の原文・内容・HEAD・共用の確認と`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`「出力」の返却前確認へ進む。内容の判定に追加本文が必要な場合は`--list`で対象行を取得する。未判定記録の一覧の表示にはverification-recordを使い、返却の`--show-all-rows`は記入済み証拠の受領に使う。

JSONの最上位は`{"wi_conditions": [...], "user_requirements": [...]}`とする。

- `wi_conditions`の要素は`awi`、`condition`、`outcome`、`source`、`evidence`、`reviewed_head`を持つ。`condition`には`## 完成条件`の各項目の原文を逐語で置く
- `user_requirements`の要素は`awi`、`requirement`、`origin`、`outcome`、`source`、`evidence`、`reviewed_head`を持ち、`origin`で発言の所在を示す。計画だけからの行は`awi`を空文字列とし、`origin`へ計画内の所在を置く
- `evidence`にはその行を直接満たす根拠（ファイルと行、テスト名と結果、観測記録の所在など）だけを置き、WI単位の根拠を全行へ写す書き方は採らない。複数行に共通する長い根拠は`完成条件証拠`と同じディレクトリの共通ノートへ一度だけ書き、各行は行固有の判断と`<絶対パス>#<見出し>`の参照で構成する。共通ノートは参照後に変更せず、内容を変える場合は別のファイルを作る。証拠のパスが計画最終化の進捗ログに残るため、同じディレクトリの共通ノートにも到達できる。`--evidence-file`の共通指定は選択した全行へ全文を複製するため、長い共通根拠には使わない。観測手段を名指しする条件は`agent-basics:review-standards`の`references/reviewer.md`「実行レビューの判定」の名指しの観測手段に従う

返す前に、対象WIの完成条件の各要求単位と`wi_conditions`、元のユーザー発言の各要求単位と`user_requirements`を原文で比べ、各単位に1行以上が対応し判定と証拠参照がそろうことを確かめる。一文に含まれる複数の要求や、例示と要件の区別は機械的な最低行数に委ねず自身で比べる。WIにも計画にも元のユーザー発言が無ければ`user_requirements`の行は空でよい。

## 受理済み判定への参照

後続レビューで`受理済みの完成条件証拠`を受領した場合、または同じレビュー系列の再レビューで前ラウンドの返却を委譲元が受領した証拠の写しを保存した場合は、その行の結果へ作用する成果物・テスト・入力・実行環境が今回の差分の前後で同じと確認した行だけを参照できる。差が作用する行と受理済み判定が無い行は、未判定根拠と現物の観測で判定する。
参照は既存の更新操作へ`--accepted-evidence <受理済みJSONの絶対パス> --accepted-row <選択行の配列:N> <参照行の配列:N>`を渡して行う（複数行は反復）。今回の判定を各`--row-outcome`と`--reviewed-head`へ明示し、今回も適用できる理由を1件の`--evidence-file`へ保存して、`--mode replace`で参照と説明だけを記録する。
参照先は同じ配列・WI・原文の要求単位で、非空の判定と完全OIDの確認版を持つ必要があり、不成立の行が1件でもあれば全保存が拒否される。判定済みJSONを`--verification-record`へ渡す継承は従来どおり拒否され、未判定記録の判定欄は空欄のまま保つ。
保存される`受理済み判定:`のJSON（絶対パス、配列、1始まりの行番号、判定、取得時の確認版）と説明が今回の根拠になる。参照先の根拠本文と回収済みファイルの所在確認は受理済み証拠の側にだけ残り、返却前確認は参照先の実在・行・同一原文・判定を読む。参照先を読めなくなったら、読める受理済み証拠か今回の観測へ戻る。
参照先の確認版は取得時の判定を示す値であり、`--rewrite-map`が更新する現行成果物の`commit:`参照とは別に保持する。適用条件の確認と今回の判定はレビュー担当が担う。

## 記録する行と要求単位

- 完成条件節のあるAWIの各条件を`wi_conditions`へ、同じAWIの末尾の`## ユーザーコメント`の要求単位を`user_requirements`へ記録する
- 完成条件節のない原文AWIはfrontmatterと処理結果を除いた本文から、回答済みUWIは`## 回答`の記入済み本文から要求単位を取る（回答欄の案内コメント、質問・選択肢・判断材料・処理結果は除く）。計画の`ユーザー指示`行も同様に記録する
- `## ユーザー指摘の逐語引用`は投入元で解決済みの発話であり（`agent-toolkit:wi-standards`の`references/origin-and-approval.md`）、要求単位を取らず解釈の根拠として読む
- 要求単位の最小は箇条書きの項目、句点・疑問符・感嘆符で区切る文、終止記号のない段落とする。ASCIIの`.`・`!`・`?`は直後が空白か段落末の場合だけ文末とし（ドメイン名・ファイル名・版番号・インラインコード内は文の一部）、直後の閉じ括弧は同じ文に含める。補足のフェンス付きコードブロックは単位へ分けず背景資料として読む

## 判定の値

判定は`達成`・`未達`・`証拠不足`・`失効`のいずれかとし、`user_requirements`の行だけは`割当外`と`背景`も使える。通常の根拠はレビュー対象差分、検証結果、開始時点の既存実装から示す。

| 値 | 使う行 | `source`と`evidence`への記入 |
| --- | --- | --- |
| `割当外` | `reviewer.md`「割当外・背景」で割当外とした`user_requirements`の行 | `source`へ割当を記録した箇所（WIのファイル名と節名`反映内容と反映先`、または計画ファイルの絶対パスと節名`実施内容`）、`evidence`へ記録どおりの割当先（WIファイル名、`「」`で囲んだタイトルか説明、または`分割元の依頼全体`）。引受の記録を使う場合は、`source`へ割当先のAWIのファイル名と節名`反映内容と反映先`（保存済みの形では`ユーザー指摘の逐語引用`）、`evidence`へそのファイル名 |
| `背景` | `reviewer.md`「割当外・背景」で背景とした`user_requirements`の行 | `source`へ分類の記録の所在（WIのファイル名と節名`反映内容と反映先`、計画ファイルの絶対パスと節名`実施内容`、レビュー指摘管理表の絶対パスのいずれか）、`evidence`へ記録を指したうえで要求を含まない理由 |
| `失効` | 「失効の根拠」に当たるユーザー判断の否定がある完成条件と原文要求の行、およびメインの技術判断の記録があるエージェント由来のAWIの完成条件の行 | `source`へ否定したユーザー判断の要求単位と所在か技術判断の記録の所在、`evidence`へ不採用の根拠（計画の不採用行か、実装着手後に採否を変えた結論を記録した表の行） |
| `未達`（`reject`の終端） | 全体不採用で`reject`終端するWIの完成条件。初回からこの判定を使う | `evidence`へ終端区分`reject`と、計画または`--input-record`へ渡した入力記録の`実施内容`の不採用根拠の所在（絶対パスと節名） |
| `達成`・`未達`・`証拠不足` | 前記に当たらない行 | 「根拠の書き方」に従う |

- `割当外`: 所在の節の割当の語（`割当`・`割り当て`・`分割元の依頼全体`）を持つ行に割当先の表記が現れるかを確認コマンドが確かめる。`「」`の割当先はH1タイトルのほか要求内容を特定できる説明も受理する
- `背景`: 分類の記録の行は背景とした原文の範囲を`「」`で引用し（中略は`…`）、同じ行に「背景」の語と理由を持つ。確認コマンドは所在、引用が要求単位を覆うこと、`evidence`の理由を確かめる。起草時の記録が無い単位は、計画の起草中なら計画担当が`## 実施内容`の根拠へ、実装着手後なら本担当がレビュー指摘管理表へ分類と範囲を記録してから使う。完成条件証拠へ`背景`と書くだけでは記録に当たらない。処理中の元AWIの本文の書換えは記録の手段から外す
- `失効`: 失効した完成条件も`wi_conditions`へ1行ずつ残す
- 出所を変更する更新JSONは、現行`source`で行を選び、前表の所在を`new_source`へ記入する。通常の判定へ`new_source`を付ける更新と、`wi_conditions`の`割当外`・`背景`は受理しない
- `reviewed_head`: その行を実際に確認したレビュー対象commitを、返却する`レビューしたHEAD`と同じ対象をGitで解決できるOIDで置く。計画だけにある原文要求の行にも記録する

計画なしでWI全体を不採用とする場合は、`--input-record`へ渡す入力記録に`## 実施内容`の表を置く。表は`実施内容`・`採否`・`根拠`の列を持ち、対象WIごとにファイル名を含む行を1行以上置く。その全行を`不採用`とし、各行に空でない根拠を記録する。`evidence`には`reject`終端と、その入力記録の絶対パスおよび`実施内容`節を記す。

## 失効の根拠

失効行の`source`には否定した要求単位と次のいずれかの所在を書く（技術判断の記録では要求単位の代わりに記録の所在）。最初の3種が失効の根拠として受け付けるユーザー判断であり、`agent-toolkit:wi-standards`「由来と承認」の明示由来のうちユーザー自身の記入か記録位置付きの逐語発話に当たる。関連計画の実施内容の由来はエージェントが書いた記録のためユーザー判断に含めない。

- 対象AWIのファイル名と`## ユーザーコメント`の所在
- 関連UWIのファイル名と`## 回答`の所在
- 会話中のユーザー発話の所在: `session-review-evidence --user-events`の元の出力ファイルの絶対パスと、その直後の`<record>:<line>`（例: `claude:<セッションID>:625`）。`record`・`line`はJSONレコードの同名欄の値をコロンも含めてそのまま書く（`line`は元のセッション記録の行位置であり、照会出力の物理行とは異なる）。否定した要求単位は発話本文（確認回答では回答と自由記述）から「」で囲んだ逐語で書く
- メインの技術判断の記録の所在: 計画確定前は、今回レビューへ渡された計画の絶対パスと`## 実施内容`の根拠欄（対象AWI・対象条件・`メインの技術判断`・外す根拠を記録した行）。実装着手後は、対象AWIのファイル名と`メインの技術判断`の文字列を含む行があるレビュー指摘管理表の絶対パス。計画の記録がそろう場合は表への転記を要しない。この根拠は`source`を持つエージェント由来のAWIの`wi_conditions`の行だけに使い、`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`「技術判断で外せる完成条件」に当たる条件だけを外す

計画か表の不採用行は`evidence`へ書き、ユーザー判断の参照先と区別する。ユーザー判断も技術判断の記録も無い条件除外の要請は委譲元へ返し、委譲元が確定してから失効の可否を決める。

失効への更新では一覧にある現行`source`を選択値とし、前記の判断の所在を`new_source`（直接引数では`--row-source`）へ渡す。不採用の根拠を説明ファイルへ記入して同時に保存し、更新後の一覧と返却前確認で判断の所在と根拠を確かめる。

会話の証拠には、受領した対象発話の逐語内容と時点・文脈を使う。`agents_server`の委譲先が必要時に`atk run-script session-review-evidence -- --delegation-record root --user-events`でユーザー発話を持つ最上位の会話を解決する。メイン自身のセッションID・thread ID・transcriptの絶対パスの手渡しは要らない。取得済みの出所と、明示された会話の識別子か記録パスを優先する。同文反復は受領した時点・文脈と元の記録位置で区別する。
解決が終了コード2で失敗した場合は、委譲元から対象会話のセッションID、thread IDか記録パスを受け取り、`--claude-session-id`・`--codex-thread-id`・`--transcript`のいずれかと`--user-events`で再実行する。`Agent`ツールなど解決を確認していない起動方法でも明示値を使う。担当自身の`CLAUDE_CODE_SESSION_ID`と`CODEX_THREAD_ID`は委譲先を指し、委譲元の識別子へ代用できない。
`--owner-session --user-events`は環境の`AGENT_TOOLKIT_OWNER_SESSION`が示す所有会話を読む別の指定であり、直接の委譲元とは限らない。未設定、`mcp-`で始まる値、記録0件・複数件では終了コード2になる。環境変数の値は出力せず、失敗時は前段の明示指定で再実行する。
取得済みの出所は再抽出せず、`atk run-script session-review-evidence -- --user-events-file <元の保存ファイルの絶対パス> --user-event-at <record>:<line>`で全欄を読む。構造化確認では質問・全選択肢・選択回答・自由記述の対応を保ち、ユーザー由来の判断は回答と自由記述から確定する。取得不能・不一致・一意に特定できない入力では証拠を確定せず、具体的な不足を委譲元へ返す。

## 統合時の完成条件判定

計画ごとの完成条件証拠へ行う次の確認を「統合時の完成条件判定」と呼ぶ。委譲元は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」の時点で行う。統合するレーン担当は`${CLAUDE_PLUGIN_ROOT}/share/lane-integration.subagent.md`「入力」の時点で行う。受理できない行があれば、委譲元は統合指示を保留し、レーン担当はマージとAWI終端へ進まない。

1. 計画ごとの`完成条件証拠のパス`のJSONを全て読み、各証拠の計画名と対応AWI集合を確かめる
2. 各WI本文の要求固有の完成条件と`wi_conditions`、元のユーザー発言の要求単位と`user_requirements`が過不足なく対応し、参照できる証拠を持つことを確かめる。元のユーザー発言は`## ユーザーコメント`、UWIの`## 回答`、完成条件節の無い人間由来のAWI本文、計画の`ユーザー指示`行から取り、`## ユーザー指摘の逐語引用`は除く
3. 統合時に`adopt`するWIの行は、次表で受理する行を除き`達成`を要する。実行レビューの返却の`達成以外の行`から証拠の該当行へ到達し、原文、`source`の記録と`evidence`を読んで受理条件を判定する。`<配列>の判定内訳`の件数だけで済ませない
4. 各`達成`行の根拠を、条件が指定した入力・操作・観測結果と比べる。隔離環境や部分実行を指定する条件では、その指定どおりの観測を直接の根拠として使える。後続工程（版数更新・配布・push後のCI・実ホストへの反映など）の予定や、指定した観測を別の隔離再現・部分実行で代用した記録だけで達成とした行は、同じ実行レビュー担当へ再判定を求めて統合指示を保留する。再判定で`証拠不足`となった行は延期`adopt`の条件として後続工程と検収時機を保持し、公開工程の検収の後に終端する
5. 全体検証とCIの成功は`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`の公開工程判定に従う。既存実装による充足も同じ条件で確かめる
6. 受理した行以外に欠落・重複・未達・証拠不足・参照不能の行があれば、委譲元はそのWIと欠けている内容を実行レビュー担当へ返して統合指示を保留し、レーン担当は不足したAWIと条件または要求単位を`続行できない理由:`へ書いて返す

| 行 | 受理する条件と扱い | 受理できない行 |
| --- | --- | --- |
| `wi_conditions`の`失効` | エージェント由来のWIの行に限り、否定したユーザー判断（「失効の根拠」）の要求単位と不採用の根拠を`source`と`evidence`から特定できれば受理する。`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`「技術判断で外せる完成条件」に当たる条件では、メインの技術判断の記録（計画確定前の実施内容の根拠欄か実装着手後の表の行）が判断と外す根拠を持ち、条件が境界の内側に当たることを読んで確かめて受理する。不採用の根拠は計画の`## 実施内容`の不採用行か、実装着手後に採否を変えた結論を記録した表の行とする（計画は実装着手後に凍結されるため） | 手順6のとおり返す |
| `user_requirements`の`割当外` | 割当の記録がWI本文の`## 反映内容と反映先`か計画の`## 実施内容`の`根拠`に実在するか、割当先のAWIの引受の記録を指していれば受理する | 記録を特定できない行は返す |
| `user_requirements`の`背景` | `source`の分類の記録が「」で引用した範囲がその単位と対応し、単位が要求・制約・採否・選好・回答を求める問いを含まないことを原文の文脈で確かめて受理する | 記録を特定できない行、範囲が対応しない行、要求を含む行は返す |
| 統合時に`reject`で終端するWIの行 | 初回から`未達`とし、`evidence`の終端区分`reject`と不採用根拠の所在から、同じ入力記録で全体不採用を特定できれば受理する。部分失効・延期adopt・割当外・背景と混同しない | 手順6のとおり返す |
| 延期`adopt`のWIの行 | 終端区分が後続工程と検収時機を明示する条件だけ`未達`か`証拠不足`を許容し、残りは`達成`を要する。統合時に終端せず、後続工程の成功を検収してから終端する | 手順6のとおり返す |
| `adopt`するWIの任意の判断材料の行 | 原文が行全体を`agent-toolkit:wi-standards`「通常AWIの本文」の任意の判断材料と明示する行（冒頭が「任意の判断材料」で始まる行など）は、`証拠不足`のまま受理する（得られた場合にだけ使う観測で、統合と終端を止めないため）。行の一部だけが任意の判断材料なら、残りの条件に`達成`を求める | 観測が得られて条件を満たさない`未達`は受理しない |

## 公開後に成立する条件と任意の判断材料

これらの行を`証拠不足`とするかは`reviewer.md`「公開後に成立する条件と任意の判断材料」に従い、`evidence`へは次を書く。

- 版数更新の条件: 終端担当が行う後続工程と、現時点で確認した範囲
- 公開・配布・実ホストへの反映の後に成立する条件: 観測に要る後続工程（版数更新、pushや反映処理など）と、それまでに確認できた範囲
- 任意の判断材料の行: 任意の判断材料であることと確認できた範囲（行の一部だけなら除いた部分）

## 根拠の書き方

- 保存結果の成功集合と修正後の限定再実行による被覆は、`agent-basics:check-execution`の`references/verification-scope.md`「実行条件と再実行」で判定する。記録の取得と要求行への対応付けは`agent-toolkit:check-execution`の`references/verification-scope.md`「構造化試験結果の取得と記入」を使う
- 各行には現在の要求単位に直接必要な観測と適用理由を保存する。必要な旧取得版・入力・結果と、その観測を現在へ適用できる理由は保持し、失効した説明と別要求の経緯は置換する
- 修正ラウンドの経緯・応答・履歴統合は既存のレビュー指摘管理表と観測記録へ残す。各行は判定に必要な所在と観測内容を参照し、複数要求が同じログを使う場合も該当する観測を行ごとに対応付ける
- 各ラウンドで、根拠に使う現物の該当箇所を読んでから記入する。リポジトリ内の資料はレビュー対象commitの本文から参照名と見出し・行位置を写し、検証記録はその行が求める入力と結果があることを確かめる。計画の採用ファイル名や前回の参照だけを転用せず（受理済み判定を使う場合は「受理済み判定への参照」の適用条件と今回の判定を記録する）、該当入力の観測が無ければ実在ファイルでも`証拠不足`とする
- 保存済みのテスト出力や手動観測を、取得した版と異なるレビュー対象版の根拠に使う場合は、記録の取得時の版と実行条件（`atk run-command`の保存JSONの`cwd`・`git_head`・`git_status`、別実体を実行した場合はその版）を読む。`git_head`はcommit、`git_status`は変更ファイルと変更状態を示す。未commit・未追跡の本文の同定には取得時の保存本文など別の根拠を使う。そのうえで、結果に作用する内容と条件（テスト対象と依存ファイル、入力、実行環境）が変わったかを差分で判定する。祖先関係、旧新OIDの対応、`git range-diff`の`=`はtree全体と条件の同一性を示さないため判定に使えない。変わっていなければ祖先でなくても使え、`evidence`へ観測ファイル（保存JSONの絶対パスなど）の参照と適用できる理由を書く。取得時の版は観測ファイルの参照と、地の文へ併記した裸のOIDが保持する。現行成果物を指す参照だけを`commit:<OID>`で書き、`--rewrite-map`はこの標識だけを更新する（分割した各対応先もcommit:で残る）。裸のOID、HEAD・git_head・比較元、観測ファイル、判定と`reviewed_head`は変わらない。既存の自由文を推測して新形式へ移さず、曖昧・不正な対応は部分保存されず拒否される。根拠共用のCOMMIT_REFERENCEによる数字の保護は別の責務として維持する。変わった行と取得時の版を特定できない行は`証拠不足`とし、影響する行だけの追加観測を実装担当へ求める。履歴そのものを試す検証は取り直す
- ファイルは絶対パスか対象worktreeからの相対パスで書く。ファイル名だけや途中からのパス（pytestのノードIDなど）は、追跡ファイルのパス末尾が1件に決まる場合だけ受理され、決まらなければ確認コマンドが候補を示すので、その行の`evidence`だけを直す（`condition`と`requirement`は原文のまま）。裸のパス、インラインコード、Markdownリンク、`stdout=/absolute/file.txt:1`のラベル、`/absolute/file.txt:1: 観測説明`、引用符で囲んだ絶対パスのいずれでもよく、行番号（1始まり）・節名・テスト識別子を添えてよい。パスを伴わない具体的な`test_`始まりのテスト名と明示された成功結果も書ける
- 所在と説明の境界は確認コマンドの切り出し規則で決まる。地の文の`path#見出し`は空白・読点・句点・括弧の手前までを見出し名として実在の見出しと比べるため、見出しの直後に説明を続ける場合は空白か読点で区切る。空白を含む見出しは、インラインコードかMarkdownリンクで参照全体を囲む。行位置は`:N`か`:N-M`で書き、複数の範囲は範囲ごとにパスを書き直す。複数のファイルは各パスを読点・`・`・空白で区切り、スラッシュでつながない。テスト名の角括弧の中のパスは試験の入力名として扱われ所在を確かめないため、根拠の所在とするファイルは角括弧の外へ書く。雛形の次の操作と参照を解決できない診断も、同じ形式を例とともに示す
- 同じ参照を複数行で共用する場合は、参照のどこで何を観測したかを行ごとに書き分ける。異なるWIの異なる要求どうしで共用できるのは、具体的なテスト名と成功結果を持つ根拠だけとする
- 確認コマンドは行の識別情報（対象単位の名前、行の標識、条件文・要求原文の再掲）を除いて根拠を比べ、識別情報だけを変えた同じ根拠の写しを拒否する
- 根拠の比較では、ファイル参照の行位置・見出し、テスト名付き成功結果、commit参照を保護し、その外の番号を正規化する。番号はUnicodeの数値属性を持つ文字の連なりと、前後が同じ文字種に接しない1文字の英字（全角を含む）・片仮名とする
- 番号付きのラベル句は、文頭か区切りの直後にあり、平仮名を含まない語、任意の連結記号、番号の順に並んで区切りか文末で終わる句として除く。空の括弧と連続した区切りをまとめ、本文末尾の句点・読点・空白も除いて比べる
- 平仮名を含むラベル句と、番号の定義に当たらない平仮名・漢字1文字のラベル（`い`・`甲`など）は意味の判定へ残す。コマンドが受理しても、各行を直接満たすかは記録の内容を読んで判定する
