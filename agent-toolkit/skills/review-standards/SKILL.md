# レビュー担当側心得

本スキルは、レビュー担当が欠陥を判定する際の知識を提供する。レビュー出力は次の完成条件をすべて満たす。

対象成果物の作成規範（スキル、又は成果物契約の明示された正本文書）を最初に全文読み、成果物契約は起草側を正本とする。
本スキルは欠陥の証拠、重大度、未検証の区別、報告形式だけを定める。
計画・設計の採用案や指摘・発見の妥当性を評価する場面では`references/judgment-details.md`を併せて読む。

## 目的との整合

- 指摘候補を報告する前に、元のユーザー目的、公開契約、適用規範、明示された入力前提と非目標を
  確認する。計画を入力契約として受け取るレビューは計画が定める実装も確認し、計画を受け取らない
  盲検系のレビューは`review_contract`を確認する。レビュー担当は各候補について、確認対象のどれへ違反するかを内部的に
  対応付け、いずれにも違反しない候補は指摘として報告しない
- 技術的に再現できる事象でも、異なる脅威モデル、入力主体、動作条件を必要とする場合は指摘しない。
  目的外の改善案や独立問題はレビュー出力へ含めない
- 重大度と検証用の入力集合は、明示された入力生成主体、信頼境界、通常入力、対象外入力、
  誤許可と誤拒否の消費主体への影響へ合わせる
- セキュリティ境界ではないUX補助へ、敵対的入力に対する堅牢性を暗黙の要件として課さない。
  明示された役割と入力前提の範囲で、目的を満たす最小の実装を評価する
- 各指摘には、元の目的、契約または適用規範の何に違反するかを1文で記す

## 全レビュー系統へ共通する観点

- 確定指摘の前に、通常運用で発生する再現経路と入力主体を示し、対象外の入力前提又は異なる脅威モデルだけで成立する候補を除外する
- 永続状態、所有権、期限、復旧経路又は互換経路の新設を求める前に、何もしない案、既存操作だけの案、局所運用案及び新機構案を比較し、単純案で十分である場合は新機構を要求しない
- レビュー対象外と明示された入力前提を欠陥の根拠にしない
- 永続状態等を要する修正方針が認可範囲を超える場合は、実装担当へ渡さず呼び出し元へ差し戻す
- ドキュメントレビューでは、正本を宣言する記述と同じ契約本文の複製が同時に残っていないかを点検する

## 完成条件

### 指摘の導出と限定

- 指摘候補は元の目的、契約、適用規範から導出し、重大な実在欠陥だけへ限定する。
  同じ違反契約又は同じ再現可能な重大欠陥が、元の目的若しくは公開契約へ影響する範囲だけを確認する。
  文字列、見出し、目的語、混在構造、接続関係だけの類似は、影響を示す証拠にならない
- 作成規範の努力目標だけへの違反は指摘しない。公開契約または成果物の機能へ影響する実在欠陥がある場合だけ扱う
- 同一の判定軸から生じる指摘は、確認できた該当箇所を1件の指摘へまとめ、
  重大度は該当箇所のうち最も高いものを採用する。
  判定軸ごとにまとめずに同じ判定軸の別箇所を後続の指摘へ残すと、
  再レビューを伴う運用では収束に要する反復が判定軸の数を超えて増える
- 指摘を確定する前に、元の目的、公開契約又は通常運用で再現する重大な欠陥への影響を確認できる範囲を
  `grep -n`等で走査する。指摘本文へ走査コマンド、一致件数、走査範囲及び未走査範囲を記録し、
  影響を確認できない類似箇所を走査範囲へ含めない
- 機械チェック（lint・format・textlint・型検査・スペル検査・補助スクリプト）で判定できる項目は扱わない。
  行数など定量項目もレビュー担当が推定算出して指摘しない
- 各指摘は対象差分・周辺コード・参照仕様を確認した確実な誤り・規約違反・欠陥のみとし、
  「調査が必要」「確認した方がよい」等の曖昧な留保のまま報告しない。
  現コードで発生しない仮定ベースの懸念、プロジェクト方針に根拠のない主観的好みは報告しない

### 根拠と重大度

- 裏付けを取得できない候補は`未検証`と明記して確定指摘から分離する
- 規範・契約への違反を報告する前に、出典の原文、適用範囲、例外条件を確認する。
  対象の実行形態、配布形態、起動経路が適用条件を満たす観測事実を指摘へ含める。
  対象への適用を確定できない候補は`未検証`へ分離する。
  原文が対象形態を扱わない場合は対象成果物の違反とせず、根拠側の適用範囲の問題として返す
- 重大度ラベルは`重大`だけを用いる。
  `重大`は要件未達、公開契約破壊、データ破損、セキュリティ欠陥、消費主体が観測する機能不全、回帰、
  実在欠陥を検出できないテスト不足及び読み手が実装・運用の判断を誤る内部不整合を指す。
  内部不整合は次の問いで判定する

> 内部不整合が読み手の実装又は運用の判断を誤らせるか。

- 表記揺れ、参照の追従漏れ、及び読者がSSOTへ到達でき判断へ影響しない派生記録とSSOTの差異は指摘しない
- 重大な実在欠陥に該当しない好みや改善余地も報告しない
- 既存規範への違反として指摘する場合は当該規範の出典（ファイル・節・原文）を引用形式で明示する。
  引用できない事項は規範違反として指摘せず、改善提案としてもレビュー出力へ含めない。
  明文範囲を超えた拡張解釈・類推適用で違反を構成せず、
  明文の対象外まで一般化した解釈に基づく望ましさは規範改訂の提案として扱う
- 指摘に示す修正方針は欠陥を解消する候補とする。
  レビュー担当は修正方針を、元のユーザー目的、公開契約、保持対象の変更を認可する記述として書かない
- 直前ラウンドの修正が原因で生じた同一箇所への指摘では、再現経路に加えて、
  当該箇所が採っている方式のままで違反した契約を満たせるかの判定を併記する。
  満たせないと判定した場合は、方式そのものの撤去又は置換を要する旨を指摘本文へ明示する
  （方式の枠内での条件追加を反復させないため）
- 構文の合法性はlint・型検査の担当領域のため指摘対象外とする。対象言語バージョンで有効化された
  新構文を学習知識との齟齬で構文エラーと判定しない。判定前に実行環境バージョン
  （`.python-version`・`requires-python`・`engines`等）を確認する

### 報告形式

- レビュー表が指定された場合は、調整主体から渡された`track`を保持し、`atk review-table validate --allow-unanswered <レビュー表>`で構造を確認してから
  `atk review-table show --track <track> <レビュー表>`で必要な行を確認し、`atk review-table add --round <ラウンド> --track <track>`で指摘を登録する。
  表の構造と正規の`track`値は`agent-toolkit/scripts/_review_table.py`を正本とし、本書へ列一覧を重複記載しない。
  行頭へ`[重大度] path:123`形式の箇所指定を付ける行内列挙は、レビュー表が指定されない場合に用いる
- 指摘は行頭に`[重大度] path:123`形式の箇所指定を付け、修正方針を簡潔に併記する。
  `指摘内容`には当該指摘が属する判定軸を1行で明記する。
  機械チェック辞書の検出語・違反パターンを再現する具体文字列は指摘文へ転記せず観点を抽象的に説明する
  - 複数箇所をまとめた指摘では代表箇所を行頭へ置き、残りの箇所を指摘本文へ列挙する
- 指摘が無い場合は本文を`指摘なし`のみとし前置き・確認過程・全体サマリーを含めない。
  最終指摘リストは1回のみ出力し、試行錯誤の中間版を含めない
- gitignore対象ファイル（`CLAUDE.local.md`・`.env`等）を根拠とする指摘は本文表現を
  抽象化した観点で書き、非公開内容を統合先の成果物へ転記しない

## 計画ファイル文脈での例外

計画ファイル本文（`~/.claude/plans/*.md`）は実装判断を記録する作業文書であり、次を指摘対象外とする。
計画の残存中は監査や再開に利用できるが、正式仕様書として継続保守する文書ではない。

- 記述形式（章構成・段落構成・表現選択・書き方・情報の配置）への指摘。
  記述間の矛盾は、実装時の判断では解消できず、計画の実施可能性又は公開契約の成立を損なう場合に限り対象に含む
- 実装時にエージェントが判断可能な細部（変数名・エラーメッセージ文言・局所的な制御フロー等）
- 件数・行番号・行数・ファイルサイズなど数値の正誤及び本文の列挙・表から導出できる件数の記載
  （レビュー担当が推定算出して検証しない）

計画レビューの指摘範囲は次のとおりとする。

- 指摘対象は、実装時の判断では解消できず計画の実施可能性又は公開契約の成立を損なう計画本文の矛盾、
  計画した変更が生じさせる欠陥、または計画を実施不能にする既存契約との不整合とする
- 類似箇所は、同じ計画変更が適用できるかではなく、元の目的、公開契約か通常運用で再現する重大な欠陥に
  同じ違反契約が影響するかで判定する。表現、見出し、目的語、混在構造、接続関係だけが共通する箇所は含めない
- 初版の成立性と独立する既存問題は計画レビューと分ける。
  同じ失敗構造に属する問題は、初版の類似見直し範囲との整合を確認して区分する
