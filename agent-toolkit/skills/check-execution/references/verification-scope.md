# 変更範囲の検証の対象選定

本書は変更範囲の検証で動かすチェックとテストを選ぶ主体（計画担当、実装担当、実行レビュー担当、計画なしで変更する主体）へ、対象を選ぶ判断基準を与える。
変更範囲の検証は変更ファイルとその直接消費側を対象にし、リポジトリ全体の検証はCIへ委ねる。全体検証の判定とpush前に実行するチェックは`agent-toolkit:commit`の`references/publish.md`「検証とCI」が定める。
直接消費側を対象から外すと、そのテストの失敗はpush後のCIで初めて見つかり、修正と再実行の往復が増える。

## 直接消費側の類型

直接消費側は、変更を読む主体を次の類型で集める。変更ファイルの近くにあるテストを探索の起点にし、変更ファイルからの参照名でたどれるかは問わない。参照名と固定文字列の検索は所在を探す補助として使い、静的な参照名だけでは見つからない接続も同じ類型で対象へ加える。

- 変更する処理を参照・importして経由する実装とそのテスト。変更する基底クラス、共通処理、共有関数を継承または経由する各実装を含む。パッケージやディレクトリの境界を越えて、リポジトリ全体から探す
- 全追跡ファイルや全ソースを走査する横断テスト（参照の実在、文字コード指定、通知文の言語などの不変条件を確かめるテスト）
- 複数の呼び出し手段（コマンド、サブコマンド、hookなど）が共有する処理と出力の契約を観測するテスト。共有の起動手段（タスクランナーのターゲット、共通スクリプトなど）を経由して起動されるテストと、共通の出力（通知、標準エラー、終了後の処理など）を期待値に持つ別の呼び出し手段のテストを含む
- 変更ファイルの内容を期待値として保持するテスト（文面、生成物、スナップショットなど）
- 変更値を別の文法で解釈するテスト（CI定義、設定ファイル、マニフェストを解析するテストなど）
- 実行中に読み直される実行ファイルと、親処理と時間上限を共有する子処理

テストの読込範囲を変える変更（pytestの`conftest.py`やfixture、テストツールの設定など）では、その範囲に属するテスト全体が直接消費側になる。

## 範囲の決め方

- 横断テストは、プロジェクト規範が識別手段（pytestのマーカーなど）と実行形を定める場合にそれで選び、変更の種類によらず変更範囲の検証へ含める
- 複数の呼び出し手段が共有する処理や出力の契約、広く使われる共通処理を変え、読む側を探索で列挙しきれない場合は、それらの呼び出し手段のテストを含む検証単位全体（パッケージ全体のテストなど）を実行する
- 名前を削除または改名する変更では、変更ファイルの外に残る参照を検出する静的解析（型チェックなど）をリポジトリ全体へ実行し、変更範囲の検証へ含める
- 変更差分からファイル集合を組み立てる指定（チェックツールの差分オプション、`git diff --name-only`の出力など）は読む側を含まない。この指定を使う場合は、読む側のテストを別の引数として加える
- 対象はファイル単位で並べる。検証単位全体（パッケージ全体のテストなど）とリポジトリ全体の静的解析は、ファイルを並べず、その範囲を指定する
- 対象は実装後の実差分から確定する。計画で対象を列挙した場合も、実装の現物と比べ、計画が挙げなかった変更ファイルの読む側を同じ類型で加える。加えない対象は、理由を検証の記録（計画では`## 要件・外部仕様`の追随範囲）へ残す

## 実行のしかた

- 初回の変更範囲の検証では、変更ファイルに適用できるチェックを全て動かす。修正後の再実行では、失敗したチェックだけに限定してよい
- 並行する別の書込主体が新しい呼び出し元を加えると結果が変わる検証（共有契約やパッケージ外の利用者を変えた変更の検証、全体を走査するチェック）は、プロジェクト規範が統合後の検証として定める場合に、統合時にも実行する
