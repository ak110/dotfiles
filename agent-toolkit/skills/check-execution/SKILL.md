# チェックの品質基準と実行・保存

検証対象の選定と結果判定に関する品質基準は、`agent-basics:check-execution`が定義する。本スキルは、対象プロジェクトのタスク定義と公開入力から実行形を選び、統合ツールの実行、計画に基づく検証の実施、実行記録の保存、および完了報告への連携手順を担当する。

## 名指し参照の読込方法

本文内の各参照における適用条件を確認し、選択した資料を読み込み、指定箇所に注目してから、その基準を用いた具体的な判断に進む。起動時の行に指定された資料は、起動時の本文とともに提供される。

## 統合実行ツール経由の起動

- 確定した計画に基づく変更範囲の検証は、計画ファイルの`## 検証`（訂正済み検証表が存在する場合はその表）に記載された各コマンドを、対象のworktree内で上から順に実行する。実行前には、コマンドの検証対象に実際のGit差分が含まれていることを確認する。途中で1件が失敗した場合も残りのコマンドを最後まで実行し、すべてのコマンドの終了コードと出力を確認して結果を総合的に判定する。検証コマンド行や訂正済み検証表の書式、引き継ぎ方法、およびpyfltrの完了検収基準は、`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「検証と公開工程」に従う。
- プロジェクトで採用されている統合実行ツール（`pyfltr`など）を利用し、対象範囲を絞り込む場合もその統合ツールに対象パスを渡して実行する。個別のツールを直接単体で起動する運用は、デバッグ、最小限の再現環境の構築、原因特定など、プロジェクト規範で明示的に認められている場面に限定する。
- チェック実行用のMCPツールが利用できる場合はそれを優先し、pyfltrにおいては`run`ツールを使用する。MCPが利用できない外部のチェックや手動での動作確認は、実行環境が提供する標準の実行機能、背景実行、および待機機能を用いて実行する。検証ログの全量を別の担当エージェントへ引き渡す場合は、自身のセッション用のmanaged-temp内に標準出力と標準エラー出力を個別に分けて保存し、終了コードと取得時点の`git rev-parse HEAD`を`検証結果`に記録する。
- 同一のOSアカウント内で同時に1プロセスのみ実行を許可する実行枠（スロット）に参加する検証処理は、先行する他の検証が完了するのを待ってから実際の処理を開始する。この実行枠に参加する対象は、pyfltrを起動するすべての手段（CLI、MCPの`run`、pyfltrを呼び出すタスクランナー、commit hookが動く`git commit`など）と、プロジェクトでこの実行枠へ参加するよう設定されたpytestプラグインを読み込むpytestである。以下の起動方法と3つの分類基準は、この対象群に限定して適用する。
  - シェルからコマンドを起動する場合は、ツール自体に組み込まれているタイムアウト機能（スロット待ち時間を除き、実際の処理時間のみに適用される）を活用し、コマンドの先頭に`timeout <秒>`を付与しない。背景実行で起動する場合は、実行ホスト側の背景実行タイムアウトを最大値にするか、他の検証による待機時間を見込んだ十分な長さに設定する。スロットの待機中は、pyfltrの`execution-slot`警告、またはpytestプラグインによる待機通知が標準エラー出力に1回出力される。
  - 待機中を含め現在実行中の検証処理は、プロセス起動時に取得した識別子と公開されている待機機能を用いて完了を回収する。同一の対象範囲に対する多重起動は避け、常に1つの実行プロセスを維持する。
  - ホスト側のタイムアウト上限によって途中で強制終了された検証は、標準エラー出力に待機通知が出ているかどうか、および最終行のメッセージを確認して、スロット待機中のタイムアウトか処理実行中のタイムアウトかを判別する。待機中のタイムアウトであれば実際のテスト処理は開始されていないため、同じ対象集合に対して初回実行として再度コマンドを起動する。
  - 処理実行中のタイムアウトであった場合は、`references/diagnostics.md`の診断および再実行の規則に従って対処し、実際の処理時間に対する上限はスロット待ち時間とは切り離して管理する。
  - 過去に保存した結果と検証対象のファイル集合は、これら3つの分類のいずれの場合であっても、変更を加えずにそのまま再利用する。
- 実際に取得したrun_id、保存したログ出力、および手動観測の記録は、完了報告の送信前確認へ引き渡す。報告する検証結果と保存ログの対応関係は、`agent-toolkit:completion-report`の`references/report-formats.md`「検証結果と実行記録」の規定に従う。

## pyfltrの起動形

- 起動形式は、対象プロジェクトのタスクランナー定義（`Makefile`、`mise.toml`のtasks、`package.json`のscriptsなど）を起点とし、対象環境の公開ヘルプやMCPスキーマで受理される入力を確認して選ぶ。プロジェクト内に明示的な定義が存在しない場合は`uvx pyfltr`を用いる。計画と訂正済み検証表には、対象到達、必要なチェックの完了、終了状態および診断を判定できる同じ選定結果を記録する。
- 実行対象のチェック項目が確定した段階で、対象版が提供する公開手段から実効設定（有効化フラグ、使用する実行ツール、実行コマンドライン、解決された実行バイナリのパス）を取得する。`command-info`を提供する版では、その公開ヘルプで入力と出力形式を確認して用いる。
- コマンドに渡した対象ファイルやカレントディレクトリ（cwd）は、実際の実行対象集合と完全に一致しないことがある。モノレポ構成では子プロジェクトへ自動展開される場合があり、設定項目（pytestの`pytest-always-targets`など）によって指定外のファイルが実行対象へ追加される場合もある。起動前に実効設定と設定ファイルの内容から実際の実行集合を見積もり、実行後は保存結果からサブプロジェクトごとの実行件数を確認する。同一の変更内容に対して同一の検証集合を重複して実行することは避け、失敗した対象のみを再確認する際は`--only-failed`オプションや`commands`による絞り込みを活用する。
- サブコマンドの使い分け、入出力フォーマット、および失敗時の再実行方法については、`pyfltr <サブコマンド> --help`やMCPツールのスキーマを参照して確認する。ドキュメントに未掲載の設定項目や導入手順については、<https://ak110.github.io/pyfltr/llms.txt>を参照する。

## 保存した実行出力の取得

出力を保存する前に、生成元ツールが公開している出力オプションを確認し、目的に合致したフォーマットと対象範囲を選択する。
保存されたpyfltrログは、対象版が提供する結果取得方法で読む。`show-run`を提供する版では、その公開ヘルプで対象・本文・構造化診断の取得方法を確かめる。別版の引数を流用せず、対象到達、必要なチェックの完了、終了状態および診断を保存結果から判定する。本文の表示だけを目的とする場合は、公開された本文表示機能を使い、不要なJSON解析を避ける。
構造化された診断情報が必要で、選んだ出力形式がJSONの場合は`jq`コマンドで読み取る。テスト結果については、完全なテスト名と結果行を取得できる形式を対象のテストツールの公開契約から選び、要求仕様と正確に対応付ける。
生成元ツールに専用の表示オプションが存在しない場合や、結果の関連付け・意味内容を評価する処理は、単なる本文ログの表示・取得処理とは明確に区別して取り扱う。
