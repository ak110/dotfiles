# 成果物へ書く事実の調査

本書は成果物、ユーザーへの報告と回答、委譲プロンプトへ書く事実主張の裏付け調査の基準を定める。対象は外部の挙動、ホスト機能の可否および規範の有無を記述の根拠にする場面とする。

## 情報源と裏付けの手段

Xの投稿本文・日時・添付写真を取得する前に、同じスキルの`references/x-posts.md`を全文読んで適用する。

二次資料の本文を有料・会員限定などの理由で一部しか読めない場合は、読める範囲の書誌・リンク・表題・著者などを手掛かりに、その資料が依拠する一次資料を探して本文を調べる。
元論文、公式発表、公式ドキュメント、公式リポジトリ、報告元のIssue、データセットなどを対象にし、結論と提案の根拠を一次資料の該当箇所へ置く。
二次資料だけの主張はその資料へ帰属させ、読めない部分を推測で補わない。
二次資料と一次資料の対応を確認できない場合は、候補を特定した根拠と対応が未確認であることを書く。
一次資料も取得できない場合は「裏付け手段の回復と前提の相違」に従う。
全文を読める二次資料と取得ツールによる出力の省略は、この取得不能の条件に含めない。

- 外部ライブラリ・SDK・外部API・実行環境の挙動は、対象バージョンの公式一次資料（公式ドキュメント、公式ブログ、CHANGELOG、公式リポジトリのソース、MDN、RFCやWeb標準などの仕様書）を先に確かめて裏付ける。記載が無いか不足する範囲は実機再現と実装の読解で補い、補った範囲を成果物で区別する。実機再現と実装の読解だけで結論づけてよいのは、公式一次資料に記載が無いと確かめた範囲に限る。挙動の因果は実機再現で確かめ、出所の記述と異なる場合は観測事象を保って因果を実装挙動へ揃える
- 提供元が暗号化して返す値や、解釈せず送り返す用途だけを定める値（暗号化された思考、署名など）は、公式一次資料が定める判別条件か、値を開かずに観測できる項目で判別する。デコードや内部構造の解析は、ホスト本体がその値を解析している場合も判別の手段から外す。どちらの手段も無ければ判別不能と成果物へ書く
- 低コストの実行1回で確定できる主張（正規表現の一致・終了コード・件数など）は実行結果で裏付け、成果物へ転記する集計値には集計コマンドと出力を併記する
- 外部コマンド・ツール・MCPツールの手順を成果物へ書く前に、受理パラメーター・省略時の動作・相互制約を確かめる。手段はヘルプ出力、公式リファレンスまたはツールスキーマ（`ToolSearch`での照会を含む）など実行を伴わない照会とする（努力目標）
- WebFetchは要約モデルを経由するため、外部資料の逐語引用は同じURLの生データをmanaged-temp（`agent-toolkit:managed-temp`）へ保存し、その本文から引用する

## 不在の主張

- 不在の主張（非推奨・廃止・唯一・取得できない・該当箇所が無い、hookが発火しない、文書や設定が定めない等）は、使った観測が対象を捉える範囲を確かめてから書く。ツールが通知した上限、自分で付けた切り詰め（`head`・`cut`・件数の指定など）、記録やログが残る条件（出力を返さない実行を記録しない記録など）、検索の対象外のパスや項目は範囲を狭める。範囲内の観測は範囲内の結論としてだけ書き、範囲外の不在は公式一次資料の明示記載・機能一覧・網羅的な検索・実機実行のうち適した手段で確かめてから書く

## 裏付け手段の回復と前提の相違

- 依頼が参照する外部資料を代替手段でも取得できない場合は`agent-toolkit:user-confirmation-and-report`の`references/pending-decisions.md`「未確定判断の保留と暫定判断」に従う
- コマンドの未導入や認証の失効で裏付けられない場合は、導入、再認証または別手段で回復できるかを先に確かめ、ユーザーの操作か承認が要るならユーザー確認する。手段の不在は、規範・スキル・手順書と対象プロジェクトの参照先も確かめてから結論にし、導入状態を根拠にする場合は`command -v`などのコマンドと結果を併記する
- 依頼・AWI・引き継ぎ資料の観測値と自分の測定値が一致しない場合は、差が生じる条件を設けて追加で測り、矛盾を解消してから前提の成否を確定する
- 作業環境の性質（本番か検証か、実データの有無）を前提にする場合は、ユーザーの記述か構成（composeのprofile、環境変数、ホスト名など）で確かめる
- 依頼の前提が事実と異なると判明した時点で、調査を続ける前に報告する
- 既存の記述が前提とするホスト機能や実行環境の挙動と異なる観測を得たら、公式一次資料の明示記載か実機再現で条文の失効を確定できるか判定する。確定できれば調査したエージェントが`agent-toolkit:bugfix`を起動し、`agent-toolkit/skills/bugfix/SKILL.md`「問題を見つけたときの対処」に従って是正するか改訂を提案する。ユーザー確認するのは、確定に要る観測がユーザーの環境か資料でしか得られない場合と、是正が`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「認可を要する操作」に当たる場合であり、観測事象、条文の位置および再検証手段を添える。確定できない場合は条文を維持し、相違と再検証の手段を`agent-toolkit/rules/01-agent.md`「完遂と先送り」の方法でWIへ残す

## 根拠と主張の一致

入力の条件一致には、値の形に加えて、入力を生成する主体と消費側までの変換・送出経路を含める。
生成経路を省いた手製入力の検証が保証するのは実際に通した範囲であり、実経路との同等性を確かめた範囲だけを、その経路の到達・結果の根拠へ使う。
この判定は原因の主張、正常性、対応済みの判断、対象の除外や採用案の成立を左右する前提にも適用する。
SDKの例外生成、パーサー、フレームワークの応答変換などで、生成側が消費側へ値を渡す前に例外を送出する経路も確かめる。

- 公式一次資料と対象の実装（コード・設定・ログなど）のいずれからも裏付けられない事実主張は、実際に動かして確かめるか、`agent-toolkit/rules/01-agent.md`「確認を要する事項」で確定するか、未確定と明示する。対象は症状、原因、意思決定の経緯、数値の根拠、過去の挙動、運用背景、仕様の意図を含む
- 根拠と主張は対象・集約粒度・実行環境を一致させる。全体の観測（ロードアベレージ、メモリー使用量、接続数など）から特定のプロセスへ原因を帰属させるときは、観測値を生成した主体を実際に測る。既存の項目やAPIの戻り値を新しい用途に使うときは、書き込む箇所と更新の契機を実装から確かめる。そのうえで用途が求める粒度（session単位かturn単位か、作成時か最終更新時かなど）と一致させる。異なるplatform・runtime・ホスト・実行手段の観測は、同等性を確かめた範囲だけ根拠にし、残る条件差を明示する。サービスの稼働は、サービス名かプロセスを起点に実効の待受ポートやソケットを対応付けて確かめる
- 出所へ帰属させる主張: 他の主体の報告、セッション記録、ツール出力、以前に読んだ内容の記憶を出所として主張を書く場合は、出所が明示する内容だけを出所へ帰属させる。出所が明示しない主体（実行した担当）、時点、条件、結果、因果を手掛かり（パス、コマンドの引数、ツールの戻り値の文言、記憶した要旨など）から補った部分は、書き手の推定として分けて書く。帰属させる内容は書く時点で出所の該当箇所（報告の本文、記録位置の全文と記録の由来、実装）と照らし、読めない場合は未確認と書く。
  この定義は記述先（ユーザーへの報告と回答、委譲プロンプトと追送、WI投入担当への要求、計画、WI本文、完了報告と中継）によらず適用する。補いの典型は、観測していない時点の結果を報告の要旨へ足すこと、ツールの戻り値の文言から画面への表示を観測した事実とすること、記録の識別子や要約から実行主体を推して記録の内容とすることである

## エージェント向け文書の技術的条文

- 現物の観測を根拠にエージェント向け文書の技術的条文（外部ライブラリ、実行環境、外部コマンドなどの挙動）を新規に書くか改訂する場合は、観測事象を条文へ書き、観測の記録を条文を保持するリポジトリの`docs/development/audit-records.md`へ残す。
  記録には観測した日付（再現条件として）、観測した版数および再検証手段の3項目だけを書き、見出しは`<ファイルパス>：<節名>：<日付>`とする。条文には観測した環境やモデルの版数を書かず、条文の末尾へ記録の所在を示す1文を置く。適用範囲を定める対象の版（参照資料冒頭の対象バージョンなど）は条文へ書く。
  常時規範（`agent-toolkit/rules/`配下と`agent-toolkit/share/rules-*.md`）では全エージェントの読込量を抑えるため記録の見出しだけを索引とする。条文を移したら見出しのファイルパスと節名を移動先へ直す。
  再検証が条文と異なる結果を示した場合は再現条件をそろえて再検証し、そろえられない条件差を記録する。失効はそろえた再検証の結果で判定する。
  エンドユーザー向け文書、README、設定ファイル、コードのコメントと、ユーザーの指示に由来する規範、運用手順、確認の選択肢の説明は対象外とする。既存の記述は現行のまま扱う（努力目標）。ただし既存の条文の誤りがQに影響する場合の是正の要否と範囲は、この限定によらず`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「QとC・Dの区別」「類似見直し」に従う

## 実行結果の検証

- 事実、推論、評価、仮説を分け、名前のある機構を原因に挙げる場合はその関与を現物の観測で確かめる。規範に判定区分がある語（採用、合格、完了など）は、その区分を実際に判定してから使う
- 副作用の有無は、変更対象の実体で確かめる（失敗した操作も途中まで変更を残す）
- 共有状態を扱うホスト・ツールやエージェントCLI（`claude -p`、`codex exec`など）を実際に動かして調べる場合は、公開された状態隔離手段（`CODEX_HOME`など）の適用範囲を確かめ、必要な状態だけをmanaged-tempへ隔離する。隔離の成立は入力を設定した事実から推定せず、消費側が実際に使う読込先・書込先を公開の解決手段（設定の解決値を出力するコマンドなど）で取得し、実データへの最初のアクセスより前に期待する検証領域と一致することを判定する。誤った変数名や、ホームを差し替えても直接指定の保存先が継承される場合もこの判定で検出する。副作用には、起動したエージェント自身のシェル・ファイル編集・MCP経由の送信も含める。実在のセッションの再開・分岐（`--resume`・`--continue`・`--fork-session`、`codex exec resume`など）と、記録から取り出した実際の作業指示の実行は元の作業を続ける。その実行は元のmanaged-temp・委譲先・WIキューなどの共有資源へ作用し得るため、ツールの挙動を調べる場合を除いてツールを外す。Claude Codeでは`--tools "" --strict-mcp-config --mcp-config '{"mcpServers":{}}'`を組み合わせる。ツールを外す必要があるCodexの調査で同等の公開された除外手段を確認できない場合は、実在セッションを再開・分岐せず、実際の作業指示も実行しない。保存記録の照会と公式一次資料で調べる。使えるツールと権限は1回目の実行記録で確かめてから複数実行へ展開する。Claude Codeではstream-jsonの`system`イベントの`subtype: init`にある`tools`・`mcp_servers`・`permissionMode`を読む。無副作用かは観測で判断する。`--allowedTools`は確認なしで実行できるツールの指定であり、ツールを制限しない。`codex --ephemeral`はセッションの永続化を抑えるが、ChatGPT認証の更新と`auth.json`への保存は抑えない（トークンの期限が5分以内、または最後のrefreshから8日を超えると更新して保存する）。隔離環境で認証できない場合は通常の認証解決を保ち、共有実体のmtimeなどの変化を観測して副作用を報告する。Git作業ツリー外の認証情報を隔離先へ複製せず、委譲先は`share/rules-subagent.md`「作業ツリーと認証情報の扱い」に従う。隔離の追加はこの調査に限り、通常利用と既存のテスト隔離は現行のまま保つ。監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/writing-standards/references/investigation.md：実行結果の検証：2026年10月9日」にある。追加の監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/writing-standards/references/investigation.md：実行結果の検証：2026年10月18日（1）」にある
- 応答内容を使わない実機確認・対照・識別子の観測のためにエージェントCLI（`claude -p`、`codex exec`など）や`agents_server`の委譲を起動する場合は、検証対象がモデル・effort・設定・ツールに依存しない限り、最安段位のモデルの別名とeffort `low`を指定する。モデルは版付きの旧IDへ固定しない。`agents_server`では`model_type`に`claude:haiku/low`か`codex:luna/low`を渡す。検証対象が`delegate`・`task`の起動そのものでない限り、軽量起動の`explore`か`shell`の`mode`で起動する。CLIを直接起動する場合はセッションを保存せず、設定・ツール・MCPを読まず、最小のシステムプロンプトで起動する。Claude Codeでは`--model haiku --effort low`に`--no-session-persistence --setting-sources "" --tools ""`を付ける。さらに`--strict-mcp-config --disable-slash-commands --system-prompt <文>`も付ける。プロンプトは`--`の後ろへ置く（`--tools ""`が後続の位置引数を値として消費する）。`--bare`はOAuth認証を読まない。Codexでは`-c model_reasoning_effort=low --ignore-user-config --ignore-rules`を付け、記録が不要なら`--ephemeral`も付ける。`codex exec`はChatGPT認証で系列名`luna`を拒否するため、直接起動では`luna`系列の最新の完全IDを指定する。起動回数は判定に必要な最小にする。監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/writing-standards/references/investigation.md：実行結果の検証：2026年10月18日（2）」にある
- 負荷に依存する値は、同じホストで重い処理を止めてから測る。ユーザーしか観測できない適否は実装の完了を報告し、評価は事後承認へ回す
- 独立した複製で比較条件を多数へ展開する調査では、展開前に代表条件で、資料と関連資料の取得、対象版と入力の対応、判定コマンドの起動まで成立することを確かめる。複製には主入力、消費側がたどる関連資料と対象リポジトリの識別を含める。対象の未達と、環境不備による判定不能を分け、後者を比較結果へ混ぜない
- 次のセッションでも変更を使えるかは、保持branchから実行時の読込元までの配布と反映の流れ（再起動や自動更新の契機を含む）で確かめる
- 操作の完了と成功は、開始・受理の観測と区別し、終了状態を定める主体の観測で判定する。観測前は進行中または未確認と書き、主体を観測できない場合は対象と不足条件を報告する
