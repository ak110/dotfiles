# 成果物へ書く事実の調査

本書は成果物へ書く事実主張の裏付け調査の基準を定める。本書の対象は外部の挙動、ホスト機能の可否及び規範の有無を成果物の記述の根拠にする場面とする。

- 外部ライブラリ・SDK・外部API・実行環境の挙動を成果物へ書く場合は、対象バージョンの公式一次資料と実機再現で裏付ける。
  裏付けが出所の記述と異なる場合は、観測事象を保ちつつ因果の記述を実装挙動へ揃える。
  誤った一般則は、以降の全判断を誤った前提の上で確定させる
- 選択肢または手段の不在を述べる主張（非推奨・廃止・唯一・取得できない・該当箇所が無い等）は、
  公式一次資料の明示記載・機能一覧・網羅的な検索・実機実行のうち対象に適した手段で不在を確認してから書く
- 依頼が参照する外部資料を対象に適した代替取得手段でも取得できない場合の扱いは「協調と自律」が定める
- 裏付けに用いるコマンドの未導入、認証の失効などにより現物を観測して裏付けられない場合は、導入、再認証又は対象に適した別手段で裏付け手段を回復できるか確認する。
  回復にユーザーの操作が必要な場合と承認が必要な場合はユーザー確認する。
  手段の不在と裏付け不能の結論は、回復可否を確認した後に確定する。
  一時的な実行手段の不足は、対象に適した裏付け手段の不在とは別の事象である
- 低コストの実行1回で確定できる主張（正規表現の一致・終了コード・件数など）は実行結果で裏付ける。
  成果物へ転記する集計値には、集計コマンドとその出力を典拠として併記する
- 依頼・AWI・引き継ぎ資料が挙げる観測値と自分で測った値が一致しない場合は、差が生じる条件を意図的に設けて追加で測り、矛盾を解消してから前提の成否を確定する。
  条件差と環境差による説明で依頼側の主張を維持したまま記述すると、成果物が技術的に成立しない
- 依頼の前提が事実と異なると判明した時点で、以降の調査を続ける前にその事実を報告する
- 権威ある情報源は公式ドキュメント・公式ブログ・CHANGELOG・MDN・Web標準とする
- 既存の記述がホスト機能や実行環境の挙動を前提とする場合、前提と異なる観測を得た時点で、
  公式一次資料の明示記載・実機再現のいずれかで条文の失効を確定できるかを判定する。
  確定できる場合は`agent-toolkit:bugfix`の`references/response.md`に従って自ら是正するか改訂を提案する。
  条文の失効を確定できない場合と、是正が`agent-toolkit:confirmation-and-uwi`の`references/judgment.md`「認可を要する操作」
  （公開インターフェース変更・破壊的操作・エンドユーザー向け画面・文書・通知の変更など）に当たる場合だけユーザー確認する。
  確認には観測事象、条文の位置及び再検証手段を添える。同一セッション内で扱いを確定できない事項は「完遂と先送り」が定める方法で登録する。
  失効した前提のまま条文を適用すると、以降の判断が誤った前提の上で確定する
- 後続の判断を拘束する規範文書の技術的条文を、現物を観測した結果を根拠として新規に記述又は改訂する場合は、観測事象を条文へ書き、その観測の記録を条文を保持するリポジトリの`docs/development/audit-records.md`へ残す。
  記録の見出しは条文のファイルパスと節名で構成する。記録する項目と、条文の末尾へ置く索引の1文は`references/agent-documents-additions.md`「規範追記時の判定」が定める。
  本項の対象は、外部ライブラリ、実行環境、外部コマンドその他の対象の挙動を現物の観測で確かめた規範文書の技術的な条文に限る。
  利用者向け文書、README、設定ファイル、コードのコメントは対象外とする。
  ユーザーの指示に由来する規範、運用手順及び確認の選択肢の説明も対象外とし、これらは観測事象を伴わない文面のまま置く。
  記録する3項目へは、観測した日付を再現条件として書く。条文を記述した日付、条文を導入した経緯、セッションの識別子は記録の対象の外に置く。
  再検証が条文と異なる結果を示した場合は再現条件をそろえ、そろえられない条件差を記録する。条文の失効は、再現条件をそろえた再検証の結果で判定する。
  本項は新規の記述・変更箇所へ適用し、既存の記述へ遡及適用しない（努力目標）
- 成果物へ書く事実主張のうち、公式一次資料と対象の実装（コード・設定・ログなど）のいずれからも裏付けを得られない事項は、実際に動かして確かめるか、「確認を要する事項」の手順で確定するか、未確定である旨を成果物へ明示する。
  対象には、症状、原因、意思決定の経緯、数値の根拠、過去の挙動、運用背景及び仕様の意図を含める。
  推測で補った記述は、裏付けを持たないまま以降の判断の前提となる
- 根拠と事実主張は、対象・集約粒度・実行環境を一致させる。全体の観測から一部や構成要素を主張する場合は、
  観測値を生成した主体を実際に測り、その主体が主張の対象に属することを確定する。ロードアベレージ、メモリー使用量、
  接続数などの資源総量から特定のプロセスや処理へ原因を帰属させる場面も同じ扱いとする。
  総量や全体の値を測定済みである事実は、一部への帰属を導く段の裏付けの外に置く。
  異なるplatform、runtime、ホスト、実行手段の観測は、対象環境との同等性を実際に確かめられた範囲だけ根拠に使う。
  条件差が残る場合は、その差と未確定の範囲を成果物へ明示する。
  標準ポートだけを対象とした待受一覧のように範囲を限定した観測は、その範囲の観測としてだけ説明し、範囲外は未観測として扱う。
  サービスの稼働は、サービス名又はプロセスを起点に実効の待受ポートやソケットを対応付けて確かめる。
  対象・粒度・実行環境のずれた根拠は無関係な主体や条件を原因として提示し、以降の調査を誤った対象へ向ける
- 操作の開始・受理・関連状態の観測を、操作の完了を示す根拠として用いない。終了状態を定める主体で完了を観測する前は、
  進行中または未確認の状態として書く。未完了の操作を完了形で記録すると、後続の主体が残る工程を実行済みとして省く
- WebFetchは要約モデルを経由するため、逐語引用の根拠には保存した生データを用いる。
  外部資料を逐語で引用する場合は、同じURLの生データを`atk managed-temp`で作成した管理対象一時領域へ保存し、
  保存した本文から該当箇所だけを引用する。
  要約経由の本文は原文と一致せず、引用の同一性を検証できない。
  要約、要点の抽出及び引用を伴わない読解を目的とする取得は本項の対象外とする

## 実行結果の検証

- 事実、推論、評価、仮説を分け、原因を名前のある機構で説明する際はその事象への関与を現物の観測で確かめる。未確認なら観測した値と条件を書く。採用、合格、完了など、規範に判定区分がある語は、その区分を実際に判定した後に使う。
- 手段の不在を結論にする前に、規範、スキル、手順書と対象プロジェクトの参照先を確認する。導入状態が根拠なら、`command -v`などの実行結果とコマンドを同じ記述へ併記する。
- 操作が副作用を残したかは、変更対象の実体で確かめる。操作の失敗も途中まで変更を残すため、終了コードだけで副作用の不在を結論にしない。
- プロジェクトのコードは、そのプロジェクトが定める品質チェックの手順で検証する。完了と成功は終了状態を定める主体で観測し、警告が残る場合は原因と影響を調べる。主体を観測できない場合は対象と不足条件を報告する。
- 負荷に依存する値を測る間は、同じホストで重い処理を並行させない。ユーザーしか観測できない適否は実装の完了を報告し、評価は事後承認の手続きへ回す。
- 次のセッションでも変更を利用できるかを説明する際は、保持branchから実行時の読込元までの配布と反映の流れを確認する。その流れに再起動や自動更新が含まれる場合は、その契機も確認する。
