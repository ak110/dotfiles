# 機械チェックスクリプトの設計原則

エージェントが反復実行する機械チェックスクリプト（`check_*.py`など、計画ファイル・エージェント向け文書に対するチェック全般）は、出力がエージェントのコンテキストへ蓄積されるため、ノイズの抑制と起動回数の削減を設計段階で担保する。

自動チェックを追加するのは、入力が構造化され期待値が一意であり、判定が安定して違反時の是正方法を一意に示せる場合に限る。
自然言語の意味、責務の妥当性、命令性など、複数の正当な解釈がある対象は作成規範とレビューで扱う。

## 出力の簡潔さ

- 成功時（違反なし）はexit 0とし、出力を省く（出力を省く部分は努力目標）
- `error`区分の違反は`stderr`へ該当箇所、要点と修正方法だけを出力してexit 1とする。`warning`区分は`[warn]`などの識別子付きで`stderr`へ出力し、exit codeへ算入しない。修正方法と、行動を要する警告の次の操作は`writing.md`「読み手別の追加注意点」のプログラムが出力するメッセージの項目に従う
  - 複数の条件をまとめて判定する違反では、成立しなかった条件と比べた値（期待値と実際の値）を要点に含める
  - 複数の種類の違反を出力するチェックでは、違反を生成する箇所が種類ごとの修正方法を持ち、出力に現れた種類の修正方法だけを1回ずつ出力する。共通の修正方法へ種類ごとの対処を足すと、現れない種類の対処が毎回含まれ、新しい種類の対処の欠落にも気付けない
- 引数誤用・対象ファイル不在・権限不足・不正なエンコーディングなど、チェックを開始できない実行前エラーはexit 2とし、違反（exit 1）と区別する（努力目標）
- 外部コマンド（textlintなど）の生出力を転記せず、構造化出力をパースして違反件数と該当箇所へ要約する

## 起動の統合

- 同一契機で反復起動される複数の独立スクリプトは、1プロセスへ集約する（努力目標）

## 構造化文書の解析

Markdownなどの構造化文書をチェックする場合は、構造認識と原記法のチェックを分離する。
設計の詳細は`agent-toolkit/agent_toolkit/_plan/structure/__init__.py`のモジュールdocstringを参照する。

## チェック項目のerror・warning区分

- `error`区分は、チェック対象の成果物が成立しない問題（パス・スキル名・節見出しの実在確認失敗など）に限る
- 体裁・表記系（textlint・markdownlint・typos・口語表現など）は`warning`に限る（体裁の修正待ちで成立している成果物の確定を止めないため）
- 新設チェックの区分の判定根拠はスクリプトのdocstringへ書く（努力目標）
