# 機械チェックスクリプトの設計原則

エージェントが反復実行する機械チェックスクリプト（`check_*.py`等、計画ファイル・エージェント向け文書に対する
チェックスクリプト全般）は、出力がエージェントのコンテキストへ蓄積されるため、
ノイズの抑制と起動回数の削減を設計段階で担保する。

自動チェックは入力が構造化され、期待値が一意な場合だけ追加する。
仕様変更以外では判定が安定し、違反時の是正方法を一意に示せることも条件とする。
自然言語の意味、責務の妥当性、命令性など、
複数の正当な解釈がある対象は作成規範の契約とレビューで扱う。

## 出力の簡潔さ

- 成功時（違反なし）はexit 0とし、出力を省く（出力を省く部分は努力目標。成功時の出力は違反の有無を確かめるために読む手間とコンテキストを費やすため）
- `error`区分の違反時は`stderr`へ該当箇所と要点、および修正方法のみを出力し、exit 1とする。
  修正方法の書き方は`writing.md`「読み手別の追加注意点」のプログラムが出力するメッセージの項目に従う。
  `warning`区分は`stderr`へ`[warn]`等の識別子付きで出力しexit codeへ算入しない。
  受け取る側の行動を要する警告には、同じ`writing.md`の項目に従って次の操作を添える
  （区分の判定基準は`チェック項目のerror・warning区分`節を参照する）
- 引数誤用・対象ファイル不在・読み込み権限不足・不正なエンコーディングなど
  チェックを開始できない実行前エラーはexit 2とし、チェック違反（exit 1）と区別する。
  呼び出し側が「チェック対象の内容に問題がある」と「チェックする前提条件が満たせない」を
  判別できる状態を保つ（努力目標。呼び出し側が内容違反と前提不成立を判別できるようにする）
- 外部コマンド（textlint等）の生出力をそのまま転記せず、違反行のみへ要約する
  （JSONL等の構造化出力はパースして違反件数・該当箇所のみ提示する）

## 起動の統合

- 同一契機で反復起動される複数の独立スクリプトは、1プロセスへ集約する
  （努力目標。起動ごとのプロセス生成と初期化がその件数だけ積み上がるため）

## 構造化文書の解析

Markdownなどの構造化文書をチェックする場合は、構造認識と原記法のチェックを分離する。
設計の詳細は`agent-toolkit/agent_toolkit/_plan/structure/__init__.py`のモジュールdocstringを参照する。

## チェック項目のerror・warning区分

- `error`区分（exit codeへ算入）は、チェック対象の成果物が成立しない致命的な問題の検出に限定する
  （パス・スキル名・節見出しの実在確認失敗等）
- `error`区分に含める項目は、チェック対象の成果物の成立可否に影響するものに限る
- 体裁・表記系（textlint・markdownlint・typos・口語表現等）は`warning`出力に限定し、
  exit codeへ算入しない
  （体裁の指摘で成果物の成立を止めると、成立している成果物の確定が体裁の修正待ちになるため）
- 新設チェックを追加する場合、`error`・`warning`区分の判定根拠をスクリプトのdocstringへ明記する（努力目標。区分を見直す読み手が根拠をたどれるようにするため）
