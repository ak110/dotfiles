# 文字エンコーディングの詳細

日本語環境（Windows／Linux混在）で開発する際の陥穽と対処を示す。

## 基本原則

- 入出力境界でエンコーディングを明示し、内部処理はUTF-8を基本とする。日本語WindowsのACPはCP932であり、ランタイムの自動選択に依存すると文字化けや例外が起きる
- 生データを復元する用途では、ライブラリのフィールドにプラットフォーム依存の暗黙加工が含まれ得るため、未加工のフィールド／APIが別にないかを確認する
- バイト長と文字数（コードポイント数・書記素クラスター数）を区別する
- BOMは読み込み時に有無の両方を許容し、出力時は付けない（Excelに渡すCSVなど対象側が要求する場合を除く）

## 日本語テキストの自動判定順序

入手元の情報で決められない場合は、BOM検出→ISO-2022-JPのエスケープシーケンスの整合性検証→UTF-8での厳格なデコード→EUC-JP・CP932の順で判定する。
ISO-2022-JPはASCII系バイト列でUTF-8の厳格なデコードにも成功するため、UTF-8より先に検出する。

## ZIPファイル名の扱い

General Purpose Bit FlagのBit 11がセットされていればUTF-8でデコードする。
未設定時の仕様上の基本はCP437であり、作成元が日本語Windowsなどである根拠がある場合だけCP932をフォールバック候補とする。Info-ZIP Unicode Path Extra Fieldなどの補助情報も確認する。

Pythonの`zipfile.ZipInfo.filename`は`_sanitize_filename`を経由し、Windowsでは`\`が`/`に置換されるため、CP932の2バイト目に`0x5C`を含む文字（ソ・ポ・表など）を往復復元できない。生バイト列の復元には`orig_filename`を使う。

## Unicodeの比較と安全性

- 比較・検索・一意性判定のキーはドメイン要件に応じてNFCなどで正規化する。認可・識別キー・パスワードでNFKCを使うと、合字・互換文字経由のバイパスを許す恐れがある
- 大文字小文字の畳み込みはNFCで正規化してから`casefold`を適用する
- HFS+はApple変種のNFD相当でファイル名を保存し、APFSは正規化形式を保持するため、ファイルシステム・API境界をまたぐ比較では正規化形式の差を考慮する
- Bidi制御文字（Trojan Source）・ゼロ幅文字・ホモグラフは、ソースコード・識別子・ユーザー入力・ログで禁止または警告する

## 書込ツールの改行・BOM保全

ホストの書込ツールごとの改行・BOM・文字コードの扱いと、CRLF・BOM・非UTF-8のファイルを作成・編集する共通の手段を「書込ツールの改行・BOM保全」と呼ぶ。
EditとWriteが要求する読取状態は`file-editing.md`「ファイル更新時の編集ツールの前提」が定める。

- Claude CodeのRead・Edit・WriteはUTF-8を前提とし、非UTF-8（CP932など）のファイルを直接扱えない
- EditはCRLF改行とUTF-8 BOMを維持するため、既存ファイルの編集にはEditを使う
- Writeは常にLF改行・BOMなしで書く。CRLFやBOMを要するファイルをWriteで書いた場合は改行とBOMを復元し、新規作成はBash経由で改行とBOMを明示して書く
- 非UTF-8のファイルは、`iconv -f <元の文字コード> -t utf-8`でUTF-8へ変換してReadで読んでからEditで編集し、`iconv -f utf-8 -t <元の文字コード>`で戻す（新規作成もUTF-8で書いてから戻す）。文字コードの往復が不要な編集は、Pythonで置換前後を元の文字コードで符号化してバイト列を置換し、行末のCRLFも維持する
- `.gitattributes`の`eol=crlf`の管理対象は改行だけである（BOMの復元は対象外）
