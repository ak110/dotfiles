# LLM口調

論点を増やさず装飾として用いる型を排除する。
術語・概念を議論や説明に使うこと自体は対象外とする。

## 予告と総括

主張内容を述べずに姿勢・構成を宣言する前置きや言い換えだけの結びは、
主張そのものを直接書くことで代替できる。

```text
悪い例: 重要なのは、テストを設計段階から考慮することである。まとめると、境界値を外さないことが大切だ。
書き換え: テスト設計は実装前の仕様策定段階から開始する。テストケースは境界値を網羅する。
解説: 「重要なのは〜である」は姿勢の宣言であり主張を含まないため削除する。
「まとめると」が直前の言い換えとして機能する場合はその文ごと削除する。
```

## 正面から系

中身の代わりに対象への取り組み姿勢を宣言する型は、
対象範囲を具体化した記述に置き換える。

```text
悪い例: エラー処理を正面から扱う。例外設計の問題を正面から回収する。
書き換え: 呼び出し側の想定外入力を起点とする例外クラスの設計方針を示す。
解説: 「正面から扱う」「正面から回収する」は扱う内容を示さない姿勢宣言のため、
対象範囲と述べる内容を具体化した文に置き換える。
```

## 空虚な形容

中身を述べずに強調や概観だけを示す形容詞類は、
観点と帰結を具体化した記述に置き換える。

```text
悪い例: 不可欠な性能改善として、キャッシュ戦略が核心的な役割を担う。
書き換え: キャッシュを導入するとDBクエリ回数が減少し、レスポンスタイムが短縮される。
解説: 「不可欠な」「核心的な」は改善の内容や帰結を述べない形容のため、観測可能な指標と因果関係で記述する。
```

```text
悪い例: 本UIは直感的に操作できる。
書き換え: 本UIはメニューを2階層に抑え、主要操作を1クリックで完了する構造とする。
解説: 「直感的」は読者ごとに解釈が異なる形容のため、観測可能な構造（階層数・操作ステップ数）で記述する。
```

## 空虚な動詞

何をどう記述したかを示さず終わる動詞類は、
述べる対象と内容を具体化した動詞句に置き換える。

```text
悪い例: APIのレスポンス仕様について深掘りする。認証エラーの挙動に触れる。
書き換え: APIのレスポンスボディの構造とステータスコードの対応を示す。
解説: 「深掘りする」「触れる」は何を述べるかを示さないため、具体的な対象を明示した動詞句に置き換える。
```

## 接続の型

新情報を持たない接続表現の連打は、複数の事項を1文に集約することで代替できる。

```text
悪い例: 設定において、タイムアウト値を指定する。また、リトライ回数を指定する。さらに、ログレベルを設定するという側面から挙動を変更できる。
書き換え: タイムアウト値・リトライ回数・ログレベルの3項目を設定ファイルで指定する。
解説: 「において」「また」「さらに」「という側面から」で分割した各文が独立情報を持たない場合は、1文へ集約して接続表現を削除する。
```

## 弱い緩和と称賛

根拠のない述部で主張を弱めたり、観測値を持たない強調語で記述を膨らませたりしない。
推量・仮定・読者の疑念を示す場面では不確実性を示す述部を保持する。

```text
悪い例: バリデーションを追加すると、非常に安全になると言えるだろう。
書き換え: 入力バリデーションを追加すると、不正値による処理中断を防止できる。
解説: 「非常に」は観測値を持たない強調語のため削除する。「〜と言えるだろう」は根拠のある判断を弱める述部のため「〜できる」に置き換える。
ただし推量・仮定・読者の疑念を表す場面では「かもしれない」「だろう」を保持して不確実性を示す。
```

## 翻訳調・英語統語

無生物を主語に据えて分析系の他動詞で結ぶ構文は、判断した主体と根拠を文面から消す。
直訳調の説明構文と推量述部の重ね掛けも同じく、確定している内容を確定していない形で提示する。

```text
悪い例: この結果はキャッシュ層の不足を示唆している。ログの差分が問題の所在を物語っている。
書き換え: キャッシュ層が不足していると判断した。根拠はログの差分で、キャッシュミス率が起動10分後に80%へ達した。
解説: 「示唆している」「物語っている」は無生物を主語に立てる分析系他動詞のため、判断した主体と観測値を明示した文へ置き換える。
```

```text
悪い例: 本設定が必要な理由は、それが再実行時の整合性を担保するという点で重要だからではないかと思われる。
書き換え: 本設定は再実行の開始時に中間ファイルを削除する。削除しない場合は前回の出力が残り、結果が変わる。
解説: 「それは〜である。なぜなら〜だ」型の2文構成と「〜という点で重要」は英語構文の直訳形のため、動作と帰結を1文ずつで書く。
「〜ではないかと思われる」は推量述部を二重に重ねた曖昧化のため、確定している内容は断定で書く。
```

## 定型の結び・呼び掛け

節や文書の末尾に置く結論の押し付けと、読者へ行動を促す締めの定型句は、判断材料を増やさない。
規定は拘束力を読み取れる形で言い切り、呼び掛けは削除する。

```text
悪い例: 以上の理由から、本方式が最適であると言えます。ぜひ導入してみてください。
書き換え: 本方式を採用する。既存方式より再実行1回あたりの所要時間が30秒短い。
解説: 「〜と言えます」は結論を押し付ける結びのため、規定として言い切る。
「ぜひ〜してみてください」は読者への締めの定型句のため削除し、採否の根拠を残す。
```

```text
悪い例: この設計には課題が残るのではないでしょうか。移行手順を次節で整理していきたいと思います。
書き換え: この設計は再実行時に同じレコードを二重登録する。移行手順を次節で規定する。
解説: 「〜のではないでしょうか」は問い掛け形で断定を避ける型のため、確定した事象を断定で書く。
「〜していきたいと思います」は意志表明で言い切りを避ける型のため、記述する内容そのものへ置き換える。
```

## 免責・予防線の定型句

適用条件を書かずに責任範囲だけをぼかす免責句は、読み手が適用可否を判定できない状態を残す。
成立条件・計測環境・出所を具体的に書く。

```text
悪い例: 環境によって結果が異なる可能性があり、一概には言えません。あくまで一例ですが、この設定で改善したという声もあります。
書き換え: 本設定はLinuxのCPython 3.12で所要時間が半減した。Windowsでは未計測とする。
解説: 「一概には言えません」「あくまで一例ですが」は適用条件を示さない免責句のため、計測した条件と未計測の範囲を明示する。
「〜という声もあります」は出所を示さない匿名の裏付けのため、観測値と観測環境で置き換える。
```

```text
悪い例: 本手法には効率が良いという側面もありますが、常に有効とも限りません。一般にメモリ消費が少ないと言われています。
書き換え: 本手法は入力が1万件を超える場合にメモリ使用量を40%削減する。1万件以下では削減を観測していない。
解説: 「〜という側面もあります」「〜とも限りません」は適用範囲をぼかす予防線のため、効果が成立する境界値で書く。
「〜と言われています」は伝聞への逃げのため、自身が観測した結果として書く。
```

## 感嘆・共感の演出

驚きや発見を挿入句で演出しても、読み手が判断に使える情報は増えない。
落差そのものを事実として書く。

```text
悪い例: 驚くべきことに、キャッシュを外すと処理が速くなった。興味深いことに、この傾向は入力が大きいほど強い。
書き換え: キャッシュを外すと処理時間が20%短縮した。入力が1万件を超えると短縮幅は35%へ拡大する。
解説: 「驚くべきことに」「興味深いことに」は書き手の感情を演出する挿入句のため削除し、差の大きさを数値で示す。
```

## 三点構成・網羅の圧力

列挙数を先に宣言すると、成立する論点を宣言した数へ合わせる操作が発生する。
数を先に決めず、根拠が成立する項目だけを列挙する。

```text
悪い例: 本方式を採用する理由は、大きく分けて3つある。速度、保守性、そして拡張性である。
書き換え: 本方式は再実行1回あたりの所要時間が30秒短い。既存の設定ファイルをそのまま読み込むため、移行作業も不要となる。
解説: 「大きく分けて3つある」は列挙数を先に確定する宣言のため削除し、根拠を示せる項目だけを書く。
数を先に宣言すると、根拠の薄い項目を数合わせで加える経路が生じる。
```

## メタ構造宣言

構成を本文で予告・自己解説する記述は、見出しと本文から読み取れる情報を繰り返す。
予告を削除し、規定・手順の内容から書き始める。

```text
悪い例: 以下の3つの観点から説明する。それぞれ順に見ていく。ここからが本題である。
書き換え: 検索フェーズはクエリを正規化してからベクトル検索を実行する。
解説: 「以下の〜から説明する」「順に見ていく」「ここからが本題」は構成の予告で内容を含まないため削除し、最初の項目から書く。
```

```text
悪い例: 見出し「キャッシュ設計の要点」の直後に、本文冒頭で「本節ではキャッシュ設計の要点について改めて整理する」と書く。
書き換え: 見出しを「キャッシュ設計」とし、本文冒頭を「キャッシュキーはリクエストURLとAuthorizationヘッダーのハッシュで構成する」とする。
解説: 見出しの言い換えを本文冒頭へ置くと同じ内容を2回書くことになるため、見出しは名詞句とし本文は具体的な規定から始める。
「改めて整理する」は自身の記述を解説する前置きのため削除する。
```

## AI偏愛語・名詞比喩・造語

根拠を伴わない抽象評価語と、道具・土台に見立てた名詞比喩は、対象の性質を述べずに価値だけを主張する。
観測できる構造・数値へ置き換える。

```text
悪い例: 本ライブラリの本質は地に足のついた設計にあり、利用側の解像度を上げる土台となる。
書き換え: 本ライブラリは入出力を関数3つに限定し、内部状態を持たない。利用側は各関数を単体で呼び出すことができる。
解説: 「本質」「地に足のついた」「解像度を上げる」は根拠を示さない抽象評価語のため、構造の記述へ置き換える。
「土台となる」は名詞比喩のため、利用側から見た具体的な機能で書く。
```

```text
悪い例: 本規範は開発フローの羅針盤であり、品質の哲学を凝縮した結晶である。
書き換え: 本規範はレビュー時の判定条件を定める。判定条件を満たさない変更は差し戻す。
解説: 「羅針盤」「結晶」は道具・造形に見立てた名詞比喩のため、文書が定める内容そのものを書く。
「哲学」「凝縮」は対象を壮大に見せる熟語のため削除する。
```
