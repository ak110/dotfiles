# LLM口調

主張、操作と結果を、読み手が判断できる形で直接書く。
例文は観点を示すための文章であり、適用時は素材の事実・条件・不確実性を保つ。
判定基準は`writing.md`に従い、各例は通常の文章検査へ渡す。
術語と概念は、議論や説明で必要な意味に沿って使う。

## 予告と総括

結論と必要な次の操作から書く。前置きと結びには、読者の判断を変える情報を置く。

```text
例文: 設定はJSONで保存する。
説明: 読者が知る必要のある保存形式を直接示す。
```

```text
例文: テスト設計は実装前の仕様策定段階から開始する。テストケースは境界値を網羅する。
説明: 開始する時点と、検証する範囲を示す。
```

## 空虚な形容

評価する対象、成立条件と観測した結果を具体的に示す。

```text
例文: キャッシュの導入後、DBクエリ回数が減り、応答時間が短くなった。
説明: 観測した変化を書く。因果関係と測定値は、取得した根拠の範囲で述べる。
```

```text
例文: 本UIはメニューを2階層に抑え、主要操作を1クリックで完了する構造とする。
説明: 設計する構造と操作回数を具体的に示す。
```

## 空虚な動詞

説明する対象と内容を、動詞の目的語とその関係で特定する。

```text
例文: APIのレスポンスボディの構造とステータスコードの対応を示す。
説明: 何について、どの関係を説明するかを読み取れる。
```

## 接続の型

並列の情報は同じ構造でまとめ、因果関係や条件は接続から読み取れる形にする。

```text
例文: タイムアウト値・リトライ回数・ログレベルの3項目を設定ファイルで指定する。
説明: 同じ手段で指定する項目をまとめる。
```

## 翻訳調・英語統語

判断した主体、観測とその根拠を対応付ける。
システムの動作と結果が示す値は、その主体で説明する。
確定した内容と未確定の内容は、素材と同じ確実性で書く。
エージェント自身が確かめた内容は、その取得条件で言い切る。
ユーザーが限定付きで述べた内容は、その限定を保つ。

```text
例文: 担当者がログを確認し、キャッシュへの要求が失敗したと判断した。原因はまだ分からない。
説明: 判断した主体、判断の根拠と未特定の範囲を示す。
```

```text
例文: 集計結果は成功が8件、失敗が2件であることを示す。システムは失敗した要求を再実行する。
説明: 集計値と処理主体の動作を直接述べる。無生物を主語にする文も、その関係が成立すれば使う。
```

```text
例文: この処理は結果を保存する。
説明: 処理が行う動作を直接示す。
```

```text
例文: 入力には整数を指定する。
説明: 受理する入力を具体的に示す。必要な入力制約と除外条件は保持する。
```

```text
例文: 本設定は再実行の開始時に中間ファイルを削除する。削除しない場合は前回の出力が残り、結果が変わる。
説明: 設定の動作と、その動作を行わない場合の結果を対応付ける。
```

## メタ構造宣言

見出しは主題を示し、本文はその主題の仕様や手順から書く。

```text
例文: 検索処理はクエリを正規化してからベクトル検索を実行する。
説明: 操作の対象と順序を示す。
```

```text
例文: キャッシュキーはリクエストURLとAuthorizationヘッダーのハッシュで構成する。
説明: キャッシュ設計の節で、キーの構成を直接示す。
```

## AI偏愛語・名詞比喩・造語

対象の性質、観測できる構造や数値を書く。
体験と感想は本人が述べた範囲を保つ。

```text
例文: 変更箇所を読んだが、まだ原因を理解できていない。
説明: 調べた対象と、未確定の内容を対応付ける。
```

```text
例文: 会議で初めて自分の案を説明できてうれしかった。
説明: 本人が述べた出来事と感想を、その範囲で伝える。
```

```text
例文: 本ライブラリは入出力を関数3つに限定し、内部状態を持たない。利用側は各関数を単体で呼び出せる。
説明: ライブラリの構造と、利用側ができる操作を示す。
```

```text
例文: 本規範はレビュー時の判定条件を定める。判定条件を満たさない変更は差し戻す。
説明: 文書が定める内容と、その条件による処置を示す。
```

## 唐突な否定と不変の表明

先行する問いや話題に対応する内容を書く。
否定・除外・不変の表明は、読み手がその判断や操作に使う場合に示す。

```text
例文: その2件をサブエージェントの一覧へ加える。
説明: 対象の分類を問う文脈で、対象と処置を示す。
```

```text
例文: レーンの検証を妨げる確定済みの既存不良は、メインが修正対象を同じレーンへ名指しして認可する。
認可を受けたレーン担当は、計画の実装と別のcommitで修正する。
説明: 認可する主体と条件、修正する主体と方法を対応付ける。
```

```text
例文: 実データで2回目以降の一覧が0.15秒を超えていたため、変更のないファイルの再確認と時刻の整形を省く。返す一覧の内容は変えない。
説明: 性能改善の説明では、出力が変わるかも読み手の判断に使われるため、その扱いを示す。
```
