# コーディングエージェント向け文書品質（基本）

本書は、コーディングエージェントが直接読み込む文書（`AGENTS.md`・`CLAUDE.md`・ルール・`SKILL.md`・サブエージェント定義・`references/`）の責務、記述内容、条件の書き方及び語調の基準を定める。
規範文書へ新しい規定を追記する場面と文書の記述量を管理する場面の基準は`agent-documents-additions.md`に従う。
なお、計画ファイルの成果物契約は`agent-toolkit:plan-mode`が定め、本書の対象外とする。

## 完成条件

新規作成・改訂した文書は次の要件を満たす。

### 責務と構成

- agent定義、スキル、タスク指示文書では、冒頭で担当する責務、担当しない責務、最初に行う行為を明示する。本箇条を受信者の責務の記述の正本とする
- 委譲元側の文書は受渡しと検収に専念する。委譲先固有の手順は委譲先側の文書に持たせ、委譲先は渡されたタスク文書と必要な規範を自ら読み込む
- 冒頭の1〜2文で目的（適用判断の核となる動機）を述べ、frontmatterの`description`には目的の詳細を書かない
- 新しい挙動や制約は次の区分へ振り分ける。常時参照する横断標準は`AGENTS.md`や`CLAUDE.md`本文またはpaths未指定ルール、特定パス限定則はpaths指定ルール、手順やワークフローはスキル、機械的な強制や自動検査はhook、調査の隔離や冗長出力の抑制はサブエージェントとする
- スキルやエージェントの責務配置は、スキル編集の資料に従う
- 記述は、それを必要とする工程で確実に読み込まれる文書へ置く。常時ロードされる規範、その工程で起動する`SKILL.md`、工程内で明示的に読む指示がある`references/`がこれに当たる。読む契機が定められていない記述は、実行時の判断材料として参照されない。逆に、特定の工程でだけ必要な記述を常時ロードされる文書へ置くと、全工程がその分を読む
- 参照先を「<条件>のとき: <参照先>」の形で条件付きに挙げる文書は、その条件が成立した時点で参照先を読むことと、読む前にその条件が成立する操作へ着手しないことを同じ文書へ書く。条件の成立を判定する工程が定まらないと、条件が成立したまま参照先を読まずに操作へ進む経路が残る
- MCPツールなどの説明文は、呼び出しの可否と方式を左右する判定の正本として書く。ツールの組み合わせと実行順序は手順文書へ置く

### 記述内容の取捨

- すでに自動ロード済みや呼び出し済みの規範を不要に要約・反復しない。各記述は、削除すると判断の一貫性が損なわれる場合に限って残す
- 実行判断に直接寄与しないメタ情報（管理方針、編集判断、同期対象など）はfrontmatterコメントへ移し、本文には実行判断に直結する記述のみを置く
- サブエージェントと委譲先は起動時に共通ルールを受け取るため、既に届いている条文を再掲せず参照する

### 条件と範囲の記述

- 判断条件、例外条件、許容条件は客観的に観測可能な事実（コマンド終了コード、ファイルの有無、ユーザー合意など）で記述する。作業量や所要時間などの主観的な推定量は条件に含めない
- 条文は、守るべき価値と、その価値から外れた場合に生じる不利益を書く。手段は一般的な場合に有効な例として示し、読み手がその場の観測で手段を選べる形にする
- 適用範囲、除外対象及び前提条件の列挙は、技術的な不成立、データ破損、公開インターフェース破壊、セキュリティ欠陥のいずれかを防ぐ条文に限る。これらに当たらない条文では、適用する場面と適用しない場面を列挙しない
- 独立して変化し得る複数の制約は箇条書きを分け、個別に記述する
- 何かを制限する場合は、制限対象と代わりに行うべき行動を合わせて書く
- 既存規定の表現形式を変える場合は、変更前後で実行時の振る舞いが変わらないことを確認する（努力目標。細則を一般則へ畳む改訂まで仕様変更と同じ手続きを要すると、条文の整理が進まない）
- 手順では、各工程の後に続く工程と参照先の所在を示す（努力目標。次に進む先が分からないと、実行主体が手順の外から工程を組み立てる）
- 読み手が対象を一意に同定できる語で書く。多義的な語は条文内で限定し、指示語は具体的な名称へ置き換える
- 数値の上限は表や固定形式の出力にのみ適用し、探索や判断を伴う出力では重要度の順序や除外条件で制御する
- 規範と手順では達成すべき性質を規定する。特定のツールや実行順序を限定する場合は、その手段が必要不可欠である根拠を併記する

### 語調と現行規則の表現

- 読み手が対象を一意に同定できる平易な日本語で書く。判定基準と望ましい行動を肯定形で直接述べ、役割は具体名で呼ぶ。法令調の硬い表現は平易な動詞へ置き換える
- 現行の規則だけを記述する。過去の版との差異を示す表現は、読み手が参照できない旧規則の推測を促す
- 語調を強める表記（`必ず`、`絶対`など）は、違反を防ぐ理由が明確な重要規定に限って用いる
- 技術的な不成立、データ破損、公開インターフェース破壊、セキュリティ欠陥のいずれかを防ぐ条文は既定で従う規定とし、標示を付けずに平文で理由を添える。それ以外の条文は努力目標とし、「（努力目標。〜）」の形式で理由を書く
