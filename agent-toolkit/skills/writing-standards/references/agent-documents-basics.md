# エージェント向け文書品質（基本）

本書はエージェント向け文書の責務、記述内容、条件の書き方および語調の基準を定める。エージェント向け文書は、コーディングエージェントが直接読み込む文書（`AGENTS.md`・`CLAUDE.md`・ルール・`SKILL.md`・サブエージェント定義・`references/`・`<役割名>.subagent.md`と`<役割名>.parent.md`・hook関連の文書）を指す。コードでは`is_agent_doc_target_file`がこの範囲を判定する。
エージェント向け文書へ新しい規定を追記する場面と文書の記述量を管理する場面の基準は`agent-documents-additions.md`に従う。
なお、計画ファイルの成果物契約は`agent-toolkit:plan-mode`が定め、本書の対象外とする。
本書が規定の理由として挙げる読み手（LLM）の傾向は、運用で観測された傾向に基づく設計上のリスクモデルであり、個別の環境とモデルでの成立は実際の観測で確かめる。

## 完成条件

新規作成・改訂した文書は次の要件を満たす。

### 責務と構成

- agent定義、スキル、`<役割名>.subagent.md`では、冒頭で担当する責務、担当しない責務、最初に行う行為を明示する。委譲先の責務は本箇条に従って記述する。読み手は文書内に登場する役割の記述（「管理者として説明する」など）を実行中の自身の役割として取り込むことがあるため、読み手自身の責務を冒頭で特定する
- 委譲元側の文書は受渡しと検収に専念する。委譲先固有の手順は委譲先側の文書に持たせ、委譲先は渡された`<役割名>.subagent.md`と必要な規範を自ら読み込む。委譲元と委譲先の指示を同じ文書へ併記すると、委譲元が委譲先の制約を自分へ適用し、委譲先へ委ねる判断を自分で処理しやすい
- 冒頭の1〜2文で目的（適用判断の核となる動機）を述べる。frontmatterの`description`へ書く範囲は、スキルでは`agent-skills.md`「YAML frontmatter」、サブエージェント定義では`sub-agents.md`「frontmatter」に従う
- 新しい挙動や制約は次の区分へ振り分ける。常時参照する横断標準は`AGENTS.md`や`CLAUDE.md`本文またはpaths未指定ルール、特定パス限定則はpaths指定ルール、手順やワークフローはスキル、機械的な強制や自動検証はhook、調査の隔離や冗長出力の抑制はサブエージェントとする
- 記述の置き場所（保存先）は、読込契機と実行主体に加えて、その置き場所が届く読み手の範囲でも判定する。
  規定が成立する理由（共有branchの状態、チームの合意、特定ホストの制約、個人の運用判断など）から規定を守るべき読み手の範囲を特定し、候補の置き場所が届く範囲と比べる。
  比べる向きは双方向とする。共有すべき規定を個人の環境へ置く置き場所は狭すぎ、個人またはプロジェクトに限る規定を共有リポジトリや配布物へ置く置き場所は広すぎる。
  ユーザーが置き場所を指定した場合も比べる。合わない場合は指定どおり書き、同じ応答で範囲が合う置き場所とその判断を入れ替える値（チーム共通の規定か個人の運用かなど）を示す。置き場所は自ら変えない。
  この扱いは`agent-toolkit/rules/01-agent.md`「QCDと3段判定」のユーザーが示した手段の評価に当たる。範囲が狭すぎると規定を守るべき主体へ届かない。広すぎると、適用対象でない主体が規定を自身へ適用する

<例>
個人のルール: `~/.claude/rules/`配下、`CLAUDE.local.md`
全員とCIが読む規範: `AGENTS.md`、`CLAUDE.md`、プロジェクトスキル
全配布先の規範: 配布物の`rules/`と`skills/`
</例>

- 実行主体別規範は読み手と読込契機で配置する。全主体共通は`rules/`、メイン限定は`share/rules-main.md`、委譲先限定は`share/rules-subagent.md`、ホスト固有の差分は同じ接頭辞のホスト別ファイルへ置く。Claude CodeとCodexのhook、agents_serverの通常委譲および生成manifestが、その読み手へ同じ規範を配送するため、これらは常時ロードと同じ拘束力を持つ。委譲元と委譲先の双方が守る受け渡し規定は全主体共通として扱う。片側だけに適用する規定を`rules/`へ置くと、適用対象でない主体がその規定を自身へ適用する。軽量委譲へ共通規範を配送しない場合は、軽量委譲の起動契約へ必要な制約を置く。特定作業時だけ必要な内容はスキルか`references/`へ置く。agent-toolkitが読み手へ常に配送する規範（`rules/`配下と、読み手に応じて配送する`share/rules-main*.md`・`rules-subagent*.md`）を常時規範と呼ぶ

- プロジェクト規範は対象リポジトリが規範として定める指示（`AGENTS.md`、`CLAUDE.md`、`.claude/rules/`、プロジェクトのスキルなど）を指す。プロジェクト方針はプロジェクト規範に加え、README、コードコメント、設定など規範化されていない記述に書かれた方針を指す
- スキルとエージェントの責務配置は`agent-skills.md`と`sub-agents.md`に従う
- 記述はそれを必要とする工程で確実に読み込まれる文書へ置く。常時ロードされる規範、その工程で起動する`SKILL.md`、工程内で明示的に読む指示がある`references/`がこれに当たる。読む契機が定められていない記述は、実行時の判断材料として参照されない。逆に、特定の工程でだけ必要な記述を常時ロードされる文書へ置くと、全工程がその分を読む。冒頭で一括ロードされる規範は、作業が進んで文脈上の距離が広がるほど参照されにくくなる。このため、常時ロードには優先順位、不変条件、禁止事項、完了条件とプロジェクト固有の概念を置き、言語・領域・作業種別ごとの規範はスキルかpaths指定ルールへ、デプロイ・migration・releaseなど工程の途中で要る詳細手順は`references/`と工程内の読込指示へ置く
- 読込表とはスキル本体と`<役割名>.parent.md`・`<役割名>.subagent.md`の冒頭に置く表であり、行ごとの時点や条件が成立したときに、その条件が対象とする操作の前に同じ行の参照資料を全文読むことを示す。列は「時点または条件」と「全文読む資料」の2つとし、条件は観測できる操作や入力で書く。主体や工程で必読の組が変わる場合は行を分ける。参照資料を条件付きで読ませる指示は読込表の行へ集め、本文の各所へ「〜のとき全文読む」と散在させない。散在した指示は条件の成立を判定する工程が定まらず、条件が成立したまま参照先を読まずに操作へ進む抜け道を残す。常時規範は読込表を持たず、スキルの起動契機、起動対象およびそのスキルが定める範囲だけを書く（`agent-documents-additions.md`「規範追記時の判定」）
- MCPツールなどの説明文は、呼び出しの可否と方式を左右する判定の基準として書く。ツールの組み合わせと実行順序は手順文書へ置く
- 複数の文書や実装から使う手順は、定義の所有者を1つ決め、生成元と全消費側を列挙する。定義は所有者だけへ置く。消費側は参照、呼び出し、生成検証のいずれかで接続する。共通手順のレビューでは、生成元と全消費側の列挙、定義の所有者、参照または呼び出しの到達性、同期の検証を確認する。同じ判断を複数箇所が独立に定義している場合は所有者へ統合し、各消費側の範囲、認可、検証および終端条件を保持する。スキル間と`<役割名>.subagent.md`間でも同じ判定を転記せず、読込契機から定義元へ到達できる参照を置く。統合で消費側に新たなスキル起動か`Read`が生じる場合は、増える読み込み量と、重複の解消で防げる改訂時の食い違いとを比べて採否を決める。読み込みが増える統合は全工程の費用を増やし、重複を残すと改訂のたびに片方だけが更新される危険が残る
- 同時に必要となる情報をまとまりとして配置し、異なる主題の項目は見出しで分ける（努力目標。同時に必要な情報が別々のファイルへ散ると読み込みの取りこぼしが起き、テーマの異なる項目が1つの列挙へ混在すると現在の作業と関係の薄い項目ほど読み手の注意から脱落しやすいため）。読者の異なる記述が同じ文書に同居した場合も、語彙、前提知識、説明の粒度が混乱しやすい
- 重要な規則には、参照する契機と実行する工程を対応付ける。宣言だけで実行時の遵守を期待せず、作業手順の特定時点で必要な規範は観測可能な契機と結びつけ、参照資料の読込は読込表の行、スキルの起動は「〜を検知したら〜を起動してから編集する」のような工程内の指示として置く（努力目標。規則を説明できても、作業中に適用する契機が無いと遵守しにくいため）。判断の偏りも、規範の宣言だけでは抑止しにくい。途中で採った仮説へ後続の探索が偏ること、開いたファイルや検索結果を全体と誤認すること、自己生成した記述が後続の判断へ影響することがこれに当たる。既存の慣習を仕様と誤認すること、一般論を固有の事情があるプロジェクトへ持ち込みすぎることも当たる。連続するタスクで前のタスクの制約・仮説・識別子を後続へ持ち越すことも当たり、類似のファイル名・API名・概念がある場合に起きやすい。これらへの対策は各作業の手順として置く。手順が求めるのは、反証候補の確認、網羅性の判定、維持する契約の確認、事実と推論の区別、タスク境界での受け渡しの確認である

### 主要用語の初出定義先

エージェント向け文書群を横断して用いる主要用語は、その用語の定義元文書を1つ定め、その文書の本文へ1文形の初出定義を置く。
他の文書はその定義元を参照して用語を使い、独自の定義を置くのは定義元だけとする。
複数の文書で使う工程・レビュー・検証・判定・担当の名前なども対象とし、単一の文書内でしか使わない呼称と技術用語は`writing.md`「日本語の書き方」の初出定義に従う。これらを名前で指す時と新しい名前を付ける時は`defined-names.md`「命名の方針」に従う。
定義を持たない用語が文書を横断して現れると、読み手がその意味を文書ごとに推測する。
繰り返し参照する原則や工程などには短い固有名を付け、その名から同じ定義へ到達できるようにする（努力目標。名前付きの概念は再利用されやすく、呼称が一定だと参照先を想起しやすい一方、名前の異なる言い換えは判断の分岐を増やすため）。

### 記述内容の取捨

- すでに自動ロード済みや呼び出し済みの規範の要約・反復を避ける（努力目標。読み込み量が増えるため）
- 実行判断に直接寄与しないメタ情報（管理方針、編集判断、同期対象など）はfrontmatterコメントへ移し、本文は実行判断に直結する記述で構成する（努力目標。判断に使わない記述も毎回読み込まれるため）
- サブエージェントと委譲先は起動時に共通ルールを受け取るため、既に届いている条文は参照で示す（努力目標。再掲は読み込み量を増やし、改訂時に片方だけが更新される食い違いを招くため）

### 条件と範囲の記述

- ユーザー要求を規範や手順へ変換する前に、原文が示す目的、要件、対象範囲、例示の開放性、変更指示および論理関係を保持する。既存の分類や下位規範はその後に適用し、原文の意味を既存の分類へ収まる範囲へ縮めない
- 判断条件、例外条件、許容条件では確認できる事実を根拠にする。作業量や所要時間の見込みは品質、費用および完了までの時間を比べる材料として扱い、単独で依頼を縮小する停止条件にしない。工程を省ける条件（独立した確認や委譲を省く条件を含む）も、その工程が検出または達成する対象に当たる変化が差分や対象にあるかで書き、行数、文の数、「局所的」「軽微」などの規模の印象を条件にしない。規模の印象を条件にすると、工程を省く主体が手元で数えられる行数で判断し、その工程が見つけるはずの変化を含む差分まで省く
- 判断を要する条文では守る価値、そこから外れた場合の不利益、考慮する観点を示し、結論はそれらを踏まえた総合判断へ委ねる
- 短い基本方針の後に手段を示す場合は、独立行の`<例>`と`</例>`で囲み、間へ1行1例の語句か`<条件>: <対応>`を書く。例示は開放集合であり、適用範囲は基本方針で決める。適用範囲、除外、前提の閉じた列挙は、`agent-toolkit/rules/01-agent.md`「規定の区分と標示」の硬い制約を守る条文で使う。硬い制約以外で判断材料を閉じる列挙や例外を増やすと、その場の目的に合う判断を妨げる

<例>
適用範囲と除外を段階的に列挙する追記
「ただし」「除く」「限る」で結ぶ二重条件
他の文書が定めた判断の転記
依頼にない上限や入力拒否
</例>

- 独立して変化し得る複数の制約は箇条書きを分け、個別に記述する（努力目標。まとめて書くと一方の改訂時に他方を読み違えやすいため）
- 衝突し得る指示には優先順位または衝突時の判定原則を示す。否定形や例外が重なる場合は、条件と行動の対応を読み取れる形へ分ける（努力目標。複数の指示が併存すると局所的に満たしやすい指示へ判断が偏りやすく、「最小変更」と「根本原因の修正」の併存では最小差分の対症療法へ偏る。否定形、例外、二重条件は誤適用されやすい）
- 代替が自明でない制限では、制限対象と代わりに行う行動を合わせて書く。代わりの行動が書かれていないと、実行主体が代替を探す工程を要する
- 既存規定の表現形式を変える場合は、変更前後で実行時の振る舞いが変わらないことを確認する。条文を所有者への参照へ畳む改訂では、畳んだ条文が持っていた義務（判定、工程、契機）を参照先の節の本文が持つことを、その節を読んで確かめる（努力目標。細則を一般則へ畳む改訂まで仕様変更と同じ手続きを要すると、条文の整理が進まない）
- 手順では各工程の後に続く工程と参照先の所在を示す（努力目標。次に進む先が分からないと、実行主体が手順の外から工程を組み立てる）
- 読み手が対象を一意に同定できる語で書く。多義的な語は条文内で限定し、指示語は具体的な名称へ置き換える。既存の段落へ文を挿入または移動する編集では、挿入した文と同じ段落の後続の文にある指示語の指す先も変わっていないかを確かめる。挿入した文が後続の指示語の先行詞の候補を増やすと、変えていない文の意味が変わる
- 数値の上限は、その値が無いと成果物の品質または利用場面を守れないときに設ける。探索や判断を伴う出力では、重要度と除外理由を先に検討する
- 規範と手順では達成すべき性質を規定する。特定のツールや実行順序を限定する場合と、検出や判定の候補を固定の検索語、正規表現、キーワードの一覧などで閉じる場合は、その手段が必要不可欠である根拠を併記する。固定の一覧で候補を閉じるときは、一覧が対象全体を被覆できる根拠も示す。被覆の根拠を示せない場合は、一覧の外も文脈から判定できる方法（対象を文脈ごと読むなど）と比べて手段を選ぶ。公開契約によって候補が有限かつ完全な場合と、一覧を候補の優先付けに使い別の工程で一覧の外も判定する場合は、その根拠を示して固定の一覧を使える。形式や語彙を事前に確定できない出力から未知の異常を探す手順で、既知の語の一覧だけを候補全体として扱うと、一覧に一致しない異常が確認の対象から外れる

### 語調と現行規則の表現

- 経験のある同僚が後輩へ説明するように、読み手が対象を一意に同定できる自然な日本語で書く。判定基準と望ましい行動を直接述べ、役割は具体名で呼ぶ。意味、適用範囲、拘束力、条件および例外を保ちながら法令調の硬い表現を平易な動詞へ置き換える。読み手は文脈にある文体を再生産し、否定形の宣言、指示語、法令調の語を多く含む文書を読んだ後の成果物は同じ文体になり、範囲外の追加要素と過剰な設計も増える。観測記録は`docs/development/audit-records.md`の「agent-toolkit/skills/writing-standards/references/agent-documents-basics.md：語調と現行規則の表現：2026年9月16日」にある
- 現行の規則を記述する（努力目標。過去の版との差異を示す表現は、読み手が参照できない旧規則の推測を促すため）
- 語調を強める表記（`必ず`、`絶対`など）は違反を防ぐ理由が明確な重要規定に限って用いる。重大度の表明と禁止事項の列挙よりも、行動の条件を明瞭にした指示が働きやすい
- 規定の拘束力と努力目標の標示は`agent-toolkit/rules/01-agent.md`「規定の区分と標示」に従う
