# コーディングエージェント向け文書品質（基本）

本書はコーディングエージェントが直接読み込む文書（`AGENTS.md`・`CLAUDE.md`・ルール・`SKILL.md`・サブエージェント定義・`references/`）の責務、記述内容、条件の書き方及び語調の基準を定める。
規範文書へ新しい規定を追記する場面と文書の記述量を管理する場面の基準は`agent-documents-additions.md`に従う。
なお、計画ファイルの成果物契約は`agent-toolkit:plan-mode`が定め、本書の対象外とする。

## 完成条件

新規作成・改訂した文書は次の要件を満たす。

### 責務と構成

- agent定義、スキル、タスク指示文書では、冒頭で担当する責務、担当しない責務、最初に行う行為を明示する。受信者の責務は本箇条に従って記述する
- 委譲元側の文書は受渡しと検収に専念する。委譲先固有の手順は委譲先側の文書に持たせ、委譲先は渡されたタスク文書と必要な規範を自ら読み込む
- 冒頭の1〜2文で目的（適用判断の核となる動機）を述べ、frontmatterの`description`には目的の詳細を書かない
- 新しい挙動や制約は次の区分へ振り分ける。常時参照する横断標準は`AGENTS.md`や`CLAUDE.md`本文またはpaths未指定ルール、特定パス限定則はpaths指定ルール、手順やワークフローはスキル、機械的な強制や自動検証はhook、調査の隔離や冗長出力の抑制はサブエージェントとする
- 実行主体別規範は読み手と読込契機で配置する。全主体共通は`rules/`、メイン限定は`share/rules-main.md`、委譲先限定は`share/rules-subagent.md`、ホスト固有の差分は同じ接頭辞のホスト別ファイルへ置く。Claude CodeとCodexのhook、agents_serverの通常委譲及び生成manifestが、その読み手へ同じ規範文書を配送するため、これらは常時ロードと同じ拘束力を持つ。委譲元と委譲先の双方が守る受け渡し規定は全主体共通として扱う。片側だけに適用する規定を`rules/`へ置くと、適用対象でない主体がその規定を自身へ適用する。軽量委譲へ共通規範を配送しない場合は、軽量委譲の起動契約へ必要な制約を置く。特定作業時だけ必要な内容はスキルか`references/`へ置く
- スキルやエージェントの責務配置は、スキル編集の資料に従う
- 記述はそれを必要とする工程で確実に読み込まれる文書へ置く。常時ロードされる規範、その工程で起動する`SKILL.md`、工程内で明示的に読む指示がある`references/`がこれに当たる。読む契機が定められていない記述は、実行時の判断材料として参照されない。逆に、特定の工程でだけ必要な記述を常時ロードされる文書へ置くと、全工程がその分を読む
- 参照先を「<条件>のとき: <参照先>」の形で条件付きに挙げる文書は、その条件が成立した時点で参照先を読むことと、読む前にその条件が成立する操作へ着手しないことを同じ文書へ書く。条件の成立を判定する工程が定まらないと、条件が成立したまま参照先を読まずに操作へ進む抜け道が残る
- MCPツールなどの説明文は、呼び出しの可否と方式を左右する判定の基準として書く。ツールの組み合わせと実行順序は手順文書へ置く
- 複数の文書や実装から使う手順は、定義の所有者を1つ決め、生成元と全消費側を列挙する。定義は所有者だけへ置く。消費側は参照、呼び出し、生成検証のいずれかで接続する。共通手順のレビューでは、生成元と全消費側の列挙、定義の所有者、参照又は呼び出しの到達性、同期の検証を確認する。同じ判断を複数箇所が独立に定義している場合は所有者へ統合し、各消費側の範囲、認可、検証及び終端条件を保持する。スキル間とタスク文書間でも同じ判定を転記せず、読込契機から定義元へ到達できる参照を置く
- 同時に必要となる情報をまとまりとして配置し、異なる主題の項目は見出しで分ける（努力目標。現在の作業と関係の薄い項目ほど読み手の注意から脱落しやすいため）
- 重要な規則には、参照する契機と実行する工程を対応付ける。宣言だけで実行時の遵守を期待せず、作業手順の特定時点で必要な規範は観測可能な契機と結びつけた読込・起動指示（「〜を検知したら〜を読み込んでから編集する」等）としてその工程へ埋め込む（努力目標。規則を説明できても、作業中に適用する契機が無いと遵守しにくいため）

### 主要用語の初出定義先

規範文書群を横断して用いる主要用語は、その用語の定義元文書を1つ定め、その文書の本文へ1文形の初出定義を置く。
他の文書はその定義元を参照して用語を使い、独自の定義を置くのは定義元だけとする。
対象は複数の文書で頻出する用語に限り、単一の文書内でしか使わない技術用語は`writing.md`「日本語の書き方」の初出定義に従う。
定義を持たない用語が文書を横断して現れると、読み手がその意味を文書ごとに推測する。
繰り返し参照する原則には短い固有名を付け、その名から同じ定義へ到達できるようにする（努力目標。名前の異なる言い換えが判断の分岐を増やすため）。

### 記述内容の取捨

- すでに自動ロード済みや呼び出し済みの規範を不要に要約・反復しない。各記述は削除すると判断の一貫性が損なわれる場合に限って残す
- 実行判断に直接寄与しないメタ情報（管理方針、編集判断、同期対象など）はfrontmatterコメントへ移し、本文には実行判断に直結する記述のみを置く
- サブエージェントと委譲先は起動時に共通ルールを受け取るため、既に届いている条文を再掲せず参照する

### 条件と範囲の記述

- ユーザー要求を規範や手順へ変換する前に、原文が示す目的、要件、対象範囲、例示の開放性、変更指示及び論理関係を保持する。既存の分類や下位規範はその後に適用し、原文の意味を既存の分類へ収まる範囲へ縮めない
- 判断条件、例外条件、許容条件では確認できる事実を根拠にする。作業量や所要時間の見込みは品質、費用及び完了までの時間を比べる材料として扱い、単独で依頼を縮小する停止条件にしない
- 判断を要する条文では守る価値、不利益、考慮する観点を示し、結論はそれらを踏まえた総合判断へ委ねる。基本方針、例示と閉じた列挙の書式は`agent-toolkit/rules/01-agent.md`「規定の区分と標示」に従う
- 独立して変化し得る複数の制約は箇条書きを分け、個別に記述する
- 衝突し得る指示には優先順位又は衝突時の判定原則を示す。否定形や例外が重なる場合は、条件と行動の対応を読み取れる形へ分ける（努力目標。局所的に満たしやすい指示へ判断が偏りやすいため）
- 何かを制限する場合は、制限対象と代わりに行うべき行動を合わせて書く
- 既存規定の表現形式を変える場合は、変更前後で実行時の振る舞いが変わらないことを確認する（努力目標。細則を一般則へ畳む改訂まで仕様変更と同じ手続きを要すると、条文の整理が進まない）
- 手順では各工程の後に続く工程と参照先の所在を示す（努力目標。次に進む先が分からないと、実行主体が手順の外から工程を組み立てる）
- 読み手が対象を一意に同定できる語で書く。多義的な語は条文内で限定し、指示語は具体的な名称へ置き換える
- 数値の上限は、その値が無いと成果物の品質又は利用場面を守れないときに設ける。探索や判断を伴う出力では、重要度と除外理由を先に検討する
- 規範と手順では達成すべき性質を規定する。特定のツールや実行順序を限定する場合は、その手段が必要不可欠である根拠を併記する

### 語調と現行規則の表現

- 経験のある同僚が後輩へ説明するように、読み手が対象を一意に同定できる自然な日本語で書く。判定基準と望ましい行動を直接述べ、役割は具体名で呼ぶ。意味、適用範囲、拘束力、条件及び例外を保ちながら法令調の硬い表現を平易な動詞へ置き換える
- 現行の規則だけを記述する。過去の版との差異を示す表現は、読み手が参照できない旧規則の推測を促す
- 語調を強める表記（`必ず`、`絶対`など）は違反を防ぐ理由が明確な重要規定に限って用いる
- 規定の拘束力と努力目標の標示は`agent-toolkit/rules/01-agent.md`「規定の区分と標示」に従う
