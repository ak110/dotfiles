# 頻出lint違反パターン

textlintを中心としつつ、`pyfltr`経由で同時実行される他のツール（markdownlint・typos等）の違反対処も含む。

## textlint指摘への修正方針

textlintの指摘へ対応するときは、指摘語を別の語へ差し替えず、指摘のある文を自然な日本語へ書き直す。
指摘語を単位に修正を組み立てると語の差し替えが最短の手段になり、文全体の自然さを誰も確かめなくなる。
本節は`preset-ai-words-ja`に限らず、`ja-no-redundant-expression`や`sentence-length`のように文の組み替えを要するtextlintの指摘すべてに適用する。
`textlint --fix`が自動で直す表記の指摘（全角と半角の間隔、句読点の種類など）は本節の対象外とする。

- 指摘のある文の書き直しは`agent-toolkit:delegation`の`start_write`へ委ねる
  - 依頼には読者（人間向け文書かエージェント向け文書か）、対象ファイルと該当段落、指摘のルール名と指摘語、保つべき事実と契約を書く
  - 指摘語だけを別の語へ置き換えた文を返さないことと、次の項が挙げる修正（同義語への機械的な言い換え、略語や英語への置き換えなど）をしないことも依頼へ書く
  - 読者が異なる文書は別々の依頼に分ける
- 語の置換ではなく文を書き直し、次の修正はしない
  - `sed`などによる一括置換
  - 略語や英語への置き換え（例: `正本`を`SSOT`へ置き換える）
  - 同義語への機械的な言い換え（例: `検査`を`チェック`へ置き換える）
  - `.textlintrc.yaml`の`allows`への登録
- 指摘語が担っていた動作や関係を、動詞や普通の言い回しで表す
  - `Xを正本とする`は`Xに従う`や`Xが定める`と書く
  - `確認経路へ送る`は`ユーザー確認する`と書く
  - `実測で確定する`は`実際に動かして確かめる`と書く
  - `AとBを照合する`は`AがBと一致するか確かめる`と書く
  - `公開入口`は`利用者が使うコマンドや画面`と書く
  - `機械検査`は`lint`や`自動チェック`と書く
- `no-short-topic-comma`（短い主題の直後の読点）の指摘では、読点を外すか文を組み替える
- 書き直すと意味や契約が変わる箇所は書き換えず、UWIでユーザー確認する
  - 指摘の件数が多いことや書き直しが難しいことは、対応範囲を縮める理由にしない
- 起草を委ねた主体は、返った文を原文と比べて事実と契約が保たれているかを確かめ、textlint、口語表現チェック、ダッシュチェックを通す
  - 受け入れる前に`git diff --word-diff=plain --word-diff-regex=.`で原文と文字単位で比べる。日本語の文は空白で区切られないため、既定の単語単位の差分では行全体が1語として扱われる
  - 変更が1か所だけの行を確認の候補に挙げる。変更箇所の数だけでは組み替えと置き換えを区別できないため、候補の各行を置き換え後の語句の働きで判定する
  - 指摘語を同じ働きの別の1語へ差し替え、文の他の部分が変わっていない行は、書き直しが済んでいない行として同じ委譲先へ差し戻す
  - 指摘語を句や節へ展開し、述語や文の組み立てが変わった行は、書き直した行として受け入れる
- 書き直しで繰り返し使ったパターンは本節の`典型パターン`へ追記する

### 典型パターン

- `実測`は実行に限らず実物のファイル、出力、記録を読んで確かめる意味を含む。実行を指す文だけ`実際に動かして確かめる`と書き、それ以外は`現物を観測して確かめる`のように範囲を狭めない書き方にする
- `公開入口`はコマンドや画面に限らずAPI、hook、ライブラリ関数なども含む。`公開された呼び出し手段（コマンド、画面、API、hookなど）`のように開いた列挙で書く
- `経路`は文脈に応じて、手段、方法、仕組み、処理の流れ又は起動方法から選ぶ。計画メタ情報の`起動経路`のように構造定数やコードと一致させる識別子は、書き換えずにインラインコードで囲む
- 見出しに指摘語がある場合は見出しを改名し、その節名を`「」`やバッククォートで参照する全ての文書とコードを同じ変更でそろえる
- 用語として定義した語に指摘語が含まれる場合は、定義文と全ての使用箇所を同じ新しい語へそろえる（例: `硬いゲート`を`硬い制約`へ改めた）
- 語の出現頻度を集計した記録のように、指摘語そのものがデータである箇所は語を変えずにインラインコードで示す
- `no-short-topic-comma`の多くはインラインコードで始まる主題の直後の読点（例: `` `start`は、 ``）である。読点を外して解消する
- 書き直しの後は、インラインコード、見出し、コードブロックが書き直し前から変わっていないかを機械的に比べる。意味と契約が保たれているかは、書き直した主体とは別の担当に差分をレビューさせて確かめる

## 文字種と間隔

- 日本語と半角文字（英数字・記号・インラインコード）が隣接する場合、間にスペースを挿入しない（JTF 3.1.1）
  例: `Pythonの設定`、`chezmoiで管理する`、「`uv add`を使う」
  - 実装側のソースコード文字列リテラル（ログ・エラー・CLIヘルプなど）をMarkdown本文へ引用する場合、
    Markdown側のJTF 3.1.1 auto-fixで全角・半角間スペースが除去される
    ソースコード側のスペース保持と非対称になる
  - ユーザーが`grep`等で文字列の完全一致検索をする想定がある場面では、
    引用文を地の文に置かず`text`または言語指定付きコードフェンスで包んでauto-fix対象外にする
- 和文中にハイフン`-`を使わない（JTF 4.2.6）。接頭辞名や識別子はインラインコード内に含める
- 対応のない山括弧`<>`を本文に書かない。プレースホルダーはインラインコード内に含める（JTF 4.3.7）

## 文長

- 一文は150文字以内、読点は1文あたり4個未満に抑える（ja-technical-writing/sentence-length、max-ten）
- 中黒（`・`）区切りで多項目を1文に並列列挙すると、句点までを1文として連結判定するため150字を超過しやすい
  複数文への分割または箇条書きへの展開で解消する

## 文体と箇条書き

- 強調は語句強調にのみ使い、見出しには見出し記法を使う
- 形容詞・口語表現をかぎ括弧で強調しない
- インラインコードはコードリテラル・コマンド・ファイルパス・識別子に限る
- 1文ごとに改行する
- 箇条書きは1項目1文・1項目1行とし、複数論点は階層化又は分割する
- 長い補足は丸括弧へ追加せず独立した文にする
- `preset-jtf-style 1.1.3.箇条書き`の`shouldUsePoint`を`false`とする設定のもとで箇条書き項目末尾に句点を付けない
- 冗長表現（`ja-no-redundant-expression`の`dict5`系）は`tone-examples.md`の「冗長表現」が定める処置から選んで書き換える
- 順序付きリストの1項目へ空行で区切った入れ子の箇条書き又は段落を追加すると、`preset-jtf-style 1.1.3.箇条書き`が当該リストの全項目を句点の統一チェックの対象とする。
  全ての項目が句点で終わる手順の一覧では、入れ子の要素を独立した節へ移して各項目を1行に保つ。
  監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/writing-standards/references/textlint-violations.md：文体と箇条書き：2026年9月10日」にある

## コードフェンスとラベル

- Markdownのコードブロック外側fenceに4バッククォートを採用するとtextlintは外側fenceを認識しない。
  内側文面は地の文として処理されsentence-length等の違反として誤検出される
  - 外側fenceは3バッククォートを既定とする。内側に3バッククォートを含むコードブロックを書く場合のみ4バッククォートを採用する
- 列挙の分類ラベルに英字（`a`・`b`・`c`等）を使うと違反が連鎖する
  - 全角の`（a）`は`ja-technical-writing/ja-unnatural-alphabet`違反を招く
  - バッククォート囲み表記は本書「文体と箇条書き」が定めるインラインコードの用途規約に反する
  - バレット内番号ラベル方式（`- 1. xxx` `- 2. yyy`）はmarkdownlint-cli2の自動正規化で全番号が`- 1.`へ統一され識別性が失われる
  - 分類ラベルには順序付きリスト記法（`1. xxx`形式の直接記述）または意味ラベル（「仕様変更系」「追認系」等）を使う

## 頻出違反パターン予防策

恒久成果物のtextlint実行で頻発する違反パターンを次のように予防する。

- バッククォート付き識別子（定数名・変数名・関数名など）を並べる場面では、
  テーブル形式や「`<定数名>などを典拠とする`」形式の参照記述で代替する
  （`sentence-length`違反予防）
- 俗語や不自然な比喩表現は`tone-examples.md`の「ら抜き言葉と可能表現」「カタカナ動詞比喩」「比喩動詞」の各節に従って書き換える
- AWI原文、レビュー指摘及びエラー出力の引用フレーズを、そのまま規範文へ埋め込まない。原文の主旨を保ったうえで、規範文の語尾へ整えてから反映する
- 同じ接続詞（`又は`、`及び`など）を隣接する文で続けて使わない。
  `ja-technical-writing/no-doubled-conjunction`は1文の内側だけでなく、連続する文の間でも同じ接続詞を検出する
- 同一階層で同名の見出しはmarkdownlint MD024違反を招くため、区別する語を括弧書きで付与して一意化する
- 日本語と半角文字が隣接する節名（半角空白で区切られた節名など）の参照はバッククォート囲みで書く。
  `「」`で囲むとJTF 3.1.1のauto-fixが日本語と半角文字の隣接スペースを削除し、
  計画チェック側の節名不在チェックで誤検出される

## typos擬陽性回避

typos linterは`text`コードブロック内もチェック対象とする。固有名や末尾が切り詰められたファイル名で擬陽性が発生しやすい。
除外語登録・プレースホルダー化のいずれも緩和判断に該当する。
採用可否は`lint-relax-criteria.md`の「緩和判断のフレーム」に従う。

- 対象語句が固有名・意味のある語（プロジェクト名・OSS名等）の場合は除外語登録を選ぶ
  - 登録先は`pyproject.toml`の`[tool.typos.default.extend-words]`
  - `.typos.toml`採用環境では当該ファイルの`[default.extend-words]`を使う
- 対象語句が廃棄前提の識別子（自動生成名・テスト用ダミー値等）の場合はプレースホルダー化を選ぶ
  - `XXX`等への置換と、原文の趣旨を示す注釈の併記とで対処する
