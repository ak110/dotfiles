# 危険語彙・禁止パターンの対比集

本ファイルは、口語の検出語・主観的修飾・比喩動詞・冗長表現などの意図的な違反例を収録する。
執筆者とレビュアーは、`notation-rules.md`の「Markdown記述スタイル」が定める口調例の参照契約に従って参照する。
読み込んだ悪い例の文面は指摘テキストへ転記せず、口語表現チェックの検査対象から除外する。
悪い例は観点を示すため、writing-standardsの規定違反を含む状態で保持する。

## 運用注記

- 読み込んだ悪い例の文面は指摘テキストへ転記しない
- 口語表現チェックの検査対象から除外される（`pyproject.toml`の`[tool.pyfltr] extend-exclude`で対象パスを列挙する運用）
  そのため悪い例には辞書検出語が含まれてよい
- 悪い例の文面はwriting-standardsの規定違反のままで構わない。観点を示すために必要なため意図的に違反させている
  書き換え案・解説文・観点説明文はwriting-standardsに準拠する

## 修飾過多

主観的・感情的な修飾語を名詞句に付けると、観測事実から離れて宣伝的な響きになる。
フラットに対象名詞のみで表記する。

```text
悪い例: 強力なバリデーション機能により、堅牢なコード品質を実現します。
書き換え: バリデーション機能を提供する。設定したルールに違反するコードを検出する。
解説: 「強力な」「堅牢な」は主観的修飾語のため削除し、何を提供するかを観測事実で記述する。
```

```text
悪い例: シンプルで使いやすいAPIを備えた、優れたライブラリです。
書き換え: APIは関数3つで構成される。`load`・`save`・`validate`の各関数を提供する。
解説: 「シンプル」「使いやすい」「優れた」は主観評価のため削除し、APIの構造を具体名で示す。
```

## 不要なアピール

営業的・宣伝的な記述は技術ドキュメントの読者の判断材料にならない。
「何ができるか」「どう動くか」を観測事実として書く。

```text
悪い例: 推奨は uvx での実行。事前のインストールやdev依存への追加は不要で、常に最新のpyfltrを利用できる。
書き換え: `uvx pyfltr`で実行する。事前インストールやdev依存への追加なしで最新版を取得して実行する。
解説: 「推奨は」「常に最新の…を利用できる」は宣伝的表現のため削除し、コマンドと挙動のみを記述する。
```

```text
悪い例: エージェント向け出力（run-for-agent）も用意しており、CIとの連携も容易です。
書き換え: エージェント向け出力モードとして`run-for-agent`サブコマンドを提供する。CIから呼び出すことができる。
解説: 「容易です」は主観評価のため削除し、サブコマンド名と利用可能性を事実として記述する。
```

## 擬人化副詞

警告や標準出力なしで処理が進む動作を「静かに」「黙って」のような副詞で擬人化すると、
動作内容が観測事実から離れる。何が起き何が起きないかを観測動詞や明示的な振る舞い記述に置き換える。

```text
悪い例: 設定が見つからない場合は静かにスキップされる。
書き換え: 設定が見つからない場合は処理を継続する。警告ログは出力しない。
解説: 「静かに」は処理の不可視性を擬人化する副詞のため、何が起きるか・何が起きないかを観測事実で記述する。
```

```text
悪い例: ロックが取れないときは黙ってリトライする。
書き換え: ロックが取れないときはログ出力なしでリトライする。最大3回まで再試行する。
解説: 「黙って」は擬人化副詞のため、観測可能な振る舞い（ログ出力なし・リトライ回数）に置き換える。
```

## ら抜き言葉と可能表現

可能を表す表現では、文法的な誤りや冗長な言い回しに注意する。

- 五段動詞の可能動詞（「書ける」「使える」「読める」など）は標準的な日本語表現であり、そのまま用いてよい。能動形＋「〜することができる」への過度な展開は文章を冗長にするため、簡潔に「〜できる」「〜可能である」と書くことを推奨する
- ら抜き言葉: 一段動詞・カ変動詞の可能形から「ら」を脱落させる表現（「見れる」「来れる」など）は文法的な誤りである。正しい可能形（「見られる」「来られる」）や別の動詞（「確認できる」など）に置き換える

```text
悪い例: 出力ログを見れる。設定の挙動が見れる。
書き換え: 出力ログを見られる。設定の挙動を確認できる。
解説: 「見れる」はら抜き言葉のため、本来の可能形「見られる」または「確認できる」に置き換える。
```

```text
冗長な例: 本ツールを用いることで、スクリプトを実行することができるようになっている。
書き換え: 本ツールでスクリプトを実行できる。
解説: 「〜することができるようになっている」は冗長な表現のため、簡潔に「〜できる」と書く。
```

## カタカナ動詞比喩

カタカナ造語・横文字メタファーを動詞化すると、素直な日本語動詞に比べて意味が間接的になる。
素直な日本語動詞へ戻す。技術用語として一般的に確立した語（`コンテキスト`・`アライメント`・`キャッシュ`など）は対象外。

```text
悪い例: 習慣をインストールする。マインドをリファクタリングする。人生をハックする。
書き換え: 習慣をつける。考え方を整理する。工夫する。
解説: カタカナ造語の動詞化比喩のため、対応する素直な日本語動詞に置き換える。
```

## カタカナ用語省略形

カタカナ用語・技術用語の口語的な省略形は書き言葉として定着していない。確立した正式表記を使う。
一般的に確立した略称（`API`・`CLI`・`JSON`・`URL`など）は対象外。

```text
悪い例: アーキを見直す。スペックを確認する。ドキュを更新する。インフラを増強する。
リポをクローンする。コンフィグを変更する。パラメタを渡す。環境変数は省略しない。
書き換え: アーキテクチャを見直す。仕様を確認する。ドキュメントを更新する。
インフラストラクチャ（基盤）を増強する。リポジトリをクローンする。設定を変更する。パラメーターを渡す。
解説: 口語的省略形のため、確立した正式表記に置き換える。
```

## 比喩動詞

物理動作や行為の比喩を技術文書に持ち込むと、観測可能な動作から離れて読者が挙動を確認できない。
標準的な技術用語の動詞（「分類する」「振り分ける」「同等に扱う」「適用する」など）で書く。

検出語は接触・打撃・破壊・搬送の3系統に整理できる。各系統の代表例を示す。

```text
悪い例: 不正な入力を弾く。許可されない操作を蹴る。サブコマンドを叩く。
入力値がスキーマに刺さるか確認する。型定義に噛み合うか検査する。
書き換え: 不正な入力を拒否する。許可されない操作を拒否する。サブコマンドを呼び出す。
入力値がスキーマに合致するか確認する。型定義に整合するか検査する。
解説: 接触・打撃動作の比喩のため、観測動詞「拒否する」「呼び出す」「合致する」「整合する」で置き換える。
```

```text
悪い例: 旧APIを潰す。互換シムを殺す。
書き換え: 旧APIを無効化する。互換シムを削除する。
解説: 破壊・暴力の比喩のため、観測動詞「無効化する」「削除する」で置き換える。
```

```text
悪い例: 設定を流し込む。修正をmainブランチに乗せる。
既存スタイルを引きずって書き換える。先行プロジェクトの方針を被せる。
書き換え: 設定を適用する。修正をmainブランチへ反映する。
既存スタイルを踏襲して書き換える。先行プロジェクトの方針を採用する。
解説: 俗語的・乱暴な比喩表現を避け、「適用する」「反映する」「踏襲する」「採用する」「取り込む」など、技術・編集の文脈で確立された自然な動詞を用いる。
```

## 冗長表現

動作名詞に「を行う」「を実施する」を機械的に重ねると、冗長な文章になりやすい。
多くの場合は、動作名詞を直接動詞化（サ変動詞化）するか、簡潔な動詞に戻すことで明瞭になる。
ただし、複合語などで無理に分解すると不自然になる場合は、前後の文脈やリズムを優先して自然な表現を選ぶ。

```text
悪い例: 設定の読み込みを行う。
書き換え: 設定を読み込む。
解説: 「読み込みを行う」は「読み込む」と簡潔に動詞化できる。
```

```text
悪い例: 整合チェックを行う。事前確認を実施する。
書き換え: 整合をチェックする（または整合性を確認する）。事前に確認する。
解説: 動作名詞が複合語の場合は、「整合をチェックする」「整合性を確認する」「事前に確認する」のように無理のない自然な語を選ぶ。
```

```text
例文: ファイル出力を実行する。全項目を実施する。
解説: コマンドラインやスクリプトなどの起動動作を表す文脈での「実行する」や、単体動詞としての「実施する」は問題なく使用できる。
機械的な言い換えによって文が不自然にならないよう配慮する。
```
