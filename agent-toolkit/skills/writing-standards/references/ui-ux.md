# 画面の設計と実描画による検収

本書は、エンドユーザーが操作する画面を計画、作成、変更又はレビューする主体が使う共通基準を定める。最初に利用者の目的、主要な操作、既存のデザインシステムを調べ、操作から結果までの流れを定める。

参考資料: [frontend-ui-ux-skill](https://github.com/overseek944/frontend-ui-ux-skill)、[ux-designer-skill](https://github.com/szilu/ux-designer-skill)、[Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)。これらの要点を日本語の判断基準へ再構成した。個別の数値は末尾の一次資料を典拠とする。

## 判断の順序

依頼者の明示指示、対象プロジェクトのデザインシステムと一貫した慣例、本書の既定をこの順に適用する。着手前に既存のコンポーネント、トークン、スタイル規約を調べ、同じ役割の部品や値は既存のものを再利用する。画面を使う人と、その人が画面で終える仕事を特定し、主要な操作から結果まで到達できる設計を選ぶ。

## 操作と情報

- 画面の主目的と主要操作を明確にし、関係の薄い操作は次の段階で示す。選択肢が増えるほど判断が遅れるため、関連項目をまとまりで配置する。3〜5件はまとまりを点検する目安とし、必要な項目の表示を優先する。
- 操作の結果、現在の状態、取り消し方、エラーからの復旧を利用者が分かる位置へ示す。画面の言葉と配置は、その分野で利用者が慣れた慣例と利用者の言葉を優先する。
- 頻用する主要操作は見つけやすく押しやすい領域へ置く。破壊的操作は頻用操作から離し、誤操作の損失に応じて確認又は取り消し猶予を設ける。
- 表示する情報と操作は、利用者がその場で判断する順に並べる。取り消せる操作は手戻りの経路を示し、入力を保持して再開できるようにする。

## 状態と内容

- 初期表示、読み込み中、空、結果あり、入力エラー、通信エラー、保存中、保存後を、到達する操作とともに設計する。読み込み中は最終配置に近い領域を予約し、操作開始から約100ms以内に進行を示す。空状態とエラーには、その状態から取れる次の操作を示す。
- 短い値、通常の値、表示幅を超える長い値で、情報と操作の全体へ到達できることを確かめる。文字の折り返し、行数の制限、全文への到達手段を用途で選ぶ。
- モーダルや割り込みは、現在の作業を止める必要がある場合に使う。情報通知は文脈と緊急度に合う位置と持続時間を選び、無効ボタンには理由を示す。

## 視覚と構造

- 文字サイズは少数の一貫した比率、余白は4px又は8pxを基準にしたトークンで構成する。ブランド色と成功・警告・危険の意味色を分け、文言や形状も使って意味を伝える。
- ライトとダークの両テーマを提供する画面では、それぞれの文字、境界、背景、フォーカスを確認する。ダークテーマの新設は、その画面の要求に応じて判断する。
- 動きには150〜300msを目安とし、位置や透明度の変化へ用途を限定する。`prefers-reduced-motion`では装飾的な動きを抑える。
- ネイティブの操作要素と意味のある見出し構造を優先する。モバイルの幅から配置を組み、横幅が増えたときに情報密度を調整する。左右方向に依存するスタイルは論理プロパティーを使い、ページ本体の横スクロールを避ける。
- 一律の角丸と影、根拠のないグラデーション、どの製品にも当てはまる定型文言を使う場合は、製品の情報、操作と既存トークンから必要性を確認する。

## アクセシビリティと性能

WCAG 2.2 AAを下限として、キーボードだけで全操作を終え、フォーカス位置を視認できる状態を保つ。入力欄とラベルを関連付け、入力エラーと非同期の結果を読み上げられるようにする。通常文字のコントラストは4.5:1以上、大きな文字と情報を伝えるUI部品の境界は3:1以上とする。操作対象はWCAG 2.2 SC 2.5.8の24×24 CSS pxを下回らず、主要なタッチ操作は44px程度を目安とする。

実際の利用環境でCore Web Vitalsを測定できる場合は、LCP 2.5秒以下、INP 200ms以下、CLS 0.1以下を良好域の目標にする。画像と埋め込みの領域を先に予約し、初期表示に不要な資源は後で取得する。性能の判定は同じ端末とネットワーク条件で測り、静穏な条件で得た値を比較に用いる。

## 完了前の実描画確認

ブラウザーを利用できる環境では、変更した画面を実際に描画し、次を観測してから完了とする。実装者の自己点検と独立した画面レビューの双方で同じ観測を使う。

1. エンドユーザーと同じクリック、入力、キーボード操作で、主要な利用シナリオを結果まで終える。
2. ドロップダウン、ダイアログ、読み込み中、入力エラー、空の一覧、通知など、操作後に現れる状態へ実際に到達する。それぞれの画面キャプチャーで配置、文言、フォーカスと読み上げの対象を確認する。
3. 320px幅と400%拡大、キーボードのみの操作、利用するテーマ、`prefers-reduced-motion`、短い値と長い値を確認する。重複した固定値、不要な要素、横スクロールも点検する。
4. 観測した問題を修正し、同じシナリオと状態を再確認する。問題が解消した観測をもって画面の作業を完了とする。

描画手段には対象プロジェクトのE2E環境、Playwright又はブラウザー操作ツールを使う。ブラウザーを利用できない環境では、確認した条件と未確認の画面状態を記録し、実描画の適否を未確定として報告する。

## 数値の一次資料

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/): 通常文字4.5:1、大きな文字と非テキストの情報部品3:1、SC 2.5.8の操作対象24×24 CSS px。
- [web.dev Core Web Vitals](https://web.dev/articles/vitals): LCP 2.5秒、INP 200ms、CLS 0.1の良好域。
- [Apple Human Interface Guidelines: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons): タッチ操作領域44×44 ptの目安。CSS pxへの等価換算ではなく、主要操作の余裕を設計する参考値とする。
