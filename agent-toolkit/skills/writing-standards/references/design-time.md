# 設計時のコーディング品質

本書は計画ファイルを作成する時点で確定する実装方針、エンドユーザーデータの移行方針およびエンドユーザー接点の規範を扱う。
コードを編集する時点の規範は`implementation-time.md`が扱う。

## 実装方針の選択

- 必要性を先に確かめ、標準機能と既存依存を優先し、独自実装は最後に選ぶ。案の比較は`design-heuristics.md`「問題と手段の比例性」に従う
- 標準仕様のある形式（YAML・JSON・TOML等）は、サブセットを自前パースせず正規のパーサーで読み書きする（サブセット実装は複数行・入れ子の値などの正当な入力を静かに誤読する）
- 集計値の判別条件と、入力形態が複数あり得る解析処理（正規表現・パーサー・突合条件）は、対象の命名規則・出力仕様が生成し得る形態を洗い出してから確定する。構造化データ（frontmatter・JSON等）は構造を解析した結果を根拠とし、条件に合致しなかった対象も個別に確かめて取りこぼしと過大計上の双方を防ぐ。
  既存の解析処理を変える場合は変更前後を全形態へ適用して比べ、変更前に取れていた情報が意図せず取れなくなる案を採用対象から外す。意図した除外なら理由を計画か変更の説明へ残す
- 公開仕様の解析は、利用可能な参照実装と突合して仕様準拠を確かめる（努力目標）
- 自動承認やポリシー判定に用いる解析処理を新規作成・変更する前に、入力生成主体、信頼境界、通常入力、対象外入力、誤許可と誤拒否の影響を明示し、実装とテストの入力集合をこの宣言へ合わせる。宣言外の脅威モデルを暗黙の要件として追加することを禁止する

## エンドユーザーデータの移行

永続するデータと継続的に増えるデータを新設・変更する場合は、想定する保持期間と容量、容量上限、上限到達時にエンドユーザーが観測する動作、保守を起動する契機と所有者を、固定の汎用上限や自動削除ではなく利用シナリオから導いて設計時に確定する。完了判定には、保持期間か容量が長期条件へ達した状態の検証（縮小モデル、境界値、実際に測定できる運用手順のいずれか）も含める。

- エンドユーザーが蓄積したデータ（ファイル配置・ファイル形式・スキーマ・設定形式）を変更し、移行しないと蓄積データが読めなくなるか失われる場合と、コマンドや機能の起動が失敗する場合は、旧形式からの移行処理を同一の変更へ含める。移行は実装が完遂する。
  技術的制約で含められない場合に限り、拒否時の案内文へエンドユーザーが単独で完遂できる手順を書き、案内文が要求する外部の状態は実装するエージェントが用意しておく
- 移行処理と案内出力が同じ対象を扱う場合は判定関数を共有し、移行成立後に案内が自動的に無効になるようにする
- 設定キーや環境変数の改名・統合・削除で、旧キーの値が無視されても文書化された初期値の動作へ戻るだけで失敗しない変更は前項の対象外とする。旧キーを撤去して破壊的変更として記録し（commitでは`agent-toolkit:commit`の`references/message.md`の`!`）、エンドユーザー向け文書から旧キーの記述を除き、旧キーの解釈、自動移行、移行待ちの表示、旧キー専用の拒否と案内は設けない。
  初期値へ戻るとセキュリティ上の保護が外れる場合と、1回の設定操作では旧キーで得ていた動作を再現できない場合は前項に従う

## エンドユーザー接点と公開インターフェース

- CLIの案内は操作に即した語で対象・拒否理由・次の操作を示し、現行仕様だけで理解でき、拒否した値と違反した条件を識別できる文面にする
- 受理条件と文言は同じ定義から導く（努力目標）
- 関連するモジュールでは命名・エラー処理・返却値の規約をそろえる
- 公開インターフェース（API・UI、CLIオプション・設定形式・出力形式、ライブラリの公開関数・公開クラス・データ形式など配布物のエンドユーザーが直接触れる面）を変更する場合は、追従が要るテスト、ドキュメント・サンプル・出力例、利用元のコード、エラーメッセージ・案内文を全件洗い出す。洗い出しには変更した識別子・出力文字列の全文検索を使う。
  この洗い出しではリポジトリ内部のモジュール・関数・クラスはpublic修飾の有無を問わず内部実装として扱う（テストの検証単位を選ぶ基準には使わない）
