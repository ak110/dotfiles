# 実装時のコーディング品質

本書はコードを編集する時点で適用する記述順序、データ処理、リソース管理、セキュリティおよび機械チェックの規範を扱う。
計画ファイルを作成する時点で確定する規範は`design-time.md`が扱う。

## 編集前の読解

- 編集対象ファイルは、部分読解によるスタイル逸脱とリファクタリングの必要性の見逃しを避けるため、編集前に全体を読む。
  実装の仕様は実装本体を読んで確定し、docstringは補助の材料として扱う

## 記述順序と命名

- 上位から構造をたどれる順序で、関連する定義を近くへ置く（努力目標。読解を容易にする）
- 追加先全体の命名と用語を観察し、既存規約へそろえる（努力目標。検索と読解の一貫性を保つ）

## 言語横断のツールと構文

プロジェクトに指定が無い場合は、次の標準ツールを使う。

| 言語 | 依存管理・ビルド | lint・format・補助ツール |
| --- | --- | --- |
| Python | `uv` | `pyfltr`、`pytilpack` |
| TypeScript | `pnpm`、一度限りの実行は`pnpx` | `Biome`。未対応ルールが必要な場合だけESLintとPrettierを併用 |
| Rust | `cargo` | `cargo clippy -D warnings`、`cargo fmt` |
| C# | `dotnet` CLI | `dotnet format`、Roslynアナライザー、`Microsoft.CodeAnalysis.NetAnalyzers` |
| Bash | 該当なし | `shellcheck`、`shfmt` |
| PowerShell | 該当なし | PSScriptAnalyzer |

公開互換性として宣言した範囲で利用できる新しい言語機能を積極的に使う。
利用可否は対象プロジェクトの言語バージョン（Pythonの`requires-python`、TypeScriptのバージョン、Rustの`rust-version`・edition、C#の`LangVersion`・`TargetFramework`など）と公式リリースノートで確認する。
確認先は次のとおりとする。

- Python: <https://docs.python.org/3/whatsnew/index.html>
- TypeScript: <https://www.typescriptlang.org/docs/handbook/release-notes/overview.html>
- Rust: <https://doc.rust-lang.org/releases.html>
- C#: <https://learn.microsoft.com/dotnet/csharp/whats-new/>

構文は公開互換性として宣言された全対応版で受理されることを確認する。この判定には、固定された開発・実行版だけでなく、宣言された全対応版での受理を用いる。
同等の品質で代替できる場合は、外部依存より標準ライブラリを選ぶ。
依存を減らすと保守費用が下がる一方、標準ライブラリで書く実装量や品質差が依存の保守費用を上回る場合もあるため、比べる順序は`design-time.md`「実装方針の選択」に従う。
プロジェクト固有の規約はそのプロジェクトの`CLAUDE.md`・`.claude/rules/`へ置く。

## コメントの記述粒度

- コメントは意図・成立条件・非自明な理由を残す（努力目標。自明な処理の再掲による乖離を避ける）
  - 実装の判断根拠となる外部の挙動と観測値は、その根拠を失うと後続の変更が分岐の成立条件を判定できなくなるため、観測した原文のまま残す。
    規範は安定したファイルと節、観測は再現条件、ユーザー要望は恒久的な要件もしくは外部挙動へ変換する。変換の対象をこれらに限定し、セッション、個人および対話の経緯は手元の記録にとどめる
- 設定値・変数値・数値リテラルそのものは、同じ値がコード上に現れて重複記載となる場合はコメント本文へ埋め込まず、
  値の選定理由・制約の根拠のみを書く（値変更時のコメント修正の取りこぼしで実態と乖離することを避ける）
  - その値がコード上に現れないか、コード上の値と別の出所を持ち、かつ判断根拠として必要な場合は本項の対象から外し、出所とともに書く
- 冒頭は役割と適用範囲、局所のコメントは実装の判断を説明する（努力目標。構造と細部を読み分けられるようにする）
- 同じ概念の説明は呼出関係の起点へ集約し、定義を一元化する
- ドキュメントはコードからわからない情報や意図・設計理由を書いて現在の状態を直接記述し、時系列表現を避けて履歴はコミットメッセージへ委ねる
  （努力目標。時系列の記述は現状と乖離しやすいため）
  - 過去の挙動が現在の判断の根拠となる場合は、履歴へ委ねず、その挙動を判断根拠として現在の記述へ含める

## データと計算

- 計算量を入力規模に合わせる
- 浮動小数点: 金額など正確さが必要な計算には整数演算や専用の十進型を使い、等値比較は許容誤差で行う
- 日時: 意味を区別し、プロジェクト方針が無ければタイムスタンプはUTC、市民時刻はタイムゾーン情報を保持する。
  CLI引数など外部から受け取る時刻がタイムゾーンを持たない場合の扱い（拒否するか、どのタイムゾーンの時刻とみなすか）は、入力の意味から決めてヘルプへ書く。
  記録やファイルなど内部データ向けの解析処理の扱いを流用しない。手で書く値をUTCとみなすと、ローカル時刻のつもりで書いた境界がタイムゾーンの差だけずれ、該当0件の結果と区別できない
- 文字エンコーディング: 詳細規定は`encoding.md`が定める
- 可変長入力の境界: hashや識別子の入力に複数の可変長値を連結する場合は、長さ接頭辞または仕様で一意な正規形式により境界を一意にし、異なる値の分割が同じ入力列にならない反証ケースをテストする
- 乱数: 言語標準APIを使い、シードには予測できない値を使う。範囲変換には専用API（`randint`等）を使い、
  剰余での変換は避ける。セキュリティ用途ではCSPRNGを使う
- 整数オーバーフロー: 固定幅整数を扱う言語では、意図しないオーバーフローが生じ得る演算・型変換に
  オーバーフロー検出付きの演算、より広い型、事前の範囲検証のいずれかを適用する。
  意図的なラップアラウンドは、言語仕様で剰余動作が保証される演算・型、または専用のwrapping演算といった
  実行時に成立する機構で表す。コメントは実行時の演算を変えないため、意図の補足として併記する
- ファイルの更新時刻: 更新時刻とサイズの一致を内容が変わっていないことの代わりに使う場合、
  更新時刻の精度はファイルシステムが決める（1秒や2秒の環境がある）ため、精度の範囲内で同じサイズのまま書き換えても更新時刻とサイズは変わらない。
  値の単位がナノ秒でも、精度は環境ごとに確かめる。更新時刻から精度の幅以上が過ぎてから読んだ結果だけを再利用し、それより前に読んだ結果は次回に読み直す

## リソースと並行処理

- 資源の所有と解放を対応させ、RAII等で寿命を管理する
- 共有状態を減らし、残る共有には同期を設ける。I/O待ちは非同期処理を基本とする

## セキュリティ・ロギング・エラー処理

- セキュリティ: 信頼境界（外部入力・API応答・ユーザー操作など）を常に意識する
  - 外部入力はコマンドの引数として渡し、評価系コマンドが受け取るコードは固定する。動的な実行が必要な場合は固定候補へ分岐する（言語別の書き方はその言語の資料が定める）
  - 入力検証は型・範囲・形式を検証し許可リスト方式を優先する。
    SQL・コマンド・HTMLなどの実行・解釈文脈への直接結合、
    未正規化のパス構築によるパストラバーサル、信頼できないデータの安全でない復元は避ける
  - シークレットの保管先と出力先は、ソースコードとログの外に限定する。プロセス・トークン・DB接続などの権限は必要最小限にし、
    スタックトレース・内部パスなどの内部情報をエンドユーザーへ露出しない
- ロギング: 障害時の原因究明を前提に書き、構造化ログ・相関IDの伝播を推奨する
  - シークレット・個人情報も、ログの出力対象から除外する
- エラー処理: 例外の種別ごとに方針を決めて扱う
  - 一時的エラー（ネットワーク・ロック競合等）はリトライ対象。指数バックオフ + ジッタを基本とする
  - 永続的エラー（入力不正・権限不足等）は即座に失敗させ、呼び出し元に原因を返す
  - プログラマエラー（不変条件違反）はfail-fastで例外を送出し、上位へ伝播させる
  - catchは具体的な型に限定し、広域キャッチは境界層に限る。リトライ回数・タイムアウトは設定可能にする
  - 失敗の原因を報告する前に後始末の時間制限付き待機が超過する場合は、その待機が送出する例外を捕捉し、待機対象の強制終了と回収を終えてから原因付き報告へ制御を戻す。同じ待機が複数箇所にある場合は、停止・待機・超過時の回収を1つの関数へ集約する。後始末の例外が元の失敗報告を置き換えると、呼び出し元が失敗原因を判定できない
  - 外部状態の取得失敗時に安全側の結論（処理の中止・延期など）を採用する判定では、先に保護対象への
    到達可能性（所有権・権限・アクセス境界など、判定結果へ実際に影響する条件）で母集団を定め、
    母集団内の対象の取得失敗だけを安全側の根拠とする。安全側の根拠となる取得失敗は、母集団内の対象に限定する。
    母集団と取得失敗時の扱いを定めた後、実環境の入力に対してその結論が常時成立しないことを実物の観測で確認する。
    母集団を定めずに取得失敗を安全側の根拠とすると、判定と無関係な対象の取得失敗によって
    結論が常時成立し、その機能を恒久的に停止させる

## 依存と自動生成物

- 依存と設定は専用CLIを優先し、lockとmanifestを一致させる。生成物は生成元または専用CLIから更新する
- 自動生成ファイルを直接編集する必要があると判断した場合は、生成元側の設定変更で表現できないかを先に検討する
- 既存コードの意図的な制約（型制約・アクセス制限・lint設定・不変条件のアサーション等）は、新規コードを追加するときも維持する。
  制約の変更が必要と判断した場合は先にその必要性を検証する

## lintと機械チェック

- lint指摘への対応方針は`agent-toolkit/rules/01-agent.md`「判断指針」のQCD（Qualityを先に守り、その範囲でCostとDeliveryを比べる）で決める。本節をlint対応の原則の定義の所有者とし、抑制を採用するかどうかも実行主体が技術判断として確定する
- 正当な指摘は修正し、意図した設計に当てはまらない指摘だけ必要な範囲で抑制する。理由が自明でなければ併記する
- ファイル・設定単位の緩和は、方針との不一致か反復する抑制があり、局所の対処では足りない場合に限る。後続の違反も見逃す影響を評価する
  - ファイル全体の上限抑制も同じ判断を要する。過大化が原因なら責務やシナリオでの分割を優先する
  - 振る舞いを変えずlintの指摘だけを回避するコード変更は避ける
  - 抑制コメントの新規追加時は、同ファイル内・同種ファイルにある既存の抑制コメントとは独立に本節の判断基準を適用する
  - 対応する個別実行で変更対象を事前に確認し、自動修正を反映する
- lintルール・機械チェックを新規に有効化・強化する変更は、着手前に既存コードへの検出結果をトリアージする工程を対応方針へ含める。
  区分は「共通化・修正すべき是正対象」と「意図的な設計による許容対象（理由コメント付き抑制等で対処）」とし、検出を件ごとにこの2区分へ割り当てる
  - 例: `pylint`の`duplicate-code`では、同期・非同期の並行実装やプラットフォームペア実装間の類似が意図的な許容に該当し得る
