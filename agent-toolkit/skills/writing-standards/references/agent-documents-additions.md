# コーディングエージェント向け文書への追記と記述量の管理

本書は、コーディングエージェントが直接読み込む文書へ新しい規定を追記する場面と、
文書の記述量を管理する場面の判定基準を定める。
文書の責務、記述内容、条件の書き方及び語調の基準は`agent-documents-basics.md`が定める。

## 規範追記時の判定

規範文書へ新しい規定を追記し、又は既存の記述を改訂する前に、その文章がQCDへ貢献するかを判定する。
判定は`agent-toolkit/rules/01-agent.md`「判断指針」が定めるQCDで行い、貢献しない文章は書かず、既存の文章であれば除去する。
読む主体のコンテキストを占めるだけの文章は、Costを増やしてQualityもDeliveryも改善しない。

そのうえで、次を確認する。

- 一般則で表現できる事象は一般則で書く。既存の一般則の補強が目的を満たす場合は、その補強だけを行う。
  観測した事象はその事象が属する類型を特定して原則として書き、観測事実は原則の裏付けとして併記する。
  条文の適用範囲は、観測した事象より広い類型の範囲で書く
- 同じ目的を果たす既存条文を統合又は撤去できないかを併せて判定する。判断材料は、追加する条文がもたらす適用範囲の拡大と、
  常時ロードされる読み込み量の増加との比較とする。統合可否の判定根拠は「文書記述量の管理」に従う
  （努力目標。個別の条文が積み上がると、適用範囲を広げないまま毎セッションの読み込み量だけが増える）
- 規範へ判断の分岐、報告本文の欄、成果物の欄のいずれかを書く場合は、対象を個別に列挙する形と、列挙全体を貫く
  判定基準として表現する形を比較し、基準で表現できる場合は基準を選ぶ。既存の列挙形式へ是正指示を
  反映する場合も同じ比較を先に行う。列挙又はプレースホルダー参照を残す場合は、列挙に当たらない場合の
  扱いと、その欄が覆う対象範囲を同じ条文へ書く。
  列挙外の扱いと対象範囲を定めない条文は、実行主体が狭い解釈を選んでも違反にならず、
  意図した場面で発火しない
- 追記する規定がメインエージェント、サブエージェント及び委譲先の全てへ適用されるかを判定する。
  全てへ適用する規定だけを`agent-toolkit/rules/`配下へ置く。
  メインエージェントだけに適用する規定は`agent-toolkit/share/rules-main.md`へ置き、Claude Code固有分は`agent-toolkit/share/rules-main.claude-code.md`へ置く。
  サブエージェントと委譲先だけに適用する規定は`agent-toolkit/share/rules-subagent.md`へ置く。
  これらは実行環境が各主体の起動時に文脈へ追加するため、常時ロードと同じ拘束力を持つ。
  委譲元と委譲先の双方が守る受け渡し規定は、全てへ適用する規定として扱う。
  片側だけに適用する規定を`rules/`へ置くと、適用対象でない主体がその規定を自身へ適用する。
  特定作業時のみ必要な内容はスキルまたは`references/`へ置く
- 常時ロードされる規範（`agent-toolkit/rules/`配下・`AGENTS.md`・`CLAUDE.md`）がスキル又は`references/`の
  起動・読込を指示する箇所では、起動契機、起動対象及びそのスキルが正本とする範囲だけを置く。
  スキル側の正本が扱う観点、判定手順、例外及び具体例は、スキル側だけが持つ。
  これは既定で従う規定である。
  同じ判定が常時ロード側とスキル側の双方に置かれると、実行主体がどちらを正本とするか判定できない。
  適用対象を広げないまま全工程の読み込み量だけが増える
- 共通手順のレビューでは、生成元と全消費側の列挙、定義の所有者、参照又は呼び出しの到達性、同期検査を確認する。同じ判断を複数箇所が独立に定義している場合は、所有者へ統合し、各消費側の範囲、認可、検証及び終端条件を保持する。スキル間とタスク文書間でも、同じ判定を転記せず、読込契機から正本へ到達できる参照を置く
- 規範が入口として名指しする起動対象は、その規範を読む実行主体が自ら起動できるものに限る
  （努力目標。起動できない対象を入口として読んだ実行主体は起動に失敗し、別の入口を探し直す分の工程を失う）
- 知識の追記は、その追記が生む便益と、常時読み込むコンテキストが増える費用を比べて採否を決める
  （努力目標。費用が便益を上回る追記を重ねると、判断へ使わない記述を毎セッション読む分だけ本来の作業へ回る能力が減る）
- 規範、基準又は目標値が定められているかを判定する場合は、その判断をする工程でその記述がコンテキストへ載るかを
  確認する。単なる検索結果の一致だけで判断せず、実際に読み込まれる経路を確認する
- 数値の閾値・複雑な判定手順を、単純な原則で代替できないか。
  閾値を置く場合は境界値の妥当性根拠を本文へ残す
- 宣言だけで実行時に遵守されると期待していないか。作業手順の特定時点で必要な規範は、
  観測可能な契機と結びつけた読込・起動指示（「〜を検知したら〜を読み込んでから編集する」等）として
  その工程へ埋め込む（努力目標）
- 直接操作又は代替手段に関する要件を新設、改訂又は移設する場合は、操作開始に必要な対象と入力を列挙し、
  同じ読込文脈から対象と入力を取得できる観測可能な手段を記載する
- 品質要件を生成側（起草時と実装時の完成条件）と検出側（レビュー観点、検査項目、機械検査）のいずれか一方へ追加する場合は、
  もう一方へも同じ改訂で追加する（努力目標。片側だけにある要件は、書かれても検出されないか、検出されても書き手が知らないまま残る）
- 実行環境とモデルのいずれかの版数を伴う条文では、その条文へ観測事象だけを書き、実測した日付、観測した版数及び再検証手段をそのリポジトリの`docs/development/audit-records.md`へ記録して所在を条文から示す（努力目標。版数を固定した条文は、次の更改で観測を経ないまま失効する）
- ユーザーへの発話へ適用する規定を追加しようとしていないか。発話を書く時に参照する規範は
  `agent-toolkit/share/rules-main.md`「ユーザー向け発話ルール」節だけとし、同節へ置くのは、
  守らないとユーザーへ内容が伝わらない条文に限る。発話を適用対象とする規定は同節だけが持つ
  （努力目標。発話のたびに参照する規定が増えると、発話を書く判断へ能力が費やされ、本来の作業へ回る分が減る）
- 同一の事象へ反対の判断を与える条文を併存させない。追加する規定と衝突する既存条文を見つけた場合は、同じ変更でその条文を置換するか、優先順を確定する。
  別リポジトリの所管で同じ工程に解消できない場合は、そのリポジトリ向けのAWIへ記録する。
  衝突したまま併存させると、実行主体がどちらを適用するか判定できない
- 規定を追加・強化する場合は、既存成果物のうちその規定へ違反する箇所を探し、同じ変更で是正する
  （努力目標。違反を残すと、後続の実行主体が既存例を慣例として再利用し、同じ違反を反復する）
- 複数の委譲先の起動を定める手順では、起動ごとの固定コストと呼び出し元の待機往復が件数だけ積み上がるため、1件へまとめた手順を初期案とする。分けて起動する場合はその理由を条文へ書く（努力目標）
- 工程の完了条件を定める規定では、その工程が達成すべき成果を条件として書く。
  記録項目の充足だけを完了条件とすると、その工程の目的を満たさない成果が完了として確定する

計画やレビュー契約へ、実装順序・単位分割・個別コマンドなどの手順詳細を記載する場合は、既存規範と確定済み外部仕様から一意に導出できないかを確認する。一意に導出できる詳細は省略し、安全性、データ保全、公開契約又は主体間の認可境界を守るために必要な場合だけ明示する。

## 文書記述量の管理

対象は、コーディングエージェントが読み込む配布物と、その判定条件を持つ機械チェックの実装コードとする。
これらを新規作成・改訂する際は、記述量を現状の水準で保つことを既定とする。
既存記述との重複統合（除去・統合・`references/`分離のいずれか）を常に検討する。
本規定は努力目標とし、合計行数への上限は機械検査の外に置く。

常駐規範の削減をユーザーが求めた場合の範囲と手段は次のとおりとする。
削減の対象は、名指しされたファイルにかかわらず自動ロード対象の常駐規範の全体とする。
既定で従う規定として明記された条文も検討の対象とし、削除も候補に含める。
移設先のスキルが無い場合は新規スキルの作成を採用してよい。
削減の目標値は、ユーザーが具体値を示した場合だけ採用し、示されない場合は本節の判断基準で採否を決める。

規範量が作業へ影響する経路は、同一契約の分散で同期対象箇所が増えることと、判断に使わない記述を起動時に読んで初期コンテキストを消費することの2つとする。削減対象はこの2つの経路で決め、総バイト数は判定の補助に留める。
記述は次の5階層を持ち、読む主体と必要になる時点に合わせて配置する。
階層と配置先は次のとおりとする。

- 常時ロード: `rules/`とfrontmatterの`description`
- 主体別注入: `share/`配下の`rules-`で始まるファイル
- メイン起動時: `SKILL.md`本体
- 明示Read時: `references/`
- サブエージェント注入: agent定義とfrontmatterの`skills`
スキルの本数削減は常時ロード量をほとんど減らさない。削減では、`SKILL.md`本体から`references/`への退避とagent定義の縮小を先に検討する。
スキルの統廃合は消費主体が観測する起動経路を変えるため、その変更が起動の判断を改善する場合に採用する。

文体、表記及び口調の統制は、編集時のフックとlintによる機械検査を一次手段とする。
規範文書は生成時の予防ガイドとして維持し、機械検査と重複する細則のうち細かすぎるものだけを削減する。
検出後の書き直しだけに頼ると、初出の指摘とその対応の往復が増えるためである。

統合を検討する場合、削減判定は次のいずれかの根拠を満たすことを条件とする。

- SSOT違反: 他ファイルに正規の記述がありここは転記に過ぎない
- 自明導出: 上位指針・学習データから自明に導出できる。
  ただし知識として自明でも、明示されないとエージェントが安定して考慮しない種類の観点
  （セキュリティ・エラー処理の作法など）は自明導出に当たらない
- 公式ドキュメント代替可能: 公式ドキュメントの一次資料参照で同等の情報が得られる
- 上位指針への統合: 細則列挙を束ねる上位指針へ昇格できる。
  同一工程を扱うバレットが同一節配下へ並列蓄積している場合も統合を検討する
- 手段固定: 達成すべき性質ではなく特定のコマンド、ツール、実行順又はパスを固定し、その手段でなければ性質を満たせない根拠を併記していない
- 個別事象特化: 観測1件の対象、工程又は識別子へ貼り付いており、機構の水準の一般則へ畳める
- 条件の入れ子: 例外と除外が重なり、条件と行動が一対一で対応していない
- 拘束力の過剰: 技術的な不成立、データ破損、公開インターフェース破壊、セキュリティ欠陥のいずれも防がない条文を既定で従う規定として書き、適用範囲と除外を列挙している

数値・閾値・境界値の判断根拠部分（由来・境界を分ける理由・トレードオフ）は削減対象から除外する。
削減後に規範性が失われる場合は他節での代替可否を確認し、代替不能なら圧縮せず残す。
既存規範を圧縮・統合する際は、元の規定が持っていた順序の制約・前提条件・除外条件をそのまま保つ。

記録先を新設、改名又は移設する改訂では、同じ内容の記録を求める既存条文を新しい記録先を指す参照へ置き換える。
同じ内容を2つの記録先へ求める条文が併存すると、実行主体がどちらを正本とするか判定できなくなる。

圧縮・統合・削除のいずれの操作でも、次の項目は保護対象として維持し、削減しない。

- 本文冒頭の目的記述（適用判断の核となる動機）
- 開いた列挙表現（「等」「〜を含む」「〜など」）。閉じた列挙への書き換えは範囲を狭めるため避ける
- 同一ファイル内の既存表記との整合が必要な用語と、並列表現の対称性

行数調整のみを目的として、必要な意味内容や前提条件を省く操作は避ける。
