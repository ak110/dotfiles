# Playwrightテスト記述スタイル

本書はPlaywright Testでブラウザーテストを書くエージェントとレビューするエージェントへ、ロケーター、アサーション、テストの分離、flaky対策、Page Object Modelの採否と並列実行の設定で判断を誤りやすい箇所の基準を示す。
対象バージョン: Playwright Test v1系（参考実利用バージョン: 1.60）。公式のベストプラクティスは<https://playwright.dev/docs/best-practices>を参照する。
本書はPythonバインディング（`playwright.async_api`・`playwright.sync_api`）を用いるテストへも適用し、綴りが異なるAPIは同じ機能のPython側の名前へ読み替える。

## ロケーター戦略

- エンドユーザーが認識するroleと名前を第一候補にし、特定できない要素はtestIdを使う。DOM構造に依存する選択は最終手段とする

## アサーション

- 観測可能な状態をweb-first assertionで検証し、一時点の判定で非同期の完了を代用しない
- `page.waitForTimeout()`とPythonバインディングの`page.wait_for_timeout()`による固定時間待機は使わない（`testing.md`「安定性: flakyテスト防止」の同期点の手段）。状態変化を待つ場合は独自の待機ループを実装せず、ロケーターの自動待機・actionabilityチェックまたは`expect().toPass()`を使う
- 画面がエンドユーザーの操作によらず非同期処理を始める場合は、その処理の観測できる結果（表示された本文、置換後の要素、送られた要求など）を待ってから、外部状態の変更、要素の寸法の測定または送信された要求の記録へ進む。非同期処理には初期表示での自動選択と本文の取得、外部変更の通知による再読込、遅れて加わるスタイル、再描画による要素の置換などがある。可視になった最初の要素を画面の準備完了とみなさない。ローカルの単独実行では自発的な処理が先に終わって成功しても、負荷の高いCIでは処理の結果がテストの操作より後に届く。その場合、テストは操作の対象を失うか、処理の前後で異なる測定値と記録を得る

## テスト分離

- テストは順序と他の結果から独立させ、状態を隔離・回収する。認証はsetupとstorageStateで再利用する
- 制御できない外部サイトはNetwork APIで代用し、外部の可用性をテストの前提にしない

## flaky対策

- `retries`設定はCI環境でのみ有効化し、ローカル実行では0のままにする（ローカルでの再試行はflakyの発見を妨げるため）。CIの再試行は次項のトレースを得る手段として使い、失敗を通す手段にしない。Playwright Testでは`failOnFlakyTests`（CLIでは`--fail-on-flaky-tests`）を併せて有効にし、再試行で成功したテストを含む実行を失敗として扱う。そのテストは`testing.md`「失敗テストの除外による回避禁止」に従って根本原因を直す
- `trace: 'on-first-retry'`を設定し、CI上のデバッグ手段は動画・スクリーンショットよりトレースビューアーを優先する。トレースは操作ログ・DOM・ネットワークを時系列で参照でき、失敗原因の特定が容易なため

## Page Object Model採用の判断基準

POMは構造化の選択肢とし、再利用と変更箇所の集約が維持費用を上回る場合に採る。小規模な操作列はテスト本文へ置いてよい。

## 並列実行・CI設定

- CIは変更に近い時点で実行し、測定した所要時間に応じてshardingを選ぶ
- 対応するブラウザーをprojectsで分離し、Playwrightと同梱ブラウザーを更新する
- 非同期処理の未完了は静的解析でも検出する
