# SQLAlchemy

SQLAlchemy 2.0系のORMを使うコードへ適用する。
NULLチェックには`.is_(None)`を使う。
既定構成の`Session`はORM対応の問い合わせを送信する前に保留中の変更をflushする。
このautoflushにより、入力検証で扱うべき誤りがDB制約違反として先に送出されることを防ぐ。

## 成立条件

次の条件が全て成立する処理を対象とする。

1. `Session`のautoflushが有効である。
2. 永続インスタンスのマップ済み属性を更新中か、新規行を`Session`へ追加した後である。
3. 保留中の変更が一意、`NOT NULL`、外部キーなどのDB制約へ違反し得る。
4. 呼び出し元がアプリケーションの入力エラーとDBドライバー由来の例外を区別する。

永続インスタンスへの最初の属性代入から、入力値の検証と必要な属性代入を終えるまでを属性代入区間とする。
新規行では`Session`への追加から必須属性の代入を終えるまでを同じ区間として扱う。

## 問い合わせと属性代入の順序

- DBへの問い合わせは属性代入区間の外側で行う。
  設定値の判定や一意性の事前確認を含む問い合わせは区間より前に完了し、結果を変数へ保持してから代入する。
  本規定は原則として適用する。
  問い合わせ前のautoflushが未検証の変更を送信し、アプリケーションの入力エラーより先にDB制約違反を送出するためである。
- 前項で移動した問い合わせは、DBアクセスを要しない入力検証を終えた後へ置く。
  これは努力目標とする。
  入力検証だけで終了する処理では、`Session`の開始とDB問い合わせを避けられるためである。
- 同じ処理単位の保留変更を反映した問い合わせ結果へ依存する契約は維持する。
  必要な箇所では`Session.flush()`を明示し、保留変更を送信する時点を問い合わせより前へ固定する。
  読み取り側でautoflushを無効にする方法へ置き換えない。
  本規定は原則として適用する。
  autoflushを無効にすると、同じ処理単位で追加又は更新した行を問い合わせる呼び出し元が古いDB状態を受け取るためである。
