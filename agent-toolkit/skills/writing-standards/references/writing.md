# ドキュメント品質

本書は人間が読む文章（Markdown・README・技術文書・API文書、業務・仕様文書、体験を述べる文章、コメント類、AWI・UWIの本文）の品質基準を定める。
コード内のコメントやエージェント向け文書も人間が読む文章を含むため、本書の基準を併せて適用する。

## 文章の共通規定

エージェントが書く文章は、結論または目的、主要な関係、理解・判断・行動を変える詳細の順に構成する。既知の前提や同じ内容の再掲は省き、正確性、安全性、認可、監査および既存形式が要求する必須情報は保持する。件数や文字数の固定上限は設けず、読み手が判断と行動に必要な情報量で書く。

本節は人とエージェントが読む、エージェントの書く全ての文章へ適用する。委譲プロンプトと追送、WI本文、計画ファイル（進捗ログを含む）、Issueとコメント、PR・MRの説明、レビューへの返信、コミットメッセージ、報告などを含む。各スキルの文書は成果物の種別に固有の事項だけを扱い、同じ観点の規定を重ねることを避ける（努力目標。重複した規定は改訂時に一致しなくなる）。
メインエージェントのユーザー向け発話には、`agent-toolkit/share/rules-main.md`「ユーザー向け発話ルール」も適用する。

- 書く前に読み手と読む時点を定め、その読み手が判断、操作、再取得に使う内容だけを書く。他の規範が記載を求める項目にもこの判定を適用し、読み手が使う粒度で書く。追加の理由は省くと読者が失う判断や操作とし、書き手が知る是正前の症状、調査中の疑問や担当エージェントの誤判断は読者の前提から外す。利用方法、実在する制約、意図的な仕様差と維持する設計判断は、読者の判断や操作に必要な範囲で残す
- 書き手が確かめた過程（検索した範囲と語、観点ごとの結論、0件・非該当の理由、比べた記録の所在、中間出力のパス）は、読み手が使う場合を除き証拠ファイルか委譲元への返却に残す。本文には結論と、読み手が再取得に使う所在を書く
- 委譲プロンプトと追送には、委譲先が作業に使う入力だけを書く。委譲先が自ら読む規範・スキルの再掲と、作業に使わない経緯は省く
- commitは読み手で示し方を選ぶ。人向けには日付、件名、PR・MR番号、tagで示し、再取得に使う場合だけ一意な短縮OIDを添える。エージェント向けには一意な短縮OIDを使い、完全OIDは`agent-toolkit:commit`の`references/git-identifier.md`に従って操作の直前に解決する
- 読者が文脈上すでに知っている情報は省き、既知の概念を起点に未知の事項との関係を示してから詳細へ入る
- 1つの段落では1つの話題を扱う。手順や並列データは一覧にし、因果関係や判断の理由は段落でつなぐ。箇条の一項目で説明や理由が続くときは段落へ分ける（努力目標）
- コミットメッセージの本文やPR・MRの説明では、変更が必要になった理由と目的を書く
- AWIやUWIは作業者の手元の個人記録であるため、外部に公開する成果物からはその内部ファイル名やキュー状態などの識別子を除く。AWI・UWIや個人のセッション記録が事実の出所や再検証の手段を保持する場合は、公開の実装・テスト・資料と観測の条件・結果を本文へ写して読者がたどれる形にする。個人記録の識別子と行番号は書かず、写せない一次記録はリポジトリ外にあることだけを記す。計画ファイル、AWI・UWIの本文およびレビュー指摘管理表は例外とする
- 仕様、設計、規範や使い方を後から参照する文書は、完了後も必要な仕様、判断と理由で構成し、作業の進捗、タスクのチェックボックス、個別のPR番号は作業用文書へ置く。製品や運用の状態、判断の採用・廃止、経緯記録で事実の出所を示す時点と識別子は作業の進捗と区別して記す
- バージョン管理下の文書には、バージョン管理の対象外の個人メモ（`CLAUDE.local.md`、作業中の計画ファイル、managed-tempのファイルなど）を出所や参照先として書かず、読み手が到達できる実装、設定または文書へ置き換える
- 変更の由来（ユーザー指示か自律判断か）は、読者の判断に必要な場合に限って書く
- テストの説明で失敗モードを述べる場合は、観測地点で起きる事象と後段で引き起こす結果を（入力の種別で扱いが異なれば種別ごとに）対応付けて書き、説明と実際の判定をそろえる。ずれると、テストが保証しない結果を読み手が保証済みと扱う
- 確定した事実と未確認の可能性を区別し、因果関係や推奨には成立条件と根拠を添える
- 既存の対象は、規範か対象の成果物に実在する名前（画面名、表示文言、コマンド名、規範が定義した名前など）で指し、実在する名前が無い対象は説明で書く。その場で考案した呼称と、会話、コミットメッセージ、障害記録など読んだ記録にある定義の無い呼称は、正式名か説明へ置き換える。完成時の読み直しでは、既存の対象を指す名詞句ごとに定義元を固定文字列で検索し、定義元が無ければ正式名か説明へ書き換える
- 強調、一般論、前置きと結びは読者が判断に使う内容に限る。対比フレーミングと必要な否定の扱いは`agent-toolkit/rules/01-agent.md`「使用言語」に従う。先行する問いや話題が求めていない否定・除外・不変の表明は省く（努力目標。内容を増やさない装飾は本題から注意を逸らす）

この判断の例と説明は`tone-examples-llm-tone.md`「唐突な否定と不変の表明」にある。

- 例示する対象が集合の一部である場合は、上位概念と範囲を明示する。閉じた一覧として書くと、読み手が例の外にある適切な手段を除外する
- 完成時は規範が求める項目を含む各記述が読み手の判断、操作、再取得に使われるか、識別子が読み手に合うかを読み直す。節をまたぐ再掲のうち使わない記述を除く。必須構造、要求の逐語、根拠および適用範囲の具体例は保持する

表記の自動チェックは口語表現チェック、textlint、ダッシュチェック、agent-doc-toneが担う。

## 読み手別の追加注意点

- プログラムが出力するメッセージ（読み手がエンドユーザー、開発者、エージェントのいずれでも）: エラー、警告、遮断、失敗、待機の打ち切り、状態値の返却では、観測した事実に加えて次の操作を書く。事実だけを受け取った読み手は推測で行動し、実行できない操作や同じ失敗を繰り返す
  - 次の操作には、何を実行するか、実行できない場合の代替手段か報告先を書く。警告の出力条件は次項のエージェントが読む出力の規定に従う。生成側が対処を特定できない場合は、不足している情報と、それを得る手段か報告先を書く
  - 受信側がその時点で持つ文脈（自分が実行した操作と引数、受け取った情報）で一意に解釈できるように書き、生成側の内部用語や受信側が観測できない条件は前提から外す。案内するコマンド、ツールおよび引数は受信側が実行できる実在の名前で書き、対象と操作を具体的に示す
  - 対処方法が元の操作を可能にしない場合は、その方法が達成する別の目的を明記する
  - 出力の共通手段が次の操作を別の引数として受け取る場合は、本文へ混ぜずにその引数へ渡す
  - 出力を新設・変更する時は、その処理から到達する既存の分岐も読み、各分岐の次の操作を確認する。共通の出力関数を通らない直接出力、状態行、例外処理も含め、欠けていれば同じ変更で補う。共通関数や規定が存在することだけを、個別出力への適用の証拠にしない
  - エージェントが読む出力は、処理の結果と、失敗・警告およびその次の操作など受信側が次の判断に使う行で構成し、無関係な通知、対処不要な付随処理の報告、毎回同じ固定の案内、反復を混ぜない（努力目標。混ぜると受信側は出力をパイプで選別し、終了コードと警告を観測しなくなる）。規範の所在を届けること自体を目的とする定型の配送（hookの`notice`区分の注記など）は本項の対象外とする
    警告は受信側に操作（条件付きの操作を含む）がある事象に限る。操作の無い事象は、結果に必要な場合だけ結果行で示す
- エンドユーザー向け: 内部実装の知識を持たない読者（ユーザーを含む）を想定し、専門用語は初出時に補足する。ドキュメントは「何ができるか」「どう使うか」を中心に、対話型UIでは操作、状態、対処を端的に伝える
  - 操作、設定または対処方法を案内する場合は、実装の処理の流れまたは実行結果から、実行後に説明した状態へ到達することを確定する。設計文書の記載は手段の実在の裏付けに留まる
  - 行動指示は常体では「〜を参照」、敬体では「〜を参照してください」の形を用いる（努力目標）
  - 条件に応じて語を前置・連結して組み立てる表示文（CLIの状態表示やログなど）は、分岐ごとに完成した出力を1文として読み、目的語と述語が揃うかを確かめる
- 開発者向け: 前提知識を共有する開発者を想定し、初歩的な説明とコード識別子レベルの細部を省いて、「なぜそう設計したか」「どこに注意が必要か」を中心に書く
- エージェント向け文書: 前置きや自己紹介、書き手目線の解説を省き、判断に必要な情報のみを直接記述する
  - 要求事項は主体、対象、拘束力を明確に読み取れる形式（命令形、依頼形、体言止め、規定文など）で示す
  - 箇条書きにおける体言止めの列挙を許容する
  - 記述の詳しさと各文章への適用は「文章の共通規定」に従う。読み手のモデルが学習データから知っている一般知識（一般的な設計・実装・検証の作法など）は、守る価値と判断の観点に、その知識を想起する手掛かりとなる代表語を添えて書く。具体的に書くのは、学習データから導けない事実と硬い制約（`agent-toolkit/rules/01-agent.md`「規定の区分と標示」）に限る。学習データから導けない事実には、プロジェクト固有のパス・コマンド・規約、実際に観測した環境依存の注意点、知識カットオフ後に変わった仕様がある
  - 記述量は手掛かりが足りないと読み手が考慮すべき観点を想起できず、手段や例を細かく書くと読み手がその手段や例へ判断を固定することを比べて決める。文字数や例の件数で一律に決めない
  - 読み手のエージェントは広い知識と常識的な判断力を持つ前提で書く。常識と文脈から判断できる工程、確認、分岐、例外処理は手順化しない。細かな手順は、書かれた手順以外の行動を禁じられたという先入観を読み手に与えて目的に合う判断を妨げ、文章量に比例して読込の費用も増やす。手順として書くのは目的と守る価値、硬い制約、プロジェクト固有の事実および目的と守る価値が示されていても読み手が誤った箇所に限る。誤りを観測したことだけでは、常識で判断できる事項を手順化する理由にならない。それ以外の進め方は読み手の判断へ委ねる

## 文書種別ごとの注意点

本節の指針は前節の読み手別の注意点と重ねて適用する。箇条書きや太字の比率、漢字の比率、文末の形は数値の目標にせず、条件と結果の関係に合わせて書く。数値に合わせた書き換えは、その関係を変えることがある。

### 技術文書

技術記事、設計書、技術解説などに適用する。

- 読者が使う入力、コマンド、設定とその結果を示し、手を動かして再現できる記述にする
- 太字は読者が見逃すと判断を誤る箇所に限る（努力目標）
- 冒頭の一般的な前置きを省き、解決する課題や前提条件から書き始める。起きる事象と発生条件を直接書く

```text
例文: キャッシュが無効化された場合、警告やエラーを出力せずに処理が失敗することがある。
説明: 発生条件と観測できる結果、発生の不確実性を対応付ける。
```

### 業務・仕様文書

PR・MRの説明、仕様書、業務報告、提案書など、読者が判断や行動に移るための文書に適用する。

- 誰が、どの条件で、何を決め、どう扱うかを書く。決定や合意は決めた主体を主語にする
- 対応する条件、対象、動作と量を書く。不明な条件や数値は補わず、不明であることを示す
- 前置きの宣言や効果を約束する文を省き、結論や依頼事項から書き始める。対象と採否の基準を直接書く

```text
例文: 採否の基準を満たさないレコードは、登録の対象から除外する。
説明: 判定する対象、採否の基準と処置を対応付ける。
```

### 体験を述べる文章

エッセイ、体験記、個人ブログなど、本人の経験と感想を伝える文章に適用する。

- 本人が述べた状況、感覚、感想を保ち、客観的な効果や一般論、普遍的な教訓や提言へ広げない（努力目標）
- 素材にない描写や感情、読者への定型の呼びかけを加えない

```text
例文: この店のコーヒーは酸味が少なくて飲みやすかった。
説明: 本人が述べた対象と感想の範囲を保つ。
```

## ユーザー入力素材の取扱い

ユーザーが事情や経緯を説明しながら作業を指示する場合、提示された文面は対象読者と必要な情報粒度に合わせて整理してから取り込み、要件として反映する情報と背景の参考に留める情報を区別する。
質問への回答と成果物を変える要求も分け、説明を成果物へ加えるかは「文章の共通規定」の情報を加える前の判定に従う。回答内容を文書へ反映するかは、質問へ回答したこととは独立に判定する。

- 書き直しの前後で主体、対象、条件、動作、数値、例外、識別子と不確実性を比べ、原文や観測にない仕様、設定値、原因、効果は補わずに不明な点として保つ
- 一時的な事情、セッション固有の事象、個人への名指しは、後続の読者の判断に必要な場合だけ残す
- 対話で参照した対象は、第三者が一意に特定できる実体名か説明で書く
- 原文の改変を避けるべき逐語引用は、言語指定を`text`としたフェンス付きコードブロックで囲む。内側は各種チェックの対象外となり、原文のまま保持できる

完成時には作業の経緯を知らない読者の視点で通読し、制作過程の痕跡を整理する。実装上の制約や除外した代替案は構成と語彙へ反映し、免責の形の言及は読者が制約そのものを知る必要がある場合に限る。修正指示への対応表明や前版との差分説明はコミットメッセージやレビュー応答へ書く（努力目標）。名詞句の定義元の確認は「文章の共通規定」の名前の項に従う。

文章の起草を`agents_server`の`start`の`write`へ委ねる場合の条件と検収は`textlint-violations.md`「文の書き直しの委譲と検収」に、textlintの指摘への対応は同書「textlint指摘への修正方針」に従う。

## 構成・構造

- 冒頭に目的や概要を置き、前提条件（必要な知識、ツール、環境）は本題の前に、全体から詳細へ掘り下げる
- 読者が独立して知りたい問いを確かめ、見出しなし、並列の節、親子の節の順に最も簡単な構成を選ぶ。見出しや書式を指定された文書ではその形式を守る
- 各見出しが指す問いと本文が答える内容を比べ、答えのない見出し、見出しと異なる話題、同じ答えの重複を整理する。見出しの親子関係は内容の包含関係に合わせ、見出しの階層は3段（`##` / `###` / `####`）までを目安とする
- 関連する内容は近くにまとめ、前方参照は段落末や節末に置く
- コマンド例やコードスニペットはそのまま実行可能な形で書き、外部リンクには要点を本文にも添える

## 日本語の書き方

伝える内容を肯定文で直接書き、主張を際立たせるために否定する側を並べる対比フレーミングを禁止する。否定は肯定文から読み取れず読み手の判断に要る実在の制約、選択肢または誤解に限り、独立した事実の文で示す。

行為者、対象、動作、条件と結果を文と前後の文脈から読み取れる形で書く。省略した要素の補い方が一意に定まり、動詞の意味が読み手と共有され、主題と述語の関係が成立することを確かめる。参照先が曖昧な代名詞は対象名へ戻し、同じ段落で一意に分かる指示語は残す。主語の文頭配置や受動文の排除を一律に求めず、自然な語順を保つ（努力目標）。

操作や状態が分からない比喩、漢語と名詞の過剰な連結は、動詞と助詞を補って文全体を組み直す。表現の不自然さを指摘するときは、その文や句から成立しない関係を説明し、別の箇所や専門知識との不一致から判断する内容の誤りと区別する。定着した専門用語、字義通りの動作、文脈から一意に復元できる省略、見出しと必要な一覧、規範の体言止めは保つ（努力目標）。

システムの動作は、その主体で説明する。意志や感情を仮託する擬人化や、判断した主体と根拠を隠す推量は、動作または判断と根拠を対応付けて書く。文長や文末の指標だけを満たすための分割や言い換えはせず、条件と結果の関係、時制と確実性を保つ（努力目標）。

```text
例文: 設定ファイルが存在する場合、CLIは指定された保存先へ結果を書き込む。
説明: 条件はファイルの存在、動作の主体はCLI、対象は指定された保存先であり、書き込まれる結果との関係が読み取れる。
```

新しい概念名と識別子を導入するときは、`referent-table.md`の候補語の確定を適用し、語より先に指示対象と役割を確定する。単一の文書内でしか使わない技術用語は、その文書の初出で定義する。

## 改訂・保守

- READMEとエージェント向け文書の内容が重複する場合はREADMEを基本とし、エージェント向け文書からは参照するか要点のみを再掲する
- 追記は既存の記法、見出し構成、記号の運用と整合させる
- 順序を持つ既存の集合（文書の節・一覧・表の行、列挙型、設定項目、メニューなど）へ要素を加えるときは、同じ対象群の既存の順序の基準に合う位置へ置く。基準が無い場合は並びの原則を自ら定めて根拠を残す（努力目標）
- 相互参照している項目名や表の列名、本文と連動するコード例・目次・件数表示は、改訂時にすべての箇所をそろえる。実態と合わなくなった記述は更新または削除する
- 要約・統合では元の文章の前提条件、適用範囲、例外条件を保つ
