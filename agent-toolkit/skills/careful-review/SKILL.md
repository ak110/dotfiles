# レビュー工程

対象範囲（ファイル群または差分）の評価を`plan-codex-delegate`（`用途: 実装差分レビュー`）へ委ね、
指摘を統合する。codex利用不可（`codex-review.md`「codex利用可否の2段階判定」節の段階2）が
成立した場合のみ`plan-reviewer`を代替として起動する。

## 入力

呼び出し元から計画ファイルパス（省略可）・対象範囲（ファイルパス列挙またはgit差分範囲、
いずれか）を受け取る。対象範囲が未指定で計画ファイルのみ提示された場合、
計画着手前コミットから`HEAD`までの差分を対象範囲とする（不変参照点は計画記載のSHAを優先する）。

## 起動

- `plan-codex-delegate`（`用途: 実装差分レビュー`）を単独起動する。プロンプト構成は
  同エージェント定義側が担うため、本スキルは対象範囲・対象外ファイル・計画ファイルパス・
  差分取得コマンド・起動元識別子の受け渡しのみを担当する
- 起動プロンプトへ起動元自身の識別子を明記し、完了報告の宛先として指定する。
  メインセッションからの起動は`main`、サブエージェント配下からの起動は当該サブエージェントの`name`とする。
  サブエージェント配下で本スキルを起動し識別子を一意に指定できない場合は、
  `run_in_background=false`のforeground実行へ切り替えてAgentツールの戻り値として直接受領する
- 段階2成立時は`plan-reviewer`を起動する。担当観点は`agent-toolkit:review-standards`の
  完成条件と同一とし、コーディングエージェント向け文書カテゴリを含む場合は
  `01-agent.md`・`agent-standards`適合性の評価も同一起動へ含める（`agent-doc-validator`の
  独立起動は行わない）
- 計画ファイルの有無で担当観点の範囲が変わる。計画ファイルありの場合は仕様適合性と
  成果物間の整合性の双方を評価し、計画ファイル無しの場合は仕様への適合性評価が
  成立しないため成果物間の整合性のみを評価する。起動プロンプトへ計画ファイルの有無を明示する

## 指摘の統合と修正依頼

`agent-toolkit/rules/02-claude-code.md`「サブエージェント運用」節の固定書式表で指摘を統合する。
対応要否は重大度で判断し、`致命的`・`重大`は既存違反でも対応する。`軽微`はメイン判断とする。
統合前に品質俯瞰棚卸し（登録済み手順に無い品質作業の点検）を1回実施し、発見事項を表へ追加する。

構文の合法性を根拠とする指摘は採用しない。対象プロジェクトの宣言バージョンに適合する
処理系・構文チェッカ（`uv run --python=<適合版>`起点の`ast.parse`・`tsc --noEmit`・`cargo check`等）で
実機検証してから取り下げる。

重大度`致命的`・`重大`の指摘は修正着手前に対象箇所を単体`Read`し、表層の現象が設計意図上の
ディフェンシブ実装として成立し得るかを照合する。成立し得る場合は
`（メイン判断: 不対応 — 設計意図上のディフェンシブ実装として成立）`で不対応とする。
対応不要と判断した指摘は末尾へ`（ユーザー判断: 不対応 — <理由>）`または
`（メイン判断: 不対応 — <理由>）`を付す。

修正実装はcodexを優先する（`execution-process.md`
「実装委譲（plan-codex-delegate / plan-implementer）の判断指針」節参照）。
修正のコミット反映は直前の未プッシュコミットと件名・対象範囲が整合する場合`git commit --amend`で統合する。

## 再レビュー

再レビューは独立コンテキストの新規`Agent`で行うため、起動プロンプトへ前回指摘一覧
（重大度・箇所・内容）と反映済み内容（対応方針・不対応と判定した項目とその理由）を
本文で渡す。これにより新規インスタンスが「前回指摘の反映確認」と「反映差分自体の新欠陥」の
2点へ対象を限定できる（`02-claude-code.md`「サブエージェント運用」節の独立コンテキスト
原則と整合）。

再レビューの対象は「前回指摘の反映が正しく行われたか」と「反映差分そのものが新たに生んだ欠陥」の
2点に限定する。反映差分と無関係の新規観点・計画に無い仕様拡張の要求は当該回の指摘として扱わず、
別件候補として報告末尾へ列挙させ当該回では修正しない。
指摘が示す欠陥と同種の箇所への`grep`点検（`agent-toolkit/agents/plan-impl-executor.md`
「レビュー指摘反映時の手順」節）は反映差分の水平展開に当たり、上記の対象外扱いには含めない。

初回レビュー1回＋再レビュー4回（合計5回のレビューラウンド）を絶対上限とする。
「## 起動」節が定めるとおり`用途: 実装差分レビュー`は単独起動（並列起動しない）であるため、
1ラウンドは1エージェントインスタンスの起動1回に対応する。
上限到達時点で致命的・重大の指摘が残っている場合、
`01-agent.md`「完遂と先送り」節（自セッションで導入した不良・作業中に発見した機能不全は
同一セッション内で対応する規定）に従う。
再レビューは再起動せずメイン側が直接指摘の成否を検証し、
反映内容か却下理由の明記まで完遂してからコミットを確定する。
軽微の指摘のみが残る場合はその旨を完了報告へ列挙したうえでコミットを確定してよい
（重大度体系は`致命的`・`重大`・`軽微`の3種のみであり、他の区分は用いない）。
成果物本体に影響しない軽微修正のみの場合は再起動しない。
新しい`Agent`で起動する（先入観排除のため`SendMessage`再開は採らない）。
foreground実行で起動したレビューを再開する場合も同様に新規のforeground起動とする。
`SendMessage`による再開はbackground実行となり、戻り値による受領経路が失われるためである。
前回と同型の指摘が繰り返される場合は上限を待たずメイン側で採否を確定して
計画本文への反映、もしくは明示的な不対応判定の記録を完了させる。

再レビュー対象の限定・絶対上限5回・重大以上の指摘解消義務は厳守規定とする
（上限を設けないと往復が収束せず、致命的・重大の指摘を残置したままの公開という
技術的な不成立を招くため）。起動プロンプトの構成方法・報告書式は努力目標とする。
