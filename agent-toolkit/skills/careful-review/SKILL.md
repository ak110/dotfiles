# レビュー工程

対象範囲（ファイル群または差分）の評価を`plan-codex-delegate`（`用途: 実装差分レビュー`）へ委ね、
指摘を統合する。codex利用不可（`codex-review.md`「codex利用可否の2段階判定」節の段階2）が
成立した場合のみ`plan-reviewer`を代替として起動する。

## 入力

呼び出し元から計画ファイルパス（省略可）・対象範囲（ファイルパス列挙またはgit差分範囲）・
変更の意図・意図的に受け入れた挙動変化を受け取る。
変更の意図は呼び出し元から指定された値を使用する。
未指定で計画ファイルがある場合は、計画ファイルの`### 経緯`から作成した要約を使用する。
計画ファイルがなく、呼び出し元からも指定されていない場合は`なし`とする。
挙動変化には、デメリットとして認識済みの機能低下・検出範囲の縮小・互換性の変更などを列挙する。
該当する挙動変化がない場合は`なし`を受け取る。
対象範囲が未指定で計画ファイルのみ提示された場合、
計画着手前コミットから`HEAD`までの差分を対象範囲とする（不変参照点は計画記載のSHAを優先する）。

## 起動

- `plan-codex-delegate`（`用途: 実装差分レビュー`）を起動する。
  起動数は`references/impl-review-launch.md`「codexの分担起動閾値」節の判定に従う。
  プロンプト構成は`plan-codex-delegate`定義側が担う。
  `careful-review`は対象範囲・対象外ファイル・計画ファイルパス・差分取得コマンド・変更の意図・
  意図的に受け入れた挙動変化を引き渡す。
  変更の意図と意図的に受け入れた挙動変化は、起動数によらず全インスタンスへ同一内容を渡す
- 列挙した挙動変化の妥当性はレビュー担当の再評価対象から除外する。
  列挙内容と実装が一致しない場合は指摘対象とする
- 起動は`name`を指定しないforeground実行とし、完了報告をAgentツールの戻り値として直接受領する。
  起動プロンプトへ、完了報告を戻り値で返し`SendMessage`による能動送付をしない旨を明記する
- 段階2成立時は`plan-reviewer`を起動する。担当観点は`agent-toolkit:review-standards`の
  完成条件と同一とし、コーディングエージェント向け文書カテゴリを含む場合は
  `01-agent.md`・`agent-standards`適合性の評価も同一起動へ含める（`agent-doc-validator`の
  独立起動は行わない）
- 計画ファイルの有無で担当観点の範囲が変わる。計画ファイルありの場合は仕様適合性と
  成果物間の整合性の双方を評価し、計画ファイル無しの場合は仕様への適合性評価が
  成立しないため成果物間の整合性のみを評価する。起動プロンプトへ計画ファイルの有無を明示する

## 指摘の統合と修正依頼

`agent-toolkit/rules/02-claude-code.md`「サブエージェント運用」節の固定書式表で指摘を統合する。
対応要否は重大度で判断し、`致命的`・`重大`は既存違反でも対応する。`軽微`はメイン判断とする。
統合前に品質俯瞰棚卸し（登録済み手順に無い品質作業の点検）を1回実施し、発見事項を表へ追加する。

構文の合法性を根拠とする指摘は採用しない。対象プロジェクトの宣言バージョンに適合する
処理系・構文チェッカ（`uv run --python=<適合版>`起点の`ast.parse`・`tsc --noEmit`・`cargo check`等）で
実機検証してから取り下げる。

重大度`致命的`・`重大`の指摘は修正着手前に対象箇所を単体`Read`し、表層の現象が設計意図上の
ディフェンシブ実装として成立し得るかを照合する。成立し得る場合は不対応と判定する。
不対応と判定した指摘（本項に限らず対応不要と判断した指摘全般を含む）の注記を付す主体・書式は
`agent-toolkit/rules/02-claude-code.md`「サブエージェント運用」節（SSOT）に従う。
本スキルが委譲先として起動されている場合、判定結果と照合根拠を完了報告へ記載するに留め、
注記は自ら付さない。

レビュー専用の委譲では、対象ファイルごとの起動前内容を`cp`で一時バックアップする。
起動前に存在しない対象は不在として記録し、対象ごとの内容ハッシュも別途記録する。
バックアップは既存の未コミット変更を含む起動直前の内容を保存する。

レビュー担当の完了報告を受領したら内容ハッシュを再計算し、変更の有無を検知する。
変更を検知した場合は次の順で対処する。

1. バックアップと作業ツリーを比較し、レビュー担当による編集を特定する
2. 起動前に存在した対象はバックアップの内容を戻し、起動前に存在しなかった対象は不在状態へ戻す
3. 復旧後の内容ハッシュを起動前の記録と照合し、既存の未コミット変更を含む起動前状態への復元を確認する
4. レビュー担当が報告した指摘内容自体の当否を判断し、採用する指摘は実装担当へ引き継いで正規手順で反映する
5. 正規反映後に変更に近いtest・lint・formatを再実行し、レビューを継続する

復旧の完了後に一時バックアップを除去する。
レビュー担当による直接編集の発生有無と、実装担当による正規反映は区別して記録する。

修正実装はcodexを優先する（`execution-process.md`
「実装委譲（plan-codex-delegate / plan-implementer）の判断指針」節参照）。
修正のコミット反映は`agent-toolkit:commit`「コミット運用」節に従い、
変更目的と対象範囲からamend・fixup・新規コミットを選ぶ。
amend・fixupの対象は基点コミットより後に作成したコミットへ限定する。
基点コミットは、計画ファイルがある場合は計画着手前SHA、無い場合は起動時に受け取った
対象範囲（差分レンジ）の開始点とする（計画着手前SHAを不変参照点とする`caller-reception.md`の
照合が成立しなくなるため）。基点コミットを確定できない場合は新規コミットのみを選ぶ。
基点コミット以前のコミットを修正対象とする場合も新規コミットへ反映する。
修正の実装後に影響範囲の近接検証を実行し、コミット反映後に計画全体の最終検証を再実行する。

## 再レビュー

再レビューは独立コンテキストの新規`Agent`で行うため、起動プロンプトへ前回指摘一覧
（重大度・箇所・内容）と反映済み内容（対応方針・不対応と判定した項目とその理由）を
本文で渡す。これにより新規インスタンスが「前回指摘の反映確認」と「反映差分自体の新欠陥」の
2点へ対象を限定できる（`02-claude-code.md`「サブエージェント運用」節の独立コンテキスト
原則と整合）。

再レビューの対象は「前回指摘の反映が正しく行われたか」と「反映差分そのものが新たに生んだ欠陥」の
2点に限定する。反映差分と無関係の新規観点・計画に無い仕様拡張の要求は当該回の指摘として扱わず、
別件候補として報告末尾へ列挙させ当該回では修正しない。
指摘が示す欠陥と同種の箇所への`grep`点検（`agent-toolkit/agents/plan-impl-executor.md`
「レビュー指摘反映時の手順」節）は反映差分の水平展開に当たり、上記の対象外扱いには含めない。

初回レビュー1ラウンドと再レビュー4ラウンドの合計5ラウンドを絶対上限とする。
各ラウンドの起動数は`references/impl-review-launch.md`「codexの分担起動閾値」節の判定に従う。
分担起動時の1ラウンドは、同一レビュー対象に対する複数インスタンスの並列起動全体に対応する。
同一ラウンドで並列起動した複数インスタンスは個別に数えず、まとめて1ラウンドとして数える。
上限到達時点で致命的・重大の指摘が残っている場合、
`01-agent.md`「完遂と先送り」節（自セッションで導入した不良・作業中に発見した機能不全は
同一セッション内で対応する規定）に従う。
再レビューは再起動せずメイン側が直接指摘の成否を検証し、
反映内容か却下理由の明記まで完遂してからコミットを確定する。
本スキルが`plan-impl-executor`（Sonnet固定）配下で起動されている場合、「メイン側」は
`plan-impl-executor`自身を指す。残る指摘が計画本文の方針見直し・ユーザー合意を要する判断・
対象範囲の変更を要すると観測される場合がある。この場合、`plan-impl-executor`は自身で
採否を確定せず`needs_escalation`で呼び出し元セッションへ返す
（分岐の詳細は`agent-toolkit/agents/plan-impl-executor.md`「停止禁止」節を正典とする）。
軽微の指摘のみが残る場合はその旨を完了報告へ列挙したうえでコミットを確定してよい
（重大度体系は`致命的`・`重大`・`軽微`の3種のみであり、他の区分は用いない）。
成果物本体に影響しない軽微修正のみの場合は再起動しない。
新しい`Agent`で起動する（先入観排除のため`SendMessage`再開は採らない）。
foreground実行で起動したレビューを再開する場合も同様に新規のforeground起動とする。
`SendMessage`による再開はbackground実行となり、戻り値による受領経路が失われるためである。
前回と同型の指摘が繰り返される場合は上限を待たずメイン側で採否を確定して
計画本文への反映、もしくは明示的な不対応判定の記録を完了させる。

再レビュー対象の限定・絶対上限5回・重大以上の指摘解消義務は厳守規定とする
（上限を設けないと往復が収束せず、致命的・重大の指摘を残置したままの公開という
技術的な不成立を招くため）。起動プロンプトの構成方法・報告書式は努力目標とする。
