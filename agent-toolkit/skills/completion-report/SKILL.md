# 作業完了報告とセッションの完了処理

作業の結果は、都合の悪い結果も含めて正直に報告する。作業完了報告、振り返り結果報告およびAWI投入結果報告のいずれにも適用する。

反映・公開・UWI保存・セッション終了は、各対象を操作するCLIと参照資料がそろう環境で行う。操作機能が無い場合は、提示された成果と確認済みの証拠から結果を説明し、未実施の反映・公開・保存を区別する。残る操作はそれらの機能を使えるClaude CodeまたはCodexへ渡し、ここで書く報告の下書きには[文章の品質基準](references/quality-standards.md)を使う。

適用するのは、実装、計画、AWI投入など成果物を確定した作業をメインが完了したときである。成果物の確定を伴わない回答（単発の調査依頼など。その後に作業が続き得る）と、サブエージェントが委譲元へ返す完了報告には適用しない。
適用するプロジェクト規範による省略は、`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」でメインが判断する。
本スキルの起動を省く場合は、`references/termination-evidence.md`を直接読み、省略を記録して通常の報告を届ける。

報告は入力が確定した時点で内容を確かめ、独立した節で届ける。順序は次のとおりとする。

- `## 作業完了報告`を振り返りの起動前に届ける
- 振り返りでAWIを1件以上投入する場合は、`agent-toolkit:session-review`の`SKILL.md`「工程」のWI投入担当を起動する段落に従って投入前に`## 振り返り結果の予告`を届け、投入後の`## AWI投入結果報告`を最終報告とする
- 投入0件、未実施または失敗の場合は、振り返り完了後の`## 振り返り結果報告`を最終報告とする

送達は`agent-toolkit:user-confirmation-and-report`「手段の選択」に従う。Claude Codeは途中・末尾とも`mcp__agent-toolkit__send_to_user`を使う。最終報告だけ末尾に「以上で、このセッションの作業は全て終わりました」と書く。

## 完了の到達水準

「完了」は対象全体と既知の問題へ対応し、ユーザー操作が必須の事項だけが残る状態とする。代表箇所や一部だけの反映は途中経過として報告する。
環境制約などで確認しきれない場合は、実施可能な検証を終え、その結果と実機確認などが未実施である範囲・理由を報告する。
未確認の範囲だけを理由に個別UWIやユーザーの操作依頼を追加しない。
既知の不良と未充足の明示要件は、未達として区別する。

## 工程

番号は入力がそろう順序であり、前の手順の出力に依存しない作業は`agent-toolkit:session-review`の稼働中も含めて並行して進めてよい。
本スキルの起動と本書の読了は工程の開始にあたり、手順5の作業完了報告から手順9の終端工程まで同じ応答で進める。確認の回答や委譲先の結果を待って中断した場合は、再開後に残る手順から続ける。

1. 常時稼働サーバーへの反映: 対象プロジェクトが開発マシン上で常時稼働するサーバーを持ち、その規範またはタスクランナー定義が反映手段と稼働確認手段の双方を定める場合に行う。起動元の工程が先行して反映した結果（反映済みHEADの完全OID、反映コマンドの終了状態、稼働確認の結果）があり、報告時点の主作業ツリーHEADと一致し双方成功していれば再反映を省く。それ以外は現行HEADを反映して稼働を確かめる。報告には再反映の有無と稼働確認の結果を含める。反映しない場合は理由と未反映の状態を報告し、ユーザー対応が必要な未完了事項は`agent-toolkit:user-confirmation-and-report`「手段の選択」で個別UWIの登録要否を判定する。自明な反映操作の案内は報告へ添える。
   起動元の工程が反映を先行して始められるのは、反映が対象リポジトリへ書き込まず、公開の入力を生成せず、公開操作と成果物・排他資源で競合しない場合に限る。
2. メイン自身が作成した作業用領域は、`agent-toolkit:managed-temp`が定める寿命で回収する。元資料から再生成できる抽出・比較用の複製と検証用の環境は、全消費工程と外部プロセスの終了後に`atk managed-temp cleanup`で回収する。セッションのmanaged-temp本体と、後続turnへの入力・証拠・引き継ぎ記録は7日保持する側へ残す。
   process-wiの登録済みレーン資源はこの時点で回収せず、追加と振り返り後の工程に備えて保持する。全工程・外部プロセスの終了後に、通常終了では`atk agents-exit-session`が、process-loopでは子の終了後の処理が、`atk lane delete`と同じ条件で回収する。未統合・dirty・稼働中・不明・部分失敗の対象は成果と理由・残る操作を保存して保持し、次回開始時の`atk lane delete --list`から再判定する。
3. そのセッションでユーザーが確定した判断を`agent-toolkit/rules/01-agent.md`「協調と自律」の保存対象と比べ、未保存の判断の保存またはAWIの投入を完了する。保存の前に`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」の、程度の限定と確度を保持する箇条と、確度を伴う発話の保存を扱う箇条を適用する。
4. 協調モードでcommitした成果があり、確認済みの公開範囲がcommitより先へ及ぶ場合は、`agent-toolkit:commit`の`references/publish.md`に従ってその範囲の公開を完了する。`agent-toolkit:process-wi`と`agent-toolkit:single-lane-process`は自身の工程で公開する。
5. 実施した公開範囲とリリース判定の結果を含む作業完了報告を`references/report-formats.md`「作業完了報告のフォーマット」に従って1回届け、同じ応答で手順6へ進む。
6. 適用する規範の優先順位から振り返りの要否を決め、実施する場合は`agent-toolkit:session-review`を起動する。省略する場合はその理由を手順8の報告へ含める。同じセッションで振り返りを実施済みでも、前回の準備時刻（`atk run-script session-review-prepare`のJSONの`prepared_at`）より後に本体の作業を続けた場合か、準備に含まれない実際の改善点が届いた場合は再び起動する。準備後のユーザー発話と改善点の扱いは同スキルの工程6が定め、前回投入したAWIは既存項目として重複判定される。前回の振り返り自身の起草・投入・待機・検収と、取込み済みの行の転記・再掲は前回実行の続きとして扱う。規範から実施を要すると判断した振り返りは、追加の作業・ユーザー発話・未取込みの改善点が無い場合だけ再起動を省略し、起動要否はこの追加分で決める。
7. 手順6で作業ツリーまたは履歴が変わり、起動元の工程がその公開を定める場合は公開を完了する。起動元の工程が報告前の確認を定める場合はそれも完了する。
8. 振り返りの最終報告を書く。対策のAWIを1件以上投入した場合は`references/report-formats.md`「AWI投入結果報告のフォーマット」、0件・未実施・失敗の場合は同書「振り返り結果報告のフォーマット」に従う。

   自律モードでは、作業完了報告と振り返り結果から、ユーザーが結果を把握し是正を依頼するための事後承認型UWIを1件作る。これを「報告用UWI」と呼び、本手順を定義の所在とする。本文は`references/report-formats.md`「報告用UWIのフォーマット」、投入は`agent-toolkit:wi-standards`の事後承認型の書式に従う。保存は`atk wi add`・`atk wi edit`の成功報告と警告で検収する（`agent-toolkit:wi-standards`の`SKILL.md`「投入と取得」）。保存の検収がユーザーへの伝達の完了条件であり、可視発話の有無とは別に判定する。投入に失敗した場合は既存のWI投入失敗の処置に従う。

   `atk run-skill`の実行では、報告用UWIの投入に`--source run-skill --scope <実行したスキル名>`を指定し、本文先頭のfrontmatterへ`run_skill_report: true`を置く。`atk wi add`と`atk wi edit`は起動元の実行識別子を`run_skill_run_id`へ記録する。同じ実行の再開と報告更新でもこの区分を保持する。報告本文の生成と十分性の判断は本スキルが所有し、起動元は保存済みUWIとGitの反映結果から、本文のcommitとupstream設定時のpushへの到達を確認する。保存未達は時間上限と区別した非0終了となるため、保存CLIの警告を解消し、同じ会話で報告保存を完了する。

   続けて最終報告を1回届ける（自律モードでは報告用UWIの保存を検収してから）。`send_to_user`が成功したら本文の送達は完了とし、要約や受領文を足さず同じ応答で手順9へ進む。ツールがない場合は最終報告自体をターン終端の本文とする。
9. 起動元の工程が報告の完了後に実行する工程（`agent-toolkit:process-wi`の`atk agents-exit-session`など）を定める場合は、最終報告と同じ応答でその工程を実行する。別の応答へ持ち越すと工程が起動されないまま`atk wi process-loop`が停止する。新しい改善点が無ければ報告後に実行するのはこの工程だけとし、通常の作業ターンへは次の指示を受けてから戻る。
   送達後に実際の新しい改善点が生じた場合は、`agent-toolkit:session-review`の工程6へ戻って取り込み・分析し、手順8を再実行して報告用UWIと結果を更新し、更新後の最終報告を届けてから本手順へ進む。
   全工程を終えて通常ターンだけを閉じる場合、`send_to_user`で最終報告を送達済みなら`…`だけを出力する。`atk agents-exit-session`で停止した分岐は出力も終える。送達失敗、Stop hookの遮断、新しいユーザー指示では、それぞれの回復・続行手順に従う。

最終送達後の終端指示の対照と再検証方法は、`docs/development/audit-records.md`の「completion-report：最終報告送達後のターン終端：2026年10月9日」にある。

### Stop hookの判定

Stop hookは、成果作業（`agent-toolkit:process-wi`・`agent-toolkit:add-awi-by-user`の開始、リポジトリの編集、計画やWIの保存、commit・push）を対象とする。
有効な省略と本スキルの起動の双方を確認できない終了を遮断し、起動と残る工程への続行を案内する。起動はClaude CodeではSkillの成功、Codexでは本書の読取の結果で確かめる。
Stop hookは報告本文の見出し、区切り、区分、候補IDを判定せず、起動後の工程の完遂と報告の内容も確かめない。各手順の完了と報告の内容は、メインが本節の手順と`references/report-formats.md`に従って確かめる。
遮断を受けたら、適用するプロジェクト規範による省略は`references/termination-evidence.md`へ進む。
起動が必要な場合は、本スキルを起動していなければ起動して手順1から、起動済みなら残る手順から進める。
ユーザーの中止・置換、確認の回答や委譲先の結果の待機、技術的に続行できない場合の判断の記録は`references/termination-evidence.md`に従う。

完了判定は本節の各手順の充足で行い、完了を自己申告する状態フラグは作成しない（セッション途中で失われると誤警告を反復させ、正当な工程を遮断するため）。
