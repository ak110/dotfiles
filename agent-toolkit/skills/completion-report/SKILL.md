# 作業完了報告

実装、計画、AWI投入など、成果を伴う作業をメインが完了したときに適用する。
適用の要否は、そのセッションで確定した成果物があるかで判定する。回答を返すに留まり成果物の確定を伴わない依頼は、適用の対象から外れる。単発の調査依頼がその例であり、調査報告をもとにその後の作業が発生する可能性があるためである。
サブエージェントが呼び出し元へ返す完了報告も適用の対象から外れる。

報告は`## 作業完了報告`と`## 振り返り結果報告`の独立した2つの節として順に出力する。
各節は入力が確定した段階で個別に内容を確かめる。作業完了報告を振り返りの起動前に出力し、振り返り結果報告を振り返りの準備スクリプトの終了後の応答で出力する。これにより、ユーザーは元作業の完了を振り返りの待機時間より先に把握できる。

## 完了の到達水準

「完了」は既知の問題を含めて対応済みである状態を指す。
ユーザーの操作が必須の事項だけが残った状態まで到達してから完了と報告する。
完了として報告できるのは、対象の全体を処理した状態とする。代表箇所だけの対処と一部の件数だけの反映は、途中経過として報告する。

## 工程

番号は各手順の入力が揃う順序を示し、直列に待つ対象を前の手順の出力へ依存する作業に限る。`agent-toolkit:session-review`の稼働中も、その成果を入力とせず同じ書込資源を占有しない作業は並行して進める。

1. 対象プロジェクトが開発マシン上で常時稼働するサーバーを持ち、そのプロジェクトの規範又はタスクランナー定義が稼働環境への反映手段と稼働確認手段の双方を定義している場合は、その反映手段で変更を反映し、その稼働確認手段で反映後の稼働を確認する。常時稼働するサーバーを持たないプロジェクトと、双方の手段を定義していないプロジェクトは対象外とする。反映しない場合は、その理由と、ユーザーが自分で反映するために必要な操作を報告へ含める。
2. メイン自身が`atk managed-temp create`で個別に作成した`.git`を含む領域（`agent-toolkit:managed-temp`の例外用途）があれば、管理CLIで回収する。セッション領域とその中のファイルは回収しない。
3. そのセッションで確定した人間由来の判断が`agent-toolkit/rules/01-agent.md`「協調と自律」の保存対象と比較済みであることを確認する。同節はこの確認を要求単位と計画の起草工程で実施すると定めるため、本手順では確認の結果を確かめるに留める。起草工程で確認していない場合だけ、ここで比較し、保存又はAWIの投入を完了させる。
4. `## 作業完了報告のフォーマット`に従って作業完了報告を管理対象一時領域へ起草する。`atk run-script completion-report-check -- <報告本文の絶対パス> --stage work-complete`で検証し、終了コード0の標準出力を作業完了報告として1回出力する。この段階では振り返り状態を指定しない。可視出力は実行環境がターンの終端として扱うため、出力だけで応答を終えず、同じ応答で手順5の起動へ進む。
5. `agent-toolkit:session-review`を起動する。

   そのセッションの振り返りを既に実施している場合は、前回の準備時刻と現在のセッションの記録の終端を比べる。
   準備時刻より後に作業を継続している場合は、`agent-toolkit:session-review`を再び起動する。前回の素材AWIは新しい素材の既存キュー項目に載り、処理するレーンが重なる候補を前回の素材AWIへ対応付ける。
   起動を省略できるのは、比べた結果、準備時刻より後の作業が無い場合とする。素材AWIを投入済みであることは、省略の条件から外れる。
6. 手順5の結果として作業ツリー又は履歴が変わり、起動元の工程がその変更の公開を定める場合は、その公開手順を完了してから次へ進む。
7. 起動元の工程が報告前に完了させる確認を定める場合は、その確認を完了してから次へ進む。
8. `## 振り返り結果報告のフォーマット`に従って振り返り結果報告を管理対象一時領域へ起草する。正常完了、未実施又は失敗に対応する`--review-state`を指定する。次のコマンドで検証する。

   ```text
   atk run-script completion-report-check -- <報告本文の絶対パス> --stage review-result --review-state <success|not-run|failed>
   ```

   自律モードでは、手順4と本手順で確定した完了報告と振り返り結果を、1件の事後承認型UWIの判断材料へまとめる。同じ作業で曖昧な要求を具体化した場合は、元の要求、採用した解釈、対応範囲、実施結果及び判断根拠を含める。元の要求単位に未達がある場合は、形式上の完成条件を満たしていても、その結果と理由を同じUWIへ含める。未解決の問題、見送り・先送り、ユーザーの操作が必要な事項、処理中にユーザーの指摘へ答えた内容も同じUWIへ含める。振り返りが失敗した場合は、完了した成果と分析未完了の状態を記す。UWIは`agent-toolkit:wi-standards`の事後承認型の書式で投入し、保存成功と保存本文を`atk wi show`で確認する。投入に失敗した場合は既存のWI投入失敗の処置に従い、保存成功の確認をセッション終了の条件とする。完了報告と振り返りは同じUWIへ記録する。

   本手順の終了コード0の標準出力を、振り返り結果報告として1回出力する。自律モードでは、前段のUWI保存を確認してから出力する。
9. 起動元の工程が報告の完了後に実行する工程を定める場合は、その工程を実行する。`agent-toolkit:process-wi`では、報告完了後に`atk agents-exit-session`を単独で実行する工程が該当する。
    振り返り結果報告と同じ応答へ、この工程を含める。
    報告の完了後にその応答で実行するのはこの工程だけとし、通常の作業ターンへの復帰は次の指示を受け取ってから行う。
    報告本文は実行環境がターンの終端として扱う可視出力であり、工程を別の応答へ分けると、その工程が起動されないまま常駐処理が停止する。

## 作業完了報告のフォーマット

手順5の起動より前に、次の書式で起草してチェックする。振り返りを実行する旨の予告行は書かない。

```text
## 作業完了報告

<1文の元作業の完了結果>

### 成果

- <元作業に対する成果の全体>

### 投入したWI

- <ファイル名>: <H1タイトル>
- <ファイル名>: <H1タイトル> (target_repo=<...>)
```

`### 成果`へ書く対象は、そのセッションで受け取った依頼（元作業）に対する成果の全体とする。
セッションの途中で生じた別事象への処置は、元作業に対する成果と区別できる形で添える。
同一セッションで本スキルを2回目以降に起動して報告する場合も、既に報告済みの成果を含めて元作業に対する成果の全体を再構成する。
報告の発行に先立って、そのセッションで受け取った依頼の原文にある要求単位と`### 成果`の各項目を対応付ける。形式上の完成条件を満たしていても、要求単位に未達があれば結果と理由を書き、協調モードではその場で伝える。
振り返りが未完了でも元作業が完了していれば、冒頭は元作業の完了を言い切る。

`### 投入したWI`はそのセッションで作業完了報告のテキスト出力前に投入したWI（AWIとUWI、種別は問わない）のうち、報告時点で終端していない項目を対象とする。処理対象として取得した項目と、`adopted`か`rejected`へ終端した項目は対象外とする。終端項目は同じユーザーが回答や終端判断の時点で内容を確認しており、再掲しても新しい判断材料にならないためである。
報告のテキストを出力する直前に、そのセッションで投入したファイル名を全て引数として`atk wi show <ファイル名>... --target-repo=<対象リポジトリの絶対パス> --skip-pull`を1回実行し、`### <ファイル名> [<状態>]`の見出し行から現在状態を読む。対象リポジトリが異なる項目は対象リポジトリごとに1回へまとめる。
0件の場合は`- なし`と書く。1件あたりの表示は`- <ファイル名>: <H1タイトル>`とし、`target_repo`が現在の対象リポジトリと異なる場合だけ、末尾へ半角空白1字に続けて`(target_repo=<正規化リモートURLか絶対パス>)`を追記する。

## 振り返り結果報告のフォーマット

`agent-toolkit:session-review`が正常完了した場合は、次の書式で起草してチェックする。

```text
## 振り返り結果報告

- 候補: <N>件 (<候補種別> <件数>件 / ...)
- メイン由来の改善点: <M>件
- 所要時間: <秒数>秒 (素材作成時点)

### 対策として投入したWI

- <素材AWIのファイル名>: <H1タイトル>
```

振り返りが未実施又は失敗の場合は、次の書式で起草してチェックする。

```text
## 振り返り結果報告

### 振り返り

- session-review未実施: <理由。関連するUWIがある場合はファイル名を末尾に併記>
```

未実施の理由は2種に分類する。既に振り返りを実施した成果が、そのセッションの記録の終端まで覆っている場合は`成果を再利用したため起動省略`とする。準備スクリプトが再実行後も失敗した場合は`分析失敗のため欠陥AWIへ記録`とする。後者でも元依頼のうち認可済みで技術的に実行可能な工程を継続する。

正常完了の`### 対策として投入したWI`と、未実施又は失敗の`### 振り返り`は同じ振り返り結果報告へ併記しない。

各値の取得元は準備スクリプトの1行JSONとする。

- `候補`は`candidate_total`と`candidate_counts`の種別ごとの件数とする。0件の場合は`0件`だけを書く
- `メイン由来の改善点`は`main_observation_count`とする
- `所要時間`は`elapsed_seconds`とし、セッションの最初の記録から素材の作成時点までの値であることを括弧書きで示す。セッション全体の所要時間と目標の比較は、素材AWIを処理するレーンが行う
- `### 対策として投入したWI`は`submitted`が真の場合に`awi_filename`の素材AWIを1件書く。投入しなかった場合は`- なし`とし、`skipped_reason`がある場合はその理由を、対象リポジトリを渡さなかった場合は素材本文を投入していない旨を同じ行へ書く。報告直前の状態取得と1件あたりの表示規則は`### 投入したWI`と同じとする

完了判定は`## 工程`の各項目の充足で行い、呼び出し忘れ検出用の状態フラグは作成しない。
状態フラグはセッション途中で失われて誤警告を反復させ、正当な工程を誤って遮断した実績がある。
