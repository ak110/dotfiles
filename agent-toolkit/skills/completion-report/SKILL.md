# 作業完了報告とセッションの完了処理

作業の結果は、都合の悪い結果も含めて正直に報告する。作業完了報告、振り返り結果報告およびAWI投入結果報告のいずれにも適用する。

実装、計画、AWI投入など、成果を伴う作業をメインが完了したときに適用する。
適用の要否は、そのセッションで確定した成果物があるかで判定する。回答を返すに留まり成果物の確定を伴わない依頼は、適用の対象から外れる。単発の調査依頼がその例であり、調査報告をもとにその後の作業が発生する可能性があるためである。
サブエージェントが委譲元へ返す完了報告も適用の対象から外れる。

報告は入力が確定した時点で内容を確かめ、独立した節で届ける。`## 作業完了報告`は振り返り起動前に出力する。
振り返りでAWIを1件以上投入する場合は、`agent-toolkit:session-review`の`SKILL.md`「工程」のWI投入担当を起動する段落に従って、投入前に`## 振り返り結果の予告`を報告し、投入後は`## AWI投入結果報告`を最終報告とする。
投入0件、未実施または失敗の場合は、振り返り完了後の`## 振り返り結果報告`1回を最終報告とする。
送達は`agent-toolkit:user-confirmation-and-report`「手段の選択」に従う。Claude Codeは途中・末尾とも`mcp__agent-toolkit__send_to_user`を使い、ツール不在時の代替は主体別規範に従う。最終報告だけ、末尾に「以上で、このセッションの作業は全て終わりました」と書く。

## 読込表

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 作業完了報告、振り返り結果報告、AWI投入結果報告または報告用UWIの本文を書く前 | `references/report-formats.md` |
| 手順4で、協調モードの確認済みの公開範囲がcommitより先へ及ぶ場合 | `agent-toolkit:commit`の`references/publish.md` |
| Stop hookが終了工程の不足を示して遮断した時と、ユーザーの中止・置換、回答や委譲先の待機、技術的不成立の判断を記録する時 | `references/termination-evidence.md` |

## 完了の到達水準

「完了」は対象全体と既知の問題へ対応し、ユーザー操作が必須の事項だけが残る状態とする。代表箇所や一部だけの反映は途中経過として報告する。

## 工程

番号は各手順の入力が揃う順序を示し、直列に待つ対象を前の手順の出力へ依存する作業に限る。`agent-toolkit:session-review`の稼働中も、その成果を入力とせず同じ書込資源を占有しない作業は並行して進める。

1. 対象プロジェクトが開発マシン上で常時稼働するサーバーを持ち、そのプロジェクトの規範またはタスクランナー定義が稼働環境への反映手段と稼働確認手段の双方を定義している場合に本手順を適用する。常時稼働するサーバーを持たないプロジェクトと、双方の手段を定義していないプロジェクトは対象外とする。本スキルを起動した工程が反映を先行して実施した場合は、反映済みHEADの完全OID、反映コマンドの終了状態と稼働確認の結果を受け取り、報告時点の主作業ツリーHEADを完全OIDで取得して次のとおり扱う。
   - 先行反映済みHEADと一致し、反映・稼働確認の双方が成功している: その結果を用いて再反映を省く。
   - HEADが異なるか、先行結果が失敗している: 現行HEADを反映して稼働を確認する。
   - 先行結果が無い: その反映手段で変更を反映し、その稼働確認手段で反映後の稼働を確認する。

   反映しない場合は、その理由と、ユーザーが自分で反映するために必要な操作を報告へ含める。反映した場合は、再反映の有無と稼働確認の結果を報告する。

   本スキルを起動した工程が反映を先行して始められるのは、反映が対象リポジトリへ書き込まず、公開の入力を生成せず、読み取る成果物と排他資源が公開操作と競合しない場合に限る。
2. メイン自身が`atk managed-temp create`で個別に作成した`.git`を含む領域（`agent-toolkit:managed-temp`の例外用途）があれば、`atk managed-temp cleanup`で回収する。セッションのmanaged-tempとその中のファイルは回収しない。
3. そのセッションでユーザーが確定した判断を`agent-toolkit/rules/01-agent.md`「協調と自律」の保存対象と比較し、保存されていない判断は保存またはAWIの投入を完了させる。保存の前に`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」の、程度の限定と確度を保持する箇条と確度を伴う発話の保存を扱う箇条を適用する。
4. 協調モードで対象リポジトリへcommitした成果があり、確認済みの公開範囲がcommitより先へ及ぶ場合は、`agent-toolkit:commit`の`references/publish.md`に従ってその範囲の公開を完了する。`agent-toolkit:process-wi`と`agent-toolkit:single-lane-process`は自身の工程で公開するため、この分岐を重ねない。
5. `references/report-formats.md`「作業完了報告のフォーマット」に従い、実施した公開範囲とリリース判定の結果を含む作業完了報告を、冒頭の送達手段で1回届ける。出力だけで応答を終えず、同じ応答で手順6の起動へ進む。
6. `agent-toolkit:session-review`を起動する。

   そのセッションの振り返りを既に実施している場合は、前回の準備時刻（`atk run-script session-review-prepare`のJSONの`prepared_at`）と現在のセッションの記録の終端を比べる。
   準備時刻より後に本体の作業を継続した場合、または準備に含まれていない実際の改善点が届いた場合は、`agent-toolkit:session-review`を再び起動する。準備後のユーザー発話と改善点の扱いは同スキルの工程6に従う。
   前回の振り返りが投入したAWIは未終端の既存項目として重複判定の対象になり、同じ問題を重ねて投入しない。
   前回の振り返り自身の通常の起草・投入・待機・検収と、取込み済みの行の転記・再掲は、前回実行の続きとして扱う。
   起動を省略できるのは、比べた結果、追加の作業・ユーザー発話・未取込みの改善点が無い場合とする。起動要否はAWIの投入状態ではなく、この追加分から決める。
7. 手順6の結果として作業ツリーまたは履歴が変わり、本スキルを起動した工程がその変更の公開を定める場合は、その公開手順を完了してから次へ進む。
8. 本スキルを起動した工程が報告前に完了させる確認を定める場合は、その確認を完了してから次へ進む。
9. 振り返りの最終報告を書く。振り返りが対策のAWIを1件以上投入した場合は`references/report-formats.md`「AWI投入結果報告のフォーマット」に従い、投入が0件の場合と振り返りが未実施・失敗の場合は同書「振り返り結果報告のフォーマット」に従う。

   自律モードでは、手順5と本手順で確定した完了報告と振り返り結果から、ユーザーが結果を把握し是正を依頼するための事後承認型UWIを1件作る。このUWIを「報告用UWI」と呼び、本手順を定義の所在とする。本文は`references/report-formats.md`「報告用UWIのフォーマット」に従う。報告用UWIは`agent-toolkit:wi-standards`の事後承認型の書式で投入し、保存の検収は同スキルの`SKILL.md`「投入と取得」にある`atk wi add`・`atk wi edit`の成功報告と警告の検収に従う。投入に失敗した場合は既存のWI投入失敗の処置に従い、保存の検収の成立をセッション終了の条件とする。報告用UWIの保存の検収はユーザーへの伝達の完了条件であり、可視発話の有無とは別に判定する。

   続けて、振り返りの最終報告を冒頭の送達手段で1回届ける。自律モードでは、前段の報告用UWIの保存を検収してから出力する。
   `send_to_user`が成功した後は本文の送達を完了とし、同じ応答で手順10へ進む。要約、再説明、受領文などの追加本文の代わりに、手順10の終端本文を使う。ツールがないClaude CodeとCodexでは最終報告自体をターン終端の本文とし、末尾の固定文で閉じる。手順5の作業完了報告と振り返りの予告は残工程があるため、続行する。
10. 本スキルを起動した工程が報告の完了後に実行する工程を定める場合は、その工程を実行する。`agent-toolkit:process-wi`では、報告完了後に`atk agents-exit-session`を単独で実行する工程が該当する。
    振り返りの最終報告と同じ応答へ、この工程を含める。
    新しい改善点が無い場合は、報告の完了後にその応答で実行するのはこの工程だけとし、通常の作業ターンへの復帰は次の指示を受け取ってから行う。
    送達後に実際の新しい改善点が生じた場合は、`agent-toolkit:session-review`の工程6へ戻って取り込み、分析する。
    続けて手順9を再実行し、保存した報告用UWIと結果を更新して、更新後の最終報告を同手順の送達手段で届けてから本手順へ進む。
    最終報告の送達とターン終端を接続し、この工程まで同じ応答で完了させる。別の応答へ持ち越すと、その工程が起動されないまま`atk wi process-loop`が停止する。
    全工程を終えて通常ターンだけを閉じる場合、`send_to_user`で最終報告を送達済みなら`…`だけを出力する。`atk agents-exit-session`で既に停止した分岐は出力も終了とする。送達失敗、Stop hookによる不足の遮断、新しいユーザー指示では、それぞれの既存の回復・続行手順に従う。

最終送達後の終端指示の対照と再検証方法は、`docs/development/audit-records.md`の「completion-report：最終報告送達後のターン終端：2026年10月9日」にある。

Stop hookは送信本文を含む可視発話の報告見出しと振り返りの準備結果から、冒頭の報告順で不足する段階を示す。予告後はAWI投入結果報告を待ち、旧形式の`## 振り返り結果報告`に`AWI登録予定`がある記録も同じく扱う。
振り返りの報告は最新の成功した準備以後の本文で判定し、それより前の予告・結果・投入結果は流用しない。
再準備が失敗した場合は直前の成功した準備との対応を使い、作業完了報告は作業開始以後の本文で判定する。
未取込みの改善点の通知を受けた場合は、通知された行を準備・分析へ含め、結果報告を更新してから終了する。
次の確認を、項目数によらず「報告本文の判定」と呼ぶ。

- `### 確定した問題と対策`の各行が先頭の区分に応じた根拠を持つか（`AWI登録`と`AWI登録済み`はAWIのファイル名、`AWI登録予定`はH1タイトル、`実装済み`は要旨と根拠）
- `### 対策を見送った問題`の`判定済み`行が問題と根拠を持ち、根拠に未照会・未確定を使っていないか
- 同じ節の`未確定`行が照会、再現、残る理由を全て持ち、`再発防止策なし`行が評価した案、採らない理由、反復を全て持つか
- 準備結果の`mandatory_candidates`が挙げる再発防止策が必須の候補を、いずれかの行が候補IDで扱い、その候補の`判定済み`行が根拠の先頭へ除外区分を持ち、`再発防止策なし`行の反復が準備結果の過去の同種記録のファイル名を持つか
- `## AWI投入結果報告`に`AWI登録予定`の行が残っていないか

Stop hookは予告にも同じ内容判定を適用し、違反した行と直し方を示す。H3の順序・要約の接頭辞・なしの併記・未実施理由の定型文・終端の一文・言い回しは報告本文の判定に含めない。遮断を受けたら不足段階と修正した本文を冒頭の送達手段で届ける。
ユーザーの中止・置換、確認の回答や起動した委譲先の結果の待機、技術的に続行できない場合の判断の記録は、読込表の行が挙げる`references/termination-evidence.md`に従う。

完了判定は`## 工程`の各項目の充足で行い、呼び出し忘れ検出用の状態フラグは作成しない。状態フラグはセッション途中で失われると誤警告を反復させ、正当な工程を誤って遮断するためである。
