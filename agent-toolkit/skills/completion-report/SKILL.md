# 作業完了報告

作業の結果は、都合の悪い結果も含めて正直に報告する。作業完了報告、振り返り結果報告およびAWI投入結果報告のいずれにも適用する。

実装、計画、AWI投入など、成果を伴う作業をメインが完了したときに適用する。
適用の要否は、そのセッションで確定した成果物があるかで判定する。回答を返すに留まり成果物の確定を伴わない依頼は、適用の対象から外れる。単発の調査依頼がその例であり、調査報告をもとにその後の作業が発生する可能性があるためである。
サブエージェントが委譲元へ返す完了報告も適用の対象から外れる。

報告は`## 作業完了報告`、`## 振り返り結果報告`および`## AWI投入結果報告`の独立した節とし、それぞれの入力が確定した時点で順に出力する。
各節は入力が確定した段階で個別に内容を確かめる。作業完了報告は振り返りの起動前に出力する。振り返りが対策のAWIを1件以上投入する場合、振り返り結果報告は`agent-toolkit:session-review`の工程5が投入の前に予告として出力し、投入の完了後に`## AWI投入結果報告`を最終報告として出力する。投入が0件の場合と振り返りが未実施・失敗の場合は、振り返り結果報告を振り返りの完了後に1回だけ出力する。これにより、ユーザーは元作業の完了を振り返りの待機より先に、投入しようとしているAWIを投入の待機より先に把握できる。

## 読込表

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 作業完了報告、振り返り結果報告、AWI投入結果報告または報告用UWIの本文を書く前 | `references/report-formats.md` |
| 手順4で、協調モードの確認済みの公開範囲がcommitより先へ及ぶ場合 | `agent-toolkit:commit`の`references/publish.md` |

## 完了の到達水準

「完了」は既知の問題を含めて対応済みである状態を指す。
ユーザーの操作が必須の事項だけが残った状態まで到達してから完了と報告する。
完了として報告できるのは、対象の全体を処理した状態とする。代表箇所だけの対処と一部の件数だけの反映は、途中経過として報告する。

## 工程

番号は各手順の入力が揃う順序を示し、直列に待つ対象を前の手順の出力へ依存する作業に限る。`agent-toolkit:session-review`の稼働中も、その成果を入力とせず同じ書込資源を占有しない作業は並行して進める。

1. 対象プロジェクトが開発マシン上で常時稼働するサーバーを持ち、そのプロジェクトの規範またはタスクランナー定義が稼働環境への反映手段と稼働確認手段の双方を定義している場合に本手順を適用する。常時稼働するサーバーを持たないプロジェクトと、双方の手段を定義していないプロジェクトは対象外とする。本スキルを起動した工程が反映を先行して実施した場合は、反映済みHEADの完全OID、反映コマンドの終了状態と稼働確認の結果を受け取り、報告時点の主作業ツリーHEADを完全OIDで取得して次のとおり扱う。
   - 先行反映済みHEADと一致し、反映・稼働確認の双方が成功している: その結果を用いて再反映を省く。
   - HEADが異なるか、先行結果が失敗している: 現行HEADを反映して稼働を確認する。
   - 先行結果が無い: その反映手段で変更を反映し、その稼働確認手段で反映後の稼働を確認する。

   反映しない場合は、その理由と、ユーザーが自分で反映するために必要な操作を報告へ含める。反映した場合は、再反映の有無と稼働確認の結果を報告する。
2. メイン自身が`atk managed-temp create`で個別に作成した`.git`を含む領域（`agent-toolkit:managed-temp`の例外用途）があれば、`atk managed-temp cleanup`で回収する。セッションのmanaged-tempとその中のファイルは回収しない。
3. そのセッションで確定した人間由来の判断を`agent-toolkit/rules/01-agent.md`「協調と自律」の保存対象と比較し、保存されていない判断は保存またはAWIの投入を完了させる。保存の前に`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`の、程度の限定と確度を保持する箇条と確度を伴う発話の保存を扱う箇条を適用する。
4. 協調モードで対象リポジトリへcommitした成果があり、確認済みの公開範囲がcommitより先へ及ぶ場合は、`agent-toolkit:commit`の`references/publish.md`に従ってその範囲の公開を完了する。`agent-toolkit:process-wi`と`agent-toolkit:single-lane-process`は自身の工程で公開するため、この分岐を重ねない。`references/report-formats.md`「作業完了報告のフォーマット」に従って実施した公開範囲とリリース判定の結果を含む作業完了報告を可視の発話本文へ直接1回書く。可視出力は実行環境がターンの終端として扱うため、出力だけで応答を終えず、同じ応答で手順5の起動へ進む。
5. `agent-toolkit:session-review`を起動する。

   そのセッションの振り返りを既に実施している場合は、前回の準備時刻（`atk run-script session-review-prepare`のJSONの`prepared_at`）と現在のセッションの記録の終端を比べる。
   準備時刻より後に作業を継続している場合は、`agent-toolkit:session-review`を再び起動する。前回の振り返りが投入したAWIは未終端の既存項目として重複判定の対象になり、同じ問題を重ねて投入しない。
   起動を省略できるのは、比べた結果、準備時刻より後の作業が無い場合とする。前回の振り返りでAWIを投入済みであることは、省略の条件から外れる。
6. 手順5の結果として作業ツリーまたは履歴が変わり、本スキルを起動した工程がその変更の公開を定める場合は、その公開手順を完了してから次へ進む。
7. 本スキルを起動した工程が報告前に完了させる確認を定める場合は、その確認を完了してから次へ進む。
8. 振り返りの最終報告を可視の発話本文へ直接1回書く。振り返りが対策のAWIを1件以上投入した場合は`references/report-formats.md`「AWI投入結果報告のフォーマット」に従い、投入が0件の場合と振り返りが未実施・失敗の場合は同書「振り返り結果報告のフォーマット」に従う。自律モードでは後段の報告用UWIの保存を検収してから発話する。

   自律モードでは、手順4と本手順で確定した完了報告と振り返り結果から、ユーザーが結果を把握し是正を依頼するための事後承認型UWIを1件作る。このUWIを「報告用UWI」と呼び、本手順を定義の所在とする。本文は`references/report-formats.md`「報告用UWIのフォーマット」に従う。

   報告用UWIは`agent-toolkit:wi-standards`の事後承認型の書式で投入し、保存の検収は同スキル「投入と取得」手順9に従う。投入に失敗した場合は既存のWI投入失敗の処置に従い、保存の検収の成立をセッション終了の条件とする。

   本手順で確定した振り返りの最終報告を可視の発話本文へ直接1回書く。自律モードでは、前段の報告用UWIの保存を検収してから出力する。報告用UWIの保存の検収はユーザーへの伝達の完了条件であり、可視発話の有無とは別に判定する。
9. 本スキルを起動した工程が報告の完了後に実行する工程を定める場合は、その工程を実行する。`agent-toolkit:process-wi`では、報告完了後に`atk agents-exit-session`を単独で実行する工程が該当する。
    振り返りの最終報告と同じ応答へ、この工程を含める。
    報告の完了後にその応答で実行するのはこの工程だけとし、通常の作業ターンへの復帰は次の指示を受け取ってから行う。
    報告本文は実行環境がターンの終端として扱う可視出力であり、工程を別の応答へ分けると、その工程が起動されないまま`atk wi process-loop`が停止する。

Stop hookは可視発話の報告見出しと振り返りの準備結果から不足段階を示す。作業完了報告・準備の後は振り返り結果報告を、投入予定を示した予告の後はAWI投入結果報告を直接発話する。
Stop hookが報告の本文へ適用する次の判定を、報告本文の判定と呼ぶ。報告本文の判定は報告の項目数によらずこの名前で指す。

- `### 確定した問題と対策`の各行が、投入したAWIのファイル名、`（投入予定: <H1タイトル>）`、`（同一セッションで実装済み: <...>）`のいずれかを持つか
- `### 対策を見送った問題`の`判定済み`行が問題と根拠を持ち、根拠に未照会・未確定を使っていないか
- 同じ節の`未確定`行が照会、再現、残る理由を全て持つか
- `## AWI投入結果報告`に`投入予定:`が残っていないか

Stop hookは違反した行と直し方を示す。H3の順序・要約の接頭辞・なしの併記・未実施理由の定型文・言い回しは報告本文の判定に含めない。遮断を受けたら不足段階を発話し、示された違反行を直す。
ユーザーが作業の中止、別作業への置換を指示した場合、確認の回答または起動した委譲先の結果を待つ場合、技術的に続行できない場合は、`atk run-script termination-evidence -- --decision-file <判断JSONの絶対パス>`で判断を記録する。
判断JSONは`session_id`、`action`（`cancel`・`replace`・`start`・`resume`・`wait`・`blocked`）、対象の`work_id`と`reason`を持つ。
中止・置換・開始・再開にはユーザーの原入力の`input_id`と全文の`quote`を、確認待ちには投入した未回答UWIの`uwi_file`と全文の`quote`を、委譲先の待機には`target_session_id`を、技術的不成立には失敗した呼び出しの`call_id`とその応答全体のJSONの`quote`を渡す。
`session_id`、`work_id`と直近のユーザー入力の`input_id`は遮断の通知から得る。
判断は指定した作業だけへ作用し、ユーザーの割り込みと直接関係しない他の作業の残工程は残る。
生成されたStopの継続入力やhookの注記はユーザーの原入力として受理されず、完了の申告を記録する操作は無い。
証拠を取得できない場合は遮断せず、判定できなかったことを記録する。
自律モードの報告用UWIの保存検収と`atk agents-exit-session`は報告段階の判定と別の工程として維持する。

完了判定は`## 工程`の各項目の充足で行い、呼び出し忘れ検出用の状態フラグは作成しない。状態フラグはセッション途中で失われると誤警告を反復させ、正当な工程を誤って遮断するためである。
