# 報告のフォーマット

本書は`agent-toolkit:completion-report`が出力する作業完了報告、振り返り結果報告、AWI投入結果報告と、自律モードで投入する報告用UWIの本文の書式を定める。出力する時点と順序は同スキルの`SKILL.md`「工程」が定める。

4種の報告は、ユーザーが結論と、判断・行動に必要な要点（作業結果、未達、必要な操作、処置の状態）を短く読める形で書く。原因分析や照会の経緯、AWIのH1タイトルと同じ内容の概要は展開せず、分析はAWIと証拠の記録に残す。判定済みの観測根拠、未確定の照会・再現・残る理由、未達と必要な操作は判断を変える内容のため、要約して残す。

## 作業完了報告のフォーマット

`SKILL.md`「工程」の手順5の起動より前に、次の書式で可視の発話本文へ直接書く。振り返りを実行するという予告の行は省き、実施済みの内容を書く（努力目標。未実施の工程を報告へ混ぜないため）。

```text
## 作業完了報告

<依頼者がその依頼で知りたかった答えを1文で>

### 成果

- <元作業に対する成果>

### 投入したWI

- <ファイル名>: <H1タイトル>
- <ファイル名>: <H1タイトル> (target_repo=<...>)
```

冒頭は原文の目的に答え、達成した結果を工程・件数より先に示す。後続工程へ委ねる成果は見込みか算出できない理由を書き、必要な値を委譲先が持つ場合は返却を指定する。振り返りの進行とは分けて、元作業で確定した答えを述べる。

`### 成果`は原文の要求単位に対応させ、元作業の成果全体を1件1行で書く。冒頭との重複を省き、別事象への処置は区別して添える。同一セッションで再報告する場合も既報分を含む全体を示す。形式上の完成条件によらず、要求単位の未達は結果と理由を記し、協調モードではその場で伝える。

`### 投入したWI`にはそのセッションで作業完了報告のテキスト出力前に投入したWI（AWIとUWI、種別は問わない）のうち、報告時点で終端していない項目を書く。処理対象として取得した項目と、`adopted`か`rejected`へ終端した項目は対象から外す。終端項目は同じユーザーが回答や終端判断の時点で内容を確認しており、再掲しても新しい判断材料にならないためである。
報告の直前に、そのセッションで投入した全ファイル名を`atk wi show <ファイル名>... --summary-only --target-repo=<対象リポジトリの絶対パス> --skip-pull`へ渡す。
`### <ファイル名> [<状態>]`の見出し行から現在状態を、その次の行からAWIのH1タイトルかUWIの質問本文の先頭行を読む。
照会は対象リポジトリごとに1回へまとめる（努力目標。往復を減らすため）。
0件の場合は`- なし`と書く。1件あたりの表示は`- <ファイル名>: <H1タイトル>`とし、UWIではH1タイトルの位置へ質問本文の先頭行を書く。`target_repo`が現在の対象リポジトリと異なる場合だけ、末尾へ半角空白1字に続けて`(target_repo=<正規化リモートURLか絶対パス>)`を追記する。

ユーザーの操作・回答・判断が必要な場合だけ、末尾へ`### 要対応`を置き、ユーザーが次に行う具体的な1操作を書く。対応が不要な場合は節ごと省く。自律モードの報告用UWIが持つ`### 要対応`はこの省略規則の対象外とする。
質問せずに自ら確定した判断のうち、別の合理的な実装者なら異なる判断をし得るものがある場合は、`### 成果`の後へ`### 自ら確定した判断`を置き、次の書式で書く。該当が無い場合は節ごと省く。並べ順はユーザーが異論を持つ可能性が高い順とする（努力目標。異論の出やすい判断を先に読めるようにするため）。

```text
### 自ら確定した判断

- **決定**: <エージェントが選んだ内容>
  - **理由**: <なぜそれを選んだか>
  - **最有力の対案**: <選ばなかった中で最も有力だった案>
```

この節は承認を求めるものではなく、報告の後に追加承認を待たない。ユーザーが後から異論を示した場合は、その判断と依存する後続判断を更新する。自律モードでは、報告用UWIの`### 自ら確定した判断`へも同じ内容を同節の1件1行の形式で書く。

## 振り返り結果報告のフォーマット

`agent-toolkit:session-review`が正常完了した場合は、次の書式で可視の発話本文へ直接書く。

```text
## 振り返り結果報告

- 候補: <N>件 (<候補種別> <件数>件 / ...)
- 所要時間: <秒数>秒 (準備時点)
- 改善見込み: <案の合計短縮見込み、改善後の全体所要時間、目標値との差、超過時の律速区間。時間改善案が無い場合は「なし」>

### 確定した問題と対策

- AWI登録予定: <H1タイトル>（<候補ID>）
- AWI登録: <ファイル名>: <H1タイトル>（<候補ID>）
- AWI登録済み: <ファイル名>: <H1タイトル>（<候補ID>）
- 実装済み: <対策の要旨>; 根拠: <commitの短縮OIDまたは変更した成果物>（<候補ID>）

### 対策を見送った問題

- 判定済み: <問題>; 根拠: <対策不要と確定した観測>（<候補ID>）
- 未確定: <問題>; 照会: <試行と結果>; 再現: <試行と結果または不能の具体的理由>; 残る理由: <確定できない理由>（<候補ID>）
- 再発防止策なし: <問題>; 評価した案: <案>; 採らない理由: <理由>; 反復: <過去の同種記録のファイル名と前回の処置で再発を防げなかった条件、または「一致なし」>（<候補ID>）
- なし
```

`### 確定した問題と対策`は原因・対策を確定した問題ごとに1行とし、前掲書式の区分を次の意味で使う。

- `AWI登録予定`: `agent-toolkit:session-review`の工程5による投入前の予告
- `AWI登録`: 振り返りで新しく投入したAWI
- `AWI登録済み`: 対策を覆う既存の未終端項目
- `実装済み`: 同じセッションで実装した対策

H1タイトルから問題と対策を読み取れる行には同じ内容の概要を重ねず、読み取れない場合だけ`; 要旨: <補う内容>`をタイトルの後へ添える。複数の問題を1件のAWIで覆う場合は、それぞれの行へ同じAWIを書くか、1行の候補IDの括弧へ複数のIDを並べる。

`### 対策を見送った問題`には候補一覧と会話の流れで見つけた問題のうち対策を見送ったものを前掲の形式で書く。除外、欠陥ではないとの判断、再発防止策なしの判断のいずれの場合も理由を示す。`判定済み`の根拠には確認済みの観測を短く書き、欠陥ではないとの判定、原因が未確定、分析した後に処置を採用しない判断のどれに当たるかが読み取れるようにする。原因または対策が未確定なら`未確定`の行へ照会、再現と残る理由を全て書く。分析した後に再発防止策を採用しない問題は`再発防止策なし`の行で書く。見送ってよい条件は`agent-toolkit:session-review`の`references/analysis.md`「入力と照会」「一次選別」「原因と対策」に従う。

候補一覧の候補に当たる行は、行末の括弧へ候補ID（`c0006`の形。複数は読点で区切る）を書く。`atk run-script session-review-prepare`が再発防止策を必須と示した候補（1行JSONの`mandatory_candidates`）は次のいずれかの行で必ず扱う。

- `### 確定した問題と対策`の行
- 根拠の先頭へ除外区分（`single-inquiry`、`non-changing-request`、`unexplained-refusal`、`necessary-confirmation`）を書いた`判定済み`の行（例: `根拠: non-changing-request: <観測>`）
- `未確定`の行
- `再発防止策なし`の行。準備結果がその候補に過去の同種記録を示した場合は、反復の欄へそのうち1件以上のファイル名と、前回の処置で再発を防げなかった条件を書く

Stopが判定するのは`SKILL.md`「工程」の報告本文の判定までで、証拠の実在、原因との対応と案の採否はメインが確かめる。
いずれのH3も該当が無い場合は`- なし`とする。報告直前の状態取得と1件あたりの表示規則は`### 投入したWI`と同じとする。

振り返りが未実施または失敗の場合は、次の書式で可視の発話本文へ直接書く。

```text
## 振り返り結果報告

### 振り返り

- session-review未実施: <理由。関連するUWIがある場合はファイル名を末尾に併記>
```

未実施の理由は2種に分類する。既に振り返りを実施した成果が、そのセッションの記録の終端まで覆っている場合は`成果を再利用したため起動省略`とする。`atk run-script session-review-prepare`が再実行後も失敗した場合は`分析失敗のため欠陥AWIへ記録`とする。後者でも元依頼のうち認可済みで技術的に実行可能な工程を継続する。

正常完了の2つのH3と、未実施または失敗の`### 振り返り`は同じ振り返り結果報告へ併記しない。

要約行の値の取得元は`atk run-script session-review-prepare`の1行JSONとする。

- `候補`は`candidate_total`と`candidate_counts`の種別ごとの件数（`atk run-script session-review-evidence`の除外後）とする。0件の場合は`0件`だけを書く
- `所要時間`は`elapsed_seconds`とし、セッションの最初の記録から準備時点までの値であることを括弧書きで示す。セッション全体の所要時間と目標の比較は、振り返りの所要時間の分析が行う
- `改善見込み`は時間改善案の最終値を集計し、合計短縮見込み、改善後の所要時間、目標値との差を1か所で示す。超過する場合は律速区間も示す。各AWIにはその案固有の値だけを書く

## AWI投入結果報告のフォーマット

振り返りが対策のAWIを1件以上投入した場合は、予告の後の最終報告を次の書式で可視の発話本文へ直接書く。

```text
## AWI投入結果報告

<1文。予告どおり投入を完了した旨、または予告と異なる結果があった旨>

### 投入したAWI

- <ファイル名>: <H1タイトル>
- <ファイル名>: <H1タイトル> (target_repo=<...>)

### 予告との差分

- <予告した対策>: <実際の結果>
```

`### 投入したAWI`には新たに投入したAWIを書き、0件なら`- なし`とする。報告直前の状態取得と1件あたりの表示規則は`### 投入したWI`と同じとする。予告の分析の再掲は省く。
`### 予告との差分`は予告と異なる結果が1件以上ある場合だけ置き、予告どおりなら省く。既存の未終端AWIへの統合（そのファイル名とH1タイトル）、`condition_not_met`（不成立の条件と根拠）、続行できない理由を返した要求（その理由と、ユーザー確認か保留の扱い）などを短く書く。

## 報告用UWIのフォーマット

報告用UWIは`SKILL.md`「工程」の手順8が定める、自律モードで作業結果と振り返りを1件にまとめる事後承認型UWIである。
冒頭の問いは次の一文とし、`## 選択肢と帰結`は`agent-toolkit:wi-standards`の事後承認型の2択を使う。

```text
<実行日>の<対象リポジトリ名>の作業結果と振り返りについて、この対応で問題ありませんか？
```

`## 判断材料`のH3は次の順序だけで置く。`### 要対応`は常に置き、該当がなければ`- なし`と書く。他のH3は該当する情報があるときだけ置く。対話の報告をそのまま転記せず、1件を1行の要点へまとめ、同じ内容は1つのH3だけへ書く。

1. `### 要対応`: ユーザーが行う操作、回答、判断を`- <対象>: <必要な行動>`とする。操作を求める項目は、その行の下へ`agent-toolkit:wi-standards`の`references/uwi-format.md`の「ユーザーへ操作を依頼する場合」の段落に従う番号付きの手順を置く。別のUWIで手順を示した操作は、そのUWIのファイル名を挙げ、手順を再掲しない。
2. `### 未達・持ち越し`: 元の要求単位の未達、未解決の問題、先送りを`- <対象>: <残った状態>（理由: <理由>、再開条件: <条件>）`とする。再開条件がまだ無い場合はその欄を省く。形式上の完成条件を満たしても、元の要求に未達があれば書く。
3. `### 処理中のご指摘への回答`: `- <指摘・質問>: <回答・対応結果>`とする。
4. `### 曖昧な要求の解釈`: `- <元の要求>: <採用した解釈>（理由: <採用理由と判断根拠>、範囲: <対応範囲>、結果: <実施結果とエンドユーザーが観測する結果>）`とする。
5. `### 自ら確定した判断`: 質問せずに自ら確定した判断のうち、別の合理的な実装者なら異なる判断をし得るものを`- <決定>（理由: <理由>、最有力の対案: <対案>）`とし、ユーザーが異論を持つ可能性が高い順に並べる。
6. `### 成果`: 処理したWIごとに`- <ファイル名>: <H1タイトル>（<達成した結果>）`を1行置く。達成した結果はタイトルと重なる内容を除いて短く書く。公開・リリースなどWI単位へ収まらない成果は1行で添える。
7. `### 振り返り`: 次の行を置く。
   - 確定した問題と対策は、振り返り結果報告の`### 確定した問題と対策`と同じ区分の行（`AWI登録`、`AWI登録済み`、`実装済み`）を1件1行で書く。
   - 見送りは`- 見送り: <件数>件`に続けて`- <問題>: <見送った根拠>`を1件1行とする。
   - 毎回`- 所要時間: <時間または計測できない理由>（目標との差: <差または算出できない理由>）`を1行で示す。
   - 失敗時は`- 振り返り未完了: <理由>`を1行で示す。

作業完了報告の各節は、報告用UWIの次のH3へ載せる。作業完了報告へ節を加える変更と報告用UWIのH3を変える変更では、この対応も同時に改める。

- 冒頭の1文と`### 成果`: `### 成果`。元の要求単位の未達は`### 未達・持ち越し`
- `### 投入したWI`: 回答を求めるUWIは`### 要対応`、先送りしたAWIは`### 未達・持ち越し`、振り返りが投入したAWIは`### 振り返り`
- `### 要対応`: `### 要対応`
- `### 自ら確定した判断`: `### 自ら確定した判断`

完了報告と振り返りは同じ報告用UWIへ記録する。振り返りの結果は、予告を出力した場合も確定した問題と対策、見送った問題とその理由、投入したAWIのファイル名とH1タイトルを記録する。予告の`AWI登録予定`の行は投入結果に応じた`AWI登録`か`AWI登録済み`の行へ置き換え、予告との差分を反映する。
