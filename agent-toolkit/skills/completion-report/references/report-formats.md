# 報告のフォーマット

本書は`agent-toolkit:completion-report`が出力する作業完了報告、振り返り結果報告、AWI投入結果報告と、自律モードで投入する報告用UWIの本文の書式を定める。出力する時点と順序は同スキルの`SKILL.md`「工程」が定める。

## 作業完了報告のフォーマット

`SKILL.md`「工程」の手順5の起動より前に、次の書式で可視の発話本文へ直接書く。振り返りを実行するという予告の行は省き、実施済みの内容を書く（努力目標。未実施の工程を報告へ混ぜないため）。

```text
## 作業完了報告

<依頼者がその依頼で知りたかった答えを1文で>

### 成果

- <元作業に対する成果の全体>

### 投入したWI

- <ファイル名>: <H1タイトル>
- <ファイル名>: <H1タイトル> (target_repo=<...>)
```

`### 成果`へ書く対象は、そのセッションで受け取った依頼（元作業）に対する成果の全体とする。
セッションの途中で生じた別事象への処置は、元作業に対する成果と区別できる形で添える。
同一セッションで`agent-toolkit:completion-report`を2回目以降に起動して報告する場合も、既に報告済みの成果を含めて元作業に対する成果の全体を再構成する。
冒頭の1文と`### 成果`には工程をやり終えたことや作成物の件数より先に、依頼者がその依頼で知りたかった答え（依頼の目的がどこまで達成されたか、または達成される見込みか）を書く。目的が量の変化ならその量、判断を求める依頼ならその判断、不具合の是正なら直ったかどうかが答えに当たり、答えの形は依頼ごとに原文の目的から決める。成果を後続の工程へ委ねる場合は見込みを、見込みを得られない場合はその理由を書き、答えに必要な値を委譲先が持つ場合は委譲プロンプトでその値を返させる。報告の発行に先立って、依頼の原文にある要求単位と`### 成果`の各項目を対応付け、形式上の完成条件を満たしていても要求単位に未達があれば結果と理由を書き、協調モードではその場で伝える。
振り返りが未完了であることを理由に冒頭の答えをぼかさず、元作業で確定した答えを言い切る。

`### 投入したWI`はそのセッションで作業完了報告のテキスト出力前に投入したWI（AWIとUWI、種別は問わない）のうち、報告時点で終端していない項目を対象とする。処理対象として取得した項目と、`adopted`か`rejected`へ終端した項目は対象外とする。終端項目は同じユーザーが回答や終端判断の時点で内容を確認しており、再掲しても新しい判断材料にならないためである。
報告の直前に、そのセッションで投入した全ファイル名を`atk wi show <ファイル名>... --summary-only --target-repo=<対象リポジトリの絶対パス> --skip-pull`へ渡す。
`### <ファイル名> [<状態>]`の見出し行から現在状態を、その次の行からAWIのH1タイトルかUWIの質問本文の先頭行を読む。
照会は対象リポジトリごとに1回へまとめる（努力目標。往復を減らすため）。
0件の場合は`- なし`と書く。1件あたりの表示は`- <ファイル名>: <H1タイトル>`とし、UWIではH1タイトルの位置へ質問本文の先頭行を書く。`target_repo`が現在の対象リポジトリと異なる場合だけ、末尾へ半角空白1字に続けて`(target_repo=<正規化リモートURLか絶対パス>)`を追記する。

ユーザーの操作・回答・判断が必要な場合だけ、前記の書式の末尾へ次の節を加える。

```text
### 要対応

<ユーザーが次に行う具体的な1操作>
```

対応が不要な場合は`### 要対応`を置かない。自律モードの報告用UWIが持つ`要対応`はこの省略規則の対象外とする。
質問せずに自ら確定した判断のうち、別の合理的な実装者なら異なる判断をし得るものがある場合は、`### 成果`の後へ`### 自ら確定した判断`を置き、`agent-toolkit:user-confirmation-and-report`の`references/grilling.md`「終了時報告」の書式で書く。該当が無い場合は置かない。

## 振り返り結果報告のフォーマット

`agent-toolkit:session-review`が正常完了した場合は、次の書式で可視の発話本文へ直接書く。

```text
## 振り返り結果報告

- 候補: <N>件 (<候補種別> <件数>件 / ...)
- 所要時間: <秒数>秒 (準備時点)
- 改善見込み: <案の合計短縮見込み、改善後の全体所要時間、目標値との差、超過時の律速区間。時間改善案が無い場合は「なし」>

### 確定した問題と対策

- <問題>: <対策>（<投入したAWIのファイル名>: <H1タイトル>）
- <問題>: <対策>（投入予定: <H1タイトル>）
- <問題>: <対策>（同一セッションで実装済み: <commitの短縮OIDまたは変更した成果物>）

### 対策を見送った問題

- 判定済み: <問題>; 根拠: <対策不要と確定した観測>
- 未確定: <問題>; 照会: <試行と結果>; 再現: <試行と結果または不能の具体的理由>; 残る理由: <確定できない理由>
- なし
```

`### 確定した問題と対策`には原因と対策を確定した問題ごとに、問題と対策を1行で書く。対策として投入したAWIのファイル名とH1タイトルを添える。`agent-toolkit:session-review`の工程5が投入の前に出力する予告では、ファイル名が未確定であるため`（投入予定: <H1タイトル>）`を添える。同じセッションで実装した場合は、対策のcommitの短縮OIDか変更した成果物を添える。複数の問題を1件のAWIで覆う場合は、それぞれの行へ同じAWIを書く。既存の未終端項目が対策を覆う場合は、そのファイル名とH1タイトルを書く。同じセッションで実装した対策はこの節へ書く。`### 対策を見送った問題`には実装を見送った候補を記す。
`### 対策を見送った問題`には候補一覧と会話の流れで見つけた問題のうち対策を見送ったものを、前掲の固定形式で書く。除外、欠陥ではないとの判断、再発防止策なしの判断のいずれの場合も理由を示す。除外したユーザー介入は除外区分を根拠へ含める。原因または対策が未確定なら、照会、再現と残る理由を全て書く。`判定済み`の根拠には確認済みの観測を書く。欠陥ではないとの判定、原因が未確定、分析した後に処置を採用しない判断のどれに当たるかが根拠から読み取れるように書く。Stopが判定するのは`SKILL.md`「工程」の報告本文の判定までで、証拠の実在、原因との対応と案の採否はメインが確かめる。見送ってよい条件は`agent-toolkit:session-review`の`references/analysis.md`「入力と照会」「一次選別」「原因と対策」に従う。
いずれのH3も該当が無い場合は`- なし`とする。報告直前の状態取得と1件あたりの表示規則は`### 投入したWI`と同じとする。

振り返りが未実施または失敗の場合は、次の書式で可視の発話本文へ直接書く。

```text
## 振り返り結果報告

### 振り返り

- session-review未実施: <理由。関連するUWIがある場合はファイル名を末尾に併記>
```

未実施の理由は2種に分類する。既に振り返りを実施した成果が、そのセッションの記録の終端まで覆っている場合は`成果を再利用したため起動省略`とする。`atk run-script session-review-prepare`が再実行後も失敗した場合は`分析失敗のため欠陥AWIへ記録`とする。後者でも元依頼のうち認可済みで技術的に実行可能な工程を継続する。

正常完了の2つのH3と、未実施または失敗の`### 振り返り`は同じ振り返り結果報告へ併記しない。

要約行の値の取得元は`atk run-script session-review-prepare`の1行JSONとする。

- `候補`は`candidate_total`と`candidate_counts`の種別ごとの件数（`atk run-script session-review-evidence`の除外後）とする。0件の場合は`0件`だけを書く
- `所要時間`は`elapsed_seconds`とし、セッションの最初の記録から準備時点までの値であることを括弧書きで示す。セッション全体の所要時間と目標の比較は、振り返りの所要時間の分析が行う
- `改善見込み`は時間改善案の最終値を集計し、合計短縮見込み、改善後の所要時間、目標値との差を1か所で示す。超過する場合は律速区間も示す。各AWIにはその案固有の値だけを書く

## AWI投入結果報告のフォーマット

振り返りが対策のAWIを1件以上投入した場合は、予告の後の最終報告を次の書式で可視の発話本文へ直接書く。

```text
## AWI投入結果報告

<1文。予告どおり投入を完了した旨、または予告と異なる結果があった旨>

### 投入したAWI

- <ファイル名>: <H1タイトル>
- <ファイル名>: <H1タイトル> (target_repo=<...>)

### 予告との差分

- <予告した対策>: <実際の結果>
```

`### 投入したAWI`には新たに投入したAWIを書き、0件なら`- なし`とする。報告直前の状態取得と1件あたりの表示規則は`### 投入したWI`と同じとする。
`### 予告との差分`は予告と異なる結果が1件以上ある場合だけ置き、予告どおりなら置かない。既存の未終端AWIへの統合（そのファイル名とH1タイトル）、`condition_not_met`（不成立の条件と根拠）、続行できない理由を返した要求（その理由と、ユーザー確認か保留の扱い）などを書く。

## 報告用UWIのフォーマット

報告用UWIは`SKILL.md`「工程」の手順8が定める、自律モードで作業結果と振り返りを1件にまとめる事後承認型UWIである。
冒頭の問いは次の一文とし、`## 選択肢と帰結`は`agent-toolkit:wi-standards`の事後承認型の2択を使う。

```text
<実行日>の<対象リポジトリ名>の作業結果と振り返りについて、この対応で問題ありませんか？
```

`## 判断材料`のH3は次の順序だけで置く。`### 要対応`は常に置き、該当がなければ`- なし`と書く。他のH3は該当する情報があるときだけ置く。対話の報告をそのまま転記せず、一件を一行へまとめる。

1. `### 要対応`: ユーザーが行う操作、回答、判断を`- <対象>: <必要な行動>`とする。
2. `### 未達・持ち越し`: 元の要求単位の未達、未解決の問題、先送りを`- <対象>: <残った状態>（理由: <理由>、再開条件: <条件>）`とする。再開条件がまだ無い場合はその欄を省く。形式上の完成条件を満たしても、元の要求に未達があれば書く。
3. `### 処理中のご指摘への回答`: `- <指摘・質問>: <回答・対応結果>`とする。
4. `### 曖昧な要求の解釈`: `- <元の要求>: <採用した解釈>（理由: <採用理由と判断根拠>、範囲: <対応範囲>、結果: <実施結果とエンドユーザーが観測する結果>）`とする。
5. `### 成果`: 処理したWIごとに`- <ファイル名>: <H1タイトル>（<達成した結果>）`を一行置く。公開・リリースなどWI単位へ収まらない成果は一行で添える。
6. `### 振り返り`: 次の行を置く。
   - 投入したAWIは`- 投入: <ファイル名>: <H1タイトル>`を一件一行とし、タイトルから問題と対策を読み取れないときだけ要旨を添える。
   - 既存項目で対処済みの問題と同じセッションで対処した問題は`- 対策: <問題>: <対策>（<既存AWIまたは実装成果>）`を一件一行とする。
   - 見送りは`- 見送り: <件数>件`に続けて`- <問題>: <見送った根拠>`を一件一行とする。
   - 毎回`- 所要時間: <時間または計測できない理由>（目標との差: <差または算出できない理由>）`を一行で示す。
   - 失敗時は`- 振り返り未完了: <理由>`を一行で示す。

完了報告と振り返りは同じ報告用UWIへ記録する。振り返りの結果は、予告を出力した場合も確定した問題と対策、見送った問題とその理由、投入したAWIのファイル名とH1タイトルを記録する。予告の`（投入予定: <H1タイトル>）`は投入結果のファイル名とH1タイトルへ置き換え、予告との差分を反映する。
