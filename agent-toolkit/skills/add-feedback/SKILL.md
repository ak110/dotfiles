# フィードバック投入

フィードバック投入の共通契約を定める。処理、採否、実装、計画作成は担当しない。

## 入力経路

- 完成済み本文を受け取った場合は、本文の選択肢や要求を問い直さず非対話経路へ進む。
  呼出元は本文、対象リポジトリ、種別、source、plan file、依存関係のうち該当する値を渡す
- 通常型フィードバックの主題だけを受け取った場合は、未確定の利用者向け結果を現在の対話で確認する。
  技術調査や明文化済み方針で確定できる事項は自ら確定し、内部実装の判断は本文へ固定しない
- 自律経路で利用者の回答が必要な場合は、未完成本文を投入せず、
  `process-feedbacks/references/hold-with-tbd-inject.md`に従ってTBDだけを投入する

## 共通投入手順

1. 各本文を単体で意味が完結する形にし、対象、観測事象、期待する結果、出典、関連提案との関係を含める
2. `git -C <repo-path> remote get-url origin`で対象リポジトリを確認し、
   `target_repo`へパス名ではなく確認したリモートURLを記録する
3. `atk mq list --status=active --target-repo=<repo-path>`で主題の重複を確認する。
   重複時は`atk mq show <filename>`で既存本文を取得し、差分情報を統合して
   `atk mq edit <filename> <統合後本文>`で更新する
4. 他リポジトリの改訂に追従する提案では、直近の履歴と反映先の現行内容から実装済みでないことを確認する。
   実装済みなら投入せず、確認結果を報告する。新規の不具合報告と機能提案は本確認の対象外とする
5. 対象リポジトリをプロセスの作業ディレクトリに指定して`atk mq add`を実行する。
   本文は`$'...'`のANSI-Cクォートで単一引数として渡す。
   ヒアドキュメント、パイプ、リダイレクト、コマンド置換、言語別文字列リテラルの連結は用いない
6. 種別、scope、question type、choices、plan file、依存関係、source、target repoは
   `atk mq add --help`が定める専用オプションで指定する。
   計画実装型は`--plan-file <絶対パス> --source plan`を指定し、通常型では`--plan-file`を指定しない
7. 完了表示で保存後の`target_repo`、`target_commit`、`plan_file`、`depends_on`を照合する。
   続けて`atk mq show <filename>`でmetadataと本文を再取得し、入力と一致することを確認する

`atk mq add`または`atk mq edit`が警告やエラーを出力した場合は、終了コード0でも保存内容を再取得する。
欠落を検出した場合は同じ経路で修復し、専用更新経路のないmetadataが一致しない場合は処理を止めて報告する。

## 完成条件

- 利用者向け結果に影響する未確定事項が通常型本文へ残っていない
- 対象リポジトリ、重複、必要な実装済み判定を確認している
- 種別とmetadataが呼出元の入力に一致している
- 保存後に取得した本文が完成済み本文と一致している
