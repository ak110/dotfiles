# フィードバック投入

本スキルは、フィードバックまたはTBDを投入する手順を提供する。

## 入力

- 完成済み本文は問い直さず、本文、対象リポジトリ、種別、source、plan file、依存関係を受け取る
- 完成済みの通常型本文では、投入元が同じ対象と技術主張について完了した調査の証拠を持つ場合に受け取る。
  証拠には計画、調査結果、実行結果を含み、再利用できない範囲の調査は本スキルが担う
- 計画実装型では、投入元が計画作成に使ったworktreeの絶対パスと計画base commitを受け取る。
  計画ファイルに記録された`agent-toolkit:plan-mode`の調査成果を証拠として再利用する。
  リポジトリ本体や別worktreeへ解決し直さず、同じ絶対パスを作業ディレクトリと対象リポジトリ引数へ渡す
- 通常型でも対象の正確なローカルworktreeが既知なら、その絶対パスを`atk mq add --target-repo`へ渡し、
  CLIに正規の対象リポジトリと作成時点のHEAD完全OIDを同時に確定させる。
  worktreeを推測せず、利用できるローカルworktreeがない場合だけURLを渡す
- 通常型の主題だけを受け取った場合は、本スキルが調査を担い、利用者向け結果を現在の対話で確定する
- 計画実装型では、計画へ吸収してrejectedへ移した元項目のファイル名を投入元から受け取る

## 手順

1. 全投入で`references/coordination-preflight.md`を全文読む。
   複数リポジトリの場合だけ
   `references/cross-repository-submission.md`も全文読む
2. 通常型は、適用規範、対象全文、定義・参照・呼び出し元、関連テスト、生成・配布経路、履歴から、
   技術主張に該当する証拠集合を調査する。
   完成済み本文は投入元の証拠を同じ対象と主張へ照合し、不足する範囲だけ同じ証拠集合を調査する。
   技術主張は実装、実行結果、公式一次資料のいずれかで裏付ける。
   技術的未確定が残る間は保存せず、利用者依存事項はモード別確認又はTBDへ分離する
3. 本文の起草前に`agent-toolkit:writing-standards`をSkill機能で起動する。
   本文冒頭に、何をどう変えるかの結論（提案・依頼・確認事項）を1〜3文で置き、
   観測事象・裏付け・代替案などの詳細は結論の後へ簡潔に置く。
   簡潔化は表現の圧縮で行い、採否を左右する判断材料（代替案・費用・副作用・重複判定など）の削除で行わない
4. 各本文を単体で意味が完結する形にし、対象、観測事象、期待結果、出典、関連提案との関係を含める
   投入後に変化する自己言及的な値（レビューのラウンド数、収束状態、素材件数）は本文へ書かず、計画ファイルの該当節へ委ねる
5. 保存直前にactive一覧を再取得して同期を所有し、同じ確認で関連項目を読む場合だけ、必要なファイル名を
   1回の`atk mq show <filename>... --target-repo=<repo-path> --skip-pull`で再取得する。
   別操作、時間を空けた確認、この手順をやり直す際のactive一覧取得では同期を省略しない。
   事前確認の判断表を再適用して処置を確定し、競合で拒否された場合も同様に再取得して再適用する
6. 新規項目は`atk mq add`で保存し、計画実装型は吸収元のファイル名を本文へ記録する
7. 完了表示のファイル名、`target_repo`、`target_commit`、`plan_file`、`depends_on`を入力と照合する。
   警告又はエラーが出た場合だけ、終了コード0でも`atk mq show <filename> --target-repo=<repo-path>`で
   保存内容を再取得し、欠落を同じ経路で修復する

本文へ引用符・改行を含む場合は、本文をファイルへ保存し`atk mq add --body-file <path>`で渡す
（複数回指定可。位置引数との併用は拒否される）。

`atk config show`が出力する`private_notes`配下の`inbox/`又は`processing/`にあるキュー管理ファイルを
専用サブコマンド以外で変更した場合は、作業を終える前に`atk mq commit`を実行する。

## セッション主タスクとしての完了報告

利用者が本スキルを直接起動し、投入がセッションの主タスクである場合は、手順6の照合後に次の構成で完了報告を提示する。
他スキルから呼び出された場合は呼び出し元の報告形式に従い、本節を適用しない。
完了報告のメッセージはこの構成だけとし、枠の前後へ地の文を加えない。
`## 振り返り`節は書かない（session-review完了後の最終報告だけが置く）。

```text
<冒頭1文: 投入完了の言い切り>

## 成果

- 投入フィードバック: `<ファイル名>`（<種別>、対象: `<target_repoの値>`）
- タイトル: <本文H1の見出し文（H1が無い場合は本文冒頭の要点1行）>
- 要旨: <本文の要点1、2行>
- 依存: `<depends_onの値>`（無い場合は`なし`）
```

複数件を投入した場合は`## 成果`の項目一式をファイルごとに繰り返す。
本文の全文は転記しない（コードフェンス転記は見出しがレンダリングされず、モバイルで横スクロールになるため）。
全文は`atk mq show <ファイル名> --target-repo=<対象リポジトリ>`又はビューアーで確認する。

## TBD本文の必須要素

全TBDは、回答者が回答対象を識別できる問いを疑問文で1文以上含める。
`--question-type=choice`では選択肢の提示を問いとして扱う。
全TBDは本文だけで判断できるよう、対象、背景及び判断根拠を含める。
回答者が選ぶ問い・選択肢を本文冒頭へ置き、背景・経緯・原因分析は問いの後へ簡潔に置く。
簡潔化は表現の圧縮で行い、判断に必要な情報（対象、背景、判断根拠、選択肢の影響）の削除で行わない。
キュー項目IDや計画ファイル名などの識別子は、対象との関係を示す文脈語とともに用い、識別子の列挙で文脈を代替しない。

`atk mq add --type=tbd`へ渡す本文は質問本文だけとし、ツールが自動付与する`## 質問`見出し、
`## 回答`以降及び回答欄マーカーを本文へ含めない（厳守規定。含めると投入が拒否される）。
既存TBDの表示出力や過去のTBDファイルを起草の起点にする場合は、当該見出しと回答欄を除去してから渡す
（質問本文内の`## 回答方法`節は保持する）。
拒否対象は、前後の空白を除いた行全体が`## 質問`又は`## 回答`と一致する行であり、行中での言及は許容される。

TBDで外部環境の実機確認を回答者へ依頼する場合は、本文だけで確認と回答を完了できる
自己完結した記述とし、次の要素を含める（厳守規定）。

- 対象環境・事前条件・回答者が行う番号付き操作
- 画面またはコマンドの確認場所と取得する値
- 別ファイルの参照だけに委ねず、本文へ直接記載した期待値
- 回答欄へ貼り付ける最小の返信形式と、確認できない場合に記載する内容

TBDで複数項目の判断を回答者へ求める場合は、次の要素を含める（厳守規定）。

- 変更を伴う選択肢は、変更前後が分かるdiff形式または削除・追加対象の全文で示す
- 各項目に、採用と不採用の影響を利用者に伝わる語彙で1文ずつ示す
- 起票者の推奨と根拠を項目ごとに1行で示す
- 項目が4件以上の場合は、共通する判断基準で群にまとめ、群単位の一括回答を許容する

## 完成条件

- 利用者向け結果に影響する未確定事項が通常型本文へ残っていない
- 通常型は入力形態を問わず、本文の技術主張を実装、実行結果又は公式一次資料で裏付け、
  該当する証拠集合の調査を完了している
- 技術的未確定が通常型本文へ残っていない
- 保存直前のactive状態に基づいて新規、終端、追随、依存、追加無しを確定している
- 完了表示のファイル名、`target_repo`、`target_commit`、`plan_file`、`depends_on`が入力と一致し、
  投入時のエラーを解消済みで、警告があれば再取得により保存内容に欠落が無いことを確認済みで、
  processing項目を変更していない
