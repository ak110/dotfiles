# AWIの起草・保存と指摘への対応

本書は`../SKILL.md`の手順3・4、指摘の分類とセッション境界を定める。
手順番号は同スキルと共通とする。

## 起草と保存

<!-- markdownlint-disable MD029 -->

3. wi-standardsにおける要求の同一性基準に基づいて独立した要求を分割する。
   件数の多寡にかかわらず、メインエージェント自身が調査、対策の確定、起草、検収、および保存までを一貫して担当することを原則とする。
   - バグ対応では投入元が原因分析、類似調査と分類、独立別件の具体化・登録、再発防止方針の選定を登録前に終える。
     実行側は確定した修正と再発防止策を実装し、有効性を検証する。
   - `../../wi-standards/references/wi-standards-body.md`「起票目的別の調査出口」に従って確定した内容をAWI本文に記載する。
     変更を使うためにエンドユーザー側の操作が必要なら、`../../wi-standards/references/awi-body-content.md`「要求固有性と記載量」に従い、エンドユーザー向け公開後の設定実施と専用案内UWIも反映内容へ含める。
   - ユーザーの原文、情報の出所、確定した要件、および技術的な判断を明確に区別し、取得済みの証拠を再利用する。
     複数の要求を混同せずに個別管理し、同一要求の更新は同じ作成主体が現在の要件と差分情報に基づいて行う。
   - 登録する要求がない場合も、採否を左右する論点の検討を終え、採用・既存充足・不採用と根拠を既存の調査記録で確かめてから手順4へ進む。
     資料起点の依頼では、資料の主張ごとに既存の定義元、現状の機能・契約の被覆、同じ利用条件で同じ結果を得られる根拠（実装・受け手の利用結果）、表現・構成の改善余地、改善案の採否と理由を別欄で対応付けた表を既存の作業記録へ残してから結論を出す。
     被覆を最終採否とせず、書き換え・統合・削除・実装改善を比較する。
     資料の項目を候補の上限にせず、方針として採否を伝える時点で比較を対応付け、未確認は調査中と伝える。
     必要条件を保った改善に便益がなければ無変更を選ぶ。
     コード改善では、作り込みと見逃しの判断、適用した規範・参照経路、実装構造を対応付け、既存bugfix基準で条文の不足・未適用・誤解を招く条件や例示・レビュー保証範囲の取り違えを判定する。
     観測した因果と改善の技術判断を分け、原因に作用する改訂を同じ要求か独立要求へ接続する。
     全てを規範の不在に帰属させたり、同じ条文を重ねたりしない。
     選好を要する不採用は、手順2の質問でユーザーの回答を得てから確定する。
     未調査で案がない状態と、根拠の薄い候補だけを撤回した状態は、原要求の残る検討へ戻る。
     ユーザーの訂正で候補を撤回した場合も同じように判定する。
   - 本来の作業に付随する別件の登録など、作業の文脈を分ける明確な理由がある場合は、`add-wi.parent.md`に従って委譲を選択する。
     判断基準が明確な大量の走査処理には軽量な読み取り探索を利用してよく、起草と保存の最終責任はメインエージェントが保持する。
   - 原稿確定前、登録0件で終える前、候補を不採用にする前に`omission-check.md`の全類型を再点検し、原文・原稿・調査根拠との対応と処置を更新する。
   - 検収の構成は`../../wi-standards/references/drafting-workflow-review-route.md`「直接起草と独立した検収の選択」に従う。
     原文と反映内容を読み比べて構造を確認し、`../../wi-standards/references/draft-semantic-review.md`に基づいて文脈を再確認する。
     本スキルでは4条件への該当にかかわらず毎回投入前レビューする。
     同時に準備した原稿、要求内容、出所、証拠を要求識別子で紐付けて`${CLAUDE_PLUGIN_ROOT}/share/wi-draft-review.parent.md`へ一括して引き渡し、作成主体がレビュー指摘の採否を確定した上で保存する。
     `要求と出所`には起動したリポジトリ（起動時のcwdが属するリポジトリ）を、`成立性の証拠`には対象リポジトリの選定結果（起動したリポジトリの採否と理由、派生して見直したリポジトリ）を含める。
   - ユーザー自身しか決定できない未確定事項のみを手順2の質問に戻す。
     委譲した調査に不足がある場合は元の調査担当へ差し戻す。
4. `atk wi submission end --findings-file <指摘対応記録の絶対パス>`に投入前レビューの返却ファイルを`--review-result`で添えて実行する。
   検査が不足を示したら記録を補って再実行し、成功すると投入作業のセッション記録が削除される。
   成功後は、作業完了報告を書く前に`agent-toolkit:report-completion`を起動し、投入成功の要約を別の最終応答にせず、同スキルが定める終了処理まで終える。
   表示された報告用要約と、出力された`ファイル名`、登録・再利用の結果、検収結果、未達事項を同スキルの作業完了報告へ集約して送達する。
   依頼から自明な後続の実行工程の説明は省き、結果と必要な判断材料を伝える。
   同期の振り返りは起動しない。

## 指摘の分類と処置

質問には現在の検討状況と根拠を先に回答し、停止・変更・撤回を明示した原文がある部分だけを要求変更へ取り込む。
質問だけなら現行要求と作業契約を保持して元工程へ戻る。
過去判断を問われた場合は方針要約に加え元の質問・全選択肢・実際の回答を取得し、一括採用を個別比較・選択の事実へ置き換えず説明する。

ユーザーからの指摘・追加発話と、独立した方針検収・本文検収の指摘は、受領した時点で次の手順を行う。
修正・再評価・再確認へは、分類と処置を終えてから進む。
作業中・完了後の追加発話と従来の`direct`指定を含む全経路に適用する。
報告や結論への異議は、質問への回答と明示変更の判定を終えてから指摘として分類し、`agent-basics:bugfix`の起動を候補の再評価・修正・確認より先に行う。

1. 要求単位への分解（確定済みの範囲を勝手に縮小しない）: 受領した発話は、文章の書き方に対する指示や行動の是正も含めて要求単位に分解する。
   単位ごとに、`agent-toolkit:wi-standards`冒頭の要求の同一性基準に基づいて、既存・起草中のAWIへ合流させるか独立した要求として扱うかを判定する。
   同一ファイル、同一節、同一文章に対する部分的な重複は、編集上の競合として扱う。
   発話の一部が既存AWIの更新に該当する場合でも、残りの要求単位は個別に判定する。
   合流させる要求単位は確定済みの作業範囲と比較し、ユーザー発話が範囲の一部のみに言及している場合であっても、確定済みの作業範囲を勝手に縮小しない。
   明示的に範囲の縮小が指示された場合や意図が曖昧な場合は、現在の範囲を`共通前提`として明示して確認する。
2. 分類（処置の種類を決める）: 要求単位ごとに次のいずれかへ分類する。
   追加要求という要求管理上の扱いは、この分類の代わりにしない。
   - 考慮漏れ: 原文、取得済みの調査結果、現物、適用中の規範から導けたのに方針へ反映しなかったもの。
     手順4で処置する。
   - ユーザーだけが持つ新しい情報: 選好、未開示の制約など、登録前の調査では導けなかったもの。
     要件として反映する。
   - 前提の誤り: 指摘の技術的前提が現物と一致しないもの。
     根拠と代替案を示す。
   - 採用しない提案: 検討の結果採らない提案。
     根拠を示す。
3. 介入評価（ユーザーの手を煩わせた原因を見逃さない）: 分類とは別に、既存判断を是正した介入を`../../user-confirmation-and-report/references/analysis-operations-intervention.md`「ユーザー介入と確認の判定」で評価する。
   同じ要求単位が以後の同種作業にも適用する方針の候補を含むかは、`../../user-confirmation-and-report/references/user-utterance-incorporation.md`「原文の保持と取り込み」で今回の原稿への反映と分けて判定する。
4. 考慮漏れの処置（同じ仕組みの漏れを防ぐ）: `agent-basics:bugfix`を起動して原因を分析し、同じ仕組みで漏れうる観点を全方針で見直す。
   再発防止策を検討してから方針へ反映する。
   再発防止策は本スキルの成果物制限に従い、`## 原因分析`付きの別AWIとして起草し、元のAWIと一緒に登録する。
   投入先は対策の対象を所有するリポジトリとする。
   投入先が元の投入先と異なる場合は、手順2の5に従い、全投入先を指定して`atk wi submission begin`を再実行する。
   確認の往復中も投入作業のセッション記録を維持する。
5. 反映と再確認（新しい判断が必要な点だけを確認する）: 考慮漏れの処置後に方針を再確認する場合も、論点ごとに確認要否を判定する。
   判定は`../../user-confirmation-and-report/references/user-confirmation-and-report-decisions.md`「確認要否の判定」に従う。
   既存の方針や技術とQCDで決まる論点は自ら確定して報告し、選好を要する論点だけを確認する。
6. 記録（確認経緯と再発防止策を追跡できるようにする）: 受領した実ユーザー発話（自由記述を含む確認回答を含み、提示した選択肢をそのまま選んだ回答を除く）と投入前レビューの指摘ごとに、指摘対応記録へ項目を残す。
   指摘でない依頼・回答には理由を残す。
   指摘には前述の分類、分類根拠、採否、処置結果を残し、考慮漏れには原因分析と再発防止策の採否・引渡し先も残す。
   再発防止策を採用しない場合も両系統の候補・費用比較・残存リスクを原因分析へ残し、既存のレビューで回収したことだけを不採用の理由にしない。
   記録の形式は`atk wi submission end --help`に従う。
   考慮漏れか新しい情報かの判断と処置の十分性はメインと投入前レビューが検収し、`end`は対応と必須欄の欠落だけを検査する。
7. 戻り先: 質問ラウンド中は手順2の2、原稿の確定・検収中は手順3の再点検、完了報告後は手順2の1から再開し、独立した要求は手順3の担当選定に戻す。

本文検収の指摘では、指摘ごとの分類、採否、考慮漏れへの処置結果と登録予定の別AWIを示し、完了報告には確定した判断結果を再利用する。
作業完了報告には、ユーザーが確認経緯と再発防止策を追跡できるよう、`atk wi submission end`が表示した報告用要約（確認の往復回数、指摘ごとの分類、再発防止策の採否と登録先）を省略せず記載する。
Claude Codeでは、要約の行が最終応答に無い場合にStop hookが再報告を求める。

## セッション境界

成果物をAWIの登録と更新に限定する契約には、`../../user-confirmation-and-report/references/user-utterance-correction.md`「成果物の制限」を適用する。

ユーザーによる中止や依頼の取り下げで投入作業を中止する場合は、保存せずに必ず`atk wi submission end --abort`を実行する。
完了後に追加の発話を受けて投入を再開する場合は、投入先リポジトリの確定時に手順2の5の記録処理を再度行い、再開した投入が完了した際は手順4、再度中止となった際は`--abort`で`atk wi submission end`を実行する。
既存AWIの更新と判断した場合は、調査に着手する前に手順1の保留処理を適用し、手順3の同一作成主体が、現行の本文、確定した変更内容、および原文テキストを対象の`ファイル名`に紐付けて更新する。
スキル起動後に届く「反映して」「修正して」という指示や、再発防止・作業完遂の要求は、すべてAWI本文への反映指示として取り扱う。
成果物制限の例外として許可される操作は次のものに限る。
登録用の一時入力ファイルの作成、作成した一時ディレクトリの`rm -r -- <作成した絶対パス>`による後始末、対象リポジトリの規範が同一工程内で求めている追跡用ファイルへの記載である。
また、完成条件や採否判定に用いる測定処理と測定のための可逆な一時変更（`measurement.md`）も含まれる。

対象リポジトリの外部に対する操作の依頼範囲、認可の有無、確認要否は、`agent-toolkit/share/rules/common/01-agent.md`「完遂と先送り」に従う。
あわせて次の資料にも従う。

- `../../user-confirmation-and-report/references/user-confirmation-and-report-decisions.md`「確認要否の判定」
- `../../user-confirmation-and-report/references/approval-scope.md`
委譲する場合は、起動するスキル名、対象リポジトリ内の恒久変更をAWIに限定する制限範囲、対象外となる通常の判断基準、セッション終了条件を委譲プロンプトに明記する。
