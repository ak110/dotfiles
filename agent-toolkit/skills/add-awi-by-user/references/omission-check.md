# WI保存前の考慮漏れ点検

WI起草者と投入前レビュー担当が、原文・原稿・調査根拠から考慮漏れを探すための資料である。
起草の方針（対象・範囲・採否・手段）を決める前、質問ラウンドを終える前、原稿確定前、登録0件で終える前、候補を不採用にする前に、次の全類型を点検する。
最初の時点は、方針をどう伝えるかによらず、方針を決める判断の前である。
推奨案や選択肢を提示する場合、確認を経ずに起草へ進むと決める場合、自分で決めた方針をユーザーへ伝える場合（「〜するAWIを起草する」と予告する途中報告を含む）、方針を伝える工程を持たない起草の流れ（プロジェクト固有のWI作成スキルを含む）は、いずれもこの時点に当たる。
選択肢を提示する前は、過去の判断との関係(c)と継続費用を含む過剰さ(d)を、推奨しない案を含む提示する全ての案と、推奨の結果として登録しないことになる候補へ適用する（推奨案が「登録しない」の場合を含む）。
自分で決めた方針にも全類型を適用し、とくに範囲の限定(a)、既存の仕組み・過去の判断との関係(c)、過剰さ(d)を確かめてから伝える。
再発した考慮漏れの予防は、該当する類型をこの資料へ統合して次の点検へ戻す。

## 点検類型

| 類型 | 比べる内容 |
| --- | --- |
| (a) 範囲の限定 | 対象・調査母集団・完成条件を原文の範囲表現と比較し、例示・理由・観測した症状・現行の仕組みで扱える範囲への縮小がないか。対象外・不採用とした判断の前提（利用主体、環境、利用場面）が観測した事実か、確かめていない想定か |
| (b) 関連して必要な変更 | 共通化・リファクタリング、同じ機構を使う他の箇所、追随修正、同時に直すべき既存不良が含まれるか。エージェント向け文書の変更は`agent-toolkit:wi-standards/references/drafting-workflow-writing.md`「エージェント向け文書の構成」に従ったか |
| (c) 既存の仕組み・過去の判断との関係 | 同じ目的の既存機構、対象プロジェクトの方針記録・過去のユーザー指示、回答済みUWI、他AWIとの重複・衝突がないか |
| (d) 過剰さ | 読み手が常識で判断できる細則、過剰な制限・仕組みがないか、より単純な構成案と比較したか。推奨しない案と不採用にする候補は、`agent-basics:writing-standards/references/design-heuristics-proportionality.md`「問題と手段の比例性」に従い、既存要素の再利用・統合・削除を使う構造の異なる案と比べたか。案の目的を満たす構成を対象リポジトリの既存の部品（稼働中の主体、既存の通信経路、既存のコマンドなど）から組める場合に、その構成の費用と便益で評価したか |
| (e) 後続工程の模擬 | process-wiの計画・実装・完成条件の検証・公開・終了までをたどり、検証の認可・費用・第三者が観測する操作・実環境の対象、目標値未達時の扱い、実装詳細で分かれる外部挙動、公開範囲にユーザー判断が残らないか |
| (f) 既存充足の過大判定 | 目的や名前が似た規定・機構があるだけで既存充足としていないか。同じ利用条件で同じ結果を得られる根拠と、判断の時点で本文が届く経路（`agent-basics:writing-standards/references/agent-documents-basics-ownership.md`「既存規範による被覆の判定」）を確かめたか。実効性は送り手の入力や設定だけで代替せず、受け手（委譲先、エンドユーザー、後続工程など）が実際に受け取る、自動付加を含む入力・画面・出力で確かめたか |
| (g) 選好を要する不採用の未確認 | 不採用の理由がユーザーの選好で決まるトレードオフを含むのに、確認せずに確定していないか |
| (h) 技術判断の過剰な確認 | 既存の方針や技術とQCDで決まる事項を確認に回していないか。結果を変える自己判断は(k)で点検する |
| (i) 対象リポジトリの選定 | 起動したリポジトリを対象として資料と突き合わせたか、関係を成果物での主題の扱いで判定したか、他リポジトリの見直しを派生として行い起動したリポジトリの採否と理由を記録したか |
| (j) エンドユーザーが観測する仕様と作業 | 公開コマンドの体系・名前、設定の名前・デフォルト値、指定がない場合の動作、保護の強さと許容する残存リスク、作業の担い手を、未確定の選好があるまま技術判断として決めていないか。既存の保護の変更・撤去には`../../wi-standards/references/drafting-completion-policies.md`「方針と判断の記録との比較」の保護の扱いと確認要否の定義元を適用し、(h)(k)も同じ判定へ通したか。エージェントが実施できる作業は、エージェントが行う案を推奨し、選択肢の初期選択にしたか |
| (k) 観測結果を変える自己判断の未確認 | 自ら確定した判断を、終了時報告へ書く予定のものと原稿の「技術判断」の注記も含め全件列挙したか。表示箇所・条件・文言、今後の同種対象への適用、既存運用の費用・頻度・対象への副作用、追加した関連変更の範囲など、ユーザーやエンドユーザーが観測する結果を変える判断ごとに、原要求・既存判断・技術とQCDで確定する根拠があるか、本人固有の未確定値が残るかを、確認要否の定義元で判定したか。未確定の結果側の選好を技術手段として自己確定せず、確認へ回したか。追加発話で要求が増えた場合も派生する判断を列挙し直したか |

## 資料起点の比較

以下の比較は`../SKILL.md`の主張別の既存対応表へまとめる。
現状の機能・契約の被覆、受け手側での実効性、表現・構成の改善余地、改善案の採否を分けて比較する。
意味が一致していても、説明順序・具体性・重複の統合で同じ利用場面の理解と判断を改善できないかを(d)(f)で点検する。
短さだけで置換せず、条件・適用範囲・例外・拘束力・認可・判断に必要な理由を保つ文章品質と規範縮小の共通基準を適用する。
未確認の観点は調査中として残し、改善不要へ変換しない。

外部成果物は公式manifest、公開パッケージ・ソース、評価、更新・プライバシー仕様から提供機能を確定し、対象側の単独利用・併用・配布環境・ホスト・OS・modeと未導入・無効化・更新失敗を含む消費形態を既存の調査記録へ対応付ける。
そのまま利用、知見の統合、併用、不採用の4方式を品質効果と継続費用で比較し、方針予告前、質問ラウンド終了時、原稿確定前に未対応を補う。
機能の存在と、発見しやすさ・操作場所・手数・情報から判断と実行への接続は別に評価する。
参考依頼の目的を保ち、既存機能の接続・統合も候補に含め、技術判断で決まる導入可否は起草者が確定する。
資料起点では、機能と消費形態の対応記録を(a)(d)(f)(h)へ適用する。
既存機能の有無だけで充足とせず、現在と改善後の操作手順、便益、4方式の品質効果と継続費用を比較する。
対象側が提供・支援する利用条件から、例示外のホスト・OS・modeや未導入・無効化・更新失敗も比較対象へ含め、採用ありの場合も方針予告前に未評価を補う。
提供範囲外は根拠付きで非該当とし、その環境への対応追加を要求しない。

## 処置と終了時報告

各類型の該当論点を、調査で確定する、この場でユーザーへ確認する、ユーザーの回答・事前認可・未達時の扱いをAWI本文へ記録する、の必要な処置へつなげる。
非該当の場合も点検結果として示し、技術とQCDで確定できる判断は起草者が確定する。
処理時に初めて判明する事項だけを理由付きで残す。
完了条件・外部挙動・対象範囲・除外条件は、前提が成立しない場合や環境・状態が異なる場合にも目的を適用して点検し、登録時点で分かる本人の判断を同じ質問ラウンドで確認する。
登録時点で確認できる曖昧さを残すと、後続の自律処理が回答待ちで停止するためである。
ユーザーが確認経緯と残る前提を判断できるよう、質問ラウンドの終了時報告に全類型の点検結果と処置の一覧を示す。
原稿確定前の再点検で新しいユーザー判断が見つかったら同じセッションで質問へ戻る。
この報告による保存前の一律承認は求めず、既存の投入前レビューに合格して保存へ進む。
