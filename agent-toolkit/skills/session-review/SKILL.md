# セッション振り返り

最上位セッションのメインエージェントだけが本スキルを起動する。
別のエージェントからタスクを受領した実行主体は自身をサブエージェントと判定し、本スキルを起動せず、起動判断を呼び出し元へ返す。
メインが自身と全サブエージェントの記録をまとめてセッション全体を分析するため、サブエージェントによる個別起動は分析対象の重複又は欠落を生じさせる。

次のセッション以降で同じユーザー介入、レビュー反復、手戻り又は無駄が再発しないよう、現セッションの問題を独立コンテキストで洗い出し、メインが恒久対策を確定する。

## 問題候補の抽出

所要時間の計測範囲は、当該セッションの開始から`agent-toolkit:session-review`の完了までとする。
振り返り自体に要する時間を計測範囲から除かない。

メインは抽出を始める前に、対象プロジェクト固有の参照文書が存在するかを確認する。
対象はClaude Codeでは`~/.claude/references/session-review-dotfiles.md`、
Codexでは`~/.codex/references/session-review-dotfiles.md`とする。
存在すれば当該文書を全文読む。
この文書は、対象プロジェクト固有の振り返り観点と、当該プロジェクトの所要時間目標を保持する。

続いて、対象プロジェクトと処理規模に対応するセッションの所要時間目標が定められているかを確認する。
目標は、読み込み済みのプロジェクト規範（`AGENTS.md`・`CLAUDE.md`・自動ロードされるルールファイル）、
前段で読んだ参照文書及びユーザー指示から解決する。
目標が定められている場合は、対象と目標値を問題候補抽出の入力へ含める。
目標が規模別の値と規模によらない上限の双方を定める場合は、両方を入力へ含め、
内訳の分析と改善提案の作成では両方に対する差を示す。
目標が定められていない場合は、全対象へ適用する固定値を新設又は推定しない。

1. `agent-toolkit:delegation`を起動し、`agents_server.start`へ`model_type="session_review"`を渡してengine、model及びeffortの解決をサーバーへ委ねる。
2. メインが読み込んだ本`SKILL.md`の絶対パスから現行plugin rootを確定し、`skills/session-review/scripts/session_review_evidence.py`の実在を確認する。実在しなければ分析失敗として扱う。
3. メインが`atk managed-temp create --prefix session-review`を実行し、標準出力が単一の絶対パスであり、そのパスが実在するディレクトリであることを確認する。非0終了又は不実在の場合は分析失敗として扱う。この領域はメインが所有し、振り返り担当が抽出結果を保持する場所として渡す。続けてメインが`date -u +%Y-%m-%dT%H:%M:%SZ`を実行し、終了コード0と単一行の出力を確認して観測境界として保持する。境界より後に親記録へ追加されるメイン自身の進捗報告を、過去の未完了工程と誤認させないためである。
4. `agents_server`で通常の読み取り専用サブエージェントを1つ起動する。専用agent定義、固定モデル及び代替モデルを使わない。起動文へは、人間向けの本文を日本語で書き、実行環境が英語で挿入した指示の言語を応答言語として引き継がない条件と、抽出を別の担当へ再委譲せず自身で完遂する条件を含める。
5. Claude Codeでは、メインが把握する現在のtranscript絶対パスを渡す。Codexではメインの`CODEX_THREAD_ID`を渡し、サブエージェントは抽出器へ`--codex-thread-id`で当該IDを渡す。いずれの実行環境でも、確認済み抽出器の絶対パス、手順3の管理一時領域の絶対パス及び同じ手順の観測境界を渡す。記録の保存先の解決と正本1件の特定は抽出器が行うため、サブエージェントは検索式を組み立てない。あわせて、`atk wi list --target-repo=<対象リポジトリの絶対パス> --status=active --json --skip-pull`の出力から`filename`と`summary`だけを取り出した未処理項目の一覧を渡す。対象リポジトリを確定できない場合は一覧を渡さず、一覧を渡していない旨をサブエージェントへ示す。抽出器が0件又は複数件を診断して終了コード2を返した場合は`evidence_insufficient`とする。
6. サブエージェントが変更してよい対象は、渡された管理一時領域の内側だけとする。対象リポジトリ、セッション記録及びAWI保管先は読み取りだけを行う。抽出器の出力を保持する場合は、走査ごとに当該領域内の異なるファイルへ書き、領域外の固定名を使わない。
7. 当該セッションの全ての委譲先の記録を走査対象とする。サブエージェントの記録、`agents_server`経由で起動した独立セッションの記録、Codexスレッドの記録はいずれも対象に含め、委譲先がさらに起動した委譲先も同じ扱いとする。所在は抽出器がメインの記録から再帰的に導出するため、メインは委譲先の記録の絶対パスを渡さない。走査対象は当該セッションの全記録とする。読む量が増える負荷は、独立コンテキストのサブエージェントへ切り出して吸収する。抽出器が`unresolved-record`として報告した記録だけを、未確認の範囲として返させる。
8. 初回依頼には振り返りの起動理由を含めない。サブエージェント自身が、`--bundle`へ手順3の管理一時領域の絶対パスを渡した集約実行を1回行い、続けて必要な`--grep`と`--detail`をそれぞれ1回の実行へまとめて行う。全ての実行へ`--observation-boundary`と受領した観測境界を付ける。集約実行は通常表示、`--warn`、`--stats`及び`--hook-notices`の走査を1回の記録読み込みで行い、走査ごとの全量を当該領域のファイルへ書き、標準出力へは走査ごとの要約だけを返す。深掘りする候補が複数ある場合も、`--detail`のオプションを同じ実行の中で繰り返して指定し、候補ごとに実行を分けない。標準出力の要約だけで候補を確定できない走査に限り、当該領域の全量ファイルを読む。各実行は全ての記録を走査し、イベントの`record`欄が由来する記録を示す。`--detail`の行番号は`<記録>:<行番号>`形式で指定する。
9. 委譲先のエスカレーションは重点的に確認する。`needs_escalation`と差し戻しは工程が止まった箇所を直接示すため、1件ずつ発生条件と直前の入力を`--detail`で取得し、単発でも問題候補とする。完了報告に現れる手順の前提不成立、再試行及び自力回避も候補へ含める。委譲先が自ら回避して作業を続けた事象は、同じ回避が複数の委譲先で現れる場合を候補とする。
10. ユーザーの介入は単発でも問題候補とする。その場限りの事実連絡及び情報提供と、恒久対策を要する事象とを判別し、判別の根拠を候補へ添える。判別は、同じ介入が対象リポジトリの既存AWI、UWI、事故記録文書などの過去のセッション由来の記録に現れるかと、当該介入が無ければ工程が誤った状態のまま進んだかで行う。過去のセッション由来の記録に同じ介入が現れる候補は再発として返し、メインは当該候補の恒久対策を必ず確定する。
11. サブエージェントは`status`、各走査の成否、問題候補ごとの要約・観測事象・再取得用query・locator・未確認事項及び全体の未確認範囲だけを返す。原因、解決案、反映先、採否、AWI本文はいずれも作成しない。所要時間目標を入力で受け取った場合は、`--stats`で実測した所要時間と目標との差も返す。内訳は`stats-gap`・`stats-tool`・`stats-slow-call`・`stats-repeat`・`stats-subagent`・`stats-agent-thread`・`stats-compaction`に基づいて返す。
    コンパクションは会話履歴の再構成に時間を要するため、所要時間目標の有無にかかわらず`stats-compaction`と`stats-compaction-total`から発生位置と回数を取得し、記録別の発生位置を問題候補へ添える。
    未処理項目の一覧を受領した場合は、列挙する候補が当該一覧のいずれかと同じ事象を指すかを照合し、指す場合はその旨と該当ファイル名を当該候補へ添える。フックの警告通知だけを根拠とする候補は、通知の種別ごとに1件へまとめ、件数と発生元を示す。この照合と集約は候補の提示形式に対する要件であり、原因、解決案、反映先、採否とAWI本文を作成しない契約を変えない。

証拠の保持は次の形で行う。集約実行が走査ごとの全量を当該領域のファイルへ書くため、走査ごとにリダイレクトを分けない。

```sh
uv run --no-project --script <抽出器の絶対パス> <transcriptの絶対パス> --observation-boundary <観測境界> --bundle <管理一時領域の絶対パス>
uv run --no-project --script <抽出器の絶対パス> --codex-thread-id <thread ID> --observation-boundary <観測境界> --bundle <管理一時領域の絶対パス>
```

メインはサブエージェントのqueryとlocatorが指す証拠だけを再取得する。この参照文書を通常サブエージェントへは渡さない。セッション全体の要約・再抽出のいずれも作成しない。

メインは振り返り担当の終端と返却内容を検収した後、`atk managed-temp cleanup --path <手順3で確認した絶対パス>`を実行し、終了コード0を確認して領域を回収する。振り返りが異常終了した場合は、原因調査に必要な間だけ領域を保持し、調査を終えた時点で同じコマンドで回収する。

ユーザーによるエージェントの間違い等の指摘又は同じ成果物・責任範囲のレビュー第3ラウンドが起動理由であり、対応する候補が初回出力に無い場合は、同じ`agents_server` sessionへ`send_message`で当該事象と証拠位置を送り、対象を再確認させる。別sessionを起動しない。

## 所要時間の分析と改善提案

所要時間目標が定められている場合は、超過の有無にかかわらず所要時間の内訳を毎回分析する。
規模によらない上限が定められている場合は、当該上限に対する超過の有無も分析へ含める。
メインは所要時間の内訳から寄与の大きい工程と反復を特定し、
品質、必須工程及び検収範囲を維持したまま所要時間を短縮する改善提案を作成して振り返りの成果へ含める。
改善提案は、内訳で確認した時間寄与と短縮する工程を対応付ける。

所要時間、トークン量及びリクエスト数を、改善提案・確認の本文その他の利用者が読む文面へ書く場合は、抽出器の`--stats`が返した値だけを典拠とし、自作の集計を典拠にしない。総量と工程別の内訳は基準が異なるため、比率を示す場合は`agent-toolkit:agent-standards`の`agent-standards/references/session-records.md`「集計値の典拠」が定める基準差を同じ本文へ併記する。

コンパクションの回数と合計時間を所要時間の内訳へ含める。発生位置の直前の工程を`--detail`で確認し、当該工程の読込と出力を独立コンテキストのサブエージェントへ切り出す案を改善提案の候補とする。
コンパクションの回数は、コンテキスト消費そのものを減らす手段で削減する。出力量の大きい調査・検証の委譲による分離、初回取得の対象範囲の限定、結論だけを受け取る読み取り専用の探索委譲などが該当する。
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`などの発生閾値を引き上げて発生時期を先送りする手段は、コンテキスト消費を減らさないため改善提案として挙げない。

## 原因と対策

問題候補が1件以上なら`agent-toolkit:bugfix`を起動し、観測事象、2系統4段階の原因分析、原因分析の品質確認、原因起点の類似見直し、対策・横展開処置・再発防止策及び反映要否をメインが確定する。

再発防止策の必須性、省略できる条件及び良い案を確定できない場合の終端は`agent-toolkit:bugfix`の再発防止策の必須性節に従う。`agent-toolkit:process-wi`だけが起動理由で問題候補が無い場合は、対策なしで完了できる。

採用した対策のAWI又はUWIは`agent-toolkit:wi-standards`に従って起草・重複判定・投入する。本スキルは本文形式・CLI手順のいずれも定義しない。

確定した内容は候補別の判定記録の表へ記録する。

## 候補別の判定記録

メインは問題候補ごとに、`候補`、`欠陥判定`、`直接的原因`、`根本原因`、`既存規範が適用されなかった理由`、`処置`の6列表へ1行を記録し、振り返りの成果へ含める。

- `候補`には観測事象と再取得用のlocatorを書く
- `欠陥判定`には欠陥とするか否かを書き、欠陥としない場合はそう判定した観測根拠を併記する
- `直接的原因`には観測事象を発生させる実行時・データ・設定上の機構を書く
- `根本原因`には`agent-toolkit:bugfix`の原因分析で確定した結論を書く
- `既存規範が適用されなかった理由`には、当該事象を統治する既存規範がある場合に、その規範が実行経路で適用されなかった原因を書く。統治する規範が無い場合はその旨を書く
- `処置`には対策、横展開処置及び再発防止策と、同一セッションでの実装状態又は根本原因を覆うactive項目のファイル名を書く。再発防止策の適用範囲は、誤りの機構が依存する条件で書く

次のいずれかに該当する行が残る間は振り返りを完了しない。

- 欠陥と判定した行に処置が無い
- 既存規範へ違反した事象で、当該規範の存在だけを処置としている
- 参照するactive項目が根本原因と必要な全処置の一部しか覆っていない
- 再発防止策の適用範囲を、観測事象の対象、工程又は識別子だけで限定している

該当する行は、`agent-toolkit:bugfix`の再発防止策の必須性に従って処置を確定するか、同節に従ってUWIを登録してから完了する。

## 規範適用による停止の抽出と改訂提案

問題候補のうち、規範を適用した結果として工程の停止、差し戻し、空転又は同じ工程の反復が生じたものを列挙する。
本節の対象は規範を適用した結果として生じた停止であり、既存規範が適用されなかった事象を扱う`## 候補別の判定記録`とは対象が逆である。両者を同じ行へまとめない。

抽出の対象は次のいずれかを満たす候補とする。

- 規範が要求する停止、差し戻し又は確認により、当該セッションの工程が先へ進まなかった
- 規範どうしが同じ場面で両立しない動作を要求し、実行主体が適用先の判定へ工程を費やした
- 規範が要求する手順の前提が実在せず、当該手順に代替経路の定めが無かった

列挙した各箇所について、当該条文の維持、修正、置換及び撤去の4案を同じ階層で比較する。
比較の結果を`候補`、`当該条文の所在`、`観測した停止`、`4案の評価`、`採用案`の5列表へ記録し、振り返りの成果へ含める。

- `候補`には観測事象と再取得用のlocatorを書く
- `当該条文の所在`には条文を持つファイルのパスと節名を書く
- `観測した停止`には停止した工程、停止の契機となった条文の要求及び停止が解消した経緯を書く
- `4案の評価`には維持、修正、置換及び撤去のそれぞれについて、採否と判断根拠を書く
- `採用案`には採用した1案と、AWIへ登録した場合はそのファイル名を書く

採用案が維持以外の場合は、`agent-toolkit:wi-standards`に従って当該条文の改訂をAWIへ登録する。
`agent-toolkit:review-standards`の`review-standards/references/judgment-details.md`「規定の適用可否」が求める規定側の改訂の提案は、本節の登録により成立する。
該当する候補が0件の場合は表を置かず、確認した範囲と0件と判断した理由を振り返りの成果へ含める。

## 分析失敗

サブエージェント起動、親transcript解決又は証拠抽出が失敗した場合は、同じ実効設定で1回だけ自動再試行する。再失敗時は、推奨案「UWIへ記録して元作業を継続」と代替案「その場で再試行」を`AskUserQuestion`で確認する。

回答期限超過時は`agent-toolkit:wi-standards`に従い、セッションID、失敗事象、解除条件及び「当該セッションをresumeしてsession-reviewを再実行する」再開工程をUWIへ記録する。transcriptパスは保存しない。メインによる全量分析又は別モデルへのフォールバックは行わない。

手動起動では分析未完了を報告できる。`agent-toolkit:process-wi`から起動した場合は、分析未完了とUWIを`agent-toolkit:completion-report`へ返し、元作業の完了を妨げない。
