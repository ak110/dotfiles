# セッション振り返り

最上位セッションのメインエージェントだけが本スキルを起動する。
別のエージェントからタスクを受領した実行主体は自身をサブエージェントと判定し、本スキルを起動せず、起動判断を呼び出し元へ返す。
メインが自身と全サブエージェントの記録をまとめてセッション全体を分析するため、サブエージェントによる個別起動は分析対象の重複又は欠落を生じさせる。

次のセッション以降で同じユーザー介入、レビュー反復、手戻り又は無駄が再発しないよう、現セッションの問題を独立コンテキストで洗い出し、メインが恒久対策を確定する。

## 問題候補の抽出

所要時間の計測範囲は、当該セッションの最初の記録から、メインが振り返りの成果を確定した時点までとする。
振り返り自体に要する時間を計測範囲から除かない。
計測範囲の終端の取得と所要時間の算出は`## 所要時間の分析と改善提案`が定める。

メインは次の1から4の順に進める。抽出担当が入力として必要としないメイン専用の工程は、抽出担当の起動より後へ置き、抽出担当の稼働と並行させる。

1. メインが読み込んだ本`SKILL.md`の絶対パスから現行plugin rootを確定し、`skills/session-review/scripts/session_review_prepare.py`を次の形で1回実行する。
   Claude Codeではメインが把握する現在のtranscript絶対パスを`--transcript`へ渡し、Codexではメインの`CODEX_THREAD_ID`を`--codex-thread-id`へ渡す。
   対象リポジトリを確定できない場合は`--target-repo`を渡さない。
   終了コードが0でない場合と、標準出力から`${CLAUDE_PLUGIN_ROOT}/share/session-review-evidence.parent.md`が要求する項目を取得できない場合は、`## 分析失敗`へ進む。

   ```sh
   uv run --no-project --script <準備スクリプトの絶対パス> --transcript <transcriptの絶対パス> --target-repo <対象リポジトリの絶対パス>
   uv run --no-project --script <準備スクリプトの絶対パス> --codex-thread-id <thread ID> --target-repo <対象リポジトリの絶対パス>
   ```

2. `${CLAUDE_PLUGIN_ROOT}/share/session-review-evidence.parent.md`を全文読み、同書に従って抽出担当を起動する。

3. 抽出担当の稼働と並行して、振り返り用の参照文書と所要時間目標を解決する。
   いずれも抽出担当へ渡さず、メインが恒久対策と改善提案を確定するために読む。

   対象プロジェクトの規範（`AGENTS.md`・`CLAUDE.md`・自動ロードされるルールファイル）が振り返り用の参照文書を指定しているかを確認する。
   指定は実行中のホストごとに置かれ、値は`~/`で始まるホーム相対パス又は絶対パスとする。
   `~/`で始まる値は、シェルの展開を用いず、実行主体のホームディレクトリへ残りの部分を結合して解決する。
   実行中のホストに対応する指定がある場合は、解決したパスの文書を全文読む。
   この文書は、対象プロジェクト固有の振り返り観点と、当該プロジェクトの所要時間目標を保持する。
   実行中のホストに対応する指定が無い対象プロジェクトでは、参照文書を探索せず、規範とユーザー指示だけを解決先とする。

   続いて、対象プロジェクトのセッションの所要時間目標が定められているかを確認する。
   目標は、読み込み済みのプロジェクト規範、前段で読んだ参照文書及びユーザー指示から解決する。
   目標が定められている場合は、対象と目標値を`## 所要時間の分析と改善提案`の入力へ含める。
   目標が定められていない場合は、全対象へ適用する固定値を新設又は推定しない。

4. `${CLAUDE_PLUGIN_ROOT}/share/session-review-evidence.parent.md`に従って抽出担当の返却を検収した後、ユーザー発話の追加分を再照合する。
   再照合には抽出器の`--user-events`を次の形で用い、`send_message`と`wait`を発行しない。

   ```sh
   uv run --no-project --script <抽出器の絶対パス> <transcriptの絶対パス> --user-events --since <照合済み境界> --observation-boundary <再照合境界>
   uv run --no-project --script <抽出器の絶対パス> --codex-thread-id <thread ID> --user-events --since <照合済み境界> --observation-boundary <再照合境界>
   ```

   手順1が返した観測境界を照合済み境界の初期値とし、追加分が0件であり、かつ再照合境界の取得後に新しいユーザー入力を受領していない状態になるまで次を繰り返す。

   - `date -u +%Y-%m-%dT%H:%M:%SZ`を実行し、終了コード0と単一行の出力を再照合境界として保持する。
   - 抽出器を1回実行し、照合済み境界より後から再照合境界までのメイン記録のユーザー発話イベントを取得する。
   - 実行環境がユーザーメッセージへ挿入した通知（`<system-reminder>`で始まる本文など）を追加分から除き、残るイベントを抽出担当が返したユーザー介入の全件一覧の`record`欄と`line`欄の組へ突合する。
   - 追加分を当該全件一覧と候補別の判定記録へ加え、照合済み境界を再照合境界へ更新する。
   - 追加分が1件以上の場合又は再照合境界の取得後に新しいユーザー入力を受領した場合は、新しい再照合境界で再取得する。
   - 抽出器が非0で終了した場合と突合が完了しない場合は`evidence_insufficient`とし、`## 分析失敗`へ進む。

   初回の抽出結果と問題候補は変更せず、メインの進捗報告及び委譲先のタスク入力は追加分へ含めない。

## 所要時間の分析と改善提案

所要時間目標が定められている場合は、超過の有無にかかわらず所要時間の内訳を毎回分析する。
メインは振り返りの成果を確定した時点で`date -u +%Y-%m-%dT%H:%M:%SZ`を実行し、終了コード0と単一行の出力を確認する。
続けて抽出器へ当該値を`--elapsed-until`で渡して実行し、返った`elapsed_seconds`を当該セッションの所要時間とする。

```sh
uv run --no-project --script <抽出器の絶対パス> <transcriptの絶対パス> --elapsed-until <取得した時刻>
uv run --no-project --script <抽出器の絶対パス> --codex-thread-id <thread ID> --elapsed-until <取得した時刻>
```

所要時間を書く箇所には、当該値がセッションの最初の記録から`--elapsed-until`へ渡した時刻までの区間であり、
当該時刻より後に実施する工程を含まないことを併記する。
メインは所要時間の内訳から寄与の大きい工程と反復を特定し、
品質、必須工程及び検収範囲を維持したまま所要時間を短縮する改善提案を作成して振り返りの成果へ含める。
改善提案は、内訳で確認した時間寄与と短縮する工程を対応付ける。

所要時間、トークン量及びリクエスト数を、改善提案・確認の本文その他の利用者が読む文面へ書く場合は、抽出器が返した値だけを典拠とし、自作の集計を典拠にしない。総量と工程別の内訳は基準が異なるため、比率を示す場合は`agent-toolkit:writing-standards`の`writing-standards/references/session-records.md`「集計値の典拠」が定める基準差を同じ本文へ併記する。

コンパクションの回数と合計時間を所要時間の内訳へ含める。発生位置の直前の工程を`--detail`で確認し、当該工程の読込と出力を独立コンテキストのサブエージェントへ切り出す案を改善提案の候補とする。
コンパクションの回数は、コンテキスト消費そのものを減らす手段で削減する。出力量の大きい調査・検証の委譲による分離、初回取得の対象範囲の限定、結論だけを受け取る読み取り専用の探索委譲などが該当する。
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`などの発生閾値を引き上げて発生時期を先送りする手段は、コンテキスト消費を減らさないため改善提案として挙げない。

## 原因と対策

問題候補が1件以上なら`agent-toolkit:bugfix`を起動し、観測事象、2系統4段階の原因分析、原因分析の品質確認、原因起点の類似見直し、対策・横展開処置・再発防止策及び反映要否をメインが確定する。

ユーザー介入を恒久対策の対象とする場合、介入本文から趣旨を一意に確定できなければ、原因と対策を確定する前に`AskUserQuestion`で確認する。
確認を発行できないか回答を得られない場合は、`agent-toolkit:wi-standards`に従い、残る解釈候補、対策が未確定である旨及び回答後に原因と対策の確定から再開する条件をUWIへ記録する。
確認が完了するまで、当該候補の対策を確定せず、対策のAWIを起草又は投入しない。

エージェントの誤り又は工程の逸脱を是正したユーザー介入と、同じ成果物かつ同じ責任範囲で発生したレビュー第3ラウンドは、拡張原因分析の条件へ該当する事象として扱う。

再発防止策の必須性、省略できる条件及び良い案を確定できない場合の終端は`agent-toolkit:bugfix`の再発防止策の必須性節に従う。前段の2種の事象で再発防止策を省略できるのは、同節が挙げる2条件に該当する場合に限る。`agent-toolkit:process-wi`だけが起動理由で問題候補が無い場合は、対策なしで完了できる。

採用した対策のAWI又はUWIは`agent-toolkit:wi-standards`に従って起草・重複判定・投入する。本スキルは本文形式・CLI手順のいずれも定義しない。

確定した内容は候補別の判定記録の表へ記録する。

## 候補別の判定記録

メインは問題候補ごとに、`候補`、`欠陥判定`、`直接的原因`、`根本原因`、`既存規範が適用されなかった理由`、`処置`の6列表へ1行を記録し、振り返りの成果へ含める。振り返り担当が列挙したユーザー介入のうち問題候補としなかったものも、同じ表へ1行を記録し、`欠陥判定`へ除外の観測根拠を書く。

ユーザー介入の趣旨を一意に確定できない候補は、確認又はUWIへの記録を終えてから表へ記録する。
UWIへ記録した行の`処置`には、対策が未確定である旨、UWIのファイル名及び再開条件を書き、解釈候補のいずれかを前提とする対策を書かない。

- `候補`には観測事象と再取得用のlocatorを書く
- `欠陥判定`には欠陥とするか否かを書き、欠陥としない場合はそう判定した観測根拠を併記する
- `直接的原因`には観測事象を発生させる実行時・データ・設定上の機構を書く
- `根本原因`には`agent-toolkit:bugfix`の原因分析で確定した結論を書く
- `既存規範が適用されなかった理由`には、当該事象を統治する既存規範がある場合に、その規範が実行経路で適用されなかった原因を書く。統治する規範が無い場合はその旨を書く
- `処置`には対策、横展開処置及び再発防止策と、同一セッションでの実装状態又は根本原因を覆うactive項目のファイル名を書く。再発防止策の適用範囲は、誤りの機構が依存する条件で書く。1件の再発防止策で複数の候補を覆う場合は、当該候補の`根本原因`へ同一の結論を書く

次のいずれかに該当する行が残る間は振り返りを完了しない。

- 欠陥と判定した行に処置が無い
- 既存規範へ違反した事象で、当該規範の存在だけを処置としている
- 参照するactive項目が根本原因と必要な全処置の一部しか覆っていない
- 再発防止策の適用範囲を、観測事象の対象、工程又は識別子だけで限定している
- 1件の処置が複数の候補を覆いながら、当該候補の`根本原因`が一致していない
- 振り返り担当が列挙したユーザー介入又は委譲先のエスカレーションのうち、当該表のいずれの行にも対応しないものが残る

該当する行は、`agent-toolkit:bugfix`の再発防止策の必須性に従って処置を確定するか、同節に従ってUWIを登録してから完了する。

## 規範適用による停止の抽出と改訂提案

問題候補のうち、規範を適用した結果として工程の停止、差し戻し、空転又は同じ工程の反復が生じたものを列挙する。
本節の対象は規範を適用した結果として生じた停止であり、既存規範が適用されなかった事象を扱う`## 候補別の判定記録`とは対象が逆である。両者を同じ行へまとめない。

抽出の対象は次のいずれかを満たす候補とする。

- 規範が要求する停止、差し戻し又は確認により、当該セッションの工程が先へ進まなかった
- 規範どうしが同じ場面で両立しない動作を要求し、実行主体が適用先の判定へ工程を費やした
- 規範が要求する手順の前提が実在せず、当該手順に代替経路の定めが無かった

列挙した各箇所について、当該条文の維持、修正、置換及び撤去の4案を同じ階層で比較する。
比較の結果を`候補`、`当該条文の所在`、`観測した停止`、`4案の評価`、`採用案`の5列表へ記録し、振り返りの成果へ含める。

- `候補`には観測事象と再取得用のlocatorを書く
- `当該条文の所在`には条文を持つファイルのパスと節名を書く
- `観測した停止`には停止した工程、停止の契機となった条文の要求及び停止が解消した経緯を書く
- `4案の評価`には維持、修正、置換及び撤去のそれぞれについて、採否と判断根拠を書く
- `採用案`には採用した1案と、AWIへ登録した場合はそのファイル名を書く

採用案が維持以外の場合は、`agent-toolkit:wi-standards`に従って当該条文の改訂をAWIへ登録する。
`agent-toolkit:review-standards`の`review-standards/references/judgment-details.md`「規定の適用可否」が求める規定側の改訂の提案は、本節の登録により成立する。
該当する候補が0件の場合は表を置かず、確認した範囲と0件と判断した理由を振り返りの成果へ含める。

## 分析失敗

準備工程、抽出担当の起動、親transcript解決又は証拠抽出が失敗した場合は、同じ実効設定で1回だけ自動再試行する。再失敗時は、推奨案「UWIへ記録して元作業を継続」と代替案「その場で再試行」を`AskUserQuestion`で確認する。

回答期限超過時は`agent-toolkit:wi-standards`に従い、セッションID、失敗事象、解除条件及び「当該セッションをresumeしてsession-reviewを再実行する」再開工程をUWIへ記録する。transcriptパスは保存しない。メインによる全量分析は行わない（全記録がメインのコンテキストへ入ると、以降の判断へ回せる容量が残らないため）。

手動起動では分析未完了を報告できる。`agent-toolkit:process-wi`から起動した場合は、分析未完了とUWIを`agent-toolkit:completion-report`へ返し、元作業の完了を妨げない。
