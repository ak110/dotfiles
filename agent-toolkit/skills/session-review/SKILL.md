# セッション振り返り

最上位セッションのメインエージェントが本スキルを起動する。
本スキルを受け取った振り返り担当を除き、別のエージェントからタスクを受け取った実行主体は自身をサブエージェントと判定し、起動判断を呼び出し元へ返す。
1つの実行主体が対象セッションの全ての記録をまとめて分析するため、これ以外の個別起動は分析対象の重複又は欠落を生じさせる。

同じユーザー介入、レビュー反復、手戻り又は無駄が再発しないよう、対象セッションの問題を独立コンテキストで洗い出し、恒久対策を確定する。

## 実行主体

メインは自身のセッションを振り返り対象とする。メインは`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.parent.md`を全文読み、同書に従って振り返り担当を1件だけ起動する。
振り返り担当は本書の全工程を自ら実行し、抽出器を直接実行し、振り返りの成果を受け取った出力先ファイルへ書く。
メインはそのファイルを読んで検収する。セッション全体の要約と再抽出は振り返り担当が担う。
証拠の走査と分析を同じ主体へ置くのは、両者を分けた構成が同じ記録を親子で重ねて読み、返却本文の量を候補の件数に比例させたためである。

振り返り用の参照文書と所要時間目標は、振り返り担当が起動時の`cwd`から解決したプロジェクト規範から自ら解決する。
メインは目標の有無と目標値を成果ファイルの`## 対象セッション`から読む。
メインが解決して担当へ渡す形は、担当の必須入力へ目標値と参照文書を加えることになるため採用しない。

## 問題候補の抽出

所要時間の計測範囲は、対象セッションの最初の記録から、対象セッションが終了する時点までとする。
計測範囲には、振り返り自体、起動元の終端工程、`agent-toolkit:completion-report`及び`atk agents-exit-session`に要する時間も含める。
計測範囲の終端の取得と所要時間の算出は`## 所要時間の分析と改善提案`が定める。

工程を実行する主体は次の1から3の順に進める。

1. メインが、読み込んだ本`SKILL.md`の絶対パスから現行plugin rootを確定し、`skills/session-review/scripts/session_review_prepare.py`を次のいずれか1つの形で1回実行する。
   Claude Codeで把握している現在のtranscript絶対パスを`--transcript`へ渡し、Codexでは`CODEX_THREAD_ID`を`--codex-thread-id`へ渡す。
   対象リポジトリを確定できない場合は`--target-repo`を渡さない。
   終了コードが0でない場合と、標準出力から`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.parent.md`が要求する項目を取得できない場合は、`## 分析失敗`へ進む。

   ```sh
   uv run --project <plugin rootの絶対パス> --locked --no-default-groups <準備スクリプトの絶対パス> --transcript <transcriptの絶対パス> --target-repo <対象リポジトリの絶対パス>
   uv run --project <plugin rootの絶対パス> --locked --no-default-groups <準備スクリプトの絶対パス> --codex-thread-id <thread ID> --target-repo <対象リポジトリの絶対パス>
   ```

   いずれの起動形も、準備スクリプトを1回だけ実行する。

2. メインが`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.parent.md`を全文読み、同書に従って振り返り担当を起動する。
   振り返り担当は本書の全節を適用する。抽出器の実行、問題候補の判別と既存キュー項目との照合は`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.subagent.md`が定める。

   起動の後、振り返り担当が振り返り用の参照文書と所要時間目標を解決する。解決先は起動時の`cwd`から解決したプロジェクト規範とする。

   解決したプロジェクト規範（`AGENTS.md`・`CLAUDE.md`・自動ロードされるルールファイル）が振り返り用の参照文書を指定しているかを確認する。
   指定は実行中のホストごとに置かれ、値は`~/`で始まるホーム相対パス又は絶対パスとする。
   `~/`で始まる値は、シェルの展開を用いず、実行主体のホームディレクトリへ残りの部分を結合して解決する。
   実行中のホストに対応する指定がある場合は、解決したパスの文書を全文読む。
   この文書は、対象プロジェクト固有の振り返り観点と、そのプロジェクトの所要時間目標を保持する。
   実行中のホストに対応する指定が無い対象プロジェクトでは、規範とユーザー指示だけを解決先とする。

   続いて、対象プロジェクトのセッションの所要時間目標が定められているかを確認する。
   目標は、解決したプロジェクト規範、前段で読んだ参照文書及び対象セッションの記録に現れるユーザー指示から解決する。
   目標が定められている場合は、対象と目標値を`## 所要時間の分析と改善提案`の入力へ含める。
   目標が定められていない場合は、目標なしとして以降の工程を進める。全対象へ適用する固定値の新設と推定は、目標の解決手段の外に置く。
   解決した参照文書のパス、目標の有無、目標値は、振り返りの成果の`## 対象セッション`へ書く。メインはその記載から目標の有無を確定する。

   抽出器は対象セッション自身の常駐処理、再開機構、実行環境が生成した定時prompt、委譲先の入力、初期要求、提示した選択肢をそのまま選んだユーザー確認への回答を利用者介入の候補から除く。
   選択肢のいずれとも一致しない回答と自由記述を伴う回答は、従来の判断を是正した介入として候補に残す。
   発信元は抽出記録のrole、イベント種別、起動経路及び実行環境が付ける固定接頭辞で判定し、除外種類別の件数を`candidate-summary`へ記録する。
   残るユーザー発話のうち、次の介入を問題候補とする。

   - 従来の判断、工程、成果物、要求分類、完了判定のいずれかを変更、撤回若しくは是正した介入
   - 将来の振る舞いを変更する要求が明示された介入

   候補から除く条件は前段の抽出器の除外規則とし、エージェントの誤り、ユーザーの選好、追加要件のいずれへ分類したかは除外の判定の外に置く。

   現在の進捗、所要時間、状態のいずれかを尋ねる単発の照会は、後続の判断と成果物をそのまま保つため、問題候補の外に置く。照会に是正、停止、方針変更、将来の振る舞い変更のいずれかが併記されている場合は、該当部分だけを候補とする。どちらかを一意に判定できない場合は候補として保持し、`## 原因と対策`の確認経路で意図を確定する。意図の確認は確認経路で行い、詳細な進捗報告は別の工程として扱う。
   過去の振り返り又はキュー処理で不採用が確定した案は、新しい観測又は要件変更を同じ候補へ対応付けられる場合だけ再評価し、
   いずれも無い場合は不採用済みであることを根拠に提案集合から除く。

   振り返り担当を起動した直後、メインは自身のコンテキストから改善点を探し、担当の稼働と並行して列挙する。担当の終端を待たずに列挙を終える。
   機械的な抽出は標識を残す事象だけを対象とする。推測で組んだコマンドの試行錯誤、同じ資料の読み直し、採用した設計の書き直しは候補に現れない。規範の解釈へ費やした工程と、委譲先への指示不足による手戻りも同じく現れない。これらを観測できるのは、その判断を下したメイン自身のコンテキストだけである。
   探す対象はそのセッション全体とし、観点を限定しない。抽出器が候補として拾った事象と重複してよい。
   列挙する単位は、その改善で防げる事象と、その事象が生じた工程とする。記録位置の特定は求めない。
   列挙した内容は、準備工程が返した管理対象一時領域の直下のファイルへ書く。会話圧縮でコンテキストから失われた区間がある場合は、その区間を列挙の対象外として同じファイルへ書く。列挙が0件の場合は、0件と判断した理由を同じファイルへ書く。
   このファイルの配送は`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.parent.md`の`## メイン由来の改善点の配送`が定める。

3. メインが振り返り担当の返却を検収した後、ユーザー発話の追加分を再照合する。
   再照合には抽出器の`--user-events`を、手順1と同じ起動形へ`--since <照合済み境界>`と`--observation-boundary <再照合境界>`を加えて用いる。
   手順1が返した観測境界を照合済み境界の初期値とし、追加分が0件であり、かつ再照合境界の取得後に新しいユーザー入力を受け取っていない状態になるまで繰り返す。

   各回では次を行う。

   - 現在時刻を再照合境界として保持し、照合済み境界より後から再照合境界までのユーザー発話イベントを取得する
   - 実行環境がユーザーメッセージへ挿入した通知を除いた残りを、成果ファイルの判定記録が挙げるlocatorへ突合する
   - 追加分を`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.parent.md`の`## ユーザー発話の追加分の配送`に従って配送し、照合済み境界を更新する
   - 抽出器が非0で終了した場合と突合が完了しない場合は、`## 分析失敗`へ進む

   追加分の対象はユーザー発話とし、メインの進捗報告及び委譲先のタスク入力は別の記録として扱う。
   振り返りの実行中に受け取ったユーザー介入も候補別の判定記録へ取り込み、類似見直しと再発防止策の対象に含める。

## 所要時間の分析と改善提案

振り返りの成果の`## 所要時間の内訳と改善提案`へ、律速区間とその秒数、削減できると判定した区間の短縮見込み、削減できないと判定した区間の根拠、及び分解できない区間の秒数と区間を書く。
各値の典拠として、その秒数を確定した抽出器のイベント種別と値を併記する。
全区間の網羅分割と、秒数の合計を`elapsed_seconds`へ一致させる要求は置かない。形式の充足へ工程が向かい、何が遅かったかの発見が起きなくなるためである。

振り返り担当は所要時間の内訳から寄与の大きい工程と反復を特定し、
品質を保ったまま単位時間あたりに処理するユーザー由来のWIの件数を最大化する改善提案を作成して振り返りの成果へ含める。
この尺度が数えるのはユーザー由来のWIの処理件数とし、エージェント由来のWIは別に数える。
所要時間の短縮とトークンコストの削減は、この尺度を高める手段として扱う。
提案の対象は必須工程と検収範囲を含む全ての工程とし、工程の撤去、順序の変更及び並行化を候補とする。
提案の対象範囲は、対象セッションの工程に加えて、`agent-toolkit:process-wi`と`atk wi process-loop`が定める手順と、その手順が従う規範とする。
本スキルの工程と、その工程が用いる抽出器、準備スクリプトと報告生成器も同じ対象へ含める。振り返り自体の所要時間とコストも、単位時間あたりに処理するユーザー由来のWIの件数を下げるためである。
機械的な抽出が候補として返す区分のうち、改善へ結び付いた件数が少ない区分は、抽出の条件を限定する提案の対象とする。
手順と規範について撤去、変更又は置換を提案する前に、その手順の導入目的と由来を調べる。
調べる対象は、条文が理由として示す保護対象と成果、その条文を導入した変更、及び対応する計画ファイルとする。
その目的を別の手段でより低い費用で満たせると確定した場合に撤去、変更又は置換を提案し、確定できない場合は維持を提案する。
重複した検証の排除と待ち時間の活用を提案の観点へ含める。
CIが同じ検査を担う環境では、公開前のローカルの全体検査を重複として扱う。
CIの所要時間が長い環境では、CIが失敗する見込みが高い場合に限り、影響範囲を見極めた部分実行を先に行う。
その部分実行の対象には、変更したファイルに加えて、変更した定義の直接消費側と、同じ契約を保持する箇所を含める。
案の採否は、品質への影響と、トークンコストと保守コストの大幅な増加の有無で判定する。
改善提案は、内訳で確認した時間寄与と短縮する工程を対応付ける。
この特定と改善提案の作成は、所要時間目標の有無にかかわらず行う。
所要時間目標が定められ、かつ対象セッションの所要時間がその目標を超過した場合は、改善提案の作成を必須とする。
それ以外の場合は、改善できる箇所を見つけたときに提案する。

振り返り工程そのものの所要時間目標を900秒とし、改善提案の起点として用いる。本節と本書の他の箇所が対象を伴わずに`所要時間目標`と書く箇所は対象セッションの所要時間目標を指す。
計測範囲は準備工程の開始から振り返りの成果を確定した時点までとし、メインによる成果の検収と追加分の再照合は振り返り担当が観測できないため範囲の外に置く。
その区間の秒数と900秒との比較結果を成果へ書き、短縮できる箇所があれば改善提案の対象へ含める。
この目標は振り返りの完了条件の外に置く。超過を理由とする未完了の判定とUWIの登録も同じ扱いとする。

短縮の対象は、工程別の合計時間ではなく律速区間とする。
律速区間は、抽出器の`stats-critical-path`が返す`main_only_seconds`と、agent thread別の`exclusive_seconds`の並びとする。
そのイベントが`unmeasured_threads`を挙げた場合は、そのthreadを律速区間の判定材料から外し、外した対象を内訳へ書く。
成果へ書く改善提案は、律速区間のいずれかを短縮するものとする。工程別の合計時間は判断材料の一部として扱う。

改善提案ごとに、1セッションあたりの短縮見込み秒数、その見込みが依拠する実測値、及びその見込みが実測と推定のいずれであるかを書く。
実測値には、抽出器が返したイベントの種別とそのイベントの値を書く。推定の場合は算出式と前提を書く。

短時間に反復したコマンドも、呼び出しごとの所要時間と律速区間への寄与から見直す。
例えば、`atk`の同じ操作が入力形式の誤りで反復した場合は、最下層のヘルプ又は仕様の取得を先行させる。
成功した同種の操作が複数対象へ反復した場合は、そのコマンドが公開する複数対象の指定で統合できるかを比較する。
これは努力目標とする。短い操作も反復する回数に応じて待機と再実行の時間を費やすためである。

メインは自身のセッションを振り返り対象とするため、終了する時点を振り返りの時点で確定できない。
振り返り担当は、成果を確定した時点の時刻を抽出器の`--elapsed-until`へ渡して`elapsed_seconds`を取得し、その値を計測範囲の中間値とする。
成果へ書く所要時間はこの中間値とし、セッションの最初の記録からその時刻までの区間であることを併記する。
所要時間目標との比較に用いる値は、`agent-toolkit:completion-report`が報告の直前に同じ手段で取得する。
メインは、成果ファイルの`## 対象セッション`が所要時間目標を定められていると示す場合に、抽出器の絶対パスと、`--transcript`又は`--codex-thread-id`へ渡した値を同スキルの入力として保持する。
目標が定められていないセッションでは、メインはこの入力の保持を省く。

所要時間目標が定められている場合は、改善提案の短縮見込みの合計と目標値の比較結果を成果へ書き、目標値を超える場合は超過分の秒数とその超過を生じさせる律速区間を併記する。
超過は改善提案の起点として扱い、振り返りの完了条件の外に置く。
保存済みの証拠から算出できる値は成果へ確定値として書き、次回実行の再計測へ判定を委ねない。

所要時間、トークン量及びリクエスト数を、改善提案・確認の本文その他の利用者が読む文面へ書く場合は、抽出器が返した値だけを典拠とする。総量と工程別の内訳は基準が異なるため、比率を示す場合は`agent-toolkit:writing-standards`の`writing-standards/references/session-records.md`「集計値の典拠」が定める基準差を同じ本文へ併記する。

コンパクションの回数と合計時間を所要時間の内訳へ含める。発生位置の直前の工程を`--detail`で確認し、その工程の読込と出力を独立コンテキストのサブエージェントへ切り出す案を改善提案の候補とする。
`stats-compaction-total`の`total_duration_seconds`は所要時間を取得できたコンパクションだけの合計であり、`duration_unknown_count`が1以上の場合はその件数を内訳へ併記する。所要時間が不明なコンパクションは件数として内訳へ残す。
コンパクションの回数は、コンテキスト消費そのものを減らす手段で削減する。出力量の大きい調査・検証の委譲による分離、初回取得の対象範囲の限定、結論だけを受け取る読み取り専用の探索委譲などが該当する。
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`などの発生閾値を引き上げて発生時期を先送りする手段は、コンテキスト消費を減らさないため改善提案の候補の外に置く。

## 原因と対策

問題候補が1件以上なら`agent-toolkit:bugfix`を起動し、観測事象、2系統4段階の原因分析、原因分析の品質確認、原因起点の類似見直し、対策・横展開処置・再発防止策及び反映要否を確定する。

ユーザー介入を恒久対策の対象とする場合、介入本文から趣旨を一意に確定できなければ、原因と対策を確定する前に確認する。
振り返り担当は`AskUserQuestion`を発行できないため、その候補を確認事項として呼び出し元へ差し戻し、メインが同じ確認を発行する。
確認を発行できないか回答を得られない場合は、メインが`agent-toolkit:wi-standards`に従い、残る解釈候補、対策が未確定である旨及び回答後に原因と対策の確定から再開する条件をUWIへ記録する。
その候補の対策の確定と、対策のAWIの起草と投入は、確認の完了後に行う。

次の事象は拡張原因分析の条件へ該当するものとして扱う。

- 従来の判断、工程、成果物、要求分類、完了判定のいずれかを変更、撤回若しくは是正したユーザー介入。介入をエージェントの誤り、ユーザーの選好、追加要件のいずれに分類したかにかかわらず適用する
- 同じ成果物かつ同じ責任範囲で発生したレビュー第3ラウンド

再発防止策の必須性、省略できる条件及び良い案を確定できない場合の終端は`agent-toolkit:bugfix`の再発防止策の必須性節に従う。前段の2種の事象で再発防止策を省略できるのは、同節が挙げる2条件に該当する場合に限る。`agent-toolkit:process-wi`だけが起動理由で問題候補が無い場合は、対策なしで完了できる。

目的の適用範囲は、目的と例示の上位概念を対応付けて定め、ユーザーが例示した手段はその上位概念の一例として扱う。同じ目的を満たす候補を比較する。
判断工程の欠陥では、欠陥のある判断を事前に検出するか成立させなくする工程と、その工程を検証する手段を対応付ける。成果物の回帰テストは、その工程の検証手段の一部として扱う。

採用した対策のAWI又はUWIは`agent-toolkit:wi-standards`に従って起草・重複判定・投入する。本文形式とCLI手順は同スキルが定める。

確定した内容は候補別の判定記録の表へ記録する。

## 候補別の判定記録

対象セッション全体から抽出したユーザー介入、auto mode classifierによる拒否、エスカレーション、警告、hook通知を、正規化イベントごとの集約候補として一次選別する。
ユーザー介入、拒否、エスカレーション、未解決証拠は全件を保持する。block又はwarnのhook通知はhook識別子、発動元及びタグを発生源とし、正規化した通知種別ごとの発生件数を数える。同じ発生源では件数降順かつ安定順の上位5種だけを候補とし、各種の安定順で最初のlocatorを代表位置にする。候補へ発生総数と省略locator数を保持し、`candidate-summary.excluded`へ省略総数を機械可読に記録する。各発生源から最低1候補を残す。その他の候補は発生件数と安定順の全locatorを保持する。
恒久対策を要しないことが明確な候補だけを除外し、観測根拠を記録する。不確かな候補は完全分析へ送る。
一次選別の除外は分析の省略を意味し、最終報告では候補を保持する。
完全分析では、抽出器が候補ごとに束ねた有界な`candidate-evidence.jsonl`を先に読み、証拠が不足する候補だけ追加照会する。`candidate_id`と`analysis_group_hint`を起点に、直接的原因と対策の変更単位が同じ候補を1つの`analysis_id`へまとめる。原因分析、類似見直し、再発防止策の確定には`agent-toolkit:bugfix`を適用する。既存キュー項目との照合も完全分析の対象だけへ行う。

全候補の判定は、`候補`、`欠陥判定`、`直接的原因`、`根本原因`、`既存規範が適用されなかった理由`、`処置`の表へ記録する。
一次選別で除外した候補は、候補表の`判定`へ除外の観測根拠を書き、`分析ID`を`-`とする。
完全分析した候補は候補表へ全locator、判定及び`analysis_id`を記録し、原因と処置は分析表へ`analysis_id`ごとに1回だけ記録する。block又はwarnを1回以上発火した各発生源には、確定した処置とその根拠を記録する。現状維持を選ぶ場合は、その発火が規範どおりに停止させた証拠を1件添える。
`permission-denial`の候補にも、確定した処置とその根拠を記録する。許可ルールを変える案で確定した候補は、拒否本文と分類名を証拠として`agent-toolkit:writing-standards`の`references/auto-mode.md`が定めるワークフローの対象へ送る。
抽出した集約候補の全locatorを平坦化し、一次選別集合と最終表のlocatorについて、過不足、重複及び欠落欄を`skills/session-review/scripts/session_review_report.py`で構造検査する。
一時的な振り返り報告は報告の成立に必要な構造を検査する。汎用の文章lintは、登録するWIと恒久成果物へそれぞれの作成規範に従って適用する。
これは既定で従う規定とする。原因分析を省略する候補を記録から失わせると、未処理の欠陥と分析済みの結果を区別できないためである。

表を確定する前に、`candidate-summary`の`included_locators`とその表の`候補`欄が挙げるlocatorの集合が過不足なく一致することを確認する。
一致しない場合は、不足するlocatorごとに行を追加してから確認をやり直す。
工程の簡素化、担当の統合又は委譲の省略をする処理回でも、この確認を実施する。
行への対応は表の行で示す。振り返りの成果の地の文での言及は、行の補足として扱う。

ユーザー介入の趣旨を一意に確定できない候補は、確認又はUWIへの記録を終えてから表へ記録する。
UWIへ記録した行の`処置`には、対策が未確定である旨、UWIのファイル名及び再開条件を書く。解釈候補のいずれかを前提とする対策は、確認の完了後に書く。

本表の判断基準は2つとする。第1に、抽出した全候補を表に残すこと。第2に、欠陥と判定した候補へ、成果物への修正と再発防止策の両方を対応付けることである。
`候補`には観測事象、発生件数及び再取得用locatorを書き、block又はwarnのhook通知では代表位置と省略件数を併記する。
`欠陥判定`には欠陥とするか否かと、欠陥としない場合の観測根拠を書く。`直接的原因`には観測事象を発生させる実行時・データ・設定上の機構を、`根本原因`には`agent-toolkit:bugfix`の原因分析で確定した結論を書く。
`既存規範が適用されなかった理由`には、その事象を統治する既存規範が実行経路で適用されなかった原因を書く。
`処置`には対策、横展開処置と再発防止策に加えて、根本原因を覆うactive項目のファイル名を書く。再発防止策の適用範囲は、誤りの機構が依存する条件で書き、成立条件は`agent-toolkit:bugfix`の`references/root-cause-analysis.md`が定める。
1件の再発防止策で複数の候補を覆う場合は、それらの候補の`根本原因`へ同一の結論を書く。
ユーザー介入に由来する行では、その介入の発生条件と、再発防止策がその条件を成立させなくする対応を書く。

成果物の書き換えと、事象の趣旨を分類した説明は、成果物への修正として記録する。再発防止策と同じ記述を両方へ用いると、その候補は再発防止策を持たない。
処置を確定できない候補は、`agent-toolkit:bugfix`の再発防止策の必須性に従ってUWIを登録する。

## 規範適用による停止の抽出と改訂提案

問題候補のうち、規範を適用した結果として工程の停止、差し戻し、空転又は同じ工程の反復が生じたものを列挙する。
本節の対象は規範を適用した結果として生じた停止であり、既存規範が適用されなかった事象を扱う`## 候補別の判定記録`とは対象が逆である。両者は別の行へ分けて記録する。

抽出の対象は次のいずれかを満たす候補とする。

- 規範が要求する停止、差し戻し又は確認により、そのセッションの工程が先へ進まなかった
- 規範どうしが同じ場面で両立しない動作を要求し、実行主体が適用先の判定へ工程を費やした
- 規範が要求する手順の前提が実在せず、その手順に代替経路の定めが無かった

列挙した各箇所について、確定した処置を`候補`、`当該条文の所在`、`観測した停止`、`採用案`の4列表へ記録し、振り返りの成果へ含める。
`候補`には観測事象と再取得用のlocatorを、`当該条文の所在`にはファイルのパスと節名を、`観測した停止`には停止した工程と契機となった条文の要求を書く。
`採用案`には採用した案とその根拠を書き、条文の維持を選ぶ場合は停止が再現する条件と許容する理由を添える。

採用案が維持以外の場合は、`agent-toolkit:wi-standards`に従ってその条文の改訂をAWIへ登録する。
`agent-toolkit:review-standards`の`review-standards/references/judgment-details.md`「規定の適用可否」が求める規定側の改訂の提案は、本節の登録により成立する。
該当する候補が0件の場合は表を置かず、確認した範囲と0件と判断した理由を振り返りの成果へ含める。

## 分析失敗

準備工程、振り返り担当の起動、親transcript解決又は証拠抽出が失敗した場合は、同じ実効設定で1回だけ自動再試行する。
振り返り担当は再失敗を`analysis_failed`として呼び出し元へ返す。
再失敗を受け取ったメインの処置は`${CLAUDE_PLUGIN_ROOT}/share/session-review-delegate.parent.md`の`## 受領`が定める。

UWIへ記録する場合は、`agent-toolkit:wi-standards`に従い、セッションID、失敗事象、解除条件及び再開工程を記録する。
再開工程は「当該セッションをresumeしてsession-reviewを再実行する」とする。transcriptパスは保存しない。分析は再開したセッションのsession-reviewが担う。全記録がメインのコンテキストへ入ると、以降の判断へ回せる容量が残らない。

手動起動では分析未完了を報告できる。`agent-toolkit:completion-report`から起動した場合は、分析未完了とUWIを同スキルへ返し、元作業の完了を妨げない。
