# 振り返りの判断基準

本書は`agent-toolkit:session-review`の工程3と工程4で、メインが問題候補と会話の流れから問題を選別し、原因と対策を確定するときの判断基準を定める。
工程の順序、準備スクリプトの入出力及び投入の手順は同スキルのSKILL.mdが定め、振り返り結果報告の書式は`agent-toolkit:completion-report`が定める。

## 入力と照会

判断の入力は、準備スクリプトが書いた会話の流れ、問題候補の一覧、セッション統計と、メイン自身のコンテキストとする。
候補一覧の要約と会話の流れで直接原因を確定できない候補に限り、次の手段で原因を確定する。会話圧縮はメインのコンテキストから区間を失わせるだけで、セッション記録には圧縮前のイベントが残る（Claude Codeの`compact_boundary`、Codexの`compacted`）。圧縮された区間の事象も分析の対象とし、`圧縮で実測できない`という判断を、原因を未確定とする根拠にしない。

- 候補一覧が示す記録位置を`atk run-script session-review-evidence --`の`--detail`へ渡し、全文を取得する。検索語から探す場合は`--grep`を使う。抽出器は委譲先（Claude Codeのサブエージェント記録と`agents_server`の子セッション記録）を再帰的に収集するため、委譲先の内部の事象もこの照会で参照できる
- 記録に理由の本文が無い事象（ツールの応答が本文を欠くなど）は、同じツール呼び出しやコマンドを再実行する再現と、実装の読解で原因を確定する

照会と再現を試みても確定できない場合に限り原因を未確定とし、試みた照会と再現、及びそれでも確定できない理由を振り返り結果報告の「対策を見送った問題」へ書く。記録が実在しない場合（記録ファイルの削除、抽出器が`unresolved-delegation`として報告する委譲先）がこれに当たる。
照会と再現を経ても介入の趣旨などユーザーの判断を要する要素が残る候補は、推測で確定せず、`agent-toolkit:confirmation-and-uwi`に従ってユーザーへ確認する。

## 一次選別

問題候補と、会話の流れから見つけた問題を対象とする。会話の流れから見つけた問題は、同じ事象を指す候補とまとめ、対応する候補が無いものは独立して原因分析へ進める。
恒久対策を要しないことが明確な候補だけを除外し、除外の根拠を振り返り結果報告の「対策を見送った問題」へ書く。不確かな候補は分析へ送る。

- 失敗したコマンドとツール: 終了コード、コマンド、診断から恒久対策の要否を判定する。恒久対策を要しないことが本文から明確な候補は除外できる
- 委譲返却: 抽出器が正常な完了だけの返却を除いた残りを、本文の内容まで判定する。想定外事象を持つ返却は、その事象を判定する。明示的な`needs_escalation`は独立した候補として扱う
- hook通知: 候補一覧にはblockかwarnの通知だけが載る。blockかwarnを1回以上発火した各発生源には、欠陥判定にかかわらず、規範、判定条件又はフック撤去のいずれかの改善案を1件以上対応付ける。現状維持を選ぶ場合は、その発火が規範どおりに停止させた根拠を書く
- 権限拒否: 確定した処置と根拠を書く。許可ルールを変える案で確定した候補は、拒否本文と分類名を証拠として`agent-toolkit:writing-standards`の`references/auto-mode.md`が定めるワークフローへ送る
- 過去の振り返り又はキュー処理で不採用が確定した案は、新しい観測又は要件変更を同じ候補へ対応付けられる場合だけ再評価し、いずれも無い場合は提案の集合から除く

### ユーザー介入の判定規則

ユーザー介入は従来の判断を是正した事象であり、原則として再発防止策を要する。ユーザー介入の候補と会話の流れで見つけた是正は、次の3区分に当たる場合だけ除外でき、区分と根拠を振り返り結果報告へ書く。

- `single-inquiry`（単発の照会）: 進捗、所要時間、状態のいずれかを尋ねるだけで、是正、停止、方針変更、将来の振る舞い変更のいずれも含まない発話。根拠は当該発話の本文
- `non-changing-request`（判断を変えない追加要求）: 従来の判断、工程、成果物、要求分類、完了判定のいずれも変えない要求。根拠は変えていないことを示す本文の箇所
- `unexplained-refusal`（理由の無い拒否・中断）: ツール実行の拒否・中断の定型本文で、直後のユーザー発話が理由や是正を述べていないか、直後の発話が無いもの。根拠は直後の発話の本文又はその不在。直後の発話が是正なら、拒否・中断をその発話と同じ問題としてまとめる

これ以外のユーザー介入は欠陥として拡張原因分析の対象にする。「ユーザーの選好」「追加要件」「既存規範で扱える」を根拠とする除外と非欠陥判定は認めない。これらの分類は介入が生じた原因の説明であり、同じ是正を次のセッションで防ぐ根拠にならないためである。
照会に是正、停止、方針変更、将来の振る舞い変更のいずれかが併記されている場合は、該当部分を是正として扱う。介入の趣旨を一意に確定できない候補は除外せず、残る解釈候補をユーザーへ確認する。回答を得られずUWIへ送られた場合は、そのUWIのファイル名を再発防止策の所在として報告し、解釈候補のいずれかを前提とする対策は回答後に確定する。

## 原因と対策

次の事象は拡張原因分析の条件に該当するものとして扱う。

- 従来の判断、工程、成果物、要求分類、完了判定のいずれかを変更、撤回若しくは是正したユーザー介入。介入をエージェントの誤り、ユーザーの選好、追加要件のいずれに分類したかにかかわらず適用する
- 同じ成果物かつ同じ責任範囲で発生したレビュー第3ラウンド

再発防止策の必須性、省略できる条件及び良い案を確定できない場合の終端は`agent-toolkit:bugfix`の再発防止策の必須性節に従う。前段の2種の事象で再発防止策を省略できるのは、同節が挙げる2条件に該当する場合に限る。再発防止策なしと判断した問題は、評価した案と採らない理由を振り返り結果報告の「対策を見送った問題」へ書き、この報告（自律モードでは完了報告のUWI）で同節が求める事後承認型UWIを兼ねる。
目的の適用範囲は、目的と例示の上位概念を対応付けて定め、ユーザーが例示した手段はその上位概念の一例として扱う。判断工程の欠陥では、欠陥のある判断を事前に検出するか成立させなくする工程と、その工程を検証する手段を対応付ける。成果物の回帰テストは、その工程の検証手段の一部として扱う。

欠陥と判定した問題では、`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「処置の階層」の3層を区別してAWIの本文へ書く。成果物の書き換えと、事象の趣旨を分類した説明は、成果物への修正として扱う。再発防止策と同じ記述を両方へ用いると、その問題は再発防止策を欠く扱いになる。既存規範を守るという宣言は再発防止策に当たらない。
既存規範が実行時に適用されなかった問題では、`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「再発防止策の必須性」の未適用規範の是正原則で原因を特定し、条文の想起性改善案と、改善後の条文が誤りの機構を想起させる見込みの根拠をAWIへ書く。判定には`agent-toolkit:writing-standards`の`references/llm-characteristics.md`「知識の想起」「コンテキスト配置」「指示の明瞭さ」を用いる。
1件の再発防止策で複数の問題を覆う場合は、それらの問題の根本原因へ同一の結論を書く。ユーザー介入に由来する問題では、その介入の発生条件と、再発防止策がその条件を成立させなくする対応を書く。

同じ概念を持つ規範、実装、テストの組についても互いの契約を比べる。単独の文書内では成立していても組み合わせると矛盾する契約は、矛盾した判断の生成元、原因、全消費側を特定して対策へ接続する。単なる重複文字列は欠陥の対象外とする。

## 既存キュー項目との重複確認

AWIの起草では、`agent-toolkit:wi-standards`の条件付き重複判定に従って未終端の既存項目と比べる。既存項目が問題の事象、原因及び完成条件を全て覆う場合は新しいAWIを投入せず、そのファイル名と対応根拠を振り返り結果報告の「確定した問題と対策」へ書く。一部だけを覆う問題と新しい証拠を持つ問題は、不足分をAWIへ起草する。
既存規範が適用されなかった問題では、採用済みの振り返り由来の項目との反復を`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「再発防止策の必須性」に従って判定する。反復した問題では、その事実、項目のファイル名、前回採用した再発防止策の段、前回の処置で再発を防げなかった条件をAWIへ書く。
採用済み項目の本文検索には`atk wi grep <Pythonの正規表現> --state=adopted --source=session-review --target-repo=<対象リポジトリ> --skip-pull`を使い、終了コード1は一致0件として扱う。

## 規範適用による目的逸脱

規範を適用した結果として工程の停止、差し戻し、空転、同じ工程の反復又は目的に照らして不適切な判断や成果物が生じた事象を列挙する。既存規範が適用されなかった事象とは原因を分けて扱う。

- 規範が要求する停止、差し戻し又は確認により、そのセッションの工程が先へ進まなかった
- 規範どうしが同じ場面で両立しない動作を要求し、実行主体が適用先の判定へ工程を費やした
- 規範が要求する手順の前提が実在せず、その手順に代替手段の定めが無かった
- 規範の字面を満たした結果、元の依頼の要求単位を満たさない判断や成果物になった

列挙した各箇所について、条文の所在（ファイルのパスと節名）、観測した停止、採用案とその根拠を書く。条文の維持を選ぶ場合は、停止や目的逸脱が再現する条件と許容する理由を振り返り結果報告の「対策を見送った問題」へ添える。維持以外の採用案は、その条文を改訂するAWIとして起草する。`agent-toolkit:review-standards`の`references/judgment-details.md`「規定の適用可否」が求める規定側の改訂の提案は、この改訂により成立する。

## 所要時間の分析と改善

セッション統計から、寄与の大きい工程と反復を特定し、品質を保ったまま単位時間あたりに処理するユーザー由来のWIの件数を最大化する改善を確定する。エージェント由来のWIは別に数える。所要時間の短縮とトークンコストの削減は、この尺度を高める手段として扱う。

- 短縮の対象は律速区間とする。律速区間は統計の律速区間（メインだけの区間とagent thread別の排他区間）であり、未計測のthreadは判定材料から外して、その対象を記録する。工程別の合計時間は判断材料の一部として扱う
- 対象は必須工程と検収範囲を含む全ての工程とし、`agent-toolkit:process-wi`と`atk wi process-loop`が定める手順、その手順が従う規範、`agent-toolkit:session-review`の工程と準備スクリプトを含める。工程の撤去、順序の変更及び並行化を候補とする
- 手順と規範の撤去、変更又は置換を選ぶ前に、条文が示す保護対象と成果、その条文を導入した変更及び対応する計画ファイルから導入目的を調べる。その目的を別の手段でより低い費用で満たせると確定した場合に採用し、確定できない場合は維持する
- 重複した検証の排除と待ち時間の活用を観点へ含める。CIが同じ検証を担う環境では、公開前のローカルの全体検証を重複として扱う。CIの所要時間が長い環境では、CIが失敗する見込みが高い場合に限り、変更したファイル、変更した定義の直接消費側及び同じ契約を保持する箇所へ部分実行を先に行う
- 短時間に反復したコマンドも、呼び出しごとの所要時間と律速区間への寄与から見直す（努力目標。短い操作も反復する回数に応じて待機と再実行の時間を費やす）。入力形式の誤りによる反復は最下層のヘルプ又は仕様の取得を先行させ、成功した同種の操作の反復はそのコマンドが公開する複数対象の指定で統合できるかを比較する
- コンパクションは回数と合計時間を記録し、所要時間が不明な回は件数として残す。回数はコンテキスト消費そのものを減らす手段（出力量の大きい調査・検証の委譲による分離、初回取得の範囲の限定、結論だけを受け取る読み取り専用の探索委譲など）で削減する。発生閾値を引き上げて発生時期を先送りする手段は、コンテキスト消費を減らさないため候補の外に置く
- 機械的な抽出が返す候補の区分のうち、改善へ結び付いた件数が少ない区分は、抽出の条件を限定する候補とする
- 案の採否は品質への影響と、トークンコストと保守コストの大幅な増加の有無で判定する

改善ごとに、1セッションあたりの短縮見込み秒数、その見込みが依拠する統計の値、見込みが観測値と推定値のいずれに基づくかをAWIへ書く。推定では算出式と前提を書く。短縮前後の比較は同じ観測済み区間の集合だけで行い、未観測区間を0秒又は推定値として加えない。
所要時間目標が定められている場合は、短縮見込みと目標値の比較結果を書き、目標値を超える場合は超過分と、その超過を生じさせる律速区間を併記する。超過は改善の起点として扱い、振り返りの完了条件の外に置く。有効な処置を特定できない場合は、観測結果と理由だけを振り返り結果報告の「対策を見送った問題」へ書く。
所要時間、トークン量及びリクエスト数を利用者が読む文面へ書く場合は、セッション統計の値だけを典拠とし、比率を示す場合は`agent-toolkit:writing-standards`の`references/session-records.md`「集計値の典拠」が定める基準差を同じ本文へ併記する。
