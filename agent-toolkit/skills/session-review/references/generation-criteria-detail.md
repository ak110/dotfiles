# session-reviewの提案基準

本書は、メインがadvisorの問題一覧と再抽出証拠から改善候補を確定する基準を定める。
advisorは問題と証拠位置の列挙だけを担い、本書が定める判断をしない。
振り返りの起動、証拠抽出、表示、投入手順は`agent-toolkit:session-review`が所有し、本文書では扱わない。

## 提案する候補

この節の候補化判定はメインが所有する。

次の順に評価し、先に該当した層で候補化の可否を決める。

候補層の判定前に、メインは`atk mq list --status=active --target-repo=<repo-path> --skip-pull`を一度だけ実行し、`processing`配置を含む対象リポジトリの唯一のactive一覧を取得する。取得した各項目について、状態が`active`、対象リポジトリが同一、`process-loop`で処理可能であることを検証する。第1層から第3層までの全候補層の抑止判定は、この検収済み一覧を共通に用いる。

1. 問題一覧と再抽出証拠から、ユーザー介入、破壊的結果、誤成果物、手戻り、再設計を要した計画不備、実測したフックの誤検出・誤ブロックを確認する。これらは単発でも候補にする。
   第1層に該当する事象のうち、証拠からエージェントの誤りが利用者介入を招いたと確定した事象と、明白なコスト浪費を観測した事象では、既存フィードバック、既存規範、重複及び過剰設計を理由とする抑止判定の前に、`agent-toolkit:bugfix`の深掘り契約を完了する。
   直接的原因、混入要因、動機的要因、見逃し原因、根本原因と原因起点の類似見直しを確定する。続いて、是正処置・横展開処置・再発防止処置を確定する。
   根本原因を成立させる各単位は、現行実装・テスト若しくは反復しない実測により有効性を確認した実装済み処置へ対応づける。検収済み一覧に含まれる、同一対象リポジトリで`process-loop`が処理できる有効なactiveフィードバックも対応先にできる。
   activeフィードバックを被覆とする条件は、単なる処理可能性だけではない。フィードバック本文または対応計画が、対応づける各根本原因単位と、その単位に必要な是正処置・横展開処置・再発防止処置の全てを覆う根拠を確認する。既存規範が守られなかった場合は、規範の存在を有効性の根拠にせず、規範が機能しなかった原因を処置へ含める。
   原因単位の被覆が部分的な場合は未被覆単位だけを候補とし、全単位が被覆されている場合だけ「提案無し」を許可する。
   activeフィードバックを被覆とする場合は、ファイル名、状態、対象リポジトリ及び被覆単位を報告する。本文又は対応計画が各根本原因単位と必要な処置の全てを覆う根拠、`process-loop`で処理できる根拠及び非重複理由も報告する。処理不能・失効済み・終端済みの項目は被覆に数えない。
   原因分析と各単位の被覆確認は、候補化及び抑止条件の判定に優先する。抑止した場合も原因分析の結果を報告へ残す。
   「提案を抑止する条件」のいずれかに該当して提案を確定しない場合は、重複による抑止では対応する既存項目のファイル名又は規範の節名を、その他の抑止条件では該当した条件と成立の判定根拠を報告へ記載する。
2. コンテキスト効率や計画段階の摘出率を大きく改善する事象は、効果を観測事実で示せる場合だけ候補にする。
3. その他の単発ミスは、同一セッション、既存のフィードバック、git履歴のいずれかに反復証跡がある場合だけ候補にする。

レビューが正常に検出した設計判断や公開仕様上の指摘は、検出された事実だけを理由に工程追加へ結び付けない。
初回実装で防げた同型指摘だけを、委譲文、計画粒度、既存規範、機械検査の改善候補として扱う。

同じ計画・基点から続く累積実装を、同じ責務系統のレビュー担当が第3回以降も指摘した場合は原因調査の対象とする。
2回以下、結果未返却、別成果物、別責務系統は合算しない。レビュー対象又は責務系統を転換した場合は、転換後の最初のレビューを第1回としてカウントを取り直す。
レビュー側と初版作成・指摘反映側の原因を別々に確定し、抑止条件に該当しない限り原則として改善提案を1件以上確定する。

### ユーザー入力イベントの被覆と発火時点

advisorが全利用者入力を点検し、メインは確認済みイベントID一覧を機械検収する。問題一覧についてだけ、メインが介入、原因、処置及び発火時点を確定する。

問題一覧の各証拠は、取得元で実行した完全な引数列と順序を表す`query`と、その照会のJSONL出力内で対象イベントが現れる0始まりの`event_index`だけをlocatorとして保持する。異なる`--detail`引数列は別のqueryとして扱い、まとめて再照会しない。
既定の利用者入力を含む全ての照会結果へ同じlocator契約を適用する。
`query`へ利用者入力や自由形式の本文、grepの検索本文を記録せず、grepの結果は完全な引数列を持つdetail照会へ変換する。
問題一覧は利用者入力又は自由形式の本文を逐語転記せず、問題を判別できる要約と、問題の観測に残る`unverified`を保持する。
全ての利用者介入が問題一覧と証拠位置で確認できる場合だけ、メインは介入の分類、原因、予防処置及び介入前の発火契機を確定する。

## 根本原因と反映先

この節の根本原因の一般化、行動主体、対象ファイル単位の反映先及び概念比較はメインが所有する。
ファイル内の節・関数・行、同期対象、実装根拠による代替案の不採用を含む反映先の実在・整合は、メインが「提案の確定」で照合する。

- 表層の固有事象から、同じ原因で起きる事象を包含する根本原因へ遡る。
- 原因候補を元のユーザー要件へ対応付け、複数の症状を包含する最も早い判断の誤りを根本原因とする。
- 反映先を確定する前に、当該規範が行動を変える主体を特定する。
- 対象文書がその主体の読む文書であることを確認する。
- 委譲先向けのagent定義・タスク文書は委譲先の行動だけを変えるため、呼び出し元の行動を変える規範は呼び出し元が読むスキル・手順へ置く。
- 上位の要件解釈違反で説明できる個別の確認漏れは検証項目として保持できるが、根本原因には採用しない。
- 固有名詞を除いても成立する規範は一般化し、固有名詞は必要な具体例へ分離する。
- 既存の仕組みを変える候補では、目的、現行の寄与、副作用、保守費を確認する。
- 維持、内部修正、簡素化、別手段への置換、撤去を同じ階層で比較する。
- 反映先はコード・自動検査、局所文書、プロジェクト規範、配布規範、条件付きスキルの順に比較する。
- 高頻度で常時ロードされる文書への追記は、同じ効果を条件付き読込や機械検査で得られない場合だけ選ぶ。

## 総ライフサイクルコスト

この節の概念比較と候補の採用後に必要な契約同期の実地検索はメインが所有する。

候補ごとに、初回実装費だけでなく次を比較する。

- 常時消費するコンテキスト
- 委譲、再試行、状態管理、フック起動の恒常費
- ユーザーと実装者の運用負担
- 誤検出、誤ブロック、情報欠落などの副作用
- 変更の検証、配布、将来の保守費

候補がagent定義、タスク文書・作業手順の参照文書、hook、script、規範文書などに記載された操作、判断条件、
状態遷移又は入出力契約を新設又は変更する場合は、採用候補に限りメインが、反映先の当該節に加えて同じ契約を定義・参照・
実行・検収するファイルを実読する。候補の対象パス、節名、agent・タスク文書・hook・scriptの識別子、入出力フィールド名、
変更する規範文を対象リポジトリ全体で検索し、テスト設定と既存テストの配置・命名へ照合する。
メインは関連ファイル、契約同期テスト及び同時改訂を要する条文・テストを列挙し、その費用を初回実装費へ含める。

防止効果が総費用を上回る根拠を示せない候補は抑止する。
候補ごとに、何もしない案、既存の仕組みの修正または撤去、他候補との統合を同じ階層で比較し、
単純な案が目的を満たす場合は新しい工程、規範、委譲を追加しない。

## 提案を抑止する条件

既存規範またはactiveなフィードバックとの重複を含む全ての抑止条件の判定はメインが所有し、候補の不採用基準とする。

### メインが所有する抑止判定

- 既存規範またはactiveなフィードバックと実質的に重複する（既存規範への違反が観測された事象では、既存文面の再掲だけを重複とし、違反原因に対応する別階層の対策は重複としない）

次のいずれかに当たる候補は提案しない。

- タスク固有の一時的事情だけに依存する
- 軽微な好み、表記、体裁に留まり、公開契約や実在欠陥へ影響しない
- 将来の仮定だけに依存し、観測事象がない
- 対策が失わせる成功経路や情報を評価していない
- 観測主体が利用できない情報を判定条件に使う
- 恒久対策ではなく今回の修正内容の再掲に留まる

既存条文が守られなかった場合は、単純な文面追加も対策なしも既定にしない。規範が既に存在することを対策不要の根拠にせず、違反の原因（文面の曖昧さ、実行時に参照されない配置、機械的検証の欠如）を判別し、規範追加以外の階層（機械検査、フック、工程・入力構造の変更）の対策を候補として評価する。同じ階層の追記を選ぶ場合はそれが有効である根拠を示し、対策を見送る場合は再発の頻度と影響の評価を見送り根拠として示す。

## 既存判断との照合

この節はメインが所有する。

- 候補確定前に、既採用のユーザー方針、不採用済みの同一主題、active・processing項目との重複を照合する
- 規範追加候補は、同じ計画内で既存規範を削減又は置換できるかを評価する
- ユーザーが固定した方針を、自己生成の改善提案によって緩和しない
- `process-feedbacks`固有の採否書式や後始末を本文書へ持ち込まない

## 報告契約

この節は、メインが確定する改善候補の必須情報を定める。

候補ごとに次を報告する。

- 観測事象と裏付け手段
- 根本原因
- 推奨する恒久反映先（対象ファイル単位）と変更内容。ファイル内の節・関数・行及び同期対象はメインが確定する
- 期待効果
- 総ライフサイクルコストと副作用（恒常費・副作用・保守費の概念比較）
- 比較した代替案と不採用理由（概念比較。実装根拠・リポジトリ照合による不採用はメインが確定する）
- 新規の機構（ファイル、状態、受け渡し経路又は専用コマンドなど）を設ける候補では、同じ情報又は効果を
  既存コマンド若しくは既存経路で得られるかを確認した手段と結果。該当しない候補は「非該当」
- 実害がありエージェントの誤りが利用者介入を招いた問題について「提案無し」とする場合は、4原因区分・根本原因・類似見直し・三層処置及び各根本原因単位の被覆根拠を報告する。実装済み処置を使う場合は検証結果を記録する。反復しない実測を使う場合も記録する。activeフィードバックを使う場合は、ファイル名、状態と対象リポジトリを記録する。被覆単位、本文又は対応計画が各根本原因単位と必要な処置の全てを覆う根拠、`process-loop`処理可能性と非重複理由も記録する
- 未検証事項。ない場合は「なし」

`未検証`へ置けるのは、解決結果が候補の採否を変えない事項に限る。
費用見積りの前提、`提案する候補`第3層が要求する反復証跡及びtranscript証拠で確定できる事項は報告前に確定する。
反映先での成立性・既存手段による代替可否・契約同期・候補の抑止はメインが確定する。

裏付けを取れない主張は`未検証`と明記し、確定事実として扱わない。
