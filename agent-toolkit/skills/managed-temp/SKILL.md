# managed-temp

一時ファイルの配置場所や、作業用ディレクトリの作成・回収に関する手順を定める。

領域の作成や回収には、対象ファイルを操作できるホスト環境が必要である。ファイル操作ができない環境では、保存する内容や保存先に求める条件を整理した原稿を返し、実際の保存と回収はClaude CodeまたはCodexで行う。[文章の品質基準](references/quality-standards.md)はこのスキルフォルダー内で参照できる。

## 一時rootと自動削除

managed-tempの一時rootは次のディレクトリとなる。

- Linux: `${XDG_CACHE_HOME:-~/.cache}/agent-toolkit/managed-temp`
- macOS: `~/Library/Caches/agent-toolkit/managed-temp`
- Windows: `%LOCALAPPDATA%\agent-toolkit\managed-temp`

一時root直下の各ディレクトリや通常ファイルは、配下の最終更新から7日を経過すると、`atk`の実行時に自動的に削除される。未来の更新時刻は、現在以前の状態変更時刻へ置き換えて判定する。ただし、領域外の実在するgitdirと逆参照が一致する登録済みworktreeを含む領域や、使用中の配布物の複製は自動削除の対象外とする。

## セッションのmanaged-temp

SessionStartは、セッションごとに一時root直下へ専用の作業ディレクトリ（セッションのmanaged-temp）を準備し、その絶対パスをコンテキストへ通知する。同じ`session_id`で再開した会話や、会話圧縮が行われた後にも同じパスが通知される。
同一セッション内で参照するターンまたぎの入力、完成条件の証拠、検証結果、委譲先へ渡す成果物、および引き継ぎ記録は、この領域（サブディレクトリを含む）へ配置する。セッション終了後やWIの完了後に参照する記録（後続工程の解除条件、取得すべき記録、再開手順など）は、作成時に対象AWIの本文または計画ファイルの`## 進捗ログ`に記載する。最後に参照する時点まで確実に残る保存先を選択する。
作業目的の退避ファイル、差分比較用の一時ファイル、中間出力なども作業ツリーの外に配置し、コミット対象の成果物と混ざらないようにする。

セッションのmanaged-tempディレクトリ自体の回収は、自動削除に任せる。同一の`session_id`で再開した会話に同じ領域を引き継ぐためである。
`Agent`ツールで起動されたサブエージェントには、担当専用の子ディレクトリが通知される。一時ファイルはその子ディレクトリへ配置する。親ディレクトリは委譲元から渡されたファイルの読み書きに使用してよい。

## 作業用ディレクトリ

元資料から再生成できる抽出・比較用の複製や検証用の環境は、永続的に保存する成果物と生存期間を分ける。
用途ごとに、通知されたセッションのmanaged-temp内へ`mktemp -d '<セッションのmanaged-tempの絶対パス>/<用途>-XXXXXXXX'`を実行して作業用ディレクトリを作成する。参照を終えた作成者は、すべての消費工程と起動プロセスが終了した後に`rm -r -- <作成した絶対パス>`で回収する。Windows PowerShellでは`New-Item -ItemType Directory -Path <絶対パス>`で作成し、`Remove-Item -LiteralPath <作成した絶対パス> -Recurse -Force`で回収する。
TMPDIRなどを作業用ディレクトリに向けたテスト用の一時ディレクトリも、同様に回収の対象とする。
過去のエージェントが残した作業用領域は、`agent-toolkit/rules/02-agent-operations.md`「プロセス終了の安全規定」の共通判断で調査し、現在の利用と必要な成果を保護して不要な範囲を回収する。セッションのmanaged-tempの7日保持と証拠の寿命、使用中の配布物の保護は維持する。
Git管理下の作業ツリーを検証用に複製する場合は`git worktree add`やcloneで作成し、仮想環境などの依存環境はパッケージマネージャーの同期機能で作成する。worktreeは`rm`を実行する前に`git worktree remove`で登録を解除する。
作業ツリーのファイルを複製する際は、入れ子のworktreeやgitignore対象の仮想環境について、キャッシュとのハードリンクを解除した実容量で複製する。
後続ターンへの入力や、後から参照される証拠・検証結果は、回収対象の作業用ディレクトリの外側（セッションのmanaged-temp直下など）へ残す。

## 一時root直下に作成する領域

次の用途では、作業用ディレクトリを一時root直下に`mktemp -d '<一時root>/<用途>-XXXXXXXX'`で作成する。

<例>
セッションのmanaged-tempの通知を受け取っていない場合: ディレクトリを作成し、回収は7日間の自動削除に任せてよい。
Git worktree、検証用clone、Git fixtureなど`.git`を含む領域を配置する場合: ディレクトリを作成し、作成した工程が不要になった時点でworktreeの登録を`git worktree remove`で解除した後に`rm -r --`で回収する。登録済みworktreeの保護を解除し、7日を待たずに容量を返すためである。
別のファイルシステム名前空間（Dockerコンテナーなど）から同じパスへアクセスさせる場合: すべての消費主体からアクセス可能な既存の共有ディレクトリを確認し、`mktemp -d -p <共有先の絶対パス>`で作成した上で、作成者が明示的に回収する。
</例>

process-wiのレーンworktreeは、対象リポジトリの主作業ツリー配下にある`.claude/worktrees/process-wi-<レーン識別子>`に`atk lane create`で作成し、worktree、branch、および所有セッションと紐付けて登録する。統合後も追加の変更に備えて保持し、全工程と外部プロセスの終了後に`atk lane delete`で回収する。回収順序は、対象リポジトリが`atk lane create --commands-file`に渡したdeleteコマンド、worktree、branch、以前の構成でworktreeを配置していた個別managed-tempの順となる。通常終了時の`atk agents-exit-session`や、process-loopが子セッション終了後に行う処理も、同様の回収処理を呼び出す。メインエージェントは所有資源を手作業で再登録しない。未統合、dirty、稼働中、状態不明、または一部失敗した資源をCLIが保持した場合は、メインが共通判断で理由を調べる。解消した対象は同じ回収操作で再判定し、保護する成果や現在の担当、残るユーザー判断と再開条件がある対象を保持する。登録情報や回収結果への参照は、回収対象のworktree、branch、個別managed-tempとは別の状態ディレクトリに保存し、回収結果は通常の7日間保持に任せる。統合や回収の再開に必要な選定情報、rebase後の対応表、検証記録も、`atk lane`が所有登録と同じ状態ディレクトリに保持するため、managed-tempの7日間保持を前提としない。選定原本も所有登録の選定情報も存在しない古い登録の作業ツリーは、`atk lane recover --session-id <所有session>`で解放する。次回開始時は`atk lane delete --list`を実行して、残存理由と再開すべき操作を確認する。
`.git`を含む領域に配置するものは、作業ツリー本体や、それと一緒に破棄してよい一時的なファイルに限る。完成条件の証拠、検証記録、引き継ぎ記録、完了報告が参照する保存物（検証出力や手動観測の記録など）、および委譲先に指定する保存先は、同一セッション内で利用する場合、委譲元または委譲先セッションのmanaged-tempに配置する。セッション終了後やWI完了後に参照する記録の保存先は、前節「セッションのmanaged-temp」に従う。このように分けておくことで、作業領域の回収時に内容を個別に確認することなく安全に破棄できる。

## 設定領域を変更する前の一時バックアップ

バージョン管理や自動同期が有効な設定領域（etckeeperで管理されている`/etc`など）を変更する場合は、変更前の版をその領域のローカル履歴から復元できるのであれば、その履歴をバックアップとして利用する。別の複製が必要な場合はmanaged-tempに配置する。
設定領域内に配置したファイルは、自動コミットによって履歴に取り込まれ、後から削除してもローカル履歴やリモートへ送信された履歴に残ってしまう。ローカルの自動コミットと外部への送信状況をそれぞれ確認し、変更完了後は双方に作業用ファイルが混入していないことを確かめる。
