# WI原稿の投入前レビューの起動と検収

```text
起動対象: wi-draft-review.subagent.md
```

投入前レビューは、親エージェントが意味を検収しない作成主体（専念型のWI投入担当、`add-awi-by-user`のメインなど）が、原稿の保存前に独立したレビュー担当から受けるレビューである。
検収の品質水準は`agent-basics:review-standards`「文章成果物の実害」の作業項目の基準とし、意味を変えない表現だけの修正は保存の条件から外す。
付随型では`agent-toolkit:atk-mode/roles/add-wi.parent.md`の委譲元による検収を使う。
起動の要否は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「直接起草と独立した検収の選択」で判定する。
`add-awi-by-user`では同節の4条件によらず毎回行い、考慮漏れの点検資料の全類型もこのレビューで検収する。
それ以外で同節が直接起草を選べるとする原稿には、メインによる意味の検収と機械チェックを使う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| add-awi-by-userの投入前レビュー結果を検収する前 | `agent-toolkit:atk-mode/references/omission-check.md` |

## 入力

<!-- 生成元: skills/atk-mode/roles/wi-draft-review.subagent.mdのrequired_inputs・optional_inputs。手動編集しない。 -->
入力の定義はこの起動契約とagents_serverの`start`の検査が所有する。
役割固有の入力（`extra_params`）はこの契約の入力一覧で完結する。
通常起動（`mode: delegate`）の共通の準備: 起動の前に`agent-toolkit:atk-mode/references/work-contract.md`に従う全体作業契約を用意し、`extra_params`とは別の公開入力`whole_contract_path`へ絶対パスを渡す。

- 必須入力名: `要求と出所`、`成立性の証拠`、`引き継ぎ記録先`
- 任意入力名: `確認段階`、`方針`、`原稿`

各資料は実在するファイルの絶対パスで受け取り、原稿、出所、証拠には同じ既存ファイルを指定してもよい。

- `確認段階`: `方針`か`本文`。
  省略時は`本文`として扱う。
- `要求と出所`（両段階）: 原文、確定した要件、技術判断、割り当て、由来を記録したファイル。
  原稿や起草者の分類より先に利用主体、開始状態、到達結果を確定できる原文を含める。
  原文のユーザー発話（原稿の`## ユーザー指摘の逐語引用`に載せたものを含む）ごとに、扱う`要求識別子`と処置（`## 反映内容と反映先`の項番か`## 原因分析`の行）、または扱わない理由を対応付ける。
- `成立性の証拠`（両段階）: 観測結果、原因、採否の根拠、引用と構造チェックの結果、dry-runの入力原稿と抽出保存先の対応を記録したファイル。
  資料起点の要求では提供機能と消費形態、操作手順、4方式の比較を、規範の差分では成立する条件付き参照と、既存の充足と追加の差分の対応を既存記録から含める。
  観測された問題への対処では、既存手順の対策一覧を含める。
- `方針`（方針段階）: 対象、変更後の挙動、範囲、除外、完成条件、採否と実現方式を記録したファイル。
  完成原稿と本文専用の読者別探索は、本文段階で扱う。
- `原稿`（本文段階）: 単一原稿の絶対パスか、複数原稿の対応表を保存したUTF-8のJSONファイルの絶対パス。
  対応表は空でない配列で、各要素は`要求識別子`（一意な文字列）、`原稿`、`要求と出所`、`成立性の証拠`（後ろの3項目は読める絶対パス）を持ち、任意の`ユーザー向け部分`にはdry-runの抽出保存先の絶対パスを置く。
  共通の出所や証拠は、同じパスを指してよい。
- `引き継ぎ記録先`: 省略と継続の扱いは`agent-toolkit:atk-mode/references/delegation-prompt.md`「引き継ぎ記録先」に従う。

<!-- input-contract:wi-draft-review:end -->

本文段階の入力は、作成主体が次の順でそろえる。

1. 保存前に原稿を原文と読み比べ、新規は`atk wi add --dry-run --body-file <原稿の絶対パス> --source <起動スキル由来のsource>`、更新は`atk wi edit <WI名> --dry-run --body-file <原稿の絶対パス>`で検証する。
   `source`は`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と`source`」に従い、原稿のfrontmatterで指定済みなら`--source`を省ける。
   UWIの新規では`--type=uwi`と回答形式の指定も加える。
   受領済みの抽出がある時は`--compare-opening-file <抽出の絶対パス>`も加え、複数原稿の対応順と不一致時の更新は`agent-toolkit:atk-mode/references/draft-semantic-review.md`「ユーザーが読む部分」に従う。
2. 結果と、dry-runが返した入力原稿と抽出保存先の対応を成立性の証拠へ記録し、原稿、要求と出所、成立性の証拠の各ファイルを直接渡す。
   対応表の`ユーザー向け部分`には抽出保存先の絶対パスを置き、原稿を変えたらdry-runをやり直して対応を更新する。
   共通の根拠説明や対応表は、渡された形式のまま扱う。
3. 同時に用意した原稿は対応表でまとめ、まだ届いていない原稿を待つだけの待機は置かない。
   対応表を使う時も`要求と出所`と`成立性の証拠`には共通資料の絶対パスを置き、要求ごとの対応は対応表で保つ。

## 起動

確認資料を「入力」に従ってそろえた後、`agents_server`の`start`を呼び、`cwd`に対象リポジトリの絶対パス、`subagent_md_path`に`wi-draft-review`、`extra_params`に「入力」の値を渡す。
工程別の`model_type`は役割表で解決される。

## 検収と修正

1. 方針段階と本文段階のどちらでも、指摘を受け取ったら、採否と修正を確定する前に呼出元が定める分類と処置を適用し、その結果を次の確認へ引き継いでから修正と再判定へ進む。
   `add-awi-by-user`の分類は`agent-toolkit:atk-mode/playbooks/add-awi-by-user.md`「指摘の分類と処置」に従う。
   実ユーザーの発話やWIの記入欄による介入の評価は、分類元によらず`agent-toolkit:atk-mode/playbooks/user-utterance.md`「ユーザー介入と確認の判定」へつなぐ。
2. 返却の確認段階と対象資料が入力と一致するかを確かめる。
   方針段階では、要求・調査根拠と方針の対応と未解決の指摘を検収し、合格したら呼出元が定める承認条件に従って本文を起草する。
   本文は同じsessionへ`send_message`の`instruction: 本文確認`と、`extra_params`の`原稿`、`要求と出所`、`成立性の証拠`（全て実在ファイルの絶対パス）で渡す。
   方針の合格は本文の合格として扱わず、本文の検収を経てから保存する。
   到達できない時は`agent-toolkit:atk-mode/references/work-contract.md`「引き継ぎ記録」に従う。
3. 本文段階では、返却された要求識別子と原稿の集合が入力と一致するかを確かめ、要求ごとの意味の判定、検収者による冒頭の判定、読者別探索の識別子・結果・証拠を追跡する。
   各判定の`読者別探索:`欄を確かめ、識別子があれば返却を読んで、ユーザー向け部分への確認結果であることを確かめる。
   再利用なら前回の抽出との一致を、起動条件に当たらないなら条件と自己確認の根拠を確かめ、行の欠落や無効な省略は合格判定でも同じ担当へ差し戻す。
   `add-awi-by-user`では、点検資料の全類型の判定と処置が原文、原稿、調査根拠へ対応するかを確かめ、ユーザーの判断が要る指摘はメインがその場で確認して本文へ記録する。
   合格した原稿は他の原稿の修正を待たずに保存してよく、追加の原稿は新しい識別子で既存の担当へ渡して取得済みの共通資料を再利用させる。
4. 指摘の採否と再調査の要否は、`agent-basics:review-standards`を適用して作成主体が確定する。
   要件との不一致の指摘は、前提の値の出所を、元の要求、実際の回答、`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と`source`」に照らして採否を決める。
   質問や選択肢の説明を要件として扱う指摘は、由来を示して同じ担当へ再判定を頼み、ユーザー自身の決定が要る事項だけを確認へ回す。
   元の要求の解釈でレビュー担当と作成主体の見解が分かれ、結果や作業範囲が変わる時は`agent-basics:review-standards`の共通規定に戻る。
   原文、実際の回答、現物を確かめても解けず、ユーザー自身の判断に委ねる事項が残れば、その修正を保留し、双方の解釈と結果をユーザーへ確認できるメインへ報告する。
5. 修正は部分的な追記で済ませず、開始、終了、途中の失敗からの再開までの一連の流れについて、変えた方式全体の整合を`agent-toolkit:atk-mode/references/drafting-decisions.md`「実現方式の成立」で確かめてから再提出する。
   修正のたびに状態管理や照会手段を足す指摘が続く時は、方式の維持、縮小、代替案への切り替えを`agent-basics:writing-standards/references/design-heuristics.md`「問題と手段の比例性」で比べる。
   指摘が繰り返される原因は`agent-basics:bugfix/references/recurrence.md`に従って分析し、成立性の未解決事項は繰り返されても解消してから合格とする。
6. 修正後は、変えた要求識別子、現行の原稿、差分、直接の影響範囲を同じレビュー担当へ渡して再判定を頼む。
   変更の無い共通資料と合格済みの要求の結果は保ち、変わらない抽出は読者別探索の再点検を省く条件に従って再利用する。
   検収済みの参照関係に基づく正式名への置換だけの差分は、再判定へ戻さず、`agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入」に従って先行項目の保存結果と正式名が一致するかを確かめてから保存へ進める。
7. 未解決の指摘が0件で、原稿と証拠の対応を確かめたら、`agent-toolkit:atk-mode/playbooks/wi-saving.md`に従って保存する。
   ユーザー自身の判断が要る事項は、確認が取れるまで保留する。

## 投入前レビューの返却契約

`指摘:`は最上位の箇条1つを1件とし、根拠や実際値などの補足をその下へ字下げしてよい。
指摘対応記録のtextと比較するのは最上位項目の先頭行だけとし、入れ子の補足は親の指摘に含める。

以下の形式のみを返す。
単一原稿の場合はこの形式をそのまま用いる。
複数原稿の場合は`レビュー結果:`の下に対話ごとの要求をまとめ、要求ごとに`要求識別子:`と以下の全項目を記載する。
すべての要求を漏れなく重複なく返し、資料不足、修正待ち、あるいは読者確認の失敗など一部の事象についても該当する要求にのみ対応付ける。
続行不能と追加報告行は、共通契約`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従う。

```text
判定: 合格 | 修正要
確認段階: 方針 | 本文
対象資料: <方針または原稿の受領した絶対パス>
未解決指摘: <件数>
指摘:
- <対象箇所、実際値、期待値、根拠と適用理由。0件なら「なし」。前回の指摘の解消など0件のときの補足は「なし（前回の指摘1件は解消済み）」のように「なし」に続く丸括弧の中へ書く>
確認した要求と根拠: <確認対象と観測の所在>
ユーザー向け部分の確認: <抽出パス、検収者の判定と根拠、読者別探索を起動した場合は識別子・各抽出の判定・証拠。省略時の値は「記録なし」であり、確認完了とは扱わない>
読者別探索: <起動結果の識別子と返却の所在、または省略の条件と前回の識別子。起動条件非該当の場合はその根拠>
```

方針段階では`ユーザー向け部分の確認:`と`読者別探索:`を省略でき、行の不在は`対象外（方針段階）`として解釈する。
本文段階では修正要を含むすべての判定に両欄を記載する。
原稿・方針・要求と出所・成立性の証拠に根拠の不足がある場合は合格とせず、確認対象と不足する根拠を指摘に含める。
レビュー担当自身で取得できる未読、切り詰めの未回収部分、未実施の原文や証拠との突き合わせは返却前に完了させ、判定理由や指摘にしない。
許可された取得手段を尽くしても入力に到達できない場合は、共通契約の続行できない区分と理由で返す。
本文段階の読者別探索の実施または省略条件の確認も担当内で完了させ、根拠を該当欄へ記載する。
原稿や証拠側の不足と、自身の確認の残りを区別して返却する。
