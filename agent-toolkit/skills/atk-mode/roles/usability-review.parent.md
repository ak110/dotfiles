# ユーザビリティレビューの起動と検収

```text
起動対象: usability-review.subagent.md
```

画面差分がある時の並列画面レビュー（`agent-toolkit:atk-mode/references/workflow-phases.md`「用語」）で、実行レビューを起動する者（レーン工程ではレーン担当）がユーザビリティレビュー担当を起動・検収する手順である。
判定の基準は`agent-basics:review-standards/references/reviewer-usability.md`「ユーザビリティレビューの判定」にあり、本書は入力、起動、受領を定める。
見た目の完全一致を求められた移行の検収は、本書ではなく`agent-toolkit:atk-mode/playbooks/visual-parity.md`に従う。

入力の定義はこの起動契約とagents_serverの`start`の検査が所有する。
役割固有の入力（`extra_params`）はこの契約の入力一覧で完結する。
通常起動（`mode: delegate`）の共通の準備: 起動の前に`agent-toolkit:atk-mode/references/work-contract.md`に従う全体作業契約を用意し、`extra_params`とは別の公開入力`whole_contract_path`へ絶対パスを渡す。

- 必須入力名: `対象worktree`、`変更画面`、`主要シナリオ`、`検証環境`、`引き継ぎ記録先`、`round`
- 任意入力名: `レーン識別子`

<!-- input-contract:usability-review:end -->

起動側が決める値は次のとおりである（各入力の意味は`agent-toolkit:atk-mode/roles/usability-review.subagent.md`「入力」が定め、所在参照）。

- `主要シナリオ`: 計画かWIが定めたエンドユーザーの作業の流れと、そこで確かめるUXの観点。
  変更画面ごとに求める改善と、今回の変更による既存品質の退行を確かめる観点を書き、原要求か確かめる品質が画面ごとに違えばシナリオも分ける。
  担当が通常の開始状態と代表作業を独立に選べる利用文脈を渡す。
  機能の正しさ（期待結果との一致、データの反映、操作の成否）は判定基準として渡さず、別画面の新機能を求める観点も入れない。
  `検証環境`で禁止された操作と、実データから切り離した環境でだけ行う操作（`agent-basics:writing-standards/references/ui-ux.md`「完了前の実描画確認」の手順1）を要する観点は、切り離した`検証環境`と許す操作を明記するか、観点から外す。
- `round`: 初回は1、同じ担当への再判定では直前の値に1を加える。
- `レーン識別子`: レーンの作業を対象とする起動だけで渡す。
  session識別名は`<レーン識別子>-usability-review`とする。

## 起動

1. 起動の前に、対象worktreeの書込担当が、プロジェクトの手順で対象HEADを配備し直すか起動し、完了を確かめる。
   実装途中に配備した環境も対象HEADへ更新し、修正後の再判定でも新しい対象HEADで同じく準備する。
2. `agents_server`の`start`を、`cwd`に対象worktreeの絶対パス、`subagent_md_path`に`usability-review`、`extra_params`に本書「入力」の値を渡して呼ぶ。
   実行レビューと同じ対象HEADで並行して起動する。

## ユーザビリティレビューの返却契約

次の形式のみを返す。

```text
判定: 合格 | 不合格 | 未確定
判定の回数: <番号>
レビューしたHEAD: <7文字以上の一意な短縮OID>
記録: <引き継ぎ記録先の絶対パス>
```

判定が`未確定`の場合は、上記4行の後に`E2E環境`、`Playwrightのライブラリ`、`ブラウザー操作ツール`のそれぞれについて次の行を配置し、計3行を追加する。

```text
試行: <手段> | <実行したコマンド> | <終了コードまたは失敗の観測>
```

続行不能と追加報告行は、共通契約`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従う。
環境による未確定の判定と試行結果は本節の固有結果として保持する。
<!-- return-contract:usability-review:end -->

## 返却後

1. 記録に対象HEADと`判定の回数`が正しく示されているかを確かめる。
   - `合格`か`不合格`: 完遂を試みたシナリオ、観測した状態、キャプチャの実在を確かめる。
   - `未確定`: `E2E環境`、`Playwrightのライブラリ`、`ブラウザー操作ツール`の3つの`試行:`行がそろうかを確かめる。
     欠けていれば受理せず、同じthreadへ不足する手段の試行と再判定を求める。
   - 主要作業の機能停止による`owner_input`の返却: 機能の担当へ必要な修正と再開条件を渡し、解消後に同じ通常の開始状態から再判定を頼む。
     再判定が済むまで、停止で未検証となった部分を含む合格は受理しない。
2. `不合格`の根拠は、原要求、変更画面の既存品質、今回の変更による退行の範囲に入るかで分ける。
   round 2以降は、既指摘、修正差分とその退行に限る。
   - 範囲外の観察（別画面の新機能追加など）: 判定の根拠から外し、適用範囲を示して同じthreadへ再判定を頼む。
     その観察がエンドユーザーの作業の停止か誤った結果を示す欠落なら、`agent-toolkit:atk-mode/playbooks/confirmation.md`「認可を要する操作」のバグの修正と新しい挙動の追加の区分で扱う。
     それ以外は参考の記録とする。
   - 範囲内の根拠: 問題の機構、対象範囲、画面状態、操作手順、表示幅、観測結果を修正条件にまとめ、同じ実装担当（レーン工程では同じレーン担当）へ返す。
     実装担当は指摘箇所に加えて同じ機構を持つ依頼対象の全体を確かめ、新しい対象HEADを実ブラウザで描画し、試した条件と表示結果を再提示する。
     同じ機構の該当箇所へ修正が反映されたことを確かめたら、同じユーザビリティレビュー担当のthreadへの再判定と、実行レビュー担当への再レビューを、同じHEADに対して並行して頼む。
3. 統合へ進む前に、同じ対象HEADでユーザビリティレビューが`合格`か`未確定`で、実行レビューの未解決の指摘が0件であることを確かめ、ユーザビリティレビューの記録を計画の検証結果へ加える。
   `未確定`では、使えなかった描画手段と未確認の画面状態を完了報告に書く。
