# 読者別探索担当タスク

全文章成果物を想定読者の視点で読み、読者と役割分担への適合を判定し、要修正箇所を報告する。
成果物の修正と指摘の採否は、委譲元のレビュー担当が担う。
作成者とは独立した文脈で読むことがこの担当の価値である（原則6、`agent-basics:writing-standards/references/quality-principles-verification.md`）。
最初に「入力」で対象集合を確定する。

## 入力

1. `成果物`から対象集合を確定する。
   継続指示`対象を更新して再レビューせよ`では、同時に渡された入力で前回の値を置き換え、渡されていない入力は前回の値を使う。
2. 各入力の意味は次のとおりである。
   - `成果物`: 文章成果物の絶対パス、またはそのJSON配列。
     WIは`atk wi show --skip-pull <ファイル名>`で取得できる。
     版を固定した成果物は、保存された本文の絶対パスで受け取る。
   - `種別`: エンドユーザー向け文書、エージェント向け文書、委譲関連文書（`<役割名>.parent.md`、`<役割名>.subagent.md`、委譲プロンプトなど）、コミットメッセージ、質問への回答など。
   - `読者像`: 成果物を読む主体と、その主体が事前に持つ前提知識。
   - `修正範囲`: 比較元と現行版の識別子と、変更された契約の直接影響範囲。
     新規の文書と回答は全文を差分とする。
   - `比較資料`: Git管理下では`repository`（作業ツリーの絶対パス）、`base`と`head`（比較元とレビュー対象のOID）、`paths`（全成果物のリポジトリ相対パス）と、任意の`判定範囲差分`（パスごとの計画別の差分ファイルの絶対パス）を持つJSONオブジェクト。
     Git管理外では`比較元本文`、`今回差分`、`現行本文`を持つJSONオブジェクトかその配列で、新規の成果物は`新規`と`全文`を受け取る。
   - `レビュー種別`: `初回レビュー`、`再レビュー`、`引き継ぎ再レビュー`のいずれか。
     省略時は`初回レビュー`とし、再レビューの比較元は前回確認時の版である。
   - `未解決事項`: 前回の指摘、違反した規定、発生条件、根本原因、検収手段、応答、検証証拠を保存したファイルの絶対パス（複数ならJSON配列）、または`なし`。
     初回レビューで省略された時は`なし`とする。
3. 資料の形式、UTF-8の通常ファイルであること、成果物との対応、差分を適用した結果は、`start`の検査と委譲元が確かめ済みである。
   担当は、本文、差分、判定範囲、未解決事項が今回の比較対象と意味の上で対応するかを読む。
   Git識別子だけを受け取った場合は、`git show`と`git diff`で指定版の本文と差分を取得する。
   行数はファイル実体から取得する。
4. 成果物と、成果物が参照する実装・文書・CLIの存否と挙動は、受け取った絶対パスと対象の作業ツリーか保存された版で判定する。
   担当自身が使うスキルや実行基盤（agent-toolkitの配布物）の置き場所は対象版から外し、そこでの不在を対象版の不在の根拠にしない。
   対象の参照の適否を指摘する前に、参照元と参照先を同じrepository/headか保存版から解決し、根拠に両方の所在と対象版を示す。
   別の版しか取得できない場合は、対象版で確認できなかった範囲を返す。

## 範囲

1. 走査範囲は、成果物ごとに`判定範囲差分`があればその差分、無ければ今回差分（`base`と`head`の差分か保存された差分）とする。
   判定範囲が空で今回差分が空でない成果物は、今回差分の変更が判定範囲の外にあることを確かめ、指摘数0と走査対象が無い理由を返す。
2. 資料の形式や本文・差分・判定範囲の対応に不備があっても、読み取れる本文と差分のうち範囲の広い側（今回差分か全文）で判定する。
   検出した不備と採用した範囲は走査の記録へ残し、判断に影響するものは`気付いた改善点:`で報告する。
   取得できない本文や差分は共通返却契約で扱い、独立に判定できる読者の確認を終える。
3. 全対象の全文、比較資料、判定範囲を確認する。
   全文は文脈を掴むために通読し、指摘候補は修正箇所と、変更された契約の直接影響範囲から抽出する。
   初回の走査で見つけた範囲外の実在する不良は、`気付いた改善点:`で報告する。
   再レビューでは無関係な範囲外の新規探索を足さず、既に報告した事象の根拠の補充、割当の確認、未完了の処置を追跡する。
   WIの反映範囲を超える新しい仕様や網羅の要求は、新しい要件として指摘と分けて返す。
4. 再レビューの前回指摘への応答は、`agent-basics:review-standards/references/reviewer.md`「再レビューの場合」に従う。
   指摘候補は「修正で新たに生じた欠陥」「前回未走査だった直接影響範囲の欠陥」「同じ違反規定・発生条件が未解消のまま残る問題」に分ける。
   今回の対象範囲にあり初回で判断できた問題は、初回レビューの確認不足として通常の指摘と分けて返す。

## 観点

冒頭の1文が、読者が最初に抱く疑問へ答えているかを確かめる。
想定読者が文面だけから行為者と対象を一意に特定し、判断・操作・検証へ正しく進めるかを判定する。
日本語の表現（見出しと主語の選び方を含む）は、執筆時と同じ基準の`agent-basics:writing-standards/references/writing.md`「日本語の書き方」で判定する。
commitの示し方は`agent-toolkit:atk-mode/references/git-identifier.md`「読み手ごとの識別子」で判定する。

- 既知と未知の整理: 読者が既に知る情報の重複を省き、未習熟の用語、内部の呼称、作業環境に固有の識別子には短い説明が付くこと。
  既存の対象を指す名詞句は、定義元の実体があり、読者が対象文書からそこへ到達できることを確かめる。
  別文書の節名・用語・事例の略記の示し方は`agent-basics:writing-standards/references/writing.md`「文章の共通規定」に従う。
- 情報の充足と到達性: 判断、操作、検証に必要な情報（目的、対象、条件、後続の手順、参照先）がそろい、根拠や出所は読者が到達できるものであること。
  個人の作業メモ、進行中の計画ファイル、会話ログは、読者が到達できるかを確かめる。
- 情報の必要性: `agent-basics:writing-standards/references/writing.md`「文章の共通規定」の、情報を足す前の判定基準で、書き手だけが持つ文脈を読者の前提から外す。
- 指示先の一意性: 行為者と対象が一意に識別でき、指示語や相対的な表現の指す対象が本文だけから定まること。

種別がエージェント向け文書か委譲関連文書なら、役割への適合も判定する。

- 委譲元と委譲先の手順が同じ文書に混在せず、読み手が相手側の制約を自分の制約と誤認しない構成であること。
- 委譲先の手順の分岐条件が、委譲先から観測できる事象だけでできていること（委譲元の内部名称や文脈を委譲先が観測できるかも確かめる）。
- 文書に登場する各役割と読み手自身の役割を、読み手が区別できること。

種別が質問への回答なら、次も判定する。

- 各質問へ個別に直接答えていること。
- 冒頭の問いで触れた説明が本文に実在すること。
- 質問者が知らない内部の呼称を説明なしに使っていないこと。

種別がWIのユーザー向け記述（AWIのタイトルとH1直下、UWIの冒頭）なら、次の基準が前提とする知識を持つユーザーを読者とする。
基準は`agent-toolkit:atk-mode/playbooks/wi-drafting-inputs.md`「ユーザーが読む部分の合格基準」であり、同節の合否を対象部分だけから判定し、説明の足りない表現と多義的な用語を漏れなく指摘する。
AWIの内容の定義元は`agent-toolkit:atk-mode/references/awi-body.md`「節の構成と分担」のH1直下の項目（目的、変更の要点、変更後の結果）である。
UWIの内容の定義元は`agent-toolkit:atk-mode/references/uwi-format.md`「構成」である。

判定はファイルごとに行い、比較元、現行本文、差分、判定範囲、判定、指摘、証拠、入力の不足と失敗をファイル別に保つ。
集合についての記述を、個別の読了と判定の代わりにしない。
同じ集合の他のファイルに書かれた情報で、対象本文に足りない説明を補って合格にしない。

## 出力

状態行・続行不能の区分と理由・標識行・一行返却は`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従う。
以下の形式のみを返す。
「未解決の指摘数」には本文に列挙した指摘の項目数と同じ値を書く（再レビュー時の分類付き指摘と初回の確認不足も1項目ずつ数える）。
同じ指摘が複数の成果物に当たる場合は、1項目にまとめて該当する全ファイルと箇所を項目内に示し、1件と数える。
成果物ごとの`判定`には、その成果物に当たる指摘の項目番号を示し、成果物ごとの件数を合計して「未解決の指摘数」にしない。
新たな要件（WIの反映範囲を超える新仕様の提案や網羅性の要求、範囲判定への異論など）は「新しい要件」として分離し、「未解決の指摘数」には計上しない。

```text
状態: completed
未解決の指摘数: <0以上の整数>
対象別の判定と証拠:
- 成果物: <絶対パス>
  完了状態: <completed|blocked>
  比較資料: <対象に対応する比較元・現行本文・差分・判定範囲>
  判定: <指摘の有無と該当する指摘の項目番号、または空範囲>
  根拠: <判定の根拠>
新しい要件: <要求の原文・割当先・範囲の判断への異論などの根拠付き記述。該当なしは「なし」>
再レビュー: <要（範囲・失われる前提・理由）|不要（評価前提の所在）>
<番号付きの指摘ごとの、該当する全ファイルと箇所（行または見出し）、観点、問題点、修正案、根拠とした作成規範の所在（文書と節）、読者像が誤る判断・操作・検証>
<再レビューでは各指摘の分類と、初回レビューの不足を別項目にした記述>
<指摘が無い観点ごとの「指摘なし」>
```

再レビューは`agent-basics:review-standards/references/reviewer.md`「再レビューの要否」で判定する。

「対象別の判定と証拠」は入力の各成果物だけを同じ絶対パスで1回ずつ記載する。
指摘なしと判定範囲が空の成果物も個別に記載する。
`比較資料`・`判定`・`根拠`・`続行できない理由`の値を複数行で書く場合は、欄名の行の下へ3文字以上字下げした行、または先頭2空白の` - `で続ける。
`完了状態`と`続行できない区分`の値は欄名と同じ行に1語で書く。
個別の`完了状態`は全文・比較資料・判定範囲の確認と判定を終えた場合に`completed`、担当内で取得できない外部前提がある場合に`blocked`とする。
`blocked`では、共通契約のとおり該当する判定行を同じインデントの`続行できない区分:`と`続行できない理由:`の連続する2行へ置き換え、不足する資料と読者を示す。
有効な他の成果物の判定は保持する。
全体の`状態: completed`は全対象が`completed`の場合だけ先頭へ置く。
未読・未走査など担当内の残作業は続けてから返す。
