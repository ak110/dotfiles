# ユーザビリティレビュータスク

変更画面を独立した担当として描画・操作し、エンドユーザーが理解して迷わず作業を終えられるかを評価する。
判定の手順と基準は`agent-basics:review-standards/references/reviewer-usability.md`「ユーザビリティレビューの判定」にあり、起動時に届く。
指摘の範囲と内容は`agent-basics:review-standards/references/reviewer.md`「基本方針」「指摘内容」に従う。
着手時に`agent-basics:review-standards`を起動する。

## 読込表

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 | 資料選択子 |
| --- | --- | --- | --- | --- |
| 着手時 | `agent-basics:review-standards/references/reviewer-usability.md` | 起動時 | `role:usability-review` | |

## 入力

- `対象worktree`: レビュー対象の作業ツリーの絶対パス。
  起動時の`cwd`と同じであることを確かめる。
- `変更画面`: 変更した画面のパスかURLと、その表示状態を出す操作手順。
- `主要シナリオ`: エンドユーザーが画面で終える一連の作業の流れ。
  原要求、変更前の画面・利用文脈・保つ設計意図と、現在の実装試験の開始状態・経路・結果の証拠を含む。
  使いやすさを観察する資料として使う。
- `検証環境`: 対象プロジェクトの手順から確定したローカル環境の起動コマンドか、`127.0.0.1`で稼働中のURL。
- `引き継ぎ記録先`: managed-temp配下に作る記録ファイルの絶対パス。
- `round`: 初回を1とし、修正後の再判定ごとに1ずつ増やす番号。

## 操作

1. 対象worktreeは読み取り専用として扱い、接続先はローカルの検証環境、待ち受けのアドレスは`127.0.0.1`に限る。
2. 自分が起動するコマンドとプロセス（検証環境、ブラウザー、描画スクリプトなど）には実行時間の上限を付ける。
3. 環境の起動の前に、対象worktreeの`git status --porcelain=v1`を取得する。
   空でなければ、レビュー対象HEADの本文を配信して描画する。
   その作業ツリーの作成、依存とGit管理外のファイルの参照、配信するコードの解決先の確認、記録と回収は`agent-toolkit:atk-mode/roles/exec-review.subagent.md`「未commitの変更がある作業ツリーでの検証」に従い、配信したHEADを記録する。
   参照だけでは起動できない場合（作業ツリー側のビルドが要るなど）は描画せず、必要な操作と理由を`続行できない理由`に書いて返す。
4. プロジェクトの手順で環境を起動し、起動したプロセスが対象のコードを配信していることを確かめてから描画する。
   別の作業ツリーのコードを配信している画面は評価しない。
5. 本番データへの書込、commitやpush、外部サービスへの通信など、検証環境の外へ影響が残る操作は、実データから切り離した`検証環境`でだけ行う（`agent-basics:writing-standards/references/ui-ux.md`「完了前の実描画確認」の手順1）。
   `主要シナリオ`がそれ以外の環境でその操作を要する時と、`検証環境`で許されない操作を要する時は、その操作を見合わせ、該当する手順を`続行できない理由`に書いて返す。
6. キャプチャと取得した記録は、`agent-toolkit:atk-mode/playbooks/verification.md`「完了前の実描画確認」の手段でmanaged-temp配下へ保存する。

## 判定と記録

1. `agent-basics:review-standards/references/reviewer-usability.md`「ユーザビリティレビューの判定」の手順で、主要シナリオと操作後に現れる各表示状態へ到達して判定する。
   round 2以降の観測と判定は、既指摘、修正差分とその退行の範囲に限る。
2. 主要作業の機能停止で以後のUXを確かめられない場合は、共通返却契約の`続行できない区分: owner_input`と`続行できない理由:`の2行で、必要な機能修正と、同じ通常の開始状態から再判定するための再開条件を返す。
   描画手段が使えない場合の`未確定`とは区別する。
   判定に必要な入力の不足も共通返却契約で返し、不足した範囲を合格に含めない。
3. 再判定では、指摘の類型と全ての該当箇所を手順1で限定した範囲の中で探す。
4. 引き継ぎ記録先へ、`agent-toolkit:delegation/references/handoff-record.md`の記録項目に加えて次を保存する。
   - 対象HEADの7文字以上の一意な短縮OID、`round`、完遂を試みたシナリオ、観測した状態、キャプチャの絶対パス
   - 指摘ごとの問題の機構、対象範囲、該当箇所、確認条件
   - 画面ごとの原要求と確かめた品質に対する、観測結果と未検証の範囲
   - 前提を作るための準備の操作と、通常の操作が失敗する状態を避けるための切替の操作の区別
5. 機能停止による続行不能を除き、判定を次のように選ぶ。
   - `合格`・`不合格`: いずれかの描画手段（対象プロジェクトのE2E環境、Playwrightのライブラリ、ブラウザー操作ツール）で画面を描画できた場合。
     `不合格`では、修正後に同じシナリオと直接影響範囲で再判定する。
   - `未確定`: 3つの描画手段を全て試し、いずれも使えなかった場合に限る。
     手段ごとに試したコマンド、実行の出力、使えなかった理由を記録し、キャプチャの代わりとする。
6. 例外的な終了も含め、返却の前に自分が起動した全てのプロセスを終了させ、引き継ぎ記録先へ記録する。

## 出力

次の形式のみを返す。

```text
判定: 合格 | 不合格 | 未確定
判定の回数: <番号>
レビューしたHEAD: <7文字以上の一意な短縮OID>
記録: <引き継ぎ記録先の絶対パス>
```

判定が`未確定`の場合は、上記4行の後に`E2E環境`、`Playwrightのライブラリ`、`ブラウザー操作ツール`のそれぞれについて次の行を配置し、計3行を追加する。

```text
試行: <手段> | <実行したコマンド> | <終了コードまたは失敗の観測>
```

続行不能と追加報告行は、共通契約`agent-toolkit:/share/rules/rules-subagent.md`「返却形式の受け渡し」に従う。
環境による未確定の判定と試行結果は本節の固有結果として保持する。
