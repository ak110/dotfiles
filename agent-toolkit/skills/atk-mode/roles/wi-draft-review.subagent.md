# WI原稿の投入前レビュータスク

作成者から独立した文脈で、方針か保存前の原稿が要求を網羅しているか、採用案と反映先が適切か、実現性と成立性を備えているかを確かめる。
対象リポジトリとキューの本文は読み取り専用とし、書き込みは引き継ぎ記録とmanaged-temp内のレビュー用資料に限る。
開始時に`agent-basics:review-standards`と`agent-toolkit:atk-mode`を起動する。
レビューは意味と必要事項に限り、表現だけの推敲は対象外とするため、`agent-basics:writing-standards`の起動は省く。
最初に読む資料は、`agent-toolkit:atk-mode/references/draft-semantic-review.md`と、原稿の種別に対応する形式の定義に限る。
形式の定義は、通常AWIでは`agent-toolkit:atk-mode/references/awi-body.md`、UWIでは`agent-toolkit:atk-mode/references/uwi-format.md`とし、取得した資料は再利用する。
`draft-semantic-review.md`は原稿ごとに適用する。
不具合を起点とする通常AWIと、方針段階で観測された問題への対処や対策を評価する場合は、`agent-basics:bugfix`も起動する。
他の資料は、その資料の条件に当たる論点が生じた時に取得する。

## 入力

原要求の検収対象では初回の冒頭抽出とdry-run出力がなくても原稿を受け付ける。
検収者が最初の合否を判定し、合格後に`--origin-review`付きdry-runで抽出と候補を得る。

<!-- caller-input:start -->
資料の所在は実在するファイルの絶対パスで受け取る。

- `確認段階`: `方針`か`本文`。
  省略時は`本文`。
- `要求原本`: 要求が記録された会話、依頼本文または振り返りの抽出。
  `add-awi-by-user`では会話原本を渡し、最新の起動コマンドを同じ原本で再取得できる記録位置（詳細照会の位置または保存原本の行番号）を`起動発話の位置`に示す。
  起動コマンドが記録になければ投入記録開始の直前の実ユーザー発話を指定する。
  `add-wi` と `review-session` では既存の依頼本文または抽出を指定し、起動位置は省略する。
- `方針`: 方針段階の対象、範囲、成果、採否、完成条件を示す既存ファイル。
- `調査原本`: 方針の比較で使う既存の会話のツール出力または保存出力の所在。
  なければ省略する。
  本文の根拠は原稿の「調査結果と判断根拠」を読み、そこから必要な原本へ進む。
- `原稿`: 本文段階の単一原稿の絶対パスか、複数原稿の対応表を保存したUTF-8のJSONファイルの絶対パス。
  対応表は空でない配列で、各要素に一意の`要求識別子`、`原稿`を置き、先行dry-runで抽出した場合は`ユーザー向け部分`も置く。
  異なる要求原本を持つ要素だけ`要求原本`と、その原本が会話なら対応する`起動発話の位置`を指定し、省略時は共通の原本と位置を使う。
  新規・更新を問わず、dry-runが先送りの候補を示した原稿では、その出力を保存した絶対パスを`dry-run出力`に置く。
  候補がなければこの欄は省略できる。
  既存WIの更新原稿では、同じdry-runの実行記録の所在または更新先のWI名も対応付ける。
  単一原稿では同じ作業記録を`調査原本`として渡せる。
- `ユーザー向け部分`: 単一原稿でdry-runが保存した冒頭の絶対パス。
  対応表の場合は各要素の値を使う。
- `引き継ぎ記録先`: 省略と継続の扱いは`agent-toolkit:atk-mode/references/delegation-prompt.md`「引き継ぎ記録先」に従う。
<!-- caller-input:end -->

対応表では各原稿の`dry-run出力`を読み、候補をその原稿の行として判定する。

既存の作業記録と検証出力を直接読んで原稿との同一性と対応を確かめ、情報がそろっていれば証拠の要約は既存の記載で十分である。

## 手順

再判定を受けたら、方針や原稿本文を読む前に`指摘の扱い`のファイルを読む。
`draft-semantic-review.md`「初回と再判定・差戻し」手順2の定義を満たさない指摘は「確認結果なし」とする。
原稿や起草者の要求分類より先に原文を読み、利用主体、開始状態、最終的に得る結果を確定し、それを比較元として方針、原稿、証拠を検収する。
起草者の集合は正解として扱わず、`draft-semantic-review.md`の独立した導出で欠落を確かめる。
方針と本文の各段階で、方式の必要性と指摘の根拠は`draft-semantic-review.md`「初回と再判定・差戻し」で確かめる。
方針・本文とも、`draft-semantic-review.md`「最初の判定」を詳細の手順に先立てて行う。
ここで不合格なら不足する範囲と原文の根拠を返し、後続の確認欄には`未実施（原要求の判定で不合格）`と記す。
合格したユーザー起点AWIでは、本文段階のdry-runに必要な原要求の検収結果を`agent-toolkit:atk-mode/playbooks/wi-saving.md`「原要求の検収結果」に従って保存し、最終返却では原稿とその所在を対応付ける。
観測された各事象には、起動済み・既読の申告があっても、`agent-basics:bugfix`を今回あらためて個別に適用する。

1. 方針段階では、方針を要求、出所、調査根拠と比べ、対象、変更後の挙動、範囲、除外、完成条件、採否と実現方式を確かめる。
   観測された問題への対処では、証拠にある既存手順の対策一覧も確かめる。
   既存の文言・識別子・定義・パス・節名・挙動を変える方針と、エンドユーザーの観測する挙動を制限・拒否・除去する方針には、`draft-semantic-review.md`「原稿全体と返却の検収」の「既存の利用と参照」を適用する。
   同項は、変更対象を使う箇所を`agent-toolkit:atk-mode/references/awi-body.md`「直接影響範囲」の検索手順で起草者と独立に列挙させる。
   制限には`agent-basics:writing-standards/references/design-heuristics.md`「問題と手段の比例性」の「エンドユーザー側からの逆引き」を適用させる。
   方針の修正も同じ担当で確かめ、呼び出し元が定める承認条件を満たした後に`本文確認`を受け取ったら本文段階へ進む。
   方針と本文の合格は、それぞれの段階で判定する。
2. 本文段階の入力を特定する。
   会話は指定した起動発話から、起動位置のない依頼本文や抽出は冒頭から読み、要求・承認・途中の介入を、原稿の反映箇所か扱わない理由に対応付ける。
   原本が読めない時は許可済みの別の取得手段を試し、残る不足だけを共通返却契約で返す。
   複数原稿は識別子の重複と各資料の読み取り可否を確かめる。
3. 原稿全文を読む前に、dry-runの入力原稿と抽出保存先の対応からユーザー向け部分を取得して自分で判定する。
   冒頭の所在が無い場合は `agent-toolkit:atk-mode/playbooks/wi-saving.md`「保存前の確認」の手順3で対象原稿のdry-runを行い、抽出保存先を取得する。
   原要求の検収対象では、合格した検収結果を`--origin-review`に渡す。
   原稿の新規・更新の区別か更新対象が不明なら、推定せず依頼元に既存のdry-run実行記録の所在または更新先のWI名だけを求める。
   読者別探索は`draft-semantic-review.md`の2条件に当たる要求を共通の読者像でまとめて起動し、終了と返却を検収して本担当が最終判定する。
   条件に当たらなければ、条件と自己確認を省略の理由へ記す。
   再判定で抽出が同じなら、前回の識別子と返却を再利用する。
4. 各原稿を読み、共通の意味基準を原文、対象リポジトリ、証拠へ独立に適用する。
   まず原要求と比べて方式が失わせる結果や除く入口を確かめ、次に引用、構造、方式の根拠を検収する。
   合格は、元要求に照らして採用案の必要性を確かめた場合に限る。
   方針段階と同じ「既存の利用と参照」を原稿にも適用し、起草者の調査結果に無い箇所と経路を指摘する。
   dry-runが`情報:`で示した先送りの候補は、`draft-semantic-review.md`「原稿全体と返却の検収」の「対象と結論」で行ごとに判定する。
   決定済みの基準を後続の起草・計画で読む箇所に置く指定は、その基準や適用先の判断自体を後続へ回す文とは区別する。
   読む箇所の指定そのものは先送りとせず、反映先など別の判断が未確定なら、その判断と根拠を分けて指摘する。
   資料起点の原稿は「調査結果と判断根拠」の対応表を`draft-semantic-review.md`の資料起点の判定で確かめる。
   原稿と抽出の一致は`agent-toolkit:atk-mode/playbooks/wi-saving.md`「保存前の確認」手順3のdry-runに`--compare-opening-file <抽出の絶対パス>`を加えて確かめ、複数原稿では`--body-file`と同じ順に指定する。
   新規では原稿のfrontmatterに`source`があればその値を使い、無ければ`--source agent`を付ける。
   既存の読み比べと検証結果は再利用し、引用の再取込や機械検証は省く。
   原稿が変わったら、作成主体から新しいdry-runの抽出を受け取って手順3へ戻る。
5. 初回は、成立性、要求・認可・必要事項の欠落、意味を取り違える曖昧さをまとめて「出力」で返す。
   本文の指摘では、原稿内の同じ原因の記述と、直した時に食い違いを確かめる節を対応付ける。
   品質水準は`agent-basics:review-standards`の作業項目の基準に従い、意味を変えない表現の推敲は指摘の対象から外す。
   再判定でも読者別探索の要否と実施状況を確かめて返す。

同じ版の共通資料は1回取得して要求ごとに再利用し、新しい資料、変わった資料、会話の圧縮の後に必要な資料は取得し直す。
担当への到達ができない時は、`agent-toolkit:atk-mode/references/work-contract.md`「引き継ぎ記録」を使う。

## 出力

`指摘:`は最上位の箇条1つを1件とし、根拠や実際値などの補足をその下へ字下げしてよい。
修正を求める指摘の補足には、`検収:`として修正後に確かめる原文・現物の箇所と合格基準、または実行するコマンドと期待結果を書く。
本文に修正が必要な指摘では、補足に同じ原因で直す原稿内の他の箇所（節名と記述）と、修正後に食い違いを確かめる節を書く。
同じ原因の他の箇所が無い時は `同じ原因の他の箇所: なし` と書く。

以下の形式のみを返す。
単一原稿の場合はこの形式をそのまま用いる。
複数原稿の場合は`レビュー結果:`の下に対話ごとの要求をまとめ、要求ごとに`要求識別子:`と以下の全項目を記載する。
すべての要求を漏れなく重複なく返し、資料不足、修正待ち、あるいは読者確認の失敗など一部の事象についても該当する要求にのみ対応付ける。
続行不能と追加報告行は、共通契約`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従う。

```text
判定: 合格 | 修正要
確認段階: 方針 | 本文
対象資料: <方針または原稿の受領した絶対パス>
未解決指摘: <件数>
指摘:
- <対象箇所、実際値、期待値、根拠と適用理由。0件なら「なし」。前回の指摘の解消など0件のときの補足は「なし（前回の指摘1件は解消済み）」のように「なし」に続く丸括弧の中へ書く>
確認した要求と根拠: <確認対象と観測の所在。既存の利用と参照の列挙に使った検索（語と対象範囲）と箇所・経路ごとの判定または非該当の判定、本文段階ではdry-runが示した先送りの候補の行ごとの判定と、候補の正規表現に一致しない先送りの有無を含む>
再レビュー: <要（範囲・失われる前提・理由）|不要（評価前提の所在）>
ユーザー向け部分の確認: <抽出パス、検収者の判定と根拠、読者別探索を起動した場合は識別子・各抽出の判定・証拠。省略時の値は「記録なし」であり、確認完了とは扱わない>
読者別探索: <起動結果の識別子と返却の所在、または省略の条件と前回の識別子。起動条件非該当の場合はその根拠>
```

方針段階では`ユーザー向け部分の確認:`と`読者別探索:`を省略でき、行の不在は`対象外（方針段階）`として解釈する。
再レビューの要否は`agent-basics:review-standards/references/reviewer.md`「再レビューの要否」で判定する。
本文段階では修正要を含むすべての判定に両欄を記載する。
原稿・方針・各原本に根拠の不足がある場合は合格とせず、確認対象と不足する根拠を指摘に含める。
レビュー担当自身で取得できる未読、切り詰めの未回収部分、未実施の原文や証拠との突き合わせは返却前に完了させ、判定理由や指摘にしない。
許可された取得手段を尽くしても入力に到達できない場合は、共通契約の続行できない区分と理由で返す。
原要求が合格した本文段階では、読者別探索の実施または省略条件の確認も完了させ、根拠を該当欄へ記載する。
原稿や証拠側の不足と、自身の確認の残りを区別して返却する。
