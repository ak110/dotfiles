# 読者別探索担当の起動と受領

```text
起動対象: reader-fit-review.subagent.md
```

文章成果物を含むレビューで、レビュー担当（実行レビュー担当など）が、直接確認か読者別探索担当の起動を選び、全対象と想定読者の結果をそろえる手順である。
方針: 読者に合うかは、作成者と同じ文脈では判定できないため、独立した担当が読む（原則6、`agent-basics:writing-standards/references/quality-principles-verification.md`）。
受領は担当の申告ではなく、対象ごとの完了状態と証拠で行う。
担当の確認観点は`agent-toolkit:atk-mode/roles/reader-fit-review.subagent.md`にある。

## 起動

1. 起動の要否を決める。
   レビュー開始時点からレビューHEADまでの全変更パスを`atk run-script agent-doc-changes -- --repo <対象worktreeの絶対パス> <開始時点> <レビューHEAD> --review-risk`で判定する。
   - `低リスク`（コード、設定、エージェント向け文書を含まない人間向けMarkdownだけの変更）で、Git管理外の文章成果物、外部サービスへの送信文面、回答下書きが無い: レビュー担当が直接確認してよい。
     ユーザーが可読性の是正を求めた対象と、レビュー担当だけでは判断が難しい対象は、該当ファイルと読者を担当へ渡す。
   - 通常リスク、判定不能、Git管理外の文章: 担当を起動する。
   直接確認でも、次の手順2〜4の対象集合、比較資料、読者別の基準を適用し、ファイルと読者ごとに判定・根拠・証拠を記録する。
2. 対象集合を確定する。
   - 初回レビューは、`git diff --name-only --diff-filter=d <開始時点> <レビューHEAD> -- '*.md' '*.md.tmpl'`の全ファイルを対象とする（改名は変更後のパス）。
     誤字や整形だけの差分も含め、内容によらず全てを対象にする。
     対象の除外・縮小と、問題の対処要否は`agent-basics:bugfix/references/prevention.md`「害と費用の比べ方」で判定し、作業費用や所要時間だけを理由にした除外は避ける。
   - コードコメントは通常のコードレビューで扱う。
   - 回答下書きとGit管理外の文章は、新規作成か修正された範囲を入力とする。
   - 1つのレビュー単位に複数の計画があれば、単位内の全計画のcommitと、どの計画にも属さないcommitをまとめて判定範囲とし、`review_contract`の「別計画の認可」が示す単位外の計画のcommitだけを除く。
     単位外の計画だけが変えた文書は除く。
     双方が変えた文書は、パスごとに単位内の判定対象commitの`git show --format= <commit> -- <パス>`を順に保存して「判定範囲差分」とする。
     同じ行は最終変更commitの計画に帰属させ、単位外の計画の記述の前提を単位内の計画が変えた場合は直接影響範囲に含める。
     判定範囲の差分が空のファイルも、手順4の省略条件を満たさない限り起動の対象とする。
3. 起動の単位を分ける。
   同じ読者像で確認できる文書群は、`成果物`配列とファイルごとに1対1で対応する`比較資料`を使い、まとめて起動する。
   ディレクトリやスキルなど共通の文脈を保つ単位で、1起動の成果物を今回差分の合計2万5千文字以下かつ60ファイル以下に分ける。
   担当が1回の起動で全対象の差分を全て読めるかは差分の量で決まるため、件数の上限と量の上限を両方満たす。
   量は起動前に測る。
   - Git識別子で渡す: `git diff <比較元> <現行> -- <成果物のパス>`の出力の文字数。
   - 保存資料で渡す: 今回差分の文字数（新規の成果物は全文の文字数）。
   - 判定範囲差分を渡す: 担当は今回差分も読むため、今回差分で測る。
   1ファイルの差分だけで2万5千文字を超える成果物は、そのファイルだけで1回の起動とする。
   上限内でも、読取量、共通の文脈、読者像の違い、確認の品質から必要なら更に分ける。
   この契約を、初回レビュー、再レビュー、引き継ぎ再レビュー、Git管理下・管理外の文書、回答下書きのすべてへ適用する。
   比較元、現行本文、完全な差分、判定、指摘、証拠を対象ごとに保ち、起動の識別子を各ファイルへ対応付ける。
4. 再レビューでは、前回と今回の各開始時点からそれぞれのレビューHEADまでのファイル別の差分を、各`review_contract`の判定範囲で比べる。
   差分と契約の境界がどちらも完全に一致するファイルは、「再点検対象なし」として起動を省ける。
   前回の契約が無い旧形式の入力は従来の比較で判定し、契約の境界が変わった箇所は再点検する。
   rebaseで開始時点が変わった場合も双方の差分を比べ、空白の変更を含むファイルは起動の対象とする。
   差分が変わっても、既に担当が「不要」とし、受領側が修正後の証拠で評価前提が保たれると確かめた範囲は、同じ扱いとする。
   根拠は同じ引き継ぎ記録に残す。
   資料が不足する場合は、補ってから判定する。
5. `agents_server`の`start`を、本書「入力」の引数で呼ぶ。
   形式の不備は`start`が診断文で返すため、示された入力を補って再発行する。
6. 担当が「要」とした範囲へ再レビューを頼む時は、同じ`session_id`への`send_message`に`instruction: 対象を更新して再レビューせよ`を指定する。
   要否が欠けるか修正で評価前提が変わる場合は、ラウンドを増やす前に要否を照会する。
   `extra_params`には、対象集合全体の絶対パスの配列にした新しい`成果物`と、変えた`比較資料`・`修正範囲`・`未解決事項`・`レビュー種別`だけを渡す。
   担当はこの`成果物`を以後の対象集合とし、返却の検査もこの集合を基準にする。

起動側が決める値は次のとおりである。
入力・比較元の不足は起動前に補い、再レビューでは`レビュー種別`と`未解決事項`も渡す。

- `成果物`: 成果物の絶対パス、または空でない絶対パスのJSON配列。
  WIは担当が`atk wi show --skip-pull <ファイル名>`で取得できるため、ファイル名で渡せる。
  版を固定する成果物は、委譲元が保存した本文の絶対パスを渡す。
- `種別`: 成果物の種別。
- `読者像`: 成果物を読む主体と、その主体が前提として持つ事柄。
- `修正範囲`: 比較元と現行版の識別子（Git管理下はOID、Git管理外は旧本文の複製と現行本文の絶対パス）と、変更された識別子や契約の直接影響範囲。
  新規の文書や回答は、新規である旨と全文を差分として示す。
  `atk`でだけ取得できる本文で版の固定が要るものは、`atk wi show`などで取得して自分のセッションのmanaged-tempへ保存して渡す。
  まとめて起動する場合は、ファイルごとの比較元、現行本文、今回差分を対応付けて全対象を渡す。
- `比較資料`: Git管理下は`{"repository":"/repo","base":"<比較元OID>","head":"<レビューHEAD>","paths":["文書.md"]}`とし、`paths`へ全成果物のリポジトリ相対パスを入れる。
  計画別の判定範囲があれば、同じオブジェクトの`判定範囲差分`へ、`paths`の各パスから判定範囲の差分だけを保存したファイルの絶対パスへの対応を入れる。
  Git管理外は`{"比較元本文":"/保存先/before.md","今回差分":"/保存先/change.patch","現行本文":"/成果物.md"}`か、その配列とする。
  今回差分は比較元本文と現行本文の間の完全な差分にする。
  初回レビューの新規成果物に限り、`{"比較元本文":"新規","今回差分":"全文","現行本文":"/成果物.md"}`を使える。
- `レビュー種別`: 再レビューでは`再レビュー`。
  再レビューと引き継ぎ再レビューの`修正範囲`と`比較資料`の比較元は、前回確認時の版（Git管理下は前回レビューのHEAD、Git管理外は自分のmanaged-tempへ複製した前回の本文）とし、前回の未走査範囲と証拠不足だった範囲も明示する。
- `未解決事項`: その読者に関わる前回の指摘箇所、違反した規定、発生条件、根本原因、求めた検収手段、前回指摘への応答（採否と不採用理由、範囲外なら割当先）、検証証拠を書いたファイルの絶対パス（複数はJSON配列）。
  コマンドの出力による証拠は、自分のmanaged-tempへ保存して渡す。
  説明は保存ファイルへ書き、値はパスだけにする。
  該当が無ければ`なし`を渡す。

成果物と、成果物が参照する実装・文書・CLIの存否と挙動は、渡した絶対パスと対象の作業ツリーか保存された版で判定させる。
担当自身が使う配布物の置き場所は、存否の判定の対象から外させる。

## 受領

1. 引数なしの`atk agents wait`で結果を回収し、読者ごとに終了状態と返却本文を確かめる。
   `completed`はターンの終了を示すだけであり、受理の根拠は各対象の`完了状態: completed`と対象別の証拠である。
   起動時に渡した成果物の集合と返却の対象を比べ、欠落、重複、依頼外の対象と、各対象の比較資料・完了状態・判定・根拠の不足を確かめる。
   - `agents_server`は返却形式の回復で対象集合と機械可読な個別完了を検査する。
     構文の検査を通ることと、本文、比較資料、判定範囲が実際に確かめられたことは別であり、後者はレビュー担当が検収する。
   - 比較資料が、各成果物に渡した版、本文、差分、判定範囲と対応するかを確かめる。
     参照の適否を指摘している場合は、根拠にした参照元と参照先の両方が同じ対象版に対応することも確認し、一致しない根拠は採否に使わない。
   - 各ファイルへの起動識別子の申告だけでは、個別の判定の完了とみなさない。
   - `blocked`を含む結果は全体を未完了とし、有効な他の対象の判定は保つ。
2. 不備のある対象は完了の判定に使わず、該当するパスと不足を示して同じ担当へ補完を求め、有効な対象の結果は保つ。
   補完の指示（`agents_server`の自動の返却形式の回復を含む）の後も欠落した対象が減らなければ、同じ指示を繰り返さない。
   有効な結果を保ち、欠落分だけを「起動」手順3の上限で分けた新しい起動へ移し、その結果も本節の同じ検査で受理する。
3. 資料の不足、実行の失敗、本文の欠落があった対象と読者は「未取得」とし、起動手段が示す後続の操作と本節の手順で同じ読者の結果を回収し直す。
   - 入力の不足や資料の対応の不備で中断した探索は、資料を補って同じ読者で起動し直す。
   - 確認範囲を確定できなかった結果は、今回の完了の判定に使わない。
   - 前回の結果と現行の差分を目視しただけでは、今回の独立した探索の完了とみなさない。
   - 起動前に再点検不要と判定した読者は、欠落の対象から外す。
   回復しても結果がそろわない、または資料を補えない場合は、欠けている読者、必要な資料、再開に要る事項を`続行できない理由`に書いて工程を止め、委譲元へ返す。
4. 採否の前に、`未解決の指摘数`と本文に列挙した指摘の項目数を比べる。
   一致しない返却は採否に入らず、両方の数を示して同じ担当へ件数か列挙の是正を求める。
5. 各指摘を、成果物の本文と適用対象の契約に照らして裏付け、採否と根拠、採用分の記録先、または不採用理由（同じ原因の既存指摘へ統合する場合は統合先）を自分のレビュー記録へ残す。
   `未解決の指摘数: 0`も、対応付ける指摘が無いことを記録する。
   - 採る基準: 指摘が根拠とする作成規範の条文に本文が反するか、読者像から本文だけを根拠に行為者・対象・条件・結果を一意に読み取れず、判断・操作・検証を誤るか中断するか。
     文章成果物の実害の判定は`agent-basics:review-standards`の`SKILL.md`「文章成果物の実害」に従い、作成規範への違反は既存要件への指摘とする。
   - 計画やWIの完成条件を満たすこと、機能上の実害が無いこと、説明の追加だけを求める指摘であることは、不採用の根拠に使わない。
     説明の追加の要否は`agent-basics:writing-standards/references/writing.md`「文章の共通規定」の、情報を足す前の判定基準で判定する。
   - 不採用の理由は、指摘ごとに「条文への非該当」「範囲外」「事実誤認」のどれかを特定し、根拠を記録する。
   - 未解決件数に数えるのは、差分と直接影響範囲にある既存要件への指摘だけである。
   - 初回に報告された範囲外の実在する不良は`気付いた改善点:`として受け取り、是正の担当と結果の検収へ渡す。
   - 再レビューでは、既報の追跡と、今回の修正差分・直接影響範囲の指摘を分ける。
     新しい要件と初回レビューの確認不足は、通常の指摘と分けて委譲元へ伝える。
6. 実行レビューの返却では、ファイルごとに直接確認の結果、起動結果の識別子の配列、再点検の省略のどれかを申告する。
   申告の形式と対象集合は`agent-toolkit:atk-mode/roles/exec-review.parent.md`「実行レビューの返却契約」が定める。
   直接確認は、架空の起動識別子を付けずに同契約の`direct`で申告する。

## 読者別探索の返却契約

状態行・続行不能の区分と理由・標識行・一行返却は`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従う。
以下の形式のみを返す。
「未解決の指摘数」には本文に列挙した指摘の項目数と同じ値を書く（再レビュー時の分類付き指摘と初回の確認不足も1項目ずつ数える）。
同じ指摘が複数の成果物に当たる場合は、1項目にまとめて該当する全ファイルと箇所を項目内に示し、1件と数える。
成果物ごとの`判定`には、その成果物に当たる指摘の項目番号を示し、成果物ごとの件数を合計して「未解決の指摘数」にしない。
新たな要件（WIの反映範囲を超える新仕様の提案や網羅性の要求、範囲判定への異論など）は「新しい要件」として分離し、「未解決の指摘数」には計上しない。

```text
状態: completed
未解決の指摘数: <0以上の整数>
対象別の判定と証拠:
- 成果物: <絶対パス>
  完了状態: <completed|blocked>
  比較資料: <対象に対応する比較元・現行本文・差分・判定範囲>
  判定: <指摘の有無と該当する指摘の項目番号、または空範囲>
  根拠: <判定の根拠>
新しい要件: <要求の原文・割当先・範囲の判断への異論などの根拠付き記述。該当なしは「なし」>
再レビュー: <要（範囲・失われる前提・理由）|不要（評価前提の所在）>
<番号付きの指摘ごとの、該当する全ファイルと箇所（行または見出し）、観点、問題点、修正案、根拠とした作成規範の所在（文書と節）、読者像が誤る判断・操作・検証>
<再レビューでは各指摘の分類と、初回レビューの不足を別項目にした記述>
<指摘が無い観点ごとの「指摘なし」>
```

再レビューは`agent-basics:review-standards/references/reviewer.md`「再レビューの要否」で判定する。

「対象別の判定と証拠」は入力の各成果物だけを同じ絶対パスで1回ずつ記載する。
指摘なしと判定範囲が空の成果物も個別に記載する。
`比較資料`・`判定`・`根拠`・`続行できない理由`の値を複数行で書く場合は、欄名の行の下へ3文字以上字下げした行、または先頭2空白の` - `で続ける。
`完了状態`と`続行できない区分`の値は欄名と同じ行に1語で書く。
個別の`完了状態`は全文・比較資料・判定範囲の確認と判定を終えた場合に`completed`、担当内で取得できない外部前提がある場合に`blocked`とする。
`blocked`では、共通契約のとおり該当する判定行を同じインデントの`続行できない区分:`と`続行できない理由:`の連続する2行へ置き換え、不足する資料と読者を示す。
有効な他の成果物の判定は保持する。
全体の`状態: completed`は全対象が`completed`の場合だけ先頭へ置く。
未読・未走査など担当内の残作業は続けてから返す。
