# 実行レビューの起動から収束まで

実装を終えた差分の実行レビューを起動し、返却の受領と修正を経て、統合へ渡せる返却を受理するまでの手順書であり、節の順に実行する。
使うのは実装した側の起動者で、作業`process-wi`ではレーン担当（single-laneではメイン）、`agent-toolkit:atk-mode/playbooks/write-plan.md`ではメインである。
CI修正の系列では、`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「修正系列」の手順4の担当が使う。
複数レーンの実行でメインは実行レビューを起動せず、判断要請への処置、既存不良の処置の時機、統合の許可、最終結果の受領を担う。
合否は実装していない実行レビュー担当の返却で決め、起動側は返却を現物と突き合わせて受理する（原則6、`agent-basics:writing-standards/references/quality-principles-verification.md`）。
終了条件は、本書「収束と統合への引渡し」の条件を満たす返却を受理し、受理の記録を進捗ログ（計画なしでは引き継ぎ記録）へ残した時点である。

## 起動

1. 変更範囲の検証と受入シナリオの`検証結果`が、`agent-toolkit:atk-mode/playbooks/verification.md`「完成条件証拠の検証記録」の形で進捗ログ（計画なしでは引き継ぎ記録）にあることを確かめる（メイン自身の実装も同じ）。
   委譲プロンプトへは記録を再掲せず、残工程の担当と再開先、検証済み・未実施・条件変更の別だけを渡す。
2. 実装を認可した資料から、レビュー基準を`計画`、`WI`、`CI記録`（計画の無いCI失敗の対応）から選ぶ（組み合わせてよい）。
   1回の実行レビューは`cwd`から解決する1つのリポジトリだけを対象とし、リポジトリが異なる基準はレビューを分ける。
   対象WIの`担当モデル.実行レビュー担当`の値は`model_type`と入力`担当モデル`へ渡し、WIごとに違えばレビューを分ける。
   指定値と実行値の比較と記録は`agent-toolkit:atk-mode/references/model-settings.md`「工程別モデル設定」に従う。
3. 単一計画の初回でない起動は、起動方法ごとの次の資料を読んでから入力を決める。
   - 内部の群は`agent-toolkit:atk-mode/references/exec-review-launch-groups.md`を読む。
   - 複数の計画は`agent-toolkit:atk-mode/references/exec-review-launch-plans.md`を読む。
   - `CI記録`だけの基準は`agent-toolkit:atk-mode/references/exec-review-launch-ci.md`を読む。
   - 引き継ぎ再レビューは`agent-toolkit:atk-mode/references/exec-review-launch-handover.md`を読む。
     契約を作り直す時は、直前の契約か初回の計画を基準にし、方式見直しで確定した境界が未反映なら管理表の応答から要求と認可を確かめて加える。
4. 入力を次の表で決める（入力名は`agent-toolkit:atk-mode/roles/exec-review.parent.md`「入力」）。

   | 入力 | 値 |
   | --- | --- |
   | `レビュー基準` | 手順2の基準名だけ。資料は基準ごとの入力へ渡す |
   | `計画` | 計画ファイルの絶対パス |
   | `WI記録` | 計画の`## 実施内容`に無い対象WIのファイル名、要求、完成条件、由来、採否（計画が無ければ全ての対象） |
   | `開始時のHEAD` | 専用branchなら起動の直前に`git merge-base <専用branch> <ベースbranch>`で解決した分岐元（計画の有無によらない）。それ以外で`計画`を含まずに`WI`を渡す時（`CI記録`との併用を含む）は作業開始時のHEAD |
   | `対象HEAD` | 起動の直前に対象worktreeで`git rev-parse HEAD`を実行して得た完全OID |
   | `引き継ぎ記録先` | `agent-toolkit:atk-mode/references/delegation-prompt.md`「引き継ぎ記録先」で決める |
   | `review_contract` | 複数の計画、計画外の条項、新形式AWIのどれかがあれば`agent-toolkit:atk-mode/references/review-contract.md`「`review_contract`の生成」で作り、初回から渡す |
   | `レーン識別子` | 特定のレーンの作業なら渡し、セッション識別名を`<レーン識別子>-exec-review`とする |
   | `受理済みの完成条件証拠` | 同じ計画の進捗ログにある受理済みの返却ファイルのうち後続の担当が読めるものの絶対パス。無ければ`なし` |
   | `レビュー種別`、`round` | 初回は省く。再レビューは本書「ラウンド番号の保持先」の値を`round: <ラウンド番号>`で渡す |
   | `Git管理外の変更` | 引き継ぎ記録にある変更前後の複製の全ての対。無ければ省く |

   リポジトリ、対象HEADからの変更ファイル、検証結果、指摘管理表はレビュー担当が解決する。
5. 基準、開始時点、指摘管理表、`review_contract`が同じリポジトリに属し、渡すパスが実在することを確かめる。
   不足時は起動せず引き継ぎ記録と原本で補い、不具合なら診断を保持して `agent-basics:bugfix` で認可内の是正後に再検証する。
   補えない入力・影響・試行だけを委譲元へ返す。
6. `agents_server`の`start`を、`cwd`に対象worktreeの絶対パス、`subagent_md_path`に`exec-review`、`extra_params`に手順4の入力、`model_type`に手順2の値（無ければ省く）を渡して呼ぶ。
   通知を変えた差分では、検証記録の最終の配送本文の保存先と入力・版・ホスト・生成元を渡し、レビュー担当が全文を開けることを確かめる（ソースのリテラルや合格の総数で代用しない）。
7. 画面表示の変更があれば、`agent-toolkit:atk-mode/roles/usability-review.parent.md`でユーザビリティレビュー担当も並行して起動する。
   文章成果物の読者別探索は`agent-toolkit:atk-mode/roles/reader-fit-review.parent.md`の直接確認の条件、起動単位、入力に従う。
8. 起動の後もレーンは同じ作業ツリーで別の修正を続けてよい（検証の場所はレビュー担当が決める）。
   渡すWIと、計画の`## 実施内容`に「人間由来のWI」「エージェント由来のWI」として挙がった関連WIを合わせて対象WI集合と呼び、これが空でないか`ユーザー指示`由来の行がある時は返却に条件別判定行が出る。

## 完成条件証拠の受領確認

`atk agents wait`で受け取った`agent_message_path`の返却本文を読む。
正式原本の所在が返れば、`agent-toolkit:atk-mode/playbooks/delegation-receiving.md`「受領手段と報告様式の選択」で対応付けた原本を返却本文とする。

1. 返却が`agent-toolkit:atk-mode/roles/exec-review.parent.md`「実行レビューの返却契約」の行（出るべき条件別判定行を含む）を欠くか自然文だけなら受理せず、同じ担当に不足の行を足して出し直させる。
2. `git rev-parse <返却の値>`で解決した`レビューHEAD`が起動時に固定した対象と一致することを確かめる。
   round、指摘管理表、開始時点と前回確認版、再レビューの要否と評価前提を同じ結果として保つ。
   要否・評価前提の欠落や不正は担当へ返し、次のラウンドの起動や「不要」で代えない。
3. 返却の`未解決の指摘数`が`atk review-table show <表の絶対パス> --format=summary --round <round>`の`unanswered_count`と一致し、`recheck_pending_count`があれば0であることを確かめる。
   0でなければ同じ担当に前回の指摘を再確認させる。
4. `読者別探索`の申告が返却契約の定める全ての申告対象と想定読者を覆い、各ファイルの値が返却契約の条件を満たすことを確かめ、満たさなければ同じ担当に探索と判定をやり直させる。
   Git管理下の対象は、`git diff --name-only --diff-filter=d <レビュー開始時点> <レビューHEAD> -- '*.md' '*.md.tmpl'`から`review_contract`で判定対象外としたcommitだけによる変更を除いて求める。
5. 未解決の指摘が1件以上なら、本書「レビュー修正」へ進む。
6. 未解決の指摘が0件なら、対象WI集合の本文を取得し、`agent-toolkit:atk-mode/references/review-record-acceptance.md`「統合時の完成条件判定」で全ての判定行を検収する。
   `達成`行は所在と観測内容の組に加え、指定の記録とcommitの差分（`git show <レビューHEAD>:<パス>`）を実際に読んで確かめる。
   組を欠く`達成`行と、条件文の文末だけを変えた定型句の`達成`行は、件数とHEADが一致していても同じ担当へ差し戻す。
   `失効`の行とレーン担当による条件の除外は、本書「技術判断で外せる完成条件」の境界と、要求の取り下げか不採用の根拠との対応を本文で確かめ（`review_contract`の記述だけをユーザーの判断の代わりにしない）、足りなければ本書「エスカレーションの事由別の扱い」で差し戻す。
7. 受理した返却本文のパス（正式原本ならそのパス）を、計画名、対象WI集合、`レビューHEAD`、原要求と`review_contract`、指摘管理表の所在とroundに対応付け、`受理済みの完成条件証拠`として進捗ログ（計画なしでは引き継ぎ記録）へ記録する。
8. HEADが変わったら`agent-toolkit:atk-mode/references/exec-review-head-update.md`で影響を調べ、必要と明示された範囲だけを再レビューする。

## 返却に含まれる既存不良の受領

差分の外として指摘管理表から外した不良は`気付いた改善点:`行で届き、受領側は処置の時機だけを決めて、原因分析と起草は独立した投入担当へ任せる。

1. 各ラウンドの通知、返却、走査記録で、管理表から外した候補と`気付いた改善点:`行の対応を確かめ、行を要求ごとに保つ。
   process-wi中の処置の時機は、レーン担当が受領した不良もメインが`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」で決める。
2. 正式な対応は`agent-toolkit:atk-mode/roles/add-wi.parent.md`の専念型の投入担当へまとめて渡し、受領側は`agent-basics:bugfix`の起動と走査記録からの原因と対策の読み取りをしない。
   要求ファイルには`気付いた改善点:`行の全文と走査記録の絶対パスを`確定済みの観測`へ書く（原因・広がり・処置は`投入前に確定すべき事項`）。
3. 起動した投入担当の`session_id`と対象の不良を引き継ぎ記録へ対応付け、再レビューで同じ不良が報告されても担当を重ねて起動しない。
4. 投入担当の完了を待たずに収束、統合、公開を進め、最終の作業完了の報告の前に全ての担当の終了を完了通知で確かめる。
5. process-wi中に保存済みAWIの正式名を受けたら、`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「開始後に追加されたWIの確認」の手順3で今回の処理へ加えるかを判定する。
6. 不良ごとに正式名、担当、選定と計画、是正の結果か残る工程を引き継ぎ記録へ対応付け、レビューの未解決件数と分けて再レビューの後も追跡する。
   実行全体の完了の前に、是正の結果、根拠付きの非該当の判定、先送り条件に当たる事実と残作業と再開条件のどれかを検収する（不採用の記録、報告済みであること、指摘管理表の未解決0件は根拠にならない）。

## レビュー修正

修正と、その採否、方針、検収は対象worktreeの書込所有者が持つ（手順は`agent-toolkit:atk-mode/playbooks/review-fix.md`）。

1. 起動側が書込所有者（レーン担当、single-laneのメイン）なら、同書に従って自分で直す。
2. 書込所有者が別のthreadなら、毎ラウンド全ての指摘を元の要求、計画、契約、既存の証拠、応答と比べ、`agent-basics:review-standards/references/reviewee.md`に従い、根拠と価値・QCDの比較を指摘ごとに`レビュー参考意見`へ書く。
   この工程では探索と再現を追加せず、応答の確定は書込所有者に任せる。
   合成した構成だけの結果は通常運用の結果と区別する。
   そのthreadへ`send_message`の`instruction: レビュー指摘の対応をせよ`を送り、roundは表から解決させる。
   `extra_params`には全ての計画の`レビュー指摘管理表`と、あれば`レビュー参考意見`を`agent-toolkit:atk-mode/roles/exec.parent.md`「入力」の形で渡す。
3. 同じthreadを続けられなければ、`agent-toolkit:atk-mode/playbooks/delegation-recovery.md`「継続と新規起動」に従って`レビュー修正担当`を起動し、`再開位置`に`~/.claude/plans`の計画の絶対パスを、管理表と参考意見を手順2の形で渡す。
4. 修正の返却（`対応完了`、`対応完了（再レビュー不要）`）に`検証結果`と`画面差分`の行が無ければ出し直させる。
   全指摘について本書「応答済みの判定」で未応答0件と、採用した修正の検証を確かめる。
   返却の種類、指摘数、修正commitの有無で再レビューの要否を決めない。
5. レビュー担当が「要」とした範囲だけ、同じthreadへ`send_message`の`instruction: 再レビューせよ`、`round: <ラウンド番号>`、送信直前に固定した`対象HEAD: <完全OID>`を送る。
   - 方式の見直しで守る挙動と許容する挙動を決めた時は、起動側が管理表の応答を要求と認可に照らして確かめ、`review_contract`へ反映する。
   - 開始時からの累積差分に別の計画の認可commitがあれば、判定対象外commitを最新のOIDへ更新する。
   - 契約を更新する時は`agent-toolkit:atk-mode/references/review-contract.md`「`review_contract`の生成」に従い、初回の条項を保つ。
     初回が計画だけの時も契約を作り、更新をまとめた新版を`review_contract: <絶対パス>`で渡す。
   - 前回の後に履歴を書き換えたら、`agent-toolkit:atk-mode/playbooks/history-rewrite.md`「WI実装commitの対応の継承」が保存したJSONを`rewrite_map: <絶対パス>`で渡す（引き継ぎ再レビューでは`extra_params`）。
   - `画面差分: あり`で未起動のレビューには初回を依頼する。
     既に判定を受けた範囲は、その担当が必要と明示した時だけ再レビューする。
6. レビュー担当が「不要」とした範囲は、`agent-basics:review-standards/references/reviewee.md`「方式見直しと再レビュー」に従い、評価の前提を修正後も保つか確かめる。
   前提が保たれる場合は、修正後の検証が示す条件の証拠を受領側が検収する。
   不足があれば修正担当へ補完を求める。
7. 再レビューを省くと確かめたら、統合入力HEADを判定行の`レビューHEAD`と別に確定する（amendかautosquashでOIDが変わるため）。
   新しい画面資産が加わっていれば、ユーザビリティレビューは省かず同じHEADで依頼する。
   未応答0件と管理表の修正前後の短縮OIDの対応を確かめ、`git rev-parse --short=7`で解決した専用branchのHEADが修正後の短縮OIDと一致することを確かめる。
   その値を統合入力HEAD（`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「統合の指示と受領」）とする。
   受領確認は最後に実際にレビューした`レビューHEAD`で行い、判定行の対象を修正後のHEADへ付け替えない。

## ラウンドの遷移

1. 再レビューの指摘を受けたら、修正の指示を確定する前に本書「反復原因の判定」を行う。
2. 同じレビュー担当へ、同じ`開始時のHEAD`（`CI記録`では`修正系列の開始時のHEAD`）、レビュー基準、指摘管理表を渡して再レビューさせる。
   契約を更新した場合は本書「レビュー修正」の新版を渡し、それ以外では直前の契約か計画を使う。
   再レビューの範囲は、前回指摘の修正、前回のレビューHEADから今回のHEADまでの修正差分、変えた識別子と契約の直接影響範囲である（定義元は`agent-basics:review-standards/references/reviewer.md`「再レビューの場合」）。
3. 本書「完成条件証拠の受領確認」の手順2で保った開始時点とHEADは、rebaseで開始時点が変わっても上書きせず、両方の差分の一致とファイル別の申告を同じ受領確認へ渡す。
   履歴を書き換えた後の開始時点には、書き換え後の対応するOIDを使う。
4. 修正に着手する前に、`agent-basics:review-standards/references/reviewee.md`「方式見直しと再レビュー」の手順11に該当するかを確かめる。

## ラウンド番号の保持先

ラウンド番号の出所は、指摘管理表の同じ系統（track）に記録された最大のラウンド番号である。
初回レビューは1、再レビューは最大値に1を足した値とし、1つのラウンドは1つの表の1つの番号で決まる。
各ラウンドの契約ファイルも保ち、現在の契約へ更新した後も、前回の契約を前回の開始時点とHEADとともに保つ。

## 応答済みの判定

起動側は、`atk review-table show <表の絶対パス> --format=summary --round <対応したround>`の`unanswered_count`が0の時だけ再レビューへ進む。

## 反復原因の判定

反復した原因と、どの担当へ何を返すかを決める。

1. `atk review-table show <表の絶対パス> --track <対象track> --format=jsonl`で過去の指摘と応答を読み、今回の指摘と比べる。
2. 違反した規定と発生条件の一致、修正の不足、新しい要件、レビュー契約の不足を判定する。
   完成条件や指摘の件数が同じことだけで同じ指摘と判定しない。
3. 同じ機構で同じ向きの境界の指摘が前のラウンドに続いて出たら、発生条件が違っても、個別修正の前に方式を見直す。
   どの機構が何をどう誤って扱い、誰に何の害を生むかで比べる。
   同じ待機判定でも、作業を待機と数える誤りと待機を作業と数える誤りは逆向きである。
   要求を保ったまま、判定する入力を狭める案や、判定できない入力を害の少ない側へ倒す案を現方式と比べる。
   修正側は比較と採否を管理表の応答に残し、誤りの向きによって害が異なる場合は、守る挙動と許容する挙動も書く。
4. 同じ指摘なら、局所の修正の前に`agent-basics:bugfix`を起動し、`agent-basics:bugfix/references/recurrence.md`「前回の対策を調べる」で前回の修正が防げなかった理由を特定させる。
5. 新しい要件か認可範囲の変更なら本書「エスカレーションの事由別の扱い」へ回し、レビュー契約の不足なら`review_contract`を直してから再レビューへ渡す。

## 収束と統合への引渡し

1. 次の全てを満たした時に収束とする。
   - 初回レビューは全て完了し、レビュー担当が要とした範囲の独立確認と、不要とした範囲の修正後の検証がそろっている。
   - 元のWI全体の条件別判定が`agent-toolkit:atk-mode/references/review-record-acceptance.md`「統合時の完成条件判定」の受理条件を満たす。
   - 全ての指摘管理表の未解決の指摘が0件である。
2. 指摘管理表は`agent-toolkit:atk-mode/references/review-record-table.md`「レビュー指摘管理表の保存」に従って保存するか削除する。
3. 統合は実行レビューの受理の後に行い、複数レーンの実行では`統合準備完了`を返して、メインから`統合許可`を受けてから統合へ進む（`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「統合の許可」）。

## エスカレーションの事由別の扱い

担当から判断要請を受けた委譲元（レーン担当からはメイン、修正担当からは起動した担当）が使う。
処置の前に、担当が付けた区分（「要件」「要求の変更」など）を`agent-toolkit:atk-mode/playbooks/confirmation.md`「要件と技術判断を分ける」で確かめ、ユーザーにしか決められない残りを同書「確認要否の判定」で分ける。
登録漏れ、判定行の不備、検証の失敗、技術的に解消できる実装の欠陥など担当の内部で補える不足は同じ担当に直させ、エスカレーションは担当が補えない判断、認可、入力、外部環境の不足に限る。

| 事由 | 委譲元の処置 | 再開位置の記録 |
| --- | --- | --- |
| 計画の条項とWIの明示条件の衝突 | WIの明示条件から契約が一意に定まればWIを優先して確定し、同じレビューイーへ返す。人間由来の要求の解釈が分かれれば、ユーザーに確認して確定してから返す | 不要 |
| 選定結果の`担当モデル`とAWI本文のモデル指定の不一致 | 選定原本の該当項目の`担当モデル`だけを本文の組へ直し（初回の配分と判断履歴は保つ）、`atk run-script pick-wi-check -- <元の選定原本の絶対パス> --work-dir <対象リポジトリの絶対パス>`の終了コード0を確かめる。未確定のモデルを推測させず、下位の担当で補わない。`実装担当`が変われば返却元の終了を確かめて新しい`model_type`で同じレーンを起動し直し、`実行レビュー担当`だけなら同じthreadへ続行を返す | 不要 |
| 完成条件の変更か除外の判断要請 | 本書「技術判断で外せる完成条件」に当たればメインが判断と根拠を担当へ返して記録させ、当たらなければユーザーの判断の記録を確かめ、無ければ`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」で確認する | 必要 |
| ユーザーの選好、要件、認可範囲の変更 | ユーザーに確認して回答を同じレビューイーへ返す | 不要 |
| 外部状態か権限の不足 | 回復の手段を確かめ、ユーザーの操作が要れば確認する。既存不良が原因なら既存不良の行も適用する | 必要 |
| 同じ論点の2回目以降の差し替え | `agent-basics:review-standards/references/reviewee.md`「同じ指摘の反復」に従う（反復の回数だけを確認の理由にしない） | 必要 |
| 対象リポジトリや配布物のhook・CLI・規範などの既存不良による続行不能 | 担当の回復と欠陥の処置を分け、`agent-toolkit:atk-mode/references/conduct.md`「完遂と先送り」の条件の内側で判定する。process-wi中は`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」で時機を決める | 必要 |
| 同じthreadを続けられない | 後続の担当へ同じ計画ファイル（`~/.claude/plans`配下）、指摘管理表、確定した判断を引き継ぐ。既存不良が原因なら前の行も判定する | 必要 |

「再開位置の記録」が「必要」の事由では、計画ファイルを`~/.claude/plans`へ保存し、`atk run-script plan-progress --`で`## 進捗ログ`へ完了した工程、続行できない理由、再開位置を記録し、キューの項目は今の状態のまま保つ。
完成条件の判断をUWIで待つ場合は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「未確定判断の保留と暫定判断」に従って元のAWI全体をそのUWIへの依存で待たせる。
回答の前に失効を認めて統合へ進めず、この待機は全ての要求を不採用とする`reject`と別に扱う。
回答を得たら、既存の指摘管理表とラウンド番号を引き継いで再開する。

## 技術判断で外せる完成条件

完成条件の変更か除外は、次の全てを満たす時に技術判断で行える。
要求の由来と、変える観測の方法や判定の水準の由来を分けて判定し、満たさなければユーザーの判断の記録を探して、無ければユーザーに確認する。

- 変えるか除く部分は、ユーザー自身の指定でなくエージェントの具体化である（明示の由来の要求でも、その目的、対象範囲、期待する結果、明示された検証の水準は保つ）。
- `agent-toolkit:atk-mode/playbooks/confirmation.md`「認可を要する操作」の「ユーザーが確定した判断の変更」に当たらず、ユーザーにしか決められない値（同書「確認要否の判定」）も要しない。
- 害の大きさに見合う広がりの探索と再発防止に要る結果と品質を保つ（`agent-basics:bugfix/references/spread.md`「害が大きい時」、`agent-basics:bugfix/references/prevention.md`「案を比べる順」）。
  確認の手段は、同じ水準に届く別の手段へ変えてよい。

`source`を持つAWIで目的の達成に要らないエージェント起草の条件は、レーン担当が上の境界を確かめて除き、判断を記録して報告する。
それ以外の変更と除外の判断要請はメインが判定し、統合の時にもメインが記録と境界を確かめる。
記録の項目と記録先は`agent-toolkit:atk-mode/references/review-record-verdicts.md`「失効の根拠」の技術判断の2つに従って判断の時点で選ぶ。
対話の中の判断を根拠にする時は、同書「失効の根拠」の会話の証拠（発話の逐語と、同じ発話の反復と区別できる時点と文脈）を、その証拠を使う担当へ渡す。
メインは出所の抽出の完了を待たずに回答を返す。

返す報告に含める項目: 起動した実行レビューとレビュー基準、受理した返却のパスと`レビューHEAD`、ラウンドごとの未解決件数、再レビューを省いた計画と理由、受領した既存不良と投入したWI、エスカレーションの処置と確認した事項、統合入力HEAD。
