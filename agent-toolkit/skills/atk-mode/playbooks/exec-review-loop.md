# 実行レビューの起動から収束まで

実装を終えた変更差分の実行レビューを起動し、返却を受領し、指摘を修正へ渡して、統合へ渡せる返却を受理するまでの手順書であり、節の順に実行する。
使うのは実装を担当した側の起動者で、作業`process-wi`ではレーン担当（single-laneではメイン）、`agent-toolkit:atk-mode/playbooks/write-plan.md`ではメインである。
CI修正の系列では、`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「修正系列」の手順4で起動する担当が使う。
複数レーンの実行でメインが担うのは、判断要請への処置、既存不良の処置の時機、統合の許可、最終結果の受領である（`agent-toolkit:atk-mode/playbooks/process-wi-execution.md`）。
レビューイーは、`process-wi`では対象レーンのレーン担当、`write-plan`ではメイン、公開工程のCI修正では公開担当が起動する`CI修正担当`である。
合否は実装していない実行レビュー担当の返却で決め、起動側は返却を現物と突き合わせて受理し、起動した担当の終了まで追跡する。
これは原則6（`agent-basics:writing-standards/references/quality-principles-verification.md`）を中心に、原則3と原則7を適用したものである。
原則3の本文は`agent-basics:writing-standards/references/quality-principles-facts.md`にある。
原則7の本文は`agent-basics:writing-standards/references/quality-principles-ownership.md`にある。
終了条件は、本書「収束と統合への引渡し」の条件を満たす返却を受理し、受理の記録を進捗ログ（計画なしでは引き継ぎ記録）へ残した時点である。

## 起動

1. 変更範囲の検証と受入シナリオの`検証結果`が、`agent-toolkit:atk-mode/playbooks/verification.md`「完成条件証拠の検証記録」の形で進捗ログ（計画なしでは引き継ぎ記録）にあることを確かめる（メイン自身の実装も同じ）。
   レビュー担当がその記録を読むので委譲プロンプトへ再掲せず、起動側が持つ残工程は後続の担当と再開先、検証済み・未実施・条件変更の別を整理して渡す。
2. その実装を認可した手元の資料からレビュー基準を決める。
   対応する計画があれば`計画`、対象WIがあれば`WI`、計画が無くCI失敗に対応した実装なら`CI記録`とし、組み合わせてよい。
   1回の実行レビューは`cwd`から解決する1つのリポジトリだけを対象とし、リポジトリが異なる基準はレビューを分ける。
   対象WIに`担当モデル.実行レビュー担当`の指定があれば、その値を`model_type`と入力`担当モデル`へ渡す（読者別探索の担当にも引き継がれる）。
   WIごとに指定が違えばレビューを分け、比較と記録は`agent-toolkit:delegation/references/process-model-settings.md`「工程別モデル設定」に従う。
3. 単一計画の初回でない起動は、該当する節を読んでから入力を決める。
   - 内部の群へ分けて実装した時は`agent-toolkit:atk-mode/references/exec-review-launch-variants.md`「内部の群」を読む。
   - 同じレーンに複数の計画がある時は同書「複数の計画」を読む。
   - レビュー基準が`CI記録`だけの時は同書「CI記録」を読む。
   - 前の担当から再レビューを引き継ぐ時は同書「引き継ぎ再レビュー」を読む。
4. 入力を次の表で決める（入力名は`agent-toolkit:atk-mode/roles/exec-review.parent.md`「入力」）。

   | 入力 | 値 |
   | --- | --- |
   | `レビュー基準` | 手順2の基準名だけ。資料は基準ごとの入力へ渡す |
   | `計画` | 計画ファイルの絶対パス |
   | `WI記録` | 計画に無い対象WIのファイル名、要求、完成条件、由来、採否（計画の`## 実施内容`に挙がったWIはレビュー担当が取得する。計画が無ければ全ての対象） |
   | `開始時のHEAD` | 専用branchなら起動の直前に`git merge-base <専用branch> <ベースbranch>`で解決した分岐元（計画の有無によらない）。それ以外で`WI`だけを渡す時は作業開始時のHEAD |
   | `引き継ぎ記録先` | `agent-toolkit:delegation/references/base-contract-handoff.md`「引き継ぎ記録先」で決める |
   | `review_contract` | 複数の計画、計画外の条項、新形式AWIのどれかがあれば`agent-toolkit:atk-mode/references/review-contract.md`「`review_contract`の生成」で作り、初回から渡す |
   | `レーン識別子` | 特定のレーンの作業なら渡し、セッション識別名を`<レーン識別子>-exec-review`とする |
   | `受理済みの完成条件証拠` | 同じ計画の進捗ログにある受理済みの返却ファイルのうち後続の担当が読めるものの絶対パス。無ければ`なし`（使える条件は`agent-toolkit:atk-mode/references/review-record.md`「受理済み判定への参照」） |
   | `レビュー種別`、`round` | 初回は省く（初回レビューとround 1になる）。再レビューは本書「ラウンド番号の保持先」の値を`round: <ラウンド番号>`で渡す |
   | `Git管理外の変更` | 引き継ぎ記録にある変更前後の複製の全ての対（`agent-toolkit:atk-mode/playbooks/implementation.md`「実装」の手順で作る）。無ければ省く |

   リポジトリ、レビューHEAD、変更ファイル、検証結果、指摘管理表はレビュー担当が解決する。
5. 全ての基準、開始時点、指摘管理表、`review_contract`が同じリポジトリに属し、渡すパスが実在することを確かめ、不足があれば起動せずに不足する入力か条項を委譲元へ返す。
6. `agents_server`の`start`を、`cwd`に対象worktreeの絶対パス、`subagent_md_path`に`exec-review`、`extra_params`に手順4の入力、`model_type`に手順2の値（無ければ省く）を渡して呼ぶ。
   通知を変えた差分では、`agent-toolkit:atk-mode/playbooks/verification.md`「完成条件証拠の検証記録」が対応付けた最終の配送本文の保存先と、入力・版・ホスト・生成元を渡す。
   レビュー担当がその全文を開けることを確かめ、ソースのリテラルや合格の総数で代用しない。
7. 画面表示の変更があれば、`agent-toolkit:atk-mode/roles/usability-review.parent.md`に従ってユーザビリティレビュー担当も並行して起動する。
   文章成果物の読者別探索は`agent-toolkit:/share/reader-fit-review.parent.md`の直接確認の条件と起動単位に従う。
   起動側が読者別探索を起動する時は、Git管理下の比較資料を同書「入力」のGit参照の形で渡し、再レビューでは比較元を前回のレビューHEADにする。
8. 起動の後もレーンは同じ作業ツリーで別の修正を続けてよい（検証の場所はレビュー担当が`agent-toolkit:atk-mode/roles/exec-review.subagent.md`「操作区分」で決める）。
   渡すWIと、計画の`## 実施内容`に「人間由来のWI」「エージェント由来のWI」として挙がった関連WIを合わせた集合を、対象WI集合と呼ぶ。
   対象WI集合が空でない時と`ユーザー指示`由来の行がある時を「証拠要求あり」と呼び、その返却には条件別判定行が出る。
   受理した返却の保存先（`atk agents wait`が示す`agent_message_path`）は、計画名と対象WI集合に対応付けて後続の検収へ渡す。

## 完成条件証拠の受領確認

`atk agents wait`で受け取った`agent_message_path`の返却本文を読む。
正式原本の所在が返った時は、`agent-toolkit:delegation/references/receiving-format.md`「受領手段と報告様式の選択」で担当・終了・原本を対応付け、その原本を返却本文とする。
直接実装でもレーン統合でも、受領側はこの確認で`agent-toolkit:atk-mode/references/review-record.md`「統合時の完成条件判定」の意味の検収を1回行い、統合時は受理の記録を再利用する。

1. 返却が`agent-toolkit:atk-mode/roles/exec-review.parent.md`「実行レビューの返却契約」の行（`状態`、`レビューHEAD`、`未解決の指摘数`、`読者別探索`、開始時点と前回確認版の行、証拠要求ありなら条件別判定行）を満たすことを確かめる。
   行が欠けた返却と自然文だけの返却は受理せず、同じ担当に不足の行を足して出し直させる。
2. `git rev-parse <返却の値>`で解決した`レビューHEAD`が、対象worktreeの最新のHEADと完全に一致することを確かめる。
   一致しなければ同じ担当に現在のHEADで判定し直させ、一致したら、round、指摘管理表のパス、`レビュー開始時点`、`前回確認版の開始時点`、`前回確認版HEAD`を一連の結果として保つ。
3. 返却の`未解決の指摘数`が`atk review-table show <表の絶対パス> --format=summary --round <round>`の`unanswered_count`と一致し、同じsummaryの`recheck_pending_count`があれば0であることを確かめる。
   0でなければ、同じ担当に前回の指摘の再確認を指示する。
4. `読者別探索`のファイルごとの申告を、Git管理下の集合とGit管理外の集合に突き合わせる。
   Git管理下の集合は、`git diff --name-only --diff-filter=d <レビュー開始時点> <レビューHEAD> -- '*.md' '*.md.tmpl'`から`review_contract`で判定対象外としたcommitだけによる変更を除いたものである。
   Git管理外の集合は、起動側が持つ回答下書きの絶対パスと、引き継ぎ記録の`Git管理外の変更`の元ファイルのうち`.md`か`.md.tmpl`のものである。
   各ファイルに起動結果の識別子、条件（`agent-toolkit:/share/reader-fit-review.parent.md`「起動」）を満たす直接確認の`direct`、返却契約の条件を満たす`再点検対象なし`のどれかがあることを確かめる。
   直接確認と起動先の結果を合わせて全てのファイルと想定読者を覆い、`文章成果物なし`は両方の集合が空の時に限り、満たさなければ同じ担当に探索と判定をやり直させる。
5. 未解決の指摘が1件以上の返却は、修正へ渡す正常な中間結果として受け取り、本書「レビュー修正」へ進む。
6. 未解決の指摘が0件の返却では、対象WI集合の本文を取得し、`agent-toolkit:atk-mode/references/review-record.md`「統合時の完成条件判定」の手順で全ての判定行を検収する。
   `達成`行は、所在と観測内容の組を持つことに加え、指定の記録とcommitの差分（リポジトリ内は`git show <レビューHEAD>:<パス>`）を実際に読んで確かめる。
   組を欠く`達成`行と、条件文の文末だけを変えた定型句の`達成`行は、件数とHEADが一致していても同じ担当へ差し戻す。
   `失効`の行とレーン担当による条件の除外は、本書「技術判断で外せる完成条件」の記録先を読んで境界を確かめる。
   `review_contract`の記述だけをユーザーの判断の代わりにせず、要求の取り下げか不採用の根拠との対応を本文で確かめ、根拠の足りない変更は本書「エスカレーションの事由別の扱い」で差し戻す。
7. 受理した返却本文のパス（正式原本ならそのパス）を、`レビューHEAD`、原要求と`review_contract`、指摘管理表の所在とroundに対応付け、計画の進捗ログへ`受理済みの完成条件証拠`として記録する（計画なしでは引き継ぎ記録）。
8. 受理の後にHEADが変わったら、`agent-toolkit:atk-mode/references/exec-review-launch-variants.md`「HEADの更新と再レビューの要否」で影響が無いと確かめた計画を除き、最新のHEADで全ての条件を判定し直した返却を受理してから先へ進む。

## 返却に含まれる既存不良の受領

差分の外として指摘管理表から外した不良は`気付いた改善点:`行で届き、受領側は処置の時機を決め、原因分析と起草は独立した投入担当へ任せる（レビューの受領と調査の文脈を分け、総費用を抑えるため）。

1. 各ラウンドの通知、返却、走査記録を受けた時点で、管理表から外した候補と`気付いた改善点:`行の対応を確かめ、行を要求ごとに保つ。
   レーン担当が受領した不良も同じ扱いとし、process-wiの処置の時機はメインが`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」で決める。
   process-wiの外では、`agent-toolkit:delegation/references/receiving-followup.md`「受領後の扱い」で時機を決める。
2. 正式な対応は、`agent-toolkit:atk-mode/roles/add-wi.parent.md`の専念型の投入担当へまとめて渡し、受領側は`agent-basics:bugfix`の起動と走査記録からの原因と対策の読み取りを行わない。
   要求ファイルには、`気付いた改善点:`行の全文と走査記録の絶対パスを要求の趣旨と`確定済みの観測`へ、原因・広がり・処置の検討項目を`投入前に確定すべき事項`へ書く（投入先は`agent-toolkit:atk-mode/references/add-wi-inputs.md`）。
3. 起動した投入担当の`session_id`と対象の不良を、そのレビューの引き継ぎ記録へ引き渡し済みとして対応付け、再レビューか引き継ぎ再レビューで同じ不良が報告されたら担当を重ねて起動しない。
4. 投入担当の完了を待たずに、レビューの収束、統合、公開を並行して進める。
   投入担当の終了はバックグラウンドの完了通知で確かめ、最終の作業完了の報告の前に全ての担当の終了を確かめる（統合と公開の前提条件には含めない）。
5. 保存済みAWIの正式名を受けたら、process-wi中は`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「開始後に追加されたWIの確認」の受領時の判定で今回の選定・担当・追加の計画へつなぐ。
6. 不良ごとに、正式名、担当、選定と計画、是正の結果か残る工程を既存の引き継ぎ記録へ対応付け、AWIの保存の後も是正の結果を検収するまで追跡する。
   実行全体の完了の前に、是正の結果、根拠付きの非該当の判定、先送り条件に当たる事実と残作業と再開条件のどれかを検収する（不採用の記録、報告済みであること、指摘管理表の未解決0件は完了の根拠にならない）。
   差分外の不良はレビューの未解決件数と分けて管理し、初回に報告された未処置の事項は再レビューでも同じ記録で追跡する。

## レビュー修正

修正は対象worktreeの書込所有者が行い、採否、対象commit、修正方針、成果物とGitの状態と検証の検収は修正する担当が持つ（手順は`agent-toolkit:atk-mode/playbooks/review-fix.md`）。

1. 起動側が書込所有者（レーン担当、single-laneのメイン）なら、同書に従って自分で直す。
2. 書込所有者が別のthreadなら、毎ラウンド全ての指摘を元の要求、計画、契約、既存の証拠、応答と比べ、前提・必要性・修正の規模への疑問を指摘と対応付けて`レビュー参考意見`にする。
   追加のコードの探索、再現、詳しい調査は行わず、分からない点は疑問として渡し、疑いだけで指摘を消すことも対応済みにすることもしない。
   そのthreadへ`send_message`の`instruction: レビュー指摘の対応をせよ`を送り、`extra_params`に全ての計画の`レビュー指摘管理表`（1件は絶対パス、複数は絶対パスのJSON配列）と、あれば`レビュー参考意見`を渡す。
   自由文も同じ名前の入力で渡し、roundは表から解決させる。
3. 同じthreadを続けられなければ、`agent-toolkit:delegation`の`SKILL.md`「継続と新規起動」と`agent-toolkit:atk-mode/roles/exec.parent.md`「入力」に従って`レビュー修正担当`を起動する。
   `再開位置`に`~/.claude/plans`の計画の絶対パスを渡し、管理表と参考意見は手順2と同じ形で渡して、引き継ぎ記録で全ての計画との対応を保つ。
4. 修正の返却（`対応完了`、`対応完了（再レビュー不要）`）に`検証結果`と`画面差分`の行が無ければ出し直させる。
   修正commitと履歴の統合の有無で返却の種類を判定せず、本書「応答済みの判定」で未応答0件を確かめ、全ての指摘を根拠付きで不採用とした`対応完了`も通常どおり再レビューへ進める。
5. `対応完了`では、同じレビューのthreadへ`send_message`の`instruction: 再レビューせよ`と`round: <ラウンド番号>`を送る（組み込みの委譲機構では`agent-toolkit:delegation/references/sending.md`の生成用CLIを使う）。
   - 送る直前に、開始時からの累積差分に別の計画の認可commitがあるかを確かめる。
     あれば`agent-toolkit:atk-mode/references/review-contract.md`「`review_contract`の生成」で判定対象外commitを最新のOIDへ更新し、初回の条項を含む契約を`review_contract: <絶対パス>`で渡す。
   - 前回の後に履歴を書き換えたら、`agent-toolkit:atk-mode/playbooks/history-rewrite.md`「WI実装commitの対応の継承」が保存したJSONを`rewrite_map: <絶対パス>`で渡す（引き継ぎ再レビューでは`extra_params`）。
   - `画面差分: あり`なら、`agent-toolkit:atk-mode/roles/usability-review.parent.md`に従う再判定（未起動なら初回）も同時に依頼する。
6. `対応完了（再レビュー不要）`では、修正が`agent-basics:review-standards/references/reviewee.md`「方式見直しと再レビュー」の再レビューを省ける修正に当たることを確かめる。
   低リスクの段階だけは、修正後のHEADで`agent-toolkit:atk-mode/playbooks/review-fix.md`「完了報告」の判定コマンドを実行する。
   直前の返却に、修正に関わる`未達`か`根拠不足`の行が`agent-toolkit:atk-mode/references/review-record.md`「統合時の完成条件判定」で受理できないまま残れば、再レビューする。
7. 再レビューを省くと確かめたら、次の順で統合入力HEADを確定する（amendかautosquashでOIDが変わるので、判定行を出した時の`レビューHEAD`とは別に保つ）。
   1. `画面差分: あり`で新しい画面資産が加わっていれば、ユーザビリティレビューを省かず同じHEADで依頼する。
   2. 本書「応答済みの判定」で未応答0件と、管理表の該当行に修正前後の短縮OIDの対応があることを確かめる。
   3. 専用branchのHEADを`git rev-parse --short=7`で解決し、管理表の修正後の短縮OIDと一致することを確かめる。
   4. その値を統合入力HEAD（`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「統合の指示と受領」）として保つ。
      `agent-toolkit:atk-mode/references/lane-integration-format.md`「マージありの統合」のcommitの一致確認はこの値で行う。
   5. 受領確認では最後に実際にレビューした`レビューHEAD`と突き合わせ、判定行の対象を修正後のHEADへ形式的に付け替えない。

## ラウンドの遷移

1. 再レビューの指摘を受けたら、修正の指示を確定する前に本書「反復原因の判定」を行う。
2. レビューイーは全ての指摘の採否と応答を記録し、採用した指摘を直し、変更範囲を検証して証拠を指摘管理表へ記録する。
   採用0件も正常な対応完了とし、commitと履歴の統合は実差分がある時だけ行う（計画ファイルだけの修正ではcommitしない）。
3. 同じレビュー担当へ、同じ`開始時のHEAD`（`CI記録`では`修正系列の開始時のHEAD`）、レビュー基準、初回に受理した`review_contract`（直接の契約かMarkdownファイルの絶対パス）、指摘管理表を渡して再レビューさせる。
   計画だけから条項を作った場合は、初回の計画の内容を使い続ける。
   再レビューの範囲は、前回指摘の修正、前回のレビューHEADから今回のHEADまでの修正差分、変えた識別子と契約の直接影響範囲である（定義元は`agent-basics:review-standards/references/reviewer.md`「再レビューの場合」）。
   範囲外の既存不良を新しく探すのは初回だけで、既報の不良の根拠の補充、割当、未完了の処置は追跡を続ける。
4. 返却ごとに今回の`レビュー開始時点`と、2回目以降の`前回確認版の開始時点`と`前回確認版HEAD`を保つ。
   rebaseで開始時点が変わっても前回の値を上書きせず、両方の差分の一致とファイル別の申告を同じ受領確認へ渡し、履歴を書き換えた後の開始時点には書き換え後の対応するOIDを使う。
5. 第3ラウンド以降も未解決の指摘が残る時は、修正に着手する前に`agent-basics:review-standards/references/reviewee.md`「方式見直しと再レビュー」を適用させる。
   方式を置き換えた直後の再レビューは、開始時点からの全差分を対象にする。
6. レビュー修正、mergeの競合の解消、rebaseでHEADが変わった時に再レビューする計画は、`agent-toolkit:atk-mode/references/exec-review-launch-variants.md`「HEADの更新と再レビューの要否」で決める。

## ラウンド番号の保持先

ラウンド番号の出所は、指摘管理表の同じ系統（track）に記録された最大のラウンド番号である。
初回レビューは1、再レビューは最大値に1を足した値とし、1つのラウンドは1つの表の1つの番号で決まる。
各ラウンドの契約ファイルも保ち、現在の契約へ更新した後も、前回の契約を前回の開始時点とHEADとともに保つ。

## 応答済みの判定

レビューイーは全ての指摘への応答を`agent-toolkit:atk-mode/playbooks/review-fix.md`「実行レビュー反復での記録」に従って記録する。
起動側は`atk review-table show <表の絶対パス> --format=summary --round <対応したround>`の`unanswered_count`が0の時だけ再レビューへ進む。

## 反復原因の判定

再レビューの指摘を受けて修正の指示を確定する前に、反復した原因とどの担当へ何を返すかを決める（レビューイー側の比べ方は`agent-basics:review-standards/references/reviewee.md`「同じ指摘の反復」）。

1. `atk review-table show <表の絶対パス> --track <対象track> --format=jsonl`で過去の指摘と応答を読み、今回の指摘と比べる（summaryの`previous_findings`のround番号と行番号を手掛かりにする）。
2. 違反した規定と発生条件の一致、修正の不足、新しい要件、レビュー契約の不足を判定する。
   完成条件や指摘の件数が同じことだけで同じ指摘と判定しない。
3. 同じ指摘と確かめたら、局所の修正の前に`agent-basics:bugfix`を起動し、`agent-basics:bugfix/references/recurrence.md`「前回の対策を調べる」で前回の修正が防げなかった理由を特定させる。
   既存の設計を保つ案と置き換える案を比べた根拠と採否の理由は、指摘管理表の応答欄へ記録させる。
4. 新しい要件か認可範囲の変更なら本書「エスカレーションの事由別の扱い」へ回し、レビュー契約の不足なら`review_contract`を直してから再レビューへ渡す。

## 収束と統合への引渡し

1. 次の全てを満たした時に収束とする。
   - 全てのレビューが最終のHEADで完了しているか、最後のレビューの後の差分が`agent-toolkit:atk-mode/references/exec-review-launch-variants.md`「HEADの更新と再レビューの要否」で影響しない修正だけである。
   - 元のWI全体の条件別判定が`agent-toolkit:atk-mode/references/review-record.md`「統合時の完成条件判定」の受理条件を満たす。
   - 全ての指摘管理表の未解決の指摘が0件である。
2. 指摘管理表は同書「レビュー指摘管理表の保存」に従って保存するか削除する。
3. 統合は実行レビューの受理の後に行う（`agent-toolkit:atk-mode/playbooks/process-wi-execution.md`「継続する工程」の手順5）。
   複数レーンの実行では`統合準備完了`を返し、メインから`統合許可`を受けてから統合へ進む（`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「統合の許可」）。

## エスカレーションの事由別の扱い

担当から判断要請を受けた委譲元（レーン担当からの要請ではメイン、修正担当からの要請では起動した担当）が使う。
処置の前に、その処理が属する契約とユーザーにしか決められない残りを`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」で分ける。
担当が付けた区分（「要件」「要求の変更」など）は、同書「要件と技術判断を分ける」で確かめてから扱う。
指摘管理表への登録漏れ、判定行の不備、検証の失敗のように担当の内部で補える不足は同じ担当に直させ、エスカレーションとして扱うのは担当が補えない判断、認可、入力、外部環境の不足に限る。

| 事由 | 委譲元の処置 | 再開位置の記録 |
| --- | --- | --- |
| 計画の条項とWIの明示条件の衝突 | WIの明示条件から契約が一意に定まればWIを優先して確定し、同じレビューイーへ返す。人間由来の要求の解釈が分かれれば、ユーザーに確認して確定してから返す | 不要 |
| 選定結果の`担当モデル`とAWI本文のモデル指定の不一致 | 保存済みの選定原本の該当項目の`担当モデル`だけを本文の担当とモデルの組へ直し、初回の配分と既存の判断履歴は保つ。`atk run-script pick-wi-check -- <元の選定原本の絶対パス> --work-dir <対象リポジトリの絶対パス>`を実行し、終了コード0を1回で確かめる。未確定のモデルを生成側に推測させず、下位の担当を足して補うこともしない。`実装担当`が変わった場合は、引き継ぎ記録と専用資源を保って返却元の担当の終了を確かめ、同じレーンの回復として新しい値を`model_type`に渡して起動し直す。`実行レビュー担当`だけが変わった場合は、同じthreadへ続行の指示を返す | 不要 |
| 完成条件の変更か除外の判断要請 | 本書「技術判断で外せる完成条件」に当たれば、メインが技術判断と根拠を担当へ返して記録させる。当たらなければユーザーの判断の記録を確かめ、無ければ`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」で確認する。ユーザーの判断の出所と受理の条件は`agent-toolkit:atk-mode/references/review-record.md`「失効の根拠」にある | 必要 |
| ユーザーの選好、要件、認可範囲の変更 | ユーザーに確認して回答を得て、同じレビューイーへ返す | 不要 |
| 外部状態か権限の不足 | 回復の手段を確かめ、ユーザーの操作が要れば確認する。既存不良が原因なら既存不良の行も適用する | 必要 |
| 同じ論点の2回目以降の差し替え | `agent-basics:review-standards/references/reviewee.md`「同じ指摘の反復」のとおり指摘と変更の実体から意図と影響範囲を確かめ、ユーザーの判断で意図か範囲が分かれる時だけ確認してから直す（反復の回数だけを確認の理由にしない） | 必要 |
| 技術的に解消できる実装の欠陥 | レビューイーが同じ工程の中で直す | 不要 |
| 対象リポジトリや配布物のhook・CLI・規範などの既存不良による続行不能 | 担当の回復と欠陥の処置を分け、`agent-toolkit:/share/rules/common/01-agent.md`「完遂と先送り」の条件の内側で判定する。process-wi中は`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」で対処の時機を決める | 必要 |
| 同じthreadを続けられない | 後続の担当へ同じ計画ファイル（`~/.claude/plans`配下）、指摘管理表、確定した判断を引き継ぐ。既存不良が原因なら前の行の処置も判定する | 必要 |

「再開位置の記録」が「必要」の事由では、計画ファイルを`~/.claude/plans`へ保存し、`atk run-script plan-progress --`で`## 進捗ログ`へ完了した工程、続行できない理由、再開位置を記録し、キューの項目は今の状態のまま保つ。
完成条件の判断をUWIで待つ場合は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「未確定判断の保留と暫定判断」に従い、元のAWI全体をそのUWIへの依存で待たせる。
回答の前に失効を認めて統合へ進めることはせず、回答を待たずに着手できる他の項目を並行して進める（この回答待ちは、キューの項目を変えない再開の記録とも、全ての要求を不採用とする`reject`とも別に扱う）。
回答を得たら、既存の指摘管理表とラウンド番号を引き継いで再開する。

## 技術判断で外せる完成条件

完成条件の変更か除外は、次の全てを満たす時に技術判断で行える。
対応する要求の由来と、変える観測の方法や判定の水準の由来を分けて判定し、満たさなければユーザーの判断の記録を探して、無ければユーザーに確認する。

- 変えるか除く部分は、ユーザー自身の指定でなくエージェントの具体化である。
  対応する要求が明示の由来でも、その目的、対象範囲、期待する結果、明示された検証の水準は保つ。
- 変更は`agent-toolkit:atk-mode/playbooks/confirmation.md`「認可を要する操作」の「ユーザーが確定した判断の変更」の外にある。
- ユーザーにしか決められない値（同書「確認要否の判定」）を要しない。
- 害の大きさに見合う広がりの探索と再発防止に要る結果と品質を保つ（`agent-basics:bugfix/references/spread.md`「害が大きい時」、`agent-basics:bugfix/references/prevention.md`「案を比べる順」）。
  確認の手段は、同じ水準に届く別の手段へ変えてよい。

この判定は完成条件の意味を実質で評価するものであり、根拠にはエージェントの具体化であることと上の全ての条件を満たすことを示す。
`source`を持つAWIで目的の達成に要らないエージェント起草の条件は、レーン担当が上の境界を確かめて除き、判断を記録して報告する。
それ以外の変更と除外の判断要請はメインが判定し、統合の時にもメインが記録と境界を確かめる。
記録には、旧条件、新条件か除外の範囲、保つ要求、判断の主体と根拠（技術的な制約による変更ではその制約）を書き、記録先は判断した時点で選ぶ。

- 計画の確定前は、対象AWIの実施内容の根拠欄（`agent-toolkit:atk-mode/references/plan-format.md`）へ書く。
- 実装の着手後は指摘管理表へ書き、既存の指摘行が無ければ`agent-toolkit:atk-mode/references/review-record.md`「レビュー指摘管理表の共通操作」で行を足す。
- 計画なしでレーン担当が除く場合は引き継ぎ記録へ書き、計画の確定後のレーン担当の除外は進捗ログと`review_contract`にも記録してAWIの処理結果へ反映する。

対話の中の判断を根拠にする時は、対象の発話の逐語と、同じ発話の反復と区別できる時点と文脈を、その証拠を使う担当へ渡す（会話の証拠の解決と失効の根拠の書式は`agent-toolkit:atk-mode/references/review-record.md`「失効の根拠」）。
メインは出所の抽出の完了を待たずに回答を返す。

返す報告に含める項目: 起動した実行レビューとレビュー基準、受理した返却のパスと`レビューHEAD`、ラウンドごとの未解決件数、再レビューを省いた計画と理由、受領した既存不良と投入したWI、エスカレーションの処置と確認した事項、統合入力HEAD。
