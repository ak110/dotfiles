# 権限拒否と手順どおりに進められない場合

ツール呼び出しの拒否、事前判定の判定不能、手順どおりに進められない状況で、保護を保ったまま次の工程を決める手順書である。
拒否された範囲の保護は、別手段・別担当・設定変更で迂回せず、許された代替で続けるか、制約と残る工程を報告する（`agent-basics:writing-standards/references/quality-principles-constraints.md`）。
拒否を受けたら「共通判断」から始め、そこで選んだ節を上から実行する。

## 共通判断

1. 拒否された対象・操作、診断本文、実行した主体と拒否した主体を保持する。
2. 診断から拒否した主体を区別し、次の表で進む節を選ぶ。
   拒否した主体が確定しない時は、区別に必要な範囲（診断本文、呼び出し先、起動route）だけを取得する。
   偽陽性かどうかを推定で決めず、確定するまで保護を保つ。
3. 委譲先は対象・操作・診断と、必要な認可や入力を委譲元へ報告し、確認の手順は委譲元が引き継ぐ。
4. 作業依頼の認可は、ホストやサービスの拒否を解除する根拠から除く。

| 診断と拒否した主体 | 進む節 |
| --- | --- |
| `agents_server`のwriter境界、Codexホストの権限 | 本書「writer境界・Codexホストの拒否」 |
| Claude Codeのpermissions・auto mode classifierの拒否 | 本書「拒否の確認手順」。偽陽性を判断する時は本書「既知の誤拒否パターンと対応」と「偽陽性と判断できる拒否への対応」も使う |
| classifierの`gave no verdict (error)`など、通知本文が一時的な失敗として再試行を許すもの | 本書「一時的な判定不能」の手順2 |
| classifierの`gave no verdict (it skipped this action)`など、通知本文がhard failureとして再試行を禁じるもの | 本書「一時的な判定不能」の手順3 |

アクセス制御、認証、公開範囲などのセキュリティ設定を変える操作が拒否された時は、変更候補の作成、現在の実効値と候補の比較、候補の適用のどの段階が拒否されたかを特定する。
1つのツール呼び出しに複数の操作が含まれていた時は、候補の作成が拒否されたとみなす。
候補の作成が拒否された時は、別の手段で同様の候補を作らず、比較が未実施であることを明記して、拒否された操作の承認をユーザーへ確認する（委譲先は委譲元へ報告する）。
セキュリティ設定の変更は、承認を得てから実施する。
比較の手段が機能しない時は、実効値が保たれているとみなさず、比較できた項目と未確認の範囲を分けて報告する。

## writer境界・Codexホストの拒否

`agents_server`のwriter境界の拒否では、割り当てられた操作範囲と書き込み所有権を保ち、拒否された照会・操作を権限のある委譲元へ返す。
Codexホストの権限拒否では、そのホストの診断と公開された承認手段に従う。
この2種の拒否だけを根拠に、Claude Codeの設定の照会や偽陽性の承認へ進まない。

## 拒否の確認手順

Claude Codeのpermissionsとauto mode classifierによる実際の拒否に適用する。

1. 別の手段を試す前に、有効な設定ファイルを読み、許可・拒否のルールを確かめる。
   対象は`/etc/claude-code/managed-settings.json`、`~/.claude/settings.json`、リポジトリ直下の`.claude/settings.json`と`.claude/settings.local.json`である。
   拒否の本文が同じ結果の再試行や関連する操作を禁じている時は、設定の読み取りも拒否されうるため、読み取りを省いて本書「偽陽性と判断できる拒否への対応」へ進む。
2. 拒否された操作を、有効な`autoMode.allow`の各規則と、対象の操作、適用条件、信頼境界の包含関係で照らし合わせる。
   該当するallow規則があれば、拒否本文の分類名と文面が完全に一致しなくても、偽陽性の可能性が高い。
   `hard_deny`に当たる操作は、偽陽性としての対応の対象から外す。

権限はpermissionsルール（deny、ask、allowの順で最初に一致したもの）、作業ディレクトリ内の編集などの自動承認、auto mode classifierの順で評価される。
PreToolUseフックの`permissionDecision: "allow"`より前にpermissionsの評価が確定するため、拒否ルールに当たる操作は拒否ルールそのものを見直して解決する。
permissionsの設定が出す確認ダイアログの扱いは`agent-basics:writing-standards/references/claude-hooks.md`「PermissionRequest」に従う。

## 既知の誤拒否パターンと対応

dotfilesの管理設定`claude_settings_json_managed.json`を導入した環境で観測した拒否と、その対応である。
観測日と対象の版を記録していないため、当てはめる前に実行環境で拒否本文と分類名（`claude auto-mode defaults`の出力の区分）を取得し、該当するかを確かめる。
表の「偽陽性フロー」は本書「偽陽性と判断できる拒否への対応」を指す。

| 拒否される操作 | 分類名 | 対応 |
| --- | --- | --- |
| 自分が作ったHEADへの`git commit --amend` | Git Destructive | 許可ルール`Personal Repository Operations`の対象である。拒否が解消しなければ偽陽性フローへ進む |
| MR/PRのマージ（`glab mr merge`、`gh pr merge`など） | Merge Without Review | 同じルールの対象である。リモートホストによる制限は設けていない |
| リリースワークフローの起動 | `Production Deploy`が有力な候補（拒否本文では未取得） | 同じルールが起動と結果の確認を対象に含む |
| コンテナーまたはサービスの再作成 | Interfere With Workloadsなど | 許可ルール`Reversible Change Approval`が、ユーザー本人の環境で変更前の構成を復元できる再作成を対象に含む |
| 承認条件の緩和、規範の改訂、設定原本の変更を含むcommit | Self Modification | 許可ルール`Agent Workspace Writes`の対象である |
| 常時読み込む規範ファイル（`~/.claude/rules/`配下など）の編集 | Self Modification | 許可ルール`Agent Workspace Writes`の対象である |
| 規範の配布元であるユーザー本人のリポジトリの読み取り | Self Modification | 許可ルール`Agent Workspace Writes`が値を変えない参照を対象に含む |
| `atk agents-exit-session`による本人確認済みのPIDの停止 | Interfere With Workloads | 許可ルール`Session And Delegation Control`の対象である |
| 委譲先の状態・終了・通知・結果の観測と受領（`atk agents wait`、`list`、`show`など） | Self Modification | 許可ルール`Session And Delegation Control`が、委譲の内容によらず、受領済みにする操作と結果・通知ファイルの削除を含めて対象とする |
| 自分で新しく作ったtmuxセッションでの、対話CLIの起動し直し、キー入力の送信、画面の取得 | Tmux Self Drive | 許可ルール`Session And Delegation Control`の対象である。権限確認を省くオプション（`--allowedTools`、`--dangerously-skip-permissions`など）と別の権限モードの指定（`--permission-mode`など）のどちらも付けない起動に限る。`--allowedTools`を付けた起動は拒否され、付けない起動は拒否されなかった（2026年11月11日と12日の観測）。拒否されたらオプションを外して起動し直し、解消しなければ偽陽性フローへ進む |
| UWIの回答でエージェントに実行を任せた、システムへの永続的な変更（sudoによるパッケージの導入など） | Unauthorized Persistence | UWIの回答は、分類器が参照する会話ログ上のユーザー発言に現れない。実行前に個別に確認せず、拒否されたら偽陽性フローの冒頭で具体的な承認と実行する操作の一致を確かめ、一致を確かめられなければ偽陽性フローの`AskUserQuestion`へ進む |
| エージェントの誤操作で変わった状態（リポジトリ共通のGit設定など）を変更前の値へ戻す操作 | Modify Shared Resourcesなど | 許可ルール`Agent Mistake Recovery`の対象である。拒否が解消しなければ偽陽性フローへ進む |
| エージェントや、エージェントが起動したテスト・スクリプトが残したプロセスの、PIDを個別に指定した`kill` | Destructive or Unwanted Actions | 許可ルール`Agent Process Cleanup`の対象である。終了の直前にコマンドラインかパスで同定する。`pkill`と`killall`は対象外 |

- 許可ルールは、リモートホスト、由来、所有者で限定せず、操作の種別と除外条件で対象を決める。
- 必須のレビューや必須のチェックを回避するオプション（`--admin`、`--force`など）と、リポジトリや組織のチェック設定そのものを変える操作は許可ルールの対象外で、CI Bypassの領域として制限が続く。
- リリースワークフローの起動の拒否本文には分類名が出ないため、`Production Deploy`は初期設定の`soft_deny`との対応から推した候補である。

## 偽陽性と判断できる拒否への対応

auto mode classifierの拒否を受けたら、具体的な承認と実行する操作が一致するかを確かめる。
出所を確かめられる具体的な承認（直接の対話、UWIの実際の回答、委譲先の報告が示す実際の回答）を、構造化した要求の対象リポジトリ、cwd、ツール、実際の入力、実行の対象と範囲へ対応付ける。
委譲先の報告そのものはユーザーの承認として扱わず、報告が示す実際の回答と要求の由来を確かめる。
要求・実際の回答・実際の入力が一致し、撤回・要求の変更・消費が無く、拒否がsoft拒否だと一意に確かめられた場合に限り、既存の承認処理で同じ操作への許可を適用する。

soft拒否の特定には、`PermissionDenied.reason`のラベル列が、公開コマンド`claude auto-mode config`のJSONのどの区分に属するかを確かめる。
観測した版2.1.325のreasonには構造化したhard/softの区分が無いため、この版と一致する時だけ、この区分の確認結果を許可の根拠に使う。
`hard_deny`、重複したラベル、名前の無いラベル、no-verdict、再試行の禁止、設定の取得の失敗、版の不一致の時はallowを適用しない。
permissionsの明示的なdeny・askも上書きしない。

具体的な承認の由来を確かめられない時、上の条件がそろわない時、ホストがallowを受理しない時は、自律モードでも協調モードでも、下の手順で`AskUserQuestion`により確認する。
拒否は事前に正確には予測できないため、拒否を観測してから確認する。
偽陽性と判断できる拒否を最初に観測した時点で、同じ操作を再試行せずにこの手順へ進む。
`clears`が成立するのは、ユーザーが拒否を偽陽性だと明示して回答した場合に限り、作業の継続への同意だけでは成立しない。

この手順はユーザーまたは処理中のAWIがその操作を承認済みだと確かめられ、拒否理由がその承認を反映していない場合と、本書「拒否の確認手順」で対応するallow規則が見つかった場合に適用する。
対象の操作は、`git commit`、`git commit --amend`、`Write`・`Edit`・`MultiEdit`によるファイルの編集、外部サービスの設定を変えるコマンドなど、一般的な操作を広く含む。
メインとサブエージェントのどちらの操作にも適用する。

委譲先は`AskUserQuestion`を発行せず、拒否本文、分類名、拒否された操作と対象を`agent-toolkit:atk-mode/playbooks/subagent.md`「確認事項の即時通知」に従って委譲元へ報告する。
代替の手段で作業を進めた時と、下位の委譲先から拒否を受け取った時も、同様に委譲元へ引き継ぐ。
委譲元はその拒否を自分が発行した操作と同様に扱い、設定ファイルとallow規則を確かめる。
承認を得た後は、委譲先の状態によらずメインが該当の操作を直接実行する。

1. 拒否理由を本文で確かめ、取得できれば分類名と本文を記録する。
   `claude auto-mode defaults`の実行が拒否された時は、本文を根拠に進める。
2. `AskUserQuestion`で次の選択肢を示す。
   ダイアログの説明は要点にとどめ、詳細は同じターンの本文に書く（努力目標。この種の拒否はほとんどが偽陽性であり、確認を短く保つため）。
   - 偽陽性として実行を承認する
   - 該当の操作を撤回する
   - サブエージェント側でレビューを終えてから判断する
3. 承認を得たら、メインが該当の操作を直接実行する。
   撤回なら操作を取りやめ、委譲された操作なら撤回と再開の条件を委譲先へ伝える。
   レビューの完了を待つ時は、委譲先がレビューし、完了報告を受け取った後に手順1で理由を確かめ、手順2で判断を求める。
4. `AskUserQuestion`が未回答のまま時間切れになったら、対象の操作を保留にし、回答待ちのUWIを記録して、代替の手段だけで作業を続ける。
5. 未回答の後でUWIへ回答が保存されたら、本節の冒頭のとおり具体的な承認と実行する操作の一致を確かめる。
   一致を確かめられない時と、ホストがallowを受理しない時は、手順2で同じ操作を確認し、回答に従って手順3へ進む。
6. ユーザーが拒否を偽陽性として許可するたびに、メインは同じ種別の誤拒否を防ぐ許可ルールをその場で追加する（2026年11月16日のユーザー指示）。
   許可には、手順3の承認、拒否の後の発話での実行の指示、ホストの許可ダイアログによる同じ操作の許可を含む。
   委譲先から報告された拒否もメインが担当し、承認済みの操作の実行を先に終えてから追加する。
   - 文面: 個別の識別子を操作の種別へ一般化する。
     書き方は`agent-basics:writing-standards/references/claude-hooks.md`「カスタムルール記述の注意点」に従う。
     有効な規則との比較と追加は`agent-toolkit:atk-mode/references/auto-mode-rule-addition.md`「カスタムルール追加のワークフロー」に従う。
     既存の規則が対象を全て網羅する時は追記を省く。
   - 環境に固有のルール（マシンの構成、ローカルの設定、接続先などを前提とする規則）: 配布元のソースの有無によらず、`~/.claude/settings.json`の`autoMode.allow`へ直接追記する。
     管理ラベルや非推奨の文字列と衝突しない独自の文面にする。
   - 汎用のルール: dotfilesを編集できる環境では、管理原本`share/claude_settings_json_managed.json`の`autoMode.allow`へ追記してcommitする。
     公開前から今の環境で有効にするため、同じ文面を`~/.claude/settings.json`の`autoMode.allow`へも追記する。
     process-wiの巡回中は統合先のworktreeでcommitする。
     dotfilesを編集できない環境では、文面、根拠、反映先を書いたdotfiles向けのAWIを`agent-toolkit:atk-mode/playbooks/wi-drafting.md`に従って登録し、`~/.claude/settings.json`へは直接追記する。
   - 今回限りの対応: 明確な一時的条件があり、同じ種別の誤拒否が再発しない根拠を示せる時だけ、追加を省ける。
     過去に発生例が無いことや分類に迷うことは、省く理由にならない。
   - 追加の確認: 作った文面が承認済みの操作種別、拒否区分、副作用区分の範囲内なら、直接の追記とAWIの登録はユーザーへの追加の確認なしで行う（`agent-toolkit:atk-mode/playbooks/confirmation.md`「承認源と適用範囲」の成立済みの承認の適用）。
     許容範囲が広がる時だけ、文面案、追記先、広がる範囲を事前承認としてユーザーへ確認する。
   - 完了の報告: 直接追記した時は、追加したルールの本文、追記先、設定の取り消し方を報告する。
     AWIを登録した時は、設定の配布の通常の反映を経て有効になることを、今の実効設定への即時の反映と区別して伝える。
     追加を省いた時は、一時的な条件と再発しない根拠を報告する。

## 一時的な判定不能

1. classifierの判定不能は、通知本文の再試行の指示で区別する。
   `no verdict`という語だけで一時的な失敗と扱わず、操作への拒否、`hard_deny`、偽陽性とも分ける。
2. `gave no verdict (error)`で`transient failure`・`You may try the action again once`と示す一時的な失敗では、許された同じ操作を1回だけ再試行する。
   通知が指定する遅延、再試行の回数、turnの停止の制約を守る。
3. `gave no verdict (it skipped this action)`で`hard failure`・`Don't retry it`と示す操作は、同じ操作を再試行しない。
   読み取りと独立した作業を続け、その操作が必要なら対象・操作・通知本文を伝える。
   委譲先は`agent-toolkit:atk-mode/playbooks/subagent.md`「確認事項の即時通知」で委譲元へ、メインは`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」でユーザーへ伝える。
   同じ変更を別のツールで実行して判定し直させることと、権限設定の変更は、対処に含めない。
4. 操作が未起動・実行中・完了・成否不明のどれかと、未回収の対象の識別子を保持する。
   待機を開始できない時の観測の続け方は`agent-toolkit:atk-mode/references/delegation-wait-anomalies.md`「待機を開始できない場合」に従う。

## 手順どおりに進められない場合

手順と規範は目的を達成する手段である（`agent-basics:writing-standards/references/quality-principles-qcd.md`）。
手順どおりに進められない時も、目的から次の工程を選び直し、依頼の完遂を目指す。
適用する前に、`agent-toolkit:atk-mode/references/conduct.md`「方針が衝突する場合の優先順位」で適用対象の優先順位を確定する。
その優先順位でも次の工程が決まらず、次のどれかを観測した時に本節を適用する。

- 適用範囲が重なる2つ以上の手順や規範が、同じ状況で両立しない動作を求めている
- 手順が前提とする対象、コマンド、状態が実在せず、代替の手段の定義も欠けている
- 手順が指定する取得手段で得た値が、手順の目的から外れている

指定されたスキル、コマンド、ファイルが無い時は、規範が定める役割、責務、所有者から、同じ成果に届く代替の候補を導く。
取得した値が目的に合わない時も、手順の目的から必要な入力を考え直す。

次の順に判定し、最初に成立した対応を選ぶ。

1. 委譲先が受けた依頼文と適用中のスキルの規則が矛盾する時、または必要な権限や認証が足りない時は、`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従って委譲元へ差し戻す。
2. ユーザーの確認を要する事項に当たる時は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従ってユーザーへ確認する。
3. ユーザーの目的、要件、必須の制約を保ったまま次の工程を実行できる時は、実行して作業を続ける。
   手段が複数あればQCDで選び、目的から工程が一意に決まる時は自分で判断して実施し、根拠を報告する。
   ユーザーの選好や承認が必要な論点だけは判定順2で確認する。
   規範や手段の方針から、QCDの明らかな悪化を理由に外れる時も、`agent-basics:writing-standards/references/quality-principles-qcd.md`「QCD」と判定順2に従う。
4. どの手段でも目的、要件、必須の制約を保てない時は、その操作に着手せず、その操作を待たずに進められる工程を続ける。

下位の手順書や`<役割名>.subagent.md`が差し戻しや確認の対象を限定して列挙していても、本節の適用条件を満たす事象は判定順1と2の対象にする。
その列挙は挙げた事象について差し戻しを必須とする規定として読む。

選んだ対応と根拠は同じターンで報告し、判断に使った規範の所在と条文を示して、条文が明示する要求と自分の解釈を区別する。
2つ以上の手順や規範が両立しない時は、それらのファイル名と節名を報告に含め、条文の矛盾は`agent-toolkit:atk-mode/references/conduct.md`「完遂と先送り」に従って直すか登録する。
条文を直す前に、本書「規範どうしが矛盾する場合の由来確定」で由来を確かめる。
手順の前提が無いだけで規範の矛盾が無い時は、報告にとどめる。
委譲先の返却の形は`agent-toolkit:atk-mode/playbooks/subagent.md`「手順どおりに進められない場合の返却」が定める。

## 規範どうしが矛盾する場合の由来確定

規範どうしが矛盾する条文そのものを直す前に、各条文の由来を確かめる。
由来を確かめずに優先順位を当てると、ユーザーの指示に由来する条文を下位の規範として扱い、合意済みの要件を取り消してしまう。

1. `git log -S`などで該当の変更を入れたcommitを特定し、ユーザーの明示的な指示によるものか、エージェントの判断によるものかを見分ける。
2. 対応するキューの項目や計画ファイルがあれば、項目の`source`や明示された由来、計画ファイルの実施内容の由来欄を判断の材料にする。
3. 現在の明示的な要求、判断の記録、優先順位を確かめてから、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」を当てる。
   由来が分からないことは、修正してよいかをユーザーへ尋ねる理由から除く。
   目的、要件、結果、既存の承認を保てる修正は自分で確定して報告する。
   合意済みの目的の側の要求を取り消す修正と、ユーザー固有の資料や判断が必要な修正だけを、論点を限定してユーザーへ確認する。

作業を進める間にどちらの規範に従うかは、本書「手順どおりに進められない場合」の判定順で決める。

## 返す報告に含める項目

拒否された対象・操作・診断本文と拒否した主体、選んだ処置とその根拠（使った規範の所在と条文、自分の解釈との区別）、追加・省略した許可ルールの本文・追記先・取り消し方または省略の根拠、保留した操作と再開の条件を含める。
