# WIの選定

目的: 選定メインが時間目標を配分の目安に使い、処理可能な依頼を全件、依存順に進められるようにする。
作業`process-wi`のメイン（複数レーンの選定メイン、single-laneのメイン、all-reposのリポジトリ担当）が、WIキューから今回の処理対象を選んで`processing`へ移すまでの手順書である。
確定するのは、処理対象、依存順、レーン割当と、前回`processing`に残った項目の再開位置である。
選定は、ユーザーの指定があってもメイン自身が行う。
計画の起草、実装、採否（`adopt`・`reject`）はレーン担当が行い、不採用と既存実装による充足の確定もレーン担当の計画起草に任せる。
選定YAMLの書式と欄の意味は`agent-toolkit:atk-mode/references/process-wi-selection-format.md`が定める。
処理対象WIを含めた理由や除外した理由を尋ねられた時は、`agent-toolkit:atk-mode/playbooks/process-wi-selection-explanation.md`に従う。

方針は次のとおりである。
監査と追加WIの投入の終了を待たずに、独立した既存候補の選定とレーンの起動を進め、結果が必要な候補だけを待つ。
規模と分類は本文で確定できない部分だけを限定調査し、根本原因と実装方式はレーンの計画起草へ委ねる。
レーン数の上限、時間目標、巨大WIの承認は、ユーザーが決めた時間目標の運用である（`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`）。
選定確定後の見込みの超過は配分の組み直しで扱い、対象の削減、必要な品質工程の省略、着手した作業の次回送りは手段から外す。

## 直前の同期結果の検分

選定を始める前に、`atk config show`の`state_dir`直下の`sync-report.json`を確認する。
同期が失敗したまま着手すると、処理が途中で成立しなくなるためである。

1. ファイルが無いか、`status`が`succeeded`で`post_apply`に失敗が無ければ、次の工程へ進む。
2. `status`が`failed`か`post_apply.failed_steps`が1件以上なら診断を保全し、不具合は `agent-basics:bugfix` で調査して認可内で回復する。
   適用済みか確認し、繰り返せない処置は再発行せず、安全な場合だけ同期を再試行する。
   回復を試した後に前提が揃えば根拠を伝えて進み、揃わなければ着手せず `atk wi process-loop abort` を要請し、失敗工程・試行・再開条件を伝えて終える。
3. 今回の起動または再開へ引き継いだ未検収のupdate-dotfiles実行がある場合だけ、そのログを1担当が検分する。
   `update-dotfiles logs`の当回分と`sync-report.json`の実行ID・開始終了時刻を対応付け、標準出力・標準エラーと`notices`も確認する（更新ログは同じ状態ディレクトリの`update-dotfiles.log`にあり、回転した分は同じ実行IDの範囲を回転先から補う）。
   更新実行を特定できない範囲は未確認として記録する。
   独立した選定とレーン起動を検分の終了まで待たせず、成立性に関わる失敗だけを手順2の判断へ渡す。
4. 警告は正常な案内、安全な保留、是正が必要な不良へ分類し、対象範囲・分類・処置を既存の進捗記録に残す。
   不良は`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」とWI投入へ、本人の信頼登録などを要する事項はユーザー確認へ渡す。
   各レーンへは必要な検分結果を共有し、当回のログの取得と確認は1担当へ集約する。

## 自動コードレビュー監査

対象リポジトリがGitHub上にある場合は、選定を始める前に未判定（pending）の有無を確かめ、必要な監査を`agent-toolkit:atk-mode/playbooks/process-wi-review-audit.md`「自動コードレビュー監査担当の起動と受領」に従って起動する。
監査の終了と追加WIの投入の完了は、独立した既存候補の選定・レーン起動と並行して待つ。
同じ実行へ追加するWIは、保存結果の正式なファイル名を受領した直後に`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」へ渡す。

## 明示された目標からの実行

### 目標の取り込みと作業構成

ユーザーが単一リポジトリの目標を追加指示で示した場合は、メインが目的、達成を観測する結果、対象、保持する挙動、許容操作を既存の作業契約（`agent-toolkit:atk-mode/references/work-contract.md`）へ統合する。
解法と必要作業の列挙はエージェントが担い、確認の要否は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」で決める。
未登録の必要作業は既存のWI作成手順で具体化して「処理対象WIの追加」へ渡し、目標の達成に必要と判断した作業は同じ実行の対象にする。
目標達成は、候補の件数ではなく目標と観測結果の比較で判断する。
通常のキュー処理は、開始時に処理可能な全WIと、開始後に今回の対象と判定した全WIを処理する。

### 証拠に基づく反復

次の作業、優先度、並行化、局所結果の採否、方針転換、全体の完了はメインが判断する。
局所担当は割り当てられた設計・実装判断を所有し、メインは全体目的への適合と結果間の矛盾を検収する（独立した評価は実行レビュー担当が行う）。
反復して試す作業では、効果が無かった変更を取り除いてから次へ進む。
採否を変える不確実性が残る場合に限り、`agent-basics:writing-standards/references/investigation.md`に従って必要最小限の確認を選ぶ。
新しい証拠で前提が崩れた時と、30分点検で残工程の見込みが目標所要時間を超えると分かった時は、待ちの除去、重複した実行の集約、独立した準備の先行を比べて作業構成を更新し、追加分を追加計画と選定の合流へ渡す。
確定済み計画の凍結と、他の処理対象WIの保持を守る。

### 再開と完了判定

中断と圧縮の後は、`agent-toolkit:atk-mode/references/work-contract.md`「圧縮と再開の後の復元」で作業を戻す。
完了は目標と観測結果を比べて判断し、ユーザー判断待ちと未達を区別する。

## 対象と保存先

1. 対象リポジトリと規範はメインの作業ディレクトリから解決し、選定結果はmanaged-temp直下の`pick-wi.yaml`へ保存する。
2. `atk lane delete --list`で前回の残存登録と回収結果を確かめ、所有と稼働状態に応じた再判定と再開を`agent-toolkit:atk-mode/playbooks/process-wi-lane-resources.md`「レーン資源の作成・再利用・回収」へ渡す。
3. レーン識別子は手順2の処置の後に決める。
   新しいレーンには`lane-01`から空いている最小の番号を使い、回収できない登録が作成先を占有している番号は避ける。
   同じ実行への追加選定では、使っている番号とWIの対応を保つ。
   再開する成果と稼働中のプロセスは、番号を空ける目的でも保持する。
4. 対象リポジトリにmiseの設定があり`mise trust --show`が`untrusted`を示す場合は、`mise trust <対象リポジトリの絶対パス>`を実行する。
5. `WIファイル名一覧`の明示的な指定があればそれを候補集合とし、無ければ次節の初期集合を使う。

## 処理対象の決定

1. 公開対象のリポジトリとベースブランチを明示し、対象forgeの実際のCI状況を確かめる（開始時のCI点検）。
   GitHubでは公開時の検収対象のワークフローごとの直近のrunを、GitLabではベースブランチの直近のパイプラインの識別子、対象SHA、状態、URLを取得する。
   失敗した実行はジョブとログまで取得し、原因と残工程への影響を評価して、今回の差分と無関係でも`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」へ渡す。
   CIの状態は「正常」「失敗」「未終了」「実行未登録」「CI定義なし」「CI実行対象外」「照会不能」を区別し、ログの取得権限は実際に取得して確かめる。
   未終了と実行未登録は、失敗を示す証拠を得てから既存不具合かを判断する。
   認証、ネットワーク、CLIの不備、対象解決の失敗は技術的に回復できるものを回復し、資格情報の準備などユーザーだけが対応できる事項は`agent-toolkit:atk-mode/playbooks/confirmation.md`で確認し、待たずに進められる作業を続ける。
2. 通常起動では、次のコマンドで初回の一覧を取得し、全状態・全種別の識別子集合（開始時集合JSON）を新着確認と再開へ引き継ぐ。
   新着不良・マージ用AWIは`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「開始後に追加されたWIの確認」で今回の対象と進捗へ対応付け、担当済みの成果を回収する。
   常駐では随時点検し、新着の存在だけで公開を止めない。
   all-reposのリポジトリ担当は、受け取った`candidate_file`の保存原本と`readiness`を初回の取得結果として扱う（`agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md`「取得済み候補の受領」）。

   ```text
   atk wi list --jsonl --status=processable --target-repo=<対象リポジトリの絶対パス> --target-branch=auto --pull --with-staleness --snapshot-output <開始時集合JSONの絶対パス>
   ```

   追跡するブランチが登録外でコマンドが失敗した場合は、処理を始めず、示された系統と起動方法をユーザーへ報告して終了する（`agent-toolkit:atk-mode/playbooks/process-wi.md`「系統を登録したリポジトリ」）。
3. 通常の候補は、`processing`の全項目と、`ready: true`または`blocked_reason: dependency-unmet-internal`の`inbox`の項目である。
   未回答のUWIは候補から除く。
   追加選定にも同じ条件を使う。
   `staleness`の値は、選定結果の`鮮度`欄へそのまま保存する。
   選定時間を短く保つため、`notice`が付いただけでは履歴を調べず、内容の不一致、充足済み、巻き戻しの危険を観測した項目だけ履歴を確認する。
4. 明示した項目が初回取得に含まれない場合は、`atk wi show <WIファイル名> --target-repo=all`で保存済みの`target_repo`を取得し、originとの不一致が移転やパス改名によるものか別リポジトリかを判定する。
   同一性と変更先の根拠は、ユーザーの明示的な指定か移転・別名の対応記録に限る（`ls-remote`のOID一致は根拠から外す）。
   移転が確定した項目は、`start-processing`の前に`atk wi edit <WIファイル名> --target-repo=<保存済みtarget_repo> --body-file <原稿>`で`target_repo`と本文中の操作先を変更先に合わせる。
   同じ作業ツリー指定の一覧から対象と完成条件を取得できることを確かめてから、候補に加える。
   根拠が得られない場合は、両方の識別子と不足する根拠を`続行できない理由`に記録する。
5. 実行時に同じ要求の重複が分かった場合は、要求と充足を比べ、既存の項目・計画・成果を統合または再利用して残差だけを実装する。
   他の担当が処理中なら二重に着手せず、既存の担当と状態管理へ接続する。
   同じファイルの編集競合は要求の重複と区別する。
6. `depends_on`の各依存先を`atk wi show <依存ファイル名> --skip-pull`で全状態・全リポジトリから解決する。
   対象リポジトリ内にあればそれを使い、複数リポジトリに同名があれば自動選択せず`続行できない理由`を記す。
   別リポジトリの依存先は、終了済みなら充足、未終了なら`dependency-unmet-external`とする。
7. その巡回の選定済みまたは現在の候補にある先行項目だけに依存するAWIは、書込対象に包含関係があっても候補に残す。
   推移的な依存先も含め、同じレーン内で依存順に処理する。
   先行項目がどちらにも含まれない場合か着手できない場合は、後続項目だけ着手せず依存待ちを保つ。
   日付境界の順序要求で、先行項目の終了か公開先へのマージ完了が後続の開始条件になっている場合は、先行条件の成立を確かめてから後続を候補に含める。
   依存の辺、日付の帰属、マージ条件にユーザーだけが決める未確定事項が残る場合の保留とUWIは、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「依存と冷却時間」「着手不能要因の分類」に従う。
8. 通常起動では、次のコマンドで回答済みUWIの本文を取得する。
   `run_skill_report: true`を持つ報告用UWIも対象に含める。
   all-reposの担当は、受け取り済みの候補のうち同じ条件に当たるものを使う。

   ```text
   atk wi show --all --type=uwi --answered=yes --status=processable --target-repo=<対象リポジトリの絶対パス> --target-branch=auto --skip-pull
   ```

   - 回答に処理手順があるUWIは、選択が見送りであっても`選定`に含める。
     処理手順も作業もない回答のUWIは「集合確定直後の処理開始」で終了処理し、それ以外は`選定`に含める。
   - `source: run-skill`のUWIも候補に含める。
     処理担当は通常のスキル・モードを起動せず、必要な回答処理の手順を調べる時だけfrontmatterの`scope`を参照する。
     UWI本文の「回答の処理」節と実際の回答に従い、`agent-toolkit:atk-mode/references/answer-transitions.md`「回答後の状態遷移」の手順1〜3を適用する。
     必要な手順を解決できない時は、不足するscopeと必要な資料を`続行できない理由`へ記録する。
   - UWIが元項目を参照している場合は、元項目の状態と`ready`を確かめる。
     元項目が依存する未回答のUWIが残っていれば、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「回答済みUWIの取り込み」に従い元項目を対象外のまま保つ。
     元項目が`inbox`で処理候補にある場合と、旧運用で`hold`に置かれ`ready=true`の場合は、処理対象に1回だけ含め、UWIを元項目と同じレーンへ割り当てる。
     それ以外の状態は、不足する状態条件を`続行できない理由`に記録する。
9. 再開位置を次の基準で決め、選定結果へ記録する（キュー項目は受け取り時の状態のまま保つ）。
   - AWI本文に`## 反映後の観測の再開記録`がある候補（`hold`から戻す元項目を含む）は、最後の同名節の`再開区分`が`反映後の観測だけが残る`である場合に限り再開記録として扱い、`atk plans list`の結果によらず観測のみの書式で該当節の`計画`の値を記録する。
     それ以外の`再開区分`（`再実装へ戻す`など）の節は、再開位置の根拠から外す。
   - 回答済みのUWIとともに`inbox`から取り込む元項目は、依存の保存時に本文の`## 処理結果`の後ろへ追記された再開手順を読む（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「回答済みUWIの取り込み」）。
     再開手順が計画の絶対パスを示せば、その計画（`~/.claude/plans`に無ければ`atk plans checkout`で取得する）の絶対パスを記録する。
     示さなければ、旧形式で再開手順を進捗ログだけへ記録した項目を含め、次項と同じ照合で決める。
   - 再開記録を持たない`processing`の項目、`hold`から戻す元項目、再開手順に計画を示さない前項の元項目は、`atk plans list`で`~/.claude/plans`配下の計画の`related_wis`（旧形式では`関連WI`）に候補が含まれるかを確かめ、一意に対応する計画の絶対パスを記録する。
     残る工程は、旧形式の計画では`## 進捗ログ`の最終行から、新しい計画と計画の無い項目では専用branchのcommit履歴とレビュー指摘管理表から決める。
     対応する計画が複数なら推測で選ばず`続行できない理由`とする。
     計画が無い項目は、専用branchかレビュー指摘管理表が残っていれば`再開位置: 計画なし`とし、どちらも無ければ、`processing`の項目は`続行できない理由`、元項目は再開位置なしとする。
   - 旧形式の計画の進捗ログの最終行に「反映後の観測だけが残る」とある場合も、計画ファイルの絶対パスと残る工程の書式を用いて`再開位置`に記録する。
     観測のみの書式は、AWI本文に記載された再開記録を読み取った項目に対してのみ使用する。

## レーン分け

調査、分類、レーン分け、所要時間の見込み、内部担当の同時数、上流投入、プロジェクト規範の指定は、`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`の各節を上から実行する。

## 集合確定直後の処理開始

候補と`選定`の集合が確定したら、選定YAMLの保存、検査、レーンの起動を待たずに次を行う。

1. 開始時の候補と選定完了前の明示的な追加WIを合わせた処理可能集合が、`選定`のファイル名集合と完全に一致し、各ファイル名が1回だけ現れ、複数レーンに重ねて割り当てられていないことを確かめる。
2. `atk wi show <選定の全ファイル名> --target-repo=<対象worktreeの絶対パス> --skip-pull`を1回実行し、終了コード0と、保存済みの`target_repo`と対象作業ツリーのoriginの一致を確かめる。
   不一致の診断なら「処理対象の決定」の手順4へ戻る。
   後続の`adopt`、`unhold`、`start-processing`でも、状態を変える前に両者の一致を確かめる。
3. 処理対象に含めた、処理手順も作業もない回答済みUWIを`atk wi adopt <filename>... --target-repo=<対象リポジトリの絶対パス>`で終了する。
4. 回答済みUWIが参照する元項目のうち旧運用で`hold`にあるものを`atk wi unhold <filename>... --target-repo=<対象リポジトリの絶対パス>`で`inbox`へ戻す。
5. `inbox`の`選定`対象と手順4の元項目を、`atk wi start-processing <filename>... --target-repo=<対象リポジトリの絶対パス>`で1回ずつ`processing`へ移す。
   成功を確かめた遷移は再実行せず、引数にはまだ`processing`でない項目だけを指定する。
   別の会話の`processing_owner`が残る選定済み項目は、レーンへ渡す前に`atk wi take-over <ファイル名>`で担当を引き継ぐ。
   前の会話の終了を確認できない項目には着手しない。
   引き継ぎの条件は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「状態遷移」に従う。
   今回の巡回で移したUWIは開始済みの項目として処理担当へ渡し、他の担当が処理中のUWIと区別する。
6. 部分的な状態の不一致や原因不明の失敗が起きたら、追加の遷移をせずに`続行できない理由`を記録する。
   一括の開始の後に失敗した場合は、次の全条件を確かめる。
   全対象が`state=processing`であること、対象遷移の未commit差分が無いこと、今回の集合の開始を記録した遷移commitがあること、remoteの設定時はそのcommitがupstreamに含まれることである。
   全て成立した時だけ開始済みとし、欠ければ項目別の再実行を避けて未完了で止める。

### 公開工程の承認スコープ

環境変数`AGENT_TOOLKIT_PROCESS_LOOP_SESSION`が`1`の起動は自動常駐起動（`atk wi process-loop`の子セッション）、それ以外は手動起動とし、選定工程で1回だけ判別する。
手動起動では、確定したAWIの完成条件に明記されたrelease、tag、push、PRまたはMRの作成、配布の操作を、記載の内容・対象・影響範囲に限り承認スコープとして保持する。
自動常駐起動では承認スコープを空にする。
承認済みの範囲は実行し、具体化で範囲が変わる部分だけをユーザーへ確認し、破壊的な操作の前の事前説明は保つ。

## 保存後のチェック

1. 分類、割り当て、担当モデル、配置根拠、見込み時間、プロジェクト規範の指定、結合条件の意味判断を、`agent-toolkit:atk-mode/references/process-wi-selection-format.md`「選定の生成入力」の形式でYAMLへ記録する。
   鮮度、初回候補、初回割当、不可分成分と、確定した入力から導ける各辺のパス・段階・依存は転記しない（生成ツールが作る）。
   今回扱わない候補は下記の生成時に照合する。
   未確定の分類と担当モデルは生成ツールに推測させずメインが本文と現物から補う。
2. `atk wi list --jsonl --with-staleness`の取得済み出力を`--candidate-file`に渡し、定型欄の生成、本文との対応確認、全体の検査、保存を1回の操作で行う。
   候補が0件の場合と再開位置を持つ初回選定も同じ操作を使い、`--body-wi`は省く。
   処理可能な未選定候補が示されたら、選定漏れを直し、今回扱わない集合を確かめてから`除外確認`を渡す。
   報告の除外候補と理由は生成された`除外記録`から読む。

   ```text
   atk run-script pick-wi-check -- <意味判断YAMLの絶対パス> --candidate-file <取得済み候補JSONLの絶対パス> --output <pick-wi.yamlの絶対パス> --work-dir <対象リポジトリの絶対パス>
   ```

   完成済みの選定YAMLを受け取った場合は、`atk run-script pick-wi-check -- --work-dir <対象リポジトリの絶対パス> <出力先の絶対パス>`で確かめる。
   検査に成功した同じ入力の再実行は、保存や再確認だけが目的なら省く。
3. 終了コード1なら、該当WIの本文に戻って分類を判断し直し、変更領域や重複関係が変わったら`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`「調査とレーン分け」で配分を見直してから手順2を再実行する。
   終了コード2なら、出力の`次の操作:`に従って直し、手順2を再実行する。
4. 終了コード0なら、標準出力の要約（WI総数、レーンごとの件数・段階・先行レーン・秒数・WI名）で選定件数と候補件数の一致を確かめ、次節へ進む。
   検査の後にYAMLを編集したら、検査をやり直す。
   追加WIと統合状態の記録にも、全体検査付きの保存の成功結果を使う。

## 保存後の意味検収

追加選定の入力と保存は`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」に従う。

終了コード0は、構文と書き込み予定・レーン関係の機械的な確認だけを示す。
初回、修正後、追加選定のいずれでも、選定YAMLと元のWI本文（AWIも`atk wi show`で取得する）を読み、次を確かめる。
不一致は観測した事実を添えて直し、再検査する。
`選定`と`レーンの所要時間`が空の結果も正常として受け入れる。

- 分類: `書込対象`と`公開工程の書込対象`の個別対象に欠落がなく、妥当な範囲に限られ、元本文の変更要求と`公開工程の規範根拠`が指す規範・節に合っている。
  機械的に抽出したパス、ファイルの有無、名前順、件数だけを根拠にした配分と、一律の独立性の宣言は差し戻す。
  パスが明示されない作業を伴う回答済みUWIは、限定調査で導いた範囲が回答の作業内容に合っている。
- `導出した新設先`: 要求と配置根拠が元本文と限定調査の現物に対応し、要求範囲を満たす具体化になっている。
- 重なり: 同じ段階の未統合レーンで共通パスを持つ組は、双方の変更定義が意味上独立している（記録は`レーン間の重なり`の`共通パス`、`レーン1の定義`、`レーン2の定義`、`判定`）。
  別段階では書き込み予定の重複が`先行レーン`へ直接か推移的に反映されている。
  着手条件と統合順の区別は、`agent-toolkit:atk-mode/references/process-wi-selection-format.md`の所要時間の各欄に従う。
- 追加分の担当: レーン担当、メインの直接作業、別のサブエージェントと資源の組を品質・費用・時間で比べたことが`レーンの所要時間`の行の`根拠`から読め、担当の選定理由が上限以外にある。
- 依存: 候補内の同じリポジトリの依存を、正規化した`target_repo`と`depends_on`から推移的にたどり、両端が同じレーンにあって依存先が先に処理される。
  別レーンの開始順だけで依存を満たす割り当ては差し戻す。
- 段階と上限: 段階2以上か6000秒超の単一段階なら、`レーンの所要時間`の行の`根拠`で両案の秒数と採用理由（段階案が無ければその理由）を確かめる。
  書込対象の推移的な重複だけで6000秒超過を不可避とせず、比較と後段の先行統合条件が整合するかを検収する。
  初回は元の候補・割当・結合条件を元入力と照合する。
  追加時は終了済みを除き、後段の未着手分を含む当該時点のWIとレーンを照合する。
  初回情報を欠く旧入力は、過去の記録から復元して同じ操作を再実行し、記録を確かめられなければ情報不足とする。
- 所要時間: `レーンの所要時間`が`なし`以外のレーンと過不足なく一致し、秒数が0以上で、根拠が記入されている。
  補正前の2数値と`見込みの補正`から各工程の積が正しく、共有待ちが全体へ1回だけ加算されている。
- 上流投入: 省略時の値を解決した各項目が、`上流投入`と`レーン`の組み合わせ条件を満たしているかを検収し、外れていれば分類を修正して再チェックする。
  通常レーンの外部操作だけの項目は、ファイル変更が無くても分類を保つ。
- `プロジェクト規範の指定`: 指定されたファイルが実在し読み取れる（資料を読んだかの確認は使うレーン担当が行う）。
- 再開位置: 再開位置が設定されており、その値が`計画なし`でも`反映後の観測だけが残る`で始まる値でもない項目については、`~/.claude/plans`配下の計画ファイルの絶対パスで、その計画の`related_wis`（旧形式では`関連WI`）に対象AWIが含まれる。
  `計画なし`の項目は、対象AWIの専用branchかレビュー指摘管理表が残っている。
  `反映後の観測だけが残る`で始まる値は、AWI本文の末尾の`## 反映後の観測の再開記録`（`agent-toolkit:atk-mode/playbooks/process-wi-observation.md`「延期adoptと反映後の観測」が追記する）の`再開区分`が`反映後の観測だけが残る`である項目だけに認め、前述の計画ファイルの確認に代えて、該当節の`計画`と再開位置の`計画:`の一致を確かめる。
  値が`private-notes/plans/`からの相対パスなら、`atk config get private_notes`が返すパスの`plans/`配下に実在し`関連WI`に対象AWIを含むことも確かめる。
  再開位置が無い項目は、新しく計画を起草する対象とする。
- 採否: 不採用の決定と既存実装による充足の確定は、レーン担当へ残されている。
- `続行できない理由`: 根拠を検収し、自分で補える入力と技術的な不足は補って再検査する。
  ユーザーだけが判断できる事項に限って確認し、回答を得られなければUWIを登録して、回答を要する項目の`depends_on`へ加える（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「承認型UWIと元項目」）。

## 選定工程の完了

1. `atk wi list --target-repo=<対象リポジトリの絶対パス> --skip-pull`を1回実行し、選定した全項目（`unhold`した元項目を含む）が`processing`にあり、対象外の回答済みUWIが`processing`に含まれないことを確かめる。
   不一致があればレーンの起動へ進まず、状態と理由を記録する。
2. 対象リポジトリの規範が選定完了時点の評価や記録を求めていれば、この工程の中で保存する。
3. 以降は保存・検収済みの`選定`集合を基準にし、監査の終了を待たずレーンの起動へ進む。
   通常レーンが0件なら、会話圧縮を予約せず監査と公開へ進む。

返す報告に含める項目: 選定件数と候補件数、レーンごとの件数・段階・見込み秒数、除外候補と理由、時間目標の比較と採った配分、`続行できない理由`。
