# 実行レビューの手順

実行レビュー担当（`agent-toolkit:atk-mode/roles/exec-review.subagent.md`）が起動から返却まで上から実行する手順書である。
レビューの基準は`agent-basics:review-standards`が定義元で、本書はagent-toolkit固有の差分だけを置く。
終了条件は、全条件の判定と管理表の検査を終え、役割文書「出力」の形式で返した時点である。

## 着手時の確認

1. `agent-basics:review-standards`と`agent-basics:writing-standards`を起動し、前者は索引のレビュー担当と実行レビューの行、後者は変更ファイルの成果物の種類に合う資料を読む。
2. 起動入力に`全体作業契約`があれば、`agent-toolkit:atk-mode/references/work-contract.md`「工程境界での要求と成果の確認」で読み、判定を自分の記録に残す。
3. 対象worktreeは`cwd`、リポジトリはGitの共通ディレクトリ、対象HEADは起動入力の`対象HEAD`（省略時は着手時のHEAD）、変更ファイルはその固定版から解決する。
   プロジェクト規範と適用するスキルは対象worktreeと現在のplugin rootから解決する。
   計画、WI、CI記録、開始時点、管理表の所属リポジトリが異なれば、続行できない理由として返す。
4. 本文で受け取ったCI記録とWI記録は、すぐに自分のmanaged-tempのMarkdownへ原文のまま保存して入力記録とする（絶対パスで受けた記録はそのまま使う）。
   判定の根拠は入力記録のパスと行番号で引き、再レビューで更新された値は同じファイルへ追記する。
5. 管理表は、最初に読む前に`agent-toolkit:atk-mode/references/review-record-table.md`「レビュー指摘管理表のパス」で用意する。
6. `再レビューせよ`の追送か引き継ぎ再レビューなら、本書「再レビュー」へ進む。

## 差分とWIの取得

1. 開始時点は、`開始時のHEAD`があればその値、無ければ`計画`を含む時は実装着手前の作業ツリー、`CI記録`だけの時は`原因commitOID`の親commitとする。
   差分を取る直前に、開始時点とレビュー対象HEADを具体的なcommitへ解決する。
2. 基準ごとの要求を読む。
   - `計画`: `agent-toolkit:atk-mode/references/plan-format.md`（旧形式は`agent-toolkit:atk-mode/references/plan-legacy-formats.md`の対応）のH1直下の要約、`## 実施内容`、要求を書く節。
   - `CI記録`: 7項目の各項目。
   - `WI`: 要求、完成条件、由来、採否。
3. 対象WIは、受け取ったWI記録と、計画の`## 実施内容`で`由来`が`人間由来のWI`か`エージェント由来のWI`の行のWIとし、状態（`processing`、`adopted`、`rejected`など）によらず全て含める。
   計画の由来と採否は再利用し、原文との具体的な反証がある単位だけ根拠を示して訂正する。
4. 対象WIの本文は、`評価用WI原本`があればその一覧から、無ければ対象worktreeで`atk wi show`で取得する（複数件は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「複数件の`atk wi show`の取得」）。
   対象WIが全状態の一覧に無い時と指定された保存版を取得できない時は、不足する原本と再開の条件を返す。
   関連するUWIがあれば、その回答を取得してから判定する。
5. AWIの新旧の形式は`agent-toolkit:atk-mode/references/awi-body.md`「節の構成と分担」で判別して読み、要求単位は`agent-toolkit:atk-mode/references/review-contract.md`「記録する行と要求単位」で切り出す。
6. WIの鮮度（staleness）は計画の`## 調査結果と判断根拠`（8節形式では`## 変更履歴`）にある条件付きの履歴確認の判断を使う。
   `評価用WI原本`を使わない場合は、鮮度の記録がない項目をファイル名の形式で分け、対象worktreeで次のとおり照会する。
   - 固定年月形式の名前が1件以上あれば、`atk wi list --state=all --target-repo=<対象worktreeの絶対パス> --skip-pull --staleness-for <WIファイル名>`を実行する。
     同形式の複数件は`--staleness-for`を反復して1回で照会する。
   - 保存年月を名前から求められない旧名が1件以上あれば、`atk wi list --jsonl --state=all --target-repo=<対象worktreeの絶対パス> --skip-pull --with-staleness`を1回実行し、旧名に一致する行だけを読む。
     この照会はキューの全件走査を伴う。
   `notice`の表示だけでは履歴を調べず、現行の内容との食い違い、既存の実装によってすでに充足されている事実、変更の巻き戻しの危険を観測した項目について変更の履歴を調べる。

## 条項の生成

1. 期待する結果は、契約と差分を読む前に、`agent-basics:review-standards/references/reviewer.md`「初回レビュー」の手順1〜2で原要求から決める。
2. `計画`を受け取ったら、計画の各節と開始時点の実態から、出典付きの独立した条項を作る。
   条項には同手順1の事項に加え、合意事項、認可の範囲、除外と保持の事項、通常の入力と対象外の入力、誤った許可と誤った拒否が利用側へ及ぼす影響を含める。
   対象の集合は条件で定義し、件数そのものが合否の条件である時だけ計測した値と時点を残す。
3. 計画が過去の契約へ戻すか撤去する変更か、保持・不変性・完全復元の契約を含む時は、`agent-toolkit:atk-mode/references/plan-format.md`の「保持・不変性・完全復元の契約」「復元・巻き戻し型の変更」も条項にする。
4. `review_contract`は全文を読み、必要性と整合を評価する。
   新形式のエージェント由来AWIの条件表は`agent-toolkit:atk-mode/references/review-contract.md`「記録する行と要求単位」で検収し、具体的な成果の欠落と表の不足は判定行を作る前に起動元へ差し戻す。
5. 条項が指すcommit、WI、認可の資料を直接読み、認可された範囲を確かめる。
   解決できないcommit、取得できないWIか認可の資料、認可の範囲との不一致は、ラウンドによらず「認可不足」として続行できない理由で返す。
   事前に確認済みの認可の範囲は判定を重ねず、共通の公開契約、安全性、求められた統合結果への適合は評価する。

## 判定の観点と並行する探索

1. 走査を始める前に、文章成果物があれば本書「読者別探索」を行う。
   起動と終了の観測は`agent-toolkit:atk-mode/playbooks/delegation.md`「実行手段」に従い、`agents_server`が使えないCodexの代替では`fork_turns: "none"`で独立した文脈を保つ。
2. 各要求単位と変更面を`agent-basics:review-standards/references/reviewer.md`「初回レビュー」の手順で走査し、指摘は同「指摘内容」で書く。
   本書「再発防止観点の確認」も、同じ走査で担当自身が行う。
   追加を求める指摘には、削除・簡素化では要求を満たせない理由を添える。
   判定は`agent-basics:review-standards/references/reviewer-execution.md`「実行レビューの判定」の各節で行い、計画、WI、CI記録の読み方と語の読み替えは本書「計画と表の優先」「実行レビューの判定」による。
3. 走査の結果は、観点を1つ終えるごとに`agent-toolkit:atk-mode/references/review-record.md`「走査記録と差分外の不良」の走査記録へ保存する。
4. 本書「返却前の処理」へ進む。

## 計画と表の優先

- 計画の記述と管理表の応答が一致しない時は、後から記録された応答を現在の結論とする。
  要求の解釈を変える応答は、ユーザーの判断が確定するまで採らずに確認へ差し戻す。
- 計画と差分の食い違いは種類2とする。
- 計画の条項を根拠に指摘を登録する前に、条項が対象WIの明示の条件（`## 反映内容と反映先`、`## 完成条件`、`## ユーザーコメント`、関連するUWIの`## 回答`）と合うかを確かめる。
  衝突する時は指摘を登録せず、計画の条項とWIの該当箇所を並べて続行できない理由として返す。
  実装がWIの条件を満たし計画の条項だけから外れる時は、計画の不備として実装の状態とともに報告する。
- エージェント由来AWIの完成条件のうち、`agent-toolkit:atk-mode/references/review-record-verdicts.md`「失効の根拠」が受け入れる判断で否定されたものは、失効として扱い計画との衝突とみなさない。
  否定された範囲を超える条件と、人間由来のWIの条件は通常どおり判定する。
- 要求の縮小に当たるかは`agent-toolkit:atk-mode/playbooks/confirmation.md`「原文からの具体化を要する軸」で判定する。

### WIの完成条件

- 任意の節や引用位置の記録を省いた旧形式のAWIも、書かれた内容から検収する。
- リポジトリ全体の検証とCIの成功は、個別のWIの完成条件として判定せず、公開工程判定（`agent-toolkit:atk-mode/references/workflow-phases.md`「用語」）へ渡す。

### ユーザー要求単位

一般の方針を含むユーザーコメント、回答、追加入力の保存（`agent-basics:review-standards/references/reviewer-execution.md`「原要求と利用結果」）は、計画やWIに保存の項目が無くても原入力と比べて確かめる。
方針の反映、既存の規範による充足、反映しない妥当な理由のどれかを、表の体裁でなく保存先の内容で確かめる。

### 割当外・背景

- `割当外`: `agent-toolkit:atk-mode/references/review-record-verdicts.md`「判定の値」が受理する割当か引受の記録がある単位を達成の確認から外し、引用位置の記録が無いことだけで再起草を求めない。
- `背景`: 要求を含む単位を背景と分類した記録は種類1か種類5とする。

### 公開後に成立する条件と任意の判断材料

根拠欄は`agent-toolkit:atk-mode/references/review-record-verdicts.md`「公開後に成立する条件と任意の判断材料」に従い、次を加える。

- バージョン更新を完成条件に含むWIは、レーンの数によらず公開工程の完了処理担当が版数と派生するmanifestを更新して検収するので、レーンの差分に達成を求めずに`根拠不足`として延期`adopt`へ渡す。
  公開工程で更新する予定の記述は達成の証拠にしない。
- 行全体が任意の判断材料と明記された完成条件は、観測が無ければ`根拠不足`とし、指摘として登録しない。

### ユーザビリティレビューとの並行

同じ対象HEADのユーザビリティレビューが稼働中なら、その結果がまだ届かない条件を種類5とせず、役割文書「出力」の`判定工程: ユーザビリティレビュー`、`進行状態: 並行中`で返す。
画面の再レビューを省いた範囲は、前回の評価版と修正後の描画証拠を`agent-toolkit:atk-mode/roles/usability-review.parent.md`「返却後」に従って比べる。

## 実行レビューの判定

`agent-basics:review-standards/references/reviewer-execution.md`「実行レビューの判定」の語は、agent-toolkitでは次を指す。

| 定義元の語 | agent-toolkitで指すもの |
| --- | --- |
| 計画の検証欄 | 計画の`## 検証`の`変更範囲の検証`行（計画が無ければ引き継ぎ記録の検証コマンド） |
| 受入シナリオ | 計画かWIの要求が求める入口からの操作と期待結果（8節形式の計画では`### 受入シナリオ`の行） |
| リファクタリングの検討の結論 | 計画の`## 調査結果と判断根拠`にある既存箇所の見直しの結論（8節形式では`### リファクタリング`） |
| CI失敗の調査記録 | CI記録の各項目（「原因分析結果」「公開契約」を含む） |
| 進捗の記録 | 計画の`## 進捗ログ` |
| 提出された探索記録 | 実装担当が保存して`検証結果`から参照する、直接影響範囲の探索成果物 |

## 読者別探索

文章成果物があれば、直接確認か読者別探索担当の起動を選び、受領までを`agent-toolkit:atk-mode/roles/reader-fit-review.parent.md`の「起動」「入力」「受領」に従って行う。

ユーザーがAWIの`## ユーザーコメント`かUWIの`## 回答`へ担当者宛てに直接書いた質問（AWI本文へ転記された質問を除く）への回答下書きは、Gitの差分に無くても、検証結果が示す絶対パスを成果物、種別を「質問への回答」、読者を「質問したユーザー」として渡す。
事実を言い切る記述の根拠と現物を自分でも確かめ、根拠が欠ければ種類1として下書きの修正へ差し戻す。
回答UWIの保存は、レビューの収束後にメインエージェントが行う。

## 再発防止観点の確認

1. H1が`# 再発防止セルフチェック観点`で始まるMarkdownを、対象worktreeの追跡ファイルと現在の配布rootの両方から探す。
   対象worktreeで配布物の原本を追跡している場合は対応する配布版を除き、別のファイルは名前や内容が重なっても残す。
   検索と終了コード、採用した実在ファイルと除いた重複を走査記録へ書き、検索の失敗と該当なしを区別する。
   失敗した側は原因を除いて再取得し、取得できるまではその範囲を確認済みにしない。
2. 各項目の対象条件を今回の差分に当てはめ、該当する項目では根拠規範を読み、確認内容を現物で判定する。
   採用した項目は指摘の種類7の行へ観点のパスと項目名を記し、同じ指摘に当たる項目は既存行へまとめる。
   それ以外は、対象外・適合・不採用の理由を項目ごとに走査記録へ書く。
   再レビューは前回のレビューHEADからの差分と、差分の有無にかかわらず前回の未解決指摘を対象とする。

## 再レビュー

`再レビューせよ`の追送か、引き継ぎ再レビューの起動で使う。
確認の範囲とラウンドの継承は`agent-basics:review-standards/references/reviewer.md`「再レビューの場合」に従う（前回指摘の修正、修正差分、直接影響範囲に限り、範囲外の新規探索は初回に限る）。

1. 同じsessionの管理表、開始時点、レビュー基準、`review_contract`を引き続き使い、`review_contract`が更新されたら旧版を保存してから新しい版を使う。
   引き継ぎ再レビューでは、`前回確認版`から前回の開始時点、レビューHEAD、Git管理外の本文の複製を復元する。
   今回の対象は新たに受け取った`対象HEAD`で固定し、旧入力で省略された場合はこのラウンドの着手時のHEADを固定する。
2. `rewrite_map`を受け取ったら、判定の前に、前回確認版の開始時点とHEAD、前回の判定行と検証結果が指すcommitを新しいOIDへ読み替える。
   履歴の書き換えの後は、前回と今回の開始時点・HEADと各時点の契約から、ファイルごとの差分を比べる。
3. 修正差分の比較元は前回のレビューHEADとし、返却の`レビュー開始時点`には初回から引き継ぐ開始時点（書き換えの後は対応するOID）を書く。
   方式が変わった場合も、明示した再レビューの範囲を確認する。
   HEADが前回と同じでも、現在の入力で判定する。
4. 本書「差分とWIの取得」から「再発防止観点の確認」までを、今回の範囲で行う。
5. 前回のラウンドの各行は、現在の成果物、管理表の応答、検証結果から判定し、`agent-toolkit:atk-mode/references/review-record.md`「レビュー指摘管理表への登録」の`atk review-table recheck`で記録する。
6. 完成条件証拠は、影響する条件の新しい根拠と、影響しない条件で引き継いだ判定を分けて返す。
   HEADの表記だけの書き換えを再判定としない。
7. 再レビュー不要の修正は`agent-toolkit:atk-mode/references/review-record-acceptance.md`で受理し、実際のレビューの返却を書き換えない。
8. 本書「返却前の処理」へ進む。

## 返却前の処理

1. 完成条件証拠を求められていれば、`agent-toolkit:atk-mode/references/review-record.md`「完成条件証拠の作成」で全条件を判定し、同「条件別判定行の形式」の返却前の確認を終える。
2. 裏付けの取れた指摘だけを同「レビュー指摘管理表への登録」のとおり登録し、`atk review-table validate <表の絶対パス> --allow-unanswered`で表の構造を確かめる。
3. 未解決の指摘が0件でも、区分名の無い`未達`か`根拠不足`の条件が残れば、その不足を指摘として登録する。
   延期の記録で許容した未達は管理表と別の台帳へ写さず、判断の妥当性も確かめる。
4. 探索で得た全ての指摘と再発防止観点の全項目が、走査記録で表の行番号か根拠のある不採用の理由へ対応付いていることを確かめる。
5. 差分の外とレビューの範囲外の候補は`agent-toolkit:atk-mode/references/review-record.md`「走査記録と差分外の不良」で分類して渡し、それだけを理由に続けられるレビューを続行不能にしない。
6. 各ラウンドの開始時点、レビューHEAD、判定に使った契約をmanaged-tempの記録ファイルへ保存し、その絶対パスを引き継ぎ記録へ`前回確認版`として書く。
   同じ記録へ、Git管理外の文章成果物ごとの識別子（回答下書きは元の絶対パス）と読んだ本文の複製のパス、再発防止観点に由来する未解決の指摘、今回の差分の比較元も対応付ける。
   前回の本文と契約の保存ファイルは上書きせず、この工程を終えた時に次の比較元へ切り替える。
7. 担当の中で終えられる処理（判定行、検証、読者別探索の受領、再判定など）は返す前に終える。
   委譲元の判断か認可、取得できない入力、権限か外部状態の不足だけを、再開の位置とともに続行できない理由として返す。

メインが直接レビューする場合は、評価を求めた工程の形式で返す。
検証が到達できないと確定した要求は、計画か規範の問題として`続行できない理由:`で返す（`agent-basics:review-standards/SKILL.md`「検収手段の到達可能性」）。

返す報告に含める項目: 実行レビュー担当は役割文書「出力」の各行と延期の記録の所在。
