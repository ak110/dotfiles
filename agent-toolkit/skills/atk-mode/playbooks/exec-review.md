# 実行レビューの手順

実行レビュー担当（`agent-toolkit:atk-mode/roles/exec-review.subagent.md`）が、起動から返却までを上から実行する手順書である。
レビューの基準は`agent-basics:review-standards`が定義元である。
指摘の基準は`agent-basics:review-standards/references/reviewer.md`、実行レビューの判定と指摘の9種類は`agent-basics:review-standards/references/reviewer-execution.md`にある。
本書は、その定義元を使う時のagent-toolkit固有の差分（WIと計画の読み方、`review_contract`、指摘管理表、並行する探索、返却）だけを置く。
入力は役割文書「入力」、操作は同「操作区分」の範囲に限り、実装と修正はしない。
判定の根拠には、自分で観測した所在と内容を使う（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。
探索の担当の結果も、裏付けを確かめてから使う（原則6、`agent-basics:writing-standards/references/quality-principles-verification.md`）。
起動した探索の担当は、終了を観測して結果を回収する（原則7、`agent-basics:writing-standards/references/quality-principles-ownership.md`）。
終了条件は、全条件の判定と管理表の検査を終え、役割文書「出力」の形式で返した時点である。

## 着手時の確認

1. `agent-basics:review-standards`と`agent-basics:writing-standards`を起動する。
   `review-standards`の索引から、レビュー担当と実行レビューの行を選んで読む。
   `writing-standards`の資料は変更ファイルの成果物の種類ごとに選び、指摘の種類7の根拠に使う。
2. 起動入力に`全体作業契約`があれば、`agent-toolkit:atk-mode/references/work-contract.md`「工程境界での要求と成果の確認」に従って読み、判定を自分の記録に残す。
3. 対象worktreeは`cwd`、リポジトリはGitの共通ディレクトリ、対象HEADと変更ファイルは現在のGitの状態から取る。
   計画、WI、CI記録、開始時点、管理表の所属リポジトリが異なれば、続行できない理由として返して止める。
   プロジェクト規範と適用するスキルは、対象worktreeと現在のplugin rootから解決する。
4. 本文で受け取ったCI記録とWI記録は、すぐに自分のmanaged-tempのMarkdownへ原文のまま保存して入力記録とする（絶対パスで受けた記録はそのまま入力記録とする）。
   判定の根拠は入力記録のパスと行番号で引き、再レビューで更新された値は同じファイルへ追記する。
5. 管理表のパスと、初回に表が無い時の初期化は、最初に表を読む前に`agent-toolkit:atk-mode/references/review-record.md`「レビュー指摘管理表のパス」に従って行う。
   再レビューで表が無い時に空の表を作らないことも、同節にある。
6. `再レビューせよ`の追送か引き継ぎ再レビューなら、本書「再レビュー」へ進む。

## 差分とWIの取得

1. 開始時点を決める。
   `開始時のHEAD`があればその値、無ければ`計画`を含む時は実装着手前の作業ツリー、`CI記録`だけの時は`原因commitOID`の親commitとする。
   差分を取る直前に、開始時点とレビュー対象HEADを具体的なcommitへ解決する。
2. 基準ごとの要求を読む。
   - `計画`: `agent-toolkit:atk-mode/references/plan-format.md`に従い、H1直下の要約、`## 実施内容`、要求を書く節を読む。
     8節形式などの旧形式は`agent-toolkit:atk-mode/references/plan-legacy-formats.md`の対応で読む。
   - `CI記録`: 7項目の各項目。
   - `WI`: 要求、完成条件、由来、採否。
3. 対象WIの集合は、受け取ったWI記録と、計画の`## 実施内容`で`由来`が`人間由来のWI`か`エージェント由来のWI`の行のWIを合わせたものとする。
   計画の由来と採否は再利用し、原文との具体的な反証がある単位だけ、根拠を示して訂正する。
   状態（`processing`、`adopted`、`rejected`など）によらず、全ての対象WIを含める。
4. 対象WIの本文は、`評価用WI原本`があればその一覧から、無ければ対象worktreeで`atk wi show`で取得する（複数件は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「複数件の`atk wi show`の取得」）。
   全状態の一覧に対象WIが1件も無い時と、指定された保存版を取得できない時は、不足する原本と再開の条件を返す。
   関連するUWIがあれば、その回答を取得してから判定する。
5. AWIの新旧の形式は`agent-toolkit:atk-mode/references/awi-body.md`「節の構成と分担」の判別で読み、frontmatterの`type`が`awi`か`uwi`の項目の要求と完成条件を差分と比べる。
   要求単位の切り出し（ユーザーコメント、UWIの回答、計画の`ユーザー指示`の行、`## ユーザー指摘の逐語引用`の扱い）は`agent-toolkit:atk-mode/references/review-contract.md`「記録する行と要求単位」に従う。
6. WIの鮮度（staleness）は、計画があれば`## 調査結果と判断根拠`（8節形式では`## 変更履歴`）の条件付きの履歴確認の判断を使い、記録の無い項目は`atk wi list --with-staleness`で取る。
   計画も`評価用WI原本`も無い時は、対象worktreeで`atk wi list --state=all --target-repo=<対象リポジトリの絶対パス> --skip-pull --with-staleness`を1回実行して取る。

## 条項の生成

1. 期待する結果は、契約と差分を読む前に、`agent-basics:review-standards/references/reviewer.md`「初回レビュー」の手順1〜2で原要求から決める。
2. `計画`を受け取ったら、計画の各節と開始時点の実態からレビューの条項を作る。
   条項は、ユーザーの目的、現行の公開契約、合意事項、認可の範囲、除外と保持の事項、通常の入力と対象外の入力を、出典付きの独立した単位で書く。
   誤った許可と誤った拒否が利用側へ及ぼす影響も条項にする。
   変更対象に当てはまる作成規範とプロジェクト規範も条項に加える。
   対象の集合は条件で定義し、件数そのものが合否の条件である時だけ、計測した値と時点を残す。
3. 計画が過去の契約へ戻すか撤去する変更、または保持・不変性・完全復元の契約を含む時は、`agent-toolkit:atk-mode/references/plan-format.md`の同名の節（「保持・不変性・完全復元の契約」「復元・巻き戻し型の変更」）も条項にする。
4. `review_contract`は全文を読み、必要性と整合を評価する。
   新形式のエージェント由来AWIの条件表は`agent-toolkit:atk-mode/references/review-contract.md`「記録する行と要求単位」で検収し、具体的な成果の欠落と表の不足は判定行を作る前に起動元へ差し戻す。
5. 条項が指すcommitは対象リポジトリで特定し、WIは本書「差分とWIの取得」の取得元から読み、認可の資料を直接読んで認可された範囲を確かめる。
   解決できないcommit、取得できないWIか認可の資料、認可の範囲との不一致があれば、ラウンドによらず「認可不足」として続行できない理由を返す。
   事前に確認できた認可の範囲は認可の判定を重ねないが、共通の公開契約、安全性、求められた統合結果への適合は評価する。

## 判定の観点と並行する探索

1. 走査を始める前に、並行する探索を起動する。
   文章成果物があれば本書「読者別探索」を、毎ラウンド本書「再発防止セルフチェックの起動と受領」を行う。
   起動と終了の観測は`agent-toolkit:delegation/references/runtime-routing.md`「実行手段」に従い、`agents_server`が使えないCodexの代替では`fork_turns: "none"`で独立した文脈を保つ。
2. 各要求単位と変更面を、`agent-basics:review-standards/references/reviewer.md`「初回レビュー」の手順で走査する。
   判定は`agent-basics:review-standards/references/reviewer-execution.md`「実行レビューの判定」の各節で行う。
   計画、WI、CI記録の読み方は本書「計画と表の優先」、定義元の語の読み替えは本書「実行レビューの判定」にある。
3. 指摘は`agent-basics:review-standards/references/reviewer.md`「指摘内容」の基準（挙動の不具合に再現するコマンドと出力を添える基準を含む）で書く。
4. 走査の結果は、観点を1つ終えるごとに`agent-toolkit:atk-mode/references/review-record.md`「走査記録と差分外の不良」の走査記録へ保存する。
5. 本書「返却前の処理」へ進む。

## 計画と表の優先

計画、WI、CI記録、`review_contract`を定義元の比較元として読む時の、agent-toolkit固有の扱いである。

- 計画ファイルの記述とレビュー指摘管理表の応答が一致しない時は、後から記録された応答を現在の結論とする。
  実装着手後は計画ファイルを直接更新せず、要件変更への実装側の応答は管理表に記録されるためである。
  ただし元の要求の解釈を変える応答は、ユーザーの判断が確定するまで結論にせず、ユーザーへの確認へ差し戻す。
- 計画と差分の食い違いは種類2とする。
  計画ファイル自体の体裁、節の構成と整合、進捗ログは指摘にせず、更新するかは所有者に任せる。
- 計画の条項を根拠に指摘を登録する前に、その条項が対象WIの明示の条件（`## 反映内容と反映先`、`## 完成条件`、`## ユーザーコメント`、関連するUWIの`## 回答`）と合うかを確かめる。
  衝突する時は指摘を登録せず、計画の条項とWIの該当箇所を並べて続行できない理由として返す。
  実装がWIの条件を満たし計画の条項だけから外れる時は、計画の不備として実装の状態とともに報告する。
- エージェント由来AWIの完成条件のうち、`agent-toolkit:atk-mode/references/review-record.md`「失効の根拠」が受け入れる判断（ユーザーの判断、メインの技術判断など）で否定されたものは、失効として扱い計画との衝突とみなさない。
  否定された範囲を超える条件と、人間由来のWIの条件は通常どおり判定する。
  全体を不採用とするWIは、初回から`reject`の`未達`とする（`agent-toolkit:atk-mode/references/review-record.md`「判定の値」）。
- 要求の縮小に当たるかは`agent-toolkit:atk-mode/playbooks/confirmation.md`「原文からの具体化を要する軸」で判定する。
- 設計時に記録された鮮度の判断は、`notice`の表示だけを履歴を調べる根拠にしない。
  現行の内容との食い違い、既存の実装によってすでに充足されている事実、変更の巻き戻しの危険を観測した項目について、変更の履歴を調べる。

### WIの完成条件

- 旧形式のAWIは`agent-toolkit:atk-mode/references/awi-body.md`「節の構成と分担」の対応で読み、任意の節や引用位置の記録を省いた本文も、書かれた内容から検収する。
- リポジトリ全体の検証とCIの成功は、個別のWIの完成条件として判定せず、公開工程判定（`agent-toolkit:atk-mode/references/workflow-phases.md`「用語」）へ渡す。

### ユーザー要求単位

受け取ったユーザーコメント、回答、追加入力が一般の方針を含む時は、その場の要求の達成と、将来の判断主体が必要な時に読む成果物への保存を分けて確かめる。
方針を保存する項目が計画やWIに無くても原入力と比べ、方針の反映、既存の規範による充足、反映しない妥当な理由のどれかを確かめる。
合否は、表の体裁でなく保存先の内容で判断する。

### 割当外・背景

- `割当外`: WI本文か計画に他のWIへの割り当てが記録された要求単位と、割当先のAWIに引受の記録がある要求単位は、達成の確認から外す。
  引用位置の記録が無いことだけを理由に、再起草を求めない。
- `背景`: 分類の記録と原文の文脈を個別に確かめ、背景と認められる単位に限る。
  疑問符、過去形、注記だけを根拠に背景とせず、要求を含む単位を背景と分類した記録は種類1か種類5とする。
- 両区分の判定行、根拠欄の書き方、受理する記録の形は`agent-toolkit:atk-mode/references/review-record.md`「判定の値」に従う。

### 公開後に成立する条件と任意の判断材料

公開、配布、実環境への反映を要する条件の一般の扱いは、`agent-basics:review-standards/references/reviewer-execution.md`「提出された実動作の証拠」にある。
agent-toolkitでは次を加える。

- バージョン更新を完成条件に含むWIは、レーンの数によらず、公開工程の完了処理担当がバージョン番号と派生するmanifestを更新して検収する。
  実行レビューの時点ではレーンの差分で達成を求めずに`根拠不足`とし、延期`adopt`へ渡す。
  公開工程で更新する予定を書いた計画の記述は、達成の証拠にしない。
- 行全体が任意の判断材料と明記された完成条件（冒頭が「任意の判断材料」などで始まる行）は、観測が無ければ`根拠不足`とし、統合時にそのまま受理されるため指摘として登録しない。
- 根拠欄の書き方は`agent-toolkit:atk-mode/references/review-record.md`「公開後に成立する条件と任意の判断材料」に従う。

### ユーザビリティレビューとの並行

画面差分があれば、同じ対象HEADへ独立したユーザビリティレビューが並行する（`agent-toolkit:atk-mode/references/workflow-phases.md`「用語」の並列画面レビュー）。
結果がまだ届かない条件は種類5で登録せず、役割文書「出力」の延期の記録（`判定工程: ユーザビリティレビュー`、`進行状態: 並行中`）で返す。

## 実行レビューの判定

`agent-basics:review-standards/references/reviewer-execution.md`「実行レビューの判定」の各節を上から適用する。
同節の語は、agent-toolkitでは次のものを指す。

| 定義元の語 | agent-toolkitで指すもの |
| --- | --- |
| 計画の検証欄 | 計画の`## 検証`にある`変更範囲の検証`行（計画が無ければ引き継ぎ記録の検証コマンド） |
| 受入シナリオ | 計画かWIの要求が求める入口からの操作と期待結果（8節形式の計画では`### 受入シナリオ`の行）で、`検証結果`の実行範囲へ対応付ける |
| リファクタリングの検討の結論 | 計画の`## 調査結果と判断根拠`にある既存箇所の見直しの結論（8節形式では`### リファクタリング`） |
| CI失敗の調査記録 | CI記録の各項目（「原因分析結果」「公開契約」を含む） |
| 進捗の記録 | 計画の`## 進捗ログ` |
| 提出された探索記録 | 実装担当が変更範囲の検証の前に保存し、`検証結果`から参照する直接影響範囲の探索成果物 |

## 読者別探索

文章成果物があれば、直接確認か読者別探索担当の起動を選び、入力をそろえて結果を受領するまでを、`agent-toolkit:/share/reader-fit-review.parent.md`の「起動」「入力」「受領」に従って通常の走査と並行して行う。
共通の読者像で確かめられる文書はまとめて起動し、ファイルごとの比較資料、検証結果、証拠、起動の識別子を対応付ける。
探索の結果は、裏付けを確かめてから指摘へ統合する。

ユーザーがAWIの`## ユーザーコメント`かUWIの`## 回答`へ担当者宛てに直接書いた質問への回答下書きは、Gitの差分に無くても文章成果物として扱う（AWI本文へ転記された質問は除く）。
検証結果が示す下書きの絶対パスを成果物、種別を「質問への回答」、読者を「質問したユーザー」として渡す。
本担当は事実を言い切る記述の根拠と現物を確かめ、根拠が欠けていれば種類1として指摘し、下書きへの修正として差し戻す。
回答UWIの保存は、レビューの収束後にメインエージェントが行う。

## 再発防止セルフチェックの起動と受領

毎ラウンド、`agent-toolkit:atk-mode/roles/recurrence-self-check.parent.md`に従って観点を集め、通常の走査と並行して担当を1件起動し、結果を受領する。
起動を省く条件と渡す今回差分の比較元は同書「入力」に、結果の裏付け、採否、種類7としての登録は同書「受領と採否」にある。
セルフチェックへ渡す差分の比較元によらず、再レビュー全体の確認範囲は本書「再レビュー」のとおりとする。

## 再レビュー

`再レビューせよ`の追送（`round`と、任意の`review_contract`と`rewrite_map`）か、引き継ぎ再レビューの起動で使う。
確認の範囲とラウンドの継承は`agent-basics:review-standards/references/reviewer.md`「再レビューの場合」に従う（前回指摘の修正、修正差分、直接影響範囲に限り、範囲外の新規探索は初回に限る）。

1. 同じsessionの管理表、開始時点、レビュー基準、`review_contract`を引き続き使う。
   `review_contract`が更新された時は、旧版を保存してから新しい版を使う。
   引き継ぎ再レビューでは、`前回確認版`から前回の開始時点、レビューHEAD、Git管理外の本文の複製を復元する。
2. `rewrite_map`を受け取ったら、判定の前に、前回確認版の開始時点とHEAD、前回の判定行と検証結果が指すcommitを対応表で新しいOIDへ読み替える。
   履歴の書き換えの後は、前回と今回の開始時点・HEADと各時点の契約から、ファイルごとの差分を比べる。
3. 修正差分の比較元は前回のレビューHEADとし、返却の`レビュー開始時点`には初回から引き継ぐ開始時点（書き換えの後は対応するOID）を書く。
   管理表の応答欄に設計か実装方式の全面的な置き換えが記録された直後の再レビューに限り、開始時点からの全差分を確かめ直す。
   HEADが前回と同じでも、現在の入力で判定する。
4. 本書「差分とWIの取得」から「再発防止セルフチェックの起動と受領」までを、今回の範囲で行う。
5. 前回のラウンドの各行は、現在の成果物、管理表の応答、検証結果から判定し、`agent-toolkit:atk-mode/references/review-record.md`「レビュー指摘管理表への登録」の`atk review-table recheck`で記録する。
   修正で新しく生じた違反は、区分を付けて同節のとおり登録する。
6. 完成条件証拠を求められたら、全条件を新しいHEADで判定し直す。
   委譲元が前ラウンドの返却を受理した行は、修正差分と前提の変化が影響しない条件だけ`agent-toolkit:atk-mode/references/review-record.md`「受理済み判定への参照」で参照し、維持の理由を根拠欄へ書く。
   版の違う観測を使えるかは`agent-toolkit:atk-mode/references/review-record.md`「根拠の書き方」で判断する。
   解消済みの指摘を理由に`未達`か`根拠不足`としていた条件と、今回影響する条件は、新しい根拠で判定する。
   HEADの表記だけを書き換えることは、再判定に当たらない。
7. `対応完了（再レビュー不要）`で収束する時は、直前の実際のレビューの返却が完成条件証拠になる。
8. 本書「返却前の処理」へ進む。

## 返却前の処理

全条件と探索の結果を確かめて記録を終えてから、役割文書「出力」の形式で返す。
正式原本で返す時も、同じ確認を原本へ当てる。

1. 完成条件証拠を求められていれば、`agent-toolkit:atk-mode/references/review-record.md`「完成条件証拠の作成」で全条件を判定し、同「条件別判定行の形式」の返却前の確認を終える。
2. 裏付けの取れた指摘だけを`agent-toolkit:atk-mode/references/review-record.md`「レビュー指摘管理表への登録」のとおり登録する。
   表の構造は`atk review-table validate <表の絶対パス> --allow-unanswered`で確かめる（レビュー対象者の応答は待たない）。
   `未解決の指摘数`は同節の`unanswered_count`を使い、`recheck_pending_count`が0でなければ`recheck_pending_row_ids`の行を判定してから返す。
3. 未解決の指摘が0件でも、区分名の無い`未達`か`根拠不足`の条件が残れば、その不足を指摘として登録する（修正の担当へ渡す具体的な指摘が要るため）。
   延期の記録（役割文書「出力」）で許容した未達は管理表と別の台帳へ写さず、記録があることに加えて判断が妥当かを確かめる。
4. 探索で得た全ての指摘と再発防止セルフチェックの全項目は、管理表の行へ対応付けるか、根拠のある不採用の理由を記録する。
   セルフチェックの起動を省いた時は、その根拠を走査記録に残す。
5. 差分の外とレビューの範囲外の候補は`agent-toolkit:atk-mode/references/review-record.md`「走査記録と差分外の不良」で分類して渡す。
   再レビューでは、初回に報告した未処置の事項を委譲元の担当と是正の結果に突き合わせ、未完了の分を同じ報告へ対応付ける。
   報告済みであることと元のレビューの未解決0件だけを、全体の是正の完了としない。
   差分の外の不具合があることだけを理由に、続けられるレビューを続行不能にしない。
6. 各ラウンドの開始時点とレビューHEAD、判定に使った契約を、managed-tempの記録ファイルへ保存し、その絶対パスを引き継ぎ記録へ`前回確認版`として書く。
   Git管理外の文章成果物ごとの識別子（回答下書きは元の絶対パス）と読んだ本文の複製のパス、セルフチェック由来の未解決の指摘、今回の差分の比較元も、同じ記録へ対応付ける。
   前回の本文と契約の保存ファイルは上書きせず、この工程を終えた時に次の比較元へ切り替える。
7. 判定行、検証、読者別探索の起動・回復・受領、申告の補正、新しいHEADでの再判定など、担当の中で終えられる処理は返す前に終える。
   委譲元の判断か認可、取得できない入力、権限か外部状態の不足だけを、不足と再開の位置とともに続行できない理由として返す（区分は`agent-toolkit:/share/rules/rules-subagent.md`「返却形式の受け渡し」）。

## 専用レビュータスク契約

役割文書の入力にレビュー指摘管理表の絶対パスと`track`が明示された場合を、専用レビュータスク契約と呼ぶ。
この契約の担当だけが管理表を直接操作し、本書「完了報告」の形式で返す。
表と`track`を受け取った実装担当の一般の妥当性評価と、この契約を受け取らないメインエージェントの直接レビューは対象外とし、評価を求めた工程の形式で返す。
メインエージェントの直接レビューでも、検証が物理的に到達できないと確定した要求は、計画か規範の問題として`続行できない理由:`で返す（判断は`agent-basics:review-standards/SKILL.md`「検収手段の到達可能性」）。

### 完了報告

指摘は`atk review-table add <表の絶対パス> --round <ラウンド番号> --track <区分> --level <指摘レベル> --location-file <指摘箇所PATH> --issue-file <指摘内容PATH>`で記録する。
引数の渡し方と保存した本文の検証は`agent-toolkit:atk-mode/references/review-record.md`「レビュー指摘管理表の共通操作」に従う。

- 正常に終えた時は、`指摘件数: <非負整数>`と`要件仕様件数: <非負整数>`（そのラウンドで登録した`指摘レベル`が`要件`か`仕様`の件数）の2行を返し、指摘の本文は含めない。
  指摘の内容、検証の網羅性、検証結果、変更の要約は管理表に残る。
- 基準の文書を読む時に切り詰めの通知を受けた場合だけ、続けて`切り詰め: <文書の絶対パス> <全文読解の成否>`（`全文到達`、または`未到達`とその範囲）の1行を書く。
  この行が無いことは、切り詰めの通知を受けなかったことを示す。
- `気付いた改善点:`の行と、続行不能の区分と理由は、`agent-toolkit:/share/rules/rules-subagent.md`「返却形式の受け渡し」に従う。

返す報告に含める項目: 実行レビュー担当は役割文書「出力」の各行（状態、レビューHEAD、未解決の指摘数、読者別探索、開始時点と前回確認版、条件別判定行）と延期の記録の所在、専用レビュータスク契約の担当は本書「完了報告」の2行と切り詰めの行。
