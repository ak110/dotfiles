# 指示文の評価

<!-- 元ネタ: https://zenn.dev/mizchi/articles/empirical-prompt-tuning -->
<!-- 節をまたぐ手順を通し番号で示す。 -->
<!-- markdownlint-disable MD029 -->

エージェントへの指示文を、前提知識を持たない独立したプロンプト評価担当に読ませて指摘を集め、採否を決めて反映する手順書である。
作る者と確かめる者を分ける原則（`agent-basics:writing-standards/references/quality-principles-verification.md`）の適用であり、評価の偏りを防ぐため、評価担当へ渡す手掛かりは本書「起動」が定める入力だけにする。

## 評価する場合

- スキル、役割文書（`<役割名>.subagent.md`）、常時規範の節を新しく作る場合は、レビューへ渡す前に、シナリオを与えて評価する。
  対象は利用頻度の高いスキルと自動化の中核となる文書に限り、起動の費用に見合わない単発のプロンプトと、作成者の主観的な好みを反映するだけの作業は対象外とする。
- 指示と挙動の食い違いは、原因を指示の曖昧さに限らず、先に`agent-basics:bugfix`で調べる。
  その結果、指示文の改訂が必要と確定した場合に、改訂案を同じ方法で評価する。
- モデルかホストの更新を契機に文書の点検を求められた場合は、本書「文書の点検」を行う。
- 評価の対象はこの3つの場合に限り、どれにも当たらない既存の規範の改訂は対象外とする。
  この除外の範囲は評価という手段の選択だけで、品質に影響する指示文の欠陥の処置は`agent-basics:bugfix`で決める。
- 実際の操作、対話、成果物で確かめる試行（`agent-toolkit:atk-mode/playbooks/refine-prompt-trials.md`）の対象は構造に関わる変更（手順、分岐、入力と返却、起動の条件）に限る。
  文体や言い回しだけの変更は、費用の高い試行の対象から外す。
- 複数の記述をまとめて削る前後の3条件比較は、削減の判定根拠（`agent-basics:writing-standards/references/agent-documents-additions.md`「削減の判定根拠」）を得る任意の検証であり、上の限定によらず使える。

## 使用条件

- Plan modeの外で実行する（Claude Codeでは`ExitPlanMode`）。
- 委譲の手段（`agent-toolkit:delegation`）、参照資料、対象の実行環境を使えない環境では、提示された指示文を現在のセッションで直接評価する。
  結果を示す時に「プロンプト評価担当を起動できないため直接評価」と書き、未実施の試行の内容を明記する。
  独立した担当による評価、試行、ファイルへの反映は、委譲を実行できるClaude CodeかCodexで続ける。

## 条件と行動

| 条件 | 行動 |
| --- | --- |
| 新設か改訂の指示文を評価する | 本書「ワークフロー」から順に進める |
| 構造に関わる変更を、実際の操作、対話、成果物で確かめる | `agent-toolkit:atk-mode/playbooks/refine-prompt-trials.md` |
| 実セッションで観測した誤りから小課題を作り、条文の効果を比べる | `agent-toolkit:atk-mode/playbooks/refine-prompt-trials.md`「実セッション由来の小課題による比較」 |
| 複数の記述をまとめて削る前後を比べる | `agent-toolkit:atk-mode/playbooks/refine-prompt-trials.md`「大きな削減の3条件比較」 |
| モデルかホストの更新で文書を点検する | 本書「文書の点検」 |
| 評価担当を起動できない | 本書「使用条件」の直接評価 |

## ワークフロー

1. `agent-basics:writing-standards`を起動し、改善案の文面と対象の文書に同じ基準を当てる。
   評価は元の依頼の一工程として行い、元の依頼の計画の要否をそのまま保つ（`agent-toolkit:atk-mode/playbooks/write-plan.md`の起動は不要）。
   問題起点では、`agent-basics:bugfix`で確定した原因と対策の範囲を入力とし、評価担当の指摘は参考情報として扱う。
2. 対象と目的に応じて手法を選ぶ。
   通常は、シナリオを与えた読み取り専用の単発評価とし、反復する評価のシナリオは初回と同じ内容を保つ。
   シナリオなしの通読は、同じ基準を適用する実行レビューと役割が重なるため、本書「文書の点検」だけで使う。
   構造に関わる変更で、実際の操作、対話、成果物を見る必要がある場合は、`agent-toolkit:atk-mode/playbooks/refine-prompt-trials.md`の試行を加える。
   既存の固定課題か単発評価で判断できる場合は、その結果を使う。
3. 分量や論点数から評価担当の人数を決め、手順4へ進む。

## プロンプト評価担当の起動と受領

```text
起動対象: refine-prompt.subagent.md
```

入力の定義はこの起動契約とagents_serverの`start`の検査が所有する。
役割固有の入力（`extra_params`）はこの契約の入力一覧で完結する。

- 必須入力名: `対象プロンプト`、`シナリオ`
- 任意入力名: `点検資料`

<!-- input-contract:refine-prompt:end -->

評価担当の手順は`agent-toolkit:atk-mode/roles/refine-prompt.subagent.md`が定める（所在参照）。
返却の形式は本書「評価担当の返却契約」に従う。

### 起動

4. 指示文をUTF-8のファイルへ保存し、決めた人数分を同じ入力で並行して起動する。
   `agents_server`の`start`へ次の引数を渡す。

   | 引数 | 値 |
   | --- | --- |
   | `cwd` | 対象プロンプトを保持するリポジトリの絶対パス |
   | `subagent_md_path` | `refine-prompt` |
   | `extra_params` | 次の名前付き入力だけ |

   - `対象プロンプト`: 対象プロンプトの名前と、本文を保存したファイルの絶対パス
   - `シナリオ`: 手順2で決めた状況設定の1段落。
     文書の点検では`なし`
   - `点検資料`: 文書の点検だけで渡す、対象の一覧と公式の一次資料の保存先をまとめたファイルの絶対パス

   評価担当へは上の入力だけを渡し、改訂の経緯、前回の指摘、期待する指摘、作成したモデルの名前、他の評価担当の存在は伏せる。
   対象プロンプトの名前、本文を保存するファイルの名前と置き場所も、版や改訂を示す語（`old`、`new`、`v2`、`fixed`など）を避けて付ける。
   再評価も新しい担当を起動し、シナリオは改訂に合わせず初回のまま渡す。
   単発評価は、読み取り専用で指摘を返すまでで完結させる。

### 受領

5. 引数なしの`atk agents wait`で受け取り、本書「評価担当の返却契約」と形式が合わなければ、同じ入力で新しい担当を1回だけ起動し直す。
   文書の点検では、指摘ごとに対象と観点、該当の文言、行動への影響、根拠、修正案と承認範囲への作用がそろっているかを確かめ、本書「文書の点検」の手順5へ戻る。
   通常の評価は手順6へ進む。

### 評価担当の返却契約

以下の固定形式のみを返却する。
指摘1件ごとに`### 指摘`の見出しから`種別`の行までを繰り返して記述し、点検時は後述の欄を加える。

```text
状態: completed
### 指摘 N: <問題箇所を1行で>
- 重要度: 高 / 中 / 低
- 該当箇所: <対象プロンプト中の引用または位置を1〜2文で>
- 問題内容: <何が問題か1〜2文>
- 想定される悪影響: <この問題による行動への影響を1文で>
- 種別: 不明瞭 / 冗長 / 不足 / 誤り / 過剰な指定 / その他
```

続行不能と追加報告行は、共通契約`agent-toolkit:/share/rules/rules-subagent.md`「返却形式の受け渡し」に従う。
入力不足の場合は、対象プロンプトの不足情報と取得不能の根拠を記す。

`点検資料`がある場合は、各指摘へ次の4行を加え、末尾に点検済み・未点検範囲と未試行の比較を記載する。
指摘がない場合も、状態と点検範囲・比較の実施状況を返す。

```text
- 対象ファイル: <対象のパス>
- 観点: <点検観点>
- 根拠: <一次資料や現物の所在、該当文言、守る価値。仮説は区別する>
- 推奨する処置: <具体的な修正案と、承認範囲・権限が広がるかの説明>
```

## 指摘の集約と改善案作成

6. 重複する指摘と関連する指摘をまとめ、`agent-basics:review-standards`を起動して、レビューイーとして採否を決める。
   定義元の内容の転記を求める指摘は`agent-basics:writing-standards/references/agent-documents-basics.md`「定義の所有者」で評価し、採用する指摘の改善案をdiffで作る。
   評価担当の出力はユーザーへ直接表示されないため、指摘を示す時は原表現をできる限り保つ。
7. 技術的な指摘の採否は自分で決めて反映し、目的や期待される結果の変更と、ユーザーの選好や認可が要る事項だけをユーザーへ確認する（`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」）。
8. 反映した後は、対象の編集手順を定めるスキルと`agent-basics:check-execution`に従い、ユーザーの確認を待たずに元の依頼の残工程へ進む。
   評価の受領だけで全体を終えず、成果と検証結果を元の依頼の作業完了報告（`agent-toolkit:atk-mode/playbooks/report-completion.md`）へまとめる。
   振り返り（`/atk-mode review-session`）はこの手順書の外の独立した依頼として扱う。

## 文書の点検

モデルかホストの更新を契機に、エージェント向け文書を読み取り専用で点検し、提案の一覧を返す。
費用のかかる通読を必要な文書に限るため、検索による判定と評価担当の通読の2段階で行う。
点検の観点と処置の選び方は`agent-basics:writing-standards/references/agent-documents-additions.md`「文書記述量の管理」に従う。

1. 常時配送される規範（`share/rules/common/`と`share/rules/rules-main*.md`などの起動時の本文）、agent-basicsとagent-toolkitのスキル本体とreferences、hookがエージェントへ返す通知文を、配送元の定義から列挙する。
   点検済みと未点検は分けて示す。
   ホストの更新による点検では、変更履歴の該当項目と関係する規範だけを対象にする。
2. 処理するセッションのモデルとホストに対応する公式のプロンプトガイドを`agent-basics:writing-standards/references/claude-hooks.md`「モデル別の公式プロンプトガイド」から選び、版と適用条件を確かめる。
   対象の一覧と取得した一次資料の保存先を、点検資料のファイルへまとめる。
3. 1段階目として、対象の全ファイルを観点ごとに検索し、該当箇所を読んで判定する。
   ファイルごとに、`該当なし`、`提案あり`、`本文を読まないと判定できない`のどれかと、検索語、一致件数を記録する。
4. 2段階目として、常時配送される規範と、1段階目で`本文を読まないと判定できない`とした文書を、本書「起動」の手順で評価担当へ渡す。
   `シナリオ`は`なし`、`点検資料`は手順2のファイルの絶対パスとする。
   対象が多い場合は委譲の基準に従って範囲を分け、全範囲の結果を回収する。
5. 指摘を観点ごとの提案一覧へまとめ、提案ごとに対象ファイル、該当箇所、観点、根拠、推奨する処置を書く。
   全対象ファイルについて1段階目の判定と通読の有無を示し、未点検の範囲と未試行の比較を明示する。
6. 一覧を自分のmanaged-tempへ保存し、本文と保存先をユーザーへ届けて終える（自律処理では報告用UWIで届け、委譲先は委譲元へ返す）。
   提案に基づく編集は、ユーザーが採否を決めた後に別のAWIとして扱う。
   点検記録（点検した日付、基準にしたガイド、モデルID、ホストごとの確認済みの版、提案一覧の保存先）を、プロジェクトが点検の要否の判定に使う記録へ追加または更新する。

返す報告に含める項目: 評価した対象と手法（単発評価、試行、直接評価）と評価担当の人数、採用と不採用の指摘とその理由、反映した差分、未実施の試行（文書の点検では提案一覧の本文と保存先、未点検の範囲）。
