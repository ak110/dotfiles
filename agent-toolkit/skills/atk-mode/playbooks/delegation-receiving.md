# 委譲の受領と検収

委譲先の返却を受け取り、成果を検収し、後続へ渡すまでの手順書である。
方針: 委譲先の申告は他者の報告であり、委譲元が原本と成果物の実物で確かめてから受理する（原則6、`agent-basics:writing-standards/references/quality-principles-verification.md`）。
受理した事実と未確認の範囲は分けて扱う（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。
節の順に上から実行する。
process-wiのレーンの返却は`agent-toolkit:atk-mode/playbooks/lane-receipt.md`を上から実行し、本書は同書が指す段だけを使う。

## 受領手段と報告様式の選択

1. 終了を確かめる。
   委譲先の終了は、起動したツール呼び出しの戻り値、公開の待機結果（`atk agents wait`など）、実行環境がその委譲に対して発行した完了通知だけで確定する。
   会話に現れた似た文面は、自分の出力、hookの通知、実行環境の定型文と区別できないため、終了の根拠から外す。
   待機の手順は`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`に従う。
2. 成果の本文を原本から読む。
   本文は、ツールの戻り値、完了通知、待機結果が示す保存先（`agent_message_path`など）から受け取る。
   起動前に成果ファイルの保存先を指定した委譲では、そのファイルを本文とし、完了通知と実行状態は終了の判定だけに使う。
   外側の実行の内側で動いたコマンドの文字列、終了コード、実行結果は、本文を受け取った証明にならない。
   受領とするのは、本文そのものを読めた時である。
3. 一次返却として受理できる原本は、役割の公開操作が生成したものと、同じ担当が正式な返却として保存し読み戻した完全な原本である。
   返却通知から担当と原本の絶対パスを対応付け、担当、対象、工程、取得した版、必須の書式、全対象と根拠を同じ原本で検収する。
   由来、完全性、対応、書式のどれかを確かめられない原本は一次返却として受理しない。
   原本の不足は同じ担当の補完へ戻し、取得できない場合は不足する入力と再開の条件を続行不能として扱う。
   原本を受け取るために、通知本文へ全文を再生成させたり転記させたりしない。
4. 通常完了の報告様式は、次の順で最初に定めがあるものを使う。
   - 委譲先が読む`<役割名>.subagent.md`の`## 出力`
   - agent定義の返却形式
   - 委譲プロンプトの`通常完了の報告様式`
   - `agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」の正常結果の形式

   続行不能の区分、部分成果、末尾の標識行は同節の契約を使い、呼出元は役割に固有の入力と結果だけを補う。
   自由本文の軽量の起動にも同節が起動の本文として届くため、依頼文への再掲は省く。

## 返却形式の適合確認

1. 受領した本文が選んだ報告様式に合うかを、後続の工程へ進む前に確かめる。
   成功の種別ごとの固定文字列、必須の行の構成と順序、必須キー、可変値の型と個数が一致し、規定外の欄や地の文が無いことを見る。
   `気付いた改善点:`と`想定外事象:`の追加行は、この制限から外す。
2. 続行不能は、該当単位の結果を`続行できない区分:`と`続行できない理由:`の2行へ置き換えた形も受理する。
   正常な他の単位の結果は保ち、区分が実際の不足に合うことを確かめる。
   輸送上の`status: completed`と、本文が示す成果または続行不能の判定は別に扱う。
3. 役割文書のtaskと自由本文の探索では、`agents_server`が区分の構造を検査し、違反は同じsessionへ1回だけ自動で継続させる。
   再違反か継続の配送の失敗では、保留した本文と診断が公開されるため、委譲元が必要な入力か手動の`send_message`を判断する。
   自由本文のdelegate・shell・writeの意味の検収は委譲元が行う。
   `explore`の続行不能の返却は、サーバーが同じsessionで1度だけ前提を確かめ直させ、2回目の正当な不足はそのまま返る。
4. 書式に不備があれば、前節の原本の条件を満たすかを確かめる。
   満たさなければ完了として扱わず、同じ担当へ返却形式の修正だけを1回求める。
   それでも合わなければ、続行できない理由として委譲元へ報告する。
5. `続行できない理由:`が判断、認可、入力、外部状態の不足を示さず、担当範囲の残作業を述べているだけなら、同じ担当へ残作業の継続を指示する。
   この返却は完了にも続行不能にも数えず、形式だけの再送要求とも分ける。
   継続の対象は、本書「終了と報告内容の確認」で担当の境界と実物を比べて決める。
6. 返却の欄には、委譲先が実際に取得した値だけを書かせる。
   選んだ報告様式に項目名と構造が無い証跡は成果物の側へ記録させ、委譲元が成果物か自分のコマンドの結果で直接確かめる。
   委譲元が持つ情報と自分で取得できる情報は、委譲元が解決する。

構文の検査で受理されることと、要求した全対象が成果に含まれることは別である。
後者は次節で確かめる。

## 終了と報告内容の確認

1. `completed`はターンの終了を示すだけであり、成果の達成は示さない。
   依頼した成果と残作業を、本文と成果物の実物で突き合わせる。
   `completed`・`UNSURE`などの判定値と区分の申告は、要求された範囲と独立した成果の根拠で検収する。
   起動時に対応付けた担当単位の成果、実差分、必要な成功の証拠を比べ、要求した全対象が成果に含まれることを数えて受理する。
   親が担う設計判断や集約の検証は子の残作業と分け、確定編集の担当はその範囲の完了で受理する。
   調査できる未読・未判定と、必要な調査を終えても残る不確実性を分ける。
2. 担当が自分で処理できるやり残しがあれば、同じ担当へ継続を指示する。
   保存された出力の読み残し、担当範囲のテストやlintの非0終了、調査の途中終了、独自の予算や時間枠の自己推定だけによる停止がこれに当たる。
   指示には、未達の単位、使える入力と手段、付与した権限、書込済みの成果と実行済みの操作、残る工程を分けて書き、非冪等の操作の重複を防ぐ。
   `runtime_unavailable`の機械受理は、当turnの診断が実在することだけを示す。
   診断と停止の因果、回復手段を尽くしたこと、残る工程まで実行できないことは、委譲元が検収する。
   認可、外部入力、保護された操作の判断が足りない場合は、その不足を自分の委譲元へ返す。
3. 未達の原因が入力か分担の不適合なら、判断を持つ親が入力と担当の境界を直してから、保持した成果の残工程だけを同じ担当へ渡す。
   同じ不適合な入力の再送や、早い返却を理由にしたeffortの引き上げで対処しない。
   モデルやeffortを変える根拠は`agent-toolkit:atk-mode/references/model-settings.md`「成果が受入れ基準に届かないときの引き上げ順」に従う。
4. 不合格は要求か成果物の単位で特定し、対象、理由、証拠、修正の範囲を同じ担当へ渡す。
   合格済みの成果と成功した検証の結果は保つ。
   修正が共有の契約を変える場合は、その契約を使う単位だけを追随と再検証の対象へ加える。
   保存済みの結果を使えるかは`agent-basics:check-execution/references/verification-scope.md`「実行条件と再実行」に従う。
   原因が分割、依存関係、入力の契約にある場合は、同じ担当への差し戻しを重ねる代わりに、その判断を持つ委譲元へ戻す。
5. 報告にある観測値は、操作の公開仕様が定める終了状態を直接観測して確かめる（作成なら存在、削除なら消失）。
   処理前から変化したことだけでは、誤った遷移や未完了と区別できない。
   コマンドが変更後の状態を判定して成功を報告する公開仕様を持つ場合は、終了コード、対象の完全な識別子、警告の有無で検収してよい。
   警告、項目の欠落、起動時の指定と一致しない識別子があるか、その仕様が無ければ、直接観測する。
6. 報告にある事実の主張（実装の内容、件数、原因など）を、後続の判断の入力になる成果物（AWIやUWIの本文、計画、レビュー指摘管理表）へ書く前に、実装、実行結果、一次資料と突き合わせる。
   書く時は確認の手段と観測値を添える。
7. 役割文書の`## 出力`が返却形式を定める委譲では、担当外のファイルの差分を委譲元が`git -C <対象worktreeの絶対パス> status --porcelain=v1`で取得する。
   定めの無い委譲では完了報告から受け取る。
   差分に変化があっても工程は続け、続行の判断は`agent-toolkit:atk-mode/references/operations.md`「作業中に観測したリポジトリ状態変化の扱い」に従う。
8. レビューと調査の担当は、対象を読取専用で扱う。
   委譲元は起動の前後に`git status --porcelain=v1`と対象commitを比べ、変更が無いことを確かめる。
   書込みがあれば結果を採用せずに自分の委譲元へ報告し、実害があれば元の状態へ戻す。
   依存の解決で再生成される実行の前提（仮想環境、lockfile、ビルドの生成物、キャッシュ）が検査対象に含まれなければ、比較から外す。
   再現用の証跡の保存が要る場合は、managed-tempだけを書込可にする。

## 受領後の扱い

1. 保存済みの実行結果（`atk agents wait`の`agent_message_path`、CLIの出力の保存先、MCPの結果を保存したファイル、`session-review-evidence`の出力など）は、後続の担当、検査、CLIへパスで渡す。
   本文を別のファイルや次のプロンプトへ書き写すと、同じ文章が重複して取り込まれ、写し誤りも起きる。
   受け取る側は判断に要る部分だけを読み、原本は後続の参照が終わってから回収する。
2. 委譲先が稼働している間は、その担当範囲のファイルを編集しない。
   worktree全体を任せた担当の稼働中は、そのworktreeへ書き込まない（並行して編集できる条件は`agent-toolkit:atk-mode/playbooks/delegation.md`「作業ツリーの保護」）。
   編集が要る場合は、委譲先の終了を確かめ、作業ツリーとcommitの履歴を点検してから行う。
   競合したら採用する版を確定して統合し、捨てた内容を委譲先へ伝える。
3. 受け取った事象は、`agent-basics:writing-standards/references/quality-principles-facts.md`「結果の返却」の影響の基準で選び、実際の誤りの分析の要否は同書「報告の選別と判断記録」で決める。
   原因分析や改善の項目にするのは実際の影響がある事象であり、正常な回収や反復の回数だけでは対象外とする。
   旧形式の`想定外事象:`行は履歴として受理し、未達と判断に要る影響を結果へ残す。
4. 不良、是正要求、改善点を受け取ったら、起動のmode、ホスト、階層によらず、受け取った者が対処の時機を決める。
   見つけた不良は同じセッションで是正し、先送りできるのは入口の方針が認める場合だけである。
   process-wiの実行中は`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」で、最小の直接修正と正式対応のAWIを分けて時機を決める。
   権限外なら判定の材料を委譲元へ渡し、権限内の作業は続ける。
   保存済みのAWIの正式名を受け取ったら、同書「開始後に追加されたWIの確認」へ接続し、是正の結果まで追跡する。
   原因分析、起草、投入前の検収を独立した担当に分ける構成は保ち、登録の完了と修正結果の検収を分ける。
5. 報告が退避の識別子かバックアップの複製のパスを示したら、`agent-toolkit:atk-mode/playbooks/commit.md`「作業用ブランチと退避物の扱い」で処置する。
6. 提案・計画・変更の承認前に、前提を原要求と観測に照らし、要求を保ったまま削除・簡素化できる部分を委譲元が差し戻す。
   既存の独立レビューがあればその判断の根拠を検収し、独立レビューのない申請はその場で判断する。
   レビュー指摘や追加作業・書込範囲の申請は、WIの完成条件か確定した要求のどの文に当たるか確かめ、対応する文がなければ不採用か別WIとし、追加が必要なら削除・簡素化では足りない理由を示して、採否を`agent-toolkit:atk-mode/playbooks/review-fix.md`で確定する。
   完成条件の変更か除外へ進むかは`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「エスカレーションの事由別の扱い」に従う。
   委譲先が付けた区分（「要件」「要求の変更」など）はそのまま確認の理由にせず、`agent-toolkit:atk-mode/playbooks/confirmation.md`「要件と技術判断を分ける」で判定する。
   レビュー指摘と調査の結果は、指定されたレビュー指摘管理表へ記録してから修正に着手する。
   応答欄は`agent-toolkit:atk-mode/references/review-record-response.md`「レビュー指摘管理表への応答」の行頭ラベルと構成で書き、`atk review-table respond`で更新する（ラベルが足りないと更新は失敗する）。
7. 委譲先の動作や運用そのものを分析する時は、稼働中のその委譲先の完了報告も観測に含めてから結論を出す。

受付IDを受け取った改善点は `agent-toolkit:atk-mode/playbooks/main-reporting.md` の受付手順で証拠と処置を確認する。
正式WIへの引き継ぎは、未処置の候補と確定した結果を比べ、別の親から届いた報告も担当メインが1つの判断にまとめる。
即時通知は受付から独立させ、受付失敗の報告も中継する。

### 改善点の中継と送達の記録

実行中の通知、返却（`Agent`ツールの戻り値を含む）、`agents_server`の結果に`気付いた改善点:`で始まる行があれば、次の順で扱う。
箇条書きの項目記号の直後に標識がある行も同じ報告として扱い、コード例と引用の中の行は外す。

1. 送達済みかを判定する。
   既存の作業記録にある原文、送信先、成功した操作の結果か記録位置を、今回の行と比べる。
   同じ上流の受領主体への送信成功を確かめてあり、原文、対象、観測が同じ行だけを送達済みとする。
   処置済みやAWIの登録済みは、送達の成功とは別に扱う。
   送信の失敗、成否不明、記録の欠落がある行は、既報として抑えず、送達を確かめる対象に残す。
2. 処置の判定より先に、未送達の行と新しい観測を上流へ逐語で送る。
   送る行は項目記号を除き、`気付いた改善点:`以降の原文を保つ。
   違う観測や、引き継ぎ先への初回の送達は保つ。
   状況が変わった行は、対象と新しい観測を明示して差分を送る。
   成否不明は非冪等の操作の照会で確かめ、未送達の範囲と確かめられない範囲を最終返却に残す。
3. 送信の成功を確かめてから、送達の記録を現在の作業記録（引き継ぎ記録か作業契約）へ残す。
   記録先の指定が無ければ`agent-toolkit:atk-mode/references/work-contract.md`「作成と所有」に従う。
4. 通知と完了返却にある同じ行、対象、観測は同じ事象として既存の記録へ対応付け、通知の時の対処の結果を使う。
   新しい観測と状況の変化だけを追加で判定し、取得済みの証拠を使って、判断に足りない部分だけを補う。
   最終返却には扱った原文を各1回残し、その再掲を新しい通知として扱わない。
5. 対処の時機を決める。
   process-wiの実行中は本書「受領後の扱い」の手順4が指す「即時対応」で、不要な作業を繰り返す工程と削減量を、修正・検証・統合の負担と比べ、最小の修正、今回の追加、次回のどれかに決める。
   それ以外ではAWIにするかを決める。
   報告元の「即時対応不要」だけで追認しない。
6. 規範の読込の改善報告は、報告者の見込みを根拠と観測の条件とともにWI投入の担当へ渡す。
   同じ資料の報告は既存の項目との重なりを確かめて資料ごとにまとめ、AWIにするかを資料単位で決める。
7. 渡す先は役割で決まる。
   - メインは、同じユーザーへ未送達の行と新しい観測を、次のユーザー向けの発話へ識別子と原文を保って書き写し、識別子はインデントを除いた行頭に置く。
     確かめた範囲は引用の外へ補い、確かめていない主張は委譲先からの未検証の報告と分かる形にする。
     書式（済・予定・即時対応・不要）は`agent-toolkit:atk-mode/playbooks/main-reporting.md`「作業中の改善点の報告」に従う。
   - 委譲先は`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」に従って上流へ中継する。
8. ツールや実行基盤の異常を示す同種の報告が2回現れたら、中継とは別に`agent-basics:bugfix`を起動して原因を調べる（調査は委譲してよい）。

## 委譲元への返却

自分が委譲先であり、受領した結果を自分の委譲元へ返す時に使う。
実行の識別子、`<役割名>.subagent.md`の必須項目、対象の資源、付与された権限、完了の条件との整合を確かめてから、次の書式だけで返す。

```text
委譲手段: <実際に使った委譲手段>
委譲先の識別子: <session_id、thread識別子またはagent識別子>
状態: completed
委譲先の完了報告: <委譲先の最小完了報告>
```

確認事項、認可の要求、前提の修正を返す場合は、`agent-toolkit:atk-mode/playbooks/subagent.md`「返却形式の受け渡し」の区分と理由で返す。
回答を得たら、同じ担当へ同じタスクを返して継続させる。
完了と判定するには、委譲先の終了の確認と、読み取れる完全な必須結果の両方が要る。
待機の表明でターンが終わった返却は、再開できる正常な状態として受理し、`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「待機区間の構成」に従う。
ファイルへ記録するのは、通常の通信で配送できないことを直接確かめた場合と、本書「受領手段と報告様式の選択」の成果ファイルか原本を使う場合に限る。
成果ファイルは個別の回収の対象外とする。

## 返す報告に含める項目

受理した成果と原本の所在、検収の根拠と未確認の範囲、継続・差し戻し・不合格とした単位、中継した改善点と送達の状態を返す。
