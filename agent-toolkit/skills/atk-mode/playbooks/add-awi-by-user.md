# AWI投入

`/atk-mode add-awi-by-user [入力]`で始める、AWI（エージェントワークアイテム）の具体化と登録の手順書である。
この作業は、ユーザーの入力が名指しした時だけ選ぶ。
協調モードで動き、成果物はWIの登録と更新に限る（本書「セッション境界」）。
対象リポジトリの実装、実装用worktreeの作成、AWIの`processing`への変更、実装担当の起動は、後続の`agent-toolkit:atk-mode`の作業`process-wi`が担う。

登録前に分かる本人固有の判断はこの場で確認し、技術判断は原則1に従って自ら確定する。
起動を登録の認可として扱う。
投入前レビューの合格後に保存する。
この場で求められた回答や判断はここで終え、後続の変更とWIとの同期が要る作業を登録する。
`atk`・対象リポジトリ・既存キューを読めない場合は原稿を下書きとして返す。

## 読む節

着手前に本書を全文読み、「手順」と「セッション境界」に従う。
原稿を作る前と登録0件で終える前は「起草と保存」、指摘・追加発話・異議を受けた時は「指摘の分類と処置」を適用する。
実際に測定する時は「測定の手順」、巡回や作業の進め方を改善する要求を扱う時は「稼働中の巡回への連絡」に従う。
報告前は「完成条件」と「返す報告に含める項目」を確かめる。

## 手順

1. 着手時に、managed-temp直下に現行の作業契約が無ければ、`agent-toolkit:atk-mode/references/work-contract.md`「作成と所有」で作る。
   系統は`agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入」の系統を登録したリポジトリ宛ての段に従って選び、決められなければ`agent-toolkit:atk-mode/playbooks/request-intake.md`の手順7で聞く。
   不具合・指摘・エラーは先に`agent-basics:bugfix`を起動する。
   既存AWIの更新・懸念は質問や調査の前に扱い、`inbox`・`hold`は保留し、`processing`への変更は別AWIに切り出す（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「保留と本文修正」）。
2. `agent-toolkit:atk-mode/playbooks/request-intake.md`の手順で要求を受け付け、方針を確定する。
   目的の衝突、指定範囲との不一致、認可不足、変更を左右する読みの違いは、同書の手順7で扱う。
   方針を決めた時点で、中心と理由、継続費用を加える対象、除外と理由、調査済みと未調査の成果物の種類を一度報告する。
   確認が要らない依頼では、回答を待たずに続ける。

3. メインが調査、対策、起草、検収、保存を担う。
   - `agent-toolkit:atk-mode/playbooks/wi-drafting.md`「起票目的別の調査出口」に従い、独立した要求へ分けて起草し、逐語引用と由来・確定要件・技術判断を分ける。
     現物を読む新規AWIでは、同書「対象の調査基点」を保存まで保持する。
     不具合は原因、類似箇所、別件、再発防止を起草前に確定する。
     コードと規範の不一致は`agent-basics:bugfix`で判定し、同じ条文を足さない。
     使い方が変わる要求は、ガイドと公開後の案内も反映内容へ書く（`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「使い方が変わる変更」）。
   - 付随の別件など文脈を分ける理由がある時だけ`agent-toolkit:atk-mode/roles/add-wi.parent.md`で委譲する。
     基準が明確な大量走査は読取専用で分担できる。
   - 原稿確定・不採用・登録0件の前に`agent-toolkit:atk-mode/playbooks/request-intake.md`の手順6を再点検する。
     選好を要する不採用は同書の手順7で確認し、未調査や根拠の薄い候補の撤回だけなら残る検討へ戻る。
   - 起草者は`agent-toolkit:atk-mode/playbooks/wi-saving.md`「保存前の確認」と`agent-toolkit:atk-mode/roles/wi-draft-review.parent.md`「入力」に従い、原稿を原文と読み比べ、dry-runで冒頭の抽出を確かめる。
     保存する原稿は毎回同じ親契約で独立検収する。
     会話原本と起動発話の位置を渡し、同時にそろった原稿は識別子と冒頭の所在を対応付ける。
     指摘は本書「指摘の分類と処置」で扱う。
   - 独立検収後の保存とその結果の確認は、`agent-toolkit:atk-mode/playbooks/wi-saving.md`の「投入と取得」の導入と「投入」「保存結果の検収」「返す報告に含める項目」に従う。
4. 投入を終える。
    登録0件で対応表を作った場合は、原稿か作業記録に残した対応表と採否を読む。
    登録0件でも起動発話以降のユーザー発話を原本で読み直し、投入前レビューがあればその返却も読む。
    ユーザー発話ごとに原稿への反映か処置の送達を確かめる。
    原稿を変えたら修正後の根拠を確かめ、前提か範囲が変わる場合は投入前レビュー担当へ要否を照会する。
    変えない指摘を含めて処置を伝え、要とされた範囲の再判定を終える。
    未処置の項目はその場で扱い、原稿を変えない場合は処置を伝える。
    振り返りは通常終了と分ける。

## 指摘の分類と処置

ユーザーの指摘・追加発話と投入前レビューの指摘は、作業中か完了後かによらず、受けた時点で次の順に扱う。
修正、再評価、再確認へは、分類と処置を終えてから進む。
質問には、今の検討状況と根拠を先に答える（`agent-toolkit:atk-mode/playbooks/user-utterance.md`「問い・提案・疑問形の扱い」）。
停止、変更、撤回を明示した原文がある部分だけを要求の変更として取り込み、質問だけなら今の要求を保って元の工程へ戻る。
過去の判断を問われた時は、元の質問、全ての選択肢、実際の回答を取得して答え、一括の採用を個別に比べて選んだ事実へ言い換えない。
報告や結論への異議は、分類の前に`agent-basics:bugfix`を起動する。

1. 要求単位へ分ける。
   文章の書き方への指示と行動の是正も含めて分け、単位ごとに、既存・起草中のAWIへ合流させるか独立した要求にするかを判定する。
   発話が範囲の一部だけに触れていても、確定済みの範囲を縮めない。
   縮小の明示がある時と意図が曖昧な時は、今の範囲を`共通前提`に示して確認する。
2. 分類する。
   - 考慮漏れ: 原文、調査結果、現物、適用中の規範から導けたが、方針へ反映しなかったもの（手順4で処置）。
   - ユーザーだけが持つ新しい情報: 選好、未開示の制約など、登録前の調査では導けなかったもの。
     要件として反映する。
   - 前提の誤り: 指摘の技術的な前提が現物と合わないもの。
     根拠と代替案を示す。
   - 採用しない提案: 検討の結果、採用しないと決めた提案。
     根拠を示す。
3. 既存の判断を是正した介入は、分類とは別に`agent-toolkit:atk-mode/playbooks/user-utterance.md`「ユーザー介入と確認の判定」で評価する。
   以後の同種の作業にも当てる方針の候補を含むかは、今回の原稿への反映と分けて判定する。
4. 考慮漏れは、`agent-basics:bugfix`で原因を分析し、同じ仕組みで漏れうる観点を全ての方針で見直してから反映する。
   再発防止策は`## 原因分析`付きの別のAWIとして起草し、対策の対象を所有するリポジトリへ、元のAWIと一緒に登録する。
   投入先が増える時は、本書「手順」の1の`begin`を再実行する。
5. 処置の後に方針を確かめ直す時は、論点ごとに`agent-toolkit:atk-mode/playbooks/request-intake.md`の手順7の基準を適用する。
   追加の発話が新たな改善の検討（何を変えるかを選び直すこと）を求める時と、既存の仕組みの前提を変える値・範囲・方式を指定した時は、既存の要求へ合流する場合も含めて次を行う。
   変わった範囲を同書の手順4の比較（指定された変更が前提を変える既存の仕組みを引く案を含む）にかけ、採る案・採らない案と理由を方針として起草の前に報告する。
   確認するのは、同書の手順7の条件（本人の選好、未開示の制約、認可）に当たる論点だけとし、技術で決まる採否は報告して進む。
   方針全体の質問は、初回の依頼だけに課す（同書の手順7の最初の箇条）。
6. 分類・処置と根拠をその場で一度だけ `send_to_user` で伝える。
   使えない環境では通常の本文で伝える。
   再発防止の判断は必要な場合に原稿の `## 原因分析` へ反映し、別の指摘対応記録は作らない。
7. 戻る。
   質問の途中なら`agent-toolkit:atk-mode/playbooks/request-intake.md`の手順6、原稿の確定・検収の途中なら本書「起草と保存」の3の再点検、完了報告の後なら本書「手順」の1から再開する。
   独立した要求は`agent-toolkit:atk-mode/playbooks/request-intake.md`の手順1から受け付け、同書「依頼の種類と確認」に従ってから本書「起草と保存」の3で起草する。

## セッション境界

成果物をWIの登録と更新に限る制限には、`agent-toolkit:atk-mode/playbooks/user-utterance.md`「成果物の制限」を適用する。
起動の後に届く「反映して」「修正して」と、再発防止・完遂の要求は、全てAWIの本文への反映の指示として扱う。
例外として行ってよい操作は、次のものに限る。

- 登録用の一時入力ファイルの作成と、作成した一時ディレクトリの`rm -r -- <作成した絶対パス>`による回収
- 対象リポジトリの規範が同じ工程で求める追跡用ファイルへの記載
- 完成条件や採否を決める値の測定と、そのための可逆な一時変更（本書「測定の手順」）
- 稼働中の巡回への連絡（本書「稼働中の巡回への連絡」）

中止と再開は次のとおり扱う。

- ユーザーが中止するか依頼を取り下げた時は、保存せずに終える。
- 完了の後の追加発話で投入を再開する時は、調査の前に本書「手順」の1をやり直し、完了では本書「起草と保存」の4で終える。
  再開を生んだ発話から、原稿への反映と処置の送達を確かめる。
- 既存AWIの更新と判断した時は、調査の前に本書「手順」の1のとおり保留し、同じ起草者が、現行の本文、確定した変更、原文を対象の`ファイル名`に結び付けて更新する。

対象リポジトリの外への操作の認可と確認の要否は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
委譲する時は、起動する作業の名前、対象リポジトリ内の恒久的な変更をAWIに限る制限、制限の対象外になる判断、セッションの終了条件を依頼文に書く。

## 稼働中の巡回への連絡

登録する要求が、AWI処理の巡回やエージェントの作業の進め方の改善（所要、委譲、待機、起動、点検など）である時に行う。
製品機能の要求など、巡回の進め方に関わらない登録は対象外とする。
ユーザーが対話で起動した振り返りにも同じ手順を適用し、非同期にまとめて行う振り返りと巡回自身は対象にしない。

1. 投入先のリポジトリを処理している巡回の会話が稼働中かを、ホストが提供するセッション間の連絡手段で確かめる。
   宛先は、複数のリポジトリを統括する会話か、対象のリポジトリを直接担当する会話である。
   Claude Codeでは、同じマシンの他のセッションの一覧に巡回の会話が無ければ、稼働していないものとして扱う。
2. 分析で「実装を待たずに今すぐ適用できる改善」が確定した時点で、AWIの保存を待たずに伝える。
   `ファイル名`は保存の後に続けて伝え、伝えた内容に誤りが分かれば訂正を送る。
   ユーザーの指示を待たずに行い、ユーザーが既に伝えたと述べた内容は繰り返さない。
3. 伝える内容は、観測した事実と出所、今すぐ取れる行動を分けて書き、指示や承認の形にしない。
   採否と時機は、受け取った統括が自分の規範で決める。
   統括の起票の予定と重なる時は、重ねて起票しなくてよいことを添える。
4. 巡回のWIの状態変更、担当の停止、設定の変更など、巡回への直接の操作は行わない。
   相手の側で権限の承認待ちになっても、再送や別の経路での強制はしない。
5. 連絡手段が無いか使えない環境では、伝える内容を作業完了報告へ「稼働中の巡回へ未伝達」として示し、ユーザーが中継できるようにする。
6. 作業完了報告へ、伝えた内容の要旨と、伝えられなかった場合はその理由を書く。

## 測定の手順

測定の後に、対象リポジトリの作業ツリーを測定前の状態へ必ず戻す。

1. 環境変数、コマンドライン引数、別名の一時設定ファイルなど、Gitの追跡対象を変えない手段を優先する。
2. 追跡対象を一時的に変える時は、測定の前に`git status --porcelain=v1`の出力と変更するファイルの内容を退避する。
   変更するファイルか、測定で書き換わりうるパスに既存の差分がある時は、`git worktree add --detach`で作った検証用worktreeの中で測定する。
3. 元の作業ツリーで測定した時は、変えたファイルを退避した内容で戻す。
   `git -c submodule.recurse=false checkout`と`git clean`は、測定前に差分が無かったパスだけに実行し、初期化済みのサブモジュールのHEAD、ブランチ、作業内容を保つ。
4. 測定後の`git status`が退避した測定前の状態と合わない時は、後続へ進まず、差分の内容と退避先のパスをユーザーへ報告する。

## 完成条件

- 登録の時点の調査で分かる、要件や結果を左右する本人固有の事項に回答を得ている。
  処理の時に初めて分かる事項だけが、残す理由とともに本文にある。
- 登録した全てのAWIが`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「起票目的別の調査出口」を満たす。
- 質問を終える時の報告に全類型の点検結果と処置がある。
  原稿を保存する場合は、原稿確定前の再点検、意味の確認、dry-run検証、投入前レビューの合格、保存結果の検収を終えている。
- 登録0件でも、原本で処置を確認し、選好を要する不採用に回答を得ている。
- 対象リポジトリの実装ファイルと`processing`のAWIが、起動前の状態のままである。

## 返す報告に含める項目

登録・更新・終了したAWIのファイル名とタイトル、AWI本文に記載していない判断、未達を返す。
