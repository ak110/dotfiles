# AWI投入

`/atk-mode add-awi-by-user [入力]`で始める、AWI（エージェントワークアイテム）の具体化と登録の手順書である。
この作業は、ユーザーの入力が名指しした時だけ選ぶ。
協調モードで動き、成果物はWIの登録と更新に限る（本書「セッション境界」）。
対象リポジトリの実装、実装用worktreeの作成、AWIの`processing`への変更、実装担当の起動は、後続の`agent-toolkit:atk-mode`の作業`process-wi`が担う。

方針は次のとおりである。
このセッションは、ユーザーと追加の費用なしに対話できる最後の機会である。
後続で必要になるユーザー判断はUWIの投入と回答待ちを生むため、登録の時点で分かる本人固有の論点は今確認する。
技術で決まる事項は、原則1（`agent-basics:writing-standards/references/quality-principles-roles.md`）のとおり自分で決めて報告する。
AWI登録の認可は名指しの起動で成立しているため、本文の全文を示した一律の登録可否の確認は省き、投入前レビューに合格したら保存する。
この場で求められた設計案、回答、選好の確定はこのセッションで終え、後続で行う変更の要求と、WIの内容と同期が要る作業をAWIとして保存する。

`atk`、対象リポジトリ、既存キューの読み取りが使えない環境では、対話で整理した原稿を登録前の下書きとして返す。

## 手順

1. 開始を記録する。
   - 調査の前に、起動したリポジトリ（起動時のcwdが属するリポジトリ）と既知の投入先を並べて`atk wi submission begin --target-repo <リポジトリ>`を実行する。
   - 投入先を足すか変えた時は、調査・採否確認中のリポジトリと未保存の要求の投入先を全て並べて再実行する（`begin`は集合を置き換え、開始時刻を保つ）。
   - 記録がある間は、該当リポジトリの`atk wi process-loop`が投入の完了を待つ。
     登録0件でも手順10の終了検査まで進み、中止する時は本書「セッション境界」の`--abort`で終える。
   - 投入先が系統を登録したリポジトリなら、宛先の系統を要求の内容から決め、決まらなければ手順7で確認する（`agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入と取得」）。
   - 不具合、ユーザーの指摘、エラー、hookの誤動作を起点とする要求は、調査の前に`agent-basics:bugfix`を起動する。
   - 依頼が未完了の既存AWIの更新や懸念を含む時は、質問と調査の前に状態を扱う。
     `inbox`・`hold`の項目は保留にしてから更新し、`processing`の項目への変更は新しいAWIとして切り出す（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「保留と本文修正」）。
2. 入力から要求を読む。
   起動後の入力は全て要求として扱う（動作を選ぶ引数は無い）。
   原文の範囲表現、列挙、例示、理由は`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」に従って読み、明示・合意済みの要件は確定済みとして扱う。
   - 引数の無い起動で、直前の応答が項目ごとの対応方針を示している時は、その内容を登録の入力とし、示した基準で決まらない項目だけを質問する。
   - URLや文書などの資料だけを渡された時は、資料を参考に起動したリポジトリを改善する投入として扱う。
     範囲の限定が無ければ、資料の全目的を改善候補とする範囲が確定した依頼であり、目的が複数あることや本人の用途が書かれていないことだけでは確認せずに調査へ進む。
   - 目的の衝突、依頼本文の限定と資料の目的の不一致、認可の不足、資料の読みが両立せず読みで変更が変わる場合（手順5）は、本人の判断が残る場合として手順7で確認する。
   - ユーザーがモデル、ツール、担当、操作手順などの手段を指定した時は、どの工程（`agent-toolkit:atk-mode/references/workflow-phases.md`「工程表」）向けかを原文から対応付ける。
     このセッション向けの指定は後続工程の要件に含めず、対応が一意に決まらず要件や完成条件を変える時だけ工程ごとに確認する。
3. 実物と既存WIを調べる。
   - 外部資料を起点とする投入では、最初に、資料の主張者が公開している実装（リポジトリ、スキルの本文）を探して読む。
     要約や紹介の投稿だけを読んで規範と比べる進め方は誤りである。
   - 実物を読んだ直後に、その名称と主題で全状態の既存WIを検索する（`atk wi grep --summary-only -F <語> --state=all`）。
     ユーザーが持ち込んだ新しい主題でも検索する。
   - 資料との対応付けは起動したリポジトリから始め、成果物（コード、規範、文書、設定）が資料の主題をどう扱っているか（記述の有無と正誤）で関係を判定する。
     主題の語がコードに現れるかでは判定しない。
     他のリポジトリの見直しはそこから派生して行い、他のリポジトリだけへ投入する場合も起動したリポジトリの採否と理由を記録する。
   - 多数のファイルを作り替える要求は、登録の前に対象をファイル単位で棚卸しし、変更前の読込量、構成の目安、削ると再発が見込まれる保護を本文に書く。
   - 観測された問題（失敗、不具合、未対応）を起点とする要求は、証拠を集める前に問題の主文から母集団を定め、現れ（確認UWI、追加修正、ユーザーのコメント、是正の回答）を先に挙げて、調べるか調べない理由を残す。
     対処方針は、原因分析と類似箇所の見直しで対策が決まってから選ぶ。
   - 対象リポジトリの外へ成果を反映する要求は、反映先ごとの終了状態（commitまでかpushまでか）を`agent-toolkit:atk-mode/references/awi-body-completion.md`「完成条件」で判定する。
4. 方針の案を組む。
   - 資料を参考にする投入では、最初に、目的を対象の側の結果で1文に書く（対象の何を良くするか）。
     資料は手段であり、資料の形に合わせることを目標と完成条件に置かない。
   - 外部の成果物を参考にする投入では、内容の対応付けより前に、配り方（何が常に読まれ、何が起動した時だけ読まれ、何が検査されるか）を対象の現行の配り方と並べて比べる。
   - 細則の多い対象を整理する投入では、置き場所の対応付けより前に、細則が守ろうとしている結果を上位の原則へまとめる案を比べる。
     領域に分けて調べる前に、領域をまたぐ同じ主題の組を表題、見出し、ファイル名の機械的な一致で挙げ、組ごとに定義元と担当を決める。
   - 新しいAWIを作る案と、未処理（`inbox`・`hold`）の既存WIへ統合する案を、最初から並べて比べる。
     比べる相手は、目的が同じWI、同じ文書・ファイルを変えるWI、今回の要求が直す文書を作り替えの対象に含むWIである。
     統合する時は、既存WIの本文を変更の対象と目的で組み直して同じファイルへの変更を1か所にまとめ、節を機械的に連結しない。
     独立して採否と完成を判定できる要求は混ぜず、統合しない理由を方針の提示に書く。
   - 資料の目的と手法は、対象の現在と改善後の操作手順・便益へ対応付け、提供機能と消費形態は`agent-toolkit:atk-mode/references/omission-check.md`「資料起点の比較」で比べる。
     資料の全項目を対応付けた後も、同じ問題に関わる実行経路、制約、利用場面から資料の外の改善候補を探す。
     機能の差だけで追加を選ばず、対象での必要性と便益で採否を決め、便益が無ければ無変更を選ぶ。
   - 論文、ベンチマーク、他プロジェクトの実績を根拠にする案は、提案の前に`agent-basics:review-standards`を起動して評価する。
5. 資料の主張を、既存の規範と既存のAWIに1文ずつ比べる。
   途中報告と方針の予告より前に、この段を終える。
   - 主張の読みを`agent-toolkit:atk-mode/references/omission-check.md`「点検類型」の(l)で先に比べる。
   - 比べる単位は資料の1文であり、要約の単位では比べない。
     主張ごとに、それが実際に働いていることの観測（検査の実物、commitの履歴、記録の件数、効果確認の判定など）を1つ以上取ってから充足と判定する。
     観測を取れない主張は未確認と書き、ユーザーへは調査中と伝える。
     語の所在の検索と本文の読み比べだけで「扱い済み」と報告しない（原則3の失敗例）。
   - 主張ごとに、既存の定義元、被覆、同じ利用条件で同じ結果を得られる根拠、表現・構成の改善余地、改善案の採否と理由を対応表にして作業記録へ残す。
     被覆を最終の採否にせず、書き換え、統合、削除、実装の改善を比べる。
   - 主張ごとの判定と観測は、指摘対応記録の`material_claims`へ書く（URLを含む発話で始めた投入では`atk wi submission end`が欄を検査する。形式は`atk wi submission end --help`）。
6. 考慮漏れを点検し、方針を知らせる。
   方針を決める前に`agent-toolkit:atk-mode/references/omission-check.md`「点検類型」の全類型を点検する。
   方針が決まったら、調査を深めて起草する前に次の4点を短く1回知らせ、返事を待たずに続ける。
   - 改善の中心に置く成果物と理由
   - 継続的な費用（手順、確認、必須の記載）を加える対象
   - 対象から外す成果物と理由
   - 実物を調べた成果物の種類と、調べていない種類

   外部の成果物を参考にする投入では、採らなかった種類の違う構成の案と理由も添える。
7. 本人の判断が残る事項だけを確認する。
   - ユーザーが目的と方向を示した後は、その内側の手段、保護の強さ、範囲の分け方を確認せず、QCDで決めて報告する。
     確認は、取り消せない操作と、ユーザーしか持たない情報（選好、未開示の制約、認可）に限る。
     依頼に無い条件を自分で足して範囲を狭めない（原則1の失敗例）。
   - 確認する時は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従い、特定した課題、依頼どおりの案、種類の違う案、採らなかった構成の案と理由、点検済みの推奨を判断材料として先に示す。
     手順6の知らせは、この判断材料で兼ねてよい。
   - 回答、追加発話、異議は、次の質問の前に本書「指摘の分類と処置」で扱う。
   - 要件や結果を変える未確定の事項が無くなるまで、手順6と7を繰り返す。
8. 質問を終える。
   全類型を点検し直し、`agent-toolkit:atk-mode/references/omission-check.md`「処置と終了時報告」の報告を出して、要求単位ごとの投入先、種別、趣旨、確定した要件をそろえる。
   確認が1件も無かった投入でも、この報告は出す。

## 起草と保存

<!-- markdownlint-disable MD029 -->

9. 起草し、レビューを受けて保存する。
   件数によらず、メインが調査、対策の確定、起草、検収、保存を一貫して担う。
   - 着手の時点で、セッションのmanaged-temp直下に現行の`work-contract.md`が無ければ、`agent-toolkit:atk-mode/references/work-contract.md`「作成と所有」に従って作る。
   - `agent-toolkit:atk-mode/playbooks/wi-drafting.md`に従い、独立した要求へ分けて起草する。
     登録の条件は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「起票目的別の調査出口」である。
     ユーザーの原文は逐語で引用し、出所、確定した要件、技術判断と分けて書く。
   - バグ対応では、原因分析、類似調査、独立した別件の具体化と登録、再発防止の方針の選定を登録の前に終える。
     コードの改善では、適用した規範・参照の経路と実装の構造を対応付け、規範の不足、未適用、誤解を招く条件や例示を`agent-basics:bugfix`で判定する。
     全てを規範の不在に帰さず、同じ条文を重ねない。
   - 変更を使うためにエンドユーザーの操作が要る時は、公開後の設定の実施と専用の案内UWIも反映内容へ含める（`agent-toolkit:atk-mode/references/awi-body.md`「要求固有性と記載量」）。
   - 本来の作業に付随する別件の登録など、文脈を分ける明確な理由がある時だけ`agent-toolkit:atk-mode/roles/add-wi.parent.md`で委譲する。
     基準が明確な大量の走査には読み取りだけの探索を使ってよく、起草と保存の責任はメインが持つ。
   - 原稿を確定する前、登録0件で終える前、候補を不採用にする前に、手順6の点検をやり直す。
     選好を要する不採用は、手順7で回答を得てから確定する。
     未調査で案が無い状態と、根拠の薄い候補を撤回しただけの状態は、原要求の残る検討へ戻る。
   - 原文と反映内容を読み比べ、`agent-toolkit:atk-mode/references/draft-semantic-review.md`で意味を確かめる。
   - 保存する原稿は毎回、`agent-toolkit:atk-mode/roles/wi-draft-review.parent.md`で独立した投入前レビューを受ける。
     同時に準備した原稿、要求、出所、証拠を要求の識別子で結び付けて一括で渡す。
     `要求と出所`には起動したリポジトリを、`成立性の証拠`には対象リポジトリの選定結果（起動したリポジトリの採否と理由、派生して見直したリポジトリ）を含める。
     指摘は本書「指摘の分類と処置」で扱い、採否は起草者が決める。
   - `agent-toolkit:atk-mode/playbooks/wi-saving.md`に従い、`atk wi add --dry-run`の検証、回答済みUWIとの整合の確認、保存、保存の後に保存結果を検収する。
10. 投入を終える。
    - 登録0件なら、手順5の対応表と採否の根拠を自分で検収する。
    - `atk wi submission end --findings-file <指摘対応記録の絶対パス>`を実行し、投入前レビューの返却は登録件数によらず全て`--review-result`で添える。
      検査が不足を示したら記録を補って再実行する。
    - 成功したら、`agent-toolkit:atk-mode/playbooks/report-completion.md`を読んで終了処理まで行う。
      `end`が表示した報告用要約（確認の往復回数、指摘ごとの分類、再発防止策の採否と登録先）は、省略せず作業完了報告へ書く（Claude Codeでは、最終応答に要約の行が無いとStop hookが再報告を求める）。
      同期の振り返りは起動しない。

## 指摘の分類と処置

ユーザーの指摘・追加発話と投入前レビューの指摘は、作業中か完了後かによらず、受けた時点で次の順に扱う。
修正、再評価、再確認へは、分類と処置を終えてから進む。
質問には、今の検討状況と根拠を先に答える（`agent-toolkit:atk-mode/playbooks/user-utterance.md`「問い・提案・疑問形の扱い」）。
停止、変更、撤回を明示した原文がある部分だけを要求の変更として取り込み、質問だけなら今の要求を保って元の工程へ戻る。
過去の判断を問われた時は、元の質問、全ての選択肢、実際の回答を取得して答え、一括の採用を個別に比べて選んだ事実へ言い換えない。
報告や結論への異議は、分類の前に`agent-basics:bugfix`を起動する。

1. 要求単位へ分ける。
   文章の書き方への指示と行動の是正も含めて分け、単位ごとに、既存・起草中のAWIへ合流させるか独立した要求にするかを判定する。
   発話が範囲の一部だけに触れていても、確定済みの範囲を縮めない。
   縮小の明示がある時と意図が曖昧な時は、今の範囲を`共通前提`に示して確認する。
2. 分類する。
   分類名は`atk wi submission end`が検査する値であり、追加要求という扱いで代えない。
   - 考慮漏れ: 原文、取得済みの調査結果、現物、適用中の規範から導けたのに方針へ反映しなかったもの。
     下の4で処置する。
   - ユーザーだけが持つ新しい情報: 選好、未開示の制約など、登録前の調査では導けなかったもの。
     要件として反映する。
   - 前提の誤り: 指摘の技術的な前提が現物と合わないもの。
     根拠と代替案を示す。
   - 採用しない提案: 検討の結果、採用しないと決めた提案。
     根拠を示す。
3. 既存の判断を是正した介入は、分類とは別に`agent-toolkit:atk-mode/playbooks/user-utterance.md`「ユーザー介入と確認の判定」で評価する。
   以後の同種の作業にも当てる方針の候補を含むかは、今回の原稿への反映と分けて判定する。
4. 考慮漏れは、`agent-basics:bugfix`で原因を分析し、同じ仕組みで漏れうる観点を全ての方針で見直してから反映する。
   再発防止策は`## 原因分析`付きの別のAWIとして起草し、対策の対象を所有するリポジトリへ、元のAWIと一緒に登録する。
   投入先が増える時は、本書「手順」の1の`begin`を再実行する。
5. 処置の後に方針を確かめ直す時も、論点ごとに本書「手順」の7の基準を適用し、選好を要する論点だけを確認する。
6. 指摘対応記録（形式は`atk wi submission end --help`）へ残す。
   実ユーザー発話（自由記述を含む確認の回答を含み、示した選択肢をそのまま選んだ回答を除く）と投入前レビューの指摘の1件ごとに項目を作る。
   再発防止策を採用しない時は、`agent-basics:bugfix`が定める区分名と理由を原因分析の`再発防止:`の行へ書く。
   `end`は対応と必須の欄だけを検査するため、考慮漏れか新しい情報かの判断と処置の十分性は、メインと投入前レビューが確かめる。
7. 戻る。
   質問の途中なら本書「手順」の6、原稿の確定・検収の途中なら9の再点検、完了報告の後なら1から再開する。
   独立した要求は9で起草する。

## セッション境界

成果物をWIの登録と更新に限る制限には、`agent-toolkit:atk-mode/playbooks/user-utterance.md`「成果物の制限」を適用する。
起動の後に届く「反映して」「修正して」と、再発防止・完遂の要求は、全てAWIの本文への反映の指示として扱う。
例外として行ってよい操作は、次のものに限る。

- 登録用の一時入力ファイルの作成と、作成した一時ディレクトリの`rm -r -- <作成した絶対パス>`による回収
- 対象リポジトリの規範が同じ工程で求める追跡用ファイルへの記載
- 完成条件や採否を決める値の測定と、そのための可逆な一時変更（本書「測定の手順」）
- 稼働中の巡回への連絡（本書「稼働中の巡回への連絡」）

中止と再開は次のとおり扱う。

- ユーザーが中止するか依頼を取り下げた時は、保存せずに必ず`atk wi submission end --abort`を実行する。
- 完了の後の追加発話で投入を再開する時は、調査の前に本書「手順」の1をやり直し、完了では10、中止では`--abort`で終える。
  再開後の指摘対応記録は、再開を生んだ発話と今回の期間の指摘・確認だけを対象にする。
- 既存AWIの更新と判断した時は、調査の前に本書「手順」の1のとおり保留し、同じ起草者が、現行の本文、確定した変更、原文を対象の`ファイル名`に結び付けて更新する。

対象リポジトリの外への操作の認可と確認の要否は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
委譲する時は、起動する作業の名前、対象リポジトリ内の恒久的な変更をAWIに限る制限、制限の対象外になる判断、セッションの終了条件を依頼文に書く。

## 稼働中の巡回への連絡

登録する要求が、AWI処理の巡回やエージェントの作業の進め方の改善（所要、委譲、待機、起動、点検など）である時に行う。
製品機能の要求など、巡回の進め方に関わらない登録は対象にしない。
ユーザーが対話で起動した振り返りにも同じ手順を適用し、非同期にまとめて行う振り返りと巡回自身は対象にしない。

1. 投入先のリポジトリを処理している巡回の会話が稼働中かを、ホストが提供するセッション間の連絡手段で確かめる。
   宛先は、複数のリポジトリを統括する会話か、対象のリポジトリを直接担当する会話である。
   Claude Codeでは、同じマシンの他のセッションの一覧に巡回の会話が無ければ、稼働していないものとして扱う。
2. 分析で「実装を待たずに今すぐ適用できる改善」が確定した時点で、AWIの保存を待たずに伝える。
   `ファイル名`は保存の後に続けて伝え、伝えた内容に誤りが分かれば訂正を送る。
   ユーザーの指示を待たずに行い、ユーザーが既に伝えたと述べた内容は繰り返さない。
3. 伝える内容は、観測した事実と出所、今すぐ取れる行動を分けて書き、指示や承認の形にしない。
   採否と時機は、受け取った統括が自分の規範で決める。
   統括の起票の予定と重なる時は、重ねて起票しなくてよいことを添える。
4. 巡回のWIの状態変更、担当の停止、設定の変更など、巡回への直接の操作は行わない。
   相手の側で権限の承認待ちになっても、再送や別の経路での強制はしない。
5. 連絡手段が無いか使えない環境では、伝える内容を作業完了報告へ「稼働中の巡回へ未伝達」として示し、ユーザーが中継できるようにする。
6. 作業完了報告へ、伝えた内容の要旨と、伝えられなかった場合はその理由を書く。

## 測定の手順

測定の後に、対象リポジトリの作業ツリーを測定前の状態へ必ず戻す。

1. 環境変数、コマンドライン引数、別名の一時設定ファイルなど、Gitの追跡対象を変えない手段を優先する。
2. 追跡対象を一時的に変える時は、測定の前に`git status --porcelain=v1`の出力と変更するファイルの内容を退避する。
   変更するファイルか、測定で書き換わりうるパスに既存の差分がある時は、`git worktree add --detach`で作った検証用worktreeの中で測定する。
3. 元の作業ツリーで測定した時は、変えたファイルを退避した内容で戻す。
   `git -c submodule.recurse=false checkout`と`git clean`は、測定前に差分が無かったパスだけに実行し、初期化済みのサブモジュールのHEAD、ブランチ、作業内容を保つ。
4. 測定後の`git status`が退避した測定前の状態と合わない時は、後続へ進まず、差分の内容と退避先のパスをユーザーへ報告する。

## 完成条件

- 登録の時点の調査で分かる、要件や結果を左右する本人固有の事項に回答を得ている。
  処理の時に初めて分かる事項だけが、残す理由とともに本文にある。
- 登録した全てのAWIが`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「起票目的別の調査出口」を満たす。
- 質問を終える時の報告に全類型の点検結果と処置があり、原稿確定前の再点検、意味の確認、dry-run検証、投入前レビューの合格、保存結果の検収を終えている。
- 登録0件で終える時は、資料の主張ごとの対応表と分類が作業記録にあり、選好を要する不採用に回答を得ている。
- `atk wi submission end --findings-file`の検査が成功し、表示された報告用要約を作業完了報告へ書いている。
- 対象リポジトリの実装ファイルと`processing`のAWIが、起動前の状態のままである。

## 返す報告に含める項目

登録・再利用したAWIの`ファイル名`、報告用要約の全行、扱った資料の目的と自ら確定した判断（`### 自ら確定した判断`）、検収の結果、未達の事項、稼働中の巡回へ伝えた内容の要旨か伝えられなかった理由を返す。
