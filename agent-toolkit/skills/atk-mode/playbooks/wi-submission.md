# 独立したWI投入

確定した要求を、投入元が終了した後も独立したセッションが意味確認、保存、報告まで完遂するための手順書である。
投入元は本書「入力と受付票」に従い、要求を`atk wi submit --request-file <JSONの絶対パス>`へ渡す。
`atk wi submit`が起動した投入セッションは、本書「投入セッション契約」の手順を上から実行する。
起草は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`、保存と検収は`agent-toolkit:atk-mode/playbooks/wi-saving.md`に従う。

方針は次のとおりである。
受付票は、入力の永続化と独立した監督への所有の移管を示し、投入の完了は示さない。
投入済みかの判断には、要求ごとの結果と報告の同期を使う。
成否が分からない受付の要求を、新しい実行として無条件に再送しない（再開の操作は本書「失敗・再開・保持」）。

## 入力と受付票

入力はUTF-8のJSONで、要求のobject1件か、同じ対象の要求objectを並べた空でない配列とする。
同時に確定した同じ対象の要求は1つの配列で渡し、各要求の識別子、原文、処置を保つ。
配列の`request_id`は一意に、`target_repo`は同じ値にする。
CLIは全件の入力を検証してから同じロックの中で保存するので、監督は新しい要求の集合を一度に取得できる。
応答は、object入力にはobjectを、配列入力には要求ごとの同じ形式のobjectを入力の順に並べた配列を返す。
既存のIDの再送は元の受付へ対応付く。
過去に別々に受け付けた要求を、再実行してまとめ直さない。
各要求objectには次の項目を全て含め、文字列は空白以外の文字を含む値にする。

| 項目 | 形式・意味 |
| --- | --- |
| `request_id` | 英数字で始まる英数字・`_`・`-`の128文字以内のID |
| `target_repo` | 正規化したリポジトリURL（`github.com/example/repository`の形式） |
| `source` | 投入元の識別子。登録時もこの由来を維持する |
| `origin` | `kind`が`human`または`agent`、`text`が逐語原文であるobject |
| `requirements` | 確定要件の非空文字列配列。1件以上 |
| `observations` | 観測した事象の文字列配列。観測なしは空配列 |
| `evidence` | 証拠本文を含む文字列配列。1件以上 |
| `update_targets` | 更新対象と保留の扱いを明記した文字列配列。新規だけの場合もその旨を1件以上記す |

原文と証拠の本文は入力へ直接含める。
投入元の一時ファイルや撤去するworktreeの所在は、入力に含めた原文と証拠への補足としてだけ使う。
受付は投入ごとの配布物を保持してから監督へ移すので、投入元は受付の後に自分のworktreeを回収してよい。
保持に失敗した受付は成立しない。
同じIDの同じ入力は同じ受付に対応し、違う入力は拒否される。
同じかどうかはJSONを解析した後の全項目の値で比べ、objectのキーの順とJSONの空白は比べない。

公開の応答の`ticket`は、`request_id`、`target_repo`、`accepted_at`、`owner`（監督の`pid`と`create_time`によるPID世代）を持つ。
投入元の待機集合（完了を待つ要求の集合）から外す主体は、同じホストで`atk wi submit --show <request_id>`を実行する。
終了コード0、`ticket_verified: true`、応答の`ticket`と受領済みの票の一致を確かめた受付だけを外す。
配列入力では各応答の票を確かめ、全件の所有の移管が成立した場合に限り全件を外す。
終了コードが0以外、票が無い、一致しない場合は待機の対象に残し、保存された失敗と次の操作を確かめる。
所有の移管の記録は、監督が正常に終わった後も有効である。
`--show`は、票、保存した入力、処置、ログを持つ実行ディレクトリと、未報告の所在を返す。

## 投入セッション契約

1. 開始する。
   `atk run-skill`の起動入力が示す独立WI受付の`run.json`を読み、`requests`の全件を対象にする。
   この入力は確定した契約の引き継ぎであり、手動入力向けの協調モードを自律モードへ読み替える。
   対象リポジトリのコードを恒久的に変える権限は持たない。
2. WI投入担当へ渡す。
   `agent-toolkit:atk-mode/roles/add-wi.parent.md`を全文読み、その起動・入力・受領の契約に従って`add-wi`担当へ`投入経路: 専念型`で渡す。
   同時に受け付けた同じ対象の要求は、1回の実行へまとめてよい。
   要求ファイルには、各`request_id`、対象リポジトリと種別、原文と由来、確定要件、技術判断、観測と証拠、更新対象と保留の扱いを分けて書く。
   エージェントが確定した事項は`委譲元の判断`へ、人間が明示・承認した要件は`確定した要件`へ対応付ける。
   `source`は受付の値を保つ。
   `origin`の由来と逐語の原文、確定要件、証拠も受付のまま保ち、既存WIとの意味の重複を確かめさせる。
3. 結果を検収する。
   専念型の担当が独立した投入前レビューと保存まで行い、この実行は全ての要求の結果、保存、保留の解除を検収する（`agent-toolkit:atk-mode/playbooks/wi-saving.md`「保存結果の検収」）。
   各WIの保存・更新と同じ操作で、frontmatterの`wi_submit_bindings`へ`run_id`をキー、対応する`request_id`の配列を値として書く。
   既存WIが持つ他の実行の対応は残す。
   要求全体の完了は、対応するWIの本文が要件を全て満たすことで判断する。
   ユーザー固有の判断が足りない要求は確認UWIを保存し、未完了として保持する。
4. 保存の応答が不明な要求を片付ける。
   保存の後、finishの前に中断しても、`atk wi submit --show <request_id>`の`saved_wi_bindings`から要求に対応する正式なWIを取得できる。
   保存の応答が不明な要求は、この対応と`atk wi show <ファイル名>`の現行本文を取得し、必要な同期を終えてからfinishへ進む。
   `saved_wi_bindings`が元の`requirements`と`update_targets`を満たす範囲を確かめ、保存済みのWIを再利用して残る処置を進める。
5. 結果を保存する。
   次の構造のJSONを作り、`atk wi submit --finish <結果ファイルの絶対パス>`で保存する。
   `run_id`には起動入力と同じ実行IDを、`results`には受付の全ての`request_id`を1回ずつ含める。

   ```json
   {
     "run_id": "0123456789abcdef0123456789abcdef",
     "results": [
       {
         "request_id": "request-1",
         "status": "registered",
         "files": ["20261106-120000-001.md"],
         "reason": "確定要件を新規AWIとして保存した"
       }
     ]
   }
   ```

   `status`は`registered`（登録）、`reused`（既存WIの再利用）、`unnecessary`（不要）、`incomplete`（未完了）のどれかとし、`reason`に判断の根拠を書く。
   `registered`と`reused`の`files`には、同じ対象リポジトリに実在する正式なWIのファイル名を1件以上書く。
   `unnecessary`の`files`は空配列でよい。
   `incomplete`では保存した確認UWIを書き、技術的に保存できない場合は空配列と理由を残す。
   完了した処置は保たれ、同じ実行の再開では未完了の処置だけを更新できる。
6. 報告を同期する。
   finishの保存後、同じ`run_id`の作業完了報告を`agent-toolkit:report-completion`で1件だけ同期する。
   未完了を含む場合も、今回の処置結果と、残る確認UWIと解除の条件を同じ報告へ書く。
   報告は`source: run-skill`、`scope`（`atk run-skill`がこのセッションで起動したスキルの名前）、`run_skill_report: true`、自動で取得される`run_skill_run_id`で識別される。
   再開した時は`--show`の`report_files`で既存の報告を取得し、`atk wi edit`で同じ報告を更新する。
   保存の応答を失った場合も、`report_files`が示す既存の報告の同期を再開し、報告を新たに登録し直さない。
   監督が正式なWIの実在、全要求の処置、報告の同期を確かめた時点で完了となる。

## 失敗・再開・保持

監督は、起動前の失敗、子の異常終了、時間切れ、finishの欠落、報告の未同期を検出する。
排他の競合は未実行として最大1時間待ち、解放の後に同じ監督が実行する。
可用性の判定を含む子の実行全体の時間上限は6時間である。
監督が消えたかは、保存したPID世代をSessionStart・SessionEndと照会の時に観測し直して判定する。
監督は起動した子の終了を確かめ、同じ`run_id`の保存済みWIと結果を先に照会してから、失敗報告用のUWIを1実行1件で同期する。
同期できない場合と時間上限に達した場合は未報告として保存し、次の契機で同じ実行の照会と同期だけを再開する。

成否が分からない要求は、次の順に再開する。

1. 失敗報告のUWIを受け取った担当は、`atk wi submit --show <request_id>`で状態を照会する。
2. モデルの起動前でセッション記録が無い場合は、`atk wi submit --resume <request_id>`で同じ受付と`run_id`を監督へ移し直す。
   元の会話がある場合も同じ操作を使い、監督が既存の`atk run-skill --resume <RUN_ID>`へつなぐ。
3. 確認UWIが未回答の要求は、回答と解除の条件がそろってから再開する。
4. 元の会話か残り時間が足りない場合は、報告UWIの担当が、未完了の要求、保存済みのWI、必要な判断を確認UWIへ引き継ぐ。
   その回答を得た担当が、元の受付とWIの対応を保って後続の処理を起動する。

未完了と未報告の受付は保持する。
完了して報告を同期した受付と実行ログは、最終更新から30日後の再観測で回収される。

## 返す報告に含める項目

要求ごとの`status`と`files`、finishと報告の同期の結果、残る確認UWIとその解除の条件を返す。
