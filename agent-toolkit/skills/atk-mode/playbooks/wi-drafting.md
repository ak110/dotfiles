# WIの起草

後続の`process-wi`の担当とユーザーが、本文から目的、対象、結果を判断できるよう、`agent-basics:writing-standards/references/writing.md`で起草を始める。
要約で埋めず、発話・資料・コードと実行結果から決まることを投入前に本文で確定し、ユーザーだけが決めることを確認する（原則1・3）。

本書は、通常AWIと報告用を除くUWIを起草する者（`/atk-mode add-awi-by-user`や独立したWI投入のセッションのメイン、WI投入担当、他の作業中にUWIを書く者）が上から実行する。
報告用UWIは`agent-toolkit:atk-mode/references/report-formats.md`「報告用UWIの確認と保存」に従い、`--question-type=report`で保存する。

## 手順

1. 「対象の調査基点」を確定してから、投入条件と起票目的に応じた調査結果を「投入条件の判定」「起票目的別の調査出口」に従って決める。
2. 原文と現物から前提と観測を確かめる（本書「前提と観測の確認」）。
3. 全状態の既存WIを検索し、重複と、未処理のWIへの統合を比べる（本書「重複判定」「AWIの粒度と統合」）。
4. 要件、委譲元の判断、未確定事項を分け、残るユーザー判断を確認へ回す（本書「確定した要件と委譲元の判断」「未確定事項と確認」）。
5. 原因と変更する定義の所有者、対象集合の採否、実現方式を決め、1つの案にする（`agent-toolkit:atk-mode/references/drafting-decisions.md`）。
6. 本文を起草する（本書「本文の起草」）。
7. 確定を判定し、検収の構成を選ぶ（本書「確定の判定」「直接起草と独立した検収の選択」）。
8. `agent-toolkit:atk-mode/playbooks/wi-saving.md`の手順で保存する。

## 起票目的別の調査出口

起票の目的は、`source`の文字列ではなく、元の要求と起票の目的から決める。

| 起票の目的 | 登録前に満たす条件 | 後続工程へ渡す内容 |
| --- | --- | --- |
| 全ての起点に共通 | 要求か観測事実、期待との差、対象と期待結果、対応が必要な根拠を確かめ、既存の実装・文書・WIとの被覆を比べる（本書「重複判定」）。規範・手順の被覆は`agent-basics:writing-standards/references/agent-documents-basics.md`「既存規範による被覆の判定」で判定する | 確かめた結論と再取得できる根拠 |
| ユーザーが手動作成で具体化を求めた要求 | 対象ごとの採否、外部から観測できる仕様、必要なユーザー判断を投入元で確定し、投入前レビューを経る | 確定した変更の内部設計、実装単位、実装後の検証 |
| 作業の途中で見つけた、現在の要求から独立した別件 | 共通の条件を満たし、確定した事実、原因の仮説、未確定事項を分ける | 原因の解明と解法の選定の残り、次に確定する問いと期待結果 |
| 完了の工程の後に見つけた独立した問題（軽い引き継ぎ） | 本節の軽い引き継ぎの条件を満たす | 原因分析、類似の見直し、対策の選定、実装と検証 |

全ての起点で、投入先の決定前に原因の所有と回復費用を確かめる。
追跡される定義に原因があり、文書どおりの準備でも起きる事象は、その定義を持つリポジトリが扱う。
追跡外の状態が原因で通常の準備をやり直せば回復する事象は、そのプロジェクトへ投入しない。
配布側の定義に原因があるなら、確認できた配布元へ対応付ける。

手動作成では、今回必要な対象別の検討を、処理時点の仕分けや後続の調査を理由に後へ回すことは避け、付随する独立した別件と、元の要求の一部を分けた別件にも共通の条件を適用し、振り返りなどで確定済みの原因と対策は保つ。

軽い引き継ぎは、元作業の実装、検証、必要な公開と公開後の操作が完了し、完了報告・終了処理の段階以降に初めて分かった独立した問題に使える。
問題を観測したメインが通常AWIとして直接起草・保存し、原因の確定、対策の選定、広い類似調査、別の起票担当、独立した投入前レビューは登録の条件から外す。
本文には、観測した事実と期待との差、発生条件と影響、対象、再取得できる証拠（原記録、診断、実行の識別子）、実施済みの処置、未確定の事項と次に調べる問いを判明した範囲で短く書き、原因の候補は仮説と明記する。
保存の前に、メイン自身が適用条件、意味、必要な情報と証拠の保存を確かめ、`agent-toolkit:atk-mode/playbooks/wi-saving.md`の保存前の検査を経て、保存の成功を検収する。
元作業の未達、今回の変更の不良、未回収の実行、進行中の被害への応急処置と証拠の保全は軽い引き継ぎにせずその場で対処し、条件を満たさない問題は即時対応か通常の起票へ戻す。
工程が進んだことを理由に、既知の未完了事項を新しく見つけた独立の問題へ分類し直さない。
後続の`process-wi`は原因分析から実装と検証までを担い、調査の未完了だけを起票の不備とはせず、確定済みの事実・処置・ユーザー判断を再利用し、引き継ぎの保存、元作業の完了、問題自体の解消を分けて報告する。

### 対象の調査基点

現物を根拠にする新規AWIは、採否を左右する最初の読み取りより前に宛先を選ぶ。
登録済み系統では `origin/<系統>` を取得し、未登録では宛先worktreeの上流を取得する。
未登録で上流が未設定なら宛先のローカルブランチを使い、必要な参照を取得できなければ止める。
共有作業ツリーを動かさず固定版を読み、宛先worktree、宛先のブランチ、一意な短縮OIDを渡す。
各操作の直前に短縮OIDを解決し、隔離worktree、dry-runと保存の `--draft-base BRANCH OID` に完全OIDを使う。
`BRANCH`は宛先の`refs/heads/<ブランチ>`か、宛先に実在し、`/`を含まないブランチ名で指定する。
取得に使う`origin/<系統>`は渡さない。

## 重複判定

新しい通常AWIを起草する前に、要求の名称と主題（外部資料が起点なら資料と実装の名前も）で全状態の既存WIを検索し、本文を読んで比べる。
起点がユーザーの持ち込んだ新しい主題でも、類似の見直しで見つけた独立の別件でも同じく検索し、既存AWIの更新の依頼では指定された項目を取得して比べる。
ユーザー自身が要求単位を書いた原稿の整形投入、UWI、移行と復元の作業は対象外とし、回答済みUWIとの整合確認は種別によらず`agent-toolkit:atk-mode/playbooks/wi-saving.md`「保存前の確認」の手順2で行う。

```sh
atk wi grep --summary-only --state=all --target-repo=<対象リポジトリの絶対パス> --skip-pull -F -- '<語>'
```

正規表現で探す時だけ`-F`を外して`'<Pythonの正規表現>'`を渡し、終了コード1は一致が0件の正常な結果として検索の失敗と区別する。
語の一致は候補を減らすことにだけ使い、本文を`atk wi show`で読んで被覆を判断する（複数件は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「複数件の`atk wi show`の取得」）。
比べる観点は、対象、期待される結果、観測事象、破られた不変条件、根本原因の仕組み、必要な処置である。
ファイル名・hook名・コマンド名の違いだけでは別件とせず、同じ根本原因でも直接の原因と必要な処置が独立するものは本書「AWIの粒度と統合」の基準で分ける。
採用済みと終了済みの項目は適用条件、修正内容、実際に使われている版と配布の状況も比べ、単語の一致や採用済みという状態だけでは解消済みとしない。
未配布の旧版で同じ事象が起きた場合は既存の成果の再利用と更新後の確認へつなぎ、修正後も同じ条件で再発する場合と処置が覆われていない場合は是正の要求を残す。
既存項目が要求の全てを覆う場合は再利用し、一部を覆う場合は覆われていない部分だけを起草するか既存項目を更新し、比べた結果を投入時の報告に書く。
別環境への移送などで元の項目を削除し、削除前の履歴を取得できる運用では、候補の番号が分からなくても、現行キューに加えて同じ宛先の削除前の本文を探し、宛先での反映状況と照合する。
削除そのものは移送・採否・完了の証拠にしない。
同じ事象への既存要求が未反映か反映を確認できなければ重複投入せず、新たに観測した未被覆の範囲だけを起草する。
宛先の公開成果で反映済みと確認できた場合は再発かを比べる。
担当の返却は`agent-toolkit:atk-mode/roles/add-wi.parent.md`「WI投入担当の返却契約」の`既存項目の扱い`と`reused`を使う。
検索の条件と比べた項目は証拠に残し、`atk wi add`の直前に同じ条件で`--skip-pull`を付けずに検索し直す（既知の項目とだけ比べた場合は、その項目の状態を確かめる）。
削除前の履歴を照合する運用では、保存直前も同じ範囲の履歴と宛先の反映状況を照合する。
一部の被覆、要求どうしの衝突、覆っていた項目の終了など結果が変わったら、保存を止めて本文の修正と意味の確認へ戻る（付随型の担当は変化と必要な修正を`続行できない理由`で返す）。

## AWIの粒度と統合

AWIの粒度は要求の同一性で決め、同じユーザー目的・成果へ向けた小さな変更は1件へまとめる（技術上の話題、手段、編集箇所の違いだけで分けると、調査・計画・検証・レビューとレーン起動の費用が件数分繰り返される）。
別のAWIにするのは、別の目的を持ち、単独で採否・実装・完成判定が成り立つ要求であり、既存・起草中のAWIの目的、対象、完成条件の具体化や変更はそのAWIの更新として扱う。
元の不具合の解消に必要な追随修正は元のAWIへ含め、類似の見直しで見つけた独立の別件は根本原因を共有していても別のAWIにし、元の事象への寄与が分かった対象は元の修正範囲へ戻す。
1件のAWIは1つの成果を扱う。
既存AWIの範囲を見直す場合も、原文、確認回答、起票根拠の観測から求められた成果を特定する。
既存AWIで満たす成果は対応先を示し、独立した未被覆の成果は別のAWIへ分け、根拠のない追加事項だけを除く。
統括は書き直しの指示にこの区分を適用し、意味検収では各成果に対応先があり、原文で求められた内容を保つかを保存前に確かめる。
1件のAWIの中のバグの単位は、`agent-toolkit:atk-mode/references/analysis-records.md`「バグ単位の分け方」に従う。
投入先のリポジトリが分かれる場合は、`agent-toolkit:atk-mode/references/cross-repository-submission.md`「独立したAWIへの分割と依存」に従う。
独立した要求は、先行の成果が必須でなければどちらの順で処理しても完了できる本文にする。

新しい要求を起草する前に、未処理（`inbox`・`hold`）の既存WIへ統合する案を、新しいAWIを作る案と並べて比べる。
比べる相手は、目的が同じWI、同じ文書・同じファイルを変えるWI、その要求が直す文書を作り替えの対象に含むWIである。
統合する前に、更新前の有効な要求と採用する追加要求を原文で比べ、主体・行為・適用条件・結果を保つ部分と、明示の指示や認可で変える部分を分ける。
定義元と起動条件を現物で確かめ、この比較と理由を既存の成立性の証拠へ残す。
統合する場合は、その比較に沿って既存WIの本文を変更する対象（ファイル、手順書）と目的で組み直し、同じファイルへの変更を1か所にまとめ、節の機械的な連結は避ける。
独立して採否と完成判定が成り立つ要求を1件に混ぜて巨大にすることは避け、統合しない場合はその理由を方針の提示と報告に書く。
既存WIを更新する順序（調査の前に保留にする、`processing`の項目は本文を置き換えずに追記し、変更の要求は新しいAWIにする）は、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「保留と本文修正」に従う。
