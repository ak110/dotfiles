# 公開工程

目的: 公開の担当が認可された範囲だけを外部へ出し、CIと公開状態まで確かめて、ユーザーが変更を実際に使える状態で受け取れるようにする。
公開工程はcommitの作成からバージョンの更新、push、CIの確認、公開状態の確認、プロジェクト固有の公開後の操作までの一連の処理を指し、本書を定義元とする。
本書を上から実行すると公開が終わる。

方針は次のとおりである。
pushと公開後の操作は取り消しの難しい外部への作用である（原則4、`agent-basics:writing-standards/references/quality-principles-constraints.md`）。
起動の形態によらず、ユーザーの指示、確認への回答、自律モードのスキルの定めから、認可された範囲と対象を確定してから行う。
CIの通過と公開の成功は、終了状態を決める主体の出力で確かめ、監視の終了と公開の成功を区別する（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。

## 公開範囲

協調モードの公開範囲の選択肢は`agent-toolkit:atk-mode/references/publish-scope.md`「公開範囲の確認」が定める。
各範囲で実施する工程は次のとおりである。

| 範囲 | 実施する工程 |
| --- | --- |
| commitしない | 実装、変更箇所の検証、必要な自動生成ファイルの同期を終え、commitの手前で止める |
| commitまで | 必要なバージョンの更新、自動生成ファイルの同期、検証を行い、commitまで進める |
| push・CIまで | commitまでの工程に続けて、push、CIの通過の確認、公開状態の確認まで終える |
| 既存の判断基準どおり | push・CIまでの工程に続けて、プロジェクト規範によるリリース判定と、認可済みのプロジェクト固有の公開後の操作まで行う |

PRの作成、リリースの作成、タグ付けを依頼が明示した場合は、本書「プロジェクト固有の公開後の操作とリリース」の操作として扱う。
`agent-toolkit:atk-mode`の作業`process-wi`（`single-lane`を含む）では、同作業の手順書が定める自律モードの公開範囲を適用する。

## バージョンと生成物

1. バージョンの更新が必要な場合は、公開単位の未pushの差分全体を対象に、配布物ごとにプロジェクトの採番方針が定める最上位の種別を決める。
   各レーンから受け取った種別と根拠を照合し、起草後に加わった上位の変更も含める。
   方針がなければ、`agent-basics:writing-standards/references/versioning.md`に従い、過去のリリースの慣行に合わせる。
   バージョンの更新、派生マニフェストの同期、自動生成ファイルの同期の確認、commitを続けて行う。
   同期は各ジェネレーターが定める対象ファイル群と終了コードで判定する。
   commitは`agent-toolkit:atk-mode/playbooks/commit.md`で作る。
2. バージョンを決める時は、次の指定と認可を守る。
   - ユーザーが明示した区分（MAJOR、MINOR、PATCH）を最優先にする。
   - MAJORは、ユーザーの明示の指示がある時だけ上げる。
   - `major.minor.patch`の3つの数で表せないバージョンは、プロジェクトの対応表かユーザーの明示の指示に従う。
     手がかりが無ければバージョンを変えず、判定できない根拠を報告する。
3. `agent-toolkit:atk-mode`の作業`process-wi`の完了担当は、未pushの追加差分と公開済みのバージョンを比べて更新し、公開済みの成果を重複して数えない。
   追加差分の無い再検収ではバージョンの更新とpushを省き、同じ公開先とcommitのCIを検収済みなら待機も省く。
   CIが未判定なら本書「公開工程の続行不能からの再開」へ進む。

## 検証とCI

1. 検証範囲と成功の再利用は`agent-basics:check-execution/references/verification-scope.md`に従う。
   公開候補を送る直前のバージョンと、最初の取り込み前の基点で対象を選び直す。
2. CIが実行しないチェックの範囲はプロジェクト規範に従い、明文が無ければCIの実行設定、有効なチェック、参照設定、実行環境を比べて特定する。
   範囲が不明な場合とCI定義が無い場合（`agent-toolkit:atk-mode/references/ci.md`「公開先に対応するCI定義の判定」）は、タスクランナーの全体検証をpush前に1回実行する。
   「ローカル全体検証成功」と「CI未判定」は区別して保持する。
   CI固有のOS、言語のバージョン、実機など、手元で再現できない条件へ変更が及ぶ場合は、CIの完了まで待つ。
3. push前のチェックの前に、ロックファイルの変更の有無によらず、対象リポジトリの開発手順が定める環境の同期を毎回実行し、仮想環境をロックファイルの依存とCIのPythonのバージョンへ一致させる。
   `uv run`の自動同期は不要なパッケージを環境に残しうるため、同期の手段に使わない。
   `.python-version`が無いプロジェクトと、`UV_PYTHON`などでバージョンを指定した環境では、既存の仮想環境のPythonのバージョンも保つ。
4. push前のチェックと全体検証は出力が多いため、標準出力と標準エラーをmanaged-tempへ保存する分離実行（`agents_server`の`start`の`shell`など）で行う。
   公開担当は、保存した出力の実在、内容、終了コード0を検収する。
5. チェックの失敗と、設定の未適用や処理の未完了を示す警告は、続けられない原因として`agent-basics:bugfix`で扱い、認可の範囲内で直す。
   `agent-toolkit:atk-mode`の作業`process-wi`の完了担当のCI修正は、`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「検証またはCIの失敗」に従う。

## pushと公開状態

ベースブランチへpushする差分がある時だけpushする。
差分が無い時は、現在のHEADのCIの結果を1回確かめて確定し、本書「公開状態の4項目」へ進む。

### push前

常駐の公開では、バージョン・生成物を通常のレーンで検証・統合した後、その時点のベースブランチを通常どおりpushする。
公開担当は主作業ツリーを変更せず、pushしたcommitのCIをバックグラウンドで確認する。
公開中も選定・レーンの作成・直列統合を続け、push後の統合・CI修正は次のpushに入れる。

1. 候補branch、作業branch、履歴を書き換えるpushを含む全てのpushの前に、`agent-toolkit:atk-mode/playbooks/commit.md`と本書を読み、適用してからpushする。
   候補branchのpushを公開工程と別の軽い操作と扱い、手順を読む前にpushした誤りがある。
   読み込みの警告はpushを止めないため、この順序を自分で守る。
   適用したことを、`atk run-script plan-progress -- <記録先> --handoff --completed-step push前 --result <宛先とcommit>`で引き継ぎ記録へ1行で残す。
   どちらも無い作業では、作業完了の報告に含める。
2. pushの認可（計画に記録された元の要求、確認への回答、委譲の依頼文、ユーザーの直接の指示）が、対象のリポジトリとブランチを含むことを確かめる。
   amendかfixupの直後は、作業ツリーに未commitの差分が無いことも確かめる。
3. `git fetch`の後、上流との差分を双方向で確かめる。
   常駐の公開で上流の取り込みが必要なら通常のレーンで統合し、影響を受けた検証を確かめてからpushする。
   それ以外で上流が進んでいれば取り込み、本書「検証とCI」の手順1で検証を選び直して影響を受けた検証だけ取り直す。
4. pushの方法をdry-runで確定する。
   `git remote -v`、現在のブランチ、追跡ブランチ、`push.default`、承認済みの宛先から、引数なしのpushの到達先を判定する。
   - 承認済みの宛先へ確実に届く時は、引数なしの`git push --dry-run --porcelain`を使う。
   - 到達先が確実でない時は、`<remote> <source>:refs/heads/<destination>`を明示したdry-runを使う。
     引数なしのpushが設定上必ず失敗すると分かっている時は、引数なしのdry-runを省いてよい。
   - `<source>`へ渡す値は解決したコマンドの終了コード、空でないこと、形式を確かめてから使う。
     送信元が空のrefspecは、リモート参照の削除になる。
   - dry-runが成功し、出力の全てのstatus lineが承認済みのremoteと宛先へのrefspecを示す時だけ、その方法でpushする。
     拒否か失敗が予定されるref、未承認のremoteか宛先を含む時は、pushを中止する。
5. CIの通過を判定するかを決める。
   CI定義の有無は`agent-toolkit:atk-mode/references/ci.md`「公開先に対応するCI定義の判定」で確定する。
   委譲元が「本セッション内ではCI通過を判定しない」と明示した場合と、CI定義が無いと確定した場合は、baselineと監視を省く。
   判定する場合は、同書「baselineの作成」でpush前にbaselineを作る。

### pushと監視

1. 引数なしの方式では`git push`を単独で実行し、引数を明示する方式では、成功したdry-runのコマンドラインから`--dry-run --porcelain`を除いた同じ引数でpushする。
2. 作業refの先行CI（`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「修正系列」）の結果は、検証したSHA、ref、ジョブの範囲だけに適用し、正式公開のrefのcheck集合は別に検収する。
3. push後は、`agent-toolkit:atk-mode/references/ci.md`「CIの待機」でCIを待ち、CI定義なしとCI実行対象外は同書「公開先に対応するCI定義の判定」で受理する。
   常駐では監視中も選定・レーン・統合を続け、失敗を見たら通常の修正レーンへ渡して次のpushに入れる。
   失敗は同書「選択の流れ」で扱う。
4. CIを照会できない時は、完了したpushと公開状態を保ち、本書「公開工程の続行不能からの再開」へ進む。

### 公開状態の4項目

push・CIの確認の後に、ベースブランチへの変更が公開されたことを次の4項目で確かめる。
判定する時点の現在のGit状態から値を取得し、4項目の全てを満たす時だけ「公開済み」とする。
常駐の公開では、宛先branchの認可、pushしたcommitの検証済みのtree、公開先refとそのcommitの一致、そのcommitの統合完了の証拠の4項目を検収する。
後続の統合によるローカルのaheadや一時的な作業状態は、push済みのcommitを未公開へ戻す理由にしない。
以下の現在の作業ツリーを使う4項目は手動の単回実行へ適用する。
値は各項目のコマンドで取得し、`.git`の内部を直接探さず、複数のrefを1回の`git rev-parse --short`へ渡さない。

1. `git -C <対象リポジトリの絶対パス> status --porcelain=v2 --branch`の出力の`# branch.head`が、ベースブランチ名と一致する。
2. 同じ出力で、`#`で始まらない行が0件である（作業ツリーが完全にクリーン）。
3. 同じ出力の`# branch.ab`のaheadが`+0`である（リモート追跡ブランチが無く値を取れない場合は不成立）。
4. `git -C <対象リポジトリの絶対パス> status`の出力に、rebase、merge、cherry-pickなどの進行中の表示が無い。

未達の項目は所定の手順で解消し、自力で解消できなければ項目名を報告する。

### 後始末

1. 監視の終了と公開の成功を区別して後続へ渡す。
   終了状態は、CI成功、CI定義なし、CI実行対象外、CI判定の委譲、バグ対応完了、push失敗、監視不能、run未登録、forge CLI失敗、中断のどれかである。
2. `agent-toolkit:atk-mode`の作業`process-wi`の完了担当は、検収できた`CI成功`と`CI定義なし`、ローカル全体検証の成功と非生成の証拠を確かめた`CI実行対象外`を、完了報告の`CIの結果`として返す。
   それ以外は既存の`続行できない理由:`に理由を書き、CIの照会不能か公開後の操作の前提不足に当たる場合は、本書「公開工程の続行不能の受渡し」の記録も含める。

## プロジェクト固有の公開後の操作とリリース

1. 認可されたPR・MRの作成、リリースの作成、タグ付け、パッケージの配布などを依存の順に実行する。
   CIの成功を前提とする操作（リリースやデプロイのワークフローの起動を含む）は、対象commitのCIの通過を確かめてから実行する。
   他の担当へ分担済みの工程は、その担当に任せる。
2. PR・MR・Releaseの本文は、差分を持つ読み手が1分で読める要約にし、検証の詳細はログを貼らずに記録の所在で示す。
   変更説明の組み立ては`agent-basics:writing-standards/references/writing-genres.md`「判断と行動を求める記述」に従う。
3. `atk config repos list`の`merge_from`に取り込む側として登録した系統（継続して作業が入るoriginのブランチ）では、リリースの操作（タグ付け、リリースの作成、リリース用ブランチへのマージ、配布）の前に、取り込み元の系統に未取り込みのcommitが無いことを次で確かめる。

   ```sh
   git -C <対象リポジトリの絶対パス> fetch origin
   git -C <対象リポジトリの絶対パス> log --oneline origin/<取り込む側>..origin/<取り込み元>
   ```

   出力が1行以上なら未取り込みがあり、取り込み元をマージして、競合の解消、検証、取り込む側の系統のCIの成功を確かめてからリリースへ進む。
   競合でどちらの系統の挙動を残すかが要求と現物から決まらない場合は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
4. マージの要求が受け付けられたことと、マージされたことを分けて確かめる。
   自動マージの予約とマージキューへの投入はマージではない。
   PR・MRを読み直して状態がマージ済みで宛先が意図したベースであることを確かめ、宛先を取得してマージcommitが履歴にあることを確かめる。
5. 公開範囲が「既存の判断基準どおり」の協調モードと、公開工程まで自動で進める自律モードでは、CIの成功の後にプロジェクト規範のリリース判定を起動する。
   リリースの認可とバージョンの種類は、プロジェクト規範と本書「バージョンと生成物」で決める。
6. 公開後の操作で変更が必要なら、常駐では通常のレーンで新しいcommitとして検証・統合し、次の公開単位のCIと公開状態を確かめる。
   手動の単回実行は新しいcommitを再pushしてCIと公開状態を確かめる。
7. 公開後の操作やリリース判定の前提が不足する場合は、本書「公開工程の続行不能からの再開」に従う。

## 公開工程の続行不能の受渡し

CI定義の判定、baselineの作成、push後の監視、公開後の操作が前提の不足で完了できない場合は、同じ対象について完了済みの工程と残りの工程を分け、次を記録して後続へ渡す。

- 対象: forge、リポジトリ、commit、ref
- 失敗: 失敗した操作とその対象（リリース名、タグ名、配布先など）、診断、不足している前提条件
- 完了済みの工程: pushの成否（pushの手前で止めたら「push未実行」、push後なら「確認済みpush」）、正常に終わった公開後の操作、本書「公開状態の4項目」の観測、ローカル全体検証の成否、バージョン、生成物、延期したadoptの進み具合
- CIの結果（未判定ならその旨）
- 所在: baselineと保存した出力の絶対パス、引き継ぎ記録の絶対パス
- 再開する工程

「公開状態の4項目」の成立やローカル全体検証の成功だけで、CI成功と判断しない。
回復と確認は本書「公開工程の続行不能からの再開」で行う。

## 公開工程の続行不能からの再開

本節はCIを照会できない場合（CI定義の判定、baselineの作成、CIの監視に必要な前提の不足）と、push後の公開後の操作が認証、ネットワークの到達、対象の指定、権限の不足で続けられない場合に適用する。

1. 既存の設定と認可の範囲で解消できる場合は、同じ公開先とcommitについて、未完了の工程のみを再開する。
   完了済みのpush、公開状態、CI結果、および正常終了した公開後操作の内容は確実に保持する。
2. 自力で回復できない場合、委譲先は本書「公開工程の続行不能の受渡し」の記録を委譲元へ返す。
   公開後の操作だけが未完了なら、確認済みのCIの結果を返す。
   baselineは既存の保存先を示し、未作成なら理由（CI定義なしなど）を書く。
   成功済みのCIを報告するためだけにbaselineを新しく作らない。
3. 公開を担当するメインは、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」で確認の要否と手段を決め、ユーザーの手作業（資格情報の提供や操作）か追加の認可が必要な時だけ確認する。
   ターンかセッションの後まで作業が残る場合は、`agent-toolkit:atk-mode/references/delivery.md`「個別UWI」で個別UWIを保存し、同じ内容の確認が既にあれば再利用する。
   UWIには、公開先、commit、完了済みの工程、必要な操作、返してほしい結果を書く。
   パスワードやトークンなど、資格情報そのものの書き写しはユーザーに求めない。
4. ユーザーの回答を要する未完了の元タスクだけを、UWIの保存の後に`agent-toolkit:atk-mode/references/states-and-dependencies.md`「承認型UWIと元項目」に従って、そのUWIへの依存で待たせる。
   完了済みの実装タスクの状態はそのまま保つ。
5. 残りの公開工程の再開記録は、引き継ぎ記録へ書き、別セッションで必要な情報は公開工程を扱う未完了AWIの本文へ追記する。
   該当するAWIが無ければ`agent-toolkit:atk-mode/playbooks/wi-drafting.md`で作り、個別UWIと関連付ける。
   再開記録は本書「公開工程の続行不能の受渡し」の項目に、個別UWIの所在を加えたものとする。
   引き継ぎ記録は同じセッションの中の受け渡しに使い、次のセッションが読む再開記録と証拠は、作成した時点で計画かAWIの本文へ保存する。
6. 回答を得たら、`agent-toolkit:atk-mode/references/answer-transitions.md`「回答後の状態遷移」に従う。
   元の担当のセッションがあれば回答を届け、無ければ再開記録から未完了の工程のみを再開する。
   すでに成功しているバージョン更新、push、公開後操作を重複して実行しない。
   process-wiでの元項目の取り込みは、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「回答済みUWIの取り込み」に従う。
7. 独立した有効な証拠でCI定義の不在を確定できた場合は、`agent-toolkit:atk-mode/references/ci.md`「公開先に対応するCI定義の判定」へ戻る。
   ローカル全体検証の失敗は、独立した未完了の事項として是正する。

## 返す報告に含める項目

実施した公開範囲と終了状態、pushの宛先とcommit、CIの結果と証拠の所在、公開状態の4項目、公開後の操作とリリース判定の結果、続行できない工程と再開記録の所在を返す。
