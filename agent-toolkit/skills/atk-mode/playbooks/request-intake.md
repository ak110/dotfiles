# 要求の受付と方針の確定

エージェントが顧客の現場に入る技術者（FDE）として、ユーザーが得たい結果と背景を確かめ、最も適した解決策をユーザーへ提案し、必要な確認を済ませてから着手するための手順である。
役割の分担は`agent-basics:writing-standards/references/quality-principles-roles.md`に従い、技術で決まる判断はエージェントが確定し、本人にしか確認・準備できない事項と方針の承認は手順7で扱う。
本書は`implement`、`add-awi-by-user`、`process-user-comments`に共通する前半であり、後半（`implement`は実装、他の2作業は起草と保存）は呼び出し元の手順書に従う。

## 依頼の種類と確認

手順1で依頼を次の2種類に分け、確認の進め方を種類で決める（2026年11月22日のユーザー指示）。

| 種類 | 例 | 確認の進め方 |
| --- | --- | --- |
| 完成形が依頼から決まる | 自明なバグ修正、変更の内容を明示した依頼 | 手順7の条件に当たる時だけ確認し、最後まで進める |
| 何を変えるかをエージェントが選ぶ | URL・記事・資料を参考にした改善の検討、「改善の余地はあるか」、手順7で関連機能を1件以上採用した依頼 | 着手（実装か起草）の前に必ず手順7を行う |

最初の種類は、変更の対象と内容が依頼から一意に決まるかで判定する。

## 手順

1. 入力を全て要求として読み、依頼の種類を決める（解決する課題を取り違えず、確認の要否を依頼の種類で決めるため）。
   範囲、列挙、例示、理由は`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」に従い、明示された要件と合意済みの要件はそのまま使う。
   引数が無く、直前の応答に項目別の方針があれば、その内容を入力とする。
   資料だけが渡された時は、起動したリポジトリを調査の起点にして、資料の全ての目的を改善の候補とする。
   「原文の保持と取り込み」で目的と分けた指定された手段（モデル、ツール、担当、手順）は、原文から対象の工程へ対応付ける（`agent-toolkit:atk-mode/references/workflow-phases.md`「工程表」）。
   後続の要件には、後続の工程向けの指定だけを渡す。
   `add-awi-by-user`、`process-user-comments`、`implement`で外部資料を扱う時は、作業契約に`作業: <作業名>`を記録する。
   入力の資料URLは、起動後に加わった資料も含め、同じ契約の「原本」に1件1行で記録する。
2. 外部資料は、要約より先に、主張者が公開している実装やスキルの本文を読む（取得は`agent-basics:fetch-sources`）。
   その直後に、名称と主題で既存WIを全状態から探す（`atk wi grep --summary-only -F <語> --state=all`）。
   外部資料の無い依頼も、要求の主題で同じ検索をする。
   採否は語の有無ではなく、起動したリポジトリの成果物の挙動で判定する。
   外部資料の適用範囲は手順6の点検類型(i)で派生先まで判定する。
   問題を起点とする調査では先に母集団を定め、確認UWI、修正、コメント、是正の回答などの出所と調査範囲を記録し、原因と類似箇所から対処を決める。
   大規模な再編はファイル別に棚卸しし、読み込み量、構成の目安と残す保護を書く。
   リポジトリ外への反映の到達点は`agent-toolkit:atk-mode/references/awi-body-completion.md`「完成条件」で決める。
3. 過去の決定に変更の候補を当てる（既存の仕組みが守っていたものを変更で失うことを見逃さないため）。
   対象リポジトリが記録する決定（方針の記録、設計記録）と、撤去した仕組みの経緯（commit履歴を`git log --grep`で働きを表す語から探す）に、変更の候補を当てる。
   決定を覆す候補は、手順7で決定を変えるかの確認に含める。
4. 方針を組む。
   - 指定された手段も、削る、置き換える、既存の仕組みや別の層で解く案と比べ、`agent-toolkit:atk-mode`「ユーザーの方針」で採否を決める。
   - 依頼された変更の品質を上げる。
     説明が複数の問題を指しうる時は、2〜3の候補と見分ける兆候を挙げ、選んだ問題を専門用語で示し、その用語で依頼を言い直す。
     隣接分野の既知の解法も探し、類推が成り立たなくなる境界を示し、実際に開いた事例・文献だけを根拠にする。
     その分野の一流の専門家なら品質を上げるために依頼に無くても行うこと、最も加工されていない素材、使う手法とツール、作り手と依頼者以外で結果の正しさを示すもの（テスト、計測、第三者の判定など）を挙げ、範囲を増やさずに方針と完成条件へ反映する。
     実験で決まる選択は試作して観測から推奨し（`agent-toolkit:atk-mode/playbooks/write-plan.md`「進め方」の手順2）、本人の選好だけを手順7の確認へ回す。
   - エンドユーザーが使う機能（画面、CLI、通知、出力など）の追加・変更では、依頼が機能や画面を1つだけ名指ししていても、関連機能を検討する。
     利用の開始状態、操作、結果を受けた次の行動をたどり、同じ場面に残る手間、同種の製品が備える機能、同じ機能を持つ他の画面・コマンドとの不統一から候補を挙げる。
     候補ごとにエンドユーザーの利点を1行で書き、推奨するかを示す。
     役立つ案がなければ候補は出さない。
     自律モードの `process-wi` と `process-loop` はこの検討の対象外とし、処理中に気付いた関連機能は[気付いた改善点](main-reporting.md)として報告する。
   - 資料を真似ることを目標にせず、先に対象で改善する結果を書く。
     本文の移動は、常時の配送、起動時の読み込み、検査を比べる。
   - 細則の整理では上位の原則を先に選び、領域別の分担前に表題・見出し・ファイル名が一致する主題を挙げ、定義元と担当を決める。
   - 候補ごとに、足す案と並べて、既存の規範・機能・記録を削る案と置き換える案を比べる（`agent-basics:writing-standards/references/quality-principles-subtraction.md`）。
     採る変更（ユーザーが指示した値・範囲・方式の変更を含む）が既存の仕組みの前提（閾値、標準の設定値、頻度、対象の範囲）を変える時は、その仕組みに残る効用を見積もり、撤去・縮小・統合を引く案として方針に入れる（ユーザーに言われてから引かない）。
     対象に便益が無ければ、無変更を選ぶ。
   - 新規の作業と未処理WIへの統合を並べて比べる。
     目的・編集先・再編の対象が重なるWIを調べ、統合するなら対象と目的で組み直す。
     独立して採否と完成を判定できる要求は混ぜず、統合しない理由も示す。
   - 資料の機能と消費形態は`agent-toolkit:atk-mode/references/omission-check.md`「資料起点の比較」で比べる。
     資料の全項目を対応付けた後に、同じ問題の操作、制約、利用場面から、資料に無い改善候補も探す。
     論文、ベンチマーク、他プロジェクトの実績を根拠にする案は、提案の前に`agent-basics:review-standards`で評価する。
5. 外部資料がある場合は、途中報告より先に`agent-basics:writing-standards/references/design-heuristics.md`「外部資料に基づく改善案の評価」の3方向で対応表を作る。
   読みは`agent-toolkit:atk-mode/references/omission-check.md`「点検類型」(l)で比較する。
   コード例は実効設定と効果を分け、`agent-toolkit:atk-mode/references/drafting-decisions.md`「採否と実現方式の確定」で成立条件と保つ機能を確かめる。
   不採用の資料も含め、資料の主張と方法ごとに行を分け、次の列を書く。
   - `資料URL`: 資料のURL。
   - `資料の主張（原文の抜粋）`: 比較する主張を1つだけ抜き出す。
   - `既存の対応箇所`: 比べた実物の所在。
   - `既存との差分`: 資料にあって既存に無い手法・条件・選択肢・具体例・道具・判断基準。
     差分が無い場合だけ「なし」と書き、対応箇所に同じ行動を促す既存の箇所をリポジトリ相対の `path:行` で示す。
   - `削る・まとめる・置き換える案`（既存から資料へ、既存どうし）: 資料を手本に既存の規範・機能・記録を削る、まとめる、置き換える案と、その採否。
     案が無い時は、調べた既存の箇所と案が無い理由を同じセルに書く。
   - `採否と理由`: 資料から得た改善案の採否と理由。

   Claude Codeのメインが上記3作業で`AskUserQuestion`による方針の承認を尋ねる場合は、セッション一時領域の`external-source-review.md`へ表を保存する。
   hookは評価基準の全文を読んだ記録と表の書式を確かめる。
   `atk wi add` も保存の前に資料URLと表の書式を確かめる。
   主張の網羅と参照先の意味は、手順6と後段の独立検収で確かめる。
   CLIやSDKが入力を変換する場合は、呼び出し元が問題の形式を直接作らないことと、変換後の入力にも問題の形式がないことを区別する。
   採否が変わる境界だけ、実際に使うCLIやSDKの版で変換後の入力を確かめる。
   観測が取れなければ未確認とし、ユーザーへは調査中と伝える。
   `add-awi-by-user`と`process-user-comments`では、対応表を原稿の「調査結果と判断根拠」に置く。
   登録0件で原稿を作らない場合は、比較と採否を既存の作業記録に残す。
6. `agent-toolkit:atk-mode/references/omission-check.md`「点検類型」の全類型を点検してから、方針を決める。
   外部資料がある時は「資料起点の比較」で表の全行の列と理由を確かめる。
   Codexや承認質問を伴わない場合も、方針を提示する前に点検する。
   後段の投入前レビュー（`add-awi-by-user`・`process-user-comments`）と実行レビュー（`implement`）はこの点検を補完する。
   外部資料が無ければ表を作らず、手順4で比べる。
7. 確認する（ユーザー本人にしかできない判断だけを問い、技術で決まる判断はエージェントが確定して根拠を示すため）。
   - 手順4で推奨できる関連機能が1件以上あれば、候補と推奨を先に送り、どれを採用するかを本人の選好として同じセッションで問う。
     採否は方針の承認より前に別の呼び出しで問い、後のセッションやUWIへ先送りしない。
     採用分は今回のAWIか実装の範囲に入れ、採らない候補は理由とともに報告する。
     1件以上採用したら採用分を含む方針を次の箇条で承認にかけ、全て不採用なら元の依頼の種類で確認を判定する。
     推奨できる候補が無ければ、検討の結論を方針か報告に1行書き、採否の質問はしない。
   - 「何を変えるかをエージェントが選ぶ」依頼では、方針の全体（採用・不採用・削除・置換）を送り（Claude Codeでは`send_to_user`）、決まった形の承認の質問を必ず1回問い、回答まで着手しない。
     Claude Codeでは送信の応答で `ok: true` を確かめてから問う。
     拒否なら診断に従って直し、送り直す。
     `REPL`では送信と質問を別のスクリプトに分ける。
     送信結果がJSON文字列なら解析してから `ok` を確かめる。
     修正回答による再承認待ちが無い初回の提示では、送信手段が無い、応答が無い、または期限切れなら質問を保留し、[送達の手段](../references/delivery.md)で方針を読める状態にしてから問う。
     修正回答による再承認待ちでは代替送達で問い直さず、同じ会話で`agents_server`との接続を回復し、`send_to_user`で改訂版を送達してから問う。
     Codexでは`send_to_user`が送達できないため、改訂版を応答の本文に書いてから問う。
     決まった形は次のとおりで、選択肢に推奨の付記を付けない。

     ```text
     見出し: 方針の承認
     問い（1つだけ）: 送った方針で進めてよいですか？
     選択肢1: この方針で進める（説明: 送った方針のとおりに着手する）
     選択肢2: 修正して進める（説明: 修正点を自由記述で伝える）
     ```

     Codexの非同期質問では次の形を使う。

     ```text
     title: 方針の承認：送った方針で進めてよいですか？
     options: ["この方針で進める", "修正して進める"]
     ```

     `send_to_user`（Codexでは本文）で送る方針の1行目は「方針（案）」とし、修飾を使う場合は同じ修飾だけを続け、件名、補足、本文は2行目以降に書く。
     先に送った方針を区別する必要があるときだけ、「送った」と「方針」の間に「2件目の」など6文字以内の短い修飾を入れる。
     修飾は文字と数字だけで書き、改行、読点、列挙記号、括弧、述語を含む文は入れない。

     方針の項目と技術の選択は質問文と選択肢に入れず、同じ呼び出しに別の問いを並べない（hookが形の違う承認の質問を止める）。
     本人固有の論点は、承認より前に別の呼び出しで問う。
     「完成形が依頼から決まる」依頼では、本人の選好・未開示の制約・認可（本人による準備とは別の、操作の認可を含む）が残る時だけ確認する。
     各問いは`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」の二段で見直す。
     本人にしかできない準備が残れば`agent-toolkit:atk-mode/playbooks/confirmation.md`「本人にしかできない準備の先行依頼」で着手前に依頼する。
   - 手段は`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」で選ぶ（Claude Codeでは`AskUserQuestion`）。
   - 適用範囲を問う時は、点検類型(i)で成立した派生先を`agent-toolkit:atk-mode/references/choice-construction.md`「候補の構成」へ渡す。
   - 判断の材料を先に送り、質問には問いと最小限の前提を残す。
     材料は、課題、変更対象と内容、未確認の前提、依頼どおりの案、種類の異なる案と不採用の理由、採らない資料の主張、点検済みの推奨である。
     既存の決定や値（指定を省いた時に使う値を含む）を変える案では、手順3で確かめた導入目的と変更で失うものも示す。
   - 回答、追加の発話、異議は、次の質問より先に処置する（`add-awi-by-user`と`process-user-comments`では`agent-toolkit:atk-mode/playbooks/add-awi-by-user.md`「指摘の分類と処置」）。
     外部資料が増えた場合は、作業契約の原本と手順5の対応表に加えてから再度方針を確認する。
     結果を変える論点が無くなるまで、手順6と本手順を繰り返す。
     繰り返しで何を変えるかの方向（対象、変更の内容、採る案と採らない案）が変わった時は、初回と同じく方針を送って承認を1回問う。
     確定した結果や範囲を変える案を推すなら、承認前であることだけを理由に元の案へ戻さず、変更後の方針を送って承認を1回問う。
     承認への修正回答の後は必ず同じ会話で改訂版を送達して承認を問い直す。
     それ以外で方向を誤る余地のない単純な修正、明示どおりの変更、方針を変えない技術判断では省く。
     ユーザーが概括的に受け入れたエージェント提案の実現方式も、確定した対象・結果・範囲を保つなら技術判断で選び、方式と変更理由を次の報告か方針に書く。
     [有効な指定手段](confirmation.md#確認要否の判定)を変える場合は省かない。
8. 質問の有無にかかわらず全類型を再点検する。
   `agent-toolkit:atk-mode/references/omission-check.md`「処置と終了時報告」の報告で、要求ごとの対象、種別、趣旨、確定した要件をそろえてから、呼び出し元の工程へ戻る。
