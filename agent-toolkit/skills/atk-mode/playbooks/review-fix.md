# レビュー指摘への対応

目的: 指摘を受けた担当が指摘ごとに採否と修正を記録して返し、独立したレビューの検出をユーザーへ届く成果へ確実に反映する。
実行レビューの指摘かCIの失敗を受けた担当が、指摘の受領から返却までを上から実行する手順書である。
使うのは、`CI修正担当`と、実行レビューの次のレビューイーである。

- 作業`process-wi`のレーン担当（同じthreadの継続`レビュー指摘の対応をせよ`で受ける）と、そのthreadを継続できない時に起動する`レビュー修正担当`
- 単一レーン処理と`agent-toolkit:atk-mode/playbooks/write-plan.md`で計画を作ったメイン
- 公開工程のCI修正系列で実行レビューを受けた`CI修正担当`

方針: 採否と修正の一般の手順は`agent-basics:review-standards/references/reviewee.md`に従う。
これは原則6（`agent-basics:writing-standards/references/quality-principles-verification.md`）の適用である。
本書は、agent-toolkitに固有の差分（道具の操作、記録の所在、計画の由来の列、返却の形）だけを置く。
入力（`レビュー指摘管理表`、`レビュー参考意見`、`CI記録`）と担当種別ごとの操作の権限は`agent-toolkit:atk-mode/roles/exec.subagent.md`にある。
終了条件は、全ての指摘に応答を記録し、修正があれば履歴へ統合して再検証を記録し、本書「返却前の確認」を通して返却した時点である。

## 担当種別ごとの修正

1. `agent-basics:review-standards`を起動し、レビューイーとして同スキルの手順と`references/reviewee.md`に従って、受領、採否、修正、公開可能性の検証、方式見直しを行う。
   次の手順2〜7は、reviewee.mdの各段にagent-toolkitで加える差分である。
2. 受領の時に、対象と記録の所在を確かめる。
   - `レビュー指摘管理表`は、1件の絶対パスか、全計画の表の絶対パスを並べたJSON配列で届く。
     各表で対応するroundは、その表の最大のroundである。
   - 新しいthreadで起動された`レビュー修正担当`は、`再開位置`の計画（`計画なし`なら引き継ぎ記録）と引き継ぎ記録の全計画の進捗を読み、受け取った各表がその計画群のどれかに属することを確かめる。
   - `レビュー参考意見`は統括の疑問と理由であり、指摘の原文と区別する。
     参考意見だけを採否の根拠にせず、現物と要件から採否を決める。
   - 計画に基づく修正では、採否と修正内容を決める前に本書「計画の確定内容の保持」を行う。
3. 提出前の記録との比較（`agent-basics:review-standards/references/reviewee.md`「指摘発生時の扱い」）では、提出前の主張と根拠を既存の検証記録と引き継ぎ記録から読む。
   比べた結果は、専用の台帳を作らずに指摘管理表の応答へ書く。
4. 再レビューでは、個別修正に着手する前に`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「反復原因の判定」を行う。
   同じ指摘の反復は `agent-basics:review-standards/references/reviewee.md` で扱い、方式見直しの契機は同資料の手順11で判定する。
   理由と結論を各指摘の応答に書く。
5. 類似見直しの検索と個別判定を専用の担当へ渡す時は`agent-toolkit:atk-mode/roles/similar-review.parent.md`で起動し、受け取った結果からの原因の判断と採否は自分が持つ。
6. 採用した指摘とCI記録の失敗は`agent-toolkit:atk-mode/playbooks/implementation.md`「実装」の手順で直してテストし、返却は本書「完了報告」で行う。
   修正の方針で新しい操作・機構・副作用を採用する前に、`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「計画準備の受領」手順3の禁止条件と突き合わせる。
   担当種別ごとに次を加える。
   - レビューの指摘の修正は、どの担当もレビュー修正だけのcommitを作らずに、本書「レビュー修正の履歴統合」で既存の実装commitへ統合する。
     `レビュー修正担当`は受領した指摘だけを直し、commitはfixup（直前の1件だけが対象ならamend）に限る（`agent-toolkit:atk-mode/roles/exec.subagent.md`「操作区分」）。
   - ユーザビリティレビューの指摘は、指摘の操作手順、画面状態、表示幅で新しいHEADを対象の実行環境で描画して確かめ（`agent-toolkit:atk-mode/playbooks/verification.md`「完了前の実描画確認」）、試した条件と結果を応答へ書く。
   - `CI修正担当`は、`CI記録`の7項目を実装契約とし、原因となった失敗だけを直す。
     原因の調査の前に`agent-basics:bugfix`を起動し、7つの問いをCI記録の原因分析結果へ当てる。
     診断コードを足す時は、CI記録が対応付けた仮説と採取対象に限る（`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「修正commitが必要なCI失敗を修正するエージェント」の手順3）。
     原因を特定できない時は是正commitとして返さず、行った比較検証、残る可能性、足した診断コードを推定と明記して返す（原則3）。
     原因commitへ取り込むかは`agent-toolkit:atk-mode/references/ci.md`「原因commitへ取り込む区分」で決める。
     取り込んだ時は、書き換え前後のOIDの対応と`git range-diff`の結果を返す。
     同じ仕組みを持つがCI記録が認可していない箇所は直さず、対象と修正の方向を委譲元へ返す。
     この報告は、CIログの有無、再現性、一時的な障害、再実行の認可と回数によらず行う。
     リモートへのpushは委譲元が行う。
7. ユーザーの判断か追加の認可が必要な対立と、要件か認可の変更が必要な方式見直しは、直さずに「続行できない理由」として委譲元へ返す。
   委譲元の扱いは`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「エスカレーションの事由別の扱い」にある。
   担当の内側で補える証拠の修復、探索、再判定は、返す前に自分で終える。

## 計画の確定内容の保持

計画に基づく修正の担当（レーン担当、レビュー修正担当、CI修正担当と、これらを統括するエージェント）は、修正内容を確定する前に、計画が列挙したWIの本文（本文の節を持つ保存済みの計画では計画のH1直下の要約と要求を書く節も）を読む。
構成は`agent-toolkit:atk-mode/references/plan-format.md`「計画ファイルの構成」、旧形式は`agent-toolkit:atk-mode/references/plan-legacy-formats.md`にある。
計画で確定した目的、方針、採否、対象範囲、除外と維持の事項は保つ。
実行工程の判断だけでこれらを覆すと、ユーザーと合意していない成果物ができる。

計画と既存の実装か規範が矛盾する時は、計画側（`由来`列と`## ユーザー指摘の逐語引用`）と、矛盾する側を入れた変更の双方の経緯と由来を調べる。
元の要求と明示された認可の内側で目的と結果を保つ技術的な解決を確定できれば、ユーザーへ確認せずに担当の権限の内側で直す（原則1、`agent-basics:writing-standards/references/quality-principles-roles.md`）。
計画側が優先することや相手側の由来が不明なことは、確認の理由から外す。
権限を超える判断が必要な時は、計画の記述、矛盾箇所、調べた由来、技術的な代替案を委譲元へ返す。

## 修正の分担と計画の保持

- 修正を複数の担当へ分ける時は、変更するファイルが重ならない指摘群を別の担当へ並行して割り当て、同じファイルを変える指摘は1人へまとめる。
- 実装に着手した後の計画は凍結している。
  指摘で確定した要件の変更と、記述の不整合に採った解釈は、計画を直さずに指摘管理表の応答へ書く（`agent-toolkit:atk-mode/references/plan-format.md`「計画ファイルの構成」）。
- 計画のユーザー指示・人間由来のWI・ユーザー確認の回答に基づく要求は、指摘を反映する時も要求の文面を原文のまま保つ。
  条件の追加、範囲の限定、終了条件の付与も変更に当たる。
  修正案は、そのレビューのラウンドを`由来`とする別の行に書く。
  内容が衝突する時は、ユーザーの確認（委譲先では本書「担当種別ごとの修正」の手順7の返却）を経てから書き換える。
  反映する担当の解釈で書き換えると、ユーザーと合意していない条件が合意済みとして扱われる。
- 要求の由来と原文の具体的な不一致を見つけた時は、根拠を示して既存の採否の記録（指摘管理表、計画が無ければ引き継ぎ記録）を訂正する。

## レビュー修正の履歴統合

採用した指摘の修正を、push前の既存の実装commitへ統合する。
採用が0件の時は、commitも履歴の統合もせず、履歴と作業ツリーをそのまま保って本書「検証結果の記録」へ進む。

1. 統合先と操作（fixupとautosquash、直前の1件だけが対象ならamend）は`agent-toolkit:atk-mode/playbooks/history-rewrite.md`「修正方法の選択」で決め、同書の確認と制約に従って実行する。
2. 書き換える直前に、対象のOIDが全て自分のレーンのcommitであることを確かめる（原則7）。
3. 失敗した時は`agent-toolkit:atk-mode/playbooks/history-rewrite.md`「失敗時の扱い」に従う。
   委譲元へ返す「続行できない理由」には、失敗したphaseの名前と、本節の末尾の表のその行の対象を添える。
4. 統合した後は指摘管理表の該当する指摘の応答に、修正commit、書き換え前後の7文字以上の一意な短縮OIDの対応、`history-compare`の一致確認の結果、対応表の絶対パスを書く。
   委譲元はこの対応で統合入力HEADを確かめる。
   WIとの対応の継承は`agent-toolkit:atk-mode/playbooks/history-rewrite.md`「WI実装commitの対応の継承」で行う。
5. 会話の履歴を失って再開した時は、指摘管理表の完了内容を現在のGitの実体と比べる。
   保存済みの書き換え前後のOIDの対応、公開済みかの判定、commit件名の一意性から対象を確実に特定できる場合だけ続ける。
   旧OIDは、指定の無いreflogを出典にせず、保存済みの記録から取る。
   特定できない時は、対象のOIDと不足する情報を「続行できない理由」として返す。

| phase | 対象 |
| --- | --- |
| `pre_fixup` | そのラウンドの最古のfixup対象から元のHEADまでのfirst-parentの全OID |
| `fixup` | 指摘を対応付けた元のcommitの完全OID（過去の作業単位を含む場合は元のHEADも対象） |
| `autosquash` | そのラウンドの最古のfixup対象から元のHEADまでのfirst-parentの全OID |
| `amend` | 書き換え後のHEADの完全OID |

### 検証結果の記録

1. 影響する検証を新しいHEADで実行し直し、`検証結果`を`agent-toolkit:atk-mode/playbooks/verification.md`「完成条件証拠の検証記録」の形で書く。
   手動観測は`agent-toolkit:atk-mode/playbooks/verification.md`「手動観測の保存」で全量を保存する。
2. 同じ内容を`atk run-script plan-progress -- <記録先> --handoff`で引き継ぎ記録へ書く。

## 実行レビュー反復での記録

採用した指摘の `検収:` を修正後のHEADで実行し、管理表の応答に `検収結果:` を記録する（`agent-toolkit:atk-mode/references/review-record-response.md`）。
履歴統合でHEADを変えた時は、結果が適用できることを確かめ、履歴統合後の短縮OIDを応答へ反映する。

レビューイーは指摘管理表に登録された全ての指摘に、採否、根拠、対応、検証の証拠を応答として記録する。
委譲元は`atk review-table show <表の絶対パス> --format=summary --round <対応したround>`の`unanswered_count`が0件であることを確かめる。
再レビューの要否は指摘の応答とは別に扱う。

応答は`atk review-table respond`で、`agent-toolkit:atk-mode/references/review-record-response.md`「レビュー指摘管理表への応答」の操作とラベルに従って記録する。

## 完了報告

1. 修正した時は、本書「レビュー修正の履歴統合」と「検証結果の記録」を終えてから返す。
2. レビュー担当の返却を持つ受領側が、指摘の採否・修正後の検証と、要否と評価前提を比べる。
   修正担当も正式な返却を受け取っていれば同じ前提を確かめ、前提が変わる時は`agent-basics:review-standards/references/reviewee.md`「方式見直しと再レビュー」に従う。
3. 本書「返却前の確認」を行い、次の形で返す。
   採用が0件の時も同じ形で返し、正式な返却の「不要」の評価前提を保つと確かめた時だけ1行目を`対応完了（再レビュー不要）`にできる。

   ```text
   対応完了
   検証結果: <`実装完了`と同じ書式>
   画面差分: <あり（変更した画面資産のリポジトリ相対パスの列挙）|なし>
   同種の既存画面: <画面・部品、状態を出す操作、再利用・相違と理由 | なし（検索語と範囲）>
   ```

   画面差分があるか、画面資産を変えずに画面の仕様を変えた場合は、`同種の既存画面:`が必須となる。
   既存機能の仕様変更では、全画面・共通部品の全呼び出し元への適用の有無と、未適用の理由を同じ行に含める。
   それ以外は省略でき、行が無ければ非該当とする。

   `CI修正担当`がCI記録の修正を返す時は`実装完了`の形（`agent-toolkit:atk-mode/roles/exec.subagent.md`「出力」）を使う。
   委譲先でないメインは返却せず、`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「レビュー修正」の再レビューか統合へ進む。

### 返却前の確認

`実装完了`と`対応完了`を返す前に、返却の不足を防ぐため次を確かめる。

- `git -C <対象worktreeの絶対パス> status --porcelain=v1`の出力に自分の担当範囲のパスが無いこと。
  出たらcommitしてから確かめ直す（統合されるのはcommitした変更だけである）。
  担当範囲の外のパスだけが残る時はそのまま返してよい。
- `検証結果`の手動観測の各行に、実在する保存先の絶対パスがある。
  欠ける行は保存してから書き直す。
- 返す`検証結果`と同じ内容が、引き継ぎ記録に記録済みである。
- `画面差分`は担当した差分に含まれる画面資産の有無で決め（定義は`agent-toolkit:atk-mode/references/workflow-phases.md`「用語」）、`あり`なら変更した画面資産のリポジトリ相対パスを並べる。

返す報告に含める項目: 返却の1行目（`対応完了`、`対応完了（再レビュー不要）`、`実装完了`のどれか）、`検証結果`、`画面差分`、委譲元へ返す担当外の箇所と続行できない理由。
