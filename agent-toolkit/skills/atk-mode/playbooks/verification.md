# 検証の起動、実行対象と証拠、限定した再検証

変更を検証する時に上から実行する手順書である。
検証の範囲、起動の形、結果の判定、再実行の基準は`agent-basics:check-execution`が定義元で、検証を始める前に起動する。
本書は、その定義元を使う時のagent-toolkit固有の差分（保存先、記録する値、レビューと統合への受け渡し、検査ツールの操作）を定める。
観測できなかった結果を成功として扱わない（`agent-basics:writing-standards/references/quality-principles-facts.md`）。
検証が簡単に成功しすぎた時と失敗した時は、対象の不具合を調べる前に観測の方法（対象に到達したか、実行集合、検証したcommit）が正しいかを確かめる。

## 条件と行動

| 条件 | 行動 |
| --- | --- |
| 変更範囲の検証を始める | 本書「実行のしかた」の手順1から |
| 受入シナリオや完成条件を手動で観測する | 本書「手動観測の保存」 |
| 画面を新設・変更した | 本書「完了前の実描画確認」 |
| 分岐条件の効果を一時的なコード置換で確かめる | 本書「分岐条件の効果の裏付け」 |
| commitとフックの結果で検証を省く・置き換える | `agent-toolkit:atk-mode/playbooks/commit.md`「commitとフックの検証」 |
| 文章チェックをMCPを使わずに実行する | 本書「文章チェックの一括実行」 |
| 検証結果を返却・引き継ぎ記録へ書く | 本書「完成条件証拠の検証記録」 |

形式検証は、害が大きく通常の試験が届きにくい性質を、保証範囲・実効性・費用で選ぶ。
特定の語の有無を適用・不適用の根拠にしない。

## 実行のしかた

1. `agent-basics:check-execution`を起動し、変更範囲とベースコミットを決める。
2. 後続のレビューや統合で結果を使う検証は、実行の前に本書「検証時本文の保存」を行う。
3. 本書「統合実行ツール経由の起動」で起動し、本書「保存した実行出力の取得」で結果を読む。
4. 引き継ぎ記録の検証コマンドを実行し、変更したコマンドも同じ記録に残す。
   計画が無ければ引き継ぎ記録で確定したコマンドを使い、同じ実行と判定の基準を当てる。
5. 結果を本書「完成条件証拠の検証記録」の形で残す。

`agent-toolkit:atk-mode/playbooks/publish.md`「検証とCI」に従う。
完成条件の観測手段と未確認の範囲は`agent-toolkit:atk-mode/references/awi-body-completion.md`「完成条件」に従う。

## 統合実行ツール経由の起動

- チェック実行用のMCPツールが使える場合はそれを優先し、pyfltrでは`run`ツールを使う。
  Codexで設定上共有の実行枠を取得する検証では、枠の待ちがMCPの期限を超えても同じ実行を回収できるよう、検査自体の所要にかかわらず最初からCLIを使う。
  枠を取らない実行は従来どおりMCPを優先する。
  MCPが使えない外部のチェックと手動の確認は、実行環境の標準の実行・バックグラウンド実行・待機機能で実行する。
- 検証ログの全量を別の担当へ渡す場合は、セッションのmanaged-temp内へ標準出力と標準エラーを分けて保存し、終了コードと取得時点の`git rev-parse HEAD`を`検証結果`へ記録する。
- 検証やCIの待機予算を選ぶ担当は、同じ仕事量の所要実績、現在の検査やジョブの進行、経過時間、待機を続ける場合と分ける場合で変わる検証範囲・時間を既存の検証記録へ残す。
  次の待機や終了を決める担当はこの記録を使い、運用上の目安、待機の上限に達した観測、検証結果を区別する。
  必須の検証や硬い上限は変えない。
- 共有の実行枠に参加する検証（pyfltrを起動する全ての手段と、実行枠へ参加するよう設定されたpytest）は、空き枠が無ければ先行する検証の完了を待つ。
  枠の数は検証を起動するpyfltrとプロジェクトの設定が決める（数はプロジェクト固有の値として各プロジェクトの規範にある。仕様はpyfltrの`docs/guide/usage.md`「同時に起動した検証の待機」）。
  - 巡回内のMCP・シェルのpyfltr、枠に参加する直接のpytest、統合の最終検証、commitの起動順は、`agent-toolkit:atk-mode/playbooks/process-wi-lane-resources.md`の資源管理で決める。
    順番が決まる前に対象のツールを起動せず、実行枠の待ち行列を増やさない。
    枠に参加しない収集などには適用しない。
  - シェルから起動する時は、ツール自体のタイムアウト（実行枠の待ち時間を除いた処理時間だけに掛かる）を使い、コマンドの先頭に`timeout <秒>`を付けない。
    バックグラウンド実行ではホストのバックグラウンド実行の上限を最大にするか、他の検証の待ちを見込んだ長さにする。
    待機中は、pyfltrの`execution-slot`警告かpytestプラグインの待機通知が標準エラーへ1回出る。
  - `agent-toolkit:atk-mode/references/operations.md`「待機とバックグラウンド実行」に従う。
  - 待機の通知を受けた後も対象や直接の利用側の編集を続ける場合は、待機中の実行を止め、書き込みを終えてから同じ対象集合で1回だけ起動し直す。
    待機を終えた実行は待機を始めた時点の内容を検証しないため、待ったままでは古い状態の検証が実行枠を占める。
  - ホストの上限で強制終了された検証は、待機通知の有無と最後の行で、待機中か処理中かを見分ける。
    待機中のタイムアウトなら処理は始まっていないので、同じ対象集合へ初回として起動し直す。
    処理中のタイムアウトは`agent-basics:check-execution/references/diagnostics.md`に従い、処理時間の上限は待ち時間と分けて管理する。
  - どの場合も、過去に保存した結果と対象のファイル集合は変えずに再利用する。

### pyfltrの起動形

- プロジェクトに起動の定義が無い場合は`uvx pyfltr`を使う。
  引き継ぎ記録には、対象への到達、必要なチェックの完了、終了状態と診断を判定できる同じ選定結果を書く。
- チェックが決まったら、対象のバージョンの公開手段から実効設定（有効化、実行ツール、コマンドライン、解決された実行ファイルのパス）を取る。
  `command-info`を持つバージョンでは、その公開ヘルプで入力と出力を確かめて使う。
- 渡した対象ファイルとcwdは、実際の実行集合と一致しないことがある（モノレポの子プロジェクトへの展開、`pytest-always-targets`などの追加）。
  起動の前に実効設定と設定ファイルから実際の実行集合を見積もり、実行の後は保存結果からサブプロジェクトごとの件数を確かめる。
- 失敗した対象だけを確かめ直す時は`--only-failed`や`commands`の指定で対象を限定する。
- サブコマンドと入出力は`pyfltr <サブコマンド> --help`かMCPのスキーマで確かめ、文書に無い設定は<https://ak110.github.io/pyfltr/llms.txt>を見る。

## 保存した実行出力の取得

保存されたpyfltrのログは、対象のバージョンが持つ取得方法（`show-run`など。公開ヘルプで対象・本文・構造化診断の取り方を確かめる）で読み、引数はそのバージョンの公開ヘルプが示すものを使う。
本文の表示だけが目的なら公開された本文表示を使い、構造化診断がJSONなら`jq`で読む。
テスト結果は、テストの完全名と結果の行を取れる形式（pytestは`-v`か`p`を含む`-r`、vitest・Playwright・dotnet testは1件ずつ出るレポート形式）で取り、要求と対応付ける。
個別の合否は結果の行で判定し、進捗のドットと成功の総数は根拠から外す。

### 警告の判定

警告は`agent-basics:check-execution/references/diagnostics.md`「読む出力」「合否の判定」に従い、検証結果へ記録する。

## 文章チェックの一括実行

MCPの`run`ツールを使えない場合に限り、本書「pyfltrの起動形」で解決したCLIを使い、同じ対象と制約で実行する（外部のファイルを指定する場合は`--allow-external-paths`を加える）。
完了は、出力JSONLの最終行の`summary`レコードへ`agent-basics:writing-standards/references/textlint-violations.md`の全対象被覆の条件を当てて判定する。
日本語の地の文と見出しのダッシュは、プロジェクトのpyfltr設定へ`writing-check-dash`として登録し、`run`の`commands`へ含める。
登録する実行手段は、複数の対象ファイルを受け取る公開CLI`atk run-script writing-check-dash -- <ファイル...>`である（検出の実装は`agent-toolkit/agent_toolkit/_atk/check_dash.py`）。

## 検証時本文の保存

検証を実行する担当は、実行の前に取得HEADの完全なOID、変更状態、検証の対象と直接影響範囲を確定する。
未commitの変更を含む場合は、その範囲の実行時の本文を復元できる保存物をセッションのmanaged-temp内に作り、後続のレビュー担当とレーン担当が出力と対象のバージョンを対応付けられるようにする。

- 追跡済みの変更は取得HEADを基点とする差分（バイナリを含む場合は`git diff --binary <取得HEAD> -- <対象パス...>`）で保存し、差分に入らない未追跡ファイルの本文は相対パスを保った複製で補う。
- 削除・改名・実行属性も含め、保存物と取得HEADから対象の内容を復元できることを確かめる。
- Git管理外の設定・入力を変えて使う場合も、必要な本文を同じく保存する。
  作業ツリー外の認証情報ファイルは複製しない。
- cleanなcommitの本文はOIDで取り直せるので、本文の保存物を省ける。
- 本文の同定には復元できる保存物を使い、パス一覧、status、ハッシュ値、検証後のcommitは補足として扱う。
  リポジトリ全体の複製、履歴を変える退避、全コマンドの自動snapshotは足さない。

実行の後は、保存物との実際の差分で本文が変わっていないことを確かめる（formatterとcommit hookによる更新も含める）。
実行中に本文が変わり検証した内容を確定できない結果は、終了後の本文保存で補ったことにせず、影響する範囲の追加観測へ戻す。
保存物は、それを参照するレビューと統合の受領が終わるまで保持する。

## 手動観測の保存

受入シナリオか完成条件を手動で観測する直前に、`agent-toolkit:atk-mode/references/workflow-phases.md`の起動条件で対象を起動し、コマンドは標準の実行機能で対象worktreeから実行する。
別の担当が出力の全量を確かめる観測では、`mktemp -d '<セッションのmanaged-temp>/<用途>-XXXXXXXX'`で作ったディレクトリへ標準出力と標準エラーを分けて保存する。
終了コード、cwd、argv、取得時点の`git rev-parse HEAD`による完全なOID、`git status --porcelain=v1`の結果を検証結果へ書き、PATH上の別の実行ファイルを使った観測はそのバージョンも書く。
保存に失敗した観測と、終了コードか取得HEADが無い観測は、保存できる形で実行し直す（レビュー担当は保存された観測だけを判定に使える）。
保存したディレクトリは、それを使うレビューと統合の受領が終わった後に作成者が`rm -r -- <作成した絶対パス>`で回収する。

## 完了前の実描画確認

画面の確認の基準は`agent-basics:writing-standards/references/ui-ux-topics.md`「完了前の実描画確認」にある。
Webではブラウザー、ネイティブGUIでは対象OSで描画し、同じ操作の画面画像・要素構造・キーボード操作経路を対応付ける。
通常の開始状態、代表作業、到達した状態と証拠は既存の検証記録へ残す。
機能上の停止を観測した場合は、開始状態・操作・停止箇所・未検証部分・証拠を機能テストか実行レビューの担当へ渡す。
画面キャプチャは描画ツールが書ける場所へ保存して絶対パスを記録し、PlaywrightのライブラリやE2Eテストではmanaged-tempへ直接保存する。
保存先が制限されたブラウザー操作ツール（`@playwright/mcp`など）では、ファイル名を指定せずに保存し、返されたパスを絶対パスへ解決して記録する（名前を指定するとcwd基準で解決され、出力ディレクトリの外への書き込みが拒否される）。
出力ディレクトリが対象の作業ツリー内にある場合は、managed-tempへ移してから記録する。

## 分岐条件の効果の裏付け

方法の基準は`agent-basics:writing-standards/references/testing.md`「分岐条件の効果の裏付け」にある。
一時的なコード置換で確かめる場合は、置換の前に既存の未commitの変更を退避し、確認の後に`git -c submodule.recurse=false restore --source=HEAD --staged --worktree <パス>`でインデックスと作業ツリーの両方を戻す。
親リポジトリだけを戻し、初期化済みサブモジュールのHEAD、ブランチ、作業内容は保つ。

## 完成条件証拠の検証記録

この記録は、実行対象と観測した出力を対応付け、別の担当（実行レビュー担当など）が同じ観測を再取得して判定できるようにするためのものである。
実行レビューが完成条件証拠を判定する作業では、実装担当とメインが検証結果の原本を引き継ぎ記録の1か所へ書き、返却の`検証結果`には原本の所在と、担当の判定に必要で原本にない情報だけを書く（違う実行対象や違う合否が2つの記録に残らないようにするため）。
原本への参照を保てない時（引き継ぎ記録が無い、委譲元が読めない場所にある）は、返却に一度だけ記録する。
判定（達成、未達、根拠不足）は実行レビュー担当だけが記入する（`agent-toolkit:atk-mode/references/review-record.md`）。

- 要求ごとの状態は`agent-basics:writing-standards/references/quality-principles-verification.md`に従い、未実施は未検証、観測不能・出力なし・終了状態なしは判定不能とする。
  未検証と判定不能は、対象の要求、理由、試した手段、残る限界を書き、後続の工程へ回した項目は採否と後続を記録した所在を書く。
- コマンドごとに、コマンド、cwd、終了コード、判定の根拠にした出力の要点（失敗、警告、対象への到達、件数）、検証したcommitの完全なOIDを書く。
  未commitの変更で検証した場合は、本書「検証時本文の保存」の保存物を対応付け、全量を保存した場合は両出力の絶対パスを添える。
- 受入シナリオごとに、公開された呼び出し手段、入力、期待結果、実際の結果として、テストの完全名と合否か、保存した手動観測の所在を書く。
  pyfltrなどが出力を保存する場合は、その出力に結果の行があることを確かめ、実行の識別子と出力ファイルの絶対パス・行番号を書く（レビュー担当が個別の結果のためだけに実行し直さずに判定できる）。
- テスト用の入力と実際に動いた実行環境のバージョンは別の値として書く。
  OSを模擬したテストは`agent-basics:writing-standards/references/testing.md`「プラットフォーム分岐の検証」に従い、模擬した値と実ホストOSを同じ記録へ対応付け、模擬の成功を実OSと初回起動へ広げない。
- エージェント宛ての通知を変えた場合は、既存のhookテストが返す整形・結合・ホスト変換後の最終応答（`additionalContext`、`permissionDecisionReason`、`reason`、圧縮時の注入本文など）を省かず保存し、入力・実行対象・ホスト・通知ごとの観測箇所と対応付ける。
  途中の整形結果での代用と、専用の収集CLIや常設の台帳の追加はしない。
- 前のバージョンでの観測を引き続き使う場合は、取得時のHEADと適用の理由を保つ（書き分けは`agent-toolkit:atk-mode/references/review-record.md`「根拠の書き方」）。
  複数の要求が同じログを共有する場合も、要求ごとに観測の所在と内容を分けて書く。
- レビュー指摘の修正と履歴の統合の後は、影響する検証を新しいHEADで実行し直して`検証結果`を更新し、影響の無い検証は取得時のHEADと理由を書いて再利用する。
- 足りない観測は自分で操作できる範囲で取り足し、入力・権限・外部状態が必要な不足は続行できない理由として委譲元へ返す。

返す報告に含める項目: 検証したコマンドと実行対象、要求ごとの3値の状態、保存物と出力の所在、限定した再検証の範囲。
