# レーン資源と後段レーンの先行調査

作業`process-wi`のレーンの専用worktree・branch・所有登録を`atk lane`で作成・再利用・回収し、所有と成果を保護する手順書である。
メインが資源を作って回収し、レーン担当は受け取った資源で作業して`レーン開始時刻`を統合へ渡す。
後段レーンのworktreeを作る前に始める読み取り専用の先行調査も本書で扱う。
一時ファイルの置き場所の一般則は`agent-toolkit:atk-mode/playbooks/managed-temp.md`にある。
終了条件は、全てのレーンの資源を回収するか、保持した資源ごとに保護の理由と再開条件を記録した時点である。

## 書き込み所有権とレーンの境界

レーンは専用worktreeの単一の書き込み担当（単一writer）と実行レビューの体制を保つ。
レーン内の分担は`agent-toolkit:atk-mode/playbooks/implementation.md`「レーン内の分担」に従い、書き込み先と一体の生成物を担当ごとに分ける。
主作業ツリーへの書き込みは、`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「統合の許可」の条件と`atk lane integrate`の排他で直列化する。

## レーン資源の作成・再利用・回収

1. 開始時に`atk lane delete --list --repo <対象リポジトリ>`で、前回の残存登録、回収結果、回復処理で残ったbranchとHEADを確かめる。
   `orphan_candidates`は登録外の候補の由来と保護理由を表示する。
   残る登録は、担当や関連プロセスの終了を確かめてから、元の所有sessionを指定した`atk lane delete --session-id <所有session>`で再判定する。
   再開に使う登録は、登録ファイルの`record_path`をcreateの`--reuse-record`へ渡して新しい所有sessionへ移す（旧配置の個別managed-temp配下の登録も同じ作成先のまま移せる）。
   再利用するworktreeが無ければ移さずに、元の所有sessionへのdeleteで登録を回収してから作り直す。
2. 過去のエージェントの残存資源や誤変更を認めたら、`agent-toolkit:atk-mode/references/operations.md`「プロセス終了の安全規定」で登録と実体を調べる。
   未統合・dirty・稼働中・登録なしの表示は調査の起点として扱い、現在の担当への引き継ぎと成果の保全を先にする。
   登録済みの資源は、保持の理由を解消してから同じ所有sessionへのdeleteで安全判定をやり直す。
   既に終了した旧所有sessionで選定の未統合だけが残る場合は、`atk lane delete --session-id <旧所有session> --retire-integrated` で取込みを検査する。
   保存した回収結果で `retire_integrated: true` の場合は、保持理由を解消した後も同じフラグを付けて再試行する。
   これは選定の終了の代行ではない。
   統合先から履歴を辿れるか、ファイル・配置・gitlinkを含むtree全体が一致する場合だけ取込みを認める。
   clean・未使用を確かめて回収し、到達点と選定の記録を回収結果へ残す。
   登録外の一時worktreeやbranchは、命名だけでエージェント作成と決めない。
   作成時のsession記録やmanaged-tempの所有から作成者を確かめ、取込み・clean・未使用が確認できれば回収する。
   作成者が不明なら候補と保持理由を残し、ユーザー確認なしに削除しない。
   主作業ツリーは対象外とする。
3. レーンごとの専用branch・専用worktree・所有登録を次のコマンドで作る。

   ```text
   atk lane create --repo <対象リポジトリの絶対パス> --base-branch <統合先branch> --lane <レーン識別子> --selection-file <選定YAMLの絶対パス>
   ```

   作成先は主作業ツリー配下の`.claude/worktrees/process-wi-<レーン識別子>`に固定される。
   `process-wi`は対象リポジトリごとに1つだけ起動する前提のため、別セッションや`process-loop`のworktreeから呼んでも同じパスになる。
   系統を登録したリポジトリでは、この前提を系統ごとに適用し、常駐も系統ごとに作業ツリーと所有を分ける。
   作成先は`.claude/worktrees/process-wi-<統合先ブランチ>-<レーン識別子>`（ディレクトリ名に使えない文字は置き換える）となり、同じ名前のレーンでも系統ごとに別のパスになる。
   固定の作成先とは別の場所が必要な場合だけ`--worktree <絶対パス>`を指定し、そのパスは固定の配置から外れる。
   所有session、Git共通ディレクトリ、専用branch、作成先、回収対象、選定原本、固有手順、実行記録は`record_path`の登録ファイルへ保存されるため、手作業で登録し直すことは避ける。
   createは選定原本からレーンに属するWI集合と統合状態を所有登録へ写し、選定原本が一時領域から消えた後も保持した値で統合と回収を判定する。
4. 対象リポジトリに固有の作成・環境準備・撤去の手順があれば、create・prepare・deleteの各argv配列を持つJSONファイルを`--commands-file <絶対パス>`へ渡す。
   argvの`{repo}`、`{worktree}`（固定の作成先）、`{branch}`、`{lane}`は、シェルを介さずに作成側が展開する。
   前提ファイルのコピー、`mise trust`、依存の同期はprepareに含め、固有手順でdetached HEADになった場合は作成側が専用branchへつなぐ。
   対象リポジトリのClaude Code設定に`WorktreeCreate`があれば、作成をそのhookだけに任せ、対象cwd・環境変数・公式のイベント入力で実行して、返されたパスを同じ所有登録へ保存する。
   hookが失敗したら、診断と作成途中の資源を保ったまま同じ操作で回復し、通常のGitコマンドでの作成へ切り替えることは避ける。
   `WorktreeRemove`があれば、回収時に同じ設定と返されたパスを使う。
   前提ファイルのコピーはhookかprepareが行う。
5. 終了コード0、`ready`の状態、prepareの標準出力・標準エラーを読み、警告の有無と環境準備の成立を確かめてから担当を起動し、環境構築の結果を`agent-toolkit:atk-mode/roles/exec.parent.md`の`環境構築`へ渡す。
   準備に失敗した資源は、登録と途中の成果を保ったまま入力を直し、同じcreateで再開する。
   別の名前空間へworktreeを渡すレーンでは、使う全ての主体から同じ絶対パスへアクセスできることを読み取り専用で確かめてから担当を起動し、確かめられなければ起動を見送る。
6. 各レーンの担当を初回に起動する直前に、タイムゾーン付きのISO 8601の現在時刻を`レーン開始時刻`としてレーンごとに自分の引き継ぎ記録へ保存し、同じ値を起動の入力で渡す（`agent-toolkit:atk-mode/roles/exec.parent.md`「入力」）。
   同じレーンの再起動、担当の交代、統合だけを担う担当の起動でもこの値を保って渡す。
   レーン担当はこの値を`atk lane integrate`のmanifestの`lane_started_at`へ渡し、CLIは最初の値をレーンの稼働秒数の起点として所有登録へ保つ。
7. 同じレーンへの追加と同じWIの再開は元のレーンで行い、選定原本を未統合へ戻してから同じcreateを呼ぶ。
   createは、前回の統合完了を確かめられるcleanな専用worktreeだけを現在の統合先の先端へfast-forwardし、回収済みなら作り直す。
   未保存の差分、稼働中の別のwriter、履歴の分岐があればcreateは成果を保って失敗するため、診断から所有・差分・基点を確かめて回復する。
   同じ入力HEADの再開でも、再検証と選定の再統合を終えてから統合済みとする。
8. 固定の作成先が別のセッションの登録で使われている場合、createは回収の条件を満たす資源だけを回収して同じパスに作り直す。
   未統合、dirty、稼働中、所有の登録の無い実体は変更せずに失敗とし、理由と`--reuse-record`かdeleteでの回復の手順を返す。
   選定の情報を持たない旧形式の登録は、`atk lane recover --session-id <所有session>`で元のbranchを保ったまま作業ツリーだけを解放する。
   組み込みの回復では、未追跡の変更に加えて、Gitの無視対象でも回収可能と確認できないファイルがあれば、対象パスを示して保持する。
   回復を終えた登録は固定の作成先の所有・回収の判定から外れ、残ったbranchとHEADは`atk lane delete --list`の出力で確かめられる。

## レーンworktreeの扱い

1. 統合・最終化の検収と消費の工程を終えたレーンは、巡回全体の終了を待たずに、メインが`atk lane delete`で回収する。
   公開中の公開単位に含まれるレーンだけは、その単位の検収まで回収を止める（`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「公開担当の起動と並行工程」）。
   同じthreadへの追加は、保存したcommit・計画・引き継ぎを使い、`atk lane create`で環境を作り直してから再開する。
2. 回収の順は、`--commands-file`に渡したdeleteコマンド、worktree、branch、以前の構成の個別managed-tempとする。
   回収時は主作業リポジトリから実体のパス、Git登録、branchの有無を照会し、全てが無いと確定した登録だけを、警告と最後に記録したHEADを残して回収する。
   組込み回収では、再生成できると判別した無視対象だけが残る登録済みレーンも回収する。
   配布用の派生ディレクトリは、生成時に記録した内容と一致する場合だけ回収する。
   記録が無い旧ディレクトリは保持する。
   判別できない無視対象や別のGit資源は保持する。
   `WorktreeRemove` を使うプロジェクトでは、そのhookが作業ツリーの撤去を担う。
   作業ツリーのパスが無ければdeleteの手順は実行せずに、Git登録だけが残っていれば登録を強制解除し、branchが残っていれば統合済みかの判定を続ける。
   通常の終了時は`atk agents-exit-session`が回収し、巡回では統括がセッションを終える前に回収する。
   `lane delete --repo <統合先worktree>` は登録外資源も調べる。
   `orphans`の安全判定は`agent-toolkit:atk-mode/references/operations.md`「プロセス終了の安全規定」に従う。
   `orphans`の回収結果と保持理由を確かめ、`user_confirmation`の資源はユーザーの確認なしに削除しない。
3. 容量を空ける目的で回収した場合は、回収の前後の`df -h /`と空いた容量を報告に含める。
4. CLIが未統合・dirty・稼働中・状態不明・一部失敗の資源を保持したら、メインが本書「レーン資源の作成・再利用・回収」手順2の共通判断で理由を調べる。
   理由を解消した対象は同じ操作で再判定し、保護する成果、現在の担当、残るユーザーの判断と再開条件がある対象は保持して、その理由を記録する。
5. 登録情報と回収結果の参照は、回収対象のworktree・branch・個別managed-tempとは別の状態ディレクトリに保存される。
   回収結果は通常の7日保持に任せ、再開に必要な選定情報・merge後のHEAD・検証記録は`atk lane`が所有登録と同じ状態ディレクトリに保つため、managed-tempの7日保持に頼る必要は無い。

## 後段レーンの先行調査

1. メインは、後段レーンのworktreeを作る前に、先行成果を要しない読み取り専用の調査を既存の委譲手段で始めてよい。
   対象は、要求・規範の確認、実装・テスト・参照先の所在、先行成果に依存しない設計材料、正式化の前の計画の下書きとする。
   同じレーンの後続も`agent-toolkit:atk-mode/playbooks/process-wi-execution.md`「計画の起草」で準備を早める。
2. 書き込み競合だけで後段になる場合と、調査や判断自体が先行成果を要する場合を区別し、後者の未確定の部分は成果の到着まで保留する。
   後者のworktree作成と正式な計画・編集は、必要な成果の統合後に行う。
3. 共有実行枠（`agent-toolkit:atk-mode/playbooks/verification.md`「統合実行ツール経由の起動」）での検証と直列統合の処理能力を踏まえ、独立した準備の先行と準備・検証の集約を比べ、先行させた後に前提と所要時間の見込みを更新する。
   実行枠が埋まった時と即時対応の検証が起動できる時は、巡回の統括が既存の作業記録で検証の起動順を管理する。
   起動の順は、即時対応の検証、統合の検証、各レーンの途中の検証とする。
   稼働中の検証は止めない。
   即時対応の検証が終了、失敗、取消になったら結果を回収し、成功と区別して次の起動へ進む。
   先行調査の担当も巡回全体の同時数Cへ数え、資源・費用の比較と巨大WIの判定は`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`「内部担当の同時数と巨大WIの判定」に従う。
4. 調査担当など統合先へ書き込まない補助の担当は、作業ディレクトリを統合先とレーンのworktreeの外（起動者か担当自身のmanaged-tempなど）にして起動し、読み取り対象は絶対パスで渡す。
   `atk lane integrate`は作業ディレクトリが属するworktreeで稼働中の担当を集め、役割文書を持たない起動を書き込み担当と数えて統合を止めるためである。
5. 調査担当は、取得したリポジトリの版、対象パス、確かめた事実と仮定、残る問いを自分のmanaged-tempへ保存する。
   先行調査は読み取りに限り、正式な計画の作成、WIの状態の変更、レーン資源の登録、対象worktreeへの書き込みは後段の担当に残す。
   新しいCLI、準備専用のレーン、キューの状態は設けず、レーン数の上限と書き込み所有権を保つ。
6. 開始できる通常のレーンは、先行調査の準備や終了を待たずに起動する。
   メインは調査担当の終了を既存の委譲の契約で観測し、結果の絶対パスを`先行調査記録`としてレーン担当へ渡す。
   結果が未完了や失敗でも、後段の通常の調査と計画は始められる。
7. 後段のworktreeは、先行調査の有無によらず`agent-toolkit:atk-mode/playbooks/process-wi-lanes.md`「レーンと資源」の条件で作る。
   レーン担当は、調査で取得した版とworktreeの現行版の差分を確かめて、影響する調査だけを更新する。
   計画の下書きはそのまま確定せず、`agent-toolkit:atk-mode/playbooks/process-wi-execution.md`「計画の起草」の正式な起草と検査を経て実装する。

返す報告に含める項目: 作成・再利用・回収したレーンと資源、保持した資源と理由と再開条件、`レーン開始時刻`、容量を空けた場合は回収の前後の`df -h /`と空いた容量。
