# Claude Codeの手順書

Claude Codeで動くエージェントが、ホストに固有のツール、通知、hookのイベントを扱う時の手順書である。
方針: ツールの公開状況と通知の配送はClaude Codeの版、設定、プロバイダーで変わるため、可否と状態は実際の呼び出し結果と終了の観測で決める（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。
起動した委譲、バックグラウンド処理、定期の再確認は、起動した主体が終了を観測して回収する（原則7、`agent-basics:writing-standards/references/quality-principles-ownership.md`）。

## 読む節

本書を全文読み、表で場面に合う節を選んで適用する。
委譲の共通の手順は`agent-toolkit:atk-mode/playbooks/delegation.md`の索引から選び、本書はClaude Codeに固有の差だけを持つ。

| 主体と場面 | 読む節 |
| --- | --- |
| メインがユーザーへ届ける、尋ねる、ターンを終える | 本書「ツールの入出力」「ユーザー確認（AskUserQuestion）」「ターンの終え方」 |
| 自分のセッションIDやtranscriptを使う、委譲先へ渡す | 本書「自身の会話の記録」 |
| 利用上限の猶予通知を受けた、hookが示した資料を取得する | 本書「利用上限の猶予通知」「資料の取得」 |
| Code Modeで、ツールの有無、接続、バックグラウンド実行の状態を判断・報告する | 本書「Code Modeでのツールの探索と実行結果の回収」 |
| `Agent`ツールで委譲する、`SendMessage`・`ListAgents`・`TaskStop`を使う | 本書「実行時能力と通信scope」から「稼働状態の観測と継続依頼」まで |
| バックグラウンド処理や委譲の完了を待つ | 本書「背景ジョブの起動形（Claude Code）」「待機中の定期再確認と背景転換」「長時間待機前の会話圧縮」 |
| hookで`Stop`と`SubagentStop`を扱う | 本書「委譲先での発火」 |

## ツールの入出力

- プラグインの再読み込みと`agents_server`・`pyfltr`のMCP再接続は、メインが`apply_runtime_changes`で予約し、ターンを終えて反映の結果を確認する。
  常駐のprocess-loop統括では、巡回の途中で予約しない。
  途中のStopは巡回を終えていないターンの終了を止めるため、予約だけが残る。
  現在の環境のまま進めるか、必要な版を反映して残工程を早めるかは、[更新のための本人再開](process-wi-all-repos.md#更新のための本人再開)で決める。
  ユーザーに操作を頼まず、再接続の予約が失敗した時か接続を失った後に限り`/mcp`での復旧を依頼する。
- Windows版のBashツールは引用符付きのheredocや単一引用符の中でも`\\`を`\`へ縮めるため、エスケープを含むコードはWriteでmanaged-tempへ保存して実行する。
- `mcp__plugin_agent-toolkit_agents_server__send_to_user`を使える時は、`agent-toolkit:atk-mode/references/delivery.md`「Claude Codeの本文送信と再送」に従う（地の文はAPIで要約されうる）。
  最終の完了報告には `kind: "completion"` を指定する。

## ユーザー確認（AskUserQuestion）

1. 質問ごとに`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」を適用し、確認が不要な問いは確定した案と根拠を報告して進める。
2. その場で回答を求める質問・選択は、ツール一覧に`AskUserQuestion`があればそれで尋ねる。
   本書「ツールの入出力」で`send_to_user`を使う時は、必要な判断材料や直前の問いへの答えを短い前置きとして先に送れる。
   それ以外は材料を質問の本文か`preview`へ書く。
   質問ツールが無い時は`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」に従う。
3. `AskUserQuestion`の質問は、ダイアログだけの表示と拒否の後の作り直しに備え、単独で通じる最小限の前提、問い、選択肢、推奨で書く。
   質問と選択肢の数はスキーマに従い、自由記述は各質問への回答、一般の返答は別の`response`で受け取る。
4. 推奨する案を第1の選択肢にしてlabelの末尾に`(Recommended)`を付け、`共通前提:`、質問、選択肢は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認の選択肢を組む手順」で組む。
   方針の承認の質問は`agent-toolkit:atk-mode/playbooks/request-intake.md`手順7の決まった形とし、`(Recommended)`を付けない。
5. `askUserQuestionTimeout`が`never`でも、REPLの実行上限（Claude Code 2.1.331で2時間）は質問を打ち切る。
   `REPL execution exceeded its wall-clock limit`はユーザーの回答でも拒否でもないため、同じ質問を出し直してチャットでも回答できると伝える。

## ターンの終え方

- 作業完了報告の確定、対象作業での自動終了の要求、通常本文で報告した後の固定文の扱いは`agent-toolkit:atk-mode/playbooks/report-completion.md`「工程」に従う。
- 確認の前置きを送っただけでターンを閉じず、質問は本書「ユーザー確認（AskUserQuestion）」の手段で尋ねる。
- `send_to_user`で送達済みなら、新しい結果・訂正だけを追加で送り、`…`だけで終える（送った内容の言い換え、翻訳、要約、抜粋は不要）。
  空の応答は再生成を求められるため、未送達でも伝える内容の無い待機は`…`を返し、ホストの無発話の注意を受けた時も同じ終え方を保つ。
- process-loopの統括と`atk run-skill`が起動したセッション（最初の入力の`atk-auto`要素の`source`が`process-loop`か`run-skill`）では、担当の工程を終えた時だけ`…`を完了の1文に替え、報告の抜粋や補足は含めない。
- 完了通知を待つ区切りは`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「完了通知を待ってターンを終える場合」に従う。
  反映予約の受付は成果完了とせずターンを区切り、次のターンで反映結果を確かめて作業を続ける。
- process-loopの統括と`atk run-skill`が起動したセッションは、全ての待機対象を回収した後、最終のターンを閉じる前に、共通のpromptと一致する非durableの定期再確認タスクを`CronList`で特定して`CronDelete`で消す。
  経過時間の義務を足したタスク、durableなタスク、無関係なcronタスクは残し、他のセッションはmodの自動回収に任せる。
- 計画はどのモードでも直接作成し、Plan modeの承認待ちへ移るかはユーザーの操作に委ねる。

## 自身の会話の記録

- 自分のセッションIDとtranscriptの絶対パスは、SessionStartの通知の値を使い、圧縮、再開、clear、forkの後は新しい通知の値へ更新する。
  更新時刻の順、cwdから推測した名前、MCPの`root_session_id`、委譲先のIDで代えると、別のセッションを取り違える。
- 通知で取得できないとされた値は、Bash・PowerShellの`CLAUDE_CODE_SESSION_ID`か、特定済みのIDを渡す`atk run-script session-review-evidence -- --claude-session-id <ID>`で解決する。
- 委譲先へ証拠を渡す時もこの値を使い、過去の会話や委譲先の会話は指定された識別子で取得する。

## 利用上限の猶予通知

猶予通知は`Usage limit reached; a short grace allowance remains`で始まる注記である。
受けたら`agent-toolkit:atk-mode/references/usage-limit.md`「利用上限の猶予通知を受けたときの続行と再開」の手順で再開情報を保存し、残りの工程を進める。
終了の記録（`agent-toolkit:atk-mode/references/termination-evidence.md`）では、上限の解除待ちを`wait`、観測した技術的な不成立を`blocked`とし、待ちを失敗として扱う誤りを避ける。

## 資料の取得

- hookが示した対象は、導入済みのスキル名なら`Skill`で起動し、参照資料、起動が禁じられたスキル、別の版の写しなら`Read`で読む。
- `agent-toolkit:<スキル>/<パス>`は起動の通知が示す実在のplugin rootの`skills/<スキル>/<パス>`へ解決する。
- 明示された実パスは、その実体を読む。

## Code Modeでのツールの探索と実行結果の回収

JavaScriptからツールを呼ぶCode Modeでは、ツールの一覧とバックグラウンド実行が通常の会話と違う形で公開されるため、通信や待機の判断と状態の報告の前に次を確かめる。

1. `tools`に名前が無い時は、未展開か遅延公開かを先に調べ、公開されている`searchTools`・`describeTool`かToolSearchで登録を探して入力スキーマを確定してから可否を判断する。
   MCPの切断と報告するのは、探索でも登録が見つからず、接続の診断が切断を示した時に限る。
2. 登録の発見と呼び出しの成功は別の状態として報告し（認証の失敗は登録の後でも起きる）、正常な接続での拒否や対応しない入力の拒否は探索の後も拒否として報告する。
3. REPLで未awaitのPromiseを作った段階は、起動を求めただけである。
   公開されているBashの入力とPollの契約で起動、実行中、終了を区別し、終了コードと結果を回収してから状態を報告する（受付だけが成功した起動は実行中として扱う）。
4. 拒否された指定（`run_in_background`など）は拒否として受け入れ、別の切り離し方で迂回せずに、未実行の操作だけを公開された方法（通常のawaitとPoll）で実行する。

機械処理と原文確認の使い分けは`../references/operations.md`「出力の保持と観測」に従う。
例えば`describeTool`で配列を返す契約を確認した読み取りツールなら、REPLで応答を`await`し、成功した配列を集計して件数だけを返せる。
診断や実行中の識別子は元の応答から回収する。
Code Modeを使えない場合は通常の公開ツールやCLIを使う。

## 実行時能力と通信scope

- `SendMessage`と`ListAgents`を使えるかは、自分に実際に公開され、呼び出しが成功するかで決め、環境変数、プロバイダー、agent定義の`tools`（権限の上限を示すだけ）から推測する誤りを避ける。
- `ListAgents`が使えない時は、保持したagent ID、完了通知、成果物の状態、自分が起動してプロセスIDを持つプロセスの生存（止めたなら停止の成否）を組み合わせて判断する（以下「代替稼働観測」）。
  プロセス名の一致だけでは、生存も対象も決められない。
- `agents_server`が起動したClaudeの委譲先は起動の本文で、`Agent`ツールのサブエージェントはSubagentStartの通知で、`agent-toolkit:atk-mode/playbooks/subagent.md`を受け取る。
- 同じセッションの親子の委譲は、`Agent`の起動結果が返すagent IDへ、`SendMessage`が公開されIDが同じ委譲の木で有効な時に送る。
- Agent Teamsと独立したセッションの間の通信は、機能が有効で`ListAgents`と`SendMessage`の呼び出しが成功する時だけ使い、成立しなければ設定の変更、親子の委譲への読み替え、代わりの仕組みの追加をせずに見送る。

### 即時通知の宛先

- 宛先に使えるのは、起動結果が返したagent ID、ホストが明示する機械可読の返信アドレス、ホストが値を示して到達を確かめた`senderTaskId`だけであり、`from`、`origin.from`、`name`、`subagent_type`は使えない。
- `Agent`ツールの委譲先は、`SendMessage`の`to: "main"`を、最上位のセッションへの確認事項と改善点の即時通知（判定は`agent-toolkit:atk-mode/playbooks/subagent.md`「確認事項の即時通知」）だけに使う。
  直接の委譲元への返信、完了報告の返却、独立したセッションの間の通信には使えない。
- 独立したセッションへ即時指示を送れなければ記録で宛先・送信状態を確認し、不具合なら `agent-basics:bugfix` で認可内の修復後、未送達を確認できた場合だけ再送し、結果または未回復の影響・試行・再開条件を委譲元へ返す。
  `atk wi process-loop instruct`は次の起動で読む指示を保存する仕組みであり、即時の配送とは別に扱う。

## 委譲先での発火

- `Stop`は、そのセッション自身のターンの終了で発火し、独立したClaude Agent SDKのセッションである`agents_server`の委譲先でも同じである。
- `agents_server`が起動したセッションかは、そのセッションだけに付く環境変数`AGENT_TOOLKIT_DELEGATED_SESSION`で判定する。
- `SubagentStop`は`Agent`ツールのサブエージェントのターンの終了だけで発火して入力の`agent_id`で判別でき、登録する処理はサブエージェントが実行できる処置に限る。
- 規範の上の役割とhookの種別は別に扱い、最上位のセッションに限る工程は`起動経路`の記録で最上位かを判定する。

## 起動パラメーター

[Claude Codeの組み込み委譲の起動](delegation-start-recovery.md#claude-codeのagent起動)に従う。

### 委譲プロンプトへ含める前提

- 専用の役割文書かagent定義を持つ起動では、依頼文を`agent-toolkit:atk-mode/references/delegation-prompt.md`「委譲プロンプトの構成」で組み、戻り値で1回だけ返し`SendMessage`では送らない契約は定義の側に書く。
- 専用の定義を持たない`claude`・`Explore`・forkの依頼文には、待機した対象の結果も含めてツールの戻り値で1回だけ返す（`SendMessage`は使わない）指示を入れ、forkでは親の背景の情報の再掲を省く。
- 委譲先向けの手順書（`playbooks/subagent.md`）はSubagentStartの通知で読まれるため、依頼文で読み込みを指示する手間は不要である。
- 組み込みの`Explore`と`Plan`は、親のCLAUDE.md、メモリーの階層、gitの状態を引き継がない（同名のユーザー定義かプロジェクト定義で上書きした時は引き継ぐ）。
  このため、判定に使う実行系のコマンド、検証のコマンド、除外する範囲、報告の様式を依頼文に書く。
- 委譲先がさらに読み取り専用の調査やレビューを`Agent`ツールで起動する時は、起動の前にmanaged-tempの中の成果物ファイルの絶対パスを決めて依頼文に入れ、定義ファイルが無ければ完了報告の形式も書く。
  委譲先は全必須項目を含む完了報告を書き、失敗時は本文と診断で保存先を確認し、不具合なら `agent-basics:bugfix` で認可内の修復後に同じパスへ保存して再読する。
  直せない時は成功を返さず、影響・試行・再開条件を完了報告に含める。

## 結果の受け取り方

1. 結果は、同期の起動ではツールの戻り値で、バックグラウンドで起動した直接の子からは完了通知（task-notification）で届く。
   完了通知はターンが終わったことを示すだけであり、検収は届いた本文と成果物の原本で`agent-toolkit:atk-mode/playbooks/delegation-receiving.md`の手順に沿って行う。
   `idle_notification(available)`は待機できる状態を示すだけで、完了の根拠にならない。
2. 成果物ファイルを指定して自分が起動した調査やレビューでは、稼働中に見えた内容を途中経過とし、終了を確かめた後に同じ絶対パスから読み直して、必須の項目を全て含む最終の完了報告であれば受理する。
   終了不明・ファイル欠損時は絶対パス・終了観測・診断を保全して原因を確認し、不具合なら `agent-basics:bugfix` で認可内の修復後に子を再起動せず再観測し、回復できない分の影響・試行・再開条件を続行不能の理由として返す。

### 背景ジョブ完了通知と実プロセスの終了順

バックグラウンドタスクの完了通知を受けた後も同じ`atk agents wait`の実プロセスが残っている場合があり、同じ待機を重ねて発行するのは誤りである（後続の扱いは`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`）。
ホストの停止通知では、外側のタスクと子のプロセスの終了を分け、`agent-toolkit:atk-mode/references/delegation-wait-anomalies.md`「ホストによる背景待機の停止後」で元の出力の回収と監視の再開を決める。

### 完了通知と中継の実行順

`Agent`ツールで新しく起動した子の完了通知は直接の委譲元へ、`SendMessage`で継続した相手の完了通知は最上位のセッションへ届くため、後者の工程は最上位のセッションの中継で再開する。

1. 委譲元は、`Agent`ツールの戻り値から直接の子のagent IDを保持し、通信の宛先にはそのIDだけを使う。
2. 委譲先は通常の完了報告をツールの戻り値で1回だけ返し、`SendMessage`は本書「即時通知の宛先」の即時通知だけに使う。
3. 直接の委譲元でない祖先が子孫の完了通知を受けたら`status`と`result`を保持し、`SendMessage`が公開され、保持した直接の子のIDへの呼び出しが成功する時に限り、同じIDへ逐語で中継する。
4. `SendMessage`の`success: true`やqueuedは送信側の受理を示すだけであり、送信の後に返る完了通知か戻り値が中継先のIDのものであることを確かめて、受信とする。
5. `SendMessage`が未公開か拒否された時と、送信後の結果を観測できない時は再送を控え、担当と権限に収まる工程だけを自分で巻き取る。
   それ以外は、保持した通知の内容、送信先のID、送信の結果、未観測の状況を続行不能の理由として報告する。
6. 子孫の工程を中止、変更、再開させる指示も、同じ手順で直接の子へ送る。
   直接の子が停止していてもまず同じIDへの継続を試し、成立しない時だけ孫以下へ直接1回送り、送信元のエージェント名、役割、指示の理由を本文に書く。
7. 最上位のメインが委譲の木の全体を取り下げるのは、`ListAgents`が使える時に限り、委譲元と列挙された全ての子孫を止めて、その系統に稼働中のエージェントが無いことを確かめる。
   `ListAgents`が使えなければ未知の子孫の不在を確かめられないため、取り下げを始めずに保持したIDと観測を続行不能の理由として報告する。
   取り下げの途中で届いた子孫の完了通知は記録に留め、取り下げを続ける。

## 稼働状態の観測と継続依頼

- `ListAgents`と`TaskStop`は、自分のツールの一覧に公開され、呼び出しが成功する時だけ使う。
- 進捗だけを見る時点では成果物の側を観測し（`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「成果物側の観測」）、`ListAgents`は停滞の判定、催促や巻き取りの宛先の確定、終了の検知の時点で呼ぶ。
  成果物のパスも管理するプロセスも無い時は、進捗の報告を省いて完了通知を待つ。
  完了の直後の委譲先は一覧に現れないことがあり、一覧に無いことは終了を支える参考に留める。
- `Agent`ツールの`output_file`はセッションのJSONLへのシンボリックリンクの場合があり、リンク自体が変わらなくても、リンク先は追記されている。
  観測は`stat -L -c %Y -- <output_file>`（macOSは`stat -L -f %m -- <output_file>`）と`wc -l -- <output_file>`で行い、本文はログの全文でコンテキストを圧迫するため、結果は終了の応答から得る。
- `ListAgents`と`TaskStop`が使えない時は、起動結果の識別子、出力ファイルの末尾の標識（回数の上限付き）、上の観測、保持したプロセスの生存の照会を組み合わせ、更新が続く間は完了とみなさずに催促に留める。
- 同じworktreeで実装担当を引き継ぐ時は、前任の全てのプロセスの終了を、完了報告のツールの終了結果か実行識別子で確かめてから後任を起動する。
  フォアグラウンドの担当が終わった後にプロセスの残存が分かったら、引き継ぎを中止して未完了として報告する。
- バックグラウンドの実装担当を交代する時は、残るバックグラウンドのタスクとエージェントを`TaskStop`で止め、その系統に稼働中のものが無いことを`ListAgents`（使えなければ停止の結果を含む代替稼働観測）で確かめてから交代する。
  未知の子孫の不在か停止後の終了を確かめられない時は、書き込みの権限を移さず、保持したIDと観測を続行不能の理由として返す。
- `Agent`ツールで起動した担当を同じ識別子で継続する条件と、配送できない時の判定は、`agent-toolkit:atk-mode/playbooks/delegation-recovery.md`「継続と新規起動」にある。

## 背景ジョブの起動形（Claude Code）

待機（`atk agents wait`、CIの監視など）の起動と回収は`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「待機区間の構成」で扱い、本節は待機以外の長いコマンドを扱う。

1. 検証やビルドなど時間のかかるコマンドは、Bashツールの`timeout`を上限まで上げてフォアグラウンドで実行し、収まらなければホストのバックグラウンド実行と実行識別子で回収する（検証を保てるなら複数回のフォアグラウンド実行へ分けてよい）。
2. ツールの側でバックグラウンド実行を指定したコマンドにシェルの`&`や`nohup`を重ねると、シェルの終了が先に完了通知として届く。
3. `nohup`や`setsid`による切り離しは、完了通知が届かず監視と本体の寿命が分かれるため、エージェント自身が一時的に応答できなくなる工程に限り、リモートの実行ではSSHの接続も保つ。
4. フォアグラウンドの時間の上限で自動的にバックグラウンドへ移された時は、通知された実行識別子と出力ファイルで回収を続け、監視の期限の到達、通知の未着、終了コードのファイルの未生成は本体の終了の根拠にしない。
5. 終了状態と出力は、起動の結果が示す出力ファイルの絶対パスから得る。
   このファイルは全ての出力と`[exited with code <整数>]`の形の終了状態の行を持ち、再起動で失効する実行識別子と違ってディスクに残るため、待機を引き継ぐ時はこのパスも渡す。
6. 完了か失敗かは、実行識別子によるプロセスの生存の確認と出力ファイルの末尾の終了状態の行で判定し、ファイルが空なら保留する。
   再起動や巻き取りの前に生存を確かめ、生存している間に同じ処理を重ねて起動するのは誤りである。
7. バックグラウンドで実行中のBashコマンド（`run_in_background=true`か、実行環境がバックグラウンドへ移したもの）を止める時は、起動の結果か移行の通知が返したタスクIDだけを`TaskStop`へ渡す。

## 待機中の定期再確認と背景転換

未完了の委譲やバックグラウンドの処理を待つメインは、完了通知を主な解除の手段とし、`CronCreate`、`CronList`、`CronDelete`が公開されている時に限って定期再確認タスクを併用する（`ScheduleWakeup`は`/loop`専用）。
タスクを設定するのはメインだけであり、`Agent`ツールのサブエージェントに設定すると、共有の`CronList`を通じてそのプロンプトが親の会話へ届く。
`agents_server`が起動した委譲先は、独立したセッションのメインとして扱う。

1. agent-toolkitのmod（会話のイベントを処理するFunction hooks module）は、メインの最初の`start`の中か、バックグラウンドタスクを残してターンを終える時にタスクを設定する。
   設定に失敗した時は`start`の結果か次のターンの警告に従う。
2. 3つのCronツールが使えてもmodが自動設定しない環境では、メインが標識を持つタスクの不在を確かめてから設定する。
   設定は`atk wait-schedule`を1回実行し、出力の`cron`と`prompt`を変えずに`CronCreate`へ渡し、`recurring: true`で1件だけ作る。
   プロンプトの1行目は`<atk-auto source="periodic-recheck" kind="periodic-recheck">`だけの行であり、UserPromptSubmitのhookと再開後の所有の確認はこの標識の完全一致を使う。
3. プロンプトは、待機対象を記録から列挙する手段、成果物のパスの特定方法、動的に解決したパスを渡すコマンドの形だけを持ち、IDやパスや残りの工程は発火のたびに記録から読み直させる（静的な写しは進行とずれる）。
   セッションに固有の経過時間の義務（定期の報告、クールダウンの解除、期限の監視など）は、測るコマンドと閾値を1行ずつ`</atk-auto>`の前へ足し、保持したIDを`CronDelete`で消してから同じ標識で作り直し、新しいIDを管理する。
   cronは壁時計の基準でREPLの待機中だけ発火し、繰り返しのタスクは7日で失効し、発火の時刻には揺らぎがある。
4. タスクIDはプロンプトの外で保持し、未完了の対象がある間は同じタスクを使い続ける（modのタスクのIDは`CronList`の標識の完全一致から得る）。
   再開や圧縮の後は保持したIDが`CronList`に実在するかを確かめ、IDを失った時は標識で所有のタスクを1つに特定できる時だけ再利用か削除へ進み、重複の作成を避ける。
   未完了の対象か経過時間の義務が残る間は、未実施の定期確認を「該当なし」へ変えずに保つ。
5. 発火した時は、blocking waitとそのバックグラウンドタスクが所有していない待機対象の記録と完了通知を確かめ、終わった対象を受領の手順へ移す。
   全てが未完了なら閾値に達した経過時間の義務だけを行い、無ければ報告を出さずに待機を続け、発火そのものは完了や停滞の判定の入力に使わない。
6. `run_in_background`を指定していないBashコマンドが実行環境の判断でバックグラウンドへ移った時も再確認の対象にし、移行の結果が示す出力ファイルを、同じパスを含む完了通知の後に`Read`で読んで結果を確かめる。
7. 通知の仕組みが無く同じターンで回収する時は、出力ファイルの末尾の終了の標識を回数の上限付きで確かめ、得られなければ`ListAgents`か代替稼働観測で確かめ、確定できなければ書き込みの権限を移さずに続行不能として報告する。
8. modは、全ての待機対象の結果を回収した後のStopの処理で、共通のプロンプトと一致する非durableな所有のタスクを消す（process-loopの統括と`atk run-skill`のセッションは本書「ターンの終え方」でメインが消す）。
   一部だけが終わった時、バックグラウンドの処理が続く時、未配送の完了通知か`agents_server`の未回収の結果が残る時、回収の拒否や失敗の時は、タスクを保つ。
9. modが無い環境で自分が設定したタスクは、全ての対象の終了を確かめた時点で`CronDelete`し、消えたことを確かめる。
10. Cronのツールが使えない時と`atk wait-schedule`が失敗した時も、`sleep`、ビジーループ、バックグラウンドのタイマー、独自の待機の仕組みで代えるのは誤りであり、事象が届かない障害の時に打ち切る契機を失う。
    同じセッションの再開が保証されれば完了通知を待ってターンを終え、それ以外は公開された待機の手段で同じターンに回収する。

## 長時間待機前の会話圧縮

Claude Codeのメインが、他の担当やCIの監視の結果を後続の工程の入力として待つ時の手順であり、予約の時機と工程の状態は呼び出し元の手順書に従う。
独立して進められる先の工程を始めてから待機へ進み、圧縮の後の復元は`agent-toolkit:atk-mode/references/work-contract.md`に従う（要求と認可の確定には要約でなく原本を使う）。

1. `mcp__plugin_agent-toolkit_agents_server__compact_conversation`が無い環境では、前提が成り立たなかったことを引き継ぎ記録に残して通常の待機へ進む（Codexは本手順の対象外）。
2. このツールを引数なしで1回呼び、予約の受付と圧縮の完了を区別して、圧縮が終わるまで予約を1件に保つ。
3. `agents_server`の結果は、Bashのバックグラウンド機能が公開されていれば、引数なしの単独の`atk agents wait`をバックグラウンドで起動して待つ（`session_id`は結果の突き合わせだけに使う）。
   バックグラウンド機能が無い時（SessionStartがバックグラウンド実行の無効を通知し、Bashの公開入力に`run_in_background`が無い時）は、フォアグラウンドのBashへ`timeout=600000`を指定して同じターンで回収する。
   CIの監視では、起動済みの`wait_ci.py`のタスクを保つ。
4. バックグラウンドの待機では今のターンを終えて、届いた完了通知と保存された全ての出力から終了状態を回収し、フォアグラウンドの待機ではCLI自身の期限で返る終了コードを回収して、終わっていなければ同じコマンドで待ち続ける。
5. 完了通知を受けたら、復元した要求のうち受け取った結果で満たされたものと残るものを分け、同じ工程から再開する。
   圧縮が失敗しても担当の作業と監視は続け、予約の失敗、圧縮の成功、待機の結果はそれぞれの既存の記録へ残す。

バックグラウンドのBashで待つメインと、`agents_server`が起動した委譲先（Claude・Codexとも全ての起動の区分）は、hookと所有のバックエンドが同じ圧縮を自動で予約する。
条件は、バックグラウンドのタスクが60秒以上続き、使用量が400,000トークンと文脈の上限の40%の大きい方以上で、ターンの間であることである。
自動の圧縮は同じバックグラウンドの待機で1回までであり、自動の予約が働く場合に手動の予約を重ねる必要は無い。
単発のタイマーとターンの完了通知を使い、続けてのポーリングや圧縮のためだけのLLMのターンを足すのは避ける。

## 返す報告に含める項目

ツールの公開と呼び出しの結果、保持したagent ID・実行識別子・出力ファイルの絶対パス、定期再確認タスクのIDと処置、圧縮の予約と結果、続行できない理由を返す。
