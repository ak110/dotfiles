# 反映後の観測と報告前の確認

目的: 作業`process-wi`のメイン（統括かリポジトリ担当）が、公開工程の後か観測だけが残るAWIの再開時に反映後の挙動を観測して採否を確定し、ユーザーへ効果を確かめた成果だけを採用として報告する。
入力は、公開担当から受け取った延期`adopt`の未終了集合、統合結果の`保存した計画ファイル`、統合時に`終了しない`と判定した観測のみの項目である。
終了条件は、全ての対象が採用・再実装への差し戻し・待機のいずれかに保存され、その保存を本書「報告前に確かめる保存状態」で確かめた時点である。

統括が選定済みの項目の公開後の観測をレーンから引き取る場合は、統合許可より先に選定へ担当を記録する。
次のコマンドで選定原本と所有控えを更新し、レーンへ対象を伝える。
統括の会話IDでなくレーンの作成時に使った所有IDを渡す。

```text
atk run-script pick-wi-check -- <選定YAML> --handoff-observation <WI名> --lane-session-id <対象別のlane_session_id> --output <選定YAML> --work-dir <統合先worktree>
```

再開位置と採否は変えない。
レーン自身が観測を再開する場合には指定しない。

## 延期adoptと反映後の観測

本節は、要件そのものが実環境での観測を求める未終了の項目を扱う。
実装と統合を終え、反映後の完成条件の観測だけが残る項目は延期`adopt`とする。
固有の指示が公開工程の後の`adopt`を求める項目と、バージョンの更新を完成条件に持つ項目も延期の対象とする。

1. 未達条件の延期を選ぶ前に、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」と`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と承認」を適用する。
   - 後日の対策効果が完成条件の場合も、適用条件・観測の機会と、待てば解決する見込みの根拠を特定して再開記録へ残す。
     cooldownを使える境界は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「依存と冷却時間」「着手不能要因の分類」にある。
   - 見送り、追加の認可、見込みの立たない外部変更待ちの判断は、`agent-toolkit:atk-mode/references/delivery.md`「個別UWI」に従う。
   - 実装・検証の成功と後日の効果を区別し、適用の機会が無い項目は効果未確認として保つ。
   - 通常の効率改善へ長期の観測を一律に足すことと、環境の制約だけを理由に人手の実機確認を完成条件へ足すことや個別のUWIを登録することは、対象外とする。
   - 実施できる範囲の検証を終え、その結果と確かめられなかった範囲・限界を完了報告へ書く。
     既知の不具合と明示された要件の未達は、未達事項として本節の再開の手順で扱う。
2. 観測できなかった理由、足りない前提、前提を妨げる状態の生成元・起動元・起動の契機、未確定の範囲から、完成条件ごとに前提を整えられる主体を判定する。
   エージェント自身や常駐のプロセスが作った状態は、OSの実行ユーザーが同じでも人間が起動した状態と区別し、生成元が未確定の状態や人間が通常操作する入力・環境であることだけを根拠にユーザーの操作が必要と判定しない。
   ユーザーに操作を求める前に自己観測の可否を判定する。
   - 実装・設定・公開された起動手段から必要な入力、トリガー、対象ブランチ、実行順序を調べ、同じセッションで準備でき、既存の指示と権限で操作できるか確かめる。
     追加の認可が必要な場合だけユーザーへ確認する。
   - コマンドの起動に加えて、PR作成や特定の入力など、workflowやhookの発火条件を満たせるか確かめる。
   - 人間が観測する完成条件や人間が操作する入力・環境でも、入力を作って結果を観測する手段を探す（観測主体は`agent-toolkit:atk-mode/references/awi-body.md`）。
     手段には、自作の対話セッションへの入力と画面・ログ取得（tmuxや端末操作）、同じセッションでの配布後のCLIやauto modeの応答確認も含む。
   - 対話CLIは、権限確認を省くオプションや別の権限モードを付けずに起動する（auto modeの許可ルールが自己操作を許すのはその起動に限るため）。
   - 自作の観測用CLIだけを空の環境で起動し、通常のホームと元の認証情報を使う。
     POSIXではペイン内も含め、`env -i HOME="$HOME" PATH="$PATH" … claude`（または `codex`）で、`…` に `TERM`、ロケール、ユーザー、シェル、デスクトップ接続に必要な変数だけを指定する。
     Windowsでは子の環境を空にして `USERPROFILE`、`PATH`、`SystemRoot` など必要な値だけを渡す。
     どちらのOSでも観測ごとに識別子を決めて `AGENT_TOOLKIT_AGENTS_SERVICE_SCOPE` に渡し、同じ観測で起動するCLIも同じ識別子を使う。
     通常の配布物であっても、観測用の管理サービスは通常側から分かれる。
     共有daemonが観測対象でなければCodexは `codex --no-daemon` で起動する。
     `CODEX_HOME`の分離だけではCLI終了後もdaemonが残る。
     tmuxは観測専用に作ったサーバーだけを観測後に終了する。
   - 入力手段があることと実際に結果を受け取れたことを区別し、版、入力、権限、結果、終了ステータスを記録して、成功は実際に受け取った結果から判定する。
   - 実行記録などからユーザー自身が起動したと分かるセッション、ユーザーしか入れない本番環境、新たな認可が必要な操作は、自己操作の範囲外とする。
     自作セッションの操作権限は、ユーザーの既存セッションには及ばない。
   - 手段が成り立たない項目は採否を確定せず、不足する前提と根拠を手順5に記録する。
     ユーザーの操作か追加の認可が無ければ前提を整えられないと確かめた項目だけ、完成条件を変えずに手順4のUWIで前提の充足を求める。
     自分で前提を整えて次回観測できる項目は、実装を繰り返さず観測へ回す。
3. 公開担当の処理が終わったら、`agent-toolkit:atk-mode/roles/session-termination.parent.md`から受け取った延期`adopt`の未終了集合について、稼働環境への反映の終了ステータスと対象HEADを確かめて観測する。
   - エージェントから届く環境では、新しいプロセスで残りの完成条件を直接観測する。
   - ユーザーしか届かない場合は、手順4のUWIで得た観測結果と証拠をエージェントが完成条件と比べて判定する。
   - 条件を満たした項目は、検収済みの実装commitを関連付けた`atk wi adopt`（`--target-repo`に主作業ツリーの絶対パス。実装差分が無ければ`--commit`を省き、観測の根拠をnoteに書く）で採用を確定する。
   - 満たさなかった項目は採用せず手順7へ進み、観測できなかった項目は採否を確定せず次の手順へ進む。
4. 統合結果の`保存した計画ファイル`にある各計画の`related_wis`を、`atk wi show <ファイル名>... --summary-only --target-repo=<対象リポジトリの絶対パス> --skip-pull`で確かめる（公開担当の起動を省いた場合も行う）。
   - 見出し行`### <ファイル名> [<状態>]`が`processing`の項目の計画を、`atk plans checkout`で`~/.claude/plans`へ戻す（同名のファイルが既にあれば除く）。
     観測で完成条件を満たせなかった項目の計画は、保存済みのまま残す。
   - 引き継ぎ記録には、`atk run-script plan-progress -- <記録先> --handoff`で手順5の実装・観測・再開の値を残す。
   - 明示された要件を満たすのに本人にしかできない操作か追加の認可が必要で、その結果で採否や対処が変わる項目だけ、計画を戻した後にUWIを保存する。
     到達できない環境があることだけを理由に観測を依頼せず、届く環境と試験・CIで完成条件を判定し、満たさなければ再実装へ戻す。
     起草入力には、元WIの識別子、現行の完成条件と有効な変更要求、残る観測、再開記録の所在を含める。
     保存前に`agent-toolkit:atk-mode/references/draft-semantic-review.md`に従い、検収者が元WIから選んだ必要な結果と原稿を独立に比べる。
     書式は`agent-toolkit:atk-mode/references/uwi-format.md`に、保存の条件は`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」に従う。
     投入は`agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入」に従う。
   - UWIの本文には、元AWIのファイル名、足りない前提と自己操作が成り立たない根拠を書き、操作の主体と選択肢を`agent-toolkit:atk-mode/references/uwi-format.md`「ユーザーへ操作を依頼する場合」で振り分ける。
     手段があり認可だけが足りない工程では、エージェントが行う認可を求め、認可後の操作・観測・証拠の保存はエージェントが担う。
     ユーザーしか届かない工程でユーザーの操作を選ぶ場合は、その操作内容と返してほしい観測結果を書く。
     観測できない場合に完成条件の扱いを変えるにはユーザーの明示の判断が必要な旨も書く。
     ホストやサービスが操作を拒否した場合は、`agent-toolkit:atk-mode/playbooks/permission-denial.md`へ進み、同資料の基準で拒否の解除を判定する。
   - 起草から回答の受領まで同じ観測結果へ対応付け、配備後の結果や要求の変更があれば現行の原本と証拠から残る観測を更新する。
     UWIの保存だけでは観測完了とせず、回答の受領時に元の各完成条件の結果を既存の証拠と合わせて確かめ、手順3の採否か再開へ進む。
     既に成功した操作は再依頼せず、本人にしかできない残る観測だけを手順と回答項目へ対応付ける。
   - UWIの保存の成功を確かめてから、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「状態と依存」の承認型UWIと元項目の規定に従い、元AWIの`depends_on`へUWIを加えて`inbox`へ戻す。
     手順5の再開記録には、UWIのファイル名と、回答後に観測する主体・必要な前提・結果の取得方法を追記する。
     UWIの保存に失敗した項目は`processing`のまま残す（待つUWIが無いまま依存を設定すると、再開の契機が失われるため）。
5. 観測だけが残る未終了の項目（観測で完成条件を満たせなかった項目を除く）は、計画の有無にかかわらず、本書「反映後の観測の再開記録」の手順で記録する。
6. 観測できる最も早い時刻が現在より後の項目は、待たずに、追記の成功を確かめてから`atk wi return-to-inbox <ファイル名> --target-repo=<対象リポジトリの絶対パス>`で`inbox`へ戻す。
   続けて`atk wi edit <ファイル名> --cooldown-until <その時刻> --target-repo=<対象リポジトリの絶対パス>`で再処理の抑制期限を設定する。
   それ以外の観測待ちの項目は、必要なUWIと依存を手順4で保存するまで`processing`のまま保つ。
7. 観測で完成条件を満たせなかった項目は、観測結果を引き継ぎ、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「既存WIの再開」の`--reopen-wi`と`--new-plan`で同じ巡回の計画から再開する。
   担当側で満たせない外部の前提で進められない場合だけ、試した代替手段と結果を`reimplement`で記録し、終了区分を`終了しない`として、記録の成功を確かめてから`atk wi return-to-inbox <ファイル名> --target-repo=<対象リポジトリの絶対パス>`で戻す。
   追記に失敗した項目は`processing`のまま保つ。

## 反映後の観測の再開記録

詳細をmanaged-tempのファイルへ書き、`atk wi record-observation <ファイル名> <needs-verify|reimplement> --body-file <絶対パス> --target-repo=<対象worktree>`でAWIへ追記する。
見出しと再開区分はCLIが付ける。
計画にも残す場合は保存した節を転記する。

- `needs-verify`（反映後の観測だけが残る）: 実装commit（差分が無ければ充足の根拠）、残る完成条件、観測手段と起動条件・実装の所在、観測できる最も早い時刻（タイムゾーン付きISO 8601または不明）、計画（保存先の相対パスまたは計画なし）。
- `reimplement`（`再開区分: 再実装へ戻す`）: 観測した実装commit（無ければなし）、満たさなかった完成条件、操作と実際の結果、観測の記録の絶対パス、計画。

## 報告前に確かめる保存状態

報告原稿と対象別の結果を確定する前に、今回処置する全てのWIを現在のキューのfilenameと状態へ対応付けて確かめる。
母集団は選定の原本、各レーンの延期と終了しない集合、メインの直接処置、今回追加した処理対象WIから得て、別の消込み台帳は作らない。

1. 対象ごとのfilename・state・ready・blocked_reasonを母集団へ対応付ける。

   ```text
   atk wi list --state=all --jsonl --skip-pull --target-repo=<対象worktree> --target-branch=auto
   ```

   `--target-branch=auto`は、系統を登録したリポジトリで処理中の系統だけを母集団にするために付ける（系統を登録しないリポジトリでは限定しない）。
   複数リポジトリでは各対象worktreeで取得し、所属リポジトリとfilenameの組で今回の処置の原本と比べ、本文や計画の再開情報が必要な対象だけを`show`などで補う。
2. adopt・rejectの保存済みの状態と、正当な延期の未達条件・再開記録・計画の復帰・必要な依存か冷却の保存の成功を確かめる。
   processing、着手できるinbox、対処が必要な不正なmetadata、未最終化のレーンは未完了として保つ。
   依存や冷却が有効でも、必要な再開情報の保存を確かめられなければ未処理として保つ。
3. 不一致は既存の観測・保存の手順へ戻して処置し、今回進められる工程を続ける。
   正当な外部前提の不足だけが残る場合は、対象・未達条件・解除条件・再開先と保存状態を完了報告へ反映する。
4. 公開・CI・統合の成功とWI全体の完了を区別し、処理の意図や自分で作った進捗の要約は保存状態の証拠から除く。
   原本・対象別list・保存成功の確認を既存の検証記録へ残し、その値を報告原稿の入力とする。

返す報告に含める項目: 採用した項目と根拠、再実装へ戻した項目、観測待ちで戻した項目と観測できる最も早い時刻、保存したUWIと依存、保存状態の確認結果（対象別listとレーンの最終化）、残る外部前提。
