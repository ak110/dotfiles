# 登録全体のAWI処理の結果と終了

`agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md`の統括が、全対象の処理の後に対象別の結果を確定して報告し、担当とwriterの終了を観測して終える手順書である。
検収は全対象の結果を確定し、起動した全ての担当とwriterの終了を観測した時点で終わる。
対象別の結果は完了報告に書き、ファイルへは保存しない（結果ファイルを読む処理は無い）。

## 結果と終了

起動の目的は、統括セッション自身が担当する`agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md`と本書の工程の完遂であり、正当な先送りを結果へ記録した終了も含む。
目標の達成は本節の最終結果と既存の工程の証拠で判断し、回復できる残工程があれば続ける。

1. 処理を始めた担当とwriterの終了を`atk agents wait`と`atk agents list`で観測してから、所有の解放と回収へ進む。
   同じ対象を複数の担当が書かないよう、配下の担当の終了を確かめてから統括自身の作業へ切り替える。
2. `agent-toolkit:atk-mode/playbooks/wi-submission.md`で永続の受付と独立した監督への所有の移管が成立した投入は、今回の製品writerと区別する。
   今回の製品writer・リポジトリ担当、公開CI、報告は本節どおり終え、独立した投入の終了観測・報告・受付資源の回収は受付先の監督が所有する。
   受付票を報告に含め、投入が未完了であることを明記する。
   単なるPopenの成功、委譲のsession IDの発行、未確認の受付はこの区分に含めない。
3. 続行できない対象は理由と再開位置を残し、独立した他の対象は処理する。
   統括は実行の完了報告と報告用UWIを1回だけ作り、全対象の結果を集約する（配下のリポジトリ担当は報告用UWIを作らず、公開結果・CI・残工程を返す）。
4. 今回の処理を終える前に、対象ごとの`status`と`remaining`を確定する。

   - 対象は今回の対象一覧の`target`に限り（系統を登録しないリポジトリでは`target_repo`と同じ値）、明示resumeでも今回の集合だけを扱う。
   - `status`は`completed`、`incomplete`、`blocked`、`pending`のどれかである。
     `completed`は、今回進められる作業と処理済み部分の公開・CIの検収が終わったことを表す。
     必要な判断を終え、正当な先送り（有効な未来の冷却期限、未回答のUWI、外部の先行項目への依存、ユーザーが許した後回し）に当たる項目だけが残る場合も含める。
     WI自体の完成とは区別し、残す項目・未達条件・解除条件・再開先を`remaining`へ書く。
   - 今回進められる作業、対象全体のprocessing、対処の要る不正なmetadata、未統合のレーン、未完了の公開工程があれば`incomplete`、続行不能なら`blocked`、未着手なら`pending`とする。
     `incomplete`は残る未完了の工程を表す（終えた統括を同じ会話で自動で再起動する要求とは別である）。
   - 内部の依存待ち、欠落か失敗の返却、未停止のwriterは正当な先送りから外し、今回の工程として扱う。
   - 各対象の残工程、再開先、続行不能の理由を`remaining`に含める。
5. 次の1回の実行へ回せるのは、残る工程が手順4の正当な先送りに当たる場合、続行不能の場合、統括が利用上限かユーザーの停止で中断された場合に限る。
   その場合は実態に合う状態と残工程を報告して今回の統括を終える。
   計画の区切り・目標時間・残り時間・作業量・コンテキスト使用量による持ち越しは、`agent-toolkit:atk-mode/references/conduct.md`「完遂と先送り」に従って行わない。
   区切りごとに統合する計画も、統合・公開・CIの検収の後に同じ実行で次の区切りへ進む。
   有効な延期の条件と開始側の判定が起動を抑えるため、冷却期限は延期の条件がある項目だけに付ける。
6. 各対象に固有の終了条件、報告と終了観測を検収し、最終の`status`と`remaining`を確定する。
   - 統括のcwdと異なる対象も、対象worktreeの`AGENTS.md`などのプロジェクト規範が終了時に求める資料を取得する。
   - 所要時間と次回の目標達成に要る改善を終了条件とする対象では、全候補・全工程・合理的な内部の同時数と共有の検証能力、未確認の前提を含む見込みを実測と残量から検収する。
     リポジトリ担当へ任せた場合もその根拠を受け取り、対象に固有の条件が未達なら今回進められる改善を続ける。
     局所の実装・公開の成功と、全体の達成見込みの成立を区別する。
   - 選定YAMLを持つ各対象では、結果の確定と終了の前に`atk run-script pick-wi-check -- <選定YAMLの絶対パス> --require-integrated`を実行し、選定全体の統合状態を読み取り専用で検収する。
     後段を含む未統合のレーンが返れば、その工程を続けるか、対象・具体的な理由・解除条件・再開先を`remaining`へ書き、`completed`へ短絡することは避ける。
     入力の不正や読取りの失敗は統合完了とみなさず、原本を回復して検収し直す。
   - 各レーンの完了は、所有登録のphaseが`finalized`であることで個別に確かめる（`git-integrated`は統合の途中の段階であり、計画の保存とWIの採否まで終えた`finalized`で完了とする）。
   - `agent-toolkit:atk-mode/playbooks/process-wi-observation.md`「報告前に確かめる保存状態」を実行し、今回の全対象（各レーンの選定WI、延期と差し戻し、直接処置、追加分）を現在のキューへ対応付ける。
     検収の失敗や保存の未確認を完了へ変えず、同節で確かめた保存状態を報告の入力にする。
   - `completed`でも正当な延期があれば、対象・未達条件・解除条件・再開先を`remaining`へ列挙する。
7. 確定した結果が、既存の公開・CI・レーンの検収記録と対応することを確かめる。
   巡回を続ける場合は巡回手順の区切りに進み、終了する場合は必要な報告の後に最上位セッションの終了手順へ進む。
8. 既存のWIを同じ巡回で再開する時は、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」の既存WIの再開の公開操作へつなぎ、元レーンと初回配分を保って未統合へ戻す。
   保った資源の再利用か回収後の再準備から、現在のレビューHEADで統合し直し、今回の最終化と選定の原本の更新が終わったことを確かめる。
9. 完遂の判定は訂正後の最終の結果と既存の工程の証拠に基づき、訂正前の記載や正当に延期した項目があることだけを未達としない。
   Stop hookが終了を遮断したら、遮断の理由が示す不足を確かめ、結果の`remaining`を1件ずつ、今回進められる工程と手順4の正当な先送りに分ける。
   今回進められる工程は再開し、正当な先送りだけが残る場合は、項目ごとに保存したWI・延期の状態と解除条件への対応を確かめてから、遮断の理由が求める終了工程を実行する。
   遮断を解くためだけの追加のレビューや同じ検証の繰り返しは行わず、不足か不一致がある範囲を補う。
10. 先行工程を次の巡回へ回す時は、それを先行条件にしていた後続の全工程の先行条件を、`agent-toolkit:atk-mode/playbooks/process-wi-lane-resources.md`「後段レーンの先行調査」の区別で判定し直す。
    書込競合だけで後段にした工程など先行成果を要さない工程は、先行の統合を待たずに統合先の最新HEADから専用worktreeを作成し、今回の巡回で実装・検証まで進める。
    次の巡回へ回す後続の工程は、`remaining`へ工程ごとに先送りの理由を書く。
11. 続行不能の時も、実態に合う状態、理由と残工程を報告して制御を返す。
    起動済みの担当やwriterが未終了なら、資源を保って終了を待つ。

返す報告に含める項目: 対象ごとの`status`・`remaining`、直接担当とまとめ担当・個別担当の割当と理由、正当な先送りと解除条件、独立した投入の受付票。
