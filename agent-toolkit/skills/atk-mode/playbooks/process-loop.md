# 登録リポジトリを巡回する

目的: 巡回のセッションが登録リポジトリのWIを処理し続け、ユーザーが個別に起動しなくても対象ごとの成果が公開まで届くようにする。
ユーザーか `atk wi process-loop` が名指しした時だけ使う。
CLIは起動・再起動と制御、セッションはWIの処理と更新を担う。

## 巡回する

選定・レーンの実装と統合、公開・CI検収と反映は並行して進める。
候補の取り込みは`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「開始後に追加されたWIの確認」に従う。
新着不良・マージ用AWIは選定と進捗へ対応付け、担当済みの成果を回収し、新着の存在だけで公開を止めない。
その時点のベースブランチを通常どおりpushし、pushしたcommitのCIをバックグラウンドで確認する。
公開中に統合した変更は次のpushに入れる。

1. `atk config repos list` で登録した対象のパス、系統、直接編集と検証の条件を確かめる。
   全体作業契約には目的、現行要求と保つ対象だけを書き、再開した場合は既存の検証・公開の結果を読み戻す。
2. 起動直後と上記の取り込み契機でキューを同期し、処理可能なWIを原則すべて処理候補にする。
   初回に保存した開始時集合JSONと選定原本を本人再開後も引き継ぎ、追加分を追記する。
   必要なら `atk wi check-alerts` でCIの失敗を別に確認する。
   GitLabの登録と`github_issues`を有効にしたGitHubの登録では、初回の選定前と空のキューを再確認する時に
   `atk wi check-alerts --periodic --target-repo <登録パス>`で定期確認する。
   GitLabでは定期CIの失敗を含み、GitHubではCIの失敗とIssue・PRを確認する。
   コマンド側で同じ登録の確認間隔（`--alert-interval`、既定1800秒）と`--no-alerts`を判定する。
   省略された場合は失敗なしとは判定せず、手動の確認で代用しない。
   新たに保存したWIもキューの確認に含める。
   常駐では候補の有無にかかわらず、30分点検の時機に達したら待機の前に[継続中の公開と更新](../references/orchestrator-runtime.md#継続中の公開と更新)に従って点検する。
   次の公開単位が無くても、同節のリリース判定から対象プロジェクトの手順へ進む。
   ホスト本体のバージョンと稼働開始からの経過時間も手順5の条件で点検し、公開の有無によらず本人再開を判定する。
   期限前に終了する時の引き継ぎは、`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「公開状態の検収と再起動」に従う。
   次の担当が決まらなければ未達の見込みとして報告する。
   dotfilesの点検では、稼働ホストで `atk serve versions` を実行する。
   `docs/development/operations-services.md` の手順と同じく、未導入のサービスだけを対象から外す。
   一致は通知せず、不一致と取得不能を区別して対象・バージョン・再確認の操作を伝える。
   CI成功済みの前回の公開の反映が残っていれば、候補の有無にかかわらず、待機・終了や次の公開より先に手順4・5の未完了段階から再開する。
   報告の保存時か本人再開の境界があれば、選定の判定を先に終え、[前区間の振り返り](#前区間の振り返り)を独立に始める。
   候補がある場合は手順3の選定後、候補がない場合は空と判定した後に行う。
   進められる対象が1つも無ければ、常駐では対象ごとに `atk wi wait --new-since <その対象の開始時集合JSON> --target-repo <対象> --timeout <次の30分点検までの秒、最大1800>` をバックグラウンドで起動する。
   回答待ちのUWIがあれば `--uwi <正式ファイル名>` も付ける。
   `待機中: <タスクID>` の行でターンを終え、完了通知か時間切れで手順2へ戻る。
   1件でも検知したら他の待機は止めてよい。
   単回実行では「中断と再開」に従って完了報告して終了する。
3. `agent-toolkit:atk-mode/playbooks/process-wi.md` で対象ごとの設定・認可と候補を確認し、選定、専用worktree、実行レビュー、統合、公開を進める。
   複数対象の配分と担当への受け渡しは `agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md` を使う。
   登録元checkoutは直接編集せず、対象と系統ごとの専用作業ツリーから各レーンを作る。
   通常の担当を起動する前に[後続に使う改善の先行](#後続に使う改善の先行)の要否を判断する。
   常駐では取り込み契機ごとに[処理可能なWIの追加](process-wi-immediate-fix.md#開始後に追加されたwiの確認)を判定し、対象別のレーン上限を守って担当を見直す。
   同じファイルを編集する候補は既存レーンへの合流を先に比べる。
   処理中に30分点検の時機に達した時も手順2と同じ対象を点検する。
   GitLabの定期確認には手順2と同じコマンドを使い、照会できる時機を判定する。
   新規の失敗は既存の新着WIの選定へ渡し、進行中の作業は中断しない。
   既存レーンに加えられる候補は上限を理由に延期しない。
   致命的な不良は区切りを待たせない。
   統括は対象ごとに[独立した公開単位](process-wi-publishing.md#独立した公開単位)で公開担当を起動し、公開待ちでも選定・起動できるレーンの処理・統合を続ける。
   公開単位の検収では、進捗点検と同じく[開始と振り分け](process-wi-all-repos.md#開始と振り分け)の手順7で担当の過不足を見直す。
   dotfilesへの公開は、`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「独立した公開単位」に従う。
4. dotfilesは選んだ公開単位ごとに、CI・必要なリリースの成功を検収した直後、次の公開を始める前に利用環境へ反映する。
   リリースをまだ行わないdevelopの公開単位も反映する。
   [公開状態の検収と再起動](process-wi-publishing.md#公開状態の検収と再起動)の公開OID・配布物のバージョンと未完了の段階を保存し、統括の利用環境で `update-dotfiles` を実行する。
   公開担当が同じホストで成功済みなら記録を再利用する。
   終了0と更新内容を確かめる。
   失敗は `agent-basics:bugfix` で対処し、更新から再開する。
   成功済みのpush・リリースは繰り返さない。
5. 更新後、Claude Codeでは `apply_runtime_changes` でプラグインと必要なMCP（`agents_server`・`pyfltr`）の反映を予約する。
   予約を記録してターンを終え、反映結果を受け取って読み込んだバージョンと再接続を確かめる。
   受付・失敗・照会不能は反映済みにしない。
   他のホストでは既存の更新・再接続手段を使い、本人再開で読み込み直すものは再開後に確かめる。
   反映結果、導入済みのバージョン・MCPの接続と `atk serve versions --published <そのホスト向け公開OID>` の一致を確かめ、同じ会話で続ける。
   30分点検での本人再開の判定は、[更新のための本人再開](process-wi-all-repos.md#更新のための本人再開)に従う。
   運用対象と未導入の区別、再起動、確認操作はdotfilesの `docs/development/operations-services.md` に従う。
   一致しないか証拠が得られなければ未完了の段階へ戻る。
   本人再開を使えないホストで強制終了しない。
6. 単回実行では「中断と再開」に従って完了報告して終了する。
   常駐の成果報告は[作業完了報告](report-completion.md#工程)に従う。
   報告の保存時に[前区間の振り返り](#前区間の振り返り)の境界を残し、同じ会話で手順2へ戻る。
   終了するのは「中断と再開」の条件に当たる時だけである。

### 後続に使う改善の先行

巡回の後続担当が使うツールや規範の変更を先に届けると、後続の品質や効率を改善できる場合に検討する。
agent-toolkit、agent-basics、後続担当が使う検証ツールなどの改善を候補とし、登録先の名前では限定しない。
改善幅・件数と後続での効果を、並行着手の遅れや公開・CI・利用環境への反映・再開を分ける負担と比べ、利点が見合う場合に採る。
改善が小さく少数であれば通常の並行処理を選んでよい。

1. 処理可能な全候補を今回の選定に保ち、その全件と追加時の通常の算定でレーン数の上限を決める。
   依存・再開位置・書込競合を保ったまま、既存の上限内で独立して公開できる先行レーン群を配分できる場合に限り、先行群を先に起動する。
   段階ごとに上限を数え直さず、後続を新着扱いや次回送りにしない。
   統括は初回・追加・再開の起動や追送の直前に、選定原本と現在の反映状態を確かめる。
   反映確認の前に新たに実行へ渡すのは、先行群と統括が[即時対応](process-wi-immediate-fix.md#即時対応)に当たると判断したWIだけである。
   即時対応を委譲する場合は、対象の着手可能な集合へそのWIを加え、通常の後続は加えない。
   既に着手した作業は止めない。
   同じ対象に先行と後続がある場合も、全候補の原本とは別に、対象ごとの着手可能なWI名と後続への切替条件をリポジトリ担当の既存の`追加指示`で渡す。
   稼働中の担当に追送する場合も変更後の着手可能な集合を示す。
   未着手の後続は、進捗点検、CI検収直後、本人再開時にも起動・追送しない。
2. 先行群を[独立した公開単位](process-wi-publishing.md#独立した公開単位)として検収し、公開とCIの成功、後続担当が使う実行環境への反映を確かめる。
   dotfilesは「巡回する」の手順4・5を使う。
   公開の成功、反映の予約、統括だけの稼働中のバージョンの確認では条件を満たさない。
   後続が使う配布物のバージョンと必要な接続の反映を確かめてから、後続担当をそのバージョンで起動する。
   稼働中の担当に後続を渡すのは、その担当も新しいバージョンを読み直したと確認できる場合に限る。
   確認できなければ既存の終了・引き継ぎを経て後任を起動する。
3. CIの失敗や未反映は既存の公開・更新の復旧手順で是正し、既存の選定と引き継ぎ記録に現在の段階を残して、未完了の操作から再開する。
   反映の見通しが立たず先行を続ける不利益が大きい場合は、取りやめの理由・未完了分を記録し、先行の成果を実際に必要とするWIを除いて通常の起動順に戻す。
   保留するWIの依存と残作業は保持する。

## 中断と再開

- `abort`による中断要求の通知かユーザーの中断を受けたら、新たな対象の選定を止め、書き込み担当と公開の結果を回収し、未達の工程を記録して完了報告後に終了する。
- 追加指示の通知を受けたら、現在の会話で適用する。
- `completion_report: true`を付けた完了報告と、その後の`atk agents-exit-session`による終了は、`--once`の単回実行、`abort`、ユーザーの中断、会話を替える交代の時だけ行う。
  更新のための本人再開では完了報告を作らず、再開を予約してから終了する。
- 再開時は候補・認可・検証・操作結果を読み戻し、成功した公開と保存を再利用して未完了工程から進める。
  引き継ぎ記録は[更新のための本人再開](process-wi-all-repos.md#更新のための本人再開)の項目から再開に要る現在の状態を保ち、完了した項目は除く。
- Claude Codeの再開は会話IDを指定する。
  起動元が事前に同じ会話を圧縮し、統括は復元通知に従って保存済みの記録を読む。
  圧縮だけが失敗・時間切れした場合、起動元は記録を残して圧縮なしで同じ会話を再開する。
  元の会話の停止を確かめられない場合は再開せず、同じIDの再開操作を案内する。
- 追加指示、中断、再開の予約は `atk wi process-loop --help` を参照する。
- 手順5の条件で本人再開する時は、同じ会話IDを予約し、原子的な操作の完了と記録の保存後に配下を止めずに再開する。
  [前区間の振り返り](#前区間の振り返り)の境界だけを引き継ぎ、振り返りは始めない。
  利用上限と予約なしの異常終了の引き継ぎは[登録集合](process-wi-all-repos.md#登録集合)に従う。
- 会話を替える統括の交代では、配下のwriterと公開の結果を回収して通常終了の所有を解放して資源を回収する。
  引き継ぎ記録に次の起動への指示を残し、完了報告を保存・送達して`atk agents-exit-session`で終了する。
  別セッションの起動や再開はCLIが担うため、手動で行わない。
  統括のモデルを変更する操作は、操作時の承認を経る。

## 前区間の振り返り

報告の保存時と本人再開の境界で、既存の単発振り返りで前区間を処理する。
今の巡回を妨げる不具合は区切りを待たず対処し、振り返りの完了を再開・終了の条件にしない。

1. 報告の保存時か再開の予約の直前のUTC時刻（小数秒付きISO 8601）と対象のホスト・会話IDを既存の作業契約の引き継ぎに残す。
   Claude Codeは対象のtranscriptの絶対パスも保持する。
   ホスト値は `claude`、`codex`、`agy` から選ぶ。
   前の振り返りが終わっていなければその境界と担当の実行IDを残し、新しい境界は後へ並べる。
2. 報告の保存後か本人再開後の統括は先に新着を含めて選定し、着手できる作業を始める。
   選定の後に `atk run-script session-review-state -- show --target <host> <会話ID>` で確認する。
   `batch` の区間は既存batchに任せ、`batch-busy` または診断不能なら次の進捗点検で再確認する。
   batchが完了したら同じ処理済み位置を使う。
   batchが境界より後の範囲を確定した場合は、同じ境界で `--conversation-only` を指定し、`bundle/scope.json` の各記録を既存の処理済み位置と元記録に照らして確かめる。
   同じ元記録の確定済み範囲に区間全体が入る場合は引き継ぎから外し、分析を始めない。
   確かめられなければ境界を残す。
   自動batchを無効にした環境でも設定は変えず、以下の単発を使う。
3. 同じ会話の最も古い未確定の境界を1つだけ扱う。
   担当の実行中・中断後の再試行前・結果到着後の未検収を区別し、その区間を確定するまで次の境界は起動しない。
   巡回は続ける。
   同じ区間を担当中の実行がなく、巡回の起動・進行を妨げない実行枠があれば、既存の委譲手段で単発の振り返り専用の担当を非同期で起動する。
   対象・境界・作業の目的・起票の認可範囲を渡し、対象の元記録だけを読む。
   `session-review-prepare` に `--observation-boundary <境界>` を渡す。
   Claude Codeは `--transcript <パス>`、Codexは `--codex-thread-id <ID>`、Antigravityは `--agy-session-id <ID>` を指定し、照会と同じ会話の処理済み位置を使う。
   `--full` は使わず、既存の処理済み位置より後の区間だけを対象とする。
   専用担当は[単発の振り返り](review-session.md#工程)の準備・分析の手順で結果本文を確定する。
   処理済み位置は進めない。
   準備結果のJSONの絶対パス、結果と残る範囲を統括へ返す。
4. 統括は巡回を続け、到着した返却だけを次の進捗点検か再開時に検収する。
   分析・必要な保存・報告本文を確認でき、未確認範囲が無い時だけ `atk run-script session-review-state -- complete --prepared <準備結果JSON>` で既存の処理済み位置を進める。
   未起動・中断・未達なら位置を変えず、次の進捗点検または再開時に同じ境界を既存の位置から再試行する。
   終了のための待機や別の台帳は設けない。
