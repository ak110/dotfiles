# 振り返りの分析

通常の振り返りとbatchが、準備の後に対象ごとに上から実行する分析の手順書である。
会話の記録から問題と改善の機会を見つけ、原因と対策を確定し、AWIの投入と振り返り結果報告の材料までを作る。
記録から見つけた問題は逸脱として扱い、原因の掘り下げ、前提、広がり、再発防止の選び方は`agent-basics:bugfix`に従う（原則5、`agent-basics:writing-standards/references/quality-principles-deviation.md`）。
本書が持つのは、振り返りに固有の入力（prepareの出力、会話の流れ、候補ID、batchの範囲、既存のWIキュー）の扱いと、振り返りで起きる判断である。
事実は観測した範囲で言い、省略された表示と未確認の範囲を不在や確認済みの根拠にしない（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。
batchでは全対象に同じ基準を使い、対象IDと候補IDの組で出典を保つ。

改善点の受付IDが証拠に含まれる場合は、`agent-toolkit:atk-mode/playbooks/main-reporting.md` の受付手順で観測と確定済みの処置を確認する。
同じ事象を再調査・再投入せず、受付外の新しい証拠や別の問題は通常どおり扱う。

## 分析と投入

工程2〜5は、メインが作る1つの分析の記録を引き継ぐ。
記録は問題ごとに1項目とし、候補ID（候補が無ければ記録位置）、取得した証拠の位置と範囲、書き出す場面に当たれば`agent-basics:bugfix`の`SKILL.md`「記録」の行、費用の比較の採否を書く。
正常、必須、回復済みという分類は欠陥の有無の結論であり、証拠の十分さと費用の比較はそれとは別に判定する。
欠陥の有無を判定できない読取の不足や通知は、未確定として残す。
未処置の通知でも欠陥を確定できた場合は、工程4で処置、被覆、対策か調査を決める。
工程5の報告はこの記録から作り、候補に無い通読上の問題と未確定の不足も含める。

### 工程2

1. 準備の1行JSONの`reference_document`に値があれば、通読の前にその文書（対象リポジトリに固有の振り返りの参照文書）を全文読む。
2. `candidates.md`を読む前に、メインが`conversation.md`の全期間を1つの流れとして通読し、観点を限定せずに問題と改善の機会を挙げる。
   通読と全体の判断はメインだけで行い、順序、入力、前後関係の確認が要る箇所は記録位置を`--detail`へ渡して全文を取る。
   準備の後の会話圧縮で通読の材料が失われたら、同じ生成物を全文読み直す。
3. 通読では、エラーとして現れない遠回り、手戻り、不要な反復、ユーザーの軌道修正、時間の浪費を、ツールの呼び出しと前後の発話から探す。
   コマンドの試行錯誤、同じ資料の再読、設計のやり直し、規範の解釈の迷い、委譲の指示不足、定義元の手探り、出力の後加工の反復、保存済みの値の転記が当たる。
4. 手順書やスキルの作業をmanaged-tempの一時スクリプトで代行した箇所を探す。
   委譲先の分は、`session-review-evidence`の`--grep`でmanaged-temp配下のスクリプトのパスを検索する。
5. 従った規範と手順そのものを、QCDに見合ったかで懐疑的に見直す。
   問題が起きなかった区間も含め、守った成果に比べて費用や時間が大きかった規定、往復や待機を増やした規定、制定時の前提が失われた規定を探し、縮小、撤去、簡素化を提案する（判定は本書「規範の未適用と目的逸脱」）。
6. `気付いた改善点:`で始まる行は全て問題の列挙に入れる。
7. `stats.md`と通読の結果から、`agent-toolkit:atk-mode/references/review-session-cost.md`「コストの無駄の確認」の観点で費用を比べる。
   正常に成功した操作、問題の無い返却、振り返り自身の作業も比べる対象に入れ、結論を工程3・4と報告の`費用確認`へ渡す。
   記録全体を比べる観点は本書「通読で使う比較」にある。
8. 同じ資料の「所要時間の分析と改善」（対象に巡回があれば同節「巡回の比較」から）、「hookの所要時間」、「CI履歴からの継続改善」を対象セッションへ適用し、律速と改善案を工程3・4と報告の`所要時間`・`改善見込み`へ渡す。

### 工程3

1. 全候補を、通読で見つけた問題と取得済みの証拠へ対応付ける（候補の読み方は本書「候補の抽出」）。
   同じ事象の根拠が揃っていれば再利用し、新しい事象、変更、未確認、判定の不一致だけを補う。
   候補ごとの原記録の網羅的な調査と、基準で走査して該当しなかった全件の再走査は省く。
   確定した判断を変えるのは、追加の候補が結論を覆す証拠を持つ時に限る。
2. 通読では捉えにくい事象を`candidates.md`で補う。
   直近30日の複数セッションで反復した失敗、hook通知の発生源と件数、除外の件数、`adhoc-processing`、委譲先の内部の処理が当たる。
   候補に無い通読上の問題と、成功した作業から見つけた改善の機会も、独立した問題として扱う。
3. `agent-toolkit:atk-mode/references/review-session-triage.md`で、原因分析へ送る問題と除外する問題を分ける（定義本文の読込の候補は同書「定義本文の読込の判定」で分類する）。
4. 本書「採用済みAWIの効果の確認」で、採用済みAWIを選んで判定する。
5. 原因や費用の判断に要る材料が概要に無ければ、候補の有無によらず本書「入力と照会」の照会で取る。
   事実の調査を委譲する時は、先に`agent-toolkit:atk-mode/playbooks/investigation-delegation.md`を全文読む。
   公開の待機中に先行した調査とAWIの原稿は、選別の結果と公開後の実態で採否を確定し、公開の成否で判断が変わる問題は結果の確定後に調べる。

### 工程4

選別した問題ごとに、メイン自身が`agent-basics:bugfix`を起動し、事象、期待された契約、実際の結果、発生条件を入力にする。
同じセッションで前に起動していても振り返りごとに適用し、WI投入担当の分析をメインの原因分析の代わりにしない。

1. 既存の上位の規範、対象の目的、技術的な常識から導ける事項かを、`agent-basics:bugfix/references/premises.md`「規範に従った結果の失敗」で確かめる。
2. `agent-basics:bugfix`の`SKILL.md`「書き出す場面」に当たれば、5つの問いの答えを証拠に照らし、確定した原因と対策、未確定の事項を分ける。
   `agent-toolkit:atk-mode/playbooks/user-utterance.md`「ユーザー介入と確認の判定」が前例の有無によらず対象にする事象（ユーザー介入、確認の過不足、ユーザーの手を煩わせた事象、品質を損ねた事象、所要時間の目標の超過など）は、1回目で再発防止を検討し、2回目を待たない。
   再発防止の案は`agent-basics:bugfix/references/prevention.md`「案を比べる順」の順に比べる（原則9）。
   過去のAWIとの比較は本書「原因と対策」に従い、既存の未完了AWIによる被覆、起票、実装と配布、今回の条件での解消を分けて工程5へ渡す。
3. 工程2・3の費用の比較を使い、欠陥の有無の判定と実施方法の採否を分けて確定する。
   不具合と確定した問題には、同じ作業での処置、実条件を覆う既存対策、または登録する対策・調査を対応付ける。
   原因か方式が未確定なら、観測事実、仮説、次に確かめる問いを分けて調査の要求にする。
   費用だけを理由に不具合を見送らない。
   再発防止を採用しない時は、理由が`agent-basics:bugfix/references/prevention.md`「再発防止を採用しない場合」の区分に当たることを確かめる。
4. 再利用の価値がある成功の手順、誤記の訂正、重複の整理と参照の補修も、既存の記録と比べて選ぶ。
   知見の保存と再利用は`agent-basics:writing-standards/references/investigation.md`「経験の保存と適用」に従い、恒久の変更が要るものを工程5へ渡す。

### 工程5

1. 工程4の結果を、振り返り結果報告と報告用UWIの結果欄へ引き継ぐ。
   書式は`agent-toolkit:atk-mode/references/report-formats-retrospective.md`「振り返り結果報告のフォーマット」に従う。
   既存の未完了AWIで覆う場合も、残る原因の条件、処置の担当、適用機会と観測結果を同じ行に残し、登録と今回の条件での解消を分ける。
   不具合でない候補の見送りは、工程2〜4の観測と費用の比較から根拠を書く。
   正常終了、規範どおり、回復済みという分類だけで代えない。
2. 通常の振り返りでは、確定した対策と未確定事項の調査を区別し、既存AWIによる被覆を整理する。
   確定した対策は`agent-toolkit:atk-mode/roles/add-wi.parent.md`「起動方法」の単位でWI投入担当へ渡し、同書「受領と検収」で検収する。
   欠陥が確定して原因か方式が未確定なら、メインが本節の手順3に従って根拠を区別し、起草、意味の検収を経て保存する。
   登録する要求が1件以上あれば、投入担当の起動またはメインによる保存の前に`## 振り返り結果の予告`（全ての登録予定を`AWI登録予定`の行で書く）をユーザーへ送り、同じターンで起動または保存へ進む。
3. batchでは、対象ごとの工程4で対策または調査の要求が確定した時点でメインが直接起草し、残りの対象の工程2〜4も続ける。
   起草、意味の検収、保存は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`に従い、原因分析を含む原稿は`agent-toolkit:atk-mode/roles/wi-draft-review.parent.md`の独立した投入前レビューを経る（原則6）。
   後の対象で同じ根本原因を見つけたら保存前の原稿へ統合し、更新した内容を検収し直す。
   保存は全対象の工程4と、`agent-toolkit:atk-mode/playbooks/review-session-batch.md`のセッション横断の整理を終えてから行い、その直前に確定した全要求を予告として送る。
4. 予告は`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」に従って届ける。
5. 要求は次の形にする。
   - `source`は`session-review`とする。
   - batchが登録するAWIは、ユーザーの内容確認を待たず、エージェント由来の要求として採否を検討する対象にする。
   - 要求の間に依存がある時は、先行する成果が要る理由を趣旨に書く（`agent-toolkit:atk-mode/roles/add-wi.parent.md`「渡す入力」）。
   - ユーザーの発話を逐語で引用する要求には、原文がある記録（`conversation.md`や`session-review-evidence`の出力ファイル）の絶対パスを出所として書く。
   - 恒久の処置は、原因と対策を確定した通常AWIとして起草する。
     1件の再発防止で複数の問題を覆う時も、問題ごとの原因と処置の対応を残す。

## 入力と照会

入力は、`atk run-script session-review-prepare`が出す会話の流れ（`conversation.md`）、比較材料（`comparison-materials.md`）、候補索引（`candidates.md`）、統計（`stats.md`）と、メイン自身の文脈である。
会話の流れは観点を限定せずに問題を探す起点、候補索引は通読で見つけた問題との対応付けと、通読で捉えにくい事象の補いに使う。
最初に会話の流れ、候補索引、統計の3文書を読み、判断に要る原文と文脈は個別の候補の詳細から取る（全候補、全担当、全対象の一律の通読と、準備をやり直した後の判断が変わらない箇所の読み直しは省く）。

- 全候補の対応と必須性は`bundle/review-index.jsonl`が持ち、索引に表示されない候補も含めて全件を対応付ける。
- 候補の全項目、発生位置、操作の入力、質問文と全選択肢、実際の回答は、`bundle/candidates.jsonl`と、索引の`candidate_id`・`evidence_path`が指す個別の証拠から取る。
- 通読や候補の判定で、委譲時の入力や規範の読込が判断を左右すると分かった時だけ、`comparison-materials.md`から該当する区分を取る。
  区分ごとの全件・表示・省略の件数を確かめ、表示外の項目は`bundle/comparison-materials.jsonl`の`record`・`line`・`result_line`から照会する。
  直接渡された本文とファイルの参照、明示の読取とコマンド文字列だけの観測、返却本文の量と現在のファイルサイズは分けて数える。
  参照ファイルの内容量、自動配送、読了の有無は、受領の記録などの証拠が無ければ未確認とする。
- メインと全担当の費用はセッション統計から取り、トークン数、キャッシュ量、料金は`agent-toolkit:atk-mode/references/session-records.md`「集計値の典拠」の定義で数える（Codexの総入力にキャッシュ済み入力を重ねて加えない）。
- 候補文書と統計文書の未確認範囲（JSONの`unconfirmed_scope`）は、未解決の記録と識別子の取れなかった呼び出しを示す。
  正常に処理された件数だけで全範囲を確認済みとしない。

直接の原因を特定できない候補と、比較に要る操作や成果の材料が概要に無い時は、事前の候補の有無によらず全文と契約を取る。
照会は`atk run-script session-review-evidence -- <引数>`で行い、引数と検索の注意は`agent-toolkit:atk-mode/references/session-records.md`「本文の検索」に従う。
振り返りで主に使うのは、本文・入力・実行結果を取る`--detail <記録位置>`、委譲先も再帰的に集めてツールの呼び出しを並べる`--tool-calls`、出所付きの改善点の全行を取る`--reported-improvements`である。
会話圧縮で文脈から消えた区間もログには残る（Claude Codeの`compact_boundary`、Codexの`compacted`）ため、圧縮区間の事象も分析し、文脈で確認できないことだけで原因を未確定としない。
記録に理由の本文が無い事象は、同じ呼び出しを再実行して再現するか、実装のコードを読んで確定する。

照会と再現でも確定できない場合（記録ファイルの削除、`unresolved-delegation`と報告された委譲先など）は、照会と再現の経過を残す。
欠陥の有無を確定できなければ報告の`未確定`へ、欠陥が確定していれば工程4の調査の要求へ渡す。
介入の意図などユーザーの判断が要る要素が残る候補は、推測で確定せず`agent-toolkit:atk-mode/playbooks/confirmation.md`で確認する。

## 候補の抽出

候補は`atk run-script session-review-evidence`が生成し、prepareが1件1行の要約と記録位置を付けて`candidates.md`へ出す。
候補の区分と除外の条件はprepareの実装（docstring）が定める。

- 候補の操作の実行主体は、要約の表現から推測せず、各記録位置に付く`record-provenance`の由来（役割文書、起動モード、起動元の記録）で決める。
- ユーザー介入、WIの記入欄の是正（`wi-user-response`）、エスカレーションの全文、hook通知の前後の応答は、索引の短い概要で判断せず、保存された証拠から全文を取る。
- 評価が必須の候補（1行JSONの`mandatory_candidates`）は全件を評価する。
- 準備は、構造から正常と判定できる事象（一致0件の検索、試験の失敗を正しく検出した検証、正常な完了だけを返した委譲、応答言語hookの警告など）を候補から除き、区分ごとの件数だけを`excluded_counts`に残す。
  除外された事象に欠陥の兆候があれば、本書「通読で使う比較」の抽出の偽陰性として調べる。

## 原因と対策

再発や悪化を問う入力と、同じ機構への局所の修正の反復や過去の対策との共通の構造を記録に認めた場合は、個別の候補の採否より前に、`agent-basics:bugfix/references/recurrence.md`で分析の単位と比べる範囲を決める。
ユーザーの再発の指摘やファイル名の一致を待たず、通読と変更履歴から共通の前提を探す。
選別した問題と所要時間の律速の条件は、発見元や前例によらず工程4の`agent-basics:bugfix`へ渡す。
記録は`agent-toolkit:atk-mode/references/analysis-records.md`「原因分析の記録先」の書式とし、`処置:`と`再発防止:`は`agent-basics:bugfix/references/prevention.md`「言葉の区別」で分ける。
費用の判断は`agent-toolkit:atk-mode/references/review-session-cost.md`「コストの無駄の確認」の採否を再利用し、品質の判断と分けて保つ。

過去の対応項目は、候補の`similar_records`と`atk wi grep`の検索から取り、本文を`atk wi show`で確かめる。
検索の条件は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「重複判定」に従う。
`similar_records`が空でも、表現の違う是正の事例を本文の検索で補う。
目的、事象、原因、適用の条件、実装と配布の状態、処理の後の観測を比べ、結果を未反映、未適用、範囲不足、適用後の同原因、別原因、効果未確認に分ける（`agent-basics:bugfix/references/recurrence.md`「前回の対策を調べる」）。
原因が違っても同じ害なら反復として記録し、反復した問題には過去の項目名、前回の対策の種類、解消されずに残った条件を`再発:`の行に書く。
完成条件が後日の効果の観測を明示する項目は、観測の条件と再開の手段を保って公開工程の延期のadoptへ渡し、一般の効率の改善には長期の観測を一律に足さない。

### 採用済みAWIの効果の確認

通常とbatchの両方で、採用済みAWIの効果を、対象のセッションの実際の操作と結果と比べて確かめる。
AWIの登録、実装、規範の読込、仕組みの起動は効果の根拠にならず、適用の機会と観測した結果で判定し、適用の機会が無ければ未確認とする（原則3）。

1. 見直す項目を、確認待ちの一覧（`atk wi list --state=adopted --effect-check=pending`）と`atk wi grep --state=adopted`の検索から選ぶ。
   ファイル別に一部だけ効果不足と判定された項目は、状態を限らない検索から選ぶ。
   対象のセッションで続いているか悪化している問題（所要時間の分析で悪化した巡回の所要、同じ種類の指摘や介入の反復、同じ不具合の再発）を目的に採用された項目を先に選び、先に判定する。
2. 選んだ項目が変えたファイル（`atk wi show`が示す対応commit）と、対象のセッションでの実際の操作（`session-review-evidence`の照会）を確かめる。
3. 目的の値を比べる前に、提供する側の変更（対応commit）、配布（版の公開と稼働環境への反映）、使う側への適用（使う側が固定する版、主checkoutへの反映、対象のセッションの実行記録）を同じ根拠でつなぐ。
   使う側へ適用されていなければ、目的の値の変化から判定せず「効果不足（未適用）」とする。
4. その項目の目的（H1直下の、何をどれだけ改善するか）の結果を、採用の前後で、同じ原因が残っているか、適用の条件が満たされたか、1回あたりの所要と回数、仕事の量に分けて比べる。
   区間が短くなっていないことだけで効果不足とせず、回数や仕事の量が増えた場合はその原因へ帰属させる。
   元の目的の未達と、対策が生んだ副作用の解消は別々に保つ（容量の問題で、掃引の遅さの解消だけを見て容量の目的も達成済みとした誤りがある）。
5. その変更が所要（足した工程、待ち）、複雑さ（足した状態、設定、条文）、不具合（その変更を直すための修正と作業項目）を増やしていないかを、変更履歴とキューの検索で確かめる。
6. 判定を「効果を確認」「効果不足（同原因の再発・未適用・範囲不足）」「適用機会なし・観測不能（確認待ち）」「後日の確認不要」から選び、適用の機会、観測の位置、未確認か不要の理由を残す。
   目的を達していない項目と、増やした負担が効果を上回る項目は効果不足として保存し、是正のAWIを登録する（元の変更をやめる案と単純にする案を先に比べる。`agent-toolkit:atk-mode/references/drafting-decisions.md`「採否と実現方式の確定」）。
   保存は`agent-toolkit:atk-mode/references/effect-records.md`「採用済みAWIの効果記録」に従い、判定済みのファイルの是正先を保ち、一部だけの効果不足で他の目的の範囲まで確認済みとしない。
7. 実装したセッションで測れる部分はそのAWIの完成条件で確かめ、巡回の所要のように実装の後の巡回でしか測れない部分は、後の振り返りが採用の前後の巡回を同等の入力（件数、由来の内訳、レーンの数、検証・CI・成果の範囲）で比べ、開始から終了までの所要を元の項目の目標と比べて判定する。
   結果は報告の`効果確認`の行に書き、対応commitや適用の機会が不明なら効果未確認として残す。

### 情報探索の問題

情報探索の証拠と原因は、`agent-basics:bugfix/references/causes.md`「場面ごとの確かめ方」で確定する。
対策の要求には、探していた情報、探索した区間、参照した文書の順、定義元、探索を妨げた要因（資料の陳腐化なら、参照した記述、現行の仕様との差、判断への影響）を、根拠の絶対パスと記録位置に対応付けて書く。
AWIの節の分担は`agent-toolkit:atk-mode/references/awi-body.md`「節の構成と分担」に従い、振り返り結果報告からAWIのファイル名でたどれるようにする。

## 規範の未適用と目的逸脱

規範が適用されなかった事象と、規範に従った結果として目的から外れた事象は、原因を分けて分析する。
警告への未対応から検査の強化、誤検出や反復の負担へ続いた場合は、行動の原因と対策の副作用を1つの連鎖として比べ、行動規則の改訂、規範の統合・簡素化、hookの縮小・撤去、維持から選ぶ（遮断と毎回の警告は極力避ける）。
正当な初回の警告と安全の保護を撤去する案は、発火の件数に加えて、保護の目的と実際の作用で評価する。
一度の警告の後に必要な対応を取らなかった行動も是正の対象とし、一般則の存在、警告の発火、最後の回復だけで是正済みとしない。

規範の問題の有無を問われた時は、まず規範の本文と必要な変更履歴を読み、欠陥が確定すれば記録の照会を省いて是正へ進む。
本文に欠陥が見当たらず、未適用の区分で対策が変わる場合に限り、次のとおり照会する。

1. 事象の時点の条文（改訂済みなら`git log -S`で当時の文面を特定する）から特徴的な1行を選び、`atk run-script session-review-evidence -- --context-at <事象の記録位置> --phrase=<文字列>`で文脈の中の存在を照会する。
   判定と、条文を文脈へ入れた出所を示す`channel`を、AWIの`原因:`の行へ書く。
2. `absent`は起動の契機の欠落か参照の時点の問題、`dropped-by-compaction`は会話圧縮の問題、`present`は条文の判定条件、責務の所在、想起性の問題とする。
   一致した`channel`が`user`と`assistant`だけなら、会話の中の言及として扱う。
3. 適用されなかった規範を前回の対策として`agent-basics:bugfix/references/recurrence.md`「前回の対策を調べる」で扱い、想起性を改善する案と、その案で誤りを防げる見込みの根拠をAWIへ書く。

`present`の未適用で実際のモデル階層が対策の選定を左右する時は、記録から確かめたモデル階層を`agent-toolkit:atk-mode/playbooks/delegation-recovery.md`「代替時の組合せの目安」と比べる。
上位の階層なら性能不足を原因とせず、条文の追加より先に既存の条文の削除、緩和、集約、単純化、一般化を比べる。
中位と軽量の階層は、条文が明確で権限・手段・入力が揃っていても失敗した時に限り、割り当てるモデルの変更を対策の候補にする。
記録からモデルを特定できない工程は推測で補わない。

目的逸脱には、規範に従ったことによる停止、差し戻し、空転、不要な反復、条文間の矛盾、前提の欠落、要求を満たさない成果物が当たる。
規範が求める工程は適用のたびに生じるため、1セッションで1回の発生でも反復する負担として評価し、必読範囲の縮小・集約、準備を呼ばれる側へ移す案、探索を不要にする案を比べる。
条文を改める時は守る価値、導入の目的、期待する成果に対応付け、現行のまま保つ時は同じ停止が起きる条件と許容する理由を書く。
判断の到達可能性は`agent-basics:review-standards/SKILL.md`「検収手段の到達可能性」で確かめる。

## 通読で使う比較

記録全体を通読する時は、次の観点のうち該当する操作や成果があるものを、目的、契約、利用結果、QCDで比べる。
表は代表例であり、該当する観点だけを使い、表に無い観点にも同じ比較を適用する。
文字数、実行回数、トークン量だけで欠陥や対策の要否を決めない。

| 原則 | 観点（括弧内は原則だけでは外れやすい比べ方） |
| --- | --- |
| 1 顧客と技術者 | 範囲の拡大（設計やレビュー由来の追加も探す）、例示への固定、割込・圧縮後の脱落（要求の追加・撤回・完了と、引き継ぎ記録・最終報告を比べる）、必要な確認の負担（`agent-toolkit:atk-mode/references/review-session-triage.md`「ユーザー介入の判定規則」）、説明と行動の不一致、実利用への適合、必要な追従の不足（生成元、消費側、公開手段、配布先、OSの組と最終結果）、委譲入力・所有権の不足 |
| 3 観測 | 証拠以上の事実主張、検証対象の不一致（最後の修正・生成・検証の時刻、パス、版、OIDと完了の根拠）、版・時点・配布手段の混在（発生時点の文面を確かめる）、未確認範囲の受渡し、縮約による文脈喪失、情報アクセス（判断に不足した情報と、既存の認可で届く情報源）、定期の通知・点検の未発火（通知が無い区間は発生源と条件を調べ、不在を正常の証拠にしない） |
| 5 逸脱は情報 | 完了条件のすり替え、合格を目的にした対処（失敗から合格までの差分・除外設定・期待値）、代替指標の目的化、表記が異なる同原因の失敗、前提確認の遅れ、原因分析の記録（`原因:`が観測の所在を持つか、`処置:`が足す案ならより前の案を採用しない理由があるか、`広がり:`が検索と結果を持つか、`再発:`が前回と違う種類の対策を示すか） |
| 6 作る者と確かめる者 | 実装と同じ誤解を持つテスト、正常返却の未検収、レビューの後出し・往復（第3ラウンド以降に限らず、初回の時点で取れた根拠と比べる） |
| 7 所有と終了 | 資源の所有と終了（完了の申告だけで終了としない）、読取操作の副作用（正常終了でも共有状態が変わっていないか）、証拠の寿命 |
| 9 足す前に引く | 根拠の無い追加設計（状態管理、監視、互換維持、フォールバック）、自動チェック（既存の検査の未接続・無効化・対象の欠落の修復を新設より先に比べる）、コーディング規約（機械判定できる違反は型やlintへ）、無効な指示、入口と起動時に届く本文の肥大化、対策の副作用と総費用、改善要求の分断と滞留（登録件数を効果の代わりにしない） |
| 2 費用と所要 | `agent-toolkit:atk-mode/references/review-session-cost.md`「コストの無駄の確認」の観点に加え、委譲単位の過小・過大、不要な先行工程待ち（実行時刻の重なりだけで完了待ちが要ったとしない）、作業量の偏り、成功した呼出しの集約、ツールの経済性（既存の公開オプションの未利用も確かめる）、成功するポーリング、出力設計による読み直し、ナビゲーション、責務と読者のずれ、失敗の無い改善機会、良い手段の再利用、測定単位のずれ、要約に出ない費用、正常・非律速委譲の問題（律速でないことを除外の理由にしない）、実行系・呼出形式の被覆差、振り返り自身の費用（準備を再実行せず、既存の索引と照会で工程3〜5へ送る）、抽出の偽陰性（除外区分と抽出条件を代表例で確かめる） |

## 既存キュー項目との重複確認

完了していない既存のキュー項目との比較は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「重複判定」に従い、既存項目の作用の機構が今回の事象、根本原因、完了条件を全て覆うかを確かめる。
本文の削減、読取の手段、hookの発火、会話圧縮の時機は別々の作用の機構であり、同じ費用の分類でも個別に覆うかを判定する。
完全に覆うなら新規の投入を見送り、ファイル名と根拠を報告の「確定した問題と対策」に書く。
一部だけ覆う時と新しい証拠がある時は、不足分の採否を確定して起草する。
既存の未完了AWIで覆う場合も、登録と今回の条件での解消を分ける（本書「工程5」）。

## 通知の前提が成立しない場合

hook、ツール、実行環境からの通知が、担当外の対象、実行できない処置、実在しない前提を示していた場合は、個別の対応とは別に通知の機構の欠陥として処置する。
処置は、同じセッションでの是正、`agent-toolkit:atk-mode/playbooks/wi-drafting.md`に従ったAWIの起草、同じ欠陥を扱う未完了WIの参照のどれかとする。

返す報告に含める項目: 振り返り結果報告の材料（問題ごとの候補IDと扱い、投入したAWIと見送りの根拠、`費用確認`、`効果確認`、未確定の範囲と理由）。
