# CI失敗の修正

目的: CI失敗を直す担当を1人に定めて修正とレビューを繰り返し、ユーザーへ届く公開版がCIを通った状態を保つ。
修正commitが必要と確定したCI失敗と全体検証の失敗を、誰がどの記録で直し、どの条件でレビューして再pushするかの手順書である。
作業`process-wi`のレーン担当・メイン・リポジトリ担当と、公開工程の公開担当が使う。
CI失敗の取得・分類・原因分析は`agent-toolkit:atk-mode/references/ci.md`にある。
push先・run監視・証拠の保存と後始末は`agent-toolkit:atk-mode/playbooks/publish.md`に、直接原因の特定は`agent-basics:bugfix`にある。
本書が扱うのは、書き込みの所有権、修正の担当、CI記録、修正系列と回数、先行CI、レビューの起動である。
終了条件は、修正系列のCI成功を判定し、計画と指摘管理表を再保存した時点である。

## 修正commitが必要なCI失敗を修正するエージェント

1. 修正commitが必要と確定したCI失敗は、元の計画の実行工程へ再投入せず、本節の担当へ渡す（修正の書き込み所有権を守るため）。
2. 本書を適用するエージェントが対象作業ツリーの書き込み所有権を持ち、そのツリーへ書いている稼働中のエージェントが居なければ、自ら直す。
   それ以外は`CI修正担当`を1件起動して委譲する（起動と入力の形式は`agent-toolkit:atk-mode/roles/exec.parent.md`）。
   公開工程は本書「公開工程の公開担当が扱うCI修正」の例外に従う。
3. 起動の前に`CI記録`を作る。
   `CI記録`は、原因分析結果、修正認可根拠、対象の検証結果、変更目的、対象、公開契約、入力計画の7項目からなる。
   - 修正認可根拠には、計画ファイルに記録された元の要求か確認回答の該当箇所、原因となった変更を認可したユーザー指示の原文、既存の公開契約の該当箇所のいずれかを書く。
     根拠を特定できない場合は修正担当を起動せず、ユーザーへ確認する。
   - 原因特定のために診断コードを足す場合は、原因分析結果で競合する仮説ごとに確かめる観測を、公開契約で採取する対象と属性を対応付ける。
     全件の列挙や走査は仮説の判別に必要な場合に限り、大きいデータは一時領域へ全量を保存して範囲を読む（完全性を保つため容量上限で切り詰めることは避ける）。
     元の失敗と終了コードは保ち、情報採取自体の失敗は別に記録する。
   - レビュー基準には、原因commit自身に対応する計画があればその計画を、無ければCI記録を使う（処理対象WIに含まれる無関係な別の計画は使わない）。
   - 計画を持たないCI修正commitが再push後に別の失敗の原因となった場合は、直前のCI記録を引き継いで7項目を更新する。
     CI対応レビュー指摘管理表があれば、そのパスと`修正系列の開始時のHEAD`も引き継ぐ。
4. 本書「修正系列」の手順で直し、再pushしてCI確認へ戻る。

### 修正系列

最初のCI失敗（公開工程では全体検証の失敗を含む）から、CIが成功するか工程が終わるまでを1つの修正系列とする。
修正回数、CI記録、レビュー指摘管理表、`修正系列の開始時のHEAD`はこの単位で引き継ぎ、原因commitが変わっても回数を数え続ける。
回数は、ログの該当箇所と直接原因に対応付けた是正の件数で数え、原因commitへ取り込んだ修正（`agent-toolkit:atk-mode/playbooks/publish.md`「pushと監視」の「原因commitへ取り込む区分」）も1回と数える。
ユーザーの割り込み操作と独立した事象へのcommitは回数から除く。
取り込んだ場合は、`exec-review`へ渡す`原因commitOID`に履歴書き換え後に解決できる値を使い、書き換え前後のOIDの対応と`git range-diff`の結果をCI記録へ残す。

1. 入力計画: 修正の基準をそろえるため、`入力計画`に原因commitに対応する計画ファイルのパスを渡す。
   - 保存済みの計画は、起動側が起動前に`atk plans checkout <private-notes/plans/からの相対パス>`で`~/.claude/plans`へ取得し、そのパスを渡す。
     保存済みのパスを直接渡すと、引き継ぎ記録と指摘管理表への記録が拒否される。
     同じ修正系列の実行レビュー（`レビュー基準: 計画`）にも同じパスを渡す。
   - 未保存の計画は`~/.claude/plans`のパスをそのまま渡し、対応する計画が無ければ`なし`とする。
2. 修正者は、原因の修正、全項目の検証、差分の検収、ステージング、commitを終える。
   修正前の計画は`agent-toolkit:atk-mode/references/ci.md`「選択の流れ」に従い、公開工程の外で自ら直す場合は同節の手順4の計画を使う。
   外部サービスの障害など、修正commitを要さない失敗では実装担当を起動しない。
3. 先行CI: 手元では失敗した条件の成否を観測できず、認可済みの作業ブランチで対象ジョブと直接影響範囲を実行できる場合は、修正commitを早めにpushして先行CIで確かめる。
   - 対象リポジトリ・ブランチへのpush認可と書込担当の終了を確かめてから、`agent-toolkit:atk-mode/playbooks/publish.md`「push前」「pushと監視」の通常の操作を使う。
     認可が足りなければ追加の認可を求める。
   - 作業refの先行CIは再レビューの合格を待たずに始め、必要なレビューと他の検証を並行して進める。
     修正の合格と正式公開は、先行CIの結果と必要なレビューの合格を検収してから確定する。
   - 証拠にはSHA、ref、baseline、実行されたジョブと条件を残し、失敗したジョブが同じ条件で実行されて期待結果になったことを確かめる。
     対象ジョブが起動しなければ検証済みとせず、再現環境の確保か認可の確認へ進む。
     修正合格の根拠には成功した先行CIだけを使い、確かめた試験不良の同じSHAの再実行の成功は除く（`agent-toolkit:atk-mode/references/ci.md`「CI通過の判定」）。
   - 手元で同じ条件を再現できる修正はローカル検証を優先し、先行CIを使った場合も正式公開refで要求されるcheck集合を検収する。
4. レビューの起動: 同じ修正系列の3回目以降の修正と、回数によらず公開契約や設計に及ぶ修正では、初回の`exec-review`を起動する（公開工程の修正系列にも適用する）。
   それ以外は`exec-review`を起動せず、再pushしてCI確認へ戻る。
   3回以上の修正が必要な事態は、直前の修正で根本原因の把握が足りなかったことを示すため、3回目からレビューを入れる。
   CI対応レビュー指摘管理表の作成・更新・保存は、`exec-review`を起動する場合だけ行う。
   - 起動は`agent-toolkit:atk-mode/roles/exec-review.parent.md`に従う。
     計画があれば`レビュー基準: 計画`で計画ファイルを、無ければ`レビュー基準: CI記録`で7項目、`修正系列の開始時のHEAD`、`原因commitOID`を渡す。
     CI記録を基準に含めるときは、`agent-toolkit:atk-mode/references/review-contract.md`に従い、CI記録の認可範囲と原因commitの親からの変更を条項にして`review_contract`へ渡す。
   - `修正系列の開始時のHEAD`は系列の開始時点のHEADの7文字以上の一意な短縮OIDで、系列の間は変えない。
     `原因commitOID`は今回の原因commitの7文字以上の一意な短縮OIDで、再帰的なCI失敗では7項目と同時に更新する。
   - 計画を基準とする後続の実行レビューには、引き継ぎ記録に記録された読み取れる受理済みの実行レビュー返却ファイルの絶対パスを任意入力`受理済みの完成条件証拠`として渡す（無ければ`なし`）。
     使える条件は`agent-toolkit:atk-mode/references/review-record.md`「受理済み判定への参照」にある。
     受領を確かめた新しい返却ファイルの所在も同じ引き継ぎ記録へ記録する。
   - 同じ修正系列の中では同じレビュー指摘管理表を引き継ぐ。
     独立確認の要否と修正後の証拠の受理は`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「レビュー修正」に従う。
5. 成功の判定: 修正系列を完了とするCIの成功は、失敗したジョブを判定対象に含み、期待される終了状態（許容された失敗を含む）で正常終了したパイプライン（GitHub Actionsではrun）に限る。
   試験自身の不良と確かめた失敗は、同じSHAの再実行の成功を数えない（`agent-toolkit:atk-mode/references/ci.md`「選択の流れ」の手順7）。
   push先で対象ジョブが実行されない場合（保護ブランチ限定、スケジュール実行、特定パスの変更条件など）は、ジョブの実行環境を含むローカル再現で成否を確かめる。
   再現は`agent-toolkit:atk-mode/references/ci.md`「失敗ログとartifactの取得」に従い、同じSHAで行う。
   ローカル再現もできない場合は、未確認のジョブ、試した再現手順、残る実行条件の差をエスカレーションとして報告する。
6. 再保存: 修正系列の完了時に、起動側が`atk plans commit <private-notes/plans/からの相対パス>`で計画を再保存し、成功の表示と警告が無いことを確かめる。
   CI記録を基準とする`ci-<修正系列の開始時のHEAD>.exec-review.tsv`も同じ時点で`atk plans commit ci-<修正系列の開始時のHEAD>.exec-review.tsv`で保存する。
   修正系列が続く間（再pushの結果待ちを含む）は表を`~/.claude/plans`に残し、先に保存した場合は`atk plans checkout ci/ci-<修正系列の開始時のHEAD>.exec-review.tsv`で戻してから続ける。

### 公開工程の公開担当が扱うCI修正

公開工程でのCI修正は、新しい計画ファイルを作らずにCI記録で引き継ぐ。
失敗した公開担当は結果と残る監視を統括へ返し、修正を統合した次の公開単位を待つ間は進行中の公開を占有しない。
公開担当は7項目のCI記録を統括へ渡し、専用worktreeの`CI修正担当`へ直させる（本節は自ら直す原則の例外である）。
全体検証の失敗も同じ修正系列として数え、`exec-review`の起動条件は本書「修正系列」の手順4と同じである。
手順は本書「検証またはCIの失敗」にある。

## 検証またはCIの失敗

公開を直接実行するメイン・リポジトリ担当と、`agent-toolkit:atk-mode/roles/session-termination.subagent.md`の公開担当が、全体検証かCIの失敗を受けた時の手順である。

1. 最初に観測した失敗から、CIの成功か本工程の終了までを1つの修正系列として扱う。
   `agent-basics:bugfix`を起動し、ログ、参照実装、期待値から直接原因を特定して、本書「修正commitが必要なCI失敗を修正するエージェント」の7項目のCI記録を持つ。
2. 修正が必要なら、統括が`agent-toolkit:atk-mode/roles/exec.parent.md`に従い、通常のレーンの専用worktreeを対象作業ツリーとする`CI修正担当`を起動する。
   主作業ツリーを公開担当へ渡さず、修正は新しいcommitとして通常の検証・必要なレビュー・`atk lane integrate`の直列統合を経て次の公開単位へ入れる。
   原因commitに対応する保存済みの計画があれば、本書「修正系列」手順1の`入力計画`の取得と、修正系列の終了時の再保存を公開担当が行い、計画の`private-notes/plans/`からの相対パスと再保存の結果を引き継ぎ記録へ残す。
   CI修正担当から受け取った修正commitと`検証結果`は引き継ぎ記録へ残す。
3. 手元で対象条件の成否を観測できない修正は、本書「修正系列」手順3の先行CIへ進む。
   公開担当が認可済みの作業refへのpushと監視を担い、CI修正担当の書き込み終了を確かめてから始める。
   先行CIの結果のSHA・ref・対象ジョブと、正式公開のcheck集合を区別し、修正合格には対象ジョブの実行と成功を求める。
4. 本書「修正系列」手順4の起動条件に当たる修正では、実行レビューを1件起動する。
   `レビュー基準: 計画`の表は計画の再保存時に、`レビュー基準: CI記録`の表は修正系列の終了処理時に公開担当が保存し、結果を引き継ぎ記録へ残す。
5. 修正commitを受け取るたびに、通常のレーンで版数、manifest、生成ファイルと検証を確かめ、統合後の完全OIDを次の公開単位として確定する。
   公開済みの原因commitは書き換えず、次のOIDのpushと新しいbaselineでCIを確かめ直す。
   pushする範囲は変えず、キューの操作はまだ`adopt`していないAWIだけに行う。
6. 再push後に新しい失敗が起きた場合は、新しい原因commitについて対応する計画の有無を判定し直し、手順1へ戻る。

返す報告に含める項目: 修正系列の開始時のHEAD、修正回数、各修正の原因と対処、起動したレビューと結果、成功と判定したrun（先行CIと正式公開を区別）、再保存した計画と表、未確認のジョブと残る差。
