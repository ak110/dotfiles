# 委譲の継続と復旧

起動済みの担当を同じ識別子で続けるか、新しい担当へ交代させるか、障害の後にどう起動し直すかを決める手順書である。
方針: 起動した担当は、起動した者が終了を観測してから次の担当へ移す（原則7、`agent-basics:writing-standards/references/quality-principles-ownership.md`）。
同じ作業へ書く主体を2つ作らず、検収済みの成果は保って残る工程だけを渡す。
該当する節だけを実行する。

| 条件 | 行動 |
| --- | --- |
| 委譲済みの主題を追加で調べる、答える、続きを頼む | 本書「継続と新規起動」 |
| Claude Codeの`Agent`ツールで起動した担当を続ける | 本書「継続と新規起動」の後に本書「Agentツールの継続」 |
| Codexで元担当を回復、置換、再起動、中断する | 本書「後続操作の共通先行条件」 |
| 委譲先を止めた後に起動し直す | 本書「停止した担当の成果の引き取り」 |
| 起動の後に可用性の障害や利用上限を観測した | 本書「代替起動」 |
| `agents_server`のMCPサーバーが再起動した | 本書「MCPサーバーの再起動後」 |
| 会話の圧縮、上限での停止、交代の後に状態を戻す | `agent-toolkit:atk-mode/references/work-contract.md`「圧縮と再開の後の復元」 |

## 継続と新規起動

1. 委譲済みの要求を自分で精読、調査、回答する前に、元の担当へユーザーの原文、未確定の論点、参照する記録を渡して調査と技術判断を任せる。
   元の担当の文脈を使い直すためである。
   稼働中なら追送し、終了後は以下の条件で継続か新規起動を選ぶ。
   委譲元は認可、全体の調整、検収を担い、返った根拠を確かめる。
2. 同じ担当へ同じタスクの未完了の作業、指摘への対応、再レビューを頼む時だけ、既存のsessionを継続する。
   稼働中は同じ`session_id`へ`send_message(session_id, prompt, timeout)`を送る。
   完了済みなら起動時と今回の工程の`model_type`が一致することも確かめる。
   サーバーは選んだengine、model、現在のeffortを保持するため、可用性による候補の切替や候補列の設定変更の後も同じ担当を続けられる。
   effortだけを変える時は`agent-toolkit:atk-mode/references/model-settings.md`「同じ会話のeffortの上げ下げ」に従い、同じ識別子を続ける。
   サーバーは実行中のターンへのsteer、終了後のreply、保持期限を過ぎた後の再開を選ぶため、管理元のプロセスが終わっていても継続できる。
3. 次の場合は、検収済みの状態を渡して新しいsessionを起動する。
   - `model_type`が一致しない、担当かタスクが変わる、処理が中断された、完了通知を配送できない、前提が無効になった。
   - レーンの担当かCI修正の担当を交代させる（前任の識別子は使い直さずに新しく起動する）。
   - 独立したレビュー、別の観点の評価、先行の履歴を前提にしない検証をする（手順1の重複した調査とは別の扱いとする）。

   レビュー指摘への対応はレーンの担当のsessionを続け、続けられない時だけ検収済みの状態と指摘の所在を渡してレビュー修正の担当を起動する。
   同じ計画の起草、実装、変更範囲の検証は、同じレーンの担当が同じworktreeで行う。
4. 継続の本文を組む。
   計画、進捗ログ、保存済みのレビュー指摘管理表に状態があれば、絶対パス、対象のID、未記録の差分だけを渡す。
   記録が無ければ、未完了の事項と検収済みの状態を本文へまとめ、必要なレビュー表は委譲元がmanaged-tempに作って絶対パスで渡す。
   1つの応答で複数の継続を送る時は、送信の前に宛先の識別子と本文の組を確かめる。
5. 配送を確かめる。
   `send_message`のタイムアウトは、配送の成否が未確定であることだけを示す。
   継続の受理か、その要求による新しいターンの開始を観測してから配送の完了とし、待機を続ける。
   `wait`の`status=completed`や`agent_message`の文字列の一致だけでは、配送の判定に足りない。
   確かめられない場合は、再送も継続不能の判断もせず、続行できない理由として委譲元へ報告する。
6. 継続不能は、継続の手段を実際に呼んだ結果で判定する。
   `send_message`が役割の`model_type`の変更を理由に未配送を返したら、同じ識別子へ再送せず、`start`の`handoff_from`へ前任の識別子を渡す。
   前任の起動入力とセッション記録を一意に復元できた場合は後任の起動を確かめてから未配送の指示を渡す。
   復元できない場合や`unknown session: <session_id>`の場合は確認できた記録と残る工程を通常の`start`へ渡す。
   識別子の体系の違いを示すエラーと、`wait`の`session retention expired: <session_id>`は、継続できる状態として扱う。
   保持した識別子を見失ったら、終了や失敗と推測する前に、公開の一覧と個別の照会で探す。
7. 担当が安全上の拒否ではなく単に早く返した場合は、残工程と完了条件を同じsessionへ追送して完遂を求める。
   自分で処理できる作業を残した返却が繰り返される場合は、再送を重ねる前に、交代と作業単位の組み直しを比べる。
   交代させる時は前任の終了を確かめ、検証済みの成果と未完了の作業を後任へ渡す。
   安全上の拒否を受けた作業は、追送やモデルの変更で再試行しない。
   切り離せる作業を別の担当へ渡す時は、適用する制約と対象外の範囲を明記し、確認済みの成果と残工程を既定の工程モデルで引き継ぐ。
   通信の失敗による継続不能とは分けて判断する。
   停止や失敗の反復の原因が既存の不良なら、欠陥の処置は回復と別に決める（process-wiの実行中は`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「即時対応」）。
8. ユーザーが介入した時は、`agent-toolkit:atk-mode/playbooks/review-fix.md`「担当種別ごとの修正」で採否を確定した差分だけを追送する。
   担当を止めるのは、対象か前提が無効になり、続けると誤った成果物ができ、稼働中の作業の完了まで待てない場合に限る。
9. `start`の`handoff_from`で`model_type`を省くと、前任の起動時に`model_type`を明示していなければ現行の役割設定を使う。
   前任が工程名を明示して起動した場合は、その工程名を引き継ぐ。
   候補列を直接指定した前任の値は継承しない。
   後任の工程名か、上書き区分と根拠を付けた候補列を明示する。
   現在の設定へ戻すには、前任の役割に定めた元の工程名を`model_type`へ明示する。
10. 交代の時は、`agent-toolkit:atk-mode/references/work-contract.md`「会話の少量取得」で全体の要求と最新の変更を読み、同書「引き継ぎ記録」の記録と比べる。
    書き込み権限を移す時は`agent-toolkit:atk-mode/playbooks/delegation.md`「作業ツリーの保護」に従う。

### Agentツールの継続

Claude Codeの`Agent`ツールで起動した担当には、`agents_server`の`send_message`の代わりに`SendMessage`を使い、本書「継続と新規起動」に次を加える。

- 完了報告を返して止まった識別子も、同じ担当へ同じタスクの続きを頼み、継続の直前に確かめた実効の`engine`、`model`、`effort`が起動時と一致する場合だけ、`SendMessage`で再開してよい。
  継続の本文には、前に作成・読み取りしたファイルでも書き込みの直前に現行の内容を取得し直す条件を入れる。
- 完了通知の配送先はプロバイダーと構成で変わり、3階層以上の配送先は確かめていない。
  起動結果のIDへの`SendMessage`の成功と、送信後の対応する完了通知の受信で、継続の成立を判定する。
- 担当とタスクの組が違う、実効の3値が一致しない、完了報告を配送できない、前提が無効になった、処理が中断された場合は、止まった識別子を使い直さずに新しく起動する。
  参照できる記録があれば、絶対パス、対象のID、未記録の差分だけを渡す。
- `SendMessage`が`No transcript found for agent ID: <識別子>`で失敗したら配送不能とし、新しく起動する。
  識別子が変わった場合は、タスクの出力先のディレクトリの識別子を`ls`などで旧識別子の配下と突き合わせる。

### Codexの組み込み委譲の継続

Codexの`spawn_agent`で起動した担当へ追加の作業を頼む時は、終了済みか待機中の担当へ`followup_task`を使う。
`send_message`は実行中の担当へメッセージを足す時だけに使う。
Codexの`send_message`は新しいターンを始めず、終了済みの担当へ送った内容はキューに残る。
待機は、`followup_task`が受理され、担当の新しいターンの開始か結果の返却を観測した時に成立する。
`wait_agent`のタイムアウトが続く時は、再送の前に`list_agents`で対象の状態を確かめる。

## 後続操作の共通先行条件

Codexで元担当（同じ作業のために起動済みの委譲先）を扱う時に適用する。
元担当が無い初回の起動は`agent-toolkit:atk-mode/references/model-settings.md`「工程別モデル設定」に従う。
クライアントの接続の確立中か`thread/start`の前に可用性のエラーが起き、状態の照会でsessionが未生成で元担当も無いと確かめた場合も、初回の起動と同じに扱う。
それ以外の代替起動と、sessionか元担当が生成された後の操作は、次の条件に従う。

1. 元担当の回復、置換、再起動、代替起動と、`interrupt_agent`による中断は、ユーザーの明示の要求、終了か失敗への状態の遷移、タスクの契約上のキャンセルのどれかを確かめた時だけ行う。
2. 回復、置換、再起動、代替起動の前に、元担当の終了と書き込み権限の解放を確かめる。
3. `list_agents`が元担当を`running`と返す間は、その状態を受け入れ、後続の操作を保留する。
4. ファイルの差分、HEAD、更新時刻、無応答、経過時間から停滞を推測しない。
   補助の観測や催促の結果だけを根拠に後続の操作を始めない。
5. 元担当を置き換える新しいthreadは、この条件を満たしてから起動する。

## 停止した担当の成果の引き取り

委譲先を止めた後は、起動し直す前に止めた時点の成果を検収する。

1. 完了の条件を満たしていれば、委譲元が成果を引き取る。
2. 未完了なら、委譲元が残りを引き取るか、完了した工程、試したやり方、確かめた失敗を渡して続きから起動し直すかを、`agent-toolkit:atk-mode/playbooks/delegation.md`「要否判定」で選ぶ。
   書き込みの所有権を引き取る時は同書「作業ツリーの保護」に従う。
3. レーンの担当を新しいsessionへ移す時は、検収済みの直前のcommitの短縮OID（7文字以上で一意）、完了した工程、残りの工程を渡す。
   状態の記録があれば本書「継続と新規起動」の手順4に従い、無ければ委譲元がmanaged-tempにレビュー指摘管理表を作って絶対パスで渡す。
4. レビューの担当のsessionを続けられない時は、同じ`model_type`で新しいレビューの担当を起動する。
   実行レビューでは`agent-toolkit:atk-mode/references/exec-review-launch-handover.md`の入力（`レビュー種別: 引き継ぎ再レビュー`、`前回確認版`、`round`、作り直した`review_contract`）を渡す。
   他のレビューの役割では、その役割の`<役割名>.parent.md`が定める引き継ぎ再レビューの入力を渡す。
   レビュー指摘管理表とレビュー対象のHEADは担当が自分で解決するので渡さない（役割文書が宣言していない入力は`start`が拒否する）。
   ラウンド番号は`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「ラウンド番号の保持先」に従い、管理表の最大値から続ける。
   新しい担当は、解消済みの指摘を調べ直さず、未解消の行とそのラウンドの確認範囲だけを扱う。

## 代替起動

`agents_server`の起動時の候補の切替はサーバーが行う。
本節は、主に`Agent`ツールの起動と、起動後に観測した障害に適用する。

1. 利用不能時はサーバーの自動切替を使う。
   自動切替の不具合を観測した場合に限り、失敗の根拠を添えて`model_override=fallback_failure`で代替起動する。
2. 委譲先の作業やツール入力の失敗は、モデルを替えずに原因を直す。
3. 利用上限での候補切替・解除待ち・再開はサーバーに任せる。
   ユーザーが切替を指示した時に前任が実行中なら、`kill`で終了を確かめる。
   ユーザーが即時停止を求めたら`force=true`を指定する。
   `start`へ`handoff_from`と後任の候補列を`model_type`で渡し、`model_override=user_instruction`と指示の要旨を添える。
   ユーザーが`atk config`の工程別のモデル設定を変えた場合は、その変更を切替の指示として扱い、候補列を省いて現在の設定で引き継げる。
   この場合`agents_server`は前任を終了して引き継ぎの起動を案内するため、委譲元はその終了の結果から後任を起動する。
   引き継ぎの起動は、新しい会話へ起動の本文、追送、各turnの最終応答を要約せずに渡し、前任の会話を置き換える（Claude、Codex、Antigravity、OpenCodeに共通）。
4. ユーザーの明示の指示が無い限り、設定ファイルを書き換えたり`atk config set`を実行したりしない。
   設定はユーザー単位の1つの値として全セッションで共有され、並行する他のセッションへ影響するためである。
5. 代替の候補は本書「代替時の組合せの目安」から、障害を観測した時点の状況で選ぶ。
   上位の行から軽量の行へ向かい、各行では`codex`列、`claude`列の順を目安に、観測した障害と各組合せの可用性で決める。
   該当する組合せは`engine`と`model`の一致で判定し、失敗した組合せが表にあれば同じ行のもう一方から試す。
   engineの実行機能を呼べない組合せは利用不能として外す。
   残る全ての候補が失敗か利用不能なら打ち切り、`agent-toolkit:atk-mode/references/model-settings.md`「工程別モデル設定」に従って結果を返す。
6. `Agent`ツールの後任には、前任の起動時の本文と、`引き継ぎ記録先`があればそれを`（継続）`として渡す。
   `atk run-script session-review-prepare`が生成した`conversation.md`を読み、引き継ぎ記録と合わせて確定事項と残る工程を戻し、追加の入力と各ターンの最終応答は全文を渡す。
   詳細は`atk run-script session-review-evidence -- --codex-thread-id <id>`か`--claude-session-id <id>`に`--detail <記録位置>`を付けて照会する。
   コマンドを実行できない後任へは記録ファイルの絶対パスを渡し、Antigravityの前任は`atk agents logs <session_id> --format markdown`の出力を渡す。
   後任には、完了済みの操作と成果を実物で確かめ、最新の指示と残る認可の範囲で進めるよう指示する。
7. 起動後のターンでそれ以外の可用性の障害が確定したら、前任の終了と書き込み所有権の解放を確かめ、終了の結果の`next_action`に従って`start`へ`handoff_from`だけを渡して1回起動する。
   後任の`session_id`を追加入力の送信先と待機の対象にする。
   同じ障害が続く場合は自分でできる範囲を進め、委譲が欠かせない工程は未完了として委譲元へ返す。
8. 委譲先は、自分の判断で設定と違うengineやモデルへ切り替えない。
   `agent-toolkit:atk-mode/references/model-settings.md`「工程別モデル設定」の定めで結果を返す。

### 代替時の組合せの目安

本節の表は本書「代替起動」の候補の選定だけに使う。
対応と得手不得手は運用上の目安であり、モデルの能力を厳密に比べた結果とは別物である。

| レベル | `codex` | `claude` |
| --- | --- | --- |
| 上位 | `gpt-6-sol/medium` | `opus/medium` |
| 中位 | `sol/medium` | 用途に応じて`opus/medium`または`sonnet/medium` |
| 軽量 | `gpt-6-luna/medium` | `haiku/medium` |

- 同じ行の`codex`と`claude`を相互の代替とし、effortは表の値を使う。
  行の間で世代がそろっている必要は無い。
- 通常は上位の行を選ぶ。
  中位と軽量の行は、工程別のモデル設定の値がその行に当たる場合か、内容が確定したリスクの低い機械的な作業に限る。
- 表に無いモデルは、表の組合せと同等以上の能力を確かめられる場合だけ代替に使う。
- effortを指定できない実行環境で表の組合せを満たせない場合は、`codex`列か上位の行を選ぶ。
  Claudeのeffortはエージェント定義のfrontmatterで決まり、frontmatterを持たない起動では指定できない。
- 差分の逐条の確認や欠陥の列挙が主な成果の工程は`codex`列、複数の案の比較や設計の確定が主な成果の工程は`claude`列を選ぶ。

## MCPサーバーの再起動後

1. 元担当の状態を確かめる。
   MCPサーバーの再起動の後も、session登録簿を通じて同じ`session_id`が解決される。
   結果の観測と会話の再開に使えるのは、終了が確定した記録だけである。
   正常に止まったサーバーは、実行中だったターンを`interrupted`として公開する。
   強制終了で`running`のまま残ったCodexの記録は、どのサーバーもそのsessionを持たず、委譲先CLIのプロセスが終わり、Codexのthreadの記録がターンの終了を示す時、`show`、`send_message`、`kill`の照会で終了状態として引き継がれる。
2. 旧サーバーが応答しないまま残るか、旧サーバーの下で委譲先CLIが作業を続けている場合は、所有サーバーを失った実行中のsessionである。
   `show`か`atk agents show`の出力で、`status`が`running`かつ`ownership`が`owner_lost`であることで見分ける。
   あわせて`recorded_processes`（所有サーバーと委譲先CLIのPIDと生存）、`owner_root_session_id`、`stranded_notice_count`を確かめる。
   この状態のsessionへの`send_message`は`error.recovery=owner_lost`で拒否される。
3. 作業を続けさせる場合は、`atk agents wait`で終了を待つ。
   旧ルートに残った委譲先の通知は、新しいサーバーの`atk agents wait`、`show`、`send_message`、`kill`の応答で回収される。
4. 続けるための追加の指示が必要な場合は、同じsessionへ`kill`を発行して委譲先CLIを止めてから、同じ`session_id`へ`send_message`を送る。
   新しい`start`で後任を起動すると、旧い委譲先CLIが作業ツリーへ書き続け、書き込みの主体が重複する。
5. `error.recovery=turn_unobserved`はターンの終了が未確定であることを示す。
   同じ作業を新しい`start`でやり直さず、まだ実行中の可能性を添えて委譲元へ報告する。
6. `missing`、`unreadable`、`no_resume_info`は、委譲先CLIのプロセスが残っていないことを確かめてから、そのsessionを失われたものとして扱う。
   起動時の応答か記録からPIDを取れる場合は生存を確かめ、生きていれば終了を待つ。

## 返す報告に含める項目

継続か新規起動かとその根拠、前任の終了と書き込み所有権の解放の確認、引き継いだ範囲とやり直した範囲、代替起動では観測した障害・`atk config get`で確かめた設定値・使った組合せ・見送った組合せとその理由を返す。
