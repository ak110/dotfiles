# 固定課題による多ターン試行

<!-- 節をまたぐ手順を通し番号で示す。 -->
<!-- markdownlint-disable MD029 -->

指示文の改訂前後を、独立した評価対象エージェントに同じ課題を実際に解かせて比べる、手動の検証の手順書である。
対話課題では、独立したユーザー役が質問に応じて要件を段階的に開示し、この手順書を実行する仲介担当が両者を中継して、対話履歴の全体と提出された成果物から採点する。
採点の情報を評価対象へ漏らさず、同じ条件で比べ、機能の未達と試行の不成立を分ける。
判定は評価対象の申告からではなく、観測した記録と成果物から取る（`agent-basics:writing-standards/references/quality-principles-facts.md`）。
版を比べる判定は、記号と版・モデルの対応を知らない別の文脈が行う（`agent-basics:writing-standards/references/quality-principles-verification.md`）。
試行は費用が高いため、構造に関わる変更と、本書「大きな削減の3条件比較」だけに使う（`agent-toolkit:atk-mode/playbooks/refine-prompt.md`「評価する場合」）。

## 素材と準備

1. `atk run-script multi-turn-trials -- --list`で課題名、種別`kind`（`dialogue`か`single`）、開示条件を取得し、確かめたい結果に合う課題を選ぶ。
   合う課題が無い時は、本書「実セッション由来の小課題による比較」で課題を作るか、単発評価の結果で判断して試行を未実施と報告する。
   固定課題の素材は`${CLAUDE_PLUGIN_ROOT}/skills/atk-mode/fixtures/multi-turn/`にあり、出典と改変の内容は各課題の`private/trial.json`の`source`にある。

| 課題 | 成果物で確かめる結果 |
| --- | --- |
| `attachment-paths` | 添付の参照・関連付け・削除のパスと従来API |
| `weekday-queries` | Sunday=1の維持と別の公開ISO問い合わせ |
| `batch-conditions` | 異なる条件の複数要素、順序、空入力と単体API |
| `display-spaces` | 空白を含む表示の回復と正常表示の維持 |
| `verification-status` | 未実行と実行済みの期待失敗の分類 |
| `skill-selection` | 依頼と説明による初期選択と、本文を読んだ後の追加選択 |
| `test-selection` | 隠れた依存を含む変更から実行すべきテストの選択 |
| `goal-discovery` | 目標から注文集計CLIを完成させ、既存APIを保つ |
| `strategy-update` | 単位の異なる明細と担当間の矛盾を整合させ、既存結果を保つ |
| `purpose-boundary` | 目的の確認後に、確定した改善領域を要求へ反映する |
| `protection-removal-agent`、`protection-removal-user` | 追加審査の撤去を、自ら決める場面と本人へ確認する場面 |
| `forbidden-guidance-agent`、`forbidden-guidance-user` | HTTP 403の案内の修正を、自ら決める場面と、表示箇所・今後の対象への適用・費用の上限を本人へ確認する場面 |
| `overrun-retry-agent`、`overrun-retry-user` | 超過の確かめ方を、過去の回答の範囲から自ら決める場面と、回答が再実行の禁止を明示していて本人へ確認する場面 |
| `assumption-transcription` | エージェントが補った前提を、ユーザーの要求として書き写さない |
| `suppression-scope-agent`、`suppression-scope-user` | 抑止の範囲を、原文どおりに自ら決める場面と、原文に無い延長を本人へ確認する場面 |
| `merge-depth-agent` | 統合の深さを本人へ尋ねず、公開事実から群ごとの扱いを決める |
| `scope-excel-first`、`scope-excel-correction`、`scope-preserve-existing` | 指定された取り込みの追加、依頼外の追加と拒否の除去、作業前からある別形式の維持 |
| `scope-shared-options`、`scope-past-decision` | 全画面を同じ仕様にそろえ、前提が変わった過去の判断を今の認可へ照らす |

- 名前が`-agent`と`-user`で終わる課題は確認判断の対で、依頼文と`task.py`が同じで`facts.json`だけが違う。
  確認の基準を変える時は両方を同じ条件で試し、不要な質問と必要な確認の省略の両方向を比べる。
- `trial.json`の`examples`と、単独課題`verification-status`、`skill-selection`、`test-selection`の保存例は採点の形式を確かめる合成素材であり、実モデルの比較実績とは分けて扱う。
- `skill-selection`と`test-selection`の採点対象は提出した識別子による選択判断だけである。
  実モデルで比べる時は、本文を開いたことと依存を探したことをsession記録（開いた本文、検索と読み取りの順序）で確かめ、入力・出力トークン、所要時間、費用を併記する（取れない値は「未取得」）。
- `test-selection`の手動比較では、最初の情報だけで選ぶ方式と、検索と読み取りの結果を次の判断へ反映する方式を分けて記録し、実際に実行するテストの範囲はこの結果によらず元のまま保つ。

2. 版と課題ごとの作業ディレクトリをmanaged-tempの中に作り、まだ存在しない新しいパスへ公開素材を準備する。

   ```sh
   atk run-script multi-turn-trials -- prepare --case attachment-paths --output <公開素材の新規絶対パス>
   ```

   複製されるのは課題の`public/`（`request.md`、`task.py`と課題の素材）だけである。
   仲介担当が付ける名前（作業ディレクトリ、評価対象の文書の複製、依頼文）は、プロジェクトらしい名前にする。
   評価や比較を示す語（eval、test、trial、judge、grade、rubric、score、compare、benchmark、candidateなど）と版を示す語（old、new、v2など）は避ける。
   版かモデルを比べる時は、各試行の保存先を記号（`A`、`B`など）で名付け、記号と版・モデルの対応は比較を指示した者だけが持つ。
   評価対象の読み書きは公開素材と評価対象の文書の複製に限って課題のコードだけを変えさせ、`private/`、採点のテスト、正解、ユーザー役の入力とその置き場所は仲介担当が隠して管理する。
   同じOSの上のディレクトリの分離は完全なsandboxではないため、意図しない読み取りが無かったかを仲介担当がsession記録で確かめる。
   評価対象が`private/`、採点のテスト、正解、ユーザー役の入力のどれかを読んだ試行は、開示の規則の違反として不成立とする。

## 両役の入力と返却

3. 非公開の情報を事前に知らせないため、次の入力で、`agent-toolkit:atk-mode/playbooks/delegation.md`の`agents_server`の自由文の委譲により両役を独立した新しいセッションとして起動する（`single`は評価対象だけ）。
   入力と返却の形式は依頼の本文で指定する。
   起動のオプションはスキーマで確かめ、モデル名と設定を保存する。

| 役割 | 渡す入力 | 返却 |
| --- | --- | --- |
| 評価対象 | 適用する文書の本文、公開素材、公開依頼、公開素材だけの書き込み範囲、課題固有の終了条件 | 応答全文、質問か変更の説明、提出した`task.py`の絶対パス、完了宣言 |
| ユーザー役 | 公開依頼、選んだ条件、`trial.json`の要件と質問による開示条件だけ、下の開示の制約 | 応答全文、開示した要件の識別子、対応する質問の引用、情報源 |

   評価対象への依頼はユーザーが送る依頼の形で目的を書き、試行や評価であること、モデルの名前、採点の基準、他の版や他の試行の存在、適用した規範やファイルの列挙の求めは除く。
   最初の依頼には`public/request.md`の内容をそのまま転送する。
   `trial.json`の成功例と失敗例、採点のテスト、対話の判定基準、正解のコード、採点の結果は両役へ渡さず、ユーザー役へは必要な要件と開示条件だけを抜き出した入力を保存して渡す。
   ユーザー役は、評価対象から適切な質問があった要件だけに答え、知らない内容や答えられない質問には情報を持っていないことをそのまま伝える。
   表示課題の`no-followup`では、ユーザー役は追加の回答が得られないことだけを返す。
   `observations-only`では、質問に関係する画面の表示、入力、操作の結果などの客観的な観測だけを答える。
   内部の実装と「空白が消えている」という原因の正解はユーザー役にも伏せ、評価対象は追加の回答の有無によらず、初期報告の再現手順と課題のコードを自分で調べて原因を特定する。

## 仲介と終了

4. 開示の範囲と対話の連続性を守るため、同じ課題では双方のセッションを保ち、評価対象の応答全文をユーザー役へ、ユーザー役の応答本文だけを評価対象へ転送する（`single`は仲介を省く）。
   ユーザー役が返した開示要件の識別子などの管理用の情報は、仲介担当が持つ。
   送信の受付と応答の完了を分け、`atk agents wait`で返却と終了状態を確かめてから次を送る。
   応答を終えたセッションへの追加の送信が、同じ対話の次のターンになる。
   待機、状態の観測、中断は`agent-toolkit:atk-mode/playbooks/host-claude-code.md`と`agent-toolkit:atk-mode/playbooks/host-codex.md`に従う。
5. `dialogue`は提出物を伴う完了宣言か、評価対象の応答が`trial.json`の`max_rounds`（固定課題は6回）に達した時、`single`は課題固有の終了条件で、終了を観測する。
   この上限は、固定課題を同じ費用と条件で比べるための試行専用の制約である。
   上限に達した時点で未解決の要件は未達とし、起動の失敗、実行のエラー、開示の規則の違反は試行の不成立とする。
   起動した全てのターンの終了状態を確かめてから、試行の結果を返す。

## 保存対話と採点

6. `dialogue`では仲介担当が履歴全体を読み、開示の規則の違反、`trial.json`の対話の基準への適合、質問と回答の論理的な対応を採点する（`single`は本書「単独作業の採点」）。
   判定の根拠は、評価対象の完了宣言や各役の自己評価からではなく、保存した対話、session記録（実際に開いたファイル、検索と読み取りの順序）、提出物から取る。
   版かモデルを比べる時は、記号と版・モデルの対応を知らない新しい文脈を、`agents_server`の自由文の委譲で判定役として起動する。
   判定役へは、比べる全ての記号の対話（`model`と`document_version`は空）、`trial.json`の対話の基準、仲介担当がsession記録から取ってモデルの情報を除いた抜粋（開いたファイル、検索と読み取りの順序）を記号付きで渡す。
   判定役は全ての記号を1回でそろえて判定し、記号ごとに基準ごとの判定、理由、根拠のターン番号を返す。
   対話JSONの`model`と`document_version`は、判定を受け取った後に記入する。
   採点のCLIが確かめるのは判定項目の網羅、引用したターン番号、開示条件への適合までで、対話の意味の妥当性は判定する担当が決める。

   保存する対話JSONは次の項目を持ち、ターン番号は1から数える。

| 項目 | 値 |
| --- | --- |
| `case`、`condition` | 課題名と開示条件 |
| `document_version` | commitと対象パス、または保存した文書本文の絶対パス |
| `model`、`settings` | 実際のモデル名と起動設定のオブジェクト |
| `sessions` | `candidate`と`user`の別々の実session識別子 |
| `termination` | `submitted`、`turn-limit`、`error` |
| `execution_errors` | 起動と実行の障害の配列。無ければ空配列 |
| `turns` | 初期依頼から交互の`role`（`user`、`candidate`）と応答全文`text` |
| `disclosures` | 開示ごとの`requirement`、`question`と`answer`（各`turn`と逐語の`quote`）、`matched`（仲介担当が対応を妥当と認めたら`true`）、`source`（`requirements`か`observations`） |
| `disclosure_audit` | 全userターンの番号`reviewed_user_turns`と、意味で判定した違反の配列`violations` |
| `behavior` | 基準ごとの`criterion`、`verdict`（`適合`、`不適合`、`未判定`）、`reason`、`evidence`（`role`、`turn`、`quote`） |

   不成立の試行でも取得した対話は保存し、取得できなかったセッションと根拠は未取得と書く。
   入力の検証で拒否された時は、終了コードと診断を保存して不成立に分類する。

7. 保存した情報で採点する（`single`は本書「単独作業の採点」の引数を使う）。

   ```sh
   atk run-script multi-turn-trials -- grade --case attachment-paths --candidate <提出task.pyの絶対パス> --dialogue <対話JSONの絶対パス> --output <結果JSONの絶対パス>
   ```

   `--condition`を省くと課題の最初の開示条件で採点するため、表示課題の`observations-only`では指定し、`--timeout`（成果物のテストの秒数）は省くと10秒になる。
   CLIは提出物を専用の作業領域へ複製して公開操作のテストを実行し、結果JSONの`functional`へ機能テストごとの期待値と実際の値か例外を、`requirements`へ要件ごとの達成か未達と根拠のテスト識別子を出す。
   `behavior`は対話の基準の判定、`test_run`はテストの引数、終了コード、標準出力、標準エラーを持つ。
   終了コードは、0が機能テストに全て合格、1が成果物は成立したが機能の要件に未達、2が試行の不成立か入力の不正である。
   対話の基準の不適合と機能の要件の未達は、別の評価軸として扱う。

### 単独作業の採点

`single`の課題は`--dialogue`の代わりに`--execution`へ実施情報のJSONを渡し、ユーザー役のsession、`turns`、開示の記録と監査は省く。
実施情報は`case`、`condition`、`document_version`、`engine`、解決後のモデルIDの`model`、`settings`（実際の`effort`を含む）、`sessions.candidate`を持つ。
`termination`は提出を観測した`submitted`か障害で終わった`error`とし、障害の文字列の配列`execution_errors`は省くと空として扱われる。

```sh
atk run-script multi-turn-trials -- grade --case verification-status --candidate <提出task.pyの絶対パス> --execution <実施情報JSONの絶対パス> --output <結果JSONの絶対パス>
```

機能テスト、要件別の判定、終了コードの意味は対話課題と同じで、結果の`execution_path`は実施情報の絶対パス、`provenance`はengineを含む起動記録を持つ。
単独作業の`behavior`は空の配列であり、判断の内容は判定する担当が作業の記録から判定して比較要約へ残す。

### 作業構成・方針更新・目的確認の3課題

`goal-discovery`と`strategy-update`は`single`、`purpose-boundary`は`dialogue`で、公開APIと入力の契約は`public/README.md`、行動の判定基準は`private/trial.json`、固定の期待値は`private/grade.py`にある。
単独の2課題は追加の回答をせず、初期依頼から提出までの応答とツールの操作・出力を保存し、行動の基準ごとの判定、理由、根拠の保存先と引用を比較要約へ書く。
`strategy-update`の再開試行では、評価対象が一度応答を終えた時点で目標、観測、未完了の作業を作業領域へ保存させ、同じ担当へ「保存した目標・観測・未完了作業を確認して続けて」とだけ追送する。
再開の前後の入力、終了状態、復元に使った証拠を保存する。
`purpose-boundary`のユーザー役へは、`trial.json`の目的と範囲に関する回答と開示条件だけを渡し、機能の採点ではその回答で確定した要件を確かめる。
回答の前に選べる目的の一般について、1つの目的を正解として扱わない。
同じ公開素材での手動の対照として、目指す状態を最初から明記した依頼と、性能などを例示する広い依頼を、別々の新しい文脈で試す。
前者は目的の内側の技術判断を続けられるか、後者は例示を閉じた範囲へ変えずに必要な目的の確認ができるかを観測し、固定課題の結果とは入力条件を分けて保存する。

## 改訂前後の比較と受領

8. 版ごとに、同じ素材、モデル、起動設定、開示と終了の条件、採点基準で手順2〜7を繰り返す。
   各役は新しいセッションとし、固定の初期入力だけを渡して、以前の履歴、正解、指摘、採点結果を遮断する。
   対話課題は、表示課題の2条件を含む全条件の結果を課題と条件ごとに並べ、版の改訂で変わった判定とその根拠を確かめる。
   受領するものは、評価した文書の本文と版、起動の引数の記録、各担当への入力、対話の全体、各ターンの終了状態、提出物、結果JSON、テストの実行ログである。
   比較の記録から全ての保存ファイルへ絶対パスで届くようにし、実行レビューの担当が判定の根拠を直接確かめられる状態を保つ。
   試行の結果は単発評価の指摘一覧と分けて扱い、少数の固定課題で得た差はその課題での観測として報告する。
   素材と結果の保存、不要になったファイルの回収は`agent-toolkit:atk-mode/playbooks/managed-temp.md`に従う。

## 実セッション由来の小課題による比較

規範の条文が誤った誘導や不要な作業を生んでいないかを確かめたい時に選ぶ、任意の検証である。
元の依頼、初期状態、モデルをそろえて1文だけを変えて比べる方法（[OpenAIのソフトウェア保守事例](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)）を、この試行の環境へ当てはめる。

実際の依頼、入力、初期状態の成果物、観測した誤った誘導か余分な作業の記録から、独立して完結する小課題を作る。
評価対象へ示す公開の依頼と素材を仲介担当だけが持つ要件と評価基準から分け、元の会話と独立した新しいセッションで試し、実環境に作用する操作の対象は課題専用の素材へ置き換える。
読み書きの範囲の制限と実行後の読み取りの確認は本書「素材と準備」に従い、保存の形式へ整える前の課題は、その公開操作を実行して要件の充足を確かめる。

同じ依頼、初期状態、モデル、effort、起動の引数、開示と終了の条件、評価基準で、現行の規範と1文だけを変えた規範をそれぞれ新しい文脈で実行し、モデルやeffortの違いは文書を固定した別の検証として比べる。
確率的な出力を比べる時は、採点基準と候補を固定した時点と実行順の偏りもそろえ、判断に必要な数の独立した反復を選ぶ（回数は課題ごとに決める）。
要件別の達成、成功率、時間・トークン・費用の代表値と分布を分け、不成立の試行と良好な試行だけを選んだ集計を区別して、全試行を`comparisons.jsonl`へ対応付ける。

提出物の機能と保つべき要件の充足を先に判定し、その上で判断の内容、ツール操作の回数、トークン数、所要時間、推定費用を、根拠のログと対応付けて比べる。
計れなかった指標は推測せず「未取得」とし、少数の試行の差はその事例での観測として扱う。
比較の記録には、両版の文書、初期状態、モデルと設定、対話の全体、提出物、検証の結果、各指標の算出の根拠を対応付けて保存する。

| 結果の例 | 判定 |
| --- | --- |
| 同じ課題で全要件を満たし、不要な読み取りや操作が減った | その事例で品質を保ったまま改善したと判定する |
| 所要時間やトークンは減ったが、保つべき公開機能が損なわれた | 機能の未達と判定する |
| 両版でモデルや初期状態が違う | 条文の変更の効果を示す根拠に使わない |
| 起動のエラーなどの障害で成果物が得られなかった | 試行の不成立とし、機能の未達と区別する |

### 調整用課題と検収用課題

規範案を事例に合わせて直した効果を一般の改善と取り違えないよう、任意で課題を、規範案の作成と修正に使った調整用課題と、案を固定した後に初めて実行する検収用課題に分ける。
両版で入力、モデル、設定、採点基準をそろえ、案の作成と選定に渡す実行記録から検収用課題とその採点結果を外す。
検収用課題の結果を見て案を直したら、その課題は以後調整用として扱い、別の未使用の課題で検収するまで結論を試した事例の範囲に留める。
検収用課題か採点結果が案の作成側へ渡った場合と、ネットワークを含むアクセスの範囲で分離を保証できない場合は、その限界を比較結果へ残し、その課題の結果を調整用課題の結果として扱う。
両方の課題で改善した時だけ未使用の課題でも改善を観測したと報告し、調整用課題だけの改善と検収用課題を用意しない比較の結論は、試した事例での改善に限る。

### 課題の選別と保存

比較を担当したエージェントは、現行の規範とモデルでも対象の誤りや判断の差が実際に生じうることを試行の記録から確かめ、再比較に使う小課題を保存する。
差が出ないほど容易な課題は保存せず、再実行で比較の価値を失った課題は保守の時に整理する。

1. 比較に使った依頼、初期状態、判断の差を生む条件を小課題へ残し、個人名、実パス、業務データなどは課題専用の値へ置き換える。
2. `agent-toolkit/skills/atk-mode/fixtures/multi-turn/<課題名のアンダースコア表記>/`へ、`public/request.md`、`public/task.py`、`private/trial.json`、`private/grade.py`を保存する。
3. `trial.json`に`case`、`kind`（`dialogue`か`single`）、`source`、`conditions`、`termination`、要件とテストIDの対応`requirements`、判断基準`behavior_criteria`、成功と失敗の保存例`examples`を書く。
   対話課題には既存課題と同じ`max_rounds`、要件の開示条件、対話と引用の根拠を書き、単独課題には対話の代わりに実施情報の保存例を用意する。
4. 課題専用の`grade.py`で公開操作と期待値を共通の`grade_fixture`へ渡し、`agent-toolkit/skills/atk-mode/scripts/multi_turn_trials.py`の`CASES`へハイフン表記の課題名を登録する。
5. 一覧、`prepare`、採点を公開のCLIから実行し、公開素材だけが複製されること、成功・未達・不成立の区別、既存課題の採点結果を確かめる。

### 比較要約と手動再実行

後から再比較する担当が条件と結果を確かめられるよう、課題ごとの`private/comparisons.jsonl`へ1試行1行の要約を保存し、素材と一緒に版管理する。
比較を担当したエージェントが比較の時に記録を追加・更新し、初回の比較元も同じ形式で残す。
要約には実施日、engine、解決後のモデルID、effort、文書の版、課題の素材と条件・起動設定、課題の用途（調整用か検収用）と候補を固定した時点、要件ごとの結果、判断の過程の要点、取得できた指標と単位・算出の根拠を書く。
未取得の指標は「未取得」とし、不成立の試行は理由を書いて機能の未達と分ける。
対話の全文や大量のログは版管理へ入れず、受領に必要な全記録はmanaged-tempに保ち、要約へ条件と判断の根拠を写す。

評価に使うengineか解決後のモデルIDが要約の値から変わった時は、文書を固定して保存した課題を手動で再実行する（設定名が同じでも、実際に解決されたモデルIDで判断する）。
初期素材、開示と終了の条件、評価基準、比べる対象以外の起動設定をそろえ、要件の充足、判断の内容、取得できた指標の順に前回と比べる。
LLMの試行をCIで自動実行すること、その合否を後続の処理の条件にすること、session記録から課題を自動で作ることはしない。

## 大きな削減の3条件比較

複数の記述をまとめて削る時は、任意の検証として、削る前の版、削った後の版、対象の文書を読み込まない構成の3条件を、同じ課題、初期状態、モデル、effort、起動の引数、開示と終了の条件、評価基準のもとで、それぞれ新しい文脈で比べられる。
採否は`agent-basics:writing-standards/references/agent-documents-additions.md`「削減の判定根拠」で決める。
指標と記録は本書「実セッション由来の小課題による比較」に従って3条件の本文と構成、結果、根拠を対応付け、保存した課題を使った比較は`private/comparisons.jsonl`へ3条件を区別して書く。

返す報告に含める項目: 試した課題と条件、版ごとの結果JSONと比較要約の保存先、要件ごとの達成と未達、試行の不成立とその理由、行動の判定と根拠、取得できた指標（取れない値は「未取得」）、観測の範囲の限定。
