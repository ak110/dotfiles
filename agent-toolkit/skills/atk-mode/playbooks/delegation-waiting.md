# 委譲と背景処理の待機

委譲先とバックグラウンドタスクの終了を待ち、結果を回収するまでの手順書である。
待機中の停滞もここで扱い、待機の異常は`agent-toolkit:atk-mode/references/delegation-wait-anomalies.md`が扱う。
方針: 起動した者が、起動時に返された識別子で終了を観測して結果を回収する（原則7、`agent-basics:writing-standards/references/quality-principles-ownership.md`）。
終了、停滞、不在は、識別子の直接照会と保存出力で確かめ、更新時刻と通知の有無は補助の観測として扱う（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。

## 作業の要否と読む範囲

該当する条件の行だけを実行する。

| 条件 | 行動 |
| --- | --- |
| 待機を始める、待機手段を選ぶ | 本書「待機手段の選択」から上から実行する |
| `atk agents wait`が返った | 本書「`atk agents wait`の応答の扱い」 |
| 待機だけを理由にターンを終える、完了通知でターンが始まった | 本書「完了通知を待ってターンを終える場合」 |
| CI、デプロイ、ユーザーの回答など外部の状態を待つ | 本書「外部サービスの状態変化を待つ場合」 |
| 完了通知が届かない、委譲先の活動の観測値が変わらない | 本書「停滞の検知と巻き取り」 |
| `atk agents wait`が0と3以外で終わった、待機の起動が拒否された、ホストがバックグラウンド待機を止めた、起動前に版の違いが示された | `agent-toolkit:atk-mode/references/delegation-wait-anomalies.md` |
| MCPサーバーが再起動した、`show`が`ownership: owner_lost`を示した | `agent-toolkit:atk-mode/playbooks/delegation-recovery.md` |
| Claude Code固有の操作（バックグラウンド実行の起動形、定期の再確認、完了通知の中継、Code Mode） | `agent-toolkit:atk-mode/playbooks/host-claude-code.md` |
| Codex固有の操作（cell IDとsession IDの回収、二層待機、実行中の担当への後続操作） | `agent-toolkit:atk-mode/playbooks/host-codex.md` |

## 待機手段の選択

| 待機対象 | 待機手段 | 終了の受領 |
| --- | --- | --- |
| 自分のwriterの子 | `atk agents wait` | 終了行の`session_id`と`agent_message_path`の本文 |
| 引き継いだ子 | MCPの`collect_handoff`（`running`なら再発行） | 終了結果。全件回収で`expired` |
| ホストの`Agent`ツールのサブエージェント | ホストの完了通知と委譲一覧 | 完了通知か戻り値と、依頼文で指定した成果物 |
| Codexの組み込み委譲のthread | `wait_agent`と`list_agents` | `wait_agent`の終了通知と照会した状態 |
| ホストのバックグラウンドタスク | ホストのバックグラウンド実行と完了通知 | 実行識別子の終了状態と、出力ファイルの終了状態行 |
| Codexの`functions.exec`のcell ID、`exec_command`のsession ID | `functions.wait`、`write_stdin` | 同じターンで回収した出力と終了コード |
| 外部サービスの状態変化 | 本書「外部サービスの状態変化を待つ場合」 | 終了条件が成立したコマンドの結果 |
| ユーザーの回答 | 定時起動の各回の`atk wi wait --uwi <正式名> --timeout <秒>` | 終了0で対象のUWIの回答を検知 |

どの対象でも完了通知を待機の解除手段とし、`sleep`やCodexの`sleep`ツールによるフォアグラウンドでの時間待ちは使わない。

## 待機区間の構成

1. 結果を回収できる起動形を選ぶ。
   - 完了通知で同じセッションを再開でき、ホストがバックグラウンド実行を公開する待機は、対象の種類と件数によらずバックグラウンドで起動する。
     Claude Codeでは`atk agents wait`、CIとデプロイの監視、終了条件ループを`run_in_background=true`で起動する。
   - 再開の保証が無い場合とバックグラウンド実行が無い場合は、非対話起動のメインも公開の待機手段で同じターンに回収する。
     フォアグラウンドでは、ホストの実行時間上限を待機コマンド自身の上限以上にする。
   - Claude Codeでバックグラウンド実行が無効（`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`）の時は、単独の`atk agents wait`へBashの`timeout=600000`を指定する。
     無効かどうかはSessionStartの通知とBashの入力に`run_in_background`が無いことで判別し、拒否されるバックグラウンド指定は試さずに済ませる。
     CLIは540秒以内に終了コード3で返るため、未終了なら同じコマンドを再発行する。
   - Codexのcell IDとsession IDは同じターンで回収する（回収時間と二層待機は`agent-toolkit:atk-mode/playbooks/host-codex.md`）。
   - 既に起動した実行は、識別子を保持して回収する。
2. 自分のwriterの待機は、引数なしの単独の`atk agents wait`で発行する。
   発行時点の起動中セッションと未回収結果が対象で、待機上限はCLIが算出する。
   外側の`timeout`、パイプ、`wc`などを連結すると、待機が途中で打ち切られるか終了コードが覆い隠される。
   ホストのツールの`timeout`引数の決め方は`agent-toolkit:atk-mode/references/operations.md`にある。
   ルートの明示が必要な環境（`functions.exec`など）では起動応答の`root_session_id`を`--root-session-id <値>`で渡す。
   続行は終了コードと応答だけで判断する。
3. 複数の子を待つ委譲先は、自動再開の範囲を確かめてからターンを終える。
   `agents_server`の委譲先が起動した子セッションは追跡され、全件の終了まで最初の結果が保留され、そのターンにつき1回だけ同じセッションが自動再開される。
   Codexのバックエンドでは組み込み委譲の子スレッドも、Claudeのバックエンドではバックグラウンドのシェル、バックグラウンドのAgent、バックグラウンドへ移ったMCP呼び出しも対象になる。
   自動再開は対象を実際に起動した場合に限り、起動せずに待機を表明しただけなら委譲元が完了を確かめて再開を指示する。
   残工程に使う子の結果は表の手段で同じターンに回収する。
   待機の表明でターンを終えるのは、全件がそろうまで進める工程が無い時に限る。
   過去の自動継続の消費やCLIのidleの状態だけで、未回収の子の観測責任を終えない。
4. 制御が戻ったら、戻り方で次の観測を選ぶ。
   - ホストが観測をバックグラウンドへ移し、その完了通知で同じセッションが再開されると示した時だけ、再発行せずに待機を表明してターンを終える。
   - 観測が自身の上限で戻った時は、本書「待機中の先行実施」の工程を先に進めてから、同じターンで再発行する。
   - 再発行してよいのは、1回の呼び出しが待機時間を消費する観測手段に限る。
     状態照会は、完了通知の不着、終了状態の確認、定時起動の各回など、状態が変わりうる契機にだけ発行する。
   - 実行時間の長いコマンドの実行中は、催促と巻き取りを保留する。
5. 先に届いた独立の待機の通知から、保存出力と終了状態を回収して対応する工程を進める。
   各待機は単一の実行として管理し、別の待機が終わるまでフォアグラウンドやMonitorを占有することは避ける。
6. 終了状態を返しても依頼の返却値を含まない終了は、未完了として扱う。
   終わったターンは以後の通知を出さないため、保持した識別子で同じセッションへ続きを依頼して返却値を得る。
   委譲先が自身の子の終了を待たずにターンを終えた場合も同じに扱う。

## バックグラウンドタスクの所有記録

バックグラウンドタスクは、BashやAgentをバックグラウンドで実行した非同期処理を指す。
所有の根拠は、自身の呼び出しに返された識別子である。
起動の失敗時、時間上限やユーザー操作によるバックグラウンド移行時、MCPのバックグラウンド移行の通知で返された識別子も追跡し、出力本文に現れた同じ文言は根拠から外す。
未完了の処理は起動の集合から完了の集合を除いて特定し、返却本文か保存出力と終了状態を回収する。
割り込みへの回答や会話の圧縮の後に戻る時も、この記録から未終了の実行を選んで同じ識別子で回収し、同じ目的の待機と監視は既存の実行を使う。
公開の状態が`running`の記録の件数だけを理由に、待機を遮断しない。

## `atk agents wait`の応答の扱い

1. 行の形式と待機の成立の判定は`atk agents wait --help`が定める。
   回収行の依頼は`label`で判別し、失敗の行は`error`と`next_action`に従う。
   既回収の`awaiting_reply`行は`session_id`で依頼を識別し、結果の再回収をせず`next_action`に従う。
2. 本文は終了行の`agent_message_path`のファイルにある。
   要約に本文が無い時、後のターンで読み直す時、他の担当へ渡す時は、このファイルを直接読む。
3. 終了コード3と`status: running`は未終了を示し、同じコマンドを再発行して待機を続ける。
4. `notices`は実行中の委譲先からの即時通知で、同じ通知は1度だけ返る。
   本文を保持し、終了行が無ければ同じターンで再発行する。
   `助言依頼:`で始まる通知は`agent-toolkit:atk-mode/playbooks/advice-request.md`で扱う。
5. 終了行は完了報告として扱い、そのセッションを未終了の対象から外して`agent-toolkit:atk-mode/playbooks/delegation-receiving.md`で受領する。
   返った結果はその場で処理し、残るセッションは`atk agents wait`を再発行して待つ。
   全件の終了まで戻らないループやスクリプトで待機を包まない。
6. 回収は結果と通知の削除を伴うため、バックグラウンドへ移った後も含めて、同じ結果を得る待機を重ねて発行しない。
   バックグラウンドタスクの完了通知の後も、同じ`atk agents wait`の実プロセスがしばらく残る場合がある。
   完了通知を受けたら通知された出力ファイルの全体を読んで回収し、残った実プロセスを未回収と見て待機を重ねることは避ける。
   バックグラウンド待機の実行中の進捗は`list`と`show`の活動情報で確かめ、出力の途中の内容は進捗として扱う。
7. 結果は経過時間では破棄されず、配送か`stop`での明示の破棄まで保持されるため、完了通知から時間がたっても回収できる。
8. `終了行:`に`unfinished_waits`を含む結果は、保留を確定した待機表明である。
   `error`の`heldResultFinalized`が真であり、再開したターンの結果ではない。
   件数が0でも完了の返却に数えない。
   待機対象が残っていればその状態を確かめ、続ける作業があれば同じセッションへ依頼する。
   待機の表明かどうかは、`unobservedSessions`の有無以外の情報も併せて判別する。

## 完了通知を待ってターンを終える場合

1. 自動再開の能力があることと、今回の未回収の対象について追跡、結果の保留、継続が成立していることを分けて確かめる。
   待機の未起動や過去の継続の消費を、対象の終了として扱わない。
2. 1回のブロッキング待機（`atk agents wait`か、それを起動したバックグラウンドタスク）は、発行時点の起動中セッション全体を、終了状態を返すまで所有する。
   定期の再確認では、所有されていない対象についてだけ、記録側の状態、完了通知、経過時間に応じた起動の義務を確かめる。
   完了通知の不着を検出した対象と、待機手段が終了状態を返さずに失敗した対象は、所有されていないものとして扱う。
   定期の再確認の設定はホストの手順書（Claude Codeは`agent-toolkit:atk-mode/playbooks/host-claude-code.md`）に従う。
3. 未回答のUWIを持つセッションは、定時起動の各回に`atk wi`で回答の有無を確かめ、回答があれば同じターンで元の作業へ反映する。
4. 定時起動の依頼文には、状態を読み直す手段（計画ファイル、引き継ぎ記録、作業ツリー、タスク一覧）だけを書く（努力目標。可変の状態の写しは実態とずれる）。
   定時起動の発火は停滞時間の起点を更新せず、停滞は実際の観測値で判定する。
5. Claude CodeのStopの時点で未配信の完了通知があり、通知の後に同じセッションの再開が保証され、他のagent-toolkitの検査がブロックしていなければ、ターンを終えて次のターンで回収する。
6. 待機だけを理由にターンを終える時は、次の表の出力にする。
   自動再開の対象は、自身が`agents_server`で起動した委譲先、Codexの組み込み委譲の子スレッド、Claude Codeの通知付きのバックグラウンドタスクであり、Codexのcell IDとsession IDは含まれない。

| エージェント | 同じセッションの自動再開あり | 自動再開なし |
| --- | --- | --- |
| メイン | 本文を空にする。空の応答をホストが再生成させる場合（Claude Code）は`…`だけを出す | 公開の待機手段で同じターンに終了状態と結果を回収し、後続の工程を終えてから報告する |
| `agents_server`の委譲先 | `待機中: <実行識別子>`の1行 | 待機を理由にターンを終えず、フォアグラウンドの待機で終了を確定してから所定の返却を返す |
| `Agent`ツールのサブエージェント | 完了通知で再開する起動形では`待機中: <実行識別子>`の1行 | 同上のフォアグラウンドの待機 |

### 完了通知で始まったターンの対処

バックグラウンドタスクの完了の自動通知で始まったターンは、ユーザーの発話とは別に扱う。
通知を届けるための前のターンの`Stop`の終了は、今のターンのツール操作の禁止を意味しない。
通知の保存出力と終了状態を回収し、未終了の担当が残る時は、有効な待機を続けるか同じセッションの自動再開が維持されていることを確かめる。
観測を試みた履歴だけでは、今も待機か継続の主体が在ることの証拠にならない。
ホストが今の操作を実際に拒否した場合は、その拒否と`agent-toolkit:atk-mode/playbooks/permission-denial.md`に従う。

## 待機中の先行実施

1. 待機へ移る時と再開する時は、残りの工程が要する具体的なデータと、共有資源、同じ箇所への書き込み、認可による順序の制約を分ける。
   待機の結果が内容も成否も変えず、制約も無い確定済みの作業は先に行う。
2. 待機中に判定できる改善点は、`agent-toolkit:atk-mode/playbooks/main-reporting.md`の判断担当が既存WIと比べ、`agent-toolkit:atk-mode/playbooks/wi-drafting.md`の手順でAWIの保存まで進める。
   修正を次回へ渡す判断と、結果の報告にまとめる都合は、投入を延ばす理由に含めない。
   `予定`にするのは、登録の前提が`判断待ち`、`認可待ち`、`入力待ち`、`書込競合`のいずれかに当たる時に限る。
   報告の書式は`agent-toolkit:atk-mode/playbooks/main-reporting.md`に従い、前提、再開の条件、再開の時点は既存の作業記録へ残す。
3. 延ばす時は、必要な待機の結果か具体的な順序の制約を確かめ、漠然とした競合の懸念は根拠から外す。
   競合は担当の範囲と実際の差分で判断し、読み取りのレビューと同時の書き込みを区別する。
   レビュー中の成果物への確定した修正は先に反映して同じレビュー担当へ追送し、検収は変更後の原稿へ対応付ける。

## 外部サービスの状態変化を待つ場合

1. 待つ前に、待機で得る結果が既存の証拠と次の必須の工程の判定に足りないかを比べる。
   既存の情報で判断できる時は待たずに工程を省き、その旨を報告する（原則2、`agent-basics:writing-standards/references/quality-principles-qcd.md`）。
2. CIとReleaseワークフローの完了は、`agent-toolkit:atk-mode/playbooks/publish.md`「pushと監視」の手順で待つ（基準の無い公開後のRelease確認は同節の`--wait-sha`）。
3. 対象のCLIに終了条件付きの待機があれば、それを使う。
4. 無ければ、時間上限を設けた終了条件ループを本書「待機区間の構成」の形で起動して回収する。
   照会に成功して未完了、照会の失敗、時間上限への到達を区別し、ループを再起動するのは上限に達して最後の照会が成功かつ未完了の時に限る。
   照会の失敗で終わった時は、保持した診断から原因を確かめて待機手段を選び直す。
5. 固定時間で待つのは、所要時間が確定した数秒程度の待ち（レート制限など）に限る。
   `sleep`と状態確認の反復は待ち時間を浪費し、中断の契機を失う。
6. ユーザーの入力か外部の基盤の復旧を待つ時は、定時起動の各回で条件の成立を確かめる。
   UWIの回答は各回の時間枠内で`atk wi wait --uwi <正式名> --timeout <秒>`を使って待ち、終了3（時間切れ）と検知・失敗を区別する。
   基盤の復旧は公開の状態照会か対象ジョブの再確認で判定する。
   照会の間隔は、残る解除条件の種類に合わせ、種類が変わったら見直す。

## 成果物側の観測

1. 委譲先が新しく作る成果物のパスは、依頼文で指定した値か、委譲先が明示的に報告した値で確定する。
   共有の出力ディレクトリの一覧と更新時刻は根拠から外し、パスが確定するまでは生存の確認と完了通知を待つ。
2. 成果物側の状態値は、`git -C <worktree> status --porcelain=v1`（差分）、`git -C <worktree> rev-parse --short HEAD`（HEAD）で取る。
   ファイルは`wc -l -- <file>`（行数）と`stat -L -c %Y -- <file>`（最終更新のエポック秒。macOSでは`stat -L -f %m -- <file>`）で取る。
3. これらは静的な値だけを返すため、生存中、識別子の消失、終了後の未回収を区別するには実行識別子の直接照会を併用する。
   差分とHEADは並行セッション、CI、フォーマッターの変更も含むため、実際の書き込み主体へ対応付けて補助の観測として使う。
   報告に載せる観測値は自身が書き込みを担う対象の値に限り、担当外の値を載せる時は判断への影響と実際の書き込み主体を添える。
4. 工程と所要時間の比較と残りの工程の組み直しは、進捗点検（`agent-toolkit:atk-mode/playbooks/main-reporting.md`）に従う。
   配下の残りの工程の見込みが目標所要時間を超える時は、担当が動いて成果が進んでいても、判断が必要な変化として通知する。

## 停滞の検知と巻き取り

委譲先とバックグラウンドタスクを止めるのは、ユーザーが即時の停止かモデルの切替を明示した場合と、本節の手順で停滞が確定した場合に限る。
進みの遅さ、手順の非効率、活動の観測値が変わらないことは、それだけでは担当を止めて交代させる根拠に含めない。
Codexで実行中の担当の中断を避ける条件と、利用上限の待ちでモデルを変えないユーザーの方針があるためである。
止めることを求める発話に複数の解釈が成り立つ時は、止める前にユーザーへ確認する（止めた作業は再開できず、そこまでの成果と観測が失われる）。

1. 再試行と利用上限の待ちを、実際の失敗と分ける。
   `show`か`list`が`status: running`と`api_error`を返す間は、催促、巻き取り、別のエンジンへの再委譲をせずに終了まで待つ。
   利用上限の待ちを理由にモデルを切り替えることは避け、切替はユーザーが指示した場合に限る（前任を終了して引き継ぐ手順は`agent-toolkit:atk-mode/playbooks/delegation-recovery.md`）。
   `api_error`が解消するか終了に達したら、通常の判定へ戻る。
   - ClaudeのAPIの再試行（合成のassistantメッセージ、`api_retry`）は活動時刻を進めないため、`seconds_since_activity`の増加を停滞の根拠から外し、`retry_at`を確かめてHTTP 429以外でも終了まで待つ。
   - Claudeの`usage_limit`（Weekly limitか5時間の利用上限）は、`claude_usage_limit_wait`の設定に従い、同じ会話で後続のAPIへ切り替えるか`resets_at`の後に同じセッションで再開する。
     設定が省略されていれば5時間の上限の解除を待ち、活動の停止が長いことだけを理由にCodexへ再委譲することは避ける（ユーザーの指示）。
     作業が不要になった場合とユーザーが切替を指示した場合は、`kill`で止めて結果を受け取る。
     ユーザーが即時停止を求めた場合は`force=true`を渡す。
   - Codexのターン内の再試行（`willRetry: true`）は、通知の種別とHTTPのstatusを確かめ、追加の送信を控えて解消かターンの終了まで待つ。
     `atk agents wait`が再試行の長期化を`next_action`で示したら、それに従う。
   - Codexの`serverOverloaded`の後の自動継続では継続を促す`send_message`を控え、上限回数に達して失敗の結果が届いたら失敗の診断と未完了の作業を確認する。
     再起動が必要なら元の工程名で起動し、候補はサーバーに選ばせる。
2. 停滞の兆候を見たら、`show`を1回実行する（保留中のセッションへ新しいターンを始めないため）。
   - `active_tool_uses`の同じ呼び出しが同じ開始時刻のまま続く時は、長いコマンドの実行中として催促と巻き取りを保留する。
   - `result_held`が真の時は、委譲先はターンを終え、バックグラウンドタスクか子セッションの終了、または利用上限の解除を待って結果を保留している。
     `live_background_tasks`の`seconds_since_start`と`live_child_sessions`で待機を続けるかを決め、後続の結果が不要なら`kill`で保留中の結果を受け取る。
   - `active_tool_uses`が無く、`seconds_since_activity`が停滞と見るに足る長さに達した時だけ次へ進む。

   停滞と判断する前に、引き継ぎ記録などの更新時刻を担当の実行記録の最終活動と比べ、実行記録で作業が続いていれば作業中として扱う。
3. 委譲先が所有する外部プロセスとバックグラウンドタスクは、成果物の差分と実行識別子の直接照会の両方で、生存中、識別子の消失、終了後の未回収を区別する。
   外部プロセスを終了できるのは所有者だけであり、委譲元は生存中の処理を重ねて起動することを避ける。
4. 間隔を空けた複数回の観測（別のターンか次の定時起動）で変化が無ければ、継続を促す。
   それでも応答が無ければ、未完了の工程を巻き取るか範囲を限定した新しい担当を起動し、観測をユーザーへ短く報告する。
   成果物の更新が続く間と、更新元を他の主体（CI、フォーマッター、並行セッション）と区別できない間は催促にとどめる（努力目標。回数と間隔は対象に合わせる）。
   区別できないことだけによる保留は、観測値が30分変わらなければ解いて催促へ進み、この30分は止めることや巻き取りの期限とは別である。
   手順1と2の保留の条件はこの基準より優先し、Codexで`list_agents`が`running`を返す間は巻き取り、新規起動、役割の引き継ぎを保留する（条件は`agent-toolkit:atk-mode/playbooks/host-codex.md`）。
5. 稼働中の同じ委譲先へ矛盾する指示の差し替えを重ねそうな時は、いったん保留を指示し、方針を確定してから旧方針との差分を統合した指示を1回で送る。
6. 明示した制約への違反が同じ委譲先で繰り返す時は、指示の再送と起動の反復をやめ、その工程を巻き取るか別の手段へ切り替える。
   切り替える前に、違反の原因が委譲先の出力か委譲元の判定条件かを実装で確かめ、委譲元に原因があれば判定条件を直す。
7. 巻き取りの前に、委譲先のトランスクリプト、委譲先が起動した子孫のタスクの記録、外部実行のログの末尾を確かめる。
   完了報告が取れる状態なら再実装せずに検収し、取れなければ未完了の工程だけを巻き取る。
   担当の範囲か権限の外の作業なら、続行できない理由を委譲元へ返す。
   継続か新規起動かの判断と、停止や反復の原因になった既存の不良の処置は、`agent-toolkit:atk-mode/playbooks/delegation-recovery.md`で行う。
   停滞を確定して止める時は、対象ごとに根拠を記録してから止める。
   Claude Codeでは`atk run-script record-stall-detection -- --session-id <現在のCLAUDE_CODE_SESSION_ID> --task-id <停止対象の完全なタスクID>`が記録を作り、終了コード0を返した対象だけを止められる。
8. `kill`か`send_message`の配送が再発行しても確定しない時は、同じ前提で再発行を重ねず、`show`の`owner_server_instance`と`queried_server_instance`を比べる。
   `show`や`list`も応答しなければ、照会を待つ代わりに`agent-toolkit:atk-mode/references/delegation-wait-anomalies.md`「管理サービスへの操作が応答しない場合」へ進む。
   - 別の世代かプロセスが所有していれば、その世代の退出か移譲を待つか、所有プロセスを処置する。
     処置の前に、委譲先が保存した成果（引き継ぎ記録、結果ファイル、作業ツリーの差分）の所在を確かめて保全する。
   - 止めるプロセスが自身のMCPの接続先でないことを、`list`の`queried_server_instance`と`server_generations`の`queried: true`の世代で確かめる。
     自身の接続先を止めると、以後の照会と回収ができなくなる。
   - 処置した世代が`list`の`server_generations`から消えたことを確かめる。
     `show`では処置したturnの終了を確認する。
     新世代が自動再開した場合は、`interrupted_turns`のturn番号と診断のサーバー識別子が処置した対象と一致することを確かめる。
   - Claude CodeでMCPの再接続が必要な時は、`agent-toolkit:atk-mode/playbooks/host-claude-code.md`「ツールの入出力」に従う。
     管理サービスが応答しない時は、予約の受付を未確認として扱い、待機に入る前に接続の復旧へ進む。
     Claude Code以外で予約できない場合や接続を失った後は、ホストの再接続の手段で復旧するようユーザーへ依頼する。
     停止・再起動を伴う場合の担当の記録と引き継ぎは、`agent-toolkit:atk-mode/references/delegation-wait-anomalies.md`「管理サービスへの操作が応答しない場合」に従う。

## 返す報告に含める項目

回収した結果の`session_id`と`agent_message_path`、未回収の対象と待機の状態、停滞と判断した根拠と処置（催促、巻き取り、停止）、再開した観測、続行できない理由を返す。
