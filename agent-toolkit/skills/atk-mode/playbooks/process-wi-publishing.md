# 公開工程とセッション終了

目的: メインが統合済みの成果を公開まで届けて検収し、ユーザーが承認した変更がユーザーの手元へ実際に届いたことを報告で確かめられるようにする。
全てのレーンが終わった後に、公開対象を判定し、公開担当（直接実行か委譲）で公開して検収し、回復と再公開を経て、完了報告と終了までを行う手順書である。
作業`process-wi`のメイン（single-laneのメイン、複数レーンのメイン、all-reposの統括とリポジトリ担当）が使う。
版数の更新、生成物の同期、push前のチェック、push、CIの確認、公開後の操作の定義は`agent-toolkit:atk-mode/playbooks/publish.md`にあり、本書は公開の担当の割り当て、単一の書き込みの主体、レーンの資源の保持、延期の扱いを定める。
終了条件は、公開状態の4項目と選定全体の処置を検収し、報告と終了の処理を終えた時点である。

公開工程は、公開する単位に属するレーンが完了し、その単位の自動コードレビュー監査を起動した場合は返却の受領と処置の確定を終えた時点で始める（単位を分けていなければ選定全体が対象）。

- レーンの完了は、通常レーンではfast-forwardマージ、`adopt`、計画の保存が済んだ状態を指す。
  固有の指示で`adopt`を延期したレーンと`上流投入`が`混在`のレーンでは、ffマージと計画の保存が済んだ状態（`混在`では元の項目を依存付きで`inbox`へ戻した状態）を指す。
- 巡回の最終完了は、単位ごとの公開の成功とは別に、選定全体の処置と最終SHAのCI成功で判定する。
  長い処理の間も、統合済みで公開できる変更は`agent-toolkit:atk-mode/references/orchestrator-runtime.md`「継続中の公開と更新」の期限で先に公開し、未完了のレーン・WI・計画・所有と元の要求は保つ。
- 公開工程の開始前に、選定メインが`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`「開始後に追加されたWIの確認」を行い、今回追加と判定した項目は必要な工程を終えてから公開へ進む。
  公開操作が新着WIの通知で止まったら、今回扱う必要のない項目はinboxに残し、判定を記録せず同じ公開操作を再発行する。
  公開対象は、選定で確定した項目と、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」で合流した項目である。
  目標が明示されている場合の必要な作業は`agent-toolkit:atk-mode/playbooks/process-wi-selection.md`「明示された目標からの実行」に従い、それ以外の新規の項目は次回へ残す。
- all-reposから委譲されたリポジトリ担当も、自分の対象のcwd、処理対象WI、ベースブランチへ公開工程を適用し、処理の所有を公開・CI・確認・再開まで保つ。
  公開結果、対象リポジトリ、担当セッション、公開commit、CIの結果、未完了の工程、再開記録を統括へ返し、作業完了報告と報告用UWIは統括が1件にまとめる。
  ある担当が回答待ちや続行不能になっても、独立した他の担当は公開工程を続ける。
- 公開と終了の前に、対象リポジトリのプロジェクト規範が定める所要時間と終了条件を取得し、全工程の現在の見込みと未確認の前提を検収する。
  「次回の目標達成に必要な改善と検収」を求める条件は、局所の修正の完了や公開の予定ではなく、改善の実施と検収を終えた時に満たす。

## 使い方が変わる変更

1. 計画・実装の担当は、AWIの記載によらず、公開コマンド・オプション・設定・画面操作・運用手順が追加、変更、廃止されるかを判定する。
   使い方が変わらない内部修正、従来の操作で直る不具合、誤記の修正は対象外とする。
   設定・移行・導入などが必要な場合は、配布時の自動適用や、設定を省いた時の値で操作を不要にできるかを先に比べる。
   明示された設定の上書き、認証、課金、本人の選択は自動化せず、案内に残す。
2. プロジェクトの利用ガイドに変更後の使い方を書き、実装と同じ公開に含める。
   本人の設定や許可を待つ機能では、未設定時の動作と設定手順を書く。
   ガイドが無いプロジェクトでは新設せず、案内UWIに使い方を書く。
   元AWIの採用時の対応結果には、ガイドがある場合はファイルと見出し、いずれの場合も確定した名前・値、環境別の実施状況、公開の成立条件を記録する。
   公開が後日になる場合も同じ記録から再開できるよう、計画と公開担当への引き継ぎに所在を残す。
3. 公開担当は実装がエンドユーザー向けに公開されたことを確かめてから案内する。
   該当するガイドがある場合は、その内容の公開も確かめ、含まれていなければ追記して公開してから案内する。
   公開済みの版を使い、環境別の確認・設定・移行を `agent-toolkit:atk-mode/references/uwi-format.md`「ユーザーへ操作を依頼する場合」に従って振り分け、到達可能かつ認可済みの操作を実施して結果を記録する。
4. 変更後の使い方、最終名、元AWI、環境別の実施結果と、ガイドがある場合はその場所を専用の案内UWIにまとめ、回答を求めない報告（`--question-type=report`）で登録する。
   本人にしかできず結果で対処が変わる操作が残る場合だけ、保存担当はその操作を理由とともに個別のUWIで依頼する。
   一覧が無ければ把握した環境に加え、それ以外の環境の手順を1つ示す。
   全環境で操作不要なら、そのことと変わった使い方を示す。
   報告用UWIとは分け、報告用には登録済みか公開後の登録予定を1行で示す。
   エンドユーザー向けの公開が開発ブランチへのpushと別の工程なら、リリース完了後に登録する。

## 公開対象が無い場合の短絡

1. 公開の短絡・直接実行・委譲を選ぶ前に、選定メインが保存した選定の原本へ次を実行する（独立した公開単位を先に公開する場合は本書「独立した公開単位」の確認を使い、巡回の最終確認ではこのコマンドで全件を確かめる）。

   ```text
   atk run-script pick-wi-check -- <選定YAMLの絶対パス> --require-integrated
   ```

   - 終了0は全段階のレーンの統合済みを示す。
   - 未統合を示す終了1では、出力のレーン・段階・所属WI・先行レーンが原本と一致することを確かめ、未起動の後段も始めるか続ける。
     既存の依存・確認・冷却の基準で延期すると判断したWIは、理由・解除条件・再開位置を既存の記録へ対応付け、今回の選定全体を処置した根拠を保つ（統合状態は書き換えずに保つ）。
   - 終了2の入力不備は直し、原本との一致の確認と意味判断を終えてから公開へ進む。
   - 全体の母集団には選定の原本の全対象を使い、レーンなしのWI、上流投入、回答済みUWIの処置も別に検収する。
     選定の原本の所在とこの判断の記録は、公開担当とall-reposの全体の結果へ引き継ぐ。
2. 公開対象の変更や外部操作が1つも無く、公開状態の4項目が全て成り立つ場合に限り、公開担当を起動せずに`agent-toolkit:atk-mode/playbooks/process-wi-observation.md`「延期adoptと反映後の観測」へ進む。
   - 外部操作は、選定結果の`選定`で`レーン`が`なし`、`上流投入`が`なし`以外、`プロジェクト固有の公開後の操作の順序`が`既定`以外の項目と、このセッションで回答を受けたUWI、選定工程で記録したプロジェクト固有の公開後の操作、レーン工程から引き継いだ延期`adopt`の対象である。
   - これらが無ければ、`agent-toolkit:atk-mode/playbooks/publish.md`「公開状態の4項目」を主作業ツリーから読み取り専用で取得する（レーンの統合に伴う未公開のcommitもこの4項目で検出される）。
   - 4項目が揃い、前回までの公開後の反映に未完了が無ければ、本書「公開状態の検収と再起動」で検収済みとして扱う。

### 独立した公開単位

選定時に、成果の依存・書き込み競合・統合状態・公開工程の書込対象から、独立に検証・公開できるレーン群を既存の配分の根拠へ記録する。
通常は検証と公開をまとめる。
分ける案は同じ仕事と資源の条件で、最初の到達時期、全件の完了時期、検証・CI・版数・生成物・再指示・反映と再開の費用を比べ、到達か全件完了を早める分割だけを採用する。

1. 公開する群が検収済みになったら、選定の全量を保ったまま次を繰り返し指定して確かめる。

   ```text
   atk run-script pick-wi-check -- <選定YAMLの絶対パス> --require-integrated --publication-lane <公開単位のレーン>
   ```

   終了コード0を確かめてから手順2へ進む。

2. 指定した群と推移的な先行レーンの統合を検収し、未統合の独立群は元の選定と担当へ保つ。
   同じ保存先を書き換える群や成果を必要とする群は、依存を保って公開の可否を判定する。
3. 公開の開始時に、実際に含む全てのcommitとWI、入力SHA、検証とCIの担当と実行識別子、未完了の群の再開位置を既存の進捗記録へ対応付ける。
   公開担当が単一writerとなる区間は統合先への次の統合を待ち、別worktreeの独立した実装とレビューを続ける。
4. 入力SHAのCIの成功と、この単位に必要な公開後の操作を検収してから次の公開単位へ進み、全ての要求を処置するまで巡回を続ける（各単位の成功と全件の完了を区別する）。

## 公開担当の起動と並行工程

1. 発見済みの独立した改善は、発見時に`agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`で処置を決め、必要な証拠がそろった時点から調査・起草・意味の確認を進める。
   公開結果に依存しない原稿、報告の構成、公開前の実績、結果JSONは先に準備し、未確定のCIと修正後の結果は確定後に補う。
   公開後にも独立して成り立つWIの投入は、`agent-toolkit:atk-mode/playbooks/wi-submission.md`の公開受付へ自己完結した要求を渡してよい。
   永続の受付と独立した監督への所有の移管を確かめた後は、その投入を今回のwriterの待機へ残さず、受付票と未完了の投入を報告で区別する（受付が成り立たない場合は既存の投入担当の起動・検収・保存を同じセッションで終える）。
2. レーンの数によらず、各レーン担当が返した統合結果から公開工程へ進み、計画・実装・レビューの定型の報告は求め直さずに、最終のHEAD、計画の保存、WIの採否の確定、延期の対象を検収する。
3. 統合後の独立した即時の修正は同書「レーンの変更範囲へ加える修正の認可」で担当と時機を決め、統合先の現行のHEADで限定の検証と独立文脈レビューで確かめる。
   元WIの未達を除き、統合済みのレーンへ戻す再統合は避ける。
   公開後なら修正の検収後に公開状態を検収し直し、必要な再公開へつなぐ。
   最後の検証の後に加えた変更（統合後の即時の修正、公開中のCI修正、版数の更新に伴う追随など）は、変えた定義・文言・構成・実行前提の変更前の値を固定文字列で探し、消費する実装・検査・テストを検証の対象へ戻してから公開へ進む。
4. 対象リポジトリの規範がセッションの終了工程と同じ時機に固有の追跡先への記録を求める場合は、その記録を終えてから終わる。
5. 公開担当の起動から公開とCI修正の終了までの間は、専用worktreeとレーン専用branchの回収を止める。
   回収はGit共通ディレクトリを変え、`agent-toolkit:atk-mode/roles/session-termination.parent.md`「起動前の前提」の単一writerの条件と競合するためである。
   それより前に`agent-toolkit:atk-mode/playbooks/process-wi-lane-resources.md`「レーンworktreeの扱い」の回収の時点を迎えたレーンは公開担当の起動前に回収し、残りは公開とCI修正を含む全工程と外部プロセスの終了後に回収する。
6. 統合後に保存済みの計画をcheckoutして履歴書換えへ追随させるメインか配下の担当は、全ての計画バンドルを更新・再保存する。
   手順は`agent-toolkit:atk-mode/playbooks/history-rewrite.md`「WI実装commitの対応の継承」に従い、成功と警告を検収してから公開担当を起動する。
   同じ`plan-rewrite`の処理が、統合時に採否を確定したAWIの対応commitと件名も新しいcommitへ付け替える。
   通常のレーンの統合はOIDを保つmergeなので、この追随の対象外である。
7. メインはレーン数によらず、各レーンの記録を対象リポジトリの版数の採番規範に照らし、未公開の統合変更に適用する最上位の`bump種別`を決める（選び方は`agent-toolkit:atk-mode/playbooks/publish.md`）。
   公開担当は既決の種別で、版数の更新、生成物の同期、push前のチェック、push、CIの確認、失敗時の修正、割り当てられた公開後の操作、延期`adopt`を終える。
   CIの監視で失敗したjobを見たら、全pipelineの終了を待たずに入力SHA・job・診断・残る監視の識別子をCI修正担当へ渡す。
   CI修正担当は単一writerを保って診断と是正を始める（`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「検証またはCIの失敗」）。
   継続中のjobの監視と最終SHAの全体のCIの成功の確認は保ち、終了時の一括通知しかない監視では既存の公開状態の照会を並行して使って途中の失敗を得る。
8. 主作業ツリーへ書き込む主体は、公開担当と起動したCI修正担当のうち常に1者とし、公開を委譲したメインはその間、主作業ツリーとベースブランチを読み取り専用とする。
9. 公開はメインか対象リポジトリ担当の直接実行を通常とし、直接実行と委譲の選択・入力・検収は`agent-toolkit:atk-mode/roles/session-termination.parent.md`に従う。
   本書の公開担当には直接実行する担当と委譲された担当の両方が含まれ、直接実行では自分の進捗記録と観測から同じ条件で検収し、失敗から回復する。
   実行レビューとCI修正担当の起動条件はそのまま適用する。
10. 公開担当の公開処理やCIの完了待ちと並行して進めてよい作業は、主作業ツリーとベースブランチへ書かず、公開担当の入力を作らない工程に限る（既存の別worktreeでの編集とそのbranchへのcommitを含む）。
    worktreeの作成・回収のようにGit共通ディレクトリの構成を変える操作は、公開担当の終了後に行う。
    並行作業の成果は公開担当の終了後にベースブランチへ統合し、本書「公開状態の検収と再起動」に従う。
    - キューへの投入: `agent-toolkit:atk-mode/roles/add-wi.parent.md`に従い、公開担当の起動と同じ工程で投入担当へ委譲する（書き込み先はprivate-notes）。
      公開担当の結果を見て初めて内容が決まる項目は、結果が返った後に渡す。
    - 読み取りの調査とAWI原稿の準備: 公開結果を待たずに調べられる既知の警告の調査やAWI原稿の起草は、主作業ツリーとprivate-notesへ書かない独立した担当へ任せる。
      原稿は投入担当へ渡し、返った原稿をメインが`agent-toolkit:atk-mode/roles/add-wi.parent.md`「原稿の検収」で検収する。
      公開結果が必要な問題の調査は結果の確定後に始める。
    - 独立した追加の工程: 長い公開・デプロイ・CIの待機や追加の公開工程は、入力commit、成果物、配備先、排他が必要な資源、先行の成功を前提とするかを起動前に進捗記録へ書く。
      独立して進められる工程は別のエージェントへ任せて並行させ、先行の成功を入力とする工程は先行の成功を確かめてから始める。
    - 常時稼働サーバーへの反映: `agent-toolkit:atk-mode/playbooks/report-completion.md`「常時稼働サーバーへの反映」の共通の条件を使う。
      反映と稼働確認の手段があるプロジェクトでは、全レーンの統合を検収して資源を保ったまま、反映の入力が使えるようになった時点で反映と再起動を始める（push済みのSHAならpushの確認後、ローカルの成果なら必要なローカルの検収後）。
      CIが未判定でもこの条件を満たせば進める。
      ただし、dotfilesの利用環境への反映などCI・リリースの成功を前提とする配備は、その成功を待つ。
      再起動の前に入力SHA、CIの監視の担当・実行識別子・保存出力、未完了の工程と再開位置を既存の引き継ぎ記録へ保ち、反映したHEADの一意な短縮OID、反映コマンドの終了ステータス、稼働確認の結果を完了報告へ渡す。
11. 同じ統括がafter評価、追加のレーン、再公開を続け、役割の宣言や起動時の資料の検査が失敗した場合は、元の診断と稼働中の実装・資源の版を確かめる。
    版の相違が示された時だけ`agent-toolkit:atk-mode/references/delegation-wait-anomalies.md`「役割資源との版相違」で新しいプロセスからの回復へ進み、配下の実行中・結果未回収・停止後に再開できる担当と入力・結果を保護する。
12. 公開担当がcheckoutした保存済みの計画を履歴書換えへ追随させた場合も手順6と同じく扱い、担当工程の最後に更新した全ての計画バンドル（延期`adopt`と未終了を含む）を再保存して成功と警告を検収する。
    メインはその結果を検収してから、観測と再開記録のためのcheckoutへ進む。
13. 公開手順で新たに命名・設定値・手段を決めた時は、起草した担当が`agent-basics:writing-standards/references/quality-principles-subtraction.md`「変更の範囲」の既存例と比べ、比較先と採用理由を手順か既存の進捗記録に残す。
    メインは公開担当の起動前（起動後に決まった値は公開担当がその操作に入る前）にその記録を照合し、照合を終えるまで該当操作へ進ませない。
    直接実行でも、実行する担当が比較先と理由を確かめてから操作し、計画・実行レビュー済みの判断は同じ記録を使う。

### 公開担当起動後の会話圧縮

1. 公開担当の起動に伴って会話圧縮を一律に手動で予約せず、`agent-toolkit:atk-mode/playbooks/host-claude-code.md`「長時間待機前の会話圧縮」の条件付きの自動予約とホスト標準の圧縮に任せる。
   並行の工程は開始条件を満たしたものから進め、既存の予約があればそれを使う。
2. 圧縮後の復元では、注入された要約を起点に、対象worktree、公開の入力commit、担当別の引き継ぎ記録、保存出力と既存の資源の登録から必要な情報を得て、要求・認可・未完了の操作を原本から確定し、同じ公開工程へ戻る。

## 公開工程の続行不能の回復と再開

1. 公開担当からCIの照会不能か公開後の操作の前提不足が返った場合は、公開状態の4項目が成り立っていても本節へ進む。
   確認済みのpush、全体検証、版数の更新、生成物の同期、公開後の操作、WIの採否の確定の各到達点を保ち、残るCIの判定と公開後の操作を公開工程の未完了の事項として扱う（成功済みの公開後の操作もそのまま保つ）。
   回復、確認、個別のUWIの保存と回答を要する未終了の項目の保留は、`agent-toolkit:atk-mode/playbooks/publish.md`「公開工程の続行不能からの再開」に従う。
   全体検証の失敗を含む場合は`agent-toolkit:atk-mode/playbooks/process-wi-ci-fix.md`「検証またはCIの失敗」へ渡し、全体の成功はCIの未判定の解消とは別に全体の結果で判定する。
2. 公開担当の引き継ぎ記録で再開位置と証拠を管理する。
   `atk run-script plan-progress -- <記録先> --handoff`で進捗を引き継ぎ記録へ追記する。
   計画が無ければ、同節に従って再開記録と必要な証拠を公開工程を扱う未終了のAWIの本文へ保存して個別のUWIと対応付け、該当のAWIが無ければ同じ手順で新規に登録する。
   未終了の元の項目には、公開先、commit、確認済みの工程、成功済みの公開後の操作、CIの結果、失敗した操作と対象、足りない前提、baseline・保存出力・UWIの所在、再開位置を`atk wi edit --append`で追記する。
   UWIの保存に失敗した場合は元の項目へ依存を設定せず、未保存の確認事項があることと未完了である旨を記録する。
   採否の確定を終えた実装の要求は元の状態に戻さず、残る公開工程だけを個別のUWIと再開記録へ引き継ぐ。
3. ユーザーの回答を受けたら、対象リポジトリの担当が元の公開先とcommitを確かめ直し、同じ公開担当のセッションが残っていれば足りなかった回答を渡す。
   残っていなければ、保存済みの計画か公開工程を扱うAWI本文の再開記録から、未完了の工程だけを担当へ渡す。
   成功済みのpush、版数の更新、公開後の操作は繰り返さず、対象のcommitが進んでいれば追加の差分と残る工程を区別して本書「公開状態の検収と再起動」へ進む。
   有効な不在の証拠が得られれば通常の不在の受理へ、CIの成功を確かめれば通常の検収へ戻る。
   回復待ちのまま終える場合は公開工程を完了扱いとせず、CIの未判定か未完了の公開後の操作と、UWIと再開記録の保管場所を報告する。

## 公開状態の検収と再起動

1. report-completionによる報告の前に、公開状態の4項目（`agent-toolkit:atk-mode/playbooks/publish.md`）の検収を確かめる。
   短絡時の検収か`agent-toolkit:atk-mode/roles/session-termination.parent.md`「受領と検収」で得た4項目は、主作業ツリーや対象の参照を変える操作や外部からの更新が間に無ければそのまま使い、それ以外は現在のGit状態から取り直す。
   公開担当が返した`ベースbranchの状態`は、取り直した4項目と突き合わせて確かめる。
2. 公開担当の結果の返却後に、主作業ツリーのHEAD、追跡ref、最新のHEADのCIの状態、作業ツリーの状態を確かめる。
   GitLabがCI実行対象外を返した場合は、終了8のproject・commit・ref・errorsと同じHEADのローカルの全体検証の成功を検収し、新しいHEADへ更新された場合は非生成も判定し直す。
3. 前回の公開単位の反映・本人再開・稼働版の検収が残っていれば、次の公開に進む前に未完了段階から再開する。
   その後、状態に応じて次へ進む。
   - 前回pushしたOIDからベースブランチへ新しいcommitが統合された場合（主作業ツリーで直接作った是正commitを含む）: 全てのレーンの終了と書き込みの主体の解放を確かめる。
     次に、追加の差分のbump種別、プロジェクト固有の公開後の操作、延期`adopt`だけを入力に同じ公開の手順を再実行し、最新のHEADのpushとCIの結果を同書「受領と検収」の受理の条件で確かめる。
   - 新しいcommitが無く、CIの未判定だけが残る場合: 本書「公開工程の続行不能の回復と再開」に従い、同じcommitの未完了の工程を再開する。
   - 新しいcommitが無く、公開後の操作だけが未完了の場合: 同節に従い、同じcommitの未完了の公開後の操作だけを再開する。
   - 新しいcommitが無く、CIの検収と公開後の操作が全て済んだ場合: 既に検収した反映・再起動を繰り返さず報告へ進む。
   - 新しいcommit以外の要因で公開状態が成り立たない場合: 原因と復旧の手段を調べて既存の認可の範囲で回復を図り、ユーザーにしか判断できない事項だけをUWIで確かめて、観測結果と未完了の内容を報告に含める。

4. dotfilesの公開担当は、push・CI・必要なリリースの成功後、各対象ホストの追跡系統に対応する公開OIDとそのOIDのagent-toolkit配布版を、操作結果とともに統括へ渡す。
   巡回では[巡回する](process-loop.md#巡回する)の手順4・5で更新、反映、本人再開と版の検収を終える。
   委譲した公開担当は、統括にしかできない操作を残す時は公開済み・利用環境は未検収と返し、統括が完了を確定する。
   稼働中のサービスとの一致を確認するまで公開完了と返さない。
   公開済みの結果は保持し、未完了段階を再開点とする。

## 完了報告と終了

1. 単独のメインは公開工程の検収後に`agent-toolkit:atk-mode/playbooks/process-wi-observation.md`「報告前に確かめる保存状態」を実行し、現在のキュー・再開記録・レーンの最終化との一致を確かめる。
   保存済みのレーン計画とCodexのセッション記録を使い、`agent-toolkit:atk-mode/references/review-session-cost.md`「レーンの保存済み統計」の集計結果と基準との差を既存の作業記録に残す。
   委譲した場合は担当の返却にある結果を再利用する。
   その後`agent-toolkit:atk-mode/playbooks/report-completion.md`へ進んで、成果・検証・公開結果・未達を同じ作業完了報告へまとめる。
2. 終了前にも選定の原本へ`atk run-script pick-wi-check -- <選定YAMLの絶対パス> --require-integrated`を実行し、公開後の追加や再開で未統合へ戻った項目が無いかを確かめる。
   未統合があれば残工程を続け、正当な延期だけを対象・理由・解除条件・再開先に対応付ける。
   入力の不正や読み取れない状態を完了と扱わず、元の選定を回復して検収し直す。
3. 自律モードでは報告用UWIの保存の成功と警告を検収し、元の要求と実際の送達、残工程、新しい指摘の処置を確かめてから、同書の終了処理へ進む。
   完了の工程の後に初めて分かった独立した問題は、`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「起票目的別の調査出口」の軽い引き継ぎで登録できる。
   最終報告には公開結果と元の要求に対する到達点を含める。
4. 統括からのリポジトリの委譲は、`agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md`「リポジトリ担当の返却契約」に従って統括へ成果を返し、`atk agents-exit-session`は実行しない。
   単独・統括・委譲先のどれも、作業の終了と公開では同期のreview-sessionを工程の対象外とし、作業完了報告は非同期の振り返りの結果とは独立して送る。
   常駐起動の統括と単独のメインのホストの終了はreport-completionが所有する。
5. 終了時の回収主体と時点は`agent-toolkit:atk-mode/playbooks/process-wi-lane-resources.md`「レーンworktreeの扱い」に従う。
   メインは終了の要求の前にも既知の残った資源と誤った変更を`agent-toolkit:atk-mode/references/operations.md`「プロセス終了の安全規定」で調べ、解消できる保持理由を正して既存の回収操作へ戻す。
   返却に未回収の対象があれば`agent-toolkit:atk-mode/playbooks/process-wi-lanes.md`「未回収レーンの再回収」に従い、認可の範囲で再回収する。
   保持が残る対象は`agent-toolkit:atk-mode/playbooks/report-completion.md`「工程」の手順2に従い、使用中の保護とユーザーへの個別UWIを区別する。
   回収の失敗をホストの終了要求の成功で覆わず、次回の`atk lane delete --list`へ引き継ぐ。
   統括は各担当の終了結果と続行の予定、保持すべき成果を検収し、既存のレーンの回収条件に従う。

返す報告に含める項目: 公開した単位と入力SHA、CIの結果、公開状態の4項目、延期`adopt`の結果、続行不能と回復の状況、エンドユーザー側の操作と案内UWI、回収と保持の結果。
