# 即時対応と開始後に追加されたWIの確認

作業`process-wi`の実行中に不良・是正要求・改善を観測または受領した時と、ユーザーが時機の指示として「即時対応」や同義の表現を使った時に、対処の時機・担当・基点・認可を決めて実施する手順書である。
統括、選定メイン、single-laneのメイン、レーン担当が使い、統括と選定メインは30分ごとの点検と公開工程の開始前に本書「開始後に追加されたWIの確認」も行う。
時機は、直接修正、今回の実行への追加、次回への引き継ぎから選ぶ。
終了条件は、受け取った項目ごとに時機と担当を決めて実施か投入まで進め、判定と根拠を既存の引き継ぎ記録へ残した時点である。

改善点の受付と対処時機は別に扱う。
受け取った受付IDは `agent-toolkit:atk-mode/playbooks/main-reporting.md` の受付手順へ対応付ける。
元WIの未達と今回混入した不良は、この受付を理由に別案件へ移さない。

## 即時対応

1. 対処や追加の操作を選ぶ前に、元の発話と発生条件から、ユーザーの是正要求、今回の作業で混入した不良、同じ実行へ明示的に追加された要求、独立した既存不良・改善を区別する。
   今回混入した不良と、初期選定のWIが求める正式対応は、元の要求と完成条件で同じセッションのうちに完遂する。
   明示の追加は`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」へ渡す。
   即時対応を理由に初期選定の作業範囲を縮めることは避ける。
2. 独立した既存不良は、費用や工程への作用を比べる前に、根拠から欠陥と確定しているかを判定する。
   エンドユーザーや利用システムへの現在の影響、配備済みの環境で発生中の失敗、運用の監視・集計を妨げている欠落と、既存のコード・文書・設定の契約違反を現物から確定した不良は、発生場面が未観測でも欠陥と確定した対象とする。
   巡回を妨げる不良は手順4に従う。
   どちらの進行も妨げない独立不良は、今回収束させる費用と次回の開始が遅れる費用を比べ、全体の処理量を増やす時機を選ぶ。
   次回へ渡す場合は、確定不良と調査・認可待ちを混同せず、両巡回への影響・費用の比較をAWI本文に残す。
   終了時は保存済みAWIの根拠が先送り条件を満たすか確かめる。
   今回の変更の不良と選定済みWIは元の要求で処理する。
   担当側で満たせない外部の前提で続行できない場合は、試した代替手段・結果と再開条件を残す。
   公開工程の開始後は`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「公開状態の検収と再起動」で今回の再公開へつなぐ。
3. まだ今回の処理対象ではない欠陥の候補と効率改善は、以降の進行への作用と、減る仕事量と修正・検証・統合の負担を比べて時機を決める。
   - 削減量には今回の巡回のうちに得られる分だけを数える。
     エージェントが使うツール・規範・hookの改善は、今回の残工程で使われないことが多い。
     次回の巡回で直しても直した時点から修正済みの版を使えるため（`agent-toolkit:atk-mode/references/operations.md`「`atk`の呼び出し」）、今回へ追加して早まる効果は巡回の間隔の分に限られる。
   - 再発の自然発生や一律の回数・時間・トークン数を待たずに、同じ規範や操作が次回も使われる具体的な見込みを根拠にしてよい。
   - 公開工程の開始前で、削減が負担に見合い、既存の認可・依存・書込所有権の内側に安全な受入先がある正式改善AWIは今回へ追加する。
     既存レーンの残り工程、統合・公開の負荷、共有実行枠（`agent-toolkit:atk-mode/playbooks/verification.md`「統合実行ツール経由の起動」）の混雑を含めても実行全体の完了時期を遅らせない見込みを、根拠とともに記録する。
   - 今回の巡回で得られる削減が無い改善、安全な受入先か完了時期の見込みが成立しない項目、公開工程の開始後の独立改善は、理由と再開条件を残して次回へ渡す。

   ユーザーが改善の即時実施など時機を指定した場合は、その指示を優先する。
4. 即時対応の要否は、残る工程か次のセッションで、処理の停止・遮断、誤った判断や成果物の作成、手戻りが起きるかで判断する。
   該当する不良は、工程が完全には止まっていないことや不良の種別を理由に次回へ送らず、本書「即時対応の手順」で、現在か次のセッションの進行に不可欠な最小限の修正をその場で施す。
   担当の交代・引き継ぎ・再起動、エンジンやモデルの切り替え、迂回操作は、欠陥を残したまま進行を戻す手段であり、直接修正とは別に扱う。
   回避で進行が戻っても、欠陥が残る工程か次のセッションで処理を止めるなら、同じセッションで直接修正する。
   テストの追加、独立した文脈でのレビュー、根本原因の分析、類似箇所の見直し、再発防止策は、正式対応用AWIへ記録する。
   手順2で今回とした不良は、最小修正の後の正式対応も今回行い、次回とした対象と未確定の候補・効率改善の未実施の分析・見直し・恒久対策だけを後続のAWIへ分ける。
5. 容量不足の警告は、自動掃引の観測範囲に限られる。
   保護・猶予・削除失敗や対象外の領域は、個別に回収できないことや残存が全て使用中であることの根拠から外す。
   現在の容量不足には、共通の安全規定で回収できる資源を調べて処置する担当と、生成元・回収処理を恒久修正する担当を分けてつなぐ。
   実行基盤の拒否は迂回せず、拒否された対象と操作だけを承認待ちに分け、認可の内側の調査と是正は続ける。
6. 追加と所要を受け取った時は、内部の群の量・実測の速度・待ち・依存と、公開か終了までの全工程を、目標の絶対完了時刻へ対応付けて見込みを更新する。
   全体の見込みが成立しなければ、先行準備、群別のレビュー、共通の検収の重複除去を元の担当へ指示し、所要の転記や増員だけで達成と扱うことは避ける。
   内部担当の同時数と巨大WIの個別承認は`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`「内部担当の同時数と巨大WIの判定」に従う。
7. 巡回中のAWIは `atk wi add` で保存し、`--process-wi-timing this-run`（今回）か `--process-wi-timing next-run`（次回）を渡す。
   今回追加とした項目は、起草・検収・保存の後の正式なファイル名を受領した時点で、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」の候補差分へ含める。
   既存のmerge操作での全体確認と保存、未遷移の項目の処理開始、選んだ担当への引き渡しまで確かめ、作業中のレーンには凍結済みの計画を保って工程境界で追加の計画を受け入れさせる。
   登録を`予定`とする場合は、修正の時機とは別に、本書「対象外の不良と是正要求」が参照する待機中の前提と再開条件を確かめる。
8. 実行レビューから返された差分範囲の外の既存不良も本節で時機を判定し、原因分析と起草は`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「返却に含まれる既存不良の受領」の独立した投入担当へ渡す。

## 即時対応の手順

本書「即時対応」で直接修正が要ると判定した、メインや委譲先が見つけた既存不良と、処理中にユーザーから届いた是正要求に使う。
最小限の直接修正と正式対応用AWIの登録でいったん区切るのは、欠陥と未確定の候補・効率改善と、先送り条件に当たる不良に限る。

1. 事象、期待する結果、現在と後続のセッションへの影響を確かめ、直接修正の対象と方針を決める。
   原因は安全に修正できる程度まで特定し、本格的な原因分析は正式対応へ委ねる。
2. 本書「レーンの変更範囲へ加える修正の認可」で担当・基点・時機を決め、書込権限を持つ担当が必要な範囲に限って修正し、修正箇所が安全に動くことを確かめる。
   修正対象、方針、認可、観測結果と、残る工程と次のセッションで同じ停止が起きるかの判定と根拠を、後続の担当が修正の充足を検収できるよう既存の引き継ぎ記録へ追記する。
3. 修正後の規範が配布と再起動を経て届くまで従わせる規則（暫定規則）が確定したら、メインは現行の全体作業契約の「即時対応で確定した暫定規則」節へ書き、稼働中の担当へ同節の再読を指示する。
   以後に起動する担当へは全体作業契約の受け渡し（`whole_contract_path`）で届け、軽量起動では必要な規則を委譲本文へ写す。
   各暫定規則には、目的、前提とした観測、適用範囲、緩和・解除の条件を添える。
   条件が変わった時の継続の判断は`agent-toolkit:atk-mode/playbooks/main-reporting.md`「進捗点検」で行い、ユーザーが決めた結果や認可の変更はユーザーの判断を得て行う。
   暫定規則は同じセッションの全体作業契約を受け取る担当にだけ届くため、規範への最小修正を今回の公開に含め、公開工程の開始前に各暫定規則に対応する最小修正のcommitがあることを確かめる。
   並行・後続の別セッションにも影響する停止の回避策は、`agent-toolkit:atk-mode/playbooks/main-reporting.md`「停止の回避策の共有」に従い、既存のホスト固有の規範にも記録する。
4. `agent-toolkit:atk-mode/roles/add-wi.parent.md`に従って正式対応用のAWIを起草して投入する。
   通常の投入の例外として、暫定修正のcommitと差分、観測と検証の結果、未確認事項、残りのテスト、独立した文脈でのレビュー、原因分析、類似箇所の見直し、再発防止策の情報を引き継ぐ。
   既存のAWIを再利用する場合は、これらが全て含まれていることを確かめる。
   暫定修正のcommitが無く回避だけで進めた場合は、手順2の停止の判定と根拠も渡す。
   次のセッションで停止、誤った判断や成果物の作成、ユーザーの再指摘が起きる見込みがあれば、投入の前に直接修正へ戻る。
   未実施の正式な分析、類似の見直し、恒久対策は未実施と明示する。
   正式対応の時機は本書「即時対応」で判定し、今回なら選定と担当への追送まで進め、次回なら理由と再開条件を付けて引き継ぐ。
5. 直接修正と正式対応AWIの対応を引き継ぎ記録に残してから、元の工程を再開する。

正式対応を引き継いだ後続のセッションは、暫定修正を完了とみなさず、AWIの全ての要求と`agent-basics:bugfix`の基準で検証する。

## レーンの変更範囲へ加える修正の認可

直接修正の担当・基点を決める前に、修正先リポジトリの`repositories`設定の`edit`を確かめる。
`allow`の場合だけ直接修正し、`awi`なら正式対応AWIを投入し、`deny`か未登録なら必要な変更をユーザーへ報告する。
未登録でユーザーが編集を明らかに求めている場合は、識別子と編集可否を示してエージェントが登録する案を確認し、承認後に登録する。

1. 担当・基点・時機は、現在の工程と修正対象の所有権から次の順で決め、判定と根拠を既存の引き継ぎ記録へ残す。
   独立した修正ごとに統合済みのレーンを再開する必要は無い。

   | 状態 | 担当・基点・時機 |
   | --- | --- |
   | 未統合のレーンが同じ対象を編集中 | 現担当へ最小修正を認可し、そのレーンの現行版で検証・独立文脈レビューする |
   | 全レーン統合後の独立した修正 | 統合先を所有する担当が統合済みHEADを基点に直接修正し、限定検証と独立文脈レビューを経る |
   | 現工程の進行を妨げない独立修正 | 現工程の安全な区切りで実施し、公開前に取り込む。公開後なら公開手順の再公開へ接続する |
   | 現工程または次の処理を停止・遮断する修正 | 必要な最小修正を先に行い、安全性を確かめて元工程へ戻る |
   | 元WIの未達・今回混入した不良 | 元の担当・要求・完成条件で完遂し、独立した即時修正へ付け替えない |

2. 未統合のレーンへ加える場合は、技術的に確定した最小範囲の対象と方針を同じスレッドへ追送し、正式対応AWIの起草中も認可済みの修正を進める。
   統合先に書き込む担当が未確定なら、メインが担当と認可範囲を確定してから書き込む。
   - 認可には修正対象、修正方針、出所（レーン担当の報告とメインの判定）を含める。
     この対象と方針が追加修正の書込認可の境界であり、エージェント向け文書も同じ境界で扱い、確定済みの計画は保つ。
   - 実行レビュー担当を起動する時は、その認可を`review_contract`の条項として渡す（`agent-toolkit:atk-mode/references/review-contract.md`「`review_contract`の生成」）。
   - 対象や方針が定まらなければ安全な修正に必要な事項を調べ、ユーザー固有の判断が残る場合だけ確認する。
   - 修正済みの箇所も正式対応AWIの検証対象に含め、メインが修正commitと報告を担当へ渡して正式対応AWIの登録を確かめる。

## 対象外の不良と是正要求

1. 本書「即時対応」で次回へ渡す不良・是正要求・独立改善は、`agent-toolkit:atk-mode/roles/add-wi.parent.md`への委譲で`source: process-wi`のAWIとして投入する。
   次回へ渡す理由は、欠陥と確定した既存不良なら該当する先送り条件の名前と根拠から、未確定の候補・効率改善ならその区分の根拠と本書「即時対応」手順3の比較の結果から書き始め、再開条件も同じ記録へ残す。
   修正の時機とAWIの登録の時機は分け、待機中に判定できる改善要求は`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「待機中の先行実施」に従って発見時に保存まで進める。
   ユーザーからの要求は、`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と承認」に従って発話を逐語的に転記する。
2. 投入担当から結果を受け取ったら、投入済みのWIと対象箇所を自分の引き継ぎ記録に対応付け、報告元へその対応を伝える。
3. 公開工程の開始後も、CIの失敗など公開を妨げる不良は公開担当の手順で直し、独立した既存不良への最小限の修正は正式対応AWIと対応付ける。
   同じ実行への明示追加・今回の不良・次回の遮断も「即時対応」に従う。
   追加修正の統合後の再公開は`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「公開状態の検収と再起動」に従う。

## 開始後に追加されたWIの確認

1. 選定メインは初回の取得で、一覧の表示条件とは独立した開始時の集合（全状態・全種別のWI識別子）を同じ実行で保存し、再開時も同じ保存集合を使う。

   ```text
   atk wi list --summary-only --state=processable --target-repo <対象リポジトリの絶対パス> --target-branch=auto --snapshot-output <開始時集合JSONの絶対パス>
   ```

   all-reposの初回保存と担当への引き継ぎは`agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md`「開始と振り分け」に従い、各対象の`snapshot_file`を使う。
2. 30分ごとの点検と公開工程の開始前に、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」の手順5と同じ方法で現在の候補差分を取得する。
   開始時の集合は新規と既存の区別にだけ使う。
3. 未判定の各WIの本文を`atk wi show`で取得する。
   常駐のprocess-loopが起動した統括は、30分ごとの点検と公開開始前の新着確認で、今回の対象の処理可能なAWIが`source: implement`と`merge_branch`を持つことを確認したら、公開開始前は「即時対応」の改善の時機判定を経ず、その回の追加候補へ入れる。
   現在担当中のWIは重複して割り付けない。
   選定済みで担当を離れ、未完のままinboxへ戻った項目は、今回扱うと判定したら新規の追加ではなく`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「既存WIの再開」へ渡す。
   公開開始後の新着は次回の選定へ残す。
   追加候補は`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」へ渡す。
   マージ用AWIは`レーン: なし`とし、`agent-toolkit:atk-mode/playbooks/implement.md`「マージ用AWIの処理」で取り込んで公開する。
   それ以外の項目は本書「即時対応」で時機を判定し、即時対応・今回追加の項目を同じ追加手順に渡す。
   ツール・規範・hookの改善という分類だけで次回へ回さず、今回扱うと明示された項目は既存の依存・保留・系統・認可の条件を満たせば処理する。
   WIの識別子、判定、根拠を既存の作業記録へ残し、前提が変わらない場合に次の点検で再利用する。
4. 通常とsingle-laneでは選定メイン、all-reposでは統括が、対象リポジトリ、開始時の集合の所在、今回の同期取得の結果、未判定の集合と時機を点検の記録へ対応付ける。
   同期の失敗、基準の欠落、未判定を「新着なし」と扱うことは避ける。
   再開後も同じ基準と残りの確認を復元し、公開の開始前に実施の証拠の欠落を補う。
5. 同じ実行で保存済みWIの正式名を受け取ったメインは、保存先が今回の処理対象リポジトリなら、30分の点検を待たずに受領した時点で本書「即時対応」の時機を判定する。
   WI投入担当の保存結果、実行レビューの既存不良、改善点の通知など、受領の経路を問わず適用する。
   起草時の投入先や前提が変わった場合は、保存結果の対象と本文で判定し、判定と根拠を既存の引き継ぎ記録へ残す。
6. all-reposでは統括が各対象の確認を所有し、処理を終えた対象の追加・再開候補も、律速でなく資源に余力があれば他の対象の終了を待たずに同じ巡回で処理する。
   実行中の対象への是正要求と今回混入した不良は、本書「即時対応」手順1の完遂の条件で扱う。
   処理中のリポジトリ担当へ確認を任せた場合は、その判定の記録を受領して再利用し、今回追加とした項目の選定と担当への追送を確かめる。
   開始時の候補と初回配分は保持し、新着のWIは追加分として扱う。

返す報告に含める項目: 項目ごとの区分と時機、担当と基点、直接修正のcommit、投入したAWIと次回へ渡した理由と再開条件、新着の確認の記録の所在。
