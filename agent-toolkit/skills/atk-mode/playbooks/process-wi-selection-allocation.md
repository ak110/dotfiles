# WIの選定：調査とレーン分け

選定メインが、候補の規模と書込対象を調べ、今回の集合とレーン分けと所要の見込みを決める手順書である。
`agent-toolkit:atk-mode/playbooks/process-wi-selection.md`「処理対象の決定」の後に上から実行し、終えたら同書「集合確定直後の処理開始」へ戻る。
欄の書式は`agent-toolkit:atk-mode/references/process-wi-selection-format.md`、見込みの補正は`agent-toolkit:atk-mode/references/process-wi-selection-estimates.md`が定める。

方針は次のとおりである。
レーン分けで満たす価値は、所要時間の均等化、依存の連結成分を分けないこと、レーン数の最小化の3つである。
全体の完了時間は最も遅いレーンで決まり、レーンを増やすほど起動の固定費も増える。
レーン数の上限、6000秒の比較、全工程の所要算定、巨大WIの承認は、ユーザーが決めた時間目標の運用であり、全ての選定で行う。
監査記録は`docs/development/audit-records-wi.md`にある。
レーン数ごとの所要の比較の節は「agent-toolkit/skills/atk-mode/playbooks/process-wi-selection-allocation.md：調査とレーン分け：2026年11月17日」である。
配分の節は「agent-toolkit/share/pick-wi.subagent.md：調査とレーン分け：2026年8月31日」である。

## 調査とレーン分け

1. 各AWI本文を`atk wi show`で取得し（all-reposの担当は受け取り済みの本文を使い、不足する項目だけ取得する）、実装・実行レビュー担当と`engine:model/effort`の明示指定を探して`担当モデル`へ写す。
   処理区分、依存順、変更対象の重複、規模を本文で確定できない場合だけ、定義・参照元・既存実装を限定調査する。
   `source`の無い手動投入AWIも症状と端末出力から要求を読み、本文と調査で一意に解決できない不足だけを返す。
   規模は本文からも見積もり、矛盾すれば実測を優先する。
   依存連鎖と独立WIの準備順と後続の不確実性を比べ、成果依存を区別して`根拠`欄へ渡す。
2. 作業を伴う回答済みUWIは、質問、判断材料、回答から新たに必要になった作業を特定し、その書込対象を元項目とは独立に限定調査で見積もる。
3. 本文の変更要求から「既存先」「新設先」「参照先」「除外先」「公開工程所有」を判別する。
   本文から抽出したパス、ファイルの有無、名前順、件数は手がかりにとどめ、幅広い暫定範囲は重複判定の前に限定調査で必要な対象へ狭める。
4. 処理可能な候補は目標所要時間にかかわらず全件を選ぶ。
   着手済みの`processing`と再開位置を持つ項目を含める。
   回答済みUWIを先に置き、AWIは最古の項目と`urgent`の最古の項目を交互に、重複なく並べる。
   並べる前に`urgent`の本文と`atk wi list`の`priority_reason`を読み、影響が解消していれば解除する。
   依存・保留・認可を優先区分より先に判定し、処理対象外の候補と理由を記録する。
   回答済みUWIの元項目は同じレーンに含めて1回だけ数える。
5. レーン数は`floor((WI数+9)/10)`を例外のない上限とし、3つの価値を満たす最小の数を選ぶ。
   `WI数`は`agent-toolkit:atk-mode/references/process-wi-selection-estimates.md`「初回配分の算定根拠」の`候補WI`の件数N（今回選んだ全件）である。
   途中で追加されたWIは初回の件数から外し、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」で扱う。
   初回の候補集合、初回割当、成分を構成するWI、型付き結合条件は`初回配分`に保存する。
6. 所要時間は、既存の方針から変更を一意に導ける軽い項目か設計判断を要する項目かという性質と、変更対象の範囲から見積もり、同じリポジトリの直近の統合済みの実行記録で補正する。
   - 再開位置を持つ項目は、計画の進捗ログや証拠に残りの作業量と処理済みの量があれば、残量とその計画で観測した速さから見積もる。
     記録が無ければ、その旨と採った根拠を`根拠`へ書く。
   - 実装・検証・直列統合の時間と、共有資源の処理能力と待ちも見積もり、上限内の並列数、独立準備の先行、準備・検証の集約を比べる。
   - 多数のファイルを編集するWIは1回だけ割り当て、ファイル群ごとの分担はレーン内で行う前提で、スクリプトで完結する変換、内部担当へ分担できる処理、レーン担当に残る判断・検収・検証・統合を分けて見込む。
     見込みは、各群を直列に足した値と全処理が同時に進む前提の値の間にあり、内部の作業構成から求める。
   - 共有の待ちの記録が無い場合は0秒にせず、共有実行枠（`agent-toolkit:atk-mode/playbooks/verification.md`「統合実行ツール経由の起動」）と統合の順番から推定する。
   - `target-seconds`がある場合は、補正後の全体の完了見込みを目標と比べる。
     超える場合（`pick-wi-check`は警告し、選定は止めない）は、上限の内側で段階の組み直し、独立した準備の先行、準備・検証の集約を比べ、採った案と比べた見込みを`目標超過時の配分比較`へ記録する。
     超過が残っても組み直しの判断を30分ごとの進捗点検で続ける。
   - 6000秒は、対象と品質工程を保つ配分を上限内で比べる目安である。
     超えても全対象を同じ実行に保ち、複数の成分を同じレーン内で順に処理し、段階案でも累計のレーン名数を上限内に抑える。
7. レーンを次の手順で分ける。
   1. 各項目の変更要求から、予定するファイルか妥当なディレクトリ範囲を`書込対象`へ記録する。
      公開工程だけが書く対象（対象リポジトリの規範が公開単位の統合後の公開工程でだけ書くと定めたもの）は`公開工程の書込対象`へ分け、`公開工程の規範根拠`にパス、規範ファイル、節を1件ずつ記録する。
      他候補と重なる暫定範囲は限定調査でファイルと節・定義まで狭め、一意に定まらなければ分割不能とする。
   2. 候補内の同じリポジトリの`depends_on`、同じ再開計画、同じ段階で同じファイルの同じ節・定義を変える項目は、分割不能な連結成分として同じレーンへ置く。
      同じ再開計画かは、`~/.claude/plans`内の絶対パスか、観測のみの再開位置の`private-notes/plans/`からの相対パスで比べる（`計画なし`と再開位置なしの項目どうしは結合の対象外）。
      同じ計画は進捗ログとレビュー指摘管理表を共有する書込資源なので、どの割り当てでも1つのレーンに置く。
      同じファイルでも変更箇所が一意に特定でき重ならなければ別レーンに置ける。
      書込の直列化はレーン内の実装順か段階化で扱い、`depends_on`の新設と次回送りは手段から外す。
   3. あるAWIの書込対象が別の候補の書込対象を完全に包含する場合は、単一段階案では包含する側を先にし、重なる候補を同じ成分に含める（包含だけを理由に`depends_on`を設定しない）。
   4. 6000秒の超過を不可避とする前に、上限の範囲内で互いに独立したグループを同じ段階に置く段階案と単一段階案を比べる（例: AがX、BがXとY、CがYを変える場合、A・B・Cを並行に始め、BはA・Cの後に統合する）。
      各段階の最長レーンの実装時間と統合時間の和を全段階で合計し、共有待ちを1回加えて短い案を採用する。
      比べた数値は比較欄、理由はレーンの`根拠`に記録する。
      後段レーンの着手条件と統合順は`agent-toolkit:atk-mode/playbooks/process-wi-lanes.md`「レーンと資源」に従う。
   5. 保存前に別レーンの`書込対象`をパス要素で比べる。
      共通ファイルか包含範囲を持つ未統合レーンを独立に進める場合だけ、共通ファイルか狭い方の範囲ごとに双方の定義と`交わらない`判定を`レーン間の重なり`へ1件記録する。
      定義が交わるか独立性が未確定なら、同じレーンへまとめるか手順4へ戻る。
      書込が交わる場合の順序はレーン行の並びで示し、必要な成果の依存は`着手前に必要なレーン`に書く。
      段階と先行レーンは生成結果から読む。
8. 書込競合と成果依存を分け、先行成果を要しない調査・要求の確認・機械的な変換の準備は`agent-toolkit:atk-mode/playbooks/process-wi-lane-resources.md`「後段レーンの先行調査」と比べて先行統合の前に進める。
   成果依存で後から行う差分確認と正式な計画の起草・検査も所要に含める。
9. 上限との関係は次のとおり扱う。
   - 同じ成分を同じレーンに保ったまま、複数の成分を各レーンへ順に割り当て、見込みが6000秒を超えても上限を保つ。
   - 1つの成分の見込みが他の成分の合計より長い場合は、上限の内側で、その成分と書込対象が交わらない成分を別のレーンへ置き、この配置を均衡より優先する（同じレーンの項目の統合と公開が長い成分の完了まで待たされるため）。
     別のレーンを確保できない場合は、その成分を後に回す順序を選び、比較を`根拠`へ書く。
10. 段階2以上を採用する場合は、比べた単一段階案の補正後の完了見込み秒数を最上位の`単一段階案の完了見込み秒数`に記録する。
    全行が段階1で実装秒数が6000秒を超える場合は、比べた段階案の補正後の秒数か、固定値`成立する段階案なし`を`段階案の完了見込み秒数`に記録する。
    本文に無い新設ファイル名まで特定できた場合は書込区分に個別パスを指定し、`導出した新設先`に要求との対応と配置根拠を記録する。
    共有の設定や定義の字面の違いだけで独立と判断せず、双方の定義と接続先を確かめてから分割不能条件を当てる。

## 内部担当の同時数と巨大WIの判定

配分と進捗点検では、内部群の総数と、巡回全体で同時に動かす軽い内部担当の数Cを分ける（読取・実装・レビューの担当を合わせて数える）。
agents_serverは役割とエンジンを問わず全担当を合算し、マシン全体の上限を超える起動を空きが出るまで待たせるので、Cとレーン担当の合計がこの上限を超える配分は見込みに使わない。
内部群の所有と起動は`agent-toolkit:atk-mode/playbooks/delegation.md`「委譲単位の確定」に従う。

1. Cの上限は、実行マシンのCPU・メモリー、共有実行枠、サービスの利用上限と費用から決め、プロジェクト規範が値を定めていればそれを使う。
   上限の内側では、最長経路が目標所要時間に収まるCを選び、特段の理由が無ければ各レーンへ均等に配る。
2. 選定時に、仕事群ごとの作業量W、最長の群P、共有検証量Vと直列部分から最長経路を見積もる（未確認の条件や作業量を0にしない）。
   最初の30分点検で群ごとの実測と比べ、差が大きければ上限の範囲で配分を替えるか群を組み直す。
3. 同時数が律速かは、必要成果がそろった仕事のC上限待ちを、成果依存、共有実行枠、公開CI、資源とサービスの待ちと実測で区別して裏付ける。
   上限を超える案は、上限の同時数でも最長経路が目標を超え、上限待ちが律速と実測で示された場合に、資源と追加費用の根拠を添えて比べる。
   既存の金額上限を守り、未指定の金額と未取得の料金は未換算の実行量のまま示す。
4. 巨大WIの判定では、長い初期見込みだけを根拠にせず、同じ品質で分割、並行化、先行レビュー、共通仕事の集約を比べる。
   並行区間と不可避の直列区間を先に分け、並行区間の総worker分W、成果依存の最長経路P、共有実行枠の検証量Vを対応付け、検証の同時数をKとして、合理的なCの下の`max(W/C,P,V/K)`に、重複加算しない直列分Sと他の工程との依存・資源Fを順序どおり加える。
   この下限が目標所要時間を超える場合だけ、配分では収まらない根拠になる。
5. 巨大と裏付けられた具体的なWIだけ、ユーザーが名指しで承認した場合に時間目標から除外できる。
   レーンは対象、範囲、資源費用の根拠、最短案、目標との差、除外範囲、通常WIへの影響を統括へ通知し、統括は`agent-toolkit:atk-mode/references/delivery.md`の事前承認へ進む。
   有限の回答期限と公開の質問手段があればその場で質問し、無ければ個別の事前承認型UWIと元WIの回答依存へ接続する。
   個別承認は、一般的な例外方針、無回答、対象の無い継続指示と区別して確かめる。
   未承認と拒否の時は通常の時間対象に保ち、承認後も全件の実装、必要な品質、公開を保つ。

同時数の監査記録は`docs/development/audit-records-wi.md`にある。
該当節は「agent-toolkit/skills/atk-mode/playbooks/process-wi-selection-allocation.md：内部担当の同時数と巨大WIの判定：2026年11月12日」である。

## 反映先と上流投入

1. 反映先の調査は、分類、変更領域、配分の確定に要る範囲に限る。
   実装方式、採否、既存実装による充足はレーンの計画起草で判断する。
2. 対象リポジトリ単体では完結せず上流リポジトリの改訂が要る項目は、`上流投入`、`上流投入先`、`上流要求`を記録する。
   レーンの割り当ては`agent-toolkit:atk-mode/references/process-wi-selection-format.md`「選定結果の書式」の組み合わせ条件に従い、外部操作だけを要する項目も同じ条件で通常レーンへ渡す。
3. `続行できない理由`に記録する事由は、キュー入力の不整合、本文から明白に読めるユーザーの選好、外部待ちに限る。
   公開契約の変更要否と採否は、レーン担当が計画の起草で確定する。

## プロジェクト規範の指定

1. 書込の前に、プロジェクトのスキル表から選定や`プロジェクト規範の指定`を扱うスキルを特定して起動し（起動できなければ資料を読む）、各AWIの反映先へ指定内容を適用する。
2. `プロジェクト規範の指定`には、プロジェクト規範が選定結果への記載を明示している場合に限り、その規範が指定する値を記録し、指定の無い内容を推測で補わない。
   値にファイルパスが含まれる場合は、実在して読めることを確かめる。
   `pyproject.toml`の`[tool.agent-toolkit.pick-wi-check]`の`norm-spec`が条件を定めている場合の指定の欠落は、`atk run-script pick-wi-check`が終了コード1で示すので、直して終了コード0にする。

返す報告に含める項目: 処理対象の件数と除外理由、レーン数と上限、段階、目標との比較と採った配分案、巨大WIの承認の要否。
