# 由来と承認の形式

本書は、WIの要求単位の由来、`source`と`scope`の値、承認として扱う記述、範囲語と程度、ユーザー専用の記入欄、逐語引用を定める。
いずれも、顧客の言葉を目的から読んで狭めも強めもしない原則1と、観測したことだけを事実として言う原則3の適用である。
原則の本文は`agent-basics:writing-standards/references/quality-principles-roles.md`と`agent-basics:writing-standards/references/quality-principles-facts.md`にある。
要求がユーザーの言葉かエージェントの補足かを取り違えると、ユーザーが求めた範囲が処理対象から外れるか、求めていない条件が後続の工程を縛る。

## 由来と承認

要求単位の由来は、要求ごとに出所を観測して決める。
WIの作成者と起票の契機（`source`）は、個々の要求の出所と承認範囲とは別の事実として扱う。

- frontmatterに`source`が無い項目だけを、人間由来の初期値とする。
- `source`に値がある項目は、要求単位の由来が次の4つのいずれかで裏付けられない限りエージェント由来とする。
  末尾に置いた厳密なH2見出し`## ユーザーコメント`の下の要求（本書「ユーザー専用の記入欄と是正要求」）、UWIの`## 回答`に記録された要求、関連する計画書の「実施内容」に記録された由来、本書「逐語転記」の形で本文に残した対話の逐語引用（他の見出しの下にあってもよい）である。
- 起草者が「ユーザーの要件」と要約した記述も、逐語引用に無い範囲はエージェント由来とする。
- 由来を区別できない要求は、人間由来として扱う。
- 引用された発話の主と、WIを作成したセッションや実行環境は別の事実であり、後の2つは作成処理の記録から判定する。

ユーザーが指定した要件は、原文で明示された要求単位に限る。
エージェントの提案への了解は、実際に提示して問うた結果と範囲だけに対応付ける。
後から具体化した内部方式、仮説、未回答の案は、エージェント由来として扱う。
ユーザーが明示した技術条件は内容を保つ。

確認の回答のうちユーザー自身の回答として扱うのは、選んだ選択肢と自由記述だけである。
質問文、`共通前提:`の行、選択肢の説明はエージェントが作成した文章であり、ユーザーから異論が出なかった場合もユーザーの要件から外す。

- `atk run-script session-review-evidence`の出力では、`text`と`user_response`（`answers`と`notes`）が回答に当たる。
  `assistant_context`（`question`と`options`）は意味、対象、除外、認可の解釈の補助に限って使い、JSONLの1行全体への部分一致は証拠から外す。
- 保存済みの記録が行頭ラベル`質問:`、`選択肢:`、`回答:`、`自由記述:`を持つ形式なら、`回答:`と`自由記述:`の値だけが回答である。
- 選んだ選択肢で確定するのは、その質問が直接尋ねた判断事項だけである。
- `共通前提:`の行が過去の合意を記していれば、合意が成立した発話か確認回答の逐語引用で確かめる。

失敗例: レビューの時機を問う確認で、質問の共通前提に「どちらの案でもレビューと修正は特定のモデルが行う」と書き、選択肢の説明に後続の処理もそのモデルで行うと書いた。
ユーザーは選択肢名だけで答えたが、起草者は後続の実装とレビューにもそのモデルを使う条件を全てのAWIの確定した要件へ置き、ユーザーが後で是正した。

逐語引用から直接導けない対象、範囲、外部から観測される結果を補った時は、引用の外に書いてエージェント由来とする。
補った内容がエンドユーザーの操作するコマンドや画面の動作を大きく変える時（進行を見る画面を無くす、会話や操作の単位を置き換える、自動で行う範囲を広げるなど）は、保存の前に確認する。
確認は`agent-toolkit:atk-mode/playbooks/confirmation.md`「認可を要する操作」に従う。
軽微な利便性の向上と、ユーザーが意識していない細部の変更は、エージェントが確定して報告する。
この確認の承認源は、その変更を示した発話か回答に限る（改善や見直しを広く任せる発話は承認源から外す）。
自律モードでは事前承認型UWIを保存してそのAWIの`depends_on`へ加える（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「承認型UWIと元項目」）。

## 由来と`source`

`source`は起票処理の記録であり、明示的な出所を持たない要求単位の由来の初期値に使う。
保存済みの`source`と`scope`の値と形式は、そのまま保つ。

- エージェントが投入する項目には`source`を必ず指定する。
  値は、起動中の作業かスキルの名前からプラグイン名の接頭辞を除いたもの（`add-awi-by-user`、`process-wi`など）とし、該当する作業もスキルも無い起票では`agent`とする。
  `/atk-mode add-awi-by-user`の作業は`add-awi-by-user`とする。
- スキル名が`review-session`の場合、作成するAWIの`source`は保存済み項目と由来をそろえるため`session-review`とする。
- ユーザーの指示に基づいて投入する場合も同じ規則で値を付け、人間由来の範囲は明示的な由来の記載で示す。
- `atk run-skill`が起動したセッションのUWIでは、`source`を`run-skill`とする。
  同じセッションのAWIには上の一般の規則を適用する。

一般の確認UWIと報告用UWIのどちらも、`--scope`にはSessionStartの起動入力の`skill`と`mode`から得た起動単位を渡す。
モードがあればスキル名、半角空白、モードを連結し、モードが無い通常起動ではスキル名だけを使う。
scopeに入れるのはモード語までとし、それ以外の自由記述は除く。

| 起動入力のskill | 起動入力のmode | scope |
| --- | --- | --- |
| `agent-toolkit:review-session` | なし | `agent-toolkit:review-session` |
| `agent-toolkit:review-session` | `batch` | `agent-toolkit:review-session batch` |
| `agent-toolkit:process-wi` | なし | `agent-toolkit:process-wi` |
| `agent-toolkit:process-wi` | `single-lane` | `agent-toolkit:process-wi single-lane` |
| `agent-toolkit:process-wi` | `all-repos` | `agent-toolkit:process-wi all-repos` |

起動入力の`skill`が作業`process-wi`の修飾名の行は、入口`atk-mode`の作業`process-wi`の起動単位を表す（同名のスキルは無い）。

次回の同じ起動単位はこのscopeのUWIを取り込み、通常起動や別モードのUWIと区別する。
旧保存データの取り込みは`agent-toolkit:atk-mode/references/answer-transitions.md`「`atk run-skill`の過去の実行のUWI」に従う。

## 承認

人間由来の内容を一部でも含む要求単位を、全部または一部不採用とする時は、事前に元の文面との差異、技術的な理由、代替案を示してユーザーの明示的な承認を得る。
未承認のまま処理を終えると、ユーザーが依頼した範囲が処理対象から失われるためである。
事後承認の予定、変更を元に戻せること、一部を採用済みであることは、承認の判定材料から外す。
一部の不採用に当たるかは、要求単位が求める結果で決める（`agent-toolkit:atk-mode/playbooks/confirmation.md`「原文からの具体化を要する軸」）。

承認として扱うのは、人間由来のWI本文、ユーザーコメント、UWIの回答、対話中の回答に、外部操作、対象、範囲が具体的に書かれている時の、その範囲だけである。
既存の承認を使う時は、その承認と今回の操作を対象、操作、影響、条件のそれぞれで比べ、全てが一致する範囲に適用する。
`source`の値、空のコメント欄、エージェントの推奨文、「進めてください」のような一般的な了解、無回答は、承認から除く。

要求の一部を別の作業単位へ引き継ぐことを理由に元のWIから外す時は、引き継ぎ先のWIが実在し、外す要求単位を過不足なく含むことを確かめる。
引き継ぎ先が無ければ、元のWIへ要求を戻すか、先に新しいWIを確定する。
同じ委譲元から同時に依頼された一連の分割起票と、投入先リポジトリの外の対象を委譲元へ通知して割り当てを委ねた場合は、元のWIを先に保存してよい。
その場合の引き継ぎ先の実在と対応は、委譲元が`agent-toolkit:atk-mode/roles/add-wi.parent.md`「保存の検収」で確かめる。

## 範囲語と程度

範囲語や開放列挙で示された集合は、`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」の記録書式で書く。
集合を狭める縮小に当たるかとその承認は`agent-toolkit:atk-mode/playbooks/confirmation.md`「原文からの具体化を要する軸」に従い、承認を得た除外は出所と除外理由を添えて書く。

「消せるだけ消して」「できる範囲で」のように程度や裁量を含む要求は、対象にする範囲の境界、待機時間や再試行回数、代替手段へ切り替える基準をエージェントが決める（`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」）。
走査した対象を測った値、観測根拠、QCDで決まる境界は確定し、根拠と除外した対象を完了報告に書く。
ユーザーへ確認するのは、調査を尽くしても境界の位置で要件や意図が曖昧に残る時と、許容できる費用や手放してよい保護などユーザー固有の判断が残る時である。
確認する時は、境界の位置ごとに外部から観測される結果と推奨案を示し、回答をその対象と範囲に適用する。
範囲語や開放列挙の集合のうち未走査の部分は確認に回さず、走査が技術的に可能な限り最後まで走査する（原則7、`agent-basics:writing-standards/references/quality-principles-ownership.md`）。
回答が得られない時の保留と終了は、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「承認型UWIと元項目」と「終了」に従う。

## ユーザー専用の記入欄と是正要求

UWIの`## 回答`とAWIの`## ユーザーコメント`は、ユーザーだけが書く節である。
エージェント環境の`atk`は、これらの節を含む本文の投入と編集を拒否し、`atk wi edit --body-file`では`## ユーザーコメント`を編集対象から外して保存済みの内容を保つ。
例外として`atk wi edit --move-user-comment`は、保存済みのコメントの全行が新しい本文の`## ユーザー指摘の逐語引用`にある時だけコメント節を削除する（`agent-toolkit:atk-mode/playbooks/process-user-comments.md`）。

エージェント由来の項目への記入や回答が、その項目の前提、対象、方針、採否を否定していれば、ユーザーからの是正要求として扱い、次の順に進める。

1. 対象項目が未終了なら、調査より先に保留する（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「保留と本文修正」）。
2. `agent-basics:review-standards/references/reviewee.md`「ユーザー指摘の受領」に従って採否を確定する。
3. `agent-basics:bugfix`を起動し、是正の対象へ5つの問いを適用する。

記入が以後の同種の作業にも当てはまる方針の候補を含むかは、是正要求に当たるかによらず`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」で判定する。
記入欄に処理担当宛ての質問があれば、回答をUWIに記録して返し、その保存の完了を、対象の維持か変更を確定して元のWIを終了する条件にする。
協調モードの対話で回答を伝えて本文へ記録した質問は、UWIへの記録を省く（`agent-toolkit:atk-mode/playbooks/process-user-comments.md`）。

既存のWIを、状態によらず別の判断の前提、制約、代替案の不採用理由、完成条件などの根拠に使う時は、ユーザー専用の記入欄を含めて全文を読み、本書「由来と承認」の要求単位ごとの由来から有効な要求を確定する。
エージェント由来の本文とユーザーの記入や回答が衝突する時は、ユーザーの記入を有効な前提とし、是正された本文側の古い記述を根拠から外す。
根拠に使う判断の主体が、その是正要求を直接受けたエージェントでない場合も同じである。

## 逐語転記

`## ユーザー指摘の逐語引用`に転記した発話は、そのAWIを投入したセッション（投入元セッション）へ向けた発話である。
質問の形か、解決済みと明記されているか、`source`の値によらず、投入元セッションで解決済みとして扱う。
後続の処理側（実行レビュー担当、統合時の完成条件の判定など）は、逐語引用を達成すべき要求や回答すべき質問として扱わず、`## 反映内容と反映先`と`## 完成条件`を正しく解釈する背景として読む。
処理側が達成を確かめるユーザー発話は、処理側宛ての`## ユーザーコメント`、回答済みUWIの`## 回答`、計画書の`ユーザー指示`行、完成条件節を持たない人間由来のAWI本文である。

ユーザーの要求を起点とするWIには、会話の中で採否や実装方針の根拠になった原文を逐語で転記する。
ユーザーの発話と、エージェントの質問、説明、判断は区別する（`agent-basics:writing-standards/references/writing-genres.md`「ユーザー入力素材の取扱い」）。
認可や解釈の判断に再取得が要る場合は、必要な所在を残す。
転記は、ユーザー専用の2つの記入欄とは別に置く。
転記する発話に質問が含まれていれば投入元のエージェントが回答を作り、実際にユーザーへ届けた質問に限り、引用の近くに「回答済み」と書く。
届けたかは、回答を確定したことではなく、ユーザーへ実際に送ったことで判定する。
WI投入担当の調査が要る回答を届ける時期と、返却後の訂正は`agent-toolkit:atk-mode/roles/add-wi.parent.md`に従う。

## 逐語引用の対応付け

引用節は、ユーザー発話を起点とするAWIだけに設ける。
転記する対象は、目的、対象範囲、外部から観測できる結果、実行上の制約、承認状態を変える、実際に届いたユーザーメッセージに限る。
委譲先のエージェントでは、委譲の依頼文と追加メッセージのうち`<forwarded-user-input>`で囲まれた逐語テキストだけを対象にする。
引用節の原文と反映内容を読み比べ、脱落、追加、意味の変化が無いことを確かめる。

複数の項目へ分割する時は、`## 反映内容と反映先`に記録する要求内容と割当先の短い説明で、各項目の担当範囲を特定する。
分割元の依頼全体や背景に属する単位は、同じ節にその内容と役割を短く書き、担当範囲と区別する。
原文が開放集合を示す時は、調査で確かめた具体的な対象、根拠のある追加、承認された除外を、`## 反映内容と反映先`の該当項目へ対応付ける。
原文は引用節に1度だけ残す。

分割、開放集合、多数の発話を含む複雑な取り込みでは、保存の前に`atk run-script wi-quote-check`で引用と原文の一致、要求単位ごとの引用位置を確かめられる。
通常の転記は、ログの探索、位置の計数、専用のスクリプトでの一致確認を省いてよい。
