# WI保存前の考慮漏れ点検

WIの起草者と投入前レビュー担当が、原文・原稿・調査根拠から考慮漏れを探すための定義である。
点検する時点は、起草の方針（対象、範囲、採否、手段）を決める前、質問を終える前、原稿を確定する前、登録0件で終える前、候補を不採用にする前である。
最初の時点は、方針の伝え方がどれであっても、方針を決める判断の前である。
推奨案や選択肢を示す場合、確認せずに起草へ進むと決める場合、「〜するAWIを起草する」と予告する場合、方針を伝える工程を持たない起草の流れ（プロジェクト固有のWI作成スキルを含む）のどれも、この時点に当たる。
選択肢を示す前は、(c)と(d)を、推奨しない案と、推奨の結果として登録しないことになる候補にも適用する。
再発した考慮漏れの予防は、該当する類型を本書へ統合して次の点検へ戻す。

## 点検類型

原稿や起草者の分類を読む前に、原文から利用主体、開始状態、到達結果を定め、各類型の結論がその結果に対応するかを確かめる。

| 類型 | 比べる内容 |
| --- | --- |
| (a) 範囲の限定 | 規定の対象、完成条件、実物を調べた範囲を原文の範囲表現と比べ、例示、理由、観測した症状、現行の仕組みで扱える範囲への縮小が無いか。改善の中心に置く対象、継続的なコストを加える対象、対象外・不採用の前提（読み手、環境、利用場面）を、観測した事実と未確認の想定に分けたか。採用する対象の読み手と利用場面も観測で確かめたか |
| (b) 関連して必要な変更 | 共通化、同じ機構を使う他の箇所、追随修正、同時に直す既存不良を含めたか。エージェント向け文書の変更は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「エージェント向け文書の構成」に従ったか |
| (c) 既存の仕組み・過去の判断との関係 | 同じ目的の既存機構、対象プロジェクトの方針記録と過去のユーザー指示、回答済みUWI、他のAWIとの重複・衝突が無いか |
| (d) 過剰さ | 読み手が常識で判断できる細則、過剰な制限・仕組みが無いか。推奨しない案と不採用にする候補も、既存要素の再利用・統合・削除を使う構造の違う案と比べたか（`agent-basics:writing-standards/references/design-heuristics.md`「問題と手段の比例性」）。対象リポジトリの既存の部品（稼働中の主体、既存の通信経路、既存のコマンド）で組める構成を、そのコストと便益で評価したか |
| (e) 後続工程の模擬 | process-wiの計画、実装、完成条件の検証、公開、終了までをたどり、検証の認可とコスト、第三者が観測する操作、実環境の対象、目標値に届かない時の扱い、実装の詳細で分かれる外部挙動、公開範囲にユーザー判断が残らないか |
| (f) 既存充足の過大判定 | 目的や名前が似た規定・機構があるだけで充足としていないか。同じ利用条件で同じ結果を得られる根拠と、判断の時点で本文が届く経路を確かめたか（`agent-basics:writing-standards/references/agent-documents-basics.md`「既存規範による被覆の判定」）。実効性を、送り手の入力や設定ではなく、受け手（委譲先、エンドユーザー、後続工程）が実際に受け取る入力・画面・出力で確かめたか |
| (g)(h)(j) 確認の要否 | `agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従い、確認の要否を判定したか |
| (i) 対象リポジトリの選定 | 方針確定か選択肢の提示前に、起動元と `atk config repos list` の登録先を、成果物で資料の主題が成立するかで判定したか。起動元の採否と理由、成立する派生先と除外理由を記録し、適用範囲を問う時は `agent-toolkit:atk-mode/references/choice-construction.md`「候補の構成」へ渡したか |
| (k) 自ら確定した判断の列挙 | 自ら確定した判断を、終了時報告へ書く予定のものと原稿の「技術判断」の注記も含めて全件挙げたか。追加発話で要求が増えた時に挙げ直したか。ユーザーやエンドユーザーが観測する結果を変える判断は、1件ずつ(g)(h)(j)と同じ判定へ通す |
| (l) 資料の主張の読み | 資料から読み取った主張ごとに、原文の該当箇所を語を変えずに示し、自分の言葉でまとめる前に、文字どおりの読みを含めて成り立つ読みを挙げたか。比べ方は`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」に従う |

(l)では、挙げた読みを資料の文脈（引用元と引用先、返信、具体例、添付、同じ資料の他の記述）と一次資料で確かめ、成り立たない読みを外す。
残った読みが両立すれば全て扱う。
確認するのは、読みが両立せず、ユーザーがその資料で何を問題にしたかで変更が変わる場合だけである。
調査で読みが定まる場合と、どの読みでも変更が同じ場合は、確認を省いて進む。

失敗例: 文章の下書きについての投稿を「見出しの過剰な細分化」と自分の言葉でまとめて方針を予告し、文字どおりの読み（見出しそのものを文で書く）と、引用した投稿が述べていた過記載を比べなかった。
読み違いの訂正は完了報告の後になった。

## 資料起点の比較

資料を起点とする起草では、次の順で比べ、結果を主張別の対応表（`agent-toolkit:atk-mode/playbooks/request-intake.md`の手順5）へまとめる。

1. 実物の調査を始める前に、資料が扱う成果物の種類に対応する、対象側の成果物の種類を挙げる。
   種類ごとに、実物を調べるか、調べない理由を残し、資料の主題に最も近い種類から調べる。
2. 1種類で問題が多く見つかっても、その件数だけで改善の中心を決めず、他の種類の結果と並べる。
   未調査の種類と調査済みの根拠は分けて示す。
3. 対応表は`agent-basics:writing-standards/references/design-heuristics.md`「外部資料に基づく改善案の評価」の3方向で作る。
   表現と構成が同じ利用場面の理解と判断を良くするかは(d)(f)で点検する。
4. 未確認の観点は、改善不要とせず調査中として残す。

外部の成果物（ツール、プラグイン、スキルなど）を参考にする場合は、次も比べる。

- 提供機能は、公式のmanifest、公開パッケージとソース、評価、更新とプライバシーの仕様から確定する。
- 利用形態は、対象側の単独利用、併用、配布環境、ホスト、OS、modeと、未導入、無効化、更新失敗を含めて対応付ける。
  例示に無いホスト、OS、modeも、対象側が提供・支援する利用条件なら比べる。
  提供範囲の外は根拠を付けて非該当とし、その環境への対応の追加は要求から除く。
- そのまま利用、知見の統合、併用、不採用の4方式を、品質への効果と継続コストで比べる。
  既存機能の接続と統合も候補に含め、技術で決まる導入の可否は起草者が決める。
- 機能があることと、見つけやすさ、操作する場所、手数、情報から判断と実行へのつながりは、別に評価する。
  既存機能の有無だけで充足とせず、現在と改善後の操作手順と便益を比べる。

この比較は、方針を予告する前、質問を終える時、原稿を確定する前に未対応を補い、(a)(d)(f)と確認の要否の点検へ使う。

## 処置と終了時報告

各類型で該当した論点は、調査で確定する、この場でユーザーへ確認する、回答・事前の認可・未達の時の扱いをAWIの本文へ記録する、のうち必要な処置へつなげる。
技術とQCDで決まる判断は起草者が決める。
完成条件、外部挙動、対象範囲、除外条件は、前提が成り立たない場合と環境・状態が違う場合にも目的を当てて点検し、登録の時点で分かる本人の判断を同じ質問の中で確認する。
登録の時点で確かめられる曖昧さを残すと、後続の自律処理が回答待ちで止まるためである。
処理の時に初めて分かる事項だけを、理由を付けて本文へ残す。

質問を終える時の報告に、全類型の点検結果（非該当を含む）と処置の一覧を示す。
ユーザーが確認の経緯と残る前提を判断するために使う。
原稿を確定する前の再点検で新しいユーザー判断が見つかったら、同じセッションで質問へ戻る。
この報告で保存前の一律の承認は求めず、投入前レビューに合格したら保存へ進む。
