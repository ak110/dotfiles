# 確認と報告の送達

メインエージェントが、ユーザーの判断が必要な確認と報告を見落とされない手段で届け、判断に関係しない実況でユーザーの注意を奪わないようにする。

ユーザーへの確認と報告を届ける手段と保存先、認識合わせの手順、自動生成する本文の標識、進捗点検の通知の扱いを定める。
確認するかの判定は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」が定め、本書はその後の届け方を扱う。

## 手段の選択

表の「発話本文」は、進捗・確認の前置き・完了報告など、回答を求めないメッセージを指す。
回答を求める質問・選択の手段は表の確認の行で選ぶ。

- Claude Codeは、`send_to_user`を使える時は常に`send_to_user`で届ける（`agent-toolkit:atk-mode/playbooks/host-claude-code.md`「ツールの入出力」）。
- Codexは途中経過を`commentary`、通常の最終応答を必要なツール処理の後の`final`で届ける（`agent-toolkit:atk-mode/playbooks/host-codex.md`「Codexホスト契約の適用」）。
  ホスト本体を停止する場合は、必要な報告を停止の前の`commentary`で届ける。
- 成果作業では、`agent-toolkit:atk-mode/playbooks/report-completion.md`で確定した作業完了報告の本文をそのまま使う。
- 報告の送達を終えてからホストを停止する。
  自律モードの完了報告は、報告用UWIの保存とファイル名の応答を`agent-toolkit:atk-mode/playbooks/report-completion.md`「工程」に従って行う。

作業の途中でユーザーへ送るのは、ユーザーの判断・確認・操作が必要なもの、ユーザーの発話への回答（作業前に置く「発話の理解」を含む）、確定した結果（WIの保存・採否、公開、失敗とその対処）、30分ごとの進捗点検に限る。
操作の実況（これから行うこと、待っているもの、読み終えた資料、次の工程の予告）と、結論や判断を変えない数値の細かい訂正は送らない。
送達済みの内容を地の文で言い換えたり再掲したりせず、伝える内容が無い時は`…`だけで終える。
1件の報告は短く書く。
送らない対象を広げて、判断が必要な報告や失敗の報告まで止めない。

本書「個別UWI」の条件と、権限拒否の偽陽性への`agent-toolkit:atk-mode/playbooks/permission-denial.md`「共通判断」の手順は、次の表より優先する。

| 工程 | 協調モード | 自律モード |
| --- | --- | --- |
| 事前承認 | 構造化質問を使う。Claude Codeは`AskUserQuestion`と`agent-toolkit:atk-mode/playbooks/host-claude-code.md`の制約、Codexは`agent-toolkit:atk-mode/playbooks/host-codex.md`の手順に従い、合う手段が無ければ`agent-toolkit:atk-mode/references/choice-construction.md`「質問の形式」の固定形式を使う | 有効な回答期限があり、ホスト契約に合う構造化質問を発行できるメインだけがその場で質問し、期限を過ぎたら「未確定判断の保留と暫定判断」へ進む。それ以外は最初から事前承認型UWIへ記録し、回答を要する元項目だけを保留する |
| 事前承認以外で回答を待つ確認 | 事前承認と同じ | 回答期限によらずその場では質問せず、事前承認型UWIへ記録して「未確定判断の保留と暫定判断」に従う |
| 事後承認 | その場で構造化質問する | 回答を待たずに事後承認型UWIへ記録し、作業を続ける |
| 認識合わせ | 本書「認識合わせ」の手順と事前承認の手段でその場で質問し、回答を待つ | その場で質問し、有効な回答期限を過ぎたら「未確定判断の保留と暫定判断」へ進み、期限が無ければ回答を待つ。構造化質問を発行できないCodex Default modeでは、自分の理解と質問をUWIへ記録し、回答を要する元項目だけを保留する |
| ユーザーへの報告 | 発話本文として届け、作業完了時は`agent-toolkit:atk-mode/playbooks/report-completion.md`の書式を使う | 同スキルの報告用UWIに記録する（セッションにつき1件） |

表の「未確定判断の保留と暫定判断」は`agent-toolkit:atk-mode/playbooks/confirmation.md`「未確定判断の保留と暫定判断」を指し、回答が無いまま終わった確認と、事前承認を要する元項目の回答待ちも同節に従う。
自律モードの「有効な回答期限」は、`atk wi process-loop`のように起動時に与えられた有限の期限を指し、有限の期限を設定したprocess-loopのClaude統括もその場で質問できる。
ユーザーの回答まで待つ設定・環境（無期限の設定、期限の機能が無い環境、期限が無効になる条件が成り立つ環境、Codex Default mode）は「期限なし」とする。
REPLの実行上限による質問の中断は回答期限ではない。
「期限なし」のまま、`agent-toolkit:atk-mode/playbooks/host-claude-code.md`「ユーザー確認（AskUserQuestion）」に従い聞き直す。
端末のフォーカスによる待機の延長中も「有効な回答期限」の区分を保ち、ユーザーが運用で対処する。
認識合わせを期限によらずその場で問うのは、割り込みや是正の直後に理解を確かめるためである。
ユーザーとの窓口を持たない委譲先は、確認事項を委譲元へ通知する（`agent-toolkit:atk-mode/playbooks/subagent.md`「確認事項の即時通知」）。

### Claude Codeの本文送信と再送

`send_to_user`を使える時は、手段の選択に従い進捗・確認の前置き・完了報告などを`message`で送る。
送達済みとするのは、ユーザーの画面への描画を確かめた成功の応答だけであり、呼び出したことや受付の応答は送達の証明にならない。
委譲の入力や記録に「回答済み」と書くのは、この手段で伝えた回答に限る。
REPLでは `await` で成否を確かめ、ツール名だけが表示された時はToolSearchかCode Modeの`describeTool`で説明を読む。
拒否の例外を文字列に変えて後続の質問や報告へ進まず、送信の失敗を処置する。

送信を拒否され本文の修正が必要なら、REPLの`Read`ツールで保存した本文を読む。
読んだ本文は出力せず、指摘箇所だけを`edit()`で直し、通知の呼び出しでファイルから再送する。
未読や未回収が原因なら先に解消し、保存した本文はそのまま再送する。
ツールを直接呼ぶ場合は本文を引数に渡して再送する。
判定が誤っている時だけ `misdetection` で申告し、正しい検出には本文を直して応じる。
未送達なら同じ本文に通知の `check` と1行の `reason` を添え、表示済みなら本文を再掲せず、次の送信に警告の `delivery_id` も添える。

### 個別UWI

個別UWIの要否は「確認要否の判定」で決め、未達条件の見送り、追加の認可を要する代替案、見込みの立たない外部変更待ちの選択もこの判定に含める。
自律モードでは必要な判断を事前承認型UWIへ保存し、元項目の依存の設定と回答後の再開へつなぐ。
委譲先は必要と確定した時点で委譲元へ通知し、リポジトリ担当は統括へ判断事項を渡す。
窓口を持つ統括は、保存と依存の設定を確かめた後に確認済みとして扱う。
依頼されたバグ修正の結果、自明な取得や再実行の案内、環境の制約で実機を確かめられなかった範囲は、通常の完了報告に含める。
手順が定める報告用UWIは必ず保存し、ユーザーが結果を確かめられるようにする。

次の場合は、モードによらず個別UWIを使う。

- AWIの`## ユーザーコメント`やUWIの`## 回答`へ直接書かれた質問への回答は、自律モードでも報告用UWIとは別の個別UWIで報告する。
  協調モードの対話で回答を伝え、本文へ記録した質問（`agent-toolkit:atk-mode/playbooks/process-user-comments.md`）は除く。
- ユーザーの判断・資料・操作が次の作業に必要な未完了事項は、必要と確定した時点で個別UWIへ保存し、保存の成功を確かめてから所在を案内する（同じ依頼の既存UWIは再利用する）。
  回答を待たずに確定できる作業は続け、関連作業の完了後に必要な事項は、その完了工程でのUWI登録を記録する。
  会話中の確認で回答を得た事項と、在席中に直接案内して完了を確かめた本人の準備（`agent-toolkit:atk-mode/playbooks/confirmation.md`「本人にしかできない準備の先行依頼」）は対象外とする。
- `agent-toolkit:atk-mode/references/conduct.md`「作業中に見つけた資格情報」の報告対象は、所在ごとに1件の報告用UWIを登録する。
  報告対象の値は、ユーザーが問題ないと判断して置いたものとして報告だけで扱う。
  所在は`agent-toolkit:atk-mode/references/uwi-format.md`「載せる情報」の表記に揃え、同じファイルの値は1件にまとめる。
  投入の前に、所在を固定文字列として`atk wi grep --summary-only -F --type=uwi --state=all --target-repo=all -- '<所在>'`で探し、同じ所在の報告があれば、発見の手法・作業リポジトリ・状態が違っても重ねない。
  無ければ、発見時の作業リポジトリに`--question-type=report`で登録し、回答を求めない。

報告にはUWIの所在だけを書き、判断や行動を求める依頼の見出しは省く。

### 報告用UWIに含めるもの

自律モードでは、次を個別の事後承認にせず報告用UWIに含め、事前承認の対象は事前承認のまま扱う。

- 起動中のスキル、適用中の規範、指示、計画の回答が定めた工程・対象範囲・副作用の枠内の作業
- 調査で解釈が一意に決まった要求の実施
- 規範からの逸脱
- エージェントが起草した完成条件の、技術的な理由による変更
- 限定探索の終了や再発防止策を見送る判断。
  害の大きさに応じた確定は`agent-basics:bugfix/references/similar-review.md`「害が大きい時」と`agent-basics:bugfix/references/prevention.md`「再発防止を採用しない場合」に従う。
  `review-session`の対象では、振り返りの結果の報告が兼ねる

事後承認は、実施の是非がユーザー固有の基準（選好、認可、成果物の見え方など）で決まる場合だけ求める。
回答で分かれる観測結果や操作を書けない事項と、内部の工程や進捗でしか判断の材料を説明できない事項は、報告に回す。
報告は判断を求める行為と区別し、報告用UWIは回答欄を持たない`--question-type=report`で保存する。
非同期の質問の送信の成功や初期のカーソル位置は回答や承認ではなく、回答を要する操作は実際の回答まで確定しない。
確認の拒否や承認要求の取り下げは無回答と区別し、「確認要否の判定」を適用し直す。
認識の違いで要件や結果が変わる事項が残れば事前承認型UWIへ記録して元項目の`depends_on`へ加え、確認が不要であれば自ら確定して続ける。

## 認識合わせ

冒頭の「発話の理解」（`agent-toolkit:atk-mode`「ユーザーの方針」）は、ユーザーの回答を待たずに作業を続ける提示である。
調査が要る質問・提案ではこれを調査前の一次回答に使い、調査後にメインが正式回答を届ける。
委譲先は結論と根拠をメインへ返す。
一次回答はClaude Codeでは既存の`send_to_user`（使えなければ通常本文）、Codexでは`commentary`を使う。
正式回答もユーザーに直接届け、操作が続く場合は同じ途中送達手段を使う。
即答できる質問は回答を分けない。
本節は、解消していない理解の差について、実際の回答を得る確認である。
ユーザーと認識がずれている可能性がある時と、行動を繰り返し指摘された時は、目標と課題の理解を次の手順で確かめる。

1. ユーザーが達成したい目標と解決したい課題を自分の言葉で示し、発話から得た理解と自分が補った前提を分ける。
2. 発話・記録・現物から確定できる訂正は、その場で直して報告する。
   残る相違だけを「確認要否の判定」と`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認の選択肢を組む手順」で問いにし、本書「手段の選択」の認識合わせの手段で実際の回答を得る。
   理解の確認と解決案の承認は、別の問いにする。
3. 回答を元の依頼の目的と要件に照らして、次の対応（採用済みの案の縮小、撤回、差し替えを含む）を決める。
   関係しない工程の実行モードは保ち、委譲先で認識合わせが必要な場合は、確認すべき論点を委譲元へ返す。

## エージェント宛てメッセージの標識

エージェントに直接渡る出力（`reason`、`additionalContext`、終了コード2のstderr）は、全体を`atk-auto`要素で囲む。
hookの出力はユーザーの発言と同じ形式で会話へ注入されるため、機械的に識別できる境界と出所を付ける。
`source`には、agent-toolkit自身なら接頭辞の無い生成元名を、他の生成元なら`<所有者>/<生成元>`を指定し、`kind`には通知の種別を指定する。

種別は、受け取ったエージェントが通知の原因を除けるかで選ぶ。
原因を除ける事象には`warn`、発話ごとの定型の配送には`notice`、遮断には`block`を使う。
`atk run-script session-review-evidence`は`info`か`notice`を持つhook通知を問題の候補から外すので、原因や対策を持たない通知に`warn`を付けると、発話のたびに候補の判定が起きる。

```xml
<atk-auto source="pretooluse" kind="warn">
detected ...
</atk-auto>
```

エージェント宛ての通知を`systemMessage`へ写す場合は、同じ`atk-auto`の開始・終了タグを保つ。
それ以外の`systemMessage`や`stopReason`などユーザー専用の本文と、追加のメッセージを持たない`permissionDecision: "allow"`の呼び出しには付けない。

## hook以外で生成する本文の要素

自動生成する本文は、hook以外の生成元でも`atk-auto`で囲み、`source`と`kind`で生成主体と用途を区別する。
エージェント間のメッセージ配送では、委譲先から委譲元への通知に限り`from`で送信元を示す。
境界は、最初の開始タグと、それに対応する最後の同名の終了タグで決まる。
保存済みの会話の記録にある旧要素名（`agent-toolkit-auto-inserted`）も、同じ境界として読む。

| 要素 | 対象の本文 |
| --- | --- |
| `atk-auto` | hook通知、規範、エージェント間の配送、機械生成の入力 |
| `forwarded-user-input` | 自動生成本文の中に保持したユーザー自身の入力 |

スラッシュコマンドはホストが1行目の先頭でだけ解釈するので、コマンドを含む本文では標識を引数の位置に置く。

## 起動案内と進捗通知

会話の開始、`clear`、会話の圧縮の時には、入口`agent-toolkit:atk-mode`の起動を求める案内が届くので、案内に従って起動する。
進捗点検通知（`source="progress-self-check"`）を受けた主体は`agent-toolkit:atk-mode/playbooks/main-reporting.md`「進捗点検」に従う。
委譲元は点検ごとの一律の受領の返答や再照会を求めず、ユーザーへの送達は本書「手段の選択」に従う。
