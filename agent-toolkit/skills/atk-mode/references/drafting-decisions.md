# 採否と実現方式の判断

WIの起草で、原因と変更する定義の所有者を決め、採否と実現方式を投入前に1つの案へ決める時の判断を定める。
起草の手順は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`にあり、本書はその手順5で読む。
確認へ回す事項は、同書「未確定事項と確認」へ戻して扱う。

## 原因と定義の所有者

通常の実装を求めるAWIでは、直接の原因と根本原因を現物で確定し、対策を1つの案に決める（手動の登録では独立した別件も同じ。原因分析はAWIで行い、UWIでは確認事項として扱う）。
事象を観測した場所、欠陥を作った実装、変更する定義、変更後に検収する場所を分けて特定し、`target_repo`には変更する定義を持つリポジトリを指定する。
外部のツール、SDK、共有設定の欠陥が利用側で表に出た場合は、定義を持つ生成側のリポジトリへ投入し、利用側で再現する条件を完成条件に含める。
ユーザーが出力だけを示した場合は、エージェント自身の実行環境（ツールの実行、サンドボックス）、CI、配備先も候補に入れてログと記録から発生箇所を特定し、ユーザーしか持たない情報が必要な場合は推測で埋めずに確認へ回す。
原因の特定に変動する値を使う場合は、事象の発生時点の値との比較を`## 原因分析`に書き、発生後の値しか得られなければ原因を未確定とする。
ユーザーが選んだ値、品質の水準、適用範囲に関わる対策では、それを保つ根拠か、変更への明示の合意を同じ節に書く。
ファイルや仕組みを削除・改名する場合と意味を変える場合は、変更前のパスと概念を表す語を対象リポジトリ全体（隠しディレクトリを含む）で固定文字列検索する。
設計文書とエンドユーザー向けの案内を含む直接影響範囲（`agent-toolkit:atk-mode/references/awi-body.md`「直接影響範囲」）を反映先に含める。
過去の記録を含むファイルでも、現在の状態を述べる記述（冒頭の案内、現在形の説明）は反映先に含め、除外は記述ごとに判定して根拠を証拠に残し、処理側の判断を左右する除外だけを本文に書く。

投入先リポジトリは、ユーザーの指定か委譲の入力の値に固定する。
投入先の外にも原因の仕組みを共有する対象は、`agent-basics:bugfix/references/similar-review.md`「同じ仕組みの他の箇所」に従って扱う。
委譲先は、その対象の所在、所有するリポジトリ、根拠、処置の要否を委譲元へすぐ知らせ、AWIの`## 反映内容と反映先`に、投入先の外であることと、委譲元へ知らせ済みで投入先は委譲元が決めることを書く。
投入先の中の原稿は完成させ、付随型は委譲元へ返し、専念型は検収と保存まで終え、メインは確認の要否の判定に従って投入先を確定する。
投入先の外の対象を処置不要と判断する場合は、現物のファイルとリビジョンを対応付けてその版で原因の条件が成り立たないことを確かめ、AWIの`## 反映内容と反映先`の除外事項かUWIの成立性の証拠に残す。

## 採否と実現方式の確定

採否と実現方式は投入前に1つの案へ決め、本文には確定した案だけを書く。
退けた案は、採った案の根拠を理解するのに必要な範囲で書く。
詳しい内部設計、変更するファイルの分割、実装単位、検証の手順と、起草者の環境で成立を観測できない機構の細部（外部CIでタグとビルド元を対応付ける手順、未実装の内部機構での競合の扱いなど）は、投入後の計画工程で決める。
後者は達成する状態と第三者が判定できる検収条件だけを本文に書く（成立を確かめていない細部を確定した原稿で、投入前レビューが往復した）。

解決する事象の実在と技術的な主張は、実装コード、実行結果、公式の一次資料で裏付け、採否の根拠として本文に書く。
ユーザーの発話や委譲元の依頼文にある過去の変更、出来事、既存の状態への言及も技術的な主張として扱い、差分、履歴、現物と合わなければ観測した結果を前提にする。
ユーザーにしか決められない選好・要件・判断は逐語引用と由来の定めで扱い、裏付けの調査は採否、実現方式、完成条件に関わる主張に限る。
値や外から観測できる動作を変える要求は、エンドユーザーの呼び出し手段から、値の生成元、設定元（デフォルト値やプリセット）、保持先、直接の消費先、最終的に観測される結果までを実装コードでたどり、`## 反映内容と反映先`と`## 完成条件`へ対応付ける。
保存前の読み直しで対象集合と除外を確かめる時は、この集合を使う。
設定やオプションの例は、ユーザーが残す機能と止める機能を先に分け、対象の入口ごとに使用版・設定層・実際に変わる挙動を対応付けてから採否を決める。
名称やヘルプでの掲載ではなく、空設定が残す値、対話と非対話、CLIとSDK、管理ポリシー専用など、結果を変える境界を一次仕様・実装・必要な最小観測で確かめる。
同じ目的の対象を除く前に既存機能と両立する構成を探し、調査しても許容される機能喪失が決まらなければ、失う操作を示して確認する。

観測された事象を契機とする要求では、採用を確定する前に、対策が直接の原因と主な害に作用するかを確かめる。
原因が推測だけに依拠していないことは`agent-basics:bugfix/references/causes.md`「観測と推測の区別」で、案の比べ方は`agent-basics:bugfix`の問い3（処置）で確かめる。
再発の主な原因か害の発生源が残る案は、残す正当な理由を確定してから採る。
害の発生源を定める既存の方針や仕様があることは、それだけでは残す理由に数えず、本書「方針と判断の記録との比較」で変更案として扱う。

完成条件を固定する前に、起点の資料の目的と、エージェントが選んだ中間の手段（安全策、検収用のログ、例外処理、フォールバックなど）を分ける。
新しい機構を作らずに既存の操作で利用側に必要な結果が得られるかを、`agent-basics:writing-standards/references/design-heuristics.md`「自作機構の兆候と自問」で比べて結論を本文に書く。
新しい処理の追加は、利用側に必要な結果から、既存機構の流用、統合、追加しない案、新設を同じ資料で比べる。

類似の見直しや再発防止として新設する要素と、完成条件で必須にする観測手段・比較・検収・工程は、明示の要件、規範上の制約、観測済みの欠陥のどれに応じて必要かを要素ごとに示す。
処理しない・延期するといった保護の条件と、期待結果・完成条件・反映内容に書いた省略・拒否・保存しない分岐も同じ根拠に対応付け、処置自身の失敗の最悪の結果を元の問題の最大の影響と比べる。
これらの根拠は`agent-toolkit:atk-mode/references/awi-body.md`「調査結果と判断根拠」に従って書く。
可能性があることや安全側に倒れることは、それだけでは採用の理由に数えない。
検収の準備・実行・再試行の負担と期待する品質の改善を比べ、求めた結果を判定できる負担の少ない観測方法を選ぶ。
反復して実行される処理は、実行ごとのモデル呼び出し、読み込み、照会、待機、再試行のコストも比べ、後続の担当が方式を選べるよう結論と根拠を本文に書く。

効率化が目的のAWIでは、通常の利用場面とユーザーの目的から全体の結果と保つ品質を定め、集約・共有・再利用の便益を保つ条件へ対応付ける。
主対象で減る仕事と他の対象で増える仕事、故障時に続ける手段（無効化、単純な動作への復帰）の有無を比べ、追加・拡張の案は撤去・単純化・現状維持の案と同じ通常の構成で比べる。
コストには起動、共通の読み込み、中継、結果の検収、並行の待ち、障害による停止と調査・修正の所要時間を含め、同じ仕組みの修正回数と関連WIを変更履歴とキューで確かめ、続ける手段を置くかを含む結論を採否の理由と成立性の証拠へ残す。
専用の計測と運用上成り立たない入力の網羅は一律には加えず、効率化の実測と不採用の境界は`agent-toolkit:atk-mode/references/awi-body-completion.md`「完成条件」に従う。

目的や要件に関する既存の方針と衝突する案は、本書「方針と判断の記録との比較」に従って方針を変える案として確認へ回す。
手段に関する方針と衝突する要求は、QCDが明らかに良くなる場合に限り方針からの逸脱として採る（原則2、`agent-basics:writing-standards/references/quality-principles-qcd.md`）。
方針との整合や変更の認可が確定しない間は、確認の手順で扱う。

## 対象集合の仕分け

対象集合の見直し、存廃、要否、仕分けを求める要求（単一の対象だけを変える依頼を除く）は、判定する時点を元の要求から特定する。
投入前の仕分けを求める要求と、起草の段階で調べられる集合は、登録から外す項目と連動する対（規範とテスト、設定と状態など）も現物で確かめ、各対象の採否と根拠を本文で確定する（1件1行の表が読みやすい）。
処理の時点で処理担当が集合を判定する形は、元の要求が処理時点の判定を求める場合（処理時に内容が変わる集合への恒常的な規則など）に限り、分類の軸、判定の主体と時点、保つ条件、外から確かめられる完成条件、対象を列挙する手段と全対象への到達を起草時に確定する。
処理側は各対象を変える前に採否と根拠を確定し、元の対象集合と変更結果を全件対応付けて検収する。
仕分け、要約、統合の後も、個別の採否、変更箇所、保つ条件、根拠が元の調査結果と対応付く書き方にする。

## 実現方式の成立

実現方式が前提にする公開契約、実行環境の機能、対象の実装が実在することを現物で確かめ、隣の既存機構、共通の契約、類似の実装と整合するかを実装コードを読んで判定する。
これは`agent-basics:writing-standards/references/quality-principles-subtraction.md`「変更の範囲」の既存例との照合を、実現方式へ当てる観点である。
特定の値の成立、1つのパスでの成功、設定操作ができることは、採る案全体の成立の一部にすぎない。
案を確定する時と原稿を返す前に、次の観点も確かめる。

- 一連の処理全体の成立: `agent-basics:bugfix/references/similar-review.md`「探す対象を決める」に従い、対策が使う資源と時間の総量、同じ資源を使う既存の処理、上限が作用する単位を、処理全体の制約と比べる。
- 適用と除外の条件: 原因が作用する条件を生成側と利用側の現物で確かめ、除外と適用の範囲を、機構の前提が成り立つ範囲とそろえる。
  工程を省くか判断権を移す場合は、判定に使った入力・前提・見解が後で変わる場面まで扱う。
  変化に気付く担当、旧判定を更新する担当、見解の対立や証拠不足から通常工程へ戻るか終了する条件を、反映内容と成立性の根拠でそろえる。
  更新後の再変更と、旧判定の前提を示す入力が欠けた場合も、同じ責任分担と移行条件で処理できることを確かめる。
- 設定の再現性: 設定の定義元と、配備・再作成・稼働環境への反映の手順を比べ、手作業の変更よりリポジトリで管理する定義の修正を先に検討する。
- 対象リポジトリの規範との整合: 変更の順序、段階の間の移行条件、完了の判定など方式を制約する規約を、`agent-toolkit:atk-mode/references/awi-body.md`「配置規約と導入目的の調査」に従って方式の決定前に読み、案と比べる。
- エンドユーザーを導く経路: 方式がエンドユーザーの観測する挙動を制限・拒否・除去する場合は、`agent-basics:writing-standards/references/design-heuristics.md`「問題と手段の比例性」の「エンドユーザー側からの逆引き」を当てる。

整合を確かめられない案は投入を止めて調査を続け、自力で取得できない資料とユーザーの判断が必要な事項だけを確認へ回す。
成果物を新設・分割・移設・統合する方式は、`agent-basics:writing-standards/references/design-heuristics.md`「設計品質の劣化確認」で評価し、採否を左右する結論と再取得先を本文に書く。
観点ごとの確認の過程と比べた対象は成立性の証拠に残し、後続の担当が成立性を判断して着手できるよう、結論と根拠の再取得先を本文に書く。

## 方針と判断の記録との比較

比べる目的は、過去の判断でユーザーが重視した結果とトレードオフ（例: コストと提供時期の悪化を嫌って一律の必須をやめた）を、今回の案の評価へ引き継ぐことである。
認可の成否の確認はその一部であり、認可が成り立った後も比較を続け、案を示す時はその案が過去に重視された結果へ与える影響を説明に含める。
従う対象にする過去の判断は、主体がユーザーである根拠（発話、回答、`AGENTS.md`などが案内するユーザーの方針・判断の記録の要旨）があるものに限る。
過去のWIや設計記録にあるエージェントの技術判断は、今回の依頼と比べて選び直し、却下された案を今回取り込む場合は却下の理由を示してから取り込む。

変更する仕組みの導入目的と由来は、変更履歴とユーザーの方針・判断の記録から調べ、記録が索引と個別のファイルに分かれていれば個別のファイルの節と比べる。
検索語には、対象の名前に加え、案が導入・維持しようとする仕組みや概念（フォールバック、API、状態管理など）も含める。
変更する値、設定キー、配布元・配布先のパスを名指しする規範（配布元の原本を含む）も、その文字列で対象リポジトリの全ての追跡ファイル（隠しディレクトリを含む）から固定文字列で探す（`agent-basics:search`）。
この比較は変更する対象ごとに行う。

過去の目的や要件の記録と衝突する変更は、ユーザーが確定した判断の変更として扱う。
過去の判断で比べた目的と得失、採った結果、却下した案を、現在の逐語の要求が示す変更の意向と比べる。
対象の範囲に含まれることや改善の目的が合うことは、それだけでは判断の変更の認可に数えない。
過去に比べ済みの目的が再び示されただけなら、[確定した判断の範囲と前提](../playbooks/confirmation.md#認可を要する操作)を確かめ、引き続き有効な採用結果と却下を保つ。
現在の要求が判断を変える意向を明らかに示している場合は、過去の記録を名指ししていなくても、その要求と成り立った認可に従って進める。
目的と得られる結果を損なわずに技術的な実現手段を選ぶことは、通常の技術判断として自分で行う。
既存の目的を別の手段で保てると判断して値や機構を置き換える場合は、目的が保たれることを観測できる完成条件を置くか、観測の結果を本文に示す。
置き換えた手段の設定値やテストの一致は、目的の保持を判定する根拠から除く。
条件付きで示された変更（「〜が改善されるなら減らす余地は無いか」など）は、条件の成立を観測できてから確定する。
これらを当てた後も残る事項（変更の意向が示されていない依頼で目的側の判断を変える必要、未合意の選好や認可、硬い制約やホストの規約と両立しない場合）だけを未確定事項にする。
過去の記録が名指しされていないことは、それだけでは確認の理由に数えない。

既存の保護（エラーの検出、確認の表示、制限、フォールバックなど）を保つか、撤廃して代替の機構を足すかは、現在の要件と観測に基づく必要性（守る事象の観測頻度と最大の影響）で比べる。
エージェントが自分で選んだ保護は受入条件と分け、代替の補償の機構は必要性が示された場合だけ対案のコストに数える。
ユーザーが明示した保護の要件、目的側の判断、硬い制約は保つ。
現在の明示の要求が仕組みの変更を求め、ユーザー固有の判断事項が残らない場合は、要求どおりに変える。
由来が不明なことと、既存の保護が無くなることそれ自体は、再確認の理由から除く。
過去のWI（状態は問わない）を記録として比べる場合は、`agent-toolkit:atk-mode/references/origin-and-approval.md`「ユーザー専用の記入欄と是正要求」に従い、ユーザーのコメントと回答を含めて確定した有効な要求と比べる。

確認の質問やUWIの選択肢を作る時は、過去の記録や規範に反したままの案を除くか、過去の判断を変える案であることと記録の所在を説明に書く。
比較の結論と再取得先は本文に、検索の範囲、検索語、記録ごとの比較結果は成立性の証拠に残す。
確認の質問とUWIには、ユーザーの選択を左右する結論と記録の所在を書く。
