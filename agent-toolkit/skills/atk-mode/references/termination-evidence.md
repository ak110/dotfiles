# 終了工程の判断の記録

作業を終える担当が終了の判断を記録し、ユーザーが報告の無い終了や未達を完了と誤認しないようにするための手順である。
Stop hookが完了報告の起動不足を示した時の対応と、完了報告の省略、作業の中止・置換、待機、技術的不成立の判断を記録する手順を定める。
プロジェクト規範が完了報告を省くと定める場合は、`agent-toolkit:atk-mode/playbooks/report-completion.md`を読まずに本書を直接読む。
統括から明示的に委譲されたリポジトリ担当が報告・送達・ホスト終了の担当外であることは役割文書で判断し、その除外のために本書を読む必要は無い（`omit-completion`とも別である）。
Stop hookの判定の仕組みと設計の経緯は、開発リポジトリの`docs/development/design-hooks-termination-evidence.md`にある。

Stop hookが起動不足を示した時、作業を完了して終えるなら完了報告の手順書を全文読み（Claude Codeでは`/atk-mode report-completion`の起動でもよい）、残る工程を進める。
この通知は手順書の読み取りか起動で解消し、報告本文の文面の修正や全文の再送は解消の手段の外にある。

## プロジェクト規範による省略

メインは、`agent-toolkit/skills/atk-mode/references/conduct.md`「方針が衝突する場合の優先順位」に基づいて、その作業で完了報告を省くかを判断する。
省く場合は、次のJSONを一時領域へ保存し、`atk run-script termination-evidence -- --decision-file <判断JSONの絶対パス>`で記録してから通常の報告をする。

```json
{
  "session_id": "現在の会話の識別子",
  "action": "omit-completion",
  "work_id": "観測済み作業の識別子",
  "reason": "規範の意味と優先順位から省略する理由",
  "policy_file": "/対象リポジトリ/CLAUDE.md",
  "target_repo": "/対象リポジトリ"
}
```

- 各識別子はStop hookの通知から取る。
  Claude Codeでは`atk run-script termination-evidence -- --context`でも取れる（取れる項目は次節）。
- 省略は人間の入力を根拠とするため、取得結果の`input_id`に値がある会話でだけ記録できる。
  省略した`input_id`は、現在の会話の直近の人間入力へ対応付ける。
- `policy_file`は対象リポジトリで適用するプロジェクト規範の絶対パス、`target_repo`は観測した成果作業が属するGitリポジトリのルートの絶対パスとする。
  複数のリポジトリにまたがる成果作業は、リポジトリごとに区切って判断する。
- 記録処理は`policy_file`から規範の全文を読んで保存し、成果作業の対象と所在、現在のメイン、会話、人間入力の対応を確かめる。
  `quote`を指定した場合は規範の全文との一致を確かめる。
  規範の解釈と優先順位の適用はメインが判断する。
- 規範が変わった、新しい判断をする、新しい人間入力の後に成果作業が生じた場合は、過去の省略を流用せず判断し直す。
- 省略は指定した作業の起動不足にだけ作用する。
  別の作業の起動不足と、process-loopで`atk agents-exit-session`を実行する義務は残る。
- process-wi all-reposのリポジトリ担当は成果と残工程を統括へ返し、統括が報告を集約してホストを終了する。
- 振り返りは別担当の非同期処理で、省略の判断と通常の終了条件の対象外である。
  手動の振り返りを依頼された場合は、その独立した要求を保つ。

## 中止・置換・待機・技術的不成立

作業の中止や別作業への置換を指示された場合、確認への回答や起動した委譲先の結果を待つ場合、技術的に続けられない場合は、`atk run-script termination-evidence -- --decision-file <判断JSONの絶対パス>`でその判断を記録する。

- 判断JSONには`session_id`、`action`（`cancel`、`replace`、`start`、`resume`、`wait`、`blocked`のいずれか）、対象の`work_id`、`reason`を入れる。
- 根拠の識別子は、中止・置換・開始・再開ではユーザーの元の入力の`input_id`、確認待ちでは投入した未回答UWIの`uwi_file`、委譲先の待機では`target_session_id`、技術的不成立では失敗した呼び出しの`call_id`とする。
- `wait`は実際に続いている待機がある場合、`blocked`は観測した失敗で技術的に続けられない場合に記録する。
- `session_id`、`work_id`、直近のユーザー入力の`input_id`は、通知から取る。
  Claude Codeでは`atk run-script termination-evidence -- --context`でも取れる。
  取得結果は人間入力の有無によらず`session_id`と現在の`work_id`を含み、`input_id`と原文の`quote`は人間入力を観測した場合だけ値を持つ（無ければ`null`）。
- 委譲先の待機と技術的不成立は実行結果を根拠とするため、人間入力の無い自動起動の会話でも記録できる。
  中止・置換・開始・再開は人間の元の入力を根拠とするため、`input_id`に値がある場合だけ記録できる。
- 記録処理は各識別子から本文や応答を読み、由来と対象を確かめる。
  `quote`は省略でき、指定した場合は取得した実体の全文との一致を確かめる。
- 記録は指定した作業にだけ作用し、ユーザーの割り込みと関係しない他の作業の起動不足は残る。
- Stop hookの継続入力や注記はユーザーの元の入力として受理されず、完了を自己申告する記録の操作は無い。
- 証拠を取得できない場合、Stop hookは遮断せず判定不能を記録する。
- 報告用UWIの保存検収は、`agent-toolkit:atk-mode/playbooks/report-completion.md`「工程」の手順6に従う。

ホストの猶予通知で続行が許されている間は、残りの工程を進める。
ホストが再開を禁じた場合は、現在の状況と再開に必要な操作を`agent-toolkit:atk-mode/playbooks/confirmation.md`に沿ってユーザーへ伝える。

## 受理する証拠

完了報告の起動証拠として、Stop hookは次のものだけを受理する。

- Claude Code: `Skill`ツールでスキル`atk-mode`を引数の先頭語`report-completion`で起動して成功したもの、または`skills/atk-mode/playbooks/report-completion.md`を`Read`ツールで読んで現在の版の全文を受け取ったもの。
  メインの`Bash`では、配布中のそのファイルをリダイレクトしない本文表示か全行を覆う`sed -n`で読み、出力に全文があるものも受理する。
- CodexとAntigravity: 出力をリダイレクトしない本文表示か、1行目から始まる`sed -n`の行範囲の表示で`skills/atk-mode/playbooks/report-completion.md`を読み、結果が現在の版の全文を含むもの。
- パスの文字列だけの言及、起動の予告、失敗した読み取りや空の読み取り、途中で終わる範囲の読み取り、ホストが省略した結果、旧版の読み取り、検索の一致行、他の作業や委譲先の起動は受理しない。
- 起動証拠として有効なのは、最後の会話圧縮の後にメインが得たもので、手順書の版が現在の版と同じものに限る。
  この条件を満たす起動証拠は、新しい人間の入力の後の作業にも使う。

判断の記録が受理する証拠は次のとおりである。

- 技術的不成立の記録（`blocked`）: 失敗応答を返したツール呼び出しだけを受理する。
  別の`call_id`で再試行した呼び出しの結果は、元の失敗の証拠から外れる。
- `wait`: 所有する委譲先への待機が続いている場合だけを受理する。
  待機が終わっている場合は、`atk agents wait`で待機を始めるか、回収後の残工程へ戻る。

## 技術的不成立の判定

利用上限の猶予通知と、ホストによるバックグラウンドコマンドの停止は、技術的不成立に含めない。
猶予通知を受けた場合は、`agent-toolkit:atk-mode/references/usage-limit.md`に従って同じ工程を続ける。
ホストが再開を禁じた処理は、再開してよいかをユーザーへ確かめる。
確認の手段は、協調モードでは`AskUserQuestion`、自律モードではUWIの投入とし、UWIは`wait`の`uwi_file`で記録する。
ホストの通知による停止は、終了理由の記録の対象外である。

## 終了方法の分岐

Stop hookが起動不足を示した時は、終了の理由に応じて次の操作を選ぶ。

| 終了の理由 | 操作 | 判定条件 |
| --- | --- | --- |
| 起動が必要な作業を完了して終える | `agent-toolkit:atk-mode/playbooks/report-completion.md`を全文読み（Claude Codeでは`/atk-mode report-completion`の起動でもよい）、その工程の残り（作業完了報告、最終報告、呼び出し元が定める公開工程）へ進む | 適用するプロジェクト規範が起動を禁じていない |
| プロジェクト規範が起動を省く | 本書「プロジェクト規範による省略」で`omit-completion`を記録し、通常の報告を届ける | 規範の意味と優先順位から省略できる。`work_id`を特定できない作業は省略を記録できないので、手順書を読んで工程を進める。規範が起動を禁じる場合は、その旨をユーザーへ報告する |
| ユーザーが中止・置換を指示した | `cancel`か`replace`を記録する | 元の人間入力の`input_id`がある |
| 確認の回答や委譲先の結果を待つ | `wait`を記録する | 確認待ちは未回答UWIの`uwi_file`、委譲先の待機は`target_session_id`を指定する |
| 技術的に続けられない | `blocked`を記録する | 失敗した呼び出しの`call_id`を指定する。判定は本書「技術的不成立の判定」に従う |

記録は、元の証拠と対象の`work_id`を判断JSONに入れ、`atk run-script termination-evidence -- --decision-file <判断JSONの絶対パス>`へ渡して行う。
