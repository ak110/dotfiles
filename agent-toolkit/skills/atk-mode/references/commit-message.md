# コミットメッセージ

commitを作るエージェントが、履歴を読むユーザーと開発者が件名から変更の対象と影響を判断できるメッセージを書く。

コミットメッセージの件名、形式、type、description、本文、`Co-Authored-By:`の決まりである。
コミットメッセージの1行目を「件名」と呼ぶ。
計画ファイルやPRの説明へ書くコミットメッセージの案にも同じ決まりを当てる。

## 形式と書き方

プロジェクトに固有の方針が無ければ、Conventional Commitsの形式で書く。
プロジェクトが固定の文言の体系（カテゴリ名や決まった件名の型など）を定めていれば、それに従う。
方針は`CLAUDE.md`、`AGENTS.md`、`.claude/rules/`、コミットテンプレート、lintの設定など、明文の資料から確かめる。
明文に無い事項は、同種の複数のcommitで一貫して観測でき、明文の方針と矛盾しない形式だけを慣例として採る。
明文の方針と履歴が矛盾する場合は、`agent-basics:bugfix/SKILL.md`「バグ対応」に従う。

- 形式: `<type>[(<scope>)]: <description>`とし、破壊的変更には`!`を付ける。
  本文かtrailerを書く場合は、件名の後に空行を1行入れる。
- typeと`!`: 成果物を使う主体（配布先のエンドユーザー、開発者、エージェント）の振る舞いへの影響で選ぶ。
  機能の追加、修正、性能の改善はそれぞれ`feat`、`fix`、`perf`とする。
  使う主体の振る舞いに直接影響しない内部の変更は`chore`、`ci`、`refactor`、`docs`、`test`とする。
  lintやformatterの設定、CIの手順、依存パッケージの整理など、開発者向けの設定の変更には`!`を付けない。
  設定キーや環境変数の改名、統合、削除は`agent-basics:writing-standards/references/design-data-interfaces.md`「エンドユーザーデータの移行」に従う。
  移行処理が無いと使う主体のデータの消失、読み取りの失敗、起動の失敗のどれかが起きる場合に`!`を付ける。
- エージェント向け文書: 配布先のエージェントの判断と振る舞いを直接定めるため、本文中の判断の分岐の変更、規範の削除、機能的な規範の変更は`chore`にしない。
  振る舞いを変える場合は`fix`、変えない構造の整理は`refactor`とする。
- scope: 変更が1つのモジュールか特定の機能に閉じる場合だけ、短い名詞で書く（努力目標）。
- description: 日本語で、変更の対象と、変更の内容か問題の種類が一目で分かる簡潔な表現にする。
  複数の変更を含む場合は共通の目的にまとめて件名とし、変更が必要になった背景と個別の詳細は本文に書く。
  エンドユーザーが呼ぶAPIの名前、設定キー、画面で目にする識別子はそのまま書き、読み手が直接知りえない内部の識別子だけを必要に応じて平易な語へ言い換える。
- 本文: 書くかは任意とし、書く場合は`agent-basics:writing-standards/references/writing.md`「文章の共通規定」に従う。
- WIの識別子と内部の認可の情報は公開するメッセージに書かず、`agent-toolkit:atk-mode/references/commit-wi-records.md`の対応の記録へ残す。

## `Co-Authored-By:`

値は、ユーザーの明示の指示、明文のプロジェクトの方針、実行環境が示す帰属の指定の順に確かめ、最初に見つかった定義に従う。
空文字列の指定は、帰属の表示を明示的に無効にしたものとして扱う。
どの定義も無ければ`Co-Authored-By: <実行中のモデルの表示名> <noreply@<モデル提供元のドメイン>>`を付ける（Codexではドメインを`openai.com`とする）。
モデル名と推論量（effort）は、commitを実行するターンのホストの記録から実際に観測した値を使う。
モデルの設定値、エイリアス、起動時の候補一覧は起動用のパラメーターとして扱い、実際に観測できた場合だけtrailerを付ける。
trailerは最終のメッセージに1回だけ入れ、既存の異なるtrailerは保つ。

- Claude Code: 帰属の指定に含まれる`{model}`と`{effort}`は展開されずに渡るため、観測した値へ置き換えて書く。
  推論量は`printenv CLAUDE_EFFORT`で取得し、先頭を大文字にする。
  例は`Co-Authored-By: Claude Opus 5.5 / Medium <noreply@anthropic.com>`である。
- Claude CodeとCodex: 本書を読むと（シェルの読み取りとClaude Codeの`Read`）、PreToolUseの追加コンテキストとして、読み取り時点に観測したモデルと推論量の帰属行が渡る。
  観測できない場合は推測で補わず、commitを実行するターンのホストの記録を確かめる。
- 読み取り時点の値は後で変わりうるため、commitの直前にも今のモデルと推論量を確かめる。
  通知が示す帰属行に直してcommitをやり直す。

## 実行時の検査

本文が変わらないと分かる場合はPreToolUseで検査し、止まった場合は連結した前段も未実行である。
本文を組み立てる場合や既存のGit hookが整形する場合は、Gitの`commit-msg`で既存hookが成功した後の本文を検査する。
そこで遮断された場合は既に実行した前段を繰り返さず、commitだけをやり直す。
退避の競合を解消するため既存hookを外す認可がある時は、検査できるよう確定本文を`-m`か保存済みファイルの`-F`で渡す。
本文の確認では既定の`#`または`core.commentChar`で明示した記号に従ってコメント行を除く。
`--cleanup=verbatim`などでコメント行だけに残る文字列は検出しない。
`core.commentChar=auto`でGitが選んだ記号はhookに渡らないため、`#`で始まる行が実際の本文に残っても、その行だけの違反は検出できない。
Codexでは導入後に設定を読んだプロセスで開始・再開する。
稼働中のdaemonが旧設定を保持する場合は、安全に切り替えられる保守時間に導入手順に従ってから既存の会話を再開する。
