# 振り返りの一次選別

振り返りの担当が、ユーザーに影響する問題を原因分析へ漏らさず送り、影響の無い候補に分析の手間をかけないための基準である。
振り返りの分析で、候補と通読で見つけた問題を、原因分析へ送るものと除外するものに分ける基準を定める。
本書は`agent-toolkit:atk-mode/playbooks/review-session-analysis.md`の工程3で読み、送り先の「原因と対策」「規範の未適用と目的逸脱」は同書の節を指す。

## 一次選別

欠陥（契約の不成立）と、品質を保って費用や時間を減らす改善の機会を分ける。
通読で見つけた問題は同じ事象を指す候補とまとめ、対応する候補が無い問題も原因分析へ送る。
回復済みの事象も根本原因を分析し、回復の事実と要した操作を別に記録する（`agent-basics:writing-standards/references/quality-principles-facts.md`「報告の選別と判断記録」）。
欠陥と確認した候補は、発生が単発か回復済みかによらず、処置、被覆、対策か調査の判定へ送る。
欠陥でないと確かめて見送る候補は、根拠を報告の「対策を見送った問題」へ書く。
探索の深さと再発防止の要否は`agent-basics:bugfix/references/prevention.md`「害と費用の比べ方」で決める。

- 必要な裏付けの調査、出力の上限に合わせた分割の読み取り、起動時のスキル展開、変更後の再確認、過去資料の参照を誤りとするのは、契約の不成立を観測した時に限る。
- 規範が求める工程の量が過大かは、同書「規範の未適用と目的逸脱」で判定する。
- 既存の規範が適用されなかった問題は、条文があることで除外せず、確証の無い候補も分析へ送る。
- 過去の振り返りやキューの処理で不採用と確定した案は、新しい観測か要件の変更がある時に限って評価し直す。
- 資格情報の所在の報告は、発話も`気付いた改善点:`の行も`credential-report`で判定する（区分の定義は`agent-toolkit:atk-mode/playbooks/user-utterance.md`「ユーザー介入と確認の判定」）。

候補の種類ごとに次を確かめる。

- 失敗したコマンドとツール: 入力誤りや契約の不成立を確認した失敗は、単発や再実行成功でも、終了コード、コマンド、診断から原因を調べる。
  反復は実際のログで確かめ、発生したセッションの数と条件を残す。
  正常な入力検査や意図した試行の失敗は誤りとせず、根拠を残す。
  同じ検査コマンドが別々の呼び出しで同じ違反（パス・WI名・数値を除いた診断の1行）を2回以上示した場合は、
  失敗を誤りに数えず、記載要求を見直す候補として[規範の未適用と目的逸脱](../playbooks/review-session-analysis.md#規範の未適用と目的逸脱)へ渡す。
  候補、`bundle/review-index.jsonl`の`single-failure`、通読で取得した証拠を使い、反復の手掛かりがあるが件数を判断できない場合だけ、
  `atk run-script session-review-evidence -- <対象の指定> --tool-calls --failure-fixed-string <違反の行の固定部分>`で照会する。
  対象の記録と検査コマンドを照合し、同じ呼び出し内の重複は1回に数える。
  見直しでは導入の目的と、値の自動導出・既定値・引き継ぎで省けるかを、検査や診断の追加より先に比べる。
- 成功した操作: 保存済みの値を長く再入力した手掛かりがあれば、実際のツール引数と前の入力を照合し、不要な転記を費用の比較へ送る。
  選定の追加の`除外候補`などで、画面に長い差分が出ただけ、必要な差分を1回入力しただけ、実入力の証拠が無い場合は同じ費用に数えない。
- 委譲の返却: 正常に完了しただけの返却は詳細の照会を省き、実施の方法と費用を費用の比較へ送る。
  それ以外は本文まで読み、`続行できない理由:`の行を持つ返却（`escalation`）は、担当の内で補える不足（出力の切り詰めなど）を理由に続行不能を返した判断と、続行不能の原因を評価する。
- hook通知: 通知ごとに、操作の目的、`--detail`で取った元の記録、通知に従った後の結果を対応付け、出力自体の不良、呼び出し手順への規範の未適用、案内と操作の不一致を分ける。
  `hook通知への対応:` の行があれば、その対象・結果・理由を通知に対応付ける。
  行が無いことによる未処置の候補と処置率の母集団は、`conduct.md`「方針が衝突する場合の優先順位」の処置を求める通知に限る。
  後続の操作から判断した結果とは区別する。
  誤判定として継続した記録は、誤判定、判断の誤り、正常な支援に分ける。
  warn通知の後に案内どおりの対応を取らなかった事象と、件数が多いか処置の割合が低い通知の種類（`atk-auto`の`source`ごとに`session-review-evidence`の出力から数える）は、同書「原因と対策」へ送る。
  未取得資料の読み込み案内では、案内を受けた主体自身が、対象操作の結果を使う前に資料を取得しなかった事象も含め、読み込みの案内（読込表の条件、スキルのdescription、資料の配置）、警告文、手順の簡素化を比べる。
  発生源ごとに`agent-basics:writing-standards/references/claude-hooks-block-warn.md`で、事前に防ぐ型か遮断後に対処する型かを決める。
  遮断後に対処する型の発火は想定どおりとし、1回の対処で解消しない、同じ呼び出しで反復した、頻度で費用の比較が変わる場合に限り、行動への対策と機構の負担を比べる。
  事前に防ぐ型には、規範の改訂、判定条件の見直し、hookの撤去、遮断後に対処する型への移行から1件以上の案を対応付け、現状維持ならその発火が不正な操作を止めた根拠を書く。
  読み込みの案内をhookの拒否へ変える案と、規範を読まないと書けない引数を足す案は、過去の拒否の運用で誤判定とコンテキストの無駄が大きかったため候補から外す。
  事前の確認の工程を足す案は、操作ごとに増える呼び出しの回数を費用として書く。
- 権限拒否: `agent-toolkit:atk-mode/playbooks/permission-denial.md`「偽陽性と判断できる拒否への対応」の適用条件を満たしたか、満たしたなら適用されたかを、委譲先の拒否も含めて委譲元の記録で判定する。
  条件を満たしたのに適用されなかった拒否は、作業の進行への影響によらず同書「原因と対策」へ送る。
  許可ルールを変える案は、拒否の文面と分類名を添えて`agent-toolkit:atk-mode/references/auto-mode-rule-addition.md`の手順へ送る。
- 手順書の作業を一時スクリプトで代行した箇所: 将来も再実行される手順（資格情報の更新、設定の再登録、別環境の構築、定期の運用など）なら、スクリプトを手順を所有するリポジトリのスクリプトの置き場所へ移して手順書から呼ぶ対策を、そのリポジトリを`target_repo`とする通常AWIへまとめる。
  1回限りの作業と、同じセッションで是正済みのものは対象から外す。
- その場のコードによる加工（`adhoc-processing`、通読で見つけた後加工、同じ目的のコマンドの反復）: 呼び出しごとに、どの出力から何を取ったかを特定する。
  同じセッションで同じ目的の加工が2回以上あれば反復とし、規範の手順が毎回求める工程のための加工と、`agent-toolkit`のコマンドの出力形式の制約で必要になった加工は1回でも反復とする。
  反復する加工は、加工を不要にする案（`agent-basics:bugfix/references/premises.md`「外部の変化と加工の反復」）と比べるために同書「原因と対策」へ送る。
  反復しない調査でも欠陥を観測していれば同じ分析へ送る。
  欠陥でない場合だけ、目的と根拠を見送りに書く。
- `気付いた改善点:`の行: その場の原因と影響の調査と処置を確かめて再利用し、未調査、変更、不一致の部分だけを補って同書「原因と対策」へ送る。
  その場でユーザーへ伝えた行も対象に含める。
- `definition-body-read`と`definition-read-unresolved`: 本書「定義本文の読込の判定」で分類する。

### ユーザー介入の判定規則

介入、WIの記入欄の是正、ユーザー確認の必須性、除外の区分は、元の発話と構造化した確認の全項目を材料に、`agent-toolkit:atk-mode/playbooks/user-utterance.md`「ユーザー介入と確認の判定」で判定する。
同じ種類の承認を繰り返し求めた記録は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「繰り返す操作の認可」に照らし、既存の認可の探索の欠落、単発の許可だけの提示、恒久の認可の保存の欠落、次回の適用の欠落を分けて判定する。
単発の回答の範囲を守った場合も、反復する回答の負担は分析の対象に残す。
人間の発話と生成された本文の判別は、`agent-toolkit/agent_toolkit/_common/runtime_inserted.py`と`session-review-evidence --user-events`の抽出条件に従う。

## 定義本文の読込の判定

`definition-body-read`は、明示的な読み取りか、静的に読み取りと対象を対応付けた操作の候補である。
`definition-read-unresolved`は、取得の有無を静的に決められない操作の候補で、`calls`と個別の証拠の`definition_reads`に元の記録位置、入力、結果の位置、操作ごとの理由を持つ。
準備は`definition-body-read`の各読み取りを`launch_check`で判定し、同じ記録の後で同じ役割を起動した読み取りを`suspected`、それ以外を`cleared`とする。
メインが分類するのは、`suspected`の読み取りと`definition-read-unresolved`の全発生位置であり、`cleared`は判定の理由（`reason`）を確かめれば十分である。

Codexの`functions.exec`の記録では、`calls`の要素の`tool`の末尾の名前が`exec`なら、その要素の`line`・`result_line`は外側のセル（`functions.exec`へ渡したJavaScriptの1回の実行）の位置である。
現在のCodexの記録ではセルへの帰属を確認できないため、内側の実行は`tool`が`CommandExecution`の独立した要素になる。
外側セルの読み取り候補は各呼び出しの記録済み入力から判定し、静的に決められない操作を未確定として残す。
旧版の`execution_line`と`execution_result_line`は内側の実行の位置であり、同じターンにあることや記録順だけでセルへの帰属を確定しない。

取得の有無、目的、結果の成否は別々に判定する。
編集対象の本文、JSONの参照、履歴の検索条件、他の操作の引数、記録に含まれるコードに定義名があるだけでは、取得の根拠にしない。
根拠は、呼び出した主体と対象、元の記録の本文と実行結果、前後の起動・編集・返却の文脈に求め、近くの編集や役割名の一致だけで目的を決めない。
取得を確かめた位置は、起動準備、編集作業、自身が受領した定義、返却後の検収、目的不明のどれかに分ける。
編集作業、自身が受領した定義、返却後の検収は、根拠を添えて`definition-read-context`で判定済みとする。
起動準備の読み込みは`agent-toolkit:atk-mode/playbooks/delegation.md`「送信」の禁止事項（起動の準備で役割文書の本文を読むこと）への違反であり、処理の成功、単発の発生、費用の多寡によらず、原因、対策、対策の保存先を対応付ける。
分類の証拠が足りない位置は報告の`未確定`に残す。
違反を確定した箇所で対策が未確定なら、観測と問いを保って調査の要求に進む。
