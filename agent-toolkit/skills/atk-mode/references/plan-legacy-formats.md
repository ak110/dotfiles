# 旧形式の計画の読み方

保存済みの旧形式の計画を読む時の判別と、読み取りで受け付ける節、表の列名、IDを定める。
対象は、表付き形式、8節形式（`## 要件・外部仕様`などの固定8節を持つ1ファイルの形式）、旧単一ファイル形式（対応する`<stem>.detail.md`が無い9節の形式）、旧二ファイル形式（`<stem>.detail.md`がある形式）である。
旧形式は既存の計画の読み取りにだけ使い、新しい計画は全て`agent-toolkit:atk-mode/references/plan-format.md`の現行の形式（frontmatterとAWIと同じ節だけ）で作る。
読み取りで受け付ける値は`agent_toolkit/_plan/structure/constants.py`の読み取り互換用の定数にあり、`plan-check`は旧形式を処理したうえで現行の形式への移行を促す警告を出す。

既存の計画の旧表記は、後方互換のためそのまま受け付ける。
計画メタ情報の`実装詳細`行、`- バグ調査ファイル:`で始まる参照行、`~/.claude/plans`（`LEGACY_PORTABLE_ROOT`）への参照と旧絶対パスが対象である。
`$(atk config get private_notes)/`で始まる付属ファイルの参照と、`<計画stem>.tsv`形式のレビュー指摘管理表なども受け付ける。
既存の計画のID、系統名、表の内容は保存された値のまま保つ。

## 旧形式の判別

対応する`<stem>.detail.md`があれば旧二ファイル形式とする。
無い場合、`## 要件・外部仕様`と`## 恒久化・リファクタリング`の両方を持てば8節形式とする。
frontmatterを持ち計画メタ情報を持たなければ現行の形式とする。
`## 反映内容と反映先`を持つか、計画メタ情報をH1直下に置いていれば表付き形式とし、どれでもなければ旧単一ファイル形式として検査する。

## 表付き形式

表付き形式は、2026年11月18日から本形式の廃止までに作った計画である。
H1と要約、`### 計画メタ情報`、`## 実施内容`、要求を書く節（現行の形式と同じ）、`## 検証`、`## 進捗ログ`の順に並ぶ。
保存済みの計画の読み取り、`plan-check`（`--reject-migration-warnings`なし）、`atk run-script plan-progress`による進捗ログの追記、対応commitの記録で受け付け、作成済みで実装中の計画はこの形式のまま完了できる。

| 表付き形式の節 | 現行の形式で書く場所 |
| --- | --- |
| `### 計画メタ情報`（起動経路、対象リポジトリ、関連WI、作業種別） | frontmatterの`launch_route`、`target_repo`、`related_wis`、`work_kind` |
| `## 実施内容`（`実施内容`・`由来`・`採否`・`根拠`の表） | `## 反映内容と反映先`と`## 調査結果と判断根拠` |
| `## 検証`（`変更範囲の検証`の1行表と訂正済み検証表） | 引き継ぎ記録の検証コマンド |
| `## 進捗ログ`（`日時`・`完了した工程`・`結果・特記事項`） | 引き継ぎ記録と、AWI本文の予測補正記録 |

表付き形式の計画で作業を続ける担当は、`## 検証`の`変更範囲の検証`行（訂正済み検証表があればその表）を検証コマンドとして読み、進捗を`## 進捗ログ`へ追記してよい。
`実施内容`表の採否は`移管`・`不採用`・`対象外`・`保留`・`充足済み`の値を、書かれたとおりに読む。

## 8節形式

8節形式は、要求を書く節を通常AWIの本文と共通にする前の形式である。
保存済みの計画の読み取り、進捗ログの追記、対応commitの記録と書き換えで受け付け、作成済みで実装中の計画はこの形式のまま完了できる。
検査は変更前と同じ結果を返して移行の警告を出さず、新しい計画は作れない。

固定のH2見出しは次の順で、`## 要件・外部仕様`の直後に任意の`## 設計・実装方針`を置ける。
現行の形式で同じ内容を書く場所を併記する。

| 8節形式の節 | 現行の形式で書く場所 |
| --- | --- |
| `## 概要`と`### 計画メタ情報` | H1直下の要約と`### 計画メタ情報` |
| `## 実施内容` | `## 実施内容` |
| `## 要件・外部仕様`（`### 受入シナリオ`を含む） | `## 反映内容と反映先`と`## 完成条件` |
| `## 設計・実装方針` | `## 調査結果と判断根拠` |
| `## 恒久化・リファクタリング`（`### 恒久化`、`### リファクタリング`） | 保存する変更と見直しは`## 反映内容と反映先`の項目、確認の結論は`## 調査結果と判断根拠` |
| `## 変更履歴`（`### ユーザー発言<連番>`） | ユーザーの発言は`## ユーザー指摘の逐語引用`。起草中の経緯は残さない |
| `## 検証` | `## 検証` |
| `## 公開工程` | 固有の公開後の操作がある場合だけ`## 反映内容と反映先`の項目 |
| `## 進捗ログ` | `## 進捗ログ` |
| 計画メタ情報の`計画ファイル（バグ）`行と`<stem>.bugs.md` | 計画本体の`## 原因分析` |

`### 受入シナリオ`は`シナリオ`、`由来`、`消費主体と入口`、`利用目的と後続行動`、`操作`、`期待結果`、`テスト`の7列表、`### 恒久化`は`知見`、`出所`、`反映先`、`根拠`の4列表、`### リファクタリング`は`対象`、`現状の問題`、`対応`の3列表である。
`<stem>.bugs.md`はH1とバグ単位ごとのH3だけを持ち、バグ単位ごとに原因分析の記録を置く。

## 旧単一ファイル形式と旧二ファイル形式

旧単一ファイル形式の固定H2見出しは、`## 概要`、`## 実施内容`、`## 提示素材`、`## 変更履歴`、`## バグ調査結果`、`## 恒久化・リファクタリング内容`、`## 実装資料`、`## 完了条件`、`## 進捗ログ`の順に並ぶ。
`## バグ調査結果`は作業種別がバグ対応の時だけ置かれる。
`## 概要`から`## 変更履歴`までは人間向けの固定領域、`## 変更履歴`の直後から`## 進捗ログ`の直前までは実装者向けの領域として読む。

旧二ファイル形式のメインファイルが受け付けるH2見出しには、次の2つの系統がある。

1. `## 概要`、`## 実施内容`、`## エージェント提案詳細`、`## 提示素材`、`## 変更履歴（計画時）`、`## 検証区分`、`## 終端工程`、`## 進捗ログ（実行時）`
2. `## 概要`、`## 実施内容`、`## 提示素材`、`## 変更履歴`、`## 検証区分`、`## 終端工程`、`## 進捗ログ`

対応する`<stem>.detail.md`の固定H2見出しは、`## 恒久化・リファクタリング内容`、`## 実装資料`、`## 完了条件`の順に並ぶ。
計画メタ情報は`起動経路`、`対象リポジトリ`、`作業種別`、`ベースコミット`、`計画ファイル（詳細）`を持ち、`実装詳細`は`計画ファイル（詳細）`の旧名として受け付ける。
旧書式では、現行の`## 反映内容と反映先`と`## 完成条件`に書く内容を、`## 実装資料`のファイル群別の変更説明と`## 完了条件`へ読み替える。

## 読み取る表の列名

- `## 実施内容`: `実施内容`、`採否`、`ユーザー指示との関係`、`根拠`。
  さらに古い形式は`採否`列を持たない3列表である
- `## 提示素材`の素材表: `素材ID`、`種別`、`キューID`、`投入元`、`引用範囲`
- `## 提示素材`の要求表: `要求ID`、`素材参照`、`実装に必要な要件`、`採否`、`採用範囲`、`除外範囲`、`根拠`
- `## 変更履歴（計画時）`か`## 変更履歴`: `ID`、`起点`、`指摘内容`、`採否・現在の結論`、`同期先`
- `## 検証区分`: `区分`、`検証コマンド`の2列で、`レーン内検証`、`統合後検証`の2行を持つ
- 8節形式の`## 検証`: `変更範囲の検証`の旧名`近接検証`の1行表と、`近接検証`・`全体検証`の旧2行表
- `### 実装単位`: `単位ID`、`目的`、`先行依存`、`統合順`、`近接検証`。
  さらに古い形式は`対象の実施内容`を加えた6列表である
- `### 合意済みの除外・保持`: `合意内容`、`対象と箇所`、`素材・要求参照`、`確認方法`
- `## 進捗ログ（実行時）`か`## 進捗ログ`: `日時`、`完了した工程`、`結果・特記事項`
- 8節形式の`### 受入シナリオ`: `利用目的と後続行動`列を持たない6列表。
  第3列が`利用者と入口`の形式と、最終列が改名前の名称の形式も含む。
  列の並びは`PLAN_LEGACY_ACCEPTANCE_TABLE_HEADERS`が定め、検査は表頭に対応する列数と空のセルの有無を確かめる

素材IDは`P-`で始まる形式、要求IDは`R-<素材ID>-<3桁連番>`、実装単位IDは`U-[0-9]{3}`の形式を受け付ける。
変更履歴のIDは、`R<正の整数>-<系統名>`の形式のほか、旧二ファイル形式の`C-`か`H-`の形式と旧系統名、旧単一ファイル形式の`C-<3桁連番>`の形式と`conformance`系統を受け付ける。
これらのIDは新しく採番せず、既存の値をそのまま保つ。

旧形式の`text`コードフェンスと`原文参照`列、原因分析表を持たない固定14行の旧調査表、本文の中に調査表を含む形式、統廃合の前の行構成を持つ調査表、6区分化の前の8行の調査表（`直接的原因`・`原因分析の根拠`の行を持つもの）も、読み取りの互換のためそのまま受け付ける。
