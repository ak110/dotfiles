# WI投入担当へ渡す入力

WI投入担当（役割`add-wi`）へ渡す入力の作り方と、入力`投入する要求`の欄を定める。
「起動前の前提」は委譲元が入力の値を確定する手順で、残りの節は欄の定義である（委譲元は書く時に、担当は読む時に使う）。
委譲元の推論や言い換えで担当の調査範囲と要求の対象を狭めないよう、確定した結論、原文、観測、問いを分けて書く。

## 起動前の前提

1. 未完了の既存WIを更新・修復する必要が生じた時点や、具体的な懸念が寄せられた時点では、認識合わせや調査より先に対象を保留する（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「保留と本文修正」）。
   保留の後は修正、検収、解除を他の作業より先に進め、付随型では委譲元が担当への割当、原稿の検収、保存の指示、保存結果の検収、解除をこの順で、専念型では作成主体が解除まで進める。
   状態が`processing`の項目は、変えたい内容を新規投入の要求として渡す。
2. `agent-toolkit:atk-mode/playbooks/wi-drafting.md`「起票目的別の調査出口」で原因の所有範囲と回復費用を判定する。
   所有範囲外は投入先に展開しない。
   要求ごとに投入先の対象リポジトリと種別を確定してから渡し、投入先が複数の要求は要求と投入先の組へ展開しておく。
   `add-awi-by-user`から委譲する時は、`atk wi submission begin`で投入作業を記録してから渡す。
   起動後に新しい担当へ要求を足す時も同じで、渡した要求のうち保存を終えていないものの投入先も記録に含める。
   投入先の`atk wi process-loop`はこの記録を持つ会話の委譲先も同じ投入作業として完了を待つため、記録は委譲元だけが作る。
3. 観測した問題（失敗、不具合、未対応など）を起点とする要求では、委譲元の調査は投入先と要求の範囲を確定する観測に限る。
   投入先は、症状が出た成果物、原因を作る定義、共通の機構を持つ成果物のうち、委譲元の文脈で所有リポジトリを特定できる対象から決める。
   原因分析（期待・原因・処置・広がり・確認と、条件付きの再発・再発防止）は担当が確定するので、起動の前提として同じ調査を重ねることは避ける。
   広がりの探索の終了は`agent-basics:bugfix/references/spread.md`「害が大きい時」に、保つ是正範囲は`agent-basics:bugfix/references/prevention.md`「害と費用の比べ方」に従う。
   委譲元が確定した観測は保存原本の所在を添えて`確定済みの観測`として渡し、原因を観測で確かめていない要求は観測した事象、期待する契約、確定すべき問いを渡す。
   担当の調査で投入先の外に原因を共有する対象が見つかったら、`agent-toolkit:atk-mode/roles/add-wi.parent.md`「続行できない理由の扱い」の投入先の外の対象として扱う。
   実行レビューの差分外の既存不良を専念型へ渡す時（`agent-toolkit:atk-mode/playbooks/exec-review-loop.md`「返却に含まれる既存不良の受領」）は、投入先を確定する観測も省き、不良の対象ファイルを管理するリポジトリを投入先とする。
4. ユーザーが明示した対象集合は、既知の欠陥の修正や、足した・強めた規定の既存対象でもそのまま保つ。
   集合を名指しの例だけに限定する案は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「原文からの具体化を要する軸」に沿って確認する。
5. 原因調査に必須で、ユーザーだけが提供できる資料や実例がある時は、担当の返却を待たずに資料の提供を依頼し、その要求を保留する（`agent-toolkit:atk-mode/playbooks/confirmation.md`「未確定判断の保留と暫定判断」）。
   この依頼は対処方法を問う確認と分けて送り、原因の説明は資料で事実を確定してから伝え、資料が無くても進められる要求はそのまま渡す。
6. 要求の分類は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「確定した要件と委譲元の判断」に従い、逐語の本文と実際の回答の出所から確認の要否を判定する。
   ユーザー自身の判断に委ねる事項が残る時は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」で必要性を確かめ、回答を得てから渡す。
   技術的に確定できる前提は理由とともに`委譲元の判断`へ渡し、実装手段の違いを未回答のユーザー要件として扱うことは避ける。
7. 対象集合の見直し、存廃、要否、仕分けを求める依頼では、`agent-toolkit:atk-mode/references/drafting-decisions.md`「対象集合の仕分け」に沿って判定の時期を確定する。
   投入前に判定する対象は結論を`委譲元の判断`へ、未調査の対象は`投入前に確定すべき事項`へ書き、処理の時点で判定する要求には分類軸、判定主体、判定時期、保持条件と完成条件を渡す。

## 投入する要求の欄

要求ファイルは要求ごとに次の欄を持つ。
`再発の経過を問う要求`以外の欄は、省略すると`なし`として扱う。

- 要求の識別子、投入先の対象リポジトリ（絶対パスか正規化したリモートURL）、種別（AWIかUWI）。
- 要求の趣旨: 委譲元が確定した結論（対象、観測した事象、確定していれば原因と対策の1案、要求間の依存）だけを書く。
  事象は発話や観測に示された語句の範囲で書き、推測は`agent-basics:writing-standards/references/investigation.md`「根拠と主張の一致」に従って出所へ帰属させる。
  原因が未確定なら`投入前に確定すべき事項`へ回す（担当は原因を特定できなければ投入せずに返すので、原因調査を後続の要求へ分けさせないため）。
- `再発の経過を問う要求`: `該当`か`非該当`と、根拠の逐語語句。
  失敗・誤り・指摘の反復、頻度、悪化、いつからか守られなくなったことへの言及が該当する（「多すぎる」「また」「毎回」「いつの間にか」などは例）。
  `該当`なら、委譲元の原因判断は経過を分析していない仮説として扱う。
  委譲元は要求ごとに1回判定して書き、省略された時は担当が逐語本文と趣旨から判定して起草の返却へ記す。
- `質問への回答の扱い`: 逐語本文の質問ごとに、送達済みの回答と送達の事実か、担当の調査で確定させる回答の対象を書き、その回答がWIの採否や内容を左右するかを添える。
  調査で確定させる回答は、送達した後に回答済みと注記する。
- `確定した要件`: ユーザーが明示した要件と、確認への回答で合意した要件だけを書き、担当はこれを覆せない制約として扱う。
  要件ごとに、由来（ユーザー自身の指定か、エージェント案の採択か）と根拠の発話・回答の出所を付ける。
  回答として扱う範囲は`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と承認」に従う。
  選択形式の回答から確定するのは、その質問が直接問うた判断だけとし、質問文、選択肢の説明、`共通前提:`行からエージェントが補った内容（採った案の説明にある条件など）は理由を添えて`委譲元の判断`へ回す。
  後続工程（計画・実行・実行レビュー）のモデル、ツール、担当、操作方法は、その工程への適用を示す発話か独立した確認の回答がある時だけ書く。
  AWIの粒度で別個の要求と判定した要件（同じ発話の中の要件、進め方への注文、再発防止を含む振る舞いの是正も単位ごとに判定する）は、要求ごとの原稿と根拠へ分ける。
  分類は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「確定した要件と委譲元の判断」に従う。
- `委譲元の判断`: 委譲元が技術判断として決めた前提と理由を書く（範囲の判断と、ユーザーの指定ではなく委譲元が選んだ比較・検収の手段を含む）。
  担当は調査で得た事実で覆してよく、受け取った方針は独自の原因分析から導いた案と比べる候補として扱う。
  これを`確定した要件`へ混ぜると覆せない制約として扱われ、品質の低い案が選ばれる。
  観測した問題への対策の方向性は、直接の原因を観測で確かめ、`確定済みの観測`へ対応付けた時だけ書く。
  原因が未確認の要求では、観測した事象、期待する契約、確定すべき問いを書き、推測した修正箇所、対策案、想定する回答は除く。
  理由に使う事実は、渡す直前に同じセッションで確かめた観測か方針記録の所在へ対応付け、他の主体の報告は元の出所を読んで内容の一致を確かめ、未確認の前提は`投入前に確定すべき事項`へ問いとして書く。
  案を外す理由には、変更量や改訂の費用の大きさだけでなく品質への影響を示す。
- ユーザー要求の対象（原文の語句が指す集合）: 原文の範囲表現を逐語と出所で書く（記録の形は`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」）。
  `委譲元の判断`へ書けるのは、該当する具体例と根拠のある追加だけである。
  原文の集合から対象を外す判断（字面に無いことを理由に外す判断を含む）は、ユーザー確認で合意した範囲として承認の出所とともに`確定した要件`へ書く。
  原文の集合を委譲元の言葉で言い換えた基準や定義は渡す対象から除く（技術判断の欄に置くと、対象が狭まったまま起草されるため）。
- `投入前に確定すべき事項`: 確定が要る項目だけを書き、委譲元が想定する回答や案は除く。
- `source`: 委譲元が`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と`source`」に従って決めた値（`add-awi-by-user`、`session-review`、`process-wi`、`agent`など）。
  担当はそのまま原稿へ付ける。
- `他の要求単位の割当`: 渡した逐語本文のうち、その要求で扱わない単位ごとの割当先を書く。
  値は、投入済みAWIのファイル名とH1見出し、同じ委譲で別の担当へ渡した要求を指す「」付きの説明、`分割元の依頼全体`のいずれかとし、割当先が決まった単位だけを渡す。
- `確定済みの観測`: 観測ごとの内容、手段（実行したコマンドと入力）、日時、取得済みの記録位置（元の記録の`<記録>:<行番号>`）か保存した出力の絶対パスを書く。
  位置が未取得なら、観測時の入力の特徴と日時で足り、位置を特定するためだけの照会は省く。
  担当は内容と観測条件が一致する範囲で再利用し、再実行の要否を自分で判定するので、再確認を促す指示は省く。
  範囲の語や開放列挙に例や理由を添えた依頼では、例の近傍から探した観測であることを明記して集合全体の観測と分け、集合全体の観測は「原文の保持と取り込み」の独立した調査を委譲元が済ませて含める。
- ユーザー発話: 委譲元が保持していれば対象の逐語本文を渡し、必要なら日時や文脈を添える。
  構造化確認では、ユーザーの回答とエージェントの質問・説明を分ける。
  出所の所在は、認可や解釈の判断に再取得が要る時だけ渡す。
- 要求間の依存: 先行成果の必要性の根拠を添える（`agent-toolkit:atk-mode/references/states-and-dependencies.md`「依存と冷却時間」）。

## 要求の種類ごとの追加の欄

- 上流投入: 要求ごとに`元項目`（元項目のAWIファイル名）と`投入条件`を書く。
  省略時の値はそれぞれ`なし`と`無条件`で、値がある要求を上流投入として扱う。
  投入先が複数なら、元項目と投入先の組へ展開する。
- 投入済みAWIの更新と失敗後の再開: 保留を済ませた対象の`ファイル名`を書く。
- 元WIの完成条件を観測するUWI: 元WIの識別子、現行の完成条件と有効な変更要求、残る観測、再開記録の所在を書く。
  委譲元の依頼文は伝達の要約なので、起草者と検収者がそれぞれ元WIの現行本文と再開記録を取得できる入力を渡す。
- 規範読込の改善報告: 報告者の資料パス、読込の契機、利用した節、不要な範囲、削減見込み、方針候補と理由を、根拠と観測条件とともに書く。
  観測は`確定済みの観測`へ、推定と方針候補は`委譲元の判断`へ分け、同じ資料の報告と既存項目の被覆を資料単位でまとめる。
