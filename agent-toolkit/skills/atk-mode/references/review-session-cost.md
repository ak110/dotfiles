# 振り返りの費用と所要時間の分析

本書は、振り返りの分析で、費用（読込、Skill、結果量、反復、tokenの上位）と所要時間を比べて改善案を選ぶ基準を定める。
分析の手順書`agent-toolkit:atk-mode/playbooks/review-session-analysis.md`を全文読み、費用を比べる時は「工程2」の手順7に従う。
品質を保ち、その内側で費用と時間を比べる（原則2、`agent-basics:writing-standards/references/quality-principles-qcd.md`）。
数値は観測した範囲だけを事実とし、未計測を推定で埋めない（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。
改善案は`agent-basics:bugfix/references/prevention.md`「案を比べる順」の順に比べ、採否は同書「害と費用の比べ方」、採用しない時の区分は同書「再発防止を採用しない場合」で決める。
集計値の典拠と数え方は`agent-toolkit:atk-mode/references/session-records.md`「集計値の典拠」が定める。

## 比較して探す観点

### コストの無駄の確認

振り返りのたびに、準備（`atk run-script session-review-prepare`）が書く総量、担当別の上位、読込回数、反復処理、出力量の要約を使って確かめる。
17の観点と各観点の照会先は、準備が書く`stats.md`の「費用確認17観点の照会先」が示す。
判断に要る全量は`bundle/stats.jsonl`と`bundle/resource-usage.jsonl`から取り、上位に入らない担当や律速でない担当も必要な範囲で確かめる。

観点は無駄を探す補助であり、報告には具体的な作業単位と代替案を書く。
通読、統計、取得済みの証拠から作業単位を特定し、成果と要求元、作業量と発生源、同じ品質を保てる代替案（操作の除去、ホストの標準機能、既存のexploreやshellへの移管、入力コンテキストの保持期間の短縮、現状維持）、採否と根拠を対応付けて分析の記録へ残す。

- 入力の生成、引用、検証、受け渡し、振り返りの起草は、受け取る側が使い終えるまでを1つの作業単位として比べる。
- 生成された入力、managed-tempの参照、hookの生成元と同じ本文は、`resource-usage.jsonl`の記録位置から調べ、指示、専用のRead操作、返却本文、外部から注入された資料を分ける（記録に無い読取量や料金は未確認とする）。
- 同じ本文が再び現れた箇所は前後の文脈から、必要な差分の提示、独立した配送、圧縮後の文脈の復元、不要な再読込を見分け、API履歴の再送と会話コンテキストへの新しい追加も分ける。
- 編集、外部の更新、会話圧縮に伴う再読込、分割取得、独立した検収、別の文脈での判断に要る読込は、保つべき成果を確かめてから代替案と比べる。
- 証拠が欠けた作業は正常として見送らず、欠けた範囲を取得して判断する。
  補うのは判断に足りない証拠だけとし、全操作の台帳、候補の抽出機構、常時の監視、専任の担当のような仕組みは候補から外す。

費用の比較の採否は、正常完了、エラーからの回復、工程が必須であることとは別に、成果と作業量の比較で決める。
改善が要る消費側があり実質的な効果が見込める案は、分析の手順書`agent-toolkit:atk-mode/playbooks/review-session-analysis.md`「原因と対策」へ送る。
現状維持なら、代替案より妥当とした根拠を振り返り結果報告の`### 対策を見送った問題`に残し、確認の結論は同じ報告の`費用確認`の行に1行で書く。

大出力の点検では、準備が書く「大出力の点検上位」と「退避された大出力」を見直し、上位の外の結果も全量の集計から照会する。
退避された結果は、生成の後に読み直す操作の費用も点検する。
自作のツール（`atk`、`pyfltr`、`agents_server`など）は、判断に要る材料、保存先ファイルへの参照、実際の返却を比べ、不要な引数（argv）、Gitの状態、全量の詳細を繰り返していないかを確かめる。
出力が大きいことだけで品質上の欠陥とせず、簡素化の案は品質を確実に保てる手段から選ぶ。

### 通読で使う比較

記録全体を通読する時の比較の観点は、分析の手順書`agent-toolkit:atk-mode/playbooks/review-session-analysis.md`「通読で使う比較」が持つ。
通読で費用の判断材料を得た作業は、本書「コストの無駄の確認」の比較と採否を再利用する。
例えば次の作業は、品質を保ったまま作業量を減らす余地を比べる。

- 未読の補完や未走査0件への再依頼: 初回の分割取得や完了できる作業の割当で済んだか
- 規範の累積読込: 定義元への集約、既読の結果の再利用、読込の時機の整理
- ユーザー向けの文面と原稿全体の独立した確認: 役割ごとに要る入力と起動の統合
- 起動と保存: 準備、入力の生成、保存の集約
- 振り返り自身の再整理と起草: 確認済みの事実や比較結果の再利用による再照会と起草の削減

## 規範適用による目的逸脱

規範に従った結果、処理の停止、差し戻し、空転、不要な反復、過大な読込や準備が生じた事象を扱う。
規範が適用されなかった事象との切り分けと、記録の照会による判定は、分析の手順書`agent-toolkit:atk-mode/playbooks/review-session-analysis.md`「規範の未適用と目的逸脱」で行う。
前提の評価には`agent-basics:bugfix/references/premises.md`「規範に従った結果の失敗」を適用し、条文の緩和、削除、一般化を追加より先に比べる。
正常に完了した作業でも、読込、準備、検収、後始末の作業量を成果と比べ、規範が求める工程を簡略化できないかを検討する。

- 記録すること: 対象の条文の所在（ファイル名と節）、観測された処理の停止、採る改善案と根拠
- 改訂を採用する時: 対象の条文を改訂するAWIへ渡す（`agent-basics:review-standards/references/reviewee.md`「修正要否の立証」が求める規範改訂の提案も、このAWIで行う）
- 現状維持の時: 再現の条件と許容する理由を、振り返り結果報告の`### 対策を見送った問題`に書く

## 所要時間の分析と改善

目的は、品質を保ったまま単位時間あたりに処理できるユーザー由来のWIの件数を最大にすることである。
エージェント由来のWIは別に数え、所要時間とトークンの削減はこの指標を上げる手段として扱う。
分析は目標の有無によらず行い、律速の情報を費用の分析にも使い、改善の候補は律速区間に限らず作業全体から選ぶ。
実行時間が短い処理も、成功した操作の適用頻度、入力の再構築の費用、トークンと保守の費用を本書「コストの無駄の確認」で比べ、その採否を再利用する。

### 振り返り自体の目標と計測区間

振り返り自体の所要時間の目標は、通常300秒、batchは対象1件あたり300秒とする。
計測区間は振り返りの起動から最終報告までで、予告の通知は終点に数えず、対象セッション全体の`elapsed_seconds`と区別する。
終点は最終報告の直前に取得した現在時刻（`date -u +%FT%TZ`など）とし、起点は次の表の値を使う。
自身のセッションIDは、Claude CodeではSessionStartの通知値か`CLAUDE_CODE_SESSION_ID`、CodexではthreadのIDを使い、時刻は表の照会で取る（自身の記録ファイルを`head`や`grep`などの汎用ツールで読む操作は省く）。

| 場面 | 起点 |
| --- | --- |
| batch | manifest（`AGENT_TOOLKIT_SESSION_REVIEW_BATCH`が指す実行情報JSON）の`started_at`。準備の時間も区間に入る |
| batchで準備区間と分析区間の内訳が律速の判定に要る | `atk run-script session-review-evidence -- --claude-session-id <自身のセッションID> --elapsed-until <終点の時刻>`が返す`start`（Codexでは`--claude-session-id`の代わりに`--codex-thread-id <自身のthread ID>`） |
| batchの再開 | `started_at`。中断の時間も経過に含まれるため、そのことを報告に注記する |
| 通常（Claude Code） | `atk run-script session-review-evidence -- --claude-session-id <自身のセッションID> --tool-calls --tool Skill --input-regex 'review-session'`が返す`tool-call`の`timestamp`。該当が無ければ`--user-events --user-match-fixed review-session`が返す発話の時刻、それも無ければ`--elapsed-until`の`start`を使い、そのことを報告に注記する |
| 通常（Codex） | `atk run-script session-review-evidence -- --codex-thread-id <自身のthread ID> --user-events --user-match-fixed review-session`が返す発話の時刻。該当が無ければ`--elapsed-until`の`start`を使い、そのことを報告に注記する |

目標の用途は、超えた時に所要の改善案を必須とする判断に限り、必要な調査の範囲、順序、省略、先送り、停止は目標と切り離して決める。
この基準は、メインの実行区間、レーンの内部、公開と検証の区間、振り返り自体のいずれにも当てはめる。

振り返り自体が300秒を超えた時は、起動から最終報告までの超過を1件の事象とし、原因、必要な全処置、報告の内容が確定した時点で処置済みとする。
既存の統計と追加の照会を使い、材料が足りない時だけ再準備する。
追加のWI投入で経過秒数が増えただけでは同じ事象を分析し直さず、別の原因が分かった時だけ、その原因を「原因と対策」と通常のWI投入へ足す。
準備の完了後に届いたユーザーの発話や、気付いた改善点の追加の分析は、処置済みでも行う。

### 比較の条件

- 改善の前後は、同じ要求、品質、観測区間の集合の受け入れ済みの成果で比べ、分割の件数や再試行は作業量として数える。
- ユーザー由来のWI件数を単位時間で比べる指標に、成果の内訳と、人間の確認・修正の負担を併記する。
  人間の実作業時間は既存の記録で観測できた範囲だけとし、セッションの経過時間から推定しない。
- 時間、金額、実行量は別々に示し、数値化には既存の記録を使う。
- 要件や選好の追加と、エージェントの誤りを是正する介入を、原文から区別する。
- エージェントの実行量だけが減り人間の負担が増えた案は負担の移転として評価し、同じ品質で両方を減らす案と比べる。

### 巡回の比較

対象が巡回のセッション（`agent-toolkit:atk-mode`の作業`process-wi`を起動して作業項目を処理した1回のセッション。`atk wi process-loop`が起動した回と手動で起動した回を含む）なら、内訳の分析より前に過去の回と比べる。
比べ方は`agent-basics:bugfix/references/causes.md`「場面ごとの確かめ方」の所要が増えた時の確かめ方に従い、巡回に固有の値は次のとおり取る。

- 今回と直前の巡回の所要を並べる（さかのぼるのは3回まで、判定には直前の1回だけを使う）。
  候補の件数と使ったレーンの数が取れる場合は添える。
- 目標の所要を達成できていた時期の基準値を並べ、今回との差を示す。
  基準値はプロジェクト規範が記録した値を読んで使う。
  基準の時期を記録から特定できない場合は、その旨と、さかのぼれた範囲で最も良い値を示す。
- 統計の`stats-unit-costs`（ツール呼び出し1回の所要の中央値、応答1回の平均所要と入力・出力・推論トークン、報告の件数と長さ、同時に作業中だった記録の最大数、時間上限による失敗の件数）も基準値と並べる。
  WI 1件あたりの内訳には本書「レーンの保存済み統計」を使う。
- 同時に作業中だった数と、完了件数・時間上限の失敗から、agents_serverの同時稼働数の上限の係数を上げるか下げるかを判定し、判定と根拠を報告に載せる。
  係数の初期値を変えるのが妥当なら、配布物の初期値を変えるAWIを通常の手順で登録し、実行中のマシンの設定は変えない。
- 巡回の開始・終了は統括のセッション記録の最初と最後の時刻から、候補とレーンの上限は選定YAMLから取り、比較値を得られない時は「未取得」と理由を記して今回分を分析する。
  2026年11月22日より前の版の巡回を比べる時は、その版が残した`process-loop-ownership/rounds/`の集合JSONと結果を使う。
  過去の振り返り報告は`atk wi grep`で`agent-toolkit:review-session batch`を検索して取得し、対象ごとの所要の秒数を使う。
- 件数は比較の材料として添えるだけで、判定と延びた理由は所要の内訳から決める。

今回の所要が目標を超え、かつ直前の回より長い場合を「悪化している」と判定する。
目標が無い対象では、直前の回より長い状態が2回続いた場合とする。
目標を超えていても直前の回より短い場合は悪化とせず、超過の規定だけを当てはめる（超過した時は、直前の回より短くても上の比較をする）。

### レーンの保存済み統計

終了時に今回の巡回の保存済み計画とCodex rolloutを明示して1回集計する。
パスはファイル名でも引用したglobでもよく、各引数を繰り返して複数のレーンを指定できる。

```sh
atk run-script session-review-evidence -- --stats --saved-plan "$plan" --saved-rollout "$rollout"
```

- 担当を計画と対応付けて分かるのは、その記録の帰属先までである。
  全対象WIの処理と全担当の記録がそろった証拠は別に必要なため、この入力では計画全体の率（`plan_wide_rates`）は`null`となる。
- 同じ巡回・レーンの計画と記録を指定し、日付で選ぶ場合は計画日とrolloutの開始日をそろえてファイル全体を使う。
  計画の識別には、初回呼出し前の委譲入力の「計画」を使う（作業ディレクトリは再利用され、資料や出力には他計画の名前も現れる）。
  年月付きの保存名は保存先からの相対位置、作業名は計画名と巡回専用branch（計画の進捗行にあるworktree・branchとrolloutのGit情報）が一致することを確かめる。
  `paired_rollouts`は計画に対応した記録、`assigned_wis_by_rollout`は委譲入力の「担当WI」が計画メタ情報の関連WIに含まれると確認した記録と担当WIである。
- `assigned_record_rates`は指定した担当記録の呼出し・所要・読取量を、その記録に明示された担当WI数（計画内の重複を除く）で割る。
  12件の計画のうち1件を担当した記録に10呼出しがあれば、10回/担当WIである。
  計画・担当WI・呼出しに欠測がある場合は実数を残し、率を`null`とする。
  対応記録のない計画は`unpaired_plans`、欠測理由別の件数は`gaps`に示す。
- `plans.recorded_work`の実働は工程の開始から終了までの分数の合計で、中断から再開までは`between_phase_minutes_per_wi`に分ける。
  開始・終了の対応が欠けた計画は`incomplete_plans`に数え、実働の集合から除く。
  `plans.legacy_estimate`は旧書式の推定で、分まで読める隣接行の間隔を各120分で打ち切り、終了側の語で分類する。
  旧推定は最初と最後の進捗行の間に限られ、その間の中断も含みうる。
  書式ごとに`by_kind`は作業種別別の計画数・WI数と「計画の分数÷関連WI数」の中央値を、`phase_minutes_per_wi`は工程別の合計を同じ集合の延べWI数で割った値を示す。
- `matched_calls`はレーンの作業ディレクトリ内でIDと時刻がそろう呼出しから結果までの秒数。
  `process-wi-lane-NN`、系統付きの `process-wi-<系統>-lane-NN`、旧配置の `lane-NN`・`lane-NN-<一時名>/wt`・`process-wi-lane` を対象とする（NNは2桁）。
  合計は並列区間も足す。
  `thinking_proxy`は同じ記録の直近の出力から次の呼出しまでの0秒以上600秒未満の間隔で、推論だけの時間ではない。
  ターン境界はまたがず、モデルと推論量が同じ群の標本数・中央値を比べる。
- `read_calls`は引数冒頭400文字から分類したMarkdown読取で、テスト・待機・atk操作を先に分類する。
  出力量は記録に残った結果の文字数とUTF-8バイト数で、切り詰め前の出力やファイルサイズではない。
  入力が片方だけでも集計できる。
  未一致のパス、除外計画、打切り数、`gaps`と各指標の標本数を示し、標本なしの時間や不明な推定値は`null`のまま扱う。
- 振り返りでは終了時の結果を再利用し、週次の横断比較にはその結果を渡す。
  維持・単純化・撤回は、`agent-basics:check-execution/references/performance.md`「LLMを含む作業の仕事量」に従い、変更が減らす仕事と失う機能・保護・ユーザー要件を比べて判断する。
  巡回に明示された全体所要の目標は、個別変更の採否とは別に検収する。

### 悪化した巡回の内訳

- 複数のレーンを使った巡回では、開始から統合の完了までが最も長いレーン1つについて、既存の記録（そのレーンの計画の進捗ログ、レーンの所有登録にある統合の結果、検証の実行記録）から工程ごとの時間を出す。
  統計の`overlap_seconds`はレーン内部の委譲先も含むため、レーンどうしが同時に動いた時間やその割合の判定には使わない。
  段階実行で最後に終わったレーンが最長のレーンと違う場合は、最後のレーンの開始が何の完了を待っていたかを添える。
- 「次回の振り返りで調べる」を、この区間の分析を終える理由にしない。
  振り返りは回ごとに別のセッションで行われ、前の回の再開の条件を次の回が読む手段が無いためである。
- 出した工程のうち、レーン、作業項目、統合ごとに繰り返すもの（検証、レビュー、同期、順番待ち、それらを調整する仕組み）を挙げる。
  それぞれ、その工程を求める条文がユーザーの要求かエージェントの判断か（変更履歴と元の作業項目で確かめる）と、直前の回と比べた1回の所要と回数の変化（取れる範囲）を確かめる。
- 対策の候補は、工程をやめる案、単純にする案、順序を変える案、仕組みを足す案の順に比べる。

### 改善案の選び方

- 短縮の主な対象は、統計が示す律速区間（メインが単独で動く区間と、エージェントのスレッドごとの排他区間）とする。
  スレッドの排他区間が律速なら、工程、反復、待機の内訳を準備の`stats.md`の`律速threadの内訳:`で把握し、全文が要る箇所だけを`--detail`か`--grep`で照会する。
  委譲先の所要時間と反復の回数は、`agent-toolkit:atk-mode/references/session-records.md`「集計値の典拠」の数え方を確かめてから比べる。
  未計測として除くスレッドは、記録ファイルが無いか`unresolved-delegation`と報告された対象に限り、その対象を明記する。
- 委譲先の返却本文にある時間の使い道の説明や、所要時間の目標の適用外であることは、見送りの根拠にしない。
  内訳が分解されていない区間は内訳未確定とし、計測できない見込みの短縮秒数と、記録から実現性を判断できる工程の改訂とは分けて採否を決める。
- 改善の対象は、必須の工程と検収の範囲を含む全工程とする（`agent-toolkit:atk-mode`の作業`process-wi`と`atk wi process-loop`の手順、準拠する規範、振り返りの工程、`atk run-script session-review-prepare`を含む）。
  規範が求める工程も必須の前提として残さず、不要な工程の撤去、順序の変更、並行化を候補にする。
  手順や規範の撤去と置換は`agent-basics:bugfix/references/premises.md`「規範に従った結果の失敗」に従って導入時の目的を調べ、今も必要な目的は、より費用の低い手段で確実に達成できる場合に限り置き換える。
- 重複した検証の排除と待ち時間の活用を観点に含める。
  CIが同じ全体の検証を担うなら、レーン内、統合時、公開前のいずれのローカルの実行も重複とし、ローカルでは変更箇所と特定した利用側の部分検証を選ぶ。
- 外部サービスの利用上限、レート制限、課金枠による待機の扱いを変える対策は、AWIとして確定する前に`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と承認」の裁量と変更の程度の判定を当てる。
  待機、モデルや実行環境の切り替えは、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」で確認の要否を判定し、指定された費用、サービス、待機の条件を保つ技術判断は自分で確定する。
  比較には、停止、実行先の切り替え、打ち切り、上限到達の事前の回避に加え、今の待機を続ける案も残す。
- 短時間に反復したコマンドも、呼び出しごとの所要と律速区間への寄与から見直す（努力目標。無駄な呼び出しの削減）。
  入力形式の誤りによる反復は最下層のヘルプや仕様の取得を先にし、成功した同種の操作の反復は複数の対象の指定でまとめられるかを比べる。
- 複雑なシェルの実行を専用のツールへ置き換える候補は、`agent-toolkit:atk-mode/references/review-session-triage.md`「一次選別」のその場のコードによる加工の反復の判定で決める。
  代替案は`agent-basics:bugfix/references/premises.md`「外部の変化と加工の反復」で比べる。
  手順書の作業を一時スクリプトで代替した箇所も、同じ判定で将来の再実行性を決める（Claude CodeとCodexに同じ基準を当てる）。
- コンテキストの圧縮は発生回数と合計の所要時間を記録し、取得範囲の限定や調査の分離など、コンテキストの消費そのものを抑える案を比べる（発生の閾値を上げるだけの案は候補から外す）。
- 改善につながった事例が少ない候補の区分は、抽出の条件を限定する対象として検討する。

### 数値化と結論

- 改善の効果の数値化は、既存の統計や証拠で確かに裏付けられる範囲に限る（数値を出すためだけの再計測やデータ収集は省く）。
- 短縮秒数を数値化できるAWIには、1セッションあたりの見込みの削減時間と根拠の統計値を実測か推定かの別とともに書き、推定には計算式と前提条件を添える。
  所要を縮める目的のAWIには、後の見直しで比べられるよう、目標の値、今回の値、対象の区間の値も書く。
  根拠が足りなければ、削減対象の工程名と「未計測」を書く。
- 複数の案の合計の削減時間、改善後のセッション全体の時間、目標との差、超過した律速区間は、振り返り結果報告の`改善見込み`の行に1回だけ書く。
- 超過したかによらず既存の統計と証拠を使い、根拠が足りない律速区間だけを追加で照会、再現する。
- 超過しなかった時は、証拠から改善提案の要否を判断し、照会と候補の比較の経過を証拠に残す。
  不具合が確認済みで対策を特定できなければ、振り返りの分析の工程4で調査の要求にする。
  欠陥ではない費用・所要だけの改善で見送る場合は、理由の結論と根拠の再取得先を`### 対策を見送った問題`に書く。
- 超過した時は再発防止の対象とし、律速区間へ直接作用する対策を確定する。
  原因か方式を確定できなければ、観測した超過と次に確かめる問いを調査の要求にする。
- 今回の律速区間への処置は、AWI化の基準など別の対象への先行の回答と分けて確定し、先行の回答はその質問が対象とした要求にだけ当てはめる（`agent-toolkit:atk-mode/playbooks/confirmation.md`「原文からの具体化を要する軸」）。
- 新しい律速の原因は、過去の不採用の判断や既存AWIの有無によらず、原因を解消する効果で採否を決める。
  既知の原因を既存の作業項目が扱う場合も、それを理由に所要の分析を終える前に、その項目の状態を確かめる。
  採用済みで今回の巡回より前に反映された項目は、分析の手順書「原因と対策」の採用済み項目の見直しへ渡す。
  未着手か処理中の項目は未反映と書き、その項目の登録から何回の巡回が過ぎたかを添える。
- 所要時間、トークン量、リクエスト数をユーザー向けの文面に書く時は、比率に基準値との差分を併記する。

### トークン量からの所要の見積もり

モデル別にトークン量から所要時間を見積もる時は、モデル、推論設定、実行環境（runtime）、接続条件をそろえた応答単位の所要時間と使用量（usage）を使い、入力、キャッシュ済み入力（cached input）、出力の重複を除いてモデル式を校正する。
例えば`応答秒数 = 固定費 + 未キャッシュ入力の係数 × 未キャッシュ入力 + キャッシュ入力の係数 × キャッシュ入力 + 出力の係数 × 出力`のような線形モデルを候補とし、別の応答で誤差を検証して、標本数と誤差範囲を書く。
セッション全体の経過秒数には並行処理、ツールの実行、人の入力待ち、サービスの利用上限による待機が含まれるため、総経過時間を総トークン数で割った値をモデルの処理速度に使わない。
校正に要る対応のログが無ければ数値の予測は未確定とし、既存の証拠から再読込、重複調査、入力の再生成などの具体的な削減対象を比べる。
処理時間の超過時も、推定式の残差だけでモデルの過負荷を原因とせず、工程と待機の内訳を確かめ、品質を保てるトークンの削減や既存の機構への集約を比べる。
入力キャッシュの不調が疑われる時は、Codexの `last_token_usage` を同一会話・同一モデルの継続応答で比べ、初回、モデル切替直後、圧縮直後を別に扱う。
生の `input_tokens - cached_input_tokens` が未キャッシュ入力で、集計済みの未キャッシュ入力はそのまま使う。
この差から指示欄別の原因、実請求、契約枠の消費は確定できないため、[報告 #62312](https://github.com/openai/codex/issues/62312) の診断表示とusageの差も区別する。
Responses APIを直接送る場合は、同じ指示を先頭の `developer` メッセージへ置く対照を試せるが、OpenCodeでは版と接続先を先に確かめる（[v2.3.2の変更と圧縮時の例外](https://github.com/anomalyco/opencode/pull/64542)）。
OpenCode 1.19.5のOpenAI OAuthで疑わしい時は、設定を自動移行する代わりに同じモデルのCodexでも比べる。
Codex 0.171.0の通常要求は既にbase指示を `input` に含めるため、`baseInstructions` や `AGENTS.md` は維持する。

## hookの所要時間

対象セッションのmanaged-tempにある`hook-timings.jsonl`で、イベント、処理名、区間、所要秒数、成否を確かめる（件数と保持の範囲は準備の`stats.md`「hookの所要時間」が示す）。
`total`の計測範囲はPythonのエントリーポイントからの所要で、プロセスの起動前の待ち時間は別に評価する。
SessionStartは、通知の構成（`normative-content`）、振り返りの起動要求、圧縮の復元の区間も比べる。
1秒以上かかる処理は重いものとして改善の対象に調べ、この閾値は調査の目安に限り、元の操作の成否は通常の判定に従う。
必要な処理を保ち、重複した取得・解決、同期の起動、入力の再構築を同じ観測条件で比べる。

## CI履歴からの継続改善

1. 通常・batchとも、対象セッションがCIの変更、公開、待機を扱ったリポジトリを抽出する。
   同じbatchの同じリポジトリはまとめて証拠を再利用し、最初は直近50実行を目安に、標本が足りなければ理由を示して広げる。
   他者の調査件数や短縮の実績は、今回の必須の件数や目標値と区別する。
2. 履歴を、workflow、イベント、branch、構成の世代、成功・失敗・中止、再実行、共通CIの所有・非所有で区別する。
   遅いジョブの件数、中央値、分布の幅、run URL、対象SHA、計測の定義を分析の記録へ残す。
   待機、準備、検証、後処理、依存ジョブの待ちに分け、ジョブの秒数の合計と並行するworkflowの経過時間を分ける（取得できない値は未取得とする）。
3. 必要な検証を保つ改善の候補を、ランナーの待ち、lintと型検査、テストの分割と初期化、準備・キャッシュ・checkout、並列度と`needs`、変更範囲、push前の部分検証とCIの役割、連続したpush、再ビルドとプリビルド、OSの選択、重複した処理から選ぶ。
   文書の変更にも、必要な文書・規範・生成物の検証と必須のcheckを保つ。
   連続したpushの取り消しはbranchの役割と現行の方針で判断し、リリースの条件と検証対象のcommitを保つ。
4. 改善案ごとに、対象ファイルと変更内容、現状の秒数、見込みの効果と根拠、検証の維持、資源・料金への影響を確定し、既存のWI投入の手順へ渡す。
   追加の課金、有料のランナー、必要な検証の削減などユーザーに固有の判断は、ユーザーへの確認へ回す。
5. 変更前後の実測と残る律速を報告とAWIへ残し、次回は同じ条件の証拠を再利用して、効果の出なかった変更も評価し直す。
   既存の振り返りの契機と記録を使い、常駐、定期ジョブ、永続の台帳は足さない。
