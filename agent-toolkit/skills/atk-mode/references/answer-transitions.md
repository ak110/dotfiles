# 回答済みUWIの扱い

回答が得られたUWIを元の作業へ反映する手順と、`atk run-skill`で起動したセッションが過去の実行で作られたUWIを処理する手順を定める。

## 回答後の状態遷移

投入済みで未回答のUWIを持つ間は、定期確認の時機（`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`）ごとに`atk wi`で回答の有無を確かめる。

処理するUWIは場面で決まる。

- `agent-toolkit:atk-mode`の作業`process-wi`の実行中は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「状態と依存」に従う。
  回答が得られたUWIは`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」へ渡す。
  処理中の主題を保留していたUWIの回答だけを同じセッションで反映し、保留していた工程を再開する。
  それ以外の回答済みUWIは、ユーザーが告げた場合を除き、次のprocess-wiの実行の選定に任せる。
- process-wiの実行中でないセッションは、自セッション（委譲先を含む）が投入したUWIだけを処理し、セッションを終える前に、回答の反映から回答を待っていた作業の再開までを終える。
  ユーザーの明示的な指示が無い自動通知で届いた他セッションのUWIは、読まずに置く。
  他セッションのUWIは投入したprocess-wiの実行か次の選定が処理し、無関係なセッションが扱うと余計な確認の往復が生じるためである。
- ユーザーが現在のセッションで直接回答を伝えたUWIは、明示的な指示として処理する。

標準の2択の事後承認型UWIに肯定の回答が得られた時の遷移は`agent-toolkit:atk-mode/references/states-and-dependencies.md`「状態と依存」に従い、同じUWIへの`adopt`の再実行や追加の是正は不要である。
問題の指摘を含む回答、事前承認型UWIへの回答、選択型の報告用UWIへの回答は、次の手順を一連の作業として順に終える。

1. 質問と回答を取得する。
   ユーザーが回答を伝えたUWIは`atk wi show <UWIファイル名> --pull`で取得し、通常の定期確認には`atk wi show <UWIファイル名>`を使う。
   強制同期と未到達時の再取得は`agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入と取得」に従う。
   強制同期の後も未回答なら、送信側の同期が終わっていない可能性を考え、後の定期確認の時機に同じ公開操作をもう一度試す。
   回答を取得した後に、事前の暫定の判断との差分を確定する。
2. 反映を始める前に`atk wi start-processing <UWIファイル名>`でUWIを`processing`へ移し、回答を処理中であることをキューと`atk serve`の画面へ示す。
   今回の巡回でUWIを`processing`へ移したことを開始結果で確かめた場合は、遷移を繰り返さず、割り当てられた処理担当が回答を反映する。
   別の担当が処理中のUWIには着手しない。
   別の担当が先に着手・終了して状態遷移に失敗した場合も、回答を反映しない。
   回答を保存しただけで反映を始めていないUWIは`inbox`のまま残す。
   続けて回答を元の作業へ反映し、UWI本文に「回答の処理」節があれば実際の回答に従ってその手順を実施する。
   process-wiでは報告用UWIの回答処理のために元の調査をやり直したり、同じ調査の報告用UWIを新たに保存したりしない。
   回答済みUWIはUWIとして扱い、別の作業の要求が明示された時だけ、独立したAWIを起草するかを判定する。
   回答が確認の要否や担当の扱い方を一般的に正す内容（今後の扱いの指示、確認自体が不要という指摘、過去にも伝えたという指摘など）を含む時は、個別の項目の反映に加えて`agent-basics:bugfix`を起動し、この確認や行動を生んだ規定・出力・テスト・手順を特定する。
   既存の条文があるだけで十分と判定せず、その生成元が今回作用した理由を確かめ、同じ処理で生成元を直すか、権限外ならAWIを登録する。
   個別の項目を終えただけでは、同じ生成元が次の確認や行動を生むためである。
3. 回答が継続して適用することを明示している時は、`agent-toolkit:atk-mode/references/awi-body.md`「継続的な方針の保存」で、読み手・適用範囲・出所を保って既存の方針の原本へ反映する。
   `agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」で以後の方針の候補と判定した回答も同じ基準で扱い、今回限りの回答を無断で一般化しない。
   回答の保存と、実装や方針の原本への反映の完了を区別し、必要な認可とレビューは元の作業の契約を保つ。
   選ばれた対応の反映を終えたUWIは`atk wi adopt <UWIファイル名>`で終了させる。
   選択型の報告用UWIで対応を全て見送る回答なら、提案を反映せず`atk wi reject <UWIファイル名>`で終了させる。
   回答が提案や質問を退ける内容なら`reject`を使い、退けた理由を回答と対応付けて記録する。
4. そのUWIを`depends_on`に持つ元の項目は、UWIの終了で依存が解ける。
   元の項目が依存する未回答のUWIが他に無ければ、中断していた元の処理を再開する。
   旧運用で`hold`に置かれた元の項目は、回答を反映した後に`atk wi unhold <元項目ファイル名>`で`inbox`へ戻す。
   再開する前に`atk wi show --pull <元項目ファイル名>`で状態を照会し、`inbox`なら`atk wi start-processing <元項目ファイル名>`で`processing`へ移す（`unhold`で戻した項目を含む）。
5. 元の`agents_server`のセッションが残っていれば、そのセッションへ回答を届けて処理を再開する。
   残っていなければ、元AWI本文の再開記録で未完了の工程から再開する。
   旧形式の計画で再開手順を進捗ログだけへ記録していた作業は、その計画の進捗ログから再開する。

各遷移の完了は、状態を変えるコマンドの正常終了と、警告が出ていないことで判断する。
途中で失敗したら、完了していない遷移からやり直す。

## GitHubの外部報告を取り込む回答

`source: github-submission`のUWIに「取り込む」と回答すると、atkは`github_source`が同じAWIを1件だけ残し、UWIを採用で終える。
「取り込まない」ではAWIを登録せず、UWIを不採用で終える。
どちらも回答の保存と同時に処理するため、手で同じ報告を起票しない。

## `atk run-skill`の過去の実行のUWI

`atk run-skill`は同じ対象リポジトリで同じスキルを反復して実行する作業であり、次に起動するセッション自身が「次の実行」に当たる。
そのため、本書「回答後の状態遷移」の、他セッションのUWIを読まずに置く規定はこの場面に当てない。

一般の確認UWIと報告用UWIは、`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と`source`」の保存規則で求めた起動単位か、SessionStartの起動入力の取込対象scopeが、保存済みのscopeと一致する時に取り込む。
モード語以外の自由記述が違っても、同じ起動単位として扱う。
作業名を修飾しない旧版が保存した形（`process-wi single-lane`、`review-session batch`など。先頭の`agent-toolkit:`が無い）も、起動入力の`accepted_scopes`に並ぶ。
この形も同じ起動単位として読む。
スキル名が`review-session`の時は起動入力の`accepted_scopes`に並ぶ旧scopeも同じ起動単位として読む。
旧scopeの保存値は次の3形式で、1行目は通常の起動、残りはbatchモードに当たる。
保存済みのscopeは変えず、通常の起動とbatchモードを区別する。

```text
agent-toolkit:session-review
agent-toolkit:session-review batch
agent-toolkit:session-review-batch
```

1. 作業を始める前に`atk wi show --pull --all --type=uwi --state=active --source=run-skill --target-repo=<対象リポジトリの絶対パス>`を実行する。
2. frontmatterの`scope`が自分の起動単位（スキル名とモードの組。通常の起動はスキル名）か、起動入力の取込対象scopeと一致する項目を、同じ作業の過去の実行が投入したUWIとして扱う。
   `processing`の項目は別セッションの処理対象として残す。
   報告用か承認用かを問わず、回答後のprocess-wiが先に処理して終えていることもあるため、取得した未終了の項目だけを扱う。
3. 項目ごとに次のとおり扱う。
   - 回答済みの項目には本書「回答後の状態遷移」の手順1〜3を適用し、承認された対応をそのセッションで行う。
     元の項目と保持する`agents_server`のセッションは無いため、手順4と5は当てない。
   - 未回答の事前承認型UWIは未回答のまま残す。
     同じ対応がまた要る時も新しいUWIは投入せず、対応を見送り、報告用UWIの`### 未達・持ち越し`に、見送った対応と回答待ちの既存UWIのファイル名を書く。
   - 未回答の報告用UWIは、各実行回の記録として残す。
