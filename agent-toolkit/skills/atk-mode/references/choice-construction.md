# 確認文と質問ラウンド

確認文の根拠、候補、影響、回答の単位、語と、質問ラウンドの進め方の定義である。
ユーザーが確認文だけで判断でき、選択肢の出し直しと事実確認の往復が起きない形にする。
確認するかの判定は`agent-toolkit:atk-mode/playbooks/confirmation.md`が定める。

## 確認提示項目

`agent-toolkit:atk-mode/playbooks/request-intake.md`手順7の方針の承認は、問いの目的と対象を明確にし、本書の確認提示項目と`共通前提:`は先に送る方針本文へ書く。
比較や解釈は必要な内容として示し、特定ラベルの有無を意味の充足としない。

確認文と、委譲先からの確認の通知には、次の項目を全て含める。

- 判断の対象
- ユーザー固有の判断である根拠（足りない選好・認可・本人しか持たない情報と、調査や成立済みの認可で補えない理由）
- 推奨案と代替案
- 根拠（規範や仕様を挙げる時は、従うことで防げる問題か得られる成果も書く）
- 影響範囲と、ユーザーが観測する結果
- 回答後に行う操作（協調モード）

確認を受領・発行する前に、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
項目をそろえても、確認が必要かは`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」で決まる。
確認を発行するメッセージの地の文にも、推奨案と根拠の要約を書く（フォームより先に届く文面が判断を委ねると、ユーザーが推奨を尋ね直すため）。

## 根拠の確定

候補を作る前に、変更する対象の現行のユーザー決定、その出所、今回変える根拠を対応付ける。
決定済みの目的、上限、全件処理、必要な品質は問い直さず、新しい判断が必要な範囲だけを確認する。

- 前提、影響、副作用は、推測の注記を付ける場合も、コード、規範、実行結果で確かめる。
  既存の機能を使う案は、存在に加えて、その案が使う起動の形、終了時の動き、状態、権限でも成立することを確かめる。
  他者の報告や文書は一次資料で確かめ、裏付けの無い内容は確認文から外す。
- 共通の仕組みを変える案は、手元の実行例だけで影響を決めず、`agent-toolkit:atk-mode/references/awi-body.md`「直接影響範囲」に従って、従来の動作を前提とする指定を調べる。
- 作業を完遂できるか、コンテキストの容量が足りるかは、前提から外す（実行環境が会話を自動で圧縮して続けるため）。
- 既存の値、設定、規範の規定を変える案は、その値を明記した記録や規範と比べ、従来の判断を保つ案と、変更の承認が必要な案を分けて示す。
- 本文や選択肢で触れるコマンド、ツール、設定項目は、同じセッションで公開仕様（ヘルプ、入力スキーマ、公式仕様）を取得してから書く。
  各案の効果は、入力の補正、デフォルト値、権限の検査を経て実際に適用される状態で評価する。
- 集合の外に対象が無いという主張と利用箇所の列挙には、母集団の総数、除外した分類ごとの件数、判定の条件を添える。
  包含の条件を選んでもらう時は、案ごとに扱いが変わる実データの行を比較表で示す。
- 「違いは〜のみ」「残る利点は〜だけ」と限定して説明する時は、対象範囲、入力、実行主体、使う資源、出力、終了状態などで実際の仕様を比べてから書く。
- 同じ実装の構造を共有する対象の一部を外す時は、その構造がもたらす外部から観測できる結果で判断し、観測済みの症状が再現しないことだけを理由にしない。
- エンドユーザーが見る表示、通知、帳票の文面案は、表示を判定する実装の条件と比べ、合わなければ文面と条件のどちらを直すかを同じ回答の単位に含める。

## 候補の構成

外部資料の適用範囲を問うときは、`agent-toolkit:atk-mode/references/omission-check.md`の点検類型(i)で成立した派生先への展開案を、初回に提示する候補群へ含める。
主題が成立しない登録先は理由を示して外す。
登録自体は適用の認可ではない。

質問本文、選択肢、`共通前提:`では、原文や回答に由来する内容と、エージェントの案・推論を分けて示す。
背景の理由から補った目的を合意済みとして扱わず、原文と違う対象、契機、結果、適用期間を提案する時は、差と根拠を書く。

問いの主題は、ユーザーだけが判断できる方針、基準、許容する影響に置き、恒久的な成果物へ残せる粒度にする。
実装内部の値や手段を選ばせる問いは、ユーザーが判断の材料を持たないため、同じ確認が繰り返される。
手段の比較を選択肢にする前に、その手段が満たす達成目標と受入れ条件を確定し、確定できなければそれ自体を確認する。
確認文には、対象の識別子、回答ごとに変わる外部から観測できる結果、採用時に行う操作の要約を書く。
経緯、調査結果、案の詳しい比較は、ユーザー向け本文の送達ツールを使えるホストでは質問より先に送り、質問には問いと最小限の前提を残す。
送達ツールが無いホストとCodexでは、判断の材料も質問本文へ書く。

各質問の本文に`共通前提:`で始まる1行を置く。
全ての選択肢が共有する前提、その前提を外した案を含めたか含めない根拠、選択肢の評価を左右する技術的な事実（対象を作る主体、その時点でそろう情報など）を書き、どれも無ければ`共通前提: なし`と書く。
前提は、判断の時機、実施の主体、対象の範囲、工程の順序、結果の届け方、全ての案で共通の観測結果、論点に関わる既存の機能・規則の存続、ユーザーの発話にある語句の観点で探す。

推奨案と前提を共有する案だけを並べると、ユーザーが欠けた案を自分で挙げ直すことになる。
共有する前提ごとに、その前提で達成しようとした上位の目的から、前提を外した案を検討する。
検討には、不要な分岐・条件・確認・対象そのものを無くす案、既存の名称を使う案、既存側を変えない案、先行するユーザーの判断を反映する案、後続の工程を前倒しする案を含める。
載せる対案はユーザーの判断が必要なものに限り、1件以上載せるか、載せない根拠を書く。

<例>
「小さいリポジトリで試してから全体へ広げたい」と述べた後、試行の結果が出た時点で質問する: 同じ回で全体へ展開する案も並べる。
新しい方針を、既存の規則が別扱いにしている場合へ広げるかを問う: 規則を残す案と規則の内側で当てはめる案に加え、その規則を外す案を載せる。
依頼が範囲語で対象を定めながら、例示や問いで特定の対象を知りたい目的を示している: 範囲語どおりの案に加え、例示と問いが示す対象へ限定する案を載せる。
</例>

- 名称、識別子、用語の候補は`agent-basics:writing-standards/references/defined-names.md`「命名の方針」に従って作り、既存の成果物で同じ対象を指す語を採用しない場合は理由を書く。
  ユーザーが挙げた例示と、同じ適用区分で先行するユーザーの判断も候補へ反映する。
  表示名の記法を既存のラベルへそろえる案は、設計意図の記録が無ければ現状維持を推奨し、そろえる案には記録が無いことを書く。
- 工程の一部を後で行う案（後続のセッション、`atk wi process-loop`、別の担当への引き継ぎ、回答や外部状態を待つ保留）には、その工程を終える主体と時機、ユーザーへ結果が届く報告先と時機を書く。
  完了を委ねる既存の仕組みが、その実行形態でも働くことを確かめる。

推奨案は第1選択肢に置き、選ぶ判断をユーザーへ戻さない。

1. 変更後の成果物を使う主体と、その主体にとって理想的な動作を整理して確認文に示す。
   技術判断にだけ使う情報は自分で処理し、ユーザーが選ぶために必要な結果、コスト、影響を残す。
2. 確定した達成目標と受入れ条件を満たす案から選ぶ。
   エージェントが実施できる作業は、エージェントが行う案を推奨して最初から選択しておく。
   候補が複数あれば、足すか保つ仕組み（上限、分岐、専用の状態、エンドユーザー向けの機能・設定、保つ既存の保護とそれを補う機構など）が最も少ない案を選ぶ。
3. 選んだ案より仕組みが少ない各案について、満たせない受入れ条件を説明文に書けるかを確かめ、書けなければその案へ替える。
4. 仕組みや対策を足す案を推奨するのは、それが無いと要件を満たせないことを観測した事象（発生の条件、確かめた頻度、最大の影響）で示せる場合に限る。
   示せなければ、足さない案を推奨する。
   ドキュメントと実装が合わない場合は、合意済みの目的へ既存の手段で届くならドキュメント側の修正を推奨する。
5. 受入れ条件を満たさない案を載せる時は、満たせない条件を説明文に書く。

観測された問題への対処を選んでもらう確認では、選択肢を作る前に`agent-basics:bugfix`に従う。
比べた処置の案（無くす、単純にする、直す）を選択肢に含めるか、成立しない根拠を示す。
原因を特定できない場合は、特定に必要な調査とその実施の条件を確認の主題にする。

## 影響と回答単位

- 推奨案は、技術的な観点と、ユーザーが気付きにくい・取り消しにくい副次的な影響（秘匿値の残留、可逆性、第三者からの観測、監査や通知、管理外の複製）を比べて決め、他の案の利点も推奨の理由に書く。
- 確認文には、外部から観測できる差（入出力、応答時間、画面表示、情報量、通知の頻度など）と、変更に伴って直す成果物（設計書、運用手順、ヘルプ、テスト、公開ドキュメントなど）を書く。
  直す対象が無い案では0件と書く（努力目標。追随の検討を済ませたことを示す）。
- 同じ論点を繰り返し問わずに済むよう、必要な事項を1つの回答の単位にまとめる。
  回答の結果として値の登録、保存、作成、変更を伴う質問には保持先の論点を含め、保持先に登録済みの項目を実物で挙げる。
  値の指定を委ねる論点では、候補の値を1件以上示す。
- 既存のフラグ、カラム、設定項目、状態の値を変える論点では、その値を参照する箇所と、各箇所の意味が保たれることを書く。
- どの選択肢でも残る外部から観測できる結果は、今回の作業で許容するか、別の要求として扱うかを同じ確認文で示す。
- 独立して決められる事項は別の質問に分け、個別の回答から合意を判定する（構造化質問では同じ呼び出しに並べてよい）。
  提案全体への大まかな賛同を、各項目の合意の根拠にしない。
  回答が互いに依存する事項は同じ単位にまとめる。
  UWIでは質問ごとに1件を作り、書式は`agent-toolkit:atk-mode/references/uwi-format.md`に従う。

## 本文の語

発行の前に、本文と選択肢の名詞を点検する。
ユーザーの発話の語、一般に意味が一意な語、本文で説明済みの語のどれでもない語は、説明を付けるか平易な語へ直す。
内部のツール名や実装候補の名前は、回答の影響を理解するために必要な場合だけ補い、質問の主題を内部名の選択へ置き換えない。
規範が定義する工程、レビュー、検証、判定、担当の名前はそのまま使い、指す対象を同じ本文で説明する。
対象、機能、検証手段の有無は、別々の事実として書き分ける。
繰り返す操作の確認では、`agent-toolkit:atk-mode/playbooks/confirmation.md`「繰り返す操作の認可」に照らし、既存の認可と合う質問を省き、未成立の継続範囲だけを候補にする。

## 質問ラウンド

起動元の工程が指定した場面で、相互の理解を深めるために行う。
確認する事項と完了後の工程は起動元に従う。

1. 求められている案・評価・説明を先に返し、回答を前提とする質問はその後に行う。
2. 依頼と合意済みの内容から、未確定の判断、判断どうしの依存、要求間の競合、実現に必要な未指定の値を洗い出す。
   現物、仕様、既存の回答で調べて分かる事項は確定し、残りへ`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」を適用する。
   目的が複数あることだけでは確認の理由にせず、互いに衝突する目的など本人の選択が残るものを、候補と推奨を示して確認する。
3. 判断ごとに独立した質問を作り、他の未回答に依存せず答えられる質問を同じラウンドで出す。
   本人にしか分からない基準は、抽象的な好みでなく、成功・失敗と感じる具体的な利用例、避けたい結果、競合する価値の優先順位から尋ねる。
   質問数に固定の上限は無く、ホストの上限に従う。
4. 回答から依存を更新し、その回答を前提とする質問を次のラウンドへ進める。
   別の質問文に載せた例示へ異論が無かったことを、その変更への合意として扱わない。

### 終了条件

元の依頼が求めた案や説明をユーザーへ返し、確認が必要な未回答事項と、その回答に必要な未調査の事実がどちらも残っていない状態で終える。
ユーザーが切り上げを求めた場合は、残る不確実性と許容される暫定の結果を分ける。
切り上げや「十分」という表現で、未取得の認可や必須の要件を承認済みに変えない。

### 終了時報告

自分で確定した事項のうち、合理的な別の判断もありうるものを、ラウンドの終了時にまとめて報告する。
書式は`agent-toolkit:atk-mode/references/report-formats.md`「作業完了報告のフォーマット」の`### 自ら確定した判断`に従う。
この報告は承認を求めるものでなく、報告の後は起動元の工程へそのまま進む。

## 質問の形式

Codexで、条件に合う構造化質問が使えない場合に限り、次の固定形式で質問を示す。
質問が複数ある時も、質問ごとに同じ単位で区切る。

```text
**Q1** - **<質問タイトル>**: <質問本文。複数段落や複数の選択肢を含めてもよい>
共通前提: <全選択肢が共有する前提と外した案の扱い、および選択肢の評価を左右する技術的事実。いずれも無い場合は「なし」>

推奨: <推奨回答>

---

**Q2** - **<質問タイトル>**: <質問本文>
共通前提: <Q1と同じ内容の区分>

推奨: <推奨回答>
```
