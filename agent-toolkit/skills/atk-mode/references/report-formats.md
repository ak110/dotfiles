# 報告のフォーマット

作業完了報告と、自律モードで保存する報告用UWIの本文の書式を定める。
振り返り結果報告とAWI投入結果報告の書式は`agent-toolkit:atk-mode/references/report-formats-retrospective.md`にある。

報告は、ユーザーが結論と判断に必要な要点（作業結果、未達、対応状況）を短く把握できるように書く。
内容と書式はStop hookの判定の対象外なので、報告を書くメインが送達の前に本書と照らして確かめる。

- 原因分析、調査の経緯、AWIのH1タイトルと重なる概要は、AWIや証拠記録の側に書く。
- 確定した観測の根拠、未確定の照会・再現の状況、理由が残る事項、未達は要約して残す。
- 送達の前に各文が加える情報を確かめ、依頼や起動した手順から既知の工程説明を省く。
  登録が成功した時の後続実装の説明もこの基準で扱い、未達、失敗、制約、予想との差は残す。
- 本人に求める判断はユーザー確認の本文で示し、報告には決まった結果と根拠、未達がある場合はその範囲を記す。
- ユーザーの対応が必要な未完了事項は、`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」で個別UWIの要否を判定し、保存した場合は既存の見出し（`### 投入したWI`など）で所在を書く。
- 自明な取得、再実行、実機確認の手順の案内は、成果や検証結果に添えてよい。
- 見出しは規定の構成を使い、判断や行動を促す独自の見出しを足さない。

## 作業完了報告のフォーマット

元の作業の結果を次の書式へ1回集約して届ける。
局所工程の成功の要約を別の最終応答にせず、この本文へ含める。
非同期の振り返りの開始と完了はこの報告の前提にせず、実施済みの内容と未達を書く。

```text
## 作業完了報告

<ユーザーがその依頼で知りたかった答えを1文で>

### 成果

- <元作業に対する成果>

### 検証結果

- <対象>: <結果>（記録: <実際の識別子または所在>）

### 投入したWI

- <ファイル名>: <H1タイトル>
- <ファイル名>: <H1タイトル> (target_repo=<...>)
```

- 冒頭: 元の依頼の目的への答えを、工程や件数より先に書く。
  後続の工程に委ねる成果は、見込みであることか、今は算出できない理由を書く。
  振り返りの進み具合とは分け、元の作業で確定した結論を述べる。
  途中の報告やツール出力を見ていない読み手が、結論の対象と未達の範囲を本文だけから区別できるようにする。
- `### 成果`: 元の依頼の要求単位に対応させ、途中報告で伝えた成果も含めて、最終報告の成果全体を1件1行で書く。
  最終報告を届けた後の補足では、新しい結果と訂正だけを書き、報告済みの成果・未達は繰り返さない。
  別の事象への処置は区別して書き添える。
  形式上の完成条件によらず、要求単位で未達の事項は結果と理由を書き、協調モードではその場で伝える。
- `### 検証結果`: 本書「検証結果と実行記録」に従って、各結果と参照先を書く。
  観測した結果と推論、未検証の範囲を区別し、判断に使う主張には再取得できる根拠を添える。
  取得できなかったものの説明は、結論や残工程に影響する範囲に限る。
  検証した項目が無ければ「未実行」と書く。
- `### 投入したWI`: このセッションで報告の前に投入したWI（AWIとUWI）のうち、報告の時点で終了していないものを書く。
  処理対象として取得した項目と、`adopted`・`rejected`で完了した項目は除く（ユーザーが終了時に確認済みのため）。
  報告の直前に、投入した全ファイル名を`atk wi show <ファイル名>... --summary-only --target-repo=<対象リポジトリの絶対パス> --skip-pull`へ渡す。
  出力の`### <ファイル名> [<状態>]`の行で状態を確かめ、続く行からAWIのH1タイトルか、UWIの質問本文の先頭行を取る。
  ユーザーに委ねた判断や行動を保存した個別UWIの所在も、ここで伝える。
  `target_repo`が現在の対象リポジトリと違う場合だけ、末尾に半角空白1つと`(target_repo=<正規化リモートURLか絶対パス>)`を足す。
  該当が0件なら`- なし`とする。
- 途中報告で`予定`とした改善点の確定結果: `済`のうち新しく投入した項目は`### 投入したWI`へ、再利用した既存項目と`不要`は`### 成果`へ`- 改善点<対象>: <既存項目のファイル名または不要の理由>`として書く。
  確定できない対象は、`### 成果`の未達として理由と残工程を書く。
- `### 自ら確定した判断`: ユーザーに尋ねずに確定した判断のうち、別の合理的なエージェントなら違う判断をしうるものだけを、`### 成果`の後に、ユーザーが異論を持ちそうな順で次の書式で書く。

```text
### 自ら確定した判断

- **決定**: <エージェントが選んだ内容>
  - **理由**: <なぜそれを選んだか>
  - **最有力の対案**: <選ばなかった中で最も有力だった案>
```

- 要求の範囲を定める決定は、`agent-toolkit:atk-mode/playbooks/user-utterance.md`「原文の保持と取り込み」の範囲記録の書式で書く。
- 文書と既存コードの不一致のうち、文書を直さずに残したものは、従った側とともに1件ずつ書く（文書を直したものは`### 成果`へ書く）。
- 未検証の仮説や未確定の原因を理由に対策を見送った判断には、検証AWIのファイル名か、その仮説が対策の採否を左右しない理由を添える（仮説と確かめ方は`agent-basics:bugfix/references/causes.md`「観測と推測の区別」）。
- 仕様として確定した解釈でも、外部から観測される結果を変える選択は、成果欄に結果を書いた場合も判断欄へ理由と対案を書く。
- 判断欄は承認を求めるものではなく、報告の後に承認を待たない。
  後日ユーザーが異論を示したら、その判断と、それを前提にした後続の判断を更新する。
- 判断欄へ記録する前に、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」を適用し、ユーザー固有の判断が必要な値が残れば、報告で確定扱いにする前に確認する。

## 検証結果と実行記録

結果の3値（検証済み、未検証、判定不能）は`agent-toolkit:atk-mode/playbooks/verification.md`「完成条件証拠の検証記録」の定義を使う。
未実施と未確認の範囲は、実施した検証と分けて理由を書く（`agent-basics:check-execution`の工程5）。

- 検証結果の行には、対象と合否に加えて、実際に返されたpyfltrの`run_id`、外部コマンドの終了ステータスと保存した標準出力・標準エラー出力の所在、または保存した手動観測の記録の所在を添える。
  手動観測の記録は読者が開ける所在を書き、渡せなかった場合はホスト名とパス、開けないこととその理由を書く（`agent-basics:verify-skill`「生成するスキルの節」の証拠の引き渡し）。
  報告WIの添付を使う場合はWIファイル名と添付名で示す。
  private-notesの履歴へ保存できる証拠に限る。
- 検証の結果と参照先は、協調モードでは作業完了報告、自律モードでは報告用UWIに書く。
  振り返り結果報告とAWI投入結果報告で検証結果に触れる時も同じにする。
- 記録の取得と保存出力の読み方は、`agent-toolkit:atk-mode/playbooks/verification.md`「統合実行ツール経由の起動」「保存した実行出力の取得」に従う。
- 送達の前に、保存した記録を実際に読み、具体的な対象、入力、操作、観測結果、終了ステータスか合否に基づいて書く。
  記録ファイルの存在は内容の正しさを示さないので、判定行を参照する場合も元の実行・観測記録まで辿れることを確かめる。
- 識別子は、前方一致や`latest`などの指定ではなく、実際の値で書く。
- 記録の無い検証は未実行として書く。
  開始後の失敗、タイムアウト、観測対象への未到達は、保存した記録に基づいて区別して書く。

### 検証記録の引き渡し

実際に取得した`run_id`、保存したログ、手動観測の記録は、完了報告を送る前の確認へ渡す。

## 報告用UWIのフォーマット

報告用UWI（`agent-toolkit:atk-mode/playbooks/report-completion.md`の手順6）の`## 選択肢と帰結`は、`agent-toolkit:atk-mode/references/uwi-format.md`「承認型ごとの内容」の事後承認型の2択とする。
冒頭の問いには次の1文を使う。

```text
<実行日>の<対象リポジトリ名>の作業結果について、この対応で問題ありませんか？
```

問いに続けて、確かめてほしい項目（未達・持ち越し、自ら確定した判断の有無）と答え方、成果の要点を1〜2文で書く。
操作を依頼しない報告にコマンドは不要であり、別のUWIで操作を案内する場合は手順を重ねない。
冒頭の語句は`agent-toolkit:atk-mode/playbooks/wi-drafting.md`「ユーザーが読む部分の合格基準」で選ぶ。

`## 判断材料`には、該当する項目がある場合だけ、次の順でH3を置く。
会話を転記せず1件1行の要点にまとめ、同じ内容を複数のH3へ重ねない。

1. `### 未達・持ち越し`: 元の要求単位の未達、未解決の問題、先送りした事項を`- <対象>: <残った状態>（理由: <理由>、再開条件: <条件>）`で書く。
   予定した改善点の処置を確定できない場合もここに置く。
   再開条件が未定なら省く。
   ユーザーの判断や対応を待つ項目は、保存した個別UWIのファイル名を再開条件に書く。
2. `### 処理中のご指摘への回答`: `- <指摘・質問>: <回答・対応結果>`で書く。
3. `### 曖昧な要求の解釈`: `- <元の要求>: <採用した解釈>（理由: <採用理由と判断根拠>、範囲: <対応範囲>、結果: <実施結果とエンドユーザーが観測する結果>）`で書く。
4. `### 自ら確定した判断`: 作業完了報告と同じ対象を`- <決定>（理由: <理由>、最有力の対案: <対案>）`で、異論の出やすい順に書く。
5. `### 成果`: 処理したWIごとに`- <ファイル名>: <H1タイトル>（<達成した結果>）`を1行ずつ書き、タイトルと重なる内容は省く。
   公開やリリースなど、WI単位に収まらない成果は1行で書き添える。
   新規登録したWIは本書「作業完了報告のフォーマット」の「投入したWI」と同じ方法で所在を確かめ、未達・振り返りに当たらないものを成果に置く。
   途中報告で予定した改善点のうち、実施した処置と不要と判断した理由も成果に置く。
   使い方が変わる変更では、案内のUWIを登録済みか、リリース後に登録する予定かを1行で示す（`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「使い方が変わる変更」）。
   検証結果は本書「検証結果と実行記録」に従い、対象、結果、参照先の行を同じH3に添える。
6. `### 振り返り`: 手動かbatchで振り返り自体を実施した報告に限り、`agent-toolkit:atk-mode/references/report-formats-retrospective.md`「報告用UWIの振り返りの行」の行を書く。
   通常作業の報告では、非同期の振り返りの未実施を記載の対象から外す。

`### 曖昧な要求の解釈`には元の要求と解釈の対応を、`### 自ら確定した判断`には選んだ理由と対案を、`### 成果`には実施の結果を置く。
両欄を比べ、成果欄だけに残った解釈の選択が無いかを確かめる。

## 報告用UWIの確認と保存

本節は`agent-toolkit:atk-mode/playbooks/report-completion.md`が定める報告用UWIに適用する。
通常の事後承認型UWIには共通の起草手順を適用し、`--question-type=post-approval`だけでは報告用と判定しない。
通常WIの共通起草の3資料は、報告用だけの保存のためには取得しない。
由来、認可、保存先、回答済みUWIとの整合は、`agent-toolkit:atk-mode/playbooks/wi-saving.md`の該当する操作の契約に従う。

1. 元の要求と実施結果・根拠を比べ、未達、未確認、持ち越しを成果と分ける。
   事実、他者の報告、推測、自分の判断を分け、未確定のユーザー固有の判断は確認の手順へ渡す。
2. 原稿をファイルへ保存し、dry-runで検証する。
   新規は`atk wi add --type=uwi --question-type=post-approval --dry-run --body-file <原稿の絶対パス> --source <起動スキルに対応するsource>`を使う。
   更新は`atk wi edit <UWI名> --dry-run --body-file <原稿の絶対パス>`を使う。
   sourceは`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と`source`」に従い、原稿のfrontmatterで指定済みなら`--source`を省ける。
   入力の原稿、抽出の保存先、終了状態、両出力を対応付け、検証か抽出の保存に失敗した結果は使わない。
3. dry-runの抽出を先に読み、確かめてほしい項目と答え方が冒頭だけで分かるかを、`agent-toolkit:atk-mode/references/uwi-format.md`「構成」で判定する。
   次に全文を読み、同書「載せる情報」「ユーザーへ操作を依頼する場合」のうち該当する基準と、`agent-toolkit:atk-mode/references/awi-body.md`「通常AWIの本文」の自己完結、節の間の重複を確かめる。
   一致は同じdry-runに`--compare-opening-file <抽出の絶対パス>`を付けて、改行、前後の空白、末尾の空行を含む完全一致で判定する。
   原稿を変えたら手順2へ戻り、新しい抽出で確かめる。
   本保存へ同じ指定を付けると、一致した時だけ保存する。
4. `agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入と取得」に従って保存し、保存本文の一致、終了コード0、成功メッセージと警告を検収する。
   表記の警告は該当行を確かめ、それ以外の警告とエラーは直す。
   失敗した時にファイル名を取得済みなら、同じUWIを`atk wi edit --body-file`で直す。
   未プッシュの通知は既存の投入手順で反映し、保存の成功と警告の検収を終えた時点で伝達を完了とする。
