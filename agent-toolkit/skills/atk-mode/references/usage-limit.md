# 利用上限の予告・猶予通知への対応

利用上限が近いことを示す予告と、到達後の猶予通知を受けたメインエージェントの保存と続行、解除後の再開を定める。
利用上限やサーバー側の一時的なAPIエラーによる中断の後に自動で始まったターンも、本書で再開情報を取得し、最初の未完了の工程から続ける。

利用上限の通知と解除後の再開に関する観測記録がある。
詳細は`docs/development/audit-records-usage-limit.md`にある。
該当節は「agent-toolkit/skills/atk-mode/references/usage-limit.md：利用上限後の再開：2026年10月14日」である。

Claude Codeのメインエージェントでは、agent-toolkitの`hooks/usage_limit_resume.ts`（Function hooks module。[mods API](https://code.claude.com/docs/en/plugins/mods/api)）が、利用上限に当たった時に同じ会話への再開プロンプトを予約し、解除予定時刻の後に投入する。
Remote Controlの接続中と非接続時のどちらも対象であり、`agents_server`の委譲先と、`agentId`を持つサブエージェントのターンは対象外である。
別のターンが始まると予約は取り消される。
`atk wi process-loop`が起動した統括と`atk run-skill`の会話では予約しない。

`StopFailure`の`error`が`server_error`の場合も、同じ会話への再開を予約する。
連続する自動再開の待ち時間は1分、5分、15分とし、3回再開しても失敗した場合は停止を画面に表示する。
サーバー側の一時的なAPIエラー以外でメインターンが終わると、連続回数をリセットする。
利用上限の予約と重なった場合は利用上限を優先し、解除後に一度だけ投入する。
中止されたターンからは予約しない。
認証エラー、課金エラー、原因不明などは自動再開の対象外である。
予約はセッション内のタイマーであり、モジュールの再読み込みやCLIの終了で失われる。

## 常駐から起動された統括の保存と再開

`atk wi process-loop`が起動した統括は、予告か猶予通知を受けた時点で、本書「利用上限の猶予通知を受けたときの続行と再開」の再開情報を保存し、通常どおり工程を続ける。
未完了を完了として保存しない。
利用上限を理由に、対象の範囲を縮めることと、未検証の成果を急いで公開することはしない。

利用上限は会話ごとの枠とは限らず、同じアカウントの次の起動も影響を受ける。
Claudeの統括は、起動元が同じ会話の利用可能な接続を選び直して再開し、代替が無ければ解除予定時刻まで待つ。
Codexの統括が上限で終了した時は、次の巡回の可用性の判定と保存済みの作業資源から再開する。
利用可能な候補が無ければ、起動元が解除予定時刻（不明なら再確認の時点）まで待つ。
CLIが終わると会話内のタイマーによる予約も失われるため、同じ会話を再開できない時は保存した再開情報、レーンの所有登録、WIキューから再開する。
巡回の更新と明示のresumeの扱いは`agent-toolkit:atk-mode/playbooks/process-wi-all-repos.md`「登録集合」にある。

## 利用上限の猶予通知を受けたときの続行と再開

猶予通知はClaude Codeが会話へ挿入する`[Usage limit reached; a short grace allowance remains`で始まる注記である。
ホストの挿入注記として扱い、通知が無い時と同じく本来の工程を続け、仕上げ、検証、公開、完了の報告、振り返りなど、依頼の達成に必要な後続の工程を保つ。
通知の後も権限とツールの利用契約を守り、ホストが強制終了した時は中断として扱い、ユーザーの明示的な中止の指示には従う。

1. 再開情報を保存する。
   保存先は、既存の引き継ぎ記録、無ければ`agent-toolkit:atk-mode/playbooks/managed-temp.md`で確定したセッションのmanaged-tempの中のMarkdownファイルとする。
   目的、承認の内容と出所、対象のworktreeの絶対パス、成果物の絶対パスかcommitのハッシュ、完了した工程と検証結果、取り下げた手段と理由、順序付きの未完了の工程と次の一手を書く。
   強制終了の後は書き込めないため、通知を受けた時点で保存し、工程が進むごとに更新する。
2. 通知を受けた時点で、完了済みの成果、未完了の工程、打ち切られた時の再開位置、再開情報を保存した絶対パスをユーザーへ報告する。
   解除後の再開はFunction hooks moduleかホストが自動で起動するため、この報告でユーザーへ再開の指示を求める必要は無い。
3. `agents_server`で`api_error.type`が`usage_limit`になった委譲先は、制限の解除後に同じセッションで自動的に処理を再開する。
   バックグラウンドの`atk agents wait`や定期確認のタスクはそのまま保ち、停止の要否は`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「停滞の検知と巻き取り」で判定する。
4. 猶予通知が示す「実行中のサブエージェント」は、同じ会話で`Agent`ツールを使って起動した委譲先を指す。
   独立したセッションで動く`agents_server`の解除待ちには、その停止の案内を当てない。
5. 中断の後に、ユーザーの再開指示、Function hooks moduleの再開プロンプト、ホストの自動継続のどれかを受けたら、保存した再開情報を読む。
   記録された成果が現在のファイルの実態と一致するかを確かめ、得ている承認と成果に基づいて、最初の未完了の工程から再開する。
   主成果物が確定した後に完了処理が残る時は、`agent-toolkit:atk-mode/playbooks/report-completion.md`の適用条件と「工程」の再開条件で、元の適用内容と未完了の工程を引き継ぐ。
   保存先や承認の情報を復元できない時は、足りない情報をユーザーへ確認する。

## 組織向け設定

組織の管理設定で`classic.`のFunction hooksイベントが省略される環境でも、利用上限（`rate_limit`）とサーバー側の一時的なAPIエラー（`server_error`）は記録される。
`StopFailure`のコマンドhookが記録を残し、`turn.complete`が読み取って再開を予約する。
