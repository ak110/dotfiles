# UWI本文の書式

UWIの本文は、ユーザーが対象ファイルや他のキュー項目を参照しなくても、単体で判断できる内容にする。

## 構成

本節は質問のUWIに適用する。
報告用UWI（`--question-type=report`）は保存時に`adopted`となり、質問・回答欄を持たず、未回答の一覧と選定の対象に入らない。
本文は`agent-toolkit:atk-mode/references/report-formats.md`「報告用UWIのフォーマット」に従い、問い、答え方、選択肢、`## 選択肢と帰結`を書かない。

冒頭に、ユーザーが何を判断し、どう答えるかを短く書く。
判断を尋ねる問いは疑問文（1文を推奨）にする。
操作が必要なら、対象環境と最初にすることも冒頭に置く。
理由、推奨とその根拠は要点だけを続け、確認だけなら操作を加えない。
表題（H1）は、質問なら問いを含む文、報告用UWIなら`報告:`で始める文にし、一覧で区別できるようにする。
確認の対象は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。
1件のUWIで扱う問いは1つにする。
互いの選択肢や結果に影響しない問いは別のUWIへ分け（事前承認型では、それぞれに同じ元項目のファイル名を持たせる）、影響し合う問いは組み合わせを選べる1つの問いにまとめる。
複数の項目を共通の基準で一度に問う場合は、採否の分かれ目となる差分、項目ごとの採用・不採用の結果、推奨方針と根拠を示し、共通の情報は1か所にまとめる。

回答形式は、`--question-type=choice`と`--choices`（各選択肢の短い名前）で指定するか、二者択一の可否なら`--question-type=yes-no`を使う。
同じ値を本文のfrontmatterにも置いた場合は引数にそろえて保存し、不一致は拒否する。
続けて`## 選択肢と帰結`を設け、選択肢と、それぞれを選んだ場合に生じる結果を書く。
値の指定やログの貼り付けのように選択肢を網羅できない回答でも、回答欄への記入方法や、確認できない場合の扱いを選択肢として示す。
自由記入の回答欄は選択肢の後ろに加えられる。
末尾には`## 判断材料`を置き、返信形式の細部が必要な場合はここに書く。
本文の見出しはH2までにする（報告用UWIだけは、`agent-toolkit:atk-mode/playbooks/report-completion.md`が定めるH3を`## 判断材料`の内側に置ける）。
`## 回答方法`の節は設けない。
ブラウザーの画面がfrontmatterの情報から選択肢を表示するためである。
保存形式の`## 質問`・`## 回答`の外枠は`atk`が付けるため、本文には質問の内容を書く。

問い、選択肢、選択肢ごとの結果の根拠は、実在する属性・選定条件・依存・冷却期限・公開コマンドなどを観測で確かめてから書く（確認の問いと選択肢の組み方は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認の選択肢を組む手順」）。
キューが処理環境を区別しない場合は、別環境のprocess-wiへ処理を回す選択肢を示さず、必要な観測結果をユーザーが回答へ記入する選択肢を使う。
別環境での作業を依頼する場合も、その回答で同じ環境の巡回から元AWIが外れると説明するには、実在する選定条件の裏付けが必要になる。

## 載せる情報

本文に書く情報は、回答、是正の依頼、結果の把握、依頼された操作の実行に役立つものに限定する。
判断の理由、推奨、選択肢ごとの重要な結果、操作を止める条件、必要最小限の返信だけを書く。
内部の再開工程や作業手順、調査の途中経過、本文内の重複、ユーザーが手動で取り消すための手順やコマンドは省く。
是正は回答を受けたエージェントが担うため、取り消せるかが判断に必要な場合は、その性質とエージェントが是正を担う事実だけを書く。
回答待ちの再開情報は`agent-toolkit:atk-mode/references/answer-transitions.md`「回答待ちの再開情報」に従う。
本文の語は、原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）に従ってユーザーが既に知っている語にする。
内部の状態は、何が完了し、何が残り、回答で何が変わるかで書く。

`## 判断材料`に書く事実は、投入前の観測か一次資料で裏付ける。
起草者が自分で調べて確かめられる事項は先に確かめ、ユーザーの手元の環境の状態など確かめる手段が無い事項だけを、未確認と明記して回答の前提から外す。
過去の記録の理由を問われた場合は元の判断まで遡り、ユーザーの要件や合意事項、独立した観測結果や公式資料、エージェントの推測を区別して説明する。
推測だけに基づく判断は、主体と根拠の限界を示して是正を推奨し、明示の判断や独立した観測結果を持つ記録は、作成者によらず元の根拠で評価する。
推奨する方針は、冒頭の問い、判断材料、選択肢ごとの結果の間で一貫させる。
是正する内容は元の要求に照らして確定し、確認の要否は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従う。

資格情報を見つけた旨を報告する場合（`agent-toolkit:atk-mode/references/conduct.md`「完遂と先送り」が報告の対象とする値に限る）は、認証情報の値を再掲せず、所在と種類を短く示す。
所在は、リポジトリ内のファイルなら正規化したリモートURLとリポジトリ相対パスで、外部の環境ならイメージ名やファイルの絶対パスで書く。
所在ごとの重複の確認と報告用UWIの扱いは`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」に従う。
資格情報の失効や削除の要否と時期はユーザーの判断に任せ、具体的な操作手順や完了確認の回答を求める記述は省く。

## ユーザーへ操作を依頼する場合

ユーザーへ操作を依頼するのは、エージェントが実施できない場合に限り、その理由を示す。
実行環境が拒否した権限は、確認への承認だけで上書きしない（原則4。`agent-basics:writing-standards/references/quality-principles-constraints.md`）。
原稿を書く前に、既存の引き継ぎや対応結果を使い、必要な環境ごとに操作を振り分ける。
対象環境はユーザーの規範と設定、到達可否は実行時の状態、認可は既存の規範と承認情報で確かめる。
検証対象OSの設定の用途は検証範囲の判定に限る。

- 実施済み: 対象・版・条件が合う実施結果を使い、再度依頼しない。
- エージェントが実施: 到達可能で認可済みの操作を実施し、結果を引き継ぎか対応結果へ残す。
  実施済みへの変更には実施結果が必要である。
- 認可待ち: エージェントが行う案を推奨して初期選択にし、操作をユーザーへ転嫁しない。
  承認後に行う操作と影響を示し、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」へ渡す。
- 到達不能: 到達できる環境と試験・CIの結果で判定し、到達できない環境の結果を得るためだけの確認は依頼しない。
- 本人専用: 本人にしか行えない操作のうち、その結果で対処が変わるものだけを理由付きで依頼に残す。
- 操作不要: 依頼に含めない。

保存担当は原稿の各操作を環境別の振り分けと実施結果に対応付け、本人専用のために残る操作だけを理由付きの依頼として保存する。
レーンの原稿を実施結果の代わりにせず、実施に失敗した場合は結果と残る前提から振り分け直す。

元WIの完成条件の観測を依頼する場合は、起草者が元WIの現行本文、有効な変更要求、再開記録を取得し、必要な結果を確定してから手順と返信形式を組む。
結果ごとの既存の証拠、残る操作、手順と回答項目の対応は、既存の成立性の証拠や引き継ぎ記録へ残す。
既存の証拠は、対象・版・観測条件を現行の要求と比べて適用できるものを使い、それで満たす結果は再び依頼せず、本人にしかできない残りの観測だけを依頼する。
同じ操作で複数の必要な結果を確かめられる場合は一連の依頼へまとめ、各結果を返信で回収できるようにする。
再開記録、配備後の結果、依頼の変更で残る観測が変わった場合は、過去の原稿や記憶から補わず、現行の原本と証拠から更新する。
保存の前に、`agent-toolkit:atk-mode/references/draft-semantic-review.md`「ユーザーが読む部分」に従って、原稿の手順・返信形式を元WIの必要な結果と比べる。

操作の詳細を要する場合は、`## 判断材料`に対象、順序、完了の確かめ方を短く示す。
画面や本人の操作が必要なら、画面名・項目名と操作を示す。
端末で操作する場合は実行する環境と端末を示し、値やパスの差し替え、前の出力からの転記、条件の読み替えをせずに貼り付けて実行できるコマンドを、選択肢や環境ごとに示す。
機械で判定できる適用条件は依頼前に確かめ、ユーザーの環境でしか分からない条件はコマンドで確かめる。
コマンドは同意した範囲から外れると分かった場合や、適用条件を確かめられない場合は変更せずに止める。
返信には後続の作業に必要な結果と、操作できない場合の扱いだけを求める。
資格情報や設定出力全体は求めない。

## 承認型ごとの内容

報告用UWIは、`agent-toolkit:atk-mode/references/report-formats.md`「報告用UWIのフォーマット」「報告用UWIの確認と保存」と、本書の「構成」「載せる情報」で確かめる。
通常の事後承認型UWIには、本書の共通の書き方を適用する。

事前承認型のUWIでは、確認を要する解釈の相違やユーザーだけが持つ情報、各案を採用した場合に対外的に生じる影響、推奨案、回答を待つ元項目のファイル名と対象範囲、必要な回答や資料を`## 判断材料`に書く。
元項目とUWIの対応は、UWIの本文の中だけに記録する。
確認が不要な問いはUWIへ送らず、エージェントが確定する（`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」）。

事後承認型のUWIでは、実施済みの対応の可否を尋ね、投入したエージェントは回答の到着を待たずに元の作業を続ける。
事後承認にする判定基準は`agent-toolkit:atk-mode/playbooks/confirmation.md`「事前承認と事後承認」に従う。
実施済みの対応内容、その方針を選んだ根拠、エンドユーザーから見た影響のうち、回答や是正の依頼に必要なものだけを書き、内部の技術選定の経緯や調査の過程は省く。
環境の制約で確かめられなかった範囲は、実施できた確認の結果とともに報告する。
是正を求める回答への対応は、`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」に従って新しいUWIの登録要否を判定する。
`--question-type=post-approval`を指定し、`--choices`を省いて投入すると、固定の選択肢`その対応で問題無い`と`問題がある`が表示される（通常の`choice`や`yes-no`より優先される）。
`問題がある`を選んだ場合に、希望する是正内容を回答欄へ書くよう促す案内文を添える。

ユーザーの質問に答える事後承認型UWIでは、個々の質問へ`## 判断材料`の中で直接答える。
「なぜその事象が起きたのか」という問いには、発生原因、変更した内容、今後の再発防止策を、段落の冒頭や小見出しで分かりやすく整理する。
冒頭の問いで挙げた説明項目（「理由」「対策」など）は、本文でも同じ見出しや表現で説明する。
