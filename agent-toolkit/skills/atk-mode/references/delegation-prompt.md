# 依頼文と起動入力の形式

委譲の依頼文、追送、引き継ぎ記録先の行の形式を定める。
起動の手順は`agent-toolkit:atk-mode/playbooks/delegation.md`「送信」にあり、本書はその手順から使う。
依頼文は委譲先が受け取る唯一の入力であり、委譲元の会話、読んだファイル、起動したスキルは届かない（forkを除く）。
このため、対象、目的、完了の条件をその文章だけで分かるように書く（原則8、`agent-basics:writing-standards/references/quality-principles-readers.md`）。

## 入力の適格性と追送

初回の依頼文と追送に入れるのは、委譲先が他の入力から得られない次の要素に限る。

- ユーザーの発話の逐語。
  原文と、提案の評価・採否、実施する依頼を分ける。
  未評価の提案や未回答の問いはその旨を明記し、調査・評価の対象としてだけ渡す。
  委譲先は結論と根拠をメインに返し、メインが正式回答を送る。
  原文と出所は`forwarded-user-input`の標識（`agent-toolkit:atk-mode/references/delivery.md`「hook以外で生成する本文の要素」）の内側へ置き、起動前に原文と標識の整合を確かめる。
- 作業の対象と、参照する基準の記録の絶対パスと対象ID。
- 基準の記録に無い目的、要件、制約、完了の条件。
- 全体作業契約が自動で届かない委譲では、担当に該当する暫定規範の項目（従う内容、原本の絶対パスと版、適用・緩和・解除の条件）。
  該当しない軽量起動に契約の入力や本文を求めない。
- 委譲元が実物で確かめた事実と、実行時に確定した値。
  自分で裏付けていない具体値と既存実装の挙動は`未検証`と明記し、着手前の裏付けを指示する。
  ユーザーや他者が示した原因の推定は、出所を添えて`未検証`と明記し、委譲先が確かめる仮説として渡す。
- 役割文書、プロジェクトの規範、適用するスキルが定めていない権限と対象範囲。
  操作の許可と禁止は対象リポジトリと操作を対にして書き、WIや計画を保存するprivate-notesは別の対象として扱う。
- 既存の規範が依頼文へ入れるよう定めた項目（`引き継ぎ記録先`、前提を覆す追送での残す成果と捨てる成果の範囲など）。

役割文書、プロジェクトの規範、適用するスキルが既に決めている手段（commitの分け方、fixupの使用、検証の方法、pushの可否、必須スキルの起動など）は書かない。
二重に指示すると、委譲先はどちらを優先するか決められず、委譲元の誤った指示がそのまま成果物に入る。
手段を書けるのは、ユーザーが指定した場合と、要件の達成にその手段が欠かせないことを実装、公式仕様、実機の検証が裏付ける場合（根拠を添える）に限る。
操作を制限する時は、コマンド名ではなく、操作の目的、対象の資源、状態の遷移で指定し、役割文書が求める状態の遷移と衝突させない。

エージェント向け文書の修正を指示する時は、同じ論点に必要なファイルを一度に全て指定し、節名は所在の手掛かりとして示す。
新しい論点、指定外のファイル、ユーザーが限定した節の変更は、委譲先から委譲元へ判断を戻させる。
作業契約を持つ委譲元は、起動、追送、受領の時に自分の記録と割り当てを照らし、保つ対象と残る完了の条件を担当へ渡す。

追送は内容を確定してから送る。
確定した要件は、依頼の前提（対象、範囲、観測される結果、判断の基準）を覆す場合も、先行の応答を待たずに追送し、残す成果と捨てる成果の範囲を示す。
追送で既存の成果を引き継げない時に限り、実行中の担当を終えて新しく起動する。
稼働中の委譲先を強制的に止めるのは最後の手段とし、失われる書き込み、未着の報告、文脈を確かめ、回収できる成果を全て回収してから止める。

## 委譲プロンプトの構成

1行目に命令、2行目以降に必須の入力を1項目ずつ並べる形で依頼文を組む。

1. 1行目は`<役割文書の絶対パス>の手順を実行せよ。`とし、役割文書もagent定義も渡さない委譲では具体的な命令文1文にする。
2. 2行目以降は、1行に収まる値を`<項目名>: <値>`で書く。
   改行を含む値と、役割文書が構造を定めた値は、`<項目名>:`だけの行に続けて各行の先頭へ半角空白2文字を付けて書く。
   字下げの無い行が現れた所で値が終わる。
3. 入力の値をパス、識別子、実行時に確定した客観的な事実に限る。
   委譲先の文書と規範に既にある手順、権限、検証、返却の形式、背景、経緯、委譲元の途中の推測は入れない（他者が示した原因の推定は本書「入力の適格性と追送」の`未検証`の扱いで渡す）。
   委譲先が自分で判断する余地を先回りして狭めないためである。
   `cwd`とそこからGitで解ける情報、役割文書の省略時の値、他の値から一意に出せる値も省く。
4. 基準の記録で内容が一意に決まる時は、絶対パスと対象IDだけを渡し、手順、合意、調査済みの事実を写さない。
   判断材料が2万文字（目安）を超える時は、managed-tempへ所有者だけが読み書きできるMarkdownとして保存し、絶対パスを渡す。
   複数の委譲先が読む共通の資料は、一度保存して各依頼へ絶対パスを渡す（努力目標）。
5. 改訂中の規範を適用させる時は、作業ツリーの原本の絶対パス、適用する節、版（commitのハッシュか、未commitならその旨と確定した日時）を渡し、委譲先に判断の前に読ませる。
   稼働中のCLI、hook、MCPが読む版と作業ツリーの版を区別する。
6. 指示は対象、権限、完了の条件を明確にし、その枠の中で委譲先が技術の判断をできるように書く。
   目的、保つべき挙動、どこまでで十分か、やらないことを示し、直し方は委譲先に任せる。
   対象外または完了済みのため省くファイル、項目、commit、WI、検証名やコマンドを列挙する。
   委譲元と委譲先の両方が完了を判定できる単位に分けて渡す。
   強調語や例示は字面どおりに範囲や厳密さを広げる根拠になりうるため、使うときは理由と求める程度を添える。
7. 調査と測定の委譲では、結果を読む委譲元の判断に必要な回答の項目を起動前に選び、共通の返却形式で決まらない項目だけを`通常完了の報告様式`で補う。
   後続の処理を分岐させる判定は、結論に加えて分岐の根拠になった観測値（終了コード、該当の行、一致件数、走査した対象、打ち切りの有無）を逐語で返させる。
   件数と行数は、実行した集計コマンドと出力を典拠に返させる。
   削除・撤去・簡潔化を提案させる点検では、候補ごとに、撤去対象が検出している違反、代わりに同じ違反を検出するテストの入力と期待値、双方の本文を確かめた結果を返させる。
   複数の委譲先の能力（ツール、権限、モデル）を比べる時は、同じ照会コマンドを同じ条件で全ての対象へ実行させる。
8. 書き込みを伴う委譲では、書き込みの主体を取り決める。
   委譲先が書く間、委譲元はそのファイルを読み取り専用として扱う。
   成果物は指定した絶対パスへ直接出力させる。
9. 委譲先に適用させる手順のスキル名と、指摘への修正を委ねる時の`agent-toolkit:atk-mode/playbooks/review-fix.md`を、自由本文とホスト組み込みの委譲では本文へ書き、役割の起動では規範の指定を宣言した入力がある時だけその入力で渡す。
   確定したファイル編集を自由本文かホスト組み込みの委譲で委ねる時は、`agent-basics:writing-standards/references/file-editing.md`を適用の条件として書く。
10. 自由本文の起動では、サーバーが`mode`ごとの起動の本文（`agent-toolkit:atk-mode/playbooks/subagent.md`「起動の種類ごとの役割」）を自動で付ける。
    そこにある内容（読み取り専用であること、応答言語、担当の範囲）は依頼文へ重ねない。
    同じ役割への再委譲の禁止は通常起動とホスト組み込みの委譲へ自動で届くので、届かない軽量起動で制限が必要な時だけ本文へ書く。
    `agents_server`を経由しない起動では、ユーザーが読む本文と成果物は日本語で書くことを`応答言語`の入力で渡し、英語の自動挿入の指示を成果物の言語へ引き継がない条件も伝える。
11. 文書、コメント、WIの本文の起草を自由本文で委ねる時は、`<plugin root>/.venv/bin/python -m pyfltr.colloquial <起草ファイルの絶対パス>`の実行と、指摘の解消か解消しない理由の報告を求める（努力目標）。
12. 作業ツリーで実行可能な資源の欠陥を直し、稼働中のplugin rootへまだ反映されていない時に限り、`是正済み資源: <plugin rootからの相対パス> = <作業ツリー側の絶対パス>`の行を資源ごとに入れる。
    同じ行に、直した欠陥と、それが委譲先の工程を止める理由を書く。
13. `shell`で時間の上限（目安は10分）を超えうる複数のコマンドは、コマンドごとにバックグラウンドで実行させ、各終了状態と、一時領域へ分けて保存した標準出力・標準エラーを受け取る。
    同じシェルの状態を共有するために連結する時は、コマンドごとの終了コードを別ファイルへ残すスクリプトをmanaged-tempに置き、その記録の返却を`summary_policy`で指定する。

ユーザーが程度の語（「軽微」「十分」など）で示した基準を判定の条文へ具体化する時に、解釈で結果が変わるなら、判定の対象、主体、時機、除外の形の具体化案を作る。
案の優先がユーザーの判断による時は`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従って確かめてから送り、技術で一意に決まれば確定して送って報告する。

ホスト組み込みの委譲の本文は、要求のJSONをUTF-8で保存し、`atk run-script delegation-prompt -- --input <要求JSONの絶対パス>`が返す`prompt`をそのまま使う。
初回と継続の要求JSONの項目は`atk run-script delegation-prompt -- --help`で確かめる。
`agents_server`の継続の指示は`send_message(session_id=..., instruction=..., extra_params=...)`で送り、初回の値は省いて今回の差分だけを渡す。
定型指示に添える説明は`supplement`で同時に渡す。
必須入力や認可の代わりにはしない。
`send_message`は配送を確定するだけで、相手の応答の完了は`atk agents wait`で観測する。

## 引き継ぎ記録先

役割文書で2つ以上の工程を順に実行する委譲では、依頼文に`引き継ぎ記録先: <絶対パス>（新規）`か`引き継ぎ記録先: <絶対パス>（継続）`の行を入れる。
記録の内容は`agent-toolkit:atk-mode/references/work-contract.md`が定める。

- 最初の担当には`（新規）`、先行の担当の記録を継ぐ担当には`（継続）`を付ける。
  新規か継続かが無いと、委譲先は先行の記録を探すべきかを決められない。
- パスは委譲元のセッションのmanaged-temp直下のファイルとし、自動の回収から外す。
- 役割の`task`と自由本文の`delegate`では行を省いてよく、サーバーが`（新規）`の記録先を用意して`handoff_record_path`で返す。
  依頼文に行を書いた時は、その値が唯一の記録先になる。
- `Agent`ツールなどサーバーを経由しない起動では、委譲元が行を書く。
- 応答の止まった担当の工程を別の担当へ継ぐ時は、前回のパス（省いた時は返った`handoff_record_path`）に`（継続）`を付けて渡す。

`handoff_record_path`は記録先の予約であり、ファイルは委譲先が書く値を持った時に作られる。
`（継続）`でもファイルが無い場合がある。
受領の時に記録を読めればその記載も検収し、不在を確かめた時は書く値が無かったものとして起動の本文、返却、現物で検収する。
それ以外で読めない時は、既存の資料と現物から復元し、復元できない値を未確認として扱う。
