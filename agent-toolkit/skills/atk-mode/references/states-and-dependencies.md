# キューの状態と依存の形式

本書は、WIの保存先、状態、状態遷移、保留、依存、冷却期限、終了、private-notesの扱いを定める。
状態を変えた者がその終了まで持つ原則7と、取り消せない操作の前で止まる原則4の適用である。
原則7の本文は`agent-basics:writing-standards/references/quality-principles-ownership.md`にある。
原則4の本文は`agent-basics:writing-standards/references/quality-principles-constraints.md`にある。
キューは常駐の`atk wi process-loop`、`atk serve`、別のセッションが並行して読み書きするため、状態を変える順序を誤ると、古い本文や未確定の項目を別の主体が処理する。
採用済みAWIの効果記録は`agent-toolkit:atk-mode/references/effect-records.md`「採用済みAWIの効果記録」が定める。

## 状態と依存

WIの保存先は`private-notes/yyyy/MM/<filename>`に固定し、種別と保存状態はfrontmatterの`type`と`state`で表す。
本文は`atk wi show <WIファイル名>`で取得し、保存先の解決はCLIに任せる。
状態を遷移しても、ファイルパス、内部キー、画面のURLは同じ値を保つ。

重要フラグはfrontmatterの`important: true`で表し、キーの省略はfalse、解除はキーの削除とする。
一覧、検索、全件表示、Web画面の一覧では、重要度のフィルター`all`、`yes`、`no`を使える。
重要フラグは通常の`agent-toolkit:atk-mode`の作業`process-wi`の選定、優先度、状態遷移に影響せず、ユーザーが対象集合として明示した時だけ参照する。

選定の優先度は、重要フラグとは別の優先区分（frontmatterの`priority: urgent`と本文の「優先の根拠」節）で表す。
urgentは、処理を後に回すと具体的な損失が続く項目（処理の停止や遮断、誤った判断や成果物、エンドユーザーの環境での継続的な失敗、データ損失の危険など）に限り、観測した影響、観測条件と根拠の所在、解除条件を示せる時だけ付ける。
バグという分類や改善の期待は、損失の根拠から外す。
起票時はWI投入担当が、処理中に新たな影響や解消を観測した時は処理担当が、`atk wi set-priority`で付与、更新、解除する。
区分の無い項目は通常の扱いとする。
処理可能な候補は全件を選び、処理可否と順序は`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`に従う。

## 状態と一覧集合

| 分類 | 値 | 意味 |
| --- | --- | --- |
| 保存状態 | `inbox` | 次の処理主体による取得を待っている。依存が未解決なら`blocked`と判定する |
| 保存状態 | `processing` | `agent-toolkit:atk-mode`の作業`process-wi`などが取得し、処理を進めている |
| 保存状態 | `hold` | ユーザーかエージェントが編集中のため、自動処理の対象から外れている |
| 保存状態 | `adopted` | 採用した要求の実施が完了した |
| 保存状態 | `rejected` | 全ての要求を採用しないことが確定した |
| 導出判定 | `ready` | 全ての依存先が終了し、UWIの回答、metadata、計画が有効で着手できる |
| 導出判定 | `blocked` | 依存の未完了、cooldownの未到来、metadataの不備で着手できない。回答が未保存のUWI自身も`blocked`とする |
| 一覧集合 | `active` | `inbox`、`processing`、`hold`の総称。未終了の項目を一覧する範囲 |
| 一覧集合 | `processable` | `inbox`と`processing`の総称。着手できるか（`ready`）は個別に判定する |

今処理すべき項目の重複は、`active`の項目の本文同士を比べて確かめる。
過去の同様の要求は、`--state=all`で終了済みの項目も含めて取得して確かめる。
`agent-toolkit:atk-mode`の作業`process-wi`は`processable`の項目だけを候補の選定、優先度の評価、依存の判定、個別指示の読み取りの対象にする。

## 状態遷移

エージェントが実行できる遷移は次のとおりである。
ユーザーはブラウザーのUIから任意の状態へ遷移できる。

| 遷移 | 操作 | 実行する主体と契機 |
| --- | --- | --- |
| `inbox`→`hold` | `atk wi hold` | 項目の修正が必要と判断した主体。ユーザーの回答待ちには使わず、本書「承認型UWIと元項目」の依存で表す |
| `processing`→`hold` | `atk wi hold --state=processing <ファイル名>` | 項目を処理しているセッションが、本文の修正が必要と判断した時点。エージェント環境では`--state=processing`が無いと失敗する |
| `hold`→`inbox` | `atk wi unhold` | 項目を修正した主体が、保存した本文の一致を確かめた時点 |
| `inbox`→`processing` | `atk wi start-processing` | 項目の作業に着手する主体が、開始の契機によらず着手の時点で先に実行する。対象は通常のAWI、作業を伴う回答済みUWI（是正を求める回答が保存された事後承認型UWIと、元項目での追加作業を求める回答済みの事前承認型UWI）、依存の解消や`unhold`で`inbox`へ戻った元項目である。開始の契機は`agent-toolkit:atk-mode`の作業`process-wi`の選定、中断した実行の再開、実行中の回答の反映、`agent-toolkit:atk-mode`の作業`process-wi`の外での回答の反映を含む |
| `inbox`→`adopted` | `atk wi adopt` | `agent-toolkit:atk-mode`の作業`process-wi`のメインエージェントが、回答済みで未終了のUWI（是正要求を含まない事後承認型を含む）を、AWIの処理を始める前に終了する時 |
| `processing`→`adopted` | `atk wi adopt` | メインエージェントが回答済みUWIを終了する時と、作業レーンがマージの完了後かコード変更を伴わない要求充足の確定後にAWIを終了する時。実装commitはcommitごとに`--commit <OID>`を渡し、補足は`--note`か`--note-file`に書く。コード差分の無い充足では`--commit`を省き、充足の根拠を処理結果に書く |
| `processing`→`rejected` | `atk wi reject` | 計画工程で確定した全要求の不採用を、メインエージェントが確かめた後にレーンが実行する |
| `hold`→`adopted`か`rejected` | `atk wi adopt`、`atk wi reject` | 保留中の項目の採否が確定して残作業が無い時に、採否を確定した主体が`unhold`を実行せずに直接終了する（`unhold`すると、終了の前に`atk wi process-loop`が取得し得る） |
| `processing`→`inbox` | `atk wi return-to-inbox` | 上流リポジトリへ投入したAWIの終了を待つ項目をキューへ戻す時（`agent-toolkit:atk-mode/references/cross-repository-submission.md`「上流リポジトリへの投入と元項目」）と、本書「承認型UWIと元項目」の依存を保存した後 |
| `adopted`か`rejected`→`inbox` | `atk wi return-to-inbox --state=<adoptedかrejected>` | 誤って採否を確定した項目から過去の処理結果を除き、再処理のためにキューへ戻す時 |
| `adopted`か`rejected`→`hold` | `atk wi hold --state=<adoptedかrejected>` | 誤って採否を確定した項目から過去の処理結果を除き、確認や修正の間保留する時 |

会話を解決できるエージェント環境で`atk wi start-processing`を実行すると、最上位の会話とホストを`processing_owner`へ記録する。
レーンからの操作も統括の会話を使う。
remoteを設定した環境でエージェントが`adopt`、`reject`、`return-to-inbox`、`hold`する前に最新の状態を取得して担当の有無を確認する。
取得できない場合は失敗する。
担当付きの項目は担当の一致を確かめてから送信まで終える。
担当が違う場合は失敗する。
担当が一致していても、共有先がある担当付きの項目をエージェントが終了する場合は`--skip-push`を指定できない。
人の操作と担当欄が無い旧項目では担当の一致を求めない。
担当を移す時は`atk wi take-over <ファイル名>`を使う。
同じホストでは会話が終了している記録が必要。
別のホストでは前の担当が停止したことを確かめ、確認方法を`--reason`へ渡す。

同じ遷移、メモ、commit、対象リポジトリで終了できる複数の項目は、個別に確かめたファイル名を並べて1回の`atk wi adopt <ファイル名>...`か`atk wi reject <ファイル名>...`で終了する。
効果確認を指定する採用をまとめるには[効果確認](effect-records.md)の判定と理由もそろえる。
実装commitの対応記録の保存、取得、補完は`agent-toolkit:atk-mode/references/commit-wi-records.md`「WI実装commitの対応」に従う。
終了後に履歴を書き換える時は`plan-rewrite`で対応commitと件名を付け替え、採否の結果と処理日時は保つ。

## 保留と本文修正

既存のWIの本文を直す必要が分かった時点、または対象と根拠が明確な懸念を受けた時点で、採否の確定や調査を待たずに`atk wi hold <ファイル名>`を実行する。
保留しないまま時間を置くと、別の処理主体が古い要求内容で作業を始め得る。
保留は、後で元に戻せるかによらず、必要が分かった時点で行う。
`atk wi hold`が失敗した時は、その項目を未保留として扱う。

失敗例: 既存のAWI2件の更新を求められ、関係する調査を終えてから`atk wi hold`を実行した。
調査の間、2件は自動処理の取得候補に残っていた。

1. 保留の期間は、調査、認識合わせ、修正案の起草から、保存した本文の一致を確かめて`atk wi unhold`を実行するまでの全工程である。
2. 編集のために保留した項目は、修正、保存した本文の検収、`atk wi unhold`を独立した他の作業より先に進め、保留の時間を最小にする。
   修正の採否や内容を決めるための他の項目の調査は先に行い、修正に関係しない全件の調査や別の要求の作業は解除の後に回す。
3. 修正にユーザーの判断や外部の入力が必要な間は、保留と再開の条件を保ったまま、回答に依存しない作業へ進む。
4. 既に`hold`の項目は、保留を保ったまま修正と検収を進める。
5. 誤って投入したと確認できた項目は、`atk wi rm`で削除する。
   エージェントが削除できるのは`inbox`と`hold`の項目で、ユーザーはブラウザーのUIから終了済みの項目も削除できる。

本文の編集は`inbox`、`processing`、`hold`のどの状態でもできる。
ただし、別のセッションが処理している`processing`の項目は、保留も本文の置き換えもせず、変更後の要求を新しい項目として投入する。
状態を確かめた後に別の主体が`processing`へ遷移させて`atk wi hold`が失敗した場合も同じである。
エージェント環境の`atk wi edit`は`processing`の項目の本文全体の置き換えを受け付けず、既存の項目へは`--append`で追記だけを行う。
追記は`## 処理結果`の後ろに、元の要求内容と分けて保存される。
ユーザー自身の操作は、この制限の対象外である。

## 承認型UWIと元項目

1. 事後承認型UWIは、元の作業の進行を妨げないため`depends_on`へ加えず、元の項目はユーザーの回答を待たずに終了する。
   `question_type: post-approval`のUWI（保存済みの標準的な2択の`choice`を含む）へ`その対応で問題無い`だけが回答された時は、`atk wi answer`と`atk serve`が回答の保存と同時に項目を`adopted`にする。
   `yes-no`形式の回答、否定的な回答、追加の記述を含む回答は回答済みのまま残り、通常の手順で取り込む。
   是正を求める回答は、`agent-toolkit:atk-mode/references/origin-and-approval.md`「ユーザー専用の記入欄と是正要求」を適用し、新しいAWIを起票せずに、そのUWI自身を作業要求として処理する。
2. 事前承認型UWIを保存したら、元の項目の`depends_on`へそのUWIを加え、回答待ちを編集のための`hold`と区別する。
   `atk wi set-dependencies <元項目のファイル名> --depends-on <UWIのファイル名>`を実行する。
   このコマンドは依存を指定した集合で置き換えるため、元の項目が既に持つ依存先も`--depends-on`へ並べる。
   元の項目が`processing`なら、依存を保存した後に`atk wi return-to-inbox <元項目のファイル名>`で`inbox`へ戻す。
   依存の保存より先に戻すと、依存の無い`inbox`の項目を別の処理主体が取得し得る。
   未回答のUWIを待つ元の項目は`blocked`と判定され、処理候補から外れる。

## 回答済みUWIの取り込み

回答前の依存は、未回答の間だけ元の項目を留める。
キューは処理環境を区別しないため、別の環境で処理する旨の回答の後も元の項目は今の環境の巡回対象に残る（その結果になる選択肢を出さない基準は`agent-toolkit:atk-mode/references/uwi-format.md`「構成」）。

1. 回答が保存されたUWIと、そのUWIを`depends_on`に持つ元の項目は、同じキューの処理候補に入る。
   次にそのキューを処理する`agent-toolkit:atk-mode`の作業`process-wi`のメインエージェントは、両方を同じ実行の処理対象へ加え、同じ作業レーンへ割り当てる。
   実行中にユーザーから回答を伝えられた場合は、`agent-toolkit:atk-mode/playbooks/process-wi-additions.md`「処理対象WIの追加」に沿って取り込む。
2. レーンは回答を反映してUWIを終了し、依存が解消した元の項目を処理して終了する。
   回答によって元の項目側の追加作業が不要になった場合は、メインエージェントがUWIを終了し、元の項目だけを処理対象に加える。
3. 同じ元の項目が依存する未回答のUWIが他に残る間、元の項目は`blocked`のままで、回答済みのUWIは先に終了してよい。
4. UWIは元の項目のファイル名と回答の判断に必要な情報だけを持つ。
   計画の有無によらず、依存の保存時に`atk wi edit <元AWIのファイル名> --append --body-file <絶対パス> --target-repo=<対象リポジトリ>`で元のAWIへ再開手順（計画があればその絶対パスを含む）を追記し、回答側は`## 処理結果`の後ろからそれを読む。
   旧形式の計画で再開手順を進捗ログだけへ記録した項目は、その進捗ログから読む。

## 依存と冷却時間

`depends_on`は、先に終了させておくべきキュー項目のファイル名を持つ。
先行する項目の成果物が無いと後続のWIを安全に実施できない時か、完成の判定が成り立たない時に限って設定する。
依存先ごとに、待つ成果物、それが無いと成り立たない工程や完了条件、今の成果物で代替できない理由を後続の項目の本文に書く。
同じファイルの変更、変更範囲の重複、作業順序の好み、共通方針の反映は依存の理由にせず、書き込みの競合と実装の順序はレーンの割り当てで調整する。

依存先には、`target_repo`が異なるリポジトリの項目も指定できる。
同じファイル名の項目が複数の`target_repo`にある時は、依存元と同じ`target_repo`の項目を依存先とし、それが無ければそのファイル名を持つ全ての項目を依存先とする。
依存は`atk wi set-dependencies <filename> --depends-on <filename>`で、`inbox`、`processing`、`hold`の項目へ登録する。
このコマンドは保存状態を変えないため、保留の間に本文の修正と依存の確定をまとめて行える。
`ready`か`blocked`かは、メタデータに記録された依存だけから導く。

`cooldown_until`はAWIだけに設定する。
初回の投入では`atk wi add --cooldown-until <タイムゾーン付きISO 8601日時>`で指定する。
既存の`inbox`か`hold`のAWIへは`atk wi edit <filename> --cooldown-until <日時>`で設定し、同じ操作に空文字列を渡すと解除する。
UWIに期限が保存されていると着手可否の判定で不正な期限になるため、同じ操作で解除する。
期限の時刻を過ぎた後は、他に続けられない理由が無ければ`ready`になる。

先送りを選ぶ前に、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」と`agent-toolkit:atk-mode/references/origin-and-approval.md`「由来と承認」を適用する。
待てば解決する見込みは、既知の解除時刻、提供予定、同じ条件の一次情報や実際の観測といった具体的な根拠で判断する。
解決の保証までは求めず、任意に決めた再確認日や将来のAPIの追加の可能性は根拠から外す。

## 着手不能要因の分類

| 解除される契機 | 該当する要因 | 設定方法 |
| --- | --- | --- |
| 時間の経過のみ | レート制限のバックオフ、再試行間隔の待機、指定期日の到来待ち、解決する見込みの根拠がある外部成果の再確認までの待機 | `cooldown_until`を設定する |
| 実在する先行キュー項目の終了 | 先行するキュー項目の成果待ち。別リポジトリの成果物でも、先行項目の終了を同じキューで追跡できればここに当たる | その項目のファイル名を`depends_on`へ直接加える |
| ユーザーからの回答 | ユーザーだけが決める判断、提供できる資料や観測結果、実施できる操作の完了待ち。別環境の実機でしか取れない観測も含む | `agent-toolkit:atk-mode/references/uwi-format.md`の事前承認型の書式でUWIを保存し、元の項目の`depends_on`へ加える（本書「承認型UWIと元項目」） |

UWIは、ユーザーの判断、資料の提供、操作が必要なことを根拠に起票し、1件で1つの問いを扱う。
起票の要否は環境の違いではなく、ユーザーだけが出せる入力や認可の不足で決める。
既に認可を得た操作はUWIにせず、`agent-toolkit:atk-mode`の作業`process-wi`の外部操作の手順で実施する。
一連の作業が終わった後に必要なユーザー側の対応は、`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」でUWIの登録の要否を決める。
登録する場合は、関連するAWIの完了工程に登録の予定を書き、そのAWIの担当がUWIの保存を確かめる。

先行項目を別環境へ移して元の項目を削除するなど、元のキューでは先行項目の終了を追跡できないと事前に分かっている場合は、`depends_on`を設定しない。
後続の本文に、対象リポジトリ、待つ成果物、反映を確かめる条件と確認先、成立後の作業を書く。
暫定規範の終了を同じ理由で追跡できない場合も、番号の所在ではなく成果物に保護が反映されたことを確かめてから削除する。

外部成果を待つ`cooldown_until`は、再確認までの待機だけを解く。
外部の解除条件と解除後の作業をAWIの本文へ残し、期限の時刻を過ぎた時に条件を確かめる。
未反映なら着手せず、解決の見込みを見直す。
公開日が決まっていなくても、解決する見込みの根拠があり必要な判断が済んでいれば、次の再確認の時点を設定できる。
見込みを確かめられない時はcooldownを設定せず、見送り、別案、外部の変更待ちの扱いを事前承認型UWIで確認する。

## 終了

`adopt`のメモの冒頭には、AWIのH1直下の変更要求（`agent-toolkit:atk-mode/references/awi-body.md`「節の構成と分担」）を実施した結果として、何をどう変えたかを1文で書く。
回答済みUWIを終了する時は、回答を踏まえて実際に行った対応を1文で書き、元のAWIに残る作業と区別する。
`reject`のメモの冒頭には、要求を採用しなかった理由を1文で書く。
commitやレビュー記録などの詳細は、その1文の後ろに置く。
メモはユーザーが既に知っている語彙で書く。

メモに書く処理結果は、原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）に従い、終了の直前に確かめる。
対象のプラットフォーム、ランタイム、呼び出し手段で自ら観測したことだけを事実として書き、参照するcommit、PR、CI run、外部操作は完了を確かめてから、後続の担当が解決できる識別子で書く。
`--commit`を伴う採否では、そのリビジョンを解決でき、originが対象リポジトリと一致するworktreeの絶対パスを`--target-repo`に渡す。
[効果確認](effect-records.md)の引数は実装commit付きAWIの`adopt`に限る。

`rejected`は、全ての要求単位の不採用が確定した時に限る。
項目ごとに、エージェント由来の要求には技術的な根拠、人間由来か出所不明の要求にはユーザーの明示的な承認を要する。
技術的な失敗、情報の不足、外部条件の成立待ち、計画の不備では`active`のまま保ち、本書「着手不能要因の分類」で待ち方を決める。
不採用の確認の回答を待つ項目は、採用できる範囲を含んでいても分割せず、全体を確認のUWIへの依存で待たせる（本書「承認型UWIと元項目」）。
技術的に解消できない問題と続けられない理由は、未達事項として記録する。

採用済みの内容を同じリポジトリの別の項目へ統合した時は、元の項目を`rejected`にせず、統合先を`note`に書く。
元の項目が`inbox`か`hold`で、操作主体の担当範囲と書き込み権限の内にある時に限り、`rm`で削除する。
統合だけを理由にする場合、`processing`と`adopted`の項目は今の状態のまま残す。
検収を終えた別リポジトリへの移管は、`agent-toolkit:atk-mode/references/cross-repository-submission.md`「元項目の移管」に従う。

エージェント自身が誤って投入した項目は、`atk wi rm`で削除するか、`atk wi edit`で本来の要求に書き直して再利用する。
削除した項目はprivate-notesのGit履歴から戻せるため、削除の前のユーザーへの確認は省く。
`rejected`は、成立する要求を正当な理由で採用しない時だけに使う。

## 対象リポジトリとprivate-notesの区別

作業の対象リポジトリと、AWI、UWI、計画ファイルを保管するprivate-notes（`atk config get private_notes`が返すリポジトリ）は区別し、報告でリポジトリのパスや状態を書く時はどちらかを明記する。

- 変更対象の特定、差分の確認、commit、変更の退避や巻き戻しは、依頼が指定した対象リポジトリの作業ツリーで行う。
- private-notesへの変更は、`atk wi`、`atk plans`、`atk serve`を通じて行う。
  `atk`がGit履歴の分岐やrebaseの失敗を報告し、再実行でも解消しない時に限り、その出力が示す回復手順の範囲で`git`を直接実行し、前後の状態と実施した操作を報告する。
  回答やユーザーコメントが競合したら、その本文と、それを前提とした状態・処理結果を一緒に確認する。
  現行の回答に適用できない旧結果は採らず、必要なら再処理へ戻す。
  回答が同じなら有効な結果を保つ。
  旧結果はGit履歴に残す。
  private-notesは常駐の`atk wi process-loop`、`atk serve`、別のセッションが並行して更新するため、回復手順の範囲でも`atk worktree-stash`、`git stash`、未コミット差分の破棄は行わない。
- AWIとUWIは、`atk config get private_notes`が返す作業ツリーへ直接投入する。
  別に作った作業ツリーのローカルcommitは、ユーザーと後続のセッションが確認できないままになる。
- private-notesの未コミット差分（年月ごとの固定ディレクトリのWIや計画ファイルを含む）は`atk wi commit`で確定する。
  作業ツリーがクリーンでないことでコマンドが失敗しても差分を退避せず、同じコマンドで確定するか、差分を持つ別のプロセスの終了を待つ。
- 委譲先へ伝える「push不可」は対象リポジトリへの`git push`の禁止であり、`atk`がprivate-notesへ内部で行うcommitとpushは対象外である。
- ユーザーは外部のエディターでキューのファイルを直接編集してよく、生じた未コミットの変更は`atk wi commit`で確定する。

## 委譲先によるprivate-notesへの反映

委譲先は、状態を変える`atk wi`を反映を抑止するオプション無しで実行する。
担当の確認が要らない場合に`atk wi adopt`や`atk wi reject`を`--skip-push`付きで実行すると、その呼び出しから裏の同期を起動しない。
担当の確認が要らない場合は、最後の変更操作を`--skip-push`なしで実行しても、裏の同期を起動するだけで共有先への到達は待たない。
最後の変更操作も`--skip-push`を使った場合は、`atk wi commit`で送信する。
共有先への到達を確認してから次へ進む必要がある場合は、`atk wi commit`でその場で送信する。
未pushのcommitが残ると、別のセッションとの同期で履歴が分岐する。
`atk plans commit`による計画バンドルの保存は対象外とし、抑止の指定は保存を指示する各手順に従う。

## 複数件の`atk wi show`の取得

同じ対象リポジトリの複数の項目を同じ工程で取得する時は、取得条件ごとに`atk wi show <filename>... --skip-pull`を1回実行し、保存先の出力を読んで本文が切り詰められていないことを確かめる。
取得した内容を正式な本文として採るのは、終了コードが0で、要求した全てのファイル名に対応する`### <ファイル名> [<状態>]`見出しが揃っている時に限る。
見出しが欠けた項目と、保存先のファイルを読めない時の各項目は、単独で取得し直す。
終了コードが0以外の部分出力は捨て、取得元の工程が定める手順（処理の停止か1件ずつの再取得）へ進む。
単一の項目の取得、警告やエラーの後の再取得、UWIの回答の確認では、項目を1件ずつ指定する。
