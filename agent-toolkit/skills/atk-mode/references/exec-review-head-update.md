# HEADの更新と再レビューの要否

レビューを受けるエージェントが、HEADの更新で影響を受けた単位だけを再レビューし、確かめていない変更の統合と同じ確認の繰り返しをどちらも避ける。

レビュー修正かmergeの競合の解消でHEADが変わったら、計画（計画なしではWI）の単位ごとに、影響と直近の評価前提が保たれる範囲を確かめる。
前回のレビューHEADを`R`、最新のHEADを`H`、開始時のHEAD（rebase後はrebase先のOID）を`<基点>`とし、次のどちらかに当たる単位を「影響を受ける単位」とする。

- `git range-diff <開始時のHEAD>..<R> <基点>..<H>`で、その単位の判定対象commit（`review_contract`で判定対象外としたcommitを除く）のどれかが`=`以外で対応している。
- `git diff --name-only <R> <H>`の変更ファイルが、その単位の判定対象commitで変更されたファイルと重なる。

1. 対象worktreeで上のコマンドを直接実行する。
   判定対象commitは、計画ありでは`atk run-script plan-commits -- <計画の絶対パス> --worktree <対象worktreeの絶対パス>`の一覧、計画なしでは前回レビューに渡したWIの判定対象commitとその対応記録から、判定対象外を除いたものである。
   変更ファイルは`git show --name-only --format= <commit>`で確かめ、終了コードが0でなければ原因を解消して判定し直す。
2. 影響を受けない単位でも、既に「要」とした確認が残れば省かない。
   省く場合は計画名かWI名、`R`と`H`の完全なOID、実行したコマンド、対応行の要点、理由を引き継ぎ記録へ残す。
   rebaseでcommitのOIDだけが変わったことは、新たな再レビューの理由にしない。
3. 影響を受ける単位では、`agent-basics:review-standards/references/reviewee.md`「方式見直しと再レビュー」で評価の前提を比較する。
   前提を保つ場合はレビュー担当が「要」とした範囲に限り再レビューする。
   前提か範囲が変わる場合は影響する担当へ要否を照会し、回答とそれぞれの確認範囲を引き継ぎ記録へ残す。
