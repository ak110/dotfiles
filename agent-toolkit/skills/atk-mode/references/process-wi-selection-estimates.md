# 選定の所要見込みと補正

作業`process-wi`の選定で、全工程の所要見込み、初回配分の上限、見込みの補正、予測補正記録を求める方法を定める。
これらはユーザーが決めた時間目標の運用であり、選定のメインが入力を書く時と、巡回の完了時に実測を残す時に使う。
欄の形と省略規則は`agent-toolkit:atk-mode/references/process-wi-selection-format.md`「選定結果の書式」にある。

## 全工程と通常対象の算定

`全工程の見込み`の`並列数`と`工程`は必須で、`巨大WI`を省略した場合は空の列として読む。
モデル同時数は資源とサービスの上限以下とし、根拠の資源・サービス・費用を原記録へ対応させる。
`検証同時数`は共有実行枠（`agent-toolkit:atk-mode/playbooks/verification.md`「統合実行ツール経由の起動」）の定義と、対象リポジトリの検証が使うpyfltrの版と`PYFLTR_EXECUTION_SLOTS`から決め、`根拠.検証`へ記録する。
保存済みの旧記録でこの値が無い場合は、従来の容量で読む。
選定で使う同時数はCPUコア数から自動で決めず、資源、実際のAPIとCLIの制限、起動・読込・検収まで含む総費用の比較から意味判断の所有者が決める。
これとは別に、マシン全体で作業中の委譲先の上限はagents_serverが論理CPU数から求めて起動時に強制するため、モデル同時数はこの上限を超えない値にする。
根拠の真正性と費用の合理性は、数値の検査の後に意味判断の所有者が検収する。

工程の依存は次のように組む。

1. 工程IDは一意とし、`先行工程`には実在する別のIDを循環なく挙げる。
   共有定義の避けられない直列処理と、前段レーンの統合待ちを依存に含める。
2. 検証工程は`検証同時数`を容量とする検証資源、統合工程は容量1の直列資源を使う。
   実装とレビューはモデル資源を使い、同じ定義を変える仕事の直列性は`先行工程`で表す。
   選定・準備・公開・後始末・報告はモデルか直列の資源へ割り当て、検証資源は検証工程だけに使う。
3. 全ての処理対象WIを実装・レビュー・検証・統合へ対応付け、選定・公開・後始末・報告も含める。
   各群の実装に対するレビューと検証は統合の前に置き、独立した群は他の群の実装中にもレビューを始められる。
   公開は統合の後、後始末は公開の後、報告は後始末の後に置く。

秒数は共有待ちを含めない仕事の処理秒数とし、資源不足による開始待ちは計算側が求める。
残量/速度による算定には0以上の`残量`と正の`速度`を加え、秒数をその比と1秒以内で一致させる。
実測と残量/速度の根拠を残し、未確認はnullと未確認前提の列で表す。
条件付き試算、未確認の算定、空でない未確認前提が残る見込みは、数値が目標内でも実行可能性を未成立とする。
未測定の固定工程や待ちは未確認のまま保つ。
計算は、依存を満たした仕事を資源容量の内側で重ねる静的な見込みであり、担当の起動や制御、数学的な最短時間の証明とは別である。

巨大WIの認定と今回の承認は、意味判断の所有者が原文と根拠を確定した後に入力する。
巨大の根拠があり、`承認元`の対象WIが同じWIで判断が承認の場合だけ、そのWIだけに属する仕事を通常対象の計算から外す。
承認は同じWIへの名指しの原文と対応させ、別のWIへの承認や自由文からの推定は承認として扱わない。
承認が無い、拒否、未回答の巨大WIは通常対象に残り、目標超過は警告になる。
共通の固定仕事と通常WIにも属する仕事は外さず、残る依存と容量から通常対象を再計算する。
除外前の全件の壁時計見込みは、並行した通常仕事を差し引かずに別に表示する。

追加のmergeは、追加側が合流後の全対象について確定し直した`全工程の見込み`を渡すと、その値を採用する。
渡さない場合は既存の`全工程の見込み`を引き継がず（追加分を含まない値は誤った見込みになるため）、見込みが未確認になった旨の警告が出る。
旧選定を`--history`で表示する場合は新たな実行可能性の成立を示さず、更新操作と併用できない。
配分を変えない`--mark-integrated`は旧配分の履歴を保存でき、新規生成、追加のmerge、再開の配分には目標の検収を適用する。
目標を設定していない既存入力の局所値は`履歴の局所見込み秒数`と表示され、全工程の成立とは別に扱う。

## 初回配分の算定根拠

レーンの`根拠`には、依存の連鎖と独立したWIを合わせた順序の判断を含める。
後続の独立した準備を始める時機と未確定の事項を引き継ぎ、選定での詳細設計の重複を省く。

単独のチェック、状態の記録、merge操作の既存側のYAMLでは`初回配分`が必須となる。
merge操作の追加側のYAMLだけは省略でき、選定された全てのWIが`追加WI`に分類される。
初回配分の内容は、追加の統合やレーン名の対応付けの前後で同じ値を保つ。
`候補WI`には、開始時の候補から通常の処理対象外の条件に当たる項目を除き、今回選んだ全件（包含された項目を含む）を1回ずつ書く。
初回確定の前に明示的に追加したWIは、`agent-toolkit:atk-mode/playbooks/process-wi-selection.md`「処理対象の決定」の集合和に含める。
`レーン割当`は、初回に選定した各WIを初回のレーンか`なし`に対応付ける。
初回の割当集合と`追加WI`は互いに排他で、両者の和が現在の選定集合と一致する。
不可分成分は初回の`なし`以外のWIを1回ずつ網羅し、各成分を1つのレーンへ割り当てる。
単独のWIからなる成分の結合条件は空のリストでよく、複数のWIを含む成分は有効な辺で互いに連結させる。
成分の項目は`WI`と`結合条件`だけとし、所要時間の見込みはレーン別の所要時間と根拠に書く。
結合条件の各辺は`WI1`、`WI2`、`種別`、`根拠`だけを持ち、両WIは成分内の異なる項目とする。
保存される`根拠`は、次の項目だけを持つマップである。

- `依存`: `リポジトリ1`、`リポジトリ2`（正規化した識別子）、`依存元`（両端のどちらかのWI名）、`depends_on`（元の依存先文字列のリスト）。
  依存の必要性は、メインが元のWI本文から検収する。
- `再開計画`: `計画1`、`計画2`（同じ計画を指す文字列）。
  初回の`なし`と`計画なし`以外の同じ計画を指す履歴として保ち、要求が変わった後の現在の`再開位置`との一致は求めない。
  現在の同じ計画を複数のレーンへ割り当てることはできない。
- `書込重複`: `定義1`、`定義2`（各変更定義の空でない文字列リスト）、`段階比較`（空でない比較理由）。
  定義どうしが重なり、現在の両端の`書込対象`に同じパスか包含関係の範囲があり、両端のレーンの`段階`が等しい組に使う。
  範囲をファイル単位で特定できない場合は、双方の定義に同じファイル名を書く。
  段階比較と定義の妥当性は、メインが検収する。

Nは`候補WI`の件数で、`agent-toolkit:atk-mode/playbooks/process-wi-selection-allocation.md`「調査とレーン分け」の`WI数`も同じ件数を指す。
上限Bは`floor((N+9)/10)`とし、初回の割当数と、現在の全レーン集合（`なし`を除き、統合済みレーンと全段階のレーンを含む）をそれぞれB以下に抑える。
所要時間の見込み、成分の規模、追加件数などを理由とした例外は無く、独立した成分の数がBを超える場合は複数の成分を同じレーンにまとめて順に処理する。
追加時の最終レーン名には既存のレーン名だけを使い、Bに空きがあってもレーンを新設しない。
追加時の仮名は既存のレーン名に対応付け、合流先のレーンだけを未統合に戻す。
初回の情報が欠けた入力は、元の候補、初回割当、結合根拠の記録から復元して補い、元の記録を確かめられない場合は情報不足として扱う。

## 見込みの補正の算出

全工程の見込みには過去の完走の実測を使う。
工程別の区間と補正前の予測がそろわない間は、同じリポジトリの直近の完走レーンの「所要÷関連WI数」の中央値を使う。
所要は計画の進捗ログの開始から完了までとし、同じレーンの複数の計画を1件と数える。
本文だけから見積もった秒数を実測の代わりにせず、参照した記録・期間・件数・中央値と未測定の範囲を選定の根拠へ残す。
選定・公開・CI・後始末・報告と直列統合の費用も同じ完走記録から加え、並行区間は重なりを除いて計上する。
処理可能な全件を対象にし、目標との差は配分と工程の改善に使う。

巡回の完了報告には、選定時の見込み、実際の全工程の所要、差、選択件数・残数と参照した記録を残す。
次の選定はこの記録を既存の予測補正記録と合わせて読み、予測差が続く場合も実測を量の決定へ反映する。
保存先は既存の完了報告と予測補正記録に集約する。

工程別の係数は次の手順で求める。

1. 計画の`## 進捗ログ`か、計画を持たないレーンの対象AWI本文に保存された予測補正記録から、対象リポジトリ、選定元、レーン、完了時刻を突き合わせて、実行とレーンの対応を確定する。
2. 補正前の予測値が欠けた記録、対象工程の予測合計が0秒の記録、対応や工程別区間が不明な記録は、理由を添えて除外する。
   区間が分かれていない記録は工程別の係数へ転用せず、前述の完走レーンの中央値へ戻す。
3. 同じ実行・レーンの中の複数の計画やAWIを1件として、実装と統合の実仕事の秒数を工程ごとに集計し、補正前の予測秒数の合計で割って`実装係数`と`統合係数`を求める。
   共有資源の待ちは実仕事の係数から分ける。
   有効な工程別の記録が無ければ過去の実行へ遡り、それでも無ければその工程の係数を1とする。
4. 各レーンに`補正前の実装秒数`と`補正前の統合秒数`を、最上位の`見込みの補正`に工程別の係数、`共有待ち秒数`、参照した記録、除外した記録と理由を記録する。
   `実装秒数`と`統合秒数`には、対応する工程の係数を掛けた値を書く。
5. 共有待ちの根拠はレーンの`根拠`へ対応付け、未計測と待ちなしの実測を区別する。
   過去の記録から待ちを測れない場合は`共有待ちの算定`を`推定`とし、共有実行枠と統合の順番から見積もった0より大きい秒数を使う。

6000秒の判定と段階案との比較にも補正後の値を使う。
旧方式の局所比較では共有待ちを1回加え、全工程の成立の証拠とは別に扱う。
`全工程の見込み`の処理秒数は実測か残量/速度から得た値を書き、同じ係数と共有待ちを除いた仕事の処理秒数として扱う。
選定・公開・後始末・報告の未測定はnullと未確認前提のまま保ち、`pick-wi-check`は未成立を警告で示す。
追加の候補も既存と同じ工程別の係数で補正し、既存レーンへ合流する場合は補正前の2つの値を累積してから工程の係数を掛ける。
合流後の全工程の入力は追加側で確定し直し、固定工程と共有待ちをそれぞれ1回だけ計上する。
全件の壁時計見込みと、承認済みの巨大WIを除いた通常対象の見込みは、同じ依存入力から別々に求める（本書「全工程と通常対象の算定」）。

## 予測補正記録

統合工程の進捗ログと、計画を持たないレーンの対象AWI本文に保存する。
書式は`予測補正記録: 対象リポジトリ=<識別子>; 選定元=<出力先の絶対パス>; レーン=<識別子>; 完了時刻=<時差付き時刻>; 補正前実装秒=<秒数>; 補正前統合秒=<秒数>; 補正係数=<係数>; 総経過秒=<秒数>`とする。
選定元は1回のprocess-wiの実行を一意に識別する。
補正前の2値は選定結果の`レーンの所要時間`の`補正前の実装秒数`と`補正前の統合秒数`から、係数は最上位の`見込みの補正`から取る。
追加のWIがある場合は、レーンの累積の予測値を使う。
補正前の欄には事前の予測値と確認できた値だけを書き、復元できない過去の記録は不明として次回の集計の分母から外す。
同じレーンの複数の計画と、同じ実行・レーンの記録を持つ複数のAWIは、同じ値で1件と数える。
セッション内の引き継ぎ記録には保存先を書く。

工程別の補正を持つ選定では、書式の`補正係数`を`実装係数`・`統合係数`・`共有待ち見込み秒`へ置き換え、対応する選定値を記録する。
実装側の計画・実装・検証本体・レビューと修正、統合の処理、共有実行枠と統合許可の待ちを、進捗ログの開始・終了とコマンド・レビューの記録へ対応付ける。
工程別の実測秒と根拠の所在も同じ記録へ添え、並行する区間は重なりを除いて数える。
区間を確定できない工程は不明とし、その総経過から工程の係数を推定しない。
旧形式の総経過・単一係数の保存記録は区間が分かれていない履歴として読み、工程別の実測へ流用しない。
