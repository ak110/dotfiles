# 原因分析を記録する場所

本書は、観測された不具合の原因分析を記録するエージェント向けに、記録先とバグ単位の分け方を定める。
記録の形（`期待:`・`原因:`・`処置:`・`広がり:`・`確認:`の5行と、条件が成立した時の`再発:`・`再発防止:`の行）と各行に書く内容は、`agent-basics:bugfix`の`SKILL.md`「記録」が定める。

## 原因分析の記録先

確定したバグ単位は、観測された不具合を起点とする通常AWIの`## 原因分析`節に記録し、計画ファイルからはその節をWIファイル名で参照する。
これにより、分析内容の記述をWI側の1か所に集める。
複数のリポジトリで共通する分析は、`agent-toolkit:atk-mode/references/cross-repository-submission.md`「独立したAWIへの分割と依存」に従って代表AWIへ集約できる。
固有AWIにある正式名・target_repo・指定箇所から記録と確認結果を取得し、リポジトリ固有の事実と処置の適用は個別に確かめる。
計画ファイルの本体に`## 原因分析`を置く条件は`agent-toolkit:write-plan/references/plan-file-standards-verification.md`「原因分析」に従う。
別ファイル（`<計画名>.bugs.md`）は、保存済みの計画の読み取りでだけ受け付ける。

AWIの`## 原因分析`節と計画ファイルの`## 原因分析`節のバグ単位は、どちらも5行の記録で書く。
AWIでは、`処置:`の行に要旨と`## 反映内容と反映先`節の対応項目への参照を書き、具体的な変更内容は`## 反映内容と反映先`節へ置く。
AWIの`確認:`の行には、処理側が確かめる方法を書く。
件数やログの数値を挙げる場合は、実測で確かめていない数値を推定値と明記する。
記録を書いたことだけで処置済みとは判断しない。

保存時の検査は、新規の作成と原因分析を変える更新で、バグ単位ごとに5つの行頭の語がそろい、各行に本文があることを確かめる。
内容の十分性は検収者が判断する。
保存済みの旧形式（原因分析表と処置の表）は、読み取りと、原因分析を変えない編集で受け付け、書き換えを求めない。

## バグ単位の分け方

複数のバグ単位を含むAWIでは、`## 原因分析`節の中にバグ単位ごとのH3見出しを設ける。
H1直下は短い目的・変更・結果を保ち、各バグの現象と期待は`期待:`の行の1か所に記録する。

複数の観測事象を1つのバグ単位にまとめるのは、原因と処置の変更対象がともに同一である場合に限る。
背景の事情が共通していることだけを統合の理由から除く（たとえば入力解析処理と状態更新処理のように原因が異なる場合は個別のバグ単位に分け、同一の原因と処置によって保存失敗と再試行停止の双方が解消される場合は1つに統合できる）。
対応の網羅性を確かめる際は、計画メタ情報に書かれた関連WIの各バグが、WIの`## 原因分析`節か、計画ファイルの`## 原因分析`節の確定済みバグ単位に対応していることを確かめる。
広がりの記述は原因分析の記録にだけ置き、ほかの節からは参照する。

## 潜在欠陥の受渡し

元の修正に必要な追随は元の作業に含める。
独立した別件は投入元が具体化して別AWIへ渡し、元の記録に調査結果と登録先を残す。
手動登録では登録前に別件の原因と変更内容を確定し、他の工程では観測事実、支持根拠のある原因仮説、残る問いを区別して渡せる。
元の原因から広がりを探す調査と、別件自身の原因の確定を区別する。
観測された事象に対する因果関係が観測で確定していない潜在的な欠陥は、その因果関係を実測で確かめた場合か、ユーザーが同一計画への併記に明示的に合意した場合に限り、同一の計画に含め、合意や確認の根拠を計画へ記録する。
同一の計画に含めない是正対象は、独立した通常のAWIとして登録するか委譲元へ返却し、引き渡し先と処置の進捗を記録する。
引き渡し先を指定せずに調査対象から除外した場合は、広がりの確認を未完了とみなす。
計画を分割するのは記録の単位を整理するためであり、引き渡した処置は引き継ぎとして記録し、元の作業の完了と分ける。

## 暫定回避と結果報告

解除条件を伴う暫定回避を行う場合は、WIの通常の投入手順（`agent-toolkit:atk-mode/playbooks/wi-saving.md`「投入」）に従い、正式対応の対象、解除条件、復帰後に期待される結果を保存済みのAWIへ記録して接続する。
時間経過や外部公開の待機は、`agent-toolkit:atk-mode/references/states-and-dependencies.md`「依存と冷却時間」「着手不能要因の分類」に従って、ユーザー判断の要否と解決の見込みを先に確定し、UWIか冷却期限を選ぶ。
再発防止を採用するかどうかの判断は、`再発防止:`の行と、作業完了報告と報告用UWIの`### 自ら確定した判断`に根拠とともに記録する。
ユーザーだけが判断できる事項は、`agent-toolkit:atk-mode/playbooks/confirmation.md`「確認要否の判定」に従って確認する。
