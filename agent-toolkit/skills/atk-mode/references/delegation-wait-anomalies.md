# 待機の異常

`atk agents wait`の終了コード、待機を開始できない場合、ホストによる待機の停止、役割資源の版の違いへの対処を定める。
平常の待機と停滞は`agent-toolkit:atk-mode/playbooks/delegation-waiting.md`、MCPサーバーの再起動からの回復は`agent-toolkit:atk-mode/playbooks/delegation-recovery.md`が扱う。

## 終了コードと呼び出しの失敗

`atk agents wait`の終了コードと行動を次に示す。
応答の行の形式は`atk agents wait --help`が定める。

| 終了 | 意味 | 行動 |
| --- | --- | --- |
| 0 | 回収できた | `agent-toolkit:atk-mode/playbooks/delegation-waiting.md`「`atk agents wait`の応答の扱い」へ進む |
| 3 | 待機上限に達した | 同じコマンドを再発行する |
| 4 | 状態ディレクトリを解決できない実行環境 | 診断・環境情報を保持して設定を確認する。不具合は `agent-basics:bugfix` で認可内に限り直し、CLIの診断に従い再待機する。未回復の影響・試行・再開条件を委譲元へ返す |
| 8 | 先行runとの競合、合流中の期限到達、先行runの記録の読取失敗、配信済みか回収済み | 本書の8の手順 |
| 10 | 委譲元の状態管理に待機対象が登録されていない | 本書の10の手順 |
| 11 | 本文ファイルを書けない（回収途中の結果は退避済み） | 原因を解消して再発行し、同じ結果を受け取る |
| その他の非0で、待機対象の登録と`starting`を含む保持中のセッションがともに0件 | 回収する対象が無い | 再実行せず、起動時の応答を確かめる |

8は待機対象の異常とは別の事象である。

1. 同じ書込主体の待機が動いている時、後発のプロセスは`current.json`が示す先行のrunを固定し、そのロックの解放後にrunの状態を確かめる。
   配信済み（`foreground-delivered`か`consumed`）なら本文を再出力せず、終了コード8と`run_path`を含む回復の情報を返す。
   未配送の`published`なら保存済みの本文を回収し、`running`なら追加の対象も含めて待機を続ける。
2. 先行するバックグラウンドタスクの保存出力を確かめ、先行の待機が終わってから待ち直す。
3. 保存出力を取れなければ、`jq -r .output -- <run_path>`で終了行を確かめ、その`agent_message_path`から本文を読む。
4. それも失敗したら、原本、退避ファイル、先行runを保持し、書込主体、固定run識別子、待機対象、`run_path`の絶対パスを委譲元へ報告する。

10は委譲先の失敗とは別の事象である。
同じコマンドは再発行せず、起動時の応答と`atk agents list`でセッションの存在を確かめる。
ホストの組み込み機能で起動した対象は、ホストの委譲一覧と指定した成果物で終了を観測する。

委譲先か自身のツール呼び出しが終了状態を返さずに終わった場合（アイドル上限のアボート、待機上限の超過、無応答による中断）は、実行基盤の欠陥として`agent-basics:bugfix`を起動する。
同じ欠陥は別のセッションでも再発するため、待機を続けるかも個別に判定する。
ホストのリソース上限やメモリー不足で背景待機が止まった時は、本書「ホストによる背景待機の停止後」へ進む。
委譲先の停滞、中断、再起動は、`atk agents list`の各セッションの`status`で判定する。

## 待機を開始できない場合

1. 待機が未起動なら、`agent-toolkit:atk-mode/playbooks/permission-denial.md`「共通判断」で通知本文の再試行の指示を確かめる。
   - `gave no verdict (error)`で「transient failure」「You may try the action again once」と示す通知は、許された1回の再試行と指定の遅延に従う。
   - `gave no verdict (it skipped this action)`で「hard failure」「Don't retry it」と示す通知では、同じ待機の起動を再試行せず、別のツールでの再判定と権限設定の変更も行わずに済ませる。
     読取と独立の作業、許容された別の観測手段での終了の観測を続ける。
     その操作が必須なら、対象、操作、通知本文を、委譲先は委譲元への即時通知で、メインは`agent-toolkit:atk-mode/references/delivery.md`「手段の選択」でユーザーへ伝える。

   実際の拒否は、同書の拒否の主体別の節に従う。
2. 失敗した待機の起動状態、既存の待機の実行識別子、未回収の子と背景処理の識別子を保持する。
   再試行までの間は独立の作業を進め、classifierへの再試行の間隔を、子の完了を固定のsleepで照会する方式へ置き換えることは避ける。
3. 待機が未起動でも、未回収の対象の終了を観測する責任は残る。
   許容された待機と回収の手段で観測を続け、自動再開の能力だけを根拠にターンを終える前に、今回の対象の追跡、結果の保留、継続が成立しているかを確かめる。
4. ホストの上限か停止の制約で観測を続けられない時は、未回収の対象、待機の起動状態、診断、再開の条件を委譲元へ渡し、観測を引き継ぐ主体を明確にする。
   未回収の対象は未完了として返す。

## ホストによる背景待機の停止後

停止通知の`killed`は、外側のバックグラウンドタスクが終わったことを示す。

1. 起動結果と停止通知の実行識別子、元の出力ファイルを保持し、外側のシェルと、そこから起動された待機の子プロセスの終了を個別に確かめる。
   子プロセスは、起動時刻、プロセスの親子関係、実行コマンドの突き合わせで同じ実行と確かめる。
2. 同じ待機の子が生存している間は、完了通知か定期の再確認で終了を観測し、元の出力ファイルから本文の全量と終了状態を回収する。
   先行の待機がロックを持つ間に後発の待機が失敗しても、先行の停止や結果の喪失を意味しない。
3. 元の待機が終わり、元の出力ファイルにも必要な終了の結果が無い時は、担当の情報と得た結果を保持して同じ対象の観測を再開する。
   観測だけの再開は、ユーザーの再依頼を待たずに行う。
   再開したら、停止されたこと、ホストが示した理由、観測を再開したことを次の応答で短く伝える（委譲先は委譲元への返却に含める）。
   元の結果を回収できて再開が要らなかった場合は、この報告の対象から外す。
4. CIの監視も同じに扱い、既存のcommit SHAとベースラインで`wait_ci.py`の観測を続ける。
   この観測はCIのジョブや委譲先の実処理を再起動しない。
   実処理の再起動が要る時は、既存の認可の範囲と副作用で判断する。
5. ホストが待機コマンドを止め、再開にユーザーの指示が要る時は、取得済みの結果を保持し、再開の可否を`agent-toolkit:atk-mode/playbooks/confirmation.md`でユーザーへ確認する。

## 管理サービスへの操作が応答しない場合

稼働中だった委譲先の状態を確認できない時は、終了状態を未確認として扱う。
判明している委譲先ID、最後に受理された要求、受理を確認できない要求、結果の所在を引き継ぎ記録へ残す。
管理サービスへの反映予約が応答しない時は、予約の受付を未確認として扱う。

停止が必要になった場合は、管理サービス自身の記録から対象の起動単位と配下の状態を確かめ、停止操作の認可を得る。
停止対象は、プロセス名や経過時間ではなく管理サービスの記録が示す起動単位で特定する。
再起動後はホストのMCP接続を更新し、新しい管理サービスで同じIDの状態を照会する。
接続を更新する操作がユーザーにしかできない場合は、Claude Codeの`/mcp`、Codexの会話を閉じて同じ会話を開く`codex resume`など、ホストに合う手段を伝える。

復旧した委譲先の結果を回収してから、未完了の工程だけを続ける。
送信の受付が不明な要求は再送せず、同じIDの状態と最新の結果から配送の有無を確かめる。
復旧後の結果がその要求に対応するか分からなければ、配送未確定のまま扱う。

## 役割資源との版相違

役割宣言か起動時資料の確認が起動前に失敗したら、元の診断、稼働実装のrootと起動時の版、役割資源のrootと現在の版を対応付ける。
文書を更新しても、長命なMCPプロセスが読み込んだコードは更新されない。
版が同じ場合と版を取れない場合も、元の診断を保持して原因を確かめる。

1. 版が違う場合は、ホストのMCPの再接続で、同じ入力を新しいコードと資源の組で確かめ直す。
2. 再接続の前に、起動済みの担当の識別子、稼働状態、未回収の結果、再開の入力を既存の引き継ぎ記録へ保存し、稼働中の担当は止めずに残す。
3. 再接続の後は同じ担当を照会し、継続と結果の回収の責任を引き継ぐ。
4. ホストが再接続を提供しない場合は、既存の自由本文の委譲を、新しいプロセスから正規の役割を起動する中継として使える。
   中継には原要求、全体作業契約、正規の起動の入力、対象の役割の絶対パスを渡し、同じ役割の丸ごとの再委譲を避け、起動、終了、結果の受領を所有する。
5. 同じ版の新しいプロセスでも失敗する場合は、元の診断が示す文書か入力を直す。
