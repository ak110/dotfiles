## 実施内容

完成条件の転記前に`../../wi-standards/references/awi-body-completion.md`「完成条件」で目的上の必要性と由来を判定し、不要条件の除外根拠を採否記録に残す。
明示要求や必要な品質の変更は既存の確認手順へ渡す。

後続要求単位は`部分採用`の残りも含め`移管`の別行にし、計画確定前に登録済みWIのファイル名を根拠へ書く。
登録予定は未登録として扱う。
実施しない単位は`不採用`・`対象外`、回答待ちは`保留`とする。

`## 実施内容`には`実施内容`、`由来`、`採否`、`根拠`の4列表を置き、要求単位と実施範囲が分かる概念単位で書く。
同じWIでも、要求・判断ごとに出所、承認範囲、採否が異なる内容は行を分ける。
実装手順・内部方式は`## 設計・実装方針`、検証コマンドは`## 検証`へ記し、必要な成果と区別する。
競合するWIの組合せと採った対応は`実施内容`へ書き、見送る除外項目と現状を保つ保持項目も行にする。

`由来`列は`人間由来のWI`、`エージェント由来のWI`、`ユーザー指示`、`エージェント提案`のいずれかとする。

- WI由来の行は、区分名、半角スペース、半角丸括弧で囲んだWIファイル名の順に書き（例: `エージェント由来のWI (20260831-000000-001.md)`）、`関連WI`と一致させる。
  区分の判定は`../../wi-standards/references/wi-standards-origin.md`「由来と承認」に従う
- 構造検査は意味上の由来・承認を保証しない。
  `source`・見出し・既存の`[対話由来]`注記で一括分類せず、原文・回答から要求単位の出所と採用範囲を既存根拠欄・変更履歴へ記録する。
  旧形式も受理する
- `ユーザー指示`はユーザー自身の発話で確定した内容に、`エージェント提案`はエージェントが立案した指示で確定した内容に使う

`採否`列は`採用`、`部分採用`、`不採用`、`充足済み`、`保留`、`対象外`、`移管`のいずれかとする。
`充足済み`は、既存のコミットや実装で要求がすでに満たされ、追加の実装が要らない場合に使う。

`根拠`列には、実施しない範囲と理由を、他の参照先を見ずに分かるように書く。

- `エージェント提案`と`エージェント由来のWI`の行には観測可能な根拠を書く。
  計画担当が範囲を変えずに採用するWIの行は、そのWIの完成条件と手段の必要性を現在の方針に照らして判定済みの場合に限り、非空の`## 反映内容と反映先`または旧形式の非空の`## 適用範囲`を参照して`-`とできる。
  範囲や採否を変える場合と、必要性の無い条件を外した場合はその理由を書く
- `人間由来のWI`と`ユーザー指示`の行には、採否にかかわらず原文の要求単位ごとに、原文の該当箇所と、実施範囲へ採用するか除外するかを対応付けた分解を書く（起草者の判断だけで作業範囲が縮むのを防ぐため）。
  WIの`## 反映内容と反映先`に要求単位ごとの対応があれば、踏襲する旨と計画で採否を変えた単位だけを書く。
  原文の全要求単位を開放性を保ったまま受け入れる`採用`行に限り、根拠を`-`としてよい
- 原文が例示表現（「など」「例えば」「〜も」など）で示した開放的な集合を限定的な列挙へ絞った行は`部分採用`とし、絞った対象と理由を書く
- 対話の内容を複数のWIへ分けて起票した場合は、各WIへ割り当てた要求単位を採否の母集団とし、他のWIへ割り当てた単位とそのファイル名も併記する（部分採用の判定には含めない）。
  どのWI単独でも達成を確認できない共通事項（全体目的、数値目標、調査方針など）はその旨だけを書く。
  どのWIにも割り当てずに除外した要求単位は`部分採用`とする
- `充足済み`の行と、充足済みの範囲を含む`部分採用`の行には、充足を確認した実装箇所かコミットと確認手段を書く。
  ユーザーから報告された不具合を充足済みとする前に、報告された呼び出し手段と操作手順で対象を実際に動かして期待どおりの結果を確かめる（コードの読解や既存テストの確認だけで充足済みとしない）。
  根拠のコミットが報告日時より前なら、デプロイ済みのバージョン、操作手順、実行環境など報告時との差を調べ、確認結果と未特定の範囲を書く。
  調査が終わっていない行は`充足済み`の対象から除く
- 計画の確定前に完成条件を変更・除外するメインの技術判断を受けた場合は、対象AWI、旧条件、新条件または除外範囲、技術的制約、保持する要求、`メインの技術判断`と根拠を書く。
  判断の境界は`review-loop-coordination.md`「技術判断で外せる完成条件」に従う。
  後続のレビューと統合はこの記録で処理し、実装着手後の判断はレビュー指摘管理表に記録する
- 大規模な反復作業では、ユーザーが示した低負担な方法や既存の一括処理（`agent-basics:writing-standards/references/notation-rules.md`「表記の一括置換」など）を代表的な対象で試す。
  作業件数と読込・レビュー・検証・統合の負担を比べ、採った方式と理由を書く。
  試行と費用比較の詳細は証拠資料に保存する。
  大量のファイル編集では、スクリプトや既存CLIで処理する部分、内部担当へ分担する確定済みの処理、作業全体の完成に責任を持つ担当に残る判断・検収・検証・統合を分け、それぞれの開始条件を書く。
  改善見込みを書く場合は、起動・必読資料・変換・検収・修正・検証・統合を含む同じ対象集合で方式を比べ、記録から分離できる実測と推定を区別する。
  検証プロセスの負荷と担当の分担数の効果は別の項目として扱う

人間由来のWIの要求を全部または一部不採用とする行は、`../../wi-standards/references/wi-standards-origin.md`「由来と承認」に従ってユーザーの確認を得る（確認が要る範囲縮小と、事後報告で済む裁量の境界も同節に従う）。
ユーザーがAWIの`## ユーザーコメント`やUWIの`## 回答`に作業担当者宛ての質問を直接書いた要求単位は、回答をUWIに記録してユーザーへ返す工程を`## 実施内容`に置く（AWI本文へ転記された質問は対象外とし、同節に従う）。
