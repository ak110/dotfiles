## 検証と公開工程

受入と通常検証の比較・統合は`agent-toolkit:/share/verification-operations.md`に従う。

完成条件と検証手段を具体化するときは、`../../wi-standards/references/awi-body-completion.md`「完成条件」の自己観測と未確認範囲の規定を適用する。

`## 検証`には、`区分`と`検証コマンド`の2列で`変更範囲の検証`の1行だけを持つ固定表を置き、変更対象に応じた検証（対象ファイルを限定したformat、lint、対象テストなど）を書く。
リポジトリ全体の検証とCIの判定は後続の公開工程で行う。

- 検証の対象は変更ファイルとその直接影響範囲に限り、ファイル単位で指定する（努力目標）。
  直接影響範囲の分類と範囲は`agent-toolkit:/share/verification-operations.md`に従い、選んだテストファイルや検証単位をコマンド引数に明記する。
  直接影響範囲のうち検証から外すものは、理由を直接影響範囲の記述欄に書く。
  検証表は起草時点の選定なので、実行者が実行直前に同書に沿って実差分から補正する
- タスクランナーのターゲット単位でコマンドを分けて書く（努力目標。失敗したターゲットだけを再実行できるようにするため）
- 表のセルには、1つのインラインコード（code span）に1つの完全なコマンドを書く。
  複数のコマンドは`<br>`で区切り、説明は表の外に書く。
  パイプライン、リダイレクト、環境変数の代入などシェル固有の処理は実行可能なスクリプトファイルへ移し、そのスクリプトを実行する引数配列（argv）を書く（統合時に`atk lane integrate`がmanifestの`verification`へargv配列として渡し、シェルを介さず直接実行するため）
- 実行は「計画した検証の実行」に従う

計画凍結後に検証条件を訂正した場合は、レビュー指摘管理表の現在の結論を反映した全コマンドを別ファイルへ保存し、「訂正済み検証表」とする。
このファイルには本節と同じ`## 検証`の固定表を1つ置き、計画メタ情報は置かず、凍結した計画ファイルの検証表全体を差し替える内容を書く。
訂正後の検証は訂正済み検証表のコマンドで行う。
計画ファイル、訂正の結論、訂正済み検証表の対応と絶対パスは引き継ぎ記録に書き、実装、実行レビュー、統合の各工程へ渡す。
訂正済み検証表を更新したら、保存済み成功の本文・実行条件・対象の被覆と更新後の要求を比較する。
不足または結果が変わる範囲を追加実行する。
本文と条件の同定、成功保持、再実行の共通基準は`agent-basics:check-execution/references/verification-scope-reruns.md`に従い、同じ成功を表の更新だけで破棄しない。

計画・訂正済み検証表・実行記録には、`agent-toolkit:/share/verification-operations.md`に従って選んだ起動形を記す。
対象到達・完了・終了状態・診断を確かめる。

`## 公開工程`には、合意した公開範囲と、コミット・プッシュ後に行う操作（PR/MRの作成とタイトル・本文の指定、リリース作成、タグ付けなど）を書く。
公開範囲の確認が不要で公開後の固有操作もない計画は`なし`とする。

## バグ調査

作業種別が`バグ対応`の計画では、原因分析を記録した関連WIの`## 原因分析`を参照する。
複数バグでは、各バグの見出しと現象・期待する契約の記録先まで一意に再取得できることを確かめる。
計画ファイル（バグ）を作るのは、入力WIがない計画（`関連WI: なし`）か、起草時にWIの原因分析を訂正・追加した計画に限る（`## 原因分析`を持たない登録済みAWIを処理する計画もこの追加に当たる）。
訂正・追加では対象のバグ単位だけを完全な表で書き、実態との乖離の観測結果と導いた結論を`## 変更履歴`に記録する。
計画ファイル（バグ）には計画の主題のH1見出しを置き、バグ単位ごとのH3見出しの下に原因分析表と調査表をこの順に置いて全セルに値を書く（見出しはH1とH3だけ、各H3配下の表はこの2つだけとする）。
行名、列名、並び順、統合・分割の規則、恒久化の参照規約は`agent-toolkit:wi-standards/references/analysis-records.md`「原因分析の記録先」に従い、類似箇所の見直し結果も同所に沿って調査表に記録する。
`check_plan_file.py`は、作業種別が`バグ対応`でメタ情報に`計画ファイル（バグ）`行を持つ計画について、ファイルの実在、計画ファイル名（stem）との一致、計画ファイル（バグ）の構造を検証する。
`関連WI`が`なし`のバグ対応計画ではこのメタ情報行を必須とする。

## 要件の成立性

`## 要件・外部仕様`は、消費主体が得る結果とそれを損なう要因を計画ファイルと関連WIから把握でき、正常系と主要な異常系の再現手順、既存の正常動作手順への影響を評価できる粒度で書く。

仕様の整合性を確かめる主な観点は、データの送受信、条件分岐、制約、機能廃止、外部から観測される挙動、配布形態である。
共有されるインターフェース仕様（契約）は呼び出し側と提供側の双方を同じ計画内で確定し、変更する分岐の入力パターンと変更前後の動作結果を正しく対応付ける。
制約の追加などで既存の正常動作シナリオが成り立たなくなる場合は、ユーザーとの合意内容と根拠を記録する。
機能廃止に伴う完成条件、チェックリスト、テストコードの更新方針、外部挙動を実機で確かめた根拠、プロジェクト規範が定める配布手順、バージョン更新、同期対象ドキュメントの修正も漏れなく計上する。

## 計画した検証の実行

実装担当者は、計画の`## 検証`（訂正済み検証表がある場合はその表）の各コマンドを対象worktreeで上から順に標準実行する。
実行直前に、実際のGit差分と直接影響範囲が検証対象に含まれることを確認する。
途中で失敗しても残りを実行し、各コマンドの終了コードと出力から総合的に合否を判定する。
検証表の書式・訂正・引き継ぎは「検証と公開工程」が定める。
