## 要件・外部仕様

`## 要件・外部仕様`には`### 受入シナリオ`を置き、ほかは任意H3で分ける。
仕様・設計の確定前に消費主体、利用目的、結果から行う判断・行動を特定する。
`agent-toolkit/share/rules/common/01-agent.md`「QCDと3段判定」に従い、明示要求と当然必要な要件から期待結果を導く。
内部変更・エージェント向け文書も利用場面に必要な粒度で書く。
既存の目的・利用目的・受入シナリオへ、依頼の役割と今回の結果を引き継ぐ。
関連変更の必要性と明示された限定・認可・成果物制限も確認する。

- 要件と、消費主体が観測する外部仕様（入出力、表示、公開契約、状態遷移、分岐条件、異常系、運用手順）
- 変更ファイル・識別子・契約、生成・配布、直接影響範囲。
  同じ値や挙動の別発生源（デフォルト値、プリセット、設定、環境変数、別の呼出手段、同じ操作の制約規定など）も保持先・利用先・観測結果まで追い、除外には理由を書く。
  共通CSSや関数・設定のデフォルト値など多数へ作用する挙動は、それを前提とする指定を検索して網羅し、変更後の結果を確認する。
  手元のデータ測定だけで代替しない。
  機能追加・統合で役割が変わる成果物は、名称、利用案内、ナビゲーション、運用ログ、配布metadata、既存テストなど意味が変わる箇所も網羅する
- 完了条件。
  必要成果、公開入出力、品質・認可・制約と合否の観測結果を書く。
  エージェント選定の検証コマンドは実現手段として区別する
- テストを新設・変更する場合は、保証する契約と検出する主な失敗様態。
  期待値は要求仕様や契約から導く（選定と導出は`agent-toolkit:commit/references/testing.md`に従う）
- 事象を起こさないことを求める要求では、発生件数0件を客観的に観測する手段
- エンドユーザーが観測できる公開インターフェース（設定キー、CLIオプション、環境変数、サブコマンドなど）を新設する場合は、新設の理由と、既存のインターフェースやデフォルト値の変更では目的を達成できない理由
- ユーザー確認の回答（公開範囲を含む）と、`../../user-confirmation-and-report/references/user-confirmation-and-report-authorization.md`「原文からの具体化を要する軸」の判定結果
- 実行環境の動作条件を前提とする設計方針では、実機で再現を確かめた典拠
- 永続化されるデータや増え続けるデータを扱う場合は、保持期間、容量上限、上限到達時の外部仕様、保守の契機と所有者、長期的な動作条件の検証方法（基準は`agent-toolkit:commit/references/design-time.md`に従う）

`### 受入シナリオ`には`シナリオ | 由来 | 消費主体と入口 | 利用目的と後続行動 | 操作 | 期待結果 | テスト`の7列の表を置く。

- `消費主体と入口`には結果を受け取る主体と呼び出し手段を、`利用目的と後続行動`には利用の目的と結果を受けて判断・実行することを書く。
  `操作`には具体的な入力値や初期状態を、`期待結果`にはその利用場面と有効な要求から導いた結果と検出する失敗を書く。
  実装着手前に、この対応からテストを選べる程度まで具体化する。
  `由来`にはWIの完成条件、逐語引用した要求単位、ユーザー指示の該当箇所などを書く
- `## 実施内容`に`採用`か`部分採用`の行があれば、人間由来の各要求単位と、`plan-file-standards-scope.md`「実施内容」で必要性を評価した後の各WIの有効な完成条件を1つ以上の受入シナリオ行に対応付ける。
  除外した条件は採否記録の対象条件と根拠を参照し、残る有効条件で完成を判定する。
  採用行がなければ本文を`なし`とする
- `テスト`には、公開された呼び出し手段（コマンド、画面操作、API、フックなど）を通じて同じ契約違反を検出する結合テストかE2Eテストの名前を書く。
  同じ操作と期待結果で各要求の合否を判定できる場合に限り、複数の要求を1行にまとめてよい。
  「一連の完成条件を後でテスト化する」のような参照だけの記述は具体化の完了にならない。
  自動テスト化が難しいシナリオに限り、その理由と、手動観測の入力値、操作手順、合否基準を書く
- 手動観測は、実装担当者が専用worktree内の成果物へ直接実行できる入力と操作で定め、公開、配布、稼働中の`atk wi process-loop`への反映の後にしか得られない観測を統合後へ先送りしない。
  WIの完成条件そのものが公開後にしか観測できない場合の判定は、実行レビュー担当者が`agent-toolkit:/share/exec-review-recording.md`に従って行い、計画ファイルには公開前に再現できる代替観測を置く。
  `atk wi process-loop`など本番の常駐プロセスから起動される対象は、`agent-toolkit:delegation/references/acceptance-scenarios.md`「常駐サービスの公開前の観測」に従う
- 操作、障害注入、擬似故障、自動終了の失敗などを含むシナリオは、同書の「検証資源の分離」に従って実行環境と利用の調整方法を定める
- 処理時間など負荷や並行状況で変わる測定値は、`agent-toolkit:wi-standards`の`references/awi-body.md`の完成条件と同じく、同じマシンで同時に実行する対照群との比較で書く

完了条件、受入シナリオ、手動観測で文書（規範、配布原本、設計記録、ガイド、コメントなど）の文意を判定するときは、同じファイルから転記した文字列の有無や、部分文字列・行単位の正規表現の一致だけで合否を決めない。
文意は、実装を通じた結果、他の定義との整合、検証コマンド、実行レビュー、該当節の正確な読解（対象ファイル、見出し、根拠の文の引用と判定結果を記録する）で総合的に判定する。
文字列検索は、精読する候補の抽出と、見出し、設定キー、パスなど行構造で一意に決まる実体の有無や件数の確認に使う。

変更の種類に応じて次も書く。

- 既存の外部仕様や内部規約を変える場合: 変更前の仕様を固定値で検証している既存テストなど、自動チェックの改廃方針
- 公開された呼び出し手段を置き換えるか廃止する場合: 新しい手段だけで同じ利用シナリオを最後まで完遂できることの検証（存在確認、モック、部分的な疎通確認、古い手段を併用した確認では代わりにならない）
- 工程の契約（起動の契機、待機、完了条件）を置き換える場合: 利用側に旧契約の義務（旧工程の起動、完了待ち、結果の受け渡しなど）が残らない確認も受入シナリオへ含める
- 禁止規定や制約を新設する場合: 既存の箇所へ遡って適用するか、今後の変更にだけ適用するか
- 規範、エンドユーザー向け文書、メッセージ文面などを変える場合: 変更対象の規約、該当ファイルと見出し、置換の対象範囲。
  文面は実行工程で確定し、文面の確定自体が要件の場合（ユーザーが指定した場合など）に限り言語指定付きのコードブロックで書く

直接影響範囲は、変更した定義・文言・パスなどを参照・呼出・生成・期待値に用い、連動修正が必要な箇所の全体を指す。
操作の副作用を指す「影響範囲」と区別し、旧識別子を使わず旧挙動を前提とする指定も含む。
実行処理の変更、旧値・識別子・公開手段名の固定文字列検索、周辺テスト、共通入出力（通知・生成物・設定など）の追跡を組み合わせて特定する。
仕様変更では読み書きする保持先（列・フィールド・ラベル・設定キー・ファイル名など）も検索する。

- 外部から観測できる文言を変える場合: 変更前の文言を期待値に固定しているテストを文言そのものの検索でも特定し、対象ファイルに含める。
  新設するテストの根拠は、同じファイルからの転記ではなく独立した仕様から得る
- ファイルを改名、移動、廃止する場合: 変更前のパスを固定文字列で検索し、文書、規範、コード、設定、テストの参照元を網羅する（隠しディレクトリも漏れない検索条件を使う）
- 仕様や概念の意味を変える場合: 変更前の意味を表す語句を、設計書、エンドユーザー向け文書、エージェント向け文書、docstring、コメント、データモデルのカラムコメント、生成物の入力元などから探す。
  語句の一致だけで判別できない場合は、意味を区別する文脈条件と併せて判定する。
  工程の契約を変える場合は、呼称と識別子（スキル名、コマンド名、hook名など）の両方で利用側を探し、各箇所の現行の指示を新しい契約と比べる（義務は片方だけで書かれることがある）

特定した直接影響範囲は変更対象ファイルに含めるか、含めない場合は理由を直接影響範囲の記述欄に書く。

完了条件の書き方:

- 増減の方向や数値目標を置く場合は、基準値、目標値、再実行できる測定手順を書き、再現性を確かめられる客観的な指標で合否を判定する
- コミットのOID（ハッシュ値）はrebaseで変わるため固定文字列で書かず、判定時点の作業ツリーから解決する
- 一致0件を合格とする条件は、`<検索コマンド>; test "$?" -eq 1`のように0件のとき合格となる形で書く（努力目標）
- 件数を期待値とする検索条件は、見出し、定義、設定キーなど判定対象の実体の行構造に合わせて絞り、起草時に同じ条件で測った件数を期待値にする（努力目標）。
  見出しの検索は行頭と行末を固定して数える
