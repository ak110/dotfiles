## 計画ファイルの構成

起草や更新の前に現行の作業契約を確認し、`${CLAUDE_PLUGIN_ROOT}/share/work-contract-boundaries.md`「工程境界での要求と成果の確認」に従って、計画の対象と維持する対象が当初の目的と現在の要求に一致するかを確かめる。
要求が変わったら作業契約へ反映し、計画凍結後は既存のレビュー指摘管理表と`review_contract`の原本を保持する。

計画ファイルは次の順に書く。

1. H1の主題と、H1直下の要約
2. `### 計画メタ情報`
3. `## 実施内容`
4. 要求を書く節
5. `## 検証`
6. `## 進捗ログ`

要求を書く節は、通常AWIの本文と同じ見出しを同じ順に置く。
`## 反映内容と反映先`、`## 原因分析`、`## 調査結果と判断根拠`、`## 完成条件`、`## ユーザー指摘の逐語引用`の順で、`## 反映内容と反映先`を必須とし、ほかは書く内容がある場合に置く。
各節に書く内容と書き方は、定義元である`../../wi-standards/references/awi-body.md`とその条件別資料だけが定める。
同書の「AWI」は計画、「起草者」は計画の起草者、「処理担当」は実装担当と読み替える。
構造の検査も、要求を書く節には通常AWIの本文と同じ検査を使う。
見出しを加えられるのは要求を書く節の配下に限る。
規範の適用範囲は文書パス・節名で示す。

計画には、関連WIの本文と対象リポジトリの現物から決まらない部分だけを書く。
関連WIはファイル名・1行要約を記し、確定済みの目的・要件・原因分析・範囲・方式・成立根拠・完成条件は再調査・再記述せずに参照する。
共通参照は読込表に従い指定箇所・ユーザー記入欄を読み、固有本文と採否・計画を確定する。
完成状態は関連WIと計画の目的・反映内容・原因分析・補足条件から導く。
任意節・引用位置の省略だけで再起草・再調査しない。
WIの再導出は`関連WI: なし`・対応節欠落・現物との乖離確認時に限り、影響項目だけに行う。
完成条件と手段の必要性を現在の目的・方針で判定することは再導出に当たらず、`plan-file-standards-scope.md`「実施内容」に従って常に行う。
乖離の事実・結論は`## 調査結果と判断根拠`へ記録する。
人間由来の要求範囲変更は`../../wi-standards/references/wi-standards-origin.md`「由来と承認」、原因分析の乖離は`plan-file-standards-verification.md`「原因分析」で扱う。
`agent-basics:bugfix`の基準への不適合も、原因分析の乖離に含む。
固有の公開後の操作（PR/MRの作成とタイトル・本文の指定、リリース作成、タグ付けなど）と合意した公開範囲は、ある場合だけ`## 反映内容と反映先`の項目として書く。

キューにない素材の原文とユーザーの回答全文は計画外入力の原本として保持し、調査、起草、初回レビュー、再レビューの各工程へ原文の参照を渡す。
`ユーザー指示`由来の行を`採用`か`部分採用`とした計画では、`## ユーザー指摘の逐語引用`を必ず置く。

実装着手前の指摘対応・要件追加・方針変更は各節へ統合して最終結論だけを残し、起草中の経緯は書かない。
`ユーザー指示`・`人間由来のWI`の`実施内容`欄は、`../../../share/exec-review-responses.md`「安全な修正」に従って原文を保ち、修正案を別行へ加える。
実装着手後は計画ファイルを変更しない（以下「計画凍結」）。
実装中に確定した要件変更と、記述の不整合に採った解釈はレビュー指摘管理表に記録する。
実行工程で直すと実行レビューの指摘になり、不要な往復が生じるためである。
例外は`## 進捗ログ`への追記だけとする。
凍結後に検証条件を訂正するときは、`plan-file-standards-verification.md`「検証」の訂正済み検証表に反映する。

## 要約と計画メタ情報

H1直下の要約は全体像・目的・対象範囲の順に簡潔に書き、変更時は全体を書き直す。
`../../wi-standards/references/drafting-completion-evidence.md`「既存証拠の再利用」に従う。

要約の後ろ、最初のH2より前に`### 計画メタ情報`を置き、H1直下の見出しはこの1件だけとする。
項目と順序は`plan-file-standards-template.md`「初回起草の雛形」に従う。
コロンはASCIIの`:`とし、後に半角スペースを1つ置く。
`関連WI`と`作業種別`以外の値はバッククォートで囲む。

- `作業種別`は`バグ対応`か`通常変更`とする。
  バグ対応の要求単位が1件でもあれば`バグ対応`とする。
  `## 検証`の`変更範囲の検証`は全要求単位の変更対象を覆う
- `関連WI`には入力のAWIとUWIのファイル名を1件1行で書き、コロンに続けて1行要約を添える。
  入力WIがなければ`- 関連WI: なし`とする
- `対象リポジトリ`は、計画構造の自動チェックツールへ渡す`--work-dir`のGitルートと同じ値にする（`agent-toolkit:process-wi`のレーンでは専用worktreeの絶対パス）
