# 状態と依存：終了

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 終了

AWIを終了する主体は、`adopt`のメモの冒頭に、`awi-body-content.md`「節の構成と分担」のH1直下に記載された変更要求を実施した結果として、具体的に何をどのように変更したかを1文で簡潔に記述する。
回答済みUWIを終了する場合は、ユーザーの回答を踏まえて実際に実施した対応内容を1文で記述する。
元AWI側にまだ残作業があるときは、その未完了の作業ときちんと区別して記録する。
一方、`reject`のメモの冒頭には、要求を採用しなかった理由を1文で記述する。
コミット情報やレビュー記録などの詳細は、その1文の後ろに配置する。
メモで使用する語彙は、`SKILL.md`冒頭に定められた用語基準に合わせる。

`adopt`または`reject`を実行して項目を終了する主体は、実行直前に`--note`や`--note-file`へ指定する処理結果の事実関係を十分に確認する。
事実として記載する内容は、対象のプラットフォーム、ランタイム、および呼び出し手段において自ら観測したものに限る。
別環境での観測結果を用いる場合は、動作の同等性が確認できている範囲に限定する。
処理結果の記述から参照するcommit、PR、CI run、外部サービスへの操作などは、正常に完了したことを実際に確認したうえで、後続の担当者が確実に解決できる形式の識別子を記載する。
未完了の処理や未観測の事項がある場合は、本文の記述を見直してから完了形として記録する。
`--commit`を伴う採否操作では、リビジョンを正しく解決でき、かつoriginが対象リポジトリと一致しているworktreeの絶対パスを`--target-repo`に指定する（単に識別することだけが目的の操作であれば、保存済みの正規化URLも利用できる）。
リビジョンを解決できない場合は、終了コード2を返して状態を変更せずに停止する。

`rejected`は、エージェントのみが起票した要求のすべてを技術的な根拠に基づいて不採用とする場合、または人間由来の要求のすべてについてユーザーが不採用を明示的に承認した場合に限って適用する。
技術的な失敗、必要な情報の不足、外部条件の成立待ち、計画の不備といった要因によるものは`active`のまま維持する。
不採用確認の回答がまだ得られていない項目は、すでに採用可能な範囲が含まれていたとしても項目を分割せず、全体を確認のUWIへの依存で待たせる（「承認型UWIと元項目」）。
その他の要因については、`states-and-dependencies-dependencies.md`「着手不能要因の分類」に従って整理する。
技術的に解消できない問題や作業を継続できない理由は未達事項として記録し、状態は`states-and-dependencies-dependencies.md`「着手不能要因の分類」に沿って適切に保つ。

すでに採用された内容を同じリポジトリ内の別の項目へ統合した場合、元の項目を`rejected`に変更することはせず、統合先の項目を`note`に記録する。
元の項目が`rm`の対象となる`inbox`または`hold`であり、かつ操作主体の担当範囲および書き込み権限の範囲内にある場合に限り、`rm`を使って削除する。
現在`processing`の項目や、すでに`adopted`となっている項目を、本規定のみを理由として状態変更したり削除したりすることは行わない。
検収を終えた別リポジトリへの移管については、既存の「複数リポジトリへの投入」に定められた元項目の移管手順に従う。

エージェント自身が誤って投入した項目は、`atk wi rm`で削除するか、`atk wi edit`で本来の正しい要求内容に書き直して再利用する。
`rejected`は、成立する要求を正当な理由で不採用とする場合に限って用いる。
削除した項目はprivate-notesのGit履歴から復元できるため、削除にあたってユーザーへの事前確認は不要である。
上流リポジトリに対する改訂が必要となる要求については、[cross-repository-submission.md](cross-repository-submission.md)に従って対処する。
