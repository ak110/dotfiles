# 起草完了の条件

本書は`agent-toolkit:wi-standards`「通常AWIの本文」の`### 起草完了の条件`の本文であり、通常AWIを投入する前に採否と実現方式を確定する条件を定める。

採否と実現方式は投入前に一案へ確定し、本文へは確定した一案だけを保存する。調査結果に依存する未確定事項は投入前に解消する。不採用と確定した代替案は、採用案の根拠を理解するために必要な範囲で記録してよい。
完成条件を固定する前に、起点資料の目的とエージェントが選んだ中間手段を分け、消費側に必要な結果をその機構を省いた既存操作で得られるか比較する。安全対策、検収用の記録、例外・フォールバックと直接影響範囲の既存機構も対象とする。比較は`agent-toolkit:writing-standards`の`references/design-heuristics.md`「自作機構の兆候と自問」に従う。結論を`## 実現性`へ反映してから採否と外部可視の完成条件を確定する。
対象集合の見直し、存廃、要否や仕分けを求める依頼では、投入前に各対象の判定と根拠を本文で確定する。形式は本文の表へ1件1行で並べることを推奨する（対象の一部が未判定であることを見つけやすいため）。
先行成果物から登録項目を選ぶ場合も仕分けに含め、登録しない項目の理由を現物で確かめて記す。
委譲先が述べた理由も現物で確認し、種類別の方針だけで個々の採否を処理担当へ委ねない。
判定に連動して変わる対の対象（規範条文、テスト、設定、登録、状態など）も同じ表へ含める。
単一の対象を変更する依頼は、この仕分けの対象から外す。
採用の可否は、要求が解決する事象が実在することと、その要求が対象リポジトリの明文化された方針のうち目的・要件に関するものへ反しないことで判定する。手段に関する方針と衝突する要求は、`agent-toolkit/rules/01-agent.md`「QCDと3段判定」でQCDが明らかに改善する場合に採用し、逸脱として扱う。実現方式の成立は、その方式が依存する公開契約、実行環境の機能、対象実装が現に存在することを現物の観測で判定する。いずれかが未確定の間はAWIを投入せず、調査を続けるか、認識の違いで要件や結果が変わる未確定事項をユーザー確認する。確定するのはここまでとし、その方式の内部設計、変更対象ファイルの分解、実装単位と検証手順は投入した後の計画工程が確定する。
観測事象を契機とする要求では、起草者が`agent-toolkit:bugfix`を起動し、直接的原因と根本原因を現物の観測で確定してから対策の実現方式を1案へ確定する。

起草の前に、事象を観測した入力・成果物、欠陥を生成した実装、変更する定義、変更後の検収場所を分けて特定する。`target_repo`は変更する定義を所有するリポジトリとし、事象を観測した場所は特定の補助として扱う。外部ツール、SDKまたは共有設定の欠陥が消費側のリポジトリで表面化した場合は、生成側のリポジトリへAWIを投入し、消費側で再現する条件を`完成条件`へ保持する。投入するのは、本文が示す反映先と変更対象の所有者が`target_repo`と一致する本文とする。
ユーザーが出力だけを示して発生箇所を明示しない場合は、出力の書式を手掛かりに、エージェント自身の実行環境と対象リポジトリの成果物のコマンドを実行する仕組みを候補へ含める。製品のツール実行やサンドボックス、CI、配備先などの実行元を実装から探し、候補ごとに同じ出力が生じる条件を確かめる。候補を1件に絞れなければ、推定した箇所を確認の共通前提へ置かず、発生箇所そのものを選択肢で問う。

エージェントが起草する通常AWIで原因に可変値を用いる場合は、事象時点との比較結果を`## 原因分析`へ記録する。事象後の値しか得られない場合は原因を未確定とし、その値を前提とする対策を確定しない。利用者が選んだ値、品質、適用範囲に関わる対策では、それらを維持する根拠か変更への明示的な合意を同節へ記録する。
確定に要する調査をそのセッションで実施できる場合は実施する。完成条件が名指しする並列度や閾値、上限値などを実行で確定できる場合は、その実行も投入前の調査へ含める。完成条件に現れる値は前段が計画工程へ委ねる内部設計とは区別する。原因を現物の観測で確定できない場合は投入前の調査を続け、確定に必要な情報が得られない場合はユーザー確認する。投入するのは、調査の結果によって対象、反映先または完成条件が変わらない段階まで確定した本文とする。次の処理主体が本文から採否を判断するためである。
認識の違いで要件や結果が変わると判明した未確定事項は、ユーザー確認で回答を得るかUWIへ分離し、回答を得られない場合はその事項に依存するAWIを回答まで保留する。
協調モードで動作するセッションから投入する場合は、本文が確定していない対象、適用範囲、外部可視の結果と除外内容の調査を投入前に完了し、認識の違いで要件や結果が変わる未確定事項はユーザー確認で回答を得てから投入する。確認の要否はその調査の結果として判明するためである。処理側で確認が必要になった場合の手段は`agent-toolkit:user-confirmation-and-report`「手段の選択」に従う。回答を得られない条件では依存する実装が保留されるため、投入前に要求を確定する。
ファイルや仕組みの撤去、改名、意味の変更を求める原稿では、`## 反映内容と反映先`を確定する前に、変更前のパスと概念を表す語を対象リポジトリ全体（隠しディレクトリを含む）で固定文字列検索する。一致した参照元は反映先へ含めるか、含めない理由を本文へ書く。探索の方法は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」の参照元の探索に従う。撤去対象を直接参照する規範とスクリプトだけを個別に検索すると、変更前の意味を保持する設計文書や利用者向けガイドが反映先の候補から外れる。

確定したと判定できるのは、その事項の結論が本文へ現れる場合に限る。調査を別の要求単位へ分離することと、後続の計画工程へ移すことは、確定に当たらない。
エージェントが調査で確かめられる事項を確かめないまま投入しない条件は、通常AWIに限らずAWI全般とUWIにも同じく適用する。UWIで問う対象はユーザーだけが持つ値と起草者が確かめる手段を持たない事項に限る。エージェント環境から起動した`atk wi add`と`atk wi edit`は本文の表の`直接的原因`行が未確定を宣言する値（「未確定」「不明」「未特定」「調査中」「未確認」のいずれかが冒頭に単独で置かれるか、直後に句読点・空白・括弧・Markdown装飾の閉じ記号が続く値）を持つ場合に保存を拒否する。
原因と対策の実現方式が未確定の項目を受け取った処理側は、原因の調査からやり直し、確定する対策が投入時の内容から変わる。
本書の条件の適用を要する要求を受領した時点で、何を列挙し何をユーザー確認するかをユーザーが観測できる出力へ宣言する。宣言は受領したturnの中で行い、調査の完了を待たないことを推奨する。早く宣言するほど、ユーザーが列挙と確認の範囲を訂正できる時機が早くなる。

## 方針と判断の記録との比較

本節は`agent-toolkit:wi-standards`「通常AWIの本文」の導入目的の調査から参照される。
導入目的と由来の調査先には、変更履歴に加えて、対象リポジトリのエージェント向け文書（`AGENTS.md`など）が所在を示す、利用者が確定した方針と判断の記録を含める。記録が索引と分割ファイルに分かれる場合は、変更対象のファイル名、工程名、機能名や条文の特徴的な語で分割ファイルを検索し、一致した節の本文と比べる。比較は変更対象ごとに行う。依頼全体に対する一般方針だけを確認して、個々の対象と記録の対応を確かめる作業を省かない。
目的・要件に関する記録と衝突する対象の変更は、人間が確定した判断の変更に当たる（`agent-toolkit/rules/01-agent.md`「協調と自律」）。手段の方針の記録との衝突は同節に従う。比較で衝突が見つかったら、まず現在の逐語要求が定める目的・結果・対象集合を記録の判断と比べ、`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」と成立済みの認可を適用する。現在の明示要求の目的・結果・集合が記録の対象を含み、その変更を求めている場合は、記録の判断の固有名や変更を名指ししていなくても、その要求を適用する。例えば通知全般を必要なものへ減らす依頼は、以前に全件通知すると決めた項目も対象に含む。
この適用を経ても残る事項だけを、認識の違いで要件や結果が変わる未確定事項として投入前に扱う。残るのは原文から変更を導けず目的側の判断の変更が残る場合（変更の意向を含まない調査の依頼など）、未合意の選好や認可、硬い制約やホスト契約と両立しない場合である。名指しの欠落だけを未確定の理由にすると、既に要求された変更を利用者へ問い直す確認が生じる。記録と比較した結果（一致した記録の所在と判定か、一致が無いこと）は導入目的の調査記録と同じH1直下へ書き、対象ごとの判定表を持つ本文ではその表の対象ごとの行へ書く。
