# 状態と依存：承認型UWIと元項目

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 承認型UWIと元項目

1. 事後承認型UWIは、元の作業の進行を妨げないため`depends_on`には追加しない。
   元の項目は、ユーザーからの回答を待たずに終了させる。
   `question_type: post-approval`が指定された事後承認型UWIに対して`その対応で問題無い`という選択肢のみが回答された場合、`atk wi answer`と`atk serve`は回答の保存と同時に項目を`adopted`へ遷移させる。
   保存済みの標準的な2択`choice`で同様の回答があった場合も同様である。
   一方、一般的な`yes-no`形式の回答、否定的な回答、または追加の記述が含まれる回答については、回答済みの状態のまま保持され、通常の手順で取り込まれる。
   是正を求める回答が届いた場合は、`origin-and-approval-comments.md`「ユーザー専用の記入欄と是正要求」の手順を適用し、そのUWI自身を作業要求として処理する。
   新しいAWIの起票は不要である。

2. 事前承認型UWIを保存したら、元の項目の`depends_on`へそのUWIを加え、回答待ちを編集目的の`hold`と区別する。
   `atk wi set-dependencies <元項目のファイル名> --depends-on <UWIのファイル名>`を実行する。
   このコマンドは依存を指定した集合で置き換えるため、元項目が既に持つ依存先も`--depends-on`へ並べる。
   元項目が`processing`の場合は、依存を保存した後に`atk wi return-to-inbox <元項目のファイル名>`で`inbox`へ戻す（依存の保存より先に戻すと、依存の無い`inbox`の項目を別の処理主体が取得し得るため）。
   未回答のUWIを待つ元項目は着手可否判定で`blocked`となり、処理候補に入らない。
   `atk serve`のWI画面は、この項目へ`blocked`のバッジを表示する。

## 回答済みUWIの取り込み

1. 回答が保存されたUWIは処理候補に入り、そのUWIを`depends_on`に持つ元項目も同じキュー内の依存待ちとして処理候補に入る。
   次回そのキューを処理する`agent-toolkit:process-wi`のメインエージェントは、両方を同じ実行の処理対象へ加える。
   進行中の`agent-toolkit:process-wi`の実行中にユーザーから回答が伝えられた場合は、`../../process-wi/references/selection-procedure-addition.md`「処理対象WIの追加」に沿って取り込む。
   メインエージェントは、UWIとその元項目を同一の作業レーンへ割り当てる（具体的な操作順序は同文書を参照）。
   割り当てられたレーンが回答内容を反映したうえでUWIを終了し、依存が解消した元項目を処理して終了させる。
   もし回答内容によって元項目側の追加作業が不要となった場合は、メインエージェントがUWIを終了させたうえで、元項目のみを処理対象として追加する。
   同一の元項目が依存している未回答のUWIが他に残っている間は、元項目は`blocked`のまま処理候補に入らない（1件のUWIには1つの問いだけを持たせる運用のため、1つの元項目に対して複数のUWIが紐づく場合があるためである）。
   回答済みのUWIは先に終了してよい。
   UWIには元項目のファイル名と回答の判断に必要な情報のみを保持させ、作業再開時の手順については、担当レーンが元項目の計画ファイルにある進捗ログから読み取る。
   計画ファイルが存在しない場合は、依存の保存時に`atk wi edit <元AWIのファイル名> --append --body-file <絶対パス> --target-repo=<対象リポジトリ>`で元AWI本文へ追記した再開手順を、`## 処理結果`の後ろから読み取って確認する。
   公開追記として保存された内容は、元の要求内容と分離して管理されるためである。
