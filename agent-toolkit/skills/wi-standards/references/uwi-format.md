# UWI本文の書式

UWI本文は、回答者が対象ファイルと他のキュー項目を参照せずに判断できる状態を満たす。

冒頭へ、回答者が何を回答するかを示す疑問文を置き、必要に応じてその問いが生じた目的を同じ位置へ続ける。疑問文は1文に収めることを推奨する（回答者が最初に問いを把握できるため）。表題を置く場合も問いを含む文とし、背景説明は問いの後に続ける。
1件のUWIが問う問いは1つとする。複数の問いは、各問いの回答が他の問いの選択肢か選んだ結果を変えない場合に独立とし、独立した問いは問いごとに個別のUWIとして投入する。個別のUWIはそれぞれ本文だけで判断できる内容とし、事前承認型では各UWIが同じ元項目のファイル名を持つ。他の問いの回答で選択肢か選んだ結果が変わる問いは、組合せを選択肢とする1つの問いにまとめる。独立した問いを1件へ束ねると、選択肢を1組しか持てない回答欄で問いごとの選択肢を示せず、全体への回答を個別の合意として扱うことになる。
回答形式は`--question-type=choice`で`--choices`へ各選択肢の短い名前を渡すか、2択の可否を問う場合は`--question-type=yes-no`とする。次に`## 選択肢と帰結`のH2を置き、選択肢と各選択肢を選んだときの結果を書く。値の指定、ログの貼り付けや実機確認の結果のように選択肢を列挙できない回答を求める問いも、回答の扱い（回答欄へ書き込んで返すか確認できないかなど）を選択肢として示す。回答欄は選択肢で値を入れた後に書き足せるため、選択肢に無い回答も受けられる。
最後に`## 判断材料`のH2を置き、次の基準で選んだ情報だけを書く。識別子は対象との関係を示す文脈語とともに用いる。

UWIへ書く情報は、ユーザーがその本文で使う用途（回答、是正の依頼、結果の把握、依頼された操作）のいずれかを持つものとし、情報ごとに用途を確かめて採否を決める。実施した内容、エンドユーザーが観測する影響、選択肢ごとの結果と判断に必要な理由は残す。
内部の再開工程や作業指示、調査の経過、本文の中での重複、ユーザーが手動で取り消すための方法やコマンドは本文から除く。是正は回答を受けたエージェントが行うため、取り消せるかが判断に必要な場合は、その性質とエージェントが是正を担うことだけを書く。回答後の処理に要る内部の情報は、計画の進捗ログか引き継ぎ記録へ残す。
対象、問いと回答による結果が本文だけで分かれば、本文が短くてもそのまま投入する。
本文の名詞は、回答者の発言に現れた語、一般に意味が一意な語、同じ本文で説明した語のいずれかとする。判定基準は`agent-toolkit:user-confirmation-and-report`の読込表で確認本文と選択肢を起草する前に読む`references/choice-construction.md`「影響と回答単位」末尾の語の確認に従う。工程名・担当名・チェック名などの内部の呼び名を説明なしで使うと、回答者は何を了承するのか分からないまま回答を求められる。規範が定義した名前の扱いも同書の同節に従う。
回答者が起動または使用している公開名（スキル名、コマンド名、ツール名など）は説明を付けずに使う。既に知っている語へ説明を重ねると、回答者は問いを探す手間を負う。
問いの文で内部の工程や作業の状態を指す場合は、その呼び名を使わず、何が済んでいて何が残り、回答で何が変わるかを書く。

ツールが自動付与する`## 質問`と`## 回答`の見出しは本文と同じ階層のH2となるため、本文へ置くH2はこの2つと異なる名前にし、節の区切りはH2までとする。
`agent-toolkit:completion-report`が作成する報告用UWIだけは、同スキルが定める固定H3を`## 判断材料`の内側へ置く。一般のUWIの見出し構成は用途に応じて選ぶ。
`atk wi add --type=uwi`へ渡す本文は質問本文だけとし、見出しと回答欄マーカーの付与はツールに任せる。既存UWIを起草の起点にする場合は、その見出しと回答欄を除去する。
`## 回答方法`節は置かない。ブラウザーUIがfrontmatterから選択肢を表示するため、UIが表示する選択肢と回答方法を本文へ重複して書かないためである。返信形式の指定が要る場合は、後述の実機確認の依頼と同じく`## 判断材料`へ書く。

`## 判断材料`へは起草時に実際に観測した結果または一次資料で確認した事実だけを書く。
起草者が調査や実行で確かめられる事項は投入前に確かめ、未確認のまま残さない。未確認の事項を残すと、回答者はエージェントが確かめられた事実まで推測して判断することになる。
ユーザーの手元にだけある状態など、起草者が確かめる手段を持たない事項に限り、確認していないことを同じ節へ書き、回答の前提から外す。

問いの主題と、選択肢を置く形式での選択肢の主題の選び方は、`agent-toolkit:user-confirmation-and-report`の「確認の選択肢を組む手順」に従う。

外部環境の実機確認を依頼する場合は、実行する主体、対象環境、必要な前提、番号付き操作、確認場所と取得値、本文へ直接記載した期待値、回答欄へ貼り付ける最小の返信形式および確認できない場合の記載内容を、その依頼の成立に必要な範囲で`## 判断材料`へ含める。本文で既に説明した情報は再掲しない。

1つの問いが複数の項目を扱う場合（共通する判断基準で群にまとめた項目の採否を1回で問う場合など）は、採否を分ける差分（判断に全文が要る場合は対象全文）、各項目の採用と不採用の結果、起票者の推奨と根拠を示し、項目に共通する情報は1か所へまとめる。項目ごとに独立した判断を要する場合は、冒頭の規定どおり項目ごとに個別のUWIとする。

事前承認型UWIは、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」で確認を要すると判定した解釈の相違かユーザーだけが持つ値と、それぞれで変わる外部可視の結果、起票者の推奨案を`## 判断材料`へ含める。
同じ節へ、保留した元項目のファイル名と対象の説明、必要な回答や資料と、回答で変わる結果を含める。回答後に元項目で再開する工程は、元項目の計画の進捗ログか引き継ぎ記録へ残す。
元項目とUWIの対応関係はUWIの本文だけが保持する。同じ判定で確認を要しない問いはUWIへ送らず自ら確定する。

事後承認型UWIは、実施済みの対応、その対応を選んだ根拠とエンドユーザーが観測する影響のうち、回答と是正の依頼に必要な情報だけを`## 判断材料`へ含める。実装過程の技術選択と調査経緯は起草者の手元にとどめる。
ユーザーの質問へ答える事後承認型UWIでは、質問の一つひとつへ`## 判断材料`で直接答える。「なぜ」を問われた場合は、なぜ起きたか・何を変えたか・今後どう防ぐかを、回答者が見つけられるよう段落の冒頭か小見出しで示す。この原因の説明は前項の調査経緯と別に扱う。冒頭の問いが名指しする説明（「理由」「対策」など）は、本文に同じ名前で実在させる。問いが本文に無い説明を名指しすると、回答者は存在しない説明の了承を求められる。
問いは`--question-type=choice`の2択とし、選択肢を`その対応で問題無い`と`問題がある`とする。
`問題がある`の説明には望む是正内容を回答欄へ書くよう求める文を置く。
