# UWI本文の書式

UWI本文は、ユーザーが対象ファイルと他のキュー項目を参照せずに判断できる状態を満たす。

冒頭へ、ユーザーが何を回答するかを示す疑問文を置き、必要に応じてその問いが生じた目的を同じ位置へ続ける。疑問文は1文に収めることを推奨する（ユーザーが最初に問いを把握できるため）。表題を置く場合も問いを含む文とし、背景説明は問いの後に続ける。
1件のUWIの問いは1つとする。他の問いの選択肢や結果を変えない独立した問いは分け、それぞれ本文だけで判断できる内容とする。事前承認型では各UWIに同じ元項目のファイル名を持たせる。回答が相互に選択肢や結果を変える問いは、組合せを選ぶ1つの問いへまとめる。
回答形式は`--question-type=choice`で`--choices`へ各選択肢の短い名前を渡すか、2択の可否を問う場合は`--question-type=yes-no`とする。次に`## 選択肢と帰結`のH2を置き、選択肢と各選択肢を選んだときの結果を書く。値の指定、ログの貼り付けや実機確認の結果のように選択肢を列挙できない回答を求める問いも、回答の扱い（回答欄へ書き込んで返すか確認できないかなど）を選択肢として示す。回答欄は選択肢で値を入れた後に書き足せるため、選択肢に無い回答も受けられる。
最後に`## 判断材料`のH2を置き、次の基準で選んだ情報だけを書く。識別子は対象との関係を示す文脈語とともに用いる。

情報は回答・是正の依頼・結果の把握・依頼された操作に使うかで選ぶ。実施内容、可視の影響、選択肢ごとの結果と判断の理由を保ち、対象・問い・回答による結果が分かれば短い本文でも投入する。
内部の再開工程や作業指示、調査の経過、本文の中での重複、ユーザーが手動で取り消すための方法やコマンドは本文から除く。是正は回答を受けたエージェントが行うため、取り消せるかが判断に必要な場合は、その性質とエージェントが是正を担うことだけを書く。回答後の処理に要る内部の情報は、計画の進捗ログか引き継ぎ記録へ残す。
本文の名詞は、ユーザーの発言に現れた語、一般に意味が一意な語、同じ本文で説明した語のいずれかとする。判定基準は`agent-toolkit:user-confirmation-and-report`の読込表で確認本文と選択肢を起草する前に読む`references/choice-construction.md`「本文の語」に従う。工程名・担当名・チェック名などの内部の呼び名を説明なしで使うと、ユーザーは何を了承するのか分からないまま回答を求められる。規範が定義した名前の扱いも同書の同節に従う。
ユーザーが起動・使用している公開名（スキル、コマンド、ツールなど）は説明を重ねない。
問いの文で内部の工程や作業の状態を指す場合は、その呼び名を使わず、何が済んでいて何が残り、回答で何が変わるかを書く。

ツールが自動付与する`## 質問`と`## 回答`の見出しは本文と同じ階層のH2となるため、本文へ置くH2はこの2つと異なる名前にし、節の区切りはH2までとする。
`agent-toolkit:completion-report`が作成する報告用UWIだけは、同スキルが定める固定H3を`## 判断材料`の内側へ置く。一般のUWIの見出し構成は用途に応じて選ぶ。
`atk wi add --type=uwi`へ渡す本文は質問本文だけとし、見出しと回答欄マーカーの付与はツールに任せる。既存UWIを起草の起点にする場合は、その見出しと回答欄を除去する。
`## 回答方法`節は置かない。ブラウザーUIがfrontmatterから選択肢を表示するため、UIが表示する選択肢と回答方法を本文へ重複して書かないためである。返信形式の指定が要る場合は、後述の「ユーザーへ操作を依頼する場合」の段落と同じく`## 判断材料`へ書く。

`## 判断材料`の事実は投入前の観測または一次資料で裏付ける。起草者が確かめられる事項は調べ、ユーザーの手元の状態など手段のない事項だけを未確認と明記して回答の前提から外す。
先行する記録の理由を問われた場合は、記録の存在ではなく元の判断へたどり、ユーザーの要件・合意、独立した観測・公式資料、エージェントの推定を区別して説明する。エージェントの推定だけに基づく判断は、主体と根拠の限界を示して是正を推奨する。明示判断や独立した観測を持つ記録は、作者にかかわらず元の根拠で評価する。
独立した根拠に基づく推奨を、問い、判断材料と選択肢ごとの結果へ一貫させる。是正の内容は元の要求に照らして確定し、認可と確認の要否は`agent-toolkit:user-confirmation-and-report`「確認要否の判定」に従う。

問いの主題と、選択肢を置く形式での選択肢の主題の選び方は、`agent-toolkit:user-confirmation-and-report`の「確認の選択肢を組む手順」に従う。

ユーザーへ操作を依頼する場合（外部環境の実機確認、昇格・配備・設定変更などの反映、権限の付与、プロセスの停止など）は、ユーザーが本文だけを読み、判断や読解を補わずに上から順に実行して、終わったことを確かめられる手順を`## 判断材料`へ書く。
実行する主体、対象環境、必要な前提、確認場所と取得値、本文へ直接記載した期待値、回答欄へ貼り付ける最小の返信形式および操作できない場合の記載内容を、その依頼の成立に必要な範囲で含め、操作は番号付きの手順にする。
操作する場所（画面と項目、MR、作業ツリーの絶対パスとコマンド、依頼先など）、具体的な入力値（MRの元branchと先branch、コマンドの全文、画面で入力する項目と値またはその値の求め方など）、その手順が終わったことの確かめ方の3点を各手順へ持たせる。
「運用判断に従い」「計画どおりに」のように、判断や資料の読解をユーザーへ残す表現を手順に使わない。ユーザーだけが決められる判断は手順から外し、問いか選択肢で扱う。
起草者が権限と到達を確かめて自ら行えると判定した工程（計画や差分の生成、読み取り専用の確認、MRの作成、ログの読み取りなど）はユーザーの手順から外し、エージェントが行うことと、ユーザーが判断に使うその結果を本文へ書く。
本文で既に説明した情報は再掲しない。

1つの問いが複数の項目を扱う場合（共通する判断基準で群にまとめた項目の採否を1回で問う場合など）は、採否を分ける差分（判断に全文が要る場合は対象全文）、各項目の採用と不採用の結果、起票者の推奨と根拠を示し、項目に共通する情報は1か所へまとめる。項目ごとに独立した判断を要する場合は、冒頭の規定どおり項目ごとに個別のUWIとする。

事前承認型UWIは、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」で確認を要する解釈の相違かユーザーだけが持つ値、各案の外部可視の結果と推奨案を`## 判断材料`へ書く。保留した元項目のファイル名と対象、必要な回答・資料も同節へ置き、内部の再開工程は元項目の計画の進捗ログか引き継ぎ記録へ残す。
元項目とUWIの対応関係はUWIの本文だけが保持する。同じ判定で確認を要しない問いはUWIへ送らず自ら確定する。

事後承認型UWIは、実施済みの対応、その対応を選んだ根拠とエンドユーザーが観測する影響のうち、回答と是正の依頼に必要な情報だけを`## 判断材料`へ含める。実装過程の技術選択と調査経緯は起草者の手元にとどめる。
ユーザーの質問へ答える事後承認型UWIでは、質問の一つひとつへ`## 判断材料`で直接答える。「なぜ」を問われた場合は、なぜ起きたか・何を変えたか・今後どう防ぐかを、ユーザーが見つけられるよう段落の冒頭か小見出しで示す。この原因の説明は前項の調査経緯と別に扱う。冒頭の問いが名指しする説明（「理由」「対策」など）は、本文に同じ名前で実在させる。問いが本文に無い説明を名指しすると、ユーザーは存在しない説明の了承を求められる。
事後承認の問いは専用の`--question-type=post-approval`で投入し、`--choices`を省略する。固定の選択肢`その対応で問題無い`と`問題がある`が表示される。一般の問いの`choice`・`yes-no`指定より本項を優先する。
`問題がある`の説明には望む是正内容を回答欄へ書くよう求める文を置く。
