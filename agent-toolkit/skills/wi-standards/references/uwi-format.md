# UWI本文の書式

UWI本文は、ユーザーが対象ファイルや他のキュー項目を参照せずに判断できる内容にする。

## 構成

冒頭へ、ユーザーが何に答えるかを示す疑問文（1文を推奨）を置き、必要ならその問いが生じた目的を続ける。表題を置く場合も問いを含む文とする。
1件のUWIの問いは1つとする。互いの選択肢や結果を変えない問いは別のUWIへ分け（事前承認型では各UWIに同じ元項目のファイル名を持たせる）、互いに変える問いは組合せを選ぶ1つの問いにまとめる。複数の項目を共通の基準で1回に問う場合は、採否を分ける差分、各項目の採用・不採用の結果、推奨と根拠を示し、共通の情報は1か所にまとめる。
回答形式は`--question-type=choice`と`--choices`（各選択肢の短い名前）か、2択の可否なら`--question-type=yes-no`とする。続けて`## 選択肢と帰結`に選択肢と各選択肢を選んだ結果を書く。値の指定やログの貼り付けのように列挙できない回答も、回答の扱い（回答欄へ書いて返す、確認できないなど）を選択肢として示す。回答欄は選択肢の後に書き足せる。
最後に`## 判断材料`を置く。問いの主題と選択肢の組み方は`agent-toolkit:user-confirmation-and-report`の「確認の選択肢を組む手順」に従う。

ツールが自動付与する`## 質問`と`## 回答`と同じ名前のH2を置かず、節の区切りはH2までとする（`agent-toolkit:completion-report`の報告用UWIだけは同スキルが定めるH3を`## 判断材料`の内側に置く）。`atk wi add --type=uwi`へは質問本文だけを渡し、見出しと回答欄マーカーはツールに任せる。既存UWIを起点にする場合はその見出しと回答欄を除く。
`## 回答方法`節は置かない。ブラウザーUIがfrontmatterから選択肢を表示するためである。返信形式の指定が要る場合は`## 判断材料`へ書く。

## 載せる情報

情報は、回答、是正の依頼、結果の把握、依頼された操作のいずれかに使うかで選ぶ。実施内容、可視の影響、選択肢ごとの結果と判断の理由を保ち、それが分かれば短い本文でよい。
内部の再開工程や作業指示、調査の経過、本文内の重複、ユーザーが手動で取り消す方法やコマンドは本文から除く。是正は回答を受けたエージェントが行うため、取り消せるかが判断に要る場合はその性質とエージェントが是正を担うことだけを書く。回答後の処理に要る情報は計画の進捗ログか引き継ぎ記録へ残す。
本文の名詞は、ユーザーの発言に現れた語、一般に意味が一意な語、同じ本文で説明した語のいずれかとする（`agent-toolkit:user-confirmation-and-report`の`references/choice-construction.md`「本文の語」）。工程名・担当名・チェック名などの内部の呼び名は説明なしで使わず、内部の状態は何が済み何が残り回答で何が変わるかで書く。ユーザーが使っている公開名（スキル、コマンド、ツールなど）はそのまま使う。識別子は対象との関係を示す語とともに使う。

`## 判断材料`の事実は投入前の観測か一次資料で裏付ける。起草者が調べて確かめられる事項は確かめ、ユーザーの手元の状態など手段のない事項だけを未確認と明記して回答の前提から外す。
先行する記録の理由を問われた場合は、記録の存在ではなく元の判断へたどり、ユーザーの要件・合意、独立した観測・公式資料、エージェントの推定を区別して説明する。推定だけに基づく判断は主体と根拠の限界を示して是正を推奨し、明示判断や独立した観測を持つ記録は作者によらず元の根拠で評価する。
推奨は問い、判断材料、選択肢ごとの結果へ一貫させる。是正の内容は元の要求に照らして確定し、確認の要否は`agent-toolkit:user-confirmation-and-report`「確認要否の判定」に従う。

任意の対応を選ぶ判断（関連作業の完了後に行うかをユーザーが選べる処置など）も、行う場合と行わない場合を選択肢として問う。行った結果の回答が後の作業に要る場合だけ、返信形式を次節の操作依頼と同じく書く。
ユーザー自身の秘匿値の露出への失効案内は、値を書かずに対象を識別できる短い判断材料（露出した値の種類と記録の所在）と、必要なら失効する旨だけで構成し、失効の要否と時機をユーザーへ残す。必須の再発行、認証方式の変更、詳細な操作手順と完了の回答は求めない。

## ユーザーへ操作を依頼する場合

外部環境の実機確認、反映、権限の付与などの操作を依頼する場合は、ユーザーが本文だけを読み、判断や読解を補わずに上から順に実行して完了を確かめられる番号付きの手順を`## 判断材料`へ書く。各手順には、操作する場所（画面と項目、作業ツリーの絶対パスとコマンド、依頼先など）と具体的な入力値（コマンドの全文、入力する値かその求め方など）、終わったことの確かめ方を持たせる。期待値、回答欄へ貼る最小の返信形式と、操作できない場合に書く内容も必要な範囲で添える。
「計画どおりに」のように判断や読解をユーザーへ残す表現を使わず、ユーザーだけが決められる判断は問いか選択肢で扱う。起草者が権限と到達を確かめて自ら行える工程（差分の生成、読み取り専用の確認、ログの読み取りなど）は手順から外し、その結果を本文へ書く。

## 承認型ごとの内容

事前承認型UWIは、確認を要する解釈の相違かユーザーだけが持つ値、各案の外部可視の結果、推奨案、保留した元項目のファイル名と対象、必要な回答・資料を`## 判断材料`へ書く。元項目とUWIの対応はUWIの本文だけが保持する。「確認要否の判定」で確認を要しない問いはUWIへ送らず自ら確定する。

事後承認型UWIは、実施済みの対応、選んだ根拠、エンドユーザーが観測する影響のうち、回答と是正の依頼に要る情報だけを書き、技術選択と調査経緯は書かない。`--question-type=post-approval`で投入して`--choices`を省くと、固定の選択肢`その対応で問題無い`と`問題がある`が表示される（一般の`choice`・`yes-no`より優先する）。`問題がある`の説明には、望む是正内容を回答欄へ書くよう求める文を置く。
ユーザーの質問へ答える事後承認型UWIでは、質問の一つひとつへ`## 判断材料`で直接答え、「なぜ」には、なぜ起きたか・何を変えたか・今後どう防ぐかを段落の冒頭か小見出しで示す。冒頭の問いが名指しする説明（「理由」「対策」など）は本文に同じ名前で置く。
