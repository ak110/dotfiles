# UWI本文の書式

UWIの本文は、ユーザーが対象ファイルや他のキュー項目を参照しなくても、単体で判断を下せる内容にする。

## 構成

冒頭にはユーザーが何に答えるべきかを示す疑問文（1文を推奨）を配置し、続けて問いが生じた理由、推奨する回答とその根拠を簡潔に述べる。表題を設ける場合も問いを含む文とする。
1件のUWIで扱う問いは1つに限る。互いの選択肢や結果に影響を与えない独立した問いは別のUWIへ分割する（事前承認型の場合は、それぞれのUWIに同じ元項目のファイル名を持たせる）。互いに影響を及ぼし合う問いは、組み合わせを選べる1つの問いにまとめる。複数の項目を共通の基準で一度に問う場合は、採否の分かれ目となる差分、各項目を採用または不採用にした際の結果、推奨方針とその根拠を示し、共通の情報は1か所に集約する。
回答形式には、`--question-type=choice`と`--choices`（各選択肢の簡潔な名前）を指定するか、二者択一の可否であれば`--question-type=yes-no`を用いる。続けて`## 選択肢と帰結`見出しを設け、用意した選択肢と、それぞれを選んだ場合に生じる結果を記載する。具体的な値の指定やログの貼り付けのように選択肢を網羅できない回答であっても、回答欄への記入方法や確認できない旨の扱いを選択肢として提示する。自由記入の回答欄は選択肢の後ろに追加できる。
文書の末尾には`## 判断材料`を配置する。問いの主題の選定や選択肢の組み立て方は、`agent-toolkit:user-confirmation-and-report`の「確認の選択肢を組む手順」に従う。

ツールが自動付与する`## 質問`や`## 回答`と重複するH2見出しは設けない。本文の見出しレベルはH2までとする（`agent-toolkit:completion-report`の報告用UWIに限り、同スキルが定めるH3見出しを`## 判断材料`の内側に配置できる）。`atk wi add --type=uwi`には質問本文を渡し、見出しや回答欄マーカーの付与はツールに任せる。既存のUWIをもとに作成する場合は、あらかじめ見出しと回答欄マーカーを除去しておく。
`## 回答方法`という節は設けない。ブラウザーUIがfrontmatterの情報に基づいて選択肢を表示するためである。返信形式の指定が必要な場合は、`## 判断材料`の中に記載する。

## 載せる情報

本文に記載する情報は、回答、是正の依頼、結果の把握、または依頼された操作の実行に役立つものに絞り込む。実施内容、目に見える影響、選択肢ごとの結果、および判断の理由が明確に伝わるのであれば、簡潔な本文で構わない。
内部の再開工程や作業手順、調査の途中経過、本文内での重複記述、ユーザーが手動で取り消すための手順やコマンドなどは本文から省く。是正は回答を受けたエージェントが担うため、取り消しが可能かどうかが判断に要る場合は、その性質とエージェントが是正を担当する事実のみを記載する。回答後の処理に必要な情報は、元項目の計画ファイルにある進捗ログへ記録する。計画ファイルが存在しない場合は、`atk wi edit --append`で元AWIの本文へ追記しておく。
本文で使用する語彙は、`SKILL.md`冒頭の用語基準に従う（確認の質問文については、`agent-toolkit:user-confirmation-and-report`の`references/choice-construction.md`「本文の語」を参照）。内部の状態を説明する際は、何が完了していて何が残っており、回答によって何が変わるのかという観点で記述する。

`## 判断材料`に記載する事実は、投入前の観測や一次資料で裏付ける。起草者が自ら調べて確かめられる事項はあらかじめ確認し、ユーザーの手元環境の状態など確認手段がない事項に限り、未確認である旨を明記して回答の前提から外す。
過去の記録の理由を問われた場合は元の判断まで遡り、ユーザーの要件や合意事項、独立した観測結果や公式資料、エージェントによる推測を明確に区別して説明する。推測のみに基づく判断は主体と根拠の限界を示したうえで是正を推奨し、明示的な判断や独立した観測結果を持つ記録は、作成者に関わらず元の根拠に基づいて客観的に評価する。
推奨する方針は、冒頭の問い、判断材料、および選択肢ごとの結果の間で一貫性を保つ。是正する内容は元の要求に照らして確定し、確認の要否は`agent-toolkit:user-confirmation-and-report`「確認要否の判定」に従う。

任意の対応を選択させる判断（関連作業の完了後に任意の処置を実施するかどうかをユーザーが選べる場合など）であっても、実施する場合と実施しない場合の両方を選択肢として提示する。実施した結果の回答が後続の作業に必要な場合に限り、次節の操作依頼と同様に返信形式を指定する。
資格情報を発見した旨を報告する際は、認証情報の具体的な値を再掲せず、その所在と種類を簡潔に示す。所在の表記には統一された表現を用い、リポジトリ内のファイルであれば正規化されたリモートURLとリポジトリ相対パスで、外部環境であればイメージ名やファイルの絶対パスで記載する。
所在ごとの重複確認や報告用UWIの扱いは、`agent-toolkit:user-confirmation-and-report`「手段の選択」に従う。資格情報の失効や削除の要否と実施時期はユーザー自身の判断に委ね、具体的な操作手順や完了確認の回答を求める記述は省く。

## ユーザーへ操作を依頼する場合

外部環境での実機確認、成果物の反映、権限の付与といった操作を依頼する場合は、ユーザーが本文を読むだけで判断や読解を補わずに上から順に実行して完了を確かめられるように、番号付きの手順を`## 判断材料`へ記載する。各手順には、操作する場所（画面名と項目名、作業ツリーの絶対パスと実行コマンド、依頼先など）、入力する具体的な値（コマンドの全文、入力する文字列やその求め方など）、および作業が完了したことの確認方法を漏れなく持たせる。期待値、回答欄へ貼り付ける最小限の返信形式と、何らかの事情で操作できない場合に記入すべき内容も、必要に応じて添える。
操作に必要な対象、値、順序、完了条件はすべて本文中で示し、ユーザー自身の判断に委ねるべき事項のみを問いや選択肢として提示する。
手順を記述する前に、各工程を実行権限と到達可能性で次のように振り分ける。

- 到達可能かつ実行権限がある工程（差分の生成、読み取り専用の確認、ログの読み取りなど）は起草者自身が事前に実施し、その結果を本文へ記載する。
- 到達可能であり実行権限のみが不足している工程は、起草者がエージェントによる実施の可否を尋ねる選択肢を用意し、`agent-toolkit:user-confirmation-and-report`「手段の選択」に従って確認を取る。承認後の操作と影響範囲については、`agent-toolkit:user-confirmation-and-report`の`references/approval-scope.md`「新しい挙動と準備の提示」および`agent-toolkit/rules/01-agent.md`「協調と自律」に従う。
- エージェントから到達できない工程は、ユーザー自身が実行する手順を提示する案と、エージェントへ到達権限を付与してもらう案を比較する。権限付与の案を選択肢に含めない場合は、その理由を`## 判断材料`へ明記する。

## 承認型ごとの内容

`agent-toolkit:completion-report`が定義する報告用UWIは、同スキルの`references/report-formats.md`「報告用UWIのフォーマット」「報告用UWIの確認と保存」と、本書の構成・情報選定で確認する。
通常の事後承認型UWIには共通起草手順を適用し、`--question-type=post-approval`だけでは報告用と判定しない。

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 |
| --- | --- | --- | --- |
| completion-reportが定義する報告用UWIを確認・保存する前 | `../../completion-report/references/report-formats.md`の「報告用UWIの確認と保存」 | 判断 | `section:agent-toolkit:*/skills/completion-report/references/report-formats.md#「報告用UWIの確認と保存」` |

事前承認型のUWIでは、確認を要する解釈の相違やユーザーのみが持つ情報、各案を採用した際に対外的に生じる影響、推奨案、回答を待つ元項目のファイル名と対象範囲、および必要な回答や資料を`## 判断材料`に記載する。元項目とUWIの対応関係は、UWIの本文内のみに記録する。`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「確認要否の判定」に基づき、確認を必要としない問いはUWIへ送らずエージェント自身で確定する。

事後承認型のUWIでは、実施済みの対応内容、その方針を選んだ根拠、ならびにエンドユーザーから見て観測される影響のうち、回答や是正の依頼に必要な情報のみを記載する。内部的な技術選定の経緯や調査の過程は記載しない。`--question-type=post-approval`を指定し、`--choices`を省略して投入すると、固定の選択肢である`その対応で問題無い`と`問題がある`が自動的に表示される（通常の`choice`や`yes-no`より優先される）。`問題がある`を選んだ場合の説明として、希望する是正内容を回答欄に記入するよう促す案内文を添えておく。
ユーザーからの質問に答える事後承認型UWIでは、個々の質問に対して`## 判断材料`の中で直接回答する。「なぜその事象が起きたのか」という問いに対しては、発生原因、変更した内容、および今後の再発防止策を、段落の冒頭や小見出しを用いて分かりやすく整理する。冒頭の問いで言及した説明項目（「理由」や「対策」など）がある場合は、本文中でもそれと同じ見出しや表現を用いて解説する。
