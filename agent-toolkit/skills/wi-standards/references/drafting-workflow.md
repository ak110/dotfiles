# WIの調査・起草・保存の共通手順

作成主体は専念型のメイン（WI作成専用セッションで独立要求1件を扱う場合）と専念型の担当、他の作業中の投入（付随型）のWI投入担当である。専念型の担当を起動する場面は`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`「起動方法」が定める。各主体はwi-standardsとwriting-standards、欠陥起点ならbugfixとそれぞれの読込表、対象リポジトリの規範を適用する。
要求の原文・出所・確定要件・技術判断・観測の記録を分け、取得済み証拠を再利用する。専念型メインが持つ自身の原文と観測は、委譲入力へ再構成せず元の記録を使う。
投入先の確定、既存項目の保留・解除と回答済みUWIの照会はwi-standardsの状態・投入契約に従う。投入先の外の対象は後掲の処置の要否で判定し、ユーザーだけが決める値が残る場合は「未確定事項」へ渡す。
基準付きの大量走査は軽量explore・shellへまとめる候補とし、原因・採否の判断と起草は上位の作成主体が所有する。分割はdelegationの総費用判断に従う。

## 出所と観測の取得

引用の一致や判断の由来の証拠を使う時に、出所を次の公開操作で確定する。取得済みの証拠は再抽出しない。専念型メインはユーザーから直接受けた発話と自身の記録を使い、ホストが公開する自身のセッション識別子を渡す。`agents_server`の要求別担当と付随型担当は、ユーザー発話を持つ最上位の会話を`--delegation-record root`で解決する。

```sh
atk run-script session-review-evidence -- --delegation-record root --user-events
atk run-script session-review-evidence -- --claude-session-id <対象となるセッションID> --user-events
atk run-script session-review-evidence -- --codex-thread-id <対象となるthread ID> --user-events
atk run-script session-review-evidence -- --transcript <対象となる記録の絶対パス> --user-events
atk run-script session-review-evidence -- --user-events-file <元の保存ファイルの絶対パス> --user-event-at <record>:<line>
```

取得元は取得済みの出所ファイルと`record`・`line`、要求が明示した識別子か記録パス、委譲関係から解決した記録の順に選ぶ。専念型メインは自身の記録を明示する。識別子指定は対象ホストに対応する形を選び、取得済みの指定組は`--user-events-file`と`--user-event-at`で読む。
`--delegation-record root`は起動結果を登録簿より優先する共通の親子判定で最上位の会話を解決する。`--owner-session --user-events`は環境の`AGENT_TOOLKIT_OWNER_SESSION`が示す所有会話を読む別の指定であり、直接の委譲元とは限らない。担当自身の`CLAUDE_CODE_SESSION_ID`と`CODEX_THREAD_ID`は委譲先の記録を指すため、委譲元の識別子へ代用しない。
解決できず終了コード2になった場合は、委譲元から対象会話のセッションID、thread IDか記録の絶対パスを受け取り、対応する明示指定で再実行する。`--owner-session`は未設定、`mcp-`で始まる値、記録0件・複数件でも終了コード2になり、環境変数の値は出力しない。`Agent`ツールなど解決を確認していない起動方法でも明示指定を使う。記録取得を要しない要求の起草はそのまま続ける。
対象の逐語内容・時点・文脈と一致するイベントの全欄を読み、出所を元の保存ファイルの絶対パスとJSONレコードの`record`・`line`へ確定する。`line`は元のセッション記録の行位置であり、保存出力の物理行番号とは区別する。`<record>:<line>`は末尾のコロンだけで区切る。
同文の反復も内容一致だけで一意とせず、元の記録位置を確定する。取得不能・不一致・特定に必要な入力不足は続行できない理由として返す。
構造化確認は質問、全選択肢、選択回答と自由記述の対応を保ち、ユーザーの回答として使う範囲は`agent-toolkit:wi-standards`「由来と承認」に従う。この出所を引用の一致確認と、対象・除外・認可の由来の確認へ使う。複数の一致を保持する照会の結果は、証拠の一意性の確認とユーザー由来の判定の代わりにならない。

委譲先の必須入力の欠落は`agents_server`の`start`が起動時に確かめるため、受領した入力のまま着手する。委譲先が欠落を観測した場合は`rules-subagent.md`「委譲時の厳守事項」に従う。
投入先はユーザーの指定または委譲入力の値へ固定する。調査で投入先の外にも原因の機構を共有する対象が見つかった場合は、`agent-toolkit:bugfix`の`references/root-cause-analysis.md`の基準で是正か予防の処置の要否を判定する。処置を要する対象と、処置の要否を判定できない対象は事実と所在を記録する。専念型メインはユーザーへ確認し、委譲先は`続行できない理由`として委譲元へ返す。その対象を除いた原稿は未完成として扱う。処置不要と判定した対象は、根拠とした現物の所在（ファイルと版）とともにAWIの`## 適用範囲`の除外例、UWIでは成立性の証拠へ記録して起草を続ける。認可を超える不可逆操作も同じ確認先へ、操作と対象を示して送る。

## 調査と本文の起草

### 投入条件の判定

`元項目`を受領した要求では、最初に`atk wi show <元項目> --target-repo=<起動時のcwdが属するGit worktreeのroot> --skip-pull`で本文を取得して根拠に加える。
`投入条件`が`無条件`でない要求では、条件を観測可能な判定へ具体化して投入先を読み取り専用で調査する。不成立ならWIを投入せず`condition_not_met`と調査対象・結果を`条件判定`へ返し、判定できない場合や投入先の現状を確認できない場合は続行できない理由を返す。

### 前提と観測の確認

委譲先が受領した`他の要求単位の割当`の単位が、調査で確定した根本原因を共有すると判明した場合は、その単位と根拠を`続行できない理由`へ書いて返す。要求の統合は委譲元が判断する。
`投入前に確定すべき事項`と`agent-toolkit:wi-standards`の`references/drafting-completion.md`が投入前の確定を求める事項を、投入先の読み取り専用の調査で、計画工程へ回さずに自ら確定する。分割読取で読める未読や未調査の原因・対象は、続行不能の理由とせずに調査を続ける。実際の到達・権限不足、調査後も残るユーザー依存事項、固定要件の帰属違いなど自身で解消できない条件だけを根拠付きで返す。
観測した欠陥を起点とする要求の原因、類似見直しの母集団と再発防止は、`agent-toolkit:bugfix`の`references/root-cause-analysis.md`の基準（QとC・Dの区別、重大度別の探索と終了、根本原因から導く母集団、処置の階層、完了の判定）で確定する。母集団が受領した投入先の外（他の所有リポジトリを含む）へ及ぶ場合も、前掲の投入先の固定の処置要否判定と除外記録に従う。
`委譲元の判断`の理由に含まれる事実上の前提も技術主張として裏付け、観測と異なれば観測へ改める。ユーザーの方針は記録の所在と該当箇所を確かめ、`drafting-completion.md`「方針と判断の記録との比較」の優先順位を現在の逐語要求と`確定した要件`へ適用する。既存WIを前提・制約・代替案の不採用理由・完成条件の根拠に用いる場合は、`origin-and-approval.md`「ユーザー専用の記入欄と是正要求」の参照するWIの規定でユーザー専用の記入欄を含む有効な要求を確定し、その要求と原稿の判断との比較を成立性の証拠へ残す。
`確定済みの観測`は取得済みの位置と保存出力を再利用する。位置が未取得の委譲先は`atk run-script session-review-evidence -- --delegation-record parent --tool-calls`で直接の委譲元を照会し、コマンド・入力の特徴・時点から候補を特定する。専念型メインと明示された別会話の観測では、その記録を明示指定する。得た`record`・`line`と必要な`result_line`は同じ記録指定の`--detail <record>:<line>`へ渡して入力と結果を読む。解決失敗時は「出所と観測の取得」の再指定に従う。ツール名と時刻だけでは一致を認めず、値と観測条件（コマンド、入力、環境変数など）を元の記録か受領内容と比べる。反復した同じ操作を区別できなければ、その不足を未確定事項として扱う。
一致した観測は`drafting-completion.md`「採否と実現方式の確定」の実行結果による裏付けに使い、再実行を省く。値か条件の不一致、起草中に読んだ現物や別観測との不一致、観測後に値を変える変更があった場合は再実行する。
依存を受領した要求では、`states-and-dependencies.md`の基準で独立に実施と完成判定が成立するかを確定し、必要な依存だけを本文とメタデータへ反映する。
外部の既存挙動の再現を完成条件へ採る場合は、`awi-body.md`「外部の既存挙動の再現」を起草中に適用する。確認を処理側の計画へ回さず、再現できない場合は同節の扱いに従い、無制限の再試行や待機で代えることは避ける。

### 確定した要件と委譲元の判断

`確定した要件`と`委譲元の判断`を分類するときは逐語本文と実回答の出所を入力として、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」「原文の保持と取り込み」を適用する。根拠は成立性の証拠へ記録し、確認事項は「未確定事項」へ渡す。
`確定した要件`は記述ごとに、ユーザー自身の指定かエージェント案の採択かの由来と、支持する発話・回答の出所を保持して扱う。由来の解釈は`origin-and-approval.md`「由来と`source`」に従い、選択回答が確定するのはその質問が問うた判断だけとする。質問本文、選択肢の説明、`共通前提:`行から補われた内容が`確定した要件`にあれば`委譲元の判断`として扱い、その判定と出所を成立性の証拠へ残す。採択されたエージェント案とユーザー自身の明示指定が両立しないと判明した場合は、`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」の採択案の扱いへ当てはめ、原稿を作成せず衝突と代替案を`続行できない理由`へ書いて返す。

`確定した要件`は起草者が変えられない制約である。守れないと分かった要求は、原稿を作成せずに続行できない理由を返す。次の`確定した要件`も本文へ取り込まず、原稿を作成せずに該当する要件と根拠を`続行できない理由`へ書いて返す。

- `agent-toolkit:wi-standards`冒頭のAWIの粒度で、別の要求に当たると判定した要件（根拠に別要求と判定した理由を書く）。要求の趣旨を調査した結果、受領した内容に同じ粒度で独立した要求が含まれると判明した場合も、その要求単位を起草・保存せず同じく返す。委譲元が`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`「起動方法」に従って新しい担当へ分け、専念型のメインは`agent-toolkit:add-awi-by-user`の要求数に応じた分担へ移す
- 後続工程（計画・実行・実行レビュー）へモデル、ツール、担当エージェント、操作方法を適用するのに、逐語本文か適用工程を独立して問うた確認の回答の支持が無いもの（矛盾する入力の該当箇所を書く）。起草した完成条件が同じ適用を含む場合も同じ確かめを行う

`委譲元の判断`は調査の前提として扱う。ただし、原文の集合に属する対象を字面で名指しされていないことを理由に除く判断は前提にせず逐語本文と比べ、原文より狭ければ原文の集合へ戻す案を覆す案とする。前提を守ると品質の退行、機能の一律な無効化、回避策の追加などの不利益が生じる場合は、前提を守る案と覆す案を比べる。
観測した問題の対策の方向は、直接的原因を確かめた観測との対応を確かめてから候補として扱う。原因未確認の入力に修正箇所や対策案が含まれていた場合は、それらを選定の前提から外し、観測事象、期待する契約と問いから調べる。`agent-toolkit:bugfix`の原因分析で独立に対策を導いてから候補を比べ、技術的に優れる案を採用する。
受け取った判断と異なる案を採用する場合は次のとおり扱う。

- 覆す案が`確定した要件`の対象、範囲、外部可視の結果の内側で成立し技術的に優れる場合は、その案で起草し、覆した判断、採った案と理由を`判断の変更`へ記録する
- 覆す案がそれらを`確定した要件`の外へ広げるか変える場合と、前提を守る案が品質の退行など外部可視の結果の変化を伴う場合は、原稿を作成せず両案と各案の不利益を`続行できない理由`へ書いて返す

### 本文の起草

受領した制約は適用される工程を原文から確定する。WI作成工程だけの書込範囲・操作の許可と禁止は作成主体の行動へ適用し、後続の計画・実装・公開を拘束する要件へ移すのは、その工程への適用を原文が示すものに限る。原稿の反映内容・適用範囲・完成条件を確定する時点で、各制約と適用工程の対応を確かめる。

新しい通常AWIでは起草の前に`drafting-completion.md`「重複判定」を行い、既存項目が全てを覆えば原稿を作成せず、部分的に覆えば未被覆部分だけを起草する。付随型は判定と既存項目のファイル名を`既存項目の扱い`へ書いて返す。専念型の担当は全てを覆う要求を投入前レビューと保存へ進めず、`add-wi.subagent.md`「保存の返却」の`reused`で返し、部分被覆は保存結果と既存項目が覆う範囲を分けて返す。
AWIは`agent-toolkit:wi-standards`「通常AWIの本文」、UWIは`references/uwi-format.md`に従い、投入先の読者が委譲元の会話や元項目を参照せずに判断できる本文にする。受領した指示文の転記と、委譲元の文脈を前提とする参照表現は本文から除く。上流改訂後に元項目の対象リポジトリで行う作業があれば本文へ含める。
完成前に節の分担表を基準に節をまたぐ再掲を除く。読者の判断に使う根拠、範囲、引用は容量にかかわらず残す。
完成条件を固定する前に、比較・検収・工程の指定を逐語本文と由来に照らして、ユーザーが明示した目的・要件と、委譲元か自分が選んだ中間手段に分ける。手段は`drafting-completion.md`の必要性比較で残すかを決め、必要性を示せない内部の検証手順は計画工程へ委ねる。ユーザーが指定した手段は残す。手段を固定する根拠には、委譲元の追送が求めたことに加えて固定する必要性を示す。
逐語本文を受領した要求では、「入力」で確定した出所を用い、`drafting-completion.md`「投入前の読み直し」の逐語引用の項の取り込み操作で出所と原文を引用節へ取り込む。原文はtextフェンスの中だけに置き、編集入力やコマンド引数へ書き写さない。`## 反映内容と反映先`で要求単位ごとの反映先を対応付け、背景とする文も引用位置で示す。他AWIへの割当先には受領した`他の要求単位の割当`の値だけを書く（他の担当が起草する本文の題名は推測でしか書けないため）。要求の趣旨にも割当にも当たらない単位があれば、原稿を作成せずその単位を`続行できない理由`へ書いて返す。
`質問への回答の扱い`が送達済みとする質問だけに、`## ユーザー指摘の逐語引用`で回答済み注記を書く。調査で回答を確定しただけの質問は回答案と根拠を成立性の証拠へ残し（回答済み注記は送達後）、確定できない質問は調査対象と限界を同じ証拠へ残す。質問への回答に限界があっても、採否と実現方式が確定した原稿は作成する。

### 未確定事項

「確定した要件と委譲元の判断」の確認要否判定でユーザーだけの値が残る要求は、専念型メインは`agent-toolkit:user-confirmation-and-report`に従ってユーザーへ確認し、委譲先は確認を発行できる委譲元へ続行できない理由として返す。質問の発行と実回答の取得を区別し、回答を得て分類を確定してから原稿の確定・保存を再開する。本書の各節で続行できない理由を返す場面も、この主体別の確認先を使う。適用した原文と回答の出所を、残るユーザー依存の事項と分けて書く。
観測事象を契機とする要求では、確定した直接的原因とその観測の所在、依拠する値ごとの生成元と比較の所在、原因へ作用する対策の案も含め、委譲元が原因を確定し直さずに確認を組めるようにする。
他の要求の調査と起草は続ける。

## 保存前の確認

各要求の本文を他の要求から独立して`drafting-completion.md`「投入前の読み直し」で読み直し、あわせて次を確かめる。不合格の本文は修正して再チェックする。

- 前節の起草時の条件（要求単位と引用位置の対応、原文のフェンス内保持、送達済みの質問だけへの回答済み注記、完成条件と後続工程の手段の根拠）が本文に成立する。逐語本文が原文と一致することは`atk run-script wi-quote-check`の取り込みで確かめ、取り込み後に引用節を編集した場合は同じスクリプトへ`--source`を渡して確かめる。コマンド・終了コード・出力を証拠へ含める
- 完成条件ごとに同一セッションで自己観測できる手段を確かめ、例外は`awi-body.md`「完成条件」に従って根拠を`## 実現性`へ残した
- 本文が`agent-toolkit:writing-standards`の`references/writing.md`の人間向け文書の共通規定を満たし、managed-tempの一時証拠を参照しなくても、結論・判断条件・原文と、再取得に要る実装・設定・版管理文書の根拠が本文から復元できる
- 仕分け・要約・統合した本文と元の調査結果の対応を証拠へ記録した
- UWIの各情報が`uwi-format.md`の選び方に照らして必要で、重複していない

原稿と根拠をmanaged-tempへ保存する。新規は`atk wi add --dry-run`、既存更新は現行本文と保留状態を確かめて`atk wi edit <ファイル名> --dry-run --body-file <原稿>`で、保存を伴わずに確かめる。そのコマンド・終了コード・出力を証拠へ含める。付随型は原稿と証拠を委譲元へ返し、意味の検収を待つ。専念型は投入前レビューへ進む。
類似見直しの限定探索はbugfixの重大度判断で終了を決め、探索範囲・限界・許容する残存リスクを原稿と証拠へ記録する。ユーザーが明示した対象集合は保持する。
前記の限定探索で許容した未走査部分を除き、確かめていない範囲（`投入前に確定すべき事項`、範囲語か開放列挙の集合のうち未判定の対象、検索語に一致せず読んでいない対象、権限や到達性を含む）は、証拠や`想定外事象:`の行へ書いても返却の理由にならず、手段がある間は調査を続ける。手段が無い範囲は`awi-body.md`の`## 実現性`の確認していない範囲の条件と、`origin-and-approval.md`の範囲語か開放列挙の未走査部分の段落に従い、どちらでも扱えなければ続行できない理由を返す。内部設計・実装単位・実装後の検証は計画・実行工程へ渡す。
修正の指示を受けたら、返された不一致だけを同じ原稿へ反映して再返却する。各指示が投入前に解消する成立性の不足か計画へ渡す具体化か説明から補われた要件かを`draft-semantic-review.md`の不足の指摘と由来の判定の基準で確かめる。後二者は投入条件へ加えず、判定の根拠を成立性の証拠へ記録して返す。指摘が要件とした値を支持する出所（逐語要求、実回答、エージェントが書いた質問や選択肢の説明）の判定も根拠へ含める。計画担当の判断に要る具体化は、計画で決める事項として原稿の`## 実現性`へ残す。方式を変える修正は、開始・終了・途中失敗から再開までつながることを確かめてから再返却する。

## 投入

既存更新で保留した項目は、専念型では作成主体が保存本文の一致確認の成功後にunholdまで行い、付随型では委譲元が保存結果の検収後に解除する。ユーザー回答待ちや起草・保存の失敗は保留を保持する。既存項目を変更せず再利用する結論と取り下げでは、状態契約に従って必要な更新と採否を確定し、未解決の懸念が残る間は保留を保つ。誤投入の削除とholdからの採否終端はstates-and-dependencies.md「保留と本文修正」「終端」に従う。

付随型は同じthreadで`保存開始`と検収済みの要求識別子を受領した集合を保存する。専念型は`share/wi-draft-review.parent.md`に従う投入前レビューを収束させた集合を保存する。保存前に原稿の現行本文を確かめ、検収後に変わっていれば保存せず修正へ戻る。先行項目を後続より先に保存して正式ファイル名を対応付ける。
検収後の差分が、検収済みの参照関係に基づいて先行項目の未確定名を正式ファイル名へ置換しただけなら、作成主体が置換後の本文と依存指定を先行項目の保存結果と比べ、一致すれば同じ検収結果で保存へ進む。参照先、依存の必要性、要求内容のいずれかが変わる差分は修正と検収へ戻す。ユーザー依存事項の回答待ちは、保存の指示を受けても回答まで保つ。
要求ごとに1回だけ投入する。`ファイル名`を受領した要求は新規投入せず、`atk wi show`で取得した現行本文を基に書き直して`atk wi edit --body-file`で保存する。
警告かエラーを検出したら同じ手順で修復して再投入し、修復できない要求は続行できない理由を返して他の要求の投入を続ける。
