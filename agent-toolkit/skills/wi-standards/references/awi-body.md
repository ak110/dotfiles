# 通常AWIの本文

本書は通常AWIを起草・読解・採否判定するエージェントへ、本文の形式と各節の判断条件を定める。
本文の読み手は、対象リポジトリのプロジェクト文脈を持たず、本文と対象リポジトリの実体だけで判断する実装担当である。その担当が本文だけで着手できるよう、変更対象、判断基準および完成条件を確定して書く。

全AWIで`## 反映内容と反映先`と`## 完成条件`を必須とする。`source`を持つ通常AWIは`## 適用範囲`と`## 実現性`を、ユーザー要求を起点とする場合は`## ユーザー指摘の逐語引用`を、観測した欠陥を起点とする場合（起草者が`agent-toolkit:bugfix`を起動して起草する場合）は`## 原因分析`を加える。H2は次のテンプレートの順に置き、H1は1つとする。
`source`を持つ通常AWIで必須H2の欠落・空の本文・順序の不一致、または置いた`## 原因分析`が空の場合、`atk wi add`は該当を全件示して保存前に非0で終了する。

```markdown
# <対応内容や理由などがユーザーへ伝わりやすいタイトル>

<目的。必要に応じて手段の概要と、その目的が生じた観測事象または要件を併記する>

## 反映内容と反映先

<何をどう変えるかと、対象リポジトリ、文書、機能などの反映先>

## 原因分析

<観測した欠陥を起点とする場合に置く>

## 適用範囲

## 実現性

## 完成条件

<変更後に消費主体が達成できる状態>

## ユーザー指摘の逐語引用

<ユーザーの指摘または要求を起点とする場合に置く>
```

## 要求固有性と記載量

本文には原要求か、要求固有の採否・実装・完成判定に使う記述だけを残す。通常の版数更新・生成物同期、一般則を変えない旨、汎用の検証・CI、通常の記録追随、投入前調査の経過は除く。必要な境界、原因、代替案、外部可視の結果および否定形の完成条件は残す。
説明追記を反映内容や完成条件へ含める前に、`agent-toolkit:writing-standards`の`references/writing.md`「人間向け文章の共通規定」の情報を加える前の判定を適用する。
記述の詳しさは同書「読み手別の追加注意点」のエージェント向け文書の項に従う。要求固有の事実と契約、ユーザーが指定した手段、硬い制約は具体的に書き、一般的な実装方法や検証手順の解説は省く。
`## 反映内容と反映先`と`## 完成条件`は、実装担当が対象の特定、候補の列挙、分類のいずれの調査も追加せずに着手できる粒度で書く。これが本書の各規定が守る価値である。
調査後に正常な対象と変更を要する対象が混在する場合は、冒頭の1文で両者とAWIが変更する範囲を対照し、`欠陥`、`不足`、`未追随`などの評価語には対象名を伴わせる。
素材で確立した事実と起草者の推測を区別し、確定要件には事実だけを置く。対象を調査手順で表す場合も、指す集合を本文から判定できるようにする。
エージェント由来の通常AWIには、影響範囲と改修規模の見込みを1〜2行で任意に書ける。
既存の規範の適用範囲へ言及する場合は、条文を持つ文書のパスと節名を参照し、再掲しない（努力目標）。参照で完成条件を一意にできず再掲する場合は、その理由を書く。条文の変更を求める項目が変更前後の文面を引用することは再掲に当たらない。

## 節の構成と分担

H1のタイトルは対応内容や理由がユーザーへ伝わる表現で書き、目的を直下へ書く。各内容は次の表の節へ置き、他の節からは節名で参照する。

| 節 | 書く内容 | 書かない内容 |
| --- | --- | --- |
| H1直下 | 目的、目的が生じた観測事象または要件の要約、既存の値を変える提案で調べた導入目的の調査記録 | 反映の具体と根拠の詳細（各H2へ置く） |
| `## 反映内容と反映先` | 何をどう変えるか、反映先、処置の層（対策・横展開処置・再発防止策）、要求単位と反映先の対応、他AWIへの割当 | 成立の根拠と原因の説明 |
| `## 原因分析` | `agent-toolkit:bugfix`の`references/analysis-records.md`「原因分析の記録先」が定める表と行 | 変更の具体と該当箇所の列挙 |
| `## 適用範囲` | 誤りの機構が依存する条件、該当例と除外例、それぞれの根拠 | 該当箇所へ加える変更の内容（`## 反映内容と反映先`の項目名で示す） |
| `## 実現性` | 成立を確かめた観測の所在（ファイルパス、識別子、実行したコマンド）と結論、追加する規定や機構の必要性と代替の可否 | 反映内容、原因分析および確認の経過の再掲 |
| `## 完成条件` | 外部可視の終了状態と、それを観測する主体と手段 | 「完成条件」が省く記述 |
| 独自H2 | 前掲の節だけでは完成条件と採否を判定できない証拠、代替案または再現手順。`## 完成条件`と`## ユーザー指摘の逐語引用`の間へ置く | 前掲の節が持つ内容 |
| `## ユーザー指摘の逐語引用` | 原文、出所と引用範囲、質問への回答済みの注記 | 要求単位と反映先の対応（`## 反映内容と反映先`が持つ） |

## 逐語引用の対応付け

逐語引用を持つ本文では、`## 反映内容と反映先`へ、引用した原文の要求単位ごとの反映先を書く。要求単位は内容の説明か引用位置で示し、原文は`## ユーザー指摘の逐語引用`のtextフェンス内だけに置く。位置は`逐語引用 text[N] 文字A-B`で示し（Nは同じ引用節のtextブロックの1始まりの番号、A-Bは改行も1文字と数えるUnicodeコードポイントの範囲）、値は`atk run-script wi-quote-check`の出力から写す。
対応付けは`source`、分割、背景としての引用によらず全要求単位へ適用する。逐語引用は解釈の根拠である（`origin-and-approval.md`「逐語転記」）ため、反映先を持たない単位にも、他AWIへの割当・分割元の依頼全体・背景・投入元で解決済み（実施・回答・判断の内容を添える）のいずれかを記録する。引用節の完了済み・回答済みの注記もその記録に当たり、回答済みの質問はその注記で対応付けを終えられる。独立した変更要求を含まない質問への回答を、説明追記の完成条件へ変換しない（`agent-toolkit:writing-standards`の`references/writing.md`「ユーザー入力素材の取扱い」）。

1つの依頼を複数のAWIへ分けて起票する場合、本AWIが担わない要求単位は反映先を「他AWIへ割当」とし、委譲元から受け取った値だけで割当先を次のいずれかで示す。

- 同じ担当が同時に起草する本文のH1タイトルを「」で囲む
- 割当先の要求内容を特定できる説明を「」で囲む
- 投入済みのファイル名を書く

割当先の確定を待たずに保存してよく、保存後の追記も不要である。組の全単位が保存されたかは委譲元が保存の検収で確かめる（`origin-and-approval.md`「承認」）。
どのAWI単独でも達成を示せない依頼全体の文（目的、目標値、調査方針など）は反映先を「分割元の依頼全体」とし、他AWIへ割り当てた単位とともに本AWIの完成条件に含めないことを同じ節へ書く。
割当先は、割当先AWIの記録の有無にかかわらず本文へ書く。実行レビューは割当先が同じ単位を自身の反映先へ対応付けた記録（引受の記録）も割当の根拠として受理する。対応付けが欠けた逐語引用の扱いも`origin-and-approval.md`「逐語転記」に従い、処理側の達成対象は本AWIの`## 反映内容と反映先`と`## 完成条件`から確定する。
過去の観測や経緯だけを伝え、要求・制約・採否・選好・回答を求める問いを含まない文は背景とする。背景は原文を再掲せず、引用位置と原文の箇所を特定できる短い抜粋か要約を示し、「背景」の語、要求を含まない理由および完成条件に含めない扱いを書く。保存済みの`「」`による引用（中略は`…`）は読取互換として保持する。一部に要求を含む文、依頼全体に作用する文、判定が一意でない文は要求単位として扱い、疑問符・過去形・注記だけで背景と判定することは避ける。
原文が開放集合を示す場合は、`## 反映内容と反映先`と`## 適用範囲`の対象を`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」の範囲の記録書式で書き、調査で見つかった該当例と根拠付きの追加を含める。集合を狭める除外は、`origin-and-approval.md`「範囲語と程度」の事前の明示承認の出所とともに書く。

## 原因分析・適用範囲・実現性

`## 原因分析`は計画がWIファイル名で参照する原因分析の記録であり、書き方は`agent-toolkit:bugfix`の`references/analysis-records.md`「原因分析の記録先」に従う。

`## 適用範囲`には、誤りの機構が依存する条件（`agent-toolkit:bugfix`の`references/root-cause-analysis.md`の基準）と、観測事象と表面構造が異なる該当例を1件以上書く。条件が観測事象のファイル名、工程名、識別子だけで構成される本文は投入せず、機構の条件を再導出する。類似見直しの母集団、是正対象と予防対象は同ファイルの「類似見直し」（根本原因から導き、時間軸と他リポジトリを含む）と「QとC・Dの区別」に従う。軽微な問題の限定探索では、実際の探索範囲・限界・許容する残存リスクを示し、ユーザーが明示した対象集合は保持する。

`## 実現性`は、処理する担当が実現方式の成立を再調査せずに着手できるように書く。APIやCLIの存在に加えて、要求が依存する消費側、開始から完了までの状態遷移、途中失敗時の状態を現物で確かめた根拠と範囲を対応付ける。他の処理への影響が無いと主張する場合は、読んだ実装のファイルパスと識別子と接続の確認結果を書き、不変の主張は確認済みの範囲に限る。
確認していない範囲を書けるのは、起草者が自環境の手段（読み取りの照会、権限と到達の確認など）で確かめられず、かつ未確定でも実現方式の成立と完成条件の判定が変わらない事項に限る。未確認の結果を失敗として記録する設計にしたことは、この条件の根拠から外す。判定を変える事項と実施の有無が分岐する要求は、投入前に現物で確定するか本文の範囲から外す。
採用の確定には元の目的に対する必要性の判定を含める。当初の目的に無い永続状態、周辺機能、運用手順、規範の条文を足す場合は、その必要性と既存の機能・条文での代替可否を書く。
処理を実施しない・延期する保護条件（判定できない場合に実施しない条件を含む）を置く場合は、保護条件ごとに対応する確定した要件、規範的制約、観測済みの欠陥のいずれかを書く。外部文書が利用の可能性を記すことと結論が安全側であることは根拠にしない（`agent-toolkit:writing-standards`の`references/design-heuristics.md`「自作機構の兆候と自問」）。

## 完成条件

`## 完成条件`には外部可視の終了状態を一意に書く。内部のファイル名、節名、配置先を固定するのは、ユーザー要件や公開契約が名前自体を求める場合に限る。
条件は完成判定に必要十分なものに限る。全体検証・CIは`agent-toolkit:process-wi`の公開工程へ委ね、反映内容の言い換え、採否と実装を変えない列挙、外部挙動の再現の結論・典拠以外の経過、他項目や過去セッションの経緯は書かない。観測した欠陥を起点とするAWIでは、重大度に応じた類似見直しと再発防止の完了（`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「類似見直しと再発防止の完了」）を判定できる状態を含める。根本原因への処置の要否と完了は同節で判定し、採用した処置の効果を結果で示す。共通定義の消費や検査の存在など選んだ処置の内部構造を固定しない。
各条件には観測する消費主体と手段（CLI、画面、hook、文書など）を対応付ける。文書の文面や文意を観測する手段は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」に従う。
完成判定の観測主体はその項目を処理するエージェントとする。
完成条件と実現方式を選ぶ段階で、CI・再現テストなどにより同じ作業内で合否を観測して完遂できる手順を優先する。
自己観測できる事項をユーザーの実機確認へ転嫁しない。
起草者は遠隔操作、非対話CLI、ログやAPIなど同一セッションで成立する観測手段を確かめて選び、GUIや配布後という分類だけで人手・後日の観測と決めることは避ける。人手の観測自体が明示要件である場合は、その根拠を`## 実現性`へ書く。環境制約などで自己観測しきれないことだけを理由に、人手の完成条件や個別UWIを追加しない。可能な確認の手段と残る限界を示し、実施後は完了報告へ記載する。処理する主体も、人が観測主体と書かれた条件について現在の到達性から自己観測を検討する。
複数の実装方式を許す場合も、達成する状態と消費主体へ求める操作の要否は一意にする。
対象リポジトリの外（サブモジュール参照、別のリポジトリが所有する設定など）へ成果を反映する項目では、処理側が反映先ごとに完成とする状態（commitまでかpushまでか）と、その操作の対象・影響範囲を判定できるようにする。状態が反映先のプロジェクト規範か成立済みの認可で一意に定まる場合は、その規範のパスと節名か承認の出所を参照し、公開の一般則をWIごとに再掲しない。認可の適用は`agent-toolkit:user-confirmation-and-report`の`references/approval-scope.md`「承認源と適用範囲」に従う。参照で定まらない反映先、今回だけの例外、個別に承認された範囲を、要求固有の境界として完成条件へ書く。完成条件へ公開操作（push、release、配布など）を書くのは承認源を併記できる場合に限り、起草者の記載だけを新しい公開の認可として扱わない（`origin-and-approval.md`「承認」）。状態を決める値がユーザーだけにある場合は`drafting-completion.md`「未確定事項と確認」で扱う。
否定形の条件は観測範囲を要求の差分へ限定し、「要求の差分に含まれない」と書く。成果物全体の不変・不在を条件にできるのは、独立した後続要求でも変わらない状態に限る。

完成条件と判断材料の観測は、低コストで処理する同一セッション内に得られる範囲に収める（公開・配布後も同じセッションで反映して観測できるなら含める）。事象の自然発生、専用計測の構築、複数セッションの蓄積を要する観測は任意の判断材料にするか要求から外す。既知の不良と明示要件の未充足は未達として区別する。要件自体が必要とする観測は独断で外さず、成立しない根拠を残して`agent-toolkit:process-wi`の`references/finish-session.md`の延期adoptと再開記録へ渡す。起動前提を満たさない新設workflowなどは、実装の検証と公開工程の検収を分ける。
所要時間などマシンの負荷で変わる計測値は、同じマシン・同じ時点で実行した対照（変更前の版か原因の要因だけを戻した構成）との比か差で書き、起草時の両者の値と比、測定時の負荷を`## 実現性`へ残す。ユーザーが指定した目標値はそのまま使い、`timeout`などの設定値は計測値に当たらない。

## 外部の既存挙動の再現

外部製品・サービス・ホストの既存挙動を再現する観測を完成条件へ採る前に、起草者が処理側へ求める手段で実行し、成否に関わる主体、版、入力と設定を結果へ対応付ける。過去の記録は現在の再現性の根拠にせず、再利用する場合は対象と条件の一致を確かめる。
再現しない場合と条件をそろえられない場合は任意の判断材料とし、実行条件、結果と未確認の範囲を`## 実現性`へ残す。非再現だけを根拠に外部の不具合解消や過去の記録の誤りと結論づけることは避ける。合意済みの要件がその観測を必要とする場合は、要件を弱めず未確定事項として委譲元へ返す。

## 配置規約と導入目的の調査

`## 反映内容と反映先`の対象に配置規約か領域の編集手順を定めるスキルがある場合は、起草前にそのスキルを起動し、定める同期先、記録先およびテストの追随を反映先へ含めるか、含めない理由を書く。配置規約を持つ対象とは、置き場所で読込契機か適用範囲が変わる文書群とコード群であり、判定は`agent-toolkit:writing-standards`と対象リポジトリの配置規約に従う。
対象リポジトリのプロジェクトスキルを起動できない場合は、対象リポジトリの`AGENTS.md`等が示す所在と現物から絶対パスを確定する。`.claude/skills/`のスキルは`<対象リポジトリのroot>/.claude/skills/<スキル名>/SKILL.md`であり、ホーム配下の同名スキルとは区別する。Codexの`.agents/skills`がリンクならリンク先も確かめる。確定した`SKILL.md`と同書が定める必読資料を全文読んで起動に代える。

既存の実装、設計、規範を過去の形へ戻す提案、過去の契約を撤去する提案、既存の値を変える提案（上書きの解除と値の削除を含む）では、その箇所を現在の形にした変更の導入目的を調べ、案がその目的を満たすかを確定する。追加する設定値・記述・規定が反映先ファイルの履歴で過去に削除されている場合も過去の形へ戻す提案として扱う。調べ方は`agent-toolkit:plan-mode`の`references/plan-restoration-contracts.md`「復元・巻き戻し型の変更」に従う。
案が目的を満たさない場合は両方を満たす案へ改め、調べた変更の識別子と判定結果をH1直下へ記録する。方針と判断の記録との比較は[drafting-completion.md](drafting-completion.md)「方針と判断の記録との比較」に従う。
