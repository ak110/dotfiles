# 複数リポジトリへの投入

本書は複数リポジトリへ投入するAWI、同じ成果の整合を要求する複数のAWI、上流リポジトリの改訂を要する要求と、別リポジトリへ移す元項目の扱いを定める。

## 独立したAWIへの分割と依存

- 各リポジトリの現行状態を確認し、原則として自身の対象だけで完結するAWIへ分ける。各本文に規則の内容、反映先、完成条件を持たせ、現行成果物だけで実施と完成判定ができる組には、整合や投入順の指定だけを理由に`depends_on`を付けない
- 後続AWIの着手か完成判定に先行成果が必要な場合は、待つ成果と、それが無いと成立しない工程または完成条件を後続本文へ特定する。先行AWIは自身の対象だけで完了できる内容とし、後続AWIの着手・完了を`完成条件`へ含めない。先行AWIを登録してから、得たファイル名を後続AWIの`depends_on`へ指定する
- 依存を設定した場合は、保存後に`depends_on`が後続から先行への一方向であることと、先行本文が後続の着手・完了を待たないことを確認する。双方向の依存または相互の完了待ちを検出した場合は、後続側だけが先行成果へ合わせる形へ本文と`depends_on`を修正する
- 同一変更が複数のリポジトリで不可分であり、単一計画・単一検証でしか成立しない場合だけ1つの計画へ集約する
- 投入元固有の後続本文は各AWI本文へ直接記し、その本文だけで処理側が内容を確定できる形にする

## 上流リポジトリへの投入と元項目

- 対象リポジトリで実装できず上流リポジトリの改訂を要する要求は移管せず、上流リポジトリへ新規のAWIとして投入して元項目を残す。投入する本文には要求内容、対象リポジトリの識別子、および上流の改訂後に対象リポジトリで行う作業を記載する。その作業が無い場合は上流成果の確認だけが残ると記載する
- 投入後は元項目の依存を投入先のファイル名で更新し、元項目が`processing`にある場合は`inbox`へ戻す。更新後は元項目が`blocked_reason=dependency-unmet-external`となることを確認する。依存を置き換える操作では、保持する既存依存も同じ実行で指定する
- 先行AWIまたは上流項目が未終端であっても、その成果の未達を理由に元項目を保留する前に、元項目の`完成条件`を対象リポジトリの現行HEADと成果物で確認する。確認した`完成条件`、観測したHEADの7文字以上の一意な短縮OIDおよび判定結果を記録する
- `完成条件`の充足を確定した場合は、キュー上の状態によらず依存を解除して終端する。実装差分のない充足済みの扱いは`states-and-dependencies.md`「状態遷移」の`processing`→`adopted`に従い、`--commit`を省き、確認した条件・HEAD・判定結果を処理結果へ残す
- 対象リポジトリを取得できない場合と、`完成条件`の充足を確定できない場合は実装済みと推定せず、依存先、未達の`完成条件`および再開条件を明記して保留する
- 上流項目の終端後は元項目が着手可能へ戻る。対象リポジトリ側の残作業を実施して終端し、残作業が無い場合は上流成果を確認して終端する

## 元項目の移管

- 元項目そのものを別リポジトリへ移す場合は、frontmatterと本文を含むメッセージ全体を正しい`target_repo`へ移管し、`agent-toolkit:wi-standards`で登録する。上流の改訂を要する要求は前節に従い元項目を残す
- 移管では予約frontmatterキー`target_repo`だけを移管先の値へ置き換え、`alert_keys`などの非予約frontmatterとsourceは元項目の値を保持する。通常の`atk wi add`はfrontmatterの`target_repo`をCLI値で置き換えない
- 登録の成功後だけ、移管先リポジトリと移管先ファイル名を除去の理由として記録したうえで元項目を除去する
