# 複数リポジトリへの投入

- 原則としてリポジトリごとに単独で完結するAWIへ分け、各リポジトリの現行状態を個別に事前確認する
- 同じ成果の整合を要求する複数のAWIを起草する場合は、登録の前に先行AWIと後続AWIを確定する。先行AWIは自身の対象だけで完了できる内容とし、後続AWIの着手又は完了を`完成条件`へ含めない。後続AWIへは先行成果へ合わせる要求を書く
- 先行AWIを先に登録し、得たファイル名を後続AWIの`depends_on`へ指定して後続AWIを登録する。実装順序が必要な場合も同じ方向で記録する
- 登録の後は、`depends_on`が後続から先行への一方向であることと、いずれの本文にも相手の着手若しくは完了を待つ記述が無いことを`atk wi show`の保存本文で確認する。双方向の依存又は相互の完了待ちを検出した場合は、後に着手する側だけが相手へ合わせる形へ本文と`depends_on`を修正する
- 同一変更が複数のリポジトリで不可分であり、単一計画・単一検証でしか成立しない場合だけ1つの計画へ集約する
- 投入元固有の後続本文は各AWI本文へ直接記し、処理側の将来ステップによる自動生成を前提にしない
- 対象リポジトリで実装できず上流リポジトリの改訂を要する要求は移管せず、上流リポジトリへ新規のAWIとして投入して元項目を残す。投入する本文には要求内容、対象リポジトリの識別子、及び上流の改訂後に対象リポジトリで行う作業を記載する。当該作業が無い場合は上流成果の確認だけが残る旨を記載する
- 投入後は`atk wi set-dependencies <元項目ファイル名> --depends-on=<投入先ファイル名> --target-repo=<元項目のtarget_repo>`で元項目の依存を更新する。同コマンドは指定した値で依存を置き換えるため、保持する既存依存も同じ実行で指定する
- 元項目が`processing`にある場合は`atk wi return-to-inbox <元項目ファイル名>`で`inbox`へ戻す。更新後は`atk wi list --target-repo=<元項目のtarget_repo>`で当該項目が`blocked_reason=dependency-unmet`となることを確認する
- 先行AWI又は上流項目が未終端であっても、その成果の未達を理由に元項目を保留する前に、当該項目の`完成条件`を当該項目の対象リポジトリの現行HEADと成果物へ照合する。照合した`完成条件`、観測した完全OID及び判定結果を記録する
- 照合により`完成条件`を満たすと確定した場合は、キュー上の未終端だけを理由に元項目を保留せず、`atk wi adopt <当該項目のファイル名> --commit=<観測した完全OID> --target-repo=<当該項目のtarget_repo>`で当該項目を終端して依存を解除する
- 当該対象リポジトリを取得できない場合と、`完成条件`の充足を確定できない場合は実装済みと推定せず、依存先、未達の`完成条件`及び再開条件を明記して保留する
- 上流項目の終端後は元項目が着手可能へ戻る。対象リポジトリ側の残作業を実施して終端し、残作業が無い場合は上流成果を確認して終端する
- 別リポジトリへ移管する項目は、元項目のfrontmatterと本文を含むメッセージ全体を正しい`target_repo`へ移管して`agent-toolkit:wi-standards`で登録する
- 投入前処理で入力メッセージの予約frontmatterキー`target_repo`だけを移管先の値へ一時的に置き換える
- 通常の`atk wi add`はfrontmatterの`target_repo`をCLI値で置き換えず、frontmatterの値を優先する
- `alert_keys`などの非予約frontmatterは元項目の値を保持する
- source欄がない場合はsourceを指定しない。指定済みsourceがある場合は同じ値を渡す
- 登録後は`atk wi show <移管先ファイル名> --target-repo=<target_repo> --skip-pull`で、移管先ファイル名、`target_repo`、本文、指定済みsource及び元項目の非予約frontmatter全体を照合する
- 登録と照合の成功後だけ、`atk wi rm <元項目ファイル名> --force --note=<移管先リポジトリと移管先ファイル名>`で元項目を除去する
