# 通常AWIの本文：完成条件の観測の書き方

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 公開後にしか観測できない完成条件の判定を定める前 | `agent-toolkit:/share/exec-review-recording.md` |
| 常駐プロセスから起動される対象、障害注入を含む観測を定める前 | `agent-toolkit:/share/acceptance-scenarios.md` |
| 新しい試験の要否を判断する前 | `agent-basics:writing-standards/references/testing.md` |

## 入口からの操作と期待結果

各要求は、利用する主体の入口からの操作と期待結果で判定できるようにする。
結果を受け取る主体と呼び出し手段、利用の目的と結果を受けて判断・実行すること、具体的な入力値や初期状態、その利用場面と有効な要求から導いた結果と検出する失敗を対応付ける。
`## 完成条件`に書くのは、本文の反映内容からこの対応が一意に導けない要求だけとする。
実装着手前に、この対応からテストを選べる程度まで具体化する。

- 人間由来の各要求単位と、必要性を評価した後の各完成条件に、判定できる観測を1つ以上対応付ける。
  同じ操作と期待結果で各要求の合否を判定できる場合に限り、複数の要求を1つの観測にまとめてよい
- 観測の方法は価値に基づいて選ぶ。
  既存試験の名前、コード・文書の読解、実装時の手動観測から、必要な結果を確認できる最小の方法を選ぶ。
  受入の観測方法と自動試験の常設の要否は別に判断し、新しい試験の要否は`agent-basics:writing-standards/references/testing.md`で判断する。
  「一連の完成条件を後でテスト化する」のような参照だけの記述は、具体化が未完了の状態として扱う
- 手動観測を選ぶ場合は入力値、操作手順、合否基準を書く。
  手動観測は、実装担当者が専用worktree内の成果物へ直接実行できる入力と操作で定め、統合の前に終える。
  公開、配布、稼働中の`atk wi process-loop`への反映の後にしか得られない観測は、次の代替観測へ置き換える。
  完成条件そのものが公開後にしか観測できない場合の判定は、実行レビュー担当者が`agent-toolkit:/share/exec-review-recording.md`に従って行い、本文には公開前に再現できる代替観測を置く。
  `atk wi process-loop`など本番の常駐プロセスから起動される対象は、`agent-toolkit:/share/acceptance-scenarios.md`「常駐サービスの公開前の観測」に従う
- 操作、障害注入、擬似故障、自動終了の失敗などを含む観測は、同書の「検証資源の分離」に従って実行環境と利用の調整方法を定める

## 文書の文意の判定

完成条件や手動観測で文書（規範、配布原本、設計記録、ガイド、コメントなど）の文意を判定するときは、実装を通じた結果、他の定義との整合、検証コマンド、実行レビュー、該当節の正確な読解（対象ファイル、見出し、根拠の文の引用と判定結果を記録する）で総合的に判定する。
同じファイルから転記した文字列の有無や、部分文字列・行単位の正規表現の一致は、単独では合否の根拠から除く。
文字列検索は、精読する候補の抽出と、見出し、設定キー、パスなど行構造で一意に決まる実体の有無や件数の確認に使う。
規範の文面を変える場合は、文面を受け取ったエージェントがそのとおりに動くかだけを、委譲先やセッションを起動して確かめる観測を置かない。
正しく書けば書いたとおりに動き、効果は公開後の効果確認で見るためである。
文面と要求の読み比べ、文書の上での当てはめの試行、文面がエージェントへ届くこと（配布、読み込み、hookによる配送など）の検証、hookやCLIなどコードを変える部分の検証、要件が明示した観測は、従来どおり置く。

## 検索と数値による条件

- 出力内容、診断件数、条件分岐の結果などを完成条件にする場合は、生成元と利用先、分岐が有効になる条件、修正前の状態と修正後の期待値を対応付ける。
  修正前後で値が変わらない条件、該当の分岐が無効な条件、正常時に出力されないメッセージの不在は、公開されている状態や直接の契約テストでの確認へ置き換える
- 増減の方向や数値目標を置く場合は、基準値、目標値、再実行できる測定手順を書き、再現性を確かめられる客観的な指標で合否を判定する
- 処理時間など負荷や並行状況で変わる測定値は、同じマシンで同時に実行する対照群との比較で書く
- コミットのOID（ハッシュ値）はrebaseで変わるため固定文字列で書かず、判定時点の作業ツリーから解決する
- 一致0件を合格とする条件は、`<検索コマンド>; test "$?" -eq 1`のように0件のとき合格となる形で書く（努力目標）
- 件数を期待値とする検索条件は、見出し、定義、設定キーなど判定対象の実体の行構造に合わせて絞り、起草時に同じ条件で測った件数を期待値にする（努力目標）。
  見出しの検索は行頭と行末を固定して数える
