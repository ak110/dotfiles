# WI原稿の意味の確認

付随型の委譲元と専念型の投入前レビュー担当は、原稿、原要求・出所と成立性の証拠を次の基準で比べる。専念型は原稿パスと要求識別子を入力から得る。起草結果の報告形式に関する行は付随型だけへ適用する。機械的なチェックは引用・構造を担い、本書の意味の確認と組で用いる。

- ユーザーが読む部分は、AWIのタイトルとH1直下（UWIでは冒頭の問い・理由・推奨する回答）だけを抽出したファイルをmanaged-tempへ保存し、起草と検収の文脈を持たない読者別探索担当へ判定させる。付随型の委譲元と専念型の投入前レビュー担当のどちらも本項を適用する
  - 起動は`agent-toolkit/share/reader-fit-review.parent.md`に従う。`種別`はWIのユーザー向けの部分、`読者像`は`SKILL.md`冒頭の語の基準が前提とする知識を持つユーザーとして渡す
  - 新規の原稿の`比較資料`は`{"比較元本文":"新規","今回差分":"全文","現行本文":"<成果物と同じパス>"}`とする。同じ委譲元の複数の原稿は`成果物`の配列にして1回の起動へまとめてよい
  - 判定の基準は2つである。1つ目は、その部分だけから次をユーザーの語で言い直せることである。AWIは何が起きたか・原因の種類（実装の誤り、設計判断の結果、規範の不足のいずれか）・何をどう直すか・類似見直しで確かめたこと・再発防止策である。UWIは何を問われ・なぜ問われ・どう答えるかである。2つ目は、説明の無い内部の呼び名が無いことである
  - 基準を満たさない原稿は修正要として作成主体へ戻す
- 書込範囲・操作の許可と禁止は、原文の適用工程と原稿での適用工程が一致する。WI作成だけの制約を後続の実装・公開要件へ移した原稿は、起草者へ戻す

- `起草結果`の要求識別子が重複せず、渡した要求の集合と一致する。全体の`状態`行の有無が要求ごとの`結果`行と`続行できない理由`行から規則どおり導かれている
- `drafted`の要求は`既存項目の扱い`が再利用の場合を除き、原稿と成立性の証拠の絶対パスが実在して読める。原稿は`agent-toolkit:wi-standards`「通常AWIの本文」（UWIは`references/uwi-format.md`）を満たし、委譲元の会話や元項目に依存せず本文だけで理解できる。全節が`references/drafting-completion.md`「投入前の読み直し」の要求固有性の点検を満たす
- `既存項目の扱い`を返した要求は、既存項目の本文を読んで`drafting-completion.md`「重複判定」が成立することを確かめる。再利用は`保存開始`を送らず既存ファイル名を投入結果とし、部分被覆は原稿が未被覆部分だけを扱うことを確かめる
- AWIの反映内容・完成条件、UWIの問い・判断材料・回答による結果が、渡した要求（確定した要件と逐語本文）と一致し、「他AWIへ割当」の割当先が渡した`他の要求単位の割当`の値だけである
- 要件と技術判断の分類は、原要求・実回答の出所と成立性の証拠を入力として、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」で独立に検収する。ユーザーに帰属させる内容は`origin-and-approval.md`「由来と`source`」で判定し、選択回答が確定するのはその質問が問うた判断だけとする。質問本文、選択肢の説明、`共通前提:`行から補った実行方法や対象除外を要件として原稿へ求めない。修正要の原稿は作成主体へ戻す
- 不足の指摘には、その不足が採用案の成立か要求の達成を左右する理由を対応付ける。公開契約の実在、必要な値への到達、操作の開始から終了と途中失敗時の状態の成立は投入前に解消させる。成立性を変えない具体化（フィールド名、内部の関数分割、テストdoubleの形、実装後の検証手順など）は投入条件へ加えず計画工程へ渡す
- 再判定では前回指摘の解消、修正差分とその直接影響、要求追加を分けて確かめる。新しい指摘には、初回から残った不足、修正由来の不成立、要求追加のどれから生じたかを添える。整合の確認には全文を読み、修正の外の領域で新しい内部設計を求めない。前回の判定に無かった重大な不成立は根拠を添えて指摘する
- 説明追記は完成条件と一致していても`agent-toolkit:writing-standards`の`references/writing.md`「文章の共通規定」の必要性判定を満たす場合だけ受理し、満たさなければ採否の再選定を返す
- 仕分け・要約・統合を経た原稿は、成立性の証拠の元の調査結果へ個別の採否、変更箇所、保持条件、根拠を対応付けられる（`drafting-completion.md`「対象集合の仕分け」）
- 観測した欠陥を起点とするAWIは、`drafting-completion.md`「投入前の読み直し」の原因分析の項を委譲元が原稿と証拠の読取で独立に確かめる。直接的原因の根拠の値ごとに生成元と比較があり、主張の対象を表すと読み取れなければ不合格とする（委譲元は取得済み証拠を再利用する）。母集団が根本原因から導かれ全所有リポジトリへ展開されていること、処置の層と完了の判定が`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「類似見直し」「処置の階層」「類似見直しと再発防止の完了」に合うことも同じ確かめに含める
- 既存の値や設定を変える反映内容・選択肢には、`drafting-completion.md`「方針と判断の記録との比較」の結果が成立性の証拠と、AWIでは`## 実現性`にある
- 採用案の成立は、起草者と同じ`drafting-completion.md`の「実現方式の成立」の各項（経路全体の成立、適用・除外条件、設定の再現性、対象リポジトリの規範との整合）で判定する。観測事象を契機とする要求では、同書「採否と実現方式の確定」の、対策が直接的原因と主要な害へ作用することの確認も判定に含める。個別の値・特定のパス・手作業の操作など局所的な成立だけを根拠にした原稿は、不足する比較を添えて作成主体へ戻す
- 既存WIを前提・制約・代替案の不採用理由・完成条件の根拠に用いる原稿は、参照先WIの本文の引用が正しいことに加え、`origin-and-approval.md`「ユーザー専用の記入欄と是正要求」の参照するWIの規定でユーザーコメントと回答を含めて確定した有効な要求と結論が整合することを確かめる。ユーザーの是正と逆向きの前提へ依拠した原稿は作成主体へ戻す
- 投入先として指定された所有リポジトリの外にある対象を、処置不要として除外した原稿は、根拠とした現物のファイルと版が記録され、その現物で問題が生じないことを示すか確かめる。根拠が示さなければ同じ作成主体へ戻す
- 原稿が必須とする手段と条件が次の根拠に対応する。委譲元自身の追送やWIの記述は、次の根拠へ対応付けて評価する
  - 横展開処置・再発防止策が新設する構成要素と、完成条件が必須とする観測手段・比較・検収・工程: 明示要件、規範的制約、観測済みの欠陥に対応した必要性。共通定義、自動チェック、テスト、対象とする値の集合ごとに確かめる
  - 後続工程のモデル、ツール、担当エージェント、操作方法: その工程への適用を示すユーザー発話か独立した確認回答。渡した`確定した要件`が含めていた場合は要件から外して渡し直す
  - 処理を実施しない・延期する保護条件: `## 実現性`にある確定した要件、規範的制約、観測済みの欠陥のいずれか。外部文書が記す可能性や安全側であることだけでは対応先にならず、同じ担当へ戻す
- 依存が`states-and-dependencies.md`の基準に従い、後続本文の先行成果の必要性と対応する。先行項目の正式ファイル名が保存まで未確定でも、原稿と要求・成立性の証拠から先行要求と参照箇所の対応が一意に定まり、その意味を検収できれば合格とする。保存時の正式名への置換と保存結果との一致の確認は作成主体が`drafting-workflow.md`「投入」で行う
- 対象リポジトリの外へ成果を反映する原稿は、`awi-body.md`「完成条件」の外部反映の終了状態を反映先ごとに判定できる。規範と成立済みの認可から確定できる部分が未記載なら同じ担当へ戻し、ユーザーだけが決める範囲だけを「続行できない理由の扱い」の未確定事項として確認する
- ユーザーが明示した対象集合に未走査・後送りの範囲があれば不合格とし、残りの調査と反映を指示する。根本原因から導いた類似見直しの限定探索は、bugfixの重大度判断と探索範囲・限界・許容する残存リスクの記録を検収する。分割読取で読める未読や未調査を委譲元の調査へ引き取らない
- bugfixの重大度判断で終了した類似見直しの未走査部分を除き、原稿、証拠、返却（`想定外事象:`を含む）の未確認範囲は、担当が確かめる手段を持つ間は不合格とし、手段のある範囲は担当へ戻すか委譲元が確かめて渡す。受理の根拠には、要求された結果に到達した観測と成立条件を求める。失敗の記録を残す設計や完成判定への影響の有無だけでは、未確認範囲の成立を保証できない。手段の無い範囲は、根拠が`## 実現性`にあり`agent-toolkit:wi-standards`の`references/awi-body.md`「原因分析・適用範囲・実現性」の条件を満たす場合だけ受理する
- `判断の変更`を返した要求は、採った案が`確定した要件`の対象、範囲、外部可視の結果と両立することを確かめ、手段や条件を加える場合は前掲の根拠も確かめる
- `condition_not_met`の要求は`条件判定`が不成立の条件、調査対象、確認結果を示している。その要求は投入先のファイル名を使う後続工程から除く
