# AWIとUWIの共通規範

AWIとUWIは、ユーザーとエージェントが非同期に作業要求と確認事項を共有する人間向け文書である。
WI作成工程の入力、責務および出口は`${CLAUDE_PLUGIN_ROOT}/share/workflow-phases.md`に従う。
AWIは未完了の作業要求を、UWIはユーザーの判断を要する確認事項を表す。
UWIは回答を得るまで元の作業を再開または確定できない事前承認型と、最善と判断する対応を実施したうえでその対応の可否を問う事後承認型に分かれる。
自律モードのユーザーへの報告と回答はUWIへ記録し、UWIを使う場合はその保存を伝達の完了条件とする。確認の手段と無回答時の切替は`agent-toolkit:user-confirmation-and-report`「手段の選択」が定める。別項目の完了待ちと時間経過待ちは、依存関係と冷却時間で扱う。
WIの投入は、次回以降の`agent-toolkit:process-wi`が取得して処理する要求をキューへ保存する操作である。
投入したWIは投入元セッションの処理対象WIに加えず、同じセッションでの実施認可は既存の指示と承認から判定する。
現在の依頼と承認の範囲内で即時の是正が必要な場合は、そのセッションで是正を完遂する。後続セッションにも独立した作業要求を残す必要がある場合だけ、是正とは別にWIを投入する。
AWIとUWIはprivate-notesで管理するユーザーの手元の記録であり、対象リポジトリの公開物ではない。
リポジトリの外の読み手が参照できる成果物へこれらの識別子を書かない規定は`agent-toolkit:writing-standards`の`references/writing.md`「人間向け文章の共通規定」が定める。

対象リポジトリはAWIが対象とする実装リポジトリ、private-notesはWIのキューを保持するリポジトリを指す。

本文は`agent-toolkit:writing-standards`に従い、技術的な実装へ寄り過ぎず、単独で対象と期待結果を特定できる粒度で書く。
AWIは受け取った主体が本文の内容を実施するだけで完了へ到達できる粒度とする。反映先と完成条件が他の要求と重ならず、単独で採否と実装を判断できる要求は、別のAWIへ分ける。投入済みまたは起草中のAWIの対象、範囲または完成条件を具体化・変更する要求は、そのAWIを更新する。反映内容と反映先は投入の前に確定する。
調査を経なければ反映先を確定できない場合は、その調査を投入前に完了させ、確定した反映内容と反映先を本文へ書く。
本文の短縮は、重複の除去と、判断を変えない記述の削除だけで行う。略語や圧縮した用語は、本文か参照先で定義した用語として導入する場合に使い、定義せずにその場で作成した表現で短縮しない。定義の無い表現は、次の処理主体が本文だけで意味を確定できなくするためである。文字数と行数に機械的な上限を設定せず、内容に必要な長さとする。

## 通常AWIの本文

通常AWIは、受け取った主体が本文と対象リポジトリの実体だけで採否を判断し実装へ着手できる文書とする。必須H2の集合と順序は`atk wi add`が保存前に確かめ、各H2に書く内容は1つの節だけが持つ。本文形式、節の分担、完成条件と実現性の書き方は[references/awi-body.md](references/awi-body.md)が定める。

`## 反映内容と反映先`でWI処理の工程や運用を変える通常AWIを起草する場合は、起草前に`agent-toolkit:workflow-overview`を起動する。

### 起草完了の条件

AWIとUWIは採否と実現方式を投入前に一案へ確定し、投入前の読み直しの全項を満たした本文だけを投入する。確定の条件、実現方式の成立、重複判定および投入前の読み直しの点検は[references/drafting-completion.md](references/drafting-completion.md)が定める。

## 由来と承認

`source`の欠落だけを人間由来の初期値とし、値を持つ項目は要求単位に明示由来が無い限りエージェント由来として扱う。人間由来の要求単位を全部か一部不採用にする場合と、ユーザーが範囲語か開放列挙で示した集合を狭める場合は、ユーザーの明示承認を要する。AWIの`## ユーザーコメント`とUWIの`## 回答`はユーザーだけが書き込む。
明示由来の種類、承認として扱う記述、`source`の値、範囲語と程度、ユーザー専用の記入欄と是正要求および逐語転記は`references/origin-and-approval.md`が定める。

## 状態と依存

WIは`inbox`、`processing`、`hold`、`adopted`、`rejected`のいずれかの保存状態を持ち、`agent-toolkit:process-wi`は`inbox`と`processing`の項目だけを処理する。既存WIの更新・修復・採否の見直しが必要と分かった時点と、既存WIへの具体的な懸念を受けた時点では、調査や認識合わせより先に対象を保留する。別セッションが処理中の`processing`の項目は保留も本文の置換もせず、書き換えたい内容を新しい項目として投入する（処理中の項目の扱い）。
状態遷移と各遷移を起こす主体、commitを記録する採否操作の共通前提、保留と本文修正、終端、依存と冷却時間、事前承認型UWIの元項目の保留と「回答済みUWIの取り込み」は[references/states-and-dependencies.md](references/states-and-dependencies.md)が定める。上流リポジトリへの投入と元項目の扱いは[references/cross-repository-submission.md](references/cross-repository-submission.md)が定める。

## 事後承認型UWI

事後承認の判定は`agent-toolkit:user-confirmation-and-report`の`references/approval-scope.md`の事前・事後承認の区分に従う。事後承認型UWIの対象は実施した対応の可否とし、投入した主体は回答を待たずに元の作業を続ける。要求単位の未達の報告は`agent-toolkit:user-confirmation-and-report`「手段の選択」のユーザーへの報告に従う。本文と2択の書式は事前承認型を含めて[references/uwi-format.md](references/uwi-format.md)が定める。
是正を求める回答を受け取って実施した是正についても、その適否を実行主体が観測できない場合は、その回答を保存したUWIを終端したうえで、同じ手順で新しい事後承認型UWIを投入する。

## 投入と取得

WIの投入前と投入済みWIへの着手前には、対象リポジトリの回答済みUWIを`atk wi list --target-repo=<対象リポジトリの絶対パス> --type=uwi --answered=yes --skip-pull --summary-only`で取得する。同じ実装領域を扱う項目があれば`atk wi show`で回答本文を読み、新しい要求の`## 反映内容と反映先`および`## 完成条件`との両立を確認する。両立しない場合は投入または着手を止め、回答を上位として要求を是正するかユーザー確認する。回答済みUWIが0件なら比較対象は空とする。
対象リポジトリの有効な規範がWIの追跡先と本文形式（タイトルの接頭辞、参照行など）を同じ工程に求める場合は、その規範を確認して本文へ反映する。
追跡先の規範が投入前の記載を求める場合も、検知時の記載を求める場合も、その順序で記載し、登録後に記載の完了を確かめる。
この確認と外部操作は、追跡先を定めるリポジトリでだけ行う。

依存を伴う要求は、投入または依存の更新前に`references/states-and-dependencies.md`の先行成果の必要性基準を適用し、現行成果物だけで独立に実施・完成判定できないかを確定する。確定した依存だけを後続本文と`depends_on`へ反映する。

投入済みの項目を取得して着手する主体は、着手の前に`## 反映内容と反映先`・`## 完成条件`と`## 適用範囲`の対象集合の一致を`references/drafting-completion.md`「投入前の読み直し」と同じ基準で確認する。不一致を検出した場合は実装へ進まず、`agent-toolkit/rules/01-agent.md`「確認を要する事項」に従ってユーザー確認する。

1. エージェントが通常AWIを投入するとき、および投入済みAWIの内容（対象、範囲、完成条件などの本文）を更新するときは、自ら本文を起草せず、調査、本文の起草、投入または更新を`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`に従ってWI投入担当へ委譲する。長い対話や元の作業で文脈を占有された主体が起草すると、読んでいる既存規定を起草へ適用し損ねるため、起草を作業文脈の少ない担当へ移す。委譲する主体は`add-wi.parent.md`に従って起動、入力の受け渡しならびに返却値を検収する。既存AWIの更新では更新する項目の`ファイル名`を渡し、保留と解除は`references/states-and-dependencies.md`の順序で委譲元が行う。委譲先は確認を発行できないため、認識の違いで要件や結果が変わる未確定事項は、回答を得てからその要求を渡す。
2. 本文を保存する主体は、本文をファイルへ保存し、`atk wi add --body-file <path>`または`atk wi edit --body-file <path>`で渡す。投入直前に`references/drafting-completion.md`「投入前の読み直し」の対象集合の一致確認を行う。WI本文をコマンドライン引数で渡す受理形式は存在しない。手元で短い本文を投入する場合は`$EDITOR`を使う。
   同じ対象リポジトリへ、同じ時点で本文が確定した複数件を投入する場合は、`--body-file`を件数分繰り返し指定して1回の`atk wi add`へまとめる（努力目標。1回の呼び出しが生成した全エントリを1回のcommitとpushで確定し、反映の往復を減らすため）。
   依存する複数原稿の内容と依存関係が確定し、先行項目の正式ファイル名だけを待つ場合は、先行項目から依存順に投入する。先行項目の`atk wi add`が返した正式名を原稿へ対応付けてから、後続項目の`depends_on`と本文へ記入する。
3. 登録は本文の内容が確定した時点で行う。複数件をセッション終了時までためず、確定した順に登録する。
4. 登録するAWIの対象ファイルが現在のセッションの変更対象と重なる場合は、そのセッションが対象ファイルの変更を完了してから登録する（努力目標）。`atk wi process-loop`が動作する環境では登録が遅れると次の反復まで着手が遅れる一方、変更対象が重なる項目を即時に登録すると別の作業ツリーで同じファイルへ並行着手し得るため、両者を比較して時機を選ぶ。
5. エージェント自身の投入では「由来と承認」で確定した`source`を付ける。`source`が未指定の人間由来入力は、値を付けずに登録する。
6. `atk wi add`と`atk wi edit`が出力する成功報告と、表記診断以外の警告の不在を検収する。保存本文と送信元本文の一致確認はそのコマンドが行い、終了コードが0であれば一致が成立したとみなすため、保存本文の再取得は不要である。口語表現とダッシュの警告は行番号をもとに起草者が確認し、表記警告だけのときは保存済みWIを完了扱いとする。その他の警告やエラーは完了扱いにせず同じ手順で修復する。コマンドはprivate-notesのcommitとremote反映まで行うため、作業ツリー、branch、remoteの再取得も不要である。未push commitの通知がある場合だけ`atk wi commit`で反映する。保存は`atk`が使う作業ツリーで行う。
