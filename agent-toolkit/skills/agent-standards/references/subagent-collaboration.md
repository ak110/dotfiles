# サブエージェント連携の設計

サブエージェント（Agentツール・forkスキル等で独立コンテキスト起動される主体）を
含む設計・改訂時の観点を集約する。
呼び出し元スキル・agents定義・plan-mode計画本文のいずれでも本規定を適用する。

本規範は本節の新設以降に新設または改訂するサブエージェント設計・
呼び出し元起動プロンプトに対して適用する。
既存の呼び出し元スキル・エージェント
（`plan-impl-executor`・`agent-toolkit:plan-mode`等）は
本規範の各項目適合性の確認対象とする。
各スキルの次回改訂契機で個別確認する。

## サブエージェント定義と起動文の責務分離

名前付きサブエージェントの定義本文は呼び出し先だけへ自動ロードされる。
定義本文は恒常的な役割、手順、規範、受信側の入力契約、出力契約の正本とする。
呼び出し元は定義本文を読まず、呼び出し元側の専用referenceを起動契約の正本とする。
起動契約は正しい`subagent_type`、必須入力、起動形式、呼び出し元側の準備、
完了報告の検収、後続処理を定める。
起動文は専用referenceが要求する実行時の値と、同referenceが許容する追加指示だけで構成する。
呼び出し先の恒常的な内部手順は起動文へ再掲しない。

呼び出し元は次を担当する。

- 専用referenceが要求する値を実測し、欄名と意味を保って渡す
- 専用referenceが定める`subagent_type`と起動形式で起動する
- 呼び出し元だけが保持するユーザー合意、実施済み結果、継続用識別子を渡す
- 直接起動した子のAgent識別子を保持し、同じ子を継続する場合は自身が`SendMessage`で再開する
- 専用referenceの完了報告検収契約に従って検収し、後続工程を実施する

定義本文は次を担当する。

- 全起動へ共通する役割、手順、判断基準、制約を定める
- 常時参照する規範スキルをSkillツールで読み込む手順を定める
- 入力の意味、必須性、未指定時の扱いを定める
- 完了条件と出力契約を定める

専用定義を持たない`claude`と`Explore`への起動文は、対象、適用規範、成功条件、
制約を含む自己完結した本文とする。
名前付き定義の恒常的な内部手順と完了報告の生成方法は定義本文を正本とする。
呼び出し元が制御する`subagent_type`と起動形式は専用referenceを正本とする。

専用定義を持たない型へ委譲する場合は、作業難易度に対応するモデルも呼び出し元が起動文で指定する。
委譲する作業の内容を確定するのは呼び出し元であり、名前付き定義のように定義側がモデルを保持しないためである。
名前付き定義のモデルは定義frontmatterを正本とする。

## 独立コンテキスト前提の認識

Claude Code固有のサブエージェント実装制約は`agent-toolkit/rules/99-claude-code.md`
「サブエージェント実装」節に集約する。本節は独立コンテキスト起動全般に共通する一般原則のみを扱う。

サブエージェントはメイン側の会話履歴・拡張思考・他サブエージェント出力を
参照できない。このため起動プロンプトから以下を排除する。

- 相対参照（具体的な語彙は`agent-toolkit/rules/02-agent-operations.md`
  「サブエージェント運用」節に集約する。本節は当該参照のみを配置する）
- 呼び出し元の暗黙前提
  （プロジェクト固有ディレクトリ構成の暗黙認識など）
- メイン側で確定済みの判断結果への参照
  （サブエージェント側で再導出できない材料）

Agentツール起動は常に独立コンテキストで開始される確定事実であり、
「コンテキストがクリアされている可能性がある」等の不確定表現をサブエージェント定義本文へ書かない。
呼び出し元の行動（起動前準備・完了報告の受領後の手順・自立性の担保責務等）を規定する記述は、
サブエージェント定義本文でなく呼び出し元文書（スキル本文・`references/`）側へ書く。

孫サブエージェント（サブエージェントからさらに委譲する場合）も
同様の非共有前提を適用する。

## 成果物へのユーザー発話・合意事項の転記制約

サブエージェントが成果物へ転記するユーザー発話・合意事項は、
起動プロンプトで引き渡された原文に限る。
プロンプトに存在しない合意・指示を生成した場合はエージェント提案として区分し、
合意欄へ含めない。

## 必要な規範スキルの引き渡し

名前付きサブエージェントが常時参照する規範スキルは、定義本文の手順としてSkillツールで読み込む。
frontmatterの`skills:`によるプリロードは採用しない。
プリロードはSkillツールの呼び出しを伴わないためセッション状態フラグが真化せず、
当該フラグを参照する検査が委譲先のツール呼び出しをブロックする。
起動文は実行時の対象によって追加適用する条件付き規範だけを渡す。
条件付き規範の受理方法は定義の`## 入力`へ明記する。

非forkサブエージェントは、親セッションが実際に読み込んだCLAUDE.mdとメモリー階層
（プロジェクトルールを含む）を受け取る。組み込み`Explore`と`Plan`は当該階層を省略する。
親セッション開始時のgitステータスは、作業ディレクトリがGitリポジトリで
`includeGitInstructions`が有効な場合に限り受け取る。組み込み`Explore`と`Plan`はいずれの条件でも省略する。
同名のユーザー定義またはプロジェクト定義が組み込み定義を上書きした場合は、
カスタムサブエージェントとして親が読み込んだ当該階層を受け取る。
組み込み当該2種へ委譲する場合は、適用する規範の節本文を起動文へ引用転記するか、
規範ファイルの絶対パスと適用節を示して着手時に全文Readさせる。
専用定義を持たない`claude`は親が実際に読み込んだ当該階層を受け取るため、
引用転記を求める対象から外す。
組み込み定義かカスタム定義かを名前だけで判定しない。

委譲先の出力を候補として受け取り、規範適合性を呼び出し元が確定する委譲では、
判断の独立性を確保する目的でプロジェクト規範を渡さない選択を採用できる。
この場合は成果物へ規範適合を求めず、報告を候補として扱う旨と、
呼び出し元が規範に照らして確定する旨を起動文へ明記する。

対応方針の選択・推奨を求める調査は、前段落が定める「プロジェクト規範を渡さない」例外の対象外とする。
技術的な最適と明文化された方針への適合は別軸であり、独立コンテキストでの判断を理由に
方針適合の確認を省略できないためである。実行時の方針文書読取と衝突確認は、
`02-agent-operations.md`「サブエージェント運用」節が定める。

## 起動契約と受信側入力契約のペア更新

名前付きサブエージェントの起動契約は、呼び出し元側の専用referenceを正本とする。
受信側の解釈はサブエージェント定義の`## 入力`または相当節を正本とする。
入力名、意味、値集合、必須性、未指定時の扱い、出力への反映を片方で改訂する場合は、
もう片方を同じ計画で更新する。
完了報告の生成欄と呼び出し元の検収欄も同じペア更新を適用する。
起動契約だけに存在する欄と、呼び出し元から渡す経路が無い受信欄は、
計画レビューの重大指摘対象とする。

## 計画処理の委譲関係

計画レビューは`agent-toolkit:plan-mode`の呼び出し元が機械チェック・修正系と総合レビュー系へ直接委譲する。
直接委譲の比較基準、累積差分、採否、反映、限定再レビューは、
`agent-toolkit/skills/plan-mode/references/plan-review-delegation.md`を正本とする。

`plan-impl-executor`はHaiku固定の委譲窓口として維持する。
同executorは成果物を直接編集せず、`agent-toolkit:codex-exec`を接続経路として、
実装・修正系、計画準拠実装レビュー系、独立実装レビュー系へ委譲する。
3系統は履歴、thread、Agent識別子を共有せず、2つのレビュー系は並列起動する。

codexまたは汎用Agentへの共通の起動文、通常配送、代替記録、完了済みAgentの継続条件は、
`agent-toolkit/skills/codex-exec/references/delegation-boilerplate.md`を正本とする。
Agent識別子の所有主体は直接起動した主体とし、所有主体だけが同じAgentを継続できる。
用途固有の資料契約は`agent-toolkit/skills/codex-exec/references/`配下のtask referenceを正本とする。

## 出力節への追加要素導入

サブエージェント定義の`## 出力`節に新規要素（観点網羅サマリー・チェックリスト等）を導入する場合、
既存の「前置き禁止」「全体サマリー禁止」等の規定を「本節の新規要素を除き〜」形式で例外化する。
例外化文言のテンプレートは「`{追加要素名}`を除き前置き・全体サマリーは含めない」とする。

- 追加要素が定型構造（節見出し・チェックボックス等）を伴う場合はコードフェンス内テンプレートへ配置する
- 追加要素が運用条件（例外的許容の要件・入力欠落時の挙動等）のみで定型構造を伴わない場合は
  地の文の箇条書きで規定する
