# LLM読者特性と記述指針

コーディングエージェント向け文書の読者はLLMであり、知識の想起・注意・推論に人間の読者と異なる傾向を持つ。
観測されやすい特性ごとに、文書設計で取る行動を定める。
各特性は運用で観測された傾向に基づく設計上のリスクモデルであり、個別環境・個別モデルでの成立を保証しない。
全指針は努力目標とし、`agent-toolkit/skills/agent-standards/SKILL.md`・他の規範と重なる場合は
当該規範の本文を正本とする。

## 知識の想起

- LLMはコンテキスト内の語彙に誘発されて知識を想起する傾向があり、関連分野の語がコンテキストに
  無い場合は原理原則だけでは必要な知識を引き出せないことが多い。
  一般則には対象分野の語彙を含む具体的事項の列挙を添える
- 例示は発想を例の近傍へ狭める作用を持ちやすい。
  例示には上位概念と範囲語を併記して代表例であることを示す
  （書式は`../../writing-standards/SKILL.md`の開いた列挙規定、読み手側の解釈は
  `agent-toolkit/rules/01-agent.md`「ユーザー発話の解釈」が定める）
- 名前付き概念は再利用されやすい。
  繰り返し参照する原則には短い固有名を付け、以後は名前で参照する

## コンテキスト配置

- 冒頭で一括ロードされる文書（`AGENTS.md`・`CLAUDE.md`・ルールなど）の規範は、
  作業が進みコンテキスト内の距離が広がるほど参照から漏れやすい。
  次の3層を目安に配置する
  - 常時保持: 優先順位、不変条件、禁止事項、完了条件、プロジェクト固有概念
  - 条件付きロード: 言語・領域・作業種別ごとの規範（スキル・paths指定ルール）
  - 手順途中ロード: デプロイ・migration・releaseなどの、フェーズ依存の詳細手順
    （`references/`分割と工程内の読込指示）
- 分割は1回の作業で同時に必要となる情報のまとまりを単位とし、
  常に同時に読む内容を複数ファイルへ分けない
- テーマの異なる項目が単一階層の列挙へ混在すると、現在の作業と関連の薄い項目ほど注意から脱落しやすい。
  項目はテーマ別または適用場面別の見出しへ分ける
- 規則を質問されれば説明できる状態と、作業中に遵守できる状態は別である。
  重要規則は宣言に加え、観測可能な契機と結びつけたチェックポイント
  （「schema変更を検知したらmigration手順を読み込んでから編集する」等）として工程へ埋め込む

## 指示の明瞭さ

- LLMは重要度の表明より指示の明瞭さに強く反応する傾向がある。
  抽象的な要求は観測可能な行動へ変換して書く（規定本文は`agent-toolkit:agent-standards`「完成条件」）
- 禁止事項の羅列は誤行動を誘発しやすい。
  正しい行動を肯定形で明記する（規定本文は`agent-toolkit:agent-standards`「完成条件」）
- 複数の指示が併存すると局所的に満たしやすい指示へ寄りやすい
  （「最小変更」と「根本原因の修正」の併存では最小差分の対症療法へ偏る等）。
  衝突し得る指示には優先順位または衝突時の判定原則を明示する
- 否定形・例外・二重条件（「Aの場合を除きBしない。ただしCなら〜」等）は誤適用されやすい。
  条件と行動が一対一へ近づく形（decision table・条件別の箇条書き）で書く

## 判断の偏りと工程設計

判断の偏りは規範の宣言では抑止しにくいため、偏りを相殺する工程を手順として明文化する。

- 途中で採用した仮説へ後続の探索が偏りやすい。
  デバッグ・調査の手順には、修正前の原因実証と反証候補の確認を工程として置く
- 開いたファイル・検索結果などの可視範囲を全体と誤認し、未探索領域を見落としやすい。
  網羅性を要する手順には母集団の定義と網羅確認の工程を置く
- 既存コードの慣習・技術的負債を仕様と誤認して模倣することも、
  一般論を固有事情のあるプロジェクトへ持ち込みすぎることもある。
  維持する契約と単なる現状を文書上で区別する
  （実態と方針の照合は`agent-toolkit/rules/01-agent.md`「規範と実態の照合」が定める）
- 自己生成した記述もコンテキストとなり後続判断へ影響する。
  重要な状態を記録する書式には「推測」と「確認済み」の区分を設ける

## 文脈・役割の混同

- 対象読者: 複数読者向けの記述が同居すると語彙・前提知識・説明粒度が混ざりやすい
  （読者別の書き分けは`../../writing-standards/SKILL.md`「読み手別の追加注意点」が定める）
- 実行主体: 委譲の呼び出し側と受信側の指示を同一文書へ併記すると、
  呼び出し元が受信側の制約を自分へ適用し、受信側へ委ねる判断を自分で処理しやすい
  （責務の分離は`references/agent-skills.md`「委譲文書の責務分離」が定める）
- 役割記述: 文書内に登場する役割の記述（「管理者として説明する」等）を、
  実行中の自身の役割として取り込むことがある。
  説明対象としての役割と読者へ求める役割を区別できる形で書く
- タスク間の状態: 連続する複数タスクでは前タスクの制約・仮説・識別子を後続へ持ち越しやすい
  （類似のファイル名・API名・概念がある場合に起きやすい）。
  複数タスクを扱う手順にはタスク境界と、境界で引き継ぐ状態・破棄する状態の列挙を求める
