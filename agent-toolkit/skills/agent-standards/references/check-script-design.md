# 機械チェックスクリプトの設計原則

エージェントが反復実行する機械チェックスクリプト（`check_*.py`等、計画ファイル・規範文書に対する
検査スクリプト全般）は、出力がエージェントのコンテキストへ蓄積されるため、
ノイズの抑制と起動回数の削減を設計段階で担保する。

自動検査は入力が構造化され、期待値が一意な場合だけ追加する。
仕様変更以外では判定が安定し、違反時の是正方法を一意に示せることも条件とする。
自然言語の意味、責務の妥当性、命令性など、
複数の正当な解釈がある対象はauthor契約とreviewで扱う。

## 出力の簡潔さ

- 成功時（違反なし）は無出力でexit 0とする。違反発見の有無を確認するため出力を読む手間を発生させない
- `error`区分の違反時は`stderr`へ該当箇所と要点のみを出力し、exit 1とする。
  `warning`区分は`stderr`へ`[warn]`等の識別子付きで出力しexit codeへ算入しない
  （区分の判定基準は本ファイル末尾の区分基準節を参照する）
- 引数誤用・対象ファイル不在・読み込み権限不足・不正なエンコーディングなど
  検査を開始できない実行前エラーはexit 2とし、検査違反（exit 1）と区別する。
  呼び出し側が「検査対象の内容に問題がある」と「検査する前提条件が満たせない」を
  判別できる状態を保つ。本規定は新規実装・改修時に適用する努力目標とし、
  既存スクリプトへの一括遡及適用は求めない
- 外部コマンド（textlint等）の生出力をそのまま転記せず、違反行のみへ要約する
  （JSONL等の構造化出力はパースして違反件数・該当箇所のみ提示する）

## 起動の統合

- 同一契機（例: 計画ファイル書き込み直後）で反復起動される複数の独立スクリプトは、
  1プロセスで実行する統合ランナーへ集約する
- 統合ランナーは各スクリプトが公開済みの検査用関数をimportで再利用する。
  同一検査対象への重複したサブプロセス起動を避ける（配布境界を跨ぐ場合の
  サブプロセス呼び出しは許容する）。`check_plan_file.py`を参考実装とする

## 構造化文書の解析

Markdownなどの構造化文書を検査する場合は、構造認識と原記法の検査を分離する。

- 見出し、コードフェンス、表の範囲、節の親子関係は、標準準拠のパーサーが1回生成したトークン列と位置情報から認識する
- パーサーが補完、除去、段落へ変換する可能性がある原記法は、表トークンと段落トークンの位置情報から取得した原文を別関数で検査する
  - 表の列数、外側パイプ、セル数の一致を原文から判定する
  - 表に変換されなかった段落では、パイプ区切りのヘッダー候補と直後の区切り行候補についてセル数の不一致を検出する
- 原文検査の対象範囲は、パーサーが表または段落として分類した箇所に限定する
- 構造認識と原記法検査の関数は分離し、各docstringへ担当する検査、受け取るトークン範囲、段落内の候補条件を記載する
- 正規表現は原文の内容照合に限定し、列数は区切り記号で分割した要素数から計算する
- 検査項目を追加する場合は、次の構文境界を含む共通コーパスへ検体を追加してから実装する
  - インデント、コードブロック内の記述、見出しの閉じ記号
  - 表の外側パイプの省略、表トークンになる列数不一致、段落へ変換される列数不一致
  - 同名節の重複、親節の違い
- 解析結果を各検査へ渡し、検査ごとの再解析を避ける

## 検査項目のerror・warning区分

- `error`区分（exit codeへ算入）は、計画が成立しない致命的な問題の検出に限定する
  （パス・スキル名・節見出しの実在確認失敗、対象ファイル一覧との不整合等）
- 計画の成立可否に影響しない体裁・表現規範は新規の機械チェック対象にしない。
  本文から数えて把握できる件数・列挙を明記しない日本語表現の原則は、
  機械チェック対象化を明示的に禁じているためこの区分に属し、機械チェックを持たない
- 体裁・表記系（textlint・markdownlint・typos・口語表現等）は`warning`出力に限定し、
  exit codeへ算入しない。判断根拠は`agent-toolkit:plan-mode`の
  「計画作成プロセス自体を変更する場合」節の改訂方針（体裁・表記の指摘は警告に留める）に従う
- 新設検査を追加する場合、`error`・`warning`区分の判定根拠を検査スクリプトのdocstringへ明記する
