# 「品質最優先」原則の先送り例外規定

`agent-toolkit/rules/01-agent.md`「品質最優先」節の詳細補足として、
`atk mq`連携の先送り例外規定・非該当時のデフォルト完遂義務・
登録済み手順の省略禁止と品質作業追加の正規経路（非対称原則）を集約する。

## 正規追加経路の非対称原則

いかなる理由（例: 変更規模・所要時間見込み等）があっても登録済み手順を省略しない。
ここでの登録済み手順とは、規範文書が明示し発火条件が成立した必須の工程・ステップを指す。
条件不成立で対象外となった工程・説明目的の節は含まない。
代表例は`agent-toolkit:plan-mode`「計画ファイルの完成条件」節の各要件・`agent-toolkit:process-feedbacks`ステップ1〜7である。
一方、登録済み手順に列挙のない品質作業（品質最優先の原則・判断の妥当性を評価する観点・
`agent-toolkit:review-standards`が求める自発判断型の点検を含む）の追加実施は常時許可する。
ただし公開インターフェース変更・破壊的操作・他利用者への影響を伴う追加実施は、
`agent-toolkit/rules/01-agent.md`「品質最優先」節の既存合意要件を維持したまま実施する。
追加実施の帰結は次の2経路と1例外のいずれかへ収束させる。

- 経路1: 現在進行中の計画または現在のセッションの作業へ取り込む
  （`## 変更内容`・`### 恒久化・リファクタリング内容`等へ反映し同一計画内で完遂する。
  計画ファイル不在時は同一セッション内で対応を完遂するものとする）
- 経路2: 「`atk mq`連携の先送り例外」節が定めるいずれかの例外区分について、
  その区分の全条件を満たす場合に`atk mq add`で正規登録する
- 例外: `agent-toolkit/rules/01-agent.md`「完遂と先送り」節が定める先送り基準を満たす場合、
  別セッションへの移管（別計画化）を第三の対応区分として認める。
  基準は、根拠が現在の作業と独立し成果物の品質に影響しない事象とする。
  またはユーザー合意・別リポジトリ横断作業・独立した新規計画の立案を要する事象も基準に含める。
  同節の規模基準に当たる未着手の追加対応も基準に含める

上記2経路・1例外のいずれも伴わない先送り（登録を伴わない停止・省略・確認待ち等）は本原則の対象外とする。
当該先送りは`scope-escalation-phrases.md`「縮退表明の定義」節が定める縮退表明として禁止される。

本原則は次の緊張点の解消基準を兼ねる。

- 定性的な状況説明と数値化された作業量主張の境界: 品質最優先の原則に基づき対応範囲を拡大した旨を説明する場合、
  実施済み観測事象（点検した観点・発見した事象・反映先）のみを記述する。
  件数・所要時間・残作業量等の自己推定量は記述しない
  （`agent-toolkit/rules/01-agent.md`「完遂と先送り」節が定める、所要時間・作業量・コンテキスト消費量を
  着手・継続・停止の判断材料にしない規定と同一基準を用いる）。
  本禁止は実行時の自己申告に適用し、「`atk mq`連携の先送り例外」節が定める
  変更対象ファイル数の判定手続きとは適用対象を異にする
- `agent-toolkit:plan-mode`「工程の進め方」節の暗黙スキップ・明示バイパスの禁止バレットと
  本ファイルの適用順序: 登録済み工程の省略発話・記録を検知した場合、
  まず即時無効化・正規工程への復帰を先に完了させる。
  復帰後に当該発話・記録を観測事象として扱いたい場合のみ、本ファイル
  「`atk mq`連携の先送り例外」節の条件充足を判定する（順序の入れ替えは不可）

## フィードバック自動継続機構の例外

フィードバック自動継続機構（`atk mq process-loop`等の外部処理系）が導入された環境では、
処理系設計上の分割（inbox残存を引き継ぎ媒体とする自動継続）を「完遂と先送り」節の例外として認める。
未導入環境では本例外は適用対象外となり、処理単位の確定後の対象削減は縮退表明として禁止する。

- 本例外の適用範囲は着手前の処理単位の確定タイミングでの全件取得のみとし、
  処理単位の確定後およびネストスキル実行中は先送り・中断・呼び出し元スキルへの復帰の根拠に転用しない
- 途中中断は`atk mq process-loop`側で異常終了扱いとなり自動継続自体が停止する
  （次セッションの自動起動は`agent-toolkit:exit-session`の正常終了コード検知後にのみ発生）

## `atk mq`連携の先送り例外

- 次の全条件を満たす事象は`atk mq add`によるフィードバック登録を正規経路として認める。
  本条件を満たすフィードバック登録は縮退表明に該当しない
  - 根本原因が現在の作業・計画と独立すること（自セッション導入の不良・当該計画スコープ内の問題は対象外）
  - 現在のセッションの成果物品質（テスト成功・lint適合・規範適合・コミット可能性）に影響しないこと
  - 対応にユーザー合意（公開インターフェース変更・規範方針判断など）・別リポジトリ横断作業・
    独立した新規計画の立案のいずれかを要すること
  （上記全条件は`agent-toolkit/rules/01-agent.md`「完遂と先送り」節が定める、所要時間・作業量・
  コンテキスト消費量を着手・継続・停止の判断材料にしない規定に従う）
- 先送り時は事象・根本原因分析・対応案を含む完結したフィードバック本文で登録し、
  登録した旨をユーザーへ報告する（登録をもって「正規経路への引き渡し完了」と扱う）。
  自セッション由来のlint違反・テスト失敗・品質ゲート指摘・自セッション導入の問題は先送り禁止のまま維持し、
  同一根本原因のフィードバックが既にinboxまたは処理履歴にあれば重複登録せず既存項目を見直す。
  判断に迷う場合は先送りせず同一セッション内で対応する（既定は完遂側）
- 既存不良（flaky test・既知バグ・既存lint違反・既存規範違反・既存の陳腐化記述等）も本例外規定の対象に含む。
  例外の全条件を満たさない場合は計画スコープ外を理由に対処を見送らず、発見時点で同一計画内に対処項目として組み込む。
  対処不能の根拠は公式仕様・実機検証で観測可能な事実に限り、成立しない場合は判断を保留せずメイン側へ即時報告する。
  既存コード・既存ファイルの規範違反パターンや「既存の同種ファイルと同運用」等の類似性主張も
  新規追加分の正当化根拠にせず、新規追加分・既存違反自体ともに同一計画内で是正する
- 機械検出（`_scope_escalation.py`によるカテゴリ判定、`pretooluse.py`・`stop_advisor.py`双方の検出経路を含む、
  `pattern-conformance`カテゴリ）は本例外の条件充足を判定しない。
  `process-omission`カテゴリの`session-review`・振り返り・観測事象を主語とする記録型フレーズ、
  および正規のフィードバック登録報告文（`atk mq add`実行後の登録通知など）も同じ扱いとする。
  当該事象で機械検出がフレーズを拾った場合は、根本原因の独立性・成果物品質への非影響・
  対応要件充足を個別に確認する。
  条件充足を確認したうえで、事象そのものを`atk mq add`による正規経路の
  完結したフィードバック本文として登録する（上記のとおり引き渡し完了として扱う）
- 段階的移行の継続例外を認める。対象計画とテーマ・設計意図が同一の後続段階であっても、
  次の全条件を満たす場合は`atk mq add`によるフィードバック登録を正規経路として認める。
  独立事象向けの既存条件とは適用対象を異にし、同一の先送り事象が両条件を同時に満たすとは扱わない
  - 対象計画の成果物が、引き継ぎ分を含まずに単独完結すること
    （テスト成功・状態の一貫性・コミット可能性を満たす）
  - 引き継ぎ分が独立した計画として成立する分離性を持つこと
  - 完結したフィードバック本文の登録を伴うこと
- 段階的移行の継続例外の適用時は、登録した旨の報告のみで足り、
  協調モード・自律実行モードとも事前確認・事後確認は求めない
- 規模超過の先送り例外を認める。次の全条件を満たす場合は、
  `atk mq add`によるフィードバック登録を正規経路として認める。
  独立事象向けの既存条件・段階的移行の継続例外とは適用対象を異にし、
  同一の先送り事象が複数区分を同時に満たすとは扱わない
  - 未着手の追加対応であること（着手済み工程の継続には適用しない）
  - `agent-toolkit/rules/01-agent.md`「完遂と先送り」節の規模基準に当たること。
    判定は対応に必要な変更対象ファイルのパスを列挙し、
    現在の作業の変更対象に含まれないものを数える手続きによる
  - 機能不全（バグ・テスト失敗・lint違反・品質ゲートの指摘）の是正以外であること
  - 完結したフィードバック本文の登録を伴うこと
- 規模超過の先送り例外の適用時は、登録した旨の報告のみで足り、事前確認・事後確認は求めない。
  ただし当該事象が`agent-toolkit/rules/01-agent.md`「協調モードでの確認」節の確認要件
  （公開インターフェース変更・破壊的操作・他利用者への影響を伴う場合等）に該当するときは、
  協調モードでの確認義務を維持する
- 規模超過の先送り例外において、先送りを選ぶか同一セッション内で対応するかの選択は努力目標とし、
  先送りを選んだ場合の完結した本文での登録と報告は厳守規定とする
- 30件という基準値は、1回の作業単位あたりの変更ファイル数と所要時間の関係、
  および先送りした事象が実際に処理されるまでの待ち時間の実測から定めた。
  運用実績がこれらの前提と乖離する環境では、基準値ごと見直す
- いかなる理由（例: 段階的移行の継続例外・規模超過の先送り例外に該当すること）があっても、
  フィードバック登録を伴わない先送り宣言を発行しない
