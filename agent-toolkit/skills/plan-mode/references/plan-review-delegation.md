# 計画レビュー

計画の計画担当が計画構造検査、指摘の検収、計画修正を所有し、計画レビュー担当へ成立性の評価だけを委譲する。

## 計画担当の計画構造検査

初版の起草後、計画担当自身が`../scripts/check_plan_file.py`を実行する。
新規計画は`<計画名>.md`（メイン側）と`<計画名>.detail.md`（detail側）の両方を書き込み、
`check_plan_file.py`へはメイン側の絶対パスだけを渡す（同スクリプトが対応するdetail側を
stem導出で解決し、両側の節構成を検査する）。
通常モードでは計画担当が正規計画へ書き込み、正規計画（メイン側・detail側の両ファイル）を検査する。plan modeでは計画担当が指定された
サンドボックスへ書き込み、同じサンドボックスを検査する。調整主体はサンドボックスの検収後に正規計画へ反映し、
正規計画を検査する。plan modeを終了した後の修正は計画担当が正規計画へ書き込む。各パスの書込主体は常に1名とする。
違反は現在の書込主体が対象ファイルで修正し、全検査を再実行する。終了コード、警告、修正概要を保持する。

計画構造検査の各回（初版の起草後と指摘反映後）に、`git -C <対象リポジトリ> rev-parse HEAD`を同じ回で実行する。
現行HEADが`### 計画メタ情報`のベースコミットと一致しない場合は、`git diff <ベースコミット>..HEAD --name-only`で差分ファイル一覧を取得する。
差分がファイル群別の変更説明の対象又は完了条件の判定前提へ及ぶ場合は、ベースコミットと当該前提を更新してからレビューを起動する。
及ばない場合はベースコミットを更新しない。

## 計画レビュー担当

計画構造検査の成功後、計画担当は計画レビュー担当を起動する前に、`plan-file-standards.md`の全項と
計画本文を照合する計画自己監査を1巡する。
自己監査は品質形成であり、計画レビュー担当の検証責務を置き換えない。

自己監査を完了後、計画担当を起動した調整主体がある場合は調整主体が計画レビュー担当を起動する。
調整主体が無い場合は計画担当が`agent-toolkit:delegation`に従って起動する。
調整主体はレビュー表の絶対パスを確定する。
初回strict検証の前に表へ`atk review-table init <レビュー表>`を実行し、直後に`atk review-table validate <レビュー表>`を実行する。
1つの表を全ラウンドで使い続け、先頭4列の複合キーへラウンドを含めることで、未解消の同一指摘を次ラウンドの行として再提示する。
起動主体はレビュー担当の新規起動又は継続接続の直前に`atk config get plan_review_model`を実行し、
`../../delegation/references/runtime-routing.md`「工程別モデル設定」に従って経路を解決する。
起動文は受信者への命令を先頭に置き、次の絶対パスと今回のレビュー種別を全レビュー共通の入力として渡す。
初回・再レビュー固有の入力は、後続の規定に従って追加する。

- `plan-review-task.md`
- 正規計画（新書式はメイン側・detail側の絶対パスの組、旧形式は単一パス）
- 対象リポジトリ
- プロジェクト規範
- `plan-file-standards.md`と`../../review-standards/SKILL.md`
- レビュー指摘管理表の絶対パス

初回レビューでは、計画全文に加えて元のユーザー指示、
復元・巻き戻し型の変更では項目別の維持・修正・撤去の判定と根拠を照合基準として明示的に渡す。
フィードバック原文経路では、対象のフィードバックファイル名、対象リポジトリ及び計画内の素材表・要求表を渡す。
新形式の素材表に`種別=フィードバック`かつファイル名の`キューID`を持つ行が存在するとき、レビュー担当は
同じ対象リポジトリの全キューIDを後述の`### 一括取得の管理対象一時領域`の手順で対象リポジトリごとに1回取得する。
終了コード0で要求した全項目が出力された場合だけ、要求ID、素材参照、採否、採用範囲、除外範囲、根拠へ照合する。
終了コード2では標準出力の部分結果を使わず、初回レビューを開始しないで入力不足として起動主体へ返す。
旧形式では`原文正本ID`のフィードバックファイル名を同じ条件で取得する。該当素材が無い場合は取得を省略する。
この経路ではフィードバック本文と専用ファイルを起動文へ複製しない。
直接起動経路では、素材表・要求表と出所・引用範囲を渡す。
キューにない素材の逐語本文・回答全文は計画外の明示入力として、初回レビュー担当へ渡す。
元のユーザー指示は経路と独立した入力とする。
人間由来の場合は種別、出所及び引用範囲を付けた入力を渡し、常駐自動起動の場合は非該当と起動事実を渡す。
直接起動経路では、直接受領した実際の利用者メッセージを渡す。
`AskUserQuestion`由来の合意は、投入元を`AskUserQuestion`、引用範囲を`回答全文`として示し、質問本文をエージェントが作成した文として区別する。
出所と引用範囲を失った要約だけを一次入力にせず、レビュー担当が素材表・要求表から目的と適用範囲を再確認できる状態にする。

### 一括取得の管理対象一時領域

取得主体が`atk managed-temp create --prefix mq-show`を実行し、終了コード0、標準出力が単一の絶対パス、かつ実在するディレクトリであることを確認する。作成主体だけがcleanup完了まで領域と保存内容を所有し、別の実行主体へパス又は内容を渡さない。
作成時に得た絶対パスの`mq-show.stdout`へ`atk mq show <filename>... --target-repo=<repo> --skip-pull`の標準出力を保存し、保存ファイルを全文読む。
終了コード0で全項目が出力された場合だけ本文を採用する。出力順序と本文境界は`atk mq show`のCLI契約とする。
採用後は本文照合後、非0終了時は部分出力を使わないことを確定してから、作成時と同じ実在する絶対パスを検収し、`atk managed-temp cleanup --path <検収済み絶対パス>`を実行する。cleanup終了コード0を確認してから、非0終了では要求した全項目を単数取得し、採用時は照合へ進む。
標準出力の保存または保存ファイルの読取機能が無い場合、`managed-temp create`が非0終了した場合、保存・書込み・再読込が失敗した場合だけ、cleanup成功後に分割取得へ代替する。cleanup非0終了時は絶対パスとエラーを起動主体へ返して停止し、分割取得、新しい一時領域の作成と後続工程へ移行しない。

再レビューでは、既知でない情報に加えて、今回のラウンド番号と今回の表の絶対パスを必須差分入力として渡す。
`runtime-routing.md`の同じ担当・同じタスク・実効3値一致の条件により同一threadを継続する場合は、
同一threadでは、前項の必須差分入力を添えて「再レビューを実施せよ」に相当する指示を送る。
初回レビュー起動後に人間由来の入力（`AskUserQuestion`の回答、TBDの回答、利用者の追加指示）を受領した場合は、
素材ID、種別、逐語文、出所、引用範囲、要求IDとの対応をレビュー担当へ渡す。
利用者合意か参考素材かの区分も渡してから再レビューを指示する。
同一threadの継続では当該情報を追送し、新規起動では初回と同じ入力パス集合と検収済み状態を渡す。
再レビューへの追送には、キューにない素材の逐語本文・回答全文も計画外の明示入力として含め、初回から共有した入力と同じ値を保持する。
当該情報を渡さない限り、その発話を根拠とする実施又は除外を計画へ書かない。
解決内容、変更履歴ID、再監査条項、出力形式、読み取り専用契約を起動文へ再記述しない。
新規起動では経路に応じた初回と同じ入力パス集合と検収済み状態を渡す。
差分要約と追加範囲は計画本文を正本とし、起動文へ再記述しない。

レビュー担当は正規計画と対象リポジトリを読み取り専用とする。
レビュー担当を起動した調整主体は起動前後のGit状態を比較し、レビュー担当の書き込みを検出した場合は結果を採用しない。
調整主体が無い場合は計画担当が比較する。

## 指摘の検収と修正

計画担当は`agent-toolkit:reviewee-standards`の`SKILL.md`を適用し、
`agent-toolkit:review-standards`の`references/judgment-details.md`を全文読んで指摘の採否と修正を確定する。
調整主体が指摘を配送する場合は、`agent-toolkit:reviewee-standards`の`SKILL.md`と
`agent-toolkit:review-standards`の`references/judgment-details.md`の絶対パスを計画担当への配送文へ含める。
一部しか解消していない指摘は、残余を同じラウンド内で修正してから再レビューへ送る（努力目標）。
計画の目的と合意済みの除外・保持を満たす最小限の修正を選ぶ。
採否と対応結果を要求表、変更履歴及び`atk review-table`の固定7列TSV（ラウンド、重大度、指摘箇所、指摘内容、対応要否、対応内容、対応不要理由）へ統合してから、plan mode中は調整主体が採用指摘を正規計画へ一括反映し、
plan mode外は計画担当が正規計画へ反映する。
採用行の反映と同じ修正回で、各採用指摘へ対応する`## 変更履歴`の行を追加する。
再レビューの送信前に、当該ラウンドの採用件数と追加した履歴行数が一致することを確認する。
スコープ、公開契約、ユーザー合意を変える修正は確認へ送る。

採否の確定前と反映後に、`## 概要`、`## 提示素材`、`## 実施内容`、任意の`### 合意済みの除外・保持`、
`## 完了条件`を現行計画全体へ照合する。`## 概要`は実施内容とファイル群別の変更説明と同じ内容を述べている状態を保つ。
前回ラウンドとの差分だけで完了を判定しない。
変更の方向または数値目標がある場合は計画記載の方法で累積結果を再測定する。
採用の累積が逆行して合意変更となる場合は追加採用を止め、確認へ送る。
照合結果は計画とGitから毎回再計算し、別の永続状態を設けない。

採用指摘の反映後、計画担当は各修正差分を対象に計画自己監査を1巡する。
各修正が根拠とした正本の該当箇所、変更前の条文、`## 変更履歴`と本文の一致を照合し、
計画目的と合意済みの除外・保持を維持していることを確認する。
採用指摘の修正が新しい機構、状態、工程、実行主体を追加した場合は、追加分へ初版の該当する完成条件をすべて適用し、
ライフサイクルの粒度、ファイル群別の変更説明、完了条件、検査項目、主体別の入力と知識境界を含む未確定を解消してから
再レビューへ送る。
修正が計画内の反復要素（事例、表の行、素材、検査項目などの同型の並び）へ一律に適用される必須項目、書式又は契約を
変更した場合は、全要素へ当該契約を適用したことを照合してから再レビューへ送る。
採用指摘の修正が共有データ表現・入力正規化・状態・実行時期のいずれかをまたぐ接続を変更した場合は、
全生産者、全消費者、公開入口を対象リポジトリの実装と既存テストへの識別子検索で再列挙し、結果を現行計画へ反映する。
再列挙に用いた識別子と検索コマンドを計画へ記録する。
各実行時点で利用できる情報、維持対象の既存成功経路と対応テストも同じ再列挙へ含める。
再列挙の結果を同じ修正回で`## 変更履歴`、ファイル群別の変更説明及び`## 完了条件`へ整合させてから再レビューへ送る。
単純な文面変更と局所修正は本再列挙の対象外とする。

用語・数値・コマンド名・判定手段を是正した反映では、是正前の表記を`grep -n`で正規計画全体へ検索し、残存が0件または`## 提示素材`と`## 変更履歴`の引用だけであることを確認してから計画構造検査へ進む。検索した表記と一致件数を反映報告へ含める。

反映後は現在の書込主体が計画構造検査を再実行する。レビュー担当の起動前に、調整主体が前ラウンドの
`atk review-table validate <レビュー表>`を実行し、表を全文読取して全件応答済みを検証する。初回strict検証の前には
`atk review-table init <レビュー表>`を実行する。レビュー担当とレビューイーはラウンド開始時に
`atk review-table validate --allow-unanswered <レビュー表>`と自身の表の全文読取を実行して構造を検証する。
レビュー担当が終端した後、調整主体が表を読み、ラウンドの帰属を維持したまま指摘と対応結果を統合する。
レビューイーの応答後は次ラウンド起動前のstrict検証へ戻り、未応答又は重複行を残さない。
調整主体がある場合は調整主体が同じレビュー担当へ前掲の最小入力で再レビューを指示し、調整主体が無い場合は計画担当が`agent-toolkit:delegation`に従って指示する。
計画担当は調整主体が担当する再レビューの実施及びその結果を主張しない。
実識別子は`runtime-routing.md`の実効3値と担当・タスクの継続条件に従う。
同じ担当へ同じタスクの未完了作業、指摘への対応又は再レビューを返し、継続直前の実効3値が一致する場合だけ同一threadを継続する。
Claudeは追加指示を`SendMessage`で返す。Codexは`codex_send_message(session_id, prompt)`を使う。
先行turnを`codex_result`で回収した後は`codex_start_reply`で接続する。
条件不一致時は検収済み状態を渡して解決後のengineで新規起動する。

レビュー担当が再設計・簡素化・撤去を求めた箇所へ小修正で応じない。
初回と第2回での収束を目標とし、前記の`needs_escalation`による確定経路を除きレビュー回数に上限を設けない。
未解決の実在欠陥がある限り、修正と累積再レビューを同じ条件で反復する。
ユーザー判断または対象外の変更が必要な場合は、指摘、根拠、必要な判断を`needs_escalation`として返す。
指摘修正後に残る変更が全て軽微である場合は、再レビューせず収束させてよい。
軽微かどうかは修正担当である計画担当が修正完了後に実際の変更影響から判断し、
「その修正は再レビューを要するほど計画を変えたか」という問いだけを判定基準とする。
計画の実装単位の新設・分割、依存又は順序の変更、`## 実施内容`の行の追加・削除、公開インターフェース、
完了条件又は設計の追加・削除は軽微でない変更の例である。
誤記、用語の統一、参照の訂正及び意味を変えない説明の明確化は軽微な変更の例である。
例示を機械的な除外一覧として用いず、重大度ラベルと指摘件数も判定入力にしない。
判断に確信が持てない場合と、1件でも軽微でない変更がある場合は既存の累積再レビューへ進む。
再レビューを省略した修正と理由はレビュー表と`## 進捗ログ`へ記録する。
本経路は未解決の実在欠陥を残すために用いず、実装内容へ影響しない文書整合の修正1件ごとに全レビューが1周して
収束コストが指摘の実害と比例しなくなる事象を防ぐため、全件修正後の再レビューだけを省く努力目標とする。

レビュー報告が同一箇所、同一の違反契約、同一の新設・変更機構、同一の目的条項又は同一の混入構造のいずれかへの指摘であり、
2ラウンド連続して成立した場合は、全体のレビュー回数によらず発火する。
個別の文面修正を止め、再設計・簡素化・撤去を同じラウンド内で比較する。
同一の違反契約では、当該契約の全出現箇所を走査する。同一の新設・変更機構では、当該機構と全接続先契約面を走査する。
同一の目的条項では当該目的が及ぶ全記述を、同一の混入構造では同じ混入・動機・見逃し構造が及ぶ全箇所を走査する。
契約名、機構名、目的条項、混入構造及び範囲を記録する。比較結果と不採用理由も記録する。

レビュー担当が当該契約の全走査を1ラウンドで完了できない場合は、未走査範囲を明示して返す。
計画担当は未走査範囲を受け取った時点で、次ラウンドを起動する前に当該契約が及ぶ計画本文の全行を実測照合する。
照合の対象は、各行が前提とする実体（対象ファイルの現行文面、実装挙動、既存テスト）とする。
読解量が1担当を超える場合は、範囲を重複なく分割して読み取り専用の担当へ並行させてよい。
各担当には、担当範囲の全行を打ち切らずに照合すること、及び不一致を全件、計画の記述と実測値の双方で返すことを求める。
判明した不一致を一括是正し、計画構造検査を再実行してから次ラウンドを起動する。

2ラウンド連続後の再設計・簡素化・撤去の比較において、どの案も欠陥を解消すると立証できない場合は、
3ラウンド目を実施せず`needs_escalation`で呼び出し元へ返す。
制約へ適合する案が無い場合と、直前の修正が新しい欠陥を導入して次ラウンドでの合格に自信を持てない場合も同じ扱いとする。
この判断は計画担当が観測事実から裁量で行い、機械判定しない。
前記の早期返却に該当せず、再設計と全行照合を経てもなお同じ単位へ指摘が成立して連続3ラウンドへ達した場合も、
計画担当が当該単位の処置を自ら確定しない。
いずれの返却も対象の単位、各ラウンドの指摘と期待値、比較した案と不採用理由及び確定できない理由を含める。
いったん採用した変更の撤去と同一内容の復元をともに観測した場合も同じ扱いとする。
呼び出し元が当該単位の処置を確定して指示した場合は、当該指示のとおり反映し、当該単位へ追加のレビューラウンドを実施しない
（厳守規定。確定経路が無いと、同一単位の文面が往復し続けて収束しない）。

計画が指定した方式の枠内では契約を満たせないと判明した場合は、当該方式を保ったまま条件を追加せず、
計画の該当節が不成立であることを根拠付きで呼び出し元へ差し戻す。

各レビューラウンドの反映後、計画担当は正規計画の`## 進捗ログ`へ1ラウンドにつき1行を追記する。
結果・特記事項にはラウンド番号と、指摘を「起草時に判断可能」「初回レビューの見逃し」「直前修正による混入」へ
分類した内訳を記録する。同一箇所、同一契約、同一機構及び同一目的条項に対する連続指摘のラウンド数と対象も記録する。
同一混入構造に対する連続指摘も同じ記録対象とする。反復規定の適用判定結果と不適用時の根拠を記録し、
軽微判定による再レビュー省略の有無と理由も残す。

計画構造検査がエラー0で成功し、重大な指摘を解消し、未承認の変更が無い場合だけ計画レビューを完了する。
レビュー表の回収は、計画レビューが収束した後に調整主体（無い場合は計画担当）が行う。

同一箇所・同一契約について、いったん採用して反映した変更の撤去と、その後の同一内容の復元をともに観測した場合は、
当該箇所を収束不能と判定する。
撤回だけ、又は訂正だけで収束した箇所は本判定の対象としない。
収束不能と判定した単位は、計画の`## 実施内容`、`## 完了条件`及び関連する節から分離し、
`## 変更履歴`へ起点`方針転換`として分離の事実と、採用した撤去指摘のIDおよび復元指摘のIDを1行記録する。
残りの項目でレビューを収束させ、分離した単位は`needs_escalation`として調整主体へ返す。
判定と分離は計画担当が行い、調整主体がある場合は分離の事実を検収する。
