# 計画レビュー

計画の起草担当が機械検査、指摘の検収、計画修正を所有し、独立したレビュー担当へ成立性の評価だけを委譲する。

## 起草担当の機械検査

初版の起草後、起草担当自身が正規計画へ`skills/plan-mode/scripts/check_plan_file.py`を実行する。
違反は正規計画で修正し、全検査を再実行する。終了コード、警告、修正概要を保持する。
機械検査を別の書込担当へ委譲せず、正規計画の書込主体を起草担当1名に保つ。

## 独立したレビュー担当

機械検査の成功後、起草担当は独立したレビュー担当を起動する前に、`plan-file-standards.md`の全項と
計画本文を照合する意味自己監査を1巡する。
自己監査は品質形成であり、独立したレビュー担当の検証責務を置き換えない。

自己監査を完了後、起草担当を起動した調整主体がある場合は調整主体が独立したレビュー担当を起動する。
調整主体が無い場合は起草担当が`agent-toolkit:delegation`に従って起動する。
起動主体はレビュー担当の新規起動又はCodex経路の継続接続の直前に`atk config get plan_review_model`を実行し、
`agent-toolkit:delegation`の`references/runtime-routing.md`「工程別モデル設定」に従って経路を解決する。
起動文は受信者への命令を先頭に置き、次の絶対パスと今回のレビュー種別を全レビュー共通の入力として渡す。
初回・再レビュー固有の入力は、後続の規定に従って追加する。

- `plan-review-task.md`
- 正規計画
- 対象リポジトリ
- プロジェクト規範
- `plan-file-standards.md`と`agent-toolkit:review-standards`

初回レビューでは、計画全文に加えて元のユーザー指示、
復元・巻き戻し型の変更では項目別の維持・修正・撤去の判定と根拠を照合基準として明示的に渡す。
フィードバック原文経路では、対象のフィードバックファイル名、対象リポジトリ及び計画内の`原文正本ID`対応を渡す。
レビュー担当は各ファイル名について`atk mq show <filename> --target-repo=<repo> --skip-pull`を1回実行する。
この経路ではフィードバック本文と専用ファイルを起動文へ複製しない。
直接起動経路では、`## 提示素材`の逐語原文を渡す現行契約を維持する。
元のユーザー指示は経路と独立した入力とする。
人間由来の場合は出所と引用範囲を付けた逐語文を渡し、常駐自動起動の場合は非該当と起動事実を渡す。
直接起動経路では、直接受領した実際の利用者メッセージを渡す。
`AskUserQuestion`由来の合意は、出所を回答の逐語として表示し、質問本文をエージェントが作成した文として区別する。
要約だけを一次入力にせず、レビュー担当が原文から目的と適用範囲を再確認できる状態にする。

再レビューでは既知でない情報だけを渡す。
同一threadでは「再レビューを実施せよ」に相当する指示を送る。
初回レビュー起動後に人間由来の入力（`AskUserQuestion`の回答、TBDの回答、利用者の追加指示）を受領した場合は、逐語文、出所、引用範囲、利用者合意又は参考素材の別を同一threadへ追送してから再レビューを指示し、追送しない限り当該発話を根拠とする実施又は除外を計画へ書かない。
解決内容、変更履歴ID、再監査条項、出力形式、読み取り専用契約を起動文へ再記述しない。
新規起動では経路に応じた初回と同じ入力パス集合と検収済み状態を渡す。
差分要約と追加範囲は計画本文を正本とし、起動文へ再記述しない。

レビュー担当は正規計画と対象リポジトリを読み取り専用とする。
レビュー担当を起動した調整主体は起動前後のGit状態を比較し、レビュー担当の書き込みを検出した場合は結果を採用しない。
調整主体が無い場合は起草担当が比較する。

## 指摘の検収と修正

起草担当は`agent-toolkit:reviewee-standards`を起動し、
`agent-toolkit:review-standards`配下の`references/judgment-details.md`を全文読んで指摘の採否と修正を確定する。
一部しか解消していない指摘は、残余を同じラウンド内で修正してから再レビューへ送る（努力目標）。
計画の目的と合意済みの除外・保持を満たす最小限の修正を選ぶ。
採否と対応結果を6列表へ統合してから、採用指摘を正規計画へ一括反映する。
採用行の反映と同じ修正回で、各採用指摘へ対応する`## 変更履歴`の行を追加する。
再レビューの送信前に、当該ラウンドの採用件数と追加した履歴行数が一致することを確認する。
スコープ、公開契約、ユーザー合意を変える修正はモード別の確認へ送る。

採否の確定前と反映後に、`## 概要`、`## 提示素材`、`## 実施内容`、任意の`### 合意済みの除外・保持`、
`## 完了条件`を現行計画全体へ照合する。`## 概要`は実施内容とファイル群別の変更説明と同じ内容を述べている状態を保つ。
前回ラウンドとの差分だけで完了を判定しない。
変更の方向または数値目標がある場合は計画記載の方法で累積結果を再測定する。
採用の累積が逆行して合意変更となる場合は追加採用を止め、モード別の確認へ送る。
照合結果は計画とGitから毎回再計算し、別の永続状態を設けない。

採用指摘の反映後、起草担当は各修正差分を対象に意味自己監査を1巡する。
各修正が根拠とした正本の該当箇所、変更前の条文、`## 変更履歴`と本文の一致を照合し、
計画目的と合意済みの除外・保持を維持していることを確認する。
採用指摘の修正が新しい機構、状態、工程、実行主体を追加した場合は、追加分へ初版の該当する完成条件をすべて適用し、
ライフサイクルの粒度、ファイル群別の変更説明、完了条件、検査項目、主体別の入力と知識境界を含む未確定を解消してから
再レビューへ送る。
修正が計画内の反復要素（事例、表の行、素材、検査項目などの同型の並び）へ一律に適用される必須項目、書式又は契約を
変更した場合は、全要素へ当該契約を適用したことを照合してから再レビューへ送る。
採用指摘の修正が共有データ表現・入力正規化・状態・実行時期のいずれかをまたぐ接続を変更した場合は、
全生産者、全消費者、公開入口を現行計画から再列挙する。
各実行時点で利用できる情報、維持対象の既存成功経路と対応テストも同じ再列挙へ含める。
再列挙の結果を同じ修正回で`## 変更履歴`、ファイル群別の変更説明及び`## 完了条件`へ整合させてから再レビューへ送る。
単純な文面変更と局所修正は本再列挙の対象外とする。

反映後は起草担当が機械検査を再実行する。
調整主体がある場合は調整主体が同じ論理レビュー系統へ前掲の最小入力で再レビューを指示し、調整主体が無い場合は起草担当が`agent-toolkit:delegation`に従って指示する。
起草担当は調整主体が担当する再レビューの実施及びその結果を主張しない。
実識別子は実行系別のライフサイクルに従い、Codexは同一thread、Claudeは検収済み状態を渡した新規起動とする。

レビュー担当が再設計・簡素化・撤去を求めた箇所へ小修正で応じない。
初回と第2回での収束を目標とするが、レビュー回数に上限を設けない。
未解決の実在欠陥がある限り、修正と累積再レビューを同じ条件で反復する。
ユーザー判断または対象外の変更が必要な場合は、指摘、根拠、必要な判断を`needs_escalation`として返す。

機械検査がエラー0で成功し、重大・中程度の指摘を解消し、未承認の変更が無い場合だけ計画レビューを完了する。

第3回のレビューを超えて重大又は中程度の指摘が継続する場合、起草担当は個別の文面修正の反復を止め、
指摘が反復している箇所の再設計・簡素化・撤去を同じラウンド内で比較して現行計画を是正する。
現行計画から独立した恒久的な工程・規範の欠陥は、是正の完了後に`agent-toolkit:add-feedback`で
次回セッションへ登録する。
