# 計画レビュー

計画の計画担当が計画構造検査、指摘の検収、計画修正を所有し、計画レビュー担当へ成立性の評価だけを委譲する。

## 計画担当の計画構造検査

初版の起草後、計画担当自身が現行plugin rootの`skills/plan-mode/scripts/check_plan_file.py`を解決し、
実在を確認した絶対パスで実行する。解決した構造検査スクリプトの絶対パスは、初回・再レビューの入力へ含める。
計画構造検査は、検索、レビュー表検証及びその他の検査と同じシェル呼び出しへ連結せず、独立したコマンドとして実行する。
計画構造検査が直接返した終了コードと警告を検収し、終了コード0の場合だけ計画自己監査と計画レビューへ進む。
新規計画は`<計画名>.md`（計画ファイル（メイン））と`<計画名>.detail.md`（計画ファイル（詳細））の両方を書き込み、
`check_plan_file.py`へは計画ファイル（メイン）の絶対パスだけを渡す。
同スクリプトは、対応する計画ファイル（詳細）をstemから導出し、両側の節構成を検査する。
通常モードでは計画担当が正規計画へ書き込み、正規計画（計画ファイル（メイン）・計画ファイル（詳細）の両ファイル）を検査する。plan modeでは計画担当が指定された
サンドボックスへ書き込み、同じサンドボックスを検査する。調整主体はサンドボックスの検収後に正規計画へ反映し、
正規計画を検査する。plan modeを終了した後の修正は計画担当が正規計画へ書き込む。各パスの書込主体は常に1名とする。
違反は現在の書込主体が対象ファイルで修正し、全検査を再実行する。終了コード、警告、修正概要を保持する。

計画メタ情報のベースコミットは計画作成時点の参照値として表示するだけであり、計画構造検査の成功条件、レビューの開始条件又は対象範囲の決定条件にしない。
レビュー時点のHEAD、差分及び対象範囲を確認する必要がある場合は、当該レビューで必要な公開契約・実装対象へ直接照合する。

## 計画レビュー担当

計画構造検査の成功後、計画担当は計画レビュー担当を起動する前に、`agent-toolkit:plan-mode`の計画ファイル基準の全項と
計画本文を照合する計画自己監査を1巡する。
自己監査は品質形成であり、計画レビュー担当の検証責務を置き換えない。

自己監査を完了後、計画担当を起動した調整主体がある場合は調整主体が計画レビュー担当を起動する。
調整主体が無い場合は計画担当が`agent-toolkit:delegation`に従って起動する。
調整主体はレビュー表の絶対パスを確定する。
レビュー表の共通ライフサイクル、`track`、モデル解決及び収束判定は`agent-toolkit:plan-mode`のレビュー継続契約を適用する。
計画レビューの`track`は`plan-review`とし、計画ごとに1つの表を全ラウンドで使う。
起動主体はレビュー担当の新規起動又は継続接続の直前に`atk config get plan_review_model`を実行し、
`agent-toolkit:delegation`の工程別モデル設定に従って経路を解決する。
起動文は受信者への命令を先頭に置き、次の絶対パスと今回のレビュー種別を全レビュー共通の入力として渡す。
初回・再レビュー固有の入力は、後続の規定に従って追加する。

- `agent-toolkit:plan-mode`の計画レビュー担当契約
- 正規計画（新書式は計画ファイル（メイン）・計画ファイル（詳細）の絶対パスの組、旧形式は単一パス）
- 対象リポジトリ
- プロジェクト規範
- `agent-toolkit:plan-mode`の計画ファイル基準と`agent-toolkit:review-standards`のSKILL.md
- 計画担当が解決した構造検査スクリプト`check_plan_file.py`の絶対パス
- レビュー指摘管理表の絶対パス

レビュー表の初回・途中の構造検証は`atk review-table validate --allow-unanswered <レビュー表>`を用い、
全行への応答後のstrict検証は`atk review-table validate <レビュー表>`を用いる。

初回レビューでは、計画全文に加えて元のユーザー指示、
復元・巻き戻し型の変更では項目別の維持・修正・撤去の判定と根拠を照合基準として明示的に渡す。
新規計画メインの`## エージェント判断`と`## 変更履歴（計画時）`は、計画担当が確定した判断・確認回答の入力としてそのまま渡す。
初回レビューの完了報告を受領した調整主体は、計画の独立要件が被覆結果へ過不足なく対応することを検収する。
各要件の全観点が`確認済み`又は理由付きの`非該当`でない場合は、計画レビューの完了を受理しない。

欠落した要件又は観点と同じレビュー表を渡し、同じレビュー担当へ未走査範囲の走査を指示する。
フィードバック原文経路では、フィードバック由来行の正本ファイル名、対象リポジトリ、計画ファイル（メイン）・計画ファイル（詳細）の計画と直接受領したユーザーメッセージを渡す。
フィードバック本文は対象リポジトリごとに一括取得し、各実施内容行の採否、範囲、理由へ照合する。
本セッションのユーザー発言は、変更履歴の逐語コードブロックと同じ原文をレビュー担当へ渡す。
終了コード0で要求した全項目が出力された場合だけ、正本ファイル名と実施内容行を照合する。
終了コード2では標準出力の部分結果を使わず、初回レビューを開始しないで入力不足として起動主体へ返す。
旧形式では`原文正本ID`のフィードバックファイル名を同じ条件で取得する。該当素材が無い場合は取得を省略する。
この経路ではフィードバック本文と専用ファイルを起動文へ複製しない。
直接起動経路では、正本ファイル名と出所・引用範囲を渡す。
キューにない素材の逐語本文・回答全文は計画外の明示入力として、初回レビュー担当へ渡す。
元のユーザー指示は経路と独立した入力とする。
人間由来の場合は種別、出所及び引用範囲を付けた入力を渡し、常駐自動起動の場合は非該当と起動事実を渡す。
直接起動経路では、直接受領した実際のユーザーメッセージを渡す。
`AskUserQuestion`由来の合意は、投入元を`AskUserQuestion`、引用範囲を`回答全文`として示し、質問本文をエージェントが作成した文として区別する。
出所と引用範囲を失った要約だけを一次入力にせず、レビュー担当が正本ファイル名から目的と適用範囲を再確認できる状態にする。

### 一括取得の管理対象一時領域

同一対象リポジトリの複数ファイル名を同一工程で取得する時点で、`agent-toolkit:add-feedback`の一括取得契約を読み、同契約の手順を完了させる。
終了コード2では標準出力の部分結果を使わず、初回レビューを開始しないで入力不足として起動主体へ返す。

### 計画再レビューの前回版

計画再レビューではGitの完全OIDを利用できないため、調整主体は各ラウンドの指摘受領後かつ計画担当への修正指示前に、レビュー済み計画を呼び出し元が当該計画専用に作成したmanaged temp領域へ前回版として保存する。
対象集合は、計画メインと同じstemの`<stem>.detail.md`の実在で形式を判定し、詳細ファイルが存在しない旧形式では作業種別にかかわらず計画メイン1ファイルとする。
詳細ファイルが存在する新書式では計画メインの固定メタ情報`作業種別`から分岐し、通常変更では計画メイン・詳細の2ファイル、バグ対応では計画メイン・詳細・バグ調査の3ファイルとする。
計画担当の修正後は、前回版と現行版から取得した機械差分、変更した見出し、採用指摘との対応及び直接影響範囲を再レビュー担当へ渡す。
新規担当への切替時も同じ絶対パスと差分を渡す。

前回版はラウンドごとに上書きせず、ラウンド番号を含む一意な名前で保存する。
調整主体は保存直後に形式と作業種別に対応するファイル数、各ファイルのバイト数及びハッシュを検収し、再レビュー起動直前に再照合する。
旧形式で詳細又はバグ調査を別ファイルとして対象に含める、形式又は`作業種別`が不明、新書式の通常変更でバグ調査を対象に含める、又は新書式のバグ対応でバグ調査が欠ける場合は保存へ進まず`needs_escalation`で不整合と再開条件を返す。
保存した前回版、機械差分、検収値のいずれかが欠けた場合は累積全体の再監査へ戻らず、`needs_escalation`で欠落項目と再開条件を返す。

呼び出し元は計画レビュー開始前に、1計画につき1回`atk managed-temp create --prefix plan-review-baseline`を実行する。
返された絶対パスは当該計画専用として計画ファイル（メイン）の絶対パスと対応付け、別の計画と共有せず、当該計画の全ラウンドだけで保持して調整主体へ渡す。
調整主体はレビュー済みの各ファイルについて、当該計画専用managed temp領域内の保存先が存在しないことを`test ! -e <保存先>`で確認してから、次の形で保存する。

```sh
cp -- <計画ファイルの絶対パス> <当該計画専用managed temp絶対パス>/round-<ラウンド番号>.<main|detail|bugs>.previous
```

保存直後と再レビュー直前に、当該計画専用managed temp領域の前回版だけを対象とし、旧形式では対象1ファイル、新書式の通常変更では対象2ファイル、新書式のバグ対応では対象3ファイルを同一コマンドへ列挙して`wc -c`と`sha256sum`を実行する。
再レビューの機械差分は、当該計画専用managed temp領域に保存して検収した前回版と、対象集合の各現行計画ファイルについて次の形で取得する。

```sh
diff -u --label previous-<main|detail|bugs> --label current-<main|detail|bugs> <当該計画専用managed temp領域内の前回版絶対パス> <現行計画ファイルの絶対パス>
```

`diff`の終了コード0は変更なし、1は差分あり、2は比較失敗として扱う。
終了コード1の標準出力だけを差分入力としてレビュー担当へ渡し、終了コード0のファイルは変更対象外として列挙する。
終了コード2は`needs_escalation`へ返す。
差分出力は対象ファイルごとに個別取得し、複数ファイルを1回の呼び出しへまとめない。

調整主体はレビュー収束時に、呼び出し元が回収前照合へ使用する`cleanup_evidence`を次の構造で返す。

```yaml
cleanup_evidence:
  plan: <計画ファイル（メイン）の絶対パス>
  managed_temp: <当該計画専用managed temp領域の絶対パス>
  rereview_count: <再レビュー回数>
  baseline_not_saved: <true | false>
  rounds:
    - round: <再レビューのラウンド番号>
      target_plan: <対象計画ファイルの絶対パス>
      previous_files:
        - path: <前回版の絶対パス>
          bytes_after_save: <保存直後のバイト数>
          sha256_after_save: <保存直後のSHA-256>
          bytes_before_rereview: <再レビュー直前のバイト数>
          sha256_before_rereview: <再レビュー直前のSHA-256>
          mechanical_diff:
            current_path: <対応する現行計画ファイルの絶対パス>
            exit_code: <diffの終了コード0又は1>
            verified: true
```

調整主体は`plan`と`managed_temp`へ受領値をそのまま返す。再レビュー0回では`rereview_count: 0`、
`baseline_not_saved: true`、`rounds: []`とする。再レビュー1回以上では`baseline_not_saved: false`とし、
`rounds`の要素数を`rereview_count`と一致させる。各`rounds`要素は1回の再レビューへ対応し、
対象集合の全前回版を`previous_files`へ含める。`verified`は、前回版と現行計画ファイル、ラウンド及び
機械差分の終了コードを調整主体が対応付けて検収した場合だけ`true`とする。

当該計画のレビュー収束後、呼び出し元は受信した`cleanup_evidence`と作成時から保持する値及び専用領域の現状を、
再レビュー回数に応じて次のように回収前照合する。

- 再レビュー0回では、`plan`と`managed_temp`が保持値に一致し、`baseline_not_saved: true`かつ`rounds: []`であり、当該計画専用managed temp領域に`round-*.previous`の前回版が存在しないことを確認する
- 再レビュー1回以上では、`baseline_not_saved: false`であり、`rereview_count`と`rounds`の要素数が一致することを確認する。各再レビューについて、全`previous_files`のパス、保存直後と再レビュー直前のバイト数・SHA-256及び`mechanical_diff`が、当該計画、現存する前回版と該当ラウンドへ一致し、`verified: true`であることを照合する

該当する回収前照合の成功後に限り、`atk managed-temp cleanup --path <当該計画専用managed temp絶対パス>`を単独で実行し、その領域だけを回収する。
複数計画を扱う場合も各計画の再レビュー回数を独立して照合し、各計画の領域を独立して回収し、別の計画の開始又は収束を回収条件にしない。別の計画の再レビュー回数も回収条件にしない。`cleanup_evidence`の欠落、必須項目の欠落、不一致、中断、失敗時は当該計画専用managed temp領域を保持し、レビュー収束を成功として扱わない。

再レビューでは、既知でない情報に加えて、今回のラウンド番号と今回の表の絶対パスを必須差分入力として渡す。
初回に受領した構造検査スクリプト`check_plan_file.py`の絶対パスも、必須差分入力として保持する。
継続接続では、前項の必須差分入力を添えて「再レビューを実施せよ」に相当する指示を送る。
初回レビュー起動後に人間由来の入力（`AskUserQuestion`の回答、TBDの回答、ユーザーの追加指示）を受領した場合は、
正本ファイル名、種別、逐語文、出所及び引用範囲をレビュー担当へ渡す。
ユーザー合意か参考素材かの区分も渡してから再レビューを指示する。
同一threadの継続では当該情報を追送し、新規起動では初回と同じ入力パス集合と検収済み状態を渡す。
再レビューへの追送には、キューにない素材の逐語本文・回答全文も計画外の明示入力として含め、初回から共有した入力と同じ値を保持する。
当該情報を渡さない限り、その発話を根拠とする実施又は除外を計画へ書かない。
解決内容、変更履歴の記録方針、再監査条項、出力形式、読み取り専用契約を起動文へ再記述しない。
新規起動では経路に応じた初回と同じ入力パス集合と検収済み状態を渡す。
差分要約と追加範囲は計画本文を正本とし、起動文へ再記述しない。

レビュー担当は正規計画と対象リポジトリを読み取り専用とする。
レビュー担当を起動した調整主体は起動前後のGit状態を比較し、レビュー担当の書き込みを検出した場合は結果を採用しない。
調整主体が無い場合は計画担当が比較する。

## 指摘の検収と修正

計画担当は`agent-toolkit:reviewee-standards`の`SKILL.md`を適用し、
`agent-toolkit:review-standards`の判断詳細契約を全文読んで指摘の採否と修正を確定する。
調整主体が指摘を配送する場合は、`agent-toolkit:reviewee-standards`の`SKILL.md`と
`agent-toolkit:review-standards`の判断詳細契約の絶対パスを計画担当への配送文へ含める。
一部しか解消していない指摘は、残余を同じラウンド内で修正してから再レビューへ送る（努力目標）。
計画の目的と実施内容に記録された採否・除外・保持を満たす最小限の修正を選ぶ。
採否と対応結果を実施内容、イベント単位の変更履歴及び`atk review-table`のレビュー表へ統合してから、plan mode中は調整主体が採用指摘を正規計画へ一括反映し、
plan mode外は計画担当が正規計画へ反映する。
採用行の反映と同じ修正回で、当該ラウンドのレビュー指摘をラウンド単位で要約した`## 変更履歴`の行を1行追加する。
再レビューの送信前に、レビュー指摘管理表をstrict検証し、当該ラウンドの指摘原文・個別採否・対応内容が表へ記録され、変更履歴にはラウンド単位の要約行があることを確認する。
スコープ、公開契約、ユーザー合意を変える修正は確認へ送る。

採否の確定前と反映後に、`## 概要`、`## 提示素材`、`## 実施内容`、`## 変更履歴`、計画ファイル（詳細）`### 恒久化`、`## 実装資料`及び`## 完了条件`を現行計画全体へ照合する。`## 概要`は実施内容とファイル群別の変更説明と同じ内容を述べている状態を保つ。
前回ラウンドとの差分だけで完了を判定しない。
変更の方向または数値目標がある場合は計画記載の方法で累積結果を再測定する。
採用の累積が逆行して合意変更となる場合は追加採用を止め、確認へ送る。
照合結果は計画とGitから毎回再計算し、別の永続状態を設けない。

採用指摘の反映後、計画担当は各修正差分を対象に計画自己監査を1巡する。
各修正が根拠とした正本の該当箇所、変更前の条文、`## 変更履歴`と本文の一致を照合し、
計画目的と実施内容に記録された採否・除外・保持を維持していることを確認する。
計画へ新規に追加又は変更した行番号、条文引用及び編集指示は、対象行を実読して実体と照合する。
探索結果、レビュー報告の要約及び自前の要約を照合先に代用しない（厳守規定。編集指示と対象行の実体が一致しないと、同型の指摘が連続ラウンドで成立して収束が延びる）。
採用指摘の修正が新しい機構、状態、工程、実行主体を追加した場合は、追加分へ初版の該当する完成条件をすべて適用し、
ライフサイクルの粒度、ファイル群別の変更説明、完了条件、検査項目、主体別の入力と知識境界を含む未確定を解消してから
再レビューへ送る。
修正が計画内の反復要素（事例、表の行、素材、検査項目などの同型の並び）へ一律に適用される必須項目・書式・契約を
変更した場合は、全要素へ当該契約を適用したことを照合してから再レビューへ送る。
採用指摘の修正が共有データ表現・入力正規化・状態・実行時期のいずれかをまたぐ接続を変更した場合は、
元の目的、公開契約又は再現可能な通常運用で実害のある欠陥への影響を確認できる接続面だけを対象リポジトリの実装と既存テストへ照合し、結果を現行計画へ反映する。
照合に用いた識別子と検索コマンドを計画へ記録する。
各実行時点で利用できる情報、維持対象の既存成功経路と対応テストも同じ再列挙へ含める。
再列挙の結果を同じ修正回で`## 変更履歴`、ファイル群別の変更説明及び`## 完了条件`へ整合させてから再レビューへ送る。
単純な文面変更と局所修正は本再列挙の対象外とする。

用語・数値・コマンド名・判定手段を是正した反映では、是正前の表記を`grep -n`で正規計画全体へ検索し、残存が0件または`## 提示素材`と`## 変更履歴`の引用だけであることを確認してから計画構造検査へ進む。検索した表記と一致件数を反映報告へ含める。

反映後は現在の書込主体が計画構造検査を再実行する。レビュー表の初期化、ラウンドごとの構造検証、応答検収及びstrict検証は
`agent-toolkit:plan-mode`のレビュー継続契約に従う。計画レビューでは`plan-review`の帰属を保ったまま、計画担当が採否と対応結果を検収する。
調整主体がある場合は調整主体が同じレビュー担当へ前掲の最小入力で再レビューを指示し、調整主体が無い場合は計画担当が`agent-toolkit:delegation`に従って指示する。
計画担当は調整主体が担当する再レビューの実施とその結果を主張しない。
計画修正後の再レビュー省略可否は`agent-toolkit:plan-mode`のレビュー継続契約にある収束判定に従う。

レビュー担当が当初のユーザー目的、現行の公開契約又は再現可能な通常運用で実害のある欠陥へ影響する範囲の走査を1ラウンドで完了できない場合は、未走査範囲を明示して返す。
計画担当は未走査範囲を受け取った時点で、次ラウンドを起動する前に当該目的・契約・欠陥が及ぶ計画本文の範囲を実測照合する。
同じ文字列、見出し、目的語、混在構造、接続関係だけの一致は、元の目的・公開契約・通常運用で実害のある欠陥への影響が確認できない限り走査範囲へ含めない。
照合の対象は、各行が前提とする実体（対象ファイルの現行文面、実装挙動、既存テスト）とする。
読解量が1担当を超える場合は、範囲を重複なく分割して読み取り専用の担当へ並行させてよい。
各担当には、担当範囲の全行を打ち切らずに照合すること、及び不一致を全件、計画の記述と実測値の双方で返すことを求める。
判明した不一致を一括是正し、計画構造検査を再実行してから次ラウンドを起動する。

計画が指定した方式の枠内では契約を満たせないと判明した場合は、当該方式を保ったまま条件を追加せず、
計画の該当節が不成立であることを根拠付きで呼び出し元へ差し戻す。

各レビューラウンドの反映後、計画担当は正規計画の`## 進捗ログ（実行時）`へ1ラウンドにつき1行を追記する。
結果・特記事項にはラウンド番号と、指摘を「起草時に判断可能」「初回レビューの見逃し」「直前修正による混入」へ
分類した内訳を記録する。同一箇所、同じ違反契約か変更機構が元の目的・公開契約・通常運用で実害のある欠陥へ影響する場合の連続指摘のラウンド数と対象も記録する。
文字列、見出し、目的語、混在構造、接続関係だけの一致は同じ記録対象にしない。反復規定の適用判定結果と不適用時の根拠を記録し、
軽微判定による再レビュー省略の有無と理由も残す。

計画構造検査がエラー0で成功し、全ての指摘を解消し、未承認の変更が無い場合だけ計画レビューを完了する。
レビュー表の回収は、計画レビューが収束した後に調整主体（無い場合は計画担当）が行う。

同一箇所・同一契約について、いったん採用して反映した変更の撤去と、その後の同一内容の復元をともに観測した場合は、
当該箇所を収束不能と判定する。
撤回だけ、又は訂正だけで収束した箇所は本判定の対象としない。
収束不能と判定した単位は、計画の`## 実施内容`、`## 完了条件`及び関連する節から分離し、
`## 変更履歴`へ起点`方針転換`として分離の事実と、採用した撤去指摘のIDおよび復元指摘のIDを1行記録する。
残りの項目でレビューを収束させ、分離した単位は`needs_escalation`として調整主体へ返す。
判定と分離は計画担当が行い、調整主体がある場合は分離の事実を検収する。
