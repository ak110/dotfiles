# レビュー収束ループの調整

レビュー収束ループの調整主体だけが適用するループ運営の正本である。
レビュー担当の点検とレビューイーの採否・修正は各役割の正本へ委ね、本書へ記載しない。

## 役割と反復構造

調整主体は、初版又は実装差分の入力を確定し、レビュー表の存在確認・必要時の初期化を行い、各ラウンドの起動・応答・収束を調整する。
調整主体はレビュー担当の評価やレビューイーの採否を代行せず、正本の状態と各主体の完了を検収する。

1ラウンドは、表の構造検証、レビュー担当の起動、レビュー指摘の追加、レビューイーの全行応答、strict検証で構成する。
未解消の指摘は次ラウンドの行として同じ表へ追加し、過去ラウンドの行を変更しない。
計画レビューでは計画ごとの表を、実装レビューでは対象となる1つの`review.tsv`を全ラウンドで使用する。

## ラウンドと表のライフサイクル

調整主体は初回ラウンドの前にレビュー表の存在を確認する。未作成の場合だけ`atk review-table init <レビュー表>`を実行し、既存の場合は初期化せず表を保持する。その後、`atk review-table validate --allow-unanswered <レビュー表>`を実行する。
各ラウンドのレビュー担当起動前には前ラウンドをstrict検証し、レビュー担当へ今回の表の絶対パス、ラウンド番号、担当する`track`を渡す。
レビューイーへは同じ表の絶対パス、ラウンド番号、修正対象として確定した採用指摘の`track`集合を渡す。
調整主体は応答済みの表を再検収し、次ラウンドが必要な場合は同じ表を用いる。
全行が回答済みとなった後のstrict検証は`atk review-table validate <レビュー表>`を実行する。

実装レビューは単一のレビュー担当が計画照合と成果物評価を同じコンテキストで行い、`implementation-review`の単一`track`へ指摘を追加する。
実装レビュー担当へは同じ表の`implementation-review`行だけを渡し、他の`track`の行や出力を入力へ含めない。

## 共通契約の受理

レビュー担当の初回・再レビュー範囲と被覆証拠は、review-standardsの共通契約に従う。
調整主体は、未走査、根拠のない`確認済み`又は理由のない`非該当`を含む完了報告を受理せず、同じレビュー担当へ不足範囲を返す。
再レビューで初回から判断できた問題が見つかった場合も、初回レビューを未完了として不足範囲を同じレビュー担当へ返し、補完後に再レビューを続ける。

## モデル解決と起動

初版レビュー、再レビュー、レビュー修正の各起動又は継続の直前に、起動主体は対象工程の`atk config get`を実行する。
実効`engine`、`model`、`effort`は`agent-toolkit:delegation`の工程別モデル設定に従って解決し、同じ担当・同じタスク・実効3値一致の場合だけ同じthreadを継続する。
実効値が一致しないか、担当・タスクが異なる場合は、新しい識別子へ検収済み状態を渡して起動する。
各担当文書に固有の起動点、工程キー、入力、出力及び読み取り専用契約は各文書へ残し、本書は共通の解決手順だけを定める。

## 収束判定

調整主体は初回と第2回での収束を目標とするが、未解決の実在欠陥がある限り、前回修正と直接影響範囲を入力として修正と再レビューを反復する。
第2ラウンド以降を起動する前に、採用指摘ごとの修正要素を元のユーザー目的、公開契約、規範的制約、通常運用で実害のある欠陥のいずれかへ対応付ける。
過去ラウンドの指摘や修正方針そのものは対応先として扱わない。
対応先のない状態、API、識別子、互換経路、復旧経路及び検査は、次ラウンドの前に撤去する。
全ての指摘が解消し、表のstrict検証、計画か実装差分との照合、完了条件の検収が成立した時点で収束とする。
修正が実装単位、依存、順序、公開契約、完了条件、設計のいずれかを変更する場合は軽微と扱わず、変更箇所と直接影響範囲を再レビューへ渡す。
意味を変えない誤記・用語統一・参照訂正だけが残る場合は、修正理由を記録して再レビューを省略できる。

同一箇所か同じ違反契約・変更機構が、当初のユーザー目的、現行の公開契約、再現可能な通常運用で実害のある欠陥に対して2ラウンド連続して成立した場合は、個別修正を止め、当該目的・契約・欠陥へ実際に影響する範囲を走査したうえで再設計・簡素化・撤去を比較する。
同じ文字列、見出し、目的語、混在構造又は接続関係だけが共通する箇所は、元の目的・公開契約・再現可能な通常運用で実害のある欠陥への影響が確認できない限り横展開の対象にしない。
比較後も同じ単位への指摘が3ラウンド連続する場合、比較案で欠陥を解消できない場合、撤去と同一内容の復元をともに観測した場合は、対象単位、各ラウンドの根拠、比較案及び確定できない理由を添えて`needs_escalation`へ返す。
第3ラウンドへ進むか`needs_escalation`へ返す場合は、初版からの差分をレビュー開始前の目的と非目標へ再照合し、レビュー起因で追加した構成要素を列挙する。
元の目的、公開契約、規範的制約、再現可能な通常運用で実害のある欠陥のいずれにも対応しない要素は、既に実装済みであっても撤去してから返す。
