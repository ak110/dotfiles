# 計画ファイル作成基準

本書は計画ファイル（作業実体は`~/.claude/plans/*.md`）の成果物契約を定める。計画を起草するエージェントは全項を満たす計画を作成し、実行レビュー担当は点検の基準に使う。読込の時点は、起草者では`agent-toolkit:plan-mode`のSKILL.mdの読込表、実行レビュー担当では`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`の読込表が定める。
保存先と参照の書式は`plan-file-storage.md`、過去の契約へ戻す変更と保持・不変性・完全復元の契約は`plan-restoration-contracts.md`、構造の検証は`plan-structure-check.md`が定める。

計画ファイルは要求単位の欠落を防ぎ、実装と実行レビューの基準を示し、中断後の再開と作業記録に使う内部資料である。ユーザーの承認を前提としない。
実装担当が新たな要件判断なしに着手できる要件・外部仕様の水準で書く。詳しさは`agent-toolkit:writing-standards`の`references/writing.md`「読み手別の追加注意点」のエージェント向け文書の項に従う。一般的な作法は方向性と代表語に留め、対象、確定した要件・外部仕様、入力、期待結果、異常系、受入条件、固有の検証コマンドは具体的に書く。
実装手順、関数分割、内部の制御構造、改訂後の全文は実行工程が現行コードから確定する。実装水準の欠陥はテストで検出し、実行レビューは要件・外部仕様の達成と過剰設計の有無を判定する。

`ユーザー`と`エンドユーザー`は`agent-toolkit/rules/01-agent.md`「役割分担」に従う。本書のユーザーは計画の要求・指示・合意を与え確認に回答する人を指す。`消費主体`は成果物ごとの利用・検証の主体であり、人と人以外（呼び出し元のコード、委譲元、CIなど）を含む。

計画に属するファイルは次の呼称で指す。

| 呼称 | 実体 |
| --- | --- |
| 計画ファイル | `<計画名>.md` |
| 計画ファイル（バグ） | `<計画名>.bugs.md` |
| 実行レビュー指摘管理表 | `<計画名>.exec-review.tsv` |
| 計画バンドル | 計画ファイルと、同じstemの付属ファイル（計画ファイル（バグ）、実行レビュー指摘管理表など）の組 |

## 計画ファイルの構成

起草・更新の前に現行の作業契約を参照し、`share/work-contract.md`「工程境界での要求と成果の確認」に従う。計画の対象と保持対象が当初の目的・現行要求に合うかを確かめる。要求が変わった場合に同記録へ反映し、凍結後は既存のレビュー指摘管理表と`review_contract`の原本を保つ。

計画ファイルはH1の主題に続けて次のH2を固定順で置く。

1. `## 概要`
2. `## 実施内容`
3. `## 要件・外部仕様`
4. `## 恒久化・リファクタリング`
5. `## 変更履歴`
6. `## 検証`
7. `## 終端工程`
8. `## 進捗ログ`

自由なH3は`## 要件・外部仕様`と`## 変更履歴`の配下だけに置き、見出しはH3までとする。
同じ事実・数値・要約は計画全体で1箇所に置き、他は節名で参照する（努力目標。記述間の矛盾を防ぐため）。既存規範の適用範囲へ言及する場合は、条文の文書パスと節名を参照する。

関連WIはWIファイル名と1行要約だけを持ち、本文はWIが持つ。WIを入力とする計画は、WIが確定した目的、要件、原因分析、適用範囲、実現方式と成立の根拠を再調査・再記述せずWIファイル名で参照し、変更対象の分解、外部仕様、受入シナリオ、テスト、検証コマンド、恒久化・リファクタリング、終端工程を書く。
計画側で導出し直すのは、入力にWIが無い計画（`関連WI: なし`）、WIが該当する節を持たない場合、WIの記述と現物の食い違いを観測した場合に限る。食い違いは観測した現物と結論を`## 変更履歴`へ記録し、影響する事項だけを導出する。人間由来の要求の範囲を変える食い違いは`agent-toolkit:wi-standards`「由来と承認」の確認手順、原因分析の食い違いは「バグ調査」で扱う。類似見直しの母集団・QとC・Dの区別・処置の層・完了の判定が`agent-toolkit:bugfix`の`references/root-cause-analysis.md`の基準を満たさない場合も原因分析の食い違いに含める。

指摘、要件追加、方針転換は、実装着手までは既存記述と統合して現在の結論だけが残る形へ節を編集し、経緯を`## 変更履歴`へ記録する。ただし`由来`が`ユーザー指示`か`人間由来のWI`である行の`実施内容`欄は統合せず、`agent-toolkit:review-standards`の`references/reviewee.md`「安全な修正」に従って原文のまま保ち、是正案を別行にする。
実装着手後は計画ファイルを更新しない（以下「計画凍結」）。実装中に確定した要件変更と、記述の不整合に対して採った解釈はレビュー指摘管理表へ記録する。実行工程が計画を整備すると、それが実行レビューの指摘になって往復が生じるためである。例外は`## 進捗ログ`の追記とする。
凍結後の検証条件の訂正は「検証と終端工程」の訂正済み検証表へ反映する。

### 概要と計画メタ情報

`## 概要`直下へ全体像、目的、対象範囲の順で短い地の文を書き、内容が変わる場合は追記を重ねず節全体を書き直す。

直下のH3は`### 計画メタ情報`だけとし、行と順序は「初回起草の雛形」に従う。コロンはASCIIの`:`に半角空白1字を続け、`関連WI`と`作業種別`以外の値はバッククォートで囲む。計画ファイル（バグ）を作成する場合だけ、末尾へ``- 計画ファイル（バグ）: `~/.claude/plans/__PLAN_STEM__.bugs.md` ``を加える。

- `作業種別`は`バグ対応`か`通常変更`とする。バグ対応の要求単位を1件でも含めば`バグ対応`とし、計画ファイル（バグ）にはバグ対応の要求単位に対応するバグ単位だけを置く。`## 検証`の`変更範囲の検証`は全要求単位の変更対象を覆う
- `関連WI`には入力のAWIとUWIのWIファイル名を1件1行で置き、コロンに続けて1行要約を書く。入力が無ければ`- 関連WI: なし`とする
- `対象リポジトリ`は計画構造の自動チェックへ渡す`--work-dir`のGitルートと一致させる（`agent-toolkit:process-wi`のレーンでは専用worktreeの絶対パス）

### 実施内容

`## 実施内容`には`実施内容`、`由来`、`採否`、`根拠`の4列表を置き、要求単位の欠落と実施範囲を判断できる概念単位で書く。AWIは1ファイル1行を原則とし、実装手順やテスト項目は`## 要件・外部仕様`が扱う。WI間で対象・方針・変更内容が競合する場合は、競合する組と採った処置をその行の`実施内容`へ書く。実施しない除外・保持も行として記録する。

`由来`は`人間由来のWI`、`エージェント由来のWI`、`ユーザー指示`、`エージェント提案`のいずれかとする。

- WI由来の行は区分に半角空白1字と半角丸括弧で囲んだWIファイル名を続け（例: `エージェント由来のWI (20260831-000000-001.md)`）、`関連WI`と一致させる。2区分の選び方は`agent-toolkit:wi-standards`「由来と承認」に従う
- 計画構造の自動チェックがWI本文から読み取る明示由来は本文末尾の厳密なH2`## ユーザーコメント`とUWIの`## 回答`の2つであり、`source`を持つWIの行をこれ以外の明示由来で`人間由来のWI`とする場合は、ファイル名に続けて半角空白1字と`[対話由来]`を付ける。これ以外の明示由来（`## ユーザー指摘の逐語引用`などに出所と引用範囲を保持した対話回答、関連計画の実施内容に記録された由来）を使った行は、その出所と引用範囲を`## 変更履歴`へ記録する。`source`を持たないWIの行は注記を要さない
- `ユーザー指示`はユーザー自身の発話から、`エージェント提案`はエージェントが構成した指示から確定した実施内容に使う

`採否`は`採用`、`部分採用`、`不採用`、`充足済み`、`保留`、`対象外`、`移管`のいずれかとする。`充足済み`は既存commitか既存実装が要求を満たし実装を要しない場合に使う。

`根拠`は、実施しない範囲と理由が他の参照を解決せずに読み取れるように書く。

- `エージェント提案`と`エージェント由来のWI`の行は、採否を問わず判断を確定した観測可能な根拠を書く。`エージェント由来のWI`では適用範囲を誤りの機構が依存する条件から再導出した結果も含める。WIが非空の`## 適用範囲`を持ち計画が範囲を変えない採用行は`-`とする
- `人間由来のWI`と`ユーザー指示`の行は、採否を問わず原文の要求単位ごとに、原文の該当部分と実施範囲へ採用するか外すかを対応付けた分解結果を書く（分解が残らないと範囲の縮小が起草者の自己申告だけで通る）。WIの`## 反映内容と反映先`が要求単位ごとの対応を持つ場合は、それを採る旨と計画で採否を変えた単位だけを書く。原文の全単位を開放性を保ったまま採る`採用`の行に限り`-`とできる
- 原文が例示表現（「など」「例えば」「〜も」など）で示した開放集合を閉じた列挙へ置き換えた行は`部分採用`とし、閉じた集合と理由を書く
- 対話から複数のWIへ分割起票した場合は、各WIへ割り当てた要求単位を採否の母集団とし、他のWIへ割り当てた単位とそのファイル名も書く（部分採用の判定に含めない）。どのWI単独でも達成を示せない分割元の依頼全体の単位（目的、目標値、調査方針など）は、その旨だけを書く。いずれのWIにも割り当てず除外した単位は部分採用とする
- `充足済み`の行と充足済みの範囲を含む`部分採用`の行は、充足を確かめた実装箇所かcommitと裏付け手段を書く。ユーザーが観測して報告した不具合を充足済みとする前に、報告された呼び出し手段と操作順で対象を動かして期待する結果を観測する（コードの読解と既存テストだけでは確定しない）。根拠commitが報告より前なら、配備された版、操作順、環境など報告時との相違を調べて結果と未特定の範囲を書き、調査中の行は`充足済み`にしない
- 計画確定前にエージェント由来の完成条件を外すメインの技術判断を受けた場合は、対象AWI、対象条件、`メインの技術判断`、外す根拠を書く。外せる境界は`review-loop-coordination.md`「技術判断で外せる完成条件」に従い、人間由来の条件・原文要求・ユーザー判断の変更にはユーザーの判断を要する。後段のレビューと統合はこの記録を使い、実装着手後の判断はレビュー指摘管理表へ記録する
- 大規模な反復作業では、ユーザーが示す低費用の方法や既存の一括処理（`agent-toolkit:writing-standards`の`references/notation-rules.md`「表記の一括置換」など）を代表例で試す。件数と読込・レビュー・検証・統合の費用を比べ、採った方式と選定理由を書く。試行と費用比較の詳細は証拠へ残す

人間由来のWIの要求を全部または一部不採用にする行は、`agent-toolkit:wi-standards`「由来と承認」に従ってユーザーの確認を得る（確認を要する縮小と事後報告で扱う裁量の境界も同節）。
ユーザーがAWIの`## ユーザーコメント`かUWIの`## 回答`へ処理側に宛てた質問を直接記入した単位では、回答をUWIへ記録してユーザーへ返す工程を`## 実施内容`へ置く（AWI本文へ転記された質問は対象外。扱いは同節）。

### 要件・外部仕様

`## 要件・外部仕様`には固定H3の`### 受入シナリオ`を置き、他は自由なH3で区切ってよい。仕様・設計を決める前に、変更する成果物の消費主体、利用目的と後続の判断・行動を確定する。
`agent-toolkit/rules/01-agent.md`「QCDと3段判定」の原則から、明示要求と当然必要な条件を合わせて期待結果を導き、次の項目へ反映する。内部変更やエージェント向け文書も、その成果物の利用場面に必要な粒度で記す。

- 要件と、消費主体が観測する外部仕様（入出力、表示、公開契約、状態遷移、分岐条件、異常系、運用手順）
- 変更対象のファイルと識別子、変更する契約、生成・配布の過程と直接影響範囲。同じ値や動作をもたらす別の発生源（以下「別発生源」。省略時の値、プリセット、設定、環境変数、別の呼び出し手段、同じ操作を制約する別の節など）も保持先・消費先・エンドユーザーが観測する結果までたどり、該当しないものは根拠を付けて除く。多数の対象へ同時に作用する動作（共有CSSクラスのレイアウト方式、関数や設定の省略時の値など）を変える場合は、その動作に依存する指定を検索で列挙して変更後も同じ結果になるか確かめる（手元のデータでの測定は代わりにならない）。機能の追加・統合で成果物の役割が変わる場合は、名称、案内、ナビゲーション、運用ログ、配布メタデータ、既存テストで意味が変わる箇所も含める
- 完了条件。消費主体が観測できる成果と合否を判定する観測値かコマンドを、他の記述を参照せずに実行できる形で書く
- テストを新規作成・変更する場合は、保証する契約（検出する契約違反）と主要な失敗様態。期待値は要求仕様・契約から導く（選定と導出は`agent-toolkit:writing-standards`の`references/testing.md`）
- 事象を発生させないことを求める要求では、発生件数を0として観測する手段
- エンドユーザーが観測する公開インターフェース（設定キー、CLIオプション、環境変数、サブコマンド）を新設する場合は、新設の理由と、既存のインターフェースや省略時の値の変更では目的を満たせない理由
- ユーザー確認の回答（公開範囲を含む）と、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文からの具体化を要する軸」の判定結果
- 実行環境の受理条件に依存する設計方針の実機再現の典拠
- 永続または継続的に増えるデータでは、保持期間、容量上限、上限到達時の外部仕様、保守契機と所有者、長期条件の検証方法（基準は`agent-toolkit:writing-standards`の`references/design-time.md`）

`### 受入シナリオ`には`シナリオ | 由来 | 消費主体と入口 | 利用目的と後続行動 | 操作 | 期待結果 | テスト`の7列表を置く。利用目的の列を持たない旧6列表は保存済み計画の読取に限り受理する。

- `消費主体と入口`には実際に結果を受け取る消費主体と使う呼び出し手段、`利用目的と後続行動`には何のために使い、結果を受けて何を判断・実行するかを書く。`操作`には具体的な入力と初期状態、`期待結果`にはその利用場面と有効な要求から導いた結果と検出する失敗を書く。実装前に、この対応から試験を選べる状態へ具体化する。`由来`にはWIの完成条件、逐語引用の要求単位、ユーザー指示の所在を書く
- `## 実施内容`に`採用`か`部分採用`の行があれば、人間由来の各要求単位と各WIの完成条件を少なくとも1行へ対応付ける。採用行が無ければ本文を`なし`とする
- `テスト`には公開された呼び出し手段（コマンド、画面、API、hookなど）を経由して同じ契約違反を検出する結合・E2Eテスト名を書く。複数要求は同じ操作と期待結果で各合否を判定できる場合だけ1行へまとめる。群の完成条件を後でテスト化するという参照だけでは具体化を終えたことにならない。自動化できない行だけ、理由と手動観測の入力・操作・判定方法を書く
- 手動観測は実装担当が専用worktreeの成果物へ実施できる入力と操作で定め、公開、配布、稼働中の`atk wi process-loop`への反映の後にしか得られない観測を統合後へ先送りしない。WIの完成条件そのものが公開後にしか観測できない場合の判定は実行レビュー担当が`agent-toolkit:review-standards`の`references/exec-review-recording.md`で行い、計画には公開前に再現できる代替観測の行を置く。`atk wi process-loop`など本番の起動単位から起動する対象は、`agent-toolkit:check-execution`の`references/acceptance-scenarios.md`「常駐サービスの公開前の観測」に従う
- 操作・注入・故障と自動終了失敗を含むシナリオは、同書「検証資源の分離」に従って実行先と利用調整を定める
- 所要時間など負荷や並行処理で変わる計測値は、`agent-toolkit:wi-standards`の`references/awi-body.md`の完成条件と同じく、同じマシンで同じ時点に実行する対照との比較で書く

完了条件・受入シナリオ・手動観測が文書（規範、配布原本、設計記録、ガイド、コメントなど）の文意を判定する場合は、同じファイルから転記した文字列の有無や、部分文字列・行単位の正規表現の一致で合否を決めない。文意は、実装を経由した結果、他の定義との整合、検証コマンド、実行レビュー、または該当節の読解（ファイル・見出し・根拠の文の引用と判定を記録する）で判定する。文字列検索は読む候補の列挙と、見出し・設定キー・パスなど行の構造で一意に決まる実体の有無や件数に使う。

変更の種類に応じて次も書く。

- 既存の外部仕様・内部契約を変える場合: 変更前の仕様を期待値に固定している既存テストなどの自動チェックの改廃方針
- 公開された呼び出し手段を置換・廃止する場合: 新しい手段だけで同じ利用シナリオを結果まで完遂する検証（存在確認、mock、部分的なprobe、旧手段を併用した成功は代わりにならない）
- 禁止規定や制約を新設する場合: 既存箇所へ遡及するか今後の変更だけに適用するか
- 規範、エンドユーザー向け文書、メッセージの文面を変える場合: 変更する契約、対象のファイルと見出し、置換境界。文面は実行工程が確定し、文面の確定が要件そのもの（ユーザーが指定した場合など）のときだけ言語指定付きコードブロックで書く

直接影響範囲とは、変更した定義・文言・パスを参照、呼び出し、生成、期待値のいずれかとして持ち、合わせて直す必要がある箇所の全体を指す（単独の「影響範囲」が指す操作の副作用の範囲とは別の語）。変更前の識別子を名前で参照せず、変更前の動作を前提に書かれた既存の指定も含む。実行処理の変更点だけからは導けないため、変更前の値と識別子（変更した呼び出し手段の名前を含む）の固定文字列検索、変更ファイルの近くのテストを起点とした探索、共通の入出力（通知、生成物、設定など）からの追跡を組み合わせて探す。契約の内容を変える場合は、その契約が読み書きする保持先（列、欄、ラベル、設定キー、ファイルなど）の名前も検索語に含める。

- 外部から観測できる文言の変更: 変更前の文言を期待値に固定するテストを文言そのものの検索でも特定し、対象ファイルへ含める。新しいテストの根拠は同じファイルからの転記以外の契約から得る
- ファイルの改名・移動・廃止: 変更前のパスを固定文字列で検索し、文書、規範、コード、設定、テストの参照元を拾う（隠しディレクトリも欠落しない検索形にする）
- 仕様・概念の意味の変更: 変更前の意味を表す語句を、設計書、エンドユーザー向け文書、エージェント向け文書、docstringとコメント、データモデルのカラムコメント、生成物の入力元などで検索し、語句だけで区別できなければ意味を区別する条件と併せて判定する

見つかった直接影響範囲は対象ファイルへ含めるか、含めない理由を直接影響範囲の記述へ書く。

完了条件の書き方:

- 増減の方向や数値目標を定める場合は、基準値、目標、再実行できる測定方法を書き、再現性を確かめられる指標で判定する
- commit OIDはrebaseで変わるため固定文字列で書かず、判定時点の作業ツリーから解決する
- 一致0件を合格とする条件は`<検索コマンド>; test "$?" -eq 1`のように0件を合格と判定できる形で書く（努力目標）
- 件数を期待値とする検索は、見出し・定義・設定キーなど判定する実体の行構造へ条件を限定し、起草時に同じ条件で測った件数を期待値とする（努力目標）。見出しは行頭と行末を固定して数える

### 恒久化・リファクタリング

`## 恒久化・リファクタリング`直下へ`### 恒久化`と`### リファクタリング`をこの順で置き、この2つだけを見出しとする。いずれも後続の担当が実装と検収に使う結論を書く。検討の経過は証拠へ残す。

恒久化は、計画外でも使う方針・選定基準・却下理由・制約・前提を、後続の判断時に読まれる場所へ残す。直接実装する変更と計画自身の記録は候補から除く。

- `### 恒久化`は`知見`、`出所`、`反映先`、`根拠`の4列表で知見ごとに1行書く。対象が無ければ表を置かず、対象が無い旨を1文で書き、探索範囲と0件の理由は証拠へ残す
- `出所`には知見の由来（関連WI、確認への回答、エージェント提案など）、`反映先`には反映先のファイルと節（反映しない知見は`計画限り`）、`根拠`には反映の必要性と反映先の選定理由か反映しない理由を書く
- 反映先は、その知見を要する判断の工程でエージェントが読む契機があるかで選ぶ。自動チェックへ反映する場合は、失敗時にエージェントが読む位置へ制約の理由を併記する
- 反映を確定した知見は`## 実施内容`の行に計上し、反映先の契約と置換境界は`## 要件・外部仕様`へ書く
- バグ対応では関連WIの`## 原因分析`・`## 反映内容と反映先`か計画ファイル（バグ）の対応行を参照して原因と処置を対応付け、表には参照先が扱わない知見だけを書く

リファクタリングは`agent-toolkit/rules/01-agent.md`の付帯作業として、本変更に伴う既存部分の是正を実装と同時に完遂し、成果物群の設計品質を保つ。

- 検討の対象は、本計画が変更・新設する成果物の変更後のファイル全体と、参照・呼び出し・読込表の行で関係する成果物（定義、呼び出し元、既存テスト、生成・配布手順を含む）、`## 実施内容`が新設・分割する構造、`### 恒久化`の反映先とする
- 観点と判定基準は`agent-toolkit:writing-standards`の`references/design-heuristics.md`「設計品質の劣化確認」に従い、`### リファクタリング`へ後続の実装・検収に使う結論を書く。観点ごとの確認過程は証拠へ残す。劣化を是正する箇所と、合わせて整理すると類似処理・責務・記述の分散を解消できる箇所を`対象`、`現状の問題`、`対応`の3列表へ1行ずつ置く（含める箇所が無ければ表を置かない。記入例は「初回起草の雛形」）
- WIを入力とする計画でも、WIの`## 実現性`が同節の評価を記録していなければ、WIが確定した実現方式を同節で評価し、劣化する場合は是正を`## 実施内容`へ計上する
- エージェント向け文書を新設・改訂する計画では、`agent-toolkit:writing-standards`の`references/agent-documents-additions.md`「文書記述量の管理」を読み、同じ文書への変更全体をサイズ上限、責務、読込時点、重複と比べて整理の結論を書く。比較の過程は証拠へ残す
- 本計画に含めるリファクタリングは`## 実施内容`の行に計上する。テスト更新、直接影響範囲の同期、生成物同期などの実装付随作業は`## 要件・外部仕様`へ置き、`## 実施内容`の行にしない
- 根本原因を同じくする箇所の類似見直しは、作業種別によらず`agent-toolkit:bugfix`の`references/root-cause-analysis.md`「類似見直し」の母集団と「類似見直しと再発防止の完了」の判定に従う。通常変更の計画では結果を`### リファクタリング`へ記録し、専用節を設けない
- 本計画が触れず是正の必要も生じない既存の不備を見つけた場合は、`agent-toolkit:bugfix`を起動して`agent-toolkit/skills/bugfix/SKILL.md`「問題を見つけたときの対処」に従う

### 変更履歴

`## 変更履歴`は初版の作成、実装中の要件変更、方針転換を見出しと地の文で記録する（表と履歴IDは使わない）。

- 記録対象のユーザー発言は`### ユーザー発言<1から始まる連番>`のH3の下へ、原文を改変しない`text`コードブロックと、その発言から確定した現在の結論を置く。`ユーザー指示`由来の行を`採用`か`部分採用`とした計画では、`### ユーザー発言1`と空でない`text`コードブロックを1件以上置く
- 記録するのは、計画の目的、対象、範囲、外部可視の結果、実行制約または承認を変える、実在するユーザーメッセージの逐語引用に限る。委譲先では、委譲プロンプトと追送文のうち`<forwarded-user-input>`で囲まれた逐語本文だけが対象である（標識の扱いは`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」）
- ユーザー発言以外の記録は、内容を判別できる任意のH3の下へ置く
- ユーザー発話から導いたユーザー要求の対象の範囲を計画へ書く場合は、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」の範囲の記録書式（原文の逐語と出所、該当例、追加、承認の出所付きの除外）で書く。`## 実施内容`の要求単位ごとの分解と`部分採用`の規定も併せて適用する

### 検証と終端工程

完成条件と検証手段の具体化では、`agent-toolkit:wi-standards`の`references/awi-body.md`「完成条件」の自己観測と未確認範囲の扱いを適用する。

`## 検証`は`区分`、`検証コマンド`の2列と`変更範囲の検証`の1行の固定表とし、変更対象に対応する検証（対象ファイル限定のformat・lint・対象テスト）を書く。全体検証とCIの成否は公開工程で判定する。既存計画の旧名「近接検証」の1行表と旧2行表、旧名を持つ実装単位表の列は読み取り互換で受理し、新規作成と改訂では拒否する。

- 走査対象は変更ファイルとその直接影響範囲に限り、ファイル単位で書く（努力目標）。直接影響範囲の類型と範囲は`agent-toolkit:check-execution`の`references/verification-scope.md`に従い、選んだテストファイルと検証単位をコマンドへ明示する。類型に当たるが外すものは理由を直接影響範囲の記述へ書く。検証行は起草時点の選定であり、実行する担当が実行の直前に同書に従って実差分で補正する
- タスクランナーのターゲット単位ごとにコマンドを分ける（努力目標。失敗した単位だけを再実行できるように）
- セルは1 code spanに1つの完全なコマンドを書き、複数は`<br>`で分け、説明は表の外へ置く。shellのpipeline・redirect・環境代入などは実行可能なscriptへ移してそのargvを書く（引数はshellの再評価なしに解析される）
- 実行は`atk run-script plan-verify -- --plan <計画の絶対パス> --worktree <対象worktreeの絶対パス> --timeout <正の有限秒数> --summary-only`を使い、先に同じ入力の`--list`で順序とargvを確かめる。失敗やtimeoutの後も残りのコマンドを動かして全件の結果を返すため、集約の非0だけで終えず各記録と出力を判定する

凍結後に検証条件を訂正した場合は、レビュー指摘管理表の現在の結論を反映した全コマンドを別ファイルへ保存し、訂正済み検証表とする。そのファイルには本節と同じ`## 検証`の固定表を1つ置く。計画メタ情報は不要で、凍結計画の検証表全体を置き換える内容を書く。
列挙と実行の双方へ`--verification-plan <訂正済み検証表の絶対パス>`を加える。計画・訂正の結論・訂正済み検証表の対応と絶対パスを引き継ぎ記録へ残し、実装・実行レビュー・統合へ同じ内容を渡す。引き継いだ内容を保持し、訂正済み検証表を更新した場合は更新後の条件で列挙と検証をやり直す。

pyfltrの`run`・`run-for-agent`・`fast`・`ci`をplan-verifyから実行するときは`--output-format=jsonl`を明記し、対象到達・完了を示すsummaryを保存する。plan-verifyはこのオプションを自動付与しない。検証の合否は結果まとめの各行の`state`と`failure`も含めて判定する。summaryが示す未到達・未完了や完了結果の取得失敗は子の終了0でも`state: failure`と集約終了1になるため、子の終了0だけで合格にしない。

`## 終端工程`は確認した公開範囲と、commit・push後の操作（PR/MRの作成とタイトル・本文、リリース、タグ付けなど）を書く。公開範囲の確認を要さず公開後の固有操作も無い計画は`なし`と書く。

### バグ調査

作業種別が`バグ対応`の計画は、原因分析を記録した関連WIの`## 原因分析`を参照する。
計画ファイル（バグ）を作成するのは、入力にWIが無い計画（`関連WI: なし`）と、計画時にWIの原因分析を訂正または追加した計画に限る（`## 原因分析`を持たない投入済みAWIを処理する計画は追加に当たる）。訂正・追加では対象のバグ単位だけを完全な表で書き、食い違いの観測と結論を`## 変更履歴`へ記録する。
計画ファイル（バグ）には計画主題のH1と、バグ単位のH3ごとに原因分析表と調査表をこの順で置き、各セルを空欄にしない（見出しはH1とH3だけ、各H3の表はこの2件）。行名、列名、順序、統合分割規則、恒久化の参照契約は`agent-toolkit:bugfix`の`references/analysis-records.md`「原因分析の記録先」に従い、類似見直しも同所の規定で調査表へ記録する。
`check_plan_file.py`は作業種別が`バグ対応`で`計画ファイル（バグ）`行を持つ計画について、実在、計画stemとの一致、計画ファイル（バグ）の構造を検証する。`関連WI`が`なし`のバグ対応計画は同行を必須とする。

### 進捗ログ

`結果・特記事項`には後続の工程と再開するエージェントが使う値だけを書く。観測の経過と後続が読まない一時ファイルのパスは省き、commitは一意な短縮OIDで示す。

`## 進捗ログ`は中断後に再開できる粗い記録として、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。起草時は内容行を置かない。

- 追記は`atk run-script plan-progress -- <計画ファイル> --completed-step <完了した工程> --result <結果・特記事項>`で行う（日時は同処理が生成する）
- 実装開始後は、再開時に次の工程を選べる情報（commitの完了、変更範囲の検証の結果、実行レビューの収束、完了判定、専用worktreeの絶対パス・専用branch名・回収対象）を追記する
- WI実装commitの記録・取得・履歴変更後の継承は`agent-toolkit:commit`の`SKILL.md`「WI実装commitの対応」に従う（対応記録ファイルへ短縮OIDとAWI集合を保存し、進捗ログには固定3列表の行だけを追記する）
- `agent-toolkit:process-wi`のレーンでは、統合の行の結果・特記事項へ`レーン稼働時間: <秒数>秒`を書く。秒数はメインが最初のレーン担当起動直後に保存して渡した`レーン開始時刻`から、`atk lane integrate`のGit統合の成功後・最終化の最初の操作の前までの総経過時間とし、待機・レビュー・統合前の失敗と復旧を含め、担当sessionの置換後も最初の起点を保つ。秒数・完了時刻は同CLIが確定した値を最終化argvの参照で受け取り、手で仮の値を書かない
- 同じ行へ`予測補正記録: 対象リポジトリ=<識別子>; 選定元=<出力先の絶対パス>; レーン=<識別子>; 完了時刻=<時差付き時刻>; 補正前実装秒=<秒数>; 補正前統合秒=<秒数>; 補正係数=<係数>; 総経過秒=<秒数>`を記録する。選定元は1回のprocess-wiの実行を識別する。補正前2値は選定結果の`レーンの所要時間`の`補正前の実装秒数`と`補正前の統合秒数`から、係数は最上位の`見込みの補正`の`係数`から取得する（追加WIがあればレーンの累積予測）。補正前の欄には補正前と確かめた値だけを書き、復元できない旧記録は不明として次回の分母から除く。同じレーンの複数計画では同じ値を使って1件と数え、計画なしのレーンは、同じ書式をそのレーンの対象AWI本文へ保存する。同じ実行・レーンの記録が複数のAWIにあっても1件と数える。セッション内の引き継ぎ記録には保存先を記す
- 完了報告を発行するエージェントは、完了条件ごとの充足根拠か未達理由を最終行へ記録する

再開するエージェントは、進捗ログの最終行、`## 概要`の目的、`## 変更履歴`のユーザー発言、完了条件、レビュー指摘管理表の応答を読んでから次の工程を選び、計画の記述と異なる箇所は指摘管理表の応答を現在の結論とする。

## 要件の成立性

`## 要件・外部仕様`は、消費主体の結果とそれを損なう条件を計画と関連WIから復元でき、正常系・主要な異常系の再現と既存の成功手順への影響を判定できる粒度に保つ。WIの`## 実現性`が示した成立の根拠は再掲せずWIファイル名で参照する。

契約整合の手掛かりは送受信、分岐、制限、廃止、外部挙動、配布とする。共有契約は双方を同じ計画で確定し、変更する分岐の入力集合と変更前後の結果を対応付ける。
制限などで現行の成功シナリオを失う場合はユーザー合意の根拠を記録する。廃止に伴う完成条件・チェックリスト・テストの追随、外部挙動を実物で確かめた典拠、プロジェクト規範が定める配布・版数更新・同期先文書も計上する。
