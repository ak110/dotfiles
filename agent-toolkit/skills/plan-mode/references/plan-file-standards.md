# 計画ファイル作成基準

本書は計画ファイル（作業実体は`~/.claude/plans/*.md`）の成果物契約の単一の正本である。
計画を起草する主体は初版の起草前に本書を全文読み、全項を満たす計画を作成する。
実行レビュー担当は本書の各項を点検の基準として同じ本文を読む。

計画ファイルは、ユーザーが実施内容と採否を判断でき、実装担当が迷わず着手できる要件・外部仕様水準の記述を持つ。
実装手順、関数分割、内部の制御構造及び改訂後の全文は書かず、実装工程が現行コードから確定する。
実装水準の欠陥はテストで検出し、実行レビューは要件・外部仕様の達成と過剰設計の有無を判定する。

本書でいう`ユーザー`は計画の要求・指示・合意を与え、確認経路で回答する主体、
`エンドユーザー`は成果物を利用する主体、`消費主体`は成果物ごとに定まる利用・検証の主体を指す。

## 計画ファイルの保存と参照

計画は1ファイル`<stem>.md`とし、作業種別が`バグ対応`の場合だけ同じstemの`<stem>.bugs.md`を同じディレクトリへ置く。
新規作成は`${CLAUDE_PLUGIN_ROOT}/skills/plan-mode/scripts/create_plan_files.py`を経由し、private-notesへ実装前の計画ファイルを作成しない。
作成処理は同じstemに属する全ファイルを排他的に確定し、読み戻しと計画構造検査に成功してからパスを返す。
stemは起動経路ごとに次のとおりとし、`dd`は作成日、`HHmm`は作成時刻とする。同じstemが既にある場合は作成処理が`-<小文字16進数4桁>`を付けて再試行する。

| 起動経路 | stem |
| --- | --- |
| `agent-toolkit:process-wi`のレーン | `dd-HHmm_process-wi_レーンNN` |
| `agent-toolkit:fast-process-wi` | `dd-HHmm_fast-process-wi` |
| `agent-toolkit:plan-mode`の直接起動 | `dd-HHmm_<日本語の簡潔な名詞>` |

`agent-toolkit:process-wi`のレーンは、内部作成処理へ`--lane lane-NN`で起動文のレーン識別子を渡す。`NN`は2桁のレーン番号とし、日付、時刻、固定接頭辞及びレーン番号を呼び出し側で組み立てない。

計画本文が参照する計画ファイル（バグ）とレビュー指摘管理表には、固定接頭辞`~/.claude/plans/`とファイル名を使う。
接頭辞後の値はファイル名1件だけとし、パス区切り文字、`..`、シェル式、Windows区切り文字を含めない。
参照の解決では接頭辞を展開せず、当該参照を含む計画ファイルのディレクトリへファイル名を結合して実体を求める。
既存計画の本文に残る`$(atk config get private_notes)/`から始まる参照は読み取り互換として受理する。

計画は実行レビューの収束時点まで`~/.claude/plans`直下で更新し、収束後に`atk plans commit <作業root直下のメイン計画ファイル名>`で`private-notes/plans/yyyy/MM/`へ移動して保存する。
同コマンドは計画ファイル、計画ファイル（バグ）及びレビュー指摘管理表を同じcommitで保存する。
`agent-toolkit:process-wi`のレーンが実行レビューの収束前に終端する場合は、当該終端の時点で保存する。
保存済み計画は完了した作業の記録であり、次のセッションの実装入力にしない。
中断したレーンの再開は`agent-toolkit:process-wi`の`skills/process-wi/references/run-lanes.md`が定める。
計画作業rootの各計画バンドルには所有セッションの記録が付き、`atk plans list`で所有セッションと最終更新時刻を一覧できる。
自身が所有しない計画はそのまま残す。private-notesの計画ファイルを編集ツールで直接書き換えない。

実行レビュー指摘管理表は計画ファイルと同じディレクトリへ`<計画stem>.exec-review.tsv`（`track`は`exec-review`）として置く。
計画を持たない実行レビューの表は`~/.claude/plans`直下へ置く。`agent-toolkit:fast-process-wi`の直接実装では`fastwi-<処理開始時点の7文字以上の一意な短縮OID>.exec-review.tsv`、公開工程のCI失敗修正では`ci-<起点commitの7文字以上の一意な短縮OID>.exec-review.tsv`とする。短縮OIDは`git rev-parse --short=7 <revision>`が返した値をそのまま用いる。
前者は収束後に削除し、後者は`atk plans commit ci-<起点commitの7文字以上の一意な短縮OID>.exec-review.tsv`で`private-notes/plans/ci/`へ保存する。

本書、`agent-toolkit:plan-mode`のSKILL.md及び`${CLAUDE_PLUGIN_ROOT}/share/`配下の計画関連文書は、計画に属するファイルを次の呼称で指す。

| 呼称 | 実体 |
| --- | --- |
| 計画ファイル | `<計画名>.md` |
| 計画ファイル（バグ） | `<計画名>.bugs.md` |
| 実行レビュー指摘管理表 | `<計画名>.exec-review.tsv` |

## 計画ファイルの構成

計画ファイルはH1の主題に続けて次のH2を固定順で置く。

1. `## 概要`
2. `## 実施内容`
3. `## 要件・外部仕様`
4. `## 恒久化・リファクタリング`
5. `## 変更履歴`
6. `## 検証`
7. `## 終端工程`
8. `## 進捗ログ`

自由なH3は`## 要件・外部仕様`と`## 変更履歴`の配下だけに置き、H4以深の見出しは置かない。
同じ事実、数値、要約は計画全体で1箇所だけに置き、他の箇所は節名で参照する。
関連WIはAWI・UWIの正本ファイル名と1行要約だけを保持し、本文全文を計画へ転記しない。
既存の規範の適用範囲へ言及する場合は条文を再掲せず、条文を持つ文書のパスと節名を参照する。
指摘、要件追加又は方針転換を反映する際は、対象節の末尾へ追記せず、既存記述と統合して現在の結論だけが残る形へ節を編集し、経緯は`## 変更履歴`へ記録する。

### 概要と計画メタ情報

`## 概要`直下へ全体像、目的、対象範囲の順で短い地の文を書く。計画を初めて読む読者が現在の計画の全体像を把握できる要約として保ち、内容が変わる場合は節全体を書き直す。

直下のH3は`### 計画メタ情報`だけとし、次の行を固定順で置く。
コロンはASCIIの`:`、コロン後は半角空白1字とし、`関連WI`と`作業種別`以外の値はバッククォートで囲む。

```md
- 起動経路: `<skillまたは起動経路>`
- 対象リポジトリ: `/absolute/repository/path`
- 関連WI:
  - 20260831-000000-001.md: AWIの1行要約
- 作業種別: バグ対応
- 計画ファイル（バグ）: `~/.claude/plans/<計画stem>.bugs.md`
```

`作業種別`は`バグ対応`又は`通常変更`とする。
`関連WI`には、計画の入力となったAWIとUWIの正本ファイル名を1件1行で置き、コロンに続けて当該要求の1行要約を書く。入力が無い計画では`- 関連WI: なし`と書く。
`計画ファイル（バグ）`の行は`バグ対応`の場合だけ置く。
`対象リポジトリ`は計画構造検査へ渡す`--work-dir`のGitルートと一致させる。`agent-toolkit:process-wi`のレーンでは当該レーンの専用worktreeの絶対パスを書く。

### 実施内容

`## 実施内容`には`実施内容`、`由来`、`採否`、`根拠`の4列表を置き、ユーザーが計画ファイルだけで何を実施し何を実施しないかを判断できる概念単位で記載する。
AWIは1ファイルを1行とし、実装手順、テスト項目、内部の分解単位ごとに行を分けない。
複数のWIを扱う計画では、WI間で対象、方針又は変更内容が競合する場合に、競合する組と採用した処置を当該行の`実施内容`へ書く。

`由来`は`人間由来のWI`、`エージェント由来のWI`、`ユーザー指示`、`エージェント提案`のいずれかとする。
WI由来の行は、区分に続けて半角空白1字を置き、半角丸括弧で囲んだ正本のファイル名を記載する（例: `エージェント由来のWI (20260831-000000-001.md)`）。当該ファイル名は計画メタ情報の`関連WI`と一致させる。
2つのWI区分のどちらを選ぶかは`agent-toolkit:wi-standards`の「由来と承認」に従う。
正本の本文から機械判定できない明示由来を根拠に`人間由来のWI`とする行は、ファイル名に続けて半角空白1字と`[対話由来]`を付け、当該由来の出所と引用範囲を`## 変更履歴`へ記録する。
エージェントが構成した指示から確定した実施内容は`エージェント提案`とし、`ユーザー指示`としない。

`エージェント由来のWI`又は`エージェント提案`の変更が、`agent-toolkit/rules/01-agent.md`「協調と自律」のユーザーが直接観測する結果の変更に当たり、同節で事後承認と判定した場合は、`根拠`を`事後承認対象:`で始める。同じセルへ変更後にユーザーが観測する結果、採用理由及びトレードオフを書く。レーン担当自身はUWIを投入せず、この標識を`agent-toolkit:process-wi`のメインへ引き渡す。該当しない行へ標識を書かない。

計画初版の確定後、実装とレビュー修正のいずれかで新たに確定した実装判断が同じ事後承認条件を満たす場合は、`## 実施内容`へ`エージェント提案`の別行を追加する。同じ標識、ユーザーが観測する結果、採用理由及びトレードオフを当該行へ記録する。`ユーザー指示`と`人間由来のWI`のいずれの行にも当該判断を追記せず、由来を混同しない。

`採否`は`採用`、`部分採用`、`不採用`、`充足済み`、`保留`、`対象外`、`移管`のいずれかとする。
`充足済み`は、要求が成立し、既存commit若しくは既存実装が当該要求を満たすため実装を要しない場合に用いる。
`根拠`は次のとおり書く。

- `由来`が`エージェント提案`又は`エージェント由来のWI`の行は、採否にかかわらず、当該判断を確定した観測可能な根拠を1文で書く。`エージェント由来のWI`では、当該要求の適用範囲を誤りの機構が依存する条件から再導出した結果も含める
- 上記以外で`採否`が`採用`の行は`-`とする
- 上記以外の行は、実施しない範囲と理由を、別の参照を解決せず理解できる文面で書く。`部分採用`の行は、実施する範囲を`実施内容`へ書き、実施しない範囲と理由を`根拠`へ書く
- `充足済み`の行と充足済みの範囲を含む`部分採用`の行には、充足を確認した実装箇所又はcommitの識別子と、充足の成否を確定した裏付け手段を加える

人間由来のWIの要求を全部又は一部不採用にする行は、`agent-toolkit:wi-standards`の「由来と承認」に従ってユーザーの確認を得る。
実施しない除外・保持も`## 実施内容`の行として記録し、専用の表を設けない。
計画作成の対話や調査で得た恒久的な知見（当該計画固有でない方針、選定基準、却下した代替案の判断根拠、調査で確定した制約）を恒久成果物へ反映する場合は、反映先を`実施内容`へ書いた行として計上する。

### 要件・外部仕様

`## 要件・外部仕様`には、実装担当が新たな要件判断を要さず着手できる粒度で、次を書く。
自由なH3で区切ってよく、対象へ該当しない項目は書かない。

- 要件と、消費主体が観測する外部仕様（入出力、表示、公開契約、状態遷移、分岐条件、異常系、運用手順）
- 変更対象のファイルと識別子、変更する契約、及び生成・配布経路と参照元の追随の範囲。改訂後の全文と実装コードは書かない
- 完了条件。消費主体が観測できる成果と、合否を判定する観測値又はコマンドを、計画内の他の記述を参照せずそのまま実行できる形で書く
- テストコードを新規作成又は変更する場合は、テストが保証する契約（検出対象とする契約違反）と想定する主要な失敗様態。期待値は要求仕様・契約から導出し、実装の実行結果を根拠にしない
- 外部可視の要件ごとに、当該要件を誤って実装した場合に失敗する検体（テスト、検査コマンド又は観測手順）の対応。特定の事象を発生させないことを求める要求では、当該事象の発生件数を0として観測する手段を書く
- ユーザーから得た承認の範囲、及び`agent-toolkit/rules/01-agent.md`「協調と自律」に従って具体化した軸の判定結果
- 実行環境の受理条件に依存する設計方針の実機再現の典拠

既存の外部仕様又は内部契約を変える計画では、変更前の仕様を期待値として固定している既存テストその他の機械検査の改廃方針を書く。
禁止規定や制約を新設する計画では、既存箇所へ遡及適用するか今後の変更箇所だけへ適用するかを書く。
規範、エンドユーザー向け文書、メッセージの文面を変更する計画では、変更する契約、対象のファイルと見出し、置換境界を書き、文面自体は実装工程が確定する。
文面の確定が要件そのものである場合（ユーザーが文面を指定した場合など）だけ、当該文面を言語指定付きコードブロックで書く。
外部から観測できる文言を変更する計画では、変更前の文言を期待値として固定する検体を文字列検索で特定し、実装単位の対象ファイル集合へ含める。変更する定義への直接参照だけを検体の探索条件にしない。

計画が増加又は削減の方向や数値目標を定める場合は、基準値、目標及び再実行できる測定方法を完了条件へ書き、再現性を確認できない指標は合否ゲートにしない。
完了条件がcommit OIDを検査する場合は、rebaseで値が変わるOIDを固定文字列として書かず、検査時点の作業ツリーから解決する形で書く。
一致0件を合否条件とする完了条件は`<検索コマンド>; test "$?" -eq 1`の形式で書く。

### 恒久化・リファクタリング

`## 恒久化・リファクタリング`直下へ`### 恒久化`と`### リファクタリング`のH3をこの順で置き、他の見出しを置かない。
いずれのH3でも`なし`、`不要`、`該当なし`、`特になし`だけの記載は認めず、検討した範囲と結果を書く。

恒久化では、計画作成の対話・確認・調査で得た恒久的な知見を、完了後は参照されなくなる計画ファイルではなく、恒久的に参照される成果物へ書き残す判定を確定する。
次の知見を候補として列挙し、明示的な再利用性、外部公開契約、必要な設計理由又は検証済みの反復欠陥に該当するものだけを恒久化する。

- ユーザーが指示・発話又は確認への回答で示した方針・要件・合意事項のうち、当該計画固有でないもの、又は当該計画で選んだ実装に固有でも将来の合理的な代替案を制約するもの
- ユーザーが確認への回答（`AskUserQuestion`の回答とUWIの`## 回答`節を含む）に付した判断基準・選択理由・補足（選択そのものより選定理由が将来の意思決定で再利用されるため）
- エージェントが確定した判断のうち、他の計画にも適用できる選定基準・指針
- 却下した代替案のうち、将来の意思決定で再利用できる判断根拠
- 調査で確定した制約・前提・外部仕様の理解
- 計画が新設又は変更する判定・遮断・順序制御の機構が依存する前提と、前提が崩れた場合に生じる観測事象（反映先は当該機構の実装箇所又はdocstringとし、コードだけで意図が自明な処理へ説明コメントを一律追加しない）

次の情報は候補から除く。

- `## 実施内容`が直接実装する機能、規範又は文書変更そのもの
- 当該計画の実施内容・検証条件・進捗など、計画ファイル自身が記録する情報
- セッション固有の事情・一時状態・個人名指し（`../../writing-standards/SKILL.md`「ユーザー入力素材の取扱い」と同じ扱い）
- 既存の恒久成果物が既に記載する内容（参照の補強で十分な場合は反映しない）

`### 恒久化`の本文は`知見`、`出所`、`反映先`、`根拠`の4列表とし、知見ごとに1行で記載する。
候補が1件も無い場合は表を置かず、確認した範囲と0件と判断した理由を書いた1行の地の文を置く。
`出所`には関連WI、確認への回答、エージェント提案など知見の由来を書く。
`反映先`には反映先のファイルと節を書き、反映しない知見には`計画限り`と書く。
`根拠`には反映の必要性と反映先の選定理由、又は反映しない理由を書く。
反映先は、当該知見を要する判断をする工程で実行主体が当該反映先を読む契機があるかを先に判定し、契機がある候補の中から、コードに近い仕組み、プロジェクト規範、配布規範、スキルの順に比較して選ぶ。読む契機が無い反映先は選ばない。
反映先が機械検査である場合は、当該検査が失敗したときに実行主体が読む位置へ当該制約の理由を併記する。
反映を確定した知見は`## 実施内容`の行として計上し、反映先へ書く契約と置換境界は`## 要件・外部仕様`へ書く。
バグ対応では、計画ファイル（バグ）の対応行を正本として参照し、同じ説明を複製しない。
計画ファイル（バグ）のいずれの行にも対応しない知見・変更（恒久化・リファクタリングで新たに導入・変更する機構を含む）だけを4列表へ記載し、無い場合は表を置かず参照のみとする
（厳守規定。同じ原因による既存欠陥を計画対象から漏らさないため）。

リファクタリングは実装と同時に行う既存部分の周辺是正とし、本来の対応に関連して既存部分を整理すると設計又は実装が改善する場合は、それを補う是正まで完了して計画の完了とみなす。
実施内容そのもの、新設する機能そのもの及び実装・検証に必須の付随作業はリファクタリングとして記載しない。
検討の対象は、本計画が確定した設計に伴う修正が起因となって是正が必要になるか、当該修正と合わせて既存部分を整理すると類似処理・責務・記述の分散を解消できる周辺箇所に限る。
本計画の変更が触れず、当該変更によって是正の必要が生じない既存の不備は対象にせず、発見した場合は`agent-toolkit:bugfix`の`references/response.md`の経路に従う。
検討の範囲は本計画が変更する対象と、その定義・参照・呼び出し元・既存テスト・生成・配布経路のうち、当該変更が是正を必要にする箇所とする。

- コードでは、本計画の変更で陳腐化する既存実装・既存テスト、本計画の変更が分散させる類似処理、本計画の追加により責務が肥大化するモジュール・ファイル・関数
- 文書では、本計画の追記に対する既存節の粒度不整合、変更後の内容に合わない節構成、本計画の変更が生じさせる同一トピックの分散

`### リファクタリング`の本文は、次の`対象`、`現状の問題`、`対応`の3列表を1件置き、本計画へ含める箇所ごとに1行を書く。実施しない候補と採否欄は表へ置かない。

```md
| 対象 | 現状の問題 | 対応 |
| --- | --- | --- |
| <対象箇所> | <問題> | <対応> |
```

対象が無い場合は表を置かず、対象を検討した範囲と0件と判断した理由を書いた1行の地の文を置く。
本計画に含めるリファクタリングは`## 実施内容`の行として計上する。
実装・検証の成立に必須のテスト更新、参照元同期、生成物同期などの実装付随作業は`## 要件・外部仕様`へ置き、`## 実施内容`へ個別の作業行を追加しない。
規範文書へ新しい節又は項目を追加する計画では、`agent-toolkit:writing-standards`の「文書記述量の管理」に従い、既存記述の重複統合と削減を検討する。
同じ原因を持つ他の箇所の点検は、通常変更ではリファクタリングの検討範囲として扱い、計画本文へ類似見直しの専用節を置かない。

### 変更履歴

`## 変更履歴`は、計画初版の作成、実装中の要件変更及び方針転換を記録する。表を置かず、履歴IDを設けない。
記録対象のユーザー発言は`### ユーザー発言<1から始まる連番>`のH3見出しの下へ置き、直下へ原文を改変しない`text`コードブロックを置いて、その発言から確定した現在の結論を併記する。
`ユーザー指示`由来の行の採否を`採用`と`部分採用`のいずれかとした計画では、`### ユーザー発言1`と空でない`text`コードブロックを1件以上置く。
記録対象は、計画の目的、対象、範囲、外部可視の結果、実行制約又は承認を変更するユーザー発言とし、実際のユーザーメッセージとして存在する発話の逐語引用に限る。
委譲先が受領した起動文と追送文は起動側が構成した指示であり、`<forwarded-user-input>`で囲んで渡された逐語本文だけを記録の対象とする。標識の書式は`${CLAUDE_PLUGIN_ROOT}/share/rules-subagent.md`「受領した本文の出所」を正本とする。
ユーザー発言以外の記録は、変更の内容を判別できる任意のH3見出しの下へ置く。
ユーザー発話から導いた結論を計画本文へ書いた主体は、書いた直後に`agent-toolkit/share/rules-main.md`「ユーザー発話の解釈」と照合し、原文が限定していない適用範囲を結論側で狭めていないことを確認する。

### 検証と終端工程

`## 検証`は`区分`、`検証コマンド`の2列2行の固定表とし、`近接検証`行には変更対象に対応する検査（対象ファイル限定のformat・lint・対象テスト）のコマンドを、`全体検証`行には対象リポジトリ全体の検査コマンドを書く。
近接検証は、変更するファイルとその直接消費側のうち当該検査が必要とするファイルへ走査対象を限定し、ディレクトリ指定で集合の外のファイルを走査する形を書かない。
変更するファイルが複数の処理と共有する実行入口を経由して検体から起動される場合は、当該入口を共有する検体を直接消費側へ含める。参照関係を持たない検体も、当該入口を経由して変更の影響を受けるためである。
全体検証を対象リポジトリのCIが同値の検査として担う場合は、`全体検証`行へ`CIで代替`と書く。同値の判定は`${CLAUDE_PLUGIN_ROOT}/share/session-termination.subagent.md`「生成物とpush」が定める。
全体検証を持たない対象リポジトリでは`全体検証`行へ`なし`と書く。
セルへは、タスクランナーが独立したターゲットとして公開する検査単位ごとにコマンドを分けて並べ、複数のターゲットを連結した1件の合成コマンドを書かない。

`## 終端工程`はcommit・push後に実行する操作（PR/MRの作成とタイトル・本文、リリース、タグ付けなど）だけを列挙する。終端工程が無い計画は`なし`と書く。

### バグ調査

作業種別が`バグ対応`の計画は、計画メタ情報の`計画ファイル（バグ）`が参照する`~/.claude/plans/<計画stem>.bugs.md`へバグ調査を分離する。
計画ファイル（バグ）には、計画主題に対応するH1と、バグ単位のH3ごとに固定の原因分析表と固定の調査表をこの順で置き、各セルを空欄にしない。
各表は`agent-toolkit:bugfix`の原因分析契約が定める行名、列名、順序、統合分割規則及び恒久化の参照契約を維持する。
H2とH4以深の見出しを置かず、各H3の配下へ2件以外の表を追加しない。
`check_plan_file.py`は作業種別が`バグ対応`の場合に、実在、計画stemとの一致、分離先の構造を検査する。
同じ原因を持つ他の箇所の点検は、同契約の類似見直しに従って調査表へ記録する。

### 進捗ログ

`## 進捗ログ`は実装工程を中断後に再開できる粗い記録として、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。
起草時は内容行を置かず、新規作成では内容行を持つ本文を受理しない。
実装開始後は、計画を実装する主体がcommitの完了、近接検証の結果、実行レビューの収束及び完了判定を追記する。
実装開始時は、専用worktreeを用いる経路では絶対パス、専用branch名、作成時HEADの7文字以上の一意な短縮OID、所有主体、回収対象を記録する。
結果・特記事項にはcommitの7文字以上の一意な短縮OID、検証結果、計画との差異、阻害要因を必要な範囲で書く。
完了報告を発行する主体は、報告の直前に`## 要件・外部仕様`の完了条件を全文再読し、各条件の充足根拠又は未達理由を進捗ログの最終行へ記録する。
実装工程を中断後に再開する主体は、進捗ログの最終行に加えて`## 概要`の目的、`## 変更履歴`が保持するユーザー発言の逐語本文、及び`## 要件・外部仕様`の完了条件を読み直してから次の工程を選ぶ。

## 計画構造検査

GFM表のセルにリテラルの`|`を含める場合は、コードスパン内を含めて`\|`と記述する。
計画構造検査が受理する書式のうち、全ての節へ共通する形式を次に定める。

- 本書が列名又は行名を定める固定表は、当該名称と順序を完全一致で判定する。同じ列名の固定表を同じ節へ複数置かず、内容行の全セルを空にしない
- 固定H3を定める節へは、当該H3以外の見出しを置かない
- 節の本文へ`なし`と書くと定めた箇所では、`なし`の1行だけを置く
- 計画メタ情報の`関連WI`の子項目は、半角空白2字の字下げに続けて`-`と半角空白1字を置き、ファイル名は`yyyymmdd-hhmmss-nnn.md`の形式で重複させない
- `## 実施内容`の`由来`へ書く正本ファイル名には、パス区切り文字、半角丸括弧及び空白を含めない
- `## 要件・外部仕様`と`## 終端工程`を空にしない
- 計画本文がスキル又はサブエージェントを起動の形で参照する場合は、当該定義の実在を検査する
- コードフェンスを閉じる
- `## 変更履歴`配下へGFM表を置かず、`### ユーザー発言<連番>`は連番を1から欠番なく昇順に置く
- 計画作業root直下の計画ファイルは、「計画ファイルの保存と参照」節のstem規約に対応する保存工程の受理条件を、起草時の検査でも満たす。計画作業root直下に無い計画ファイルはファイル名を検査しない

`skills/plan-mode/scripts/check_plan_file.py`が計画の構造と実体を検査する。
同じ祖先見出しの下に同じ文言の見出しが複数現れる状態は不正とする。
本スクリプトはplugin同梱の`agent_toolkit`パッケージへ依存するため、次のいずれかの形で実行する。引数には計画ファイル`<計画名>.md`の絶対パスを渡す。

```sh
uv run --project <plugin rootの絶対パス> --locked --no-default-groups /absolute/path/to/plan-mode/scripts/check_plan_file.py --reject-migration-warnings /absolute/path/to/plan.md
PYTHONPATH=<plugin rootの絶対パス> python /absolute/path/to/plan-mode/scripts/check_plan_file.py --reject-migration-warnings /absolute/path/to/plan.md
```

`uvx --from agent-toolkit python <スクリプトの絶対パス>`は当該パッケージを解決せず、本スクリプトは当該解決の失敗を検出した場合に上記の起動形を示して終了コード2で終わる。
対象リポジトリがセッションの作業ディレクトリと異なる場合は`--work-dir /absolute/path/to/target-repository`を付ける。
`--reject-migration-warnings`は新規作成・改訂で旧形式からの移行警告をエラーとして扱う。保存済み計画を読み取りだけで検査する場合は同オプションを省略する。
通常のシェルでは`${CLAUDE_PLUGIN_ROOT}`が展開されないため、読込済みの本書の絶対パスからスキルの絶対ベースディレクトリを確定して指定する。
旧形式（単一9節、二ファイル）の計画は`references/legacy-plan-file-standards.md`が定める読み取り互換で受理し、構造検査は新書式への移行を警告する。
構造定数と値抽出は`agent-toolkit/agent_toolkit/_plan/structure/`を正本とする。
素材と要約の意味照合、根拠の妥当性、検討の実質はレビューで確認する。

## 保持・不変性・完全復元の契約

保持、不変性又は完全復元を計画の契約とし、又は確認へ送る選択肢へ書く場合は、
確定前に採用する入力形式が当該不変性を表現できるかを対象実装を読んで確認する。
併せて、保存・読込・UI・エディターなど通過する既存経路が加える変換（再直列化・trim・strip・既定値補完・値の正規化）も対象実装を読んで列挙する。
成立しない範囲がある場合は、不変とする対象と変更を許す例外を明示した契約へ書き換えてから確定し、選択肢本文にも同じ限界を書く。
無条件の「そのまま保存」「元と一致」という表現を契約及び完了条件へ用いない。

## 復元・巻き戻し型の変更

過去の契約へ戻す変更と過去の契約を撤去する変更では、対象項目ごとに導入目的を調べ、維持、修正、撤去を項目別に判定して`## 要件・外部仕様`へ記録する。
復元候補ごとに、現行状態が喪失後に意図的に確立されたものかを、当該領域の後続commit、消費主体が観測する仕様及び実装コメントの参照関係で確認し、意図的な再設計と判定した項目は復元対象から外して判定根拠を記録する。
由来の判定はファイル単位の最終更新者ではなく、現行に残る記述は行単位の作者、失われた記述は当該記述を除去したcommitで行う。

## 要件の成立性

`## 要件・外部仕様`が定める変更は、書式への適合に加えて次の各項を満たす。

- 要件シナリオ: 正常系、完遂範囲・順序・条件を指定する入力、及び消費主体が観測する主要な異常系のそれぞれについて、実行主体、認可根拠、外部から観測できる状態更新の時機、失敗時の経路が計画本文から一意に定まる。消費主体が観測しない内部の状態遷移と例外経路は対象に含めない
- 外部コマンドの挙動: 計画が実行を指示する外部コマンドについて、分岐、遮断、完了判定の入力とする挙動（終了コードの意味、出力が相対か絶対か、オプションの導入バージョン、設定の優先順位）を安全な実行又は管理対象一時領域での同等再現で確認し、結果を典拠として書く。確認できない観点は未検証範囲として明記する
- 送受信契約の対: 委譲の起動契約、返却契約その他の主体間で渡す契約を変更する計画では、送信側と受信側の双方を同じ計画で確定し、受信側の発動条件と入力の消費が現行の文面のまま成立するかを判定して、成立しない受信側を変更対象へ含める
- 管轄規範の追随: 変更対象ファイル群を管轄するプロジェクト側の編集規範が定める配布経路、版数更新及び同期先文書の追随を計画へ計上する
- 新設機構の成立範囲: 新しい状態、所有権、期限、回収、復旧、ホスト固有入力、外部コマンドの解決を導入する計画では、正常系と主要な境界条件を計画単体から復元できる粒度で書き、当該機構を設けない案との比較と採用根拠を書く
- 観測・診断出力の成立範囲: 集計値、レポート、ログなど消費主体が判断に使う出力を新設又は拡張する計画では、出力の消費主体とその主体が出力から確定する判断を列挙する。判断ごとに必要な分解軸を出力項目へ対応付ける
- 追加する制約の成功経路: 計画が新たに追加する拒否条件、受理する入力値の縮小、容量・件数制限、権限強化、既存機能の利用不可化を列挙し、現行実装で成功する利用シナリオを失う場合は公開契約変更としてユーザー合意の根拠を書く
- 判定・分類・写像・振り分け・ステータス又はエラー種別を変更する計画では、変更する分岐へ到達する入力集合を対象実装から列挙し、入力ごとの変更前後の結果と、結果を変えない入力の不変性を固定する検証を書く
- 検査又は処理の到達性を完了条件にする計画では、対象が処理対象集合へ入った事実と、到達後の結果を別の観測値で判定する。指摘0件、成功件数、終了コード0、欠落・除外・skipの不在のいずれも、それだけで到達の根拠にしない
- 検索結果を完了条件へ用いる計画では、検索の入力、対象パス、パターン及び検索対象の最終本文を記録し、いずれかが変化した場合だけ再検索する。網羅性を主張する場合は、母集団を定める述語と除外条件を計画へ書く
- 間接的に作用する既存機構: 明示的な変更対象としない既存の判定・遮断・順序制御の機構へ間接的に作用する場合は、当該機構の設計根拠を記録した箇所から成立条件を抽出し、計画の変更が当該条件を崩さないことを書く
- 新しい実行主体・提供者・プラットフォームの追加: 既存機能へこれらを追加する計画では、候補方式の選定前に既存正常系を実測し、消費主体が観測する入力、出力、UI、処理単位、終了条件、後続処理への接続と新経路との対応を書く。新経路で維持できない差異だけをユーザー合意へ送る
