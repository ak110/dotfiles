# 計画ファイル作成基準

本書は`~/.claude/plans/*.md`の全項目を起草・実行レビューの契約とする。
読込時点は起草者が`agent-toolkit:plan-mode`、レビュー担当が`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`の読込表に従う（所在参照）。
保存・参照は`plan-file-storage.md`、復元型の変更と保持・不変性・完全復元は`plan-restoration-contracts.md`、構造検証は`plan-structure-check.md`が定める。

計画は要求漏れを防ぐ実装・実行レビューの共通基準と、記録・中断後の再開用の内部資料であり、ユーザー承認は不要である。
要件の追加判断なしに実装へ着手できる要件・外部仕様とし、`agent-basics:writing-standards/references/writing.md`「読み手別の追加注意点」のエージェント向け文書の基準に従う。
一般設計・コーディングは方針とキーワードで示し、変更対象、確定要件・外部仕様、入力、期待結果、異常系、受入条件、固有の検証コマンドを具体化する。
実装手順・関数分割・制御フロー・修正後全文などは実行時のコードで確定し、実装不良はテスト、要件・外部仕様の充足と過剰設計は実行レビューで判定する。

`ユーザー`・`エンドユーザー`は`agent-toolkit/rules/01-agent.md`「役割分担」に従い、ユーザーは計画の要求・指示・合意・確認回答を示す人である。
「消費主体」は人間、コード、委譲元エージェント、CIなど成果物を利用・検証する主体を指す。

計画を構成するファイル群は次の呼称で区別する。

| 呼称 | 実体 |
| --- | --- |
| 計画ファイル | `<計画名>.md` |
| 計画ファイル（バグ） | `<計画名>.bugs.md` |
| 実行レビュー指摘管理表 | `<計画名>.exec-review.tsv` |
| 計画バンドル | 計画ファイルと、同じステム名の付属ファイル（計画ファイル（バグ）、実行レビュー指摘管理表など）の一式 |

## 計画ファイルの構成

起草や更新の前に現行の作業契約を確認し、`share/work-contract.md`「工程境界での要求と成果の確認」に従って、計画の対象と維持する対象が当初の目的と現在の要求に一致するかを確かめる。要求が変わったら作業契約へ反映し、計画凍結後は既存のレビュー指摘管理表と`review_contract`の原本を保持する。

H1の主題に続けて、次のH2見出しを順に置く。

1. `## 概要`
2. `## 実施内容`
3. `## 要件・外部仕様`
4. `## 恒久化・リファクタリング`
5. `## 変更履歴`
6. `## 検証`
7. `## 公開工程`
8. `## 進捗ログ`

任意名のH3見出しは`## 要件・外部仕様`と`## 変更履歴`の配下だけに置き、H4以下は使わない。
事実・数値・要約は1箇所に集約し節名で参照する（努力目標。矛盾防止）。規範の適用範囲は文書パス・節名で示す。

関連WIはファイル名・1行要約を記し、確定済みの目的・要件・原因分析・範囲・方式・成立根拠を参照する。
共通参照は読込表に従い指定箇所・ユーザー記入欄を読み、固有本文と採否・計画を確定する。
完成状態は目的・反映内容・原因分析・補足条件から導く。任意節・引用位置の省略だけで再起草・再調査しない。
計画で変更対象の分解・外部仕様・受入シナリオ・テスト・検証コマンド・恒久化・リファクタリング・公開工程を具体化する。
WIの再導出は`関連WI: なし`・対応節欠落・現物との乖離確認時に限り、影響項目だけに行う。乖離の事実・結論を`## 変更履歴`へ記録する。人間由来の要求範囲変更は`agent-toolkit:wi-standards`「由来と承認」、原因分析の乖離は「バグ調査」で扱う。母集団・QとC・D・適用レイヤー・完了判定の`agent-toolkit:bugfix`の`references/root-cause-analysis.md`への不適合も後者に含む。

キューにない素材の原文とユーザーの回答全文は計画外入力の原本として保持し、調査、起草、初回レビュー、再レビューの各工程へ原文の参照を渡す。計画本文へは全文を転記しない。変更履歴に記録するユーザー発言は同節の書式に従う。

実装着手前の指摘対応・要件追加・方針変更は各節へ統合し、最終結論を残して経緯を`## 変更履歴`へ書く。
`ユーザー指示`・`人間由来のWI`の`実施内容`欄は、`agent-toolkit:review-standards`の`references/reviewee.md`「安全な修正」に従って原文を保ち、修正案を別行へ加える。
実装着手後は計画ファイルを変更しない（以下「計画凍結」）。実装中に確定した要件変更と、記述の不整合に採った解釈はレビュー指摘管理表に記録する。実行工程で直すと実行レビューの指摘になり、不要な往復が生じるためである。例外は`## 進捗ログ`への追記だけとする。
凍結後に検証条件を訂正するときは、「検証と公開工程」の訂正済み検証表に反映する。

## 概要と計画メタ情報

全体像・目的・対象範囲の順に簡潔に書き、変更時は全体を書き直す。
`wi-standards/references/drafting-completion.md`「既存証拠の再利用」に従う。

直下のH3見出しは`### 計画メタ情報`だけとし、項目と順序は「初回起草の雛形」に従う。コロンはASCIIの`:`とし、後に半角スペースを1つ置く。`関連WI`と`作業種別`以外の値はバッククォートで囲む。計画ファイル（バグ）を作る場合だけ、末尾に``- 計画ファイル（バグ）: `~/.claude/plans/__PLAN_STEM__.bugs.md` ``を加える。

- `作業種別`は`バグ対応`か`通常変更`とする。バグ対応の要求単位が1件でもあれば`バグ対応`とし、計画ファイル（バグ）にはバグ対応の要求単位の項目だけを置く。`## 検証`の`変更範囲の検証`は全要求単位の変更対象を覆う
- `関連WI`には入力のAWIとUWIのファイル名を1件1行で書き、コロンに続けて1行要約を添える。入力WIがなければ`- 関連WI: なし`とする
- `対象リポジトリ`は、計画構造の自動チェックツールへ渡す`--work-dir`のGitルートと同じ値にする（`agent-toolkit:process-wi`のレーンでは専用worktreeの絶対パス）

## 実施内容

完成条件の転記前に`agent-toolkit:wi-standards`の`references/awi-body.md`「完成条件」で目的上の必要性と由来を判定し、不要条件の除外根拠を採否記録に残す。
明示要求や必要な品質の変更は既存の確認手順へ渡す。

後続要求単位は`部分採用`の残りも含め`移管`の別行にし、計画確定前に登録済みWIのファイル名を根拠へ書く。
登録予定は未登録として扱う。
実施しない単位は`不採用`・`対象外`、回答待ちは`保留`とする。

`## 実施内容`には`実施内容`、`由来`、`採否`、`根拠`の4列表を置き、要求単位と実施範囲が分かる概念単位で書く。
AWIは原則1ファイル1行とし、実装手順やテスト項目は`## 要件・外部仕様`へ書く。
競合するWIの組合せと採った対応は`実施内容`へ書き、見送る除外項目と現状を保つ保持項目も行にする。

`由来`列は`人間由来のWI`、`エージェント由来のWI`、`ユーザー指示`、`エージェント提案`のいずれかとする。

- WI由来の行は、区分名、半角スペース、半角丸括弧で囲んだWIファイル名の順に書き（例: `エージェント由来のWI (20260831-000000-001.md)`）、`関連WI`と一致させる。区分の判定は`agent-toolkit:wi-standards`「由来と承認」に従う
- 計画構造の自動チェックツールがWI本文から読む明示的な由来は、本文末尾の厳密なH2見出し`## ユーザーコメント`とUWIの`## 回答`の2つであり、`source`属性を持つWIの行をそれ以外の明示的な由来で`人間由来のWI`とする場合は、ファイル名の後に半角スペースと`[対話由来]`を付ける。逐語引用や関連計画の記録などを使う場合は、判断の根拠を`## 変更履歴`に記録する。引用位置の計数だけを理由に再調査しない。`source`属性を持たないWIの行に注記は要らない
- `ユーザー指示`はユーザー自身の発話で確定した内容に、`エージェント提案`はエージェントが立案した指示で確定した内容に使う

`採否`列は`採用`、`部分採用`、`不採用`、`充足済み`、`保留`、`対象外`、`移管`のいずれかとする。`充足済み`は、既存のコミットや実装で要求がすでに満たされ、追加の実装が要らない場合に使う。

`根拠`列には、実施しない範囲と理由を、他の参照先を見ずに分かるように書く。

- `エージェント提案`と`エージェント由来のWI`の行には観測可能な根拠を書く。計画担当が範囲を変えずに採用するWIの行は、非空の`## 反映内容と反映先`または旧形式の非空の`## 適用範囲`を参照して`-`とできる。範囲や採否を変える場合はその理由を書く
- `人間由来のWI`と`ユーザー指示`の行には、採否にかかわらず原文の要求単位ごとに、原文の該当箇所と、実施範囲へ採用するか除外するかを対応付けた分解を書く（起草者の判断だけで作業範囲が縮むのを防ぐため）。WIの`## 反映内容と反映先`に要求単位ごとの対応があれば、踏襲する旨と計画で採否を変えた単位だけを書く。原文の全要求単位を開放性を保ったまま受け入れる`採用`行に限り、根拠を`-`としてよい
- 原文が例示表現（「など」「例えば」「〜も」など）で示した開放的な集合を限定的な列挙へ絞った行は`部分採用`とし、絞った対象と理由を書く
- 対話の内容を複数のWIへ分けて起票した場合は、各WIへ割り当てた要求単位を採否の母集団とし、他のWIへ割り当てた単位とそのファイル名も併記する（部分採用の判定には含めない）。どのWI単独でも達成を確認できない共通事項（全体目的、数値目標、調査方針など）はその旨だけを書く。どのWIにも割り当てずに除外した要求単位は`部分採用`とする
- `充足済み`の行と、充足済みの範囲を含む`部分採用`の行には、充足を確認した実装箇所かコミットと確認手段を書く。ユーザーから報告された不具合を充足済みとする前に、報告された呼び出し手段と操作手順で対象を実際に動かして期待どおりの結果を確かめる（コードの読解や既存テストの確認だけで充足済みとしない）。根拠のコミットが報告日時より前なら、デプロイ済みのバージョン、操作手順、実行環境など報告時との差を調べ、確認結果と未特定の範囲を書く。調査が終わっていない行は`充足済み`にしない
- 計画の確定前に完成条件を変更・除外するメインの技術判断を受けた場合は、対象AWI、旧条件、新条件または除外範囲、技術的制約、保持する要求、`メインの技術判断`と根拠を書く。判断の境界は`review-loop-coordination.md`「技術判断で外せる完成条件」に従う。後続のレビューと統合はこの記録で処理し、実装着手後の判断はレビュー指摘管理表に記録する
- 大規模な反復作業では、ユーザーが示した低負担な方法や既存の一括処理（`agent-basics:writing-standards/references/notation-rules.md`「表記の一括置換」など）を代表的な対象で試す。作業件数と読込・レビュー・検証・統合の負担を比べ、採った方式と理由を書く。試行と費用比較の詳細は証拠資料に保存する

人間由来のWIの要求を全部または一部不採用とする行は、`agent-toolkit:wi-standards`「由来と承認」に従ってユーザーの確認を得る（確認が要る範囲縮小と、事後報告で済む裁量の境界も同節に従う）。
ユーザーがAWIの`## ユーザーコメント`やUWIの`## 回答`に作業担当者宛ての質問を直接書いた要求単位は、回答をUWIに記録してユーザーへ返す工程を`## 実施内容`に置く（AWI本文へ転記された質問は対象外とし、同節に従う）。

## 要件・外部仕様

`## 要件・外部仕様`には固定H3見出し`### 受入シナリオ`を置き、ほかは任意のH3見出しで分けてよい。仕様や設計の確定前に、変更対象の成果物の消費主体、利用目的、結果を受けた判断や行動を特定する。
`agent-toolkit/rules/01-agent.md`「QCDと3段判定」に基づき、明示された要求と当然満たすべき要件から期待結果を導き、次の各項目に反映する。内部的な変更やエージェント向け文書も、利用場面で必要な粒度で書く。

- 要件と、消費主体が観測する外部仕様（入出力、表示、公開契約、状態遷移、分岐条件、異常系、運用手順）
- 変更対象のファイルと識別子、変更する仕様（契約）、生成と配布の流れ、直接影響範囲。同じ値や挙動を生む別の発生源（以下「別発生源」。デフォルト値、プリセット、設定ファイル、環境変数、別の呼び出し手段、同じ操作を制約する他の規定など）も、保持先、利用先、エンドユーザーが観測する結果まで追い、該当しないものは理由を添えて除外する。多数の対象に同時に作用する挙動（共通CSSクラスのレイアウト、関数や設定のデフォルト値など）を変える場合は、その挙動を前提とする指定を検索で網羅し、変更後も同じ結果になるか確かめる（手元のデータでの測定は代わりにならない）。機能の追加や統合で成果物の役割が変わる場合は、名称、利用案内、ナビゲーション、運用ログ、配布用メタデータ、既存テストなど意味が変わる箇所も網羅する
- 完了条件。消費主体が観測できる成果と、合否を判定する観測値かコマンドを、他の記述を参照せずに実行できる形で書く
- テストを新設・変更する場合は、保証する契約と検出する主な失敗様態。期待値は要求仕様や契約から導く（選定と導出は`agent-basics:writing-standards/references/testing.md`に従う）
- 事象を起こさないことを求める要求では、発生件数0件を客観的に観測する手段
- エンドユーザーが観測できる公開インターフェース（設定キー、CLIオプション、環境変数、サブコマンドなど）を新設する場合は、新設の理由と、既存のインターフェースやデフォルト値の変更では目的を達成できない理由
- ユーザー確認の回答（公開範囲を含む）と、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文からの具体化を要する軸」の判定結果
- 実行環境の動作条件を前提とする設計方針では、実機で再現を確かめた典拠
- 永続化されるデータや増え続けるデータを扱う場合は、保持期間、容量上限、上限到達時の外部仕様、保守の契機と所有者、長期的な動作条件の検証方法（基準は`agent-basics:writing-standards/references/design-time.md`に従う）

`### 受入シナリオ`には`シナリオ | 由来 | 消費主体と入口 | 利用目的と後続行動 | 操作 | 期待結果 | テスト`の7列の表を置く。旧6列表（利用目的の列なし）は保存済みの計画ファイルを読むときだけ受理する。

- `消費主体と入口`には結果を受け取る主体と呼び出し手段を、`利用目的と後続行動`には利用の目的と結果を受けて判断・実行することを書く。`操作`には具体的な入力値や初期状態を、`期待結果`にはその利用場面と有効な要求から導いた結果と検出する失敗を書く。実装着手前に、この対応からテストを選べる程度まで具体化する。`由来`にはWIの完成条件、逐語引用した要求単位、ユーザー指示の該当箇所などを書く
- `## 実施内容`に`採用`か`部分採用`の行があれば、人間由来の各要求単位と、「実施内容」で必要性を評価した後の各WIの有効な完成条件を1つ以上の受入シナリオ行に対応付ける。
  除外した条件は採否記録の対象条件と根拠を参照し、残る有効条件で完成を判定する。採用行がなければ本文を`なし`とする
- `テスト`には、公開された呼び出し手段（コマンド、画面操作、API、フックなど）を通じて同じ契約違反を検出する結合テストかE2Eテストの名前を書く。同じ操作と期待結果で各要求の合否を判定できる場合に限り、複数の要求を1行にまとめてよい。「一連の完成条件を後でテスト化する」のような参照だけの記述は具体化の完了にならない。自動テスト化が難しいシナリオに限り、その理由と、手動観測の入力値、操作手順、合否基準を書く
- 手動観測は、実装担当者が専用worktree内の成果物へ直接実行できる入力と操作で定め、公開、配布、稼働中の`atk wi process-loop`への反映の後にしか得られない観測を統合後へ先送りしない。WIの完成条件そのものが公開後にしか観測できない場合の判定は、実行レビュー担当者が`agent-toolkit:review-standards`の`references/exec-review-recording.md`に従って行い、計画ファイルには公開前に再現できる代替観測を置く。`atk wi process-loop`など本番の常駐プロセスから起動される対象は、`agent-toolkit:check-execution`の`references/acceptance-scenarios.md`「常駐サービスの公開前の観測」に従う
- 操作、障害注入、擬似故障、自動終了の失敗などを含むシナリオは、同書の「検証資源の分離」に従って実行環境と利用の調整方法を定める
- 処理時間など負荷や並行状況で変わる測定値は、`agent-toolkit:wi-standards`の`references/awi-body.md`の完成条件と同じく、同じマシンで同時に実行する対照群との比較で書く

完了条件、受入シナリオ、手動観測で文書（規範、配布原本、設計記録、ガイド、コメントなど）の文意を判定するときは、同じファイルから転記した文字列の有無や、部分文字列・行単位の正規表現の一致だけで合否を決めない。文意は、実装を通じた結果、他の定義との整合、検証コマンド、実行レビュー、該当節の正確な読解（対象ファイル、見出し、根拠の文の引用と判定結果を記録する）で総合的に判定する。文字列検索は、精読する候補の抽出と、見出し、設定キー、パスなど行構造で一意に決まる実体の有無や件数の確認に使う。

変更の種類に応じて次も書く。

- 既存の外部仕様や内部規約を変える場合: 変更前の仕様を固定値で検証している既存テストなど、自動チェックの改廃方針
- 公開された呼び出し手段を置き換えるか廃止する場合: 新しい手段だけで同じ利用シナリオを最後まで完遂できることの検証（存在確認、モック、部分的な疎通確認、古い手段を併用した確認では代わりにならない）
- 禁止規定や制約を新設する場合: 既存の箇所へ遡って適用するか、今後の変更にだけ適用するか
- 規範、エンドユーザー向け文書、メッセージ文面などを変える場合: 変更対象の規約、該当ファイルと見出し、置換の対象範囲。文面は実行工程で確定し、文面の確定自体が要件の場合（ユーザーが指定した場合など）に限り言語指定付きのコードブロックで書く

直接影響範囲とは、変更した定義、文言、パスなどを参照元、呼び出し元、生成元、期待値のいずれかとして持ち、連動して直す必要がある箇所の全体を指す（単独の「影響範囲」が指す操作の副作用の範囲とは別の語）。変更前の識別子を名前で参照していなくても、変更前の挙動を前提とする既存の指定も含む。実行処理の変更点だけでは網羅できないため、変更前の値や識別子（変更対象の呼び出し手段名を含む）の固定文字列検索、変更ファイルの周辺テストからの探索、共通の入出力（通知、生成物、設定など）からの追跡を組み合わせて特定する。仕様の内容を変える場合は、その仕様が読み書きする保持先（列名、フィールド名、ラベル、設定キー、ファイル名など）の名前も検索語に含める。

- 外部から観測できる文言を変える場合: 変更前の文言を期待値に固定しているテストを文言そのものの検索でも特定し、対象ファイルに含める。新設するテストの根拠は、同じファイルからの転記ではなく独立した仕様から得る
- ファイルを改名、移動、廃止する場合: 変更前のパスを固定文字列で検索し、文書、規範、コード、設定、テストの参照元を網羅する（隠しディレクトリも漏れない検索条件を使う）
- 仕様や概念の意味を変える場合: 変更前の意味を表す語句を、設計書、エンドユーザー向け文書、エージェント向け文書、docstring、コメント、データモデルのカラムコメント、生成物の入力元などから探す。語句の一致だけで判別できない場合は、意味を区別する文脈条件と併せて判定する

特定した直接影響範囲は変更対象ファイルに含めるか、含めない場合は理由を直接影響範囲の記述欄に書く。

完了条件の書き方:

- 増減の方向や数値目標を置く場合は、基準値、目標値、再実行できる測定手順を書き、再現性を確かめられる客観的な指標で合否を判定する
- コミットのOID（ハッシュ値）はrebaseで変わるため固定文字列で書かず、判定時点の作業ツリーから解決する
- 一致0件を合格とする条件は、`<検索コマンド>; test "$?" -eq 1`のように0件のとき合格となる形で書く（努力目標）
- 件数を期待値とする検索条件は、見出し、定義、設定キーなど判定対象の実体の行構造に合わせて絞り、起草時に同じ条件で測った件数を期待値にする（努力目標）。見出しの検索は行頭と行末を固定して数える

## 恒久化・リファクタリング

`## 恒久化・リファクタリング`の直下には`### 恒久化`と`### リファクタリング`だけをこの順に置く。どちらにも後続の担当エージェントが実装や検収で使う明確な結論を書き、検討の経緯や詳細は証拠資料に残す。

恒久化とは、将来にも適用すべき方針、選定基準、却下理由、制約、前提条件などを、今後の判断工程で読まれる場所へ保存する作業を指す。今回の変更で直接実装する内容と計画ファイル自体の記録は候補から外す。

- `### 恒久化`には`知見`、`出所`、`反映先`、`根拠`の4列の表を置き、知見1件を1行で書く。反映する知見がなければ表を置かず、対象がない旨を1文で書く（調査範囲や0件の理由は証拠資料に残す）
- `出所`には知見の由来（関連WI、確認への回答、エージェントの提案など）、`反映先`には記録先のファイルと節名を書く（反映せず計画内にとどめる知見は`計画限り`とする）。`根拠`には反映が必要な理由と反映先の選定理由、または外部へ反映しない理由を書く
- 反映先は、その知見を要する判断の際にエージェントがその文書を実際に読むかで選ぶ。自動チェックツールへ反映する場合は、チェック失敗時にエージェントが見る位置に制約の理由を併記する
- 反映を確定した知見は`## 実施内容`の表にも行として計上し、反映先で適用する仕様や置換の境界は`## 要件・外部仕様`に書く
- バグ対応では、関連WIの`## 原因分析`や`## 反映内容と反映先`、または計画ファイル（バグ）の該当行を参照して原因と対応策を対応付け、本表にはそれらで扱っていない追加の知見だけを書く

リファクタリングは`agent-toolkit/rules/01-agent.md`が定める付帯作業であり、今回の変更で必要になる既存箇所の見直しを実装と同時に行い、成果物全体の設計品質を保つ。

- 検討対象は、本計画で変更・新設する成果物の変更後ファイル全体、参照・呼び出し・読込表で結び付く関連成果物（定義、呼び出し元、既存テスト、生成・配布手順など）、`## 実施内容`で新設・分割する構造、`### 恒久化`の反映先とする
- 観点と判定基準は`agent-basics:writing-standards/references/design-heuristics.md`「設計品質の劣化確認」に従う。設計の劣化を是正する箇所や、併せて整理すれば類似処理・責務・記述の分散を解消できる箇所は、`対象`、`現状の問題`、`対応`の3列の表に1行ずつ書く（対象がなければ表を置かない。記入例は「初回起草の雛形」）
- WIを入力とする計画でも、WI本文の調査結果と判断根拠に設計品質劣化の評価がなければ、WIで確定した実現方式を同節の基準で評価する。旧形式の対応節は`agent-toolkit:wi-standards`の`references/awi-body.md`冒頭に従う。劣化があればその是正を`## 実施内容`に計上する
- エージェント向け文書を新設・改訂する計画では、`agent-basics:writing-standards/references/agent-documents-additions.md`「文書記述量の管理」を確認する。同じ文書への変更全体についてファイルサイズの上限、責務の範囲、読込の時点、既存記述との重複などを比べ、整理の結論を書く
- 本計画で行うリファクタリングは`## 実施内容`の表に行として計上する。テストの更新、直接影響範囲の同期、生成物の再生成など実装に付随する作業は`## 要件・外部仕様`に書き、`## 実施内容`の行にしない
- 同じ根本原因を持つ類似箇所の見直しは、作業種別を問わず`agent-basics:bugfix`の`references/root-cause-remediation.md`「類似見直し」の母集団と「類似見直しと再発防止の完了」の判定基準に従う。通常変更の計画では結果を`### リファクタリング`に記録し、専用の見出しは設けない
- 本計画の変更範囲外で是正の必要も生じない既存の不備を見つけた場合は、`agent-toolkit:bugfix`を起動し、`agent-toolkit/skills/bugfix/SKILL.md`「問題を見つけたときの対処」に従う

## 変更履歴

`## 変更履歴`には、初版の作成経緯、実装中の要件変更、方針転換などを見出しと地の文で記録する（表形式や履歴IDは使わない）。

- 記録するユーザー発言は、`### ユーザー発言<1から始まる連番>`のH3見出しの下に、原文を変えない`text`コードブロックと、その発言で確定した現在の結論を書く。`ユーザー指示`由来の行を`採用`か`部分採用`とした計画では、`### ユーザー発言1`と空でない`text`コードブロックを1件以上必ず置く
- 記録対象は、計画の目的、対象範囲、外部から観測できる結果、実行上の制約、承認状態を変える、実際に届いたユーザーメッセージの逐語引用に限る。委譲先エージェントでは、委譲プロンプトや追加メッセージのうち`<forwarded-user-input>`で囲まれた逐語テキストだけを対象とする（タグの扱いは`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」に従う）
- ユーザー発言以外の経緯は、内容が分かる任意のH3見出しの下に書く
- ユーザーの発話から導いた要求範囲を書く場合は、`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`「原文の保持と取り込み」の記録書式に従う。原文の逐語と出所、該当する具体例、追加事項、承認出所を明記した除外事項を記録する。`## 実施内容`の要求単位ごとの分解と`部分採用`の規定も適用する

## 検証と公開工程

受入と通常検証の比較・統合は`../../check-execution/references/verification-scope.md`に従う。

完成条件と検証手段を具体化するときは、`agent-toolkit:wi-standards`の`references/awi-body.md`「完成条件」の自己観測と未確認範囲の規定を適用する。

`## 検証`には、`区分`と`検証コマンド`の2列で`変更範囲の検証`の1行だけを持つ固定表を置き、変更対象に応じた検証（対象ファイルを限定したformat、lint、対象テストなど）を書く。リポジトリ全体の検証とCIの判定は後続の公開工程で行う。過去の計画の旧名「近接検証」の1行表、旧2行表、旧名を含む実装単位表の列は読み取り互換のために受理するが、新規作成と計画改訂では現行形式で書く。

- 検証の対象は変更ファイルとその直接影響範囲に限り、ファイル単位で指定する（努力目標）。直接影響範囲の分類と範囲は`agent-toolkit:check-execution`の`references/verification-scope.md`に従い、選んだテストファイルや検証単位をコマンド引数に明記する。直接影響範囲のうち検証から外すものは、理由を直接影響範囲の記述欄に書く。検証表は起草時点の選定なので、実行者が実行直前に同書に沿って実差分から補正する
- タスクランナーのターゲット単位でコマンドを分けて書く（努力目標。失敗したターゲットだけを再実行できるようにするため）
- 表のセルには、1つのインラインコード（code span）に1つの完全なコマンドを書く。複数のコマンドは`<br>`で区切り、説明は表の外に書く。パイプライン、リダイレクト、環境変数の代入などシェル固有の処理は実行可能なスクリプトファイルへ移し、そのスクリプトを実行する引数配列（argv）を書く（統合時に`atk lane integrate`がmanifestの`verification`へargv配列として渡し、シェルを介さず直接実行するため）
- 実装担当者は対象のworktreeで各コマンドを順に標準実行する。1つが失敗しても残りを実行し、各コマンドの終了コードと出力を個別に確かめて合否を判定する

計画凍結後に検証条件を訂正した場合は、レビュー指摘管理表の現在の結論を反映した全コマンドを別ファイルへ保存し、「訂正済み検証表」とする。このファイルには本節と同じ`## 検証`の固定表を1つ置き、計画メタ情報は置かず、凍結した計画ファイルの検証表全体を差し替える内容を書く。
訂正後の検証は訂正済み検証表のコマンドで行う。計画ファイル、訂正の結論、訂正済み検証表の対応と絶対パスは引き継ぎ記録に書き、実装、実行レビュー、統合の各工程へ渡す。引き継いだ内容は確実に保持し、訂正済み検証表を更新したら更新後の条件で検証を最初からやり直す。

計画・訂正済み検証表・実行記録には、`../../check-execution/references/verification-scope.md`に従って選んだ起動形を記す。対象到達・完了・終了状態・診断を確かめる。

`## 公開工程`には、合意した公開範囲と、コミット・プッシュ後に行う操作（PR/MRの作成とタイトル・本文の指定、リリース作成、タグ付けなど）を書く。公開範囲の確認が不要で公開後の固有操作もない計画は`なし`とする。

## バグ調査

作業種別が`バグ対応`の計画では、原因分析を記録した関連WIの`## 原因分析`を参照する。
計画ファイル（バグ）を作るのは、入力WIがない計画（`関連WI: なし`）か、起草時にWIの原因分析を訂正・追加した計画に限る（`## 原因分析`を持たない登録済みAWIを処理する計画もこの追加に当たる）。訂正・追加では対象のバグ単位だけを完全な表で書き、実態との乖離の観測結果と導いた結論を`## 変更履歴`に記録する。
計画ファイル（バグ）には計画の主題のH1見出しを置き、バグ単位ごとのH3見出しの下に原因分析表と調査表をこの順に置いて全セルに値を書く（見出しはH1とH3だけ、各H3配下の表はこの2つだけとする）。行名、列名、並び順、統合・分割の規則、恒久化の参照規約は`agent-toolkit:bugfix`の`references/analysis-records.md`「原因分析の記録先」に従い、類似箇所の見直し結果も同所に沿って調査表に記録する。
`check_plan_file.py`は、作業種別が`バグ対応`でメタ情報に`計画ファイル（バグ）`行を持つ計画について、ファイルの実在、計画ファイル名（stem）との一致、計画ファイル（バグ）の構造を検証する。`関連WI`が`なし`のバグ対応計画ではこのメタ情報行を必須とする。

## 進捗ログ

`## 進捗ログ`は中断後に再開するための大まかな記録で、`日時`、`完了した工程`、`結果・特記事項`の3列の表を置く。初回起草時はデータ行を入れない。

`結果・特記事項`列には、後続の工程や再開するエージェントが使う情報だけを書く。途中の観測経過や後続で参照しない一時ファイルのパスは省き、コミットは一意に特定できる短縮OIDで書く。

- 追記は`atk run-script plan-progress -- <計画ファイル> --completed-step <完了した工程> --result <結果・特記事項>`で行う（日時はスクリプトが生成する）
- 実装開始後は、再開時に次の工程を判断できる情報（コミットの完了、変更範囲の検証結果、実行レビューの完了、全体の完了判定、専用worktreeの絶対パス、専用ブランチ名、回収するリソースなど）を順に追記する
- WI実装コミットの記録、取得、履歴改変後の引き継ぎは`agent-toolkit:commit`の`SKILL.md`「WI実装commitの対応」に従う（対応記録ファイルに短縮OIDと対象AWI群を保存し、進捗ログには固定3列表の行だけを追記する）
- `agent-toolkit:process-wi`のレーン処理では、統合工程の行の`結果・特記事項`に`レーン稼働時間: <秒数>秒`を記録する。秒数は、メインエージェントが最初のレーン担当者を起動した直後に保存・伝達した`レーン開始時刻`から、`atk lane integrate`のGit統合が成功して最終化の最初の操作を始める直前までの総経過時間で、待機、レビュー、統合前の失敗と復旧を含み、担当セッションが交代しても最初の開始時刻を起点にする。秒数と完了時刻は同CLIが算出した値を最終化コマンドの引数参照から取り、手作業で仮の数値を入れない
- 同じ行に`予測補正記録: 対象リポジトリ=<識別子>; 選定元=<出力先の絶対パス>; レーン=<識別子>; 完了時刻=<時差付き時刻>; 補正前実装秒=<秒数>; 補正前統合秒=<秒数>; 補正係数=<係数>; 総経過秒=<秒数>`を記録する。選定元は1回のprocess-wi実行を一意に識別する。補正前の2値は選定結果の`レーンの所要時間`の`補正前の実装秒数`と`補正前の統合秒数`から、係数は最上位の`見込みの補正`の`係数`から取る（追加のWIがある場合はレーンの累積予測値を使う）。補正前の欄には事前の予測値と確認できた値だけを書き、復元できない過去の記録は不明として次回の集計分母から外す。同じレーンの複数の計画と、同じ実行・レーンの記録を持つ複数のAWIは、同じ値で1件と数える。計画ファイルを作らないレーンでは同じ書式の記録を対象AWIの本文へ保存する。セッション内の引き継ぎ記録には保存先を書く
- 完了報告を作るエージェントは、完了条件ごとに達成の根拠か未達の理由を進捗ログの最終行に記録する

再開するエージェントは、進捗ログの最終行、`## 概要`の目的、`## 変更履歴`のユーザー発言、完了条件、レビュー指摘管理表の回答を確かめてから次の工程を決める。計画ファイルと指摘管理表の内容が食い違う場合は、指摘管理表の回答を現在の正式な結論とする。

## 要件の成立性

`## 要件・外部仕様`は、消費主体が得る結果とそれを損なう要因を計画ファイルと関連WIから把握でき、正常系と主要な異常系の再現手順、既存の正常動作手順への影響を評価できる粒度で書く。

仕様の整合性を確かめる主な観点は、データの送受信、条件分岐、制約、機能廃止、外部から観測される挙動、配布形態である。共有されるインターフェース仕様（契約）は呼び出し側と提供側の双方を同じ計画内で確定し、変更する分岐の入力パターンと変更前後の動作結果を正しく対応付ける。
制約の追加などで既存の正常動作シナリオが成り立たなくなる場合は、ユーザーとの合意内容と根拠を記録する。機能廃止に伴う完成条件、チェックリスト、テストコードの更新方針、外部挙動を実機で確かめた根拠、プロジェクト規範が定める配布手順、バージョン更新、同期対象ドキュメントの修正も漏れなく計上する。
