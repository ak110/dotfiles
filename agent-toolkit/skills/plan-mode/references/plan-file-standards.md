# 計画ファイル作成基準

本書は計画ファイル（`~/.claude/plans/*.md`）の成果物契約の単一の正本である。
計画担当は初版の起草前に本書を全文読み、全項を満たす計画を作成する。
レビュー担当は本書の各項を点検の基準として同じ本文を読む。
計画ファイルへの要件の追加・変更は本書へ行い、レビュー用のタスク文書へ検査項目を追加しない
（起草側が知らない検査基準は、初回レビューの不合格と修正往復を構造的に生むため）。

本書でいう`ユーザー`は計画の要求・指示・合意を与え、確認経路で回答する主体、
`エンドユーザー`は成果物を利用する主体、`消費主体`は成果物ごとに定まる利用・検証の主体を指す。
`利用者`は既存形式の値や引用本文を除き、新規の説明ではこれらの語へ具体化する。

## 計画ファイルの完成条件

計画は`<計画名>.md`（計画ファイル（メイン）。人間・メインエージェント向け）と
`<計画名>.detail.md`（計画ファイル（詳細）。実装者向け）の2ファイル構成とする。
両ファイルはstem一致（`<stem>.md`と`<stem>.detail.md`）で対応付ける。
ファイル間の参照は計画ファイル（メイン）から計画ファイル（詳細）への片方向だけとし、計画ファイル（メイン）`### 計画メタ情報`の
`実装詳細`行（後述）が参照を持つ。

計画ファイル（メイン）はH1の主題に続けて次のH2を固定順で置く。

1. `## 概要`
2. `## 実施内容`
3. `## エージェント判断`
4. `## 提示素材`
5. `## 変更履歴（計画時）`
6. `## 検証区分`
7. `## 終端工程`
8. `## 進捗ログ（実行時）`

新規作成・改訂では上記の括弧付き見出しを使う。既存計画の`## 変更履歴`と`## 進捗ログ`は読み取り互換として受理するが、構造検査は新見出しへの移行をwarningで案内する。

計画ファイル（詳細）はH1を持たず、次のH2を固定順で置く。
`## バグ調査結果`は作業種別がバグ対応の場合だけ先頭へ置き、他のH2は全計画で必須とする。

1. `## バグ調査結果`（バグ対応のみ）
2. `## 恒久化・リファクタリング内容`
3. `## 実装資料`
4. `## 完了条件`

読者の割当: メインエージェントは計画ファイル（メイン）だけを読む（統合後検証と完了報告の直前に計画ファイル（詳細）の
`## 完了条件`を追加で読む）。実装担当（実装担当）は計画ファイル（詳細）だけを受け取り、素材・要求の復元が
必要な場合に限り計画ファイル（メイン）を追加取得する。計画レビュー担当・計画担当は両ファイルを扱う。
自由な見出しは`## 実装資料`配下のH3以下に限る。

計画ファイルのパスを一般に言及する文書・frontmatter（キューの`plan_file`）・完了報告・進捗参照は、
計画ファイル（メイン）のパスを指す。実装詳細が必要な読み手はstemから`<stem>.detail.md`を導出して計画ファイル（詳細）を辿る。
これにより計画パスを一般言及するだけの文書は個別改訂を要しない。

改訂前に作成済みの旧形式（単一ファイル、次表の9節）は読み取り互換として受理するが、
新規作成では生成しない。対応する`<stem>.detail.md`ファイルの実在により二ファイル形式と旧単一ファイル形式を分け、
二ファイル形式ではメインのcanonical固定H2により新規書式と旧二ファイル形式を分ける。旧単一ファイル形式の固定H2順序を次表に示す。
`## バグ調査結果`は作業種別がバグ対応の場合だけ置く。

1. `## 概要`
2. `## 実施内容`
3. `## 提示素材`
4. `## 変更履歴`
5. `## バグ調査結果`
6. `## 恒久化・リファクタリング内容`
7. `## 実装資料`
8. `## 完了条件`
9. `## 進捗ログ`

旧形式では人間向け固定領域を`## 概要`から`## 変更履歴`まで、実装者向け領域を
`## 変更履歴`直後から`## 進捗ログ`直前までとする。旧形式の計画は実行時も単一パスを
`plan-impl-executor`・実装担当・レビュー担当へ渡し、`## 検証区分`・`## 終端工程`を持たないため
検証区分を起動前に指定せず、現行の検証契約（レーン内で計画記載の全検証）を適用する。

新規作成と新規改訂では合成IDを持たない書式だけを生成する。
既存の単一ファイル形式と素材・要求IDを持つ二ファイル形式は読み取り互換として受理し、構造検査は新規書式への移行をwarningで案内する。
旧形式のID、表及び逐語素材を新規計画の生成契約へ再利用しない。

旧二ファイル形式（対応する`<stem>.detail.md`が実在するが、メインが新規固定H2を備えない形式）は、旧単一ファイル形式とは別の読み取り互換として判定する。旧二ファイルの変更履歴に残る旧ID（`C-`・`H-`形式など）、`R<round>-<旧系統名>`形式の旧レビューID及び旧系統名は、既存計画の読み取りに限り受理し、移行warningだけを出力する。既存の旧ID・旧系統名・旧表は改訂せず、新規計画へ生成しない。
旧単一ファイル形式は対応する`<stem>.detail.md`が無い形式として別に判定し、既存の`C-<3桁連番>`形式と`conformance`系統を読み取り互換で受理する。新規書式のメインはcanonical固定H2を備え、履歴のIDと系統名を`R<正の整数>-<plan-review|plan-conformance|independent>`へ限定する。旧二ファイル・旧単一の互換値を新規書式の検査へ混入させない。

変動しやすい事実は名前付きのSSOTを1箇所だけ持ち、他の箇所は参照又は変動しない要約を使う。
新規作成・新規改訂の提示素材はフィードバック/TBDの正本ファイル名だけを保持し、フィードバック原文全文を計画へ転記しない。
キューにない素材の逐語本文・回答全文は計画外の明示入力として調査、起草、初回レビュー、再レビューへ保持し、計画には転記しない。
既存計画の旧形式（素材IDと`text`フェンス）は読み取り互換として受理するが、新規生成しない。
その他の同一事実、数値、要約も計画全体で1箇所だけに置き、他の箇所はファイル名か節名で参照する。
目的、実施内容、検証条件のように役割が異なる記述は、同じ対象を扱っても重複に含めない。
例外は、旧形式の読み取り互換と監査記録となる変更履歴の行だけとする。

外部の可変な対象に属する事実（フィードバックキューのactive・processing集合と依存関係、`HEAD`、作業ツリーの差分、並行する実行主体の進行状況）は、集合の列挙ではなく取得コマンドと判定規則として書く。
規範上の要求で列挙する項目は取得時刻と取得コマンドを併記し、列挙の完全性を主張しない。
計画の入力基準又は監査基準として意図的に固定する値（変更前実測値、ユーザー合意で固定した対象集合）は本規定の対象外とし、固定値として書く。
実装時にだけ確定する技術値で、方針、公開契約、実装成立性を左右しないものは、計画段階で仮値を固定しない。
計画ファイル（詳細）へ権威ある設定・実測・対象バージョンと導出方法を記録し、実装時に確定した値と解決方法を完了報告へ返す。
実行環境の差で確定できない場合は、代替の判定方法か計画の再起草条件を計画ファイル（詳細）へ記録する。

同一計画内の表・節から機械的に導出できる件数、割合、合計及び分類数を本文へ複製しない。
件数を根拠として必要とする場合は、対象集合、取得コマンド、集計条件、判定時点を明記し、正本と別の固定値にしない。
フィードバックキューはファイル名の列挙を正本へ複製せず、`atk mq list`・`atk mq show`の取得結果を
重複排除、依存判定、件数照合の入力とする。共有ファイルを変更する項目でも、対象が無関係であることを
本文の取得コマンドと判定規則で確認できる場合は、ファイル名を固定の依存へ追加しない。

役割が異なる複数箇所へ同じ事実値、手順又は禁止事項が現れる場合は、いずれかを修正する時点で計画全体を検索して全出現箇所を洗い出し、同じ修正回で同期する。
自己監査で訂正した値にも同じ扱いを適用する。

レビュー指摘、要件追加又は方針転換を計画へ反映する際は、対象節の末尾への追記を既定とせず、既存記述と統合して現在の結論だけが残る形へ節を編集する。
反映の経緯は`## 変更履歴`が正本として記録する。

### 計画ファイルの分割

1つの入力バッチから複数の要求単位を計画する場合は、対象ファイル集合の重なりと検証境界の独立性を主判定として計画ファイルの分割を決める。
対象ファイル集合が重なる要求単位と、同じ検証コマンドでしか合否を確定できない要求単位は、同じ計画ファイルへまとめる。
対象ファイル集合が重ならず近接検証が独立に成立する要求単位の組は、別の計画ファイルへ分ける。
1つの計画ファイルが扱う要求単位は5件前後を補助目安とし、件数を主判定にも固定上限にもしない。
同じファイル群へ集中する小規模な項目は目安を超えてもまとめ、対象ファイル集合と検証境界が独立していれば目安に満たない件数でも分ける。
計画ファイルの分割はレビューの単位とし、1ラウンドの対象を小さくして反復の所要を下げる。
分割後の各計画ファイルを1レーンへ割り当て、1計画1専用worktreeで実装する。
分割した場合は、判定に用いた対象ファイル集合と検証境界を各計画の`## 実装資料`へ記録する。

### 概要と計画メタ情報

`## 概要`直下へ全体像、目的、対象範囲の順で地の文を書く。
変動しやすい集計値や対象範囲は複製せず、実施内容又は名前付きSSOTを参照する。
`## 概要`は、計画を初めて読む読者が現在の計画の全体像を把握できる短い要約として保つ。
経緯、旧方針及び指摘の記録は`## 変更履歴`と`## 提示素材`を正本とし、`## 概要`へ複製しない。
要件の追加、方針転換又はレビュー反映で内容が変わる場合は、変更部分の追記を重ねず、節全体を現在の計画に合わせて書き直す。

`agent-toolkit:process-feedbacks`が通常型フィードバックを計画へまとめる場合、計画対象集合は`pick-feedbacks.md`が返した新しい実装変更の同一レーン集合に従う。
複数の統合計画へ分割した場合は、各計画へ割り当てた担当フィードバックファイルを`## 実施内容`へ原則1ファイル1行ずつ記録し、全計画の担当ファイル集合が合わせて計画対象集合を過不足なく被覆する。
分割しない場合は計画対象集合を担当ファイル集合とする。
各フィードバック行へ由来、採否、採用範囲、実施しない範囲及び理由を統合する。
部分採用では採用範囲と実施しない範囲を同じフィードバック行へ記載し、要求別の採否詳細は内部採否記録を正本とする。
概要に独立したバッチ採否表は置かず、採否と方針を同じ実施内容へ統合する。

直下のH3は`### 計画メタ情報`だけとし、次の5行を固定順で置く（旧形式は末尾の`実装詳細`行を持たない4行）。
コロンはASCIIの`:`、コロン後は半角空白1字とし、`作業種別`以外の値はバッククォートで囲む。

```md
- 起動経路: `<skillまたは起動経路>`
- 対象リポジトリ: `/absolute/repository/path`
- 作業種別: バグ対応
- ベースコミット: `<作成時点の参照値>`
- 実装詳細: `<計画名>.detail.md`
```

`作業種別`は`バグ対応`又は`通常変更`とする。
`実装詳細`は計画ファイル（詳細）のファイル名（stem導出値と一致する`<計画名>.detail.md`）とする。

### 新規書式の実施内容、提示素材及び変更履歴

新規作成と新規改訂では、人間・メイン向けの判断資料へ合成IDを生成しない。`## 実施内容`には、`実施内容`、`由来`、`採否`、`根拠`の4列表を置く。
ユーザーが計画ファイル（メイン）だけで、何を実施し、何を実施しないかを判断できる概念単位で記載する。
フィードバックは原則として1ファイルを1行とし、実装手順、テスト項目、内部の分解単位ごとに行を分けない。
複数の採否を持つフィードバックは`部分採用`の1行とし、実施する範囲と実施しない範囲を`実施内容`へ併記する。

`由来`は`人間由来のフィードバック`、`エージェント由来のフィードバック`、`ユーザー指示`、`エージェント提案`又は`計画レビュー第<正の整数>ラウンド`のいずれかとする。
フィードバック由来の行は、区分に続けて正本のファイル名を括弧内へ記載する。
`計画レビュー第<正の整数>ラウンド`は計画レビューで新たに追加した行だけに使い、`根拠`のルートを
`/absolute/path/review.tsvのround <同じ正の整数>`とする。指定したTSVに同じroundが存在することを検査する。
`採否`は`採用`、`部分採用`、`不採用`、`保留`、`対象外`、`移管`のいずれかとする。
`由来`が`エージェント提案`の行だけは、`根拠`へ当該成果物の消費主体、利用シナリオ、そのシナリオが発生する条件及び当該条件を確定した観測可能な根拠を記載する。
これ以外の`採用`の`根拠`は`-`とし、採用以外の採否では実施しない範囲と理由を、別の参照を解決せず理解できる文面で記載する。
実施しない除外・保持も`## 実施内容`の行として記録し、専用の表を設けない。
対象を概念名だけで一意に特定できない場合は、曖昧な言い換えを作成せず、実在するファイルパス、識別子、コマンド名を記載する。

### エージェント判断

`## エージェント判断`は、計画担当がユーザー要求の原文から新たに具体化した判断だけを、`実施内容`、
`観測事象`、`ユーザー要求との関係`、`具体化した内容`、`根拠`の5列表へ記録する。
`## 実施内容`の`由来`が`エージェント提案`である行と、同表の`実施内容`を一対一で対応させ、対応する行を同じ順序で置く。
エージェント提案が無い場合は表を置かず、`なし`と記載する。表を置く場合は各セルを空欄にせず、同じ実施内容の観測根拠と具体化の関係を復元できる文面にする。
この節は計画担当の技術判断を監査するためのものであり、ユーザーが対象、範囲及び結果を明示した提案を同じ内容で採用した行は記録しない。

`## 提示素材`には、計画の入力となったフィードバックファイル名とTBDファイル名だけを箇条書きで記載する。
該当するファイルがない場合は`なし`と記載する。本セッションで受領したユーザー発言は提示素材へ重複して記載しない。

`## 変更履歴（計画時）`は、計画初版の作成と計画レビュー中の変更を記録する。変更の内容を判別できる見出しごとの記録とし、履歴IDを設けない。
本セッションで受領したユーザー発言は、原文を改変せず`text`コードブロックへ記録し、その発言から確定した現在の結論を併記する。
計画レビュー、方針転換及び計画修正は、起点、内容、現在の結論と同期先を自然文で記録する。
レビュー回数のようにユーザーが時系列を判別する値は、合成IDに当たらない。

### 既存形式の実施内容と合意済みの除外・保持（読み取り互換）

初版の実施内容は、提示された各素材を要件単位へ分解して列挙する。各要件は方針・概要レベルの実施内容、対象外・不採用の理由、
又は確認済みの回答のいずれか1つで被覆し、素材から計画の決定へ逆照合できる状態を保つ。
「確認済み」と宣言するだけでは被覆とせず、対象の現行値、取得手段又は実機結果を併記する。

`## 実施内容`へ`実施内容`、`採否`、`ユーザー指示との関係`、`根拠`の4列表を1行以上置く。
行は提示素材又は独立に採否を判断できる方針単位とする。
記載粒度は、ユーザーが何を、なぜ、どの方針で行うかを確認できる方針・概要レベルとする。
対象領域と変更の方向を曖昧にしない範囲で、`実施内容`セルへ実装詳細（対象ファイルのパス、実装上の識別子、変更前後の値、テスト更新、版数更新など）と、素材ID・要求ID・調査結果の項目IDなど計画内部の管理識別子は書かない。
実装詳細の正本は`## 実装資料`のファイル群別の変更説明とする。
`採否`は`採用`、`部分採用`、`不採用`、`保留`、`対象外`、`移管`のいずれかとする。
`採用`・`部分採用`の行は採用系とし、`根拠`へ採用要求IDを1件以上記載する。
`不採用`・`保留`・`対象外`・`移管`の行は非採用系とし、`根拠`へ空でない理由を記載する。`実施内容`セルには不採用等とした対象を肯定形の名詞句で書く（否定形では`採否`列と二重否定になり、不採用の意味が反転すると解釈できるため）。
非採用系の`根拠`に要求ID形式のトークンを含める場合だけ要求表への実在を検査し、不採用要求の参照を許容する。
要求表に現れない保留、移管及び対象外の項目は、実施内容表の行にファイル名と理由の要旨を書いて識別できるようにする。
`ユーザー指示との関係`は採用系の行では`指示どおり`、`具体化`、`エージェント追加`のいずれかとし、非採用系の行ではこれらに加えて`非該当`を許容する。
部分採用の行は、採用範囲と除外範囲の要点を`実施内容`セルへ書き、詳細は要求表の採用範囲と除外範囲を正本とする。
`指示どおり`の根拠は要求IDを記載し、他の値はユーザー指示との差分と必要性を記載する。
frontmatterの`source`が`agent-toolkit:process-feedbacks`の`pick-feedbacks.md`でエージェント由来と判定される提示素材は、自己生成起点として`エージェント追加`へ分類する。
外部仕様への言い換えだけの記述は用いない（`agent-toolkit/rules/01-agent.md`「役割分担」節の識別子を避ける方針より優先する）。
並行実行が起こり得る状態の更新について、取り消し・復元・再試行の方式を計画で指定する場合は、
書き込み元を識別する手段まで含めて当該方式が成立することを実装読解又は実機で検証してから書く。
検証していない場合は方式を指定せず、満たすべき契約だけを書く
（厳守規定。成立しない方式を名指しすると、実装とレビューが当該方式の枠内で条件を追加する反復を続ける）。
実施内容表と任意の合意表における`指示どおり`は、根拠に引く提示素材が対象と範囲を明示している場合に限る。
原文が問いに留まる場合は、当該素材を`指示どおり`の根拠にせず、範囲を確定する問いを確認経路へ送り、受領した回答を根拠へ併記する。
原文が提案的表現に留まる場合と、本文から提案と判定できる弱い自信の表現に留まる場合は、`指示どおり`の根拠にしない。
この場合は技術判断で対象と範囲を確定して`具体化`へ計上し、根拠へ確定の理由を書く。
提案と判定できない不確かな事実記述は、従来どおり確認経路で確定してから計画へ書く。
提案と異なる判断を確定する場合は、当該判断と理由を報告したうえで確認経路へ送り、受領した回答を根拠へ併記する。
ユーザー合意に対応する実施・除外・保持・対象範囲の変更は、対応する提示素材か確認済み回答と条項単位で照合する。
確認済み回答には、`AskUserQuestion`で受領した回答と、確認事項を記録したTBDの`## 回答`節へ記録された回答を含める。
TBDの回答有無は`atk mq show <filename> --target-repo=<repo>`が表示する`answered`で判定し、`## 回答`見出しの直後に空行と1行のHTMLコメント以外の行があることを回答済みの条件とする。
対象・条件・適用範囲が拡大若しくは縮小する場合は、計画へ書く前に確認へ送る。
規範又は設定の反映先を選ぶ判断は技術判断とするが、選んだ反映先が統治する対象集合が指示の名指し対象を超える場合は適用範囲の拡大に当たり、計画へ書く前に確認へ送る。
対象範囲が指示に明示されている場合は、`agent-toolkit/rules/01-agent.md`「ユーザー発話の解釈」節が定める対象集合の技術判断による採用を適用しない。
実測に基づく内部実装の技術判断は、この照合の対象外とする
（厳守規定。ユーザー合意に対応しない範囲変更を防ぐため）。
ユーザー合意を根拠に撤去・削除する行は、合意文の語ではなく実測で確定したパス及び識別子の集合で対象を書き、
合意範囲との差（拡大又は縮小）が生じる場合は計画へ書く前に確認へ送る
（厳守規定。未合意の削除と撤去漏れを防ぐため）。
既存の手順、検証手段又は完了判定を廃止若しくは変更する計画では、当該手順名、コマンド名及び契約語句を変更対象ファイル群と参照元へ検索する。
廃止後に成立しなくなる完成条件、チェックリスト及びテストは`## 実装資料`のファイル群別の変更説明と`## 完了条件`へ計上する。

実施へ対応しない除外又は保持の合意がある場合だけ、直下へ`### 合意済みの除外・保持`を置く。
`合意内容`、`対象と箇所`、`素材・要求参照`、`確認方法`の4列表を1行以上置く。
対象と箇所には編集で変動しにくいファイル、節、frontmatter項目を書く。
`素材・要求参照`には素材IDと要求IDを1件以上ずつ書き、確認方法には差分か成果物から不変を判定する手順を書く。
実施、除外、保持が混在する合意は条項単位へ分解する。
実装後と各レビュー反映後に、実装を統括する主体が確認方法を実行し、差分が必要な場合は確認へ送る。

`### 合意済みの除外・保持`へ書く行にも、実施内容表と任意の合意表に共通する`指示どおり`の判定を適用する。
`### 合意済みの除外・保持`へ書く行は、素材・要求参照が示す要求の採用範囲か除外範囲を明示している場合に限る。
原文が提案的表現、又は本文から提案と判定できる弱い自信の表現で範囲を一意に定めない場合は、技術判断で対象と範囲を確定する。実施を伴わない除外・保持は`### 合意済みの除外・保持`へ記録し、`合意内容`へ確定した内容と技術判断による確定である旨、`対象と箇所`へ確定した対象範囲、`素材・要求参照`へ素材IDと要求ID、`確認方法`へ不変を判定する手順を書く。提案と異なる判断を確定する場合だけ、範囲を確定する問いを確認経路へ送り、受領した回答に対応する素材IDと要求IDを`素材・要求参照`へ記載する。

### 既存形式の提示素材（読み取り互換）

`## 提示素材`では素材表の直後に要求表を置き、入力の出所、引用範囲、実装要件、要求単位の採否と範囲を構造化する。
素材表は`素材ID`、`種別`、`キューID`、`投入元`、`引用範囲`の5列とし、素材IDは`P-[0-9A-Za-z][0-9A-Za-z_-]*`を受理する。
種別は`フィードバック`、`利用者指示`、`利用者合意`、`参考素材`、`処理対象資料`、`起動事実`のいずれかとする。
フィードバックだけはキューIDに`[0-9]{8}-[0-9]{6}-[0-9]{3,}\.md`形式のファイル名を置き、その他は`非該当`とする。
フィードバックの引用範囲は`本文全文`、直接対話の旧形式の`利用者指示`は投入元`本セッション`・引用範囲`全文`、起動事実は投入元`常駐自動起動`・引用範囲`非該当`とする。
直接対話では、実行環境上で実際のユーザーメッセージを旧形式の`利用者指示`素材として記録する。
キューにないユーザー指示、ユーザー合意、参考素材及び処理対象資料の逐語本文・回答全文は、計画外の明示入力として工程間で保持する。
受信した起動文全体を機械的に転記せず、委譲元が人間由来として明示した出所と引用範囲だけを素材表へ記録する。
ユーザー合意は本セッションなら`全文`、`AskUserQuestion`又は`TBD:<filename>#回答`なら`回答全文`とし、委譲元が明示した出所と引用範囲もそのまま記録する。参考素材と処理対象資料も明示された出所と引用範囲を記録し、投入元から位置付けや認可を推定しない。

新規素材IDは、フィードバックファイル名昇順と後続入力の受領順で、並列調査の開始前に一括割当する。
既存IDのうち`P-[0-9]{3,}`へ完全一致するIDだけから最大数値を求め、次の値を3桁以上の10進表記で使う。
該当する既存IDが無い場合は`P-001`から始め、`P-999`の次は`P-1000`とする。
非数値や混在形式の既存IDは維持するが採番集合へ含めず、初回割当後の素材IDを再採番しない。

要求表は`要求ID`、`素材参照`、`実装に必要な要件`、`採否`、`採用範囲`、`除外範囲`、`根拠`の7列とする。
要求IDは`R-<素材ID>-<3桁連番>`とし、素材ID全体を名前空間に含め、同じ素材IDでは`001`から欠番なく採番する。要求表は要求ID昇順に置き、素材参照は実在する素材IDを1件以上、昇順かつ重複なしで記録する。
初回抽出では各素材の本文内出現順で連番を割り当て、複数素材が共同で新しい要求を確定する場合は素材参照の最小IDを名前空間に使う。
既存素材から要求を追加する場合は原文位置にかかわらず同じ名前空間の最大連番+1を使い、既存要求IDを維持する。
要求を分割する場合は先頭の維持部分へ既存IDを残し、追加部分へ記述順に末尾の連番を割り当てる。
要求を統合する場合は既存行とIDを残し、採否と採用範囲か除外範囲を同じ判断単位へそろえ、統合用IDを生成しない。
回答や資料が既存要求を具体化または変更する場合は、要求IDを維持して素材参照へ該当する素材IDを加える。
採否は`採用`か`不採用`だけとし、`部分採用`と`保留`は要求表へ置かない。採用行は採用範囲を、不採用行は除外範囲を記録し、反対側は`非該当`とする。
同一ファイルに採用要求が1件以上ある場合は、不採用要求も要求表へ残し、採否理由と除外範囲を計画へ記録する。
同一ファイルの要求集合の一部だけを採用する場合も、ファイルは採用要求を含む採用項目として扱い、不採用要求だけを理由にファイル全体をrejectしない。
ファイル単位の終端と計画対象集合は`agent-toolkit:process-feedbacks`の`pick-feedbacks.md`による項目別採否と処理区分に従う。
素材表の旧形式の`フィードバック`、`利用者指示`、`利用者合意`は要求表から1件以上参照し、参考素材、処理対象資料、起動事実は要求を直接持たない場合も受理する。
実施内容表の採用系の`根拠`と合意表の`素材・要求参照`には対応する要求IDを記載し、実装担当が原文を再取得せず要求と範囲を復元できるようにする。
実施内容表の非採用系の`根拠`は空欄にせず、理由を記載する。
実装を伴わず終端工程だけで完了する採用要求は、`採用範囲`を`終端工程のみ`で始める。
当該要求は`## 実施内容`の`根拠`と`### 合意済みの除外・保持`の`素材・要求参照`による被覆の対象から除く。

フィードバック由来素材がある場合、計画担当と初回計画レビュー担当だけが、同じ対象リポジトリかつ同じ条件の全キューIDを
`### 一括取得の管理対象一時領域`の手順で対象リポジトリごとに1回取得する。
終了コード0で全項目が出力された場合だけ本文を採用し、構造化情報と照合する。出力順序と本文境界は`atk mq show`のCLI契約とし、
非0終了時は一括出力全体を使わず要求した全項目を単数取得する。該当素材が無い場合は取得を省略する。
終了コード2では標準出力の部分結果を使用せず、計画作成と初回レビューのいずれも開始しないで入力不足として起動主体へ返す。
単一項目の調査、警告・エラー後の当該項目だけの再取得とTBD回答確認は、
`atk mq show <filename> --target-repo=<repo> --skip-pull`を単数形で1回実行する。
調査担当は担当ファイルを1回取得して要求IDと素材参照を返し、再レビュー、実装担当、実装レビュー担当は計画を正本として原文を取得しない。
旧形式の素材ID、`text`フェンス、`原文参照`列は読み取り互換として受理するが、新規・改訂では生成しない。旧形式を含む計画はCLIがwarningを出力する。

### 一括取得の管理対象一時領域

同一対象リポジトリの複数ファイル名を同一工程で取得する時点で、`agent-toolkit:add-feedback`の一括取得契約を読み、同契約の手順を完了させる。
計画作成経路では、終了コード2の部分結果を使用せず、計画作成又は初回レビューを開始しないで入力不足として起動主体へ返す。

### 既存形式の変更履歴（読み取り互換）

`## 変更履歴`へ`ID`、`起点`、`指摘内容`、`採否・現在の結論`、`同期先`の5列表を置く。
起点は`ユーザー発言`、`レビュー指摘`、`方針転換`のいずれかとする。
ユーザー発言行の指摘内容には素材IDだけを書き、他の起点では具体的な指摘内容を書く。
委譲元が構成した指示、及び出所を持つ処理対象資料を起点とする行は`方針転換`とし、`ユーザー発言`は`### 提示素材`の出所分類で人間由来と確定した素材だけに使う。
起点`レビュー指摘`の行は系統・ラウンド単位で1行とする。
`ID`は`R<正の整数>-<系統名>`形式のラウンド識別子とし、系統名はレビュー表の正規値`plan-review`、`plan-conformance`、`independent`のいずれかにする（例: `R3-plan-conformance`）。系統名の各部分は小文字英字又は小文字数字で構成し、ASCIIハイフンで連結する。同じ系統・ラウンドを異なるID表記で重複させない。旧二ファイル形式では、既存の`C-`・`H-`形式、`R<round>-<旧系統名>`形式の旧レビューID及び旧系統名を読み取り互換として受理する。旧単一ファイル形式では、既存の`C-<3桁連番>`形式と`conformance`系統を読み取り互換として受理する。いずれの旧形式も新規生成せず、新形式の検査へ互換値を適用しない。`指摘内容`は当該ラウンドの主要な指摘の要約、`採否・現在の結論`は採否の集計と主要な結論、`同期先`は当該ラウンドで変更した節とする。
指摘原文、個別の採否、対応内容の正本はレビュー指摘管理表とし、変更履歴へ複製しない。
管理表の列契約は`agent-toolkit/scripts/_review_table.py`とそのテストを正本とする。
起点`ユーザー発言`と`方針転換`の行は、現行どおり事象単位で1行とする。
現在状態の正本は後続の各節とし、本表は解決済み論点を識別する監査記録とする。

### 検証区分と終端工程

計画ファイル（メイン）`## 検証区分`は`区分`、`検証コマンド`の2列2行の固定表とし、
`レーン内検証`行には変更対象に近い最小検証（対象ファイル限定のformat・lint・対象テスト）のコマンドを、
`統合後検証`行にはフル検証（`make test`等）のコマンドを書く。
計画担当が初版で提案し、計画レビューが妥当性を照合する。
既定の割当は「変更ファイル限定検査＝レーン内、全体検証＝統合後」とする。
計画が理由付きでレーン内フル検証を要求する場合（性能測定、他計画と独立に合否確定が必要な検証など）は
その指定を優先する。

計画ファイル（メイン）`## 終端工程`はcommit・push後に実行する操作（PR/MRの作成とタイトル・本文、リリース、タグ付けなど）
だけを列挙する。終端工程が無い計画は`なし`と書く（空欄は不可）。

### バグ調査結果

作業種別が`バグ対応`の場合だけ`## バグ調査結果`を置く。
バグ調査の本体は、計画付属ファイル`~/.claude/plans/<計画stem>.bugs.md`へ分離する。
計画本文の`## バグ調査結果`直下には、`- バグ調査ファイル:`に続けて分離先の絶対パスを1行だけ置く。
バグ調査ファイルには、計画主題に対応するH1と、バグ単位のH3ごとの`項目`・`内容`の2列表を置く。
各表は`agent-toolkit:bugfix`の根本原因分析契約にある固定14行を記載し、行名、順序、統合分割規則及び恒久化・類似見直しの参照契約を維持する。
起草担当はバグ調査ファイルを保存した直後に読み戻して内容を確認し、実装担当とレビュー担当は読み取り専用で着手前に実在を確認する。
欠落時は起草工程へ差し戻す。
`check_plan_file.py`は作業種別が`バグ対応`で分離先を参照する場合に、実在、計画stemとの一致、分離先の構造を検査する。
分離先はバグ単位のH3を1件以上含み、各H3に固定14行表を置き、`内容`セルを空欄にしない。
本文内に固定14行表を持つ旧形式は読み取り互換として受理する。

### 恒久化・リファクタリング内容

`## 恒久化・リファクタリング内容`直下へ次のH3を固定順で置く。

- `### 恒久化`
- `### リファクタリング`
- `### 類似見直し`

`なし`、`不要`、`該当なし`だけの記載は認めず、対象、比較、確認結果及び理由を書く。

恒久化では、計画作成の対話・確認・調査で得た知見のうち当該計画固有でない恒久的な知見を、
完了後は参照されなくなる計画ファイルではなく、恒久的に参照される成果物へ書き残す判定を確定する。
次の知見を候補として列挙し、明示的な再利用性、外部公開契約、必要な設計理由又は検証済みの反復欠陥に該当するものだけを恒久化する。

- ユーザーが指示・発話又は確認への回答で示した方針・要件・合意事項のうち、当該計画固有でないもの
- ユーザーが確認への回答（`AskUserQuestion`の回答とTBDの`## 回答`節を含む）に付した判断基準・選択理由・補足
  （選択そのものより選定理由が将来の意思決定で再利用されるため）
- エージェントが確定した判断のうち、他の計画にも適用できる選定基準・指針
- 却下した代替案のうち、将来の意思決定で再利用できる判断根拠
- 調査で確定した制約・前提・外部仕様の理解
- 計画が新設又は変更する判定・遮断・順序制御の機構が依存する前提と、前提が崩れた場合に生じる観測事象（反映先は当該機構の実装箇所又はdocstringとし、コードだけで意図が自明な処理へ説明コメントを一律追加しない）

次の情報は候補から除く。

- 当該計画の実施内容・検証条件・進捗など、計画ファイル自身が記録する情報
- セッション固有の事情・一時状態・個人名指し
  （`../../writing-standards/SKILL.md`「ユーザー入力素材の取扱い」と同じ扱い）
- 既存の恒久成果物が既に記載する内容（参照の補強で十分な場合は反映しない）

通常変更の恒久化は、`知見`、`出所`、`反映先`、`根拠`の4列表とし、知見ごとに1行で記載する。
候補が1件も無い場合は、`知見`へ`候補なし`、`出所`へ確認した範囲、`反映先`へ`計画限り`、
`根拠`へ0件と判断した理由を書いた1行だけを置く。
バグ対応の恒久化の記載範囲は本節末尾のバグ対応の規定に従う。
出所には提示素材ID、確認への回答、エージェント判断など知見の由来を書く。
反映先には反映先のファイルと節を書き、反映しない知見には`計画限り`と書く。
根拠には反映の必要性と反映先の選定理由、又は反映しない理由を書く。
反映先の比較前に、`agent-toolkit:session-review`の根本原因と反映先の比較契約をReadで全文読み、定められた比較順に従う。
反映を確定した知見は方針レベルの行として`## 実施内容`へ計上し、反映先へ書く文面はファイル群別の変更説明で確定する。
実装者の解釈が分かれないよう、自然文の指示ではなく転記できる確定文面を書く。

リファクタリングは実装と同時に行う周辺是正とし、本来の対応で理想的な状態が崩れる場合は、
それを補う是正まで完了して計画の完了とみなす。
計画対象の変更を契機に発見した、本来の対応に内包されず採否を実施内容から独立して
判断できる既存の不備を検討する。
検討の範囲は調査工程で読む変更対象とその定義・参照・呼び出し元・既存テスト・生成・配布経路とする。

- コードでは、対象モジュールの責務肥大化、類似処理の分散、ファイル・関数の肥大化、
  計画対象の変更で陳腐化する既存実装・既存テストなどの既存不備
- 文書では、追記に対する既存節の粒度不整合、変更後の内容に合わない節構成、
  同一トピックの分散などの既存不備
- その他、計画作成中に発見した既存記述の陳腐化・誤り・不整合・テスト不足・観測不能な挙動

検討結果は対象、現状の問題、対応、本計画に含めるかの4行表とする。
本計画に含めるリファクタリングは方針レベルの行として`## 実施内容`へ計上する。
実装・検証の成立に必須のテスト更新、参照元同期、生成物同期などの実装付随作業は、`## 実装資料`のファイル群別の変更説明へ置く。
実装付随作業の検証条件は`## 完了条件`へ置き、`## 実施内容`へ個別の作業行を追加しない。

規範文書へ新しい節又は項目を追加する計画では、`agent-toolkit:agent-standards`の
`文書記述量の管理`に従い、既存記述の重複統合と削減を検討する。
作業中に問題を発見した場合は`agent-toolkit/rules/01-agent.md`の`問題を見つけたときの対処`の経路に従う。
通常変更の類似見直しは母集団、点検観点、該当箇所の3行表とし、該当箇所は実測結果を根拠に列挙する。
列挙から導出できる件数は書かない。
バグ対応では、恒久化と類似見直しの双方でバグ調査ファイルの対応行を正本として参照し、同じ説明を複製しない。
バグ対応でも、バグ調査ファイルのいずれの行にも対応しない知見・変更
（恒久化・リファクタリングで新たに導入・変更する機構を含む）は各表へ記載する
（厳守規定。同じ原因による既存欠陥を計画対象から漏らさないため）。
バグ調査ファイルに対応しない知見・変更が無い場合は、恒久化の4列表を置かず参照のみとする。

### 実装資料と完了条件

`## 実装資料`配下のH3以下へ実装資料、変更内容、実行方法を記載する。
変更対象と変更内容はファイル群別の変更説明を正本とし、同じパス集合の一覧を複製しない。
別コンテキストの実装者が不要な再調査をせず、現行コードとの照合を開始できる粒度で書く。

`## 実装資料`直下へ`### 実装単位`を必ず置き、次の5列表へ1行以上の実装単位を記載する。

新規書式の`### 実装単位`には、`実装単位`、`目的`、`先行依存`、`統合順`、`近接検証`の5列表を置く。
`実装単位`には、同じ表の中で一意となり、変更対象又は達成する結果を具体的に判別できる説明的な名前を記載する。`U-001`のような合成IDは生成しない。説明的な名前へASCIIカンマを含めない（`先行依存`のASCIIカンマ区切りと曖昧になるため）。
`先行依存`は、依存する行の`実装単位`名を原文どおりASCIIカンマで区切って記載し、依存がなければ`なし`とする。
各行を独立した成果として検証でき、対象ファイル集合、commit及び近接検証がそれぞれ分離できる場合だけ1つのcommitへ対応させる。共有成果又は検証を手順差だけで分割せず、`統合順`による実行順序は維持する。
説明的な名前が長くなる場合も、定義のない短い概念名へ言い換えず、実在するファイルパスや識別子を含めて対象を一意にする。

計画ファイル（詳細）は、新しいコンテキストの実装者が、計画時の対象範囲と判断を推測せず実装できる具体性を持たせる。
計画時の調査で変更範囲を確定した場合は、検索・読解の対象範囲、実行したコマンド、範囲へ影響した一致結果と不一致結果、各結果を変更対象か対象外とした理由を記録する。
検索した事実や件数だけでは調査結果とせず、実装者が同じ対象集合を復元できるファイルパスと識別子を残す。
出力全体が大きい場合は、原出力を複製せず、対象集合を欠落なく列挙した結果と再実行できるコマンドを記録する。

規範、エンドユーザー向け文書、設定断片又はメッセージなど、文面自体が変更成果物となる場合は、修正後の確定文面を言語指定付きコードブロックで記載する。
「趣旨を追記する」「整合させる」など、実装者が文面を再設計できる指示だけで確定文面を代替しない。
既存文面の一部を維持する場合は、置換境界と維持部分をファイルパス、見出し、識別子で一意に示す。

計画ファイル（詳細）へ記載した変更対象は、生成元、参照元、呼び出し元、配布先及び既存テストの検索結果と照合する。
該当しない接続先は、検索対象と不一致結果を根拠として対象外であることを記載する。
計画レビューは、文面の細かな好みではなく、この情報を欠くと新しいコンテキストで対象漏れ又は別解釈が生じるかを基準に具体性を判定する。

以下の表とID規則は、既存計画の読み取り互換だけに適用し、新規生成では使わない。

| 単位ID | 目的 | 先行依存 | 統合順 | 近接検証 |
| --- | --- | --- | --- | --- |
| U-001 | 1つの原子的なcommitで達成する目的 | なし又は先行する単位ID | 1 | レーン内で実行する検証コマンド |

既存形式では単位IDを`U-[0-9]{3}`形式とし、`U-001`から欠番なく昇順に採番する。
実装単位と実施内容の対応付けは、各単位の`目的`とファイル群別の変更説明が担う。
既存形式の`先行依存`は実在して統合順が前の単位IDをASCIIカンマ区切りで列挙し、依存が無い場合は`なし`とする。
`統合順`は1から欠番なく昇順に置く。
既存形式で単一の実装単位で完結する計画も`U-001`の1行を明示する。
複数の独立した公開契約や検証境界を1つの実装単位へまとめる場合は、`目的`へ同じcommitで扱う必要がある根拠を記載する。
対象ファイル集合が重ならず近接検証が独立に成立する連続した実装単位は、1回の委譲へまとめて割り当ててよい。
まとめた場合も実装単位ごとにcommitを分け、既存形式では単位IDとcommitの1対1の対応を維持する。
既存計画に残る`対象の実施内容`を含む6列表は読み取り互換として受理し、当該列の値を検査しない。

計画へ固定する細部は、実装者が既存規範と確定済み外部仕様から安全に判断できる範囲を除く。
変数名、消費主体が観測しない文言及び局所的な制御フローは計画へ固定しない。
一方、対象ファイルと識別子、外部可視の入出力、状態遷移、分岐条件、異常系、生成・配布経路及び
合否を判定する観測値は、実装可能性を保つために計画へ記載する。

テストコードの新規作成又は変更を含む計画では、`## 実装資料`配下へテスト設計を記載する。
テスト設計を確定する前に、対象に関係する複数の利用・運用上の立場から観点漏れを点検し、対象契約に該当すると判明した失敗様態だけを既存のテスト設計へ記載する。
テストが保証する契約（検出対象とする契約違反）、想定する主要な失敗様態（異常系・境界値を含む）、
各失敗様態を検証するテストレイヤーの選択を書き、期待値は要求仕様・契約から導出して確定する。
実装の実行結果として得た出力は期待値の導出根拠にしない
（実装の欠陥ごと期待値へ固定され、契約違反を検出できないテストになるため）。
テスト対象ファイルの集合はファイル群別の変更説明を正本とし、テスト設計へ再列挙しない。
`## 完了条件`の実行コマンドは正本の集合と一致させる。

既存テストの除去、parametrize行の削除又は対象の付替えを含む計画では、対象テストごとに単独で検証している契約の有無を`## 実装資料`へ記載する。共有するテスト本体・fixture・parametrize列外のハードコード値が付替え後も成立するかを確認し、唯一の検証だった契約の除去後の担保手段を`## 実装資料`のテスト設計と`## 完了条件`へ計上する。

実装識別子の撤去又は改名を含む計画では、対象リポジトリ全体を既存テストと生成物を含めて除外指定なしで検索する。
用いた識別子、検索コマンド文字列及び一致件数を`## 実装資料`へ記録し、参照の追随範囲を実装前に確定する。

禁止規定又は制約を新設する計画では、既存の該当箇所へ遡及適用するか、今後の新規・変更箇所だけへ適用するかを
`## 実装資料`へ明記する。遡及適用する場合は、対象母集団と完了条件も記載する
（厳守規定。変更範囲と完了判定を起草時に一意にするため）。

`## 完了条件`には消費主体が観測できる成果と検証条件を書く。
共有構造検査、統合検査、対象固有のテストを区別し、同じ条件を複数箇所へ書かない。

外部コマンドの出力を合否判定に使う場合、変更前状態での事前実測は既定の手順としない。
変更後の検査で失敗を観測した時点で、実装開始時点の状態を取得できる場合に同じ判定を1回実行し、当該失敗が既存由来か本計画の変更由来かを切り分ける。
切り分けの結果は原因特定のための診断として記録し、完了判定からの免除に用いない。
変更後に観測した失敗は由来を問わず修正する。

変更前後で出力の差分を安定して識別できない検査は、合否条件から外すか、事前実測又は同等の安定した比較手段を維持したうえで用いる。
完了条件には、実在して安全に反復できる対象固有の検査だけを用いる。

計画担当が実行して結果を確認していない環境構築・後始末の手順列を完了条件へ書かず、手段の確立は実装工程へ委ねる。
完了条件へは合否を判定する観測値と、検査が満たすべき制約（実装本体を経由すること、同一ロジックを複製した検査で代えないこと、主作業ツリーの追跡ファイルとユーザー設定を変更しないこと、必要な稼働環境）を書く。

計画が増加又は削減の方向や数値目標を定める場合は、完了条件へ基準値、目標及び再実行できる測定方法を書く。
各レビューラウンド後に実装を統括する主体が再測定し、累積結果が合意へ逆行する場合は追加採用を止めて確認へ送る。
数値目標を合否ゲートへ置く前に、計画担当が起草時に測定手段を実行して再現性を確認する。
実行環境の条件（モデル、思考量、利用できるツール、system prompt、入力データなど）を変更前後で同一に固定できず再現性を確認できない指標は、合否ゲートにしない。
この場合は対策の帰結を機械判定できる構造条件（工程数、呼び出し回数、外部コマンドの実行有無など）を`## 完了条件`へ置き、実測値は参考値として`## 実装資料`へ記載する。
再現性を実行して確認できる指標では、従来どおり数値を合否ゲートへ置く（努力目標。再現できない測定を合否条件へ置くと、測定手段の不成立がラウンドごとに新たな指摘として成立し、計画が収束しない）。

実行済みの検査には実行したコマンドと観測結果を併記し、環境構築・後始末の実行方法は`## 実装資料`へ書く。
完了条件へ書くコマンドは、計画内の他の記述を参照せずそのまま実行できる形で書く。
対象パスを`同ファイル`・`上記`などの指示語や省略形で代替せず、各コマンドへ対象の完全なパスを記す。

`## 完了条件`と`## 実装資料`へ書く探索コマンド（grep、git grep、lsなど対象を変更しない検索）は、起草時と各修正回にそのまま1回実行する。
実行がエラー終了でないことを確認し、対象パスの実在は当該コマンドの終了コードと別の手段で確認する
（`ls`は存在しないパスへ終了コード2を返し、`git grep`は存在しないパス指定と無一致をいずれも終了コード1で返すため）。
併せて、出力が計画の対象集合列挙を過不足なく被覆することを確認する。
ここでの確認はコマンドの実行可能性と対象被覆の確認であり、変更前状態での合否の事前実測を既定の手順としない規定は変更しない。

改称、除去又は語彙統一を目的とする探索コマンドは、旧語の異形、略記及び派生形を含む語幹単位のパターンを用いる。
実在した異形文字列を入力とする1回の実行で対象異形を捕捉できることを実証し、実行したコマンドと出力を計画へ記録する。

計画が機構（担当種別、返却status、動作モード、ファイル書式、設定キーなど）を新設又は変更する場合は、`## 実装資料`へ機構ごとの接続先契約の対応表を置く。
列は`機構`、`受け渡し文書`、`返却statusの受領一覧`、`担当種別・入力・出力の定義先`、`機械検査・同期テスト`、`完了条件・エンドユーザー向けガイド`とし、各セルへ対象のファイルと識別子、あるいは該当しない理由を書く。
機構の新設・変更が無い計画では本表を省略する。

### 進捗ログ（実行時）

`## 進捗ログ（実行時）`は実装開始後のcommit単位の受領、実装レビューの収束、完了判定を記録する最後のH2とし、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。
旧形式では`## 進捗ログ`は実装開始後のcommit単位の受領、実装レビューの収束及び完了判定を記録する最後のH2とし、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。
起草時は内容行を要求しない。
実装開始後は呼び出し元が各commit単位の受領時と実装レビュー収束時に追記する。
実装開始時は、1つの計画ファイルへ1つの専用worktreeを対応付け、絶対パス、作成時のHEAD完全OID、所有主体、回収対象を記録する。
結果・特記事項にはcommit、検証結果、計画との差異、阻害要因を必要な範囲で書く。
完了報告を発行する主体は、報告の直前に`## 完了条件`を全文再読し、各条件の充足根拠又は未達理由を進捗ログの最終行へ記録する。
新形式の計画で同じstemのレビュー指摘管理表（`<計画名>.tsv`）が存在する場合、構造検査は表の最大`round`がこの表のデータ行数以下であることを確認する。旧二ファイル形式及び旧単一形式は読み取り互換としてこの進捗照合を適用しない。表が無い計画はこの照合を省略し、表が不正な場合は計画入力のエラーとして扱う。

### 復元・巻き戻し型の変更

過去の契約へ戻す変更と過去の契約を撤去する変更では、対象項目ごとに導入目的を調べる。
削除commitから得た項目別の対象記述と復元文面を1対1で対応させる。
維持、修正、撤去を項目別に判定し、親子階層を含む一意な現物の挿入位置と既存規定との重複を確認する。
判定結果と根拠は初回レビューの入力に含める。
復元候補ごとに、現行状態が喪失後に意図的に確立されたものかを確認する。
確認手段は当該領域の後続commit、消費主体が観測する仕様（画面表示・集計値・公開契約）及び実装コメントの参照関係とし、意図的な再設計と判定した項目は復元対象から外して判定根拠を記録する。
由来の判定はファイル単位の最終更新者ではなく、現行に残る記述は行単位の作者、失われた記述は当該記述を除去したcommitで行う。

### 計画構造検査

GFM表のセルにリテラルの`|`を含める場合は、コードスパン内を含めて`\|`と記述する。
Jinjaフィルターや正規表現など、コードとして評価される文字列も表構文の区切りと衝突しないよう同じ規則を適用する。

`skills/plan-mode/scripts/check_plan_file.py`が計画の構造と実体を計画構造検査する。
本スクリプトはPEP 723スクリプトであり、次の形で実行する。引数には常に計画ファイル（メイン）`<計画名>.md`の
絶対パスを渡す（計画ファイル（詳細）のパスを渡さない）。

```sh
uv run --script /absolute/path/to/plan-mode/scripts/check_plan_file.py /absolute/path/to/plan.md
```

対象リポジトリがセッションの作業ディレクトリと異なる場合は、
`--work-dir /absolute/path/to/target-repository`を付ける。
通常のシェルでは`${CLAUDE_PLUGIN_ROOT}`が展開されないため、読込済みの本書の絶対パスから
スキルの絶対ベースディレクトリを確定して指定する。
対応する`<stem>.detail.md`ファイルの実在により二ファイル形式と旧単一ファイル形式を分ける。
二ファイル形式では計画ファイル（メイン）・計画ファイル（詳細）の両方の節構成、計画ファイル（メイン）の`実装詳細`行の存在、
参照先パスがstem導出値と一致することを検査し、メインのcanonical固定H2により新規書式と旧二ファイル形式を分ける。
detailが実在しない場合は旧単一ファイル形式（9節）として検査する。
構造定数と値抽出は`agent-toolkit/scripts/_plan_format.py`を正本とする。
素材と要約の意味照合、根拠の妥当性、検討の実質はレビューで確認する。

## 保持・不変性・完全復元の契約

保持、不変性又は完全復元を計画の契約とし、又は確認へ送る選択肢へ書く場合は、
確定前に採用する入力形式が当該不変性を表現できるかを対象実装を読んで確認する。
併せて、保存・読込・UI・エディターなど通過する既存経路が加える変換
（再直列化・trim・strip・既定値補完・値の正規化）も対象実装を読んで列挙する。
成立しない範囲がある場合は、不変とする対象と変更を許す例外を明示した契約へ書き換えてから確定し、選択肢本文にも同じ限界を書く。
無条件の「そのまま保存」「元と一致」という表現を契約及び完了条件へ用いない。

## 要件の成立性

計画が定める変更は、書式への適合に加えて次の各項を満たす。

複数ファイル名の一括取得は`### 一括取得の管理対象一時領域`を正本として適用する。

- 要件シナリオ: 正常系、完遂範囲・順序・条件を指定する入力、主要な異常系のそれぞれについて、
  実行主体、認可根拠、状態更新の時機、失敗時の経路が計画本文から一意に定まる
- 実機再現の典拠: 設計方針の選択が外部サービス、外部API又は実行環境の受理条件に依存する場合は、
  公式資料の引用に加えて実機再現の典拠（実行条件と結果）を計画へ記載する。
  方針選択に影響しない参考記述には課さない
- 計画が実行を指示する外部コマンドについて、分岐、遮断、完了判定の入力とする挙動を確認する。
  対象は終了コードの意味、出力が相対か絶対か、オプションの導入バージョン、設定の優先順位とする。
  安全な実行、管理対象一時領域での同等再現のいずれかによる結果を典拠として記載する。
  レビュー指摘の反映で新たに追加した呼び出し、変更した呼び出しにも同じ典拠を取得する。
  公式仕様は実測条件・結果の補足に限り用いる。安全な実行、同等再現で確認できない観点は、理由を問わず未検証範囲として明記する
- 参照元の追従: 既存ファイルの変更を含む計画では、変更対象を参照する既存箇所の追従方針を記載する
- 管轄規範の追随: 変更対象ファイル群を管轄するプロジェクト側の編集規範が定める配布経路、版数更新及び
  同期先文書の追随を調査工程で確定し、該当する実装付随作業を`## 実装資料`のファイル群別の変更説明と`## 完了条件`へ計上する
- 新設機構の成立範囲: 新しい状態、所有権、期限、回収、復旧、ホスト固有入力、外部コマンドの解決を
  導入する計画では、正常系と主要な境界条件を計画単体から復元できる粒度で記載する。
  併せて、当該機構を設けない案との比較と採用根拠を記載する
- 観測・診断出力の成立範囲: 集計値、レポート、ログなど、消費主体又は別の実行主体が判断に使う出力を
  新設又は拡張する計画では、出力の消費主体と、その主体が出力から確定する判断を列挙する。
  判断ごとに必要な分解軸（対象主体別、時系列、上位順、内訳など）を出力項目へ対応付ける。
  全体値だけでは判断が確定しない場合は当該分解軸を計画へ含め、含めない分解軸には除外根拠を書く
- 追加する制約の成功経路: 計画が新たに追加する拒否条件、受理する入力値の縮小、容量・件数制限、
  ネットワーク遮断、権限強化、既存機能の利用不可化を列挙する。
  現行実装で成功する利用シナリオを失う場合は、公開契約変更としてユーザー合意の根拠を記載する
- 判定・分類・写像・振り分け・ステータス又はエラー種別を変更する計画では、変更する分岐へ到達する入力集合を対象実装から全て列挙する。入力ごとの変更前後の結果を`## 実装資料`へ記載し、結果を変えない入力の不変性を固定する検証を`## 完了条件`へ計上する
