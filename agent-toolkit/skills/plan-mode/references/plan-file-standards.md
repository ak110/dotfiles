# 計画ファイル作成基準

本書は計画ファイル（作業実体は`~/.claude/plans/*.md`）の成果物契約を定める基準文書である。
計画を起草する主体は初版の起草前に本書を全文読み、全項を満たす計画を作成する。
実行レビュー担当が本書を点検の基準として用いる場合の読込は`${CLAUDE_PLUGIN_ROOT}/share/exec-review.subagent.md`が定める。

計画ファイルは、ユーザーが実施内容と採否を判断でき、実装担当が迷わず着手できる要件・外部仕様水準の記述を持つ。
実装手順、関数分割、内部の制御構造及び改訂後の全文は実装工程が現行コードから確定する。
実装水準の欠陥はテストで検出し、実行レビューは要件・外部仕様の達成と過剰設計の有無を判定する。

本書でいう`ユーザー`は計画の要求・指示・合意を与え、確認の問いに回答する主体、
`エンドユーザー`は成果物を利用する主体、`消費主体`は成果物ごとに定まる利用・検証の主体を指す。

## 計画ファイルの保存と参照

計画は1ファイル`<stem>.md`とし、作業種別が`バグ対応`の場合だけ同じstemの`<stem>.bugs.md`を同じディレクトリへ置く。
`atk plans commit`が保存する付属ファイルは計画ファイル（バグ）と実行レビュー指摘管理表だけとする。
計画stemで始まるそれ以外のファイルは保存されず、同じ操作で作業側から削除される。
計画に属さない作業ファイルは、計画stemとは別の名前で管理対象一時領域へ保存する。
新規作成は`atk run-script plan-create --`を経由し、実装前の計画ファイルは作業root直下へ作成する。
作成処理は同じstemに属する全ファイルを排他的に確定し、読み戻しと計画構造の自動チェックに成功してからパスを返す。
stemは計画メタ情報の`起動経路`ごとに次のとおりとし、`dd`は作成日、`HHmm`は作成時刻とする。同じstemが既にある場合は作成処理が`-<小文字16進数4桁>`を付けて再試行する。

| `起動経路` | stem |
| --- | --- |
| `agent-toolkit:process-wi`のレーン | `dd-HHmm_process-wi_レーンNN` |
| `agent-toolkit:plan-mode`の直接起動 | `dd-HHmm_<日本語の簡潔な名詞>` |

作業root直下の計画ファイル名は、上表のstemに`.md`を続けた形と、保存先の正準形`dd-<名称>-<小文字16進数4桁>.md`の双方を受理する。保存先の正準形だけを満たす名前を自ら組み立てる必要はない。

`agent-toolkit:process-wi`のレーンは内部作成処理へ`--lane lane-NN`で起動文のレーン識別子を渡す。`NN`は2桁のレーン番号とし、日付、時刻、固定接頭辞及びレーン番号は作成処理が組み立てる。
この`起動経路`の日付と時刻には、作成処理を実行する環境のローカルタイムゾーンを用いる。
`agent-toolkit:plan-mode`の直接起動では、内部作成処理へ`--name <名称>`を渡す。日時接頭辞を持たない名称では作成処理がUTCの日付と時刻を組み立て、既に`dd-HHmm_`接頭辞を持つ完全stemはそのまま用いる。

計画本文が参照する計画ファイル（バグ）とレビュー指摘管理表には、固定接頭辞`~/.claude/plans/`とファイル名を使う。
新規作成では最終stemが未確定であるため、ファイル名のstem部分へ固定プレースホルダー`__PLAN_STEM__`を書く。
作成処理がこの文字列を最終stemへ置換する。プレースホルダーの値は`${CLAUDE_PLUGIN_ROOT}/skills/plan-mode/scripts/create_plan_files.py`の`PLAN_STEM_PLACEHOLDER`に従う。
接頭辞後の値はファイル名1件だけとし、パス区切り文字、`..`、シェル式、Windows区切り文字を含めない。
参照の解決では接頭辞を展開せず、参照を含む計画ファイルのディレクトリへファイル名を結合して実体を求める。
既存計画の本文に残る`$(atk config get private_notes)/`から始まる参照は読み取り互換として受理する。

計画は実行レビューの収束時点まで`~/.claude/plans`直下で更新し、収束後に`atk plans commit <作業root直下のメイン計画ファイル名>`で`private-notes/plans/yyyy/MM/`へ移動して保存する。
同コマンドは計画ファイル、計画ファイル（バグ）及びレビュー指摘管理表を同じcommitで保存する。
`agent-toolkit:process-wi`のレーンが実行レビューの収束前に終端する場合は、その終端の時点で保存する。
保存済み計画は完了した作業の記録とし、次のセッションの実装入力には新しい計画を作成する。
中断したレーンの再開は`agent-toolkit:process-wi`の`skills/process-wi/references/run-lanes.md`が定める。
計画作業rootの各計画バンドルには所有セッションの記録が付き、`atk plans list`で所有セッションと最終更新時刻を一覧できる。
自身が所有しない計画はそのまま残す。private-notesの計画ファイルの更新は`atk plans`の各コマンドで行う。

実行レビュー指摘管理表は計画ファイルと同じディレクトリへ`<計画stem>.exec-review.tsv`（`track`は`exec-review`）として置く。
計画を持たない実行レビューの表は`~/.claude/plans`直下へ置く。WIだけをレビュー基準とする直接実装では`wi-<処理開始時点の7文字以上の一意な短縮OID>.exec-review.tsv`、公開工程のCI失敗修正では`ci-<起点commitの7文字以上の一意な短縮OID>.exec-review.tsv`とする。短縮OIDは`git rev-parse --short=7 <revision>`が返した値をそのまま用いる。
前者は収束後に削除し、後者は`atk plans commit ci-<起点commitの7文字以上の一意な短縮OID>.exec-review.tsv`で`private-notes/plans/ci/`へ保存する。

本書、`agent-toolkit:plan-mode`のSKILL.md及び`${CLAUDE_PLUGIN_ROOT}/share/`配下の計画関連文書は、計画に属するファイルを次の呼称で指す。

| 呼称 | 実体 |
| --- | --- |
| 計画ファイル | `<計画名>.md` |
| 計画ファイル（バグ） | `<計画名>.bugs.md` |
| 実行レビュー指摘管理表 | `<計画名>.exec-review.tsv` |

## 計画ファイルの構成

計画ファイルはH1の主題に続けて次のH2を固定順で置く。

1. `## 概要`
2. `## 実施内容`
3. `## 要件・外部仕様`
4. `## 恒久化・リファクタリング`
5. `## 変更履歴`
6. `## 検証`
7. `## 終端工程`
8. `## 進捗ログ`

自由なH3は`## 要件・外部仕様`と`## 変更履歴`の配下だけに置き、見出しの深さはH3までとする。
同じ事実、数値、要約は計画全体で1箇所だけに置き、他の箇所は節名で参照する。
関連WIはAWI・UWIそれぞれのWIファイル名と1行要約だけを保持し、本文全文は元のWIファイルが持つ。
既存の規範の適用範囲へ言及する場合は、条文を持つ文書のパスと節名を参照する。
指摘、要件追加又は方針転換を反映する際は、既存記述と統合して現在の結論だけが残る形へ節を編集し、経緯は`## 変更履歴`へ記録する。この編集の適用時機は計画の起草と承認までとする。
承認後の実行工程は計画ファイルを更新せず（以下「計画凍結」）、実装中に確定した要件変更と、計画の記述の不整合に対して実装側が採用した解釈をレビュー指摘管理表へ記録する。
実行工程が計画ファイルを更新すると、実装済み差分の欠陥ではない記述の整備が実行レビューの指摘になり、修正の往復が生じる。
例外は`## 進捗ログ`の追記とする。中断後の再開に要する情報は計画バンドルの内側に残す必要があるため、同節の追記だけを実行工程の更新対象に残す。

### 概要と計画メタ情報

`## 概要`直下へ全体像、目的、対象範囲の順で短い地の文を書く。計画を初めて読む読者が現在の計画の全体像を把握できる要約として保ち、内容が変わる場合は節全体を書き直す。

直下のH3は`### 計画メタ情報`だけとし、次の行を固定順で置く。
コロンはASCIIの`:`、コロン後は半角空白1字とし、`関連WI`と`作業種別`以外の値はバッククォートで囲む。

```md
- 起動経路: `<skillまたは起動経路>`
- 対象リポジトリ: `/absolute/repository/path`
- 関連WI:
  - 20260831-000000-001.md: AWIの1行要約
- 作業種別: バグ対応
- 計画ファイル（バグ）: `~/.claude/plans/__PLAN_STEM__.bugs.md`
```

`作業種別`は`バグ対応`又は`通常変更`とする。
`関連WI`には計画の入力となったAWIとUWIのWIファイル名を1件1行で置き、コロンに続けてその要求の1行要約を書く。入力が無い計画では`- 関連WI: なし`と書く。
`計画ファイル（バグ）`の行は`バグ対応`の場合だけ置く。
`対象リポジトリ`は計画構造の自動チェックへ渡す`--work-dir`のGitルートと一致させる。`agent-toolkit:process-wi`のレーンではそのレーンの専用worktreeの絶対パスを書く。

1つの計画にバグ対応と通常変更の要求単位が混在する場合は、バグ対応の要求単位を1件でも含めば`作業種別`を`バグ対応`とし、計画ファイル（バグ）を置く。計画ファイル（バグ）へはバグ対応の要求単位に対応するバグ単位だけをH3として置き、通常変更の要求単位をバグ単位に含めない。`## 実施内容`は作業種別によらず要求単位ごとに行を分け、`## 検証`の`近接検証`には全要求単位の変更対象を覆うコマンドを書く。

### 実施内容

`## 実施内容`には`実施内容`、`由来`、`採否`、`根拠`の4列表を置き、ユーザーが計画ファイルだけを読んで実施範囲と除外範囲を判断できる概念単位で記載する。
AWIは1ファイルを1行とし、行の分割単位は概念単位とする。実装手順、テスト項目、内部の分解単位は`## 要件・外部仕様`が扱う。
複数のWIを扱う計画では、WI間で対象、方針又は変更内容が競合する場合に、競合する組と採用した処置をその行の`実施内容`へ書く。

`由来`は`人間由来のWI`、`エージェント由来のWI`、`ユーザー指示`、`エージェント提案`のいずれかとする。
WI由来の行は、区分に続けて半角空白1字を置き、半角丸括弧で囲んだWIのファイル名を記載する（例: `エージェント由来のWI (20260831-000000-001.md)`）。このファイル名は計画メタ情報の`関連WI`と一致させる。
2つのWI区分のどちらを選ぶかは`agent-toolkit:wi-standards`の「由来と承認」に従う。
WIファイルの本文から機械判定できない明示由来を根拠に`人間由来のWI`とする行はファイル名に続けて半角空白1字と`[対話由来]`を付け、その由来の出所と引用範囲を`## 変更履歴`へ記録する。
エージェントが構成した指示から確定した実施内容は`エージェント提案`とする。`ユーザー指示`はユーザー自身の発話から確定した実施内容に使う。

`採否`は`採用`、`部分採用`、`不採用`、`充足済み`、`保留`、`対象外`、`移管`のいずれかとする。
`充足済み`は要求が成立し、既存commit若しくは既存実装がその要求を満たすため実装を要しない場合に用いる。
`根拠`には実施しない範囲と理由が別の参照を解決せずに読み取れる文面を書く。
`由来`が`エージェント提案`又は`エージェント由来のWI`の行は採否にかかわらずその判断を確定した観測可能な根拠を書き、`エージェント由来のWI`では適用範囲を誤りの機構が依存する条件から再導出した結果も含める。
`由来`が`人間由来のWI`と`ユーザー指示`のいずれかである行は、採否にかかわらず、原文が示す要求単位ごとの分解結果を`根拠`へ書く。各単位について、原文の該当部分と、その単位を実施範囲へ採るか外すかを対応付ける。
原文が質問を含む単位では、その回答をUWIへ記録してユーザーへ返す工程を`## 実施内容`へ置く。質問への回答の扱いは`agent-toolkit:wi-standards`の「由来と承認」に従う。
対話から複数のWIへ分割起票した場合は、起票時に各WIへ割り当てた要求単位を採否の母集団とする。他のWIに割り当てた単位とそのファイル名も`根拠`へ記録し、当該WIの部分採用判定には含めない。いずれのWIにも割り当てず除外した単位は部分採用として扱う。
原文が「など」「等」「その他」「例えば」「〜も」その他の例示表現と追加関係の表現で示した開放集合を、閉じた列挙へ置き換えて実施範囲を定めた行は、`採否`を`部分採用`とし、閉じた集合と閉じた理由を`根拠`へ書く。
同じ2区分で`採否`を`採用`とできるのは、原文の全要求単位を、原文が示す開放性を保ったまま実施範囲へ採る行に限る。
それ以外で`採否`が`採用`の行は`-`とする。
分解結果を`根拠`へ残さないと、原文が示した集合と成果物が扱う集合との対応がどの成果物にも残らず、範囲の縮小が起草者の自己申告だけで通過する。
`充足済み`の行と充足済みの範囲を含む`部分採用`の行には充足を確認した実装箇所とcommitのいずれかの識別子を書く。あわせて、充足の成否を確定した裏付け手段も書く。

人間由来のWIの要求を全部又は一部不採用にする行は、`agent-toolkit:wi-standards`の「由来と承認」に従ってユーザーの確認を得る。
確認を要する縮小と、事後の報告で扱う裁量の境界も同節が定める。
実施しない除外・保持も`## 実施内容`の行として記録する。

### 要件・外部仕様

`## 要件・外部仕様`には実装担当が新たな要件判断を要さず着手できる粒度で、次を書く。
固定H3の`### 受入シナリオ`を置き、それ以外は自由なH3で区切ってよい。対象へ該当する項目だけを書く。

- 要件と、消費主体が観測する外部仕様（入出力、表示、公開契約、状態遷移、分岐条件、異常系、運用手順）
- 変更対象のファイルと識別子、変更する契約、生成・配布の過程と参照元の追随範囲。同じ値や動作をもたらす別の発生源（以下「別発生源」。既定値・プリセット・設定・環境変数・別の呼び出し手段・同じ操作を制約する別の節など）の追随範囲も含める。別発生源は保持先、直接消費先及び利用者が観測する結果までたどり、該当しないものは根拠を付けて除く。機能の追加・統合によって成果物の役割が変わる場合は、消費主体の利用場面から、名称、案内、ナビゲーション、運用ログ、配布メタデータや既存のテストで意味が変わる箇所を点検して範囲へ含める。改訂後の全文と実装コードは実装工程が確定する
- 完了条件。消費主体が観測できる成果と、合否を判定する観測値又はコマンドを、計画内の他の記述を参照せずそのまま実行できる形で書く
- テストコードを新規作成又は変更する場合は、テストが保証する契約（検出対象とする契約違反）と想定する主要な失敗様態。期待値は要求仕様・契約から導出する
- 特定の事象を発生させないことを求める要求では、その事象の発生件数を0として観測する手段
- 利用者が観測する公開インターフェース（設定キー、CLIオプション、環境変数、サブコマンド）の新設を含む計画では、そのインターフェースを新設する理由と、既存インターフェース又はその既定値の変更ではその目的を満たせない理由
- ユーザーから得た承認の範囲、及び`agent-toolkit:confirmation-and-uwi`の`references/judgment.md`「原文からの具体化を要する軸」に従って具体化した軸の判定結果
- 実行環境の受理条件に依存する設計方針の実機再現の典拠
- 永続又は継続的に増加するデータを扱う場合は、保持期間、容量上限、上限到達時の外部仕様、保守契機と所有者、及び長期条件の検証方法。設計基準は`agent-toolkit:writing-standards`の`references/design-time.md`に従う

テストの選定と期待値の導出は`agent-toolkit:writing-standards`の`references/testing.md`に従う。
`### 受入シナリオ`には`シナリオ | 由来 | 利用者と入口 | 操作 | 期待結果 | テスト`の6列表を置く。`## 実施内容`に`採用`か`部分採用`の行がある場合、人間由来の各要求単位と各WIの完成条件を少なくとも1行へ対応付ける。`由来`にはWIの完成条件、逐語引用の要求単位又はユーザー指示の所在を書く。`テスト`には公開された呼び出し手段（コマンド、画面、API、hookなど）を経由して同じ契約違反を検出する結合・E2Eテスト名を書く。自動化できない行だけ、理由と手動観測の入力・操作・判定方法を記す。採用行が無い場合は同H3の本文を`なし`とする。
規範Markdownの文面と配布原本の文面・値のいずれかを変更する場合は、同じファイルの本文だけを入力とする部分文字列チェックを選ばない。
実装を経由した結果、他の定義との整合、検証コマンドや実行レビューを使い、契約違反を検出できる検証単位を選ぶ。

既存の外部仕様又は内部契約を変える計画では、変更前の仕様を期待値として固定している既存テストその他の自動チェックの改廃方針を書く。
公開された呼び出し手段（コマンド、画面、API、hookなど）を置換・廃止する計画では、新しい呼び出し手段だけで同じ利用シナリオを結果まで完遂する検証を書く。存在確認、mock、部分的なprobe、旧来の呼び出し手段を併用した成功は、いずれもこの検証の代替から外す。
禁止規定や制約を新設する計画では、既存箇所へ遡及適用するか今後の変更箇所だけへ適用するかを書く。
規範、エンドユーザー向け文書、メッセージの文面を変更する計画では、変更する契約、対象のファイルと見出し、置換境界を書き、文面自体は実装工程が確定する。
文面の確定が要件そのものである場合（ユーザーが文面を指定した場合など）だけ、その文面を言語指定付きコードブロックで書く。
外部から観測できる文言を変更する計画では、変更前の文言を期待値として固定する既存のテストを文字列検索で特定し、実装単位の対象ファイル集合へ含める。テストの探索条件には、変更する定義への直接参照に加えて文言そのものの検索を含める。この探索は既存の直接消費側を追随させるために行う。新しいテストの根拠は、変更後の文言を同じファイルから転記する方法以外の契約から得る。
ファイルの改名・移動・廃止と、既存の仕様・概念の意味を変える計画でも、変更前の値を保持する参照元を同じ目的で探す。
参照元は変更する定義を指しながら変更前の値を保持できるため、実行処理の変更点だけから対象集合を導くと追随から漏れる。
見つかった参照元は、計画の対象ファイル集合へ含めるか、含めない理由を`## 要件・外部仕様`の追随範囲へ記録する。

- ファイルの改名・移動・廃止: 変更前のパス（ファイル名を含む）を固定文字列で検索し、文書、規範、コード、設定、テストコードなどの参照元を拾う。隠しディレクトリを母集団に含む場合は、その集合が欠落しない検索形を選ぶ
- 仕様・概念の意味の変更: 変更前の意味を表す語句を、設計書、利用者向け文書、docstringとコメント、データモデルのカラムコメント、生成物の入力元などで検索する。語句の単独一致では意味を区別できない場合は、意味を区別する条件と併せて判定する

計画が増加又は削減の方向や数値目標を定める場合は、基準値、目標及び再実行できる測定方法を完了条件へ書く。合否判定に用いるのは、再現性を確認できる指標とする。
完了条件がcommit OIDを判定する場合は、rebaseで値が変わるOIDを固定文字列として書かず、判定時点の作業ツリーから解決する形で書く。
一致0件を合否条件とする完了条件は、0件を合格と判定できる観測可能な形で書く（`<検索コマンド>; test "$?" -eq 1`など）（努力目標。検索コマンドの終了コードをそのまま合否に使うと、一致が無い場合の非0終了を失敗と読み違える）。
件数を期待値とする検索では、見出し、定義、設定キーなど判定する実体の行構造へ検索条件を限定し、起草時に同じ条件で測った件数を期待値とする（努力目標。対象名を引用する説明行まで数えると、本文の変更で期待値が変わる）。見出し名を数える場合は、行頭と行末を固定して見出し行だけを検索する。

### 恒久化・リファクタリング

`## 恒久化・リファクタリング`直下へ`### 恒久化`と`### リファクタリング`のH3をこの順で置き、この2つだけを見出しとする。
いずれのH3でも、検討した範囲と結果が読み取れる形で書く。
対象が無い場合は表を置かず、検討した範囲と0件と判断した理由を書いた1行の地の文を置く。

恒久化が守る価値は、この計画の外でも使う知見を、計画の完了後に参照されなくなる場所へ残さないことである。
その計画に固有でない方針、選定基準、却下した代替案の判断根拠、調査で確定した制約、新設する機構が依存する前提が候補に当たる。
`## 実施内容`が直接実装する変更そのものと、その計画自身が記録する情報は候補から除く。

`### 恒久化`の本文は`知見`、`出所`、`反映先`、`根拠`の4列表とし、知見ごとに1行で記載する。
`出所`には関連WI、確認への回答、エージェント提案など知見の由来を書き、`反映先`には反映先のファイルと節を、反映しない知見には`計画限り`と書く。
`根拠`には反映の必要性と反映先の選定理由、又は反映しない理由を書く。
反映先はその知見を要する判断をする工程で実行主体がその反映先を読む契機があるかで選ぶ。
反映先が自動チェックである場合は、その判定が失敗したときに実行主体が読む位置へその制約の理由を併記する。
反映を確定した知見は`## 実施内容`の行として計上し、反映先へ書く契約と置換境界は`## 要件・外部仕様`へ書く。
バグ対応では、計画ファイル（バグ）の対応行を基準として参照し、同じ説明を複製しない。
計画ファイル（バグ）のいずれの行にも対応しない知見・変更（恒久化・リファクタリングで新たに導入・変更する機構を含む）だけを4列表へ記載し、無い場合は表を置かず参照のみとする。
この扱いにより、同じ原因による既存欠陥を計画対象から漏らさない。

リファクタリングは実装と同時に行う既存部分の周辺是正とし、本来の対応に関連して既存部分を整理すると設計又は実装が改善する場合は、それを補う是正まで完了して計画の完了とみなす。
実施内容そのもの、新設する機能そのもの及び実装・検証に必須の付随作業は、それぞれ`## 実施内容`と`## 要件・外部仕様`が扱う。
検討の対象は、本計画が確定した設計に伴う修正が起因となって是正が必要になるか、その修正と合わせて既存部分を整理すると類似処理・責務・記述の分散を解消できる周辺箇所に限る。
本計画の変更が触れず、その変更によって是正の必要が生じない既存の不備を発見した場合は、`agent-toolkit:bugfix`の`references/response.md`の手順に従う。
検討の範囲は本計画が変更する対象と、その定義・参照・呼び出し元・既存テスト・生成・配布手順のうち、その変更が是正を必要にする箇所とする。

- コードでは本計画の変更で陳腐化する既存実装・既存テスト、本計画の変更が分散させる類似処理、本計画の追加により責務が肥大化するモジュール・ファイル・関数
- 文書では本計画の追記に対する既存節の粒度不整合、変更後の内容に合わない節構成、本計画の変更が生じさせる同一トピックの分散

`### リファクタリング`の本文は次の`対象`、`現状の問題`、`対応`の3列表を1件置き、本計画へ含める箇所ごとに1行を書く。表へ置くのは本計画へ含める箇所とし、実施しない候補と採否欄は検討の地の文が扱う。

```md
| 対象 | 現状の問題 | 対応 |
| --- | --- | --- |
| <対象箇所> | <問題> | <対応> |
```

本計画に含めるリファクタリングは`## 実施内容`の行として計上する。
実装・検証の成立に必須のテスト更新、参照元同期、生成物同期などの実装付随作業は`## 要件・外部仕様`へ置く。`## 実施内容`が持つ行は概念単位のものに限り、これらの実装付随作業は個別の作業行の対象から外れる。
規範文書へ新しい節又は項目を追加する計画では、`agent-toolkit:writing-standards`の「文書記述量の管理」に従い、既存記述の重複統合と削減を検討する。
同じ原因を持つ他の箇所の点検は、通常変更ではリファクタリングの検討範囲として扱う。計画本文で類似見直しを扱う節は`### リファクタリング`とし、専用節の新設は計画の構成の外に置く。

### 変更履歴

`## 変更履歴`は計画初版の作成、実装中の要件変更及び方針転換を記録する。記録は見出しと地の文で構成し、表と履歴IDは本節の書式の外に置く。
記録対象のユーザー発言は`### ユーザー発言<1から始まる連番>`のH3見出しの下へ置き、直下へ原文を改変しない`text`コードブロックを置いて、その発言から確定した現在の結論を併記する。
`ユーザー指示`由来の行の採否を`採用`と`部分採用`のいずれかとした計画では、`### ユーザー発言1`と空でない`text`コードブロックを1件以上置く。
記録対象は計画の目的、対象、範囲、外部可視の結果、実行制約又は承認を変更するユーザー発言とし、実際のユーザーメッセージとして存在する発話の逐語引用に限る。
委譲先が受け取った起動文と追送文は起動側が構成した指示であり、記録の対象は`<forwarded-user-input>`で囲んで渡された逐語本文とする。標識の扱いは`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」に従う。
ユーザー発言以外の記録は、変更の内容を判別できる任意のH3見出しの下へ置く。
ユーザー発話から導いた結論を計画本文へ書いた主体は、書いた直後に`agent-toolkit:confirmation-and-uwi`の`references/user-utterance.md`と比較し、結論側の適用範囲が原文の範囲と一致することを確認する。
比較の結果は`## 実施内容`の`根拠`列へ残す。比較の実施を起草者の申告だけで済ませると、原文と成果物の差が誰にも観測されない。

### 検証と終端工程

`## 検証`は`区分`、`検証コマンド`の2列と`近接検証`の1行の固定表とし、変更対象に対応する検証（対象ファイル限定のformat・lint・対象テスト）のコマンドを書く。全体検証とCIの成否は公開工程で判定する。既存計画の`全体検証`行は読み取り互換で受理する。
近接検証は変更するファイルとその直接消費側へ走査対象を限定する。ディレクトリ指定は、集合の外のファイルを走査するため対象の書き方から外す。
直接消費側は、変更するファイルからの参照関係だけでなく、そのファイルを読む側の関係からも拾う。共有の起動手段（タスクランナーのターゲット、共通スクリプトなど）を経由して起動されるテストと、変更するファイルの内容を期待値として保持するテストがこれに当たる。
読み手側にだけ現れる関係を走査対象から外すと、そのテストの失敗が公開後のCIまで残る。
セルへはタスクランナーが独立したターゲットとして公開するターゲット単位ごとにコマンドを分けて並べる。複数のターゲットを連結した1件の合成コマンドは、ターゲット単位とコマンドの対応が失われるため、セルの記載形式の外に置く。

`## 終端工程`はcommit・push後に実行する操作（PR/MRの作成とタイトル・本文、リリース、タグ付けなど）だけを列挙する。終端工程が無い計画は`なし`と書く。

### バグ調査

作業種別が`バグ対応`の計画は計画メタ情報の`計画ファイル（バグ）`が参照する`~/.claude/plans/<計画stem>.bugs.md`へバグ調査を分離する。
計画ファイル（バグ）には、計画主題に対応するH1と、バグ単位のH3ごとに固定の原因分析表と固定の調査表をこの順で置き、各セルを空欄にしない。
各表は`agent-toolkit:bugfix`の原因分析契約が定める行名、列名、順序、統合分割規則及び恒久化の参照契約を維持する。
見出しはH1とH3だけを置き、各H3の配下の表はこの2件とする。
`check_plan_file.py`は作業種別が`バグ対応`の場合に、実在、計画stemとの一致、分離先の構造を検証する。
同じ原因を持つ他の箇所の点検は、同契約の類似見直しに従って調査表へ記録する。

### 進捗ログ

`## 進捗ログ`は実装工程を中断後に再開できる粗い記録として、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。
起草時は内容行を置かず、新規作成の受理条件も内容行を持たない本文とする。
実装開始後の追記は`atk run-script plan-progress -- <計画ファイル> --completed-step <完了した工程> --result <結果・特記事項>`で行う。日時は同処理が実行時のローカル時計から生成し、呼び出し側は日時を渡さない。
実装開始後は、中断した主体が再開時に次の工程を選べる情報を追記する。commitの完了、近接検証の結果、実行レビューの収束、完了判定と、専用worktreeを用いる運用ではその絶対パス、専用branch名、作成時HEADの短縮OID、回収対象がこれに当たる。
`agent-toolkit:process-wi`のレーンでは、統合の行の結果・特記事項へ`レーン稼働時間: <秒数>秒`を書く。秒数はレーン担当のsessionの開始時刻から統合の完了時刻までの経過時間とする。
完了報告を発行する主体は、`## 要件・外部仕様`の完了条件について各条件の充足根拠又は未達理由を進捗ログの最終行へ記録する。
中断後に再開する主体は、進捗ログの最終行、`## 概要`の目的、`## 変更履歴`のユーザー発言、`## 要件・外部仕様`の完了条件、及びレビュー指摘管理表の応答を読んでから次の工程を選ぶ。計画ファイルの記述と異なる箇所は管理表の応答を現在の結論として採る。

## 計画構造の自動チェック

GFM表のセルにリテラルの`|`を含める場合は、コードスパン内を含めて`\|`と記述する。
計画構造の自動チェックが受理する書式のうち、全ての節へ共通する形式を次に定める。

- 本書が列名又は行名を定める固定表は、その名称と順序を完全一致で判定する。同じ列名の固定表は節ごとに1件とし、内容行は少なくとも1つのセルへ値を持つ
- 固定H3を定める節へは、そのH3だけを見出しとして置く
- 節の本文へ`なし`と書くと定めた箇所では、`なし`の1行だけを置く
- 計画メタ情報の`関連WI`の子項目は半角空白2字の字下げに続けて`-`と半角空白1字を置き、ファイル名は`yyyymmdd-hhmmss-nnn.md`の形式で重複させない
- `## 実施内容`の`由来`へ書くWIファイル名には、パス区切り文字、半角丸括弧及び空白を含めない
- `## 要件・外部仕様`と`## 終端工程`はそれぞれ内容を持つ
- 計画本文がスキル又はサブエージェントを起動の形で参照する場合は、その定義の実在を確認する
- コードフェンスを閉じる
- `## 変更履歴`配下の記述は地の文とコードブロックで書き、`### ユーザー発言<連番>`は連番を1から欠番なく昇順に置く
- 計画作業root直下の計画ファイルは、「計画ファイルの保存と参照」節のstem規約に対応する保存工程の受理条件を、起草時のチェックでも満たす。計画作業root直下に無い計画ファイルはファイル名を検証しない

`skills/plan-mode/scripts/check_plan_file.py`が計画の構造と実体を検証する。
同じ祖先見出しの下に同じ文言の見出しが複数現れる状態は不正とする。
引数には計画ファイル`<計画名>.md`の絶対パスを渡し、現在のagent-toolkit環境から次の形で実行する。

```sh
atk run-script plan-check -- --reject-migration-warnings /absolute/path/to/plan.md
```

内部scriptを別のPythonから直接起動してplugin packageを解決できない場合は、上記の公開されたコマンドを示して終了コード2で終わる。
対象リポジトリがセッションの作業ディレクトリと異なる場合は`--work-dir /absolute/path/to/target-repository`を付ける。
専用worktreeで作業する場合は、そのworktreeを作業ディレクトリとして検証するか、`--work-dir`へそのworktreeの絶対パスを渡す。
本スクリプトは`--work-dir`が解決するGitルートが計画メタ情報の`対象リポジトリ`と一致するか確かめるため、複製元の作業ツリーから実行するとその確認が成立せず、計画が拒否される。
`--reject-migration-warnings`は新規作成・改訂で旧形式からの移行警告をエラーとして扱う。保存済み計画を読み取りだけで検証する場合は同オプションを省略する。
通常のシェルでは`${CLAUDE_PLUGIN_ROOT}`が展開されないため、読込済みの本書の絶対パスからスキルの絶対ベースディレクトリを確定して指定する。
旧形式（単一9節、二ファイル）の計画は`references/legacy-plan-file-standards.md`が定める読み取り互換で受理し、構造チェックは新書式への移行を警告する。
構造定数と値抽出は`agent-toolkit/agent_toolkit/_plan/structure/`に従う。
素材と要約の意味の一致、根拠の妥当性、検討の実質はレビューで確認する。

## 保持・不変性・完全復元の契約

保持、不変性又は完全復元を計画の契約とし、又は確認へ送る選択肢へ書く場合は、
確定前に採用する入力形式がその不変性を表現できるかを対象実装を読んで確認する。
併せて、保存・読込・UI・エディターなど通過する既存処理が加える変換（再直列化・trim・strip・既定値補完・値の正規化）も対象実装を読んで列挙する。
成立しない範囲がある場合は、不変とする対象と変更を許す例外を明示した契約へ書き換えてから確定し、選択肢本文にも同じ限界を書く。
契約及び完了条件へ書く表現は、成立する範囲を明示した形とする。「そのまま保存」「元と一致」を無条件の表現として使うと、通過する処理が加える変換が契約から脱落する。

## 復元・巻き戻し型の変更

過去の契約へ戻す変更と過去の契約を撤去する変更では、対象項目ごとに導入目的を調べ、維持、修正、撤去を項目別に判定して`## 要件・外部仕様`へ記録する。
復元候補ごとに、現行状態が喪失後に意図的に確立されたものかを、その領域の後続commit、消費主体が観測する仕様及び実装コメントの参照関係で確認し、意図的な再設計と判定した項目は復元対象から外して判定根拠を記録する。
由来の判定はファイル単位の最終更新者ではなく、現行に残る記述は行単位の作者、失われた記述はその記述を除去したcommitで行う。

## 要件の成立性

`## 要件・外部仕様`が定める変更は、書式への適合に加えて次の性質を満たす。
消費主体が観測する結果と、それを損なう条件が、計画単体から復元できる。
実装担当が別の資料を読まずに正常系と主要な異常系を再現でき、変更が既存の成功手順を失わせるかを判定できる状態を保つためである。

代表例として、次のような場面ではその成立を計画本文へ書く。

- 委譲の起動契約と返却契約のように、送信側と受信側が同じ契約を持つ変更では、双方を同じ計画で確定する
- 判定の分類や振り分けを変える計画では、変更する分岐へ到達する入力集合と、入力ごとの変更前後の結果を書く。ステータスとエラー種別の変更も同じ扱いとする
- 拒否条件、入力値の縮小、容量制限、権限強化を追加する計画では、現行実装で成功する利用シナリオを失うかを判定する。失う場合はユーザー合意の根拠を書く
- 既存の手順、検証手段又は完了判定を廃止する計画では、廃止後に成立しなくなる完成条件、チェックリスト及びテストを変更対象へ計上する
- 外部コマンドの挙動（終了コードの意味、オプションの導入バージョン、設定の優先順位など）を分岐の入力とする計画では、その挙動を実物で確かめた典拠を書く
- 変更対象ファイル群を管轄するプロジェクト側の編集規範が定める配布手順、版数更新及び同期先文書の追随を計上する
