# 計画ファイル作成基準

本書は新規計画ファイル（作業実体は`~/.claude/plans/*.md`）の成果物契約の単一の正本である。
計画担当は初版の起草前に本書を全文読み、全項を満たす計画を作成する。
レビュー担当は本書の各項を点検の基準として同じ本文を読む。
計画ファイルへの要件の追加・変更は本書へ行い、レビュー用のタスク文書へ検査項目を追加しない
（起草側が知らない検査基準は、初回レビューの不合格と修正往復を構造的に生むため）。

本書でいう`ユーザー`は計画の要求・指示・合意を与え、確認経路で回答する主体、
`エンドユーザー`は成果物を利用する主体、`消費主体`は成果物ごとに定まる利用・検証の主体を指す。
`利用者`は既存形式の値や引用本文を除き、新規の説明ではこれらの語へ具体化する。

## 計画ファイルの保存と参照

新規計画は`~/.claude/plans/dd-{日本語の簡潔な名詞}-{小文字16進数4桁}.md`をメインとし、
同じstemの`<stem>.detail.md`を同じディレクトリへ保存する。stemの4桁は内部作成処理が生成し、同じディレクトリの`<stem>.*`との衝突時は再試行する。
新規作成は`${CLAUDE_PLUGIN_ROOT}/skills/plan-mode/scripts/create_plan_files.py`を経由し、private-notesへ実装前の計画ファイルを作成しない。
新規作成では計画ファイル（メイン）と計画ファイル（詳細）の本文を同じ作成処理へ渡し、作業種別が`バグ対応`の場合は計画ファイル（バグ）の本文も同時に渡す。
作成処理は同じstemに属する全ファイルを排他的に確定し、全ファイルの読み戻しと計画構造検査に成功してからパスを返す。
計画構造検査が旧形式からの移行を促す警告を返した場合、作成処理は失敗として扱い、確定した計画ファイルを回収する。
計画の行数が閾値を超えた場合の警告など、旧形式に由来しない助言の警告は作成を妨げない。

作業中の実体位置にかかわらず、計画本文、付属素材、バグ調査ファイル、レビュー表及びキューmetadataの永続参照には、固定接頭辞
`$(atk config get private_notes)/`とprivate-notes配下の相対パスを使う。接頭辞後の値は`..`、絶対パス、シェル式、Windows区切り文字を含めない。
実際のファイル検査やセッション状態では解決済み絶対パスを使い、portable値をシェルで評価しない。
保存時はメイン計画ファイルの作成日から年月を取得し、stemを変えずに`private-notes/plans/yyyy/MM/`へ移動する。
保存済み計画を再び更新する場合は、`atk plans checkout <plans rootからの相対メイン計画パス>`で計画ファイルを作業root直下へ取得する。
取得した計画ファイルは新規計画と同じ手順で更新し、`atk plans commit <作業root直下のメイン計画ファイル名>`で取得元と同じ保存先へ反映する。
取得の後に保存元が変わった場合、`atk plans commit`は保存先と作業側のいずれも変更せず、競合を通知して失敗する。
取得した計画バンドルは、更新の要否が確定した時点で`atk plans commit`により保存先へ戻す。更新しなかった場合も同じ操作で戻す。
計画作業rootに残る計画バンドルは、取得した主体以外からも保存先へ未反映であると判別できる。セッション終了時のフックが計画作業rootの計画ファイル（メイン）を列挙して通知するためである。
通知を受領した主体は、自身が担当しない計画をそのまま残し、実装レビューが収束した自身の担当分だけを保存先へ戻す。
private-notesの計画ファイルを編集ツールで直接書き換えない。
既存の作業root内の日付階層形式は読み取りと保存の互換経路として受理するが、新規作成には用いない。

レビュー指摘管理表は計画ファイルと同じディレクトリへ、計画レビュー用を`<計画stem>.plan-review.tsv`（`track`は`plan-review`）、
実装レビュー用を`<計画stem>.exec-review.tsv`（`track`は`implementation-review`）として置く。
作成済みのレビュー表は、全ての要求を充足済みと確定して実装工程を省略する計画では計画レビュー完了まで、それ以外は実装レビュー完了まで作業rootで更新する。
`atk plans commit`はレビュー表を計画バンドルとして収集し、計画ファイルと同じcommitでprivate-notesへ保存する。

本書、`agent-toolkit:plan-mode`のSKILL.md及び`${CLAUDE_PLUGIN_ROOT}/share/`配下の計画関連文書は、
計画に属するファイルとレビュー記録を次の呼称で指す。新規の記述では次表の呼称以外の別名を用いない。

| 呼称 | 実体 |
| --- | --- |
| 計画ファイル | 同じstemに属するファイル全体 |
| 計画ファイル（メイン） | `<計画名>.md` |
| 計画ファイル（詳細） | `<計画名>.detail.md` |
| 計画ファイル（バグ） | `<計画名>.bugs.md` |
| 計画レビュー指摘管理表 | `<計画名>.plan-review.tsv` |
| 実装レビュー指摘管理表 | `<計画名>.exec-review.tsv` |

`実装詳細`の語は、実装上の細部を指す一般名詞としてだけ用いる。

## 計画ファイルの完成条件

計画は`<計画名>.md`（計画ファイル（メイン）。人間・メインエージェント向け）と
`<計画名>.detail.md`（計画ファイル（詳細）。実装者向け）の2ファイル構成とする。
両ファイルはstem一致（`<stem>.md`と`<stem>.detail.md`）で対応付ける。
計画ファイル（メイン）から計画ファイル（詳細）への対応はstemから導出する。

計画ファイル（メイン）はH1の主題に続けて次のH2を固定順で置く。

1. `## 概要`
2. `## 実施内容`
3. `## エージェント提案詳細`
4. `## 変更履歴（計画時）`
5. `## 検証区分`
6. `## 終端工程`
7. `## 進捗ログ（実行時）`

新規作成・改訂では上記の括弧付き見出しを使う。

計画ファイルの見出し、固定H3及び表の行名は、消費主体が用途を判別できることを基準に改訂する。
追随範囲の広さを改訂を見送る根拠にしない。

計画ファイル（詳細）はH1を持たず、次のH2を固定順で置く。
`## バグ調査結果`は作業種別がバグ対応の場合だけ先頭へ置き、他のH2は全計画で必須とする。

1. `## バグ調査結果`（バグ対応のみ）
2. `## 恒久化・リファクタリング内容`
3. `## 実装資料`
4. `## 完了条件`

読者の割当: メインエージェントは計画ファイル（メイン）だけを読む（統合後検証と完了報告の直前に計画ファイル（詳細）の
`## 完了条件`を追加で読む）。実装担当（実装担当）は計画ファイル（詳細）だけを受け取り、素材・要求の復元が
必要な場合に限り計画ファイル（メイン）を追加取得する。計画レビュー担当・計画担当は両ファイルを扱う。
自由な見出しは`## 実装資料`配下のH3以下に限る。

計画ファイルのパスを一般に言及する文書・frontmatter（キューの`plan_file`）・完了報告・進捗参照は、
計画ファイル（メイン）のパスを指す。実装の詳細が必要な読み手はstemから`<stem>.detail.md`を導出して計画ファイル（詳細）を辿る。
これにより計画パスを一般言及するだけの文書は個別改訂を要しない。

新規作成と新規改訂では合成IDを持たない書式だけを生成する。

変動しやすい事実は名前付きのSSOTを1箇所だけ持ち、他の箇所は参照又は変動しない要約を使う。
新規作成・新規改訂の関連フィードバックはフィードバック/TBDの正本ファイル名と1行要約だけを保持し、フィードバック原文全文を計画へ転記しない。
キューにない素材の逐語本文・回答全文は計画外の明示入力として調査、起草、初回レビュー、再レビューへ保持し、計画には転記しない。
その他の同一事実、数値、要約も計画全体で1箇所だけに置き、他の箇所はファイル名か節名で参照する。
目的、実施内容、検証条件のように役割が異なる記述は、同じ対象を扱っても重複に含めない。
例外は、監査記録となる変更履歴の行だけとする。

外部の可変な対象に属する事実（フィードバックキューのactive・processing集合と依存関係、`HEAD`、作業ツリーの差分、並行する実行主体の進行状況）は、集合の列挙ではなく取得コマンドと判定規則として書く。
規範上の要求で列挙する項目は取得時刻と取得コマンドを併記し、列挙の完全性を主張しない。
計画の入力基準又は監査基準として意図的に固定する値（変更前実測値、ユーザー合意で固定した対象集合）は本規定の対象外とし、固定値として書く。
実装時にだけ確定する技術値で、方針、公開契約、実装成立性を左右しないものは、計画段階で仮値を固定しない。
計画ファイル（詳細）へ権威ある設定・実測・対象バージョンと導出方法を記録し、実装時に確定した値と解決方法を完了報告へ返す。
実行環境の差で確定できない場合は、代替の判定方法か計画の再起草条件を計画ファイル（詳細）へ記録する。

同一計画内の表・節から機械的に導出できる件数、割合、合計及び分類数を本文へ複製しない。
件数を根拠として必要とする場合は、対象集合、取得コマンド、集計条件、判定時点を明記し、正本と別の固定値にしない。
フィードバックキューはファイル名の列挙を正本へ複製せず、`atk mq list`・`atk mq show`の取得結果を
重複排除、依存判定、件数照合の入力とする。共有ファイルを変更する項目でも、対象が無関係であることを
本文の取得コマンドと判定規則で確認できる場合は、ファイル名を固定の依存へ追加しない。

役割が異なる複数箇所へ同じ事実値、手順又は禁止事項が現れる場合は、いずれかを修正する時点で計画全体を検索して全出現箇所を洗い出し、同じ修正回で同期する。
自己監査で訂正した値にも同じ扱いを適用する。

レビュー指摘、要件追加又は方針転換を計画へ反映する際は、対象節の末尾への追記を既定とせず、既存記述と統合して現在の結論だけが残る形へ節を編集する。
反映の経緯は`## 変更履歴`が正本として記録する。

### 計画ファイルの分割

1つの入力バッチから複数の要求単位を計画する場合は、対象ファイル集合の重なり、検証境界の独立性及び実装本体の推定規模を判定入力として計画ファイルの分割を決める。
実装本体の推定規模は、実装単位数、合計変更行数、計画レビュー1ラウンドあたりの読解量から見積もる。
対象ファイル集合が重なる要求単位と、同じ検証コマンドでしか合否を確定できない要求単位は、同じ計画ファイルへまとめる。
対象ファイル集合が重ならず近接検証が独立に成立する要求単位の組は、別の計画ファイルへ分ける。
ただし、単一の入力バッチに由来し、各要求単位が単一の実装単位かつ数十行程度の変更に収まる組は、対象ファイル集合が重ならなくても1つの計画ファイルへ統合する。
この統合の判定では、要求単位ごとに計画ファイルとレビュー指摘管理表を起草・維持して計画レビューを別個に反復する運用コストと、実装本体の作業量を比較する。
規模は判定の重み付けに用い、固定の閾値として適用しない。
1つのレーンへ割り当てられた要求単位も、先行成果依存が無い限り同じ計画ファイルへ統合する。
1つの計画ファイルが扱う要求単位は5件前後を補助目安とし、件数を主判定にも固定上限にもしない。
同じファイル群へ集中する小規模な項目は目安を超えてもまとめ、対象ファイル集合と検証境界が独立し前段の統合にも該当しない場合は目安に満たない件数でも分ける。
計画ファイルの分割はレビューの単位とし、1ラウンドの対象を小さくして反復の所要を下げる。
分割後の各計画ファイルを1レーンへ割り当て、1計画1専用worktreeで実装する。
判定に用いた対象ファイル集合、検証境界及び実装本体の推定規模は、分割した場合と統合した場合のいずれも各計画の`## 実装資料`へ記録する。

統合した計画に作業種別の異なる要求単位が混在する場合は次のとおり書き分ける。
バグ対応の要求単位を1件でも含む計画は`作業種別`を`バグ対応`とし、`## バグ調査結果`と計画ファイル（バグ）を置く。
計画ファイル（バグ）へはバグ対応の要求単位に対応するバグ単位だけをH3として置き、通常変更の要求単位をバグ単位に含めない。
`## 実施内容`は作業種別によらず要求単位ごとに行を分ける。
`## 検証区分`のレーン内検証には、統合した全要求単位の変更対象を被覆するコマンドを書く。

### 概要と計画メタ情報

`## 概要`直下へ全体像、目的、対象範囲の順で地の文を書く。
変動しやすい集計値や対象範囲は複製せず、実施内容又は名前付きSSOTを参照する。
`## 概要`は、計画を初めて読む読者が現在の計画の全体像を把握できる短い要約として保つ。
経緯、旧方針及び指摘の記録は`## 変更履歴（計画時）`と計画メタ情報の関連フィードバックを正本とし、`## 概要`へ複製しない。
要件の追加、方針転換又はレビュー反映で内容が変わる場合は、変更部分の追記を重ねず、節全体を現在の計画に合わせて書き直す。

`agent-toolkit:process-feedbacks`が通常型フィードバックを計画へまとめる場合、計画対象集合は`agent-toolkit:process-feedbacks`のpicker選定契約が返した新しい実装変更の同一レーン集合に従う。
複数の統合計画へ分割した場合は、各計画へ割り当てた担当フィードバックファイルを`## 実施内容`へ原則1ファイル1行ずつ記録し、全計画の担当ファイル集合が合わせて計画対象集合を過不足なく被覆する。
分割しない場合は計画対象集合を担当ファイル集合とする。
各フィードバック行へ由来、採否、採用範囲、実施しない範囲及び理由を統合する。
部分採用では採用範囲と実施しない範囲を同じフィードバック行へ記載し、要求別の採否詳細は内部採否記録を正本とする。
概要に独立したバッチ採否表は置かず、採否と方針を同じ実施内容へ統合する。

直下のH3は`### 計画メタ情報`だけとし、次の5行を固定順で置く。
コロンはASCIIの`:`、コロン後は半角空白1字とし、`関連フィードバック`と`作業種別`以外の値はバッククォートで囲む。

```md
- 起動経路: `<skillまたは起動経路>`
- 対象リポジトリ: `/absolute/repository/path`
- 関連フィードバック:
  - 20260831-000000-001.md: フィードバックの1行要約
- 作業種別: バグ対応
- ベースコミット: `<作成時点の参照値>`
```

`作業種別`は`バグ対応`又は`通常変更`とする。
`関連フィードバック`には、計画の入力となったフィードバックとTBDの正本ファイル名を1件1行で置き、コロンに続けて当該要求の1行要約を書く。
入力が無い計画では`- 関連フィードバック: なし`と書く。

### 新規書式の実施内容、関連フィードバック及び変更履歴

新規作成と新規改訂では、人間・メイン向けの判断資料へ合成IDを生成しない。`## 実施内容`には、`実施内容`、`由来`、`採否`、`根拠`の4列表を置く。
ユーザーが計画ファイル（メイン）だけで、何を実施し、何を実施しないかを判断できる概念単位で記載する。
フィードバックは原則として1ファイルを1行とし、実装手順、テスト項目、内部の分解単位ごとに行を分けない。
複数の採否を持つフィードバックは`部分採用`の1行とし、実施する範囲と実施しない範囲を`実施内容`へ併記する。

`由来`は`人間由来のフィードバック`、`エージェント由来のフィードバック`、`ユーザー指示`、`エージェント提案`又は`計画レビュー第<正の整数>ラウンド`のいずれかとする。
フィードバック由来の行は、区分に続けて正本のファイル名を括弧内へ記載する。
フィードバック2値のどちらを選ぶかは`agent-toolkit:feedback-standards`の「由来と承認」に従って判定する。
`source`の欠落だけが既定で人間由来であり、値を持つ項目は全て既定でエージェント由来とする。`source`の値は投入したスキルの名前であって、由来の区分を示さない。
同節が列挙する4種の明示由来を当該要求単位へ記録している場合だけ、既定を上書きして人間由来とする。
明示由来の有無は種類ごとに本文を確認して判定し、`## ユーザーコメント`の見出しの有無だけで判定しない。同見出しはユーザー専用の記入欄であり、出所と引用範囲を保持した対話回答は別の見出しの下に置かれることがある。
実施内容のフィードバック由来行が参照する正本ファイル名は、計画メタ情報の関連フィードバックへ記載したものと一致させる。
`人間由来のフィードバック`と記載する行のうち、正本の本文から機械判定できない明示由来（出所と引用範囲を保持した対話回答、関連計画の実施内容に記録された由来）を根拠とする行は、`由来`のファイル名に続けて半角空白1字と`[対話由来]`を付ける。
この注記を付けた行は、正本の`source`との照合を免除し、`## エージェント提案詳細`ではなく`## 変更履歴（計画時）`が当該由来の出所と引用範囲を記録する。
`計画レビュー第<正の整数>ラウンド`は計画レビューで新たに追加した行だけに使う。
`採否`は`採用`、`部分採用`、`不採用`、`充足済み`、`保留`、`対象外`、`移管`のいずれかとする。`充足済み`は、要求が成立し、既存commit若しくは既存実装が当該要求を満たすため実装単位を持たない場合に用いる。
`根拠`へ書く内容は、次の4つの規則を上から順に判定し、最初に該当した規則だけを適用して決める。

1. `由来`が`計画レビュー第<正の整数>ラウンド`の行は、採否にかかわらず`根拠`の先頭を`/absolute/path/<計画stem>.plan-review.tsvのround <同じ正の整数>`とする。指定したTSVに同じroundが存在することを検査する。`採否`が`採用`以外の行は、この参照に続けて句点で区切り、規則4が求める内容を書く。
2. `由来`が`エージェント提案`の行は、採否にかかわらず当該判断の要点を1文で書く。消費主体、利用シナリオ、そのシナリオが発生する条件、当該条件を確定した観測可能な根拠及び判断主体は`## エージェント提案詳細`を正本とし、同じ内容を`根拠`へ重ねない。
3. `採否`が`採用`の行は`-`とする。
4. 上記のいずれにも該当しない行は、実施しない範囲と理由を、別の参照を解決せず理解できる文面で書く。`部分採用`の行は、実施する範囲を`実施内容`へ書き、実施しない範囲と理由を`根拠`へ書く。

`充足済み`の行と、充足済みの範囲を含む`部分採用`の行には、該当した規則が求める内容へ充足の裏付けを加える。
裏付けとして、充足を確認した実装箇所又はコミットの識別子と、充足の成否を確定した裏付け手段を書く。
裏付け手段には読解した対象、実行した検査とその結果を書く。実装箇所の実在だけを根拠にせず、要求が挙げる全ての対応案と現行実装を突合した結果を書く。
対象を概念名だけで一意に特定できない場合は、曖昧な言い換えを作成せず、実在するファイルパス、識別子、コマンド名を記載する。
実施しない除外・保持も`## 実施内容`の行として記録し、専用の表を設けない。

### エージェント提案詳細

`## エージェント提案詳細`は、計画担当がユーザー要求の原文から新たに具体化した判断と、メイン、調整主体その他のエージェントが構成した指示から計画担当が確定した判断だけを、`実施内容`、`観測事象`、`ユーザー要求との関係`、`具体化した内容`、`根拠`の5列表へ記録する。
`## 実施内容`の`由来`が`エージェント提案`である行と、同表の`実施内容`を一対一で対応させ、対応する行を同じ順序で置く。
エージェント提案が無い場合は表を置かず、`なし`と記載する。表を置く場合は各セルを空欄にせず、同じ実施内容の観測根拠と具体化の関係を復元できる文面にする。
`根拠`へは判断主体と、当該判断を確定した観測可能な根拠を書く。
この節は計画担当の技術判断を監査するためのものであり、ユーザーが対象、範囲及び結果を明示した提案を同じ内容で採用した行は記録しない。

`## 変更履歴（計画時）`は、計画初版の作成と計画レビュー中の変更を記録する。変更の内容を判別できるH3見出しごとの記録とし、履歴IDを設けない。
記録対象のユーザー発言は`### ユーザー発言<1から始まる連番>`のH3見出しの下へ置き、直下へ原文を改変しない`text`コードブロックを置いて、その発言から確定した現在の結論を併記する。見出しへ発言の要旨を書かない。
ユーザー発言以外の記録は、変更の内容を判別できる任意のH3見出しの下へ置く。
`ユーザー指示`由来の行の採否を`採用`と`部分採用`のいずれかとした計画では、`### ユーザー発言1`と空でない`text`コードブロックを1件以上置く。
本セッションで受領したユーザー発言のうち、計画の目的、対象、範囲、外部可視の結果、実行制約又は承認を変更するものを記録対象とする。作業手順の確認、エージェントの挙動への質問、計画の成果物を変えない訂正など、これらを変更しない発言は記録しない。
記録できる対象は、実際のユーザーメッセージとして存在する発話の逐語引用に限る。メイン、調整主体その他のエージェントが構成した指示は、上位主体の判断であってユーザーの発話ではないため、当該コードブロックへ記録しない。委譲文、質問を作成したエージェントの文面及びフィードバック本文も同じ扱いとする。
エージェントが構成した指示から実施内容を確定した場合は、当該行の`由来`を`エージェント提案`とし、`ユーザー指示`としない。判断の内容と判断主体は`## エージェント提案詳細`へ記録する。

計画レビュー、方針転換及び計画修正は、起点、内容、現在の結論と同期先を自然文で記録する。
レビュー回数のようにユーザーが時系列を判別する値は、合成IDに当たらない。

### 検証区分と終端工程

計画ファイル（メイン）`## 検証区分`は`区分`、`検証コマンド`の2列2行の固定表とし、
`レーン内検証`行には変更対象に近い最小検証（対象ファイル限定のformat・lint・対象テスト）のコマンドを、
`統合後検証`行にはフル検証（`make test`等）のコマンドを書く。
計画担当が初版で提案し、計画レビューが妥当性を照合する。
既定の割当は「変更ファイル限定検査＝レーン内、全体検証＝統合後」とする。
計画が理由付きでレーン内フル検証を要求する場合（性能測定、他計画と独立に合否確定が必要な検証など）は
その指定を優先する。

計画ファイル（メイン）`## 終端工程`はcommit・push後に実行する操作（PR/MRの作成とタイトル・本文、リリース、タグ付けなど）
だけを列挙する。終端工程が無い計画は`なし`と書く（空欄は不可）。

### バグ調査結果

作業種別が`バグ対応`の場合だけ`## バグ調査結果`を置く。
バグ調査の本体は、新規計画では計画付属ファイル
`$(atk config get private_notes)/plans/yyyy/MM/<計画stem>.bugs.md`へ分離する。
計画本文の`## バグ調査結果`直下には、`- 計画ファイル（バグ）:`に続けて分離先のportable値を1行だけ置く。
バグ調査ファイルには、計画主題に対応するH1と、バグ単位のH3ごとの原因分析表および`項目`・`内容`の2列表を置く。
各表は`agent-toolkit:bugfix`の原因分析契約にある固定の原因分析表と固定の調査表を記載し、行名、列名、順序、統合分割規則及び恒久化の参照契約を維持する。
統廃合前の行構成を持つ調査表は読み取り互換として受理し、新規作成・改訂では生成しない。
実装担当とレビュー担当は読み取り専用で着手前に計画ファイル（バグ）の実在を確認する。
欠落時は起草工程へ差し戻す。
`check_plan_file.py`は作業種別が`バグ対応`で分離先を参照する場合に、実在、計画stemとの一致、分離先の構造を検査する。
分離先はバグ単位のH3を1件以上含み、各H3に固定の原因分析表と固定の調査表をこの順で置き、各セルを空欄にしない。

### 恒久化・リファクタリング内容

`## 恒久化・リファクタリング内容`直下へ次のH3を固定順で置く。

- `### 恒久化`
- `### リファクタリング`

`なし`、`不要`、`該当なし`だけの記載は認めず、対象、比較、確認結果及び理由を書く。

恒久化では、計画作成の対話・確認・調査で得た知見のうち当該計画固有でない恒久的な知見を、
完了後は参照されなくなる計画ファイルではなく、恒久的に参照される成果物へ書き残す判定を確定する。
次の知見を候補として列挙し、明示的な再利用性、外部公開契約、必要な設計理由又は検証済みの反復欠陥に該当するものだけを恒久化する。

- ユーザーが指示・発話又は確認への回答で示した方針・要件・合意事項のうち、当該計画固有でないもの
- ユーザーが確認への回答（`AskUserQuestion`の回答とTBDの`## 回答`節を含む）に付した判断基準・選択理由・補足
  （選択そのものより選定理由が将来の意思決定で再利用されるため）
- エージェントが確定した判断のうち、他の計画にも適用できる選定基準・指針
- 却下した代替案のうち、将来の意思決定で再利用できる判断根拠
- 調査で確定した制約・前提・外部仕様の理解
- 計画が新設又は変更する判定・遮断・順序制御の機構が依存する前提と、前提が崩れた場合に生じる観測事象（反映先は当該機構の実装箇所又はdocstringとし、コードだけで意図が自明な処理へ説明コメントを一律追加しない）

次の情報は候補から除く。

- 当該計画の実施内容・検証条件・進捗など、計画ファイル自身が記録する情報
- セッション固有の事情・一時状態・個人名指し
  （`../../writing-standards/SKILL.md`「ユーザー入力素材の取扱い」と同じ扱い）
- 既存の恒久成果物が既に記載する内容（参照の補強で十分な場合は反映しない）

通常変更の恒久化は、`知見`、`出所`、`反映先`、`根拠`の4列表とし、知見ごとに1行で記載する。
候補が1件も無い場合は表を置かず、確認した範囲と0件と判断した理由を書いた1行の地の文を置く。
バグ対応の恒久化の記載範囲は本節末尾のバグ対応の規定に従う。
出所には関連フィードバック、確認への回答、エージェント提案詳細など知見の由来を書く。
反映先には反映先のファイルと節を書き、反映しない知見には`計画限り`と書く。
根拠には反映の必要性と反映先の選定理由、又は反映しない理由を書く。
反映先は、コードに近い仕組み、プロジェクト規範、配布規範、スキルの順に比較して選ぶ。
反映を確定した知見は方針レベルの行として`## 実施内容`へ計上し、反映先へ書く文面はファイル群別の変更説明で確定する。
実装者の解釈が分かれないよう、自然文の指示ではなく転記できる確定文面を書く。

リファクタリングは実装と同時に行う周辺是正とし、本来の対応で理想的な状態が崩れる場合は、
それを補う是正まで完了して計画の完了とみなす。
検討の対象は、本計画が確定した設計に伴う修正が起因となって是正が必要になる周辺箇所に限る。
本計画の変更が触れず、当該変更によって是正の必要が生じない既存の不備は対象にせず、
発見した場合は`agent-toolkit/rules/01-agent.md`の`問題を見つけたときの対処`の経路に従う。
検討の範囲は本計画が変更する対象と、その定義・参照・呼び出し元・既存テスト・生成・配布経路のうち、当該変更が是正を必要にする箇所とする。

- コードでは、本計画の変更で陳腐化する既存実装・既存テスト、本計画の変更が分散させる類似処理、
  本計画の追加により責務が肥大化するモジュール・ファイル・関数
- 文書では、本計画の追記に対する既存節の粒度不整合、変更後の内容に合わない節構成、
  本計画の変更が生じさせる同一トピックの分散

検討結果は対象、現状の問題、対応、本計画に含めるかの4行表とする。
対象が無い場合は表を置かず、対象を検討した範囲と0件と判断した理由を書いた1行の地の文を置く。
本計画に含めるリファクタリングは方針レベルの行として`## 実施内容`へ計上する。
実装・検証の成立に必須のテスト更新、参照元同期、生成物同期などの実装付随作業は、`## 実装資料`のファイル群別の変更説明へ置く。
実装付随作業の検証条件は`## 完了条件`へ置き、`## 実施内容`へ個別の作業行を追加しない。

規範文書へ新しい節又は項目を追加する計画では、`agent-toolkit:agent-standards`の
`文書記述量の管理`に従い、既存記述の重複統合と削減を検討する。
作業中に問題を発見した場合は`agent-toolkit/rules/01-agent.md`の`問題を見つけたときの対処`の経路に従う。
同じ原因を持つ他の箇所の点検は、バグ対応では`agent-toolkit:bugfix`の類似見直し契約に従いバグ調査ファイルの調査表へ記録し、通常変更ではリファクタリングの検討範囲として扱う。計画本文へ類似見直しの専用節を置かない。
バグ対応では、恒久化でバグ調査ファイルの対応行を正本として参照し、同じ説明を複製しない。
バグ対応でも、バグ調査ファイルのいずれの行にも対応しない知見・変更
（恒久化・リファクタリングで新たに導入・変更する機構を含む）は各表へ記載する
（厳守規定。同じ原因による既存欠陥を計画対象から漏らさないため）。
バグ調査ファイルに対応しない知見・変更が無い場合は、恒久化の4列表を置かず参照のみとする。

### 実装資料と完了条件

`## 実装資料`配下のH3以下へ実装資料、変更内容、実行方法を記載する。
変更対象と変更内容はファイル群別の変更説明を正本とし、同じパス集合の一覧を複製しない。
別コンテキストの実装者が不要な再調査をせず、現行コードとの照合を開始できる粒度で書く。

`## 実装資料`直下へ`### 実装単位`を必ず置き、次の5列表へ1行以上の実装単位を記載する。

新規書式の`### 実装単位`には、`実装単位`、`目的`、`先行依存`、`統合順`、`近接検証`の5列表を置く。
`実装単位`には、同じ表の中で一意となり、変更対象又は達成する結果を具体的に判別できる説明的な名前を記載する。`U-001`のような合成IDは生成しない。説明的な名前へASCIIカンマを含めない（`先行依存`のASCIIカンマ区切りと曖昧になるため）。
`先行依存`は、依存する行の`実装単位`名を原文どおりASCIIカンマで区切って記載し、依存がなければ`なし`とする。
各行を独立した成果として検証でき、対象ファイル集合、commit及び近接検証がそれぞれ分離できる場合だけ1つのcommitへ対応させる。共有成果又は検証を手順差だけで分割せず、`統合順`による実行順序は維持する。
実装単位の対象ファイル集合は、変更する定義、その直接消費側、契約テスト及び生成・配布物のうち、当該commitの正式な近接検証を成立させるために必要な対象を含める。

検索で確認した直接参照だけを対象とし、推測した間接依存及び無関係な同語使用を含めない。
1つの計画ファイルにつき実装単位1件を既定とする。先行するcommitだけで後続単位の着手前に正式な近接検証が成功し、
かつ分割によってrevertの単位又は公開契約の境界を分ける利益がある場合に限り、この対象集合を複数の実装単位へ分けられる。
説明的な名前が長くなる場合も、定義のない短い概念名へ言い換えず、実在するファイルパスや識別子を含めて対象を一意にする。

主作業ツリーでのみ実行できる操作は実装単位へ置かない。
専用worktreeへ書き込む実装担当は当該操作へ着手できないため、当該操作は計画ファイル（メイン）`## 検証区分`の統合後検証か、`## 実装資料`直下の`### 主作業ツリー前処理`へ置く。
`### 主作業ツリー前処理`は`前処理`、`実行主体`、`実行場所`、`後続が消費する成果`、`失敗時に遮断する実装単位`の5列表とする。
`後続が消費する成果`には、当該前処理が生成し後続の実装単位が入力とする成果物を書き、成果を消費する実装単位が無い場合は`なし`と書く。
`失敗時に遮断する実装単位`には、当該成果を入力とする実装単位名を`### 実装単位`の名前と同じ文字列で書き、遮断する単位が無い場合は`なし`と書く。
実行順序が先であることだけを理由に実装単位を遮断対象へ書かない。
主作業ツリーでのみ実行できる操作が無い計画では表を置かず、該当する操作が無いことを確認した範囲と理由を書いた1行の地の文を置く。

全ての要求を`充足済み`と確定した計画では実装変更を伴わないため、`### 実装単位`へ充足の確認だけを行う1行を置く。`実装単位`へ確認対象のファイルパス又は識別子、`目的`へ充足を確認して実装変更を行わない旨、`近接検証`へ充足を確認する検査コマンドを記載する。

計画ファイル（詳細）は、新しいコンテキストの実装者が、計画時の対象範囲と判断を推測せず実装できる具体性を持たせる。
計画時の調査で変更範囲を確定した場合は、検索・読解の対象範囲、実行したコマンド、範囲へ影響した一致結果と不一致結果、各結果を変更対象か対象外とした理由を記録する。
検索した事実や件数だけでは調査結果とせず、実装者が同じ対象集合を復元できるファイルパスと識別子を残す。
出力全体が大きい場合は、原出力を複製せず、対象集合を欠落なく列挙した結果と再実行できるコマンドを記録する。

実装レビューの起動側が`review_contract`を生成できるよう、ユーザー目的とユーザー合意は計画ファイル（メイン）の既存節へ、公開契約、入力生成主体、信頼境界、通常入力、対象外入力及び誤許可・誤拒否の消費主体への影響は計画ファイル（詳細）の`## 実装資料`へ記録する。
同じ内容が既存の見出し又は表の行に一意な確定文面として存在する場合は専用の節へ複製せず、当該箇所を生成元として用いる。
対象へ該当しない観点は、観測した対象範囲と該当しない理由を記録する。

規範、エンドユーザー向け文書、設定断片又はメッセージなど、文面自体が変更成果物となる場合は、修正後の確定文面を言語指定付きコードブロックで記載する。
「趣旨を追記する」「整合させる」など、実装者が文面を再設計できる指示だけで確定文面を代替しない。
既存文面の一部を維持する場合は、置換境界と維持部分をファイルパス、見出し、識別子で一意に示す。

自然言語の文からなる確定文面は、計画へ記載する前に対象リポジトリが定める文章検査へ通し、検査を通過した文面だけを記載する。
検査は対象リポジトリの作業ツリーを変更しない入力経路で実行する。
管理対象一時領域へ当該文面だけを含むファイルを作成し、検査コマンドへ対象リポジトリを作業ディレクトリとして与え、当該領域のパスを検査対象として受理させ、自動修正を伴うモードを用いない。
検査が指摘した箇所は、指摘を解消した文面へ書き換えてから記載する。
設定値、コード、識別子など自然言語の文を含まない確定文面は本検査の対象外とする。
対象リポジトリが文章検査を持たない場合も対象外とし、対象外とした理由を`## 実装資料`へ記録する。
本検査は文面断片を単独のファイルとして評価する。
見出し階層、リンクの解決、文書全体での重複など、転記先の文脈に依存する検査は本検査の対象外とする。
pyfltrを文章検査へ用いる対象リポジトリでは、次のコマンドがこの入力経路を満たす。

```sh
uvx pyfltr run --commands=textlint,colloquial-check --enable=colloquial-check --no-exclude --no-fix --allow-external-paths --work-dir <対象リポジトリの絶対パス> --output-format=jsonl <一時ファイルの絶対パス>
```

検査が実際に実行されたことは、出力のうち`source`が`external-path`である`warning`レコードが0件であることと、`summary`の`commands_summary.no_issues.succeeded`が`--commands`へ指定したコマンドの件数と一致することの両方で判定する。
いずれかが成立しない場合は、当該文面が検査されていないものとして扱い、計画へ記載しない。検査経路の入力形を修復してから再実行する。
終了コードと`diagnostics`の値だけを検査の成否の根拠にしない。対象から除外された場合も終了コードは0となり、`diagnostics`は0のまま返るためである。

計画ファイル（詳細）へ記載した変更対象は、生成元、参照元、呼び出し元、配布先及び既存テストの検索結果と照合する。
該当しない接続先は、検索対象と不一致結果を根拠として対象外であることを記載する。
計画レビューは、文面の細かな好みではなく、この情報を欠くと新しいコンテキストで対象漏れ又は別解釈が生じるかを基準に具体性を判定する。

計画が変更する外部可視の要件ごとに、当該要件を誤って実装した場合に失敗する検体と、対応する完了条件を対応付けて記載する。
外部可視の要件とは、消費主体が観測する入出力、表示、公開契約及び運用手順とする。
`## 実装資料`直下へ`### 外部可視要件と検証の対応`を置く。
`外部可視要件`、`誤実装時に失敗する検体`、`対応する完了条件`の3列表へ要件ごとに1行を記載する。
検体には、テスト関数、検査コマンド又は成果物から観測する手順を、対象を一意に特定できるファイルパスと識別子で書く。
検体は、当該要件の必須条項のいずれか1つを欠いた成果物で失敗するものを選ぶ。
外部可視の要件を変更しない計画では表を置かず、変更しないことを確認した範囲と理由を書いた1行の地の文を置く。
本表は、対応する検証を持たない要件と、要件に対応しない完了条件を起草時に判別するために置く。

実装単位と実施内容の対応付けは、各単位の`目的`とファイル群別の変更説明が担う。
`統合順`は1から欠番なく昇順に置く。
複数の独立した公開契約や検証境界を1つの実装単位へまとめる場合は、`目的`へ同じcommitで扱う必要がある根拠を記載する。
対象ファイル集合が重ならず近接検証が独立に成立する連続した実装単位は、1回の委譲へまとめて割り当ててよい。

計画へ固定する細部は、実装者が既存規範と確定済み外部仕様から安全に判断できる範囲を除く。
変数名、消費主体が観測しない文言及び局所的な制御フローは計画へ固定しない。
一方、対象ファイルと識別子、外部可視の入出力、消費主体が観測する状態遷移、分岐条件、異常系、生成・配布経路及び
合否を判定する観測値は、実装可能性を保つために計画へ記載する。
消費主体が観測せず実装コードの構造に依存する内部の状態遷移と例外経路の細部は、計画へ固定せず実装時に確定し、実装レビューで扱う。

テストコードの新規作成又は変更を含む計画では、`## 実装資料`配下へテスト設計を記載する。
テスト設計を確定する前に、対象に関係する複数の利用・運用上の立場から観点漏れを点検し、対象契約に該当すると判明した失敗様態だけを既存のテスト設計へ記載する。
テストが保証する契約（検出対象とする契約違反）、想定する主要な失敗様態（異常系・境界値を含む）、
各失敗様態を検証するテストレイヤーの選択を書き、期待値は要求仕様・契約から導出して確定する。
実装の実行結果として得た出力は期待値の導出根拠にしない
（実装の欠陥ごと期待値へ固定され、契約違反を検出できないテストになるため）。
テスト対象ファイルの集合はファイル群別の変更説明を正本とし、テスト設計へ再列挙しない。
`## 完了条件`の実行コマンドは正本の集合と一致させる。

既存テストの除去、parametrize行の削除又は対象の付替えを含む計画では、対象テストごとに単独で検証している契約の有無を`## 実装資料`へ記載する。共有するテスト本体・fixture・parametrize列外のハードコード値が付替え後も成立するかを確認し、唯一の検証だった契約の除去後の担保手段を`## 実装資料`のテスト設計と`## 完了条件`へ計上する。

実装識別子の撤去又は改名を含む計画では、対象リポジトリ全体を既存テストと生成物を含めて除外指定なしで検索する。
用いた識別子、検索コマンド文字列及び一致件数を`## 実装資料`へ記録し、参照の追随範囲を実装前に確定する。

禁止規定又は制約を新設する計画では、既存の該当箇所へ遡及適用するか、今後の新規・変更箇所だけへ適用するかを
`## 実装資料`へ明記する。遡及適用する場合は、対象母集団と完了条件も記載する
（厳守規定。変更範囲と完了判定を起草時に一意にするため）。

`## 完了条件`には消費主体が観測できる成果と検証条件を書く。
共有構造検査、統合検査、対象固有のテストを区別し、同じ条件を複数箇所へ書かない。

外部コマンドの出力を合否判定に使う場合、変更前状態での事前実測は既定の手順としない。
変更後の検査で失敗を観測した時点で、実装開始時点の状態を取得できる場合に同じ判定を1回実行し、当該失敗が既存由来か本計画の変更由来かを切り分ける。
切り分けの結果は原因特定のための診断として記録し、完了判定からの免除に用いない。
変更後に観測した失敗は由来を問わず修正する。
リポジトリ全体を対象とする検査を完了条件へ置く場合は、実装着手時点で既に存在し、かつ本計画の変更対象ファイルへ帰属しない指摘を合否判定から除く。
除いた指摘は対象と観測値を計画へ記録し、別のフィードバックとして扱う。
本計画の変更に由来する失敗は前項のとおり由来を問わず修正し、この除外の対象としない。

変更前後で出力の差分を安定して識別できない検査は、合否条件から外すか、事前実測又は同等の安定した比較手段を維持したうえで用いる。
完了条件には、実在して安全に反復できる対象固有の検査だけを用いる。

計画担当が実行して結果を確認していない環境構築・後始末の手順列を完了条件へ書かず、手段の確立は実装工程へ委ねる。
完了条件へは合否を判定する観測値と、検査が満たすべき制約（実装本体を経由すること、同一ロジックを複製した検査で代えないこと、主作業ツリーの追跡ファイルとユーザー設定を変更しないこと、必要な稼働環境）を書く。

計画が増加又は削減の方向や数値目標を定める場合は、完了条件へ基準値、目標及び再実行できる測定方法を書く。
各レビューラウンド後に実装を統括する主体が再測定し、累積結果が合意へ逆行する場合は追加採用を止めて確認へ送る。
数値目標を合否ゲートへ置く前に、計画担当が起草時に測定手段を実行して再現性を確認する。
実行環境の条件（モデル、思考量、利用できるツール、system prompt、入力データなど）を変更前後で同一に固定できず再現性を確認できない指標は、合否ゲートにしない。
この場合は対策の帰結を機械判定できる構造条件（工程数、呼び出し回数、外部コマンドの実行有無など）を`## 完了条件`へ置き、実測値は参考値として`## 実装資料`へ記載する。
再現性を実行して確認できる指標では、従来どおり数値を合否ゲートへ置く（努力目標。再現できない測定を合否条件へ置くと、測定手段の不成立がラウンドごとに新たな指摘として成立し、計画が収束しない）。

実行済みの検査には実行したコマンドと観測結果を併記し、環境構築・後始末の実行方法は`## 実装資料`へ書く。
完了条件へ書くコマンドは、計画内の他の記述を参照せずそのまま実行できる形で書く。
対象パスを`同ファイル`・`上記`などの指示語や省略形で代替せず、各コマンドへ対象の完全なパスを記す。

`## 完了条件`と`## 実装資料`へ書く探索コマンド（grep、git grep、lsなど対象を変更しない検索）は、起草時と各修正回にそのまま1回実行する。
実行がエラー終了でないことを確認し、対象パスの実在は当該コマンドの終了コードと別の手段で確認する
（`ls`は存在しないパスへ終了コード2を返し、`git grep`は存在しないパス指定と無一致をいずれも終了コード1で返すため）。
併せて、出力が計画の対象集合列挙を過不足なく被覆することを確認する。
完了条件が検査する文字列は、`## 実装資料`の確定文面へ実際に含まれていることを確認してから書く。確定文面へ含まれない文字列と、実在しないパスを完了条件へ書かない。

同じ対象ファイルに対し、ある文字列の存在を要求する完了条件と、別の文字列の不在を要求する完了条件を併記する場合は、両方の文字列が包含関係を持たないことを確認する。
不在を要求する文字列が存在を要求する文字列の部分文字列となる場合は、不在側の検索範囲又はパターンを両立する形へ限定する。
一致0件を合否条件とする完了条件は`<検索コマンド>; test "$?" -eq 1`の形式で書く。
`grep -c`は一致0件でも`0`を出力して終了コード1を返すため、出力値を合否の根拠にしない。
`! <検索コマンド>`の形式は、パスの欠落と不正な正規表現による検索エラーも成功へ反転させるため用いない。

ここでの確認はコマンドの実行可能性と対象被覆の確認であり、変更前状態での合否の事前実測を既定の手順としない規定は変更しない。

改称、除去又は語彙統一を目的とする探索コマンドは、旧語の異形、略記及び派生形を含む語幹単位のパターンを用いる。
実在した異形文字列を入力とする1回の実行で対象異形を捕捉できることを実証し、実行したコマンドと出力を計画へ記録する。

計画が機構（担当種別、返却status、動作モード、ファイル書式、設定キーなど）を新設又は変更する場合は、`## 実装資料`へ機構ごとの接続先契約の対応表を置く。
列は`機構`、`受け渡し文書`、`返却statusの受領一覧`、`担当種別・入力・出力の定義先`、`機械検査・同期テスト`、`完了条件・エンドユーザー向けガイド`とし、各セルへ対象のファイルと識別子、あるいは該当しない理由を書く。
機構の新設・変更が無い計画では本表を省略する。

確定した内容を計画本文の外の可変ファイルへ置き、これを実装工程の確定入力とする場合は、次の配置規約を適用する。
当該ファイルを計画ファイルと同じディレクトリへ`<計画stem>.<用途を表す接尾辞>`として保存する。
計画本文へは`$(atk config get private_notes)/`から始まるportable参照で記載する。
セッション一時領域と管理対象一時領域へ置いたファイルは実装工程の確定入力にしない。
そのうえで当該ファイルの版を計画へ固定する。
版の固定には内容を露出しない指紋を用いる。
portable参照、指紋の算出に用いたコマンド及びその出力値を`## 実装資料`へ記載する。
指紋は対象ファイル内容のSHA-256とする。
`## 完了条件`へは、実装着手前、当該ファイルへ書き込む主体の終端時、計画と実装を照合する時点の3時点で
同じ手段により指紋を再計算し、`## 実装資料`の記載値と一致することを検査する条件を置く。
検査コマンドはportable参照を解決した絶対パスで書き、portable値をシェルで評価しない。
一致しない場合は実装を進めず、起草工程へ差し戻して計画の記載値と対象ファイルを再確定する。
確定内容を計画本文だけで表現できる場合は本規定の対象外とし、指紋を記録しない。

### 進捗ログ（実行時）

`## 進捗ログ（実行時）`は実装工程を中断後に再開できる粗い記録として、commit単位の受領、実装レビューの収束及び完了判定を記録する最後のH2とし、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。

本節は実装工程の記録だけを収める。計画作成と計画レビューの経過は`## 変更履歴（計画時）`が正本であり、計画レビューのラウンド、指摘反映、計画構造検査及び自己監査の結果を本節へ記録しない。
起草時と計画レビュー中は内容行を置かない。新規作成では内容行を持つ本文を受理しない。
実装開始後は呼び出し元が各commit単位の受領時と実装レビュー収束時に追記する。
実装開始時は、1つの計画ファイルへ1つの専用worktreeを対応付け、絶対パス、作成時のHEAD完全OID、所有主体、回収対象を記録する。
結果・特記事項にはcommit、検証結果、計画との差異、阻害要因を必要な範囲で書く。
完了報告を発行する主体は、報告の直前に`## 完了条件`を全文再読し、各条件の充足根拠又は未達理由を進捗ログの最終行へ記録する。
計画時の人間向け変更要約は`## 変更履歴（計画時）`、実装工程の粗い再開記録は`## 進捗ログ（実行時）`、個別指摘の詳細はレビュー指摘管理表を正本とする。用途の異なる記録を行数やラウンド数で相互照合しない。

### 復元・巻き戻し型の変更

過去の契約へ戻す変更と過去の契約を撤去する変更では、対象項目ごとに導入目的を調べる。
削除commitから得た項目別の対象記述と復元文面を1対1で対応させる。
維持、修正、撤去を項目別に判定し、親子階層を含む一意な現物の挿入位置と既存規定との重複を確認する。
判定結果と根拠は初回レビューの入力に含める。
復元候補ごとに、現行状態が喪失後に意図的に確立されたものかを確認する。
確認手段は当該領域の後続commit、消費主体が観測する仕様（画面表示・集計値・公開契約）及び実装コメントの参照関係とし、意図的な再設計と判定した項目は復元対象から外して判定根拠を記録する。
由来の判定はファイル単位の最終更新者ではなく、現行に残る記述は行単位の作者、失われた記述は当該記述を除去したcommitで行う。

### 計画構造検査

GFM表のセルにリテラルの`|`を含める場合は、コードスパン内を含めて`\|`と記述する。
Jinjaフィルターや正規表現など、コードとして評価される文字列も表構文の区切りと衝突しないよう同じ規則を適用する。

`skills/plan-mode/scripts/check_plan_file.py`が計画の構造と実体を計画構造検査する。
同じ祖先見出しの下に同じ文言の見出しが複数現れる状態は不正とし、祖先見出しを含む経路の一意性で判定する。
本スクリプトはPEP 723スクリプトであり、次の形で実行する。引数には常に計画ファイル（メイン）`<計画名>.md`の
絶対パスを渡す（計画ファイル（詳細）のパスを渡さない）。

```sh
uv run --script /absolute/path/to/plan-mode/scripts/check_plan_file.py /absolute/path/to/plan.md
```

対象リポジトリがセッションの作業ディレクトリと異なる場合は、
`--work-dir /absolute/path/to/target-repository`を付ける。
通常のシェルでは`${CLAUDE_PLUGIN_ROOT}`が展開されないため、読込済みの本書の絶対パスから
スキルの絶対ベースディレクトリを確定して指定する。
検査対象本文のportable参照は固定接頭辞から安全に解決し、旧計画に残る絶対パスは互換値として検査する。
対応する`<stem>.detail.md`ファイルの実在により二ファイル形式と旧単一ファイル形式を分ける。
二ファイル形式では計画ファイル（メイン）・計画ファイル（詳細）の両方の節構成を検査し、計画メタ情報の`関連フィードバック`の有無により新規書式と旧二ファイル形式を分ける。
detailが実在しない場合は、`agent-toolkit/scripts/_plan_format.py`が定める旧単一ファイル形式の固定H2順で検査する。
構造定数と値抽出は`agent-toolkit/scripts/_plan_format.py`を正本とする。
素材と要約の意味照合、根拠の妥当性、検討の実質はレビューで確認する。

## 保持・不変性・完全復元の契約

保持、不変性又は完全復元を計画の契約とし、又は確認へ送る選択肢へ書く場合は、
確定前に採用する入力形式が当該不変性を表現できるかを対象実装を読んで確認する。
併せて、保存・読込・UI・エディターなど通過する既存経路が加える変換
（再直列化・trim・strip・既定値補完・値の正規化）も対象実装を読んで列挙する。
成立しない範囲がある場合は、不変とする対象と変更を許す例外を明示した契約へ書き換えてから確定し、選択肢本文にも同じ限界を書く。
無条件の「そのまま保存」「元と一致」という表現を契約及び完了条件へ用いない。

## 要件の成立性

計画が定める変更は、書式への適合に加えて次の各項を満たす。

- 要件シナリオ: 正常系、完遂範囲・順序・条件を指定する入力、及び消費主体が観測する主要な異常系のそれぞれについて、
  実行主体、認可根拠、外部から観測できる状態更新の時機、失敗時の経路が計画本文から一意に定まる。
  実装コードの構造に依存し消費主体が観測しない内部の状態遷移と例外経路は、本項の対象に含めない
- 実機再現の典拠: 設計方針の選択が外部サービス、外部API又は実行環境の受理条件に依存する場合は、
  公式資料の引用に加えて実機再現の典拠（実行条件と結果）を計画へ記載する。
  方針選択に影響しない参考記述には課さない
- 計画が実行を指示する外部コマンドについて、分岐、遮断、完了判定の入力とする挙動を確認する。
  対象は終了コードの意味、出力が相対か絶対か、オプションの導入バージョン、設定の優先順位とする。
  安全な実行、管理対象一時領域での同等再現のいずれかによる結果を典拠として記載する。
  レビュー指摘の反映で新たに追加した呼び出し、変更した呼び出しにも同じ典拠を取得する。
  公式仕様は実測条件・結果の補足に限り用いる。安全な実行、同等再現で確認できない観点は、理由を問わず未検証範囲として明記する
- 参照元の追従: 既存ファイルの変更を含む計画では、変更対象を参照する既存箇所の追従方針を記載する
- 送受信契約の対: 委譲の起動契約、返却契約その他の主体間で渡す契約を変更する計画では、送信側と受信側の双方を同じ実装単位で確定する。変更する契約ごとに、受信側の発動条件と入力の消費が現行の文面のまま成立するかを判定し、成立しない受信側を変更対象へ含める。判定した契約、受信側のファイルと識別子及び判定結果を`## 実装資料`へ記録する
- 管轄規範の追随: 変更対象ファイル群を管轄するプロジェクト側の編集規範が定める配布経路、版数更新及び
  同期先文書の追随を調査工程で確定し、該当する実装付随作業を`## 実装資料`のファイル群別の変更説明と`## 完了条件`へ計上する
- 新設機構の成立範囲: 新しい状態、所有権、期限、回収、復旧、ホスト固有入力、外部コマンドの解決を
  導入する計画では、正常系と主要な境界条件を計画単体から復元できる粒度で記載する。
  併せて、当該機構を設けない案との比較と採用根拠を記載する
- 観測・診断出力の成立範囲: 集計値、レポート、ログなど、消費主体又は別の実行主体が判断に使う出力を
  新設又は拡張する計画では、出力の消費主体と、その主体が出力から確定する判断を列挙する。
  判断ごとに必要な分解軸（対象主体別、時系列、上位順、内訳など）を出力項目へ対応付ける。
  全体値だけでは判断が確定しない場合は当該分解軸を計画へ含め、含めない分解軸には除外根拠を書く
- 追加する制約の成功経路: 計画が新たに追加する拒否条件、受理する入力値の縮小、容量・件数制限、
  ネットワーク遮断、権限強化、既存機能の利用不可化を列挙する。
  現行実装で成功する利用シナリオを失う場合は、公開契約変更としてユーザー合意の根拠を記載する
- 判定・分類・写像・振り分け・ステータス又はエラー種別を変更する計画では、変更する分岐へ到達する入力集合を対象実装から全て列挙する。入力ごとの変更前後の結果を`## 実装資料`へ記載し、結果を変えない入力の不変性を固定する検証を`## 完了条件`へ計上する
- 間接的に作用する既存機構: 計画が明示的な変更対象としない既存の判定・遮断・順序制御の機構へ間接的に作用する場合は、
  当該機構の設計根拠を記録した箇所（docstring、コメント、先行計画、設計文書）から成立条件を抽出し、
  計画の変更が当該条件を崩さないことを`## 実装資料`へ記録する
- 新しい実行主体・提供者・プラットフォームの追加: 既存機能へこれらを追加する計画では、候補方式の選定前に既存正常系を実測し、
  消費主体が観測する入力、出力、UI、処理単位、終了条件、後続処理への接続を復元して新経路との対応を計画へ記載する。
  新経路で維持できない差異だけをユーザー合意へ送り、実装方式固有の検査項目を同等性確認の代わりにしない
