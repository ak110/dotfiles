# grilling

ユーザーとエージェントの責任範囲を明確にしながら、実装前に必要な共通理解へ到達するためのユーザー確認手順。

## 基本原則

確認すべき意思決定を **設計ツリー（design tree）** として整理する。

設計ツリーでは、ある意思決定の結果によって、後続して確認すべき意思決定が枝分かれする。

ただし、すべての意思決定をユーザーに委ねるわけではない。
以下の「ユーザーが決める事項」と「エージェントが自分で決める事項」の責任分担に従う。

### ユーザーが決める事項

次のような、プロダクトや成果物の性質に影響する意思決定はユーザーに確認する。

* 要件、目的、優先順位
* ユーザー体験や外部仕様
* トレードオフの選好
* 後から変更すると大きな手戻りになる設計判断
* 複数の妥当な選択肢があり、技術だけでは正解を決められない事項
* `01-agent.md` の役割分担においてユーザー担当とされている事項

これらについて、未確認の回答を推測して先へ進んではならない。

### エージェントが自分で決める事項

次の事項は原則としてユーザーに質問せず、エージェントが合理的な判断をする。

* `01-agent.md` の役割分担においてエージェント担当とされている事項、特に技術的詳細
* 間違っていても容易かつ低コストでやり直せる、細かい内部設計上の判断

たとえば、外部仕様を変えず、局所的に修正可能で、後続の大きな設計判断を拘束しない実装詳細はエージェント側で決める。

ただし、一見技術的な事項でも、次のいずれかに該当する場合はユーザー側の意思決定として扱う。

* 外部仕様やユーザー体験に影響する
* セキュリティ、可用性、コスト、運用負荷などに大きなトレードオフを生む
* 後から変更するための手戻りが大きい
* `01-agent.md` でユーザー担当とされている

エージェントが自分で決めた事項は記録しておき、確認フェーズ終了時にまとめて報告する。

## 設計ツリーとフロンティア

ツリーは**ラウンド単位**で進める。

**フロンティア（frontier）** とは、次の条件をすべて満たす意思決定の集合を指す。

1. 前提となる意思決定がすべて確定している
2. ユーザーが決めるべき事項である
3. まだユーザーに確認していない
4. 他の未回答事項を推測せず、「今」質問できる

各ラウンドでは、フロンティア上の質問をすべてまとめて提示する。

同じラウンド内の別の未回答質問に答えが依存する質問は、そのラウンドでは聞かず、**後のラウンド**に回す。

ユーザーが各ラウンドに回答するたびに設計ツリーを更新し、フロンティアを再計算する。

## 残り質問数の予告

各ラウンドの質問を提示する前に、現在の設計ツリーから見積もった**残り質問数**を短く予告する。

例:

```text
現時点では、今回を含めてあと5問程度の見込みです。
回答による分岐で増減する可能性があります。
```

正確な件数を確定できない場合は、無理に断定せず「3〜5問程度」「あと数問程度」のように見積もる。

この見積もりには、エージェントが自分で決める事項を含めない。

## 質問形式

各ラウンドでは、フロンティア上の質問それぞれに番号を付け、エージェント自身の推奨回答も示す。

形式は次のとおり。

```text
現時点では、今回を含めてあと3問程度の見込みです。

❓ **Q1** - **<質問タイトル>**: <質問本文。複数段落や複数の選択肢を含んでもよい>

➡️ <あなたの推奨回答>

---

❓ **Q2** - **<質問タイトル>**: <質問本文。複数段落や複数の選択肢を含んでもよい>

➡️ <あなたの推奨回答>
```

AskUserQuestionのようなユーザー確認用ツールが利用可能であり、この形式を十分表現できる場合は、そちらを使用してよい。

質問を提示したら、そのラウンドの回答を待ってから次のラウンドへ進む。

## 事実確認

**事実を調べることはエージェントの仕事であり、ユーザーの仕事ではない。**

環境上の事実、既存コード、ファイルシステム、利用可能なツール、ライブラリ仕様など、自分で調査可能な事項をユーザーに尋ねてはならない。

特に `01-agent.md` が参照可能な環境では、自分で読み、その役割分担を判断に反映する。

フロンティア上の判断に環境上の事実が必要な場合は、自分で調査するか、利用可能なら調査用のサブエージェントを起動する。

ただし、その調査の完了待ちによって確認作業全体を停止してはならない。

進行中の調査結果を必要とする質問だけを「未確定の前提」として保留し、それに依存しない他のフロンティア上の質問は先に提示する。

## エージェント判断の記録

ユーザーに質問せずエージェント自身で決めた事項について、少なくとも次を記録する。

* 決定した内容
* その判断理由
* 選ばなかった選択肢のうち、最有力だった対案

細かすぎて報告価値のない機械的な判断まで列挙する必要はない。
一方で、別の合理的な実装者なら異なる判断をする可能性がある事項は記録対象とする。

## 確認フェーズの終了

次の条件をすべて満たした時点で、確認フェーズを終了する。

* ユーザーに確認すべきフロンティアが空になった
* 未回答のユーザー判断事項が残っていない
* 未調査の事実によって保留されているユーザー判断事項が残っていない

つまり、ユーザーが決めるべき設計ツリーのすべての枝を確認し、ユーザー判断を必要とする暗黙の前提が残っていない状態である。

## 確認フェーズ終了時の報告

質問がなくなったら、ユーザーへの追加確認は行わず、まず**エージェントが質問せずに自分で決めた事項の一覧**を報告する。

一覧は、**ユーザーが異論を持つ可能性が高いと思われるものから順**に並べる。

各項目には必ず次を含める。

```text
- **決定**: <エージェントが選んだ内容>
  - **理由**: <なぜそれを選んだか>
  - **最有力の対案**: <選ばなかった中で最も有力だった案>
```

この一覧は承認を求めるためのものではなく、エージェント側で行った判断を可視化し、必要ならユーザーが後から異議を示せるようにするためのものである。

報告後はユーザーからの追加承認を待たず、**直ちに次のステップへ進む**。

ユーザーがその後いずれかのエージェント判断に異論を示した場合は、その判断と依存する後続判断を更新する。
