# CI失敗の対処選択肢別判定表

CI失敗の対処選択肢を横断で比較し、観測事実に対応する選択肢を確定するための判定表を提供する。
`agent-toolkit:commit`の`push後のCI通過確認`節から参照される。
本referenceはCI固有の証拠収集、再現性評価、対処候補の比較を担う。

## 前提

push直前に、`uv run --no-project --script <helper> create --prefix ci-evidence`を単独で実行して管理対象一時領域を作成し、
標準出力の絶対パスを再生成せず保持する。
Claude Codeでは`${CLAUDE_PLUGIN_ROOT}/scripts/_managed_temp.py`を使う。
Codexでは読み込んだ本referenceの絶対パスからplugin rootを確定し、
`<plugin rootの絶対パス>/scripts/_managed_temp.py`を使う。
続けてpushのdry-runが返す全status lineから更新対象refを確定する。
全更新対象refのsourceのpeel前OID・object typeと、remote側対象refのpush前OID・object typeを
所有者だけが読み書きできる一時領域へ保存し、存在しない側は不存在と記録する。annotated tagではtag objectの全内容と、
再帰的にpeeledした対象のOID・object typeも保存する。
commitへpeeledできるrefでは、ref単位の変更系列の基準SHAと完全長SHA列、
基準SHAからpush後commitまでの系列差分を同じ一時領域へ保存する。
upstreamが未設定の新規branchでは有効なGit設定も照合し、対象remoteから到達できないcommitを基に
変更系列を確定する。到達できないcommitが0件の場合は、変更系列の基準SHA・完全長SHA列・系列差分・
親差分を`対象なし`と記録し、先頭commitまたは親を参照しない。
削除refとcommitへpeeledできないrefでは、commit系列の資料が対象外であることを保存する。
全refのpush後commitから重複を除いた各完全長SHAをCI監視対象とし、1件の失敗検出を理由に
他SHAの監視を取り消さず、SHAごとの期待run・pipeline集合がすべて終端するまで結果を受領する。
push後commitが0件の場合は監視対象SHAを`対象なし`と記録する。
最初のCI失敗ではplan modeを開始する前に、失敗したSHA、CI識別子、取得可能な失敗ログ、
生成される場合のartifactを同じ一時領域へ暫定保存する。
早期失敗検出後は期待run・pipeline集合の全対象が終端するまで待ち、
全失敗ジョブのログとartifactを取得し直してから初回証拠の実在と分量を確認する。
初回ログと同一SHAのローカル再現結果から再現性を暫定分類する。
非決定性の疑いがある場合はplan mode開始前に同一SHAの対象失敗ジョブを原因単位で1回だけ再実行し、
再実行後のログとartifactを取得して両試行の資料の実在と分量を確認する。
初回証拠と必要な再実行証拠の取得完了後にplan modeを開始する。
取得済みの初回資料と、再実行した場合の追加資料を読み取り専用で調査する。
plan mode内でローカル書き込みやforge上の状態変更を伴う追加証拠が必要と判明した場合は、
計画ファイル起草工程を`pending`のままplan modeを終了する。
追加証拠の取得と実在確認をplan mode外で完了してからplan modeを再開する。
元の計画が存在する場合は、元の計画と実装・検証・レビュー結果も引き継ぐ。
元の計画が存在しない場合は、ref単位の基準SHA、完全長SHA列、
基準SHAから失敗SHAまでの系列差分を主要資料として引き継ぐ。
全refのpeel前OID・object type、annotated tag objectとpeeled先、削除refと非commit refの記録も引き継ぐ。
計画関連項目を`なし`と記録する。
commitを指すrefでは、全親の完全長SHAと各親から失敗SHAまでの差分も引き継ぐ。
親ごとの差分は補助資料とし、merge commitでは全親、親のないroot commitではempty treeを用いる。
親ごとの差分で系列差分を代替しない。
一時領域はpush主体が所有する。次の操作、保持理由、正確なパスを記録した再試行中状態だけ保持する。
追加pushでは別の領域を作成して全パスを個別に記録する。
CI成功、バグ対応完了、push失敗・監視不能・run未登録・forge CLI失敗後の中止、
シグナル終了、例外終了を全終端状態に含める。
plan mode外で記録した各絶対パスへ`uv run --no-project --script <helper> cleanup --path <保持した絶対パス>`を単独で実行する。
終了コード0と残存しないことを確認する。
因果分析、深掘り判定、類似見直し、処置階層は`bugfix.md`をSSOTとし、本referenceの分類だけから修正を開始しない。
push後のCI失敗で、原因が自セッションに帰属するか、セッション帰属が未確定の場合は`bugfix.md`の深掘り条件に該当する。
この条件では直接的原因の明白さを問わず深掘り経路を適用する。
失敗ジョブの調査は`bugfix.md`「事象単位の並列調査委譲」節に従い、同節が定める分割単位で委譲する。
対処選択肢を決める前に、CI失敗の性質を実測で分類する。

- 監視で取得したrun IDまたはpipeline ID・job IDを引き継ぎ、失敗ジョブのログを取得する
  - GitHubでは`gh run view <run-id> --log-failed`を使用する
  - GitLabでは`glab ci list --sha=<sha> -F json`でpipeline IDを取得する。
    取得したIDを`glab ci get -p <pipeline-id> --with-job-details`へ渡し、
    失敗したjobを`glab ci trace <job>`へ渡す
- artifactが生成されるジョブでは、VRT差分画像やtest-resultsなどのartifactも取得する
- 取得したログとartifactを読み取り、失敗の性質を目視で確認する
- 同一SHAでローカル再現を試し、再現可否を確認する

artifactを生成しないlint・ビルド・テストの失敗は、ログ本文から分類する。
失敗テスト名・失敗ステップ・エラーメッセージを観測事実として使用する。

## 失敗の性質による分類

CI失敗は、原因箇所・セッション帰属・再現性の3観点を独立して分類する。
VRT失敗では、VRT固有差分分類も追加する。

### 原因箇所

原因箇所は、失敗を生じさせた対象を分類する。

| 原因箇所 | 特徴 | 代表的な観測方法 |
| --- | --- | --- |
| 実装コード欠陥 | 変更コードが公開契約やテスト期待値と矛盾する | 失敗ログ、変更ファイルと失敗テストの対応関係 |
| テストコード欠陥 | テスト側の期待値・待機条件・fixtureが実装変更に追随していない | 失敗テストの差分、実装側の意図との照合 |
| 環境起因 | 実行環境・依存・外部サービスが失敗を生じさせる | ローカルでの同一SHA再現、CI環境のイメージdigest、外部サービスの応答 |

### セッション帰属

セッション帰属は、原因が自セッションの変更に由来するかを分類する。

| セッション帰属 | 特徴 | 代表的な観測方法 |
| --- | --- | --- |
| 自セッション帰属 | 変更ファイルや設定変更が失敗箇所へ影響する | 変更差分、失敗ジョブ、呼び出し経路の対応関係 |
| 自セッションと無関係 | 変更ファイルと失敗箇所に依存関係がない | 失敗ジョブ名・エラー内容・変更ファイルとの非関連性 |

### 再現性

再現性は、同一SHAと同一実行条件で結果が変動するかを分類する。

| 再現性 | 特徴 | 代表的な観測方法 |
| --- | --- | --- |
| 非決定性を確認できない | 成功と失敗の変動を観測していない | 初回失敗ログ、同一箇所での再失敗 |
| 非決定性の疑い | ログにネットワーク断・runner枯渇・タイムアウトなどの一時的な障害が現れる | 初回失敗ログ、実行環境の状態 |
| 非決定的 | 同一SHAと同一実行条件で成功と失敗が変動する | 原因単位で一度限りの対象ジョブ再実行、実行時刻ごとのログ差分 |

非決定性の疑いは暫定判定とする。
同一原因につき対象ジョブを1回だけ再実行し、結果が変動した場合は非決定的と確定する。
同一箇所で再失敗した場合は非決定性を確認できなかったものとして再実行を打ち切り、
原因調査へ進む。
再実行は再現性を更新する診断であり、成功を原因除去または自セッションとの無関係を示す完了判定に用いない。

実装コード欠陥やテストコード欠陥が競合状態や待機条件の不備を含む場合、
原因箇所は実装コードまたはテストコード、セッション帰属は自セッション帰属となる。
成功と失敗の変動を観測した場合、再現性は非決定的となる。
非決定的であることを、両者の修正対象から除外する根拠にしない。

### VRT固有差分分類

VRT失敗では、artifactの差分画像を用いたVRT固有差分分類を3観点の分類と併せて実施する。
VRT固有差分分類は画像に現れた差分形態だけを示し、3観点を確定しない。
原因箇所・セッション帰属・再現性は、ログ・変更差分・ローカル再現結果から別途確定する。

| VRT差分分類 | 特徴 | 3観点の確定に必要な追加観測 |
| --- | --- | --- |
| 実装意図UI変更 | 差分画像がレイアウト変更を示す | 変更の意図・公開契約・対象画面の変更差分を照合し、実装コード欠陥またはテストコード欠陥を判定する |
| データ差分 | 差分画像に表の行数・件数・順序・値などの変化がある | 実装のデータ処理・初期データ・先行テストの副作用・並列実行順を照合する |
| 描画微差 | フォント・アンチエイリアス・線幅・スクロールバー幅などに微差がある | ブラウザー・フォント・OS・描画設定と変更コードを照合する |
| 静的アセット配信不良 | スタイルが適用されず、ワイヤーフレーム状に表示される | ビルドログ・HTTP応答・生成物・配信設定・実行環境を照合する |

原因箇所とセッション帰属が確定するまで恒久的な対処選択肢を決めない。
再現性の観測結果を更新するための一度限りのジョブ再実行は診断手順として先に実施できる。
環境差やタイミング差などの仮説だけで対処選択肢を先に決めない。

## 対処選択肢と判定基準

適用可能な分類には、原因箇所・セッション帰属・再現性を組み合わせて使用する。
VRTベースライン再生成とマスク追加では、VRT固有差分分類も併用する。

| 対処選択肢 | 適用可能な3観点 | 適用不可の条件 | 上位対策の検討 |
| --- | --- | --- | --- |
| 実装コード修正 | 実装コード欠陥。セッション帰属と再現性は問わない | 該当なし | `bugfix.md`で確定した原因に対応する修正として適用する |
| テストコード修正 | テストコード欠陥。セッション帰属と再現性は問わない | 該当なし | fixture汚染・先行テストの副作用・並列実行順が原因の場合は、テスト設計を是正する |
| CI環境・依存・外部連携の修正 | 環境起因かつ自セッション帰属。再現性は問わない | 自セッションと無関係 | CIイメージ・環境変数・配信設定・依存・外部サービス連携を原因に応じて修正する |
| VRTベースライン再生成 | テストコード欠陥で、VRT固有分類が実装意図UI変更に該当する。セッション帰属は問わない | その他の分類 | 環境起因ではローカル環境をCIと一致させる。データ差分では初期データを固定する |
| マスク追加 | テストコード欠陥で、VRT固有分類が動的値のデータ差分に該当する。セッション帰属は問わない | 実装コード欠陥・環境起因の主要領域 | 初期データの固定を優先する |
| 失敗ジョブの再実行 | 非決定性の疑い。同一原因の対象ジョブにつき1回に限る | 非決定性の疑いがない失敗 | plan mode開始前の診断手順として再現性を観測する。複数jobが独立した原因で失敗した場合は原因ごとに診断要否を判定する。自セッション帰属の場合は、再実行の成否にかかわらず原因箇所を修正する |
| `rules:changes`によるジョブ除外 | 適用可能な分類なし | すべての分類 | 対象ファイル変更時に品質検証が欠落するため適用しない |
| specまたはtestの`.skip`・`xfail` | 適用可能な分類なし | すべての分類 | テスト修正または実装修正を適用する |
| `allow_failure: true`の付与 | 適用可能な分類なし | すべての分類 | 原因を除去する |
| 依存バージョンピン | 環境起因で、ライブラリのバージョン差が原因と実測で確定した場合に限る | その他の分類 | 自セッションと無関係な場合はユーザー確認を得る。該当ライブラリの仕様変更へ追随する |
| 変更差分がない`CI trigger`空コミットの再push | 適用可能な分類なし | すべての分類 | 非決定性の疑いがある場合は`gh run rerun`または`glab ci retry`で1回だけ再実行する |

ジョブ除外・テスト除外・失敗許容化は、`agent-toolkit:commit`の`push後のCI通過確認`節にある
CI設定側の抑制に関する具体的な禁止条件へ該当する。
変更差分がない空コミットの再pushは、同節の再実行上限と具体的な禁止条件へ該当する。
失敗が自セッション変更と無関係と判明済みで、根拠を提示してユーザーの明示合意を得た場合のみ制約を解除できる。
セッション帰属は、競合仮説と深掘りの適用要否、および無関係な環境起因でユーザー確認が必要かの判定に使用する。
実装コード欠陥とテストコード欠陥は、セッション帰属を問わず同一作業内で修正する。

## 選択の流れ

1. plan mode開始前に、失敗ログと生成される場合のartifactを所有者限定の一時領域へ暫定保存する
2. 早期失敗検出後は、期待run・pipeline集合の全対象が終端するまで待つ
3. 全対象の終端後に全失敗ジョブのログとartifactを取得し直す。初回証拠の実在と分量を確認する
4. 初回ログと同一SHAのローカル再現結果から再現性を暫定分類する
5. 非決定性の疑いでは同一SHAの対象失敗ジョブを原因単位で1回だけ再実行する
6. 再実行した場合は、再実行対象の試行が終端するまで待つ。再実行後のログとartifactを取得し、両試行の資料の実在と分量を確認する
7. 必要な証拠取得の完了後にplan modeを開始し、新しいバグ計画の調査工程へ入る
8. 原因箇所、セッション帰属、再現性を分類する
9. 自セッション帰属または帰属を否定できない場合は、初回ログの見え方を問わず競合仮説の支持・反証・判別実験を記録する
10. 自セッションと無関係な外部基盤障害を実測で確定した場合だけ競合仮説評価と深掘りの対象外とする
11. VRT系ではVRT固有差分分類も併記する
12. `bugfix.md`に従って直接的原因と深掘り要否を確定する
13. 自セッション帰属を否定できない場合は、直接的原因の明白さを問わず4原因区分、原因起点の類似見直し、3処置層を確定する
14. 確定した原因に適用可能な対処を判定表から選定する
15. 調査工程を完了してから、計画の有無に応じた基準情報、CIの生の観測事実、分析結果、選定した対処を引き継いだ新しいバグ計画の初版を起草する

## 分類判定の補助

自セッション帰属または帰属を否定できないすべてのCI失敗で、次の層を競合仮説の母集団として評価する。
初回ログが決定的な失敗を示す場合も、タイミング依存を除外せず評価対象に含める。
自セッションと無関係な外部基盤障害を、失敗ジョブ、エラー内容、変更差分との非関連性から実測して確定した場合だけ対象外とする。

- 実装: 競合状態、実行順序、共有状態、時刻依存、待機条件、eventual consistency
- テスト: fixture汚染、テスト順序、並列実行、固定されていないデータ・時刻・乱数
- CI環境: 設定、キャッシュ、資源制約、依存・runtime差、コンテナーまたはOS差
- 外部要因: runner、ネットワーク、DNS、外部サービス

仮説ごとに支持する事実、反証する事実、仮説間で結果が変わる判別実験を記録する。
該当しない層も反証する事実を記録し、名称だけで除外しない。
同じ条件の無目的な反復を判別実験として数えない。

同一SHAの再実行結果だけで原因層を確定しない。
再実行成功は非決定性を確定するが、自セッションと無関係であることを示さない。
実装・テストの競合や順序依存を修正対象から除外せず、判別実験で確定する。

分類を単独で確定できない場合は、観測を追加する。

- 同一SHAをローカルで再現し、CIの結果と比較する
- `git log --oneline --grep="<失敗パターン>"`で過去の同一失敗事例を検索する
- テスト対象のコードを意図的に壊し、当該テストが失敗するかを確認する

分類が2つ以上残る場合は複数原因の合成として扱い、すべての適用可能な選択肢を検討する。
先に確定できる原因へ対処し、残る分類は観測を追加して確定する。

- 原因箇所・セッション帰属・再現性では、失敗ログを再取得し、ローカル再現を追加で試す
- VRT固有差分分類では、取得済みの差分画像を再検査する。
  不足するartifactが必要な場合はplan modeを終了し、plan mode外で取得して実在確認してから再開する
- artifactを生成しないジョブでは、失敗ログのみを対象とする
