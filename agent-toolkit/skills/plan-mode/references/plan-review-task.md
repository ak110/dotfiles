# 計画レビュータスク

計画の成立性を、計画担当から独立した読み取り専用のレビュー担当として検査する。計画とリポジトリを修正しない。

## 入力

- 正規計画（新書式はメイン側・detail側の絶対パスの組、旧形式は単一パス。両ファイルを対象に読む）、
  対象リポジトリ、プロジェクト規範、`plan-file-standards.md`、`../../review-standards/SKILL.md`
- 計画構造検査スクリプト`check_plan_file.py`の絶対パス
- 初回レビューでは次の排他的な提示素材入力のいずれか
  - フィードバック原文経路では、対象のフィードバックファイル名、対象リポジトリ及び計画内の素材表・要求表
  - 直接起動経路では、`## 提示素材`の素材表・要求表、投入元及び引用範囲、キューにない素材の逐語本文・回答全文
- 元のユーザー指示
  人間由来の場合は種別、出所及び引用範囲を付け、常駐自動起動の場合は種別を起動事実、投入元を常駐自動起動、引用範囲を非該当とする入力
- キューにない素材の逐語本文・回答全文は計画外の明示入力として受け取り、計画本文の逐語転記を要求しない
- 復元・巻き戻し型の変更では項目別の維持・修正・撤去の判定と根拠
- 初回または再レビューの別。再レビューでは、同一thread継続でも新規起動でも、今回のラウンド番号と今回の表の絶対パスを必須差分入力として受け取る
- レビュー指摘管理表の絶対パス。計画レビューでは
  `~/.claude/plans/<計画stem>.tsv`を用いる
- 計画レビューで使用するレビュー表の`track`は`plan-review`とする
- レビュー表の操作書式は、初回・再レビューの操作前に`atk review-table --help`と使用する各サブコマンドの
  `--help`を実行して確認する。保存TSVの構造を私有実装から推測せず、公開CLIのヘルプ出力を正本とする
- 再レビューでは、今回のラウンドの指摘を同じ表へ`atk review-table add --round <ラウンド> --track plan-review`で追加する。過去ラウンドの行は変更しない

レビュー担当は`plan-review`の系統値で自身の指摘を追加し、レビューイーは指定された行を同じ系統値で応答する。

計画ファイルの作成規範の正本（成果物契約の明示された正本文書）は`plan-file-standards.md`とする。

入力が欠ける場合は推測せず、欠落項目を返す。
人間由来の指示があるのに種別、出所又は引用範囲がない場合は入力不足として返す。
元のユーザー指示を非該当とする場合に常駐自動起動の事実がないときも入力不足として返す。

## レビュー

### 作成基準への適合

他の点検より先に`plan-file-standards.md`を全文読み、同書の全項と計画本文を1項ずつ照合する。
照合の対象は`## 計画ファイルの完成条件`配下の各節、`## 保持・不変性・完全復元の契約`及び
`## 要件の成立性`のすべてとする。不成立の項は、`review-standards`が定める計画レビューの指摘範囲に
含まれる場合だけ指摘する。
同書が定める要件を本タスク文書へ再掲しない。
計画ファイルへ要件を追加すべきと判断した場合は、本タスク文書ではなく同書の改訂として指摘する。

### 要件シナリオ走査

初回レビューでは他の点検より先に、正常系、完遂範囲・順序・条件を指定する入力、主要な異常系を構成する。
各シナリオを端から端まで通し、実行主体、認可根拠、状態更新の時機、失敗時の経路が一意に定まるか確認する。
要件レベルの欠落を優先して報告する。
再レビューでは追加又は変更された機構へ同じ走査を適用する。

### 一般点検

- 計画全体と対象ファイルを直接読み、成果、対象、実装手順、検証、生成・配布経路の対応を確認する
- 内部整合性、実装可能性、現行実装との一致、対象網羅、規範適合を点検する
- 目的と観測可能な成果、対象範囲、利用者合意、実装者が安全に再現できない判断と制約、必要な順序、検証可能な完了条件がそろうかを確認する
- 追記要求には欠落している事実、その欠落で未確定となる判断または検証、阻害される成果を対応付ける
- 計画ファイル特有の指摘除外範囲は`../../review-standards/SKILL.md`「計画ファイル文脈での例外」節に従う
- 計画へ固定しない細部（変数名、利用者が観測しない文言、局所的な制御フロー）を追記させず、
  対象ファイルと識別子、外部可視の入出力、状態遷移、分岐条件、異常系、生成・配布経路及び
  合否を判定する観測値の欠落だけを実装不能又は契約不成立として指摘する
- 完了条件では合否を判定する観測値と検査が満たすべき制約の欠落を指摘し、計画担当が未実行の手順列の追記を要求しない
- 合否を公開後にしか判定できない完了条件がある場合は、その成立を左右する実行環境の前提が公開前に実測できる条件として併記されているかを確認する
- 利用者が指定した入力形式か外部仕様に内在する非可逆性・曖昧性に起因する事象は、計画が新たに生じさせた欠陥と区別する。該当する場合は、形式の置換、新形式の新設、利用者確認の発行を修正方針として要求せず、計画側の契約が当該限界を超える保持又は復元を約束している箇所の限定だけを指摘対象とする
- 工程や恒常規範の追加、既存機構の維持・修正では、目的の存続と総ライフサイクルコスト、削除・簡素化候補の比較を確認する
- 計画が明示的な変更対象としない既存の判定・遮断・順序制御の機構へ間接的に作用する場合は、当該機構の成立条件が計画へ抽出され、計画の変更が当該条件を崩さないことが示されているかを確認する
- 全レビュー系統へ共通する観点は`../../review-standards/SKILL.md`を正本とする
- 採用案の目的を、ユーザーが観測する成果と公開契約、計画や一覧などの中間手段へ分類する。
  中間手段の完全性を独立した目的として扱い、利用者成果に帰属する変更より優先していないかを確認する
- 計画内部の契約が利用者成果と衝突する場合は、追加機構で内部契約を保存する案より、契約の簡素化または撤去を先に指摘する
- `## 実施内容`の採用系（`採用`・`部分採用`）の`根拠`と`## 提示素材`の素材表・要求表を直接照合し、要求、採否、採用範囲、除外範囲及び素材参照の欠落、拡大、縮小、未合意事項の混入を確認する
- 同一ファイルに採用要求と不採用要求がある場合は、不採用要求が要求表の理由と除外範囲へ残り、`## 実施内容`の採用系の行が根拠へ採用要求だけを参照することを確認する
- 初回レビューで新形式の素材表にフィードバック由来素材が存在する場合、同じ対象リポジトリの全キューIDをまとめ、
  `../../add-feedback/references/managed-temp-bulk-show.md`を読み、同文書の一括取得手順を対象リポジトリごとに1回実行する。
  終了コード0で全項目が出力された場合だけ本文を採用し、要求ID、素材参照、採否、範囲及び根拠へ照合する。
  終了コード2では標準出力の部分結果を使わず、レビューを開始しないで入力不足として起動主体へ返す
  旧形式では`原文正本ID`のファイル名を同じ条件で取得し、該当素材が無い場合は取得を省略する
- 再レビューでは更新済み計画と追送された人間由来入力を正本とし、フィードバックキュー原文を再取得しない
- 元のユーザー指示が、直接受領した実際の利用者メッセージ又は委譲元が人間由来として出所と範囲を明示した入力であることを確認する
- キューにない素材の逐語本文・回答全文が、調査、起草、初回レビュー、再レビューの明示入力として保持され、計画本文へ転記されていないことを確認する
- 計画担当の起動文、フィードバック本文、調査資料を利用者発言へ分類しておらず、直接対話の利用者発話を除外していないことを確認する
- 任意の`### 合意済みの除外・保持`がある場合は、条項、対象と箇所、素材・要求参照、確認方法を1対1で照合する

### バグ対応固有点検

- バグ対応の分類には`## 概要`直下の`### 計画メタ情報`にある固定値`作業種別`だけを用いる。
  値の欠落、未知値、複数値は分類契約の不成立として指摘し、タイトルや説明から推測しない
- 作業種別が`バグ対応`の場合だけ`../../bugfix/SKILL.md`と計画本文が参照するバグ調査ファイルを読む。
  `../../bugfix/references/root-cause-analysis.md`の固定14行の調査表が事象単位、原因区分、
  類似見直し、3処置の意味契約を満たすかを確認する
  - 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）が、類似見直しの規則・母集団と再発防止処置の双方へ対応するかを確認する
  - 誤りの機構が依存しない文脈との連言で狭められた観点・処置と、対応の無い単位を指摘する

### 公開契約と制約

- 既存機能へ新しい実行主体、提供者、プラットフォームを加える計画では、既存正常系の入力、出力、UI、
  処理単位、終了条件、後続処理への接続が実測され、新経路との対応が確定しているかを確認する
- 提示素材とユーザー合意を目的と実装者向け領域へ突合し、
  外部可視のコマンド、引数、操作順序、入出力、公開インターフェースの変更に合意根拠があるか確認する

### 初回・再レビュー

- 初回レビューでは指摘候補を内部的に網羅列挙し、異なる観点で再走査してから確定指摘を一括して返す
- 再レビューでは全修正と累積計画全体を再監査する。
  `## 変更履歴`が解決済みとする論点は、現行計画に同じ違反が残る場合だけ再提示し、現存箇所と破る契約を示す
- 再レビューでは計画の`## 変更履歴`にあるラウンド単位の要約行と、レビュー指摘管理表の過去全ラウンドの表を全文読取して、解決済み論点と追加範囲を識別する
- 第2回以降に新しい欠陥を指摘する場合は、計画起草時に判断可能だった事項、初回レビューの見逃し、
  直前の修正による混入のいずれかへ分類し、根拠と該当する正本を示す
- 同一見出し配下（`## 変更履歴`の`同期先`が同一）、同一の違反契約、同一の新設・変更機構、同一の目的条項又は
  同一の混入構造について、2ラウンド連続して指摘が成立した場合は、
  当該箇所の小修正案を修正方針とせず、再設計・簡素化・撤去を含む方針を提示する。
  違反契約が同一の場合は当該契約の全出現箇所を走査し、新設・変更機構が同一の場合は当該機構と全接続先契約を走査する。
  目的条項が同一の場合は当該目的が及ぶ全記述を走査し、混入構造が同一の場合は同じ混入・動機・見逃し構造が及ぶ
  全箇所を走査する。走査した契約名、機構名、目的条項、混入構造及び範囲を報告本文へ明記する。
  当該箇所が既存実装の状態、遷移、コマンドを記述する場合は、実装本体とテストを根拠として示す
  - 当該節を単独で全走査し、同種観点の残欠陥を同一ラウンドで一括して返す
  - 当該節が手順列を含む場合は、前提の充足、必須引数、対象の起動状態、観測対象の出力、後始末の登録順序、時間依存など、手順の実行可能性を左右する観点を走査する
  - レビュー対象計画が記述する機構の外部コマンドについて、終了コードの意味、出力が相対か絶対か、オプションの導入バージョン、設定の優先順位を走査する
  - 当該機構が呼ぶ全コマンドを同一ラウンドで安全な実行、管理対象一時領域での同等再現のいずれかにより確認し、実行条件と結果を指摘の根拠へ含める。前記の確認ができないコマンド・観点は、公式仕様は実測条件・結果の補足に限り、実測済みとせず、理由と未検証範囲を返す

### 根拠と出力

- 指摘ごとに違反契約の原文または計画項目と、対象への適用根拠を示す。
  実行結果、公式資料、実装箇所のいずれかで裏付けられない候補は`未検証`とする

## 出力

指摘は`plan-review`の系統値を付けたレビュー表へ登録する。
`指摘内容`には違反契約の原文または計画項目、対象への適用根拠、根拠及び修正方針を含める。
修正方針は候補であり、元の目的、公開契約、合意済みの除外・保持を変更する認可ではない。
指摘がない場合は`指摘なし`と明記する。未検証候補は指摘と分ける。
正規計画と対象リポジトリを変更していないことを`write_status: unchanged`として返す。
完了報告はツール戻り値で1回返し、`SendMessage`で能動送付しない。
