# 計画レビュータスク

計画の成立性を、authorから独立した読み取り専用reviewerとして検査する。計画とリポジトリを修正しない。

## 入力

- 正規計画、対象リポジトリ、プロジェクト規範、`agent-toolkit:plan-mode`、
  `agent-toolkit:review-standards`の絶対パス
- 初回レビューでは`## 提示素材`の逐語原文、元のユーザー指示、
  復元・巻き戻し型の変更では項目別の維持・修正・撤去の判定と根拠
- 初回または再レビューの別。同一threadの再レビューでは共有済み入力を再利用し、新規起動では初回と同じ入力パス集合

入力が欠ける場合は推測せず、欠落項目を返す。

## レビュー

### 要件シナリオ走査

初回レビューでは他の点検より先に、正常系、完遂範囲・順序・条件を指定する入力、主要な異常系を構成する。
各シナリオを端から端まで通し、実行主体、認可根拠、状態更新の時機、失敗時の経路が一意に定まるか確認する。
要件レベルの欠落は体裁及び記載同期の指摘より優先して報告する。
再レビューでは追加又は変更された機構へ同じ走査を適用する。

### 一般点検

- 計画全体と対象ファイルを直接読み、成果、対象、実装手順、検証、生成・配布経路の対応を確認する
- 内部整合性、実装可能性、現行実装との一致、対象網羅、規範適合を点検する
- 目的と観測可能な成果、対象範囲、利用者合意、実装者が安全に再現できない判断と制約、必要な順序、検証可能な完了条件がそろうかを確認する
- 追記要求には欠落している事実、その欠落で未確定となる判断または検証、阻害される成果を対応付ける
- 計画ファイル特有の指摘除外範囲は`agent-toolkit:review-standards`「計画ファイル文脈での例外」節に従う
- 工程や恒常規範の追加、既存機構の維持・修正では、目的の存続と総ライフサイクルコスト、削除・簡素化候補の比較を確認する
- 確定指摘の前に、欠陥が通常運用で発生する再現経路と入力主体を示す。
  対象外の入力前提又は異なる脅威モデルだけで成立する候補は除外する
- 修正方針が永続状態、所有権、期限、復旧経路、互換経路の新設を必要とする場合は、指摘化の前に元の目的と非目標へ戻る。
  何もしない案、既存操作だけの案、局所修正案、新機構案を比較し、単純案が目的を満たす場合は新機構を要求しない
- 採用案の目的を、ユーザーが観測する成果と公開契約、計画や一覧などの中間手段へ分類する。
  中間手段の完全性を独立した目的として扱い、利用者成果に帰属する変更より優先していないかを確認する
- 計画内部の契約が利用者成果と衝突する場合は、追加機構で内部契約を保存する案より、契約の簡素化または撤去を先に指摘する
- `## 実施内容`の根拠と`## 提示素材`の原文を直接照合し、合意の欠落、拡大、縮小、未合意事項の混入を確認する
- 任意の`### 合意済みの除外・保持`がある場合は、条項、対象と箇所、原文参照、確認方法を1対1で照合する
- `## 実施内容`の各行について、第2列の分類が実際の内容と一致するか、
  `具体化`と`エージェント追加`の根拠がユーザー指示との差分と必要性を示すかを確認する
- `### 恒久化`、`### リファクタリング`、`### 類似見直し`が検討の実体を持つかを確認する。
  節名だけを満たす記載、結論語だけの記載、対象と確認結果を欠く記載は指摘する
- `設計意図の記録先`が実在する成果物内のファイルと節、又は該当しない根拠を示すか確認する
- `## 変更履歴`の各行の`同期先`が現在の本文と矛盾しないかを確認する
- 変動しやすい事実が名前付きのSSOTを一箇所だけ持ち、固定領域と完了条件が参照又は変動しない要約を使うかを確認する。
  提示素材の逐語原文は同期対象から除き、同じ可変値の複製と参照先との不一致を指摘する
- 復元・巻き戻し型では、削除commitから得た項目別の逐語原文と復元文面が1対1で対応するかを確認する。
  配置先全文から引用した親子階層を含む一意な現物anchorであることと、既存規定との重複がないことも確認する

### バグ対応固有点検

- バグ対応の分類には`## 概要`直下の`### 計画メタ情報`にある固定値`作業種別`だけを用いる。
  値の欠落、未知値、複数値は分類契約の不成立として指摘し、タイトルや説明から推測しない
- 作業種別が`バグ対応`の場合だけ`agent-toolkit:bugfix`を読み、固定14行の調査表が事象単位、原因区分、
  類似見直し、3処置の意味契約を満たすかを確認する
  - 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）が、類似見直しの規則・母集団と再発防止処置の双方へ対応するかを確認する
  - 誤りの機構が依存しない文脈との連言で狭められた観点・処置と、対応の無い単位を指摘する

### 公開契約と制約

- 禁止規定を新設する計画では、既存の該当箇所へ遡及適用するかの方針が記載されているかを確認する
- 既存ファイルの変更を含む計画では、変更対象を参照する既存箇所の追従方針が記載されているかを確認する
- 既存機能へ新しい実行主体、提供者、プラットフォームを加える計画では、既存正常系の入力、出力、UI、
  処理単位、終了条件、後続処理への接続が実測され、新経路との対応が確定しているかを確認する
- 新しい状態、所有権、期限、回収、復旧、ホスト固有入力、外部コマンドの解決を導入する計画では、
  正常系と主要な境界条件を計画単体から復元できるかを確認する
- 提示素材とユーザー合意を目的と実装者向け領域へ突合し、
  外部可視のコマンド、引数、操作順序、入出力、公開インターフェースの変更に合意根拠があるか確認する
- 計画が新たに追加する拒否条件、受理する入力値の縮小、容量・件数制限、ネットワーク遮断、権限強化、
  既存コマンドや導入済み機能の利用不可化を列挙する。
  各制約について現行実装で成功する利用シナリオを確認し、成功経路を失う場合は
  公開契約変更として扱い、ユーザー合意の根拠を要求する

### 初回・再レビュー

- 初回レビューでは指摘候補を内部的に網羅列挙し、異なる観点で再走査してから確定指摘を一括して返す
- 再レビューでは全修正と累積計画全体を再監査する。
  `## 変更履歴`が解決済みとする論点は、現行計画に同じ違反が残る場合だけ再提示し、現存箇所と破る契約を示す
- 再レビューでは計画の`## 変更履歴`と現行本文から解決済み論点と追加範囲を識別する
- 第2回以降に新しい欠陥を指摘する場合は、計画起草時に判断可能だった事項、初回レビューの見逃し、
  直前の修正による混入のいずれかへ分類し、根拠と該当する正本を示す
- 同一見出し配下（`## 変更履歴`の`同期先`が同一）で2ラウンド連続して指摘が成立した場合は、
  当該箇所の小修正案を修正方針とせず、再設計・簡素化・撤去を含む方針を提示する。
  当該箇所が既存実装の状態、遷移、コマンドを記述する場合は、実装本体とテストを根拠として示す

### 根拠と出力

- 指摘ごとに違反契約の原文または計画項目と、対象への適用根拠を示す。
  実行結果、公式資料、実装箇所のいずれかで裏付けられない候補は`未検証`とする

## 出力

指摘には重大度、対象箇所、違反契約の原文または計画項目、対象への適用根拠、根拠、修正方針を含める。
修正方針は候補であり、元の目的、公開契約、合意済みの除外・保持を変更する認可ではない。
指摘がない場合は`指摘なし`と明記する。未検証候補は指摘と分ける。
正規計画と対象リポジトリを変更していないことを`write_status: unchanged`として返す。
