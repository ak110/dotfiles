# 計画ファイルのcodexレビュー

## 実行経路

codexはMCP版（`mcp__codex__codex`・`mcp__codex__codex-reply`）のみを使う。

- Agentツールで`subagent_type: agent-toolkit:plan-codex-delegate`（`用途: 計画レビュー`）を起動する
  - 計画ファイルの絶対パス・プロジェクトルートの絶対パス・初回か継続かの別を渡す。
    継続時は`threadId`を渡す
  - `model`パラメーターは省略し、エージェント定義frontmatterの指定に従う
  - サブエージェント経由の起動がauto mode下でブロックされた場合、
    メインが`mcp__codex__codex`（初回）・`mcp__codex__codex-reply`（継続）を直接呼び出して継続する

`mcp__codex__codex`呼び出し時の`sandbox`・`config`（`model_reasoning_effort`）指定は
`agent-toolkit/agents/plan-codex-delegate.md`「## 共通処理」節をSSOTとする。

## codex利用可否の2段階判定

- 段階1（MCP利用）: `mcp__codex__codex`の名前解決成否で判定する。
  ツール一覧に見当たらない場合も`ToolSearch`（`select:mcp__codex__codex`）で取得を試みる。
  `ToolSearch`経由でも解決できない場合に限り段階2へ移る。
  `mcp__codex__codex-reply`（継続呼び出し用ツール）の未解決だけでは段階2へ移らない
  （継続呼び出しの解決失敗時は初回呼び出しの形へ切り替えて再試行する）。
- 段階2（claudeフォールバック）: 段階1の名前解決がいずれの経路でも成立しない場合、または
  クレジット上限・利用限度への到達を示すエラー応答を受領した場合。
  この場合の代替は計画レビュー`plan-reviewer`とする。
  タイムアウト・一時的な呼び出し失敗は段階2に該当せず、`plan-codex-delegate`側で分割再試行する。

  利用限度到達の観測は`plan-codex-delegate`の完了報告へ`codex_unavailable: usage-limit`行として
  記録される。親セッションのPostToolUseがセッション状態フラグ`codex_usage_limit_observed`へ真化する。
  `codex_usage_limit_observed`と`plan_reviewer_invoked`がともに真の場合、`pretooluse.py`のゲートが
  実装工程（ExitPlanMode・`plan-impl-executor`）への進行を許可する。
  当該フラグは新計画着手時にリセットされるため、利用限度到達を観測した後も
  次の計画では段階1から改めて判定する。codexの利用を試みずにフォールバックへ移らない。

## codexレビューの進め方

- 継続呼び出しは初回レビュー1回と、呼び出し元が重大以上（`致命的`・`重大`）の指摘を
  計画ファイルへ反映した場合の反映確認レビュー1回までとする。
  反映確認レビューで前回と異なる重大以上の指摘が新たに検出された場合は上限の対象外とし、
  呼び出し元が新たな重大以上の指摘が出なくなるまで継続する。
  前回と同型の指摘が繰り返される場合は上限を適用し、呼び出し元が採否を確定して
  計画本文への反映または明示的な不対応判定の記録を完了させる
- 規範違反主張を伴う指摘は呼び出し元が実機検証で成立を確認する。不成立なら
  `### 却下した代替案`へ実機検証結果とともに却下する
- codex指摘1件が複数セクションに伝播する場合、呼び出し元が関連セクションすべてを
  `## 変更内容`本文へ同一ターン内で反映する
- 呼び出し元が計画ファイルを全面改訂した場合は過去のcodexセッションを破棄し、
  新規セッションでやり直す

## 初回プロンプト雛形

```text
{plan_full_path} この計画ファイルをレビューして。
レビュー対象ファイルを編集せず、指摘と修正案だけを応答する。

レビュー観点:

- 発見した指摘は重大度ラベルを付けて全件報告する（採否の選別はメイン側で行う）
- 同種カテゴリの違反が同ファイル内に複数出現する場合は代表例1件に集約し、残箇所は箇所数のみ示す
- `agent-toolkit:*`スキルや`plan-*`エージェントなどの識別子はcodex側から実在確認できないため、
  これらの実在性に関する指摘は不要
- 構文の合法性は機械チェック担当領域のため指摘対象外とする
- 計画ファイルは実装着手後に廃棄される一時文書である。記述スタイル・実装時に判断可能な細部
  （変数名・エラーメッセージ文言等）は指摘対象外とする
- 指摘対象は計画ファイル自立性が崩れる重大不備（参照先実体の不在・対象ファイル一覧の欠落・
  矛盾する判断記述・実装段階で再現できない曖昧な手順）に限定する
- 計画が引用する既存実装の挙動・制約・公開契約について指摘を組み立てる場合は、
  対象リポジトリの実ファイルを読んで確認してから成否を判定する。
  確認対象にはシグネチャ・API仕様・既定値・排他ロック・例外捕捉・安全性などを含む。
  実ファイルを確認しないまま、確認できないことを根拠に重大度を付与しない
  （前掲の`agent-toolkit:*`スキル・`plan-*`エージェント識別子は実ファイルを持たないため、
  実在性に関する指摘は引き続き不要とする）

加えて次を指摘対象に含める。

    計画へ実装コードが埋め込まれている場合、そのコード自体の論理欠陥を指摘対象に含める。
    特に、一意性を前提とする識別子・キーが実際にその適用範囲で一意かを検証する
    （番号体系がリポジトリ・プロジェクト単位で振り直される場合の衝突など）。
    テストコードが埋め込まれている場合、テスト名・説明文が宣言する検証内容と実際の検証内容が
    一致しているかを検証する。宣言と異なる経路を検証している、未使用の変数を削除文などで
    辻褄を合わせている場合は指摘する。
```

継続プロンプトは「計画ファイルを更新したので再レビューして。対象は計画ファイル本文への初回指摘反映であり、
実装コード・対象ファイル現状の状態は評価対象外である」とする。

境界条件・タイムゾーン等の追加観点が必要な実装案コードを含む計画では、
起動時のプロンプトへ具体的な観点（空入力・EOF終端・タイムゾーン契約など）を1〜2行で追加する。
Windows環境ではcodexのPowerShell経由ファイル読み書きがShift-JISになるため、
「UTF-8エンコーディングを明示すること」を追記する。

## plan-file-creatorからの起動

`agent-toolkit:plan-file-creator`は`subagent_type: agent-toolkit:plan-codex-delegate`を
`用途: 計画作成`・`用途: 計画レビュー`で使う。
auto modeでブロックされた場合の用途別対応は、
`plan-file-creator.md`「エスカレーション基準」節をSSOTとする。

計画ファイルレビューは観点分担で並列起動する。基本は「構造・整合性」「実現可能性・技術妥当性」の2並列とし、
規範文書（`AGENTS.md`・`CLAUDE.md`・`.claude/rules/`配下・`agent-toolkit/`配下）の改訂を含む場合は
「規範整合」を加えた3並列とする。起動は`agent-toolkit/rules/02-claude-code.md`
「サブエージェント運用」節が定めるforeground並列の既定に従う。担当ラベルは各インスタンスの
`追加のレビュー観点`欄へ埋め込む。
全担当は、計画が追加または変更する成果物全体の規模を、元の要求が示す反映内容の粒度と期待効果へ対照する。
要求されていない機械的手続きや新規規約が含まれていないかを点検する。
恒常的に読まれる規範文書への追加・変更は、分量に見合う再発防止効果があるかも判定する。
`plan-reviewer`（claude）は段階2成立時のみ代替として起動する。

`plan-codex-delegate`は`用途: 計画作成`（計画ファイル起草の委譲）も受け付ける。詳細は
`agent-toolkit/agents/plan-file-creator.md`「計画ファイルの起草」節を参照する。起草と計画レビューの
初回起動は別`threadId`のインスタンスで実施し、起草スレッドをレビューの初回起動へ継続利用しない
（自己レビュー回避が目的であり、「codexレビューの進め方」節が定めるレビュー自身の反映確認継続は妨げない）。
