# バグ対応の完成条件

対症療法（表面的な症状の解消）と根本対応（原因の除去と再発防止）を区別する。

## 根本原因の特定

- 事象を再現し期待値・実際値・発生条件を明確にする。再現困難な場合はログ・関連コミット履歴から特定する
- 表面的な症状で止めず、コード変更・データ蓄積・外部サービス変更・設定不整合など起点まで追跡する
- 上流ライブラリ・ツール・OSの変更が原因候補の場合、リリースノート・CHANGELOGを参照し
  挙動差分の観察だけでworkaroundを採用しない
- 推測した因果チェーンは該当コードを`Read`して1段ずつ裏付ける。裏付けが取れない段は
  `### バグ調査結果`表の「直接原因の候補」欄へ列挙し、断定形の「根本原因」欄には書かない
- 直接アクセスできない環境（本番環境など）の事象で、コードベース調査と開発環境の再現だけでは
  因果チェーンを確定できない場合、計画ファイルの作成へ進まない。
  実測データの採取手順（コンソールへ貼り付ける調査用のコード片・ログ採取の手順書など）をユーザーへ提示し、
  代行採取を依頼する。実データで根本原因が確定してから計画作成へ着手する
- バグ箇所が責務境界を越える呼び出し・非公開関数の横断利用・重複記録などの回避処理を含む場合、
  根本原因の確定前に同機能の正常な兄弟経路、設計書が定める所有責務、当該処理の導入コミットを
  突合する。局所処理を維持・共通化する案と正常経路へ復帰する案を比較し、後者を棄却する根拠を
  確認できるまで前者を根本対策と判定しない（努力目標。対症療法の強化を根本対策と誤認する
  方針転換を防ぐ規定であり、既存の調査記録への遡及適用は求めない）

## 対策強度の序列

再発防止策は次の順で選定し、上位が成立しない場合のみ下位を選ぶ。下位採用時は上位の不成立理由を
`### 却下した代替案`へ記録する。

1. 設計変更による誤りの構造的抑止（不正な状態を表現できない型定義・API境界の再設計等）
2. 自動チェック（型制約・lint・テスト・CI・hook等）
3. チェックリスト・手順書
4. ドキュメント・注意喚起（選定時は上位層への格上げ条件を1行以上検討済みであることを要する）

テストを再発防止策として計上する場合、再現テスト（今回の具体値のみに依存し修正検証を担う）と
再発防止テスト（別の入力・別の呼び出し元でも同じ原因の不具合を検出・防止できるか）を区別する。
肯定で答えられないテストは再発防止策として計上しない。

テストを再発防止策として計上する場合、当該テストが是正前の実装で失敗することを実測で確認する。
確認手段は是正前の版を別ファイルへ取り出して同一の検体を通すこととし、失敗を確認できない場合は
検体が判定分岐へ到達していないものとして検体を見直す。
新設・変更した条件分岐そのものの効果を裏付ける手順は
`agent-toolkit:coding-standards`「分岐条件の効果の裏付け」節に従う。

## 計画ファイルへの集約

根本原因・直接の修正方針・再発防止策・類似見直しの範囲・知見の記録先を、
`## 背景`の`### バグ調査結果`H3配下の項目・内容の2列表
（根本原因・直接原因の候補・修正方針・再発防止策・類似見直し結果・知見の記録の6行）へ集約する。
`### 恒久化・リファクタリング内容`では「バグ調査結果表に記載」と参照し重複させない
（努力目標。`plan-mode/SKILL.md`項目3と同一の書式統一であり、区分の根拠も同一とする）。
