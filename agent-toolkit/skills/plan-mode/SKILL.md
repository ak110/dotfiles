# 計画モード

計画ファイルを作成し、承認後の実装を`plan-impl-executor`へ引き継ぐ。
計画はユーザーが結果と判断を確認でき、fresh sessionの実装者が必要な材料を取得できる状態にする。

## 進め方

1. 適用規範、変更対象全文、定義・参照・呼び出し元、既存テスト、生成・配布経路、類似実装を調査する
2. 技術的に確定できない利用者依存事項だけをモード別の確認へ送る
3. 調査工程を完了してから、メインが計画ファイル初版を起草する
4. `references/plan-review-delegation.md`に従い機械検査と総合レビューを別系統で実施する
5. 計画ファイル、成立させる結果、ユーザー指示との差分、レビュー反映状況を提示する
6. 承認後に`references/plan-impl-caller-reception.md`を読み、`plan-impl-executor`へ引き継ぐ

バグ対応では`references/bugfix.md`に従い、直接的原因、深掘り要否、必要な原因区分、類似見直し、
是正・横展開・再発防止を確定する。

## 計画ファイルの完成条件

計画本文はユーザー向けの概要・合意と、実装者向けの調査結果・変更材料を分離する。
機械検査のためだけの定型表、識別子、履歴を増やさない。

先頭行にATX形式のH1を1件だけ置く。次のH2を基本構成とする。

- `## 変更履歴`: 判断が変わった場合の要約。単なる編集履歴は記録しない
- `## 背景`: 計画メタ情報、経緯、現状、必要な提示素材、バグ調査結果
- `## 対応方針`: 実施内容、ユーザー合意済み事項、エージェント判断、却下した代替案、恒久化・類似見直し
- `## 調査結果`: 実装が依存する確認済み事実、参照元、既存テスト、生成・配布経路
- `## 変更内容`: 対象ファイル一覧とファイル別の変更後文面または再現可能な差分
- `## 実行方法`: 実装、近接検証、commit、最終検証、二系統レビューの順序
- `## 完了条件`: 利用者が観測できる結果と検証条件
- `## 進捗ログ`: 実装中の節目、計画との差分、最終検証、route/thread
- `## 計画ファイル（本ファイル）のパス`: 本ファイルの絶対パス

### 計画メタ情報

対象リポジトリ、完全長のベースコミット、作業種別、起動経路を記載する。
作業種別は`- 作業種別: <固定値>`の記法とし、固定値には`バグ対応`または`通常変更`を用いる。
コロンはASCIIの`:`、コロン後は半角空白1字とする。
外部仕様や実行時挙動に依存する事実は一次資料か実機実行で裏付ける。

### 対応方針

実装後に成立させる結果を先に要約する。ユーザーの発話から直接得た合意は
`### ユーザー合意済み事項`へ、ユーザー指示外で確定した技術判断は根拠とともに
`### エージェント判断`へ記載する。既存機構の改訂では維持・修正・簡素化・置換・撤去を比較する。

### 調査結果

対象ファイルの現状、定義・参照・呼び出し元、既存テスト、生成・配布経路、外部仕様、実機結果を記載する。
集計値は実行コマンドと出力を根拠にし、入力形態が複数ある解析処理は全形態を確認する。

### 対象ファイル一覧

`## 変更内容`の冒頭に次の固定記法で全対象を列挙する。

```text
- [ ] `<パス>`（現行N行）
- [ ] `<パス>`（新設）
- [ ] `<パス>`（現行N行、廃止・削除）
```

各項目と1対1で対応する`###`<パス>``見出しを置き、配下のコードブロックへ変更後文面または
再現可能な差分を書く。削除対象は削除する旨を明記する。既存パスは実在確認し、新設は親ディレクトリを確認する。

### `## 変更内容`

対象ファイル一覧とファイル別H3を1対1で対応させる。

### 実行方法

想定commit単位ごとに実装、近接検証、差分確認、commitを反復し、全単位後に最終検証して二系統でレビューする。
各中間`HEAD`も公開契約とテストを満たす。対象リポジトリ外の操作が必要なら、操作と全対象を明示する。
`git push`とCI通過確認は`references/plan-impl-caller-reception.md`が扱う。

### 機械検査

`scripts/check_plan_file.py`はH1、対象一覧とH3、削除指示、Markdown構造、ベースコミット、
呼び出すskill・agent・pathの実在、`--base-commit`指定時の実差分を検査する。
意味の妥当性は総合レビューで確認する。

## 計画ファイルの保存

保存先は`~/.claude/plans/<stem>-<rand>.md`とし、`<rand>`は`openssl rand -hex 2`の実行結果を使う。
初版作成前にnoclobberで占有し、成功直後に同じパスを読み、本文全体を書き込む。
既存計画は改名せず、同じパスを改訂する。

## 計画作成プロセス自体を変更する場合

工程、検査、レビュー経路を追加する改訂では、同一改訂内で簡素化または撤去も比較する。
恒常費に見合わない工程を追加しない。
