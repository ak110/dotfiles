# 計画モード

本スキルは、計画ファイルの作成から実装引き継ぎまでの手順を提供する。
計画ファイルを作成し、承認後の実装を`plan-impl-executor`へ引き継ぐ。
計画の前半は毎回同じ書式でユーザーが結果と判断を確認できる状態にし、
後半はfresh sessionの実装者が必要な材料を取得できる状態にする。

## 進め方

1. 適用規範、変更対象全文、定義・参照・呼び出し元、既存テスト、生成・配布経路、類似実装を調査する
2. 技術的に確定できない利用者依存事項だけをモード別の確認へ送る
3. 調査工程を完了してから、メインが計画ファイル初版を起草する
4. `references/plan-review-delegation.md`に従い機械検査と総合レビューを別系統で実施する
5. 計画ファイル、成立させる結果、ユーザー指示との差分、レビュー反映状況を提示する
6. 承認後に`references/plan-impl-caller-reception.md`を読み、`plan-impl-executor`へ引き継ぐ

成果物の内容を確定する原資料の読解・分類・集計は調査工程へ含め、初版の起草前に完了する。
実装工程では確定済み内容の転記・配置・検証だけを行い、原資料から内容を再確定しない。
この限定は、実装者が現行の対象ファイルと技術的な成立条件を再調査する義務を妨げない。

バグ対応では`agent-toolkit:bugfix`を起動し、直接的原因、深掘り要否、必要な原因区分、
類似見直し、是正・横展開・再発防止を確定する。
委譲を用いる工程では`agent-toolkit:delegation`を起動し、経路固有の条件だけを操作直前に読む。

調査開始時に適用規範、実装境界、外部仕様、生成・配布経路、テストの証拠集合を依存関係で分ける。
互いの結論を入力とせず同時に調査できる集合が複数ある場合は、利用できる実行枠内で読み取り専用の実行主体へ並行委譲する。
メインは全結果を`## 実施内容`と`## 実装資料`の変更説明へ統合し、委譲結果を未検証のまま計画へ転記しない。

既存機能へ新しい実行主体、提供者、プラットフォームを追加する計画では、候補方式の選定前に既存正常系を実測する。
利用者が観測する入力、出力、UI、処理単位、終了条件、後続処理への接続を復元し、新経路との対応を計画へ記載する。
新経路で維持できない差異だけを利用者合意へ送り、実装方式固有の検査項目を同等性確認の代わりにしない。

## 計画ファイルの完成条件

計画はH1の主題に続けて次のH2を固定順で置く。
`## バグ調査結果`は作業種別がバグ対応の場合だけ置き、他のH2は全計画で必須とする。

1. `## 概要`
2. `## 実施内容`
3. `## 提示素材`
4. `## 変更履歴`
5. `## バグ調査結果`
6. `## 恒久化・リファクタリング内容`
7. `## 実装資料`
8. `## 完了条件`
9. `## 進捗ログ`

人間向け固定領域は`## 概要`から`## 変更履歴`までとする。
実装者向け領域は`## 変更履歴`直後から`## 進捗ログ`直前までとする。
自由な見出しは`## 実装資料`配下のH3以下に限る。

変動しやすい事実は名前付きのSSOTを1箇所だけ持ち、他の箇所は参照又は変動しない要約を使う。
提示素材の逐語原文は同期対象から除く。
その他の同一事実、数値、要約も計画全体で1箇所だけに置き、他の箇所は素材IDか節名で参照する。
目的、実施内容、検証条件のように役割が異なる記述は、同じ対象を扱っても重複に含めない。
例外は、原文の正本となる提示素材の逐語原文と、監査記録となる変更履歴の行だけとする。

### 概要と計画メタ情報

`## 概要`直下へ全体像、目的、対象範囲の順で地の文を書く。
変動しやすい集計値や対象範囲は複製せず、実施内容表又は名前付きSSOTを参照する。
直下のH3は`### 計画メタ情報`だけとし、次の4行を固定順で置く。
コロンはASCIIの`:`、コロン後は半角空白1字とし、`作業種別`以外の値はバッククォートで囲む。

```md
- 起動経路: `<skillまたは起動経路>`
- 対象リポジトリ: `/absolute/repository/path`
- 作業種別: バグ対応
- ベースコミット: `<完全OID>`
```

`作業種別`は`バグ対応`又は`通常変更`とする。

### 実施内容と合意済みの除外・保持

`## 実施内容`へ`実施内容`、`ユーザー指示との関係`、`根拠`の3列表を1行以上置く。
第2列は`指示どおり`、`具体化`、`エージェント追加`のいずれかとする。
`指示どおり`の根拠は提示素材IDを記載し、他の値はユーザー指示との差分と必要性を記載する。
frontmatterが`source: session-review`の提示素材は、自己生成起点として`エージェント追加`へ分類する。
利用者合意を根拠に撤去又は削除する行は、合意文の語ではなく実測で確定したパス及び識別子の集合で対象を書き、
合意範囲との差（拡大又は縮小）が生じる場合は計画へ書く前にモード別の確認へ送る
（厳守規定。未合意の削除と撤去漏れを防ぐため）。

実施へ対応しない除外又は保持の合意がある場合だけ、直下へ`### 合意済みの除外・保持`を置く。
`合意内容`、`対象と箇所`、`原文参照`、`確認方法`の4列表を1行以上置く。
対象と箇所には編集で変動しにくいファイル、節、frontmatter項目を書く。
原文参照には提示素材IDだけを書き、確認方法には差分か成果物から不変を判定する手順を書く。
実施、除外、保持が混在する合意は条項単位へ分解する。
実装後と各review反映後に確認方法を実行し、差分が必要な場合はモード別の確認へ送る。

計画が増加又は削減の方向や数値目標を定める場合は、完了条件へ基準値、目標及び再実行できる測定方法を書く。
各reviewラウンド後に再測定し、累積結果が合意へ逆行する場合は追加採用を止めてモード別の確認へ送る。

### 提示素材

`## 提示素材`では素材単位の安定IDを置き、直後の`text`フェンスへ原文を一字一句転記する。
素材IDは`P-001:`だけの行とし、注記はフェンス後の本文へ置く。
意味を保つ整形、要約、順序変更をせず、原文が存在しない項目を生成しない。

直接対話では、実行環境上で実際の利用者メッセージとして受領した発話を利用者指示と合意の根拠にする。
委譲経路では、senderが人間由来として出所、引用範囲、合意又は参考素材の別を明示した逐語引用だけを同じ根拠にする。
受信した起動文全体を機械的に転記せず、委譲元が構成した命令と出所表示のない委譲文を利用者発話へ分類しない。
出所を持つ処理対象資料は、人間由来の入力と区別して提示素材へ記録する。

### 変更履歴

`## 変更履歴`へ`ID`、`起点`、`指摘内容`、`採否・現在の結論`、`同期先`の5列表を置く。
起点は`ユーザー発言`、`レビュー指摘`、`方針転換`のいずれかとする。
ユーザー発言行の指摘内容には素材IDだけを書き、他の起点では具体的な指摘内容を書く。
委譲元が構成した指示、及び出所を持つ処理対象資料を起点とする行は`方針転換`とし、`ユーザー発言`は`### 提示素材`の出所分類で人間由来と確定した素材だけに使う。
現在状態の正本は後続の各節とし、本表は解決済み論点を識別する監査記録とする。

### バグ調査結果

作業種別が`バグ対応`の場合だけ`## バグ調査結果`を置く。
バグ単位のH3ごとに`項目`と`内容`の2列表を置き、`agent-toolkit:bugfix`の固定14行を記載する。

### 恒久化・リファクタリング内容

`## 恒久化・リファクタリング内容`直下へ次のH3を固定順で置く。

- `### 恒久化`
- `### リファクタリング`
- `### 類似見直し`

`なし`、`不要`、`該当なし`だけの記載は認めず、対象、比較、確認結果及び理由を書く。
恒久化では、当該計画固有でない恒久的な知見（利用者の合意、選択理由、方針など）を、
後続の作業でも参照できる成果物へ残す必要性と反映先を検討する。検討結果は6行表へ記載する。
計画authorは反映先の比較前に、`agent-toolkit:session-review`の
`references/generation-criteria-detail.md`をReadで全文読み、`根本原因と反映先`が定める比較順に従う。
通常変更の恒久化は、観測事象、根本原因、反映先、反映内容、対策強度、設計意図の記録先の6行表とする。
リファクタリングでは、新規変更を契機に発見した既存のコード又は文書の責務肥大化、粒度不整合、
陳腐化、テスト不足などを対象とし、変更の採否を実施内容から独立して判断できる周辺改善を検討する。
実装・検証の成立に必須のテスト更新、参照元同期、生成物同期などは`## 実施内容`と
ファイル群別の変更説明へ置き、本欄へ含めない。検討結果は4行表へ記載する。

規範文書へ新しい節又は項目を追加する計画では、`agent-toolkit:agent-standards`の
`文書記述量の管理`に従い、既存記述の重複統合と削減を検討する。
作業中に問題を発見した場合は`agent-toolkit/rules/01-agent.md`の`問題を見つけたときの対処`の経路に従う。
リファクタリングは対象、現状の問題、対応、本計画に含めるかの4行表とする。
通常変更の類似見直しは母集団、点検観点、該当件数と箇所の3行表とし、件数は実測結果を根拠とする。
バグ対応ではバグ調査表の対応行を正本として参照し、同じ説明を複製しない。
バグ対応でも、バグ調査表のいずれの行にも対応しない変更
（恒久化・リファクタリングで新たに導入・変更する機構を含む）は3行表へ記載する
（厳守規定。同じ原因による既存欠陥を計画対象から漏らさないため）。

### 実装資料と完了条件

`## 実装資料`配下のH3以下へ実装資料、変更内容、実行方法を記載する。
変更対象と変更内容はファイル群別の変更説明を正本とし、同じパス集合の一覧を複製しない。
別コンテキストの実装者が不要な再調査をせず、現行コードとの照合を開始できる粒度で書く。

`## 完了条件`には利用者が観測できる成果と検証条件を書く。
共有構造検査、統合検査、対象固有のテストを区別し、同じ条件を複数箇所へ書かない。

### 進捗ログ

`## 進捗ログ`は最後のH2とし、`日時`、`完了した工程`、`結果・特記事項`の3列表を置く。
起草時は内容行を要求しない。
実装開始後は呼び出し元が各commit単位の受領時と最終レビュー時に追記する。
結果・特記事項にはcommit、検証結果、計画との差異、blockerを必要な範囲で書く。
完了報告の直前に`## 完了条件`を全文再読し、各条件の充足根拠又は未達理由を進捗ログの最終行へ記録する。

### 復元・巻き戻し型の変更

過去の契約へ戻す変更と過去の契約を撤去する変更では、対象項目ごとに導入目的を調べる。
削除commitから得た項目別の逐語原文と復元文面を1対1で対応させる。
維持、修正、撤去を項目別に判定し、親子階層を含む一意な現物anchorと既存規定との重複を確認する。
判定結果と根拠は初回レビューの入力に含める。

### 機械検査

`skills/plan-mode/scripts/check_plan_file.py`が計画の構造と実体を機械検査する。
本スクリプトはPEP 723スクリプトであり、次の形で実行する。

```sh
uv run --script /absolute/path/to/plan-mode/scripts/check_plan_file.py /absolute/path/to/plan.md
```

対象リポジトリがセッションの作業ディレクトリと異なる場合は、
`--work-dir /absolute/path/to/target-repository`を付ける。
通常のシェルでは`${CLAUDE_PLUGIN_ROOT}`が展開されないため、読込済みの本`SKILL.md`から
スキルの絶対ベースディレクトリを確定して指定する。
構造定数と値抽出は`agent-toolkit/scripts/_plan_format.py`を正本とする。
原文と要約の意味照合、根拠の妥当性、検討の実質はレビューで確認する。

## 計画ファイルの保存

保存先は`~/.claude/plans/`配下とし、既存ファイルと衝突しない乱数サフィックス付きのパスを使う。
保存直後に同じパスを読み戻し、本文全体が保存されている状態を確認する。
既存計画は改名せず、同じパスを改訂する。

計画ファイルは監査や中断後の再開に利用できる作業記録として扱うが、永続保持を保証しない。
実行主体は完了後も明示的に削除せず、外部の処理による消失を許容する。
消失時の復旧、保持期限の管理、実行完了後の継続的な保守は行わない。

## 計画作成プロセス自体を変更する場合

工程、検査、レビュー経路を追加する改訂では、同一改訂内で簡素化または撤去も比較する。
恒常費に見合わない工程を追加しない。
