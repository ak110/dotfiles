# 計画モード

本スキルは、計画ファイルの作成から実装引き継ぎまでの手順を提供する。
計画ファイルを作成し、承認後の実装を`plan-impl-executor`へ引き継ぐ。
計画の前半は毎回同じ書式でユーザーが結果と判断を確認できる状態にし、
後半はfresh sessionの実装者が必要な材料を取得できる状態にする。

## 進め方

1. 適用規範、変更対象全文、定義・参照・呼び出し元、既存テスト、生成・配布経路、類似実装を調査する
2. 技術的に確定できない利用者依存事項だけをモード別の確認へ送る
3. 調査工程を完了してから、メインが計画ファイル初版を起草する
4. `references/plan-review-delegation.md`に従い機械検査と総合レビューを別系統で実施する
5. 計画ファイル、成立させる結果、ユーザー指示との差分、レビュー反映状況を提示する
6. 承認後に`references/plan-impl-caller-reception.md`を読み、`plan-impl-executor`へ引き継ぐ

バグ対応では`agent-toolkit:bugfix`を起動し、直接的原因、深掘り要否、必要な原因区分、
類似見直し、是正・横展開・再発防止を確定する。
委譲を用いる工程では`agent-toolkit:delegation`を起動し、経路固有の条件だけを操作直前に読む。

調査開始時に適用規範、実装境界、外部仕様、生成・配布経路、テストの証拠集合を依存関係で分ける。
互いの結論を入力とせず同時に調査できる集合が複数ある場合は、利用できる実行枠内で読み取り専用の実行主体へ並行委譲する。
メインは全結果を対象一覧と対応方針へ統合し、委譲結果を未検証のまま計画へ転記しない。

既存機能へ新しい実行主体、提供者、プラットフォームを追加する計画では、候補方式の選定前に既存正常系を実測する。
利用者が観測する入力、出力、UI、処理単位、終了条件、後続処理への接続を復元し、新経路との対応を計画へ記載する。
新経路で維持できない差異だけを利用者合意へ送り、実装方式固有の検査項目を同等性確認の代わりにしない。

## 計画ファイルの完成条件

計画は、ユーザーが毎回同じ位置で目的と合意を確認できる人間向け固定領域と、
別コンテキストの実装者が判断材料を取得できる実装者向け可変領域で構成する。

### 人間向け固定領域

先頭行へATX H1を1件置き、計画の主題を示す。
続けて次の見出しを固定の順序と階層で置く。

1. `## 変更履歴`
2. `## 目的`
   1. `### 概要`
   2. `### 計画メタ情報`
   3. `### 提示素材`
   4. `### ユーザー合意済み事項`
3. `## バグ調査結果`（作業種別が`バグ対応`の計画だけに置く）
4. `## 対応方針`
   1. `### 実施内容`
   2. `### 恒久化・リファクタリング内容`
      1. `#### 恒久化`
      2. `#### リファクタリング`
      3. `#### 類似見直し`

固定領域へH2を追加せず、固定見出しの名称、順序、階層、表の列を変えない。
計画固有の説明を要する場合は、固定H3・H4と同階層の見出しを追加してよい。
ただし`## バグ調査結果`直下のH3は各バグ単位の固定14行表専用とし、説明用の追加H3を置かない。
`## 進捗ログ`は固定の最終H2とする。

`エージェント判断`、`却下した代替案`、計画ファイル自身のパスは独立節として置かない。
実施内容表だけでは失われる判断はリファクタリング表か実装者向け領域へ書き、
実在する比較が採用根拠に必要な場合だけ該当行の根拠へ書く。

### 実装者向け可変領域

`## 対応方針`の直後から`## 進捗ログ`の直前までを実装者向け領域とし、
実装資料、変更内容、実行方法、完了条件だけを扱う。
領域は新しいH2から始める。`## 対応方針`配下のH3・H4として置いた見出しは領域に含まれず、
そこへ`### 対象ファイル一覧`を置いた計画は対象一覧が空として拒否される。
構成変更を許容する範囲はこの4領域に限り、人間向け固定領域と`## 進捗ログ`へ拡大しない。

対象範囲と、現行実装から安全に再取得できない判断、制約、必要な順序、生成・配布経路を記載する。
変更説明は共通方針、ファイル群、個別差分、正確な文面のうち必要十分な形式を選ぶ。
一般的なコード構造、標準のcommit・レビュー手順、リポジトリから再取得できる全文は省略できる。
利用者合意と異なる判断、実装者が安全に決められない選択、通常と異なる順序は省略しない。
完了条件には利用者が観測できる成果と、実装者が成否を判定できる検証条件を記載する。

計画には調査を完了した確定内容を書き、結論を実装段階へ先送りする表現を用いない。
テスト実行・動作確認など検証作業自体の計画と、`未検証`と明記して着手前の裏取りを指示した
事実確認は本規定の対象外とする。

成果物、公開動作、状態のライフサイクルを変え得る分岐は、計画で一意に確定した事項、回答済みTBD、
技術調査を継続する事項のいずれかへ分類する。
技術調査を継続する事項がなく、利用者依存事項がモード別の確認経路を完了した場合だけ起草と実装引き継ぎを完了する。
新しい状態、所有権、期限、回収、復旧、ホスト固有入力、外部コマンドの解決を導入する分岐は、
正常系と主要な境界条件を計画単体から復元できる粒度で確定する。

複数の実装単位を置く場合は、単位ごとの対象ファイル集合、先行依存、共通のベースコミット、統合順を記載する。
対象集合が交差せず、先行単位の成果を設計入力にせず、同じ生成物を所有しない単位だけを並列可能とする。
統合後の累積差分を対象に、生成同期を行い、全体を検証してレビューし、並列化を理由に品質工程を省略しない。

構造が複雑な箇所へ図を含める場合は、言語を指定したフェンスコードブロック
（` ```mermaid `・` ```svg `）で埋め込む。
言語指定の無いフェンスとインラインのSVGタグは図として処理されないため使わない。
単純な情報を図へ置き換えず、実装に必要な識別子、条件、詳細は本文にも記載する。

計画が対象リポジトリ外への操作（他リポジトリへのフィードバック投入・外部サービスの設定変更など）を
含む場合は、当該操作と全対象を実装者向け領域へ列挙する。
本記載を認可根拠とする操作では、記載の無い対象へ委譲先が及ばない。
適用中の規範が明示的に義務づける登録操作は、当該規範自体を認可根拠とするため列挙を要しない。

### 変更履歴

`ID`、`起点`、`指摘内容`、`採否・現在の結論`、`同期先`の5列表を1行以上置く。
本表は計画レビュー時の再指摘回避のため、指摘、対応内容、採否と現在の結論を安定IDで残す。
`起点`はレビュー指摘、ユーザー発言、方針転換に限り、実装経過は記録しない。
現在状態の正本は後続の各節とし、本表はfresh reviewerが解決済み論点を識別するために使う。
方針転換後は`同期先`の各節を全文検索し、履歴と本文が矛盾しない状態にする。

### 計画メタ情報

`### 計画メタ情報`へ次の4行を固定順で置く。
コロンはASCIIの`:`、コロン後は半角空白1字とし、`作業種別`以外の値はバッククォートで囲む。

```md
- 起動経路: `<skillまたは起動経路>`
- 対象リポジトリ: `/absolute/repository/path`
- 作業種別: バグ対応
- ベースコミット: `<完全OID>`
```

`作業種別`の固定値は`バグ対応`または`通常変更`とする。
本4行は構造検査、フィードバック登録、2系統のPreToolUseが共有parserで読む正規形であり、
別の見出しへ複製しない。

### 提示素材

素材単位の安定ID（`P-001:`等）を置き、直後の`text` fenceへユーザー発言、
フィードバック原文、エラー出力を一字一句転記する。
意味を保つ整形、要約、順序変更も許可せず、原文が存在しない項目を捏造しない。
レビューは要約ではなく本節の原文から目的と適用範囲を再確認する。

### ユーザー合意済み事項

`合意事項`、`適用範囲`、`原文参照`の3列表を1行以上置く。
`適用範囲`には合意が及ぶ対象と、及ばない対象を書く。
`原文参照`には提示素材の安定IDだけを書き、要約で原文を置き換えない。

### バグ調査結果

作業種別が`バグ対応`の場合だけ置く。
バグ単位ごとにH3見出しを置き、`項目`と`内容`の2列表へ次の14行を固定順で書く。

観測事象、期待する契約、直接的原因、混入要因、動機的要因、見逃し原因、根本原因、
原因分析の根拠、類似見直しの観点、類似見直し結果、是正処置、横展開処置、再発防止処置、設計意図の記録。

`観測事象`には発生条件と実際値を含める。
各行の意味契約は`agent-toolkit:bugfix`の`references/root-cause-analysis.md`に従う。

### 実施内容

`実施内容`、`ユーザー指示との関係`、`根拠`の3列表を1行以上置く。
第2列は`指示どおり`、`具体化`、`エージェント追加`のいずれかに限る。

- `指示どおり`: ユーザー指示が明示した内容をそのまま実施する
- `具体化`: ユーザー指定の外部可視要素を維持したまま内部詳細を確定する
- `エージェント追加`: ユーザー指示に無い対象を追加する

`具体化`と`エージェント追加`は`根拠`列へユーザー指示との差分と必要性を書く。

### 恒久化・リファクタリング内容

3つのH4をすべて置く。
`なし`、`不要`、`該当なし`だけの記載は検討の省略として成立せず、
対象、比較、確認結果、理由を記載する。

- `#### 恒久化`: 通常変更では対象ごとに`観測事象`、`根本原因`、`反映先`、`反映内容`、`対策強度`の5行表を置く。
  バグ対応ではバグ調査表の是正・横展開・再発防止・設計意図の記録を正本として参照し、同じ説明を複製しない
- `#### リファクタリング`: 対象ごとに`対象`、`現状の問題`、`対応`、`本計画に含めるか`の4行表を置く
- `#### 類似見直し`: 通常変更では`母集団`、`点検観点`、`該当件数と箇所`の3行表を置き、件数は実測コマンドとその出力を根拠にする。
  バグ対応ではバグ調査表の類似見直しの観点・類似見直し結果を正本として参照し、同じ説明を複製しない

### 対象ファイル一覧

実装者向け領域へ`### 対象ファイル一覧`を一意に置き、全対象を通常箇条書きで列挙して対象範囲のSSOTとする。

```text
- `<パス>`
- `<パス>`（新設）
- `<パス>`（削除）
```

パスは対象リポジトリ相対で記載する。
既存対象、新設対象、削除対象の注記はベースコミット上の状態と一致させる。
同じパスを重複させず、コードフェンス内の類似箇条書きは対象一覧に数えない。
各パスは、個別の説明または明示したファイル群のいずれかから変更契約を特定できる状態にする。
同じパス集合を所属表やファイル別見出しへ重複して記載しない。

### 保持対象

ユーザーが維持を明示した契約を持つ計画だけ、実装者向け領域へ`### 保持対象`を置く。
`対象`、`箇所`、`保持する契約`、`原文参照`、`確認方法`の5列表へ、ファイルと節名、
frontmatterの項目名など編集で変動しにくい箇所を列挙する。
保持対象が無い計画に空の表を置かない。
実装後と各review反映後に列挙箇所をベースコミットと比較し、差分が必要な場合は実装で確定せずモード別の確認へ送る。

計画が増加または削減などの方向や数値目標を定める場合は、完了条件へ基準値、期待する方向または目標、
同じ条件で再実行できる測定方法を記載する。
各reviewラウンド後に再測定し、採用の累積が逆行して合意変更となる場合は追加採用を止めてモード別の確認へ送る。
累積結果は計画とGitから毎回再計算し、別の永続状態を新設しない。

### 進捗ログ

`日時`、`完了した工程`、`結果・特記事項`の3列表を1行以上置く。
本表は実装工程の作業状況追跡に使い、異常終了からの再開に必要な現在状態を残す。
`結果・特記事項`にはcommit、検証結果、計画との差異、blockerを必要な範囲で書く。
レビュー指摘の採否は本表へ書かず、`## 変更履歴`へ記録する。
計画作成中は調査とレビューの工程完了をauthorが記録する。
実装開始後は呼び出し元を既定の書込主体とし、各commit単位の受領時と最終レビュー時に行を追記する。
完了報告の直前には`## 完了条件`を全文再読し、各条件の充足根拠または未達理由を進捗ログの最終行へ記録する。

### 復元・巻き戻し型の変更

過去の契約へ戻す変更と、過去の契約を撤去する変更では、例示された項目だけを調べない。
対象項目ごとに過去の契約と導入目的を調べ、維持、修正、撤去を項目別に判定してから計画へ反映する。
判定結果と根拠は初回レビューの入力に含める。

### 機械検査

`scripts/check_plan_file.py`が計画の構造と実体を機械検査する。検査する項目は同スクリプトを正本とする。
`--base-commit`指定時は`<base>..HEAD`のコミット済み差分と対象一覧の不一致もエラーにする。
未コミットの作業ツリー差分は照合対象に含めないため、起草直後の初版検査ではオプションを指定せず、
実装コミットの作成後の最終照合だけで指定する。
原文と要約の意味照合、根拠の妥当性、検討の実質はレビューで確認する。

構造定数と値抽出は`agent-toolkit/scripts/_plan_format.py`を正本とし、
構造検査、フィードバック登録、2系統のPreToolUseは同じ共有結果を使う。

## 計画ファイルの保存

保存先は`~/.claude/plans/`配下とし、既存ファイルと衝突しない乱数サフィックス付きのパスを使う。
保存直後に同じパスを読み戻し、本文全体が保存されている状態を確認する。
既存計画は改名せず、同じパスを改訂する。

計画ファイルは監査や中断後の再開に利用できる作業記録として扱うが、永続保持を保証しない。
実行主体は完了後も明示的に削除せず、外部の処理による消失を許容する。
消失時の復旧、保持期限の管理、実行完了後の継続的な保守は行わない。

## 計画作成プロセス自体を変更する場合

工程、検査、レビュー経路を追加する改訂では、同一改訂内で簡素化または撤去も比較する。
恒常費に見合わない工程を追加しない。
