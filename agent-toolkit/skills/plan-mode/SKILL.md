# 計画モード

計画ファイルを作成し、実装を`plan-impl-executor`へ引き継ぐ。
計画ファイルは実装者が再調査せず着手でき、コンテキストを引き継がないサブエージェントが単独で読んで完遂できる状態を満たす。

## 進め方

1. 「計画ファイルの完成条件」を満たせる状態まで調査する。
   コードベース・公式ドキュメント・実機実行で確定できる事項は、質問へ回す前にすべて確定させる。
   併せて対象タスクが該当する設計領域を列挙する。`agent-toolkit:coding-standards`の
   `references/design-heuristics.md`が該当領域を収録していれば定石・トレードオフ・陥りやすい誤りを
   確認し、未収録の領域についても各自の定石・トレードオフ・陥りやすい誤りを自問してから方針を確定する。
   想起した結果のうち計画へ影響した判断は`### エージェント判断`等の既存節へ記録する
   （新規節は追加しない）。設計領域の列挙・設計観点の確認・判断記録は努力目標とする
   （未実施でも計画ファイル自体は完成条件を満たし技術的に成立し、設計品質の底上げに資する
   性質の指針であるため）。
   新設するフィールド・引数・サブコマンドを含む計画では、それらが既存の共有関数・
   既存のエラー処理経路の呼び出し契約と矛盾しないかを工程3の委譲より前に確定する。
   確定は呼び出し元自身の調査、または設計調査を目的とした委譲で行い、
   確定結果を工程3の起動プロンプトの`## 合意済み事項`・`## 照合結果`へ含める。
   `plan-file-creator`はSonnet固定の窓口として転記・整形・委譲仲介を担うため、
   設計上の対立点の解消を同エージェントへ委ねる形の委譲を避ける（厳守規定。
   未確定のまま委譲すると計画レビューで設計不整合の指摘が反復し、計画が収束しないため）
2. 調査で確定できない論点（ユーザーの意図・選好・優先度）が残る場合に限り、
   `AskUserQuestion`でまとめて確認する。各論点には推奨案を併記し第1選択肢へ置く
   （調査を経ずに質問を組み立てない。調査前の時点では論点の妥当性も選択肢の技術的成立性も
   判断できない）
3. Agentツールで`plan-file-creator`を起動する。起動プロンプトは
   `references/plan-file-creator-prompt-template.md`が定める必須見出し4点
   （`## 計画ファイルパス`・`## permission_mode`・`## 合意済み事項`・`## 照合結果`）を満たす形で構成し、
   対象ファイル一覧と、フィードバック原文・ユーザー発話・エラー出力といった原文素材を
   `### 提示素材`へ転記する旨を含める。コーディングエージェント向け文書が含まれるかの判定は
   `plan-file-creator`が自律的に行う（`plan-file-creator.md`「入力」節が規定済み）。
   計画ファイルの起草は`plan-file-creator`配下の`plan-codex-delegate`（用途: 計画作成）へ
   委譲する構成である。メイン側・`plan-file-creator`自身も直接起草しない既定経路のほか、
   次の例外がある：MCP不可時は`plan-file-creator`自身の直接起草へフォールバックし、
   auto modeでの起動ブロック時は`plan-file-creator.md`「エスカレーション基準」節（SSOT）に従い
   呼び出し元が直接起草するか、計画レビュー時はcodexレビューを代行する。
   同一テーマを複数計画へ分割して並列起草する場合、各`plan-file-creator`起動プロンプトへ
   他計画が専任する対象ファイルと主題の除外一覧を含める。起草担当は自計画の対象が
   除外一覧と重複しないことを完成条件の確認に含める
4. 計画ファイルの完成後、`references/codex-review.md`に従いcodexレビューを実施する。
   `plan-file-creator`へ委譲した経路では同エージェントが内部で実施するため、完了報告を2点で検収する。
   `invoked_subagents`欄に`codex-review`が含まれること、`review_summary`欄がレビューごとの
   指摘件数と反映内容を示していることとする。`invoked_subagents`欄が欠ける場合はMCPが利用可能なら
   呼び出し元から実行し、`review_summary`欄が欠ける場合は実装工程へ進まず委譲先へ照会して受領する。
   委譲先が受領できない場合は呼び出し元が当該レビューの記録から指摘本文を取得する
5. plan mode下では`ExitPlanMode`で承認を得る。承認後（またはplan mode外では直ちに）Agentツールで`plan-impl-executor`を起動する

バグ・障害・エラー・デグレードへの対応は`references/bugfix.md`に従う。判定がつかない場合はバグ対応として扱う。

## 計画ファイルの完成条件

H2の構成を次の順で固定する。各節の記載要件を満たした時点で計画ファイルは完成とする。
記載要件を満たすために必要な調査は、計画ファイルを書く前に済ませる。
判断・調査・ユーザー確認はすべて計画ファイル内で確定し、実装段階への先送り表現は書かない。
既存パスは実在確認し、新規作成予定パスは`（新設）`を付けて親ディレクトリの実在を確認する。

### `## 変更履歴`

方針転換・全面改訂・却下の履歴のみを時系列で残す。通常の指摘反映は`## 変更内容`本文を直接更新する。

### `## 背景`

なぜこの変更をするか。次のH3で分類する（該当なしは省略する）。

- `### 計画メタ情報`（必須）: 起動経路と対象リポジトリ
- `### 経緯`: 動機・依頼内容・期待する成果
- `### 現状`: 現行の挙動・構成・問題点
- `### 提示素材`: ユーザー発話・フィードバック原文・エラー出力を原文のまま転記する（`text`コードブロックで包む）
- `### バグ調査結果`: バグ対応時のみ。`references/bugfix.md`が定める表形式で記載する

### `## 対応方針`

- `### ユーザー合意済み事項`: ユーザーの発話・確認で合意した事項のみ。推測・既定判断は含めない
- `### エージェント判断`: ユーザー指示外で確定した事項。撤廃・削除では対応範囲を明示する
- `### 却下した代替案`: 選択肢になり得たが採らなかった案（無い場合は「なし」）
- `### 恒久化・リファクタリング内容`: 次の3節を必ず置く。該当なしでも節を残し「なし」と根拠を書く。
  各節配下の書式（H5見出し＋項目・内容の2列表）は努力目標とする
  （可読性向上が目的であり、既存計画への遡及適用は求めない）
  - `#### 恒久化`: 対象ごとに`##### <対象の要約>`見出しを設け、配下へ項目・内容の2列表
    （観測事象・根本原因・反映先・反映内容・対策強度の5行）を置く。対策強度は仕組み・機械チェック・
    規範文書の順で上位から成立可否を評価し、下位選定時は上位不成立の根拠を書く
  - `#### リファクタリング`: 対象ごとに`##### <対象の要約>`見出しを設け、配下へ項目・内容の2列表
    （対象・現状の問題・対応・本計画に含めるかの4行）を置く
  - `#### 類似見直し`: 対象ごとに`##### <対象の要約>`見出しを設け、配下へ項目・内容の2列表
    （母集団・点検観点・該当件数と箇所の3行）を置く。母集団は修正対象が属するカテゴリ全体とする

### `## 調査結果`

既存コードの挙動・依存・制約を、実装者が再調査せず着手できる粒度で書く。

- `### 対象ファイルの現状`: 対象ファイルの`wc -l`実測値
- `### 事実確認済み事項`: 計画が依存する前提を、確認手段（`grep`結果・`Read`箇所・実機実行の出力）とともに1行ずつ列挙する
- 既存コードの変更を含む計画では、変更対象を参照する既存テストを`grep`で検索して列挙し、
  変更が当該テストの前提を崩すかを確定して`### 事実確認済み事項`へ記載する
  （厳守規定。既存テストの見落としは実装段階で技術的な不成立（テスト失敗の見過ごし）に
  直結するため）。
  新規テストで非公開の要素を対象にする場合は`agent-toolkit:coding-standards`
  `references/testing.md`のprivate関数直接テスト禁止規定・`references/python.md`の
  保護メンバー参照に関する規定に従い、静的解析の制約への対処方針も記載する
- 遡及スキャン結果: `## 変更内容`「対象ファイル一覧」節が定める発動条件に該当する編集を伴う場合、
  対象パターン・検出件数・対応方針の3語をリテラル文字列として本節へ記載する
  （専用のH3見出しは要求しない）。3語は`check_plan_file.py`の機械検査でAND条件として照合される。
  検出件数と併せて計測に用いたコマンドも記載する。実装後の増加確認は当該コマンドを再実行して行う。
  本要件は当該項目を記載する計画（新規作成・改訂を問わない）に適用し、既存計画への遡及適用は求めない

推測のまま前提へ採用すると計画全体が破綻する事項（外部ツールの挙動・ライブラリの仕様・環境条件）は、
実機で確認してから本節へ書く。
退避・復旧・巻き戻しなど、失敗すると元の状態を失う手順を計画へ記載する場合は、
各操作の動作を一次資料または実機で確認する。
手順全体が目的の状態へ到達することを確定し、確認結果を`### 事実確認済み事項`へ記載する。

### `## 変更内容`

冒頭に`### 対象ファイル一覧`を置き、変更対象を`- [ ] <パス>（現行N行、または（新設）／（廃止・削除））`形式で全件列挙する。
続けてファイルごとに``### `<パス>` ``のH3を置き、一覧の項目と1対1で対応させる。
各H3配下に変更後の最終文面・差分のいずれかを`text`コードブロックで埋め込む。計画本文のみで変更を再現できる粒度とする。
差分は既存箇所との対比・追記・全文置換のいずれかが明確に分かる形で書けばよく、専用ラベル体系は要求しない。
削除ファイルは「削除する」旨と退避先（該当する場合）を明示すれば足り、全文転記は求めない。
Markdown文書の箇条書き行や見出し行など、行頭に記号を持つ行は差分記号と衝突し得る。
変更後の文面が一意に定まらない場合は差分形式を使わない。
変更前の文面と変更後の文面を、それぞれ独立した`text`コードブロックで示す。

埋め込む内容がフェンスを含む場合、外側フェンスは内側の最長フェンスより長くする（`check_plan_file.py`が機械検出する）。

対象は`pretooluse.py`の`_plan_format.is_agent_doc_target_file`が判定する、
コーディングエージェント向け文書を含む計画とする。
判定対象は次のとおり。

- `agent-toolkit/rules/`・`agent-toolkit/skills/*/SKILL.md`・
  `agent-toolkit/skills/*/references/`・`agent-toolkit/agents/`・`agent-toolkit/references/`配下
- `.chezmoi-source/dot_claude/rules/`・`.chezmoi-source/dot_claude/skills/`配下
- ファイル名が`AGENTS.md`・`CLAUDE.md`のもの

次のいずれかに該当する編集を伴う場合を発動条件とし、遡及スキャン結果の記載形式は
`## 調査結果`の記載要件（「遡及スキャン結果」項）を参照する。

- 「いかなる理由（例）があっても〜しない」形式の全称禁止表現の新規出現
  （バレット冒頭に限らず、本文中の任意の位置への出現も対象とする）
- 行頭記号直後から80文字以内に「しない」「禁止する」「発行しない」「省略しない」が
  句点または行末で続く汎用禁止形バレットの増加
- `##`以上の見出しの件数増加

計画がスキル廃止・ファイル削除・識別子改名を含む場合、`#### 廃止・改名対象一覧`H4節を配置し
削除・改名する識別子（スキル名・パス・関数名等）をバッククォート付きで列挙する。

### `## 実行方法`

実装からコミットまでを実行順に箇条書きで書く。標準の順序は実装 → 検証 → コミット → レビューとする。
`git push`とCI通過確認はセッション運用工程（呼び出し側の完遂順序、
`agent-toolkit/references/plan-impl/caller-reception.md`が定める）であり計画へ記載しない。
本節は当該計画の実装・検証・コミット・レビューに限定し、セッション運用工程は記載しない（`check_plan_file.py`が機械検出する）。

検証は変更が壊し得るものを確かめる手段を書く。
結果が自明な変更（一時ファイルの削除・定数値の変更など）へ形式的な存在確認を並べない。

コミットは`agent-toolkit:commit`の規約に従い、件名案を添える。
レビューは`agent-toolkit:careful-review`を既定とする。
ユーザーが不要と指示した場合のみ「レビューは実施しない」と書く。

### `## 進捗ログ`

実装中に節目ごとで追記する。初版作成時は空でよい。

### `## 計画ファイル（本ファイル）のパス`

末尾に絶対パスを書く。保存先は`~/.claude/plans/<stem>-<rand>.md`とする。
`<rand>`は`openssl rand -hex 2`の実行結果である16進4桁とし、生成側が値を考えて書かない。
並行セッションが同一の主題名を選んだ場合の上書きを防ぐためである。
起草の前に`(set -o noclobber; : > <保存先>)`で保存先を確保し、非ゼロ終了なら乱数を取り直す。
確保に成功したパスへ本文を書き込む。
乱数の値域は65536通りで、同一主題名かつ同一乱数の同時選択を確率だけでは排除できないためである。
存在確認と作成を別操作に分けると、双方が不在確認を通過して後着が先着を上書きする。
`noclobber`下のリダイレクトは作成と占有を1操作で行うため、当該競合が成立しない。
既存の計画ファイルは改名しない。改訂時は既存パスをそのまま使う。

## 計画作成プロセス自体を変更する場合

本スキル・配下referencesの工程・チェック項目・レビュー経路を追加する改訂では、
同一改訂内で同等以上の削減を併せて検討し結果を`#### リファクタリング`表へ記録する。追加のみの一方向の改訂をしない。
削減案を検討結果として記載した場合、当該削減が`## 変更内容`の変更後文面へ実際に反映されていることを
計画の確定前に照合する。照合は削減対象として挙げた記述が変更後文面から実際に消えているかを確認する形で行う。
