# 計画モード

計画ファイルを作成し、実装を`plan-impl-executor`へ引き継ぐ。
計画ファイルは実装者が再調査せず着手でき、コンテキストを引き継がないサブエージェントが単独で読んで完遂できる状態を満たす。

## 進め方

1. 「計画ファイルの完成条件」を満たせる状態まで調査する。
   コードベース・公式ドキュメント・実機実行で確定できる事項は、質問へ回す前にすべて確定させる。
   併せて対象タスクが該当する設計領域を列挙する。`agent-toolkit:coding-standards`の
   `references/design-heuristics.md`が該当領域を収録していれば定石・トレードオフ・陥りやすい誤りを
   確認し、未収録の領域についても各自の定石・トレードオフ・陥りやすい誤りを自問してから方針を確定する。
   想起した結果のうち計画へ影響した判断は`### エージェント判断`等の既存節へ記録する
   （新規節は追加しない）。設計領域の列挙・設計観点の確認・判断記録は努力目標とする
   （未実施でも計画ファイル自体は完成条件を満たし技術的に成立し、設計品質の底上げに資する
   性質の指針であるため）。
   新設するフィールド・引数・サブコマンドを含む計画では、それらが既存の共有関数・
   既存のエラー処理経路の呼び出し契約と矛盾しないかを工程3の起草より前に確定する。
   確定は呼び出し元自身の調査、または設計調査を目的とした委譲で行い、
   確定結果を工程3で自ら起草する計画ファイル初版の`## 対応方針`配下（`### ユーザー合意済み事項`・
   `### エージェント判断`）へ含める。設計上の対立点は計画ファイル初版の起草前に確定する
   （厳守規定。未確定のまま起草すると計画レビューで設計不整合の指摘が反復し、計画が収束しないため）
2. 調査で確定できない論点（ユーザーの意図・選好・優先度）が残る場合に限り、
   `AskUserQuestion`でまとめて確認する。各論点には推奨案を併記し第1選択肢へ置く
   （調査を経ずに質問を組み立てない。調査前の時点では論点の妥当性も選択肢の技術的成立性も
   判断できない）
3. メイン側が計画ファイル初版を起草する。保存先の占有から初回`Write`までは
   「`## 計画ファイル（本ファイル）のパス`」節が定める順序で実施する。
   「計画ファイルの完成条件」節を満たす本文を書き込む。既存処理の移設または既存APIの呼び出しを含む記述が必要な場合は、
   対象リポジトリの実ファイルから対象実装の本体を取得し、引用形式で計画ファイルへ含める
   （シグネチャの記述だけでは推測による呼び出しを防げないため、実装本体を材料とする）。
   品質規範は`writing-standards`を常に適用し、コーディングエージェント向け文書判定が真の場合は
   `agent-standards`を、対象ファイル一覧にコード・テストコードを含む場合は`coding-standards`を
   追加適用する。あわせて`agent-toolkit:review-standards`「計画ファイル文脈での例外」節を
   起草時点で確認する。同スキルはレビュアー側の心得であり著者が全面適用する規範ではないが、
   計画レビューの指摘範囲を定める節であるため、起草時点で満たすべき水準を確定できる。
   同一テーマを複数計画へ分割する場合、各計画が専任する対象ファイルと主題が
   重複しないことを確認する
4. `references/plan-review-delegation.md`をReadし、同referenceが定める初回機械検査、
   比較基準の保存、総合レビュー、3区分の採否、反映、限定再レビューを呼び出し元が実施する。
   機械チェック・修正系と総合レビュー系は`agent-toolkit:codex-exec`を介して別系統で起動する。
   呼び出し元は各応答と成果物実体を検収し、指摘の採否とスコープ拡大の承認要否を確定する。
   未解決事項と再開状態は同referenceの返却契約に従い、正常完了後だけ一時ディレクトリを後始末する。
5. 計画の確定をユーザーへ提示する。提示内容は次の4点とし、計画ファイルの記載から引く。
   本スキル以外の経路（`agent-toolkit:process-feedbacks`・`agent-toolkit:plan-and-add-feedback`など）で
   計画ファイルを作成した場合も同じ提示をする。
   - 計画ファイルの絶対パスと、計画全体で成立させる結果の要約
   - `### 実施内容`表のうち`ユーザー指示との関係`が`具体化`または`エージェント追加`の行。
     `具体化`はユーザー要求を維持したまま実装詳細を確定した箇所、
     `エージェント追加`はユーザー要求へ対象を追加した箇所として区別して示す。
     ユーザー指示を実施しない箇所がある場合は、両区分と別に差分と理由を示す。
     自己生成起点の入力（`source: session-review`のフィードバックなど）に対する差分は対象外とする
   - `### エージェント判断`節のうち、前項の具体化・追加またはユーザー指示との差分の根拠となる判断
   - レビューの実施状況と、指摘の反映が完了したか否か
   plan mode下では`ExitPlanMode`で承認を得る。承認後（またはplan mode外では直ちに）
   `references/plan-impl-caller-reception.md`をReadする。
   同referenceの起動契約に対応する実行時の値だけで起動文を構成し、
   呼び出し元の読込対象は同referenceに限定する。
   `subagent_type: agent-toolkit:plan-impl-executor`を指定してAgentツールで起動する。
   完了報告の受領後は`references/plan-impl-caller-reception.md`に従う

バグ・障害・エラー・デグレードへの対応は`references/bugfix.md`に従う。判定がつかない場合はバグ対応として扱う。
すべてのバグ計画で、同referenceの「初動と深掘り判定」を直接的原因の確定直後に実施する。
事象の調査は、同referenceの「事象単位の並列調査委譲」節に従って独立事象ごとに委譲する。
深掘り条件に該当する場合だけ「深掘り資料と因果の確定」から「再発防止策」までを適用し、判定結果を「計画ファイルへの集約」に記録する。

## 計画ファイルの完成条件

H1はファイルの先頭行へ、先頭空白のないATX形式`# <主題>`で1件だけ置く。
計画全体で成立させる主題を簡潔に示す。
先頭行を除く0〜3個の先頭空白を持つATX形式と、非空行直後の`=`下線は、
追加H1または不正形式として扱う。

H2の構成を次の順で固定する。各節の記載要件を満たした時点で計画ファイルは完成とする。
記載要件を満たすために必要な調査は、計画ファイルを書く前に済ませる。
判断・調査・ユーザー確認はすべて計画ファイル内で確定し、実装段階への先送り表現は書かない。
既存パスは実在確認し、新規作成予定パスは`（新設）`を付けて親ディレクトリの実在を確認する。

`### 実施内容`・`### ユーザー合意済み事項`・`## 変更内容`の3節は、計画レビューが
初版のスコープ基準として保存し、以降の各ラウンドで差分を照合する対象となる。
これら3節を確定しないままレビューへ渡すと、以降の変更のうち対象パス・成果・合意・
利用者が観測する挙動のいずれかを変えるものがスコープ拡大として区分され、
呼び出し元の承認を要するラウンド外の往復が生じる。

### `## 変更履歴`

計画の改訂過程を監査できる要約として、初版、レビュー指摘、ユーザー指摘、方針転換、
全面改訂、却下を時系列で残す。`## 変更内容`は実装する最終状態の正本とする。
全面改訂でも既存履歴を保持する。

レビュー指摘とユーザー指摘は1件につき物理1行で記録する。
指摘要約、採否、採用時の反映内容または不採用理由、同期先の見出しを含める。

```text
- レビュー指摘（第Nラウンド・指摘M）: <要約>。採用: <反映内容>。同期先: <見出し>
- ユーザー指摘（N件目）: <要約>。不採用: <理由>。同期先: なし
```

指摘反映前に旧表現、新表現、関連識別子を抽出し、計画全文の出現箇所を列挙する。
履歴資料を除く現在状態の全記述へ同じ判断を同期する。
反映後は差分と旧表現・新表現双方の検索結果を確認し、現在状態へ旧判断が残っていないこと、
新判断が依存箇所へ反映されたことを確定する。

方針転換を記録した場合、計画の確定前に本文全体を遡及点検する。
判定基準は、方針転換前に確定した記述のうち転換後の方針を前提としないものが残っていないかとする。
点検対象は方針転換前に確定した節を含む本文全体とし、`### 却下した代替案`の却下理由・
削除対象への参照・部分適用の設定方針・`### 事実確認済み事項`の記述は、
転換の影響を受けやすいため優先して確認する。

### `## 背景`

なぜこの変更をするか。次のH3で分類する（該当なしは省略する）。

- `### 計画メタ情報`（必須）: 起動経路・対象リポジトリ・ベースコミット・作業種別
  （ベースコミットは`git rev-parse HEAD`の実測値とする）。
  環境変数`DOTFILES_AUTONOMOUS_EXIT_REQUIRED`が設定されていないセッションは、
  並行稼働セッションが対象ファイルへコミットしうる旨と実装着手時の再確認手順への参照を付記する
  - 作業種別は`- 作業種別: <固定値>`形式で記載する。コロンはASCIIの`:`、コロン後は半角空白1字とし、
    固定値には`バグ対応`または`通常変更`を用いる
    判定がつかない場合は`バグ対応`とする
- `### 経緯`: 動機・依頼内容・期待する成果
- `### 現状`: 現行の挙動・構成・問題点
- `### 提示素材`: ユーザー発話・フィードバック原文・エラー出力を原文のまま転記する（`text`コードブロックで包む）
- `### バグ調査結果`: バグ対応時のみ。文書全体で1件だけ置き、その親H2を`## 背景`とし、
  `references/bugfix.md`が定める表形式で記載する

### `## 対応方針`

- `### 実施内容`（必須）: 実装後に成立させる変更を結果単位で先に要約する。
  `実施内容`・`ユーザー指示との関係`・`根拠`の3列表で記載する。
  `ユーザー指示との関係`は`指示どおり`・`具体化`・`エージェント追加`のいずれかとする。
  `具体化`は、ユーザーが指定していない内部実装詳細を確定し、明示された外部可視のコマンド、
  引数、操作順序、入出力、公開インターフェースを維持する場合に限る。
  明示された外部可視要素を変更する案は`具体化`に分類せず、`### ユーザー合意済み事項`へ合意を記録する。
  `具体化`と`エージェント追加`は、根拠列へユーザー指示との差分理由を書く。
  `エージェント追加`の可否は、計画の主目的の達成に必要かで判定する。対象ファイルや対象範囲が
  本計画と重複することを追加の根拠にしない。主目的の達成に必要でない項目は、対象範囲が重複していても
  当該計画へ含めず`atk mq add`で登録する。
  ファイル別の差分、調査根拠、判断経緯は後続節へ記載し、本節へ重複転記しない
- `### ユーザー合意済み事項`: ユーザー自身の発話、または確認への回答として観測できた合意に限り、
  実施内容表だけでは失われる制約と詳細だけを書く。
  呼び出し元エージェントが確定した採否・承認は当該節へ書かず、`### エージェント判断`へ
  判断根拠とともに記録する。
  該当がなければ`なし`と記載する
- `### エージェント判断`: ユーザー指示外で確定した事項のうち、
  実施内容表だけでは失われる詳細な判断と根拠だけを書く。
  撤廃・削除では対応範囲を明示し、該当がなければ`なし`と記載する
- `### 却下した代替案`: 選択肢になり得たが採らなかった案（無い場合は「なし」）
- `### 恒久化・リファクタリング内容`: 次の3節を必ず置く。該当なしでも節を残し「なし」と根拠を書く。
  各節配下の書式（H5見出し＋項目・内容の2列表）は努力目標とする
  （可読性向上が目的であり、既存計画への遡及適用は求めない）
  - `#### 恒久化`: バグ対応では`### バグ調査結果`の処置3行と設計意図の記録を正本とし、
    本節は「バグ調査結果表に記載」とする。バグ以外は対象ごとの5行表を使う
  - `#### リファクタリング`: 対象ごとに`##### <対象の要約>`見出しを設け、配下へ項目・内容の2列表
    （対象・現状の問題・対応・本計画に含めるかの4行）を置く
  - `#### 類似見直し`: バグ対応では`### バグ調査結果`の類似見直し2行を正本とし、
    本節は「バグ調査結果表に記載」とする。バグ以外も表面上のカテゴリではなく、
    同じ判断・設計・見逃し構造が成立する母集団、点検観点、該当件数と箇所を記載する。
    バグ以外で該当件数と箇所を記載する場合は、母集団抽出に用いた実測コマンドとその出力を
    典拠として併記し、出力の各行が対象ファイル一覧の項目または非該当の根拠のいずれかへ
    1対1で対応することを確認してから件数を確定する。母集団の確定は判断規則に基づいて行い、
    実測コマンドの出力は件数の裏付けとして用いる（`references/bugfix.md`「類似見直し」節が
    定めるとおり、検索一致だけで類似性を確定しない）

### `## 調査結果`

既存コードの挙動・依存・制約を、実装者が再調査せず着手できる粒度で書く。

- `### 対象ファイルの現状`: 対象ファイルの`wc -l`実測値
- `### 事実確認済み事項`: 計画が依存する前提を、確認手段（`grep`結果・`Read`箇所・実機実行の出力）とともに1行ずつ列挙する
- 既存コードの変更を含む計画では、変更対象を参照する既存テストを`grep`で検索して列挙し、
  変更が当該テストの前提を崩すかを確定して`### 事実確認済み事項`へ記載する
  （厳守規定。既存テストの見落としは実装段階で技術的な不成立（テスト失敗の見過ごし）に
  直結するため）。
  テストランナーの実行オプション・並列度・分配方式・タイムアウトなど、テストコードから
  参照されずに実行条件を変える設定を変更する計画では、文字列検索で影響を検出できない。
  この場合は検索による列挙に代えて、設定の参照元、対象版の公式仕様、既存テストへの影響を確定し、
  `### 事実確認済み事項`へ記載する。
  変更後の設定によるテストスイート実行は実装後の検証へ記載する。
  計画段階で実測する場合は、コマンドラインでの上書きなど、実ファイルの変更を要しない手段に限定する。
  新規テストで非公開の要素を対象にする場合は`agent-toolkit:coding-standards`
  `references/testing.md`のprivate関数直接テスト禁止規定・`references/python.md`の
  保護メンバー参照に関する規定に従い、静的解析の制約への対処方針も記載する
- 設定の既定値・定数・公開インターフェースの値を変更する計画では、既存テストの列挙に加えて、
  当該値を参照する実装コードを`grep`で検索して列挙し、変更が各参照箇所の前提を崩すかを確定して
  `### 事実確認済み事項`へ記載する。検索は値そのものと、値を保持するキー名の双方を対象とする
- 参照追従の網羅列挙: 変更対象の識別子・規定・パスを参照する既存箇所を`grep`で全件列挙し、
  各件の追従要否を判定した結果を記載する
  - 本項は`### 対象ファイル一覧`へ`（新設）`マーカーを持たない項目を1件以上含む計画に適用する。
    適用対象は新規作成の計画と既存計画の改訂の双方とし、既存計画を改訂する場合も
    確定前に必須3語を追記する（機械検査は計画ファイル全体を毎回検査するため、
    3語を欠く既存計画は改訂時の再検査でexit 1となる）
  - `参照追従対象`・`入力形態`・`追従要否`の3語をリテラル文字列として本節へ記載し、
    列挙に用いたコマンドと検出件数も併記する
    （`check_plan_file.py`の機械検査がAND条件として照合する。error区分。不足はexit 1となる）
  - 必須3語の記載義務は他バレットの発動状況にかかわらず維持する
  - 解析処理（正規表現・パーサー・突合条件）の新規作成または変更を含む場合は、
    `agent-toolkit/rules/01-agent.md`「調査と検証」節が定める入力形態の網羅列挙を適用し、
    対象の命名規則・出力仕様が生成し得る形態を`入力形態`として列挙する。
    含まない場合は`入力形態: 該当なし`と記載して充足させる
  - 既存テストの`grep`列挙と遡及スキャン結果は、それぞれの記載要件に従って列挙内容を具体化する
- 実行契約: `### 計画メタ情報`へ`- 実行系変更: あり|なし`を1件記載する。
  CLI・hook・状態遷移・自動化のいずれかを新設または変更する場合は`あり`とし、
  `## 調査結果`配下へ`### 実行契約`表を置く。
  表は変更単位・入力・起動契機・実行主体・SSOT・出力形式と終了状態・検証主体・テスト対象の8列を
  この順序で持ち、変更単位ごとに1行以上記載する。実行系を変更しない計画は`なし`とし、表を要求しない
- 先行計画適用後の状態投影: `### 計画メタ情報`が先行計画を挙げる場合、当該計画の適用後に
  各対象が新設・既存・削除・改名のいずれの状態になるかを投影してから`### 対象ファイル一覧`を確定する。
  現時点の実在状態だけで判定しない
- 新設識別子の波及先列挙: 本計画で新たに導入する識別子（欄名・定数名・環境変数名など）のうち、
  リポジトリ内の既存出現が0件のものを列挙し、当該識別子を保持すべき文書・実装・機械検査の一覧と、
  `### 対象ファイル一覧`との突合結果を記載する。
  既存出現が0件の識別子は参照追従の`grep`で波及先を列挙できないため、
  波及先の特定を計画作成時に前倒しする。
  該当が無い場合は`新設識別子: 該当なし`と記載する
  （`check_plan_file.py`の機械検査が必須語`新設識別子`と各識別子の名称を照合する。warning区分）
- 遡及スキャン結果: `## 変更内容`「対象ファイル一覧」節が定める発動条件に該当する編集を伴う場合、
  対象パターン・検出件数・対応方針の3語をリテラル文字列として本節へ記載する
  （専用のH3見出しは要求しない）。3語は`check_plan_file.py`の機械検査でAND条件として照合される（error区分。不足はexit 1となる）。
  検出件数と併せて計測に用いたコマンドも記載する。実装後の増加確認は当該コマンドを再実行して行う。
  本要件は当該項目を記載する計画（新規作成・改訂を問わない）に適用し、既存計画への遡及適用は求めない

推測のまま前提へ採用すると計画全体が破綻する事項（外部ツールの挙動・ライブラリの仕様・環境条件）は、
実機で確認してから本節へ書く。
他リポジトリでの実測結果を根拠として同じ対象を自リポジトリの計画へ転記する場合も、
自リポジトリの環境で再実測してから書く。ツールの版は環境ごとに異なりうるため、
他リポジトリの実測は自リポジトリでの成立を保証しない。
実測手順と結果は`### 事実確認済み事項`へ記載する。
退避・復旧・巻き戻しなど、失敗すると元の状態を失う手順を計画へ記載する場合は、
各操作の動作を一次資料または実機で確認する。
手順全体が目的の状態へ到達することを確定し、確認結果を`### 事実確認済み事項`へ記載する。

### `## 変更内容`

冒頭に`### 対象ファイル一覧`を置き、変更対象を次の記法で全件列挙する。

```text
- [ ] `<パス>`（現行N行）
- [ ] `<パス>`（新設）
- [ ] `<パス>`（現行N行、廃止・削除）
```

各項目と1対1で対応するファイル別H3は、対象ファイル一覧と同じ表記でパスをバッククォートで囲む。

```text
### `<パス>`
```

未チェックのチェックボックスとバッククォートで囲んだパスは、機械検査が対象パスを抽出するための固定記法である。
バッククォートを省くと、対象ファイル一覧とファイル別H3のいずれでも抽出対象から外れる。
チェックボックス側だけを省いた場合はファイル別H3との1対1対応が崩れ、終了コード1で停止する。
チェックボックスとファイル別H3の双方で省いた場合は抽出対象が空になり、
参照追従の必須3語などの検査が発動しないまま終了コード0となる。
実装の完了状態を示す目的で完了マークへ書き換えた場合も、対象パスを抽出できなくなり検証が失敗する。
ファイル別H3配下には、変更後の最終文面か差分を`text`コードブロックで示す。
既存箇所との対比、追記、全文置換の別を判別でき、計画本文だけで変更を再現できる粒度とする。
削除ファイルは削除する旨と退避先がある場合のパスを明示する。
埋め込む内容がフェンスを含む場合は、外側のフェンスを内側の最長フェンスより長くする
（`check_plan_file.py`が機械検出する。error区分。違反はexit 1となる）。

関係性や分岐、時系列、階層などの、構造が複雑な箇所は、文章や小表より理解しやすくなる場合に最小限の図を含める。
Mermaidを既定とし、自由配置や独自図形などMermaidで正確に表現しにくい場合に限りSVGを使う。
図はMermaidまたはSVGを言語指定したフェンスコードブロック（` ```mermaid `・` ```svg `）で埋め込む。
インラインSVGタグや言語指定なしのフェンスは図として処理されないため使用しない。
単純な情報を図へ置き換えず、実装に必要な識別子、条件、詳細は本文にも記載する。

差分・参照箇所の特定に行番号（`<ファイル>:<行番号>`形式・「N行目」等）を用いない。
H2・H3見出し名、または対象ファイル中の一意な既存文字列をアンカーとして用いる
（並行稼働セッションによるコミットで行番号がずれても、アンカーは対象箇所を特定できるため）。

対象は`pretooluse.py`と`check_plan_file.py`が参照する`_plan_format.is_agent_doc_target_file`が判定する、
コーディングエージェント向け文書を含む計画とする。
判定対象は次のとおり。

- `agent-toolkit/rules/`・`agent-toolkit/skills/*/SKILL.md`・
  `agent-toolkit/skills/*/references/`・`agent-toolkit/agents/`配下
- `.chezmoi-source/dot_claude/rules/`・`.chezmoi-source/dot_claude/skills/`配下
- `.claude/rules/`配下・`.claude/skills/*/SKILL.md`・`.claude/skills/*/references/`配下
- ファイル名が`AGENTS.md`・`CLAUDE.md`のもの

本列挙は`_plan_format.py`の`AGENT_DOC_TARGET_PATTERNS`・`AGENT_DOC_TARGET_BASENAMES`と同期する。

次のいずれかに該当する編集を伴う場合を発動条件とし、遡及スキャン結果の記載形式は
`## 調査結果`の記載要件（「遡及スキャン結果」項）を参照する。

- 「いかなる理由（例）があっても〜しない」形式の全称禁止表現の新規出現
  （バレット冒頭に限らず、本文中の任意の位置への出現も対象とする）
- 行頭記号直後から80文字以内に「しない」「禁止する」「発行しない」「省略しない」が
  句点または行末で続く汎用禁止形バレットの増加
- `##`以上の見出しの件数増加

計画がスキル廃止・ファイル削除・識別子改名を含む場合、`#### 廃止・改名対象一覧`H4節を配置し
削除・改名する識別子（スキル名・パス・関数名等）をバッククォート付きで列挙する。

### `## 実行方法`

実装からコミットまでを実行順に箇条書きで書く。
想定コミット単位ごとに対象実装、近接検証、差分確認、コミットを反復し、
全コミット完了後に計画全体の最終検証、レビューの順で進める。
想定コミット単位が1件の計画では、計画全体の最終検証を当該コミットの前に置く。
対象リポジトリの開発者向け規範が検証をコミット前の工程として定める場合は、当該規範を優先して実行順序を組む。
検証に用いるコマンドも当該規範が定める実行手段に合わせる。
規範が特定のツールの直接起動を禁じ、一括実行コマンドまたは品質チェックツール経由での実行を定める場合は、
当該制約が計画の検証工程にも及ぶ。
各中間`HEAD`は当該時点の公開契約とテストを満たす状態とする。
独立して検証できない変更は同一コミット単位へまとめる。
想定単位を順に実装する手順を記載し、実装済みの全変更から過去の境界を再構成する形を避ける。
環境変数`DOTFILES_AUTONOMOUS_EXIT_REQUIRED`が設定されていないセッションは、実装工程の冒頭へ
`git rev-parse HEAD`と`### 計画メタ情報`のベースコミットとの比較、差分がある場合の
アンカー該当箇所の再確認手順を置く。
本節の対象は、当該計画の実装・検証・コミット・レビューと、
当該計画が必要とする対象リポジトリ外への操作に限定する。
`git push`とCI通過確認を含むセッション運用工程の範囲は
`agent-toolkit/skills/plan-mode/references/plan-impl-caller-reception.md`が定める。
本節へは記載しない。
`check_plan_file.py`が機械検出する。warning区分のため終了コードへ算入されないが、
検出時は内容を確認して是正の要否を判断する。

当該計画が対象リポジトリ外への操作（他リポジトリへのフィードバック投入・外部サービスの設定変更など）を
含む場合は、操作と全対象を本節へ列挙する。本節の記載を認可根拠とする操作では、
記載の無い対象へ委譲先が及ぶことはない。
適用中の規範が義務づける登録操作（実装差分レビューで登録対象と定めた独立提案の
`atk mq add`登録など）は、当該規範自体を認可根拠とするため本節へ列挙しない。
認可根拠ごとの範囲は
`agent-toolkit/skills/plan-mode/references/plan-impl-caller-reception.md`「完了報告の検収」節が定める。

検証は変更が壊し得るものを確かめる手段を書く。
結果が自明な変更（一時ファイルの削除・定数値の変更など）へ形式的な存在確認を並べない。

検証コマンドは、対象リポジトリの規範文書が検証手順を定める場合、当該手順の起動経路に従う。
個別ツールの直接起動は、規範が当該経路を認める場合に限る。

コミットは`agent-toolkit:commit`の規約に従い、想定コミット単位ごとに対象、近接検証、件名案を添える。

件名案は`` - 件名案: `<件名>` ``の形式で記載する。
`check_plan_file.py`が`--base-commit`付きの実行で実際のコミット件名と対応を照合する。

同規約が本文（body）の記載を必須とするコミットでは本文案も併記する。
フィードバック採用を反映するコミットなどが該当する。
同規約が必須と定める行も本文案へ含める。
フィードバック採用起因コミットでは「再発予防: 」行が該当する。

実装差分に応じて単位を変更でき、変更時は通常の計画同期規定に従う。
レビューは`plan-impl-executor`が計画準拠系と独立系を並列実行する。
ユーザーが不要と指示した場合のみ`レビューは実施しない（ユーザー指示）`と書く。
直後の行へ`レビュー省略のユーザー指示原文: <原文>`を記録する。

### `## 進捗ログ`

実装中に節目ごとで追記する。初版作成時は空でよい。

### `## 計画ファイル（本ファイル）のパス`

末尾に絶対パスを書く。保存先は`~/.claude/plans/<stem>-<rand>.md`とする。
`<rand>`は`openssl rand -hex 2`の実行結果である16進4桁とし、生成側が値を考えて書かない。
並行セッションが同一の主題名を選んだ場合の上書きを防ぐためである。
起草の前に`(set -o noclobber; : > <保存先>)`で保存先を確保し、非ゼロ終了なら乱数を取り直す。
確保に成功した直後に同じパスを`Read`し、最初の編集で本文全体を`Write`する。
Claude CodeはBashが作成した空ファイルも既存の未読ファイルとして扱うため、この順序で本文の再送を防ぐ。
乱数の値域は65536通りで、同一主題名かつ同一乱数の同時選択を確率だけでは排除できないためである。
存在確認と作成を別操作に分けると、双方が不在確認を通過して後着が先着を上書きする。
`noclobber`下のリダイレクトは作成と占有を1操作で行うため、当該競合が成立しない。
既存の計画ファイルは改名しない。改訂時は既存パスをそのまま使う。

## 計画作成プロセス自体を変更する場合

本スキル・配下referencesの工程・チェック項目・レビュー経路を追加する改訂では、
同一改訂内で同等以上の削減を併せて検討し結果を`#### リファクタリング`表へ記録する。追加のみの一方向の改訂をしない。
削減案を記載した場合は、計画の確定前に当該記述が`## 変更内容`の変更後文面から消えていることを照合する。
