# リポジトリ変更の公開工程

「公開工程」とは、コミットの作成からバージョン（版数）更新、push、CI確認、公開状態の確認、およびプロジェクト固有の公開後作業までの一連の処理を指し、本書をその定義元とする。起動形態（協調モードや自律モードなど）にかかわらず、ユーザーの指示、確認に対する回答、または自律モードのスキル契約から認可された範囲を確定したうえで作業を進める。pushの実行およびCIの監視手順については、`references/push-and-ci.md`に従う。

## 公開範囲

協調モードにおける公開範囲の選択肢は、`agent-toolkit:user-confirmation-and-report`の`references/publish-scope.md`「公開範囲の確認」で定義されている。ユーザーからの依頼でプルリクエスト作成、リリース作成、タグ付けなどが明示的に求められている場合は、それらをプロジェクト固有の公開後操作として扱う。

| 範囲 | 実施する工程 |
| --- | --- |
| commitしない | 実装、変更箇所の検証、および必要な自動生成ファイルの同期を完了させ、コミットの手前で作業を終了する |
| commitまで | 必要なバージョン更新や自動生成ファイルの同期、検証を行い、コミットの完了まで進める |
| push・CIまで | コミットまでの工程に加えて、push、CI通過の確認、および公開状態の確認まで完了させる |
| 既存の判断基準どおり | push・CIまでの工程に続けて、プロジェクト規範に基づくリリース判定と、認可済みのプロジェクト固有の公開後操作を実施する |

`agent-toolkit:process-wi`および`agent-toolkit:process-wi single-lane`では、各スキルがあらかじめ定めた自律モード用の公開範囲を適用する。

## 版数と生成物

配布物のバージョン更新が必要な変更では、バージョニング規範と未プッシュの差分を突き合わせて必要な変更種別のうち最上位のものを採用する。そのうえで、バージョンの更新、派生マニフェストの同期、自動生成ファイルの同期確認、およびコミットを一連の作業として連続して実行する。同期が正しく行われたかどうかは、各ジェネレータが規定する対象ファイル群と終了コードによって判定する。
`agent-toolkit:process-wi`では、完了処理を担当するエージェントが、未プッシュの追加差分とすでに公開済みのバージョンを比較してバージョンを更新する。すでに公開されている成果を追加差分として重複計上してはならず、追加差分が存在しない再検収時にはバージョン更新やpushを省略する。
同一の公開先およびコミットに対するCIをすでに検収済みであればCI待機も省略する。CIの結果がまだ判定できていない場合は、後述の「公開工程の続行不能からの再開」へ進む。

プロジェクト固有の方針が定められていない場合は、以下の基準でバージョンを更新する。

- ユーザーが明示的に指定した区分（MAJOR、MINOR、PATCH）を最優先とする。
- MAJORバージョンの更新は、ユーザーからの明示的な指示がある場合に限る（これは後方互換性の破壊を外部に宣言する操作であり、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「認可を要する操作」における承認対象である）。
- 現在のバージョンが3つの数値からなるセマンティックバージョニング（SemVer）形式でない場合は、プロジェクト定義の対応表またはユーザーの明示指示に従って決定する。いずれの手がかりもない場合はバージョンを変更せず、判定不能となった根拠を報告する。

## 検証とCI

プロジェクト全体の検証は、push後に実行されるCIで最終確認する。そのためpush前の段階では、「CIでは実行されないチェック」と、「複数エージェントによる変更を統合したあとに初めて結果が確定する全体走査チェック（変更箇所以外からの静的参照、重複実装、ファイルをまたぐ循環importの有無など）」のみを実行する。変更範囲に限定した検証を、安易に一律の全体lint実行に置き換えない。
CIで実行されないチェックの対象範囲は、プロジェクト規範の定めに従う。明文の定めがない場合は、CIの実行設定、有効化されているチェック内容、参照設定、実行環境などを比較して特定する。対象を特定できない場合やCI定義が存在しない場合（`references/push-and-ci.md`「公開先に対応するCI定義の判定」を参照）は、タスクランナーによる全体検証をpush前に1回実行する。ただし、直前に同一ツリーで実行済みの結果がある場合は、それを再利用してよい。
CI定義の有無が未判定である場合も、「ローカルでの全体検証の成功」と「CI未判定」という2つの状態を明確に区別して保持する。
CI環境特有のOS、言語バージョン、実機環境など、ローカルでは再現できない条件に変更が及ぶ場合は、CI完了までの待機を必ず作業工程に含める。
push前のチェックを実行する前には、ロックファイルの変更有無にかかわらず、対象リポジトリの開発手順で定められた環境同期処理を毎回実行し、仮想環境をロックファイルの依存関係およびCI環境のPythonバージョンと完全に一致させる。なお、uvの`uv run`による自動同期は不要なパッケージが環境内に残留する可能性があるため、同期手段から除外する。`.python-version`ファイルが存在しないプロジェクトや、`UV_PYTHON`などで特定のバージョンが指定されている環境では、既存の仮想環境のPythonバージョンも正確に維持する。監査記録は`docs/development/audit-records.md`の「agent-toolkit/skills/commit/references/publish.md：検証とCI：2026年10月11日」にある。`.python-version`の有無と版の指定による条件別の観測は、同じ文書の「agent-toolkit/skills/commit/references/publish.md：検証とCI：2026年10月19日」にある。

push前のチェックやローカルの全体検証はログ出力が膨大になりやすいため、`agent-toolkit/rules/02-agent-operations.md`「ツール・コマンド運用」に定める分離実行（`agents_server`の`start`による`shell`実行など）を用いて行う。
`shell`実行時には、対象リポジトリを`cwd`に、実行コマンドをそのまま`command`に、managed-temp内の一時出力先を`summary_policy`に渡す。
公開を担当するエージェントは、保存された出力ファイルの実在とその内容、および終了コードが0であることを確認して検収する。警告メッセージについてはその内容と影響を精査し（`agent-basics:bugfix`の`SKILL.md`「問題を見つけたときの対処」を参照）、設定の未適用や処理の未完了を示す警告は作業を続けられない原因として対処する。
チェックや検証が失敗した場合は、公開担当エージェントが`agent-basics:bugfix`を用いて原因を特定し、認可された範囲内で修正する。`agent-toolkit:process-wi`の完了担当者によるCI修正の手順は、同スキルの`references/termination-ci-failure.md`「検証またはCIの失敗」の定めに従う。

## pushと公開状態

ベースブランチへpushすべき差分が存在する場合に限り、`references/push-and-ci.md`に従ってpushを実行する。完全OIDを要求するCI照会APIに対しては、直前に`git rev-parse --verify <revision>^{commit}`を単独で実行し、終了コードが0であること、および40桁または64桁の小文字の16進文字列が1行で出力されることを確認したうえで渡す。プッシュすべき差分がない場合は、現在のHEADに対するCIの結果を1回確認して確定させる。
CI定義が存在しない場合は、共通判定によって得られた「CI定義不在」の証拠と、「ローカルでの全体検証の成功」をセットにして後続の処理へ引き継ぐ。
CIの照会が不可能な状態である場合は、すでに完了しているpushと公開状態を保持したまま、次節の手順へ進む。

pushとCIの確認を完了したあとは、`references/push-and-ci.md`に定める「公開状態の4項目」を現在のGit状態から確認する。満たされていない項目がある場合は所定の手順で解消し、自力で解消できない場合は該当する項目名を報告する。公開後の各種操作によって新たなコミットが作成された場合は、再度pushを行い、そのコミットに対するCIの通過と公開状態を確認する。

## 公開工程の続行不能からの再開

本節は、CIの照会が不可能な場合（CI定義の判定、ベースラインの作成、CI監視に必要な前提条件の不足など）や、push完了後の公開後操作が認証・ネットワーク到達性・対象指定・権限などの不足によって続行できなくなった場合に適用する。既存の設定や認可の範囲内で問題を解消できる場合は、同じ公開先とコミットに対する未完了の工程のみを再開する。その際、完了済みのpush、公開状態、CI結果、および正常終了した公開後操作の内容は確実に保持する。
自力で回復できない前提条件の不足がある場合、委譲先エージェントは確認済みの工程情報とともに、`references/push-and-ci.md`「公開工程の続行不能の受渡し」に沿って委譲元へ状況を報告する。公開後の操作のみが未完了である場合は、確認済みのCI結果をそのまま返す。ベースライン情報については既存の保存先を案内し、未作成であればその旨と理由（CI定義が存在しない等）を記載する。正常終了したCIに対して、報告のためだけにベースラインを新規作成する必要はない。
公開を担当するメインエージェントは、`agent-toolkit:user-confirmation-and-report`に従ってユーザー確認の要否と手段を判断し、ユーザー自身の手作業による資格情報の提供や操作、追加の認可が必要な場合にのみ確認を求める。
ターンやセッションが終了したあとも作業が残る場合は、同スキルの「手段の選択」に従って個別UWIを作成・保存し、すでに同一内容の確認が存在する場合はそれを再利用する。
UWIには、対象の公開先、コミット、完了済みの工程、必要な操作、返却してほしい結果を記載する。なお、パスワードやトークンなどの資格情報そのものの書き写しをユーザーに求めない。

ユーザーからの回答を必要とする未完了の元タスクのみを、UWIの保存完了後に`agent-toolkit:wi-standards`「状態と依存」に従って保留状態にする。
すでに完了している実装タスクの状態はそのまま維持する。残りの公開工程に関する再開記録は作業計画の進捗ログに保存し、計画ファイルが存在しない場合は、公開工程を扱う未完了AWIの本文中に記録する。該当するAWIが存在しない場合は、`agent-toolkit:wi-standards`の通常の投入手順で新規作成し、個別UWIと関連付ける。引き継ぎ記録は同一セッション内での受け渡しに用い、次のセッションが参照する再開記録と必要な証拠データは、作成時点で計画ファイルまたはAWI本文に保存しておく。
再開記録には、公開先、コミット、参照（ref）、完了済みの工程、正常終了した公開後操作、CI結果（未判定の場合はその旨）、失敗した操作とその対象、ベースラインファイル・保存出力・UWIの配置場所、不足している前提条件、および再開すべき作業位置を明記する。
ユーザーから回答が得られたあとは、`agent-toolkit:user-confirmation-and-report`の`references/answer-transitions.md`に従う。元の担当セッションが保持されていればそこへ回答を届け、セッションが残っていなければ再開記録をもとに未完了の工程のみを再開する。すでに成功しているバージョン更新、push、公開後操作を重複して実行しない。
process-wiにおける元項目の取り込み手順は、`agent-toolkit:wi-standards/references/states-and-dependencies.md`「回答済みUWIの取り込み」に従う。
独立した有効な証拠によってCI定義が存在しないことが確定できた場合は、「CI定義なし」を正常な完了状態とする通常のフローに復帰する。一方、ローカル全体検証の失敗は独立した未完了事項として扱い、必要な是正をする。

## プロジェクト固有の公開後の操作とリリース

認可済みのプルリクエスト（PR）やマージリクエスト（MR）の作成、リリースの作成、タグ打ち、パッケージ配布などの操作は、それぞれの依存関係に沿って順次実行する。CIの成功を前提条件とする操作は、対象コミットに対するCIが正常に通過したことを確認してから実行する。他のエージェントへすでに分担されている作業工程は、その担当エージェントに任せる。
公開範囲が「既存の判断基準どおり」に設定された協調モードや、公開工程まで自動で進める自律モードでは、CIが成功したあとにプロジェクト規範に沿ったリリース判定処理を起動する。リリースの認可状態やバージョンの種類は、プロジェクト規範と本書の「版数と生成物」に基づいて決定する。実施した公開範囲、CI結果、公開後操作の内容、およびリリース判定の結果は、最終的な完了報告に含める。

公開後の操作やリリース判定で起動した手順が前提条件の不足によって続行できなくなった場合は、確認済みの公開工程と正常終了した操作の内容を保持したまま、前述の「公開工程の続行不能からの再開」へ進む。実装の欠陥やCIの失敗が判明した場合は、`agent-basics:bugfix`を起動して修正する。
