# リポジトリ変更の公開工程

「公開工程」はcommitから版数更新・push・CI・公開状態・プロジェクト固有の公開後の確認までを指し、本書を定義元とする。起動形態を問わず、ユーザー指示・確認回答・自律モードのスキル契約から認可範囲を確定して適用する。pushとCI監視は`references/push-and-ci.md`に従う。

## 公開範囲

協調モードの選択肢は`agent-toolkit:user-confirmation-and-report`の`references/publish-scope.md`「公開範囲の確認」が定める。元の依頼がPR、release、tagを個別に求める場合は、それをプロジェクト固有の公開後の操作として扱う。

| 範囲 | 実施する工程 |
| --- | --- |
| commitしない | 実装、変更範囲の検証および必要な生成同期を終え、commitの手前で止める |
| commitまで | 必要な版数更新と生成同期、検証、commitまで行う |
| push・CIまで | commitまでの工程に続けてpush、CI確認および公開状態の確認まで行う |
| 既存の判断基準どおり | push・CIまでの工程に続けて、プロジェクト規範のリリース判定と認可されたプロジェクト固有の公開後の操作を行う |

`agent-toolkit:process-wi`と`agent-toolkit:single-lane-process`は各スキルが確定した自律モードの公開範囲を用いる。

## 版数と生成物

配布物の版数更新を要する変更では、版数規範と未push差分を比べて必要な種別のうち上位を採用し、版数更新、派生manifest同期、生成同期の確認、commitを連続して行う。同期の判定は生成器が定める対象集合と終了コードを使う。
`agent-toolkit:process-wi`では終端担当が未pushの追加差分と公開済みの版を比べて版数を更新する。公開済みの成果を追加差分へ再び含めず、差分が無い再検収では版数更新、push、CI待機を省く。

プロジェクト方針が無い場合の版数の区分:

- ユーザーが明示した区分（MAJOR、MINOR、PATCH）を最優先とする
- MAJORはユーザーの明示指示がある場合に限る（互換破壊の外部宣言であり、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「認可を要する操作」の承認対象）
- 現行版が数値3要素のSemVerでない場合は、プロジェクトの対応表かユーザーの明示から決め、どちらも無ければ版数を変えず判定不能の根拠を報告する

## 検証とCI

全体検証はpush後のCIで判定する。push前は、CIが実行しないチェックと、複数のエージェントの変更を統合した後にだけ結果が確定する全体走査のチェック（変更外の静的参照、重複実装、ファイルをまたぐimport循環など）だけを動かす。変更範囲の検証を一律の全体lintへ置き換えない。
CIが実行しないチェックの集合は、プロジェクト規範の定めを使い、無ければCIの実行形、有効なチェック、チェックが読む設定、実行環境を比べて求める。集合を確定できない場合とCI定義が無い場合（`references/push-and-ci.md`「push前」の判定）は、タスクランナーの全体検証をpush前に1回実行する。直前に同じtreeで実行済みならその結果を使う。
CIのOS・言語版・実機などローカルで実行しない条件へ変更が及ぶ場合は、CI待機を工程へ含める。
統合差分がロックファイルを変えた場合は、チェックの前に対象リポジトリの開発手順が定める環境同期を実行する。

push前のチェックとローカルの全体検証は出力が大きいため、`agent-toolkit/rules/02-agent-operations.md`「ツール・コマンド運用」の分離した実行（`agents_server`の`start`の`shell`など）で行う。
`shell`には対象リポジトリを`cwd`、コマンドをそのまま`command`、managed-temp内の出力保存先を`summary_policy`へ渡す。
公開を担うエージェントは保存された出力の実在と内容、終了コード0を検収する。警告は意味で判定し（`agent-toolkit:bugfix`の`SKILL.md`「問題を見つけたときの対処」）、未適用・未完了を示す警告は阻害とする。
失敗した場合は公開を担うエージェントが`agent-toolkit:bugfix`で原因を確定し、認可範囲内で是正する。`agent-toolkit:process-wi`の終端担当のCI修正は同スキルの`references/termination-ci-failure.md`「検証またはCIの失敗」が定める。

## pushと公開状態

ベースbranchへpushする差分がある場合だけ`references/push-and-ci.md`に従ってpushする。完全OIDを要求するCI照会APIへは、直前に`git rev-parse --verify <revision>^{commit}`を単独実行し、終了コード0と40桁か64桁の小文字16進数1行を確かめた値を渡す。差分が無い場合は現在HEADのCI結論を1回確定する。CI定義が無い場合は、push前のローカルの全体検証の成功をCI成功の代わりに後続へ渡す。

pushとCI確認の後、同書「公開状態の4項目」を現在のGit状態から観測し、不成立の項目は同じ手順で解消し、解消できなければその項目名を報告する。公開後の操作で新しいcommitが生じた場合は再度pushし、そのcommitのCIと公開状態を確かめる。

## プロジェクト固有の公開後の操作とリリース

認可済みのPRかMR、release、tag、配布等は依存順に、CI成功を入力とするものは対象commitのCI成功後に行う。別のエージェントへ割り当てた工程はその担当に任せる。
公開範囲が「既存の判断基準どおり」の協調モードと、公開まで進む自律モードでは、CI成功の後にプロジェクト規範のリリース判定を起動する。リリースの認可と版数種別はプロジェクト規範と本書「版数と生成物」による。実施した公開範囲、CI結果、公開後の操作、リリース判定の結果を完了報告へ渡す。
