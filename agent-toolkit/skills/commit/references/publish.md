# リポジトリ変更の公開工程

本書は作業の起動形態によらず、commitから公開後の確認までを扱う。実行主体は元のユーザー指示、確認回答または自律実行スキルの契約から公開範囲を確定してから適用する。pushの具体的な受理条件とCI監視は`references/push-and-ci.md`を全文読んで適用する。

## 公開範囲

協調モードの選択肢は`agent-toolkit:user-confirmation-and-report`の`references/judgment.md`「公開範囲の確認」が定める。各範囲で実施する工程は次のとおりとする。元の依頼がPR、releaseまたはtagを個別に求める場合は、その明示指示をプロジェクト固有の公開後の操作として扱う。

| 範囲 | 実施する工程 |
| --- | --- |
| commitしない | 実装、変更範囲の検証および必要な生成同期を終え、commitの手前で止める |
| commitまで | 必要な版数更新と生成同期、検証、commitまで行う |
| push・CIまで | commitまでの工程に続けてpush、CI確認および公開状態の確認まで行う |
| 既存の判断基準どおり | push・CIまでの工程に続けて、プロジェクト規範のリリース判定と認可されたプロジェクト固有の公開後の操作を行う |

`agent-toolkit:process-wi`と`agent-toolkit:single-lane-process`は各スキルが確定した自律モードの公開範囲を用いる。

## 版数と生成物

配布物の版数更新を要する変更では、版数規範と未push差分を比べ、必要な種別のうち上位を採用する。版数更新、派生manifest同期、生成同期の確認、commitを連続した1工程として実行する。同期の判定には生成器が定める対象集合と終了コードを用い、派生先は生成器の定義に従う。
`agent-toolkit:process-wi`では未pushの追加差分と公開済みの版を比べ、必要な版数更新を公開工程の終端担当が行う。公開済みの成果を追加差分へ再び含めず、差分が無い再検収では版数更新、pushおよびCI待機を繰り返さない。プロジェクト固有の更新時機と公開版との比較は対象プロジェクトの規範を使う。

## 検証とCI

対象リポジトリの全体検証は、push後のCIの結論で判定する。push前には、タスクランナーの全体検証に含まれるがCIが実行しないチェックと、複数の書込主体の成果を統合した後にだけ結果が確定する全体走査のチェックだけを実行する。CIが実行しない検証を公開前に取りこぼさず、CIと同じチェックをローカルで重ねてCIの開始を遅らせないためである。

CIが実行しないチェックの集合は、プロジェクト規範がその集合か実行コマンドを定める場合はそれを使う。定めが無い場合は、CIの実行形、有効なチェック集合、チェックが読む設定および実行環境の4つを比べて求める。集合を確定できない場合は、タスクランナーの全体検証をpush前に1回実行する。push対象のtreeが、直前に同じチェックを実行したtreeと同じ場合は、push前の再実行を省く。

統合差分が依存のロックファイルを変えた場合は、push前に実行するチェックの前に、対象リポジトリの開発手順が定める環境同期を実行する。

push前に実行するチェックとローカルの全体検証は出力が大きく、呼び出し元で直接実行すると、検証の品質は変わらないまま呼び出し元のコンテキストを消費する。呼び出し元のコンテキストを保護するため、分離した実行（`agents_server`の`start`の`shell`など）を推奨する。`start`の`shell`へ渡す場合は、対象リポジトリを`cwd`、コマンドを変更せず`command`として渡す。管理対象一時領域の標準出力・標準エラー保存先を`summary_policy`へ渡し、委譲先には双方の全量、終了コード、終了シグナル、警告と失敗行、保存先、切り詰めの有無を返させる。どの手段で実行した場合も、呼び出し側は標準出力と標準エラーの保存先の実在と内容を確かめ、終了コード0を検収する。警告は意味で判定し（`agent-toolkit:bugfix`の`references/response.md`「問題を見つけたときの対処」）、未適用・未完了を示す警告は阻害とする。処理の成立に影響しない警告は根拠を報告へ残す。同じtreeと条件の結果を統合時に判定済みの場合は、その判定と根拠を引き継ぐ。

失敗した場合は公開を担う主体が`agent-toolkit:bugfix`をSkill機能で起動し、直接的原因を確定して認可範囲内で是正する。`agent-toolkit:process-wi`の終端担当によるCI修正と返却は`${CLAUDE_PLUGIN_ROOT}/share/session-termination.subagent.md`「検証またはCIの失敗」が定める。

## pushと公開状態

ベースbranchへpushする差分がある場合だけ、`references/push-and-ci.md`に従ってpushする。CI照会の直前に、対象リポジトリで`git rev-parse --verify <revision>^{commit}`を単独実行する。終了コード0、空でない1行の標準出力、40桁か64桁の小文字16進数を確認し、その完全OIDを外部APIへ渡す。本手順は完全OIDを要求するAPIへ適用する。差分が無い場合は現在HEADのCI結論を1回確定する。CIと同値と判定した全体検証の結論は、このCI結果で確定する。

pushとCI確認の後、同書「公開状態の4項目」を現在のGit状態から観測する。不成立の項目は同じ公開手順で解消し、解消できない場合はその項目名を報告する。プロジェクト固有の公開後の操作で新しいcommitが生じた場合は再度pushし、そのcommit自身のCI結果と公開状態を確認する。

## プロジェクト固有の公開後の操作とリリース

認可済みのPRかMR、release、tag、配布等は依存順に実施する。CI成功を入力とする操作は対象commitのCI成功後に行う。別主体へ割り当てた工程はその担当に任せる。

公開範囲が「既存の判断基準どおり」の協調モードと、公開まで進む自律モードでは、pushとCI成功の後にプロジェクト規範が定めるリリース判定を起動する。リリースの認可と版数種別はプロジェクト規範と`references/push-and-ci.md`を使う。実施した公開範囲、CI結果、固有工程、リリース判定の結果を完了報告へ渡す。
