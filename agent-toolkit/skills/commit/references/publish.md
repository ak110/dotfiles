# リポジトリ変更の公開工程

「公開工程」はcommitから版数更新・push・CI・公開状態・プロジェクト固有の公開後の確認までを指し、本書を定義元とする。起動形態を問わず、ユーザー指示・確認回答・自律モードのスキル契約から認可範囲を確定して適用する。pushの受理条件とCI監視は`references/push-and-ci.md`に従い、`SKILL.md`の読込表どおりpush前に読む。

## 公開範囲

協調モードの選択肢は`agent-toolkit:user-confirmation-and-report`の`references/publish-scope.md`「公開範囲の確認」が定める。各範囲で実施する工程は次のとおりとする。元の依頼がPR、releaseまたはtagを個別に求める場合は、その明示指示をプロジェクト固有の公開後の操作として扱う。

| 範囲 | 実施する工程 |
| --- | --- |
| commitしない | 実装、変更範囲の検証および必要な生成同期を終え、commitの手前で止める |
| commitまで | 必要な版数更新と生成同期、検証、commitまで行う |
| push・CIまで | commitまでの工程に続けてpush、CI確認および公開状態の確認まで行う |
| 既存の判断基準どおり | push・CIまでの工程に続けて、プロジェクト規範のリリース判定と認可されたプロジェクト固有の公開後の操作を行う |

`agent-toolkit:process-wi`と`agent-toolkit:single-lane-process`は各スキルが確定した自律モードの公開範囲を用いる。

## 版数と生成物

配布物の版数更新を要する変更では、版数規範と未push差分を比べ、必要な種別のうち上位を採用する。版数更新、派生manifest同期、生成同期の確認、commitを連続した1工程として実行する。同期の判定には生成器が定める対象集合と終了コードを用い、派生先は生成器の定義に従う。
`agent-toolkit:process-wi`では未pushの追加差分と公開済みの版を比べ、必要な版数更新を公開工程の終端担当が行う。公開済みの成果を追加差分へ再び含めず、差分が無い再検収では版数更新、pushおよびCI待機を繰り返さない。プロジェクト固有の更新時機と公開版との比較は対象プロジェクトの規範を使う。

版数の区分は、プロジェクト方針が無い場合は次の基準で決める。

- ユーザーが明示したバージョン区分（MAJOR、MINOR、PATCH）を最優先とする
- MAJORリリースはユーザーの明示指示がある場合に限る。MAJORは互換破壊の外部宣言であり、`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「認可を要する操作」が定める承認対象に当たる
- 現行版が数値3要素のSemVerでない場合は、プロジェクトの対応表またはユーザーが明示した区分から区分を決める。いずれも無い場合はバージョンを変更せず、判定不能の根拠を報告する。文字列の辞書順と桁数は区分の判定材料から外れる

## 検証とCI

全体検証はpush後のCIで判定する。push前は、タスクランナーの全体検証のうちCIが実行しないチェックと、複数のエージェントの変更を統合した後にだけ結果が確定する全体走査のチェックを動かし、欠落と重複実行を避ける。
全体走査には、変更外の静的参照、重複実装、複数ファイルをまたぐimport循環の検出などが当たる。変更ファイルだけを指定しても関係する全ファイルの問題を検出できるかで選ぶ。変更範囲の検証を一律の全体lintへ置き換えない。
対象リポジトリにCI定義が無い場合（`references/push-and-ci.md`「push前」の判定）は、タスクランナーの全体検証をpush前に1回実行し、その結果で全体検証を判定する。

CIが実行しないチェックの集合は、プロジェクト規範がその集合か実行コマンドを定める場合はそれを使う。定めが無い場合は、CIの実行形、有効なチェック集合、チェックが読む設定および実行環境の4つを比べて求める。集合を確定できない場合は、タスクランナーの全体検証をpush前に1回実行する。push対象のtreeが、直前に同じチェックを実行したtreeと同じ場合は、push前の再実行を省く。

push前にCI定義とローカル検証の対応・未実行条件（OS・言語版・実機など）を確定する。
変更が未実行条件へ及ぶ場合はローカルで検証できる形を推奨し、変更費用とCI待機・手戻りを比較する。変えない場合はCI待機を工程へ含める。

統合差分が依存のロックファイルを変えた場合は、push前に実行するチェックの前に、対象リポジトリの開発手順が定める環境同期を実行する。

push前に実行するチェックとローカルの全体検証は出力が大きいため、`agent-toolkit/rules/02-agent-operations.md`「ツール・コマンド運用」の分離した実行（`agents_server`の`start`の`shell`など）で行う。`start`の`shell`へ渡す場合は、対象リポジトリを`cwd`、コマンドを変更せず`command`として渡す。managed-tempの中の標準出力・標準エラー保存先を`summary_policy`へ渡し、委譲先には双方の全量、終了コード、終了シグナル、警告と失敗行、保存先、切り詰めの有無を返させる。どの手段で実行した場合も、公開を担うエージェントは標準出力と標準エラーの保存先の実在と内容を確かめ、終了コード0を検収する。警告は意味で判定し（`agent-toolkit:bugfix`の`SKILL.md`「問題を見つけたときの対処」）、未適用・未完了を示す警告は阻害とする。処理の成立に影響しない警告は根拠を報告へ残す。同じtreeと条件の結果を統合時に判定済みの場合は、その判定と根拠を引き継ぐ。

失敗した場合は公開を担うエージェントが`agent-toolkit:bugfix`を起動し、直接的原因を確定して認可範囲内で是正する。`agent-toolkit:process-wi`の終端担当によるCI修正と返却は`agent-toolkit:process-wi`の`references/termination-ci-failure.md`「検証またはCIの失敗」が定める。

## pushと公開状態

ベースbranchへpushする差分がある場合だけ、`references/push-and-ci.md`に従ってpushする。CI照会の直前に、対象リポジトリで`git rev-parse --verify <revision>^{commit}`を単独実行する。終了コード0、空でない1行の標準出力、40桁か64桁の小文字16進数を確認し、その完全OIDを外部APIへ渡す。本手順は完全OIDを要求するAPIへ適用する。差分が無い場合は現在HEADのCI結論を1回確定する。CIと同値と判定した全体検証の結論は、このCI結果で確定する。CI定義が無い場合はCI結論を確定せず、push前に実行したローカルの全体検証の成功を、CI成功を入力とする後続の工程へ渡す。

pushとCI確認の後、同書「公開状態の4項目」を現在のGit状態から観測する。不成立の項目は同じ公開手順で解消し、解消できない場合はその項目名を報告する。プロジェクト固有の公開後の操作で新しいcommitが生じた場合は再度pushし、そのcommit自身のCI結果と公開状態を確認する。

## プロジェクト固有の公開後の操作とリリース

認可済みのPRかMR、release、tag、配布等は依存順に実施する。CI成功を入力とする操作は対象commitのCI成功後に行う。CI定義が無い場合は、pushの成功とローカルの全体検証の成功をCI成功の代わりの入力とする。別のエージェントへ割り当てた工程はその担当に任せる。

公開範囲が「既存の判断基準どおり」の協調モードと、公開まで進む自律モードでは、pushとCI成功（CI定義が無い場合はpushとローカルの全体検証の成功）の後に、プロジェクト規範が定めるリリース判定を起動する。リリースの認可と版数種別はプロジェクト規範と本書「版数と生成物」を使う。実施した公開範囲、CI結果、プロジェクト固有の公開後の操作、リリース判定の結果を完了報告へ渡す。
