# 履歴書換え：WI実装commitの対応の継承

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## WI実装commitの対応の継承

コミット対応表のJSONフォーマットは、1対1または多対1の対応を表す`{"oldOID":"newOID"}`とする。
コミットを分割した場合は、`{"oldOID":[{"commit":"newOID-A","awi":["WI-A.md"]},{"commit":"newOID-B","awi":["WI-B.md"]}]}`の形式でAWIの割り当てを明示する。
WIは保存ファイル名で、OIDはGit上で一意に解決できる値で指定する。
同一のAWIを複数の新しいコミットに割り当ててもよく、元の各commitに紐づくAWIをいずれかの新commitへ漏れなく割り当てる。
従来の単一スカラー値形式、保存済みのrewriteイベント、および本文中のコメントも引き続き読み取り可能である。

**1.** AWIとの対応を保持するため、対応表には、`atk run-script history-compare`による検証が成功した際に保存された完全OIDの新旧対応表を使用する。
rebaseの検証には`--operation rebase`、autosquashには`--operation autosquash`、amendには`--operation amend`を用い、それぞれの分岐元（base）を除いたheadまでの範囲を指定する。
autosquashとamendの起動コマンドは`history-rewrite-verification.md`「操作前後の確認」を参照する。
WIの対応付けを持たないコミットであっても、fixupとその統合元コミットが同一の新しいコミットへ統合される場合は、両方の古いOIDを対応表に含める。
amendの場合は、新旧HEADの1対1の対応が1件だけ記録される。

rebase後はまず指定なしで比較し、history-compareが「変更内容が対応しない旧commit」として示したOIDだけを`--resolved-conflict <旧OID>`で反復指定する。
対象は旧commitの変更を新しい親へ3-way適用した結果が新commitと一致しないもので、周辺の文脈行だけの変化は対象から除く。

統合先の修正を未統合レーンへ取り込む手段は、そのレーンの履歴から選ぶ。
レーン独自のcommitがまだ無ければfast-forwardで取り込み、未記録の直線区間だけを対応記録へ渡す。
レーン独自のcommitがある場合は、必要な修正をcherry-pickするか、認可された履歴書換えの手順でrebaseする。
2つの親を持つmerge commitは、`commit-wi-records.md`の区間記録とhistory-compareの検収対象外のため、単一親の履歴を保つ。
cherry-pickした修正が後の統合rebaseで省略された場合の対応は、次の同一変更の検収に従う。
rebaseが競合した場合は解消して`rebase --continue`し、まず指定なしで比較する。
件名・順序・必要なパスの欠落や対応の曖昧さがある場合は、診断に従って端点・指定・履歴を是正する。
内容を保持した履歴を構成できなければ、保存済み成果を保持して委譲元へ返す。
`--restart-review`は現在の統合先へ再追随し、その後も履歴の比較を実行する。

rebaseで部分省略・全件省略された旧commitは、空白を含む同一変更が統合先の履歴に一意に存在し、旧commitの変更そのものが新baseに残っている場合に、その既存commitへ対応付ける。
全件省略時は新baseと新HEADに同じOIDを指定する。
変更が残っているかは、旧commitの差分を新baseへ逆適用でき、順適用できないことで判定する。
同じpathへの後続編集も、変更箇所とその前後の文脈に重ならなければ受理する。
重なる書換えは、取消しの後の編集と差分の適用では区別できないため、指定なしでは拒否し、`--resolved-conflict <旧OID>`の指定を求める診断を返す。
この指定は、統合先の書換えの内容を読み、書換え後の統合先でレーンの変更が成立することを確かめた場合だけ行う。
指定した旧commitは既存commitへ対応付け、成功の報告に列挙する。
新baseへ順適用できる取消しは指定しても拒否するが、取消しの後に文脈を編集した場合のように差分の適用で区別できない喪失は機械的に排除できず、指定する側の検収に委ねる。
同じ旧commitへの`--exclude-path`との併用は拒否する。
revertやmergeで不採用となった変更、消失した変更、対応が曖昧な変更は受理しない。
省略されたWIなしの依存commitも比較表に含め、WI付きcommitの対応は計画と引き継ぎ記録へ継承する。
対応先が既存のWI対応を持つ場合は、旧commitのWI集合と合併する。
同コマンドは、コミット件名、相対的な順序、変更パスをもとに一意な対応関係を検証する。
競合解消commitの変更パスは、旧コミットの変更パスのうち統合先に残るものを全て含む必要がある。
統合先の改名・削除で消えた既存ファイルのパスは外れてよいが、旧コミットが新設したパスは外れてはならない。
増えたパスと外れた旧パスは成功出力に示されるため、検収の入力にする。
旧commitの変更パスの一部を意図して外した書換えは、この増減の受理とは別の入力で明示し、`history-rewrite-verification.md`「一部の変更パスを外した対応の確認」に従って対応表を生成する。
同一変更が系列内で繰り返す場合は、旧新が同数のときに限り位置で対応付ける。
引数の不足や不正、あるいは対応関係の曖昧さがある場合は保存せず、次に行うべき操作を案内して終了する。
検証済みの対応表は、後述の`atk run-script plan-rewrite --`コマンドに渡す（個別の記録を更新する場合は、`atk run-script plan-progress --`の`--rewrite-map`を使用する）。
再レビューを依頼する際は、この対応表を`rewrite_map`として実行レビュー担当者へ渡し、新しいHEADをもとに完了条件を再判定してもらう。
実装担当者は、OIDの対応関係だけで以前の検証結果を機械的に新しいバージョンへ流用しない。
変更内容や条件が結果に影響を与える検証項目のみを再実施し、影響を受けない項目については取得時のHEADと再検証を省略する理由を記載する。

**2.** 書き換え直前のHEADと対応表は、書き換え範囲のコミットを参照しているすべての計画（作業中および保存済み）や引き継ぎ記録とともに、以下の形式で1回だけ渡して実行する（記録、worktree、対応表は絶対パスで渡し、`--rewrite-map`にはファイルパスを指定する）。
履歴書換えを繰り返す間は毎回同じ記録集合を渡す。

```text
atk run-script plan-rewrite -- --worktree <worktree> --previous-head <書換え前のHEAD> --rewrite-map <対応表のJSONファイルの絶対パス> --completed-step <工程> --result <結果> --plan <計画>... --handoff <引き継ぎ記録>...
```

同コマンドは、すべての記録ファイルを検証したうえで書き込みを行う。
記録済みOIDの欠落（今回の不足と過去の未記録を区別して案内する）や対応表の誤りがある場合は、どのファイルも変更せずに失敗するため、生成側で不足情報を補正する。
最新の対応関係の取得方法は、`commit-wi-records.md`「WI実装commitの対応」に従う。
書き換え範囲に関連しているにもかかわらず指定されていない記録が存在する場合、コマンドは書き込み前にそれらを一覧表示して処理を拒否する。
複数の対応表を適用する場合は、履歴を書き換えた順序に沿って`--rewrite-map`を繰り返し指定する。
適用後は、合成された最終的なOIDが現在HEADの履歴に含まれることを確認する。

この`plan-rewrite`コマンドは、渡された記録に対応する`adopted`状態のAWIについて、`## 処理結果`の記述も自動的に更新する。
対応表の古いOIDに該当するコミットOIDと件名を新しい情報へ更新し、コミット分割の場合はそのAWIへ割り当てられたすべての新しいコミットを記録する。
採否区分、処理日時、メモ、および対応表に含まれないコミットの情報はそのまま保持される。
完了状態のAWIは、WIの保存処理によってprivate-notesへコミットしてプッシュされる。
保存後の内容が更新内容と一致することを確認して、計画ファイルや引き継ぎ記録への追記が行われる。
保存処理に失敗した場合はコマンドが非0で終了するため、同期エラーや保存エラーを解消したうえで同じ引数で再実行する。
すでに更新済みのAWIや滞留コミットの情報は保持され、残りの変更が反映される。

**3.** `atk plans checkout`で保存済み計画を取得して履歴に追随させた担当者は、作業工程の最後に、更新したすべての計画バンドル（未完了のWIや延期されたadoptを含む計画も含む）を`atk plans commit`で再度保存し、終了コードと警告の有無から正常終了を確認する。
保存先や保存タイミングに関する共通規約は、`agent-toolkit:write-plan`の`references/plan-file-storage.md`に従い、レーン処理、観測のみの作業、CI実行時における既存の保存タイミングを遵守する。
