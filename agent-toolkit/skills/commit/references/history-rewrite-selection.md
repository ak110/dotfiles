# 履歴書換え：修正方法の選択

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 修正方法の選択

**1.** 中間commitの公開契約を保つため、通常の実装モードにおいてレビューで指摘された修正をする際は、既存の実装コミットへ統合する。
レビュー修正専用のコミットは作成対象から除く。

レビュー修正担当は、指摘管理表と現在の履歴を比べ、採用指摘IDと実装単位commitの短縮OIDを対応付ける。
対応する実装単位commitへ統合し、対象の位置で手順2の方法を選ぶ。
過去のコミット単位へのfixupは、その修正が統合先のコミット時点で独立して成立し、変更範囲の検証を単独で再実行できる場合にのみ行う。
対象直後から現在HEADまで各commitを`git diff-tree`や差分で調べ、変更箇所と順序から中間commitの公開契約を判定する。
同一ファイルの変更だけで競合と判断しない。
対応を特定できない修正、複数のコミット単位にまたがって不可分な修正、あるいは過去の単位へ統合すると中間コミットの公開契約を維持できない（または独立して検証できない）修正については、そのレビューが対象とする計画の実装コミットのうち最も新しいコミットへ統合する。
統合先のコミットがすでにプッシュ済みである場合や、OIDが一致しない場合は、履歴や作業ツリーを変更せずに作業を中断し、続行できない理由を報告する。

**2.** 対象の位置に合う方法で修正を統合する。
`history-rewrite-verification.md`「操作前後の確認」の手順1〜3を先に行い、fixupは`history-rewrite-fixup.md`「fixupの実行上の制約」に従う。

- 直前の最終コミットのみが対象の場合: 修正、検証、ステージングを行ったあと、`amend`フェーズでプッシュ済み判定を再実行し、未プッシュであることを確認してamendを実行する
- 過去のコミットを含む場合: 最終コミットを含め、すべての統合先コミットに対して履歴順に1単位ずつ修正を作成、検証、ステージングしてfixupコミットを作成する。
  fixupを作成するごとに、対象のOID、件名、および作業ツリーがクリーンであることを確認してから次の単位へ進む。
  すべてのfixupを作成し終えたあとに、autosquashを1回だけ実行する。
  各fixupの作成前に行う確認手順は`history-rewrite-verification.md`「操作前後の確認」に従う
autosquashの単位は、レビュー識別子（指摘管理表の絶対パスとround値）と最古fixup対象の短縮OIDの組とする。
  受渡しや再開があっても、全fixup作成後の1回だけ実行する。
  作業を再開した際は、`history-rewrite-verification.md`「履歴確認の起動形」の`git log`を実行し、件名が`fixup!`、`squash!`、または`amend!`で始まるコミットがある場合だけautosquashを実行する。
作成済みfixupを通常commitへ再構成する場合は、元fixupごとの差分・件名・本文を個別取得し、新commitと1対1で比べる。
  メッセージの取り違えは最終ツリーの一致だけでは検出できない。
autosquash成功後は`git rev-parse --short=7 HEAD`で新HEADを取得し、新旧の実装単位を対応付ける。
  厳密な比較では各短縮OIDを直前に解決する。

統合後は`history-rewrite-verification.md`「操作前後の確認」の手順4〜6へ進む。

本節の手順1・2は通常実装のレビュー修正に限る。
未プッシュかつ単一の実装担当者が専有する作業ツリーでは、本書のプッシュ済み判定で安全を十分に確保できる。
リモートの広告参照との比較、replace参照、graft、浅いクローンに対する防御策は、実際の事象を観測・記録したうえで必要に応じて追加する。

**3.** 作業工程によらず同一の実装単位・目的の変更は既存commitへ統合する。
手順2と同じ事前確認を経て、次から選び、操作後は`history-rewrite-verification.md`「操作前後の確認」の手順4〜6へ進む。

- 統合先が直前のコミットのみである修正は、`git commit --amend --no-edit`で統合する（通常実装のレビュー修正で過去の単位を含む場合は、前述の手順に従う）
- それ以前の未プッシュコミットを補正・完成させる修正は、メッセージ変更なしなら`git commit --fixup=<sha>`、`Co-Authored-By:`等の追加・更新なら`--fixup=amend:<sha>`、メッセージのみ変更なら`--fixup=reword:<sha>`を用いる。
  統合先の件名が変更範囲内で重複している場合は、`history-rewrite-fixup.md`「fixupの実行上の制約」に従い、完全OIDを件名に含めたfixupを作成する
- 独立した新しい変更目的を持つ修正や、統合先に適した未プッシュコミットがない修正は、新規コミットとして作成する（ただし通常実装モードのレビュー修正にはこれを適用せず、前述のとおり適切な既存コミットへ統合する）。
  付帯作業を関連する開発コミットに含める場合も、独立した変更目的の対象から除く
