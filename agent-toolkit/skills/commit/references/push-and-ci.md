## 公開状態の4項目

ベースブランチへの変更が正しく公開されたことを確認するための以下の4項目を「公開状態の4項目」と呼ぶ。判定する時点で現在のGit状態から値を取得し、4項目すべてが満たされた場合にのみ「公開済み」と判定する。値の取得には各項目に指定されたコマンドを用い、`.git`ディレクトリ内部のファイルを直接探索したり、複数のrefを1回の`git rev-parse --short`にまとめて渡したりすることは避ける。

1. `git -C <対象リポジトリの絶対パス> status --porcelain=v2 --branch`の出力に含まれる`# branch.head`が、ベースブランチ名と一致していること
2. 上記と同じ出力において、`#`で始まらない行が0件であること（作業ツリーが完全にクリーンであること）
3. 上記と同じ出力に含まれる`# branch.ab`のahead値が`+0`であること（リモート追跡ブランチが存在せず値を取得できない場合は不成立とする）
4. `git -C <対象リポジトリの絶対パス> status`の出力に、rebase、merge、cherry-pickなどが進行中であることを示す表示がないこと

## 公開先に対応するCI定義の判定

承認済みのpush先forge、リポジトリ（ホスト名を含む）、および対象コミットを入力とし、その公開先で実行されるCI定義が存在するかどうかを判定する。
判定結果を記録する側とそれを受け取る側は本節の基準を共通して用い、候補となるCI定義は公開先forgeに属するものだけに限定する。
複数の公開先や更新対象の参照（ref）がある場合はその組み合わせごとに判定し、対象コミットのツリー情報を判定の証拠として用いる。

| 公開先 | 判定する定義と不在の根拠 |
| --- | --- |
| GitHub | 対象コミットの`.github/workflows`ディレクトリ直下に存在する、拡張子が`.yml`または`.yaml`のblobファイルを候補とする。`git ls-tree -r <対象commit> -- .github/workflows`を実行してオブジェクトの種類とパスを確認し、終了コード0で候補が0件であれば不在と判定する。READMEやサブディレクトリ内のYAMLファイル、ツリーオブジェクト自体は候補に含めない |
| GitLab | 対象プロジェクトの有効な設定が指定するCI設定ファイル、およびAuto DevOpsの状態を判定する。標準の`.gitlab-ci.yml`だけでなく、独自の`ci_config_path`が指す同一プロジェクト・別プロジェクト・外部URLの設定、および継承設定を含むAuto DevOpsの有効状態を確認する。対象コミットと設定の参照先を突き合わせ、有効な定義が存在せずAuto DevOpsも無効であると確定した場合に限り不在と判定する |

GitLabの設定取得には、[Projects API](https://docs.gitlab.com/api/projects/)と[独自CI設定の仕様](https://docs.gitlab.com/ci/pipelines/settings/#specify-a-custom-cicd-configuration-file)を利用する。
APIレスポンスにおいて権限不足による項目の欠落がないか、および継承された[Auto DevOps](https://docs.gitlab.com/topics/autodevops/)が有効になっていないかを確認する。
GitLab CIの不在を確定させるには、標準設定ファイルの不在だけでなく、プロジェクト設定上で有効なCI設定が存在しないことを確認した証拠が必要である。
独自設定が指定されているにもかかわらずその参照先を取得できない場合は、不在とはみなさず未判定とする。

情報の取得失敗、権限不足、レスポンスの切り詰め、設定項目の不足などにより候補集合を確定できない場合は未判定として扱い、安易にCI成功や定義不在とみなさない。
CI定義自体は存在するもののトリガー条件に合致せず実行されない場合は「run未登録」であり、「CI定義不在」とは区別する。
判定結果の記録には、公開先、対象コミット、取得したツリー情報や有効設定と参照先、実行したコマンド、終了コード、および診断結果を残す。
CI定義の不在を確定できた場合はベースライン作成と監視を省略し、ローカルでの全体検証の成功と組み合わせて最終状態を「CI定義なし」とする。
未判定となった場合は後述の「公開工程の続行不能の受渡し」へ引き継ぎ、定義の再判定または該当コミットに対するCI照会手順の復旧を図る。

## push前

- pushの認可（計画に記録された元の要求、ユーザー確認に対する回答、委譲プロンプト、ユーザーからの直接指示など）に対象リポジトリと対象ブランチが含まれていることを確認する。amendやfixupを実行した直後は、作業ツリーに未コミットの差分が残っていないこともあわせて確認する
- `git fetch`を実行したあと、上流ブランチとの差分を双方向で確認する。上流が進んでいる場合はその変更を取り込み、検証を最初からやり直す
- pushの実行方法は、dry-runを実行して確定させる。`git remote -v`、現在のブランチ、追跡ブランチ、Git設定の`push.default`、および承認済みのプッシュ先（destination）から、引数なしのpushがどこへ到達するかを判定する。
  承認済みのdestinationへ確実に到達すると判断できる場合は、引数なしの`git push --dry-run --porcelain`を用いる。到達先が確実でない場合や判定が難しい場合は、`<remote> <source>:refs/heads/<destination>`を明示したdry-runを実行する（設定上、引数なしのpushが確実に失敗すると分かっている場合は引数なしのdry-runを省略してよい）。
  dry-runが成功し、出力されたすべてのstatus lineが承認済みのremoteとdestinationへのrefspecを示している場合に限り、その方法で実際にpushを実行する。拒否や失敗が予定されるrefが含まれている場合や、未承認のremote・destination宛てが含まれている場合は、直ちにpushを中止する

CI定義の有無は、前節「公開先に対応するCI定義の判定」に従って確定する。
委譲元から「本セッション内ではCI通過を判定しない」と明示されている場合も、ベースラインの作成と監視処理を省略する。

CIの通過を判定する場合は、pushを行う前に以下の手順でベースラインを作成する。

1. セッション用のmanaged-temp（`agent-toolkit:managed-temp`）内に、pushごとに独立したディレクトリを作成する
2. 削除対象の参照を除き、更新対象となる参照ごとに、確定したrefspecの左辺`<source>`をそのまま`--source-ref`へ渡す（右辺のdestination refやリモート追跡ブランチの値とは異なるため注意する）。補助スクリプトはsource refをコミットまで再帰的にpeelし（注釈付きタグ・軽量タグのいずれも対応）、完全長のコミットSHAを保存する。コミットへpeelできない参照が指定された場合、ベースラインの作成は失敗する
3. `(destination ref, source ref)`の組み合わせごとに以下のコマンドを実行する。以降のCI監視処理も、同様に`atk run-script wait-ci --`を用いて起動する

   ```text
   atk run-script wait-ci -- --repo <owner/repo> --forge github --ref <destination-ref> --source-ref <source-ref> \
     --write-baseline <手順1の領域>/<更新refごとに一意なファイル名>.json
   ```

ベースライン作成時には、`--repo`（ローカルパスではなく`owner/repo`またはホスト名を含むURL）、`--forge <github|gitlab>`、`--ref`、`--source-ref`をすべて明示する。後続の`--baseline`を指定した監視や再起動ではベースラインファイルに保存された値が自動的に使われるため、これらの引数は省略できる。ベースラインに保存されている値と異なる引数を指定した場合は、終了コード3で終了する。その他の引数の詳細は`--help`で確認する。複数の参照を更新する場合は組み合わせごとにベースラインを作成し、1件の作成が失敗した場合でも残りの作成を続行する。

GitLabにおけるリポジトリ識別子とSSH接続先は、glabコマンドのホスト別設定を選択するためのキーとして利用する。
接続ホストの選択には、環境変数で指定された`GITLAB_HOST`、`GITLAB_URI`、`GL_HOST`の順、およびglabのホスト別設定を用い、API接続先を明示的に上書きする場合は`GITLAB_API_HOST`を用いる。
リポジトリ識別子やSSH接続先の情報をもとに`GITLAB_API_HOST`を不用意に上書きしない。
API接続先を明示的に指定する場合は、ポート番号を含むHTTP(S) URLを`--repo`に渡す。
明示的なURL指定と環境変数指定の優先関係は、glab本来の名前解決ルールと呼び出し側の`prefer_environment`設定に従い、ベースライン作成時と監視・再開時で常に同じ設定を適用する。

## pushと監視

1. 引数なしの方式では`git push`を単独で実行し、引数明示の方式では成功したdry-runのコマンドラインから`--dry-run --porcelain`を除いた同一の引数でpushを実行する
2. pushが成功したあとは、各ベースラインに対して`atk run-script wait-ci -- --baseline <baselineの絶対パス>`を実行する（本セッションでCI通過を判定しない場合は実行せず、後始末の工程へ進む）
   - コマンドの起動と結果の回収は、`agent-toolkit:delegation`の`references/waiting-and-monitoring.md`「待機区間の構成」に従う。完了通知によって同一セッションが自動再開される監視処理はバックグラウンドで起動し、他の独立待機処理よりも先に通知が届いたものから順次処理する。同一ベースラインに対する監視処理がすでに起動している場合はそのプロセスを回収し、二重に起動しない
   - ホスト環境からバックグラウンド監視プロセスの停止通知を受け取った場合は、同スキルの`references/wait-anomalies.md`「ホストによる背景待機の停止後」に従う。停止した監視プロセスとその出力を回収したうえで、同一のSHAおよびベースライン（または待機専用記録）を用いて監視を再開する。この際、実際のCIジョブ自体の再実行は行わない
   - 総待機時間（タイムアウト値）は、判定対象runと同一のジョブ構成（実行ジョブ、パス変更条件によるスキップ、マトリックス、軽量実行有無等）を持つ過去の成功run所要時間（GitHub Actionsでは`updatedAt - startedAt`）を基準とする。これにジョブ登録の猶予時間と変動マージンを加算し、有限値の`--timeout`として渡す。直近の成功runが軽量実行や一部ジョブのみの実行である場合は、通常実行の作業量を網羅している過去の成功runまで遡って時間を算出する。所要時間は`gh run view <run ID> --json startedAt,updatedAt,jobs`などを用いてジョブ構成とともに確認し、取得や算出ができない場合はデフォルト値として270秒を指定する。なお、`gh`コマンドの入出力形式は実行直前のヘルプで確認する
   - 終了コード6を受け取った場合は、同一の引数で再度コマンドを呼び出す。終了コード2（タイムアウト）の場合は、同一のSHAおよびベースライン（または待機専用記録）を保持したまま、その時点のジョブの進行状況と経過時間から残りの必要時間を見積もり、`--timeout`の値を増やして再度呼び出す。終了コード7（引数の誤り）の場合は、`atk run-script wait-ci -- --help`で正しい指定形式を確認して引数を修正し、起動し直す。それ以外の終了コードが返った時点で待機処理の完了（終端）とする
   - バックグラウンド実行する際は、ホスト側がコマンドを強制停止する時間上限を、スクリプトに渡す総待機時間よりも長く設定する。ホスト側によって先に停止されると、スクリプトが判定結果を返せなくなるためである。実行ハンドルのyieldや再開をする場合は、60秒未満の間隔で同一プロセスに再接続し、プロセスを短い`--timeout`ごとに分割したり、プラグインルートの更新を契機に別プロセスへ置き換えたりしない
   - push前のベースラインが存在しない場合（リリース完了後のReleaseワークフローの完了確認など）や、他の主体がpushしたコミットを待機する場合は、40桁の完全長SHAを`--wait-sha`に渡し、managed-temp内に作成した待機専用JSONを`--failure-record`に渡す。この形式では対象SHAの全実行が判定対象となる（ベースライン方式は自身のpushによって新たに登録された実行のみを判定する）
   - GitLabでは、同一プロジェクト内のbridgeが再帰的に参照する下流（downstream）パイプラインやジョブも判定対象に含まれる。別プロジェクトの下流パイプラインは対象外とする
3. すべての監視対象が終了コード0で完了した場合に限り「CI通過」と判定する。出力が空である場合や成功完了を示すマーカーが存在しない場合は、未判定として扱い直接状況を確認する。判定対象はベースラインに保存されたコミットSHAの実行であり、push後に送信元ブランチが進んだ場合でも同じSHAを対象として判定する。また、ジョブ登録の猶予時間内に新しく登録された実行も判定に含める（この猶予時間は実行が1件も登録されていない状態を識別するための待機であり、判定自体の制限時間とは異なる）。なお、GitHub Actionsにおいて監視対象から除外するのは、`event`が`dynamic`かつワークフロー名が`Dependabot Updates`である実行のみとする
4. 終了コード6が返った場合は`agent-toolkit:bugfix`を起動し、並行して同じベースラインと引数でコマンドを再度呼び出す。終了コード1が返った場合も同スキルを用いて対処する
5. 修正作業する際は、元のベースライン待機が終了した時点の出力に含まれるすべての失敗ジョブの集合を修正範囲に含め、そのうえで再度pushする（失敗の全体集合を取得できない場合は、まずその原因を解消する）。
   再pushを行うごとに新しいベースラインを作成して再監視し、前回失敗したジョブが新しいpushの監視対象に正しく含まれていることを確認する。
   もし含まれていない場合は、`agent-toolkit:bugfix`の`references/ci-failure-handling.md`「修正commitが必要なCI失敗を修正するエージェント」に定める修正系列の定義に従う。修正のコミット方法は、以下の2つの区分から選択する。
   - 原因コミットへ取り込む区分: 以下の3条件がすべて成立する場合に限り、修正を原因コミットへ統合する（amend、またはfixupとautosquash）。
     リモートの更新は、`git push --force-with-lease=<destination ref>:<書き換え前に観測したremote側のOID>`のように期待するOIDを明示して実行する。期待値を省略すると、バックグラウンドの`git fetch`等でリモート追跡ブランチが進んだ際に保護が無効化されるためである。
     具体的な実行手順は、`references/history-rewrite.md`の「fixupの実行上の制約」「操作前後の確認」「失敗時の扱い」に従う。
     - push先ブランチが、リモートのHEADが指しているブランチ（`git ls-remote --symref <remote> HEAD`で確認）とは異なること
     - push先ブランチが、対象リポジトリの規範（`AGENTS.md`など）において直接pushやforce pushを禁止しているブランチではないこと
     - 操作直前に`git fetch --all --prune`を実行後、書き換え対象の最古コミットに対する`git for-each-ref --contains=<そのcommit> refs/heads/ refs/remotes/`の出力が、push先ローカルブランチとその追跡ブランチのみであること
   - 通常コミットを追加する区分: 前述の3条件のいずれか1つでも満たされない場合（ベースブランチへ直接pushする運用を含む）は、同一ブランチへ通常のコミットを追加し、force pushは行わない。また、forge側のブランチ保護設定によってforce pushが拒否された場合も、通常コミットによる修正へ切り替える
   - 取り込む区分を採用する場合でも、「push前」節に示すdry-runを同一の明示形式で実行し、強制更新を示すstatus lineが上記3条件を満たす承認済みdestinationへの更新である場合のみ承認済みとして扱う。CIの記録には、書き換え前後のOID、ツリー・親コミット・件名の対応関係、`git range-diff`の結果、および解消した原因との対応関係を残す
6. 原因調査のためにCIジョブを手動で再実行した場合も、同じベースラインを指定して`atk run-script wait-ci -- --baseline <baselineの絶対パス>`を再実行し、監視をスクリプトに任せる。独自の待機ループを作成すると、ベースラインに基づく正確な判定を再現できないため避ける。許容された再実行をしても失敗が解消されない場合は、最終状態を「CI未通過」とする。このCI未通過の事実と帰属の判定結果は、完了報告、採否記録、および`atk run-script plan-progress --`による計画ファイルの「進捗ログ」に記録する。対象ワークフローが同一のconcurrency groupで`cancel-in-progress: true`に設定されている場合、再実行の完了前に新しくpushすると先行runが自動的にキャンセル（`cancelled`）され判定証拠を失う。先行実行の完了を確実に確認してから次のpushを実行する

`--baseline`による判定が完了するまでは、同じコミットに対して`gh workflow run`などを用いてワークフローを手動起動しない。`wait_ci.py`はベースラインに含まれていない同一コミットの実行も監視対象に含めるため、手動起動した実行が失敗するとCI全体の失敗として扱われてしまうためである。リリースやデプロイ用のワークフローは、CIの通過が確定したあとに起動する。

`wait_ci.py`の終了コードの定義は以下のとおりである。

| 終了コード | 意味 |
| --- | --- |
| 0 | CI通過 |
| 1 | すべてのrunが終了し、CIが失敗した状態。報告済みのものを含む失敗ジョブの全体集合を出力する |
| 2 | タイムアウト（timeout） |
| 3 | forge CLIの実行失敗、または対象リポジトリ・参照の特定失敗 |
| 4 | runが未登録の状態 |
| 5 | CI定義が存在しないため、監視対象が存在しない状態 |
| 6 | 新たな未報告の失敗を検出したが、まだ実行中のrunやjobが残っている状態。同一引数で待機を再開する |
| 7 | コマンド引数の誤り。正しい引数形式を確認して修正し、再起動する |
| 130 | 処理の中断 |

## 後始末

本工程における完了状態（終端状態）には、CI成功、CI定義なし、CI判定の委譲、バグ対応完了、push失敗、監視不能、run未登録、forge CLI失敗、および中断が含まれる。
監視処理自体の完了と、公開工程としての成功は明確に区別して扱う。
`agent-toolkit:process-wi`の完了担当エージェントは、正常に検収できた`CI成功`または`CI定義なし`を、完了報告の`CIの結果`として返す。
それ以外の未完了状態となった場合は、既存の`続行できない理由:`にその理由を記載して返し、CI照会不能や公開後操作の前提不足に該当する場合は、次節に示す引き継ぎ情報も含める。
追加のpush（原因コミットへ統合した修正のforce pushを含む）を行う際は、その都度新しいディレクトリを作成し、新たなベースラインを作成する。

## 公開工程の続行不能の受渡し

CI定義の判定、ベースラインの作成、push後の監視、または公開後操作が前提条件の不足によって完了できない場合は、同一対象について「完了済みの工程」と「残りの未完了工程」を明確に分けて引き継ぎを行う。
記録には、対象のforge、リポジトリ、コミット、参照（ref）、失敗した操作とその対象（リリース名、タグ名、配布先など）、診断情報、正常終了した公開後操作、pushの成否、および「公開状態の4項目」の観測結果を含める。
さらに、ローカル全体検証の成否、バージョン番号、生成ファイル、公開後操作、延期されたadoptの進捗状況も記録し、CI結果を保持する（未判定の場合はその旨を明記する）。
ベースラインファイルや保存済み出力のパス、引き継ぎ記録の絶対パス、不足している前提条件、再開すべき作業工程を後続へ渡す。
pushの手前で中断した場合は「push未実行」、push完了後であれば「確認済みpush」の状態を維持する。
「公開状態の4項目」が満たされていることや、ローカルでの全体検証が成功していることのみをもって、安易にCI成功と判断しない。

回復処理およびユーザー確認の手順は、`references/publish.md`「公開工程の続行不能からの再開」に従う。
CI判定が回復したあとは、保存済みのベースライン、または「pushと監視」節に記載の`--wait-sha`を用いて監視を再開する。公開後操作については、記録された対象と再開位置をもとに同一コミットに対する未完了の工程のみを再開し、すでに成功しているバージョン更新、push、および公開後操作を重複して実行しないようにする。
