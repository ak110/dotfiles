# レーンの計画から後始末

②の開始時に、①の出力を確定したprocess-feedbacksのメインがこの文書を全文読み、計画、実装、マージ、`adopt`及び所有資源の後始末へ適用する。
この文書はレーン内の責務境界を定義し、①で固定したprocessableなready項目の全体選定を再実行しない。
②の入力となる項目は①で全て`processing`へ移っているため、レーンは`start-processing`を再実行しない。
レーンはpushとCIを実行せず、全レーン後の③へ結果を返す。

## レーンと資源

1つの計画ファイルを1レーンとし、各レーンへ専用managed-tempと専用git worktreeを作成する。
現在worktreeの借用、統合branch、統合worktree及び先行依存する複数計画の同一レーン共有は行わない。
異なるレーンは、ファイルの重複にかかわらず独立して起動できる。

レーンのフィードバックファイル名一覧は、pickerが確定した実装依存順を変更せずに渡す。確認・保留事項と固有の終端順序も同じ対応を維持する。0件のレーンは起動せず、1件以上のレーンだけを計画又は実装へ渡す。
レーンの計画担当と実装担当へは、ファイル名、計画ファイルの絶対パスと再開位置を渡す。各担当は自らの契約に従って正本を直接読み、メインによる本文の要約を入力の代替にしない。
専用managed-tempと専用worktreeの絶対パス、所有主体、作成目的及び回収可否をレーンの入力へ記録する。

専用worktreeでの検査コマンドが、複製元では成立している実行前提（ツール管理器による設定の信頼登録など）の不足で停止した場合は、
当該ツールの公式仕様又は実測で解消手段を確認してから実行する。
複製元への登録が当該worktreeへも及ぶことを確認できた場合は複製元へ登録し、確認できない場合は停止した対象を直接登録する。
信頼するパス等を列挙する環境変数は、既存の登録を置換して複製元を対象から外す動作を持つ場合があるため、
置換しないことを確認できるまで解消手段に用いない。

## 通常型の計画

`feedbacks-planner`を起動する時点で`${CLAUDE_PLUGIN_ROOT}/share/feedbacks-planner.parent.md`を全文読む。

計画レビュー完了後、通常型フィードバックを計画型へ変換し、当該計画を同じレーンの`plan-executor`へ渡す。
既存計画のフィードバックは計画と計画レビューを繰り返さず、1計画1レーンとして並列に起動する。
計画担当は計画完了後の実装、実装レビュー、マージ及びキュー終端を担当しない。

計画担当が調査の結果として担当フィードバックの全ての要求を不採用と確定した場合は、実装、実装レビュー及びマージを行わない。
レーンは不採用の対象と根拠をメインへ返し、メインが`atk mq reject <filename>`を実行して保存結果を照合する。
人間由来の要求を含む不採用は、メインがユーザーの確認を得てから実行する。

## 実装とレビュー

`plan-executor`は依存先計画が導入する単一の実装レビュー担当を使う。
直接実装、レビュー省略、全体レビューへの責任移管をしない。
同じレーンの実装単位は依存順に同じ専用worktreeで実装し、同時に1つの実装担当だけを置く。
実装レビューが収束した時点で、`plan-executor.parent.md`の計画最終化を完了してからマージ許可を要求する。
計画レビューの収束時点ではprivate-notesへ移動又はcommitしない。

実装レビューの`review_round`は、第3ラウンド以降のラウンドと指摘0件で収束したラウンドだけを`round`と`findings_count`で返す。第1・第2ラウンドはレーン内で次のラウンドへ進める。第3ラウンド以降はメインがレビュー指摘管理表を読み、方向性、再設計、継続可否へ介入する。
レビュー表の行数を監視へ追加する仕組み、受領済み行数、次回比較、未着是正メッセージを用いない。無進行は一般的な待機と観測の契約で扱う。

認可範囲外、前提差異、ユーザー判断が生じた場合は`needs_escalation`でメインへ返す。
メインが判断した後、同じexecutorと、同じtask・実効`engine`・`model`・`effort`が成立する同じ実装担当threadへ指示を返す。
route変更、識別子消失又は前提無効時だけ一般的な継続契約に従って新規起動する。

## マージとadopt

レーン内レビュー収束後は`merge_request`でメインへ許可を求める。メインは1レーンずつマージ許可を与え、許可中は他レーンのベース更新を許可しない。
与えた許可は当該レーンが`計画実行完了`を返すまで有効であり、rebase競合と再レビューを経た後も同じ許可でffマージまで進む。レーンは同じ収束に対して`merge_request`を再送しない。

許可を受領した最後の作業担当は最新のベースtipへrebaseする。競合解消が実装差分を生んだ場合は同じ担当がレビュー指摘管理表へ競合と解消結果を記録し、
単一の実装レビューを再度完了してからffマージへ進む。競合解消のためだけの別レビュー又は統合差分レビューを使わない。

最後の作業担当はベースbranchへ`--ff-only`でマージする。
成功後のベースHEAD完全OIDを取得し、固有の延期指示がない関連フィードバックを1件ずつ`atk mq adopt --commit=<完全OID>`で終端して保存結果を照合する。

固有指示が`adopt`をPR又はMRのマージ、release又は配布後へ明示的に延期する場合だけ、ベースHEAD完全OIDと未完了の固有順序を③へ渡す。
レーンを完了扱いにせず、実装に使ったbranch、worktree及びレーンmanaged-tempを再利用しない。
レーンがffマージ後に自身の所有記録と対象を読み取り専用で照合して回収し、③で先行工程が成功した後、同じレーン責務として`adopt`と保存結果を照合して完了する。
新しいworktree又はレビューを作成しない。

## 後始末と非実装項目

通常は`adopt`後、レーンが自身の所有を記録したbranch、worktree及びレーンmanaged-tempだけを読み取り専用で照合して削除する。
ffマージを実行した作業ツリーの絶対パスとマージ先branch名を後始末まで保持する。
branchの削除の直前に、`git -C <保持した作業ツリーの絶対パス> symbolic-ref --short HEAD`の出力が保持したマージ先branch名と一致することを読み取り専用で照合する。
一致した場合だけ`git -C <保持した作業ツリーの絶対パス> branch -d <所有branch名>`を実行し、統合済みかどうかの判定をGitへ委ねる。
一致しない場合と当該コマンドが失敗した場合はbranchを削除しない。
保持した絶対パス、期待するマージ先branch名と観測した出力を`needs_escalation`で返す。
Gitはコマンドを実行した作業ツリーが指すbranchを統合判定の基準にするため、実行場所と現在のbranchを確認しないと、統合先と異なるbranchを基準に未統合と判定されて削除が拒否されるか、統合先の子孫にあたる別のbranchを基準に削除が通る。
対象外worktree、複製元、管理外領域は削除しない。失敗時は残存対象を`needs_escalation`へ返す。

外部操作だけの項目は必要な認可と結果を確認して終端する。既存commitと既存実装で充足済みの項目は対象commitと要求充足を実測して`adopt`する。
これらに計画ファイル、worktree、計画レビュー、実装レビューを作成しない。

## レーン完了報告

レーンは次を完了してから`計画実行完了`だけを返す。

- 計画型は計画レビュー、実装、単一の実装レビュー、ffマージ、`adopt`及び所有資源の回収
- 既存計画の実装は実装、単一の実装レビュー、ffマージ、`adopt`及び所有資源の回収
- 外部操作又は既存実装の確認は、認可、結果、対象commit及び要求充足

固有の延期指示で終端工程が残る場合は完了報告を返さず、ベースHEAD完全OID、未完了の固有順序及び回収済み資源を`needs_escalation`でメインへ返す。
