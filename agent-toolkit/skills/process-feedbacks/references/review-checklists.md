# フィードバック調査と採否の観点

`process-feedbacks`の調査と採否だけを扱う。分類方法、委譲プロンプト、実装、レビュー、commitの手順は扱わない。

## 反映内容と配置の調整

フィードバックの目的を保ちながら、重複と恒常コストが最小になる成果物へ調整する。

### 主提案

- 文書による回避策、例外、適用除外が提案された場合は、原因となるコード、設定、規範の修正または撤去で
  同じ目的を達成できるかを先に確認する
- 既存の仕組みを変更する場合は、その目的が現在も必要かを確認し、維持、内部修正、置換、撤去を比較する。対象リポジトリごとに運用が異なる事項（公開先など）をスクリプトが推測して起動プロンプトへ注入する仕組みは、撤去候補として明示して比較する
- 候補は正確性、運用負担、失敗時の再試行、恒常的なcontext消費を含む総ライフサイクルコストで比較する
- 根本原因と独立した改善は現在の実装へ混ぜず、実行主体が`agent-toolkit:add-feedback`をSkill機能で起動し、
  完成済み本文と対象リポジトリを渡す

### 配置

- 既存記述で同じ命題を扱える場合は、新しい節や箇条書き項目を増やさず既存記述を補強する
- コード、設定、プロジェクト文書、横断規範のうち、判断主体と適用範囲が一致する場所を選ぶ
- 複数の成果物へ一般化できる原則は上位規範を候補にし、固有名を除いても成立するか確認する
- SRP、共有状態、排他、非同期処理が判断を左右する場合だけ、
  `agent-toolkit:coding-standards`の設計ヒューリスティクスから該当節を読む
- 公式資料の参照だけで確認できる外部ツールの操作方法は恒常規範へ転記しない

### 保持する情報

原文が示す観測事象、期待結果、外部可視の手段と順序、判断根拠を保持する。
未指定の内部実装は目的と公開契約を維持する最適案へ置き換えられる。
外部可視要素を変える案は同等性を推測せず、ユーザー確認またはTBDへ送る。
フィードバック原文が示す文言案、列挙及び節配置をユーザー合意とみなさない。
目的と指定された外部可視要素を維持する文面調整は技術判断として確定し、原文との差異と根拠を採否記録へ残す。

## 内容調整チェックリスト

- 各採否記録が原文正本ID、人間由来の指示又は方針の優先度、項目ごとの調査根拠、欠陥原因及び採否理由を同じ項目へ対応付けていることを確認する
- バッチ全項目の採否記録を保持し、全要求不採用の項目をreject対象、保留項目をhold対象と計画スレッドの起動前に判定して計画対象集合から除外していることを確認する。判定結果にファイル名、区分、採否理由及びhold対象の既存TBD・依存・`blocked`状態との対応があり、`feedbacks-planner`がキュー状態を変更せずメインへ返していることも確認する
- メインが完了報告のreject対象とhold対象を検収し、既存のキュー操作経路で処理していることを確認する。操作前に保存状態を照合し、完了済みの操作を再実行していないことも確認する
- 統合計画の`## 実施内容`が計画対象集合と一致し、部分採用行が`agent-toolkit:plan-mode`の計画ファイル基準へ適合することを確認する
- 完全採用以外の結果へ項目固有の採否理由又は原文との差異があり、部分採用では採用範囲と除外範囲の両方があることを確認する
- 不採用の`--note`が項目ごとの実際の採否理由を持ち、同じメモを複数項目へ用いる場合も各項目で同じ採否理由が成立する根拠を確認する
- `agent-toolkit:process-feedbacks`の採否結果契約にある値集合でエージェント由来と確認できる項目だけを不採用時のユーザー確認から除外し、それ以外のsource、欠落及び不明は確認対象にすることを確認する
- `feedbacks-planner`の`status`を失敗処理より先に確認し、`awaiting_confirmation`を失敗として扱わないことを確認する
- 不採用確認用`user_decisions`を通常の将来判断TBDと区別し、停止済みの識別子へ継続せず、直接回答又は保留結果を同じ`feedbacks-planner`系列の新しい識別子へ渡すことを確認する
- 初回起動には再開コンテキストを含めず、`awaiting_confirmation`後の新規起動だけへ`agent-toolkit:process-feedbacks`の採否記録契約が定める累積レコードと再開入力を渡すことを確認する
- 保存済みの不採用確認用TBDを受領した再開では既存TBDと元項目の`blocked`状態だけを照合し、TBD再投入、再依存及び再inboxを実行しないことを確認する
- 保存済みの不採用確認用TBDを受領した再開の工程が失敗しても、既存の確認TBDを同じ依存として保持し、新しい失敗TBD、再依存及び再inboxを作成又は実行しないことを確認する
- 保留項目を既存の`blocked`状態のまま計画対象集合から除外し、残る採用項目がある場合だけ計画起草を続行することを確認する
- 部分採用をユーザー確認へ機械的に含めず、差異、採用範囲、除外範囲及び採否理由を記録することを確認する
- 別リポジトリ項目は`agent-toolkit:add-feedback`の別リポジトリ投入契約を正本として、登録、照合及び元項目の終端順序を確認する

- 原文を目的、観測事象、期待結果、指定された外部可視要素、未指定の内部実装へ分解する
- 原文の理由とトレードオフを反映内容または成果物へ保持する
- 既存の同一命題、SSOT、禁止・推奨規定との重複または衝突を確認する
- 反映先の目的、読者、適用範囲と提案の抽象度を一致させる
- 判定条件や列挙を新設する場合は、説明対象の全項目との対応を確認する
- 既存の成功経路を失う拒否条件、入力制限、権限強化は公開契約変更として扱う
- 原文を実装要求とcommit作成以降の終端工程へ分離して識別する

## 網羅調査チェックリスト

- 変更対象の全文、定義、参照元、呼び出し元、既存test、生成・配布経路を確認する
- 原文の具体値と識別子を実装へ照合し、誤記は正しい帰属先へ読み替える
- フィードバック投入後の変更が原文の前提を無効化していないか履歴と現行実装で確認する
- 外部仕様は公式一次資料で裏付け、当該仕様が方針選択の根拠となる場合は実機再現も併せて示す。裏付けられない候補を`未検証`とする
- 新しい規範を追加する場合は、同じ適用範囲の既存実装を確認し、既存不整合の扱いを確定する
- ユーザー由来の外部可視要件を変える案は、観測上の同等性にかかわらず、仕様変更として確認経路へ送る

## 批判的検討チェックリスト

- 品質向上へ寄与し、元の目的または公開契約に対応する要求だけを採用する
- 自己生成起点のフィードバックでは生成工程の欠陥も候補に含める。
  懐疑的に採否を判定する位置づけは`agent-toolkit/rules/01-agent.md`「方針が衝突する場合の優先順位」節に従う
- 技術的不成立は指定された利用シナリオの実測で確定し、未明示の既存制約だけを理由にしない
- 不採用の根拠に既存対応済みを用いる場合は、既存対処が原文の目的を満たすことを実測する
- 明文化方針との衝突を不採用根拠にする前に、原文が当該方針の改訂を要求範囲に含めるかを全ての提案で確認する。
  改訂要求を含む場合は、現行方針との差異自体ではなく、改訂後の方針案を適用優先順位に照合して採否を確定する
- 原文が検証手段を明示し、その手段が現行の検証方針に適合する場合は、実行前であることだけを全ての提案の不採用根拠にしない。
  検証を要求する生成・採否契約は維持し、当該契約が定める工程で検証してから採否を確定する
- ユーザー判断事項は`agent-toolkit/rules/01-agent.md`「協調と自律」節の確認境界へ照合する。
  フィードバック原文の文面案との差異だけをユーザー合意との衝突又はTBD候補として扱わない

## process固有の履歴照合

- ユーザー起草の既採用方針と不採用履歴を確認し、同一主題の判断を無言で覆さない
- 因果主張は原文、現行実装、履歴の対応を確認し、既存対処が目的を満たす場合は重複追加しない
- 不採用は目的不達、技術的不成立、公開契約又は明文化方針との衝突を示す実測根拠を記録する

一般的な原因分析と類似見直しは`../../bugfix/SKILL.md`、文章品質は`../../writing-standards/SKILL.md`、
調査と判断の共通契約は`agent-toolkit/rules/01-agent.md`を正本とする。
