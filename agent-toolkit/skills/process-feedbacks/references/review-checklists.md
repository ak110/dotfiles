# フィードバック調査と採否の観点

process-feedbacksの調査と採否だけを扱う。分類方法、委譲prompt、実装、review、commitの手順は扱わない。

## 内容調整チェックリスト

- 原文を目的、観測事象、期待結果、指定された外部可視要素、未指定の内部実装へ分解する
- 原文の理由とトレードオフを反映内容または成果物へ保持する
- 既存の同一命題、SSOT、禁止・推奨規定との重複または衝突を確認する
- 反映先の目的、読者、適用範囲と提案の抽象度を一致させる
- 判定条件や列挙を新設する場合は、説明対象の全項目との対応を確認する
- 既存の成功経路を失う拒否条件、入力制限、権限強化は公開契約変更として扱う

## 網羅調査チェックリスト

- 変更対象の全文、定義、参照元、呼び出し元、既存test、生成・配布経路を確認する
- 原文の具体値と識別子を実装へ照合し、誤記は正しい帰属先へ読み替える
- フィードバック投入後の変更が原文の前提を無効化していないか履歴と現行実装で確認する
- 外部仕様は公式一次資料または実機で裏付け、裏付けられない候補を`未検証`とする
- 新しい規範を追加する場合は、同じ適用範囲の既存実装を確認し、既存不整合の扱いを確定する
- ユーザー由来の外部可視要件を変える案は、観測上の同等性にかかわらず、仕様変更として確認経路へ送る

## 批判的検討チェックリスト

- 品質向上へ寄与し、元の目的または公開契約に対応する要求だけを採用する
- 自己生成起点のフィードバックは通常より懐疑的に評価し、生成工程の欠陥も候補に含める
- 技術的不成立は指定された利用シナリオの実測で確定し、未明示の既存制約だけを理由にしない
- 単一要求は採用か不採用とし、量や実装負担を理由に内容を薄めない
- 複数の独立要求だけを要求単位へ分け、採用、部分採用、不採用を判定する
- 不採用は既存対応済み、目的不達、技術的不成立、公開契約または明文化方針との衝突のいずれかを
  実測できる場合に限る
- 技術または方針で確定できない事項は不採用にせず保留する
- 採用内容が現行ユーザー合意と衝突する場合は、合意との差異と暫定判断をTBDへ送る
