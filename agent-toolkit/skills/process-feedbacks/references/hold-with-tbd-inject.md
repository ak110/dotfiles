# 保留判定・部分採用の除外要求のTBD投入

保留判定時、フィードバック原文内に事前確認が必要な論点・確認事項・仕様上の未確定項目が列挙されている場合は、
当該事項を`atk mq add --type=tbd`で個別投入してから保留する。

## 準用範囲

本節の書式（`atk mq add --type=tbd`のオプション指定・`--scope`検証等）は、
保留判定を伴わない場合にも準用する。準用先は次のとおり。

- `agent-toolkit:process-feedbacks`「フィードバック投入」節のTBD投入
- `agent-toolkit:process-feedbacks`ステップ3「複数要求の分解判定」で部分採用と判定した際の除外要求投入

「フィードバック投入」節のTBD投入は`atk mq add`実行前に発生するため、
対象フィードバックファイルは未生成であり、
`--scope`値の事前ファイル存在検証（`ls`・`grep`照合）は適用対象外とする。
部分採用の除外要求投入は既に生成済みの対象フィードバックファイルを`--scope`値に指定するため、
事前ファイル存在検証は通常どおり適用する。
`atk mq add`が生成するファイル名`{timestamp}-{counter:03d}.md`の`{timestamp}`部分は
`atk mq add`実行時点で確定し、秒単位で異なる値になり得るため事前予測は不可能である。
TBD投入時は暫定値（投入セッションの現在時刻等）を`--scope`に指定し、
`atk mq add`実行後に事後照合する。
不一致が確認された場合は、`atk mq show <ファイル名>`で現在の質問本文を確認し、
`atk mq edit <ファイル名> $'---\nscope: <実ファイル名の日付連番部分>\n---\n\n<現在の質問本文>'`で
`scope`だけを更新する。
editはTBDの回答欄と既存回答を保持する。
1回の`atk mq add`呼び出しで複数`counter`のファイルが生成された場合は、
論点が全ファイル共通なら共通の`{timestamp}`部分のみを`--scope`に指定する。
論点がcounter個別ファイル固有なら全`counter`値へ個別のTBDを紐付ける。

## 保留判定を確定する前の観測ソース精査

確定前に、原因調査に利用可能な観測ソースを全件洗い出したうえで精査を試みる。

- 対象観測ソースは`~/.claude/projects/`配下のセッションjsonlログ・実行トレース・作業ツリー痕跡（`git status`・`git log`・`git reflog`）などを含む
- 精査で源が特定できた場合は保留判定を再検討する
- 特定できない場合のみ保留判定を確定し、精査対象と検索パターン・結果件数を保留理由へ添える

## 対象論点の判定基準

次のいずれかを満たす記述のうち、ユーザーの判断を要するものだけを対象とする。
調査・実機実行で確定できる技術判断と、方針から一意に定まる事項は投入せず自ら確定する。
本条件は「保留判定時のTBD投入」節が定める条件と同一とする。

- 「事前確認が必要な論点」「未確定事項」「要確認」等の見出し配下の項目
- 質問形式で明記された項目

## 投入コマンド

各論点を個別に次の書式で投入する。

`atk mq add --type=tbd --question-type=choice --choices "<選択肢1>,<選択肢2>,..." --scope=<提案識別子> "<論点本文>"`

対象リポジトリは`atk mq add --type=tbd`実行時のカレントディレクトリから自動解決される。

選択肢化可能な論点は`--question-type=choice`と`--choices`を用いた選択肢形式を優先する。
選択肢化が困難な自由記述質問のみ`--question-type=free-form`（既定）を用いる。

`<提案識別子>`はフィードバックファイル名の日付連番部分などを使う。
`--scope`引数の値はフィードバックファイル名の日付連番部分と一致することを投入前に検証する。
検証は`ls`で該当ファイル名を確認するか、`--scope`値を含むファイル名を`grep`で照合する。

投入する論点本文は疑問文・判定に至った経緯や前提記述・自己完結性
（当該ファイル単体で採否判定できる情報の充足）の各要件を満たす形で書く。
判断が必要な点を複数列挙する場合、各項目を回答を求める文の形で個別に書く
（列挙のみで終える項目を残さない）。
後述の「保留判定時のTBD投入」節が定める
保留理由・実機検証済みの内容・次回再評価時の確認事項の3項目は状態記録であり、本要件の規範上の対象外とする。
ただし`_atk_mq_tbd.py`の機械検出は投入元（`--source`）で分岐せず、
疑問文・自己完結性いずれの欠如も警告のみで投入は成功する。

調査・実機実行で確定できる技術判断はTBDへ投入せず自律決定する
（`agent-toolkit/rules/01-agent.md`「協調と自律」節の
「技術的に優劣を判断できる事項は選択肢化せず最適な手法を選ぶ」をTBD投入経路へも適用する）。
ユーザーの判断を要する事項を投入する場合、回答者が選ぶ対象ごとにメリットとデメリットを
本文へ明示する。実装識別子・内部構造の羅列を判断材料の代替としない。

## 本文に含めない要素

TBD本文には質問内容のみを書く。
frontmatter・見出し・回答欄はツールが自動付与するため、本文へ同じ要素を書かない。
含めた場合は`atk mq add --type=tbd`が投入を拒否する。
本節は「投入コマンド」節・「保留判定時のTBD投入」節の双方の投入経路へ適用する。

## 投入後の扱い

TBD投入はフィードバック本体の配置を変更しない。
本体の所在は「フィードバック投入」節のTBD投入では`atk mq add`実行後のinbox配下、
それ以外の場合（保留判定・部分採用の除外要求の投入時）はprocessing配下となる。
次回起動時、回答済みTBDと合わせて再評価する。

## 保留判定時のTBD投入

`agent-toolkit:process-feedbacks`ステップ2.5で保留判定を確定した時点で、
保留の内容がユーザーの判断を要する論点を含む場合にのみ次のコマンドを実施する。

`atk mq add --type=tbd --scope=hold --source=session-hold --question-type=free-form "<本文>"`

`--scope=hold`は固定値運用とし、本ファイル「対象論点の判定基準」節の`--scope`値検証手順
（`ls`・`grep`によるファイル名照合）は本用途では適用しない。

feedback原文内に事前確認の対象が列挙される場合は、本節の投入と本ファイル「投入コマンド」節の
個別論点投入を併用する（保留全体の記録と個別論点の記録の両方を残す）。

ユーザーの判断を要する論点を含まない保留（外部前提の充足を待つだけのもの等）は本コマンドを実施しない。
対象ファイルを`Read`し、frontmatter終端以降の既存論理本文を取得する。
既存論理本文の末尾へ次の3項目を追記した完全な本文を構築し、`atk mq edit <FILENAME> "<既存論理本文と3項目を結合した完全な本文>"`（非対話編集）へ渡して記録する。
実行後に対象ファイルを再度`Read`し、既存論理本文が欠落・改変していないことと、3項目が全て追記されていることを確認する。
確認できない場合は保留記録の完了と扱わず、元本文を保持した完全な本文を再構築して是正する。
3項目を要約せず記載する自己完結性の要件は本節末尾の規定に従う。

本文には次の3項目を含める。

- 保留理由（何を待っているか・何が未確定か）
- 実機検証済みの内容（前提条件を確認した手段・確認結果）
- 次回再評価時の確認事項（何が判明すれば採用可能になるか）

投入するTBD本文は、フィードバック原文・計画本文など他ドキュメントを参照しなくても
本文単体で採否判定に必要な情報が揃う自己完結した記述とする。
保留理由・実機検証済みの内容・次回再評価時の確認事項の3項目を要約せず
判定根拠・観測事実・トレードオフを直接転記する。本要件はユーザー確認事項全般に共通する
原則（回答者がTBD本文のみで判断できる状態を満たす）であり、保留判定時のTBD投入に限定されない。
本文が規範上の用語・過去の経緯に由来する語を用いる場合は、その語が指す実体
（定義の所在・対象範囲）を本文内で示す。
自己完結とは回答者の判断に必要な情報が揃っている状態を指し、見出し・回答欄の書式を整えることではない。
