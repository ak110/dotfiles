# 計画実装型フィードバック

トップレベルの`plan_file`を持つactiveなフィードバックだけを計画実装型とする。本文から型を推測しない。
計画実装型を処理する呼び出し元は、通常開始又は中断後再開の最初の委譲前に`agent-toolkit:delegation`をSkill機能で起動する。

## 実行バッチ

同じ計画ファイル（同じ`plan_file`）を持つready項目を1レーンとする。
レーンは、1つの計画ファイルと、その実装専用のworktree及び書込担当で構成する並列実装の単位である。
readyなレーンが1件なら現在のcleanなworktreeで実行する。
完全な一覧には`用途=lane`、`管理対象領域=なし`、`作成主体=既存`、`回収可否=不可`として含める。
複数レーンなら変更対象ファイルの重複を待機又は分割の条件にせず、利用可能な書込担当枠まで上流追随済みの別worktreeへ1計画ファイルずつ割り当てる。
呼び出し元は管理対象領域内へレーンのworktreeを作成する。
完全な一覧の記録属性は`plan-impl-caller-reception.md`を正本とする。
1つの計画ファイルに属する実装単位は、1つの書込担当が同じworktreeで順次実装する。
異なる計画ファイルのレーンだけを別worktreeで並列化し、dirty差分を前提とする計画は並列化しない。

各レーンの呼び出し元は、`plan-impl-executor`の起動前に`agent-toolkit:delegation`をSkill機能で起動する。
各レーンは`plan-impl-executor`を起動する。
各レーンの呼び出し元は`agent-toolkit/skills/plan-mode/references/plan-impl-caller-reception.md`を全文読み、
`plan-impl-executor`の起動と受領に関する委譲元契約の正本とする。
readyな計画が1件の場合は、借用する現在worktreeを回収不可として含む完全な一覧を同文書に従って構成する。
複数レーンの場合は、レーンのworktreeと計画が明示する管理対象worktreeを含む完全な一覧を同文書に従って構成する。
起動文には計画、プロジェクト規範、該当する作成規範スキルの絶対パス、
worktreeの完全な一覧、ソート済みフィードバックファイル名一覧、追加指示、
許容済みの挙動変化、権限だけを渡し、
実装とレビューのタスク本文を複製しない。
フィードバックファイル名一覧が0件の場合はレーンを起動しない。
1件の場合も一覧として渡し、複数件の場合は項目をファイル名昇順に保つ。

レーンの結果を受領後、呼び出し元は`atk managed-temp create --prefix <統合用途を示す値>`を単独で実行し、
標準出力の絶対パスを統合用管理対象領域として保持する。
同領域内に統合対応表を作成し、領域の絶対パス、用途、所有主体、回収可否を各レーン計画の`## 進捗ログ`へ記録する。

統合対応表はレーン項目とレビュー修正項目を判別可能にする。
レーン項目はソート済みフィードバックファイル名一覧、レーンのcommitの完全OID、計画ファイルの絶対パス、統合順を持つ。
レビュー修正項目は安定ID、関係する全計画パス、指摘ID、適用元OID、再適用後OIDまたは
状態`適用済みスキップ`、統合順を持つ。
新規レビュー修正だけを追加し、既存項目は統合担当の適用結果で置換更新する。

統合対応表の作成直後に、レーン項目のソート済みフィードバックファイル名一覧を全レーン分連結し、
ファイル名ごとの出現回数を数える。
母集団は`atk mq list --type=feedback --status=processing --target-repo=<repo>`の出力から
当該バッチで不採用又は保留と確定した項目を除いた集合とする。
母集団の各ファイル名の出現回数が1回であり、母集団に含まれないファイル名の出現回数が0回であることを確認する。
未割当と重複を0件とする原則は`../../delegation/SKILL.md`の「送信」工程1が定め、再集約でも同じ不変条件を適用する。
出現回数0回の未割当、2回以上の重複、母集団外のファイル名の混入のいずれかを検出した場合は統合担当を起動しない。
未割当では欠落したレーンを統合順へ追加し、重複では担当レーンを1つへ確定し、
母集団外の混入では当該ファイル名をレーン項目から除いたうえで、同じ照合を再実行してから起動する。

呼び出し元は`git fetch`後の上流最新OIDから同領域内へ統合worktreeを新規作成する。

### 統合担当の起動

統合担当の起動前に、呼び出し元は各レーンの計画から配布物の版数更新の入力を次の項目で読み取る。

- 適用可否: 当該レーンの計画が`agent-toolkit/`配下を変更対象に含むかで判定する。含まないレーンは以降の項目を持たず、集約の対象にもしない
- 種別: `bump不要`、PATCH、MINOR、MAJORのいずれか
- 選定根拠: 当該種別を選んだ理由
- 認可根拠: 種別がMAJORの場合の利用者の明示指示。他の種別では持たない

適用可否が是のレーンで種別又は選定根拠のいずれかを読み取れない場合は、統合担当を起動せず当該レーンへ差し戻す。
適用可否が是のレーンが1件も無い場合、及び適用対象の全レーンの種別が`bump不要`の場合は、統合段階で版数を更新せず「統合段階で1回だけ適用する変更」を`なし`として統合担当を起動する。
それ以外では`bump不要`、PATCH、MINOR、MAJORの順序で最も上位の種別を確定し、当該種別の版数更新を「統合段階で1回だけ適用する変更」として統合担当を起動する。
確定した種別がMAJORで、当該種別を記録したレーンの認可根拠を読み取れない場合は、統合担当を起動せず確認へ送り、回答を得るまで起動しない。

統合担当の各新規起動又はCodex経路の継続接続の直前に`atk config get merge_model`を実行し、
`runtime-routing.md`「工程別モデル設定」で経路を解決する。
統合担当へ`merge-task.md`、統合worktreeと作成時HEADの完全OID、統合対応表、全計画、プロジェクト規範、
作成規範スキル、検証コマンド、統合段階で1回だけ適用する変更、commit可・push不可・worktree作成回収不可・キュー変更不可の権限を渡す。
統合担当はrebaseを行わず、全項目を単一cherry-pickシーケンスで適用する。競合処理のGit操作と検収は`merge-task.md`を正本とし、
統合担当は完了報告の`conflicts`と`integration_changes`へ結果を返し、呼び出し元は返却値だけを検収する。

初回統合では、統合worktreeの作成後に本節の手順で統合担当を起動する。

各レーンのcommitはレーン内で二系統レビュー済みであるため、統合後のレビュー対象は統合段階で新たに生じた差分に限る。
当該差分は、統合担当が作成したcommitの累積差分と、cherry-pick中に競合を解消した箇所とする。
差分の由来による区分は設けず、生成器又はbumpツールが作成した差分も同じ対象へ含める。
統合段階で新たに生じた差分が無い場合は、統合後のレビューを実施しない。
差分がある場合は、当該箇所と同一ファイルの隣接する記述を対象として`plan-impl-executor`の統合後レビュー調整モードを起動し、レーンのcommitをそのまま適用できた箇所を対象へ含めない。
統合段階の変更一覧は統合担当が返す値を正本とし、呼び出し元は無加工で保持して統合後レビュー調整モードへ渡す。
一覧の生存範囲は現行の統合worktreeの世代に一致させ、次の時機で状態を遷移させる。

- 統合worktreeを作成した時点で、当該worktreeの一覧を空で新規作成する
- 同一worktree内で統合担当が新しい一覧を返した時点で、保持している一覧へ当該値を追加し、累積で保持する
- 統合worktreeを回収した時点で、当該worktreeの一覧を現行のレビュー範囲から外す。レビュー履歴として保持してよい
- 統合worktreeを作成した後、統合後レビューの収束を呼び出し元が各計画の`## 進捗ログ`へ記録するまでのどの時点で中断した場合も、当該統合worktreeを再利用せず、新規作成の時点から再実行する

レビュー修正で生じた差分も同一worktreeの集合へ加わるため、収束判定は現行worktreeの一覧の累積差分に対する二系統の指摘0件とする。

起動時は共通入力として、モード指定`統合後レビュー調整モード`、プロジェクト規範、
該当する作成規範スキルの絶対パス、追加指示、許容済みの挙動変化、git操作の制約を渡す。
モード固有入力として、統合worktree、統合担当へ渡した作成時HEADの完全OIDと同じ文字列、
最終HEADの完全OIDと統合段階の変更一覧を渡す。
加えて、統合対応表の絶対パス、統合対応表に含まれる全計画の絶対パス、
統合スレッドの検証結果及び統合用管理対象領域の絶対パスを渡す。
再レビュー時は既存の固定6列TSV（重要度、指摘箇所、指摘内容、対応要否、対応内容、対応不要理由）ファイルの絶対パスも渡す。
統合後HEADはレビュー対象として渡すが、統合担当以降の差分を公開契約の認可基準へ含めない。
`plan-impl-executor`は採用指摘の固定6列TSVを統合用管理対象領域内へ保存し、絶対パスと実在・分量証跡を返す。
呼び出し元は内容を読まず、再統合と再レビューへ絶対パスだけを渡す。

push直前のfetch照合、pushのdry-run、実pushで上流進行またはnon-fast-forward拒否を観測した場合は再統合する。
統合対応表へ新規レビュー修正commitを追加し、既存レビュー修正項目を適用結果で更新してから旧worktreeを回収する。
新しい上流最新OIDから統合worktreeを再作成し、本節の手順で統合担当を起動する。
全項目の単一cherry-pickシーケンスと検証を再実施し、レビューは前掲の統合段階で新たに生じた差分の条件で判定する。
統合段階の変更一覧は新しい統合worktreeの適用結果から再構築し、旧worktreeの一覧を現行のレビュー範囲へ引き継がない。
前回の採用指摘と差分は既存の固定6列TSVファイルのパスで引き継ぐ。

終了条件は実push成功と当該OIDのCI通過とする。
終端工程を持つ項目は、終了条件の後かつadoptの前に本文が列挙した終端工程を統合順で1回だけ実行する。
完了後に成功した項目へ、ソート済みフィードバックファイル名一覧の順で既存の`atk mq adopt`を1件ずつ実行する。
各保存結果を照合した後に、成功したレーンのworktreeを回収する。
統合用管理対象領域はadopt完了後にだけ`atk managed-temp cleanup --path <検収済み絶対パス>`で回収する。
中断後はキューの`plan_file`から各計画の進捗ログを辿り、統合用管理対象領域の実在、所有、対象フィードバックとの対応を照合して再利用する。
照合できない旧領域は保持し、統合を最初からやり直す。
統合worktreeを作成した後、統合後レビューの収束を各計画の`## 進捗ログ`へ記録するまでのどの時点で中断した場合も、統合用管理対象領域を照合できるかにかかわらず旧統合worktreeを再利用しない。
再開では、領域内の検証済みの統合対応表と既存の固定6列TSVファイルだけを引き継ぎ、新しい上流最新OIDから統合worktreeを作成して、統合、統合段階の変更一覧の生成及び統合後レビューを最初から再実行する。
旧統合worktreeは調査可能な状態で保持し、当該worktreeの一覧を現行のレビュー範囲へ含めない。回収は再実行が公開へ到達した後に行う。

失敗したレーンは調査可能な状態で保持する。ユーザー合意を覆す判断は自動反映せずTBDへ送る。
