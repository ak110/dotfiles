# 計画実装型フィードバックの処理フロー

計画実装型フィードバック（既存レビュー済み計画の実装のみを要求するフィードバック）の
判定基準と実行制御を定める。
`agent-toolkit:process-feedbacks`「ステップ1: 入力の確定」「ステップ5: 計画作成と実行」
「計画分割基準」から参照されるSSOTとする。

## 判定基準

フィードバック本文が既存計画ファイルの絶対パスに言及し、かつ当該ファイルが実在する場合を
「計画実装型」とし、それ以外を「通常型」として扱う。判定条件は「本文の絶対パス言及」と
「当該ファイルの実在」のみとする。計画実装型は`agent-toolkit:plan-and-add-feedback`の
投入元セッションで工程1〜7（レビュー含む）を完遂済みである。
そのため`agent-toolkit:process-feedbacks`ステップ2〜4（内容調整・網羅調査・批判的検討）を適用せず、
計画ファイル実在確認のみで採用扱いとする。計画ファイルが実在しない場合は通常型として扱う。

## 混在時の並行制御

`atk mq schedule`は、選抜した計画実装型の対象ファイルと通常型の推定対象ファイルを突合する。
非競合群だけを計画実装型の実行中に通常型のステップ2〜5まで進める。

競合群は計画実装型の完了報告を検収した後に、通常型のステップ2から処理する。
対象ファイルが空の通常型も競合群へ含める。
計画実装型が完了せず競合群を次回へ送る場合は、各項目を`conflict:<filename>`形式にする。
その値を`atk mq schedule --record-deferral <reason:filename...> --target-repo=<repo-path>`へ渡し、
理由と繰越回数を記録してinboxへ戻す。

競合項目を計画実装型へ統合する場合は、計画ファイルを改訂してCodex再レビューを完了する。
実装中の委譲先へ追加指示として注入しない。
協調モードは統合可否をユーザーへ確認する。
自律モードはTBDへ記録し、計画実装型の完了後に通常型として処理する。

各起動の直前には`agent-toolkit/references/plan-impl/caller-reception.md`の
起動前の準備（`git rev-parse HEAD`による計画着手前SHAの記録）を都度実施する。
完了通知の受領のたびに`agent-toolkit/references/plan-impl/caller-reception.md`の
受領手順で検収し、次の計画実装型を1件ずつ起動する。
作業ツリー・コミットの競合を避けるため、計画実装型どうしの実装は直列に限定し並列起動しない。
バックグラウンド実装は当該の計画実装型フィードバックについて作業ツリーを触る唯一の主体とし、
検証・コミット・`agent-toolkit:careful-review`実施まで`plan-impl-executor`へ委譲する。`git push`は委譲せず
本スキル「ステップ7: 採否確定の後始末」で一括実施する。
通常型の計画実装（`plan-impl-executor`起動）は、先行する全ての計画実装型`plan-impl-executor`のうち
最後に起動した1件の完了報告本文を呼び出し元が受領した時点で開始条件が成立する。
完了報告本文の必須欄は`agent-toolkit/references/plan-impl/caller-reception.md`手順0のSSOTに従い、
`review_handoff`欄を含む形式とする。
作業ツリー全体へ影響する検証・コミットの競合を避けるため直列とする。
commit SHAの進捗観測を単独の判定根拠にしない。

## 計画実装型のみの場合

計画実装型フィードバックのみを処理対象とする場合、計画作成工程を実施しない。
直列実装の消化完了後、本スキル「ステップ6: 連鎖feedbackの自律投入」以降へ進む。
採否確定はいずれの場合も「ステップ7: 採否確定の後始末」（`atk mq adopt`等の後始末コマンド）で行う。

## 複数リポジトリ横断作業の分解投入

作業が複数リポジトリを対象とする場合は、各リポジトリ向けの独立したfeedbackへ分解投入し
`atk mq process-loop`で1リポジトリ1計画1コミット単位の直列消化を既定とする。
単一計画へ集約するのは次のいずれかに限定する。

- 対象が単一リポジトリに閉じる場合
- 複数リポジトリ間で不可分な同期改訂を必要とする場合（同一shaで揃える必要がある改訂など）

上記いずれにも該当しない場合は本節冒頭の分解投入規定に従う。分解投入により対象リポジトリの1つで
別セッションによる並行編集が発生しても、担当外変更の混在・切り分けコスト・衝突リスクが
構造的に発生しない状態を保つ。

## 通常型の計画作成時に行うSSOT事前照合

複数フィードバックを統合する計画を作成する場合は、初版Write前に各反映先ファイルのSSOT間の
相互整合（同期の注記、重複を意図的に明記した箇所の追随、実装典拠との整合）を事前照合するチェックリストを併用する。

## `run_in_background`起動の制約

`run_in_background`起動は権限プロンプトへ応答できない制約
（`agent-toolkit/rules/02-claude-code.md`「サブエージェント運用」節）を持つ。
委譲先が権限プロンプト起因で停滞した場合、同節の停滞検知手順に従い
メイン側で`agent-toolkit/references/plan-impl/caller-reception.md`が定める完遂順序
（実装→検証→コミット→レビュー→push→CI通過確認）のうち未完了の工程を巻き取る。
ただし`git push`とpush後のCI通過確認は本スキル「ステップ7: 採否確定の後始末」で一括実施するため、
本フローでの巻き取り範囲は実装・検証・コミット・レビューまでとする。
本フローは自律実行モード・協調モードを問わず適用する。
自律実行モード（`atk mq process-loop`経由等）はユーザー不在のため本制約の顕在化頻度が高い。
