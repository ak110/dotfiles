# 採否結果と後始末

## 採否結果

要求ごとに次を記録する。素材単位の採否は記録せず、同じ素材から独立した要求行へ分解する。

```markdown
### <filename>: <要約>

- 素材ID: <事前割当した素材ID>
- 要求ID: <素材ID名前空間の要求ID>
- 素材参照: <要求を確定する素材IDの昇順リスト>
- 原文正本ID: <要求の元となる提示素材の原文正本ID>
- 人間由来の指示又は方針の優先度: <要求に対応する優先順位と根拠>
- 調査根拠: <要求ごとの実測・履歴・既存規範又は一次資料>
- 欠陥原因: <採否確定時に個別に確定した原因。該当しない場合は該当なしの根拠>
- 採否: 採用 | 不採用（`部分採用`・`保留`は要求単位の値を持たず、ファイル単位の終端判定だけで扱う）
- 採否理由: <実測した根拠。仕組みを維持・修正する場合は、削除・簡素化案と比較した根拠。不採用は要求固有の採否理由又は原文との差異を含める>
- 投入元識別子: <原文frontmatterのsource文字列又は明示された出所。欄が無い場合は「値なし」>
- 引用範囲: <本文全文、全文、回答全文又は明示された範囲>
- 適用優先順位: <本節の値集合でエージェント由来と判定される項目だけ。優先順位4に準じる判断を記載>
- 懐疑的判定の根拠: <本節の値集合でエージェント由来と判定される項目だけ。通常起点より懐疑的に判定した根拠>
- 採用範囲: <採用時は実装範囲。不採用時は「非該当」>
- 除外範囲: <不採用時は除外範囲。採用時は「非該当」>
- 反映先: <採用時だけ>
- 反映内容: <採用時だけ>
- 確認: <不採用確認用`user_decisions`で必要なAskUserQuestionの質問、回答又は保存したTBD。本節の値集合でエージェント由来と判定されない項目だけ>
- 移管先: <別リポジトリの場合のtarget_repo、指定済みsource（ない場合は該当なし）、登録ファイル名、登録・照合結果。該当しない場合は該当なし>
- 解除条件: <保留時だけ>
```

原文案の文言、列挙又は節配置を技術判断で調整した場合は、差異と根拠を`採否理由`又は`反映内容`へ記録する。

各項目の採否確定では、原文正本ID、人間由来の指示又は方針の優先度、調査根拠、欠陥原因及び採否理由を同じ記録へ対応付ける。
関連性の低い項目を同じ包括理由だけで一括判断せず、同じ`--note`を複数項目へ使う場合も各項目で同じ理由が成立する根拠を記録する。
不採用の結果は項目固有の採否理由・原文との差異を記録する。同一ファイル内で採用要求と不採用要求が混在する場合（ファイル単位の部分採用）は、各要求の採用範囲・除外範囲・採否理由のすべてを記録する。

投入元識別子は`source`の文字列又は「値なし」を改変せず記録する。
エージェント由来の値集合は`session-review`・`alert-monitor`・`agent`とし、これらを値に持つ`source`はエージェント由来と判定して優先順位4へ照合する。
人間由来の値集合は`human`・`plan`とし、その他のsource、source欠落及び不明も人間由来として扱う。
この値集合を由来区分の正本とし、他文書は本節を参照して判定する。
その他の値を含めて値を保持したまま生成経路固有の規定へ照合する。

`source: session-review`の通常本文はエージェント由来とする。末尾のexact H2 `## ユーザーコメント`配下から導出した要求だけは人間由来とし、通常本文から導出した要求と分けて採否を記録する。両方にまたがる記述は独立して採否できる要求へ分解し、ファイル全体の由来を人間へ昇格させない。`source`の原値と予約節は要求の優先順位及び不採用時の確認境界を決める運用上の由来情報であり、push、公開、破壊的操作又は外部サービス変更の利用者認可を証明しない。

独立した要求ごとに採否を確定する。
同一ファイルに採用要求が1件以上ある場合は、採用要求と不採用要求を内部採否記録へ併記し、
不採用要求の採否理由と除外範囲を残す。
ファイル単位の部分採用は独立した複数要求（採用要求と不採用要求）へ分解し、各要求の原文との差異、採用範囲、除外範囲及び採否理由を記録する。
部分採用を理由にAskUserQuestionを機械的に発行せず、`agent-toolkit/rules/01-agent.md`「協調と自律」節の確認経路は
不採用候補の由来境界に従って適用する。
エージェント由来の値集合に含まれる項目の不採用は追加確認を要しない。
それ以外の項目の不採用は、原文との差異と技術的理由を示す`AskUserQuestion`の回答後だけ確定する。
回答が得られない場合は同じ質問内容をTBDへ保存して元項目を保留し、回答又はTBDを確認できない状態では`reject`を実行しない。
不採用確認用`user_decisions`は通常の将来判断TBDと区別する。直接回答、回答なしで保存したTBDのいずれかは、停止済みの識別子へ継続せず、
同じ`feedbacks-planner`系列の新しい識別子へ渡す。

確認待ちを複数サイクルで処理する場合、受領した`user_decisions`原文は現在の未解決項目だけへ置き換えず、原文正本IDごとの累積レコードとして渡す。
各レコードは`id`、`raw`（不採用候補の原文）、`question`（発行したAskUserQuestionの逐語文）、`answer_or_tbd`（逐語回答・保存TBD）と
`unanswered`（未受領ならtrue、受領済みならfalse）、`resolution`及び`decision`を保持する。
`resolution`は未受領なら`未確定`、逐語回答で採否を確定した場合は`回答による確定`、保存TBDで保留した場合は`TBDによる保留`とする。
`decision`は未受領なら`未確定`、逐語回答による確定では`採用`・`部分採用`・`不採用`のいずれか、保存TBDによる保留では`保留`とする。再開した`feedbacks-planner`は`decision`が確定済みのIDを再判断せず、その採否をファイル単位の終端判定に用いる。
新しい回答・TBDは対応するIDへ追記し、過去の確認サイクルのレコードを削除又は上書きしない。
初回起動には再開コンテキストを含めない。
確認待ち後の再開起動へだけ元のバッチ全項目の調査結果全文を渡す。
原文frontmatterの`source`原値（欠落は値なし）、原文正本IDごとの累積`user_decisions`、出所と引用範囲付きの逐語回答・保存TBD、
初回起動と同じ計画ファイルの絶対パスを渡す。
保留項目を計画対象集合から除外し、残る採用項目がある場合だけ計画起草を続行する。通常の将来判断TBDの暫定判断を不採用確認へ混在させない。
別リポジトリ項目の投入と照合は`../../add-feedback/references/cross-repository-submission.md`を正本とする。

sourceによる由来境界の判定と利用者認可の確認を分ける。
sourceは由来境界の判定にだけ用い、source又はフィードバック本文から利用者認可を推定しない。

`atk mq reject`は、process-loop内で要求の全てを不採用と確定した項目だけに用いる。採用済み内容を別項目へ統合した元項目は、統合先をnoteへ記録して`atk mq rm`で除去する。別リポジトリへ移管して投入先を検収した元項目は、移管先をnoteへ記録して`atk mq rm`で除去する。技術的な失敗、入力不足又は外部条件待ちは不採用へ変換しない。TBD依存を追加してactive状態に保つ。

保存済みの不採用確認用TBDを受領した再開で工程が失敗した場合は、既存の確認TBDを同じ依存として保持する。
新しい失敗TBDを作成しない。再依存・再inboxを行わず、既存の`blocked`状態と依存を結果として返す。
既存TBD又は依存を照合できない場合も新しいTBDを作成せず、照合不能の失敗として返す。

## ファイル単位の終端

- 採用要求が1件以上あり、未確定要求が無いファイルは、内部採否記録へ採用・不採用の全要求を保持し、
  計画では当該ファイルを`採用`又は`部分採用`の1行へ投影して採用終端へ進める。
- 全要求が不採用のファイルは、process-loop内で項目固有の採否理由を含むreject対象と計画スレッドの起動前に判定し、計画対象集合から除外する。
- 保留又はTBDなど未確定要求が1件以上あるファイルはhold対象と計画スレッドの起動前に判定し、既存TBD、依存及び`blocked`状態との対応を記録して計画対象集合から除外する。
- reject対象とhold対象のファイル名、判定区分及び理由を完了報告でメインへ返す。`feedbacks-planner`はキュー状態を変更しない。
- 判定で除外されなかったファイルを計画対象集合とする。`## 実施内容`の部分採用行は`../../plan-mode/references/plan-file-standards.md`を正本とする。

## 後始末

- 採用要求を含むファイルは対象commitのpush完了後に
  `atk mq adopt <filename> --note=<反映概要> --commit=<完全長SHA>`で終端させる。
- 採用済み内容を別項目へ統合した元ファイルは、統合先をnoteへ記録して`atk mq rm --force`で除去する。別リポジトリへ移管した元ファイルは、移管先をnoteへ記録して`atk mq rm --force`で除去する。
- process-loop内で全要求不採用と確定したファイルだけを`atk mq reject`で終端する。技術的な失敗、入力不足又は外部条件待ちのファイルは、TBD依存を設定したactive状態で保つ。

`--note`には1行の結果を渡す。`--commit`は対象リポジトリの完全長SHAとし、rejectへは渡さない。
実行後に対象エントリを再取得し、`## 処理結果`の採否、note、commitを入力と照合する。
