# フィードバック選定とレーン分け

①の開始時に、process-feedbacksのメインがこの文書を全文読み、1処理回のprocessableなready項目の固定、選定モデルの起動及び出力の検収へ適用する。
この文書は全体の処理対象を選定する契約であり、通常レーンの計画起草や実装の手順を定義しない。

## 最初の操作

メインは①の開始時に`atk mq list --status=processable --target-repo=<repo-path> --skip-pull`で対象リポジトリの
processable一覧を取得し、そのうち表示上の判定が`ready`である項目だけを処理回の対象集合として固定する。
既存の`planning`、`editing`及び`hold`項目は、候補、優先度、依存判断又は固有指示の入力へ含めない。
processable一覧で`blocked`の項目も、その処理回のpickerへ渡さない。
処理回の進行中に追加されたフィードバックを、進行中のpicker出力又はレーンへ混ぜない。

明示的な連続処理では、②の全レーンが後始末まで完了した後にready一覧を再取得する。
新しいready項目があれば新しい処理回として①へ戻り、0件を確認した場合だけ③へ進む。
この再取得で、完了済みの処理回の項目を再選定しない。

取得した一覧について、保存済みのメタデータと入力の実在を確認する。保存済みのメタデータから`depends_on`、回答済みTBD、`cooldown_until`、frontmatter、計画ファイルの有効性を確認する。
`depends_on`は外部待ち条件だけに用い、本文から再構築しない。日付境界、別リポジトリ候補探索、cycle再計算をせず、`queue_schedule`も移行しない。

CLI操作は実行前に検証する。警告又は失敗があれば対象を再取得し、意図した状態なら再実行せず、部分状態又は原因不明なら`needs_escalation`へ返す。
private notesによるGit復旧、専用の失敗分類及び別の選定キューを作成しない。

## pickerの起動

メインは`atk config get pick_feedbacks_model`を起動直前に実行し、`agent-toolkit:delegation`の工程別モデル設定に従って選択モデルを直接起動する。
`feedbacks-planner`を全体選定の中間調整主体にしない。

pickerへ次の入力だけを渡す。

- 固定した処理対象のフィードバックファイル名一覧
- 対象リポジトリの絶対パス
- プロジェクト規範の絶対パス
- フィードバック本文に固有の処理順、公開、確認又は検証指示

pickerは各フィードバック本文、対象実装及び既存計画の先行成果依存を調査する。
ファイル名を識別子として扱い、レーン内の実装依存順を技術判断する。
出力は対象ファイル名ごとの処理区分、採否と理由、レーン、レーン内の実装依存順、確認・保留事項に限定する。

## 処理区分

pickerは次の区分を重複なく判定する。

- 新しい実装変更
- 既存計画の実装
- 外部操作だけ
- 既存commit又は既存実装で充足済み
- 全要求不採用
- ユーザー又は外部待ちの保留

新しい実装変更だけを計画起草レーンへ送る。既存計画の実装は計画ファイルの絶対パスを保ったまま実装レーンへ渡す。
外部操作だけの項目、既存commitと既存実装で充足済みの項目、全要求不採用の項目及び保留項目に、計画ファイル、計画レビュー、実装レビュー又は専用worktreeを作成しない。

レーンは計画ファイル単位で割り当て、同じレーンの項目を実装依存順で出力する。
ファイル名の昇順へ並べ替えず、保存済みの`depends_on`を実装順序の根拠に使わない。

## 由来と確認境界

`source`の原値を改変せず、エージェント由来と人間由来の境界を判定する。`source`は認可の証明には使わない。

`source`が`session-review`、`alert-monitor`又は`agent`の場合はエージェント由来とする。ただし、`source: session-review`の通常本文と末尾のexact H2 `## ユーザーコメント`配下から導出した要求は分け、後者を人間由来とする。
`human`、`plan`、その他の値及び`source`欠落は人間由来として扱う。

全要求不採用と確定できるエージェント由来項目は、メインが`atk mq reject <filename>`を実行し、保存結果を照合する。
人間由来項目の不採用、公開契約変更及びユーザー選好はpickerが`needs_escalation`で返し、メインが確認する。
pickerはキューを変更しない。

## TBDと同一セッションの再開

回答が得られない確認事項と外部待ちだけを、`agent-toolkit:add-feedback`の通常契約に従って1件のTBDへ保存し、依存を追加して保留する。
技術的失敗専用TBD、共通失敗集約及びplanner失敗TBDを作成しない。

同一セッション中に回答を受領した場合は、メインが回答をTBDへ保存し、TBDを先に終端して元項目の依存解除を確認する。
routeとtaskが有効なら同じpicker threadを再開し、その他は一般的な継続契約に従う。別セッションまで機械的に待たない。

## 固有指示の引継ぎ

フィードバック本文に固有の処理順、公開、確認と検証指示がある場合は、デフォルト手順より優先する。
その指示をレーン又は③の終端工程へ渡し、pickerの出力に対象ファイル、先行工程及び適用時機を記録する。
`adopt`をPR/MRのマージ後、release後、配布後のいずれかへ明示的に延期する指示は、対象フィードバック、先行する終端工程、`adopt`時機を一組の固有順序として記録する。

## 出力

pickerは次の内容をファイル名ごとに返す。同じレーンの項目は実装依存順で連続して並べる。

```text
status: completed | needs_escalation
decisions:
- feedback: <フィードバックファイル名>
  category: <処理区分>
  decision: <採用、部分採用、不採用又は保留>
  reason: <採否理由>
  lane: <レーン識別子又は「なし」>
  depends_on: <保存済み依存又は「なし」>
  confirmation_or_hold: <確認・保留事項又は「なし」>
  terminal_order: <固有の終端順序又は「既定」>
阻害要因:
- <needs_escalationの場合の確認事項。完了時は「なし」>
```

メインは出力のファイル名、区分、依存、確認境界及び固有順序を検収してから②へ進む。
`needs_escalation`の場合は、pickerの結果を変更せず、確認又はTBDの回答を受領して一般的な同一担当継続契約へ渡す。
