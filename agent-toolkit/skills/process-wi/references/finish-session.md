# push、CIおよび終了

公開工程は選定工程で固定した集合の全レーンが完了し、選定工程で自動コードレビュー監査を起動した場合はその返却の受領と処置の確定も終えた時点で開始する。
通常レーンはffマージ、`adopt`および後始末まで、固有指示で`adopt`を延期したレーンと`upstream_submission`が`混在`のレーンはffマージと実装資源回収まで完了した状態を開始条件とする。
`混在`のレーンは元項目を依存付きで`inbox`へ戻した状態とする。
ready一覧とactive一覧は公開工程の開始時点の内容のまま扱い、ここで処理するのは先行レーンが渡した終端工程だけとする。

## 公開対象が無い処理回の短絡

公開工程の開始時に、公開対象と外部操作が1つも無いことを確認する。pickerの`decisions`では、`lane`が`なし`、`upstream_submission`が`なし`以外、または`terminal_order`が`既定`以外の項目だけを外部操作として数える。省略された行はpickerが定める既定値で解釈する。各レーンの`merged_head`は処理開始時のベースbranch HEADから進んだ場合だけ公開対象として数える。短縮OIDの文字列を比較せず、両方を対象リポジトリのGitで個別にcommitへ解決して同一性を判定する。このセッションで回答を受け取ったUWI、選定工程で記録した固有の終端工程およびレーン工程から受け取った延期`adopt`の対象も確認する。

いずれもが無い場合は、メインが`agent-toolkit:commit`の`references/push-and-ci.md`「公開状態の4項目」を対象リポジトリの主作業ツリーから読み取り専用で取得する。4項目が全て成立する場合は終端担当を起動せず、「セッション終了」節へ進む。

いずれかがある場合と、4つの観測項目に成立しないものがある場合は、終端担当への委譲を通常どおり実施する。
短絡時に全成立を確認した4項目は、後段の「セッション終了」節へ検収済みの公開状態として引き継ぐ。

## セッション終了

対象リポジトリの規範が、対応する管理先への計上または終端と同じ工程で固有の追跡先への記載を求める場合は、その規範が定める対象と記載先を確認し、対応する記載を完了してからセッションを終端する。

終端担当の入力がそろい、対象リポジトリの主作業ツリーへ書き込む主体が解放された時点で終端担当を起動する。外部APIへcommitを渡す終端処理では、`agent-toolkit:commit`の`references/publish.md`「pushと公開状態」の完全OID解決契約を適用する。branch名または短縮OIDを公開契約として受理する操作へは拡張しない。対象リポジトリへ書き込まず、かつ終端担当の入力を生成しない工程の完了は待たず、その工程を起動後に実施する。この条件を満たすキュー投入に加え、公開結果に依存しない既知の警告の読取調査と管理対象一時領域でのAWI原稿準備は、終端担当の公開・CI待機と並行して進める。メインは起動時に調査対象、既存の証拠、反映先候補を独立した担当へ渡し、その担当は主作業ツリーとキュー管理リポジトリへ書き込まない。準備した証拠と原稿は公開後に`agent-toolkit:session-review`へ渡し、正式な候補選別の結果と現行状態に照らして採否を確定する。公開結果に依存する問題は結果確定後に調べる。キュー投入は`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`に従い、終端担当の起動と同じ工程で1件の投入担当へ委譲する。投入担当の完了と独立して終端担当を起動する。投入担当の書込先はキュー管理リポジトリとする。終端担当の観測によって初めて内容が確定する項目だけを、終端担当の返却後に同じ投入担当へ追送する。

終端担当の起動前に、長時間の公開・デプロイ・CI待機と追加の公開工程について、各工程の入力commit、成果物、配備先、排他資源および先行工程の成功結果への依存を進捗記録へ書く。終端担当への指示には待機対象と並行開始できる工程を区別して示し、後者を終端担当の実行対象から外す。これらが独立する追加工程は別の実行主体へ渡し、長時間工程の終端待ちと並行して開始する。例えば`deploy_azure_vm`の待機中に別の成果物と配備先へ緊急デプロイする工程は並行できる。同じDB migrationの成功を必要とするデプロイは、先行工程の成功を確認してから開始する。

専用worktreeとレーン専用branchの回収は前項の対象から外し、終端担当の起動前に完了する。`git worktree remove`と`git branch -D`は対象リポジトリのGit共通領域を書き換え、`${CLAUDE_PLUGIN_ROOT}/share/session-termination.parent.md`「起動前の前提」が定める単一の書込主体と競合するためである。

メインはレーン数を問わず、各レーンの記録を対象リポジトリの版数規範の判定基準で比較し、未公開の統合変更へ適用する最上位の`bump種別`を確定する。公開工程のうち、版数更新、生成物同期、全体検証の要否判定、push、CI確認、検証失敗時の修正（終端担当が起動するCI修正担当が主作業ツリーで行う）、終端担当自身の実行対象とした固有の終端工程および延期`adopt`を1件の終端担当へ委譲する。起動、渡す入力、受領と検収は`${CLAUDE_PLUGIN_ROOT}/share/session-termination.parent.md`が定める。同書を全文読んでから起動する。終端担当は`agent-toolkit:commit`の`references/publish.md`に従い、対象リポジトリのタスクランナーが定める全体検証とCIの同値性から全体検証の要否を決める。終端担当の稼働中に対象リポジトリの主作業ツリーへ書き込む主体は、終端担当と終端担当が起動したCI修正担当に限り、同時に書き込む主体は常に1つとする。メインの作業は読取に限る。

completion-reportが報告する前に、メインは公開状態の4項目（`agent-toolkit:commit`の`references/push-and-ci.md`）が検収済みかを確認する。
短絡時の検収か`${CLAUDE_PLUGIN_ROOT}/share/session-termination.parent.md`「受領と検収」のいずれかで得た4項目は、主作業ツリーや対象refを変える操作、外部更新が間に観測されなければ、そのまま用いる。
状態が変わった場合と4項目が未検収の場合だけ、現在のGit状態から取得し直す。終端担当が返した`base_branch_state`だけでは検収済みと扱わない。
終端担当の返却後と`agent-toolkit:completion-report`の振り返り後に、主作業ツリーのHEAD、追跡ref、最新HEADのCIと作業ツリーの状態を確認する。前回pushのOIDからベースbranchへ新しいcommitが統合された場合は、全レーンの終端と書込主体の解放を確かめ、追加差分のbump種別、固有終端工程および延期`adopt`だけを入力にして同じ終端手順を再実行する。主作業ツリーで直接作成した是正commitも追加差分に含める。再実行の返却を検収し、最新HEADのpushとCI成功を確かめる。新しいcommitが無い場合は再起動せず、既存のUWIへの報告処理へ進む。公開状態の不成立が新しいcommit以外に起因する場合は、`agent-toolkit:wi-standards`をSkill機能で起動してUWIを登録し、観測結果を報告へ含める。
公開工程の完了後に`agent-toolkit:completion-report`を起動する。完了報告と振り返りを1件の事後承認型UWIへ保存し、`agent-toolkit:wi-standards`「投入と取得」手順9の検収が成立してからセッションを終了する。振り返りが失敗した場合も未完了部分を同じUWIへ明示し、重複するUWIを投入しない。手順と報告内容は同スキルに従う。

公開工程の後にactive一覧へ現れた追加分は、次回セッションで扱う。
