# レーン資源と後段レーンの先行調査

process-wiのメインエージェントが、レーンの専用worktree・branch・所有登録を作成、再利用、回収する手順と、後段レーンのworktreeを作成する前に始める読み取り専用の先行調査を定める。
レーンの処理順、担当の起動、統合は`run-lanes.md`が定め、本書はその「レーンと資源」から読む。

## レーン資源の作成・再利用・回収

開始時や回収時に過去のエージェントによる残存資源・誤変更を認めた場合は、メインが`agent-toolkit/share/rules/common/02-agent-operations.md`「プロセス終了の安全規定」で登録と実体を調べる。
登録済み資源の保持理由を解消した後は、元の所有sessionを指定した`atk lane delete --session-id <所有session>`で安全判定をやり直す。
CLIが自動回収しない登録外の一時worktree、回復処理で保持されたbranch、誤変更は、由来・現在の利用・必要な成果・認可を確認して既存のGit操作等で個別に処置する。
現在の担当への引き継ぎと成果保全を優先し、未統合・dirty・稼働中・登録なしという表示は調査の起点として扱う。

レーンごとの専用branch、専用worktree、および所有権の登録は以下のコマンドで実行する。
専用worktreeは、対象リポジトリのメイン作業ツリー配下の`.claude/worktrees/process-wi-<レーン識別子>`に作成される。
`process-wi`は対象リポジトリごとに1つだけ起動される前提であり、配置先パスはリポジトリとレーン識別子のみによって一意に定まるため、別セッションや`process-loop`のworktreeから呼び出した場合でも同一のパスとなる。

```text
atk lane create --repo <対象リポジトリの絶対パス> --base-branch <統合先branch> --lane <レーン識別子> --selection-file <選定YAMLの絶対パス>
```

対象リポジトリに固有の作成・環境準備・撤去手順が定められている場合は、create、prepare、deleteの各argv配列を含むJSONファイルを`--commands-file <絶対パス>`へ渡す。
各argvに含まれる`{repo}`、`{worktree}`、`{branch}`、`{lane}`は、シェルを介さずに作成側によって直接展開される。
`{worktree}`には規定の固定作成先が渡される。
前提ファイルのコピー、`mise trust`、必要な依存関係の同期処理はprepareに含める。
固有手順によってdetached HEADとなった場合、作成側がそれを専用branchへ接続する。
`--worktree <絶対パス>`は、固定作成先とは異なる場所が必要な場合にのみ指定し、その場合のパスは固定配置とならない。

対象リポジトリのClaude Code設定に`WorktreeCreate`が定義されている場合は、対象cwd、環境変数、公式イベント入力を与えて該当hookを実行し、返却されたパスを同一の所有登録へ保存する。
作成hookを利用する場合は、worktree作成処理をそのhookのみに委ねる。
hookが失敗した場合は、診断情報と作成途中のリソースを保持したまま同一操作による回復を試み、通常のGitコマンドによる作成へ安易に切り替えることは避ける。
`WorktreeRemove`が設定されている場合は、終了時のリソース回収時に同一の設定と返却先パスを使用する。
前提ファイルのコピーはhookまたはprepareが担当する。

所有セッション、Git共通ディレクトリ、専用branch、作成先パス、回収対象、選定原本、固有手順、ならびに実行記録は、`record_path`に示される登録ファイルへ保存される。
リソース情報を手動で再登録することは避ける。
メインエージェントは、終了コード0、`ready`の状態、prepareの標準出力・標準エラー出力の内容を確認し、警告の有無と環境準備が正しく成立したことを確認した上で担当エージェントを起動する。
そして、環境構築の結果を`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`環境構築`へ引き渡す。
準備に失敗したリソースについては、登録情報と途中成果を保持したまま入力を修正し、同一のcreate操作で再開する。

別の名前空間へworktreeを引き渡す実装レーンでは、利用するすべての主体から同一の絶対パスへアクセスできることを読み取り専用で確認した上で担当を起動する。
アクセスが確認できない場合は担当を起動しない。
作成先は現行の`atk lane create`の仕様に従う。

統合済みのリソースもセッション終了まで破棄せずに保持し、同一レーンへの追加作業が発生した場合は、前回のcreate操作の返却情報から専用worktreeとbranchを再利用する。
同じWIを再開する場合も元のレーンを維持し、選定原本を未統合へ戻してから同じcreateを呼ぶ。
createは前回の統合完了を確認できるcleanな専用worktreeだけを、現在の統合先先端へfast-forwardする。
未保存差分、稼働中の別writer、履歴の分岐がある場合は成果を保持して失敗するため、診断から所有・差分・基点を確かめて回復する。
同じ入力HEADの再開でも、再検証と選定の再統合を終えてから統合済みとする。
登録情報と回収結果は専用リソースの外部に保持される。
前回のセッションが強制終了した場合などに残存した登録情報は、`process-wi`開始時に`atk lane delete --list`で確認し、担当エージェントや関連プロセスの終了を確認した上で、同一所有セッションに対するdelete操作によって再判定する。
再開に利用する場合は、登録ファイルの`record_path`をcreateの`--reuse-record`へ渡して新たな所有セッションへと移管する。
再利用すべきworktreeが存在しない場合は移管せず、元の所有セッションに対するdelete操作で登録を回収した後に再作成する。
旧配置（個別のmanaged-temp配下）の登録であっても、同一の作成先を維持したまま移管できる。
固定の作成先パスが別セッションの登録によって保持されている場合、createは回収条件を満たすリソースのみを回収し、同一パス上に再作成する。
未統合のリソース、変更が残っている（dirtyな）リソース、稼働中のリソース、所有権の登録がない実体については、変更を加えることなく処理を失敗させ、その理由とともに`--reuse-record`またはdeleteによる回復手順を返す。
createは、渡された選定原本からレーンに属するWI集合と統合状態を所有登録へコピーし、選定原本が一時領域から消失した後であっても、保持された値に基づいて統合と回収を判定する。
選定情報を含まない旧形式の登録は、`atk lane recover --session-id <所有session>`を実行することで、元のbranchを保持したまま作業ツリーのみを解放する。
回復処理を終えた登録は固定作成先の所有・回収判定から除外され、残存したbranchとHEADは`atk lane delete --list`の出力本文から確認できる。
リソース回収時は、メインリポジトリから実体パス、Git登録とbranchの存在を照会し、すべて存在しないと確定した登録のみを、警告と最終記録HEADを残して回収する。
作業ツリーのパスが存在しない場合はdelete手順を実行せず、Git登録のみが残存している場合は登録を強制解除する。
branchが残っている場合は統合済みかどうかの判定を継続する。
CLIはメイン作業ツリーや登録のない実体を自動回収しない。
メインは本節冒頭の共通判断で、残存資源と誤変更を個別に調べて処置する。

各レーンの担当エージェントを初回起動した直後に、`atk agents list --include-terminated`を実行し、起動結果の`session_id`に一致する項目の`created_at`をタイムゾーン付きの`レーン開始時刻`としてレーンのリソース記録へ保存する。
`started_at`はターンの開始時刻を表すため、初回起動の起点には`created_at`を使う。
同一レーンを再起動したり担当を交代したりした場合でもこの値は変更せず、統合指示を送信する際に`exec.parent.md`の同名入力項目として引き渡す。
レーン担当はこの値を`atk lane integrate`のmanifestに含まれる`lane_started_at`へ渡し、CLI側でも最初の値を所有登録へ保持してレーン稼働秒数を算出する起点として利用する。

## 後段レーンの先行調査

同一レーンの後続も`lane-planning-drafting.md`「計画の起草」で準備を早め、委譲は総費用で選ぶ。

メインは、後段レーンのworktreeを作成する前に、先行成果を要しない読み取り専用調査を既存の委譲手段で開始してよい。
対象は要求・規範の確認、実装・テスト・参照先の所在、先行成果に依存しない設計材料、正式化前の計画下書きとする。
書込競合だけで後段となる場合と、調査や判断自体が先行成果を要する場合を区別し、後者の未確定部分は成果の到着まで保留する。
共有検証や直列統合の処理能力を踏まえ、独立した準備の先行と準備・検証の集約を比較し、先行変更後に前提と所要見込みを更新する。

調査担当は取得したリポジトリの版、対象パス、確認した事実と仮定、残る問いを自身のmanaged-tempへ保存する。
先行調査では、正式計画の作成、WI状態の変更、レーン資源の登録、および対象worktreeへの書き込みを行わない。
新しいCLI、準備専用レーン、キュー状態は設けず、レーン数上限と書込所有を維持する。

開始可能な通常レーンを先行調査の準備や終了待ちで遅らせない。
メインは調査担当の終了を既存の委譲契約で観測し、結果の絶対パスを`先行調査記録`としてレーン担当へ渡す。
結果が未完了・失敗でも、後段の通常の調査・計画を開始できる。

後段worktreeは先行調査の有無によらず、`run-lanes-launch.md`「レーンと資源」の条件で作成する。
レーン担当は調査で取得した版とworktreeの現行版との差分を確認し、影響する調査だけを更新する。
計画下書きはそのまま確定せず、`lane-planning.md`の正式計画の起草・検査を経て実装する。
