# CI失敗の修正系列と修正担当

本書は、修正commitが必要と確定したCI失敗を、誰がどの記録で修正し、どの条件でレビューして再pushするかを定める。
CI失敗の取得、分類、原因分析は`agent-toolkit:commit/references/ci-failure-handling.md`が定め、push先・run監視・証拠の保存と後始末は`agent-toolkit:commit/references/push-and-ci.md`が定める。

## 修正commitが必要なCI失敗を修正するエージェント

**1.** 修正の書込所有権を守るため、修正commitが必要と確定したCI失敗は本節の担当へ渡す（元の計画の実行工程へ再投入しない）。

本節を適用するエージェントが対象作業ツリーの書き込み所有権を保持しており、そのツリーに書き込み中の稼働エージェントが存在しない場合は、自ら修正する。
それ以外の場合は、`CI修正担当`を1件起動して修正を委譲する（起動手順と入力形式は`agent-toolkit:/share/exec.parent.md`に従う）。

`CI記録`は、原因分析結果、修正認可根拠、対象の検証結果、変更目的、対象、公開契約、および入力計画の7項目で構成する。

- 修正認可根拠: 計画ファイルに記録された元の要求または確認回答の該当箇所、原因となった変更を認可したユーザー指示の原文、あるいは既存の公開契約の該当箇所を記載する。
  根拠を特定できない場合は修正担当を起動せず、ユーザーへ確認する
- 原因特定の目的で診断コードを追加する場合は、「原因分析結果」において競合する仮説ごとに検証すべき観測内容を対応付け、「公開契約」において採取する対象と属性を対応付ける。
  全件の列挙や走査は仮説の判別に不可欠な場合にのみ限定し、データが大きい場合は一時領域への保存と範囲読み取りを活用する（完全性を損なうような容量上限を新設することは避ける）。
  元の失敗と終了コードは保持し、情報採取自体の失敗は別途記録する
- レビュー基準には、原因コミット自身に対応する計画が存在する場合はその計画を採用し、存在しない場合はCI記録を採用する（処理対象WIに含まれる無関係な別の計画を使用しない）
- 計画を持たないCI修正コミットが再push後に別の失敗の原因となった場合は、直前のCI記録を引き継いで7項目を更新する。
  CI対応レビュー指摘管理表が存在する場合は、そのパスおよび`修正系列の開始時のHEAD`も併せて引き継ぐ

### 公開工程の公開担当が扱うCI修正

**2.** 公開工程に該当する場合、`agent-toolkit:process-wi`のCI修正は公開工程の内部で完結させ、新たな計画ファイル（バグ）は作成しない。

 公開担当は7項目のCI記録を保持し、メインの作業ツリーを対象とする`CI修正担当`へ修正させる（本節冒頭で定めた自ら修正する原則に対する例外であり、具体的な手順は`agent-toolkit:/share/session-termination.subagent.md`に従う。所在参照）。
 全体検証の失敗も同一の修正系列としてカウントし、`exec-review`の起動条件および起動しない修正の前提条件は後述の「修正系列」と同一とする。
 修正コミットを作成するたびにバージョン番号とマニフェストを再判定したうえで再pushを行い、CI確認へ戻る。
再push後に新たな失敗が発生した場合は、新しい原因コミットについて対応する計画ファイルの有無を再判定する。

### 修正系列

最初のCI失敗（公開工程においては全体検証の失敗を含む）から、CIが成功するか工程が終了するまでの一連の過程を「修正系列」と呼ぶ。
修正回数、CI記録、レビュー指摘管理表、および`修正系列の開始時のHEAD`はこの単位で引き継ぎ、原因コミットが変わった場合でも回数のカウントを継続する。
修正回数は是正した失敗に対応する修正の件数として数え、原因コミットへ取り込んだ修正（`agent-toolkit:commit`の`references/push-and-ci.md`「pushと監視」の「原因commitへ取り込む区分」）も1回として計算する。
コミットを取り込んだ場合、`exec-review`へ渡す`原因commitOID`には履歴書き換え後に解決可能な値を指定し、書き換え前後のOIDの対応関係と`git range-diff`の結果をCI記録へ記録する。

**3.** 修正の基準を揃えるため、`入力計画`には、原因コミットに対応する計画ファイルのパスを指定する。

- 保存済みの計画ファイルは、起動側エージェントが起動前に`atk plans checkout <private-notes/plans/からの相対パス>`を実行して`~/.claude/plans`へ取得し、そのパスを渡す。
  保存済みパスを直接渡すと、進捗ログや指摘管理表への記録が拒否される。
  同一の修正系列における実行レビュー（`レビュー基準: 計画`）へも同一のパスを渡す
- 未保存の計画ファイルの場合は、`~/.claude/plans`のパスをそのまま渡し、対応する計画が存在しない場合は`なし`とする

**4.** 修正者は原因の修正、全項目の検証、差分検収、ステージング、commitを完了する。
修正前の計画は「選択の流れ」に従い、公開工程外で自ら直す場合は`agent-toolkit:commit/references/ci-failure-handling.md`「選択の流れ」手順6の計画を使う。

**5.** 手元の実行環境では失敗した条件の成否を観測できず、認可済みの作業ブランチで対象ジョブと直接影響範囲を実行できる場合は、修正コミットを早期にpushして先行CIで検証する。

 対象リポジトリ・ブランチへのpush認可と書込担当の終了を確認してから、`push-and-ci.md`「push前」「pushと監視」の通常操作を用いる。
 作業refでの先行CIは再レビューの合格を待たずに開始でき、必要なレビューと他の検証を並行して進める。
 修正合格と正式公開は、先行CIの結果と必要なレビューの合格を検収してから確定する。
 認可が不足する場合は追加認可を求める。
 先行CIの証拠にはSHA、ref、baseline、実行されたジョブと条件を残し、失敗したジョブが同じ条件で実行され、期待結果になったことを確認する。
 対象ジョブが起動しない場合は検証済みにせず、再現環境の確保または認可の確認へ進む。
 先行CIの失敗は修正合格の根拠から外れる。
 手元で同条件を再現できる修正はローカル検証を優先する。
 先行CIを使った場合も、正式公開refで要求されるcheck集合の検収を保持する。
 差分更新後は影響する検証とレビューを更新し、既存証拠の適用範囲を区別する。

**6.** 同じ修正系列の3回目以降の修正と、回数にかかわらず公開契約や設計に及ぶ修正では、単一の`exec-review`を合格するまで反復して実施する（公開工程の修正系列にも同様に適用する）。
それ以外の場合は`exec-review`を起動せず、再pushを行ってCI確認へ戻る。
2回目までの修正を修正者自身の確認で完了させ、3回目以降でレビューを起動するのは、3回以上の修正が必要になる事態が直前の修正における根本原因の把握が不十分であることを示すためである。
CI対応レビュー指摘管理表の作成、更新、および保存は、`exec-review`を起動する場合にのみ行う。

 `exec-review`を起動しない修正では、失敗ログの該当箇所を要約せずに精読し、失敗した検証処理が参照している実装コードや期待値の現物と比較して直接的原因を特定する。
修正後は対象の検証処理を同一条件で再実行して期待通りの終了状態を確認し、影響を受ける可能性のある他のチェック処理も再実行する。
 外部サービスの障害など、コード修正コミットを必要としない失敗については実装担当を起動しない。

 計画を基準とする後続の実行レビューでは、計画の進捗ログに記録された読み取り可能な受理済み実行レビュー返却ファイルの絶対パスを、任意入力`受理済みの完成条件証拠`として渡す（存在しない場合は`なし`とする）。
利用可能な条件は、`../../../share/exec-review-recording-evidence.md`「受理済み判定への参照」に従う。
受領確認を終えた新たな返却ファイルの所在も同一の進捗ログへ記録し、修正系列における後続の起動から参照できるようにする。

**7.** 修正系列を完了とするCIの成功判定は、失敗したジョブが判定対象に含まれ、期待される終了状態（許容された失敗を含む）で正常終了したパイプライン（GitHub Actionsではrun）に限定される。
push先のリモートで対象ジョブが実行されない場合（保護ブランチ限定、スケジュール実行、特定パスの変更条件など）は、ジョブの実行環境を含めたローカル再現（「分類判定の補助」）によって成否を確認する。
ローカル再現も行えない場合は、未確認のジョブ、試みた再現手順、および残存する実行条件の差異をエスカレーションとして報告する。

**8.** 修正系列の完了時に、起動側エージェントが`atk plans commit <private-notes/plans/からの相対パス>`を実行して再保存し、成功メッセージと警告がないことを確認する。
CI記録を基準とする`ci-<修正系列の開始時のHEAD>.exec-review.tsv`も同一のタイミングで`atk plans commit ci-<修正系列の開始時のHEAD>.exec-review.tsv`を実行して保存する。
修正系列が継続している間（再pushの結果待ちを含む）は表を`~/.claude/plans`に残し、先行して保存した場合は`atk plans checkout ci/ci-<修正系列の開始時のHEAD>.exec-review.tsv`で復元してから作業を継続する。
