# レーン計画の起草と再開

初回選定を受け取ったレーン担当は、まず選定結果の各項目に記載された再開位置を確認する。そして、`再開位置`が指定されていないAWI群に対して`agent-toolkit:plan-mode`「計画ファイルの作成要否」を適用する。1件でも作成条件に該当する場合は、それらを1つの計画にまとめて起草する（計画を分割する条件は「計画の起草」の手順4を参照）。すでに`再開位置`を持つAWIは新規計画には含めず、「再開」の手順に従って作業を継続する。

対象リポジトリのバージョン規約により更新が必要な場合は、レーン数にかかわらずバージョン更新の種別（bump種別）とその根拠を計画に記録する。同一実行内の変更がより上位の更新区分に該当する場合は、その上位区分を選択する。実際のバージョン更新作業は公開工程の公開担当が行う。

入力情報は、pick-wi-checkが検証・保存した完成版の選定YAMLとレーン識別子から取得する（メインエージェントの生成入力、候補JSONL、定型欄は委譲プロンプトへ転記されない）。選定時の分類と要求の採否は独立した判断として扱う。鮮度、省略値、担当モデルに不一致がある場合は、同一担当の引き継ぎ記録を通じてメインエージェントへ報告する。準備済みリソースの所有権登録は`atk lane create`が保持するため、レーン担当はカレントディレクトリのworktreeに対してのみ書き込みを行う。統合完了後もリソースは回収せず、同一スレッドで追加指示を受け付ける。

## 作成要否と計画なしの準備

すべてのAWIが計画作成を省略できる条件に該当する場合は、`atk wi show`で要求と完成条件を確認する。その上で、由来・採否、AWI集合、最も近い既存実装、直接影響範囲、変更範囲の検証コマンド、および統合区分（採用した要求を実装する場合は`マージあり`、不要な場合は`マージなし`）を引き継ぎ記録先へ記録する。ユーザーからの依頼またはWIで明示された禁止条件が存在する場合は、禁止条件と採用する手段も同様に記録し、以下の形式のみを返してメインエージェントからの`実装開始`または`実装なし`の指示を待つ。

```text
計画なし準備完了
AWI: <AWIファイル名のASCIIカンマ区切り>
統合区分: <マージあり|マージなし>
```

禁止条件が存在しない場合は、「計画検査完了の通知」を`計画ファイル: なし`として送信し、応答を待たずに`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`「実装」へ進む（`マージなし`の場合は実装せず、メインエージェントからの統合指示を待つ）。調査の過程で設計判断、バグ対応、または人間由来の要求の縮小が必要と判明した場合は、「計画の起草」へ切り替える。

## 計画の起草

計画中に同じ要求の重複が判明した場合は、`selection-procedure.md`「処理対象の決定」に従って元担当・計画・成果へ接続し、残差の採否と各AWIの処置を記録する。同一ファイルへの書込競合は要求の重複とは別に扱う。

1. `agent-toolkit:plan-mode`を起動して同スキルの読込表の資料を読み、AWI、プロジェクト規範、対象実装、既存テスト、生成・配布手段、類似実装を調査する。
   - 対象実装を読む前に、要求と公開契約から比較対象とする最も近い既存実装を選ぶ。境界の候補は、入力値、時間経過、操作順序、保持状態、反復、権限や環境の差異などの軸から選定する。
   - 調査後は、採用案の前提を客観的に評価する観点から、変更箇所が責務を負う必要性、既存機構への統合、上流ツールや共有設定への移管、機構の削除や簡素化を比較検討して計画へ反映する。AWI本文の`## 調査結果と判断根拠`（旧形式は`agent-toolkit:wi-standards`の`references/awi-body.md`冒頭に従う）に結論が示されている観点については、記述との明白な食い違いが観測されない限り再度の比較検討は行わない。「設計品質の劣化確認」（`agent-basics:writing-standards/references/design-heuristics.md`）は常に実施する。評価条件は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「恒久化・リファクタリング」に準拠する。不具合対策においては、`agent-toolkit:review-standards`の`references/reviewer.md`「初回レビュー」の「前提を疑う観点」に従い、観測された害の解消策と呼び出し側の修正案も併せて比較する。
   - `選定`の各項目における`鮮度`を計画の`## 変更履歴`へ記録する。`鮮度`が`notice`であることのみを理由として作業を中断することは避け、現行内容との不一致、既存実装による充足済み、巻き戻しの危険のいずれかが確認された項目に限定して関連履歴を調査し、確認条件、調査した履歴、および採否への影響を同一記録に残す。
   - レーン担当は、レーン数にかかわらず自身のレーン内の作業分担を`agent-toolkit:delegation`の`references/routing.md`「要否判定」「委譲単位の確定」に基づいて検討する。自身が直接実施する単位と委譲先を起動して委ねる単位を、その理由とともに`## 実施内容`（計画なしの場合は引き継ぎ記録）へ記録する。計画の起草はレーン担当自身が行う。内部担当へ計画起草や設計判断を委ねる運用は、明らかに独立した複数タスクを扱う場合に限る。分担の記載には、内容が確定した書き込み作業の単位ごとに、委譲先の工程または自ら行う理由を明記する（工程の区分は同スキルの`references/runtime-routing.md`「工程別モデル設定」の工程分担の段落を参照）。
   - 多数の対象へ同一作業を適用する要求では、`plan-file-standards.md`「実施内容」の実施方式も比較検討し、採用した方式と理由を記録する。
   - 独立した複製環境での対照実験など時間を要する比較調査は、入力と版を固定でき独立複製へ出力可能であれば、`agent-toolkit:writing-standards`の`references/investigation.md`「実行結果の検証」の準備確認を終えた後に、通常の修正作業と並行して開始する。結果の到着を待つ工程のみを直列化する。作業順序は、先行成果、書き込み先、観測リソースの競合状況を考慮して決定し、`## 実施内容`へ明記する。
   - 検証コマンドを確定する前に`agent-toolkit:check-execution`を起動し、`references/verification-scope.md`の類型に基づいて変更範囲の検証対象を確定した上で、`## 検証`の`変更範囲の検証`へ追加する。追加しない対象がある場合は、その理由を`## 要件・外部仕様`の追随範囲へ記載する。
   - 変更対象を確定する前に全文を確認する文書は、原則として候補ファイルと名指しされた基準文書（計画・WI・エージェント向け文書など）に限定する（努力目標。コンテキスト消費を抑制するため）。候補の絞り込みや横断的な列挙は、探索委譲や検索を用いて結論のみを取得する。他の役割の`<役割名>.subagent.md`や変更対象を含まないスキル本体は、検索によって必要な箇所のみを確認する。
   - 採否を確定する前に、変更対象パスに対応する必須スキル（対応表はプロジェクト規範に記載）を起動し、変更対象の成立条件と禁止条件を定める節を検索で特定して読んだ上で、要求内容と比較する。衝突する要求がある場合は、`## 実施内容`において不採用または手段変更とし、人間由来の要求であれば手順2に従って通知する。編集段階で衝突に気付く事態を防ぎ、後からの判断要請や実装済み差分の取り消しを回避する。
   - `上流投入結果`を受け取った場合は、`結果`が`completed`となっている要求を採用範囲に含めず、`移管`として投入先の`ファイル名`とともに記録する。
2. 人間由来の要求を不採用・部分採用とする判断は、`agent-toolkit/share/rules-subagent.md`「確認事項の即時通知」に従い、計画の確定前にメインエージェントへ通知する。完成条件の変更・除外に関するメインの技術判断は`review-loop-coordination.md`「技術判断で外せる完成条件」に従い、旧条件、新条件または除外範囲、技術的制約、保持する要求と根拠を実施内容の根拠欄に記録する。実装着手後の判断はレビュー指摘管理表へ記録する。
3. 通知した確認事項の回答をすべて受け取って採否へ反映するまでは、回答待ちの間でも進められる調査や下書きの作成にとどめる。
4. `agent-toolkit:plan-mode`の`references/plan-file-standards.md`「初回起草の雛形」に該当案件の値を記入し、同書に従って計画本文を起草してmanaged-temp配下のファイルへ保存する。単一の計画では`plan-check`の行数警告（1200行）を回避できない見込みである場合は、実装着手前に分析単位と依存関係順序に基づいて自己完結した複数の計画へ分割し、すべての計画を同一レーン、専用worktree、書き込み所有者のままで管理する（確定後の計画の事後分割やレーンの再配分は行わない）。バグ調査用計画ファイルを作成する場合（同書「バグ調査」）は、本文を別ファイルへ保存する。各計画は、`atk run-script plan-create -- --main-source <計画本文の絶対パス> --lane <レーン識別子> --work-dir <計画メタ情報の対象リポジトリ>`を実行して`~/.claude/plans`に作成する。バグ調査用計画ファイルが存在する場合は、`--bugs-source <計画ファイル（バグ）の本文の絶対パス>`も併せて渡す。stemには該当処理が生成した値を使用する。
5. 計画全体から、編集・新設・移動の対象となるエージェント向け文書の集合を確定し、すべてのパスをリポジトリ相対パスとして計画本文に明記する。この集合は、書き込み認可の境界（WIの要求）の範囲内で着手時に想定した書き込み先の記録であり、実装中の追加は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`「実装」に従う。確認にあたっては以下のコマンドを単独実行し、集合内のすべてのパスを`--agent-rule-path <リポジトリ相対パス>`で反復指定する。

   ```text
   atk run-script plan-check -- --reject-migration-warnings --selection-file <選定結果の出力先ファイル> --lane <レーン識別子> <計画ファイルの絶対パス>
   ```

   終了コード0および警告が存在しないことを確認する。計画を分割した場合は、すべての計画を位置引数に並べて1回のコマンドで実行する。処理中に追加されたAWIの計画を検証する場合は、同一レーンの先行する凍結済み計画をすべて`--prior-plan <先行計画の絶対パス>`で指定する。不一致となったパスは一覧から除外せず、計画本文を修正した上で同一の集合を用いて再確認する。各オプションの仕様は、`agent-toolkit:plan-mode`の`references/plan-structure-check.md`に準拠する。
6. `## 実施内容`に人間由来の`部分採用`または`不採用`の行が含まれる場合、あるいはユーザーからの依頼やWIで明示された禁止条件が`## 実施内容`に存在する場合は、以下の形式の行のみを返信し、同一スレッドでメインエージェントからの`実装開始`または`実装なし`の指示を待つ。それ以外の場合は、「計画検査完了の通知」へ進む。

```text
計画作成完了
計画ファイル: <絶対パス>
```

分割した計画では、`計画ファイル:`の行を作成順に繰り返して記載する。

## 再開

再開位置が計画ファイルの絶対パスである場合は、`## 概要`、`## 変更履歴`、`## 要件・外部仕様`、`## 進捗ログ`、および同一stemを持つレビュー指摘管理表の応答を確認する。計画本文と管理表の応答に相違がある場合は管理表の応答を現在の確定情報とし、進捗ログの最終行が示す位置から既存の計画を引き継いで再開する。

`再開位置: 計画なし`の場合は、引き継ぎ記録からAWI集合、採否、検証コマンドを取得し、完了済みコミットを`git merge-base <専用branch> <ベースbranch>`および`git log <その結果>..<専用branch>`によって特定する。レビュー指摘管理表も確認した上で、最後に完了した工程の次から作業を再開する。計画の新規作成は行わず、コミット済みの範囲を再実装することも避ける。

選定結果の`再開位置`が`反映後の観測だけが残る`で始まる項目、および進捗ログの最終行が「反映後の観測だけが残る」と示している再開では、既存の実装コミットの再実装は行わず、観測のみを実施する。

1. AWI本文末尾の`## 反映後の観測の再開記録`から、`実装commit`、`残る完成条件`、`観測手段`（起動条件と根拠の所在を含む）、および`計画`の値を確認する。`~/.claude/plans`に該当の計画が存在しない場合は、`atk plans checkout <private-notes/plans/からの相対パス>`によって取得する。起動条件が不足している場合や変化が認められる場合は、`finish-session.md`「延期adoptと反映後の観測」に従って実際の実装や設定から情報を補い、実行可能性を確定させてから認可と操作内容を判断する。
2. 残りの完成条件を、記録された手順に従って新規プロセスから観測し、その結果と報告時点からの差分を進捗ログ（`計画`が`計画なし`の場合は引き継ぎ記録）へ追記する。引き継ぎ記録には、観測のみの再開であること、取得した計画のパス、元の専用worktreeの回収状況も記録する。`計画なし`の項目については、再開記録の`実装commit`を検収済みの実装として引き継ぐ。取得した計画は`atk plans commit`による保存は行わずに`~/.claude/plans`に保持し、保存は`${CLAUDE_PLUGIN_ROOT}/share/lane-integration.subagent.md`「計画最終化」の段階で一度だけ行う。
3. 統合区分を`マージなし`に設定して「計画検査完了の通知」を送信する（計画なしの場合は`計画ファイル: なし`とする）。追加された処理対象WIの工程が残っている場合はそれを継続し、全計画の実装要否が確定した段階でメインエージェントからの統合指示を待つ。
4. 観測の結果が完成条件を満たさなかった場合でも、再実装は行わずに`マージなし`として扱う。満たせなかった完成条件、観測時の操作と結果、観測ログの保存先を進捗ログ（計画なしの場合は引き継ぎ記録）および返却メッセージに記載する。終了区分は`終了しない`に設定し、`agent-toolkit:process-wi`の`references/run-lanes.md`「採否の確定と終了区分」に従う。
5. 完成条件を直接観測できない場合は、不足している反映状態と観測手段を「続行できない理由」として報告する。残存プロセスや環境状態が前提条件を阻害している場合は、それらの生成元、起動元、起動契機を実態（プロセスの親子関係、起動時刻、実行ログ、実装内容など）から調査し、未確定の事項と併せて記載する。OS上の実行ユーザー情報だけではエージェント、常駐プロセス、人間のユーザーを判別できないため、ユーザー名のみを生成元の根拠としない。

## 計画検査完了の通知

再開位置が`なし`であり、いずれの待機条件にも該当しない場合は、以下の形式で`atk agents notify`を用いてメインエージェントへ通知し、応答を待たずに実装作業へ進む。統合区分は計画ごとに判定し、採用した実施内容を持つAWI行が含まれていれば`マージあり`、含まれていなければ`マージなし`とする。計画を分割した場合は、この3行の組を計画ごとに作成順で繰り返し、`AWI:`にはその計画の`関連WI`のみを記載する。すべての組が`マージなし`となった場合は実装せず、メインエージェントからの統合指示を待つ。

```text
計画検査完了
計画ファイル: <絶対パス|なし>
統合区分: <マージあり|マージなし>
AWI: <AWIファイル名のASCIIカンマ区切り>
```
