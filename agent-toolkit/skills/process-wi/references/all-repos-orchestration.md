# 登録リポジトリの中継と担当への受渡し

`atk wi process-loop all-repos`は、あらかじめ登録されたリポジトリ群の情報を取得し、各対象ディレクトリ（cwd）へ通常の委譲として処理を中継する。
リポジトリ担当エージェントはそのディレクトリの規範を読み込み、渡された候補情報に基づいて通常のprocess-wiを完遂する。
対象の選定、実装、Git操作、事前準備（prepare）、およびプロジェクト固有の判断は、すべて対象cwdを担当するエージェントが受け持つ。
ホームディレクトリ上で動作する常駐プログラムは、担当エージェントの起動、所有権の管理、完遂の判定、続行指示、ならびに返却結果の記録のみを行う。
ユーザーとのやり取りや、メインエージェントが担う各種判断・報告は、担当エージェント自身が直接実施する（詳細は「担当の役割」を参照）。

## 担当の役割

リポジトリ担当エージェントは、対象リポジトリにおけるprocess-wiのメインエージェントとして動作し、自身のセッションが自身および配下の担当エージェントの記録における最上位となる。
agents_serverの通常委譲として起動されるため委譲先向けのメッセージが配送されるが、委譲元は常駐プログラムであるため、返却結果や通知、判断の委任を受け取る相手は不在である。

- メインエージェントおよび最上位セッションに限定された条文を自身に適用する。公開後の`agent-toolkit:completion-report`（作業完了報告、`agent-toolkit:session-review`による振り返り、報告用UWIの作成）、WIの投入、UWIによる確認、`気付いた改善点:`行の振り返りへの取り込みなどを自ら実行する
- メイン向けの規範は自動配送されないため、作業着手時に`${CLAUDE_PLUGIN_ROOT}/share/rules-main.md`と、実行ホストに応じた`rules-main.claude-code.md`または`rules-main.codex.md`を全文読み込んで適用する
- 委譲元への返却・通知・判断委任を定める条文（`share/rules-subagent.md`の確認事項の即時通知や標識行の引き継ぎ、`agent-toolkit/rules/01-agent.md`「完遂と先送り」に定められた委譲先からの返却手順など）は適用の対象外とする。ユーザーの判断が必要な値はUWIを通じて確認し、担当範囲外の既存不良や他リポジトリへの作業依頼は新たにWIとして登録し、改善点は振り返りで扱う
- 配下の担当（レーン担当、実行レビュー担当、終端担当、WI投入担当など）に対しては、通常の委譲元として起動、結果受領、検収をする
- 常駐プログラムへの最終返却は記録用であり、対象リポジトリ、担当セッション、公開コミット、CI結果、未完了工程、および再開先を記載する。処理を続行できない場合は`続行できない理由:`の行で明記する（常駐プログラムはこの行の有無によって所有権を解放する）
- `agent-toolkit:completion-report`の報告後に実行する終端コマンド`atk agents-exit-session`は呼び出さず、最終返却を出力してターンを終える。このコマンドは祖先の対話CLI本体へ終了を要求するため、常駐プログラムが返却結果を受け取る前に対当セッションが終了する恐れがある

## 登録集合と開始

処理対象は、`atk config`の`process_loop_repositories`に保存されたローカルworktreeの絶対パスのJSON配列で定義する。
通常の作業ディレクトリ（cwd）単一での起動や、登録外リポジトリへのWI投入は、本機能とは独立して利用できる。
配列が空の場合は常駐プログラムが待機状態に入り、JSONの形式不正、パスの解決不能、読み取り不能が発生した場合は、診断メッセージに示された登録先を修正した後に処理を開始する。
同じoriginを持つリポジトリは登録順の先頭にまとめ、Git共通ディレクトリとworktreeを適切に対応付ける。
登録内容を変更した場合は次の取得サイクルから反映され、現在進行中である担当の処理対象WIはそのまま維持される。

一括取得は`atk wi list --configured-repos`で実行できる。
常駐プログラムは同一の登録解決とキューの一括取得を通じて、対象リポジトリごとの候補本文、依存関係、鮮度、回答済みUWI、および着手可否（readiness）を取得する。
担当エージェントを起動する対象は、処理すべきWI候補が存在するか、あるいは監査の開始条件を満たしているリポジトリに限定する。
活動猶予期間の確認や、未回答UWIによる処理開始の抑止判定は、常駐プログラムが起動対象の集合全体に対して一括して行う。
処理開始前のツール更新や自己再起動は全体で1回のみ行い、監査、CI、worktreeの準備状況、失敗や再開の各状態はリポジトリごとに個別に管理する。

## 取得済み候補の受領

常駐プログラムは各対象ディレクトリ（cwd）で通常の`delegate`を起動し、JSON形式の`target_repo`、`worktree`、`common_dir`で対象を指定する。
各パラメーターの意味は次のとおりである。`candidate_file`は起動元が保存した初回取得済み候補JSONの絶対パス、`readiness`は対象ごとの着手可否判定、`lane_limit`は設定されたレーン上限数を表す。
`ownership_record`および`ownership_token`は取得済みの処理所有権、`previous`は前回の成果と再開情報、`worktree_name`は環境隔離の指定を表す。
担当エージェントは、常駐プログラムから渡された値と取得済みの所有権をそのまま利用する。
`lane_session_id`は対象ごとのレーン所有権を示しており、レーンの作成、再開、終了時回収をする各操作の`--session-id`引数へ同じ値を渡す。

担当エージェントは初期一覧を再取得せず、`candidate_file`に保存された原本を初回候補として利用する。
候補の`state`と、`readiness.ready`や`readiness.internal_dependency_waits`などの集合情報から、通常の着手可否を判定する。
候補レコード内の`ready`や`blocked_reason`は同一のreadinessから生成された対象ごとの判定結果であるため、待機理由を判断する際も受け取ったreadinessの診断情報をそのまま活用する。
`pick-wi-check`の`--candidate-file`引数には、受け取った絶対パスをそのまま渡す。モデルが候補本文や鮮度を再出力する工程は省く。
起動元は入力ごとに新たな保存先を確保し、所有権の記録から再開および検収の完了までそのファイルを保持する。担当エージェントの完了を検収して所有権を解放した時点でファイルを回収する。
すでに受け取っている本文、回答、依存関係の情報を活用し、不足している本文や依存先のみを通常のキューCLIで補う。
回答済みUWIの元項目の扱い、状態遷移、選定完了後の状態確認の手順は[selection-procedure.md](selection-procedure.md)に従う。
選定YAMLは対象リポジトリごとに保存し、選定件数の上限はその対象の候補数Nから計算する`floor((N+9)/10)`とする。
複数対象の総件数をNとして代入してはならず、初回情報や追加後の上限の扱いについては[selection-format.md](selection-format.md)に従う。

担当エージェントに隔離指定が与えられている場合は、WorktreeCreate/Removeや準備・撤去の対応を含む[run-lanes.md](run-lanes.md)のリソース操作手順を利用する。
作成hookの返却先と、Git登録、ブランチ、共通ディレクトリ、および所有権の対応関係を確認する。
設定済みhookが失敗した場合は、診断情報と作成途中のリソースを保持したまま、同じhookの再開処理へ引き渡す。
設定済みhookが失敗した際に、通常のGit作成操作へ暗黙のうちに切り替えることは避ける。
hookが用意されていない対象については、固定の配置とプロジェクト固有のprepare処理を用い、処理を繰り返す場合も同じ配置を再利用する。
レーンの数にかかわらず、各レーン担当は単一担当の実行契約に基づいてレビューの調整まで一貫して進める。常駐プログラムはこの調整から外れる。準備、統合、回収には共通の公開操作を用い、統合処理は[run-lanes.md](run-lanes.md)ならびに`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の手順に接続する。
公開工程とCIの検収は[finish-session.md](finish-session.md)へ引き継ぐ。

## 所有、制御と再開

処理の所有権は通常起動とall-reposで共有管理し、同一originのWIと書き込み主体（writer）が常に1つの担当に保たれるようにする。
短時間の排他制御によって所有記録とプロセスの生存を確認し、長時間の処理や回答待ちの期間は、担当セッションと登録記録によって所有権を保持し続ける。
別の所有者が正常終了した場合は候補一覧を取得し直し、異常終了した場合は未統合の成果物を保持したまま既存の再開手順へ渡す。
ある担当エージェントが失敗したり所有権の獲得待ちになったりしている間も、すでに開始されている他の対象の担当エージェントは処理を継続する。

常駐プログラムは担当エージェントの終了後、起動時の候補にinboxやprocessingが残っているか、対象リポジトリにprocessingが残っているか、あるいは`lane_session_id`に未統合レーンが残っているかを確認して完遂を判定する。
未完了のタスクや待機期限によって保留された結果が残っている場合は、同じセッションへ残存するWI名とレーン情報を添えて続行を指示する。
担当エージェントは続行指示を受け取った段階で、残りの工程を再開する。
常駐プログラムは未完了で終了するたびに、対象リポジトリのinboxやprocessingにあるWI名とその状態、および`lane_session_id`の各レーン登録における統合状態とブランチのHEADを記録する。
この記録が直前の終了時記録と2回続けて一致した場合、あるいは返却結果に`続行できない理由:`の行が含まれている場合は、続行を指示せずに所有権を未完了のまま解放し、再開情報を次の処理サイクルへ引き継いで今回の待機を終了する。
出力停止の検知や待機の失敗も常駐プログラム側で処理し、正常に停止を確認できた担当エージェントの所有権のみを解放する。
停止が確認できない担当エージェントの所有権は維持し、以後の処理サイクルや常駐プログラムの再起動後も、担当セッションの生存を確認した上で起動可否を判定する。

常駐プログラムは、完遂、続行不能の返却、進捗なしによる打ち切り、停止確認のいずれかによって所有権を解放するたびに、その担当の`lane_session_id`に紐づくレーンリソースを`atk lane delete`と同等の条件で回収する。
続行指示を出した担当や、停止が確認できず所有権を保持している担当のリソースは回収の対象外とする。
未統合、未コミット、あるいは使用中などの条件に該当するリソースは保持され、次のサイクルで再開する際に同じ`lane_session_id`が担当エージェントへ引き渡される。
リソースを保持した理由と、`atk lane delete --session-id <lane_session_id>`による再回収手順は、常駐側の端末出力およびprocess-loopのログに記録される。

続行不能の返却や進捗なしの打ち切りが発生した後は、その担当の起動時と終了時の双方に存在していた起動入力（候補WI、対応が必要な診断本文と着手可否区分、起動時の未判定Dependabotアラート）を、このホストの無進捗記録へ保存する。
同じ起動入力が維持されている間、常駐プログラムはその対象の担当エージェントを起動せず、見送りの理由と起動を再開する条件となる変化を端末およびprocess-loopのログへ出力する。
起動を再開する契機となる変化には、新たなWIの到着、既存WIの本文・状態・依存関係・冷却期限の変更、着手可否区分の変化、ユーザーコメントやUWI回答の追記、新たな未判定アラートの発生が含まれる。
担当エージェントの稼働中に追加されたWIはこの記録には含めず、次回のサイクルで起動対象として扱う。
`--resume`や`--auto-resume`で明示された対象は、この無進捗記録に関係なく起動する。
このホストでは処理できない候補を担当エージェントが`続行できない理由:`として返した場合でも、同じWIを処理できる別ホストの起動処理は継続する。

`abort`、`status`、`instruct`などの制御コマンドはOSアカウント単位で利用する。
`instruct`は次回のall-repos起動集合へ1回だけ渡され、各担当エージェントは自身のリポジトリに関係する指示のみを適用する。
all-reposの再開対象は、記録されたall-repos担当のセッションIDに限定される。
担当エージェントからの返却結果は、対象ごとの確認済み工程、残存工程、および再開先情報とともに保持し、続行不能の理由と正常完了の結果を明確に区別して受け取る。
