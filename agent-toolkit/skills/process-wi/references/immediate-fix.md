## 開始後に追加されたWIの確認

選定メインは初回取得で、全状態・全種別のWI識別子集合を保存する。
一覧の表示条件とは独立した開始時集合を同じ実行で保持し、再開時も同じ保存集合を使う。

```text
atk wi list --summary-only --state=processable --target-repo <対象リポジトリの絶対パス> --snapshot-output <開始時集合JSONの絶対パス>
```

30分点検ごとと公開工程の開始前に、次のコマンドで開始時集合に無い最新の処理可能WIを取得する。

```text
atk wi list --summary-only --state=processable --target-repo <対象リポジトリの絶対パス> --new-since <開始時集合JSONの絶対パス>
```

未判定の各WIの本文を`atk wi show`で取得し、本書「即時対応」で対処時機を判定する。
識別子は正規化した対象リポジトリとWIファイル名の組とし、現在の集合と開始時集合の差から新着を判定する。
開始時集合の欠落・破損・読取失敗は原本を回復し、現在一覧で基準を作り直さない。
即時対応・今回追加と判定した項目は`selection-procedure-addition.md`「処理対象WIの追加」で同じ実行へ加え、それ以外は次回へ残す。
WI名、判定、根拠を既存の作業記録へ残し、判定済み項目の記録は次の点検でも再利用する。

all-reposの統括は各対象の確認を所有する。
常駐から渡される集合JSONの各対象の`snapshot_file`を開始時集合として使い、担当へ同じパスを引き継ぐ。
処理中のリポジトリ担当へ確認を任せた場合は、その判定記録を受領して再利用し、今回追加とした項目の選定と担当への追送を確認する。
開始時候補と初回配分は保持し、新着WIは追加分として扱う。

## 即時対応の手順

本手順は、メインエージェントや委譲先が発見した既存不良、および処理中にユーザーから届いた是正要求に適用する。
実行レビューで見つかった差分外の不良は、通常`../../../share/exec-review-parent-existing-defects.md`「返却に含まれる既存不良の受領」に従ってAWIへ引き継ぐ。
本書「即時対応」の基準で直接修正が必要と判定した場合に本手順を用いる。
即時対応は最小限の直接修正と正式対応用AWIの登録までにとどめ、独立した既存不良を同一セッション内で正式対応まで完了させる一般原則の例外として扱う。

1. 発生した事象、期待する結果、現在および後続セッションへの影響を確認し、本書「即時対応」に従って直接修正の対象と修正方針を定める。
   安全に修正できる程度まで原因を特定し、本格的な原因分析は正式対応へ委ねる。
2. 「レーンの変更範囲へ加える修正の認可」で担当・基点・時機を決め、メインエージェントまたは書き込み権限を持つ担当者が、必要な範囲に限定して修正し、修正箇所が安全に動作することを確認する。
   修正対象、方針、認可内容、観測結果に加え、残る工程と次のセッションで同じ停止が起きるかの判定と根拠を、後続担当が修正の充足を検収できるよう既存の引き継ぎ記録へ記録する。
   修正した規範は配布と再起動を経るまで稼働中の担当へ届かず、会話圧縮で失われることもある。
   このため、修正後の規範が届くまで従わせる規則（暫定規則）が確定したら、メインエージェントは現行の全体作業契約の「即時対応で確定した暫定規則」節へ書き、稼働中の担当へ同節の再読を指示する。
   以後に起動する担当へは既存の全体作業契約の受け渡し（`whole_contract_path`）で届け、軽量起動には必要な規則を委譲本文へ写す。
   新しい記録ファイルは作らない。
3. `${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`に従って正式対応用のAWIを起草し、投入する。
   暫定修正のコミットや差分、観測結果と検証結果、未確認事項、残りのテスト、独立した文脈でのレビュー、原因分析、類似箇所の見直し、再発防止策の情報を引き継ぐ。
   既存のAWIを再利用する場合は、これらの情報がすべて含まれていることを確認する。
   登録したAWIは今回の選定対象には加えずに後続のセッションへ引き継ぐ。
   回避だけで進め、暫定修正のcommitが無い場合は、手順2の停止判定と根拠も必ず渡す。
   次のセッションで停止する見込みがあれば、投入前に直接修正へ戻る。
   未実施の正式な分析、類似見直し、恒久対策は未実施と明示する。
   これは通常投入で調査済み事項を引き渡す手順の例外である。
4. 直接修正と正式対応AWIの対応関係を引き継ぎ記録に残した上で、元の作業工程を再開する。
   ユーザーから明示的に追加された要求や、今回の作業で混入した不良については、元の要求や完成条件に従って対処する。

正式対応を引き継いだ後続セッションでは、暫定修正を完了とみなさず、AWIに記載されたすべての要求と`agent-basics:bugfix`の基準に沿って検証する。

## レーンの変更範囲へ加える修正の認可

1. 即時修正の担当・基点・時機は、現在の工程と修正対象の所有権から次の順で決める。
   判定と根拠は既存の引き継ぎ記録へ残し、独立修正ごとの統合済みレーンの再開は省く。

   | 状態 | 担当・基点・時機 |
   | --- | --- |
   | 未統合のレーンが同じ対象を編集中 | 現担当へ最小修正を認可し、そのレーンの現行版で検証・独立文脈レビューする |
   | 全レーン統合後の独立した修正 | 統合先を所有する担当が統合済みHEADを基点に直接修正し、限定検証と独立文脈レビューを経る |
   | 現工程の進行を妨げない独立修正 | 現工程の安全な区切りで実施し、公開前に取り込む。公開後なら公開手順の再公開へ接続する |
   | 現工程または次の処理を停止・遮断する修正 | 必要な最小修正を先に行い、安全性を確かめて元工程へ戻る |
   | 元WIの未達・今回混入した不良 | 元の担当・要求・完成条件で完遂し、独立した即時修正へ付け替えない |

2. 未統合レーンへ加える場合は、直接修正の対象と方針が技術的に確定した最小範囲を同じスレッドへ追送する。
   正式対応AWIの起草中も、認可済みの修正作業を進める。
   統合先に書き込む担当が未確定なら、メインが担当と認可範囲を確定してから書き込む。

   - 認可内容には修正対象、修正方針、出所（レーン担当の報告とメインエージェントの判定）を含める。
     この対象と方針が追加修正における書き込み認可の境界となる。
     エージェント向け文書も個別に指定せず同一の境界で扱う。
     確定済みの計画はそのまま保持する。
   - 実行レビュー担当を起動する際に、その認可内容を`review_contract`の条項として渡す（`${CLAUDE_PLUGIN_ROOT}/share/exec-review-contract-generation.md`「`review_contract`の生成」）。
   - 修正対象や方針が定まらない場合は、安全な修正に必要な事項を調査し、ユーザー固有の判断が必要な事項が残る場合は確認する。
   - 修正済みの箇所も正式対応AWIの検証対象に含める。
     メインエージェントが修正コミットと報告を担当者へ渡し、正式対応AWIが登録されたことを確認する。

## 対象外の不良と是正要求

1. 本書「即時対応」の対処時機判定で次回へ渡す不良・是正要求・独立改善は、`add-wi.parent.md`への委譲を通じて`source: process-wi`のAWIとして投入する。
   次回へ渡す具体的な理由と再開条件は既存記録へ残す。
   修正時機とAWIの登録時機を分け、待機中に判定できる改善要求は`../../delegation/references/waiting-and-monitoring-independent-work.md`「待機中の先行実施」に従って発見時に保存まで進める。
   次回修正の判定だけで投入自体を延期しない。
   ユーザーからの要求は、`../../wi-standards/references/wi-standards-origin.md`「由来と承認」に従って発話を逐語的に転記する。

2. メインエージェントは、即時対応の対象外とした既存不良についても、投入担当からの結果を受け取った時点で投入済みWIと対象箇所を自身の引き継ぎ記録に対応付け、報告元へその対応内容を伝える。

3. 公開工程の開始後であっても、CIの失敗など公開を妨げる不良は公開担当の手順に従って修正する。
   独立した既存不良に対する最小限の修正は、正式対応AWIと対応付ける。
   ユーザーが同一実行内での対応を明示した要求や、今回の作業で混入した不良は、元の要求や完成条件に従って同一セッション内で処理する。
   次のセッションの処理を停止・遮断する既存不良にも、本書「即時対応」を適用する。
   追加修正を統合した後の再公開は`finish-session-recovery.md`「公開状態の検収と再起動」に従う。

## 即時対応

対処や追加操作を選ぶ前に、元の発話と発生条件から、ユーザーの是正要求、今回の作業で混入した不良、同じ実行へ明示的に追加された要求を区別する。
今回混入した不良と初期選定の要求は元の完成条件で処置し、明示追加は`selection-procedure-addition.md`「処理対象WIの追加」へ渡す。
独立した既存不良・改善は、本節で最小の直接修正、今回追加する正式改善AWI、次回へ渡す独立改善を選ぶ。
登録を`予定`とする場合は、修正の対処時機とは別に「対象外の不良と是正要求」が参照する待機中の前提・再開条件を確認する。

即時対応では、現在または次のセッションの進行に不可欠な最小限の修正をその場で施し、テストの追加、独立した文脈でのレビュー、根本原因の分析、類似箇所の見直し、再発防止策の策定といった正式な対応は次のセッション用AWIとして登録する。
暫定修正も安全に利用できることを検証で確かめてから成果として扱う。
なお、登録した正式対応用のAWIは今回の選定対象には追加しない。
選定済み作業に必要な調査と正式な処置は同じ処理内で完遂する。
即時対応は未実施の正式分析、類似見直しと恒久対策を次回AWIへ渡す例外である。
即時対応の要否は、残る工程や次のセッションで処理の停止・遮断、誤った判断や成果物の作成、手戻りが発生するかどうかで判断する。
ユーザーから改善の即時実施などタイミングの指定があった場合は、その指示を優先する。
進行を妨げない独立改善でも、観測した不要作業、それを繰り返す具体的な後続工程や操作、削減できる仕事量と修正・検証・統合の負担を比較する。
再発の自然発生や一律の回数・時間・トークン数を待つ代わりに、同じ規範や操作が次回も使われる具体的な見込みを判断の根拠にできる。
公開工程開始前で、削減が負担に見合い、既存の認可・依存・書き込み所有権の内側に安全な受入先がある正式改善AWIは今回へ追加する。
進行に不可欠でない新着を追加する場合は、既存レーンの残り工程、共有検証枠、統合・公開の負荷を含めても実行全体の完了時期を遅らせない見込みを根拠とともに記録する。
安全な受入先または完了時期への見込みが成立しない項目は、理由と再開条件を残して次回へ渡す。
起草・検収・保存後の正式ファイル名を受領したメインは、`selection-procedure-addition.md`「処理対象WIの追加」の候補差分へ含める。
既存のmerge操作による全体確認と保存、未遷移項目の処理開始、同じ担当への追送まで確認する。
作業中のレーンにも凍結済み計画を保って工程境界で追加計画を受け入れる手順を使う。
書込競合・先行成果・既存レーンを調べても安全な受入先が成立しない場合と、公開工程開始後の独立改善は、具体的な理由と再開条件を残して次回へ渡す。
最小修正後の未実施の正式分析・テスト等は、前述の即時対応の手順どおり次回用AWIへ分離する。
担当の交代・引き継ぎ・再起動、エンジンやモデルの切り替え、迂回操作など、欠陥を残したまま進行を回復する手段は、即時対応の直接修正には当たらない。
回避で進行が戻っても、欠陥が残る工程か次のセッションで処理を停止・遮断するなら、同じセッションで直接修正する。
即時対応に該当する不良を、工程が完全に停止しているわけではないという理由や、不良の種別だけで次回へ先送りしない。
今回の作業自体で混入させた不具合や、初期選定のWIが本来求めている正式対応は、元の要求と完成条件に沿って同一セッション内で完了させる。
即時対応の枠組みを口実にして、初期選定された作業範囲を縮小しない。
実行レビューから返された差分範囲外の既存不良も本節で対処時機を判定し、原因分析・起草は`../../../share/exec-review-parent-existing-defects.md`「返却に含まれる既存不良の受領」の独立した投入担当へ渡す。

具体的な手順、レーンの変更範囲に修正を加える際の認可、および対象外とした不良や是正要求の扱いについては、`immediate-fix.md`の定めに従う。
