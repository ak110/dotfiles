# 選定YAMLの欄の意味

`書込対象`はレーン担当が変更を加えるファイルを、リポジトリ相対パスのYAMLフローリスト形式で指定する。
WI本文、作業を伴うUWIの回答、参照されている手順書と限定調査から、変更予定と判断した個別対象を欠かさず指定する。
具体的な書き込み先ファイルを特定できない項目については、限定調査で見積もったディレクトリ範囲を末尾に`/`を付けて指定する。
配下の個別パスとあわせて記載されたディレクトリ範囲（「対象リポジトリは`agent-toolkit/`配下とする」といった範囲の説明）は記載せず、配下の個別パスのみを記述する。
`レーン`が`なし`の項目であっても行自体は残し、空のリスト`[]`を指定する。
`書込対象`は初期配分と段階の見積もりに使う予定である。
開始後の編集認可はWIの要求を境界とする。
要求内の追加編集は`../../../share/exec-subagent-implementation.md`「実装」に従い、追加一覧の受渡しや選定YAMLへの反映を省いて進める。
初期配分の見積もりを修正する場合は、次の既存操作で追加・全体チェック・保存を行える。

```text
atk run-script pick-wi-check -- <選定YAML> --extend-write-targets <追加YAML> --output <保存先> --work-dir <対象リポジトリの絶対パス>
```

追加用YAMLの最上位項目は`選定`と`レーン間の重なり`とし、選定の各行に`WI`、追加する`書込対象`、必要な`導出した新設先`の4項目、および更新が必要な場合は更新後の`プロジェクト規範の指定`（文字列）を記述する。
`プロジェクト規範の指定`を書いた行は保存値をその値で置き換え、書かない行は保存値を保つ。
エージェント向け文書の追加でプロジェクトの規範指定の条件に当たるパスが増える場合は、増えた記載を含む全文を渡す。
追加した`書込対象`と同じパスか、その範囲の配下にある`書き込まない反映先`の要素は、同じ保存で`書き込まない反映先`から除かれる。
各リストは省略時に空のリストとなり、行が存在しない場合も空のリストとして解釈する。
既存のリストの順序を保ったまま重複なく追記するため、記録の追記のみを行う用途にも対応している。
同一段階の未統合レーンと重複する追加については、`レーン間の重なり`に定義と判定結果を渡す。
この操作では`初回配分`を含む既存の項目を保持し、全体チェックに成功した場合に限り不可分に保存する。
失敗した場合は選定YAMLを変更せず、不足している記録と次に取るべき操作を出力する。
本文の一部のチェックを指定する`--body-wi`や、新しいWIの合流、その他の更新操作を同時に指定しない。

`公開工程の書込対象`は対象リポジトリの規範において、各レーンでは編集せず全レーン統合後の公開工程でのみ変更すると明記されたファイルパスを指定する。
このパスも書込予定の妥当性を検証し、レーン間の重複・包含・連結成分の判定からは除外される。
`公開工程の規範根拠`には、各パスに対応する記録を過不足なく1件ずつ記載する。
規範ファイルには対象リポジトリに実在する通常ファイルを指定し、節にはそのMarkdown見出しと完全に一致する文字列を指定する。
余分なパスや重複した指定は検証で拒否される。
省略時は空のリストとなり、公開工程の対象が存在しない場合のみ省略できる。

両書込区分の要素は、実在するファイル、末尾に`/`を付けた実在ディレクトリ、本文で明示された新設先、または正当な`導出した新設先`の個別パスを指定する。
環境変数名、定義名、WI名、URL、絶対パス、親ディレクトリへの遡行（`../`）、グロブ、一般的な語句はパスとして指定できない。
ファイル名の直後に「の」を介して続く定義名は配下パスとはみなさない。
一方、ディレクトリ名の直後に「の」を介してファイルを列挙している記述は、そのディレクトリ配下の指定として扱う。
ファイル名やディレクトリ名に含まれる空白はパスの一部として扱い、インラインコード全体を1つのパス候補として解決する。
YAML内での引用符の有無や種類にかかわらず、同じ文字列であれば同一の判定結果となる。
空白を含む新設先であっても実在する親ディレクトリと完全なファイル名を要求し、パスの妥当性、過大範囲、重複の判定においても同じ個別パスを用いる。
両書込区分の要素、`導出した新設先`、書込予定の範囲と区分、`公開工程の規範根拠`、`プロジェクト規範の指定`の検証は作業ツリーのファイルを参照するため、未統合の項目にのみ適用される。
これらは作業着手前の作業ツリーで成立していた選定時の前提条件である。
そのため、統合済みの項目（項目自体または所属レーンの`統合状態`が`統合済み`である項目、および同じ呼び出しで`--mark-integrated`に指定されたレーンの項目）については、レーンでの作業によってファイルの改名、削除、追加が行われた後であっても、過去の履歴として扱われ検証で拒否されることはない。

`導出した新設先`の各記録には所定の4項目を記述し、すべての値に空でない文字列を指定する。
この4項目は選定時の判断履歴であり、ファイルが実際に作成された後も保持して、各パスと反映範囲・書込区分との対応関係を確認するために用いる。
パスには実在する親ディレクトリと拡張子を含む正規化された完全な新設ファイル名を指定し、未作成または作成済みの通常ファイルのみを受理する（ディレクトリなど通常ファイル以外が実在する場合は拒否される）。
反映範囲には、その新設先をパス要素として含む末尾`/`付きの実在ディレクトリを指定する。
本文に記載された範囲の外にある関連テストコードや補助ファイルであっても、要求との対応関係と配置根拠を備えていれば、個別の新設先として記録できる。
メインエージェントは、元のWI本文と限定調査の現物資料から意味上の対応関係を検収する。
各パスは両書込区分のいずれか一方へ個別に配置する。
新設先を具体化した後も、他の予定書込先の欠落がないことは元本文と限定調査から意味検収する。

`単一段階案の完了見込み秒数`と`段階案の完了見込み秒数`は旧方式の局所比較の履歴であり、全工程の成立判定から分離する。
旧方式は段階ごとの最長実装と直列統合の和へ、全体の共有待ちを1回加えた値である。
新しい算定では`全工程の見込み`を入力とし、結果は計算側から得る。
要約では`全工程の壁時計見込み秒数`と`通常対象の完了見込み秒数`を別に出す。
段階2以上を採用する選定では本項目を省略できない（型の不正は終了コード2、項目の欠落は終了コード1となる）。
追加用YAMLでは、統合後の全体配分について確定し直した値を渡し、既存の値は検収した上で使用する。

旧方式の`段階案の完了見込み秒数`はすべての行が段階1であり、いずれかのレーンの`実装秒数`が6000秒を超える場合に必須となる。
値には、比較対象とした段階案の補正後の完了見込み秒数（真偽値以外の0以上の数値）、またはレーン数上限の範囲内で成立する段階案が存在しないことを示す固定値`成立する段階案なし`を記録する。
必須条件に該当しない場合の省略は、比較値なしとして解釈される。
項目の欠落は終了コード1、型の不正は終了コード2となる。
合流処理では、両比較欄とも追加用YAMLで再確定された値のみを採用する。

`見込みの補正`は必須項目であり、`実装係数`、`統合係数`、`共有待ち秒数`、`共有待ちの算定`、`参照した記録`、`除外した記録`の6項目を持つ。
参照または除外した記録が存在しない場合は、それぞれのリストを空とする。
いずれかの工程係数が1以外の場合は、`参照した記録`に1件以上の記録を指定する。
各レーンの`補正前の実装秒数`と`補正前の統合秒数`も必須とし、`実装秒数`は補正前実装秒数×実装係数、`統合秒数`は補正前統合秒数×統合係数と1秒以内の誤差で一致させる。
秒数と比較値にはbool以外の0以上の有限数を使う。
共有待ちの見込みの根拠はレーンの`根拠`へ対応付け、未計測と実際の待ちなしを区別する。
`共有待ちの算定`は、参照した記録から測った値を`実測`、測っていない値を`推定`とする。
`推定`で0秒の組と、`実測`で`参照した記録`が空の組は終了コード1となる。
生成と追加の入力では`共有待ちの算定`を省略できず、追加側の値を採用する。
`共有待ちの算定`を持たない保存済みの選定も履歴として読む。
目標を持つ新しい配分は、この省略にかかわらず全工程を検収する。

`--work-dir`の`pyproject.toml`の`[tool.agent-toolkit.pick-wi-check]`に`target-seconds`（bool以外の正の有限数）がある場合は、その値を1回の処理の目標所要秒数とする。
実行用の選定に`全工程の見込み`が無い場合、未確認前提が残る場合、通常対象が目標を超える場合は、終了コード0のまま標準エラー出力へ警告を出し、全対象と品質工程・レーン上限を保つ組み直しを案内する。
これらは経過時間や観測待ちに由来し、検査を渡した担当がその場で解消できないため、選定・追加mergeは止めない。
完成経路の工程欠落、統合への経路の欠落、工程と選定のWI集合の不一致、承認元の対象WIの不一致は、入力を直せば解消できるため終了コード1とする。
`目標超過時の配分比較`は代替案の記録として残せ、超過の判定には影響しない。
比較欄を指定する場合の空文字列などの型の不正は終了コード2となる。
設定値の不正は終了コード2となる。
合流処理では`目標超過時の配分比較`も追加用YAMLで再確定された値のみを採用する。
項目の欠落や値の不一致は終了コード1、型の不正は終了コード2となる。
追加用YAMLにも同じ工程係数を指定し、合流処理では補正前の各値を加算した後に対応する工程係数を適用する。
共有待ちは全体配分について追加側で再確定した値を1回採用する。

保存済みの旧形式（`係数`・`参照した記録`・`除外した記録`）も読み取る。
旧形式の係数は、両工程を分離していない履歴の補正として両方へ適用する。
追加mergeは既存の形式と係数を維持し、異形式の混合を拒否する。

## 全工程と通常対象の算定

`全工程の見込み`の`並列数`と`工程`は必須で、`巨大WI`を省略した場合は空列として解釈する。
同時数は資源とサービスの上限以下とし、根拠の3欄を原記録へ対応させる。
同時数はCPUコア数から自動決定せず、資源・実際のAPI/CLI制限・起動/読込/検収まで含む総費用比較を意味判断の所有者が検収する。
根拠の真正性と費用の合理性は、数値検査後に意味判断の所有者が検収する。

工程IDは一意とし、先行工程は存在する別IDとする非循環の依存を指定する。
共有定義の不可避な直列処理と前段レーンの統合待ちを依存に含める。
検証工程は容量2の検証資源、統合工程は容量1の直列資源を使う。
実装・レビューはモデル資源を使い、同じ定義を変更する仕事の直列性は`先行工程`で表す。
選定・準備・公開・後始末・報告はモデルまたは直列資源へ割り当て、検証資源は検証工程だけに使う。
全ての処理対象WIを実装・レビュー・検証・統合へ対応付け、選定・公開・後始末・報告も含める。
各群の実装に対するレビューと検証を統合前へ置き、独立群は、他群の実装中にもその群のレビューを開始できる。
公開は統合後、後始末は公開後、報告は後始末後の経路へ対応させる。

秒数は同じ共有待ちを含めない仕事の処理秒数とし、資源不足による開始待ちは計算側で求める。
旧`見込みの補正`の`共有待ち秒数`は新しい計算の加算対象から除く。
残量/速度による算定には非負の`残量`と正の`速度`を追加し、秒数がその比と1秒以内で一致するようにする。
実測・残量/速度の根拠を残し、未確認はnullと前提の列で表す。
条件付き試算、未確認の算定、非空の未確認前提は実行可能性を未成立とする。
未測定の固定工程や待ちは未確認のまま保持する。

計算は依存を満たした仕事を資源容量の内側で重ねる、静的な構成の見込みである。
実際の担当を起動・制御せず、数学的な最短時間の証明とも区別する。
仕事量と依存の最長経路、資源待ちを区別し、各仕事と待ちを1回だけ計上する。

巨大WIの認定と今回の承認は、意味判断の所有者が原文と根拠を確定した後に入力する。
`承認元`は省略時に承認なしと解釈し、判断が拒否/未回答のときも通常対象に保つ。
巨大の根拠があり、承認元の対象WIが同じWIで判断が承認の場合だけ、当該WIにだけ属する仕事を通常対象の計算から外す。
承認は同じWIへの名指しの原文と対応させ、別WIへの承認や自由文からの自動推定を拒否する。
承認が無い、拒否、未回答の巨大WIは通常対象に含まれ、目標超過は警告になる。
拒否（終了コード1）になるのは、承認元の対象WIが不一致の入力に限る。
共通の固定仕事と通常WIにも属する仕事は外さず、残る依存と容量から通常対象を再計算する。
並行した通常仕事まで全体の秒数から減算せず、除外前の全件の壁時計はそのまま別に表示する。

追加mergeは、追加側が合流後の全対象について再確定した`全工程の見込み`を渡すと、その値を採用する。
渡さない場合は既存の`全工程の見込み`を合流後の選定へ引き継がず（追加分を含まない値は誤った見込みになるため）、見込みが未確認になった旨を警告として出す。
旧選定を`--history`で表示する場合は新たな実行可能性の成立を示さず、更新操作との併用を拒否する。
配分を変えない`--mark-integrated`では旧配分の履歴を保存できるが、新規生成・追加merge・再開配分には目標の検収を適用する。
目標を設定しない既存入力の局所値は`履歴の局所見込み秒数`と表示し、全工程の成立とは分けて扱う。

`書き込まない反映先`はAWIの`## 反映内容と反映先`や、作業を伴うUWIの質問・判断材料・回答に記載されているものの、`process-wi`では変更を加えない参照先または除外先を指定する。
公開工程で書き込む対象は`公開工程の書込対象`に配置する。
本項目に含める前に、該当する表の行、箇条書き、段落（UWIの場合は回答）を確認し、変更要求なのか、参照や除外の説明なのかを区別する。
この分類は本文の意味内容に基づいて判断する。
AWI本文で変更しないと明記されている上位ディレクトリ（例：「他の`docs/`配下は変更しない」における`docs/`）を任意で記録する場合は範囲としてここへ配置し、その配下で実際に変更するファイルは`書込対象`に個別に指定する。
この範囲指定は、書込区分へ個別に指定したパスを除いた残りの領域を表す。
参照先・除外先の記載は任意とし、本文から抽出した非書込パスの全分類は求めない。
`プロジェクト規範の指定`は両書込区分から判定する。
機械抽出できないUWIの書込予定も、メインが限定調査と回答内容から検収する。
旧版の選定YAMLに存在した`書込範囲の理由`は読み取り時に破棄する。

`レーンの所要時間`は`なし`以外のレーンを重複なく1件ずつ含め、実装時間と直列統合時間とを分けて1回のみ計上する。
比較値は前述の比較欄および各行の秒数から読み取り、後段レーンの`先行レーン`には、開始前に統合を完了しておくべきすべてのレーンを指定する。
同一レーン内で実装担当のモデル指定が異なる場合は、WI名と指定値を確認し、レーン起動前に割り当てを修正する。
`統合状態`は、すべての計画の保存とWIの終了処理が完了した後に`atk lane integrate`が記録し、メインエージェントはその実行結果とレーン担当の終了状態を検収する（未知の値は終了コード2となる）。
この記録処理によって、該当レーンの行と、その時点でそのレーンに属している全項目の`統合状態`が`統合済み`に更新される。
資源操作の入力と再開手順は[run-lanes-integration.md](run-lanes-integration.md)「統合とAWI終了」を参照する。
統合済み相手の詳細記録は省略でき、その相手だけとの重複なら同段階・先行指定なしで開始できる。
保存済みの別段階・統合済み相手の詳細記録は履歴として受理する。
未知のレーン・余剰の共通パス・重複記録は拒否する。
追加WIが既存レーンへ合流した場合は、合流先のレーン行を未統合に戻し、既存項目は統合済みのまま追加項目を未統合とする。
追加時の仮名は最終レーン名へ変換し、追加のないレーンと所属WIは保持する。
