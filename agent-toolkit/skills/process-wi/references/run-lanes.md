# レーンの実行

メインエージェントが確定した対象WIの集合を、選定結果に示されたレーン割り当てと依存順序に従って実行する。各レーンでは同一の担当スレッドが、必要に応じた計画の起草、実装、レビュー指摘の修正、コミット履歴の統合、およびメイン作業ツリーへの統合を担当する。

## レーンと資源

各レーンに準備された専用worktreeと処理対象WIを1名のレーン担当へ引き渡し、レーン数にかかわらず`${CLAUDE_PLUGIN_ROOT}/share/single-lane-execution.md`を適用する。以降の工程境界におけるやり取りは同契約の継続工程として扱い、複数レーンが存在する場合は、メインエージェントが`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の許可」に従ってメイン作業ツリーへの統合許可のみを直列に送信する。

選定結果の`段階`を昇順に処理し、同一の段階に属する独立したレーンを並行して起動する。`先行レーン`が指定されている後続段階は、列挙されたすべての先行レーンの統合完了を確認した後に、統合先の最新HEADを基点としてworktreeを作成する。段階が1つのみの場合は、すべてのレーンを同時に作成して起動する。

レーンごとの専用branch、専用worktree、および所有権の登録は以下のコマンドで実行する。専用worktreeは、対象リポジトリのメイン作業ツリー配下の`.claude/worktrees/process-wi-<レーン識別子>`に作成される。`process-wi`は対象リポジトリごとに1つだけ起動される前提であり、配置先パスはリポジトリとレーン識別子のみによって一意に定まるため、別セッションや`process-loop`のworktreeから呼び出した場合でも同一のパスとなる。

```text
atk lane create --repo <対象リポジトリの絶対パス> --base-branch <統合先branch> --lane <レーン識別子> --selection-file <選定YAMLの絶対パス>
```

対象リポジトリに固有の作成・環境準備・撤去手順が定められている場合は、create、prepare、deleteの各argv配列を含むJSONファイルを`--commands-file <絶対パス>`へ渡す。各argvに含まれる`{repo}`、`{worktree}`、`{branch}`、`{lane}`は、シェルを介さずに作成側によって直接展開される。`{worktree}`には規定の固定作成先が渡される。前提ファイルのコピー、`mise trust`、必要な依存関係の同期処理はprepareに含める。固有手順によってdetached HEADとなった場合、作成側がそれを専用branchへ接続する。`--worktree <絶対パス>`は、固定作成先とは異なる場所が必要な場合にのみ指定し、その場合のパスは固定配置とならない。

対象リポジトリのClaude Code設定に`WorktreeCreate`が定義されている場合は、対象cwd、環境変数、公式イベント入力を与えて該当hookを実行し、返却されたパスを同一の所有登録へ保存する。作成hookを利用する場合は、worktree作成処理をそのhookのみに委ねる。hookが失敗した場合は、診断情報と作成途中のリソースを保持したまま同一操作による回復を試み、通常のGitコマンドによる作成へ安易に切り替えることは避ける。`WorktreeRemove`が設定されている場合は、終了時のリソース回収時に同一の設定と返却先パスを使用する。前提ファイルのコピーはhookまたはprepareが担当する。

所有セッション、Git共通ディレクトリ、専用branch、作成先パス、回収対象、選定原本、固有手順、ならびに実行記録は、`record_path`に示される登録ファイルへ保存される。リソース情報を手動で再登録することは避け、親の`parent-handoff.md`には作成結果の保存先と担当スレッドと引き継ぎ記録の対応関係を記録する。メインエージェントは、終了コード0、`ready`の状態、prepareの標準出力・標準エラー出力の内容を確認し、警告の有無と環境準備が正しく成立したことを確認した上で担当エージェントを起動する。そして、環境構築の結果を`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`環境構築`へ引き渡す。準備に失敗したリソースについては、登録情報と途中成果を保持したまま入力を修正し、同一のcreate操作で再開する。

別の名前空間へworktreeを引き渡す実装レーンでは、利用するすべての主体から同一の絶対パスへアクセスできることを読み取り専用で確認した上で担当を起動する。アクセスが確認できない場合は担当を起動しない。作成先は現行の`atk lane create`の仕様に従う。

統合済みのリソースもセッション終了まで破棄せずに保持し、同一レーンへの追加作業が発生した場合は、前回のcreate操作の返却情報から専用worktreeとbranchを再利用する。登録情報と回収結果は専用リソースの外部に保持される。前回のセッションが強制終了した場合などに残存した登録情報は、`process-wi`開始時に`atk lane delete --list`で確認し、担当エージェントや関連プロセスの終了を確認した上で、同一所有セッションに対するdelete操作によって再判定する。再開に利用する場合は、登録ファイルの`record_path`をcreateの`--reuse-record`へ渡して新たな所有セッションへと移管する。再利用すべきworktreeが存在しない場合は移管せず、元の所有セッションに対するdelete操作で登録を回収した後に再作成する。旧配置（個別のmanaged-temp配下）の登録であっても、同一の作成先を維持したまま移管できる。固定の作成先パスが別セッションの登録によって保持されている場合、createは回収条件を満たすリソースのみを回収し、同一パス上に再作成する。未統合のリソース、変更が残っている（dirtyな）リソース、稼働中のリソース、所有権の登録がない実体については、変更を加えることなく処理を失敗させ、その理由とともに`--reuse-record`またはdeleteによる回復手順を返す。createは、渡された選定原本からレーンに属するWI集合と統合状態を所有登録へコピーし、選定原本が一時領域から消失した後であっても、保持された値に基づいて統合と回収を判定する。選定情報を含まない旧形式の登録は、`atk lane recover --session-id <所有session>`を実行することで、元のbranchを保持したまま作業ツリーのみを解放する。回復処理を終えた登録は固定作成先の所有・回収判定から除外され、残存したbranchとHEADは`atk lane delete --list`の出力本文から確認できる。リソース回収時は、メインリポジトリから実体パス、Git登録とbranchの存在を照会し、すべて存在しないと確定した登録のみを、警告と最終記録HEADを残して回収する。作業ツリーのパスが存在しない場合はdelete手順を実行せず、Git登録のみが残存している場合は登録を強制解除する。branchが残っている場合は統合済みかどうかの判定を継続する。メイン作業ツリーや登録のない実体はそのまま保持する。

各レーンの担当エージェントを初回起動した直後に、`atk agents list --include-terminated`を実行し、起動結果の`session_id`に一致する項目の`created_at`をタイムゾーン付きの`レーン開始時刻`としてレーンのリソース記録へ保存する。`started_at`はターンの開始時刻を表すため、初回起動の起点としては使用できない。同一レーンを再起動したり担当を交代したりした場合でもこの値は変更せず、統合指示を送信する際に`exec.parent.md`の同名入力項目として引き渡す。レーン担当はこの値を`atk lane integrate`のmanifestに含まれる`lane_started_at`へ渡し、CLI側でも最初の値を所有登録へ保持してレーン稼働秒数を算出する起点として利用する。

同一レーン内のAWIは選定結果に示された依存順序を守り、依存先から順に処理する。計画の作成が必要なレーンでは原則として1つの計画にまとめ、単一の計画では行数制限の警告を回避できない初回の起草時に限り、`references/lane-planning.md`「計画の起草」の手順4に従って複数の計画へと分割する。
依存先タスクの失敗や保留、あるいは上流投入の完了待ちによって必要な成果物が得られない場合は、後続タスクを依存待ちの状態にし、必要な成果物を取得した後に作業を再開する。ユーザーからの明示的な指示によって追加された依存先が既存レーンに存在する場合は、「処理中に確定した必須是正レーン」に基づいて受け入れ可能かどうかを確認し、同一レーンで受け入れられない項目については待機する。

稼働中のレーンが1つのみとなった場合でも、そのレーンに含まれる未着手のAWIは同一レーン内で処理を継続する。未着手のAWIを別レーンへ移管すると計画ファイルの分割や書き込み所有権の移譲が必要となり、計画凍結（`agent-toolkit:plan-mode`の`references/plan-file-standards.md`）の原則に反するためである。単独稼働となる期間は、選定工程における段階設計を工夫することで短縮を図る。

レーン担当を起動する際は、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`に定められた入力を渡す。初回起動時における各AWIの再開位置は選定結果から読み取り、担当エージェント全体に対する`再開位置`は中断した同一担当を再開する場合にのみ渡す。該当レーンに属する各WIの`担当モデル.実装担当`は、`agent-toolkit:delegation`の`references/runtime-routing.md`「工程別モデル設定」に従って`model_type`へ指定し、比較検討の結果を引き継ぎ記録へ残す。異なる指定が含まれている場合はWI名と設定値を明示し、いずれかの指定を独断で破棄して起動することは避ける。
初回の`書込担当一覧`は合意済みのセッションIDと担当範囲に基づいて確定し、担当の交代、再開、および単一レーンへの追送時に更新する。
一覧と対象worktreeの対応関係は引き継ぎ記録へ保持し、統合を担当するレーン担当が同一の認可セットを利用できるようにする。

## 各段階の全初期通常レーン起動後の会話圧縮

Claude Code環境では、各段階（複数段階の場合は中間の段階も含む）において、すべての初期通常レーンの初回起動が完了した直後、その時点で並行開始できる独立工程を先行して開始した上で、待機状態に入る前に会話圧縮を予約する。通常レーンが0件の場合や処理中に追加されたレーンでは予約せず、実行レビュー待機時にも修正作業に必要な文脈を保持する。Codex環境では予約処理を省略して通常の待機へ進む。圧縮の予約および通知後の文脈復元手順は、`agent-toolkit:delegation`の`references/waiting-and-monitoring.md`「長時間待機前の会話圧縮」に従う。

予約前にセッションのmanaged-temp直下の`parent-handoff.md`へ次を保存する。担当別記録と保存物は、この記録に書いた参照から取得する。

- 選定YAMLの絶対パス、現在の段階番号、初回起動済みのレーン集合とそれぞれの`session_id`
- 専用worktreeおよびbranchの所有主体、回収対象、保持した最初のレーン開始時刻
- 各レーンの引き継ぎ記録、蓄積された計画集合とその保存状態
- 統合済みのレーン集合、後続段階の先行統合条件、次に受領すべき工程境界

通知を受け取った後は、保存された段階番号と`session_id`を用いて、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の該当する受領工程へ復帰する。

## 上流投入

レーン担当を起動する前に、`上流投入`が`なし`以外のすべての項目について、`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`の上流投入手順に従って委譲する（同一の`元項目`に属する組は同一の投入担当へ委譲する）。投入が完了した上流項目は、返却値に含まれる`ファイル名`によって識別する。レーン起動に先行して投入する理由は、`混在`区分の項目において上流へ引き渡した要求を、レーン担当が実装対象から除外できるようにするためである。「続行できない理由」を返してきた要求を含む項目については、`add-wi.parent.md`「受領と検収」に従って元項目の状態を変更せずに保留とする（`混在`区分の場合はレーン自体の起動も保留する）。

`上流要求だけ`（`レーン`が`なし`）の項目は次のとおり扱う。

- `completed`の要求が含まれる場合: レーンは起動せず、取得したすべての`ファイル名`を`atk wi set-dependencies`を用いて元項目の`depends_on`へ追加し、`atk wi return-to-inbox`で`inbox`へ差し戻す
- すべての要求が`condition_not_met`の場合: 依存関係は追加せず、条件不成立の理由や調査によって確定した投入見送りの結論を、根拠と証拠の所在に基づいて確認する。人間由来の要求を投入見送りとする判断は、`agent-toolkit:wi-standards`の`references/origin-and-approval.md`「承認」に従って確定した上で、元項目を終了処理（終端）する

`混在`区分の項目では、投入結果（要求内容、投入先、`ファイル名`、`結果`）を`exec.parent.md`の`上流投入結果`として渡す。`completed`の要求が含まれる項目については、統合指示における`AWI終端区分`を`終端しない`に設定し、統合の検収完了後にメインエージェントがすべての`ファイル名`を`depends_on`へ追加した上で`inbox`へ差し戻す。すべての要求が`condition_not_met`となった場合は、通常の終端処理を適用する。

## 処理中に確定した必須是正レーン

処理中に追加された対象WI（ユーザーから明示指示のあったAWI、処理中に回答が得られたUWIとその元項目）は、`selection-procedure.md`「処理対象WIの追加」に従って分類と処理開始手続きを完了した後に、本節の基準に沿ってレーンへ割り当てる。未回答のUWI、要求内容が確定していない項目、ユーザーからの明示指示がない新規到着項目は、追加の対象外とする。即時対応における正式対応AWIは、後続のセッションへ引き継ぐ。

追加された項目は必ず既存のレーンへ割り当て、処理中の一環として新たな最終レーン名を新設することは避ける（上限値および算定集合は`selection-format.md`「初回配分の算定根拠」が定める。所在参照）。既存レーンが0件の場合は、上限および割り当て先リソースの不足を「続行できない理由」として報告する。

1. 変更対象のファイルと該当箇所、実際の依存関係、再開対象の計画、既存レーンの残り工程、および書き込み所有権の状況を確認する。
2. 同一の再開対象計画を持つ既存レーンが存在する場合は、そのレーンへの割り当てを最優先の分割不能条件として確定し、費用比較よりも先行させる。受け入れ不能な技術的要因が観測された場合でも、該当計画を別レーンへ割り振ることはせず、同一レーンにおける所有権と再開状態の回復を図る。
3. その他の項目については、実際の依存関係と書き込み所有権を満たす既存レーンに対して、工程境界で受け入れられるよう割り当てる。待ち時間や残存作業量は既存レーン間の選択基準として利用し、互いに独立した要素であっても同一レーン内で順次処理する。
4. 割り当ての理由として、実際の依存関係、再開対象計画、待ち時間、現在の進行工程、書き込み所有権、および同一実行内で処理する順序を記録する。

メインエージェントは、`selection-procedure.md`「処理対象WIの追加」に定められた公開merge操作によって仮の名称を既存の名称へと対応付け、全体確認の終了コード0と保存の成功を検収した上で、追加分のタスクを引き渡す。合流先のレーンは未統合の状態へ戻るが、追加のない他のレーン、所属WI、および初回の登録情報はそのまま保持される。

割り当て先のレーンがすでに統合済みであってもリソースは保持されているため、同一の`atk lane create`を実行して所有登録とGit登録の一致を確認し、返却された同一のworktreeおよびbranchへ追加する。指示は、すでに準備された環境を維持している同一の担当スレッドと引き継ぎ記録へ送信する。登録情報と実態が一致しない場合は途中成果を保持し、回復に必要な事実を報告する。合流先レーンは未統合状態に戻るため、セッション終了時であっても再統合が完了するまでリソースを保持する。

選定YAMLへの追加が完了した時点で、現在実行中の工程の完了を待たずに、同一スレッドへ一度だけ指示を送信する。指示には、追加するWI名、専用worktreeおよびbranch、引き継ぎ記録、選定YAMLから本文と`プロジェクト規範の指定`を取得すべき旨、ならびに現在の工程を中断・破棄せずに完了させ、ターンを終えずに追加計画の起草へ進むべき旨を含める。割り当ての再検討のみを目的として稼働中の担当エージェントを中断させない。
工程境界における通知方法は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`に従い（所在参照）、一律の返答を要求しない（非待機の`計画検査完了`は`atk agents notify`による一方的な通知であり、返信を義務付けると実装作業が停止してしまうためである）。レーン担当は、現在工程の実行結果を、追加指示の受領後に最初に送信する工程境界メッセージの先頭に含める。
メインエージェントはその工程境界メッセージの受領をもって追加工程の開始を認識し、先行する計画を凍結した状態を維持しながら、追加計画の絶対パス、対象AWI集合、保存状態、および進捗状況をレーンの引き継ぎ記録へ順次蓄積し、実行レビューと統合の段階へすべての計画を引き渡す。

同一スレッドの再開が成立しない場合は、公開応答の事実、対象、および不足している条件を「続行できない理由」として報告し、同一レーンの回復に関する判断を仰ぐ。再開が不可能な場合や全レーンが統合済みである場合であっても、新規レーンを作成することは避ける。追加分に対しても、計画起草、レビュー、統合、終端という既存の手順をそのまま適用する。

同一セッション内で共有ツールや共通手順を修正し、稼働中のレーンが残りの作業でそれらを利用する場合は、該当するレーンに対してのみ、修正コミット、反映されるタイミング、再起動の要否、および反映前の回避手順を1通のメッセージにまとめて通知する。

## メインが読む対象の境界

メインエージェントは、WI選定時にAWIやUWIの元本文を確認し、選定後は主として選定の構造化出力、計画の`## 概要`および`## 実施内容`、工程境界における出力、レビュー指摘管理表の状態、ならびに統合結果を確認する（努力目標。メインエージェントのコンテキスト消費を抑制するため）。計画内の他の節や実装差分については、エスカレーション時、ユーザー対応時、またはレビュー収束の可否を判断する際に必要な場合に限って確認する。統合結果に含まれる`変更したエージェント向け文書`の再取得は、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従う。

処理対象WIに含めた理由、除外した理由、または選定の構成についてユーザーから質問を受けた場合は、`selection-procedure.md`の読込表に示された説明手順を参照する。
該当する説明手順は`${CLAUDE_PLUGIN_ROOT}/skills/process-wi/references/selection-explanation.md`に定められており、メインエージェントは保存済みの選定結果と判断内容に基づいて、その根拠と適用限界をユーザーへ説明する。

## 採否の確定と終端区分

人間由来の要求を全面的または部分的に不採用とする場合のレーン担当による判定および通知手順は、`references/lane-planning.md`「計画の起草」に準拠する。メインエージェントは、除外範囲、原文との差異、技術的な理由、および代替案を受け取り、部分採用における除外範囲も含めてユーザーへ確認する。確認待ちの間も、ユーザーの回答を待たずに進められる他のレーンの作業を継続する。計画確定後の後続工程では要求の由来を再判定せず、計画内で確定した採否をそのまま適用する。

回答が得られない場合は、`agent-toolkit:wi-standards`に従ってUWIを登録し、`atk wi hold --state=processing <元AWIのファイル名>`を実行して保留状態にする。UWIの本文には、元AWIのファイル名、対象、必要とする回答内容、および回答によって分岐する結果を明記する。保留の解除条件と再開工程は、`atk run-script plan-progress --`を用いて計画の`## 進捗ログ`へ記録する。計画ファイルが存在しない場合は、`atk wi edit <元AWIのファイル名> --append --body-file <絶対パス> --target-repo=<対象リポジトリ>`を実行して元AWI本文へ追記する。採否の決定は回答を受け取った後に行う。同一実行内で回答が得られた場合は、実装開始前であればレーン担当が計画へ、実装着手後であればレビュー指摘管理表へそれぞれ反映し、同一レーン内で採否を確定する。

各AWIを次の終端区分へ割り当てる。

- 採用した要求を実装して完成条件を満たした項目、および既存の実装によって要求と完成条件がすでに満たされていることを現物で確認した項目: `adopt`
- 必要な採否手順を経て不採用と確定した項目: `reject`
- 回答を保存した事前承認型のUWI、およびその回答を反映して採否を確定した元AWI: いずれも`adopt`
- ユーザーからの回答待ちとなっている項目: 終端処理は行わず、`atk wi hold --state=processing <AWIのファイル名>`を実行して保留とする
- 外部環境の状態変化や上流の変更待ちとなっている未実装項目: 終端処理は行わず、`inbox`へ差し戻す
- 実装と統合が完了し、反映後の完成条件の観測のみが残っている項目: 延期`adopt`とし、観測専用の再開手順で確認した結果に応じて以下のとおり処理する。再開記録の追記、状態変更、計画への記録は`references/finish-session.md`「延期adoptと反映後の観測」に従う。
  - 直接観測によって完成条件を満たしたことが確認できた場合: `adopt`
  - 直接観測によって完成条件を満たせなかったことが確認できた場合: この実行では`adopt`を行わず、既存の実装コミットの上へ再実装することも避けて、終端区分を`終端しない`とする。`再開区分: 再実装へ戻す`の再開記録を追記し、再処理抑制期限を設定せずに`inbox`へ差し戻す。次回の`process-wi`実行時に通常の項目として計画起草から着手する。
  - 観測自体ができなかった場合: 終端処理は行わず、レーン担当から返却された観測結果（理由、不足している前提条件、前提を阻害している状態の生成元・起動元・起動契機、および未確定の範囲）に基づいて、残存する完成条件ごとに前提を整えられる主体を判定する。エージェント自身や常駐プロセスが生成した状態は、OS上の実行ユーザーが同一であっても人間が起動した状態とは区別し、生成元が未確定の状態をユーザーのみが対処可能な状態として扱わない。人間が通常操作する入力や環境であることだけを根拠として、ユーザー操作が必要と判定することは避ける。自己操作による手段が成立するかどうかは、`references/finish-session.md`「延期adoptと反映後の観測」の自己観測判定に従って確認する。
    - 次回セッションでエージェント自身が前提を整えて観測可能な項目（新規プロセスの起動、反映処理の完了待ちなど）: 実装を無駄に繰り返さず、次回セッションでの観測へ回す。観測可能となる最も早い時刻が将来である場合は再処理抑制期限を設定して`inbox`へ戻し、それ以外は`processing`状態を維持する。
    - ユーザーによる操作や追加認可がなければ前提を整えられない項目（実行ログ等でユーザーが起動したと確認されたセッションの停止など）: 自己操作が成立しないと確認されたものに限り、完成条件を変更することなくUWIを発行して前提条件の充足を求め、元AWIを`hold`へ移す。操作主体と選択肢の振り分けは`agent-toolkit:wi-standards`の`references/uwi-format.md`「ユーザーへ操作を依頼する場合」に従い、実行権限はあり認可のみが不足している工程については、エージェントが実行することに対する認可を求める。UWIには、必要な操作または認可、観測結果、不足している前提、および自己操作が成立しない根拠を記載する。同一の観測タスクを無批判に次回へ引き継ぐと、前提が整わないまま不毛な処理が繰り返されるためである。

複数要求を持つAWIは、採用した要求を全て満たした場合に`adopt`し、未解決の保留が残らない場合にだけファイル全体を終端する。固有指示が終端工程後のadoptを求める項目と、版数更新を完成条件に持つ項目は延期対象とする。

## 実装とレビュー

準備結果の取り扱い、および待機を要する場合の`実装開始`または`実装なし`の返却は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「計画準備の受領」に従う。また、`実装完了`の受領、実行レビューおよびユーザビリティレビューの起動、指摘事項の修正と収束判定については、同書「実装完了の受領」に準拠する。

選定結果に記載された担当モデル、起動側が解決したモデル候補、および終了後の実行ログから観測された実行identityをそれぞれ独立した値として比較する。不一致がある場合は値とその出所を明確に区別し、観測できなかった場合は未観測として後続へ引き継ぐ。

レーン担当から確認事項や事後承認の対象を受け取った場合は、その時点で根拠と既存の認可状況を精査し、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」および`agent-toolkit:wi-standards`に基づいて発行の要否を判断する。確認が不要な技術的判断は報告事項として扱い、事前承認が必要な確認事項は受け取り次第速やかに発行する。事後承認型のUWIは受領時には発行せず、実行レビュー（画面レビューを並行する場合はユーザビリティレビューを含む）が収束した後、かつ統合処理の前に、最終的な実装内容と一致する本文で発行する。実行レビューしないレーン（`実装なし`および`マージなし`）では、終端返却を受け取った時点で発行する。`atk wi add`の成功と作成されたファイル名を記録し、ユーザーからの回答を待たずに後続作業を継続する。受け取った全事項の判定と発行が完了したことを確認して統合処理へ進むものとし、確認不要な報告のみを理由として統合を遅延させない。

## 統合とAWI終端

統合前の確認作業は、`agent-toolkit:review-standards`の`references/exec-review-recording.md`「統合時の完成条件判定」に従う。レーン担当へ委ねる統合指示、およびメインエージェント自身がCLIを実行する場合の検収は、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に準拠する。

Git統合、全計画の保存、WIの終端処理、選定情報の統合状態更新は、同一の所有登録をもとに`atk lane integrate`が一括して実行する。呼び出し引数とmanifestの作成手順は、レーン担当の`lane-integration.subagent.md`「公開統合操作」に従う。メインエージェント自身が現行CLIを呼び出す場合も、独立した文脈でのレビューと完成条件の判定を通過した同一の入力情報を使用する。Git統合と統合状態の更新は、この公開操作に集約して実施する。

終了コード0、`phase: finalized`、統合結果のOID、計画ファイルの保存、ならびにAWIの終端完了を確認し、`parent-handoff.md`へ記録する。`git-integrated`は最終化処理の途中の状態であり、統合完了とはみなさない。処理が失敗した場合は、同一のmanifestとレビュー対象HEADを用いて未完了の工程から再開する。rebase後のコミット対応表と検証記録は所有登録と同一の状態ディレクトリへ保存され、一時領域から失われた過去の状態は同一操作によって再生成されて検収待ちの状態へ復帰する。CLIは今回のWI集合と所有権を検収し、すべての最終化操作が正常に完了した後に選定原本を不可分（アトミック）に「統合済み」へと更新する。統合前の稼働確認では、統合先worktreeとレーンのworktreeをカレントディレクトリ（cwd）として動作中の担当エージェントを確認する。書き込み役割を持つもの（役割文書に`作業ツリーへの書込: あり`と明記されているもの）、役割文書を特定できないもの（自由入力による`delegate`、`shell`、`write`など）、宣言内容を読み取れないものをカウントする。
所有セッション、合意済みの`書込担当一覧`、統合を呼び出す担当の委譲元チェーンを共通の認可セットとする。
`explore`や`作業ツリーへの書込: なし`と明記されている担当エージェントは書き込み判定から除外し、認可一覧に含まれない実際の書き込み担当が存在する場合にのみGitの変更処理前に拒否する。
合意済みの担当エージェントは`--writer-session`で指定する（`lane-integration.subagent.md`「公開統合操作」）。リソース回収時は、すべての担当エージェントと外部プロセスが終了していることを確認する。リソース、完了済みレーン、所属WIは、追加タスクの発生に備えて保持する。

リソースの回収は、セッション終了時に`atk lane delete`によって実行する。登録全体を事前に確認し、すべての工程および外部プロセスが終了していること、選定情報が統合済みであること、存在するworktreeがクリーンであること、Git共通ディレクトリと専用branchの登録が一致していること、および統合先への到達が可能であることを削除直前にも確認する。`finalized`となったレーンについては、branchのHEADが統合時に記録された入力HEADと一致している場合、統合先でコミット履歴の書き換えが行われた後であっても統合済みとして回収する。実体が存在しない登録については、これらの確認判定を省略する。確認完了後は、実在するworktreeに対してのみ`--commands-file`で指定された`delete`コマンドを実行し、worktree、統合済み判定を再確認したbranchの`-D`削除、旧配置の登録が保持する個別managed-tempの順序で回収を進める。未統合、dirty、稼働中、状態不明、または処理途中で失敗した対象については、その理由と残存する操作内容を回収対象の外部へ保存し、再実行時には残りの処理から再開する。セッションのmanaged-tempや証拠ファイルは専用worktree内には置かず、回収対象から除外する。通常終了時の`atk agents-exit-session`、および`process-loop`が子セッション終了後に実行する処理は、同一の回収操作を呼び出す。ターンごとの`SessionEnd`イベントでは回収しない。
自動終了のいずれの経路でも同一の適格判定基準を用い、終了済みセッションからの解放応答を待機せず、未確認の事項があれば既存の保持理由と結果の保存先を返す。
対話的な`lane delete`、固定作成先での`lane create`、`--reuse-record`、ならびに`lane recover`の各操作は、所有者側の解放応答と実行中プロセスの終了を指定の期限まで待機する。
解放要求の完了後に別の担当や外部プロセスによる使用が検知された場合は、一度の照会によって保持理由を更新し、同一の公開操作による再判定へと回す。
終了済みの委譲セッションが保持しているリソースについては、回収処理が所有者側の`agents_server`に対して解放を要求し、未回収の結果を保持した状態で解放処理してから、使用中かどうかの判定をやり直す。
実行中のセッションや解放できないリソースは破棄せずに保持し、次項の手順に従って再回収する。

到達確認を行った上で`-D`オプションによりbranchを削除する理由は、通常の`-d`オプションがupstreamを基準に判定するため、push前のローカル統合を未統合と判定して削除を拒否してしまうためである。監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/process-wi/references/run-lanes.md「統合とAWI終端」：所有資源の回収：2026年9月3日」に記載されている。

### 未回収レーンの再回収

回収結果に未解放として示された委譲セッションについて、終了状態であること、および`atk agents wait`によって結果本文が回収済みであることを確認する。今後再開する予定がない場合は、公開MCPである`agents_server`の`stop`ツールを呼び出し、`session_id`として該当のIDを指定する。
呼び出し形式は`stop(session_id="<回収結果にある委譲sessionのID>")`とする。
公開ツールである`stop`は終了結果も同時に破棄し、結果保持を指定するための引数は存在しない。
これに対し、回収処理が所有者側へ要求する自動解放処理では、未回収の結果が保持される。
現在実行中のセッションについては終了を待機し、その結果を回収する。

停止処理が成功してリソース保持の理由が解消された後は、対象リポジトリを作業ディレクトリ（cwd）として`atk lane delete --session-id <レーン資源を作成した所有sessionのID>`を再実行する。
`--session-id`には、元の回収操作と同一の「レーンリソースを作成した所有セッション」のIDを指定する。
このIDは`atk lane delete --list`の所有登録情報から確認でき、`stop`に渡す委譲セッションのIDとは役割が異なる。
停止処理に失敗した場合や、外部プロセスによる使用が継続している場合は、リソースおよび回収結果を保持したまま、その理由と残存する操作内容を報告する。

## 中断レーンの再開

`processing`状態のまま残存している項目については、計画が存在するレーンでは選定結果の`再開位置`に記載された計画ファイルを使用する。複数の計画が存在する場合は、引き継ぎ記録に蓄積されたすべての計画、対象AWI集合、進捗状況、および保存状態を突き合わせた上で引き渡す。計画のないレーンでは、引き継ぎ記録のAWI集合、レビュー指摘管理表、ならびに`git merge-base <専用branch> <ベースbranch>`および`git log <その結果>..<専用branch>`によるコミット履歴を確認して再開すべき工程を決定し、`再開位置: 計画なし`として引き渡す。計画ファイルまたは引き継ぎ記録の実在、AWI集合の一致、および専用worktreeの元の所有主体が終了済みであることを事前に確認する。
反映後の観測のみが残っている項目については、`references/finish-session.md`「延期adoptと反映後の観測」によりAWI本文へ追記された再開記録に基づき、選定結果の観測専用の再開位置をそのまま引き渡す。レーン担当は`references/lane-planning.md`「再開」に従って観測作業のみを実施する。

残存している専用worktreeおよびbranchを安全に再利用できる場合は、同一の絶対パス、branch、最新HEAD、および再開位置を新規のレーン担当へ渡す。安全に再利用できない場合は、既存の作業成果を損なわないよう最新HEADから新規の専用worktreeを作成し、移行内容を`atk run-script plan-progress --`を用いて進捗ログ（計画なしの場合は引き継ぎ記録）へ記録する。コミットされていない差分については所有権と実態を確認し、権限の範囲内で成果物を損なわずに復元・移送する作業は自ら行う。他者やユーザーの差分の破棄、あるいは所有権を確定できない成果物を消失させるおそれのある処置については、「確認要否の判定」に従って事前に認可を求める。

## レーン完了

すべてのレーンについて、統合結果の検収、AWIの終端または保留への状態遷移、および計画ファイルの保存を完了させ、リソースを終了時の回収処理へ引き渡す。追加された処理対象WIは、元の選定結果へ反映された分のみを含める。公開工程へは、`references/finish-session.md`冒頭に定められた開始条件が成立した後に進む。
