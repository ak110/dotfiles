# レーンの実行

pickerが固定した集合を、選定結果のレーン割当と依存順に従って実行する。各レーンの同じ担当threadが、必要な計画の起草、実装、レビュー修正、履歴統合および主作業ツリーへの統合を担う。

## レーンと資源

レーンごとに専用branchと専用worktreeを1つ作成する。対象リポジトリの規範がworktreeの作成手順を定める場合は、その手順で作成し、返された作成先の絶対パスを記録する。手順がdetached HEADのworktreeを作成する場合は、そのworktreeで専用branchを作成する。対象の作成手順が無い場合は、レーン用のmanaged-tempを`atk managed-temp create --prefix <レーン識別子>`で作成し、専用worktreeをその直下のサブディレクトリへ作成する。`.git`を含むmanaged-temp直下の作業ディレクトリは自動削除の対象外であるため、「統合とAWI終端」が回収する。用途、作成先の絶対パス、managed-tempを作成した場合はそのパス、作成主体、所有主体、回収対象および専用branch名を記録する。対象リポジトリが定めるworktree前提ファイルとmise trustを準備する。

専用worktreeが検証に必要な環境をベース作業ツリーから引き継がない場合は対象リポジトリの開発手順が定める環境構築をworktreeの作成と同じ工程でバックグラウンドタスクとして開始する。作成主体はそのタスクの終了コードと出力を観測し、終了コード0と警告の不在を確認してからレーン担当を起動する。タスクは出力の全量をレーン用のmanaged-temp、作成しなかった場合はセッションのmanaged-tempのファイルへ保存し、環境構築コマンド自身の終了コードを保持する形で実行する。`tail`などへのパイプは末尾のコマンドの終了コードで元の失敗を覆い、残した末尾の行だけでは警告の不在を判定できない。完了を確定できない場合と失敗した場合は、レーン担当の委譲プロンプトへ環境構築を自ら実行する指示を渡す。その結果は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`環境構築`の項目でレーン担当へ渡す。

環境を構築する作成主体の書込みはレーン担当の起動前に終端する。レーン担当の稼働区間と重ねないことで、専用worktreeへ書き込む主体を1つに保つ。

同じレーンへ割り当てられたAWIはpickerの実装依存順を維持する。候補内の同一リポジトリの必要な依存は同じレーンへまとめ、依存先から処理する。計画を要するレーンは1つの計画へまとめる。計画の作成要否は`agent-toolkit:plan-mode`「計画ファイルの作成要否」で判定する。独立したレーンは別worktreeで並行できる。
依存先の失敗・保留や、選定後の上流投入による外部成果待ちで必要な成果を得られない場合は、後続を依存待ちとし、必要な成果の取得後に実装と完了判定へ進む。明示追加の依存先が既存レーンにある場合は、「処理中に確定した必須是正レーン」の受領可能性を確かめ、同じレーンが受領できない項目は待機する。

レーン工程の進行中に稼働レーンが1つになった時点では、そのまま続行する。そのレーンの未着手のAWIを新しいレーンへ移さない。
移す方式は計画ファイルの分割と書込所有権の移譲を要し、計画凍結（`agent-toolkit:plan-mode`の`references/plan-file-standards.md`）と両立しない。
単独稼働の区間は、選定工程が1レーンの見込みの上限を守ることで短くする。

レーン担当の起動前に`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`を全文読み、同書所定の入力を渡す。初回起動の各AWIの再開位置は選定結果から読む。担当全体の`再開位置`は中断した同じ担当の再開にだけ渡す。

## 上流投入

メインはレーン担当を起動する前に、pickerの`上流投入`が`なし`以外の全項目の上流投入を、`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`が定める上流投入の手順で委譲する。同書「起動方法」の単位に従い、同じ`元項目`の組を同じ投入担当へ渡す。起動、渡す入力（`元項目`と`投入条件`を含む）、検収は同書に従い、投入済みの上流項目は要求ごとの返却値`ファイル名`で識別する。レーンより先に投入するのは、`混在`の項目で上流へ渡した要求をレーン担当が計画の採用範囲から除くためである。

`上流要求だけ`（`レーン`が`なし`）の項目は投入結果に応じて次のとおり扱う。

- `completed`の要求がある場合: レーンを起こさず、全`ファイル名`を`atk wi set-dependencies`で元項目の`depends_on`へ加え、`atk wi return-to-inbox`で`inbox`へ戻す
- 全要求が`condition_not_met`の場合: 未実在の依存先を加えず、条件不成立を外部操作の観測結果として確認して元項目を終端する
- `needs_escalation`の要求がある場合: `add-wi.parent.md`「受領と検収」に従い、元項目の状態を変えず、続行できない理由の解消まで保留する

`混在`の項目では投入結果（要求、投入先、`ファイル名`、`結果`）を`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`上流投入結果`としてレーン担当の起動入力へ加える。レーン担当は投入済みの要求を計画の採用範囲から除く。`completed`の要求がある項目は、統合指示の`AWI終端区分`へ`終端しない`として渡して統合（ffマージ）の後も`adopt`の対象から外し、統合の検収後にメインが全`ファイル名`を元項目の`depends_on`へ加えて`inbox`へ戻す。全要求が`condition_not_met`の項目は通常のレーン終端を適用する。`needs_escalation`の要求を含む項目は、`add-wi.parent.md`「受領と検収」に従い、続行できない理由の解消まで元項目の状態を保ってレーンの起動を保留する。

## 処理中に確定した必須是正レーン

追加した処理対象WIは、`../SKILL.md`「即時対応」で確定したAWIと、ユーザーが明示したAWIとする。いずれも`${CLAUDE_PLUGIN_ROOT}/share/pick-wi.parent.md`「処理対象WIの追加」でpickerへ渡す。pickerが分類・処理開始・返却前の`pick-wi-check`を終えた追加出力をメインが検収し、本節の基準でレーン識別子を対応付ける。元の`選定結果の出力先ファイル`へ反映してからレーンへ渡す。未回答UWI、要求が未確定の項目および明示指示の無い新着項目は追加しない。ready一覧は再取得しない。

追加した処理対象WIごとに、変更するファイルと節（`書込対象`）、先行成果を入力にする実依存、既存レーンの残る工程と統合待ちを確認する。割当先は既存レーンの受領可能性と、既存レーンの工程境界まで待つ時間と新規レーンの準備費用の比較で決め、最初の処理対象WIと追加した処理対象WIの合計件数はその目安とする。合計が目安の10件未満では、現在工程後に同じthreadと資源で計画を作成できる既存レーンへの割当を通常の選択とする。書き込むファイルと節が異なる項目も工程境界で受領できる場合は既存レーンへ割り当てる。既存レーンが受領できない技術的条件を観測した場合は、その条件を示してユーザー確認する。処理中の追加には初回pickerの件数式に代えて、この合計件数と既存レーンの受領可能性を用いる。合計が目安の10件以上では、同じファイルと節に書き込むか実依存を持つ項目を、それらを所有する既存レーンへ割り当てる。独立した項目は既存レーンの工程境界まで待つ時間と新規レーンの準備を比べ、書込所有権を保てる場合は新規レーンで並行する。各項目の割当理由へ合計件数、実依存、待ち時間、現在工程および書込所有権の判定を記録する。
`選定結果の出力先ファイル`の割り当て先の`選定`へAWIを追加した時点で、現在工程の完了を待たずに、同じthreadへ開始まで含めた指示を1回送る。
指示は追加AWI名、継続する専用worktreeとbranch、継続する引き継ぎ記録先、AWI本文と`プロジェクト規範の指定`を`選定結果の出力先ファイル`から取得する指示を持ち、現在工程を置換せずに、その完了後にturnを終えず追加した処理対象WIの計画起草へ進むことを伝える。最初の工程境界の届け方は指示で指定せず、`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`がその形式に定める届け方に委ねる。メインの判断を待つ`計画作成完了`と`計画なし準備完了`は返却、非待機の`計画検査完了`は`atk agents notify`の通知であり、現在工程の結果はその本文の先頭に含まれる。返却を一律に求めると、非待機の境界でもレーン担当がturnを終え、次の指示まで実装が止まる。境界ごとに返却と開始指示を往復させると、同じ担当が続けて行える作業の着手が1往復ずつ遅れ、担当の再開費用も生じる。配送状態の意味と継続手段は`${CLAUDE_PLUGIN_ROOT}/skills/delegation/references/waiting-and-monitoring.md`に従う。
開始済みの判定は、追加した処理対象WIの最初の工程境界（`計画作成完了`、`計画なし準備完了`または`計画検査完了`など）の返却または通知の受領で行う。確定済みの既存計画は更新しない。
メインは最初の計画と追加計画の絶対パス、各計画のAWI集合、保存状態と工程の到達点をレーンの引き継ぎ記録へ順に累積する。工程境界の`計画ファイル`はその境界で作成した1件だけを示す。メインは同じレーンの通知を累積して、実行レビューと統合へ全計画を渡す。
追加した処理対象WIの最初の工程境界を受領する前にthreadが継続不能になった場合は、`agents_server`の公開応答から同じthreadを再開できるかを判定する。再開可能な場合は同じthreadへ指示を送り直し、再開不能な場合は書込所有権を確認して新しい是正レーンへ割り当てる。書き込むファイルと節が既存レーンと重なる新しいレーンは、そのレーンの現在の工程境界を受領する前に作成しない。

稼働中のレーンが無い場合、または書き込むファイルと節の所有者が追加項目を受領できない場合は、合計10件未満なら前段の確認を先に終える。その後、実依存と書き込むファイルと節でまとめた項目群ごとに専用branchと専用worktreeを持つ是正レーンを作成する。
実依存が無い新規レーンは、統合待ちがあっても計画と実装を直ちに開始する。`agent-toolkit:session-review`の稼働と`agent-toolkit:completion-report`の残る手順は、それ自体では是正レーンの開始を待たせる条件にしない。実依存があるレーンの開始と、全レーンの主作業ツリーへの統合だけを依存順および書込所有権に従って直列化する。

新規の追加レーンにも本書の計画、レビュー、失敗時の再開、AWI終端および資源回収の契約をそのまま適用する。追加したAWIとレーン割当は以後の処理対象WIとして保持する。

同じセッションで共有ツールまたは手順を修正し、残作業でその修正を使う稼働中レーンがある場合は、対象レーンへ通知する。通知は1回のメッセージへまとめる（努力目標。往復を減らすため）。通知には修正commit、実行時に変更を読み込む時機、再起動の要否および反映前の回避手順を含める。レーンの現行操作を維持し、そのツールまたは手順を使うレーンだけへ通知する。

## メインが読む対象の境界

メインは主にpickerの構造化出力、計画の`## 概要`と`## 実施内容`、レーン担当の工程境界出力、レビュー指摘管理表の状態、統合結果を読む（努力目標。メインのコンテキストを保護する）。統合結果の`変更したエージェント向け文書`の再取得は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従う。AWI本文、計画の他の節、実装差分は、エスカレーション、ユーザー介入またはレビュー収束判断で内容が必要になった場合に読む。

ユーザー介入のうち、処理対象WIへの包含理由、除外理由またはその構成を尋ねる質問は、`${CLAUDE_PLUGIN_ROOT}/share/pick-wi.parent.md`「選定理由への質問」の説明手順へ渡す。WI本文の調査はpicker説明担当が担い、メインは返された根拠と限界をユーザーへ伝える。

## 計画の起草と実装開始

計画あり・なしの準備結果と、待機を要する場合の`実装開始`または`実装なし`の返却は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「計画準備の受領」に従う。

## 採否の確定と終端区分

レーン担当は計画の起草時に要求単位の由来を判定する。人間由来の要求を全部または一部不採用にする場合は、その範囲、原文との差異、技術的理由、代替案を計画の確定前にメインへ即時報告し、メインがユーザーへ示して確認する。確認対象には、行全体の採否値に加えて部分採用の除外範囲も含める。回答を計画へ反映するまで`計画作成完了`を返さない。計画確定後の工程は由来を再判定せず、計画で確定した採否を用いる。確認が必要な不採用範囲がある場合は、依存しないレーンを進めながら採否を確定する。

回答を得られない場合は`agent-toolkit:wi-standards`に従ってUWIを登録し、`atk wi hold --state=processing <元AWIのファイル名>`で処理中の元AWIを保留する。そのUWIの本文へ、保留した元AWIのファイル名と対象の説明、必要な回答と回答で変わる結果を書く。回答後に再開する工程はユーザーの判断に使わないためUWIへ書かず、`atk run-script plan-progress --`で計画ファイルの`## 進捗ログ`へ確認事項と再開位置を記録して、`~/.claude/plans`に残す。計画の無いレーンでは引き継ぎ記録へ同じ内容を残す。採用または不採用としての確定は、回答を受け取ってから行う。同じprocess-wiの実行で回答を受け取った場合は、その回答を反映して同じレーンで採否を確定する。実装開始の送付前に受け取った回答はレーン担当が計画へ反映し、実装着手後に受け取った回答はレーン担当がレビュー指摘管理表へ記録する。実装着手後の計画ファイルは`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`が更新の対象から外している。

第2段として、各AWIを次の終端区分へ割り当てる。

- 採用した要求を実装し、完成条件を満たした項目: `adopt`
- 既存実装で要求と完成条件を満たすことを現物で確かめた項目: `adopt`
- 計画確定前の確認を含む必要な採否工程を終え、不採用と確定した項目: `reject`
- 回答を保存した事前承認型UWIと、その回答を反映して採否を確定した元AWI: 双方を`adopt`
- ユーザー回答を待つ項目: このprocess-wiの実行では終端せず`atk wi hold --state=processing <AWIのファイル名>`で保留する
- 外部状態または上流変更を待つ未実装の項目: このprocess-wiの実行では終端せず`inbox`へ戻す。実装と統合が済み、反映後の新プロセスによる観測だけが残る項目は`references/finish-session.md`「セッション終了」に従って`processing`で再開する

複数要求を持つAWIは、採用した要求を全て満たした場合に`adopt`する。ファイル全体を終端するのは、未解決の保留が残らない場合とする。固有指示が終端工程後のadoptを求める場合は延期対象とする。

## 実装とレビュー

`実装完了`の受領、実行レビューとユーザビリティレビュー（並列画面レビュー）の起動、指摘の修正の返送と収束は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「実装完了の受領」に従う。

メインはレーン担当から確認事項または事後承認の対象を受け取った時点で、`agent-toolkit:user-confirmation-and-report`と`agent-toolkit:wi-standards`に従って発行要否を判定する。発行対象は受領時に発行し、事後承認型UWIでは`atk wi add`の成功と、その出力が示す投入先のファイル名を保持して回答を待たず元の作業を続ける。レビュー収束後、受領した全対象について発行が完了し、事後承認型UWIごとに投入の成功と投入先のファイル名を確かめたことを確認してから統合へ進む。

## 統合とAWI終端

統合指示の前の確認（統合時の完成条件判定）と統合指示の送付は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従い、同じレーン担当threadへ統合指示を送る。

統合結果のOID、計画保存およびAWI終端を検収した後、レーン担当の終端と外部プロセスの終了を確認する。専用worktree、専用branch、作成した場合のレーン用managed-tempは、それらを入力とする全工程が完了してから、メインが「レーンと資源」で記録した値を使って次の手順で回収する。対象リポジトリの規範がworktreeの撤去手順を定める場合は、その手順を`git worktree remove`より前に実行する。レーン担当の作業ディレクトリは回収対象のworktreeの内側にあるため、回収はメインが自ら行う。

- `マージあり`: `git -C <統合先worktree> symbolic-ref --short HEAD`が統合先branchと一致することを確かめる。`git -C <対象リポジトリ> worktree remove <専用worktree>`を専用branchの削除より先に実行する。続けて`git -C <統合先worktree> merge-base --is-ancestor <専用branch> <統合先branch>`の終了コード0で到達を確認し、`git -C <統合先worktree> branch -D <専用branch>`で削除する。削除には到達確認を経た`-D`だけを使う。専用branchにupstreamが設定されている場合、`-d`はローカルのマージ先ではなくupstreamを基準に統合を判定し、push前の統合を未統合として拒否する。監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/process-wi/references/run-lanes.md「統合とAWI終端」：所有資源の回収：2026年9月3日」にある
- `マージなし`: 専用worktreeで`git status --porcelain=v1`の出力が空であり、`git symbolic-ref --short HEAD`が専用branch名であることを確かめる。続けて`git -C <対象リポジトリ> worktree remove <専用worktree>`を実行する。その後、`git -C <統合先worktree> merge-base --is-ancestor <専用branch> <統合先branch>`を実行する。終了コード0は専用branchが統合先branchに無いcommitを持たないことを示し、その場合だけ`git -C <統合先worktree> branch -D <専用branch>`で削除する。終了コードが0でない場合は専用branchを削除しない

worktreeとbranchの削除後、レーン用のmanaged-tempを作成した場合だけ`atk managed-temp cleanup --path <レーン用のmanaged-temp>`でそのディレクトリを削除する。削除の完了は各コマンドの終了コード0と成功の報告で判定する。確認結果が記録や期待と一致しない場合（到達確認の終了コードが0でない場合を含む）や削除に失敗した場合は、以降の資源を削除せず、期待値と観測値の差分と残存対象を`agent-toolkit:wi-standards`に従ってWIへ登録し、他のレーンを続ける。

## 中断レーンの再開

`processing`のまま残った項目では、計画を持つレーンはpickerが`atk plans list`と計画の`関連WI`から特定した`~/.claude/plans`内の計画ファイルを`再開位置`として使う。複数計画を持つ場合は引き継ぎ記録に累積した全計画、各AWI集合と進捗、保存状態を比べてから渡し、単数の計画名だけで再開工程を決めない。計画なしのレーンは引き継ぎ記録のAWI集合とレビュー指摘管理表に加え、`git merge-base <専用branch> <ベースbranch>`と`git log <その結果>..<専用branch>`から得た開始時点とcommitで再開工程を決め、`再開位置: 計画なし`として渡す。メインは計画ファイルまたは引き継ぎ記録の実在、AWI集合の一致および専用worktreeの所有主体が終端済みであることを確認する。

残存する専用worktreeとbranchが安全に再利用できる場合は、新しいレーン担当へ同じ絶対パス、branch、現在HEADおよび再開位置を渡す。再利用できない場合は、既存成果を失わない新しい専用worktreeを現在HEADから作成し、計画を持つレーンでは`atk run-script plan-progress --`で`## 進捗ログ`へ、計画なしのレーンでは引き継ぎ記録へ移行内容を記録する。未コミット差分の復元、破棄または別worktreeへの移送が必要な場合は独自に処理せずユーザー確認する。

## レーン完了

全レーンについて統合結果の検収、AWIの終端または保留への遷移、作成した計画の保存および資源回収を完了する。ユーザーの明示追加と即時対応の確定項目は、別のpicker出力を検収して`選定結果の出力先ファイル`へ追記した分だけを含める。監査担当を起動した場合はその処置を確定してから公開工程へ進む。
