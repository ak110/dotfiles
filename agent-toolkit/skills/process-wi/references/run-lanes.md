# レーンの実行

メインが固定した集合を、選定結果のレーン割当と依存順に従って実行する。各レーンの同じ担当threadが、必要な計画の起草、実装、レビュー修正、履歴統合および主作業ツリーへの統合を担う。

## レーンと資源

選定結果の`段階`を昇順に処理し、同じ段階の独立レーンを並行起動する。`先行レーン`を持つ後段では列挙した全レーンの統合完了を受領してから、統合先の現行HEADを基点にworktreeを作成する。先行レーンが未統合なら後段の作成と起動を待つ。単一段階の選定では、先行レーンの統合を待たずに全レーンを同時に作成して起動する。

レーンごとに専用branchと専用worktreeを1つ作成する。対象リポジトリの規範がworktreeの作成手順を定める場合は、その手順で作成し、返された作成先の絶対パスを記録する。手順がdetached HEADのworktreeを作成する場合は、そのworktreeで専用branchを作成する。対象の作成手順が無い場合は、レーン用のmanaged-tempを`atk managed-temp create --prefix <レーン識別子>`で作成し、専用worktreeをその直下のサブディレクトリへ作成する。`.git`を含むmanaged-temp直下の作業ディレクトリは自動削除の対象外であるため、「統合とAWI終端」が回収する。用途、作成先の絶対パス、managed-tempを作成した場合はそのパス、作成主体、所有主体、回収対象および専用branch名を記録する。対象リポジトリが定めるworktree前提ファイルとmise trustを準備する。資源の回収後もレーン識別子・担当thread・引き継ぎ記録と作成先の絶対パスを保持し、追加の再開に使う。

専用worktreeが検証に必要な環境をベース作業ツリーから引き継がない場合は対象リポジトリの開発手順が定める環境構築をworktreeの作成と同じ工程でバックグラウンドタスクとして開始する。作成主体はそのタスクの終了コードと出力を観測し、終了コード0と警告の不在を確認してからレーン担当を起動する。タスクは出力の全量をレーン用のmanaged-temp、作成しなかった場合はセッションのmanaged-tempのファイルへ保存し、環境構築コマンド自身の終了コードを保持する形（`tail`などへのパイプで失敗と警告を覆わない形）で実行する。完了を確定できない場合と失敗した場合は、レーン担当の委譲プロンプトへ環境構築を自ら実行する指示を渡す。その結果は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`環境構築`の項目でレーン担当へ渡す。

環境を構築する作成主体の書込みはレーン担当の起動前に終端する。レーン担当の稼働区間と重ねないことで、専用worktreeへ書き込む主体を1つに保つ。
メインは各レーンのレーン担当をprocess-wiの1回の実行で最初に起動した直後、そのsessionの`created_at`を時差付きの`レーン開始時刻`としてレーンの資源記録へ保存する。同じレーンを新しいsessionで再起動・置換してもこの値を変えない。統合指示では`exec.parent.md`の同名入力で渡す。最初の起動時刻を保持することで、置換前の稼働もレーンの見込みと比較できる。
取得には`atk agents list --include-terminated`を使い、起動結果の`session_id`と完全一致する項目の`created_at`を選ぶ。即時終端したsessionも一覧へ含め、詳細プロンプトの照会は不要とする。`started_at`はturnの開始時刻であり、初回起動の起点へ代用しない。

同じレーンへ割り当てられたAWIは選定結果の実装依存順を維持する。候補内の同一リポジトリの必要な依存は同じレーンへまとめ、依存先から処理する。計画を要するレーンは1つの計画へまとめ、単一の計画では行数の警告を避けられない初回だけ`references/lane-planning.md`「計画の起草」の手順4に従って複数の計画へ分ける。計画の作成要否は`agent-toolkit:plan-mode`「計画ファイルの作成要否」で判定する。独立したレーンは別worktreeで並行できる。
依存先の失敗・保留や、選定後の上流投入による外部成果待ちで必要な成果を得られない場合は、後続を依存待ちとし、必要な成果の取得後に実装と完了判定へ進む。明示追加の依存先が既存レーンにある場合は、「処理中に確定した必須是正レーン」の受領可能性を確かめ、同じレーンが受領できない項目は待機する。

レーン工程の進行中に稼働レーンが1つになった時点では、そのまま続行する。そのレーンの未着手のAWIを新しいレーンへ移さない。
移す方式は計画ファイルの分割と書込所有権の移譲を要し、計画凍結（`agent-toolkit:plan-mode`の`references/plan-file-standards.md`）と両立しない。
単独稼働の区間は、選定工程で1レーンの見込みと段階案を比較して短くする。書込の推移的な重なりだけで6000秒超過を不可避とせず、独立群の並行と先行統合後の後段開始を単一段階案と比較する。実依存・同じ再開計画の不可分性、全要求と品質確認、Claudeの利用上限時の待機方針を保つ。

レーン担当の起動では`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`所定の入力を渡す。同書を読む時点は`../SKILL.md`の読込表が定める。初回起動の各AWIの再開位置は選定結果から読む。担当全体の`再開位置`は中断した同じ担当の再開にだけ渡す。

レーン担当の起動では、選定結果の当該レーンの各WIの`担当モデル.実装担当`を`agent-toolkit:delegation`の`references/runtime-routing.md`「工程別モデル設定」の担当モデルの段落に従って`model_type`へ渡し、比べた結果を引き継ぎ記録へ残す。異なる指定があればWI名と値を示し、どれかを捨てて起動しない。

## 全初期通常レーン起動後の会話圧縮

Claude Codeでは、選定した全初期通常レーンの初回起動が完了した直後、待機へ入る前に会話を圧縮する。単一段階では全起動直後、複数段階では先行統合を経て最後の段階の全起動が完了した時点に限る。途中の段階、通常レーン0件、処理中の追加レーン、公開工程の待機は予約の対象から除く。Codexは予約の工程を省いて通常の待機へ進む。

この境界で、modが公開するツール`mcp__agent-toolkit__compact_conversation`が提供されているか確認する。modの実装は`${CLAUDE_PLUGIN_ROOT}/hooks/compact_conversation.ts`にある。ツールが提供される場合は、以下の手順で一度だけ予約する。提供されない環境は適用範囲外の実行前提とし、前提不成立である旨を進捗・引き継ぎ記録へ残す。そのうえで、圧縮せず通常の待機へ進む。

予約前に、既存の親引き継ぎ記録へ選定YAMLの絶対パス、段階、初回起動済みレーン集合、各session_id、専用worktreeとbranchの所有主体・回収対象、保持した最初のレーン開始時刻、各レーンの引き継ぎ記録、累積した計画集合と保存状態・工程の到達点を保存する。これらは既存の資源記録だけに保持する。

`instructions`には親引き継ぎ記録と選定YAMLの絶対パス、待機するsession_idを指定し、バックグラウンドタスクの完了通知でこれらの現物を読み、現在の工程から続行することを書く。受付と圧縮完了を区別する。予約後は対象を指定した既存の`atk agents wait`をClaude CodeのBashバックグラウンドタスクで起動し、前景の待機を省いて現在ターンを終える。待機の終了状態はバックグラウンドタスクの完了通知と保存した出力から確定する。この区間だけの待機方式とし、通常の待機には委譲の契約を使う。

通知後は同じレーンのsession_idと工程を復元して続行し、再選定と初回レーンの再起動を対象から除く。圧縮失敗の通知では保存した現物から工程を続行できるか判定する。予約の失敗と圧縮成功は別の結果として記録する。

## 上流投入

メインはレーン担当を起動する前に、選定結果の`上流投入`が`なし`以外の全項目の上流投入を、`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`が定める上流投入の手順で委譲する。同書「起動方法」の単位に従い、同じ`元項目`の組を同じ投入担当へ渡す。起動、渡す入力（`元項目`と`投入条件`を含む）、検収は同書に従い、投入済みの上流項目は要求ごとの返却値`ファイル名`で識別する。レーンより先に投入するのは、`混在`の項目で上流へ渡した要求をレーン担当が計画の採用範囲から除くためである。

`上流要求だけ`と`混在`のどちらの項目も、続行できない理由を返した要求がある場合は`add-wi.parent.md`「受領と検収」に従い、元項目の状態を変えず、続行できない理由の解消まで保留する（`混在`ではレーンの起動も保留する）。

`上流要求だけ`（`レーン`が`なし`）の項目は投入結果に応じて次のとおり扱う。

- `completed`の要求がある場合: レーンを起こさず、全`ファイル名`を`atk wi set-dependencies`で元項目の`depends_on`へ加え、`atk wi return-to-inbox`で`inbox`へ戻す
- 全要求が`condition_not_met`の場合: 未実在の依存先を加えず、条件不成立を外部操作の観測結果として確認して元項目を終端する

`混在`の項目では投入結果（要求、投入先、`ファイル名`、`結果`）を`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`上流投入結果`としてレーン担当の起動入力へ加える。レーン担当は投入済みの要求を計画の採用範囲から除く。`completed`の要求がある項目は、統合指示の`AWI終端区分`へ`終端しない`として渡して統合（ffマージ）の後も`adopt`の対象から外し、統合の検収後にメインが全`ファイル名`を元項目の`depends_on`へ加えて`inbox`へ戻す。全要求が`condition_not_met`の項目は通常のレーン終端を適用する。

## 処理中に確定した必須是正レーン

追加した処理対象WIは、`../SKILL.md`「即時対応」で確定したAWI、ユーザーが明示したAWI、ユーザーが処理中に告げた回答済みUWIとその元項目とする（判断は`selection-procedure.md`「処理対象WIの追加」）。メインが同節で分類と処理開始を行い、追加出力を検収する。本節の基準でレーン識別子を対応付け、元の`選定結果の出力先ファイル`へ反映してからレーンへ渡す。未回答UWI、要求が未確定の項目および明示指示の無い新着項目は追加しない。ready一覧は再取得しない。

追加項目は既存レーンへ割り当てる。上限と算定集合はselection-format.md「初回配分の算定根拠」を参照し、処理中の追加で新しい最終レーン名を作成しない。
既存レーンが0件の場合は、メインが上限と割当先の不足を続行できない理由として返す。

1. 変更するファイルと節、実依存、再開計画、既存レーンの残る工程と書込所有を確認する
2. 同じ再開計画を持つ既存レーンがある場合は、そのレーンへの割当を分割不能条件として費用比較より先に確定する。受領不能な技術的条件を観測した場合も、その計画を別レーンへ割り当てず、同じレーンの所有と再開を回復する判断へ進む
3. その他の項目は、実依存と書込所有を満たす既存レーンの工程境界で受領できるよう割り当てる。待ち時間と残る仕事量は既存レーン間の選択に使い、独立成分も同じレーンで順に扱う
4. 割当理由へ実依存・再開計画・待ち時間・現在工程・書込所有と、同じ実行で処理する順序を残す

メインはselection-procedure.md「処理対象WIの追加」の公開mergeで仮名を既存名へ対応付け、全体確認の終了コード0と保存成功を検収してから追加分を渡す。既存レーンへの合流先は未統合へ戻し、追加のないレーン・所属WI・初回情報を保持する。

割当先が統合済みで資源を回収済みなら、「レーンと資源」の記録から同じ絶対パスと専用branchの所有・存否を確認する。そのパスへ統合先の現行HEADから専用worktreeを再作成し、専用branchが削除済みなら同じ名前で作成する。既存の所有を確定できないbranchと、未回収の成果は保持して必要な回復判断を返す。環境準備の終了コード0と警告の不在を検収した後、保持した同じ担当threadと引き継ぎ記録へ追加指示を送る。

選定YAMLへ追加した時点で、現在工程の継続と、完了後にturnを終えず追加計画の起草へ進む指示を同じthreadへ送る。指示は追加WI名・専用worktreeとbranch・引き継ぎ記録・選定YAMLから本文と規範指定を取得する手順を持つ。割当を見直すためだけに稼働中の担当を中断しない。
工程境界の届け方は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`に従う。メインの判断を待つ計画境界は返却し、非待機の計画検査完了は通知して実装へ続ける。現在工程の結果は最初の追加工程境界の本文の先頭へ置く。
メインはその境界の受領で追加工程の開始を判定し、先行計画を凍結したまま追加計画とAWI集合・保存状態・進捗を順に累積してレビューと統合へ渡す。

同じthreadの再開が成立しない場合は、公開応答の事実・対象・不足する条件を続行できない理由として返し、同じレーンの回復判断を受ける。再開不能や全レーン統合済みを新しいレーン作成の例外にしない。追加後も計画・レビュー・統合・終端の既存手順を使う。

同じセッションで共有ツールまたは手順を修正し、残作業でその修正を使う稼働中レーンがある場合は、対象レーンへ通知する。通知は1回のメッセージへまとめる（努力目標。往復を減らすため）。通知には修正commit、実行時に変更を読み込む時機、再起動の要否および反映前の回避手順を含める。レーンの現行操作を維持し、そのツールまたは手順を使うレーンだけへ通知する。

## メインが読む対象の境界

メインは選定時に`selection-procedure.md`に従ってAWI・UWIの元本文を読み、分類と配分を意味検収する。その後は主に選定の構造化出力、計画の`## 概要`と`## 実施内容`、レーン担当の工程境界出力、レビュー指摘管理表の状態、統合結果を読む（努力目標。メインのコンテキストを保護する）。統合結果の`変更したエージェント向け文書`の再取得は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従う。計画の他の節と実装差分は、エスカレーション、ユーザー介入またはレビュー収束判断で内容が必要になった場合に読む。

ユーザー介入のうち、処理対象WIへの包含理由、除外理由またはその構成を尋ねる質問は、`${CLAUDE_PLUGIN_ROOT}/share/pick-wi-explain.parent.md`の説明手順へ渡す。WI本文の調査は選定理由の説明担当が担い、メインは返された根拠と限界をユーザーへ伝える。

## 採否の確定と終端区分

人間由来の要求を全部または一部不採用にする場合のレーン担当の判定と即時通知は`references/lane-planning.md`「計画の起草」が定める。メインはその通知で範囲、原文との差異、技術的理由、代替案を受け取り、ユーザーへ示して確認する。確認対象には、行全体の採否値に加えて部分採用の除外範囲も含める。計画確定後の工程は由来を再判定せず、計画で確定した採否を用いる。確認が必要な不採用範囲がある場合は、依存しないレーンを進めながら採否を確定する。

回答を得られない場合は`agent-toolkit:wi-standards`に従ってUWIを登録し、`atk wi hold --state=processing <元AWIのファイル名>`で処理中の元AWIを保留する。そのUWIの本文へ、保留した元AWIのファイル名と対象の説明、必要な回答と回答で変わる結果を書く。回答後に再開する工程はユーザーの判断に使わないためUWIへ書かず、`atk run-script plan-progress --`で計画ファイルの`## 進捗ログ`へ確認事項と再開位置を記録して、`~/.claude/plans`に残す。計画の無いレーンでは引き継ぎ記録へ同じ内容を残す。採用または不採用としての確定は、回答を受け取ってから行う。同じprocess-wiの実行で回答を受け取った場合は、その回答を反映して同じレーンで採否を確定する。実装開始の送付前に受け取った回答はレーン担当が計画へ反映し、実装着手後に受け取った回答はレーン担当がレビュー指摘管理表へ記録する。実装着手後の計画ファイルは`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`が更新の対象から外している。

第2段として、各AWIを次の終端区分へ割り当てる。

- 採用した要求を実装し、完成条件を満たした項目: `adopt`
- 既存実装で要求と完成条件を満たすことを現物で確かめた項目: `adopt`
- 計画確定前の確認を含む必要な採否工程を終え、不採用と確定した項目: `reject`
- 回答を保存した事前承認型UWIと、その回答を反映して採否を確定した元AWI: 双方を`adopt`
- ユーザー回答を待つ項目: このprocess-wiの実行では終端せず`atk wi hold --state=processing <AWIのファイル名>`で保留する
- 外部状態または上流変更を待つ未実装の項目: このprocess-wiの実行では終端せず`inbox`へ戻す
- 実装と統合が済み、反映後の完成条件の観測だけが残る項目: 延期`adopt`と観測のみの再開で行う反映後の観測の結果を、次の3つに分けて扱う。AWI本文への再開記録の追記、状態の変更と計画への記録は`references/finish-session.md`「延期adoptと反映後の観測」で行う
  - 観測が完成条件を満たす（残る完成条件を直接観測でき、その結果が完成条件を満たす）: `adopt`
  - 観測が完成条件を満たさない（残る完成条件を直接観測でき、その結果が完成条件を満たさない）: このprocess-wiの実行では`adopt`も既存の実装commitの上への再実装もせず、終端区分を`終端しない`とする。そのうえで、`再開区分: 再実装へ戻す`の再開記録を追記して、再処理抑制期限を付けずに`inbox`へ戻す。次回のprocess-wiが通常の項目として計画から着手する
  - 観測できなかった: このprocess-wiの実行では終端せず、メインが次の順に扱う
    1. レーン担当が返した観測結果（観測できなかった理由、欠けている前提、前提を妨げる状態の生成主体・起動元・起動契機と未確定の範囲）から、残る完成条件ごとに、エージェント自身、常駐機構、ユーザーの操作、追加認可のどれが前提を整えられるかを判定する。エージェント自身や常駐機構が生成した状態は、OS上の所有者が同じでもユーザーが起動した状態と区別し、生成主体が未確定の状態も、ユーザーだけが整えられる状態とは別に扱う。入力や稼働環境を通常は人が操作することは、ユーザーの操作と判定する根拠から外す。エージェント自身が入力を生成して観測できる手段（自分で起動した対話セッションへの入力送信を含む）が成立するかは、`references/finish-session.md`「延期adoptと反映後の観測」の自己観測の判定で確かめる
    2. 後続のprocess-wiでエージェントが前提を整えて観測できる項目（新しいプロセスの起動、反映の完了待ちなど）は、実装を繰り返さず次回の観測へ進める。観測できる最も早い時刻が先にある項目は再処理抑制期限を付けた`inbox`へ戻し、それ以外は`processing`を維持する
    3. ユーザーの操作または追加認可がなければ前提を整えられない項目（実行記録などでユーザーが起動したと確かめたセッションの停止、ユーザーだけが操作できる稼働環境での観測など）は、元AWIの完成条件を変えずに必要な操作と観測結果をUWIで求め、元AWIを`hold`へ移す。この項目は自己観測の判定で自己操作の手段が成立しないと確かめたものに限り、UWIには欠ける前提と自己操作が成立しない根拠も書く。同じ観測を次回のレーンへ繰り返し渡すと、前提が成立しないまま処理だけが反復する

複数要求を持つAWIは、採用した要求を全て満たした場合に`adopt`する。ファイル全体を終端するのは、未解決の保留が残らない場合とする。固有指示が終端工程後のadoptを求める項目と、版数更新を完成条件に持つ項目（レーン数によらない）は延期対象とする。

## 実装とレビュー

計画あり・なしの準備結果と、待機を要する場合の`実装開始`または`実装なし`の返却は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「計画準備の受領」に従う。

選定結果の担当モデル、起動側が解決した候補、終端後の物理記録から観測した実行identityを別の値として比較し、一致を確認する。不一致は値と由来を区別して引き継ぎへ残す。観測不能は未観測として引き継ぐ。

`実装完了`の受領、実行レビューとユーザビリティレビュー（並列画面レビュー）の起動、指摘の修正の返送と収束は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「実装完了の受領」に従う。

メインはレーン担当から確認事項または事後承認の対象を受け取った時点で、根拠と既存認可を検収し、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」と`agent-toolkit:wi-standards`に従って発行要否を判定する。確認不要と確定した技術判断は報告へ振り分け、発行対象だけを直ちに発行する。事後承認型UWIでは`atk wi add`の成功と投入先のファイル名を保持して回答を待たず続ける。レビュー収束後、全受領事項の判定と必要な発行を完了し、必要な事後承認型UWIごとの投入成功とファイル名を検収して統合へ進む。確認不要の報告にUWIの未発行を理由とする統合待ちを設けない。

## 統合とAWI終端

統合指示の前の確認は`agent-toolkit:review-standards`の`references/exec-review-recording.md`「統合時の完成条件判定」に従う。統合指示は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従って同じレーン担当threadへ送る。

統合結果のOID、計画保存およびAWI終端を検収した後、レーン担当の終端と外部プロセスの終了を確認する。専用worktree、専用branch、作成した場合のレーン用managed-tempは、それらを入力とする全工程が完了してから、メインが「レーンと資源」で記録した値を使って次の手順で回収する。対象リポジトリの規範がworktreeの撤去手順を定める場合は、その手順を`git worktree remove`より前に実行する。資源を回収しても、レーン識別子・同じ担当thread・引き継ぎ記録は保持し、追加を受ける場合は「処理中に確定した必須是正レーン」の再作成と再開へ進む。レーン担当の作業ディレクトリは回収対象のworktreeの内側にあるため、回収はメインが自ら行う。
メインはこの検収と終端確認の後、資源回収・追加選定の前に、次の公開操作で選定YAMLの統合状態を保存する。実装完了や統合指示の送付の時点では未統合として保持する。

```text
atk run-script pick-wi-check -- <選定YAML> --mark-integrated <レーン識別子> --output <同じ選定YAML> --work-dir <対象リポジトリの絶対パス>
```

複数の検収済みレーンは`--mark-integrated`を反復して指定できる。同じレーンへの記録も反復できる。状態記録とmergeは別々に実行する。全体検査の成功後だけ原子的に保存され、未知レーン・入力不備・内容違反では保存先を保持する。終了コード0と保存成功を検収して既存の親引き継ぎへ記録し、非0では診断した入力を修正して同じ操作を再実行する。完了レーンと所属WIを履歴として保持したまま、状態に応じて重なりを判定する。

- `マージあり`: `git -C <統合先worktree> symbolic-ref --short HEAD`が統合先branchと一致することを確かめる。`git -C <対象リポジトリ> worktree remove <専用worktree>`を専用branchの削除より先に実行する。続けて`git -C <統合先worktree> merge-base --is-ancestor <専用branch> <統合先branch>`の終了コード0で到達を確認し、`git -C <統合先worktree> branch -D <専用branch>`で削除する。削除には到達確認を経た`-D`だけを使う。専用branchにupstreamが設定されている場合、`-d`はローカルのマージ先ではなくupstreamを基準に統合を判定し、push前の統合を未統合として拒否する。監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/process-wi/references/run-lanes.md「統合とAWI終端」：所有資源の回収：2026年9月3日」にある
- `マージなし`: 専用worktreeで`git status --porcelain=v1`の出力が空であり、`git symbolic-ref --short HEAD`が専用branch名であることを確かめる。続けて`git -C <対象リポジトリ> worktree remove <専用worktree>`を実行する。その後、`git -C <統合先worktree> merge-base --is-ancestor <専用branch> <統合先branch>`を実行する。終了コード0は専用branchが統合先branchに無いcommitを持たないことを示し、その場合だけ`git -C <統合先worktree> branch -D <専用branch>`で削除する。終了コードが0でない場合は専用branchを削除しない

worktreeとbranchの削除後、レーン用のmanaged-tempを作成した場合だけ`atk managed-temp cleanup --path <レーン用のmanaged-temp>`でそのディレクトリを削除する。削除の完了は各コマンドの終了コード0と成功の報告で判定する。確認結果が記録や期待と一致しない場合（到達確認の終了コードが0でない場合を含む）や削除に失敗した場合は、以降の資源を削除せず、期待値と観測値の差分と残存対象を`agent-toolkit:wi-standards`に従ってWIへ登録し、他のレーンを続ける。

## 中断レーンの再開

`processing`のまま残った項目では、計画を持つレーンはメインが`atk plans list`と計画の`関連WI`から特定した`~/.claude/plans`内の計画ファイルを`再開位置`として使う。複数計画を持つ場合は引き継ぎ記録に累積した全計画、各AWI集合と進捗、保存状態を比べてから渡し、単数の計画名だけで再開工程を決めない。計画なしのレーンは引き継ぎ記録のAWI集合とレビュー指摘管理表に加え、`git merge-base <専用branch> <ベースbranch>`と`git log <その結果>..<専用branch>`から得た開始時点とcommitで再開工程を決め、`再開位置: 計画なし`として渡す。メインは計画ファイルまたは引き継ぎ記録の実在、AWI集合の一致および専用worktreeの所有主体が終端済みであることを確認する。
反映後の観測だけが残る項目は、中断ではなく`references/finish-session.md`「延期adoptと反映後の観測」がAWI本文へ追記した再開記録から再開する。メインが保存した観測のみの再開位置を選定結果のままレーン担当へ渡し、レーン担当は`references/lane-planning.md`の観測のみの再開に従って、計画の有無によらず再実装せず観測だけを行う。

残存する専用worktreeとbranchが安全に再利用できる場合は、新しいレーン担当へ同じ絶対パス、branch、現在HEADおよび再開位置を渡す。再利用できない場合は、既存成果を失わない新しい専用worktreeを現在HEADから作成し、計画を持つレーンでは`atk run-script plan-progress --`で`## 進捗ログ`へ、計画なしのレーンでは引き継ぎ記録へ移行内容を記録する。未コミット差分も所有と現物を確かめ、権限内で成果を失わない復元・移送は自ら確定する。他者・ユーザーの差分の破棄や、所有を確定できない成果の損失につながる処置は、共通の確認要否判定で必要な認可を求める。

## レーン完了

全レーンについて統合結果の検収、AWIの終端・保留への遷移、作成した計画の保存および資源回収を完了する。ユーザーの明示追加、ユーザーが告げた項目と即時対応の確定項目は、メインが初期集合へ合流または追加選定し、検収して元の`選定結果の出力先ファイル`へ反映した分だけを含める。公開工程へは`references/finish-session.md`冒頭の開始条件が成立してから進む。
