# レーンの計画から後始末

②の開始時に、①の出力を確定したprocess-wiのメインがこの文書を全文読み、計画、実装、マージ、`adopt`及び所有資源の後始末へ適用する。
この文書はレーン内の責務境界を定義し、①で固定したprocessableなready項目の全体選定を再実行しない。
②の入力となる項目は①で全て`processing`へ移っているため、レーンは`start-processing`を再実行しない。
レーンは作業対象リポジトリのpushとCIを実行せず、全レーン後の③へ結果を返す。
`atk`がキュー管理リポジトリへ行う反映はこの制限の対象外であり、レーンはキュー操作で当該反映を抑止しない。

## レーンと資源

1つの計画ファイルを1レーンとし、各レーンへ専用managed-tempと専用git worktreeを作成する。
異なるレーンは、ファイルの重複にかかわらず独立して起動できる。

メインは②のレーンを起動する前に、`upstream_submission`が`なし`以外の項目について、pickerが返した`upstream_target_repo`と`upstream_request`を用いて上流リポジトリへフィードバックを投入する。投入は項目ごとに1回とし、投入先のファイル名を保持する。`上流要求だけ`の項目はレーンを起こさず、投入先のファイル名を元項目の`depends_on`へ加えて`inbox`へ戻して終える。`混在`の項目は投入を終えてから、対象リポジトリで実施できる要求だけをpickerが確定した区分のレーンへ渡す。投入先か要求が欠ける場合と投入に失敗した場合は、当該項目のレーンを起動せず、元項目の状態を変更しない。

レーンのフィードバックファイル名一覧は、pickerが確定した実装依存順を変更せずに渡す。確認・保留事項と固有の終端順序も同じ対応を維持する。`upstream_submission`が`混在`の項目では、上流へ投入済みの要求と対象リポジトリ側で計画する要求の対応も、既存のレーン入力として計画担当へ渡す。0件のレーンは起動せず、1件以上のレーンだけを計画又は実装へ渡す。
レーンの計画担当と実装担当へは、ファイル名、計画ファイルの絶対パスと再開位置を渡す。各担当は自らの契約に従って正本を直接読み、メインによる本文の要約を入力の代替にしない。
専用managed-tempと専用worktreeの絶対パス、所有主体、作成目的及び回収可否に加え、専用branch名、対象リポジトリの絶対パス及び専用worktree作成時のHEAD完全OIDをレーンの入力へ記録する。
計画メタ情報の`対象リポジトリ`へ記載する絶対パスは、当該レーンの専用worktreeの絶対パスとする。計画構造検査は同じGitリポジトリの別作業ツリーを対象リポジトリの代用として受理しないため、複製元のリポジトリルートを記載しない。

専用worktreeを作成した時点で、当該worktreeでの検査実行に必要な実行前提を呼び出し元がまとめて整える。
少なくとも、ツール管理器による設定の信頼登録を対象とする。
登録は複製元のリポジトリルートへ1回行い、複製元への登録が当該worktreeへも及ぶことを当該ツールの公式仕様又は実測で確認する。
及ばない場合だけ、当該worktreeの対象を直接登録する。
信頼するパス等を列挙する環境変数は、既存の登録を置換して複製元を対象から外す動作を持つ場合があるため、置換しないことを確認できるまで解消手段に用いない。
同じ前提を各レーンの委譲先が個別に整える手順は、レーンの起動文へ含めない。

メインは、計画ファイル（詳細）の`### 主作業ツリー前処理`に`該当なし`以外の行がある場合、当該レーンの専用worktreeを作成する前に、主作業ツリーで当該前処理を1回実行する。
前処理を専用worktreeの実装単位へ割り当てず、実装担当へ実行を指示しない。
実行の直前に`git -C <主作業ツリーの絶対パス> status --porcelain=v1`を実行し、出力が挙げるパスを既存の差分として記録する。
実行前に当該前処理が変更するパスの集合を確定できる場合は、既存の差分と当該集合が交差しないことを確認してから実行する。確定できる場合とは、`### 主作業ツリー前処理`の`前処理`欄が変更するパスを列挙している場合と、実行するコマンドが変更対象を列挙する試行実行の手段を持つ場合とする。
交差するパスが1件でもある場合は前処理を実行せず、当該行の`失敗時に遮断する実装単位`が挙げる実装単位を遮断し、交差したパスと観測した出力を`agent-toolkit:wi-standards`に従って登録する。
実行前に当該集合を確定できない前処理では、staged、unstaged及びnon-ignored untrackedが全て空であることを確認し、空でない場合は前処理を実行せず、同じ手順で遮断して登録する。変更するパスを特定できない場合、同じパスへ既存の差分と前処理のいずれが作用したかを変更の有無だけでは識別できないためである。
前処理が成功した場合は、生成された差分をメインが検収し、レーンの専用worktreeへ持ち込まない。
前処理が失敗した場合は、交差しないことを確認した経路では当該前処理が変更するパスを、cleanであることを確認した経路では`git -C <主作業ツリーの絶対パス> status --porcelain=v1`が返す全てのパスを、当該前処理の生成物として扱う。
追跡対象のパスを`git -C <主作業ツリーの絶対パス> checkout -- <パス>`で復元し、未追跡のパスを削除する。
復元又は削除が失敗したパスがある場合は、以降の復元を中止し、当該パスと観測値を失敗の観測値へ含める。
前処理の失敗では、当該行の`失敗時に遮断する実装単位`が挙げる実装単位だけを遮断し、他の実装単位を持つレーンは起動する。
遮断した実装単位、失敗の観測値及び復元できなかったパスを`agent-toolkit:wi-standards`に従って登録する。

## 通常型の計画

通常型の各レーンでは、メインが`plan_model`で計画担当を起動し、`plan_review_model`で独立した計画レビュー担当を起動する。
起動入力と収束判定は`${CLAUDE_PLUGIN_ROOT}/share/plan-review.parent.md`と`${CLAUDE_PLUGIN_ROOT}/share/plan-drafting.parent.md`を正本とする。
計画初稿とレビュー指摘反映は同じ計画担当threadへ返す。
メインは計画担当へ当該レーンのフィードバックだけを渡し、要求単位の由来と確認結果を添えて採用要求を計画へ記録させる。
渡す由来は人間由来とエージェント由来のいずれかへ確定した値とし、`フィードバック`のような区分を伴わない値を渡さない。確定は`agent-toolkit:wi-standards`の「由来と承認」に従う。
`upstream_submission`が`混在`の項目では、上流へ投入済みの要求と対象リポジトリ側で計画する要求の対応も渡す。計画担当はこの対応を元フィードバックの要求単位へ照合し、上流へ投入済みの要求を対象リポジトリ側の実施内容へ含めない。
計画中にユーザー判断が必要になった場合、計画担当は`needs_escalation`でメインへ返す。メインの回答又は同一セッションで回答されたTBDを受領した後、一般的な同一担当継続条件を満たす同じ計画担当threadから再開する。
採用取りやめはメインがキュー終端を確定し、不要な実装工程へ進めない。
計画レビューの各ラウンドの受領は`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`に従う。

既存計画のフィードバックは計画と計画レビューを繰り返さず、1計画1レーンとして並列に起動する。
既存計画のレーンでは、メインが実装工程へ着手する前に`agent-toolkit:plan-mode`の計画ファイル基準の`## 計画ファイルの保存と参照`が定める取得を1回実行し、当該計画を作業rootへ置く。キュー項目と計画の対応はキューmetadataの`plan_file`が保持するため、取得した計画をそのまま同じレーンの実装へ渡す。
計画担当は計画完了後の実装、実装レビュー、マージ及びキュー終端を担当しない。

計画担当は、対象実装を読解した調査結果を計画の`## 実施内容`へ原則1フィードバックファイル1行で統合し、フィードバック行ごとの採否と根拠を確定する。
計画担当が調査の結果として担当フィードバックの全ての要求を既存commit又は既存実装で充足済みと確定した場合も、要求別の行へ分割せず、担当フィードバックごとの行を`充足済み`とする。
1つのフィードバックで複数の採否が混在する場合は、当該フィードバック行を`部分採用`とする。
同じ行の`実施内容`へ実施する範囲を書き、`根拠`へ実施しない範囲と理由を書く。
充足済みの範囲を含む場合は、`根拠`へ充足を確認した実装箇所・コミットのいずれかと裏付け手段も書く。
`根拠`の具体的な記載規則は`agent-toolkit:plan-mode`の計画ファイル基準を正本とする。
計画レビューは、`充足済み`のフィードバック行について、`根拠`が挙げる実装箇所・コミットの実在を検証する。
要求が挙げる全ての対応案との突合も検証し、裏付け不足があれば収束させない。
充足済みの範囲を含む`部分採用`のフィードバック行では、充足の根拠を同じ方法で検証する。
充足済みの範囲と残る実施範囲を、当該行の`実施内容`と`根拠`により判別できることも確認する。
計画レビュー完了後、メインは、計画レビューが検証したフィードバック由来の各行を受領する。
メインは対象実装を再読解せず、この検証済みの行だけを後続工程の入力に用いる。

第1段へ進む前に、メインは各フィードバック行に記録された採否ごとの範囲と由来を確認する。
計画の`由来`欄をそのまま信頼せず、正本を`atk mq show`で取得し、`source`の有無と`agent-toolkit:wi-standards`の「由来と承認」が列挙する4種の明示由来の有無へ照合して、人間由来かどうかを確定する。明示由来は種類ごとに本文を確認し、`## ユーザーコメント`の見出しの有無だけで判定しない。
人間由来のフィードバックに不採用の範囲が1件でも含まれる場合は、行全体の採否値と最終的なキュー操作にかかわらず、当該範囲、原文との差異、技術的理由及び代替案をユーザーへ示して確認する。
確認を発行する前に他のレーンへ返す指示は、`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`の`## ラウンドの遷移`が定める。
確認を得るまで、計画証拠を確定せず、当該フィードバックのキュー終端へ進まない。
ユーザーが不採用に同意しない場合は、回答を計画担当へ返して計画と計画レビューを再開する。
回答を得られない場合の扱いは、`agent-toolkit:wi-standards`に従う。
回答を得られないまま当該レーンを終える場合は、確認を得るまでキュー終端へ進まないとする前段の制約に代えて、次の手順を適用する。
採用する実施範囲を持つ行について、実装、単一の実装レビュー、ffマージの順に完了する。
続いて、確認を得られない不採用の範囲だけを内容とする新しいフィードバックを、当該範囲について保存したTBDのファイル名を`atk mq add`の`--depends-on`へ渡して登録する。
元のフィードバック行は、採用済みの範囲を持つため第2段の規則で1回だけ`adopt`して終端する。
新しい項目は計画ファイルを持たないため、次の処理回では新しい実装変更として扱われ、ffマージ済みの計画が再び実装されることはない。
同じレーンの他のフィードバック行は、確認待ちの行と独立に第2段の規則で終端する。
所有資源は「後始末と非実装項目」のffマージを実行したレーンの手順で回収し、レーンは完了報告を返す。
採用する実施範囲と採用済みの範囲をいずれも持たない行だけが残る場合は、実装、実装レビュー並びにffマージを行わない。
この場合は`agent-toolkit:wi-standards`に従って暫定的に`rejected`へ終端し、採用する実施範囲がなくマージを実行しないレーンの手順で所有資源を回収する。
計画担当又は計画レビュー担当の起動前の検査で、plugin root配下の資源が実在しないことを検知した場合は、当該担当を起動しない。`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`の`## エスカレーションの事由別の扱い`が定める`plugin資源不在`の行に従って扱う。当該レーンを終端した項目は、常駐する`atk mq process-loop`が次のセッションで再選定する。再選定したセッションは、自身が解決する現行のrootで、同じ表が求める再開位置から計画工程を実行する。

第1段では、`## 実施内容`に採用する実施範囲を持つフィードバック行が1行以上あるかだけを判定する。
該当する行がある場合だけ通常型フィードバックを計画型へ変換し、当該計画を同じレーンの実装工程へ渡して、その実施範囲を実装する。
該当する行がない場合は、実装、実装レビュー及びマージを行わず、実装担当を起動しない。
この場合、メインは確定した計画、付属素材、計画レビュー表を`atk plans commit <計画作業root直下のメイン計画ファイル名>`で保存し、保存実体と作業側の消失を確認する。

第2段では、実装工程の実施有無にかかわらず、計画レビューが検証した採否に従って各フィードバック行を独立に終端する。
採用済みの範囲を持つ行は、当該フィードバックを1回だけ`adopt`で終端する。
採用する実施範囲を持つ行では、その範囲の実装を含むffマージが成功した後のベースHEAD完全OIDを用いる。
採用する実施範囲を持たない採用済み範囲は、計画に記録された対象commitと要求の充足を同じ裏付け手段で実測し、対象commitの完全OIDを用いる。
この規則は`充足済み`の行と、新規実装を持たず充足済みの採用範囲を含む`部分採用`の行に適用する。
それぞれ`atk mq adopt <filename> --commit=<確定した完全OID>`を実行する。
採用済みの範囲を持たない`不採用`の行は、メインが`atk mq reject <filename>`で終端する。
人間由来の不採用範囲について確認を得た行も、採用済みの範囲があれば1回の`adopt`へ、採用済みの範囲がなければ`reject`へ接続する。
各操作後に保存結果を照合し、全てのフィードバック行を終端してから「後始末と非実装項目」へ進む。

## 実装とレビュー

メインは、同じ計画ファイルへ書き込む計画担当の終端を確認してから実装担当を起動し、次を渡す。

- 計画ファイル（メイン・詳細）、プロジェクト規範、作成規範スキル及びタスク文書の絶対パス
- レーン専用worktree及びレーンmanaged-tempの絶対パス
- pickerが確定した順序を保持したフィードバックファイル名一覧
- フィードバック固有の処理順、公開、確認又は検証指示
- 複製元、対象外worktree、commit可、ffマージ可、所有資源の回収可、作業対象リポジトリへのpush不可という権限。`agent-toolkit/rules/02-agent-operations.md`「対象リポジトリとキュー管理リポジトリの区別」節のとおり、`atk`がキュー管理リポジトリへ行う反映は当該権限の対象外である旨も渡す

計画レビューの指摘管理表は渡さない。同表は計画の確定までに用いる記録であり、実装担当の入力ではない。
実装担当が扱うのは実装レビューの指摘管理表だけとし、その受領条件は`${CLAUDE_PLUGIN_ROOT}/share/implementation.subagent.md`が定める。
計画レビューの経緯が必要になる事象が生じた場合だけ、当該事象を示して同表の絶対パスを追送する。

メインは依存先計画が導入する単一の実装レビュー担当を使う。
メイン自身による直接実装、レビュー省略、全体レビューへの責任移管をしない。
同じレーンの実装単位は依存順に同じ専用worktreeで実装し、同時に1つの実装担当だけを置く。
担当範囲の未commitの変更が残らないことを実装担当が完了値の返却前に確認する手順は、`${CLAUDE_PLUGIN_ROOT}/share/implementation.subagent.md`が定める。
実装工程へ進む計画は、計画レビューの収束時点ではprivate-notesへ移動又はcommitしない。後続のセッションで実装する計画は本項の対象外とし、保存の契機は当該計画を作成した経路が定める。

実装レビューの各ラウンドの受領は`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`に従う。
レビュー表の行数を監視へ追加する仕組み、受領済み行数、次回比較、未着是正メッセージを用いない。無進行は一般的な待機と観測の契約で扱う。

認可範囲外、前提差異、ユーザー判断が生じた場合、実装担当は`needs_escalation`でメインへ返す。
受領した事象は`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`の`## エスカレーションの事由別の扱い`が定める区分へ対応付けて扱う。
メインが判断した後、同じtask・実効`engine`・`model`・`effort`が成立する同じ実装担当threadへ指示を返す。
route変更、識別子消失又は前提無効時だけ一般的な継続契約に従って新規起動する。
ユーザーの選好に依存する判断は`agent-toolkit/rules/01-agent.md`「協調と自律」の確認経路へ送る。

## マージとadopt

メインは実装レビューの収束を`${CLAUDE_PLUGIN_ROOT}/share/review-loop-coordination.md`に従って確定した後、1レーンずつマージ許可を与え、許可中は他レーンのベース更新を許可しない。
許可を与える前に、`${CLAUDE_PLUGIN_ROOT}/share/implementation-review.parent.md`の「実装レビュー後の計画最終化」を完了する。
許可メッセージには、マージ先worktreeの絶対パス、マージ先branch名及び今回のレーンへ入っている計画ファイルの絶対パス一覧を含める。マージ先HEAD完全OIDは渡さない。
与えた許可は当該レーンが`統合完了`を返すまで有効であり、rebase競合と再レビューを経た後も同じ許可でffマージまで進む。同じ収束に対して同じレーンへ同じ許可を再送しない。

許可を受領した最後の作業担当は最新のベースtipへrebaseする。競合解消が実装差分を生んだ場合は同じ担当がレビュー指摘管理表へ競合と解消結果を記録し、
単一の実装レビューを再度完了してからffマージへ進む。競合解消のためだけの別レビュー又は統合差分レビューを使わない。

最後の作業担当はベースbranchへ`--ff-only`でマージする。
成功後のベースHEAD完全OIDを取得し、固有の延期指示がなく、`upstream_submission`が`混在`でないフィードバック行を第2段の規則で1件ずつ終端して保存結果を照合する。

メインは`統合完了`とともに受領した`merged_head`、`adopted`及び`released`を次のとおり照合する。いずれかが一致しない場合は同じ実装担当へ差し戻し、成果物と実装差分の再読解は行わない。

- `git -C <マージ先worktreeの絶対パス> rev-parse <マージ先branch名>`の出力が`merged_head`と一致する
- `adopted`が挙げるファイル名の集合が、当該レーンへ渡したフィードバックのうち固有の延期指示を受領したものと`upstream_submission`が`混在`のものを除いた集合と、過不足なく一致する。一致を確認した各ファイル名が、`atk mq list --target-repo=<対象リポジトリ> --status=adopted --skip-pull --json`の出力へ`filename`として現れる
- `released`が挙げる資源の集合が、起動時に当該レーンへ記録した所有worktree、所有branch及びレーンmanaged-tempの集合と、過不足なく一致する。一致を確認した所有worktreeと所有branchが、`git -C <マージ先worktreeの絶対パス> worktree list`と`git -C <マージ先worktreeの絶対パス> branch --list <所有branch名>`の出力へ現れない。一致を確認したレーンmanaged-tempについて、`test ! -e <当該managed-tempの絶対パス>`が終了コード0を返す

件数の一致だけでは、別の項目を終端した報告と所有資源を列挙から省いた報告を区別できないため、集合の一致を先に確認してから各要素の実状態を照合する。
各要素の照合は、当該操作の公開契約が定める終了状態を直接観測して行う。`adopted`は`atk mq adopt`の終了状態が`adopted`への移動であるため当該状態への存在を観測し、`released`は資源回収の終了状態が資源の消失であるため当該消失を観測する。`processing`に現れないことは、`inbox`・`hold`・`rejected`への移動と未終端を区別しないため用いない。
照合はいずれもコマンド1回で判定でき、成果物と実装差分の再読解を伴わない。メインは成果物、Git状態、検証結果及びレビュー表を完了報告の再検収目的で読み直さない。

`upstream_submission`が`混在`の項目は`adopt`しない。レーンはffマージ後に所有資源を回収して既存の完了報告を返す。メインは完了報告を受領した後、投入先のファイル名を元項目の`depends_on`へ加え、`atk mq return-to-inbox`で`inbox`へ戻す。再着手は次の処理回とする。

固有指示が`adopt`をPR又はMRのマージ、release又は配布後へ明示的に延期する場合だけ、ベースHEAD完全OIDと未完了の固有順序を③へ渡す。
レーンを完了扱いにせず、実装に使ったbranch、worktree及びレーンmanaged-tempを再利用しない。
レーンがffマージ後に自身の所有記録と対象を読み取り専用で照合して回収し、③で先行工程が成功した後、同じレーン責務として`adopt`と保存結果を照合して完了する。

## 後始末と非実装項目

各フィードバック行の終端後、又は`upstream_submission`が`混在`のレーンのffマージ後に、次のレーン種別に対応する手順で、自身の所有を記録したbranch、worktree及びレーンmanaged-tempだけを読み取り専用で照合して削除する。

- ffマージを実行したレーンは、マージを実行した作業ツリーの絶対パスとマージ先branch名を後始末まで保持する。branchの削除の直前に、`git -C <保持した作業ツリーの絶対パス> symbolic-ref --short HEAD`の出力が保持したマージ先branch名と一致することを照合する。一致した場合だけ、先に`git -C <記録した対象リポジトリの絶対パス> worktree remove <記録した所有worktreeの絶対パス>`で専用worktreeを削除する。Gitは所有branchをcheckoutしている専用worktreeが存在する間は当該branchを削除しないため、worktreeの削除をbranchの削除より先に行う。続けて`git -C <保持した作業ツリーの絶対パス> branch -d <所有branch名>`を実行する。`git branch -d`は、対象branchにupstreamが設定されている場合、実行した作業ツリーが指すbranchではなくupstreamを統合判定の基準にする。所有branchのupstreamがマージ先branchのリモート追跡refを指し、当該refがマージ済みのローカルcommitをまだ含まない間は、正しい作業ツリーと正しい現在branchで実行しても削除が拒否される。拒否された場合は、`git -C <保持した作業ツリーの絶対パス> merge-base --is-ancestor <所有branch名> <保持したマージ先branch名>`を実行する。終了コードが0で所有branchがマージ先branchへ到達済みである場合だけ、`git -C <保持した作業ツリーの絶対パス> branch -D <所有branch名>`で削除する。一致しない場合、worktreeの削除が失敗した場合、到達確認の終了コードが0以外の場合及び`-D`による削除が失敗した場合は以降を削除せず、保持した絶対パス、期待するマージ先branch名及び観測した出力を`needs_escalation`で返す。upstreamを統合判定の基準にする挙動は、2026年9月3日にgit version 2.43.0で、upstreamに`origin/develop`を設定した専用branchをローカルの`develop`へff統合した直後に`branch -d`が未統合として拒否されることを実測した。再検証は`git branch -vv`で対象branchの追跡先を確認したうえで、同じ状態の`branch -d`の終了コードを観測する。
- 採用する実施範囲がなくマージを実行しないレーンは、メインが`git -C <記録した所有worktreeの絶対パス> status --porcelain=v1`の出力が空であることを照合する。続いて、`git -C <記録した所有worktreeの絶対パス> symbolic-ref --short HEAD`が記録した専用branch名と一致することを照合する。`git -C <記録した所有worktreeの絶対パス> rev-parse HEAD`が専用worktree作成時のHEAD完全OIDと一致することも照合する。全て一致した場合だけ、`git -C <記録した対象リポジトリの絶対パス> worktree remove <所有worktreeの絶対パス>`でworktreeを削除する。次に`git -C <記録した対象リポジトリの絶対パス> update-ref -d refs/heads/<所有branch名> <専用worktree作成時のHEAD完全OID>`を実行する。これにより、期待OIDから更新されていない所有branchだけを削除する。いずれかが一致しない場合、worktree又はbranchの削除が失敗した場合は以降を削除しない。この場合は、記録値、観測値及び残存対象を`needs_escalation`で返す。

branchとworktreeの回収後に、記録したレーンmanaged-tempを照合して削除する。対象外worktree、複製元及び管理外領域は削除しない。失敗時は残存対象を`needs_escalation`へ返す。

`needs_escalation`で返された資源回収の照合失敗を受領したメインは、記録値と観測値の差分、残存対象及び当該レーンのキュー項目の状態を`agent-toolkit:wi-standards`に従って登録する。残存する資源を推測で削除せず、当該レーンを終端して他のレーンを継続する。
回収の完了を照合する検証では、対象の不在を成功として判定する。
worktreeとbranchは、`git -C <記録した対象リポジトリの絶対パス> worktree list`と`git -C <記録した対象リポジトリの絶対パス> branch --list <所有branch名>`の出力へ当該worktreeと当該branchが現れないことで判定する。
レーンmanaged-tempは`test ! -e <記録したレーンmanaged-tempの絶対パス>`の終了コード0で判定する。
`ls`と`find`は対象が存在しない場合に非0で終了するため、これらの終了コードを検証結果に用いない。

外部操作だけの項目は必要な認可と結果を確認して終端する。
外部操作が上流リポジトリへのフィードバック投入である場合は、対象リポジトリ側の元項目を終端しない。メインが投入先のファイル名を元項目の`depends_on`へ加えて`inbox`へ戻す。
外部操作だけの項目には計画ファイル、worktree、計画レビュー、実装レビューを作成しない。既存commitや既存実装で充足済みの候補である項目をこの扱いの対象にせず、充足の成否を計画レーンで確定する。

## レーン完了報告

最後の作業担当は次を完了してから、`統合完了`と自身が実測した`merged_head`、`adopted`及び`released`の3行をメインへ返す。
統合担当が各値の終了状態を観測して検証する手順は、`${CLAUDE_PLUGIN_ROOT}/share/implementation.subagent.md`が定める。

- 採用する実施範囲を持つ通常型は、計画レビュー、実装、単一の実装レビュー、ffマージ、フィードバック行ごとの終端及び所有資源の回収。`upstream_submission`が`混在`の項目はキュー終端を完了条件から除く
- 既存計画の実装は実装、単一の実装レビュー、ffマージ、`adopt`及び所有資源の回収。`upstream_submission`が`混在`の項目は`adopt`を完了条件から除く
- 採用する実施範囲を持たない通常型は、計画レビュー、計画証拠の保存、フィードバック行ごとの終端及び所有資源の回収
- 外部操作の確認は、認可、結果及び実施範囲

固有の延期指示で終端工程が残る場合は完了報告を返さず、ベースHEAD完全OID、未完了の固有順序及び回収済み資源を`needs_escalation`でメインへ返す。
