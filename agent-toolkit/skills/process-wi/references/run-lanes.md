# レーンの実行

メインが固定した集合を、選定結果のレーン割当と依存順に従って実行する。各レーンの同じ担当threadが、必要な計画の起草、実装、レビュー修正、履歴統合および主作業ツリーへの統合を担う。

## レーンと資源

初期選定が1レーンの場合は、準備済みの専用worktreeと処理対象WIを1人のレーン担当へ渡し、`${CLAUDE_PLUGIN_ROOT}/share/single-lane-execution.md`を適用する。以降の工程境界の往復は同契約の継続する工程へ読み替える。

選定結果の`段階`を昇順に処理し、同じ段階の独立レーンを並行起動する。`先行レーン`を持つ後段は、列挙した全レーンの統合完了を受領してから、統合先の現行HEADを基点にworktreeを作成する。単一段階なら全レーンを同時に作成して起動する。

レーンごとの専用branch・専用worktreeと所有登録は次の操作で作成する。専用worktreeは対象リポジトリの主作業ツリーの`.claude/worktrees/process-wi-<レーン識別子>`へ作成される。process-wiは対象リポジトリごとに1つだけ起動する前提で、配置はリポジトリとレーン識別子だけで決まり、別sessionやprocess-loopのworktreeから呼んでも同じパスになる。

```text
atk lane create --repo <対象リポジトリの絶対パス> --base-branch <統合先branch> --lane <レーン識別子> --selection-file <選定YAMLの絶対パス>
```

対象リポジトリが作成・環境準備・撤去の固有手順を定める場合は、create・prepare・deleteのargv配列を持つJSONを`--commands-file <絶対パス>`へ渡す。各argvの`{repo}`・`{worktree}`・`{branch}`・`{lane}`は作成側がshellを介さず展開する。`{worktree}`には固定作成先が渡る。前提ファイルの複製、mise trust、必要な依存同期はprepareへ含める。作成側は固有手順のdetached HEADを専用branchへ接続する。`--worktree <絶対パス>`は固定作成先と別の場所が必要な場合だけ指定し、その場合のパスは固定されない。

対象のClaude Code設定にWorktreeCreateがある場合は、対象cwd・環境・公式イベント入力でhookを実行し、返却先を同じ所有登録へ保存する。作成hookを使う場合、作成はそのhookだけに委ねる。hookの失敗では診断と途中資源を保持して同じ操作から回復し、通常Git作成へ切り替えない。WorktreeRemoveが設定されていれば、終了時の回収は同じ対象設定と返却先を使う。前提ファイルの複製はhookまたはprepareが担う。

所有session、Git共通ディレクトリ、専用branch、作成先、回収対象、選定原本、固有手順と実行記録は`record_path`の登録へ保存される。資源情報を手書きで再登録せず、親の`parent-handoff.md`には作成結果の所在と担当thread・引き継ぎ記録の対応を残す。メインは終了コード0・`ready`とprepareの保存済み両出力を読み、警告と環境準備の成立を判定してから担当を起動し、環境構築の結果を`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の`環境構築`へ渡す。準備が失敗した資源は登録と成果を保持し、入力を是正して同じcreateで再開する。

統合済みの資源もセッション終了まで保持し、同じレーンへの追加は同じcreateの返却から専用worktreeとbranchを再利用する。登録と回収結果は専用資源の外に保持される。前回の強制終了などで残った登録は、process-wi開始時に`atk lane delete --list`で読み、担当とプロセスの終端を確かめてから同じ所有sessionのdeleteで再判定する。再開に使う場合は登録の`record_path`をcreateの`--reuse-record`へ渡して新しい所有sessionへ移す。旧配置（個別managed-temp）の登録も同じ作成先のまま移せる。固定作成先を別sessionの登録が保持している場合、createは回収条件を満たす資源だけを回収して同じパスへ再作成する。未統合・dirty・稼働中の資源と所有登録の無い実体は変更せずに失敗し、理由と`--reuse-record`またはdeleteの回復操作を返す。createは渡された選定原本からレーンのWI集合と統合状態を所有登録へ写し、選定原本が期限付き領域から失われた後も統合と回収はその保持値で判定する。選定情報を持たない旧形式の登録は、`atk lane recover --session-id <所有session>`で元のbranchを残したまま作業ツリーを解放する。回復済みの登録は固定作成先の所有と回収の判定から外れ、残したbranchとHEADは`atk lane delete --list`の登録本文で読める。回収は所有登録と現物が一致した専用資源に限り、主作業ツリーと登録のない資源は保持する。

各レーンのレーン担当を最初に起動した直後に、`atk agents list --include-terminated`から起動結果の`session_id`と一致する項目の`created_at`を時差付きの`レーン開始時刻`としてレーンの資源記録へ保存する。`started_at`はturnの開始時刻であり、初回起動の起点には使えない。同じレーンを再起動・置換してもこの値を変えず、統合指示で`exec.parent.md`の同名入力として渡す。レーン担当はこの値を`atk lane integrate`のmanifestの`lane_started_at`へ渡し、CLIは最初の値を所有登録へ保持してレーン稼働秒数の起点に使う。

同じレーンのAWIは選定結果の依存順を守り、依存先から処理する。計画を要するレーンは1つの計画へまとめ、単一の計画では行数の警告を避けられない初回だけ`references/lane-planning.md`「計画の起草」の手順4に従って複数の計画へ分ける。
依存先の失敗・保留や上流投入の成果待ちで必要な成果を得られない場合は後続を依存待ちとし、成果の取得後に進める。明示追加の依存先が既存レーンにある場合は「処理中に確定した必須是正レーン」の受領可能性を確かめ、同じレーンが受領できない項目は待機する。

稼働レーンが1つになっても、そのレーンの未着手のAWIはそのレーンで続ける。未着手のAWIを別のレーンへ移すと計画ファイルの分割と書込所有権の移譲が要り、計画凍結（`agent-toolkit:plan-mode`の`references/plan-file-standards.md`）と両立しないためである。単独稼働の区間は選定工程の段階比較で短くする。

レーン担当の起動では`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`所定の入力を渡す。初回起動の各AWIの再開位置は選定結果から読み、担当全体の`再開位置`は中断した同じ担当の再開にだけ渡す。当該レーンの各WIの`担当モデル.実装担当`は`agent-toolkit:delegation`の`references/runtime-routing.md`「工程別モデル設定」に従って`model_type`へ渡し、比べた結果を引き継ぎ記録へ残す。異なる指定があればWI名と値を示し、どれかを捨てて起動しない。

## 各段階の全初期通常レーン起動後の会話圧縮

Claude Codeでは、各段階（複数段階では途中の段階も含む）の全初期通常レーンの初回起動が完了した直後、その時点で並行開始できる独立工程を先に始めてから、待機へ入る前に会話圧縮を予約する。通常レーン0件と処理中の追加レーンでは予約せず、実行レビュー待機では修正に使う文脈を保持する。Codexは予約を省いて通常の待機へ進む。予約と通知後の復元は`agent-toolkit:delegation`の`references/waiting-and-monitoring.md`「長時間待機前の会話圧縮」に従う。

予約前にセッションのmanaged-temp直下の`parent-handoff.md`へ次を保存する。担当別記録と保存物は、この記録に書いた参照から取得する。

- 選定YAMLの絶対パスと現在段階、初回起動済みレーン集合と各session_id
- 専用worktreeとbranchの所有主体・回収対象、保持した最初のレーン開始時刻
- 各レーンの引き継ぎ記録、累積した計画集合と保存状態
- 統合済み集合、後段の先行統合条件、次に受領する工程境界

通知後は保存した段階とsession_idを使い、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`の現在の受領工程へ戻る。

## 上流投入

レーン担当を起動する前に、`上流投入`が`なし`以外の全項目を`${CLAUDE_PLUGIN_ROOT}/share/add-wi.parent.md`の上流投入の手順で委譲する（同じ`元項目`の組は同じ投入担当へ）。投入済みの上流項目は返却値`ファイル名`で識別する。レーンより先に投入するのは、`混在`の項目で上流へ渡した要求をレーン担当が採用範囲から除くためである。続行できない理由を返した要求がある項目は、`add-wi.parent.md`「受領と検収」に従って元項目の状態を変えずに保留する（`混在`ではレーンの起動も保留する）。

`上流要求だけ`（`レーン`が`なし`）の項目は次のとおり扱う。

- `completed`の要求がある場合: レーンを起こさず、全`ファイル名`を`atk wi set-dependencies`で元項目の`depends_on`へ加え、`atk wi return-to-inbox`で`inbox`へ戻す
- 全要求が`condition_not_met`の場合: 依存を加えず、条件不成立を外部操作の観測結果として確かめて元項目を終端する

`混在`の項目では投入結果（要求、投入先、`ファイル名`、`結果`）を`exec.parent.md`の`上流投入結果`として渡す。`completed`の要求がある項目は統合指示の`AWI終端区分`を`終端しない`とし、統合の検収後にメインが全`ファイル名`を`depends_on`へ加えて`inbox`へ戻す。全要求が`condition_not_met`なら通常の終端を適用する。

## 処理中に確定した必須是正レーン

追加した処理対象WI（即時対応で確定したAWI、ユーザーが明示したAWI、処理中に告げられた回答済みUWIとその元項目）は、`selection-procedure.md`「処理対象WIの追加」で分類と処理開始を終えてから、本節の基準で割り当てる。未回答UWI、要求が未確定の項目、明示指示の無い新着は追加の対象外とする。

追加項目は既存レーンへ割り当て、処理中の追加で新しい最終レーン名を作成しない（上限と算定集合はselection-format.md「初回配分の算定根拠」）。既存レーンが0件なら、上限と割当先の不足を続行できない理由として返す。

1. 変更するファイルと節、実依存、再開計画、既存レーンの残る工程と書込所有を確認する。
2. 同じ再開計画を持つ既存レーンがある場合は、そのレーンへの割当を分割不能条件として費用比較より先に確定する。受領できない技術的条件を観測しても、その計画を別レーンへ割り当てず、同じレーンの所有と再開を回復する。
3. その他の項目は、実依存と書込所有を満たす既存レーンへ、その工程境界で受領できるよう割り当てる。待ち時間と残る仕事量は既存レーン間の選択に使い、独立成分も同じレーンで順に扱う。
4. 割当理由へ実依存・再開計画・待ち時間・現在工程・書込所有と、同じ実行で処理する順序を残す。

メインは`selection-procedure.md`「処理対象WIの追加」の公開mergeで仮名を既存名へ対応付け、全体確認の終了コード0と保存成功を検収してから追加分を渡す。合流先は未統合へ戻り、追加のないレーン・所属WI・初回情報は保持される。

割当先が統合済みでも資源は保持されているため、同じ`atk lane create`で所有登録とGit登録の一致を確かめ、返された同じworktree・branchへ追加する。指示は準備済みの環境を保持した同じ担当threadと引き継ぎ記録へ送る。登録と現物が一致しない場合は成果を保持し、回復に必要な事実を返す。合流先は未統合へ戻るため、終了時も再統合が完了するまで資源を保持する。

選定YAMLへ追加した時点で、現在工程の完了を待たずに同じthreadへ1回指示を送る。指示には追加WI名、専用worktreeとbranch、引き継ぎ記録、選定YAMLから本文と`プロジェクト規範の指定`を取得すること、現在工程を置換せず完了後にturnを終えず追加計画の起草へ進むことを含める。割当を見直すためだけに稼働中の担当を中断しない。
工程境界の届け方は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`に委ね、返却を一律に求めない（非待機の`計画検査完了`は`atk agents notify`の通知であり、返却を求めると実装が止まる）。レーン担当は現在工程の結果を、追加後に最初に届ける工程境界の本文の先頭へ含める。
メインはその境界の受領で追加工程の開始を判定し、先行計画を凍結したまま、追加計画の絶対パス、AWI集合、保存状態と進捗をレーンの引き継ぎ記録へ累積して実行レビューと統合へ全計画を渡す。

同じthreadの再開が成立しない場合は、公開応答の事実・対象・不足する条件を続行できない理由として返し、同じレーンの回復判断を受ける。再開不能や全レーン統合済みであっても新しいレーンを作成しない。追加分にも計画・レビュー・統合・終端の既存手順を使う。

同じセッションで共有ツールや手順を修正し、稼働中のレーンが残作業でそれを使う場合は、そのレーンへだけ修正commit、反映される時機、再起動の要否、反映前の回避手順を1回のメッセージで通知する。

## メインが読む対象の境界

メインは選定時にAWI・UWIの元本文を読み、その後は主に選定の構造化出力、計画の`## 概要`と`## 実施内容`、工程境界の出力、レビュー指摘管理表の状態、統合結果を読む（努力目標。メインのコンテキストを保護する）。計画の他の節と実装差分は、エスカレーション、ユーザー介入、レビュー収束の判断で要る場合に読む。統合結果の`変更したエージェント向け文書`の再取得は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従う。

処理対象WIへの包含理由、除外理由またはその構成を尋ねるユーザーの質問は、`selection-procedure.md`の読込表が示す`${CLAUDE_PLUGIN_ROOT}/share/pick-wi-explain.parent.md`の説明手順へ渡し、返された根拠と限界をユーザーへ伝える。

## 採否の確定と終端区分

人間由来の要求を全部または一部不採用にする場合のレーン担当の判定と通知は`references/lane-planning.md`「計画の起草」が定める。メインは範囲、原文との差異、技術的理由、代替案を受け取り、部分採用の除外範囲も含めてユーザーへ確認する。確認の間も依存しないレーンを進める。計画確定後の工程は由来を再判定せず、計画で確定した採否を使う。

回答を得られない場合は`agent-toolkit:wi-standards`に従ってUWIを登録し、`atk wi hold --state=processing <元AWIのファイル名>`で保留する。UWIの本文には元AWIのファイル名、対象、必要な回答と回答で変わる結果を書く。解除条件と再開工程は`atk run-script plan-progress --`で計画の`## 進捗ログ`へ記録する。計画が無ければ`atk wi edit <元AWIのファイル名> --append --body-file <絶対パス> --target-repo=<対象リポジトリ>`で元AWI本文へ追記する。採否は回答を受け取ってから確定する。同じ実行で回答を受け取った場合は、実装開始前ならレーン担当が計画へ、実装着手後ならレビュー指摘管理表へ反映して、同じレーンで確定する。

各AWIを次の終端区分へ割り当てる。

- 採用した要求を実装して完成条件を満たした項目と、既存実装で要求と完成条件を満たすことを現物で確かめた項目: `adopt`
- 必要な採否工程を経て不採用と確定した項目: `reject`
- 回答を保存した事前承認型UWIと、その回答を反映して採否を確定した元AWI: 双方を`adopt`
- ユーザー回答を待つ項目: 終端せず`atk wi hold --state=processing <AWIのファイル名>`で保留する
- 外部状態または上流変更を待つ未実装の項目: 終端せず`inbox`へ戻す
- 実装と統合が済み、反映後の完成条件の観測だけが残る項目: 延期`adopt`と観測のみの再開で観測し、結果で次のとおり扱う。再開記録の追記、状態の変更、計画への記録は`references/finish-session.md`「延期adoptと反映後の観測」で行う
  - 直接観測して完成条件を満たした: `adopt`
  - 直接観測して完成条件を満たさなかった: この実行では`adopt`も既存の実装commitの上への再実装もせず、終端区分を`終端しない`とする。`再開区分: 再実装へ戻す`の再開記録を追記し、再処理抑制期限を付けずに`inbox`へ戻す。次回のprocess-wiが通常の項目として計画から着手する
  - 観測できなかった: 終端せず、レーン担当が返した観測結果（理由、欠けている前提、前提を妨げる状態の生成主体・起動元・起動契機と未確定の範囲）から、残る完成条件ごとに前提を整えられる主体を判定する。エージェント自身や常駐機構が生成した状態は、OS上の所有者が同じでもユーザーが起動した状態と区別し、生成主体が未確定の状態もユーザーだけが整えられる状態とは扱わない。人が通常操作する入力や環境であることは、ユーザーの操作と判定する根拠にしない。自己操作の手段が成り立つかは`references/finish-session.md`「延期adoptと反映後の観測」の自己観測の判定で確かめる
    - 次回にエージェントが前提を整えて観測できる項目（新しいプロセスの起動、反映の完了待ちなど）は、実装を繰り返さず次回の観測へ進める。観測できる最も早い時刻が先にあれば再処理抑制期限を付けて`inbox`へ戻し、それ以外は`processing`を維持する
    - ユーザーの操作か追加認可でしか前提を整えられない項目（実行記録などでユーザーが起動したと確かめたセッションの停止など）は、自己操作が成り立たないと確かめたものに限り、完成条件を変えずにUWIで前提の充足を求めて元AWIを`hold`へ移す。操作の主体と選択肢は`agent-toolkit:wi-standards`の`references/uwi-format.md`「ユーザーへ操作を依頼する場合」で振り分け、到達があり認可だけが欠ける工程はエージェントが実施する認可を問う。UWIには必要な操作か認可、観測結果、欠ける前提と自己操作が成り立たない根拠を書く。同じ観測を次回へ繰り返し渡すと、前提が成立しないまま処理だけが反復する

複数要求を持つAWIは、採用した要求を全て満たした場合に`adopt`し、未解決の保留が残らない場合にだけファイル全体を終端する。固有指示が終端工程後のadoptを求める項目と、版数更新を完成条件に持つ項目は延期対象とする。

## 実装とレビュー

準備結果と、待機を要する場合の`実装開始`または`実装なし`の返却は`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「計画準備の受領」、`実装完了`の受領、実行レビューとユーザビリティレビューの起動、指摘の修正と収束は同書「実装完了の受領」に従う。

選定結果の担当モデル、起動側が解決した候補、終端後の物理記録から観測した実行identityを別の値として比べ、不一致は値と由来を区別して、観測できなければ未観測として引き継ぐ。

レーン担当から確認事項または事後承認の対象を受け取ったら、その時点で根拠と既存認可を検収し、`agent-toolkit:user-confirmation-and-report`「確認要否の判定」と`agent-toolkit:wi-standards`で発行要否を判定する。確認不要の技術判断は報告へ回し、事前承認の確認事項は受領時に直ちに発行する。事後承認型UWIは受領時には発行せず、実行レビュー（並列画面レビューではユーザビリティレビューを含む）の収束後・統合前に、収束した実装と一致する本文で発行する。実行レビューを行わないレーン（`実装なし`と`マージなし`）では、終端返却を受領した時点で発行する。`atk wi add`の成功とファイル名を保持し、回答を待たずに続ける。全受領事項の判定と発行を検収して統合へ進み、確認不要の報告のために統合を待たせない。

## 統合とAWI終端

統合前の確認は`agent-toolkit:review-standards`の`references/exec-review-recording.md`「統合時の完成条件判定」に従う。レーン担当へ委ねる統合の指示とメイン自身によるCLI実行の検収は、`${CLAUDE_PLUGIN_ROOT}/share/exec.parent.md`「統合の指示と受領」に従う。

Git統合、全計画保存、WI終端と選定の統合状態は`atk lane integrate`が同じ所有登録から実施する。呼出入力とmanifestの作成はレーン担当の`lane-integration.subagent.md`「公開統合操作」に従う。メイン自身が現行CLIを呼ぶ場合も、独立文脈レビューと完成条件判定を受理した同じ入力を使う。Git統合と統合状態の更新は、この公開操作にまとめる。

終了コード0と`phase: finalized`、統合結果のOID、計画保存、AWI終端を検収し、`parent-handoff.md`へ記録する。`git-integrated`は最終化途中であり統合完了としない。失敗では同じmanifestとレビュー対象HEADで未完了工程から再開する。rebase後の対応表と検証記録は所有登録と同じ状態ディレクトリへ保存され、期限付き領域で失われた旧状態は同じ操作が再生成して検収待ちへ戻る。CLIは今回のWI集合と所有を検収し、全最終化操作が成立してから選定原本を原子的に統合済みへ更新する。統合前の稼働判定は統合先worktreeとレーンworktreeをcwdとする稼働中の担当のうち、書き込む役割（役割文書の`作業ツリーへの書込: あり`）、役割文書を特定できない起動（自由本文の`delegate`・`shell`・`write`）および宣言を読めない担当を数える。
統合を呼び出した担当とその委譲元の連鎖、`explore`、`作業ツリーへの書込: なし`の役割の担当は数えない。数えた担当が残る場合は、合意した担当だけを`--writer-session`で指定する（`lane-integration.subagent.md`「公開統合操作」）。回収では全担当と外部プロセスの終了を確認する。資源、完了レーンと所属WIは追加に備えて保持する。

資源の回収は終了時の`atk lane delete`が行う。登録全体を先に判定し、全工程と外部プロセスの終了、選定の統合済み、clean、Git共通ディレクトリと専用branchの登録一致、統合先への到達を削除直前にも確かめる。確認後は`--commands-file`で指定した`delete`コマンドの実行、worktree、到達を再確認したbranchの`-D`、旧配置の登録が持つ個別managed-tempの順で回収する。未統合、dirty、稼働中、不明、途中失敗の対象は、理由と残る操作を回収対象の外へ保存し、再実行は残る処理から続ける。セッションのmanaged-tempと証拠は専用worktreeへ置かず、回収対象から外す。通常終了の`atk agents-exit-session`と、process-loopが子セッションの終了後に行う処理が同じ回収を呼び出し、turnごとのSessionEndでは回収しない。
終端済みの委譲sessionが保持する資源は、回収処理が所有側の`agents_server`へ解放を要求し、未回収の結果を保って解放してから使用中判定をやり直す。
実行中のsessionと解放できない資源は保持し、次節の手順で再回収する。

到達確認を経た`-D`でbranchを削除するのは、`-d`がupstreamを基準に判定し、push前のローカル統合を未統合として拒否するためである。監査記録は`docs/development/audit-records.md`「agent-toolkit/skills/process-wi/references/run-lanes.md「統合とAWI終端」：所有資源の回収：2026年9月3日」にある。

### 未回収レーンの再回収

回収結果が示す未解放の委譲sessionについて、終端と`atk agents wait`による結果本文の回収を確認し、再開する予定が無ければ、公開MCPの`agents_server`の`stop`へ`session_id`としてそのIDを渡す。
呼び出しは`stop(session_id="<回収結果にある委譲sessionのID>")`とする。
公開`stop`は終端結果も破棄し、結果保持を指定する引数を受け取らない。
回収処理が所有側へ要求する自動解放では、未回収の結果を保持する。
実行中のsessionは終端を待ち、結果を回収する。

停止が成功して保持理由を解消した後、対象リポジトリをcwdとして`atk lane delete --session-id <レーン資源を作成した所有sessionのID>`を再実行する。
`--session-id`には元の回収操作と同じレーン資源の所有sessionを指定する。
このIDは`atk lane delete --list`の所有登録から確認でき、`stop`へ渡す委譲sessionのIDとは役割が異なる。
停止に失敗した場合や外部プロセスの使用が残る場合は、資源と回収結果を保持し、理由と残る操作を報告する。

## 中断レーンの再開

`processing`のまま残った項目は、計画を持つレーンでは選定結果の`再開位置`の計画ファイルを使う。複数計画を持つ場合は引き継ぎ記録に累積した全計画、AWI集合、進捗、保存状態を比べてから渡す。計画なしのレーンは、引き継ぎ記録のAWI集合とレビュー指摘管理表、`git merge-base <専用branch> <ベースbranch>`と`git log <その結果>..<専用branch>`のcommitから再開工程を決め、`再開位置: 計画なし`として渡す。計画ファイルか引き継ぎ記録の実在、AWI集合の一致、専用worktreeの元の所有主体が終端済みであることを確かめる。
反映後の観測だけが残る項目は、`references/finish-session.md`「延期adoptと反映後の観測」がAWI本文へ追記した再開記録から、選定結果の観測のみの再開位置をそのまま渡し、レーン担当は`references/lane-planning.md`「再開」に従って観測だけを行う。

残存する専用worktreeとbranchを安全に再利用できる場合は、同じ絶対パス、branch、現在HEAD、再開位置を新しいレーン担当へ渡す。再利用できない場合は既存成果を失わない新しい専用worktreeを現在HEADから作成し、移行内容を`atk run-script plan-progress --`で進捗ログ（計画なしでは引き継ぎ記録）へ記録する。未コミット差分は所有と現物を確かめ、権限内で成果を失わない復元・移送は自ら行う。他者・ユーザーの差分の破棄や、所有を確定できない成果を失う処置は、確認要否の判定に従って認可を求める。

## レーン完了

全レーンについて統合結果の検収、AWIの終端・保留への遷移、計画の保存を完了し、資源は終了時回収へ渡す。追加した処理対象WIは、元の選定結果へ反映した分だけを含める。公開工程へは`references/finish-session.md`冒頭の開始条件が成立してから進む。
