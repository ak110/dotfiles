# セッション記録の構造と集計：集計値の典拠

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 集計値の典拠

期間を指定した週ごとのトークン消費量や実行レビューの指標、ならびにセッションごとの推定費用については、`atk run-script cost-metrics -- --since <開始日> --until <終了日>`の出力を典拠とする。
このコマンドは、月曜0時を起点とするローカルの週ごとに、採用されたAWIの件数、全ルートとprocess-wiにおける4成分のトークン量・AWIあたりの数値、レビューのラウンド数・レベル・修正なしで応答した比率を返す。
レビューの指標は実際のレビュー指摘を対象とし、明示的な実装中の判断記録を除外する。
採否集計の`review-adoption`も同じ分類を使い、両方の出力で除外件数と元の表・行を追跡できる。
`excluded_judgment_count`が除外件数、`excluded_judgments`の`table`と`row`が元表と1始まりの行番号を示す。
表の期間・モデル帰属は保持し、明示されていない判断記録の完全な識別は保証しない。
移管先を明示した行は`transferred`として採用・不採用・未応答と別に数え、修正なしで応答した比率の分子から除く。
不採用の理由区分は`判断主体:`を典拠とし、ラベルの無い旧記録は`判断主体不明`とする。
自由文の冒頭から判断主体を推定せず、メイン・レーン担当・統括の技術判断とレビュー担当の撤回を区別する。
`--until`を省略した場合は、コマンド実行時刻までを集計範囲とする。
`cost-metrics-hook-notice`は、同じルートセッションと全委譲先のhook通知をルートの開始週へ帰属させ、`week`、`runtime`、`hook`、`hook_name`、`tag`、`kind_text`ごとの`count`を返す。
`tag`は`block`・`warn`・`notice`などの重要度、`kind_text`はパスやセッションIDなどの可変部分を正規化した本文の冒頭であり、`session-review-evidence --hook-notices`と同じ分類を使う。
hook実行の記録とツール結果だけにある遮断を対象とし、同一呼び出しの重複を除く。
通常の標準出力や会話中の引用は含めない。
出力に含まれる`cost-metrics-coverage`の走査ルート、集計期間、最古の読み取り記録、読み取り不能件数、未解決委譲件数、および各週の`missing_token_records`を併記し、対象範囲の網羅（カバレッジ）に欠落がある週の値は、完全な総量としては扱わない。

`cost-metrics-session`は、指定期間内に開始されたルートセッションごとに、子孫エージェントを含むAPI料金換算の推定額（USD）を返す。
Claudeの場合は最新の`type: cost-state`レコードに記録された`totalCostUSD`を優先し、その後の応答分や累積額の記録がないセッションについては、同一`message.id`の最後の`usage`とモデルの単価を基に補完する。
親セッションの算出額にあらかじめ含まれているClaudeサブエージェントの費用は二重計上せず、別プロセスで起動された委譲先の費用を加算する。
内訳における`breakdown.self`はその記録自身の累積額を含み、`breakdown.claude_subagents`はそこに含まれない追加分を表す。
Codexの場合は各`token_count.info.last_token_usage`と直前の`turn_context.model`を参照し、キャッシュ読み取りと推論出力を二重計上しないように計算する。
単価が不明な分は`unknown_responses`や`unknown_tokens`として残し、合計の`estimated_usd`をnullとした上で、算出できた範囲を`known_usd`として提示する。
料金表の出所、基準日、区分、計算式、およびTTL不明時の仮定については、`cost-metrics-coverage.pricing`の内容を併記する。
なお、`atk serve`による費用表示もこれと同じ記録収集と計算ロジックを使用する。
実支払額との区別については、後述の「複数セッションの比較結果」に従う。

セッション記録から集計したトークン量、リクエスト数、所要時間を成果物やユーザーへの提示文書に記載する場合は、`atk run-script session-review-evidence -- <引数>`の出力を典拠とし、独自に作成した集計結果を根拠としない。
`duration-analysis.md`が求めるレーンの工程時間は、同書で指定した工程記録の時刻差を使う。
セッション統計の値とは区別し、時刻の出所と区間を保持する。
トークン量とリクエスト数を取得する場合は`--stats`を指定し、所要時間を取得する場合は`--elapsed-until <ISO 8601形式の時刻>`を指定する。
振り返りの対象候補は`--bundle`が生成する`candidates.jsonl`から取得し、`atk run-script session-review-prepare`を実行して`candidates.md`へ整形する。

別セッションを含む担当別の費用要約を取得する場合は、`--stats --summary-only`を使用する。
これは、総量、親セッション、Claudeサブエージェント、agent threadごとの要約と出所、未解決の診断情報を保持したまま出力する表示オプションであり、トークンの定義や合算ロジックは全量表示と完全に同一である。
bundleには全量の詳細な内訳が保持され、準備文書には初回確認に必要な索引、総量、上位項目、詳細照会先のみが縮約して記載される。
全候補ID、必須性、詳細の対応関係は`bundle/review-index.jsonl`から、担当別・対象別の全量は`bundle/stats.jsonl`および`bundle/resource-usage.jsonl`から取得する。
毎回全量を通読する処理と証拠の保持を明確に分離し、候補の選別や原因特定、ならびに`analysis-cost.md`「コストの無駄の確認」が定める17観点の費用確認に必要な詳細情報のみを追加取得する。

- Claude Codeの記録では、1回のAPI応答が同一の`usage`を持つ複数のレコードに分かれて現れることがある。
  上記のコマンドは、同一の`message.id`を持つ最後の`usage`に集約した値を返す。
- `--elapsed-until`で出力される`elapsed_seconds`は、セッションの最初のレコードから指定時刻までの経過時間であり、指定時刻より後の工程の所要時間は含まない。
- `--stats`で出力される総量の`elapsed_seconds`は、最初と最後のレコードの時刻差である。
  一方、工程ごとの`stats-tool`に示される秒数はツール呼び出しごとの実行時間であり、親と委譲先が並行して動いている区間は重複して加算されるため、合計値が全体の総量を超えることがある。
  比率を示す場合は、この基準の違いを併記する。

監査記録は`docs/development/audit-records-session-records.md`の「agent-toolkit/skills/review-session/references/session-records.md：集計値の典拠：2026年9月3日」に記載されている。

集計値を判断の根拠として利用する前に、計測の始点・終点や数え方が、判断に必要な観点と正しく一致しているかを必ず確認する。
過去に不一致が観測された例には以下のものがある。

- 委譲先の所要時間を比較する際は、`stats-agent-thread`や`stats-subagent`の`turn_elapsed_seconds`を用いて比較する。
  `elapsed_seconds`にはターン完了後にプロセスが残存していた時間や待機時間（`after_last_turn_seconds`）が含まれてしまう。
- `agent-toolkit:process-wi`の複数回の実行履歴から現行工程のパフォーマンスを評価する場合は、集計期間中にその工程を規定する文書が改訂されたかどうかを`git log --since=<期間の開始> -- <文書のパス>`などで確認する。
  改訂されていた場合は、改訂後の記録のみを現行プロセスの値として扱う。
- 同一ファイルを行範囲に分割して複数回に分けて読み取った場合は、全体で1回の読了として数える。

## 複数セッションの比較結果

カタログにおける親セッションの行は、`--catalog-workflow`による完全一致、`--catalog-known-workflow`によるunknown以外の抽出、および`--catalog-cwd-contains`による部分文字列一致で絞り込める。
複数の行条件を併記した場合は、すべての条件を満たす行のみが返される。
`--catalog-fields`にカンマ区切りで項目名を渡すと、指定された順序で項目が出力され、指定を省略した場合は全項目が出力される。
なお、`kind`は行の種類を示す必須項目のため、常に保持される。
条件で絞り込んだ後も、`catalog-summary`には走査全体の範囲が記録され、走査した親セッション全体のレコード数である`parent_record_count`と、選択された行数である`selected_parent_count`が区別して出力される。
これらの指定方法はClaudeとCodexの親セッション一覧で共通しており、行条件は`--user-events`や`--grep`と併用する場合でも親セッションの選定に適用される。
また、`--catalog-fields`や`--tool-calls`による呼び出し照会は、親セッションの行条件とは分けて指定する。

カタログと`--grep <正規表現>`を併用すると、指定期間の本文とツール入力を記録横断で検索できる。
対象は`--since`より後で`--observation-boundary`以前の一致とし、結果の`record`・`line`から単一記録の詳細照会へ進む。
`--summary-only`では記録別の一致エントリ数と合計を残す。
時刻を確定できない一致行数は`undated_match_count`へ返し、一致エントリ数の合計と区別する。
未解決の記録は`unresolved_record_count`へ返すため、0件の判定ではこれらの未確認範囲も保持する。
家族収集で解決できたroot外の記録は検索側の未解決から除き、全走査rootの診断と選択した照会に関わる診断を区別する。

「最新」「該当なし」「全件」のように全体や終端を表す結論を述べる場合は、走査ルート、実行環境（runtime）、開始境界、観測境界、未解決レコード数を同じ文面に明記し、その調査範囲（カバレッジ）のみを対象として述べる。
指定ルート外の記録や、観測境界より後の記録、未解決の記録については、未確認の範囲として明記する。

WIの処理件数を数える場合は、成功結果まで正常に記録された直接の`atk wi`操作のみをカウントし、操作ごとにセッション識別子と記録行のロケーター（位置情報）を残す。
workflow名、作業ディレクトリ（cwd）、ブランチ名、時刻、トークン量、処理件数などを記録から特定できない項目については、`unknown`として扱う。

費用を記載する際は、請求書や決済記録から確認した実際の実支払額と、API利用量に公開単価を掛け合わせて計算した見積額を、明確に別の値として提示する。
見積額を記載する場合は、価格表の出所、価格の基準日、入力・キャッシュ書き込み・キャッシュ読み取り・出力の区分、および計算式を併記する。
なお、契約プランに伴う定額料金は実支払額の区分に含める。

施策の前後の差を因果関係による効果として主張する場合は、変更した変数、比較対象において固定した条件、および反実仮想（施策を実施しなかった場合の想定）を明示する。
集計期間、実行環境、対象workflow、処理したWIの由来、あるいは並列度が異なっている比較については、単なる相関関係として記載し、施策自体の純粋な効果は追加の対照比較を行って確定させる。
