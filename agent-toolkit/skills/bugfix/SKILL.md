# バグ対応

本スキルはバグ対応時の考え方・対応手順を提供する。

観測した不具合を再現し、期待する契約、実際の結果、発生条件、直接的原因を確定して是正する。
ユーザー要求を満たさずに完了した未対応と、過去に成立した機能または規範が失われたデグレードも不具合として扱い、同じ初動から原因分析、類似見直しおよび再発防止策の判定へ進める。
実装方式、計画形式、レビュー一般、pushとCI監視はそれぞれ`agent-toolkit:writing-standards`、`agent-toolkit:plan-mode`、`agent-toolkit:review-standards`、`agent-toolkit:commit`へ委ねる。

## 適用手順

問題を発見した時点で、対処に着手する前に`references/response.md`を全文読む。
事象がWI処理の工程や運用に関わる場合は、対策を選ぶ前に`agent-toolkit:workflow-overview`を起動する。

1. 後述の「初動と拡張原因分析の判定」を読む
2. 拡張原因分析の条件に該当する場合だけ、`references/root-cause-analysis.md`を全文読む。
   同書は対策の選定に関わる2つの判断を定める。不在を原因へ採る前に事項が既存の上位規範から導かれるかを確かめる判断と、条文の追加より除去・緩和・一般化を先に評価する選定順である。対策と再発防止策を選ぶ前に読む
   局所不良でも、AWIの`## 原因分析`を起草する場合、計画ファイル（バグ）を作成する場合と事象単位の調査を委譲する場合は、同書の該当節を読む
3. CI失敗を扱う時は`agent-toolkit/skills/bugfix/references/ci-failure-handling.md`を全文読む
4. 計画、実装、レビューのいずれでも同じ判定と原因分析の段階を用いる

CI通過へ入る前は`agent-toolkit:commit`の`commit/references/push-and-ci.md`を全文読む。
履歴を扱う実装単位へ入る前は`${CLAUDE_PLUGIN_ROOT}/share/exec.subagent.md`を全文読む。
実装担当の委譲先を確定する前は`agent-toolkit:delegation`を起動し、同スキルの`delegation/references/runtime-routing.md`を全文読む。
`references/testing.md`「分岐条件の効果の裏付け」による検証へ入る前は`agent-toolkit:writing-standards`を起動し、同スキルの`references/testing.md`を全文読む。
文書・規範・出力文面を変える対策の直し方をユーザーへ提案するか委譲先へ渡す前は、`agent-toolkit:writing-standards`を起動し、受け取る主体が観測できる条件で方向を評価する。

## 初動と拡張原因分析の判定

- 処置案を検討する前に、事象、実際の結果および発生条件を再現・ログ・実装から確定する。期待する契約は対象の目的を定める仕様・設計記録・規範から確定し、実装が述べる前提や文言は比べられる側として扱う。次に直接的原因、作り込み要因、見逃し要因および類似範囲を確定し、その後にだけ対策・横展開処置・再発防止策を選定する。直接的原因は、候補の機構だけを変えた対照で事象が変わることを観測して確定する。同時に変化した値の相関だけから得た候補と、計測手段が対象の区間を記録するか確かめていない計測値（出力の到着時刻を処理の時刻とみなす計測など）は、推定として扱う。設定、依存版、外部状態、規範・スキル・手順の条文その他の可変値を原因へ用いる場合（条文が適用されなかった、条文が欠けていたと述べる場合を含む）は、その値と文面が事象時点にも同じ形で適用されていたことを履歴か当時の記録で確かめる。履歴は`git log -S '<文面の特徴的な語>' -- <パス>`や、事象時点のcommitに対する`git show <commit>:<パス>`で調べる。事象後の現行の値と文面だけでは事象時点の値を確定せず、時点を確かめていない候補は推定として扱う。類似範囲は直接的原因の機構を共有する対象全体とし、症状を観測した呼び出し元や、上限の超過など症状の程度で狭めない
- 対策を確定する前に、その対策が変える値や動作の影響範囲を実装からたどる。参照・呼び出す側（変更前の動作を前提として書かれた既存の指定を含む）と別発生源（いずれも範囲は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」）を対象とし、追随が必要な箇所を対策へ含める。影響が局所にとどまると考えられる場合も同じ範囲を調べる。除外、免除または解決済みとして扱う対策では、保証する側の規定や実装で先行動作が成立し、除外する側がその動作を前提としているか、双方の現物を読んで確かめる。主体をまたぐ場合も先行側の保証を確かめ、保証が無ければ同じ対策に含める
- ユーザーが失敗例その他の観測事象の実物を提示した場合は、対象の母集団を発話の範囲語から確定してから発生条件を定める。提示された実物は母集団の一例として扱う。範囲語と例示が併存する場合の優先順位は`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`に従う
- エンドユーザーが観測した症状の件数や該当対象を数えるときは、エンドユーザーが観測する層で数える。画面では描画結果、CLIでは出力がこの層に当たる。中間の値（一覧APIの戻り値、状態ファイルなど）や一部の記録（特定の形式や付随ファイルを持つ記録だけなど）で数える場合は、その値からエンドユーザーが観測する層までの変換（表示側での検索の引き直し、抽出条件、件数上限など）を実装からたどる。変換が該当の判定を変えないことと、数えなかった記録に該当が無いことを確かめてから母集団として使う。件数を成果物（AWIの`## 原因分析`の`原因分析の根拠`行など）へ書くときは、数えた層と、中間の値で数えた場合に確かめた変換を併記する。この項はユーザーが実物を提示したかによらず適用する。中間の値が正しくても後段の変換を経た結果が正しいとは限らず、手前の層で数えると症状の大半が母集団から外れ、是正をやり直すことになる
- 外部から受け取った不具合報告が、別の環境、別の版、過去の時点のいずれかでは事象が生じないと述べている場合は、その主張の成否を判定してから発生条件を確定する。判定は報告が挙げる環境または版が配備する成果物の実装差分を取得し、その成果物へ差し替えて再現することで行う。判定結果と根拠を成果物へ書く。報告に事象が生じない環境・版・時点の記述が無い場合は、この判定を省く
- 事象への対処をAWIの投入で終える場合も、本節の初動と原因分析を投入の前に完遂する。投入の前に確定する事項は`agent-toolkit:wi-standards`の`### 起草完了の条件`が定める
- 作業途中で発見した事象は、着手前に記録した状態と現在の差分を先に突合し、進行中の未コミット変更で混入した事象と着手前から存在する事象を区別する
  - 進行中の未コミット変更で混入した場合は、現在の指示、計画、実装判断を混入原因として調べる。既存機能の導入履歴は別の系統として扱う
- 直接的原因までの確定直後に、拡張原因分析の条件に用いる判定材料を確認する。
  確認対象は、対象判断を記録した計画・設計文書と当時の指示・契約、およびその判断を導入した変更履歴に限る。
  確認後も判断材料の有無を確定できない場合は拡張原因分析へ進む
- 判定材料の確認後に、次の拡張原因分析の条件を評価する
  - 拡張原因分析の条件は、事象が計画または設計の時点で判断材料が揃っており、その時点で適切に判断していれば
    回避できたか否かとする。この条件へ該当する事象は、機能的な不具合の有無、動作の正否、
    エンドユーザーへの実害の有無にかかわらずバグとして扱う
  - 該当する事象の例は次のとおり
    - ユーザーが明示した要件または公開契約と成果物が異なる
    - 設計判断、代替手段の選択、誤ったテスト期待値の固定が不具合へ関与する
    - 現行コードだけでは意図を説明できず、コメント・文書・履歴の確認を要する
    - 同じ原因が別の箇所ですでに成立するか、同じ判断・工程が反復される箇所を現行の実装・手順・履歴から観測できる
    - push後のCI失敗で、原因が自セッションに帰属するか、セッション帰属が未確定
    - エージェント向け文書の欠陥、判定条件の抜けや矛盾
    - ツールの使い勝手の悪さ、ツールが出力するメッセージの分かりにくさ
    - 公開インターフェース・コマンド体系・配置規約の一貫性の逸脱
    - 既存の拡張点を使わず別系統を新設した実装
  - 列挙は拡張原因分析の条件の適用例であり、列挙に無い事象もこの条件へ該当すれば対象とする
  - 計画または設計の時点では入手できなかった情報により初めて判明した事象と、
    外部環境の変化に起因する事象は本条件の対象外とする
  - 本条件の判定は努力目標とする。判定を誤っても対策自体は完遂され、
    成果物の機能は損なわれないためである。
    判定を誤った場合も、`references/root-cause-analysis.md`「再発防止策の必須性」が定める必須性はそのまま働く
- 同じ原因が別の箇所ですでに成立するか、同じ判断・工程が反復される箇所を挙げる例は、実在する別の該当箇所または反復される箇所を特定した場合に限って成立する
- 拡張原因分析の条件に該当する場合は、「拡張原因分析の資料と因果の確定」以降の工程へ進む
- 拡張原因分析の条件に該当しない局所不良は、対策と変更範囲の検証に限定する
  - 局所対応での原因の調査範囲は直接的原因までとする。対策の影響範囲の調査はこの限定の外にある
  - 履歴、AWI、計画、セッションログの探索、2系統4段階の原因分析、汎用的な恒久対策は拡張原因分析だけに適用する
  - 実行主体が対策と変更範囲の検証を完遂し、横展開処置と再発防止策を該当なしと判断した根拠を報告する
- 同種の問題が反復する場合は、`agent-toolkit:review-standards`の`review-standards/references/judgment-details.md`「規範の前提の再検討」を適用し、その事象を統治する規範の条文も分析対象に含める

### 同一症状の修正反復

同じ期待契約、症状、検証条件で1回目と2回目の修正後も症状が残り、3回目の修正が必要になった時点で追加修正を止める。原因仮説が依存する入力、環境、実装、期待契約、検証手段、統治規範を現物で支持または反証してから修正案を選び直す。別症状、別契約、条件不一致、未適用の修正、外部基盤障害は回数へ含めない。現物で観測できずユーザーだけが持つ値が必要な場合だけ、診断質問を1つに限定する。`references/ci-failure-handling.md`の3回目以降のレビュー契約は置換せず併用する。
