# 原因分析

対症療法と原因除去を区別し、すべてのバグで直接的原因まで確定する。
直接的原因の確定後に拡張原因分析の要否を判定し、局所不良へ履歴調査や汎用的な恒久対策を一律適用しない。

## 事象単位の並列調査委譲

バグ対応とCI失敗対応の調査工程に適用する。

独立事象ごとに観測事実の収集を分ける。初回は症状または失敗ジョブを単位とし、
報告後に同一原因を統合し、複数原因を分割する。
委譲を使う場合は`../../delegation/SKILL.md`に従い、起動文へ事象、期待する契約、実際の結果、
発生条件、ログと資料の絶対パス、対象commit、再現手順だけを渡す。
呼び出し元の仮説、疑わしい実装箇所、修正案、他事象の調査結果は渡さない。
報告された推定と対策案は候補として実測し、原因と処置の確定は呼び出し元が所有する。

## 拡張原因分析の資料と因果の確定

- 次の資料を上から順に確認し、設計判断を説明できた段階と確認不能だった資料を記録する
  1. 現行の実装、テスト、コメント、エンドユーザー向け文書、設計文書
  2. `git blame`、変更履歴、導入コミット、関連レビュー
  3. 要求原文、issue、フィードバック、当時の計画ファイル
  4. 前段で動機または見逃し経路を説明できない場合のセッションログ・会話履歴
- 拡張原因分析の資料を確認した後に対立する原因候補を列挙する。各候補を反証する事実の有無を確認し、棄却できない候補を区別してから因果を確定する
- 各層の探索結果として、探索先・実行したコマンド・観測時点・検出結果・確定できる範囲とその限界を記録する
- 集計値を記載する場合は判定条件と母集団の総数を併記し、判定条件は観測時点に依存しない形で定義する
- 作成時点を直接示さない指標を判定に用いる場合は、その指標では確定できない範囲を明記し、
  対象が存在しないことを断定しない
- 資料が別環境にあり取得できない場合は、探索先と不足を明記する。内心を推測で断定せず、確認済みの最深層と棄却できない候補を区別する
- 推測した因果チェーンは、各段を資料または実機結果で裏付ける。原因候補の不確定性が類似範囲・処置を変える場合は、残る候補の和集合を対象にする
- 直接アクセスできない環境の事象で、コードベース調査と開発環境の再現だけでは因果を確定できない場合は、計画ファイルの起草を停止する。コンソールへ貼り付ける調査用コードまたはログ採取手順を提示し、ユーザーへ代行採取を依頼する。実測データで原因を確定してから起草を再開する
- 上流ライブラリ・ツール・OSの変更が原因候補の場合は、リリースノートまたは公式CHANGELOGを確認する。回避処理の採用には、挙動差分の観察に加えて同資料の裏付けを必須とする
- 責務境界を越える呼び出し、非公開関数の横断利用、重複記録等の回避処理がある場合は、同機能の正常な兄弟経路、設計上の所有責務、当該処理の導入コミットを突合する。局所処理の維持・共通化案と正常経路への復帰案を比較し、正常経路を棄却する根拠を確認できるまで、局所処理を根本対策と判定しない
- 有効・無効のような二値状態をステータスコードで表現するAPIでは、コードの一般的な語義と実際の意味が
  反転しうる。外部ツールが表示する要約・短縮形（注釈の出典表示など）から原因や対象を断定する場合は、
  生の応答を取得して確認する
- 外部サービスへ依存する工程が期待どおり起動しない場合、自環境の設定・定義・実行状態の確認を
  2回以上繰り返す前に、当該サービスの公式ステータスページまたは障害情報を照会する。
  当該工程へ影響する障害の掲載を確認できた場合は外部起因を支持する材料として扱い、
  自環境側の確認の反復を打ち切る。
  掲載を確認できない場合は原因を未確定として扱い、自環境側と外部側の追加確認へ進む
  （努力目標。掲載が無い場合は空振りとなるため）

## 原因分析の段階

本節は拡張原因分析の条件に該当する場合に適用する。

作り込み要因（なぜ誤りを成果物へ追加したか）と見逃し要因（なぜレビュー、テスト、監視で事前に検出できなかったか）の
2系統へ分け、各系統をL1からL4の順に分析する。

| 段階 | 作り込み要因で問うこと | 見逃し要因で問うこと |
| --- | --- | --- |
| L1 現象 | 何を誤って実装したか | どこで検出されなかったか |
| L2 判断 | なぜそれでよいと判断したか | なぜ問題だと判断できなかったか |
| L3 構造 | なぜその判断でも実装できたか | なぜ検出機構が働かなかったか |
| L4 システム | なぜその構造を許す規範・設計になっているか | なぜ検出を特定の仕組みまたは人へ依存させているか |

- 「考慮不足」「仕様を理解していなかった」「確認不足」などの記述はL1からL2に当たる事象の言い換えとして扱い、原因として終端させない
- 対策を除く処置の決定は、原則として両系統のいずれかがL3へ到達した後に行う
- 両系統をL4まで掘ることは求めない。L3の構造へ作用する処置で同じ失敗構造を断てる場合はL3で止め、止めた根拠を記録する
- L3へ到達できない系統がある場合は、確認した資料と到達できない理由を記録し、当該系統を根拠とする処置を確定しない
- 規範、仕様又は設定の条文どうしが矛盾する事象では、各条文の導入変更を`git log -S`等で特定し、
  ユーザー指示由来かエージェント判断由来かを確定してからL2とL3を記述する。
  由来を確定できない条文を、既存の規範であることだけを理由に低い優先度で扱わない

直接的原因（観測した不具合を発生させる実行時・データ・設定上の機構）は、両系統の前段としてすべてのバグで確定する。
根本原因は、到達した最深段の作り込み要因と見逃し要因を因果で結び、
どの原因を除けば同じ失敗構造を断てるかを一般化した結論とする。直接的原因との差分を含める。
根本原因の記録先は原因分析表の到達した最深段のセルとし、調査表へ独立した行を設けない。

各段は該当内容または「該当なし」と根拠を記録する。
資料不足は「未確認」と探索結果を記録し、「該当なし」と同一視しない。
参照すべき規範、仕様又は設計文書の不在をL3、L4又は根本原因へ採用する前に、当該事項が既存の上位規範から導かれるかを確認する。
導かれる場合は、不在ではなく当該規範を適用しなかった判断を原因とし、当該事項の文書への再掲を再発防止策に数えない。
確認対象の上位規範には、`agent-toolkit/rules/01-agent.md`「判断指針」が定める消費主体と利用シナリオによる十分性判定を含める。

## 原因分析の品質確認

根本原因の確定後、類似見直しへ進む前に次の3点を確認する。

- 人物を変えても成立するか。担当した実行主体の注意力、経験又は状況へ帰す記述が残る場合はL3へ戻る
- 対象を変えても成立するか。観測事象のファイル、機能、識別子を別の対象へ置き換えても同じ原因が成立するかを確認する
- 他の危険箇所を導出できるか。同じ原因から、まだ欠陥として観測していない箇所を1件以上挙げられるかを確認する

いずれかを満たせない場合は、原因の記述が事象の言い換えに留まっているとみなし、原因分析へ戻る。
本確認は原因分析を成立させる工程であり、確認結果を調査表の独立した行として記録しない。

## 類似見直し

拡張原因分析経路で原因分析を終えた後、処置選定前に実施する。
根本原因は2系統4段階の要約ではなく、後続の規則と処置が失敗構造全体を扱うかを照合する基準とする。

類似見直しは2つの役割を持つ。すでに同じ欠陥が成立している箇所を見つけて横展開処置へ渡す是正の役割と、
まだ欠陥化していないが同じL3・L4の構造を持つ箇所を見つけて再発防止策へ渡す予防の役割とする。
母集団は根本原因が依存するL3・L4の構造が成立する箇所とし、観測事象と同じ症状を示す箇所へ限定しない。

1. 作り込み要因・見逃し要因の各到達段と根本原因から、破られた不変条件または誤った判断規則を独立した規則ごとに1文で表す。複数の規則を1文に束ねない
2. 各規則の適用境界は、当該判断が誤りとなる機構が依存する条件だけで定める
3. 観測事象のファイル、機能、工程、データ構造は、誤りの機構が依存する場合を除き限定条件にしない
4. 誤りの機構が依存する条件を母集団境界として維持し、各規則が適用される判断境界を母集団として列挙する。ファイル、言語、症状、必要な是正が異なっても除外しない
5. 規則ごとに母集団と点検結果を対応づけ、該当箇所と非該当の根拠を実測コマンドとともに記録する。列挙から導出できる件数は書かない
6. 識別子・コード形状の検索は母集団抽出の補助として使い、検索一致だけで類似性を確定しない
7. 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）が、少なくとも1つの規則とその母集団へ対応することを確認し、対応を記録する
8. 単一の規則が複数の単位を被覆する場合は、各単位からの対応をすべて記録する。未対応の単位を残す例外は設けない
点検結果は是正対象（既存欠陥）と予防対象（同じ構造を持つ未発生箇所）へ分けて記録する。

## 処置の階層

- 対策: 観測した不具合そのものと、当該不具合を固定した誤ったテスト・文書を直す
- 横展開処置: 類似見直しで見つけた、同じ原因による既存不具合を取り除く
- 再発防止策: 同じ原因による誤りの混入を防ぐか、混入しても見逃さない仕組みを追加する

3層を混同せず、対策、横展開処置、再発防止策の順に実装対象を確定する。
横展開処置の記録先は調査表の`類似見直し結果`行とし、是正対象として列挙した該当箇所へ対応づけて書く。
局所経路では対策だけを具体化し、横展開処置と再発防止策を「該当なし」と根拠付きで記録する。

## 再発防止策

本節は拡張原因分析の条件に該当する場合に適用する。
再発防止策は次の優先順位で評価し、上位段が成立しない根拠を記録してから下位段を選ぶ。

1. 除去: 誤りの対象となった実装、分岐、オプション、独自機構又は条文そのものを不要にする
2. 制約・集約:
   - 制約: 誤った値、状態又は記述を表現できない入力形式、インターフェース、型又は書式にする
   - 集約: 同じ判断を複数箇所で正しく行う必要をなくし、共通機構又は単一の正本へ閉じ込める
3. 最短経路化: 追加の作業をせずに書いた実装、記述又は操作が既定で正しくなるようにする
4. 自動検出: 機械検査、テスト、フックで混入または見逃しを検出する
5. 手順・チェックリスト: 実行主体が参照する工程へ判定を組み込む
6. コメント・文書: 維持する契約と選択の理由を記録する

段2の制約と集約には順位差を置かない。
誤った値を表現できない構造と判断箇所の集約のどちらが成立するかは、対象が持つ表現手段によって決まるためである。
「正しく実装する方法」を定める前に「実装しなくて済む方法」を探す。

自動チェックを選ぶ場合は、当該チェックの起動と実効性を無効化する変更（削除、起動条件の変更、空実装化）を何が検出するかを先に確定する。
設定の編集で無効化できる構成では、必須実行を強制する機構が対象環境に存在するかを一次資料で確認する。
存在しない場合は、検査で保証できる範囲と保証できない範囲を分け、後者を人手確認へ割り当てて記録する。
保証範囲を確定しないまま検査を積み増さない。

## 再発防止策の必須性

拡張原因分析の条件に該当する不良では再発防止策を必須とする。
再発防止策は、当該事象そのものの再発ではなく、同様または類似した原因による別の問題の発生を防ぐ。
`該当なし`と記録できるのは局所経路に限る。

省略できるのは次の場合に限る。

- 同一セッションで当該処置を実装済みである
- activeな既存フィードバックが根本原因と必要な全処置を覆う。部分被覆では不足分を投入する

当該事象を統治する既存規範が存在することは、前記のいずれにも当たらない。
既存規範へ違反した事象では、規範の存在と同趣旨条文の重複を再発防止策の省略事由にせず、
当該規範が実行経路で適用されなかった原因（起動契機、参照時点、判定条件、責務の所在）へ作用する処置を確定する
（厳守規定。規範の存在を処置として扱うと、同じ違反が同じ経路で再発する）。

いずれの段でも恒常コストに見合う案を確定できない場合は、処置なしで終端せず、
`agent-toolkit:wi-standards`をSkill機能で起動してTBDを登録し、ユーザーへ助言を求める。
TBD本文には観測事象、根本原因、評価した各段の案、各案を採用しない理由及び恒常コストの見積りを含める。

毎計画又は毎セッションへ恒常コストを課す規範を再発防止策として新設する場合は、適用範囲を誤りの機構が依存する条件で定め、契機となった事象の対象、工程及び識別子で限定しない。適用範囲の判定は「類似見直し」の手順2と手順3を唯一の基準とする。
恒常コストは、失敗を観測した場合だけ実行する遅延評価案と、条件を満たす場合だけ適用する条件付き案を同じ階層で比較して抑える。
観測できた発生頻度と当該処置の恒常コストの比較を記録してから確定する。
案の比較は`agent-toolkit:review-standards`の`review-standards/references/judgment-details.md`「問題と手段の比例性」に従う。

再発防止策は次の成立条件をすべて満たすものとする。

- 後続の実行でも参照される成果物または永続規範として残る
- 根本原因または見逃し経路へ作用し、同じ原因による混入または見逃しを減らす
- 表面構造の異なる類似事象でも同じ因果へ作用する
- 適用境界が類似見直しの母集団を被覆する。観測事象そのものの再現だけへ適用境界が限定される処置は再発防止策に数えない
- 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）に、当該単位の混入を防ぐか、混入しても見逃さない処置を対応づける
- 単一の処置が複数の単位を被覆する場合は、各単位からの対応をすべて記録し、未対応の単位を残さない

個別計画の変更履歴、単一セッション内の説明、その実行だけで使うレビュープロンプトは後続の実行で参照されないため、
是正内容の確認記録であり再発防止策には数えない。

## 再発防止としてのテスト

テストを再発防止へ数える場合は、今回の具体値を検証する再現テストと、
別入力・別呼び出し元でも同じ原因を検出する再発防止テストを区別し、是正前の版で失敗することを確認する。
是正前の版で失敗を確認できない場合は、検体が判定分岐へ到達していないものとして検体を見直す。
期待値は要求仕様または契約から導出する。
実装の現行出力、現行文言又は現行の設定値をそのまま固定するテストは、
変更時の追随箇所を増やす一方で同じ原因の再発を検出しないため、再発防止策に数えない。
誤ったテスト期待値が見逃し要因である事象では、
当該テストの是正（契約由来の期待値への置換、または当該テストの削除）を対策へ含め、同じ文言を別のテストへ固定し直さない。
自動検査を新設する場合は、計画へ書く前に、判定対象を対象ツールの公開API又は実行結果から取得し、
対象ツールの選択・分類条件を検査側へ再実装していないことを確認する。
ネットワーク、キャッシュ、権限などの実行環境依存は対象環境で実測し、実測結果を計画の完了条件へ記載する。
新設または変更した分岐自体の効果は、`agent-toolkit:coding-standards`の分岐条件の効果の裏付け節に従って確認する。
是正前の失敗確認における作業ツリーの置換・復元手段も同節に従う。

外部契約の写像、直感に反する制約、意図的な仕様差はコメントまたは設計文書へ、
何を維持するかとなぜその選択をしたかを記録する。
コードだけで意図が自明な処理へ説明コメントを一律追加しない。

## 計画ファイルへの集約

原因分析後に確定した最終バグ単位は、計画付属のバグ調査ファイルへ集約する。
バグ調査ファイルの保存先、計画本文からの参照行の書式及びファイル内の見出し構成は、`agent-toolkit:plan-mode`の計画ファイル基準を正本とする。
バグ単位ごとの見出しの配下へ、原因分析表と調査表をこの順で置く。

原因分析表は`要因系統`、`L1 現象`、`L2 判断`、`L3 構造`、`L4 システム`の5列とし、
`作り込み要因`、`見逃し要因`の2行を固定順で置く。
到達しなかった段のセルには`該当なし`と、その段まで掘らずに処置を確定できる根拠を書く。

調査表は`項目`と`内容`の2列とし、次の8行を固定順で書く。

| 行名 | 記載内容 |
| --- | --- |
| 現象 | 事象に加えて発生条件と実際値を含める |
| 期待する契約 | 事象の対象が満たすべき仕様、規範、公開契約 |
| 直接的原因 | 観測した不具合を発生させる実行時・データ・設定上の機構 |
| 原因分析の根拠 | 再現結果、`git blame`、導入コミット、資料の該当箇所 |
| 対策 | 観測した不具合そのものと、それを固定した誤ったテスト・文書の修正 |
| 類似見直し観点 | 破られた不変条件または誤った判断規則、その適用境界、根本原因を成立させる各単位との対応 |
| 類似見直し結果 | 母集団、是正対象と予防対象へ分けた該当箇所の列挙、非該当の根拠、是正対象へ実施する横展開処置（列挙から導出できる件数は書かない） |
| 再発防止策 | 混入を防ぐか見逃さない仕組み、選定した優先順位の段、上位段を採用しない根拠、根本原因を成立させる各単位との対応、維持する契約とその選択の理由を残す先 |

拡張原因分析の条件に該当しない局所不良では、原因分析表の各セルと、拡張原因分析固有の行（類似見直し観点、
類似見直し結果、再発防止策）へ
`該当なし`と拡張原因分析の条件に該当しない根拠を書く。
表の追加・削除、行名・列名の変更、順序変更は行わない。
複数の観測事象は、直接的原因と対策の変更単位がともに同じ場合だけ1つのバグ単位へ統合する。
直接的原因または対策の変更単位のいずれかが異なる場合は分け、根本原因の共有だけを統合理由にしない。
同じ根本原因でも入力解析と状態更新のように直接的原因が異なる事象は別のバグ単位にする。
同じ直接的原因と対策から保存失敗と再試行停止のような複数症状が生じる場合は統合できる。
対応網羅確認では、計画メタ情報の関連WIに現れる各バグがいずれかの確定したバグ単位へ対応することを確認する。
計画の`### 恒久化`は対応する計画ファイル（バグ）の調査表を正本として参照し、同じ内容を複製しない。計画本文へ類似見直しの専用節を置かない。
