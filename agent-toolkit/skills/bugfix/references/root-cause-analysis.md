# 原因分析

対症療法と原因除去を区別し、すべてのバグで直接的原因まで確定する。
直接的原因の確定後に深掘り要否を判定し、局所不良へ履歴調査や汎用的な恒久対策を一律適用しない。

## 事象単位の並列調査委譲

バグ対応とCI失敗対応の調査工程に適用する。

独立事象ごとに観測事実の収集を分ける。初回は症状または失敗ジョブを単位とし、
報告後に同一原因を統合し、複数原因を分割する。
委譲を使う場合は`../../delegation/SKILL.md`に従い、起動文へ事象、期待する契約、実際の結果、
発生条件、ログと資料の絶対パス、対象commit、再現手順だけを渡す。
呼び出し元の仮説、疑わしい実装箇所、修正案、他事象の調査結果は渡さない。
報告された推定と対策案は候補として実測し、原因と処置の確定は呼び出し元が所有する。

## 深掘り資料と因果の確定

- 次の資料を上から順に確認し、設計判断を説明できた段階と確認不能だった資料を記録する
  1. 現行の実装、テスト、コメント、利用者向け文書、設計文書
  2. `git blame`、変更履歴、導入コミット、関連レビュー
  3. 要求原文、issue、フィードバック、当時の計画ファイル
  4. 前段で動機または見逃し経路を説明できない場合のセッションログ・会話履歴
- 深掘り資料の確認後に対立する原因候補を列挙する。各候補を反証する事実の有無を確認し、棄却できない候補を区別してから因果を確定する
- 各層の探索結果として、探索先・実行したコマンド・観測時点・検出結果・確定できる範囲とその限界を記録する
- 集計値を記載する場合は判定条件と母集団の総数を併記し、判定条件は観測時点に依存しない形で定義する
- 作成時点を直接示さない指標を判定に用いる場合は、その指標では確定できない範囲を明記し、
  対象が存在しないことを断定しない
- 資料が別環境にあり取得できない場合は、探索先と不足を明記する。内心を推測で断定せず、確認済みの最深層と棄却できない候補を区別する
- 推測した因果チェーンは、各段を資料または実機結果で裏付ける。原因候補の不確定性が類似範囲・処置を変える場合は、残る候補の和集合を対象にする
- 直接アクセスできない環境の事象で、コードベース調査と開発環境の再現だけでは因果を確定できない場合は、計画ファイルの起草を停止する。コンソールへ貼り付ける調査用コードまたはログ採取手順を提示し、ユーザーへ代行採取を依頼する。実測データで原因を確定してから起草を再開する
- 上流ライブラリ・ツール・OSの変更が原因候補の場合は、リリースノートまたは公式CHANGELOGを確認する。回避処理の採用には、挙動差分の観察に加えて同資料の裏付けを必須とする
- 責務境界を越える呼び出し、非公開関数の横断利用、重複記録等の回避処理がある場合は、同機能の正常な兄弟経路、設計上の所有責務、当該処理の導入コミットを突合する。局所処理の維持・共通化案と正常経路への復帰案を比較し、正常経路を棄却する根拠を確認できるまで、局所処理を根本対策と判定しない
- 有効・無効のような二値状態をステータスコードで表現するAPIでは、コードの一般的な語義と実際の意味が
  反転しうる。外部ツールが表示する要約・短縮形（注釈の出典表示など）から原因や対象を断定する場合は、
  生の応答を取得して確認する
- 外部サービスへ依存する工程が期待どおり起動しない場合、自環境の設定・定義・実行状態の確認を
  2回以上繰り返す前に、当該サービスの公式ステータスページまたは障害情報を照会する。
  当該工程へ影響する障害の掲載を確認できた場合は外部起因を支持する材料として扱い、
  自環境側の確認の反復を打ち切る。
  掲載を確認できない場合は原因を未確定として扱い、自環境側と外部側の追加確認へ進む
  （努力目標。掲載が無い場合は空振りとなるため）

## 原因区分

本節は深掘り条件に該当する場合に適用する。

- 直接的原因: 観測した不具合を発生させる実行時・データ・設定上の機構
- 混入要因: 誤った仕様、設計、実装、テスト期待値を成果物へ混入させた判断または工程
- 動機的要因: 混入判断を合理的に見せた前提、思い込み、優先順位、トレードオフ
- 見逃し原因: 調査、計画、レビュー、テスト、監視が誤りを検出できなかった理由
- 根本原因: 確認できた4区分を因果で結び、どの原因を除けば同じ失敗構造を断てるかを示す結論。直接的原因との差分を含める

各区分は該当内容または「該当なし」と根拠を記録する。
資料不足は「未確認」と探索結果を記録し、「該当なし」と同一視しない。

## 類似見直し

深掘り経路で原因分析を終えた後、処置選定前に実施する。
根本原因は4区分の要約ではなく、後続の規則と処置が失敗構造全体を扱うかを照合する基準とする。

1. 根本原因・混入要因・動機的要因・見逃し原因から、破られた不変条件または誤った判断規則を独立した規則ごとに1文で表す。複数の規則を1文に束ねない
2. 各規則の適用境界は、当該判断が誤りとなる機構が依存する条件だけで定める
3. 観測事象のファイル、機能、工程、データ構造は、誤りの機構が依存する場合を除き限定条件にしない
4. 誤りの機構が依存する条件を母集団境界として維持し、各規則が適用される判断境界を母集団として列挙する。ファイル、言語、症状、必要な是正が異なっても除外しない
5. 規則ごとに母集団と点検結果を対応づけ、該当箇所と非該当の根拠を実測コマンドとともに記録する。列挙から導出できる件数は書かない
6. 識別子・コード形状の検索は母集団抽出の補助として使い、検索一致だけで類似性を確定しない
7. 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）が、少なくとも1つの規則とその母集団へ対応することを確認し、対応を記録する
8. 単一の規則が複数の単位を被覆する場合は、各単位からの対応をすべて記録する。未対応の単位を残す例外は設けない

## 処置の階層

- 是正処置: 観測した不具合そのものと、当該不具合を固定した誤ったテスト・文書を直す
- 横展開処置: 類似見直しで見つけた、同じ原因による既存不具合を取り除く
- 再発防止処置: 同じ原因による誤りの混入を防ぐか、混入しても見逃さない仕組みを追加する

3層を混同せず、是正、横展開、再発防止の順に実装対象を確定する。
局所経路では是正処置だけを具体化し、横展開・再発防止を「該当なし」と根拠付きで記録する。

## 再発防止策

再発防止処置は設計による構造的抑止、自動チェック、手順・チェックリスト、コメント・文書の順で評価する。
下位層を選ぶ場合は上位層が成立しない根拠を記録し、発生頻度と影響に見合わない仕組みを追加しない。
自動チェックを選ぶ場合は、当該チェックの起動と実効性を無効化する変更（削除、起動条件の変更、空実装化）を何が検出するかを先に確定する。
設定の編集で無効化できる構成では、必須実行を強制する機構が対象環境に存在するかを一次資料で確認する。
存在しない場合は、検査で保証できる範囲と保証できない範囲を分け、後者を人手確認へ割り当てて記録する。
保証範囲を確定しないまま検査を積み増さない。
本節は深掘り条件に該当する場合に適用する。

毎計画又は毎セッションへ恒常コストを課す規範を再発防止処置として新設する場合は、契機となった失敗様態へ適用範囲を限定する。
確定前に、失敗を観測した場合だけ実行する遅延評価案と、条件を満たす場合だけ適用する条件付き案を同じ階層で比較する。
観測できた発生頻度と当該処置の恒常コストの比較を記録してから確定する。

再発防止処置は次の成立条件をすべて満たすものとする。

- 後続の実行でも参照される成果物または永続規範として残る
- 根本原因または見逃し経路へ作用し、同じ原因による混入または見逃しを減らす
- 表面構造の異なる類似事象でも同じ因果へ作用する
- 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）に、当該単位の混入を防ぐか、混入しても見逃さない処置を対応づける
- 単一の処置が複数の単位を被覆する場合は、各単位からの対応をすべて記録し、未対応の単位を残さない

個別計画の変更履歴、単一セッション内の説明、その実行だけで使うレビュープロンプトは後続の実行で参照されないため、
是正内容の確認記録であり再発防止処置には数えない。

テストを再発防止へ数える場合は、今回の具体値を検証する再現テストと、別入力・別呼び出し元でも同じ原因を検出する再発防止テストを区別し、是正前の版で失敗することを確認する。
是正前の版で失敗を確認できない場合は、検体が判定分岐へ到達していないものとして検体を見直す。
自動チェックを新設する場合は、計画へ書く前に、判定対象を対象ツールの公開API又は実行結果から取得し、対象ツールの選択・分類条件を検査側へ再実装していないことを確認する。
ネットワーク、キャッシュ、権限などの実行環境依存は対象環境で実測し、実測結果を計画の完了条件へ記載する。
新設または変更した分岐自体の効果は、`../../coding-standards/SKILL.md`の`分岐条件の効果の裏付け`節に従って確認する。

外部契約の写像、直感に反する制約、意図的な仕様差はコメントまたは設計文書へ、何を維持するかとなぜその選択をしたかを記録する。
コードだけで意図が自明な処理へ説明コメントを一律追加しない。

## 計画ファイルへの集約

原因分析後に確定した最終バグ単位を計画の`## バグ調査結果`へ集約する。
バグ単位ごとにH3見出しを置き、`項目`と`内容`の2列表へ次の14行を固定順で書く。

| 行名 | 記載内容 |
| --- | --- |
| 観測事象 | 事象に加えて発生条件と実際値を含める |
| 期待する契約 | 事象の対象が満たすべき仕様、規範、公開契約 |
| 直接的原因 | 観測した不具合を発生させる実行時・データ・設定上の機構 |
| 混入要因 | 誤りを成果物へ混入させた判断または工程 |
| 動機的要因 | 混入判断を合理的に見せた前提、思い込み、優先順位 |
| 見逃し原因 | 調査、計画、レビュー、テスト、監視が検出できなかった理由 |
| 根本原因 | 4区分を因果で結び、どの原因を除けば同じ失敗構造を断てるかの結論 |
| 原因分析の根拠 | 再現結果、`git blame`、導入コミット、資料の該当箇所 |
| 類似見直しの観点 | 破られた不変条件または誤った判断規則、その適用境界、根本原因を成立させる各単位との対応 |
| 類似見直し結果 | 母集団、該当箇所の列挙、非該当の根拠（列挙から導出できる件数は書かない） |
| 是正処置 | 観測した不具合そのものと、それを固定した誤ったテスト・文書の修正 |
| 横展開処置 | 同じ原因による既存不具合の除去 |
| 再発防止処置 | 混入を防ぐか見逃さない仕組みと、根本原因を成立させる各単位との対応 |
| 設計意図の記録 | 維持する契約と、その選択の理由を残す先 |

深掘り条件に該当しない局所不良では、深掘り固有の行（混入要因、動機的要因、見逃し原因、
根本原因、類似見直しの観点、類似見直し結果、横展開処置、再発防止処置）へ
`該当なし`と深掘り条件に該当しない根拠を書く。
行の削除、名称変更、順序変更は行わない。
複数の観測事象は、直接的原因と是正処置の変更単位がともに同じ場合だけ1つのバグ単位へ統合する。
直接的原因または是正処置の変更単位のいずれかが異なる場合は分け、根本原因の共有だけを統合理由にしない。
同じ根本原因でも入力解析と状態更新のように直接的原因が異なる事象は別のバグ単位にする。
同じ直接的原因と是正処置から保存失敗と再試行停止のような複数症状が生じる場合は統合できる。
総合レビューでは、利用者の提示素材に現れる各バグがいずれかの確定したバグ単位へ対応することを確認する。
計画の`### 恒久化`と`### 類似見直し`は対応するバグ単位の14行表を正本として参照し、同じ内容を複製しない。
