# 原因分析

本書は、拡張原因分析の条件に該当する不良の原因分析、類似見直し、処置及び計画ファイルへの集約を定める。
すべてのバグで直接的原因まで確定する規定と、拡張原因分析の要否の判定は`SKILL.md`「初動と拡張原因分析の判定」が定める。
履歴調査と汎用的な恒久対策は、拡張原因分析の条件に該当する不良へ適用する。
同じ原因に属する処置の統合と、異なる原因の分離は`agent-toolkit:writing-standards`の`references/design-heuristics.md`「設計案の予備選別」を正本とする。

## 事象単位の並列調査委譲

バグ対応とCI失敗対応の調査工程に適用する。

独立事象ごとに観測事実の収集を分ける。初回は症状または失敗ジョブを単位とし、
報告後に同一原因を統合し、複数原因を分割する。
委譲を使う場合は`../../delegation/SKILL.md`に従い、起動文へ事象、期待する契約、実際の結果、
発生条件、ログと資料の絶対パス、対象commit、再現手順だけを渡す。
起動文へ渡すのはこの7項目とし、呼び出し元の仮説、疑わしい実装箇所、修正案、他事象の調査結果は自身の手元に残す。これらを渡すと調査担当がその仮説を検証する範囲へ調査を狭め、独立したコンテキストで別の原因へ到達する利益が失われる。
報告された推定と対策案は候補として実測し、原因と処置の確定は呼び出し元が所有する。

## 拡張原因分析の資料と因果の確定

- 次の資料を上から順に確認し、設計判断を説明できた段階と確認不能だった資料を記録する
  1. 現行の実装、テスト、コメント、エンドユーザー向け文書、設計文書
  2. `git blame`、変更履歴、導入コミット、関連レビュー
  3. 要求原文、issue、AWI、当時の計画ファイル
  4. 前段で動機または見逃し経路を説明できない場合のセッションログ・会話履歴
- 拡張原因分析の資料を確認した後に対立する原因候補を列挙する。各候補を反証する事実の有無を確認し、棄却できない候補を区別してから因果を確定する
- 各層の探索結果として、探索先・実行したコマンド・観測時点・検出結果・確定できる範囲とその限界を記録する
- 集計値を記載する場合は判定条件と母集団の総数を併記し、判定条件は観測時点に依存しない形で定義する
- 作成時点を直接示さない指標を判定に用いる場合は、その指標では確定できない範囲を明記し、
  対象の存否は別の観測で確定する
- 資料が別環境にあり取得できない場合は、探索先と不足を明記する。内心は確認済みの資料の範囲で述べ、確認済みの最深層と棄却できない候補を区別する
- 推測した因果チェーンは、各段を資料または実機結果で裏付ける。原因候補の不確定性が類似範囲・処置を変える場合は、残る候補の和集合を対象にする
- 設定、依存版、外部状態その他の可変値を事象の原因へ用いる場合は、その値が事象の発生時点にも適用されていたことを履歴又は当時の記録で照合する。事象後の観測値だけでは当時の値を確定せず、時点を照合できない原因候補は未確定として残す
- 直接アクセスできない環境の事象で、コードベース調査と開発環境の再現だけでは因果を確定できない場合は、計画ファイルの起草を停止する。コンソールへ貼り付ける調査用コードまたはログ採取手順を提示し、ユーザーへ代行採取を依頼する。実測データで原因を確定してから起草を再開する
- 上流ライブラリ・ツール・OSの変更が原因候補の場合は、リリースノートまたは公式CHANGELOGを確認する。回避処理の採用には、挙動差分の観察に加えて同資料の裏付けを必須とする
- 責務境界を越える呼び出し、非公開関数の横断利用、重複記録等の回避処理がある場合は、同機能の正常な兄弟経路、設計上の所有責務、その処理の導入コミットを突合する。局所処理の維持・共通化案と正常経路への復帰案を比較し、局所処理を根本対策と判定できるのは、正常経路を棄却する根拠を確認できた場合とする
- 有効・無効のような二値状態をステータスコードで表現するAPIでは、コードの一般的な語義と実際の意味が
  反転しうる。外部ツールが表示する要約・短縮形（注釈の出典表示など）から原因や対象を断定する場合は、
  生の応答を取得して確認する
- 外部サービスへ依存する工程が期待どおり起動しない場合、自環境の設定・定義・実行状態の確認を
  2回以上繰り返す前に、そのサービスの公式ステータスページまたは障害情報を照会する。
  その工程へ影響する障害の掲載を確認できた場合は外部起因を支持する材料として扱い、
  自環境側の確認の反復を打ち切る。
  掲載を確認できない場合は原因を未確定として扱い、自環境側と外部側の追加確認へ進む
  （努力目標。掲載が無い場合は空振りとなるため）

## 原因分析の段階

本節は拡張原因分析の条件に該当する場合に適用する。

作り込み要因（なぜ誤りを成果物へ追加したか）と見逃し要因（なぜレビュー、テスト、監視で事前に検出できなかったか）の
2系統へ分け、各系統をL1からL4の順に分析する。

| 段階 | 作り込み要因で問うこと | 見逃し要因で問うこと |
| --- | --- | --- |
| L1 現象 | 何を誤って実装したか | どこで検出されなかったか |
| L2 判断 | なぜそれでよいと判断したか | なぜ問題だと判断できなかったか |
| L3 構造 | なぜその判断でも実装できたか | なぜ検出機構が働かなかったか |
| L4 システム | なぜその構造を許す規範・設計になっているか | なぜ検出を特定の仕組みまたは人へ依存させているか |

L3の作り込み要因には、既存規範が判断材料や結論を過剰に閉じ、目的に合う判断を妨げた構造も含める。条文の適用自体が不適切な成果を生む場合は、条文を足す前に制限の緩和、削除、一般化を調べる。

- 「考慮不足」「仕様を理解していなかった」「確認不足」などの記述はL1からL2に当たる事象の言い換えとして扱い、さらに深い段へ進む
- 対策を除く処置の決定は、原則として両系統のいずれかがL3へ到達した後に行う
- 両系統をL4まで掘ることは求めない。L3の構造へ作用する処置で同じ失敗構造を断てる場合はL3で止め、止めた根拠を記録する
- L3へ到達できない系統がある場合は、確認した資料と到達できない理由を記録する。処置の根拠に用いるのはL3へ到達した系統とする
- 規範、仕様又は設定の条文どうしが矛盾する事象では、各条文の導入変更を`git log -S`等で特定し、
  ユーザー指示由来かエージェント判断由来かを確定してからL2とL3を記述する。
  優先度は確定した由来で決め、既存の規範であることは優先度の判定の外に置く

直接的原因（観測した不具合を発生させる実行時・データ・設定上の機構）は、両系統の前段としてすべてのバグで確定する。
直接的原因が処理の不成立である場合は、制御がその処理へ到達しない経路と、到達したうえで処理が失敗する経路を分けて列挙する。前者では取り消しや離脱の時点、保護機構の内側と外側、複数の確定処理の間の区間を分解する。後者では呼び出しが成立した証拠と、失敗を示す終了状態・出力を対応付ける。未到達の根拠は制御が到達しない経路の観測とし、到達したが問題を検出しなかった結果は後者の系統で扱う。
根本原因は、到達した最深段の作り込み要因と見逃し要因を因果で結び、
どの原因を除けば同じ失敗構造を断てるかを一般化した結論とする。直接的原因との差分を含める。
根本原因の記録先は原因分析表の到達した最深段のセルとし、調査表へ独立した行を設けない。

各段は該当内容または「該当なし」と根拠を記録する。
資料不足は「未確認」と探索結果を記録し、「該当なし」とは別の記録として扱う。
参照すべき規範、仕様又は設計文書の不在をL3、L4又は根本原因へ採用する前に、その事項が既存の上位規範から導かれるかを確認する。
導かれる場合は、不在ではなくその規範を適用しなかった判断を原因とする。再発防止策には、規範の適用経路へ作用する処置を選び、同じ事項の文書への再掲は別の記録として扱う。
確認対象の上位規範には、`agent-toolkit/rules/01-agent.md`「判断指針」が定める消費主体と利用シナリオによる十分性判定を含める。

## 原因分析の品質確認

根本原因の確定後、類似見直しへ進む前に次の3点を確認する。

- 人物を変えても成立するか。担当した実行主体の注意力、経験又は状況へ帰す記述が残る場合はL3へ戻る
- 対象を変えても成立するか。観測事象のファイル、機能、識別子を別の対象へ置き換えても同じ原因が成立するかを確認する
- 他の危険箇所を導出できるか。同じ原因から、まだ欠陥として観測していない箇所を1件以上挙げられるかを確認する

いずれかを満たせない場合は、原因の記述が事象の言い換えに留まっているとみなし、原因分析へ戻る。
本確認は原因分析を成立させる工程であり、確認結果は原因分析の記述へ反映して、調査表の独立した行を設けない。

## 類似見直し

拡張原因分析経路で原因分析を終えた後、処置選定前に実施する。
根本原因は2系統4段階の要約ではなく、後続の規則と処置が失敗構造全体を扱うかを照合する基準とする。

類似見直しは2つの役割を持つ。すでに同じ欠陥が成立している箇所を見つけて横展開処置へ渡す是正の役割と、
まだ欠陥化していないが同じL3・L4の構造を持つ箇所を見つけて再発防止策へ渡す予防の役割とする。
母集団は根本原因が依存するL3・L4の構造が成立する箇所とし、観測事象と同じ症状を示すかは母集団の判定の外に置く。

破られた不変条件と誤った判断規則を規則ごとに1文で表し、各規則の母集団を、その判断が誤りとなる機構が依存する条件だけで定める。
観測事象のファイル、機能、工程、データ構造は、誤りの機構がこれらへ依存する場合に限って限定条件へ加える。
ファイル、言語、症状、必要な是正の相違は、母集団から除く条件の外に置く。識別子とコード形状の検索は母集団抽出の補助として使う。
根本原因を成立させる各単位が少なくとも1つの規則とその母集団へ対応することを確認し、規則ごとに母集団、該当箇所及び非該当の根拠を実測コマンドとともに記録する。
点検結果は是正対象（既存欠陥）と予防対象（同じ構造を持つ未発生箇所）へ分けて記録する。

観測事象への因果的寄与を実測で確定していない潜在的な欠陥は、独立した通常AWIへ分離する。観測事象の直接的原因が確定したバグ単位と同じ計画へ含められるのは、その寄与を実測済みである場合又はユーザーが併記を明示合意した場合に限り、その根拠を計画へ記録する。

## 処置の階層

- 対策: 観測した不具合そのものと、その不具合を固定した誤ったテスト・文書を直す
- 横展開処置: 類似見直しで見つけた、同じ原因による既存不具合を取り除く
- 再発防止策: 同じ原因による誤りの混入を防ぐか、混入しても見逃さない仕組みを追加する

事象と期待する契約、直接的原因、2系統の原因、類似見直しを確定した後、3層を混同せず、対策、横展開処置、再発防止策の順に実装対象を確定する。
処置を選ぶ際は、利用者が選んだ値、品質及び適用範囲を元の要求から照合し、それらを保つ案を先に評価する。元の選択を変更する縮退案は、その変更への明示的な合意がある場合だけ採用する。復旧の成否だけで要求の達成を判定すると、障害を除いても利用者が選んだ結果を失う。
横展開処置の記録先は調査表の`類似見直し結果`行とし、是正対象として列挙した該当箇所へ対応づけて書く。
局所経路では対策だけを具体化し、横展開処置と再発防止策を「該当なし」と根拠付きで記録する。

## 再発防止策

本節は拡張原因分析の条件に該当する場合に適用する。
再発防止策は次の優先順位で評価し、上位段が成立しない根拠を記録してから下位段を選ぶ。

1. 除去: 誤りの対象となった実装、分岐、オプション、独自機構又は条文そのものを不要にする
2. 制約・集約:
   - 制約: 誤った値、状態又は記述を表現できない入力形式、インターフェース、型又は書式にする
   - 集約: 同じ判断を複数箇所で正しく行う必要をなくし、共通機構又は単一の正本へ閉じ込める
3. 最短経路化: 追加の作業をせずに書いた実装、記述又は操作が既定で正しくなるようにする
4. 自動検出: 機械検査、テスト、フックで混入または見逃しを検出する。フックの遮断・警告を選ぶ案は`agent-toolkit:writing-standards`の`references/claude-hooks.md`「遮断・警告フックの成立条件」で判定し、成立しない案は採らない
5. 手順・チェックリスト: 実行主体が参照する工程へ判定を組み込む
6. コメント・文書: 維持する契約と選択の理由を記録する

段2の制約と集約には順位差を置かない。
誤った値を表現できない構造と判断箇所の集約のどちらが成立するかは、対象が持つ表現手段によって決まるためである。
「正しく実装する方法」を定める前に「実装しなくて済む方法」を探す。規範を字面どおり適用したことが原因の事象では、段1の条文の緩和、削除、一般化を先に評価する。条文の追加を選ぶ場合は、これらで目的を達成できない根拠を記録する。

既存規範が実行経路で適用されなかった事象では、段1から段3を評価した後、誤った判断の偏りを相殺する工程を先に検討する。独立した検証担当による問い直しや、決定前に反例を調べる工程が、その実行経路で実際に働くか確かめる。次に段4の自動検出を検討し、誤検出による停止と修正の往復費用を防止効果と比較する。最後に既存条文の語彙、例示、配置、条件と行動の対応を見直し、読み手が使う経路で想起しやすくなるかを`agent-toolkit:writing-standards`の`references/llm-characteristics.md`で判定する。いずれの対策も成立しない場合は理由を記録して段5以下を評価する。条文を増やすだけの処置は、既存条文の改訂と集約を検討した後に限る。

対策、横展開処置又は再発防止策として、新しい記録、フラグ、識別子、ハッシュ値又は検証機構を加える案では、`agent-toolkit:writing-standards`の`references/design-heuristics.md`「自作機構の兆候と自問」の発火条件を照合する。
該当する案には同節の3つの問いを適用し、答えを処置の選定根拠へ書く。
（努力目標。再発防止の段4以下は新しい機構を加える形になりやすく、兆候を照合しないと段1の除去を検討しないまま機構が増える）

自動チェックを選ぶ場合は、そのチェックの起動と実効性を無効化する変更（削除、起動条件の変更、空実装化）を何が検出するかを先に確定する。
設定の編集で無効化できる構成では、必須実行を強制する機構が対象環境に存在するかを一次資料で確認する。
存在しない場合は、検査で保証できる範囲と保証できない範囲を分け、後者を人手確認へ割り当てて記録する。
検査を追加するのは、保証範囲を確定した後とする。

## 再発防止策の必須性

拡張原因分析の条件に該当する不良では再発防止策を必須とする。
再発防止策は、その事象そのものの再発ではなく、同様または類似した原因による別の問題の発生を防ぐ。
`該当なし`と記録できるのは局所経路に限る。

省略できるのは次の場合に限る。

- 同一セッションでその処置を実装済みである
- activeな既存AWIが根本原因と必要な全処置を覆う。部分被覆では不足分を投入する

省略の条件は前記の2つに限り、その事象を統治する既存規範の存在は条件の外に置く。
既存規範へ違反した事象では、規範の存在と同趣旨条文の重複を省略事由から外し、
その規範が実行経路で適用されなかった原因へ作用する処置を確定する。
原因には、起動契機、参照時点、判定条件、責務の所在に加え、条文が想起の手掛かりを与えないことも含む。
例えば、対象分野の語彙が条文に現れない、例示が発想を例の近傍へ狭めている場合がある。
繰り返し参照する原則に固有名がない、条件と行動が一対一に対応していない場合もある。
条文の想起性を改善する処置は、規範の存在や同趣旨条文の重複とは区別する。
規範の存在を処置として扱うと、同じ違反が同じ経路で再発する。

`agent-toolkit:session-review`が過去に採用して終端した対策による根本原因の被覆を反復と判定した候補では、前回の処置で再発を防げなかった条件を確かめる。同じ段でも、その条件を解消する別の処置なら採用できる。段の違いだけで有効性を判定しない。

自動検出を選ぶ前に、元の要求と観測した事象に対して何を防ぐかを示す。実行時の値を測れることだけを設置理由にせず、通知や遮断が正当な作業を妨げる費用も比べる。遮断を選ぶ場合は、同条件が求める結果の不可逆性を、観測した事象の事実から判定する。例えばパッケージの削除では、設定ファイルを残す`remove`か残さない`purge`かを確かめる。事象の種類の印象だけで不可逆と判定すると、可逆な操作まで止める遮断が入る。

いずれの段でも恒常コストに見合う案を確定できない場合は、採用する再発防止策なしと判断して終端する。
判断の根拠として、観測事象、根本原因、評価した各段の案、各案を採用しない理由及び恒常コストの見積りを計画ファイル（バグ）の`再発防止策`行へ記録する。
案の採否は技術判断であり、事前にユーザーへ委ねない。
あわせて`agent-toolkit:wi-standards`の事後承認型UWI（`その対応で問題無い`と`問題がある`の2択）を1件投入し、記録した根拠を平易に書く。回答を待たずに作業を続ける。
再発防止策なしで終えた判断をユーザーが見直せないと、同じ失敗が再発しても誰も気付かない。
ユーザーの選好に依存する要素が残る場合は、その要素だけを`agent-toolkit:confirmation-and-uwi`の確認経路へ送る。

毎計画又は毎セッションへ恒常コストを課す処置を再発防止策として新設する場合は、適用範囲を誤りの機構が依存する条件で定める。対象は処置の種別ではなく恒常コストの有無で決まり、規範に加えて、機械検査、pretooluse hookその他の自動検出と、毎回の検査で実行する検体を含める。前節の6段のうち段4の`自動検出`を選ぶ案は、いずれもこの対象に当たる。観測した事象だけを是正し、毎回の実行へ恒常コストを課さない対策は、この対象の外に置く。契機となった事象の対象、工程及び識別子は、適用範囲の判定の外に置く。適用範囲の判定は「類似見直し」の手順2と手順3を唯一の基準とする。
恒常コストは、失敗を観測した場合だけ実行する遅延評価案と、条件を満たす場合だけ適用する条件付き案を同じ階層で比較して抑える。
観測できた発生頻度とその処置の恒常コストの比較を記録してから確定する。
案の比較は`agent-toolkit:review-standards`の`review-standards/references/judgment-details.md`「問題と手段の比例性」に従う。

再発防止策は次の成立条件をすべて満たすものとする。

- 後続の実行でも参照される成果物または永続規範として残る
- 根本原因または見逃し経路へ作用し、同じ原因による混入または見逃しを減らす
- 表面構造の異なる類似事象でも同じ因果へ作用する
- 適用境界が類似見直しの母集団を被覆する。観測事象そのものの再現へ適用境界が限定される処置は、対策として記録する
- 根本原因を成立させる各単位（破られた不変条件・誤った判断規則）に、その単位の混入を防ぐか、混入しても見逃さない処置を対応づける
- 単一の処置が複数の単位を被覆する場合は、各単位からの対応をすべて記録し、全ての単位へ対応を残す

個別計画の変更履歴、単一セッション内の説明、その実行だけで使うレビュープロンプトは後続の実行で参照されないため、
是正内容の確認記録として扱う。

## 再発防止としてのテスト

同じ問題が再発した場合は、以前の対策と再発防止策が対象にした入力・呼び出し元・発生条件を、今回の観測条件と突き合わせる。
以前の検体が今回の経路へ到達するかを確認し、被覆しなかった条件とその理由を原因分析の見逃し要因及び類似見直しへ反映する。
以前の処置を同じ形で反復せず、今回の条件にも届く処置を選ぶ。

テストを再発防止へ数える場合は、その事象の具体値を検証する再現テストと、
別入力・別呼び出し元でも同じ原因を検出する再発防止テストを区別し、是正前の版で失敗することを確認する。
是正前の版で失敗を確認できない場合は、検体が判定分岐へ到達していないものとして検体を見直す。
期待値は要求仕様または契約から導出する。
実装の現行出力、現行文言又は現行の設定値をそのまま固定するテストは、
変更時の追随箇所を増やす一方で同じ原因の再発を検出しないため、追随の記録として扱う。
誤ったテスト期待値が見逃し要因である事象では、
そのテストの是正（契約由来の期待値への置換、またはそのテストの削除）を対策へ含める。置換後の期待値は契約から導出し、同じ文言の固定は別のテストでも避ける。
自動検査を新設する場合は、計画へ書く前に、判定対象を対象ツールの公開API又は実行結果から取得し、
対象ツールの選択・分類条件を検査側へ再実装していないことを確認する。
ネットワーク、キャッシュ、権限などの実行環境依存は対象環境で実測し、実測結果を計画の完了条件へ記載する。
新設または変更した分岐自体の効果は、`agent-toolkit:writing-standards`の`references/testing.md`「分岐条件の効果の裏付け」に従って確認する。
是正前の失敗確認における作業ツリーの置換・復元手段も同節に従う。

外部契約の写像、直感に反する制約、意図的な仕様差はコメントまたは設計文書へ、
何を維持するかとなぜその選択をしたかを記録する。
説明コメントを書く対象は、コードだけでは意図が定まらない処理とする。

## 計画ファイルへの集約

原因分析後に確定した最終バグ単位は、計画ファイル（バグ）へ集約する。
計画ファイルの`### 計画メタ情報`に置く`計画ファイル（バグ）`行から参照する。
計画ファイル（バグ）の保存先、参照行の書式及びファイル内の見出し構成は、`agent-toolkit:plan-mode`の計画ファイル基準を正本とする。
バグ単位ごとの見出しの配下へ、原因分析表と調査表をこの順で置く。

原因分析表は`要因系統`、`L1 現象`、`L2 判断`、`L3 構造`、`L4 システム`の5列とし、
`作り込み要因`、`見逃し要因`の2行を固定順で置く。
到達しなかった段のセルには`該当なし`と、その段まで掘らずに処置を確定できる根拠を書く。

調査表は`項目`と`内容`の2列とし、次の8行を固定順で書く。

| 行名 | 記載内容 |
| --- | --- |
| 現象 | 事象に加えて発生条件と実際値を含める |
| 期待する契約 | 事象の対象が満たすべき仕様、規範、公開契約 |
| 直接的原因 | 観測した不具合を発生させる実行時・データ・設定上の機構 |
| 原因分析の根拠 | 再現結果、`git blame`、導入コミット、資料の該当箇所 |
| 対策 | 観測した不具合そのものと、それを固定した誤ったテスト・文書の修正 |
| 類似見直し観点 | 破られた不変条件または誤った判断規則、その適用境界、根本原因を成立させる各単位との対応 |
| 類似見直し結果 | 母集団、是正対象と予防対象へ分けた該当箇所の列挙、非該当の根拠、是正対象へ実施する横展開処置（列挙から導出できる件数は書かない） |
| 再発防止策 | 混入を防ぐか見逃さない仕組み、選定した優先順位の段、上位段を採用しない根拠、根本原因を成立させる各単位との対応、維持する契約とその選択の理由を残す先 |

拡張原因分析の条件に該当しない局所不良では、原因分析表の各セルと、拡張原因分析固有の行（類似見直し観点、
類似見直し結果、再発防止策）へ
`該当なし`と拡張原因分析の条件に該当しない根拠を書く。
表の構成、行名・列名及び順序は本節が定めるとおりに保つ。
複数の観測事象は、直接的原因と対策の変更単位がともに同じ場合だけ1つのバグ単位へ統合する。
直接的原因または対策の変更単位のいずれかが異なる場合は分ける。統合の条件は直接的原因と対策の変更単位の一致とし、根本原因の共有は条件の外に置く。
同じ根本原因でも入力解析と状態更新のように直接的原因が異なる事象は別のバグ単位にする。
同じ直接的原因と対策から保存失敗と再試行停止のような複数症状が生じる場合は統合できる。
対応網羅確認では、計画メタ情報の関連WIに現れる各バグがいずれかの確定したバグ単位へ対応することを確認する。
計画の`### 恒久化`は対応する計画ファイル（バグ）の調査表を正本として参照し、同じ内容を複製しない。計画本文へ類似見直しの専用節を置かない。
