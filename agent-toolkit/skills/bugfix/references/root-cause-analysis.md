# 原因分析

本書は拡張原因分析の条件に該当する不良の原因分析、類似見直しおよび処置を定める。原因分析を記録するAWIの`## 原因分析`と計画ファイル（バグ）の表の構成は`analysis-records.md`「原因分析の記録先」が、事象単位の調査の委譲は`investigation-delegation.md`が定める。
すべてのバグで直接的原因まで確定する規定と、拡張原因分析の要否の判定は`SKILL.md`「初動と拡張原因分析の判定」が定める。
履歴調査と汎用的な恒久対策は、拡張原因分析の条件に該当する不良へ適用する。
同じ原因に属する処置の統合と、異なる原因の分離は`agent-toolkit:writing-standards`の`references/design-heuristics.md`「設計案の予備選別」に従う。

## 拡張原因分析の資料と因果の確定

- 次の資料を上から順に確認し、設計判断を説明できた段階と確認不能だった資料を記録する
  1. 現行の実装、テスト、コメント、エンドユーザー向け文書、設計文書
  2. `git blame`、変更履歴、導入コミット、関連レビュー
  3. 要求原文、issue、AWI、当時の計画ファイル
  4. 前段で動機または見逃しの過程を説明できない場合のセッションログ・会話履歴
- 拡張原因分析の資料を確認した後に対立する原因候補を列挙する。各候補を反証する事実の有無を確認し、棄却できない候補を区別してから因果を確定する
- 各層の探索結果として、探索先・実行したコマンド・観測時点・検出結果・確定できる範囲とその限界を記録する
- 集計値を記載する場合は判定条件と母集団の総数を併記し、判定条件は観測時点に依存しない形で定義する
- 作成時点を直接示さない指標を判定に用いる場合は、その指標では確定できない範囲を明記し、
  対象の存否は別の観測で確定する
- 資料が別環境にあり取得できない場合は、探索先と不足を明記する。内心は確認済みの資料の範囲で述べ、確認済みの最深層と棄却できない候補を区別する
- 推測した因果チェーンは、各段を資料または実機結果で裏付ける。原因候補の不確定性が類似範囲・処置を変える場合は、残る候補の和集合を対象にする
- 直接アクセスできない環境の事象で、コードベース調査と開発環境の再現だけでは因果を確定できない場合は、計画ファイルの起草を停止する。コンソールへ貼り付ける調査用コードまたはログ採取手順を提示し、ユーザーへ代行採取を依頼する。採取したデータで原因を確定してから起草を再開する
- 責務境界を越える呼び出し、非公開関数の横断利用、重複記録等の回避処理がある場合は、同機能で正しく動いている並列の処理（兄弟処理）、設計上の所有責務、その処理の導入コミットを比べる。局所処理の維持・共通化案と正しく動く既存処理への復帰案を比較し、局所処理を根本対策と判定できるのは、正しく動く既存処理を棄却する根拠を確認できた場合とする
- 外部から得た応答の意味は、公式の定義と生の応答で確定し、コードの一般的な語義や要約表示から推定しない。
  例えば、有効・無効のような二値状態をステータスコードで表現するAPIではコードの一般的な語義と実際の意味が反転しうる。
  外部ツールが表示する要約・短縮形（注釈の出典表示など）から原因や対象を確定する場合も、生の応答を取得して確認する
- 外部サービスへ依存する工程が期待どおり起動しない場合、自環境の設定・定義・実行状態の確認を
  2回以上繰り返す前に、そのサービスの公式ステータスページまたは障害情報を照会する。
  その工程へ影響する障害の掲載を確認できた場合は外部起因を支持する材料として扱い、
  自環境側の確認の反復を打ち切る。
  掲載を確認できない場合は原因を未確定として扱い、自環境側と外部側の追加確認へ進む
  （努力目標。掲載が無い場合は空振りとなるため）

## 原因分析の段階

本節は拡張原因分析の条件に該当する場合に適用する。

作り込み要因（なぜ誤りを成果物へ追加したか）と見逃し要因（なぜレビュー、テスト、監視で事前に検出できなかったか）の
2系統へ分け、各系統をL1からL4の順に分析する。

| 段階 | 作り込み要因で問うこと | 見逃し要因で問うこと |
| --- | --- | --- |
| L1 現象 | 何を誤って実装したか | どこで検出されなかったか |
| L2 判断 | なぜそれでよいと判断したか | なぜ問題だと判断できなかったか |
| L3 構造 | なぜその判断でも実装できたか | なぜ処理自身が不一致の時点で失敗せず、検出機構も働かなかったか |
| L4 システム | なぜその構造を許す規範・設計になっているか | なぜ検出を特定の仕組みまたは人へ依存させているか |

L3の作り込み要因には、既存規範が判断材料や結論を過剰に閉じ、目的に合う判断を妨げた構造も含める。条文の適用自体が不適切な成果を生む場合は、条文を足す前に制限の緩和、削除、一般化を調べる。

- 「考慮不足」「仕様を理解していなかった」「確認不足」などの記述はL1からL2に当たる事象の言い換えとして扱い、さらに深い段へ進む
- 対策を除く処置の決定は、原則として両系統のいずれかがL3へ到達した後に行う
- 両系統の分析は、L3の構造へ作用する処置で同じ失敗構造を断てる場合にL3で止め、止めた根拠を記録する
- L3へ到達できない系統がある場合は、確認した資料と到達できない理由を記録する。処置の根拠に用いるのはL3へ到達した系統とする
- 規範、仕様または設定の条文どうしが矛盾する事象では、各条文の導入変更を`git log -S`等で特定し、
  ユーザー指示由来かエージェント判断由来かを確定してからL2とL3を記述する。
  優先度は確定した由来で決め、既存の規範であること自体は優先度の判定材料に含めない

直接的原因は両系統の前段で確定する実行時・データ・設定上の機構とする。
直接的原因が処理の不成立である場合は、制御がその処理へ到達しない場合と、到達したうえで処理が失敗する場合を分けて列挙する。前者では取り消しや離脱の時点、保護機構の内側と外側、複数の確定処理の間の区間を分解する。後者では呼び出しが成立した証拠と、失敗を示す終了状態・出力を対応付ける。未到達の根拠は制御が到達しない流れの観測とし、到達したが問題を検出しなかった結果は後者の系統で扱う。
根本原因は到達した最深段の作り込み要因と見逃し要因を結び、同じ失敗構造を断つ条件を一般化した結論とする。
直接的原因との差分を含め、原因分析表の最深段のセルへ記録する。

各段は該当内容または「該当なし」と根拠を記録する。
資料不足は「未確認」と探索結果を記録し、「該当なし」とは別の記録として扱う。
参照すべき規範・仕様・設計文書の不在をL3、L4、根本原因のいずれかへ採用する前に、その事項が事象時点に存在した既存の上位規範から導かれるかを確認する。事象時点の存在は`SKILL.md`「直接的原因と事象時点の確定」に従って確かめる。
導かれる場合は、不在ではなくその規範を適用しなかった判断を原因とする。再発防止策には、規範の適用手順へ作用する処置を選び、同じ事項の文書への再掲は別の記録として扱う。
確認対象の上位規範には、`agent-toolkit/rules/01-agent.md`「判断指針」が定める消費主体と利用シナリオによる十分性判定を含める。

## 原因分析の品質確認

根本原因の確定後、類似見直しへ進む前に次の3点を確認する。

- 人物を変えても成立するか。担当したエージェントの注意力、経験または状況へ帰す記述が残る場合はL3へ戻る
- 対象を変えても成立するか。観測事象のファイル、機能、識別子を別の対象へ置き換えても同じ原因が成立するかを確認する
- 他の危険箇所を導出できるか。同じ原因から、まだ欠陥として観測していない箇所を1件以上挙げられるかを確認する

いずれかを満たせない場合は、原因の記述が事象の言い換えに留まっているとみなし、原因分析へ戻る。
確認結果を原因分析へ反映し、調査表の所定の行構成を保つ。

## 類似見直し

原因分析後、処置選定前に、根本原因が依存するL3・L4の構造を持つ箇所を見直す。
破られた不変条件・誤った判断規則を各1文で表し、その機構が依存する条件で意味上の母集団を定める。検索で抽出した候補は母集団へ到達する手掛かりとして扱い、集合全体の確定には規則への依存を確認する。
探索は`agent-toolkit:search`「検索の範囲と母集団」に従い、規則の定義元、生成側、消費側から機構への依存をたどる。語に一致しない消費側も所属を確かめ、各対象を規則の依存条件と現物から該当・非該当に分ける。観測事象とファイル・言語・症状・是正方法が違うことは除外理由にしない。
根本原因の各単位を規則と母集団へ対応付け、規則ごとに母集団の導出根拠、到達した定義元・生成側・消費側、候補の抽出方法、各対象の所属と除外の根拠、確認コマンドを既存の類似見直しの記録へ残す。
結果は是正対象（既存欠陥、横展開処置へ渡す）と予防対象（同じ構造の未発生箇所、再発防止策へ渡す）に分ける。

観測事象への因果的寄与を観測で確定していない潜在的な欠陥は、独立した通常AWIへ分離する。観測事象の直接的原因が確定したバグ単位と同じ計画へ含められるのは、その寄与を観測で確認済みである場合またはユーザーが併記を明示合意した場合に限り、その根拠を計画へ記録する。

## 処置の階層

処置の階層とは、不具合そのものへの対策、同じ原因による既存不具合への横展開処置、同じ原因の混入または見逃しへの再発防止策を区別する枠組みを指す。

- 対策: 観測した不具合そのものと、その不具合を固定した誤ったテスト・文書を直す
- 横展開処置: 類似見直しで見つけた、同じ原因による既存不具合を取り除く
- 再発防止策: 同じ原因による誤りの混入を防ぐか、混入しても見逃さない仕組みを追加する

事象と期待する契約、直接的原因、2系統の原因、類似見直しを確定した後、3層を混同せず、対策、横展開処置、再発防止策の順に実装対象を確定する。
処置を選ぶ際は、ユーザーが選んだ値、品質および適用範囲を元の要求と比べ、それらを保つ案を先に評価する。元の選択を変更する縮退案は、その変更への明示的な合意がある場合だけ採用する。復旧の成否だけで要求の達成を判定すると、障害を除いてもユーザーが選んだ結果を失う。
横展開処置の記録先は調査表の`類似見直し結果`行（AWIでは`## 適用範囲`）とし、是正対象として列挙した該当箇所へ対応づけて書く。

## 再発防止策

本節は拡張原因分析の条件に該当する場合に適用する。
再発防止策は次の優先順位で評価し、上位段が成立しない根拠を記録してから下位段を選ぶ。

1. 除去: 誤りの対象となった実装、分岐、オプション、独自機構または条文そのものを不要にする
2. 制約・集約:
   - 制約: 誤った値、状態または記述を表現できない入力形式、インターフェース、型または書式にする
   - 集約: 同じ判断を複数箇所で正しく行う必要をなくし、共通機構または単一の共通定義へ閉じ込める
3. 何もしなくても正しくする: 追加の作業をせずに書いた実装、記述または操作がそのままで正しくなるようにする
4. 自動検出: 自動チェック（lint、型チェックなど）、テスト、フックで混入または見逃しを検出する。選び方は後掲の「自動検出の選定」に従う
5. 手順・チェックリスト: エージェントが参照する工程へ判定を組み込む
6. コメント・文書: 維持する契約と選択の理由を記録する。外部契約の写像、直感に反する制約、意図的な仕様差はコメントまたは設計文書へ、何を維持するかとなぜその選択をしたかを記録する。説明コメントを書く対象は、コードだけでは意図が定まらない処理とする

段5と段6で失敗時の回復手順を規範や文書へ置く案は、配置先を`agent-toolkit:writing-standards`の`references/agent-documents-additions.md`「規範追記時の判定」の失敗時の回復手順の項に従って選ぶ。

段2の制約と集約は対象の表現手段に照らして同順位で評価する。
「正しく実装する方法」を定める前に「実装しなくて済む方法」を探す。規範を字面どおり適用したことが原因の事象では、段1の条文の緩和、削除、一般化を先に評価する。条文の追加を選ぶ場合は、これらで目的を達成できない根拠を記録する。

既存規範が作業の流れで適用されなかった事象では、段1から段3を評価した後、誤った判断の偏りを相殺する工程を先に検討する。独立文脈レビューによる問い直しや、決定前に反例を調べる工程が、その作業手順の中で実際に働くか確かめる。次に段4の自動検出を検討し、誤検出による停止と修正の往復費用を防止効果と比較する。最後に既存条文の語彙、例示、配置、条件と行動の対応を見直し、読み手が参照する場面で想起しやすくなるかを判定する。判定には`agent-toolkit:writing-standards`の`references/agent-documents-basics.md`の各規定が理由として挙げる読み手の特性を用いる。いずれの対策も成立しない場合は理由を記録して段5以下を評価する。条文を増やすだけの処置は、既存条文の改訂と集約を検討した後に限る。

対策、横展開処置または再発防止策として、新しい記録、フラグ、識別子、ハッシュ値または検証機構を加える案では、`agent-toolkit:writing-standards`の`references/design-heuristics.md`「自作機構の兆候と自問」の発火条件を確認する。
該当する案には同節の3つの問いを適用し、答えを処置の選定根拠へ書く。
（努力目標。再発防止の段4以下は新しい機構を加える形になりやすく、兆候を確認しないと段1の除去を検討しないまま機構が増える）

### 自動検出の選定

自動検出を選ぶ前に、元の要求と観測した事象に対して何を防ぐかを示す。実行時の値を測れることだけを設置理由にしない。停止に気付かない待機や手戻りで失う作業時間は取り戻せない結果として扱い、可逆な失敗として対策を見送る根拠にしない。hookを採用するか、遮断と警告のどちらにするかは、`agent-toolkit:writing-standards`の`references/claude-hooks-block-warn.md`「遮断・警告フックの成立条件」のQCDの費用比較で判定し、成立しない案は採らない。遮断の根拠に結果の不可逆性を用いる場合は、観測した事象の事実から判定する。例えばパッケージの削除では、設定ファイルを残す`remove`か残さない`purge`かを確かめる。事象の種類の印象だけで不可逆と判定すると、可逆な操作まで止める遮断が入る。

処理の結果が期待する状態と一致しないことを検出する案では、その処理自身が不一致の生じた時点で失敗する案を、別系統（定期実行の確認ジョブ、監視、通知など）で後から検出する案より先に評価する。処理自身を失敗させる案が成立する場合は、別系統を新設せずにその案を採用する。
別系統は処理と判定の時点がずれるため、処理と無関係な時点の状態（意図した手動操作など）でも失敗し、別系統の仕組みと、その仕組みの欠落を見つける仕組みの保守費用も恒常的に残る。
別系統で検出する案を選ぶ場合は、処理自身を失敗させる案が成立しない根拠（処理の完了後に外部から状態が変わり、処理の時点では不一致を観測できない場合など）を記録する。

自動チェックを選ぶ場合は、そのチェックの起動と実効性を無効化する変更（削除、起動条件の変更、空実装化）を何が検出するかを先に確定する。
設定の編集で無効化できる構成では、必須実行を強制する機構が対象環境に存在するかを一次資料で確認する。
存在しない場合は、自動チェックで保証できる範囲と保証できない範囲を分け、後者を人手確認へ割り当てて記録する。
自動チェックを追加するのは、保証範囲を確定した後とする。

毎計画・毎セッションへ恒常コストを課す再発防止策の新設は、処置の種別を問わず「類似見直し」の母集団を適用範囲の唯一の基準とする。規範・自動チェック・pretooluse hook・毎回のテストを含み、段4の案は全て対象とする。観測事象だけを是正して恒常コストを課さない対策は除く。範囲は誤りの機構への依存で定め、契機となった対象・工程・識別子では限定しない。
恒常コストは、失敗を観測した場合だけ実行する遅延評価案と、条件を満たす場合だけ適用する条件付き案を同じ階層で比較して抑える。
観測できた発生頻度とその処置の恒常コストの比較を記録してから確定する。
案の比較は`agent-toolkit:writing-standards`の`references/design-heuristics.md`「問題と手段の比例性」に従う。

## 再発防止策の必須性

拡張原因分析の条件に該当する不良では再発防止策を必須とする。
再発防止策は、その事象そのものの再発ではなく、同様または類似した原因による別の問題の発生を防ぐ。
`該当なし`と記録できるのは局所対応に限る。

再発防止策の評価そのものを省略できるのは次の場合に限る。各段を評価した結果として恒常コストに見合う案が無い場合は省略に当たらず、本節の後段が定める「採用する再発防止策なし」の終端で扱う。

- 同一セッションでその処置を実装済みである
- activeな既存AWIが根本原因と必要な全処置を覆う。部分被覆では不足分を投入する

省略は前記2条件に限る。事象時点に存在した規範へ違反した場合は、その存在や同趣旨条文の重複を省略事由にせず、未適用の原因へ処置を確定する。この扱いを「未適用規範の是正原則」と呼ぶ。
時点は`SKILL.md`「直接的原因と事象時点の確定」で確認する。原因の観点は起動契機・参照時点・判定条件・責務・想起性（語彙、例示、原則名、条件と行動の対応）とし、想起性の改善を条文の重複と混同しない。

由来（振り返り、ユーザーの手動投入など）を問わず、過去に採用して終端した対策と同じ原因の候補では「類似見直し」で導いた今回の母集団と、前回の母集団・除外理由・処置の適用条件を比較する。今回の発生条件が前回の範囲外なら範囲不足、範囲内で処置が適用されていなければ未適用、適用されても原因が残れば効果不足と分ける。比較の根拠を既存の原因分析の記録へ残す。有効性は条文の存在・過去記録の取得・処置の採用や終端に加え、今回の条件で原因を解消するかで判定する。同じ段でも残った条件を解消する別の処置なら採用でき、段の違いだけでは有効性を判定しない。

全ての段を評価しても恒常コストに見合う案を確定できない場合は、採用する再発防止策なしと判断して終端する。この終端は評価を終えた結果であり、前段の省略の条件を要しない。
判断の根拠として、観測事象、根本原因、評価した各段の案、各案を採用しない理由および恒常コストの見積りを`analysis-records.md`「原因分析の記録先」の`再発防止策`行へ記録する。
案の採否は技術判断としてエージェントが確定する。
あわせて記録した根拠を平易にした1行を、作業完了報告と報告用UWIの`### 自ら確定した判断`へ書き、回答を待たずに作業を続ける。`agent-toolkit:session-review`が扱う問題では振り返り結果報告が兼ねる。
再発防止策なしで終えた判断をユーザーが報告から見直せないと、同じ失敗が再発しても誰も気付かない。
ユーザーの選好に依存する要素が残る場合は、その要素だけを`agent-toolkit:user-confirmation-and-report`でユーザー確認する。

再発防止策は次の成立条件をすべて満たすものとする。

- 後続の実行でも参照される成果物または永続規範として残る
- 根本原因または見逃しの過程へ作用し、同じ原因による混入または見逃しを減らす
- 表面構造の異なる類似事象でも同じ因果へ作用する
- 適用境界が類似見直しの母集団を被覆する。観測事象そのものの再現へ適用境界が限定される処置は、対策として記録する
- 根本原因の各単位（不変条件・判断規則）へ混入防止または検出の処置を対応付け、共通処置の場合も各単位からの対応を記録する

個別計画の変更履歴、単一セッション内の説明、その実行だけで使うレビュープロンプトは後続の実行で参照されないため、
是正内容の確認記録として扱う。

## 再発防止としてのテスト

同じ問題が再発した場合は、以前の対策と再発防止策が対象にした入力・呼び出し元・発生条件を、今回の観測条件と比べる。
以前のテストが今回の処理へ到達するかを確認し、被覆しなかった条件とその理由を原因分析の見逃し要因および類似見直しへ反映する。
以前の処置を同じ形で反復せず、今回の条件にも届く処置を選ぶ。

テストを再発防止へ数える場合は、その事象の具体値を検証する再現テストと、
別入力・別呼び出し元でも同じ原因を検出する再発防止テストを区別し、是正前の版で失敗することを確認する。
是正前の版で失敗を確認できない場合は、テストが判定分岐へ到達していないものとしてテストを見直す。
期待値は要求仕様か契約から導出する。
実装の現行出力、現行文言、現行の設定値のいずれかをそのまま固定するテストは、
変更時の追随箇所を増やす一方で同じ原因の再発を検出しないため、追随の記録として扱う。
誤ったテスト期待値が見逃し要因である事象では、
そのテストを契約由来の期待値へ直すか削除する対策を含める。置換後の期待値は契約から導出し、同じ文言の固定は別のテストでも避ける。
自動チェックを新設する場合は、計画へ書く前に、判定対象を対象ツールの公開APIか実行結果から取得し、
対象ツールの選択・分類条件をチェック側へ再実装していないことを確認する。
ネットワーク、キャッシュ、権限などの実行環境依存は対象環境で観測し、その観測結果を計画の完了条件へ記載する。
新設・変更した分岐自体の効果は、`agent-toolkit:writing-standards`の`references/testing.md`「分岐条件の効果の裏付け」に従って確認する。
是正前の失敗確認における作業ツリーの置換・復元手段も同節に従う。
