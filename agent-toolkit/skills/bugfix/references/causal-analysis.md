# 因果の確定と原因分析の段階

本書は拡張原因分析へ進む場合と、根本原因の確定に履歴・記録の探索や2系統の分析を用いる場合に、資料の確認順、因果の確定、作り込み要因と見逃し要因の2系統4段階の分析、直接的原因と根本原因の記録を定める。分析で確定した根本原因から導く類似見直し、処置の階層と再発防止策は`root-cause-analysis.md`が定める。

## 拡張原因分析の資料と因果の確定

- 次の資料を上から順に確認し、設計判断を説明できた段階と確認不能だった資料を記録する
  1. 現行の実装、テスト、コメント、エンドユーザー向け文書、設計文書
  2. `git blame`、変更履歴、導入コミット、関連レビュー
  3. 要求原文、issue、AWI、当時の計画ファイル
  4. 前段で動機または見逃しの過程を説明できない場合のセッションログ・会話履歴
- 拡張原因分析の資料を確認した後に対立する原因候補を列挙する。各候補を反証する事実の有無を確認し、棄却できない候補を区別してから因果を確定する
- 各層の探索結果として、探索先・実行したコマンド・観測時点・検出結果・確定できる範囲とその限界を記録する
- 集計値を記載する場合は判定条件と母集団の総数を併記し、判定条件は観測時点に依存しない形で定義する
- 作成時点を直接示さない指標を判定に用いる場合は、その指標では確定できない範囲を明記し、
  対象の存否は別の観測で確定する
- 資料が別環境にあり取得できない場合は、探索先と不足を明記する。内心は確認済みの資料の範囲で述べ、確認済みの最深層と棄却できない候補を区別する
- 推測した因果チェーンは、各段を資料または実機結果で裏付ける。原因候補の不確定性が類似見直しの母集団・処置を変える場合は、残る候補の和集合を対象にする
- 直接アクセスできない環境の事象で、コードベース調査と開発環境の再現だけでは因果を確定できない場合は、計画ファイルの起草を停止する。コンソールへ貼り付ける調査用コードまたはログ採取手順を提示し、ユーザーへ代行採取を依頼する。採取したデータで原因を確定してから起草を再開する
- 責務境界を越える呼び出し、非公開関数の横断利用、重複記録等の回避処理がある場合は、同機能で正しく動いている並列の処理（兄弟処理）、設計上の所有責務、その処理の導入コミットを比べる。局所処理の維持・共通化案と正しく動く既存処理への復帰案を比較し、局所処理を根本対策と判定できるのは、正しく動く既存処理を棄却する根拠を確認できた場合とする
- 外部から得た応答の意味は、公式の定義と生の応答で確定し、コードの一般的な語義や要約表示から推定しない。
  例えば、有効・無効のような二値状態をステータスコードで表現するAPIではコードの一般的な語義と実際の意味が反転しうる。
  外部ツールが表示する要約・短縮形（注釈の出典表示など）から原因や対象を確定する場合も、生の応答を取得して確認する
- 外部サービスへ依存する工程が期待どおり起動しない場合、自環境の設定・定義・実行状態の確認を
  2回以上繰り返す前に、そのサービスの公式ステータスページまたは障害情報を照会する。
  その工程へ影響する障害の掲載を確認できた場合は外部起因を支持する材料として扱い、
  自環境側の確認の反復を打ち切る。
  掲載を確認できない場合は原因を未確定として扱い、自環境側と外部側の追加確認へ進む
  （努力目標。掲載が無い場合は空振りとなるため）

## 原因分析の段階

本節は拡張原因分析へ進む場合と、根本原因の確定に2系統の分析を用いる場合に適用する。

作り込み要因（なぜ誤りを成果物へ追加したか）と見逃し要因（なぜレビュー、テスト、監視で事前に検出できなかったか）の
2系統へ分け、各系統をL1からL4の順に分析する。

| 段階 | 作り込み要因で問うこと | 見逃し要因で問うこと |
| --- | --- | --- |
| L1 現象 | 何を誤って実装したか | どこで検出されなかったか |
| L2 判断 | なぜそれでよいと判断したか | なぜ問題だと判断できなかったか |
| L3 構造 | なぜその判断でも実装できたか | なぜ処理自身が不一致の時点で失敗せず、検出機構も働かなかったか |
| L4 システム | なぜその構造を許す規範・設計になっているか | なぜ検出を特定の仕組みまたは人へ依存させているか |

L3の作り込み要因には、既存規範が判断材料や結論を過剰に閉じ、目的に合う判断を妨げた構造も含める。条文の適用自体が不適切な成果を生む場合は、条文を足す前に制限の緩和、削除、一般化を調べる。

- 「考慮不足」「仕様を理解していなかった」「確認不足」などの記述はL1からL2に当たる事象の言い換えとして扱い、さらに深い段へ進む
- 対策を除く処置の決定は、原則として両系統のいずれかがL3へ到達した後に行う
- 両系統の分析は、L3の構造へ作用する処置で同じ失敗構造を断てる場合にL3で止め、止めた根拠を記録する
- L3へ到達できない系統がある場合は、確認した資料と到達できない理由を記録する。処置の根拠に用いるのはL3へ到達した系統とする
- 規範、仕様または設定の条文どうしが矛盾する事象では、各条文の導入変更を`git log -S`等で特定し、
  ユーザー指示由来かエージェント判断由来かを確定してからL2とL3を記述する。
  優先度は確定した由来で決め、既存の規範であること自体は優先度の判定材料に含めない

直接的原因は両系統の前段で確定する実行時・データ・設定上の機構とする。
直接的原因が処理の不成立である場合は、制御がその処理へ到達しない場合と、到達したうえで処理が失敗する場合を分けて列挙する。前者では取り消しや離脱の時点、保護機構の内側と外側、複数の確定処理の間の区間を分解する。後者では呼び出しが成立した証拠と、失敗を示す終了状態・出力を対応付ける。未到達の根拠は制御が到達しない流れの観測とし、到達したが問題を検出しなかった結果は後者の系統で扱う。
根本原因は到達した最深段の作り込み要因と見逃し要因を結び、同じ失敗構造を断つ条件を一般化した結論とする。
直接的原因との差分を含め、原因分析表の最深段のセルへ記録する。

各段は該当内容または「該当なし」と根拠を記録する。
資料不足は「未確認」と探索結果を記録し、「該当なし」とは別の記録として扱う。
参照すべき規範・仕様・設計文書の不在をL3、L4、根本原因のいずれかへ採用する前に、その事項が事象時点に存在した既存の上位規範から導かれるかを確認する。事象時点の存在は`SKILL.md`「直接的原因と事象時点の確定」に従って確かめる。
導かれる場合は、不在ではなくその規範を適用しなかった判断を原因とする。再発防止策には、規範の適用手順へ作用する処置を選び、同じ事項の文書への再掲は別の記録として扱う。
確認対象の上位規範には、`agent-toolkit/rules/01-agent.md`「判断指針」が定める消費主体と利用シナリオによる十分性判定を含める。
