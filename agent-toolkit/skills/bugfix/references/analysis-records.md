# 原因分析を記録する場所と表の構成

本書は、観測された不具合の原因分析を記録するエージェント向けに、記録先（AWIの`## 原因分析`節および計画ファイル（バグ））と各表の記載要領を定める。拡張原因分析の対象外となる不具合であっても、AWIの`## 原因分析`を起草する前、およびバグ調査の計画ファイルを作成する前に本書を確認する。

## 原因分析の記録先

確定したバグ単位は、観測された不具合を起点とする通常AWIの`## 原因分析`節に記録し、計画ファイルからはその節をWIファイル名で参照する。これにより、分析内容の記述をWI側の1箇所に集約して一元管理する。
計画ファイル（バグ）の作成条件と見出し構成は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「バグ調査」に従い、保存先および参照行の記述形式は同スキルの`references/plan-file-storage.md`に従う。

原因分析表は、`要因系統`、`L1 現象`、`L2 判断`、`L3 構造`、`L4 システム`の5列で構成し、`作り込み要因`、`見逃し要因`の2行をこの順序で記載する。各段位では必要な確認を終えた結論、または根拠のある`該当なし`を記載する。判断の具体的な検討過程は根拠資料やログへ残す。

調査表は`項目`と`内容`の2列で構成し、計画ファイル（バグ）では以下の8行をこの順序で記載する。

| 行名 | 記載内容 |
| --- | --- |
| 現象 | 発生した事象に加えて、発生条件と実際に得られた結果の値を含める。 |
| 期待する契約 | 対象の処理が本来満たすべき仕様、規範、または公開契約を記載する。 |
| 直接的原因 | 観測された不具合を直接引き起こした実行時処理、データ、または設定上の機構を記載する。 |
| 原因分析の根拠 | 再現テストの結果、`git blame`、不具合を混入させたコミット、および関連資料の該当箇所を記載する。件数やログの数値を挙げる場合は、その数値が主張対象を正しく表していることを確認した生成元と、原因の条件を満たさない比較対象群の数値（両群の件数）を併記する。実測で確認できていない数値は、`agent-basics:bugfix/references/root-cause-analysis.md`「直接的原因と事象時点の確定」に従って推定値として明記する。 |
| 対策 | 観測された不具合自体の修正と、その不具合を固定化していた誤ったテストやドキュメントの修正内容を記載する。 |
| 類似見直し観点 | 原因単位から導いた見直す対象と探す問題、および根本原因を構成する各要素との対応関係を記載する。QとC・Dの区別に基づく判定結果、重大度とその根拠、破られた不変条件または誤った判断規則、その適用境界は補足として記載する。 |
| 類似見直し結果 | 調査した母集団、是正対象と予防対象、必要となる横展開の処置、調査完了の結論、および再取得先を記載する。後続の担当者の判断に影響する探索の限界や残存リスクは本文に明記し、検索手順、非該当と判断した理由、独立走査や再検討の経過などの詳細情報は証拠ログに残す。 |
| 再発防止策 | 各策と複数の策の組合せについて、対策を選定した階層、根本原因の各要素への作用、必要性、確保するQ、選定理由、および維持すべき契約の記録先を記載する。再発防止策を採用する場合は、`agent-basics:bugfix/references/root-cause-remediation.md`「処置の階層」に従い、対策の有効性を検証するために用いた異なる形態の想定不具合（対象の所在の違い、または将来追加され得る別の形態）を1件以上挙げたうえで、その処置によって混入を防止できる理由、または確実に検出できる理由を記載する。観測箇所の回帰テストは`対策`行に記載する。再発防止策を採用しない場合は、`agent-basics:bugfix/references/root-cause-analysis.md`「QとC・Dの区別」に基づいて調査終了の結論を記載する。その際、`agent-basics:bugfix/references/root-cause-remediation.md`「再発防止策の必須性」で禁止されている根拠（適用が漏れていた既存規範、後続工程での回復、別論点の判断、未確定の寄与など）を終了の理由として用いない。各階層の案を比較評価した過程の詳細は証拠ログへ残す。 |

計画ファイル（バグ）では、バグ単位ごとの見出しの下に原因分析表と調査表をこの順序で配置する。拡張原因分析の対象外となる不具合であっても、類似箇所の見直しと再発防止策は`agent-basics:bugfix`の`references/root-cause-remediation.md`に定める共通基準に従って判定し、根本原因から導かれた見直し観点、結果、および再発防止策を記録する。表の行名、列名、配置順序は変更しない。
類似見直しの実施結果と独立別件の引き渡し先、再発防止の選定済み方針、実装と有効性確認の状態を記録する。表への記載だけで処置済みとは判断しない。

AWIの`## 原因分析`節は、原因分析表と、調査表から抽出した`直接的原因`、`原因分析の根拠`、`類似見直し観点`、`再発防止策`の4行をこの順序で並べた2列表によって構成する。`類似見直し観点`行には原因単位から導いた見直す対象と探す問題を記載し、QとC・Dの区別、重大度、および探索の深さに関する根拠を補足する。`再発防止策`行には上記の調査表と同じ内容を記載し、各策と組合せの作用、必要性、確保するQ、選定理由を対応付ける。具体的な変更内容の詳細は`## 反映内容と反映先`節に記載する。調査表の残りの項目については、`現象`と`期待する契約`をH1の直下に配置し、`対策`ならびに横展開処置と再発防止策の変更内容を`## 反映内容と反映先`節（処置の階層を項目ごとに明記）に配置し、`類似見直し結果`を`## 原因分析`節の4行表の外に配置する。
拡張原因分析の対象外となる不具合のAWIでも、バグ単位ごとに5列2行の原因分析表と前述の4行表を常に掲載し、対象条件に該当しない根拠を記載する。複数のバグ単位を含むAWIでは、`## 原因分析`節の中にバグ単位ごとのH3見出しを設けて整理する。

複数の観測事象を1つのバグ単位にまとめるのは、直接的原因と対策の変更対象単位がともに同一である場合に限る。根本原因が共通していることのみを理由に統合しない（たとえば同一の根本原因であっても、入力解析処理と状態更新処理のように直接的原因が異なる場合は個別のバグ単位に分け、逆に同一の原因と対策によって保存失敗と再試行停止の双方が解消される場合は1つに統合できる）。バグ単位を分けた場合であっても、同一の根本原因を持つ一連の不具合に対する類似見直しと再発防止の完了判定は、`agent-basics:bugfix`の`references/root-cause-remediation.md`「類似見直しと再発防止の完了」に従い、全件を対象として総合的に行う。
対応の網羅性を確認する際は、計画メタ情報に記載された関連WIの各バグが、WIの`## 原因分析`節、または計画ファイル（バグ）の確定済みバグ単位に正しく対応していることを確認する。
計画ファイルの`### 恒久化`節には原因分析を記録した資料への参照を記載し、類似箇所の見直しに関する記述はその参照先資料にのみ集約して記載する。
処置と完成条件の網羅に関する結論は、`agent-basics:bugfix`の`references/root-cause-remediation.md`「類似見直し」の比較元と対応付け、既存の類似見直し結果および再発防止策の記録欄へ残す。原因分析表と類似見直し観点には、必要な確認を終えた結論と根拠のある該当なしを記載し、調査途中の仮説や未確認が解消した場合に限り分析を確定する。
