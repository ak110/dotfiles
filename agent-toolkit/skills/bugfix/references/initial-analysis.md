# 初動の確定基準

本書は`SKILL.md`「初動と拡張原因分析の判定」の初動で、事象、期待する契約、直接的原因と発生条件を確定する基準と、対策の影響範囲を調べる範囲を定める。拡張原因分析の要否はこの確定の後に同節で判定する。

## 直接的原因と事象時点の確定

- 事象、実際の結果および発生条件は再現・ログ・実装から確定する。期待する契約は対象の目的を定める仕様・設計記録・規範から確定し、実装が述べる前提や文言は比べられる側として扱う
- 対照による直接的原因の確定: 直接的原因は、候補の機構だけを変えた対照で事象が変わることを観測して確定する
- 推定として扱う値: 相関だけの候補、条件を満たさない比較群を欠く集計、測定対象との対応を生成処理・公式資料・構造定義で確かめていない値は、直接的原因の確定に使わない
- 可変値の事象時点の確認: 設定、依存版、外部状態、規範・スキル・手順の条文その他の可変値を原因へ用いる場合（条文が適用されなかった、条文が欠けていたと述べる場合を含む）は、その値と文面が事象時点にも同じ形で適用されていたことを履歴か当時の記録で確かめる。履歴は`git log -S '<文面の特徴的な語>' -- <パス>`や、事象時点のcommitに対する`git show <commit>:<パス>`で調べる。事象後の現行の値と文面だけでは事象時点の値を確定せず、時点を確かめていない候補は推定として扱う
- 類似範囲: 類似範囲は直接的原因の機構を共有する対象全体とし、症状を観測した呼び出し元や、上限の超過など症状の程度で狭めない
- 競合の候補: 排他・競合・同時更新が原因候補となる場合は、原因の絞込みとそのためのユーザー確認の前に、状態の保持先と同期・更新の流れから共有状態を更新する主体を列挙し、各主体へロックの識別方法、共有範囲および取得する操作を対応付ける。更新主体は共有状態を書き換える主体に限り、同じホストの別プロセス、ロックを取らない手動操作、リモート経由で同期する別clone・別マシンなどが当たる。ロックが存在しても、そのロックを共有しない主体は競合の候補に残す。原因候補と確認の前提を点検するときも、この主体とロックの範囲の対応を判断材料にする
- 上流の挙動・変更が原因候補なら、該当機能の公式資料・ソース差分・提供元Issueで一次情報を確かめる。実装読解と実機再現は資料の補完とし、代わりにしない。内部名だけでなく機能の説明と公開資料の用語でも探す。回避処理には挙動差分と一次資料の裏付けを求め、既知の回避策・提供元の見解を採用するか、採用しない理由を原因分析へ記録する

## 対策の影響範囲

- 対策を確定する前に、その対策が変える値や動作の影響範囲を実装からたどる。直接影響範囲（変更前の動作を前提として書かれた既存の指定を含む）と別発生源（いずれも定義と範囲は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」）を対象とし、追随が必要な箇所を対策へ含める。影響が局所にとどまると考えられる場合も同じ範囲を調べる。除外、免除または解決済みとして扱う対策では、保証する側の規定や実装で先行動作が成立し、除外する側がその動作を前提としているか、双方の現物を読んで確かめる。主体をまたぐ場合も先行側の保証を確かめ、保証が無ければ同じ対策に含める

## 母集団と件数を数える層

- ユーザーが失敗例その他の観測事象の実物を提示した場合は、対象の母集団を発話の範囲語から確定してから発生条件を定める。提示された実物は母集団の一例として扱う。範囲語と例示が併存する場合の優先順位は`agent-toolkit:user-confirmation-and-report`の`references/user-utterance.md`に従う
- 症状の件数と該当対象は、エンドユーザーが観測する層（描画結果・CLI出力）で数える。中間値や一部の記録を使う場合は、消費層までの変換を実装からたどり、該当判定が変わらず、除外した記録に該当がないことを確かめる。成果物には数えた層と確認した変換を併記する。ユーザーによる実物の提示の有無を問わず、母集団・変換・抽出条件・上限を実装と比べる

## 外部からの不具合報告

- 外部から受け取った不具合報告が、別の環境、別の版、過去の時点のいずれかでは事象が生じないと述べている場合は、その主張の成否を判定してから発生条件を確定する。判定は報告が挙げる環境または版が配備する成果物の実装差分を取得し、その成果物へ差し替えて再現することで行う。判定結果と根拠を成果物へ書く。報告に事象が生じない環境・版・時点の記述が無い場合は、この判定を省く

## 作業途中で発見した事象

- 作業途中で発見した事象は、着手前に記録した状態と現在の差分を先に突合し、進行中の未コミット変更で混入した事象と着手前から存在する事象を区別する
  - 進行中の未コミット変更で混入した場合は、現在の指示、計画、実装判断を混入原因として調べる。既存機能の導入履歴は別の系統として扱う
