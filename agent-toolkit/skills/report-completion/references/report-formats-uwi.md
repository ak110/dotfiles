## 報告用UWIのフォーマット

振り返り結果を記載するときは、`report-formats-retrospective.md`「振り返り結果報告のフォーマット」の対象化から解消までの区別と残条件を、`### 振り返り`の既存結果行へ引き継ぐ。
未完了AWIによる被覆も、残る原因条件、処置担当、適用機会と観測結果を保ち、登録と原因解消を区別する。

報告用UWI（`SKILL.md`「工程」にて定義）の冒頭の問いには次の一文を用い、`## 選択肢と帰結`には`agent-toolkit:wi-standards`の事後承認型における2択の記述を使用する。

```text
<実行日>の<対象リポジトリ名>の作業結果について、この対応で問題ありませんか？
```

この固定の問いに続けて、成果の要点と、回答前に確認してほしい項目（未達・持ち越し事項、自ら確定した判断の有無）を1〜2文で記載する。
冒頭の語句の選定は、`agent-toolkit:wi-standards`の冒頭の語に関する基準に従う。

`## 判断材料`に含める各H3見出しは、次の順序に従い該当する項目がある場合にのみ配置する。
対話のやり取りをそのまま転記することは避け、1件1行の要点に整理して記載し、同一の内容を複数のH3見出しに重複して記載しないようにする。

1. `### 未達・持ち越し`: 元の要求単位における未達事項、未解決の問題、および先送りした事項を、`- <対象>: <残った状態>（理由: <理由>、再開条件: <条件>）`の形式で記載する。
   再開条件がまだ定まっていない場合はその項目を省略する。
   形式的な完了条件を満たしている場合でも、元の要求に対する未達があれば記載する。
   ユーザーの判断や対応を待っている項目については、保存した個別UWIのファイル名を再開条件に記載する
2. `### 処理中のご指摘への回答`: `- <指摘・質問>: <回答・対応結果>`の形式で記載する
3. `### 曖昧な要求の解釈`: `- <元の要求>: <採用した解釈>（理由: <採用理由と判断根拠>、範囲: <対応範囲>、結果: <実施結果とエンドユーザーが観測する結果>）`の形式で記載する
4. `### 自ら確定した判断`: ユーザーに質問せずに自ら確定した判断のうち、別の合理的なエージェントであれば異なる判断をする可能性があるものを、`- <決定>（理由: <理由>、最有力の対案: <対案>）`の形式で記載し、ユーザーが異論を持つ可能性が高い順に並べる。
   未検証の仮説を理由に対策を見送った判断の、検証AWIのファイル名か採否を左右しない理由の併記は、作業完了報告と同じ要件である
5. `### 成果`: 処理したWIごとに`- <ファイル名>: <H1タイトル>（<達成した結果>）`を1行ずつ記載する。
   達成した結果は、タイトルと重複する内容を省いて簡潔に記載する。
   公開やリリースなど、個別のWI単位に収まらない成果は1行で書き添える。
   検証結果については`report-formats-verification.md`「検証結果と実行記録」に従い、対象、結果、参照先を示す行を同一のH3見出し内に添える
6. `### 振り返り`: 手動またはbatchで振り返り自体を実施した報告に限り、次の各行を記載する。
   通常作業の報告には非同期振り返りの未実施を追加しない
   - 確定した問題と対策については、振り返り結果報告の`### 確定した問題と対策`と同じ区分（`AWI登録`、`AWI登録済み`、`実装済み`）を用いて1件1行で記載する
   - 見送り事項については、`- 見送り: <件数>件`に続けて`- <問題>: <見送った根拠>`を1件1行で記載する
   - 毎回`- 所要時間: <時間または計測できない理由>（目標との差: <差または算出できない理由>）`を1行で記載する
   - 毎回`- 費用確認: <資源使用の比較材料を確認した結論>`を1行で記載する
   - 効果候補ごとの「効果を確認」「効果不足」「適用機会なし」と根拠・保存結果・是正AWIを記載し、効果専用の未確認件数と理由も残す。
     候補・未確認が0件ならそれぞれ「なし」とする
   - 未実施または失敗した場合は、`- 振り返り未完了: <理由>`を1行で記載する。
     記載する理由は、振り返り結果報告の`review-session未実施`と同じ規定値に限る

作業完了報告の各節は、報告用UWIの対応する次のH3見出しに反映する（いずれかの節構成を変更する場合は、この対応関係も更新する）。

- 冒頭の1文および`### 成果`: `### 成果`に反映する。
  元の要求単位における未達事項は`### 未達・持ち越し`に記載する
- `### 検証結果`: `### 成果`に各検証結果と同一の実行・観測記録の参照先を残す。
  未達や判定不能が要求の残工程を示している場合は、`### 未達・持ち越し`にもその状態を対応付けて記載する
- `### 投入したWI`: 回答や操作を求めるUWIおよび先送りしたAWIは`### 未達・持ち越し`に記載する。
  振り返りの報告では投入したAWIを`### 振り返り`に、それ以外の作業では登録自体の成果を`### 成果`に記載する
- 途中報告で`予定`とした改善点の確定結果: `済`と`不要`は`### 成果`へ、確定できない対象は理由と残工程を`### 未達・持ち越し`へ記載する
- `### 自ら確定した判断`: `### 自ら確定した判断`にそのまま反映する

予告を出力した場合でも、振り返りの確定結果（確定した問題と対策、見送った問題と理由、投入したAWIのファイル名とH1タイトル）を記録し、予告時の`AWI登録予定`の行は投入結果に応じて`AWI登録`または`AWI登録済み`に置き換える。
セッション終了前に確定した振り返り自体の所要時間超過に関する結論と根拠も、同様の区分を用いて`### 振り返り`に記録する。

## 報告用UWIの確認と保存

本節は`report-completion`が定義する報告用UWIに適用する。
通常の事後承認型UWIには共通起草手順を適用し、`--question-type=post-approval`だけでは報告用と判定しない。
報告を作成するメインは、本書と`agent-toolkit:wi-standards`の`references/uwi-format.md`で確認する。
通常WIの共通起草3資料を報告だけの保存のために取得しない。
由来・認可・保存先・回答済みUWIとの整合は、`wi-standards`の当該操作の契約を維持する。

1. 未達を正しく伝えるため、原要求と実施結果・根拠を比較し、未達・未確認・持ち越しを成果と区別する。
   検証根拠は`report-formats-verification.md`「検証結果と実行記録」に従う。
   事実、他者の報告、推測、自らの判断を区別し、未確定のユーザー固有判断は既存の確認手順へ渡す。
2. 原稿をファイルへ保存し、新規は`atk wi add --dry-run`、更新は`atk wi edit --dry-run`で検証する。
   入力原稿と抽出保存先、終了状態、両出力を対応付け、検証・抽出保存に失敗した結果は使わない。
3. dry-runの抽出を先に読み、問い、成果の要点、確認してほしい項目が冒頭だけで分かることを、`wi-standards`冒頭の語の基準で判定する。
   その後で全文を読み、本文単独の可読性、節間の重複と原稿・抽出の一致を確認する。
   一致確認は同じdry-runに`--compare-opening-file <抽出の絶対パス>`を指定し、原改行・前後空白・末尾空行を含む完全一致で判定する。
   不一致なら対応を確かめ、原稿変更時は手順2へ戻って新しい抽出で確認する。
   本保存へ同じ指定を付けると一致時だけ保存する。
4. `wi-standards`「投入と取得」に従って保存し、保存本文一致確認、終了コード0、成功メッセージと警告を検収する。
   表記警告は該当行を確認し、その他の警告やエラーは修復する。
   失敗時にファイル名を取得済みなら、同じUWIを`atk wi edit --body-file`で修復する。
   未プッシュ通知は既存の投入手順で反映し、保存成功と警告の検収を終えて伝達完了とする。
