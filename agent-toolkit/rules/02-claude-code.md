# 02-claude-code.md: Claude Code固有事項

Claude Code固有の実装挙動・制約・サブエージェント運用を扱う。

## ツール呼び出し・タスク管理

- 独立した複数のツール呼び出し（複数ファイルの`Read`等）は同一応答内で並列に呼ぶ。依存関係がある場合のみ逐次実行する
- `AskUserQuestion`の`options`は1問最大4件。判断材料は同一ターン内のテキスト出力でまとめてから発行する。
  ただしシステムプロンプトの環境情報で稼働モデルがFableと確認できる場合、
  ツール呼び出しが後続するターンの地の文が表示されない事象が観測されているため、
  判断材料を`AskUserQuestion`の`question`本文または`options`の`preview`欄へ自己完結で含める
- 選択肢の判断材料へ、利用者が呼び出す対象となる外部ツール・組み込み機能・スラッシュコマンドの
  識別子を判定の根拠として挙げる場合、当該識別子が何を行うかを1文で添える。既に会話中で
  説明済みの識別子は対象外とする
- ユーザーへの質問・承認待ちでターンを終える場合は必ず`AskUserQuestion`を使う（地の文の問いかけのみで終えない）
- 複数工程・複数完遂条件を伴う起動プロンプトの場合は`TaskCreate`で各工程を独立タスク化し、
  全タスクが`completed`になるまで完了報告を発行しない
- `cat -A`等、非印字文字を可視化するオプションは使わない。確認は`Read`・`od -c`・`xxd`で代替する
- シェルメタ文字（バッククォート・ドル記号・二重引用符・改行など）を含む本文を単一引数として
  外部コマンドへ渡す場合、プログラミング言語の文字列シリアライザー（`JSON.stringify`等）の
  出力や二重引用符で囲んだ本文リテラルをコマンド文字列へ連結しない。
  文字列シリアライザーの出力は当該言語のリテラル記法であり、シェルの引用規則とは別体系である。
  本文は`$'...'`のANSI-Cクォートで囲むか、変数へ代入してから`"$VAR"`で展開する
- 本文を登録・送信するコマンドが警告またはエラーを出力した場合、終了コードが0でも
  登録結果を取得して本文と照合する。欠落を検出した場合は同じ経路で修復する
- 定型作業の前に、`agent-toolkit/scripts/`配下、各スキルの`scripts/`配下、関連スキル、
  対象リポジトリのタスクランナー定義（`Makefile`・`mise.toml`のtasks・`package.json`のscripts等）を
  確認する。対応する専用スクリプト・スキル・サブコマンド・タスクが存在する場合はそれを使う。
  タスクランナーへ定義済みの手順がある作業では、同等と判断したコマンドを直接組み立てず当該手順を使う。
  期待どおり動作しない事象を実測した場合は代替手順を採用し、実測結果を記録する（努力目標）
  - 複数ファイルに跨る置換は`agent-toolkit:pyfltr-usage`のgrep/replaceサブコマンドを使う。
    長出力のコマンド列は「サブエージェント運用」節に従い`agent-toolkit:shell-exec`へ委譲する。
    CI通過確認は`agent-toolkit:commit`スキルの専用ツールを使う
  - 判定対象は例示以外の定型作業も含む
- 100行超の連続ブロック置換は`Edit`の`old_string`にブロック全体を含めるか行範囲スライスを使う
- `run_in_background=true`の長時間ジョブは`Monitor`で全行取得するか完了マーカーを`grep -q`で待つ。
  マーカー未生成の背景タスク完了検出目的では`Monitor`を起動しない。
  ツール側で背景実行を指定したコマンドはシェル側を前景のまま保ち、末尾の`&`や`nohup`を重ねない。
  二重に背景化するとシェルの終了が完了通知となり、実ジョブの完了を検知できない
- 作業用の複製（git worktree等）内で起動したセッションが調査・計画作成へ着手する前に、
  `git fetch`後の分岐元との差分を`git log --oneline <分岐元>..HEAD`と
  `git log --oneline HEAD..<分岐元>`の双方で確認する。後者に出力がある場合は分岐元が進んでおり、
  調査対象の実装・反映先が変化している可能性がある。この場合は先に分岐元へ追随させてから着手する。
  追随を後回しにする場合は、調査で確定した事実が分岐元の変更で無効化されていないかを
  計画確定前に再確認する（努力目標。分岐元が動いていない場合は空振りとなるため）
- 1つのセッションで複数のリポジトリを扱う場合、`git`コマンドは`-C <絶対パス>`で対象リポジトリを
  明示する。Bashツールの作業ディレクトリは呼び出し間で持続するため、直前の呼び出しで移動した先が
  暗黙の対象となる。同一のコマンド列へ`cd`と`git`を並置しない
  （努力目標。単一リポジトリだけを扱うセッションおよび既存の呼び出しへの遡及適用は求めない）
- `git merge`進行中は`git stash`を使わない。退避は別パスへの`cp`または別ブランチ退避で行う
- 1つの応答内で先頭のツール呼び出しがブロック・エラーでキャンセルされると後続の独立呼び出しも連鎖キャンセルされる。
  各呼び出しの成否を`git diff`・`Read`で個別確認してから次工程へ進む
- auto modeでツール呼び出しが拒否された場合、推測でフラグ追加・迂回を試みず`agent-toolkit:agent-standards`
  `references/auto-mode.md`を参照してカスタムルール追加の要否を判断する
- 権限設定によりツール呼び出しが拒否された場合、参照範囲の追加や別コマンドでの迂回を試みる前に、
  `/etc/claude-code/managed-settings.json`・`~/.claude/settings.json`・
  リポジトリ直下の`.claude/settings.json`・`.claude/settings.local.json`を`Read`し、
  有効な拒否ルール・許可ルール・追加参照範囲を確認する。
  拒否ルールは許可ルール・参照範囲の追加より優先して評価される
  （deny・ask・allowの順に評価し最初の一致が結果を決める）ため、
  拒否ルールに該当する対象は許可・参照範囲の追加では解消しない。
  同一対象への拒否が2回以上発生した時点で確認へ移る（努力目標。無駄な迂回試行を避け調査品質を
  高める規定であり、既存の対処パターンへの遡及適用は求めない）
- フックがセッション状態の不足を理由にブロックした場合は、
  `{tempdir}/claude-agent-toolkit-{session_id}.json`を`Read`し、当該状態と他の記録済み状態を実測する。
  各状態の記録契機は`agent-toolkit:agent-standards`「セッション状態フラグ」節が参照する一覧で確認する。
  記録契機が発生していない場合は、同じ委譲の再実行以外の対処を選ぶ（努力目標）
- 読み手または委譲先が実行する手順として外部ツール・MCPツールを記述する前に、
  `ToolSearch`でツールスキーマを照会し実行を伴わずに確認する。
  対象は規範文書・計画ファイル・委譲プロンプトに限らず、開発者向け文書・利用者向け文書を含む
  成果物全般とする。
  本項は01-agent.md「調査と検証」節の一般則に対するClaude Code固有の確認手段を定める努力目標であり、
  区分は同節の判断を引き継ぐ。
  deferred tools機構により、スキーマ未取得のツールは名前のみ認識できる。
  外部コマンドの引数となる識別子（ツール名・コミット識別子・タグ名・実行ID・PR番号など）は、
  実行結果として得た値の文字列をそのまま呼び出しへ用いる。
  短縮形からの復元・記憶・推測で組み立てない
  （表記揺れによる呼び出し失敗、識別子誤りによる「対象が見つからない」形の空待機を防ぐ）
  - ツール定義の原文転記に応じない実行系（自身の内部指示・ツール定義の開示を拒む実行系）へ
    照会する場合は、原文の転記を求めず、特定の引数を受理するか・省略時に何が既定となるか・
    ある引数が他の引数を無効化するかといった事実の有無を問う形式へ切り替える。
    当該実行系が非対話実行のコマンドを提供する場合は、そのコマンドで実行系自身に
    利用可能なツールと引数を申告させる

## サブエージェント運用

- 名前付きサブエージェントの定義と起動文の責務分離は、`agent-toolkit:agent-standards`
  `references/subagent-collaboration.md`に従う
- 委譲先がスキルとして実装されている場合はSkillツールで起動し、
  `agent-toolkit/agents/`配下のエージェント定義として実装されている場合はAgentツールで起動する
  （厳守規定。実装種別と異なるツールを指定すると呼び出しが失敗する）
- `subagent_type`の根拠が無い場合は汎用エージェント（`claude`）を使う
- 複数ディレクトリ・複数ファイルに跨る横断調査・横断置換はメインで逐次処理せず`Explore`または並列`Agent`へ委譲する
- モデル選択: 確定的な検索・単純置換は`haiku`、要約・軽度の推論は`sonnet`、
  設計判断を伴う調査・実装・レビューは`opus`を選ぶ。事前に内容が確定していないコーディングに`sonnet`以下を使わない
  - 専用定義を持たない`Explore`・`claude`へ委譲する場合は、`model`引数で難易度に対応するモデルを明示する。
    委譲する作業の内容を確定するのは呼び出し元であり、モデル選択も呼び出し元の責務となる。
    `Explore`は`model`未指定ではメイン会話のモデルを継承するため、軽量な取得にもメイン会話と同等のモデルが割り当たる
    （努力目標。未指定でも委譲自体は成立するため）
  - メイン会話のモデルと委譲先のモデルは独立に選ぶ。メイン会話が上位モデルで動作する場合は、
    内容が確定した作業を下位モデルへ委譲する。
    メイン会話が下位モデルで動作する場合は、設計判断を伴う難所だけを`model: opus`の委譲先へ切り出す。
    このモデル選択は、委譲自体が同一モデルでも成立し、料金と所要時間の改善を目的とするため、努力目標とする
- 委譲先だけが使うスキル本体と参照文書は、委譲先が起動直後に読み込む。
  委譲元は合意事項、調査済み事実、完了条件をプロンプトへ含める
- 判断材料が2万文字を超える場合は、`mktemp -d`で作成した専用ディレクトリへ
  所有者だけが読み書きできるMarkdownとして保存する。
  プロンプトは絶対パスと要約を渡し、委譲先は着手時にファイルを読み込む。
  委譲元は完了報告の受領後に、自身が作成した専用ディレクトリだけを削除する
- `gh`や`glab`の操作、pyfltrなど長出力が予想されるコマンド列は
  Skillツールで`agent-toolkit:shell-exec`を起動して委譲する。
  メインへは終了状態、警告、要求した値、後続判断に必要な要約だけを返させる
  - push後のCI通過確認の待機は委譲対象から除く。担当分離の理由は
    `agent-toolkit/skills/plan-mode/references/plan-impl-caller-reception.md`「実体照合と後続工程」節
    （SSOT）を参照する。当該待機は`agent-toolkit:commit`スキル「push後のCI通過確認」節に従い、
    `git push`を実行した主体が自身で実施する
  - CI失敗後のログ取得・要約は長出力を伴うため引き続き委譲対象とする
- 同一セッションで取得済みのファイルは、変更を観測するまで保持済み内容を再利用する。
  編集後の検収、外部更新後、正確な現行文面が必要な差分適用前に再取得する
- 計画ファイルなどを反復編集する工程は、整合確認と修正を同じ委譲先へまとめる
- `plan-file-finalizer`と`plan-impl-executor`はfrontmatterのモデル指定を適用する。
  AgentまたはTask起動時に`model`引数を指定しない
  （PreToolUseフックが機械的にブロックする）。既定モデルの変更が必要な場合は呼び出し側でなく
  エージェント定義自体のfrontmatterを改訂する。
  両定義の役割と委譲関係は`agent-toolkit:agent-standards`
  `references/subagent-collaboration.md`「計画処理の委譲関係」節を参照する
- 委譲の完了は起動形態によらず同一手順で検収する。完了報告を受領したら、受領経路を問わず
  まず成果物を実測し（`git log`・作業ツリー差分・成果物ファイルの実在と分量）、
  次に完了報告本文の必須欄を検査する。実測と本文が一致しない場合は未完遂として扱う。
  `idle_notification(available)`だけでは完了と判定しない。
  受領した本文に待機表明だけがあり完了報告を欠く場合は、残る工程を実測で確認して巻き取る
  - 通常のツール配送経路は戻り値と完了通知（task-notification）の2種である。
    `run_in_background`を省略した起動が背景実行へ転換されると受領経路が戻り値から完了通知へ変わるが、
    どちらで受領したかは検収の成否を左右しない。
    孫委譲時の記録ファイル直接読み取りは、通常のツール配送経路が成立しない場合の
    例外的な受領手段として扱い、読み取った完了報告へ同じ検収手順を適用する
- AgentまたはTask起動では`name`パラメーターを渡さず、`run_in_background`を省略する。
  `name`付きbackground起動で完了通知が配送されず停滞する事象は技術的な不成立に該当するため、
  `name`パラメーターの禁止は厳守規定とする。
  `run_in_background`の省略は起動形態を固定せず、実際の受領経路は実行結果から判定する
  - 独立した複数の呼び出しは同一応答内へ並置する
  - 名前付き定義では、foreground完了報告の返却方法、`SendMessage`不使用、
    待機対象の結果を含む完了報告の要件を定義本文へ置く
  - 専用定義を持たない`claude`と`Explore`の起動文は、完了報告をツール戻り値で返す指示、
    `SendMessage`で能動送付しない指示、待機対象の結果を含めて1回で返す指示、
    完了報告を日本語で書く指示を含む。当該2種は規範を読み込まないため、
    `01-agent.md`「日本語」節の適用宣言が実効せず、起動文への明示が唯一の伝達経路となる
- 孫エージェントの完了報告は親へ配送されない実測がある。
  実測日は2026-07-31で、`name`省略、`run_in_background`省略、待機3分以上、
  完了報告本文にマーカーを含む条件で確認した。
  当該実測は特定バージョンと前掲の起動条件での観測であり、
  サブエージェント完了時に通知されるとする公式仕様と異なる。
  孫へ委譲する場合は、記録ファイル直接読み取りを含む受領手段を確保する。
  受領手段を確保できない場合はMCPツール（`mcp__codex__codex`等）を用いるか自身で実施する
- 起動済みの子エージェントへ同一作業の続きを依頼する場合は、エージェントIDまたは名前を指定した
  `SendMessage`で再開する。再開されたエージェントは過去の会話履歴、ツール呼び出しと結果、
  推論を保持する。`SendMessage`による再開は背景実行となるため、完了報告は前掲の検収手順で受領する。
  新規起動は、既存の履歴から分離した新規文脈が必要な場合に限定し、
  その場合は必要な前提を新規起動のプロンプトへ本文で渡す
  `01-agent.md`「サブエージェント運用」節が定める利益のうち独立コンテキストを目的とする委譲は、
  当該の新規文脈が必要な場合に当たる
- 委譲先が実行する検証コマンド（テスト実行・lint実行など）は、Bashツールのタイムアウト引数を
  上限まで引き上げた前景実行を既定とする。上限時間内に収まらない場合は検証対象を分割して
  複数回の前景実行に分ける。背景実行は分割できない場合の例外とする。
  例外に該当して背景実行したジョブを待つ場合は、待機条件を満たした時点で終了する単一の
  前景実行を自身のターン内で完了させ、待機対象の結果を含む完了報告を1回の戻り値として委譲元へ返す。
  明示的に背景実行したジョブの完了通知に依存した状態でターンを終えない。
  起動が自動的に背景実行へ転換された場合は本規定の対象外とし、前掲の検収手順で完遂を判定する
- 新規起動の前に、同一の対象範囲・同一の計画ファイルを扱う既存サブエージェントの生存を
  `git log`・作業ツリー差分・成果物ファイルの`mtime`で確認する。稼働継続中と判定した場合は
  新規起動せず既存へ`SendMessage`で継続を促す。停止を指示した場合は、指示が成功を返したことだけを
  根拠にせず、指示後に間隔を空けて取得した2回の実測（成果物側の作業ツリーの変更・コミットの識別子・
  対象ファイルの更新時刻）どうしが一致することを確認してから代替の担当を起動する。
  指示前の状態との比較では、停止指示直後の最終コミット等の正常な後始末を未停止と誤判定するため用いない。
  1回だけの即時確認は、実行中の処理が確認直後に反映される可能性を排除できないため十分でない
- 委譲先が稼働している間、メイン側は委譲先の対象範囲に含まれるファイルを編集しない。
  レビュー指摘の修正をメイン側で実施する場合は、先に当該委譲先を停止させ停止の成立を確認したうえで、
  作業ツリーとコミット履歴の状態を確認してから編集へ着手する。
  完了報告の受領は委譲先の稼働終了を意味しない。
  foreground実行では完了報告の受領時点で委譲先が終了しているため、追加の停止確認を要しない。
  background実行と孫委譲の記録ファイル経由では、受領後も委譲先が稼働しうる。
  メイン側が委譲先の対象範囲へ書き込む前に作業停止を指示し、
  本節の停止手順で停止の成立を確認してから編集する。
  編集の競合を検知した場合は、どちらの版を採用するかを確定してから統合し、
  破棄した内容を委譲先へ通知する
- ユーザーからの追加指示・方針変更・是正要求（介入）が生じた時点では、稼働中のサブエージェントの強制停止・再起動を既定の対応としない。`SendMessage`で介入内容を追加指示として伝え、委譲先自身に反映させることを既定とする。停止が必要なのは、介入により当該委譲先の対象範囲・前提が無効化された場合（対象ファイル一覧の変更・方針の反転など、続行が誤った成果物を生む場合）に限る。この場合も本節の停止手順（新規起動前の生存確認・2回の実測一致確認）を経てから代替の担当を起動する
  停止が必要と判定した場合も、停止の前に当該介入の実施を稼働中の作業の完了後まで遅らせられるかを判定する。介入が`agent-toolkit/rules/01-agent.md`「ユーザー発話の解釈」節が定める明示的な即時要求を伴わず、実施を遅らせても成果物が誤らない場合は、停止せず完了を待ってから実施する。遅延できない場合に限り停止手順へ進む。
- サブエージェント完了報告の数値と実測が食い違い差し戻した場合、成果物ファイルの更新時刻が
  差し戻し送信以降に動いている間は停止・巻き取りの判断を保留し、`SendMessage`での催促にとどめる。
  更新元が委譲先か別主体（CI・formatter・並行セッション等）かを区別できない場合も、
  区別できるまでは保留側へ倒す。差し戻し直後の即時観測だけで未対応と断定せず、
  成果物の初回更新を確認するまで待つ。更新が観測されない場合は`SendMessage`で1回催促し、
  催促後も間隔を空けて再確認して応答が無ければ巻き取りへ進む
- 対応方針の選択・推奨を求める調査を委譲する場合は、委譲先へ対象リポジトリの
  明文化された方針文書を読ませる。委譲先の報告には推奨案と方針の整合判定を含め、
  方針と衝突する案を推奨する場合は衝突箇所を明示させる
- 方針が流動的な間（ユーザーとの対話で要件が変わり続けている間）は、発話の都度
  稼働中の委譲先へ中継せず、メイン側で方針を確定してから一括で送付する。
  稼働中の同一委譲先へ、先に送った方針と矛盾する差し替えを2回送る必要が生じた時点で、
  委譲先へ作業の保留を指示する。
  メイン側で方針を確定し、旧方針との差分を統合した指示を1回で送付してから再開させる
- 起動文へ明示した同一の制約に委譲先が2回続けて違反した場合、同じ制約を伝え直す起動を繰り返さず、
  呼び出し元が当該工程を巻き取るか別の経路へ切り替える。切り替えの前に、違反が委譲先の出力形式に
  起因するか受信側の判定条件に起因するかを実装で確認する。受信側に起因する場合は判定条件を是正し、
  委譲先へ同じ制約を再送する対処を選ばない
- この保留条件は稼働中の委譲先への追加指示を対象とする。
  停止後に新規起動する場合の文脈引継ぎは、既存の再起動規定を適用する
- 委譲を停止した場合は、再起動の前に停止時点の成果物を全文検収し、
  当該成果物が完成条件を満たすかを判定する。
  完成条件を満たす場合は再起動せず、呼び出し元が成果物を引き取って確定する。
  完成条件を満たさない場合に限り、再起動時の引き継ぎ規定に従う
- 同一対象で再起動する場合、停止した前エージェントの実行内容から
  完了済み工程・試行済みのアプローチ・観測できた失敗事象を抽出し、起動プロンプトへ引き継ぐ。
  白紙から同じ失敗を再分析させない
- backgroundで稼働する委譲全般（並列起動に限らず、foreground指定が自動的にbackgroundへ
  転換された場合を含む）は`git log --oneline -10`・`git status --short`・`TaskList`・
  成果物ファイルの`mtime`で停滞を検知する。
  `subagents/*.meta.json`の`agentType`・`description`・`toolUseId`・`spawnDepth`・`parentAgentId`から、
  同一種別かつ同一用途の累計起動回数も観測する。
  並列起動した複数インスタンスは各1回として合算する。
  実装差分レビューの上限は一般の起動回数と区別し、
  `agent-toolkit/skills/codex-exec/references/plan-codex-implementation-review.md`が定める
  二系統一組の最大5ラウンドで数える。
  累計起動回数が5回を超えた場合は、
  進捗の有無によらず収束を促す。
  間隔を空けた複数回の観測で前回との差分が無ければ停滞と判定し、判定した時点で同一ターン内に
  `SendMessage`による継続の催促（1回）まで完遂してからターンを終える。催促後も間隔を空けて
  再確認し応答が無ければメイン側で
  `agent-toolkit/skills/plan-mode/references/plan-impl-caller-reception.md`が定める完遂順序
  （実装→検証→コミット→二系統レビュー→push→CI通過確認）のうち未完了の工程を巻き取るか、
  縮減した新規サブエージェントを起動する。観測した結果はユーザーへ短く提示する
- 停滞検知の仕組みは`ScheduleWakeup`・`CronCreate`・Bash background loopのいずれかで実装し、
  全background起動の完了後またはセッション終了時に停止・登録解除する
- 成果物ファイルを生成・更新する委譲では、委譲プロンプトへ書き込み主体を明示する
  - 委譲先が書き込む場合、委譲元は完了報告の受領まで当該ファイルを読み取り専用として扱う
  - 委譲元が書き込む場合、委譲先へ読み取り専用である旨を伝える
  - レビュー専用として委譲先を起動する場合、委譲元は起動前の対象ファイル内容を
    `cp`によるバックアップまたは起動前状態へ適用可能なパッチとして保存する。
    内容ハッシュは変更検知用として別途記録し、完了報告の受領後に再計算する。
    変更検知後の復旧と実装担当への引き継ぎは、
    `agent-toolkit/skills/codex-exec/references/plan-codex-implementation-review.md`
    「変更検知と復元」節の手順に従う
  - 委譲先が受領手段を確保したAgent/Task経路またはMCP経路へ再委譲する場合も、
    同じ取り決めを引き継がせる
- 作業用の複製（git worktree等）内で起動したセッションが書き込みを伴う委譲をする場合、
  委譲プロンプトへ作業ディレクトリの絶対パスと、複製元リポジトリのファイルを編集しない旨を明記する。
  委譲先がさらに別の実行系（`mcp__codex__codex`の`cwd`指定を含む）へ再委譲する場合も
  同じ制約を引き継がせる。
  委譲先は自身で作業ディレクトリを解決せず、受領した絶対パスを用いる。
  委譲プロンプトへ、git操作を`git -C <作業ディレクトリの絶対パス>`の形で行う旨と、
  `git rev-parse --show-toplevel`・`cd`後の相対パス・ホームディレクトリ起点の解決など
  作業ディレクトリを自己解決する手段を用いない旨を明記する。再委譲時にも同じ形式を引き継がせる。
  `git rev-parse --show-toplevel`等の自己解決は呼び出し元プロセスのカレントディレクトリに依存する。
  委譲先プロセス（別のサブエージェントやMCPサーバーの子プロセスなど）のカレントディレクトリが
  呼び出し元と一致しない場合、複製元など意図しないパスを指す。
  直後のバレット群が定める記録・変化検出・復旧の規定は、本予防が破られた場合の備えとして併せて実施する
- 作業用の複製（git worktree等）内で起動したセッションが書き込みを伴う委譲をする場合、
  委譲開始前に想定先の作業ディレクトリと複製元リポジトリの双方について次を記録する。
  （厳守規定。記録が無いと委譲後の観測だけでは既存の変更と委譲由来の変更を区別できず、
  復旧が意図しない内容の破棄を招く技術的な不成立につながる）
  - `git rev-parse HEAD`（基準コミット）
  - 追跡ファイルの変更内容: `git diff HEAD`の出力を復旧用の一時ディレクトリへパッチとして保存する
  - 未追跡ファイルの内容: ファイル一覧と内容そのものを`cp --parents`等で復旧用の一時ディレクトリへ
    複製する（出力行の記録だけでは復元できないため、内容自体を保存する）
  - 委譲先の最初の書き込みを観測できる時点（foreground実行では完了報告の受領時点、
    background実行では停滞検知の観測時点）で、複製元側の`git rev-parse HEAD`・`git diff HEAD`・
    未追跡ファイル一覧を再取得する。未追跡ファイルは一覧の追加・削除に加え、委譲前から存在する
    各ファイルの内容を委譲前に複製した内容とバイト単位で比較し、内容変化の有無も検出する
    （一覧の再取得だけでは、既存の未追跡ファイルへの追記のように一覧に現れない変化を見落とす）
  - HEADの変化と追跡・未追跡ファイル内容の変化（一覧の増減・既存ファイルの内容差分の双方）を
    すべて検出対象とする（委譲先がコミットすると作業ツリーは清浄に戻るため、作業ツリー差分の
    比較だけでは見落とす）
  - HEADの変化または追跡・未追跡ファイルの内容変化のいずれかを検出した場合、background実行は
    同節の既存の停止手順（指示後に間隔を空けて取得した2回の実測どうしが一致することを
    確認してから代替の担当を起動する）で委譲先を先に停止してから、以降の退避・報告・復旧へ進む。
    委譲先を停止せず判断待ちへ入ると、待機中に委譲先が追加のコミット・書き込みを行いうる。
    その場合、先に取得した退避内容が最終状態を保全しないまま古びる。
    foreground実行では完了報告の受領時点で委譲先が既に終了しているため、
    停止手順を適用せずそのまま進む
  - HEADが変化していた場合は`git checkout`等による自動復旧をしない。想定外のコミットを
    `git branch <退避用ブランチ名> <コミットハッシュ>`で参照可能な状態のまま保全し、
    基準HEAD・想定外コミットのハッシュ・退避先ブランチ名をユーザーまたは呼び出し元へ報告する。
    以降の対応（基準HEADへの復帰要否）は報告先の判断に委ねる。
    HEAD変化を報告した場合、基準HEADへの復帰要否が確定するまで追跡ファイルの内容復旧へ進まない
    （復帰前に基準コミット以外の内容へ書き戻すと、委譲先の成果物と復旧内容が二重に混同する）
  - 復旧操作（`git checkout`・ファイル削除・パッチ適用等の不可逆操作）へ進む前に、変更ファイルの
    一覧・変更内容の要約・退避先パス・具体的な復旧手順をユーザーまたは呼び出し元へ提示し、
    明示的な実行確認を得る。
    この確認は厳守規定とする。確認なしに復旧操作を進めると、委譲前から存在した
    利用者の既存変更を誤って破棄する可能性がある
  - 確認を得たうえで、追跡ファイルは委譲前に記録した基準コミットのハッシュを明示して
    `git checkout <基準コミットのハッシュ> -- <path>`で当該コミットの内容へ戻した後、
    委譲前に保存したパッチを`git apply`で適用し直し、委譲前の内容（既存の変更を含む）を再現する。
    実行時点で可変な`HEAD`という記法は使わず、必ず記録済みのハッシュ値を参照する
    （HEADが変化していた場合、`HEAD`という記法は基準コミットではなく変化後の位置を指すため、
    基準コミットへ戻すことができない）。
    未追跡ファイルは委譲前に複製した内容で上書きし、委譲後に新規追加された未追跡ファイルは削除する。
    対象は委譲前後の比較で判明した変更ファイルに限る。`git stash`は使わない
  - 復旧後は想定先・複製元の双方を再実測し、想定先の書き込みが保持されたまま
    複製元が委譲前の記録と一致することを確認する
- ファイルを生成・更新する委譲では、成果物の絶対パスと、実在・分量を示すコマンド
  （`ls -l <パス>`・`wc -l <パス>`等）の実行結果を完了報告へ含めるよう委譲プロンプトで求める
  - 委譲先が受領手段を確保したAgent/Task経路またはMCP経路へ再委譲した場合も、
    委譲先自身が実在を確認してから報告させる
- サブエージェントは自身と同一の`subagent_type`を持つ別のサブエージェントへ委譲しない。
  委譲された作業は自身で完遂し、作業量を理由に同種へ再委譲しない
  - レビュー・調査などの補助的な作業をAgent/Task起動で孫へ委譲する場合も、
    記録ファイル直接読み取りを含む受領手段を確保する。
    受領手段を確保できない場合はMCPツール（`mcp__codex__codex`等）を用いるか自身で実施する
  - 起動元が送った是正指摘をAgent/Task起動で孫へ渡す場合は、
    記録ファイル直接読み取りを含む受領手段を確保する。
    受領手段を確保できない場合は、委譲先自身が反映するかMCP経路へ渡す。
    再委譲した場合は、渡した旨と渡し先を完了報告へ記載する
- サブエージェントは独立コンテキストで動作するため、委譲プロンプトへ相対参照（「上記」「前述」等）を含めない。
  合意事項、調査済み事実、完了条件は本文内で完結させ、委譲先だけが使う参照資料は起動直後に読ませる
- 計画ファイル作成のplan mode下委譲では、サンドボックスパスへの書き込みをメイン側が検収し正規パス
  （`~/.claude/plans/`配下）へ反映する。委譲先は正規パスの削除・移動をしない
- サブエージェントは`AGENTS.md`・`CLAUDE.md`・`.claude/rules/`配下・`agent-toolkit/`配下の規範文書を
  編集しない。例外はメイン側起動プロンプトで改訂を明示許可された場合に限る
  （`plan-impl-executor`が規範文書を対象ファイル一覧に含む計画を実装する場合など）
- 委譲されたタスク範囲を超える不可逆操作（`git push`・削除等）は、
  完了報告で委譲元へ返却し、自身では実行しない。
  委譲範囲に明示されていないフィードバック投入と、
  投入先リポジトリを委譲先自身が決定する投入も返却対象とする。
  この場合は指摘内容と投入すべき旨を完了報告へ記載し、投入先の決定と投入を委譲元へ返却する。
  委譲元がフィードバック投入を明示的に指示した場合は、当該指示の範囲で投入してよい。
  対象には、フィードバック処理スキルが分類委譲先へ確認事項の記録を求める場合などを含む
- サブエージェント出力（レビュー指摘・調査結果）の統合は、通番・重大度／観点・区分・箇所・内容・対応方針の
  6列表で提示してから修正に着手する。対応不要と判断した指摘は
  `（メイン判断: 不対応 — <理由>）`または`（ユーザー判断: 不対応 — <理由>）`を末尾に注記する。
  この注記は、レビューを起動した主体ではなく、当該レビュー対象の成果物に責任を持つ最上位の主体が付す。
  委譲先が受領手段を確保したAgent/Task経路またはMCP経路でレビューを実施して
  指摘があった場合、委譲先は指摘内容と自身の見解を完了報告へ記載するに留め、
  不対応注記を自ら付さない。
  委譲元は受領した見解を実測で確認したうえで注記を付す
- サブエージェントの動作・運用自体を分析対象とする場合、稼働中の当該サブエージェントの完了報告を
  観測源に含めてから結論を確定する。完了報告には運用上の観測事実が含まれるため、分析結果の記録・投入より先に受領する
- セッション記録（`~/.claude/projects`配下）を集計対象とする場合、同一事象が親セッションと
  子セッションの記録へ重複して現れる構造を先に確認し、重複を除外したうえで件数を確定する
  （努力目標。集計値の正確性を高める規定であり、既存の集計処理への遡及適用は求めない）
  - 記録階層は深さ2（`<project>/<session-uuid>.jsonl`、セッション本体）と
    深さ4（`<session-uuid>/subagents/agent-<agentId>.jsonl`、サブエージェント記録）の2値のみである。
    孫エージェントの記録も祖先セッション直下へフラット格納されるため、深さは常に4である
  - セッション単位の事象（起動・完了報告等）を数える用途では深さ2限定が有効だが、
    サブエージェント内部のイベント（ツール呼び出し等）は深さ2限定では取りこぼす。
    適用条件を明示せず用いない
  - サブエージェントの起動を1件ずつ数える用途では`subagents/*.meta.json`の
    `agentType`・`description`・`toolUseId`・`spawnDepth`・`parentAgentId`を典拠とする
- 委譲元が委譲先・背景ジョブの完了を待つ間は、各待機区間を1回のツール呼び出しへ閉じ込める。
  待機条件を満たした時点で終了するループ（`until <条件>; do sleep <間隔>; done`）を1回起動するか、
  完了通知が自動で届く委譲形態では通知の受領をもって待機解除とする。
  完了通知を待ってターンを終える場合は直前に稼働状況を1回実測し、
  成果物の更新時刻と分量、または委譲先プロセスの生存をユーザーへ1行で示す。
  ターン終了直前の実測は1回に限り、応答ごとに反復しない。
  同一の状態確認コマンドを応答ごとに反復発行する形は、同一結果の再取得へコンテキストを消費するため採らない。
  待機解除の前に状態を再確認する場合は、前回観測から変化が無い理由（待機対象の生存・待機条件の妥当性）を
  直接照会してから次を観測する。
  待機中は、後続工程のうち委譲先の対象範囲と競合しない調査・準備を先行して実施する。
  競合の有無は委譲先の対象ファイル一覧との突合で判定し、読み取りのみの調査は競合しないものとして扱う
- 待機ループ（foreground・background、`until`・`for`・`while`のいずれも含む）を起動する前に、
  待機条件が実データへ1回以上ヒットすることをforeground単発実行で確認する。
  併せて、待機条件の状態を機械的に照会できるかを評価する。状態を機械的に照会できる
  外部・ユーザー依存の条件は、充足時期を観測できない場合も待機上限まで評価を継続する。
  状態を機械的に照会できない条件は待機の対象外として、待機を起動せず次工程へ進む。
  前景実行の待機ループは、ループ自身の上限をシェル実行のタイムアウト上限以下に設定する。
  より長い待機を要する場合は、各区間の開始前に待機対象の生存と充足可能性を再確認したうえで、
  複数の待機区間に分ける。自動的に背景実行へ転換され、完了通知が届く委譲形態では、
  待機区間を追加せず完了通知を待つ経路も採用できる。
  待機ループが1回タイムアウトした時点で、単純に再度待たず原因（filter誤用・プロセス消失・条件式ミス等）を
  疑い能動的な状態調査を実施する。調査は待機対象の存在確認（`ps -p <PID>`・`gh run list --commit <SHA>`等、
  待機条件が参照する実体を直接照会するコマンド）で行う
- プロセスを終了させる操作は、自身が起動して識別子（PID）を確認したものに限る。
  例外として`agent-toolkit:exit-session`が自身をホストするClaude Code本体を終了する場合は、
  親子関係・実行ファイル・コマンドラインを照合して一意に特定した単一PIDを所有権確認済みとして扱う。
  パターン一致で該当プロセスをまとめて終了させる操作（`pkill`・`killall`・`pkill -f`等）は、
  対象の所有権を確認できないため実行しない

## 識別子・環境変数

配布物完結の環境変数は`AGENT_TOOLKIT_<PURPOSE>`形式とする。
代表例の1つは`AGENT_TOOLKIT_PRIVATE_NOTES`（`atk mq`管理repoのroot、既定`~/private-notes/`）である。
ほかに`AGENT_TOOLKIT_STOP_GATE_DEBUG`（デバッグ出力）と
`AGENT_TOOLKIT_HOOK_PAYLOAD_DUMP`（受信payloadのダンプ先）がある。
個人環境完結は`DOTFILES_`を使う。
`agent-toolkit/rules/`・`agent-toolkit/agents/`配下はサブディレクトリを設けずフラット構造を保つ。

## 公式リファレンス

スキル新規作成・hook実装では公式マーケットプレイス（`anthropics/claude-plugins-official`）の
`skill-creator:skill-creator`・`plugin-dev`各スキルを参照する。認識相違時は
`https://code.claude.com/docs/ja/`配下（`skills.md`・`sub-agents.md`・`hooks.md`等）を`WebFetch`で取得する。
列挙にないページを参照する場合は、ドキュメントインデックス（`https://code.claude.com/docs/llms.txt`）を
取得して対象ページのURLを特定してから本文を取得する。インデックスが列挙するURLは英語版
（`https://code.claude.com/docs/en/<page>.md`）のため、日本語版を読む場合は言語部分を`ja`へ置換して用いる。
