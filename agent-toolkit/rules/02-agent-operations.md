# 02-agent-operations.md: エージェントの実行運用

ツール、コマンド、リポジトリ状態、プロセスの扱いを定める。自分の実行と委譲するコマンドの双方に適用し、連結したコマンドも1つずつ判定する。

## ツール・コマンド運用

- 引数が互いの結果に依存しないツールは並列に呼び、同じコマンドが複数対象を受け取れるならまとめる（努力目標。独立した往復を減らす）。
- シェルメタ文字や空白を含む単一引数はANSI-Cクォートか変数への代入後の`"$VAR"`で渡す。言語の文字列シリアライザーをシェルの引用と混同しない。引用符が正しく対応しないと、本文や対象が変わる。
- コマンドや引数を文字列として別のシェルへ渡す場合は、渡す側の引用の有無にかかわらず、渡した先で単語分割とメタ文字の解釈が再び起こる。
  空白や`|`、`$`、`*`などを含む値の引数境界を渡した先で保てない処理は、コードをファイルへ保存し、対象のシェルへそのファイルを実行対象として渡す。
  スクリプト内で変数に格納したコマンドから呼ぶ場合にも同じ条件を適用する。
  複数行のコードはmanaged-tempの中のファイルに保存し、`bash -c`、`sh -c`、`python -c`には一行で完結するコードだけを渡す。

<例>
`ssh host grep -F 'docker ps' file`: sshは遠隔コマンドと引数を空白で連結して送り、接続先のシェルが再解釈する。
`bash -c '<コマンド>'`: `-c`の引数を新しいシェルが解釈する。
`docker run image sh -c '<コマンド>'`: コンテナー内で起動した`sh`がコマンド文字列を解釈する。
`docker exec container sh -c '<コマンド>'`: コンテナー内で起動した`sh`がコマンド文字列を解釈する。
</例>

- 既存パスはユーザー入力、基準となる文書（計画・WI・エージェント向け文書など）、直前の出力、読了済み文書から解決する。構成から推測したパスは`rg --files`か`find`で実体を探す。外部コマンドへは絶対パスを渡し、作業ディレクトリを暗黙に使うCLIは対象のworktreeで起動する。内容検索の手段は対象のGit管理境界から`agent-toolkit:search`で選ぶ。誤ったパスは別の対象への変更につながる。
- 永続状態を変えるコマンドは単独で発行してその終了コードを観測する。表示や確認のコマンドと連結すると、最後のコマンドの終了コードが失敗を覆い隠す。
- 専用コマンドで成立する用途では、その受理形式を使う。コードを評価する入力へ置き換えると引用と内容の確認が複雑になる。

<例>
構造化JSONの項目抽出: `jq`
YAMLの項目抽出: 対象プロジェクトの実行系で動く構造化パーサー
行の抽出: `rg`
</例>

- データ由来の引数にはCLIのデータ引数を使い、位置引数はオプション終端`--`の後ろ、そのCLI自身のオプションは`--`より前へ置く。`--`の後ろは先頭がハイフンの値も含めて全てデータとして扱われるため、そこへ置いたオプションはパスや検索語として解釈される。
- CLI、API、MCPツールの入力形式は、対象実装の公開仕様か同じセッションで観測した最下層のヘルプ・スキーマから確定する。同名の実装が複数あるコマンドは版を識別する。未確定の形式は単独のヘルプ取得後に実行する。推測で呼ぶと、誤った対象への操作と再試行を招く。
- テキストがホストの自動選択する文字コードと異なる文字コードで書かれているか、文字コードが不明なときは、読取コマンドの文字コード指定を使う。
- 調査と検証では標準エラーを保持する。接続先とコンテナー内のスクリプトにも適用する。`2>/dev/null`、`>/dev/null 2>&1`、`&>/dev/null`（合否だけを確かめるループを含む）で破棄すると、終了コードだけでは原因を判定しにくい。内容が事前に確定し診断を要しない出力だけを破棄する。出力を比較、計数、パスの取り込みなどの機械処理へ渡すときは、標準エラーを別のファイルか端末へ分け、`2>&1`でデータの流れへ合流させない。合流させるとエラー文が比較や計数の入力になり、意味のない結果になる。出力から取り込むパスは、生成元の終了コード、空でない集合、全パスの実在を確かめる。
- 機能の不成立や出力の不整合を主張するときは、標準出力と標準エラーを区別し、根拠の行がどちらの出力に現れたかを示す。複数の生成元が同じ端末へ書く場合の原因誤認を防ぐ。
- コマンド出力を機械処理へ渡すときは、色、ページャー、行番号や装飾を明示オプションで無効化する。無効化できないときは形式を検証し、設定による表示を正規化する。
- 自分が実行したコマンドはその終了コードと出力で判定し、重複する取得と再実行を避ける。別主体が非同期に変える状態は対象そのものを観測する。
- 操作の前に、読み書きする対象と生じる副作用を各スキルの起動条件へ照らし、該当するスキルを起動する。作業の呼び名や使うツールで判定しない。同じ対象の後続操作でも、そのセッションで未起動なら判定し直す（努力目標。スキルの手順を通さない編集と独自手順の重複を避ける）。
- 取得済みファイルは変更を観測するまで再利用する。上書きや文字列置換の直前、編集後の検収、外部更新後、会話圧縮後には現行本文を読み直す。置換は一致数を確認できる手段で行い、複数箇所では置換のたびに現行内容を確かめる。
- 外部から観測できる文言を変えるときは、旧文言を期待するテストを含む直接影響範囲（定義は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」）を固定文字列で探す。同じ契約を持つ送信側と受信側、実装とテストの値と発動条件をそろえる。
- `apply_patch`で既存ファイルを全体置換する場合も同じパスへのUpdate操作を使う。1つのpatchで同じパスをDeleteとAddに分けると適用が失敗する。
- 待機対象が終了状態を返す公開機能を持つときは、それで待つ。待機中の重複した状態照会や前景の固定時間待ちを避ける。自分で背景実行したジョブとバックグラウンドタスクへ移った処理は完了通知を確認し、保存した出力を同じターンで読む。完了通知でターンを再開できない主体（自動再開を伝えられていない委譲先など）は、`timeout <ツールの時間上限より短い秒数> sh -c 'until <終了条件のコマンド>; do sleep <秒数>; done'`で前景で待ち、成立しなければ同じ形を再発行する。`sleep <秒数>`の後に出力を読む形は、秒数がツールの時間上限に達すると出力を得られないまま打ち切られる。
- 背景実行するコマンドは、内部の処理が止まってもコマンド自体が時間上限で終わるようにする。完了通知はコマンドが終了して初めて届き、上限が無いと停止に気付くまでの時間を取り戻せない。コマンド全体の`timeout`や内部の`subprocess.run`の`timeout`引数などで上限を設けられない場合は、ホストの時間上限を持つ前景実行へ切り替えて対象を分ける。公開仕様が自身の終了上限と上限到達時の終了状態を定めるコマンド（`atk agents wait`、`wait_ci.py`など）はその上限でこの条件を満たすため、外側の上限を重ねない。外側の上限には`timeout`コマンドに加え、ホストのツールがコマンドを時間で停止する引数（Claude CodeのBashツールの背景実行の`timeout`引数など）も含む。こうしたコマンドを背景実行するときは、引数を省略した場合のホストの上限がコマンド自身の上限より長ければその引数を省略し、短ければコマンド自身の上限より長い値を指定する。コマンド自身の上限より先にホストが止めると、上限到達時の終了状態が失われる。
- 初回しか観測できない出力と再取得の費用が高い出力は、必要な全量、終了状態、診断を保持する。検証、状態変更、全量比較の出力を行数で切り詰めると失われた結果の回復が困難になる。反復可能なファイル、履歴や一覧の先頭・末尾は`head`や`tail`などで確認する。
- 全量の保持が必要で出力量が不明な取得は、標準出力をファイルへ保存して必要な範囲を読む。限定取得だけで目的を満たせるなら、コマンド自身の対象、件数、構造化条件を使う。後続工程へ渡す大きな中間成果物は、実行環境が一度に受け取れる単位へ分割する。
- Claude Codeのツール結果（Bash、PowerShell、MCPツールなど種類を問わない）が`<persisted-output>`で始まる場合は、`Output too large`の行の保存先と`Preview`の抜粋か通知だけが届いている。保存先を末尾まで読んでから内容を読了として扱う。Claude Codeでは範囲指定なしの`Read`で全文を1回で取得し、ホストが`PARTIAL view`を返した場合は残りの範囲を続けて読む。サイズ上限（256KB）かトークン上限（25000）のエラーを受けた場合は、`offset`・`limit`で範囲を狭めるか`rg`で必要箇所だけを取得し、長い行で狭めても超える場合は`rg`か行長を抑えた取得へ切り替える。Codexでは`agent-toolkit/share/rules-main.codex.md`「Codex固有の入出力」の分割取得の規定に従う。
- `atk`はエージェント環境で出力量を自ら扱い、短い出力は直接表示し、長い出力は自ら保存して保存先と行数を示す。このため`atk`はパイプ（`|`、`|&`、`2>&1 |`を含む）にもリダイレクト（`>`、`>>`、`2>`、`&>`、`2>&1`、`/dev/null`への破棄を含む）にもつながず、単独でそのまま呼び出す。出力量が不明な取得の標準出力をファイルへ保存して必要な範囲を読む項も、`atk`には適用しない。パイプかリダイレクトを介すと`atk`の終了コードと警告を同じ呼び出しで観測できず、エージェント環境では長い標準出力の代わりに保存先と行数の行が後段かファイルへ渡る。常駐と追従の表示（`atk serve`、`atk wi process-loop`の常駐、`atk agents logs --follow`）は保存の対象外であり、背景で起動するときの出力のリダイレクトはこの項の対象から外す。出力量は公開された対象限定（`--count`、`--summary-only`、状態・種別・対象リポジトリの指定など）で制御する。生成側が返す標準出力と標準エラーの保存先をそれぞれ読み、全量の機械処理と引き渡しは保存されたファイルへ別の呼び出しで行う。
- 出力が未知なら通知の有無だけで全量と判断せず、保存した行数と終端を確認する。
- 大量出力は分離した実行で全量を観測し、終了状態と要約を受け取る（努力目標。委譲元のコンテキストを保護する）。委譲の受領物と待機は`agent-toolkit:delegation`に従う。
- 削除や回収の完了は対象の不在で確認する。`test -e <絶対パス>; echo "test_e_rc=$?"`の終了表示は読み取り専用の確認として別の呼び出しで行う。操作コマンドの契約が除去完了を終了コードに含む場合はその結果を使う。`ls`、`find`、`git rev-parse`の非0終了だけで対象不在を確定しない。
- Git識別子と別worktreeの指定は`agent-toolkit:commit`の`references/git-identifier.md`に従う。前工程から受け取ったパスや識別子は、その後に移動や終了を起こす操作が介在したときに同一性を再確認する。
- 調査用サーバーは到達を要する主体の範囲だけで待ち受ける。同じホストの確認にはloopbackを使い、不要な外部公開を避ける。
- 権限設定やauto mode classifierが操作を拒否した場合は、別の手段を試す前に`agent-toolkit:user-confirmation-and-report`の`references/permission-denial.md`を適用する。

## 作業中に観測したリポジトリ状態変化の扱い

別セッションのcommitと担当外の差分は変わる。開始時のHEADと計画のベースcommitは参照情報として扱い、担当ファイル、直接影響範囲、公開契約、書込所有権、後続操作へ影響する実差分を読む。影響がなければ現在状態で続ける。対象OIDの同一性とデータ完全性を守る確認は保ち、担当外差分を変更しない。

## プロセス終了の安全規定

終了させるプロセスとジョブは、自分の起動が返した停止用識別子で所有を確認できる対象に限る。記憶した名前、部分一致、別種の識別子への推測変換は使わない。失敗した起動でも停止用識別子が返れば所有の根拠になる。自分自身を実行環境の条件で一意に識別できる場合と、引き継ぎ記録が保持する識別子を停止直前に照会して対象コマンドとの一致を確認できる場合も同じである。

作成元の作業単位が回収済みであることを読み取りで確定したエージェント由来の残存資源（プロセス、コンテナーなど）も停止してよい。確定は対象ごとに個別の識別子（コンテナーID、PIDなど）で照会し、次を全て満たすかで判定する。停止した対象と照会結果は報告へ含める。

- 対象の作業ディレクトリ、bind mountの元または実行ファイルのパスが、エージェントの工程が作業単位を作成する配置にある。配置は`<リポジトリ>/.claude/worktrees/`配下、`atk managed-temp`の領域、および対象リポジトリの手順か設定の現物が作業単位の作成先として定める場所とする
- その作業単位が回収済みである。worktreeは対象リポジトリの`git worktree list`に無く、managed-tempの領域は`atk managed-temp list`に登録が無く、いずれもパスが存在しないか空である
- 名前の部分一致やパターンで選んでおらず、停止は照会した識別子を1件ずつ指定する

`git worktree list`に登録済みの作業ツリーに属する資源と、ユーザーが作業ツリーの外で起動した資源は、この条件を満たさないため停止の対象から外れる。

現在のworktree専用の環境単位と、前段の条件で回収済みと確定した作業単位の環境単位は、その専用名を手順か設定の現物から確かめて確定できるときに撤去する。確定できないときは対象と不足条件を委譲元へ返す。待機と終端観測は`agent-toolkit:delegation`の`references/waiting-and-monitoring.md`に従う。
