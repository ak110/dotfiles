# 02-agent-operations.md: エージェントの実行運用

ツール、コマンド、リポジトリの状態、プロセスの扱いを定める。自分で実行するコマンドにも委譲するコマンドにも適用し、連結したコマンドも1つずつ判定する。

## ツール・コマンド運用

### 引用と引数

- 互いの結果を使わないツール呼び出しは並列に呼び、同じコマンドが複数の対象を受け取れるならまとめる（努力目標。往復を減らす）。
- 引数の境界を保つ。空白やメタ文字を含む引数はANSI-Cクォートか`"$VAR"`で渡し、データ引数は`--`の後ろに置く。別のシェルが再解釈するコマンド文字列（ssh、`sh -c`、コンテナー内のshellなど）で境界を保てないコードはファイルで渡す。複数行のコードはmanaged-tempの中のファイルに保存し、`bash -c`、`sh -c`、`python -c`には1行で完結するコードだけを渡す。
- 永続状態を変えるコマンドは単独で実行して終了コードを確かめる。表示や確認のコマンドと連結すると、最後のコマンドの終了コードが失敗を覆い隠す。
- 専用コマンドが受け付ける形式で済む用途は、コード評価に置き換えずにその形式を使う。
- 独自コマンド（`atk`の操作や補助スクリプト）の使用・追加・保持は、標準手段と比べて得られる目的上の便益と、学習・準備・実行・結果確認・保守の総費用で判断する。便益は目的上の効果に限り、内部の専用入力や規範がそのコマンドを必須にしていることは根拠にしない。保持するCLIは`show`・`get`・`set`・`list`・`grep`などの既存の語義を守り、名前から副作用が推測できる構成を保つ。削除した操作の呼び出しは互換ラッパーを設けずに標準手段へ移す。
- CLI・API・MCPの操作は、自分で実行する前にも、チャット・WI・報告などで案内する前にも、使う人が使う公開の呼び出し手段の入力契約（親子コマンドのオプション位置、公開リクエストの項目など）を確定する。根拠は版を特定した公開仕様か、同じセッションで確かめたヘルプ・スキーマとする。内部コードで確かめた機能や引数名は、公開された入力形式とは別に確かめる。規範や手順が判定の定義元として内部関数やモジュールを示していても、読み手に実行させる操作は同じ判定を受け付ける公開コマンドで書く。手順・規範・スキルが実行できる形で示した受理形式はそのまま使う。
- 読み取るときの文字コードは入力に合わせ、ホストの自動選択と違うか不明なら明示する。
- 権限設定やauto mode classifierが操作を拒否したら、別の手段を試す前に`agent-toolkit:user-confirmation-and-report`の`references/permission-denial.md`を適用する。

### 標準の読取・実行・一時領域

- 読み取りにはハーネスの読取ツール（Claude Codeの`Read`など）を使う。無い場合は`cat`か`sed -n '<開始行>,<終了行>p' -- <絶対パス>`、JSONは`jq`を使う。規範資料（rules、スキル本体とreferences、役割文書、share契約）、読込表・読込宣言に挙がる資料（節指定の行を含む）、手順が全文読むとする資料は、種別を問わず全体を読む。節外の前提・例外を見落とさないためである。全体を読む資料が長ければ分割して末尾まで読む。それらの外で参照する根拠・事例文書は必要箇所を取得する。
- コマンドはハーネスの標準の実行・背景実行・待機機能で実行する。
- 作業用の一時ディレクトリは、通知されたセッションのmanaged-tempの中に`mktemp -d '<親>/<用途>-XXXXXXXX'`で作り、参照を終えた作成者が`rm -rf -- <作成した絶対パス>`で回収する。置き場所の例外と回収の時点は`agent-toolkit:managed-temp`に従う。

### パスと検索

- 既存のパスは入力・基準文書・取得済みの出力から解決し、推測したパスは実在を検索で確かめる。外部コマンドへは絶対パスを渡し、cwdを使うCLIは対象のworktreeで起動する。
- 通常の検索は対象worktreeの`git grep`、追跡外のファイルは`rg`で行う。終了コード0は一致、1は一致なし、それ以外は検索の失敗として扱う。手段の選び方と出力量の制御は`agent-toolkit:search`に従う。
- 操作の対象と副作用から必要なスキルを判断し、まだ起動していなければ操作の前に起動する（努力目標。契約の確認不足と独自手順の重複を避ける）。
- 外部から観測できる名前と値（文言、設定キー、状態値、コマンド名、返却形式など）を変えるときは、旧値を期待するテストを含む直接影響範囲を固定文字列で探し、送信側と受信側、実装とテストをそろえる。直接影響範囲の定義は`agent-toolkit:plan-mode`の`references/plan-file-standards.md`「要件・外部仕様」にある。
- Git識別子と別worktreeの指定は`agent-toolkit:commit`の`references/git-identifier.md`に従う。前工程から受け取ったパスや識別子は、移動や終了を伴う操作を挟んだ後で同一性を確かめ直す。

### 出力の保持と観測

- 調査・検証は、判断に必要な全量、診断、終了状態を保持してから判定する。切り詰められた結果や未読の部分から件数・不在・網羅性を確定せず、保存先から行範囲を分けて必要な範囲を回収する。機械処理する出力は標準出力と標準エラーを分け、色やページャーなどの装飾を無効にする。取り込むパスは、生成元の終了コード、集合が空でないこと、全パスの実在を確かめる。
- 自分が実行したコマンドは終了コードと出力で判定する。取得済みの出力と本文は、読込表や手順が全文読むとする資料も含め、編集・外部での更新・会話圧縮が起きるまで再利用し、再取得と再実行を避ける。別の主体が非同期に変える状態は、対象そのものを観測する。
- 初回しか観測できない出力と再取得の費用が高い出力（検証、状態変更、全量比較など）は、生成側で全量を保存し、後続へ保存先を渡す。保存は自分の一時領域へ標準出力と標準エラーを分けて行い、終了コードと取得時のHEADを返却か引き継ぎ記録に残す。一部の取得で足りる場合は、公開の対象・件数指定を使う。
- 保存出力の抜粋だけを返すホストでは、保存先から必要な残りを取得する。ホストとCLI固有の読取指定は公開ヘルプや診断に従う。大量の出力を別の実行へ任せる場合の受領と待機は`agent-toolkit:delegation`に従う。

### 待機と背景実行

- 未完了の実行は、同じ識別子と公開の待機機能を使って、同じターンで終了と保存出力を回収する。待機中の重複発行と前景での固定時間待ちは避け、完了通知は結果を回収するきっかけとして扱う。公開の待機機能が無い場合だけ、有限の上限を持つ終了条件ループを使い、照会成功・未完了、照会失敗、上限到達を区別する。再待機は照会成功・未完了の場合に限り、失敗と上限到達は診断と終了状態を添えて返す。
- 背景実行するコマンドには、内部の処理が止まってもコマンド自体が終わる時間上限を持たせる。完了通知はコマンドの終了で届くので、上限が無いと停止に気付くのが遅れる。`atk agents wait`や`wait_ci.py`のように、公開仕様が自身の終了上限と上限到達時の終了状態を定めるコマンドはその上限で足りるので、外側の上限（`timeout`コマンドやBashツールの背景実行の`timeout`引数など）は重ねない。ホストの省略時の上限がコマンド自身の上限より短い場合だけ、それより長い値を指定する。コマンドより先にホストが止めると、上限到達時の終了状態が失われる。子プロセスを起動するコード（CLIのラッパー、hookの実行、検証の代理実行など）で時間上限を設計するときも、起動するコマンドが自身の上限を持つなら外側の上限を重ねない。
- エージェントが起動するサーバー（調査、開発、検証、一時プレビューなど）は、到達が必要な主体の範囲だけで待ち受け、同じホストからの確認にはloopbackを使う。
- 待機の起動と終了の観測は`agent-toolkit:delegation`の`references/waiting-and-monitoring.md`「待機区間の構成」に従う。通知で同じセッションを再開できる独立した待機は、先に届いた通知から回収し、別の待機が終わるまで前景を占有しない。

### `atk`の呼び出し

- `atk`はエージェント環境で出力量を自分で扱い、長い出力は自分で保存して保存先と行数を示す。そのため`atk`はパイプにもリダイレクト（`2>&1`や`/dev/null`への破棄を含む）にもつながず、単独で呼び出す。間に挟むと`atk`の終了コードと警告を同じ呼び出しで確かめられず、保存先と行数の行だけが後段へ渡る。出力量が分からない取得をファイルへ保存する前項は、`atk`を対象外とする。常駐と追従の表示（`atk serve`、常駐の`atk wi process-loop`、`atk agents logs --follow`）を背景で起動するときの出力のリダイレクトは例外とする。出力量は公開の対象限定（`--count`、`--summary-only`、状態・種別・対象リポジトリの指定など）で抑え、全量の機械処理は保存されたファイルへ別の呼び出しで行う。

### 完了と不在の確認

- 削除や回収の完了は、対象が無いことで確かめる。`test -e <絶対パス>; echo "test_e_rc=$?"`を読み取り専用の確認として別の呼び出しで実行するか、除去の完了を終了コードに含む操作コマンドの結果を使う。`ls`、`find`、`git rev-parse`が非0で終わったことだけで不在と判断しない。

## 作業中に観測したリポジトリ状態変化の扱い

別セッションのcommitや担当外の差分は作業中にも変わる。開始時のHEADや計画のベースcommitは参考として扱い、担当ファイル、直接影響範囲、公開契約、書込所有権、後続の操作に影響する実際の差分を読む。影響が無ければ現在の状態で続ける。対象OIDの同一性とデータの完全性を守る確認は保ち、担当外の差分はそのままにする。

## プロセス終了の安全規定

終了させるプロセスとジョブは、自分の起動が返した停止用識別子で所有を確かめられる対象に限る。記憶した名前、部分一致、別種の識別子からの推測は所有の根拠から外す。起動に失敗しても停止用識別子が返っていれば所有の根拠になる。実行環境の条件で自分自身を一意に特定できる場合と、引き継ぎ記録が保持する識別子を停止の直前に照会して対象コマンドとの一致を確かめられる場合も同じである。

作成元の作業単位が回収済みだと読み取りで確定した、エージェント由来の残存資源（プロセス、コンテナーなど）も停止してよい。確定は対象ごとに個別の識別子（コンテナーID、PIDなど）で照会し、次を全て満たすかで判定する。停止した対象と照会結果は報告に含める。

- 対象の作業ディレクトリ、bind mountの元、または実行ファイルのパスが、エージェントの工程が作業単位を作る配置にある。配置とは、`<リポジトリ>/.claude/worktrees/`配下、managed-tempの一時root配下、および対象リポジトリの手順か設定の現物が作業単位の作成先として定める場所を指す
- その作業単位が回収済みである。worktreeは対象リポジトリの`git worktree list`に無く、worktreeとmanaged-tempの領域はどちらもパスが存在しないか空である
- 名前の部分一致やパターンで選んでおらず、照会した識別子を1件ずつ指定して停止する

`git worktree list`に登録済みの作業ツリーに属する資源と、ユーザーが作業ツリーの外で起動した資源は、この条件を満たさないため停止の対象にならない。

現在のworktree専用の環境単位と、前段の条件で回収済みと確定した作業単位の環境単位は、その専用名を手順か設定の現物から確かめられるときに撤去する。確かめられないときは、対象と不足する条件を委譲元へ返す。
