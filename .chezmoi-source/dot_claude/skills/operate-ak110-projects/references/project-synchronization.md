# 姉妹プロジェクトへの同期と追従台帳

個人プロジェクトで変えた足回り（ツールチェイン、lint設定、CI、文書構成）や推奨ガイドの改訂を他の姉妹プロジェクトへ広げるかを決め、追従提案を投入し、他のプロジェクトでも作業が必要な改善を追従台帳へ記録する手順書である。
共通化の対象は同じコマンド名と設定キーでそろえ、本書「意図的に維持している差異」に当たらないコメントの表現、項目の順、指定を省いた時に使われる値も同じ文面か同等の設定へそろえる。

## 同期の手順

1. 変更を分類する（prek設定、mise設定、CI workflow、README構成など）。
   典型的な対象は、ビルドとタスク（`Makefile`、`mise.toml`）、設定（`pyproject.toml`、`package.json`、`.pre-commit-config.yaml`）、CI（`.github/workflows/**`）である。
   文書では`README.md`、`AGENTS.md`、`docs/**/development.md`、`docs/**/security.md`が対象になる。
2. 本書「変更時の同期対象マトリクス」で波及先を決める。
   該当する行が無い変更は、`SKILL.md`「前提」の属性表の全プロジェクトを候補にし、手順4の前提が成り立った候補だけを必須の確認へ進める。
   パッケージ管理系に固有の規範を横展開する時は、プロジェクト一覧の記載だけで決めず、対象ファイルかロックファイルの実在を確かめて波及先を確定する。
3. 本書「意図的に維持している差異」に当たる波及先と項目を除く。
   残った対象で共通方式と異なるCI実装の案は、個別採用の前に共通方式の変更提案1件にまとめ、方式の採否をそこで一度だけ決める。
   共通方式を記載する規範を持つdotfilesに提案を起票し、各対象にはその決定を反映する。
4. 移植する記述が依拠する前提（配布形態、外部サービスの有効状態など）を挙げ、各前提が移植先で成り立つかを、移植先の現物の観測か明文化された方針との比較で確かめる。
   成り立たない前提に依拠する記述は、移植先の実情に合わせて書き換えるか、移植から除く。
5. 波及先を`agents_server`の`start`（`mode`は`explore`）で読み取り専用に並列で調査し、差分を把握する。
   複数のリポジトリの全文を自分の文脈で読むと、後の判断に回す容量が残らないためである。
   あわせて波及先宛ての未処理のAWIを`atk wi list`と`atk wi grep`で照会し、実行レビューで確定した検証結果や訂正の記録があれば、その結論を変更の前提に取り込む。
6. 全ての波及先へ同じ設定値を配る場合は、その設定を制御するツールを個人プロジェクト群が所有しているかを確かめる。
   所有していれば、上流のツールで指定を省いた時の値を変える案と新設オプションへ吸収する案を、各リポジトリへ配る案と並べ、次の3点で比べる。
   設定値が同じことだけでは上流での吸収を選ばない。
   - 上流のツールの値を変えた時に、そのツールを使う全プロジェクトへ及ぶ影響
   - 波及先に固有の要件の有無
   - 新設オプションを指定しない時の動作で、個別の設定が不要になるか

   上流での吸収を選んだら、上流リポジトリ宛てのAWIを1件投入し、未投入の配布案は取り下げ、適用済みの個別の設定は別の削除対象として扱う。
7. 追従提案を、同じセッションで波及先ごとのAWIとして`agent-toolkit:atk-mode/playbooks/wi-drafting.md`の手順で投入する。
   複数のリポジトリへの投入は`agent-toolkit:atk-mode/references/cross-repository-submission.md`に従う。
   - 各提案の関連情報に、更新元のリポジトリ名とcommitを書く。
   - 追従提案の本文には、起点の変更と追従する目的を書く。
     共通CI方式の決定に基づく提案は、その決定への参照も書く。
   - 別の計画が同じ改訂を扱うと分かっているリポジトリは投入から除き、その旨を各提案の関連欄へ書く。
   - 推奨ガイドの改訂が必要な変更を`~/pyfltr`以外で確定した時は、先に`~/pyfltr`宛てのAWIを投入し、他の提案の`depends_on`へそのファイル名を書く。
     典拠の無いままの追従による整合の崩れを防ぐためである。
8. 本書「台帳への追記」の記録対象に当たる改善なら、台帳へ追記する。

## 意図的に維持している差異

次の差異は意図的に異なる設定であり、統一の対象から外す。

- 非同期テストのloopとfixtureの寿命: dotfilesと同梱のagent-toolkitはfunction単位で隔離し、テスト間の未完了のtaskや状態の混入を防ぐ。
  姉妹プロジェクトのsession単位の設定は、各プロジェクトの要件として保つ。
  ブラウザーなどsessionの寿命を明示したfixtureは、宣言した寿命を使う。
- `textlint-rule-prh`（dotfilesのみ）: Claude Codeのコンテキスト汚染を防ぐため、textlint系を特に厳しくする方針である。
- Pythonの対応バージョンとCIで使うバージョンの集合（dotfilesと同梱のagent-toolkit）: ユーザーが過去のPythonのバージョンをサポートしないと決めたため、対応するバージョンを1つ（現在は3.15）に限り、CIも同じバージョンで実行する。
  他のプロジェクトのPythonのバージョンの行列へそろえず、バージョンの宣言は将来のバージョンを許す下限で表す。
- pytilpackの`docs.yaml`に`paths:`なし（pytilpackのみ）: mkdocstringsがPythonのソースから文書を生成するため、ソースの変更でもdocs workflowを起動する。
- Dependabot alertsの有効・無効（dotfiles・GLATasksは有効、pytilpackは無効）: pytilpackはライブラリであり、ロックファイルが開発専用のため、エンドユーザーの実行環境への脆弱性の影響が限られる。
- dotfilesの`AGENTS.md`に「開発手順」「注意点」の章なし（dotfilesのみ）: dotfilesの`AGENTS.md`は概要と参照先の案内だけにし、開発手順と注意点を`.claude/skills/`配下のスキルへ置く。
  そのため、`references/doc-structure.md`の`AGENTS.md`の必須の章のうちこの2章を適用から外す。

## 台帳への追記

追従台帳は個人プロジェクト（dotfilesと姉妹プロジェクト）で行った改善のうち、他のプロジェクトでも作業が必要なものを1件1項目で記録し、対象プロジェクトへの手動適用に使う。
対象は、共通規範の配布だけでは変わらない既存コード・テストや設定に、プロジェクトごとの作業が必要な改善である。
区分「設定」は、各プロジェクトが自分で持つファイル（lint・文章チェックの設定、CI定義、pre-commit、mise、Makefile、依存管理の設定、文書構成、プロジェクト固有のエージェント向け文書など）の変更が必要な改善である。
区分「見直し」は、個人プロジェクトで実施した既存成果物（文書、テスト、コード）の再利用可能な改善である。
配布済みの規範や品質基準への追従だけでなく、規範変更を伴わないコード整理やテストの改善も含む。
CI定義や検証設定の改善は「設定」の「CIとテスト」に記録する。

| 区分 | 主題 | 台帳 |
| --- | --- | --- |
| 設定 | Markdownと文書 | `references/followup-ledger-settings-markdown.md` |
| 設定 | 依存と開発ツール | `references/followup-ledger-settings-dependencies.md` |
| 設定 | CIとテスト | `references/followup-ledger-settings-testing.md` |
| 設定 | 品質基準とスキル | `references/followup-ledger-settings-skills.md` |
| 見直し | 全て | `references/followup-ledger-reviews.md` |

プラグインや配布物の更新だけで他のプロジェクトへ届きプロジェクト側の作業が生じない変更と、agent-toolkitの内部機構、dotfiles固有の個人設定、各プロジェクトのアプリケーションロジックの変更は記録しない。

1. 追記する時機を守る。
   - dotfilesで確定した変更は、同じ作業の中で追記する。
   - 姉妹プロジェクトで確定した変更は、dotfiles宛ての追従提案（本書「同期の手順」の手順7）を登録する場合はその処理の中で追記する。
     dotfiles宛ての追従提案が無い変更では、変更を確定したセッションが、台帳への追記を求めるdotfiles宛てのAWIを登録する。
2. 区分と主題に合う台帳の末尾へ、既存の項目と同じ形で1項目を加える。
   各項目は、項目ID、実施日、内容、理由、当てはまる条件、適用方法、参照先、適用済みの見分け方を持つ。
   - 項目IDは確認記録が項目を指す識別子であり、付けた後は同じ値を保ち、台帳の全ファイルを通して重複させない。
   - 当てはまる条件と適用済みの見分け方は、プロジェクトの現物から判定できる形で書く。
   - 設定やCIの現在の推奨形はpyfltrの推奨ガイド（`docs/guide/recommended.md`、`docs/guide/recommended-nonpython.md`）を正とし、台帳には項目の所在だけを書く。
     台帳が扱うのは、いつ何がなぜ変わったかと、推奨ガイドに載らない改善である。
   - 作業項目の内部のファイル名と、個人プロジェクト以外の固有の情報は書かない。
   - 適用方法が未整備の項目（検査がdotfilesにしか無いなど）は、その状態を項目へ書き、整備された時点で項目を更新する。

## 返す報告に含める項目

波及先と判定の根拠、除いた波及先と理由、投入したAWIのファイル名、上流での吸収の採否、台帳へ追記した項目IDを返す。
