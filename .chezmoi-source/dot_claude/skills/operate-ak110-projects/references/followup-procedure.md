# 追従台帳の運用

本書は`operate-ak110-projects`の`SKILL.md`「足回り改善の適用検討と台帳への追記」から読む参照資料である。
個人プロジェクト（dotfilesと姉妹プロジェクト）で実施した足回りの改善を、一覧の外のプロジェクトで検討する手順と、台帳へ項目を追記する手順を定める。
この手順を使う人はユーザー本人に限る。

## 台帳

台帳は、個人プロジェクトで実施した改善のうち、他のプロジェクトでも作業が要るものを1件1項目で記録する。
区分ごとに次の2ファイルへ分ける。

| 区分 | 記録する対象 | 台帳 |
| --- | --- | --- |
| 設定 | 各プロジェクトが自分で持つファイル（lint・文章チェックの設定、CI定義、pre-commit、mise、Makefile、依存管理の設定、文書構成、プロジェクト固有のエージェント向け文書など）の変更が要る改善 | [followup-ledger-settings.md](followup-ledger-settings.md) |
| 見直し | プラグインで配布済みの規範や品質基準の変更のうち、それに合わせて各プロジェクトの既存成果物（文書、テスト、コード）の一括見直しを個人プロジェクトで実施したもの | [followup-ledger-reviews.md](followup-ledger-reviews.md) |

次の変更は記録の対象外とする。

- プラグインや配布物の更新だけで他のプロジェクトへ届き、プロジェクト側の作業が生じない変更
- agent-toolkitの内部機構、dotfiles固有の個人設定、各プロジェクトのアプリケーションロジックの変更

各項目は、項目ID、実施日、内容、理由、当てはまる条件、適用方法、参照先、適用済みの見分け方を持つ。
項目IDは確認記録が項目を指すための識別子であり、付けた後は同じ値を保つ。
当てはまる条件と適用済みの見分け方は、プロジェクトの現物から判定できる形で書く。
設定やCIの現在の推奨形はpyfltrの推奨ガイド（`docs/guide/recommended.md`、`docs/guide/recommended-nonpython.md`）を正とし、台帳には項目の所在だけを書く。
台帳は、いつ何がなぜ変わったかと、推奨ガイドに載らない改善を扱う。
作業項目の内部ファイル名と、個人プロジェクト以外の固有情報は台帳へ書かない。

## 適用を検討する手順

一覧の外のプロジェクトで、ユーザーから適用の検討を依頼されたエージェントが、そのプロジェクトの作業ツリーで次を行う。

1. 確認記録を読み、台帳2ファイルの項目のうち、そのプロジェクトで未確認のもの（確認記録に項目IDが無いもの）を対象にする。
2. 対象の項目ごとに、当てはまる条件の成否と、適用済みの見分け方による現状との差を、そのプロジェクトの現物から調べる。
3. 結果を一覧でユーザーへ示す。
   一覧には項目ごとに、内容、該当・非該当・適用済みの別、現状との差、適用に要る作業の概要を含める。
4. 該当した項目の採否をユーザーが項目ごとに決める。
5. 採用と決めた項目を、そのプロジェクトの作業項目キューへAWIとして登録する。
   登録は`agent-toolkit:wi-standards`の通常の投入手順に従う。
6. 項目ごとの結果（採用、不採用、非該当、適用済み）を確認記録へ保存する。

台帳の「適用方法」が未整備と書かれた項目は、その状態を一覧に示し、採否はユーザーが決める。
現物から条件の成否を判定できない項目は、不足する情報を一覧に示し、確認記録へ書かずに未確認のまま残す。

## 確認記録

確認記録は、次回の手順1で未確認の項目を選ぶために使う。
不採用と決めた項目を次回の候補に挙げないことが目的である。

- 保存先は適用先プロジェクトのリポジトリの外とし、プロジェクトごとに1ファイルを置く。
- 保存先のディレクトリは、ユーザーが指定した場所を使う。
  dotfilesプラグイン（dotfiles本体の`plugins/<名前>/`）のディレクトリの中を指定すると、プラグインのリポジトリを通じて別のPCへ引き継げる。
  プラグインの`.chezmoi-source/`から配布されたホーム側のファイルは、次回の適用で上書きされるため書込先にしない。
- 指定が無い場合は、そのPCの`~/.local/state/dotfiles/followup-records/`へ保存する。
- ユーザーが保存先を指定した場合は、その絶対パスを`~/.local/state/dotfiles/followup-records/location`へ1行で保存し、次回からは指定が無くてもその場所を使う。
  保存先を変えた場合は、既存の確認記録を全プロジェクト分まとめて新しい保存先へ移す。
- ファイル名は、プロジェクトのリモートURLからスキームと末尾の`.git`を除いた`<ホスト>/<パス>`（リモートが無ければ作業ツリーの絶対パス）の`/`と`:`を`_`へ置き換えた名前に`.json`を付ける。
  `project`には置き換える前の値を書く。
- 内容は次の形のJSONとする。
  `result`は`採用`、`不採用`、`非該当`、`適用済み`のいずれかで、`checked_on`は確認した日付、`note`は判定の根拠や登録したAWIの要旨を短く書く。

```json
{
  "project": "github.com/example/project",
  "items": {
    "markdown-one-sentence-per-line": {"result": "採用", "checked_on": "2026-11-11", "note": "検査を導入するAWIを登録"}
  }
}
```

`非該当`と記録した項目も、プロジェクトの構成が変わって条件に当たるようになった場合は、ユーザーの依頼で確認し直せる。

## 台帳への追記

「台帳」の記録する対象に当たる変更を個人プロジェクトで確定した作業の中で、台帳へ項目を追記する。

- dotfilesで確定した変更は、同じ作業の中で追記する。
- 姉妹プロジェクトで確定した変更は、`SKILL.md`「追従作業と複数リポジトリ横断投入」でdotfiles宛の追従提案が登録される場合、その処理の中で追記する。
  dotfiles宛の追従提案が無い変更では、変更を確定したセッションが、台帳への追記を求めるdotfiles宛のAWIを登録する。
- 項目は区分に合う台帳の末尾へ加え、項目IDを台帳2ファイルを通して重複させない。
- 適用方法が未整備の項目（検査がdotfilesにしか無いなど）は、その状態を項目へ書き、整備された時点で項目を更新する。
