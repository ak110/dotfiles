# リリース運用

個人プロジェクトの公開とリリースの認可、実施の時機、要否の判定、実施の手順書である。
対象のプロジェクトとリリース運用の対象は`SKILL.md`「前提」の属性表が定める。
認可は恒常的なものであり、公開範囲の明示の指定と、後からのユーザーの明示的な制限・撤回を優先する。

## 公開の恒常的な認可

「前提」の属性表の7プロジェクトで、協調モードの変更の依頼に公開範囲の指定が無ければ、ユーザーの恒常的な認可に基づき公開まで進める。
公開範囲の明示の指定がある場合は、その指定を優先する。
公開は`agent-toolkit:atk-mode/playbooks/commit.md`と`agent-toolkit:atk-mode/playbooks/publish.md`の手順でpushとCI成功まで検収する。
`dotfiles`は`release-dotfiles`の条件に従ってリリースPRの作成・マージ・検収まで、`smpr`はpushとCI成功まで進める。
属性表のリリース対象の5プロジェクトは、本書「判定」で要る場合だけリリースする。

## リリースの認可

`gv`・`lc`・`glatasks`・`pyfltr`・`pytilpack`のリリースは、ユーザーの恒常的な認可に基づき、エージェントが要否とバージョン区分（パッチかマイナー）を判断して実施する。
メジャーはユーザーの明示指示がある場合だけとする。
この認可は`agent-toolkit:process-wi`の手動の起動、`atk wi process-loop`による常駐の起動、前節の認可か明示の指定で公開まで扱う協調モードの作業に適用し、リリースのたびのユーザー確認とUWIは省く。
リリースworkflowを持たないプロジェクトは対象外とし、リリースworkflowを持ったプロジェクトは属性表で対象へ加える。

## GLATasks本番配備の恒常的な認可

`aws.tqzh.tk`上の`https://glatasks.tqzh.tk/`への既存のDeploy手順による配備は、ユーザーから恒久的に認可されている。
公開・配備を担当するエージェントは、自律・協調のどちらでも、この対象・操作に一致する通常の配備を、個別の確認や操作依頼のUWIなしで実施する。
CI成功、既存の手順の安全確認、配備後のhealthcheckと結果の報告は保つ。
別のサービス・別のホストや、既存のDeploy手順から独立した破壊的な操作には、この認可を適用しない。

## 実施時機と前提

1. 一連の作業の公開（pushとCI成功）が終わった時点で、リリースの要否を判定する。
   `agent-toolkit:process-wi`では、公開担当の返却の後に`agent-toolkit:atk-mode/playbooks/publish.md`「公開状態の4項目」の成立を確かめ、`agent-toolkit:atk-mode/playbooks/report-completion.md`を読む前に判定する。
2. ローカルのベースbranchがリポジトリのdefault branchであり、未pushのcommitと未commitの変更が無いことを確かめる。
   成り立たない場合はリリースせず、その理由を完了の報告へ含める。
   `releaser`は未pushのcommitをpushするため、この前提でpushの所有者を保つ。

## 判定

判定の対象は、引数なしの`releaser`が表示する`<直近のリリースタグ>..HEAD`の未リリースのcommit全体とする。
各commitは差分の内容で判定し、commit typeは手掛かりに留める。

リリースが要るのは、エンドユーザー影響がある変更、つまりエンドユーザーがリリースされた配布物を通じて観測する挙動や内容を変える変更である。

- 該当する: 配布されるコードのうち、エンドユーザー向けのCLI・公開API・設定を省略したときに使う値・画面を変えるもの。
  配布物に同梱して公開するエンドユーザー向けの文書（PyPIの説明になるREADMEなど）の変更。
- 該当しない: 配布コードでも消費主体がエージェントだけで、エンドユーザーが配布物を通じて観測する挙動や内容を変えないもの（MCPツールの入力スキーマの許容値・項目説明、エージェントだけが読むメッセージなど）。
  エンドユーザー向けの結果も変わる差分は、前項の基準で判定する。
  dotfilesではこの消費主体による除外を適用せず、エージェント向けの変更もリリース影響に含める（`develop`から`master`への公開は`release-dotfiles`が扱う）。
- 該当しない: 実行時依存の版指定の更新（`pyproject.toml`の`dependencies`、`package.json`の`dependencies`など）、テスト、CIとworkflow、開発手順と開発用ツールの設定（`Makefile`・`mise.toml`・pre-commit・lint設定）。
- 該当しない: エージェント向け文書（`AGENTS.md`・`CLAUDE.md`・`.claude/`配下）、開発者向け文書（`docs/development/`）、開発専用のロックファイルの更新、docsサイトだけの変更（`master`へのpushで`docs.yaml`が公開するため）。
- どれとも判別できない変更は、配布物に含まれてエンドユーザーから観測できるかで判定する。

## 実施

1. 該当する変更が1件以上ある場合だけ、次の区分からエージェントが区分を決め、`releaser <patch|minor>`を実行して完了まで検収する。
   0件の場合はリリースせず、リリースしなかったことと理由を完了の報告へ含める。
   - バグ修正・軽微な機能追加: パッチとする。
   - ある程度大きい機能追加や変更: マイナーとする。
2. メジャーはOSSの慣例に従い、ほぼ全面的な書き直しや再構築などの場合にだけ使い、セマンティックバージョニングの互換性を壊す変更でもそれだけではメジャーにしない。
   エージェントはメジャーを選ばず、ユーザーが明示的に指示した場合だけ`releaser major`を実行する。
   リリースworkflowの対象外の版数（dotfilesが配布するagent-toolkit・agent-basicsなどのプラグインの版数）の更新にも、同じ方針を使う。
3. `releaser`はdotfilesの`pytools/releaser.py`が提供するコマンドで、default branchで実行しているかと未commitの変更の有無を確かめ、未pushのcommitをpushする。
   続けてCIの完了を待ち、`release.yaml`のworkflow_dispatchを起動してrunを監視し、上流branchへのfast-forwardでローカルを最新にする。
   引数を省いた`releaser`は、ヘルプと未リリースのcommitの一覧を表示するだけで終わる。
   `gh workflow run release.yaml`などの低水準のコマンドは、`releaser`の内部の実装か、人間が手動で補助する場合にだけ使う。
4. `releaser`はCIの待機とworkflowの監視で長くかかるため、前景の実行時間の上限を超える場合は背景実行か委譲で実行し、終了状態を観測してから報告する。

## 返す報告に含める項目

公開した範囲、リリースの有無と区分（しなかった場合はその理由）、`releaser`の終了状態、GLATasksを配備した場合はhealthcheckの結果を返す。
