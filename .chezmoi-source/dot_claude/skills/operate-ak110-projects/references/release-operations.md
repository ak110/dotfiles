# リリース運用

本書は`operate-ak110-projects`の`SKILL.md`「リリース運用」から読む参照資料であり、個人プロジェクトの公開とリリースの認可、実施時機、判定、実施の手順を定める。
対象プロジェクトは`SKILL.md`「前提」の属性表が定める。

## 公開の恒常的な認可

「前提」の属性表の7プロジェクトで、協調モードの変更依頼に公開範囲の指定がなければ、ユーザーの恒常的な認可に基づき公開まで進める。
公開範囲の明示指定がある場合は、その指定を優先する。
公開は`agent-toolkit:commit`の既存手順でpushとCI成功まで検収する。
`dotfiles`は`release-dotfiles`の条件に従ってリリースPRの作成・マージ・検収まで、`smpr`はpushとCI成功まで進める。
属性表のリリース対象5プロジェクトは、次の基準で必要な場合だけリリースする。

## リリースの認可

`gv`・`lc`・`glatasks`・`pyfltr`・`pytilpack`のリリースは、ユーザーの恒常的な認可に基づき、エージェントが要否とバージョン区分（パッチかマイナー）を判断して実施する。
メジャーはユーザーの明示指示がある場合だけとする。
この認可は`agent-toolkit:process-wi`の手動起動、`atk wi process-loop`による自動常駐起動、前項の恒常的認可または明示指定により公開まで扱う協調モードの作業に適用し、リリースのたびのユーザー確認とUWIは省く。
リリースworkflowを持たないプロジェクトは対象外とし（「前提」の属性表）、リリースworkflowを持ったプロジェクトは属性表で対象へ加える。

## 実施時機と前提

一連の作業の公開（pushとCI成功）が終わった時点でリリース要否を判定する。
`agent-toolkit:process-wi`では、公開工程の公開担当が返却し、`agent-toolkit:commit`の`references/push-and-ci.md`「公開状態の4項目」の成立を確認した後、`agent-toolkit:report-completion`の起動前に判定する。
process-wi以外の作業でも、作業の変更をpushしてCI成功を確認した時点で同じく判定する。

ローカルのベースbranchがリポジトリのdefault branchであり、未pushのcommitと未コミットの変更が無いことを実施の前提とする。
前提が成立しない場合はリリースせず、その理由を完了報告へ含める。
`releaser`は未pushのcommitをpushするため、この前提でpushの所有者を保つ。

## 判定

判定対象は引数なしの`releaser`が表示する`<直近のリリースタグ>..HEAD`の未リリースcommit全体とする。
各commitは差分の内容で判定し、commit typeは補助の手掛かりに留める。

エンドユーザー影響がある変更は、エンドユーザーがリリースされた配布物を通じて観測する挙動や内容を変える変更である。
配布されるコードのうちエンドユーザー向けCLI・公開API・設定を省略したときに使う値・画面を変えるものと、配布物に同梱されて公開されるエンドユーザー向け文書（PyPIの説明になるREADMEなど）の変更が該当する。
配布コードでも消費主体がエージェントだけで、エンドユーザーが配布物を通じて観測する挙動や内容を変えない場合は対象外とする。
MCPツールの入力スキーマの許容値・項目説明、エージェントだけが読むメッセージなどが該当する。
エンドユーザー向けの結果も変わる差分は前段の基準で判定する。
dotfilesではこの消費主体による除外を適用せず、エージェント向けの変更もリリース影響に含める。
`develop`から`master`への公開は`release-dotfiles`が扱う。
実行時依存の版指定の更新（`pyproject.toml`の`dependencies`、`package.json`の`dependencies`など）はエンドユーザー影響の対象外とする。
テスト、CIとworkflow、開発手順と開発用ツールの設定（`Makefile`・`mise.toml`・pre-commit・lint設定）の変更も対象外とする。
エージェント向け文書（`AGENTS.md`・`CLAUDE.md`・`.claude/`配下）、開発者向け文書（`docs/development/`）、開発専用のロックファイル更新も同じく対象外とする。
docsサイトは`master`へのpushで`docs.yaml`が公開するため、docsサイトだけの変更も対象外とする。
いずれとも判別できない変更は、配布物に含まれてエンドユーザーから観測できるかで判定する。

## 実施

該当する変更が1件以上ある場合だけ、次のバージョン区分からエージェントが区分を決め、`releaser <patch|minor>`を実行して完了まで検収する。
0件の場合はリリースせず、リリースしなかったことと理由を完了報告へ含める。

- バグ修正・軽微な機能追加: パッチ
- ある程度大きい機能追加や変更: マイナー

メジャーはOSSの慣例に従い、ほぼ全面的な書き直しや再構築などの場合にだけ使う。
セマンティックバージョニングの互換性を壊す変更でも、それだけではメジャーにしない。
エージェントはメジャーを選ばず、ユーザーが明示的に指示した場合だけ`releaser major`を実行する。

`releaser`はdotfilesの`pytools/releaser.py`が提供するコマンドである。
default branchで実行しているかと未コミット変更の有無を確認し、未pushのcommitをpushする。
続けてCI完了を待ち、`release.yaml`のworkflow_dispatchを起動してrunを監視し、上流branchが属するremoteを取得して上流branchへのfast-forwardでローカルを最新化する。
引数を省略した`releaser`はヘルプと未リリースコミットの一覧を表示するだけで終わる。
`gh workflow run release.yaml`などの低水準コマンドは、`releaser`の内部実装または人間が手動で補助する場合にだけ用いる。
`releaser`はCI待機とリリースworkflowの監視で長時間かかるため、前景の実行時間上限を超える場合は背景実行か委譲で実行し、終了状態を観測してから報告する。
