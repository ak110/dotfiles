# 追従台帳：CIとテスト

## Linux CIの共通方式をコンテナーにそろえる

- 項目ID: linux-ci-use-common-container
- 実施日: 2026年11月
- 内容: 通常のLinux検査にpyfltr公式イメージを使う
- 理由: 公開待機と検査集合を保ったまま、現在成功する共通方式を維持する
- 当てはまる条件: 通常のLinux CIに属する静的解析、テスト、ブラウザーE2E、配布物を検証するジョブ。
  例えばpyfltrの `distribution` は配布物の検証なので含め、成果物を公開する配布・リリースは除く
- 比較条件: 同じpush・同じソースとlock・同じ検査内容で、各方式の通常のキャッシュを使用。
  pytest直下の履歴は両方式とも復元できず全件を実行し、ホスト側のuvキャッシュは復元した
- 過去の実績: smprの `801b660` はLinux検査をホストへ移した。
  同一ソースの成功2試行（`45085514485` / `45085514462`、`45085714102` / `45085714081`）ではコンテナー127〜135秒、ホスト82〜84秒だった。
  128秒から81秒に短縮した個別実績を、共通方式の判断とは分ける
- 適用方法: dotfiles、pyfltr、pytilpack、glatasksの通常Linux検査はコンテナー実行を維持し、smprもこの方式へそろえる。
  smprは `8b77d91` で適用し、CI run `45117053953` でLinuxとWindowsが成功した。
  dotfilesのホスト上のセットアップとRust検査は維持する。
  gvにLinux検査は新設せず、lcのLinuxセットアップ、glatasksのDocker Compose、pyfltrの環境互換性の検査は維持する
- 参照先: [dotfilesの比較run](https://github.com/ak110/dotfiles/actions/runs/45116121628) と[CI / リリース関連](ci-and-tooling.md#ci--リリース関連)
- 適用済みの見分け方: 対象ジョブがコンテナーを使い、各プロジェクトの既存CIが成功している

[比較run](https://github.com/ak110/dotfiles/actions/runs/45116121628) の記録を示す。
各列は準備・検査・ジョブ全体の順で、単位は秒。

## CIキャッシュを依存入力に対応させる

- 項目ID: ci-cache-by-dependency-inputs
- 実施日: 2026年11月
- 内容: 必要なサブディレクトリだけを保存し、依存入力が同じ実行では保存を省く
- 理由: イメージ同梱分の再圧縮と、不要になった版の累積を減らす
- 当てはまる条件: GitHub Actionsで実行ごとに変わるキーや前方一致の復元を使い、キャッシュを毎回保存している
- 適用方法: 推奨ガイドのCI節に沿って増分と再取得時間を測り、対象・入力ハッシュ・イメージ識別・保存するジョブを決め、同じ入力の2回目で保存が無いことを確認する
- 参照先: `github.com/ak110/pyfltr`の`docs/guide/recommended.md`「CI」と`.github/workflows/ci.yaml`
- 適用済みの見分け方: キーが依存入力を反映し、対象が必要な領域に限られ、完全一致の復元後は保存を省くことがActionsログから分かる

## 検証範囲を保ってCIを短縮する

- 項目ID: ci-runtime-and-job-structure
- 実施日: 2026年10月〜11月
- 内容: ジョブの責務分離、重い検査の独立実行、変更領域の選択と所要基準を整える
- 理由: 同じ準備や検査の重複と資源競合を減らし、CIの待ち時間を抑える
- 当てはまる条件: 直列実行、重い検査の同居、無関係な領域の検査、所要基準の欠如のいずれかがCIにある
- 適用方法: 律速と準備・本体・後処理を測り、検査集合を保って分割し、未知の変更は全体へ戻し、失敗を必須checkへ伝え、プロジェクトの実績から所要基準を定める
- 参照先: `github.com/ak110/dotfiles`の`.github/workflows/ci.yaml`と`.claude/skills/develop-dotfiles/references/verification.md`「テストとCIの所要基準」
- 適用済みの見分け方: 必須検査の集合と失敗伝播が検証され、変更領域の選択理由と、全体・律速ジョブの所要を基準と比較できる

## 試験の途中終了でも失敗名を保存する

- 項目ID: preserve-test-failures-before-interruption
- 実施日: 2026年10月
- 内容: 試験ごとの名前と結果を逐次出力し、中断前に完了した失敗を保存ログから識別できるようにする
- 理由: 最後の詳細表示へ到達しない場合にも、調査と再検証の対象を選べるようにする
- 当てはまる条件: CIで失敗した試験名を実行末尾の出力だけから得る
- 適用方法: 詳細進捗の出力を既存の収集へ加え、巨大な自動IDは短い明示IDへ直し、途中終了のログでも失敗名・外側終了状態・未完了範囲を区別する
- 参照先: `github.com/ak110/dotfiles`の`.github/workflows/ci.yaml`と`.github/actions/prepare-python-check/action.yml`
- 適用済みの見分け方: pytestなら詳細表示の引数があり、打ち切った保存ログにも完了済みの失敗node IDと結果が残る

## 任意pytestをマーカーで選択する

- 項目ID: pytest-explicit-optional-marker-selection
- 実施日: 2026年10月
- 内容: 任意実行の試験群を環境変数の全件skipからマーカーの選択へ移す
- 理由: 実行条件の指定漏れで1件も実行しなかった検証を、成功と取り違えないようにする
- 当てはまる条件: 環境変数が無いと試験群全体がskipされ、pytestが終了0になる
- 適用方法: 試験へ専用マーカーを付け、通常設定で除外し、明示実行のタスクから選択し、選択0件の非0終了と明示実行の成功を確認する
- 参照先: `github.com/ak110/dotfiles`の`pyproject.toml`、`Makefile`
- 適用済みの見分け方: 任意指定の欠落を全件skipで扱わず、通常実行では除外し、該当ファイルだけを無指定で起動した場合は収集0件の非0になる

## LinuxからWindows向けにビルドする

- 項目ID: linux-windows-cross-build-setup
- 実施日: 2026年10月
- 内容: Linuxの環境構築を1タスクにまとめ、Windows向けのビルドと可能な検査を実行する
- 理由: Windows専用アプリでもLinuxで開発し、コンパイルや静的検査の不良を早く検出する
- 当てはまる条件: Windows向けの.NETまたはRust製品をLinuxから開発する
- 適用方法: .NETはWindows targetingの有効化、Rustはcargo-xwinなどを比較し、setup・test・buildへ接続し、Linuxで実行できない試験や除外機能を明示してWindows CIで検証する
- 参照先: `github.com/ak110/lc`の`Directory.Build.props`と`mise.toml`、`github.com/ak110/gv`の`mise.toml`と`scripts/setup_linux.py`
- 適用済みの見分け方: `setup-linux`後に通常のtest・buildタスクが成功し、Windows用exeを生成でき、Linuxで未実行の試験はWindows CIが担う

## 前の版との比較を使うCIにベースコミットを渡す

- 項目ID: ci-select-base-for-change-comparison
- 実施日: 2026年11月
- 内容: 設定の廃止や移行漏れを検出する検証に、イベントに合う比較元を渡す
- 理由: 現在の設定だけでは削除されたキーを列挙できず、浅いcheckoutでは比較元のコミットを読み取れない場合がある
- 当てはまる条件: 追加・削除を判定する検証をpull requestとpushの両方で使い、比較元の選択や取得をCIが保証していない
- 適用方法: pull requestはbase、pushは更新前のコミットを比較元として渡し、そのオブジェクトを取得する。
  履歴がない初回pushや比較元を解決できない場合の扱いも決め、通常の削除と比較不能を区別する
- 参照先: `github.com/ak110/dotfiles` の `.github/workflows/ci.yaml` と `scripts/check_managed_claude_settings_removals.py`
- 適用済みの見分け方: CIログにイベント別の比較元と判定結果が残り、比較元を取得できないときに比較が成功したと表示しない

## 同じツリーの検証結果を昇格先で使う

- 項目ID: reuse-green-ci-for-identical-tree
- 実施日: 2026年11月
- 内容: リリース先への反映が検証元と同じツリーなら、成功した検証を使い、同じ検査を繰り返さない
- 理由: コミットIDだけが異なる昇格で、同じ入力の検証を繰り返さない
- 当てはまる条件: 検証を終えたブランチからリリース用ブランチへ同じツリーを反映し、両方で同じ検査を実行する
- 適用方法: 正規のワークフローで全必須ジョブと分割が成功した結果だけを使う。
  ツリー、検証条件、必要な結果のいずれかを確認できない場合は検証を実行する
- 参照先: `github.com/ak110/dotfiles` の `.github/workflows/ci.yaml` とコミット `9b1ac0e62`
- 適用済みの見分け方: 同じツリーの成功時にだけ昇格先の検査を省き、失敗・実行漏れ・ツリー差分がある入力では昇格先で検証する

## 形式検証の記録と対象の一致を確かめる

- 項目ID: verification-skill-digest-sync
- 実施日: 2026年11月
- 内容: 形式検証スキルのfrontmatterに `verifies` と `verified-digest` を記録し、CIとコミット時に対象ファイルの変更を検出する
- 理由: 検証スキルが古い実装を記述したまま正常終了する状態を放置しない
- 当てはまる条件: dotfiles・glatasksなど、追跡対象のコードに対する形式検証スキルを持つプロジェクト。
  検証スキルを作る場合も対象
- 適用方法: 検査を含むpyfltrへ更新する。
  対象ファイルを `verifies` に指定し、スキルに従って検証を実行してから `pyfltr verification-sync --update <SKILL.md>` を実行する。
  CIは作業ツリー、コミット時はGit indexを対象とする
- 参照先: `github.com/ak110/pyfltr` の `docs/guide/usage.md`「サブコマンド: verification-sync」と `docs/guide/recommended.md`「形式検証の記録」
- 適用済みの見分け方: 記録を変えず対象だけ変更すると既存のCI・コミット検査の入口から失敗し、検証を再実行して記録と対象をそろえると成功する
