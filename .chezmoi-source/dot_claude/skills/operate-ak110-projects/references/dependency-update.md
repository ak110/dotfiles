# 依存更新の判定と実施

個人プロジェクトの依存を、明示の要求かロックファイルの古さで更新し、一括更新コマンドの1回の実行で完了させる手順書である。
一括更新コマンドは`SKILL.md`「前提」の属性表の値（`Makefile`の`update`か、`Makefile`を持たないプロジェクトでは`mise.toml`の`[tasks.update]`）を使う。

## 個人プロジェクト着手時の依存更新

1. 更新するかを決める。
   - ユーザーの要求か採用済みのAWIが、一括更新コマンドの生成範囲の更新を明示している時は、ロックファイルの最終commit日時によらず更新する。
   - 明示の要求が無いAWI処理では、一括更新コマンドが実際に更新するロックファイルだけで判定する。
     対象プロジェクトの開発手順を定めるスキルが一括更新の対象外のファイルを示す時は、判定の前にそのスキルを起動して除く。
     ロックファイルの最終commit日時（`git log -1 --format=%cI -- <ロックファイル>`）が1日以上前（目安）なら更新し、1日未満なら見送る。
   - 提供元が直して公開済みの既知の不具合の修正が必要な時は、日数によらず更新し、使う側のバージョンと実行で解消を確かめる（`agent-basics:bugfix/references/recurrence.md`「前回の対策を調べる」）。
2. 計画を作るAWI処理では、計画の確定と実装の着手の前に判定し、判断を計画の`## 反映内容と反映先`へ記録する。
   更新する場合も据え置く場合も、対象プロジェクト、判定対象、判定結果、予定する更新の範囲か据え置く範囲と理由、認可元（本スキルと本節）を書く。
   計画を作らない処理では計画を足さず、同じ判断と認可元をWIと`review_contract`で実行レビュー担当へ渡す（手順6の経路）。
3. 計画の作成の後、計画対象の編集の前に、一括更新コマンドを1回実行する。
   依存更新は、計画の前の診断だけの実行、隔離したworktree、差分の退避、同じ依存更新の再実行を足さずに、この1回の実行で完了とする。
   一括更新コマンドが全体の検証まで連鎖してフォアグラウンドの時間上限内に終わらない時は、依存更新と全体の検証を別のフォアグラウンドの実行へ分ける。
   この分割は、再実行ではなく同じ依存更新の続きとして扱う。
4. コマンドが生成した差分の全体を検収し、同じcommitへ含める。
5. 更新後の検証が失敗したら、配布物のバージョン指定（`pyproject.toml`の`dependencies`など）が破壊を生じるバージョンへ届きうるかで扱いを分ける。
   - 届きうる時は、エンドユーザーの環境で成り立つ欠陥として同じセッションで是正する。
   - 開発環境のロックファイルの中に閉じる時は、更新を巻き戻して独立したAWIとして登録してよい。
   - バージョン指定に上限の記載があっても、破壊を生じるバージョンがその範囲に入れば届きうると判定する。
     Cargoで演算子を省いたバージョン指定（キャレット要件として扱われる）のように上限が常にある記法があるため、上限の有無を判定の基準にしない。
6. 実装の開始の後に巻き戻しか一部の据え置きが分かったら、計画凍結の契約に従って計画を書き換えず、実行レビュー指摘管理表と引き継ぎ記録へ実際の範囲と理由を書く。
   計画から得られない認可の情報は、初回のレビューの起動時に`agent-toolkit:atk-mode/references/review-contract.md`「`review_contract`の生成」の手順で実行レビュー担当へ渡す。

### レーンへ委ねる場合

`agent-toolkit:atk-mode`の作業`process-wi`で依存更新をレーンへ委ねる時は、要否の判定と認可の根拠を担当へ渡し、計画を作る場合は手順2のとおり計画へ記録させる。
レーンへの依頼の固有の指示には、手順3の分割の条件と同じ更新の続きであること、手順5の扱い、`references/cross-project-followup.md`「足回りファイルの推奨設定維持」の適用を含める。
本スキルを起動するのはメインだけであり、判定の結果だけを渡すと、レーンは失敗を据え置く判断や推奨設定の緩和を本スキルの規定と比べずに選ぶためである。

## 返す報告に含める項目

判定対象と判定結果、実行した一括更新コマンドと終了状態、巻き戻しや据え置きの範囲と理由を返す。
