# 委譲の共通契約の設計記録

[設計記録の索引](design.md)と[担当の責務と工程間の知識境界の設計記録](design-workflow-boundaries.md)から参照する主題別の記録である。

## 委譲の共通契約

上位担当は原因確定、設計判断、観点の選定と返却の統合を所有する。
確定済みコマンドの実行・結果観測・確定済み根拠からの起草と追随は、中位以下へ分ける。
工程表の担当段位を保ち、工程内の機械作業ごとに必要な段位を選ぶ。
1回の受信上限と担当全体の読取量を分けて評価し、原子的な読取範囲を保って分担する。

一般委譲で編集ファイルと是正論点を渡す場合は、同じ論点に属する同一ファイル内の別節まで担当範囲に含める。
process-wiの書込境界はWIの要求（目的・対象・完成条件）とし、廃止済みのメインによるファイル名指しへ戻さない。
節ごとに名指しの追送を反復する案は、同じ是正を一度で完結できなくするため採用しない。

委譲の粒度は独立文脈、段位と役割契約、起動・規範の自動配送・明示読取・親の検収・統合と再試行を含む総費用で選ぶ。
本文量の固定境界を判断の主軸にすると共通背景の読取を細かな担当へ重ねるため、同じ要求の連続作業はまとめる候補とする。
独立要求、独立文脈レビューと単一writerの境界を保つ。
詳しい文脈を持つ元担当へ調査と技術判断を戻す判定は、新しい本文読取・追加調査・回答作成の前に行う。
親は認可、全体調整と検収を所有する。

WI作成専用セッションでは要求数によらずメインが調査・起草・保存を原則として担う。
文脈分離による品質向上か複数要求の並行処理による総費用の改善が見込める単位だけ委譲する。
共通の調査・引用・原因分析・重複・成立性・起草・保存手順はwi-standardsへ集約した。
親が原稿を検収しない手順には投入前レビューを戻す。
他作業の文脈を持つ投入は独立起草・親の意味の検収・保存開始の二段階を保つ。
全投入に同じ分担を課す案は専念型にも親子の共通読取と保存中継を重ねるため採用しない。
実行レビューの差分外の既存不良の投入は、2026年10月18日のユーザー回答により専念型へ移した。
不良はレビューを受領したエージェントの変更対象の外にあり、親の作業文脈が意味の検収へ加える情報が少ない。
受領した時点で専念型の担当を起動し、原因分析・起草・投入前レビューを別の文脈へ移すことで、受領側の文脈と待ち時間から差分外の調査を外しつつ検収を保つ。
残りの工程を停止・遮断する不良だけは受領側がその場で扱う。
専念型を使う場面の定義は`agent-toolkit:/share/add-wi-parent-launch.md`「起動方法」に一本化し、他の文書は参照する。
検収が確定するのは原稿の意味（要求の被覆、採用案、反映先、成立性と、先行要求と参照箇所の対応）であり、先行項目の正式ファイル名は保存操作で後から定まる識別子である。
依存する組をまとめて検収した後の正式名への置換だけを再検収へ戻すと、意味の変わらない往復が生じる。
そこで置換だけの差分は作成主体が先行項目の保存結果と比べて同じ検収結果で保存し、参照先・依存の必要性・要求内容が変わる差分は再検収へ戻す。
一括投入で組内の依存名を自動解決する機能を新設する案は、識別子の確定時点と意味の検収を分ける目的に対して実装と保守の範囲を広げるため採らない。
投入前レビューは独立した意味の確認を保ちつつ、投入の採否を左右する成立性の不足と計画工程で決める詳細を分ける（`agent-toolkit/skills/wi-standards/references/draft-semantic-review.md`）。
2026年10月18日の専念型のWI作成で、局所修正が生んだ状態遷移を次の再判定が指摘する往復が6回続き、テストdoubleの形などの計画で決められる具体化も投入条件へ積み増された観測に由来する。
指摘ごとに成立性への作用を添え、再判定では前回指摘の解消・修正差分・要求追加を分けることで、修正由来の不成立を保持しながら変更外への内部設計の要求を抑える。
専念型のレビュー担当と付随型の親は同じ基準を読む。
レビュー回数を一律に制限する案は要求追加と修正由来の不成立を取り残し、ラウンド台帳やhookは意味の判定を代替できず恒常費用を加えるため採らない。
投入前レビュー担当と付随型の親は、原稿の要件分類を`agent-toolkit:wi-standards/references/origin-and-approval-origin.md`「由来と`source`」で判定する。
選択回答がユーザーの指定として確定するのはその質問が問うた判断だけであり、質問本文・選択肢の説明・`共通前提:`行から補った実行方法や対象除外はユーザーの指定に含めない。
LinuxからWindows向けの開発を可能にするWIの作成で、到達範囲を問う質問の選択肢説明にあったタスク配置をレビューが確定要件とし、技術判断で決められる分担をユーザーへ追加確認した観測に由来する。

親の会話履歴の大半を委譲先も要する作業では、Claude Codeの`Agent` forkとCodexの`spawn_agent`全履歴forkを使える。
判定基準は`agent-toolkit:delegation`の`references/routing.md`へ集約し、ホスト別の起動形だけを各runtime資料へ分ける。
forkは起動時点の会話を入力として共有するため、委譲プロンプトへ同じ背景を書き直さずに済む。
独立文脈レビューと工程別モデル設定のある委譲は、先入観のない評価または指定effortを守るため新規セッションの起動を保つ。
agents_serverへfork機能を実装する案は、ホスト標準の起動手段でユーザーが選んだ結果へ到達でき、別の実装と保守を増やすため採用しない。

単発の委譲は常時規範の基本委譲契約を適用し、対象、読取・書込権限、完了条件および受領後に成果物を直接確かめる検収を確定する。
工程別モデル設定、複数主体調整、継続、停滞検知または巻き取りを使う高度な委譲だけが、`agent-toolkit:delegation`の手順を適用する。

委譲元が委譲プロンプトへ載せる値に起因する欠落は、委譲元が起動前に防ぐ。
委譲先の`<役割名>.subagent.md`が要求する必須入力が委譲プロンプトにそろっていること、絶対パスで示す入力のうち起動時点で作成済みのものが実在すること、および委譲先が受領した値から自ら解決して読むplugin配下の資源が実在することを、委譲元が起動前に確認する。
委譲先の`<役割名>.subagent.md`は必須入力がそろい、参照する資源が実在するかを着手前に再確認して差し戻す手順を持たない。
欠落の検知点を委譲元へ一本化することで、委譲先の起動、規範と対象の再読、委譲元の再判断を重複して費やす往復が生じない。
必須入力と資源の確認は委譲元が自ら行い、解決した絶対パスを委譲先へ渡して実行させない。
委譲先がplugin配下の資源を自ら解決する手順は、plugin導入版の更新時に古いパスを使わないために維持する。
判定の基準は、入力や資源の欠落を委譲元が防げるかである。
絶対パスの実在のように機械的に確認できる項目に加えて、担当種別ごとに異なる必須入力の完備と、委譲元が組み立てる契約の各条項の充足も、値を載せる主体が委譲元である以上は委譲元の確認対象とする。
委譲先へ差し戻しを残すのは、Codex互換レイヤーが自ホストのplugin導入情報から起点を確定する処理のように、委譲先自身の実行環境に起因し委譲元から観測できない事象に限る。

実行中に`<役割名>.parent.md`を更新した場合に加え、`<役割名>.subagent.md`を更新した場合も、両者を同一のplugin rootから原子的に適用する。
統合済みworktree側に両者がそろい委譲起動契約を満たす場合だけ、そのrootの`<役割名>.parent.md`と`<役割名>.subagent.md`のパスを後続委譲へ採用する。
いずれかが欠ける場合や契約確認が不成立の場合は、稼働開始時のplugin rootにある両者へそろえて戻す。
どちらか一方だけを切り替える案は、版ごとには整合する必須入力名が版間で一致しないため採用しない。

`agents_server`の`start`の`cwd`は委譲先が作業場所とGit状態を解決する起点とする。
同じworktree、Git共通ディレクトリ（`--git-common-dir`）、linked worktree、現在branch、リポジトリ直下の規範は名前付き入力へ重ねない。
名前付き入力は、対象識別子、成果物のパス、観測境界、別worktreeの統合先など、呼び出し側だけが保持する状態へ限定する。
省略可能な入力の省略時の値と行が無い場合の解釈は`<役割名>.subagent.md`が持ち、呼び出し側は省略時の値と一致する行を送らない。
この分離により、環境情報の基準をGitと`<役割名>.subagent.md`の契約へ集約し、委譲元との不一致を表現できない構造にする。

Claude Codeで委譲先がさらに読み取り専用調査・レビューを委譲する場合は、起動前にmanaged-tempの中の成果ファイル絶対パスを確定する。
専用の`<役割名>.subagent.md`かagent定義がある場合はそれが定める完全な完了報告を成果形式とし、委譲プロンプトへ汎用形式を複製しない。
孫は返信先を解決できない場合も完全な最終結果を成果ファイルへ同期的に確定してから終了し、直接の委譲元は実行時に観測できる委譲先の終了後に同じファイルを再読して検収する。
完了通知の到着・祖先からの中継は成果本文の受領条件にしない。
一方、委譲先の終了を観測できない場合、稼働中の途中内容および終了後の欠損・読取不能・不完全な成果は成功扱いせず、続行できない理由を返して一時領域を保持する。
読み取り専用の委譲先へ実装担当限定の所有プロセス終了証拠を要求する案は観測不能な受理条件を生じさせるため採用しない。
全委譲へ成果ファイルを要求する案は通常の直接委譲へ恒常的な入出力を増やすため採用せず、配送不着を観測した孫以深の読み取り専用調査・レビューへ限定する。

固定書式で返す委譲先が想定外の結果を観測し、`SendMessage`で即時通知できない場合は、指定形式の末尾へ`想定外事象:`の1行を追加して委譲元へ渡す。
返却手段を増やさず地の文の禁止だけを1行分緩めるのは、固定書式の機械判定を保ったまま、重要度の高い事象が抑止される事態を防ぐためである。

分配または分類の結果を固定書式で返す委譲では、返す側が受領した入力集合と返却する区分の集合を突合し、過不足と重複の不在を1回のコマンドで確認してから返す。
受領側も同じ突合を再実行してから後続工程へ進む。
目的は入力の一部が返却から欠落した状態を、分配を委ねた作業の終了で検出することである。
構造の理由は、返却の妥当性を判定できる知識が返す側と受領側の双方にあり、返す側だけの確認では返却本文の破損を受領側が検出できず、受領側だけの確認では差し戻しの根拠となる中間状態を返す側が失うためである。
知識境界として、入力集合の基準は委譲プロンプトが挙げた識別子とし、返す側は委譲プロンプトにある識別子を区分へ写像する責務だけを持ち、区分の定義そのものを再設計しない。
確認を受領側だけに置く案は、返す側が保持する分配の中間状態を失い、差し戻しの粒度が返却全体になるため採用しない。
区分ごとの件数の一致だけを確認する案も、同じ識別子が2つの区分へ現れる誤りを通すため採用しない。

委譲先が複数値を返し、受領側が要素ごとの対応または集合を確認する欄はJSON配列で表す。
`adoptを延期したAWIとcommit`はAWIファイル名とcommitの対応を持つオブジェクト配列、`延期後にadoptしたAWI`はAWIファイル名の文字列配列とし、0件はどちらも空配列とする。
`変更したエージェント向け文書`はエージェント向け文書のリポジトリ相対パスを重複なしの文字列配列とする。
受領側は配列の形式を確認し、既に読んだ文書か残工程で読むことが確定した文書だけを統合先worktreeから再取得する。
返す委譲先と受領する委譲元は同じ配列境界を契約テストで検証する。
区切り文字を含む散文値は、複数件の境界とAWI・commitの対応を一意に復元できないため採用しない。

知識境界として、委譲の要否判定は`agent-toolkit/share/rules/common/01-agent.md`が持ち、
`agent-toolkit:process-wi`は委譲の要否を判定する場面だけを定める。
工程別モデル設定を持つ委譲では、委譲する工程を定める節が用いるキーを指定する。
却下した代替案は、割り込み作業の委譲先を一律に単一のキーへ固定する案である。
工程ごとに適した委譲先が異なり、用途を定めたキーの適用範囲を越えるため採用しない。
公開工程の工程をメインが自ら実行する案は、公開担当が所有するCI修正（CI修正担当の起動と受領）を含む工程全体がメインのコンテキストを消費し、ユーザー判断への応答余地を狭めるため採用しない。
公開担当へ専用の設定キーを新設する案も、公開工程の判断量が実装と同等であり、execute工程の適用範囲に収まるため採用しない。
レーンの終了操作をメインへ残す案は、レーンの最後のレーン担当が同じ資源とrefまたは7文字以上の一意な短縮OIDを保持しており、メインへ戻すと同じ値の受け渡しと再確認が増えるため採用しない。
統合するレーン担当の手順を実装担当の`exec.subagent.md`へ担当種別として同居させる案は、同書の冒頭がコミット単位の実装を責務とし、必須入力へ実装するコミット単位を要求し、実装手順が計画ファイルの編集を禁じているため採用しない。
同居させると、実装しない統合の手順に対して同じ行為の義務と禁止が並存する。
新しい委譲境界へ`<役割名>.parent.md`と`<役割名>.subagent.md`のペアを設けない案も、委譲先が読む恒常手順が委譲プロンプトの本文だけになり、起動のたびに手順を複製することになるため採用しない。
観点、読者像、返却項目および権限を毎回同じ内容で定める委譲は、委譲元の規範に契約を置くと起動のたびに委譲プロンプトへ書き直され、委譲プロンプトが長くなり表現も揺れる。
このため投稿前レビュー（`external-write-review`）、自動コードレビュー監査（`copilot-review-audit`）、文章成果物の読者別探索（`reader-fit-review`）、一括置換後レビュー（`bulk-replace-review`）はペアで定める。
委譲元は対象と実行時の値だけを渡す。
読み取り専用の3件は`mode: explore`で軽量に起動する。
委譲先へ届く規範とスキルは限られる（`agent-toolkit:delegation/references/delivery-scope.md`の配送範囲表）ため、判定基準を`<役割名>.subagent.md`の中で完結させる。
書込を伴う監査は通常委譲の`execute`とする。
読者別探索の初回から、実行レビュー担当が変更前・現行・今回差分と直接影響範囲を渡す。
再レビューでは前回確認版とレビュー指摘管理表から読者ごとの修正範囲・未解決事項を生成する。
新規文書と新規回答は全文を今回差分とし、既存文書の変更外の不良や範囲外の新要件を通常指摘へ混ぜない。
読者別探索担当は全文を文脈として読み、指摘候補は修正箇所と直接影響範囲から選ぶ。
前回確認版はレビューしたHEADとGit管理外本文の複製をmanaged-tempへ記録し、同じthreadでは保持し、引き継ぎ時は宣言済み入力で渡す。
質問への回答下書きも同じ比較に含み、対象のない読者は探索を再起動しない。
読者ごとの終了statusと返却本文を確認し、失敗・本文欠落を指摘0件へ変換しない。
公開waitのnext_actionと既存の回復契約に従い、同じ読者の結果を回収してから判定する。
比較元が不足したまま全体探索へ戻す案は、無関係な既存部分を再レビューへ戻すため採用しない。
探索指摘の採否は受領したレビュー担当が確定し、実行レビューでは走査結果の全指摘をレビュー指摘管理表の行または不採用理由へ対応付ける。
返却前に各指摘の対応を確かめ、採用分の統合だけで受領を終える案は未対応の指摘を検出できないため採用しない。
成果物、読者、対象コマンドが毎回異なる単発の起草（`start`の`write`）、コマンド実行（`start`の`shell`）、探索（`agent-toolkit:delegation`の`references/routing.md`）は自由本文の起動に残す。
契約の大半が起動ごとの値であり、ペアへ移しても委譲プロンプトは短くならないためである。
