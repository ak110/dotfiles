# 方針・意向: 計画と実行

## 計画と実行の運用

レビュー指摘の採否は`agent-basics:review-standards`の`references/reviewee.md`が定める。
工程別のモデル割当は`agent-toolkit:delegation`の`delegation/references/process-model-settings.md`が定める。
計画の成果物契約は`agent-toolkit:write-plan`の計画ファイル基準が定める。

- `atk`のキュー操作と計画保存のコマンドが自身の出力で成功を報告した場合は、その出力を根拠に完了と判定し、同じ状態を別のコマンドで取得し直さない。
  コマンドの出力に成功の報告があり、警告がないことを完了判定の基準とする。
  成功を報告しながら保存状態が伴わない事象は`atk`側の欠陥として`atk`を是正し、呼び出し元の恒常的な確認を維持する根拠にしない（2026年9月8日、ユーザー指示）
- レビュー指摘、改善提案、ユーザーの割り込み・是正要求および想定外の発見を受領しても、その時点では修正すると決めず、通常運用での再現手順と影響を独立に実物で確かめて必要性を立証する
- 採否は何も変更しない案を含め、残置した場合の実害と認知・保守費用、修正・検証・再レビュー費用および変更が増やす複雑性を同じライフサイクルで比較して決める
- 実害がなく意味も変えない単独誤記は、独立した修正・再レビューを起こさず、重大修正に伴う再レビューがある場合だけ同時に是正する
- 利用者向け文書の誤記または適用対象のスタイル違反は実害ありとして必ず是正し、低頻度リスクの費用比較から除外する
- その他の実害があり得る是正要求等は、発生条件・頻度・影響・残余リスクを観測し、恒常的な複雑性と保守性低下が利得を上回る場合は採用しない
- 是正要求等が達成すべき改善効果を指定する場合は、その効果を受入条件として先に確定する。
  現行構造を維持する案と変更する案を同じ階層で比較し、個別の不具合調査を比較に基づく設計判断へ対応付ける。
  構造を変更する案を、比較の前から採用する前提にしない（2026年9月8日、ユーザー指示）。
  現行の規定は`agent-basics:review-standards`の`references/reviewee.md`にある
- 修正前に過去の指摘・採否・合意・設計理由・障害対策および既存成功パターンを確認し、修正後は変更全体の自己点検と該当する自動チェックを完了して、そのまま公開できる状態だけを完了とする
- 実作業（実装・検証）はCodex等の外部実行系へ極力委譲し、
  オーケストレーションと固有知識の調査をClaude側が担う
- レビュー修正とCI失敗修正はexecute工程へ割り当て、実行レビューはreview工程で単一の実行レビュー担当へ委譲する。
  実行レビュー担当は計画との比較の後に成果物評価を同じコンテキストで行い、工程の性質に応じて設定を分ける
  - 実行レビュー担当が証拠を記録しないまま返す事象への対策では、段位を上位（当時の`high_tier_model`）へ上げる案（実機対照で全件記録）を示したうえで、ユーザーが中位（当時の`medium_tier_model`）のまま証拠の雛形出力で補助する案を選んだ（2026年10月2日、ユーザー回答）
  - 担当がさらに分ける作業の段位は、作業の性質で選ぶ。
    上位段位の担当（レーン担当など）は計画・設計判断・原因分析を自ら行い、仕事を分解して内容の確定した書込作業（単発のコーディングなど）をchores工程の委譲先へ割り振り、自ら行う方が安い場合だけ自ら行う。
    計画などの判断を分けるのは独立が明らかな複数タスクに限る（2026年10月19日、ユーザー指示。レーンから起動した委譲先が全て上位段位で動いていた観測に由来する）。
    現行の規定は`agent-toolkit:delegation`の`references/process-model-settings.md`「工程別モデル設定」の工程分担の段落と`references/routing.md`「委譲単位の確定」にある
  - 工程別にexecute・review・review_fast・chores・chores_fast・orchestrate・writeの7候補列を直接持つ。
    5プリセットはwriteを除く6工程の組を保存する。
    executeとorchestrateの初期値はClaudeを先頭にし、solは予備に置く。
    agy・OpenCodeは必要な工程へ直接指定する。
    段位9キーとengine順5キーから移行し、同居する古い工程値より合成値を優先する（2026年10月22日、ユーザー指示）。
    現行の規定は`agent-toolkit:delegation`の`references/process-model-settings.md`「工程別モデル設定」にある
- モデル指定時は推論の深さ（effort）も必ず併記する。
  `agents_server`を呼び出せず`Agent`ツールへ切り替えた委譲はeffortを渡せないため例外とし、渡せなかった設定値を報告へ記録する（2026年9月30日、ユーザー回答）
- OpenCodeは一般の委譲先として使い、orchestratorには使わない。
  必要な工程別キーへ`opencode:<provider>/<model>[@<effort>]`を直接指定する。
  OpenCode本体もupdate-dotfilesが未導入時に導入する（2026年10月20日の方針を2026年10月22日の工程別設定へ追随）。
  現行の規定は`agent-toolkit:delegation`の`references/process-model-settings.md`「工程別モデル設定」にある
- 計画は要求の調査と計画ファイルの起草までを指し、計画を作成する主体が担う。
  計画ファイルは人間の承認を要しない内部資料とする
- 実行は確定済み計画の変更作成、検証、実行レビュー、統合、WIの採否確定および資源回収までを指し、メインが調整する
- 実装は実行の配下で成果物の変更作成とコミットを担う下位担当だけを指す
- 規範、ガイド、設計文書などの説明文はこの3語を日本語で用い、エージェント名、設定キー、ファイル名など英語が必要な識別子だけ`plan`・`exec`系を用いる。
  3語の定義と綴りの使い分けの現行の規定は`agent-basics:writing-standards`にある
- レビュー反復の原因判定は、`agent-basics:bugfix`の次の資料を参照する。
  - `agent-basics:bugfix/references/root-cause-scenarios-recurrence.md`「反復した指摘の原因判定」
  - `agent-basics:bugfix/references/root-cause-severity-quality.md`「前提の再検討」

  個別修正の反復から工程・規範の構造の見直しへ接続する導入目的を保つ
- 過去計画30件のレビュー実績の実際の集計では、起草側の完成条件に対応の無い検出側専用の判定基準5件と、
  ラウンド数上位3事例での新設機構への段階的な指摘（最終的な機構の撤去・縮小で収束）を観測した。
  これに基づき、計画の成果物契約は
  `agent-toolkit/skills/write-plan/references/plan-file-standards.md`へ一元化する。
  レビュー用タスク文書へ検証項目を追加しない（2026年8月、ユーザー指示）
- push後はCIが成功することまで確認して初めて作業完了とする。
  CI成功の待機を省略できる例外条件を定める規範は現行に無い
- CIの早期失敗を検出したら全jobの終了を待たず直ちに調査へ着手する
- 2026年8月19日のユーザー指示は、条文が存在しても未適用を対策不要として終えないための判断である。
  未適用の原因と処置は`agent-toolkit:review-session`の`references/analysis-operations-root-cause.md`「規範の未適用と目的逸脱」を参照する。
  `agent-basics:bugfix`の`SKILL.md`「再発防止策の必須性」も併用し、各工程の恒久反映の契約から接続する
- 計画の起草、WIの実現方式の確定、実装および実行レビューでは、変更を適用した後の成果物群の設計品質（章構成、責務、他の成果物との関係）が変更前より劣化しないことを不変条件とし、各工程で評価する。
  毎計画の評価と変更後のファイル全体の読解は負担を増やすが、劣化を後から全関係リポジトリで見直す費用の方が大きいため、評価を省かない。
  2026年10月7日のユーザー指示による。
  計画のリファクタリングの検討がファイルの分割などの細部に留まり、分割後の章構成と他の成果物との関係を評価していなかった事象を契機とする。
  「過剰設計の抑制」の追記の不採用は常時ロードの読込量を増やす知識の追記を対象とし、この評価の工程には適用しない。
  現行の規定は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/design-heuristics-quality.md`「設計品質の劣化確認」にある
- 対象ファイル全体の読解は実装工程の規範とし、計画工程の調査範囲はコーディングエージェントの裁量に委ねる。
  理由は計画ファイルへ書かれない読解が実装工程へ引き継がれないことと、
  部分読解によるスタイル逸脱とリファクタリングの必要性の見逃しが実装工程で生じることとする（2026年9月2日、ユーザー指示）。
  変更が1つの定義の中に閉じる場合は、差分が参照する定義、同じファイルの共有の準備処理と補助関数、影響を受ける利用箇所、書き方が分かる周辺の読取で編集へ進める。
  複数の定義の構成を変える場合と、読んだ範囲に重複や不整合を見つけた場合は全文を読む。
  2026年11月10日のユーザーの発話「それはさすがに無駄なので規範も緩和したい気はする」による。
  契機は、2,154行のテストファイルの定数1行の修正に、全文読取で約24,000トークンを使った観測である。
  緩め方はエージェントが選定した。
  直近7日間の1,000行以上のファイルの編集5件では、編集前の全文読取が2件、部分読取が3件で、読取範囲と不良の対応を確定できる記録は無かった。
  現行の規定は`agent-basics:writing-standards/references/implementation-time-style.md`「編集前の読解」にある

### 経緯（計画と実行の運用）

- 各レーンでは計画を起草した担当が同じthreadで実装と変更範囲の検証まで続ける。
  実装系モデルは上位段位（当時の`high_tier_model`、現行は`execute`工程）を用いる。
  現行工程には計画ファイル（詳細）のモデル区分と計画レビューを含めない（2026年9月13日、ユーザー指示）
