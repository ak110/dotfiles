# 選定の書込範囲と入力解決の設計記録

[設計記録の索引](design.md)と[担当の責務と工程間の知識境界の設計記録](design-workflow-boundaries.md)から参照する主題別の記録である。

選定結果は変更予定を`書込対象`と`公開工程の書込対象`へ記録する。
参照先・除外先の全列挙は求めず、書込予定の個別対象の欠落はメインが元本文と限定調査で意味検収する。
レーン分け、別レーンとの重なり、包含と連結成分の判定には、同じ段階のレーン担当が書く`書込対象`だけを使う。
`公開工程の書込対象`は対象リポジトリの規範が全レーン統合後の公開工程だけへ書込を割り当てたパスに限る。
パスごとの規範ファイルと見出しを`公開工程の規範根拠`へ記録する。
明示的な割当を確認できない対象と、レーン工程でも書く対象は`書込対象`に残す。
`書き込まない反映先`は参照先と除外先だけを持ち、公開工程所有の退避先には使わない。
公開工程の所有をレーン競合へ混入させないため、両書込区分を分離する。
廃止前のpickerはこれらの値をAWI本文の`## 反映内容と反映先`から手で書き写すため、反映先の一部を欠いた値や上位ディレクトリだけを書いた値がレーン工程へ渡った（`docs/development/incidents-workflows.md`の2026年10月1日の記録）。
`atk run-script pick-wi-check`は`agent-toolkit/skills/process-wi/scripts/check_selection_paths.py`で反映先の文章とインラインコードから、完全なパスと、ディレクトリに続く省略したファイル名を抽出する。
インラインコードは内容全体を1つの候補とし、文章中のパスはASCIIの候補に続く非ASCIIの文字まで伸ばした実在の最長パスを候補とする。
パスの文字をASCIIに限って走査すると、`docs/dev/ログ監視.md`を範囲`docs/dev/`、`docs/design/LLMへのファイル入力.md`を途中の`docs/design/LLM`として読み、旧pickerに実際には書かない範囲を`書込対象`へ置かせた（2026年10月6日の観測）。
文章中で実在しない非ASCIIのパスは後続の日本語の文と終わりを区別できないため、インラインコードで書かれた場合だけを全体で読む。
抽出するのは作業ツリーに実在するファイルとディレクトリ範囲、および拡張子までそろい親ディレクトリが実在する新設先のファイル名に限る。
直後にグロブ記号（`*`、`?`、`[`、`{`）が続く語は、`share/rules/rules-*.md`の`share/rules/rules-`のようにグロブや波括弧展開の途中で途切れた断片として抽出しない。
実在しないファイルの候補が追跡ファイルのパス末尾とパス要素単位で1件だけ一致する場合は、`share/exec.parent.md`を`agent-toolkit/share/exec.parent.md`とするように追跡ファイルへ読み替える。
親ディレクトリの実在だけで採ると、途切れた語、不在の略記ディレクトリ、別の起点からの略記が新設先として抽出され、旧pickerが`書き込まない反映先`へ1件ずつ分類する手作業を生んだ（2026年10月6日の観測）。
書込予定のパス・範囲の妥当性と、任意で記載した非書込区分との重複を確かめる。
`書き込まない反映先`のディレクトリ範囲が書込区分のパスを真に含む組は重複に数えず、そのパスは書込区分の指定を優先し、範囲の残りを書き込まない扱いとする。
AWI本文が変更しない範囲として上位ディレクトリ（「他の`docs/`配下は変更しない」）を挙げ、その配下で個別のファイルを書く選定を表すためである。
同じパスを2区分に置いた組と、書込区分の範囲が非書込のパスを含む組は従来どおり重複とする。
範囲説明は書込予定の列挙と分け、不要な上位範囲を追加させない。
書込区分のディレクトリ範囲が反映先の個別ファイルを不要に広げていないことと、公開工程区分の各パスに規範根拠がちょうど1件あり、規範ファイルと見出しが実在することも確かめる。
変更要求、公開工程所有、参照か除外かの意味上の分類はメインが読む。
生成・確認・保存を同じ操作で行い、その成功結果と元本文を比較すれば、選定した主体がその場で修正できる。
暫定範囲が他候補と重なる場合は、限定調査で変更するファイルと定義を確定してから連結する。
未確定の範囲をそのまま占有範囲へ使うと、独立した項目まで直列化するためである。
調査しても範囲を狭められない場合は、その根拠を残して既存の分割不能規則を適用する。
分類と配分は、AWI・UWI本文の変更要求を読み、既存・新設・参照・除外・公開工程所有を判別し、必要な限定調査で変更領域を確定して行う。
抽出パス、存在、名前順、一定件数だけでは文脈の意味を保証できない。
`pick-wi-check`が報告した違反を修正するときも元本文へ戻り、変更領域が変われば競合と配分を再評価する。
メインは元本文を取得して意味検収を行い、不一致のWIと観測箇所を記録して分類・配分を修正する。
根拠には配分比較・不可分条件を持たせ、共通パスと双方の定義の独立性は構造化した`レーン間の重なり`へ置く。
同一レーンの全書込集合や無関係なレーンのパスを再掲しない。

ファイルに付く行番号・行範囲・節参照は、文章とインラインコードの双方で元ファイルの参照として読む。
ファイルの「の」に続くクラス・メソッド名を親ディレクトリで補完すると、存在しない新設ファイルと誤認するため、ディレクトリの「の」によるファイル指定と区別する。
並列列挙、日本語パス、一意な追跡ファイルの略記と、親が実在する完全な新設先は維持する。

列挙の後続名では、本文が明示したディレクトリと先行ファイルの親から推測したディレクトリを区別する。
推測した親に実体がない裸名は、補完前の名前で追跡ファイルの末尾と比較し、一意ならその実体へ解決する。
複数の候補がある場合はその一覧とリポジトリ相対パスによる明示方法を診断し、架空の新設先や任意の候補へ決めない。
2026年10月9日の`_atk/help_text.py`と`atk_help_test.py`の列挙は補完後の名前だけを比較すると前者の親にある架空の新設先になった。
候補の由来と実体の一意性はAWI・UWI共通の解決境界が所有する。
全文相対パスへの書き直しを全入力へ課す案は転記負担を増やすため採らず、孤立語の全リポジトリ検索も新設しない。
同親の既存実体、明示ディレクトリの新設先、完全な相対パスの新設先は維持する。

処理中の追記後は全体YAMLへ`--body-wi <WI名>`を反復指定し、本文の取得と、書込予定のパス・範囲・区分・プロジェクト規範の指定の適合確認だけを追加した処理対象WIへ限定する。
構造・モデル・再開計画・段階・レーン重複・公開工程根拠は全体について確かめる。
既存項目を削った部分YAMLでは既存レーンとの関係を判定できないため採らない。
指定省略は従来どおり全件、未知指定は終了コード2とする。
初回は省略形で全件を対象とし、追加用の意味判断は生成付きmergeで元YAMLへ保存するときに`--body-wi`を指定する。
成功出力は実際に本文の条件を確かめたWI集合と、形式・書込予定について確かめた範囲を示し、意味検収はメインに残す。
`pick-wi-check`は同一段階の未統合レーンが共有するファイルか狭い方の範囲ごとに、双方の独立した定義と判定を求める。
別段階では現在の書込予定の重複から先行関係を導く。
詳細の余剰・重複・必要な記録の欠落、同じ定義の独立性宣言、同段階の交わる判定と先行関係の欠落・逆転を拒否する。
別段階・統合済み相手の旧詳細は履歴として読み、詳細の欠落を拒否しない。
意味上の独立性はメインが検収する。
追加側は新旧間と追加内の必要な詳細を記録し、識別子の変換と同一レーン記録の除去は統合操作が所有する。
旧欄名は`_plan/selection.py`で現在の欄名へそろえる。

追加選定の統合は`atk run-script pick-wi-check -- <既存YAML> --merge <追加YAML> --lane-map <対応JSON> --output <保存先YAML>`へ集約する。
対応JSONは追加側の全レーンから最終レーンへの辞書である。
既存の識別子と項目を保持し、選定・所要時間・重なりの3列と先行レーンを同じ対応で変換する。
所要時間と根拠を合流し、自己重なりを除去し、同じ無向の組とパスの双方の定義を保持する。
全体チェックが成功した場合だけ原子的に保存するため、WI重複・対応の欠落・合流後の不整合で元の入力と保存先を損なわない。
メインの最終割当を同じ統合操作へ渡し、全体チェックに成功して元の選定結果へ保存した後に意味検収を行う。
分類と割当の意味は生成入力と元本文からメインが先に検収し、成功試行と本保存を重ねず元YAMLへの保存を1回で行う。
別の統合コマンドを設ける案はチェックの所有者を分け、手作業の変換は3列の食い違いを残すため採らない。

書込要素自身も、実在ファイル、末尾`/`付き実在ディレクトリ、または抽出した新設先に限定する。
環境変数名や存在しないログ名は書込予定の比較を成立させないためである。
抽出した実在ディレクトリも末尾`/`へそろえ、コマンド内のディレクトリと範囲指定の比較を一致させる。
`pick-wi-check`は選定結果をYAMLとして解析し、欄名、必須の欄と型を同じ受理境界で確かめる。
自由記述の値の`:`や`#`が引用されずに残ると、別の主体が解析できずにレーン工程で止まった（2026年10月2日）ためである。
終了コード2の案内は原因で2群に分け、内容と形式の誤りには選定結果の修正を、引数・パス・private-notesの解決失敗には起動条件の確認を示す。
メインの確認は最後の書き込みと`pick-wi-check`の終了状態、意味検収を結び付ける。
選定後の追加は統合操作が保存と全体チェックを同時に行うため、その成功を使う。
書き直した結果へ以前の成功を使うと、修正で欠いた分類がレーン工程まで残るためである。
旧2主体の返却欄と受領側の再実行は撤去する。
選定YAMLへチェック状態を複製せず、最新の実行結果を既存の引き継ぎ記録に保持する。
構造チェックの成功だけでは意味の分類を保証しないため、メインが元本文と限定調査の現物を比較する。
保存後のチェックと意味検収は初回・修正後・追加・0件に同じ基準で適用する。
確認結果の別保存先やハッシュを追加する案は、既存コマンドが書込予定と全体の関係を確かめるため採らない。
`書き込まない反映先`は反映先が参照先や除外として挙げる書き込まないパスを分類する欄である。
反映先には非書込のパスが混在するため、全パスを`書込対象`へ必須とすると書込範囲が広がってレーン統合が増える。
公開工程所有の対象もこの欄へ移す案は、process-wiで実際に書く責務を非書込として表し、公開工程への受渡しと分類根拠を失うため採用しない。
非書込の記載は任意とし、規範指定の条件も両書込区分から判定する。
ほかに却下した代替案は次の3つである。
既存の`plan-check --selection-file`を拡張する案は、同コマンドが計画ファイルを必須とし、レーン分けの確定後の計画起草時にしか実行されないため、欠落の検出がレーン着手後のままになる。
3区分をAWI本文から自動生成する案は、書込主体と参照・除外の意味を機械的に区別できないため成立しない。
条文の追記だけで直す案は、同じ条文が既にあって適用されなかったため採らない。
AWI本文の探索は計画構造の自動チェックと同じ`agent_toolkit/_plan/locations.py`の`find_wi_source`を使い、状態ディレクトリの扱いを1箇所に保つ。
