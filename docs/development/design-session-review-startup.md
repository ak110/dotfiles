# 振り返りの起動と失敗回復の設計記録

[設計記録の索引](design.md)

## review-sessionの構成と候補抽出

manifest作成前に子が終了した失敗は、次のSessionStartが診断ログと復旧操作を一度通知する。
manifest作成後は既存batchの失敗報告が所有する。
失敗報告は配布元リポジトリへのAWIとし、process-loopの処理担当が原因を是正する。
失敗報告の削除と原因の是正を区別するため、起票済み失敗キーを既存の短時間ロック下に保存する。
未完了AWIは配布版にかかわらず自動再試行を止め、削除後も同版では抑止を保つ。
配布版変更後は再試行できるが、同じキーの報告は重ねない。
終了AWIの観測で起票済みを解除する。
キューの存否だけで抑止する案と期限で起票済みを消す案は、原因未是正のまま同じ報告が再発するため採らない。
失敗本文へ対象入力・ホスト・記録属性・準備結果と有限の診断ログを埋め込み、別ホストの担当が合成入力で検収できるようにする。
ログ全体や会話本文の転記は、情報量と秘匿性の負担が大きいため採らない。
ユーザーの判断が要る点だけを処理担当がUWIで確認する。
失敗報告と抑止の対象は、是正できる原因を持つ失敗に限る。
記録ファイルの無いClaudeの待ち対象は、発話せずに終了した会話がSessionStartで登録されたもので、振り返る内容が無い。
準備へ渡すと不足の失敗になり、原因の無い失敗報告が同じ対象で反復したため、選定の時点で待ちから外す。
SessionStartでの登録をやめて最初の発話で登録する案は通常の会話の登録時点も変えるため採らず、準備側で不在を成功とする案は手動の準備で誤ったパスを渡した場合の診断を失うため採らない。

診断を残さず実行プロセスだけが終了した回（端末の停止など）は、同じ対象の1回目を失敗報告と抑止にせず、対象を待ちに残して次の選定で再試行する。
同じ対象の同じ世代が続けて中断した場合は、従来どおり失敗として報告する。
中断の回数は実行記録だけから数え、待ち記録へ状態を足さない。
再試行を無制限にする案は、実行のたびに終了する原因がある場合に報告されなくなるため採らない。
以前は報告先リポジトリへの事後承認型UWIとし、回答まで自動再試行を止めていた。
準備段階の失敗ではモデルが起動せず回答を取り込む主体が無いため、回答のたびに同じ失敗と報告が繰り返された（2026年10月30日、ユーザー指示で変更）。
準備に失敗した対象は他の対象から切り離し、1対象の失敗で他の対象の振り返りとモデル起動を止めない。
対象なし、活動中のみ、排他見送りは正常な見送りとして試行を確定し、pending件数や経過時間を失敗判定に使わない。

未報告の失敗と実行中の試行は保持し、報告済み・受付済み記録は既存の30日sweepへ統合する。

起動試行、batch、対象世代は`_common/session_review.py`の独立した型と遷移APIが所有する。
起動側とスキルのfinishは同じ短時間ロックで交換し、保存済みJSONのキーを保持する。
分析成功と報告同期が揃ったbatchだけを完了にし、準備後の新しい世代は別に残す。
これらを1つのstatusへ統合する案は、分析・報告・追記が別々に進む関係を失うため採らない。

## batchの共有状態

2026年11月19日に、振り返りのbatchの手順書（`agent-toolkit:atk-mode/playbooks/review-session-batch.md`）から状態の詳しい説明を外し、本節へ移した。
手順書にはエージェントが守る所有の境界と処理済みを確定する条件だけを残している。

`_common/session_review.py`はhookと活動状態の削除から独立した、OSアカウント共通の`{state_dir}/session-review/`を管理する。

- `pending/<host>-<session_id>.json`: 最上位のSessionStartがhost、会話ID、記録パス、cwd、リポジトリ、開始時の更新時刻、登録世代、batch由来かを保存する。
  処理済みの会話のUserPromptSubmitも再登録する。
  委譲先とサブエージェントは登録せず、成功の確定か取消しまで保持する。
- `reviewed/<host>-<session_id>.json`: prepareが増分を選ぶための、記録ごとの最後の完全な行と同一性を保持し、古い結果が返っても確定済みの範囲を保つ。
  batchの部分分析では、欠測の情報と、末尾の欠測を含む観測済みの物理範囲も保持する。
  元の記録が全て無く、pending、未解決の失敗、未確定のmanifestのどれからも参照されない時だけ回収する。
- `runs/`: 実行IDごとのmanifestに、開始日時、固定した対象、報告先、準備範囲、分析結果、プロセス、失敗を保持し、中断後の報告同期と未確定範囲の検収に使う。
  未確定と報告未達のものは確定まで保持する。
- `record-index/<runtime>-<走査rootのハッシュ>.json`: `_common/record_metadata_index.py`が、カタログ走査の使う記録ごとの本文なしの値を保存する。
  記録の識別（inode、更新時刻、大きさ）と値を計算するコードの版が同じ記録は解析し直さず、全記録の列挙とstatは照会のたびに行う。
- `state.lock`: 登録、状態の更新、成功の確定を短時間だけ排他する。
  モデルの起動、利用上限の待機、WIの保存はこの排他の外で行う。
- `batch.lock`: 自動と手動の全リポジトリで、対象の選定から報告同期の検収と成功の確定まで共有する。
  親が中断した時も、プロセスの識別と、子の起動引数に含めた固有のmanifestパスで生存を確かめ、二重起動を防ぐ。
- `failures/`: 起票済みの失敗キーを保持する（扱いは本書「review-sessionの構成と候補抽出」）。
- `weekly/<作業>.json`: 週枠の作業（`meta`、`research`）ごとに、実行中の回、完了を確かめた回、失敗（metaは失敗キーと是正AWIの同期、researchは同じ回の失敗回数と報告の有無）を保持する。
  旧判定（前回の開始から7日）の`meta-start.json`は初回の参照時にこの記録へ移して削除し、開始時刻では起動を判定しない。
- `weekly/research-positions.json`と`weekly/research-positions-pending.json`: 外部情報の調査の情報源ごとの読んだ位置とXのアカウントIDだけを保持する。
  取得時は回の保留へ書き、回の結果のUWIを保存した後に確定する。

  手動の再試行も、未完了の既存の失敗報告AWIを再利用する。

`session_review_auto_start`がfalseでも待ちを登録し、SessionStartで件数と手動の操作を通知する。
単発のprepareは指定が無ければ厳格に読み込み（部分の読込は`--allow-partial-records`）、単発の`complete`は未確認範囲を含む準備結果を拒否する。
欠測を明示した部分分析を確定するのはbatchだけである。

## 週枠による週次の起動

メタ分析と外部情報の調査は、日曜14時（ホストの現地時刻）を開始とする週枠ごとに1回実行する（`agent-toolkit/agent_toolkit/_atk/weekly_schedule.py`）。
判定は最新の到来済みの週枠だけを対象とし、日曜14時より前は前週の枠が最新になるため、前週が未完了の時だけ追いつく。
2回以上逃した場合も過去の枠は実行しない。
回の完了の根拠は、`weekly_slot: <作業>@<日曜の日付>`を持つ結果のUWIが全状態のどこかにあることとする。
`atk run-skill`が子へ`AGENT_TOOLKIT_WEEKLY_SLOT`を渡し、`atk wi add`がその作業の起動単位の報告用UWIと選択型UWIへ記録する。
ローカルの記録より前に止まっても保存済みのUWIで完了と判定できるため、同じ回の再調査・再課金・二重の通知が起きない。
保存の前に止まった回は未完了のまま次の判定で再実行する。

起動の経路は`atk weekly run`と、取り逃した回を追う最上位セッションの開始・終了のhookである。
`atk weekly run`は`atk serve`が15分ごとに独立プロセスで起動し、`atk weekly install`で登録したsystemdのユーザータイマーかタスクスケジューラも呼ぶ。
どの経路も`run_skill_batch.weekly_auto_start_due`で判定し、`batch.lock`で排他する。
OSのスケジューラはsystemdの`Persistent=true`とタスクスケジューラの`StartWhenAvailable`で停止中の回を起動後に追う。
メタ分析の失敗は従来の失敗キーと是正AWIで抑止する。
外部情報の調査はAWIの起票をユーザーの回答に限るため是正AWIを起票せず、失敗から6時間後の判定で同じ回を再実行し、同じ回の失敗が2回に達した時に報告用UWIを1回保存する。
6時間の間隔は、`atk serve`の15分ごとの判定が失敗のたびにモデルと外部APIを使い続けるのを避けるためである。
調査の実行では、`atk run-skill`のログへ子セッションの出力を事象の種類と文字数だけで写し、取得した投稿や記事の本文を残さない。
