# 振り返りの起動と失敗回復の設計記録

[設計記録の索引](design.md)と[振り返り・知見集約の設計記録](design-session-review.md)から参照する主題別の記録である。

## review-sessionの構成と候補抽出

hook起動は試行ごとのプロセス同一性と受付記録を保持する。
manifest作成前に子が終了した失敗は、次のSessionStartが診断ログと復旧操作を一度通知する。
manifest作成後は既存batchの失敗報告が所有する。
失敗報告は配布元リポジトリへのAWIとし、process-loopの処理担当が原因を是正する。
失敗報告の削除と原因の是正を区別するため、起票済み失敗キーを既存の短時間ロック下に保存する。
未完了AWIは配布版にかかわらず自動再試行を止め、削除後も同版では抑止を保つ。
配布版変更後は再試行できるが、同じキーの報告は重ねない。
終了AWIの観測で起票済みを解除する。
キューの存否だけで抑止する案と期限で起票済みを消す案は、原因未是正のまま同じ報告が再発するため採らない。
失敗本文へ対象入力・ホスト・記録属性・準備結果と有限の診断ログを埋め込み、別ホストの担当が合成入力で検収できるようにする。
ログ全体や会話本文の転記は、情報量と秘匿性の負担が大きいため採らない。
ユーザーの判断が要る点だけを処理担当がUWIで確認する。
失敗報告と抑止の対象は、是正できる原因を持つ失敗に限る。
記録ファイルの無いClaudeの待ち対象は、発話せずに終了した会話がSessionStartで登録されたもので、振り返る内容が無い。
準備へ渡すと不足の失敗になり、原因の無い失敗報告が同じ対象で反復したため、選定の時点で待ちから外す。
SessionStartでの登録をやめて最初の発話で登録する案は通常の会話の登録時点も変えるため採らず、準備側で不在を成功とする案は手動の準備で誤ったパスを渡した場合の診断を失うため採らない。
診断を残さず実行プロセスだけが終了した回（端末の停止など）は、同じ対象の1回目を失敗報告と抑止にせず、対象を待ちに残して次の選定で再試行する。
同じ対象の同じ世代が続けて中断した場合は、従来どおり失敗として報告する。
中断の回数は実行記録だけから数え、待ち記録へ状態を足さない。
再試行を無制限にする案は、実行のたびに終了する原因がある場合に報告されなくなるため採らない。
以前は報告先リポジトリへの事後承認型UWIとし、回答まで自動再試行を止めていた。
準備段階の失敗ではモデルが起動せず回答を取り込む主体が無いため、回答のたびに同じ失敗と報告が繰り返された（2026年10月30日、ユーザー指示で変更）。
準備に失敗した対象は他の対象から切り離し、1対象の失敗で他の対象の振り返りとモデル起動を止めない。
対象なし、活動中のみ、排他見送りは正常な見送りとして試行を確定し、pending件数や経過時間を失敗判定に使わない。
未報告の失敗と実行中の試行は保持し、報告済み・受付済み記録は既存の30日sweepへ統合する。

起動試行、batch、対象世代は`_common/session_review.py`の独立した型と遷移APIが所有する。
起動側とスキルのfinishは同じ短時間ロックで交換し、保存済みJSONのキーを保持する。
分析成功と報告同期が揃ったbatchだけを完了にし、準備後の新しい世代は別に残す。
これらを1つのstatusへ統合する案は、分析・報告・追記が別々に進む関係を失うため採らない。
