# 進捗のセルフチェック通知の設計記録

[設計記録の索引](design.md)から参照する、進捗のセルフチェック通知の記録である。

## 進捗のセルフチェック通知

目的は、長時間の作業で時間に対する進捗と改善策の有無を、ユーザーの介入を待たずにエージェント自身が点検することである。
委譲先のレビューの往復が13時間続き、ユーザーが介入するまで誰も点検しなかった事象と、委譲先が同じ想定外事象を十数回返しても原因を調べなかった事象（2026年10月27日）を契機とする。

構造は次のとおりとする。

- PostToolUseとUserPromptSubmitが共通の`progress_self_check.claim_notice`を呼ぶ。
  両ホストのhookで発火するため、メインと委譲先の全セッションが対象になる（Antigravityはアダプター経由）
- セッション状態の`progress_self_check`へ呼出主体ごとに開始時刻と最後の通知時刻を持ち、最初の観測は記録だけにする。
  前回の通知から1800秒以上たった観測で、経過時間と点検項目を`source="progress-self-check"`の通知として1回返す
- 機械注入のターン（定期再確認、タスク完了通知など）にも付ける。
  委譲先を待つ間に届くターンは主に機械注入であり、除くと長い待機の間に点検の契機が無くなるため
- 実ユーザーの発話の有無や無操作期間の長さによらず、前回通知からの経過時間で判定する。
  発話が続く間も30分間隔の点検を保つため
- 通知本文は工程の所要時間・反復・不足情報を比較する短い契機を持つ。
  比較に使う情報と改善判断の詳細は`agent-toolkit:delegation/references/waiting-and-monitoring-progress.md`「成果物側の観測」が持ち、規範側は`QCDと3段判定`の定期点検へ接続する
- 点検結果は問題の有無にかかわらず既存記録へ残す。
  委譲先の正常な前進のみの点検は、残工程の見込みが目標所要時間の内側にある場合だけ次の工程返却へまとめ、判断・認可・入力・レーン調整、無視できない改善、停滞の新根拠は既存契約どおり通知する。
  目標がある場合は、目標までの残り時間と残工程の見込み、共有の待ちの累計を比べ、差があれば代替案で残りの工程を組み直す。
  組み直しの手段は待ち・重複・手戻りの削減に限り、次のセッションへの持ち越しと品質維持に必要な工程の省略を除く。
  省いた工程はCIの失敗などの手戻りで時間面でも逆効果になりやすいとユーザーが示したためである。
  通知文面は、委譲先から受け取ったクリティカルパスの所要も規模と待ち・本体の内訳に照らして確かめるよう求める。
  2026年11月11日の巡回で、見込みが目標を大きく超え実行枠の待ちが1時間以上積み重なっても、点検が「正常な順番待ちで前進している」として対策へつながらなかった観測に由来する
  点検の実施と送達時機を分け、通知ごとの受領往復を増やさない
- 作業契約と必要な要求原本・計画・進捗記録から、当初目的と有効な全要求、保持対象、完成条件別の証拠・未達・残工程を比べる。
  全工程を100%とする概算と根拠、現在の作業の必要性、優先順位、反復の収束、低負担な方式を見直す。
  割り込み対応の一部完了を全体完了と誤認する問題への点検契機であり、新しい状態やタイマーは持たない（2026年11月、ユーザーの全体点検要求による具体化）
- 通知の生成と期日の消費を分ける。
  期日到達で予約し、最終出力へ採用された時点の配送記録で確定する。
  生成後の出力障害や未採用で期日を消費すると、通知が届かないまま次の期日まで遅れたため（2026年10月31日の故障注入による観測）
- 通知の時刻はhookが通知を採用した証拠に限る。
  点検の意味的な十分性は、エージェントが計画・引き継ぎ・実行記録との比較を報告して示す。
  実施確認用の状態や専用監視は自己申告を増やすだけで点検内容を保証しないため採らない

却下した案は2つある。
1つはagents_serverから委譲先へ点検の指示を挿入する案である。
hookが両ホストの委譲先でも発火するため、委譲基盤に別の配送経路を足す必要が無い。
もう1つは規範の条文だけで定期点検を求める案である。
既存の「長い工程では定期的に」の条文はあったが、点検の契機が無く、上記の事象では働かなかった。

既知の制約は次のとおりである。

- Codexのexplore委譲はpluginを無効にして起動し、thread設定で接続したPostToolUse（matcher `Bash`）だけが届く。
  Bash実行後の通知は届き、PreToolUseなど他のhookによる通知は届かない。
  shell・writeの委譲はpluginを有効にしたまま起動し、pluginのhookを受ける（thread設定でhookを重ねない）
- PostToolUseはhooks.jsonのmatcherに挙がったツールだけで発火する。
  matcher外のツールだけが続く区間では、次の対象ツールかUserPromptSubmitまで通知が遅れる
- `started_at`は最初のツール実行か発話で初めて観測した時刻であり、セッション開始よりわずかに遅れる
