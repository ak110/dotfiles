# セッション状態と記録解決の設計記録

[設計記録の索引](design.md)から参照する、セッション状態と記録解決の記録である。

## セッション状態の共有

独立プロセスとして動くフック間では、セッション識別子ごとの状態ファイルで単純な観測結果を共有する。
保存する状態はスキル起動やバックグラウンドタスクの起動など、後続判定に必要な小さな観測値に限定する。
更新は排他ロック下で実行し、原子的な置換で保存する。
この構造により、並列に発火したフックが互いの記録を失わず、再開したセッションでも必要な判定を継続できる。

命名用の種別と前回設定名も通常状態へ保存する。
session stateのJSONは`state_dir()/hook-sessions/claude-agent-toolkit-{sid}.json`へ置く。
通常のlockは`state_dir()/hook-sessions/.state.lock`の固定1個とし、TMPDIRが異なるプロセスも同じ排他を使う。
clearと期限回収でもlockを削除せず、sessionごとのlockファイルを蓄積させない。
共有排他は短いstate read-modify-writeだけを囲み、長いtranscript抽出と継承候補の準備はlockの外で行う。
準備結果の保存時はlock内で現行状態が不在のままかを再確認する。
旧temp lockは同じsession IDの旧JSONを移行する間だけ使う。
同じsession IDの旧JSONだけを初回読取で移行し、clearでは旧JSONも除く。
旧配置の読取互換と期限回収を保ち、TMPDIRが変わるホスト再起動後も同じ会話の判定を続ける。
一時ディレクトリだけに状態を置く案は、再起動で保存先が変わると起動済み委譲先の追送を拒否するため採用しない。

書き込み側のフックは観測したイベントだけを知り、読み取り側のフックは必要なフラグだけを判定材料にする。
状態ファイルは会話本文、成果物の内容または工程全体の進捗を正式な記録として保持しない。
成果物の適否は、対象ファイルと正式な検証結果から確認する。

`formatter`と`warning_formatter`が反復判定に用いる通知の指紋も、後続判定に必要な小さな観測値として同じ状態ファイルへ置く。
キーはイベント・主体・hook・原因・対象を結び付け、値には本文と次の操作の指紋を保存する。
同じ条件が続く間は初回だけ届け、判定範囲で条件が解消した原因を解除する。
過去の通知本文を再走査する案と発生件数だけを通知する案は、既存の小さな観測値で新規性を判断できるため採用しない。

プロセス内の変数だけで共有する案は、呼び出しごとにプロセスが分かれるため採用しない。
コマンド文字列や成果物のハッシュを多段階で同期する案も、状態と実態の不一致を新たに生むため採用しない。
状態をセッション終了時に直ちに削除する案は、同じ識別子での再開を妨げるため、期限を過ぎた状態だけを回収する。
回収は終了イベントを発したセッション自身を除いて実施し、会話が破棄された場合だけ終了イベントを発したセッションの状態を削除する。

### 出力の配送とセッション記録の解決

`additionalContext`文字列の10,000文字上限と、長い出力のファイル保存および2,000文字のプレビューは別の契約として扱う。
観測値の保証は同じ配送方法に限り、全hook出力へ適用できる上限とは区別する。
通知が受け取ったtranscript pathが実在しない場合は、同じClaude session IDのメイン記録を解決する。
0件では入力値を保ち、1件なら解決した記録を使う。
複数件では会話IDの明示を求め、一意性を推定しない。
開始時と別のディレクトリでの再開時に入力が実在しない記録を示したためである。
観測と再検証手段は[audit-records-hooks-lifecycle.md](audit-records-hooks-lifecycle.md)「docs/development/design-hooks-session-state.md：通知の整形と反復検出：2026年10月20日」にある。

応答言語判定は、send_to_userの`message`と、ユーザーへ直接送達される最上位メインのStopの`last_assistant_message`を対象とする。
AskUserQuestionの`questions[].question`・`header`と`options[].label`・`description`、ExitPlanModeの`plan`も既存の判定対象に保つ。
`options[].label`末尾の`(Recommended)`は、`rules-main.claude-code.md`「ユーザー確認（`AskUserQuestion`）」が付与を求める固定表記のため、記述言語の判定前に除く。
文字化けの判定は元の入力全体へ適用する。
通常操作の直前本文の取得と判定は撤去した。
StopとSubagentStopで最終応答が欠けた場合の判定は保持する。
終了を拒否する通知は、終了証拠、終了順序と委譲先観測の理由ごとに、実行できる続行またはユーザー確認への操作を返す。
不適切なblocked・waitの拒否境界は維持する。

圧縮再開時は既存のreview-session抽出を再利用し、メインと委譲先へ発話だけの要約`compaction-digest/conversation.md`（セッションのmanaged-temp内）を1通の通知で渡す。
要約はユーザー発話の全文とエージェントの発話（直近を長く、古いものを短く）を古い順に並べ、ツール呼び出し、記録位置、時刻を含めない。
委譲先の会話では、委譲元から受けた依頼（配送本文から機械生成の要素を除いたもの）もユーザー発話と同じ扱いで残す。
作業契約は委譲ごとの役割と入力の代わりにならないためである。
ユーザー発話と委譲元の依頼は、文書全体が上限を超える場合だけ、長いものから中ほどを省いて省いた字数を行内へ示す。
依頼の制約は末尾に置かれやすいので、末尾を省く短縮は使わない。
圧縮後に読む対象は作業契約とこの要約に限り、工程のスキル・役割文書・規範は操作・判断の条件に該当した時に読む。
入口のスキル`agent-toolkit:atk-mode`は読む対象の限定と別に扱い、SessionStartがメインへ起動を1行で案内する。
文脈を失って始まる会話（`startup`・`clear`）では作業の前の起動を、圧縮後（`compact`）では作業を再開する前の起動し直しを求める。
進めていた作業の手順書は入口の表から選ばせ、読む時点は上の限定と同じく操作・判断の条件に該当した時とする。
2026年11月16日に登録した入口の統一は圧縮後に手順書の読み直しも求めていたが、同18日に圧縮後に読む資料を限ったため、起動し直すのは入口だけにした。
通知は起動を求める1行に限り、入口の本文を載せない。
委譲先へは起動の本文が規範を届けるため案内しない。
hookを登録しないOpenCodeへは、導入時に設定の`instructions`へ登録する規範ファイルの1行で同じ案内を届ける。
生成の失敗、時間上限、子プロセスの回収不能のいずれでも、古い要約を除いて手動取得を案内する。
生成の失敗では子プロセスが標準エラーへ出した原因を通知へ含め、要約が上限を超えた場合は上限を上げた取得コマンドを示す。
同じ上限のコマンドを案内すると、同じ失敗を繰り返すためである。
新しいLLM呼び出しとPreCompact hookを設ける案は、既存の記録抽出で満たせる処理を重複させるため採用しない。
復元手順の資料、ユーザー発話の原文ファイル、会話抽出コマンドと手順資料を順に読ませる構成は撤去した。
2026年11月18日の実測で、復元だけに6往復・約5万字を要し、規範の一括の読み直しが文脈を埋めて次の圧縮を早めていたためである。

## 効率化の仕組みの棚卸し（2026年11月）

横断的な記録の条件と限界は[設計索引](design.md)の「効率化の仕組みの棚卸し」を参照。
10秒以上止まる基盤の改善はユーザーの要求で、排他区間の移動と未変更の記録の再利用は具体化である。
旧globalロックから会話別の排他へ変えた記録はあるが、自然な稼働での停止の所要と独立した件数は分からない。
探索をEventで保持した活動記録は、旧版1.003521秒、探索だけをロック外へ移した対照0.001223秒、旧版へ戻すと1.007638秒だった。
Stopへ約1.14MB・2.79MB・18.77MBの合成入力を各3回与えると、CPUの中央値は9.69msから1.67ms、19.78msから5.26ms、103.04msから15.62msになった（10月17日の`2d7724b38`・`1e0b3c220`の観測記録）。
自然な10秒の停止や全セッションの短縮へは帰属させない。
判定は維持とし、別会話の状態を同じものとして再利用せず、共有状態の更新の保全と変更時の再解析を保つ。
