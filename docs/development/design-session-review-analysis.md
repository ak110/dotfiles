# 必須候補の評価と分析の設計記録

[設計記録の索引](design.md)と[振り返り・知見集約の設計記録](design-session-review.md)から参照する主題別の記録である。

評価を必須とする候補は`atk run-script session-review-prepare`が候補一覧と1行JSONの`mandatory_candidates`で示し、振り返り結果報告は各候補の扱いを候補IDで示す（2026年10月7日、ユーザー指示）。
必須の候補は、ユーザー介入、ユーザー確認（`confirmation-request`）およびWIの記入欄の是正（`wi-user-response`）である。
ユーザー確認は選択肢どおりの確認への回答と、対象セッションが投入したUWI（`submitter_session`の一致で判定し、報告用UWIを除く）とする。
WIの記入欄の是正は、投入したUWIと`atk wi`の`start-processing`・`adopt`・`reject`・`unhold`の実行位置にあるWIから、選択肢と一致しない回答とユーザーコメントを取る。
以前は選択肢どおりの回答を`question-answer`として除外し件数だけを残していたため、不要だった確認が振り返りの入力から消えていた。
2026年10月7日の振り返りでは、メインが`references/analysis.md`を読まないまま必須のユーザー介入を「規範の当てはめ誤り」として見送り、Stopは任意の根拠を持つ`判定済み`の行を通した。
除外禁止の条文は事象の時点に存在したが文脈へ入っておらず、読込表の行は文脈にあっても従われなかった。
このため参照資料を読み込まなくても必須だと分かるようにし、準備の出力で示す。
見送れるのは、根拠の先頭へ除外区分を書いた`判定済み`、`未確定`、反復の欄を持つ`再発防止策なし`の行に限る。
候補IDを使わず報告の行数や見送りの件数を数える案は、どの必須の候補が欠けたかを示せないため採らない。
Stopで「当てはめ誤り」などの語を禁じる案は、言い換えで通過し正当な根拠にも誤検出する言い回しの判定に当たるため採らない。
人が読む`candidates.md`をStopが解析する案は、書式を変えるたびに判定が成立しなくなるため採らない。
2026年10月11日のユーザー指示でStopによる報告本文の判定を撤去し、候補の扱いは報告を書くメインが`agent-toolkit:report-completion`の`references/report-formats.md`に従って確かめる（[design-hooks.md](design-hooks.md)「終了工程の証拠」）。

2026年10月15日のユーザー指示により、候補の評価責任と再発防止策の新設を分ける。
`session_review_prepare_candidates.py`の`MANDATORY_KINDS`とJSONの`mandatory_candidates`は既存の候補種別・ID対応を保ち、表示は評価必須を示す。
重大度、探索の深さと終了はbugfixの共通定義へ集約する。
`再発防止策なし`の報告にはQ影響、重大度、探索範囲・限界と許容する残存リスクを残し、軽微な問題をQ影響なしとする旧一律条件を更新する。
意味判断は報告を書くメインが担い、専用のチェック・記録状態を加えない。
2026年10月10日のユーザー指示では、ユーザー自身の秘匿値の露出への過剰反応をやめる扱いを導入した。
2026年10月21日には、作業中に見つけた全ての資格情報を、所在ごとの報告だけで扱う判断へ一般化した。
報告まで規定どおり対応して終えた候補は、除外区分`credential-report`で`判定済み`にでき、各段の予防策評価と追加AWIを求めない。
資格情報を検出する新しい仕組みは加えず、該当の判定はメインが行う。
過剰反応自体の是正をユーザーが求めた発話は分析の対象に残す。

ユーザーの是正とWIの記入欄の是正には、private-notesの全状態・全対象リポジトリのWIから過去の同種記録を添える。
過去の同種記録は必須かどうかの判定に使わず、前回の処置で再発を防げなかった条件を調べる材料に使い、`再発防止策なし`の行の反復の欄へそのファイル名を1件以上書く。
発話を空白を除きNFKC正規化した20字以上の文に分け、文の文字5-gramの8割以上を`## ユーザー指摘の逐語引用`、`## 回答`、`## ユーザーコメント`のいずれかの節が含む場合を一致とする。
過去の振り返りの`user-intervention`候補207件とprivate-notesの全WI 6178件で比べると、WI本文全体と15字以上の文の完全一致では207件中154件が一致したが、スキル展開の定型文などが多数のWIへ一致した。
ユーザー発話の3節と12字以上・6割以上では、包含率8割未満の一致の多くが`(Recommended)`付きの短い文だった。
採用した条件では207件中19件が一致し、包含率9割5分未満の一致は同じ是正の言い換えと同じ環境のログに限られた。
言い回しが大きく異なる過去の是正は一致しないため、`references/analysis.md`「原因と対策」は由来と状態を限定しない`atk wi grep`の本文検索を併用する。
反復の検索を振り返り由来の採用済み項目に限る以前の条件は、ユーザーの手動投入で採用した前回の対策を見つけられなかったため改めた。

回復した手戻りの扱いは、`references/analysis-triage.md`「一次選別」の冒頭へ候補の種別によらない共通の判定として集約する。
元の期待する契約、実際の不成立と発生条件を先に判定し、回復した事実は別に記録して、不成立を認めた問題は「原因と対策」へ送る。
以前は回復による除外を防ぐ規定が失敗したコマンドや権限拒否などの種類別の箇条に散っていた。
2026年10月3日の手動振り返りは、探索担当への不成立な保存指示と、WI投入担当が旧方針を確認事項に変えた往復を、本文の受領や委譲元の追送で解消したことを理由に見送った。
所要時間も律速threadの総量を得た段階で、内部の照会と候補別の比較をせずに見送った。
見送りの根拠は「欠陥ではない」「原因が未確定」「分析後に処置を採用しない」の区別を既存の報告欄の記入内容で示し、報告の形式は変えない。
報告の段階と内容、証拠の実在、原因との対応と案の採否はメインが検収する。
意味を採点する仕組み、監視、毎回の別レビューを加える案は、既存の照会とメインの判断で同じ結果を得られ、追加の起動と状態の保守を課すため採らない。

律速となったagent threadの内部の工程・反復・待機の内訳は、`atk run-script session-review-prepare`が`stats.md`の律速threadごとの節へ書く。
`atk run-script session-review-evidence`はメイン記録と同じ集計（ツール別、60秒以上の間隔、反復、遅い呼び出し）を各agent threadの記録へ適用し、`--detail`へそのまま渡せる記録位置を付ける。
集計は収集済みの記録に対して行い、記録を読み直さない。
内訳の取得にメインによる規範の想起と追加の照会が必要だと、照会を省いても返却本文という説明が手元に残り、入力の欠落に気付けない。
2026年10月6日には、律速区間の委譲先を返却本文の説明と所要時間目標の適用外を理由に照会せず見送った。
2026年9月29日と10月4日に照会を求める条文を置いても同じ見送りが起きたため、照会という追加の操作を要しない準備の出力へ内訳を移す。
報告に内訳への言及を求めるStop hookは照会を経ない言及を区別できず、委譲先が自身の内訳を返却へ含める案は誤りを生んだ自己説明を根拠とするため、いずれも採らない。

振り返りはセッションで適用した規範自体がQCDの観点で最適かも見直す。
規範どおりに成功した工程の量が目的の操作に比べて過大かは、`references/analysis.md`「規範適用による目的逸脱」で判定し、一次選別の除外（必要な読込などを実行主体の誤りへ分類しない扱い）はその判定を妨げない。
2026年10月6日の振り返りは、委譲先1件の起動までに規範と手順書が求めた読込と準備操作（約58秒、ツール呼び出し11回）を、失敗が無いため問題に挙げなかった。
判断基準が問題を契約の不成立から定義し、規範どおりの工程の量を目的と比べる観点を持たなかったためである（2026年10月6日のユーザー指示を受けて観点を加えた）。
発話の間に連続したツール呼び出しの件数で機械候補を加える案は必要な裏付け調査の連続も候補に含め、正常な調査を機械候補へ加えない前述の方針と衝突するため採らない。
メインだけの区間の内訳を`stats.md`へ加える案も、準備区間が会話の流れに呼び出しの列として既に現れ、欠けていたのは判断基準だったため採らない。

2026年10月6日の旧方式では、同期振り返りの最終報告前に、準備より後に受け取ったユーザー発話を確かめ、追加があれば準備から再実行して分析へ含めた。
Claude Codeはターンの途中に入力された発話をキューから配送するため、振り返りの待機中にも発話が届くという観測に基づく。
report-completionとprocess-wiの公開工程からも同期起動していた当時の設計であり、現在の作業終了・公開では同期振り返りを行わず、非活動セッションを非同期batchで分析する。
作業完了報告は振り返りと独立して届ける。
当時、Stop hookで準備後の人間の入力を不足段階として検出する案は、入力位置の状態管理と最終報告後の入力を区別する仕組みを要するため採らなかった。
report-completionからの振り返り再起動条件を最終報告の直前へ広げる案も、振り返り自身の投入作業が必ず準備の後に生じて再実行が終わらず、手動起動も覆わないため採らなかった。
