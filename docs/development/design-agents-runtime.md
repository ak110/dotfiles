# 委譲先の稼働状態・起動診断・通知の設計記録

本書は[設計記録の索引](design.md)から主題別に分割した記録であり、機構の目的、構造の理由、知識境界と却下した代替案を保持する。
実行時に適用する規範は、各節が参照する現行のルールファイルとスキルが定める。

## 状態ファイルの構造と寿命

`agents_server`が`start`で起動したsessionは、Claude CodeのUIでは`atk agents wait`の応答が届くまで状態を観測できない。
このため`agents_server`はルートセッションごとのディレクトリへ生存中のsessionの状態ファイルを出力し、`claude-statusline`の`statusline`モードがセッション行の次の行以降へ1 sessionを1行で表示する。

状態ファイルは`atk config get state_dir`が返すディレクトリ配下の`agents-server/<ルートセッション識別子>/<書込主体>.json`とする。終端結果の未回収判定は、結果ファイルを扱える処理では公開済み・回収済み・未公開を区別する共通述語で行い、状態ファイルを記述できない処理だけは内部の配送済み状態へ縮退する。各書込主体は自身の状態ファイルと対応する一時ファイルだけを削除し、共有する終端結果と通知は保持期限を超えたものだけを回収する。別の書込主体の表示、未回収の終端結果、上り通知を起動または終了時の初期化で削除する案は、同じルートに属する並行した委譲の観測を失わせるため採用しない。
ルートセッション識別子は`AGENT_TOOLKIT_OWNER_SESSION`、無ければMCPサーバー起動時の`CLAUDE_CODE_SESSION_ID`から取る。`CLAUDE_CODE_SESSION_ID`は子プロセスの起動時に現行のsession識別子が注入される値である。Claude Codeが同一プロセスのままsession識別子を切り替えると、長命なMCPサーバーだけが起動時の値を保持し、statuslineが受け取る入力JSONの`session_id`と一致しなくなる。`claude --resume`で起動した場合も、MCPサーバーへ渡る`CLAUDE_CODE_SESSION_ID`と、会話のBashとフックが受け取る再開した会話の識別子が異なり得る（2026年10月2日の観測）。このため`agents-server/aliases/<現行のsession識別子>.json`へ索引を置き、statuslineと`atk agents wait`は会話IDの索引を経てルートセッション識別子を解決する。`atk agents notify`は所有者sessionを直接解決する方式を保ち、索引を読まない。MCPサーバーは`start`、`send_message`、`list`の応答（`show`の`verbose`では解決可能な場合）に、自身の状態ファイル書込先として解決した`root_session_id`を含める。`list`は保持sessionが0件でも`root_session_id`を返す。PostToolUseフックは、操作名を列挙せず、`root_session_id`を持つ応答であれば1か所の判定でその値を索引へ直接書く。再起動した会話の最初のMCP操作が終端済みsessionへの`send_message`であっても索引を書けるようにするためである。同じフックが`start`と`send_message`の新しいturnを待機対象へ登録するときは、`atk agents wait`と同じく索引を経たルートを使い、登録と読み取りを同じ名前空間にそろえる。状態ファイルは1秒単位で集約され、応答直後には起動したsessionが未反映であり得るため、状態ディレクトリの走査による逆引きは行わない。CLIの`list`と`wait`は索引か現行識別子自身の状態ディレクトリでルートsessionとの対応を確認する。対応未確認かつ対象0件ではCLIが解決したrootを示し、MCPの`list`を1回呼んで同じCLIを再実行するよう案内する。対応確認済みの空状態は通常の空状態として扱う。却下した代替案は、両側がClaude Codeプロセスの識別子を環境変数から解決する案と、鍵を作業ディレクトリへ変える案である。前者はMCPサーバープロセスに`CLAUDE_PID`が渡らないため成立せず、後者は同じディレクトリで複数の会話を同時に動かすと会話ごとの行を区別できないため採用しない。共有状態ごとの基準となる記録と、それを読み書きする処理の対応は`.claude/skills/agent-toolkit-edit/references/agents-server-shared-state.md`が定める。
Claude Codeが直接起動した`agents_server`は`root.json`を書き、委譲先の中で起動した`agents_server`は自身を収容するsessionの識別子を名前とするファイルを書く。
backendへ渡すrootはManagerの`StatusFileWriter.root_session_id`に統一する。環境にownerが無く生成されたrootも、Codex App Serverの子環境とthread開始・再開のMCP設定、host索引、Claude SDKの起動・再開、Antigravityの子環境へ渡す。backendごとに環境から解決するとManagerの保存先と通知先が分かれるため、その独立解決を撤去した。通知側の全root走査と手動環境設定は採らない。計画所有記録の解決は変更せず、Antigravity固有の通知元識別子取得と通知成功はこの配送の保証外とする。
収容sessionの識別子は、Claude backendの委譲先では`AGENT_TOOLKIT_DELEGATED_SESSION`が示すとおり自身の`CLAUDE_CODE_SESSION_ID`、Codex backendの委譲先では`CODEX_THREAD_ID`から取る。いずれも親の`agents_server`が公開する`session_id`と同じ値である。
Codex委譲先自身のシェルには`CODEX_THREAD_ID`が存在するため、Codex委譲先のシェルで動く待機処理と通知処理は共有状態ディレクトリを解決できる。PostToolUseフックの環境に`CODEX_THREAD_ID`が無い場合は、フック入力の検証済み現行session識別子を既存の書込主体解決へ補完し、同じ書込主体の`wait-targets`へ子sessionの開始とreply再開を登録する。フック入力を新しい台帳へ保存する案は、待機CLIとは別に基準となる記録を増やすため採用しない。
Codex backendが子のApp Serverへ`AGENT_TOOLKIT_OWNER_SESSION`を渡し、継承した`AGENT_TOOLKIT_DELEGATED_SESSION`を除く扱いと、その理由は`design-hosts.md`「ルールの配置と配送」にある。
一方、Codexホストから直接起動したMCPサーバープロセスは、所有session識別子とCodex thread識別子のいずれも持たないため状態ファイルを書かない。
所有session識別子だけが存在し、書込主体を識別できない場合も状態ファイルを書かない。
共通の`root.json`へ代替すると、活性化処理が同じ状態ディレクトリにある別の書込主体の記録を削除するためである。
書込側はsession状態の更新を1秒で集約し、自身の生存中のsession全体を原子的に全置換する。
ルートの書込主体はMCPの開始時にディレクトリ配下を空にして前回プロセスの残存を除き、終了時にディレクトリを削除する。入れ子の書込主体は自身のファイルだけを書き、終了時に削除する。
書込主体は状態ファイルのトップレベルへ生存の印`heartbeat_at`を置き、稼働中は一定間隔で更新する。読取側は`heartbeat_at`が失効した状態ファイルを表示から外す。書込主体は自身のflushのたびに、`heartbeat_at`が失効した他の状態ファイルを削除する。書込主体の異常終了では状態ファイルの回収も終端状態への更新も動かないため、生存の印を持たない設計では`status`が`running`のままのsessionが表示に残り続ける。状態ファイル名は書込主体のhost session識別子であり、同じ識別子が再び使われないため、後続の`agents_server`起動でも古い状態ファイルは除かれない。生存の印を持たない状態ファイルは、読取側の表示対象からも書込主体の削除対象からも外す。statuslineの実装とプラグインの実装は別々の仕組みで更新され、更新の順序を制御できない。印を持たないファイルを削除すると、旧版の書込主体が稼働中のsessionを次の状態変化まで書き直さないため、実在するsessionの表示が失われる。却下した代替案は、収容主体が子sessionの終端を観測した時点で子の状態ファイルを削除する案と、トップレベルの`updated_at`だけで失効を判定する案と、OSのプロセス生存確認を用いる案である。第1の案は収容主体が保持するagents_serverのsession識別子と、状態ファイル名が用いるhost session識別子が別体系であり、対応表を新設しないと対象を特定できない。第2の案は進捗の更新が届かない長時間のturnと書込主体の消失を区別できない。第3の案は読取側のstatuslineへOS別のプロセス照会を持ち込み、識別子の再利用を排除するために追加の情報を要する。
読取側はLinuxで`XDG_STATE_HOME`または`HOME/.local/state`、Windowsで`LOCALAPPDATA`から同じディレクトリを解決する。Python側の解決は`agent-toolkit/agent_toolkit/_common/state_paths.py`の`state_dir`だけが持ち、書き手と読み手が別のディレクトリを指さないよう、状態ファイルを扱う全ての処理がこの関数を使う。
複数のプロセスが排他に使うロックファイルは、同じモジュールの`lock_dir`が返す状態ディレクトリ配下の`locks/`へ置く。レビュー指摘管理表と監査のロックもここへ置き、`~/.claude`配下へは置かない。`agents-server/wait-locks/`は共有状態の登録と組で働くロックであり、`.claude/skills/agent-toolkit-edit/references/agents-server-shared-state.md`の構造に従って`locks/`の対象から外す。

`atk agents wait`が読む状態ファイルは表示と外部待機のための投影である。
取得済みのsession識別子は投影の消失後も保持し、結果または通知が無い間は`status: running`を返す。
待機開始後に投影、未回収結果、登録済み待機対象へ現れた識別子も、待機ロックを取得した巡回から同じ保持対象へ加える。
待機開始時から投影が空の場合も同じ非終端応答とする。投影の不在から`expired`を推論する案は、原子的な全置換、書込主体の終了および失効投影の回収を、権威あるsession喪失と区別できないため採用しない。
真の`expired`はsession登録簿を所有するMCPサーバーだけが判定する。

backendを開始した後の補助保存は、起動の成否と同じ成功条件に置かない。
2026年10月13日に、Windowsで`root.json`の置換がWinError 5で失敗し、起動した委譲先は正常終端した一方で`start`が例外を返した。起動応答の`session_id`を前提とするフックがcwdと所有を記録できず、同じsessionへの`send_message`と終了工程の待機判断が拒否された。
managerは開始済みのsessionについて、session登録簿と状態ファイルの射影をそれぞれ試み、失敗を`persistence_warnings`として起動応答へ加え、同じ`session_id`で続ける`next_action`を返す。登録簿は成功した値だけを公開済みとして覚えるため、次の状態更新と`flush`が保存を再試行する。表示用の状態ファイルの置換失敗は`ProjectionWriteError`で終端結果の保存失敗と区別し、予約した`flush`とheartbeatの失敗はログへ残して次回へ進む。`flush`に失敗した起動だけはmanagerが待機対象を登録するため、表示が空でも`atk agents wait`は当該sessionを待てる。`flush`が成功した起動は既存の表示とPostToolUseフックの登録を使い、登録の主体を増やさない。backendの起動前に不成立となった入力は起動済みとして登録しない。
停止時には終端の公開で生じた`ProjectionWriteError`だけをログへ残して後始末を続け、終端結果の保存の`OSError`は呼び出し元へ伝える。どちらの場合もlistenerの解除と状態ファイルの書込停止は`finally`で行い、表示の保存失敗が後始末を止めず、結果の保存失敗が成功として隠れないようにする。
共通の`atomic_write`は置換に失敗した例外へ置換元と置換先のパスを注記するため、各呼び出し側が既存ログへ記録するスタックに両パスが残り、診断のために別の状態を保存しない。
共通の`atomic_write`は原子的な全置換を保ち、置換段階のWinError 5・32だけを同じ一時ファイルで有限回（合計1秒未満）再試行する。上限後と対象外のエラーでは一時ファイルを回収し、旧本文を残して失敗を返す。読取ハンドルとの短い競合を待つ一方、恒久的な拒否も上限後は失敗として扱うためである。過去の競合主体は特定していないため、主体の種類で仕様を分岐させない。
この同期再試行をasyncioの予約保存とheartbeatから直接呼ぶと、待機中は他のtaskも進めない。非同期保存では、loop上でパス・本文・登録情報を確定し、ファイル操作だけを`file_operations.run_file_operation`でworkerへ渡す。共有session辞書、writerとタイマーはloopに残し、保存成功も取得したsnapshotへ対応付けて反映する。登録公開はsessionごとのtaskに集約し、保存中の更新を次の公開へ接続する。writerの保存と削除は直列化し、旧turnの成功を新turnへ反映せず、公開済み・回収済みの結果を再保存しない。公開応答の前に必要な保存を待ち、停止の取消時もworkerの終了と終端公開を回収してから状態ファイルを削除する。同期CLIの再試行回数・対象エラー・診断は変更しない。
`to_thread(self.flush)`で保存処理全体をworkerへ渡す案は、共有状態とタイマーの所有を別スレッドへ移して競合を増やすため採らない。別の保存queueや台帳も設けず、既存のtask、Lockとawaitによる保存境界を使う。
保存のdrainでは、並行したtaskの一部が失敗しても全workerの終了を回収してから失敗を伝える。最初の失敗で返ると、停止後の候補保存や状態ファイルの再作成が残るためである。
却下した代替案は、直接上書きへ変える案、表示用の状態ファイルの成功だけを維持する案、新しい台帳へ起動を記録する案である。1つ目は書込途中の本文を読取側へ見せ、2つ目は上限後の拒否で実際の起動が応答から失われ、3つ目は既存の登録簿と同じ情報を重複して保持する。

表示対象は終端結果を持たないsessionと、終端結果を持ち`results/<session_id>.json`が存在するsessionとする。statuslineは状態ファイルの各行について、終端状態であり対応する結果ファイルが存在しない行を描画から外す。保持期限（30分）に到達した行は書込主体が状態ファイルから外す。結果ファイルはこの時点では削除せず、前述の回収・破棄の契機まで残す。
実行中だけに限定しないのは、回収し忘れたsessionを可視化するためである。保持期限の到達後は表示を続けても回収の催促にならないため、行を外す。
ただし稼働中の子孫を持つsessionは、自身のturnが終端し、結果の回収や保持期限の到達で通常の条件から外れても、祖先の行として残す。委譲先が孫の終端を待つ間に子の行だけが消えると、孫が収容sessionを失った行として末尾へ移り、委譲のつながりを見失うためである。書込主体は同じルートの他の状態ファイルを読み、`host_session_id`と各sessionの`status`から稼働中の子孫を判定する。直下の子が終端していても、その先の子孫が稼働していれば祖先とみなす。保持期限で本体を解放したsessionも、退避済みの再開情報から行を出力する。statuslineも全状態ファイルの親子関係を解決してから結果ファイルの判定を適用する。表示する`status`は実際の終端状態のままとし、結果の再公開、保持期限の延長およびbackend資源の延命はしない。最後の子孫が終端するか、子孫の状態ファイルの`heartbeat_at`が失効すると、次のflushと描画から通常の条件へ戻る。却下した代替案は、子孫の稼働中は親の`status`を`running`へ書き換える案と、子孫の情報を集める台帳を新設する案である。前者は親自身のturn終端と結果の有無を表示から読み取れなくし、後者は状態ファイルと同じ親子関係を別の記録で重複して保持する。
入れ子の書込主体の行は、収容sessionの行の直後へ深さに応じて字下げして置く。収容sessionの行が無い場合は末尾へ置く。

## 終端結果の回収と待機ロック

子sessionへ送った`send_message`の公開応答が再開対象を示す場合は、そのsessionを再び追跡対象へ登録する。
親の待機表明は再開した子の終端まで保留する。
ClaudeとCodexの試験入力は、実際の公開応答を生成する処理から作成する。
起動時の子だけを追跡する案は、追送で再開した子を親の終端判定から失わせるため採用しない。

同じディレクトリ配下の`results/<session_id>.json`へ、終端したsessionの結果本文を原子的に書く。内容へsessionごとに1から始まり新しいturnの開始ごとに1増える`turn_seq`と、終端時刻の`finalized_at`を含める。終端結果を回収済みかどうかは`results/<session_id>.json`の存在だけで決める。回収は`agent-toolkit/agent_toolkit/_agents_server/retained_results.py`の`take_result`だけが行う。同処理は`results/.<session_id>.claim.lock`の排他ロックの内側で、結果本文の読取、公開した書込主体と所有者が一致するかの確認、ファイルの削除を1つの原子的な区間として実行する。所有者が一致しない場合は結果を返さず、ファイルも削除しない。`kill`、MCPの内部待機および`atk agents wait`はいずれも同じ`take_result`を経由して回収する。回収する各委譲元に、結果ファイルの読取と削除を個別に持たせない。読取と削除を別の呼び出しへ分けると、2つの処理が同じ結果を読んだ後に一方だけが削除でき、同じ結果が重複して配送されるためである。MCPサーバーは、一度書いた結果ファイルが消えている場合に結果を公開したsessionを回収済みとして扱い、消えた結果ファイルを再作成しない。保持期限（30分）はbackend資源とsession本体を解放する期限である。未回収の終端結果は期限の経過後も`atk agents wait`による配送か`stop`による破棄まで保持する。`atk agents wait`が`status`を`expired`とする応答を返すのは、期限を過ぎたsessionの結果が回収済みか存在しない場合だけである。同じsessionの新しいturnを開始する時点でも、前のturnの結果ファイルを同期的に削除する。削除は`send_message`と再開の応答を返す前に完了させるため、応答を受け取った呼び出し側は`atk agents wait`だけで再開したturnの終端を待てる。待機対象のturnの番号を引数で受け取る案は、呼び出し側が`turn_seq`を転記する必要を残し、転記の誤りによって、別のturnの結果を待機中のturnの終端として受領し得るため採用しない。`atk agents wait`は結果ファイルの確認と同じ周回で未回収の通知を回収し、結果を標準出力へ配送した場合だけ対応する結果ファイルを削除する。回収処理を1つに限ることで、同じ結果・通知を二重に配送しない。終端結果が未到達で通知だけを回収したsessionは、`status`を`running`とする行で返し、呼び出し側は再待機の要否を行の`status`で判定する。回収の途中で結果ファイルの読取に失敗した場合は、同じ巡回で回収済みの本文を先に標準出力へ配送してから非0で終える。回収は結果ファイルと通知ファイルの削除を伴うため、読取に失敗した時点で配送を取りやめると回収済みの本文が失われる。読取の失敗は次の起動でも同じ状態で現れるため、診断の報告を1回遅らせても失われない。`atk agents wait`は終端行の`agent_message`を呼び出しごとに作成するmanaged-tempのMarkdownファイルへもそのまま書き、その絶対パスを`agent_message_path`で渡す。各行には起動時の`label`も加え、出力を保存した場合の要約行は終端行ごとに、本文の`agent_message`と通知の`notices`を除く全項目（`label`、本文ファイルの所在、`error`、`next_action`など）を示す。委譲元が`session_id`から依頼名への対応表や、JSON文字列のエスケープを解いて本文を取り出す処理を持たずに結果を読めるようにするためである。要約行の項目は除外する項目の指定で決め、終端行へ加わった項目は要約行を作成する処理を変えずに現れる。項目を名前で選んでいた版では、失敗で終端した行の`error`と`next_action`が要約行に現れず、本文が空の失敗を委譲元が原因不明として扱い、利用上限で失敗したsessionへ継続を送った。`show`も終端したsessionが保持する空でない`error`を返し、結果を回収できなかった委譲元が原因を確かめられるようにする。`agent_message`は既存の消費側の互換のため行に残す。本文ファイルは配送より前に書き、書けない場合は回収途中の結果をrun別退避物と待機対象の登録に残したまま非0で終えるため、次の待機が同じ結果を再配送できる。終端行の`agent_message`を除いて出力を短くする案は、既存の消費側を壊すため採らない。Claude Codeの`/goal`はターン終了時に評価対象のセッションが起動した未完了のBashのバックグラウンドタスクが無い場合に目標評価を発動する。`atk agents wait`をBashのバックグラウンドタスクとして起動すると目標評価が延期され、委譲先の終端・上り通知でセッションが再開し、その標準出力だけで配送が確定する。MCPサーバーへ待機専用のツールを足す案は、追加した待機ツールの呼び出しも背景移行の対象となり目標評価の延期条件を満たさないため採用しない。

`atk agents wait`の待機所有権は書込主体につき1件とし、`wait-locks/<書込主体>.lock`のファイルロックで表す。先行待機は`wait-results/<書込主体>/<run_id>.json`へ実行中・公開済み・回収済みの状態を保存し、`current.json`へ現行run識別子を置く。同じ書込主体から2つ目の待機が発行された場合は、現行run識別子を固定してlock解放を待つ。後発はlock取得後に固定runの状態を読み直し、公開済みなら保存本文と終了コードを1回返す。先行待機が未公開の`running` runを残して終了した場合は、後発が同じrunの所有者となり、保存済み対象とrun別退避物を引き継いで結果または通知の回収を続ける。lock待ち中に先行待機が追加した対象も引き継ぐ。run記録を持たない旧形式のlockとの競合は診断を添えて直ちに終了コード8で返す。先行runを特定できる競合は、ロック取得待ちと結果待ちへ単一期限を適用する。異なる書込主体の待機は互いに遮断しない。却下した代替案は、対象sessionごとにロックを取る案と、回収処理をCLIとMCPで別々に持つ案である。第1の案は待機中に対象sessionが動的に増えるため、一部のsessionのロックだけを取得した状態が生じ、同じ書込主体の2つの待機が対象集合を分割して保持し得る。第2の案は所有者の一致確認と消費済み判定を定める箇所が2つに分かれ、片方の修正が他方へ及ばない。

待機対象が0件の終了（終了コード10）と、後続の待機による消費済みの終了（終了コード8）は、同じルートと書込主体の保存結果の所在を診断へ加える。
現行の待機runを指す索引`wait-results/<書込主体>/current.json`から、結果を保存した`<run_id>.json`を解決する。
診断の`run_path`はこの保存先の絶対パスであり、対象sessionと実在する本文パスも示す。
先行waitの継続実行を回収せずに再発行した場合も、保存済みの結果へ戻れるようにするためである。
ロック取得前に`get_cli_wait_timeout("main")`から単一期限を開始し、非ブロッキングの取得を繰り返す。
取得後の結果待ちには残時間だけを渡す。
競合が期限まで続く場合は終了コード8で、書込主体・固定run・対象・`run_path`と次の操作を返す。
先行待機の保存出力を読み、先行待機の終了後に再待機する。
保存出力を受け取れない場合は、`atk read-file`で`run_path`を読み、`output`の`agent_message_path`から本文へ到達できる。
取得失敗だけで原本・退避結果・先行runを破棄しない。
同時発行、ホスト識別子の別名、対象の追加と正常な長時間待機も同じ期限を使う。
runの`foreground-delivered`は結果を前景の呼び出し元へ返した状態、`consumed`は後続の待機が保存結果を再演して消費済みにした状態を表す。
どちらもエージェントの読了を記録しないため、診断は保存された結果の所在を示すにとどめ、自動で再配送しない。
runが無い、読めない、結果を含まない場合はその区別を診断へ返し、別の所有者のrunは復旧先にしない。
読了フラグを新設する案は配送後の読了を観測できず、結果を再配送する案は一度だけ回収する契約に反するため採らない。
知識境界として、終端結果の所有者の一致確認と一度限りの回収は`retained_results.take_result`が持つ。`atk agents wait`とMCPの内部待機は、待機対象の決定と応答の整形だけを担い、結果ファイルの読取と削除を自ら行わない。

## statuslineの表示

各行の左端は`label (engine:model/effort)`を表示し、Codexの最新turnがfast modeならmodel/effortの後ろへ`@fast`を付ける。effortが無ければmodelの後ろへ付ける。項目を持たない旧形式と他engineの表示は保持し、`label`が空の場合は起動区分を使う。採用したモデルの完全IDとeffortを状態ファイルから読み、設定時の候補表記と同じ形で示す。右端は経過時間、文脈使用量、状態の順に` · `で区切り、labelを重ねて表示しない。文脈使用量は委譲sessionの直近のモデル文脈のトークン数と、正の上限がある場合の使用率であり、Claude CodeのAgent行と同じ`subagent.rs`の`format_tokens`で描く。使用量の更新は活動時刻を進めない。モデル名を短縮して`model_type`を先頭へ置く案は、複数工程を段位へまとめた後に工程を識別できず、起動時に採用されたモデルの完全IDも失われるため採らない。
Claude Codeのstatuslineはメッセージ到着などのイベントでだけ再実行されるため、`wait`の待機中は表示が更新されない。
配布設定の`statusLine`へ`refreshInterval`を置き、待機中も経過時間と終端を反映する。
行の整形幅は、取得した端末幅からClaude Codeがstatuslineの描画へ確保する4セルを差し引いた値とする。4セルは各行の先頭へ付く2セルの字下げと、行末へ残す2セルである。差し引く値が実際の確保幅より小さいと、整形した行が溢れ、Claude Codeが行末を切り詰めて右寄せした経過時間と状態を欠く。確保幅は描画された行の表示幅（曖昧幅を1セルとして数えた値）と、statuslineの実行時に観測できる`COLUMNS`の値との差で求める。整形処理は右寄せ要素を整形幅の右端へ置くため、整形幅が実際の確保幅を超えた分は必ず右寄せ要素から失われる。このため、確保幅の値を単体テストの期待値としてだけ固定せず、描画された行の表示幅と`COLUMNS`の差を求め直す手順を確保幅の導出根拠とする。

稼働中sessionに`api_error`がある行では（Claudeの再試行とCodexの過負荷の待機の両方）説明欄へAPI失敗の種別、右端へHTTPステータス・失敗開始からの経過・件数を表示する。Claude Codeの利用上限の解除待ち（種別`usage_limit`）では待てば同じsessionで作業が続き、API再試行と対処が異なる。このため説明欄へ「利用上限の解除待ち」と種類、右端へ解除までの残り時間と待機の経過を表示する。限られた表示幅で診断を読めるよう、この間は通常のsession開始からの経過・status表示を診断項目へ譲る。`api_error`が無い行の説明欄は、最後に観測した行動を表す`last_action`を優先し、`last_action`が空の場合は`progress`を表示する。
`last_action`はassistantのテキスト出力ではその抜粋、ツール呼び出しではツール名とその呼び出しの入力を1行へ要約した値、Codex backendでは進行中itemの種別と同じ規則で要約したitemの入力を持つ。
入力の要約は、各項目を`<key>=<値>`の形でkeyの受信順に並べ、文字列以外の値をJSONへ直列化し、改行と連続する空白を1個の空白へ畳んだうえで200文字を超える分を省略記号付きで切り詰めた値とする。Codexのitemでは、`show`が別項目として返す`type`と`id`を要約から除く。
`show`が返す未完了のツール呼び出しの項目も同じ要約を`detail`として持つ。
テキスト出力の無い区間でも値が進むため、委譲先が稼働しているかを1行で読み取れる。
`last_action`は任意項目として読む。長命なMCPサーバープロセスは起動時に読み込んだモジュールを保持し続けるため、statuslineだけが先に更新される区間では`last_action`を持たない状態ファイルが書かれ続ける。`last_action`を必須項目にすると、statuslineだけが先に更新された間に実在するsessionの行が消える。
入力を含めるのは、同じツール名を繰り返す区間ではツール名だけの表示が変化せず、稼働中と停止中を区別できないためである。要約を上限で切り詰めるのは、statuslineが表示幅で再度切り詰める一方、`show`の応答では停滞の切り分けに足りる長さを残すためである。
却下した代替案は、`progress`だけを表示元として維持する案と、秘匿値の露出を避けるためにツール名とitem種別だけを表示する案である。
前者はテキスト出力の無い区間で説明欄が`label`のまま止まり、稼働しているかを判別できない。
後者では同じツールを連続して呼び出す区間で説明欄の値が変化せず、稼働と停止を区別できない。ユーザーへ示す稼働状況には、秘匿を理由に除外する情報を置かない。

知識境界として、session状態の意味（`status`、`progress`、`last_action`、結果の回収）は`agent-toolkit/agent_toolkit/_agents_server/state.py`が持つ。公開応答への射影は同じディレクトリの`result_projection.py`が持ち、状態ファイルはその射影である。
statuslineは状態ファイルを表示するだけで、sessionの制御と結果の回収をしない。

却下した代替案は、PostToolUseフックが記録する`agents_server_sessions`の状態を表示に流用する案と、状態ファイルを一時ディレクトリへ置く案である。
前者は`start`・`wait`の応答時点だけを観測し、実行中の進捗と終端を表示できない。
後者はPythonの`tempfile.gettempdir()`とRustの`std::env::temp_dir()`で環境変数の参照順が異なり、同じ環境でも別のパスへ分岐し得る。

## API失敗・過負荷・利用上限の待機

役割別のClaude接続選択では、API環境ファイルが持つ認証・接続・モデルの全キーを選択入力とする。
サブスクリプション起動では親環境と親settingsから同じキーを除き、API起動では選択したファイルの値を渡す。
新規・再開・接続切替は同じ解決を使い、未設定の通常認証と設定解除後の復帰を保つ。
一部の認証キーだけを除く案は、親の接続先とモデル指定が選択後の接続へ漏れるため採用しない。
秘匿値は診断へ保存しない。

Claude SDKの初期化応答がMCP接続失敗を示す場合、新規起動・再開ごとに公開再接続APIを1回試す。
SDK 0.2.168の`get_mcp_status`と`reconnect_mcp_server`を使い、未回復のサーバーだけをstart・showのwarningsへ返す。
ログは`claude_mcp_recovered`と`claude_mcp_recovery_failed`で回復の成否を示す。
再接続の反復を独自に増やす案は、SDKの回復境界へ別の待機を重ねるため採用しない。

接続選択のログは`claude_connection_attempt`・`claude_connection_selected`・`claude_connection_failed`を使う。
`phase`は`initialization`または`turn`とし、turnの理由は`authentication`・`api_credits`・`usage_limit`で区別する。
接続切替は`claude_api_switch`へ`previous`・`selected`・`reason`・`limit_type`を記録する。
いずれも選択と診断を示す情報であり、認証値は記録しない。

Codex接続先の優先順は`codex_model_providers`が持つ。先頭を主接続先とし、サブスク利用上限では後続の独立APIへ同じ会話を移す。API主接続の不受理も後続APIへ有限に進める。空設定はCodex通常設定に従い代替試行しない。
終端結果は既存の保留機構へ置き、MCPの監視が終端済みthreadのcold resume後に、
以前の会話と実行結果を確認して完了済み操作を繰り返さず未完了部分を続ける入力を送る。
未観測の孫や背景出力が残る場合はその待機を優先し、結果の帰属を維持する。
切替のための新しい上限台帳や監視は設けず、既存の監視と再開情報を使う。
APIへ移った会話の再開は新規起動の回復判定から独立させる。
接続先判定とcold resumeの詳細は[design-agents-server.md](design-agents-server.md#起動候補と観測identity)にある。

Claude backendが受け取るAPI失敗の合成assistantメッセージはモデルの活動を示さないため、`updated_at`を進めない。失敗の種別、取得できたHTTPステータス、連続失敗の初回時刻と件数だけをsessionに保持し、状態ファイルへ射影する。`show`と`list`は共通の射影から失敗の経過秒を算出し、通常のassistantメッセージで記録を削除する。これにより、再試行の受信で活動経過が短く表示される状態を防ぐ。親プロセスや外部ログから再試行を推定する案は、sessionの受信境界で既に失敗の種別を得られるため採用しない。
429の再試行中は同じsessionの終端または正常なモデル出力を待つ。`seconds_since_activity`はモデル活動がない間に増えるが、`api_error`が429を示す間はその値だけで委譲先を停止しない。診断の可視化と委譲先の置換を別の判断に分けることで、利用枠の回復後に同じ実行を継続できる余地を残す。
Codexのturnが`start`の可用性確認を終えた後にサーバー側過負荷（`codexErrorInfo`の`serverOverloaded`）で終端する場合がある。この場合は終端結果を既存の保留機構（`pending_result`と`awaiting_auto_resume`）へ保留し、待機の後に同じsessionへ継続の配送本文を新しいturnとして送る。2026年10月3日に、約4.85時間続いたレーン担当のturnが過負荷で終端し、14秒後の再送も過負荷で終わった。待機は15秒、30秒、60秒の最大3回とする（2026年10月4日、ユーザー指示）。上限に達しても解けない場合は最後の失敗を現行どおり公開する。このとき`_carry_over_unavailable_candidate`が候補を次回の起動の除外対象として記録し、委譲元の起動し直しで別のモデルへ移る。待機中は`status`を`running`に保ち、`api_error`へ種別`serverOverloaded`とHTTP状態の不明（`null`）、連鎖の最初の時刻と回数を記録する。この記録は`show`・`list`・状態ファイル・statuslineへ既存の射影で出力する。
対象を`serverOverloaded`へ限る。利用枠超過と流量制限は解除までの時間が応答から定まらず短い待機で解ける根拠が無く、Claudeの529は観測していないためである。可用性確認の間の過負荷は、会話の履歴を失わずに次の候補で起動し直せる既存の候補切替が扱う。未観測の孫sessionが残るturnは孫の待機を優先する。孫の終端後の再開本文が作業を再開させるためである。待機中の`kill`は新しいturnを始めずに最後の失敗で終端し、委譲元の`send_message`は保留を確定して自動継続を取り消す。

Claude CodeのWeekly limit（`seven_day`、`seven_day_opus`、`seven_day_sonnet`）と5時間の利用上限（`five_hour`）を、解除まで待つ対象とする。`claude_api_env_file`が未設定のとき、これらで拒否されたturnは解除まで待って同じsessionで続ける（2026年10月4日、ユーザー指示）。待てば確実に解除されるため、候補を切り替えると作業の文脈を失うだけで得るものが無い。Claude backendはClaude Agent SDKの`RateLimitEvent`から利用枠の状態・種類・解除予定時刻をsessionへ保持し、`SystemMessage(init)`より前に届いた報告もsessionの作成時に引き継ぐ。turnが失敗で終わり、最後の報告が`rejected`かつ上記の種類である場合は、結果を既存の保留機構へ保留し、`api_error`へ種別`usage_limit`、HTTP状態、最初の拒否の時刻、回数、種類（`limit_type`）と解除予定時刻（`resets_at`）を記録する。MCP層の常駐監視は解除予定時刻に同じsessionへ継続の配送本文を送り、再び拒否されれば待機へ戻る。解除予定時刻が無いか過ぎている場合は300秒ごとに確かめ直す。回数と総時間の上限を置かず、`auto_resume_deadline`と保持期限でも確定しない。正常なモデル出力で利用枠の記録と`api_error`を削除する。起動直後の可用性確認の間に解除待ちへ入った場合も候補を切り替えず、`start`は`running`を返す。待機中の`kill`は保留した結果（`error.usageLimit`に種類と解除予定時刻）で終端し、委譲元の`send_message`は保留を確定してreplyとして配送する。解除待ちの拒否は除外記録へ残さず、旧版がClaudeの429へ記録した理由`429`は候補を除外する根拠にしない。待機の対象外である`overage`などのClaudeの429は、理由を`429:<種類>`として記録し、従来どおり次の候補へ切り替える。判定にHTTP状態の429を使わないのは、429が利用上限と流量制限を区別せず、種類はClaudeが出力する利用枠情報だけが示すためである。過負荷の自動継続と回数上限を共有しないのは、過負荷が短時間で解ける見込みの事象であるのに対し、利用上限は解除予定時刻まで確実に続くためである。
Claudeの役割別接続候補は`_atk/claude_connection.py`へ集約し、`claude_api_env_file`を認証の所在、`claude_api_mode`を方針として分離する。
`claude_api_env_file`が未設定なら`inherit`接続を選び、親環境とClaude Codeの通常の認証解決を維持する。
認証検出による起動拒否、認証変数の除去、apiKeyHelperの上書き、役割別割当と接続切替を行わない。
可用性プローブ・本起動・再開を同じ接続種別で扱う。
未設定時に開始した会話と接続情報もAPIパスも持たない旧形式の会話は、後から設定しても通常の認証解決を使う。
以下の役割別接続管理はenvファイルを設定した会話に適用する。
既定の`pay-as-you-go`はオーケストレーターをAPIへ固定し、通常の委譲先をサブスクリプション、APIの順にする。
`api-credits`はオーケストレーターをサブスクリプションへ固定し、通常の委譲先をAPI、サブスクリプションの順にする。
通常のprocess-loopとall-reposのリポジトリ担当は同じ役割であり、起動手段がSDKでもオーケストレーターとして扱う。
認証手段が一方だけの場合はその接続を使い、空・不在・読取不能・形式不正のAPI環境ファイルを候補から除く。
直接起動のユーザー会話、Agentとfork、run-skill、commit、Codexの接続先はこの設定の対象外である。
オーケストレーターは接続を固定し、通常の委譲先は同じsession ID・model・effortで次の接続へ移る。
認証手段が一方だけの場合は既存の解除待ちを保ち、両認証を持つ全候補の失敗と認証なしを終端する。
新規sessionは毎回先頭候補から評価し、再開する会話は登録簿に保持した接続を使う。
利用上限でサブスクリプションからAPIへ移した委譲先は、上限の解除予定時刻（不明なら既存の待機と同じ既定の時刻）を会話の状態へ保持する。サブスクリプションが先頭候補のままなら、その時刻の後にClaude backendの`send_message`が始める最初のturnで同じ会話をサブスクリプションで再開し、なお上限なら既存の切替で再びAPIへ移る。対象のturnは追送と、孫sessionの終端・利用上限・過負荷の後の自動再開であり、いずれも同じ`send_message`を通るため判定を1か所に置く。接続は所有タスクの起動時に決まるため、上限でAPIへ移した場合と同じ再開の処理で所有タスクを起動し直す。CLIが自ら次のturnを始め得る待機（バックグラウンドタスクなど）の間は所有タスクを止めると作業を失うため、その待機の後にCLIが始めるturnは現在の接続で続き、次に`send_message`が始めるturnで戻す。

Claude Code 2.1.302の対話起動は、環境変数の未承認APIキーで「Detected a custom API key in your environment」の確認画面を表示する。
同版の本体は`customApiKeyResponses`による承認判定を持つ。
無人起動するAPIオーケストレーターはキーを環境変数へ直接置かず、所有者限定のsettingsファイルに`apiKeyHelper`を指定して選択したenvファイルから取得する。
キーの値をargvや登録簿へ保存せず、settingsファイルは子プロセス終端時に回収する。
親のAPI認証は環境変数と合成settingsの両方で隔離する。

サブスクリプション認証の検出は、`CLAUDE_CODE_OAUTH_TOKEN`、Linux・Windowsの設定ディレクトリにある`.credentials.json`のOAuth情報、macOSの`claude auth status`を使う。
macOSのKeychainエントリと`CLAUDE_CONFIG_DIR`の対応はCLI自身に解決させ、資格情報の値をログへ出力しない。
保存先は[認証の公式仕様](https://code.claude.com/docs/en/authentication#credential-management)、`authMethod`の判定値は[CLIの公式仕様](https://code.claude.com/docs/en/cli-reference#cli-commands)に従う。
接続先の保持とenvファイルを読む時機は[design-agents-server.md](design-agents-server.md#起動候補と観測identity)にある。

起動後の可用性失敗で、同じ会話の待機・接続先移行から回復できず終端した場合は、終端結果の`next_action`が前任IDを指定する引き継ぎ起動を案内する。

可用性失敗では除外記録の保持期間によらず前任候補を外し、設定順の後続候補を選ぶ。
作業自体の失敗には既存の継続・巻き取りの案内を使う。
後任は引き継ぎ記録を最初に読む指示、会話の流れ、委譲元の追送と各turnの最終応答全文、詳細照会手段を受け取る。
会話の流れと詳細の取得は既存のsession-reviewの記録抽出を使い、CLIを持たない後任へも読めるファイルを渡す。
Antigravityの前任は会話の流れに代えて`atk agents logs`の出力を使う。
後任のsession IDを新しい待機対象とし、完了済み操作と成果物を現物で確かめて残工程を続ける。
引き継ぎ起動は全engine・modeと起動後の全turnを対象にし、実行中の前任は終端を待つか`kill`する案内で返す。
サーバーが後任を自動起動する案は採らない。
前任の子sessionの所有と不要になった作業を引き継ぐ判断は委譲元にあり、後任IDへの対応付けも委譲元が行うためである。
起動時の候補切替、同じ会話の接続先移行、Claudeの解除待ち、終端後の明示的な引き継ぎをそれぞれの境界で扱う。

## 委譲先の起動失敗を待機側が観測できる状態

目的は委譲先の起動が失敗したときに、委譲元が失敗を短時間で受け取り、待機へ進んだ場合も待ち続けずに終わることである。
構造の理由は、待機と再試行の上限を、待機側が観測できる状態と呼び出し側が課す打ち切り閾値の双方から導出する点にある。
初期化の上限と試行回数の積は、起動直後の可用性失敗を待つ上限と直列に続く。この和がホストのMCPツール呼び出しをバックグラウンドタスクへ移す閾値を上回ると、委譲元は起動の失敗を受け取る前に待機へ進む。
待機側では待機対象の集合が待機中にも増えるため集合が空であることを即時の終了条件にできない。このため対象が0件である状態の継続に独立した上限を置き、対象0件の継続上限に達した実行は理由を標準エラーへ書いて非0で終える。対象0件の継続上限は、初期化の失敗が確定し得る最大の経過を上回る値とする。
知識境界として、上限値と導出関係は`agent-toolkit/agent_toolkit/_agents_server/state.py`の定数定義が持ち、待機側の分岐は`agent-toolkit/agent_toolkit/_agents_server/agents_wait.py`が持つ。委譲元が対象0件の継続上限による終了をどう扱うかは`agent-toolkit/skills/delegation/references/waiting-and-monitoring.md`と`atk agents wait`の公開説明が持つ。
対象が空であることを即時の終了条件にする案は、待機開始後に登録される委譲先を取りこぼすため採用しない。
待機側が`agents_server`の起動処理の進行状況を直接照会する案は、待機CLIと`agents_server`のMCPサーバープロセスの間へ新しい照会の仕組みを要し、既存の状態投影と待機対象登録簿に第3の観測面が加わるため採用しない。

## 委譲先の作業ディレクトリでのプラグイン起動の事前確認

目的は委譲先の作業ディレクトリでagent-toolkitのMCPサーバーとhookを起動できない状態を、委譲先を起動する前に委譲元へ返すことである。
委譲先のClaude Code・Codexは`agents_server`のプロセス環境を継承し、プラグインの起動コマンド（`uv`・`uvx`）を同じPATHと委譲先の作業ディレクトリから解決する。PATHの先頭にmiseのshimがあると、作業ディレクトリの未trustの設定でshimが失敗する。
Claude Codeはstdioサーバーの接続失敗をホスト共通の記録へ残す。新規起動・再開のプロセスごとに公開再接続APIを1回試し、未回復の失敗だけをstart/showの警告へ残す。成否は`claude_mcp_recovered`と`claude_mcp_recovery_failed`へ記録する。
`agents_server`は`start()`（全`mode`が経由する）と終端済みsessionの再開の直前に、委譲先の作業ディレクトリで`uv --version`と`uvx --version`を実行し、失敗時は子を起動せずに`cwd`と標準エラーを含む例外を返す。process-wiはメインの選定開始前に対象リポジトリのmise trustを準備する。
知識境界として、事前確認のコマンド集合は`agent-toolkit/agent_toolkit/_agents_server/launch_requests.py`の`PREFLIGHT_COMMANDS`が持ち、プラグインの起動コマンドを全て含むことを同モジュールのテストで確かめる。trustの判断は委譲元の手順（`agent-toolkit/skills/process-wi/references/selection-procedure.md`、`agent-toolkit/skills/process-wi/references/run-lanes.md`）が持つ。
MCP設定の`command`を絶対パスにする案は、`uv`の配置がホストとOSで異なり全エンドユーザーで共通の設定に固定できないため採用しない。委譲先のPATHからshimを外す案は、委譲先の作業ディレクトリのツール解決を失わせるため採用しない。`agents_server`が`cwd`を自動でtrustする案は、任意の`cwd`を受け取る`agents_server`がtrustの判断を担うことになるため採用しない。

## 無人セッションと人間の操作を前提とする機構

目的は`agents_server`が起動する委譲先を、人間の承認操作を要さずに起動できる状態に保つことである。
構造の理由は、委譲先が対話UIを持たない無人セッションであり、承認要求と権限申告のいずれにも応答する主体を持たない点にある。人間の操作を要しない条件は`launch_kind`とengineの種別に依存しないため、起動条件は起動区分で分けない。
claudeの委譲先では、権限モードをbypass系にすると、Claude Codeのセッション間メッセージの受信方針が、権限モードを申告しない送信側からのメッセージを保留する。委譲元は起動直後に権限モードを申告せずにメッセージを送るため、委譲先は保留のまま初期化を完了しない。このためbypass系以外の権限モードで起動する。
codexの委譲先では、hookの定義が変わると承認済みの記録が無効になり、実行前に承認を求める。このため`thread/start`と`thread/resume`のリクエストの`config`へ`bypass_hook_trust`を真値として渡す。
知識境界として、claudeの権限モードは`agent-toolkit/agent_toolkit/_agents_server/claude.py`、codexの設定は`agent-toolkit/agent_toolkit/_agents_server/codex.py`が持つ。
codexで同名のコマンドラインオプションを渡す案と、`-c`による設定上書きで渡す案は、いずれも`codex app-server`が`bypass_hook_trust`を受理しないため採用しない。
claudeで`crossSessionInbound`設定により受信を拒否する案は、追加設定ファイルとユーザー設定のいずれで渡しても初期化タイムアウトを解消しないため採用しない。

## agents_serverの上り通知の仕組み

目的は`agents_server`で起動した委譲先が自身のturnを終端させずに委譲元へ本文を届けられるようにすることである。これにより、想定外事象、エスカレーションおよび続行できない理由を委譲元がturnの終端前に受け取れる。`Agent`ツールとagents_serverのどちらで起動しても即時通知の可否がそろい、起動手段ごとに規範の適用結果が分かれない。
構造の理由は、engineに依存しない配送媒体が共有状態ディレクトリだけである点にある。Codexの委譲先にはagents_server系のMCPツールもフックの発火機構も公開されない。Claudeの委譲先にはagents_server系のMCPツールが公開されるが、委譲先のMCPサーバーは委譲元のsession登録簿を共有しないため、メモリー上の状態を介した配送は成立しない。`ListAgents`が返す宛先は表示名であり、委譲元のsessionを一意に指す識別子として利用できない。両engineの委譲先は環境変数`AGENT_TOOLKIT_OWNER_SESSION`と自身のsession識別子を保持するため、送信元と宛先を自力で解決できる。
送信は`atk agents notify`が担い、委譲元は`atk agents wait`の応答の`notices`で受け取る。CLI待機は終端前でも未回収の通知が現れた時点で復帰し、`status`を`running`のまま返す。委譲元は`status`だけで再待機の要否を判定し、`running`の応答では同じCLIを再発行する。終端と同時に未回収の通知が残る場合は、`completed`、`failed`、`interrupted`のいずれかを返す応答へ`notices`と終端結果をともに載せる。委譲元は終端結果と通知を含む応答を受け取り、両方の受領をまとめて完了する。応答へ載せた通知は状態ディレクトリから削除するため、同じ通知が二重に渡らない。
知識境界として、委譲先は宛先の解決と本文の送信だけを担い、回収の状態を持たない。委譲元は`atk agents wait`の応答だけから通知を受け取り、通知の取得のために別のコマンド、ポーリングまたは追加の待機ループを実行しない。
却下した代替案は、通知口をMCPツールとして追加する案と、フックの発火を主な手段とする案である。前者はCodexの委譲先にagents_server系のMCPツールが公開されないためengine横断で成立しない。後者はClaudeの委譲先だけが持つ発火機構であり、同じ理由で成立しない。委譲元が`atk agents wait`の外にいる間の通知は次の観測まで滞留するが、この滞留を解消するポーリングの導入は、通知の取得のために追加の待機ループを実行しないという要件と両立しないため採用しない。
