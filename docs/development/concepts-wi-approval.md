# 方針・意向: WIの確認と承認

## 確認と承認

2026年10月9日、ユーザーの全手順の見直し指示により、発行・委譲通知・受領・統合検収へ共通の確認要否判定を接続した。
2026年10月10日のユーザー指示と確認回答により、会話中の選択式の確認で回答を得た事項はその場で完結させ、回答を得ないまま終わった確認とターンを越えて残る判断・行動はモードによらず個別UWIへ保存する。
現行の規定は`agent-toolkit:user-confirmation-and-report`「手段の選択」にある。
読み手は各工程の実行主体とする。
原要求、現物、既存認可とQCDで確定する事項は自ら確定して報告し、ユーザーだけの選好・認可・適否・取得不能の入力が残る事項だけを問う。
以下の確認の時機とUWIの手段は、必要と判定した確認に適用する。
技術的受領不能、依存待ち、レビュー不成立と工程への到達だけで確認を発行しない。
メインは全受領事項の必要性判定と必要な発行の完了を検収し、確認不要の報告へUWIを要求しない。
要求取消と未認可の外部操作の保護は保持する。
現行の判定は`agent-toolkit:user-confirmation-and-report/references/user-confirmation-and-report-decisions.md`「確認要否の判定」が定める。
通知は`rules-subagent.md`、受領・統合は`exec.parent.md`と`run-lanes.md`が定める。

`source`の指定がない場合だけ本文を人間由来とみなし、値を持つ項目は全てエージェント由来とみなす。
計画、ユーザーコメント、UWI回答および出所付き対話回答に記録した要求単位の由来を優先する。
人間由来入力へ操作、対象、範囲が明記されていれば、その範囲の承認として扱う。
人間由来要求を全部または一部不採用にする場合は対話かUWIで確認する。
回答を得られなければUWIを保存し、採用済みの範囲があっても元項目を分割せずに、元項目の`depends_on`へUWIを加える。
回答を待つ元項目のファイル名と回答後の再開工程はUWIの本文が保持する。
UWIへ回答が保存されると、メインは回答済みのUWIと元項目を同じ処理回の対象へ加える。

人間由来要求の不採用は、原文との差異、技術的理由、代替案を示す`AskUserQuestion`へ送る。
回答を得られなければUWIを保存し、採用済みの範囲があっても元項目を分割せずに、元項目の`depends_on`へUWIを加える。
UWIへ回答が保存されると、メインは回答済みのUWIと元項目を同じ処理回の同じレーンへ割り当てる。
そのレーンが両方を終了する。
同一セッション中に回答を受領した場合は、回答保存を確認した後、メインの選定工程または同じレーンを一般継続契約で再開する。
部分採用はこの確認へ機械的に含めず、実施内容へ採用範囲、実施しない範囲、理由を記載し、要求別の採否詳細は内部採否記録に従う。
人間由来の本文か回答に外部操作、対象、範囲が明記されている場合は、その要求単位の範囲でユーザー認可として扱う。
source値だけの場合、空のコメント欄、エージェント推奨、一般的な進行指示は認可にしない。

- 事前承認と事後承認の区分は、確認を要する操作の性質で選ぶ。
  構造化質問かUWIかの手段の選択は`agent-toolkit:user-confirmation-and-report`へ集める。
  自律モードの事後承認は回答を待たずに続けられる事後承認型UWIへ記録する（2026年9月7日、ユーザー指示。確認のたびに作業が止まる運用を避けることによる）。
  回答を要する事前承認は、回答期限が働く実行環境ではその場で質問し、それ以外は事前承認型UWIへ記録して元項目をそのUWIへの依存で待たせる（2026年10月4日、ユーザー回答。回答待ちを保留でなく依存で表すのは、編集中の`hold`と区別できるようにする2026年10月のユーザー指示による）。
  2026年9月30日のユーザー指示は認識合わせスキルの自律モードでの質問を求めたものであり、確認手段全体をその場の質問へ広げたcommit 4b838401bfの一般化はエージェントの判断だった。
  経緯は[concepts-confirmation-decisions.md](concepts-confirmation-decisions.md#確認合意の運用)が持つ
- `agent-toolkit:process-wi`のレーン担当は、確認事項か事後承認の対象を必要な調査と検討の後に確定した時点でメインへ通知し、回答を待たずに進められる工程を続ける。
  メインは受領時にユーザー向けの粒度を確認し、確認かUWIを発行する。
  投入主体をメインに保ち、委譲境界で報告責務を失わない目的は維持する（2026年9月13日、ユーザー指示。委譲境界で報告責務が失われた障害に由来し、2026年9月21日のユーザー指示で即時通知へ変更）
- 実行主体が成果の適否を観測できない変更は、最善と判断する対応を実施して元の要求を終了し、適否を事後承認型UWIで問う。
  そのUWIへの回答で是正を求められた場合も同じ手順を繰り返し、是正の適否を観測できなければ新しい事後承認型UWIを投入する（2026年9月8日、ユーザー指示。画面表示の見え方など、実行主体が再現できない環境でだけ現れる結果を対象とする）
- 2026年9月7日の項目の軽重による処理形態の区分は翌8日のユーザー指示で改めた。
  現行の`agent-toolkit:process-wi single-lane`と`agent-toolkit:process-wi`は委譲によるレーン分けと並列実行の有無で使い分ける。
  単一レーンも計画を要する項目を処理し、同じ処理回で計画を起草してから実装する。
  2026年10月9日のユーザー判断により、single-lane-processは当面維持する。
  ユーザーは複数のリポジトリに少数のWIがある状態で使うことが多い。
  process-wiへ相当する動作を選択肢として組み込む案は、設計上は単純になるものの内部の条件が複雑になりそうだというユーザーの見込みから、いったん見送る。
  統合を恒久的に禁じる判断ではない
- `agent-toolkit:process-wi`側と共通規範は`agent-toolkit:process-wi single-lane`を名指しせず、同スキル側が共通契約の読み替えと上書きを持つ一方向の依存とする。
  スキル名はレーンへ分割せずメインが処理する機構を表す（2026年9月18日、ユーザー指示）
- 協調モードで動作するセッションからAWIまたはUWIを投入する主体は、本文が確定していない対象、適用範囲、外部可視の結果と除外内容の調査を投入前に完了する。
  確認の要否は調査の結果として判明するため、調査を投入後へ回さない。
  認識差で要件や結果が変わる未解決事項は回答を得てからAWIを投入する（2026年9月7日、ユーザー指示。2026年9月21日、ユーザー指示により確認対象を選好以外の要件差へ広げた）
- `agent-toolkit:add-awi-by-user`は`agent-toolkit:user-confirmation-and-report`の`references/grilling.md`が定める質問ラウンドで、ユーザーの選好で決まる未確定判断を解消する。
  起動時の登録依頼が成立しているため、解消後に本文の全文提示と投入可否の一律確認は行わない。
  新しい未確定要件が生じた場合だけ質問ラウンドへ戻る
  （2026年9月8日の確認不足の指摘と、2026年9月28日の現行スキルに合わせるユーザー回答に基づく）

作業中に見つけた独立した既存不良の即時対応は、その場で必要な箇所を直接修正して安全に利用できることを確認し、テスト・独立文脈レビュー・原因分析・類似見直し・再発防止などの正式対応を次セッション用のAWIへ登録することを指す。
この意味は2026年9月26日のユーザー指示に基づき、2026年10月23日の再指定で復元した。
正式対応AWIは作成した回の選定へ自動追加しない。
当初のWIが要求する完成条件、本作業で導入した不良と、その要求が含む類似箇所の是正は、当初の作業で完了する。
独立改善の反復費用は、不要作業を繰り返す具体的な工程や操作と削減量を修正・検証・統合負担と比較し、公開前に安全な受入先が成立する正式改善AWIだけを今回へ追加する。
登録済みと修正済みを区別し、保存済みの正式名を既存merge操作による全体確認と保存、同じ担当への追送へ接続する。
最小修正後に残る正式分析・テスト等は一律に今回へ追加せず、次回へ分けて元の工程を進める目的を保持する（2026年11月、反復費用改善の採用）。
2026年10月4日・9日のユーザー指示は、残工程の判断入力への作用を含めて直接修正の要否と時機を判定するものであり、正式対応を全て同じ回へ追加する根拠とはしない。
残る工程または次のセッションを停止・遮断する不良は必要な直接修正を先に行う。
2026年10月1日のユーザー指示による同じ担当の直接修正も、この扱いを使う。
担当交代、引き継ぎ、再起動、モデル・エンジン変更、別経路への迂回は可用性を回復する手段であり、不良そのものの直接修正とは分けて判定する。
回避後も次のセッションの停止が見込まれる場合は、正式対応AWIへ送る前に直接修正する（2026年10月31日、次のセッションが再び停止することも防ぐよう求めたユーザー指示）。
公開工程の開始後も、公開を妨げる不良と次のセッションを停止・遮断する不良を必要な手順で直接修正し、必要なら追加の統合・再公開を実施する。
判定と手順は`agent-toolkit/skills/process-wi/references/immediate-fix.md`が所有する。
単一レーンの読み替えは`agent-toolkit/skills/process-wi/references/single-lane.md`「見つけた既存不良の扱い」が所有する。
WIの完成条件の範囲外で見つけたユーザー向けの不足のうち、是正がバグの修正に当たるものは確認せず同じセッションで直し、新しい挙動の追加を要するものは今回の作業へ含めるか別の作業へ回すかを公開・リリースの前にユーザーへ確認する（2026年10月2日、ユーザー指示）。
ユーザーが把握しない機能が確認なしにリリースされることと、一緒に直したかった不足が知らされないまま元の変更だけがリリースされることの両方を防ぐためである。
ユーザビリティレビューが範囲外の観察として判定根拠から外した自動スクロールの欠如が、参考記録のまま別AWIへ回され、元の変更だけが公開まで進んだ観測に由来する。
バグと新しい挙動を分ける基準はユーザーがエージェントへ委ねた。
確認へ回答が無い場合は新しい挙動を保留したAWIと事前承認型UWIへ回し、元の変更は通常どおり公開する。
現行の規範は次の資料にある。

- `agent-toolkit:user-confirmation-and-report/references/user-confirmation-and-report-authorization.md`
- `agent-toolkit:user-confirmation-and-report/references/user-confirmation-and-report-questions.md`

承認区分は同スキルの`references/approval-scope.md`が定める。

### 経緯（確認と承認）

- 事後承認型UWIは自律モードでだけ用いる。
  協調モードの事後承認は、実施した対応を受け入れるかをその場の構造化質問で確かめる。
  ユーザーが指定した手段と明らかに異なる手段は、協調モードでは採用の前に確認する
  （2026年9月7日のユーザー指示。2026年9月12日のユーザー指示で加えた協調モードでも事後承認型UWIへ記録する例外は、2026年10月6日のユーザーの回答で実行前の確認へ改めた）

2026年10月30日のユーザー承認により、上記の起動スキルを統合し、単一処理は`agent-toolkit:process-wi single-lane`、登録全体は`agent-toolkit:process-wi all-repos`で選ぶ。
通常のレーン処理は引数なしで開始する。
