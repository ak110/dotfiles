# 公開の認可と短絡の設計記録

[設計記録の索引](design.md)から参照する主題別の記録である。

## 認可とCIの実行

手元で同じ失敗条件を観測できないCI修正は、認可済みの作業ブランチで先行CIを行う。
ローカルで再現できる修正にこの往復は加えない。
検証したSHA・ref・baselineと失敗ジョブの実行条件を対応付け、正式公開のcheck集合とは分けて検収する。
先行成功後の差分は影響範囲を再検証し、必要な実行レビューと認可を保持する。
すべてのpushを一律に二段化する案は、観測の不足がない修正にも待機と実行を増やすため採らない。

GitLabのCI定義不在、登録待ち、確定的な実行対象外は別の結果である。
CI Lintの対象commit・refで確定的なpipeline非生成だけを終了8へ分類する。
照会不能や他のerrorsを非生成と推定せず、既存の待機へ戻す。
受理側は非生成の証拠と同じHEADのローカル全体検証成功を確認する。

本文の明示記載を不可逆操作の認可とし、明記のない操作はUWIへ送る。
診断目的でCIを再実行した場合も同一baselineを監視し、許容回数の上限後に失敗が残れば、
CI未通過と帰属判定を終了記録へ残す。

GitHubのpush後CIは、baselineにない同一SHAのrunを監視対象とする。
ただし`event`が`dynamic`かつworkflow名が
`Dependabot Updates`であるrunは、対象pushへ帰属しない自動更新として除外する。
同名workflowの手動実行と、
他workflowの`dynamic`実行は除外しない。
SHA一致だけで除外すると手動診断の失敗を見逃し、workflow名だけで
除外すると起動契機の異なるrunを同一視するため、両fieldの積を境界とする。

## 公開工程の知識境界

メインは全レーンの統合結果、公開先、ユーザーの認可およびCI結果を知る。
レーンは担当commitと変更範囲の検証を知るが、他のレーンの完了状況や公開操作の認可を知らない。
固有指示で`adopt`を延期した項目は、指定されたベース反映後に完成条件を観測した担当が採否を確定する。
反映後の新プロセスでしか観測できない条件が残る項目は、観測を終えるまで`processing`を保つ。

この順序により、実装は公開操作と分離して進められ、公開対象を統合後の1つの変更集合へ固定できる。
レーンへ公開を委譲する案は、公開の重複と認可の分散を生むため採用しない。
明記のない不可逆操作を技術判断で補う案も、ユーザーの認可範囲を拡張するため採用しない。

## 公開の短絡と承認範囲

公開対象が1つも無いprocess-wiの実行では、公開担当を起動せずに公開工程を短絡する。
選定結果の項目は、レーン外操作、`上流投入`またはプロジェクト固有の公開後の操作の順序を持つものだけを数える。
レーンの統合による未公開のcommitは、記録した処理開始時のHEADと統合結果を比べず、公開状態の4項目のうち追跡refとのahead値（`# branch.ab`が`+0`でないこと）で検出する。
回答済みUWI、プロジェクト固有の公開後の操作および延期`adopt`も無い場合、公開担当が実行する版数更新、生成物同期、push、CI確認およびプロジェクト固有の公開後の操作は対象を持たない。
短絡の可否は、公開担当がpush後に観測するのと同じ4項目をメインが取得して判定する。
選定された通常レーンの件数を操作量とみなす案は、実装commitを持たないprocess-wiの実行まで公開工程へ送るため採用しない。

手動で起動した`agent-toolkit:atk-mode`の作業`process-wi`では、メインが固定したAWIの完成条件に操作、対象および外部可視の結果が明示された公開工程を、起動したセッションの承認範囲として選定工程で保持する。
レーン担当と公開担当が同じ範囲を要求する場合は再承認を求めず、範囲が広がる差分だけをユーザー確認する。
手動起動の指示はメインが固定したAWI集合の完遂を委任する指示であり、同じ範囲の承認を工程ごとに繰り返す運用はユーザーの操作を増やすだけで認可の範囲を変えないためである。
自動常駐起動を同じ扱いにする案は、起動時点でユーザーが対象集合を確認していないため採用しない。

## 維持する判断と戻さない条件

CI待機の省略手順は撤去済みである。
ユーザーが9月に特定のマージ後修正のCI待機省略を要求し、後に局所変更の即時公開の撤去を明示した。
複雑なCI待機の省略条件の撤去を維持し、公開に必要なCI成功と最終の公開状態の検収は省略しない。
CIの責務分離・composite action・pytestの3分割は維持する。
E2Eの分離はユーザー提案である。
必須checkの失敗伝播と、3分割で各試験が1回という品質を保つ。
更新後処理の並列化は別に評価し、CIの並列数を変更しない。
公開待機と並行する工程と、push前にCIと同じチェックを重ねない方針は、ユーザー指示である。
依存しない公開後工程だけを重ね、CI成功・公開結果の検収と認可の境界は短絡しない。
共通CIの所有判定（`common-ci-owner`）は、CI二重実行の解消と過剰設計を避けるユーザー要求による。
同じ公開対象の実検査を二重に実行せず、非所有の成功と所有判定の失敗を区別する。
post-applyの依存付きスケジューラーによる後処理の並列化は、2026年9月30日のユーザーの「遅すぎる。高速化してほしい（処理順の見直し＆並列化とか）」という要求と、確認回答「並列化と順序見直しだけ」に基づく。
同じ後処理の依存順序と失敗集約を保ち、効果を測らずに全体を順次実行へ戻さない。
2026年11月11日の同じ版・同じホストの交互測定を根拠に、並列化を保つ。
測定値と限界は[architecture-post-apply.md](architecture-post-apply.md)の「`post_apply.py`の工程間の順序」を参照。
