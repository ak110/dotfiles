# 方針・意向: 原因分析と再発防止

## 原因分析と再発防止の深さ

原因分析・類似見直し・再発防止の共通手順と判定基準は、`agent-basics:bugfix`の各資料を参照する。
共通の初動は`SKILL.md`と`references/root-cause-analysis.md`、根本原因と重大度は`references/root-cause-severity.md`に従う。
対策と影響範囲は`references/root-cause-actions.md`、類似見直しは`references/root-cause-remediation.md`に従う。
再発防止と完了は`references/root-cause-prevention.md`、記録は`references/analysis-records.md`に従う。
工程側は入力・認可・記録・検収・保存の契約を持ち、本節は共通手順を再定義せず判断の由来と導入目的を記録する。

2026年8月30日のユーザー指示は、事象の言い換えで分析を終えず、混入と見逃しの構造へ作用し、表面の異なる類似問題も防ぐ枠組みの見直しだった。
2系統の段階、止める根拠、処置の優先順位と再発防止の成立条件は共通定義が持つ。
2026年10月21日、ユーザーは外部コマンドの挙動を想像で決めたことを作り込み要因、実用シナリオを通さない単体レベルの試験を見逃し要因として扱い、個別事例より上の判断規則へ毎回一般化するよう求めた。
提供元Issueを含む一次資料と実機対照、最上位の公開操作から結果までのテスト到達範囲を原因分析へ対応付ける現行規定は`agent-basics:bugfix`とtesting規範が持つ。

2026年9月の呼び出し元の確定判断E-M1は、規範未適用と過去対策の反復を、条文の存在や段の違いだけで判定しないよう現行規範へ合わせた記録である。
E-M2は恒常コストに見合う案が無い場合も技術判断を確定し、評価の根拠をユーザーへ届ける扱いを記録した。
現在の選定と報告の手段はbugfixの「再発防止策の必須性」と`agent-toolkit:user-confirmation-and-report`が定める。

2026年9月26日、ユーザーは再発防止として規範の細則を積み増す対応をやめるよう求めた。
条文の改訂・統合、検出と想起性の改善を先に評価する判断は共通定義へ受け入れる。
現行出力や文言を固定する試験を再発防止の保証へ数えない扱いも、同じ原因を別入力で検出する導入目的に対応する。

2026年10月3日、ユーザーは配送済み規範への違反による停止や報告の欠落に対し、対策しない判断と手順の追記だけに任せることを否定し、Stopフックでの対策を提案した（対応commit `4862700e1`）。
この判断は実際の呼び出しや受理本文から確定できる不足を既存hookで検出する用途へ適用し、意味・品質・介入との関係を判定するエージェントの責任は保つ。
共通の再発防止策の選定と自動検出の境界はbugfixが持つ。

2026年10月10日、ユーザーは類似見直しと再発防止が機能せず同じ根本原因の問題が繰り返していると指摘し、両者を定義した。
類似見直しは今回の問題と根本原因を同じくする問題を全て直す活動、再発防止は根本原因を同じくする問題を今後再発させないための活動とする。
当時は成果物の品質（Q）に影響する全問題で、費用（C）と所要時間（D）を度外視して類似見直しと再発防止を必須とした。
この一律条件は2026年10月15日のユーザー指示による次段落の重大度別方針へ更新する。
母集団は根本原因が成立した時点以降の全作業へ及ぶことがあり、0件は観点か範囲の誤りの可能性が高いものとして再検討する。
ユーザーは共通の基準を複数の文書へ散在させずbugfixへ集約し、局所性や直接的原因などの条件で範囲を限定しないことも求めた。
読み手は問題対処と、類似見直し・再発防止の範囲・終了・費用比較を定める規範を改訂する全てのエージェントとする。
現行の規定は`agent-basics:bugfix`の`SKILL.md`「QとC・Dの区別」「再発防止策の必須性」にある。
同スキルの`references/root-cause-remediation.md`「類似見直し」、`agent-basics:bugfix/references/root-cause-actions-hierarchy.md`「処置の階層」も参照する。
`references/root-cause-prevention.md`「類似見直しと再発防止の完了」に従って完了を判定する。
他の文書は参照だけを持つ。

2026年10月15日、ユーザーは重大な問題では徹底した類似見直しと再発防止を保ち、軽微な問題ではgrepなどの限定探索と一定の検出不足を許容して終える方針へ更新した。
重大度は消費主体への影響、波及範囲、回復可能性で判断し、規範の一語でも危険な操作や認可境界へ及べば重大になり得る。
軽微な問題はQ影響なしへ分類し直さず、探索範囲・限界・許容する残存リスクを記録する。
同じ原因から導く母集団、既知の欠陥の是正、明示要件と硬い制約は保持する。
重大な問題でも機械的抽出と軽量段位の走査を使い、上位モデルによる全量走査は前提にしない。
2026年10月13日のユーザー指示による構成要素・完成条件の比例性は保持し、同月16日のユーザー回答で旧一律条件をこの重大度別方針へそろえる。
再発防止策の順位は同じ根本原因へ作用する案の比較に使い、新設する構成要素と観測手段を必要性へ対応付ける。
混入防止で見逃し要因も成立しなくなる場合は検出を重ねない。
技術判断をユーザーへ委ねない目的（E-M2）と、規範の細則を積み増さない判断（9月26日）は保ち、共通基準を1か所へ集約して他の文書の重複を参照へ畳む形で実現した。
`agent-basics:bugfix`の`SKILL.md`「初動と拡張原因分析の判定」が拡張原因分析の条件に該当しない不良を区分した目的は、自明な不良へ重い履歴調査を課さないことにある。
改訂後もこの目的は、分析の深さを根本原因の確定に必要な資料で選ぶ規定として保つ。
類似見直しの母集団と再発防止の要否は、分析の深さで狭めない。

同日、ユーザーは「ユーザーが指示したことをエージェントが勝手に狭めた」を再発させないことは対策であって再発防止ではないと是正し、縮小が起きた理由に対する類似見直しと再発防止を求めた。
処置の層は作用先で区別し、指示の縮小を防ぐ規範改訂は対策、縮小を成立させた構造（エージェントが自分の語で言い換えた集合の正しさを書いた本人の比較だけで保証すること）を除く改訂を再発防止策とする。
処置を再発防止策と書く記述には、記述先によらず作用する根本原因の単位を併記し、根本原因を確定する前は「原因分析後に確定」と書く。
ユーザーの範囲は原文を逐語で保ち、エージェントの記述を該当例・追加・承認の出所付きの除外に分ける書式で書く（`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「原文の保持と取り込み」）。

2026年10月11日、ユーザーは類似見直しの費用を抑えるため、履歴を遡って類似の問題を探す範囲を直近7日間に限ると選んだ。
履歴を遡らない対象は種類を問わず日付で除外せず、期間外の履歴は対処済みと認定せず見直し対象外とする。
適用時機は当初将来の見直しからと選ばれたが、後続の発話で処理中の全履歴点検にも適用すると変更された。
ユーザーは規範を細かく書かず読み手の常識に任せて簡潔に書くよう求め、区間の境界やタイムゾーンなどの細目は規範へ置かない。
現行の規定は`agent-basics:bugfix`の`references/root-cause-remediation.md`「類似見直し」にある。

同日、ユーザーは類似見直しの範囲と観点を確かめるため、今回の問題を伏せた新規担当の走査で、その問題が摘出されることを求めた。
未摘出は範囲か観点の誤りとして見直し、問題を知った担当の再利用や自分自身の走査で代えない。
この確認の適用も2026年10月15日の重大度別方針へそろえ、軽微な問題の限定探索へ一律に追加しない。
共通手順の所有者と、既存の類似見直しの記録先は前掲の規定に保つ。

2026年11月5日、ユーザーはすべての指摘・エラーで原因分析と類似見直しを必須とし、既存の仕組みで初めて検出された指摘・エラーだけ再発防止策を省ける方針へ更新した。
同じ根本原因の反復とユーザー介入での発覚は再発防止策を検討する。
類似見直しは、Git管理下のファイル・直近7日間のWI・直近7日間のセッションログを標準母集団とする段階検索と候補の個別判定で行う。
各段の検索式と件数を残し、0件なら別の語や観点で1回見直す。
検索に一致しない消費側や現存ファイルの全本文確認、重大な問題で起点の検出まで新規担当を反復起動する旧規定は、この絞り込み型の手順へ置き換える。
起点の具体的な事象・場所・修正を伏せた読取専用の担当が走査し、起点未検出時は検索条件を1回修正して再依頼する。
2026年10月15日の重大度別方針は、類似見直しを省く条件には使わず、母集団の広さと判定の深さへ反映する。
基準はagent-basics、専用担当の起動・3検索手段・受領はagent-toolkitが所有し、担当工程のモデルは中規模の読取・走査を担うchoresとする。

2026年11月3日、ユーザーは類似見直しと再発防止策が不十分で指摘が繰り返されること、原因分析の記録の「直接的原因」「原因分析の根拠」行が機能していないこと、回帰防止策が再発防止策と混同されることを指摘した。
これを受け、処置の記録を6区分（対策、回帰防止策、類似見直し観点と再発防止策の作り込み・見逃し各系統）に分けた。
4区分の候補は各1件以上とし、採否は候補とは別の2行（類似見直しの採否、再発防止策の採否）へ書く。
候補数は採用の下限ではなく、コストのかけ過ぎを避けるため、エンドユーザーへの影響（agent-toolkitとagent-basicsではエージェントの行動誤りを含む）、ユーザーの手間の増加、その他の順の影響度と総費用で採否と実施範囲を決める（同日のユーザー指示）。
直接的原因と根拠は原因分析表の該当セルと証拠参照へ統合し、原因と証拠の照合そのものは保つ。
現行の様式は`agent-toolkit:wi-standards`の`references/analysis-records.md`「原因分析の記録先」にある。
区分の定義は`agent-basics:bugfix`の`agent-basics:bugfix/references/root-cause-actions-hierarchy.md`「処置の階層」にある。

2026年11月7日、ユーザーはユーザーの手を煩わせた失敗（作業中の介入、WI記入欄での是正、不要な確認、必要な確認の欠落、余計な作業）を再発させにくくするため、再発防止策の費用比較でその損失を重く値付けする扱いを選んだ。
新しい問題区分の設置と、採用を既定として見送りに比較を課す扱いは、AWIと規範量（C・D）を増やすためユーザーが確認で退けた。
採否を費用対効果で決めること、QとC・Dの区分、2026年10月15日の重大度別方針、規範の細則を積み増さない2026年9月26日の判断は保つ。
現行の規定は`agent-basics:bugfix`の`agent-basics:bugfix/references/root-cause-severity-impact.md`「QとC・Dの区別」にある。

2026年11月13日、ユーザーは過去に指摘して直させた問題の再発が多いことを、次のとおり指摘した。

```text
ついでに、過去に指摘して直させたはずの問題の再発があまりにも多い。何か根本的におかしいのでは？
```

確定した原因は、是正が指摘された事象への条文や仕組みの追加で閉じ、後の変更が過去の決定を覆していないかを確かめる照合が働かないことである。
照合の入口である`concepts.md`が見出しだけの索引で、変更対象のファイル名や工程名で選んだ節としか照合されず、話題の違う決定が漏れていた。
`concepts.md`は各節の見出しの下に、その節で守る決定の要旨を置く形へ改めた。
