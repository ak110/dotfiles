# 方針・意向: 原因分析と再発防止

## 原因分析と再発防止の深さ

バグ、エラー、指摘への対応の手順と判定基準は`agent-basics:bugfix`が持つ。

現行の問いと記録の行は `agent-basics:bugfix` の「7つの問い」と「記録」を正本とする。
以下の過去の決定には当時の選定順と旧記録の形式を含む。
現行では文言・出し方と仕組みを効果・弊害・費用で比較し、種類による優先は設けない。
旧形式は読み取りと原因分析を変えない編集でだけ受け付ける。

### 2026年11月16日〜18日の決定（WI `20261116-004950-001.md`）

ユーザーは、bugfixが呼ばれるべき場面で呼ばれない、対応が過剰になる（前提を疑えていない）、回帰防止・類似見直し・再発防止が足りず同じ問題が繰り返す、と指摘し、手順を原理原則から整理し直すよう求めた。
確定した点は次のとおりである。

- 原則は6つである。
  逸脱は直す対象である前に情報である。
  原因は観測で確かめ、確かめていない部分は推測と呼ぶ。
  直し方は「無くす、単純にする、直す、足す」の順に比べる。
  観測した1件は標本として扱い、同じ仕組みの他の箇所と、同じ害への既存の対策を探す。
  元の失敗を観測した方法で、直ったことを確かめる。
  修正は通常の変更であり、成果物の品質基準を新規の変更と同じに適用する。
- 記録を書くのは「書き出す場面」の6つ（ユーザーの指摘、2回目の修正、足す処置、期待の側を変える処置、完了の報告か公開の後の発見、大きい害）に限る。
  既存の検査が初めて見つけた単純な誤りは、記録を書かずに直す。
- 原因分析の表2つ（2系統とL1〜L4の表、処置の表）は廃止し、記録は5つの問いへの答え（`期待:`・`原因:`・`処置:`・`広がり:`・`確認:`と`再発防止:`、条件が成立した時の`再発:`）にする（`再発防止:`の常設は2026年11月23日の改訂）。
  表は深さを求めたが、実例の誤りは広さの不足（期待は正しいか、他の箇所はどうか、より小さい直し方は無いか）だった。
  保存済みの旧形式は読み取りと、原因分析を変えない編集で受け付ける。
- 履歴を遡る範囲の上限（直近7日）は、費用の歯止めとして保つ（2026年10月11日の決定）。
  現存するファイルは日付で除外せずに検索するため、同じ害への既存の対策が今回も破られた場合は、古さによらず再発と判定できる。
- あらゆる問題の対処はbugfixの起動から始める（2026年11月15日の決定を保つ）。
- 過去のbugfixへのユーザーの言及は作り替えを縛る条件から外し、過去の問題の再発を防ぐ結果は保つ。
- 規範や計画に書いてあることで充足とせず、実際に有効に機能しているかを確かめる。
  修正のたびに、まず検査か構造で防げないかを比べる（2026年11月17日のユーザー指示）。
  再発防止は`prevention.md`「案を比べる」に従い、差分を契機にする確認項目も、文言・出し方や仕組みと同じ軸で比べる。
- 逸脱を報告する前に、今回の事象へbugfixを適用する。
  以前に本文を読んだことは、今回の適用の代わりにならない（2026年11月16日のユーザー指示「問題が起きたなら必ずbugfixスキルで対策・再発防止して」）。

### 再発防止の必須化（2026年11月23日）

2026年11月23日、ユーザーはbugfixの対処が再発防止になっていないと指摘し、bugfix自体が再発防止を決まりにしていないことを問うた。
11月18日の作り替え（commit `c332cc9a6`）で再発防止が5つの問いから外れ、記録の`再発防止:`行が「検討した場合は」の任意になっていた。
同じ作り替えで記した「再発防止は必須のまま」とも一致していなかった。
過去の発話（10月29日〜11月22日の13件）で繰り返されたのは、再発防止を行わない・書かないこと自体だった。

- 問い4を「広がりと再発防止」にし、原因が違っても同じ害を今後起こさない策を毎回決める。
  問いの数（5つ）と他の文書からの参照は変えない。
- 記録の`再発防止:`行は書き出す場面で常に書く。
- `send_to_user`は、bugfixの記録（`期待:`・`原因:`・`処置:`）があり`再発防止:`の行が無い報告を送信前に差し戻す。
  11月22日に入れた送信後の警告は、語の手掛かりに当たらない報告の欠落を見逃し、欠けた報告がユーザーへ届いていた。

### 対策の種類の語（2026年11月24日）

2026年11月24日、ユーザーは採用した対策に効果不足が多いと指摘し、有効だった型と効果不足の型をbugfixで例示するよう求めた。
採用後の効果を判定済みの記録を読み比べると、判断時に文書を思い出すことに頼る型が効果不足の例に繰り返し現れた。
母集団は調査期間内の判定済みの記録に限り、元の記録はリポジトリ外にある。

- `prevention.md`に、効果不足の型と代わりに選ぶ型を実例の対で置く。
- `再発防止:`の行は対策の種類の語で始める。
  AWIの原因分析は保存時に検査し、メインの報告の`再発防止`の行は送達前に`norm_excuse_gate`が検査する（既存の規則を理由に見送った報告が言い回しの検出をすり抜けたため）。
  保存済みの記録と計画の検査は、種類の語の欠落を許容する。

bugfixの`SKILL.md`と確認観点を変える時は、`.claude/skills/agent-toolkit-edit/references/agent-documents.md`「agent-basicsとの責務境界」の確認（確認観点の末尾の失敗例を変更後の本文へ当てる）を行う。

- `SKILL.md`は7つの問い（期待、原因、対策、回帰防止、類似見直し、再発防止、確認）だけで実施できる短い手順とする。
  確認観点は、条件が成立した時だけ読む6本の資料（`premises.md`、`causes.md`、`similar-review.md`、`recurrence.md`、`prevention.md`、`ci-failures.md`）へ外に出す

### 是正を受けたターンの送達と終了

是正後、送信前に対策・回帰防止・類似見直し・種類付きの再発防止を求めるのは、完了報告の種類を指定した送信、報告の見出しを持つ送信、再発防止の行を含む送信に限る（2026年11月26日の改訂）。
進捗や補足まで書き直させず、ターンの終了時は同じ発話に対応する送達済みの報告か、最終応答の行を確認する。
回帰テストは策として挙げたときに差し戻し、語を説明に使ったことだけでは差し戻さない。

### 保つ過去の決定

- 再発防止は、原因の違いを問わず同じ害を将来起こさない処置を指す。
  今回の原因・現象だけを防ぐ処置は対策か回帰の試験とする（2026年11月13日）。
- 採否は費用対効果で決め、技術判断としてエージェントが確定する。
  防げる損失には、ユーザーが同じ種類の指摘や是正を繰り返す手間を重く数える（2026年11月7日）。
- 害の大きさ（エンドユーザーへの影響、波及の範囲、回復できるか）は、まだ見つかっていない問題を探す深さへ反映する。
  既に分かっている欠陥の是正、明示された要件、硬い制約は、害の大きさによらず保つ（2026年10月15日）。
- 害が大きい時は、起点の事象を伏せた独立の担当による走査で、探す範囲と観点を確かめる。
  起点を検出できなければ検索の条件を1回直し、検出まで担当を増やして繰り返さない（2026年10月11日、11月5日）。
- 再発防止として規範の細則を積み増さない（2026年9月26日）。
- 是正が条文や仕組みの追加だけで閉じ、過去の決定との照合が働かないことを、反復する再発の原因として扱う。
  `concepts.md`は各節の見出しの下に、その節で守る決定の要旨を置く（2026年11月13日）。

### 再発防止のやり方（2026年11月18日）

2026年11月18日、ユーザーは作業契約・委譲と起動のプロンプト・規範・記録が膨らみ続けることを繰り返し指摘し、再発防止の扱いを次のとおり是正した。

```text
問題が起きたら再発しないようにしなければならないのは当然でしょ？ そのやり方が間違ってるから肥大化しているだけで。
```

再発防止は必須のまま、そのやり方を改める。
防止策は条文・工程・選択肢の削除や統合でも成立し、規範が適用されなかった事象では周囲の記述を減らす案を、目立たせる追加より先に比べる。
過去の処置で再発を防げなかった場合は、その処置をやめる・置き換える・単純にする案を先に比べ、重ねる場合は残す理由を示す。
規範を足す費用には、同じ時点で読む他の条文を埋もれさせる影響を含める。

同じ日、ユーザーは実行レビューの往復が続いた事象を受けて、規範と仕組みの関係を次のとおり示した。

```text
結局、いくら規範にあれやれこれやれって書いても仕組みが伴ってないと勝手にスキップしちゃうんだよね。
それを踏まえて規範を最小限にして、かつ機械的チェックとか書かせるとかもコストを意識しつつ慎重に足していくしかない気がする。
```

```text
「書く欄」は有効だけどそれを増やし過ぎると遅くなって本末転倒なのでそれにも気を付けてね。できるだけ書く量は短く済む形にした方がいい。例えば今回の場合、範囲より件数だけにするとかは？
```

規範は最小限にし、行動を確実にしたい場合は散文の規定を足すのでなく、機械的な検査や記録の欄などの仕組みを、読込・記入・実行の費用と比べて選ぶ。
記録の欄は件数や決まった値など短く書ける形にし、欄を足すたびに記録が遅くなる費用を比べる。

同じ日、ユーザーは外部の投稿（<https://x.com/iwashi86/status/2122827128957988995>）の要旨を次のとおり引用し、今後の改善の方向とするよう指示した（本文はユーザーの引用で、投稿は取得していない）。

```text
経験上、最先端のフロンティアモデルでさえ、ショートカットをしたり、楽な方法を選んだりする傾向がある
だからこそ、作ってきたスキルの多くは、「どうすれば『楽なやり方』を『正しいやり方・最善のやり方』にできるか？」という点に集中している
```

```text
今後はそういうのを踏まえて改善していくような方向にしてね。
```

改善では、正しい手順を求める規定を足す前に、正しい手順が最も手間の少ない手順になる形を探す。
例は、指定を省いた時に正しい値が使われるようにする、公開コマンドが正しい形の入力だけを受け付ける、手順をまとめて工程を減らす、正しい手順を妨げる手間を撤去する、などである。

### 規範の追加と母体の見直し（2026年11月22日）

2026年11月22日、ユーザーは外部の投稿2件（<https://x.com/steveruizok/status/2124233664326467953>、<https://x.com/RayFernando1337/status/2124222002076733869>）の実施を求め、エージェントが履歴から再発防止を行う手順のスキルを足すだけで済ませようとした時に、次のとおり是正した。

```text
規範追加だけじゃなくて見直し自体もやってね？？
```

```text
これに限った話じゃないけど規範を追加しても母体に規範に違反したものがあると後続のエージェントはそれを真似るから意味が無いんだよ。規範を追加するなら見直しも合わせてやらないと。
```

規範（基準、規約、手順）を足す変更では、同じ変更で既存の成果物から新しい規範への違反を探して直す。
実行時の規定は`agent-basics:writing-standards/references/quality-principles-subtraction.md`（原則9）にある。
努力目標の規定を新しく書く記述にだけ適用するとしていた例外（`quality-principles-constraints.md`「規定の区分と標示」、`agent-documents-additions.md`「既存対象への波及」）は、同じ日に撤去した。
履歴から繰り返す誤りを洗い出す手順は`agent-basics:harden-from-history`にあり、各段の対策で既存の同じ型の誤りも直す。
