# 計画の作成要否と成果物基準の設計記録

[設計記録の索引](design.md)

## 計画の作成要否と成果物基準の一本化

計画を作るかは入力の起票経路で決める。
`source`が`add-awi-by-user`・`process-user-comments`・`implement`のAWIは、投入前レビューを経て実装に入れる詳細度を持つため、本文をそのまま計画として使い、計画ファイルを作らない。
それ以外のAWI、作業を伴う回答済みUWI、リポジトリを変更する協調モードの依頼では、同じ詳細度・書式（AWI本文と同じ節とfrontmatter）の文書を計画ファイルとして作る。
process-wiでは`pick-wi-check`が選定結果の各WIへ`計画要否`を付け、担当は、本文の前提が成り立たなくなった時、人間由来の要求を縮める時、要求変更で再開位置を`なし`へ切り替えた時だけ、計画なしのAWIを計画へ含める。
入力にWIが無い作業でも、バグ対応でなく、既存の値や文字列の差し替えだけで完結し、検討候補が構造上生じない変更では省く。
2026年11月24日のユーザー指示（AWI以外の経路から始める作業ではAWIと同じ書式の文書を作り、計画ファイルの場所へ置いてatk serveの計画ファイル画面で詳細を確かめる）による。

置き換えた2026年11月16日の決定は、4事項（何をどう変えるか、外部仕様、完成条件、バグ対応の原因分析）が本文と現物から決まるかを担当がAWIごとに判定する形だった。
計画なしの経路は4事項の所在を引き継ぎ記録へ事項ごとに書く手順を求めて手間が多く、2026年11月23日〜24日の保存済みの計画ではほぼ全てのレーンが計画を作り、add-awi-by-userのAWIだけのレーンでも計画が要約の再掲になった。
前回`source`で分ける案を退けた理由（他経路のAWIも同じ登録条件で起草される）は、他経路の入力ではAWI書式の計画を作るという今回のユーザー指示で置き換わる。
他経路のAWIは、詳細度が足りていても計画を作る側へ倒れ、逆向きの取り違え（計画が要るのに作らない）は起きない。

計画ファイルを全て無くし、詳細化をAWIへの追記で行う案は、入力にWIが無い作業の基準になる文書が無くなり、協調モードの作業で先にAWIを作る手順へ1本化しない2026年9月30日のユーザー回答と両立しないため採用しない。
今回の形は計画ファイルを残してAWIと同じ書式にするため、協調モードの作業はAWIを作らずに計画で進められ、同回答と両立する。
計画の`## 実施内容`・`## 検証`・`## 進捗ログ`は廃止した。
採否はAWIと同じく`## 反映内容と反映先`と`## 調査結果と判断根拠`へ、検証コマンド・検証結果・進捗・再開の情報は計画の有無によらず引き継ぎ記録へ、予測補正記録は対象AWI本文へ書く。
前回これらの欄を残した理由（`atk lane integrate`の検証コマンドの読み取り、採否の検査、中断後の再開）は、検証コマンドがmanifestから渡り、再開が引き継ぎ記録とcommit履歴で足りることを確かめたため当たらない。
進捗ログを計画にだけ残すと計画ありと計画なしで記録先が分かれるため、同日のユーザー指摘を受けて残さなかった。
保存済みの表付き形式と更に古い形式は、読み取り、`plan-check`、進捗ログの追記、対応commitの記録で受け付ける（`plan-legacy-formats.md`）。
例外なく作成する案は版数などの機械的な差し替えに検討を強いる。
従来の複数基準を併存させる案は判断の所有者を分散させるため採用しない。
レーン担当は初版の起草前に`plan-format.md`を全文読む。

計画ファイル固有の要件の追加先は同書へ置く。
要求の書き方の定義元は[計画ファイルの体裁の扱い](concepts-workflows-lanes.md#計画ファイルの体裁の扱い)のとおり`awi-body.md`とその条件別資料の1か所である。
関連WIか計画の`## 完成条件`（入口からの操作と期待結果）を実装前の具体化と自己検収の比較元にし、試験選定は`writing-standards/references/testing.md`が所有する。
利用目的と後続行動を入口からの操作と期待結果の対応付けへ含め、要求の字面と内部構造だけで期待結果が決まることを防ぐ。
別の台帳や専用評価工程を設ける案は、既存の計画・実装・レビューで判断を共有できるため採らない。
凍結済み計画の書き換えを要件にしない。
ユーザーが明示した対象、範囲または外部可視の結果との差は、対応する確認済み回答でだけ確定でき、回答がない計画から実装へ進まない。

明示要件との差を管理する確認状態を新しい表で永続化する案は、既存の確認済み回答とレビュー完了時の判定で要件を満たし、状態の二重管理と別の失敗要因を増やすため採用しない。

知識境界は次のとおり分ける。
`plan-format.md`、`plan-storage.md`、`plan-legacy-formats.md`は作成された計画が満たす成果物要件だけを持つ。
要求の書き方は`awi-body.md`とその条件別資料が持ち、計画ファイルの基準へ再掲しない。
`agent-toolkit:atk-mode/playbooks/write-plan.md`は調査から起動形態ごとの終了までの工程制御だけを持ち、成果物契約は作成基準を参照する。
起動主体は渡す資源の絶対パスを工程の開始時に1回解決し、同じ工程では同じ値を使う。
解決した資源が実在しなくなった場合は、担当が差し戻し、起動主体が資源を利用する工程を終了する。
plugin導入版の更新は稼働中のセッションへ反映されず、同一セッション内で現行の版を取得する手段がないためである。
保存TSVの構造は既存の実装・テストの基準を維持するが、レビュー担当が私有実装の探索で操作書式や実行対象を補わない境界を設ける。

新しい計画は変更履歴を持たず、ユーザーの発言は`## ユーザー指摘の逐語引用`へ書き、起草中の経緯は残さない。

作成基準を独立スキルとして新設する案は、計画ファイルが`agent-toolkit:atk-mode/playbooks/write-plan.md`経由でのみ作成されて自動発火の利益が無く、
スキル一覧のdescriptionが恒常的にコンテキストを消費するため採用しない。
検出側だけにある要件をレビュー担当の`<役割名>.subagent.md`へ最小追記する案は、完成条件と点検リストの二重管理が残り、
将来の要件追加で同じ非対称が再発するため採用しない。
