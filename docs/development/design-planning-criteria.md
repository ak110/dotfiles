# 計画の作成要否と成果物基準の設計記録

[設計記録の索引](design.md)

## 計画の作成要否と成果物基準の一本化

リポジトリを変更する作業は、新しく始めるレーンと作業の全てで、対象WIの一覧だけを持つ計画を作る。
計画の中身は対象WIの本文に置き、`source`が`add-awi-by-user`・`process-user-comments`・`implement`のAWIは投入前レビューを経た本文をそのまま使い、それ以外のAWIは計画を作る時点で同じ粒度へ詳細化して本文を置き換える。
回答済みUWIは一覧に残し、作業を伴う回答は同じレーンの元のAWIへ反映するか、元のAWIを持たない時だけ詳細化済みのAWIを保留で保存して一覧へ加える。
WIの無い協調モードの依頼も、同じ粒度のAWIを保留で保存して一覧に載せる。
process-wiでは`pick-wi-check`が選定結果の各WIへ`詳細化要否`を付け、`plan-check`は一覧のWI本文を読んで詳細化済みの印を検査する。
入力にWIが無い作業でも、`agent-toolkit:atk-mode/playbooks/write-plan.md`「計画ファイルの作成要否」の省略条件に当たる変更では計画もAWIも作らない。
省略条件は、バグ対応以外で、既存の値か文字列の差し替えだけで完結し、保存する継続的な方針も見直す既存箇所も構造上生じないことである。
2026年11月26日のユーザー指示（計画ファイルは対象WIのリストだけにし、add-awi-by-userで作っていないWIは計画を作る時点で詳細化して置き換える）による。

置き換えた2026年11月24日の決定は、他経路の入力からAWIと同じ書式の計画を作り、計画を作る入力が複数あれば1つの計画にまとめる形だった。
詳細化が要る入力が複数あると、その内容を1つの計画へ書き写すため、WIと計画で情報が繰り返された。
同日のユーザー回答の意図は入力ごとにAWI相当を作ることであり、計画への書き写しは回答の取り違えだった（2026年11月26日のユーザー指摘）。
計画を全てのレーンで作るのは、add-awi-by-userのAWIだけのレーンでも実行レビュー指摘管理表と対応記録の置き場を計画と同じstemの1か所にそろえるためである（一覧だけのため作る費用はほぼ無い）。

採らなかった案は次のとおり。

- add-awi-by-user等のAWIだけのレーンでは計画を作らない案: 管理表と対応記録の置き場が計画のstemと別名の2系統に残る。
- 詳細化した内容を計画側に持ち、WIは要約だけにする案: 情報の二重化が残る。
- 選定時にメインが詳細化する案: 直列のメインに集中し、レーンで並行できる調査を失う。

詳細化はprocessingのAWIの本文を置き換えるため、2026年9月8日の決定（処理中の要求の書き換えを拒否する）の例外として、処理中の担当自身による着手前の1回だけを`atk wi edit --detail`で受け付ける（[`atk`の出力と操作](concepts-workflows.md#atkの出力と操作)）。
`plan-check`を通した後は一覧の全AWIが印を持つか詳細化の対象外のため本文は凍結され、実行レビューは実装と同じ版を読む。

計画の`## 実施内容`・`## 検証`・`## 進捗ログ`は2026年11月24日に廃止し、検証コマンド・検証結果・進捗・再開の情報は引き継ぎ記録へ、予測補正記録は対象AWI本文へ書く。
前回これらの欄を残した理由（`atk lane integrate`の検証コマンドの読み取り、採否の検査、中断後の再開）は、検証コマンドがmanifestから渡り、再開が引き継ぎ記録とcommit履歴で足りることを確かめたため当たらない。
保存済みのAWI書式、表付き形式と更に古い形式は、読み取り、`plan-check`、進捗ログの追記、対応commitの記録で受け付ける（`plan-legacy-formats.md`）。
例外なく作成する案は版数などの機械的な差し替えに検討を強いる。
従来の複数基準を併存させる案は判断の所有者を分散させるため採用しない。
レーン担当は初版の起草前に`plan-format.md`を全文読む。

計画ファイル固有の要件の追加先は同書へ置く。
要求の書き方の定義元は[計画ファイルの体裁の扱い](concepts-workflows-lanes.md#計画ファイルの体裁の扱い)のとおり`awi-body.md`とその条件別資料の1か所である。
対象WIの`## 完成条件`（入口からの操作と期待結果）を実装前の具体化と自己検収の比較元にし、試験選定は`writing-standards/references/testing-design.md`が所有する。
利用目的と後続行動を入口からの操作と期待結果の対応付けへ含め、要求の字面と内部構造だけで期待結果が決まることを防ぐ。
別の台帳や専用評価工程を設ける案は、既存の計画・実装・レビューで判断を共有できるため採らない。
凍結済み計画の書き換えを要件にしない。
ユーザーが明示した対象、範囲または外部可視の結果との差は、対応する確認済み回答でだけ確定でき、回答がない計画から実装へ進まない。

明示要件との差を管理する確認状態を新しい表で永続化する案は、既存の確認済み回答とレビュー完了時の判定で要件を満たし、状態の二重管理と別の失敗要因を増やすため採用しない。

知識境界は次のとおり分ける。
`plan-format.md`、`plan-storage.md`、`plan-legacy-formats.md`は作成された計画が満たす成果物要件だけを持つ。
要求の書き方は`awi-body.md`とその条件別資料が持ち、計画ファイルの基準へ再掲しない。
`agent-toolkit:atk-mode/playbooks/write-plan.md`は調査から起動形態ごとの終了までの工程制御だけを持ち、成果物契約は作成基準を参照する。
起動主体は渡す資源の絶対パスを工程の開始時に1回解決し、同じ工程では同じ値を使う。
解決した資源が実在しなくなった場合は、担当が差し戻し、起動主体が資源を利用する工程を終了する。
plugin導入版の更新は稼働中のセッションへ反映されず、同一セッション内で現行の版を取得する手段がないためである。
保存TSVの構造は既存の実装・テストの基準を維持するが、レビュー担当が私有実装の探索で操作書式や実行対象を補わない境界を設ける。

新しい計画は本文を持たず、ユーザーの発言は対象WIの`## ユーザー指摘の逐語引用`へ書き、起草中の経緯は残さない。

作成基準を独立スキルとして新設する案は、計画ファイルが`agent-toolkit:atk-mode/playbooks/write-plan.md`経由でのみ作成されて自動発火の利益が無く、
スキル一覧のdescriptionが恒常的にコンテキストを消費するため採用しない。
検出側だけにある要件をレビュー担当の`<役割名>.subagent.md`へ最小追記する案は、完成条件と点検リストの二重管理が残り、
将来の要件追加で同じ非対称が再発するため採用しない。
