# 計画の作成要否と成果物基準の設計記録

[設計記録の索引](design.md)と[計画と実行レビューへの受渡しの設計記録](design-planning.md)から参照する主題別の記録である。

## 計画の作成要否と成果物基準の一本化

計画ファイルの作成要否は`agent-toolkit:write-plan`が定める。
対話型、単一レーン処理と複数レーン処理は同じ基準を使う。
計画は要求の採否、恒久化・リファクタリングの検討と再開位置をエージェントへ渡す内部資料であり、原則として作成する。
既存の値や文字列の差し替えだけで完結し、検討候補が構造上生じない変更では省く。
必要時だけに限定する案では、単一ファイルの設計変更が計画の対象から外れる。
例外なく作成する案は版数などの機械的な差し替えに検討を強いる。
従来の複数基準を併存させる案は判断の所有者を分散させるため採用しない。

計画ファイルの成果物契約は`agent-toolkit/skills/write-plan/references/`の3文書だけで定め、他の文書へ再掲しない。
3文書は`plan-file-standards.md`、保存と参照の`plan-file-storage.md`、保持・復元を伴う契約の`plan-restoration-contracts.md`である。
レーン担当は初版の起草前に`plan-file-standards.md`を全文読み、計画ファイルへの要件の追加先を同書へ一元化する。
同書の受入シナリオ表を実装前の具体化と自己検収の比較元にし、試験選定は`writing-standards/references/testing.md`が所有する。
利用目的と後続行動を既存表へ組み込み、要求の字面と内部構造だけで期待結果が決まることを防ぐ。
別の台帳や専用評価工程を設ける案は、既存の計画・実装・レビューで判断を共有できるため採らない。
新規作成と改訂は7列表とし、保存済みの6列表は旧列名の形式も含めて読取互換を保つ。
凍結済み計画の書換えを要件にせず、新規作成・改訂時の移行診断で区別する。
計画なしとレビュー修正でも同じ要求由来の選定を使い、実行レビューへ根拠を渡す。
ユーザーが明示した対象、範囲または外部可視の結果との差は、対応する確認済み回答でだけ確定でき、回答がない計画から実装へ進まない。

明示要件との差を管理する確認状態を新しい表で永続化する案は、既存の確認済み回答とレビュー完了時の判定で要件を満たし、状態の二重管理と別の失敗要因を増やすため採用しない。

知識境界は次のとおり分ける。
`plan-file-standards.md`と分けた2文書は作成された計画が満たす成果物要件だけを持つ。
`agent-toolkit:write-plan`のSKILL.mdは調査から起動形態ごとの終了までの工程制御だけを持ち、成果物契約は作成基準を参照する。
作成基準は現行の一ファイル書式を扱う。
レビュー指摘管理表の操作書式は`atk review-table --help`および使用するサブコマンドの`--help`を公開の定義とし、
レーン担当は自身が解決したplugin rootの`plan-file-standards.md`、分けた2文書と`check_plan_file.py`を用いる。
起動主体は渡す資源の絶対パスを工程の開始時に1回解決し、同じ工程では同じ値を使う。
解決した資源が実在しなくなった場合は、担当が差し戻し、起動主体が資源を利用する工程を終了する。
plugin導入版の更新は稼働中のセッションへ反映されず、同一セッション内で現行の版を取得する手段がないためである。
保存TSVの構造は既存の実装・テストの基準を維持するが、レビュー担当が私有実装の探索で操作書式や実行対象を補わない境界を設ける。

計画の変更履歴、進捗ログおよびレビュー指摘管理表は、人間の変更確認、中断再開および個別指摘管理という異なる利用シナリオを持つ。
件数またはラウンド数で相互比較しない。

作成基準を独立スキルとして新設する案は、計画ファイルが`agent-toolkit:write-plan`経由でのみ作成されて自動発火の利益が無く、
スキル一覧のdescriptionが恒常的にコンテキストを消費するため採用しない。
検出側だけにある要件をレビュー担当の`<役割名>.subagent.md`へ最小追記する案は、完成条件と点検リストの二重管理が残り、
将来の要件追加で同じ非対称が再発するため採用しない。
