# 計画の作成要否と成果物基準の設計記録

[設計記録の索引](design.md)から参照する主題別の記録である。

## 計画の作成要否と成果物基準の一本化

計画ファイルの作成要否は`agent-toolkit:atk-mode/playbooks/write-plan.md`「計画ファイルの作成要否」が定める。
対話型、単一レーン処理と複数レーン処理は同じ基準を使う。
計画は要求の採否、検証と再開位置をエージェントへ渡す内部資料である。
AWIを入力とする作業では、本文と現物から何をどう変えるか、外部から観測できる仕様、完成を判定する条件、バグ対応なら確定した原因分析の4事項が決まれば計画を作らない。
決まらない事項がある時だけ、足りない部分だけを書く計画を作る。
4事項は通常AWIの登録条件が登録前に確定を求める事項と同じであり、条件を満たした本文へ計画を作ると、同じ要求を別の書式で書き直すことになるためである。
判定は`source`の値ではなく本文で、AWIごとに行い、複数のAWIを1つのレーンで扱う時も計画が要るAWIだけを計画へ含める。
入力にWIが無い作業は原則として作成し、既存の値や文字列の差し替えだけで完結し、検討候補が構造上生じない変更では省く。
2026年11月16日にユーザーが例として示した案から、エージェントが条件と書式を決めた（経緯は[計画ファイルの体裁の扱い](concepts-workflows-lanes.md#計画ファイルの体裁の扱い)）。

新しい計画ファイルは、H1と直下の要約、`### 計画メタ情報`、`## 実施内容`、要求を書く節、`## 検証`、`## 進捗ログ`の順に持つ。
要求を書く節は通常AWIの本文と同じ見出し・順序（`## 反映内容と反映先`を必須とし、`## 原因分析`、`## 調査結果と判断根拠`、`## 完成条件`、`## ユーザー指摘の逐語引用`は内容がある場合）とし、構造の検査も通常AWIの本文と同じ検査を使う。
計画ファイル（バグ）（`<計画名>.bugs.md`）は新しくは作らず、計画本体の`## 原因分析`に書く。
保存済みの8節形式とそれ以前の形式は、読み取り、進捗ログの追記、対応commitの記録で受け付け、書き換えない。
作成済みで実装中の8節形式の計画は、その形式のまま完了できる。

必要時だけに限定する案は、単一ファイルの設計変更が計画の対象から外れるとして以前は採らなかった。
現行の条件は変更の規模ではなく4事項が本文で決まるかで判定し、設計判断が本文で決まっていない変更は規模によらず計画へ回すため、この理由に当たらない。
例外なく作成する案は版数などの機械的な差し替えに検討を強いる。
従来の複数基準を併存させる案は判断の所有者を分散させるため採用しない。
計画がWIを名前で参照して重複を避けるだけの形を続ける案は、AWIごとの計画の起草・検査・保存と、計画の規範の読込（通常の計画1件の保存までに14ファイル・912行。`20261116-000421-002.md`の棚卸し）が残るため採用しない。
計画ファイルを全て無くし、詳細化をAWIへの追記で行う案は、入力にWIが無い作業の基準になる文書が無くなり、協調モードの作業で先にAWIを作る手順へ1本化しない2026年9月30日のユーザー回答と両立しないため採用しない。
`source: add-awi-by-user`のAWIだけを計画なしにする案は、振り返りやAWI処理の中で登録されるAWIも同じ登録条件で起草されており、同じ粒度の本文に計画を作る重複が残るため採用しない。
計画の全ての欄をAWIの本文と同じにし、採否・検証コマンド・進捗を引き継ぎ記録へ移す案は採用しない。
統合時の検証コマンドの読取（`atk lane integrate`）、人間由来の要求の採否の検査、中断後の再開が計画の欄を使っており、移す先の形式を新しく定める必要があるためである。
規範の重なりは要求を書く節にあるため、コードが読む欄（計画メタ情報、実施内容、検証、進捗ログ）は残す。
計画ファイルの基準の文章だけを短くし、節の構成を変えない案は、要求を書く決まりがAWIの本文の定義と計画ファイルの基準の2か所に残るため採用しない。

計画ファイルの成果物契約は`agent-toolkit/skills/atk-mode/references/plan-format.md`（形式）と`plan-storage.md`（保存と参照）で定め、他の文書へ再掲しない。
2026年11月までは、廃止したwrite-planスキルの3文書（計画ファイルの基準、保存と参照、保持・復元を伴う契約）が同じ契約を持っていた。
要求を書く節の書き方は、`plan-format.md`が`agent-toolkit/skills/atk-mode/references/awi-body.md`とその条件別資料を参照する。
定義元が1か所である点で、2026年8月の成果物契約の一元化（[計画と実行の運用](concepts-planning.md#計画と実行の運用)）を保つ。
レーン担当は初版の起草前に`plan-format.md`を全文読む。
計画ファイル固有の要件の追加先は同書へ、要求の書き方の追加先は`awi-body.md`とその条件別資料へ一元化する。
関連WIか計画の`## 完成条件`（入口からの操作と期待結果）を実装前の具体化と自己検収の比較元にし、試験選定は`writing-standards/references/testing.md`が所有する。
利用目的と後続行動を入口からの操作と期待結果の対応付けへ含め、要求の字面と内部構造だけで期待結果が決まることを防ぐ。
別の台帳や専用評価工程を設ける案は、既存の計画・実装・レビューで判断を共有できるため採らない。
新しい計画は受入シナリオの表を持たず、保存済みの7列表と6列表（旧列名の形式を含む）は読取互換を保つ。
凍結済み計画の書換えを要件にしない。
計画なしとレビュー修正でも同じ要求由来の選定を使い、実行レビューへ根拠を渡す。
ユーザーが明示した対象、範囲または外部可視の結果との差は、対応する確認済み回答でだけ確定でき、回答がない計画から実装へ進まない。

明示要件との差を管理する確認状態を新しい表で永続化する案は、既存の確認済み回答とレビュー完了時の判定で要件を満たし、状態の二重管理と別の失敗要因を増やすため採用しない。

知識境界は次のとおり分ける。
`plan-format.md`、`plan-storage.md`、`plan-legacy-formats.md`は作成された計画が満たす成果物要件だけを持つ。
これらが持つのは、計画メタ情報、実施内容、検証、進捗ログ、凍結後の訂正、保存、検査、旧形式の読み方だけである。
要求の書き方は`awi-body.md`とその条件別資料が持ち、計画ファイルの基準へ再掲しない。
`agent-toolkit:atk-mode/playbooks/write-plan.md`は調査から起動形態ごとの終了までの工程制御だけを持ち、成果物契約は作成基準を参照する。
作成基準は現行の一ファイル書式を扱う。
レビュー指摘管理表の操作書式は`atk review-table --help`および使用するサブコマンドの`--help`を公開の定義とし、
レーン担当は自身が解決したplugin rootの`plan-format.md`、`plan-storage.md`と`check_plan_file.py`を用いる。
起動主体は渡す資源の絶対パスを工程の開始時に1回解決し、同じ工程では同じ値を使う。
解決した資源が実在しなくなった場合は、担当が差し戻し、起動主体が資源を利用する工程を終了する。
plugin導入版の更新は稼働中のセッションへ反映されず、同一セッション内で現行の版を取得する手段がないためである。
保存TSVの構造は既存の実装・テストの基準を維持するが、レビュー担当が私有実装の探索で操作書式や実行対象を補わない境界を設ける。

計画の進捗ログとレビュー指摘管理表は、中断再開と個別指摘管理という異なる利用シナリオを持つ。
件数またはラウンド数で相互比較しない。
新しい計画は変更履歴を持たず、ユーザーの発言は`## ユーザー指摘の逐語引用`へ書き、起草中の経緯は残さない。

作成基準を独立スキルとして新設する案は、計画ファイルが`agent-toolkit:atk-mode/playbooks/write-plan.md`経由でのみ作成されて自動発火の利益が無く、
スキル一覧のdescriptionが恒常的にコンテキストを消費するため採用しない。
検出側だけにある要件をレビュー担当の`<役割名>.subagent.md`へ最小追記する案は、完成条件と点検リストの二重管理が残り、
将来の要件追加で同じ非対称が再発するため採用しない。
