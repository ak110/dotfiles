# SSEとサーバー停止の設計記録

[設計記録の索引](design.md)と[画面統合とセッション・計画一覧の設計記録](design-serve.md)から参照する主題別の記録である。

## SSEと接続維持

SSEは`/api/events`（AWI）、`/api/plans/events`（計画ファイル）、`/api/sessions/events`（セッション）へ画面ごとに分けた。
単一のエンドポイントへまとめると、ある画面の更新が他の画面のクライアントにも再取得を促し、表示中でない画面の更新で不要な再読込が起きる。
通信を分けることで、購読者集合と配信契機を画面ごとに閉じられる。
却下した代替案は、単一のSSE通信で種別付きイベントを配信し、クライアント側で振り分ける案である。
サーバー側の購読者集合が画面をまたいで1つになり、片方の画面の配信不良が他方へ波及するため採らない。

3画面のSSEは、通知の無い間15秒ごとにheartbeatを名前付きイベント`event: heartbeat`として送る。
コメント行のheartbeatはリバースプロキシの無通信タイムアウトを避けられるが、ブラウザーの`EventSource`はコメント行をスクリプトへ渡さない。
このため接続が途中で止まり、エラーも通知も届かない状態になると、画面は古い表示のまま待ち続ける（放置後やスリープ復帰後に観測された）。
名前付きイベントは`onmessage`へ届かないため、既存の通知処理に再取得を起こさない。
計画ファイル画面とセッション画面は`pytilpack.sse.generator`を使い続け、内側の生成器が間隔内にheartbeatを送るため、同デコレーターのコメント行は送られない。

ブラウザーは接続の確立、heartbeat、通知のいずれかを受けた時刻を記録し、heartbeat 3回分（45秒）を超えて何も届かない場合は接続を閉じて再接続する。
判定時間はサーバーがbootstrapへ埋め込み、heartbeatの間隔と同じ定義から導く。
再接続した接続の確立時には、各画面が一覧と表示中の項目を取り直す。
ワークアイテム画面のSSEは購読の登録直後に`event: subscribed`を1回送り、画面はこの合図を受けてから初期取得を始める（合図が300ミリ秒以内に届かない場合は待たずに取得する）。
`EventSource`の`open`は応答ヘッダーの受信時点で届き、サーバーの購読登録より先になり得る。
合図の後に取得した内容は、以後の変更を通知で受け取れるため、最初の接続では一覧を取り直さない。
ページを開くたびに初期取得と同じ全件の取り直しが重なり、直後の操作（保存など）と競合していたためである（2026年11月7日の計測で取り直し1回175〜722ミリ秒）。
初期取得を始めた後に届いた合図と、再接続の合図では従来どおり取り直す。
無通信の判定と再接続、`pagehide`で接続を閉じて`pageshow`（bfcacheからの復帰）で再接続する処理は共通モジュール`static/common.js`の`connectEvents`へ集約し、3画面は受け取るイベントの処理だけを渡す。
あわせて、タブが表示へ戻った時点（`visibilitychange`）の再取得も同じモジュールの`resyncWhenVisible`で3画面の契約をそろえる。
停止の原因（通信断、スリープ復帰、プロキシの挙動など）を特定しなくても、この判定は表示を最新化する。
接続の維持を`EventSource`の自動再接続だけに任せる案は、エラーを伴わない停止を検知できないため採らない。

## サーバーの停止

サーバーの停止要求（`ServeState.request_shutdown`）では処理中の全要求、スレッドで動く読み取り専用の走査、単発SSHの子プロセスおよびリモートの常駐接続を打ち切る。
hypercornは停止時に`server.wait_closed()`で全接続の終了を待ってから`graceful_timeout`を適用し、Python 3.12以降の`wait_closed`は接続が残る限り戻らない。
`asyncio.run`の終了処理はイベントループのdefault executor（`asyncio.to_thread`などが使うスレッドプール）のスレッドの終了を待つため、要求をキャンセルしてもスレッドの走査が続く間は停止しない。
systemdが`KillMode=control-group`でcgroup全体へSIGTERMを送ると常駐SSHも同時に終わり、常駐接続は`after_serving`でキャンセルされるまでバックオフの後に再接続し、処理中のRPCは単発SSHへ切り替わる。
これらのいずれかが残ると停止がその完了まで待ち、systemdの停止タイムアウトによる強制終了を招いていた（2026年9月30日の観測。SSEの購読接続、一覧・検索の処理中の要求、再接続した常駐SSHの各条件で再現した）。

要求の打ち切りはアプリのASGI呼び出し（`app.asgi_app`）を包む1箇所で行い、停止要求が要求の完了より先なら処理タスクをキャンセルし、応答を開始していなければ503で完了する。
リクエストの種類ごとに停止要求を参照させると、今後加えるリクエスト処理で同じ待ちを作り込むためである。

3画面のSSEの生成処理は`serve/state.py`の`next_subscription_item`で停止要求を待って購読を解除し、ASGIの打ち切りより先に応答を完了する。

スレッドの走査（セッション一覧、計画ファイルの一覧と本文検索）は停止要求の写し（`threading.Event`）を反復ごとに確かめて打ち切り、計画ファイルの一覧は途中までの観測で作成日時の索引を更新しない。
単発SSHは`asyncio.create_subprocess_exec`で起動し、キャンセルされたら子プロセスを終了してから送出する。
常駐接続は停止要求の時点で停止を始め、`after_serving`からの停止は停止済みの状態として受け取る。
WIの変更処理とGitの定期同期は途中で止めると作業ツリーを壊し得るため、`BoundedWorkers.run`の`asyncio.shield`で完了を保つ。

停止要求から一定時間後に`os._exit`で強制終了する案は、監視を停止せず、`after_serving`で後始末しないまま終了するため採らない。
読み取り専用の走査をデーモンスレッドへ移して終了時に待たない案は、計画ファイルの作成日時の索引の書き込みの途中で強制終了され得るため採らない。
