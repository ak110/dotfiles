# 反映後の観測と再開の設計記録

[設計記録の索引](design.md)と[担当の責務と工程間の知識境界の設計記録](design-workflow-boundaries.md)から参照する主題別の記録である。

実装と公開が済んでも、新しいMCPプロセスの配送など反映後にしか観測できない完成条件が残る場合がある。
項目をinboxへ戻すと計画からやり直すため、観測だけが残る項目には計画の有無によらず再開区分・実装commit・残る完成条件・観測手段・観測できる最も早い時刻を持つ再開記録をAWI本文へ追記し、次の実行のメインがその最後の記録から観測のみの再開位置を返す。
計画を持たない項目は引き継ぎ記録が次のセッションへ届かず、AWI本文だけが再開の手掛かりを運べるためである。
観測できる時刻が先の項目は再処理抑制期限を付けてinboxへ戻し、時刻が不明な項目はprocessingを維持する。
計画を持つ項目は保存済み計画を`~/.claude/plans`へ戻して再開位置を進捗ログへ記す。
process-wiの次の実行は実装を重ねず、新プロセスでの観測結果だけを終了へ渡す。
元の専用worktreeは回収済みなので、観測のみの再開では計画本文を凍結し、進捗ログだけを再保存する。
公開担当が公開までを検収し、反映と観測の継続はメインが担う。

観測できたが完成条件を満たさなかった項目は`adopt`せず、`再開区分: 再実装へ戻す`の再開記録を追記して再処理抑制期限なしでinboxへ戻し、次の実行が通常の項目として計画から着手する。
観測の結果は満たす・満たさない・観測できなかったの3つに分け、扱いを`agent-toolkit:process-wi/references/run-lanes-completion.md`「採否の確定と終了区分」の1箇所に置いて各工程から参照する。
古い再開記録を区分値の異なる節の追記で無効にするのは、観測を判定する時点の項目は`processing`で、エージェント環境からの本文置換が拒否され`atk wi edit --append`による追記だけが許されるためである。
追記は観測した結果も本文に残し、メインは最後の節の`再開区分`で観測のみの再開かを判定する。
同じ実行で再実装する案は、再開位置を持つ項目を新しい計画の`関連WI`から除くことを求めるplan-checkの確認と、観測のみの再開での旧計画の凍結を変える必要があるため採らない。

processingを維持するのは、後続の実行でエージェント自身が観測の前提を整えられる項目に限る。
実行記録などでユーザーが起動したと確かめたセッションの停止のように、ユーザーの操作または追加認可がなければ前提を整えられない項目もある。
元AWIの完成条件は維持し、追加認可だけが不足する工程はエージェントによる実施の認可を求める。
認可後の操作と観測はエージェントが担い、ユーザーしか到達できない工程でユーザーの操作を選ぶ場合に、必要な操作と観測結果をUWIで求める。
2026年10月5日には、残存するCodexを止めた状態を用意できないまま、同じ観測を3回の実行で試みた。
holdは選定対象から外れるため同じ観測の反復が止まり、回答後は回答済みUWIの取り込みで同じ計画の観測工程から再開する。
実装済みであることだけで完成条件を満たした扱いにする案は、人間由来の完成条件を失うため採らない。
新しい状態や再試行回数の上限は設けず、既存のUWIとholdを使う。
前提を整えられる主体の判定は2段に分ける。
レーン担当は前提を妨げる状態の生成主体・起動元・起動契機を利用できる現物（親子関係、起動時刻、実行記録、実装など）から観測し、未確定範囲とともに返す（`agent-toolkit/share/exec.subagent.md`）。
メインはその観測を入力に、エージェント自身、常駐機構、ユーザーの操作、追加認可のどれが前提を整えられるかを判定する（`agent-toolkit:process-wi/references/run-lanes-completion.md`「採否の確定と終了区分」）。
OS上の所有者は同じアカウントで動くエージェント、常駐機構、ユーザーを区別しないため、生成主体の根拠にしない。
2026年10月5日の3回目の観測では、レーン担当が残存Codexを同じOSアカウントの所有であることから「ユーザー所有」と返し、メインがUWIで「あなたが起動したもの」と書いた。
実際には`pid-update-loop`はPPID 1の常駐機構で、管理daemonはその子、`codex app-server --stdio`は同じセッションの委譲機構（`agents_server_mcp.py`）の子であり、いずれもユーザーが起動したものではなかった。
生成主体の観測を報告側の入力にし、判定側がその観測を要求する対の契約にしたのは、片側だけを直すと入力の欠落か誤った読み替えの一方が残るためである。
新しいCLIや常設の判定機構は、既存のプロセス情報、実行記録および実装から判定材料を得られるため設けない。
状態の変更と計画への記録は`agent-toolkit:process-wi/references/finish-session-observation.md`「延期adoptと反映後の観測」が持つ。

完成条件の観測主体は、状態を知覚する主体と完成を判定するために観測する主体を分け、後者をその項目を処理するエージェントとする。
2026年10月6日に、完成条件が配備後の観測主体を「運用者」と書いていたため、公開担当がその条件を担当外と読んで項目を`processing`のまま残し、メインもユーザーが是正するまで観測しなかった。
実際には開発・検証用の配備先へエージェントが到達でき、同じ観測を行えた。
判定規則は起草と読解の双方が読む`agent-toolkit/skills/wi-standards/references/awi-body.md`の完成条件の規定1箇所へ置く。
公開担当（`agent-toolkit/share/session-termination.subagent.md`）とメイン（`finish-session.md`「延期adoptと反映後の観測」）はその規定を参照し、到達できる環境を探してから観測できない項目として扱う。
人の観測そのものを禁止する案は、エージェントの実行環境から到達できない環境（Windowsでだけ動くクライアントアプリの実機など）が実在するため採らない。
`atk wi add`が完成条件の「運用者」などの人を指す語を警告する案は、状態を知覚する主体としての正当な記述を誤検出し、投入済みの本文と処理側の判断を検出できないため採らない。

反映後の観測だけが残る項目では、UWIとholdを選ぶ前に、エージェント自身が前提を整える手段を確かめる。
2026年10月7日に、観測のみの再開で残った完成条件が対話CLIへの自由記述の回答を要したため、メインは回答を生成できる主体をユーザーだけと判定し、UWIを保存して元AWIをholdへ移した。
自分で起動したtmuxセッションへキー入力を送れば同じ入力を生成できる可能性は検討されなかった。
到達環境を探す自己観測の要求は延期adoptの段落にだけあり、観測のみの再開の判定とUWI・holdの分岐には接続していなかった。
このため自己観測の判定は`finish-session.md`「延期adoptと反映後の観測」の1箇所に置き、延期adoptと観測のみの再開の両集合がその判定を経る。
`run-lanes.md`「採否の確定と終了区分」の前提を整える主体の判定とUWI・holdの手順はその判定を参照し、UWIには欠ける前提と自己操作が成立しない根拠を書く。
入力手段があることと回答を実際に受け取ったことは区別し、後者だけを観測として扱う。
tmux専用の条文を追加する案は、利用中のホストが公開する端末操作など同種の別手段を判定から外し、観測のみの再開へも適用されないまま残すため採らない。
ユーザーが起動したセッション、ユーザーだけが到達できる環境、新たな認可を要する操作は自己操作の対象から外し、既存のUWIとholdを使う。
2026年11月12日には、対話セッションの起動をclassifierに拒否されたことから、エージェントがユーザー自身による観測と結果の返信を求め、ユーザーが担当を是正した。
自己観測と認可要求の規定は存在したが、UWIの記載項目と再開記録は認可要求にも観測結果の返信を一律に求めていた。
この不整合を除くため、`finish-session-observation.md`の同じ分岐内で、認可の確認と、回答後の操作・観測の担当を対応付ける。
権限拒否への対応は既存の`permission-denial.md`が担い、観測の依頼を拒否解除へ読み替えない。

選定候補が0件の実行のように、process-wiの1回の実行の起動条件そのものを観測する完成条件は、空のキューと監査入力を制御した実行の検証で確かめてから終了する。
単一項目の観測を待つために、毎回の実行が読む選定の別集合、frontmatterの状態、公開CLIを設けた構成は、2026年10月に撤去した。
自然に発生する入力を待つ間は項目が無期限にprocessingへ残り、その1件のために全ての実行の選定と手順が分岐を読むためである。
