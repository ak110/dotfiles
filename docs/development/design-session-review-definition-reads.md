# 定義本文の取得と起動準備の設計記録

[設計記録の索引](design.md)と[振り返り・知見集約の設計記録](design-session-review.md)から参照する主題別の記録である。

## 定義本文の取得と起動準備の判定

`.subagent.md`の明示読取と静的に対応付けた読取対象は、正常終了も既存の呼出し・結果の対応から取得し、記録ごとの`definition-body-read`へ集約する。
複合入力は`session_evidence_execution.command_input_observations`と`command_inputs`が操作境界を所有する。
シェルは`session_evidence_execution.shell_simple_commands`が、置換の本体と複合コマンド（`for`・`if`・`case`・`{ }`・`( )`）の本体まで単純コマンドへ分ける。
区間の解決には既存の`agent_toolkit._common.shell_segments`を使い、PreToolUseなど助言用の消費側が共有するその公開挙動は変えない。
取得抽出はその読取操作の入力ファイル引数だけを使う。
編集本文、JSON参照、履歴の検索語、別操作の定義名を結び付ける全文検索は行わない。
Codexの`functions.exec`では、`atk run-script session-review-evidence`が同じturnの外側セルの呼出しから結果までの区間を使い、帰属が一意な内側実行（`CommandExecution`）の実際のコマンド文字列を既存の解析処理へ渡す。
候補の`calls`と個別証拠の`definition_reads`に外側セルと内側実行の入力・結果位置を残し、対応付けられない内側実行も独立した要素として保持する。
異なる識別子の一致や完了順に依存しない。
用語、位置の構造、理由区分は`agent-toolkit:review-session/references/analysis-definition-reads.md`「定義本文の読込の判定」が定義する。
動的な実行入力・対象展開と解析できない区間は、手順書を読む可能性がある場合に限って`definition-read-unresolved`へ分け、公開prepareの必須候補と索引へ接続する。
代入だけの区間、引数の無い`env`、`command -v`、構文語は読む可能性が無いため出さない。
固定の末尾から`.subagent.md`になり得ない動的な対象（`$d/test-linux.log`など）も出さない。
同一入力にある固定代入とforの列挙値を静的に解決し、処理済みWI、定義読取および加工判定で共有する。
複数値は和集合として扱い、固定の波括弧展開も解析する。
シェル自体は実行しない。
参照より後の初回供給、read等の別供給、関数本体の供給、演算付き展開およびコマンド置換は未確定に保つ。
固定されたshare外のディレクトリの単一階層globは定義候補から除き、相対パスと再帰globは保守的に扱う。
前置語の値境界が未知でも、定義を読み得る入力がなければ候補から除く。
xargsを含む区間、実行コマンドが動的な区間、閉じない構文は未確定に残す。
rg・grep・sedの反復パターンオプションは各値を消費し、パターン文字列を読取ファイルへ混ぜない。
2026年10月29日の準備では、未確定の評価必須60候補・394呼出のうち、入力に`subagent`を含む呼出は11件だけで、残りは手順書と無関係なシェル操作だった。
内側実行を対応付けられず、入力だけでも判定できない場合は、セル全体の入力と対応付け不能の理由へ集約する。
この場合の入力別の未確定理由は原記録から確認する。
同じ外側セルに含まれる静的に判定できた読取は別に保持する。
記録されたコードを実行する全面的な意味解釈は採用しない。
計算プロパティ、spread、`cmd`の短縮記法・アクセサーを持つ実行引数は、値の上書きを静的に確定できない材料とする。
Get-Contentは対象パラメーターと既知オプションの値を分け、解釈できないオプションを未確定へ送る。
初回表示は短い索引を保ち、保存した`calls`と個別証拠の`definition_reads`から全読取位置・主体・対象・結果と前後の起動や編集へ到達できる。
存在確認・名前列挙・起動入力のパス指定は本文取得と分ける。
取得の有無、取得の目的、結果の成否は独立した軸として原記録で判定し、編集、自身が受領した定義、返却後の検収は根拠を示して分類する。
静的な入力と対象の対応は、実行結果の成功や本文の読了を確定するものではない。
`agent-toolkit:delegation`の`SKILL.md`「送信」が禁止する起動準備の本文読込は、次の資料の判定に従う。

- `agent-toolkit:review-session`の`agent-toolkit:review-session/references/analysis-definition-reads.md`「定義本文の読込の判定」

原因・対策・保存先の対応を必須とする。
成功・単発・費用だけを理由に対策を省く判断から外す。
証拠不足と対策未確定は未確定として残し、処置済みの報告と区別する。
準備は`definition-body-read`の各読取を、同じ記録の後続に同じ役割の起動があるかと、読む主体の役割文書かで判定する（`launch_check`）。
起動準備の疑いがある読取を含む候補だけを評価必須にする。
禁止事項は読んだ主体がその役割を起動して初めて成立し、準備は同じ記録の起動入力と役割文書を既に持つためである。
2026年10月28日のprocess-wiの準備では手順書の読取77箇所が全件評価必須になり、後続に同じ役割の起動があったのは5箇所だった。
毎読取時に目的を判定して遮断する案は、編集や検収にも判定負担を課すため採らない。
一方で、事後の検出だけでは読んだ時点に作用せず、2026年10月24日と28日に起動準備の読込が再発した。
このため、パスと自身の役割だけで決まる非遮断の警告を既存のPreToolUseの読取判定（`agent-toolkit/agent_toolkit/_hooks/pretooluse/read_delivery.py`）へ加えた。
部分表示の初回も`large_reads.display_read_paths`で静的ファイル引数を抽出し、同じ警告へ接続する。
パイプ、head/tail、grep/rgに加え、sedの正規表現アドレス付きprintとawkの条件・アクションによる節表示を含む。
静的な入力ファイルだけを抽出し、編集・ファイルへの出力・動的実行・ディレクトリ検索は除く。
この判定は全文受領の証拠を更新せず、記録参照の警告と表示引数の解析を共有する。
警告は目的を判定せず操作も止めないため、編集と返却後の検収は警告後も続行できる。
他の宣言元の取得は時点条件の成立を示さないため、警告の除外条件にしない。
自身の役割文書と、その役割文書の読込表が自分の工程として読ませる手順書、別のリポジトリ・`share`以外の位置にある同名ファイルは除外する。
plugin rootと同じリポジトリの別worktreeにある同じ位置の手順書は警告の対象に含め、起動準備では呼出側へ生成配置した返却契約へ案内する。
範囲と理由は`design-delegation.md`「起動準備と定義本文の読込」にある。
振り返りでの検出は、警告後も読んだ場合の検出を担う。
