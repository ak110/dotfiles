# 一括取り込みと原文保持の設計記録

[設計記録の索引](design.md)と[WIキューと要求本文の設計記録](design-wi.md)から参照する主題別の記録である。

## 一括取り込みと原文保持

逐語引用と原発話の一致判定は`record`・`line`・`sequence`を内部表現で保持し、取り込みのフェンスを選択イベントへ対応付ける。
保存するWIの出所行はセッション記録の位置だけを示す。
標準出力には入力source pathと全候補位置を示し、同じ部分文字列が複数発話へ現れる場合も区別する。
一時抽出ファイルの所在を保存WIの出所にする案は、回収後に原発話へ到達できなくなるため採用しない。

別環境からの移行と復元では、キューの保存内容を字面のまま新しい環境へ複製する。
一括取り込みは`atk wi show --all`の表示形式をそのまま入力として受理し、
CLI（`atk wi add --batch`）とWeb UIの双方が同じ解析・書込み処理（`agent-toolkit/agent_toolkit/_atk/wi/batch.py`）を用いる。
通常の投入処理は`target_commit`を再取得し、UWIの見出しと回答欄を再生成し、採用しない予約frontmatterキーの入力を保存前に拒否するため、
原文保持と両立しない。
このため一括取り込みを通常処理から分離し、採番・書込み・commitだけを共有する。
取り込みが保存内容へ加える変更は、改行の正規化（CRLF・単独CRをLFへ揃え、末尾改行を1つへ揃える）と、
再採番したエントリを参照する`depends_on`要素行の差し替えに限る。
ファイル名は他の項目・計画・メモからの参照の同一性を保つため元名を維持し、取り込み先の固定配置と衝突する場合だけ再採番する。
衝突の判定は、取り込み先が名前の大文字小文字を区別するかどうかを排他区間内で1回だけ実際に確認し、その結果に応じた比較の基準を
既存名との衝突・入力内の重複・再採番の除外集合の3箇所へ共通に適用する。
OS種別から区別の有無を推定する案は、
大文字小文字を区別しないファイルシステムを標準で用いるOSでも推定が成立せず、保存内容を無警告で失う危険を残すため採用しない。

解析処理は入力テキストと取り込み先の既存ファイル名だけを知り、対象リポジトリの実在やリモートURLの解決可否を判定しない。
移行元にだけ存在する旧形式の保存値も取り込めるよう、`target_repo`の検証は非空の文字列であることに限る。
対象リポジトリの解決を要求する検証は、対象を省略する通常の新規追加処理だけが持つ。

表示形式は可逆な直列化ではないため、本文が完全な表示形式のエントリの引用を含む場合の誤分割と、
末尾の改行・連続空行の非復元は限界として明記し、ユーザーの許容のもとで受け入れる。
機械可読の専用形式を新設する案は、移行元の表示出力をそのまま入力とする利用手順が成立しなくなるため採用しない。
frontmatter全体を再直列化する案は、引用符や配列表記の字面が変わり原文保持に反するため採用しない。

Web UIの新規追加ダイアログでは、種別を`awi`・`uwi`のままshow形式の本文を送った場合も一括取り込みへ切り替える。
種別の初期値が`awi`で、ダイアログを開くたびにその値へ戻るため、一括登録のつもりの本文が単件処理へ送られやすく、そのまま受理すると表示用の見出しを含む本文全体が1件のWIとして保存される。
判定はCLIの一括取り込みと同じ構造判定（`wi/batch.py`の`is_show_batch_format`）だけで行い、エントリの検証を含めない。
構造に該当した後に検証が失敗した場合は、単件保存へ戻さず一括登録と同じエラーを返す。
単件として保存すると、切替が防ぐ誤登録と同じ結果になるためである。
ブラウザーは単件の本文をtrimして送るため、単件処理にも未trimの入力（`raw_text`）を添え、判定と取り込みはその値で行う。
trim済みの本文で取り込むと最終エントリの末尾空白が失われ、一括登録で送った場合と保存内容が一致しない。
コマンドラインの`atk wi add`は一括取り込みを`--batch`で明示的に選ぶ操作であるため、この切替を持たない。
入力の解析に失敗した項目だけを除いて取り込む案も、依存関係の参照先を欠いた部分集合が生じるため採用せず、全件拒否とする。

### 構造化確認の由来分離と逐語比較

構造化確認では、`text`と`user_response`をユーザー値、`assistant_context`を質問と全選択肢として分離する。
逐語比較はユーザー値だけへ行い、保存済みの行頭ラベル形式は読取互換だけを残す。

### WI本文の改行契約

目的はキュー項目のテキスト保存と解析結果を実行環境の改行規則から独立させながら、bytes追記が保持する保存済みの字面を変更しないことである。
テキスト書込処理は本文をLFへ正規化し、UTF-8のbytesとして保存する。
解析と保存後の本文の一致判定は`decode_entry_text`でデコードとLF正規化を一括して行う。
これにより、CRLFで受け取った本文もfrontmatterの解析と`body_match`の一致判定へ同じ文字列として渡せる。

bytes追記処理は、保存済みbytesと追記bytesをそのまま組み立てる。
保存内容を分割する関数は改行を正規化した写しで位置を解析し、入力の部分文字列を返す。
解析用の正規化を保存内容の組み立てへ流用しないのは、既存部分のCRLFをLFへ変更せず、追記前の保存bytesを保持するためである。

知識境界として、デコードと改行正規化は`agent-toolkit/agent_toolkit/_atk/wi/frontmatter.py`の`decode_entry_text`が持つ。
テキスト保存は同モジュールの`write_entry_text`が持ち、保存内容の分割とユーザーコメントの更新は`agent-toolkit/agent_toolkit/_atk/wi/user_comment.py`が持つ。
各呼び出し側は、解析と一致判定には正規化済み文字列を使い、bytes追記の組み立てには未正規化の原文を使う。

`parse_frontmatter`自体をCRLF許容へ変更する案は採用しない。
この案ではテキスト保存のLF統一、保存後の本文の一致判定およびbytes追記の原文保持を同時に成立させられず、改行の責務が呼び出し側へ分散するためである。
