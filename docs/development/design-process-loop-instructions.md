# 次の起動への追加指示の設計記録

[設計記録の索引](design.md)

## process-loopの次の起動への追加指示

`atk wi process-loop instruct <本文>`はprocess-loopの次の起動へ渡す本文を、
中断要求と同じOSアカウントの状態ディレクトリの`process-wi-instructions`へ追記する。

process-loopは次の実起動のプロンプトへ本文を追加指示として連結し、起動成功時に1回消費する。
abortや起動前の失敗では本文を保持し、空キューかどうかは消費条件にしない。
稼働中の巡回会話があれば、その会話へ通知で届けて消費する。
委譲先のセッションへは加えない。
追加指示はユーザーの入力として扱う。

本文の上限2,000文字は、旧配送先のSessionStartの`additionalContext`がClaude Codeで10,000文字に切り詰められ、超過すると規範条文が欠落したことに由来する。
目的文への連結を避けていたのは、撤去済みの`/goal`の評価へ毎ターン渡していた時期の判断である。
起動後のセッションが自ら状態ファイルを読む案は、全セッションへ読取の1工程を課し、
かつセッションが手順を実行する必要があるため採用しない。

## 効率化の仕組みの棚卸し（2026年11月）

横断的な記録の条件と限界は[設計索引](design.md)の「効率化の仕組みの棚卸し」を参照。

- オーケストレーターの可用性確認を最安モデル・effort low・軽量起動で行う方式は、ユーザーが要求し、確認回答でも選択した（2026年10月18日）。
  可用性probeの比較はモデル・effort・読込設定が同時に変わるため軽量起動だけの寄与ではなく、全体の所要時間の前後値は未確認である。
  可用性の確認は既存の設定済み候補と起動診断から選び、共有設定を勝手に書き換えない。
  可用性だけの確認を高価な実行担当へ回さない既存の最小入力を使い、実作業の品質・モデル指定を変えない。
- 撤去前は無進捗反復の検出で同入力の再起動を止め、開始前猶予ではキー入力で猶予を解除し、活動対象を限定していた。
  現行は常駐する巡回会話が開始判断を行い、追加指示を通知で受け取る。
