# 方針・意向: 規範文書の知識と手順

本書は[規範文書の書き方](concepts-document-writing.md#規範文書の書き方)のうち、知識と手順の記述を扱う。

- UWI回答に含まれる汎用的な判断基準・選択理由は恒久化候補として必ず列挙し、
  反映先または計画限りの判定と根拠を明示する（2026年8月、ユーザー合意。
  ユーザーは無条件で規範へ反映する義務の案を採用しなかった）
- 計画ファイルの`## 概要`は工程が長引き要件が増えた場合も追記を重ねず、
  現在の計画に合わせた短い要約へ書き直して保つ。
  指摘・要件の反映は
  既存記述と統合する編集として行う（2026年8月、ユーザー指示。レビュー反復時の追記累積で
  計画ファイルが乱雑になる観測に由来）
- ユーザー要求の対象、適用範囲、外部可視の結果または除外内容をエージェントが原文から新たに具体化する場合は、
  調査を完了して推奨案と観測根拠を示し、計画確定前にユーザー確認する。
  ユーザーが対象、範囲および結果を明示した提案を
  同じ内容で採用する場合、コードベースから確定できる事実、実際の検証による内部値の補正、ファイル配置、関数分割およびテスト手段は確認対象にしない
- AWI・UWI・改善提案の本文は結論を冒頭へ置き、裏付け・代替案などの詳細は簡潔化して後置する
  （2026年8月、ユーザー回答。振り返り由来本文の平均文字数が2か月で2.3倍に伸長し結論が埋没した観測に由来）
- 成果物・発話・コミットメッセージの識別子は読者基準で選ぶ。
  読者が観測・設定・操作する対象は原表記とし、
  曖昧な一般名詞への機械的な言い換えを行わない（2026年8月、ユーザー回答。miseを「ツール管理器」と
  言い換えた結果、同一文書内のログ・diffの原表記と一致せず対象を特定できなくなった観測に由来）
- 規範の条文が求める対象を定義だけで一意に示せるなら、その対象に新しい呼び名を付けない
  （2026年9月15日、ユーザー指示。「恒久成果物」の語の導入を不要な概念の追加とする指摘に由来する）
- 規範にはそれを読む実行主体が自ら起動できる対象だけを起点として記す。
  ユーザーの手動起動だけを受け付ける機能を規範の起点として書かない
  （2026年9月15日、ユーザー指示。エージェントが起動できないスキルを起点として案内した記述に由来する）。
  現行の規定は`agent-basics:writing-standards`の`references/agent-documents-additions.md`にある
- 手順と規範は達成する性質で書く。
  起動手段・ツール・実行順・同時実行の禁止を名指しするなら、
  指定した手段でなければ性質を満たせない根拠を併記する（2026年9月、ユーザー指示。
  目的に合致しない厳しすぎる制約を手順へ書かないことと、既存の同種の制約も是正することの2点を受領した）
- `agent-basics:writing-standards`の`references/implementation-time.md`が持つ言語横断の標準ツールの表は現行のまま維持する。
  同`references/independent-html.md`が定めるCDN経由のCSSフレームワークの採用と取得方式も維持する
  （2026年9月16日、ユーザー回答。全文見直しが同じ2件を繰り返し検出する事態を避けるために記録する）
- コーディング基準を編集する主体は、一般的な構文・API操作・汎用的な目安を、守る価値と判断方針、知識を想起する代表語へ整理する。
  作者固有の選好、対象版の差、特定の環境で生じる失敗、公開契約・データ保全・セキュリティの条件と例外は具体的に保持する。
  標準ツール表と単体HTMLのCDN方式の維持判断はこの整理でも継続するが、一般的な技術の細則まで一律に保護する根拠にはしない。
  2026年10月7日のユーザー依頼と「既知の知識は方針と語だけ」の回答による。
  適用先はwriting-standardsのコーディング用参照資料であり、技術別の読込表と必要な参照節は維持する
- エージェント向けの文章は、学習データから導ける一般知識を守る価値・判断の観点・想起の手掛かりになる代表語で書き、具体的に書くのは学習データから導けない事実と硬い制約に限る。
  学習データから導けない事実には、プロジェクト固有のパス・コマンド・規約、観測した環境固有の注意点、知識カットオフ後に変わった仕様が当たる。
  案件の入力と期待結果、主体間の認可境界、ユーザーが指定した手段、受入条件も具体的に残し、一般知識の省略をこれらを曖昧にする理由にしない。
  適用先は規範に加え、委譲プロンプトと追送、計画ファイル、AWI本文の起草である。
  記述量は手掛かりの不足で観点を想起できないことと、詳細な手段・例への固執の双方を比べて決め、文字数や例の件数で一律に決めない。
  従来の「明示しないと考慮されない観点は自明導出に当たらない」という扱いは、観点を代表語で残す扱いへ改め、一般知識の細則を一括して保護する根拠にはしない。
  2026年10月7日のユーザー依頼と、確認への回答「既知の知識は方針と語だけ」「委譲プロンプトと計画にも適用」による。
  現行の規定は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/writing-readers.md`「読み手別の追加注意点」が定義元であり、
  `agent-documents-basics.md`、`agent-documents-additions.md`、`agent-toolkit:delegation`の`references/base-contract.md`、
  `agent-toolkit:write-plan`の`references/plan-file-standards.md`、`agent-toolkit:wi-standards`の`references/awi-body.md`と`references/drafting-completion.md`が参照する
- エージェント向け文書は、読み手のエージェントが広い知識を持つ前提で書き、常識的に判断できることを細かく手順化しない。
  細かすぎる手順は「書かれた手順以外はやってはならない」という先入観を生んで品質を下げ、文章量に比例して費用も増やすためである。
  手順として書くのは目的、守る価値、硬い制約、プロジェクト固有の事実、実際に誤った箇所に限る。
  2026年10月11日のユーザー指示「常識的に判断できるようなことを微に入り細に穿つ説明をすべきではない」による。
  同じ指示で既存のエージェント向け文書全体の手順記述を削減した。
  2026年10月12日、ユーザーは誤りの観測後に再発防止策として追加しようとした細目もこの方針に該当すると指摘した。
  再発防止策を選ぶ場面でも、読み手が目的と常識から判断できる事項は条文を追加しない。
  現行の規定は`agent-basics:bugfix`の`SKILL.md`「原因分析の品質確認」にある。
  手順として書く「実際に誤った箇所」は、目的と守る価値が示されていても誤った箇所に限る。
  現行の規定は`agent-basics:writing-standards`の次の資料にある。

  - `agent-basics:writing-standards/references/writing-readers.md`「読み手別の追加注意点」
  - `agent-basics:writing-standards/references/agent-documents-additions-volume.md`「削減の判定根拠」

- 工程・レビュー・検証・判定・担当などの名前はその場で作成せず、定義して統一する（2026年10月2日、ユーザー指示）。
  方針は次の7点とする。
  定義を読まなくても指す対象が分かる自然な語を選ぶ。
  一般的な語（独立、root、固定、管理など）に独自の意味を持たせず、別々の概念に似た名前を付けない。
  識別子（スキル名、コマンド名、ファイル名、定数名など）がある対象は識別子で書く。
  ユーザーが名付けた名前と`atk serve`の画面などエンドユーザーが目にする場所の名前は残す。
  境界があいまいな名前はユーザー確認する。
  返却形式の欄名も日本語名にする。
  用例の多さや既存の定義の有無を名前を残す根拠にしない。
  読み手は名前を書く全ての主体（規範・設計文書・WI・計画・コミットメッセージ・コードの書き手）、適用範囲はagent-toolkitの規範に従って書く全ての成果物とする。
  名前を新たに作成せず識別子か一覧の名前を使うことを優先し、どちらも無い対象へ名前が要る場合は自然な語を選んで定義元へ1文の定義を置き、一覧へ加えてから使う。
  `agent-documents-basics.md`「主要用語の初出定義先」の一般的な語の優先は方針1と同じ向きであり、方針2と合わせて読む。
  「実在する名前が無い対象は説明で書く」規定（`share/rules/rules-main.md`、`writing.md`）は名前が要らない対象に適用し、繰り返し参照する工程などの名前ではこの方針を優先する
- エージェントが特定の場面で従う手順は、常時規範の短い箇条と`share/`の長文を組み合わせず、標準のスキルへ置く（2026年9月25日のユーザー指示）。
  実行時に従う規範は`agent-basics/skills/writing-standards/references/agent-documents-basics.md`「責務と構成」と各スキルに置く
- 明示的な手動起動を前提としないスキルは`user-invocable: false`とする。
  この方針の実行手順は`agent-basics:writing-standards`が定める
- `agent-toolkit:refine-prompt`は、エージェントが必要な場面で自分から起動する内部スキルとする。
  2026年11月10日のユーザー指示「ユーザーが手動起動するのではなく、モデルが規範見直し時に自動的に呼び出す内部的なスキルにした方がいい」と確認回答による。
  契機は、スキルや役割文書の新設時、指示と挙動の食い違いの調査で改訂が必要と確定した時、モデルまたはホストの更新時の3つで、ユーザーは「規範の改訂すべて」を選ばなかった。
  ユーザーは、重い作業は本当に必要な時だけ行うことと、`agent-basics:writing-standards`との重複の整理も求めた。
  このため、通常の評価はシナリオを与えた評価に限り、文書の点検は検索による判定と評価担当の通読の2段階とし、ホストの更新では変更履歴の確認で点検の要否を先に判定する。
  2026年10月31日に採用した点検手順はユーザーが`/agent-toolkit:refine-prompt audit`で起動する形だったが、この指示がその起動の形を置き換えた。
  点検が提案だけを返し、採否をユーザーが決める扱いは保つ。
  現行の規定は`agent-toolkit:refine-prompt`と、起動の契機を定める次の2資料にある。
  `agent-toolkit:wi-standards/references/agent-documents-additions.md`「新設と改訂の評価」と、`.claude/skills/edit-dotfiles-norms/SKILL.md`「モデルとホストの更新時の点検」である
