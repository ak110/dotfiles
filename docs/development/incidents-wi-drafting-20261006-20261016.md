# 障害・欠陥の記録: WI投入とAWI起草の欠陥（2026年10月6日〜2026年10月16日）

[WI投入とAWI起草の欠陥](incidents.md#wi投入とawi起草の欠陥)の事例を発生時期別に収録する。

- 2026年10月6日: AWIを起草したWI投入担当が、意味を確かめていない記録の項目の件数と、比べる群の無い件数を、直接的原因を確定する根拠として原稿と返却へ書いた。
  直接原因: 担当の原稿と返却は、2種の件数を確定した直接的原因の根拠として書いた。
  生成元を確かめていない記録の項目の件数と、比べる群を数えていない件数である。
  対策: `initial-analysis.md`の推定の条件を、相関だけの候補、条件を満たさない群と比べていない件数、生成元で主張の対象を表すと確かめていない値の3種へ広げた。
  `root-cause-analysis.md`の`原因分析の根拠`行へ値ごとの生成元と比較の併記を求めた

- 2026年10月6日: 地の文が画面へ届かない事象を起点とするAWIを起草したWI投入担当が、`## 原因分析`を書きながら`agent-basics:bugfix`を起動しなかった。
  直接原因: 担当は`add-wi.subagent.md`冒頭の文が挙げる2スキルだけを起動した。
  対策: `add-wi.subagent.md`冒頭の文へ、観測した欠陥を起点とする要求での`agent-basics:bugfix`の起動と、WIの起草で常に条件が成立する読込表の行の資料の全文読込を移し、原因分析の文の起動元を冒頭の起動へ寄せた

- 2026年10月6日: `add-awi-by-user`のセッションで、メインは拡張思考の中の発話が届かない事象のAWIを書き直す担当を起動する際、直前のユーザー発話の後半「雑な根拠の不正確な情報を断定口調で書かないようにして」を、そのAWIの`確定した要件`へ置いた。
  直接原因: `確定した要件`の欄は由来と後続工程の手段の条件だけを持ち、その要求へ帰属するかの条件を持たなかった。
  注文や是正の形の要求は新しい要求として認識されずにこの欄へ入り、AWIの粒度を判定されなかった。
  対策: `add-wi.parent.md`「渡す入力」の`確定した要件`の項へ、反映先と完成条件に作用する要件に限り、重ならない注文や是正は別の要求として新しい担当へ渡す条件を加えた。
  `add-wi.subagent.md`は帰属しない固定要件を本文へ取り込まず続行できない理由で返し、`add-wi.parent.md`「受領と検収」はその返却を受けて別の担当へ渡す

- 2026年10月6日: AWIを起草したWI投入担当が、全文を読むべき2つの資料を、見出しを`rg`で一覧してから一部の行範囲だけ`sed -n`で読んだ。
  直接原因: 担当は見出しの一覧から同じ文脈にあった他の文書の節名の参照が指す節の行範囲だけを選んで取得した。
  出力の切り詰めは無く、範囲は担当が選んだものだった。
  対策: `agent-basics:search`の末尾の段落へ、全文読む資料を見出しの一覧や節名の参照から範囲だけ取得した結果も本文が省略された結果に当たり、節名の参照は読む範囲を狭めないため全文を読んでから適用することを書いた。
  手順が検索で特定した節を読むと定める場面と、読込表の行が節だけを読むと定める場合はその定めに従う

- 2026年10月6日: pyfltr 3.21.0が公開待機で解決できずCIが失敗した件の対処を問うUWIで、WI投入担当が「dotfilesが配布するuv設定（`~/.config/uv/uv.toml`）でpyfltrの公開待機を外す」選択肢を載せ、委譲元のメインも検収で合格とした。
  ユーザーは回答欄で、除外は各プロジェクトの`pyproject.toml`へ置き、グローバルに設定すると各プロジェクトの`uv.lock`へ入るため禁止であると以前に伝えたと是正した。
  直接原因: WI投入担当は設定値を参照する箇所を隠しディレクトリを走査しない`rg`で探したため、`.chezmoi-source/`配下の`ci-and-tooling.md`が結果に現れなかった。
  対策: `dependency-management.md`のパッケージ単位の除外の項へ置き場所（プロジェクトは`pyproject.toml`の`[tool.uv]`、`uvx`はコマンドライン、ユーザー設定へは置かない）と理由を集約し、`ci-and-tooling.md`はその項を参照する

- 2026年10月7日: dotfilesのセッションで、WI投入担当は2026年9月25日に回答済みのUWIの判断（Herdr導入時だけ失効確認をbest-effortにする）を、同じ取得で同じ失敗を起こす`herdr update`へ当てはめたAWI原稿を返した。
  ユーザーは「エージェントが判断できないことだけユーザーに聞いて」と回答し、場面ごとの対処では再発すると是正した。
  直接原因: `judgment.md`「認可を要する操作」は、判断から外れたときに対象・範囲が変わる操作を目的側の判断の変更とし、比べる相手を記録の文言に置いていた。
  判断の目的とは比べていなかった。
  対策: 確認要否の判定の手順2へ、元の要求と人間が確定した判断の目的を手元の情報に含め、区分や解釈を決めかねる場合は目的に照らして確定して報告することを置いた。
  `judgment.md`は判断の変更を目的の変更、退けた案の採用および選んだ結果の取り消しと定めた。
  同じ目的に資する当てはめは判断の適用とし、決めかねた場合の確認の扱いを除いた

- 2026年10月7日: `agent-toolkit:atk-mode`の作業`add-awi-by-user`のセッションで、wi-commitsの記録先を変えるAWIの起草中に、ユーザーが3文の発話を送った。
  直接原因: 追送の項は追送を要件更新に限るが、要件更新に当たるかを判定する単位を定めず、合流前の比較も追加要求を1つの単位として扱っていた。
  メインは発話の単位で判定し、一部が更新に当たることから残りの文も同じ追送へ入れた。
  対策: `add-wi.parent.md`「起動方法」の追送の項と`add-awi-by-user`の手順冒頭へ、追加の発話を要求単位へ分けて単位ごとに粒度を判定し、一部が更新に当たることを残りの単位を含める理由にしないことを書いた。
  起草側の読み直しと委譲元の受領にも帰属の確認を置いた

- 2026年10月9日: ユーザーは、承認・確認・操作を求める全手順を見直し、エージェントが判断できない事項だけを問うよう是正した。
  直接原因: 共通の確認要否判定と、手段逸脱・由来不明・受領不能・依存待ち・レビュー不成立などを一律に確認へ送る発行条件が併存した。
  委譲通知と統合検収も必要性によらず全対象の発行を要求した。
  対策: 共通判定を発行・通知・受領・統合検収へ接続し、原要求、現物、既存認可とQCDで確定する事項は自ら確定して報告する。
  ユーザーだけの値が残る事項だけを問い、回答ごとの操作分岐を書けることを十分条件にしない。
  過去の以下の対策は履歴として保持する

- 2026年10月9日: 是正や調査の文脈だけから、成果物を読む人へ不要な説明を追記するAWIが作成された。

  質問への回答も文書へ反映すべき要求へ変換された。

  質問は回答済み注記で対応付けを完了でき、説明追記は独立に採否を判定する。
  再発防止策は読む主体の判断が原因へ作用するかを先に評価する。
  3実例の不要な注記と、全件取得、継続失敗、部分一覧を削除判定へ使わない設計契約の説明を対照にし、後者は開発者が維持する判断として残す

- 2026年10月16日: AWI・UWI本文を簡潔にする要求の起草中に、ユーザーが計画・Issue・PR/MR本文の冗長さも指摘した。
