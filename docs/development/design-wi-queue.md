# WIキューと実行準備の設計記録

[設計記録の索引](design.md)と[WIキューと要求本文の設計記録](design-wi.md)から参照する主題別の記録である。

## WIキューと実行準備

WIの保存先は`private-notes/yyyy/MM/<filename>`とし、作成年月とファイル名で固定する。
配置の定義は`agent_toolkit._common.wi_layout`が所有する。
保存状態はfrontmatterの`state`が持ち、状態遷移は同じファイルのメタデータを更新する。
本書で状態間の移動と呼ぶ操作は、このメタデータの変更を指す。
一覧、名前解決、依存、readiness、process-loop、alerts、Webと計画構造チェックは共通の探索・検証を使う。
状態をパスへ埋め込む案は、遷移のたびに参照と画面URLが変わるため採用しない。
旧状態別配置と旧々配置は公開CLIの移行処理が扱い、通常の利用側は現在の配置を独自に定義しない。
計画バンドルの保存配置はWI配置から独立して維持する。

AWIとUWIは、会話から独立したキューへ永続化する。
キュー機構は、状態遷移、依存関係、回答状況および計画ファイルの有効性から実行準備の成否を算出する。
この構造により、中断や別セッションへの移行後も、未完了の理由と再開位置を同じ情報から復元できる。

キュー操作は、保存内容の検証と状態変更を同じ排他区間で実行する。
参照系の`list`、`show`および`grep`は同一連続操作に限り同期結果を再利用できる。
CLIのcommitとpushを伴う状態遷移系は同期を省略せず、変更直前のキュー状態を毎回確定する。
本文取得は用途に応じて、`atk wi show`の全文、`--summary-only`の要約、反復指定できる`--section <H2名>`の指定節照会を使い分ける。
指定節は同名の節を全て保持し、フェンス内の見出しを節境界として扱わない。
要約を既存本文の編集元にすると省略部分が失われるため、編集には全文を用いる。
Webの編集・回答・状態変更・投入は排他区間で競合を確認してローカルcommitまで確定し、その時点で画面へ成功を返す。
未送信commitのpushとremote差分の取得は、定期同期またはユーザーの明示同期で行う。
remoteの待ち時間を保存操作へ含めると、成功が確定した後も次のWIを操作できないためである。
同期に失敗した場合はcommitを保持し、画面へ失敗と再試行手段を示す。
独立した永続キューを追加する案はGit commitが同じ保留状態を保持するため採用しない。
remote同期はfetch後の統合対象を現在のブランチの`@{u}`へ明示し、fast-forward更新とpush再試行時のrebaseを
共有状態の`FETCH_HEAD`とユーザーの`pull.rebase`設定から独立させる。

同じ対象リポジトリの複数項目を同一工程で読む場合は、managed-tempの中へ作業ディレクトリを作成し、`atk wi show <filename>... --skip-pull`の標準出力を保存ファイルへ書き込んでから全文を読み、ファイル名見出しから本文を対応付ける。
保存内容の構造成立・不成立・コマンド失敗を確定した後、独立登録した領域だけcleanupを完了する。
セッションのmanaged-temp直下の作業ディレクトリは同セッションの終了時に回収し、保存不能時だけ分割取得へ代替する。
readyなinbox集合の処理開始も、ファイル名昇順の
`atk wi start-processing <filename>...`を1回実行する。
処理開始コマンドは全対象の存在、状態および`target_repo`を変更前に検証するため、一部不適合で集合全体を拒否できる。
移動開始後にI/O、commitまたはpushが失敗した場合は、指定集合のprocessing配置、管理リポジトリの未コミット差分、
集合の移動だけを含む遷移commitおよびremote設定時のupstream包含を分けて確認する。
管理リポジトリの状態確認を開始する前に、`atk config get private_notes`の標準出力から絶対パスを取得する。
取得したパスを`<private-notes-path>`として管理リポジトリのGit操作対象にする。
全てのGit操作へ`git -C <private-notes-path>`を付け、対象リポジトリのcwdを使用しない。
絶対パスを取得できない場合はGitの状態確認をせず未完了で停止する。
`git -C <private-notes-path> status --porcelain`で管理リポジトリの状態を確認する。
`git -C <private-notes-path> show --name-status --format=%H%n%s HEAD`で遷移commitを取得する。
remote設定時は`git -C <private-notes-path> fetch`を実行する。
その後、`git -C <private-notes-path> merge-base --is-ancestor <transition-commit-oid> @{u}`でupstream包含を確認する。
commit前失敗で指定集合の移動だけが残る場合に限り`atk wi commit`を1回使って再確認し、
未pushのcleanなローカルcommitだけの場合や集合の状態が混在する場合は、項目別再実行で補わず未完了として停止する。
単一項目の調査、警告・エラー後の再取得およびUWI回答確認は、情報の対応関係を保つため単数形を維持する。
toolkitは自身の排他区間外で他プロセスが行うfetchを管理しないため、`FETCH_HEAD`の更新は許容し、
統合対象だけを明示refで固定する。
`git pull`を継続する案と失敗時の再試行を加える案は、
共有状態を前提とする構成を残し、恒常的な再試行の複雑性を増やすため採用しない。
処理主体は準備が整った項目だけを実装へ渡し、ユーザーの判断を要する事項はUWIへ分離する。
ファイル配置、関数分割、内部データ表現、検証手段は実装上の技術判断で確定し、UWIへ分離しない。
UWIはユーザーが決める要件と運用方針を対象とし、回答に必要な情報だけを本文へ置く。
事前承認型UWIの回答を待つ元項目は、`depends_on`へそのUWIを加えて表し、編集目的の`hold`と区別する。
回答を待つ元項目のファイル名と回答後の再開工程は、対応するUWIの本文に記録する。
未回答のUWIは処理候補に入らないため、そのUWIを待つ依存は内部依存待ちに数えず、元項目は`blocked`のまま選定の候補から外れる。
`atk serve`の一覧はこの導出値で`blocked`バッジを表示し、保存状態は増やさない。
回答が保存されるとUWIが処理候補に入り、元項目もキュー内の依存待ちとしてprocess-wiの同じ実行の候補に入るため、選定は両方を同じレーンへ割り当てる。
2026年9月16日の`378f926e8`は、依存方式では回答から実施までにUWIの終了・依存の解除・次の選定の3段を要するとして保留方式へ移した。
2026年10月に、回答待ちと編集中が同じ`hold`で区別できないとユーザーが指摘した。
未回答UWIへの依存だけを内部依存待ちから除けば回答済みUWIと元項目をprocess-wiの1回の実行で扱えるため、保留方式の目的を保ったまま依存方式へ戻した。
回答が元項目での作業を要さない場合はメインが回答済みのUWIを先に終了する。
その回答を要する元項目を処理するレーンが、ファイル名でterminal状態のUWIを再取得して保存回答を反映する。
標準の2択を持つ事後承認型UWIへ`その対応で問題無い`と回答した場合、回答保存の操作が同時にUWIを`adopted`へ移動し、後続の選定工程での終了操作を不要にする。
各項目の`depends_on`にはその項目より先に終了すべき実在するAWIのファイル名を保存し、先行成果の完了待ちを表す。
依存を保存するのは先行成果なしで安全な実施や完成判定が成立しない場合だけとし、必要性の定義は`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`に置く。
投入側はその判断を保存前に適用し、後続本文へ待つ成果と代替できない理由を残す。
書込の競合、包含、同じ方針の反映や実装順の好みは、レーン内の実装順で扱い、`depends_on`には登録しない。
値は保存済みのメタデータに従い、本文の記述から依存を再構築しない。
メインは依存先をファイル名で全状態・全対象リポジトリへ1回照会する。
現在の対象リポジトリの項目を優先し、無ければ一意な候補の保存済み`target_repo`と状態に従う。
現在の対象リポジトリに無く複数リポジトリに同名項目がある場合は、曖昧性として停止する。
別リポジトリの終了済み依存は充足済み、未終了の依存は`dependency-unmet-external`とする。
リポジトリ別に照会を重ねる案は、同じ名前の解決に複数回の取得を要するため採用しない。
無関係なactive UWIを状態遷移の一律条件にしない。
一致操作後の着手可否は、`depends_on`が全て終了することを確認する。
UWIが回答済みで、frontmatterと計画ファイルが有効であることだけを追加条件とし、同一バッチの候補集合を条件にしない。
AWIプロジェクト固有の公開後の操作の順序は選定結果の`プロジェクト固有の公開後の操作の順序`へ記録し、キューの依存へ実装順序を混在させない。
メインはAWI本文と対象実装を調査し、レーン分割とレーン内の実装依存順を技術判断する。
レーン担当は渡された要求を知る一方、キュー全体の採否や他項目の開始時機を決定しない。

### 前提の鮮度

メインが要求した場合だけ、`target_commit`以後の履歴へ12時間以上前のcommitがあるかを情報として返す。
現行内容との不一致、既存修正による充足、巻戻しの危険のいずれかを観測した項目だけ履歴を調べる。
