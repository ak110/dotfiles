# 原因分析節と保存前の確認の設計記録

[設計記録の索引](design.md)

## AWIの原因分析節と保存前の確認

原因分析は観測した欠陥を起点とする通常AWIの`## 原因分析`節だけへ書く。
WI作成工程の規範が投入前に直接的原因と根本原因の確定を求め、計画工程の規範も同じ分析の記録を独立に求めていたため、同じ分析がAWIと計画ファイル（バグ）の双方へ書かれていた。
後工程が前工程の記録を参照で済ませる手段を持たないことが二重記述の機構であり、記録を前工程側へ1つだけ置き、後工程がそれを参照する手段を設ける。
2026年11月26日以後、計画には原因分析を書かない。
入力にWIが無い依頼は計画を作る時点でAWIを作り、計画時点の観測でWIの分析を訂正・追加する場合は詳細化でWI本文を置き換えるため、どちらもWIの`## 原因分析`が記録先になる。
それより前は、この2条件に限り計画本体の`## 原因分析`へ書き、さらに前は計画ファイル（バグ）へ書いていた。
類似見直しと再発防止の範囲・採否・終了は2026年10月10日のユーザー指示により同スキルへ集約した。
2026年11月の作り替え以後、AWIの`## 原因分析`は5行の記録（`期待:`・`原因:`・`処置:`・`広がり:`・`確認:`）で書く。
同じ内容を新しい節と既存の節の双方へ書かせると、AWIの中で再び二重記述が生じるためである。
`atk wi add`は`## 原因分析`の位置と非空を検証し、必須節の集合へは加えない。
起点が観測した欠陥かは本文から機械判定できないため、必須性は投入前の読み直しで確かめる。
エージェント環境でUWIを保存する場合は、原因の欄に明示した未確定の宣言を共通の保存処理で拒否する。
確定した原因の説明に現れる語やコード例は対象にしない。
原因の妥当性は起草とレビューで確かめる。
人間の入力（エージェント環境外の`atk`と`atk serve`の画面）は拒否しない。
原因分析節や行の存在を必須にする案は、起点が観測した欠陥かを機械判定できない前段の理由により採らない。
計画構造の自動チェックは、作業種別`バグ対応`で`関連WI`が`なし`の計画に`## 原因分析`を求め、`関連WI`を持つ計画には求めない。
却下した代替案は、作り込み要因・見逃し要因の分析を計画側へ寄せてAWIには直接的原因までを書く案と、二重記述を残す案である。
前者はWI作成工程が投入前に根本原因の確定を求める規定と両立せず、後者は起草と計画の手間とAWIの容量の二重化を残すため採らない（2026年9月30日のユーザー回答で「`AWIを正本に`」を選択）。
WI作成工程が投入前に根本原因の確定を求める規定は、`agent-toolkit:atk-mode/references/awi-body.md`「起草完了の条件」にある。

## 規範の読込と共通準備の単位

通常AWIは、全経路で登録可否と既存項目との被覆を本文で比較する。
手動具体化では今回の対象別結論を投入元で確定し、独立別件では確定事実、原因仮説、未確定事項と次の問いを残せる。
保存処理は通常AWIの未確定語だけで拒否せず、UWIおよび移行・復元の既存条件を維持する。

## 効率化の仕組みの棚卸し（2026年11月）

横断的な記録の条件と限界は[設計索引](design.md)の「効率化の仕組みの棚卸し」を参照。

- WI一覧・検索の索引のうち、frontmatter再解析の除去はユーザーの目標超過対策要求への具体化である。
  更新検知・信用待ち・破損時の再走査を保つ。
  保存索引の効果は使う本文量によって違う。
- 回答待ちAWIを依存で表す方式は、2026年10月末の原本本文がholdをやめ依存とblocked表示へ戻す方式を要求しており、専用のhold解除操作を増やさない。
  回答待ちを依存へ一本化した後の独立障害の件数・所要は未確定である（旧状態の区別ができないという2026年10月の指摘がある）。
- WIの保存前検証のうち、一括状態遷移はユーザー要求、editのdry-runは提示案をユーザーがAWI化するよう要求したものである。
  WIの保存前の入力検証・原文保持という品質保護を保ち、保存済み本文の再掲・全文再検査を呼び出し側へ戻さない。
