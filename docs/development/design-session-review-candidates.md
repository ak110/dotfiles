# 人間入力と候補抽出の設計記録

[設計記録の索引](design.md)と[振り返り・知見集約の設計記録](design-session-review.md)から参照する主題別の記録である。

人間の入力の選択は、userロールだけで判断しない。
`atk run-script session-review-evidence`はCodexとClaude Codeの原文と生成標識へ既存のruntime_insertedの判定を適用し、その結果をイベントへ保持してから通常表示の本文を短縮する。
Claude Codeの`origin.kind=plugin`も同じ共通判定へ渡す。
プラグインが実行した裸のコマンドは人間の手入力と本文が同形になるため、記録自身の生成元を使う。
コマンド名や直前の予約からの推定は判定に用いない。
同じ判定を使う表示、先頭発話、終了証拠にも適用し、人間起点と生成元の無い旧記録の既存の扱いを保つ。
会話の流れ、介入候補、初期要求の位置選択と`--user-events`は保持した由来を使い、短縮後に閉じタグが無くなった本文から判定し直さない。
初期要求は人間の依頼で始まる記録では最初の人間の発話とし、`atk wi process-loop`が起動した記録では起動の目的文とする。
起動後に人間が割り込んだ最初の発話は、作業中の是正として候補に残す。
`--user-events`は人間の発話と確認回答だけを全文で返し、スキル展開・環境情報・hookの生成本文を除く。
Claude Codeが中断時に書く`[Request interrupted by user]`と`[Request interrupted by user for tool use]`については本文全体が定型文の記録だけを`--user-events`から除き、介入候補と会話の流れには残す。
介入候補では`references/analysis.md`の`unexplained-refusal`の判定対象となるため、共通の生成本文の判定へは加えない。
`--since`は省略でき、省略時はメイン記録の最初から観測境界までを返す。
呼び出し元が引用する発話より前の時刻を推測して渡していたためである（2026年10月6日の観測）。
人間の長文、手動スキル起動、提示した全選択肢と回答、記録位置および区間境界の扱いは保持する。
表示の短縮を廃止する案と、発話抽出の都度に生成本文を手作業で除く案は、それぞれ証拠量の抑制と逐語引用の目的を損なうため採らない。

`atk run-script session-review-evidence`の観測境界はメイン記録の行と委譲先の開始時刻へ適用する。
境界前に始まった委譲先は境界後の完了結果も含めて分析し、境界後に始まった委譲を候補と統計から除く。
開始時刻が分からない委譲先を推測で除く案は、対象セッションの証拠を失うため採用しない。
境界後に完了した行を一律に除く案も、境界前に始まった仕事の結果を失うため採用しない。

`atk run-script session-review-evidence`の判定は記録側が持つ種別情報に基づける。
`--warn`はフック通知、コマンド実行結果および実行系が返した構造化警告を対象とし、検索結果と取得した文書本文に現れた同形の文字列を警告として扱わない。
あわせて、問題の不在を述べる本文を警告から除く。
`final-result`の分類はCodexの記録が持つ`phase`を参照し、`commentary`のメッセージを最終結果として扱わない。
Claude Codeでは本文より後の作業ツール呼出がある場合を`commentary`とする。
同じエントリの要素順も使い、本文を運ぶsend_to_userと返却のSubagentHandbackは作業の境界から除く。
send_to_userの長い本文は詳細照会で全文を返す。
振り返りの準備は公開前に委譲先の稼働中にも実行され、最後の本文を無条件に最終結果とする形は、稼働中の委譲先の途中発話を委譲返却の候補にしたため採用しない。
表層一致だけで判定する形は、エージェント向け文書の記述例と委譲先の中間報告という実行時の問題でない本文を候補として提示し、原因を確定する工程を増やすため採用しない。

振り返りの候補は、候補が保持する位置の集合を保ったまま除外と集約だけで減らす。
抽出段では構造から正常と判定できる事象を除き（返却の欄名は旧形式の`status:`なども同じ意味で読む）、準備段では別セッションで反復していない失敗を件数表へ送る。
抽出段で除く事象には、想定外事象を持たず正常な完了だけを示す委譲返却、検索が出力なしで一致0件を返した結果および`atk wi add`・`edit`の本文表記診断の警告がこれに当たる。
委譲返却は前置きの文に続く`状態: completed`の返却（再開されず1回の配送で終えた委譲先に限る）と、報告した終了コードが全て0で失敗・警告・診断の件数が無いコマンド実行の委譲を含み、検索はパイプラインの最終段の検索（終了コード1）と検索を起動する`xargs`（終了コード123）を含む。
hookが遮断したツール呼び出しの失敗と、hook通知と同じ本文の警告は、hookの発生源標識または通知本文との一致から出所を確定できる。
このため両者をhook通知の候補として扱い、発生源と区分ごとの上限の対象にする。
上限では件数の多い種類に加えてツールごとの最多の種類を残し、件数の少ないツールの遮断も候補に残す。
反復注記とUUIDは原因を区別しないため、種類の本文から除く。
自由記述の委譲返却や、別セッションで反復し本文から原因が定まらない失敗など、本文の意味の判断を要する事象は候補に残す。
2026年9月26日のprocess-wiの実行の記録には候補が202件あり、見送った候補の多くは成功の定型返却と、hookの遮断による失敗とhook警告の重複だった。
ユーザーが候補の機械的な削減を求めたため、この規則を導入し、同じ記録の候補は100件になった。
再開された委譲先の前置きは除外しない。
受け取り済みの報告の返し直しという異常を前置きだけで述べ、対策へ結び付いた返却が実記録にあったためである。
件数の上限だけで候補を減らす案は採らない。
判定表が候補の位置の集合と一致することを求める検証と両立せず、対策へ結び付く候補も件数の順で除外するためである。

候補抽出はユーザー介入、権限拒否、`続行できない理由:`の行を持つ返却（旧形式の状態値で続行不能を示した過去の返却を含む）、未解決証拠を全件保持する。
失敗した`CommandExecution`は`command-failure`、その他の失敗ツール事象は`tool-failure`、通常の不成功返却は`delegate-return`とし、上位判断を要求する`escalation`から分離する。
通常失敗はコマンド、終了コード、診断、locatorを保持するため、検索不一致など恒久対策を要しない事象を証拠に基づいて一次選別できる。
是正を求める通知はblockかwarnの区分を必ず持つため、それ以外の区分を持つhook出力は機械除外する。
除く区分を既知値で列挙する形は、規範の注入（`kind="rules-main"`など）や配送の種別を`kind`へ持つ新しい出力を是正要求として候補へ残したため採用しない。
hook通知と失敗したツール結果の個別証拠には、同じ呼び出し識別子を持つツール呼び出しの入力と記録位置を加え、対象のコマンドを特定する照会を不要にする。
blockまたはwarnのhook通知は、hook識別子、発動元、タグを発生源として、同じ発生源の通知変種を発生件数降順の上位5種へ限定する。
各変種は安定順の代表locatorを1件保持し、発生総数と省略件数を機械可読フィールドへ残す。
発生源ごとに最低1候補を残し、振り返りでは発火した全発生源へ規範、判定条件、フック撤去のいずれかの改善提案を対応付ける。
全locatorを素材へ載せる形は、同じ原因の反復ごとに本文量と分析量を増やすため採用しない。
応答言語hookの通知（発生源が`pretooluse`か`response-language`、区分が`warn`か`block`で、本文がhook側の本文定数で始まる通知）は機械除外し、件数だけを`response-language-notice`へ数える。
モデル自身が日本語で書き直す遮断後に対処する型であり、候補へ残すと振り返りのたびに同じ見送り判定が報告へ載るためである。
本文定数はhook側からimportして判定し、文言の変更へ追随させる。
同じ`pretooluse`発生源の他の通知は従来どおり候補に残り、発生源ごとに最低1候補を残す扱いはそれらの通知へ適用する。
単独の`atk`が`該当0件:`と終了コード1で返す結果は、生成側の結果行の契約から構造的に正常な否定結果と判定できる。
