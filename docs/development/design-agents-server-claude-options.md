# Claudeのキャッシュと起動設定の設計記録

[設計記録の索引](design.md)から参照する、Claudeのキャッシュと起動設定の記録である。

## プロンプトキャッシュの保持期間

Claude Codeが起動する委譲先のプロンプトキャッシュ保持期間を未設定のままにせず、`share/claude_settings_json_managed.json`の`promptCacheTtl`と`subagentPromptCacheTtl`でメイン会話側とサブエージェント側の双方へ明示する。
Claude Agent SDKで開始する`agents_server`のセッションは、この設定だけでは意図した保持期間にならない。
このため`agent-toolkit/agent_toolkit/_agents_server/claude_options.py`の`_build_options`がenvとsettings.envへ同じ辞書から`mode`ごとの値を渡す。
user・project設定のenvは子の環境変数を上書きするため、CLIの最優先settings層にも値を置く。
SDK自身が読むイベント通知の印にはenvも必要である。
軽量起動はユーザー設定を読み、SDKのターンがmain conversationのrequest bucketとして扱われるため、main conversationのrequest bucketに対する未設定時の保持期間が適用される。
連続する要求の間隔の中央値が6.3秒であり300秒を超える間隔が516件中1件しか発生しないため、5分でも失効せず、書き込み単価の低い5分を指定する。
通常起動は設定読込元を指定していても配下のサブエージェントへ`subagentPromptCacheTtl`が届かず5分で書き込むため、1時間を指定する。
届かない原因は公開資料から特定できておらず未確定とする。
このため、サブエージェント側の未設定時の保持期間が短いことを理由に委譲を減らす設計判断は採らない。
キャッシュ効率を根拠として委譲構造を見直す場合は、実際の計測値を根拠とする。
Claude Codeでの計測値は`~/.claude/projects`配下のセッション記録から`message.usage.cache_creation`の`ephemeral_1h_input_tokens`と`ephemeral_5m_input_tokens`を担当ごとに集計して得る。
集計に用いるフィールド名はClaude Code v2.1.258で確認した。
2026年8月20日以降に開始し、サブエージェント側へ1時間を設定する前の649スレッドを対象とした集計では、Agentツール経由のサブエージェント全体は連続する要求の間隔が300秒を超える場合が3.26パーセントあり、その直後の要求が1件あたり約15万トークンを再度書き込む。
保持期間を5分へ短縮するとこの再書き込みが復活する。
1時間のトークン量に対する相対費用は5分の場合より4.45パーセント低いため、サブエージェント側の設定は1時間を維持する。

## Claudeの起動設定と受信上限

親の`--settings`がJSONなら他キーとenvの他キーを保ち、起動元の全envキーを上書きする。
ファイルの場合は内容をargvへ展開せず、所有者だけが読める起動別の合成ファイルを渡す。
不読・不正JSON・非objectの親は継承せずenvだけを使う。
合成処理と回収は`_agents_server/claude_settings.py`が担当する。
成功・失敗の接続終了と依存確認の終了で自身のファイルを回収し、異常終了後の残存物は既存のrootの7日掃引が回収する。
CLIのstdoutのNDJSONの1行には、モデルへ渡らないtool_use_resultも含まれる。
EditのoriginalFileがファイル全体を持つため、SDKの既定1MiBでは通常の編集だけで受信に失敗する。
共通optionsは全起動区分・resumeへ4GiBのmax_buffer_sizeを渡す。
CLIの最大編集可能サイズ1GiBと差分を収めるための上限値である。
この指定で4GiBを事前に確保することはない。
モデルへの出力量の指示ではこの受信失敗を防げない。

## 効率化の仕組みの棚卸し（2026年11月）

横断的な記録の条件と限界は[設計索引](design.md)の「効率化の仕組みの棚卸し」を参照。
委譲サーバーと委譲先の起動・待機の仕組みについて、主題別の記録に無い由来、実測、判定だけを残す。
実測を記さない仕組みは、同じ代表入力・並行条件で仕組みの有無を比べた全体所要が未測定である。
判定の「単純化」には、以前に独自の方式を撤去して標準の手段へまとめた変更の維持も含む。

- プロンプトキャッシュ保持期間の経路別の明示（本書「プロンプトキャッシュの保持期間」）: 2026年9月の確認回答で、ユーザーがexplore 5mとSDK配下1hの両方を選んだ。
  独自検出の細部まで指定したものではない。
  判定は測定で決めるとし、選択済みの経路別の値を保ち、変えるなら同じ入力で費用と待ちを比べる（2026年11月11日時点で変えていない）
- 待機上限の保持期間・ホスト・背景機能からの導出（[待機上限](design-agents-server-wait-timeout.md)）: 導出する方式は2026年9月2日のユーザー指定で、ホスト別の変換と270秒・1740秒・540秒の数値はエージェントの具体化である。
  旧方式では期限を縮めすぎ、約4分ごとの再発行を繰り返した。
  連動を外す案の測定と不採用は主題別の記録にある
- 待機の一本化（`wait_any`から引数なしの`wait`、CLIの`atk agents wait`へ）と全件1回の返却（[終了時の結果の回収と待機ロック](design-agents-runtime-results.md)）: ユーザーは2026年9月10日に「waitの引数なしに統一して」と指示し、9月15日に未回収の終了結果を複数まとめて返す方式を指定した。
  CLIへの移行の個別の由来は未確定である。
  待機機構群の障害報告14件は旧公開操作や保留状態の事象を含み、CLIへの一本化だけの件数は確定していない。
  判定は維持とし、引数なしの一括返却を保ち、旧待機操作は戻さず、再開状態の内部整理とは分ける
- `atk agents wait`の出力への結果本文の直接表示（[長い出力の自動保存](design-cli-auto-save.md)）: ユーザーは結果受領の手順の簡潔化を求めた。
  label、本文ファイル、直接表示と閾値はエージェントの具体化である。
  判定は単純化
- `start`の最初のモデル出力での応答（[公開ツールの起動契約](design-agents-server-start.md)）: 2026年9月26日に毎回15秒待つ観測からエージェントが起草した方式で、ユーザーの方式指定は無い。
  起動・可用性の機構群で少なくとも9件の報告がある（旧方式の3回各180秒、6回各90秒の打切りなど）。
  判定は単純化とし、起動待機の延長で対処せず、起動・保留・再開の所有をそろえる作業項目へ引き継いだ。
  同項目（2026年11月11日）は保留と自動再開の状態を扱い、起動時の応答は変えていない
- 結果の保留と自動再開（[再開状態の棚卸し](design-agents-server-resume-simplification.md)）: ユーザーは2026年9月に自動再開、10月に自動リトライ、11月に子と孫の自動復旧を求めた。
  予約・保留の状態と回数は個別の具体化である。
  保留・再開の機構群で少なくとも10件と帰属不明2件の報告がある（3回各10〜40分、32分の停止など）。
  判定（測定で決める）と候補ごとの採否は主題別の記録にある
- 軽量起動（`explore`・`shell`・`write`）と`start`への統合（[軽量起動と継続不能](design-agents-server-lightweight.md)）: 軽量モデルの既定、`start_shell`の追加、start系の統合はユーザー指定で、`write`自体の初期要求は特定できていない。
  2026年10月19日の工程別モデル割当の不一致（15起動）は、軽量起動に固有の障害件数としない。
  判定は維持とし、独立評価と書込所有権を保つ
- 起動時の規範注入と軽量起動向けの短節（[委譲先への指示と規範配送](design-agents-server-instructions.md)）: 主体別の規範をhookで起動時に注入する方式と、自動注入を全てタグで囲む方式はユーザー指定である。
  Codexへの追加配送は観測を起点とした是正である。
  判定は維持とし、重複配送と記録先の二重付与は別の欠陥として扱う
- 定期再確認の`start`内の自動装着（[定期再確認の装着と回収](design-hooks-periodic-recheck.md)）: 2026年10月6日にユーザーが起動後hookでの自動注入とmodによる定期再確認を提案し、Cronの内部操作はエージェントが選んだ。
  定期再確認の機構群で3件の報告がある（装着されない警告、残ったtaskで終了確認に止まる例など）。
  判定は測定で決めるとし、保持期間への連動を保ったため、間隔の決め方と自動装着は変えていない（2026年11月11日）
- API残高不足の観測のプロセス内1時間の共有（[接続選択とAPI残高不足](design-agents-runtime-connections.md)）: 2026年10月の実会話でユーザーが非永続化と定期再確認を求め、1時間の保持はエージェントの判断である。
  専用の初期WIは特定できていない。
  判定は維持
- 配布物の保持実体の共有、共有実行環境、ウォームアップ（`design-storage.md`「配布物の保持実体の共有」）: 容量とvenvの重複の削減はユーザー要求で、保持実体と環境の共有は具体化である。
  独立工程の並列ウォームアップはユーザーの並列化要求に由来する。
  3rootの並列ウォームアップは、交互に各3回測った中央値で11.594秒から4.553秒になった（10月30日の記録）。
  同じ依存keyの2targetで準備を共有した対照は各1回で0.470917秒から0.345644秒、prepareの起動は2回から1回で、負荷の固定は記録に無い（10月26日の記録）。
  どちらも共有実体そのものや更新全体の対照ではない。
  共有実体と再読込を含む機構群で少なくとも4件の報告がある（約85秒の起動不能、30秒上限、inotify 94件と上限128など）。
  判定は測定で決めるとし、並列ウォームアップは維持し、実施結果は主題別の記録にある
- 上り通知（[agents_serverの上り通知](design-agents-runtime-notifications.md)）: 委譲先から呼出元へ通知する機能はユーザー要求で、CLIと共有ディレクトリという媒体は具体化である。
  判定は維持とし、同じ完了報告の二重送信には使わない
- 起動失敗の短時間の観測（[起動失敗の観測と無人起動](design-agents-runtime-preflight.md)）: 起動失敗後の空待ちの防止と短い初期化上限はユーザー要求で、最終の50秒・150秒は実測に基づくエージェントの補正である。
  判定は維持
- 引き継ぎ記録先の自動付与と明示指定の共有（`design-delegation.md`「多段工程の委譲の引き継ぎ記録」）: 2026年10月17日にユーザーが引き継ぎ記録の自動生成と軽量起動の除外を提案した（導入は10月18日の`fae7c9a6d`）。
  明示のパスと別のパスを二重に付与する欠陥は要求に含まれず、同じ不具合を4起動で報告した。
  判定は維持とし、二重付与の是正だけを作業項目へ引き継いだ
