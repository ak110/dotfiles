# 共有管理サービスと世代移譲の設計記録

[設計記録の索引](design.md)から参照する、MCP接続と管理・実行資源の寿命を分ける記録である。

## 接続と管理の分離

同じOSアカウントと状態領域の接続は、共有管理サービスを使う。
転送側へManager、backend、MCP SDKを読み込む方式は採らない。
接続ごとの管理処理と監視の重複を減らし、接続切断だけで委譲先を停止しないためである。

別会話の設定・認証候補・クレジット不足の観測を混ぜず、サービス起動者の環境で不足値を補わない。
認証値はIPC内の非永続contextに限り、世代登録・ログ・再開情報へ保存しない。
接続EOFは接続だけを外し、実ホストの死亡はPIDと起動世代で判定する。

## 管理領域と通信

同版の準備は合流し、遅れて成功した旧準備で受付先を戻さない。

受付先の世代のプロセスが終了し、生存する公開済みの世代が残る場合は、生存する最新の世代へ受付先を戻す。
生存する公開済みの世代が無い場合は受付先を変更せず、転送側が受付先のrootから同じ世代を起動し直す。
生存する世代が受付先を戻す処理を持たない旧版でも受付先を戻す。
戻さないと、その世代の会話の保存は終了した受付先への転送で失敗し続ける。

`update-dotfiles`の起動確認は、管理サービスを確認用のMCP接続とは別の子プロセスから、公開を保留して起動する。
WindowsのMCP SDKは確認用の子プロセスを離脱不可の`KILL_ON_JOB_CLOSE`のJobへ入れるため、確認用の転送側から起動した管理サービスは確認の終了とともに止まる。
確認用の接続と子プロセスの終了後に候補の世代の生存を確かめてから、`service_forward.publish_service`で受付先として公開する。

Windowsの転送側は、起動元のJobからの離脱を指定して管理サービスを起動する。
SSHのセッションは所属プロセスを離脱可の`KILL_ON_JOB_CLOSE`のJobへ入れ、venvの`python.exe`は子を自動で離脱させるJobをその内側に作る。
離脱を指定しない子は外側のJobに残り、セッションの終了とともに止まる。
離脱を許さないJobの中では指定した起動が拒否されるため、所属を継承して起動し、そのJob終了後の生存を保証しない旨を診断へ残す。

LinuxはAF_UNIXのabstract socketを使い、環境や操作本文を送る前にSO_PEERCREDで相互のUIDを照合する。
Windowsは現在SIDだけを許可する明示DACL付きnamed pipeを使い、remote接続を拒否する。
発見記録だけの認証、無認証loopback、独自の共有秘密を保存する方式は採らない。

## 受付・状態writer・実行資源の移譲

受付先、会話の制御所有者、raw資源の生成元は別々に扱う。
raw資源は元世代が維持するSDK・App Server接続、生イベントはその接続からの未解釈イベントを指す。
実行中turnの解釈と制御は旧世代に残し、同じhostへ世代別のwriterを並立させない。
状態ファイルは受付先の世代が、親会話ごとに各世代から受け取った観測を重ねて書く。
公開する世代は準備の応答で旧世代の観測を受け取り、受付の公開後に状態ファイルを書き直す。
この書き直し、保存、旧世代の観測が外れた後の書き直しは、親会話ごとの同じロックを取った後の観測から書く。
ロックの外で選んだ観測を書くと、ロックを待つ間に保存された進捗やeffortを古い値へ戻す。

公開する世代は旧世代へ準備（`prepare_update`）を求めて保存と新turnを静止させ、受付の公開後に確定（`commit_update`）を通知する。
旧世代の静止を解くのは、準備1回ごとの監視taskだけとする。
監視taskは確定の通知、受付先の前進、公開元のプロセスの終了のいずれかを待ち、準備が静止を掛け終えてから解く。
先に解くと、後から掛かった静止を解く主体が残らない。
公開元は受付を公開した後で必ず確定を送るため、世代索引の受付先が自世代より新しい世代へ進んだことは確定と同じ意味を持つ。
確定の接続が一時的な通信の失敗で届かなくても、旧世代は常駐する公開元の終了を待たずに静止を解く。
公開元が確定を通知せずに終了した場合は、受付先を生存する世代へ戻してから解く。
解除済みの準備へ遅れて届いた確定は捨て、終了した世代へ受付を向け直さない。
静止中は共有監視の周期処理も保存の待機で止まるため、監視taskは周期処理と独立に公開元の生存と受付先を確かめる。
生存する公開元が確定を通知せず受付先も進まない間は、準備中の引継ぎを失わないよう時間では解かない。
旧世代は監視taskが静止を解くまで退出せず、受付先の切替の直後に届く確定の接続を閉じない。
受付先の前進で静止を解いた旧世代は確定より先に退役することがあり、この仕組みより前の版の旧世代は確定を待たずに退役する。
世代は担当会話、raw資源、受入中の移譲、取り込み待ちを残さずに終了した場合だけ世代索引へ退役を記録する。
停止の要求や例外で終了しても、それらを持っていれば記録しない。
公開元は確定が届かなければ、旧世代が生存する間は同じ確定を送り直す。
確定の受理は冪等で、解除済みの準備へ届いた確定は捨てるため、送り直しても静止の解除は1回に限られる。
進行中のturnを持つ旧世代は確定を失っても受付先の前進で静止を解いて動き続け、turnの終了後に会話を移してから退役する。
公開元は旧世代の退役を待たず、確定の配送か退役の記録で公開を完了する。
確定が届かなかった旧世代が退役を記録していれば、公開元は確定を済んだものとして扱う。
退役の記録が無いまま終了した旧世代は、会話や実行資源を新世代へ移さずに失ったことがあり得るため、公開の失敗として返す。
初回の確定RPCの応答待ち、再送の間隔、再送の応答待ちは、初回の送信から10秒の期限を共有する。
期限までに配送も退役も確認できなければ、最初の失敗（初回の応答が間に合わなければその期限切れ）を返して公開ロックを解く。
静止を解いた後は終了境界で止めた会話を受付先の世代へ移す。
受付先が自世代のままか自世代へ戻った場合は、止めた接続を取り込み直してdecodeを再開する。

旧backendの実turn終了と保存完了後に、全`SessionState`、待機圧縮などの補助状態、raw資源参照を新世代へ移す。
新世代が以後の解釈・保存・次入力を所有し、旧世代は生I/Oとイベントだけを提供する。
新世代は受け取ったsessionのraw資源を取り込み、状態を保存してから制御を受け付ける。
保存の失敗などで残った取り込み待ちは、周期処理と次の操作で取り込みと保存をやり直す。
保持期限や会話の回収で本体を解放した後の取り込み待ちは、取り込み済みのraw資源を解放が回収し、再開情報が会話の文脈に残るため、失うものが無いとして終える。
未取り込みのraw資源は、制御を引き継いだ世代が元のbrokerで閉じ、読み手のいなくなったイベントも破棄する。
破棄の応答を受け取るか、closeの応答後に元のプロセスが終了したことを確認してから待ちを終える。
回収を確認できなければ、待ちを残して次の周期でやり直す。
受付先の変更でraw資源のoriginは付け替えない。
子やバックグラウンドタスクが終了し、次の本来の入力を送る境界では通常のreleaseを経て新SDK・App Serverでresumeし、元の資源を回収する。
移譲のためのquery、中断、追加promptは送らない。
3世代以上でも次入力時の現行世代を再解決し、中間世代を経由するだけのモデル呼び出しを作らない。

所有移譲のcommit応答が失われた場合は同じ移譲IDの受理状態を照会する。
移譲先も消失して成否を確定できなければ、安全側に閉じて成否不明を返す。
旧decoderの再開や無条件再送で二重実行を起こさず、既存登録簿とbackendの物理記録による復旧へ渡す。
健康な旧raw資源の提供者を`owner_lost`障害として扱わず、実障害時の所有確認・保留・未回収結果の保持条件を維持する。

## 寿命と初回移行の境界

定常時の管理面は、接続数Nに対して接続ごとのuvと転送、および共有の診断supervisorとserviceで2N+2プロセスとなる。
backendプロセスと更新中の旧世代は別に数える。
旧世代は担当会話、受付処理、静止を解く前の準備、保存ACK前イベント、raw資源が残る間は保持し、期限だけでは停止しない。

退役の記録による公開の判定には、次の既知の制限がある。

- 退役の記録を引き継ぐものの有無で分ける仕組みより前の版の旧世代は、終了の理由によらず退役を記録する。
  その版からの更新では、会話を持ったまま停止や例外で終わった旧世代を公開の失敗として検出できない。
  この場合も中断したturnは、新世代からの`show`で`status=interrupted`、理由`owner_server_stopped`として確認できる。
- Windowsで外部から終了させた世代は強制終了となり、終了処理が動かないため退役を記録しない。
  確定を受け取る前に外部から終了させた旧世代は、引き継ぐものを持たなくても公開の失敗として返る。

共有サービスを持たない旧stdioからの初回移行は、起動中の会話が自然終了するまで旧接続を保持する。
旧版にはRPCと状態exportがなく、Claude Code・Codex双方の自動再接続も未観測であるため、会話途中の暗黙移譲はこの初回範囲では達成できない。
旧stdioへSIGTERMを送らず、旧側の待機・通知・結果回収を残し、新しい通常MCP起動から共有サービスを使う。
共有サービス導入後の更新には前節のturn終了による暗黙移譲を使う。
