# セッションの自動更新と表示分類の設計記録

[設計記録の索引](design.md)と[画面統合とセッション・計画一覧の設計記録](design-serve.md)から参照する主題別の記録である。

## セッション画面

### 自動更新と右ペイン

セッション画面の自動更新は、記録のrootの変更を監視して`/api/sessions/events`へ通知する。
ローカルはサーバーが`claude_home`配下の`projects`と`codex_home`配下の`sessions`をwatchdogで再帰的に監視する。
起動時にrootが無い場合は存在する最も近い祖先を非再帰で監視し、rootの作成を契機に監視を登録し直す。
リモートホストは常駐接続のヘルパーが同じ2つのrootを監視し、変更を応答と同じstdoutへ行で書き、サーバーがSSEへ中継する。
変更は短い時間窓でまとめて通知する。

通知の種類は、一覧の再取得を促す`refresh`と、記録1件の更新を示す`record`（host・engine・pathを含む）の2つとする。
`refresh`を送るのは一覧に載る項目の集合か表示する値が変わり得る変更に限る。
記録の作成・削除・移動と、除外中の記録にユーザー発話が現れた変更がこれに当たる。
一覧に載っている記録への追記では`record`だけを送る。
一覧の応答は800KB程度あり、進行中のセッションが追記するたびに再取得させると転送量と描画の負担が大きいためである。
監視側は記録ごとの発話の有無を一覧の取得時に引き継ぎ、未知の記録だけを変更の観測時に読む。
発話は追記で消えないため、一度発話ありと判定した記録は再び読まない。
購読者の未配信の通知が溜まった場合は、`refresh`の1件へまとめる。
クライアントは`refresh`で一覧と選択中の記録を取り直すため、まとめても取りこぼしは生じない。

選択中の記録と同じhost・engine・pathの`record`を受けると、右ペインは詳細を取り直して描き直す。
描き直しでは展開中のイベントの開閉、描画した件数およびスクロール位置を保つ。
記録のイベントは先頭からの順で並び、追記で既存の位置が変わらないため、開閉状態は位置で対応付ける。
サブエージェントの記録を開いている場合も、開いている記録自身の更新で追随する。
詳細の取得は世代で管理し、選択の切り替え後に届いた古い応答を反映しない。
一覧の通知だけで右ペインも取り直す案は、他の記録の追記でも詳細を取り直すため採らない。
末尾を読んでいるエンドユーザーには追記した末尾へ追従し、末尾より上を読んでいるエンドユーザーには位置を保つ。
常に末尾へ移る案は、読み返している位置を奪うため採らない。

親の推定費用を表示中は、一覧の親子情報から子孫と確定した記録の`record`でも詳細を取り直す。
親自身が更新されなくても子の使用量が増えるためである。
関係しない記録では取得せず、一覧の再取得も加えない。
同時に届く通知の詳細取得は既存の`coalesced`で合流し、連続更新で同じ計算を並行して繰り返さない。

右ペインは記録の先頭100件を描画し、描画済みのイベントの末尾から400px以内まで読み進めると、続きを100件ずつ操作なしで描画して記録の最後まで到達させる。
追加の描画ではスクロール位置を動かさず、読み進めた先のイベントを読ませる。
末尾より上を読んでいる間に届いた追記は通知せず、エンドユーザーが末尾まで読み進めた時点でこの描画で現れる。
続きを描画するボタンと新着の件数を示す通知は、エンドユーザーが不要とした（2026年10月6日）。
末尾まで読み進めれば自動の描画と追従で新着へ到達できるため、通知が無くても新着へ届く。

詳細API（`/api/sessions/detail`）はイベントを件数で切り詰めず全件を返す。
記録の読み込み量はバイト数の上限`MAX_RECORD_BYTES`が抑え、ローカルもリモートも記録全体を解析してから応答を組み立てるため、件数の上限はサーバーの読み込みと解析の量を減らさない。
応答量も件数よりイベント本文の長さで決まり、5,454件の記録で上限を外した応答の増加は約10%だった。
初期表示の負荷は右ペインの段階的な描画で抑える。
開始位置と件数を指定して続きを追加取得する案は、サーバーとリモートヘルパーが指定位置と使用量の合計を求めるために記録の全文を読む必要があり、短縮できるのは転送量だけである。
一方で右ペインに追記のたびの取り直しと取得済み範囲のつなぎ合わせの状態管理が加わるため採らない。

計画ファイル画面とセッション画面のペイン高さは、ヘッダーの実際の高さへ追随させる。
ヘッダーの高さを固定値の変数で見積もる方式は、ヘッダーが折り返す幅で実際の高さと一致せず、ペインの下端に余白の不足または過剰を生じるため採用しない。
あわせて、セッション画面の本文は計画ファイル画面の本文と同じ基準の文字サイズで表示し、右ペインの本文へ計画ファイル画面と同じ最大幅と左右の余白を適用する。
両画面は同じ読み物として続けて閲覧されるため、文字サイズと余白が画面ごとに変わると読み手が視線の基準を取り直す必要が生じる。

### 表示の分類

セッション画面の右ペインは、`kind`が`assistant`のイベント（アシスタントの発言）だけをMarkdownとして整形して表示し、他の種別は`<pre>`の等幅表示を保つ。
整形はサーバーの`/api/sessions/detail`がWI本文と同じ生HTML無効の`markdown_it`の設定で行い、イベントへ`html`を加える。
`text`は残す。
サーバー側で整形すると、リモートホストの記録も生データを受け取った後にサーバーで同じ整形を受けるため、リモートのヘルパーを変えずに済む。
生HTMLを無効にした整形は記録の本文に含まれるタグを文字として出力し、`javascript:`をリンクへ変換しないため、画面へ挿入しても記録の本文のスクリプトは実行されない。
整形を`session_record_format.py`の表示モデルへ持ち込まないのは、同じモデルを`agents_server`のログ出力が使い、`markdown_it`への依存とHTMLをそこへ混ぜないためである。
整形の対象を`assistant`に限る理由は、思考・要約が画面で別のラベルを持つ内部の推論であり、ツールの入出力、挿入本文、ユーザーの発話は記号をそのまま読む本文だからである。
整形した本文の長いコード行と幅の広い表は、本文の中で横スクロールさせて右ペインの横幅を超えさせない。

セッション画面の本文は、実行環境の挿入本文を`injected`として初期状態で折りたたみ、通常の`user`・`assistant`・`developer`を最初から展開する。
`injected`は既存の折りたたみイベントと同じアコーディオン操作で全文を読める。
判定はClaude Codeの`isMeta`・`turnCompanion`と、userまたはdeveloper本文の接頭辞を使い、review-sessionの証拠抽出と共通モジュールへ集約する。
ロールだけで分類すると、同じロールへ実行環境が書いた本文がユーザーの発話を埋める。
一覧では発話プレビューを描画せず、最初の発話の検索値だけから挿入本文を除く。
発話の有無は記録行のロールで判定するため、挿入本文だけの記録も一覧に残る。

`system`という表示種別は設けない。
2026年9月8日にClaude Codeのtranscript 2,544件とCodexのrollout 7,741件を対象として`"role": "system"`を検索し、一致するファイルが無いことを確認した。
Claude Codeの`type`が`system`である記録は運用通知である。
内訳は`stop_hook_summary`・`turn_duration`・`api_error`・`scheduled_task_fire`・`compact_boundary`である。
残りは`local_command`・`informational`・`agents_killed`・`bridge_status`である。
いずれもシステムプロンプトを保持しない。
Claude Codeの運用通知を本文へ表示する案は、1セッションあたりの表示件数を大きく増やす一方で、エンドユーザーが読む対象である指示と発話を埋もれさせるため採らない。
記録に現れない種別のために表示種別、ラベルおよび初期の開閉を先行して設ける案も、観測できない条件のための恒常的な分岐を増やすため採らない。
