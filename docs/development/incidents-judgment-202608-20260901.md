# 障害・欠陥の記録: 誤判定と検証不足（2026年8月〜2026年9月1日）

[誤判定と検証不足](incidents-judgment.md#誤判定と検証不足)の事例を発生時期別に収録する。

- 2026年8月: `agent-toolkit/rules/`配下へスキルの`references/`と同じ構成のサブディレクトリを作成し、
  サブディレクトリに置いたルールファイルは常時ロードされないと思い込んだ。
  実際には常時ロードの対象である。
  直接原因: rulesとスキルの構成を同一視し、配布一覧の生成条件を実物で確かめなかった。
  `scripts/gen-install-files.py`はrules直下の`*.md`だけを列挙するため、サブディレクトリのファイルは配布先へ届かない。
  対策: `agent-toolkit/rules/`配下をフラット構造で維持する規定と、その理由をagent-toolkit-editスキルへ記す

- 2026年8月: 既存commitのPR作成・マージ・CI検収だけを行うリリース専用依頼でも、`operate-ak110-projects`が姉妹プロジェクトへの波及調査を開始した。
  直接原因: リリース作業をスキルの起動条件へ追加した一方、判定手順は同期対象の変更有無を判定せず一律に波及調査を要求していた。
  対策: スキルの起動は維持し、既存commitのPR作成・マージ・CI検収だけを行い、現行セッションで同期対象を変更・計画・レビューしていないと確認できる場合だけ波及調査を開始しない境界と、確認不能時に既存手順へ進む契約テストを追加する

- 2026年8月: CI待機がSHAのみで監視対象を識別し、過去実行やpush先を取り違える構造欠陥があった。
  直接原因: 監視対象の識別子設計がSHA単独だった。
  対策: リポジトリ・ref・SHAの組で識別

- 2026年8月: GitHub APIの`204 No Content`を「無効」と誤読した（実際は「有効」）。
  直接原因: 公式リファレンスを確認せずステータスコードの意味を推定した。
  対策: HTTPステータス・APIフィールドの意味は公式リファレンスで確認してから引用する（厳守規定化）

- 2026年8月: WebFetchの要約が原文と異なる数値を返し、誤った原因分析が転記されかけた。
  直接原因: 要約出力を原文と比べずに引用した。
  対策: 数値引用時の原文確認を明記

- 2026年8月: 依頼側の観測値と実際の測定値の不一致を条件差で説明して前提を維持し、誤記述が公開文書と姉妹プロジェクトへ波及した。
  直接原因: 矛盾を解消する追加の検証をしないまま前提の成否を確定した。
  対策: 矛盾を追加の検証で解消してから前提を確定する（厳守規定化）

- 2026年8月: WIの提示素材が計画の実施内容へ正しく統合されているかを計画のレビュー担当が実体と比べられず、
  誤った不一致指摘が成立した。
  直接原因: 原文が起動文にだけ存在し、起草担当とレビュー担当が同じ保存項目を独立に取得して比べる仕組みがなかった。
  対策: 計画は元ファイル名と実施内容の採否・範囲・理由を保持し、調査担当は担当ファイルを取得する。
  起草担当と初回計画レビュー担当は、WI由来素材があるときだけ
  全キューIDを`atk wi show <filename>... --target-repo=<repo> --skip-pull`で一括取得して構造化情報が一致するか確かめる。
  再レビュー以降は更新済み計画に従い、キュー原文を取得しない

- 2026年8月: WIの投入元を二値分類し、個別のWIへ対応付けられない人間由来根拠を採否条件にしたため、
  方針改訂要求と適合する検証手段を含む提案が誤って不採用になった。
  直接原因: 任意文字列である投入元識別子をユーザー認可の根拠へ変換し、提案成立性のチェックを生成工程別の優先順位と混同した。
  対策: 投入元識別子を改変せず受け渡し、全起点共通の提案成立性のチェック後に生成工程別の優先順位を適用する二段階へ再設計

- 2026年8月: Codexがサブエージェントを利用できないという未観測の旧前提、無効設定および限定ホストを想定し、
  `agent-toolkit:process-feedbacks`へメイン主体のフォールバックを残したため、通常型AWIの`feedbacks-planner`の呼び出しが一意に定まらなかった。
  直接原因: 変更対象に含まれる既存フォールバックを明示要件、規範的制約または観測済み欠陥へ再対応付けず、
  安全側の複雑性として維持した。
  対策: Claude CodeとCodexのpickerをメインが設定モデルへ直接委譲し、`feedbacks-planner`は1つの通常レーンの計画起草と計画レビューだけを担当する。
  定義欠落、写像不能および起動失敗は別手段へ迂回せず失敗として返す。
  変更対象の既存フォールバックも根拠へ個別に対応付け、対応先がないものを撤去する厳守規定を追加。
  後継方針（2026年9月3日）: 計画起草と計画レビューの調整はメインが直接所有し、中間の調整担当を置かない。
  定義の欠落と写像不能は適用対象が無くなり、起動失敗を別手段へ迂回せず失敗として返す扱いだけを維持する

- 2026年8月: Codex互換手順の追加で、起動条件が現行agent定義へ適用できず、典拠から導けない写像表と独立して失敗し得ないテストを同時に導入した。
  直接原因: 新しい適用条件・典拠・自動チェックを、対象集合と引用元の適用範囲を比べずに確定した。
  対策: 識別子複製を検証する契約テストの追加、生成物側の自動チェックが検出する差分を明示する規範追記、
  および起動条件・agent定義・工程キーのいずれの変更でも対応関係を比べる人手確認の追加

- 2026年8月: 計画時に実行した検索の結果をdetail側へ残さず、別コンテキストの実装で変更対象が漏れた。
  直接原因: 検索の実行だけを要求し、対象範囲、一致・不一致結果、対象判断を実装契約へ保存する規定がなかった。
  対策: detail側へ検索範囲、実行コマンド、範囲へ影響する結果、対象判断、文面成果物の修正後全文を記録する

- 2026年8月: 人間向け計画メイン側へ素材・要求・履歴の合成ID表を残し、ユーザーがIDの対応付けをしなければ実施内容と採否を判断できなかった。
  直接原因: 人間の合意確認、監査トレーサビリティ、実装引継ぎを同じ固定表と合成IDで表現した。
  対策: メイン側を実施内容、由来、採否、非採用理由へ限定し、元ファイル名、ユーザー発言の逐語文、detail側の具体的証拠へ役割を分離する

- 2026年8月: Codexがユーザーの明示的な指示より共有規範を優先し、下位規範を再適用した。
  直接原因: `agent-toolkit/rules/01-agent.md`の「厳守規定は例外なく従う」「規定どおり適用する」および「手順どおりに進められない場合」の無条件表現が、
  同じ文書の優先順位判定より先に局所適用できる構造だった。
  背景原因: （観測範囲）Codexの実行環境でこの事象を観測した。
  Claude Codeで同じ事象を観測していないが、観測範囲外の発生有無は確定しない。
  対策: 優先順位を全ての規範の適用時に共通の前提として先に適用し、ユーザーの明示的な指示が下位規範を上書きした場合は下位規範を再適用しない。
  エージェントが規範を過剰と判断しただけの場合は、規範を適用したうえで改訂を提案する

- 2026年8月: Claude実行時に`ListAgents`が一覧に掲載されても実際の呼び出しが拒否される場合のfallbackに不備があった。
  直接原因: fallbackへ、起動元が保持したプロセス識別子が含まれていなかった。
  対策: 掲載と呼び出し成功を別条件とし、失敗時に所有識別子だけを補助照会へ使い、名前一致単独の判定を禁止する

- 2026年8月: 複数委譲先の能力の比較で契約不足が判明した。
  直接原因: 委譲先の能力を、対象ごとに異なる機械照会または自己申告で比較し得る契約だった。
  対策: 全対象への同一機械照会を比較条件とし、揃わない場合を未検証として返す

- 2026年8月: CIのbaseline作成で値を取る`--write-baseline`を値なしで指定し、存在しないディレクトリ指定オプションを推測した。
  直接原因: push手順が保存先JSONファイルの形と決定主体を示さず、オプション名だけを記載していた。
  対策: 管理対象一時領域配下に呼び出し側が決める更新refごとの一意な`.json`絶対パスを手順へ明記する

- 2026年8月: プロセス稼働判定がプロセス情報の取得不能を稼働中の根拠として扱い、他ユーザー所有プロセスの
  実行ファイルパスを常に取得できないため、対象が停止中でも復元処理が恒久的に延期され続けた。
  直接原因: 取得失敗時に安全側の結論を採用するフォールバックの母集団を保護対象への到達可能性で定めず、全プロセスへ適用し、
  実環境での判定結果を実際に動かして確かめずモックだけで確定した。
  対策: 判定母集団を自ユーザー所有プロセスへ限定し、安全側フォールバックの母集団限定と実機での動作確認を
  コーディング規範へ明記

- 2026年8月: `process-loop --worktree`が現在ブランチの有効な追跡先を持つ対象でも、`refs/remotes/origin/HEAD`が無いことだけで実装セッションを起動しなかった。
  直接原因: 上流ブランチを補助refだけで解決していた。
  対策: 現在ブランチの追跡先を優先し、利用不能時だけ`origin/HEAD`へ後退する

- 2026年8月: 日付境界を持つ順序条件で、境界日後の項目が境界日以前の終了処理と同じ`start-processing`集合へ混入した。
  直接原因: 条件記載項目からの一方向の依存だけを設定し、後続項目を終了項目へ依存させなかった。
  対策: 境界日前・終了・境界日後の3群を依存へ写像し、日付帰属または公開先マージ条件を確定できない場合はUWIへ送る

- 2026年8月: Docker検証で作業ツリーを別の絶対pathへbind mountした結果、ホスト側で作成した実装worktreeの可視性を検証主体から推測できない状態になった。
  直接原因: コンテナーの`working_dir`・bind mount先と、managed-tempを作成する実装主体の絶対pathが同一であることを事前に確認していなかった。
  背景原因: （観測範囲）GLATasksでは`${PWD}:${PWD}`設定と`/home/aki/glatasks`の同一絶対pathbind mountを確認したが、`/tmp`の可視性を全環境へ一般化しない。
  対策: 別namespaceへworktreeを渡す実装レーンだけ、全消費主体から同一絶対pathへ到達できる既存ディレクトリを読み取り専用で確認してから`create --root`を使い、確認できない場合はレーンを開始しない

- 2026年8月: ホスト機能の可否を調べる調査で公式ドキュメントもWeb検索も取得せず、CLIヘルプと
  実行ファイルの文字列解析を31回のツール呼び出しで続け、決定的な機能（フック出力による
  セッション名の設定）を自力で発見できずユーザーのURL提示を要した。
  続く振り返りでも、提案を最小十分な形へ縮小する過程でWeb検索の観点を是正手段から除外し、
  ユーザーの再指摘を要した。
  直接原因: 手段の不在に関わる調査で一次資料の確認と検索を先に行う手順が起動契機に無く、
  提案の縮小規定が反映先と分量に加えて是正手段の削減にも働いた。
  対策: 振り返りの提案縮小で是正手段の集合を減らさない規定を追加し、
  ホスト機能の可否判定を`agent-toolkit:agent-standards`の起動契機へ加える改訂をAWIへ投入した。
  再発（2026年10月）: ツール呼び出しより前の地の文が画面へ届かない事象で、WI投入担当はAPIとホストの挙動を原因と確定して回避策を設計し、根拠はClaude Code本体の文字列検索とセッション記録の集計だけだった。
  委譲元のメインと翌日のセッションのメインも本体の検索だけで同じ主張を確かめた。
  同じ挙動は公式ドキュメント「Thinking」の節「Progress updates between tool calls」に記載され、同じ事象はIssue `anthropics/claude-code#95764`として報告されていたが、ユーザーがIssueを示すまでいずれの主体も調べなかった。
  （前回の対策で防げなかった条件）読込の契機で読まれる`investigation.md`の外部の挙動の箇条は公式一次資料と実機再現を択一とし、実機再現だけで条件を満たせた。
  公式資料と既知の報告の確認を求める`root-cause-analysis.md`の箇条は条件が上流の変更に限られ、拡張原因分析の節にあった。
  （再発の対策）上流の確認の箇条を上流の挙動全般へ一般化し、提供元の公開Issueトラッカーの既知の報告を加えて全てのバグの初動で読む`initial-analysis.md`へ移した。
  `investigation.md`の箇条は公式一次資料を先に確かめ、実機再現と実装の読解で補う順序へ書き換えた。
  `.claude/skills/develop-dotfiles/SKILL.md`「ホスト本体のバイナリの検索」の冒頭へ、本体の検索が公式資料と既知の報告の確認を補う手段であることを加えた

- 2026年8月: 振り返りの証拠抽出器が、Codexホストの委譲呼び出しをMCPツール名の完全一致で判定し、JavaScript本文を評価してツールを呼び出すexecツールの入力へ埋め込まれた実記録の呼び出しを認識しなかった。
  委譲先の記録が実在しても走査対象数は0だった。
  直接原因: 抽出条件を、対象ホストの実記録を確かめずにMCPツールの呼び出し仕様から想定した形状で定義し、契約テストも同じ想定形状だった。
  対策: 抽出条件をホストの実記録に現れる格納形状で定め、契約テストを実記録と同じ形状にする

- 2026年8月: 同じ証拠抽出器が、委譲先の識別子へ実行系を必須キーとして与えたため、実行系の指定を伴わない継続・停止の呼び出しで得た識別子を誤った実行系で解決し、解決済みの記録を未確認範囲として重複報告した。
  直接原因: 実体の所在を決める属性を識別子と同格の必須キーとして扱った。
  その属性を取得できない入力があることも設計へ反映しなかった。
  対策: 属性を探索先を選ぶヒントへ降格し、両方の実行系を探索してから未解決と判定する

- 2026年8月: 同じ証拠抽出器で、可変長の値を取るオプションが後続の位置引数を取り込み、対象記録が未指定のまま代替出力を終了コード0で返した。
  同型の呼び出しが1セッションで16件発生し、証拠を取得できないまま分析が進んだ。
  直接原因: 必須入力の欠落と、記録を読めたが形式を判定できない状態を同じ出力と終了コードで表現した。
  対策: 可変長の値定義を撤去して順序を前提とする条件を除き、必須入力の欠落を終了コード2で返す

- 2026年9月1日: 検証コマンド出力の切り詰めに対するフック警告が1セッションで16件発生し、複数の実行主体が同じ操作を反復した。
  直接原因: 初回取得での切り詰めを出力形式によらず禁じ、代替手段を分離実行に限定したため、
  構造化出力から必要な情報だけを取得する低コストの手段が規範上の選択肢に無かった。
  対策: レコード単位で種別を判別できる構造化出力について、種別を指定した抽出を初回取得の観測手段として位置づけ、
  抽出結果を網羅性・件数・終了の根拠にしない条件を併記する
