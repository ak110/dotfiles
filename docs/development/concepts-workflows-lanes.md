# 確定済みの方針・意向: レーンと工程

## process-wiとレーン

2026年11月15日〜17日のユーザー回答により、実測から原則3時間に収まる量を、件数の下限を保って選ぶ。
回答済みUWIを先に、AWIは最古の1件と優先区分`urgent`の最古の1件を交互に並べた順で先頭から連続して選ぶ（2026年11月17日のユーザー指示で優先枠を加えた）。
長い先頭項目も後回しにせず、下限まで後続を並行処理する。
選定した全件を完遂して終了し、超過の原因と改善は次回へ記録する。
レーン数の例外のない上限と最小化を保ち、レーン内部の独立準備・確定群の先行レビュー・共有検証への早期投入を使う。
内部群の総数と、読み取り・実装・レビューを合わせた巡回全体の同時数Cを分け、資源・サービス・総費用と必要品質の比較からCを選ぶ。
費用を無視した最大化、着手後の対象削減、品質工程の省略と時間都合の次回送りは採らない。

明示された単一リポジトリの目標は、通常対話の作業契約・計画、またはprocess-wiへの追加指示で具体化する。
全体担当が必要作業、優先度、局所結果の採否、方針転換、完了を所有し、局所の設計と独立文脈レビューを保つ。
目標から具体化した必要作業は既存のWI・追加計画・選定合流で同一実行へ加える。
目標の明示がない通常キュー処理の固定集合は維持する。

2026年10月9日のユーザー指示で、両ホストの選定をメインへ移し、pickerを廃止した。
2026年10月10日の指示で、意味判断をメインに保ち、取得済み候補から鮮度・初回配分と型付き辺の定型欄をpick-wi-checkで生成して確認・保存する形へ改めた。
分類・モデル・配置根拠を生成側が推測せず、成功試行と本保存の重複を除く。
選定の被覆、上限、同じthread、単一writer、実行レビューと直列統合、計画保存とWI終了の契約は保持する。
圧縮専用のparent-handoff.mdへ重複保存する義務は2026年10月26日のユーザー指示で廃止した。

レーンの専用worktree・branchはatk lane createが準備と所有登録を持ち、統合・最終化の検収と消費工程の終了後に回収する。
2026年11月15日のユーザー指示により、再生成できる資源を使い終わった時点で回収し、同じthreadの追加作業は保存したcommit・計画・引き継ぎから環境を再作成する。
2026年10月11日のユーザー指示により、process-wiは対象リポジトリごとに1つだけ起動する前提で、レーンworktreeを主作業ツリーの.claude/worktrees/process-wi-lane-NNへ固定し、session・日時・呼び出し元worktreeで配置を変えない。
Codexのパス単位の信頼設定へ渡す作業ディレクトリをレーンの反復で増やさないためである。
2026年10月10日のユーザー指示で公開前回収を開始条件から外した経緯を保ち、通常終了のagents-exit-sessionとprocess-loopの子終了後も同じ安全な回収へ接続する。

WIの選定・追加・状態管理と本文の受け渡しの方針は、[WI選定と処理](concepts-wi-processing.md#wi選定と処理)を参照。

先行調査や選定の補助など統合先へ書き込まない担当は、作業ディレクトリを統合先とレーンのworktreeの外にして起動する。
役割の分からない担当を判定から一律に除く案は、書き込む担当の見逃しを招くため採らない。
時間の見込みが6000秒を超えても全件を同じ実行で処理し、レーン数上限の内側で独立群を並行する段階案と単一段階案を比較し、`レーンの所要時間`の行の`根拠`に秒数と理由を残す。
全要求・品質確認・利用上限時の待機方針を維持し、進行済み計画を分割しない。
`agent-toolkit:atk-mode`の作業`add-awi-by-user`と`agent-toolkit:atk-mode`の作業`process-wi`を起動したセッションでは、成果物種別を制限する指示が対象とする作業・工程・主体を確定し、その範囲内で制限を主題分類より先に適用する。
限定範囲外の是正には通常の依頼範囲・認可・確認要否を適用し、後続工程と委譲先へも種類と限定範囲を一体で引き継ぐ。
対象名の変更、修正を求める表現、主題の変化は、AWI投入専用のセッションへ直接実装の権限を加えない。
主題分類は許容された成果物種別の内側で既存項目への反映と別項目の投入を選ぶためにだけ用いる
（2026年9月21日、ユーザー指示。主題継続の判定を成果物境界より先に置き、直接実装へ分岐した観測に由来する）。

- 群ごとの独立した保存HEADと成功証拠を受理し、最終検収は群間契約・共有生成物・組み合わせ差分と未達を扱う
- 圧縮の予約は、予約へinstructionsを渡さず、受付と圧縮完了を区別し、バックグラウンド待機とターン終了へ進む。
  通知後は注入された要約から同じ担当と監視対象・工程を復元し、不足する情報だけを既存の選定・資源登録・担当記録・保存出力と状態照会から取得する。
  ユーザー操作やホスト自動処理による圧縮後にも同じ復元方法を使う。
  Codex、通常0件、追加レーン起動と実行レビュー待機は予約時点の対象外とする
- 固定パスに残る前回資源は既存の回収条件で回収して再作成し、未統合・dirty・稼働中・所有不明の資源は上書きも別パスへの回避もせず、理由と回復操作を返す
- 全登録を先に判定し、未統合・dirty・稼働中・不明・部分失敗は成果と記録を保持する（回収結果の保存と再判定は[design-storage-shared-resources.md](design-storage-shared-resources.md)にある）
- 後段レーンは、先行成果を要しない読み取り専用調査と計画下書きを先に準備できる。
  取得版・事実と仮定を記録し、先行統合後の最新HEADからworktreeを作成して、差分に応じて調査を更新し正式計画を起草・検査する。
  書き込み競合と実際の成果依存を区別し、開始可能な通常レーンを準備待ちで遅らせない。
  先行調査は既存の委譲手段とmanaged-tempを使い、正式計画、WI状態、資源登録、対象worktreeの書き込みを行わない
- 後段レーンの段階化は、実依存・同じ再開計画の不可分性と、同段階で同一定義を書かない条件を保つ。
  比較の方法と後段の開始位置は[design-lane-allocation.md](design-lane-allocation.md)にある
- 採否確定では、原文の元ファイル名、人間由来の指示・方針の優先度、調査根拠、欠陥原因、採否理由を項目ごとに対応付け、部分採用は原文との差異、採用範囲、除外範囲、理由を記録する
- 別リポジトリ項目は投入前処理で入力メッセージの予約frontmatterキー`target_repo`だけを移管先の値へ一時的に置き換え、元項目のfrontmatterと本文を含むメッセージ全体を正しい`target_repo`へ移管して登録する。
  `target_repo`をCLI値で置き換えず、frontmatterの値を優先し、sourceがある場合は同じ値を渡す
- `alert_keys`などの非予約frontmatterは元項目の値を保持する
- `agent-toolkit:atk-mode`の作業`add-awi-by-user`が新規項目を起票する場合は、ユーザー発話を原文とする手動起動を含めて`source: add-awi-by-user`を`atk wi add --source`へ必ず渡す。
  別リポジトリ項目の移管では、移管元に保存済みのsourceがある場合に同じ値を保持する

旧計画レビュー担当の取得契約は廃止前の方針である（2026年8月の知識境界を2026年9月の工程変更で改訂）。

## 工程と検証の名前

前工程の出口を後工程の入力とし、同じ判断を後工程で起草し直さない。
全体の自動チェックとCIは公開工程の検収で判定する（2026年9月24日、ユーザー指示）。

工程と検証の正式名は、実装後の実行レビューと、変更ファイルと直接利用側に限る変更範囲の検証とする。
全体の結果はCIで検収し、ローカルの変更範囲の成功で代用しない。
2026年11月27日のユーザー指示で、通常のベースへのpushは速やかに行い、CI待ちを次のレーンの作業と並行し、失敗は修正レーンで次のpushへ入れる形へ改めた。
リリースはその単位のCI成功を条件にする。
統合の流れは`agent-toolkit:atk-mode/playbooks/lane-receipt.md`「統合キュー」にある。
公開の流れは`agent-toolkit:atk-mode/playbooks/process-wi-publishing.md`「独立した公開単位」、プロジェクトの値は`develop-dotfiles`にある。
投入前レビューは2026年9月29日に全投入を委譲することを条件に廃止した。
2026年10月16日の専念型の完結する手順への変更で、親が意味を検収しない手順へ投入前レビューを戻した。

## 計画ファイルの体裁の扱い

計画ファイルは、1つの作業で扱う対象WIの一覧だけを持つ内部資料であり、人間の承認対象にしない。
実装と実行レビューの基準は対象WIの本文とし、実装着手後は本文を凍結する。
協調モードではユーザーがエージェントへ直接依頼し、`agent-toolkit:atk-mode/playbooks/write-plan.md`の要否をエージェントが判断する。

- リポジトリを変更する作業は、新しく始めるレーンと作業の全てで計画を作り、計画はfrontmatter（`launch_route`、`target_repo`、`related_wis`）とH1だけを持つ（2026年11月26日のユーザー指示「計画ファイルは対象WIのリストだけにする」）。
  例外は、WIの無い協調モードの小変更で`agent-toolkit:atk-mode/playbooks/write-plan.md`「計画ファイルの作成要否」の省略条件に当たる依頼であり、計画もAWIも作らない（同日の承認済みの方針で従来の省略を保った）。
  `source`が`add-awi-by-user`・`process-user-comments`・`implement`のAWIは本文をそのまま実装する。
  それ以外のAWIは、計画を作る時点でadd-awi-by-userと同じ粒度へ詳細化して本文を置き換え（`atk wi edit --detail`）、WIの無い協調モードの依頼は同じ粒度のAWIを保留で保存して一覧に載せる（同日のユーザー指示「WIはWIのまま管理する」）。
  2026年11月24日の決定（他経路の入力ではAWIと同じ書式の計画を作る）は、複数の入力の内容を1つの計画へ書き写して情報が繰り返されたため置き換えた。
  同日のユーザー回答「add-awi-by-userで作るレベルのAWIと同じフォーマットのものを作る」の意図は、入力ごとにAWI相当を作ることだった（2026年11月26日のユーザー指摘）。
  実行レビュー指摘管理表と対応記録は計画と同じstemの1か所に置き、計画なしの別名の置き場は公開時点で進行中のレーンの互換に限る。
  進捗・検証コマンド・検証結果・再開の情報は引き継ぎ記録へ、予測補正記録は対象AWI本文へ書く。
  計画ファイルが人間の承認を要しない内部資料であること、計画レビューを復活させないこと（2026年8月のユーザー指示）は保つ。
  協調モードの作業で先にAWIを作る手順へ1本化しない2026年9月30日のユーザー回答は、今回のユーザー承認で改めた（AWIの本文が計画の中身になり、同回答の理由だった二重の起草が生じないため）。
  条件の理由と採らなかった案は[計画の作成要否と成果物基準の一本化](design-planning-criteria.md#計画の作成要否と成果物基準の一本化)にある。
- 観測した欠陥を起点とする作業の原因分析はAWIの`## 原因分析`節へ書く。
  計画時に原因分析を訂正または追加する時は、詳細化でWIの本文へ書く。
  計画ファイル（バグ、同じstemの`.bugs.md`）は新しくは作らない（2026年11月16日の同じ決定）。
  原因分析をAWIへ置く扱いは2026年9月30日のユーザー回答による。

- 詳細化は、WIが確定した目的、要件、原因分析、適用範囲、実現方式と成立の根拠を保ち、本文から決まらない部分だけを調べて書き足す。
- 引き継ぎ記録の工程記録は中断再開用の粗い記録、レビュー指摘管理表は個別指摘の詳細として維持する。
  用途の異なる記録を件数・ラウンド数で結合・相互比較しない。

計画ファイルの体裁の差異は、工程の停止条件にしない。
体裁に関する指摘の採否は、根拠の確認と何も変更しない案を含めた費用の比較で確定する
（2026年9月15日、ユーザー指示。体裁を規範の是正対象から一律に外す扱いを撤去した）。

- 要求を書く節の書き方の定義元は、通常AWIの本文と同じ`agent-toolkit/skills/atk-mode/references/awi-body.md`とその条件別資料の1か所とする（2026年11月16日の同じ決定）
- 保存済みの表付き形式（2026年11月18日〜）、8節形式とそれ以前の形式の計画は、読み取り、進捗ログの追記、対応commitの記録で引き続き受け付け、書き換えない
- 旧二ファイル形式と計画レビューは過去の運用方針であり、読み取り互換だけを維持する（2026年8月の方針を2026年9月13日に改訂）
