# 振り返り準備と会話の流れの設計記録

[設計記録の索引](design.md)と[振り返り・知見集約の設計記録](design-session-review.md)から参照する主題別の記録である。

`agent-toolkit:review-session`は`atk run-script session-review-prepare`の実行と、メインによる同じセッション内の分析で構成する。
同コマンドの実体は`agent-toolkit/skills/review-session/scripts/session_review_prepare.py`である。
準備は証拠bundle、会話の流れ、`candidates.md`、セッション統計を作業ディレクトリへ書き、キューを変更しない。
メインは`candidates.md`より先に会話の流れ全体から観点を限定せず問題を列挙し、候補抜粋だけへ対象を縮めない。
`candidates.md`は全体像から得た問題との対応付けと、流れでは得られない事象（反復した失敗署名、hook通知の件数、委譲先の内部）の追加に使う。
メインは原因と対策を1案へ確定し、要求として`add-wi.parent.md`「起動方法」の単位でWI投入担当へ渡す。
既読証拠が足りる部分は再利用し、追加・変更・未確認・不一致だけを補完する。
最終判断を所有する振り返り担当の委譲先は起動しない。
判断基準は`agent-toolkit/skills/review-session/references/analysis.md`が持ち、所要時間の分析は同じ配下の`duration-analysis.md`が持つ。

この構成の判断根拠は、実際のセッション記録を集計した次の数値である。
2026年9月23日から25日のdotfiles向け親セッション21件では、振り返り担当が規範の読込、候補の読解、原因調査、AWI起草、報告組立を直列に行い、58回から237回の応答で580秒から3375秒を要した（記録長31秒の対象でも約600秒）。
担当の起動をやめるため、2026年9月25日から26日には`atk run-script session-review-prepare`が素材AWIを投入して後続セッションのレーンが分析する構成を採用した。
しかし、分析が素材の生成とレーンでの読み直しの二度手間になり、深刻な問題の対策の確定がprocess-wiの次の実行まで遅れる事態が生じた。
加えて、別環境で生じた素材AWIは処理側からセッション記録を照会できないこともあった（2026年9月26日、ユーザー指示により撤去）。
同じ期間の素材AWI 3件の候補は計249件で、除外や非欠陥と判定されなかったのは78件だった。
残りの171件は、正常に完了した委譲返却、一致0件の検索の終了コード（1または123）および`atk wi`の本文表記診断の警告が大半を占めた。
遅さの原因は候補の雑音と固定の往復の2つにあると判断し、雑音を`atk run-script session-review-evidence`で除き、担当を起動せずにメインが自身のコンテキストで分析する構成で両方へ作用させる。
300秒という所要時間の目標は維持するが、完了条件には含めない。

WI検索・一覧の取得では、読み取った本文と共通パーサーの解析結果を同じ内部データへ保持し、選択、表示、着手可否判定へ渡す。
属性ごとの再解析が取得費用を増やしていたため、共通の取得境界で解析し、振り返りを含む既存の呼び出し元全体へ適用する。
一覧の着手可否計算と項目選択は操作内の取得結果を共有し、再読取した内容が変わった場合と別操作では新しい解析結果を取得する。
共通パーサーが持つ字面と`queue_schedule`の型の扱い、必読資料と品質確認、300秒目標は保持する。
操作をまたぐキャッシュは鮮度管理の費用を加え、振り返り専用の実装は呼び出し元ごとに処理を分けるため採用しない。

会話の流れは、メイン記録を実ユーザー発話から次の実ユーザー発話までの区間へ分け、割当内ではアシスタント発話とツール呼出入力を記録位置順に1件1行で示す。
最小の個別行でも割当を超える場合に限り、連続する呼出しを種類別件数・失敗件数・記録位置の範囲へ集約する。
結果本文を混ぜず、ユーザー発話の少ない自動実行でも途中の操作を通読できる形にする。
委譲先は記録ごとに依頼と最終観測発話（発話数と操作量を添える）の行を作り、メインの行と時刻順に1本の時系列へ統合する。
担当間の依頼・返却・判断の前後関係を通読するためである。
記録だけでは途中の発話と返却を区別できないため返却とは呼ばず、アシスタント発話が無い記録は返却を示さず発話未観測と操作量だけを示す。
agents_serverの配送境界内の最初の依頼は、入れ子の機械生成要素を除いた本文を使い、人間発話の抽出とは区別する。
詳細本文は載せず、記録位置から取得する。
会話の流れの目的は作業の流れ（遠回り、手戻り、試行錯誤、同じ論点の反復、ユーザーによる是正）を振り返ることであり、2026年9月26日の導入時はメイン記録の発話だけを載せた。
流れは発話と呼び出しの入力から読め、結果の本文は記録から`--detail`で再取得できる。
失敗の有無は試行錯誤をたどるのに要るため結果の行へ残す。
抽出が失敗として扱わないCodexのシェル実行の非0終了も、結果の先頭の終了コードの行から失敗と示す。
失敗の診断、hook通知、反復した失敗署名は`candidates.md`が扱う。
2026年10月18日に全担当の全結果を全文で載せる構成へ改めた後、多数の委譲先を持つセッションの会話の流れは90〜108MBになり、その過半がファイル表示と前回の準備資料を読んだ結果だった。
同年10月19日には、この2種の結果だけを対象・本文量・先頭の数行へ置き換えた。
ユーザーはその後、会話の流れは発話と呼び出しの引数だけで流れを振り返るものであり、結果が混じるのは当初の目的を見失った誤りと指摘した。
全結果の全文化は、10月13日の通読への要求（次段落）を、読み手へ渡す本文を全量にすることと解した起草の判断によるもので、ユーザーの要求には含まれていなかった。
このため結果の本文を一律に外した。
結果の種類（ファイル表示、加工、失敗、ホストの通知）ごとに残すかを判定する構成は、判定の対象を増やすたびに例外が増え、流れの把握に要らない本文が残るため採らない。
CodexのCommandExecutionは結果のJSONがコマンド・終了状態・出力をまとめて持つため、呼び出しの入力にはコマンドを、成否には終了状態を使う。

2026年10月13日のユーザー指示は、候補の観点や例示に限定しない通読から改善を発見することを求めた。
通読は詳細本文の全量保持ではなく、全担当の目的・判断・操作量・失敗と手戻りを同じ全体像へ載せることで成立させる。
詳細を分割担当へ配る案、新しい監視や全操作台帳は加えない。

実行環境の挿入を判定する接頭辞は、ユーザー介入の候補の除外と会話の流れの抽出が同じ定数を使う。
`candidates.md`は候補の概要と代表位置を示し、ユーザー介入・エスカレーションの全文とhook通知の前後関係は保存証拠から取得する。
素材AWIの構成では処理側が元の記録を探し直さないよう記録位置を載せなかったが、同じセッション内のメインが読む構成ではその理由が当たらない。
ユーザー介入の候補は、単発の照会、判断を変えない追加要求、理由の無い拒否・中断の3区分だけを根拠付きで除外でき、それ以外は欠陥として再発防止策を要する。
規範の条文だけでは介入が「ユーザーの選好」などの理由で外れた観測（2026年9月24日の振り返り成果2件）があるため、完了報告の振り返り結果は除外した介入の区分と理由を「対策を見送った問題」へ載せる。

その場のコード実行と保存出力の加工は全担当の通読と既存の`adhoc-processing`候補で扱う。
候補は外側の呼び出しの記録位置と全文を保つ。
Codexのセルでは文字列・コメントと実際の`tools.exec_command`の静的な入力を分け、シェル側は既存の実行区間・パイプライン解析で実行位置と入力方法を対応付ける。
別ファイルを読む加工や、文書・fixtureへ書くコマンド例は実行の証拠へ変換しない。
呼び出しのたびに通知するhookの案も採らない。
同じセッションで該当した呼び出しは委譲先29件に分散した計112件とメインの20件で、その多くは1回限りの調査であり、実行時の通知は誤検出の往復費用が防止効果を上回るためである。
