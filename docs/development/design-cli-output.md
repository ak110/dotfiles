# 結果行と出力に含める情報の設計記録

[設計記録の索引](design.md)から参照する、結果行と出力に含める情報の記録である。

## atkの結果行の接頭辞と出力先

目的は`atk`の出力を受け取るコーディングエージェントが、返却値または結果行の先頭の語で成否を確定し、終了コードの再確認、状態の再取得および一致判定の確認を追加せずに次の工程へ進める状態にすることである。
結果行は成功を`成功:`、失敗を`失敗:`、警告を`警告:`、該当0件を`該当0件:`の4種の固定接頭辞で表す。

構造の理由は、接頭辞の文字列と成功行の出力先の決定を`agent-toolkit/agent_toolkit/_atk/outcome.py`へ集約し、出力箇所ごとに語彙と出力先が分かれる状態を表現できなくする点にある。
標準出力の値や構造化データが成功結果を表すコマンドは、その値を結果通知とする。
状態変更報告型は標準出力の1行目へ成功行を書く。
この区分を状態変更報告型、値出力型、読み取り専用型、対象外の4つとして同モジュールが保持し、`help_text.py`が各コマンドの`対象と出力`へ結果行の接頭辞と出力先を自動で加える。
`agent_toolkit/atk_help_test.py`はコマンド木の全リーフを列挙し、いずれの区分にも属さないリーフと区分の重複を検出する。

知識境界として、結果の本文は各出力箇所が持ち、本モジュールは接頭辞と結果行の要否・出力先を持つ。
どのコマンドがどの区分に属するかは同モジュールの区分表に従い、ヘルプの文面とテストの双方が区分表を参照する。

却下した代替案は、接頭辞を各出力箇所へ直接書く案と、区分表をテストだけが持つ案である。
前者は同じ語彙の決定を出力箇所の数だけ分散させ、後者はヘルプの文面とテストの判定が別々の表を持つため採用しない。

## atkの出力に含める情報

`atk`の出力は受け取るエージェントが選別せずそのまま読めば次の判断に必要な行だけを得られる構成とする。
出力するのはコマンドの結果（成否、変更・保存した対象と値、要求された値・本文・一覧）と、失敗・警告およびその次の操作である。
実行中に検出した対処を要する事象の警告も含める。
結果と無関係な状況の通知、対処不要の付随処理の報告、毎回同じ固定の案内、入力と別行の記載だけで一意に導ける値の反復は、環境によらず出力しない。
結果と無関係な補足を人向けに環境判定で振り分ける案も採用しない。
人が次の操作を選ぶための対話（確認前の候補一覧や回答前のUWI本文など）は補足行の対象から外し、結果の書式を環境で切り替える既存設計も保持する。
人が直接使う長時間・常駐CLIの実行中表示は、その時点で処理状態を判断するための情報として扱う。
開始、工程の移行、待機理由などを実行中に届け、表示量は人の判断に必要な情報で決める。
LLMが読む出力のトークン削減は、人向け表示を減らす理由にしない。
実装・改訂時は`agent-basics/skills/writing-standards/references/program-messages.md`「出力の基準」からこの観点へ到達する。

`agents_wait`のCLI待機、`git_sync`のremote同期・共有ロック取得、`run_command.execute`の子の終了待ち、`post_apply.run`の工程完了待ちは、人向けに対象と状態を標準エラーへ表示する。
判定は`_atk.environment.is_human_terminal`を使い、エージェント環境の外で標準エラーが端末の呼び出しだけへ表示する。
エージェント環境の区分は有限終了の出力を保存する既存の判定と同じであり、パイプ・ファイル・テストの捕捉へ出力する呼び出しは結果の行だけを保つ。
共有ロックは他の主体が保持して待つ場合だけ待機中と表示する。
待機が上限に達した場合は、人の端末とエージェント環境のどちらでも、保持者を示す失敗行で終える（上限と保持者の記録は`design-wi-common.md`「共通処理の構成と一覧の限定条件」）。
`agents wait`のJSON Lines、子の保存出力と終了状態、Git成功時の生出力の抑制を保つ。
post-applyは全体の実行中表示を使い、工程結果の列挙順のまとまりと永続ログの開始時刻・詳細を保持する。
工程ごとの開始行と所要時間行を画面へ重ねる案は、工程結果の列挙順のまとまりを損なうため採らない。

post-applyの進捗は標準エラーの1行を`\r`と空白で書き換えて示し、工程結果の出力前と実行の終了時に消去する。
ANSIエスケープを解釈しない端末（Windowsの`dotfiles-post-apply.exe`を含む）でも同じ表示にするため、行の消去にANSIエスケープを使わない。
表示は完了数・総数・実行中の件数と、実行時間が最も長い（開始が最も古い）実行中の工程名に限り、端末幅を超えない長さにする。
工程の例外は画面へ「工程名: 失敗: 例外の型: メッセージ」の1行だけを出力し、Tracebackは永続ログ専用にする。
失敗後の次の操作と永続ログの所在は、`update-dotfiles`経由の実行では`update-dotfiles`の終了時に1回出力し、`dotfiles-post-apply`の単独実行ではpost-applyの集計の後に1回出力する。

類似箇所の探索では、`atk`の公開登録から長時間・待機・外部照会の実装をたどり、`bin/`と`pytools/`のコマンドが行う外部処理と出力捕捉を静的に調べた。
all-reposと共有アラート照会は状態表示を持ち、watch・serve・ログ追従・画像・PDF・アーカイブ処理・releaserのCI待機は開始・対象・結果または逐次出力を持つ。
全入力規模と外部サービス遅延の測定は探索に含まれず、短いローカル処理が特定の入力で長時間になる可能性は残る。
既知の4箇所を是正し、今後の新設・改訂にも同じ表示方針を適用する。

書式を前提とする機械的な読み手がいる行は、読み手を移行してから除く。
`atk wi`の未回答UWI通知も、結果と無関係な状況の通知として扱う。
未回答UWIは、ユーザーが`atk serve`の件数表示とブラウザー通知で、エージェントが`atk wi list --type=uwi --answered=no`などの明示的な照会で確かめる。
末尾の未回答UWI通知は、ユーザーの確認手段が`atk serve`へ移って読み手を失い、エージェントには出力を選別する動機を与えて終了コードと警告の観測を妨げたため撤去した。
エージェント環境の状態変更だけで抑止する案は、人の端末でも`atk serve`が確認を担うため、環境とサブコマンドによる分岐を保つ理由がなく採用しない。
表記診断は起草者の判断に使う全行を保持し、同じ次の操作の反復だけを1行へまとめる。
WI本文の各診断は入力元、frontmatterを除いた論理本文の行・列、一致箇所を囲んだ前後の抜粋を持つ。
生成時点の本文と入力元を使うことで、複数原稿と同じ行の複数の一致から修正対象を特定できる。
入力元は追加時の本文ファイルのパスまたはエディター入力、置換時は編集対象のファイル名とする。
診断の生成を共通化し、保存詳細・人の端末への直接表示・保存失敗時の表示へ同じ結果を渡す。
起草者が全原稿へ座標を当てて文脈を復元する案は、生成側が保持する情報の再取得を繰り返すため採らない。
出力の選別をhookで検出する案は、静的解析で実行時の条件を再現できず正当な操作へ警告が続いたため撤去済みである。
出力が選別の動機を生む状態では、検出や呼び出し側の規範だけでは再発を防げないため、出力側も改める。

保存本文の一致判定は出力しない。
`atk wi add`・`atk wi edit`・`atk review-table add`・`atk review-table respond`は保存本文が送信元本文と一致しない場合に非0で終了して差異を標準エラーへ書くため、成功の終了コードだけで一致の成立を示せる。
成立時に常に同じ値を返す行を出力しても、受け取る主体の判断は変わらない。
