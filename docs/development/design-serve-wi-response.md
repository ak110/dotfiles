# WI画面の応答性と回答の設計記録

[設計記録の索引](design.md)と[画面統合とセッション・計画一覧の設計記録](design-serve.md)から参照する主題別の記録である。

## WI画面

### 参照の応答性と所要の記録

WI画面の参照（一覧・詳細・検索・対象リポジトリ候補）は、変更とGit同期と別の実行枠（`ServeRuntime.read_workers`）で処理し、`repo_lock`を取らずにローカルの保存済み内容で応答する。
変更と同期は`repo_lock`を最大30秒待つため、同じ枠を共有すると参照がロックの解放まで待つ（2026年11月6日、ユーザーの「保存処理とかが完了してなくても待たずに参照できるべき」「ローカルにある古い情報のままでいい」という要求と計測による）。
表示は古くてよく、最新化は定期同期と「今すぐ同期」で行う。
ロック自体は残す。
process-loopと各レーンの`atk wi`が同じ保存リポジトリでGit操作を共有するため、撤去するとGit履歴とリモートの整合を保てない。

同じ計測で、遅延の主因は`pull`ごとの旧予約形式の移行判定（全WIのfrontmatterをロック保持中にYAML解析し、約8000件で約7秒）だった。
移行判定は予約・付随項目の最上位キーを持つ項目が無ければ解析せずに終え、`parse_frontmatter`は型付きの値を使うキーが無ければ2回目の解析を省く。
起動直後の最初の一覧が全件の解析を待たないよう、起動時に索引の初回走査を参照の枠で始める。
外部変更の通知では、新規項目の通知判定に未終了の項目だけを取得し、実行中の再読込がある間の通知は1回にまとめる。
保存・回答・状態遷移などの変更で名前から保存先を探す処理も、ロック保持中に全件を列挙していた（保存1回の約1秒のうち約0.9秒）。
日付形式の名前は年月保存先を直接確かめ、移行前の状態配置に同名がある場合だけ従来どおり列挙する（`wi/layout.py`の`unique_dated_entry_path`）。

保存は実際の保存完了まで詳細ダイアログを閉じない。
先に閉じて裏で保存する案は、失敗・競合時にダイアログを開き直して入力を戻す処理と、受付と完了の二重の表示が要る。
主因のロック保持を短縮すれば完了まで待っても目標の1秒に収まる見込みのため採らない。

各操作の所要は状態ディレクトリ配下の`serve/timings.jsonl`へ常時記録する（`serve/timings.py`）。
サーバーは要求ごとに要求全体・実行枠の待機・ロックの待機と保持・処理本体を記録する。
ロックを取得できずに時間切れとなった待ちもロック待機に含める。
画面は取得ごとの記録と、操作全体の記録（`kind: operation`）を送る。
操作全体は押下や変更通知の受信から、結果の表示（保存後の一覧の再描画、計画の図の非同期描画など）を終えた次の描画フレームまでを測り、まとめて実行した通知は最初の受信時刻から測って待ち時間を`queued_ms`に分ける。
取得の記録は操作の`operation_id`とサーバーと同じ`X-Atk-Request-Id`を持ち、操作・取得・サーバーの区間を対応付けられる。
取得ごとの記録は本文の受信までしか測れず、保存後の表示更新や図の描画、通知後の再取得全体の遅れを追跡できないため、操作全体を別に記録する。
定期同期、通知の発行、索引の先行走査も種別付きで記録する。
1世代1MiBで`.1`へ回し、合計約2MiBに保つ。
本文・検索語・入力値は記録しない。
遅い操作の調査は、`jq`で`kind`が`operation`かつ`total_ms`の大きい記録を抽出し、同じ`operation_id`の取得と、その`request_id`のサーバー区間を比べる。

### UWIの回答操作

通常表示・条件検索で回答できるUWI（保存状態がinbox・processing・hold）を開くと、フッター上段に選択肢・1行の回答欄・「回答を保存」を、下段に採否・編集などの操作を表示する。
回答のたびにモードを切り替える操作をなくすためである（2026年11月6日、ユーザー指示「最初に開いた時点で回答とそれ以外の操作が全部できる状態にして」）。
選択肢は回答欄へ値を入れるだけとし、保存は「回答を保存」で確定する（誤クリックで回答が確定しないため）。
入力途中の回答は、外部更新や再表示でも保持し、未保存の確認の対象にする。

### 判断待ちの連続確認

判断待ちは明示的に選ぶ表示モードとし、通常表示の直近2週間と検索入力の意味を保つ。
`GET /api/entries?view=waiting`の集合と順序は`wi_operations.py`が所有する。
対象はinbox・processing・holdの未回答UWI、期間は全期間、並びは重要降順・作成日時を含むファイル名の昇順である。
`target_repo`だけを任意の限定条件として受け取り、通常/検索の条件から独立させる。
画面は判断待ち用のrepo選択を別に保持し、通常/検索へ戻ると既存の入力値を再利用する。
別の永続キューや優先度値を作る案は、既存の状態・回答・重要フラグと対象集合が分かれるため採らない。

「保存して次へ」は既存の回答APIと`expected_content`を使い、成功応答を確認してから次の候補を取得する。
「保存せず次へ」は現在項目を書き換えず、未保存入力があれば破棄を確認する。
次の候補は最新の一覧を既存の100件単位で取り直し、現在項目の重要度とファイル名より後の項目から選ぶ。
詳細取得時にも回答済み・消失・終了状態への移動を外す。
保存で一覧の前の行が消えた後も次の候補を選べるよう、保存前のページ内位置だけでは選ばない。
連続操作中は既存の一覧要求世代を更新して古い応答を無効にし、次項目を表示したら入力を初期化して本文へフォーカスを移す。

現在位置は最新一覧での順序位置、残件数はrepo限定後の未回答総数を示す。
見送りは未回答総数を減らさず、その順番での候補が尽きると残件数を通知して詳細を閉じる。
保存失敗や外部変更では現在項目と入力を保持し、競合した入力の保存を止める。
保存済みで次の取得だけが失敗した場合は再保存を止め、「保存せず次へ」で取得を再試行できる。
判断待ちの詳細は回答・見送り・閉じる操作に限定し、狭幅でも本文の読取領域を確保する。
編集・状態操作は通常/検索の詳細で維持し、キーボードは標準のTabとEnterを使う。
保存ショートカットを設けず、IME確定で回答を送信しない。

画面が完了させるのは回答の保存までであり、元AWIの独自再開や方針原本への自動反映は行わない。
継続適用を明示した回答と、以後の方針の候補と判定した回答の反映は、[回答後の状態遷移](../../agent-toolkit/skills/user-confirmation-and-report/references/answer-transitions.md#回答後の状態遷移)から既存の恒久化判断へ渡し、読み手・適用範囲・出所と元の認可を保つ。
今回限りの回答の一般化と、回答保存を方針反映完了として扱う案は採らない。
