# 方針・意向: フックのホスト間共通化

## フックのホスト間共通化

2026年8月のユーザー指示（Claude CodeにあるフックをCodexへも極力実装し、実装を共通化する）で確定した領域である。
現行の規定は[design-hooks.md](design-hooks-responsibility.md#フックの責務境界)の「フックの責務境界」にある。

- 公式契約または実物の観測で同等性を確認できるフックだけを共有中核へ集約し、
  ホスト固有の入力変換と出力契約だけを分離する方針が確定した
- 形式的な対応数を目的に、同等性を確認できない処理を移植しない方針が確定した。
  各ホストの入力から安全に判定できる範囲を先に確定し、確定できないチェックは元のホスト専用として維持する
- 配布するフックの対応状況（対応・部分対応・非対応と非対応理由）をエンドユーザー向けガイドの一覧で示す方針が確定した。
  導入ホストごとの実際の機能差をエンドユーザーが確認できることを目的とする
- フックのblockまたはwarnは、事前に防ぐ型と遮断後に対処する型の費用を比べて設計する。
  事前に防ぐ型は要求を事前に解釈できる規範と対にし、規範どおりの通常操作では発火させない。
  遮断後に対処する型の発火は規範どおりの通常操作に含め、規範には遮断時は通知に従う扱いだけを書く（2026年9月29日、ユーザー指示）。
  複数ホストへ同じ保護を設ける場合は、ホスト入力によらず共通の判定を共有する（2026年9月14日、ユーザー指示）。
  現行の規定は`.claude/skills/agent-toolkit-edit/references/claude-hooks-block-warn.md`にある
- 遮断・警告するフックを置くかは、QCDでフックの費用と防ぐ手戻りの便益を比べて決める。
  何でもフックで遮断する設計も、フックで止めてよい誤りを無理に避ける設計も、同じくQCDを下げる。
  明らかなエージェントの行動誤りで、遮断してもトークンの無駄が多くない判定は、元へ戻せる誤りを防ぐものでも置く。
  通した場合に元へ戻せない結果を防ぐ判定（不可逆な操作の防止とデータ破損の防止）と常駐運用の終了保証は、置く理由として残る。
  規範の配送と権限の自動許可は遮断・警告に当たらない。
  2026年9月26日のユーザー指示は、フックを元へ戻せない結果を防ぐ判定と常駐運用の終了保証だけに置き、範囲の外はユーザーが例外として確定した場合だけ残すとしていた。
  2026年10月2日のユーザー指示（「hookは元へ戻せない結果を防ぐものだけ残すだけだと厳しすぎる」、基準はQCD）で、この範囲限定をQCDの費用比較へ改めた。
  経緯と全件確認の表は[design-hooks.md](design-hooks-eligibility.md#全件確認の経緯2026年9月26日)「全件確認の経緯（2026年9月26日）」にある。
  現行の規定は`.claude/skills/agent-toolkit-edit/references/claude-hooks-block-warn.md`の「遮断・警告フックの成立条件」にある
- フックのblockは、通した場合の結果を復元できない操作と、遮断で失うターンの入力と作業が小さい明らかな行動誤りに用いる。
  それ以外の再編集または再実行で是正できる操作にはwarnを用いる。
  blockを使うと、そのターンの入力と作業が失われ、同じ操作の再実行が必要になるためである。
  2026年9月15日のユーザー指示はblockを復元できない操作だけに限っていたが、2026年10月2日のユーザー指示で明らかな行動誤りへ広げた。
  現行の規定は`.claude/skills/agent-toolkit-edit/references/claude-hooks-block-warn.md`の「遮断・警告フックの成立条件」にある
- ユーザーへ提示する本文そのものを入力とするフックの判定は、遮断せず警告で返す。
  ユーザーへ提示する本文には、`AskUserQuestion`の質問と選択肢、`ExitPlanMode`の計画本文が含まれる。
  ユーザーが読んで誤りを指摘できるため、遮断は是正の往復だけを増やす
  （2026年9月16日、ユーザー指示。未観測の`atk`サブコマンドを指す確認の発行を遮断する処理に由来する）。
  現行の規定は同じ「遮断・警告フックの成立条件」にある
- 委譲先の結果を回収していないことだけを理由にStopを機械的に遮断しない。
  エージェントは判断に必要な情報を自ら取得し、取得しなかった情報は判断に必要としていないためである。
  遮断機構は判断材料を増やさず、セッションの進行だけを止める
- 委譲先の結果を回収していないことを理由にStopを遮断しない方針は、結果の回収を条件とする判定を対象とする。
  `agents_server`のsessionに観測を試みていない作業が残る場合にStopで警告する処理は対象外とする。
  観測義務は`start`（全`mode`）と、新しいturnの配送が成立した`send_message`が発生させる。
  ルートセッションが所有する`atk agents wait`の待機所有権が有効である間と、同コマンドの完了をPostToolUseで観測した後は観測済みとして扱い、意図的な`kill`も義務を解消する。
  直前の応答が`待機中: <対象session識別子>`の形で待機するsessionを示して終わった場合も、自動再開でそのsessionの結果を受け取るため、観測義務は解消する（2026年9月16日、ユーザー回答）。
  CLI待機をBash背景ジョブとして継続中の正常終了は警告しない（2026年9月、ユーザー指示。起動だけを行って観測しないまま終了した障害と、正規のCLI待機を旧MCP `wait`だけの判定が誤警告した障害の観測に由来する）
