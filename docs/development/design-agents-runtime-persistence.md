# 補助保存と表示の寿命の設計記録

[設計記録の索引](design.md)から参照する、補助保存と表示の寿命の記録である。

backendを開始した後の補助保存は、起動の成否と同じ成功条件に置かない。
2026年10月13日に、Windowsで`root.json`の置換がWinError 5で失敗し、起動した委譲先は正常終了した一方で`start`が例外を返した。
起動応答の`session_id`を前提とするフックがcwdと所有を記録できず、同じsessionへの`send_message`と終了工程の待機判断が拒否された。
managerは開始済みのsessionについて、session登録簿と状態ファイルの射影をそれぞれ試み、失敗を`persistence_warnings`として起動応答へ加え、同じ`session_id`で続ける`next_action`を返す。
登録簿は成功した値だけを公開済みとして覚えるため、次の状態更新と`flush`が保存を再試行する。
表示用の状態ファイルの置換失敗は`ProjectionWriteError`で終了時の結果の保存失敗と区別し、予約した`flush`とheartbeatの失敗はログへ残して次回へ進む。
`flush`に失敗した起動だけはmanagerが待機対象を登録するため、表示が空でも`atk agents wait`は当該sessionを待てる。
`flush`が成功した起動は既存の表示とPostToolUseフックの登録を使い、登録の主体を増やさない。
backendの起動前に不成立となった入力は起動済みとして登録しない。
停止時には終了の公開で生じた`ProjectionWriteError`だけをログへ残して後始末を続け、終了時の結果の保存の`OSError`は呼び出し元へ伝える。
どちらの場合もlistenerの解除と状態ファイルの書込停止は`finally`で行い、表示の保存失敗が後始末を止めず、結果の保存失敗が成功として隠れないようにする。
共通の`atomic_write`は置換に失敗した例外へ置換元と置換先のパスを注記するため、各呼び出し側が既存ログへ記録するスタックに両パスが残り、診断のために別の状態を保存しない。
共通の`atomic_write`は原子的な全置換を保ち、置換段階のWinError 5・32だけを同じ一時ファイルで有限回（合計1秒未満）再試行する。
上限後と対象外のエラーでは一時ファイルを回収し、旧本文を残して失敗を返す。
読取ハンドルとの短い競合を待つ一方、恒久的な拒否も上限後は失敗として扱うためである。
過去の競合主体は特定していないため、主体の種類で仕様を分岐させない。
この同期再試行をasyncioの予約保存とheartbeatから直接呼ぶと、待機中は他のtaskも進めない。
非同期保存では、loop上でパス・本文・登録情報を確定し、ファイル操作だけを`file_operations.run_file_operation`でworkerへ渡す。
共有session辞書、writerとタイマーはloopに残し、保存成功も取得したsnapshotへ対応付けて反映する。
登録公開はsessionごとのtaskに集約し、保存中の更新を次の公開へ接続する。
writerの保存と削除は直列化し、旧turnの成功を新turnへ反映せず、公開済み・回収済みの結果を再保存しない。
公開応答の前に必要な保存を待ち、停止の取消時もworkerの終了と終了公開を回収してから状態ファイルを削除する。
同期CLIの再試行回数・対象エラー・診断は変更しない。
`to_thread(self.flush)`で保存処理全体をworkerへ渡す案は、共有状態とタイマーの所有を別スレッドへ移して競合を増やすため採らない。
別の保存queueや台帳も設けず、既存のtask、Lockとawaitによる保存境界を使う。
保存のdrainでは、並行したtaskの一部が失敗しても全workerの終了を回収してから失敗を伝える。
最初の失敗で返ると、停止後の候補保存や状態ファイルの再作成が残るためである。
却下した代替案は、直接上書きへ変える案、表示用の状態ファイルの成功だけを維持する案、新しい台帳へ起動を記録する案である。
1つ目は書込途中の本文を読取側へ見せ、2つ目は上限後の拒否で実際の起動が応答から失われ、3つ目は既存の登録簿と同じ情報を重複して保持する。

表示対象は終了時の結果を持たないsessionと、終了時の結果を持ち`results/<session_id>.json`が存在するsessionとする。
statuslineは状態ファイルの各行について、終了状態であり対応する結果ファイルが存在しない行を描画から外す。
保持期限（30分）に到達した行は書込主体が状態ファイルから外す。
結果ファイルはこの時点では削除せず、前述の回収・破棄の契機まで残す。
実行中だけに限定しないのは、回収し忘れたsessionを可視化するためである。
保持期限の到達後は表示を続けても回収の催促にならないため、行を外す。
ただし稼働中の子孫を持つsessionは、自身のturnが終了し、結果の回収や保持期限の到達で通常の条件から外れても、祖先の行として残す。
委譲先が孫の終了を待つ間に子の行だけが消えると、孫が収容sessionを失った行として末尾へ移り、委譲のつながりを見失うためである。
書込主体は同じルートの他の状態ファイルを読み、`host_session_id`と各sessionの`status`から稼働中の子孫を判定する。
直下の子が終了していても、その先の子孫が稼働していれば祖先とみなす。
保持期限で本体を解放したsessionも、退避済みの再開情報から行を出力する。
statuslineも全状態ファイルの親子関係を解決してから結果ファイルの判定を適用する。
表示する`status`は実際の終了状態のままとし、結果の再公開、保持期限の延長およびbackend資源の延命はしない。
最後の子孫が終了するか、子孫の状態ファイルの`heartbeat_at`が失効すると、次のflushと描画から通常の条件へ戻る。
却下した代替案は、子孫の稼働中は親の`status`を`running`へ書き換える案と、子孫の情報を集める台帳を新設する案である。
前者は親自身のturn終了と結果の有無を表示から読み取れなくし、後者は状態ファイルと同じ親子関係を別の記録で重複して保持する。
入れ子の書込主体の行は、収容sessionの行の直後へ深さに応じて字下げして置く。
収容sessionの行が無い場合は末尾へ置く。
