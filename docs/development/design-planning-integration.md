# 複数レーンの統合と版数更新の設計記録

[設計記録の索引](design.md)と[計画と実行レビューへの受渡しの設計記録](design-planning.md)から参照する主題別の記録である。

## 複数レーンの統合と版数更新

複数のレーンを1つの履歴へまとめる場合、各レーンはffマージの要求前に実行レビューを完了する。
rebase競合を解消した場合は同じexecutorと実装担当へ戻し、解消差分と直接影響範囲を含めて同じ実行レビューを再度収束させる。
競合が無いレーンや全レーンのffマージ後に全体レビューを追加しない。

配布物の版数更新と全体検証はメインが統合完了後（全レーンのff前進後）へ集約し、並列実装で決定論的に生じる競合と
全体検証の反復を除く。
版数manifestは全レーンで同一のファイルであり、レーンごとに更新すれば必ず競合するためである。
レーンの計画は版数更新の種別、選定根拠および認可根拠だけを保持し、メインが全レーンから単一の種別を確定して
適用と検証を担う。
統合の実体は完了レーンから順に自レーンworktree内で最新ベースへrebase・競合解消をし、メインが依存条件を満たしたレーンへ許可し、`atk lane integrate`が統合先ごとの排他で1レーンずつ行うffマージである。
統合するレーン担当は変更したエージェント向け文書のpath集合と後続判断へ影響する確定本文を返し、メインは統合差分との集合一致と統合後本文との逐語一致を確認してから後続判断へ適用する。

統合前の検証で終了コード0でも警告を観測した場合、統合するレーン担当は警告の意味と由来で続行か阻害かを判定する（`agent-toolkit:/share/lane-integration-subagent-operation.md`「検証結果の警告の判定」）。
未適用・未完了を示す警告は既存でも阻害とし、処理の成立に影響しない警告だけを、警告を出力したコマンドの統合前HEADでの同条件の結果と比べる。
統合前にも同じ警告がある場合は根拠を記録して続行し、メインへ受理だけを求めない。
2026年10月1日に、変更していないテスト由来の非推奨通知を「警告の不在」の条件に照らして阻害とし、メインの受理まで統合を保留した事象による。
比較は警告を観測したときだけ行う。
全検証を統合前HEADでも常に二重実行する案は、警告が無い大半の統合で費用だけを増やすため採らない。
終了コード0であることや既存であることだけで成功とする案は、処理不成立を示す既存の警告を見逃すため採らない。
終了時一括のcherry-pickと専用の統合worktreeは設けず、メインがffマージの進行に応じてベース先端を把握する。
レビュー範囲の判定軸は競合解消時に新たに生じた差分だけとし、差分の由来による区分は設けない。

### 旧統合方式の下の却下案

以下2案は旧cherry-pick統合案の下で却下したが、時間効率化（ユーザー指示）を機に前提が変わったため理由を書き改める。
レーンを先行レーンの上へ積み上げて競合自体を無くす案は、依存の無いレーンを直列化して並列実装の時間効率を損なうため、
時間効率化そのものの目的と衝突し、引き続き採用しない。
実行中に差分の由来を記録して区分する案は、旧cherry-pick方式では実行中の競合解消でcommitの分離が成立しない点が
不採用理由だった。
新方式でも競合解消はレーンのrebase実行中に生じ、区分の維持に恒常的な機構を要する点は
変わらないため、引き続き採用しない。
