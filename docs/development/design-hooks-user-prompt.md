# ユーザー発話への注入と注記の設計記録

[設計記録の索引](design.md)から参照する、ユーザー発話への注入と注記の記録である。

## UserPromptSubmitの注入と注記

ユーザー発話への起動案内は、開始・文脈喪失後の最初の実入力へ一度だけ届ける。
発話の内容を現物で確かめる一般手順は`user-confirmation-and-report`が所有する。

知識境界は次のとおりとする。
フックは起動案内を保持し、発話が是正要求かどうかを判定しない。

却下した代替案は2つある。
1つは発話の内容から是正要求を判別して注入する案である。
フックが会話の意味を判断する責務境界を越え、判別の誤りが注入の欠落として観測されないため採らない。
もう1つは経過時間ごと、または全ての通常発話へ固定手順を注入する案である。
同じ本文が繰り返しコンテキストへ載る費用に対し、文脈ごとの案内を超える便益を示す観測が無いため採らない。
後述の「進捗のセルフチェック通知」は経過時間で届くが、手順本文ではなく短い点検の契機であり、この却下の対象と区別する。

認識合わせについて、UserPromptSubmitは実ユーザー発話の全角`！！`から起動を促す注記だけを返す。
既存の機械注入判定と単一JSONへの合成を使い、同じ案内の反復を共通noticeで抑止する。
記号から感情や認識の一致を判定する責務は持たない。
叱責回数の計数や分類器は、記号がない場面でも必要となる認識合わせの判断を代替できず、
状態と判定の保守を増やすため採らない。
`agent-toolkit:user-confirmation-and-report`の`description`へ認識の不一致と繰り返しの咎めを起動契機として置くことで、hookの検出外でもモデルの判断で起動できる。

`agent-toolkit:user-confirmation-and-report`は同スキルの内容が文脈に無い状態で受けた実ユーザー発話の前に起動する契機を持つ。
この契機は会話の状態（セッション開始、`/clear`、会話圧縮）で決まり、descriptionを読んだモデルの自主的な判断だけでは最初の発話の起動の欠落が残った。
そこでSessionStartの`source`が`startup`・`clear`・`compact`で委譲先でない場合に案内待ちの状態（`user_confirmation_skill_pending`）を記録し、UserPromptSubmitが最初の実ユーザー発話へ起動を促す固定の注記を返して状態を解除する。
先行したPostToolUse(Skill)の起動でも解除する。
判定入力はSessionStartの`source`、既存の機械注入判定およびSkill呼び出しの記録だけであり、発話の意味を判定しない。
両ホストで文脈1つにつき1回だけ返す。
圧縮で文脈を失った後は同じ案内を一度再配送するため、この起動案内の一度性は既存pending状態で保証し、本文hashだけで文脈をまたいで抑止しない。
開始・文脈喪失後の案内には、不具合の有無・原因・直し方を回答や確認へ含める場合の診断前のbugfix起動も示す。
説明の補足と委譲・AWIへ渡す方針にも同じ起動契機を適用し、是正の認可は共通スキルの定義へ接続する。
診断前の条文は`user-confirmation-and-report/SKILL.md`「起動契機」へ集約する。
既存の起動案内と条文配置を使い、新しい状態・発話の意味の分類器・全文の常時注入は加えない。
同スキル未起動のツール呼び出しをPreToolUseで遮断する案は、元へ戻せる誤りの防止であり遮断の対象から外れるため採らない。
SessionStartの文脈だけで起動を促す案は、観測した起動の欠落が同じ常時配送の下で生じたため採らず、応答を始める直前に届くUserPromptSubmitの注記を選んだ。
同スキルの本文をSessionStartへ注入する案は、hookの出力が1万字で切り詰められるため成立しない。

### 例示を含む発話の範囲判断の注記

範囲語か開放列挙と例示を併せた調査・見直し・点検の依頼について、例示を除いた独立した調査を委ねてから結論を確定すると定める規定がある。
規定は`agent-toolkit:user-confirmation-and-report`の次の資料にある。

- `agent-toolkit:user-confirmation-and-report/references/user-utterance-incorporation.md`「原文の保持と取り込み」

2026年10月5日のClaude Codeのセッションでは、メインが発話の受領直後に同資料を全文読んだが、その項が当該発話に当たると判断せず、例示の対象から自ら直列に調べた。
ユーザーの指摘の後に例示を除いた探索を委ねると、例示の外にある対象が見つかった（経緯は`incidents-judgment.md`「誤判定と検証不足」）。
同項の適用条件は発話の字面の語で始まるのに、受領時に該当を示す手掛かりが無かったため、`UserPromptSubmit/user_prompt_submit`が手掛かりを返す。
2026年11月3日には、CI定義の複雑さとpytestの例を併記した調査語の無い指摘に対し、メインが対応範囲をpytestへ狭め、ユーザーがCI全体の話だと訂正した。
範囲を優先する一般則は同節にあるが、当時の注記は調査語との同時一致を条件にしていたため返らなかった。

通常発話と`AskUserQuestion`の自由記述が例示の語（`例えば`・`たとえば`・`例として`）を部分文字列として含む場合に発火し、同節「原文の保持と取り込み」の所在を示して、原文の上位の対象と例示の関係を判断させる。
調査を求める語（`確認`・`調査`・`調べ`・`見直`・`点検`・`洗い出`・`探し`・`チェック`・`レビュー`）も含む場合だけ、調査の切り出し資料の所在と、自ら調査へ着手する前の適用を加える。
資料は`agent-toolkit:delegation`の`agent-toolkit:delegation/references/routing-investigation.md`「コンテキスト消費が大きい調査の切り出し」とする。
フェンス付きコードブロック、インラインコードおよび`>`で始まる引用行は貼り付けた素材であるため、判定の前に除く。
範囲語の有無は条件に含めない。
過去の実ユーザー発話の計測では、例示の語と調査を求める語を併せ持つ8件のうち7件が範囲語の候補を含み、候補は「など」「とか」のような一般的な語に頼るため、条件に加えても発火はほとんど減らず判定の意味も持たない。
「例えば見出しを太字にして」「例えば`make test`を実行して」のような通常の指示にも注記が付く費用は受け入れ、本文は例示が対象そのものなら元の依頼を続けるよう示して、調査や委譲を無条件の義務にしない。
調査語や指摘語を列挙して条件を絞る案は、同義の提案が再び対象外になり分類の保守も増えるため採らない。
手順そのものは本文へ再掲しない。
経過時間の条件と状態の記録を持たず、該当する発話ごとに返し、成立した他の注記と1つの`additionalContext`へ結合する。

この注記は字面の一致した発話へ規範の所在を示す関連配送であり、発火・重複・受信量・再取得の費用も比較する。
同じ条件の同じ本文は共通noticeで抑止し、遮断へ昇格しない。
規範の想起を目的とするチェックをhookに置かないとした2026年9月26日以降の方針は、操作を判定して警告や遮断を返すチェックを対象とし、本注記とは区別する。
現行の判定基準は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/claude-hooks-block-warn-eligibility.md`「遮断・警告フックの成立条件」にある。
旧基準からの変更の経緯は「全件確認の経緯（2026年9月26日）」にある。
字面の一致は資料の所在を示す契機に限る。
発話が同項に当たるかは受領したメインが同項を読んで判断し、hookは発話の意味を判断しない。
字面の一致を契機に規範の所在を示して判断を受領側へ残す形は、全角`！！`から`agent-toolkit:user-confirmation-and-report`の「認識合わせ」を促す注記（`design-hosts-authorization.md`「ユーザーとの認識合わせ」）と同じである。

却下した代替案は次のとおりである。

| 案 | 採らない理由 |
| --- | --- |
| `user-utterance.md`の項を書き換えるか常時規範へ移す | 同項は発話の受領直後に全文読まれたが適用されなかった。同じ層へ文を加えても、当該発話に当てはまる手掛かりが無い状態は変わらない |
| 調査の着手時に起動するスキル（`agent-basics:bugfix`、`agent-basics:search`など）へ参照を置く | 2026年10月2日の対策が`agent-toolkit:add-awi-by-user`へ置いた参照は、同スキルを起動しない調査の依頼に届かなかった。見直しや点検はこれらのスキルを起動しないことがある |
| 全ての通常発話へ`user-utterance.md`の読込を求める注記を返す | 該当する発話は計測で約0.8%であり、残りの発話へ毎回同じ本文を載せる。手掛かりが当該発話に当てはまることも示せない |
| PreToolUseで、例示を含む発話の後の最初の検索コマンドへ通知する | 発話ごとの状態の記録と調査の着手の判定を要し、最初のツール呼び出しより前に届くUserPromptSubmitの注記より遅く複雑になる |
| hookが発話の意味から範囲語と例示を併せた依頼かを判別する | 前段の退けた判別と同じく、会話の意味をhookが判断する |
