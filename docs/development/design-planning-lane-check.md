# レーンの計画確認の設計記録

[設計記録の索引](design.md)と[計画と実行レビューへの受渡しの設計記録](design-planning.md)から参照する主題別の記録である。

## レーンの計画確認

計画ファイルの関連WI集合が選定レーンのうち再開位置を持たないWI集合と一致すること（再開位置を持つWIは再開位置が指す既存計画で続けるため一致の判定対象から外す）、人間由来行の根拠欄が埋まっていることは`plan-check`が判定する。
人間由来の要求を縮小する場合と明示禁止条件を持つ場合だけ、レーン担当は`計画作成完了`でメインの判断を待つ。
条件に当たらない計画は`計画検査完了`を通知して実装へ進む。
計画を省くレーンも、明示禁止条件を持つ場合だけ`計画なし準備完了`で待ち、その他は同じ通知で進む。

確認を全廃すると、人間由来の縮小と明示禁止条件をメインが判断する機会を失う。
集合一致まで毎レーンでメインが確かめる案は、同じ入力への機械的な判定を担当間で反復するため採用しない。

エージェント向け文書を含む書込の認可の境界は、計画の有無によらずWIの要求（目的・対象・完成条件）とする。
レーン担当は計画全体から編集するエージェント向け文書の集合を確定して計画本文へ明記し、同じ集合を`plan-check`の`--agent-rule-path`へ渡す。
この集合は境界の内側で着手時に見込んだ書込先の記録である。
`plan-check`は本文全体で各パスの文字列が現れることだけを確かめ、参照と編集対象の意味的な選別は著者に残す。
新設先と移動先は実在する前でも受理する。
初回に複数の計画へ分けたレーンは全計画を位置引数へ並べて`plan-check`を1回実行し、各計画の構造・行数と、全計画と先行計画の`関連WI`の和集合を選定レーンのWI集合と比べる。
`--agent-rule-path`の各パスはいずれかの計画の本文にあれば受理する。
各計画へ他の全計画を`--prior-plan`で渡して反復する方式は、計画数に応じた反復を要し先行計画側の構造も検証しないため採らない。
要求内の計画外編集は、別worktreeの他レーンとの重なりにかかわらず担当判断で進める。
追加ファイルはcommit差分で分かるため、専用の一覧受渡し、追加ログ、選定記録への反映を要求しない。
WIの要求を超える変更だけを即時通知でメインへ返す。
実行レビューは差分全体を計画・WIと比較し、統合では最新統合先への追随・競合解消・再検証で双方の要求を維持する。
選定の`書込対象`は初期配分と段階の見積もりに使う。
共有選定記録の更新主体はメインと`atk lane integrate`に限り、追加編集の逐次反映は行わない。
事前の通知・一覧受渡し・統合CLIへの追加接続は、既存差分とGit統合から得られる情報を重複管理するため採らない。
同一worktree内の書込所有権は維持する。
変更前はメインが`計画作成完了`の`エージェント向け文書:`行の各パスが計画に現れることを固定文字列検索で確かめ、そのまま`実装開始`で名指しし、計画後の追加も追加ファイル名の往復で追送していた。
メインの工程は`plan-check`がレーン担当の側で済ませた対象ファイルと計画の対応確認を繰り返すだけで判断を加えなかった。
この重複はエージェント向け文書を変える多くのレーンで待機と往復を生んだため、2026年10月19日に、process-wiの変更対象ファイルの管理が厳密すぎるとユーザーが指摘したことを受けて廃止した。
メインが計画全体からパスを抽出して選別する案は、抽出結果に参照だけのパスが含まれ、2026年9月26日と29日にいずれも名指しの欠落と追送の往復を生んだため採用していなかった。
