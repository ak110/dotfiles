# 保持実体の共有とレーン資源の回収の設計記録

[設計記録の索引](design.md)から参照する主題別の記録である。
managed-tempの配置と回収の境界は[一時成果物とキューリポジトリの回復の設計記録](design-storage.md)にある。

## 配布物の保持実体の共有

版付き配布物から起動するagents_serverは、同じ配布元・版に対応する保持実体をmanaged-tempへ作成し、複数プロセスで共有する。
起動側と回収側が使用中かを判断する契約は`_common/plugin_root_leases.py`が所有する。
プロセスの識別とファイル排他で使用中の実体を保護し、全使用プロセスの終了後は既存のmanaged-temp回収へ渡す。
同じ保持実体から再起動した場合もその実体を使い、異なる配布元・版と作成途中の実体を区別する。
配布物の解決と使用登録を共有することで、MCPサーバー数に比例した複製の増加を抑え、使用中の版への参照を維持する。
使用登録と回収は同じ領域別のロックを共有する。
共有しないと、回収側が使用記録を確かめた直後に起動側が登録した実体を削除し得るためである。
起動側の使用登録・複製はこのロックを待って取得し、自動掃引・内部の回収・権限hookは待たずに対象を保持する。
保存証拠と再開入力には従来の7日保持を適用する。

保持実体が使用中かは、未完了の独立WI実行の参照、領域別の使用の記録（PIDと作成時刻が一致する生存プロセス）、領域を絶対パスの引数で直接参照する生存プロセスで判定する。
旧形式・新形式とも、lease登録前に保持先を直接参照する公開MCPランチャーを保護し、親MCPの終了後も未完了の起動に必要な入力を保持する。
使用中と判定した対象は次の掃引（1日後以降）で再判定する。
取得不能な根拠も使用中として扱う。

managed-tempの掃引は、`plugin-root-leases`配下から、記録されたプロセスが存在しないと確かめられた使用の記録と旧い対応能力の記録、対応する使用の記録が無く取得できるロックファイルを削除する。
プロセスの状態を取得できない記録は残す。
ロックの取得側は取得後に同じファイルを保持していることを確かめ、削除されていれば取り直すため、削除と取得は競合しない。
対応能力の記録を書く変更前の版は、ロックを開いてから取得するまでの間にこの確認をしない。
その間にロックファイルを消すと新旧の版が別々に排他を得るため、生存中か状態を取得できない対応能力の記録が残る間は、掃引はロックファイルを消さない。
変更前の版のサーバーが全て終了すると、対応能力の記録は回収され、ロックファイルの回収が始まる。
変更前の版のサーバーが残らない通常の稼働では、配下のファイル数は生存プロセスの使用の記録と、その領域・配布元のロックの数に収まる。
移行期にはこれに生存中か状態を取得できない対応能力の記録と、それが残る間に保持するロックファイルが加わる。

2026年11月の効率化の仕組みの棚卸しで、この共有の方式を候補ごとに確かめた。
容量と重複した依存環境を減らすことはユーザーの要求であり、共有は保つ。
保持実体と環境の共有はその具体化で、独立工程の並列ウォームアップはユーザーの並列化要求に由来する。
3rootの並列ウォームアップは、交互に各3回測った中央値で11.594秒から4.553秒になった（10月30日の記録）。
同じ依存keyの2targetで準備を共有した対照は各1回で0.470917秒から0.345644秒、prepareの起動は2回から1回で、負荷の固定は記録に無い（10月26日の記録）。
どちらも共有実体そのものや更新全体の対照ではない。
共有実体と再読込を含む機構群で少なくとも4件の報告がある（約85秒の起動不能、30秒上限、inotify 94件と上限128など）。
共有だけを無効にする公開操作は確かめていない。
壊れた場合は、既存の明示データ領域、再起動、原本からの再解決で回復する。
共有実体・監視・環境の方式を整理する場合は、容量と同条件の全体所要を比べて決める。

| 候補 | 採否 | 根拠 |
| --- | --- | --- |
| lease対応能力の記録（`capability-<pid>.json`）と、lease導入前のサーバーを見分ける判定（MCPが開いている`agents-server.log`からの状態名前空間の確認、lease非対応のMCPへの無帰属の帰属） | 除いた | 記録はlease導入前のサーバーを見分けるためにあり、サーバーの起動のたびに1件書かれて消す処理が無かった。2026年11月11日のこのPCでは、稼働中のサーバーの最古の開始は同年10月28日で、leaseの導入（10月16日）より前に開始したものは無く、保持実体33件は全て共有形式の接頭辞だった |
| 領域ごとのロックファイルと使用の記録の回収 | 加えた | ロックファイルを消す処理が無く、使用の記録は対象の領域を調べたときだけ消えていた。同じPCで、約25日の間に対応能力の記録72,804件、ロック15,508件、使用の記録408件がたまっていた |
| 共有の範囲（共有をやめてサーバーごとに写しを作る案、共有する範囲を狭くする案） | 変えない | 共有をやめると写しが1件あたり約21MB・約1,200ファイル増え、容量を減らす要求に反する |

lease導入前から動き続け、保持領域を引数で参照しないサーバーが残っていた場合、その領域は使用中と判定されなくなる。
導入から26日以上動き続けたサーバーに限られるため、この残存リスクは受け入れる。
状態ディレクトリへ書く記録は、書く変更と同じ変更で回収の主体と契機を決める。
保持実体が壊れた場合の手段は、サーバーを再起動して原本から解決し直すことである。
新規の共有実体は`agents-server-plugin-root-shared`のprefixで作成し、旧形式と同じ`agents-server-plugin-root`の接頭辞で列挙しながら、作成失敗した部分領域を区別して回収する。
完成済みmarkerはコピー完了後にだけ書く。
全ファイルの台帳や別の寿命管理は加えず、既存の起動、OS参照と回収の境界を使う。
環境変数から状態ディレクトリの解決規則を複写する案は、起動後の環境変更と解決規則の重複が生じるため採用しない。

## レーン資源の終了時回収

process-wiのレーン資源の寿命は、通常の一時成果物とは分けて`atk lane create/delete`が所有する。
createは準備前にsession・lane・Git共通ディレクトリ・統合先・専用branch・worktree・選定原本・固有手順を登録し、prepareの保存結果から準備済みを返す。
統合・最終化の検収と消費工程が終了した資源は、巡回全体の終了を待たずdeleteへ渡す。
deleteは全登録の先行判定と削除直前の再判定から安全な対象だけを回収する。
主repoから照会したworktreeパス・Git登録・branchが全て無いと確定した登録は、守る実体が無いため準備・選定・稼働・cleanの判定を省いて回収する。
照会不能は保持する。
存在するworktreeは担当と外部プロセスの終了、clean、Git登録一致、選定の統合済みを要する。
Gitの保護判定の前に、無視された生成物を除外した`prepare_tree(skip=ignored)`でGitが読む範囲の権限を準備する。
判定を満たした対象はプロジェクト固有のdelete手順を実行し、再判定する。
設定されたWorktreeRemove hookを使う場合は、実行後にworktreeの実体やGit登録が残れば保持する。
hookを使わずagent-toolkit自身が直接撤去する場合は、`git worktree remove`の直前に`prepare_tree(worktree)`で全木の権限を準備する。
固有撤去後にも別所有者の内容が残れば、その所有記録と資源を保持して同じ回収操作で再開する。
branchが残る登録は統合済みを確かめる。
統合状態が`finalized`でbranchのHEADが記録済みの統合入力HEAD（`new_head`）と一致すれば回収でき、それ以外は統合先branchへの祖先判定を用いる。
名前やOSアカウントだけで所有を決めない。

統合後の公開工程で履歴を書き換えても、統合入力HEADとの一致はレーンに追加commitが無いことを示す。
統合先の現在の履歴だけへ回収を依存させると、統合済みの成果が書換えで別OIDとなった場合に資源を保持し続ける。
このため先行判定と削除直前の再判定へ同じ統合記録を使う。
統合後の追加commitや記録の無い旧登録は祖先判定で保護する。

通常のセッション終了時とprocess-loopの子セッション終了後の資源回収は、解放応答を待たずに回収適格性を判定する。
所有側の解放が終わった後の独立した使用は1回の照会で確かめ、残っていれば登録・未回収理由・同じ操作での再開先を保持する。
固定作成先の再利用、deleteとrecoverでも同じ判定を使う。
自動終了が別主体の解放を待って停止し続ける経路を避け、対話的な明示解放の待機は保持する。
通常終了とprocess-loopの子終了後が同じ回収へ接続し、対象リポジトリが`atk lane create --commands-file`へ渡したdeleteのコマンド、worktree、branch、以前の配置でworktreeを収めていた個別managed-tempの順を保つ。
worktreeパスが無い登録ではdeleteコマンドを省き、Git登録だけが残れば強制解除する。
実体の無い登録だけを回収した結果にはlane、worktree、branch、最後に記録したHEADと省いた手順を残し、消失原因と未統合成果の復元を案内する。
未統合・dirty・稼働中・不明・部分失敗は資源と登録、理由と残る操作を保持する。
登録と回収結果への参照は`state_dir`のlanes配下、結果本文は回収対象のworktreeや個別managed-tempとは別に作成したmanaged-tempへ置き、既存の7日保持へ委ねる。
保存先を確保して全登録の判定を保存してから削除するため、記録準備の失敗では資源を残す。
次回開始時はdelete --listで未解決の登録と前回結果を読み、同じ入力で残る処理を再開する。
明示reuse-recordはGit登録と稼働の一致から終了済み資源を新しい所有sessionへ移し、worktreeのパスが無い登録はdeleteによる回収を案内して移管しない。
所有登録は資源の回収まで残る一方、選定原本・対応表・検証記録の既定の保存先はmanaged-tempの7日保持である。
資料の寿命が資源より短いと回収判定と固定作成先の作成が止まるため、createと統合は読めた選定原本からレーンのWI集合と統合状態を所有登録の`selection`へ写し、rebase後の対応表と各操作の実行記録を同じlanes配下の`<lane>-integration/`へ置く。
回収時はこの資料を回収結果と同じmanaged-tempへ移して証拠として残す。
再利用と新しい作成では今回の選定から写し直す。
選定の読取失敗だけを捕捉する案は統合入力と検収資料の失効を残し、managed-tempの保持期間を延ばす案は資源の寿命との一致を保証しないため採らない。
保持値を導入する前の登録で選定原本も失われたものは、`atk lane recover --session-id <所有session>`が元のbranchとHEADを登録の`recovery`へ記録してから作業ツリーだけを解放し、branchと登録を残す。
祖先判定でbranchを削除する通常回収や、成果を引き継ぐreuse-recordでは作成先を成果を失わずに解放できないためである。
作成先を指定しない場合は同じGitリポジトリの主作業ツリーの`.claude/worktrees/process-wi-<lane>`に固定する。
系統を登録したリポジトリでは`.claude/worktrees/process-wi-<統合先ブランチ>-<lane>`とし、系統ごとに並行する処理の同名レーンを分ける。
WorktreeCreate hookへ渡す名前も同じ名前とし、hookが名前から作成先やbranchを決めるリポジトリでも同名レーンを分ける。
Codexなどパス単位で信頼設定を保存するホストへ渡すcwdを、同じリポジトリ・レーンの反復で増やさないためである。
主作業ツリーは`git worktree list`の先頭から解決し、process-loopのworktreeから呼んでもその内側へ入れ子にしない。
配置の決定はcreateだけが持ち、process-wiのメインと対象リポジトリが定めたcreateのコマンドはcreateの返値を使う。
固定パスを別sessionの登録が保持する場合は、その登録だけをdeleteと同じ判定で回収してから再作成し、保持条件に当たれば理由と回復操作を返して止める。
別の一時パスへ回避する案は配置の増加を戻すため、旧配置の登録を固定パスへ一括移動する案は中断成果の再開と衝突するため採らない。
以前の配置の登録はworktreeを収めた個別managed-tempを持ち、reuse-recordと回収で従来どおり扱う。
この登録はレーン資源の作成側が保持する回収入力であり、引き継ぎ側へ同じ値の手書き台帳を要求しない。
同じthreadの追加には、保存済みcommit・計画・引き継ぎから環境を再作成する。
turnごとの一律回収は使用中の作業を失い、別の恒常監視と独自の結果保持期限は既存の登録・終了境界・managed-tempの寿命と重複するため採らない。
主作業ツリー、セッションのmanaged-temp、証拠と他sessionの未登録資源は回収対象にしない。
