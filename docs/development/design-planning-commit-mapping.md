# 付帯作業の所有とWI実装commitの対応の設計記録

[設計記録の索引](design.md)と[計画と実行レビューへの受渡しの設計記録](design-planning.md)から参照する主題別の記録である。

## 計画と実装の付帯作業の所有境界

計画担当は文書変更全体をサイズ、責務、読込時点および重複で比較して整理を計上する。
実装担当は変更起因の超過、責務肥大または契約分散を同じ工程とcommitで整理し、対象追加が必要なら同じ処理中にメインへ返す。

## WI実装commitの対応

履歴書換え後は、作業中計画、保存済み計画と引き継ぎ記録の対応記録を同じ探索境界で取得する。
指定入力に影響対象が欠ける場合は全件を示し、全記録の検証が成立するまで書き込まない。
複数のrewrite mapは順に合成し、最終OIDが現在HEADに含まれるか確かめる。
競合解消で内容が変わった旧commitは明示指定し、件名・相対順・変更パス集合による一意な対応を履歴検収で確かめる。
指定不足、不正指定と曖昧な対応では保存せず、再実行に必要な入力を示す。
単一のmapだけを記録ごとに適用する案は、中間OIDと入力に欠ける計画が更新されずに残るため採用しない。

commit分割の旧OIDには新commitとAWIの組の配列を持たせる。
旧AWI集合を全新commitへ複写すると、分割した変更目的の区別が消え、AWIごとの現在commitの取得が過剰になるためである。
割当の意味は分割担当が確定し、共通のcommit_mappingが各記録の旧AWIの被覆を確認して指定集合だけを継承する。
全記録の確認を保存前に終え、欠落時は元のバイト列を保持する。
scalarの1対1・多対1と既存イベント・本文コメントは同じ読込で維持する。
消費側ごとに別の対応表を作成する案は同期と手作業を増やすため採らず、証拠の参照も同じ表で全対応先へ更新する。

WIに対応する実装commitは、作成時のAWI集合とcommitを、計画（計画なしでは引き継ぎ記録）と同じディレクトリで同じstemを持つ対応記録ファイル`<stem>.wi-commits.jsonl`へ保存する。
`plan-progress`は1回の呼び出しを1行のJSONオブジェクトとして追記し、計画と引き継ぎ記録の本文には進捗の行だけを書く。
取得は`atk run-script plan-commits`で行い、現在の対象worktreeで解決・HEADへの包含を確認する。
1対多・多対1を保持し、履歴検収済みの旧新OID対応を追記してAWI集合を継承する。
履歴の書換えでは、`plan-rewrite`が履歴検収で比較した範囲全体の対応表と書換え前のHEADを受け取り、影響する全記録へ、現在のHEADに無い記録済みOIDの対応だけを追記する。
記録済みOIDが対応表に無い場合（書換え前のHEADから到達できれば対応表の不足、できなければ過去の書換えの未追記）と対応表の誤りは、全記録を検証してから書き込むため、どの記録も変えずに失敗する。
記録ごとに記録済みOIDだけの対応表を作成する方式は、1回の書換えが複数レーンの記録にまたがると手作業が記録数と書換え回数の積だけ増え、追記の欠落を書換え時点で検出できないため採らない。
`git notes`の書換え時の複写は、別の永続台帳に当たり対象リポジトリのGit設定を変えるため採らない。

1回の記録の単位は、現在のHEADのfirst-parentの履歴上にある区間とし、区間内の全commitを同じAWI集合へ対応付ける。
区間の直前のcommitと末尾commitを渡すことで、範囲指定のcherry-pickやfast-forwardの後でもAWI集合ごとに記録できる。
記録・検証の可否は入力の値の性質（履歴上の位置、直列性、未記録であること）から判定する。
末尾commitと現在のHEADの一致を求める条件は、一時worktreeを対象commitへdetachすれば回避でき、誤記録を防がず正しい事後記録を妨げるため採用しない。
末尾commitが現在のHEADのfirst-parentの履歴上にない場合、区間が空の場合、前HEADが末尾commitのfirst-parentの祖先でない場合（解決できないか一意に解決できない値を含む）、記録済みcommitを含む場合は拒否する。
重複は記録対象のcommitを本文の旧形式コメントと対応記録ファイルへ履歴変更の継承を適用した後の対応と比べて確かめ、古い末尾commitの再指定による取り違えを防ぐ。
マージcommitを含む区間は、第2親側のcommitの帰属が一意に定まらないため拒否する。
内部群の統合はマージcommitを作成しない。

範囲での記録には残る制約がある。
未記録の区間で、前HEADと末尾commitがfirst-parent上の位置と直列性の条件を満たす取り違えは検出できず、区間内の全commitが渡したAWI集合へ対応付けられる。
記録し忘れた自分のcommitより前のHEADを渡す場合や、上流の変更をfast-forwardで取り込んだ後に古い前HEADを渡す場合、未記録の過去の末尾commitを取り違える場合が該当する。
操作の直前のHEADを取得し、事後記録ではAWI集合ごとの区間を確認して、この取り違えを防ぐ。
commitを列挙して渡す案も、列挙を`git rev-list`から作成すれば同じ取り違えを通すため、検出力は変わらない。

範囲での記録について不採用とした案と理由は次のとおりである。

- 内部群のcommitを1件ずつcherry-pickし、そのたびに記録する手順へ改める案: 群のcommit数だけ記録の呼び出しと進捗ログの行が増え、fast-forwardマージなど手順に書かれていない取り込み方では同じ失敗が残る
- 群の全commitを`git cherry-pick --no-commit`で1件のcommitへまとめて記録する案: 群の中でcommitを分けた単位が失われる。
  commitの分け方は変更目的ごとに定めるもので、記録の都合で変える根拠にならない
- 群の担当が自分のworktreeで各commitを記録し、取り込み後に`--rewrite-map`で継承する案: 複数の群の担当が同じ計画の記録を並行して書き、読み書きの間に別の担当の追記が失われる

記録先を本文の外へ置くのは、対応記録の消費者が`plan-commits`だけである一方、計画は実装担当、実行レビュー担当、統合するレーン担当、振り返りの主体が全文を読み、引き継ぎ記録も後任が全文を読むためである。
本文に置くと、読むたびに記録を読み込む。
履歴変更の記録は記録済みの全commitの旧新OIDを並べるため、工程が進むほど増える（2026年10月7日の計測で、保存済み計画の4.0%、最大の計画では10.9%を占めた）。
進捗ログは中断後に再開するための粗い工程記録であり、機械だけが読む記録はこの用途に合わない。
付属ファイルは対応の唯一の保存先で、本文へ同じ対応を複製しないため、同期は生じない。
計画バンドルの付属ファイルとして、`atk plans commit`と`atk plans checkout`が計画と共に扱う。

読み取り互換として、本文に残る旧形式の`wi-commits`コメントを付属ファイルの記録より前に適用する。
本文に記録を持つ作業中の計画が新しい版へ切り替わったときに、記録済みのcommitを付属ファイルへ記録し直せないためである（`plan-progress`はfirst-parent上の位置・直列性と重複記録を検証する）。
保存済み計画の既存のコメントと、終了済みのAWIの`## 処理結果`に記録済みの完全OIDと作成者日時は移行しない。
`plan-commits`が対応を取得するのは終了前の計画だけで、完全OIDの記録も短縮OIDと同じく先頭一致で比べられる。

commitの表記は、記録と取得結果のいずれも、対象worktreeで`git rev-parse --short`が返す一意な長さの短縮OIDとする。
エージェントがこれらの記録と出力を読むことがあり、完全OIDは記録とコンテキストを占有するためである。
長さを7文字に固定しないのは、dotfilesでは`git log -1 --format=%h`が9文字を返し、7文字では一意にならない場合があるためである。
入力は短縮OIDと完全OIDのどちらも受理し、記録済みの値と入力の値は比べる前に対象worktreeで完全OIDへ解決する。
後からobjectが増えて短縮OIDが一意に解決できなくなった場合は、取得が対象と次の操作を示して失敗し、誤ったcommitを返さない。

`atk wi adopt --commit`は`## 処理結果`へ短縮OIDと件名の2行を書き、完全OIDと作成者日時を書かない。
ユーザーが確認への回答で短縮OIDと件名を選んだ。
作成者日時と件名は履歴書換え後もcommitを識別できる情報として導入した経緯がある。
adoptの後にCI修正の取り込みでOIDが変わった場合も件名で対象のcommitを辿れるため、その目的は件名で保たれる。

記録先と表記の変更で不採用とした案と理由は次のとおりである。

- 対応記録を廃止し、レーンのcommit範囲かメモでadoptする案: 1つのcommitが複数のAWIへ対応する記録と、対応commitを2件以上持つAWIが実在する。
  レーン単位の記録では、commitからキュー項目の由来を探す照会で同じレーンの全AWIが候補になり、自由記述から対応を特定し直す事象も戻る
- 統合完了時に1回だけ記録する案: 対応を知るのはcommitを作成した担当であり、担当交代の後任が自由記述を読んで対応を特定し直す事象が戻る
- 追記型の記録を、AWIごとの現在値を上書きする形へ変える案: 取得の判定と既存の継承を保ち、変更を記録先とOIDの表記に限るため採らない
- Gitのnotesで対応を持つ案: `notes.rewriteRef`を設定しないとrebaseでnotesが失われる。
  全対象リポジトリのローカル設定の変更と、並行レーンが共有のnotes参照を同時に更新する競合の扱いが新たに要る
- adoptの`## 処理結果`を短縮OIDだけにする案: push先がremoteのHEADのbranchと異なる場合はCI修正を原因commitへ取り込んでforce pushするため、adoptの後にOIDが変わりうる。
  短縮OIDだけではその後のcommitを辿れない

公開trailerはWI識別子を公開しない方針と両立しないため追加しない。
別の永続台帳は既存記録との同期を必要とし、説明文や件名からの再導出は担当交代で観測した引き直しを残す。
意味的な対応は生成側が確定し、Gitの同一性はGitへ委ねる。
2026年10月4日の既存3commitとWI終了は再実行せず、過去の自由記述を一括移行しない。
