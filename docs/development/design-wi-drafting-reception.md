# 既存AWI更新と調査の受領検収の設計記録

[設計記録の索引](design.md)と[WIキューと要求本文の設計記録](design-wi.md)から参照する主題別の記録である。

## AWI本文起草の分離

### 既存AWI更新時の保留

既存AWIの更新・修復・採否の見直しでは、メインは更新の必要か具体的な懸念が分かった時点で`atk wi hold`を実行し、その後に認識合わせ、対策の調査、対象発話の逐語内容・時点・文脈の受け渡しへ進む。
出所は証拠を使う担当が必要時に抽出する。
順序は保護、要件確定、委譲、検収、解除とする。
2026年10月3日の手動登録で、既存AWIへのStop対策を調べてから2件を保留し、調査の間は自動処理の取得候補に残っていた（別セッションの取得は観測していない）。
共通定義は調査前の保留を既に定めていたが、委譲元の手順は保留を`agent-toolkit:/share/add-wi-parent-inputs.md`「渡す入力」の準備へ置き、更新の必要が分かった時点より後に位置付けていた。
保留を同書「起動前の前提」の先頭へ移し、`add-awi-by-user`、是正要求の受領と完了報告後の追加要求も同じ手順へつなぐ。
採否が未確定でも保留するのは、保留が、判断までの間に古い要求が処理されることを防ぐ操作であるためである。
状態の確認と保留の間に他主体が処理を始めた場合は`atk wi hold`の失敗で分岐する。
調査を自動で止めるhookや、新しい保留状態・所有フラグを設ける案は、更新の必要が自然言語で判明する時点をCLIの入力から得られず、誤停止と保守の費用を増やすため採らない。
既存AWIの更新で対象が`processing`にある場合、メインは保留せず、書き換えたい内容を新規投入の要求として渡し、処理中の項目へは`atk wi edit --append`による追記だけを行う。
保留を経由して置き換えた本文は、その項目を処理中のセッションへ届かず、`unhold`で項目が`inbox`へ戻って別のprocess-wiの実行の取得候補になるためである。
保留による本文置換を構造で防ぐため、エージェント環境の`atk wi hold`は`processing`の項目を`--state=processing`の明示なしに保留しない。
処理中のセッション自身は、本文の修正が必要な元項目を`--state=processing`で保留できる。
回答待ちの元項目は保留せず、依存を保存してから`inbox`へ戻す。
保留前の状態を記録して`hold`の項目の本文置換を拒否する案は、`hold`の項目の編集を`inbox`と同じ条件で許す方針と衝突するため採らない。

### 調査と手段の受領検収

WI投入担当は対象ごとにユーザーの方針と判断の記録を調べ、現在の逐語要求と比べる。
記録との衝突が見つかったら、`agent-toolkit/share/rules/common/01-agent.md`「方針が衝突する場合の優先順位」と成立済みの認可を現在の明示要求へ適用してから、残る未確定事項だけを続行できない理由として返す。
以前は範囲語で対象集合を示す依頼が記録の判断の変更を名指ししない場合を一律に未確定としていた。
2026年10月3日のUWI情報量のAWI起草で、UWI全般の不要情報を減らす依頼が報告用UWIを含むのに、全内容を保存する旧方針を名指ししていないことを理由に追加の確認を提案し、委譲元が原文と優先順位の適用を追送するまで起草が止まった。
方針調査そのものは、未合意の目的変更を投入前に検出する目的（導入時の目的）を保つため残す。
変更の意向を含まない調査の依頼、未合意の選好・認可、硬い制約やホスト契約との両立不能は引き続き委譲元の確認へ返す。
確認の発行は委譲元だけが担う分担も変えない。
hookや毎回の独立した確認担当で解釈を代替する案は、自然言語の適用を代替できず既存の判断点の改訂で対処できるため採らない。

完成条件へ固定する比較・検収・工程の指定は、起草と受領の双方で、ユーザーが明示した要求か起草側が選んだ手段かを分けて扱う。
起草側の手段は達成すべき状態と、その手段を固定する必要性を分けて判断し、必要性を示せない内部の検証手順は計画工程へ委ねる。
WI投入担当は起草の読み直しと投入前の独立した読み直しでこれを判断し、メインは受領時に手段が必須の完成条件へ昇格していないかを確かめる。
昇格を正当化する根拠は原要求か品質判定の必要性に限り、委譲元自身の追送やWIに書かれている事実は根拠にしない。
追送を起点とする手段の必須化が、起草者の読み直しと委譲元の要求比較のどちらでも見逃されたためである。
付随型では両工程を既存の担当と親の検収へ置き、別のレビュー担当は設けない。
専念型ではこの受領時の確かめを投入前レビューが担う。
処理を実施しない・延期する保護条件も同じ扱いの対象とし、メインは受領時に、保護条件ごとの本文の根拠が確定した要件、規範的制約または観測済みの欠陥であることを確かめる。
2026年10月5日、WI投入担当が外部文書の記述だけを根拠に管理daemonの停止を見送る条件を`判断の変更`として加え、メインは確定した要件との両立だけを確かめて受理し、後続の実装が状態取得の問い合わせ処理まで作り込んだ。
保護条件は後続の担当が満たす対象として完成条件へ入るため、投入前に根拠の種類を確かめられる最後の箇所が受領時の検収になる。
判定基準は`agent-basics:writing-standards/references/design-heuristics-mechanisms.md`「自作機構の兆候と自問」へ集約する。
起草（`awi-body-evidence.md`「調査結果と判断根拠の記述」）と受領（`add-wi.parent.md`「受領と検収」）が参照する。
保護条件か否かと根拠の種類は文意の判断であり、`atk wi add`の構文の確認やhookでは判定できないため自動検出は設けない。
判断を渡す直前には、理由へ使う事実を同じセッションの観測へ、ユーザーの方針を記録の所在へ対応付ける。
未検証の前提はWI投入担当の既存の裏付け工程で確かめ、現物と異なる場合は訂正する。
採否は要件と品質への影響を比べ、変更量だけで既存側を優先しない。
理由の真偽をラベルだけで保証する自動遮断は意味判断を複製し、付随型に投入前レビューを置く案は既存の担当と検収の責務を重ねるため設けない。
全観測の再実行も行わず、記録と条件が一致する観測の再利用を維持する。

委譲元の判断にはユーザー要求の対象集合を委譲元の語で定義した基準を置かない。
ユーザーの範囲は原文の逐語と出所・該当例・根拠付きの追加・承認の出所付きの除外に分けて渡す。
範囲の記録書式は、`agent-toolkit:user-confirmation-and-report/references/user-utterance-incorporation.md`「原文の保持と取り込み」にある。
2026年10月2日に置いた、対象を定める判断を原文と比べて比較結果を理由へ書く項は、2026年10月10日の事象で比較が書かれたまま縮小を通した。
比較は言い換えたのと同じ枠組みで行われ、加えた条件を軸として列挙させる記録の形が無かったためである。
書式は原文を集合のまま保つため比較そのものを不要にし、縮小は承認の出所付きの除外としてだけ現れる。
却下した案は3つある。
本人による比較の箇所を他の記入欄へ追加する案は、効果不足が観測された処置を同じ形で広げるため採らない。
付随型で投入前に独立したレビュー担当を置く案は、親の受領検収と責務が重なり、書式で比較を不要にできるため採らない。
記述が集合を限定するかをhookで検出する案は、文意の判断を要し、意味の判定をhookへ置かない方針（[design-hooks.md](design-hooks.md)）に反するため採らない。

範囲語か開放列挙と、例示か理由を併せ持つユーザーの依頼を起点とする要求では、委譲元が受け渡しの前に例示を伏せて独立に調査し、その結果を`確定済みの観測`へ含める。
調査しない場合は、観測が例示の近傍に限られることを書いて渡す。
WI投入担当は例示を含む逐語本文を受け取るため例示を伏せた調査者になれず、`確定済みの観測`は記録と条件が一致すれば再実行されないため、例示に偏った観測が対象集合の全体として本文へ固定されるためである。
調査は`agent-toolkit:add-awi-by-user`の要求単位の確定前に置く。
担当の調査結果を要する問いへの回答は、親の返却検収後に行う。
WI投入担当の手順へ例示を伏せた調査を加える案は、メインもユーザーへの回答に同じ調査の結果を要するため同じ調査を2回実行するうえ、渡す観測が調査の結果を含めば担当側の起点も偏らないため採らない。
逐語本文が範囲語と例示を含むのに観測が調査を含まない受け渡しを`atk agents start`やhookで検出する案は、「など」「例えば」がほとんどの依頼に現れて誤検出が多く、観測が対象集合を代表するかは意味の判断であるため採らない。
