# 方針・意向: 過剰設計

## 過剰設計の抑制

2026年8月にユーザーが「規範・フックがオーバーエンジニアリングに陥っていないか」と指摘し、コーディングエージェントが規範を強化した領域である。
現行の規定は`agent-toolkit/share/rules/common/01-agent.md`「判断指針」と`agent-basics:writing-standards`の`references/design-heuristics.md`にある。

2026年10月21日のユーザー指示では、役割定義のfrontmatterの静的整合性をテストで保証し、起動時は最小の確認にする設計案が示された。
同日、ユーザーは過剰設計を避ける発想を継続的に持つよう求めた。
保証を置く工程も比較する基準は、既存の`design-heuristics.md`「設計案の予備選別」へ統合した。
2026年11月8日、ユーザーが選んだ「品質を保って総費用を減らす」という目的に対し、コードの構造、既存の自動解析、公開操作からの検証を、自然言語の指示への投資より先に比較する基準へ具体化した。
各段を必須工程にせず、必要な結果を最小の構成で得る段で完結する。
意図・認可・外部契約の文章と独立した文脈のレビューを保持し、決定論的であることだけでは新しい検査を導入しない。
現行の選定基準は`agent-basics/skills/writing-standards/references/design-heuristics-screening.md`「設計案の予備選別」と`design-heuristics-decisions.md`「案の採否と実施順の判定」にある。

- ユーザー本人が設定して使い、原因が分かれば運用で直せる機能では、設定ミスなどへ備える専用処理やフォールバックを増やさずエラーで終了させる。
  開発者向け・システム管理者向け機能もシステムの前提に応じて当てはめる。
  現行の原則は`agent-toolkit/share/rules/common/01-agent.md`「QCDと3段判定」にある。
  判断観点は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/design-heuristics-mechanisms.md`「自作機構の兆候と自問」にある（2026年10月14日、ユーザー指示）
- 規範改訂では将来課す作業と継続費用を採用前に期待成果へ照らし、寄与に比べ負担が大きい案は目的を保つ案へ選び直す。
  案の比較は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/design-heuristics-decisions.md`「案の採否と実施順の判定」にある。
  追記の判断は同スキルの`agent-basics:writing-standards/references/agent-documents-additions-additions.md`「規範追記時の判定」にある（2026年10月15日、ユーザー指示）
- 対策の立案前に「そもそも対策が必要な問題か」から再検討する
- 何もしない案・既存操作だけの案を新機構案と同じ階層で比較し、
  単純案が目的を満たすなら新機構を採用しない
- 規範を追加する際は、同じ計画内で既存規範の削減・統合を検討する
- 数回のツール呼び出し削減程度の知識追記は、常時コンテキスト増加の害が上回るため
  不採用とする。
  現行の規定は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/agent-documents-additions-additions.md`「規範追記時の判定」にある
- フックによるブロックは、エージェントの手違いに再考を促す手段として使い、
  誤動作を完全に封じる手段として扱わない
- フックが実行時の値を確認できることだけでは、その存続理由にならない。
  元の要求と観測した事象の双方に照らし、無ければ達成できない結果を確認する
- フック全体で解消手段を伴わないblockを置かず、blockは通知を受領した主体が同一ターン内の行動で解消できる条件に限る。
  外部事象の完了、他主体の稼働状態、直前ターンで確定済みの内容など、主体が変更できない状態を条件にしない
  （2026年8月、ユーザー判断。待機中の調整役を`SubagentStop`でblockした結果、無操作のコマンド呼び出しとユーザーの中断が反復した事象に由来する）
- 読み取り専用の委譲では、依存の解決と実行に伴って再生成される実行前提が対象成果物を構成しない場合、その変更を結果の不採用と報告の理由にしない。
  対象成果物への書き込みだけを検出対象とし、実害を観測した時点で復旧する
  （2026年9月1日、ユーザー指示。読み取り専用の担保へ厳密な検証費用をかけすぎない判断による）
- 迂回の抑止自体を目的とするチェック処理は新設・強化せず、迂回可能な余地を残す
- 既存の機構で得られる判定を自前で組み立てる案は、過剰設計の兆候として扱う。
  該当するのは、内容の同一性を判定するハッシュ値の算出、GitのOIDの写し取り、実行主体の申告の記録などである。
  採用の前に3つの問い（オーバーエンジニアリングではないか、無いとQCDが悪化するか、保守コストに見合うか）へ答える。
  現行の規定は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/design-heuristics-mechanisms.md`「自作機構の兆候と自問」にあり、
  `agent-basics:review-standards`と`agent-basics:bugfix`の判定箇所が同節を参照する
  （2026年9月23日、ユーザー指示。AWI投入時の整合記録`scope_alignment`が、消費側を持たないまま
  frontmatterへSHA-256を保存する機構として成立していた事象に由来する）
- 文書の合計行数の上限は設けない（2026年7月末のユーザー回答で廃止した運用を復活させない）。
  ファイルごとの行数は、2026年11月11日のユーザーの判断で、種別ごとに上限と整理後の行数を1組だけ定め、上限を超えたファイルだけを整理後の行数以下へ整理する（Markdownは250行を超えたら150行以下、ソースコードとテストコードは1,000行を超えたら600行以下。改行数で数える）。
  上限の判定は実装後の機械チェック（dotfilesでは`scripts/check_file_lines.py`）だけが行い、上限以下のファイルには行数の測定・記録・削減を求めず、計画とWIの起草で行数を扱わない。
  数値は1ファイルを読む費用を約1万トークンに収める予算から導き、整理後の行数は上限の60%（2分割したときの固定の記述を見込んだ値）とした。
  過去の2方式との対応: 上限だけを判定した方式（2026年7月19日〜28日）は上限の直前まで埋まって編集しにくくなった。
  今回は整理後の行数まで下げるため上限の直下に貼り付かない。
  目標と上限の2段階の方式（2026年7月）は、計画段階の全件の行数の測定や、上限に達していないファイルの削減を招いた。
  今回は上限以下で行数を扱わないと定め、行数の確認を求める規定を取り除いた。
  `removed-mechanisms`の「文書の合計行数へ一律の上限を課す運用」とは合計とファイルごとで働きが異なり、合計の上限は復活させない。
  重複記述の統合は引き続き常に検討する
- 主張を際立たせるためだけの対比フレーミングは、成果物と委譲プロンプトを含む全ての文章で避ける。
  読み手が取り違えやすい実在の選択肢や誤解を除く対比（例: `== None`ではなく`.is_(None)`を使う）は1文で書いてよい。
  2026年8月には既存文書の用法を自然で必要と判断し、一律の禁止・機械検出・辞書登録を追加しなかった。
  2026年10月11日のユーザー指示で全面禁止とし、否定は独立した事実の文で示すことにした。
  2026年10月26日、規範の書き直しで書き手モデルが誤用を具体的に示す対比を多数加えた。
  その後、既存方針の直接適用は不自然で読みにくいのではないか、方針レベルで見直しを検討すべきというユーザー指示により、
  強調のための対比だけを避ける現行の形へ緩めた。
  `agent-doc-tone`の注意語からも「ではなく」を外した。
  2026年10月26日のユーザー指示により、肯定文の対象の一部を除く場合は別の否定文を置かず、同じ文で限定する。
  説明: 受理する入力を直接示し、整数の指定から分かる除外を省く。
  現行の規定は`agent-toolkit/share/rules/common/01-agent.md`「使用言語」にある
- Codexで既存規範を想起させる場合は、短い確認観点と`AGENTS.md`・agent-toolkit規範の原本参照だけを、計画完成時と圧縮後の低頻度境界へ渡す
- 全文注入が必要になった場合も、通知本文の原本1箇所だけを置換し、未使用のモード分岐を追加しない
- 通常用途の入力形式を手順文書へ書くことで目的を満たす制約は、フックのblockで強制しない。
  実行前の受理形式の確認は、手順・規範・スキルが実行できる形で示していない入力を自ら選ぶ場合に限って求める
  （2026年9月9日、ユーザー指示。同一セッションでヘルプ出力を観測していない`atk`サブコマンドの実行をblockする仕組みを、
  手順文書への記載で置き換えた事象に由来する）。
  同じ制約を`AskUserQuestion`の本文へ適用する処理が再び置かれたため撤去した（2026年9月16日、ユーザー指示）。
  受理形式の制約とユーザー向け提示本文の扱いは
  `agent-basics/skills/writing-standards/references/claude-hooks-block-warn.md`の「遮断・警告フックの成立条件」にある
