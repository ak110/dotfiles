# 担当の責務と工程間の知識境界の設計記録

本書は[設計記録の索引](design.md)から主題別に分割した記録であり、機構の目的、構造の理由、知識境界と却下した代替案を保持する。
実行時に適用する規範は、各節が参照する現行のルールファイルとスキルが定める。

## 委譲の共通契約

親の会話履歴の大半を委譲先も要する作業では、Claude Codeの`Agent` forkとCodexの`spawn_agent`全履歴forkを使える。判定基準は`agent-toolkit:delegation`の`references/routing.md`へ集約し、ホスト別の起動形だけを各runtime資料へ分ける。forkは起動時点の会話を入力として共有するため、委譲プロンプトへ同じ背景を書き直さずに済む。独立文脈レビューと工程別モデル設定のある委譲は、先入観のない評価または指定effortを守るため新規セッションの起動を保つ。agents_serverへfork機能を実装する案は、ホスト標準の起動手段でユーザーが選んだ結果へ到達でき、別の実装と保守を増やすため採用しない。

単発の委譲は常時規範の基本委譲契約を適用し、対象、読取・書込権限、完了条件および受領後に成果物を直接確かめる検収を確定する。
工程別モデル設定、複数主体調整、継続、停滞検知または巻き取りを使う高度な委譲だけが、`agent-toolkit:delegation`の手順を適用する。

委譲元が委譲プロンプトへ載せる値に起因する欠落は、委譲元が起動前に防ぐ。委譲先の`<役割名>.subagent.md`が要求する必須入力が委譲プロンプトにそろっていること、絶対パスで示す入力のうち起動時点で作成済みのものが実在すること、および委譲先が受領した値から自ら解決して読むplugin配下の資源が実在することを、委譲元が起動前に確認する。委譲先の`<役割名>.subagent.md`は、必須入力がそろい、参照する資源が実在するかを着手前に再確認して差し戻す手順を持たない。欠落の検知点を委譲元へ一本化することで、委譲先の起動、規範と対象の再読、委譲元の再判断を重複して費やす往復が生じない。必須入力と資源の確認は委譲元が自ら行い、解決した絶対パスを委譲先へ渡して実行させない。委譲先がplugin配下の資源を自ら解決する手順は、plugin導入版の更新時に古いパスを使わないために維持する。判定の基準は、入力や資源の欠落を委譲元が防げるかである。絶対パスの実在のように機械的に確認できる項目だけでなく、担当種別ごとに異なる必須入力の完備と、委譲元が組み立てる契約の各条項の充足も、値を載せる主体が委譲元である以上は委譲元の確認対象とする。委譲先へ差し戻しを残すのは、Codex互換レイヤーが自ホストのplugin導入情報から起点を確定する処理のように、委譲先自身の実行環境に起因し委譲元から観測できない事象に限る。

実行中に`<役割名>.parent.md`を更新した場合に加え、`<役割名>.subagent.md`を更新した場合も、両者を同一のplugin rootから原子的に適用する。統合済みworktree側に両者がそろい委譲起動契約を満たす場合だけ、そのrootの`<役割名>.parent.md`と`<役割名>.subagent.md`のパスを後続委譲へ採用する。いずれかが欠ける場合や契約確認が不成立の場合は、稼働開始時のplugin rootにある両者へそろえて戻す。どちらか一方だけを切り替える案は、版ごとには整合する必須入力名が版間で一致しないため採用しない。

`agents_server`の`start`の`cwd`は委譲先が作業場所とGit状態を解決する起点とする。同じworktree、Git共通ディレクトリ（`--git-common-dir`）、linked worktree、現在branch、リポジトリ直下の規範は名前付き入力へ重ねない。
名前付き入力は、対象識別子、成果物のパス、観測境界、別worktreeの統合先など、呼び出し側だけが保持する状態へ限定する。省略可能な入力の省略時の値と行が無い場合の解釈は`<役割名>.subagent.md`が持ち、呼び出し側は省略時の値と一致する行を送らない。
この分離により、環境情報の基準をGitと`<役割名>.subagent.md`の契約へ集約し、委譲元との不一致を表現できない構造にする。

Claude Codeで委譲先がさらに読み取り専用調査・レビューを委譲する場合は、起動前にmanaged-tempの中の成果ファイル絶対パスを確定する。
専用の`<役割名>.subagent.md`かagent定義がある場合はそれが定める完全な完了報告を成果形式とし、委譲プロンプトへ汎用形式を複製しない。
孫は返信先を解決できない場合も完全な最終結果を成果ファイルへ同期的に確定してから終端し、直接の委譲元は実行時に観測できる委譲先の終端後に同じファイルを再読して検収する。
完了通知の到着・祖先からの中継は成果本文の受領条件にしない。
一方、委譲先の終端を観測できない場合、稼働中の途中内容および終端後の欠損・読取不能・不完全な成果は成功扱いせず、続行できない理由を返して一時領域を保持する。
読み取り専用の委譲先へ実装担当限定の所有プロセス終了証拠を要求する案は観測不能な受理条件を生じさせるため採用しない。
全委譲へ成果ファイルを要求する案は通常の直接委譲へ恒常的な入出力を増やすため採用せず、配送不着を観測した孫以深の読み取り専用調査・レビューへ限定する。

固定書式で返す委譲先が想定外の結果を観測し、`SendMessage`で即時通知できない場合は、指定形式の末尾へ`想定外事象:`の1行を追加して委譲元へ渡す。
返却手段を増やさず地の文の禁止だけを1行分緩めるのは、固定書式の機械判定を保ったまま、重要度の高い事象が抑止される事態を防ぐためである。

分配または分類の結果を固定書式で返す委譲では、返す側が受領した入力集合と返却する区分の集合を突合し、過不足と重複の不在を1回のコマンドで確認してから返す。受領側も同じ突合を再実行してから後続工程へ進む。目的は入力の一部が返却から欠落した状態を、分配を委ねた作業の終端で検出することである。構造の理由は、返却の妥当性を判定できる知識が返す側と受領側の双方にあり、返す側だけの確認では返却本文の破損を受領側が検出できず、受領側だけの確認では差し戻しの根拠となる中間状態を返す側が失うためである。知識境界として、入力集合の基準は委譲プロンプトが挙げた識別子とし、返す側は委譲プロンプトにある識別子を区分へ写像する責務だけを持ち、区分の定義そのものを再設計しない。
確認を受領側だけに置く案は、返す側が保持する分配の中間状態を失い、差し戻しの粒度が返却全体になるため採用しない。区分ごとの件数の一致だけを確認する案も、同じ識別子が2つの区分へ現れる誤りを通すため採用しない。

委譲先が複数値を返し、受領側が要素ごとの対応または集合を確認する欄はJSON配列で表す。`adoptを延期したAWIとcommit`はAWIファイル名とcommitの対応を持つオブジェクト配列、`延期後にadoptしたAWI`はAWIファイル名の文字列配列とし、0件はどちらも空配列とする。`変更したエージェント向け文書`はエージェント向け文書のリポジトリ相対パスを重複なしの文字列配列とする。受領側は配列の形式を確認し、既に読んだ文書か残工程で読むことが確定した文書だけを統合先worktreeから再取得する。返す委譲先と受領する委譲元は同じ配列境界を契約テストで検証する。区切り文字を含む散文値は、複数件の境界とAWI・commitの対応を一意に復元できないため採用しない。

知識境界として、委譲の要否判定は`agent-toolkit/rules/01-agent.md`が持ち、
`agent-toolkit:process-wi`は委譲の要否を判定する場面だけを定める。
工程別モデル設定を持つ委譲では、委譲する工程を定める節が用いるキーを指定する。
却下した代替案は、割り込み作業の委譲先を一律に単一のキーへ固定する案である。
工程ごとに適した委譲先が異なり、用途を定めたキーの適用範囲を越えるため採用しない。
公開工程の工程をメインが自ら実行する案は、終端担当が所有するCI修正（CI修正担当の起動と受領）を含む工程全体がメインのコンテキストを消費し、ユーザー判断への応答余地を狭めるため採用しない。
終端担当へ専用の設定キーを新設する案も、終端工程の判断量が実装と同等であり`high_tier_model`の適用範囲に収まるため採用しない。
レーンの終端操作をメインへ残す案は、レーンの最後のレーン担当が同じ資源とrefまたは7文字以上の一意な短縮OIDを保持しており、メインへ戻すと同じ値の受け渡しと再確認が増えるため採用しない。
統合するレーン担当の手順を実装担当の`exec.subagent.md`へ担当種別として同居させる案は、同書の冒頭がコミット単位の実装を責務とし、必須入力へ実装するコミット単位を要求し、実装手順が計画ファイルの編集を禁じているため採用しない。同居させると、実装しない統合の手順に対して同じ行為の義務と禁止が並存する。
新しい委譲境界へ`<役割名>.parent.md`と`<役割名>.subagent.md`のペアを設けない案も、委譲先が読む恒常手順が委譲プロンプトの本文だけになり、起動のたびに手順を複製することになるため採用しない。
観点、読者像、返却項目および権限を毎回同じ内容で定める委譲は、委譲元の規範に契約を置くと起動のたびに委譲プロンプトへ書き直され、委譲プロンプトが長くなり表現も揺れる。
このため投稿前レビュー（`external-write-review`）、自動コードレビュー監査（`copilot-review-audit`）、文章成果物の読者別探索（`reader-fit-review`）、一括置換後レビュー（`bulk-replace-review`）はペアで定める。委譲元は対象と実行時の値だけを渡す。
読み取り専用の3件は`mode: explore`で軽量に起動する。
委譲先へ届く規範とスキルは限られる（`agent-toolkit/skills/writing-standards/references/delivery-scope.md`の配送範囲表）ため、判定基準を`<役割名>.subagent.md`の中で完結させる。書込を伴う監査は通常委譲の`high_tier`とする。
読者別探索の初回から、実行レビュー担当が変更前・現行・今回差分と直接影響範囲を渡す。再レビューでは前回確認版とレビュー指摘管理表から読者ごとの修正範囲・未解決事項を生成する。新規文書と新規回答は全文を今回差分とし、既存文書の変更外の不良や範囲外の新要件を通常指摘へ混ぜない。
読者別探索担当は全文を文脈として読み、指摘候補は修正箇所と直接影響範囲から選ぶ。
前回確認版はレビューしたHEADとGit管理外本文の複製をmanaged-tempへ記録し、同じthreadでは保持し、引き継ぎ時は宣言済み入力で渡す。
質問への回答下書きも同じ比較に含み、対象のない読者は探索を再起動しない。読者ごとの終端statusと返却本文を確認し、失敗・本文欠落を指摘0件へ変換しない。公開waitのnext_actionと既存の回復契約に従い、同じ読者の結果を回収してから判定する。
比較元が不足したまま全体探索へ戻す案は、無関係な既存部分を再レビューへ戻すため採用しない。
探索指摘の採否は受領したレビュー担当が確定し、実行レビューでは走査結果の全指摘をレビュー指摘管理表の行または不採用理由へ対応付ける。
返却前に各指摘の対応を確かめ、採用分の統合だけで受領を終える案は未対応の指摘を検出できないため採用しない。
成果物、読者、対象コマンドが毎回異なる単発の起草（`start`の`write`）、コマンド実行（`start`の`shell`）、探索（`agent-toolkit:delegation`の`references/routing.md`）は自由本文の起動に残す。契約の大半が起動ごとの値であり、ペアへ移しても委譲プロンプトは短くならないためである。

### 担当間の知識境界

メインはキュー、ユーザー合意、公開認可、要求と調査対象、確定済み計画ならびに実装結果を知り、工程全体の完了を所有する。
メインは要求を再定義せず、各担当の起動、同一threadの継続および工程遷移を自ら制御する。
実装担当は担当単位と対象worktreeを知るが、他のレーンの統合順や公開時機を決定しない。
実装担当は自身が起動した外部プロセスとバックグラウンドタスクの実行識別子と停止操作を知り、
同じworktreeの書込所有権を手放す前に全ての終了を確認する。
委譲元は完了報告、報告されたツール終了結果または実行識別子、`TaskStop`の結果および実行時に公開され呼び出しに成功した`ListAgents`の状態を知り、
同じworktreeへ実装担当を引き継ぐ場合に終了確認の成立を検収する。

職務として列挙されていない判断の確定主体は、委譲先ではなく委譲元へ一本化する。
委譲先は判断の発生を報告し、未確定の判断に基づく成果物の変更、再委譲、工程の打ち切りおよび巻き戻しに着手しない。復元や受領済み素材の削除にも着手しない。
委譲元は返却された判断を確定し、必要な再指示または工程停止を選択する。
この境界は誤った判断のまま操作へ進むと反映済みの成果が失われる一方、差し戻して待てば損害が生じないという損害の非対称性に基づく。

知識境界として、委譲先が持つのは自身の定義または`<役割名>.subagent.md`が列挙する職務、受領した入力、および判断が未確定である事実と必要な判断である。
委譲元はユーザー合意、公開認可、計画の適用範囲など、委譲先の職務として列挙されていない判断の確定を所有する。

調整専任の委譲先へセッション記録を読ませ、受領した指示の真正性を自ら判定させる案は採用しない。
セッション記録を判断材料として渡しても、真正性の判定主体を委譲先へ移すため、職務外の判断を下位へ移すだけになる。
真正性や合意の確認が必要な場合は、委譲元が直接受領したユーザー指示と既存の確認手順で確定する。

この境界により、計画単位の起動・統合費用を抑えながら、調査・実装・公開判断の混同を防ぐ。
単一主体へ全工程を集約する案は、独立した検証と公開認可の境界を失うため採用しない。
同じ計画の実装単位を複数の実装担当へ同時並行で分散する案も、同一作業ツリーに複数の書込所有者を同時に置くため採用しない。
実装単位間では、先行する実装担当の終端を確認してから次の実装担当へ逐次引き継げる。
機械的な`Read`拒否だけに依存する案はBash経由を扱えず、認証情報を別領域へ複製する案は信頼境界を越えるため採用しない。

### 委譲プロンプトと`<役割名>.subagent.md`

メインは委譲先専用の`<役割名>.subagent.md`および作成規範を読み込まず、`<役割名>.subagent.md`は役割名で、作成規範は絶対パスで各担当へ渡す。
agent-toolkitプラグイン内の`<役割名>.subagent.md`は、`agents_server`がメインから受け取った役割名を自身のplugin rootの`share/`直下へ解決する。作成規範の絶対パスは、メインが注入済みの`agent-toolkit:delegation`の所在から現行plugin rootを確定して解決する。
委譲元は新規成果物の絶対パスを起動時に指定するか、委譲先から報告を受領してから観測する。
AWI計画では、委譲元が既存ファイルと衝突しない保存先の絶対パスを確定する。
通常型のAWIの下流主体は、担当ファイル名と対象リポジトリを受け取り、キューCLIから保存本文を独立に取得する。
専用の原文ファイルを作成せず、本文を委譲プロンプトへ複製しない。
直接受領した人間由来のユーザー指示、ユーザー合意、参考素材または処理対象資料は、受領順を保持した素材レコード集合として渡す。
各レコードは種別、出所および引用範囲をこの順で保持し、逐語本文・回答全文をレコードの末尾へ続ける。
キューにない素材の逐語本文・回答全文は、計画外の明示入力として調査、起草、初回レビュー、再レビューへ渡し、計画本文へ転記しない。
初回起動後の追送ユーザー発言は、レーン担当が逐語本文、入力種別、出所、引用範囲を保持して真正性を保証し、レビュー担当は本文との整合だけを検収する。
調査担当は同じキューCLI出力のfrontmatterから投入元識別子を取得し、文字列を改変せずメインへ渡す。
`source`欄がない場合は値なしとして渡す。
レーン担当は全ての投入元で、原文が方針改訂を要求するか、明示した検証手段が現行方針に適合するかを先に確かめる。
この提案成立性の事前確認後に、投入元識別子に対応する生成手段固有の優先順位を適用する。
frontmatterの`source`からエージェント由来と判定される項目は後段で優先順位4に準じて懐疑的に判定する。
投入元識別子で由来境界を判定するが、投入元識別子やAWI本文からユーザー認可を推定しない。

別コンテキストに専用の起点の文書（`SKILL.md`、agent定義または`<役割名>.subagent.md`）を渡す構成では、委譲元は目的、入力、制約、期待出力および検収を定める。
委譲先の再走査、累積再監査、証拠抽出などの内部手順はその起点の文書だけを基準とする。
完了報告の返却方法の契約も同じ側へ置き、専用の`<役割名>.subagent.md`とagent定義のいずれかを持つ委譲では、
委譲プロンプトが基準文書の絶対パスと基準文書に未記録の差分だけを渡す。
委譲プロンプトへの前提の複製を禁じたまま契約を委譲先へ届けるには、契約の保持先を委譲先が読む資料側へ置く以外に方法が無いためである。
`claude-code-runtime.md`は契約を保持する側の要求だけを持ち、契約の本文は各`<役割名>.subagent.md`とagent定義が持つ。
同じ内部手順を委譲元へ複製する案は、委譲プロンプトへの転記と改訂時の不一致を誘発するため採用しない。
返却方法の契約を委譲プロンプトへ毎回複製する案も、専用資料を持つ委譲での複製禁止と衝突するため採用しない。
完了報告の宛先をフックで自動チェックする案は、文書1行の契約で同じ目的を満たせるため採用しない。
共有出力ディレクトリから成果物を推定する案は、並行する委譲の成果物を取り違えるため採用しない。

実行環境が委譲プロンプトを`user` roleで配送しても、そのtransport上のroleは人間の発話者を証明しない。
直接対話で受領した実際のユーザーメッセージと、委譲元が人間由来として出所と引用範囲を明示した素材だけをユーザー指示および合意へ分類する。
委譲元は起動命令と人間由来の素材を区別する。起動命令と人間由来の素材を区別する基準は委譲先にある。
配送本文の出所判定は`agent-toolkit/rules/01-agent.md`の「方針が衝突する場合の優先順位」節が担う。
計画への由来記録は`agent-toolkit/skills/plan-mode/references/plan-file-standards.md`の`由来`区分が担う。
実行レビュー担当への受け渡しは`agent-toolkit/share/exec-review.parent.md`の「`review_contract`の生成」節が担う。
起動命令をユーザー合意へ昇格させた差分は、`agent-toolkit/share/exec-review.subagent.md`の種類2（認可された対象、範囲または外部可視の結果からの逸脱）と種類7（自動チェックでは検出できない作成規範またはプロジェクト規範への違反）で指摘する。独立した指摘種類は新設しない。
委譲プロンプト全体の転記は委譲元の命令をユーザー合意へ昇格させるため採用しない。

### 実装担当のプロセス所有と終了確認

実装担当は成果物の編集、生成、初回検証、stageとcommitを所有する。
実装担当が着手前に実在を確認する入力は、起動時点で作成済みの計画・素材・作業ツリー・規範に限る。後段の工程で他の主体が作成する成果物の出力先パスは実在確認の対象にせず、未作成を入力の不備として扱わない。作成主体と作成時点は成果物ごとの基準文書へ一意に置き、受領側が推定しない。
調整役はGit状態、差分、成果物と報告済み検証結果を読み取り専用で直接確認し、完了条件への適合を検収する。
背景の実装担当では、実装担当が所有する全プロセスの終了を確認した後、実行時に`ListAgents`を利用できる場合に限り、
残る`TaskStop`対象の停止、同ツールによる稼働なし確認の順で書込所有権を移す。
`ListAgents`を利用できない場合は、保持済みのID、完了通知、停止結果、成果物観測を照らし合わせ、自身が起動して識別子を保持したプロセスの生存を照会する。プロセス名の一致だけから生存状態や対象を推定しない。
これらの既存情報から未知の子孫が存在しないことを確認できる場合だけ残る`TaskStop`対象を停止する。
停止結果と停止後に受領した完了通知・成果物観測を対応付け、全対象の終端を確認した後に限り書込所有権を移す。
停止後の終端を確認できない場合は書込所有権を移さず、停止結果と観測結果を続行できない理由として返す。
未知の子孫が存在しないことを確定できない場合は停止と書込所有権移行を開始せず、保持したIDと観測結果を続行できない理由として返す。
前景の実装担当の終了後に実装担当が所有するプロセスの存続が判明した場合、委譲元は実装担当の引継ぎを禁止し、
未完了として委譲元へ返す。

全ての委譲で背景処理を停止する案は、実装担当ではない読み取り専用の委譲が継続する正常な処理まで失わせるため採用しない。
プロセスの書込可能性を分類する案は、起動時に書込みの有無を確定できないため採用しない。
実装担当が所有するプロセスを後続主体へ移管する案は、新しい所有権契約を必要とする一方、終了確認だけで目的を満たすため採用しない。
委譲先の停止手順を委譲プロンプトへ複製する案は、責務の基準を分岐させるため採用しない。

完了報告または`ListAgents`だけから全プロセスの終了を推定する案は、外部プロセスを直接観測できないため採用しない。
所有主体の終了後に自然終了を待つ案は、終了時機を保証できず実装担当の引継ぎを停止させるため通常手順にしない。

### 即時通知の宛先

手順どおりに進められない事象の即時通知は、完了報告の返却方法とは別の手段として設計する。
完了報告は委譲元が待機を解いた後に検収する成果物であり、事象の通知は委譲元が待機中に受け取って並行する工程の判断へ使うためである。
この効果は委譲元が並行する工程を持ち、かつ実行主体が到達可能な機械可読返信識別子を保持する場合にだけ生じる。
返信識別子を保持しない場合、または現在の実行主体へ`SendMessage`が公開されず呼び出しに失敗する場合は、事象を通常の完了報告へ含める。

通信scopeは同一セッション内の親子委譲、Agent Teamsおよび独立セッション間通信に分ける。
同一セッション内の親子委譲は`Agent`の起動結果が返すagent IDを保持し、Agent Teamsと独立セッション間通信はproviderが機能を公開し呼び出しが成功した場合だけ公開された通信機能が返す識別子を使う。
Claude Platform on AWSで独立セッション間通信が成立しない確認結果を、同一セッション内の`SendMessage`の不成立または全providerの制約へ一般化しない。

宛先の由来は起動結果のagent ID、hostが明示する機械可読reply addressおよび条件付きの`senderTaskId`に限定する。
`from`・`origin.from`・`name`・`subagent_type`は表示用・種別用の値であり、返信先へ変換しない。
`SendMessage`のsuccessまたはqueuedは送信側の受理だけを示し、中継先IDと送信後の完了通知または戻り値を対応付けて受信処理を確認する。
完了通知の受領主体を最上位と直接の親のいずれにも固定せず、直接の委譲元でない主体は現在の実行主体への`SendMessage`公開と保持済みの直接の子IDへの呼び出し成功を確認した場合だけ通知を逐語中継する。
中継不能時は未反映を推定して再送せず、担当範囲と権限の内側にある未完了工程だけを巻き取り、外側の工程は続行できない理由として委譲元へ返す。
ホスト別の手段と宛先を常時規範へ書かないのは、未確認の手段を全ホストへ配布する実施契約へ含めないためである。
Claude Code固有の最上位セッションへの即時通知は`agent-toolkit/share/rules-subagent.claude-code.md`「即時通知の宛先」だけが保持し、直接の委譲元への返信、通常完了報告および独立セッション間通信と区別する。

### 委譲先への命令の範囲と却下案

委譲プロンプトの命令は、委譲先側の基準文書が定める手順の範囲を狭めない。委譲元が確定した判断の記録（レビュー指摘管理表の`対応内容`欄など）を委譲先への命令へ転写すると、委譲先が所有する採否判定と類似箇所の一括修正が失われるためである。
委譲元の入力列挙は、委譲先側の基準文書が必須とする入力を満たす。指摘の修正を委譲する手順では、委譲先が適用する作成・レビューの規範を定めるスキルを委譲時に渡す入力の一覧へ含める。
必須入力を委譲元だけで定義し委譲先の基準文書と比較しない案は、委譲先の追加ごとに入力不足を生むため採用しない。

## AWI処理の工程と選定

AWI処理は、選定工程（選定とレーン分け）、レーン工程（レーン実行）、公開工程（全レーン後の終了）に分ける。
選定工程ではメインがキュー一覧を自ら取得せず、pickerを設定モデルへ直接委譲する。
pickerの既定段位は`high_tier`とする。2026年10月8日にユーザーが割当の誤りを理由として上位段位への変更を指定したためであり、誤り率の改善を測定済みとは扱わない。説明担当など他役割の段位と、各段位の候補設定はこの変更に含めない。
pickerは`processable`一覧を自ら取得し、`processing`項目の全件と、`inbox`かつ除外条件に当たらない項目を同じ候補集合へ含める。
`processing`項目は既に選定済みであるため除外条件を適用せず、優先が必要な場合はレーン割当またはレーン内の実装依存順で表現する。候補を、実装不要、処理中に新たに必要と判定した保留および通常レーンへ分類する。要求の不採用と既存の変更による充足はpickerが確定せず、レーン担当が確定する。
`processing`項目だけを排他的に処理対象とする案は、1セッションの固定費が処理件数に依存せず、残留が1件でもあるとセッションの処理量が残留件数に固定されるため採用しない。
除外条件は外部待ち（`cooldown_until`による時間経過待ちと未終端の依存先）と修復待ち（frontmatterや依存関係の不備）とする。
既存の`hold`項目は候補、優先度、依存判断または固有指示の入力へ含めない。
選定工程はpickerが処理対象を確定した直後に、選定時点で`inbox`だった項目へ既存の一括`start-processing`を1回実行する。メインは出力の検収時に、`選定`の各項目の`WI`の全件が`processing`にあることを確認して選定工程を完了する。`start-processing`の引数集合と`選定`のうち選定時点`inbox`の集合の一致は、引数を決めるpickerが実行前に確かめる。比較集合を対象リポジトリの`processing`全件へ広げる案は、ユーザーが処理対象を明示したprocess-wiの実行で、指定した対象の外にある`processing`項目が残り、正常な実行を停止させるため採用しない。遷移をpickerへ置くのは、対象集合を確定した主体と遷移させる主体を分けると、確定から遷移までの間に別主体の検収工程が入り、遷移前にレーン工程へ進む危険が残るためである。
計画ファイル、managed-temp、worktreeとレーン担当の起動をこの遷移の成功より後へ置くことで、着手済みのprocess-wiの実行が占有する範囲を外部観測と中断後の再開位置から識別できる。
pickerの有効出力を受領したメインは、選定結果と処理開始を検証した時点でレーン起動へ進む。並行している監査の終端を`start-processing`への遷移の条件にせず、受領済みのpickerを再び待機せず、再起動もしない。監査の終端は公開工程の開始条件にだけ用い、picker出力が不正な場合だけ同じpickerへ再取得を依頼する。
ユーザーが追加を明示した項目と、公開工程前の即時対応で投入・再利用することが確定したAWIを、処理中に追加する処理対象WIとする。ready一覧は再取得しない。初期pickerの返却前は同じthreadへ追送して元の候補集合へ合流し、返却後は別出力を検収してから元の選定結果へ追記する。いずれも分類、未遷移項目の処理開始と最新の確認結果を検収して公開工程の集合を確定する。追加が未確定の通常の新着は次回の処理で扱う。
レーン工程ではメインがレーン担当と実行レビュー担当を`agents_server`で直接起動し、工程遷移と同一threadの継続を自ら制御する。レーン担当は計画の起草から変更の作成、変更範囲の検証までを担う。
実行工程へ進む各レーンは担当工程に必要な基準文書だけを受け取り、実行レビューの収束、最新ベースへのrebase、競合解消後の実行レビュー（1回）、メインから直列に許可されたffマージ、AWI行ごとの終端までを完了する。上流要求と対象リポジトリ側の要求が混在する項目は`adopt`の対象から除く。
採用する実施範囲を持たないレーンも、レーン担当が計画の保存とAWI行ごとの終端までを完了する。メインは統合完了の固定値を公開契約の終了状態と比較し、一致の確認後に統合を完了したレーンの所有資源を回収する。

選定工程の手順は`${CLAUDE_PLUGIN_ROOT}/share/pick-wi.parent.md`へ集約し、本体には目的と不変条件だけを残す。
選定工程でメインが読む資料を1件にするのは、pickerの起動までに読む資料の件数が選定の固定コストを直接押し上げるためである。
レーン工程と公開工程が同じ構造を持つため、段ごとの読込契機をそろえる。

選定結果は反映先を`書込対象`、`公開工程の書込対象`、`書き込まない反映先`の3区分へ重複なく分類する。反映先の被覆には3区分の和を使う。レーン分け、別レーンとの重なり、包含と連結成分の判定には、同じ段階のレーン担当が書く`書込対象`だけを使う。
`公開工程の書込対象`は対象リポジトリの規範が全レーン統合後の公開工程だけへ書込を割り当てたパスに限る。規範、節とpathは所要時間の根拠へ記録する。明示的な割当を確認できない対象と、レーン工程でも書く対象は`書込対象`に残す。`書き込まない反映先`は参照先と除外先だけを持ち、公開工程所有の退避先には使わない。被覆集合と競合集合を同じ二値分類で表すと、反映先の被覆に必要な公開工程所有のパスがレーン競合へ混入する。このため、工程ごとの所有を分離する。
pickerはこれらの値をAWI本文の`## 反映内容と反映先`から手で書き写すため、反映先の一部を欠いた値や上位ディレクトリだけを書いた値がレーン工程へ渡った（`docs/development/incidents-workflows.md`の2026年10月1日の記録）。`atk run-script pick-wi-check`（`agent-toolkit/skills/process-wi/scripts/check_selection.py`）は反映先の文章とインラインコードから、完全なパスと、ディレクトリに続く省略したファイル名を抽出する。インラインコードは内容全体を1つの候補とし、文章中のパスはASCIIの候補に続く非ASCIIの文字まで伸ばした実在の最長パスを候補とする。パスの文字をASCIIに限って走査すると、`docs/dev/ログ監視.md`を範囲`docs/dev/`、`docs/design/LLMへのファイル入力.md`を途中の`docs/design/LLM`として読み、pickerに実際には書かない範囲を`書込対象`へ置かせた（2026年10月6日の観測）。文章中で実在しない非ASCIIのパスは後続の日本語の文と終わりを区別できないため、インラインコードで書かれた場合だけを全体で読む。
抽出するのは作業ツリーに実在するファイルとディレクトリ範囲、および拡張子までそろい親ディレクトリが実在する新設先のファイル名に限る。直後にグロブ記号（`*`、`?`、`[`、`{`）が続く語は、`share/rules-*.md`の`share/rules-`のようにグロブや波括弧展開の途中で途切れた断片として抽出しない。実在しないファイルの候補が追跡ファイルのパス末尾とパス要素単位で1件だけ一致する場合は、`share/pick-wi.parent.md`を`agent-toolkit/share/pick-wi.parent.md`とするように追跡ファイルへ読み替える。親ディレクトリの実在だけで採ると、途切れた語、不在の略記ディレクトリ、別の起点からの略記が新設先として抽出され、pickerが`書き込まない反映先`へ1件ずつ分類する手作業を生んだ（2026年10月6日の観測）。
抽出したパスが3区分のいずれかに覆われ、区分間で重複しないことを確かめる。`書き込まない反映先`のディレクトリ範囲が書込区分のパスを真に含む組は重複に数えず、そのパスは書込区分の指定を優先し、範囲の残りを書き込まない扱いとする。AWI本文が変更しない範囲として上位ディレクトリ（「他の`docs/`配下は変更しない」）を挙げ、その配下で個別のファイルを書く選定を表すためである。同じパスを2区分に置いた組と、書込区分の範囲が非書込のパスを含む組は従来どおり重複とする。ただし同じ抽出結果に配下の別のパスを持つディレクトリ範囲（範囲説明。「対象リポジトリは`agent-toolkit/`配下とする」など）は被覆を求めず、配下の個別パスにだけ被覆を求める。範囲説明を覆える区分は`書込対象`だけであり、被覆を求めるとpickerが広い範囲を`書込対象`へ入れて全レーンが包含関係になり、`書込対象`による別レーンの重なりの検出が働かなくなる（2026年10月6日の観測）。書込区分のディレクトリ範囲が反映先の個別ファイルを不要に広げていないことと、公開工程区分に前段の規範根拠があることも確かめる。変更要求、公開工程所有、参照か除外かの意味上の分類はpickerとメインが読む。pickerは返却前に、メインは受領時にこのコマンドを実行する。選定時に実行すれば、書き写した主体がその場で修正できる。受領時の実行は形式と被覆の検査をそろえる。意味の検収にはメインもAWI本文を読む。
暫定範囲が他候補と重なる場合は、限定調査で変更するファイルと定義を確定してから連結する。未確定の範囲をそのまま占有範囲へ使うと、独立した項目まで直列化するためである。調査しても範囲を狭められない場合は、その根拠を残して既存の分割不能規則を適用する。
分類と配分は、AWI・UWI本文の変更要求を読み、既存・新設・参照・除外・公開工程所有を判別し、必要な限定調査で変更領域を確定して行う。抽出パス、存在、名前順、一定件数だけでは文脈の意味を保証できない。`pick-wi-check`が報告した違反を修正するときも元本文へ戻り、変更領域が変われば競合と配分を再評価する。メインも元本文を取得して同じ意味検収を行い、不一致を該当WIとともに同じpickerへ返す。根拠には配分比較・不可分条件を持たせ、共通パスと双方の定義の独立性は構造化した`レーン間の重なり`へ置く。同一レーンの全書込集合や無関係なレーンのパスを再掲しない。

ファイルに付く行番号・行範囲・節参照は、文章とインラインコードの双方で元ファイルの被覆として読む。ファイルの「の」に続くクラス・メソッド名を親ディレクトリで補完すると、存在しない新設ファイルと誤認するため、ディレクトリの「の」によるファイル指定と区別する。並列列挙、日本語パス、一意な追跡ファイルの略記と、親が実在する完全な新設先は維持する。

処理中の追記後は全体YAMLへ`--body-wi <WI名>`を反復指定し、本文の取得と、被覆・区分・プロジェクト規範の指定の適合確認だけを追加した処理対象WIへ限定する。構造・モデル・再開計画・段階・レーン重複・公開工程根拠は全体について確かめる。既存項目を削った部分YAMLでは既存レーンとの関係を判定できないため採らない。指定省略は従来どおり全件、未知指定は終了コード2とする。初回は省略形で全件を対象とし、追加用の別出力は統合モードで一時全体YAMLへ保存するときに`--body-wi`を指定する。成功出力は実際に本文の条件を確かめたWI集合と、形式・被覆について確かめた範囲を示し、意味検収はpickerとメインに残す。
`pick-wi-check`は別レーンの共通ファイルか狭い方の範囲ごとに、`レーン間の重なり`へ双方の定義と`交わる`・`交わらない`の判定が1件あることを確かめる。自由文への同じパスの再掲だけでは、定義が同じ場合も独立として受理できたためである。余剰・重複・欠落と、交わらない判定の同じ定義を拒否する。同段階の交わる判定を拒否し、先行指定には交わる記録の直接・推移依存を求める。共有しない組まで段階化する理由にはしない。定義の意味上の独立性はpickerとメインの読解へ残す。追加側は新旧間と追加内だけを記録する。識別子の変換は選定統合の公開操作へ集約する。メインは最終割当の対応を渡し、同一レーンとなる記録の除去も同じ操作で行う。新旧の既存欄名は`_plan/selection.py`で同じ意味へそろえる。

追加選定の統合は`atk run-script pick-wi-check -- <既存YAML> --merge <追加YAML> --lane-map <対応JSON> --output <保存先YAML>`へ集約する。対応JSONは追加側の全レーンから最終レーンへの辞書である。既存の識別子と項目を保持し、選定・所要時間・重なりの3列と先行レーンを同じ対応で変換する。所要時間と根拠を合流し、自己重なりを除去し、同じ無向の組とパスの双方の定義を保持する。全体チェックが成功した場合だけ原子的に保存するため、WI重複・対応漏れ・合流後の不整合で元の入力と保存先を損なわない。picker返却前とメイン受領時は一時全体へ保存し、メインの最終割当後だけ元の選定結果へ保存する。分類や割当の意味判断はpickerとメインに残す。別の統合コマンドを設ける案は検査の所有者を分け、手作業の変換は3列の食い違いを残すため採らない。

書込要素自身も、実在ファイル、末尾`/`付き実在ディレクトリ、または抽出した新設先に限定する。反映先の被覆だけでは環境変数名や存在しないログ名を余分に含む値を拒否できないためである。抽出した実在ディレクトリも末尾`/`へそろえ、コマンド内のディレクトリと範囲指定の比較を一致させる。
`pick-wi-check`は選定結果をYAMLとして解析し、欄名、必須の欄と型を同じ受理境界で確かめる。自由記述の値の`:`や`#`が引用されずに残ると、別の主体が解析できずにレーン工程で止まった（2026年10月2日）ためである。終了コード2の案内は原因で2群に分け、内容と形式の誤りには選定結果の修正を、引数・パス・private-notesの解決失敗には起動条件の確認を示す。
生成側の確認は、最後の書き込み、`pick-wi-check`の終了状態、返却を1つの手順に結び付ける。
書き直した結果へ以前の成功を使うと、修正で欠いた分類が受領時まで残るためである。
返却の`書込対象の検査`は最新の実行結果をメインへ渡し、選定YAMLへは写さない。
自己申告だけで実行を保証するものとは扱わず、受領側自身の確認を保つ。
結果欄を持たない旧3行は結果不明として同じ受領側の確認へ進む。
確認結果の別保存先やハッシュを追加する案は、既存コマンドが実体の被覆を確かめるため採らない。
`書き込まない反映先`は反映先が参照先や除外として挙げる書き込まないパスを分類する欄である。反映先には非書込のパスが混在するため、全パスを`書込対象`へ必須とすると書込範囲が広がってレーン統合が増える。公開工程所有の対象もこの欄へ移す案は、process-wiで実際に書く責務を非書込として表し、公開工程への受渡しと分類根拠を失うため採用しない。3区分を設けると、pickerは反映先の各パスを工程所有に沿って必ず振り分け、分類しないまま欠いたパスは検証で失敗する。

対象リポジトリの変更では要求を満たせず上流リポジトリの改訂を要する要求を含む項目は、pickerが上流投入を要する項目として示し、全投入先、投入条件、上流要求を構造化してメインへ渡す。メインはレーンの起動前に、元項目と投入先の組へ展開した固定入力をWI投入担当へ渡す。起動単位は`add-wi.parent.md`「起動方法」に従い、同じ元項目の組を同じ担当へ渡す。上流投入はWI投入の条件判定付きの派生であり、委譲先は各投入先の現状が条件を満たすか確かめ、条件が成立する組だけに通常AWIの書式で自己完結した本文を投入する。同じ機構を2つの`<役割名>.subagent.md`へ分けると、投入前調査と本文起草の契約が二重になり、片方だけの改訂が検収の食い違いを生む。上流の改訂だけで成立する項目はレーンを起こさず、投入済みの全ファイル名を元項目の`depends_on`へ加えて`inbox`へ戻す。全投入先で条件が成立しない項目は依存を追加せず、条件不成立の確認結果を外部操作の結果として終端する。対象リポジトリで実施できる要求を併せ持つ項目は分類を分けず通常のレーンへ渡す。投入済みの組があるレーンはffマージ後に所有資源を回収して固定の完了報告を返し、メインが元項目を`adopt`せず`inbox`へ戻す。全投入先で条件が成立しないレーンは通常の終端を適用する。上流投入をレーンの起動前へ置くのは、レーンの完了報告が固定文字列であり、上流の識別子と要求本文を載せる復路を持たないためである。1つの項目を要求ごとに異なる保存状態へ分けないのは、キュー項目の保存状態がファイル単位で1つに定まるためである。投入先と要求をメインが固定して渡すのは、投入先を自ら決める不可逆操作を委譲先が実行しないためである。元項目の`depends_on`更新と`inbox`への復帰はメインが保持する。
公開工程ではメインが1件の終端担当へ版数・生成物同期、push、CI、必要なCI修正、AWIごとのプロジェクト固有の公開後の操作および延期`adopt`を委譲し、受領した固定形式の値を公開契約の終了状態と比較する。自動コードレビュー監査は選定工程で起動し、完了報告と終了とあわせてメインが保持する。全体レビューは追加しない。
1つのレーンは同じworktreeで計画から実装まで順次進め、同時に1つの書込担当だけを置く。
通常レーンは初回集合を1つの計画ファイルへまとめ、処理中に追加したAWIは凍結済み計画と分けて保持する。単一の計画では行数の警告（1200行）を避けられない見込みの初回だけは、実装着手前に分析の単位と依存順で複数の自己完結した計画へ分ける。作成単位をレーンに固定したまま読込負担の判定を計画ファイル単位で行うと、大きなレーンでは規定どおりの計画が警告の不在という進行条件を満たせなくなるためである。分けた計画は同じレーン・worktree・書込所有者のまま、集合全体を`plan-check`へ1回渡して確かめ、通知・受領・計画別の実行レビュー・統合と保存は、既存の追加計画と同じく計画の順序付き集合として扱う。閾値を上げる案は読込負担を残し、レーンを細かく分ける案は少数の大きなAWIに対応できないため採らない。凍結済み計画の事後分割とレーンの再配分は対象外とする。レーンの専用worktreeは1つとし、計画の順序付き集合と各AWI、保存状態を引き継ぎ記録で累積する。pickerは`depends_on`と同じ再開計画を、段階によらず分割不能な成分とする。レーン工程で書き込むファイルと節（`書込対象`）の重なりは同じ段階での同時書込を避ける条件とし、`公開工程の書込対象`は含めない。同じ段階では、重なる項目と、変更する節または定義を一意に分離できない同一ファイルの項目を同じ成分へ置く。一意に分離できた同一ファイルは同じ段階で並行化できる。書込の重なりで推移的に連結した集合は、重なる項目を先行レーンの統合後の段階へ回す段階案と単一段階案を比べて配分する（比較の手順は「レーン配分の上限と単独稼働の扱い」）。所要時間とレーン数はこれらの制約を満たす候補の内側で比較し、レーンごとの実装時間と統合時間を`選定結果の出力先ファイル`へ残す。同じ段階で重なりを許し、競合解消時間を費用へ織り込む案は、予測済みの書込競合を許し、誤統合と再検証を後段へ残すため採用しない。
競合時は同じレーン担当が関係計画の`概要`、`実施内容`、`要件・外部仕様`と`変更履歴`を比較して最小限に解消し、影響する計画の実行レビューを最終HEADで再び収束させてからffマージを要求する。

### レーン配分の上限と単独稼働の扱い

`agent-toolkit:process-wi`の選定工程は、1レーンが担う見込みの合計へ6,000秒の上限を置く。
見込みの入力は、AWI本文に加えて過去の計画の`## 進捗ログ`が持つレーン別の稼働時間の計測値とする。
上限を置く理由は、開始時点の見込みだけで配分を確定すると、見込みが外れたレーンが他のレーンの終了後も
1つだけ動き続け、その区間がそのまま壁時計時間へ乗ることである。
2026-09-16のprocess-wiの実行では、レーン別の稼働時間が2,298秒から6,708秒まで広がり、単独稼働が9,482.3秒に達した。

候補内の同一リポジトリ依存は推移的な連結成分も同じレーンへ置き、依存先から処理する。
同じ計画を再開する候補も、進捗ログとレビュー指摘管理表を共有する単一の書込資源として同じレーンへ置く。通常中断は`~/.claude/plans`の絶対パス、観測のみの再開は`private-notes/plans/`からの相対パスを計画識別に使い、pickerが分割不能な連結成分へ加える。処理中の追加では、追加候補と既存選定の計画識別も同じ規則で比較し、同じ計画を持つ既存レーンへ費用比較より先に割り当てる。`pick-wi-check`とメインの受領確認でも同じ不変条件を確かめる。計画ファイルを探索して補う案は、pickerが確定した再開位置とは別の対象集合を確認処理が生成するため採らない。
必要な依存と同じ再開計画は上限より優先し、成分を割らずに超過根拠を残す。書込の重複は同段階の同時書込を避ける条件とし、推移的な連結だけで全件の単一レーン固定や6000秒超過を不可避としない。
例えばAがX、BがXとY、CがYを変更する独立要求では、AとCの並行後にBを始める案を比較できる。全件が同一定義を書く場合の直列性と、実依存・同じ再開計画の不可分性は維持する。既存のレーン数上限内で段階案を作成し、各段階の最長実装時間と直列統合時間の和を全段階で合計して単一段階案と比較する。短い単一段階案を採用する場合にも比較理由を残す。選定結果の既存の`段階`と`先行レーン`で先行統合後の開始を表せるため、新しい実行基盤は要らない。
着手不能な先行項目や上流成果待ちがある後続は待機を維持する。
同じ候補をprocess-wiの別の実行へ送る案は採用しない。段階化する場合も全候補をprocess-wiの同じ実行に保持し、後段は先行統合後のHEADから始める。

反映後の観測だけが残る項目では、UWIとholdを選ぶ前に、エージェント自身が前提を整える手段を確かめる。2026年10月7日に、観測のみの再開で残った完成条件が対話CLIへの自由記述の回答を要したため、メインは回答を生成できる主体をユーザーだけと判定し、UWIを保存して元AWIをholdへ移した。自分で起動したtmuxセッションへキー入力を送れば同じ入力を生成できる可能性は検討されなかった。到達環境を探す自己観測の要求は延期adoptの段落にだけあり、観測のみの再開の判定とUWI・holdの分岐には接続していなかった。このため自己観測の判定は`finish-session.md`「延期adoptと反映後の観測」の1箇所に置き、延期adoptと観測のみの再開の両集合がその判定を経る。`run-lanes.md`「採否の確定と終端区分」の前提を整える主体の判定とUWI・holdの手順はその判定を参照し、UWIには欠ける前提と自己操作が成立しない根拠を書く。入力手段があることと回答を実際に受け取ったことは区別し、後者だけを観測として扱う。tmux専用の条文を足す案は、利用中のホストが公開する端末操作など同種の別手段を判定から外し、観測のみの再開へも適用されないまま残すため採らない。ユーザーが起動したセッション、ユーザーだけが到達できる環境、新たな認可を要する操作は自己操作の対象から外し、既存のUWIとholdを使う。

選定候補が0件の実行のように、process-wiの1回の実行の起動条件そのものを観測する完成条件は、空のキューと監査入力を制御した実行の検証で確かめてから終端する。単一項目の観測を待つために、毎回の実行が読む選定の別集合、frontmatterの状態、公開CLIを設けた構成は、2026年10月に撤去した。自然に発生する入力を待つ間は項目が無期限にprocessingへ残り、その1件のために全ての実行の選定と手順が分岐を読むためである。

処理中に見つけた既存不良と是正要求のうち、持ち越すと次のセッションの進行に影響するものだけを、公開工程の開始前に同じ仕組みで追加した処理対象WIとして扱う。対象外はAWIで次回以降へ回し、このセッションを終端させる。メインは即時対応する項目を`add-wi`の委譲で調査、AWIの起草および投入まで1件の委譲先へ渡し、投入または再利用するAWI名を追加のpickerへ渡し、処理開始済みで`pick-wi-check`に合格した出力を受領する。メインは指定集合と状態を検収し、割当基準で既存レーンか新しい是正レーンへ対応付け、元の選定結果へ反映してからレーンへ渡す。調査を委譲するのは、原因分析と類似見直しの過程で得る無関係な情報を、メインと修正を担うレーンの文脈へ入れないためである。投入されたAWIは原因と対策を確定済みであるため、修正を既存レーンの文脈で行ってもこの目的を損なわない。レーン担当が自レーンの検証を妨げる既存不良を報告し、修正の対象と方向が報告と現物から技術的に定まる場合は、メインがAWIを経ずに同じレーンへ修正を認可する。原因と対象が定まった不良では調査を分ける目的が成立せず、AWIを経ると投入担当とレーン担当が同じ検証を二重に実行するためである。修正は計画の実装と別のcommitにし、両方を終えてから変更範囲の検証を1回実行する。認可は計画を更新せず、認可の出所・対象・対応する完全OIDを計画の進捗ログ（計画なしでは引き継ぎ記録）と実行レビューの`review_contract`へ置く。commitメッセージには計画外の既存不良の修正であることと修正理由だけを書く。公開commit本文の読み手は内部の認可記録へ到達できないためである。公開工程の開始後に見つけた公開を妨げない不良は、公開したcommit集合を安定させるため不良ごとにAWIで次のセッションへ回す。`agent-toolkit:single-lane-process`では同じ委譲で投入した即時対応のAWIを処理対象WIへ加え、メインが自ら実装して同じ実行レビューへ含める。

AWIを要さず見つけた主体が元の文脈で直す用途には、専用の`defect-investigation.parent.md`と`defect-investigation.subagent.md`を用意し、`agents_server`の`start`で`high_tier`の調査担当を起動する。調査担当は`agent-toolkit:bugfix`を起動し、対策、横展開処置および再発防止策の確定まで行う。見つけた主体は返った対策で修正する。`start`の`explore`は委譲先が`Skill`ツールを持たずスキルを読み込めないため使わない。`add-wi`はAWIの投入までを完了条件とするため、投入せずに直す用途と分ける。知識境界として、調査の手順は`agent-toolkit:bugfix`、起動と受領は`defect-investigation.parent.md`が持つ。process-wiとsingle-lane-processそれぞれでの扱いは`agent-toolkit/skills/process-wi/SKILL.md`「即時対応」と`single-lane-process/SKILL.md`が持つ。

却下した代替案は4つある。観測した箇所だけを局所修正して類似見直しと再発防止策を後続のAWIへ回す組は、セッションが終わるたびにAWIが投入されて次のセッションが続くため採用しない。修正まで独立した担当や新しいレーンへ分ける案は、文脈を分ける必要があるのは調査だけで、修正を分けると書込主体と工程が増えるため採用しない。是正で見つかった不良に世代の上限を置く案は、そうした連鎖を想定しなくてよいとのユーザー判断により採用しない。公開工程の開始後に見つけた不良を同じセッションで直して再公開する案は、公開工程が反復し、セッションの終端が延びるため採用しない。

## モデル段位とCI修正

計画の起草、実装および変更範囲の検証は`high_tier_model`へ割り当てる。
作業規模や計画の具体性に応じたモデル分岐は設けず、レーン担当が同じ文脈でこれらを完遂する。
レビュー修正はレビュー修正担当、CI修正はCI修正担当として、いずれも`high_tier_model`を使う。
モデル候補は工程ごとの個別キーではなく、`high_tier_model`・`medium_tier_model`・`low_tier_model`の段位と、固有用途の`write_model`・`orchestrate_model`で管理する。複数工程が同じ候補列を使う場合に設定と確認の対象が工程数だけ増えることを防ぐためである。`atk config show`と`get`は設定値だけを返し、Codex系列名の解決は起動時に行う。保存済みの旧工程キーは新しい設定の解決に用いず、移行層を設けない。旧キーの保存値を新キーへ自動対応させる案は、複数の旧工程が1つの段位へ合流するときに値の優先順位を新たに定める必要があり、ユーザーが選んだ、段位ごとの設定が無い場合の候補列と矛盾するため採用しない。
CI修正の認可根拠には、計画が記録した元の要求または確認回答、原因となった変更を認可したユーザー指示の逐語文、既存の公開契約の該当箇所のいずれかを使用する。
一般のCI失敗では計画ファイルとAWIファイル名一覧を必須とせず、存在しない資料の合成を避ける。
CI修正担当の共通出力は`awis`を維持し、AWI起因でない場合は`なし`を返す。
同一レーンでは、計画の起草から実装、変更範囲の検証、修正まで同じworktreeを使う。
担当を交代する場合は元担当の終端を確認し、検収済み状態を後続担当へ渡す。

## 待機と停滞の観測

Codexの`running`は終端未観測の状態であり、補助観測値から停滞へ変換しない。待機報告の観測値は書込主体と対象範囲を伴う。作業ツリー全体値は並行更新を含む補助情報としてだけ扱う。ホスト観測手段は一覧掲載と実際の呼び出し成功を別に検証する。`ListAgents`が不在か、呼び出しを拒否された場合は、保持済みのID、完了通知、成果物観測と自身が起動して識別子を保持したプロセスの生存を`fallback`で照らし合わせる。プロセス名の一致だけから生存状態や対象を推定しない。複数委譲先の能力比較は全対象への同一機械照会が成立した場合だけ確定し、成立しない場合は未検証を返す。
同一turn内の補助観測だけを理由とする状態照会は反復させず、完了通知の不着、次の定時turn、終端statusの確認でだけ再照会する。この扱いは`agent-toolkit:delegation`の`references/waiting-and-monitoring.md`が定める。
Claude Codeの委譲・背景処理の待機は、機械的な完了通知で待機を解除し、`CronCreate`、`CronList`、`CronDelete`が実行主体へ公開される場合だけ定期再確認を併用する。
`agents_server`の`start`ではagent-toolkitのmodが`start`の処理の中で定期再確認を作成し、それ以外の場合と装着できなかった場合は実行主体が作成する。定期再確認は`atk wait-schedule`が出力したcron式を変更せずに1件だけ作成し、保持した待機対象IDとtask IDを作成時に記録した状態と比較しながら再利用し、全対象の終端後に削除する。
`ScheduleWakeup`は`/loop`専用であり、一般の委譲待機へ広げない。定期起動を完了・停滞の証拠にせず、シェルの`sleep`や背景タイマーを追加しない。
`claude-code-runtime.md`はClaude Codeの能力とCron所有を、`waiting-and-monitoring.md`は完了通知を優先する再待機を基準として保持する。
`agent-toolkit/agent_toolkit/_hooks/background_tasks.py`はCron作成後も継続中とするStop判定を基準として保持する。
この分離により即時通知を定期再確認へ置換せず、独自設定resolver・フックの永続状態を追加せずに、同じ待機対象のライフサイクルを各境界で確認できる。

委譲元が`atk agents wait`で委譲先の結果を待つ設計は`design-delegation.md`「委譲先セッションの結果待機」にある。

## セッションの終了

調査・採否と通常型の計画化は、Claude CodeとCodexのいずれでもメインが下流担当を直接起動する共通手順を使う。
委譲先の起動失敗を別の起動手段へ迂回せず、失敗として返す。
通常処理および明示的な連続処理は、起動時に固定した項目だけを処理し、後始末後にready項目を再取得しない。
`agent-toolkit:process-wi`は起動時に副作用のない終了能力probeを実行し、完了した全条件一致だけを停止可能とし、未実行、読取失敗、値の不一致のいずれかを停止不能とする。
`atk agents-exit-session`は起動時の判定を再利用せず停止直前に対象を新規識別し、PIDの開始時刻と実行ファイルのデバイス・inodeを比べ、一致した場合だけ停止する。
Claude CodeではFunction hooks moduleの`session.start`が、実際に読み込まれたことをセッション別のファイルへ記録する。`turn.complete`は対話CLIの終了要求を読み、ターン完了後の`/exit`をキューへ入れる。
`/exit`は終了とともに停止するセッション限りの作業が残ると確認画面を表示し、無人の常駐セッションはそこで止まる。このため`turn.complete`は`/exit`の直前に非durableのcron taskを削除し、Stop hookの`autonomous_exit.py`はバックグラウンドタスクが残る場合に終了要求を取り下げる。
2つを分けたのは、失う状態の有無が異なるためである。セッション限りのcron taskは終了とともに消えるため、削除しても失う状態が無く、確認画面で「Exit and stop tasks」を選ぶのと同じ結果になる。バックグラウンドタスク（shell、subagent、monitor、workflowなど）は停止すると作業途中の結果を失うため、自動では止めずに作業の終端を確かめてから終了工程をやり直させる。
cron taskの削除は許可の判定が`allow`の場合だけ行う。`$.tool.call`は権限確認のダイアログを経由するため、判定を省くと別の確認画面で同じく止まる。Python側はファイルの更新時刻が現在の本体プロセスの開始より後か確かめ、moduleなしで再開した場合の古い記録を採用しない。両側が同じ絶対パスを使えるよう、Claude Codeの設定ディレクトリを基準にする。Pythonの一時ディレクトリだけを使うと、Function hooks側と異なる位置を指し得るため採らない。
Function hooksを読み込まないClaude CodeとCodexへのシグナルによる本体停止は、現在の対話CLI本体として安全に一意識別した自身か、自身が起動して停止識別子を保持した対象だけに行う。
共用プロセスと識別不能な環境では終了案内で完了する。前記の対象に該当しない場合も同じ扱いとする。

## 工程名の体系

レビューと自動チェックの工程名は、対象と適用する契約の組み合わせで命名する。
レビュー工程は実装後の実行レビューに一本化し、`track`は`exec-review`とする。
実行レビューは、目的、認可、公開契約および過剰実装を`要件・外部仕様`の水準で評価する。

レビュー以外の自動チェックは、計画構造の自動チェック（`check_plan_file.py`の実行）と、
レーン担当が起草後に行う計画自己監査とする。

役割と、それぞれの手順を定める基準文書は次のとおりとする。責務の説明は基準側に置き、本書へ複写しない。

| 役割 | 基準文書 |
| --- | --- |
| レーン担当 | `agent-toolkit/share/exec.subagent.md` |
| レビュー修正担当 | `agent-toolkit/share/exec.subagent.md` |
| CI修正担当 | `agent-toolkit/share/exec.subagent.md` |
| 実装担当 | `agent-toolkit/share/exec.subagent.md`の`レビュー修正の履歴統合` |
| 実行レビュー担当 | `agent-toolkit/share/exec-review.subagent.md` |
| 終端担当 | `agent-toolkit/share/session-termination.subagent.md` |
| WI投入担当 | `agent-toolkit/share/add-wi.subagent.md` |
| 監査担当 | `agent-toolkit/skills/process-wi/references/github-copilot-review-audit.md` |
| 調査担当 | `agent-toolkit/skills/delegation/references/runtime-routing.md` |
| レビュー担当 | `agent-toolkit/skills/review-standards/SKILL.md` |
| レビューイー | `agent-toolkit/skills/review-standards/SKILL.md` |
| メイン | 参照を持たない。`<役割名>.subagent.md`を持たず、各`<役割名>.parent.md`が委譲元の手順を定める |

英語識別子は日本語工程名と独立に維持し、次の写像で対応付ける。

| 英語識別子 | 対応 |
| --- | --- |
| レビュー指摘管理表の系統値`exec-review` | 実行レビュー（要件・外部仕様の水準で成果物を評価する単一レビュー） |
| 保存済み表の`implementation-review`・`plan-conformance`・`independent` | 既存表の読み取り互換。新規レビューでは生成せず、`implementation-review`は読込時に`exec-review`へ正規化する |

実行レビューを単独で記載する場合は、`要件・外部仕様`と照らし合わせて成果物を評価することを含める。
保存済み表の旧`track`は履歴の読み取りにだけ用い、新しい指摘の登録、修正対象の指定およびチェックポイントの集計には用いない。

新しい工程・サブエージェントは本分類へ収め、名称に対象と適用契約を含める。
