# 障害・欠陥の記録: 誤判定と検証不足（2026年11月11日〜）

[誤判定と検証不足](incidents-judgment.md#誤判定と検証不足)の事例を発生時期別に収録する。

- 2026年11月11日: エージェント由来の作業項目の完成条件にあった「是正の後に全体の試験を手元で1回実行する」を、計画と統括が必要性を判定し直さずに採り、検証の共有の実行枠を41分31秒占有して他の作業を止めた。
  直接原因: 計画の起草と統括の了承が、作業項目に書かれていることを理由に全体の試験を残し、全体の試験をCIへ任せる方針を「2回まで」の上限へ読み替えた。
  背景原因: 作業項目の結論を再利用して比較検討を省く規定と、採用する行の根拠を`-`にできる規定が、目的・現在の方針・利用条件の一致を前提にしていなかった。
  採用済みであることや記載済みであることが、手段をユーザーの要件と同じ強さで固定した。
  対策: 省略と再利用の条件を、結論の前提が今も一致する範囲へ狭めた。
  反映先は`lane-planning-drafting.md`手順1、`plan-file-standards-scope.md`「実施内容」、`plan-file-standards-structure.md`「計画ファイルの構成」である。
  `exec-subagent-inputs.md`、`exec-review-contract-generation.md`にも反映した。
  完成条件が手段を先取りした作業項目の原稿（起草側の必要性の判定が使われなかった別の持込み）も、受け手の判定し直しの入力に含める。
  再発（2026年11月11日）: 効果不足で、2026年9月25日・10月2日・10月28日・11月11日の対策は起票と条項化の側に作用した。
  計画とレビューの省略の規定の前提を直していなかった。
- 2026年11月11日: 提供元（pyfltr）で前日に直した実行枠の不具合が、dotfilesが使う古い版には届いておらず、文書13件だけの検査が最初の取得に2,414秒、取り直しに1,120秒待った。
  直接原因: dotfilesのロックファイルと稼働中の実行が旧版のままで、依存更新の日数の判定（1日未満）が更新を省いた。
  背景原因: 提供元の採用済みを、使う側の版と実行で解消したことの代わりにできた。
  対策: 版の下限を上げて撤去されたAPIの利用を除いた。
  過去の対策と今回の事象を比べる手順で、提供元のcommit、使う側の版、実行する主体、稼働中の実行への適用機会を対応付けるようにした（`root-cause-scenarios-recurrence.md`「反復した指摘の原因判定」）。
  日数の判定が既知の不具合の修正を取り込む更新を省く理由にならないことを、`operate-ak110-projects`の依存更新の判定へ記した。
- 2026年11月11日: 統括が、フックの実装を変える計画を扱いながら、過去のフックの障害の記録と今回の変更を突き合わせず、ユーザーに問われるまで照合しなかった。
  照合の漏れを認めた後も、担当への追加の指示だけを行い、自分の行動の原因の分析をユーザーに求められるまで始めなかった。
  直接原因: 記録を読んで形式の検査に通ることが、守る条件を今回の判断へ使ったことの代わりになった。
  質問への回答の調査で不備が分かっても、分析の契機へ戻らなかった。
  背景原因: 読んだ記録と採否・検証の対応を残す場所が無く、実装だけを変えるフックの改修では記録へ進む条件が弱かった。
  受け取った時の発話の分類（照会）が、回答の後に分かった事実による判定し直しへつながっていなかった。
  過去の対策との関係: 2026年10月7日の事例（ユーザーの是正で`bugfix`を起動しなかった）の対策は振り返りへ作用し、会話の中の入口は対象外だった（範囲不足）。
  2026年10月19日〜31日の事例（本文の配送の再導入で方針と照合しなかった）は、当時は方針の記録が足りなかった点が今回と違い、今回は記録と読む規範があるのに使わなかった（未適用）。
  対策: 読んだ記録の成果を、守る条件と今回の採否・検証の対応として計画の判断の根拠へ残すようにし、実行レビューがその対応を使う（`edit-dotfiles-norms`、`lane-planning-drafting.md`、`distribution-and-hooks.md`）。
  照会への回答の調査で不備が分かった場合は`bugfix`の初動へ進み、受け取った時の分類を判定し直す（`user-utterance-questions.md`、`analysis-operations-intervention.md`）。
- 2026年11月11日: 同じ処理の中で起きた作業のミスが分析されなかった。
  対象のミスには、`commit-with-timeout`へ`commit`を重ねて渡した引数の誤り、広すぎるプロセスとファイルの検索があった。
  担当の途中の観測を全体の未読へ強めた報告、終わっていない待機に重ねた待機の起動があった。
  検索の起点の誤りを「直したので不要」とした報告の受理、受け取った改善点9行の上位への未送達があった。
  自分で気付いて直したもの、他の担当が見つけたものも含まれる。
  発見の経路: 自分で気付いた（引数、検索、待機、9行の省略）、他の担当が気付いた（報告の強め、起点の誤り）、ユーザーが介入した（分析の未着手）。
  回復・分析・処置の区別: いずれもその場で回復したが、ユーザーの質問まで原因の分析が行われず、処置は個別の訂正で終わっていた。
  pyfltrのCIで、変更していない既存の試験の失敗が初めて見つかった件は、CIで見つけたこと自体を方針の違反とせず、検証の対象に変更した契約の利用側の試験を足す探索が使われなかったことを要因とした（担当は`bugfix`を起動して直した）。
  直接原因: 分析の入口が発見の経路と分析の行為の列挙で、自分で気付いた場合とその場で直った場合が入口の条件から読み取れず、報告の選別（正常な回復を問題にしない）が分析の省略にも読めた。
  対策: `bugfix`の入口を「期待からの逸脱を認識して診断・訂正・対処を始めるとき」の1つの条件へ改め、対象の種類、工程、発見者、修正の有無を問わないとした。
  報告の選別と分析の要否を分け、常時規範・受領後の扱い・完了報告・`agent-toolkit:user-confirmation-and-report`の各所を同じ定義へつないだ。
  commitの公開入力の具体例、割り込みと圧縮の後の復帰で起動済みの実行を同じ識別子で回収する接続、検証コマンドを使う前の利用側の試験の判定、改善点の送達と処置の再利用の順序を、それぞれの既存の規定へ加えた。
  再発（2026年11月11日）: 未適用で、同じ巡回の中で、次の事象が上の是正の前に再び起きた。
  `commit-with-timeout`への`commit`の付与（2件目、フックの163秒後に失敗）があった。
  ヘルプを確かめないオプションの付与（`plan-commits --output-file`、`atk wi list --grep`）があった。
  統括の二重待機（13:05、16:3x、17:1xの3回）があった。
  単一担当の実行契約で省くはずの「実装完了」の往復による停止もあった。
  同じ巡回の別のリポジトリでも同じ形が2件あった。
  1件目は、手元の検証の対象を計画の直接影響範囲に限り、共有の仕組みの前提（後発が実行枠を待つこと）に依存する利用側の試験が漏れ、CIで初めて失敗した。
  前提を表す語句で試験を固定文字列検索していれば事前に拾えた（検証コマンドを使う前の利用側の試験の判定で扱う）。
  2件目は、共有資源の取得規則を変える設計で、旧版と新版の待機者が混在する組合せ（旧版が待機列の先頭を占める場合）を設計担当も実行レビューも検討しなかった。
  受入シナリオに版の混在はあったが、待機列の位置ごとの組合せを列挙しておらず、統括の指摘で見つかった（レビューの見逃し）。
- 2026年11月11日: 検証の共有の実行枠の待ちを減らすため、ソースを分割する並行の担当の確認を、枠を取らない個別ツールの直接起動（ruff・pyright・import確認・保持比較）へ限った。
  一括実行が含んでいたpylintとtextlintが外れ、統合後の一括実行でpylint 1,569件とtextlint 47件の指摘が出て、是正に30〜40分の手戻りが生じた。
  発見の経路: 担当（レーン）が統合後の一括実行で気付いた。
  指示した側の統括も、検査の種類が減ることを見逃して受理していた。
  直接原因: 起動手段の置換で、起動の回数と枠の占有だけを比べ、元の手段が実行する検査の種類と照合しなかった。
  「品質の確認項目は減らさない」との指示はあったが、確認項目を検査の種類の列挙で確かめる手順が無かった。
  背景原因: 所要の短縮を待ちの削減で行う方針（品質の工程は省かない）が、手段を替える場面の確認へ具体化されていなかった。
  過去の対策との関係: 最初の検証へcommitフックや統合の検証の検査を含める規定（2026年11月11日、同じ巡回で採用）は、検証の対象の選定に作用し、起動手段の置換で種類が減る場面は対象外だった（範囲不足）。
  対策: 実行資源の占有を減らすために検証の起動手段を替える場合は、元の手段の検査の種類を列挙し、替えた後で同じ種類を満たすことを確かめてから採るとした（`verification-scope-selection.md`「範囲の決め方」）。
  再発（2026年11月11日）: 未適用で、是正の直後に同じ担当（レーン）が、lint是正の並行の担当2件へ確認をruff・pylint・pyright・構文検査に限って指示した。
  mypyとprekの検査（試験の補助モジュールの配置の検査）が外れ、次の一括実行でmypy 111件と配置の違反3件が出て、約30分の手戻りになった。
  さらに、移動先の分割を検収する収集名の比較を、全体の試験より後に置いたため、分割で取り込まれなかった試験13件の発見が試験の実行の後になった。
  対策の規定は書いた後で、指示を書く時点の照合に使われなかった（未適用）。
  処置: 是正の担当への指示は、pytestを除いた一括実行を変更ファイルへ適用する形にし、個別ツールの列挙で検査の種類を減らさないようにした。
