# 障害・欠陥の記録: レビューの発散と目的の変質（2026年9月1日〜2026年10月3日）

[レビューの発散と目的の変質](incidents-review-scope.md#レビューの発散と目的の変質)の事例を発生時期別に収録する。

- 2026年9月1日: 実装レビュー担当3件が必須入力の`review_contract`を受領できず、いずれも`needs_escalation`で停止した。
  直接原因: 受信側だけが`review_contract`を必須入力として定義し、生成主体、生成時機、粒度および起動時の受渡し形式を呼び出し側へ定めていなかった。
  対策: `plan-executor`が初回実装レビューの直前に既存の計画記述、開始時点の実体、計画外の明示入力から条項を生成し、契約本文または一意な参照先と出典を固定形式で起動入力へ渡す。
  後継方針（2026年9月3日）: `review_contract`の生成主体はメインとする。
  中間の調整担当の廃止に伴う主体の移動であり、生成時機、粒度および起動時の受渡し形式は変えない

- 2026年9月5日: `agent-toolkit:process-wi`終了時のレビュー見逃し対策を計画レビューした際、
  review-session後の1回確認というユーザー提案を、Copilotレビュー要求、生成完了待機および再取得反復へ拡大した。
  直接原因: 指摘された見逃し問題の採否とレビュー担当が示した完全待機手段の採否を分離せず、
  `対応要否=yes`を修正方針の採用として扱った。
  対策: レビュー指摘を検討材料と位置付け、追加要件、変更認可または手段指定として扱わない契約を
  `agent-toolkit:reviewee-standards`の受領時契約へ集約し、Codexでは成果物変更またはレビュー表応答より先に同契約を適用する。
  現行の参照先`agent-basics:review-standards`の`references/reviewee.md`が受領時の判断を定める。
  当時のスキルは2026年9月6日に統合された。
  指摘と修正手段の採否は「レビュー指摘の位置付け」、成果物を変更する前の確認は「指摘発生時の扱い」にある

- 2026年9月5日: push直後には未着だったGitHub Copilotレビューを終了前に再取得せず、過去PRのreview本文と未解決threadも残した。
  直接原因: 自動レビュー監査をreview-sessionと並列実行し、監査対象を未解決threadだけに限定した。
  対策: `agent-toolkit:process-wi`ではreview-session後に能動的に待機せず1回監査し、
  全PRのreview本文、inline commentおよびthreadをpagination終端まで取得する恒久手順を専用referenceへ置く。
  後継方針（2026年9月7日）: 全PRのreview本文とthreadをpagination終端まで取得する範囲は変えない。
  監査は次のセッションの選定工程で振り返りと並行して1回実行する。
  前のセッションが公開した後に到着したレビューを対象へ含められるため、実行順による限定を設けない

- 2026年9月30日: ユーザーの否定がない完成条件の除外を失効として承認し、証拠確認も通過したが統合担当が差し戻した。
  直接原因: 採否の技術判断と失効の根拠条件を別々に扱い、自由文のsourceがユーザー判断を指すかの確認を後段へ残した。
  対策: 判断要請の送受信を既存の失効受理条件へ接続し、共通の証拠確認で参照先の種別と記入済み回答の有無を確かめる。
  否定範囲と不採用根拠の意味はレビュー・統合で引き続き検収する

- 2026年9月30日: 確認手段の共通表が自律モードを一律にUWIへ固定し、その場の確認を求める要求と衝突した。
  直接原因: 既存のホスト別質問機能と回答・無回答の分岐を保持しないまま、手段をモード別の表へ移した。
  対策: 共通表を質問先行と既存の無回答退避へ接続し、WI・計画・運用の独立した手段指定を共通表の参照へ替える。
  回答期限を持たないCodex Default modeの例外、報告用UWIと個別UWIの用途は維持する

- 2026年10月2日: ユーザーが確定した実行レビュー担当の段位（medium）をhighへ上げる案について、メインは確認が無回答となった後、可逆で外部影響が無いという理由で事後承認に分類し、委譲先へ暫定実施を指示した。
  委譲先の編集がauto modeの分類器に拒否されて止まり、事前承認型UWIとして投入し直した。
  ユーザーはmediumのまま雛形で補助する案を選んだ。
  直接原因: 承認区分を定める`approval-scope.md`と`judgment.md`「認可を要する操作」が、人間が確定した判断の変更を区別せず、可逆性・副作用・観測可能性だけで事後承認へ振り分けた。
  `01-agent.md`「協調と自律」の原則は承認区分へ接続されず、暫定判断からの除外も働かなかった。
  背景原因: （作り込み・流出要因）原則と事後承認の区分が別の契機で導入され、規範の縮小で原則の文言から変更前に判断を得る時点が失われた。
  検出は実行環境の分類器だけに任せていた。
  対策: `judgment.md`「認可を要する操作」へ人間が確定した判断の変更を加え、`approval-scope.md`でその変更を可逆・外部影響なし・ユーザーだけが観測できる場合も事前承認とし、事後承認の各条件より優先させた。
  判断の記録自身が承認方式を定める場合はその定めに従う

- 2026年10月2日: `agent-toolkit:add-awi-by-user`のセッションで、ユーザーは造語や定義のない語が多いと範囲語で対象を示した。
  WI投入担当の保存本文は調査が標本であり残りは文書を編集する時点で扱うと未走査の範囲を書き、メインは作業完了報告で、残る用例は影響の小さいものに限られるとして残りを走査しないまま範囲を縮めた。
  ユーザーが他に無いかを問い、未走査の範囲に定義の無い語が残っていた。
  全件の抽出と分類は同じセッションで成立した。
  直接原因: メインが未走査の範囲を、走査が技術的に成立するのに走査させず、後続の工程へ回すと確定した。
  未走査の範囲を受けたときに読まれる`wi-standards`「由来と承認」の2段落はどちらも範囲を決める判断（事前の明示承認か完了報告での範囲確定）を扱い、走査が終わっていないだけの部分が`01-agent.md`「完遂と先送り」で続ける作業であることを示していなかった。
  `add-wi.parent.md`「受領と検収」も未走査の範囲を検収の失敗として扱わなかった。
  対策: `wi-standards`「由来と承認」へ、未走査の部分は承認と範囲確定のどちらの対象でもなく、走査が技術的に成立する間は「完遂と先送り」に従って走査を続け、後続の工程や事後の申し出へ回さないこと、範囲確定の観測根拠は走査した対象から得た値に限ることを加えた。
  `add-wi.parent.md`「受領と検収」へ、未走査の範囲を示す返却を検収の失敗とし、同じ担当へ残りの走査と反映を指示する項を加えた。
  ユーザー確認の分岐は置かない

- 2026年10月3日: 手動振り返りが、探索担当への不成立な保存指示と、WI投入担当が旧方針を確認事項に変えた往復を、本文の受領や委譲元の追送で解消したことを理由に見送った。
  所要時間も律速threadの総量だけを得た段階で、内部の照会と候補別の比較をせず短縮根拠なしとした。
  追加の照会で旧方針確認の通知と追送の区間が特定できた。
  直接原因: 一次選別の候補種別ごとの判断と、原因分析の後の処置の採否・見送りが別の判断箇所にあり、回復後の結果を元の欠陥の評価へ混ぜられた。
  報告の構造確認は根拠欄の形式だけを確かめ、内容の検収を担う工程へつながっていなかった。
  対策: 一次選別の冒頭へ元の不成立と回復を分ける共通の判定を置き、原因と対策で既存契約の改訂を先に比べてから見送る。
  所要時間は内部照会と候補別比較を見送りの根拠にする。
  予告と最終報告の前にメインが見送りの根拠と原因・比較の対応を確かめる（2026年10月4日「fix: 振り返りで回復した手戻りも原因分析へ送り見送りを原因と対策の比較から判断する」、`7f5c6c70b`）
