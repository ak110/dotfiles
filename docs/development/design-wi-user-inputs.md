# ユーザーコメントと選択肢の設計記録

[設計記録の索引](design.md)と[WIキューと要求本文の設計記録](design-wi.md)から参照する主題別の記録である。

## WIキューと実行準備

### ユーザーコメントの由来と編集境界

コメント本文はMarkdownのtoken位置から解析し、コードフェンス内の`## ユーザーコメント`は予約節として扱わない。
予約節がない場合は本文末尾へ空行2つを正規化して追記し、同名節が1件だけ末尾にある場合はその節本文だけを置換する。
同名節が複数ある場合は入力エラーとする。
予約節の後ろに別のH2がある場合も入力エラーとし、前段本文を保持する。
保存前にはコメント本文も同じ規則で解析し、コードフェンス外のH2を含む入力を無変更で拒否する。
空白だけのコメントは予約節の削除として扱い、予約節より前の本文とfrontmatterを元の改行のまま保つ。
予約節が無い本文では本文を変更せずに成功とする。
ユーザーがコメントを取り下げる操作を、本文全体の編集を経ずに入力欄だけで完結させるためである。
予約節の構造が不正な本文は、空の入力でも同じ入力エラーとする。

コメント編集を許可する条件は、`inbox`または`hold`にあるawiかつエージェント由来（frontmatterの`source`が未設定でない）であることとする。
processing、UWI、終了項目および人間由来の項目はAPIと画面の両方で対象外とする。
由来の判定は一覧フィルターと同じ`_source_kind`を用い、`source`値の列挙をユーザーコメント側へ複製しない。
保存時はロック内で取得した最新本文が`expected_content`と一致するか確かめ、競合時は無変更で失敗を返す。
詳細APIが返す抽出済みコメントと操作可否を画面が利用し、JavaScript側へMarkdown解析を複製しない。

エージェント由来のawiの通常本文はエージェント由来の要求とし、末尾の厳密なH2 `## ユーザーコメント`配下から導出した要求だけを人間由来とする。
両方にまたがる記述は独立して採否を記録し、ファイル全体の由来を人間へ昇格させない。
sourceの原値と予約節は由来と確認境界を示す情報であり、ユーザーによるpush、公開、破壊的操作または外部サービス変更の認可を証明しない。
エージェント環境から起動した`atk`は予約見出しを含む新規投入と、予約節を変更する編集の双方を拒否する。
エージェントはユーザーの発言を本文中へ出所を示して引用し、予約見出しを生成しない。
`atk serve`のブラウザー操作は人間の入力として扱い、拒否の対象にしない。

### 却下した代替案

`agent-toolkit:add-awi-by-user`と`agent-toolkit:process-wi`を起動したセッションの同一主題に対する追加指示は、各`SKILL.md`が定める成果物へ反映する。
主題の継続かAWI投入と直接実装の境界が不明な場合は、変更または投入の前に確認する。

会話内の作業一覧だけで進捗を管理する案は、中断後に依存関係とユーザー回答を再現できないため採用しない。
未回答UWIを能動的に監視し続ける案も、外部入力がない状態で実行主体を占有するため採用しない。
別の作業複製間を独自の永続状態で競合調停する構造は、通常運用の責務に比例しないため設けない。

### UWIの選択肢の受領と保存

`atk wi add`の`--choices`は反復値を蓄積し、各指定のASCIIカンマ区切りを指定順に結合して、従来の文字列として保存する。
`--choices A --choices B,C`と`--choices A,B,C`は同じ選択肢を渡す。
集合を単値へ格納すると前の指定が失われるため、引数解析で蓄積する。
選択式UWIの非空の選択肢が2件以上という条件は`add_validation.py`の`_validate_add_entries`へ置き、CLIの通常投入・dry-runとWebの通常投入で共有する。

本文に記載した選択肢と結果の説明をchoicesと自動で比べる案は採用しない。
通常投入の本文は自由なMarkdownであり、固定の箇条書き構文を解析して拒否すると既存の正しい本文にも新形式を要求する。
今回の値の欠落は引数の蓄積と最低件数で防げるため、本文との意味上の一致は起草時の読み直しで扱う。
保存済みのchoicesの修復や一括取り込みの原文変更は行わない。
