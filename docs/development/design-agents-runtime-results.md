# 終了時の結果の回収と待機ロックの設計記録

[設計記録の索引](design.md)から参照する、終了時の結果の回収と待機ロックの記録である。

## 終了時の結果の回収と待機ロック

子sessionへ送った`send_message`の公開応答が再開対象を示す場合は、そのsessionを再び追跡対象へ登録する。
親の待機表明は再開した子の終了まで保留する。
登録簿の`MISSING`・`RELEASED`・`UNREADABLE`は終了の証拠にせず、同じ子識別子を次の監視でも解決する。
終了登録または共有された終了時の結果を確認した後に同じ親へ1回だけ継続を送る。
公開waitで回収済みの子は既存の出力追跡で集合から除き、再配送しない。
登録簿の公開・解放・中断履歴更新・掃引は、sessionごとの共有ファイルロックで読み取りから置換・削除までを直列化する。
解放は所有サーバーの起動単位とturn番号が一致する場合だけ行い、古いturnの公開も新しいturnを上書きしない。
旧所有者の保持期限と新所有者の再開が重なった場合に、実行中の新turnが解放済みへ戻る競合を防ぐためである。
ロック実体は保持して同じinodeを共有し、原子的なファイル置換は既存方式を使う。
子session、Codexの子thread、Claudeの`local_agent`など終了上限を持たない対象の待機は、`auto_resume_deadline=None`で保持する。
名目7800秒の通知期限で保留結果を最終化すると、生存中の子の作業が未観測のまま失われるためである。
有界の背景コマンドには通知欠落を検出する期限を保ち、対象自身の寿命と通知の期限を分ける。
ClaudeとCodexの試験入力は、実際の公開応答を生成する処理から作成する。
起動時の子だけを追跡する案は、追送で再開した子を親の終了判定から失わせるため採用しない。

同じディレクトリ配下の`results/<session_id>.json`へ、終了したsessionの結果本文を原子的に書く。
内容へsessionごとに1から始まり新しいturnの開始ごとに1増える`turn_seq`と、終了時刻の`finalized_at`を含める。
終了時の結果を回収済みかどうかは`results/<session_id>.json`の存在だけで決める。
回収は`agent-toolkit/agent_toolkit/_agents_server/retained_results.py`の`take_result`だけが行う。
同処理は`results/.<session_id>.claim.lock`の排他ロックの内側で、結果本文の読取、公開した書込主体と所有者が一致するかの確認、ファイルの削除を1つの原子的な区間として実行する。
所有者が一致しない場合は結果を返さず、ファイルも削除しない。
`kill`、MCPの内部待機および`atk agents wait`はいずれも同じ`take_result`を経由して回収する。
回収する各委譲元に、結果ファイルの読取と削除を個別に持たせない。
読取と削除を別の呼び出しへ分けると、2つの処理が同じ結果を読んだ後に一方だけが削除でき、同じ結果が重複して配送されるためである。
MCPサーバーは、一度書いた結果ファイルが消えている場合に結果を公開したsessionを回収済みとして扱い、消えた結果ファイルを再作成しない。
保持期限（30分）はbackend資源とsession本体を解放する期限である。
未回収の終了時の結果は期限の経過後も`atk agents wait`による配送か`stop`による破棄まで保持する。
`atk agents wait`が`status`を`expired`とする応答を返すのは、期限を過ぎたsessionの結果が回収済みか存在しない場合だけである。
同じsessionの新しいturnを開始する時点でも、前のturnの結果ファイルを同期的に削除する。
削除は`send_message`と再開の応答を返す前に完了させるため、応答を受け取った呼び出し側は`atk agents wait`だけで再開したturnの終了を待てる。
待機対象のturnの番号を引数で受け取る案は、呼び出し側が`turn_seq`を転記する必要を残し、転記の誤りによって、別のturnの結果を待機中のturnの終了として受領し得るため採用しない。
`atk agents wait`は結果ファイルの確認と同じ周回で未回収の通知を回収し、結果を標準出力へ配送した場合だけ対応する結果ファイルを削除する。
回収処理を1つに限ることで、同じ結果・通知を二重に配送しない。
終了時の結果が未到達で通知だけを回収したsessionは、`status`を`running`とする行で返し、呼び出し側は再待機の要否を行の`status`で判定する。
回収の途中で結果ファイルの読取に失敗した場合は、同じ巡回で回収済みの本文を先に標準出力へ配送してから非0で終える。
回収は結果ファイルと通知ファイルの削除を伴うため、読取に失敗した時点で配送を取りやめると回収済みの本文が失われる。
読取の失敗は次の起動でも同じ状態で現れるため、診断の報告を1回遅らせても失われない。
`atk agents wait`は終了行の`agent_message`を呼び出しごとに作成するmanaged-tempのMarkdownファイルへもそのまま書き、その絶対パスを`agent_message_path`で渡す。
各行には起動時の`label`も加え、出力を保存した場合の要約行は終了行ごとに、本文の`agent_message`と通知の`notices`を除く全項目（`label`、本文ファイルの所在、`error`、`next_action`など）を示す。
委譲元が`session_id`から依頼名への対応表や、JSON文字列のエスケープを解いて本文を取り出す処理を持たずに結果を読めるようにするためである。
要約行の項目は除外する項目の指定で決め、終了行へ加わった項目は要約行を作成する処理を変えずに現れる。
項目を名前で選んでいた版では、失敗で終了した行の`error`と`next_action`が要約行に現れず、本文が空の失敗を委譲元が原因不明として扱い、利用上限で失敗したsessionへ継続を送った。
`show`も終了したsessionが保持する空でない`error`を返し、結果を回収できなかった委譲元が原因を確かめられるようにする。
`agent_message`は既存の消費側の互換のため行に残す。
本文ファイルは配送より前に書き、書けない場合は回収途中の結果をrun別退避物と待機対象の登録に残したまま非0で終えるため、次の待機が同じ結果を再配送できる。
終了行の`agent_message`を除いて出力を短くする案は、既存の消費側を壊すため採らない。
Claude Codeの`/goal`はターン終了時に評価対象のセッションが起動した未完了のBashのバックグラウンドタスクが無い場合に目標評価を発動する。
`atk agents wait`をBashのバックグラウンドタスクとして起動すると目標評価が延期され、委譲先の終了・上り通知でセッションが再開し、その標準出力だけで配送が確定する。
MCPサーバーへ待機専用のツールを追加する案は、追加した待機ツールの呼び出しも背景移行の対象となり目標評価の延期条件を満たさないため採用しない。

`atk agents wait`の待機所有権は書込主体につき1件とし、`wait-locks/<書込主体>.lock`のファイルロックで表す。
先行待機は`wait-results/<書込主体>/<run_id>.json`へ実行中・公開済み・回収済みの状態を保存し、`current.json`へ現行run識別子を置く。
同じ書込主体から2つ目の待機が発行された場合は、現行run識別子を固定してlock解放を待つ。
後発はlock取得後に固定runの状態を読み直す。
未配送の`published`なら保存本文と終了コードを1回返し、配信済みの`foreground-delivered`・`consumed`なら本文を再配送せず終了コード8と保存先への回復情報を返す。
先行待機が未公開の`running` runを残して終了した場合は、後発が同じrunの所有者となり、保存済み対象とrun別退避物を引き継いで結果または通知の回収を続ける。
lock待ち中に先行待機が追加した対象も引き継ぐ。
run記録を持たない旧形式のlockとの競合は診断を添えて直ちに終了コード8で返す。
先行runを特定できる競合は、ロック取得待ちと結果待ちへ単一期限を適用する。
異なる書込主体の待機は互いに遮断しない。
却下した代替案は、対象sessionごとにロックを取る案と、回収処理をCLIとMCPで別々に持つ案である。
第1の案は待機中に対象sessionが動的に増えるため、一部のsessionのロックだけを取得した状態が生じ、同じ書込主体の2つの待機が対象集合を分割して保持し得る。
第2の案は所有者の一致確認と消費済み判定を定める箇所が2つに分かれ、片方の修正が他方へ及ばない。

待機対象が0件の終了（終了コード10）と、後続の待機による消費済みの終了（終了コード8）は、同じルートと書込主体の保存結果の所在を診断へ加える。
現行の待機runを指す索引`wait-results/<書込主体>/current.json`から、結果を保存した`<run_id>.json`を解決する。
診断の`run_path`はこの保存先の絶対パスであり、対象sessionと実在する本文パスも示す。
先行waitの継続実行を回収せずに再発行した場合も、保存済みの結果へ戻れるようにするためである。
ロック取得前に`get_cli_wait_timeout("main")`から単一期限を開始し、非ブロッキングの取得を繰り返す。
取得後の結果待ちには残時間だけを渡す。
競合が期限まで続く場合は終了コード8で、書込主体・固定run・対象・`run_path`と次の操作を返す。
先行待機の保存出力を読み、先行待機の終了後に再待機する。
保存出力を受け取れない場合は、`run_path`の`output`（`jq -r .output`で読める）にある`agent_message_path`から本文へ到達できる。
run記録は本文を重ねて持たず、本文は終了ごとの本文ファイルだけが持つ。
取得失敗だけで原本・退避結果・先行runを破棄しない。
同時発行、ホスト識別子の別名、対象の追加と正常な長時間待機も同じ期限を使う。
runの`foreground-delivered`は結果を前景の呼び出し元へ返した状態、`consumed`は後続の待機が未配送の保存結果を配送して消費済みにした状態を表す。
どちらもエージェントの読了を記録しないため、診断は保存された結果の所在を示すにとどめ、自動で再配送しない。
runが無い、読めない、結果を含まない場合はその区別を診断へ返し、別の所有者のrunは復旧先にしない。
読了フラグを新設する案は配送後の読了を観測できず、結果を再配送する案は一度だけ回収する契約に反するため採らない。
知識境界として、終了時の結果の所有者の一致確認と一度限りの回収は`retained_results.take_result`が持つ。
`atk agents wait`とMCPの内部待機は、待機対象の決定と応答の整形だけを担い、結果ファイルの読取と削除を自ら行わない。
