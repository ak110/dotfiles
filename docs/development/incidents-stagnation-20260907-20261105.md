# 障害・欠陥の記録: 停滞と空転（2026年9月7日〜11月15日）

[停滞と空転](incidents.md#停滞と空転)の事例を発生時期別に収録する。

- 2026年9月7日: 検証中の委譲先が33分間停止し、ユーザーが稼働状況を質問するまで検知しなかった。
  定時起動の間隔は3分であり、停止から検知までに10回以上の定時起動が発生した。
  直接原因: 停滞の判定が観測値の相対的な差だけで定義され、成果物ファイルの更新元を別主体と区別できない間の保留が無期限に成立した。
  対策: 観測値が30分間変化しなければ保留を解除して催促へ進むよう、保留時間に上限を設ける

- 2026年9月8日: 実行レビュー担当が自身の委譲先へ`agents_server`の`wait`を`timeout`省略で発行し、MCP層が300秒で`timed out awaiting tools/call`を返す事象を3回反復した。
  直接原因: `wait`の呼び出しに対し、timeoutの省略時にMCPサーバーが導出した待機上限が、MCPクライアント側のツール呼び出し上限を超えていた。
  対策: 委譲先として起動されたセッションのMCPサーバープロセスは、環境変数の印から自身の位置を判定する。
  timeoutの省略時の待機上限を、そのMCPクライアントのツール呼び出し上限内に収める

- 2026年9月27日: 協調モードの公開時機を選ぶ確認で、3案がいずれも完了時判断を前提とし、ユーザーが着手前の確認を自由記述で補った。
  先行する4件の対策（2026年9月16日、9月18日、9月25日の2件）では、共通前提の列挙、先行判断、工程順序、後段の終了をそれぞれ条文に加えていた。
  直接原因: 共通前提の一般則に、選択肢の起草時に質問本文へ前提を記載する書式が無かった。
  起草者は種類別の条文を適用せずに質問を発行できた。
  対策: 各質問に`共通前提:`行を置き、前提を外した案か載せない根拠を記す。
  処置の段を条文の種類の追加から質問本文の書式へ移し、前提を確かめる契機を質問ごとに設ける

- 2026年9月30日: Claude Codeの過去のEdit失敗とRead後の成功の記録から、その失敗の再現をWIの必須の完成条件に採用した。
  処理側の主セッション4条件と実サブエージェント1条件では初回Editが成功し、完成判定の変更へユーザーの確認を要した。
  直接原因: 過去の事象の裏付けを、次の担当が現在の手段と条件で再現できる根拠として扱った。
  対策: 外部の既存挙動を必須観測に採る前に、WI投入担当が要求する手段・条件で成立を確認し、非再現と条件不一致は任意の判断材料へ移す。
  合意済み要件が観測を必要とする場合は差し戻す。
  共通判断をwi-standardsの完成条件の基準へ置き、起草工程から接続する

- 2026年9月30日: 振り返り結果の報告方法を変える確認で、共通前提行に合意済みの予告の前提だけを書き、報告本文の作成主体と情報のそろう時点を書かなかった。
  ユーザーは作成主体を誤解して問い返し、事実を加えて同じ質問を再提示する往復が1回生じた。
  直接原因: 共通前提行の記入対象が合意済みの前提に限られ、判断の時機・実施の主体などの軸は前提を外した案を探す用途にだけ使われていた。
  対策: 共通前提行の記入対象へ、選択肢の評価を左右する技術的事実（作成する主体、その時点でそろう情報など）を加え、同じ軸でその事実を探す。
  Codexの固定形式のプレースホルダーも同じ記入対象へそろえる

- 2026年10月1日: 300件を超えるファイルの説明文の是正で、計画が一括置換との比較を記録せず、4つの内部群へ多数のファイルを割り当て、群の中の分業も行わずに長い直列処理を進めた。
  直接原因: 一括置換の手順と低費用手段の比較の規定は存在したが、比較の規定は人間が方法を示した場合だけを契機とし、内部群の規定は4担当の目安と所有・統合だけを定めていた。
  方式の選択と分担の粒度を作業量と難しさで決める工程へ接続されていなかった。
  対策: `agent-toolkit:delegation/references/routing-units.md`「委譲単位の確定」へ作業量と難しさによる分割の判断を集約し、計画の実施内容の比較を多数の反復作業へ広げ、表記の一括置換の手順に方式比較の契機を加えた。
  内部群の4担当の目安は判断へ置き換え、所有表、別worktree、終了観測と統合検収は維持する

- 2026年10月6日: Claude Codeのメインが`add-wi.subagent.md`の担当を起動する前に、`agent-toolkit:delegation`の`references/`配下4資料（計527行）を読んだ。
  直接原因: `start`の`subagent_md_path`が絶対パスだけを受理し、メインのシェルでは`${CLAUDE_PLUGIN_ROOT}`を使えなかった。
  対策: `start`が役割名を受理し、modが`start`の処理の中で定期再確認を装着する

- 2026年10月6日: 分割したAWIの登録でQualityとDeliveryのどちらを優先するかを問う確認で、メインは`共通前提:`行に保留の根拠を規範のファイル名と規定の要約だけで書き、割当先の記録が後工程の実行レビューと統合時の判定に割当外の要求単位を達成対象と誤認させないことを書かなかった。
  ユーザーは選択肢を選ばずに規則の理由と必要性を問い返し、手順が必要な理由を説明するよう是正した。
  直接原因: `agent-toolkit:atk-mode/playbooks/confirmation.md`の確認提示項目の「根拠」が項目名だけで、既存の規範・手順・仕様を挙げる場合に名前や所在を書けばよいか、それが防ぐ事象まで要るかを定めていなかった。
  対策: 確認提示項目を定める段落へ、根拠、`共通前提:`行または選択肢の説明で既存の規範・手順・仕様を挙げる場合は、それに従うことで防ぐ事象か確保する結果を書くことと、その理由を加えた。
  項目の集合は変えない。
  発行前の機械的な検出は、防ぐ事象を説明したかが文意の判定であり規範のファイル名を含む正当な確認も警告するため採らない

- 2026年10月6日: 委譲先が起草して投入済みのAWIについて、ユーザーから実装と既存手順の整合を問われた委譲元は、当該委譲先へ追加調査を返さず、自ら実装と履歴の調査を始めた。
  ユーザーが、既に詳しい委譲先へ渡すよう是正した。
  直接原因: `agent-toolkit:delegation/SKILL.md`「継続と新規起動」は同じ作業の継続方法とユーザー介入時の差分反映を定めていたが、委譲先が担当する要求へ追加調査が生じた場合の調査主体を定めていなかった。
  対策: 「継続と新規起動」へ、調査中か調査済みの要求の追加調査は当該担当へ追加情報と論点を渡し、委譲元が同じ目的の調査を重ねない規定を加え、稼働中の担当への追送と終了した担当の継続・回復・置換の既存条件へ接続した。
  独立したレビューと異なる観点の評価は新規起動のまま区別する。
  UserPromptSubmitの注記は変えない

- 2026年10月6日: Claude Code 2.1.289のauto modeで、規範変更AWIを起草する委譲先を待つ単独の`atk agents wait`が`Self-Modification`として3回拒否され、同じコマンドの手動実行まで終了時の結果を受領できなかった。
  直接原因: `Session And Delegation Control`が委譲先への継続指示と値を変更しない参照を許可する一方、受領済み化と結果・通知ファイルの削除を伴う結果受領を委譲ライフサイクルの操作として含めていなかった。
  対策: 同じ許可規則を、委譲内容にかかわらず状態・終了・通知・結果を観測して受領する操作へ広げる。
  `atk agents wait`・`list`・`show`は代表例とし、サブコマンドの閉集合にはしない。
  既知の誤拒否パターン表も同じ境界へ接続する

- 2026年10月6日: process-wiの実行レビューで、レーン担当がエージェント由来のAWIの完成条件（生成元が現行に無い旧形式の回答を確認回答として除外する条件）を外す判断を求めた。
  外すかどうかは技術的に決まっていたが、メインはユーザー判断の記録が無いことを理由に確認を発行し、ユーザーが、エージェントが判断できないことだけを聞くよう是正した。
  直接原因: `review-loop-coordination.md`の判断要請の行が、否定したユーザー判断も会話中の否定の発話も無い場合にユーザー確認を求めていた。
  対策: エージェント由来のAWIの完成条件のうち、明示由来の要求単位に対応せず、人間が確定した判断の変更に当たらず、ユーザーだけが持つ値を必要としないものをメインが技術判断で確定し、レビュー指摘管理表へ記録した行を失効の根拠として受理する

- 2026年10月27日: 委譲先が前のturnの中断を`想定外事象:`として十数回返していたのに、メインはユーザーに指摘されるまで原因を調べなかった。
  直接原因: `agent-toolkit:delegation/references/receiving-followup.md`「受領後の扱い」は`気付いた改善点:`の原因分析をreview-sessionへ集約すると定める一方、`想定外事象:`の受領時に原因の調査へ着手する契機を定めていなかった。
  対策: 同節へ、ツールや実行基盤の異常を示す`想定外事象:`が同じ種類で2回現れた時点で原因の調査に着手する（調査は委譲してよい）規定を加えた。
  通知機構の欠陥の処置は`agent-basics:bugfix/references/root-cause-analysis-initial.md`「問題を見つけたときの対処」へ接続した

- 2026年10月31日: 処理を停止させる既存のhook不良を、担当エージェントの切り替えで回避し、欠陥そのものの直接修正を次のセッションへ送った。
  直接原因: 即時対応の範囲を今回の進行だけで表す文と、次のセッションも含む定義が併存し、担当の回復を選ぶ判断点から欠陥の処置へ接続されていなかった。
  対策: `agent-toolkit:atk-mode/playbooks/process-wi-immediate-fix.md`へ定義を集約し、交代や迂回と直接修正を区別する。
  回復を選ぶ判断点とall-repos統括の報告受領から同じ定義へ接続し、残る工程・次のセッションの停止可能性と根拠を正式対応AWIの前に記録・検収する
