# 通知仕様の追随と読込宣言の回復の設計記録

[設計記録の索引](design.md)から参照する、通知仕様の追随と読込宣言の回復の記録である。

## 通知本文の仕様とエージェント向け文書の長さの追随検出

`agent-toolkit`の通知本文と常時読み込むエージェント向け文書を変更した主体が、変更の時点で追随すべき対象を把握できるようにすることを目的とする。
変更箇所と直接接続していないテストや上限が全体チェックで失敗する事象の検出を、統合の後から編集の時点へ移す。
構造の理由は、同じ外部仕様を固定する箇所を1か所へ集約する点にある。
ユーザーが直接読む本文へのチェックは`agent-toolkit/agent_toolkit/_hooks/pretooluse/dispatch.py`の`_decide_user_facing_text_tool`へ集約する。
適用対象は同ファイルの`_USER_FACING_TEXT_TOOL_NAMES`だけで定める。
エージェント向け文書の合計長は、上限の超過を検出した時点で文書ごとの長さと超過分を失敗本文へ示す。
上限超過時の診断本文は`agent-toolkit/agent_toolkit/_hooks/rules_context_test.py`が組み立てる。
知識境界として、上限値は`rules_context.py`の`CLAUDE_CODE_OUTPUT_LIMIT`が持ち、超過時の診断本文はテスト側が持つ。
却下した代替案は、相反する期待を持つテストの組をテストの意味から機械的に検出する案と、エージェント向け文書の編集時点で上限までの残量を示す案である。
前者はテストの意味解析を要して成立を確認できず、後者はエージェント向け文書の編集を検出する手段の特定を要するため採用しない。

## 読込宣言の未導入時と履歴の回復

2026年10月22日、Toolkitの全表を解決する段階でBasicsの未導入が判明すると、資料取得、plugin一覧とログ照会も止まる条件を確認した。
必要な資料へ判断前に到達させる契約と、導入を回復する操作の到達を両方保つ。

必要な行だけを後から解決する案は、起動時資料、役割、動的資料と保存済みの選択を含む解決時機の変更を要した。
回復操作を判別する案は、単一の静的な読取・公開診断と、欠けた依存の正規追加へ対象を限定できる。
2026年10月22日は後者を採用した。
2026年11月10日の変更では、反復される先行解決の実測を根拠に前者へ切り替え、関連する宣言の診断と回復操作を保持する。
宣言が解決できる通常経路も必要範囲の初回案内を使い、未取得が続く再書込を許可する。

未導入時もRead・Glob・Grep、単一のcatと静的な`sed -n`の行範囲の読取、plugin一覧、単発のagents logsなどの診断を通知付きで通す。
Basicsの正規追加は、公開plugin一覧で導入済み・有効なToolkitのmarketplaceが一意に決まる場合に、その同じmarketplaceのBasics追加だけを読込宣言の復旧前にも進められる操作とする。
実際の追加は元のコマンドが実行し、hookは読み込み完了を記録しない。
書込や未知の実行にも資料の取得条件を案内し、所有・秘密・承認などの独立した保護は残る。
確認操作の警告は非遮断を保ち、自分へ指定された引き継ぎ記録だけの編集は既存の免除を使う。

取得の再利用は「宣言型読込表による操作前配送」の共通照会に従う。
主体・文脈・受信版を分離し、現在のパスと全体hashだけで過去の受信を未読へ戻さない。

同名pluginの配布cacheと開発sourceが共存する場合は、稼働版と対象プロジェクトの宣言を先に使う。
資料参照を理由に別rootの全skillsを走査すると、未選択のsource版まで同じ操作の必読になる。
参照された資料を明示取得する時にその資料の宣言だけを加え、後続操作では同じ主体の現行本文に対応する読取成功の記録を再利用する。
起動時資料も選択した実体と同じ受領単位に含める。
名前空間付きの取得と起動は、実際に選択した所有rootへ対応付ける。

過去の選択は現行宣言へ再接続し、同じ要求本文の受信を共通照会で再利用する。
明示したproject skill、変更規範、役割、起動入力の要求は保ち、未選択rootの全skillsを必読候補へ追加しない。
