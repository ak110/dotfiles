# 方針・意向: WIの状態と遷移

## WIの状態と遷移

WIは作成年月ごとの固定パスへ置き、保存状態をfrontmatterの`state`へ分離する。
重要フラグは状態と独立させ、設定・解除・表示と、重要・非重要による表示対象の限定に使う。
通常のprocess-wiの選定は、ユーザーが重要項目を対象として明示した場合だけこの値を参照する。
現行の実装契約と配置の理由は[design-wi.md](design-wi.md)にある。
固定配置は状態遷移で参照が変わる欠陥を是正する設計判断であり、重要フラグの操作と通常選定の関係はユーザーが指定した要求に由来する。

現行の規範は`agent-toolkit:wi-standards`、`agent-toolkit:process-wi`および`agent-toolkit:write-plan`の計画ファイル基準にある。
選定の詳細は`agent-toolkit/skills/process-wi/references/selection-procedure.md`と`selection-format.md`が持つ。
WI処理の機構を設計した理由（却下した代替案など）は、[design.md](design.md)の索引から主題別の設計記録を選んで読む。

- キュー項目の削除はGit履歴から復旧できる手段として維持し、エージェントが自身の誤りで投入した項目の整理に用いる
- キューの全状態は`inbox`、`processing`、`hold`、`adopted`、`rejected`とする。
  公開一覧の`active`は`inbox`・`processing`・`hold`、`processable`は通常の自動処理へ渡せる`inbox`・`processing`とし、型による差を設けない。
  `hold`は明示操作までprocess-loop、readiness、UWIスキャンおよびalertsの対象にしない（2026年9月、ユーザー指示）
- 計画作成中の通常型AWIと外部編集中の項目はいずれも`hold`へ置く。
  用途別に`planning`と`editing`を分けていた区分は、自動処理から除外する点で同じ振る舞いになり、状態集合の定義が型と操作ごとに分岐する原因になったため廃止した
- `hold`は`inbox`・`processing`・終了状態から移動し、`unhold`では`inbox`へ戻す。
  保留元を推測して`processing`へ戻す処理は設けない。
  終了状態からの再開では旧処理結果を除き、過去の採否を現在の結果として残さない。
  `hold`は自動処理からの除外だけを意味し、編集、UWI回答、ユーザーコメント、採用、不採用および削除は`inbox`と同じ条件で許可する（2026年9月25日、ユーザー指示）
- 既存WIの更新・修復・採否の見直しが必要と分かった時点、または具体的な懸念を受けた時点で、調査や認識合わせより先に`hold`で自動処理から除外する。
  採否の確定を待つことと保護を待つことは別であり、操作しない間に別主体が処理を始め得る結果も損失として評価する。
  保留は更新の必要が分かった時点で行い、保留の後で復元できることを先送りの理由にしない。
  2026年10月3日、ユーザーが保留の判断の遅れと「行動しないこと」が不可逆な変化を生む場合を指摘した発話に由来する。
  対応commitは2026年10月4日「fix: 既存WIの更新や採否見直しでは調査より先に保留して並行処理の開始を防ぐ」、`606450dfa`である
- エージェントが編集のために保留した項目は、修正、保存本文の検収、解除を独立した他の作業より先に進め、保留の時間を最小限にする。
  修正に必要な調査は先に行い、無関係な全件調査や別要求の作業は解除後に回す。
  時間上限での自動解除は未修正の本文を処理対象へ戻すため採らない（2026年10月31日、ユーザー指示「holdにしたまま放置しないで直すべきものはさっさと直してよ。その後に他の作業やって。hold時間は最小限にすべき」）。
  実行規範は次の資料にある。

  - `agent-toolkit:wi-standards/references/states-and-dependencies-editing.md`「保留と本文修正」
  - `agent-toolkit:/share/add-wi-parent-inputs.md`
  - `agent-toolkit:/share/add-wi-parent-acceptance.md`

- エージェントが作業している項目は、開始経路を問わずキュー上で`processing`にする。
  対象は通常のAWI、作業を伴う回答済みUWI、依存の解消や`unhold`で`inbox`へ戻った元項目で、経路はprocess-wiの選定、中断した実行の再開、実行中の回答の反映、process-wiの外での回答の反映を含む。
  作業を伴わない回答済みUWIを選定直後に終了する扱いと、事後承認型UWIの肯定回答を直接`adopted`にする扱いは変えない。
  選定の手順だけが遷移を定めていたため、選定を通らずに作業した項目が`inbox`のまま終了していた。
  2026年11月のユーザー指摘（エージェントの対応が要る回答済みUWIが`processing`にならないまま採用される。AWIと同様に処理中は`processing`にする）への対処である。
  契約の定義元は`agent-toolkit:wi-standards/references/states-and-dependencies-states.md`「状態遷移」で、作業を始める各手順はこの定義を参照する。
  `atk wi adopt`は`inbox`の項目を`--commit`付きで終了したときに遷移の抜けを警告する
- 項目の削除は、明示`state`として`inbox`・`processing`・`hold`に加えて終了状態（`adopted`・`rejected`）も受理する。
  エージェントが自身の誤りで投入した項目を`atk serve`の画面から片付けられるようにするためであり、`processing`の削除保護は維持する
- エージェントが実行してよい遷移は`inbox`と`hold`の相互移動、`inbox`から`processing`を経た`adopted`・`rejected`への終了、および`adopted`・`rejected`から`inbox`または`hold`への差し戻しとする（2026年9月25日、ユーザー指示）。
  `hold`から`adopted`・`rejected`への直接の終了も同じく実行してよい（2026年9月30日、ユーザー指示）。
  ユーザーはブラウザーUIから任意の状態へ遷移させられる。
  本文の編集は保存状態によらず行える（2026年9月、ユーザー指示。規範の不具合で操作不能に陥る障害を避けるため、状態による編集の制限を増やさない）
- キュー原文のスナップショット、ハッシュ、差分比較、原文変更時の遮断またはUWI化は設けない。
  現行のキュー取得機能を利用し、追加の恒常状態を持たない方針とする
  （2026年8月、ユーザー指示。原文変化への追加対策を実用上の対象外としたため）
