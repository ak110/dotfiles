# レビュー契約と指摘管理表の設計記録

[設計記録の索引](design.md)と[計画と実行レビューへの受渡しの設計記録](design-planning.md)から参照する主題別の記録である。

## `review_contract`とレビュー指摘管理表

契約生成は同じリポジトリのcommit実在と現在HEADへの包含で判定し、計画を作成したworktreeとの一致は要求しない。
計画作成と計画構造チェックの実行場所が対象worktreeと異なる場合は、対象worktreeからの実行または`--work-dir`の指定を案内する。
共通Git診断は事実を返し、公開コマンドがその入力契約に合う次の操作を加える。

レーン担当は要求と調査根拠を知り、実装者が再現できる判断を計画へ残す。
メインは全実装単位と変更範囲の検証の完了後、初回実行レビューの起動直前に、計画外の明示入力からだけ`review_contract`を生成する。
計画だけから全条項が定まる場合は生成しない。
再レビューの指示の直前にも、そのレビューの開始時点から現在HEADまでの累積差分へ別の計画で認可されたcommit（同じレーンの追加計画のcommitなど）が加わっていれば、その独立条項を現在のOIDで生成し、初回の条項と合わせて検証してから`再レビューせよ`と同じ送信へ含める。
実行レビュー担当は受領した契約を以後の契約として置き換える。
初回起動時点の契約だけを保持すると、起動後に同じbranchへ加わった別計画のcommitやrebaseで変わったOIDを再レビューが範囲外と指摘し、対応不要の記録と契約の追送が1往復ずつ増える。
先行計画の再レビューを自計画のcommitだけに限る案は、レビュー担当へcommitと計画の対応を伝える新しい入力が必要になり、既存の独立条項が同じ対応を運ぶため採用しない。
各条項は独立して成否を判定できる粒度とし、計画外の契約本文または一意な参照先と出典を委譲プロンプトへ含める。
専用成果物と計画ファイルの固定H2は設けない。
`review_contract`はMarkdownの「条項・内容・出典」の組と計画別の判定対象外commitで渡し、commitとWIの参照は条項内に置く。
送信側は初回・再レビュー・担当交代の配送でこの形式を書く。
受信した実行レビュー担当が条項からcommitを解決し、WIと認可資料を取得して認可範囲を確認する。
未解決の参照や認可不足は続行できない理由として返す。
commitの実在だけで認可済みとせず、共有公開契約・安全性・統合結果の評価も続ける。
別配列への二重記載は受信担当が読む情報を増やさず同期を増やすため撤去した。
ハッシュ、台帳、遮断hookや新担当で同期を補う案も採らない。

自計画のcommitと旧OIDは、計画の対応記録（`plan-commits`）から求め、別計画の認可へ混ぜない。
追加条項は改変せず併合する。
認可の意味を推論する機構や永続台帳は設けない。
履歴の書換え後の影響判断は、計画ごとに`git range-diff`と`git diff --name-only`を直接使い、比較の結果と理由をレーンの引き継ぎ記録へ記す。
影響がない計画の再レビューを省ける。
比較失敗を影響なしへ変換しない。
実行レビューの単位は計画の境界ではなく共有する変更で決め、変更ファイルか検証を共有する複数の計画は1回のレビューと1つの契約で扱う（2026年11月11日）。
同じ巡回で、1つのレーンが同じ背景の変更を3つの計画に分け、契約と証拠の準備とレビューの起動を3回ずつ行った観測に基づく。
計画ごとに分ける方式は要求の識別を計画の単位で保つためだったが、同じ識別は1つの契約の中の計画名とAWIごとの行でも保てる。
レビューを省く案と担当を計画の数だけ増やす案は採らない。
手順は`agent-toolkit/share/exec-review.parent.md`が持つ。
2026年10月25日に、条項の生成・構造確認を担った`review-contract`と比較を担った`review-impact`を撤去した（ユーザー指示）。
Gitの標準の比較と既存の対応記録で同じ判断が得られ、専用の入力JSONを各担当が学ぶ費用が便益を上回ったためである。
実行レビュー担当は計画の既存節と開始時点の実体から条項を生成し、計画外の`review_contract`を受領した場合はその条項も合わせて差分と比べる。
第2段階では計画の採用案に加えて、正規化した目的、公開契約、境界条件および安全性を評価する。
計画情報を渡さない別コンテキストでの検証は廃止するため、計画情報を持つ評価と計画から独立した観点を同一担当が順番に扱う副作用として、別コンテキストによる独立性は保証しない。
実行レビュー担当は二段階の候補をレビュー指摘管理表へ統合し、成果物を変更しない。
修正担当は同表の指摘を採否判断し、採用した指摘へ対応して、詳細な採否と対応結果を表へ記録する。
レビュー指摘管理表の構造と操作は`agent-toolkit/agent_toolkit/_atk/review_table.py`が定める。
初回レビューのレビュー指摘管理表は、不在の場合に限り、消費する実行レビュー担当が`agent-toolkit/share/exec-review.subagent.md`の共通手順で最初の読取前に初期化する。
親はパスを解決して渡し、表の不在だけで起動を拒否しない。
計画・WI・CIの呼出元ごとに準備主体を増やす案は採らず、登録と準備を同じ担当にまとめる。
既存表の指摘・応答・ラウンドは保持し、再レビューと引き継ぎ再レビューの不在を新規表で隠さない。
共通のラウンド受領、モデル解決と収束判定は`agent-toolkit/share/review-loop-coordination.md`へ集約する。
実行レビューは計画ディレクトリの`<計画stem>.exec-review.tsv`へ`exec-review`を付ける。
レーンごとにレビュー指摘管理表用のmanaged-tempの作業ディレクトリを作成する運用は行わない。
レビュー指摘管理表が計画ディレクトリへ移った後はレビュー指摘管理表用の一時領域に用途が残らず、レーンが作成・受け渡し・回収する資源を1つ削減するため撤去した。
実行レビュー担当は同じ`track`の表をラウンドごとに引き継ぎ、過去ラウンドの行を変更せず今回の候補だけを追加する。
レビューイーは修正対象として渡された`track`集合の行だけを扱う。
計画ディレクトリのレビュー指摘管理表では正規のファイル名と、`atk review-table`が扱う表の構造・`track`・行数を実際に確認する。
各実装担当以降のHEADや`review_contract`へ混入した未承認契約は認可根拠に含めず、
修正後の累積差分の比較は重複確認として維持する。
`exec-review`以外の新規trackは生成しない。

初回レビューの起動後に受領した人間由来の入力は、素材の種別、逐語文、出所、引用範囲および合意と参考素材の別を
レビュー担当へ渡してから再レビューを指示する。
キューにない素材の逐語本文・回答全文も計画外の明示入力として追送し、初回から同じ値を再レビューへ保持する。
同じ担当へ同じタスクを返し実効3値が一致する継続接続では同一threadへ追送し、不一致時の新規起動では初回入力とともに渡す。
レビュー担当は初回起動時点の入力しか保持しないため、追送しない発話を根拠とする実施または除外は計画へ書かない。
出所と引用範囲を失った要約だけを伝える案は、レビュー担当がユーザー合意の範囲を確定できないため採用しない。

計画どおりであることとエンドユーザーにとっての成果として正しいことは別の判定であるため、実行レビュー担当は計画との比較の後に
計画から生成した条項と、受領した場合の`review_contract`を用いて成果物評価をする。
レーン担当または実装担当だけの自己レビューは、採用案の前提を共有して
見逃しを独立に検出できないため採用しない。
計画情報を渡さない別コンテキストへ成果物評価を分ける案は、1ラウンドの
起動を2回にしてコストを増やすため採用せず、独立した評価観点を同じ担当の第2段階として維持する。
