# レーンの継続と要求の由来の設計記録

[設計記録の索引](design.md)と[担当の責務と工程間の知識境界の設計記録](design-workflow-boundaries.md)から参照する主題別の記録である。

レーン工程のレーン実行中、メインは全レーンの状態把握、レーン間の調停とユーザー判断への応答を保持し、
自身のコンテキストを消費する調査と、稼働中のレーンから独立した割り込み作業を委譲先へ移す。
AWI本文とレビュー指摘管理表を読む契機は、メイン自身が判断を確定する場面へ限る。
要求単位の由来は、レーン担当が計画の起草時にAWI本文とfrontmatterから判定し、計画の概念単位ごとに`由来`欄へ記録する。
異なる由来の要求が1つのWIに混在する場合も、概念単位を分けて表現する。
選定結果へ由来を書かず、メインと、統合するレーン担当は、統合時に由来を再判定しない。
人間由来の要求を全部または一部不採用にする確認は、レーン担当が計画確定前にメインへ即時通知して完了させ、後続工程は計画で確定した採否と終了区分を用いる。

処理中に確定した必須是正を稼働レーンへ追加する場合は、割当と同時に開始まで含めた指示を1回送る。
レーン担当は現在工程を完了した後にturnを終えず追加した処理対象WIの計画起草へ進み、現在工程の結果を追加した処理対象WIの最初の工程境界の本文の先頭へ含める。
最初の工程境界はその形式の届け方に従い、メインの判断を待つ`計画作成完了`と`計画なし準備完了`は返却、非待機の`計画検査完了`は`atk agents notify`で届けて同じturnで実装へ進む。
`agents_server`の委譲先では返却がturnの終了になるため、指示は最初の工程境界での返却を求めない。
現在工程の結果がメインの後続工程の入力になる場合は、その結果を先に通知してから進む。
開始済みの判定は追加した処理対象WIの最初の工程境界の返却または通知の受領で行う。
工程境界ごとに返却と開始指示を往復させる案は、同じ担当が続けて行える作業の着手を1往復ずつ遅らせ、担当の再開費用も生むため採用しない（2026年9月26日、ユーザー指示）。
最初の工程境界を受領する前にthreadが継続不能になった場合は公開応答から同じthreadの再開可否を判定し、再開不能なら事実・対象・不足する条件を続行できない理由として返して同じレーンの回復判断を受ける。

選定結果は対象リポジトリのプロジェクト規範が指定する内容を`プロジェクト規範の指定`として運ぶ。
メインは起動時のcwdとAWI本文から指定を解決し、参照先の実在と可読性を確認する。
消費側は選定YAMLを基準とし、委譲プロンプトへ値を複製しない。
知識境界として、何を載せるかはプロジェクト規範、受け渡しの形式は`selection-format.md`が持つ。
条件付きの必須記載は対象リポジトリの`pyproject.toml`の`[tool.agent-toolkit.pick-wi-check]`が定め、共通のチェックが保存後に欠落を検出する。
2026年10月6日に49項目の指定が全て省略された結果を受理し、目視の再取得を要したためである。
共通スクリプトへ固有のパスと文面を入れる案は内容の所有者を共有実装へ移すため採らず、ホーム側の設定はリポジトリごとの条件を持たないため使わない。
チェックが確かめるのは記載の有無であり、資料の実際の読込はレーン担当の消費に残す。
指定をレーン完了報告へ載せる案はレーン起動に間に合わないため採らない。
同じ表の`target-seconds`は、1回の処理の目標所要秒数をプロジェクトが与える欄である。
目標はプロジェクトごとの方針で配布物に値を持てず、選定YAMLへメインが手で書く形は読み落としを検査で検出できないため、既存の検査設定の表へ置いた。
チェックは目標との差を要約へ出し、超過時に配分の代替案の比較記録を求めるが、項目の除外やレーン数の判断には使わない。

エージェント由来の通常AWIは、`反映内容と反映先`、`適用範囲`、`完成条件`の対象集合を比べた結果の宣言を保存する。
3節のSHA-256 digestもfrontmatterへ保存する。
本文変更後に古い宣言を使う操作はCLIが拒否する。
人間由来のAWI、UWI、plan-file処理へ同じ制約を広げないのは、エージェントが自己生成した要求だけを通常より懐疑的に検収する境界を維持するためである。

AWI本文が示す文言案、列挙および節配置は、投入元識別子にかかわらずユーザー合意とみなさない。
レーン担当は目的と指定された外部可視要素を維持する文面を技術判断で確定し、原文との差異と根拠を採否記録と計画へ残す。
採用済み本文が明示する変更は確認事項または実装前提にしない。
残る事項だけを`agent-toolkit/share/rules/common/01-agent.md`「協調と自律」節の確認境界と照らし合わせる。
委譲元は同じ優先関係を検収し、確認境界に該当する事項をUWI投入処理へ渡す。
対象、範囲、外部可視の結果、除外内容を原文から新たに具体化する場合は、調査後かつ計画確定前にユーザー確認する。
同じ内容を明示したユーザー提案として採用する場合は、コードベースから確定できる事実、内部値の計測補正、配置、分割、テスト手段を確認対象にしない。

選定工程のメインは要求の採否と、既存の変更による充足を確定しない。
いずれも対象実装を読解して初めて確定するため、判定をレーン担当へ置く。
誤って充足済みと確定した要求は`adopt`で終了して検知手段を失う一方、充足済みを未充足と判定した損失は計画へ不要な実施内容を記録する工程だけであり、損失が非対称であるためである。
選定の意味判断は手順の読解と実セッションの試行で確かめ、CLI・YAMLの受理と文書の接続は既存の自動チェックで確かめる。
文面の存在だけを意味判断の成功と扱う案は採らない。
レーン担当は実施内容へ要求単位で由来と採否を記録し、同じAWIでも由来や承認範囲が異なる要求は行を分ける。
採用系（`採用`・`部分採用`）の行だけを実装対象とする。
frontmatterの`source`は起票処理の記録として扱い、本文と原発話から要求単位の由来と承認範囲を確かめる。
人間由来の要求の除外にユーザー判断が必要な場合は、通常の手順で確認する。
回答を得られない場合はUWIを保存して対象項目をholdとし、通常レーンから除外する。
同一セッションで回答を受領した場合は、回答保存、UWI終了、依存解除を確認して、メインの選定工程または同じレーンを`continuation.md`が定める継続の規定で再開する。
別リポジトリ項目の登録、突合および元項目の終了順序は、
`agent-toolkit/skills/wi-standards/references/cross-repository-submission.md`を基準とする。

この境界では項目単位の永続的な由来スキーマを新設せず、既存の採否記録へ原文の根拠を残す。
要求の由来とユーザー認可の確認を分け、起票処理や構造上の標識だけから承認を推定しない。
独立した採否レビュー工程や専用の移管機構を追加すると、既存の項目別調査、レーン担当の採否確定およびユーザーへの確認手段が分断され、
同じ採否記録を別状態で保持する恒常コストが増えるため採用しない。
採否確定の事実とユーザー判断の手順を既存の受渡しへ統合することで、
全項目の可視性と個別判断を保ちながら、計画の実施内容では採用系の行だけを実装対象として扱える。

エージェントが新規項目を投入する場合は、`agent-toolkit:wi-standards`に従い投入したスキル名からプラグイン名の修飾を除いた値を`atk wi add --source`へ渡す。
`agent-toolkit:add-awi-by-user`はユーザー発話を原文とする手動起動を含む全ての新規項目へ`source: add-awi-by-user`を保存する。
別リポジトリ項目の移管では新規起票の固定値を上書きせず、移管元に保存済みのsourceがある場合は同じ値を保持する。
