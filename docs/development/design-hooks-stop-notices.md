# Stopの通知と入力待ち判定の設計記録

[設計記録の索引](design.md)から参照する、Stopの通知と入力待ち判定の記録である。

## Stopフックの設計

### 未配送通知

未配送の完了通知の案内は、Stopの継続がキューに残った完了通知を配送しないホストの挙動に対処する。
バックグラウンドタスクがターンの終了より前に完了すると、完了通知は最上位transcriptの`queue-operation`へ`enqueue`として入る。
配送はツール呼び出し時の取り込み（`remove`の`absorbed_mid_turn`）か、ターン終了後の`dequeue`で起き、Stopフックや`/goal`の目標評価がターンを継続させても、継続した応答がツールを呼ばない限り起きない。
実行主体が完了通知の到着を待ってツールを呼ばずにターンを終えると、`/goal`の目標評価が「バックグラウンドタスクが未完了」と判定して継続を繰り返す（2026年9月30日の常駐セッションで5回観測）。
通常の受領では、Stopが現在ターンを`continue: false`で終了し、ホストが通知を配送する次ターンで保存結果を読む。
再開したターンでは、前ターンの配送終了を現在ターンのツール操作禁止と扱わず、保存出力・終了状態を回収して残る待機へ進む。
観測を試みた履歴は`pending_observation`のまま保持し、現在の継続主体はCLI待機ロック・対象登録と同sessionの自動再開から別に判定する。
対象登録へ残る同じ主体のsessionが登録簿で実行中と解決され、待機も自動再開もない場合は非遮断で案内する。
回収済み・終了済み・明示破棄済みの結果は再要求せず、新しい監視プロセスや同義の状態を持たない。
通知の発生元やgoalの有無による新しい状態を持たず、他の判定がblockを返す場合はその理由を優先する。
この場合の案内は通知の起動記録から種別を確かめる。
Agent・Taskに対応する通知ではtask-idだけを示し、配送された返却メッセージの利用を案内する。
返却済みの結果へ内部transcriptの読取を求めると、ホストの読取制約により受領できなくなるためである。
Bashと種別を判別できない通知では、task-idと出力ファイルの絶対パスを示し、同じターンでの読取を促す。
通知の発生元のツールの種別の対応は`background_tasks.py`が既存のtool-use-id集合とagentIdへの対応から解決する。
キュー復元では`popAll`と`popOne`も`remove`と同じく対応する本文1件を取り除き、配送済み通知を入力待ちと助言の両方から除く。
同じ本文の残りと別の本文は保持し、`popAll`を全消去として扱わない。
`popAll`の記録はユーザーが送信待ちの入力を入力欄へ取り戻した操作であり、無視すると取り戻した入力がキューに残って後続の`dequeue`の再生がずれる。
`dequeue`の記録は取り出した要素を持たないため、その後に最初に現れる最上位の`user`エントリのうち`tool_result`を含まないものの本文と比べて取り出した要素を決める。
本文と等しい要素、無ければ本文に含まれる要素を1件除き、どちらも無い場合と比べる対象のエントリが無い場合は先頭を除く。
ホストは完了通知と`<agent-message>`のように並んだ要素のうち先頭以外を先に取り出すことがあり、常に先頭を除くと配送済みの通知を未配送と案内し、未配送の通知を配送済みと誤る。
発火条件はキューの状態だけとし、`/goal`の有無、待機コマンドの種類および実行主体を条件に含めない。
キューの解析規則は入力待ち判定と共有する。
他のblockが残る場合の案内は`notify`で返し、`stop_hook_active`では抑止しない。
同じ通知への警告を1回に限る記録と警告回数は、実際に警告する場合だけ更新する。
配送へ戻す場合は案内済みの識別子を使わず、現在の未配送通知を使う。
共通応答が他のblockを上書きせず、他の通知本文とユーザー宛て通知も保持する。
毎回の出力読取を受領の前提にする案は、短時間の背景完了のたびに追加のモデル継続を生むため採らない。
CLIの前景の短いtimeoutへ替える案とgoalの有無を別のフラグへ記録する案も、既存のキューとホスト配送で結果を受領できるため採らない。
Claude Code本体の修正と上流への投稿は行わず、ホストが継続応答へ未配送通知を自然に取り込めるようになった時点で、この回避を撤去する。
常時規範へ「目標評価の指摘を受けたら出力ファイルを読む」旨を追記する案は採らない。
常時規範への追記の条件に当たらず、目標評価の理由文が「未完了」と述べるため実行主体が条文を想起しても誤った前提と競合する。
フックは実在する出力ファイルのパスを示すため、実行主体によるパスの推定を必要としない。
`/goal`のあるセッションで外側の`timeout`を付けた前景の待機へ切り替える案も採らない。
待機の規範は外側の`timeout`の連結を禁じ、バックグラウンドタスクでの待機は稼働中の延期が正しく働くことを観測済みであるため、空転の原因から除外できる。
`busy_loop_guard.py`で未配送の通知を無進捗として数え、閾値でセッションを停止する案も採らない。
停止はprocess-wiの実行そのものを失わせる一方、結果は出力ファイルに既に存在し、1回のツール呼び出しで回復できる。

### 計画保存の確認

`~/.claude/plans`に残る計画の保存確認は、現在のセッションが作成または編集した計画ファイル（メイン）が`~/.claude/plans`へ現存する場合だけ発火し、同じ対象が残る間は1回だけ確認を促す。
共通noticeで対象の変化と解消後の再発を区別し、セッション全体の通知済みフラグは使わない。
判定材料はセッション状態が記録する計画ファイル（メイン）の絶対パスのリストと、その実在に限り、実行レビューの収束有無を判定しない。
移動の要否は、通知を受領した実行主体が計画の進行状況から決める。
常駐実行の印があるセッションでは発火させない。
常駐実行では`agent-toolkit:process-wi`のレーン契約が`atk plans commit`による最終化を定めており、同じStopで`autonomous_exit.py`が停止を拒否し得るためである。
セッション終了イベントで検出する案は、通知を受領する実行主体のターンが既に終わっており、対処へ接続できないため採用しない。
実行レビューの収束状態をフックが判定する案も、フックが会話の意味と工程の妥当性を判断しない責務境界を越えるため採用しない。
対象の計画は、編集ツールの処理と計画ファイル作成処理の実行結果の双方から、計画ファイル（メイン）の絶対パスとして蓄積する。
作成処理はBashから実行され編集ツールを経由しないため、作成だけを行った計画は編集の記録契機に現れないためである。
作成処理の実行は、コマンドの区間分割と実行位置の解決により、計画作成処理を実行する区間だけを対象として識別する。
名称を引数、検索語その他の出力データとして含む読み取り操作を対象にしないためである。
パスは記録の時点で絶対化し、後続の作業ディレクトリの変更によって指す先が変わらないようにする。

### 自律終了の再促しと入力待ち判定

自律終了の再促は常駐実行の最上位セッションだけへ適用する。
常駐実行の印はプロセス環境で表され子のセッションへ継承されるため、`agents_server`が起動する委譲先セッションには起動処理が委譲先の印を付与し、フックは両方の印の組合せで最上位かどうかを判定する。
常駐実行の印そのものを委譲先で無効化する案は、同じ印を読む観測記録と入力待ちベルまで停止させるため採用しない。
最上位だけが受け取るフックイベントで`session_id`を記録する案も、セッションをまたぐ永続状態と記録喪失時の縮退設計を要するため採用しない。

入力待ち判定は、ホストがStop入力で渡すバックグラウンドタスクの申告を、Stop入力が申告するバックグラウンドタスクの種別に限って判定の基準とする。
申告しない種別の未完了はtranscriptから復元した記録を独立した根拠とする。
両者を対等な根拠として合成する案は、復元側に残る解決できない起動記録が申告を恒久的に上書きし、入力待ち判定を必要とする終了保証を働かなくするため採用しない。
`background_tasks`の権威性を全種別へ適用したまま、`agents_server`側で背景移行を申告させる案も採用しない。
ホストの入力形式を変えられないためである。

`background_tasks.py`の`is_pending_async_work`は`CronCreate`を非同期待機系として扱い、`CronCreate`後のStopでも機械的な完了通知を待つ動作を維持する。
`ScheduleWakeup`の判定は`/loop`専用の既存契約として残し、Cronの作成・再利用・確認・削除をフックの永続状態へ移さない。
最上位Stopはpayloadの`transcript_path`から生JSONLを読み、同じstemの`subagents`配下にある固定名
`agent-*.jsonl`をmetadataの親子関係で直接の子に限定して読む。
直接の子の記録にあるAgent起動を孫起動として起動集合へ加え、
最上位生transcriptの`queue-operation`で`operation`が`enqueue`または`remove`の完了通知をtool-use-idまたはtask-idで相殺する。
サブエージェント記録の不在・破損・無関係な親子関係は最上位transcriptの既存判定を維持し、Hookが追加の永続状態を作成しない。

最上位生transcriptの`queue-operation`を読む処理は、LLM実行主体が完了通知を受領・中継する委譲契約とは別のHook観測面である。
LLMへの配送成功をHookの完了判定へ変換する案、SubagentStopへ子孫待機のblockを復活させる案およびCodexの未確定transcript構造へ同じ探索を広げる案は採用しない。
