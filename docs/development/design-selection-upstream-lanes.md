# 上流投入とレーン工程の設計記録

[設計記録の索引](design.md)と[担当の責務と工程間の知識境界の設計記録](design-workflow-boundaries.md)から参照する主題別の記録である。

対象リポジトリの変更では要求を満たせず上流リポジトリの改訂を要する要求を含む項目は、メインが上流投入を要する項目として全投入先、投入条件、上流要求を選定結果へ記録する。
メインはレーンの起動前に、元項目と投入先の組へ展開した固定入力をWI投入担当へ渡す。
起動単位は`add-wi.parent.md`「起動方法」に従い、同じ元項目の組を同じ担当へ渡す。
上流投入はWI投入の条件判定付きの派生であり、委譲先は各投入先の現状が条件を満たすか確かめ、条件が成立する組だけに通常AWIの書式で自己完結した本文を投入する。
同じ機構を2つの`<役割名>.subagent.md`へ分けると、投入前調査と本文起草の契約が二重になり、片方だけの改訂が検収の食い違いを生む。
上流の改訂だけで成立する項目はレーンを起こさず、投入済みの全ファイル名を元項目の`depends_on`へ加えて`inbox`へ戻す。
全投入先で条件が成立しない項目は依存を追加せず、条件不成立の確認結果を外部操作の結果として終了する。
対象リポジトリで実施できる要求を併せ持つ項目は分類を分けず通常のレーンへ渡す。
投入済みの組があるレーンはffマージ後に計画保存と統合状態を検収し、所有資源を保持して固定の完了報告を返し、メインが元項目を`adopt`せず`inbox`へ戻す。
全投入先で条件が成立しないレーンは通常の終了を適用する。
上流投入をレーンの起動前へ置くのは、レーンの完了報告が固定文字列であり、上流の識別子と要求本文を載せる復路を持たないためである。
1つの項目を要求ごとに異なる保存状態へ分けないのは、キュー項目の保存状態がファイル単位で1つに定まるためである。
投入先と要求をメインが固定して渡すのは、投入先を自ら決める不可逆操作を委譲先が実行しないためである。
元項目の`depends_on`更新と`inbox`への復帰はメインが保持する。
公開工程ではメインが1件の公開担当へ版数・生成物同期、push、CI、必要なCI修正、AWIごとのプロジェクト固有の公開後の操作および延期`adopt`を委譲し、受領した固定形式の値を公開契約の終了状態と比較する。
自動コードレビュー監査は選定工程で起動し、完了報告と終了とあわせてメインが保持する。
全体レビューは追加しない。
1つのレーンは同じ担当threadが計画から実装、検収と統合まで責任を保持し、担当範囲の一部の書込もQCDで比べて自身の委譲先へ分ける。
同じ専用worktreeへ並列の担当を置く場合は、呼び出し元が生成物などを含む書込先を交わらない集合へ確定し、作業ツリー全体と共有状態へ作用する操作は全担当の終了後に直列に行う。
この条件は先行担当の終了を確かめない後続起動や、書込先を調停していない並走を防ぐ。
主体の数だけで同時書込を禁じる案は、同じファイルへの競合とGit hook・整形による全体への作用を区別せず、分けて実施できる作業の直列化を生むため採らない。
通常レーンは初回集合を1つの計画ファイルへまとめ、処理中に追加したAWIは凍結済み計画と分けて保持する。
単一の計画では行数の警告（1200行）を避けられない見込みの初回だけは、実装着手前に分析の単位と依存順で複数の自己完結した計画へ分ける。
作成単位をレーンに固定したまま読込負担の判定を計画ファイル単位で行うと、大きなレーンでは規定どおりの計画が警告の不在という進行条件を満たせなくなるためである。
分けた計画は同じレーン・worktree・書込所有者のまま、集合全体を`plan-check`へ1回渡して確かめ、通知・受領・計画別の実行レビュー・統合と保存は、既存の追加計画と同じく計画の順序付き集合として扱う。
閾値を上げる案は読込負担を残し、レーンを細かく分ける案は少数の大きなAWIに対応できないため採らない。
凍結済み計画の事後分割とレーンの再配分は対象外とする。
レーンの専用worktreeは1つとし、計画の順序付き集合と各AWI、保存状態を引き継ぎ記録で累積する。
メインは`depends_on`と同じ再開計画を、段階によらず分割不能な成分とする。
レーン工程で書き込むファイルと節（`書込対象`）の重なりは同じ段階での同時書込を避ける条件とし、`公開工程の書込対象`は含めない。
同じ段階では、重なる項目と、変更する節または定義を一意に分離できない同一ファイルの項目を同じ成分へ置く。
一意に分離できた同一ファイルは同じ段階で並行化できる。
書込の重なりで推移的に連結した集合は、重なる項目を先行レーンの統合後の段階へ回す段階案と単一段階案を比べて配分する（比較の手順は[「レーン配分の上限と単独稼働の扱い」](design-lane-allocation.md#レーン配分の上限と単独稼働の扱い)）。
所要時間とレーン数はこれらの制約を満たす候補の内側で比較し、レーンごとの実装時間と統合時間を`選定結果の出力先ファイル`へ残す。
同じ段階で重なりを許し、競合解消時間を費用へ織り込む案は、予測済みの書込競合を許し、誤統合と再検証を後段へ残すため採用しない。
競合時は同じレーン担当が関係計画の`概要`、`実施内容`、`要件・外部仕様`と`変更履歴`を比較して最小限に解消し、影響する計画の実行レビューを最終HEADで再び収束させてからffマージを要求する。
独立した履歴や環境が目的上必要な場合と、書込先を事前に確定できない場合は、別branch・別worktreeの一時的な内部群へ分ける。
AWIごとのcommitは全担当の終了後に呼び出し元が直列に作れるため、担当ごとにcommitを割り当てたことは分離の理由にしない（2026年11月3日のユーザー指摘による。書込範囲が重ならなければ同じworktreeで担当だけを分け、commitは最後にまとめればよいという趣旨）。
単一レーン処理（`agent-toolkit:process-wi`の`references/single-lane.md`）では指定worktreeを維持し、同じworktreeで安全に並列化できない操作は直列化する。
レーンbranchの確定済みcommitを起点とし、ファイル所有表、各worktreeの書込担当、レーン担当による群別検収、直列統合、競合解消と回収を保つ。
Gitのindexと履歴、整形の状態を群ごとに分離するため、同じbranchへのamendと全体操作の競合を避けられる。
群の粒度と同時担当数は固定値を置かず、作業量・難しさ・独立性・利用可能枠と資源の競合から`agent-toolkit:delegation`の`agent-toolkit:delegation/references/routing-units.md`「委譲単位の確定」の比較で選ぶ。
大規模な文言変更では、有限候補の代表試行と文字単位差分の全件レビューを先に行い、候補置換後のcommitから残る文単位修正を分担する。
2026年10月1日に、300件を超えるファイルの文言是正を4群へ分けただけで群内の分業も一括置換との比較もせずに進めた事象を契機に、以前の「最大4群」の目安を判断へ置き換えた。
内部群の使い分けは文言変更に限らず、書込先と全体操作の必要性で同じworktreeの分担と比べる。
単純作業は多数へ分けて直列の長さを抑え、規範の読み込みが重い難しい作業は読み込みの重複と統合費用を含めて比べる。
分担の判断は委譲の規範へ集約し、計画起草と内部群の起動はそれを参照する。
