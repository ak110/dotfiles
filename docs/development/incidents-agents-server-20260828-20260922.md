# 障害・欠陥の記録: agents_serverと委譲基盤の不全（2026年8月28日〜2026年9月22日）

[agents_serverと委譲基盤の不全](incidents-agents-server.md#agents_serverと委譲基盤の不全)の事例を発生時期別に収録する。

- 2026年8月28日: 複数レーンの計画レビュー中に、先に完了した計画担当へ指摘を返す時点で30分の結果保持期限を超え、`send_message`が`session retention expired`を返して同一会話を再開できなかった。
  直接原因: Codexの`thread/resume`とClaude Agent SDKの`resume`は保持中sessionの内部replyだけから利用でき、期限切れ後に呼び出し元の正確な識別子から到達する公開入力がなかった。
  背景原因: 初期移行時に結果本体とClaude接続の有限時間回収だけを検証し、長時間オーケストレーションが保持期限後も同じ担当へ指摘を返す利用シナリオを契約テストへ含めなかった。
  対策: 結果本文の回収後も`engine`・`cwd`・`model`・`effort`を最小状態として保持し、同じ`send_message`が両engineの保存済み会話を暗黙に再開する。
  両engineの期限切れ再開と正確な識別子配送を近接テストで固定する

- 2026年8月28日: Codexホスト経由の`agents_server`起動が`Codex App Server stdout closed`だけを返し、
  子プロセスの終了コードと標準エラーを呼出元から確認できなかった。
  直接原因: 標準エラーをMCPプロセスの標準エラーへ転送するだけで保持せず、標準出力終了時の例外を固定文にしていた。
  対策: 子プロセスの終了コードと標準エラー末尾を有界に保持し、標準出力終了時の例外とMCPログへ含める

- 2026年8月30日: `engine=claude`の委譲先への`send_message`が応答を返さず、その後の`wait`が`session retention expired`を返して委譲工程が停止した。
  直接原因: 継続要求の応答futureを解決する主体がsession所有タスクの正常終了時だけであり、保持期限の到達、message streamの例外、タスクの取り消しで所有タスクが終了する場面に未解決futureを解決する処理が無かった。
  背景原因: 同一実装のCodex側は接続終了時に未解決の要求を解決していたが、Claude側の継続要求キューは所有タスクが生存している間だけ要求が届く前提で設計され、契約テストも所有タスクの生存中と終了後の定常状態だけを固定していた。
  対策: 要求の受理と応答の解決を1つの継続要求チャネルへ集約し、所有タスクのいずれの終了条件でも受理済みの要求を解決する。
  所有タスクが終了したsessionへの継続送信は保持期限の経過と同じ再開処理へ回し、保持中の直前結果のうち`wait`または`kill`で回収されていないものを`previous_result`として返す

- 2026年8月: `agents_server` MCPの初回engine選択が、MCP起動後に置換されたプラグイン配置のローカルbackendを解決できず失敗した。
  直接原因: backend class importをengine選択時まで遅延し、MCP初期化時にローカルmoduleの存在を確定していなかった。
  対策: 共有状態moduleで循環importを解消し、Codex・Claude backend classをMCP初期化時に読み込む回帰テストを追加する

- 2026年8月: `agents_server`のPEP 723環境ウォームアップが成功しても、Claude Agent SDKのimport不足をClaude turn開始まで検出できなかった。
  直接原因: `--help`だけを実行し、lazyなSDK importとClaudeAgentOptions構築へ到達していなかった。
  対策: `--check-dependencies`でoptions構築まで検証し、Claude CodeとCodexのagents_serverウォームアップへ適用する

- 2026年9月1日: plugin cacheの更新後、長寿命の`agents_server`が保持するCodex App Serverが`thread/start`へ同じJSON-RPC errorを返し続けた。
  error messageは`failed to load configuration: No such file or directory`であり、委譲先を起動できなかった。
  直接原因: 子App Serverの作業ディレクトリをMCPサーバー自身から継承していた。
  Codexホストではpluginの版数付きcacheディレクトリが作業ディレクトリになる。
  plugin更新で旧版のディレクトリが消え、生存したままの子プロセスが設定の読込に失敗した。
  背景原因: 子プロセスの起動条件のうち、親の実行環境によって値が変わり実行中に無効化され得る値を、起動時に確定する対象へ含めていなかった。
  対策: 子App Serverの作業ディレクトリへ実行主体のホームディレクトリを明示指定する。
  親の作業ディレクトリを削除した状態で`thread/start`が成功することを近接テストで固定する

- 2026年9月2日: Codexの利用枠が上限に達した状態で、`agents_server`の`start`が返したsessionが直後に失敗し、委譲工程が3件停止した。
  `start`は`status: running`を返し、その約4秒後の`wait`が`codexErrorInfo: usageLimitExceeded`を伴う`failed`を返した。
  直接原因: サーバーが可用性の失敗を判定せず、次候補への切替を`exclude_session_id`付きの再起動という呼び出し側の操作だけに委ねていた。
  背景原因: 工程別モデル設定が候補列を持つ一方で、候補を進める契機の判定を配布物の外側へ置いていた。
  対策: `start`・`start_explore`が起動直後の終了を上限付きで確認し、engineの可用性で終了した候補を除外して次候補で起動する。
  全候補が起動不能な場合だけ失敗を返す

- 2026年9月4日: 終了時の結果の保持期限を過ぎたagents_server sessionに対して`wait`と`kill`のいずれも失敗し、ターン終了ごとの未観測警告を解消できなかった。
  直接原因: 保持期限切れのsessionへの`kill`が例外を送出し、MCPツールの失敗ではPostToolUseが発火しないため観測状態を更新できなかった。
  対策: 保持期限切れのsessionへの`kill`は中断対象が無いことを示す応答を返す。
  その応答を受けたら観測状態を解消する

- 2026年9月6日: 委譲先が`agents_server`で起動した孫sessionの終了を観測しないまま呼び出し元の`wait`が終了時の結果を返し、孫が書き込む作業ツリーへ次の書込主体が接続した。
  直接原因: `SessionState`がターン中に起動されたsessionの識別子を保持せず、別プロセスの終了状態を照会する共有記録も無かった。
  対策: 両backendがMCPツール結果から孫sessionを追跡し、プロセス間のsession登録簿で全ての終了を観測するまで結果を保留する。
  終了後は同じsessionへ一度だけ継続指示を配送し、保持期限まで未観測の識別子は既存の`error`項目へ示す

- 2026年9月7日: 所有session識別子だけを持ち、ホスト側の識別子を解決できない実行環境が、ルートの状態ファイル名を選ぶ処理を残していた。
  直接原因: Codex CLIがMCPサーバープロセスへ所有session識別子とthread識別子を渡す前提を置き、識別できない場合の戻り値を定めていなかった。
  影響: ルートの状態ファイルを活性化すると、同じ状態ディレクトリにある別の書込主体の記録を削除できる状態だった。
  対策: 所有session識別子があっても書込主体を識別できない場合は状態ファイルを書かない。
  Codex委譲先自身のシェルとCodex CLIが起動するMCPサーバープロセスの環境変数を個別に再検証する

- 2026年9月8日: `agents_server`の`wait`が実行ホストの上限を入力に持たず、`timeout`を省略した呼び出しが常に失敗するホストがあった。
  直接原因: `get_wait_timeout`が本プロセスを起動したホストを入力に持たず、保持期間`1h`に対応する1740秒を返した。
  これはCodexが1回のツール呼び出しへ課す300秒を超える。
  影響: 待機規範がCodexホストで使う待機手段と定めた`atk agents-wait`も、Codexホストでは状態ディレクトリを解決できず終了コード4で終わるため、待機の代替が無かった。
  対策: 環境変数`CLAUDECODE`の有無でホストを判定し、Claude Codeを確認できない場合は保持期間によらず270秒を返す。
  `atk agents-wait`をCodexホストの待機手段と定める条項を撤去し、上限で失敗した`wait`を`list`での状態確認と再発行で継続する手順へ差し替える

- 2026年9月13日: Windowsから`agents_server`の`start`へ正規のタスク文書を渡しても、起動文の検証で拒否された。
  直接原因: 起動処理で解決済みのタスク文書を表示用プロンプトへ直列化した後、POSIX絶対パスかつ空白なしを前提とする正規表現で再抽出していた。
  背景原因: パスを構造化値のまま検証へ渡さず、表示書式を検証入力へ逆変換する知識境界と、POSIXパスだけを使うテストを採用していた。
  対策: 解決済みPathと名前付き追加入力を検証へ直接渡し、Windowsおよび空白を含むpluginパスを公開`start`処理のテストへ追加する

- 2026年9月13日: 必須入力宣言が存在しない委譲またはタスク文書の読取に失敗した委譲が、検証不能の警告を理由に起動前に拒否された。
  直接原因: 必須入力検証が返す警告文字列を、呼び出し側が実際の必須値欠落と同じ`ValueError`へ変換していた。
  背景原因: 検証不能と検証済み不適合を同じ文字列返却へ畳み込み、marker欠落の拒否を正しい契約としてテストへ固定していた。
  対策: 検証不能は警告して起動を継続し、読めた宣言に対する必須値欠落だけを拒否する。
  marker欠落、読取不能および値欠落を別の公開された呼び出し手段のテストで固定する

- 2026年9月13日: plugin更新後のagents_serverウォームアップが失敗してもupdate-dotfilesが成功し、初回MCP起動の依存準備と失敗診断を確定できなかった。
  直接原因: 共通ウォームアップ関数が起動不能、timeoutおよび非0終了をすべてログだけへ記録して返し、MCPプロセスも標準エラー以外の永続ログを持たなかった。
  背景原因: 高速化だけを目的とするhookウォームアップのbest-effort契約をagents_serverへ共通適用し、プロセス終了後に初回起動を診断する利用シナリオをテストへ含めなかった。
  対策: agents_serverのウォームアップだけ失敗を更新段階へ伝播し、全結果へ終了コードと所要時間を記録する。
  MCP起動前に状態ディレクトリのローテーションログを初期化し、親MCPとCodex子プロセスのライフサイクルを永続記録する

- 2026年9月13日: 稼働中sessionの状態投影が消失したとき、`atk agents wait`が終了コード7の`expired`を返した。
  直接原因: 待機開始時の空の投影と、待機中に全sessionが投影から消えた状態を、権威あるsession登録簿の期限切れと同一視する2分岐があった。
  背景原因: statusline用の状態投影とMCP serverが所有するsession登録簿の責務を待機CLIで混同し、投影不在を期限切れとするテストを固定していた。
  対策: 結果または通知が無い間は投影の有無によらず`running`を返し、開始時に取得したsession識別子を投影消失後も保持する。
  真の`expired`判定はMCP serverへ限定する

- 2026年9月15日: `agents_server`の`start`と`start_custom`で起動したClaudeの委譲先が、全ての再試行を含めて初期化タイムアウトで失敗し、専用タスク文書を使う委譲が1件も成立しなかった。
  直接原因: 委譲先を`bypassPermissions`で起動していた。
  Claude Codeのセッション間メッセージの受信方針は、受信側がbypass系であり送信側が権限モードを申告していない場合に、送られたメッセージを保留する。
  委譲元は起動直後にメッセージを送るため、委譲先は保留のまま`init`を送出しなかった。
  背景原因: 無人で自動応答する委譲先を、対人セッションと同じ権限モードで、委譲元と対等なピアとして起動していた。
  同じ構造から、初期化に失敗した委譲先が入れ子起動したMCPサーバープロセスの残留も生じていた。
  影響: 実行レビュー、レーン担当および公開担当を含む通常委譲が成立せず、失敗を観測したセッションの工程をメインが引き取って実施した。
  呼び出し元が受け取る診断は受信メッセージの型別件数だけを持ち、どのメッセージで停止したかを区別できなかった。
  対策: 起動区分によらずbypass系以外の権限モードで起動する。
  委譲先CLI自身の診断を起動ごとに状態ディレクトリ配下へ保存し、保持世代を超えた記録を自動削除する。
  初期化タイムアウトの診断へ、受信メッセージを識別できる要約と委譲先プロセスの子プロセス一覧を含める

- 2026年9月15日: 委譲先の起動が失敗した後に発行した`atk agents wait`が、待機対象を1件も持たないままtimeoutを省略した場合の待機上限である3600秒に達するまで終了しなかった。
  直接原因: 待機ループが、対象識別子の集合が空である状態を終了条件として扱わず、経過時間の上限だけを持っていた。
  対象は待機中にも追加されるため空を即時の終了条件にできないが、空が継続した場合の上限を置いていなかった。
  背景原因: 初期化の上限と試行回数の積が、ホストがMCPツール呼び出しを背景タスクへ移す120秒を超えていた。
  このため`start`の失敗が呼び出し元へ届く前に`start`の呼び出しが背景へ移り、呼び出し元が対象を持たない待機へ進んだ。
  いずれの上限も、待機側が観測できる状態と呼び出し側が課す閾値へ対応づけずに単独の定数として決めていた。
  対策: 待機対象が0件である状態の継続へ独立した上限を置き、その上限に達した実行は理由を標準エラーへ書いて非0で終える。
  初期化の上限は、試行回数との積および直列に続く可用性待機との和がホストの背景移行閾値を下回る値へ下げる。
  上限値と導出関係を状態定義の1箇所へ集約し、両者の関係を定数置換なしで判定するテストで固定する

- 2026年9月15日: Claude CodeのAgentツールで起動した委譲先が`Agent terminated early due to an API error`で早期終了した。
  Anthropic Messages APIが`messages.205: system content must contain at least one block`を伴う400を返していた。
  直接原因: Claude Code CLIは、`type`が`text`のブロックと`type`が`tool_addition`のブロックを並べたcontent配列を、`role`が`system`のメッセージとして送出する。
  送出の条件はベータ`mid-conversation-system-2026-04-07`とベータ`mid-conversation-tool-changes-2026-07-01`の双方が有効であることとする。
  中継した外部エンドポイントは両ベータを解釈せず、有効なブロックを1件も認識しない状態でメッセージを拒否した。
  背景原因: 同CLIは両ベータ由来の400を分類してベータを外し再送するフォールバックを持つが、分類器は本文に`tool_addition`の語を含む400だけを対象とする。
  観測されたエラー本文はその語を含まないため分類されず、フォールバックが発動しないままAgentが終了した。
  影響: この中継環境を使うClaude CodeのAgent呼び出しが400で失敗した。
  `agents_server`が起動する委譲先の処理では観測していない。
  対策: 本リポジトリ側の対処は本記録に留める。
  同梱CLI 2.1.259（`claude_agent_sdk` 0.2.152）の実物を確認したところ、`ClaudeAgentOptions`には両ベータを個別に無効化する入力が無かった。
  同CLIが読む環境変数のうち両ベータへ作用するのは、全実験ベータを無効化する`CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`だけである。
  この変数を配布設定へ加える案は、他の実験ベータもまとめて無効化し、特定の中継環境に固有の事象に対して全実行環境の機能を恒常的に縮小するため採らない。
  防御は400を記録した中継側に委ねる。
  中継側が受信リクエストをsanitizeし、`role`が`system`のcontentから400の原因となったブロックを除く。
  対応の実装は中継側リポジトリのキュー項目が扱う。
  本リポジトリ側は上流のClaude Code CLIが観測されたエラー本文を分類対象へ加えるまで待つ。
  再検証は問題の中継環境の受信エラー記録に`system content must contain at least one block`が現れないことの確認で行う

- 2026年9月15日: プラグインの更新でhookの定義が変わった後、`agents_server`が開始するcodexの委譲先が起動しなかった。
  直接原因: codexは承認済みの記録が無効になったhookの実行前に承認を求めるが、委譲先は対話UIを持たず承認要求へ応答する主体が存在しなかった。
  対策: `thread/start`と`thread/resume`のリクエストの`config`へ`bypass_hook_trust`を真値として渡す。
  同名のコマンドラインオプションと`-c`による設定上書きは`codex app-server`が受理しないため用いない

- 2026年9月22日: Codexから起動したMCPプロセスへownerとhostの識別子が届かず、起動したsessionがCLIの一覧と待機から観測できなかった。
  直接原因: 状態writerを無効化し、CLI側は補完のため全ルートを走査していた。
  対策: Codexから起動したMCPプロセスごとに衝突しないルートを生成し、公開応答と確認済みaliasで同じ会話へ接続する。
  CLIの全ルート走査は撤去する
