# 障害・欠陥の記録: 誤判定と検証不足（2026年7月〜2026年8月29日）

[誤判定と検証不足](incidents-judgment.md#誤判定と検証不足)の事例を発生時期別に収録する。

- 2026年7月: 完了報告のコミットSHAが1文字誤っており、存在しないSHAへのCI通過待ちを約10分継続した。
  直接原因: 報告値を確認せず後続コマンドへ渡した。
  対策: 識別子は実行結果の値をそのまま使い、短縮形からの復元・記憶で組み立てない

- 2026年7月: Python 3.13/3.14で合法な構文（`except (A, B):`・PEP 758）を旧構文と誤判定した重大誤指摘が複数回発生。
  直接原因: レビュー担当が対象言語バージョンの仕様を確認せず学習知識だけを根拠に言い切った。
  対策: 言語バージョン確認とレビュー指摘採用前の一次資料での確認を義務化

- 2026年8月27日: review-sessionで、未完了作業へのユーザー介入を観測したにもかかわらず、メインが長時間待機後に既存規範・重複・過剰設計を先に評価し、「提案無し」で終了した。
  直接原因: 原因と既存対策の有効性を確定する前に抑止判定を行った。
  背景原因: （混入要因）2026年8月27日「refactor(session-review): 問題列挙と判断を分離する」、`75a3efa4`で原因分析の責務をadvisorからメインへ移した際、介入対応と被覆の完了条件を移さなかった。
  （動機的要因）advisorを問題列挙に限定し、判断の重複と実行時間を減らすことを優先した。
  （見逃し原因）「提案無し」テストがユーザー入力と証拠位置だけを確認し、4原因区分、三層処置、抑止判定の順序と根本原因単位の被覆を確認しなかった。
  （根本原因）判断責務の移管時に実害の是正を抑止判定より先に完了する不変条件を移さず、既存規範の存在を有効性の根拠へ反転できる状態を残した。
  対策: 原因分析・類似見直し・三層処置・根本原因単位の被覆を抑止判定より先に確定し、契約テストで4原因区分、三層処置、部分被覆、全被覆と最終報告の根拠を検証する。
  advisorの問題列挙専任契約は維持する

- 2026年8月28日: review-sessionのメインがadvisorの確認済みユーザー入力と問題locatorを構造検収するため、オプションを付けない、本文を含む証拠抽出を再実行し、イベント数の多いtranscriptで出力上限による欠落を発生させた。
  直接原因: 位置情報だけで成立する構造検収に、問題発見用の本文を含む、オプションを付けない出力を共用した。
  背景原因: （混入要因）advisorとメインの責務分離時に、同じ抽出結果を再利用すれば整合すると判断し、消費主体ごとの必要フィールドを分けなかった。
  （動機的要因）新しい抽出機構と状態を増やさず、既存の出力とlocator契約を再利用することを優先した。
  （見逃し原因）契約テストがイベント位置の安定性と被覆訂正を検証する一方、メイン検収の出力フィールドと問題locatorの出力予算を検証しなかった。
  （根本原因）問題発見用の本文と構造検収用の位置情報を同じ照会契約へ結合し、消費主体が必要としない本文を渡さない不変条件を設計・テストへ持たなかった。
  対策: オプションなしの抽出と同じ順序の位置情報だけを返す索引照会へメイン検収を切り替え、問題locatorからオプションなしの照会を除外し、出力フィールド・順序・照会回数・オプションなしの出力の後方互換性を契約テストで固定する

- 2026年8月29日: 複数の`planning`項目を1件の計画型AWIへ統合する手順について、既存の`convert-to-plan`が同じ状態遷移を実装済みであると判断し、文書同期だけの改善提案を作成した。
  実際の`convert_entries_to_plan`は`inbox`と`processing`だけを対象とし、`planning`の最古項目への統合、本文差替え、残項目除去と`inbox`移動を実装していなかった。
  対象WIが実装導入として示したcommitも文書だけの変更であった。
  直接原因: 公開コマンド名と複数入力対応だけを比較し、状態別の入力解決、保存結果と失敗復旧を実装本体から復元しなかった。
  背景原因: （混入要因）CLIの変更履歴をファイル差分で確認せず、関連項目に記録されたcommitを実装導入の根拠として採用した。
  （動機的要因）既存CLIを利用する文書同期だけで変更を完了できるという前提を、状態遷移を実物で確かめるより先に固定した。
  （見逃し原因）`inbox`・`processing`の一括変換テストと旧`planning`編集テストは存在した。
  ファイル名モードが指示するCLI、対象状態と最終保存集合を同じ契約として検証するテストがなかった。
  （根本原因）公開CLIを実行手順へ採用する際に、コマンド名と引数に加えて、対象状態、成功後の保存集合、失敗境界と導入履歴を実装・テスト・commit差分と比べる変更境界を設けていなかった。
  対策: `convert-to-plan`へ`planning`統合を原子的に実装し、旧`edit --plan-file`の既存保存集合と失敗境界を互換手順として保持する。
  ファイル名モードのスキル、ガイド、設計と方針を単一コマンドへ同期し、対象文書が可変長の`convert-to-plan`を指示して旧二段階手順を含まないことを契約テストで検証する
