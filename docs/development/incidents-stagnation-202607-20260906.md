# 障害・欠陥の記録: 停滞と空転（2026年7月〜2026年9月6日）

[停滞と空転](incidents-stagnation.md#停滞と空転)の事例を発生時期別に収録する。

- 2026年7〜8月: CI監視の待機ハングが複数回再発した。
  直接原因: ワークフローフィルタ不一致・登録遅延・短縮SHA不受理を考慮しない自作待機ループ。
  対策: CIの待機に専用スクリプト（`wait_ci.py`）を常に使う規定と識別子の完全形式使用

- 2026年8月24日: 孫の完了報告が呼び出し元へ配送されず、呼び出し元が成果物とtranscriptの最終更新時刻を実際に調べて終了を検出した。
  同時点でも`ListAgents`は孫を`running`と表示し、定時起動を装着していなかったため復旧の契機が無かった。
  直接原因: 完了通知の配送不着時に、独立した定時起動から停滞の検知と巻き取りへ進む手順が無かった。
  背景原因: （混入要因）`claude-code-runtime.md`が`ScheduleWakeup`と`CronCreate`を一般待機の候補として並記し、Cronの作成・再利用・resumeまたはcompaction後の確認・削除を一連の契約として定義していなかった。
  （動機的要因）完了通知を主手段とする待機設計に、通知不着時の復旧契機を定期再確認で保持する要求が組み込まれていなかった。
  （見逃し原因）主要agent定義と`_REQUIRED_TOOLS`に`CronCreate`、`CronList`および`CronDelete`がなく、`agent-toolkit/agent_toolkit/_hooks/stop_gate.py`と実際のCron待機を結ぶ検証も不足していた。
  （根本原因）完了通知、ホストの定期起動、Stopの継続判定とagent定義のtool許可を別々に管理し、待機対象と定期taskを同じ基準状態へ結び付けていなかった。
  対策: （是正）`atk wait-schedule`のcron式を変更せずに1件だけ`CronCreate`へ渡し、保持IDとtask IDを`CronList`で比較して再利用し、全対象の終了後に`CronDelete`で削除する契約をruntimeと待機文書へ置く。
  定期再確認時は更新時刻だけで終了を判定せず、記録末尾と実行識別子を比較して停滞の検知と巻き取りへ進む。
  （横展開）`CronCreate`をStopの非同期待機系と3つのagent定義の許可toolへ追加し、完了通知を標準手段として維持する実機相当のテストを追加する。
  （再発防止）`ScheduleWakeup`は`/loop`専用として一般待機から除外し、シェルの`sleep`や背景タイマーを追加せず、Cronの作成・再利用・確認・削除を1つの意味確認テストで検出する

- 2026年8月28日: process-loopのCodex起動文が開始後のready項目も同じセッションで処理するよう明示していた一方、
  `agent-toolkit:process-feedbacks`が起動時の対象集合を固定し、追加分を次回セッションへ送る逆の契約を持っていた。
  直接原因: `agent-toolkit:process-feedbacks`の処理集合変更時に呼出元のprocess-loop起動文と既存設計の連続処理条件を確認せず、
  単一処理回の集合固定をセッション全体の固定へ拡張した。
  対策: 各処理回の集合は固定したまま、明示的な連続処理では全レーンの後始末後にready一覧を再取得し、
  0件を確認した場合だけ既存の終了工程へ進む

- 2026年8月28日: `agent-toolkit:process-feedbacks`のpickerが`hold`項目を優先度の根拠に使い、ready項目の選定範囲を狭めた。
  直接原因: `hold`導入時に確定した「activeは表示用、processableだけが自動処理対象」という不変条件を、
  後発のpicker契約が参照せず、pickerへ渡す対象を`hold`を含むactive一覧として定義していた。
  対策: 各処理回はprocessable一覧のうちready項目だけを固定し、既存のplanning、editing、holdおよびblocked項目を
  候補、優先度、依存判断および固有指示の入力から除外する

- 2026年8月29日: `agent-toolkit:process-feedbacks`が5件を選定して計画作成へ着手した後も、選定済みの全件が`inbox`に残り、
  キュー上の`processing`が0件だった。
  直接原因: `pick-feedbacks.md`が対象集合の固定と出力検収までしか定めず、その直後の状態遷移を選定工程の完了条件へ接続していなかった。
  対策: picker出力の検収直後に、選定時点で`inbox`だった集合へ既存の一括`start-processing`を実行する。
  全件の`processing`配置を確認してから計画・worktree作成を含むレーン工程へ進む
  2026年9月のユーザー指示により、この状態を遷移させる主体はpickerへ移った。
  遷移が計画・worktree作成と実装担当の起動より前に完了する不変条件は維持する

- 2026年8月29日: 起動時に固定したready集合だけを処理するユーザー指示に対し、全レーン後のready再取得を現行契約として優先した。
  直接原因: 起動時の対象集合をユーザーが確定した外部可視要件として保持せず、後続のエージェント判断で変更できる内部実装詳細として扱った。
  対策: 2026年8月28日の対策として導入した全レーン後のready再取得を撤去し、起動時の固定集合の完了後は
  再取得せず終了工程へ進む契約へ、受付、選定、Codex起動文および設計をそろえる

- 2026年8月: 担当外だった`mise.lock`の変化が別セッションで解消された際と、別セッションの無関係なcommitで
  基準OIDが変化した際に、担当対象へ影響が無いにもかかわらず契約違反の可能性として監査し、
  ユーザー確認や再計画へ進んで工程を止めた。
  直接原因: 記録時点を示すOIDと担当外差分の不一致を、実質影響と区別せず停止条件として扱う規範しか無かった。
  対策: 参照情報としてのOIDと担当外差分の変化を停止条件から外し、担当対象・公開契約・書込所有権への
  実質影響で続行可否を判定する横断規範を置く。
  操作対象はrefを優先し、必要な記録には7文字以上の一意な短縮OIDを用いる契約を維持する

- 2026年8月: Codexの名前付き役割適用、実際の別主体への委譲と外側の待機を別のライフサイクルとして扱わず、差分・HEAD・無応答・経過時間を重ねて`running`中の委譲を停滞判定する事象が発生した。
  直接原因: 役割適用と実主体の境界、補助観測と終了statusの優先順位が待機契約へ分離されていなかった。
  対策: 名前付き定義の直接適用を外側委譲へ変換せず、Codexの`running`中は補助観測だけで中断しない契約をbaseと待機文書へ置くこと、加えて広範な未完了調査を独立単位へ分ける

- 2026年8月: 待機報告へ並行主体を含む作業ツリー全体の差分件数・HEADまたは別主体のartifact値を帰属なしに載せ、委譲先の進捗と解釈し得る事象が発生した。
  直接原因: 記録されていない（事象の記録時に直接原因を記していない）。
  対策: 書込対象と書込主体を報告へ結び付け、`atk watch`の全体値を単独の生存根拠にしない

- 2026年8月: 孫へ委譲した調査が完了しても、直接の委譲元へ成果が配送されず、祖先が受領した完了通知の中継も成立しない事例で同じ調査を再実行した。
  直接原因: 孫調査の起動文に成果ファイルの絶対パスと記載形式がなく、既存の記録ファイル直接読取は孫がファイルを書き込む契約を持たなかった。
  対策: 孫調査・レビューの起動前に管理対象一時領域内の成果ファイル絶対パスを確定し、専用タスク文書またはagent定義の完全な完了報告を同期的に確定してから受信者が終了する。
  直接の委譲元は完了通知の到着を成果本文の受領条件にせず、実行時に観測できる受信者の終了後にファイルを再読する。
  読み取り専用受信者へ所有プロセス終了証拠を要求せず、終了未観測・欠損・読取不能・不完全な成果は成功扱いしない。
  `needs_escalation`として一時領域を保持する

- 2026年8月: 10分周期の定時起動を装着したセッションで、1時間ごとの進捗報告が3時間以上発生せず、ユーザーの介入が2回発生した。
  直接原因: 定期promptが待機対象の基準状態だけを再確認し、経過時間で発火する定期報告の義務、確認用コマンドおよび判定閾値を含まなかった。
  対策: 定時起動を装着する際は、そのセッションで定期報告、cooldown解除、期限監視など、経過時間に応じて実行する義務を列挙する。
  確認用コマンドと判定閾値をpromptへ接続する。
  該当義務が無い場合は追加しない。
  固定周期の短縮と新しいschedulerは行わない

- 2026年8月: 遠隔ホストのGPU互換性検証を`nohup`で切り離して起動したため、前景のSSH呼び出しが即座に終了し、遠隔ジョブが終了コード1で完了しても完了通知が届かなかった。
  完了まで同じログを5回照会し、1回は前景の`sleep`を伴った。
  直接原因: 実行主体が応答可能な検証へ、実行主体自身が応答不能になる切替工程でだけ必要だった遠隔切り離しの起動形を流用した。
  対策: 遠隔側の`nohup`または`setsid`による切り離しは実行主体自身が応答不能になる工程だけに限定し、それ以外の長時間コマンドは`run_in_background=true`でSSH接続を保持するか、対象を限定した前景実行とする。
  固定周期の短縮は通知手段を回復せず、コマンド形の自動チェックは正当な切り離しも同じ形を取るため追加しない

- 2026年8月: セッション識別子の変更後に委譲先の再開を試み、`SendMessage`が`No transcript found for agent ID`で失敗した。
  直接原因: 旧セッション識別子配下の委譲先を再開可能と扱い、配送不能を新規起動へ切り替える条件に含めていなかった。
  対策: `No transcript found for agent ID`が返った場合は配送不能と判断し、再開を繰り返さず、検収済み状態を渡して新規起動する

- 2026年8月: 自律実行中の確認発行で回答受領まで105分停止した（セッション最大の停止要因）。
  直接原因: 確認への回答期限が無く、発行した確認が回答受領まで工程を止めた。
  対策: 質問の自動継続タイムアウトを配布し、期限内に回答が無い確認をUWIへ退避して続行する。
  期限を提供しない実行環境では応答を得られないと判断した時点を契機とする

- 2026年8月: 自律実行中に計画立案モードへ入り、承認待ちで工程が停止した。
  直接原因: 同モードの終了時承認が自律実行では応答を得られない。
  対策: 自律実行では計画ファイルを直接作成する（厳守規定化）

- 2026年8月: process-loopのプロセスが80個・RSS約2.33GBまで積み上がった。
  直接原因: 自己再起動の`os.execv`が`uv run`経由の親プロセスを置き換えられず1段ずつ増えた。
  対策: 再起動方式の構造修正

- 2026年8月: process-loopの子セッション正常終了後に、開始前更新と同じ`update-dotfiles --force`が同一反復で二重実行された。
  直接原因: 開始前更新を残したまま正常終了後の配布反映手順を追加していた。
  対策: 反復内は開始前更新1回に限定し、正常終了後の2回目を削除する

- 2026年9月1日: 実装レビュー収束後の計画最終化について、一方のレーンの実装担当が最終化まで実行し、他方のレーンの実装担当は職務定義との矛盾を理由に呼び出し元へ差し戻した。
  直接原因: `plan-executor.parent.md`が最終化の主体を呼び出し元と定める一方、`run-lanes.md`の記述がレーン側の工程として読めた。
  対策: 最終化の主体を計画ファイルを所有する呼び出し元へ一意化し、レーン側の文書には主体と時機を同じ内容で記述する

- 2026年9月1日: レビュー担当threadへの継続指示が`unknown session`で拒否され、再レビューの収束を確認できないままマージ、WIの採否確定および資源回収が停止した。
  直接原因: 規範が`unknown session`を継続不能の判定条件として定める一方、判定後に工程を進める手順を定めていなかった。
  対策: 継続不能と判定した主体が同じ`model_type`で新しいレビュー担当を起動し、レビュー指摘管理表、ラウンド番号ならびにレビュー対象HEADの7文字以上の一意な短縮OIDを引き継ぐ手順を置く

- 2026年9月1日: 人間由来の不採用範囲についてユーザーの確認を得られない場合のレーンの扱いを書こうとして、実装レビューが3ラウンド連続で同じ整合不成立を検出した。
  直接原因: `agent-toolkit:feedback-standards`が暫定`rejected`と`inbox`の`blocked`という2つの手段を並記し、採用済みの範囲と不採用の範囲が混在する項目でどちらを選ぶかを定めていなかった。
  対策: 採用済みの範囲の有無で終了を分ける。
  採用済みの範囲がある項目では、その部分を`adopt`で終了し、不採用の範囲だけを内容とする新しい項目へUWIを依存として付ける

- 2026年9月1日: `agent-toolkit:shell-exec`へ引数を指定して起動したが、fork先で引数が指示本文へ展開されず、コマンドを実行しない通常の完了報告が返った。
  直接原因: スキル本文がホストによる引数展開を前提とし、実行コマンドを特定できない場合に取る動作と識別可能な返却値を定めていなかった。
  対策: 実行コマンドを特定できない場合は推測せず、Bashも実行せず、固定の`引数未受領`結果だけを返す

- 2026年9月3日: ユーザーの再起動後に、背景実行した検証コマンドのタスクIDが実行環境に存在せず、終了状態も出力も回収できなかった。
  委譲先の完了条件を一部の判定を除いた範囲へ縮小して終了させた。
  直接原因: 背景ジョブの観測手段を実行識別子を入力とするものだけに限り、識別子から独立して残る出力ファイルの絶対パスを保持しなかった。
  対策: 背景ジョブの終了状態と出力を出力ファイルの絶対パスから取得する。
  待機を別の主体へ引き継ぐ場合は、その出力ファイルの絶対パスも渡す
