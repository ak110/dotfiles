# 方針・意向: レビューの運用

## レビューの運用

- 再レビューは前回指摘の修正、前回レビューHEADから今回HEADへの修正差分、変更した識別子・契約の直接影響範囲を対象とする。
  完成条件証拠は全行を新HEADで再判定する。
  round 3以上の未解決指摘では方式の維持・縮小・置換を比較し、置換直後だけ開始時点からの全差分をレビューする。
  既存のラウンド番号は修正方法の見直しに使い、回数による自動収束は行わない。
  再レビュー省略の条件と証拠再判定の優先は`agent-toolkit:/share/exec-review-responses-completion.md`「完了報告」が所有する（2026年10月18日、ユーザーが選択した改善案B）
- 人間向けMarkdownだけの低リスク段階では、実行レビュー担当が読者適合性も直接確認できる。
  可読性の是正要求と判断が難しい対象は、該当読者を別担当へ渡す。
  修正後も低リスクなら意味の変更を含む修正後の再レビューを省略できる。
  段階は`agent-doc-changes --review-risk`で全変更パスから求め、全ファイル・想定読者の判定と証拠を直接確認と起動識別子に区別して申告し、自動チェック、初回レビューと完成条件証拠の判定を保つ。
  review-sessionの基準は現状を維持する（2026年10月18日、ユーザーが選択した改善案C）
- 実行レビューの指摘管理表は、不在の初回に限り実行レビュー担当が最初の読取前に初期化し、全起動方法で同じ所有者を使う。
  親はパスの解決を担い、既存表と継続レビューの履歴を保持する。
  初回準備を消費側へ集約するのはエージェントの技術判断であり、呼出元の準備だけの往復を除くためである。
  2026年9月のユーザー指示による親の初期化から手段を改め、全起動方法で責務を統一する目的は保持する
- メインは担当の起動、同一threadの継続および工程遷移を自ら制御し、レビュー担当とレビューイーの完了報告を再検収しない。
  再検収はレビューイーとレビュー担当の責務を重複させ、同じ報告の再要求による停滞を招く（障害対策。incidents.md参照）
- 通常の実装モードでは、レビュー修正担当がレビュー表の指摘を採否判断し、採用した指摘IDと実装単位commitの7文字以上の一意な短縮OIDを対応付けて未pushの実装履歴へ統合する。
  履歴統合前に指摘の原文、対象への適用条件、実際の値と通常運用の再現手順を確認して採否を確定し、採用済みの指摘だけを修正対象へ含める。
  全指摘を不採用とした場合も根拠と応答を表へ記録し、履歴と作業ツリーを保ったまま通常の`対応完了`を返す。
  メインは未応答0件を確かめて同じレビュー担当へ再レビューを指示する。
  担当内で補える証拠修復・探索・再判定は同じ担当が返却前確認まで終え、担当で補えない判断・認可・入力・権限・外部状態の不足だけを続行できない理由として返す。
  現行の返却と受領は`agent-toolkit:/share/exec-subagent-history.md`「レビュー修正の履歴統合」と`exec-review.subagent.md`「出力」、`exec-review.parent.md`「レビュー修正」が定める。
  対応する実装単位へ統合できない修正は、新規commitへフォールバックせず最も新しい実装commitへ統合し、履歴を書き換えられない場合だけ続行できない理由を返す。
  レビュー修正専用commitは残さない（2026年10月7日のユーザー指示により、2026年8月30日に専用commitを残さないことを努力目標とした扱いを置き換えた）。
  統合先と続行できない理由を返す条件の詳細は`agent-toolkit:commit/references/history-rewrite-selection.md`「修正方法の選択」が定める。
  未pushかつ単一の実装担当が所有するworktreeの履歴書換え保護は、`agent-toolkit/skills/commit/references/history-rewrite.md`が定める汎用のプッシュ済み判定へ一本化する。
  remote広告refの直積証跡・replace ref・graft・shallow複製への追加防御は、対応する観測事象を得るまで導入しない（確認への回答に由来）。
  `rewrite_guard`は`phase`・`target_oids`・`published_decision`・各Gitコマンドの終了コード・エラー要約へ縮小し、同じ実装担当が再判定からamendまでを完結する。
  初回実装担当のrouteと実効`engine`、`model`および`effort`を保持し、レビュー修正の起動直前に解決した今回routeの実効3値と組み合わせて引継ぎを確定する。
  同じ担当へ同じタスクの未完了作業、指摘への対応または再レビューを返し、実効engine・modelが一致する場合は元の実装担当threadを継続する。
  effortだけが異なる場合は`atk agents effort up|down <子のsession_id>`で同じ会話のまま調整する。
  engine・modelが異なる場合を含むそれ以外は旧担当の終了確認後に今回routeで新しい実装担当を起動し、元の実装入力と原本の絶対パスを開始前に1回だけ渡す。
  詳細な操作手順（fixup・autosquash・amendの順序、phase名、判定コマンド）は`history-rewrite.md`が定め、本書へ転記しない
- 実行レビューの`review_contract`は実行レビュー担当を起動するメインが初回起動の直前に生成し、別の計画で認可されたcommitが累積差分へ加わった場合は再レビューの指示の直前にも再生成する。
  計画の既存節と開始時点の実体で内容が一意に定まる条項は出典付き参照で渡し、専用成果物または計画ファイルの固定H2を追加しない
- レビュー担当は、明示された範囲を独立要件と変更面へ分解し、到達可能な検収手段を持つ独立要件と直接影響範囲を被覆して、通常運用で実害が生じる契約違反だけを指摘する。
  自動チェックで検出できる事項をレビュー指摘へ転記せず、指摘に必要な根拠を取得できない場合は証拠不足の範囲と必要な検証を指摘として登録する。
  根拠を得られなかった範囲は検証済みとして扱わない（2026年9月、ユーザー指示）
- 再レビューでレビューイーが指摘の前提の不成立、適用条件の不一致または検収手段の到達不能を述べた場合、レビュー担当は指摘の前提を自ら裏付け直す。
  前提が成立しなければ指摘を取り下げ、同じ根本原因を別の観点から再提出しない。
  レビュー指摘管理表の応答値は`yes`／`no`の二値を維持し、`atk review-table`のスキーマとCLIを変更しない（2026年8月、ユーザー指示）
- 合否の判定に実機検証、完了条件、待機手順を用いる指摘は、対象成果物の許可ツール、禁止事項、入力前提および通常の状態遷移だけで指摘の合否を検証できるか先に判定する。
  到達不能と確定した要求は成果物の未達として扱わず、計画・規範の再設計へ返す。
  到達不能の結論には、探索した実行手順と各手順が成立しない観測の列挙を要する。
  この方針は実行レビューが到達不能な完了条件の未達を反復指摘して第8ラウンドまで継続した観測事象と、同じレビューで到達不能とした判定が実際の検証により覆された観測事象の双方に基づく（2026年8月、ユーザー指示）
- 計画ファイルの体裁を変える指摘と、記述間の矛盾を示す指摘も、種別を根拠に採否を確定しない。
  体裁には章構成、段落構成、表現選択、書き方および情報配置を含む。
  採否は根拠の確認と、何も変更しない案を含めた費用の比較で確定する。
  レビューの往復は、この費用比較によって抑える
  2026年9月15日のユーザー指示による。
  置き換えた方針は本節の「経緯（レビューの運用）」にある。
  現行の規定は`agent-basics:review-standards`の`agent-basics:review-standards/references/reviewee-correction.md`「修正要否の立証」にある
- コーディングエージェント向け文書または節の確定文面を全面差替えするレビュー修正では、運用手順、参照資料または直接操作を含む場合に既存の接続再列挙を適用する。
  意味・動作・契約を変えない機械的修正だけを対象外とする。
  この方針は確定文面の全面差替えで参照手順と絶対パスの受け渡しが欠落した観測事象に基づく（2026年8月、review-session）
- 実行レビューは計画に加えて、処理対象のWIの要求と完成条件も基準に含める。
  レビュー基準は`計画`・`CI記録`・`WI`の集合値とし、1件の実行レビュー担当が複数の基準を同時に受理する。
  事後承認型UWIの是正実装が実行レビューの対象になり得るため、基準の呼称はAWIに限定しない
  （2026年9月15日、ユーザー指示。`agent-toolkit:process-wi`がWI基準のレビューを実施していないという指摘に由来する）。
  現行の規定は`agent-toolkit/share/exec-review.parent.md`と`agent-toolkit/share/exec-review.subagent.md`にある
- commitとPR説明の帰属行（セッションURLを含む）はClaude Codeの既定のまま残し、投稿前レビューと振り返りはこれらを内部識別子の混入として扱わない。
  managed settingsの`attribution.sessionUrl`と`attribution.pr`も設定しない。
  2026年10月5日、セッションURLをcommitとPR説明から外す案に対して、ユーザーが設定を増やさず既定のままとすると回答したことに由来する。
  現行の規定は`agent-toolkit/share/external-write-review.subagent.md`「観点」の3項目めにある
