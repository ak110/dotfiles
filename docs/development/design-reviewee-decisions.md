# レビューイーの採否判断の設計記録

[設計記録の索引](design.md)と[検収根拠とレビュー担当間の知識境界の設計記録](design-review-evidence.md)から参照する主題別の記録である。

## レビュー担当とレビューイーの知識境界

### レビューイーの採否判断

レビュー担当とレビューイーで原文の解釈が分かれ、結果が変わる場合はユーザーだけが持つ値の確認へ戻す。
エージェント作成文の由来判定と誤記の訂正は、既存のレビュー担当とレビューイーが扱う。
エージェント間の往復だけでユーザー要求の意味を確定する案は、合意の主体を取り違えるため採用しない。
重大度で変えるのは未発見の類似欠陥の探索の深さであり、明示要求、既知の欠陥と現存成果物の是正範囲は保持する。
類似見直しへ含める対象は、根本原因が成立する利用条件が現物または明文化された方針で成立するものとする。
同じツールの使用やプロジェクト名だけで全エンドユーザー向け規範へ広げる案は、原因条件が成立しない対象も変更するため採用しない。

再レビューの省略条件は`agent-toolkit:/share/exec-review-responses-completion.md`「完了報告」へ集約する。
機械的修正、全指摘が詳細・実装だけで公開契約等を変えない修正、修正後も人間向けMarkdownだけの低リスク段階を保つ修正を同じ判断へ接続する。
根拠取得待ち・完成条件証拠の再判定・履歴欠落は省略条件より優先する。
省略時も変更範囲と公開可能性を検証し、最後に実際にレビューしたHEADの証拠を保持する。
親側は低リスクの再現と通常段階の詳細・実装条件の成立を確認する。
段階の公開操作は既存agent-doc-changesの任意オプションとし、従来のJSON出力を保つ。
全変更パスを使うため、review_contractでの限定、削除・改名の片側だけの判定による誤分類を防ぐ。

レビューイーは是正要求等を受領しても修正を前提とせず、通常運用での再現手順と影響を自ら実物で確かめて必要性を立証する。
採否は何も変更しない案を含め、残置した場合の実害と認知・保守費用、修正・検証・再レビュー費用および変更が増やす複雑性を同じライフサイクルで比較する。
実害がなく意味も変えない単独誤記のために独立した修正と再レビューを起こさず、同じ成果物に重大な修正があり再レビューする場合は、追加費用が小さい誤記も同時に是正する。
エンドユーザー向け文書の誤記または適用対象のスタイル違反は実害ありとして必ず是正し、単独誤記の修正省略および低頻度リスクの費用比較から除外する。
是正要求等は、観測した欠陥の修正と未発見の類似欠陥を探す追加作業を分ける。
探索の深さと終了は、2026年10月15日のユーザー指示による重大度別方針を持つ`agent-basics:bugfix`の`agent-basics:bugfix/references/root-cause-severity-impact.md`「QとC・Dの区別」に従う。
重大な問題の徹底した見直しを保ち、軽微な問題は探索範囲・限界と許容する残存リスクを明らかにして終えられる。
ユーザーが明示した対象集合と完成条件は保持する。
重大な実害、明示要件違反、公開契約違反とセキュリティ欠陥を費用だけを理由に残置しない。
修正前に過去の指摘・採否・合意・設計理由・障害対策と既存の成功手順を確認し、修正後は変更全体の自己点検と該当する自動チェックを完了して、そのまま公開できる状態だけを完了とする。

レビューイーは状態管理に関する指摘の操作単位対応を独立に検証する。

レビュー修正でエージェント向け文書または節の確定文面を全面差替えし、運用手順、参照資料、直接操作のいずれかを含む場合は、既存の接続再列挙を適用する。
差替え前後の読込手順、直接操作の対象・入力・取得手順、実行時に渡す絶対パスおよび契約テストを比べる。
意味・動作・契約を変えない機械的修正は対象外とする。

確定済み計画に基づく実行工程では、レビューイーの修正権限は計画が確定した目的、方針、採否、対象範囲および除外・保持の内側に限る。
既存実装もしくは規範との不整合を理由に確定内容を覆す修正は、レビューイーが確定せず委譲元へ返し、ユーザー接点を持つ主体がユーザー確認で解消する。
矛盾の判定は計画ファイル（メイン）が保持する由来と変更履歴を入力とし、新しい状態、表の列または工程を設けない。
実行レビュー担当は再レビューでも修正箇所を計画の確定内容と比べ、覆した箇所を指摘として登録する。

レビューイー側だけへ規定する案は、覆した修正が検出されず差し戻しも生じないため採用しない。
矛盾を自動チェックする案は、判定が本文の意味解釈を要し、判定対象を公開APIや実行結果から取得できないため採用しない。

著者側の判断指針のうち、成果物の消費主体に応じて配慮の水準を下げる規定には、レビュー担当側にも対応する判定条件を置く。
消費主体がユーザーとコーディングエージェントに限られるコマンドラインツールでは、観測済みの不具合、公開インターフェースの破壊およびデータの喪失を優先し、未観測の複合条件でだけ成立する競合を新しい機構で閉じる提案を指摘としない。
著者向け規定の併用だけで十分であるとする案は、著者向け規定が優先する対象を列挙しておらず、レビュー担当が指摘の可否を判定できないため採用しない。

### 担当外の既存不良の伝達

実行レビューの指摘へ採用する判断と、担当外の既存不良を是正主体へ伝える責務は分ける。
差分外という理由で不採用にしても、許された走査で現物から裏付けた不良は既存の走査記録へ保存し、
通常返却の`想定外事象:`に所在と要点を置く。
親はその記録から是正やAWI投入を判断する。
管理表の未解決件数は今回のレビュー契約に属する指摘だけを数え、再レビューでは既存の引き継ぎ記録から
報告事項と親が決めた処置を対応付ける。
成立しない候補と解消済み候補は根拠付き不採用理由に残す。
新しい報告欄や台帳を追加する案は同期を増やし、親が配下threadの記録を毎回再探索する案は
既に観測した不良を取り直すため採らない。
観測済みの不良だけを既存返却へ接続し、無関係な不良の探索は増やさない。
