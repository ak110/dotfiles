# 再開状態の棚卸しの設計記録

[設計記録の索引](design.md)から参照する、再開状態の棚卸しの記録である。

2026年11月の効率化の仕組みの棚卸しで、この節の状態と分岐を減らせるかを候補ごとに確かめた。
自動再開、自動リトライ、子と孫の自動復旧はユーザーが要求した働きであり、保つ。
除いたのは、現存する記録にも稼働中のサーバーにも対応する形式が残っていない2つの分岐である。

| 候補 | 採否 | 根拠 |
| --- | --- | --- |
| session登録簿の版数1の解決経路 | 除いた | 2026年11月11日の登録簿1,133件に版数1は0件だった。版数1の記録は他の未知の版と同じく読めない記録として扱う |
| 元turnの識別子を持たないCodexの記録を、全turnの終了から引き継ぐ分岐 | 除いた | 同じ登録簿のCodexの記録101件と解放済みの再開情報1,872個に`turn_id`の欠落は0件だった。`turn_id`の記録は2026年10月12日に導入され、稼働中のサーバーの最古の開始は同年10月28日である。`turn_id`を持たない所有者不在の記録は引き継がず、公開の`kill`・`stop`で扱う |
| 記録プロセスの識別を持たない記録を読む分岐 | 残した | 同じ登録簿に識別の無い記録が9件あり、現行の引き継ぎ公開もプロセスを載せないため、旧形式だけの分岐ではない |
| 統合前の旧名で記録された起動の追跡 | 残した | 旧名と現行名の対応表は、過去のセッション記録を読むhookと`review-session`のスクリプトも使う。自動再開の追跡だけから旧名を外すには現行名だけの定義を別に加える必要があり、定義が増える |
| 回収済みかどうかを持つ場所を1つにする | 見送った | 結果本文を返すかの最終判定は、共有結果ファイルの排他的な回収へ既に一本化されている。メモリー上の`result_delivered`は、結果ファイルを扱えない同期的な読み手と通常の登録公開の抑止が使い、除くと同期処理へファイル照会を持ち込む。回収済みの結果が再び返る障害が残る判定で再発しないことを、変更と同じ作業の中で示せなかった |
| 次のturnが無いことを確定する判定の入力（CLIのturnの状態と追跡集合の併用） | 変えない | 追跡集合だけでは2026年10月4日の誤った公開を防げず、turnの状態の報告だけではシェルの背景taskの実行中を判別できない |
| 配下が回収済みかを判定する根拠（待機の結果本文、保存先の行、背景へ移った場合の出力ファイル） | 変えない | 3つは結果が届く経路の違いに1つずつ対応する |
| 保留の理由の7種類 | 変えない | 7種類は設定する箇所と再開時の処理が全て異なる。保持するデータが同じ組（過負荷と利用上限、Claudeの接続とCodexのprovider）も、再試行の回数と失敗時の処理が別である。型名の分岐を持たない中断の終了確認も、設定条件と終了確認の所有者が他と異なる |

旧形式を読む分岐は、現存する記録と、その形式を書く版のサーバーが稼働していないことの両方を確かめてから除く。
自動再開が期待どおりに働かない場合の手段は、公開の`send_message`による同じsessionの継続と、保存した出力と引き継ぎ記録からの再開である。
起動時の候補切替は可用性確認中にengine可用性のため終了した場合と、資源を回収済みの起動前不成立（engine共通の依存判定）を型で返した場合だけ行い、他の起動例外では作成済み資源を残す可能性があるため例外を返す。
`stop`はbackend資源の解放を先に完了し、成功後に保持集合と状態ファイルを同期する。
登録簿のレコードを解放済みへ置き換えられるのは対象のsessionを所有するMCPサーバーだけとし、契機は`stop`による明示的な破棄と保持期限の経過に限る。
解放済みレコードは理由と時刻を保持する。
APIへ移行した会話は内部の再開情報を残し、Codexは同じprovider、Claudeは保持したenvファイルの絶対パスで復元する。
公開の解放判定は維持する。
レコードを削除せず解放済みへ置き換えるのは、照会した別プロセスが「所有側が正常に解放した」と「記録が無い」を区別できるようにするためである。
終了を観測した待機側は、自身が所有しないsessionのレコードを変更しない。
別プロセスの待機処理も同じレコードを観測するため、最初の観測者が変更すると残りの待機処理が終了を見失う。
上り通知は送信時刻と乱数を含む一意な最終名へ原子的に公開し、破損した通知と終了時の結果は待機側が可視の診断として扱う。
この自動再開の目的は、委譲先が子の完了を待つ場合に、委譲元が追加の継続要求なしに`<役割名>.subagent.md`所定の返却値を受け取れるようにすることである。
判定入力は`_agents_server/launch_prompts.py`の`AUTO_RESUME_NOTICE`とする。
自動再開を実際に行うbackendの`_agents_server/claude_options.py`と`_agents_server/codex_instructions.py`だけが起動時の指示へ加える。
Antigravity backendはイベントから子の起動結果を追跡集合へ登録しないため、この通知を加えず能力を約束しない。
代わりに`PUBLIC_WAIT_NOTICE`を全起動区分の開始・再開へ配送し、`atk agents wait`で同じ実行中に結果を回収させる。
2026年10月31日まで`_agents_server/antigravity.py`が`AUTO_RESUME_NOTICE`を配送しており、本節の記述と実装が食い違っていた。
追跡の接続を新設する案は、自動再開を実機で確かめられないまま保証の範囲を広げるため採らない。
Claude Code自身のバックグラウンドタスクの完了通知を消費する仕組みはClaude backendだけが持つ。
Codex backendは、孫sessionが残るturnの終了で追跡集合を消去して結果を即時公開していたため、待機表明の行が完了報告として配送された（2026年9月4日と2026年10月1日の観測）。
現在は孫sessionが残るturnの結果を`begin_auto_resume_wait`で保留し、MCP層の常駐監視が孫の終了後に同じsessionを再開する。
保留中の`kill`は中断要求を送らずに保留した結果を未観測の孫とともに確定し、子sessionの完了待ちの保留中への`send_message`は待機対象を保持して新しいturnを開始し、古い保留結果を`previous_result`として返さない。
再検証は両backendの委譲先から`agents_server`で孫sessionを起動し、孫の終了後に同じsessionが再開することを確認する。
