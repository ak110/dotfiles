# CLIの入力・結果・公開境界の設計記録

本書は[設計記録の索引](design.md)から主題別に分割した記録であり、機構の目的、構造の理由、知識境界と却下した代替案を保持する。
実行時に適用する規範は、各節が参照する現行のルールファイルとスキルが定める。

## 公開出力から導出できる項目の撤去

`atk agents list`と`atk agents show`、およびMCPの`list`は停滞の判定を表す`stalled`を返していた。
`stalled`の判定は同じ応答が返す`seconds_since_activity`と定数の閾値を比べるだけで再現できるため、公開出力から撤去した。
MCPの`list`は通常時の3項目の公開契約を保つため、`stalled`を`seconds_since_activity`へ置き換えた。Claudeの合成assistantメッセージ・`api_retry`とCodexの`willRetry: true`の`error`通知による再試行中も、一次情報から算出した`api_error`を返す。Claudeの`retry_at`は次の再試行予定時刻を、利用上限の`limit_type`・`resets_at`は種類と解除予定時刻を示し、list・show・waitで同じ射影を使う。

導出できる項目を公開出力へ置くと、同じ判定を定める箇所が生成側と呼び出し側の2つに分かれる。
閾値を変えた時点で両者が食い違い、どちらが現在の判定かを呼び出し元が確定できない。
公開出力は一次情報だけで構成し、判定は呼び出し元が行う。

公開項目は消費側の用途から選ぶ。CLI一覧は識別・活動・結果保留を、詳細は実行条件と本文を返す。通常の活動は`seconds_since_activity`にまとめ、絶対活動時刻はMCPの`show(verbose=True)`で調査する。結果のturn番号・確定時刻、通知の送信時刻、API失敗の集計回数・初回時刻、初期化の受信総数は内部保持と診断処理に残して通常応答へ通さない。内部辞書から用途別の項目集合へ射影することで、内部追加を公開契約の追加にしない。保存物の一括変換や新しい台帳は不要であり、旧保存物も回収時に同じ射影へ通す。

## dotfilesの`bin/atk`によるworktreeの選択

dotfilesの`bin/atk`と`bin/atk.cmd`は同一リポジトリ内からの通常起動でcwdのworktreeを使う。
専用worktreeの`plan-check`などを改修しても、PATHのコマンドが複製元の版を起動すると、改修版の欠陥が検証を通過する。

スクリプト自身の配置からdotfilesのrootを求め、cwdのGit共通ディレクトリと比較する。
同じ場合はcwdのworktreeにある`agent-toolkit/scripts/atk`へ委譲し、Git外と別リポジトリでは配置先の従来版を使う。
子へ引数、cwd、標準出力、標準エラーと終了コードを渡し、子の失敗で別版へ戻さない。
対象worktreeの`agent-toolkit/scripts/atk`が無い場合は、不足と復元の操作を返す。
Windowsは`call`による引数の再展開を避け、選択したバッチへ処理を移す。

配布物の`agent-toolkit/scripts/atk`は自身の配置から依存と実装を選び、常駐時の再起動を担う。
dotfilesの`bin/atk`はworktreeの選択だけを担い、配布物の実装、PATH登録、hookとMCPの起動先を保つ。
各工程へ絶対パスの選択を複製する案は、通常起動の取り違えを残すため採らない。
プラグイン側で実装を自動で切り替える案は、dotfilesを使わない環境の実装選択まで変えるため採らない。

プラグインのCLIは、Chat・Coworkがインストールを拒否する直下の`bin/`を避けて`scripts/`へ同梱する。
`scripts/launch.py`は標準ライブラリだけで配布rootと書き込み可能なデータ領域を解決し、準備済みの共有環境のPythonで対象を起動する。
依存の準備には`uv run --no-config --no-project --python 3.15 python <plugin root>/scripts/launch.py --prepare agent_toolkit/atk.py`を実行する。

`--prepare`の後ろのtargetは配布root内に存在する起動対象を確認する必須引数であり、共有環境の選択には影響しない。後述の組み合わせが未準備の場合に実行し、同じ組み合わせなら別の配布rootやworktreeでも準備済み環境を共有する。別worktreeを指定する場合の`<plugin root>`は、そのworktree内の`agent-toolkit`の絶対パスに置き換える。rootは`launch.py`の配置または`--project`から解決され、cwdの変更だけでは切り替わらない。

CLI・hook・MCPはこのスクリプトから起動し、登録済みスキルスクリプトはCLIと同じ環境内で実行する。
依存に作用するpyproject設定、`uv.lock`、選択したPythonの実行ファイルパス、OS・アーキテクチャの組み合わせから環境の保存先を分ける。
データ領域は`AGENT_TOOLKIT_RUNTIME_DATA`の明示指定を優先し、次にOSのユーザーデータ領域を使う。
ホストが渡す`CLAUDE_PLUGIN_DATA`と`PLUGIN_DATA`はユーザーデータ領域へ書き込めない場合だけ使う。
ホストごとのplugin dataを優先すると、導入後のウォームアップ・端末の`atk`・Claude Code・Codexが同じ版の環境を別々に構築し、初回のhookがウォームアップ済みの環境を使えないためである。
root・data・環境の導出は`agent_toolkit/_common/plugin_environment.py`が所有し、各SDKへ同じ判断を複写しない。

## 有限終了コマンドの出力と終了状態の保持

一般のチェックと観測は、ハーネスの標準実行・背景実行・待機機能で起動する。別担当へ渡す初回観測など全量の保存が必要な場合は、実行主体が自分の一時領域へ標準出力と標準エラーを分けて保存し、終了コードと取得時のHEADを既存の返却・引き継ぎ記録へ残す。
2026年10月25日に、公開の`atk run-command`（argv・cwd・Git状態・両出力・終了状態を`record.json`へ保存し、`--record`・`--records-file`で読み直す）を撤去した（ユーザー指示）。ハーネスの標準実行で同じ観測が得られ、専用の入出力形式を各担当が毎回学び直す費用と、保存JSONの読取・付替えの工程が便益を上回ったためである。

`atk lane integrate`が統合の各段（固有手順、最終化argv、検証argv）を記録・再開するための有限実行は、内部の`run_command.execute`として保持し、公開コマンドにはしない。shellを介さずargvを起動し、両出力を別のbinary fileへ直結し、子の終了状態とwrapper異常（起動失敗・保存失敗の125、timeoutの124、signalの128+番号）を同じ記録で区別する。検証argvはホスト共有の検証実行枠を所有して実行する。
子の環境は親の環境を複製し、共通の`strip_inherited_venv`で起動元の`VIRTUAL_ENV`と対応するPATHのbin・Scripts要素を取り除く。別プロジェクトのuvや通常の子コマンドが、atkを起動したpluginの仮想環境へ誘導されることを防ぐためである。process-loopと委譲サーバーにも使う共通処理へ接続する。

## atkのサブコマンドの登録

ヘルプのsummaryとdescriptionは、目的または最重要結果を冒頭の短い文で示す。
タイトル、件名とユーザーが読むWIの部分も同じ文章原則を使い、コマンド木の全リーフは生成されたヘルプで確認する。
定義元は`writing-standards`とし、各コマンドは自分の目的と入出力だけを説明する。

`atk`の各サブコマンドは、実装のモジュールが引数を登録する`build_parser`と実行する`dispatch`を公開する。`agent-toolkit/agent_toolkit/atk.py`はサブコマンドと`build_parser`の登録表、実行の登録表と、全サブコマンドに共通の前処理（旧形式の引数の解決、出力の保存、managed-tempの掃引）だけを持つ。`atk wi`配下の引数の登録と実行の振り分けは`_atk/wi/cli.py`、`atk serve`は起動処理の依存を遅延して読み込む`_atk/serve/command.py`が持つ。以前は`wi`の全サブコマンドの引数と`commit`・`serve`などの引数を`atk.py`へ直接書き、`main`の分岐が他モジュールの非公開の関数を呼んでいた。登録方式が2通りに分かれ、サブコマンドを加える計画ごとに`atk.py`へ追記する構造だったためである。

`atk wi`の引数の確定は`prepare_args`と`validate_args`の2段とし、前者をmanaged-tempの掃引より前、後者を掃引の後に呼ぶ。分ける前の`main`と同じ順序で、引数の誤りと掃引の警告を出力するためである。`info`・`commit`・`setup-project`は掃引より前に実行する。
知識境界として、各サブコマンドの引数と実行は実装のモジュールが持ち、`atk.py`は登録の順序と共通の前処理だけを持つ。`--help`の文面と引数は登録の移動前後で変えず、`atk_help_test.py`と既存の動作テストの期待値で確かめる。

## atkサブコマンドの引数拒否形式

委譲の開始・追送・中断・終了済みsessionの破棄はMCPサーバー`agents_server`の公開ツール`start`・`send_message`・`kill`・`stop`が所有する。`atk agents`のヘルプはこの分担とCLIの`wait`・`notify`・`list`・`show`・`logs`を示し、MCP専用名の誤入力は実行せず対応する公開説明へ案内する。引数のスキーマとホスト固有の接頭辞をCLIへ複製しないのは、MCP登録と説明の不一致を防ぐためである。

目的は`atk`の利用主体であるコーディングエージェントが、受理しないオプション名を与えた場合に、1回の出力から正しい呼び出し形式へ到達できるようにすることである。
構造の理由は、拒否の判定を`agent-toolkit/agent_toolkit/_atk/help_text.py`の`add_subcommands`が生成する全サブパーサーの`GuidedSubcommandParser`へ置き、サブコマンドごとに適用の有無が分かれる状態を表現できなくする点にある。argparseはサブパーサーが解釈できない引数をトップレベルの`parse_args`で報告するため、argparseの標準動作ではトップレベルのusageだけが出て、引数を拒否したサブコマンドが受理するオプションが出力へ入らない。
知識境界として、各サブコマンドが受理するオプションの定義は各`build_parser`が持ち、本節は拒否時の出力形式だけを扱う。
登録済みオプションが`--`の後ろで余剰引数になった場合は、位置引数と子コマンドへの転送引数を保って再解析する。
未知オプションは受理せず、登録情報から正しい呼び出し形式を案内する。
位置引数が余った場合は、その値とサブコマンドが受け取る位置引数を示す。位置引数を持たない場合も明示する。
正常に消費した位置引数と子コマンドへ転送する引数は、そのまま受理する。
全ての後置引数を一律に移す案は、位置引数と子コマンドへの転送引数を変えるため採らない。
却下した代替案は、拒否形式を必要なサブコマンドごとに`parser_class`で指定する案と、推測されやすいオプション名を追加で受理する案である。前者は同じ判定を複数の呼び出し元へ分散させ、後者は受理する名前を増やしても別の推測した名前では同じ拒否が生じるため採用しない。

## atkの実行例が受理条件を満たすことの確認

公開ヘルプ、skills・share・rulesと利用ガイドの完全な実行例は、`_testing/cli_examples.py`が実物から抽出し、コマンド木とrun-script登録先の実parserへ渡す。
引数名、必須指定、選択肢と区切り位置の不一致は案内の所在付きで検出する。
インラインの説明用断片は、引数の一部を示す用途として抽出から分ける。
プレースホルダーの値と実在ディレクトリの前提だけを検証環境で補い、引数定義は各`build_parser`が所有する。
出力パスの引き渡しはplansのcheckout・listからcommitへの往復など、既存の動作試験で操作の完了まで確かめる。
文法を写した別schemaと実行時監視は同期先を増やすため採用しない。

## atkの結果行の接頭辞と出力先

目的は`atk`の出力を受け取るコーディングエージェントが、返却値または結果行の先頭の語で成否を確定し、終了コードの再確認、状態の再取得および一致判定の確認を追加せずに次の工程へ進める状態にすることである。
結果行は成功を`成功:`、失敗を`失敗:`、警告を`警告:`、該当0件を`該当0件:`の4種の固定接頭辞で表す。

構造の理由は、接頭辞の文字列と成功行の出力先の決定を`agent-toolkit/agent_toolkit/_atk/outcome.py`へ集約し、出力箇所ごとに語彙と出力先が分かれる状態を表現できなくする点にある。
標準出力の値や構造化データが成功結果を表すコマンドは、その値を結果通知とする。状態変更報告型は標準出力の1行目へ成功行を書く。
この区分を状態変更報告型、値出力型、読み取り専用型、対象外の4つとして同モジュールが保持し、`help_text.py`が各コマンドの`対象と出力`へ結果行の接頭辞と出力先を自動で加える。
`agent_toolkit/atk_help_test.py`はコマンド木の全リーフを列挙し、いずれの区分にも属さないリーフと区分の重複を検出する。

知識境界として、結果の本文は各出力箇所が持ち、本モジュールは接頭辞と結果行の要否・出力先を持つ。
どのコマンドがどの区分に属するかは同モジュールの区分表に従い、ヘルプの文面とテストの双方が区分表を参照する。

却下した代替案は、接頭辞を各出力箇所へ直接書く案と、区分表をテストだけが持つ案である。
前者は同じ語彙の決定を出力箇所の数だけ分散させ、後者はヘルプの文面とテストの判定が別々の表を持つため採用しない。

## atkの出力に含める情報

`atk`の出力は受け取るエージェントが選別せずそのまま読めば次の判断に必要な行だけを得られる構成とする。
出力するのはコマンドの結果（成否、変更・保存した対象と値、要求された値・本文・一覧）と、失敗・警告およびその次の操作である。
実行中に検出した対処を要する事象の警告も含める。
結果と無関係な状況の通知、対処不要の付随処理の報告、毎回同じ固定の案内、入力と別行の記載だけで一意に導ける値の反復は、環境によらず出力しない。
結果と無関係な補足を人向けに環境判定で振り分ける案も採用しない。
人が次の操作を選ぶための対話（確認前の候補一覧や回答前のUWI本文など）は補足行の対象から外し、結果の書式を環境で切り替える既存設計も保持する。
人が直接使う長時間・常駐CLIの実行中表示は、その時点で処理状態を判断するための情報として扱う。
開始、工程の移行、待機理由などを実行中に届け、表示量は人の判断に必要な情報で決める。
LLMが読む出力のトークン削減は、人向け表示を減らす理由にしない。
実装・改訂時は`agent-basics/skills/writing-standards/references/writing.md`「読み手別の追加注意点」からこの観点へ到達する。

`agents_wait`のCLI待機、`git_sync`のremote同期・共有ロック取得、`run_command.execute`の子の終了待ち、`post_apply.run`の工程完了待ちは、人向けに対象と状態を標準エラーへ表示する。
判定は`_atk.environment.is_human_terminal`を使い、エージェント環境の外で標準エラーが端末の呼び出しだけへ表示する。
エージェント環境の区分は有限終了の出力を保存する既存の判定と同じであり、パイプ・ファイル・テストの捕捉へ出力する呼び出しは結果の行だけを保つ。
共有ロックは他の主体が保持して待つ場合だけ待機中と表示する。
`agents wait`のJSON Lines、子の保存出力と終了状態、Git成功時の生出力の抑制を保つ。
post-applyは全体の実行中表示を使い、工程結果の列挙順のまとまりと永続ログの開始時刻・詳細を保持する。
工程ごとの開始行と所要時間行を画面へ重ねる案は、工程結果の列挙順のまとまりを損なうため採らない。

post-applyの進捗は標準エラーの1行を`\r`と空白で書き換えて示し、工程結果の出力前と実行の終了時に消去する。
ANSIエスケープを解釈しない端末（Windowsの`dotfiles-post-apply.exe`を含む）でも同じ表示にするため、行の消去にANSIエスケープを使わない。
表示は完了数・総数・実行中の件数と、実行時間が最も長い（開始が最も古い）実行中の工程名に限り、端末幅を超えない長さにする。
工程の例外は画面へ「工程名: 失敗: 例外の型: メッセージ」の1行だけを出力し、Tracebackは永続ログ専用にする。
失敗後の次の操作と永続ログの所在は、`update-dotfiles`経由の実行では`update-dotfiles`の終了時に1回出力し、`dotfiles-post-apply`の単独実行ではpost-applyの集計の後に1回出力する。

類似箇所の探索では、`atk`の公開登録から長時間・待機・外部照会の実装をたどり、`bin/`と`pytools/`のコマンドが行う外部処理と出力捕捉を静的に調べた。
all-reposと共有アラート照会は状態表示を持ち、watch・serve・ログ追従・画像・PDF・アーカイブ処理・releaserのCI待機は開始・対象・結果または逐次出力を持つ。
全入力規模と外部サービス遅延の測定は探索に含まれず、短いローカル処理が特定の入力で長時間になる可能性は残る。
既知の4箇所を是正し、今後の新設・改訂にも同じ表示方針を適用する。

書式を前提とする機械的な読み手がいる行は、読み手を移行してから除く。
`atk wi`の未回答UWI通知も、結果と無関係な状況の通知として扱う。
未回答UWIは、ユーザーが`atk serve`の件数表示とブラウザー通知で、エージェントが`atk wi list --type=uwi --answered=no`などの明示的な照会で確かめる。
末尾の未回答UWI通知は、ユーザーの確認手段が`atk serve`へ移って読み手を失い、エージェントには出力を選別する動機を与えて終了コードと警告の観測を妨げたため撤去した。
エージェント環境の状態変更だけで抑止する案は、人の端末でも`atk serve`が確認を担うため、環境とサブコマンドによる分岐を保つ理由がなく採用しない。
表記診断は起草者の判断に使う全行を保持し、同じ次の操作の反復だけを1行へまとめる。
WI本文の各診断は入力元、frontmatterを除いた論理本文の行・列、一致箇所を囲んだ前後の抜粋を持つ。
生成時点の本文と入力元を使うことで、複数原稿と同じ行の複数の一致から修正対象を特定できる。
入力元は追加時の本文ファイルのパスまたはエディター入力、置換時は編集対象のファイル名とする。
診断の生成を共通化し、保存詳細・人の端末への直接表示・保存失敗時の表示へ同じ結果を渡す。
起草者が全原稿へ座標を当てて文脈を復元する案は、生成側が保持する情報の再取得を繰り返すため採らない。
出力の選別をhookで検出する案は、静的解析で実行時の条件を再現できず正当な操作へ警告が続いたため撤去済みである。
出力が選別の動機を生む状態では、検出や呼び出し側の規範だけでは再発を防げないため、出力側も改める。

保存本文の一致判定は出力しない。
`atk wi add`・`atk wi edit`・`atk review-table add`・`atk review-table respond`は保存本文が送信元本文と一致しない場合に非0で終了して差異を標準エラーへ書くため、成功の終了コードだけで一致の成立を示せる。
成立時に常に同じ値を返す行を出力しても、受け取る主体の判断は変わらない。

## 失敗と警告の次の操作

失敗行と警告行には、続く行に`次の操作:`で始まる次の操作を必ず置く。
結果行だけで成否は確定しても、事実だけを受け取ったエージェントは次の行動を推測で選び、実行できない操作や同じ失敗を繰り返した（`atk`の引数エラー、agents_serverの`unknown session`、hookの警告などで観測した）。
`report_failure`と`report_warning`は理由と次の操作を別々の必須の引数として受け取り、次の操作を欠いた呼び出しを失敗させる。
警告の出力条件は「atkの出力に含める情報」と`writing-standards/references/writing.md`のエージェントが読む出力の規定に従う。

共通起動の持続状態の警告は`outcome.report_persistent_warning`を通し、同じ会話で同じ内容を1回だけ出力する。
会話識別子は`AGENT_TOOLKIT_OWNER_SESSION`、`CLAUDE_CODE_SESSION_ID`、`CODEX_THREAD_ID`の順に解決し、識別子の無い端末では毎回出力する。
委譲先では共通起動の掃引警告を出力しない。`hook.py`起動時の引数不整合（usageと未知のサブコマンド）の通知は、標準入力の`session_id`で重複を抑止する。各hookの同一条件の通知は`notice_fingerprints`で重複を抑止する。

不正な管理情報を持つ項目の確認先である`atk wi show <ファイル名>`は種別と`target_repo`を検証せず保存内容を表示する。
失敗の案内が、失敗を起こした状態のまま実行できるようにするためである。
指定名の探索とファイル名の検証を持つshowへ集約し、状態ごとに`cat`などの別手段を案内する形は採らない。

次の操作を必須とする構造は`atk`以外の発生源にも同じ形で置く。
標識`次の操作:`、空の次の操作の拒否、理由と次の操作を持つ例外型（`ActionableError`）、標準エラーへの出力関数の4つは`agent-toolkit/agent_toolkit/_common/next_action.py`が持つ。
同モジュールは層の順序で最も前にあり、全ての層、公開スクリプトとスキル付属スクリプトから使える。
hookは`_hooks/notice.py`の`block_formatter`と`warn`区分の整形関数が解消手段`fix`を必須とする。通知を届ける場合は同じ行を保持し、同じ条件の警告は初回だけ届ける。
`atk`は`WebInputError`を`ActionableError`の派生とし、各サブコマンドの実行を振り分ける処理が`_atk/cli_support.py`の`report_rejected`で理由と次の操作の2行を出力する。Web APIの応答本文は`str()`が返す理由だけを使い、変えない。
agents_serverはツール関数の登録の1箇所で例外を包み、`ActionableError`と想定外の例外を次の操作付きのエラー本文へ変える。状態値だけを返す応答（配送の失敗、期限切れsessionの中断、待機の打ち切りなど）には`next_action`項目を加える。
`atk agents wait`、`wait_ci.py`、スキル付属スクリプトと計画ファイルの構造チェックも、非0の終了で同じ標識の行を出力する。

知識境界として、標識と必須性は`_common/next_action.py`、文面は各発生源、状態値の`next_action`項目はagents_serverがそれぞれ持つ。
受信時に参照できる位置は受け取ったメッセージだけであるため、次の操作をツールの説明文やエージェント向け文書だけに置く形は採らない。
却下した代替案は、本文中で次の操作を任意とし、レビューと規範で補う案である。
文面の正しさを確かめるレビューは次の操作の欠落と実在しない名前の案内を検出できず、観測した事象はいずれもレビューで検出されずに混入したため採用しない。

## エージェント環境での長い出力の自動保存

保存したファイルは、ハーネスの読取（Read）か`sed -n '<開始行>,<終了行>p' -- <絶対パス>`で、示した行数を範囲に分けて読む。
2026年10月25日に、文字位置の継続取得を提供した`atk read-file`を撤去した（ユーザー指示）。行数を示せばハーネスの読取と標準コマンドで分割取得でき、継続位置のJSONを連結する専用の手順を各担当が学ぶ費用が便益を上回ったためである。保存表示は保存先と行数の2行とし、最初の読取コマンドの行は添えない。

目的は`atk`を呼ぶコーディングエージェントが保存先の組み立てと保存後の確認をコマンドへ加えずに、長い出力を受け取れる状態にすることである。
保存先の指定を呼び出し側へ任せる形では、エージェントは出力の大小を問わず`--output-file <絶対パス>`を組み立て、`wc -c`や`tail`をつないだ長いコマンドを待機のたびに発行していた。

`AI_AGENT`・`CODEX_CI`・`CLAUDECODE`・`CURSOR_AGENT`のいずれかが設定された環境では、共通処理が有限終了の両ストリームを別々に保持する。
通常はUTF-8で16384バイト以下なら直接表示し、超える場合は全量を新規managed-tempへ保存する。`--help`の表示と、`atk info`のように結果を表示して終わるサブコマンドも同じ共通処理を実行するため、同じ量で判定する。

量によらず保存するのは、結果をファイルとして受け取る呼び出しに限る。一括取得の消費側が保存ファイルから全見出しと本文を確かめるため、FILENAMEを2件以上指定するか`--all`を指定した`atk wi show`を保存する。逐語引用の出所ファイルとしてWI投入担当へ渡すため、`atk run-script session-review-evidence`の`--user-events`を保存する。単発の`atk wi show`と`--detail`などの単発の証拠照会は、その場で本文を読むため通常の量の判定に従う。完成条件証拠のWI取得は`_atk/wi/entries.py`の指定名読取を同一プロセスで使い、CLIの直接表示・保存先を逆解析しない。showのfilename検証、状態順、repository・type・source条件は共通処理が所有し、同期と表示は呼出側が持つ。

2026年10月3日の障害対策（`incidents-workflows.md`「並行実行の競合」の同日の事例）は、保存の判断を生成側へ置き、短いWI本文と証拠照会も保存した。2026年10月4日に、短い単発照会のたびに保存ファイルを開く往復が増えることを観測したため、量によらない保存をファイルとして渡す用途へ狭めた。保存先を呼び出し側に組み立てさせない対策の目的は保ち、その他の照会は既存の16384バイトの判定で長い出力を保存する。

`atk agents wait`はエージェント環境でJSON Linesを保存せず、通知・終了の内訳と、標準出力全体が16384バイト以下に収まる範囲の通知と結果の本文を`本文開始:`・`本文終了:`の行で囲んで標準出力へ直接返す。本文は終了ごとに`agents-wait/<session_id>.md`の1ファイルだけが持ち、後続の入力へはそのパスを渡す。待機の後に本文ファイルを開く呼び出しが毎回生じていた（2026年9月29日以降のClaude Codeの記録で471件）ため本文を表示し、同じ本文を出力の保存物とrun記録へ重ねて保存していた状態を2026年10月25日に解消した（ユーザー指示）。本文の範囲の行は、委譲先が待機の出力を引用しても回収の根拠に数えない。本文ファイルの書込が成功してから配送する契約は保持する。
標準出力は保存先・行数を返し、量によらず保存する呼び出しは続けて呼び出し元が次の判断に使う値を返す。`--user-events`は`kind`が`user`の行ごとに記録位置と本文の冒頭を`発話: record=<record> line=<line> <冒頭>`で返す。WI投入担当へ渡す出所は保存ファイルのままにし、呼び出し元が記録位置を取り出す追加の照会（`jq`・`sed`・`cut`など）を不要にするためである。`record`はコロンを含むため`record=`の形で示す。`--since`は省略でき、省略時はメイン記録の最初から返す。呼び出し元が時刻を推測して渡していたためである。量によらない保存の判定と保存後の表示は`atk.py`の1つの定義で対応付け、保存する呼び出しを加えるときに表示の要否を同じ箇所で決める。標準エラーの保存先は`標準エラー保存先:`の標識を使う。
`atk wi show`の全文保存後は、保存先・行数に続け、各項目のファイル名、AWIの`## ユーザーコメント`またはUWIの`## 回答`の有無、ある場合の保存先での開始行を1行ずつ全件示す。
単発の長い出力も同じ保存後処理を通し、本文の冒頭だけを読む場面でも是正要求を含み得る記入欄へ到達できるようにする。
記入欄は既存のユーザーコメント解析と回答見出しの定義から判定し、コードフェンス内の見出しを除外する。
保存本文と直接表示・要約表示の形式は保持する。
WIの表記診断は全量を標準エラーへ直接書き、16384バイトを超える場合だけ共通の保存機構が`標準エラー保存先:`へ保存する。短い診断のたびに派生ファイルを作成しないためである（2026年10月25日、ユーザー指示）。
常駐のserve・process-loopとlogsの追従は逐次表示を維持し、人の端末は直接表示とリダイレクトを使う。
公開の保存先指定は全て除去した。本文を必要とする消費側へ保存の判断を戻す案は、保存先の組み立てを残すため採らない。stdoutだけの保存ではstderrの表記診断を失うため、両ストリームを分ける。

却下した代替案は、待機コマンドの包装を検出するhookを追加する案である。
包装の原因は、背景実行の上限を一律に求める規範、`atk agents wait`のヘルプにあった上限値の欠落、および保存先の指定を呼び出し側に任せる設計であり、これらを直せば包装する理由が消える。

## atk commitとsetup-projectの公開境界

コミット作成とプロジェクト規範の統一は、配布先の全エンドユーザーが使う操作であるため`atk`のサブコマンドとして公開する。旧コマンドをdotfilesの`pytools/`へ残すと、agent-toolkit単体のユーザーとdotfilesユーザーで到達できる機能が異なり、同じ処理を2箇所へ維持する。実装は`agent-toolkit/agent_toolkit/_atk/`に置き、モデル候補は既存の`resolve_model_candidates`でchores工程から解決する。

`atk commit`は未対応engine、実行ファイルの不在、および子の非0終了後もHEADと`git status --porcelain=v1`が起動前と一致する場合だけ次候補を試す。Git状態を変更した失敗で候補を進めると、前候補が途中まで行ったstageやcommitを別のモデルが重ね、ユーザーの意図しない履歴を作成し得る。子は一時ディレクトリで起動し、操作対象のGit rootを明示してプロジェクト規範の自動読込を避ける。ClaudeがWeekly limitか5時間の利用上限で拒否した場合は、Git状態の変化によらず次の候補へ進まず、解除予定時刻まで待って同じ会話を`--resume`で続ける（ユーザー指示）。このためClaudeは会話を保存する形（`--session-id`で識別子を指定）と構造化出力（`stream-json`）で起動し、利用枠の種類と解除予定時刻を出力から読む。元の依頼を新しい作業として送り直すと、拒否より前に行ったstageやcommitを繰り返し得るため、同じ会話へ継続だけを送る。会話は起動した作業ディレクトリでだけ再開できるため、一時ディレクトリは待機の間も保持する。`atk setup-project`は既存の指示移行とスキルリンクを通常は実行し、規範複製は指定時だけ行う。グローバル配布済みの規範を各プロジェクトへ通常時に複製すると、同じ条文を重ねて読み込むためである。

## 計画検証と検索記録

GitLab CIのbaseline、待機、一覧、詳細と失敗ログは、glabのホスト別API解決を共有する。
ホスト設定、`GL_HOST`を含む環境変数と明示HTTP(S) URLは公開glabの優先順で解決し、リポジトリ指定は設定キーとして保持する。
リポジトリ指定からHTTP APIのauthorityを独自に組み立てる案は、ホスト別endpointの指定を失わせるため採用しない。

計画の検証行は、実装担当とレビュー担当が計画の検証コマンドをハーネスの標準実行でそのまま動かす。直接影響範囲の固定文字列検索は語ごとに`git grep -n -F`か明示対象の`rg -n -F`で行い、終了コード0は一致、1は一致なし、それ以外は検索失敗として観測する。2026年10月25日に、検証行を列挙・実行・保存した`plan-verify`を撤去した（ユーザー指示）。registryを使う動的bash補完は新しいコマンド名を同じ定義から取得する。

処理中の選定の書込対象追加は、既存pick-wi-checkの`--extend-write-targets`が追記・全体チェック・原子的保存を所有する。
追加入力に新設先とレーン間の重なりの意味判断を持たせ、初回配分と既存の順序を保持する。
型と本文被覆のチェックは初回生成・合流と共有し、不足する記録があれば保存先を変更せず次の操作を返す。
各回のYAML編集コードをメインへ委ねる方式は同じ構造の加工を反復させるため、既存のチェックと保存の境界へ操作を加えた。
追加操作は自身の追記で成立し得る全体チェックの違反を同じ追加入力で解消できることを不変条件とする。このため、全体チェックが`書込対象`に連動して求める欄（`導出した新設先`、`レーン間の重なり`、`プロジェクト規範の指定`、`書き込まない反映先`）を追加入力で更新できる。`プロジェクト規範の指定`は値全体の置換、`書き込まない反映先`は追加した書込パスと同じか配下の要素の除去で扱う。2026年10月28日の1回のprocess-wiで、規範指定を受け取れない追加操作が全体チェックで拒否され、メインが選定YAMLの写しを手で書き換えて再実行することを4回繰り返したことによる。規範指定を共有スクリプトが`norm-spec`設定から自動生成する案は、読む要求の文面と原本の指定をメインが組み立てる所有の境界に反するため採らない。`書込対象`に連動するチェックを加えるときは、`selection_merge.py`の追加入力の許可欄も同じ変更で見直す。

## `atk run-skill`

`atk run-skill`はcronなど端末を持たない定期実行から、指定した対象リポジトリで指定したスキルを自律モードの最上位セッションとして1回実行する。ユーザーは別環境のリポジトリに持つスキルを数日に1回、自律モードで実行したいと求めた。確認への回答では、WIキューを経由しない単発実行コマンドと毎回の報告用UWIを選んだ（2026年10月6日）。実装は`agent-toolkit/agent_toolkit/_atk/run_skill.py`が持つ。モデル候補の解決、可用性判定、利用上限の待機と正常終了の判定は、`atk wi process-loop`と共通の`agent-toolkit/agent_toolkit/_atk/orchestrator.py`が持つ。可用性判定を軽量工程のモデル・effort `low`・軽量起動で行う理由は[design-process-loop.md](design-process-loop.md)にある。

`atk run-skill`が指定スキルを実行する子セッションは非対話起動（Claudeは`claude -p`、Codexは`codex exec`）とする。定期実行には操作する端末が無く、対話型のCLIは入力を待ったまま止まるためである。Claudeでは最初の入力を`/goal`へ渡し、目標評価で報告用UWIの保存までターンを続けさせる。Codexの非対話起動は`/goal`の行を通常の入力として残し目標として扱わないため（Codex 0.160.1で観測）、`atk-auto`要素の目的文だけを渡し、セッションはモデルの最終応答で終わる。
目的文は終わり方を2つ並べ、どちらも目標の達成として扱う。完遂した場合は報告用UWIへ結果を保存して終え、どちらにも当たらない間（子担当の失敗を許可済みの回復手段で続けられる間を含む）は続ける。この実行の中で解消できない具体的な前提（判断・認可・外部入力など）が残った場合は、未完了の理由・残る工程・再開の条件を報告用UWIへ保存して未完了のまま終える。許された回復手段をすべて試しても解消しない失敗と、スキルや依頼が再試行などの回復操作を禁じる失敗もこの前提に含める。2026年10月31日の実ホスト受入で、目標評価は未完了の終了を達成と明示しない目的文では報告保存後も完遂の証拠を求め、回復手段が残らないことを明示しない目的文では子担当の失敗を前提不足と認めずに停止を遮断した。
2026年10月30日の受入では、成功の完遂だけを終了条件にした目的文が、失敗を報告用UWIへ保存した後も停止を遮断し続け、ホストの連続遮断上限で終了した。単に`/goal`を外すと報告保存前の早期終了を許し、遮断上限の引き上げは失敗時の終了条件の欠落を解消しないため、目的文へ未完了終了の分岐を加えた。
未完了で終えた実行は報告保存の同期確認だけを満たし、振り返りbatchの分析成功の検収（`run_skill_batch.py`）と`finish`の保留は従来どおりである。

子セッションへはprocess-loop用の環境印（`AGENT_TOOLKIT_PROCESS_LOOP_SESSION`と`AGENT_TOOLKIT_PROCESS_LOOP_SESSION_ID`）を渡さない。印はStopで`atk agents-exit-session`の実行記録を求めるhookを有効にし、そのコマンドは対話型のCLI本体だけを停止対象とするため、最終応答で終わる非対話セッションが時間上限まで終われなくなる。起動元がprocess-loopの子でも印を除く。

`atk run-skill`の指定スキルの実行中に利用上限へ達した場合は、ClaudeとCodexのどちらも解除後に同じ会話を再開する。
Claudeは常に構造化出力から利用枠情報を取得し、`--resume`で継続する。
Codexは常に`--json`の`thread.started`からthread IDを取得し、ロールアウト記録の上限判定に従って`codex exec resume`で継続する。
進捗表示の有無と再開に必要な出力の取得を分け、解除待ちの時間は`--timeout`から除く。
解除予定が不明な場合は300秒後に再確認し、待機の回数と総時間を打ち切らない。
継続指示は中断前の記録を確認し、完了済み操作を繰り返さず未完了部分を続けることを伝える。
候補判定時のCodex上限は次の候補を先に試し、全候補失敗かつ上限失敗がある場合だけ最も早い解除予定まで待って先頭から判定し直す。
上限判定は共通層、同じ会話の再開はrun-skill、候補判定はorchestratorが所有する。

報告用UWIの本文作成と内容の十分性の判断は、セッション内の`agent-toolkit:report-completion`が所有する。
CLIは子の正常終了に加え、同じ実行IDと`source=run-skill`・`scope=<スキル名>`・`run_skill_report=true`を持つUWI本文のcommitを確かめる。
upstreamがある場合は実remoteへのpush到達も確かめ、全て成立した場合だけ終了コード0を返す。
保存未達は終了コード1とし、標準エラーへ診断、ログの所在と次の操作を書く。124は時間上限の到達だけに用いる。
回復時はログの実行IDと対応UWIを確認し、同じ会話を再開してreport-completionで保存する。
保存済みならWI保存先のcommit・pushを完了し、次回の実行を待つ。

過去の実行が投入したUWIは、次回の同じスキルの実行が`source`（`run-skill`）と`scope`（スキル名）で識別して扱う。手順は`agent-toolkit/skills/user-confirmation-and-report/references/answer-transitions.md`「`atk run-skill`の過去の実行のUWI」にある。process-wiは回答済みUWIの取得へ`--source=!run-skill`を付け、`calculate_readiness`もこれらのUWIをreadyへ含めない。含めると、process-wiの選定が除くUWIのためにprocess-loopが子セッションの起動を繰り返す。識別には既存の`source`と`scope`を使い、新しい状態や保存先は加えない。

実行ごとのログは状態ディレクトリの`run-skill/`へ置き、各実行の開始時に最終更新から30日を超えたものを削除する。数日に1回の起動で同じ組の直近約10回分を調べられる長さとした。多重起動は同じディレクトリの`locks/`のファイルロックで防ぎ、対象リポジトリかスキルが異なる実行は並行して起動できる。

標準エラーが端末の場合は、ログ作成直後に絶対パス、取得直後に子の識別子、受信ごとにassistantの発言とtool呼出名を標準エラーへ表示する。標準出力だけをリダイレクトした起動でも表示する。Claudeは`--output-format stream-json --verbose`を使い、起動前のUUIDを表示する。Codexは`--json`を使い、`thread.started`の`thread_id`を表示する（[非対話実行の公式仕様](https://learn.chatgpt.com/docs/non-interactive-mode#make-output-machine-readable)）。思考と生JSON全体は表示せず、表示した進捗と両streamの生診断を同じログへ残す。非TTYの子CLIの出力形式、成功時のstdout一行、失敗時のstderrと終了コード、timeoutと出力待機上限は従来どおりである。

進捗の変換と表示は`run_skill_progress.py`が持つ。`atk agents logs`の`logs_export.py`が使う`session_record_format.SessionEvent`とClaudeの変換を再利用し、Codex exec固有のitemイベントだけを同じ型へ変換する。保存済みロールアウトを読むlogsと実行中のstdoutを読むrun-skillは入力形式と所有する資源が異なるため、ログファイルの追跡機構は共通化しない。

子の終了前の表示と端末条件は、[run_skill_test.py](../../agent-toolkit/agent_toolkit/_atk/run_skill_test.py)の`test_tty_progress_arrives_before_child_exits`が、両候補・別スキル・正常終了・異常終了・timeoutを入力に検証する。

却下した案は3つある。cronからAWIを定期投入し`atk wi process-loop`に処理させる案は、ユーザーが単発実行コマンドを選んだため採らない。対話型の`claude`をcronから起動する案は、端末が無いため採らない。Claude Codeのクラウド定期実行は社内のサーバーへ届かない見込みのため採らない（届くかは確かめていない）。
