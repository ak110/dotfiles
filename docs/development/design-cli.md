# CLIの入力・結果・公開境界の設計記録

本書は[設計記録の索引](design.md)から主題別に分割した記録であり、機構の目的、構造の理由、知識境界と却下した代替案を保持する。
実行時に適用する規範は、各節が参照する現行のルールファイルとスキルが定める。

## 公開出力から導出できる項目の撤去

`atk agents list`と`atk agents show`、およびMCPの`list`は停滞の判定を表す`stalled`を返していた。
`stalled`の判定は同じ応答が返す`seconds_since_activity`と定数の閾値を比べるだけで再現できるため、公開出力から撤去した。
MCPの`list`は通常時の3項目の公開契約を保つため、`stalled`を`seconds_since_activity`へ置き換えた。ClaudeのAPI失敗を再試行している間だけ、一次情報から算出した`api_error`も返す。

導出できる項目を公開出力へ置くと、同じ判定を定める箇所が生成側と呼び出し側の2つに分かれる。
閾値を変えた時点で両者が食い違い、どちらが現在の判定かを呼び出し元が確定できない。
公開出力は一次情報だけで構成し、判定は呼び出し元が行う。

公開項目は消費側の用途から選ぶ。CLI一覧は識別・活動・結果保留を、詳細は実行条件と本文を返す。通常の活動は`seconds_since_activity`にまとめ、絶対活動時刻はMCPの`show(verbose=True)`で調査する。結果のturn番号・確定時刻、通知の送信時刻、API失敗の集計回数・初回時刻、初期化の受信総数は内部保持と診断処理に残して通常応答へ通さない。内部辞書から用途別の項目集合へ射影することで、内部追加を公開契約の追加にしない。保存物の一括変換や新しい台帳は不要であり、旧保存物も回収時に同じ射影へ通す。

## dotfilesのatkで実行するworktree

dotfilesの`bin/atk`と`bin/atk.cmd`は同一リポジトリ内からの通常起動でcwdのworktreeを使う。
専用worktreeの`plan-check`などを改修しても、PATHのコマンドが複製元の版を起動すると、改修版の欠陥が検証を通過する。

スクリプト自身の配置からdotfilesのrootを求め、cwdのGit共通ディレクトリと比較する。
同じ場合はcwdのworktreeにある`agent-toolkit/bin/atk`へ委譲し、Git外と別リポジトリでは配置先の従来版を使う。
子へ引数、cwd、標準出力、標準エラーと終了コードを渡し、子の失敗で別版へ戻さない。
対象worktreeの`agent-toolkit/bin/atk`が無い場合は、不足と復元の操作を返す。
Windowsは`call`による引数の再展開を避け、選択したバッチへ処理を移す。

配布物の`agent-toolkit/bin/atk`は自身の配置から依存と実装を選び、常駐時の再起動を担う。
dotfilesの`bin/atk`はworktreeの選択だけを担い、配布物の実装、PATH登録、hookとMCPの起動先を保つ。
各工程へ絶対パスの選択を複製する案は、通常起動の取り違えを残すため採らない。
プラグイン側で実装を自動で切り替える案は、dotfilesを使わない環境の実装選択まで変えるため採らない。

## atkサブコマンドの引数拒否形式

目的は`atk`の利用主体であるコーディングエージェントが、受理しないオプション名を与えた場合に、1回の出力から正しい呼び出し形式へ到達できるようにすることである。
構造の理由は、拒否の判定を`agent-toolkit/agent_toolkit/_atk/help_text.py`の`add_subcommands`が生成する全サブパーサーの既定クラスへ置き、サブコマンドごとに適用の有無が分かれる状態を表現できなくする点にある。argparseはサブパーサーが解釈できない引数をトップレベルの`parse_args`で報告するため、既定の動作ではトップレベルのusageだけが出て、引数を拒否したサブコマンドが受理するオプションが出力へ入らない。
知識境界として、各サブコマンドが受理するオプションの定義は各`build_parser`が持ち、本節は拒否時の出力形式だけを扱う。
却下した代替案は、拒否形式を必要なサブコマンドごとに`parser_class`で指定する案と、推測されやすいオプション名を追加で受理する案である。前者は同じ判定を複数の呼び出し元へ分散させ、後者は受理する名前を増やしても別の推測した名前では同じ拒否が生じるため採用しない。

## atkサブコマンドの実行結果出力

目的は`atk`の出力を受け取るコーディングエージェントが、結果行の先頭の語だけで成否を確定し、終了コードの再確認、状態の再取得および一致判定の確認を追加せずに次の工程へ進める状態にすることである。
結果行は成功を`成功:`、失敗を`失敗:`、警告を`警告:`、該当0件を`該当0件:`の4種の固定接頭辞で表す。

構造の理由は、接頭辞の文字列と成功行の出力先の決定を`agent-toolkit/agent_toolkit/_atk/outcome.py`へ集約し、出力箇所ごとに語彙と出力先が分かれる状態を表現できなくする点にある。
成功行の出力先は、実行したコマンドの標準出力が値、構造化データまたは本文の表示を担うかで決める。担う場合は標準エラー、担わない場合は標準出力の1行目とする。
この区分を状態変更報告型、値出力型、読み取り専用型、対象外の4つとして同モジュールが保持し、`help_text.py`が各コマンドの`対象と出力`へ結果行の接頭辞と出力先を自動で加える。
`agent_toolkit/atk_help_test.py`はコマンド木の全リーフを列挙し、いずれの区分にも属さないリーフと区分の重複を検出する。

知識境界として、結果行に続く本文は各出力箇所が持ち、本モジュールは接頭辞と出力先だけを持つ。
どのコマンドがどの区分に属するかは同モジュールの区分表に従い、ヘルプの文面とテストの双方が区分表を参照する。

`atk`の出力は、受け取るエージェントが選別せずそのまま読めば次の判断に必要な行だけを得られる構成とする。
出力するのはコマンドの結果（成否、変更・保存した対象と値、要求された値・本文・一覧）と、失敗・警告およびその次の操作である。
実行中に検出した対処を要する事象の警告も含める。
結果と無関係な状況の通知、対処不要の付随処理の報告、毎回同じ固定の案内、入力と別行の記載だけで一意に導ける値の反復は、環境によらず出力しない。
人向けの補足として環境判定で振り分ける案も採用しない。
人が次の操作を選ぶための対話（確認前の候補一覧や回答前のUWI本文など）は補足行ではなく、結果の書式を環境で切り替える既存設計も保持する。
書式に依存する機械的な読み手がいる行は、読み手を移行してから除く。
`atk wi`の未回答UWI通知も、結果と無関係な状況の通知として扱う。
未回答UWIは、ユーザーが`atk serve`の件数表示とブラウザー通知で、エージェントが`atk wi list --type=uwi --answered=no`などの明示的な照会で確かめる。
末尾の未回答UWI通知は、ユーザーの確認手段が`atk serve`へ移って読み手を失い、エージェントには出力を選別する動機を与えて終了コードと警告の観測を妨げたため撤去した。
エージェント環境の状態変更だけで抑止する案は、人の端末でも`atk serve`が確認を担うため、環境とサブコマンドによる分岐を保つ理由がなく採用しない。
表記診断は起草者の判断に使う全行を保持し、同じ次の操作の反復だけを1行へまとめる。
出力の選別をhookで検出する案は、静的解析で実行時の条件を再現できず正当な操作へ警告が続いたため撤去済みである。
出力が選別の動機を生む状態では、検出や呼び出し側の規範だけでは再発を防げないため、出力側も改める。

保存本文の一致判定は出力しない。
`atk wi add`・`atk wi edit`・`atk review-table add`・`atk review-table respond`は保存本文が送信元本文と一致しない場合に非0で終了して差異を標準エラーへ書くため、成功の終了コードだけで一致の成立を示せる。
成立時に常に同じ値を返す行を出力しても、受け取る主体の判断は変わらない。

却下した代替案は、接頭辞を各出力箇所へ直接書く案と、区分表をテストだけが持つ案である。
前者は同じ語彙の決定を出力箇所の数だけ分散させ、後者はヘルプの文面とテストの判定が別々の表を持つため採用しない。

失敗行と警告行には、続く行に`次の操作:`で始まる次の操作を必ず置く。
結果行だけで成否は確定しても、事実だけを受け取ったエージェントは次の行動を推測で選び、実行できない操作や同じ失敗を繰り返した（`atk`の引数エラー、agents_serverの`unknown session`、hookの警告などで観測した）。
`report_failure`と`report_warning`は理由と次の操作を別々の必須の引数として受け取り、次の操作を欠いた呼び出しを失敗させる。
対処が不要な警告も、続行してよいことを次の操作として書く。

次の操作を必須とする構造は`atk`以外の発生源にも同じ形で置く。
標識`次の操作:`、空の次の操作の拒否、理由と次の操作を持つ例外型（`ActionableError`）、標準エラーへの出力関数の4つは`agent-toolkit/agent_toolkit/_common/next_action.py`が持つ。
同モジュールは層の順序で最も前にあり、全ての層、公開スクリプトとスキル付属スクリプトから使える。
hookは`_hooks/notice.py`の`block_formatter`と`warn`区分の整形関数が解消手段`fix`を必須とし、反復集約の2件目以降と遮断への昇格でも同じ行を残す。
`atk`は`WebInputError`を`ActionableError`の派生とし、`atk.py:main`が理由と次の操作の2行で出力する。Web APIの応答本文は`str()`が返す理由だけを使い、変えない。
agents_serverはツール関数の登録の1箇所で例外を包み、`ActionableError`と想定外の例外を次の操作付きのエラー本文へ変える。状態値だけを返す応答（配送の失敗、期限切れsessionの中断、待機の打ち切りなど）には`next_action`項目を加える。
`atk agents wait`、`wait_ci.py`、スキル付属スクリプトと計画ファイルの構造チェックも、非0の終了で同じ標識の行を出力する。

知識境界として、標識と必須性は`_common/next_action.py`、文面は各発生源、状態値の`next_action`項目はagents_serverがそれぞれ持つ。
受信時に参照できる位置は受け取ったメッセージだけであるため、次の操作をツールの説明文やエージェント向け文書だけに置く形は採らない。
却下した代替案は、本文中で次の操作を任意とし、レビューと規範で補う案である。
文面の正しさを確かめるレビューは次の操作の欠落と実在しない名前の案内を検出できず、観測した事象はいずれもレビューを通って混入したため採用しない。

受領した主体が次に特定の工程へ入る場合は、正常に終端した結果にも`next_action`を載せる。
`agent-toolkit:review-standards`を起動して`references/reviewee.md`に従い採否を確定する次の操作は、labelが`-review`で終わるsessionの`completed`結果へ加える。
`atk agents wait`の回収と、`send_message`が未回収の結果を返す`previous_result`の双方が、`_agents_server/state.py`の同じ判定と文面を使う。
2026年10月1日に、レビュー結果を受け取った主体が同スキルを起動しないまま採否を確定し、合意の無い指摘を「承認済み」として見送った事象による。
レビュー目的の判定にはlabelを使う。`start`のlabelの凡例と`<役割名>.subagent.md`から生成するlabelが、レビューを目的とするsessionへ`-review`の末尾を与えるためである。
凡例から外れたlabelでは案内が出ないが、新しい状態や入力を加えずに、観測した事象の起動と受領を覆える。
`reviewee.md`へ合意の扱いの条文を加える案は、同書が既に合意の確認を求めており、読まれなかったことが原因であるため採らない。

## エージェント環境での長い出力の自動保存

目的は`atk`を呼ぶコーディングエージェントが保存先の組み立てと保存後の確認をコマンドへ加えずに、長い出力を受け取れる状態にすることである。
保存先の指定を呼び出し側へ任せる形では、エージェントは出力の大小を問わず`--output-file <絶対パス>`を組み立て、`wc -c`や`tail`をつないだ長いコマンドを待機のたびに発行していた。

`AI_AGENT`・`CODEX_CI`・`CLAUDECODE`・`CURSOR_AGENT`のいずれかが設定された環境で`--output-file`を省略すると、`atk.py`の`main`は`--output-file`と同じ位置でサブコマンドの標準出力を受け取る。
UTF-8で16384バイト以下ならそのまま書き、超える場合は実行ごとに新しいmanaged-tempの中のファイルへ全量を保存して、`--output-file`と同じ要約行だけを書く。
保存と要約行の書式は`agent-toolkit/agent_toolkit/_atk/output_file.py`が持ち、要約行の`保存先:`を読む`_agents_server/state.py`の回収判定は保存先の指定と自動保存を区別せずに読める。
閾値はCodexのシェル出力上限への対策として大きな読取を遮断する`_hooks/pretooluse/large_reads.py`の閾値と同じ値とし、1回のツール結果として受け取れる量に合わせる。
保存先の作成に失敗した場合は、出力を失わないよう警告を標準エラーへ書いて全量を標準出力へ書く。

対象外はエージェント環境でない起動、常駐と追従の起動（`atk serve`、`atk wi process-loop`の常駐、`atk agents logs --follow`）である。
ユーザーは端末で結果を直接読むため出力を変えず、常駐と追従の起動は終了まで出力を受け取ると経過を表示できなくなる。
`atk run-script`は対象に含める。登録scriptは同じプロセス内で実行されるため同じ仕組みで受け取れ、`session-review-evidence`の検索と一括抽出のように長い出力の主な発生源を含む。

`--output-file`は保存したファイルを別の担当へ渡す工程のように保存先を指定する必要がある場合のために残す。
`atk`の標準出力を解析する機械的な読み手は、エージェント環境から起動されても本文を受け取れるよう`--output-file`で全量を受け取る。
例として、`check_exec_review_evidence.py`は`atk wi show`の本文を一時ディレクトリの保存先から読む。

却下した代替案は、待機コマンドの包装を検出するhookを足す案である。
包装の原因は、背景実行の上限を一律に求める規範、`atk agents wait`のヘルプにあった上限値の欠落、および保存先の指定を呼び出し側に任せる設計であり、これらを直せば包装する理由が消える。

## atk commitとsetup-projectの公開境界

コミット作成とプロジェクト規範の統一は、配布先の全エンドユーザーが使う操作であるため`atk`のサブコマンドとして公開する。旧コマンドをdotfilesの`pytools/`へ残すと、agent-toolkit単体のユーザーとdotfilesユーザーで到達できる機能が異なり、同じ処理を2箇所へ維持する。実装は`agent-toolkit/agent_toolkit/_atk/`に置き、モデル候補は既存の`resolve_model_candidates`で解決する。

`atk commit`は未対応engine、実行ファイルの不在、および子の非0終了後もHEADと`git status --porcelain=v1`が起動前と一致する場合だけ次候補を試す。Git状態を変更した失敗で候補を進めると、前候補が途中まで行ったstageやcommitを別のモデルが重ね、ユーザーの意図しない履歴を作成し得る。子は一時ディレクトリで起動し、操作対象のGit rootを明示してプロジェクト規範の自動読込を避ける。`atk setup-project`は既存の指示移行とスキルリンクを通常は実行し、規範複製は指定時だけ行う。グローバル配布済みの規範を各プロジェクトへ通常時に複製すると、同じ条文を重ねて読み込むためである。
