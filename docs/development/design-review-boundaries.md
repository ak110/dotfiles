# 直接消費側探索とレビューの知識境界の設計記録

[設計記録の索引](design.md)と[検収根拠とレビュー担当間の知識境界の設計記録](design-review-evidence.md)から参照する主題別の記録である。

## 直接消費側探索の証跡

目的は外部から観測できる文言または挙動を変える実装で、変更前の期待値を保持するテストを変更範囲の検証の対象に必ず含め、実行レビューが未探索と未更新を区別できるようにすることである。
探索証跡には対象、検索語、直接消費側と採否を残し、未探索と未更新を区別できるようにする。
探索対象と方法は[plan-file-standards.md](../../agent-toolkit/skills/write-plan/references/plan-file-standards.md)「要件・外部仕様」、検証対象の選定は[変更範囲の検証の対象選定](../../agent-toolkit/share/verification-operations.md)が定める。
実行レビュー担当は提出された検証結果から成果物へ到達し、成果物の欠落だけなら不足記録、未更新の直接消費側が実在する場合は完了条件違反として扱う。
探索結果を完了報告の要約だけへ埋め込む案は、対象集合と採否の再検収ができず、記録不足と実装欠陥を分離できないため採用しない。

## レビュー担当とレビューイーの知識境界

### 役割別資料と読込境界

レビュー実施側と指摘受領側は、実行主体の文脈混同を防ぐため、`agent-basics:review-standards`の役割別参照資料へ分離する。
同スキルの`references/reviewer.md`はレビュー担当による欠陥の導出、証拠、通常運用で生じる実害および解消方向を定める。
レビュー指摘管理表の公開操作は`atk review-table --help`に従う。
7列TSVの構造と旧8列形式の読取は`agent-toolkit/agent_toolkit/_atk/review_table.py`と`agent-toolkit/agent_toolkit/_atk/review_table_test.py`が定める。
同スキルの`references/reviewee.md`はレビュー指摘、改善提案、ユーザーの割り込み・是正要求と想定外の発見を受領した主体による修正要否の立証、安全な修正、自己点検と公開可能性の検証を定める。
スキル本体は、両役割へ共通する作成規範の読込、役割別資料の読込条件、他方の役割の資料を適用しない規定、レビュー指摘管理表の共通操作だけを持つ。
一致確認は`add`と`respond`が行い、記録した主体は終了コード0を確認して一致が成立したと判断し、保存本文を再取得しない。
非0で終了した場合だけ、`atk review-table show`の`--format=jsonl`が返すデコード済みの値で差異を特定する。
応答本文は`show <表> --row-id N --field response`、対応不要理由は`--field no-response-reason`で全文を取得する。
行識別子の検証とセルのデコードは更新と表示で共有し、改行・日本語・引用符を保った本文の取得を表の所有者へ集約する。
各セルはJSON文字列として保存するため、オプションを付けない`show`の出力を差異の特定に用いると符号化した表現と送信本文が一致しない。
保存本文そのものを出力しないのは、自由記述の本文が後続の固定項目名と同じ行を含む場合に本文の終端を判別できないためである。
判定を各役割の資料へ委ねる案は、同じ判定を複数の主体が個別に実装するため採用しない。
初回レビューは採用案とテストの期待値を読む前に、利用場面から消費主体が必要とする期待結果を導く。
レビューイーは是正要求を目的、事実の認識と変更要求に分けて受け取る。
2026年10月3日に、実装、テストの期待値とレビューが同じ採用前提を共有し、互いの一致で目的に適さない表示が合格した観測に由来する。
判断基準は`agent-basics:writing-standards`の`agent-basics:writing-standards/references/design-heuristics-screening.md`「設計案の予備選別」が所有し、レビュー側は導出の時点だけを定めて基準を複製しない。
役割ごとに別スキルへ分ける案は、両役割が同じ場面で一方だけを起動するため、起動手順と常時ロードされる`description`を二重に持つだけとなり採用しない。

レビュー担当は`review-standards/references/reviewee.md`を読まず、レビューイーは`review-standards/references/reviewer.md`を読まない。
計画・設計の採用案や指摘・発見の妥当性を評価する場合だけ、両者は役割中立の共通判断手順である
`review-standards/references/judgment-details.md`を参照する。

指摘受領側の各文書は`agent-basics:review-standards`の`references/reviewee.md`の読込指示と場面固有の返却規定だけを持つ。
メインは指摘の採否を常に確定するため、同スキルを起動する。
単純案の比較は、一般判断向けの局所運用案を`share/rules/common/01-agent.md`と`judgment-details.md`で扱い、
指摘修正向けの局所修正案を`agent-basics:review-standards`の`references/reviewee.md`で扱う。

共通手順は`agent-basics:review-standards`の`references/judgment-details.md`と同スキル本体へ集約する。
レビューイーが読む範囲は役割中立の共通契約と`references/reviewee.md`に限り、レビュー担当側の`references/reviewer.md`へは依存しない。
重複を残して文言だけを統一する案は、各文書の改訂で再び文言差が生じるため採用しない。
`judgment-details.md`をレビューイー側へ移す案は、レビュー担当から役割中立の判断手順へ到達できなくなるため採用しない。
指摘修正向けの判定文を一般判断向けの原則だけで代替する案は、修正文脈固有の適用条件を保持できないため採用しない。

### respondの必須ラベル

`respond`は対応要の本文に`違反を確認した規定:`・`同じ規定の検索:`・`採用する修正範囲:`・`採用しない修正方針:`を、対応不要の本文に`根拠の所在:`を行頭のラベルとして求め、ラベルが欠けた本文と内容が空のラベルを持つ本文を記録しない。
各ラベルに書く内容は`review-standards/references/reviewee.md`が1箇所で定め、`respond`が確かめるラベル集合との一致を`review_table_invariant_test.py`が確かめる。
応答の必須要素は以前から`reviewee.md`が定めていたが、要素を書くかは記録時点でレビューイーが該当節を読み込み、想起しているかで決まっていた。
2026年10月6日には、指摘箇所だけを直した応答と、記録を探さずに書いた不採用理由が記録され、同じ論点の指摘がラウンドごとに1箇所ずつ繰り返された。
全てのレビューイーが使う唯一の記録手段である`respond`が必須ラベルの欠けた本文を拒否するため、レビューイーが該当節を読み込まなかった場合や想起しなかった場合も、検索範囲や根拠の所在を欠いた応答は表へ記録されない。
記録された応答には同じ規定の検索範囲が残るため、再レビューを担うレビュー担当はその範囲から検索の不足を判定できる。
要素を列として表す案は、表の列と応答状態を増やさない方針（本書「完成条件証拠と証拠検査」）に反し、既存の表の読み取りも変えるため採用せず、本文の行頭ラベルで表す。
`respond`はラベルの有無と内容が空でないことだけを確かめ、記述の妥当性はレビュー担当が再レビューで判断する。
この確認は新しい記録だけに適用し、ラベルを持たない既存の応答を含む表は`show`・`summary`・`validate`で従来どおり読む。

### 再レビューと反復指摘の扱い

再レビューは前回と今回の`review_contract`を別々に受領し、それぞれの契約から判定範囲を作成する。
本文が同じ文書の読者別探索は、両回の契約境界も同じ場合に再利用する。
前回契約を持たない旧入力の互換動作は維持し、契約境界の変更箇所は省略しない。
今回の契約だけで前回範囲も再構築する案は、履歴書換え後の同一本文を別の対象と誤判定するため採用しない。

再レビューの対象は前回指摘の修正、前回レビューHEADから今回HEADへの修正差分と直接影響範囲とする。
履歴書換え後は前回と今回の開始時点・HEADの組によるファイル別差分を比べる。
完成条件証拠は全行を新HEADで再判定し、修正が作用しない行はevidenceへ判定維持の理由を残す。
round 3以上で未解決指摘を受けたレビューイーは、局所修正前に全ラウンドを読み、方式の維持・縮小・置換を比較する。
維持には独立欠陥の根拠を残し、認可変更は既存のエスカレーションへ返す。
方式の置換直後だけ開始時点からの全差分をレビューする。
同じ論点の個別計数や新しい表の状態を増やさず、既存roundを見直しの契機へ使う。

`review-table show --format=summary --round <round>`は指定roundと同じtrackの過去roundにも指摘があれば、`previous_findings`へroundとrow_idsを返す。
`history_command`で全ラウンドの指摘・応答へ、`repetition_guidance`で既存の反復原因の判定へ到達できる。
現在roundの未応答件数は返却件数の生成に使い、過去の指摘の件数や完成条件の一致だけから同一性を判定しない。
指摘を受領した委譲元は、修正担当への追送を確定する時点で違反規定と発生条件を比較し、修正不足・新しい要件・レビュー契約の不足を分ける。
修正担当が局所修正に入る前に、過去の応答を確認し、設計の維持・置換を判断する契機を既存サマリーへ接続し、7列TSVと応答状態を保つ。
専用の反復キーや監視を増やす案は、既存の表から得られる入力のために保存状態と記入を増やすため採らない。

再レビューは、前ラウンドの各指摘の違反した規定、発生条件、根本原因および要求した検収手段を確認してから開始する。
レビューイーが指摘の前提の不成立、対象への適用条件の不一致や検収手段の到達不能を述べた場合、レビュー担当は指摘の前提を自ら裏付け直し、成立しなければ指摘を取り下げ、同じ根本原因を別の観点から再提出しない。
裏付けの結果として前提が成立した場合だけ、観測を示して再指摘する。
この分岐はレビュー担当が自身の前回の指摘を再評価する手順である。
新しい応答状態・新しい遷移先・メインの追加介在を設けない。
レビュー指摘管理表の応答値へ保留を追加する案は、`atk review-table`の公開スキーマを変更するうえ、前提が不成立の指摘は理由を記載した不採用で表現できるため採用しない。
レビューイーの応答を契機にメインが計画・規範へ戻す案は、レビュー担当が対応結果を読む契約と重複し、誰がどの時点で何を確認して何をするかが不定になるため採用しない。

合否の判定に実機検証、完了条件、待機手順を用いる指摘は、指摘が求める検証を対象成果物の許可ツール、禁止事項、入力前提および通常の状態遷移だけで実行できるかを先に判定する。
到達不能と確定した要求は成果物の未達として扱わず、計画・規範の再設計へ返す。
到達不能の結論には、探索した実行手段と、各手段が成立しないことを示す観測の列挙を要する。
探索を課さずに到達不能を認める案は、成立する検収手段に誰も気付かないまま工程が止まるため採用しない。
判定手順は`review-standards/references/judgment-details.md`「検収手段の到達可能性」へ置く。
レビュー担当とレビューイーの双方が同じ役割中立の手順を参照する。
同節は「論理整合性と既存の仕組みの再評価」を統合して置き換えたものであり、同じ場面へ適用する節を並置しない。

第2ラウンド以降の調整は、レビュー指摘管理表の未解消行を違反した規定および発生条件で比較し、同じ2要素を持つ指摘の未解消と新たに成立した欠陥の順に判定して最初に該当した1つだけを指示する。
前者では再設計・簡素化を指示する。
後者は前回の是正が生じさせた別の欠陥と前回未走査だった直接影響範囲の欠陥であり、新たに成立した欠陥だけの是正を指示する。
遷移の判定軸をレビュー担当の候補分類と同じ2要素へそろえ、いずれの分類にも対応しない遷移を残さない。
根本原因の特定と記録はレビューイー側の職務とし、レビュー担当と第2ラウンド以降の調整はレビューイーが記録した根本原因を読む対象に限り、判定軸には用いない。
指摘の前提や要求する検収手順の成否が再検証を経ても確定しない場合は、レビュー担当が指摘を確定できずレビューを完了しないため、前提が未確定のラウンドではcheckpointが返らない。
この状態は既存の続行できない理由の受領手順で扱い、確定していない前提を解消してから回答し、解消できない場合はユーザー確認する。
前提の未確定を第2ラウンドの候補分類へ置く案は、checkpointが返らない状態では到達しないため採用しない。
ラウンド数だけを理由とする継続と自動収束は、後半ラウンドにも実害のある欠陥が現れる観測があるため採用しない。

ユーザーの是正または実際の動作確認で前提が失効した場合は、その前提だけを根拠とする指摘、修正方針および追加機構を次回レビュー前に撤去し、その前提を必要としない要求だけを再判定する。

レビューイーは、前回の是正と同じ違反した規定または同じ根本原因を示す指摘を再び受領した場合に、`agent-basics:bugfix`の原因分析の要否判定へ接続する。
2026年10月10日のユーザー指示による`agent-basics:bugfix`への集約後、同じ根本原因の問題の母集団は同スキルの`references/root-cause-remediation.md`「類似見直し」が根本原因から導き、レビューの文書は母集団を独自に定めない。
全てのレビュー修正へ恒常的な全体走査を課す案は、反復しない大多数の修正へ同じ費用を課すため採用しない。
