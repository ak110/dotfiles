# 登録全体の統括と対象別所有の設計記録

[設計記録の索引](design.md)と[継続処理の起動・隔離・制御の設計記録](design-process-loop.md)から参照する主題別の記録である。

## 登録全体の統括と対象別所有

`atk wi process-loop`はrepositoriesのうちprocess_loopが有効な登録全体を扱う唯一の常駐起動形式とする。
repositoryの編集可否、ローカルパス、process-loopの対象、検証OSを単一の設定で保持し、`atk config repos`で属性を操作する。
旧process_loop_repositoriesは既存の設定移行と同じ時点で編集可・常駐対象の登録へ移し、対象集合を保つ。
編集保護の別台帳は同じrepositoryを二重登録するため設けず、ファイル編集とgit commitの判定もこの設定を読む。
`--once`は同じ対象取得・開始gate・所有・準備・統括起動・結果検収・回収を1集合だけ実行する。
対象が0件なら待機せず終了し、未完了・所有待ち・準備失敗が残れば非0で終了する。
手動のprocess-wi all-reposはこの公開操作へ接続し、manifest付きの統括会話が対象を処理する。
所有や準備入力を手動会話内でも生成する案は、同じ排他と資源寿命の実装を増やすため採らない。
旧単一リポジトリ起動、all-reposサブコマンド、--target-repoは廃止する。
常駐cwdで既存run_process_sessionによりorchestrateの対話CLIを1つ起動し、process-wi all-reposを完遂させる。
Claudeは先頭/goal、CodexとAntigravityは生成目的文を使い、初回と同一会話のresumeで今回の集合JSONを参照する。
通常delegateとして統括を起動する案は、最上位の役割とGoal配送の例外が必要になるため採用しない。
今回の集合JSONの対象が1リポジトリなら、統括がレーン上限によらず直接処理する。
複数対象の場合は、候補数Nに対する既存上限floor((N+9)/10)が2以上の対象を対象cwdのprocess-wi担当へ委譲し、それ以外を直接処理する。
対象内の並列度と対象間の担当分離を区別し、対象1件で中間担当を起動して統括が待つだけの費用を省く。
直接処理はレーン上限に応じて通常のレーン処理か単一レーン処理へ接続し、起動したレーン担当・writerの識別子を既存の対象別結果へ記録する。
常駐の結果形式、終了確認・所有解放・回収、previousによる未完了成果の引き継ぎは維持する。
明示resumeは台帳に元集合があれば再利用し、台帳に無い会話も現在の登録集合で再開する。
会話の再開可否と、origin単位のwriter所有の保護は、それぞれ既存の解決処理が担う。

常駐が対象別所有の下でworktreeを準備し、凍結した候補、readiness、上限、所有token、lane_session_id、前回情報を渡す。
選定・計画・独立文脈レビュー・公開・CI検収は対象worktreeごとに分ける。
統括は対象の規範とプロジェクトスキルを明示的に読む。
通常のプロジェクトhookは統括cwdでは発火せず、規範と既存チェックで目的を満たす。
WorktreeCreate/Removeは既存atkの対象設定処理を使う。

開始時のmanifestは凍結した候補・所有・準備先の入力であり、統括が保存する成果はmanifestの`result_file`へ分ける。
自動目標文は、スキル所定の処理と終了準備を終えて実態に即した対象別結果を保存した時点を、統括自身の到達点とする。
続行不能の場合も理由と残工程を保存して制御を返し、全対象への`completed`の記入を要求しない。
常駐の受理・所有解放・回収は統括CLI終了後に始まるため、その検収記録を本人の終了条件に含めると循環待ちになる。
同じ時間関係を持つ定期実行や、データ変換後に別の集計ジョブが受理する構成でも、本人が保存する成果と呼出元の事後検収を分離する。
目標の削除は無人完遂の目的を失い、別の完了フラグは既存の結果記録と重複するため採らない。

統括CLI終了後に常駐が対象別結果・キュー・laneの統合状態を照合し、その巡回を終える。
結果statusにかかわらず起動は1回とし、残る対象は次巡回の新しい統括が選定する。
同じ長い会話を残件だけで再起動する方式は、次巡回の選定と責務が重なり、延期のたびに再起動防止の条件を要するため撤去する。
終了側は開始側のrepository_inputによる現行の候補・修復診断を再利用する。
当初候補でも、有効な未来cooldownや未回答UWI・外部先行項目への依存で進められなければ今回の残件から除く。
対象全体のprocessing、今回進められる当初候補、内部依存待ち、対処を要する不正metadata、未統合laneは残す。
通常受理と中断回収が同じ判定を使い、--onceもその結果に従う。
必要な判断を終えて正当に先送りした項目だけが残る場合、処理済み部分の公開・CI検収を終えたcompletedを受理する。
待機を選ぶ意味判断は既存の確認・依存・冷却の契約が所有し、常駐が自由文の再開記録や新しいフラグから推定する案は採らない。
これにより、WI自体の完成と今回の統括の処理終了を区別し、解除後は通常の候補取得から再開できる。
続行不能の場合は、その対象の入力を無進捗記録へ保存する。
同じ入力では再起動せず、WI・診断・アラートの変化または明示resumeを待つ。
記録はホストの対象別stateに置き、別ホストのWIをholdしない。
統括IDと対象別所有を分け、次巡回でも対象別のpreviousと準備済みworktree・lane_session_idを保持する。
統括と配下writerの終了を確認してから所有解放と既存laneを回収し、停止未確認、未統合、dirty、使用中は保持する。
登録・候補・回収の契約は[all-repos-orchestration.md](../../agent-toolkit/skills/process-wi/references/all-repos-orchestration.md)が所有する。

所有記録の段階は`process_loop_ownership.py`が4段階の型へ復元し、取得・更新・解放・保留の遷移を所有する。
保存JSONのbool組合せは読取境界で検証し、PID世代の生存照会は段階と別に扱う。
対象別結果は`RepositoryResult`と`RepositoryStatus`へ変換し、既存の公開キーへ射影する。
結果に含む独立投入の受付票は対象repoとの一致と永続移管記録を検証する。
製品writerの終了・公開検収を保ったまま、別寿命の投入監督へ移管した仕事を常駐の待機集合から分離するためである。
型の汎用ライブラリーや全工程を写す新しい台帳は設けない。
