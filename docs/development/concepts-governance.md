# 確定済みの方針・意向

本書は`docs/development/concepts.md`から主題別に分割した記録であり、実行時に適用する規範の正本ではない。

## 確認・合意の運用

現行の正本は、ルールファイルの「協調と自律」と、`agent-toolkit/share/rules-main.md`の「協調と自律」「ユーザー発話の解釈」にある。
確認要否の判定の正本は`agent-toolkit:confirmation-and-uwi`の`SKILL.md`「確認要否の判定」と`references/judgment.md`にある。

- 対象、操作又は設計の選択は、許容性、必要性、実装品質の順に判定する。エージェントの範囲逸脱には新しい承認制限を加えず、既存の承認判定を技術的な必要性の判定より前へ置いて対処する
  （2026年9月、利用者指示。必要性から判断を始めると、自ら採用した設計が求める追加操作を元の依頼の要件として扱うため）
- ユーザー発話は、既存の規範へ分類する前に目的、要件、対象範囲、例示の開放性、変更指示及び論理関係を保持する。
  適用する規範は優先順位で確定し、優先順位の低い旧規範の分類で要求を縮めない
  （2026年9月21日、利用者指示。既存の確認分類と旧手順を先に適用し、是正要求を狭く解釈した観測に由来する）
- 利用者の選好に依存しない技術判断（実装手順・タスク分解・委譲判断・ファイル名など）は
  確認せず自律確定する。ローカル環境の調査で確定できる事項の確認を利用者が「聞くまでもない」と是正した。
  入力資料にある実装内部の数値・対象範囲は実測へ補正し、補正の事実と根拠を成果物へ記録することも同じ判断に含む。
  依頼範囲、明示された制約及び権限の内側にある内部改善は、規模と可逆性を問わず同じ扱いとする
- 確認を発行するかは、発行条件の列挙ではなく1判定で決める。
  判定は「その問いの答えは、ユーザーだけが持つ情報（選好、認可、外部の状態、手元に無い資料）が無いと決まらないか」とする。
  確認規範へ発行条件を追記する前に、この1判定で同じ結果を導けるかを確かめる。
  出力の表示粒度・情報量の変更は単独では確認理由にしない。協調モードで可逆な選好依存の変更を事前に問う扱いは維持する
  （2026年9月26日、利用者指示。技術的に決まる事項をユーザーへ委ねた是正が2026年7月以降に6件あり、
  各回の条文追記の後も再発した観測に由来する。hookによる機械化はhookの存廃基準と衝突するため採らない）
- UWI・確認事項は前提を含む自己完結の本文とし、選択肢形式を優先する。
  外部前提待ちだけで利用者判断を含まない事項はUWIへ投入しない
- 複数の独立事項を1つの確認へ束ねず、全体への肯定を個別合意として扱わない
  （事故対策。束ねた確認への肯定が未合意事項を確定させた事例に由来）
- エージェントの推奨案を利用者が無修正で採択した合意は、能動的に指定した要件より弱い根拠として扱う
  （「推奨されてたから大して考えずに選んだ」という利用者の内省が契機）
- 「〜かも」等の提案的表現は、技術的に適切な選択を期待した提案として扱う。提案どおり採用する場合は
  確認を取り直さず、確定する成果が利用者が示した対象・手段・外部可視の結果と一致しない場合だけ
  報告・確認する。範囲の拡大と、提案を受け入れたうえで別の仕組みを上乗せしたことによる差異も
  一致しない場合に含める（2026年8月の利用者指示を、2026年9月10日の利用者指示で一致の判定へ広げた）
- 利用者が指定した手段は、明示された目的、確認済みの意向及び制約に照らし、効果、継続的な費用、安全性及び実行可能性で評価する。
  明らかに異なる手段が目的、範囲、明示された制約、権限、安全性又は利用者が直接観測する結果を変える場合は、
  代替案、根拠及びトレードオフを示して実行前に確認する。これらを変えず依頼範囲内に収まり、重要な改善が見込める場合は、
  最善の手段を実施して同じ内容を事後承認型UWIへ記録し、回答を待たずに続行する。
  例示表現が示す開放集合の内側から選ぶ手段は差異として扱わない
- 自律実行中も確認を発行してよく、回答を得られない場合はUWIへ記録して暫定判断で続行する。
  回答期限を提供しないCodexのDefault modeでは、協調モードは利用可能な構造化質問機能を選ぶ。
  選んだ機能で利用者へ直接質問して回答を待つ。
  非同期の質問発行が返す初期選択値は回答又は承認として扱わず、後続の利用者発話を質問へ対応付けて確定する。
  構造化質問を利用できない場合だけ固定書式の地の文へフォールバックする。
  自律モードは質問を発行せず、UWIへ記録して暫定判断で続行する。
  利用者接点を持たない委譲先は確認を発行せず、呼び出し元へ判断を返す。
  （105分停止の実測が契機。質問の自動継続タイムアウトを配布し、期限を提供しない実行環境では
  応答を得られないと判断した時点を契機とする。incidents.md参照）
- 合意を要する操作は、応答が無い場合でも暫定判断で合意を補わず、可逆な代替手段を採用するか当該操作だけを保留する
  （事故対策。未回答のままforce pushを試行し分類器が拒否した事例に由来。incidents.md参照）
- 消費主体がコーディングエージェントだけであるインターフェースの変更は、確認・合意の対象にしない。
  該当の判定は成果物の配布元・置き場所・名称ではなく、実行時に呼び出す主体と出力を読む主体で行う。
  `agent-toolkit/`配下が提供するコマンドライン群（`atk`の各サブコマンド、スキル配下のスクリプト）、
  MCPツールの公開名・説明・入出力スキーマ、コーディングエージェント向け文書が定める起動契約・返却形式、
  フックがコーディングエージェントへ返す通知の本文が該当する。
  ツールが実行する操作自体の危険性とユーザーの明示要件は従来の承認境界で扱う
  （2026年8月と2026年9月1日の利用者指示を、2026年9月5日に消費主体の判定を前段へ置く一般規則へ統合した）
- 承認は成立と再利用を分けて扱い、成立した承認は承認源を問わず操作、対象、影響範囲及び成立条件が同じ範囲で再確認せず実行する。人間由来のWIから承認が成立する条件は`agent-toolkit:wi-standards`を正本とする。適用範囲を限定した指示は、限定の前提の解消後と別の対象へ引き継がない
  （2026年9月1日、利用者指示。承認済みの`make update`とpushを繰り返し確認し、private-notesの競合時だけの限定指示を別リポジトリの操作へ広げた観測に由来する）
- `atk wi rm`による削除はprivate-notesリポジトリのGit履歴へ残るため、自動承認しても復旧経路を失わない
- 滅多に起こらない不整合には恒常的な拒否機構を設けず、実装時の対処へ委ねる。
  不整合の通知は警告に留める（過剰な防御を避ける利用者判断）
- `AskUserQuestion`の判断材料を本文へ自己完結させる規定の根拠は、Fableモデル固有の地の文非表示ではなく、
  ターン途中の地の文がハーネスの要約へ置換される実測とする（2026年8月31日、Claude Code v2.1.251・Fable 5で再検証）。
  Fable稼働時も地の文は表示されるため、モデル条件付きの記述へ戻さない。
  2026年9月5日には`AskUserQuestion`直前の地の文へ選択肢の前提を置いた回でも、
  ユーザーが当該地の文を読めず確認の再発行を要した。置換されない位置を事前に確定できないため、
  判断材料を地の文へ置く経路自体を採用しない
- 確認の選択肢は、案ごとに変わる外部可視の挙動（応答時間、表示順序、情報量、通知頻度など）を本文へ含める。
  当該差が本文に無いと、ユーザーは案を比較できず同じ論点の確認をやり直すことになる（2026年9月5日の観測に由来）
- ユーザーの介入・是正要求へ応答する時は現物で照合してから同意し、照合の手段と結果を応答へ書く。
  同じ論点で2回目以降の差し替えを求められた場合は、成果物を変更する前に意図を確認する。
  この想起はUserPromptSubmitのフックが、直前の通常発話から3分以上経過した通常発話へ注入する
  （2026年9月5日、利用者指示。注入の間隔は利用者が指定した）
- 協調モードのセッションは確認の回答期限を持たず、確認への回答は必ず得られることを設計上の前提とする。
  有限の回答期限を渡すのは、常駐ループが起動する自律モードのセッションだけである。
  この前提により、協調モードで回答を得られない事態に備える分岐、条文又は機構を新設しない。
  配布値と常駐実行での上書きの実測は[operations.md](operations.md)の「質問・ダイアログのタイムアウトの配布」が保持する
  （2026年9月7日、利用者指示。前提が明記されず、当該事態に備える経路の欠落を挙げる指摘が繰り返し成立した）
- 確認の同期発行の可否を、当該確認と因果関係の無い実行状態（稼働中の委譲先の有無、受領済みの差し戻しの有無）で判定しない。
  自律モードでも回答を得られる見込みがある場面では同期確認を先に発行し、回答を得られない場合は回答期限による既存のUWI退避経路で扱う
  （2026年9月15日、利用者指示。当該判定を課していた条文を撤去した。
  回答待ちの間も稼働中の委譲先へ指示を配送できることを実測した）
- Markdownとして描画されることを前提に書いた成果物の本文をユーザーへ提示する時は、フェンス付きコードブロックで囲まず地の文へそのまま出力する。原文の改変を許さない逐語引用と、コード、コマンド、設定の断片は囲む（2026年9月8日、利用者指示。囲んだ本文が記法のまま表示され、見出しと箇条書きを構造として解釈できないことに由来する）

## セキュリティと環境

現行の正本はルールファイルの「委譲時の厳守事項」、`agent-toolkit:writing-standards`の各参照資料及び
[design.md](design.md)の「管理対象一時領域」にある。

- codex呼び出しの`sandbox: danger-full-access`指定を弱めない（事故対策）。
  他の値では相手プロセスが承認待ちから復帰せず完了を検知できない。
  弱体化改変は過去に複数回発生し、利用者が都度差し戻した（incidents.md参照）。
  本方針は旧blocking MCP経路の入力契約に対するものであり、`agents_server`経路へは適用しない。
  現行の扱いは`agent-toolkit:delegation`の`delegation/references/runtime-routing.md`が定める
- サプライチェーン対策としてmiseの`minimum_release_age`を設定し、依存の即日更新を避ける
- 配布物へ波及しない依存上書きは、利用者環境の脆弱性を未解消のまま残すため
  採用しない
- Windows（CP932・PowerShell・パス区切り）での動作を常に考慮し、subprocess境界はUTF-8を明示する
  （事故対策。デコード失敗・文字化けの反復観測に由来。incidents.md参照）
- managed-tempの登録済み領域は登録簿の`path`の親を検証・列挙・回収のroot境界とし、現在の一時rootが変わっても同じ絶対pathを扱う。
  登録済み領域は最終更新から7日を超えると`atk`の実行時に自動削除する。git worktreeやリポジトリの複製を含む領域（`.git`を含む領域）は削除しない。
  実装worktreeをDockerやVMなど別namespaceへ渡す場合だけ、全消費主体から到達できる既存共有ディレクトリを読み取り専用で確認して`create --root <絶対パス>`を使う。
  同一namespaceの実装worktreeとMQ、レビュー表、CI、publishの補助領域は既定rootを維持し、Dockerの可視性を推測しない
  登録済み領域の自動回収は、記録した実行文脈と現在の実行文脈が一致し実体の消滅を確定できた場合だけ行い、回収を警告として報告する。
  確定できない登録は保持し、到達できる実行文脈での再実行を案内する。登録を失った領域は`atk managed-temp list`が絶対パスと回収方法とともに報告する。
  `atk`の共通起動では、登録を失った領域の件数と`atk managed-temp list`による確認方法だけを1件の警告として報告し、個々の絶対パスを列挙しない。
  当該警告の宛先は回収を判断できる主体に限り、`AGENT_TOOLKIT_DELEGATED_SESSION`が`1`である委譲先セッションでは出力しない
  （2026年9月、エージェント由来のAWI。所有しない領域の警告を委譲先が同一記録で2回受け取り、処置できない通知として扱う工程が生じた観測に由来する）。
  `atk managed-temp cleanup`は`--path`を省略した場合に、現在の管理対象の絶対パスを作成時刻の昇順で示して終了コード2で終わる。
  中断した後始末の消費途中状態が残る領域は通常の後始末が再開し、消費途中状態も持たない領域の回収は
  利用者が明示指定する`atk managed-temp cleanup --path <絶対パス> --recover-registry`でだけ行う
- 同一リポジトリのworktreeへ`.env`等のGit管理外の実行前提ファイルを複製する操作は、
  認証情報複製禁止の対象外とする（2026年8月、利用者指示。worktree運用の成立を優先する）。
  複製元に`.worktreeinclude`が存在しworktree作成前である場合に限り、worktree作成時の自動複製を活用する
- 動作確認目的で`.env`及び`.env.<接尾辞>`の値を追記・変更・削除する操作は、Bashの追記・`sed -i`で行う限り
  許容する（2026年8月、利用者指示。編集ツール経由の書き換えは遮断を維持し、全文置換による原本消失を防ぐ）。
  鍵・証明書は対象外とする
- 秘匿ファイルの読み取り禁止は全環境向けの配布設定へ置かない。当該ファイルを持つプロジェクトのリポジトリ直下の`.claude/settings.json`で設定する
  （2026年9月、利用者指示。`Read(*.key)`のようにディレクトリを含まないグロブが任意の深さに一致し、無関係なディレクトリ走査まで確認ダイアログの対象へ変えるため）
- コーディングエージェントの稼働状況をユーザーへ示す表示では、ユーザーに見せてはならない情報は存在しないものとして扱い、
  表示できる範囲の情報をすべて含める。
  秘匿値が現れ得ることを理由に、ツール呼び出しの引数、コマンド文字列その他の入力を表示から除かない
  （2026年9月15日、利用者指示）。
  `agents_server`のstatusline表示がツール名だけを載せ、同じツールを繰り返す区間で稼働と停止を区別できなかった観測に由来する。
  現行の実装契約は[design.md](design.md)の「agents_server sessionのstatusline表示」にある
- Claude Codeの確認ダイアログはPermissionRequestフックで無条件に許可し、許可した要求の記録だけを残す
  （2026年9月、利用者指示。auto modeでの運用を前提とし、承認の往復を無くすことを優先する）
- auto modeの許可ルールは、操作の種別と除外条件で対象を決める。remoteのホスト、由来（AWI処理かどうか）及び所有者による限定は条件として置かない
  （2026年9月17日、利用者指示。「現状のプロンプトが全体的に禁止事項が多すぎるのでいっそもっと全体的に緩和して統一感を持たせてほしい」）。
  PR/MRのマージ許可もこの方針に含め、remoteのホストで限定しない。
  2026年9月16日のAWIは、信頼境界宣言との整合を根拠にマージ許可を`github.com/ak110`配下へ限定したが、当該限定は利用者の意向と異なる。
  以降の限定の再導入は、新しい利用者の判断からだけ行う
- auto modeの許可ルールの文面は、変化しやすい識別子（サブコマンド名、オプションの完全な綴り、個別ファイルのパス）を列挙せず、操作の種別で書く
  （2026年9月17日、利用者指示。「キュー管理サブコマンドとかはころころ変わるから列挙しないでほしい」）
- 同一の変更がpushとPR/MRで重複してCIを起動することを避ける1回限りのCIスキップは許可の対象とする。
  リポジトリ又は組織の検査設定を変える操作（必須チェックの解除、branch protectionの変更、ワークフローの無効化）は許可の範囲の外に置く
  （2026年9月17日、利用者指示。一時的にCI無効でpushする手順を持つプロジェクトがあるため）
- 常駐ループのセッションで無進捗の反復を検出した場合は、通知や再促に留めず、常駐処理への中断要求と当該セッションの終了まで実行する
  （2026年9月17日、利用者指示。auto modeの拒否で工程が進まない状態が続くと、目標評価と無進捗ターンの往復がトークンを消費し続けるため）

### 補助的なブラウザー資産の配布

`atk serve`の表示を補助するMermaidのようなブラウザー資産では、取得方式と版数が可用性、供給元の信頼、表示結果を変える。
対話で確定した方式はコード近傍と本節へ理由を残し、後続のエージェント判断だけで別方式へ置き換えない。
置き換える場合は、変更後に利用者が観測する結果、採用理由及びトレードオフを事後承認型UWIで報告する。
Mermaidは`agent-toolkit/agent_toolkit/_atk/serve/static/plans.js`の`mermaid@12.0.0`とSRIを維持する。
2026年9月13日の利用者指示は常時最新版へ戻すことではなく、対話で確定した判断の無断変更を禁止し、変更時の事後承認型UWIを求めるものである。
