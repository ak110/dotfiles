# 確定済みの方針・意向

本書は`docs/development/concepts.md`から主題別に分割した記録であり、実行時に適用する規範そのものではない。

## 確認・合意の運用

現在はルールファイルの「協調と自律」と、`agent-toolkit/share/rules-main.md`の「協調と自律」「ユーザー発話の解釈」が定める。
確認要否の判定は`agent-toolkit:user-confirmation-and-report`の`SKILL.md`「確認要否の判定」と`references/judgment.md`が定める。

- 対象、操作または設計の選択は、許容性、必要性、実装品質の順に判定する。エージェントの範囲逸脱には新しい承認制限を加えず、既存の承認判定を技術的な必要性の判定より前へ置いて対処する
  （2026年9月、ユーザー指示。必要性から判断を始めると、自ら採用した設計が求める追加操作を元の依頼の要件として扱うため）
- ユーザー発話は、既存の規範へ分類する前に目的、要件、対象範囲、例示の開放性、変更指示および論理関係を保持する。
  適用する規範は優先順位で確定し、優先順位の低い旧規範の分類で要求を縮めない
  （2026年9月21日、ユーザー指示。既存の確認分類と旧手順を先に適用し、是正要求を狭く解釈した観測に由来する）
- ユーザーの選好に依存しない技術判断（実装手順・タスク分解・委譲判断・ファイル名など）は
  確認せず自律確定する。ローカル環境の調査で確定できる事項の確認をユーザーが「聞くまでもない」と是正した。
  入力資料にある実装内部の数値・対象範囲は実際の値へ補正し、補正の事実と根拠を成果物へ記録することも同じ判断に含む。
  依頼範囲、明示された制約および権限の内側にある内部改善は、規模と可逆性を問わず同じ扱いとする
- 確認を発行するかは、発行条件の列挙ではなく1判定で決める（次項で改訂した。本項は改訂前の経緯として残す）。
  判定は「ユーザーだけが持つ値（選好、認可、外部の状態、手元に無い資料）の違いで、推奨案が変わるか」とする。
  判定の前に、選択肢を依頼の目的と要件、ユーザーが示した判断基準、QCD、明文化された方針の順で順位付ける（2026年10月2日、ユーザー指示により明文化された方針をQCDの下へ移した）。
  複数案がある、既存の規範を変える、他の画面や工程へ波及するなどの表面属性は、それだけでは確認の理由にしない。
  確認規範へ発行条件を追記する前に、この1判定で同じ結果を導けるかを確かめる。
  出力の表示粒度・情報量の変更は単独では確認理由にしない。協調モードで可逆な選好依存の変更を事前に問う扱いは維持する
  （2026年9月26日、ユーザー指示。技術的に決まる事項をユーザーへ委ねた是正が2026年7月以降に6件あり、
  各回の条文追記の後も再発した観測に由来する）。
  確認の要否は推奨案の有無という判断を要し、フックの入力から機械的に判定できないため、hookによる機械化は採らない。
  問いの形は、2026年9月30日のユーザー指示「聞くべきじゃないことをユーザーに聞くケースは多すぎる」で推奨案が変わるかを問う形へ改めた。
  直近30日の`AskUserQuestion`507回のうち18セッション・20件でユーザーが是正し、その多くでエージェントが推奨案を持ったまま確認へ回していた
- 前項の1判定は、2026年10月3日に目的・期待結果・認可の確定と、その範囲内の手段の選択を分ける判定へ改めた。読み手は確認要否を判定する全ての実行主体と、その判定を参照するWI・UWI・ホスト別規範の編集者とする。
  ユーザー介入や意図と異なる実装を可能な限り避けることは、質問を減らすことより優先する。必要な確認はそのための正常な協働であり、自律遂行と質問の削減は目的・要件とQCDを守るための手段とする。
  目的が明確で認可済みの範囲の技術事項は従来どおり自ら確定し、技術判断をユーザーへ委ねる反復を防ぐ前項の目的は保つ。推奨案を持てることや未知の値を書けないことを、目的・認可の確定とみなさない。
  実装の選択では、ユーザーが表現しきれていない要件・要求も利用場面から評価する。既存仕様との整合や算術の正しさは、目的への適切さとは別に判断する。表現されていない要求の推論は、明示要件の上書きや依頼外の機能追加を認可しない。
  2026年10月3日、ユーザーがGLATasksで字句どおりの達成だけを優先した実装を批判し、「自律遂行」と「ユーザー確認」の優先順位の解釈を問い、手順だけの浅い分析を是正した発話に由来する（対応commit `6566f6a0e`）
- ユーザーへの働きかけは、判断を求める「ユーザー確認」と判断を求めずに結果を届ける「ユーザーへの報告」の工程名で書く。
  手段（構造化質問、事前承認型UWI、事後承認型UWI、報告用UWIなど）の選択は`agent-toolkit:user-confirmation-and-report`「手段の選択」へ集める。
  呼び出し側の条文は工程名で書く。
  報告は向きを示して「ユーザーへの報告」「ユーザーからの報告」と書き、向きを示さない複合語は使わない。
  手段名が各所へ散在し、モードとホストの条件に適合しない確認を招いたため、2026年9月30日のユーザー指示で集約した。
  同日の指示により向きを示さない語を禁止し、確認とUWIを扱うスキルを工程名を表す現在の`agent-toolkit:user-confirmation-and-report`へ改名した。
  自律モードの確認手段は、確認の種類と実際に働く回答期限で分ける。事前承認は回答期限が働く実行環境（`atk wi process-loop`が起動したセッション）でだけその場で質問し、期限が働かない実行環境の事前承認と、事前承認以外の回答を待つ確認は最初から事前承認型UWIへ記録する。事後承認は回答を待たずに事後承認型UWIへ記録し、作業を止めない。
  2026年9月30日のユーザー指示は、自律モードでも構造化質問を使えるとして`agent-toolkit:realign-with-user`の認識合わせを対象に含めるよう求めたものであり、同スキルは自律モードでもその場で質問する。
  同日のcommit 4b838401bfは、この指示を確認手段の共通表全体へ広げ、事後承認もその場の質問へ変えた。この一般化はエージェントの判断であり、回答期限を無期限とする配布設定のもとで手動起動のprocess-wiが回答まで止まり得たため、2026年10月4日のユーザー回答で現在の区分へ改めた。
  Codex Default modeの期限なしの例外、報告用UWIと個別UWIの用途は保持する
- UWI・確認事項は前提を含む自己完結の本文とし、選択肢形式を優先する。
  外部前提待ちだけでユーザー判断を含まない事項はUWIへ投入しない
- 複数の独立事項を1つの確認へ束ねず、全体への肯定を個別合意として扱わない
  （障害対策。束ねた確認への肯定が未合意事項を確定させた事例に由来）
- エージェントの推奨案をユーザーが無修正で採択した合意は、能動的に指定した要件より弱い根拠として扱う
  （「推奨されてたから大して考えずに選んだ」というユーザーの内省が契機）
- 「〜かも」等の提案的表現は、技術的に適切な選択を期待した提案として扱う。提案どおり採用する場合は
  確認を取り直さず、確定する成果がユーザーが示した対象・手段・外部可視の結果と一致しない場合だけ
  報告・確認する。範囲の拡大と、提案を受け入れたうえで別の仕組みを上乗せしたことによる差異も
  一致しない場合に含める（2026年8月のユーザー指示を、2026年9月10日のユーザー指示で一致の判定へ広げた）
- ユーザーが指定した手段は、明示された目的、確認済みの意向および制約に照らし、効果、継続的な費用、安全性および実行可能性で評価する。
  明らかに異なる手段が目的、範囲、明示された制約、権限、安全性またはエンドユーザーが直接観測する結果を変える場合は、
  代替案、根拠およびトレードオフを示して実行前に確認する。これらを変えず依頼範囲内に収まり、重要な改善が見込める場合は、
  最善の手段を実施して同じ内容を事後承認型UWIへ記録し、回答を待たずに続行する。
  例示表現が示す開放集合の内側から選ぶ手段は差異として扱わない
- 自律実行中は、回答期限が働く実行環境の事前承認に限って確認をその場で発行し、回答を得られない場合はUWIへ記録して暫定判断で続行する。期限が働かない実行環境では、最初からUWIへ記録する。
  回答期限を提供しないCodexのDefault modeでは、協調モードは利用可能な構造化質問機能を選ぶ。
  選んだ機能でユーザーへ直接質問して回答を待つ。
  非同期の質問発行が返す初期選択値は回答または承認として扱わず、後続のユーザー発話を質問へ対応付けて確定する。
  構造化質問を利用できない場合だけ固定書式の地の文へフォールバックする。
  自律モードは質問を発行せず、UWIへ記録して暫定判断で続行する。
  ユーザー接点を持たない委譲先は確認を発行せず、呼び出し元へ判断を返す。
  （105分停止した事象が契機。質問の自動継続タイムアウトを配布した。incidents.md参照。
  期限を提供しない実行環境の自律モードで最初からUWIへ記録する扱いは、2026年10月4日のユーザー回答による）
- 合意を要する操作について応答が無い場合、暫定判断で合意を補わない。可逆な代替手段を採用するか、回答を要する操作だけを保留する
  （障害対策。未回答のままforce pushを試行し分類器が拒否した事例に由来。incidents.md参照）
- 消費主体がコーディングエージェントだけであるインターフェースの変更は、確認・合意の対象にしない。
  該当の判定は成果物の配布元・置き場所・名称ではなく、実行時に呼び出す主体と出力を読む主体で行う。
  `agent-toolkit/`配下が提供するコマンドライン群（`atk`の各サブコマンド、スキル配下のスクリプト）、
  MCPツールの公開名・説明・入出力スキーマ、コーディングエージェント向け文書が定める起動契約・返却形式、
  フックがコーディングエージェントへ返す通知の本文が該当する。
  ツールが実行する操作自体の危険性とユーザーの明示要件は従来の承認境界で扱う
  （2026年8月と2026年9月1日のユーザー指示を、2026年9月5日に消費主体の判定を前段へ置く一般規則へ統合した）
- 人間が確定した判断は、目的・要件・ユーザーが観測する結果に関する判断と、手段に関する方針（hookの範囲、書式、工程の手順、ツールや担当の段位の選択など）に分けて扱う。
  目的側の判断の変更は事前承認とし、手段に関する方針は規範と同じくQCDの下に置いて、外れる場合は逸脱1件ごとに事後承認の確認を発行する。
  どちらか判別できない場合は目的側として事前承認とする
  （2026年10月2日、ユーザー回答。確定済みの方針を全てQCDの下に置く案と、全て事前承認のまま保つ案から、手段の方針だけをQCDの下に置く案を選んだ）。
  現行の規定は`agent-toolkit:user-confirmation-and-report`の`references/judgment.md`「認可を要する操作」と`references/approval-scope.md`にある
- 承認は成立と再利用を分けて扱い、成立した承認は承認源を問わず操作、対象、影響範囲および成立条件が同じ範囲で再確認せず実行する。人間由来のWIから承認が成立する条件は`agent-toolkit:wi-standards`が定める。適用範囲を限定した指示は、限定の前提の解消後と別の対象へ引き継がない
  （2026年9月1日、ユーザー指示。承認済みの`make update`とpushを繰り返し確認し、private-notesの競合時だけの限定指示を別リポジトリの操作へ広げた観測に由来する）
- `atk wi rm`による削除はprivate-notesリポジトリのGit履歴へ残るため、自動承認しても復旧手段を失わない
- 滅多に起こらない不整合には恒常的な拒否機構を設けず、実装時の対処へ委ねる。
  不整合の通知は警告に留める（過剰な防御を避けるユーザー判断）
- `AskUserQuestion`の判断材料を本文へ自己完結させる規定の根拠は、Fableモデル固有の地の文非表示ではなく、
  ターン途中の地の文がハーネスの要約へ置換される事象の確認結果とする（2026年8月31日、Claude Code v2.1.251・Fable 5で再検証）。
  Fable稼働時も地の文は表示されるため、モデル条件付きの記述へ戻さない。
  2026年9月5日には`AskUserQuestion`直前の地の文へ選択肢の前提を置いた回でも、
  ユーザーは直前の地の文を読めず、確認を再発行する必要があった。置換されない位置を事前に確定できないため、
  判断材料を地の文へ置く方法自体を採用しない
- 確認の選択肢は、案ごとに変わる外部可視の挙動（応答時間、表示順序、情報量、通知頻度など）を本文へ含める。
  案ごとの違いを本文で示さないと、ユーザーは案を比較できず同じ論点の確認をやり直すことになる（2026年9月5日の観測に由来）
- ユーザーの介入・是正要求へ応答する時は現物と一致するか確かめてから同意し、確認の手段と結果を応答へ書く。
  同じ論点で2回目以降の差し替えを求められた場合は、成果物を変更する前に意図を確認する。
  この想起はUserPromptSubmitのフックが、直前の通常発話から3分以上経過した通常発話へ注入する
  （2026年9月5日、ユーザー指示。注入の間隔はユーザーが指定した）
- 協調モードのセッションは確認の回答期限を持たず、確認への回答は必ず得られることを設計上の前提とする。
  有限の回答期限を渡すのは、常駐ループが起動する自律モードのセッションだけである。
  この前提により、協調モードで回答を得られない事態に備える分岐、条文または機構を新設しない。
  配布値と常駐実行での上書きの検証結果は[operations.md](operations.md)の「質問・ダイアログのタイムアウトの配布」が保持する
  （2026年9月7日、ユーザー指示。この前提が明記されていなかったため、協調モードで回答を得られない事態に備える処理が欠けているという指摘が繰り返し成立した）
- 確認を同期発行できるかどうかは、確認自体と因果関係の無い実行状態（稼働中の委譲先の有無、受領済みの差し戻しの有無）で判定しない。
  自律モードでは回答期限が働くかを先に判定し、期限が働く実行環境の事前承認だけ同期確認を発行する。回答を得られない場合は回答期限によるUWI退避手順で扱う
  （2026年9月15日、ユーザー指示。同期確認の可否を実行状態で判定する条文を撤去した。
  回答待ちの間も稼働中の委譲先へ指示を配送できることを実際に確認した）
- Markdownとして描画されることを前提に書いた成果物の本文をユーザーへ提示する時は、フェンス付きコードブロックで囲まず地の文へそのまま出力する。原文の改変を許さない逐語引用と、コード、コマンド、設定の断片は囲む（2026年9月8日、ユーザー指示。囲んだ本文が記法のまま表示され、見出しと箇条書きを構造として解釈できないことに由来する）

## セキュリティと環境

現行の規定はルールファイルの「委譲時の厳守事項」、`agent-toolkit:writing-standards`の各参照資料および
[design-storage.md](design-storage.md#managed-temp)の「managed-temp」にある。

- codex呼び出しの`sandbox: danger-full-access`指定を弱めない（障害対策）。
  他の値では相手プロセスが承認待ちから復帰せず完了を検知できない。
  弱体化改変は過去に複数回発生し、ユーザーが都度差し戻した（incidents.md参照）。
  本方針は旧blocking MCP連携の入力契約に対するものであり、`agents_server`連携へは適用しない。
  現行の扱いは`agent-toolkit:delegation`の`delegation/references/runtime-routing.md`が定める
- サプライチェーン対策としてmiseの`minimum_release_age`を設定し、依存の即日更新を避ける
- 配布物へ波及しない依存上書きは、エンドユーザー環境の脆弱性を未解消のまま残すため
  採用しない
- Windows（CP932・PowerShell・パス区切り）での動作を常に考慮し、subprocess境界はUTF-8を明示する
  （障害対策。デコード失敗・文字化けの反復観測に由来。incidents.md参照）
- managed-tempの登録済み領域は登録簿の`path`の親を検証・列挙・回収のroot境界とし、現在の一時rootが変わっても同じ絶対pathを扱う。
  登録済み領域は最終更新から7日を超えると`atk`の実行時に自動削除する。git worktreeやリポジトリの複製を含む領域（`.git`を含む領域）は削除しない。
  実装worktreeをDockerやVMなど別namespaceへ渡す場合だけ、全消費主体から到達できる既存共有ディレクトリを読み取り専用で確認して`create --root <絶対パス>`を使う。
  同一namespaceの実装worktreeとMQ、レビュー表、CI、publishの補助領域は既定rootを維持し、Dockerの可視性を推測しない
  登録済み領域の自動回収は、記録した実行文脈と現在の実行文脈が一致し実体の消滅を確定できた場合だけ行い、回収を警告として報告する。
  確定できない登録は保持し、到達できる実行文脈での再実行を案内する。登録を失った領域は`atk managed-temp list`が絶対パスと回収方法とともに報告する。
  `atk`の共通起動では、登録を失った領域のうち最終更新から7日を超えても自動削除されずに残った件数と`atk managed-temp list`による確認方法だけを1件の警告として報告し、個々の絶対パスを列挙しない。
  回収を判断できる主体だけへこの警告を出力し、`AGENT_TOOLKIT_DELEGATED_SESSION`が`1`である委譲先セッションでは出力しない
  （2026年9月、エージェント由来のAWI。所有しない領域の警告を委譲先が同一記録で2回受け取り、処置できない通知として扱う工程が生じた観測に由来する）。
  `atk managed-temp cleanup`は`--path`を省略した場合に、現在の管理対象の絶対パスを作成時刻の昇順で示して終了コード2で終わる。
  中断した後始末の消費途中状態が残る領域は通常の後始末が再開し、消費途中状態も持たない領域の回収は
  ユーザーが明示指定する`atk managed-temp cleanup --path <絶対パス> --recover-registry`でだけ行う。
  ただし、一時rootを指定しない場合に使う場所の直下で登録を失った領域は、所有を確かめられなくても他の作業が使用中のもの以外を`atk`の実行時に自動で削除する
  （2026年10月2日、ユーザー回答。managed-tempはユーザーが作成せず、各所にゴミが残る方が有害であるため）
- 同一リポジトリのworktreeへ`.env`等のGit管理外の実行前提ファイルを複製する操作は、
  通常の作業環境準備として扱う（2026年8月のユーザー指示でworktree運用の成立を優先し、2026年10月1日のユーザー指示で作業ツリー内の秘匿扱いを解除した）。
  複製元に`.worktreeinclude`が存在しworktree作成前である場合に限り、worktree作成時の自動複製を活用する
- Git作業ツリー内には、エージェントへ隠す必要がある本物の秘匿値を置かない運用を前提とし、全ファイルを通常の読取・編集・複製・全文比較・出力で扱う。
  gitignore対象の.env、鍵、証明書などもこの範囲へ含め、作業ツリー外の認証情報を参照する場合は実体の位置で内外を判定する
  （2026年10月1日、ユーザー指示と確認回答。作業ツリー内を含む全文読取禁止と、比較用複製だけの例外を改めた）。
  dotfilesの配布設定のautoMode.environmentへもこの運用前提を加え、業務用・私用の全プロジェクトへ適用する（同日のユーザー回答）。
  作業ツリー外の秘匿値ファイルでは全文の読み取りと出力の禁止を維持し、ホーム配下の認証情報の複製、移動および別領域への保存も禁止する。
  現行の規定は`agent-toolkit:secret-files`と`agent-toolkit:delegation`の`references/mandatory-rules.md`にある
- 2026年8月のユーザー指示は、当時秘匿ファイルとして扱っていた作業ツリー内の`.env`および`.env.<接尾辞>`について、動作確認目的の値の追記・変更・削除をBashの追記・`sed -i`で行う限り許容するものだった（鍵・証明書は対象外）。
  2026年10月1日のユーザー指示で作業ツリー内の秘匿扱いを解除したため、作業ツリー内の`.env`は通常の編集で扱う。
  作業ツリー外の`.env`を動作確認のために書き換える場面は関連履歴と現行記録から確認されず、その書換を許す規定は置かない。
  秘匿ファイルの読取と編集の遮断はauto mode classifierと権限設定が担い、hookでは判定しない（2026年9月26日、ユーザー指示）
- 秘匿ファイルの読み取り禁止は全環境向けの配布設定へ置かない。秘匿ファイルを持つプロジェクトでは、リポジトリ直下の`.claude/settings.json`で設定する
  （2026年9月、ユーザー指示。`Read(*.key)`のようにディレクトリを含まないグロブが任意の深さに一致し、無関係なディレクトリ走査まで確認ダイアログの対象へ変えるため）
- コーディングエージェントの稼働状況をユーザーへ示す表示では、ユーザーに見せてはならない情報は存在しないものとして扱い、
  表示できる範囲の情報をすべて含める。
  秘匿値が現れ得ることを理由に、ツール呼び出しの引数、コマンド文字列その他の入力を表示から除かない
  （2026年9月15日、ユーザー指示）。
  `agents_server`のstatusline表示がツール名だけを載せ、同じツールを繰り返す区間で稼働と停止を区別できなかった観測に由来する。
  現行の実装契約は[design-agents-runtime.md](design-agents-runtime.md#agents_server-sessionのstatusline表示)の「agents_server sessionのstatusline表示」にある
- Claude Codeの確認ダイアログはPermissionRequestフックで無条件に許可し、許可した要求の記録だけを残す
  （2026年9月、ユーザー指示。auto modeでの運用を前提とし、承認の往復を無くすことを優先する）
- auto modeの許可ルールは、操作の種別と除外条件で対象を決める。remoteのホスト、由来（AWI処理かどうか）および所有者による限定は条件として置かない
  （2026年9月17日、ユーザー指示。「現状のプロンプトが全体的に禁止事項が多すぎるのでいっそもっと全体的に緩和して統一感を持たせてほしい」）。
  PR/MRのマージ許可もこの方針に含め、remoteのホストで限定しない。
  2026年9月16日のAWIは、信頼境界宣言との整合を根拠にマージ許可を`github.com/ak110`配下へ限定した。しかし、その限定はユーザーの意向と異なる。
  以降の限定の再導入は、新しいユーザーの判断からだけ行う
- auto modeの許可ルールの文面は、変化しやすい識別子（サブコマンド名、オプションの完全な綴り、個別ファイルのパス）を列挙せず、操作の種別で書く
  （2026年9月17日、ユーザー指示。「キュー管理サブコマンドとかはころころ変わるから列挙しないでほしい」）
- 同一の変更がpushとPR/MRで重複してCIを起動することを避ける1回限りのCIスキップは許可の対象とする。
  リポジトリまたは組織のチェック設定を変える操作（必須チェックの解除、branch protectionの変更、ワークフローの無効化）は、この許可に含めない
  （2026年9月17日、ユーザー指示。一時的にCI無効でpushする手順を持つプロジェクトがあるため）
- 常駐ループのセッションで無進捗の反復を検出した場合は、通知や再促に留めず、常駐処理へ中断を要求し、セッションが終了するまで処理する
  （2026年9月17日、ユーザー指示。auto modeの拒否で工程が進まない状態が続くと、目標評価と無進捗ターンの往復がトークンを消費し続けるため）
- エージェントが自ら作成したtmuxセッションで対話CLIを起動し、キー入力の送信と画面の取得で検証する操作は、許可ルール`Session And Delegation Control`の対象とする
  エージェント自身のpane操作と、ユーザーが作成した既存セッションの操作は対象に含めない。これらは既定の判定に委ねる
  （2026年9月30日、ユーザー指示。検証の送信操作が`Tmux Self Drive`で拒否された観測に由来する）
- エージェント、その委譲先、起動したテスト・スクリプト・ツールの誤操作が変更した範囲を記録された変更前の値へ戻す操作は、許可ルール`Agent Mistake Recovery`の対象とする。
  置き場所と共有の有無を問わず、ユーザーの承認を待たない
  （2026年10月4日、ユーザー指示。「エージェントが間違えたものを戻すのは自動でやってもらわなきゃ困る」「share\\claude_settings_json_managed.jsonに追記して」）

  ```text
  あとtmuxを使った検証は今後も自動でやってほしいので許可ルールの追加もAWI投入してほしい
  ```

### 補助的なブラウザー資産の配布

`atk serve`の表示を補助するMermaidのようなブラウザー資産では、取得方式と版数が可用性、供給元の信頼、表示結果を変える。
対話で確定した方式はコード近傍と本節へ理由を残し、後続のエージェント判断だけで別方式へ置き換えない。
置き換える場合は、変更後にエンドユーザーが観測する結果、採用理由およびトレードオフを事後承認型UWIで報告する。
Mermaidは`agent-toolkit/agent_toolkit/_atk/serve/static/plans.js`の`mermaid@12.0.0`とSRIを維持する。
2026年9月13日のユーザー指示は常時最新版へ戻すことではなく、対話で確定した判断の無断変更を禁止し、変更時の事後承認型UWIを求めるものである。
