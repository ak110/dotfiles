# 公開工程の検証の設計記録

[設計記録の索引](design.md)と[branch・CI所有権・公開・終了の設計記録](design-release.md)から参照する主題別の記録である。

## 公開工程

### 検証

レーンは計画の`## 検証`の`変更範囲の検証`行が挙げる検証だけを実行し、対象リポジトリ全体の検証はレーンで実行しない。
CIが全体を担う公開先では、レーン内・統合時・公開前とも変更箇所と特定した利用側の試験・lintだけを実行する。
全体の試験・静的検査はpush後のCIで判定し、ローカルではCIが実行しないチェックもプロジェクト手順に従って補う。
CIが実行しないチェックの集合は、プロジェクト規範の定めか、CI定義の起動形・有効なチェックの集合・各チェックが読む設定・実行環境の比較で求める。
CIが無い、または公開先でCIが実行されない場合の全体検証は、公開工程の条件に従ってpush前に1回実行する。

2026年11月の巡回で、この変更より前に統合した4レーンの保存済み成功記録には、同じ`uv run --frozen pytest -v -p no:cacheprovider agent-toolkit`があった。
次の値は最後に成功した各1回の処理区間であり、失敗した試行や統合全体の時間を足したものではない。

| レーン | コマンド本体（秒） | 保存記録の経過（秒） |
| --- | --- | --- |
| 01 | 761.901 | 761.904 |
| 02 | 4410.399 | 4410.606 |
| 04 | 595.387 | 595.388 |
| 05 | 566.975 | 566.976 |

原記録はリポジトリ外のレーン所有記録と各検証の実行記録で、いずれも終了0だった。
この値は同条件の新旧対照ではなく、統合のたびに繰り返していた作業の変更前の所要として保持する。
限定した検証への変更後の所要は統合が終わってから観測し、短縮を仮定した値は置かない。
CI定義の判定は、承認済み公開先のforge・repositoryと対象commitに対応する定義を使う。
共通の判断は`agent-toolkit:commit`の`references/push-and-ci.md`「公開先に対応するCI定義の判定」が持ち、publishと公開担当の生成側・メインの受理側が参照する。
GitHubではworkflow直下のYAML blobを候補とし、READMEや入れ子のYAMLは数えない。
GitLabでは有効project設定が選ぶ独自CI設定と継承するAuto DevOpsも判定する。
別forgeの定義を合計する案は、混在forkで実行されない定義をCIありの根拠にするため採らない。
GitLabの標準ファイルだけで不在を決める案も、別projectや外部URLの設定を見逃すため採らない。
設定の構造は[Projects API](https://docs.gitlab.com/api/projects/)と[独自CI設定](https://docs.gitlab.com/ci/pipelines/settings/#specify-a-custom-cicd-configuration-file)、[Auto DevOps](https://docs.gitlab.com/topics/autodevops/)の仕様に従う。

有効な証拠で定義不在を確定した場合は、ローカル全体検証の成功と組にして「CI定義なし」を受理する。
定義不在、トリガーによるrun未登録、権限や到達性による未判定を分ける。
ローカル全体検証の成功は照会不能なCIの成功を代替せず、全体検証が失敗した場合は別の未完了として是正する。
`wait_ci.py`の非成功終了は保持し、監視の終了を公開工程の正常完了へ読み替えない。
CIと同じチェックをpushの前に重ねると、重複する検証の所要時間だけCIの開始が遅くなる。
一方、CIが実行しないチェックまでCIへ委ねると、その種類の失敗が公開後まで残る。
レーンの変更範囲の検証は、変更を読む側のテストを機構の類型で集める一般則（`agent-basics:check-execution`の`references/verification-scope.md`）で選ぶ。
確定的な回帰をpush前に止める役割はこの対象選定が担い、プロジェクト側は類型ごとの値（マーカー名、コマンド、パス）だけを持つ。
対象選定をプロジェクト固有の規定へ事象ごとに追加する運用では、表面構造が異なる次の事象を毎回被覆できなかった。
pushの前に実行したチェックが失敗した場合はCI修正と同じ手順へ進み、pushとCIの往復を経ずに修正する。
