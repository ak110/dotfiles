# 原因分析・レビュー監査の設計記録

本書は[設計記録の索引](design.md)から主題別に分割した記録であり、機構の目的、構造の理由、知識境界と却下した代替案を保持する。
実行時に適用する規範は、各節が参照する現行のルールファイルとスキルが定める。

## バグ調査の原因分析機構

計画ファイル（バグ）は、原因分析表と調査表の2表でバグ単位を表す。
原因分析表は`要因系統`、`L1 現象`、`L2 判断`、`L3 構造`、`L4 システム`の5列に、
`実装に起因する要因`と`検出に至らなかった要因`の2行を持つ。
調査表は`項目`・`内容`の2列に8行を持つ。

段階を列として持つのは、各セルがどの問いへの答えかを表構造から確定するためである。
行名の列挙だけで記録対象を示す方式では、各記述がどの深さに到達したかを起草側もレビュー側も判定できず、
原因が事象の言い換えで終了する。
原因分析の停止条件（L3で同じ失敗構造を断てる場合は止め、根拠を記録する）も
到達段を構造から解釈できることを前提とする。

知識境界は次のとおり分ける。
原因分析の段階、品質確認、再発防止の優先順位、再発防止策の必須性と
UWI終了の判断基準は`agent-basics:bugfix`が定める。
書式と自動チェックは`agent-toolkit/agent_toolkit/_plan/structure/constants.py`が担う。
計画側の配置契約は`agent-toolkit:write-plan`の計画ファイル作成基準が持つ。
`agent-toolkit:review-session`は問題候補の列挙と
`agent-basics:bugfix`の起動だけを持ち、再発防止策の必須性を独自に定めない。
振り返りを経由しないバグ対応にも同じ必須性を適用するためである。

調査表の8行は、根本原因を原因分析表の到達した最深段のセルへ、原因分析の品質確認を原因分析の工程へ、設計意図の記録を再発防止策の記載内容へ移して得た。
同じ内容を調査表と原因分析表の双方へ書かせる行を残すと、どちらに従うべきか起草側が判定できないためである。
統廃合前の12行の調査表と、原因分析表を持たない14行の旧調査表は計画構造の自動チェックの読み取り互換として受理する。
実装が完了するまで計画と計画ファイル（バグ）を保持する規定があり、改訂時点で未完了の計画が計画構造の自動チェックに失敗するためである。

却下した代替案は2つある。
1つはL1からL4を調査表の行へ展開して8行を追加する案である。
系統と段階の対応が行名の接頭辞にしか現れず、到達段の判定が構造から確定しないため採らない。
もう1つは表構造を変えず既存3区分の記載内容の説明を詳細化する案である。
記載基準の不明瞭さを説明の追加で解消できるという前提は、同じ欠陥を生んだ現行構造の前提と同じであるため採らない。

類似見直しで履歴を遡る期間（直近7日間）は`agent-basics:bugfix`の`references/root-cause-remediation.md`「類似見直し」の母集団の定義へ置き、記録と返却は既存の`類似見直し結果`行と調査担当の`類似見直し:`欄へ収める。
期間は母集団の範囲を決める判断であり、呼び出し側の工程ごとに定めると適用条件が一致しなくなるためである。
欄を増やさないのは、期間と見直し対象外とした範囲が母集団の根拠と同じ記録に属するためである。

類似見直し観点は原因単位から対象と探す問題を導き、重大度等の補足に置き換えない。
確定・仮説・未確認・該当なしを区別し、根拠のある仮説は既存認可とQCDの範囲で改善の採否へ接続する。
Qの確保に必要な複数の観点と再発防止策を組み合わせられるが、候補の一律列挙や個数の固定は設けない。

類似見直しの範囲と観点の妥当性は、起点の問題を知らない新規担当が同じ問題を摘出できるかで確かめる。
問題を知る担当は、記述に無い条件を自分の知識で補えるため、独立した走査へ機構の記述と素材だけを渡す。
是正済みの場合は問題が残る版を素材へ含め、返却を現行へ対応付ける。
手順の定義はbugfixの「類似見直し」だけが持ち、呼び出す工程は参照と既存の記録・返却行で接続する。
自分自身の点検、同じ担当の継続、0件の場合だけの再検討では、別の対象を摘出しながら起点問題を検出できない範囲・観点の誤りを検出できない。
起点問題を伏せた独立走査の適用は、2026年10月15日の重大度別方針によるbugfixの共通定義に従う。
軽微な問題の限定探索には一律に追加しない。

## 自動コードレビュー監査の判定済み記録

目的は`agent-toolkit:process-wi`の自動コードレビュー監査が毎セッションで全Pull Requestのreview本文を再判定する状態を解消し、判定の作業量がPull Requestの累積件数へ比例しない形にすることである。
構造の理由は、判定の入力集合を外部サービス側の状態だけで決めず、自セッション側の処理済み記録との差分で決める点にある。
review threadは解決状態を持つが、inline commentもreview threadも伴わないreview本文は対応する状態を持たない。
このため取得は全Pull Requestのまま維持し、判定だけを差分へ限定する。
取得の負荷は、横断クエリーが1回に受け取るPull Requestの件数で調整する。
前回実行時刻を境界として更新日時の新しい側だけを取得する増分取得は採用しない。
要修正と分類した指摘のthreadを解決しない運用のため、指摘を含むPull Requestの更新日時が進まず、境界より古い側に未処置の指摘が残る。
取りこぼしを防ぐには未処置のPull Request集合と境界時刻を保存し、監査が途中で失敗した場合の整合も維持する必要があり、恒常的な状態が増える。
記録先は`atk config get state_dir`が返す状態ディレクトリとし、`atk review-audit`が読み書きする。
対象リポジトリ配下へ置く案は、監査が成果物を変更するため採用しない。
private-notesへ置く案は、監査のたびにキュー操作とリモート同期が増えるため採用しない。
知識境界として、記録の有無を判定へ反映する手順は`agent-toolkit/skills/process-wi/references/github-copilot-review-audit.md`が持つ。
記録の保存形式とパス解決は`agent-toolkit/agent_toolkit/_atk/review_audit.py`が持つ。
未処置対象の取得も`atk review-audit pending`が持つ。
全Pull Requestのreviewとreview threadをpagination終端まで取得し、判定済みreviewを除いた結果を構造化して返す。
未判定reviewと未解決のCopilot由来thread、未判定のDependabotアラートがいずれも0件なら、`process-wi`は高コストの監査担当を起動しない。
`merge-pr`も対象PRが含まれなければ取得と判定を省く。
機能の有効状態で判定する案は、公開APIが無く、非公開APIの契約種別からもレビューの到着を判定できないため採用しない。
記録を無効化する機構は設けない。
記録した分類は現行成果物から再導出できる補助情報であり、成果物の変更で再判定が必要になった指摘は別のdatabaseIdを持つ新しいreviewとして到着するためである。
記録時のHEADを併記して差分がある場合に無効化する案は採用しない。
ベースbranchがほぼ毎セッション進むため、記録がほぼ常に無効となり目的を達成しないためである。

判定結果は`atk review-audit`の判定記録（`review-audit.json`）に加えて対象GitHubリポジトリへも残す。
目的は判定の妥当性をユーザーと後続のセッションがGitHubのPull Request画面だけで確認できるようにすることである。
構造の理由は、分類と根拠を保持する主体を、判定を再導出できる索引である`review-audit.json`と、人間向けの基準となる記録であるGitHubの本文へ分けた点にある。
未解決のreview threadへは`addPullRequestReviewThreadReply`で分類と根拠を返信してから`resolveReviewThread`で解決し、threadを伴わないreview本文へは`gh pr comment`で投稿する。
知識境界として、書き込みの手順と承認の扱いは`agent-toolkit/skills/process-wi/references/github-copilot-review-audit.md`が持つ。
監査担当の実行範囲は`agent-toolkit/skills/process-wi/references/review-audit-launch.md`が持つ。
`dismissPullRequestReview`で分類を残す案は、Copilotのreviewが`COMMENTED`状態で到着し、`dismissPullRequestReview`が`COMMENTED`状態を受理しないため採用しない。
`resolveReviewThread`の`resolutionReason`で分類を保持する案は、読み取り型`PullRequestReviewThread`が`resolutionReason`を返さず、後続のセッションが機械的に取得できないため採用しない。

Dependabotアラートも同じ監査へ集約する。
目的は対象GitHubリポジトリにopenのアラートが出たとき、キューの状態にかかわらずprocess-wiの実行ごとに取得して対応することである。
以前は`atk wi process-loop`の待機中確認だけがアラートを取得してAWIを起票していたため、キューが空にならない間は取得処理へ到達せず、検出されない区間が生じた。
取り込みをprocess-wiの実行ごとの共通取得へまとめ、待機中確認も同じ関数で未判定件数を調べる。
待機中は1件以上ならAWIを起票せずprocess-wiを起動し、キューが空の間の監視を補う。

取得・判定区分・版付き記録の形式は`agent-toolkit/agent_toolkit/_atk/review_audit.py`が持つ。
GitHub APIの`default_branch`が指すブランチの完全SHAを、判定済み除外より先に解決する。
マニフェスト取得のref、pendingのrevision、list/markの`--revision`を同じSHAへ固定する。
pendingはそのSHAでのマニフェストの実在を判定し、監査担当は同一マニフェストの解決済み版を各ecosystemの規則で修正版と比較する。
版の比較を要する判定は監査担当が担い、新しいAPI版比較器は設けない。
判定と却下・投稿直前レビューの手順と認可は`agent-toolkit/skills/process-wi/references/github-copilot-review-audit.md`が定める。
返却は`agent-toolkit/share/copilot-review-audit.subagent.md`が定める。
起動と受領は`agent-toolkit/skills/process-wi/references/review-audit-launch.md`が定める。
process-loopのアラート確認は`agent-toolkit/agent_toolkit/_atk/wi/process_loop_alerts.py`が持つ。

判定済み番号は`review-audit.json`へ`dependabot:<番号>`として確認SHAとともに記録し、同版での反復監査を抑止する。
既定ブランチ更新後は同番号も再評価し、無版の旧記録はpending除外に使わない。
既定ブランチで修正済みかマニフェスト不在ならinaccurateで却下し、API終了0と応答number/stateの一致後だけ処置完了とする。
ベースブランチだけ修正済みなら反映待ち、未修正・比較不能・修正版なしは要修正として、却下せず確認版付きで記録する。
却下失敗・未判定は未markとし、単一・all-reposとも既存確認間隔で再取得する。
`process_loop_launch_gate`はWI部分の無進捗抑止を維持し、pendingに残るアラートを起動対象にする。
Copilot本文の日時記録と未解決threadの取得契約は維持する。

待機中確認を撤去する案は、キューが空の間に次のAWIまでアラートを放置するため採らない。
待機中確認でもAWIを起票する案は、同じアラートをAWIと監査で二重に扱い、要修正のAWIが重複するため採らない。
待機中確認をセッション開始時にも別系統のまま実行する案は、Copilotレビューの取得と取り込み時点を共通化できないため採らない。
全openを毎回監査担当へ渡す案は同版の要修正まで反復し、起動署名に別のrevision台帳を加える案は判定の有効性を重複管理するため採らない。
