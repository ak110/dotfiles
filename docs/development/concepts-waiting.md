# 方針・意向: 待機と観測

## 待機と観測

会話に残った`/exit`のローカルコマンド記録は、続行発話の有無によらず元の未完了工程を続け、操作に触れる発話と振り返りの分析・報告を省く。
関連する訂正・続行も同じ扱いとする。
作業完了の表示はreport-completionの既存の固定文言で十分であるため、待機規定・予告書式と固定文言は維持する（2026年10月14日、ユーザー指示）。
実行時の所在は`agent-toolkit:user-confirmation-and-report`の「割り込み・訂正・中止」と`agent-basics:bugfix`の`non-changing-request`である。

2026年10月13日、ユーザーは完了通知で同じセッションへ再開できる待機を常に背景起動へそろえ、ホストの複雑さに対してエージェントの行動を単純にすることを求めた。
待機の種類・件数・goal条件で前景へ戻す分岐を除き、先に届いた通知から出力と終了状態を回収する。
Codexの公開回収機能による同一ターン回収と、通知再開を持たない環境の終了観測は維持する。
現行の規定は`agent-toolkit:delegation`の`agent-toolkit:delegation/references/waiting-and-monitoring-intervals.md`「待機区間の構成」にある。

- `name`付きの背景起動は、当初完了通知の不達を確認して禁止したが、Claude Code 2.1.241での
  ユーザーの実端末再検証（`subagentStatusLine`のpayload確認）で現行版では再現しないことを確認し、
  禁止を解いた（2026年8月、実物での確認）
- 委譲先が待機表明でターンを終える動作は、完了通知だけを提供するホストの再開可能な正常状態として扱う。
  子がターンを終え、孫の終了やバックグラウンドタスクの完了の通知で再開する挙動は変えない（2026年10月4日、ユーザー判断）。
  委譲先を起こし続ける変更はトークンを浪費するためである。
  agents_serverが待機表明を終了時の結果として公開した不具合は、公開の時機の判定で直した。
  委譲先への指示とStop hookは変えない（`docs/development/design-agents-server-hold-state.md`「結果の保留と自動再開」）
  Codexで`wait_agent`が提供される場合は、終了状態を観測するまで`wait_agent`を使う。
  完了通知の受領主体を最上位または直接の親へ固定せず、通知の`status`・`result`と保持した直接の子のagent IDを用いる。
  現在の実行主体へ`SendMessage`が公開され呼び出しが成功する場合だけ同じIDへ逐語中継する。
  `ListAgents`が不在か、呼び出しを拒否された場合は、保持済みのID、完了通知、成果物観測および自身が起動して識別子を保持したプロセスの生存を確認する。
  プロセス名の一致だけから生存状態または対象を推定しない
- 委譲先または背景ジョブの完了待ちで観測手段が終了statusを返さずに制御を戻した場合は、戻り方で継続と終了を分ける。
  実行環境が背景処理へ移して完了時に通知すると示した場合は再発行せず待機表明でターンを終える。
  完了通知の手段が確立しない戻り方では、先行して実施できる工程が尽きるまで同じターン内で観測を再発行する。
  `agents_server`の結果待機は`atk agents wait`を用い、Bash背景ジョブへ移した場合はそのジョブの完了通知を結果本文として受領する
- Codexの`list_agents`が委譲先を`running`として返している間は、差分、HEAD、成果物の更新時刻・行数、無応答または経過時間だけで停滞を推定して`interrupt_agent`を実行しない。
  中断は明示的なユーザー要求、終了・失敗status、タスク契約でキャンセルが指定された場合に限る
- Codexの`running`中は補助観測だけを更新する同一turn内の状態照会を反復しない。
  完了通知の不着、次の定時turnまたは終了statusの確認では再照会してよい。
  `running`のstatusは補助観測より優先し、補助観測だけで中断しない
- 待機中の報告は、報告する実行主体が書き込む対象へ帰属させる。
  `git status --porcelain=v1`の差分件数とHEADは並行主体を含む全体値であり、単独の生存根拠にしない
- 委譲先の能力を比較する場合は、全対象へ同一の機械照会をする。
  照会不能や自己申告だけの比較は未検証として扱う
- `SendMessage`のsuccessまたはqueuedは送信側の受理だけを示すため、中継先IDと送信後の完了通知または戻り値を対応付けて受信処理を確認する。
  中継不能時は未完了の工程を担当範囲と権限の内側だけで巻き取り、外側の工程は続行できない理由として呼出元へ返す
- 委譲先・背景ジョブの完了待ちでは、シェルによる能動的な時間待ちを行わない。
  完了通知の不着は配送の道筋（どこを経由して届くか）と宛先解決を実際に確かめ、停滞の検知と巻き取りへ接続する
- Claude Codeの委譲または背景処理の待機では、機械的な完了通知を優先し、公開された`CronCreate`、`CronList`および`CronDelete`だけを定期再確認へ使う。
  5分系と1時間系の双方で定期待機する。
  定期再確認を装着するのはメインに限る。
  `atk wait-schedule`は公開情報からメインのcron式を選択し、定期再確認のpromptの共通本文とともにJSONで出力する（引数は2026年10月25日に廃止）。
  出力される`*/3 * * * *`（5分系）か`*/30 * * * *`（1時間系）の壁時計cron式を変更せずに用い、待機対象の全終了後にtaskを削除する。
  `ScheduleWakeup`は`/loop`専用とし、定期起動を完了または停滞の証拠にせず、シェルの`sleep`や背景タイマーを追加しない
