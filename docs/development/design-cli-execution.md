# 有限終了コマンドとWI投入の監督の設計記録

[設計記録の索引](design.md)から参照する、有限終了コマンドとWI投入の監督の記録である。

## 有限終了コマンドの出力と終了状態の保持

一般のチェックと観測は、ハーネスの標準実行・背景実行・待機機能で起動する。
別担当へ渡す初回観測など全量の保存が必要な場合は、実行主体が自分の一時領域へ標準出力と標準エラーを分けて保存し、終了コードと取得時のHEADを既存の返却・引き継ぎ記録へ残す。
2026年10月25日に、公開の`atk run-command`（argv・cwd・Git状態・両出力・終了状態を`record.json`へ保存し、`--record`・`--records-file`で読み直す）を撤去した（ユーザー指示）。
ハーネスの標準実行で同じ観測が得られ、専用の入出力形式を各担当が毎回学び直す費用と、保存JSONの読取・付替えの工程が便益を上回ったためである。

`atk lane integrate`は、統合を準備と検証、短い更新、記録の確定の3区間に分け、区間ごとに排他を変える。
準備と検証（rebase、history-compare、検証、検収待ち）と記録の確定（計画保存、WI終了）は、同じレーンの操作だけを止めるレーン単位の排他で行う。
短い更新（統合先HEADの照合、clean判定、adoptのcommit検査、fast-forward、`git-integrated`の保存）は、Git共通ディレクトリと統合先branchで決まる統合先単位の排他で行う。
共有の選定YAMLの更新と、`lane create`・`lane delete`・`lane recover`は所有session単位の排他を使い、回収は統合中のレーンを待たずに保持する。
取得順はレーン単位、統合先単位、所有session単位とし、逆順の取得を作らない。
短い更新で統合先が準備の前提から進んでいた場合は、統合先を変えずに終了1で返し、既存の`--restart-review`による再rebase・比較・検収へ戻す。
2026年11月11日に、所有session共通の排他を全区間で保持していた構成から改めた。
1レーンの検証の実行枠待ちと記録の確定の間、他のレーンの統合が全て待ち、ユーザーが統合を手早く行うことを求めたためである。
準備と検証だけを別の操作に分けてメインが短い更新の直前に1レーンずつ許可する案は、統合ごとの往復と通知が増え、CLIの排他と前提の照合で同じ保証が得られるため採らない。
前進を検出したCLIが自動で再rebaseまで進める案は、再rebase後の検収が人の判断を要し、`--restart-review`の比較の連鎖を別経路で持つことになるため採らない。

`atk lane integrate`が統合の各段（固有手順、最終化argv、検証argv）を記録・再開するための有限実行は、内部の`run_command.execute`として保持し、公開コマンドにはしない。
shellを介さずargvを起動し、両出力を別のbinary fileへ直結し、子の終了状態とwrapper異常（起動失敗・保存失敗の125、timeoutの124、signalの128+番号）を同じ記録で区別する。
検証argvはホスト共有の検証実行枠を所有して実行する。
子の環境は親の環境を複製し、共通の`strip_inherited_venv`で起動元の`VIRTUAL_ENV`と対応するPATHのbin・Scripts要素を取り除く。
別プロジェクトのuvや通常の子コマンドが、atkを起動したpluginの仮想環境へ誘導されることを防ぐためである。
process-loopと委譲サーバーにも使う共通処理へ接続する。

成功再利用の実行条件は、正規化後に実際の子へ渡す環境とPythonの実体・版・platformを項目別の識別情報として既存recordへ保存する。
環境全体の集約値だけでは、不一致時に必要な再検証と無関係な起動情報の差を区別できないためである。
Pythonの同じ実体を指すパス表記は正規化し、子にも渡らない起動層の復元情報を比較へ残さない。
未知の環境項目は比較に保ち、差の診断は追加・削除・変更されたキーだけを示す。
エージェントの会話・ツール呼び出し・委譲・巡回の識別子、端末・SSHのセッション、シェルの作業ディレクトリ・階層のように、再開ごとに値が変わり検証結果に影響しない既知の変数だけは、`run_command.py`の名前一覧で値を比べず有無だけを比較する。
ツール呼び出しの識別子は`CODEX_TOOL_CALL_ID`だけを一覧へ入れ、他の`CODEX_`で始まる変数は意味を確かめるまで値を比較する。
一覧を変えた版は実行条件のversionを上げ、旧版の記録を形式違いとして再利用の対象から外す。
有無は通知先の解決などの動作を切り替えうるため比較に残す。
委譲の種別や`1`で有効化するフラグは値が動作を変えるため、一覧へ入れず値を比較する。
これらを比較に残すと、同じHEAD・argv・cwdの成功が再開のたびに再利用されず、全体検証を繰り返したためである（観測は2026年11月）。
環境値の平文を別の台帳へ保存する案、接頭辞による一括除外、結果に影響する変数だけを許可する一覧は採らない。
許可一覧では、プロジェクト固有の未知の入力が比較から落ちるためである。

実行枠の区間はpyfltrの`on_wait_interval`を使い、同じkind・sequenceの開始と終了を同じ待ちへ対応付ける。
検証は`execution_slot.hold`を開始から子孫の回収まで保持し、子の終了は通常の有限待機で観測する。
2026年11月に、区切りでの譲渡・参加券・所有スレッドのcheckpointを撤去した。
区切りの到達や参加者の完了を追跡する状態が増え、待機や終了の停止を繰り返したためである。
入れ子の検証は祖先の所有を継承し、別の検証は所有者の終了後に開始する。
取得前の中断にも備えて、外側の待ちとコマンドの到達状態を同じ実行領域のtiming.jsonへ保存する。
外側のコマンド区間はGit状態取得・出力保存・子側の待ちも含むため、ツール本体の時間には代用しない。
コマンド内のpyfltrが持つ本体・待ち時間は、その実行IDの公開timingと関連付ける。
工程の開始・終了とレビュー・統合許可の時刻は既存の計画の進捗ログへ置き、並行区間の重複を除いて最長経路を比較する。

## 独立したWI投入の受付と監督

`atk wi submit`は投入元が終了した後も要求の意味確認・WI保存・報告を継続するため、自己完結した入力を状態領域へ保存してから独立監督へ所有を移す。
受付票は永続入力と監督のPID世代を対応付け、登録完了は要求ごとの処置と同じrun IDの報告同期から判断する。
同時に確定した同一対象の要求は公開入力の配列で受け取り、全件を検証して同じロック内で保存する。
要求を逐次受付してから集める競合や、複数の要求を1識別子へ潰すことを避け、元の識別子・由来・個別処置を同じ実行へ渡す。
製品のwriter・公開CIの完了と、別寿命の投入監督の処理完了を分ける。
入力・処置・失敗・報告の所在は同じ受付と実行記録へ集約し、排他と実行・報告には既存run-skillを利用する。

親の入力ディレクトリと開発worktreeの撤去に備え、入力本文を埋め込み、実行コードも既存のplugin root保持機構へ接続する。
保持に失敗した場合は受付を成立させず、未完了・未報告の実行が参照するコードは保持する。
起動前の未実行は同じ受付から回復し、保存後の応答喪失は同じ識別子の照会で判断する。
専用の常駐daemon、振り返り周期への依存、全工程を写す台帳は追加しない。
受付・投入・報告を同じ成功値にまとめる案は、親が終了できる条件と未完了の責任を区別できないため採らない。
運用契約は[wi-submission.md](../../agent-toolkit/share/wi-submission.md)が所有する。
