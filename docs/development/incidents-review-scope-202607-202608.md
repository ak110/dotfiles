# 障害・欠陥の記録: レビューの発散と目的の変質（2026年7月〜2026年8月）

[レビューの発散と目的の変質](incidents-review-scope.md#レビューの発散と目的の変質)の事例を発生時期別に収録する。

- 2026年7月: 1件の要求に対し計画が肥大化した。
  25ラウンドのレビューを重ねた末、その計画を差し戻した。
  直接原因: 要求範囲に対する成果物規模の妥当性を点検する観点が無かった。
  対策: 要求範囲との規模妥当性点検をレビュー観点へ追加

- 2026年8月28日: 通常型AWIの計画型変換で、レビュー収束後の最古項目を実装開始前に`processing`へ移し、その遷移をユーザー指示として記録した。
  直接原因: 技術的に不成立な一時`processing`案を専用`planning`へ変更した際、元案を前提とした成功後の状態と処理主体を再導出せず、各状態遷移の要件出所を確認しなかった。
  対策: 変換結果を`inbox`へ置いて処理開始を`start-processing`または`process-loop`だけに戻し、代替設計時は元案を前提とする判断を未確定へ戻して各状態遷移の主体と出所を計画・レビューで確認する

- 2026年8月28日: 計画構造の自動チェックと後続の検索・レビュー表検証を同じシェル呼び出しへ連結したため、構造エラーを返した終了コードが後続コマンドで上書きされ、計画レビューへ進んだ。
  直接原因: 計画構造の自動チェックを独立したコマンドとして実行せず、シェル呼び出し全体の最終終了コードを合否に用いた。
  背景原因: （混入要因）終了コード・警告・修正概要を保持する契約はあったが、計画構造の自動チェックの実行単位と終了コード0だけの後続条件を定めていなかった。
  （動機的要因）複数の確認を1つのシェル呼び出しへ集約した。
  （見逃し原因）契約テストが計画構造の自動チェック用スクリプトのパスと終了コード文言だけを確認し、独立実行を確認しなかった。
  （根本原因）合否判定の実行単位と後続工程の開始条件を、計画担当・レビュー担当の共通不変条件にしていなかった。
  対策: 両担当が計画構造の自動チェックを独立したコマンドとして実行し、同チェックが直接返した終了コード0の場合だけ後続工程へ進む契約と、その同期テストを追加する

- 2026年8月28日: ユーザーが明示した対象を計画が狭めたにもかかわらず、対応する確認済み回答がないまま計画レビューを完了した。
  直接原因: 明示要件との差を技術判断として`## エージェント判断`へ記録し、確認済み回答の代替として扱った。
  背景原因: （混入要因）作成基準と共有規範には確認義務があったが、起草手順とレビュー完了条件へ同じ条件を接続していなかった。
  （動機的要因）調査結果に基づく対象の具体化は自律確定できると解釈した。
  （見逃し原因）レビュー契約は事後承認扱いを禁じたが、確認済み回答がなければレビューを完了しない条件を明記していなかった。
  （根本原因）明示要件との差、確認証拠、起草・レビューの終了を1つの検出条件として定めていなかった。
  対策: エージェント判断の提示は確認済み回答の代替にならず、明示された対象・範囲・外部可視結果との差に回答がなければ起草とレビューを完了しない契約と、その同期テストを追加する

- 2026年8月28日: 同じ契約の定義・直接消費側・契約テストを話題別の三実装単位へ分けたため、先頭単位の適用後に204件中43件のテストが失敗した。
  直接原因: 中間commitの変更範囲の検証に必要な対象を別の実装単位へ分割した。
  背景原因: （混入要因）実装単位の独立性を成果・commit・対象ファイル集合・変更範囲の検証で表したが、変更定義から直接消費側・契約テスト・生成配布物までの必要範囲を定めていなかった。
  （動機的要因）中間commitの成立より話題別の小さなcommitを優先した。
  （見逃し原因）契約テストが抽象的な独立性文言だけを固定し、直接依存の分割禁止を確認しなかった。
  （根本原因）実装単位の境界を、中間commitの正式な変更範囲の検証が成立する直接依存範囲として定義していなかった。
  対策: 変更定義・直接消費側・契約テスト・生成配布物のうち中間commitの正式な変更範囲の検証に必要な対象を同じ単位へ含め、先行commit単独で変更範囲の検証が成功する場合だけ分割する契約と、その同期テストを追加する

- 2026年8月: ユーザー合意に基づく撤去計画で、旧IPythonプロファイルの親ディレクトリまで削除対象を広げる一方、
  カテゴリ機構ではCLI以外の利用方法を撤去対象から漏らし、重大指摘2件とユーザーへの再確認1回を要した。
  直接原因: 合意範囲と実装上のパス・識別子集合を対応付ける工程が計画様式に無かった。
  対策: 撤去・削除対象を実際に確認したパス・識別子集合で記載し、合意範囲との差は計画起草前に確認する規定を追加

- 2026年8月: 同一事実を計画の5箇所へ重複記載した結果、同期の脱落でレビューが13ラウンドに達した。
  直接原因: 変動事実の記載箇所を1箇所に限定する様式が無かった。
  対策: 変動事実の名前付きSSOT集約（計画様式の1事実1箇所原則）

- 2026年8月: レビュー指摘を全件採用したため、削減目的の計画が2行減にとどまり、
  保持合意済みの文面まで変更対象へ含めた（ユーザーの指摘で発覚した）。
  直接原因: 指摘の契約出所・保持対象を記録せず、目的への累積影響を測らずに採用を重ねた。
  対策: 指摘の契約出所・保持対象の記録と累積比較による目的変質検出

- 2026年8月: レビュー途中に追加した新機構の未確定要素が指摘35件中17件を占めた。
  直接原因: 修正で導入した新機構へ起草時の完成条件を適用しないまま再レビューへ送った。
  対策: 新機構追加時は起草時の完成条件を再適用してから再レビューへ送る

- 2026年8月: キューへ保留操作と一覧区分を追加する計画が13ラウンドのレビューを経て、要件に無い永続編集セッション、
  Git trailer、滞留commit復旧APIおよびrebase失敗状態まで含む実装へ拡大し、既存のWI追加テスト5件を失敗させた。
  直接原因: レビューで提案された修正要素を新しい要求として扱い、元のユーザー目的、公開契約、規範的制約または再現済み重大欠陥へ
  個別に対応付けないまま、後続レビューで新機構の内部整合性だけを高めた。
  対策: 2ラウンド目の修正前にレビュー起因の全要素を元の根拠へ対応付け、3ラウンド目へ進む前に初版からの累積差分を再監査する。
  対応先のない状態、API、識別子、互換機能、復旧処理およびチェック処理は、実装済みでも次ラウンド前に撤去する

- 2026年8月: `plan-impl-executor`が撤回済みのキュー状態変更を要求する修正方針を事前の確認なしで書込担当へ送付し、
  8ファイル・207行と4ファイル・48行の2件のcommitを実装後に破棄した。
  直接原因: 通常モードの書込担当の起動前のレーンまたは統合後モードの統合worktree作成時に検収した公開契約と
  承認済み変更を合成し、複数計画では指摘へ適用される全条項との両立を求める認可確認が修正後にしか無かった。
  対策: `plan-impl-executor`が対応方針確定前にモード別の作業前OIDを基準とする修正認可の上限と照らし合わせ、
  正常な差異は許容した上で、実際の超過、対応付け不能、計画間衝突を書込担当へ渡さず呼び出し元へ返す

- 2026年8月: `plan-impl-executor`がレビュー修正の書込担当へ送った起動文の命令が「指定worktree内で最小修正し、検証してcommitせよ」に留まり、受信者が所有する採否判定と類似箇所の一括修正を求めていなかった。
  直接原因: 委譲の共通契約が、起動文の命令と受信者側の正式な手順範囲との関係を規定していなかった。
  対策: 命令が受信者の手順範囲を狭めない規定と、受信者が適用する作成・レビューの規範を定めるスキルを起動文の必須入力へ含める規定を委譲の共通契約へ追加

- 2026年8月: 計画レビューの論点が計画ファイルの記述形式へ移り、レビューと修正が収束せず反復した。
  直接原因: レビュー担当の除外規定が記述スタイルだけを挙げる一方、計画本文の矛盾を一律に指摘対象とし、
  指摘受領側にも記述形式だけの指摘を不採用とする境界が無かった。
  対策: 記述形式を計画レビューと修正の対象外とし、実装時に解消できず実施可能性または公開契約の成立を損なう矛盾だけを扱う

- 2026年8月: review-session advisorの実装読解を縮小した後も、提案の反映先、代替案、ライフサイクルコストおよび他階層評価に、
  メインが実施するリポジトリの確認を要求する粒度が残った。
  直接原因: 実行手順の責務再配分に対して、出力欄と契約テストの情報粒度を同期していなかった。
  対策: advisorは対象ファイル単位、概念比較、受領範囲の抑止評価だけを返し、節・関数・行・同期対象・実装根拠の確定をメインへ集約する

- 2026年8月: 計画レビュー担当がレビュー表の操作書式と計画構造の自動チェック用スクリプトの所在を確定するため、私有実装とファイルシステムを探索した。
  直接原因: 公開CLIの自己記述を操作書式の正式な基準にせず、計画構造の自動チェック用スクリプトの絶対パスを初回・再レビューの入力へ渡していなかった。
  対策: `atk review-table --help`とサブコマンドの`--help`を公開基準とし、計画担当・調整主体が解決した`check_plan_file.py`の絶対パスを全ケースへ渡す。
  後継方針（2026年9月1日）: 計画レビューの実行中にplugin cacheが更新されると、渡した旧版の絶対パスが現行書式の計画を必須見出し不足として失敗させ、工程が停止した。
  計画構造の自動チェック用スクリプトの絶対パスは主体間で渡さない。
  計画レビュー担当は自身のタスク文書の絶対パスからplugin rootを導出する。
  同じrootの計画ファイル基準と計画構造の自動チェック用スクリプトを用いる。
  起動主体は渡す絶対パスを工程の開始時に1回解決し、同じ工程では同じ値を使う。
  担当からその絶対パスが見つからないと差し戻された場合、その工程を終えて次のセッションへ委ねる。
  レビュー担当が私有実装とファイルシステムを探索しない境界は維持する

- 2026年8月: 同じ計画の初回レビュー後も、後続ラウンドで初回から判断できた要件欠落が反復して見つかった。
  直接原因: 初回レビューの走査手順を完了報告の要件別被覆証拠へ接続せず、調整主体が未走査を検出できなかった。
  対策: 独立要件ごとの観点別被覆を完了報告へ要求し、欠落時は完了を受理しない

- 2026年8月: レビュー修正後の報告が`履歴書換え防止`を欠き、同じ報告の再要求を反復した結果、約40分・7ターン停滞した。
  `completed`はレーン資源回収後に返るため、欠落を検出してから無指定reflogを読む方式では旧OIDを復元できない。
  第2ラウンドで初回`review_round`のHEADを基準OIDへ保存する案を追加したが、現行`review_round`は第1ラウンドの修正後にしか返らず、最初の履歴書換えを確認できなかった。
  直接原因: 同じ機構が2ラウンド連続で不成立となった原因は、`review_round`をラウンド完了後だけの返却点とし、履歴書換え前の中間受渡しを一律に禁止した規範前提である。
  対策: executorは修正担当起動前の`before_fix` checkpointで修正前OIDを公開し、修正後の`after_fix`で修正前後OIDを返す。
  呼び出し元は`after_fix`の禁止条件の確認に合格した後だけ比較基準を更新する。
  `no_fix`は両OIDの一致だけを検収して比較基準を維持し、不一致時は測定値付き`needs_escalation`へ返す。
  禁止条件の確認は`after_fix`と最終`merge_request`だけに適用する。
  実装担当が履歴書換えを開始した後の単一担当・公開済み判定、通常の必須報告契約および資源回収順序を維持する。
  後継方針（2026年8月29日）: 実装担当が修正前後OIDと履歴書換え防止の結果をレビュー表へ保存し、同じ担当が統合前にGit実体と比べる。
  会話履歴の欠落時も保存済み完了内容から回復し、準備中の証拠しかない場合は無指定reflogへ後退せず停止する。
  調整担当の詳細検収と`before_fix`・`after_fix`・`no_fix` checkpointは廃止した。
  後継方針（2026年8月29日）: 初回レビューで成果物全体を確認する責務はレビュー担当に残し、調整担当による被覆報告の再検収は廃止した。
  各ラウンドは指摘件数だけを返し、第3ラウンド以降はメインがレビュー指摘管理表を確認して介入する

- 2026年8月: 実装レビュー中もラウンド別チェックポイントが返らず、反復レビューへの介入が遅れた。
  直接原因: 呼び出し元が受領済みチェックポイントだけを検収し、レビュー表の進行と未着状態を比べていなかった。
  対策: `review_round`を各ラウンドの返却点として維持し、第3ラウンド以降はメインが反復原因と計画目的への累積影響を調べる。
  進行中の未着と無進行は一般の待機・停滞監視で扱い、レビュー表の行数を稼働または完了の根拠にしない

- 2026年8月: 計画レビューで確定した初回被覆の確認を実装レビューへ横展開しなかった。
  通常実装・差分限定・統合差分・CI修正後の各ケースで、計画との比較と成果物評価の担当、起動数および`track`が一致しない事象が発生した。
  直接原因: 共通の実装レビュー契約を呼び出し元と受領側へ同期せず、ケースごとに計画との比較と成果物評価を別の担当と別の`track`へ分散させた。
  さらに、再レビューで前回レビュー後の修正と直接影響範囲を限定せず累積差分全体を対象にしたため、未変更部分で初回から判断できた指摘が後発して登録された。
  対策: 実装レビュー担当を`implementation-review`の単一trackへ統合し、計画との比較後の成果物評価、初回被覆結果とラウンド合計を同じ完了契約へ揃えた。
  再レビューは前回レビュー対象OIDからの修正差分、採用・未解決指摘、直接影響範囲と新設・変更契約へ限定した。
  共有parser、共通状態、公開契約、生成元、配布元のいずれかを変更した場合だけ実際の全消費先へ拡大した。
  後継方針（2026年8月29日）: 初回は全体をレビューする。
  再レビューではレビュー指摘管理表、修正箇所、直接影響範囲だけを確認する。
  調整担当の詳細報告と再検収は廃止し、作業担当が修正・検証・統合の完了責任を持つ

- 2026年8月: 実装後のレビュー指摘対応で、承認済み計画の前提・方針・意図に反する修正が反復して確定した。
  ユーザー指示に由来して固定集合へ変更した内容を、既存の規範に反するとして実装工程の判断だけで取り消した事例を含む。
  直接原因: レビューイー側契約が、過去の合意・保持対象の維持だけを規定し、承認済み計画の確定内容を覆す修正の禁止と矛盾観測時の差し戻し手順を持たなかった。
  背景原因: （混入要因）実装担当の入力契約が計画の実施内容と変更履歴を採否・範囲の上限としてのみ規定し、範囲の拡大だけを禁じて確定内容の反転を禁じなかった。
  （動機的要因）現行実装と既存規範を最新の判断材料とみなし、計画側の確定内容の由来を調べずに下位の作業メモとして扱った。
  （見逃し原因）実装レビューの再レビューが修正箇所と直接影響範囲だけを走査し、計画の確定内容と比べる条件を持たなかった。
  対策: 実装工程では計画の確定内容を覆す修正を確定せず、双方の由来を調べて優先順位を適用し、計画側が上位または由来を確定できない場合は呼び出し元へ返してユーザー確認で解消する。
  再レビューでも修正箇所を計画の確定内容と比べる

- 2026年8月: ユーザー専用のmigration操作であるとの是正後も、計画レビューが別操作のagent間排他をmigrationへ拡張し、レビュー起因のlease復旧条件をユーザー要件として扱った。
  migration用lock・leaseの追加と撤去が反復する一方、新保存先への書込認可という正常系の欠落は第5ラウンドまで検出されなかった。
  直接原因: 要件出所と適用条件を操作単位で保持せず、主要な異常系を通常の手順より先に検討した。
  対策: 正常系の起動、書込み許可、配布および成果到達を先に端から端まで走査し、状態管理の指摘を要件出所、対象操作、操作主体、競合主体および同時成立条件へ対応付け、前提失効時にその前提を根拠とする指摘と追加機構を次回レビュー前に撤去する
