# 確定済みの方針・意向: WI選定と処理

本書は`concepts.md`から主題別に分割した方針の記録である。
実行時の規範は各項目に示すスキルと`agent-toolkit/share/rules/common/`が定める。

## WI選定と処理

- 同一バッチの複数項目はメインが1つ以上の通常レーンへ明示的に分け、1件ずつの直列処理をしない。
  計画ファイルの分割は対象ファイル集合の重なりと検証境界の独立性を主判定とする。
  通常レーンは1計画ファイルと1専用worktreeを持つ。
  単一の計画では行数の警告を避けられない初回だけは、同じレーンとworktreeのまま複数の計画へ分ける。
  分けた計画は集合として構造と選定の対応を確かめてからレビューと保存へ進む（2026年10月8日、review-session由来の要求。103件のレーンで単一計画が2496行となった観測による）。
  変更対象ファイルの重なりと変更規模はレーン数の上限を広げる入力にせず、
  重なりは同段階の同時書込を避ける条件、規模は上限の内側でレーン数と割当先を選ぶ入力に用いる。
  異なるレーン間の競合はrebase時に解消する
- 実装単位は達成する成果、commit、対象ファイル集合および変更範囲の検証が独立している場合だけ分割する。
  判断から一意に導出できる実装順序やコマンド列は、
  安全性、データ保全または公開契約を守る必要がない限り常設文書へ重複記載しない
- 調査スレッドは複数のAWIをまとめてよく、調査対象ファイルが重なる項目を優先する。
  重なりは同値関係ではないため、機械的な分割規則と担当件数の上限を置かない。
  本項の判断は現行の工程構造ではレーン分けが担い、
  規範は`agent-toolkit/skills/process-wi/references/selection-procedure.md`にある
- `agent-toolkit:process-wi`のメインは選定工程で処理対象を確定した直後に、選定時点で`inbox`だった全項目を一括で`processing`へ移す。
  メインは出力の検収時に配置を確認し、計画ファイル・worktree・実装担当の起動をその後へ置く。
  2026年8月のユーザー指示により、着手中の占有範囲を外部観測と中断後の再開位置から識別するための順序とした。
  2026年9月に遷移の実行主体をpickerへ移し、2026年10月9日のユーザー指示で選定とともにメインへ移した
- 1回の`agent-toolkit:process-wi`は初回の候補と配分を保持し、30分点検と公開前に開始時識別子集合との差分で新着を確認する。
  新着確認・即時対応のユーザー指定を受け、既存項目の状態変化と新規投入を区別する方式を採る。
  全レーンの後始末後に全件を再選定する運用は加えない。
  実行規範は`agent-toolkit:process-wi/references/immediate-fix.md`「開始後に追加されたWIの確認」にある
- 処理中に明示された追加WIは、初期選定中ならメインが同じthreadで元の出力へ集合和と重複除外で合流する。
  状態移行済みの項目を再遷移させず、最新の保存後のチェックと意味検収を保つ。
  選定完了後は追加YAMLを既存の統合操作で検収して元の固定出力へ保存する。
  新着は本文から対処時機を判定し、現物で欠陥と確定した不良は、発生場面が未観測でも共通の先送り条件に当たる場合を除き今回の正式対応へ含める。
  確定した不良では、レーンや全体の所要増を先送り理由にしない（2026年11月12日のユーザー指示）。
  欠陥の有無が未確定の候補・効率改善では、不可欠な最小修正と、共有負荷・統合・公開を含めた全体完了を延ばさない追加を比較する。
  この候補・効率改善の比較で、安全な受入先か全体所要の根拠が不足する項目は次回へ残す
  （2026年9月のユーザー指示と2026年10月8日の`「先に情報送った方が二度手間にならなくて済むのでは？」`を反映）。
  追加項目は既存レーンへの割り当てを優先し、確定した不良の正式対応は新しいレーンも受入先に含める。
  同じ再開計画は元レーンで扱い、同じthreadで先行計画を保ちながら追加計画を作成する。
  統合済みでも保持した同じ資源へ追加し、選定の合流先だけを未統合へ戻す。
  割当の変更だけを理由に稼働中の担当を中断しない（2026年10月10日、ユーザー指示）。
  同じprocess-wiの1回の実行への追加を目的とするAWIは保存結果の正式ファイル名の受領直後、ユーザー指定のWIは指示と対象の確定直後に選定へ渡す。
  並行する他の要求の起草・検収・保存の一括完了を開始条件へ結び付けない。
  未告知新着を無判定で追加せず、次回向けの正式対応AWIを無条件に今回へ戻さない。
  現行手順は`agent-toolkit:process-wi/references/selection-procedure-addition.md`「処理対象WIの追加」と`run-lanes.md`にある
- AWIとUWIの元ファイル名は`## 実施内容`の由来欄が保持し、廃止した`## 提示素材`は読み取り互換に限定する
  AWI本文とUWI本文は計画へ複製せず、本セッションで受領したユーザー発言は`## 変更履歴（計画時）`へ`### ユーザー発言<連番>`の逐語`text`コードブロックで記録する
- 実装中の作業記録は`## 進捗ログ（実行時）`へ分離する
- 同一ファイルに採用要求が1件以上ある場合は、不採用要求を含む全要求を内部採否記録へ保持する
  計画では要求単位の由来・承認範囲・採否を区別し、同じAWIでも異なる単位は複数行へ分ける
- キューにない素材の逐語本文・回答全文は計画外の明示入力として調査、起草、初回レビュー、再レビューへ保持し、計画本文へ転記しない
- 初回起動後に追送されたユーザー発言は、起草担当が逐語本文、入力種別、出所および引用範囲を保持して真正性を保証する。
  レビュー担当はその真正性を再判定せず、計画本文と変更履歴の対応だけを比べる
- 選定時のファイル単位の分類とhold判定は`agent-toolkit/skills/process-wi/references/selection-procedure.md`が定める。
  要求の採否と通常の終了はレーン担当が行う
- 採用済み内容を統合した元項目と、検収済みの別リポジトリ移管元は`reject`せず、統合先または移管先を`note`へ記録して`rm`で除去する
- 技術的な失敗、入力不足、外部条件待ちは不採用へ変換せずactive状態に保つ。
  人間の回答を待つ項目は確認のUWIへの依存（`depends_on`）で待たせる（2026年10月、回答待ちを編集中の`hold`と区別するユーザー指示による）
- 一括取得の主体は、`atk wi show`が返す`保存先:`のファイルから全文を読む。
  `## target_repo:`行と`### <filename> [<state>]`行の完全一致、要求順、本文境界を確認する。
  保存内容を実行主体間で共有せず、保存ファイルを読めない場合だけ分割取得へ移る。
  保存したファイルは回収せず、managed-tempの7日の自動削除へ委ねる（2026年9月26日、ユーザー回答「managed-temp周りの手順がそもそも煩雑すぎる」により、個別の領域作成とcleanupを取得手順から外した）。
  2026年10月4日に、取得主体がセッションのmanaged-tempへ標準出力を保存する手順も外し、`atk`が保存する形へ移した。
  現行の手順は`agent-toolkit:wi-standards`の`references/wi-show-bulk.md`が定める
- 各項目の`depends_on`は安全な実施・完成判定に不可欠な先行成果の完了待ちだけを表し、書込の競合と実装順はレーン割当で扱う。
  後続本文には待つ成果、成立しない工程と現行成果物で代替できない理由を対応付ける。
  同じ開始時候補内の同一リポジトリ依存は推移的な成分も同じ処理回・同じレーンで依存先から扱い、成果を得られない後続は待機する（2026年9月30日、ユーザー指示と提案の採用）。
  人間の回答待ちは元項目から確認のUWIへの依存で表し、依存を本文から再構築しない。
  現行の規範は`agent-toolkit:wi-standards`の`references/states-and-dependencies.md`とメインの選定とレーンの担当手順にある
- 選定工程のメインは要求の採否と既存の変更による充足を確定せず、計画担当が対象実装を読解して確定し、実行レビューが要求の被覆と根拠を検証する。
  即時対応済みと本文へ記載した項目も次セッションで計画レーンへ送る（2026年9月、ユーザー指示）
- 着手不能の要因は解除される契機で分類する。
  時間経過だけで解除される要因を`cooldown_until`で表し、実在する先行キュー項目の終了で解除される要因を、その先行項目への直接依存で表す。
  人間の回答がなければ解除できない要因は元項目からUWIへの依存で表し、回答を待つ元項目のファイル名をUWIの本文が持つ（2026年10月、回答待ちを編集中の`hold`と区別するユーザー指示による）。
  外部環境の制約と別環境での実施は発生場所であり、それだけではUWIの根拠にしない。
  `cooldown_until`を設定する主体は、時間経過で解消することを現物の観測か公式一次資料で確かめる
- 通常型のキュー項目の依存は`atk wi set-dependencies`で登録する
- `atk wi process-loop`の1反復で`update-dotfiles`を実行するのはセッション開始前の1回だけとする。
  正常終了後の2回目は次の反復の開始前更新へ委ねる
- `update-dotfiles`の成功を契機に`atk wi process-loop`が自己再起動する場合は、再起動先の開始前更新を1回だけ抑止する。
  再起動の契機となった更新と再起動直後の開始前更新は同じ上流状態を対象とするため、2回目で取得する内容が変わらない
- 常駐実行の起動目的文は、`agent-toolkit:process-wi`の完遂に加えて`atk agents-exit-session`による
  セッション終了までを求める。
  目的文を短く保つ整理で終了工程の要求を削除しない
  （2026年8月、ユーザー指示）
- process-loop起動セッション以外は、常に別セッションでprocess-loopが並行稼働している前提で
  作業する
- `agent-toolkit:process-wi`のメインは選定結果へ要求単位の由来を書かず、レーン担当が計画起草時にAWI本文とfrontmatterから判定する。
  選定結果が持つのは消費側が実際に参照する項目だけとし、委譲先が自分で参照できる基準文書やデータから判定できる属性を載せない。
  項目数がWI件数に比例して増える一方、レーン担当は計画起草時にAWI原文を取得するためである（2026年9月15日、ユーザー指摘）。
  現行の規範は`agent-toolkit/skills/process-wi/references/selection-procedure.md`と`agent-toolkit/share/exec.subagent.md`にある

## 多数の単純作業の分担

上位担当の工程内でも、確定済みコマンドの実行・結果観測と確定済み根拠からの起草・追随を中位以下へ分ける。
原因確定、設計判断、観点の選定と返却の統合は上位担当が所有し、工程表の役割指定を保つ。
この分担は上位工程に含まれる機械作業の実行費用を抑えるための設計判断に由来する。

実行時に従う規範は`agent-toolkit:delegation/references/routing-units.md`「委譲単位の確定」に置く。
計画での実施方式の比較は`../../agent-toolkit/skills/write-plan/references/plan-file-standards-scope.md`「実施内容」が定める。
一括置換の手順は`agent-toolkit:wi-standards/references/notation-rules.md`「表記の一括置換」が定める。

- 簡単な反復作業は、一括置換と変更箇所の軽量レビューを使えるかを先に比べる（2026年10月1日のユーザー指示）。
- 単純作業を多数の対象へ行うときは、作業量に合わせてうまく並列化する。
  分担を粗くし過ぎず、担当の中でさらに並列に分業する手も比べる。
  難しい作業の並列化は規範の読み込みの重複でコスト効率が悪化するため、単純作業と区別して判断する（同日のユーザー指示）。
- モデルの工程指定では、作業を極力細分化して`chores`・`chores_fast`を使う（2026年10月24日のユーザー指示）。
  2026年11月1日の指示では、自律的な切出しをreview・review_fast・chores・chores_fast・writeに限定し、計画・設計判断・原因分析は役割担当が所有する。
  executeとorchestrateは役割文書や最上位・統括の所定の起動に使い、WIのユーザー明示指定を保持する。
  実行時の規範は`process-model-settings.md`「工程別モデル設定」と`agents_server`の`start`の説明に置く。
- 大量のファイル編集を含むWIは、1つのレーンが要求と完成条件を所有したまま、レーンの内部でファイル群へ分担する。
  2026年11月9日のユーザー指摘「レーン内で単純作業はスクリプトやchores_fast_modelとかでうまく高速に処理できればいいんだけどね」を受けた技術判断である。
  1つのWIをファイル別に複数の通常レーンへ割り当てる案は、複数計画の完成責任、WI終了の調整、選定形式の変更が増えるため採らない。
  対象の列挙・変換・機械比較はスクリプト、確定済みの処理と全変更文の意味の一次確認は軽量な内部担当が受け持つ。
  疑義と硬い制約に関係する変更の全件確認、一次確認済みの群からの代表の抜き取り、適用の判断はレーン担当が受け持つ。
  `chores_fast_model`はユーザーの例示であり、全作業を同じモデルへ固定しない。
  単純作業への一律の人数上限、抜き取りの固定比率、新しい台帳やモデル設定キーは設けない。
  推論担当の分担数と検証プロセスの同時実行負荷は別に判断し、ホスト全体の負荷指標だけで担当数を制限しない（検証の負荷とエージェントの並列数を混同していないかを問う、同日のユーザー指摘による）。
  軽量担当による一次確認の適否と所要の削減量は実証済みとして扱わず、同じ入力による全件検収との比較で判断する。
  実行時の規範は次の3か所に置く。
  `agent-toolkit/skills/process-wi/references/selection-procedure-allocation.md`「調査とレーン分け」は見積もり、`lane-planning-drafting.md`「計画の起草」は作業構成、`agent-toolkit/share/exec.subagent.md`「操作区分」は確認の分担を定める。
