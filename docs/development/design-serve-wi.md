# WI画面の設計記録

[設計記録の索引](design.md)と[画面統合とセッション・計画一覧の設計記録](design-serve.md)から参照する主題別の記録である。

## WI画面

WI一覧は日常確認の「通常表示」、過去の項目も探せる「条件検索」、未回答UWIを続けて確認する「判断待ち」を分ける。
通常表示はstate=active・直近2週間を適用し、条件検索の入力欄はstate=all・全期間・その他無指定で初期化する。
入力欄を変更すると条件検索へ切り替え、通常表示へ戻した間も検索値を保持する。
「条件をクリア」は検索値を全て初期化して通常表示へ戻す。
モードとクリアはフィルターの開閉によらず操作でき、適用中のモードと条件を一覧に示す。
検索入力でstateやperiodを自動変更する案は、手動指定を維持できず選択値の変化も分かりにくいため採らない。
保持は同一ページ内に限り、ブラウザー再起動後の永続保存は行わない。

一覧・件数・ページ送りと「全てコピー」は、モードと入力欄から導く同じ実効条件を使う。
条件一致0件でも条件外の項目は自動表示せず、条件を変更する操作を案内する。
検索語の反映は250msのデバウンスを用い、IME未確定文字では検索しない。
条件変更・モード切替は操作開始時に旧要求を無効化し、通常表示への復帰では保留中の検索も取り消す。
再取得と詳細閲覧はモードと入力値を保持し、target-repo候補の再取得でも選択値を保持する。

一覧の「全てコピー」は実効条件に一致する全ページを対象とする。
既存の個別コピーと同じ`<filename> <summary>`を1項目1行で並べ、取得中、0件とClipboard失敗を画面へ示す。
一覧APIと共通選択条件が対象集合を所有し、ブラウザーは取得・コピー・結果表示を担う。
表示ページだけをコピーする案は、フィルターで選んだ集合の一部がコピーから欠けるため採用しない。

重要項目は一覧に「重要」バッジを表示し、詳細では現在値に応じて「重要設定」または「重要解除」を表示する。
重要項目だけを表示するかは、CLIとWebが同じ`all/yes/no`の判定で決める。
WIの内部キーとURLは保存状態から独立させ、状態変更後も同じ項目を指す。

保存状態がinboxのAWIで有効な未来の`cooldown_until`を持つ項目は、表示ラベルだけをcooldownにする。
needs-verifyにも当たる項目ではcooldownを優先し、期限後はneeds-verifyへ戻す。
期限を適用できるか（AWIであり、タイムゾーン付きの日時であるか）は、着手可否判定と共有する`wi/readiness.py`の`applicable_cooldown_until`でAPIが判定し、画面は返された期限と現在時刻を比較する。
UWIは期限を保存していても保存状態を表示し、期限の経過で表示を変えない。
UWIはユーザーの判断を待つ項目であり、着手可否判定もその期限を不正期限として扱うためである。
保存値は詳細のfrontmatterから確認できる。
日時の解析だけを画面用の期限へ流用すると種別の条件が抜けるため、APIは共有した判定を使う。
画面だけに種別の条件を置く案は、APIの利用側と着手可否判定の条件が分かれたまま残るため採らない。
表示中の期限でラベルを更新し、一覧・読み上げ・詳細・削除確認の表示をそろえる。
バッジのホバーはJSTの解除日時を示す。
保存状態を増やす案は状態フィルターや操作の契約まで変えるため採らず、フィルター・件数・操作可否は保存状態で判定する。
holdなどinbox以外の項目は冷却期限があっても保存状態を表示する。

保存状態がinboxで回答済みのUWIは、表示ラベルだけをansweredにする。
回答済みで次の処理を待つ項目を未回答の質問と一覧で見分けるためである。
バッジの色は保存状態inboxと同じにし、状態フィルター・件数・操作可否は保存状態で判定する。
cooldownの期限はAWIだけに適用されるため、両者の優先順は生じない。
inbox以外の保存状態の回答済みUWIと未回答のUWIは保存状態を表示する。
保存状態にansweredを加える案は、状態フィルターと操作の契約まで変えるため採らない。

WI画面の詳細ダイアログの変更操作は、回答、本文の保存、ユーザーコメントの保存、採用、却下、保留、保留解除、inboxへ戻す、削除である。
これらを送信してから応答を受けるまでの間は、開いている詳細の外部更新の判定（本文の比較、警告、表示の切り替え、`currentEntry`の書き換え）を保留し、保留したことだけを記録する。
一覧の再取得は続ける。
通常表示・条件検索の操作が成功した場合は保留した再読込を破棄し、詳細を閉じて成功を通知する。
通常表示・条件検索で失敗した場合は保留した再読込を実行して外部更新を反映し、操作の失敗の表示を再読込の警告で上書きしない。
送信中に届く更新通知には操作自身の書込みが含まれ、外部更新として比べると成功した操作に「外部で項目が更新されました」の警告を表示する。
事後承認型UWIへの肯定回答の自動採用や採用・保留・削除のように操作が項目の状態も変える場合は、詳細の表示が移動先や削除済みへ書き換わり、詳細が閉じないか、自分が削除した項目を削除済みとして通知する。
成功後に詳細を閉じるかは、操作開始時の`detailSessionGeneration`とファイル名で判定し、操作で変わる状態を判定に使わない。
送信中の扱いと成功後の処理は、全変更操作を処理する`static/wi_mutations.js`の`runDetailMutation`へ集め、変更操作を加えるときも同じ処理を実行する。
他プロセスによる送信中の変更は、`expected_content`を送る操作ではサーバーが409（`edit_conflict`）で拒否し、通常表示・条件検索では失敗時の再読込で画面へ反映される。
判断待ちでは後述の連続確認の契約で入力と現在項目を保つ。
送信中の更新通知による詳細の再読込を撤去する案は、送信していない間の他プロセスの変更を通知できなくなるため採らない。

ワークアイテム一覧の期間（直近2週間・4週間・8週間・全期間）は、WIファイル名の先頭の作成日時から判定する。
更新時刻はGitの取得や同期で変わり、作成からの経過を表さないためである。
作成日時を読めない名前の項目は期間で隠さない。
一覧APIは`period`を省略すると全期間を返す。
通常表示の直近2週間は、古いWIを確認する場面は少ないというユーザーの判断（2026年10月2日）を維持し、条件検索の初期値を全期間へ分けた。

ワークアイテム一覧の「type・state」欄と、詳細ダイアログ・削除確認の種別と状態の表示は、`atk wi`のCLIとWIのfrontmatterが使う英小文字の識別子（`awi`、`uwi`、`inbox`、`processing`、`plan`など）で表示する。
CLIの出力やファイルにある状態値と画面の状態値が同じ文字列になり、両者を比べられるようにするためである。
同じ欄の「未回答」バッジだけは日本語で表示する。
ユーザーの操作が必要な項目を一覧で目立たせるためで、2026年10月7日のユーザーの判断による。
この欄へ新しいラベルを加える場合は英小文字の識別子の記法に揃え、「未回答」は揃える対象から外す。
セッション画面の種別ラベル（`static/sessions.js`の`KIND_LABELS`）と計画ファイル画面の接続状態のバッジ（`static/plans.js`の`HOST_BADGE_LABELS`）は日本語で表示し、この方針の対象外とする。
