# 運用機能: mypyの共有キャッシュ

## mypyの共有キャッシュと内部エラー時の再解析

`.bashrc`は`MYPY_CACHE_DIR=$HOME/.cache/mypy`を指定し、worktreeやプロジェクト間で
mypyの保存済み型情報を再利用する。
通常の実行ではこの共有保存先を維持する。

[mypyの上流説明](https://github.com/python/mypy/issues/21136#issuecomment-4170319426)では、同じキャッシュを使う複数プロセスの並行実行は非対応である。
SQLiteを無効にしても並行実行がサポートされるわけではない。
直接mypyを並行実行する場合は、上流の推奨どおりプロセスごとに異なる`--cache-dir`を指定する。
通常の共有設定は変更しない。

pyfltrの別実行同士は、既存の実行枠で直列に実行する。
同じpyfltr実行内でmypyのサブプロジェクトを並行処理するかは、pyfltrの版と実効設定で確認する。
`database is locked`が発生した場合は、本リポジトリのルートで`uv run --frozen pyfltr run --commands=mypy --no-fix -j 1`を実行し、mypyを直列に再実行する。

mypyがキャッシュの型情報を復元する途中で内部エラーを返した場合は、同じ入力・依存環境・設定を保ち、
元のmypyコマンドへ`--no-incremental`を付けて一度再実行する。
この指定は既存キャッシュの読取りを止めて再解析し、キャッシュへの書込みは継続する。
再実行の終了状態と診断を確認し、通常の型エラーが出た場合はその診断を修正する。
内部エラーが継続する場合は、再実行の診断から原因調査を続ける。

通常の型診断による非0終了は再解析の契機に含めない。
回復は障害時の1回の再解析とし、共有キャッシュの一括削除、恒常的なキャッシュ無効化、
通常実行での作業ディレクトリごとの分離と自動リトライは行わない。
保存済み情報と新規解析の成否差だけでは、キャッシュの共有や同時更新がその情報を不整合にした原因だとは確定できない。
