# 障害・欠陥の記録: 誤判定と検証不足（2026年9月3日〜2026年9月30日）

[誤判定と検証不足](incidents-judgment.md#誤判定と検証不足)の事例を発生時期別に収録する。

- 2026年9月3日: 統合担当が完了報告のcommit OIDを実際に確認せず短縮OIDから組み立て、同じ誤りにより`git merge --ff-only`が1回失敗した。
  同一主体が2ターン連続で同じ誤りを起こした。
  直接原因: 2026年7月の対策で置いた条文が外部コマンドの引数となる識別子だけを対象とし、報告へ書く値を適用範囲に含めていなかった。
  対策: 適用範囲へ報告、記録および成果物へ書く識別子を加える

- 2026年9月5日: `agent-toolkit:atk-mode`の作業`process-wi`の日次リリース判定で、開始時に固定した処理対象集合を再取得できていない状態を空集合と推定し、不要なrelease PRを作成した。
  直接原因: 会話圧縮後に再解決する対象をファイル・コマンド・識別子へ限定し、固定集合・保留・承認状態を内部要約の欠落から補った。
  対策: Codexでは固定集合・保留・承認状態も元の定義から再解決し、再解決できない状態を空集合・未実行・承認済みと推定しない

- 2026年9月5日: 作業中のユーザー介入が続く場面で、介入内容を現物と比べずに同意して成果物を変更する事象が繰り返し観測された。
  直接原因: 現物確認を求める規範は常時ロードされていたが、ユーザー介入を受けた時点でその条文を適用する契機が無かった。
  対策: UserPromptSubmitのフックが、直前の通常発話から3分以上経過した通常発話へ現物確認の指示を注入する

- 2026年9月5日: `AskUserQuestion`の直前の地の文へ選択肢の前提を置いたため、ユーザーが判断材料を読めず確認の再発行を要した。
  直接原因: 直前の地の文は要約へ置換されないという2026年8月31日の観測を、位置を問わない前提として保持した。
  対策: 置換されない位置を前提にしない記述へ改め、地の文がユーザーの読む本文より長い呼び出しをPreToolUseで警告する

- 2026年9月5日: ユーザーが調査と報告だけを求めた依頼で、確認を経ずに3ファイルを変更しstageまで進め、ユーザーの介入により変更を破棄した。
  直接原因: 継続と同一セッション内対応を求める条文が、依頼の求める成果物の種別との比較を求めていなかった。
  対策: 継続と同一セッション内対応を求める条文は、依頼が求める成果物の種別に限って適用する。
  依頼が求めていない変更は着手前に確認する

- 2026年9月5日: 確認の選択肢が案ごとに変わる外部可視の挙動を示さず、ユーザーが回答を改めたため同じ論点の確認が2往復した。
  直接原因: 選択肢を組む手順が、実装上の位置による差だけを必須の記載要素とし、外部可視の挙動の差を含めていなかった。
  対策: 案ごとに変わる外部可視の挙動を選択肢の本文へ書き、書いていない選択肢は成立しないものとして扱う

- 2026年9月5日: レビュー指摘を採用した是正で、指摘本文が列挙した対象だけを修正し、同じ違反契約が成立する別の入力を残した。
  次のラウンドで同じ契約の違反が再び指摘された。
  直接原因: 是正範囲を違反契約の再現範囲で確定する規定はあったが、その範囲の境界を定める基準を持たなかった。
  対策: 母集団の境界を誤りの機構が成立する条件で定め、指摘に現れたファイル名・識別子・工程・データ構造を限定条件にしない

- 2026年9月5日: 委譲の起動文と完了報告が規範の記述の転記により肥大化する事象が反復し、同種の是正要求を繰り返し受領していたことが判明した。
  直接原因: 起動文の構成と完了報告の返却形式を定める規定はあったが、呼び元手順が必須入力を散文で再列挙でき、受領側に返却形式を確認する義務が無かった。
  対策: 起動文の構成と必須入力の列挙形式を`agent-toolkit:delegation`のSKILL.mdの`## 送信`へ一元化し、呼び元手順から再列挙を除く。
  完了報告は受領側が受信者のタスク文書の`## 出力`が定める返却形式と一致するか確かめ、適合しない報告のまま後続工程へ進まない。
  再発（2026年11月18日）: 効果不足。
  作業契約、委譲と起動のプロンプト、規範、記録が膨らみ続けるとユーザーが再び指摘した。
  転記の一元化では止まらず、再発防止のやり方が条文・通知・記録を足す形に偏っていたことが共通の原因だった（防止策の定義が永続的な追加物を求め、規範の未適用の原因に周囲の記述量を数えず、再発を防げなかった処置を残したまま重ね、費用を1件ずつ比べていた）。
  bugfixの再発防止策の定義・選定と、規範改訂の費用の定義を改めた

- 2026年9月9日: 委譲先が起動した子sessionは、委譲先の終了後もstatuslineに稼働中と表示され続けた。
  直接原因: 状態ファイルの回収と終了状態への更新を書込主体の正常終了時だけに行い、書込主体の消失を読取側と他の書込主体が判定する手段を設けていなかった。
  設計文書は残存ファイルが次回の`agents_server`起動で除かれると記していた。
  対策: 状態ファイルへ生存の印を置き、失効した状態ファイルを読取側が表示から外し、他の書込主体が削除する

- 2026年9月28日: `agent-toolkit:atk-mode`の作業`process-wi`が`source: session-review`のAWIに転記された問いへ回答UWIを3件投入し、元セッションで扱った問いをユーザーへ再び尋ねた。
  直接原因: 回答UWIの対象を定める条文が、転記された問いの除外を`source: add-awi-by-user`に限っていた。
  対策: `wi-standards`、計画基準、親子タスク文書と実行レビュー文書の回答対象を、WIのユーザー記入欄へ処理側に宛てた問いにそろえた

- 2026年9月28日: 直前の監査報告からAWIへ登録する項目を仕分けた際、見送りが誤った所見が1件、見送り理由が誤った所見が2件あった。
  直接原因: 登録依頼の文面だけで仕分け手順の適用を判定し、直前の成果物から見送る所見の理由を現物で確かめなかった。
  対策: 直前の成果物を入力にする仕分けでも見送る項目を1件ずつ表へ載せ、該当行や履歴、実装などの現物で理由を確かめる

- 2026年9月29日と2026年10月2日: `atk serve`のセッション画面の左ペインで、サブエージェントと委譲先の記録がトップレベルに並ぶ症状について、母集団の取り違えが2回起きた。
  直接原因: エンドユーザーが画面で観測した症状の母集団を、画面より手前の中間の値（一覧APIの`parent_path`）か、測りやすい一部の記録（状態ファイルを持つ委譲先）で数えた。
  対策: `agent-basics:bugfix/references/root-cause-analysis-initial.md`「初動と拡張原因分析の判定」へ、次の項を加えた。
  - 症状の件数と該当対象をエンドユーザーが観測する層で数える
  - 中間の値で数える場合はエンドユーザーが観測する層までの変換と数えなかった記録を確かめる
  - 件数を成果物へ書くときは数えた層を併記する

- 2026年9月30日: Windowsのhook時間切れへの対策を問う確認で4種の誤りが重なり、ユーザーが自由記述と割り込みで計5回是正した。
  直接原因: 確認の発行時点で`agent-basics:bugfix`の初動と`agent-toolkit:atk-mode/playbooks/confirmation.md`の該当条文は文脈にあった。
  対策: `agent-basics:bugfix/references/root-cause-analysis-initial.md`「初動と拡張原因分析の判定」の第1項へ、次の内容を加えた。
  - 対照による直接的原因の確定
  - 相関だけの候補と区間を確かめていない計測値を推定として扱うこと
  - 類似範囲を機構を共有する対象全体とすること
