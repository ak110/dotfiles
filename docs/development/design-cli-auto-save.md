# 長い出力の自動保存の設計記録

[設計記録の索引](design.md)から参照する、長い出力の自動保存の記録である。

## エージェント環境での長い出力の自動保存

保存したファイルは、ハーネスの読取（Read）か`sed -n '<開始行>,<終了行>p' -- <絶対パス>`で、示した行数を範囲に分けて読む。
2026年10月25日に、文字位置の継続取得を提供した`atk read-file`を撤去した（ユーザー指示）。
行数を示せばハーネスの読取と標準コマンドで分割取得でき、継続位置のJSONを連結する専用の手順を各担当が学ぶ費用が便益を上回ったためである。
保存表示は保存先と行数の2行とし、最初の読取コマンドの行は添えない。

目的は`atk`を呼ぶコーディングエージェントが保存先の組み立てと保存後の確認をコマンドへ加えずに、長い出力を受け取れる状態にすることである。
保存先の指定を呼び出し側へ任せる形では、エージェントは出力の大小を問わず`--output-file <絶対パス>`を組み立て、`wc -c`や`tail`をつないだ長いコマンドを待機のたびに発行していた。

`AI_AGENT`・`CODEX_CI`・`CLAUDECODE`・`CURSOR_AGENT`のいずれかが設定された環境では、共通処理が有限終了の両ストリームを別々に保持する。
通常はUTF-8で16384バイト以下なら直接表示し、超える場合は全量を新規managed-tempへ保存する。
`--help`の表示と、`atk info`のように結果を表示して終わるサブコマンドも同じ共通処理を実行するため、同じ量で判定する。

量によらず保存するのは、結果をファイルとして受け取る呼び出しに限る。
一括取得の消費側が保存ファイルから全見出しと本文を確かめるため、FILENAMEを2件以上指定するか`--all`を指定した`atk wi show`を保存する。
逐語引用の出所ファイルとしてWI投入担当へ渡すため、`atk run-script session-review-evidence`の`--user-events`を保存する。
単発の`atk wi show`と`--detail`などの単発の証拠照会は、その場で本文を読むため通常の量の判定に従う。
完成条件証拠のWI取得は`_atk/wi/entries.py`の指定名読取を同一プロセスで使い、CLIの直接表示・保存先を逆解析しない。
showのfilename検証、状態順、repository・type・source条件は共通処理が所有し、同期と表示は呼出側が持つ。

2026年10月3日の障害対策（`incidents-concurrency.md`「並行実行の競合」の同日の事例）は、保存の判断を生成側へ置き、短いWI本文と証拠照会も保存した。
2026年10月4日に、短い単発照会のたびに保存ファイルを開く往復が増えることを観測したため、量によらない保存をファイルとして渡す用途へ狭めた。
保存先を呼び出し側に組み立てさせない対策の目的は保ち、その他の照会は既存の16384バイトの判定で長い出力を保存する。

`atk agents wait`はエージェント環境でJSON Linesを保存せず、通知・終了の内訳と、標準出力全体が16384バイト以下に収まる範囲の通知と結果の本文を`本文開始:`・`本文終了:`の行で囲んで標準出力へ直接返す。
本文は終了ごとに`agents-wait/<session_id>.md`の1ファイルだけが持ち、後続の入力へはそのパスを渡す。
待機の後に本文ファイルを開く呼び出しが毎回生じていた（2026年9月29日以降のClaude Codeの記録で471件）ため本文を表示し、同じ本文を出力の保存物とrun記録へ重ねて保存していた状態を2026年10月25日に解消した（ユーザー指示）。
本文の範囲の行は、委譲先が待機の出力を引用しても回収の根拠に数えない。
本文ファイルの書込が成功してから配送する契約は保持する。
標準出力は保存先・行数を返し、量によらず保存する呼び出しは続けて呼び出し元が次の判断に使う値を返す。
`--user-events`は`kind`が`user`の行ごとに記録位置と本文の冒頭を`発話: record=<record> line=<line> <冒頭>`で返す。
WI投入担当へ渡す出所は保存ファイルのままにし、呼び出し元が記録位置を取り出す追加の照会（`jq`・`sed`・`cut`など）を不要にするためである。
`record`はコロンを含むため`record=`の形で示す。
`--since`は省略でき、省略時はメイン記録の最初から返す。
呼び出し元が時刻を推測して渡していたためである。
量によらない保存の判定と保存後の表示は`atk.py`の1つの定義で対応付け、保存する呼び出しを加えるときに表示の要否を同じ箇所で決める。
量によらず保存する呼び出しの本体が非0で終わった場合は、保存後の要約を呼ばず、保存した出力のうち`kind`が`error`の行の本文と次の操作を表示する。
要約は成功した結果の件数を示すため、失敗の出力へ適用すると`--user-events`の「発話: 0件」のように、失敗を結果が無いことと読める表示になる（2026年11月10日の振り返りで観測）。
判定を呼び出しごとの要約へ置かず共通の保存処理へ置き、保存後に件数を示す呼び出しを加えた場合も同じ扱いになるようにする。
標準エラーの保存先は`標準エラー保存先:`の標識を使う。
`session-review-evidence`の`--grep`・`--tool-calls`は通常の量の判定を保つ。
保存した場合だけ、各`match`・`tool-call`を`一致: record=<record> line=<line> kind=<kind> [role=<role>] [tool=<tool>] <冒頭>`で保存順に表示する。
一致が20件を超える場合は、全件数・kindとrole/tool別の件数・件数上位10記録の件数と先頭20件だけを表示し、残り件数と保存先から読む方法を示す。
全件を表示していた版（2026年11月5日）は、一致が多い検索で保存した全量と同程度の量を配送し、保存の目的を失わせた（保存出力13,736行の検索で約2.5MBを配送した報告がある）。
件数に比例しない要約と先頭の一致で記録位置を選ぶ手掛かりは保たれ、残りは保存ファイルから記録・kindを限定して読める。
冒頭は改行を空白にした先頭160文字で、短縮時は`…`を付ける。
該当なしは`一致: 0件`を返す。
`--summary-only`と`--fixed-string`は一覧の対象外とする。
保存条件と保存後の表示を独立に選び、既存の`auto_save`のコールバックを使うことで、短い照会の直接表示と全量JSONLを保ちながら、保存後に一致一覧を再加工する操作を省く。
`--user-events`の冒頭は従来の60文字を保つ。
`atk wi show`の全文保存後は、保存先・行数に続け、AWIの`## ユーザーコメント`またはUWIの`## 回答`がある項目のファイル名と保存先での開始行を1行ずつ全件示し、記入欄が無い項目は`記入欄なし: <N>件`の1行で件数を示す。
記入欄が無い項目も1行ずつ示していた版（2026年10月18日）は、多数の項目を取得する調査で、使われない行を項目の数だけ配送した（304件の取得で304行の報告がある）。
件数の行を残すのは、行が1つも無い場合に、記入欄が無いことと案内が出なかったことを区別するためである。
保存後の案内を加えるときは、読み手が次の判断に使う対象だけを個別に示し、残りは件数で示す。
保存で抑えた出力量を、案内が対象の件数に比例して戻さないためである。
単発の長い出力も同じ保存後処理を通し、本文の冒頭だけを読む場面でも是正要求を含み得る記入欄へ到達できるようにする。
記入欄は既存のユーザーコメント解析と回答見出しの定義から判定し、コードフェンス内の見出しを除外する。
保存本文と直接表示・要約表示の形式は保持する。
WIの表記診断は全量を標準エラーへ直接書き、16384バイトを超える場合だけ共通の保存機構が`標準エラー保存先:`へ保存する。
短い診断のたびに派生ファイルを作成しないためである（2026年10月25日、ユーザー指示）。
常駐のserve・process-loopとlogsの追従は逐次表示を維持し、人の端末は直接表示とリダイレクトを使う。
公開の保存先指定は全て除去した。
本文を必要とする消費側へ保存の判断を戻す案は、保存先の組み立てを残すため採らない。
stdoutだけの保存ではstderrの表記診断を失うため、両ストリームを分ける。

却下した代替案は、待機コマンドの包装を検出するhookを追加する案である。
包装の原因は、背景実行の上限を一律に求める規範、`atk agents wait`のヘルプにあった上限値の欠落、および保存先の指定を呼び出し側に任せる設計であり、これらを直せば包装する理由が消える。
