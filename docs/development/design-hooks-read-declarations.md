# 読込宣言の解析と資料解決の設計記録

[設計記録の索引](design.md)から参照する、読込宣言の解析と資料解決の記録である。

## PreToolUseの個別設計

### 宣言型読込表による操作前配送

読込表の「契機」と「配送操作」を`_common/read_triggers.py`が解析し、`pretooluse/read_delivery.py`が必要範囲の所在と取得操作を案内する。
取得は、同じ主体がその範囲の本文を受信した事実とする。
`document_reads.acquisition_state`が現在範囲の取得済み、旧版取得後の更新、未取得を区別し、案内・圧縮候補・作業契約が共通の意味を使う。
表の条件・必要節は文書が所有し、配布物、プロジェクトとユーザーのスキルが同じ表を宣言できる。

読込表の「契機」と「配送操作」は、資料を選んで読む判断の行では省略する（2026年11月11日）。
省略した行は、契機を`判断`、配送操作を資料列から解決した資料自身の読取として解析器が導出する。
本文が名指しし表に行の無い資料には、解析器が定型文の条件の宣言を補う。
変更前は、導出と同じ値の列と、本文の名指しを写した定型文の行が、エージェント向け文書707件の読込表の行の約6割（1,084,131バイトのうち653,962バイト）を占めていた。
導出行の配送操作は資料の解決で求まるため、hookは読取対象の名前が資料列に現れる行だけを解決し、宣言一覧の資料解決の遅延を保つ。
補う宣言は本文の全行の解決で求まるため、hookは読込条件の候補の通知で、主体が取得済みの宣言元のうち読取対象を名指しする文書だけ求める。
全文書の補完を毎回求める案は、1回のhookで全エージェント向け文書の本文を解決することになるため採らない。
機械向けの宣言を別ファイルへ移す案は、同じ条件を2か所へ書かない規定（`agent-basics/skills/writing-standards/references/agent-documents-basics-read-tables.md`「読込表」）に反するため採らない。
`share/rules/`配下の規範は、hookと同期処理が配送するため補完の宣言元にしない。
補完の導入により、本文の名指しに読込表の行を求める検査（参照先へ届く経路の検査）は成立しなくなったため撤去し、参照先の実在の検査を残した。
`../`で始まる相対パスは名指しに数えず、補完の対象にしない。
表の書換えで定型の行を一律に外すと、本文が`../`の相対パスだけで示す資料への103組の経路（文書62件の100行）が失われるため、この行は明示の2列の行として表に残した。
`../`の相対パスを名指しに加える案は、この103組を回復する一方で、変更前に行が無かった163組へ新しく宣言を補い、読込条件の候補の通知を増やすため採らない（変更前後の解析結果の全量比較で確認した。前者の案を一度実装し、実行レビューの指摘を受けた再比較で増加を見つけて戻した）。
2026年11月13日の再比較でも、名指しに加えると明示の行が無い190組へ宣言が増えたため、同じ判断を保った。
写すだけの行を置かない規定（同`agent-documents-basics-read-tables.md`「読込表」）は、仕組みが補える資料に限ると読める形へ直した。

読込表の1行が並べて指す資料（同時に全文を読む資料）どうしで、条件と資料の組が同じ行を重ねていないかを、`read_triggers_references.simultaneous_duplicate_rows`と不変条件試験で検出する（2026年11月13日）。
資料を分割したときに元の表を全分割先へ写すと、同じ案内を繰り返し読ませるためである。
同じ条件の行が続く場合も同時に読む組に含める案は、汎用の条件（「本文で基準を使う資料の選択・取得時」など）で別々に選ぶ資料を並べた表まで同時読込として扱うため採らない。

Claudeのhookによる資料解決は、公開の`claude plugin list --json`が返す有効状態とscopeを用い、実効host・projectに合う資料を選ぶ。
通常のツール呼出しごとのCLI起動を抑えるため、既存のsession_stateへ公開一覧を保存し、設定・導入台帳・host実行ファイルなどのファイルメタデータと環境のハッシュが同じ間は再利用する。
設定と台帳には内容のハッシュも併用し、時刻とサイズが同じ書換えを検出する。
Windows・macOS・WSLも同じ方式を使う。
選択したrootの実体は各要求で確認する。

ファイルメタデータと環境のハッシュで検出できないWindows registry・macOS MDMなどの管理ポリシー変更は、次のSessionStartで一覧を消去して反映する。
同一セッション中の即時反映は保証しない。
通常のファイル設定と導入台帳の変更はハッシュの変化で再取得する。
plugin rootの候補が1つの場合に公開一覧の取得を省く案は、単独導入されたpluginの無効状態を判定できないため採らない。
ホストの設定合成を独自に再実装する案は、選択規則の重複を増やすため採らない。
独自常駐や時間だけで失効するキャッシュも追加しない。

既存の委譲・検索・原因分析・一時領域作成・本文編集・検証の判定は`operation_skills.py`へ保持し、取得対象の対応を`share/read-trigger-bootstrap.md`へ集約する。
起動時の行は所属スキルの起動・本文読取で取得を案内する。
判断の行は先行する起動・入力読取と、確定操作の補完を区別する。
確定操作だけへの対応を判断前の取得として数えない。
資料の取得と後続操作の順序はtranscriptで確認する。
宣言を改訂するエージェントは、その変更の検証記録へ対象・資料・案内できる時点・観測範囲を記録する。
確定操作を経ない判断など公開イベントがない経路は、観測手段がない理由とともに保証範囲から分ける。
確定操作時の案内では、資料を読んだ後に書いた内容を基準で見直し、必要な修正をするよう求める。
本文編集は、編集ツールとBashで本文を作成・更新する操作の意味をそろえる。
Bashの静的な書込先へのheredoc・here-string、インプレース置換、Pythonの本文書込を対象にし、コマンドの生成出力の保存と複製を除く。
標準入力のheredoc・here-stringは既存のBash解析が保持し、パイプ先のteeも同じ入力として扱う。
managed-tempへの書込は全拡張子を本文作成の案内から除き、WI原稿と計画初版は起草専用の配送操作で案内する。
書込先は同じコマンド内で先行する単独代入を解決してから判定し、未解決の書込先は一時領域の除外の対象にしない。
WI保存の配送操作は検証と本保存を区別する。
独立した確認と意味確認の資料は、起動本文で判別した付随型のWI投入担当には案内しない。
WI原稿と計画初版は一時領域に置いても保存される成果物の原稿であり、書込先ではなく本文の見出し行（`## 反映内容と反映先`、`## 判断材料`、`### 計画メタ情報`）で判定する専用の配送操作が、書く時点で起草規範を案内する（2026年11月13日。保存前の検査まで起草規範が届かなかった事象への対策）。
成果物へ取り込む時点で言語規約を適用する。

hookは資料本文を代替配送せず、絶対パス、ホスト本来の取得手段を警告で案内する。
Claude Codeのメインとagents_serverのtask・delegateでは、通常の`SKILL.md`は完全名を指定したSkillで起動する。
referencesなどはReadと静的Bash読取を使い、AgentサブエージェントはSkillを使えない場合のReadも案内する。
Codexは絶対パスのcatとsedを使う。
規範資料は選んだファイルの全文を取得し、前提・例外を含む基準への到達を担当が確認する。
規範以外の記録類は確認する内容に必要な範囲を選ぶ。
軽量委譲先は既存の起動契約に従い対象外とする。
Codex向けの取得案内は、内側コマンドと外側セルの初回予算をともに20,000へ固定し、結果オブジェクト全体を表示する実行例を生成する。
UTF-8バイト数とJSON包絡から本文量を見積もり、規範の全文、記録類の指定範囲、複数資料に同じ分割を適用する。
1回の枠を超える場合は実際の行バイト数で分割し、複数セルの内側予算を1つの外側セルへ無条件に合算しない。
必要範囲の選択は担当が所有し、単一行だけで枠を超える場合は制約と次の操作を案内する。
資料案内の静的な推定と、担当が規範と対象操作を比較する適用判断は分ける。
誤判定の根拠を既存の作業記録へ残した継続を可能にし、その保存を同じ要求で妨げない。
独立した認可・安全・データ保全・公開契約の保護は維持する。
通知、判断理由、継続後の結果は既存の会話と証拠照会から比較し、新しい全操作台帳を作らない。
修正版や異常状態の解消を利用できる再起動では、work-contractの既存記録へ残工程を保存して再開する。
同じ不具合を読み込むだけの再起動や、未達の完了扱いを回復としない。

非修飾名のプロジェクトスキルは、hook入力のcwdから[`project_skill_dirs`](../../agent-toolkit/agent_toolkit/_common/read_triggers.py)が返す探索範囲と実体を照合する。
範囲外の実体はSkillで起動できないため、必要本文の受信を取得要求の解除へ使う。
起動可能性は`document_reads`に集約し、通常案内・再書込の判定・取得失敗・圧縮後の案内へ同じcwdを渡す。
資料の実在だけでSkillを要求する方式は、取得できない操作を反復させるため採らない。
起動可能なスキルの起動証拠と参照読取の区別を保ち、新しい状態キーや特定のスキル名への例外は設けない。

資料の参照は、宣言を読む文書の所属版で解決する。
plugin manifestを所有しないプロジェクトスキルのplugin修飾参照は、祖先のmarketplaceが`./`相対で宣言し名前が一致するplugin rootを使い、該当が無ければ導入版を使う。
share文書の`${CLAUDE_PLUGIN_ROOT}`は所有pluginのroot、絶対パスで渡された役割文書の起動契約はその文書のrootで解決する。
作業ツリーで規範を改訂する担当が、稼働版に無い新設資料を同じ作業ツリーから取得して作業を続けられるようにするためである。
hook自体のコードは稼働版のままで、変わるのは読む文書の版だけである。
全rootを作業ツリーへ一律に切り替える案と、欠落時に別版を順に探すfallbackは、通常の導入版の選択を壊し版の混在を隠すため採らない。
資料が実際に欠けている場合は、取得失敗の案内へ宣言元を示し、宣言元と解決先の版を区別できるようにする。

宣言の一覧、取得済み資料の宣言の再解決、plugin導入情報の照会は、1回のhook呼出しの中で解析と照会の結果を共有する。
一覧の構文解析では条件・操作・資料列を保持し、操作への照合、正式起動、保存済み選択への再接続で必要となった行だけが資料実体を解決する。
選択された行の資料不在・plugin未導入の診断は保ち、strict検査は全行の実体を検証する。

プロジェクトとユーザーのスキル（プラグインの外にあるスキル置き場の文書）の宣言は、hookの実行時に行単位で扱う（2026年11月13日）。
解析・資料解決で不備が見つかった行だけを宣言から除き、PreToolUseが宣言元・行番号・理由を警告で示し、同じ表の他の行と同じ呼出しの他の判定を続ける。
これらの宣言はユーザーのリポジトリやホームにあり、プラグインの不変条件テストが保存前に検査できない。
過去の版を取り出した作業ツリーには廃止済みの語彙も残るため、1行の不備で呼出し全体を止めると、読込案内と読取記録がすべて失われていた。
プラグイン配下の宣言は不変条件テストが保存前に検出するため、従来どおり例外とする。
`hook.py`の障害応答で宣言の例外だけを警告に変える案は、例外の時点で同じ呼出しの他の判定が止まっているため採らない。
ユーザー側の宣言の資料を解析時にすべて解決する案は、前段の資料解決の遅延を崩すため採らない。
プロジェクトのスキルが`.claude/`で始まる値で書く資料は、最も近い`.claude/skills`を持つリポジトリの根から解決する。
PostToolUseのSkill観測は宣言元・選択先と実際の読取先を候補とし、未選択の全資料を先に展開しない。
役割起動判定の定数だけを使うBashではMarkdownパーサーを生成せず、起動本文を解析するときに初めて初期化する。
次のhook呼出しでは資料・設定・主体・cwdを評価し直し、取得後の資料改訂や導入先の変更を検出する。
セッションをまたぐ解析結果の保存や常駐サービスは置かない。
取得案内を送った記録のキーは`read_guidance_key`の1関数で生成し、保存・重複判定・未解消判定が同じキーを使う。
