# セッションの終了の設計記録

[設計記録の索引](design.md)と[担当の責務と工程間の知識境界の設計記録](design-workflow-boundaries.md)から参照する主題別の記録である。

## セッションの終了

レーン資源の作成と所有登録、配置の決定、固有create・prepare・deleteの手順はatk lane createが持ち、既定の作成先は主作業ツリーの.claude/worktrees/process-wi-lane-NNに固定する。
メインは準備結果と両出力を検収してから担当を起動し、統合後も同じ資源を追加に使えるよう保持する。
通常終了のagents-exit-sessionとprocess-loopの子終了後は、全登録の判定、全工程・外部プロセスの終了、clean・Git登録一致・統合先到達を確認する同じcleanupへ接続する。
未統合・dirty・稼働中・不明・途中失敗は成果と登録を残し、同じdeleteは残る処理から再開する。
登録は専用資源の外、回収結果は通常のmanaged-tempへ置いて7日の保持へ委ね、次回開始時にdelete --listから残存を読む。
turnごとのSessionEndで回収する案は担当の再開に使う資源を失い、公開前回収は追加ごとの再作成を生むため採らない。
セッションのmanaged-temp・証拠・主作業ツリーと他sessionの未登録資源は対象外とする。

調査・採否と通常型の計画化は、Claude CodeとCodexのいずれでもメインが下流担当を直接起動する共通手順を使う。
委譲先の起動失敗を別の起動手段へ迂回せず、失敗として返す。
通常処理および明示的な連続処理は、起動時に固定した項目だけを処理し、後始末後にready項目を再取得しない。
`agent-toolkit:process-wi`は起動時に副作用のない終了能力probeを実行し、完了した全条件一致だけを停止可能とし、未実行、読取失敗、値の不一致のいずれかを停止不能とする。
`atk agents-exit-session`は起動時の判定を再利用せず停止直前に対象を新規識別し、PIDの開始時刻と実行ファイルのデバイス・inodeを比べ、一致した場合だけ停止する。
Claude CodeではFunction hooks moduleの`session.start`が、実際に読み込まれたことをセッション別のファイルへ記録する。
`turn.complete`は対話CLIの終了要求を読み、ターン完了後の`/exit`をキューへ入れる。
`/exit`は終了とともに停止するセッション限りの作業が残ると確認画面を表示し、無人の常駐セッションはそこで止まる。
このため`turn.complete`は`/exit`の直前に非durableのcron taskを削除し、Stop hookの`autonomous_exit.py`はバックグラウンドタスクが残る場合に終了要求を取り下げる。
2つを分けたのは、失う状態の有無が異なるためである。
セッション限りのcron taskは終了とともに消えるため、削除しても失う状態が無く、確認画面で「Exit and stop tasks」を選ぶのと同じ結果になる。
バックグラウンドタスク（shell、subagent、monitor、workflowなど）は停止すると作業途中の結果を失うため、自動では止めずに作業の終了を確かめてから終了工程をやり直させる。
cron taskの削除は許可の判定が`allow`の場合だけ行う。
`$.tool.call`は権限確認のダイアログを経由するため、判定を省くと別の確認画面で同じく止まる。
Python側はファイルの更新時刻が現在の本体プロセスの開始より後か確かめ、moduleなしで再開した場合の古い記録を採用しない。
両側が同じ絶対パスを使えるよう、Claude Codeの設定ディレクトリを基準にする。
Pythonの一時ディレクトリだけを使うと、Function hooks側と異なる位置を指し得るため採らない。
Function hooksを読み込まないClaude CodeとCodexへのシグナルによる本体停止は、現在の対話CLI本体として安全に一意識別した自身か、自身が起動して停止識別子を保持した対象だけに行う。
共用プロセスと識別不能な環境では終了案内で完了する。
前記の対象に該当しない場合も同じ扱いとする。
