# 運用機能: Codexの旧版・診断ログ・文脈

## Codex CLI本体の旧版整理

`prune-codex-packages`は実効`CODEX_HOME`の完成済み旧パッケージを整理する。
選択中の版、`selection-history`が記録する直前の選択、使用中の実行体に対応する版を保持し、使用が終わった旧版は次の実行で回収する。
`selection-history`が選択中の版を記録していない場合は直前の選択を特定できないため、公式の整理と同じくそのパッケージを整理しない。
WindowsでCodexのセッション（`codex_processes.py`の`session`）が実行中の場合は整理を延期する。
常駐する管理daemonと更新ループは延期の理由にせず、使用中の版として保持する（延期の理由に含めるとWindowsでは整理が実行されない）。
公式インストーラーは競合版を検出したうえで削除の可否を対話で確認し、非対話実行では削除しない側を選ぶ。
競合版を検出した実行では、シェルの起動ファイルへPATH設定が追記される場合がある。
起動ファイルはchezmoiの配布対象であるため、追記された内容は次回の`chezmoi apply`で配布内容へ戻る。

Windowsでは、導入が置き換えるスタンドアローン版（`packages/standalone/`）から起動したプロセス（会話と同梱の実行体）がある間は、導入と除去を延期する。
mise版の除去は、照会した削除先から起動したプロセスがあるか、その可能性を否定できない間は延期する。
延期時にはPID、取得できたパス、判定根拠、手動の削除コマンド、更新済みの起動先を示す。

### 旧npm版（Codex・Claude Code）

正規版の導入と確認後、PATHなどで旧npm版や正規版以外の起動先を検出すると警告する。
PATHでそちらが先に解決される間は正規版の代わりにその起動先が動くため、警告に表示された正規のフルパスで起動する。
旧npm版の動作中でも、正規版を置き換えられるなら導入を進める。

更新処理は旧npm版に対して `npm uninstall` を実行せず、旧npm版と判定した起動ファイルも削除しない。
重複ツールの整理とminimalモードの整理（重複したnpmパッケージ、standalone版pnpmの`PNPM_HOME`、mise管理のNode、`~/.local/bin`の起動ファイル）は、削除してよいと確認できた対象だけを削除し、それ以外は警告して残す。
確認は通常のnpm・pnpmの配置と`package.json`の`bin`を前提とするため、それ以外の配置に置いた旧npm版は検出できない場合がある。
残した対象の警告は理由を示し、不要と確認できた項目を整理してから`update-dotfiles`を再実行すると、確認できた対象を削除する。
正規版を使う場合はfullモードで導入する。

警告が削除コマンドを表示するのは、削除対象のパッケージを確認できた場合だけである。
不要と確認できた旧npm版は、使用中のプロセスを終了してから、表示された削除コマンドを手動で実行する。
npmの導入先を照会できない場合や`package.json`を読めない場合は、削除対象を確定できないため削除コマンドを表示しない。
この警告は照会コマンドや対象のファイルと診断を示すため、npmや`package.json`を直してから`update-dotfiles`を再実行し、削除コマンドが表示された後に判断する。
npmはパッケージ内のファイルに加え、同名の起動ファイル（Windowsでは拡張子なし・`.cmd`・`.ps1`）も削除する。
警告の有無にかかわらず、先に自分で置いたファイルや編集したラッパーを別の場所へ移す。
パッケージがない配置の起動ファイルは、不要と確認できたものだけ手動で退避する。

## Codex診断ログの通常ストレージ復元

Linuxのpost-apply処理は、旧機構が`/dev/shm/codex-<UID>-<ファイル名>`へ配置した診断ログDBを`~/.codex/`へ復元する。
Codexが停止中であり、ホームディレクトリ側の3ファイルが旧機構の正確なリンクまたは欠落状態である場合だけ復元する。
復元した実行では共有メモリー側を保持し、後続のpost-apply実行で3ファイルの内容一致を確認してから回収する。

ホームディレクトリ側と共有メモリー側のDB、WAL、SHMが1件でも異なる場合は、自動的にどちらか一方を選択しない。
共有メモリー側の集合を`~/.codex/logs_2-restore-conflict-<集合SHA-256>/`へ保存し、復元未完了を警告する。
競合スナップショットは所有者だけが参照できる手動復旧用データであり、post-apply処理は削除しない。
ユーザーが次の手順を完了するまで保持する。

1. Codexを停止したまま、`~/.codex/`、`/dev/shm/codex-<UID>-*`、競合スナップショットの3集合を比べる
2. SQLiteのDB、WAL、SHMを一組として復旧し、通常ストレージ側の内容を検証する
3. 復旧結果を確認した後に限り、共有メモリー側の旧`target`と競合スナップショットを手動で回収する

## Codexの実験的コンテキスト管理

`.chezmoi-source/dot_codex/modify_private_config.toml`はCodex設定の
`features.context_management.experimental_mode`を`false`に設定する。
この機能は、保存の成否と独立に要約なしで会話文脈を破棄する操作をエージェントへ公開する。
2026年10月31日のCodex記録では、作業状態の保存がbackendエラーで失敗した直後に要約なしの切替が2回実行され、受信した依頼が失われた。
保全を担当者の判断に依存させないため、通常の会話圧縮と既存の作業記録を使う。

適用範囲はホーム設定を継承する全起動経路で、いずれも同設定に追加の指定を持たない。
`agents_server`のCodex委譲先は、threadの開始・再開時に同設定を明示的に`false`で上書きし、ホスト内部の設定継承に依存しない。
Codex組み込みの委譲（`spawn_agent`）の子threadへの継承はホスト内部の動作であり、未確認である。
2026年9月6日から10月31日まではホーム設定で`true`にしていた（元の要求は、圧縮時間を減らすために有効化も含めて検討することだった）。
有効化前の基準はリポジトリ外のセッション記録で計測したコンパクション合計69回（メインのClaudeセッション5回・合計1284.9秒、Claude委譲先10回・合計2230.3秒、Codex委譲先54回）である。
有効化後の対照値と通常圧縮による所要時間の変化は計測しておらず、有効化前の測定値は無効化の判断の根拠には使っていない。
