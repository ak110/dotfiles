# 運用機能: Codexの旧版・診断ログ・文脈

## Codex CLI本体の旧版整理

`prune-codex-packages`は実効`CODEX_HOME`の完成済み旧パッケージを整理する。
選択中の版、`selection-history`が記録する直前の選択、使用中の実行体に対応する版を保持し、使用が終わった旧版は次の実行で回収する。
`selection-history`が選択中の版を記録していない場合は直前の選択を特定できないため、公式の整理と同じくそのパッケージを整理しない。
WindowsでCodexのセッション（`codex_processes.py`の`session`）が実行中の場合は整理を延期する。
常駐する管理daemonと更新ループは延期の理由にせず、使用中の版として保持する（延期の理由に含めるとWindowsでは整理が実行されない）。
旧版の整理を`chezmoi apply`後の処理が担うのは、公式インストーラーが非対話実行時に競合するnpm版を残すためである。
公式インストーラーは競合版を検出したうえで削除の可否を対話で確認し、非対話実行では削除しない側を選ぶ。
競合版を検出した実行では、シェルの起動ファイルへPATH設定が追記される場合がある。
起動ファイルはchezmoiの配布対象であるため、追記された内容は次回の`chezmoi apply`で配布内容へ戻る。

Windowsでは、導入が置き換えるスタンドアローン版（`packages/standalone/`）から起動したプロセス（会話と同梱の実行体）がある間は、導入と除去を延期する。
除去はmise版・npm版ごとに、照会した削除先から起動したプロセスがある間はその版の除去だけを延期する。
判定は`setup_cli_common.find_windows_cli_processes`がプロセスの実行ファイルの所在で行い、除去する版ではnode・miseが起動したスクリプトの所在も見る。
所在を読めず衝突を否定できないプロセスでも延期する。
判定は該当したプロセスごとにPID、読めた実行パス、根拠（`Evidence`。所在を確かめたか、実行ファイル・起動引数を読めないか、名前だけで起動したか）を返し、延期の表示はこの結果から作る。
除去の延期の表示は、削除コマンドと、旧版がPATHで先に見つかる間に使う更新済みの起動先（Codexは`bin/codex.cmd`の起動管理、Claude Codeは`~/.local/bin/claude.exe`）も示す。
削除コマンドは`setup_cli_common.format_user_command`が作り、推奨するPowerShell 7でそのまま実行できるよう、PowerShellのコマンドと明記して、単一引用符で囲んだ実行パスの前に呼び出し演算子`&`を付ける。
npmの`uninstall`はパッケージと一緒に、`package.json`の`bin`の名前の起動ファイルを中身を確かめずに削除する。
対象はWindowsではprefix直下の`<bin>`・`<bin>.cmd`・`<bin>.ps1`、POSIXでは`bin/<bin>`である。
npm版の除去は、この起動ファイルを`setup_cli_common._find_npm_package`で列挙し、存在するものが全てnpmの生成物と確かめられた場合だけ`uninstall`する。
npmの生成物とみなすのは、POSIXではパッケージ配下へのシンボリックリンクだけである。
Windowsでは、ファイル全体が既知のnpmの生成形式のどれかと一致し、その形が`bin`の実体を参照する起動スクリプトだけである。
参照の形や引数の渡し方など本文の一部だけで判定すると、ユーザーが足した行や起動オプションを見逃して削除したため（2026年11月20日の検証で観測）、ファイル全体を比べる。
既知の生成形式は`pytools/_internal/npm_cmd_shim_forms.json`にある。
npm 6.0.0が同梱した2.0.2から、npm 12が同梱する9.0.2までのcmd-shimの全ての公開版が、`bin`の実体の先頭行（`#!/usr/bin/env node`と、shebangなし）ごとに生成する形を、`bin`の実体のパスを差し込む位置とともに持つ。
データは手で書かず、`uv run --frozen python scripts/gen_npm_cmd_shim_forms.py`が各版の配布物をnpmで取得して生成させ、別のパスでも生成物を再現できることを確かめてから書き出す。
cmd-shimの新しい版が公開されたら、同じコマンドで再生成する（`--check`は書き出さずにデータとの一致を確かめる）。
再生成までの間、新しい版が生成する起動スクリプトは生成物と確かめられないものとして扱い、自動では削除しない。
1つでも生成物と確かめられないファイルがあるパッケージは自動では削除せず、そのファイルと削除コマンドを1つの警告で示す。
`package.json`を読めないパッケージは削除するファイルを確定できないため自動では削除せず、そのパスと、同じ版の`package.json`の復元か読取権限の修正の後に再実行する手順を1つの警告で示す。
判定と表示はパッケージごとに1回にする。
本体の無い起動スクリプトの削除も同じ判定を使い、既知の生成形式と一致し、自身のディレクトリにない`node_modules/<パッケージ>`配下を参照するものだけを削除する。
使用中の可能性がある旧版は自動では削除せず、PATH全体の並べ替えもしない。
mise版・npm版の削除先を照会できない場合はその版の除去を見送り、失敗した照会のコマンドと診断を表示する。
照会の成否は導入の延期に使わない。

## Codex診断ログの通常ストレージ復元

Linuxのpost-apply処理は、旧機構が`/dev/shm/codex-<UID>-<ファイル名>`へ配置した診断ログDBを`~/.codex/`へ復元する。
Codexが停止中であり、ホームディレクトリ側の3ファイルが旧機構の正確なリンクまたは欠落状態である場合だけ復元する。
復元した実行では共有メモリー側を保持し、後続のpost-apply実行で3ファイルの内容一致を確認してから回収する。

ホームディレクトリ側と共有メモリー側のDB、WAL、SHMが1件でも異なる場合は、自動的にどちらか一方を選択しない。
共有メモリー側の集合を`~/.codex/logs_2-restore-conflict-<集合SHA-256>/`へ保存し、復元未完了を警告する。
競合スナップショットは所有者だけが参照できる手動復旧用データであり、post-apply処理は削除しない。
ユーザーが次の手順を完了するまで保持する。

1. Codexを停止したまま、`~/.codex/`、`/dev/shm/codex-<UID>-*`、競合スナップショットの3集合を比べる
2. SQLiteのDB、WAL、SHMを一組として復旧し、通常ストレージ側の内容を検証する
3. 復旧結果を確認した後に限り、共有メモリー側の旧`target`と競合スナップショットを手動で回収する

## Codexの実験的コンテキスト管理

`.chezmoi-source/dot_codex/modify_private_config.toml`はCodex設定の
`features.context_management.experimental_mode`を`false`に設定する。
この機能は、保存の成否と独立に要約なしで会話文脈を破棄する操作をエージェントへ公開する。
2026年10月31日のCodex記録では、作業状態の保存がbackendエラーで失敗した直後に要約なしの切替が2回実行され、受信した依頼が失われた。
保全を担当者の判断に依存させないため、通常の会話圧縮と既存の作業記録を使う。

適用範囲はホーム設定を継承する全起動経路で、いずれも同設定に追加の指定を持たない。
`agents_server`のCodex委譲先は、threadの開始・再開時に同設定を明示的に`false`で上書きし、ホスト内部の設定継承に依存しない。
Codex組み込みの委譲（`spawn_agent`）の子threadへの継承はホスト内部の動作であり、未確認である。
2026年9月6日から10月31日まではホーム設定で`true`にしていた（元の要求は、圧縮時間を減らすために有効化も含めて検討することだった）。
有効化前の基準はリポジトリ外のセッション記録で計測したコンパクション合計69回（メインのClaudeセッション5回・合計1284.9秒、Claude委譲先10回・合計2230.3秒、Codex委譲先54回）である。
有効化後の対照値と通常圧縮による所要時間の変化は計測しておらず、有効化前の測定値は無効化の判断の根拠には使っていない。
