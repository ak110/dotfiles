# 運用機能: Codexの旧版・診断ログ・文脈

## Codex CLI本体の旧版整理

`prune-codex-packages`は実効`CODEX_HOME`の`packages/standalone/`と`packages/app-server-daemon/`にある完成済み旧パッケージを整理する。
`CODEX_HOME`未設定時は`~/.codex`を使う。
選択中の版と使用中の実行体に対応する版を保持し、使用が終わった旧版は次の実行で回収する。
公式インストーラーと同じ`install.lock`で排他し、WindowsでCodexが実行中の場合は停止せず整理を延期する。
Windowsでの実行中と通常の更新排他競合は正常な延期として0で終了する。
選択先の不良、必要な使用中情報の取得失敗、配置の権限エラーでは対象を保持し、理由と次の操作を示して非0で終了する。
削除失敗も非0で終了する。
案内された原因を解消した後、同じコマンドを再実行する。

整理はCodex本体の導入成功後に実行する。
手動で整理する場合は`prune-codex-packages`を実行する。
手動操作と保持・延期の説明は[Codex利用ガイド](../guide/codex-guide.md#完成済みパッケージの整理)を参照する。

`chezmoi apply`後の処理はCodexの公式インストーラーを非対話で実行した後、mise npmバックエンドとPATHから解決される非正規npm版のCodexを除去する（エンドユーザー向けの説明は`docs/guide/codex-guide.md`「Codex CLI本体」）。
旧版の整理を`chezmoi apply`後の処理が担うのは、公式インストーラーが非対話実行時に競合するnpm版を残すためである。
公式インストーラーは競合版を検出したうえで削除の可否を対話で確認し、非対話実行では削除しない側を選ぶ。
競合版を検出した実行では、シェルの起動ファイルへPATH設定が追記される場合がある。
起動ファイルはchezmoiの配布対象であるため、追記された内容は次回の`chezmoi apply`で配布内容へ戻る。

## Codex診断ログの通常ストレージ復元

Linuxのpost-apply処理は、旧機構が`/dev/shm/codex-<UID>-<ファイル名>`へ配置した診断ログDBを`~/.codex/`へ復元する。
Codexが停止中であり、ホームディレクトリ側の3ファイルが旧機構の正確なリンクまたは欠落状態である場合だけ復元する。
復元した実行では共有メモリー側を保持し、後続のpost-apply実行で3ファイルの内容一致を確認してから回収する。

ホームディレクトリ側と共有メモリー側のDB、WAL、SHMが1件でも異なる場合は、自動的にどちらか一方を選択しない。
共有メモリー側の集合を`~/.codex/logs_2-restore-conflict-<集合SHA-256>/`へ保存し、復元未完了を警告する。
競合スナップショットは所有者だけが参照できる手動復旧用データであり、post-apply処理は削除しない。
ユーザーが次の手順を完了するまで保持する。

1. Codexを停止したまま、`~/.codex/`、`/dev/shm/codex-<UID>-*`、競合スナップショットの3集合を比べる
2. SQLiteのDB、WAL、SHMを一組として復旧し、通常ストレージ側の内容を検証する
3. 復旧結果を確認した後に限り、共有メモリー側の旧`target`と競合スナップショットを手動で回収する

## Codexの実験的コンテキスト管理

`.chezmoi-source/dot_codex/modify_private_config.toml`はCodex設定の
`features.context_management.experimental_mode`を`false`に設定する。
この機能は、保存の成否と独立に要約なしで会話文脈を破棄する操作をエージェントへ公開する。
2026年10月31日のCodex記録では、作業状態の保存がbackendエラーで失敗した直後に要約なしの切替が2回実行され、受信した依頼が失われた。
保全を担当者の判断に依存させないため、通常の会話圧縮と既存の作業記録を使う。

適用範囲はホーム設定を継承する全起動経路である。
対話起動、`bin/codex-medium`・`bin/codex-xhigh`とWindowsペア、`pytools/agent_launcher.py`、`atk run-skill`と`atk wi process-loop`の新規・再開はいずれも同設定に追加の指定を持たない。
`agents_server`のCodex委譲先は、threadの開始・再開時に同設定を明示的に`false`で上書きし、ホスト内部の設定継承に依存しない。
Codex組み込みの委譲（`spawn_agent`）の子threadへの継承はホスト内部の動作であり、未確認である。

2026年9月6日から10月31日まではホーム設定で`true`にしていた（元の要求は、圧縮時間を減らすために有効化も含めて検討することだった）。
有効化前の基準はリポジトリ外のセッション記録で計測したコンパクション合計69回（メインのClaudeセッション5回・合計1284.9秒、Claude委譲先10回・合計2230.3秒、Codex委譲先54回）である。
有効化後の対照値は計測しておらず、通常圧縮による所要時間の変化も未測定である。
これらの値は過去の基準であり、無効化の判断の根拠には使っていない。
