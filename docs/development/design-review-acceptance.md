# ユーザビリティと完成条件の判定の設計記録

[設計記録の索引](design.md)と[検収根拠とレビュー担当間の知識境界の設計記録](design-review-evidence.md)から参照する主題別の記録である。

## ユーザビリティレビュー

画面の実装では、同じ対象HEADで独立したユーザビリティレビューと実行レビューを並列に始める。
ユーザビリティレビューは画面を描画・操作し、自動テストでは合否を判定できない使いやすさ（表示の意味が伝わるか、配置、文言、操作の分かりやすさ、狭幅・拡大・キーボード操作時の到達性など）を判定する。
受入シナリオの期待結果との一致のような機能の正しさは`writing-standards/references/testing.md`「検証単位の選定」で選んだ層の自動テストが担い、実行レビューが提出された検証記録を差分と比べて確かめる。
両者の観測は互いの完了を入力に必要としないため、修正後も同じHEADで並列に再判定し、統合前に両方の収束を確認する。
使いやすさの判断基準は`review-standards`の`references/reviewer.md`「ユーザビリティレビューの判定」と`writing-standards`の`references/ui-ux.md`へ置く。
ユーザビリティレビューの`usability-review.parent.md`と`usability-review.subagent.md`は起動と返却の手順だけを持つ。

却下した代替案は、ユーザビリティレビューが受入シナリオの期待結果との一致も描画で確かめる方式である。
委譲元が計画の期待結果を主要シナリオとして渡すと、E2Eテストと同じ確認を重ねるだけになり、自動テストでは判定できない使いやすさを評価する工程が残らないため採用しない。

## 完成条件の判定と受領

新形式AWIの条件表は反映内容の最上位項目ごとに主要完成状態を持ち、出典の`反映内容N`で原文へ対応付ける。
起動時検査は各項目の被覆を確かめ、レビュー担当は項目内の具体的な成果も原文と読み比べる。
条件数だけの検査と節全体への出典では、要約中に一文が落ちても発見できなかったため、項目の被覆と意味の検収を分担する。
文単位の意味検査の自動化は採らず、背景や別項目への割当にも同じ出典と除外理由を持つ行を使う。
除外理由の行は主要完成状態として理由と原文・採否記録の一致を判定し、割当先の完成を判定する行とは区別する。
第三の区分を加える案は既存の判定・統合契約を広げるため採らず、既存区分で判定する対象を明記する。
定義は`agent-toolkit:/share/exec-review-recording-contract.md`「記録する行と要求単位」に置く。
構造上の必要条件は`agent-toolkit/agent_toolkit/_plan/review_contract.py`へ集約し、公開startの検査とリポジトリ直下の`scripts/review_eval.py`の生成が同じ定義を使う。
意味的な方式変更や過去証拠の充足は、この構造検査の成功とは別に検収する。
評価事例は計画・commit対応・関連WIをGit保存版へ固定し、同じ抽出原本の一覧を生成・起動検査・レビューへ渡す。
保存版の欠落を最新本文で代用する案は、評価する要求を後日の編集で変えてしまうため採らない。

検証結果は初回レビューの前に取得版、入力・環境条件、要求別の観測箇所を対応付けて渡す。
実行レビューはその保存証拠の適用可否を独立に判断し、不足または影響差分だけを追加観測する。
読者別探索では、起動側が検査済みの保存比較資料について本文と判定範囲の意味を読み、Git識別子だけの入力では指定版を取得する。
この分担により、起動前の形式・完全差分検査を各読者が再計算しない。

実装担当は計画の検証コマンドをハーネスの標準実行で動かし、返却の検証結果へコマンド・終了コード・要点と完全OIDの検証HEADを記す。
実行レビュー担当は対象HEADで必要な検証を自ら実行し、返却へ`レビューHEAD: <完全OID>`と、条件ごとの`<WI> 完成条件<N>: 達成|未達|根拠不足 — 根拠: <実行結果またはパス:行>`を残す。
原文要求に由来する条件も同じ行で扱う。
委譲元は条件番号の過不足・重複、レビューHEADと統合するHEADの一致、未達・根拠不足の処置、レビュー指摘管理表の未応答0件を確かめて受領する。
大きな返却は同じ担当が保存・全文読戻しした正式原本を直接受領し、同じ7行・条件・対象集合の検収を適用する。
通知へ全文を再生成する案は、大きなJSONと根拠を重複生成し、取り違えを増やすため採らない。
新しいHEADでは全条件を再判定する。

`達成`行の根拠は、観測した所在（試験名、実行記録・CI run、ファイルと行・見出し、commit、検証記録の箇所）と、そこで観測した条件固有の内容（値・名前・件数・終了コード・成否など）の組を必須とする。
条件文の再掲は括弧や前後の語の形を問わず観測内容に数えず、突き合わせ・確認・判定を述べるだけの句も同じとする。
組を欠く行は担当が`根拠不足`とし、委譲元は件数・HEADが一致しても受領せず差し戻す。
同じ所在を複数の条件で使う場合は、所在の中の観測箇所を条件ごとに書き分ければ受領する。
言い回しの検出をやめて組の有無で判定するのは、行の違いを表面構文で比べる判定が2026年10月3日・5日・8日の改訂ごとに列挙外の形で回避されたためである。
2026年10月5日の境界は、区切りか括弧で切り離された再掲だけを識別情報として除き、文の一部として原文を含む語を観測内容として残した。
2026年10月25日には、各行へ`完成条件「<原文>」について、…照合し、達成と判定した。`を書いた根拠が、閉じ括弧の直後に助詞が続くためこの境界に届かず、14行が受理された。
組の規則は再掲の形によらず所在を求めるため、言い換えた要約や括弧の無い再掲も同じ規則で差し戻せる。
組を持つが別の条件を満たす所在を書いた誤りはこの規則では検出できず、受領時の意味の判定に残る。
レビューの指摘数だけでは、指摘にならなかった条件が既存実装で成立したか、根拠を取得できなかったかを区別できないため、条件ごとの判定行を返却の必須項目にする。
統合するレーン担当がWI本文と全差分を再調査する案は、レビューと同じ調査を重ね、検収の主体間で判定が分かれるため採用しない。

計画外の条項は、既存の`review_contract`入力へMarkdownの「条項・内容・出典」の組と計画別の判定対象外commitとして渡す。
履歴の書換え後の影響判断は`git range-diff`と`git diff --name-only`を直接使い、レーンの引き継ぎ記録へ記す。
読者別探索の比較資料は、Git管理下では`repository`・`base`・`head`・`paths`のgit参照形式で渡し、担当が`git show`・`git diff`で読む。
再発防止観点の観点ファイルは、`git grep -l`と配布root内の`rg -l`で観点見出しを持つMarkdownを列挙した和集合を渡す。
レーンの受領は返却本文、`git rev-parse <branch>`、`atk wi show`のadopted、`atk plans list`と保存先の実在で確かめる。
WI原稿の準備は原稿ごとの`wi-quote-check`と`atk wi add`・`atk wi edit`の`--dry-run`で行い、原稿・出所・成立性の証拠を独立検収へ直接渡す。

2026年10月25日に、完成条件証拠のJSON、未判定検証記録と行ごとのHEAD照合を撤去した（ユーザー指示）。
同時に撤去した生成・確認・準備の公開スクリプトは次の9件である。

- `exec-review-evidence-check`、`verification-record`、`plan-verify`
- `review-contract`、`review-impact`、`reader-fit-prepare`
- `recurrence-items`、`lane-receipt-check`、`wi-draft-prepare`

独立文脈レビューのHEADと条件ごとの判定という目的は、標準の検証結果と既存の返却で満たせる。
専用の入力形式を各担当が毎回学び直す費用と保守の費用が、便益を上回った。
撤去前の構造と検査規則の記録は、撤去前のcommit `c406272ef`の本書の「完成条件証拠と証拠検査」以降の節にある。
WIとcommitの対応は計画の対応記録（`<stem>.wi-commits.jsonl`）を保持する。
git notesも試したが、設定なしのamendで対応が失われ、終了AWIの処理結果の更新も置き換えられないため採用しない。
