# statuslineの表示の設計記録

[設計記録の索引](design.md)から参照する、statuslineの表示の記録である。

## statuslineの表示

各行の左端は`label (engine:model/effort)`を表示し、Codexの最新turnがfast modeならmodel/effortの後ろへ`@fast`を付ける。
effortが無ければmodelの後ろへ付ける。
項目を持たない旧形式と他engineの表示は保持し、`label`が空の場合は起動区分を使う。
採用したモデルの完全IDとeffortを状態ファイルから読み、設定時の候補表記と同じ形で示す。
右端は経過時間、文脈使用量、状態の順に` · `で区切り、labelを重ねて表示しない。
文脈使用量は委譲sessionの直近のモデル文脈のトークン数と、正の上限がある場合の使用率であり、Claude CodeのAgent行と同じ`subagent.rs`の`format_tokens`で描く。
使用量の更新は活動時刻を進めない。
モデル名を短縮して`model_type`を先頭へ置く案は、複数工程を段位へまとめた後に工程を識別できず、起動時に採用されたモデルの完全IDも失われるため採らない。
Claude Codeのstatuslineはメッセージ到着などのイベントでだけ再実行されるため、`wait`の待機中は表示が更新されない。
配布設定の`statusLine`へ`refreshInterval`を置き、待機中も経過時間と終了を反映する。
行の整形幅は、取得した端末幅からClaude Codeがstatuslineの描画へ確保する4セルを差し引いた値とする。
4セルは各行の先頭へ付く2セルの字下げと、行末へ残す2セルである。
差し引く値が実際の確保幅より小さいと、整形した行が溢れ、Claude Codeが行末を切り詰めて右寄せした経過時間と状態を欠く。
確保幅は描画された行の表示幅（曖昧幅を1セルとして数えた値）と、statuslineの実行時に観測できる`COLUMNS`の値との差で求める。
整形処理は右寄せ要素を整形幅の右端へ置くため、整形幅が実際の確保幅を超えた分は必ず右寄せ要素から失われる。
このため、確保幅の値を単体テストの期待値としてだけ固定せず、描画された行の表示幅と`COLUMNS`の差を求め直す手順を確保幅の導出根拠とする。

稼働中sessionに`api_error`がある行では（Claudeの再試行とCodexの過負荷の待機の両方）説明欄へAPI失敗の種別、右端へHTTPステータス・失敗開始からの経過・件数を表示する。
Claude Codeの利用上限の解除待ち（種別`usage_limit`）では待てば同じsessionで作業が続き、API再試行と対処が異なる。
このため説明欄へ「利用上限の解除待ち」と種類、右端へ解除までの残り時間と待機の経過を表示する。
限られた表示幅で診断を読めるよう、この間は通常のsession開始からの経過・status表示を診断項目へ譲る。
`api_error`が無い行の説明欄は、最後に観測した行動を表す`last_action`を優先し、`last_action`が空の場合は`progress`を表示する。
`last_action`はassistantのテキスト出力ではその抜粋、ツール呼び出しではツール名とその呼び出しの入力を1行へ要約した値、Codex backendでは進行中itemの種別と同じ規則で要約したitemの入力を持つ。
入力の要約は、各項目を`<key>=<値>`の形でkeyの受信順に並べ、文字列以外の値をJSONへ直列化し、改行と連続する空白を1個の空白へ畳んだうえで200文字を超える分を省略記号付きで切り詰めた値とする。
Codexのitemでは、`show`が別項目として返す`type`と`id`を要約から除く。
`show`が返す未完了のツール呼び出しの項目も同じ要約を`detail`として持つ。
テキスト出力の無い区間でも値が進むため、委譲先が稼働しているかを1行で読み取れる。
`last_action`は任意項目として読む。
長命なMCPサーバープロセスは起動時に読み込んだモジュールを保持し続けるため、statuslineだけが先に更新される区間では`last_action`を持たない状態ファイルが書かれ続ける。
`last_action`を必須項目にすると、statuslineだけが先に更新された間に実在するsessionの行が消える。
入力を含めるのは、同じツール名を繰り返す区間ではツール名だけの表示が変化せず、稼働中と停止中を区別できないためである。
要約を上限で切り詰めるのは、statuslineが表示幅で再度切り詰める一方、`show`の応答では停滞の切り分けに足りる長さを残すためである。
却下した代替案は、`progress`だけを表示元として維持する案と、秘匿値の露出を避けるためにツール名とitem種別だけを表示する案である。
前者はテキスト出力の無い区間で説明欄が`label`のまま止まり、稼働しているかを判別できない。
後者では同じツールを連続して呼び出す区間で説明欄の値が変化せず、稼働と停止を区別できない。
ユーザーへ示す稼働状況には、秘匿を理由に除外する情報を置かない。

知識境界として、session状態の意味（`status`、`progress`、`last_action`、結果の回収）は`agent-toolkit/agent_toolkit/_agents_server/state.py`が持つ。
公開応答への射影は同じディレクトリの`result_projection.py`が持ち、状態ファイルはその射影である。
statuslineは状態ファイルを表示するだけで、sessionの制御と結果の回収をしない。

却下した代替案は、PostToolUseフックが記録する`agents_server_sessions`の状態を表示に流用する案と、状態ファイルを一時ディレクトリへ置く案である。
前者は`start`・`wait`の応答時点だけを観測し、実行中の進捗と終了を表示できない。
後者はPythonの`tempfile.gettempdir()`とRustの`std::env::temp_dir()`で環境変数の参照順が異なり、同じ環境でも別のパスへ分岐し得る。
