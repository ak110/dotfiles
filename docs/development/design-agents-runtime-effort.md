# 同じ委譲会話のeffort変更の設計記録

通常委譲の文脈を保ちながら推論量を調整するため、`atk agents effort up|down [session_id]`を使う。
実行時の判断基準は`agent-toolkit/skills/delegation/references/model-and-effort.md`が所有する。
engine/modelの変更は[引き継ぎ起動](design-agents-runtime-handoff-resume.md)で別の会話へ移す。

## 対象と権限

対象はagents_serverのtask・delegate起動である。
本人はIDを省略でき、直上の委譲元は子のIDを指定する。
親子関係と起動区分はCLIで確認し、適用する所有MCPでも登録簿から再検査する。
段名の直接指定は拒否し、engine/modelが受理する段を1段ずつ移る。
端では値を保ち、変更しなかったことを返す。

軽量起動には公開のeffort操作を提供しない。
exploreの形式回復と不足の前提再確認だけは、内部処理で次turnのeffortを1段上げる。
形式回復と再確認を合わせて1session1回に限り、引上げに失敗しても継続入力と親への診断を保つ。
write工程の開始値をlowにすることと、軽量write起動へ途中操作を公開することは別の仕様である。
review系の開始値はmediumを保ち、通常委譲として相対操作を使える。
統括はgoalがturnを終えさせないため、終了後の再開を前提とする本操作の対象外とする。
対話中のメインも対象外とする。

## 所有MCPと次のturn

CLIは有限期限の要求を既存のsession登録領域へ書き、所有MCPの監視loopが処理する。
希望値と変更履歴を登録簿へ保存してから応答し、CLIが要求と応答を回収する。
新しいdaemonや別の公開モデル変更APIは加えない。

要求の保存前に、登録簿の`effort_receiver`宣言と`processes`先頭の所有者、現在のPID世代の一致を検証する。
宣言は監視を備えるManagerの`activate`・`activate_async`が行い、登録簿へ所有プロセスとともに射影する。
ディスク上のコード更新だけでは、旧Managerの稼働コードは変わらない。
宣言の欠落、未対応の形式、所有者や世代の不一致では要求を保存せず、`request_sent: false`と安全な更新・再起動の案内を返す。
fork後には親の宣言を引き継がない。
送信後の応答喪失は従来の有限期限で扱い、現在値を照会して自動再送しない。

同じ検討をsession解放要求へ当てはめても、配布ファイルの存在は受信側の機能を保証しない。
解放監視の無い所有者へ送れば応答待ちになるため、受信側の稼働機能を確認する観点が必要となる。
この変更ではsession解放のプロトコルと仕様は変更しない。

会話IDを環境へ渡さないCLIは、所有ルート内の表示と登録簿を参照する。
呼出元の最も近い実行祖先とPID世代が一致するsessionだけを本人とし、曖昧な場合は拒否する。
起動の可用性確認中は表示前なので、同じ30秒の要求期限内で表示を待つ。
全ルートの走査や別の索引は使わない。

進行中のturnは中断せず、次のturnへ新しい値を渡す。
Claudeは接続を所有するタスクから既存の`apply_flag_settings`制御へ`effortLevel`を送り、成功を待つ。
Codexは次の`turn/start`、AntigravityとOpenCodeは次のCLI起動引数を使う。
本人の変更はturn番号を予約し、そのturnの終了後に1回だけ継続入力を送る。
予約・送信中の結果は回収対象から外し、別の追送が次のturnを始めていれば予約を消す。

## 規範量の目安

同じ論理資料・版・行範囲の和集合を受信記録から求め、Pythonの文字数で累積する。
本文取得の証拠は会話圧縮でリセットし、累積量と通知済みの記録は同じ会話の間保持する。
250,000文字を超え、現在値が最上段以外の場合に1回案内する。
上げるかどうかの判断は担当へ残す。

初期値は2026年11月12日の既存hook状態2,385件を集計して選んだ。
全文の受信記録がありskills/share/AGENTS/CLAUDEを含む720件について、同じ版を重複除外した文字数を求めた。
中央値は166,392文字、第75百分位は244,401文字だった。
第90百分位は330,561文字、最大は473,822文字だった。
受信記録のある群の上位約4分の1を目安に250,000文字とし、推論量の最適値や因果効果までは主張しない。
既存のセッション状態・effort履歴・最終結果を使い、実績に応じた調整を可能にする。

## キャッシュの観測

2026年11月12日にLinuxで、同じsessionのlowからmediumへの自己変更と自動再開を観測した。
変更後最初のturnのキャッシュ読取入力トークンを、`session-review-evidence --stats`の区間差と応答別の値で確認した。
観測後に確認した版はClaude Code 2.1.322、Codex CLI 0.167.1、Antigravity CLI 1.5.6、OpenCode 1.19.5である。
SDKはロックファイルが選んだ0.2.179を使った。

| engineとモデル | 変更後最初のturnのキャッシュ読取（トークン） | 今回の観測 |
| --- | ---: | --- |
| Claude / claude-sonnet-5-5 | 51,534 | キャッシュ読取あり |
| Codex / gpt-6.1-sol | 43,776 | キャッシュ読取あり |
| Antigravity / gemini-3.8-flash | 0 | 直前のlow応答では読取があったが、変更後最初の応答は読取なし |
| OpenCode / opencode/beam-free | 1,856 | 読取はあるが、直前のlow応答より小さい |

値は今回のモデル・入力・接続の観測に限る。
プロバイダーがどの接頭辞を再利用したかは、この計測だけでは特定しない。
キャッシュ読取が無くても機能は採用し、同じ会話で続けられることとキャッシュ効率を別に評価する。
Codexの重複したUserMessage記録と、OpenCodeの本文より後に確定する使用量は、各応答の確定時刻で区別した。
