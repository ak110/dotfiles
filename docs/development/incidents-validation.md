# 事故・欠陥の記録

本書は`docs/development/incidents.md`から主題別に分割した記録であり、実行時に適用する規範の正本ではない。

## 誤った完了報告・虚偽報告

- 2026年7月: 実装委譲の完了報告が「指摘5件全反映」と主張したが実差分は皆無だった。
  直接原因: 完了報告本文を差分実測と照合せず受理する検収構造。
  対策: 完了報告前の`git diff --stat`実行と引用の義務化、受領側の実測検収
- 2026年7月: 完了報告の終了コード・バイト数等の定量値が実行結果に存在しない捏造値だった。
  直接原因: 報告内の定量値を再実行で裏付ける工程が無かった。
  対策: 定量値のメイン側再実行照合を義務化
- 2026年7月: 「約230kトークン消費」等の捏造した実測風数値を根拠に縮退を提案した（実消費は約10%）。
  直接原因: 実測値の取得手段が無いのに数値の併記を求める規範が捏造の抜け道を誘発した。
  対策: 実測値を装う数値の全称禁止と機械検出、当該規範の改訂
- 2026年6月〜8月: 待機表明のみの完了報告（「完了通知を待つ」等、英語形含む）が多数のセッションで再発し、
  都度メイン側の巻き取り・催促を要した。
  2026年8月には、前景起動から自動転換された背景ジョブの回収前に委譲先が終端報告を返し、最終検証とレビューを呼び出し元が巻き取る事象が再発した。
  自動転換を対象外とする条項が、待機表明だけの応答を完了と扱わない既存契約と局所的に矛盾していた。
  直接原因: providerごとに異なる完了通知の配送先を単一環境の実測で固定し、agent定義の許可と実行時のtool公開を混同した。
  さらに表示名又はagent種別を返信先へ変換し、送信側のqueued受理を受信処理の成立と扱ったため、直接の呼出元へ結果が届かない場合の終端が無かった。
  対策: 通信scope、能力公開、宛先の由来及び送信受理と受信処理を分離し、保持した機械可読IDと実行時の公開・呼び出し成功だけで中継を判定する。
  中継不能時は未反映を推定して再送せず、担当範囲と権限の内側だけを巻き取り、外側の工程を`needs_escalation`で返す
- 2026年9月3日: 3レーンの完了報告が実在しない完全OIDを`merged_head`へ記載し、1レーンがマージも採用も資源回収も実行しないまま`adopted`と`released`を列挙し、別の1レーンが未commitの修正5ファイルを残したまま`merge_request`を3回連続で返した。
  いずれもメインの照合で検出し、差し戻しの往復が計4回発生した。
  直接原因: 3行の値を生成する統合担当と完了値を返す実装担当のいずれにも自己検証の義務が無く、即時対応で追加した義務を当該主体が読まない文書へ置いた。
  対策: 各値の終了状態の観測と完了値の返却前のclean検査を、値を生成する実装担当のタスク文書へ置き、レーン運用文書は当該正本を参照する
- 2026年9月3日: 長時間のコマンドの実行を委譲した3回のうち2回で、委譲先が背景実行へ移行した旨だけを返して終端し、呼び出し元が完了確認を追送した。
  追送1回あたり10分以上の待ち時間が加わった。
  直接原因: シェル実行の委譲先へ渡すシステム指示が終端条件をコマンドの実行結果の報告とだけ定め、背景移行の通知が結果として報告される経路を残した。
  対策: 背景実行へ移行した場合は出力ファイルから終了状態を確定してから報告する条件をシステム指示へ加える
- 2026年9月4日: 委譲先の計画担当が、自身が起動した探索の結果を待つ旨だけを出力し、タスク文書が定める返却値を伴わずに終端した。
  直接原因: 待機表明による終端を正常な終端と定める条文が、完了通知による同じsessionの再開が成立しない実行経路を区別しなかった。
  同じ指示を3つの実行経路で実行し、`agents_server`のClaude backendだけが子の完了後の返却値を返し、Codex backendとClaude CodeのAgentツールは待機表明の行を最終の返却値として返すことを実測した。
  対策: 追加指示なしの回収を保証する経路と保証しない経路を分け、待機表明で終端してよい条件を起動時の指示という観測できる入力へ結び付ける
  再発防止: `待機中: <待機対象>`の1行だけを返す規定を委譲時の厳守事項へ置く

- 2026年9月7日: 委譲先の報告に基づいて投入したAWIが、ユーザーの疑義による再調査で前提とするフックの誤発動も反映先も実在しないと確定し、取り下げへ至った。
  直接原因: 委譲先の完了報告に含まれる実装上の事実を、成果物へ書く前に実装、実行結果又は公式一次資料で確認する規定が無かった。
  対策: 委譲元が当該事実を成果物へ書く前に確認し、確認に用いた手段と観測値を当該成果物へ残す
- 2026年9月8日: 保存rootへ移動済みの計画バンドルに対する`atk plans commit`が、保存へ成功した旨を出力して終了コード0で終わりながら、作業root直下に残る同じstemのレビュー指摘管理表を保存先へ反映せず、当該ファイルを作業root側にも残した。
  直接原因: 保存root相対の引数を受領した経路が、作業側バンドルの探索キーへ年月階層を含む相対パスを用い、かつメイン計画の実在を前提としたため、作業root直下の付属ファイルが探索の対象に入らなかった。
  対策: 作業root直下に同じstemの残存ファイルがある状態を非0の終了コードで報告し、成功の報告と保存状態が一致しない経路を撤去する

## 誤判定・検証不足

- 2026年9月12日: `agent-toolkit/agent_toolkit/_atk/serve/static/vendor/mermaid.min.js`を追跡した状態で
  `git grep 123 | wc --chars`を実行すると、標準出力が1,016,731文字になった。
  `CLAUDECODE=1 uvx pyfltr grep 123 | wc --chars`も32,937文字となり、既定の除外だけでは一般的な検索語の本文出力を十分に抑制できなかった。
  直接原因: minifiedされた巨大な単一行をリポジトリへ保持し、広域検索の最初の取得で一致本文を出力できる構造にしていた。
  対策: 不要なローカルbundleをCDNの常時最新版へ置き換える。広域検索では件数・ファイル・要約を先に取得してから本文を限定する。
  pyfltrには、エージェント環境で出力量に応じて自動要約する変更をAWIとして登録する

- 2026年9月6日: 条件不成立の上流要求を登録した事象
  条件付きの上流要求を5つの投入先へそのままAWI本文として登録し、いずれも対象の欠陥が存在しない不要な項目となった。
  直接原因: 上流投入担当が`upstream_request`の逐語転記を成果物として要求され、投入先ごとの条件判定と通常AWI本文の生成を担当せず、受領側の返却単位も元項目だけで投入先を識別できなかった。
  対策: 元項目と投入先の組ごとに現状を実測し、条件成立時だけ通常AWIの書式で自己完結した本文を投入する。返却と検収も同じ組を単位とし、条件不成立の組は根拠を返して投入しない

- 2026年8月: `agent-toolkit/rules/`配下へスキルの`references/`と同じ構成のサブディレクトリを作成し、
  当該ディレクトリのルールファイルは常時ロードされないと誤認した。実際には常時ロードの対象である。
  直接原因: rulesとスキルの構成を同一視し、配布一覧の生成条件を実測しなかった。
  `scripts/gen-install-files.py`はrules直下の`*.md`だけを列挙するため、サブディレクトリのファイルは配布先へ届かない。
  対策: `agent-toolkit/rules/`配下をフラット構造で維持する規定と、その理由をagent-toolkit-editスキルへ記す
- 2026年9月5日: 実在する`agent-toolkit/share/rules-main.codex.md`を、ユーザー向け発話で未定義の「Codex基礎契約」と呼んだ。
  直接原因: 会話圧縮後の内部要約にある一時的な対象名を、対象リポジトリの実在識別子へ再解決しなかった。
  対策: Codexでは会話圧縮後の一時的な対象名を判断前に再解決し、既存のユーザー向け発話ルールを適用する
- 2026年9月5日: `agent-toolkit:process-wi`の日次リリース判定で、開始時に固定した処理対象集合を再取得できていない状態を空集合と推定し、不要なrelease PRを作成した。
  直接原因: 会話圧縮後に再解決する対象をファイル・コマンド・識別子へ限定し、固定集合・保留・承認状態を内部要約の欠落から補った。
  対策: Codexでは固定集合・保留・承認状態も正本から再解決し、再解決できない状態を空集合・未実行・承認済みと推定しない
- 2026年8月29日: 複数の`planning`項目を1件の計画型AWIへ統合する手順について、既存の`convert-to-plan`が同じ状態遷移を実装済みであると判断し、文書同期だけの改善提案を作成した。
  実際の`convert_entries_to_plan`は`inbox`と`processing`だけを対象とし、`planning`の最古項目への統合、本文差替え、残項目除去と`inbox`移動を実装していなかった。
  対象WIが実装導入として示したcommitも文書だけの変更であった。
  直接的原因: 公開コマンド名と複数入力対応だけを照合し、状態別の入力解決、保存結果と失敗復旧を実装本体から復元しなかった。
  混入要因: CLIの変更履歴をファイル差分で確認せず、関連項目に記録されたcommitを実装導入の根拠として採用した。
  動機的要因: 既存CLIを利用する文書同期だけで変更を完了できるという前提を、状態遷移の実測より先に固定した。
