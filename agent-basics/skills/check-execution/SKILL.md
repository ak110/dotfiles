# 検証の実行と判定

変更を検証する者が、動かすチェックと試験、正規の検証コマンド、結果の判定、起動した検証の回収を決める手順である。
成功の主張を観測の範囲に限る点は原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）の適用である。
検証の深さと費用の比べ方は原則2（`agent-basics:writing-standards/references/quality-principles-qcd.md`）の適用である。
起動した検証の終了を回収する点は原則7（`agent-basics:writing-standards/references/quality-principles-ownership.md`）の適用である。
各ツールの受付形式と出力形式は、ツールのヘルプ、MCPツールのスキーマ、公式の文書で確かめる。
実行環境もチェック用のMCPツールも無い環境では、対象とコマンドの選定と、提示された保存結果の判定までを担い、未実行のチェックを示して返す。

## 実行条件と結果

1. 要求の結果を直接観測できる手段と環境を、`agent-basics:writing-standards/references/testing.md`「検証単位の選定」で選ぶ。
   着手の直前に基準版を記録する（`agent-basics:check-execution/references/diagnostics.md`「基準版と変更行への帰属」）。
2. 動かすチェックと試験を、実際の差分が変えた契約から`agent-basics:check-execution/references/verification-scope.md`で選ぶ。
   ローカルは直接の利用側までとし、リポジトリ全体の試験と静的検査はCIに委ねる。
3. 正規の検証コマンドを選ぶ。
   構築・起動・単発実行の下層のツールを呼ぶ前に、作業ディレクトリからリポジトリのルートまでのタスクランナーの定義と、README・プロジェクトの規範の案内を確かめる。
   定義の例は`Makefile`、`mise.toml`、`justfile`、`Taskfile.yml`、`package.json`の`scripts`、`pyproject.toml`のタスクで、ツール固有の設定ファイルが無くても起動の方法を持つことがある。
   対象の限定などで正規のコマンドをそのまま使えない時は、そのレシピの引数・環境変数・前処理を引き継ぐ。
   同じ比較を繰り返すときは再実行できるコマンドかスクリプトを残す。
4. 保存の前に、公開仕様から、試験の完全名と個別の結果を取れる出力の形式と対象範囲を選ぶ。
   画面への本文の表示と、構造化した診断の取得は用途を分ける。
5. 本書「長いコマンドの起動と回収」に従って実行し、終了状態と出力を回収する。
6. 結果を`agent-basics:check-execution/references/diagnostics.md`「読む出力」「合否の判定」で判定する。
7. 要求ごとに、成功、失敗、未実施、観測不能を分け、成功以外は理由、試した手段、残る限界を既存の検証記録へ残して返す。
   実行や結果の保存ができない環境では、対象と手順、未実行の範囲を整理して返す。
   記録を生成する前に実行基盤が失敗した時は、既存の実行ログを使い、検証手段の改善に要る情報を保つ。
8. 修正の後は、結果が変わりうる範囲だけを`agent-basics:check-execution/references/verification-scope.md`「実行条件と再実行」に従って再実行する。

返す報告に含める項目: 実行したコマンドと検証した版、要求ごとの状態、判定に使った出力の所在、再利用した成功と再実行の範囲、所要の比較の結果。

## 長いコマンドの起動と回収

時間のかかる検証やビルドは、ホストが公開する時間上限まで延ばした前景で実行し、収まらなければホスト標準の背景実行で起動する。
背景実行と、前景から自動で背景へ移された実行は、返された実行識別子と保存出力から本体の終了状態を回収する。
同じ対象への後続の検証は、先行する実行の終了状態と出力を回収してから起動し、実行中か待機中の同じ対象の検証を重ねて起動しない。
監視の期限到達、通知の未着、終了コードファイルの未生成だけでは、本体が終了したと判断しない。
