# 検証結果の診断と警告の判定

本書は、検証を担当したエージェントが、診断メッセージや警告の内容を基準バージョンとの差分に基づいて判定し、その結果や不足事項を依頼元へ報告するための判断基準を定める。
報告先は、検証を依頼した主体とする。

## 読む出力

速度や資源使用量の改善を主目的とする作業では、変更前後の数値、同じ負荷と比較可能な環境、挙動の維持、および速度と資源使用量などのトレードオフを確認する。条件の一致する既存の保存結果は再利用する。

プロセスの終了コードやサマリー行の表示のみで成否を判断せず、診断メッセージの本文、実行時の警告、ならびに処理が未到達・未適用・未完了であることを示す出力を精読する。
例えばpyfltrの`commands_summary.needs_action.warning`は、コマンド実行結果のステータスカウントであり、個々の診断警告の件数とは異なる。この値が0であっても、診断メッセージの本文を確認し、今回の変更行に対する指摘が含まれていないかを確かめる。
出力契約の確認記録については、`docs/development/audit-records.md`の「agent-basics/skills/check-execution/references/diagnostics.md：読む出力：2026年10月3日」を参照する。

テストや検証を実行した際は、成功・失敗を問わず、結果を判定するたびに各テストケースの所要時間および実行全体の経過時間を確認し、想定を超える遅延がないかを以下の基準に基づいて評価する。この評価は、メインエージェントと委譲先、ローカル環境での実行とCI環境での結果確認のいずれにおいても共通して実施する。

- 個別のテストの所要時間は、setup、テスト本体、後始末の契約を満たすために必要な実仕事量に対応付けて評価する。全体の所要時間は、事前準備、対象テスト群、並列実行数、終了処理を含めた経過時間（実時間）で比較する。並列実行されたテストケースの累積CPU時間は、壁時計の実経過時間と区別して扱う。
- 同一の実行環境、テスト対象群、依存ライブラリのバージョン、並列度、および準備状態で取得された過去の保存記録を第一の比較対象とする。実行条件に差異がある場合は、その条件差と必要な仕事量の違いから見込まれる所要時間を考慮し、比較可能な範囲と見込みの限界を明記する。
- 過去の保存記録が存在しない初回実行時は、必要な処理内容、データ規模、外部プロセスの起動回数、契約上不可欠な待機時間などから所要時間の見込み根拠を整理し、今回の観測値と比較する。必要な待機処理や実プロセス・実環境の担保に要する時間も比較基準に含める。
- pytestのduration表示やpyfltrの`slow_tests`といった既存の所要時間出力、保存された過去の実行記録、およびツールの経過時間情報を活用する。各区間の内訳を判別するための情報が不足している不審な処理に限り、追加で計測する。

仕事量や条件の差異では説明がつかない実行時間の増大や、不要なセットアップ・データ取得・プロセス起動・待機処理の反復を検知した場合は、`agent-basics:bugfix`を起動する。そして、`agent-basics:bugfix/references/root-cause-scenarios.md`の「所要の原因調査」に処理を引き渡す。単独で再実行して成功したという事実は、仕事量の妥当性を示す根拠にはならない。観測された個別および全体の所要時間、比較基準と実行条件、妥当性の評価結果、ならびに改善や追加調査に関する判断を、既存の検証結果記録に明記する。
設計段階における不要な仕事の排除やハング検出用のタイムアウト設定については、`agent-basics:writing-standards`の`references/testing.md`「速度」に従う。ハング検知のためのタイムアウトと処理所要時間の妥当性評価とは目的が異なるため、固定の許容秒数を設けて機械的にチェックしたり、専用の管理台帳や常時監視機構を追加したり、毎回全件を再計測したりするような過剰な仕組みは追加しない。

## 基準版と変更行への帰属

変更行への帰属関係を正しく判定するため、比較の基準となるバージョン（基準版）と今回の検証対象バージョンを、検証結果、進捗ログ、または引き継ぎ記録に明記する。
基準版には、通常の機能変更では実装着手直前のコミット、CI修正では修正前のコミット、ブランチ統合では統合前のコミットを採用する。比較の途中で基準版を変更せず、一連の変更全体に対して診断結果を正しく対応付ける。

各診断メッセージについて、対象ファイル、該当行範囲、指摘ルール（rule）をGit差分の追加行・変更行と突き合わせる。行番号の情報を持たない全般的な警告については、発生元のモジュール、警告種別、メッセージ内容、発動条件を分析して帰属を判定する。
変更行に対する指摘が検出された場合は、ツールの結果ステータスにかかわらず原因を解消するか、その指摘の意味、影響範囲、あえて残す理由を記録する。指摘の位置や帰属先が特定できない場合は判断を保留し、不足している判断材料を報告先へ伝える。

警告が既存のものか今回の変更で新たに発生したものかを切り分ける必要がある場合は、該当する検証項目のみを抽出し、対象範囲、実行オプション、依存ライブラリのバージョン、並列度、および実行環境をそろえた上で基準版に対して実行して比較する。同一バージョンかつ同一条件の保存記録がすでにあればそれを再利用する。比較は診断対象ファイル、該当行、ルール、およびメッセージ内容に基づいて行い、ファイル改名、行の移動、重複出力を正しく対応付ける。警告件数が同じであってもメッセージ内容が変化していれば差分として扱い、行番号の移動だけで内容が同一のものは既存の警告とみなす。プロセスID（PID）や絶対パスなど実行ごとに変化する固有値は比較対象から除外する。

## 合否の判定

- 処理の未到達、未適用、または未完了を示す出力は、既存か新規かを問わず検証を阻害する要因として扱う。基準版との比較ができない状態や、警告の意味・影響・帰属先が未確定である状態も同様に作業を続けられない原因とし、「残す理由」を形式的に記録するだけでは合格とせず、理由と不足している条件を報告先に返却する。
- 欠陥を示す診断が検出された場合は原因を是正する。権限不足や必要な入力情報の欠落により自力で是正できない場合は、報告先へ状況を伝える。警告メッセージの意味の判定は、`agent-basics:bugfix/references/root-cause-analysis.md`の「問題を見つけたときの対処」に従う。
- 処理が正常に完了し、欠陥を示しておらず、警告の意味、影響、帰属先、比較対象バージョン、および残す妥当な理由をすべて特定できた警告については、それらの情報と診断本文を検証結果および進捗ログ（または引き継ぎ記録）に記録した上で作業を続行する。
- 是正が必要な既存の不具合を発見した場合は、観測された出力、直接的な原因、ならびに修正対象と修正の方向性を依頼元へ報告し、作業の割り当てと認可に従って是正を進める。
- ブランチ統合の際は、実装段階で警告を残す根拠とした理由が、統合後の入力や実行条件においても依然として成立しているかを確認する。条件が成立しなくなった警告や、統合によって新たに生じた欠陥は、実装時と同様の厳格な基準で判定する。
- 警告の出力抑制や検証範囲を縮小する場合は、警告の意味を正しく把握した上で、その理由を検証記録に明記して選択する。警告の意味や由来を確認すること、あるいは本来行うべき是正作業を怠る目的で抑制や範囲縮小しない。
