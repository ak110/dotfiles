# 受入シナリオ検証の試行と資源の観測

受入シナリオ検証は、エンドユーザーが使う公開操作や入力から期待する結果までの流れを実行して、要求を満たすことを確かめる検証である。
合格の主張を再現できた条件の範囲に限る点は原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）の適用である。
共有資源へ作用する前に所有者と認可を確かめる点は原則4（`agent-basics:writing-standards/references/quality-principles-constraints.md`）の適用である。
この観測から、同じ操作を毎回実行する自動テストの新設は導かず、常設の要否は`agent-basics:writing-standards/references/testing.md`「試験を書く前の確認」で決める。
不具合修正の受入確認は`agent-basics:bugfix/SKILL.md`「5つの問い」の問い5に従う。
構築・起動・単発実行のコマンドは`agent-basics:check-execution/SKILL.md`「実行条件と結果」の手順3で選ぶ。

## エージェント向け文書の試行

事前に定めた固定の入力と対象文書の全体を使い、必要な参照資料を読み終えてから判定する。
文書の不足は、抜粋や未読の部分からは判定できず、全体を読んだ後に判定する。
文書を読むだけの試行と、実際にスキルを起動する検証を分け、起動する時は実行主体の制限と操作の認可を守る。
複数のターンにわたる対話も、同じ固定の課題で、対話の継続と成果物の達成を確かめる。
入力、対象の版、結果、期待との比較、合否を、レビュー担当が後から確かめられる記録として残す。

## 検証資源の分離

テストの操作、入力の注入、故障の注入、自動終了の失敗が影響する資源は、所有者と共有範囲を確かめてから実行先を選ぶ。
エンドユーザーや他のプロセスと共有する資源は、別のセッション、仮想環境、専用の端末環境などで分離する。
分離が難しい時は、既存の認可の範囲で使う時機を調整し、認可が足りなければユーザーに確認する。
作業者間の排他やテスト後の状態復元があっても、実行中のエンドユーザーへの影響を遮断できているかを個別に評価する。

共有範囲は資源の種類ごとに違い、資源ごとに分離を確かめる。
例えばWindowsで描画を非表示のデスクトップ（desktop）へ逃がしても、同じウィンドウステーション（window station）に属するクリップボードとキーボード・マウスの入力は共有されたままである。
故障の注入や自動終了の失敗を確かめる時は、対象のプロセスが止まらなかった場合もエンドユーザーの環境に害が及ばない範囲で実行する。

分離のために変える設定と、合否に影響する条件を分け、成否に関わる起動条件、入力、状態は本番と同等に保つ。
同一の条件を再現できない部分は、差と理由を記録し、合格の範囲を再現できた条件に限って報告する。

## 常駐サービスの公開前の観測

本番の起動単位（systemd unit、コンテナーの定義、タスクスケジューラの登録タスクなど）で起動するサービスを公開前に観測する時は、稼働中の実環境から分離して起動する。
変える設定は、競合を避けるために必要な値（待ち受けポート、状態の保存先、多重起動防止ロックなど）に限る。
成否を左右する起動条件は本番と同等に保つ。
これには起動単位の設定（停止シグナルの送り先のプロセスグループ、終了タイムアウト、環境変数、作業ディレクトリなど）、常駐する子プロセスの生成、外部サービスへの接続が含まれる。
例えばsystemd unitでは、本番と同じunitの設定を`systemd-run --user`の一時unitへ渡すと、起動単位の振る舞いを再現できる。
起動単位の外からコマンドを直接起動したり、設定ディレクトリ全体を差し替えたりすると本来の成否条件が失われるため、本番と同じ起動単位の仕組みで確かめる。
再現できない設定項目は、項目と理由を観測記録に書く。
