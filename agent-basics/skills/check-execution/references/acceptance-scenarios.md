# 受入シナリオ検証の試行と資源の観測

受入シナリオ検証とは、エンドユーザーが実際に使う公開操作や入力から期待される結果に至る一連の流れを実行し、要求が満たされていることを確認する検証である。文書の試行、検証資源の分離、および本番起動単位の同等再現について、以下の基準を適用する。

## エージェント向け文書の試行

事前に定めた固定の入力内容と対象文書の全体を用い、必要な参照資料を読み込んだ上で判定する。一部の抜粋のみに基づく判定や、未読部分がある状態で「文書が不足している」と結論付けることは避け、必要な読み込みを完了させてから判定する。文書の内容を読み込む試行と、実際にスキルを起動する処理とは区別し、実際に起動する場合は起動主体の制限や操作権限の認可を厳格に守る。入力内容、検証対象のバージョン、実行結果、期待される結果との比較、および合否判定を、レビュー担当者が後から確認できる記録として保存する。複数ターンにわたる対話を扱う場合も、同一の固定課題を用いて対話の継続性と成果物の達成度を確認する。

## 検証資源の分離

テスト時の操作、入力データの注入、故障注入、および自動終了処理の失敗によって影響を受ける資源については、所有者と共有範囲を確認した上で実行先を選択する。エンドユーザーや他のプロセスと共有している資源を扱う場合は、独立した別セッション、仮想環境、または専用の端末環境などを用いて影響を分離する。環境の分離が難しい場合は、付与されている既存の認可に基づいて利用タイミングを調整し、認可が不足する場合はユーザーへ確認する。作業者間の排他制御やテスト終了後の状態を復元する場合でも、テスト実行中のエンドユーザーへの影響を遮断できているかを個別に評価する。

資源の共有範囲は種類によって異なる。例えばWindows環境において画面描画を非表示のデスクトップ（desktop）に逃がした場合でも、同一のウィンドウステーション（window station）に属するクリップボードやキーボード・マウス入力は分離されないため、資源ごとに個別に分離状態を確認する。故障注入や自動終了の失敗を検証する際は、仮に対象プロセスが正常に停止しなかった場合でもエンドユーザー環境に悪影響を及ぼさない実行範囲を確保する。

環境分離のために加える設定変更と、検証結果の合否に影響を与える本質的な条件とを明確に区別し、成否に関わる起動条件、入力値、および状態は本番と同等に保つ。本番と同一の条件を再現できない部分がある場合は、条件の差異とその理由を記録に残し、テスト合格の有効範囲を再現できた条件の範囲内に限定して報告する。

## 常駐サービスの公開前の観測

本番の起動単位（systemd unit、コンテナー定義、タスクスケジューラの登録タスクなど）によって起動されるサービスを公開前に検証・観測する場合は、稼働中の実環境から分離した状態で起動する。その際、変更する設定値は競合を回避するために必要な値（リッスンポート、状態保存ディレクトリ、多重起動防止用のロック資源など）に限定する。
検証結果の成否を左右する起動条件は、本番環境と同一に保つ。これには、起動単位の設定（停止シグナルの送信先プロセスグループ、シャットダウンのタイムアウト時間、環境変数、カレント作業ディレクトリなど）や、常駐する子プロセスの生成設定、外部サービスへの接続設定などが含まれる。例えばsystemd unitであれば、本番と同じunit設定を`systemd-run --user`の一時unitに渡すことで、起動単位の振る舞いを正確に再現できる。
起動単位の外部から直接コマンドを叩いて起動したり、設定ディレクトリ全体を一括で差し替えたりすると、本来の成否条件が失われる原因となるため、本番と同じ起動単位の仕組みを利用して検証する。本番と同等の条件を再現できない設定項目が残る場合は、その項目と理由を観測記録に明記する。
