# 性能の測定

速度や資源使用量を測る時と、測った数値で採否を決める・報告する前に、上から実行する手順書である。
数値の主張を観測の範囲に限る点は原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）の適用である。
測るかどうかと回数を判断の必要で決める点は原則2（`agent-basics:writing-standards/references/quality-principles-qcd.md`）の適用である。

## LLMを含む作業の仕事量

規範・手順・hookの変更で仕組み上減る仕事を特定できる場合は、同じ入力で読み取りファイル数・バイト数、入力トークン数、ツール呼び出し回数、子プロセス数など、変更が直接減らす仕事量を比べる。
同じ入力から仕事量が一意に決まる比較は1回で判定する。
hookのCPU時間などを使う場合は、会話全体ではなく変更した処理を切り出して測る。
必要な判断・処理・保護が維持されることを確認し、仕事量と品質で採否を決める。
LLMの会話全体の実経過時間は補助記録にとどめ、その反復や時間差だけによる不採用・撤回を求めない。
LLMを含まない処理の性能は以下の手順で測り、明示された全体所要時間の目標は変更の採否と分けて直接検収する。

## 測定の手順

1. 測る前に、その数値で決めることと、判断を変える結果を書く。
   結果で採否や方式が変わるか、目的とする利用の結果（公開操作の往復の成否など）を測れる手段か、のいずれかに当たる測定だけを行う。
2. 挙動の維持を先に確かめる。
   性能を変える変更は`agent-basics:writing-standards/references/testing-design.md`「検証単位の選定」の差分検証で基準版と比べ、コストの高い性能測定より先に、低コストに正確性を確認する。
3. 比較の条件を`agent-basics:writing-standards/references/investigation.md`「性能と負荷の測定」に従ってそろえ、条件が一致する保存済みの結果は再利用する。
4. 比較対象も本番と同じ構成（リリースビルド、本番の設定と環境変数、バッチやトランザクションの設定、キャッシュの状態など）で動かす。
   一方だけが未調整の設定（デバッグビルド、1行ごとのcommit、索引の欠落など）で動くと、実装でなく設定を比べたことになる。
   調整できない側が残る時は、その実行から優劣を決めない。
5. 試行ごとの変動の幅（ノイズの下限）を求める。
   変えていない側を同じ条件で繰り返し測り、試行ごとの幅を取る。
   差がこの幅より小さければ、測れる差は無いと判定する。
6. 測定回数は採否の判断に必要な最小限にする。
   差が幅より十分に大きければ少ない回数で足り、差が近い時は両側を交互に測って回数を増やし、代表値と分布（中央値と範囲など）で示す。
7. ボトルネック（律速要因）を特定する（なぜ2倍速くならないのか）。
   数値を2倍にできない理由になる資源かコードの経路を、報告に使わない別の実行で取ったプロファイルかシステムのメトリクスから挙げ、コードの箇所へ対応付ける。
   手掛かりはCPUのuserとsystem、I/O待ち、ディスクの待ちと書き込み量、通信、メモリーとGC、ロックや接続プールの待ちで、必要な指標だけをプロセス別・時系列に取る。
   レイテンシーが集中する値と設定値（タイムアウトなど）、受信量と一時書き込み量も比べ、負荷を生成する側が先に飽和していないかを見る。
   コードを読んだ推測はボトルネックの根拠にせず、ボトルネックを挙げられない数値は、何を測ったかが分かっていないものとして扱う。
8. 結果が上限の計算と合うかを確かめる。
   毎秒のバイト数をディスクと通信の帯域と、毎秒の操作数と1回あたりのCPU時間との積をCPUコア数と、短縮した時間を変更箇所の元の所要時間と比べる。
   上限を超える結果は、キャッシュ、空の処理、不具合など、対象の仕事以外を測っている。
9. 利用の結果は直接観測した値で判定し、内部の部分計測値は補助の手掛かりとして扱う。
10. 改善後は、ボトルネックが別の箇所へ移ったかを確かめる。

返す報告に含める項目: 単位付きの変更前後の数値、回数と範囲、ボトルネック、比較の条件、挙動の維持、速度と資源使用量の得失。
