# 変更範囲の検証の対象選定

変更を検証する担当が影響範囲に応じてローカルとCIの検証を分け、ユーザーが必要な範囲の合否を適切な時間で得られるようにする。
変更範囲の検証で実行するチェックとテストを選び、保存済みの成功を再利用するか再実行するかを決める基準である。
計画担当、実装担当、実行レビュー担当と、計画を作らずに直接変更する担当者が使う。
未観測を成功に数えない点は原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）の適用である。
ローカルとCIの分担と再実行のコストは原則2（`agent-basics:writing-standards/references/quality-principles-qcd.md`）の適用である。
直接影響範囲の定義は`agent-basics:writing-standards/references/design-heuristics.md`「変更と検証の範囲」にある。

## ローカルとCIの分担

CI・公開手順そのものを変更する時は、`agent-basics:writing-standards/references/github-actions.md`「CIと公開の設計」で、検証の並べ方と既存結果の再利用を比較する。

公開先のCIが全体のテストと静的検査を実行する場合、ローカルの検証は、変更したファイルと、参照をたどって特定した利用側のテスト・lintに限る。
ファイル単位で選びにくい時も、ローカルは関連する機能のモジュールまでを上限とし、列挙しきれなかった利用側を検証記録へ残す。
CIが無いか公開先でCIが動かない場合は、プロジェクトの開発・公開手順に従い、列挙しきれない利用側を含む検証単位の全体を実行する。
CIが実行しないチェックと、変更したファイルを対象にするcommitフック・横断テストは、プロジェクトの手順で選ぶ。
個別の類型とプロジェクトの手順も、この上限の内側で対象を選ぶ。

## 直接影響範囲の類型

変えた契約を読む・呼ぶコードと、その契約を期待値として確かめるテストを、リポジトリ全体から探す。
シンボル名の参照に加え、共通の入出力や起動インターフェースの関係からも依存をたどり、固定文字列の検索を補助に使う。
見落としやすい対象の手掛かりは次のとおりである。

- 横断の結合テスト、文字コード、コマンドやフック、通知・標準エラー・終了処理、生成物やスナップショット
- 設定のパーサーや別の構文で定義を読むテスト、共有fixtureとテストヘルパーの利用側、実行時の再読込、親子プロセスが共有するタイムアウトの上限
- 出力（APIの辞書、JSON、CLIの出力など）の項目を足す・変える変更では、同じ出力の既存の項目名を固定文字列で探し、出力全体を完全一致で比べるテストまでたどる
- 設定や登録のファイルを新たに読む処理を加える変更では、その処理を実行する既存のテストヘルパーとfixture
- 古い文言・古い集合・削除した参照で探して見つかる、新しい識別子を含まない完全一致の期待値、履歴の索引、別の実行層

次の対象を変えた場合は、それを読む全てのチェックとテストを直接影響範囲に含める。
参照先の増減が無い内部の変更でも同様に扱う。

- 共通の設定ファイル、`conftest.py`のヘルパーとfixture、pytestのプラグインなど全テストの読込時に読むモジュール
- テストランナー・linter・型検査の設定と、チェックやテストを実行するインタープリターのバージョン指定（`.python-version`、CIマトリクスのバージョンなど）
- 依存バージョン指定とlockファイル（`pyproject.toml`や`package.json`の依存、`uv.lock`、`pnpm-lock.yaml`など）

これらに共通するのは、実行時に読む外部ライブラリや実行環境のバージョンが変わり、それを使う全ての処理の結果が変わりうる点である。
新しい類型もこの観点で判定し、変更したパスから利用側を列挙できることを範囲を狭める根拠にしない。

## 範囲の決め方

要求の入力、操作、期待結果を自分で直接観測できる手段を選び、未確認の範囲と、追加の観測に要る前提を示す。
危険になりうる箇所の一覧を広げる前に、変更が安全である根拠になる1〜2個の事実（例: 消す値はもう使われていない）を見つけ、実物を動かして確かめる。
その事実が成り立てば、それに依存する懸念をまとめて外せ、成り立たなければ、その事実に依存する利用側を範囲へ加える。

- 最初の検証には、同じ変更に対してcommitフックと統合検証が実行する検査（リポジトリ横断の不変条件の検査など）を含める。
  手で選んだ一覧や近くの対象だけで組むと、漏れた検査がcommitや統合で初めて失敗し、検証とcommitを往復するためである。
  横断テストは、プロジェクトの規範が定める識別方法と実行形式で選ぶ。
- 最終検証を組む前に、成功した実行を受理する後段の検査の公開契約を確かめ、予定の引数・対象・実行条件と比べる。
  プロジェクトが事前の確認を公開していればそれを使い、事前の適合と、実行後の成功・内容の一致を別に確かめる。
- 共有の処理、共通のインターフェース、公開入力、環境変数を変えた時は、既存の要素、入力の未設定、実行環境の隔離の各条件から関連するテストを選び、列挙の限界を記録する。
- 差分から対象を絞る（`git diff --name-only`など）時は、変更したファイルを参照する側のテストを別の引数で明示して加える。
- 対象は、計画や再利用する検証コマンド（計画の検証行、前回のコマンド、CIのログなど）でなく実際のGitの差分から確定し、足りない利用側を加え、意図して外した項目は理由を検証記録へ残す。
  取得済みの対象一覧は、修正、統合、再開で変わった差分に合わせて更新する。
- パスの差分からテストを選ぶツールの成功とテストの総数は網羅性の根拠にならず、特定した利用側のテストごとに保存結果の合否を突き合わせ、結果に無いテストは追加で実行する。
  1件ずつの突き合わせが難しい時は、本書「ローカルとCIの分担」に従い、関連モジュールまでの実行と未確認の範囲の記録か、検証単位の全体の実行を選ぶ。
- 起動の手段を替える時（一括実行のツールを個別のツールの直接起動へ替えるなど）は、元の手段が実行する検査の種類を挙げ、替えた後も同じ種類を満たすことを確かめてから採る。
  起動の回数だけを比べて検査の種類が減ると、外した検査の指摘が後の一括実行で大量に出て所要時間がかえって延びる。

## 実行条件と再実行

実行の形は`agent-basics:check-execution/SKILL.md`「実行条件と結果」に従う。
渡した対象と実際に実行される対象集合は違いうる（子プロジェクトへの展開、常に加わる対象など）。
起動の前に実効設定から実行対象を見積もり、実行の後は保存した結果で、対象ごとの件数と、変更したファイルと直接の利用側へ到達したことを確かめる。

- 共有の契約・fixture・生成ファイル・共通の設定を変える作業では、直接の利用側のコードとテストの期待値の修正を先にそろえ、同じ本文と依存環境でまとめて1回検証する。
- 実行中は、結果に影響する対象と直接の利用側の編集を止める。
  未commitの変更を検証する時は、実行の前に対象の本文を復元できる形で残し、実行の後に本文が変わっていないことを確かめる。
- lockファイルやインタープリターのバージョン指定を変えた直後は、プロジェクトの手順で環境を同期してから検証する（同期前の古い仮想環境はCIと違う結果を出す）。
  同じ仮想環境を作り直しうる処理どうしは、直列に実行するか環境を分ける。
- 初回は、変更したファイルと直接影響範囲に当てはまる全てのチェックを実行する。
  その後は、結果に影響する新しい差分か未確認の範囲が出た時に、結果が変わりうる対象だけを再実行する。
- 同じ変更の集合への成功は、担当の検証、commitフック、最終検証、統合検証の間で、対象と、結果に影響する本文・依存・実行条件が一致する範囲で再利用し、同じ対象の実行を1回に保つ。
  先行の実行に無かったチェックと条件は追加で実行し、複数の検査をまとめたフックの成功表示は個別のツールと対象すべてを実行した証拠にせず、個別の結果で確かめる。
  先の成功と、失敗の後に限定して再実行した成功は、テストごとの合否で合わせて網羅を確かめてよい。
  先の成功に影響する差分が生じた範囲、中断で未実行のテスト、記録の無いテストは追加検証へ戻し、実行件数の合計だけで完了と判定しない。
- 通常の変更範囲の検証と受入確認が同じ変更を対象にする時は、初回の前に、対象、入力・環境の条件、期待結果、後続のレビューに必要な出力を比べる。
  両方を観測できる条件は1回の実行にまとめて版・環境・入力の条件・個別のテスト名と結果を保存し、条件が両立しない時や先の結果を失効させる差分がある時は理由を記録して別に実行する。
- 並行する別の作業が新しい呼び出し元を加えると結果が変わりうる検証（共有の契約やパッケージ外の呼び出し元の変更、全体を走査するチェックなど）は、プロジェクトの規範が統合後の検証として定めていれば、統合の完了時にも実行する。
