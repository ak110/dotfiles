# 変更範囲の検証の対象選定

本書は変更範囲の検証で動かすチェックとテストを選ぶエージェント（計画担当、実装担当、実行レビュー担当、計画なしで変更するエージェント）へ、対象を選ぶ判断基準を与える。
変更範囲の検証は変更ファイルとその直接影響範囲を対象にし、リポジトリ全体の検証はCIへ委ねる。公開前の全体検証は対象プロジェクトの開発・公開手順へ接続する。
直接影響範囲を外すと、そのテストの失敗はpush後のCIで初めて見つかり、修正と再実行の往復が増える。

## 直接影響範囲の類型

変更された契約を読む・呼び出す主体と、その契約を期待値に持つテストをリポジトリ全体から集める。参照名に加えて共通の入力・出力・起動手段からも関係をたどり、固定文字列検索は所在の補助とする。
想起の手掛かり: import・継承・共有関数、横断テスト、文字コード、コマンド・hook、通知・標準エラー・終了後処理、生成物・スナップショット、設定パーサーと設定・定義を別の文法で読む試験、共有fixtureと試験補助の消費側、実行中の再読込、親子で共有する時間上限。

次の対象を変更した場合は、それを読むチェックとテスト全体が直接影響範囲になる。対象は共有設定、pytestの`conftest.py`の補助やfixture、テストツール・lint・型チェックの設定、チェックとテストを動かすインタープリターの版指定（`.python-version`、CIのmatrixのPython版など）である。読込先が増減しない実装変更も同じ扱いとする。読込範囲が全テストに一致する場合も、CIに加えてローカルで実行する。

## 範囲の決め方

検証手段は要求が名指しする入力・操作・期待結果を自ら観測できるものを選び、未確認範囲と追加観測に要る条件を明示する。

- 横断テストはプロジェクト規範の識別手段と実行形で選ぶ。後続hookの対象と自動実行のない対象も含め、先行結果の再利用は後掲「実行条件と再実行」で判定する
- 複数の呼び出し手段が共有する処理や契約を変え、読む側を列挙しきれない場合は、検証単位全体（パッケージ全体のテストなど）を実行する
- 名前を削除または改名する変更では、変更ファイルの外に残る参照を検出する静的解析（型チェックなど）をリポジトリ全体へ実行する
- 差分指定（差分オプション、`git diff --name-only`など）を使う場合は、読む側のテストを別の引数で加える
- 対象は実差分で確定し、計画の列挙との差を読む側まで補う。除外理由は検証記録へ残す
- 既存の検証コマンド（計画の検証行、前回の実行、CI記録の再実行など）も、実差分から求めた直接消費側を全て対象に含むか確かめ、不足を加える。取得済みの対象集合は、修正・統合・再開で変わった範囲を補って使う
- 入力パスから試験を選ぶツールの成功とテスト総数は、直接消費側を被覆した根拠にならない。契約から求めた消費側の試験ごとに保存済みの実行結果の合否を対応付け、結果に無い試験は加えて再実行する。対応付けを列挙しきれない共有契約は、前掲の検証単位全体の実行へ切り替える

## 実行条件と再実行

- 共有契約を変える一連の編集は、直接消費側とテストの期待値を先にそろえ、同じ内容・依存条件を検証する単位にまとめて実行する。共有fixture、生成物、共通設定の変更も同じ判断を使う。実行中は結果へ作用する対象と直接消費側への書込を止める
- ロックファイルかインタープリターの版指定を変えた後は、対象リポジトリの開発手順が定める環境同期を実行してから検証する（同期前の仮想環境はCIと異なる結果を返す）
- 初回は変更ファイルと直接影響範囲へ適用できるチェックを全て動かす。その後は実差分と直前結果から再実行範囲を選び、失敗対象だけを修正した場合はその対象へ限定してよい。再実行の契機は、結果へ作用する差分か未確認範囲の発見に置く
- 保存結果の取得版・内容・依存条件を現行対象へ対応付け、必要な試験ごとに合否を判定する。全収集済み結果の成功集合と、失敗対象の修正後の限定実行の成功集合を合わせて被覆を確かめてよい。先行成功へ作用する差分があればその範囲を再検証し、途中終了で未実行の試験、未収集・記録のない試験は追加検証へ戻す。再利用できる成功結果と未確認集合を分け、総数だけで完了と判定しない
- 並行する別の書込主体が新しい呼び出し元を加えると結果が変わる検証（共有契約やパッケージ外の呼び出し元を変えた変更の検証、全体を走査するチェック）は、プロジェクト規範が統合後の検証として定める場合に統合時にも実行する
