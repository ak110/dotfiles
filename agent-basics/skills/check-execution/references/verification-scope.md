# 変更範囲の検証の対象選定

本書は、変更範囲の検証で実行するチェックやテストを選択するエージェント（計画担当、実装担当、実行レビュー担当、計画を立てずに直接変更するエージェント）に向けて、対象を適切に選定するための判断基準を提供する。
変更範囲の検証では、変更を加えたファイルおよびその直接影響範囲を対象とし、リポジトリ全体の網羅的な検証はCIパイプラインに委ねる。公開前に行う全体検証については、対象プロジェクトの開発・公開手順と連携して実施する。
直接影響範囲を検証対象から外してしまうと、テストの失敗がpush後のCIで初めて発覚し、修正と再実行の往復作業が増える原因となる。

## 直接影響範囲の類型

変更された契約（インターフェースや仕様）を読み込んだり呼び出したりしているコードと、その契約を期待値として検証しているテストケースをリポジトリ全体から抽出する。シンボル名による参照だけでなく、共通の入力・出力や起動インターフェースといった関係性からも依存をたどり、固定文字列による検索は対象特定の補助として活用する。
想起の手掛かりとなる要素には、import文、クラス継承、共有関数、横断的なインテグレーションテスト、文字コード、コマンドやフックがある。また通知・標準エラー出力・終了処理、生成物やスナップショット、設定パーサーや別構文で定義を読むテスト、共有fixtureやテストヘルパーの利用側、実行時の動的再読み込み、親子プロセス間で共有されるタイムアウト上限も含まれる。

以下の対象を変更した場合は、それらを参照するすべてのチェックおよびテストが直接影響範囲に含まれる。具体的には、共通設定ファイル、pytestの`conftest.py`内のヘルパーやfixture、テストランナー・linter・型チェッカーの設定、チェックやテストを実行するインタープリターのバージョン指定（`.python-version`やCIマトリクスのPythonバージョン定義など）である。内部実装の変更のみで参照先の増減がない場合も同様に扱う。参照範囲がすべてのテストに該当する場合であっても、CIでの実行を待つだけでなくローカル環境でも検証を実行する。

## 範囲の決め方

検証手段は、要求事項が指定する入力値、操作手順、および期待結果を自分自身で直接観測できるものを選択し、未確認の範囲や追加観測に必要な前提条件を明確にする。

- 横断テストは、プロジェクト規範が定める識別方法および実行形式に基づいて選択する。後続フックの対象や自動実行されないテストも含め、過去の実行結果を再利用できるかどうかは後述の「実行条件と再実行」に従って判定する。
- 複数の呼び出し元で共有されている処理や共通インターフェースを変更し、影響を受ける参照側をすべて列挙しきれない場合は、パッケージ全体のテストなど検証単位全体を一括して実行する。
- シンボル名を削除または変更する場合は、変更したファイルの外側に古い参照が残っていないかを検知するため、リポジトリ全体を対象とした静的解析（型チェックなど）を実行する。
- 差分指定オプション（`git diff --name-only`など）を用いて対象を絞り込む場合は、変更ファイルを参照する側のテストを別の引数として明示的に追加する。
- 検証対象は実際のGit差分に基づいて確定し、計画ファイルに列挙されていた対象との差異がある場合は、参照側も含めて不足分を補う。意図的に検証対象から除外した項目がある場合は、その理由を検証記録に残す。
- 既存の検証コマンド（計画ファイルの検証行、前回の実行コマンド、CIログに記録されたコマンドなど）を再利用する場合も、実際の差分から特定した直接的な利用側がすべて網羅されているかを確認し、不足があればコマンドに対象を追加する。すでに取得した対象一覧は、修正作業、ブランチ統合、または作業再開に伴って変化した差分範囲を反映させて更新する。
- ファイルパスの差分から自動でテストを絞り込むツールの成功結果やテスト件数の総数だけでは、直接的な利用側を網羅した根拠にはならない。変更された契約に基づいて特定した利用側のテストごとに、保存された実行結果の合否を1件ずつ突き合わせ、結果に含まれていないテストは追加で実行する。共有契約の変更などで個別の突き合わせが困難な場合は、前述のとおり検証単位全体を実行する方式へ切り替える。

## 実行条件と再実行

必要なテストが収集され実行されたかを個別の結果から確認するときは、`diagnostics.md`「読む出力」「合否の判定」に従う。
スキップや未収集も含めて未実行の範囲を特定し、追加検証または未実施の報告へ反映する。

通常の変更範囲検証と受入確認が同じ変更を対象とする場合は、初回実行の前に対象、入力・環境条件、期待結果および後続のレビューで必要な出力を比較する。両方の期待結果を観測できる条件は1つの実行単位にまとめ、取得版、実行環境、入力条件、個別の試験名と結果を保存する。条件が両立しない場合、別の結果そのものが要求される場合、または先行結果を失効させる差分がある場合は、理由を記録して別実行にする。

実行形は一般例や別プロジェクトの引数で固定せず、対象プロジェクトのタスクランナー定義、公開ヘルプ、実効設定から選ぶ。選んだ形で変更ファイルと直接消費側へ到達し、必要なチェックの完了、終了状態および診断を判定できることを検証記録で確かめる。

- 共有契約を変更する一連の作業では、直接の利用側コードとテスト側の期待値の修正を先にそろえた上で、同一のコード内容および依存環境のもとでまとめて一度に検証する。共有fixture、生成ファイル、共通設定の変更時も同様の判断を適用する。検証を実行している間は、結果に影響を与える対象ファイルや直接の利用側に対する編集を一時停止する。
- ロックファイルやインタープリターのバージョン指定を変更した直後は、対象プロジェクトの開発手順に従って環境の同期処理を実行した上で検証する（同期前の古い仮想環境では、CI環境と異なる結果が出力されるためである）。
- 初回の検証では、変更ファイルおよびその直接影響範囲に適用可能なすべてのチェックツールを実行する。2回目以降は、実際の差分と直前の検証結果を踏まえて再実行の対象を絞り込んでよく、失敗した対象のみを修正した場合はその対象に限定して再実行してよい。再実行のトリガーは、検証結果に影響を及ぼす新たな差分の発生、または未確認範囲の発見とする。
- 過去に保存した結果について、取得時のバージョン、コード内容、および依存条件が現行の検証対象と一致しているかを確認し、必要なテストごとに個別に合否を判定する。過去に収集したテスト結果のうち成功したものと、失敗後に修正して限定実行した結果の成功分とを合算して全体の網羅性を確認してよい。先行して成功していたテストに影響を与える新たな差分が生じた場合はその範囲を再検証し、途中で中断して未実行となったテストや記録が存在しないテストは追加検証の対象に戻す。再利用可能な成功結果と未確認のテスト群を明確に区別し、単なる実行件数の合計だけで完了と判定しない。
- 並行して作業している別のエージェントやユーザーが新たな呼び出し元を追加したことによって結果が変わり得る検証（共有契約やパッケージ外の呼び出し元を変更した場合の検証、全体を走査するチェックなど）は、プロジェクト規範が統合後の検証項目として定めている場合、ブランチ統合の完了時にも改めて実行する。
