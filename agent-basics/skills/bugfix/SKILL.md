# バグ対応

期待からの逸脱（エラー、失敗、指摘、自分のミス、未対応、デグレード）とその疑いに気付いたら、直す前にこの手順を使う。
逸脱は直す対象である前に情報である。
目的は、目先の失敗を消すことではなく、期待した結果を最も少ない仕組みで取り戻すことである。
同じ作業中に別の逸脱が見つかった場合も、事象ごとに7つの問いを適用する。
lint・textlint・型検査・テスト・CIの診断は、原因が明らかで本書「書き出す場面」に当たらない時は、起動せずそのまま直す。
原因を説明できない時、期待の側を変える時、同じ診断が2回目の時は起動する。
同じセッションで起動済みなら、取得済みの同じ版の本文を再利用する。

## バグの類型

1件につき、結果と原因の各軸から当てはまる語を1つ以上選ぶ。

### 結果

- 未対応: 要求に全く対応していない。
- 対応不十分: 完了とした対応が、要求の対象の一部にしか及んでいない。
  問い2で元の要求の逐語と対象を限った根拠を比べ、問い5で元の要求が対象とした全体から残りを探す。
- 実装漏れ: 決めた設計・計画・完成条件の一部を実装していない。
- 実装誤り: 実装したが、決めた動作と違う。
- 過剰対応: 求めていない範囲や結果まで変えた。
- 整合性不備: 関係する箇所どうしが食い違う。
- デグレード: 一度満たした動作が、後の変更で再び失敗する。

### 原因

- 取り違え: 要求・入力・対象を別の意味に読んだ。
- 考慮漏れ: 原文・現物・規範から導けたのに反映しなかった。
- 前提の誤り: 観測と合わない前提に基づいた。
- 未適用: 規範・手順が届いていたのに使わなかった。
- 実行ミス: 判断は正しく、操作を誤った。
- 外部要因: 依存先・環境の変化によって起きた。

前回の対策が防げなかった理由は別の軸であり、[再発時の区分](references/recurrence.md)で判定する。

## 7つの問い

1. 期待: 何が起きるはずだったか。
   その期待（要件、検査、テスト、仕組み、規範、自分で追加した目標）は、誰が何のために求めたもので、今も妥当で必要か。
   画面・通知・ファイルなど、人に届く結果の不具合では、`agent-basics:writing-standards/references/design-heuristics.md`「設計の判定順」に従い、受け取った人が次に判断・操作できるかまで確かめる。
   画面は既存の`agent-basics:writing-standards/references/ui-ux.md`に従う。
   この確認は要求を変更したり別の機能を改修したりする根拠にしない。
   テストや検査の失敗なら、実装コードより先に観測方法、期待値、実行環境、検証スクリプトを確かめる。
   正常な動作、正常な回復、仕様やテストで意図した失敗だと分かったら、その根拠を報告か作業記録へ1行残してここで終える。
2. 原因: 何がそれを起こしたか。
   観測（診断の全文、差分、再現、正常な例との比較）で確かめる。
   確かめていない部分は推測として扱う。
   同じ誤りが2回目なら、その誤りを招いた入力（手順の例、直前の出力、暗黙の前提）を探す。
3. 対策: 無くす・単純にする・直す・足す案を、原因を取り除く見込み、弊害、費用で比べる。
   再発防止の比較は`references/prevention.md`「案を比べる」に従う。
   修正は通常の変更である。
   その成果物の品質基準（`agent-basics:writing-standards`、`agent-basics:review-standards`など）を、新規の変更と同様に適用する。
   提案の時機と決定者は `agent-basics:writing-standards/references/quality-principles-roles.md`「役割分担」に従う。
   原因を取り除き、期待した結果を保てるかを確かめ、認可の要る操作は先に合意を得る。
   認可、安全性、データの完全性、公開契約を弱める案は除外する。
4. 回帰防止: 今回の事象を修正前の版で検出し、修正後に通る試験や検査を置くか。
   回帰テストの定義は`references/prevention.md`「言葉の区別」に従う。
   置かない場合は、既存の検査が同じ条件を覆う、検査可能な動作を変えない文書修正である、などの理由を書く。
5. 類似見直し: 同じ誤りを既に作り込んだ他の箇所はどこか。
   現存するファイルと直近の履歴の成果物を探し、見つけた同じ誤りを直す。
6. 再発防止: 同じ害を防ぐ対策（規範、検査、テスト）は既にあったか。
   原因が違っても同じ害を今後起こさないために何を変えるかを決める（`references/prevention.md`）。
7. 確認: 元の失敗を観測した方法で、直ったことと、周りの正常な動作が保たれたことを確かめる。

読み取り専用の環境では、確かめた原因と推測を分け、追加で調べる条件と修正案を返す。

## 書き出す場面

次のいずれかに当たる時は、処置を適用する前に、本書「記録」の各行を作業記録へ書き出す。
対策・回帰防止・類似見直し・再発防止はそれぞれ実施結果か行わない理由を書く。
対策の前に結果が出ていない行には予定を書けるが、完了を報告する前に結果か行わない理由へ書き換える。
いずれにも当たらない時（既存の検査が初めて見つけた単純な誤りなど）は、7つの問いを検討したうえで直せばよい。

- ユーザーに指摘された。
- 同じ症状への2回目の修正である（同じ誤りを別の対象で繰り返した場合を含む）。
- 処置として何かを追加する（回避処理、分岐、再試行、待機、例外処理、検査、規範の文章）。
- 処置として期待の側を変える（テスト・検査・設定を緩める、要件を読み替える、対象から外す）。
- 完了を報告した後か、公開した後に見つかった。
- 影響が大きい（データの破損、安全性、認可、公開契約、依頼の未達）。

## 確認観点

次の条件が成立した時だけ、その資料を全文読む。
読み方は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 問い1で期待の出所や必要性が分からない。問い3で足す案か期待を緩める案しか出ない | `references/premises.md` |
| 問い2で原因を説明できない。外部の挙動、並行処理、テストの作り、所要時間の増大、他者からの報告が関わる | `references/causes.md` |
| 問い5の探し方を決める。影響が大きく、探す範囲を広げる | `references/similar-review.md` |
| 問い6で対策が既にあった。同じ誤りを繰り返した。2回目の修正でも直らない。直したら別の症状が出た | `references/recurrence.md` |
| 再発防止を検討する（問い6。書き出す場面では毎回）。コスト・所要時間だけの改善機会の採否を決める | `references/prevention.md` |
| CIの失敗を扱う | `references/ci-failures.md` |
| 記録や報告を、作業項目など後に残る文書へ書く | `references/quality-standards.md` |

## 記録

書き出す場面では、次の形式で残す。
必要な記録は、作業記録や作業項目など、その工程の既存の記録先へ1回残す。
本人への報告は原因・処置・結果に要約し、同じ記録の再掲を求めない。
類似見直しは予定や未確認だけのままで完了を報告しない。

- 期待: <起きるはずだったことと、その期待が正しく必要である根拠。見直した場合はその結果>
- 原因: <`<結果の語>・<原因の語>。`で始め、起こしたものと観測の所在を書く。推測は推測と書く>

  ```text
  原因: 対応不十分・考慮漏れ。要求の対象を差分と比べると、1件が変更されていなかった。
  ```

- 対策: <無くす・単純にする・直す・足すのどれかとその結果。比較して採った理由。または行わない理由>
- 回帰防止: <用いた試験・検査と修正前後の結果。または行わない理由>
- 類似見直し: <検索の式と件数、該当箇所ごとの処置結果。または行わない理由>
- 再発防止: <対策の種類の語で始め、採用する策と変える成果物、同じ害への既存の対策を探した検索の結果。採らない場合は区分名と理由、未解決で調査へ引き継ぐ場合は`引き継ぎ`と観測した事象・次に確かめる問い・引継先（`references/prevention.md`「`再発防止:`の行」）>
- 確認: <直ったことを確かめた方法と結果>

問い6で対策が既にあった場合は`再発:`の行を加える。
書く内容は各資料が定める。
