## 原因分析の品質確認

原因分析の誤りを修正する際は、誤った結論、根拠とした観測事実、反証や代替案、適用されていなかった既存の判断基準をそれぞれ対応付け、実際に事象を引き起こした仕組みと、誤った結論を導いた判断基準を明確に区別する。処理量やリソース消費の妥当性は、処理が正常終了したかやエラーから復旧できたかとは別に検証する。

規範、仕様書、設計文書、自動チェック、テストが存在しなかったことを原因（拡張原因分析のL3やL4を含む）として挙げる前に、その事項が問題発生時に存在していた上位の規範から導き出せるものではなかったかを確認する。上位の規範には、`agent-basics:writing-standards`の`references/quality-principles.md`に定められた、利用主体や利用シナリオに基づく十分性の判定が含まれる。また、個別の規定や作業の目的（指示や計画書に示された目的を含む）、読み手が持つべき常識も導出元に含める。当時の規範が存在したかの時点確認は`root-cause-analysis.md`「直接的原因と事象時点の確定」に従う。上位規範から導き出せる内容であった場合は、その判断を適用しなかったこと自体を原因とし、安易に新しい条文を追加しない。目的が十分に読まれていなかったことや、細かな記述にとらわれて判断が硬直化したことなど、規範の適用を妨げた要因に働きかける処置を選択する。

検出の仕組みがなかったことを見逃し要因として挙げる場合は、本来その検出機能が動作すべきであったタイミングと、その時点で検出できなかった具体的な観測事実の組み合わせを根拠として提示する。

根本原因を特定した後、類似箇所の見直しに入る前に以下の項目を確認する。これらを満たせない場合は、単に発生した事象を別の言葉で言い換えたにすぎないとみなし、原因分析をやり直す。

- 担当者の注意力、経験、作業状況が変わっても同様に誤りが発生する構造になっているか
- 対象となるファイル、機能、識別子、扱う値や入力の種類が変わっても同様に成立するか
- 同じ原因から、現時点ではまだ不具合として観測されていない潜在的な危険箇所を1件以上導き出せるか
- 外部のコマンド、サービス、ホスト環境の挙動を前提とした判断については、公式のIssueを含む一次情報と実機での動作確認を調査し、事前の思い込みによる判断がなかったかを作り込み要因として整理できているか
- 見逃し要因については、欠陥を入れた変更、または誤った判断・行動を起点に、原因と関係する検出機会と事後検出の候補を扱えているか（`causal-analysis.md`「原因分析の段階」）
- 見逃し要因については、エンドユーザーや外部の消費主体が実行する最上位の公開操作から結果に至る受入シナリオと、既存テストがカバーしている範囲を比較できているか（個別の内部モジュール単体のテストが保証できるのは、そのモジュールの範囲に限られる）

3点目で導き出した潜在的な危険箇所は、`root-cause-remediation.md`「類似見直し」における母集団の選定や、該当が0件だった場合の再検討に活用し、実際に確認された欠陥と区別して証拠として記録する。
見直しを尽くしても潜在的な危険箇所を導出できない場合は、試した観点と導出できなかった根拠を記録して原因分析を確定できる。

## QとC・Dの区別

類似見直しをどこまで深く行うか、処置が必要か、どの段階で作業を終えるかは、問題の性質と重大度を評価して決定する。その結果と判断根拠は原因分析の記録に記載する。記録の記述基準は`analysis-records.md`に従う。

- 品質（Q）に影響する問題：作成した成果物（コード、文書、設定ファイル、作業要求、ユーザーへの報告や確認内容など）が、期待される契約や品質特性を満たしていない問題、または満たさなくなるおそれがある問題。過度なコスト消費が他の必要な作業や品質改善を妨げることが明確であり、機会損失として品質に悪影響を及ぼしうる場合もこれに含める。品質特性の定義は`agent-basics:writing-standards`の`references/quality-principles.md`「QCDと3段判定」に従う
- コスト・納期（C・D）のみに影響する問題：最終的に引き渡す成果物の結果には影響せず、他の必要な作業や改善を妨げる機会損失も発生しない一方で、トークン消費、保守負担、所要時間だけが増加する問題
- 双方の要素を含む問題や、どちらに当たるか判断が分かれる問題は、Qに影響する問題として扱う

Qに影響するかどうかは、その誤りが成果物、判断、報告に影響を与え得たかという観点から判断する。後続の確認工程で防げた、担当者が作業中に気付いた、再実行によって結果が正常に戻ったといった事実があっても、Qへの影響として扱う。

重大度は、利用主体への影響の大きさ、波及する範囲、回復が可能かどうか、および発生頻度から総合的に判断する。影響の目安は、エンドユーザーへの影響がある不良（agent-toolkitとagent-basicsではエージェントの行動誤りを含む）、ユーザーの手間を増やす不良、その他の不良の順に重く、影響度だけから一律の全件調査や候補の全採用を導かない。これにはデータ破損、セキュリティ上の問題、公開契約の破壊、安全性への懸念、依頼された作業を完了できなくなる影響などが含まれる。規範の誤った記述がエージェントの判断や行動にどう波及するかまで検証する。重大な影響がないと言い切るための判断材料が不足している場合は、影響の有無を切り分ける調査を優先して実施する。軽微と判断する場合は、利用主体への影響が小さいことを根拠として示す。

<例>
データ破損や、依頼された作業の完了不能につながるバグ：重大な問題として扱う。
意味を変えない単なる表記の揺れ：軽微な問題として扱ってよい。
危険な操作を案内してしまう誤記や、認可の境界を変えてしまう言葉の誤り：重大な問題になり得る。
</例>

重大度によらず`root-cause-remediation.md`「類似見直し」の標準母集団・段階検索・個別判定・0件時の見直しを行い、重大な問題では原因の及ぶ範囲と判定の深さを広げる。
再発防止策の採否と手段は、重大度にかかわらず費用対効果が最大となるように選ぶ。
防げる損失の見込み（発生頻度×1回の影響）と、読込・確認・往復・保守、反復処置の実行ごとの運用費用を比較する。
費用の定義は`agent-basics:writing-standards`の`references/design-heuristics.md`「案の採否と実施順の判定」に従い、初回限りの実装工数だけで見送らない。
処置が増やす手順の複雑さや規範量も、他の継続費用と同じ重みで数える。
データ破損、セキュリティ、認可境界、取り消せない外部公開など回復できない損失は重く見積もる。
レビューの際限のない往復、hookや実行基盤による作業阻害、過度に複雑な手順や規範の増加も、作業効率への影響の程度に応じて重く見積もる。
従量課金環境では金銭面の損失も含める。
見送る場合は比較の結論と残存リスクを記録する。
類似見直しと再発防止の候補を作ること自体のために、独立した調査工程、専用の計測、毎回の重い検証を加えない。
認可やデータ保全などの硬い制約と明示要件を満たせる手段がない場合は、試みた手段と成立しなかった事実を未達成として報告する。

軽微な問題でも同じ絞り込み型の類似見直しを行い、判定の深さと追加範囲を影響・調査負担に合わせて限定できる。観測された欠陥の修正と、まだ見つかっていない類似欠陥を探す追加調査は明確に切り分ける。どこまで調査したか、どのような調査の限界があるか、どの程度の残存リスクを許容するかを明記し、調査していない箇所まで確認済みであるかのように扱わない。Qへの影響は正直に記録し、新設する再発防止策や検討する改善案は影響の大きさに応じて選定する。

C・Dのみに影響する問題についても、改善によって得られる利点と、調査や今後の運用にかかるコストを比較して処置の要否を判断できる。改善の利点は、その問題を引き起こす操作や設計が今後の作業でどの程度使われるかという頻度に基づいて見積もり、今回たまたま1回で復旧できた場合でも将来の利用頻度から利点を評価する。
重大度は、未知の問題をどこまで深く探索して終了するかと、防げる損失の見積もりに反映する。
すでに判明している欠陥の修正、明示的に指定された対象範囲や完了条件、および規範追加前から存在する既存の成果物の是正範囲は、重大度にかかわらず維持する。
既存の成果物への規定適用は、`agent-basics:writing-standards`の`references/agent-documents-additions.md`「既存対象への波及」に従う。
努力目標ではない追加・強化された規定が適用される成果物で、規定追加前に作成され追加後も引き続き使用されるものも是正の対象に含める。
認可の境界やデータ保全といった変更できない硬い制約も、同様に維持する。

すべての重大度において、各処置の構成要素と完了条件を確認する手段を、`agent-basics:writing-standards`の`references/design-heuristics.md`「問題と手段の比例性」に照らして比較検討する。新しく採用する共通定義、自動チェック、テスト、対象とする値の範囲などは、明示的な要件、規範上の制約、または実際に観測された欠陥のいずれかに個別に対応付ける。
ユーザーが問題として扱わないと明示した事象については、その合意内容および適用中の報告方針に従う。

## 前提の再検討

再発・悪化を問う入力と、作業中の同種修正の反復や既存記録との比較で共通する構造を認めた場合は、症状の追加修正や新しい条文を選ぶ前に、`root-cause-scenarios.md`「反復した指摘の原因判定」と合わせ、個別事象の原因と、同じ失敗が残る経過を分けて分析する。ユーザーから再び指摘されるのを待たない。
共有する規範・書式・通知・工程の変更も前提の候補へ戻し、個別対策の確定と元の問いへの回答を区別する。
問題の発生に関わっている前提条件（既存の仕組み、制約、分類基準、規範の条文など）を「変更できないもの」と決めつけず、前提そのものが誤っていないか、あるいは不要ではないかを原因候補として検討した上で、前提の内側での対処法を比較する。終了条件、しきい値、判断の軸、適用範囲なども見直しの候補に含め、暗黙のうちに置いていた前提を言葉にして別の選択肢と比較する。
修正対象が規範の条文である場合は、その条文が導入・改訂されたコミットを`git log -S`などで特定し、同じ事象に対して過去にどのような修正が行われたかを確認する。すでに過去に対処が行われていた場合は、評価するタイミングや記録先を変更する案だけでなく、条文そのものを維持、修正、または撤去する案も選択肢に含める（過去の事例において、同じ条文の2度目の修正時に条文自体の見直しを行わず、3度目で廃止に至った経緯を踏まえた規定である）。

過去の再発防止策として定められた条文と、今回の改善要求が衝突する場合は、その条文が本来防ごうとしていた失敗の内容とその防止の仕組みを導入時の記録から特定し、新しい改善案でもその失敗を防げるかを判定する。改善案でも同様に失敗を防げるのであれば、同じ作業の中で条文の改訂を実施する。防げない場合は、その防止の仕組みを維持することを理由として改善案を見送る。防止の仕組みが記録から特定できない場合は、条文の文面に書かれた失敗例と比較する。
