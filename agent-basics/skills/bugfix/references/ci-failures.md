# CI失敗の分類と対処

CIの失敗を扱う時に参照する。
原因箇所、今回の変更への帰属、再現性の3つを観測に基づいて別々に分類し、原因を解消する対処を選ぶ。

## 直し始める前

- 全体の完了を待たず、取得できる失敗ジョブのログから先に分析し、完了後に全体の結果と突き合わせる。
- 失敗の全体を見渡し、次の2点を判定して根拠を記録する。
  - 実害の有無: 失敗が、エンドユーザーから観測できる動作の欠陥を示すか。
    実害のある失敗は実装を直す。
    実害のない失敗があっても、独立した反映作業は続けられる。
    CIの成功を条件とする公開と完了の判定は、テストを直してCIの成功を確かめてから行う。
  - テストの作りによる欠陥: 仕様と関係のない変更で失敗したテストは、期待値の更新で済ませず、観測できる結果を確かめる形へ直す。
    同じ保証の重複は削る。
    多数のテストが同じ理由で失敗した場合は、共通部分（fixture、補助関数）を直す。
- 修正の完了は、失敗した元のジョブを同じ条件で再実行し、期待どおりに成功した結果をもって判定する。

## 分類

| 原因箇所 | 特徴 | 確かめ方 |
| --- | --- | --- |
| 実装コードの欠陥 | 変更したコードが公開仕様やテストの期待値と合わない | 失敗ログ、変更したファイルと失敗したテストの対応 |
| テストコードの欠陥 | 期待値、待機条件、fixtureが実装の変更に追随していない | 失敗したテストの差分、実装の変更意図との突き合わせ |
| 環境起因 | 実行環境、外部の依存、外部サービスの不具合で失敗する | 同じcommitでのローカル再現、CIのイメージdigest、外部サービスの状態 |

競合状態や待機条件の不足は、原因箇所を実装コードかテストコードとし、自セッション帰属として直す。
成否がぶれる失敗も修正対象である。

| セッション帰属 | 特徴 | 確かめ方 |
| --- | --- | --- |
| 自セッション帰属 | 変更したファイルや設定が失敗箇所に影響している | 変更差分、失敗したジョブ、呼び出し関係の突き合わせ |
| 自セッションと無関係 | 変更したファイルと失敗箇所に直接・間接の依存が無い | ジョブ名、エラー内容、変更ファイルとの非関連の確認 |

| 再現性 | 特徴 | 確かめ方 |
| --- | --- | --- |
| 決定的な失敗 | 成功と失敗の変動が観測されない | 初回の失敗ログ、同じ箇所での連続失敗 |
| 非決定性の疑い | ログにネットワーク切断、Runnerの枯渇、タイムアウトなど一時的な障害の兆候がある | 初回の失敗ログ、実行環境の資源の状態 |
| 非決定的な失敗 | 同じcommitと同じ条件で成功と失敗が変動する | 対象ジョブを原因ごとに1回だけ再実行した結果、ログの差分 |

帰属を否定しきれない失敗は、次の4系統を対立する仮説として並べ、肯定と否定の事実を記録して切り分ける。
実装（競合、順序、共有状態、時刻、待機）、テスト（fixtureの汚染、順序、並列の干渉、固定していないデータ）、CI環境（設定、キャッシュ、資源、バージョンやイメージの差、Runnerの生成するシェル）、外部要因である。
ローカル再現にCIの層（Runner、Executor、サービスコンテナー）が含まれない場合は、その層を含めて再現する。
GitLab CIでは、ジョブと同じイメージdigestとRunnerのバージョンで`gitlab-runner run-single`を実行すると終了状態を比べられる。
再現していない層に原因があるとする結論は推定と書く。

## 再実行と広域の障害

- 再実行は、非決定性の兆候がある時の診断として、同じ原因につき対象ジョブを1回だけ行う。
  同じ箇所で再び失敗したら打ち切って原因を調べる。
  両方の試行のログを残す。
- 再実行が成功しても、帰属は別に判定する。
  自セッションに帰属する場合は、成否によらず原因箇所を直す。
- ログにRunnerの異常、アクションの取得失敗、外部サービスの応答エラー（HTTP 429・503など）がある場合は、再実行の前に提供元の公式な稼働状況を確認する。
  GitHubでは`curl -sS https://www.githubstatus.com/api/v2/components.json`を実行し、`components`の対象（ジョブ実行とアクション取得は`Actions`）の`status`を見る。
  値は`operational`、`degraded_performance`、`partial_outage`、`major_outage`の4つで、`operational`以外を広域の障害として扱う（出典: <https://www.githubstatus.com/api/>）。
  取得や解析ができない場合は、通常の失敗として扱う。
- 広域の障害の間の失敗は、再現性の判定から除く。
  待機と再実行を繰り返さず、`status`が`operational`へ戻るまで待ち、復旧後の実行を同じ原因の初回として扱う。

## VRTの差分

| 差分の分類 | 特徴 | 追加で確かめること |
| --- | --- | --- |
| 実装意図に伴うUI変更 | 意図した画面の変更 | 実装意図、公開仕様、差分を突き合わせ、実装とテストのどちらを更新するか決める |
| データ差分 | 行数、件数、表示順、表示値の違い | データの取得と加工、初期データ、先行するテストの副作用、並列の実行順 |
| 描画の微小な差 | フォント、アンチエイリアス、線の太さ、スクロールバーの幅 | ブラウザ、フォント、OS、描画の設定と変更差分の突き合わせ |
| 静的アセットの配信不良 | スタイルが適用されない | ビルドログ、HTTP応答、生成ファイル、配信の設定 |

判定に必要なアーティファクトが足りない場合は、取得して存在を確かめてから判定する。

## 対処

| 対処 | 使える条件 | 補足 |
| --- | --- | --- |
| 実装コードの修正 | 原因箇所が実装コードの欠陥 | 7つの問いで確かめた原因を解消する |
| テストコードの修正 | 原因箇所がテストコードの欠陥 | fixtureの汚染、副作用、実行順への依存が原因ならテストの設計を直す |
| CI環境・依存・外部連携の修正 | 環境起因かつ自セッション帰属 | イメージ、環境変数、配信の設定、依存、連携の設定を原因に応じて直す |
| VRTの基準画像の再生成 | テストコードの欠陥で、差分が実装意図に伴うUI変更 | 環境起因ならローカルをCIに合わせる。データ差分なら初期データを固定する |
| 画面マスクの追加 | テストコードの欠陥で、差分が動的な値によるデータ差分 | 初期データの固定を先に検討する |
| 失敗ジョブの再実行 | 再現性が「非決定性の疑い」。同じ原因につき1回 | 診断として行う。広域の障害では待機を優先する |
| 失敗したテストや処理の撤去・縮小 | `agent-basics:writing-standards`の`references/design-heuristics.md`「存在意義の点検」で不要と判定した | 失敗を通すことだけが目的なら使わない。エンドユーザーが観測する機能の撤去と、CIの検査・lint規則の無効化は、撤去の前にユーザーへ確かめる |
| 旧バージョンへの一時的な固定 | 環境起因で、新しいバージョンとの差が原因と確かめ、同じ作業で追随を終えられない | `agent-basics:writing-standards/references/dependency-management.md`「最新版への追従」に従い、理由と解除条件を残す |

- ジョブの除外（`rules:changes`など）、テストの`.skip`・`xfail`、`allow_failure`、差分のない空commitの再pushは使わない。
- CIの設定で失敗を抑える操作は、失敗が今回の変更と無関係であると分かり、根拠を示してユーザーの明示的な合意を得た場合に限る。
- 実装やテストの欠陥が見つかった場合は、帰属によらず同じ作業で直す。
  今回の変更と無関係な既存の不具合の修正は別のcommitに分ける。

## この観点が防ぐ失敗例

- 失敗したテストを1件ずつ期待値に合わせて直し、仕様と関係のない変更で落ちるテストが残った。
  次の変更でも同じ種類の失敗が繰り返された。
- 広域の障害の間に再実行を繰り返し、原因の調査を始めるのが遅れた。
  提供元の状態を先に見れば、待機で済んだ。
