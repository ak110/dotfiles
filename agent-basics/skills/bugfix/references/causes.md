# 原因の確かめ方

問い2で原因を説明できない時と、外部の挙動、並行する処理、試験の作り、所要の増大、他者からの報告が関わる時に確かめる。

## 観測と推測の区別

- 次のものは推測と呼ぶ: 相関だけで結び付けた原因、条件のそろわない比較、対応を確かめていない値、再現していない層にあるとした原因。
- 入力が関わる時: 入力の生成、変換、観測、消費を対応付け、どこまで確かめたかを示す。
  合成の入力で説明した範囲と、実際の入力で確かめた範囲を分ける。
- 処理が動かなかった時: 処理へ届かなかった場合と、届いて失敗した場合を分ける。
- 終了コードが0でも警告が出ている時: 警告の内容を確かめる。
- 作業の途中で見つけた時: 着手前の状態と差分を比べ、自分の未commitの変更が入れた問題か、既存の問題かを分ける。
- 原因を確定できない時: 確定したと書かず、候補と、候補を減らす次の観測を記録する。
  後続へ渡す場合は、仮説、支持する事実、確かめる方法、結果（支持、反証、判定不能）ごとの処置を書く。
- 調査のために入れた変更は、効果が無ければ自分の変更だけを戻す。
  他の担当の差分は保つ。
- 診断の出力は必要な項目だけを選んで出し、資格情報と個人の情報を除く。
- 担当の注意不足や理解不足は原因に挙げない。
  担当や注意の度合いが変わっても同じ誤りが起きる構造（誤りを誘った入力、止められなかった仕組み）を原因として特定する。

## 場面ごとの確かめ方

- 外部（ライブラリ、サービス、実行環境）の挙動を原因に挙げる時: 使っている版と同じ版の一次資料と、実機で確かめる。
  確かめるまでは推測と書く。
- 外部サービスの不調の兆候がある時: 手元の確認を繰り返す前に、提供元の公式の障害情報を見る。
- 設定の値、依存の版、規範や手順の条文を原因に挙げる時（守られなかった、足りなかったという指摘を含む）: 事象の時点でそれが適用されていたことを、変更履歴と当時の記録で確かめる。
  確かめるまでは推測と書く。
- 稼働中の環境の障害の時: 発生時刻の前後の変更（配備、設定、依存、基盤）の履歴と、ログや計測値を比べる。
  取得できない範囲は、必要な情報と取得の手段を依頼元へ示す。
- 並行や排他が候補の時: 共有する状態を変えうる全ての主体と、ロックが守る範囲を比べる。
- 再起動の後だけ失敗する時: 残っている状態（設定、キャッシュ、ロック、保存した状態）を先に調べる。
- 試験が失敗した時: 対象の欠陥と、試験の作りの欠陥を分ける。
  仕様と関係のない変更で失敗した試験は、期待値の更新で済ませず、観測できる結果を確かめる形へ直す。
- 所要が増えた時: 全体の所要を区間に分け、区間ごとに条件をそろえて比べる。
  1手あたりの費用、手数、並行する担当の数と待ちに分け、記録が残る範囲で最も良かった時期と比べる。
  説明できない差は未特定と書く。
- 他者から報告を受けた時: 期待、症状、報告者による原因の説明を分ける。
  原因の説明は仮説として扱い、現物で確かめる。
- 件数や範囲を述べる時: エンドユーザーが見る層で数える。
- 検索や読取は成功したのに必要な情報へ届かなかった時: 案内の不足や誤った参照を原因の候補に含める。

## 意図と経緯の調べ方

変更の有無、由来、「なぜこうなっているか」を答える時は、次の順に調べる。
前の資料で確定しない部分だけ次へ進む。

1. 現行の実装と文書。
2. 導入した変更（変更履歴の該当する変更と、その説明）。
3. 要求の原文（作業項目、依頼、指摘）。
4. 会話の記録。

「変えていない」「無い」と答える前に、現行の値だけでなく、変更履歴と要求の原文を確かめる。

## 独立した調査を頼む時

- 渡すのは、期待、症状、発生の条件、対象の版、取得済みの証拠の所在に限る。
  原因の候補と修正の案は除く。
- 返った結果は、現物で確かめ直してから使う。

## この観点が防ぐ失敗例

- 外部サービスの挙動を原因として記録したが、その版の資料も実機も確かめておらず、後で別の原因だと分かった。
- 設定の変更の有無を問われ、現行の値と一部の記録だけを見て「変えていない」と答えた。
  変更履歴の全件と要求の原文は確かめておらず、再び指摘を受けて調べ直した。
