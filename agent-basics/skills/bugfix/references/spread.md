# 広がりの探し方

問い4の探し方を決める時と、害が大きく探す範囲を広げる時に確かめる。

## 探す対象を決める

- 破られた条件か、誤った判断の規則を1文で書く。
- その文の、観測したファイル名、工程名、識別子を別のものへ置き換えても成り立つかを確かめる。
  成り立たない文は、観測した1件の説明にとどまっているので書き直す。
- 値や動作を変える時: その値を読む側、書く側、期待値にしている試験を、実装からたどる。
- 資源や時間の上限が関わる時: 上限を共有する単位（ホスト、プロセス、接続）での合計で比べる。

## 同じ仕組みの他の箇所

- 現存するファイルと、直近7日の履歴（作業項目、会話の記録）を探す。
  原因が他の範囲に及ぶ場合だけ広げる。
- 現存するファイルは、日付で除外せずに検索する。
- 履歴の期間の外は調べていないと記録する。
  期間の外の事例を依頼元が挙げた場合は、その事例を含める。
- 検索の式と件数を残す。
  件数が多ければ条件を足し、残った候補だけを本文で該当、保留、非該当に分ける。
  0件なら、別の語か別の観点で1回だけ見直す。
- 同じ規則で全体を機械的に検査するコマンドの全体実行は、その規則の探索として扱える。
  コマンドの対象の外は検索で補う。
- 対象を除外する時: 現物と条件の不一致を根拠にする。
  名前や場所の違いだけの対象は、探す対象に残す。
- 見つけた同じ誤りは、同じ作業で直す。
  担当の外の対象は、事象、原因、修正の方針を依頼元へ返す。

## 同じ害への既存の対策

- 現存する規範、検査、試験を、害を表す語（何が損なわれたか）で検索する。
  原因を表す語での検索は、これに加えて使う。
- 「仕組みが無い」「規範が無い」と述べる前に、この検索を実行する。
- 対策が見つかり、それでも今回起きた場合は再発である。
  `recurrence.md`の条件が成立する。

## 害が大きい時

- 起点の事象、場所、修正を伏せた独立の担当による走査を1回行う。
  起点を検出できるかを確かめる走査では、問題を含む修正前の版を対象にし、起点も他の対象と同じ並びと注釈で渡す。
- 走査が起点を検出できなければ、検索の条件を1回直す。
  それでも検出できなければ、限界として記録して終える。
- 走査を分担しても、原因の判断と結果の採否は依頼した側が持つ。
- 探した範囲、探していない範囲、許容する残りの危険を記録する。
  調べていない箇所は、未確認と書く。

## この観点が防ぐ失敗例

- ある文書の誤りを指摘されて直したが、同じ構造を持つ別の文書を探さず、同じ誤りが残った。
- 「引き継ぐ仕組みが無い」ことを原因として報告したが、その役割を持つ仕組みは既にあった。
  害を表す語で既存の対策を検索していなかった。
