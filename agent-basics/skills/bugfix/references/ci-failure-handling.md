# CI失敗の分類と適切な対処

CIの失敗について、原因箇所、今回の変更（セッション）への帰属、再現性の3つの観点から客観的な観測事実に基づいてそれぞれ分類し、原因そのものを根本から解消する対処法を選ぶ。原因が自明で単純な失敗であれば複数の対立仮説を細かく評価する手順は省略できるが、拡張原因分析が必要かどうかの判断は`root-cause-analysis.md`「初動と拡張原因分析の判定」に従って行う。

## 失敗の性質による分類

原因箇所、セッション帰属、再現性の3観点をそれぞれ個別に分類し、ビジュアルリグレッションテスト（VRT）の場合は画面差分の形態も合わせて評価する。原因箇所とセッションへの帰属を特定した上で、恒久的な対処方法を選択する。

### 原因箇所

| 原因箇所 | 特徴 | 代表的な確認方法 |
| --- | --- | --- |
| 実装コードの欠陥 | 変更したコードが公開仕様やテストの期待値と一致しない | 失敗ログ、変更したファイルと失敗したテストの対応関係 |
| テストコードの欠陥 | テスト側の期待値、待機条件、テストフィクスチャ（fixture）が実装変更に追随していない | 失敗したテストの差分、実装側の変更意図との突き合わせ |
| 環境起因 | 実行環境、外部依存ライブラリ、外部サービスの不具合によって失敗する | ローカル環境で同一コミット（SHA）での再現確認、CI環境のコンテナーイメージdigest、外部サービスのステータスや応答 |

競合状態（レースコンディション）や待機条件の不足などによる実装・テストの不具合は、原因箇所を「実装コード」または「テストコード」とし、帰属は「自セッション」として扱う。実行タイミングによって成否が変わる場合（非決定的な失敗）であっても、修正すべき対象として扱う。

### セッション帰属

| セッション帰属 | 特徴 | 代表的な確認方法 |
| --- | --- | --- |
| 自セッション帰属 | 変更したファイルや設定の変更が失敗箇所に影響を与えている | 変更差分、失敗したジョブ、コードの呼び出し関係の突き合わせ |
| 自セッションと無関係 | 変更したファイルと失敗箇所に直接・間接の依存関係がない | 失敗したジョブ名、エラー内容、今回の変更ファイルとの非関連性の確認 |

### 再現性

| 再現性 | 特徴 | 代表的な確認方法 |
| --- | --- | --- |
| 決定的な失敗（非決定性を確認できない） | 成功と失敗の変動が観測されない | 初回の失敗ログ、同一箇所での連続失敗の確認 |
| 非決定性の疑い | ログにネットワーク切断、CI Runnerの枯渇、タイムアウトなど一時的な障害の兆候が見られる | 初回の失敗ログ、CI実行環境のリソース状態 |
| 非決定的な失敗（Flaky） | 同一コミット（SHA）かつ同一の実行条件でも成功と失敗が変動する | 原因単位で1回のみ対象ジョブを再実行した結果、実行時刻ごとのログ差分の比較 |

- 非決定性が疑われる場合は、同一の原因に対して対象ジョブの再実行を1回だけ行う。結果が変わって成功すれば非決定的な失敗と判断し、同じ箇所で再度失敗した場合は再実行を打ち切って原因調査へ進む。どちらの試行についてもログとアーティファクト（生成物）を記録として残す。
- 再実行はあくまで再現性を診断するための手段であり、CI完了の判定は原因の解消と帰属の特定をもって行う。再実行によって成功した場合は、再実行回数と外部環境に起因する旨の判定を記録する。
- ログにCI Runnerの異常、GitHub Actionsのアクション取得失敗、外部サービスの応答エラー（HTTP 429・503など）が記録されている場合は、再実行する前にサービス提供元の公式ステータスを確認する。GitHubの場合は`curl -sS https://www.githubstatus.com/api/v2/components.json`を実行し、`components`から対象（Actionsのジョブ実行やアクション取得であれば`Actions`）の`status`を確認する。`status`の取りうる値は`operational`、`degraded_performance`、`partial_outage`、`major_outage`の4種類であり、`operational`以外の3つを広域障害として扱う（出典: <https://www.githubstatus.com/api/>）。情報の取得や解析ができない場合は広域障害とはみなさず、再実行の回数制限を守った上で通常の手順を進める。
- 広域障害が発生している期間の失敗は再現性の判定対象から除外する。一定時間ごとの待機と再実行を繰り返すのではなく、対象コンポーネントの`status`が`operational`に復旧するまで待機する。復旧後の実行を、同一原因における初回の試行として扱う。CI実行の監視は、対象の実行基盤が定めている標準手順に従って行う。

### VRT（ビジュアルリグレッションテスト）固有の差分分類

アーティファクトの差分画像から形態を分類し、3つの基本観点（原因箇所・セッション帰属・再現性）についてはログ、変更差分、同一コミットでの再現結果から個別に確定する。

| VRT差分分類 | 特徴 | 3観点の確定に必要な追加確認 |
| --- | --- | --- |
| 実装意図に伴うUI変更 | 意図した画面レイアウトの変更 | 実装意図、公開仕様、画面差分を突き合わせ、実装コードとテストコードのどちらを更新すべきか判断する |
| データ差分 | テーブルの行数、件数、表示順序、表示値の違い | データ取得・加工処理、初期データの内容、先行テストによる副作用、並列テストの実行順序を確認する |
| 描画の微小な差 | フォント、アンチエイリアス、線の太さ、スクロールバーの幅の違い | 使用ブラウザ、フォント設定、OS、レンダリング設定とコード変更差分を突き合わせる |
| 静的アセットの配信不良 | CSSスタイルが適用されず、ワイヤーフレームのように表示される | ビルドログ、HTTPレスポンス、生成ファイル、アセット配信設定、実行環境の状態を確認する |

## 対処法の選択肢と判定基準

| 対処法の選択肢 | 適用可能な条件（3観点） | 適用できない条件 | より上位の対策検討 |
| --- | --- | --- | --- |
| 実装コードの修正 | 原因箇所が「実装コード欠陥」。セッション帰属と再現性は問わない | なし | `agent-basics:bugfix`の原因分析で特定した根本原因を解消する修正を行う |
| テストコードの修正 | 原因箇所が「テストコード欠陥」。セッション帰属と再現性は問わない | なし | フィクスチャの汚染、先行テストの副作用、並列実行順序への依存が原因である場合は、テスト自体の設計を見直す |
| CI環境・依存関係・外部連携の修正 | 原因箇所が「環境起因」かつ「自セッション帰属」。再現性は問わない | 自セッションと無関係な場合 | CIイメージ、環境変数、配信設定、依存ライブラリ、外部サービスとの連携設定を、原因に応じて修正する |
| VRTベースライン画像の再生成 | 原因箇所が「テストコード欠陥」で、VRT固有分類が「実装意図に伴うUI変更」に該当する。セッション帰属は問わない | その他の分類 | 環境起因の場合はローカル環境をCI環境と一致させる。データ差分が原因の場合はテストの初期データを固定する |
| 画面マスクの追加 | 原因箇所が「テストコード欠陥」で、VRT固有分類が「動的値によるデータ差分」に該当する。セッション帰属は問わない | 実装コード欠陥、または環境起因による主要領域の差分 | 初期データの固定を優先する |
| 失敗ジョブの再実行 | 再現性が「非決定性の疑い」。同一原因の対象ジョブにつき1回のみ実行可能 | 非決定性の疑いがない決定的な失敗 | 修正計画を確定する前の再現性診断として実施する。独立した原因ごとに再実行の要否を判断する。自セッションに帰属する場合は、再実行の成否にかかわらず原因箇所を修正する。広域障害の場合は「再現性」に記載した待機手順を優先する |
| `rules:changes`によるジョブ除外 | 適用可能な分類なし | すべての分類 | 対象ファイルの変更時に必要な品質検証がスキップされてしまうため適用しない |
| テストの`.skip`や`xfail`指定 | 適用可能な分類なし | すべての分類 | テストコードまたは実装コードを修正する |
| `allow_failure`による失敗の許容 | 適用可能な分類なし | すべての分類 | 失敗の原因を除去する |
| 依存ライブラリのバージョン固定（ピン） | 原因箇所が「環境起因」であり、ライブラリのバージョン差異が原因であると実際に確認できた場合のみ | その他の分類 | 仕様変更への追随改修案と比較検討する。既存の認可範囲で実施できる修正は自ら進め、追加の認可やユーザー固有の判断が必要な場合は依頼元へ返す |
| 変更差分のない空コミット（`CI trigger`）の再push | 適用可能な分類なし | すべての分類 | 非決定性が疑われる場合は、提供されているCLI等を用いて対象ジョブのみを1回再実行する |

CI設定側での失敗の抑制（ジョブの除外、テストのスキップ、失敗の許容化など）は、CIの失敗が今回のセッションの変更とは無関係であることが判明し、その根拠を提示した上でユーザーから明示的な合意を得られた場合に限って使用できる。
セッション帰属の判定は、対立仮説の検討や拡張原因分析の要否に用いる。帰属だけを理由にしたユーザー確認は行わず、実装やテストの欠陥が見つかった場合は帰属にかかわらず同じ作業セッション内で修正する。

## 分類判断のための詳細検討

自セッションに帰属する、あるいは自セッションへの帰属を否定しきれない失敗については、初回のログが一見すると決定的な失敗に見える場合であっても、実行タイミングの違いによる変動を考慮し、次の各層を対立仮説として検証する。ただし、観測結果から帰属と原因を即座に判断できる失敗（自明で単純なミスや、確認済みの無関係な外部基盤障害）は、この詳細検討の対象から除外してよい。

- 実装面: 競合状態（レースコンディション）、実行順序への依存、共有状態の参照・更新、実行時刻や日付による変動、待機条件の不足、結果整合性（eventual consistency）の遅延など
- テスト面: フィクスチャの汚染、テストの実行順序への依存、並列実行時の干渉、固定されていないテストデータ・システム時刻・乱数など
- CI環境面: 設定の不備、キャッシュの影響、メモリーやCPU等のリソース不足、依存パッケージやランタイムの差異、コンテナーやOSの差異、CI Runnerや実行プログラム（Executor）の差異、Runnerがスクリプトを実行する際に生成するラッパーシェル、サービスコンテナーの挙動など
- 外部要因: CI Runner自体の障害、ネットワークの瞬断、DNSの名前解決失敗、外部サービスの障害やレートリミットなど

各仮説について、それを肯定する事実と否定する事実を記録し、仮説の真偽を切り分けるための検証実験を行って結果を記録する。該当しないと判断した層についても、否定する根拠を明確にして除外する。なお、同一コミット（SHA）での再実行が成功したとしても、それは単に実行結果が非決定的であることを示すにすぎず、原因が自セッションにあるかどうかは別途判定する必要がある。原因の分類が2つ以上残る場合は複数の原因が重なっていると判断し、特定できた原因から順次対処する。

- ローカル環境での再現検証において考慮すべき層（CI RunnerとExecutorの差異、生成されるシェル、サービスコンテナーなど）が含まれていない場合は、それらの層を含めた形で再現する。GitLab CIの場合は、ジョブと同一のイメージdigestおよびRunnerバージョンを指定して`gitlab-runner run-single`を実行することで、Runnerが報告する終了ステータスを比較できる。これに関する検証記録は`docs/development/audit-records.md`の「agent-basics/skills/bugfix/references/ci-failure-handling.md：分類判断のための詳細検討：2026年10月7日」に記載されている。再現できていない層に原因があると結論づける場合は、確定ではなく「推定」として扱う
- 過去に同様の失敗が発生していないかを`git log --grep`等で検索して確認する
- テスト対象のコードを意図的に壊し、該当するテストが失敗するかどうかを確かめる
- VRTで判定に必要なアーティファクト（差分画像等）が不足している場合は、取得可能な実行環境でアーティファクトを取得し、ファイルの実在を確認した上で判定を再開する
