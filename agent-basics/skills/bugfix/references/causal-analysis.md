# 因果関係の特定と原因分析の進め方

本書は、拡張原因分析を実施する場合や、根本原因の特定に履歴やログの調査、2系統の分析を用いる場合について、資料の確認順序、因果関係の特定方法、2系統4段階での分析手順、および直接的な原因と根本原因の記録方法を定める。
特定した根本原因から類似箇所を見直す時は`root-cause-remediation.md`、処置の階層を判断する時は`root-cause-actions.md`、再発防止策を選ぶ時は`root-cause-prevention.md`に従う。

## 拡張原因分析の資料確認と因果関係の特定

実装意図と見逃しの経緯を、次の順で調べる。

1. 調査範囲を保つため、外部障害は要求との関係と原因判定に必要な範囲に絞る。
   機能する提供元の採用や対象限定のユーザー判断を守り、除外された代替サービスは調べ続けない。
   無関係・管理不能な外部サービスの修復を完了前提にせず、必須検証が成立しなければ未確認の要求と続行できない理由を残す。
   成果物による外部エラーの誤処理などは対象内で修正する。
   外部サービスの不調では、手元確認を2回以上繰り返す前に公式ステータスや障害情報を確認し、影響する障害があれば手元確認を打ち切り、報告がなければ原因未確定として両面を調べる（努力目標）。
2. 意図と経緯の根拠を得るため、現行の実装コード・テスト・コメント・各種ドキュメント・設計書、`git blame`や導入commit・関連レビュー、要求原文・issue・作業要求・当時の計画の順に確認する。
   なお不明ならセッションログや会話履歴へ進み、説明がついた段階と確認できなかった資料を記録する。
   参照不能なら確認先と不足情報を示し、担当者の意図は確認できた記載の範囲で述べる。
   アドホックな回避処理（責務境界を越す呼び出し、非公開関数の横断利用、重複状態記録など）は、正常な関連処理、本来の責務分担、導入commitと比較する。
   正常な構造へ戻せない明確な根拠がある場合だけ、局所的な対症療法を根本対策と判定する。
3. 前提の取り違えを防ぐため、コードで説明できても`root-cause-analysis-evidence.md`「直接的原因と事象時点の確定」に従って外部入力の実形を確認し、説明上の入力と実記録を区別する。
   レスポンスの意味は公式仕様と実レスポンスから確定し、一般用語の意味や外部ツールの要約・省略表示から推測しない（二値状態をステータスコードで表すAPIでは意味が逆になる場合もある）。
   未確認の前提が採否を変える間は結論を保留する。
4. 因果を裏付けるため、対立候補を洗い出し、除外できない候補を明確にして、因果の各段階を資料や実機結果で裏付ける。
   絞り込みで母集団や処置が変わる場合は、残る全候補の範囲を合わせる。
   直接操作できない環境でコード調査・手元再現でも特定できなければ計画作成を中断し、調査用コードと取得手順を用意して操作できる主体からログなどを得る。
   得たデータで原因を特定してから再開する。
5. 個別事象から根本原因を導くため、「原因分析の段階」の2系統・L1〜L4と共通規則を適用する。
   直接的原因と根本原因を区別し、両系統の必要な確認と根拠の対応を終えてから確定する。
   確認できない事情があれば残る確認と続行できない理由を未完了事項とする。
6. 後続の再確認を可能にするため、調査先、コマンド、確認日時、結果、特定範囲と限界を記録する。
   集計には時点に左右されない統一基準と母集団総数を併記し、作成時点を直接示さない指標では特定しきれない範囲を明記する。

## 原因分析の段階

原因分析は、「作り込み要因（なぜ誤った実装・記述・判断・行動が生じたか）」と「見逃し要因（なぜレビュー、テスト、監視などで検出できなかったか）」の2系統に分け、それぞれL1からL4の順序で掘り下げる。
外部の主体には、調査対象の処理の外側で同一の共有状態を変更するローカルCLI、別プロセス、ホスト環境、外部サービスなどが含まれる。
外部の主体が関わっている場合、作り込み要因のL2には、採用した外部挙動の前提と、その前提を裏付けた同バージョン・同条件の一次資料、提供元のIssue、実機での検証結果を記載する。
事前の確認を怠り推測を事実として設計した場合は、その判断自体をL2に記録する。
個別のコマンド名や呼び出し順序の違いだけに原因を求めない。
外部の変化を受けた対処では、作り込み要因のL2に、変化の理由・現在の推奨・代替を確かめたか、確かめずに復元でよいとした判断があればその判断を記録する。
見逃し要因のL2には、復旧や既存テストの成功だけを妥当性の根拠にして比較の不足を見逃した、実在の検出機会を記録する。
未確認の判断意図や存在しない検出機会は推測で確定しない。
見逃し要因のL2には、実際の利用場面で最初に実行される公開操作、最終的に得られる結果、および既存のテストが実際に検証していた操作と状態遷移を記載する。
テストの名称だけにとらわれず、実際に実行された主体と検証境界に着目して両者の違いを判断する。
見逃し要因の系統は、作り込み要因で特定した欠陥を入れた変更（commit、MR、設定変更、規範の改訂など）を起点にする。
変更を伴わないセッション中の判断・行動・確認・委譲の誤りでは、その誤りが起きた時点を起点にし、観測までの実行レビュー、hook、振り返りなどの検出機会を検討する。
対象にする検出機会は原因の成立に関係する機会に限り、その変更のレビュー、欠陥の挙動を扱うテスト、原因の条件を確かめ得た確認や監視が該当する。
記録から確認できる機会ごとに、見逃した理由をL2以降へ記す。
ユーザーの指摘で発覚した場合は、指摘より前に作業者が何を根拠に問題へ気付けたかを、実在した判断・検収・テストの機会へ対応付ける。
混入を防ぐ構造の変更と、その構造を問題と認める判断の是正を区別し、両方への作用を示せる場合だけ同じ処置を両系統に兼用する。
記録が残らない機会は未確認として区別する。
調査の対象は原因と関係する機会に限る。
同じ変更が欠陥の挙動を期待値とするテストや、その挙動を方針として述べる設計書を含む場合は、それらとの一致を受け入れの根拠にした判断を見逃し要因のL2の候補として調べる。
欠陥を入れた変更も誤った判断・行動も存在しない事象（外部環境の変化だけが原因の場合など）は、後述の共通規則に従って起点の特定を該当なしとできる。
ユーザー指摘より前に対象または同種のセッションを振り返りが走査していた場合は、実在した検出機会として見逃し要因のL1〜L3で分析する。
まだ走査していなければ実在した機会には数えず、いずれの場合も振り返りへの観点追加などの事後検出を見逃し要因の再発防止策の候補に含める。
プロジェクトがreview-sessionを用いる場合は、その走査状況と観点を確認する。
障害注入（フォールトインジェクション）やテストダブル（モック等）を使用した場合は、実際の主体、副作用を起こす主体、発生タイミング、後続の処理をそれぞれ正確に対応づけて整理する。

| 段階 | 作り込み要因で掘り下げること | 見逃し要因で掘り下げること |
| --- | --- | --- |
| L1現象 | 具体的に何を誤って実装・記述・判断・実行したか | 欠陥を入れた変更、または誤った判断・行動から観測までの検出機会のうち、どの機会で検出できなかったか |
| L2判断 | なぜその実装・記述・判断・行動でよいと判断したか | なぜ問題であると気づけなかったか |
| L3構造 | なぜその判断のまま実装・記述・行動を進められたか | なぜ誤った結果や機能不全を責務の境界で防げず、検出の仕組みからも修正につなげられなかったか |
| L4システム | L3の構造を生んだ、または許した規範・設計・工程・役割分担・改訂の仕組みは何か | 検出が特定の仕組みや属人的な注意に頼った理由と、検出結果を修正へつなぐ仕組みの有無は何か |

- L3の作り込み要因には、既存の規範が判断材料や選択肢を過剰に狭めてしまい、本来の目的にかなう判断を阻害していた構造も考慮する。
  規範の文言どおりに従うこと自体が不適切な結果を生んでいる場合は、ルールを追加する前に、既存ルールの緩和・削除・一般化が可能かを検討する。
- 個人の理解度や注意不足を理由にするとL1〜L2の現象と判断の繰り返しにとどまるため、誤った判断を許した構造的な要因や、検出できなかった仕組みまで掘り下げる。
- 暫定対策を除く抜本的な処置は、原則としていずれかの系統がL3に到達した段階で決定してよい。
  処置を決めた後も両系統のL4まで確認・記録する。
  L3まで掘り下げられない系統がある場合は、確認した資料と掘り下げられない理由を明記し、L3まで到達できた側の系統を根拠として処置を決める。
- 規範、仕様、設定の間で条文どうしが矛盾している事象では、それぞれの条文が追加された変更を調査し、ユーザーの指示によるものかエージェントの判断によるものかを明確にしてからL2とL3を記述する。
  優先順位は確定した由来に基づいて決定する。
  単に以前から存在していることだけを優先の根拠にしない。

直接的な原因は、両系統の分析に先立って特定する実行時、データ、設定上のメカニズムである。
処理が成立しなかったことが直接の原因である場合は、制御が処理自体に到達しなかったケース（処理の中断・離脱のタイミング、保護機構の内外、確定処理の途中の区間など）と、処理に到達した上で失敗したケース（呼び出し自体は成立したがエラーや不正な戻り値となった場合）を明確に区別して扱う。
根本原因は、最深段階の作り込み要因と見逃し要因を結びつけ、同じ失敗の連鎖を断ち切る条件を一般化した結論としてまとめる。
そして、直接的な原因との違いを明確にした上で、原因分析表の最深段に記録する。
観測されたコマンド、ファイル、工程、テスト関数などを別の同種のものに置き換えたときに成り立たなくなる原因は、個別事象の説明にすぎないため、L1または直接的な原因の記述に戻す。
最深段には、「外部の挙動を確認しないまま設計できてしまった構造」や「実際の利用シナリオを検証しないまま完了とみなせてしまった構造」のように、対象が変わっても同じ誤判断を引き起こす汎用的な単位で記述する。
L1〜L4の各段と類似見直し観点における「該当なし」は、その問いに当たる事実が存在しないことを確かめた場合に限り、確かめた範囲を根拠として記録する。
前の段で説明がついたことや処置が決まったこと、処置で原因を除去できることは、該当なしの根拠にしない。
L4では、L3の構造がプロジェクトの管理外にある上流製品や外部環境だけで生じた場合など、問いに当たる事実の不在を確認した範囲を示す。
各段階に確定した具体的な内容、仮説、あるいは共通規則に沿った「該当なし」を記録する。
仮説や未確認は調査途中の状態として区別し、必要な資料・実装・履歴の確認をすべて終えた場合に限り分析を確定する。
上位段の候補は未確定だけを理由に該当なしへ変換せず、仮説に支持する事実と不確実性を残して改善の採否へ接続する。
規範、仕様、設計文書が存在しないことをL3やL4の要因として挙げる前に、`root-cause-severity-quality.md`「原因分析の品質確認」に沿って確認する。
