# 因果関係の特定と原因分析の進め方

本書は、拡張原因分析を実施する場合や、根本原因の特定に履歴やログの調査、2系統の分析を用いる場合について、資料の確認順序と因果関係の特定方法を定める。
2系統4段階の分析手順と、直接的な原因と根本原因の記録方法は`causal-analysis-stages.md`に従う。
特定した根本原因から類似箇所を見直す時は`root-cause-remediation.md`、処置の階層を判断する時は`root-cause-actions.md`、再発防止策を選ぶ時は`root-cause-prevention.md`に従う。

## 拡張原因分析の資料確認と因果関係の特定

実装意図と見逃しの経緯を、次の順で調べる。

1. 調査範囲を保つため、外部障害は要求との関係と原因判定に必要な範囲に絞る。
   機能する提供元の採用や対象限定のユーザー判断を守り、除外された代替サービスは調べ続けない。
   無関係・管理不能な外部サービスの修復を完了前提にせず、必須検証が成立しなければ未確認の要求と続行できない理由を残す。
   成果物による外部エラーの誤処理などは対象内で修正する。
   外部サービスの不調では、手元確認を2回以上繰り返す前に公式ステータスや障害情報を確認し、影響する障害があれば手元確認を打ち切り、報告がなければ原因未確定として両面を調べる（努力目標）。
2. 意図と経緯の根拠を得るため、現行の実装コード・テスト・コメント・各種ドキュメント・設計書、`git blame`や導入commit・関連レビュー、要求原文・issue・作業要求・当時の計画の順に確認する。
   なお不明ならセッションログや会話履歴へ進み、説明がついた段階と確認できなかった資料を記録する。
   参照不能なら確認先と不足情報を示し、担当者の意図は確認できた記載の範囲で述べる。
   アドホックな回避処理（責務境界を越す呼び出し、非公開関数の横断利用、重複状態記録など）は、正常な関連処理、本来の責務分担、導入commitと比較する。
   正常な構造へ戻せない明確な根拠がある場合だけ、局所的な対症療法を根本対策と判定する。
3. 前提の取り違えを防ぐため、コードで説明できても`root-cause-analysis-evidence.md`「直接的原因と事象時点の確定」に従って外部入力の実形を確認し、説明上の入力と実記録を区別する。
   レスポンスの意味は公式仕様と実レスポンスから確定し、一般用語の意味や外部ツールの要約・省略表示から推測しない（二値状態をステータスコードで表すAPIでは意味が逆になる場合もある）。
   未確認の前提が採否を変える間は結論を保留する。
4. 因果を裏付けるため、対立候補を洗い出し、除外できない候補を明確にして、因果の各段階を資料や実機結果で裏付ける。
   絞り込みで母集団や処置が変わる場合は、残る全候補の範囲を合わせる。
   直接操作できない環境でコード調査・手元再現でも特定できなければ計画作成を中断し、調査用コードと取得手順を用意して操作できる主体からログなどを得る。
   得たデータで原因を特定してから再開する。
5. 個別事象から根本原因を導くため、`causal-analysis-stages.md`「原因分析の段階」の2系統・L1〜L4と共通規則を適用する。
   直接的原因と根本原因を区別し、両系統の必要な確認と根拠の対応を終えてから確定する。
   確認できない事情があれば残る確認と続行できない理由を未完了事項とする。
6. 後続の再確認を可能にするため、調査先、コマンド、確認日時、結果、特定範囲と限界を記録する。
   集計には時点に左右されない統一基準と母集団総数を併記し、作成時点を直接示さない指標では特定しきれない範囲を明記する。
