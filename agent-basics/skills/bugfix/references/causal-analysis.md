# 因果関係の特定と原因分析の進め方

本書は、拡張原因分析を実施する場合や、根本原因の特定に履歴やログの調査、2系統の分析を用いる場合について、資料の確認順序、因果関係の特定方法、2系統4段階での分析手順、および直接的な原因と根本原因の記録方法を定める。特定した根本原因から導く類似箇所の見直し、処置の階層、再発防止策については`root-cause-analysis.md`を参照する。

## 拡張原因分析の資料確認と因果関係の特定

- 資料は次の順序で確認する。現行の実装コード・テスト・コメント・各種ドキュメント・設計書、`git blame`や導入時のコミット・関連レビュー、要求原文・issue・作業要求・当時の計画、それでも実装意図や見逃しの経緯が分からない場合はセッションログや会話履歴を確認する。どの段階で説明がついたか、またどの資料が確認できなかったかを記録する。
- 対立する原因候補を洗い出し、反証によって除外できない候補を明確にしてから因果関係を確定する。推測した因果関係の各段階は資料や実機での動作結果で裏付けを取り、原因候補の絞り込み具合によって類似見直しの母集団や処置内容が変わる場合は、残っている全候補を合わせた範囲を対象とする。
- 調査の記録には、調査先、実行したコマンド、確認した日時、結果、および特定できた範囲と限界を残す。集計値を記載する場合は、確認時点に左右されない統一した判定基準と、母集団の総数を併記する。作成時点を直接示さない指標をもとに判断する場合は、特定しきれない範囲を明記する。
- 参照できない資料がある場合は、確認先と不足している情報を明記する。当時の担当者の意図を述べる際は、確認できた資料に記載されている範囲に留める。
- 直接操作できない環境で発生した問題で、コードの調査や手元での再現によって因果関係を特定できない場合は、計画の作成を中断し、調査用コードとデータの取得手順を用意して、その環境を操作できる主体からログなどのデータを得る。得たデータをもとに原因を特定してから作業を再開する。
- 責務の境界を越えた呼び出し、非公開関数の横断的な利用、重複した状態記録などのアドホックな回避処理を見直す際は、同じ機能で正しく動作している関連処理や、本来の設計上の責務分担、導入時のコミットと比較する。局所的な対症療法を根本対策と判定できるのは、既存の正常な処理構造に戻せない明確な根拠がある場合に限る。
- 外部から受け取ったレスポンスの意味は、公式の仕様定義と実際のレスポンス内容をもとに確定する。プログラミング上の一般的な用語の意味（たとえば二値の状態をステータスコードで表すAPIでは意味が逆になる場合がある）や、外部ツールの要約・省略表示から推測して判断しない。
- 外部サービスを利用する処理が正常に動かない場合は、手元環境の確認を2回以上繰り返す前に、サービス提供元の公式ステータスや障害情報を確認する。影響する障害が報告されている場合は手元環境の確認を打ち切り、報告がない場合は原因を未確定として両面から調査を進める（努力目標）。
- 外部障害は要求との関係と原因の判定に必要な範囲で調査する。ユーザーが機能する提供元を採用した場合や対象を限定した場合は、その範囲を守り、除外された代替サービスの調査を続けない。無関係または管理不能な外部サービスの修復を完了の前提にせず、必須の検証が成立しない場合は未確認の要求と続行できない理由を残す。成果物が外部エラーを誤処理するなどの欠陥は対象内の修正として扱う。

## 原因分析の段階

原因分析は、「作り込み要因（なぜ誤ったコードや記述を成果物に含めたか）」と「見逃し要因（なぜレビュー、テスト、監視などで検出できなかったか）」の2系統に分け、それぞれL1からL4の順序で掘り下げる。
外部の主体には、調査対象の処理の外側で同一の共有状態を変更するローカルCLI、別プロセス、ホスト環境、外部サービスなどが含まれる。
外部の主体が関わっている場合、作り込み要因のL2には、採用した外部挙動の前提と、その前提を裏付けた同バージョン・同条件の一次資料、提供元のIssue、実機での検証結果を記載する。
事前の確認を怠り推測を事実として設計した場合は、その判断自体をL2に記録する。個別のコマンド名や呼び出し順序の違いだけに原因を求めない。
見逃し要因のL2には、実際の利用場面で最初に実行される公開操作、最終的に得られる結果、および既存のテストが実際に検証していた操作と状態遷移を記載する。
テストの名称だけにとらわれず、実際に実行された主体と検証境界に着目して両者の違いを判断する。
見逃し要因の系統は、作り込み要因で特定した欠陥を入れた変更（commit、MR、設定変更、規範の改訂など）を起点にする。
対象にする検出機会は原因の成立に関係する機会に限り、その変更のレビュー、欠陥の挙動を扱うテスト、原因の条件を確かめ得た確認や監視が該当する。
記録から確認できる機会ごとに、見逃した理由をL2以降へ記す。
記録が残らない機会は未確認として区別する。
調査の対象は原因と関係する機会に限る。
同じ変更が欠陥の挙動を期待値とするテストや、その挙動を方針として述べる設計書を含む場合は、それらとの一致を受け入れの根拠にした判断を見逃し要因のL2の候補として調べる。
欠陥を入れた変更が存在しない事象（外部環境の変化だけが原因の場合など）は、その根拠を記して起点の特定を該当なしとできる。
障害注入（フォールトインジェクション）やテストダブル（モック等）を使用した場合は、実際の主体、副作用を起こす主体、発生タイミング、後続の処理をそれぞれ正確に対応づけて整理する。

| 段階 | 作り込み要因で掘り下げること | 見逃し要因で掘り下げること |
| --- | --- | --- |
| L1現象 | 具体的に何を誤って実装したか | 欠陥を入れた変更から観測までの検出機会のうち、原因と関係するどの機会で検出できなかったか |
| L2判断 | なぜその実装でよいと判断したか | なぜ問題であると気づけなかったか |
| L3構造 | なぜその判断のまま実装を進められたか | なぜ誤った結果や機能不全を責務の境界で防げず、検出の仕組みからも修正につなげられなかったか |
| L4システム | なぜそのような構造を許容する規範や設計になっていたか | なぜ検出のために特定の仕組みや属人的な注意が必要だったか |

- L3の作り込み要因には、既存の規範が判断材料や選択肢を過剰に狭めてしまい、本来の目的にかなう判断を阻害していた構造も考慮する。規範の文言どおりに従うこと自体が不適切な結果を生んでいる場合は、ルールを追加する前に、既存ルールの緩和・削除・一般化が可能かを検討する。
- 個人の理解度や注意不足を理由にするとL1〜L2の現象と判断の繰り返しにとどまるため、誤った判断を許した構造的な要因や、検出できなかった仕組みまで掘り下げる。
- 暫定対策を除く抜本的な処置は、原則としていずれかの系統がL3に到達した段階で決定する。L3の構造に直接働きかける処置によって同じ失敗の再発を断ち切れる場合は、L3の分析で完了とし、その根拠を記録する。L3まで掘り下げられない系統がある場合は、確認した資料と掘り下げられない理由を明記し、L3まで到達できた側の系統を根拠として処置を決める。
- 規範、仕様、設定の間で条文どうしが矛盾している事象では、それぞれの条文が追加された変更を調査し、ユーザーの指示によるものかエージェントの判断によるものかを明確にしてからL2とL3を記述する。優先順位は確定した由来に基づいて決定する。単に以前から存在していることだけを優先の根拠にしない。

直接的な原因は、両系統の分析に先立って特定する実行時、データ、設定上のメカニズムである。処理が成立しなかったことが直接の原因である場合は、制御が処理自体に到達しなかったケース（処理の中断・離脱のタイミング、保護機構の内外、確定処理の途中の区間など）と、処理に到達した上で失敗したケース（呼び出し自体は成立したがエラーや不正な戻り値となった場合）を明確に区別して扱う。
根本原因は、最深段階の作り込み要因と見逃し要因を結びつけ、同じ失敗の連鎖を断ち切る条件を一般化した結論としてまとめる。そして、直接的な原因との違いを明確にした上で、原因分析表の最深段に記録する。
両系統の必要な確認を終え、根拠と結論を対応付けてから根本原因を確定する。確認できない事情が実在する場合は、残る確認と続行できない理由を未完了事項として明示する。
観測されたコマンド、ファイル、工程、テスト関数などを別の同種のものに置き換えたときに成り立たなくなる原因は、個別事象の説明にすぎないため、L1または直接的な原因の記述に戻す。
最深段には、「外部の挙動を確認しないまま設計できてしまった構造」や「実際の利用シナリオを検証しないまま完了とみなせてしまった構造」のように、対象が変わっても同じ誤判断を引き起こす汎用的な単位で記述する。
各段階に確定した具体的な内容、仮説、あるいは「該当なし」とその根拠を記録する。仮説や未確認は調査途中の状態として区別し、必要な資料・実装・履歴の確認をすべて終えた場合に限り分析を確定する。上位段の候補は未確定だけを理由に該当なしへ変換せず、仮説に支持する事実と不確実性を残して改善の採否へ接続する。
規範、仕様、設計文書が存在しないことをL3やL4の要因として挙げる前に、`root-cause-analysis.md`「原因分析の品質確認」に沿って確認する。
