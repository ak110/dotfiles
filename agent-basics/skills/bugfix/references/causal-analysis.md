# 因果の確定と原因分析の段階

本書は拡張原因分析へ進む場合と、根本原因の確定に履歴・記録の探索や2系統の分析を用いる場合に、資料の確認順、因果の確定、2系統4段階の分析、直接的原因と根本原因の記録を定める。確定した根本原因から導く類似見直し、処置の階層、再発防止策は`root-cause-analysis.md`が定める。

## 名指し参照の読込方法

本文の各参照の適用条件を保ち、選んだ資料の指定範囲を取得してから、その基準を使う具体的な判断へ進む。起動時の行の資料は起動本文とともに届く。

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 |
| --- | --- | --- | --- |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `root-cause-analysis.md` | 判断 | `read:agent-basics:*/skills/bugfix/references/root-cause-analysis.md` |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `root-cause-analysis.md#「原因分析の品質確認」` | 判断 | `section:agent-basics:*/skills/bugfix/references/root-cause-analysis.md#「原因分析の品質確認」` |

## 拡張原因分析の資料と因果の確定

- 資料は現行の実装・テスト・コメント・文書・設計文書、`git blame`と導入commit・関連レビュー、要求原文・issue・作業要求・当時の計画、それでも動機や見逃しの過程を説明できない場合のセッションログ・会話履歴の順に確かめる。説明できた段階と確認できなかった資料を記録する
- 対立する原因候補を列挙し、反証の有無で棄却できない候補を区別してから因果を確定する。推測した因果チェーンの各段は資料か実機結果で裏付け、候補の不確定性が類似見直しの母集団や処置を変える場合は残る候補の和集合を対象にする
- 探索の記録には、探索先、コマンド、観測時点、結果、確定できる範囲と限界を残す。集計値には観測時点によらず共通の判定条件と母集団の総数を併記する。作成時点を直接示さない指標で判定する場合は、確定できない範囲を明記する
- 取得できない資料は探索先と不足を明記し、当時の判断者の意図は確認済みの資料が示す範囲で述べる
- 直接アクセスできない環境の事象で、コードベース調査と手元の再現では因果を確定できない場合は、計画の起草を止め、調査用コードかログ採取手順を示してユーザーへ採取を依頼する。採取したデータで原因を確定してから再開する
- 責務境界を越える呼び出し、非公開関数の横断利用、重複記録などの回避処理は、同じ機能で正しく動く兄弟処理、設計上の所有責務、導入commitと比べる。局所処理を根本対策と判定できるのは、正しく動く既存処理へ戻す案を棄却する根拠がある場合に限る
- 外部から得た応答の意味は公式の定義と生の応答で確定する。コードの一般的な語義（二値状態をステータスコードで表すAPIでは反転しうる）や、外部ツールの要約・短縮表示から推定しない
- 外部サービスを利用する工程が動かない場合は、自環境の確認を2回以上繰り返す前に提供者の公式ステータス・障害情報を照会する。影響する障害が掲載されていれば自環境の確認の反復を打ち切り、無ければ原因を未確定として両側を調べる（努力目標）

## 原因分析の段階

作り込み要因（なぜ誤りを成果物へ入れたか）と見逃し要因（なぜレビュー、テスト、監視で検出できなかったか）の2系統へ分け、各系統をL1からL4の順に分析する。
外部主体には、調査対象の処理の外で同じ共有状態を変更するローカルCLI、別process、ホスト、サービスを含める。
外部主体が関わる場合、作り込み要因のL2には採用した外部挙動の前提と、その前提を確かめた同版・同条件の一次資料、提供元Issue、実機結果を書く。
確認前の想像を事実として設計した場合は、その判断をL2へ置き、個別のコマンド名や呼出順だけを原因にしない。
見逃し要因のL2には実際の利用場面で最初に実行する公開操作、最終結果、既存テストが実際に通した操作と状態遷移を書く。
テストの名称から独立して、実際に通した主体と境界から両者の差を判定する。
故障注入やテストダブルを使った場合は、実際の主体、副作用の主体、発生時点、後続処理をそれぞれ対応付ける。

| 段階 | 作り込み要因で問うこと | 見逃し要因で問うこと |
| --- | --- | --- |
| L1 現象 | 何を誤って実装したか | どこで検出されなかったか |
| L2 判断 | なぜそれでよいと判断したか | なぜ問題だと判断できなかったか |
| L3 構造 | なぜその判断でも実装できたか | なぜ誤った結果か利用継続不能を責務境界で防げず、検出機構でも是正へ接続できなかったか |
| L4 システム | なぜその構造を許す規範・設計になっているか | なぜ検出に特定の仕組みまたは人を必要としているか |

- L3の作り込み要因には、既存規範が判断材料や結論を過剰に閉じて目的に合う判断を妨げた構造も含める。条文の適用自体が不適切な成果を生む場合は、条文を追加する前に緩和・削除・一般化を調べる
- 個人の理解や注意の程度を述べるだけでは、L1〜L2の現象と判断を繰り返すため、誤った判断を許した構造と検出できなかった仕組みまで調べる
- 対策を除く処置は、原則としていずれかの系統がL3へ到達してから決める。L3の構造へ作用する処置で同じ失敗構造を断てる場合はL3で止め、根拠を記録する。L3へ到達できない系統は確認した資料と理由を記録し、処置の根拠にはL3へ到達した系統を使う
- 規範・仕様・設定の条文どうしが矛盾する事象では、各条文の導入変更を特定してユーザー指示由来かエージェント判断由来かを確定してからL2とL3を書く。優先度は確定した由来で決める（既存であることは判定材料の外に置く）

直接的原因は両系統の前段で確定する実行時・データ・設定上の機構とする。処理の不成立が直接的原因なら、制御が処理へ到達しない場合（取り消し・離脱の時点、保護機構の内外、確定処理の間の区間）と、到達して失敗する場合（呼び出しの成立と失敗を示す終了状態・出力）を分けて扱う。
根本原因は最深段の作り込み要因と見逃し要因を結び、同じ失敗構造を断つ条件を一般化した結論とし、直接的原因との差分を含めて原因分析表の最深段へ記録する。
一方の系統に未確認の因果が残る場合は、根本原因を確認済みの単位だけで書き、両系統を結ぶ因果を未確認として処置の対象へ含める。
観測したコマンド、ファイル、工程またはテスト関数を別の同種対象へ置き換えると成立しない原因は、個別事象の説明としてL1か直接的原因へ戻す。
最深段は外部挙動を確認せず設計できた構造と、実用シナリオを通さず検証済みにできた構造のように対象を替えても同じ誤判断を導く単位で書く。
各段は該当内容か「該当なし」と根拠を記録し、資料不足は「未確認」と探索結果として区別する。
規範・仕様・設計文書の不在をL3、L4へ採る前の確認は`root-cause-analysis.md`「原因分析の品質確認」に従う。
