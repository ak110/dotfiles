# 形式検証

テストは書いた場合だけを確かめ、形式検証は宣言した範囲の全ての場合（モデルの全ての手順の順序、上限までの全ての入力）を確かめる。
本スキルは、検証する箇所と道具を選んで性質を確かめ、次の担当が再実行と追従に使うプロジェクトのスキルを残す手順と、コードの変更後に検証を追従させる手順を定める。
検査が働く証拠には原則6（`agent-basics:writing-standards/references/quality-principles-verification.md`）を適用する。
保証の範囲の言い方には原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）を適用する。
反例の扱いには原則5（`agent-basics:writing-standards/references/quality-principles-deviation.md`）を適用する。
使うかどうかはプロジェクトごとに選ぶ。

## 対象と道具の選び方

- 対象は、コードが守ると約束していることのうち、テストが破れる場合へ届きにくい箇所から、検証しやすさでなく破れた時の害の大きさで1つ選ぶ。
  ユーザーが領域や不具合を挙げた場合はそこから始め、コードと記録から答えられないことだけを尋ねる。
- 道具は問いに答える最も安い手段を選ぶ。
  - 出来事が悪い順序で起きうるか（並行、再試行）: 設計の小さなモデルに対するモデル検査（TLA+など）か、実際のコードを各主体の分割できない1操作ごとに止めて全ての順序を列挙する有界の網羅検査。
  - コード自体が全ての入力で正しく振る舞うか（メモリー安全、桁あふれ、データ構造の不変条件）: コードの上で動く検証器。
    対象の言語で動く検証器が無ければそう書き、手書きのモデルでなく実際のコードを生成した入力で確かめる。
  - 上限では足りず全ての大きさで成り立つ必要がある性質: 証明支援系。
- プロジェクトの開発者が導入して再実行できる道具を優先する。
  導入の費用、再実行の所要、コードを壊した時に検査が失敗するか（手書きのモデルは実際のコードの変更を検出しない）を比べ、選んだ理由を書く。
- 失敗例: 導入済みでない道具を前提にして、次の担当が再実行できない検査を残した。
  失敗例: 手書きのモデルの検査が成功したことを、実際のコードの性質が成り立つ根拠として報告した。

## 作成の手順

1. 本書「対象と道具の選び方」で対象と道具を決める。
2. 性質と、破れた時の害を1文ずつで書く。
   性質は、実装の現在の振る舞いでなく、契約（docstring、仕様、既存の試験、障害の記録）から導く。
3. モデルか検査の枠組みを書く。
   検証の1手順は、コードの分割できない1操作（1回の外部コマンド、1つのロックの区間、1回のアトミックな書込など）に対応させ、名前は対象のコードの語彙を使う。
   順序を入れ替えても結果が変わらない操作（別の資源への操作、読取同士）を1通りだけ調べる削減は、独立と判断した根拠を前提として書く。
4. 実行する。
   反例が出たら、性質とモデルを保ったまま、反例をコードの語彙の操作列で示し、各手順が実際のコードで起こりうるかを確かめる。
   起こらない手順があれば検証の誤りとして直し、全て起こりうれば欠陥として`agent-basics:bugfix`を起動して扱う。
5. 本書「生成するスキル」に従い、プロジェクトのスキルを書く。
6. 生成したスキルに従って次の担当として1回実行し、検査が働くことを確かめる。
   実際のコードを、性質が防ぐ向きに一時的に壊し（確認の削除、手順の入れ替えなど）、検査が失敗することを確かめる。
   壊した変更を戻し、元の結果（成功、または報告する反例だけでの失敗）へ戻ることを確かめる。
   戻す時は、作業ツリーの他の変更を巻き込まない手段（元の本文を保存して書き戻すなど）を使う。
   検査が壊した変更を見逃すか手順が動かなければ、壊した変更でなくスキルか検証を直す。
   モデル単体で特定の検査が恒真になっていないか疑う場合は、そのガードだけを無効にする負の対照で反例を確かめられる。
   モデルの負の対照は実コードを変更した時の失敗確認や、モデルの1手順と実装の原子的な操作の対応を置き換えない。
7. 通常の試験へ入れるかは、所要を`agent-basics:writing-standards/references/testing.md`「速度」の基準と比べて決める。
   重い検査は通常の試験から外し、生成したスキルが示す正規のコマンドで実行する。

## 生成するスキル

- 置き場所はプロジェクトのスキルの置き場所（Claude Codeでは`.claude/skills/<領域の名前>/SKILL.md`）とし、frontmatterに領域の名前と使う時点を書く。
  名前を`verify`や`verify-`で始めない（`agent-basics:verify-skill`が生成する、アプリを操作する手順のスキルの名前である）。
- 本文には`agent-basics:writing-standards/references/testing.md`「状態遷移の性質確認」が挙げる対応（性質と影響、実装のファイル・関数・共有状態、仮定と探索範囲、1手順に当たる原子的な操作、再実行の方法、実装に一致した版の根拠）を書く。
  版の根拠は最後に同期したcommitで書き、検証が新しいcommitのコードを記述すると確かめた後にだけ進めるよう書く。
- 次の担当がスキルだけで次のことをできるようにする。
  変更が検証の対象のコードに触れるかの判定、検査の実行、欠陥と検証の誤りの区別、意図した変更に合わせた検証の更新。
- コマンド、パス、名前はこのリポジトリの実際の値で書き、仮の値は全て置き換える。
- 結果は、性質と害、反例を、検証の言語を知らない読み手が判断できる平易な文で書く。
  有限の生成例による検査（property-based testingなど）は生成した例の範囲の結果として書く。
  モデルや上限付きの検査の成功は、確かめたモデル・上限・前提の内側の結果として書き、実システム全体の保証と区別する。
- TLA+の結果を状態の図や違反までの最短の手順で示す場合は、pstackの`statechart`スキルを名前で指し、その実行基盤とコマンドは複製せず上流を使う。

## 追従の手順

コードが変わって検証が変わらないと、検査は存在しないコードを記述したまま成功し続ける。
形式検証のスキル（モデル検査器、証明系、網羅検査などを、名指ししたコードへ実行するプロジェクトのスキル）の対象のコードが、そのスキルを使わずに変わった後に行う。
編集する対象は検証（モデル、検査の枠組み、性質、そのスキル）に限り、製品のコードの修正は別の作業にする。

1. 検証のスキルを探して読み、検査ごとに性質、対象のコード、上限と前提、コマンド、最後に同期したcommitを集める。
   同期したcommitの記録が無ければ、検証のファイルを最後に変えたcommitを使い、そう報告する。
2. 何も変えずに各検査を1回実行し、結果を記録する。
   この成功は古い記述が成り立つことだけを示し、この失敗がずれか欠陥かは手順5で決める。
3. 同期したcommitから現在までの対象のコードの差分とcommitの説明を読む。
   改名・分割・移動したコードと、検査が守る状態を書く新しいコードも対象に含める。
   各変更を次のどれかに分ける。
   - 影響なし: 検証が記述するものを変えない（整形、コメント、検証の外の処理）。
     commitの説明でなく、モデルや検査の枠組みと照らして決める。
   - 記述のずれ: 1手順が2つに分かれた、分岐や確認が増減・移動した、守る状態を書く処理が増えた、値の範囲が変わった。
   - 意図した約束の変更: 変更の中に根拠（docstring、試験、変更履歴、commitの説明）がある。
   - 約束が破れた疑い: コードが変わり、約束を変えた根拠が無い。
4. 検証は、再実行の結果に合わせるのでなく、コードを読んで直してから再実行する。
   性質を変えるのは意図した約束の変更だけとし、旧と新の文言と根拠を記録する。
   上限は、変更で誤りになった場合だけ変え、下げたら報告する。
5. 再実行して判定する。
   成功なら、新しいコードを性質が防ぐ向きに壊して検査が失敗することを確かめてから戻す。
   失敗なら、反例を実際のコードで1手順ずつ再生し、起こらない手順があれば検証の誤り、全て起こりうれば欠陥として導入したcommitを示して`agent-basics:bugfix`へ渡す。
6. スキルの対象のコード、コマンド、上限、前提、同期したcommitを更新し、スキルに従って1回実行する。
   同期したcommitを進めるのは、実行して現在のコードを記述すると確かめた検査に限る。
   検証の更新は製品の修正と別の変更にする。

検査ごとの結果は、同期済み（変更が記述に影響せず成功）、更新（記述を直して成功）、欠陥（現在のコードが性質を破る）、実行不能（理由を添える）のいずれかとし、更新と欠陥は両方に当たりうる。
更新の前に成功し更新の後に失敗した検査は、古い記述の上の成功だったと報告する。

返す報告に含める項目: 性質と害・道具と理由・上限と前提・結果（反例はコードの語彙の操作列）・壊した変更で失敗した証拠・実行コマンドと所要・対象外の範囲（追従では検査ごとの結果と読んだcommit）。
