# 形式検証

テストは書いた場合だけを確かめ、形式検証は宣言した範囲の全ての場合（モデルの全ての手順の順序、上限までの全ての入力）を確かめる。
性質ベース試験のように生成した例で反例を探す方法は、全ての場合を確かめないため形式検証と区別し、反例探索として手段の比較に含める。
本スキルは、検証する箇所とツールを選んで性質を確かめ、次の担当者が再実行と追従に使うプロジェクトのスキルを残す手順と、コードの変更後に検証を追従させる手順を定める。
検査が働く証拠には原則6（`agent-basics:writing-standards/references/quality-principles-verification.md`）を適用する。
保証の範囲の言い方には原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）を適用する。
反例の扱いには原則5（`agent-basics:writing-standards/references/quality-principles-deviation.md`）を適用する。
使うかどうかはプロジェクトごとに選ぶ。

## 当てるかの判定

変更の計画、実行レビュー、1件の不具合の再発防止では、変更が次のどれかに触れる時に、形式検証（有界の網羅検査、モデル検査、証明）か反例探索（性質ベース試験）を当てるかを判定する。

- 並行する更新、ロック、再試行、状態遷移、永続データの整合、構文解析
- 認可の境界（操作が実際に影響する範囲が、認可を確かめた範囲を超えないこと）、ループと再帰の停止性
- 既存の結果を保つはずの書き換え（性能改善、リファクタリング）、固定幅整数・ビット演算・境界値の計算

判定は、破れた時の害、通常のテストで届くか、検査の作成と再実行の費用で比べ、結論と理由を`形式検証の判定: <当てる|当てない>（理由）`の1行で計画（計画を作らない時は作業項目の処理記録）へ残す。
対象コードを検証する既存のスキルがあれば、その再実行と本書「追従の手順」を検証に含める。
既存のスキルは、frontmatterの`verifies`（下記「生成するスキル」）に対象のパスを持つものと、`verifies`を持たず説明か本文が対象のコードを名指しするものの両方を探す。
当てると判定したら本書「作成の手順」へ進む。

## 対象と道具の選び方

- 対象は、コードが守ると約束していることのうち、通常のテストでは契約違反を検出しにくい箇所から、検証しやすさでなく破れた時の害の大きさで1つ選ぶ。
  ユーザーが領域や不具合を挙げた場合はそこから始め、コードと記録から答えられないことだけを尋ねる。
- 対象の例: 並行と再試行の順序、状態遷移、構文解析に加え、認可の境界（他のユーザーのデータへの影響、参照先の対象の読取権限を含む）と、ループと再帰の停止性（反復の上限）。
  最適化・リファクタリングの等価性（変更前の実装か素朴な実装を仕様にし、全ての入力か有界の範囲で新しい実装と一致すること）と、固定幅整数の桁あふれ・符号・シフト・ビット演算・境界値も対象にする。
- ツールは問いに答える最も低コストな手段を選ぶ。
  - 出来事が悪い順序で起きうるか（並行、再試行）: 設計の小さなモデルに対するモデル検査（TLA+、Quintなど）か、実際のコードを各主体の不可分な1操作ごとに止めて全ての順序を列挙する有界の網羅検査。
    [Quint](https://quint.sh/docs/getting-started)はnpm・Homebrew・Nixで導入できる。
    `quint run`は乱択シミュレーションであり、反例が見つからなくても網羅したとはいえない。
    `quint verify`はJDK 17以上が必要で、バックエンドを指定しない場合はApalacheが指定手順数まで（未指定なら10手順）を、`--backend tlc`はモデルの有限な到達可能状態を網羅する。
  - コード自体が全ての入力で正しく振る舞うか（メモリー安全、桁あふれ、データ構造の不変条件）: コードの上で動く検証器。
    対象の言語で動く検証器が無ければそう書き、手書きのモデルでなく実際のコードを生成した入力で確かめる。
  - 固定幅の整数とビット演算: 反例を返す決定手続き（Lean 4の`bv_decide`など）か、小さな幅での全ての入力の列挙。
  - 上限では足りず全ての大きさで成り立つ必要がある性質: 証明支援系。
    証明に入る前に、決定手続き、小さな範囲の全列挙、性質ベース試験で反例を探し、探した範囲（上限、生成した例の数）と未発見の結果を記録する。
    反例が見つからないことは、調べた範囲での未発見であり、証明ではない。
- 比べる仕様は、実装と別の書き方（より素朴な手順、広い型での計算、全ての場合の列挙）で書く。
  同じ書き方の二重実装は同じ誤りを複製する。
- 手書きのモデルでは、モデルの言語と対象の言語・ビルド設定の意味の差（固定幅の桁あふれがwrapかpanicか、シフト量が幅以上の時、符号付き除算の丸め、無限精度の整数など）を対応させ、前提へ書く。
- プロジェクトの開発者が導入して再実行できるツールを優先する。
  導入コスト、再実行の所要時間、コードを壊した時に検査が失敗するか（手書きのモデルは実際のコードの変更を検出しない）を比べ、選んだ理由を書く。
- 失敗例: 導入済みでないツールを前提にして、次の担当者が再実行できない検査を残した。
  失敗例: 手書きのモデルの検査が成功したことを、実際のコードの性質が成り立つ根拠として報告した。

## 作成の手順

1. 本書「対象と道具の選び方」で対象とツールを決める。
2. 性質と、破れた時の害を1文ずつで書く。
   性質は、実装の現在の振る舞いでなく、契約（docstring、仕様、既存のテスト、障害の記録）から導く。
   書いた性質は、モデル・証明・検査を作る担当と別の担当（レビュー担当かユーザー）が契約と照らして確かめてから、検査を作る。
   誤った性質に正しい証明が付くと、検査の成功が欠陥を隠すためである。
   ユーザーへ回すのは、契約から決まらず本人の意図にしか根拠が無い場合に限る。
   性質に前提（仮定）を置いたら、呼出し側がそれを保証するか（型、表明、呼出し元のコード）を別に確かめる。
3. モデルか検査の枠組みを書く。
   検証の1手順は、コードの不可分な1操作（1回の外部コマンド、1つのロック区間、1回のアトミックな書き込みなど）に対応させ、名前は対象のコードの語彙を使う。
   順序を入れ替えても結果が変わらない操作（別の資源への操作、読み取り同士）を1通りだけ調べる削減は、独立と判断した根拠を前提として書く。
   永続化するデータの形式も検証対象なら、モデルの状態をその形式で持ち、導出した値に不変条件を置く。
   たとえばイベント列を保存するなら、残高をイベント列から導き、残高が非負であることに加え、付与や消費の操作結果と導出後の残高が一致することを確かめる。
   非負だけでは、付与のイベントを記録し忘れても検出できない。
   モデル単体の成功を実装の検証とせず、実装の検証には手順6を行う。
4. 実行する。
   反例が出たら、性質とモデルを保ったまま、反例をコードの語彙の操作列で示し、各手順が実際のコードで起こりうるかを確かめる。
   起こらない手順があれば検証の誤りとして直し、全て起こりうれば欠陥として`agent-basics:bugfix`を起動して扱う。
   深刻度は、反例の入力が実際の呼出しで到達できるかを確かめてから決める。
   証明できず反例も出ない場合は、性質を弱めず、仮定や公理を足さずに、実際のコードで性質を破る入力や実行を探す。
   見つかれば欠陥として`agent-basics:bugfix`へ渡し、見つからなければ証明の未完として報告する。
   証明支援系を使った場合は、最終の性質・定理の文面が手順2で確かめた文面と一致すること、未証明の穴（Leanの`sorry`、Coqの`admit`、追加した公理・仮定）が残っていないことを、道具の機能（Leanなら`#print axioms`）で確かめる。
   結果は「反例あり」「調べた範囲で未発見」「証明済み（前提付き）」「未決（妨げたもの）」を区別して書く。
   「調べた範囲で未発見」には、全列挙した範囲（上限）か、生成した例の数と生成の方法を添え、両者を同じ保証として書かない。
5. 本書「生成するスキル」に従い、プロジェクトのスキルを書く。
6. 生成したスキルに従って次の担当者として1回実行し、検査が働くことを確かめる。
   実際のコードを、性質が防ぐ向きに一時的に壊し（確認の削除、手順の入れ替えなど）、検査が失敗することを確かめる。
   壊した変更を戻し、元の結果（成功、または報告する反例だけでの失敗）へ戻ることを確かめる。
   戻す時は、作業ツリーの他の変更を巻き込まない手段（元の本文を保存して書き戻すなど）を使う。
   検査が壊した変更を見逃すか手順が動かなければ、壊した変更でなくスキルか検証を直す。
   モデル単体で特定の検査が恒真になっていないか疑う場合は、そのガードだけを無効にする負の対照で反例を確かめられる。
   モデルの負の対照は実コードを変更した時の失敗確認や、モデルの1手順と実装の原子的な操作の対応を置き換えない。
7. 通常のテストへ入れるかは、所要時間を`agent-basics:writing-standards/references/testing.md`「速度」の基準と比べて決める。
   重い検査は通常のテストから外し、生成したスキルが示す正規のコマンドで実行する。

## 生成するスキル

- 置き場所はプロジェクトのスキルの置き場所（Claude Codeでは`.claude/skills/<領域の名前>/SKILL.md`）とし、frontmatterに領域の名前と使う時点を書く。
  名前を`verify`や`verify-`で始めない（`agent-basics:verify-skill`が生成する、アプリを操作する手順のスキルの名前である）。
- 本文には`agent-basics:writing-standards/references/testing.md`「状態遷移の性質確認」が挙げる対応（性質と影響、実装のファイル・関数・共有状態、仮定と探索範囲、1手順に当たる原子的な操作、再実行の方法、実装に一致した版の根拠）を書く。
- 版の根拠は、検証が現在のコードを記述すると確かめた後にだけ進め、次のどちらかで記録する。
  - プロジェクトがpyfltrの形式検証の記録の検査（`verifies`と`verified-digest`の2キー）を使う場合は、frontmatterへ`verifies`（検証が対象とするファイルのリポジトリ相対パスかglobの配列）を書く。
    検証を実行して性質を確かめた後に、`pyfltr verification-sync --update <スキルのパス>`で`verified-digest`を書く。
    本文には同期したcommitを書かない。
    キーの意味と要約値の計算はpyfltrのユーザー向け文書が定める。
  - それ以外は、本文へ最後に同期したcommitを書く。
- 次の担当者がスキルだけで次のことをできるようにする。
  変更が検証の対象コードに触れるかの判定、検査の実行、欠陥と検証の誤りの区別、意図した変更に合わせた検証の更新。
- コマンド、パス、名前はこのリポジトリの実際の値で書き、仮の値は全て置き換える。
- 結果は、性質と害、反例を、検証の言語を知らない読み手が判断できる平易な文で書く。
  有限の生成例による検査（property-based testingなど）は生成した例の範囲の結果として書く。
  モデルや上限付きの検査の成功は、確かめたモデル・上限・前提の内側の結果として書き、実システム全体の保証と区別する。
- TLA+の結果を状態の図や違反までの最短手順で示す場合は、pstackの`statechart`スキルを名前で指し、その実行基盤とコマンドは複製せず上流を使う。

## 追従の手順

コードが変わって検証が変わらないと、検査は存在しないコードを記述したまま成功し続ける。
形式検証のスキル（モデル検査器、証明系、網羅検査などを、名指ししたコードへ実行するプロジェクトのスキル）の対象コードが、そのスキルを使わずに変わった後に行う。
編集する対象は検証（モデル、検査の枠組み、性質、そのスキル）に限り、製品コードの修正は別の作業にする。

1. 検証のスキルを探して読み、検査ごとに性質、対象のコード、上限と前提、コマンド、版の記録（`verified-digest`か最後に同期したcommit）を集める。
   `verified-digest`を持つスキルは、その値を最後に書いたcommitを同期したcommitとして扱う。
   どちらの記録も無ければ、検証のファイルを最後に変えたcommitを使い、そう報告する。
2. 何も変えずに各検査を1回実行し、結果を記録する。
   この成功は古い記述が成り立つことだけを示し、この失敗がずれか欠陥かは手順5で決める。
3. 同期したcommitから現在までの対象コードの差分とcommitの説明を読む。
   改名・分割・移動したコードと、検査が守る状態を書く新しいコードも対象に含める。
   各変更を次のどれかに分ける。
   - 影響なし: 検証が記述するものを変えない（整形、コメント、検証外の処理）。
     commitの説明でなく、モデルや検査の枠組みと照らして決める。
   - 記述のずれ: 1手順が2つに分かれた、分岐や確認が増減・移動した、守る状態を書く処理が増えた、値の範囲が変わった。
   - 意図した約束の変更: 変更の中に根拠（docstring、テスト、変更履歴、commitの説明）がある。
   - 約束が破れた疑い: コードが変わり、約束を変えた根拠が無い。
4. 検証は、再実行の結果に合わせるのでなく、コードを読んで直してから再実行する。
   性質を変えるのは意図した約束の変更だけとし、旧と新の文言と根拠を記録する。
   上限は、変更で誤りになった場合だけ変え、下げたら報告する。
5. 再実行して判定する。
   成功なら、新しいコードを性質が防ぐ向きに壊して検査が失敗することを確かめてから戻す。
   失敗なら、反例を実際のコードで1手順ずつ再生し、起こらない手順があれば検証の誤り、全て起こりうれば欠陥として導入したcommitを示して`agent-basics:bugfix`へ渡す。
6. スキルの対象コード、コマンド、上限、前提を更新し、スキルに従って1回実行する。
   版の記録（`verified-digest`か同期したcommit）を進めるのは、実行して現在のコードを記述すると確かめた検査に限る。
   検証の更新は製品コードの修正と別の変更にする。

検査ごとの結果は、同期済み（変更が記述に影響せず成功）、更新（記述を直して成功）、欠陥（現在のコードが性質を破る）、実行不能（理由を添える）のいずれかとし、更新と欠陥は両方に当たりうる。
更新の前に成功し更新の後に失敗した検査は、古い記述の上の成功だったと報告する。

返す報告に含める項目: 性質と害・ツールと理由・上限と前提・結果（反例はコードの語彙の操作列）・壊した変更で失敗した証拠・実行コマンドと所要時間・対象外の範囲（追従では検査ごとの結果と読んだcommit）。
