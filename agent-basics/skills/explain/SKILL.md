# 説明

仕組み、経緯、理解のための説明を求める依頼に、読取だけで答える。
回答が成果物であり、説明だけを求める依頼を、実装や不具合対応へ広げない。
事実と推論の区別は原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）を適用する。
説明の組み立ては原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）を適用する。

## 手順

1. 対象と問いを定める。
   問いが仕組み、経緯、理解のどれに当たるかを決める（複数でもよい）。
   対象が曖昧な時は、会話の文脈から解釈を1文で示して進める。
2. 仕組みを問われたら、コードを読み、呼び出しの起点から実行の流れと状態の置き場所を追跡する。
   1つのモジュールで閉じる問いは自分で読み、複数のファイルやサービスにまたがる問いは2〜4個の観点に分けて調べる。
3. 経緯を問われたら、記録から答える。
   変更の履歴は`git blame -L <開始>,<終了> -- <ファイル>`、`git log --follow -p -- <ファイル>`、`git log -1 --format=%B <commit>`で読む。
   PRの本文と議論、作業項目、設計の文書も当たる。
   最新のcommitだけを根拠にせず、今の形に至った以前の決定までさかのぼる。
   人の決定の範囲が問題になる時は、発言者の原文と所在を示し、要約や解釈と分ける。
   記録に無い意図は、確かめた事実として書かず、推論か仮説と明示する。
4. 理解のための説明を求められたら、相手が聞く目的（変更の前、レビュー、調査、新しく担当する）から、持ち帰る要点を数個に限定する。
   目の前の事例から始めるか、全体像が先に要るかは読み手の知識で決める。
   3つ以上の構成要素がある流れを図にする時は、構成要素を1つずつ足して描き直す。
5. 回答を書く。
   仕組みの説明では、主要な概念、動作、所在、注意点のうち読み手に要るものを書く。
   説明の順序と語の補い方は`agent-basics:writing-standards/references/writing-genres.md`「手順と技術の説明」に従う。
   経緯は、記録で確かめた事実、記録から導いた推論、競合する仮説、分からないこと、調べた出所に分ける。
   調べた出所には、探して何も見つからなかった出所も含める。
   案の選択の相談なら、推奨と、案ごとの得失の比較表で答える。
6. 説明の途中で変更が要ると分かった時は、変更を始めず、回答で示して依頼者の判断へ返す。

## 回答

問いの種類ごとの説明本文、経緯では調べた出所（見つからなかった出所を含む）、変更が要ると分かった点を含める。
