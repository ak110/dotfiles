# 文書の役割と種類

文書を作る時と、情報をどの文書へ書き分けるかを決める時に、読者と役割から文書の種類を選ぶ。
原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）の適用である。
情報をどの文書へ書き分けるかは、`agent-basics:writing-standards/references/writing.md`「文章の共通規定」の「情報を追加する前の判断」で決める。

## 文書ごとの読者と内容

後から読む読者へ何を伝えるかを決めて、参照用、作業用、経緯の記録から用途を選び、ファイル名だけで用途を決める判断を避ける。
参照用には現在の仕様と使い方を、作業用には作業中のタスクと進捗を、経緯の記録には後から当時の判断を検証できる事実を残す。
次の表は文書の種類を選ぶ目安である。

| 文書 | 主な読者と役割 | 伝える内容 |
| --- | --- | --- |
| README | エンドユーザーと開発者が使い始めるための参照用 | 対象読者、できること、導入の前提、主要な操作、詳細な資料への案内 |
| 利用ガイド・運用手順 | エンドユーザーと開発者が操作を確かめるための参照用 | 主要な操作の前提、手順、期待される結果、前提が合わない時の対応。内部仕様とエージェント向けの指示は除く |
| 構成の説明 | 開発者と保守担当者が全体の構造を把握するための参照用 | ディレクトリ配置、各コンポーネントの責務と境界、配布先、主要な連携と実装の対応 |
| 設計の記録（ADRを含む） | 開発者と保守担当者が過去の設計判断の理由を確かめるための参照用 | 制約、構造、選定理由、見送った代替案と影響。資料が分かれる時は目次を置く |
| 技術文書 | 技術の使い方や仕組みを理解し、手元で再現する読者向けの参照用 | 入力、コマンド、設定値と結果 |
| エージェント向け文書 | コーディングエージェントが作業方針を判断するための参照用 | 想定する読み手、適用する時点、判断基準、次の操作 |
| 方針の由来の記録 | 開発者とエージェントが過去の決定の経緯を調べるための記録 | 決定、当時の背景、その判断を適用している現在の規範 |
| 障害の記録 | 開発者とエージェントが再発防止に使う記録 | 観測した事象、直接の原因、対策、発生条件 |
| 検証記録 | 開発者とエージェントが過去の技術判断を再検証するための記録 | 観測時の前提、結果、再検証の手順、結果を前提にした判断 |
| 計画ファイル | 実行担当者が変更を進めるための作業用 | 要件、変更内容、検証手順、完了条件と進捗の対応 |
| コミットメッセージ | 開発者が変更の目的を履歴から追跡するための記録 | 何をなぜ変えたかを、件名と必要な本文で示す |
| 業務・仕様文書 | 読者が意思決定や行動に移るための連絡・参照用 | 決める主体、条件と結果、採否の基準 |
| PR・MRの説明 | レビュアーと関係者へレビューを依頼する連絡 | 変更の目的、得られる結果や挙動の変化、確認済みの検証範囲 |
| Releaseの本文 | エンドユーザーと開発者へ配布した変更を伝える記録 | エンドユーザーに届く機能変更と修正、必要な操作と注意 |
| 体験を述べる文章 | 本人の体験や感想を読者へ伝える文章 | 本人が経験した状況、印象、感想、得た知見 |

## 設計の記録

長期の設計の記録を新設・追記するかは、後から変える費用、前提を知らない保守担当者が選択の理由を要するか、有力な代替案との実質的なトレードオフの3軸で選び、ADRは3軸がそろう時を目安に提案する。
変えやすく理由がコードから分かる日常の判断は、計画や作業項目、現行仕様を表すコードと参照文書、コミット履歴へ用途に応じて残し、同じ詳細を複数箇所へ写す代わりに記録先を参照する。
プロジェクト固有の記録の義務と、必要な認可・監査の記録を優先し、この選別を計画や作業項目の要求、認可、検証の証拠を省く条件に使わない。

設計の記録は、時間が経ってから記録だけを読む開発者と保守担当者が、判断の要旨と理由を理解できるように書く。

- 判断が要った実際の背景と制約、決定と理由、検討した代替案、正負の影響、適用範囲を対応付ける
- 決定済みと未決の事項、確かめた事実と推論を区別する
- 長く残る判断と理由を中心にし、変わっていく進捗と分担は計画や作業項目へ、判断を変えない実装の詳細は仕様、コード、PRの説明へ書き分ける。
  具体的な技術の選択自体が決定である場合は、その理解に要る具体性を残す
- 根拠は要約して出所への参照を添え、関連する判断と置き換えた判断を追跡できる参照を残す

ADRを書く場合は、利用先のプロジェクトの既存の形式を優先し、次も満たす。

- 背景、決定、状態、影響を、見出しか項目で判別できるようにする
- 提案中と採用済みを状態で区別し、廃止や置き換えでは関連する記録と一覧をそろえ、当時の判断と後続の判断を区別して残す
