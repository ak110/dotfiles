# 文章チェックと診断

文章チェックに対処する担当が診断と原文の意図を照らし、読み手に意味を保った読みやすい文章を届ける。
文章チェック（textlint、markdownlint、口語表現チェック、ダッシュ記号チェック、typos）の対象、実行、診断への対応と、文の書き直しを委ねる時の検収を定める。
チェックで守れる規則をチェックに任せる（原則9、`agent-basics:writing-standards/references/quality-principles-subtraction.md`）。
意味が保たれたかは作った者と別の担当が確かめる（原則6、`agent-basics:writing-standards/references/quality-principles-verification.md`）。
チェックを導入した環境では規則の判定と直し方を診断に従い、本書には規則の要旨と、診断が直し方を示さない規則の読み方を置く。

## チェックの対象範囲

- 計画ファイルは、文章lint、口語表現チェック、ダッシュ記号チェックの必須の対象から外す（読み手はその計画を実行するエージェントに限られ、表記の統一が作業の特定と完了の判定に影響しないため）。
- 後続の作業へ要求を渡す作業項目の本文は、意味を変えない推敲と表記のチェックの対象から外す。
  意味の正確さ、必要事項、原文と認可、対象・条件・完成判定の確認は保ち、最終成果物へ転記する文面には転記先の基準とチェックを当てる。
- エージェント向け文書の用例は、正しい表現とその表現が成り立つ条件を説明する文で書き、通常のチェックの対象にする。
  検出用のテストデータ、内部の保存形式の識別子、他者の逐語引用は、自作の用例と区別して原文のまま保つ。
- チェッカーを持たない環境では、完成時に本書「チェッカーが扱う規則」を自分で確かめ、チェックを実行できない状態を合格とみなさない。
- 引用の正確さ、識別子の保持、文章の意味の整合はチェッカーでは保証されないため、各担当が読んで確かめる。

### 逐語引用の検出範囲

逐語引用の書式は`agent-basics:writing-standards/references/writing-genres.md`「ユーザー入力素材の取扱い」が定め、各チェッカーの検出範囲は次のとおりである。

| チェック項目 | 引用ブロック（`>`）の内側 | フェンス付きコードブロックの内側 |
| --- | --- | --- |
| 口語表現チェック | 対象外 | 対象外 |
| textlint | 検出対象 | 対象外 |
| ダッシュチェック | 検出対象 | 対象外 |

## 文章チェックの一括実行

pyfltrと表記のチェッカーを導入したプロジェクトでは、次の手順で実行し、未導入ならプロジェクトの検証手順に従う。

1. 本書「チェックの対象範囲」と「逐語引用の検出範囲」で対象を選ぶ（拡張子は`.md`、`.py`、`.txt`、`.yaml`、`.yml`、`.toml`で、コードのコメント行を含む）。
2. 恒久的な成果物には、現在のホストが公開するserver key `pyfltr`の`run`を、下の引数で呼ぶ（完全修飾名はClaude CodeとCodexで異なる）。
   同じ設定の対象は1回の`run`にまとめる。
3. MCPの`run`が使えなければ、導入済みのpyfltrの`--help`で起動形を確かめ、下のCLIの形で同じ対象とオプションを渡す（外部のファイルには`--allow-external-paths`を付ける）。
4. `completion`が`completed`、`files_reached`が指定したファイル数、指定した全コマンドが`completed_commands`に含まれることを確かめる。
   `incomplete_commands`、`missing_targets`、`fully_excluded_files`が空であることも確かめ、CLIではJSONLの最終行の`summary`で同じ条件を見る。
   `incomplete`と`not_reached`は未完了とし、この3項目と`skipped_reason`、`warnings`から原因を調べる。
5. 完了を確かめた後に警告とエラーの件数を確かめ、詳細が要れば`run_id`をMCPの`show_run_diagnostics`へ渡す。
6. 本書「textlint指摘への修正方針」に従って診断へ対応し、警告を消すためだけに情報を減らす書き換えをしない。
   他者の原文（記事や発表の題、引用した発言、固有名詞など）の警告語句は保ち、残した箇所と理由を完了報告に書く。

`run`の引数は次のとおりである。

- `paths`: 対象の全ファイルの絶対パス（重複を除く）、`work_dir`: チェックの設定を持つプロジェクトの絶対パス
- `commands`: Markdownを含めば`["textlint", "colloquial-check"]`、他の対応拡張子だけなら`["colloquial-check"]`とし、登録されたダッシュ記号チェックなども加える
- `enable`は`["colloquial-check"]`、`no_exclude`と`no_fix`はともに`true`
- `allow_external_paths`: `work_dir`のプロジェクトの外のファイルを含む時だけ`true`

```sh
<pyfltrの起動形> run --commands=<全対象へ到達するコマンドの和集合> --enable=colloquial-check --no-exclude --no-fix --output-format=jsonl --work-dir <チェックの設定を持つプロジェクトの絶対パス> <対象ファイルの絶対パス...>
```

## textlint指摘への修正方針

- 診断の原因が明らかで、`agent-basics:bugfix`「書き出す場面」に当たらない時は、そのまま直す。
  原因を説明できない時、期待の側を変える時、同じ診断が2回目の時は同スキルを起動し、同じセッションで起動済みなら取得済みの同じ版の本文を再利用する。
- 1対1の表記変更と、限られた候補から選べる反復表現は`agent-basics:writing-standards/references/notation-rules.md`「表記の一括置換」の手順で候補を試し、変えた文を全てレビューする。
- それ以外の指摘では語句だけを置き換えず、文全体を自然な日本語へ組み立て直す（コメント、docstring、表示メッセージ、プロンプトへ注入する文を含む）。
- `textlint --fix`の自動修正が多くの箇所に及んだら、修正後の差分をレビューする。
- `.textlintrc.yaml`の`allows`へ登録するのは、緩和が妥当と判断した語に限る（判断は`agent-basics:writing-standards/references/implementation-time.md`「緩和判断のフレーム」）。
- 書き直しで意味や契約が変わる場合は`agent-basics:writing-standards/references/quality-principles-roles.md`「要件と認可」に従い、指摘の多さや難しさを理由に対応の範囲を狭めない。

### 典型パターン

抽象的な動詞や名詞の指摘（`no-ai-words`、口語表現チェック）は、診断が直し方を示さない。
その語が担っていた動作や関係を動詞で書き、基準の資料の内容、確かめる相手、実行する操作、比べる値を文脈から補う。
例「資料Xが判定条件を定める。入力Aが値Bと一致するか確かめる」は、定める内容と比べる対象の関係を文で示す。
例「公開された呼び出し手段（コマンド、画面、API、hookなど）を使う」は、上位概念と開いた例示で範囲を保つ。
`no-short-topic-comma`（短い主題の直後の読点）は、インラインコードで始まる主題も含めて、読点を外すか文を組み替える。
口語表現チェックが和語の動詞を漢語へ置き換える候補（「作る」を「作成する」）を示しても、文脈で対象と動作が明確なら和語のまま残し、辞書に無い不自然な表現はレビュー担当が文脈から判断する。

## 文の書き直しの委譲と検収

成果物の種類、読者、事実関係、根拠、反映先が確定した文章の作成を委ねる時も、次の基準で受け取る。

- 依頼文には読者の種別（人間向けかエージェント向けか）、対象ファイルと段落、指摘の規則名と語句、保つ事実と契約、本書「textlint指摘への修正方針」の禁止事項を書き、読者が異なる文書は依頼を分ける。
- 返った文を原文と比べ、事実と契約が保たれているかを確かめる（意味の比較は`agent-basics:writing-standards/references/writing-genres.md`「ユーザー入力素材の取扱い」）。
- 主体を補う時は、原文、依頼、資料に根拠のある担当、通知先、責任を保ち、既存の人物へ作業を割り当て直していないかも確かめる。
- textlintと導入済みの表記のチェッカーを実行し、変更箇所を`git diff --word-diff=plain --word-diff-regex=.`で文字単位に比べる。
  語句の置換で意味や自然さを保てなければ、述語や文の構造まで見直す。
- 見出しの指摘語を直したら、その節名を指す全ての文書とコードを同時に直し、定義済みの用語は定義と使用箇所の表記をそろえる。
  指摘語そのものをデータとして扱う箇所は変えず、インラインコードで書く。
- 書き直しの後、インラインコード、見出し、コードブロックの内容が変わっていないかを機械的に比べ、意味と契約は別の担当が差分で確かめる。

## チェッカーが扱う規則

次の規則は括弧内のチェッカーが判定し、導入した環境では診断に従い、無い環境では完成時に自分で確かめる。

- 和文と半角文字（英数字、記号、インラインコード）の間に空白を入れない（JTF 3.1.1）。
- 完全一致の検索を前提とするコードの文字列（ログ、エラーメッセージ、CLIのヘルプ）は、JTF 3.1.1の自動修正で空白が消えるため、`text`か言語名を付けたコードブロックで引く。
- 和文と半角文字が隣り合う節名はバッククォートで囲んで参照する（かぎ括弧ではJTF 3.1.1の自動修正が空白を消し、節名を比べる自動チェックで一致しなくなる）。
- 和文でハイフン`-`を使わず、接頭辞や識別子はインラインコードにする（JTF 4.2.6）。
- 本文の山括弧`<>`は対応させ、プレースホルダーはインラインコードに入れる（JTF 4.3.7）。
- 1文は150文字以内にし（`sentence-length`の`max: 150`）、バッククォート付きの識別子を多く並べる時は表か「`<定数名>`などを典拠とする」形にする。
- 1文の読点は5個までにする（`max-ten`の`max: 5`は6個以上で報告する）。
- 連続する文の間でも同じ接続詞を続けない（`no-doubled-conjunction`は連続する文の間も検出する）。
- `1.1.3.箇条書き`で`shouldUsePoint: false`とした環境では、箇条書きの末尾に句点を付けない（`preset-jtf-style`）。
- 番号付きリストの1項目に空行を入れて入れ子の箇条や段落を加えると、`1.1.3.箇条書き`がリスト全体を句点の統一の対象にするため、入れ子の内容は独立した節へ移す。
- 冗長表現（`ja-no-redundant-expression`）は`agent-basics:writing-standards/references/tone-examples.md`「冗長表現」の書き方で直す。
- 外側のフェンスを4つのバッククォートにするとtextlintが内側を地の文として扱うため、外側は通常3つにし、内側に3つのバッククォートを含む時だけ4つにする。
- 英字の分類を全角括弧で書かず（`ja-unnatural-alphabet`）、番号付きリストか分類の意味を表す名前を使う。
- 箇条書きの記号の内側に番号を書かず、番号付きリストを使う（markdownlint-cli2の自動正規化で判別しにくくなるため）。
- 同じ階層の見出しは区別する語を添えて一意にする（markdownlint `MD024`）。
- 地の文のダッシュ記号（emダッシュ、horizontal bar、2倍ダッシュ）はダッシュ記号チェックが検出し、コードブロック、インラインコード、URLは対象外である。

## typosの誤検出への対処

typosは`text`コードブロックの中もチェックするため、固有名詞や末尾を省いたファイル名で誤検出しやすい。
対処はチェックの緩和に当たるため、`agent-basics:writing-standards/references/implementation-time.md`「緩和判断のフレーム」に従う。

- 固有名詞や意味のある語は除外語へ登録する（`pyproject.toml`の`[tool.typos.default.extend-words]`、`.typos.toml`では`[default.extend-words]`）。
- 変更や破棄を前提とする識別子（自動生成の名前、テスト用のダミー値など）は`XXX`などへ置き換え、元の意図を注釈で書く。
