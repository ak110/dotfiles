# スキルの実装

本書は、Agent Skillsのスキル（`SKILL.md`、frontmatter、`references/`）を作る時と改める時の基準である。
エージェントの種類を問わない部分を扱い、Claude Codeに固有の事項は節名か項目に明記する。
主に原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）の適用である。

## YAML frontmatter

- 手順を書いたスキル（本文が順序だった作業を中心とする）の名前は動詞で始め、判断基準・契約・規約集を提供するスキルの名前は対象を表す語にする。
- `name`（ディレクトリ名と一致させる）は、担当する工程や起動のきっかけを表す語にし、実現手段（記録形式、ツール名、コマンド名など）や内部の専門用語を避ける（努力目標）。
  エージェントは名前を起動判断の手掛かりにするため、手段名を中心にすると、別の手段で同じ工程を行う時に起動されず、手段名が出ただけの文脈で誤って起動される。
- `description`には対象の作業と起動条件だけを書き、目的・背景・手順は本文に書く（努力目標。`description`は常時読み込まれるため）。
  複数行にわたる場合はYAMLの折り畳みスカラー（`>`）を使う。
- 他のスキルやエージェントから明示的に呼ばれる前提のスキルと、ユーザーが`/name`で明示的に起動する前提のスキルは、`description`に呼び出し元と起動条件だけを短く書く。
  渡された引数だけを入力とするスキル（`context: fork`を持つものなど）は、受け付ける引数と返す結果の仕様を`description`に書く。
- 起動方法に合わせて次のように設定する。
  - ユーザーが`/name`で起動しない場合は、`user-invocable: false`にする。
  - ユーザーの手動起動に限る場合（副作用の大きいワークフローなど）は、`disable-model-invocation: true`にする（Claude Code固有）。
  - エージェントとユーザーの双方が起動する場合は、どちらも設定しない。
- Codex向けの`agents/openai.yaml`を置くスキルは、`interface.display_name`をディレクトリ名と一致させる（Codexの入力補完が候補名として表示するため、違うとスキル名を入力しても候補から外れる）。
- ユーザーが`/name`で起動できるスキルが、動作を切り替える決まった語を引数に取る場合は、その語を`argument-hint`へ書く。
  自由記述だけを受け取るスキルでは省き、決まった語に続く自由記述も受け取る場合はその枠を併記する。
  省略できる引数は角括弧、択一は`|`で示し、角括弧で始まる値はYAMLの文字列として引用符で囲む。
- frontmatterで設定した仕様は、`description`や本文での再掲を避ける（努力目標）。
  `argument-hint`は人間向けの入力補完であり、エージェントが引数を選ぶための`description`の説明は保つ。

## ユーザーが起動するスキルの着手手順

`user-invocable: false`を設定していないスキルは、起動から作業の開始までにユーザーの追加操作を求めない構成で書く。
確認、選択肢の提示、追加入力の要求は、作業に着手した後の、実際に必要になった時点に置く。
ユーザーはそのスキルを作業の起点として起動するため、着手前に追加操作を求めると作業の開始を妨げる。

## SKILL.md本体とreferences/の役割分担

仕事の開始時に同じ担当が必ず使う短い判断は、その仕事を選んだ入口に置くか、入口から一意に取得できる形にする。
既存の名指しの作業・役割が入口なら、全作業の索引を再選択させない。
途中で条件が成立した時だけ使う詳細は参照に残す。
読込表では必要になる判断と直前の操作を示し、条件不成立・同じ版の取得済み・複数条件に当たる場合を区別する。
役割が確定した起動の配送は、その役割の最初の判断に使う資料だけに限る。

- 付属資料は`skills/<skill-name>/references/`に置き、特定のスキルに属さない参照文書は別名のディレクトリに置く（努力目標。どのスキルの資料かを判別しやすくするため）。
- `SKILL.md`本体には全ての対象に共通する原則と、`references/`の本文を選ぶ索引を置き、言語やトピックに固有の細則は`references/`に置く。
- トリガー条件、中心の手順、停止条件などの必須の指示は、記述量の削減を求められた場合も本体の冒頭に残す（本体の後半は、起動を判定する時点で未読のことが多い）。
- 規範の記述場所を探す時は、本体と`references/`の双方を確かめる。

## 呼び出し側プロンプトの責務分離

スキルの詳細な動作、条件分岐、引数を省いた時の動作と対象の選び方、引数の仕様は`SKILL.md`本体に集める。
呼び出し側のプロンプトには、起動の指示と、その呼び出しに固有の値を渡す引数だけを書く。
呼び出し側に動作の詳細を書くと、呼び出し元ごとに挙動が一致しなくなる。

## スキル間操作

- 別のスキルを起動するのは実行中のエージェントであるため、起動を指示する時は、起動するエージェント、スキル名、引数、期待する戻り値や効果を書く。
  資料の読込はスキルの起動と区別し、読む資料をファイルで指定する。
- 他のスキルの参照資料は、`<plugin-name>:<skill-name>`の形でスキルを識別し、その`SKILL.md`のディレクトリを基点に`references/<file>`のパスを解決して読む。
  常時読み込まれる文書には、参照先の識別子だけを書く。
- スキル間で処理を引き継ぐ時は、提供側が必要な情報を全て揃えた入力を返し、利用側は受け取った入力だけで処理を進める（提供側が利用側に固有の参照文書に依存する構成は避ける）。
- 配布物に含める参照文書は起点の文書（`SKILL.md`、エージェント定義、委譲先の手順書など）からたどれる構成にし、過去の変更履歴などの保管は配布物の外に分ける（努力目標）。

## スキルのパス解決とfork実行（Claude Code固有）

- `${CLAUDE_SKILL_DIR}`は、`SKILL.md`本文の処理時にだけ、その`SKILL.md`があるディレクトリの絶対パスへ展開される。
  自分のスキルに同梱したファイルはこの変数で、プラグイン全体や他のスキルのファイルは`${CLAUDE_PLUGIN_ROOT}`を起点に参照する。
- frontmatterに`context: fork`を指定すると、スキルを独立したサブエージェントの文脈で実行でき、`agent`で種別（`Explore`、`Plan`、`claude`など）を指定する。
  `agent: Explore`と`agent: Plan`によるfork配下では親の`CLAUDE.md`とルールが引き継がれないため、必要な規範は実行時に明示的に読む。
- fork配下では`AskUserQuestion`を使えず、入れ子は5階層までで、親へは最終報告のテキストだけが返る。
  `agent:`に`agents/`配下の定義を指定すると、その定義のツール制限とモデルの指定が適用される。
