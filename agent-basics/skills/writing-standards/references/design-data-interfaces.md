# 公開インターフェースとデータの設計

公開インターフェース、永続データの形式・移行・削除、状態と業務ルール、DBの更新と外部への作用を設計・変更・レビューする時の基準である。
公開した互換性と永続データを壊す変更は取り消しが難しいため、`agent-basics:writing-standards/references/quality-principles-constraints.md`の硬い制約として守る。
方式の比較は`agent-basics:writing-standards/references/quality-principles-qcd.md`に従う。
機構や互換処理を加える前の比較は`agent-basics:writing-standards/references/quality-principles-subtraction.md`に従う。

## エンドユーザー接点と公開インターフェース

公開インターフェースは、API・UI・CLIのオプション・設定形式・出力形式・公開関数など、エンドユーザーが直接使う要素を指す。
リポジトリの内部のモジュール、関数、クラスは、public修飾子の有無によらず内部実装として扱う。

- 公開インターフェースを変える時は、変えた識別子と出力文字列で全文検索し、テスト・文書・サンプル・出力例・呼び出し元・案内文の追従を全て洗い出す。
- エンドユーザーが直接書く要素（設定キー・設定ファイルの書式・CLIのオプション・式の文法・ファイル形式など）を新設する時は、案を示す前に、同じ用途の広く使われるツールや標準の仕様を2〜3件の一次資料で調べる。
  合わせられる語彙と書式は合わせ、合わせない点の理由と前例が無かったことは案に添える。
  プロジェクトの中の既存の命名と書式との一貫性は外部の前例より先に保ち、既存の書式に従うだけの変更は対象外とする。
- 入力の受理条件の判定と案内の文言は同じ定義から導く（努力目標。受理と案内の食い違いを防ぐため）。
  拒否の案内では、拒否した入力値と破った条件を示す。

## API設計

自コードベースの外に利用元がある公開APIに適用し、内部APIは`agent-basics:writing-standards/references/design-heuristics.md`「設計の判定順」の内部の構造を整理する方針に従う。

- 既存の呼び出し元が自身のコードを変えずに使い続けられる互換性を保ち、エラー時は完全な失敗と部分的な失敗を判別できる応答にする。
- 一覧を返すエンドポイントのページネーションは、`agent-basics:writing-standards/references/ui-ux.md`「検索・一覧画面の設計」の観点を使う。
- 長時間の接続（SSEなど）は、中継する各層のアイドルタイムアウトとバッファ、切断・再接続・欠落を利用形態と負荷から評価する。

## Webhook受信設計

送信元の真正性を署名の検証で確かめ、再送・重複受信と到着順の入れ替わりがあっても整合する受信処理にする。

## 認証・認可設計

- 権限の判定は全ての要求に適用される一元的な層に置き、明示的に許可した操作だけを受け付けるデフォルト拒否（default-deny）にする。
- セッションの有効期限と失効、権限を変える操作自体の認可、アクセス可否の判定の監査ログを、同じ設計の工程で決める。
- 権限の最小化と、Cookie認証の属性やCSRF防御を外す時の代わりの防御は、`agent-basics:writing-standards/references/implementation-time.md`「セキュリティ・ロギング・エラー処理」に従う。

## ファイルアップロード設計

- サイズの上限はアプリケーション・リバースプロキシ・ストレージサービスの各層でそろえ、ストリーミングでメモリーの消費を抑える。
  大きなボディは中継層のバッファと一時I/O、メモリーの上限とバックプレッシャー、再送・認証・サイズ制限を実際の構成と負荷で評価し、事例の固定値を一般化しない。
- ファイルの形式は拡張子だけに頼らず、先頭のマジックバイトなどの内容から判定する。
- 再生成できる一時ファイルは失敗時に削除し、ユーザー入力を含む中間生成物は`agent-basics:writing-standards/references/design-runtime.md`「並行処理・排他制御の設計観点」に従う。
- 保存領域の隔離、ダウンロード時の実行の防止、パストラバーサルの対策は、それぞれ独立した必須の防御として全て適用する。
  - 保存先は公開Webルートの外（署名付きURLか認可済みの配信エンドポイントだけから届く領域）にし、ファイル名とパスはサーバー側で一意に生成する。
  - HTMLやSVGなどスクリプトを含みうるファイルは、安全な静的形式へ変換するか、次の3つを全て設定する。
    ダウンロード用のMIMEタイプ（`application/octet-stream`など）、`X-Content-Type-Options: nosniff`、`Content-Disposition: attachment`である。
- 不特定のエンドユーザーの投稿を公開するサービスでは、権利侵害の通報窓口と削除の手順を`agent-basics:writing-standards/references/public-service-obligations.md`「義務の種類ごとの設計指針」に従って設ける。

## エンドユーザーデータの移行

永続化するデータと増え続けるデータを新設・変更する時は、保持期間、容量と上限、上限に達した時にエンドユーザーが観測する挙動、整理と保守の契機と担当を、実際の利用の場面から設計の段階で決める。
完成の判定には、保持期間やデータ量が長期運用の想定上限に達した状態での検証（縮小した模型、境界値の試験、測定できる運用手順の確認など）を含める。

- エンドユーザーが蓄積したデータ（ファイル配置・ファイル形式・スキーマ・設定ファイルの形式など）を変え、移行しないと消失・読み取り不可・起動失敗が起きる場合は、移行処理を同じ変更に含めて実装の側で完遂する。
  技術的な制約で含められない場合に限り、起動を拒否する案内にエンドユーザーが独力で完遂できる具体的な手順を書き、その手順が前提とする環境と状態を実装の担当が先に整える。
- 移行処理と案内の出力が同じ対象を判定する場合は判定関数を共通にし、移行が済めば案内が自動で止まるようにする。
- 設定キーや環境変数の改名・統合・削除で、旧キーの値が無視されても文書にある初期値の動作に戻るだけで安全に続く場合は、移行処理を必須としない。
  旧キーを廃止して破壊的変更として記録し、エンドユーザー向けの文書から旧キーの記述を消し、旧キーの解釈・自動移行・移行待ちのメッセージ・旧キー専用の拒否の案内は作らない。
  初期値に戻るとセキュリティ上の保護が外れる場合と、1回の手動設定で旧キーの挙動を再現できない場合は、前の項の移行処理に従う。

## DBスキーマ・マイグレーション設計

スキーマはコードより先に、データの要件・参照と更新のされ方・変更の見込みから設計し、スキーマの不足をコードの分岐や補正で補わない。
外部キー制約・CHECK制約・ENUM型・結合クエリなどの採否は整合性の要件・参照のされ方・変えやすさを比べて決め、プロジェクトの規範やユーザーの指定があれば従う。
既存の制約や型を変える時は、テーブルの削除と再作成を提案する前に、DBMSの変更手段（PostgreSQLの`ALTER TYPE ... ADD VALUE`、制約の付け替えなど）を調べ、再作成はそれらが使えない場合だけ比べる。

- デプロイ中に新旧の版のコードが同じスキーマへ同時にアクセスしても双方が正しく動く変更にし、マイグレーションの失敗時に元の状態へ安全に戻す手順を用意する。
- 既存データの変換とバックフィルは、本書「エンドユーザーデータの移行」に従う。
- DDLをテスト用のテーブルで確かめる時は、外部キー・参照動作・インデックス・CHECK制約などの制約も再現する（制約の無い簡易なテーブルでは、本番が拒否するDDLも成功する）。

## データの削除

削除の設計では、利用停止・通常の参照からの除外・誤操作からの復元・監査用の履歴保存・消去を目的から区別する。
保持の理由、必要なデータ、参照できる主体、復元できる期間、消去の契機と担当、エンドユーザーへ伝える削除完了の意味を要件に対応付ける。
主データ・履歴・複製・キャッシュ・バックアップの残存範囲と消去の時機を確かめ、復元した時にも削除済みのデータを再公開しない扱いを決める。

### 削除方式の設計

物理削除、論理削除、履歴・退避データの分離を目的と整合性・復元・検索・運用の費用から比べ、削除フラグと監査履歴は分けて扱う。
識別子の符号などへ削除状態を混ぜる案も、データの意味と参照関係から評価する。
論理削除では、一覧・単件取得・結合・集計・バッチなどの参照、復元の権限、一意制約・外部キー・再登録との関係を扱う。

## 状態と業務ルールの条件

状態や業務ルールを持つ機能を新設・変更する時に、単一の操作でも適用する（業務上の条件にも状態にも影響しない文言の修正と、状態を持たない処理は対象外）。

1. 原要求から対象の集合、独立した状態の軸、必要な組合せを導き、実装済みの状態名だけを母集団にせず、途中で加わった要求も反映する。
2. 業務ルールを状態が満たすべき条件（不変条件）として列挙し、関わる状態と、それを確認・変更する操作を対応付ける。
   フラグの組合せ、資源やファイルの有無、操作の順序から、暗黙の状態と許される遷移も見つける。
3. 各条件を誰が成立させ、どの境界で保証するかを、型・入力検証・更新処理・外部の契約などの実在する保証箇所へ対応付け、保証箇所・根拠・未確認・非該当の理由を既存の条件表か計画に書く。
   通常の操作、中断、再試行などで条件を破る操作列があるかを確かめる。
4. 各条件を、各操作の完了時に必ず成り立つ条件と、一時的な違反を後から訂正・補償する条件（結果整合）に分ける。
   この区別が業務上の許容に依存し、原文・既存の仕様・現物から決まらない場合は、初期状態・操作の順序・条件が破れた状態を並べた反例の場面をユーザーに示して確認する。

保証の手段は、不正な状態を表せない構造・所有者への更新の集約・境界での検証・原子的な更新・外部の契約などから選び、条件を見つけたことだけを理由にアサーション・ロック・独自の状態機械を一律に加えない。
独立した状態の軸と、外部の主体が一次の状態を持つ場合の扱いは、`agent-basics:writing-standards/references/implementation-time.md`「データと計算」に従う。

## DBトランザクション設計

更新処理と接続管理では、トランザクションの境界と分離レベル、更新消失の防止（楽観ロック・悲観ロック）、一意制約による重複の防止、デッドロック、接続プールの上限と枯渇を確かめる。
並行性能のためにロックや接続の保持を変える時は、`agent-basics:writing-standards/references/design-runtime.md`「並行処理・排他制御の設計観点」に従う。

複数のロックを同時に保持する処理では、同じ資源を操作する処理はどれも、入力順に依存しない共通の順序で取得する。
例えば口座1と口座2の間の送金では、送金元から順にロックすると逆方向の送金と待ち合う。
送金方向にかかわらず、同じトランザクション内で口座ID順に、更新に必要な強さで両行を先にロックしてから、本来の方向に残高を更新する。
これで防ぐのは取得順の逆転による循環待ちであり、暗黙のロックやロックの昇格を制御できない場合は別の循環待ちが起こりうる。
デッドロックで中断されたトランザクション全体の再試行は、予防とは別の回復策として扱う。

## クエリ性能設計

データ量と参照条件に合うインデックス、N+1クエリの防止、実行計画（`EXPLAIN`など）を確かめ、DBとの往復・転送する行と列・全件取得・重複した計算や初期化・不要な部分のデコードを減らす。

## DB更新と外部送信の整合性設計

DBの更新とメール・外部API・キューなどへの送信を組み合わせる処理では、outboxパターンなどで両者の整合性を保つ。

## DB更新と外部永続資源の整合性設計

DBの更新と、トランザクションの外にある永続資源の作成・更新・削除を組み合わせる処理に適用する。
処理順と回復の方式は整合性の要件から選び、メッセージの送信にはoutbox、外部資源には補償と状態の比較を使い分ける。

- DBと外部資源のどちらを正とするかを決め、利用できる状態と破棄してよい中間状態を区別する。
- 外部への作用の前後と完了記録の前後の各書込境界での失敗、同じ要求の再送、並行実行を扱う。
  永続的な処理状態・冪等な再試行・補償・状態の比較から方式を選び、両方向の孤立と欠落を、補償自体の失敗と再開も含めて収束させる。
- 清掃や補償が進行中の書込や後から届いた正常な書込を壊さないよう、操作キー・世代、条件付きの操作、排他、lease・fencing、削除直前の所有状態の確認などから方式を選ぶ。
- 期限は正当な最大処理時間・生存確認・遅れて届く完了との競合から決め、各境界の失敗・再送・清掃との競合を検証する。
