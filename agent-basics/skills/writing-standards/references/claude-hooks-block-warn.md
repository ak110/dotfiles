# 遮断・警告フックの成立条件と設計の型

本書は遮断・警告するフックを置くかの判定、遮断か警告かの選択、発火対象のエージェントの限定、事前に防ぐ型と遮断後に対処する型の選び方を定める。通知本文の整形は`claude-hooks-messages.md`「通知本文の整形」が、`Stop`と`SubagentStop`に固有の条件は`claude-hooks-stop.md`が定める。

## 遮断・警告フックの成立条件

遮断・警告するフックを置くかは、`quality-principles.md`「QCDと3段判定」のQCDで、フックの費用と防ぐ手戻りの便益を比べて決める。比較は両方向に行う。

- 増やしすぎの防止: 誤検出による正当な操作の遮断・警告、発火ごとのトークンと実行時間、判定の保守費用が便益を上回る判定は置かずに済ませる。誤検出を評価するときは、同じ操作やターンの終わり方を正当と定める規範を判定条件と比べる。Stopでは対象エージェントの正当なターン終了を定める規範を読む。規範が許す形のうちフックの入力から機械的に区別できる部分は判定から外す。静的な解析はシェル構文、作業ディレクトリの遷移、ホストの通知挙動を完全には再現できず、条件を広く取るほど正当な操作を止めて個別の是正が積み重なる
- 避けすぎの防止: 明らかなエージェントの行動誤りをフックの入力から機械的に判定でき、費用が小さい判定は、元へ戻せる誤りを防ぐものでも置いてよい。規範、レビュー、lint、CIだけで同じ誤りの反復を止められない場合に便益が大きい

通した場合に元へ戻せない結果を防ぐ判定（不可逆な操作の防止とデータ破損の防止）と常駐運用の終端保証は、1回の発火でも結果が残るため置く理由になる。
不可逆かどうかは対象の公開仕様が元へ戻す手段を定めているかで判定する。
規範の配送と権限の自動許可は遮断・警告に当たらず、この比較の対象外とする。
この比較はフックという手段の採否だけを決め、Qに影響する問題の処置の要否と、フックが成立しない場合に根本原因へ作用する別の手段の選定は`agent-basics:bugfix`の`references/root-cause-analysis.md`「QとC・Dの区別」に従う。

判定に必要な情報は、フックの入力（イベントpayload、対象ファイル、セッション状態）から機械的に確定できることを要件とする。
担当の別、所有、作業の収束、会話の意味など、判定条件そのものがエージェントの判断を要する対象は、遮断も警告もせずエージェント向け文書で扱う（判定できない条件の通知は、無関係なエージェントにも処置の無いターンを消費させる）。通知本文が解消手段としてエージェントの判断を求める場合は、検出した箇所、判定基準、基準を満たさない場合に入力や本文を変えずに続ける操作を示す。
同じ条件を実行基盤や別の共通フックが既に判定するなら新しいチェックを追加しない（判定差による誤遮断を生む）。
条件を満たさない既存フックは、機械的に確定できる判定へ是正するか、文書へ移して撤去する。

エージェントの出力を対象とするチェックは、適用境界を読み手で定める。ユーザーが直接読む本文は、ファイルへ書き込まない操作でも編集入力と同じ本文チェックへ通す（Claude Codeでは`AskUserQuestion`の質問本文・見出し・選択肢と`ExitPlanMode`の計画本文）。

- Bashコマンドを対象とする判定は、区間分割とトークン化で対象が実行位置にある場合だけ発火させる（検索語や引数に名前が現れるだけの読み取りを検出しないため）。
  実行を遮断するチェックは、コマンド置換・サブシェル・オプション終端まで解決できる解析を用意できるまで、過検出を許容する現行判定を維持する（解析の不足だけを理由に保護を外さない）
- 観測した状態で警告やblockの出力有無を切り替えるフックを計画するときは、別リポジトリ、別worktree、複数エージェントの同時実行などの条件が誤って成立する入力と誤って成立しない入力について、期待動作と検証方法を計画の実装者向け領域へ書く

## 遮断と警告の選択

遮断してよいのは、エージェントが同じターンで`fix`の文面どおりに再実行して是正でき、かつ次のいずれかに当たる場合とする。それ以外は警告とする。

- 通すと復元できない結果が残る（エージェントのコンテキストへの取り込み、外部への公開、プロセスやタスクの終了、対象の上書きと削除など）
- 明らかな行動誤りを止める判定で、遮断で失うターンの入力と作業（トークン）が小さい

遮断はそのターンの入力と作業を失わせ、その損失が発火のたびに生じるためである。
ユーザーへ提示する本文そのものを入力とする判定（`AskUserQuestion`の選択肢、`ExitPlanMode`の計画本文など）は、ユーザーが読んで指摘できるため警告で返す。`AskUserQuestion`の呼び出しを契機とする判定は、入力が大きく再発行の損失が大きいため、本文を入力としなくても警告で返す。
記述言語の判定は遮断してよい。ユーザーは英語の本文を読んで指摘できず、英語の質問には回答できないため再発行が要る。英語の応答後に操作すると識別子や名前を取り違える恐れもある。モデル自身に日本語で書き直させ、識別子と名前を確かめてから同じ呼び出しを再発行させる。
この選択は`PreToolUse`と`PostToolUse`の遮断に適用し、`Stop`と`SubagentStop`には`claude-hooks-stop.md`「遮断の条件と再帰呼び出し対策」を適用する。
判定ごとの結論と根拠はその判定モジュールのdocstringへ記録する（努力目標）。

警告の反復が母集団の欠落や工程停止など復元できない結果を招く場合は、昇格を明示して1件目を警告、2件目以降を遮断とする。指定しない場合は警告の扱いを維持する。後続の編集で是正できる文体などの警告は昇格させない。

## 発火対象のエージェントの限定

通知が指示する処置を特定のエージェント種別や作業ツリー種別だけが実行できる場合は、その種別を発火条件へ含める（含めないと、権限も所有も持たないエージェントが差し戻すだけの工程が発火のたびに生じる）。
エージェント種別はhook payloadの`agent_id`と委譲先セッションの環境変数、作業ツリー種別はGitへの照会から確定し、解決できない場合は通知を出力する。
呼出主体の判別に使う入力は`claude-hooks.md`「hookスクリプトの基本プロトコル」、`Stop`と`SubagentStop`の委譲先での発火は`claude-hooks-stop.md`「委譲先での発火」が定める。

## 設計の型

blockとwarnは、次の2つの型から費用の小さい型を選んで設計する。

- 事前に防ぐ型: エージェントが操作の前に条件を満たす。要件の初出は、発火前に読み得るエージェント向け文書（常時ロードのルール、またはその作業で起動するスキルの本文・参照文書）に置き、文書化済みの正式な起動形（スキル・`AGENTS.md`・タスクランナー定義が指定する形）では発火しない判定にする
- 遮断後に対処する型: hookが判定を担い、通知が解消手段を具体的に示す。発火は規範どおりの通常操作に含め、規範には遮断時は通知に従う扱いだけを書き、閾値を事前に満たすための計測や確認の工程を書かない

事前に防ぐ型の費用は操作のたびの事前工程の合計、遮断後に対処する型の費用は実際の遮断回数に遮断と通知に従った取得の分を掛けた量である。事前工程は失敗しないため振り返りに現れず、費用として観測されにくい。取り消しの難しい操作やデータ破損を防ぐhook（`pkill`の遮断など）は事前に防ぐ型で扱う。
どちらの型でも、通知が示す解消操作の入力が同じ判定条件へ一致しないことを確かめる（一致すると正しい操作のたびに通知が反復し、同じ標識の通知全体が無視されるようになる）。
Claude CodeとCodexの双方に対応するフックでは、ホスト固有の入力・終了状態が必要な判定だけを差分とし、共有できる判定条件と規範参照を共通実装へ置く。

## 迂回手段

blockするチェックは規範の読み込み不足や手順の取り違えを通知する目的で設計する。
別ツール経由の書き換えやフック自身の変更などの迂回まで遮断するかは、独立した要件や実際の認可・データ保全を守る必要がある場合に、増えるコードと保守負担を防げる事象と比べて決める。網羅的な迂回遮断は便益が小さく、費用が上回りやすい。
迂回の抑止自体を目的とするチェック処理は新設・強化せず、迂回可能な余地を残す。実行環境の権限拒否を迂回する認可にはしない。
