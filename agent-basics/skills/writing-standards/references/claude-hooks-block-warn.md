# 遮断・警告フックの成立条件と設計の型

## 遮断・警告フックの成立条件

遮断や警告をするフックを設置するかどうかは、`quality-principles.md`「QCDと3段判定」に基づき、フックの導入・運用コストと、それによって防げる手戻りの便益とを比較して決定する。比較は次の両面から行う。

- 増やしすぎの防止: 誤検出によって正当な操作を遮断・警告してしまうリスク、発火ごとに消費されるトークンと実行時間、判定ロジックの保守費用が便益を上回る場合は、フックの設置を見送る。誤検出を評価する際は、同じ操作やターンの終了方法を正当と認めている規範と判定条件とを突き合わせる。`Stop`の検証では、対象エージェントの正常なターン終了を定めた規範を確認する。規範が許容しているパターンのうち、フックへの入力から機械的に判別できるものは判定対象から除外する。静的解析だけではシェルの文脈、作業ディレクトリの遷移、ホスト側の通知挙動を完全には再現できないため、判定条件を広げすぎると正当な操作まで止めてしまい、個別の例外対応が積み重なる原因となる。
- 避けすぎの防止: エージェントの明確な行動誤りをフックの入力から機械的に判定でき、運用コストが十分に小さい場合は、後から復元可能な誤りを防ぐ目的であっても設置して差し支えない。特に、規範の記述、レビュー、lint、CIだけでは同じ誤りの繰り返しを防ぎきれない場合に大きな便益が得られる。

実行してしまうと元に戻せない操作を防ぐ判定（不可逆な操作の防止やデータ破損の防止）や、常駐プロセスの確実な終了保証は、一度の発火であっても重大な被害を防ぐ効果があるため、フックを設ける十分な根拠となる。
操作が不可逆であるかどうかは、対象ツールの公開仕様に元の状態へ復元する手段が用意されているかで判断する。
規範の自動配送や権限の自動許可フックについても、発火頻度、重複発生、受信トークン量、再取得や保守の費用と、その操作が支える成果の価値とを比較して採否を決める。遮断か警告かの選択は、実際に操作を差し戻す判定に対して適用する。
この比較はフックという手段を採用するかどうかの判断に限定される。品質（Q）に影響する問題への対処が必要かどうかや、フックが成立しない場合に根本原因へアプローチする代替手段の選定については、`agent-basics:bugfix`の`references/root-cause-analysis.md`「QとC・Dの区別」に従う。

判定に必要な情報は、フックの入力（イベントペイロード、対象ファイル、セッション状態）から機械的に一意に特定できることを必須要件とする。
担当範囲の境界、資源の所有関係、作業の収束状況、会話の意図など、判定基準自体にエージェントの文脈判断を要する事項は、フックによる遮断や警告の対象とせず、エージェント向け文書の中で扱う（機械判定できない条件で通知を出すと、無関係なエージェントにも対処法のないターンを無駄に消費させる）。通知本文の解消手順としてエージェント自身の判断を求める場合は、検出された箇所、判断基準、および基準を満たさない場合に入力や本文を変更せずにそのまま処理を継続する操作手順を明示する。
同様の条件を実行基盤や他の共通フックがすでに判定している場合は、新しいチェックを追加しない（判定基準のわずかな差異によって予期せぬ誤遮断が生じるため）。
条件を満たさない既存のフックは、機械的に確定できる判定に改修するか、文書側の規範へ移してフック自体を撤去する。

エージェントの出力を対象とするチェックは、読み手が誰であるかに応じて適用の境界を定める。ユーザーが直接読む文章については、ファイルへの書き込みを伴わない操作であっても、ファイル編集時と同じ本文チェックを適用する（Claude Codeにおける`AskUserQuestion`の質問本文・見出し・選択肢や、`ExitPlanMode`の計画本文などが該当する）。

- Bashコマンドを対象とする判定は、コマンド文字列の分割とトークン解析し、対象コマンドが実際の実行位置にある場合にのみ発火させる（検索キーワードや引数として名前が出現しただけの読み取り操作を誤検出しないため）。
  実行を遮断するチェックについては、コマンド置換、サブシェル、オプションの終端（`--`）まで正確に解決できる解析処理を用意できるまで、ある程度の過検出を許容する現行の判定を維持する（解析が不完全であることだけを理由に安全保護を解除しない）。
- 実行時の状態に応じて警告や遮断の出力を切り替えるフックを設計する際は、別リポジトリ、別worktree、複数エージェントの同時実行などの条件下で、誤って発火する入力パターンと誤って発火しない入力パターンを整理し、期待される動作と検証方法を計画ファイルの実装者向けセクションに明記する。

## 遮断と警告の選択

遮断（block）を選択できるのは、対象の操作が実在する認可・権限の境界を越える場合、破壊的な操作を伴う場合、データの整合性を損なう場合、または公開契約を破る場合であり、かつ保護対象、発生する実害、および解消のための操作を機械的に一意に特定できる場合に限定する。それ以外の場合は警告を返すか、関連資料を配送して作業を支援する。

- 外部への公開、所有権を確認できないプロセスやタスクの終了、復元手段のない上書きや削除などは、具体的な実害を防止するための保護として扱う。
- 必要な資料の未取得、作業手順の確認、通常の読み込み量の調整など、復旧が容易な手順上の支援は警告とする。資料の不足を理由に、別の通常の読み取り、診断、結果回収の操作まで遮断対象を広げることは避ける。

遮断を実行すると、そのターンの入力と進行中の作業が失われ、発火のたびに手戻りの損失が発生するためである。
ユーザーへ直接提示する文章そのものを検証する判定（`AskUserQuestion`の選択肢、`ExitPlanMode`の計画本文など）は、ユーザー自身が読んで指摘できるため、警告として返す。`AskUserQuestion`の呼び出しを契機とする判定は、ユーザーへの入力負担が大きく再発行のコストが高いため、本文の検証以外であっても警告にとどめる。
使用言語に関する判定（英語出力の検出など）は遮断してよい。ユーザーは英語の本文を読んで指摘することが難しく、英語の質問には回答しにくいため、再発行が必要となる。また英語で応答した後に操作を続けると、識別子や名前を取り違えるリスクも生じる。モデル自身に日本語で書き直させ、識別子や名称を確認してから同一の呼び出しを再実行させる。
この選択基準は、`PreToolUse`、`PostToolUse`、`Stop`、`SubagentStop`の各イベントにおける遮断に適用する。`Stop`および`SubagentStop`では、`claude-hooks-stop.md`「遮断の条件と再帰呼び出し対策」に定める終了保証と再帰防止の条件もあわせて適用する。
各判定における結論と根拠は、該当する判定モジュールのdocstringに記録する（努力目標）。

原因、対象、必要な対処が同一である警告は、同じ状況が継続している間は初回の1回のみ通知する。状況に変化が生じた場合や、一度解消した後に再発した場合は改めて通知する。発生回数のみを理由とした機械的な反復通知や、反復を理由とする遮断への自動昇格は行わない。実害を防ぐための遮断は、操作ごとに実際の条件に基づいて判断する。

## 発火対象のエージェントの限定

通知が指示する対処手順を特定のエージェント種別や作業ツリー種別のみが実行できる場合は、その種別を発火条件に含める（含めないと、権限や資源の所有権を持たないエージェントが操作を差し戻されるだけの無駄な工程が発火ごとに生じる）。
エージェントの種別はhookペイロードの`agent_id`や委譲先セッションの環境変数から特定し、作業ツリーの種別はGitへの問い合わせによって確認する。種別を特定できない場合は通知を出力する。
呼び出し主体の判別に利用する入力情報は`claude-hooks.md`「hookスクリプトの基本プロトコル」に、`Stop`および`SubagentStop`における委譲先での発火条件は`claude-hooks-stop.md`「委譲先での発火」に従う。

## 設計の型

遮断（block）と警告（warn）は、以下の2つの型からより運用コストの小さい方を選択して設計する。

- 事前に防ぐ型: エージェントが操作を実行する前に条件を満たすように促す構成。要件の初出は、発火前に読み込むエージェント向け文書（常時読み込まれるルール、またはその作業で起動するスキルの本文・参照文書）に配置し、文書化された正規の起動形式（スキル、`AGENTS.md`、タスクランナーで指定された形式）に沿っていれば発火しない判定とする。
- 遮断後に対処する型: hook側で判定し、通知メッセージの中で解消手順を具体的に提示する構成。発火を通常の運用フローの一部として受け入れ、規範側には「遮断された場合は通知の指示に従う」という取り決めのみを記載する。閾値を事前に満たすための計測や事前確認の工程は規範に記載しない。

「事前に防ぐ型」のコストは、操作のたびに行う事前確認工程の合計であり、「遮断後に対処する型」のコストは、実際の遮断発生回数に遮断と指示に基づく再取得のコストを掛け合わせた量となる。事前確認工程はエラーにならず振り返りにも現れにくいため、コストとして見落とされやすい。取り消しが困難な操作やデータの破損を防ぐフック（`pkill`の遮断など）は、「事前に防ぐ型」で設計する。
いずれの型を採用する場合も、通知が提示する解消操作の入力が、同一の判定条件に再び一致してしまわないことを確認する（一致すると、正しい操作をしているにもかかわらず通知が繰り返され、同じプレフィックスの通知全体が無視される原因となる）。
Claude CodeとCodexの双方に対応するフックでは、ホスト固有の入力や終了状態の処理のみを差分とし、共通化できる判定条件や規範への参照は共通の実装へ配置する。

## 迂回手段

遮断するチェックは、「遮断と警告の選択」で定めた実害を防ぐために設ける。規範の読み込み不足や復旧可能な手順の誤りについては、警告や関連資料の配送による支援で対応する。
別ツールを経由した書き換えやフック自体の改変といった迂回操作まで遮断するかどうかは、独立した要件が存在する場合や、実際の認可・データ保全を保護する必要がある場合に、増加するコード量や保守負担と防げるリスクの大きさとを比較して決定する。あらゆる迂回を網羅的に遮断しようとすると便益に対してコストが上回りやすい。
迂回の防止そのものを主目的とするチェック処理を新たに設けたり強化したりすることは避け、必要最小限の迂回の余地を残す。ただし、実行環境のセキュリティ制限や権限拒否を不正に回避する目的での迂回は認められない。
