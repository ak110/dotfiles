# エージェント向け文書への追記と記述量の管理

規範を改訂する担当が判断に必要な目的と条件を保ち、読み手のエージェントが作業に合う規定を選んでユーザーの意図に沿って動けるようにする。
本書は、規範の不足や誤適用に対処してエージェント向け文書の規定を足す・改める時と、文書の記述量を点検・削減する時の基準である。
主に原則9（`agent-basics:writing-standards/references/quality-principles-subtraction.md`）の適用である。
費用の比べ方は原則2（`agent-basics:writing-standards/references/quality-principles-qcd.md`）に従う。
問題への対処として規定を足す・改める時は、先に`agent-basics:bugfix`を起動する。

## 規範追記時の判定

規範は最小限にし、追記は、誤解を招いた既存の書き方の是正と、同じ目的の既存の記述の統合・削除で目的を達成できない場合に限る。
散文の規定は仕組みが伴わないと作業の流れで省かれ、エージェントは手間の少ない手順を選びがちである。
確実にしたい行動は、次の仕組みで保証できるかを、読込・記入・実行の費用と比べて先に確かめる。

- 正しい手順が最も手間の少ない手順になる形（指定を省いた時に正しい値が使われる設定、正しい形の入力だけを受け付けるコマンド、工程の統合、正しい手順を妨げる手間の撤去）
- 機械的な検査
- 記録の欄（件数や決まった値など短く書ける形にする。欄を足すほど記録が遅くなる）

仕組みが強制するようになった行動を求める散文は、欄の定義の1か所を残して削る。
改善の投資先は`agent-basics:writing-standards/references/design-heuristics.md`「設計案の予備選別」の順に比べる。
改訂案が将来増やす作業量と保守の費用は、採用の前に`agent-basics:writing-standards/references/design-heuristics.md`「案の採否と実施順の判定」で比べる。
規範・警告・hook・検査・CLIの判定などが行動を起こす条件を新設・変更する時は、その条件が必要な対応を促す場面と、不要な読込・警告・確認・停止を繰り返す場面を挙げる。
見逃しの不利益と誤適用の継続費用を同じ比較に含め、必要な品質を保つ適用の境界を採用の前に決める。
進行を止める判定（遮断、終了コード1、保存の拒否など）は、`agent-basics:writing-standards/references/design-heuristics.md`「進行を止める判定の条件」も満たす。
規範案では、一般知識は価値・観点・代表語・短い確認項目で想起させ、固有のパス・公開契約・認可の条件と硬い制約は具体的に残す。
成果物への記載を義務付ける条文は、その記載を読む主体と利用目的を同じ条文に書き、示せない場合は作成者が対象を確かめる記述にとどめる。
規範の置き場所は`agent-basics:writing-standards/references/agent-documents-basics.md`「置き場所の選定」に従う。

### 常時規範への追記条件

- 常時規範へ追記するのは、ユーザーが言葉で明示した要件を規定にする場合、硬い制約を守る条件を足す場合、既存の条文の統合でファイル全体の記述量を減らす場合に限る。
  その他の知見は、該当する工程で起動するスキル、参照資料、hookの通知へ置く。
- 常時規範からスキルや`references/`の起動・読込を指示する時は、起動の契機と対象と、そのスキルが扱う範囲だけを書く。
  観点・手順・例外・具体例はスキルの側だけに置く（両方に書くと、どちらを優先するかが曖昧になる）。
- 規範で起動を指示するツールとスキルは、その規範を読むエージェント自身が起動できるものに限る（努力目標）。
- ユーザーへの発話に適用する規定は、その発話を担当する主体が読む定義元に集め、守らないと意図が伝わらない重要な条文に限る（努力目標。発話ごとの読込量を抑えるため）。

### 失敗時の回復手順

失敗、拒否、上限超過、遮断などの異常時だけに行う手順は、異常が起きた時に読み手へ届く手段へ置く。
手段には、ホストやCLIのエラー出力、hookの遮断通知の`fix`、`PostToolUseFailure`の`additionalContext`、異常を条件とする読込表の行などがある。
全文が毎回読まれる階層（常時ロード、役割別の注入、スキル起動時、役割起動時）には、異常の種類と参照先を示す起動の契機だけを書く（努力目標。平常時の判断への影響を避けるため）。
既存の仕組みが同じ手順を通知する場合は、文書の側の記述を削る。
読み手が異常を直接観測できない場合（エラー出力なしに成果物が破損する場合など）は事前防止の規定として書き、手順の量が起動の契機と同じ程度以下ならその場に残す。

### 工程と検証の追記

- 検証・レビュー・待機・再確認などの工程を足す・改める時は、その工程が担保する成果と、先行の工程や既存の基準で達成済みの条件を確かめ、足りない条件だけを書く（努力目標）。
  工程を足す案と範囲を広げる案は、既存の実行記録から1回の所要と通常の実行回数を取って比べ、記録が無ければ未計測として適用条件を限る。
  完了条件は、その工程が達成すべき具体的な成果として書く。
- 不具合への対策として作業を制限する規定は、原因への直接の対策と、症状を抑える制約が守る価値を比べて決め、制約を残す場合は見直しの契機を書く。
- 将来の観測結果を削除の条件とする暫定の規範は、追記の時点で条件が未成立であることを実際の値で確かめ、成立後に目指す状態も同じ粒度で書く。
  削除する時は、削除条件の文面に加え、対象の節・警告の種類・実際に観測された値が削除後も必要な状態を満たすかを確かめ、同じ粒度で比べられなければ規範を残して条件の記述を直す。
- 品質要件は、生成側（起草と実装の完了条件）と検出側（レビューの観点、自動チェック）の双方へ同時に足す（努力目標）。
  再発防止のセルフチェック観点が`agent-basics:bugfix/references/prevention.md`「差分を契機にする確認項目」に当たる場合だけは、検出側に置く。
- 複数の対象の調査と起草は、同じ担当が似た対象から順に処理して知見を再利用する構成を初期案とし、分担は起動から検収と結論の再構築までの総費用で比べ、分ける場合は理由を書く。
  成果物の作成担当と文脈を共有しない担当によるレビューと、書込の所有権に基づく分担は保つ。
- 計画やレビューの契約に詳細（実装の順序・作業単位の分割・個別のコマンドなど）を書くのは、既存の規範や確定した外部仕様から一意に導けない場合と、誤ると安全性・データ保全・公開契約・権限の境界を損なう場合に限る。

### 条文の形式

- 判断の分岐と、報告や成果物の記載項目は、個別の事例を列挙する前に、全体を貫く判定基準で書けるかを検討する。
  個別の列挙を残す場合は、列挙外の場合の扱いと対象範囲を同じ条文に書く（定めないと狭く解釈され、適用すべき場面で見落とされる）。
- 担当・手段・受入先を選ぶ条文は、品質・費用・時間の比較軸を先に、制約と候補の列挙を後に置き、列挙外の手段も同じ軸で扱うと同じ条文に書く。
- 実行環境やモデルの版を含む条文は`agent-basics:writing-standards/references/investigation.md`「エージェント向け文書の技術的条文」に従う。

### 既存対象への波及

- 改訂する判断のルールと同じ処理を行う既存の規定・生成側・利用側は、`agent-basics:bugfix`の問い5（類似見直し）として探し、判断の根拠は既存の改訂記録に残す。
  新しい場面別の条文が一般則の範囲を狭めていないか、相反する指示を含むかも同じ方法で確かめる。
  品質に影響する問題への対処として規定を足した場合は、努力目標の標示によらず、既存の対象の修正範囲と完了を同スキルの問い5と問い7（確認）で決める。
- 同じ事象に相反する判断を下す条文は、同じ変更で書き換えるか優先順位を明示して解消し、別リポジトリの所管ならその担当へ変更を引き継ぐ。
- 規定を新設・強化した場合は、努力目標かを問わず、その規定が適用される既存の成果物（追加の前に作られ、追加後も使われるものを含む）も確かめる。
  根拠は原則9（`agent-basics:writing-standards/references/quality-principles-subtraction.md`）にある。
  作業権限の範囲内の違反はそのセッションで直し、範囲外は担当へ引き継ぐ。

## 文書記述量の管理

### 見直す契機と点検観点

モデルや実行環境の更新、読込量や確認の往復の増加、指示と挙動の不一致を契機に、エージェント向け文書を点検する。
対象のモデルとホストの公式のプロンプトガイドなどの一次資料と、実際に配送される本文を比べ、次の観点で処置（残す、必要な場面へ移す、機械チェックへ任せる、削除・統合する）を選ぶ。

- 新しいモデルが追加の指示なしで従う内容（熟考を促す語を含む）と、理由が当てはまらなくなった注意書き
- 広すぎる起動条件（スキルの`description`、読込表）、毎回全文を読ませる文書、常時読み込まれる量
- 読込条件の違う内容の同居、同じ条件・資料を重ねる参照、重複する確認・検証の工程、指示どうしの矛盾・重複
- 自律・確認・承認・完遂の規定の不明瞭さと、停止・確認・未完了を招く文言が守る価値と適用の境界（明示された承認条件や安全の保護は、通常の作業へ意図せず確認を求める条件と分ける）

採否を決める読者へ、提案ごとに対象ファイル・該当の文言・観点・根拠・行動への影響・具体的な修正案を示す。
修正案で承認範囲や権限が広がるかも示し、広がる提案は必要な承認を得てから適用する。
比べていない削減の候補は仮説として分け、点検だけを依頼された場合は提案の一覧を返して終える。
重複した文を圧縮・削除する時も、各文書の冒頭の目的（`agent-basics:writing-standards/references/agent-documents-basics.md`「冒頭の責務と目的」）は判断に要る記述として残し、全体の量を理由に削らない。

### 記述量の水準

規範のMarkdownは1文1行で書く。
ファイルの行数は、ファイルごとの行数の上限を検査するプロジェクトの機械チェックだけが判定し、文書の合計の行数とバイト数は判定の対象外とする。
読込の負担は、変更が増減させる常時の配送と、影響する作業で条件が成立して実際に読む範囲を分けて比べ、元から対象外の作業に読ませる変更だけを負担の増加として見直す。
上限以下のファイルでは、行数の測定・見積もり・記録・削減を省く。
上限を超えた時の整理は`agent-basics:writing-standards/references/implementation-time.md`「lintと機械チェック」に従い、整理後の水準は常時の合否の上限とは別に扱う。
容量のための移設でも、必須の意味・認可・公開契約・起動時の説明・判断の前に全文を読める状態を保ち、読みにくい圧縮を避ける。

### 必要な場面へ移す

規範の量が作業へ与える影響は、同じ取り決めの分散で同期する箇所が増えることと、判断に要らない記述を起動時に読んで初期の文脈を圧迫することの2点であり、削減の対象はこの基準で選ぶ。
読む主体・工程・対象が限られる内容は必要な場面へ移し、判断の前に全文を読める状態と、同時に要る前提・例外・終了条件を保つ。
スキルのファイル数を減らしても常時の読込量はほとんど減らないため、毎回参照しない記述の`references/`への退避と、エージェント定義の簡素化を先に検討する。
スキルの統廃合は起動の手順に影響するため、起動時の判断の精度を上げる場合に限る。

### 機械チェックへ任せる

対象プロジェクトで既に実行されるformatterやlinterが同じ条件を扱う細則は、その検査の範囲を確かめて整理する。
新しいhookや検査は、機械化できそうだという理由だけでは足さずに、費用と効果を比べて決める。
機械で判定できる表記規則を足す・改める時は、対応する検査を同じ変更で更新する。
エージェント向け文書は生成時の予防として保ち、lintと重複する細則のうち細かすぎるものだけを削る（検出後の書き直しだけに頼ると、指摘と修正の往復が増える）。

### 削減の判定根拠

簡略化・統合・移設では、配置や形式が利用側の判断で果たす機能（同時の比較・区別・実行の契機・責務）が、変更後の利用場面で保たれるかを`agent-basics:writing-standards/references/design-heuristics.md`「設計品質の劣化確認」で判定する。
別の節に同じ情報があるだけの場合は、機能を保った根拠から除く。
大きな削減では、削る前・削った後・対象の文書なしの3条件を、課題・初期状態・モデル・effort・起動の引数・評価基準をそろえて新しい文脈で試す（努力目標。費用がかかるため）。
試した場合は、削った後が要件の充足と判断の内容の両方で同等以上の時だけ採用し、文書なしでも同等だった記述は、課題がその状況を含むことを確かめて削除の候補にする。
ユーザーが常時規範の記述量の削減を求めた場合は、指定されたファイル名によらず常時規範の全体を対象にし、努力目標の標示が無い条文の削除も検討に含める。
移設先のスキルが無い場合は新設してよく、削減の数値目標はユーザーが具体的に指定した場合だけ採用する。

### 削除・統合する

削除と統合は次のどれかの根拠を満たす場合に行い、正規の定義への到達と、元の適用範囲・例外・拘束力を保つ。

- SSOT違反: 他のファイルに正規の記述があり、ここは転記である。
- 自明導出: 上位の基本方針か一般知識から導ける。
  明記しないと考慮されにくい観点（セキュリティ、エラー処理など）は代表語を残し、硬い制約は具体的に書く。
  固有の事実を自明導出として扱うのは、一般知識から導ける場合に限る。
- 公式ドキュメントで代替可能: 一次資料を参照すれば同等の情報を得られる。
- 上位指針への統合: 個別の細則を束ねる基本方針へまとめられる（同じ節に並んで溜まった同じ工程の箇条を含む）。
- 手段固定: コマンド、ツール、実行順序、パスなどを、要件上の理由を示さずに固定している。
- 個別事象特化: 特定の1件の事例、工程、識別子に依存しており、一般の規則へ抽象化できる。
- 過剰な手順化: 読み手が目的と前提知識から判断できる工程、確認、分岐、例外処理を細かく書いている。
- 条件の入れ子: 例外や除外が重なり、条件と行動の対応が一対一でなくなっている。
- 拘束力の過剰: 技術的な不成立、データの破損、公開インターフェースの破壊、セキュリティ上の欠陥のどれも防がない条文を、努力目標の標示なしで厳格に書いている。

数値・閾値・境界値の根拠（設定の理由、境界を分ける根拠、トレードオフ）は削除の対象外とする。
削ると拘束力が損なわれる場合は、他の節で代えられなければ元の記述を残す。
圧縮と統合では、元の規定の順序の制約・前提条件・除外条件と、主語と述語の関係や動詞の意味を保つ。

### 残す

固有の事実・意図・判断に要る理由・認可・安全性・公開契約は、取り除くと必要な結果や境界を失う場合に残す。
圧縮・統合・削除をする場合も、次の要素を保つ。

- 本文の冒頭の目的の記述（適用の要否を判断する根幹の動機）
- 配置や形式が担う判断の機能（保ったかの判定は本書「削減の判定根拠」）
- 開いた列挙の表現（「等」「〜を含む」「〜など」。閉じた表現に変えると適用範囲が狭まる）
- 同じファイルの既存の表記とそろえる用語と、並列の表現の対称性
