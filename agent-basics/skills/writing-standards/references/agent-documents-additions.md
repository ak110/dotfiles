# エージェント向け文書への追記と記述量の管理

本書は、エージェントが直接読み込む文書へ新しい規定を追記する場合と、文書の記述量を管理する場合の判断基準を定める。
文書の責務、記述内容、条件の書き方、語調の基準は`agent-documents-basics.md`に従う。

## 規範追記時の判定

エージェント向け文書へ規定を追記・改訂する前に、その記述がQCD（`quality-principles.md`「QCDと3段判定」）の向上につながるかを判断する。貢献しない内容は書かず、既存の記述にあれば削除する。
改訂案が将来増やす作業量と継続的な保守費用は、採用前に`design-heuristics.md`「案の採否と実施順の判定」で比較・評価する。
規範・警告・hookなどがエージェントの行動を起こす条件を新設・変更するときは、読む主体と実際の利用場面から、次の2つの場面を挙げる。

- その条件が必要な対応を促す場面
- 不要な読込・警告・確認・停止を繰り返す場面

必要な対応を見逃す不利益と誤適用の継続費用を同じ比較に含め、必要な品質を保つ適用境界を採用前に確定する。
この比較は同節の採否判断の中で行う。
評価自体の負担を抑えるため、独立した審査工程や専用の計測を増やすことは避ける。
品質（Q）に影響する問題への対処として規定を追加する場合は、`agent-basics:bugfix/references/root-cause-analysis.md`「QとC・Dの区別」に従い、調査の深さや終了条件も同資料の重大度別の基準に合わせる。
記述の詳しさは、`writing.md`「読み手別の追加注意点」のエージェント向け文書の項に従う。

成果物への記載を義務付ける条文を起草・改訂する場合は、その記載を読む主体と利用目的を同じ条文内に明記する。読み手と用途を示せない場合は、成果物を作成する主体が対象事項を確認する記述にとどめる。
成果物の分量、識別子、構成に関する共通基準は`writing.md`「文章の共通規定」に集約し、成果物ごとの文書には固有の取り決めのみを記載する。

### 常時規範への追記条件

- 常時規範へ追記できるケースは、ユーザーが言葉で明示的に示した要件を規定にする場合、`quality-principles.md`「規定の区分と標示」の硬い制約を守る条件を追加する場合、および既存の条文を統合してファイル全体の記述量を減らす場合の3点に限る。その他の知見は、該当工程で起動するスキル、参照資料、hookの通知へ配置する。
- 常時読み込まれる規範（`AGENTS.md`や`CLAUDE.md`など）でスキルや`references/`の起動・読み込みを指示する場合は、起動契機、起動対象、そのスキルが扱う範囲のみを記載する。具体的な観点、判断手順、例外、具体例はスキル側のみに持たせる。両方に重複して記載すると、どちらを優先すべきか判断が難しくなる。
- 規範の中で起動対象として指定するツールやスキルは、その規範を読むエージェント自身が起動できるものに限定する（努力目標）。
- 規範、基準、目標値が存在するかどうかを判断するときは、その判断をする工程で該当する記述がコンテキスト上に実際に読み込まれているかで判定する。
- ユーザーへの発話に適用する規定は、その発話を担当する主体が読む定義元に集約し、守らないと意図が正しく伝わらない重要な条文に限定する（努力目標。発話ごとの読み込み量を抑えるため）。

### 失敗時の回復手順

- 失敗、拒否、上限超過、遮断といった異常時にのみ実行する手順（失敗時の回復手順）は、異常が発生した際に読み手に届く手段へ配置する。具体的には、ホストやCLIのエラー出力、hookの遮断通知に含まれる`fix`、`PostToolUseFailure`の`additionalContext`、異常発生を条件とする読込表が指す`references/`などがある。
  異常の有無にかかわらず全文が読まれる階層（`agent-documents-basics.md`「置き場所と配送」の読込階層のうち、常時ロード、役割別注入、スキル起動時、役割起動時）には、異常の種類と参照先を示す起動契機のみを記載する（努力目標。平常時の判断に不要な影響を与えないため）。
  既存の仕組みで同様の手順がすでに通知される場合は、文書側の記述を削除する。読み手が異常を直接観測できない場合（エラー出力なしに成果物が破損する場合など）は事前防止の規定として記載し、手順の分量が起動契機と同等以下であれば移設せずにその場に残す。

### 工程と検証の追記

- 規範が適用されなかった問題への対策を検討する前に`agent-basics:bugfix`を起動し、`references/root-cause-remediation.md`の「再発防止策」を利用する。
- 検証、レビュー、待機、再確認などの工程を追加・改訂する場合は、その工程が担保する成果と、先行工程やすでに存在する基準で達成済みの条件を確認し、追加が必要な条件のみを記載する（努力目標。利用されない記録や重複する工程を増やさないため）。
- 不具合対策として作業を制限する規定を設ける際は、原因への直接対策と、症状を抑えるための制約が守る価値とを比較する。原因への対策によって必要な成果を確保できる場合は制約の要否を再検討し、制約を残す場合は見直しの契機を記載する。
- 将来の観測結果を削除条件とする暫定的な規範は、追記の時点でその条件がまだ満たされていないことを実際の値で確認し、条件成立後に目指すべき状態も同じ粒度で記録する。
- 直接操作や代替手段に関する要件を記述する場合は、操作の開始に必要な対象と入力を、同一のコンテキストから取得できる手順とともに記載する。
- 品質要件を追加する際は、生成側（起草時や実装時の完了条件）と検出側（レビュー観点、自動チェック）の双方へ同時に反映する（努力目標）。
- 複数対象の調査・起草は、同じ担当が似た対象から順に処理して知見を再利用する構成を初期案とする。分担は、起動、規範や背景の重複読込、指示作成、検収、結論の再構築までの総費用で比較し、有利な場合に似た対象をまとめて渡す。件数や独立性だけで担当を増やさず、分割する理由を明記する。成果物の作成担当と文脈を共有しない担当によるレビューと、書込所有権に基づく分担は維持する。
- 完了条件は、その工程が達成すべき具体的な成果として記述する。

生成側と検出側への追加に関して、再発防止のセルフチェック観点のみは検出側に限定して配置する例外とする。
この例外を適用するのは、`agent-basics:bugfix`の`references/root-cause-remediation.md`「再発防止策」の条件をすべて満たす場合に限る。
一般的な品質要件の追加については、原則どおり双方へ同時に追加する。

計画やレビュー契約に実装順序、作業単位の分割、個別コマンドなどの詳細を記載するのは、既存の規範や確定済みの外部仕様から一意に導けない場合、または手順を誤ると安全性、データ保全、公開契約、権限境界を損なう恐れがある場合に限定する。

### 条文の形式

- 守るべき価値、基本方針、例示、適用範囲の記述形式は`agent-documents-basics.md`「条件と範囲の記述」に従い、役割別の配置は同資料「置き場所と配送」に従う。
- 判断の分岐や報告・成果物の記載項目は、個別の事例を列挙するよりも、全体を貫く判定基準で表現できないかを先に検討する。個別列挙を残す場合は、列挙外のケースの扱いと対象範囲を同じ条文内に記載する（明確に定義しないと狭く解釈され、本来適用すべき場面で見落とされる恐れがある）。
- 数値の閾値や複雑な判定手順を設ける際は、より単純な原則で代替できないかを検討し、閾値を設定する場合はその境界値の根拠を本文に残す。
- 実行環境やモデルのバージョン情報を含む条文を作成する場合は、`investigation.md`「エージェント向け文書の技術的条文」に従う。

### 既存対象への波及

- 改訂対象の判断ルールと同様の処理を行う既存の規定・生成側・消費側を見直す前に、`agent-basics:bugfix`を起動し、`references/root-cause-remediation.md`「類似見直し」の母集団導出と判定手順を適用する。判断の根拠は既存の改訂記録に残す。新しい場面別の条文が一般則の対象範囲を狭めたり、相反する指示を含んだりしていないかの確認にも同じ判定を用いる。品質（Q）に影響する問題への対処として規定を追加した場合は、努力目標の表記にかかわらず、同資料の「類似見直し」および「類似見直しと再発防止の完了」に基づいて既存対象の修正範囲と完了基準を決定する。
- 同様の目的を持つ既存の条文を統合または削除できないかを合わせて検討する。不足を補う際は、新規追記、既存記述の書き換え、不採用の選択肢を比較する（努力目標。条文が増え続けると、適用範囲が広がらないまま読み込み量のみが増加するため）。
- 同一の事象に対して相反する判断を下す条文を共存させない。矛盾する既存条文がある場合は、同じ変更で書き換えるか優先順位を明確にし、別リポジトリの所管であれば該当リポジトリの担当へ変更を引き継ぐ。
- 努力目標ではない規定を新設・強化した場合は、その規定が適用される既存の成果物も確認し、作業権限の範囲内にある違反はそのセッション内で修正する。権限外の箇所は担当者へ必要な変更を引き継ぐ。これには規定追加前に作成され、追加後も継続して利用される成果物も含まれる。重大度に応じた未知の問題の探索終了と、修正対象の範囲は区別して扱う。努力目標の規定は、新しく作成する記述から適用する。
- 記録先を新設・改名・移設する改訂では、同様の内容の記録を求めている既存条文を、新しい記録先への参照へ書き換える。

## 文書記述量の管理

### 見直す契機と点検観点

モデルや実行環境の更新、読み込み量や確認往復の増加、指示と挙動の不一致を契機に、エージェント向け文書を点検する。
対象モデル・ホストの公式プロンプトガイドなどの一次資料と、実際に配送される本文を比較する。
以下の7観点を用い、削減候補が無いときの動作との差は「削減の判定根拠」の3条件比較で判断する。

- 新しいモデルが追加指示なしで従う内容（熟考を促す語を含む）
- スキルの`description`や読込表の広すぎる起動条件
- 毎回全文を読ませる文書
- 重複する確認・検証の工程
- 互いに矛盾する指示
- 作業の完了前に止めてユーザーへ確認させる規定
- 常時読み込まれる量

採否を決める読者へ、対象ファイル、該当箇所、観点、根拠、推奨する処置を提案ごとに示す。
未比較の削減候補は仮説として区別し、点検だけを依頼された場合は提案一覧を返して終了する。
既存の認可・安全性・要求充足を守る条件と、追加指示なしのモデルの動作で代替できる指示を区別する。

### 記述量の水準

対象は、エージェントが読み込む配布物と、その判定条件を実装した機械チェックスクリプトとする。
新規作成や改訂の際は記述量を現状の水準に保ち、既存の記述との重複統合（削除、統合、`references/`への分離）を常に検討する（努力目標。行数の上限は設定せず、自動チェックも行わない）。
`references/`への分離など記述を分割する方針を選ぶ前に、`design-heuristics.md`「設計品質の劣化確認」の観点 (f)に基づき、統合案や現状維持案と比較・検討する。
`<役割名>.parent.md`と`<役割名>.subagent.md`の役割分担は、`sub-agents.md`「`<役割名>.parent.md`と`<役割名>.subagent.md`の構成」に従う。

文体、表記、語調の統一には、lintによる自動チェックを主な手段として活用する。
エージェント向け文書は生成時の予防ガイドとして維持し、lintと重複する細則のうち細かすぎるもののみを削減する（自動検出後の書き直しのみに頼ると、指摘と修正の往復回数が増加するため）。

### 配置の階層

規範の文章量が作業に与える影響要因は、同一の取り決めが分散して同期箇所が増加することと、判断に不要な記述を起動時に読み込んで初期コンテキストを圧迫することの2点であり、削減対象はこの基準で選定する。総バイト数は補助的な指標として扱う。
記述は`agent-documents-basics.md`「置き場所と配送」の読込階層に沿って、その文書を読むエージェントや必要となるタイミングに合わせて配置する。
スキルのファイル数を減らしても常時読み込み量はほとんど削減されないため、起動ごとに毎回参照するわけではない記述を`references/`へ退避させることや、エージェント定義をスリム化することを優先して検討する。
スキルの統廃合はエージェントの起動手順に影響を与えるため、起動時の判断精度を向上させる場合に限って採用する。

### 削減の判定根拠

大きな削減では、同じ課題、初期状態、モデル、effort、起動パラメーター、評価基準で、削る前・削った後・対象文書なしの3条件を新しい文脈で試す（努力目標。課題の準備と複数回の実行に費用がかかるため）。
比較を実施した場合は、削った後が要件の充足と判断内容の両方で削る前と同等以上のときだけ採用し、劣った判断に対応する記述は戻す。
文書なしでも同等だった記述は、課題がその記述の対象状況を含むことを確かめて削除の候補にし、未試行の状況のための記述は残す。

ユーザーから常時規範の記述量削減を求められた場合は、指定されたファイル名にかかわらず、自動ロードされる常時規範全体を対象とし、努力目標の表記がない条文の削除も検討に含める。
移設先のスキルが存在しない場合は、新設して構わない。削減目標の数値は、ユーザーから具体的な指定があった場合のみ採用する。

削減や統合をする際は、以下のいずれかの根拠を満たすことを条件とする。

- SSOT違反: 他のファイルに正規の記述が存在し、該当箇所が単なる転記である場合。
- 自明導出: 上位の基本方針や一般的な知識から自然に導き出せる場合。
  細かな作法の記述を削る場合でも、明記しないと安定して考慮されにくい観点（セキュリティやエラー処理など）は代表的な用語を残し、硬い制約となる条件は具体的に記述する。一般的な知識から導けない固有の事実は自明導出に該当しない。
- 公式ドキュメント代替可能: 公式ドキュメントの一次資料を参照することで同等の情報を取得できる場合。
- 上位指針への統合: 個別の細則を束ねる上位の基本方針へ集約できる場合。同一工程の箇条書きが同じ節に並列で蓄積している場合も含む。
- 手段固定: 特定のコマンド、ツール、実行順序、パスなどが固定されており、その手段でなければ要件を満たせない理由が記載されていない場合。
- 個別事象特化: 特定の1件の事例、工程、識別子に依存した記述になっており、仕組み全体の一般的なルールへ抽象化できる場合。
- 過剰な手順化: エージェントが目的や前提知識から自律的に判断できる工程、確認事項、分岐、例外処理を細かく記載している場合（`writing.md`「読み手別の追加注意点」のエージェント向け文書の項を参照）。
- 条件の入れ子: 例外や除外が複雑に重なり、条件と取るべき行動とが一対一で対応していない場合。
- 拘束力の過剰: 技術的な不成立、データの破損、公開インターフェースの破壊、セキュリティ上の欠陥のいずれも防がない条文であるにもかかわらず、努力目標の表記なしで厳格に記述し、適用範囲や除外事項を細かく列挙している場合。

「個別事象特化」と「条件の入れ子」の基準は、文書を執筆する際にも`writing.md`「文章の共通規定」の限定の項として適用する。

数値、閾値、境界値の根拠（設定理由、境界を分ける根拠、トレードオフ）は削減の対象外とする。
削減によって規範としての拘束力が損なわれる場合は、他の節で代替できるかを確認し、代替できなければ元の記述を残す。文章の圧縮や統合をする際は、元の規定が持つ順序の制約、前提条件、除外条件を維持し、`writing.md`「日本語の書き方」に従って主語と述語の関係や動詞の意味を崩さないように確認する。

### 保護対象

文章の圧縮、統合、削除をする場合でも、以下の要素は必ず維持する。短縮後も前後の文脈から意味や関係性を明確に読み取れる状態を保つ。

- 本文冒頭の目的記述（適用要否を判断する根幹となる動機）
- 開かれた列挙表現（「等」「〜を含む」「〜など」）。閉じた表現に書き換えると適用範囲が狭まるため維持する
- 同一ファイル内の既存表記と統一すべき用語、および並列表現の対称性
