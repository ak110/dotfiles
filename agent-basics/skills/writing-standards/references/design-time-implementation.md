## 実装方針の選択

- 機能の実装にあたっては必要性をあらかじめ検証し、言語標準の機能や既存の依存ライブラリの活用を優先して、独自実装は最後の選択肢とする。
  代替案の比較検討は`design-heuristics-proportionality.md`「問題と手段の比例性」に従う。
- 標準仕様が定義されているフォーマット（YAML、JSON、TOMLなど）については、その一部だけを解析するような独自パーサーを作成せず、公式や実績のある正規パーサーを用いて読み書きする。
  独自パーサーでは、複数行文字列や入れ子構造といった正当な入力を正しく解釈できずに誤った動作を引き起こす恐れがあるためである。
- 集計値の判定条件や、複数の入力形態が想定される解析処理（正規表現、パーサー、突き合わせ条件など）を設計する際は、対象の命名規則や出力仕様が生成し得るすべての入力形態を事前に洗い出して確定する。
  構造化データ（frontmatterやJSONなど）は構造を正しくパースした結果を根拠とし、条件に一致しなかった対象についても個別に検証して、抽出漏れと誤判定による過大計上の両方を防止する。
  既存の解析ロジックを変更する場合は、変更前後の動作をすべての入力形態に適用して比較し、変更前に正しく取得できていた情報が意図せず失われるような案は採用対象から除外する。
  意図的な除外である場合は、その理由を計画書や変更の説明文に明記する。
- 公開仕様に準拠したパーサーを実装する際は、利用可能な公式参照実装と出力を突き合わせて仕様への適合性を確認する（努力目標）。
- 自動承認処理やポリシー判定に用いる解析処理を新規作成または変更する前に、入力の生成主体、信頼境界、通常の正常入力、対象外とする入力、誤判定（誤許可・誤拒否）による影響を明示し、実装およびテストで用いる入力データの集合をこの定義に適合させる。
  定義されていない脅威モデルを暗黙の要件として独断で追加することを禁止する。
