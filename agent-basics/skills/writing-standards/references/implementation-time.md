## 編集前の読解

- 編集対象ファイルは編集前に全体を読む（部分読解はスタイル逸脱とリファクタリングの必要性を見逃す）。実装の仕様は実装本体から確定し、docstringは補助として扱う

## 記述順序と命名

- 上位から構造をたどれる順序で関連する定義を近くへ置き、追加先の命名と用語を既存規約へそろえる（努力目標）

## 言語横断のツールと構文

プロジェクトに指定が無い場合は、次の標準ツールを使う。

| 言語 | 依存管理・ビルド | lint・format・補助ツール |
| --- | --- | --- |
| Python | `uv` | `pyfltr`、`pytilpack` |
| TypeScript | `pnpm`、一度限りの実行は`pnpx` | `Biome`。未対応ルールが必要な場合だけESLintとPrettierを併用 |
| Rust | `cargo` | `cargo clippy -D warnings`、`cargo fmt` |
| C# | `dotnet` CLI | `dotnet format`、Roslynアナライザー、`Microsoft.CodeAnalysis.NetAnalyzers` |
| Bash | 該当なし | `shellcheck`、`shfmt` |
| PowerShell | 該当なし | PSScriptAnalyzer |

公開互換性として宣言した範囲で使える新しい言語機能を積極的に使う。
利用可否は対象プロジェクトの言語バージョン（Pythonの`requires-python`、TypeScriptのバージョン、Rustの`rust-version`・edition、C#の`LangVersion`・`TargetFramework`など）と公式リリースノートで確かめる。
受理の判定には宣言された全対応版を用いる。

- Python: <https://docs.python.org/3/whatsnew/index.html>
- TypeScript: <https://www.typescriptlang.org/docs/handbook/release-notes/overview.html>
- Rust: <https://doc.rust-lang.org/releases.html>
- C#: <https://learn.microsoft.com/dotnet/csharp/whats-new/>

同等の品質で代替できる場合は外部依存より標準ライブラリを選ぶ（比べる順序は`design-time.md`「実装方針の選択」）。
プロジェクト固有の規約はそのプロジェクトの`CLAUDE.md`・`.claude/rules/`へ置く。

## コメントの記述粒度

- コメントは意図・成立条件・非自明な理由を残し、冒頭は役割と適用範囲、局所は実装の判断を説明する（努力目標。自明な処理は再掲を避ける）
- 実装の判断根拠となる外部の挙動と観測値は、観測した原文のまま残す（失うと後続の変更が分岐の成立条件を判定できない）。規範は安定したファイルと節、観測は再現条件、ユーザー要望は恒久的な要件か外部挙動へ変換して書き、セッション、個人、対話の経緯は手元の記録にとどめる
- コード上に現れる設定値・数値リテラルそのものはコメントへ埋め込まず、選定理由と制約の根拠だけを書く。コード上に現れない値や別の出所を持つ値で判断根拠に要るものは、出所とともに書く
- 同じ概念の説明は呼出関係の起点へ集約する
- ドキュメントは現在の状態を直接書き、履歴はコミットメッセージへ委ねる（努力目標）。過去の挙動が現在の判断の根拠となる場合は、その挙動を現在の記述へ含める

## データと計算

次の観点を想起する。文字エンコーディングは`encoding.md`が定める。

- 計算量: 入力規模に合わせる
- 浮動小数点: 正確さが要る計算は整数か十進型、等値比較は許容誤差
- 乱数: 標準API、予測できないシード、範囲変換の専用API、セキュリティ用途はCSPRNG
- 整数オーバーフロー: 検出付き演算・広い型・事前の範囲検証。意図的なラップアラウンドは言語仕様で保証された演算か専用のwrapping演算で表す

- 日時は意味を区別し、プロジェクト方針が無ければタイムスタンプはUTC、市民時刻はタイムゾーン情報を保持する。CLI引数など外部から受け取るタイムゾーンの無い時刻の扱い（拒否するか、どのタイムゾーンとみなすか）は入力の意味から決めてヘルプへ書き、内部データ向けの解析処理の扱いを流用しない（手で書いた値をUTCとみなすと、境界がずれた結果を該当0件と区別できない）
- hashや識別子の入力に複数の可変長値を連結する場合は、長さ接頭辞か一意な正規形式で境界を一意にし、異なる分割が同じ入力列にならない反証ケースをテストする
- 更新時刻とサイズの一致を内容不変の代わりに使う場合、更新時刻の精度はファイルシステムが決め（1秒や2秒の環境がある、単位がナノ秒でも精度は別）、精度の範囲内で同じサイズのまま書き換えた変更は検出の対象外になる。更新時刻から精度の幅以上が過ぎてから読んだ結果だけを再利用する

## リソースと並行処理

- 資源の所有と解放を対応させ、RAII等で寿命を管理する。子プロセスを時間上限や停止要求で止める場合は、停止を要求する前に子が起動した子孫を列挙し、子と子孫を全て終了させる。全ての終了を確かめてから、出力の記録や終了状態などの結果を確定する
- 共有状態を減らし、残る共有には同期を設ける。I/O待ちは非同期処理を基本とする

## セキュリティ・ロギング・エラー処理

- セキュリティ: 信頼境界（外部入力・API応答・ユーザー操作など）を常に意識する
  - 外部入力はコマンドの引数として渡し、評価系コマンドが受け取るコードは固定する。動的な実行が要る場合は固定候補へ分岐する（言語別の書き方は各言語の資料）
  - 入力検証は許可リスト方式を優先し、実行・解釈文脈（SQL・コマンド・HTMLなど）への直接結合、パストラバーサル、信頼できないデータの安全でない復元を避ける
  - シークレットはソースコードとログの外に置き、権限は必要最小限にし、内部情報（スタックトレース・内部パスなど）をエンドユーザーへ露出しない
- ロギング: 障害時の原因究明を前提に書き（構造化ログ、相関ID）、シークレットと個人情報を出力しない
- エラー処理: 例外の種別ごとに方針を決める。一時的エラーは指数バックオフとジッタでリトライし、永続的エラーは即座に原因を返し、プログラマエラーはfail-fastで伝播させる。catchは具体的な型に限り、広域キャッチは境界層に限る。リトライ回数・タイムアウトは設定可能にする
  - 失敗の原因を報告する前に後始末の時間制限付き待機が超過する場合は、その例外を捕捉して待機対象の強制終了と回収を終えてから原因付き報告へ戻す。同じ待機が複数箇所にあれば停止・待機・回収を1つの関数へ集約する（後始末の例外が元の失敗報告を置き換えると、呼び出し元が原因を判定できない）
  - 外部状態の取得失敗時に安全側の結論（中止・延期など）を採用する判定では、先に保護対象への到達可能性（判定結果へ実際に影響する所有権・権限・アクセス境界などの条件）で母集団を定め、母集団内の取得失敗だけを根拠とする。
    そのうえで、実環境の入力でその結論が常時成立しないことを実物で確かめる（無関係な対象の取得失敗で結論が常時成立すると、機能が恒久的に止まる）

## 依存と自動生成物

- 依存と設定は専用CLIを優先し、lockとmanifestを一致させる。生成物は生成元か専用CLIから更新し、直接編集が要ると判断しても先に生成元側の設定で表現できないかを検討する
- 既存コードの意図的な制約（型制約・アクセス制限・lint設定・不変条件のアサーション等）は新規コードでも維持し、変更する場合は先に必要性を検証する

## lintと機械チェック

- lint指摘への対応方針は`quality-principles.md`「QCDと3段判定」のQCD（Qualityを先に守り、その範囲でCostとDeliveryを比べる）で決める。本節をlint対応の原則の定義の所有者とし、抑制の採否もエージェントが技術判断として確定する
- 正当な指摘は修正し、意図した設計に当てはまらない指摘だけ必要な範囲で抑制し、理由が自明でなければ併記する。振る舞いを変えず指摘だけを回避するコード変更は避ける。抑制を新たに加えるときは、既存の抑制コメントの有無と独立に判断する
- ファイル・設定単位の緩和（ファイル全体の上限抑制を含む）は、方針との不一致か反復する抑制があって局所の対処で足りない場合に限り、後続の違反も見逃す影響を評価する。過大化が原因なら責務やシナリオでの分割を優先する
- lintルール・機械チェックを新規に有効化・強化する変更では、着手前に既存コードへの検出結果を「是正対象」と「意図的な設計による許容対象（理由付き抑制等）」へ件ごとに振り分ける工程を含める。`pylint`の`duplicate-code`では、同期・非同期の並行実装やプラットフォームペア実装の類似が許容に当たり得る
