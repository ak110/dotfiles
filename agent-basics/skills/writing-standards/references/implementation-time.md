# 実装時のコーディング品質

コードを編集する時の読解、書き方、データ、資源、セキュリティとエラー処理、コメント、lintの基準を定める。
主に原則9（`agent-basics:writing-standards/references/quality-principles-subtraction.md`）を実装へ適用する。
セキュリティ、資源、エラー処理の節は原則4（`agent-basics:writing-standards/references/quality-principles-constraints.md`）の適用である。

## 編集前の読解

- 編集するファイルは、編集の前に全体を読む（一部だけを読むと、全体の書き方から外れ、整理の必要に気付けなくなる）。
- 変更が1つの定義（関数、定数、テストなど）の中に閉じる時は、次を読めば編集へ進める。
  差分が参照する定義、同じファイルの共有の準備処理と既存の補助関数（識別子で検索する）、影響を受ける利用箇所、書き方が分かる周辺である。
- 複数の定義の構成を変える時と、読んだ範囲に重複や不整合を見つけた時は、全体を読んでから編集する。
- 正確な仕様はコード本体から読み、docstringは補助として扱う。

## 記述順序と命名

全体の構造を上位からたどれる順に並べ、関連する定義を近くに置く。
新しい名前と用語は既存コードの命名規則に合わせる（努力目標。後のレビューで直せる）。

## コードの簡潔さ

- 依頼に無い入力形式、オプション、フォールバックは足さず、価値があれば提案する。
  範囲を限る是正は[変更の範囲](quality-principles-subtraction.md#変更の範囲)の3通りで判断し、今回足した処理を消す代わりに拒否・警告を足さない。
  拒否が必要なのは、拒否を求められたか、既存の経路でその入力が誤った結果やデータ破損を起こす場合である。
  信頼境界では目標の状態が受け付ける入力を検証する。
  依頼で具体的な入力が渡された場合は、公開された呼び出しでその入力を処理し、構文検査の成功だけを動作の証拠にしない。

- 1か所からしか呼ばない補助関数は、先回りで切り出さずに呼び出し箇所へ書く。
  再利用される処理、複雑な境界を隠す処理、実在の概念を名指しして呼出側を読みやすくする処理は切り出してよい。
  同じ理由で変更される重複の共通化は、`agent-basics:writing-standards/references/design-heuristics.md`「責務帰属（SRP）分析の観点」に従う。
- 検証や補足の分岐が多い関数は、主処理を正常系の流れとして書き、補助関数を主処理の後ろに置く。
- returnで抜けた後のelseを省いて分岐を平らにし、条件で値を変えるだけの再代入は三項演算子やif式による1回の束縛にする。
- 一度しか使わない値は、変数名が単位、役割、判定の意図を式以上に加える時だけ変数にし、それ以外は使う箇所に式を書く。
- 内部の引数や選択肢は、全呼出側で固定される値、所有者が導出できる値、未使用の選択肢を整理し、同じ変更で内部の呼出側を移して旧来の呼出し方を撤去する。
  人間が使うCLIや設定など公開契約の存廃は、互換性と認可の基準で決める。
  整理に伴ってテストを統合する時も、別の異常条件、安全性、並行性を確かめる試験は残す。
- 型は必要を満たす最も単純なものにし、緩い型のために非null表明、型変換、「起きないはず」の例外が要る箇所だけを強める。
- 意味の違うID（ユーザーIDと注文IDなど）が同じ基本型で表され、取り違えを防ぐ必要がある時は、言語の手段（TypeScriptのブランド型、他の言語のnewtypeなど）で型を分ける。
- 型の分からない外部の値と、型で区別した値は、作る時か受け取る境界で一度だけ検証し、内側ではその型を信頼する。
  スキーマ、コンストラクター、内部の型が保証する値を、内側で検証し直すのは避ける。
- 外部のCLI、SDK、サービスの出力は、自分が所有する保存形式と分けて扱う。
  外形と選別に使う欄を先に確かめて利用対象を選び、利用時の制約はその対象の利用欄にだけ課す。
  未利用の項目や未知の追加欄の形式差は主機能を失敗させる理由から外し、利用対象の欠落や不正、相関識別子の不一致、安全性や完全性の不成立は診断できる失敗にする。
  試験では対象外の項目の欠落・変形と、正常・不正な利用対象を混ぜ、選別の前に利用時の制約を課していないことを確かめる。

## データと計算

- 計算と外部入出力を分ける関数境界は、`agent-basics:writing-standards/references/design-heuristics.md`「責務帰属（SRP）分析の観点」に従う。
- 状態の表現と所有者: 排他的な段階を型へまとめる条件は `agent-basics:writing-standards/references/design-data-interfaces.md`「状態と業務ルールの条件」に従う。
  型に閉じるデータと更新の契機を確かめ、他の段階からの参照や所有者以外からの直接の書き換えを除く。
  独立した軸は別の状態として保ち、OS、ファイル、外部サービスなど別の主体が一次の状態を持つ値は、その主体から読む。
  型の明示と、並行更新や複数資源の原子性は別の問題として扱い、遷移条件の検査と更新は同じ排他の範囲で行う。
- ハッシュと識別子の生成: 複数の可変長データを連結して入力にする時は、長さの接頭辞か一意な正規化形式で境界を確定し、分割位置の違う入力が同じ値にならないことをテストで確かめる。
- ファイルの同一性判定: 更新時刻とサイズの一致で内容を不変とみなす時は、更新時刻の精度がファイルシステムごとに異なる（1秒や2秒単位があり、ナノ秒の項目を持っていても粗い場合がある）ことを前提にする。
  精度の範囲内で同じサイズのまま書き換えた変更は検知できないため、更新時刻から精度以上の時間が過ぎた後に得た判定だけを再利用する。

### 日時処理

- 現在時刻に依存する計算・判定には、呼出側で取得した基準時刻を渡せるようにする。
  時刻の省略を許す関数では呼出時の実時計を使い、同じ基準を使う一連の判定には値を取り直さずに渡す。
  純粋な計算が時刻を必須入力として受ける設計でもよい。
  JavaScriptは引数を省いた時の式を呼出時に評価し、Pythonは関数定義時に評価する。
  Pythonでは省略した時の値を`None`とし、必要なら関数の中で時刻を取る。
- 判定に渡す固定時刻と、待機・再試行で進む時計は区別する。
  試験で進行を制御する必要がある時は時計やタイマーを差し替え、固定時刻を渡したために待機が進まない設計を避ける。
  経過時間には壁時計ではなく単調増加する時計を使う。
- 固定した時点、現地日時を守る将来の予定、繰り返しの予定、日付だけの値を区別する。
  プロジェクトに方針が無ければ、タイムスタンプはUTCで統一し、市民時刻（実生活の時刻）はタイムゾーンの情報を保つ。
- 将来の予定では、現地日時と地域のタイムゾーン識別子を保つ必要があるかを確かめる。
  固定のUTCオフセットはUTCとの差を表すだけで、地域の制度変更は地域識別子の規則で扱う。
  夏時間などの制度変更やタイムゾーンデータの更新の後も意図を保つため、派生したUTCの値を再評価するかと、その時機を決める。
- 存在しない現地時刻と重複する現地時刻、現地時刻基準の反復と固定の経過時間の違いを扱い、境界での解釈と保存形式は対象の契約から選ぶ。
- CLI引数などでタイムゾーンの指定なしに受け取る時刻は、入力の役割からエラーにするか特定のタイムゾーンとみなすかを決め、ヘルプに書く。
  この入力に内部データ用のパース処理を流用するのは避ける（手入力の値をUTCとみなすと日付の境界がずれ、検索結果が0件になる）。

## リソースと並行処理

- 資源の確保と解放を対応させ、RAIIなど言語の仕組みで生存期間を管理する。
- 子プロセスをタイムアウトや停止シグナルで止める時は、停止を指示する前に子孫のプロセスを全て列挙し、子と子孫の全てを終了させる。
  全ての終了を確かめてから、出力の記録や終了状態などの最終結果を確定する。
- 共有状態を減らして共有する箇所には排他制御か同期を置き、I/O待ちのある処理は非同期処理を基本にする。

## セキュリティ・ロギング・エラー処理

- 外部からの入力、APIの応答、画面の操作など、信頼境界を意識して扱う。
  外部入力はコマンドライン引数として渡し、コード文字列を評価する実行には固定の文字列か、定義済みの固定の候補から選んだ値だけを渡す。
- 入力の検証は許可リスト方式を優先し、解釈される文脈（SQL、シェル、HTML）への文字列結合、パストラバーサル、信頼できないデータのデシリアライズを避ける。
- 秘匿値（パスワード、APIキーなど）はソースコードとログの外に置き、権限は必要最小限にし、スタックトレースや内部のパスはエンドユーザーの画面の外に留める。
  セキュリティ用途の乱数（トークン、鍵など）は暗号論的擬似乱数生成器（CSPRNG）で作る。
- ログは障害の原因究明を前提に構造化ログと相関IDで設計し、秘匿値と個人情報を含めるのは避ける。

### 認証CookieとCSRF防御

- Cookie認証のWebアプリでは、セッションCookieに`HttpOnly`・`Secure`・`SameSite=Lax`か`Strict`を付ける。
  Domain属性は省き、ログインの時にセッション識別子を更新する。
- Cookie名は、指定が無ければ`__Host-`接頭辞（`Path=/`）を付け、別のサブドメインからの上書きを防ぐ。
  既存環境での改名の方式は、サブドメインの管理範囲と再ログインなどの負担から選ぶ。
- `SameSite=None`の設定、CSRFやOriginの検査の無効化、他サイトからの埋め込みの許可などで標準の防御を外す時は、代わりの防御を置く。
  代わりの防御はCookieが届く全てのエンドポイント（更新の要求と埋め込みの表示を含む）へ置き、その範囲をテストで固定する。
  新しいエンドポイントにも追加の設定なしで防御が働く構造（同一オリジンの制限など）にする。

### 例外の捕捉と縮退

- エラーの性質と利用目的から回復の方針を選ぶ。
  恒久的なエラーは呼出側へ原因を返し、プログラム自体の不具合は早期失敗（fail-fast）で例外を伝える。
- 例外を捕捉するのは、その場で回復する時、原因を判別できる文脈を付けて再送出する時、公開境界や信頼境界で別の失敗表現へ変える時に限る。
  回復には、要件か観測した欠陥を根拠とする再試行と、別の処理方法への切替えを含む。
- 捕捉は具体的な型に限り、全ての例外を捕捉する処理はシステムの境界に置く。
  具体的な型でも、ログを出して続行するだけの処理、決めた値や空の値で失敗を隠す処理、そのまま再送出するだけの処理は避け、例外を伝える。
  CLIが個別のエラーを捕捉して続行し、終了コードで失敗を示す処理は、境界での変換に当たる。
- 補助機能が、エンドユーザーが制御できない要因（外部の出力の変動など）で失敗し、主機能まで止めると作業を妨げる時は、縮退を設ける。
  縮退では主機能の入力、必要な成果、安全性、所有権を保ち、使えない補助機能を明示して無効にし、所有する資源を回収する。
  縮退は回復に含め、不可欠な処理の不正やプログラムの欠陥を隠す用途は対象から除く。
- 失敗の種類に合う回復（一時障害の解消を待つ、引数を直す、必要な資料を取得するなど）を選び、権限の拒否は必要な認可の手続きへ渡す。
- 再試行を足す・変える時は`agent-basics:writing-standards/references/design-runtime.md`「非同期ジョブ・リトライ設計」に従う。
- 終了処理の待ちがタイムアウトした時は、その例外を捕捉して強制終了と資源の回収を終えてから、本来の失敗の原因を報告する。
  同じ終了待ちが複数箇所にある時は、停止・待機・回収を1つの関数にまとめる（終了処理の例外が本来のエラーを上書きすると、呼出側が原因を判別できなくなる）。
- 外部の状態の取得失敗を理由に安全側の結論（中止や延期）を採用する処理では、保護する対象への権限、所有、境界の条件から判断に要る母集団を先に確定し、その母集団の取得失敗だけを根拠にする。
  その結論が運用環境で常に成立してしまわないかを現物のデータで確かめる（無関係な対象の失敗を根拠にすると、システム全体が恒久的に止まる）。

### 外部呼び出しの時間予算

- 外部のHTTP、DB、メッセージキュー、LLMのAPIなどでは、SDKのデフォルト値を確かめ、待ち時間（接続、読取、プール取得）と再試行を含む操作全体の時間予算を利用目的に合わせる。
  ストリーミングと長時間のジョブでは無通信の上限と処理全体の寿命を分け、運用で調整する回数とタイムアウトは外から設定できるようにする。
- エンドユーザーの環境で動く処理の時間上限は、遅い環境で同じ処理を正常に終えた所要に余裕を加えて決め、再試行と後始末を含む最長の待ち時間が利用目的に見合うかを確かめる。
  自動検証で遅延を検出する上限が求める値と異なる時は、エンドユーザーを守る上限と遅延を検出する上限を別に設ける。

## コメントの記述粒度

コードコメントは原則として書かず、名前、型、構造、lintやテストで制約を表す。
残すコメントは次の5種に限る。

- ツールや実行系が解釈する指示（shebang、PEP 723、エンコーディング宣言、Userscriptメタデータ、実行時に参照するdocstringなど）。
  lint、型、整形、カバレッジの抑制は正しさや安全性を隠さず、必要な範囲に限る。
  抑制の規定が理由を求める場合は、解除時に必要な理由だけを添える。
- 安全性の根拠（例: `// SAFETY:`）。
- 型やlintで強制できない複数箇所の連動先や相互参照。
- OS、外部ツール、プロトコル、依存先など、自分たちでは変えられない制約と回避に必要な情報。
  外部制約による依存の上書きでは、理由と解除条件を含む。
- ライセンスと著作権の表示（例: SPDX）。

## 依存と自動生成物

- 自動生成ファイル（ロックファイルを含む）は、生成元の定義ファイルか専用のCLIから更新し、直接の編集が要ると判断した時も生成元の設定で対応できるかを先に確かめる。
- 既存コードの意図的な制約（型定義の制約、アクセス制限、lintの設定、不変条件のアサーションなど）は新しいコードでも保ち、変える時は事前にその妥当性を確かめる。

## lintと機械チェック

lintの指摘への対応は原則2（`agent-basics:writing-standards/references/quality-principles-qcd.md`）で決め、抑制を採用するかもエージェントが技術判断として確定する。
指摘やエラーを受けた時は`agent-basics:bugfix`を起動して対処する。

- 正当な指摘はコードを直して解消する。
  意図した設計で直すべきでない指摘だけを必要な最小の範囲で抑制し、理由が自明でなければ抑制のコメントに書く。
  振る舞いを変えずに警告だけを避ける書き換えは避け、新しい抑制は既存の抑制の有無によらず個別に判断する。
- ファイルの行数の上限を検査するプロジェクトで超過が報告されたら、同じ作業の中で分割、統合、削除によって検査が示す整理後の行数以下にする。
  数行を削って上限の直下へ戻す対応と、行数だけを基準にした前後の分割は避け、主題のまとまりで分ける（上限の直下に戻すと、次の追記で再び超える）。
  整理は超過を生んだ作業に含め、整理のcommitは本来の変更のcommitと分ける。
  行数の測定、見積もり、削減は、検査が超過を報告したファイルだけで行う（計画の起草と上限以下のファイルは対象外。数値は検査の設定と診断が示す）。
- ファイル単位や設定全体でのルールの緩和（行数の上限の引き上げなど）は、プロジェクトの方針と合わない場合か、個別の抑制では対応しきれない場合に限る。
  緩和で検出されなくなる違反と将来の見逃しの影響を確かめてから行い、肥大が原因なら責務やユースケースでのファイルの分割を先に採用する。
- 新しいlintルールや静的検査を有効にする・強める変更では、着手前に既存コードでの検出結果を、直す対象と、意図した設計として理由付きで抑制する対象へ1件ずつ分ける。
  例えば`pylint`の`duplicate-code`では、同期版と非同期版の並行実装や、プラットフォームごとの対の実装の類似が、正当な許容の対象になりうる。

### 根本目的（緩和判断の基準）

文章とMarkdownのlint設定（`textlint`、`markdownlint`、`pyfltr`の推奨設定例など）の緩和、無効化、除外の追加は、そのルールが次の目的のどちらかに寄与するかで判断する。

- LLMに特有の文体の癖を除き、書き言葉として自然で読みやすい日本語を保つ（`preset-ja-technical-writing`の各ルール、`pyfltr`内蔵の`colloquial-check`など）。
- Markdownとして意味の正しい記法（強調、コードブロック、見出しの階層）を保つ（`markdownlint`の`MD022`、`MD031`、`MD040`など）。

### 緩和判断のフレーム

- 緩和する警告が現在の版で再現するかを、ルールの個別の実行（`textlint --rule <name>`、`markdownlint --rules <name>`など）で確かめる。
  再現しない警告を緩和すると、不要な除外だけが残る。
- ルールが何を防ぐかを公式の説明で確かめ、根本目的を支えるルールなら、設定の緩和や行単位の無視コメントに頼らず文章を直す。
- ルールが文を硬くする方向（平易な和語を漢語に置き換える、中黒で名詞をつなぐ、条件を1文に詰めるなど）へ誘導する時は、閾値の変更か対象の除外を検討する。
- ルールの完全な無効化は、ツールの仕様上避けられない誤作動がある時に限る（例: コード識別子のドットを句点と誤認して自動置換する）。
- 緩和の手法と範囲は本書「lintと機械チェック」に従い、確定したら、そのルールに触れる運用ガイドの記述も同じ変更で設定と合わせる。
- ユーザーが緩和を指示した時は、手元の観測が指示の理由と合わない場合も指示に従い、観測した事実を計画に記録する。

### pyfltr推奨設定例への反映

`pyfltr`の推奨設定ガイドへ反映する時も同じ基準で既存の推奨設定を見直し、緩和する箇所の根拠（根本目的に寄与しない、仕様上避けられないなど）を設定ファイルのコメントに書く。

## 言語横断のツールと構文

プロジェクトに指定が無ければ、次の標準ツールを使う。

| 言語 | 依存管理・ビルド | lint・format・補助ツール |
| --- | --- | --- |
| Python | `uv` | `pyfltr`、`pytilpack` |
| TypeScript | `pnpm`（一度限りのツール実行は`pnpx`） | `Biome`（Biomeが未対応のルールが要る時だけESLintとPrettierを併用） |
| Rust | `cargo` | `cargo clippy -D warnings`、`cargo fmt` |
| C# | `dotnet` CLI | `dotnet format`、Roslynアナライザー、`Microsoft.CodeAnalysis.NetAnalyzers` |
| Bash | 該当なし | `shellcheck`、`shfmt` |
| PowerShell | 該当なし | PSScriptAnalyzer |

- 宣言した互換範囲（Pythonの`requires-python`、Rustの`rust-version`とedition、C#の`LangVersion`と`TargetFramework`など）で使える新しい言語機能は積極的に使う。
  使えるかは公式のリリースノートと比べ、サポート対象の全ての版で動くかで判断する。
- 同等の品質を実現できるなら、外部パッケージを足すより標準ライブラリを使う。
