# 依存管理

本書では、パッケージやライブラリなどの依存関係の採用・追加・更新、バージョン指定方法、公開待機設定、およびロックファイルの運用基準を定める。これにより、サプライチェーン攻撃への対策とセキュリティの維持を図る。
依存の追加や更新を専用CLI（`uv add`、`pnpm`、`mise`など）で行う基本原則は`implementation-time.md`に従う。

## バージョン指定と更新

- 新たに依存を採用する際は、将来にわたる保守性や代替手段の有無を慎重に検討し、不要となった依存関係は速やかに整理する。
- 依存更新コマンドを実行しても対象パッケージが更新されずエラーも出力されない場合は、更新先のバージョンを明示的に指定して再実行し、依存解決エラーの出力ログから更新を阻害している制約元を特定する。
- 依存の上書き設定（`[tool.uv] override-dependencies`など）は、そのリポジトリ内での依存解決にのみ有効であり、作成される配布物のメタデータには反映されない。エンドユーザー環境へ波及する脆弱性は上書き設定で回避せず上流パッケージの修正リリースを待つ。開発環境のみで使用する依存関係に限定して上書きを適用し、いずれの場合も設定理由と解除条件をコメントとしてコード内に残す。
- 依存の追加や更新時に出力される警告メッセージにはすべて目を通し、仕様変更や非推奨化への対応要否を判断する。

## 公開待機設定

- バージョンを厳密に固定する運用は更新管理の負担が大きいため原則として採用せず、公開されたばかりの新しいバージョンを一定期間（目安として1日程度）待機してから取り込む設定を活用する。
  監査記録は`docs/development/audit-records.md`の「agent-basics/skills/writing-standards/references/dependency-management.md：公開待機設定：2026年9月16日」にある。
  なお、本項はパッケージマネージャーが解決する依存関係を対象としており、コンテナーのベースイメージやCIの外部actionについては`dockerfiles.md`および`github-actions.md`に従う。
- パッケージが公開された直後のバージョンを一定期間だけ解決対象から除外する仕組み（uvの`exclude-newer`、pnpmの`minimum-release-age`、miseの`minimum_release_age`など）を「公開待機設定」と呼ぶ。
  この設定が有効な環境では、自身がリリースした直近のパッケージも含めて解決対象から除外されるため、待機期間に満たない最新バージョンを下限として要求すると、ビルドやCIで直近の自前リリースを取り込む処理（コンテナー内での`uv tool install`など）が失敗する。この事態には以下のいずれかの方法で対処する。
  - プロジェクト設定において対象パッケージを個別に除外する（uvでは`pyproject.toml`の`[tool.uv]`配下に`exclude-newer-package = { 自パッケージ名 = false }`と記述する）。
  - 対象の処理ステップ（Dockerfile内の特定の`RUN`命令など）に限り、環境変数を使って公開待機設定を一時的に無効化する。
  - ローカル環境でビルドした成果物（wheelファイルなど）を直接渡してインストールする。
  - 待機期間の経過とパッケージインデックスへの反映（CDNのキャッシュ更新など）を待ってから依存解決を再確認する。配布物自体の依存下限バージョンを公開直後のバージョンへ引き上げる場合は、この方法を選択する。
  - 配布物の作者自身が提供しているパッケージを、プロジェクト外部から実行するコマンド（`uvx`など）で要求する場合は、待機する代わりにコマンドの起動引数でそのパッケージのみを除外対象として指定する（uvでは`--exclude-newer-package <パッケージ名>=false`）。そのパッケージが依存している他の外部パッケージには、引き続き通常の公開待機設定が適用される。
- パッケージ単位の除外設定を記述する場所は、コマンドの実行形式に応じて判断する。プロジェクト全体の依存解決では`pyproject.toml`の`[tool.uv]`に記述し、`uvx`のようにプロジェクト設定を読み込まない単発コマンドではコマンドライン引数で指定する。
  ユーザーごとのグローバル設定（uvでは`~/.config/uv/uv.toml`など）に除外設定を記述することは避ける。uvはグローバル設定の除外内容を各プロジェクトの`uv.lock`内（`[options.exclude-newer-package]`）に記録してしまうため、意図せず無関係なプロジェクトのロックファイルまで変更され、同じグローバル設定を持たない環境で`uv lock --check`が失敗する原因となる。

## 配布物の版指定の検証

- 配布物がエンドユーザー環境のパッケージマネージャーに渡すバージョン指定を変更する場合は、リポジトリへの統合前に、エンドユーザーと同じ解決手段および配布予定の公開待機設定を用いて変更後のバージョン指定を解決し、終了コードが正常であることを確認する。
  たとえばuvの場合は、プロジェクト外のディレクトリで`uvx --exclude-newer "<配布する待機期間>" --from '<変更後の版指定>' <コマンド> --version`を実行して検証する。
  `uvx`、`uv tool install`、`uv run --script`、`uv run --no-project --with`などのコマンドはプロジェクト固有の`[tool.uv]`やロックファイルを参照せず、実行環境のユーザー設定に基づいて依存を解決する。そのため、プロジェクト内での`uv lock`、`uv sync`、`uv run`の成功や、ロックファイルへの反映、インデックスへの公開、テスト用リゾルバーでのテスト通過だけでは十分な根拠とならない。
  解決に失敗する場合は、「公開待機設定」における依存下限引き上げ時の対処手順を適用してから統合を進める。

## Python対応版の追加

Pythonの対応バージョンを新しく追加する場合は、対象となるPythonバージョンやCIのOS・CPUアーキテクチャで導入される依存パッケージを特定し、採用されるwheelの互換性や、ソース配布（sdist）からビルドされる依存のビルド要件を確認する。ローカル環境のwheelキャッシュによって同期が成功したとしても、キャッシュが存在しないクリーンなCI環境でのビルド成功を保証する根拠にはならない（観測した同一環境下でのみ成立した記録として扱う）。
互換性のある事前ビルド済みwheelが提供されているバージョンへ更新する案と、CI環境に必要なツールを整えてビルドを成立させる案を比較検討する。コンパイラーやC言語ヘッダーの追加は対象パッケージのビルドに真に必要な範囲に限定し、対象環境で導入されない依存パッケージはマーカーやextrasの指定に基づいて判断対象から除外する。
採用したパッケージバージョン、Pythonバージョン、CIイメージとアーキテクチャ、配布形式、検証実施日、および再検証手順を記録に残す。観測記録の例は`docs/development/audit-records.md`「agent-basics/skills/writing-standards/references/dependency-management.md：Python対応版の追加：2026年10月10日」にある。

## 脆弱性の確認

- ソフトウェア構成分析（SCA）ツールを用いて、依存パッケージの脆弱性を定期的に監査する。

## ロックファイルの運用

- CIやMakefileによるビルド処理では依存解決を再実行せず、既存のロックファイルをそのまま利用する。環境変数を用いて一括で固定モードを適用し（uvの`UV_FROZEN=1`、pnpmの`--frozen-lockfile`など）、依存更新する専用コマンドの実行時のみ一時的に固定を解除する（開発者個人のシェル環境変数としては恒常的に設定しない）。
- 依存ロックファイルは自動生成される成果物として扱い、手作業で直接編集することは行わない（`implementation-time.md`を参照）。

## pnpm

- `packageManager`フィールドにはSHAハッシュ値を付与して保持し、更新時には`corepack use pnpm@<version>`を実行する。
- pnpmの特定バージョンでは`NPM_CONFIG_*`環境変数の読み取りが不安定であり、`pnpm config get`が環境変数の値を無視する事象が観測されている。そのため、環境変数経由での設定反映を確認する際は`npm config get`を用いる。
  監査記録は`docs/development/audit-records.md`の「agent-basics/skills/writing-standards/references/dependency-management.md：pnpm：2026年9月16日」にある。
- `pnpm-workspace.yaml`内の設定項目は、`NPM_CONFIG_*`環境変数による指定よりも優先して適用される。
