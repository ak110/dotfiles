# 依存管理

依存パッケージ、コンテナーイメージ、言語処理系、CIや自動ビルドが取得するツールとaction（以下、外部部品）の版の選び方と更新、公開待機、ロックファイル、配布物の検証を定める。
最新版への追従とサプライチェーンの保護を両立させる。
原則9（`agent-basics:writing-standards/references/quality-principles-subtraction.md`）の適用として、既存の更新の仕組みを使う。
原則4（`agent-basics:writing-standards/references/quality-principles-constraints.md`）の適用として、配布物とエンドユーザーの環境を保護する。

## 外部部品の版の追従

- 外部部品は最新の安定版へ追従させる。
  LTS制度を持つ製品は最新のLTSを選び、公開待機設定がある時は待機期間を過ぎた最新版へ追従する。
  新しい版で動かなくなった時は、組み合わせて動く他の依存も含めて直す。
- 古い系列へ留める指定は、最新版で動かない原因を観測し、同じ作業で直せない時だけの一時的な措置とする。
  指定箇所のコメントへ理由と解除条件を書き、最新版へ移す作業を作業項目に登録する。
- 再現性と改ざん防止のための固定（ロックファイル、digest、commit SHA）は、固定値を最新版へ更新し続ける自動化か定期の更新手順と組にする。

### 最新版への追従

- 版の上限、メジャー版だけを指すタグ、旧版の厳密な指定も、上の一時的な措置の条件に従う。
- 組み合わせて動く処理系やパッケージマネージャーは、組の全部を同じ更新の仕組みへ載せる。
- digestやcommit SHAの固定も、更新ツール（Renovate、Dependabot、pinactなど）か定期の更新手順で、メジャー版を含めて更新する。
- 更新の仕組みを置けないリポジトリでは、最新の安定版を指す浮動の参照（`lts`、`stable`など）を使い、定期のCIで失敗を検出して追随する。

## バージョン指定と更新

- 更新コマンドで対象が更新されずエラーも出ない時は、更新先の版を明示して再実行し、依存解決のエラーから更新を妨げる制約元を特定する。
- 依存の追加や更新で出る警告は全て読み、仕様変更や非推奨への対応の要否を判断する。
- 依存の上書き設定（uvの`[tool.uv] override-dependencies`など）が作用するのはそのリポジトリの依存解決だけで、配布物のメタデータは上書き前の指定のままになる。
  エンドユーザーの環境へ波及する脆弱性は、上書きで回避する代わりに上流の修正リリースを待つ。
  上書きは開発環境だけで使う依存に限り、理由と解除条件をコメントに書く。

## 公開待機設定

公開された直後の版を一定期間だけ解決の対象から外す仕組み（uvの`exclude-newer`、pnpmの`minimum-release-age`、miseの`minimum_release_age`など）を公開待機設定と呼ぶ。

- 更新の仕組みの無い厳密な固定の代わりに、公開されたばかりの版を一定期間（目安は1日）待ってから取り込む公開待機設定を使う。
  対象はパッケージマネージャーが解決する依存で、コンテナーのベースイメージとCIの外部actionの版は本書「最新版への追従」に従う。
- 公開待機設定が有効な環境では、自分がリリースした直近の版も除外される。
  待機期間に満たない版を下限に要求すると、直近の自前リリースを取り込む処理（コンテナー内の`uv tool install`など）が失敗するため、次のいずれかで対処する。
  - プロジェクトの設定で対象パッケージだけを除外する（uvでは`pyproject.toml`の`[tool.uv]`に`exclude-newer-package = { <自パッケージ名> = false }`）。
  - 対象の処理の段（Dockerfileの特定の`RUN`など）だけ、環境変数で公開待機設定を一時的に無効にする。
  - ローカルでビルドした成果物（wheelなど）を直接渡して導入する。
  - 待機期間の経過とパッケージインデックスへの反映（CDNのキャッシュ更新など）を待ち、依存解決を確かめ直す。
    配布物自体の依存の下限を公開直後の版へ上げる時は、この方法を選ぶ。
  - 自作パッケージをプロジェクトの外から実行するコマンド（`uvx`など）で要求する時は、起動引数でそのパッケージだけを除外する（uvでは`--exclude-newer-package <パッケージ名>=false`）。
    そのパッケージが依存する他の外部パッケージには、通常の公開待機設定が適用されたままになる。
- パッケージ単位の除外は、プロジェクト全体の依存解決ではプロジェクトの設定（uvでは`pyproject.toml`の`[tool.uv]`）に、プロジェクトの設定を読まない単発のコマンド（`uvx`など）ではコマンドライン引数に置く。
  ユーザーごとのグローバル設定（uvでは`~/.config/uv/uv.toml`など）への除外の記述は避ける。
  uvはグローバル設定の除外を各プロジェクトの`uv.lock`（`[options.exclude-newer-package]`）へ記録し、無関係なプロジェクトのロックファイルを変え、同じ設定を持たない環境で`uv lock --check`を失敗させる。

## 脆弱性の確認

依存パッケージの脆弱性を、ソフトウェア構成分析（SCA）のツールで定期的に監査する。

## ロックファイルの運用

- 依存の追加と更新は専用のCLI（`uv add`、`pnpm add`、`mise use`など）で行い、ロックファイルとマニフェストを一致させ、固定値を更新し続ける。
- CIやMakefileのビルドでは依存解決をやり直さず、既存のロックファイルを使う。
  環境変数で固定のモードを一括で適用し（uvの`UV_FROZEN=1`、pnpmの`--frozen-lockfile`など）、依存を更新する専用コマンドの実行時だけ固定を外す。
  固定のモードを開発者個人のシェルの環境変数へ恒常的に設定するのは避ける。

## 配布物の版指定の検証

- 配布物がエンドユーザーの環境のパッケージマネージャーへ渡す版の指定を変える時は、統合の前に、エンドユーザーと同じ解決手段と配布する公開待機設定で変更後の指定を解決し、終了コードが正常なことを確かめる。
  uvでは、プロジェクトの外のディレクトリで`uvx --exclude-newer "<配布する待機期間>" --from '<変更後の版指定>' <コマンド> --version`を実行する。
- `uvx`、`uv tool install`、`uv run --script`、`uv run --no-project --with`などはプロジェクトの`[tool.uv]`とロックファイルを参照せず、実行環境のユーザー設定で依存を解決する。
  プロジェクト内の`uv lock`、`uv sync`、`uv run`の成功、ロックファイルへの反映、インデックスへの公開、テスト用リゾルバーでの成功は、エンドユーザーの環境での解決の根拠から外す。
- 解決に失敗する時は、本書「公開待機設定」の、依存の下限を上げる時の対処を適用してから統合する。

## Python対応版の追加

- 対象のPython版とCIのOS・CPUアーキテクチャで導入される依存を特定し、採用されるwheelの互換性と、sdistからビルドされる依存のビルド要件を確かめる。
  ローカルのwheelキャッシュでの同期の成功は観測した同じ環境だけの記録として扱い、キャッシュの無いCIでのビルドの根拠から外す。
- 互換な事前ビルド済みwheelがある版へ更新する案と、CIに必要なツールを整えてビルドを成立させる案を比べる。
  コンパイラーやCのヘッダーの追加は対象のビルドに要る範囲に限り、対象環境で導入されない依存はマーカーやextrasの指定から判断の対象外にする。
- 採用した版、Pythonの版、CIのイメージとアーキテクチャ、配布形式、検証日、再検証の手順を記録に残す。

## pnpm

- pnpm 12以降は、初回に`npm install -g pnpm@<版>`かstandaloneで導入し、`packageManager`を`pnpm@<版>`で固定する。
  版の更新はプロジェクト内で`pnpm self-update <版>`を実行し、`packageManager`と`pnpm-lock.yaml`の先頭のboot文書を同時に更新する。
  版の固定と取得物の検証には、boot文書の`packageManagerDependencies`と`integrity`、レジストリの署名を使う（`packageManager`の`+sha512.<hash>`はpnpm自身の検証の対象外である）。
  CIでは`pnpm install --frozen-lockfile`で不整合を失敗として検出する。
- 公開待機の`minimumReleaseAge`（pnpm 11以降は指定が無ければ1440分）は`self-update`にも適用される。
  `self-update`の待機を変える時は、プロジェクトの待機設定の代わりにグローバル設定、環境変数、CLIの指定を使う。
  npmやstandaloneでの初回の導入では、導入する版の公開後の経過時間を別に確かめる。
- pnpm 10以前は、Corepackを導入し、`packageManager`にSHAハッシュ値を保って`corepack use pnpm@<version>`で更新する。
  Node.js 25以降はCorepackを同梱しないため、要る環境では別に導入する。
- pnpmの特定の版では`NPM_CONFIG_*`環境変数の読取が不安定で、`pnpm config get`が環境変数の値を無視する事象を観測しているため、反映は`npm config get`で確かめる。
- `pnpm-workspace.yaml`の設定は`NPM_CONFIG_*`環境変数による指定より優先される。
