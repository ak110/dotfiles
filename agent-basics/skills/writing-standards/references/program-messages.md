## 出力の基準

- プログラムが出力するメッセージ（読み手がエンドユーザー、開発者、エージェントのいずれの場合も共通）: エラー、警告、処理の中断、失敗、待機のタイムアウトなど、読み手の対応が必要な結果では、観測された事実に加えて次に取るべき操作を具体的に提示する。
  ユーザーが指定したオプションどおりの正常な分岐選択は入力からすでに自明であるため、その解説や復旧手順の出力は省く。
  正常終了した結果は、返された値、識別子、状態、または簡潔な結果メッセージから判定できるようにする
  - 次に取るべき操作には、何を実行すべきかを具体的に記述する。
    実行できないことが事前に判明している場合は、代替手段や問い合わせ先を案内する。
    警告を出力する条件は、後述のエージェント向け出力の規定に従う。
    出力を生成する側で対処方法を特定できない場合は、不足している情報と、それを取得する手段や問い合わせ先を明記する
  - メッセージを受け取る側がその時点で保持している文脈（自身が実行した操作と引数、受信した情報）に基づいて一意に解釈できるように記述し、出力側の内部用語や受信側から観測できない前提条件には依存しないようにする。
    案内するコマンド、ツール名、引数は、受信側がそのまま実行できる実在の名称を用い、対象と操作内容を具体的に指定する
  - 案内する対処方法によって元の操作が可能にならない場合は、その方法が達成する別の目的を明記する
  - 出力用の共通関数やフレームワークが次の操作を専用の引数として受け取る設計になっている場合は、本文に混ぜ込まずにその引数へ渡す
  - 1つの応答の中で複数の出力が合流する場合は、共通の出力処理において返却値と通知メッセージを適切に調整する。
    返却値や構造化データ自体が処理の成功を表している場合は、同じ内容を伝える成功メッセージの重複出力を省く。
    複数の通知が同時に発生して同一の指示が重複する場合は、その指示を1回だけ届ける。
    独立して配信されるエージェント向け文書の通知と、ターミナルで人間が確認する進捗ステータスは、それぞれの配信先と用途を明確に保つ
  - ターミナルで人間が直接対話して使用する長時間実行コマンドや常駐CLIでは、処理の開始、工程の遷移、待機理由など、その時点で処理の状況を正確に判断できる情報を実行中に表示する。
    人間向けの表示量は、状況判断に必要な情報量に基づいて決定する。
    LLMが読み取る出力のトークン削減を理由に、人間向けの表示を削らない。
    人間向けのステータス表示は、1回の実行全体でターミナル上に蓄積される行数を抑え、各工程の確定結果の行と混ざらないように設計し、状態の更新は既存行の書き換え（上書き）によって表現する。
    エージェント向けの出力保存や機械可読な結果と、人間向けの進捗表示は、それぞれの利用場面に合わせて独立して設計する
  - 出力メッセージを新設または変更する際は、その処理から到達し得る既存の分岐処理も確認し、各分岐で次に取るべき操作が正しく提示されているかを検証する。
    共通の出力関数を経由しない直接出力、ステータス行、例外処理も含め、案内が不足している箇所があれば同じ変更の中で補う。
    共通関数や記述規約が存在することだけを根拠に、個別の出力へ適切に適用されているとみなさない
  - エージェントが読み取る出力は、処理の確定結果、および失敗・警告・次に取るべき操作など、受信側が次の判断に直接用いる行で構成する。
    無関係な通知、対処不要な付随処理の報告、毎回同じ固定文、無駄な反復表現を混入させない（努力目標。これらが混入すると、受信側のエージェントが出力をパイプ等でフィルタリングするようになり、終了ステータスや重要な警告を見落とす原因となる）。
    規範ファイルの所在自体を知らせる定型配信は、その所在の通知という目的に限り本項の無関係な固定文の除外から外す。
    `notice`区分でも、行動を求める本文には命令形・具体的な操作・重複の削除を適用する。
    警告は、受信側が何らかの操作（条件付きの操作を含む）を行える事象に限定して出力する。
    受信側で対処の余地がない事象は、結果の把握に必要な場合に限り確定結果の行で通知する
