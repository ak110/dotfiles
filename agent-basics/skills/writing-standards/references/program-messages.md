# プログラムの出力メッセージ

プログラムがエンドユーザー、開発者、エージェントへ出すメッセージ（エラー、警告、ログ、CLIの出力とヘルプ）の基準を定める。
原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）を出力へ適用し、受信側が次の判断に使う内容を、受信側の文脈で解釈できる形で届ける。

## 出力の基準

- エラー、警告、中断、失敗、待機のタイムアウトなど受信側の対応が要る結果では、観測した事実と、次に取る操作を具体的に示す。
  実行できないと分かっている操作には、代替の手段か問い合わせ先を示す。
  出力する側で対処を特定できない時は、足りない情報と、その取得手段か問い合わせ先を書く。
  案内する対処で元の操作ができるようにならない時は、その対処が達成する別の目的を書く。
- 受信側がその時点で持つ文脈（自分が実行した操作と引数、受け取った情報）で一意に解釈できるように書き、出力側の内部用語や受信側から観測できない前提を避ける。
  案内するコマンド、ツール名、引数は、受信側がそのまま実行できる実在の名前で、対象と操作を具体的に書く。
- 指定したオプションどおりの正常な分岐は入力から自明なので、解説や復旧の手順を省く。
  正常終了は、返した値、識別子、状態、短い結果のメッセージで判定できるようにする。
- 出力の共通関数が次の操作を専用の引数で受け取る設計なら、本文へ混ぜずにその引数へ渡す。
- 1つの応答で複数の出力が合流する時は、共通の出力処理で返却値と通知を調整する。
  返却値や構造化データが成功を表すなら同じ内容の成功メッセージを省き、重なった同じ指示は1回だけ届ける。
- 出力を新設・変更する時は、その処理から到達する既存の分岐（共通関数を経由しない直接の出力、ステータス行、例外処理を含む）でも、次の操作が正しく示されるかを確かめる。
  足りない箇所は同じ変更で補い、共通関数や記述の規約があることだけで個々の出力に適用済みとみなすのは避ける。
- エージェントが読む出力は、確定した結果と、失敗・警告・次の操作など受信側が次の判断に使う行で構成する。
  無関係な通知、対処の要らない付随処理の報告、毎回同じ固定文、無駄な反復は除く（努力目標。含まれると受信側が出力をパイプでフィルタリングし、終了状態や重要な警告を読み逃す）。
  読むべき資料の所在を通知する定型の配信は、その通知が目的なので、固定文の除外から外す。
  行動を求める本文は、通知の区分によらず命令形で具体的な操作を書き、重複を除く。
- 警告を出すのは、受信側が何らかの操作（条件付きの操作を含む）を行える事象に限る。
  対処の余地が無い事象は、結果の把握に要る時だけ確定結果の行で伝える。
- ターミナルで人間が直接使う長時間のコマンドや常駐のCLIでは、処理の開始、工程の遷移、待機の理由など、その時点の状況を判断できる情報を実行中に表示する。
  表示量は状況の判断に要る量で決め、LLMが読む出力のトークン削減を理由に人間向けの表示を削るのは避ける。
  ステータスの表示は既存の行の上書きで更新し、1回の実行で蓄積する行数を抑え、各工程の確定結果の行と分ける。
- エージェント向けの出力の保存や機械可読な結果と、人間向けの進捗表示は、それぞれの配信先と用途に合わせて別に設計する。
