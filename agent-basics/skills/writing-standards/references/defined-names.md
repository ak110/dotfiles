# 名前の方針と定義済みの名前の一覧

本書では、各種の名称を選定する際の基本方針を定める。
本書の読者は、規範、設計文書、作業項目、計画書、コミットメッセージ、コードなどにおいて名前を定義・記述するすべての主体である。
個々の用語定義そのものは本来の定義元にのみ配置し、複数の資料で共通して使われる名前については、定義元を参照するための索引を設ける（`agent-documents-basics.md`「主要用語の初出定義先」を参照）。

## 命名の方針

作業工程、レビュー、検証、判定、担当役割などの名称は、あらかじめ定義して表記を統一する。
本スキルの適用範囲は、この基準に従って作成するすべての成果物とし、名前は以下の方針に基づいて選定する。

1. 定義をあらかじめ読まなくても指している対象が自然に伝わる言葉を選ぶ。
2. 一般的な単語（独立、root、固定、管理など）に文脈独自の特殊な意味を持たせることを避け、異なる概念同士に紛らわしい類似した名前を付けない。
3. すでに識別子（スキル名、コマンド名、ファイル名、定数名など）が存在する対象は、日本語の説明的な別名を作らずにその識別子をそのまま記述する。
4. ユーザーが指定した名称や、画面表示などエンドユーザーの目に直接触れる場所で使われている名称は維持する。
5. 適用範囲や境界が曖昧な名称については、元の要求や既存の定義を確認した上で`quality-principles.md`「要件と認可」を適用する。技術的に確定可能な境界はエージェント自身で判断し、ユーザー固有の好みや判断が残る場合に限って確認する。
6. 返却フォーマットの項目名（フィールド名）も日本語で命名する。
7. ある名称を維持する正当な根拠として、「単に使用頻度が高いこと」や「すでに過去の定義が存在すること」のみに依存しない。

特定の対象を指し示す際は、識別子があれば識別子を使い、識別子がない場合は定義済みの名称を用いる。
どちらも存在しない対象に対して繰り返し参照する名称が必要な場合は、直感的に分かりやすい自然な言葉を選び、本来の定義元に1文程度の定義文を記載して索引に追加した上で使用する。定義を配置する前の段階では、名称ではなく説明文として記述する（`writing.md`における実在する名前の規定を参照）。
新しく導入する概念名や、画面に新規表示する名称（1つの文書内でのみ定義する用語や、質問の説明のために作成した用語を含む）は、次の点に留意して候補を絞り込み、方針1および方針7に基づいて優先度を判断する。

- 候補の検討時には、索引に未掲載の既存の呼称も漏れなく把握するため、候補となる語句ごとにGit追跡対象の全ファイル（変更予定外の設計書、経緯記録、エンドユーザー向けドキュメント、隠しディレクトリを含む）を固定文字列で検索する。一覧表の確認だけに頼ると、既存の別用途で使われている語句を新しい概念に誤って割り当ててしまう恐れがあるためである。
- 既存の別用途で使用されている語句は、過去の記述を修正したとしても両方の意味に解釈されるリスクが残るため、命名候補から除外する。ユーザーが指定した語句を変更したい場合は、方針5に従ってユーザーに確認する。
- 画面に表示する名称は、同じ表示領域にある既存ラベルの命名規則（使用言語、英字の大文字・小文字、単語の区切り方など）に合わせる（`ui-ux.md`「判断の順序」を参照）。既存ラベルの記法に不一致がある場合は設計記録から本来の目的を確認する。記録が見当たらない場合は方針4に従って現状維持を推奨案とし、統一する案については設計意図の記録がない旨を明記して選択肢として提示する。
