# エージェント向け文書品質（基本）：読込表

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 読込表

- 規範資料は、既存の資料も含め、読込条件や利用場面が異なる内容を独立して全文を読めるファイルへ分けることを優先する（努力目標。不要な本文の取得と保守の負担を減らすため）。
  スキルの条件別資料には`references/`を使う。
  生成物も生成元で分割できるかを含めて資料構成を見直す。
- 分割後も、同時に必要な前提・例外・認可・終了条件を同じ判断単位に保つ。
  同時に必要な内容の分散、共通部分の複製、参照の往復や更新箇所の増加が便益を上回る分割は避ける。
  長さだけで一律に分割せず、同時に読むまとまりを保つ方が適切な資料は、理由を記録して全文を読む。
  編集権限のない規範資料も全文を読み、分割を必要と判断した場合はその対象と理由を既存の作業記録に残す。
  規範以外の資料は、確認する内容に必要な範囲を選べる。
- 読込表はスキル本体や、委譲先の手順書・委譲元の契約文書の冒頭に配置する表であり、各行の時点や条件を満たしたときに、対象の操作をする前に必要な基準へ到達することを示す。
  必須の列は「時点または条件」と「全文読む資料」である。
  読み手による各列の使い方は`read-method.md`が定める。
  条件は観測可能な操作や入力内容で記述し、条件付きの読み込み指示は、条件の成立を判定する工程が明確になるよう読込表に集約する。
  常時規範の記述方法は、`agent-documents-additions-additions.md`「常時規範への追記条件」に従う。
- 読込を自動化する仕組み（hookなど）を持つプロジェクトでは、その仕組みの受理契約に従って「契機」「配送操作」「資料選択子」などの列を加える。
  加えた列も同じ表に置き、読み手向けの表と仕組み向けの表へ同じ条件を分けて書かない。
  同じ条件が2か所にあると、片方だけを改訂したときに内容が一致しなくなるためである。
  仕組みが資料列や本文から導出できる値は表へ書かない（努力目標。読む量を減らすため）。
  導出と同じ値だけの列は空にするか列ごと省き、本文が名指しした資料を写すだけの行は置かない。
  条件が成果物を「書く前」「起草する前」の行には、その成果物を書く操作で成立する配送操作を付けるか、付けない理由を同じ行の条件か直後の本文へ残す（後段の保存や検査の操作だけに結び付けると、書き終えるまで基準が届かないため）。
- 兄弟資料（同じ親の下で分割した資料）の冒頭表は、親（所属SKILL.mdまたは親資料）の読込表に集約し、子には自分の本文が実際に使う行だけを残す（努力目標。複写した行は片方の改訂で食い違い、本文が使わない資料を読ませるため）。
  親と同一で本文が使わない行は、親の読込表と本文の名指しのいずれかから届くことを確かめて削除する。
- 起動のたびに常に成立する行（起動時、着手時など）について、その文書でのみ読み込ませる資料であれば表の行には含めず、内容を文書本体に直接記述する。
  共有資料については、毎回の判断で必要な資料をファイル単位で指定した行を残す。
  要求の種類によって要否が分かれる資料は、その種別を条件とする独立した行に分ける。
  本文内で全文読み込みを指示する場合も同様の基準を適用する。
  冒頭の責務と目的には、作業開始時に最初に必要な読み込みを明記する。
- ファイル全体の読込、条件の選択、取得済み本文の再利用は、`read-method.md`に従う。
  「全文読む資料」列には、規範をファイル単位で指定する。
- 「全文読む資料」列のパスは、書き方ごとに決まった基点から解決される。
  `references/`で始まる値は宣言を書いたスキルのディレクトリ、`docs/`で始まる値とプロジェクトのスキルが書く`.claude/`で始まる値はリポジトリの根を基点とする。
  `agent-basics:writing-standards`のような修飾名と、それに続けたパスは修飾名のプラグイン、その他の相対パスは宣言を書いたファイルのディレクトリを基点とする。
  読込を自動化する仕組みも同じ基点で解決するため、この書き方に合わせると読み手と仕組みの解釈がそろう。
- 条件は読み手が次に行う操作・対象・判断から選べる言葉にする。
  参照先の基準を既に知っていることを条件判定の前提にせず、同じ条件・資料の範囲は前提と例外を保持して集約する。
