# サブエージェント定義ファイルと`<役割名>.parent.md`・`<役割名>.subagent.md`の記述基準

本書は、`agents/`配下に配置するClaude Code用サブエージェント定義ファイルの新規作成・改訂、ならびにClaude CodeやCodexの委譲先が関与する手順書の作成・改訂において満たすべき基準を定めたものである。

## ディレクトリ構成

`agents/`ディレクトリ配下にはサブエージェント定義ファイルのみを配置する。`agents/`配下は再帰的に走査され、サブディレクトリ内のファイルもサブエージェント定義として登録される（プラグインでは`<plugin-name>:<サブディレクトリ名>:<name>`として公開される）。
定義ファイルが参照する資料のうち、そのサブエージェントの工程でのみ参照するものは対応するスキルの`references/`配下に配置する。複数のスキルや定義で共有する資料は、プラグイン内の共有用ディレクトリ（例: `share/`）に配置し、本文からはプラグインのrootを示す変数を前置したパス（Claude Codeでは`${CLAUDE_PLUGIN_ROOT}`）で参照する。

## `<役割名>.parent.md`と`<役割名>.subagent.md`の構成

本節は、委譲元と委譲先が共有する起動契約を持つ場合の構成の1つを定める。この構成では、委譲元の起動・検収の契約文書を`<役割名>.parent.md`、委譲先の作業手順書を`<役割名>.subagent.md`と呼び、サブエージェントの手順書をこの2つに分割して記述する。
機能上の呼び出し元が1箇所のみである契約は、その呼び出し元が必要な時点で読み込むエージェント向け文書内のセクションへ統合する。一方、複数の呼び出し元で共有される契約は、独立した`<役割名>.parent.md`として保持する。
索引、履歴、例示、あるいはテストコードからの参照は呼び出し元としてはカウントせず、実際に起動や結果を受領する主体に基づいて判定する。委譲先に対しては、委譲先向けの手順と必要な入力情報のみを渡し、責務の境界を明確に保つ。

- `<役割名>.subagent.md`、および複数呼び出し元で共有する`<役割名>.parent.md`は前述の共有用ディレクトリに配置する。単一の呼び出し元のみが存在する契約はその呼び出し元のセクション内に記述し、委譲元が入力を確定して検収するために必要な情報を過不足なく揃える
- 委譲元の契約文書には、公開されている起動手段へ渡す役割固有のパラメーターを記載する。全役割に共通する起動手順やデフォルト値は、共通の定義元へ集約する
- 委譲先の恒常的な作業手順がホスト環境のエージェント定義としてすでに存在する場合は、その本文を委譲先の定義元とする。必須となる入力名（プロパティ名）を明示的に宣言し、呼び出し元が値を確定する際のルールと整合させる

委譲元の契約（統合先のセクションまたは`<役割名>.parent.md`）は、委譲元が結果を利用するまでの「入力の確定・起動・待機・受領・検収・採否・統合」という一連の工程を扱う。`<役割名>.subagent.md`は、委譲先が入力を受け取ってから結果を返すまでの工程を扱う。以降に述べる`<役割名>.parent.md`の記述基準は、統合先のセクションにもそのまま適用する。

- 双方で共有する契約事項は、定義を持つ文書を1つに限定し（`agent-documents-basics.md`「定義の所有者」、後述の「`<役割名>.parent.md`と`<役割名>.subagent.md`の自己完結（双方向）」参照）、各文書には担当工程で必要な参照契機のみを記載する
- いずれの文書においても複数の工程を扱う場合は、その文書が対象とするすべての工程で必要となる役割や分岐条件を同一文書内に網羅する
- 特定の工程でのみ使用する判断条件、例外規定、固定フォーマット、終了状態の詳細などは、その工程で起動されるスキルの`references/`配下に配置する。各文書では、該当工程を実行することを条件とする読込表の行を設け、必要な場合に全文を取得するように指定する
- 委譲元が起動前に行うべき事前確認事項の中に、実行側（委譲先）が起動時に自ら確認・補完・実行できる事項を含めて重複させない。実行側で一意に解決できる値を委譲元にあらかじめ組み立てさせると、事前読込や呼び出しの手数が増加し、組み立て時の誤りが起動失敗を招く原因となる
- 委譲元と委譲先の双方が同じ資料を読み込み、同じように調査して結論を重複して導くような構成は避ける。調査や判断の担当主体を工程ごとに1つに定め、委譲元は確定した成果と原本の所在を委譲先に渡し、委譲先は導き出した結論、判断内容、および詳細を記録した原本の所在を委譲元へ返す。委譲元は返された結論の根拠や適用条件を検収し、同一の調査を最初からやり直すことはしない。分担するかどうかの採否は、`design-heuristics.md`「案の採否と実施順の判定」に基づき、全体の総費用を比較して判断する

`<役割名>.subagent.md`は、`agent-documents-basics.md`「責務と構成」に従い、冒頭で担当する責務を明記した上で、続けて入力、実行手順、出力形式を定義する。

### `<役割名>.parent.md`と`<役割名>.subagent.md`の自己完結（双方向）

会話履歴を引き継ぐfork機能を利用する場合を除き、委譲元と委譲先はコンテキストが完全に独立している前提で設計し、1つの取り決めは1つの文書にのみ定義する。
返却形式、応答言語、成果物のフォーマットなど、情報の受け渡しに関する取り決めは、その取り決めに従って作業するエージェントへ配送される文書を正式な定義元とし、もう一方の文書には参照情報のみを記載する。プロジェクトが全委譲先に共通の返却契約（完了、続行不能、通知、追加報告の形式）を定める場合は、その契約が共通部分を所有し、役割文書には固有の結果欄と差分を記載する。共通の返却契約が無い場合は、役割文書に完了、続行不能、通知の形式を書く。委譲先内部の条件分岐や判断手順は、委譲先側の文書のみに記載する。
同一の参照資料を委譲元と委譲先の双方に読み込ませるのは、両者がその資料を異なる判断目的で利用する場合に限定し、それぞれの判断目的の違いを条文として明記する。

`<役割名>.parent.md`は、委譲元が担当する工程（起動前の確認、入力値の確定、返却物の検収）に必要な定義を、自身の本文内だけで完結して提供する。定義を自身に記載する代わりに`<役割名>.subagent.md`のセクションや本文を参照させる記述を設けるのは、以下の3つの例外に限定する。

- 起動時の引数として渡す役割名を指定する記述
- 委譲先が実行する作業手順の基準定義が、該当文書に存在することを示す参照記述
- 役割固有の返却形式および入力の宣言。これらは`<役割名>.subagent.md`が所有する。起動前の入力値の確定は呼び出し元の契約文書内で完結させ、返却後は同書の`## 出力`と、プロジェクトが定める共通の返却契約（ある場合）を検収の基準にできる。ただし、どの項目をどの期待値と比較するかという具体的な検収判断の手順は、`<役割名>.parent.md`本文側で定義する

逆方向も同様であり、`<役割名>.subagent.md`が自身の内容を定義する代わりに`<役割名>.parent.md`を参照させるような記述は避ける。委譲先は委譲プロンプトから必要な入力を受け取るため、`<役割名>.parent.md`を読み込む手順そのものが不要である。したがって、前述の例外規定は`<役割名>.parent.md`から`<役割名>.subagent.md`を参照する方向にのみ適用される。

## 返却形式の設計

本節の規定は努力目標とする。

- 返却形式の行数や文字数が項目数に応じて肥大化する場合は、委譲元が指定した絶対パスのファイルへ結果を直接書き込ませ、ツールの戻り値としては保存先の絶対パスと処理件数のみを返却させる
- 項目を省略可能とする場合は、省略時のデフォルト値と、項目が存在しない場合にその値として扱われることを同一の本文内に明記する。同一の要素を複数の異なるデータ構造に重複して列挙させることは避ける
- ユーザーや委譲元の判断を待つための通知や、処理を続行するための条件は、プロジェクトが共通の返却契約を定める場合はそこへ集約し、定めていない場合は役割文書の返却形式にまとめる。調査によって確定できる結論については、推測ではなく確定した結果の値をそのまま返却に含める

## 名前付きagent、`<役割名>.subagent.md`およびskillの責務分離

名前付きagentとは、実行ホスト環境に定義を持ち、名前を指定して直接起動できるサブエージェントを指す。

- 名前付きagentは全体の調整責務と入力の受付形式を規定し、呼び出し時には指定された`<役割名>.subagent.md`のパスと、起動引数として許可されている値のみを受け取る
- 渡される`<役割名>.subagent.md`には、具体的な実施内容、対象範囲、成果物の作成・レビュー規範を定めるスキル、検証手順、および役割固有の返却形式を定義する。完了報告と成果物の記述言語を日本語とする条件は、プロジェクトが全委譲先へ共通に届ける規範で定めている場合はそれで充足でき、役割文書には固有の差分だけを残す
- skillは、ユーザーまたは委譲元が作業を開始する際のエントリポイントを規定し、名前付きagentや`<役割名>.subagent.md`の本文は参照として指定する
- 委譲元と委譲先の双方が必要とする共通の判断基準は、共通のskill内に定義する
- 起動時の入力として渡す項目は、委譲先が適用すべき作成・レビュー規範のスキル、プラグイン内文書、および役割定義から一意に導出できない動的な値に限定し、委譲先自身が自律的に決定できる事項は委譲先側で解決させる

## Claude Codeのfrontmatter

- サブエージェントの定義はセッション起動時に一括して読み込まれるため、セッション実行中に新設または改訂した定義は、同一セッション内の`subagent_type`からは認識・解決できない
- 特定の委譲元から明示的に呼び出される前提の定義では、`description`にはその呼び出し元（スキル名や起動契約）を一意に特定できる簡潔な文面のみを記載し、具体的な責務、処理の概要、および手順は本文側に記述する（`description`は自動委譲の判定材料として常時コンテキストを消費するため）
- 起動直後から常に必要となる作成・レビュー規範のスキルは`skills`フィールドに列挙し、本文側でそのスキルの起動手順を重複して記述することは避ける（努力目標。不要なトークン消費を抑えるため）。特定の工程でのみ必要となるスキルは`skills`には含めず、客観的に観測可能な起動条件とともに本文側へ起動手順を記載する
- `model`は指定がない限り`inherit`（親モデルを継承）とし、`tools`は省略（すべてのツールを許可）とする。モデルを固定したりツールを制限したりする場合は、実態と合致する明確な理由をfrontmatter内のコメント行に記載する（努力目標）。妥当な理由を説明できない場合はデフォルト値（省略）を使用する
- `effort`は、そのエージェントが担当する工程に求められる思考量や推論量に合わせて適切に設定する

`skills`によって注入されたスキル本文には、配置ディレクトリの絶対パスが付随しているため、プラグイン内の他のファイルはその絶対パスから特定したプラグインルートからの相対パスで解決できる。
なお、スキル配下の`references/`ディレクトリは`skills`の宣言だけでは読み込まれないため、必要な参照文書はエージェントの本文から明示的に読み込む（`Read`する）。
監査記録は`docs/development/audit-records.md`「agent-basics/skills/writing-standards/references/sub-agents.md：Claude Codeのfrontmatter：2026年8月19日」を参照。

## コンテキスト境界

通常の委譲処理は、会話コンテキストが完全に独立している前提で設計する。ホスト標準のfork機能は会話履歴を引き継ぐ例外的な形態であるため、会話履歴、適用規範、スキル、起動引数がそれぞれどのように配送されるかを個別に確認する。

`Agent`ツールを用いて`agents/`配下の定義から起動されたサブエージェントが、起動時に受け取る情報は以下のとおりである。

- エージェントの定義本文、および実行環境が付与する環境情報
- 委譲元が組み立てた委譲プロンプト
- 委譲元が読み込んでいるメモリー階層（`CLAUDE.md`やプロジェクト固有のルールなど）
- 親セッション開始時点のGitステータス（Gitリポジトリでない場合、または`includeGitInstructions`が`false`の場合は付与されない）
- `skills`で宣言されたスキルの全文
- `main`およびセッション内で稼働している他の名前付きエージェントの名簿（`tools`に`SendMessage`が含まれ、かつ他に名前付きエージェントが存在する場合）

名簿に関する監査記録は`docs/development/audit-records.md`「agent-basics/skills/writing-standards/references/sub-agents.md：コンテキスト境界：2026年9月13日」を参照。
委譲元はサブエージェントの定義本文を直接読まずに委譲プロンプトを組み立てるため、起動に必要となる入力項目は、委譲元側の手順書に明記しておく。

## 手順設計時の確認

サブエージェントが関与する手順を新規作成または改訂する際は、内容を確定する前に以下の点を確認する。

- 手順書が要求している各判断に対して、判断するエージェントが起動時に受け取る情報だけで到達できること
- 委譲元、作業工程、または処理フェーズの違いを前提条件とする記述がある場合、その差異を委譲先が「委譲プロンプト」「宣言されたスキル」「参照する文書」から客観的に識別できること（識別できない条件は判定されないまま手順が進行してしまうため）
- 委譲先が名前で参照する値のうち、委譲先自身で解決できないものは、入力の宣言、または呼び出し側の契約における引数列挙のいずれかに確実に含まれていること（不足している場合、実行時に処理を続行できない理由を返して停止してしまうため）
