# 役割文書とサブエージェント定義

委譲の文書を書く担当が役割ごとの入力と返却を定め、受け取る担当がユーザーの要求を満たす成果か判断できるようにする。
本書は、サブエージェント定義（`agents/`）と、委譲元の契約文書・委譲先の手順書（役割文書）を作る時と改める時の基準である。
Claude Codeの`agents/`のfrontmatterの項目名と値は、公式ドキュメント（`https://code.claude.com/docs/ja/sub-agents.md`）の定義に従う。
主に原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）の適用である。
分担の採否は原則2（`agent-basics:writing-standards/references/quality-principles-qcd.md`）に従う。

## ディレクトリ構成

`agents/`にはサブエージェント定義だけを置く。
`agents/`は再帰的に走査され、サブディレクトリのファイルも定義として登録される（プラグインでは`<plugin-name>:<サブディレクトリ名>:<name>`として公開される）。
定義が参照する資料のうち、そのサブエージェントの工程だけで使うものは対応するスキルの`references/`に置く。
複数のスキルや定義で共有する資料は責務の合うスキルの`references/`に置き、プラグインのrootを示す変数（Claude Codeでは`${CLAUDE_PLUGIN_ROOT}`）を前置したパスで参照する。
スキルの外に独自の共有ディレクトリ（`share/`など）を設けると、スキルの配下だけを配置するホスト（OpenCodeなど）へ届かない。

## Claude Codeのfrontmatter

- `~/.claude/agents/`と`.claude/agents/`の定義は、編集から数秒で次の委譲に反映される（[公式の定義ファイルの説明](https://code.claude.com/docs/en/sub-agents#write-subagent-files)）。
  プラグインの`agents/`の変更は`/reload-plugins`で反映する。
  `--add-dir`か`/add-dir`で追加したディレクトリ内の定義と、`--disable-slash-commands`で起動したセッションでは再起動が要る。
- 特定の委譲元から明示的に呼ばれる前提の定義は、`description`に呼び出し元（スキル名や起動契約）を特定できる短い文面だけを書き、責務・処理の概要・手順は本文に書く（`description`は自動委譲の判定材料として常時文脈を消費する）。
- 起動直後から常に要る作成・レビューの規範のスキルは`skills`に列挙し、本文で同じスキルの起動手順を重ねて書くのは避ける（努力目標。トークンの消費を抑えるため）。
  特定の工程だけで要るスキルは`skills`に入れずに、観測できる起動条件と共に本文に起動手順を書く。
- `model`は指定が無い限り`inherit`（親のモデルを継承）、`tools`は省略（全てのツールを許可）とする。
  モデルを固定する時とツールを制限する時は実態に合う理由をfrontmatterのコメント行に書き（努力目標）、理由を説明できなければ省略時の値を使う。
- `effort`は、担当する工程に要る推論量に合わせて設定する。
- `skills`で注入されたスキルの本文には配置ディレクトリの絶対パスが付くため、プラグイン内の他のファイルはそこから特定したプラグインのrootからの相対パスで解決できる。
  スキルの`references/`は`skills`の宣言だけでは読み込まれないため、必要な参照文書は定義の本文から明示的に読ませる。

## コンテキスト境界

通常の委譲は、会話の文脈が完全に独立している前提で設計する。
ホスト標準のfork機能は会話履歴を引き継ぐ例外であり、使う場合は会話履歴、適用する規範、スキル、起動引数がそれぞれどう届くかを確かめる。
`Agent`ツールで`agents/`の定義から起動したサブエージェントが起動時に受け取るのは、次のとおりである。

- 定義の本文と、実行環境が付ける環境情報
- 委譲元が組み立てた委譲プロンプト
- 委譲元が読み込んでいるメモリーの階層（`CLAUDE.md`やプロジェクトのルールなど）
- 親セッションの開始時点のGitの状態（Gitリポジトリでない場合と、`includeGitInstructions`が`false`の場合は付かない）
- `skills`で宣言したスキルの全文
- `main`とセッション内で動いている他の名前付きエージェントの名簿（`tools`に`SendMessage`が含まれ、他に名前付きエージェントがいる場合）

委譲元は定義の本文を読まずに委譲プロンプトを組み立てるため、起動に要る入力の項目は委譲元の側の手順書に書く。

## `<役割名>.parent.md`と`<役割名>.subagent.md`の構成

本節は、委譲元と委譲先が起動契約を共有する場合の構成の1つを定める。
委譲元の起動と検収の契約文書を`<役割名>.parent.md`、委譲先の作業手順書を`<役割名>.subagent.md`と呼ぶ。
委譲元の契約は入力の確定・起動・待機・受領・検収・採否・統合を扱い、`<役割名>.subagent.md`は委譲先が入力を受けてから結果を返すまでを扱う。

- 機能上の呼び出し元が1か所だけの契約は、その呼び出し元が必要な時点で読む文書の節へ統合し、複数の呼び出し元で共有する契約は独立した`<役割名>.parent.md`にする。
  呼び出し元は、実際に起動や結果の受領をする主体で数える（索引、履歴、例示、テストコードからの参照は除く）。
  統合先の節にも、本節の`<役割名>.parent.md`の基準を適用する。
- `<役割名>.subagent.md`と、共有する`<役割名>.parent.md`は、共有用のディレクトリに置く。
- 委譲元の契約には公開された起動手段へ渡す役割固有の値を書き、全役割に共通する起動手順と省略時の値は共通の定義元へ集めて省く。
- 委譲先の恒常的な作業手順がホストのエージェント定義として既にある場合は、その本文を委譲先の定義元とし、必須の入力名を明示的に宣言して、呼び出し元が値を確定する規則と合わせる。
- 複数の工程を扱う文書は、扱う全ての工程で要る役割と分岐条件を同じ文書に網羅する。
- 特定の工程だけで使う判断条件、例外、固定の形式、終了状態の詳細は、その工程で起動するスキルの`references/`に置き、工程の実行を条件とする読込表の行で読ませる。
- 委譲先が起動時に自分で確認、補完、実行できる事項は、委譲元の起動前の確認から外す（委譲元に組み立てさせると手数が増え、組み立ての誤りが起動の失敗を招く）。
- 調査と判断の担当は工程ごとに1つにし、委譲元と委譲先が同じ資料を読んで同じ結論を重ねて導く構成は避ける。
  委譲元は確定した成果と原本の所在を渡し、委譲先は結論、判断、詳細を記録した原本の所在を返し、委譲元は根拠と適用条件を検収して同じ調査をやり直さずに使う。
  分担するかは、`agent-basics:writing-standards/references/design-heuristics.md`「案の採否と実施順の判定」で全体の総費用を比べて決める。
- `<役割名>.subagent.md`は、冒頭で担当する責務を書き、続けて入力、実行の手順、出力の形式を定義する。

### `<役割名>.parent.md`と`<役割名>.subagent.md`の自己完結（双方向）

fork機能を使う場合を除き、委譲元と委譲先は文脈が完全に独立している前提で設計し、1つの取り決めは1つの文書だけに定義する。
返却形式、応答の言語、成果物の形式など受け渡しの取り決めは、その取り決めに従って作業するエージェントへ届く文書を定義元とする。
もう一方の文書には、その定義元から担当工程に要る契約の部分だけを生成して配置できる。
生成した部分は手で二重に管理せず、相対参照と見出しの階層を配置先に合わせ、委譲先の内部の手順と起動の設定は生成の対象から除く。
プロジェクトが全委譲先に共通の返却契約（完了、続行不能、通知、追加の報告の形式）を定める場合は、その契約が共通の部分を所有し、役割文書には固有の結果欄と差分を書く。
共通の返却契約が無い場合は、役割文書に完了・続行不能・通知の形式を書く。
委譲先の内部の条件分岐と判断の手順は、委譲先の文書だけに書く。
同じ参照資料を委譲元と委譲先の双方に読ませるのは、両者が違う判断の目的で使う場合に限り、目的の違いを条文に書く。

`<役割名>.parent.md`は、委譲元が担う工程（起動前の確認、入力値の確定、返却物の検収）に要る定義を自分の本文だけで提供する。
`<役割名>.subagent.md`の節や本文を参照させるのは、次の3つに限る。

- 起動の引数として渡す役割名の指定
- 委譲先が実行する作業手順の定義がその文書にあることを示す参照
- 役割固有の返却形式と入力の宣言（`<役割名>.subagent.md`が所有する）

起動前の入力値の確定は呼び出し元の契約文書の中で完結させ、返却形式は`<役割名>.subagent.md`の`## 出力`から呼出側の契約へ生成して配置する。
委譲元はその配置先と共通の返却契約（ある場合）を検収の基準にし、どの項目をどの期待値と比べるかという検収の手順は`<役割名>.parent.md`の本文に書く。

逆向きに、`<役割名>.subagent.md`が自分の内容を定義する代わりに`<役割名>.parent.md`を参照させる記述は避ける。
委譲先は委譲プロンプトから入力を受け取るため、`<役割名>.parent.md`を読む手順自体が不要である。

## 返却形式の設計

本節の規定は努力目標とする。

- 項目数に応じて返却の行数や文字数が膨らむ場合は、委譲元が指定した絶対パスのファイルへ結果を書かせ、ツールの戻り値は保存先の絶対パスと処理件数だけにする。
- 省略できる項目は、省略時の値と、項目が無い場合にその値として扱うことを同じ本文に書き、同じ要素は1つのデータ構造だけに列挙させる。
- ユーザーや委譲元の判断を待つ通知と処理を続ける条件は、共通の返却契約があればそこへ集め、無ければ役割文書の返却形式にまとめる。
- 調査で確定できる結論は、推測ではなく確定した値を返却に含める。

## 名前付きagent、`<役割名>.subagent.md`およびskillの責務分離

名前付きagentは、実行ホストに定義を持ち、名前を指定して直接起動できるサブエージェントを指す。

- 名前付きagentは全体の調整の責務と入力の受付形式を定め、呼び出し時には指定された`<役割名>.subagent.md`のパスと、起動の引数として許した値だけを受け取る。
- `<役割名>.subagent.md`には、実施内容、対象範囲、成果物の作成・レビューの規範を定めるスキル、検証の手順、役割固有の返却形式を定義する。
  完了報告と成果物を日本語で書く条件は、プロジェクトが全委譲先へ共通に届ける規範で定めていればそれで足り、役割文書には固有の差分だけを残す。
- skillは、ユーザーか委譲元が作業を始める起点を定め、名前付きagentと`<役割名>.subagent.md`の本文は参照として指定する。
- 委譲元と委譲先の双方が要る共通の判断基準は、共通のskillに定義する。
- 起動時の入力として渡す項目は、委譲先が適用する規範のスキル、プラグイン内の文書、役割の定義から一意に導けない動的な値に限り、委譲先が自分で決められる事項は委譲先で解決させる。

## 手順設計時の確認

サブエージェントが関わる手順を新設・改訂する時は、内容を確定する前に次を確かめる。

- 手順書が求める各判断に、判断するエージェントが起動時に受け取る情報だけで到達できる。
- 委譲元、工程、処理の段階の違いを前提とする記述がある場合、その違いを委譲先が委譲プロンプト、宣言されたスキル、参照する文書から識別できる（識別できない条件は判定されないまま手順が進む）。
- 委譲先が名前で参照する値のうち委譲先で解決できないものが、入力の宣言か呼び出し側の契約の引数の列挙に含まれている（不足すると、実行時に続行できない理由を返して止まる）。
