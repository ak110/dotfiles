## 基本原則

- 入出力の境界でエンコーディングを明示し、内部処理はUTF-8を標準とする。日本語Windowsのデフォルト文字コード（ANSIコードページ: ACP）はCP932であり、ランタイムの自動選択に任せると文字化けや例外が発生する原因となる。
- 生データをそのまま復元する必要がある処理では、ライブラリのフィールド値にプラットフォーム依存の暗黙的な加工が含まれる場合があるため、未加工のデータを取り出せるフィールドやAPIが別に用意されていないか確認する。
- バイト長と文字数（Unicodeコードポイント数や書記素クラスター数）を明確に区別して扱う。
- テキストを途中で切り詰めて保存する場合は、文字エンコーディングを指定して正しく文字列にデコードした上で、文字単位で切り詰めてから保存する。GNU `cut -c`などはバイト単位で分割してマルチバイト文字を破損させるため、Unicodeコードポイント単位で切り詰めるにはPythonの文字列スライスなどを使用する。
- BOM（Byte Order Mark）は、読み込み時にはBOMの有無にかかわらず両方を受け付け、書き出し時には原則としてBOMを付与しない（Excel向けCSVなど、受け取り側が明示的にBOMを必要とする場合を除く）。

## 日本語テキストの自動判定順序

文字コード情報が外部から得られず自動判定が必要な場合は、「BOMの検出」→「ISO-2022-JPのエスケープシーケンスの整合性検証」→「UTF-8での厳格なデコード検証」→「EUC-JPやCP932の判定」という順序で行う。
ISO-2022-JPはASCII互換のバイト列で構成されており、UTF-8の厳格なデコードでもエラーにならない場合があるため、UTF-8よりも先に判定する。

## ZIPファイル名の扱い

ZIP内のファイル名は、General Purpose Bit FlagのBit 11が立っていればUTF-8としてデコードする。
Bit 11が立っていない場合のZIP仕様上の基本文字コードはCP437である。作成元が日本語Windowsであることが確実な場合に限り、CP932をフォールバックとして採用する。あわせてInfo-ZIP Unicode Path Extra Fieldなどの拡張属性の有無も確認する。

Pythonの`zipfile.ZipInfo.filename`は内部で`_sanitize_filename`を呼び出し、Windows環境ではパス区切り文字の`\`を`/`に置き換えてしまう。そのため、CP932の2バイト目に`0x5C`（`\`）を含む文字（「ソ」「ポ」「表」など）は元の文字に正しく復元できなくなる。生のバイト列を正確に復元したい場合は、`filename`ではなく`orig_filename`を使用する。

## Unicodeの比較と安全性

- 文字列の比較、検索、一意性チェックのキーには、業務要件に合わせてNFCなどで正規化した文字列を用いる。認証・認可の識別キーやパスワード突き合わせにNFKCを使うと、合字や互換文字の違いをすり抜ける脆弱性につながる恐れがある。
- 大文字・小文字を区別せずに比較する場合は、NFCで正規化してから`casefold()`を適用する。
- macOSのHFS+はApple独自のNFD相当でファイル名を保存し、APFSは元の正規化形式を保持する。そのため、ファイルシステムやAPIをまたいでファイル名を比較するときは、正規化形式の違いを考慮する。
- 双方向テキスト制御文字（Trojan SourceなどのBidi制御文字）、ゼロ幅文字、および視覚的に紛らわしいホモグラフ（類似文字）は、ソースコード、識別子、ユーザー入力、ログ出力において混入を禁止するか警告を出すようにする。

## 書込ツールの改行・BOM保全

各ツールの改行コードやBOM、文字コードの仕様を踏まえて、CRLF改行、BOM付き、あるいは非UTF-8のファイルを正しく作成・編集する共通手順を「書込ツールの改行・BOM保全」と呼ぶ。
`Edit`や`Write`を実行するために必要な読み取り状態は、`file-editing.md`の「ファイル更新時の編集ツールの前提」に従う。

- Claude Codeの`Read`、`Edit`、`Write`はUTF-8を前提として動作するため、非UTF-8（CP932など）のファイルを直接扱うことはできない。
- `Edit`は既存ファイルのCRLF改行やUTF-8 BOMを保持して編集するため、既存ファイルの更新には原則として`Edit`を使用する。
- `Write`は常にLF改行・BOMなしで出力する。CRLFやBOMを必要とするファイルを`Write`で更新した場合は、書き込み後に改行コードやBOMを復元する。新規作成する場合は、Bash経由で改行コードやBOMを明示的に指定して作成する。
- 非UTF-8の既存ファイルを編集するときは、まず`iconv -f <元の文字コード> -t utf-8`でUTF-8に変換して`Read`で読み取る。そして`Edit`で編集した後に`iconv -f utf-8 -t <元の文字コード>`で元の文字コードへ戻す（新規作成時も同様にUTF-8で作成してから変換する）。文字コード変換を往復させずに編集したい場合は、Pythonスクリプトを用いて置換対象のバイト列を元の文字コードで直接置換し、行末のCRLFも保持するようにする。
- `.gitattributes`の`eol=crlf`指定は改行コードのみを管理するものであり、BOMの復元までは行われない点に留意する。
