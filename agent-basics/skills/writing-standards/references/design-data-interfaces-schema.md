## DBスキーマ・マイグレーション設計

発火条件: データベースのスキーマを新しく設計する場面、スキーマを変更する場面、およびマイグレーションを設計する場面。

スキーマは、アプリケーションコードより先に、扱うデータの要件、参照・更新のされ方、今後の変更の見込みから設計する。
スキーマ設計の不足をアプリケーションコードの分岐や補正で後から補わない。
スキーマが粗いほど、整合性を保つ処理がコードの各所へ散らばるためである。
外部キー制約、CHECK制約、ENUM型、結合クエリなどの採否は、整合性の要件、参照のされ方、値や関係の変更のしやすさを比べて決める。
比較せずに特定の手段を採用しない。
プロジェクトの規範やユーザーが制約の使い方を指定している場合は、その指定に従う。
既存の制約や型を変える必要が出たときは、テーブルの削除と再作成を提案する前に、対象DBMSが備える変更手段（PostgreSQLの`ALTER TYPE ... ADD VALUE`、制約の削除と追加による付け替えなど）を調べる。
再作成は、それらの手段が使えない場合に限って比較対象にする。

アプリケーションのデプロイ作業中に新旧バージョンのコードが同一のスキーマに同時アクセスしても双方の動作が破綻しないこと、およびマイグレーション失敗時に安全に切り戻せる復旧手順が存在することを守る。
既存データの変換やバックフィル処理は`design-time-migration.md`「エンドユーザーデータの移行」に従う。
DDLの変更内容を事前にテスト用テーブルで検証する場合は、対象テーブルに設定されている制約条件（外部キー制約、参照動作、既存インデックス、CHECK制約など）も忠実に再現する。
制約の組み合わせによって本番で拒否されるDDLであっても、制約のない簡易テーブルでは成功してしまい、本番適用時に予期せぬエラーで停止する恐れがあるためである。
