## セキュリティ・ロギング・エラー処理

- セキュリティ: 外部からの入力、APIレスポンス、ユーザーの画面操作など、信頼境界を常に意識する。
  - 外部入力はコマンドライン引数として安全に渡し、コード文字列を評価する実行コマンドには固定の文字列のみを渡す。
    動的な処理分岐が必要な場合は、あらかじめ定義した固定の候補から選ぶ方式にする（言語ごとの具体的な実装方法は各言語の資料を参照）。
  - 入力バリデーションは許可リスト（ホワイトリスト）方式を優先し、SQL、シェルコマンド、HTMLなどの実行・解釈文脈への直接的な文字列結合、パストラバーサル、信頼できないデータの危険なデシリアライズを避ける。
  - シークレット（パスワードやAPIキーなど）はソースコードやログ出力に含めず、権限は必要最小限に絞り込み、スタックトレースや内部ファイルパスなどのシステム内部情報をエンドユーザー画面へ露出させない。
  - Cookie認証のWebアプリでは、セッションCookieに`HttpOnly`・`Secure`・`SameSite=Lax`または`Strict`を付け、Domainを指定せず、ログイン時にセッション識別子を更新する。
    Cookie名は指定がなければ`__Host-`接頭辞（`Path=/`）を付け、別サブドメインからの上書きを防ぐ。
    既存環境での改名方式は、サブドメインの管理範囲と再ログインなどの負担から選ぶ。
  - `SameSite=None`、CSRF・Origin検査の無効化、他サイトからの埋め込み許可など、標準で有効な防御を外す場合は、Cookieが届く全エンドポイント（更新要求・埋め込み表示など）へ代わりの防御を置き、範囲をテストで固定する。
    同一オリジン制限など、新しいエンドポイントにも追加設定なしで防御が働く構造にする。
- ロギング: 障害発生時の原因究明を前提とした設計とし、構造化ログや相関IDを活用する。
  ログにはシークレットや個人情報を含めない。
- エラー処理: エラーの性質と利用目的から回復方針を選ぶ。
  恒久的なエラーは呼び出し元へ原因を返し、プログラム自体の不具合は早期失敗（fail-fast）で例外を伝播させる。
  例外の捕捉（catch）は具体的な型に限定し、広範な捕捉（catch-all）はシステムの境界に留める。
  一時障害という理由だけで再試行を追加せず、必要性と安全性は`design-runtime-jobs.md`「非同期ジョブ・リトライ設計」に従う。
  - 外部HTTP、DB、メッセージキュー、LLM APIなどでは、SDKのデフォルト値を確認し、接続・読取・プール取得などの待ち時間と、再試行を含む操作全体の時間予算を利用目的に合わせる。
    ストリーミングや長時間ジョブでは、無通信の上限と処理全体の寿命を区別する。
    運用で調整する再試行回数やタイムアウトは外部から設定可能にする。
  - 再試行前に、操作が未実行、実行中、完了、成否不明のどれかを確かめる。
    応答喪失だけでは未実行と判断せず、公開された状態照会と同じ実行識別子で結果を回収する。
    成否不明の非冪等操作は、結果を確認するまで再発行しない。
    読取専用、未実行確認済み、同じ論理操作の冪等性を確認できた場合は既存の再試行条件を使う。
  - 一時障害の解消待ち、引数修正、必要資料の取得など、失敗の種類に合う回復を選ぶ。
    権限拒否は必要な認可の手続きへ渡し、下位のツールやSDKによる再試行の追加は対象外とする。
  - 失敗原因の報告処理を行う前に、終了処理（クリーンアップ）のタイムアウト待ちが超過する場合は、その例外を捕捉して対象プロセスの強制終了とリソース回収を完了させてから、本来の失敗原因を報告する処理に戻る。
    同様の終了待ち処理が複数箇所にある場合は、停止・待機・回収処理を1つの関数に集約する（終了処理の例外によって本来のエラー報告が上書きされると、呼び出し元で真の原因を判別できなくなるため）。
  - 外部の状態取得に失敗した際に安全側の結論（中止や延期など）を採用するロジックでは、あらかじめ保護対象へのアクセス権や所有権、境界条件などから判断に必要な母集団を確定し、その母集団に属する対象の取得失敗のみを根拠とする。
    その上で、実際の運用環境でその結論が常に成立してしまわないかを現物のデータで検証する（無関係な対象の取得失敗を拾って安全側の結論が常時成立してしまうと、システム全体が恒久的に停止する原因となる）。

例外を捕捉できるのは、その場で回復する、失敗原因を判別できる文脈を付与して再送出する、公開境界・信頼境界で別の失敗表現へ変換する場合に限る。
回復には、要件や観測した欠陥を根拠とする再試行や、別の処理方法への切替えなどを含む。
主機能に不可欠な処理と補助機能を分ける。
外部出力の変動やエンドユーザーが制御できない要因で補助機能が失敗し、主機能まで止めると作業を妨げる場合は、主機能の入力・必要成果・安全性・所有権を保てる縮退を設ける。
利用できない補助機能を明示して無効化し、所有資源を回収する。
この縮退は回復として扱い、不可欠な処理の不正やプログラム自体の欠陥を隠す用途は適用対象から除く。
具体的な型を捕捉する場合も、ログを出力して続行するだけの処理、あらかじめ決めた値や空の値で失敗を隠す処理、そのまま再送出するだけの処理は書かず、例外を伝播させる。
CLIで個別エラーを捕捉して続行し、終了コードで失敗を示す処理は境界での変換に当たる。

```python
# 良い例: 対象を判別できる文脈を付与し、原因を保持する。
try:
    config = json.loads(config_path.read_text(encoding="utf-8"))
except json.JSONDecodeError as exc:
    raise ValueError(f"設定のJSONが不正: {config_path}") from exc

# 悪い例: 具体的な型でも、空辞書を返して失敗を隠す。
try:
    config = json.loads(config_path.read_text(encoding="utf-8"))
except json.JSONDecodeError:
    config = {}
```
