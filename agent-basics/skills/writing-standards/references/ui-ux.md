# 画面の設計とユーザビリティの検収

本書はエンドユーザーが操作する画面を計画、作成、変更またはレビューするエージェントが使う共通基準を定める。目的と必要な結果は`quality-principles.md`「QCDと3段判定」の消費主体・利用場面から仕様と設計を導く原則で確定する。画面では主要な操作と既存のデザインシステムを調べ、操作から結果までの流れを定める。

画面の判断は本書（共通）と`ui-ux-patterns.md`（主題別）が持ち、`ui-ux-web-rules.md`はHTML・CSS・JavaScriptでその判断を満たす手段とコードから判定できる条件だけを持つ。この分担を「画面基準の3層」と呼ぶ。

参考資料: [frontend-ui-ux-skill](https://github.com/overseek944/frontend-ui-ux-skill)、[ux-designer-skill](https://github.com/szilu/ux-designer-skill)、[Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)。これらの要点を日本語の判断基準へ再構成した。個別の数値は末尾の一次資料を典拠とする。

## 判断の順序

ユーザーの明示指示、対象プロジェクトのデザインシステムと一貫した慣例、本書の方針をこの順に適用する。既存のコンポーネント、トークン、スタイル規約を調べて同じ役割のものは再利用し、画面を使う人とその人が終える仕事を特定して、主要な操作から結果まで到達できる設計を選ぶ。

## 操作と情報

主要操作と必要な情報を作業のまとまりと判断の順で配置し、操作の結果、現在の状態、取り消し方、エラーからの復旧をエンドユーザーが分かる位置へ示す。言葉と配置はその分野の慣例とエンドユーザーの言葉を優先する。破壊的操作は頻用操作から離し、誤操作の損失に応じて確認か取り消し猶予を設け、入力を保持して再開できるようにする。

## 状態と内容

- 初期表示・処理中・結果・空・エラーを、到達する操作とともに設計し、読み込み中も配置を安定させる
- 短い値、通常の値、表示幅を超える長い値で、情報と操作の全体へ到達できることを確かめる
- モーダルと通知の使い分けは`ui-ux-patterns.md`「通知と割り込み」「モーダル、サイドパネル、全画面」に従い、無効ボタンには理由を示す

## 視覚と構造

文字・余白・色は既存のトークンへそろえ、意味を色・文言・形状で伝える。ライトとダークの両テーマを提供する画面では両方で文字、境界、背景、フォーカスを確かめる（ダークテーマの新設は要求に応じて判断する）。動きは状態の理解に役立つ用途に限り、動き軽減設定に従う。ネイティブの操作要素と意味のある見出し構造を優先し、モバイル幅から組み、左右を指定するスタイルは論理プロパティーを使い、ページ本体の横スクロールを避ける。

## アクセシビリティと性能

WCAG 2.2 AAを下限として、キーボードだけで全操作を終え、フォーカス位置を視認できる状態を保つ。入力欄とラベルを関連付け、入力エラーと非同期の結果を読み上げられるようにする。通常文字のコントラストは4.5:1以上、大きな文字と情報を伝えるUIコンポーネントの境界は3:1以上とする。操作対象はWCAG 2.2 SC 2.5.8の24×24 CSS pxを下回らず、主要なタッチ操作は44px程度を目安とする。

実際の利用環境でCore Web Vitalsを測定できる場合は、LCP 2.5秒以下、INP 200ms以下、CLS 0.1以下を良好域の目標にする。画像と埋め込みの領域を先に予約し、初期表示に不要な資源は後で取得する。性能の判定は同じ端末とネットワーク条件で測り、静穏な条件で得た値を比較に用いる。

## 完了前の実描画確認

機能の正しさ（受入シナリオの期待結果、データの反映、操作の成否）はPlaywrightを含むE2Eテストで担保する。実描画では自動テストが判定しない使いやすさを`agent-basics:review-standards`の`references/reviewer.md`「ユーザビリティレビューの判定」の観点で観測する。

ブラウザーを利用できる環境では、変更した画面を実際に描画して次を観測してから完了とする。実装したエージェントの自己点検と独立したユーザビリティレビューの双方で同じ観測を使う。

- エンドユーザーと同じクリック、入力、キーボード操作で主要な利用シナリオを結果まで終え、迷わず進めるか、次の操作が示されているか
- 操作後に現れる状態（ドロップダウン、ダイアログ、読み込み中、入力エラー、空の一覧、通知など）へ実際に到達し、画面キャプチャーで配置、文言、フォーカスと読み上げの対象、表示の意味が伝わるか
- 320px幅と400%拡大、キーボードのみの操作、利用するテーマ、`prefers-reduced-motion`、短い値と長い値
- 観測した問題を修正した後、同じシナリオと状態で解消を再確認する

描画手段には対象プロジェクトのE2E環境、Playwright、ブラウザー操作ツールを使う。ブラウザーを利用できない環境では、確認した条件と未確認の画面状態を記録し、実描画の結果を未確定として報告する。

効果が検証環境の外へ残る操作（エンドユーザーの実データへの書込、commitやpush、外部への送信など）は、対象プロジェクトの手順か設定が用意する、実データから切り離した環境（テスト用のデータ置き場を指す設定など）でだけ行う。無ければ操作の直前までを観測し、操作後を未観測として記録する。待受が`127.0.0.1`であることは切り離しの根拠にならない（ローカルのサーバーも実データへ書き込む）。

画面キャプチャーは後続の担当が観測結果を確認できる形式で保存し、取得先を記録する。

## 数値の一次資料

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/): 通常文字4.5:1、大きな文字と情報を伝える非テキスト要素3:1、SC 2.5.8の操作対象24×24 CSS px。
- [web.dev Core Web Vitals](https://web.dev/articles/vitals): LCP 2.5秒、INP 200ms、CLS 0.1の良好域。
- [Apple Human Interface Guidelines: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons): タッチ操作領域44×44 ptの目安。主要操作の余裕を設計する参考値とする。
