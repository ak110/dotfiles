# 画面の設計とユーザビリティの検収

画面を作る担当とレビュー担当が使う人の目的と操作から画面を評価し、使う人が必要な操作を見つけて目的を達成できるようにする。
エンドユーザーが操作する画面を計画、作成、変更、レビューする時の基準を置く。
原則8（読み手の文脈で書く）、原則3（観測したことだけを事実として言う）、原則6（作る者と確かめる者を分ける）を画面へ適用したものである。
HTML・CSS・JavaScriptでの実装手段と、コードから判定できる条件は`agent-basics:writing-standards/references/ui-ux-web-rules.md`が扱う。

参考資料（frontend-ui-ux-skill、ux-designer-skill、Web Interface Guidelines、Impeccableの画面設計基準）を日本語へ翻訳・再構成した。
原典と著作権・許諾表示（MIT License、Apache License 2.0）は[第三者表示](../../../THIRD-PARTY-NOTICES.md)にある。

## 用途と参考例の調査

画面の目的と必要な成果は、使う人、利用場面、次の行動から`agent-basics:writing-standards/references/design-heuristics.md`「設計の判定順」で確定する。
業務操作の画面は操作の一貫性と、文字を縮めずに得られる情報密度、読み物は行長と見出しの構造を重視し、宣伝や作品の提示は目的に合う表現を強めてよい。

- 既存画面の追加・変更は、着手前に同じ役割の画面と共通スタイル（色・余白・文字のトークン、部品）を調べ、それを使って組む。
  部品が足りなければ共通側へ足し、画面固有の見た目や意図しないブラウザー既定の外見を残さない。
  共通スタイルが未定義なら、既存画面の同じ役割に使う形を取り出し、既存の資料へ記録する。
  共通スタイルが古い、または既存画面どうしの不一致で取り出せない場合は、範囲外の画面を今回作り直さず別の変更として提案する。
  初めて作るか既存画面に共通形が無い場合は、ユーザーの指示、参考例、本書「視覚と構造」の起点の順で決め、採用した設定・部品を記録する。
  資料・ツールの導入や有料契約は要件に含まれる場合だけ行う
- 一般的な作りを求められた画面か、プロジェクトに同種の画面が無い標準的な用途では、画面を使う人が同じ対象を見て同じ判断をする複数の外部類例を選ぶ。
  実物か同じ版の画像を見て、共通する情報と操作の配置を比べ、採用・変更の理由を記録する。
  見られなかった例は別の例を探すか未確認とする
- 新規・刷新では提示画像と見本の実物から、配置・文字・色・密度のうち参考にする点を選ぶ。
  画像が無くても設計は続け、共通スタイルが無ければ必要な決定だけを既存の資料へ置く

参考: [Art Direction](https://github.com/RNA4219/anything-frontend-art-direction/blob/046e42c7de149373993109cf4a211a577b1c3bcc/references/visual-direction.md)と[Product Design](https://github.com/RNA4219/anything-frontend-product-design/blob/af656d5fafc982daabcbccffe5a331802977f492/modules/product-information-architecture/SKILL.md)（RNA4219、MIT）。

## ユーザーの作業から画面を分ける

刷新では、入口と通常到達する表示・共通部を列挙し、ユーザーの通常の開始状態、判断する情報と変更する対象、何をもって完了とするかを作業別に整理する。
利用頻度と誤りの影響から代表作業を選び、開始、対象の探索、判断・操作、結果の確認までを新旧の画面構成で比べる。
既存画面を変える時は開始データと幅をそろえて利点を保つかを確かめる。
各領域には一緒に見る値と操作を置き、判断を変えない反復や入力は外した案と比べる。
同じ対象を見比べる作業は検索・一覧・詳細の文脈を保ち、別の目的や異なる対象範囲の作業は入口を分ける。
既存のタブやデータの分類をそのままユーザーの分類にしない。
出発点で次の場所を選べない、別の場所に移ると条件や選択を失う、結果確認に不要な往復を要する構成は、部品が統一されていても見直す。

## 判断の順序

画面ごとに、ユーザー、開いた時にする判断、次の行動を一文で定める。
その判断に最初に必要な見出し・値・本文・主操作のうち、どれを先に見せるかを決め、次に見る項目を読む順に並べる。
例えば設定では現在の分類と値を先に見せ、出所と形式は値の近くに置くが、同じ強さで表示しない。
主役を線で囲んだり色を足したりする前に、補足やナビゲーションの強調を弱め、先頭で競合する操作を分ける。

優先順は、ユーザーの明示の指示、プロジェクトのデザインシステムと慣例、本書「用途と参考例の調査」で調べた類例の共通形、本書の方針の順とする。
既存画面では、目標と関係しない外見、挙動、文言を保ち、作り直す範囲は新しい様式に統一する。
既存機能の仕様を変える場合は、同じ機能を持つ全画面と共通部品の全呼び出し元を調べ、共通の仕様を決めて適用する。
名指しされていないことだけで以前の仕様を残さない。
依頼が画面を明示的に限定した場合はその範囲を守って不統一を報告する。
画面固有の確定した仕様や公開契約が変わる場合は、差と利害を示してそろえるか確認する。
事実、数値、機能を述べる文言の差し替えと新しい主張の追加は、ユーザーの指示がある場合に限る。

コンポーネントは見た目ではなく要素の目的で役割を判定し、同じ役割の既存のコンポーネントを再利用する。
共通部品の仕様変更は全呼び出し元に適用し、新旧を選ぶ引数を足さない。
送信項目名、文面、配置など画面の構成や送信先に必要な差は引数で渡せる。
値の表示を切り替える要素と、値を入力して送信する要素は、扱う値が同じでも別の役割とする。
近くの要素を流用する前に、同じ目的の要素が画面間でどの形に統一されているかを調べ、一致しなければ画面間の形を採用する。
例えば、月・日付の表示切替、ページ送り、条件による表示対象の限定は、同じ画面の送信用フォームではなく、画面間で同じ目的に使われる形にそろえる。
エンドユーザー、開発者、次に編集するエージェントのどれかの利便のために、他へ理解・操作・保守の負担を移さない（努力目標。使いやすい画面を継続して改善するため）。

## 操作と情報

表示する情報は、エンドユーザーの目的、利用場面、判断、次の操作から選び、タスクのまとまりと思考の順に置く。
システムが確実に判断できる値や選択（既定値、入力済みの情報から決まる項目など）はエンドユーザーに選ばせたり入力させたりせず、確実に代わりに行える処理（入力途中の保存、入力値の書式の整形など）はエンドユーザーの操作として残さない。
推測が外れると害がある値は推定値を変更可能な初期値として示す。
代わりに行う処理は、エンドユーザーが予測でき、入力・キーボード操作・読み上げを中断せず、取り消せる範囲に限る（入力途中で予告なくフォーカスを移さない。WCAG 2.2 SC 3.2.2 On Input）。

情報の過不足は説明の有無や要素の数ではなくエンドユーザーの判断と操作から評価し、必要な情報の欠落と、判断に寄与しない情報の常時表示を使いやすさの不具合として扱う。
通常の使いやすさは通常の状態の判断と操作で確かめ、狭い表示幅や極端な値での退避表示は別に評価する。
0、空、該当なし、旧仕様の情報も判断に要るかで表示を決め、0が現在の状態を伝える場合は表示を保つ。
操作の結果、現在の状態、取り消し方、エラーからの復旧手順は、ひと目で分かる位置に示し、文言はエンドユーザーが使う用語に合わせる。

- スローガン調の副題、見出し直下の冗長な解説、見れば分かる操作を言い直す補助テキストは省く。
  補足は、配置とラベルから分からない対象範囲、入力形式、制約、不可逆な影響、単位に限る。
  操作の判断に必須ならラベルか近くの常時表示で伝える
- 取り消せない操作はよく使う操作から離し、影響に応じて確認か取り消しの猶予を設ける
- 入力途中のデータは保持し、安全に再開できるようにする

操作と表示の役割を区別する。
今の作業を完了する操作を主ボタンにし、元に戻る・中止は副操作、破壊的な操作は通常操作と分ける。
同じ役割の操作を、画面や状態によって別の外見にしない。
1つの対象を移動する前後の操作は一組だけ置く。
別の対象（例えば前後の文書と現在の文書内の検索一致）を移動するなら、対象名と配置で区別する。
見出し・ラベル・状態名にはユーザーが使う言葉を使い、保存形式のキーや列挙値は照合・入力に必要な場合だけ補足に置く。

## 状態と内容

- 初期表示、処理中、完了、空、エラーの各状態を、そこへ遷移する操作とあわせて設計し、読み込み中も配置を固定する
- 極端に短いデータ、一般的なデータ、表示幅を超える長いデータで、画面全体の情報と操作に到達できるようにする
- サンプル・初期データ・デモの文言は、ダミーの欧文や仮の文言（「見出しをここに」など）ではなく、製品のエンドユーザーと用途に合う実際の文で書く
- サンプルの人名・組織名・数値・日付は利用場面に合う自然な値にし、不自然に丸い数値や同じ値の繰り返しを避け、名前は実在と取り違えられない架空のものにする
- 入力不足を理由に送信ボタンを無効にしない。
  それ以外で操作できないボタンは無効にし、対象近くの進捗などで理由が自明でない場合は、理由と次にできることを示す

## 視覚と構造

書体、文字、余白、配色は共通トークンを使い、点在する値をそろえるだけでなく、次の順に役割を割り当てる。

1. 本文の書体・サイズ・行間を決める。
   ページ見出し、区画見出し、項目名、本文、補足を少数の段へ割り当て、隣り合う段に見分けられる差を付ける。
   サイズが同じ役割は太さ・置き場所・間隔で区別する。
   長い一覧や説明を一律に太字にせず、見出しと判断を左右する値だけを太くする。
2. 余白の基準単位と段を決める。
   例えば4pxか8pxの倍数を使い、ラベルと値は近く、別の項目はその間より離し、区画の間はさらに離す。
   枠の端と文字の始点を区別し、同じ役割の文字・アイコン・行末操作は対応する基準線にそろえる。
   別の役割は対比で示す。
   囲みや面は、余白と整列だけでは関係が伝わらない場合に使う。
3. 背景、文字、補足、区切りには中立色を使い、現在地や主操作には用途を決めた強調色、成功や警告には状態色を使う。
   共通スタイルも参考例も無い業務画面ではアクセント色を1つとする。
4. 読み物は一行の終わりから次の行へ視線を戻せる長さに制限し、実際の言語・書体で確かめる。
   一覧や表に収まらないときは、判断に要る情報を選び、行・列・まとまりを変えてから文字のサイズを検討する。

デザインシステムに文字の段があればそれに従い、無い場合は本文・一覧・フォーム・ナビゲーション・ボタンの文字をブラウザー既定の16px（1rem）以上、日時・件数・補足などの補助情報とバッジを14px（既定の0.875rem）以上にする。
読み物の本文や見出しなど、既に大きい文字は縮めない。
区切りは薄い線と余白で示し、役割の無いカードの入れ子や強い影は省く。
状態の区分を併記する場合は、薄い背景の小さなバッジと状態名で示す。
選択やホバーの面の上でも、バッジの状態名と境界を読み分けられるようにする。
一覧は1件を少ない行に収める。
副情報を1行へ置く場合は、区切りを次の行に残さず、短い表示と詳細で読める完全な値を使い分ける。
情報密度は余白、行数、表示する情報の選別、列の構成で上げ、文字を基準より小さくしない。

参考: USWDSの[Typography](https://designsystem.digital.gov/components/typography/)と[Spacing units](https://designsystem.digital.gov/design-tokens/spacing-units/)から、読みやすい行長と余白の段の決め方を取り入れた（[公開方針](https://designsystem.digital.gov/about/website-policies-notices/)・[許諾](https://github.com/uswds/uswds/blob/develop/LICENSE.md)）。
GOV.UKの[Check answers](https://design-system.service.gov.uk/patterns/check-answers/)は、見出し・ラベル・値・操作の区別の比較例である（特記がない箇所は[Open Government Licence v3.0](https://www.nationalarchives.gov.uk/doc/open-government-licence/version/3/)）。
どちらも判断の参考とし、配色・数値・図版・コード・原文は転載しない。

### 自動更新

画面の外で変わるデータは、操作を待たずに表示を更新することを基本とする。
通知と定期取得のいずれを使うかは、変化の頻度と取得の費用で選ぶ。
更新時に編集中の入力を保つ。
正常時、初回取得中、一時失敗からの自動回復中は取得エラーを表示しない。
対象が同じなら直前の成功値と編集中の入力を保つ。
期限付きの取得と間隔を延ばす自動で再試行し、初回と再試行の失敗が続いた時だけ短い案内と同じ対象を再取得する1つの操作を示す。
確定した空や恒久的な制約、保存の成否とは区別する。
観測元と最後の成功時点を基に、未取得・有効な現在値・前回値を区別する。
最新でない値を残す場合はその旨と最後に取得できた時刻を対象の近くに示し、意味のある固定区分は鮮度と混同しない。

### 表現と表示環境

色と寸法はプロジェクトのトークンで決め、ライトとダークで別の値の組を持てる構造にする。
この構造はテーマの追加や切り替え機能の提供を求めない。
要素の役割と関係は、説明を足す前に、配置、余白、グルーピング、視覚的な階層と短いラベルで示す。
新規画面や外見の作り直しでは、用途と参考例を基に、写真、イラスト、図、画像なしから表現を選び、文字の役割と可読性に合う書体を選ぶ。
既存の素材と書体を優先し、必要な素材がなければ利用できる画像検索や画像生成も比べる。
写真やイラストが担う役割を無関係な図形やアイコンで代用せず、操作のアイコン、ロゴ、編集可能な図には目的に合うベクター表現を保つ。
「完了前の実描画確認」で、画像表現と書体を用途と採用した参考例に照らし、読みやすさと既存の画面との一貫性を確かめる。
ライトとダークの両テーマを提供する画面は、両方で可読性、境界線、背景色、フォーカスの見え方を確かめる（ダークテーマの新設は要件で決める）。
ブラウザー標準の操作要素と正しい見出しの階層を優先し、製品の主な利用環境を起点に組み、余白と配置は論理プロパティで指定し、ページ全体の意図しない横スクロールを防ぐ。

### 画面の動き

- 動きは状態の変化を伝えるために使い、装飾のためには使わない。
  表示や移動の起点と到達先、関係する要素が伝わるようにする。
- 部品ごとでなく状態変化を列挙する。
  表示・非表示、移動、大きさ・内容・数値の変化のほか、押下・ホバー・読み込み・完了・エラーも含める。
  各変化をエンドユーザーが理解できるか、突然切り替わっていないかを確かめる。
- 同じ種類の変化には同じイージング曲線と時間を使い、既存の画面で値が混在する場合は1組にそろえる。
- 動きは速く軽くし、繰り返す操作ほど短くする。
  業務画面の状態遷移は150〜250msを目安とし、読み込み時の装飾的な登場演出は省く（努力目標。反復操作を待たせないため）。
- ドラッグと大きさの変更は操作に直接追従させ、動きの途中で再び操作した時はその時点の状態から自然に続ける。
- 必要な要素だけを動かして描画負荷を抑え、ちらつき・配置のずれ・はみ出しを起こさない。
- OSの動き軽減設定に従い、設定時は装飾の動きを止め、状態を伝える動きも移動や拡大を伴わない表現（即時の切替、短いフェードなど）へ置き換える。

画面の主題別の基準、アクセシビリティ、完了前の確認は[画面の主題別設計と実描画確認](ui-ux-topics.md)を参照する。
