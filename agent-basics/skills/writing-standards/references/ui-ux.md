# 画面の設計とユーザビリティの検収

本書は、エンドユーザーが操作する画面を計画、作成、変更、またはレビューするエージェントが参照する共通基準をまとめたものである。
画面の目的や達成すべき成果は、`quality-principles.md`の「QCDと3段判定」に示された「利用主体と利用場面から仕様と設計を導く原則」に基づいて確定する。
画面設計では、主要な操作フローと既存のデザインシステムを調査し、ユーザーの操作から結果に至る一連の流れを定義する。

画面設計に関する基準は、本書（共通方針）と`ui-ux-patterns.md`（主題別の設計）で定め、`ui-ux-web-rules.md`はHTML、CSS、JavaScriptによる実装手段やコードから機械的に判定できる条件を扱う。この役割分担を「画面基準の3層」と呼ぶ。

参考資料: [frontend-ui-ux-skill](https://github.com/overseek944/frontend-ui-ux-skill)、[ux-designer-skill](https://github.com/szilu/ux-designer-skill)、[Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)。これらの要点を日本語の判断基準として再構成した。具体的な数値基準は末尾の一次資料を典拠としている。

## 判断の順序

基準を適用する際は、ユーザーからの明示的な指示、対象プロジェクトのデザインシステムや一貫した慣例、本書の方針の順に優先する。
既存のUIコンポーネント、デザインコード、スタイル規約を調査し、UI要素の目的で役割を判定して、同一の役割を持つ要素を積極的に再利用する。
値の表示を切り替える要素と、値を入力して送信する要素は、扱う値の種類が同じでも別の役割とする。
同じ画面にある要素や見た目が近い要素を流用する前に、同じ目的の要素がプロジェクトの画面間でどの形に統一されているかを調べる。
同じ画面の要素と画面間の形が一致しない場合は、画面間の形を採用する。
例えば、月・日付の表示切替、ページ送り、表示対象を条件で限定する操作は、同じ画面の送信用入力フォームと区別して、同じ目的で使われる画面間の形にそろえる。
画面を利用するユーザー像とそのユーザーが達成したいタスクを明確にし、主要な操作から目的の結果までスムーズに到達できる設計を採用する。

## 操作と情報

主要な操作要素と必要な情報は、ユーザーのタスクのまとまりや思考の順序に沿って配置する。
操作の結果、現在の状態、取り消し方法、およびエラーからの復旧手順は、ユーザーがひと目で把握できる位置に明示する。
文言や配置は、その業務分野の慣例やエンドユーザーが実際に使う用語を優先して選定する。
過剰なセカンダリラベルや説明文を追加するのではなく、配置や余白などレイアウト自体の工夫で意図を伝える。
スローガン調の副題、見出し直下の冗長な解説、見ただけで用途が分かる操作や構造を言い直す補助テキストは配置せず、補足テキストはレイアウトとプライマリラベルだけでは判断できない制約事項、不可逆な影響、単位などの伝達に限定する。
元に戻せない破壊的な操作は普段よく使う操作から物理的に離して配置し、誤操作による影響の大きさに応じて確認ダイアログの表示や取り消し猶予期間を設ける。また、入力途中のデータを保持していつでも安全に再開できるようにする。

## 状態と内容

- 初期表示、処理中、処理完了（結果表示）、データが空、エラー発生の各状態を、それぞれの状態へ遷移する操作とあわせて設計し、読み込み中も画面レイアウトが不用意に動かないようにする
- 極端に短いデータ、一般的なデータ、表示幅を超える長いデータが表示された場合でも、画面全体の情報と操作へ問題なくアクセスできることを確認する
- モーダルダイアログとトースト通知の使い分けは`ui-ux-patterns.md`の「通知と割り込み」「モーダル、サイドパネル、全画面表示」に従い、操作できないボタンを無効化（disabled）する場合は無効になっている理由を明示する

## 視覚と構造

フォントサイズ、余白、カラーパレットは既存のデザイントークンに統一し、要素の意味や重要度を色、文言、形状の組み合わせによって表現する。
要素の役割や関係性は、長文の説明を追加する前に、配置、余白、グルーピング、視覚的な階層構造、および端的なラベルによって直感的に伝わる設計を心がける。
ライトテーマとダークテーマの両方を提供する画面では、両環境で文字の可読性、境界線の見やすさ、背景色、フォーカスインジケーターの視認性を確認する（ダークテーマの新規作成は要件に応じて判断する）。
アニメーションなどの動きは画面状態の理解を助ける目的に限定し、OSの動き軽減設定（`prefers-reduced-motion`）を尊重する。
ブラウザー標準のネイティブ操作要素と意味的に正しい見出し構造（h1〜h6）を優先し、モバイル幅（狭い画面）を起点にレイアウトを組み立てる。左右の余白や配置の指定には論理プロパティを用い、ページ全体に意図しない横スクロールが発生しないようにする。

## アクセシビリティと性能

WCAG 2.2レベルAAへの準拠を最低限の基準とし、すべての操作をキーボードのみで完結でき、現在のフォーカス位置が明確に視認できる状態を維持する。
入力欄には必ず対応するラベルを関連付け、入力エラーや非同期通信の結果はスクリーンリーダーで正しく読み上げられるように実装する。
テキストのコントラスト比は通常文字で4.5:1以上、大きな文字や情報を伝えるUI部品の境界線は3:1以上を確保する。
操作可能な領域のサイズはWCAG 2.2 SC 2.5.8で定められた24×24 CSS pxを下回らないようにし、主要なタッチターゲットは44px程度を目安に確保する。

実際の運用環境でCore Web Vitalsを計測できる場合は、LCP 2.5秒以下、INP 200ms以下、CLS 0.1以下を良好域の達成目標とする。
画像や埋め込み要素の表示領域は事前にスタイル等で確保し、ファーストビューの表示に不要なリソースは遅延読み込み（lazy load）を行う。
パフォーマンス測定は同一の端末およびネットワーク環境で実施し、バックグラウンド処理のない安定した状態で取得した値を比較に用いる。

## 完了前の実描画確認

機能的な正確さ（受入テストシナリオの期待結果、データの更新反映、各種操作の成否など）は、`testing.md`「検証単位の選定」で選んだ層の自動テストによって担保する。
実際の画面描画による確認では、自動テストでは判定が難しい使いやすさや視覚的な違和感を、`agent-basics:review-standards`の`references/reviewer.md`「ユーザビリティレビューの判定」の観点に沿って検証する。

ブラウザーを利用できる環境では、変更を加えた画面を実際にブラウザー上に描画し、以下の項目を確認した上で作業完了とする。この確認は、実装担当エージェントによる自己点検と、独立したユーザビリティレビューの双方で共通して実施する。

- エンドユーザーと同じ手順でクリック、入力、キーボード操作をし、主要な利用シナリオを最初から最後まで実行して、迷うことなくスムーズに進められるか、次に取るべき操作が明確に示されているかを確認する
- 操作に伴って表示される各種状態（ドロップダウンメニュー、ダイアログ、ローディング表示、入力エラー表示、空の一覧、通知トーストなど）を実際に表示させ、画面キャプチャーを取得して、配置、文言、フォーカス位置、スクリーンリーダーの読み上げ対象、表示意図が正しく伝わるかを確認する
- 画面幅320pxでの表示、400%への画面拡大、キーボードのみでの操作、提供する各種テーマ（ライト/ダーク）、`prefers-reduced-motion`の有効化、極端に短い値や長い値が入力された場合の表示崩れがないかを確認する
- 観測によって見つかった不具合や使いにくさを修正した後は、同一のシナリオと状態で再度画面を描画し、問題が完全に解消されたことを確かめる

画面描画には、対象プロジェクトに導入されているE2Eテスト環境、Playwright、またはブラウザー自動化ツールを使用する。ブラウザーを利用できない環境の場合は、確認できた前提条件と未確認の画面状態を明確に記録し、実描画による確認結果を未確定として報告する。

本番データへの書き込み、Gitのcommitやpush、外部サービスへの通信など、検証環境の外部に影響が残る操作については、対象プロジェクトの手順や設定によって本番データから安全に隔離されたテスト専用の環境でのみ実行する。安全な隔離環境が用意されていない場合は操作の直前までの描画を確認し、操作後の状態は未確認として記録する。接続先が`127.0.0.1`（ローカル環境）であっても、ローカルサーバーが本番データへ直接書き込む構成もあり得るため、それ単体では隔離の根拠とみなさない。

取得した画面キャプチャーは、後続のレビュー担当者が確認できる形式で保存し、保存先のファイルパスを記録に残す。

## 数値の一次資料

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/): 通常文字のコントラスト比4.5:1以上、大きな文字および情報を伝える非テキスト要素のコントラスト比3:1以上、SC 2.5.8における操作ターゲットサイズ24×24 CSS px以上。
- [web.dev Core Web Vitals](https://web.dev/articles/vitals): LCP 2.5秒以下、INP 200ms以下、CLS 0.1以下の良好域基準。
- [Apple Human Interface Guidelines: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons): タッチ操作領域として推奨される44×44 ptの目安。主要な操作要素の余白設計における参考値とする。
