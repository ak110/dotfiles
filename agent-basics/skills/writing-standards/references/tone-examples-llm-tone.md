# LLM口調

本書は、LLM特有の不自然な言い回しを避け、読み手が適切に判断できるよう主張、操作、結果を自然に表現するための指針と用例をまとめたものである。
例文は着眼点を示すためのサンプルであり、実際に適用する際は元の情報の事実関係、前提条件、不確実性の度合いを維持する。
判定基準は`writing.md`に従い、各用例も通常の文章校正ルールに沿って確認する。
専門用語や各種概念は、議論や解説に必要な意味に合わせて正確に用いる。

## 名指し参照の読込方法

名指し参照は`../SKILL.md`「名指し参照の読込方法」に従う。

| 時点または条件 | 全文読む資料 | 契機 | 配送操作 |
| --- | --- | --- | --- |
| 本文がこの資料の基準を使う場面で、資料を選択して取得する時 | `writing.md` | 判断 | `read:agent-basics:*/skills/writing-standards/references/writing.md` |

## 機械処理へ当てはめた動詞

人や物の動きを表す比喩的な動詞を使わず、システムの処理内容を直接表現する。

| 分類 | 避ける表現 | 書き換え |
| --- | --- | --- |
| 動詞の当てはめ | `本番データを引く` | 本番データを読む |
| 動詞の当てはめ | `消えた分は夜間の処理が拾う` | 夜間の処理でまとめ直す |
| 動詞の当てはめ | `書き込みも通る` | 書き込みもできるようになっている |
| 動詞の当てはめ | `構成を選ぶときに効く` | 知っておいてほしい |
| 動詞の当てはめ | `全クライアントに響く` | 全クライアントのダッシュボードも重くなる |

## 場所の比喩名詞

場所を示す比喩表現を使わず、該当する構成要素を具体的に特定する語を用いる。

| 分類 | 避ける表現 | 書き換え |
| --- | --- | --- |
| 場所の比喩名詞 | `入口` | 公開エンドポイント |
| 場所の比喩名詞 | `受け口` | VPNの外から届くためのURL |
| 場所の比喩名詞 | `トークンを出す口` | トークンを発行するエンドポイント |
| 場所の比喩名詞 | 接続相手を指す`依存先` | つないでいる先 |

なお、WI間の`depends_on`や、ソフトウェア、パッケージ、モジュールなどの依存関係（dependency）を指す`依存`や`依存先`という語は、この対象外とする。

## 英語の定型句の逐語訳

英語の定型句をそのまま直訳せず、読者が処理結果や動作を直感的に理解できる表現に改める。

| 分類 | 避ける表現 | 書き換え |
| --- | --- | --- |
| 英語直訳句 | `中継しても足すものがない` | 中継しても得られるものがない |
| 英語直訳句 | `失効が効く` | 次のリクエストから拒否される |

## 読み手の分野の呼び名

書き手独自の略称や作業用の仮の名前を使わず、読み手の専門分野で一般的に使われている用語や動詞を用いて記述する。

| 分類 | 避ける表現 | 書き換え |
| --- | --- | --- |
| 抽象動詞（インフラ担当者向け） | `社内VPNからしか入れない` | 社内VPNからしかアクセスできない |
| 抽象動詞（経理担当者向け） | `前受金として受けて売上にする` | 前受金として計上し、役務の提供時に売上へ振り替える |
| 抽象動詞（デザイナー向け） | `Figmaの値がボタンに届く` | Figmaの値がボタンに反映される |
| 1語の言い換え | `夜間の処理`（夜間バッチを指す） | 夜間バッチ |
| 作業用の名前 | `条件Bでは失敗率が下がった` | 再試行の間隔を2倍にした条件では失敗率が下がった |
| 文書内の略称 | `以下「高」と呼ぶ` | 優先度が高い問い合わせ（略称を作らず言葉で書く） |

## 予告と総括

文章は結論や次に必要な操作から書き始める。前置きや結びを置く場合は、読者の判断に影響を与える実質的な情報を含める。

```text
例文: 設定はJSONで保存する。
説明: 読者が知るべき保存形式を直接示す。
```

```text
例文: テスト設計は実装前の仕様策定段階から開始する。テストケースは境界値を網羅する。
説明: 着手する時期と検証する範囲を明確に示す。
```

## 空虚な形容

曖昧な形容表現を避け、評価する対象、成立条件、観測された結果を具体的に記述する。

```text
例文: キャッシュの導入後、DBクエリ回数が減り、応答時間が短くなった。
説明: 観測された具体的な変化を記述する。因果関係や測定値は、客観的に確認できた根拠の範囲内で述べる。
```

```text
例文: 本UIはメニューを2階層に抑え、主要操作を1クリックで完了する構造とする。
説明: 画面の構造や操作回数を数値を用いて具体的に示す。
```

## 空虚な動詞

中身のない抽象的な動詞を避け、説明対象とその内容を、具体的な目的語と動詞の関係によって明確にする。

```text
例文: APIのレスポンスボディの構造とステータスコードの対応を示す。
説明: 何を対象としてどのような関係を説明するかが一目で分かるように記述する。
```

## 接続の型

並列の関係にある情報は同じ文構造で整理し、因果関係や前提条件は接続詞や文のつながりから自然に読み取れる形にする。

```text
例文: タイムアウト値・リトライ回数・ログレベルの3項目を設定ファイルで指定する。
説明: 同じ手段で設定する項目をまとめて示す。
```

## 翻訳調・英語統語

判断を下した主体、観測事実、その根拠を正確に対応付けて記述する。
システムの動作や結果として得られた値は、それをもたらした主体を主語にして説明する。
確定している事実と未確定の事項は、元の情報と同じ確実性の度合いを保って書き分ける。
エージェント自身が実際に検証して確認した内容は、確認した条件を添えて言い切りの形で書く。
ユーザーが条件や限定を付けて述べた内容は、その条件や限定をそのまま維持する。

```text
例文: 担当者がログを確認し、キャッシュへの要求が失敗したと判断した。原因はまだ分からない。
説明: 判断した主体、判断の根拠、未特定の事項を明確に区別して示す。
```

```text
例文: 集計結果は成功が8件、失敗が2件であることを示す。システムは失敗した要求を再実行する。
説明: 集計結果の数値と、処理を行う主体の動作を直接記述する。関係性が自然であれば無生物主語を用いてもよい。
```

```text
例文: この処理は結果を保存する。
説明: 処理が実行する動作を直接的に記述する。
```

```text
例文: 入力には整数を指定する。
説明: 受け付ける入力値を具体的に示す。必要な制約や除外条件も漏れなく記述する。
```

```text
例文: 本設定は再実行の開始時に中間ファイルを削除する。削除しない場合は前回の出力が残り、結果が変わる。
説明: 設定によって行われる動作と、その動作が行われない場合に生じる影響を対応付けて説明する。
```

## メタ構造宣言

見出しで主題を明確に示し、本文では前置きを省いてその主題に関する具体的な仕様や手順から書き始める。

```text
例文: 検索処理はクエリを正規化してからベクトル検索を実行する。
説明: 操作の対象と実行順序を端的に記述する。
```

```text
例文: キャッシュキーはリクエストURLとAuthorizationヘッダーのハッシュで構成する。
説明: キャッシュ設計を説明する節の中で、キーの構成要素を直接的に示す。
```

## AI偏愛語・名詞比喩・造語

AI特有の抽象的な愛用表現、名詞の比喩、独自の造語を使わず、対象の具体的な性質、観測可能な構造、客観的な数値を記述する。
体験談や個人の感想に言及する場合は、本人が実際に述べた内容の範囲にとどめる。

```text
例文: 検査結果を確認する。変更内容を比較する。バージョンを記録する。
説明: 対象と動作を自然な名称で示し、技術用語を一字へ縮めない。
```

```text
例文: 変更箇所を読んだが、まだ原因を理解できていない。
説明: 調査した対象と、現時点で未特定である内容を正確に対応付けて記述する。
```

```text
例文: 会議で初めて自分の案を説明できてうれしかった。
説明: 本人が語った具体的な出来事と感情を、誇張せずそのまま伝える。
```

```text
例文: 本ライブラリは入出力を関数3つに限定し、内部状態を持たない。利用側は各関数を単体で呼び出せる。
説明: ライブラリの具体的な構造と、利用側が実行可能な操作を明確に示す。
```

```text
例文: 本規範はレビュー時の判定条件を定める。判定条件を満たさない変更は差し戻す。
説明: 文書が定めている具体的な内容と、その条件に基づいた対処方針を示す。
```

## 唐突な否定と不変の表明

前後の文脈における問いや話題に自然に対応する内容を記述する。
否定、除外、あるいは仕様が変わらないことの表明は、読者が判断や操作をする上で実際に必要となる場合に限って明記する。

```text
例文: 検証を除く変更を記録する。
説明: 対象の一部を除く条件を同じ文で限定し、独立した否定文を重ねない。
```

```text
例文: その2件をサブエージェントの一覧へ加える。
説明: 対象の分類について問われている文脈において、対象とその対処方法を直接的に示す。
```

```text
例文: レーンの検証を妨げる確定済みの既存不良は、メインが修正対象を同じレーンへ名指しして認可する。
認可を受けたレーン担当は、計画の実装と別のcommitで修正する。
説明: 認可を行う主体と条件、実際に修正を担当する主体と修正方法を正確に対応付けて説明する。
```

```text
例文: 実データで2回目以降の一覧が0.15秒を超えていたため、変更のないファイルの再確認と時刻の整形を省く。返す一覧の内容は変えない。
説明: パフォーマンス改善の説明では、出力結果が変わらないかどうかも読者の重要な判断材料となるため、その点についても明記する。
```
