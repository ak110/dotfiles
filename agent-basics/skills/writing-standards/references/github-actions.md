本書は、GitHub Actionsにおけるワークフロー定義の記述スタイル基準をまとめたものである。

## 基本

- ワークフロー定義ファイルは、`actionlint`および`yamllint`を用いて静的に検証する。
- 外部のActionを参照するときは、タグの書き換えを防ぐために`uses: owner/repo@<commit-sha> # vX.Y.Z`形式でコミットSHAを固定（ピン留め）し、Renovateやpinactなどのツールを使ってバージョンを更新する。

## 権限と秘密情報

- `permissions:`設定はワークフローまたはジョブ単位で最小権限に絞り込む（原則として`contents: read`とし、書き込み権限が必要なジョブにのみ`contents: write`を付与する）。
- シークレット値は`${{ secrets.NAME }}`経由で参照し、シェルスクリプトの`run`内にハードコードしない。
- 外部から送られた信頼できないプルリクエストに対して`pull_request_target`トリガーを使用しない（レビュー前のコードによる任意のコマンド実行を防ぐため）。

## 並行制御と冪等性

- 同じリソースを操作するワークフローには`concurrency:`を設定する。リリース関連のワークフローでは途中でキャンセルされないよう`cancel-in-progress: false`を指定し、通常のPR向けCIなどでは古い実行を打ち切るため`cancel-in-progress: true`とする。
- リリースやパッケージの公開処理では、既存のGitタグやGitHub Release、公開済みパッケージの存在を確認し、再実行された場合でも二重作成が発生しない冪等な作りにする。

## 破壊的ステップと事前検証

- 破壊的な変更や公開を伴うステップ（タグ作成やpush、PyPIへの公開、コンテナーレジストリへのpush、GitHub Releaseの作成など）を実行する前には、必ず事前検証ステップを配置し、検証が失敗した場合は後続処理を実行させないようにする。
- 破壊的なステップが複数ある場合は、失敗時の復旧コストが高い処理を後ろに配置する（例えば、一度公開すると取り消せないPyPI公開は、Dockerイメージのビルドよりも後に実行する）。
- リリース直後に自身のパッケージを参照できずに依存解決が失敗する場合は、`dependency-management.md`の「公開待機設定」に記載された対処手順に従う。

## トリガーと出力

- ワークフローのトリガー、キャッシュのキー、ジョブ間の依存関係は、検証が必要な条件や依存ファイルの変化に合わせて適切に設定する。
- ステップ間で値を受け渡すときは`$GITHUB_OUTPUT`を使用し、非推奨となった`::set-output`は使用しない。
- `run`ステップのシェルスクリプトでは未定義変数の参照や途中のコマンド失敗を確実に検知できるようにし、パイプラインの途中エラーを拾えるよう`pipefail`を有効にする。
