# エージェント向け文書品質（基本）

本書はエージェント向け文書の責務、記述内容、条件の書き方および語調の基準を定める。エージェント向け文書は、エージェントが直接読み込む文書（`AGENTS.md`・`CLAUDE.md`・ルール・`SKILL.md`・サブエージェント定義・`references/`・`<役割名>.subagent.md`と`<役割名>.parent.md`・hook関連の文書）を指す。
規定の追記と記述量の管理は`agent-documents-additions.md`が定める。
本書が理由に挙げる読み手（LLM）の傾向は運用で観測した傾向に基づくリスクモデルであり、個別の環境とモデルでの成立は実際の観測で確かめる。

## 名指し参照の読込方法

本文の各参照の適用条件を保ち、選んだ資料の指定範囲を取得してから、その基準を使う具体的な判断へ進む。起動時の行の資料は起動本文とともに届く。

## 責務と構成

### 冒頭の責務と目的

- 特定の役割が読む文書（agent定義、スキル、`<役割名>.subagent.md`、`<役割名>.parent.md`など）は冒頭で担当する責務、担当しない責務、最初に行う行為を示す。読み手は文書内に登場する役割の記述を自身の役割として取り込むことがあるため、読み手自身の責務を冒頭で特定する
- 冒頭の1〜2文で適用判断の核となる目的を述べる。`description`へ書く範囲は、スキルでは`agent-skills.md`「YAML frontmatter」、サブエージェント定義では`sub-agents.md`「Claude Codeのfrontmatter」に従う

### 置き場所と配送

- 区分の目安は、常時参照する横断標準は`AGENTS.md`・`CLAUDE.md`本文またはpaths未指定ルール、特定パス限定則はpaths指定ルール、手順やワークフローはスキル、機械的な強制や自動検証はhook、調査の隔離や冗長出力の抑制はサブエージェントとする
- 置き場所（保存先）は、読込契機と読むエージェントに加えて、その置き場所が届く読み手の範囲でも判定する。規定が成立する理由（共有branchの状態、チームの合意、特定ホストの制約、個人の運用判断など）から守るべき読み手の範囲を特定し、双方向に比べる。狭すぎると守るべき主体へ届かず、広すぎると適用対象でないエージェントが規定を自身へ適用する。
  ユーザーが置き場所を指定して範囲が合わない場合は、指定どおり書き、同じ応答で範囲が合う置き場所と、判断を入れ替える値（チーム共通か個人の運用かなど）を示す。置き場所は自ら変えない（目的と認可の変更を伴う場合はユーザーの判断を得る）

<例>
個人のルール: `~/.claude/rules/`配下、`CLAUDE.local.md`
全員とCIが読む規範: `AGENTS.md`、`CLAUDE.md`、プロジェクトスキル
全配布先の規範: 配布物の`rules/`と`skills/`
</例>

- 役割別規範は読み手と読込契機で配置する。全エージェントに適用する規範と、委譲元・委譲先の片側だけの規範を分ける。双方が守る受け渡し規定には共通の定義元を設ける。起動時に常に配送する規範を常時規範と呼ぶ
- 読込の階層は、常時ロード、役割別注入、スキル起動時、役割起動時、明示読取に分ける。各階層が読み手へ実際に届く契機をホストの仕様から確かめる。明示読取以外は、その主題の操作にまだ入っていなくても起動とともに全文を読む
- どの起動区分のエージェントへ届くかは、対象ホストの配送仕様と実装で確かめる
- プロジェクト規範は対象リポジトリが規範として定める指示（`AGENTS.md`、`CLAUDE.md`、`.claude/rules/`、プロジェクトのスキルなど）を指す。プロジェクト方針はプロジェクト規範に加え、README、コードコメント、設定など規範化されていない記述に書かれた方針を指す
- スキルとエージェントの責務配置は`agent-skills.md`と`sub-agents.md`に従う。委譲元側の文書は受渡しと検収に専念し、委譲先固有の手順は委譲先側の文書に持たせる（`sub-agents.md`「`<役割名>.parent.md`と`<役割名>.subagent.md`の組」）。両者の指示を同じ文書へ併記すると、委譲元が委譲先の制約を自分へ適用しやすい
- 記述はそれを必要とする工程で確実に読まれる文書へ置く。読む契機の無い記述は参照されず、特定工程だけの記述を常時ロードへ置くと全工程がその分を読む。常時ロードには優先順位、不変条件、禁止事項、完了条件とプロジェクト固有の概念を置き、言語・領域・作業種別の規範はスキルかpaths指定ルール、工程途中で要る詳細手順は`references/`と工程内の読込指示へ置く
- 同時に必要となる情報はまとめて置き、主題の異なる項目は見出しで分ける（努力目標。散在すると読込から外れ、混在すると関係の薄い項目が注意から外れる）

### 読込表

配送操作の宣言が長くなる場合は、固定資料の宣言表を同じディレクトリの別ファイルへ置き、`<!-- read-table-source: ファイル名 -->`で接続できる。本文には条件と取得する資料・節を同じ文言で残し、資料の選択から具体的な判断までの順序を保つ。起動時、役割の起動、動的資料と自文書の解決に使う行は、本体に保持する。機械が解析する配送宣言と、主体が判断に使う本文の取得範囲を区別し、宣言の分離前後で解決先・節・契機を検査する。

操作を機械判定できる行には「操作」、スキルまたは役割の受領ごとに成立する行には「起動時」、判断内容で成立する行には「判断」を宣言する。「配送操作」には、たとえば編集対象の`path:*.py`、スキル起動の`skill:writing-standards`、資料の選択取得の`read:agent-basics:*/skills/writing-standards/references/python.md`をコード表記で書く。判断の行は起動時の短い選択基準と、具体的な判断前に詳細資料を得る操作を組み合わせる。受理する全語彙、動的資料と節指定の入力形式の所在参照は`agent-toolkit:/share/read-trigger-contract.md`である。

- 読込表はスキル本体と`<役割名>.parent.md`・`<役割名>.subagent.md`の冒頭に置く表であり、行ごとの時点や条件が成立したときに、その条件が対象とする操作の前に同じ行の資料を全文読むことを示す。列は「時点または条件」「全文読む資料」「契機」「配送操作」とし、動的資料には「資料選択子」を加える。契機は操作・起動時・判断に分け、判断に使う詳細は起動時の選択基準と、判断前の観測可能な取得操作で届ける。確定操作への配送は補完とし、条件は観測できる操作や入力で書く。条件付きの読込指示は、条件の成立を判定する工程が定まるよう読込表へ集める。常時規範の書き方は`agent-documents-additions.md`「常時規範への追記条件」が定める
- 起動のたびに成立する行（起動時、着手時など）は、この文書だけが読ませる資料なら行にせず内容を本体へ置く。共有資料はその役割が全起動で判断に使う範囲だけを指す行を残し、使う範囲が節なら節を指定する。要求の種別で要否が分かれる資料はその種別を条件とする行へ分ける。本文で全文読込を課す指示にも同じ規定を適用する。「冒頭の責務と目的」には最初に必要な読込を示す
- 全文読むと定めた資料は、見出しや節名の参照で節を特定した場合も全文を読む。手順や読込表の行が一部の節を読むと定める場合はその定めに従う。起動のたびに成立する行と本文の無条件の全文読込指示は、共有資料を含めてその役割が毎回の判断に使う範囲だけを指し、範囲が節に限られる場合は節を指定する。要求の種別で要否が分かれる資料は、その種別を観測できる条件と結び付けた行へ分ける

### 定義の所有者

- 複数の文書や実装から使う手順は、定義の所有者を1つ決めて定義をそこだけへ置き、生成元と全消費側を把握する。消費側は参照、呼び出し、生成検証のいずれかで接続する。同じ判断を複数箇所が独立に定義している場合は所有者へ統合し、各消費側の範囲、認可、検証および終端条件を保つ。共通の部分責務は呼ぶ主体が使う判断の単位へ分け、役割固有の通知や後工程を連鎖して読ませる構造を整理する。統合で消費側に新たなスキル起動か`Read`が生じる場合は、増える読込量と重複が招く改訂時の食い違いを比べて採否を決める
- 類似見直しと再発防止の定義、母集団、採否、省略、終了、費用比較の所有者は`agent-basics:bugfix`である。問題の分類・重大度・見送りなど初動に使う判断は、起動時に届く同スキルの`SKILL.md`が持つ。母集団の導出、処置の階層、再発防止策の段と完了の判定など詳細の分析は、同スキルの`references/root-cause-analysis.md`が持つ。他の文書は工程固有の入力、認可、記録、検収、保存だけを持ち、同じ判断は同スキルを参照する
- スキルの初動で毎回使う判断基準は、起動時に届く`SKILL.md`へ置き、条件付きで読む`references/`には詳細の分析だけを置く（努力目標。起動したことが参照資料の取得の代わりになり、基準を読まずに初動の判断を終える）
- 文書間の参照は呼び出し元から呼び出し先への向きにそろえる（努力目標。逆向きの参照は呼び出し元の改訂を呼び出し先へ波及させる）

### 判断の偏りへの対策

- 作業の特定時点で必要な規範は、観測可能な契機と結びつける。参照資料の読込は読込表の行、スキルの起動は工程内の指示として置く（努力目標。宣言だけでは作業中に適用されにくい）。判断の偏りには、途中の仮説への固着、開いたファイルや検索結果を全体と誤認すること、自己生成した記述の影響、慣習を仕様と誤認すること、一般論の持ち込みすぎ、前のタスクの制約や識別子の持ち越しがある。これらへの対策も各作業の手順として置く。手順が求めるのは反証候補の確認、網羅性の判定、維持する契約の確認、事実と推論の区別、タスク境界での受け渡しの確認である

## 主要用語の初出定義先

文書を横断して使う主要用語（複数の文書で使う工程・レビュー・検証・判定・担当の名前を含む）は、定義元文書を1つ定めてその本文へ1文の初出定義を置き、他の文書は定義元を参照して使う。
単一の文書内でしか使わない呼称と技術用語は`writing.md`「日本語の書き方」の初出定義に従い、名前で指す時と名前を付ける時は`defined-names.md`「命名の方針」に従う。
繰り返し参照する原則や工程には短い固有名を付け、呼称を一定に保つ（努力目標。言い換えは判断の分岐を増やす）。

## 記述内容の取捨

- 記述の詳しさは`writing.md`「読み手別の追加注意点」のエージェント向け文書の項に従う。手順として書くのは読み手が目的と常識から判断できない事柄に限る。プロジェクト固有の事実の例示は「条件と範囲の記述」の開いた`<例>`で書き、硬い制約の適用条件は具体的に書く
- 自動ロード済みや呼び出し済みの規範、委譲先へ既に届いている共通ルールは、要約・再掲せず参照で示す（努力目標。読込量が増え、改訂時に片方だけが更新される）
- 実行判断に寄与しないメタ情報（管理方針、編集判断、同期対象など）はfrontmatterコメントへ移す（努力目標）

## 条件と範囲の記述

- ユーザー要求を規範や手順へ変換するときは、原文の目的、要件、対象範囲、例示の開放性、変更指示および論理関係を保ち、既存の分類へ収まる範囲へ縮めない
- 判断条件、例外条件、許容条件は確認できる事実を根拠にする。作業量や所要時間の見込みは品質、費用および完了までの時間を比べる材料として扱う。工程を省ける条件は、その工程が検出または達成する対象に当たる変化が差分にあるかで書く。規模の印象だけで条件を決めると、その工程が見つけるはずの変化を含む差分まで省かれる
- 判断を要する条文は守る価値、外れた場合の不利益、考慮する観点を代表語で示し、結論は読み手の総合判断へ委ねる
- 短い基本方針の後に手段を示す場合は、独立行の`<例>`と`</例>`で囲み、間へ1行1例の語句か`<条件>: <対応>`を書く。例示は開放集合であり、適用範囲は基本方針で決める。閉じた列挙は`quality-principles.md`「規定の区分と標示」の硬い制約を守る条文に限る

<例>
編集する対象と、規範を読む役割を示す
入力の状態ごとに条件と行動を対応付ける
共通の判断は、その判断を定める文書へ接続する
入力を受理する条件は、要求と公開契約から決める
</例>

- 独立して変化し得る制約は箇条を分ける。衝突し得る指示には優先順位か判定原則を示し、否定形や例外が重なる場合は条件と行動の対応が読める形へ分ける（努力目標。併存する指示は満たしやすい側へ判断が偏り、変更範囲の小ささを優先する指示が原因への処置を妨げることがある）
- 代替が自明でない制限には、代わりに行う行動を合わせて書く
- 既存規定の表現を変える場合は、実行時の振る舞いが変わらないことを確かめる。条文を参照へ畳むときは、畳んだ義務（判定、工程、契機）を参照先の本文が持つことを読んで確かめる（努力目標）
- 対象を一意に同定できる語で書き、指示語は具体名へ置き換える。既存の段落を編集（文の挿入、移動、削除、置換、段落の分割・統合など）したときは、後続の文の指示語の指す先が変わっていないか確かめる
- 数値の上限は、その値が無いと成果物の品質または利用場面を守れないときに設ける
- 達成すべき性質を規定する。特定のツールや実行順序へ限定する場合と、検出や判定の候補を固定の検索語・正規表現・語の一覧で閉じる場合は、その手段が必要な根拠と、一覧が対象全体を被覆する根拠を併記する。被覆を示せない場合は、対象を文脈ごと読むなど一覧の外も判定できる方法と比べて選ぶ。形式を事前に確定できない出力から未知の異常を探す手順で既知の語の一覧だけを候補とすると、一覧外の異常が確認の対象から外れる

## 語調と現行規則の表現

- 経験のある同僚が後輩へ説明するように、自然な日本語で判定基準と望ましい行動を直接述べ、役割は具体名で呼ぶ。意味、適用範囲、拘束力、条件および例外を保ったまま、法令調の硬い表現を平易な動詞へ置き換え、肯定形で書く。読み手は文脈にある文体を再生産し、否定形の宣言、指示語、法令調の語が多い文書を読んだ後は成果物も同じ文体になり、範囲外の追加要素と過剰な設計も増える。観測記録は`docs/development/audit-records.md`の「agent-basics/skills/writing-standards/references/agent-documents-basics.md：語調と現行規則の表現：2026年9月16日」にある
- 現行の規則を書き、過去の版との差異を示す表現を避ける（努力目標）
- 語調の強さは、理由が明確な重要規定で必要な範囲にする。重大度を表明するより、行動の条件を明瞭にした指示のほうが守られる
- 規範の例示は、正しい表現と満たす性質・成立条件の説明で示す。機構を説明する文だけで意図が伝わる場合は、その説明を使う。API名、オプション名と返却形式は同じ対象を指す識別子として保ち、逐語原文・過去の観測・検出用データは例示と役割を区別する
- 拘束力と努力目標の標示は`quality-principles.md`「規定の区分と標示」に従う
