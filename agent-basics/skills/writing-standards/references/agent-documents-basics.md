# エージェント向け文書品質（基本）

本書は、エージェント向け文書の責務、記述内容、条件の書き方、語調の基準を定める。エージェント向け文書とは、エージェントが直接読み込む文書（`AGENTS.md`、`CLAUDE.md`、ルール、`SKILL.md`、サブエージェント定義、`references/`、委譲先の手順書や委譲元の契約文書、hook関連の文書など）を指す。
規定の追記と記述量の管理基準は、`agent-documents-additions.md`に従う。
本書が理由として挙げる読み手（LLM）の傾向は、運用の中で観測された傾向に基づくリスクモデルであり、個別の実行環境やモデルで実際に当てはまるかは実際の観測を通じて確認する。

## 責務と構成

### 冒頭の責務と目的

- 特定の役割が読む文書（agent定義、スキル、委譲先の手順書、委譲元の契約文書など）では、担当する責務、担当しない責務、最初に行う行動を冒頭で明示する。読み手は文書内に登場する他者の役割を自身の役割と混同することがあるため、読み手自身の責務を冒頭で明確にする。
- 冒頭の1〜2文で、適用判断の基準となる中核的な目的を述べる。`description`に記載する範囲は、スキルでは`agent-skills.md`「YAML frontmatter」、サブエージェント定義では`sub-agents.md`「Claude Codeのfrontmatter」に従う。

### 置き場所と配送

- 置き場所の区分としては、常時参照する横断的な標準は`AGENTS.md`や`CLAUDE.md`の本文、またはpaths未指定のルールに配置する。特定のパスに限定される規則はpaths指定ルールに、手順やワークフローはスキルに、機械的な強制や自動検証はhookに、調査プロセスの隔離や冗長な出力の抑制はサブエージェントにそれぞれ配置する。
- 置き場所（保存先）を決める際は、読み込みの契機と対象エージェントに加えて、その置き場所の記述が届く読み手の範囲も考慮する。規定が必要となった背景（共有ブランチの状態、チームの合意事項、特定ホストの制約、個人の運用判断など）から、適用すべき読み手の範囲を特定し、過不足がないか比較する。届く範囲が狭すぎると守るべき主体へ伝わらず、広すぎると本来対象外のエージェントが自身に適用してしまう。
  ユーザーが指定した置き場所は、適切な適用範囲と一致しない場合も自己判断で変更しない。

<例>
個人のルール: `~/.claude/rules/`配下、`CLAUDE.local.md`
全員とCIが読む規範: `AGENTS.md`、`CLAUDE.md`、プロジェクトスキル
全配布先の規範: 配布物の`rules/`と`skills/`
</例>

- 役割別の規範は、読み手と読み込みの契機に合わせて配置する。全エージェントに適用する規範と、委譲元・委譲先のどちらか一方のみに適用する規範とを明確に分ける。双方が守るべき受け渡しに関する取り決めは、共通の定義元を設けて集約する。起動時に常に読み込まれる規範を「常時規範」と呼ぶ。
- 読み込みの階層は、常時ロード、役割別注入、スキル起動時、役割起動時、明示読取に分ける。各階層の記述が実際にエージェントへ届くタイミングを、ホストの仕様に基づいて確認する。明示読取以外の階層は、該当する主題の具体的な作業に入っていなくても、起動時に全文が読み込まれる。
- どの起動区分のエージェントへ届くかは、対象ホストの配送仕様と実装を確認して判断する。
- プロジェクト規範とは、対象リポジトリが規範として定めている指示（`AGENTS.md`、`CLAUDE.md`、`.claude/rules/`、プロジェクトスキルなど）を指す。プロジェクト方針とは、プロジェクト規範に加えて、README、コードコメント、設定ファイルなど規範化されていない箇所に書かれた方針も含めた全体を指す。
- スキルとエージェントの責務の配置は、`agent-skills.md`および`sub-agents.md`に従う。委譲元側の文書はタスクの受け渡しと検収に専念させ、委譲先固有の手順は委譲先側の文書に持たせる（`sub-agents.md`「`<役割名>.parent.md`と`<役割名>.subagent.md`の構成」を参照）。両者への指示を同一の文書に併記すると、委譲元が委譲先向けの制約を自身に適用しやすくなる。
- 各記述は、その情報を必要とする工程で確実に読まれる文書へ配置する。読む契機がない記述は参照されず、特定工程でのみ必要な記述を常時ロードに置くと、無関係な全工程でその分のコンテキストが消費される。常時ロードには優先順位、不変条件、禁止事項、完了条件、プロジェクト固有の概念を置き、言語・技術領域・作業種別ごとの規範はスキルやpaths指定ルールへ、工程の途中で必要となる詳細な手順は`references/`や工程内の読み込み指示へ配置する。
- 同時に必要となる情報は1箇所にまとめ、主題が異なる項目は見出しを分けて整理する（努力目標。情報が散在していると読み飛ばされやすく、無関係な内容が混在していると重要な項目への注意が削がれるため）。

### 読込表

- 読込表はスキル本体や、委譲先の手順書・委譲元の契約文書の冒頭に配置する表であり、各行の時点や条件を満たしたときに、対象の操作をする前に該当行の資料を全文読むことを示す。必須の列は「時点または条件」と「全文読む資料」である。読み手による各列の使い方は`quality-principles.md`「読込表の読み方」が定める。条件は観測可能な操作や入力内容で記述し、条件付きの読み込み指示は、条件の成立を判定する工程が明確になるよう読込表に集約する。常時規範の記述方法は、`agent-documents-additions.md`「常時規範への追記条件」に従う。
- 読込を自動化する仕組み（hookなど）を持つプロジェクトでは、その仕組みの受理契約に従って「契機」「配送操作」「資料選択子」などの列を加える。加えた列も同じ表に置き、読み手向けの表と仕組み向けの表へ同じ条件を分けて書かない。同じ条件が2か所にあると、片方だけを改訂したときに内容が一致しなくなるためである。
- 起動のたびに常に成立する行（起動時、着手時など）について、その文書でのみ読み込ませる資料であれば表の行には含めず、内容を文書本体に直接記述する。共有資料については、毎回の判断で必要な資料を指定した行を残し、注目する節があればその節を指定する。要求の種類によって要否が分かれる資料は、その種別を条件とする独立した行に分ける。本文内で全文読み込みを指示する場合も同様の基準を適用する。「冒頭の責務と目的」には、作業開始時に最初に必要な読み込みを明記する。
- 全文を読むと定めた資料は、見出しや節の名前で特定の箇所が参照されている場合でも、資料全体を読み込む。指定された節は注目箇所であり、読込量を減らす指定ではない。起動ごとに成立する行や本文中の無条件の全文読み込み指示は、共有資料を含め、毎回の判断で使用する資料を対象とする。要求の種別によって要否が分かれる資料は、その種別を観測できる条件と紐付けた行に分割する。

### 定義の所有者

- 複数の文書や実装から共通で利用する手順は、定義の所有者を1つ決定してその場所にのみ定義を配置し、生成元とすべての利用側を把握する。利用側は参照、呼び出し、生成結果の検証のいずれかで接続する。同一の判断基準が複数箇所で個別に定義されている場合は所有者に集約し、各利用側の適用範囲、認可、検証、終了条件を維持する。共通する部分的な責務は利用主体が扱う判断単位ごとに分割し、役割固有の通知や後続工程が連鎖して読み込まれる構造を整理する。集約によって利用側に新たなスキル起動や`Read`が発生する場合は、増加する読み込み量と重複による改訂時の不整合リスクとを比較して採用を決定する。
- 類似見直しと再発防止の定義、対象母集団、採否基準、省略条件、終了条件、コスト比較の定義所有者は`agent-basics:bugfix`である。問題の分類、重大度、対応見送りなど初動で用いる判断は、起動時に届く同スキルの`SKILL.md`に持たせる。母集団の導出、対処の階層、再発防止策の段階分けや完了判定といった詳細な分析は、同スキルの`references/root-cause-analysis.md`に持たせる。他の文書には各工程固有の入力、認可、記録、検収、保存の処理のみを記載し、共通の判断は同スキルを参照する。
- スキルの初動で毎回利用する判断基準は、起動時に読み込まれる`SKILL.md`に配置し、条件付きで参照する`references/`には詳細な分析手順のみを置く（努力目標。スキルを起動したこと自体で参照資料を取得したと錯覚し、基準を確認しないまま初動判断を終えてしまう事態を防ぐため）。
- 文書間の参照方向は、原則として呼び出し元から呼び出し先へ向かう形に統一する（努力目標。逆方向の参照が存在すると、呼び出し元の改訂が呼び出し先へ波及するため）。

### 判断の偏りへの対策

- 作業の特定のタイミングで必要となる規範は、観測可能な契機と結び付けて配置する。参照資料の読み込みは読込表の行として定義し、スキルの起動は工程内の指示として記述する（努力目標。単に宣言するだけでは作業中に適用されにくいため）。判断の偏り（バイアス）としては、作業途中の仮説への過度な固着、一部のファイルや検索結果のみを全体と誤認すること、自ら生成した記述への過信、単なる慣習を仕様と誤認すること、一般論を過剰に持ち込むこと、前のタスクの制約や識別子を引きずることなどが挙げられる。これらを防ぐための対策も、各作業の手順として組み込む。手順の中では、反証候補の確認、網羅性の検証、維持すべき契約の確認、事実と推測の明確な区別、タスクの境界における適切な情報引き継ぎを求める。

## 主要用語の初出定義先

複数の文書を横断して利用する主要な用語（工程、レビュー、検証、判定、役割などの名称を含む）は、定義元となる文書を1つ定め、その本文内に1文で初出定義を記載する。他の文書ではその定義元を参照して使用する。
単一の文書内でのみ使用する呼称や技術用語は、`writing.md`「日本語の書き方」の初出定義に従う。対象を名前で指す場合や新しく名前を付ける場合は、`defined-names.md`「命名の方針」に従う。
繰り返し参照する原則や工程には簡潔な固有名詞を付け、呼称を一貫して統一する（努力目標。言い換えが多くなると判断の分岐が増加するため）。

## 記述内容の取捨

- 記述の詳しさは、`writing.md`「読み手別の追加注意点」のエージェント向け文書の項に従う。手順として詳細に記述するのは、エージェントが目的や前提知識から自律的に判断できない事項に限定する。プロジェクト固有の具体的な事実を示す例示は、「条件と範囲の記述」に沿って開かれた`<例>`の形式で記述し、硬い制約となる適用条件は具体的に記述する。
- すでに自動ロードされている規範、呼び出し済みの規範、委譲先に届いている共通ルールなどは、要約や再掲をせずに参照リンクで示す（努力目標。読み込み量が増大し、改訂時に一方の更新漏れが発生しやすくなるため）。
- エージェントの実行判断に直接寄与しないメタ情報（管理方針、編集判断の経緯、同期対象など）は、frontmatterのコメントへ移動する（努力目標）。

## 条件と範囲の記述

- ユーザーの要求を規範や手順へ変換する際は、原文が持つ目的、要件、対象範囲、例示の開放性、変更指示、論理関係をそのまま保ち、既存の分類枠に収まる範囲へと狭めないようにする。
- 判断条件、例外条件、許容条件は、客観的に確認できる事実に基づいて記述する。作業量や所要時間の見込みは、品質、コスト、完了までの時間を比較・評価するための材料として扱う。ある工程を省略できる条件を定義する場合は、その工程が検出・達成すべき変化が実際の差分に含まれているかどうかに基づいて記述する。作業規模の主観的な印象だけで条件を決めると、本来その工程で検出すべき変化を含む差分まで省略されてしまう恐れがある。
- エージェントに判断を委ねる条文では、守るべき価値、逸脱した場合の不利益、考慮すべき観点を代表的な語句で示し、最終的な結論は読み手の総合的な判断に委ねる。
- 簡潔な基本方針の後に具体的な手段を例示する場合は、独立した行の`<例>`と`</例>`で囲み、その間に1行1例の形式で語句または`<条件>: <対応>`を記述する。例示はあくまで開放的な具体例であり、実際の適用範囲は基本方針に基づいて判断する。閉じた網羅的な列挙をするのは、`quality-principles.md`「規定の区分と標示」の硬い制約を守る条文に限定する。

<例>
編集する対象と、規範を読む役割を示す
入力の状態ごとに条件と行動を対応付ける
共通の判断は、その判断を定める文書へ接続する
入力を受理する条件は、要求と公開契約から決める
</例>

- 独立して変更され得る制約事項は、箇条書きの項目を分ける。衝突する可能性がある指示には優先順位や判断基準を明記し、否定形や例外条件が重なる場合は、条件と取るべき行動との対応関係が一目で読み取れるように記述を整理する（努力目標。相反する指示が併存すると満たしやすい方に判断が偏りやすく、変更範囲の最小化を優先する指示が原因への根本対策を妨げることがあるため）。
- 代替案が自明でない制限を設ける場合は、代わりに行うべき行動を合わせて明記する。
- 既存の規定の表現を変更する際は、実行時の振る舞いが意図せず変化しないことを確認する。条文を別資料への参照に置き換える場合は、集約した義務（判定、工程、契機など）が参照先の本文に確実に含まれていることを読み取って確認する（努力目標）。
- 対象を一意に特定できる明確な言葉で記述し、指示語は具体的な名称に置き換える。既存の段落を編集（文の挿入、移動、削除、置換、段落の分割や統合など）した後は、後続の文に含まれる指示語の指示対象がずれていないかを確認する。
- 数値の上限値は、その制限を設けないと成果物の品質や利用シナリオを維持できない場合に限って設定する。
- 達成すべき本質的な性質を規定する。特定のツールや実行順序に限定する場合や、検出・判定の対象を特定の検索語、正規表現、単語リストで限定する場合は、その手段が必要な理由と、リストが対象全体を十分に網羅している根拠を併記する。網羅性を担保できない場合は、文脈を含めて全体を確認するなど、リスト外の事象も判定できる手法と比較して選定する。出力形式を事前に確定できないデータから未知の異常を検出する手順において、既知のキーワードのみを候補にすると、それ以外の異常が確認対象から漏れてしまう。

## 語調と現行規則の表現

- 経験豊富な同僚が後輩に説明するように、自然な日本語で判定基準と望ましい行動を直接述べ、役割名は具体的な名称で呼ぶ。意味、適用範囲、拘束力、条件、例外事項を正確に維持した上で、法令のような硬い表現を平易な動詞に置き換え、肯定文で記述する。読み手（LLM）はプロンプトやコンテキストに含まれる文体をそのまま出力に反映する傾向があるため、否定的な宣言、曖昧な指示語、法令調の語句が多い文書を読むと、成果物も同様の文体になりやすく、指示範囲外の要素の追加や過剰な設計を招きやすくなる。この観測記録は、`docs/development/audit-records.md`の「agent-basics/skills/writing-standards/references/agent-documents-basics.md：語調と現行規則の表現：2026年9月16日」に記載されている。
- 現在適用されている最新の規則をそのまま記述し、過去のバージョンとの差異を述べるような表現は避ける（努力目標）。
- 語調の強さは、理由が明確な重要規定において必要な範囲にとどめる。必要な明確さや拘束力を伝える語は残し、語の種類や追加された経緯だけで削らない。表現の厳しさを強調するよりも、行動すべき条件を明確にした指示の方が安定して遵守される。判断は`writing.md`「日本語の書き方」に従う。
- 規範における例示は、正しい表現と、それが満たす性質や成立条件の説明によって示す。仕組みを説明する文章だけで十分に意図が伝わる場合は、その説明を活用する。API名、オプション名、戻り値の形式などは同一の対象を指す識別子として維持し、逐語的な引用、過去の観測結果、検出用データなどは、一般的な例示とは役割を明確に区別する。
- 拘束力のレベルや努力目標の表記ルールは、`quality-principles.md`「規定の区分と標示」に従う。
