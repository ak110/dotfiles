## private関数の直接テスト禁止

本節は、段3（単一関数の内部処理）を検証する際の手段の選定基準を定める。

- private関数（モジュール内やクラス内でのみ参照される非公開関数）を直接呼び出すテストは記述せず、外部に公開された公開インターフェース経由でテストを作成する。
  なお、Rustの`#[cfg(test)] mod tests`は同一モジュール内に閉じた言語標準の機構であり、外部結合を生じさせないため、本規定の制限対象外とする
- private関数に含まれるロジックを検証する手段は、以下の優先順位に従って選択する（既存の直接テストをリファクタリングする際も同様とする。同一ファイル内に既存の直接テストが存在すること自体は、直接テストを新たに選ぶ根拠にはならない）
  1. 公開インターフェースを経由した結合テスト（呼び出し元や、同等の機能を提供する他の公開関数の活用も検討する）
  2. 関数の引数による依存性の注入（DI）を利用した制御
  3. その関数自体が単体で外部へ公開するに足る再利用価値を持つ場合における、関数のpublic化（テストの都合のためだけに公開することは避ける）
  4. 上記のいずれの手段も適用できない場合に限り、必要最小限の範囲で行う直接テスト
- テストコードのリファクタリング、移行、または共通ヘルパー関数への共通化を行う際は、検証している内容の完全性を維持する。
  特定の処理を検証するテストにおいては、`testing-conditions.md`「分岐条件の効果の裏付け」に記載された無効化手法を用いて、テストが正しく機能していることを確認する。
  検証粒度を縮小する場合は、意図的な設計変更として実施する

## 簡潔さ

- テストダブル（モックやスタブ）の使用は、外部サービス、現在時刻、乱数、グローバル状態、言語ランタイムの内部機構など、実コードをそのまま実行したのでは決定論的な検証が困難な依存関係に限定する。
  依存の差し替えを行う際は、引数経由での注入（引数が省略された場合は本番用のデフォルト実装を使用する形式）を優先する
- ホスト環境、外部CLI、外部APIなどの外部システムが生成するログ記録、フック入力、レスポンスデータを模倣したテストデータを作成する際は、対象バージョンの実際の出力ログや公式スキーマ定義から構造と値を正確に写し取り、参照したバージョンと出所をテストコード内に記録する。
  開発者の推測のみに基づいて手作業で作成したデータは、実装コードと同じ誤った前提を共有してしまう危険がある。
  入力データの形式および生成・変換手順の同等性は、`investigation-sources.md`「根拠と主張の一致」で判断する。
  実際にテストで実行した処理範囲を検証の保証範囲とする
  入力は、実際の生産処理の実出力、対象版の実ログ・公式スキーマから最小化した標本、手書きの合成入力の順に、確認する境界へ対応付ける。
  外部ホストの起動が重い網羅ケースは、標本と生成・変換の同等性を確かめた軽い試験へ置き、代表的な通しの確認と保証範囲を分ける
- 既存のクラスやモジュールに新規テストを追加する前に、共通fixtureやヘルパー関数が構築する入力データと、同種の既存テストが渡している値の構造を確認する。
  前提条件が異なる入力データを与えると、共通処理を通過してもテスト対象の機構が正しく発動しない場合がある
- テストのセットアップと後始末の処理は、入力データと期待される結果の関係性が明確に読み取れる範囲で共有し、同一の操作に対して入力値のみが異なるケースは、テストのパラメーター化（テーブル駆動）を用いて集約する（努力目標。テストの簡潔さを保つため）
