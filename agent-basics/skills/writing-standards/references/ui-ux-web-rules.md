# Web画面の実装とレビューで確認する規則

HTML、CSS、JavaScriptでエンドユーザー向けの画面と単体HTML成果物を実装・レビューする時に、ソースコードから判定できる規則を置く。
技術の選択は原則9（足す前に引く）、性能の改善は原則3（観測したことだけを事実として言う）の適用である。
操作の結果の正しさは`agent-basics:writing-standards/references/testing.md`「検証単位の選定」で選んだ層の自動テストで、分かりやすさは実描画で確かめる。
参考資料（[Vercel Web Interface Guidelinesの取得時点の原文](https://github.com/vercel-labs/web-interface-guidelines/blob/e3d624baaf29dc1fc645aff3e38f03e564d2d6b1/command.md)、Impeccableの操作とコンポーネントの基準）を日本語へ再構成し、英語の表記に固有の規則を除いた。

## Web技術の選択

目的、対象ブラウザー、アクセシビリティ、性能を満たす標準のHTML・CSS・Web APIと、独自実装・第三者依存を比べ、必要な機構が少ない案を選ぶ。
対応ブラウザーをBaselineの目標へ対応付けて現在の一次資料で確かめ、目標を満たす機能はpolyfillやフォールバックを足さずに使う。
付加的な機能は段階的な機能強化で足し、必須の機能には対象ブラウザーで結果を保てる軽いフォールバックを用意する。
Origin Trial、実験的なAPI、単一ブラウザーの不安定な機能は、ユーザーが許容した対象環境と残るリスクの範囲で採り、Baselineの目標とともにプロジェクトの要件として扱う。
Modern Web Guidance（[GoogleChrome/modern-web-guidance](https://github.com/GoogleChrome/modern-web-guidance)）とNodeを導入した環境では、実装・変更・レビューの前に該当のskillで必要なガイドを取得し、本書とプロジェクトの規範に照らして採否を決める。
導入していない環境では、現在の一次資料で同じ判断をする。
`legacy-scan`は広い近代化やlegacyの監査に限って使い、検出結果をガイドと現物で確かめる。

## アクセシビリティとフォーカス

- 実行は`button`、遷移は`a`で書き、アイコンだけのボタンには`aria-label`などの名前、意味を持つ画像には`alt`を付け、装飾のアイコンは`aria-hidden="true"`で隠す
- 入力欄にラベル（`label`、`aria-labelledby`）を関連付け、見出しを階層順に置き、スキップリンクを用意し、非同期の通知と検証結果は`aria-live`で伝える
- フォーカスは`:focus-visible`で見せ、`outline`を消す時は同じ状態に同等以上の代替を付け、固定ヘッダーやオーバーレイに隠れないようにする

## フォーム

- 目的に合う`name`、`autocomplete`、`type`、`inputmode`を指定し、ラベルのクリックで入力欄へフォーカスが移るようにし、貼り付けを受け付ける
- 送信の開始前は送信ボタンを押せる状態に保ち、送信中は進行中と示し、「戻る」とダイアログを閉じる操作でも未保存の入力を確かめる

## コンテンツ、状態、画面遷移

- 再訪や「戻る」で復元すべき状態（検索条件、フィルター条件、ページ番号など）は、URLのクエリーなどへ反映する
- 非表示にしたモーダルやオーバーレイにはフォーカスが届かないよう、DOMから外すか`inert`を付ける
- コンポーネントごとにdefault、hover、focus、active、disabled、loading、errorの状態をそろえ、読み込み中はスケルトン表示を優先する
- `overflow: hidden`や`auto`の祖先に切り取られる絶対配置のドロップダウンには、`dialog`、Popover API、portalなどを使う。
  fixed配置を選ぶ場合は、祖先が包含ブロックを作っていないかも確かめる

## アニメーション、画像、パフォーマンス

- 設計は[画面の動き](ui-ux.md#画面の動き)に従い、Webでは動き軽減を`prefers-reduced-motion`メディア特性で判定し、動かすプロパティは`transform`と`opacity`を優先する
- 画像には幅と高さを指定してCLSを防ぎ、仮想スクロールの採否は件数ではなく実際の描画負荷で決める

改善候補は、`agent-basics:writing-standards/references/ui-ux.md`「アクセシビリティと性能」の同じ条件での測定から、実測した問題に作用するものだけを採用する。
配信からデータの取得・処理まで同じ利用経路をたどり、遅延・転送量・実行回数への寄与と、運用の負担・データの整合性を比べる。

- 配信量と初期表示: 画像の寸法・形式・優先度、フォントの種類とウェイト、第三者スクリプトの要否と起動の時機、bundleの内訳と遅延
- データ取得と応答: 取得場所、独立したリクエストの並行化、静的配信、LLMの応答のストリーミング
- バックエンド: 索引・N+1・ページング、重い処理のバックグラウンド化、アプリとデータベースの配置
- キャッシュ: ユーザーや認可に依存する応答は、公開で共有できる応答と分け、そのユーザーの範囲だけで再利用する

## テーマとローカライズ

- ダークテーマなどの配色は、スクロールバー、フォームなどのネイティブ要素、選択範囲、キャレット、フォーカスリングにも適用する
- 下線は`text-underline-offset`で文字から離し、表の数値には`font-variant-numeric: tabular-nums`を使う
- 日付と数値は`Intl`などで地域設定に合わせ、SSRとハイドレーションを併用する場合は日時の描画とイベントハンドラーがサーバーとクライアントで一致するかを確かめる

## 避けるべき実装

`viewport`は拡大できる設定にし（`user-scalable=no`と`maximum-scale=1`を外す）、操作できる外見の要素は実際に反応させる。

## 単体HTML成果物

### 適用範囲

ブラウザーで開くだけで閲覧が完結し、ユーザーへ単体で渡すHTML（調査レポート、ダッシュボード、データの可視化、プレゼンテーション資料、UIのプロトタイプなど）が対象である。
Webシステムの一部として動くHTML（テンプレートやコンポーネント）は、フレームワークとプロジェクトの規約に従う。

### 実装指針

- 1つのHTMLファイルにまとめ、そのファイルを開くだけで主要な操作が完結する構成にする
- 標準のHTML・CSS・JavaScriptを基本とし、スタイルの定義をまとめてインラインスタイルの多用を避ける
- オフラインでの利用が要件の場合は、必要なCSSとJavaScriptをファイル内へ埋め込む
- テーマの切替、ナビゲーション、エクスポート、編集とプレビューの同時配置などは、用途に要るものだけを入れる

### 技術選択の指針

本書「Web技術の選択」に加えて、ユーザーの指定、既存のデザインシステムとの統一、実装・保守費用の明確な改善がある場合は、CDNから読み込むフレームワークを選べる。
その採否には、外部への通信、オフラインでの利用、供給元の障害、版の変化を含めて比べる。
外部APIへの通信やバックエンドとの連携が要る構成は単体HTML成果物の範囲から外れるため、Webシステムとして設計する。
