# Web画面の実装とレビューで確認する規則

HTML、CSS、JavaScriptでエンドユーザー向けの画面と単体HTML成果物を実装・レビューする時に、ソースコードから判定できる規則を置く。
技術の選択は原則9（足す前に引く）、性能の改善は原則3（観測したことだけを事実として言う）の適用である。
操作の結果の正しさは`agent-basics:writing-standards/references/testing-design.md`「検証単位の選定」で選んだ層の自動テストで、分かりやすさは実描画で確かめる。
参考資料（[Vercel Web Interface Guidelinesの取得時点の原文](https://github.com/vercel-labs/web-interface-guidelines/blob/e3d624baaf29dc1fc645aff3e38f03e564d2d6b1/command.md)、Impeccableの操作とコンポーネントの基準）を日本語へ再構成し、英語の表記に固有の規則を除いた。
原典と著作権・許諾表示（MIT License、Apache License 2.0）は[第三者表示](../../../THIRD-PARTY-NOTICES.md)にある。

## Web技術の選択

目的、対象ブラウザー、アクセシビリティ、性能を満たす標準のHTML・CSS・Web APIと、独自実装・第三者依存を比べ、必要な機構が少ない案を選ぶ。
対応ブラウザーをBaselineの目標へ対応付けて現在の一次資料で確かめ、目標を満たす機能はpolyfillやフォールバックを足さずに使う。
付加的な機能は段階的な機能強化で足し、必須の機能には対象ブラウザーで結果を保てる軽いフォールバックを用意する。
Origin Trial、実験的なAPI、単一ブラウザーの不安定な機能は、ユーザーが許容した対象環境と残るリスクの範囲で採り、Baselineの目標とともにプロジェクトの要件として扱う。
Modern Web Guidance（[GoogleChrome/modern-web-guidance](https://github.com/GoogleChrome/modern-web-guidance)）とNodeを導入した環境では、実装・変更・レビューの前に該当のskillで必要なガイドを取得し、本書とプロジェクトの規範に照らして採否を決める。
導入していない環境では、現在の一次資料で同じ判断をする。
`legacy-scan`は広い近代化やlegacyの監査に限って使い、検出結果をガイドと現物で確かめる。

## アクセシビリティとフォーカス

- 実行は`button`、遷移は`a`で書き、アイコンだけのボタンには`aria-label`などの名前、意味を持つ画像には`alt`を付け、装飾のアイコンは`aria-hidden="true"`で隠す
- 入力欄に可視ラベル（`label`、`aria-labelledby`）を関連付け、見出しを階層順に置き、スキップリンクを用意する
- フォーカスは`:focus-visible`で見せ、`outline`を消す時は同じ状態に同等以上の代替を付け、固定ヘッダーやオーバーレイに隠れないようにする
- 色だけで選択・警告・成功を伝えず、形や配置で区別し、それだけで意味が分からなければ短い表示を使う（[WCAG 2.2 SC 1.4.1](https://www.w3.org/TR/WCAG22/#use-of-color)）。
  フォーカスの視認と遮蔽はSC 2.4.7・2.4.11、フォーカス表示や入力境界の対比はSC 1.4.11で判定する

モーダルは[APGのキーボード操作](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboardinteraction)を実装の参考とし、開始位置、背景の操作不能化、閉じた後の復帰を実機で確かめる。
操作順と拡大時の到達は[WCAG 2.2 SC 2.4.3](https://www.w3.org/TR/WCAG22/#focus-order)・[SC 1.4.10](https://www.w3.org/TR/WCAG22/#reflow)で判定する。
比較表など2次元表示が情報に不可欠な場合は、表だけを横にスクロールできるようにし、周囲の操作まで画面外へ出さない。
任意の短い補足をツールチップにする場合は、キーボード・タッチでも意味に到達できる代替を保ち、適用される[SC 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)の閉じ方・ポインターの移動・表示の持続を確かめる。
操作の名前や必須条件をホバーだけに置かない。

## フォーム

- 目的に合う`name`、`autocomplete`、`type`、`inputmode`を指定し、ラベルのクリックで入力欄へフォーカスが移るようにし、貼り付けを受け付ける
- 送信の開始前は送信ボタンを押せる状態に保ち、送信中は操作箇所で進捗を示し、重複送信など防ぐ必要のある操作だけを非活性にする。
  通常の待機文は足さない。
  「戻る」とダイアログを閉じる操作でも未保存の入力を確かめる

## コンテンツ、状態、画面遷移

- 再訪や「戻る」で復元すべき状態（検索条件、フィルター条件、ページ番号など）は、URLのクエリーなどへ反映する
- 同じ作業内で準備できる表示は、切替より先に最初に見える内容を用意し、通常の切替は表示・現在地・フォーカスの更新とする。
  背景取得・更新と切替を分け、大きなデータや遠隔データを一括先読みしない。
  対象や検索条件の明示変更、再取得は通常の切替と区別する。
  [W3C APG Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/#keyboard_interaction)でフォーカスと同時にパネルを切り替えるのは、表示に気づくほどの遅延がない場合に限る
- 非表示にしたモーダルやオーバーレイにはフォーカスが届かないよう、DOMから外すか`inert`を付ける
- コンポーネントごとにdefault、hover、focus、active、disabled、loading、errorの状態をそろえる。
  非同期の進捗・結果・検証エラーの状態通知は、内容と緊急度に合うロールやライブ領域でフォーカスを移さず伝える（[WCAG 2.2 SC 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)）。
  可視の説明を省いても必要な名前や通知は保ち、必要なら視覚的に隠したテキストを通知に使う。
  通常の完了・件数は`role="status"`など、すぐ気付く必要があるエラーは`role="alert"`などを選ぶ。
  明示的な`aria-live`を必須にせず、監視で変化しない内容を読み上げ直さない。
  通知を変えたら実際の支援技術で状態の変化・無変化・フォーカス保持を確かめ、DOMの確認と区別する
- `overflow: hidden`や`auto`の祖先に切り取られる絶対配置のドロップダウンには、`dialog`、Popover API、portalなどを使う。
  fixed配置を選ぶ場合は、祖先が包含ブロックを作っていないかも確かめる

## アニメーション、画像、パフォーマンス

- 設計は[画面の動き](ui-ux.md#画面の動き)に従い、Webでは動き軽減を`prefers-reduced-motion`メディア特性で判定し、動かすプロパティは`transform`と`opacity`を優先する
- 画像には幅と高さを指定してCLSを防ぎ、仮想スクロールの採否は件数ではなく実際の描画負荷で決める

改善候補は、`agent-basics:writing-standards/references/ui-ux-topics.md`「アクセシビリティと性能」の同じ条件での測定から、実測した問題に作用するものだけを採用する。
配信からデータの取得・処理まで同じ利用経路をたどり、遅延・転送量・実行回数への寄与と、運用の負担・データの整合性を比べる。

- 配信量と初期表示: 画像の寸法・形式・優先度、フォントの種類とウェイト、第三者スクリプトの要否と起動の時機、bundleの内訳と遅延
- データ取得と応答: 取得場所、独立したリクエストの並行化、静的配信、LLMの応答のストリーミング
- バックエンド: 索引・N+1・ページング、重い処理のバックグラウンド化、アプリとデータベースの配置
- キャッシュ: ユーザーや認可に依存する応答は、公開で共有できる応答と分け、そのユーザーの範囲だけで再利用する

## テーマとローカライズ

- ダークテーマなどの配色は、スクロールバー、フォームなどのネイティブ要素、選択範囲、キャレット、フォーカスリングにも適用する
- テーマと操作状態ごとに、背景と文字（補足を含む）の対比をSC 1.4.3、操作要素の識別に必要な図形・境界と隣接色の対比をSC 1.4.11で確かめる。
  [WCAG 2.2](https://www.w3.org/TR/WCAG22/)は適合判定に用い、原文や訳文は転載しない（[文書の許諾](https://www.w3.org/copyright/document-license-2023/)）
- 下線は`text-underline-offset`で文字から離し、表の数値には`font-variant-numeric: tabular-nums`を使う
- 日付と数値は`Intl`などで地域設定に合わせ、SSRとハイドレーションを併用する場合は日時の描画とイベントハンドラーがサーバーとクライアントで一致するかを確かめる

図、グラフ、進捗、状態バッジは各テーマで文字・線・背景・フォーカスの対比を確認する。
外部の図を背景色と独立に再着色せず、輪郭を識別できる専用の面か、制御できる素材のテーマ別の対を使う。
入力のラベルと説明は対応する入力のそばに置く。
選択肢全体を操作できる場合は、そのまとまりでもフォーカス位置を視認できるようにする。

## 避けるべき実装

`viewport`は拡大できる設定にし（`user-scalable=no`と`maximum-scale=1`を外す）、操作できる外見の要素は実際に反応させる。

## 単体HTML成果物

### 適用範囲

ブラウザーで開くだけで閲覧が完結し、ユーザーへ単体で渡すHTML（調査レポート、ダッシュボード、データの可視化、プレゼンテーション資料、UIのプロトタイプなど）が対象である。
Webシステムの一部として動くHTML（テンプレートやコンポーネント）は、フレームワークとプロジェクトの規約に従う。

### 実装指針

- 1つのHTMLファイルにまとめ、そのファイルを開くだけで主要な操作が完結する構成にする
- 標準のHTML・CSS・JavaScriptを基本とし、スタイルの定義をまとめてインラインスタイルの多用を避ける
- オフラインでの利用が要件の場合は、必要なCSSとJavaScriptをファイル内へ埋め込む
- テーマの切替、ナビゲーション、エクスポート、編集とプレビューの同時配置などは、用途に要るものだけを入れる

解説ページでは、構造・関係・差を比べて説明する時に限り、本文だけの場合と比べて図を選ぶ。
図を使う時も同じ要点を読める本文か表を併置する。
操作に必要な要点と制約は常に表示し、補足だけを `details` と `summary` などの展開要素か本文のリンク先へ移す。
必要な情報をホバー専用のツールチップへ置かない。

例えば設定の引き継ぎを解説する原稿では、「旧設定を読み込んでから保存する。保存後の設定は古いバージョンでは開けない」を本文に置き、「保存形式の違い」の補足だけを展開要素へ移す。
図あり版では読み込みから保存への流れを本文の後に図で示し、図なし版では同じ本文から補足へ進む。
両版とも「要点と制約 → 補足」の順にたどれ、補足を閉じたまま操作できるようにする。
`ui-ux-topics.md`「完了前の実描画確認」では、幅320pxでもこの順で必要情報に到達でき、読み上げ順が成立し、展開要素をキーボードとタッチで開閉できることを確かめる。

### 技術選択の指針

本書「Web技術の選択」に加えて、ユーザーの指定、既存のデザインシステムとの統一、実装・保守費用の明確な改善がある場合は、CDNから読み込むフレームワークを選べる。
その採否には、外部への通信、オフラインでの利用、供給元の障害、バージョンの変化を含めて比べる。
外部APIへの通信やバックエンドとの連携が要る構成は単体HTML成果物の範囲から外れるため、Webシステムとして設計する。
