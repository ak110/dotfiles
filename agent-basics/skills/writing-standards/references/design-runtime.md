# 実行時の設計

並行処理・非同期ジョブと再試行・キャッシュ・常駐サービス・負荷制御・実利用環境での評価・多段の手順の工程順を、設計・変更・レビューする時の基準である。
成否の分からない操作の再発行と共有状態の破損は取り消しが難しいため、`agent-basics:writing-standards/references/quality-principles-constraints.md`の硬い制約として扱う。
ロック・再試行・監視などの機構を加える前の比較は`agent-basics:writing-standards/references/quality-principles-subtraction.md`に従う。
方式の比較は`agent-basics:writing-standards/references/quality-principles-qcd.md`に従う。

## 並行処理・排他制御の設計観点

ロック、排他制御、並行処理を伴う機能は、実装に着手する前に次の順で決める。

1. 共有する可変の状態と書込の主体を特定し、1つの保存先で整合性を保つ状態と、主体が独立に出す情報を分ける。
2. 独立した情報は、主体ごとのファイル・キー・branch・状態ディレクトリへ保存して読取側で集約する案を、ロックや直列化より先に比べる。
   同じJSONファイルの別のフィールドを担当ごとに更新しても、ファイル単位のread-modify-writeの競合は残る。
3. 同じ保存先の更新が不変条件として必要なら、ロック・単一の書込担当・直列の工程・compare-and-swapなど実際の書込を制御する方式を選び、自然言語での順序の指示とは区別する。
4. 状態や業務ルールを持つ変更では、`agent-basics:writing-standards/references/design-data-interfaces.md`「状態と業務ルールの条件」で対応付けた条件と操作から、排他とトランザクションの単位を導く。
   結果整合でよい状態を別の単位へ分ける案と、複数単位の変更を調整する方式も比べる。

あわせて次を決める。

- イベントループを塞がないよう、I/Oは可能なら非ブロッキングの手段を使い、避けられない同期処理や重い計算は別スレッド・別プロセスで行う。
- 排他の単位（プロセスかスレッドか）を明確にし、人間の入力待ちと長い処理はロックの外で行う。
- 並行性能はロック待ちの寄与・保護するキー・排他の粒度・接続の容量と保持時間・fsyncや通信や計算の配置を比べて改善し、整合性・耐久性と部分失敗・孤立データ・再試行・同時更新の扱いを保つ。
- 失敗時の共有状態の復元手順と、復元自体の成否を確かめる方法。
- ユーザー入力を含む中間生成物は正常終了時に削除し、再試行できる一時的な失敗（ネットワーク切断、タイムアウトなど）では保全する。
  入力検証や権限検証で拒否したデータは、削除か隔離をして保持期限を明示する。
- 操作の対象の資源が途中で消えた時の動作。
- 常駐プロセス・別の端末・別のセッションから共有資源を操作する成果物では、更新後も旧版のプロセスがしばらく動く前提で、旧版が作ったデータ（旧形式・0件・不完全なものを含む）を新版が読んだ時の挙動を試験する。

状態遷移、並行処理、認可の不変条件を網羅的に検証する手法は、`agent-basics:writing-standards/references/testing.md`「状態遷移の性質確認」に従う。

## 非同期ジョブ・リトライ設計

バックグラウンドジョブ、非同期処理、再試行、定期実行（CIのスケジュール実行、cronなど）、常駐プロセスに適用する。
重複して実行されても意図しない副作用が起きないこと（冪等性）と、失敗を確実に検知できることを守る。
冪等性のキーには、論理的なジョブの単位で変わらない一意な値（呼び出し元が発行するリクエストIDなど）を使う。

再試行できる一時障害であることと、副作用がまだ生じていないことは分けて判断する。

- 操作の状態を未実行・実行中・完了・成否不明に分け、応答を失っても公開された状態照会で結果を確かめられる設計にする。
- 応答を失った時は未実行とみなさず、公開された状態照会か同じ実行識別子で結果を回収する。
  成否不明の非冪等な操作は、結果を確かめるまで再発行しない。
- 読取専用の操作、未実行と確かめた操作、同じ論理操作として追加の効果が生じない契約を確かめた操作は、既存の再試行条件で回復してよい。
- 再試行の新設は、要求上必要な回復がある場合に限る（一時障害であることだけでは理由にならない）。
  対象とするエラーの選別は、`agent-basics:writing-standards/references/implementation-time.md`「セキュリティ・ロギング・エラー処理」に従う。
- 下位のツールやSDKの初期値と再試行の範囲を確かめ、上位の再試行はそれと重なる範囲を除いて設計する。
- 回数・最大待ち時間・操作全体の時間を有限にし、上限付きの指数バックオフとジッタを提供元の待機指示と全体の時間予算に合わせる。
  時間予算を超える場合は再発行をやめ、原因と、結果が確定していない範囲を伝える。

非同期化や一括書込では、応答で保証する可視性と耐久性、許容する遅延、即時に要る失効・削除と遅らせてよい記録を区別する。
集約の幅・待ち時間・未保存の量、下流への負荷の集中、停止・再起動・部分失敗・重複実行を比べ、成功応答の契約を保つ。

人の操作なしに動く処理は、失敗をどの主体がどの契機で検知するかを設計の段階で決め、計画と完了条件に含める（初回の成功の確認だけでは運用中の失敗を検知できないため）。
検知の主体は次の順に選ぶ。

1. 失敗の情報が人を介さずエージェントの処理キューへ入る既存の仕組み（作業依頼のキュー、イシュートラッカー、CIの失敗を送る監視など）。
   ログを出す前に止まる障害（設定の不足、認証エラーなど）も届くかと、全ての起動元と稼働期間が監視の対象かを確かめる。
2. エージェントが定期的に行う既存の契機（定期作業の開始時など）での実行結果の確認。
3. 上の2つが成り立たない場合に限り、ユーザーへの直接の通知（メールなど）とし、その理由を計画に書く（ユーザーが依頼するまで失敗が放置され、手間も増えるため）。

- 処理結果の不整合は、後から別の仕組み（定期ジョブ、稼働監視、外部通知など）で検知する案より先に、処理自身が見つけた時点で異常終了（終了コード非0など）させる案を比べる。
- 複数のジョブの同時実行の防止は、本書「並行処理・排他制御の設計観点」に従う。
- 出力が次回の同じ処理の起動契機になる構成（キューの処理結果が同じキューへタスクを加えるなど）では、出力が0件で終わる停止条件と待機へ移る処理を、設計の比較の段階で明示する。
- 再試行を尽くした失敗メッセージは、隔離して再処理できるようにする（Dead Letter Queue）。

## キャッシュ設計

元データとの整合性を要件の許容範囲に収め、キャッシュ層が障害で止まってもシステム全体は動き続ける構成にする。
書込時の無効化の欠落、キーの衝突、期限切れに伴う再生成の集中（キャッシュスタンピード）を防ぐ。
再利用の効果はキーの変化の頻度・期限の粒度・ヒット率・生成の費用・容量と退避・再起動後の再構築から見積もる。
更新では全件・差分の取得、局所キャッシュと複製、更新・削除・失効、応答前に反映する範囲、部分失敗を扱う。
時刻と期限の粒度や非同期の反映は、有効期限と認可、成功応答で保証する可視性と耐久性を保つ範囲で選ぶ。

## 常駐サービス設計

常駐サービスと、子プロセス・委譲先・非同期ジョブなど配下を持つ機能の停止・再開・切替に適用する。

- 停止の範囲は実行の主体・所有関係・実行環境の寿命・子と孫の階層・別のホストや接続・停止と完了の競合から決める。
- 配下の状態（稼働中・停止済みで再開できる・完了済みで結果が未回収・状態や作用が未確定など）から、継続・中断からの再開・結果の回収・重複実行の防止を判断する。
  列挙に無い状態も、配下の実際の状態を確かめて扱いを決める。
- 常駐サービスでは、安全な停止（graceful shutdown）と処理中の要求・ジョブの扱い、稼働状態と受付の可否を確かめるヘルスチェックを設ける。
- 長時間接続（WebSocket、Server-Sent Eventsなど）: 切断検知・ハートビート、再接続とその間の取りこぼし（再送・再取得）、接続数の上限、停止時の接続の閉じ方。
- 常駐中のメモリーの増え続け: 上限の無いキャッシュやキュー、解除されないリスナー。

## 負荷制御と外部呼び出しの設計

公開APIの過負荷はレート制限とバックプレッシャーで抑え、外部呼び出しの障害の波及はサーキットブレーカーで抑える。
バルクヘッド: 依存先や処理ごとに接続プール・スレッド・キューを分け、遅延や障害で他の処理の資源を使い尽くさない。
通信の各待ち時間は、`agent-basics:writing-standards/references/implementation-time.md`「セキュリティ・ロギング・エラー処理」に従って操作全体の時間予算と合わせる。
再試行は本書「非同期ジョブ・リトライ設計」に従う。
並行呼び出しの接続プールは、ピークの並行数・接続の保持時間・プールの容量・取得待ちを比べ、容量不足を観測してから保持時間や並行数の削減と増量を比べる。

## 技術仕様と実利用環境の評価

負荷、データ、外部システムの条件に依存する技術仕様と非機能要件に適用し、観測と推論の区別は`agent-basics:writing-standards/references/quality-principles-facts.md`に従う。

- 期待する利用結果、事前検証の仮定と限界、実利用環境で評価する観測を対応付ける（努力目標。影響と取得費用に合う検証を選ぶため）。
- 既存のログと計測を先に使い、対象の版・処理結果・資源の消費・入力条件を、劣化した処理や条件を特定できる粒度で関連付ける。
- 明確なエラーを出さない劣化や低頻度の失敗も既存の観測で判断できるかを確かめ、不足する観測は作業範囲の中で補う。
- 可逆な変更の限定的な展開と、取り消せない操作や永続データの変更を区別し、影響範囲・評価する観測・継続や中止や復旧の判断を既存の公開方針と認可の範囲で選ぶ。
- 事前検証、実装の完成、後日の運用効果を区別し、自然に起きる事象の待機を完成条件に含めるのは、その観測が完成の判定に要る変更に限る。

## 状態を変える多段手順の工程順

パッケージの削除、パーティションの縮小、設定ファイルの削除など、後の工程が使う前提を変える工程は、その前提を実行時に参照する全ての工程より後ろに置く。
参照の有無は、参照するコマンド、パッケージ、デバイス、ディスク上のメタデータから判断する。
例えば`grub-probe`と`grub-install`は`mdadm`とディスク上のパーティション情報を参照するため、GRUBの更新より前に`mdadm`を消すかパーティションを縮めると更新が失敗する。
