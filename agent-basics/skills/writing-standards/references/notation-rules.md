# 表記とMarkdownの規則と確認手段

本書は、人間向けの文章を執筆するエージェントや表記チェックを担当するエージェント向けに、日本語の表記ルール、Markdownの書式規則、表記の一括置換手順、チェックの対象範囲、および口語表現やダッシュ記号の検証手段をまとめたものである。
Claude Codeの`Edit`ツールや`Write`ツールによる既存ファイルの上書き前には、対象の絶対パスに対して`Read`を実行しておく前提条件がある。この前提条件や、その代替とならない操作（Bashでの表示・作成・変更や別パスのReadなど）については、同一ディレクトリにある`file-editing.md`の「ファイル更新時の編集ツールの前提」を参照する。

## 日本語の表記ルール

`textlint`の`preset-jtf-style`によってチェックされる項目は、同プリセットの規定に従う。以下はプロジェクト独自の補足ルールである。

- 日本語と全角括弧の境界にはスペースを入れずにそのまま続ける。英語の文脈で半角括弧を用いる場合は、英数字との間に半角スペースを1つ空ける（例: `Python (CPython 3.12)`）。
- 全角丸括弧の入れ子（ネスト）は避け、内側の括弧は読点（、）で区切るか、別の文に分けることで表現する。
- 括弧による補足は、本文の記述だけでは伝わらない条件や補足情報を追加する場合に用いる。単なる同義語の言い換えを重ねるだけの補足は本文へ統合するか削除し、補足を入れる際は全角丸括弧を使用する（努力目標。情報量が増えない補足は、読者が文を区切る回数だけを増やしてしまうため）。
- 日本語の地の文や見出しではダッシュ記号（emダッシュ、horizontal bar、2倍ダッシュなど）の使用を避け、同格表現や補足説明には全角丸括弧を用い、言い換えは文の分割や読点で表現する。
- 技術用語、固有名詞、コード識別子は、原典や公式ドキュメントの表記を優先して使用する。
- 「復号」という語は暗号を解く処理に限定して使用する。バイト列から文字列への変換や、JSON文字列などのエンコード表現から元のデータ構造を取り出す処理は「デコード」と表記する。
- 地の文は自然な日本語で記述する。定着している技術用語、略語、外部技術に由来する語、および識別子は元の表記を維持する。
- システム内部の役割や概念には自然な日本語の名称を優先して付け、カタカナ語を用いる場合は初出時に意味を定義する。
- 接続詞は「または」「もしくは」「および」「ならびに」のように、ひらがなで表記する。
- 法令文書のような堅苦しい指示語や回りくどい表現は、単語だけを機械的に置き換えるのではなく、指示対象や条件が明確に伝わる平易な文章へ書き直す。
- ドキュメント、コードコメント、画面表示メッセージ、エージェント向け文書を含む人間向けの文章全般では、資料が定めている具体的な内容、指定がない場合のデフォルト値、比較対象や一致を確認する条件を明確な文章で記述する。読み手が文脈から自明に補える範囲で簡潔にまとめる。文全体を書き直す際の方針は、`textlint-violations.md`の「textlint指摘への修正方針」に従う。なお、検出用のテストデータや他者の発言の逐語引用は、その目的を明記した上で原文のまま保持する。
- 人やエージェントを指す呼称は、`quality-principles.md`の「役割分担」における定義に従う。要求、指示、回答、合意、承認をする人間は「ユーザー」と呼び、作業を担当するコーディングエージェントは「エージェント」と呼ぶ。役割の違いを区別する場合は、メインエージェント、サブエージェント、委譲先、レーン担当などの具体的な役割名を添える。成果物を利用する人間は「エンドユーザー」（ユーザー自身も含まれる）と呼び、特定の成果物を使う人を指すときは「dotfilesユーザー」「agent-toolkitユーザー」のように表記する。開発者やエージェントが読む新しい説明文では、これらの呼称を用いて対象範囲を明確にする。成果物を使う人自身が読むガイドの見出しや案内では「利用者向け」も使える。人間以外も含む処理対象全般は「消費主体」、OS上の権限主体は「実行中のOSアカウント」、コードやプロセスの利用関係は「呼び出し元」「消費側」のように実態に即した言葉で表現する。旧形式のデータとの互換性維持、検出用テストデータ、および他者の逐語引用については、その役割を明示した上で原文表記を維持する。

## Markdown記述スタイル

Markdownの各要素は、それぞれの意味的な役割に沿って適切に使用する。句点の位置などの細かな規則は`markdownlint`や`textlint`で検証する。

- 図の記述にはMermaid記法を推奨する。
- 図が表現する関係性（手順の順序、状態遷移、要素間の依存関係など）に応じて適切な図の形式を選ぶ。異なる種類の関係性を1枚の図に混在させず、必要に応じて図を分ける。図の説明文も、図が示す関係性と一致するように記述する。
- 相対パスは配置先のファイルを基準として解決し、`test -e <解決後パス>`でファイルの実在を確認する。
- 文字の強調（太字など）は語句の強調のみに用い、見出しの代わりに強調記法を使わず、見出しには見出し記法（`#`）を用いる。
- 形容詞や口語表現をかぎ括弧（「」）で安易に強調しない。
- インラインコード記法（バッククォート）は、コードリテラル、コマンド名、ファイルパス、および識別子に限定して使用する。
- 1文ごとに改行を入れる。
- 箇条書きは1項目につき1文・1行を基本とし、複数の論点を含む場合は階層構造にするか項目を分割する。
- 長い補足説明は丸括弧の中に詰め込まず、独立した文として記述する。

lint設定の緩和、無効化、除外指定の追加手順は、`lint-relax-criteria.md`に従う。

## チェックの対象範囲

- 計画ファイルは、文章lint、口語表現チェック、ダッシュ記号チェックの必須対象から除外する（読み手がその計画を実行するエージェントに限られており、表記の統一がタスクの特定や完了条件の判定に影響しないため）。
- エージェント向け文書に掲載する用例は、正しい表現と、その表現が成立する条件を説明する文章で構成し、通常の文章チェックの対象とする。用例と解説の書き方は`tone-examples.md`および`tone-examples-llm-tone.md`を参照する。なお、検出用テストデータ、内部保存形式の識別子、および他者の逐語引用は、自身が作成した用例と明確に区別して原文のまま保持する。

| 規則 | 検出を担当する既存ツール | 検出対象外の扱いと意味確認の担当 |
| --- | --- | --- |
| 日本語と半角英数字の間隔、和文のハイフン、山括弧の対応 | textlintのJTF 3.1.1、4.2.6、4.3.7 | コードブロック内の逐語データやコードは原文を維持する。インライン識別子の正確さや操作例の意味は作成者が確認する |
| 1文150文字制限、読点の個数、箇条書きの末尾句点、接続詞の重複 | textlintのsentence-length、max-ten、JTF 1.1.3、no-doubled-conjunction | コードブロックを除く通常の本文を検出対象とする。文を分割した際の条件、確からしさ、意味の正確さは修正担当者が確認する |
| 同一階層における同名見出し | markdownlint MD024 | 見出しと本文の意味的な整合性や親子関係はレビュー限定基準に従って確認する |
| 口語表現の辞書突き合わせ | pyfltrのcolloquial-check | Markdownの引用ブロックとコードブロックは検出対象外とする。引用の原文は維持し、辞書にない不自然な表現はレビュー担当者が文脈から判断する。和語の動詞を漢語へ置き換える候補（「作る」→「作成する」、「出す」→「出力する」など）は、文脈で対象と動作が明確なら採らずに和語のまま残す |
| 地の文におけるemダッシュ、horizontal bar、2倍ダッシュ | プロジェクト固有のwriting-check-dash | コードブロック、インラインコード、URLを対象外とし、識別子の表記を維持する |

上記チェッカーを持たない実行環境では、完成時に手動の自己点検によって各規則を確認する。
チェックを実行できない状態を「合格」とみなさない。
引用の正確さ、識別子の保持、および文章の意味の整合性はツールの機械判定では保証されないため、各担当者が目視で確認する。
エラー診断時の詳しい対処手順は、`textlint-violations.md`を参照する。

| --- | --- | --- |
| 口語表現チェック | 対象外 | 対象外 |
| textlint | 検出対象 | 対象外 |
| ダッシュチェック | 検出対象 | 対象外 |

## 文章チェックの一括実行

恒久的な成果物は、現在のホスト環境に公開されているserver key `pyfltr`の`run`ツールを用いて一括チェックを行う（ツールの完全修飾名はClaude CodeとCodexで異なる）。指定する引数は次のとおりである。

- `paths`: 今回チェック対象とする全ファイルの絶対パス（重複を除く）
- `work_dir`: チェック設定ファイルが存在するプロジェクトの絶対パス
- `commands`: 対象ファイルの拡張子に対応するチェッカーコマンドの和集合。Markdownファイルを含む場合は`["textlint", "colloquial-check"]`、それ以外の対応拡張子のみの場合は`["colloquial-check"]`を指定し、プロジェクトに登録されたダッシュチェック等も同じ実行に含める
- `enable`: `["colloquial-check"]`
- `no_exclude`および`no_fix`: いずれも`true`
- `allow_external_paths`: 対象ファイルが`work_dir`のプロジェクト外部にある場合にのみ`true`

同一の設定でチェックできる複数のファイルは、1回の`run`呼び出しにまとめる。
チェックが完了したかどうかの判定では、レスポンスの`completion`が`completed`であり、`files_reached`が指定したファイル数と一致していることを確認する。
また、指定したすべてのコマンドが`completed_commands`に含まれており、`incomplete_commands`、`missing_targets`、`fully_excluded_files`がいずれも空であることを確認する。
拡張子ごとに適切なコマンドが選択され、必要なチェックがすべての対象ファイルに適用されたことを確かめる。
`incomplete`や`not_reached`が返った場合はチェック完了とはみなさず、`incomplete_commands`、`missing_targets`、`fully_excluded_files`、`skipped_reason`、`warnings`から原因を特定して対処する。
警告やエラーの件数は完了が確定した後に確認し、詳細なメッセージが必要な場合はレスポンスの`run_id`をMCPの`show_run_diagnostics`ツールに渡して取得する。

MCPの`run`ツールが利用できない環境では、`agent-basics:check-execution`でCLIの起動コマンドを確認し、同様の対象ファイルとオプションを指定して実行する（外部ファイルを含む場合は`--allow-external-paths`を付与する）。完了の判定は、JSONL出力の最終行にある`summary`レコードを用いてMCPと同様の条件で確認する。

```sh
<pyfltrの起動形> run --commands=<全対象へ到達するコマンドの和集合> --enable=colloquial-check --no-exclude --no-fix --output-format=jsonl --work-dir <チェック設定を持つプロジェクトの絶対パス> <対象ファイルの絶対パス...>
```

チェックの対象拡張子は`.md`、`.py`、`.txt`、`.yaml`、`.yml`、`.toml`である。Markdownの引用ブロックおよびフェンス付きコードブロックの内部は対象外となるが、ソースコード内のコメント行はチェック対象となる。
検出された語句と指摘の理由は診断結果から確認する。
辞書の改訂や誤検知の調査で辞書の実データを確認する必要が生じた場合は、使用している`pyfltr`の公開機能や提供元の資料を参照する。

警告を解消することだけを目的にして、読者に伝わる情報量を減らすような安易な書き換えをしない。他者の原文（記事や発表のタイトル、引用した発言、固有名詞など）に含まれる警告語句は原文のまま保持し、修正せずに残した箇所とその理由を完了報告に明記する。

日本語の地の文や見出しに含まれるemダッシュ、horizontal bar、2倍ダッシュは、プロジェクトに用意されたダッシュチェッカーをこの一括実行に含めて検証する。
コードブロック、インラインコード、およびURLの内部はチェック対象外とする。
