# 日本語とMarkdownの執筆規則

文章を書く時と表記を直す時に使う、日本語の表記、Markdownの書式、表記の一括置換の基準である。
原則8（`agent-basics:writing-standards/references/quality-principles-readers.md`）を表記へ当てはめる。
チェックの診断へ対応する時は`agent-basics:writing-standards/references/textlint-violations.md`「textlint指摘への修正方針」に従う。

## 日本語の表記ルール

textlintの`preset-jtf-style`がチェックする項目は同プリセットに従い、次の規則を加える。

- 和文と全角括弧の間は空白を置かずに続け、英語の文脈の半角括弧は英数字との間に半角空白を1つ置く（例: `Python (CPython 3.12)`）。
- 全角丸括弧を入れ子にせず、内側は読点で区切るか別の文に分ける。
- 括弧の補足は本文だけでは伝わらない条件や情報に使い、同義語の言い換えは本文へ統合するか削る（努力目標。情報量の増えない補足は、読者が文を区切る回数だけを増やすため）。
- 地の文と見出しではダッシュ記号（emダッシュ、horizontal bar、2倍ダッシュ）を使わず、同格と補足は全角丸括弧、言い換えは文の分割か読点で書く。
- 地の文は自然な日本語で書き、技術用語、固有名詞、略語、識別子は原典と公式の表記を保つ。
- 「復号」は暗号を解く処理に限り、バイト列から文字列への変換と、エンコードした表現から元のデータを取り出す処理は「デコード」と書く。
- 失敗や中断を含めて終わることは「終了」、成功して終わることは「完了」と書き、この意味で「終端」を使わない（文字列や区間の端、構文の終端記号は対象外）。
- システム内部の役割や概念には自然な日本語の名称を付け、カタカナ語を使う時は初出で意味を定義する。
- 接続詞はひらがなで書く（「または」「もしくは」「および」「ならびに」。JTF 2.2.1）。
- 法令文のような堅い指示語や回りくどい表現は、語の置き換えで済ませず、指示対象と条件が伝わる平易な文へ書き直す。
- 人が読む文章（文書、コメント、画面の文言、エージェント向け文書）では、資料が定める具体的な内容、指定が無い時の値、比べる対象と一致の条件を文で書く。
- 検出用のテストデータと他者の逐語引用は、その目的を明記して原文のまま保つ。

人とエージェントの呼称は`agent-basics:writing-standards/references/quality-principles-roles.md`「役割分担」に従い、役割を区別する時は具体的な役割名を添える。
成果物を使う人自身が読むガイドの見出しや案内では「利用者向け」も使える。
人間以外を含む処理対象全般は「消費主体」、OS上の権限の主体は「実行中のOSアカウント」、コードやプロセスの利用関係は「呼び出し元」「消費側」のように実態に合う語で書く。
旧形式のデータとの互換、検出用のテストデータ、他者の逐語引用は、役割を示したうえで原文の表記を保つ。

## Markdown記述スタイル

句点の位置などの細かな規則は`markdownlint`と`textlint`がチェックする。

- 図はMermaidで書く（推奨）。
  手順の順序、状態遷移、要素間の依存など、図が表す関係ごとに形式を選び、種類の違う関係は図を分け、説明文を図の関係と一致させる。
- 相対パスは配置先のファイルを基準に解決し、`test -e <解決後パス>`で実在を確かめる。
- 強調は語句の強調だけに使い、見出しには強調でなく`#`を使う（markdownlint `MD036`）。
- 形容詞や口語表現をかぎ括弧で強調しない。
- インラインコードは、コード、コマンド名、ファイルパス、識別子に限る。
- 1文ごとに改行する。
- 箇条書きは1項目1文1行を基本とし、論点が複数あれば階層にするか項目を分ける。
- 長い補足は丸括弧の外に出し、独立した文にする。

## 表記の一括置換

多数の箇所の語句を同じ働きの語句へ置き換える時（1対1の表記統一、文脈ごとに決まった候補から選ぶ置換）は、一括置換と変更箇所の全件レビューを組にする。

1. 代表例で、候補が指示対象、動作の主体、条件、否定と例外を保てるかを確かめ、箇所が少なく手で直す方が安く確かな時は手で直す。
2. 置換の前に`git status --porcelain=v1 -- <対象パス>`で未コミットの変更が無いことを確かめる。
   元に戻すのも、着手前に未コミットの差分が無かったファイルに限る。
3. 置換の直前に、`agent-basics:writing-standards/references/file-editing.md`「ファイル更新時の編集ツールの前提」でファイルごとの読取状態を確かめ、意味を保てる部分だけを一括置換する。
4. `git diff --word-diff=plain --word-diff-regex=.`で文字単位の差分を出し、変更箇所を全件レビューする。
   誤置換があれば対象の条件を限定して手順3からやり直す。
5. 候補に合わない文、意味が変わりやすい文、指摘を受けた文は個別に書き直し、`agent-basics:writing-standards/references/textlint-violations.md`「文の書き直しの委譲と検収」の条件で確かめる。
6. textlintと対象の自動テストを実行し、指摘やエラーを受けたら`agent-basics:bugfix`を起動して対処する。
