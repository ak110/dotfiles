# ドキュメント品質

本書は、人間が読む文章（Markdownファイル、README、技術ドキュメント、API仕様書、業務文書、仕様書、体験記、コードコメント、作業項目の本文など）の品質基準を定めたものである。
ソースコード内のコメントやエージェント向け文書にも人間が読む文章が含まれるため、本書の基準を同様に適用する。

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| エージェント向け文書の条件、禁止、理由を整理する時 | `agent-documents-basics-content.md`、`agent-documents-basics-tone.md` |
| 新しい概念名や内部識別子を導入する時と、既存の名前で複数の主体・プロジェクト・変更前後の対象を説明する時 | `referent-table.md` |
| 会話の要約から文章の要求・事実・認可を復元する前 | `investigation-sources.md` |

## 構成・構造

- 文書の冒頭に目的や概要を提示し、前提条件（必要な前提知識、使用ツール、動作環境など）は本題に入る前に説明して、全体像から詳細な内容へと順を追って掘り下げる
- 読者が個別に知りたい疑問やトピックを整理し、「見出しを設けない構成」「並列の見出し構成」「親子関係を持つ階層見出し構成」の中から最もシンプルな構成を選択する。
  見出し構成や書式があらかじめ指定されている文書では、その指定された形式を厳守する
- 見出しには、本文が回答している内容やテーマが一目で分かる簡潔な言葉を用い、見出しの階層は最大でも3段階（`##` / `###` / `####`）程度にとどめる。
  完成後に見出しと本文の整合性、話題の重複、親子関係の包含関係を確認する手順は、`review-only-criteria.md`の「見出しと本文の対応」に従う
- 関連性の高い内容は近くにまとめて記述し、後の章や節を参照する記述（前方参照）は段落や節の末尾に配置する
- 複数の段落または節からなる文章は、見出しと各段落の先頭文を順に読んで要旨と論理の流れが通るように並べ、同じ話題へ戻る構成を避ける。
  長い文章は、見出しと先頭文の並びを先に組んで流れを確かめてから詳細を書く（努力目標）
- コマンド例やコードスニペットは、読者がそのままコピー＆ペーストして実行できる正確な形で記述し、外部へのリンクを記載する場合はリンク先の要点を本文中にも簡潔に記載する

## 日本語の書き方

伝える内容は直接書き、主張を際立たせるためだけに否定する側を並べる対比フレーミングは避ける。
読者が取り違えやすい実在の選択肢や誤解を除くときは、「文字列ではなくバイト列で渡す」のように1文で対比してよい。
「`== None`ではなく`.is_(None)`を使う」もこの例に当たる。
肯定文だけで対象が定まる場合は、その内容を直接伝える。
肯定文の対象の一部を除く場合は、「検証を除く変更を記録する」のように同じ文で限定する（努力目標）。
肯定文の対象とは別の実在する制約、選択肢、または誤解は、独立した事実の文で示す。

程度、確度、拘束力を伝える語は、読み手の理解や判断に加える意味と拘束力を基準に残す。
強い語は、求める行動や拘束力を伝えるために必要な範囲で使う。
「原則として」は一般的に使える表現であり、硬い制約を弱めるなど実際に意味が変わる場合は文脈で判断する。

不自然な連用形の単独名詞化は、対象を特定した動詞の文か自然な名詞に直す。
見直し、組み合わせ、資金集め、住民票の写しのように定着した語は保つ。
技術用語を一字に縮めて対象が曖昧になる場合は、その分野で通じる名称を使う。
出版物の版、記号の印、身体の頭は本来の意味で使う。

```text
例文: 検証の結果、設定を保存できた。通信エラー時は再試行することがある。
例文: 設定を変更する前に、担当者へ通知してよいか。
例文: CLIはキャッシュが有効な場合、キーが一致する結果を返す。
説明: 報告、確認質問、技術説明の主体と条件を保つ。文脈から一意に分かる主体は省略でき、CLIなどの専門用語と識別子は保持する。
```

行為の主体、対象、動作、前提条件、および結果を、文単体または前後の自然な文脈から明確に読み取れる形で記述する。
省略した要素の補い方が一意に定まり、用いる動詞の意味が読者と正確に共有され、主語と述語の論理的な対応関係が成立していることを確認する。
指示対象が曖昧な代名詞は具体的な対象名に戻し、同一段落内で誰が見ても一意にわかる指示語はそのまま残す。
主語を常に文頭に置くことや受動態の全面的な排除を一律に求めるのではなく、日本語として自然な語順を重視する（努力目標）。

1文では1つの事柄を述べる。
主語や対象が異なる別々の事柄は、読点や「〜し、」「〜して」などの連用形でつないで1文にせず、文を分ける（努力目標。別々の事柄かどうかは文の意味から判断する必要があり、機械検査で判定できずレビューで回収するため）。
並列する事柄は箇条書きにする。
条件と結果、理由と結論、手段と目的のように、1つの事柄を成り立たせる論理関係は1文のまま書いてよい。
文を分ける基準は事柄の数とし、文字数や読点の数は基準にしない。

```text
例文: 旧機能は次の版で廃止する。共有フォルダーの文書は、URLを指定するだけで参照できるようにする。
説明: 旧機能の廃止と、共有フォルダーの文書の参照方法は、対象が異なる別々の事柄であるため2文に分ける。
```

具体的な操作や状態がイメージできない比喩表現や、漢語や名詞をやみくもに連続させた表現は避け、適切な助詞と動詞を補って文全体を再構成する。
表現の不自然さを指摘する際は、その文や句の内部で論理関係が破綻している箇所を具体的に説明し、他の記述や専門知識との不整合に基づく事実誤認の指摘とは明確に区別する。
定着している専門用語、字義どおりの動作表現、文脈から一意に復元できる自然な省略、見出しや箇条書きの一覧、エージェント向け文書における体言止めは適切に維持する（努力目標）。

機械のシステム処理は、取得する・読み取る・抽出する・成立する・許可される・作用する・追加するなど、実際の処理を表す正確な動詞で記述する。
人間や動物の動作を当てはめた比喩は、処理の意味を取り違えない語句へ書き換える。

システムやアーキテクチャの構造は、公開エンドポイント、起動コマンド、呼び出し元、接続先URLなど、構成要素を特定できる正確な名称で記述する。
場所にたとえた名詞は、その名称へ書き換える。
作業項目間の依存（`depends_on`など）や、ソフトウェア、パッケージ、モジュールの依存関係を表す`依存`や`依存先`は、確立された技術用語として使用できる。
一般的なドキュメントにおける成立条件や、単なるネットワーク通信の相手・接続先に対しては、この技術用語を安易に使わず、前提条件や接続先を具体的に記述する。

英語の定型句は、処理結果や動作が直感的に伝わる自然な日本語で表す。
「得られるものがない」「次のリクエストから拒否される」のように意味を直接書き、単語ごとの直訳による取り違えを防ぐ。

事物の呼び名は、想定する読者がその専門分野において自身で文章を書く際に用いる標準的な名称に統一する。
文が長くなったとしても、システムや事物を書き手が思いつきで省略した短い比喩や独自の言い換えで済ませず、その分野で正式に通じる名称を用いる（例えば、リクエストを`要求`と言い換えたり、夜間バッチを`夜間の処理`と言い換えたりしない）。
システム構成図のボックス内や表の列名など、スペースが限られた短い記述箇所ほどこうした独自の置き換えが発生しやすいため、同一の基準を適用する。
統計・数学・法律などの専門分野の用語を使うときは、文脈が専門的か一般的かを問わず、書こうとしている意味がその語の正しい語義（専門分野での定義、または辞書に載る一般語としての語義）のいずれかと一致しているかを確かめる。
一般語として定着した語義での使用は正用である（例えば「有意な設定項目」を「意味のある設定項目」の意味で書く）。
どの語義とも一致しない俗用の場合は、その語を使わず、指す内容を直接書く。
具体例として、「母数」は統計学では母集団の特性値（パラメーター）を指すため、分母、集計対象の件数、母集団、計算の基準額を指す場面では「分母」「集計対象」「母集団」「基準額」などと書く。
動詞についても、`届く`、`動く`、`入れる`、`受ける`といった抽象的で多義的な語を使わず、読者の専門分野に即した表現で何がどのように変化するかを具体的に記述する。
例として、インフラ担当者向けであれば`社内VPNからしか入れない`を「社内VPNからしかアクセスできない」とし、デザイナー向けであれば`Figmaの値がボタンに届く`を「Figmaの値がボタンに反映される」と記述する。

元の素材や作業メモに現れる作業用の仮称（実験時の条件名、Gitブランチ名、集計作業で便宜上付けたカテゴリ名など）は外部の読者には伝わらないため、そのまま使用せず、それが具体的に何を意味するのかを言葉で説明する。
ドキュメントの中で独自の短い略称や記号を新設して読者に記憶を強いる書き方（例えば`以下「高」と呼ぶ`など）は避け、通常の言葉でそのまま表現できるのであれば言葉で記述する。
どうしても略称や呼称を導入する必要がある場合は、その名称を見ただけで内容が連想できる分かりやすい語句を選定し（具体例として、住所入力と決済入力を1画面に統合したデザイン案を「1画面案」と呼ぶなど）、同一文書内では表記の揺れをなくして統一する。

システムの挙動を説明する際は、その動作を実行している主体を主語にして記述する。
システムに感情や意思があるかのように見せかける擬人化表現や、判断を下した主体と客観的な根拠を曖昧にする推量表現は避け、具体的な動作や判断内容をその根拠と正確に対応付けて記述する。
文長制限や文末表現の統一といった数値指標を満たすことだけを目的にした無理な文の分割や不自然な言い換えは行わず、条件と結果の論理的なつながり、時制、確実性の度合いを正しく維持する（努力目標）。

```text
例文: 設定ファイルが存在する場合、CLIは指定された保存先へ結果を書き込む。
説明: 発生条件が設定ファイルの存在、動作の主体がCLI、対象が指定された保存先であり、書き込まれる結果との論理関係が明確に読み取れる。
```

<!-- portable-quality:end -->

既存の名前で複数の主体・プロジェクト・変更前後の対象を説明する場合も、`referent-table.md`「適用場面」に従って各対象の所属を対応付ける。
新しい概念名や内部識別子を導入する際は、`referent-table.md`の候補語選定基準に従い、単語を決める前に対象が指す実体と果たすべき役割を明確にする。
特定の1つのドキュメントの中でのみ使用する固有の技術用語は、その文書内で最初に出現した箇所で定義を明記する。

外国語の専門用語を日本語に翻訳する際は、文脈において対象が指す具体的な実体や動作を正確に確認した上で適切な訳語を選定する（例えば`step`は、手順の流れであれば「工程」、物理的な段差であれば「段」と訳す。また`field`は、データ構造であれば「項目」、UI画面であれば「入力欄」と訳す）。
