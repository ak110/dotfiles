# Tailwind CSS記述スタイル

本書は、Tailwind CSSを使用するコードを記述・レビューするエージェントに向けて、v4系において判断を誤りやすいポイントの基準をまとめたものである。
対象バージョン: Tailwind CSS v4系（参考実利用バージョン: 4.3）。v3からの移行点を含む公式ドキュメントは <https://tailwindcss.com/docs> を参照する。

## セットアップと設定（v4のCSSファースト設定）

- 設定ファイル`tailwind.config.js`を新規に作成することは避け、CSS内の`@theme`ディレクティブを用いてデザイントークンを定義する（努力目標。JavaScript形式の設定ファイルは、互換性維持のための`@config`経由でのみ読み込まれるため）。
- エントリポイントとなるCSSファイルでは、`@import "tailwindcss";`でTailwindを読み込む。
- デザイントークンは、`@theme { --color-brand-500: oklch(...); }`のようにCSSカスタムプロパティ（CSS変数）として定義する（これにより、ユーティリティクラスとCSS変数の双方から参照可能となる）。独自に定義するカスタムトークンも、`--breakpoint-*`や`--color-*`などの公式の名前空間規則に合わせて命名する。
- デフォルトのカラーパレットをすべて自前の定義で置き換える場合は、`--color-*: initial;`で初期化してから新たなトークンを定義する。
- ダークモードの適用条件を変更する場合は、`@custom-variant dark (&:where(.dark, .dark *));`のようにCSS側でバリアントを再定義する（v4には従来の`darkMode`設定キーは存在しない）。
- クラス名のプレフィックス（接頭辞）を指定する場合は、`@import "tailwindcss" prefix(tw);`と記述する。

## ユーティリティファーストの運用原則

- スタイルの適用にはユーティリティクラスを最優先で使用し、繰り返し出現する共通のUIパターンはコンポーネントとして共通化する。`@apply`を多用してスタイル定義を二重管理することは避ける。
- CSS ModulesやVue/Svelteの`<style>`ブロックなど、別バンドルとして処理されるスタイル内では、`@apply`よりも`var(--color-blue-500)`のようにCSS変数を直接参照する方法を優先する。`@apply`や`@variant`を使用するには`@reference`によるテーマの事前読み込みが必要となり、ビルドパフォーマンスも低下するためである。
- 繰り返し使用される任意の値（`w-[123px]`など）はトークンとして共通化し、詳細度の競合はセレクタの指定や読み込み順序の調整によって解決する。`!important`の常用によってスタイルを強制上書きすることは避ける。

## クラス名の並び順

- クラス名のソートや整列は、プロジェクトで設定されているコードフォーマッターに委ねる（努力目標。記述スタイルの統一と手動整列の負担を省くため）。ツールの選定は`implementation-time.md`の標準ツール表に従い、Prettierを採用している環境では`prettier-plugin-tailwindcss`を使用する。

## 動的なクラス名生成の回避

- 条件分岐やマッピング用のテーブルオブジェクト内では、`bg-red-600`のように完全なクラス名文字列をそのまま記述する。Tailwind CSSはビルド時にソースコードをプレーンテキストとして静的スキャンするため、文字列結合などにより実行時にしか確定しない動的なクラス名はCSSとして生成されないためである。
