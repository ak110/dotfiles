# 試験の設計と見直し

テストを設計する担当が利用場面と失敗の条件から検証単位を選び、ユーザーが重要な機能の合否を確かめられるようにする。

## 検証単位の選定

受入シナリオは、利用の目的と失敗の条件、入力と初期状態、実行の境界、独立した期待値、結果の観測、保証の限界の順に具体化する。
実装の前に利用主体が達成することと検出すべき失敗を定め、仕様・公開インターフェース・通常の運用の観測から入力と初期状態を選ぶ。

- 代表の操作には、同じ違反を検出できる最も上位で安定した公開操作（通常の運用にあるCLIコマンド、hook、画面操作、更新バッチなど）を選ぶ。
  独立して使える公開操作が複数ある時は操作ごとにシナリオを用意し、1つの通常の操作がそれらを順に実行して各段の違反を検出できる時だけ統合する（既存の保護対象の試験は統合しない）。
- 要求された結果（実行、操作、出力、永続状態）を直接観測できる手段と環境を選び、実ブラウザーや本来の起動条件でしか分からない結果はその条件で観測する。
- 起動コマンドが依存の解決や環境の作成をする時は、準備済みの開発環境と導入済みの配布環境を分け、準備済みの環境の成功だけで初回の起動を判定しない。
- APIのエンドポイントの条件は、実際にリクエストを発行してパラメーターの受け渡しと状態遷移を実行する試験で確かめる。
- 外部の主体が途中で状態を変えるシナリオでは、実機か一次資料で確かめた呼出順序と副作用をテストダブルへ反映し、生成側から最終の利用側までの境界を一貫して通す。
  ダブルは外部I/Oや時機の制御に使って業務ルールの複製と分け、所有する製品の処理を通して外側だけを隔離する案を先に比べる。
- 実行した生成側・変換・利用側、差し替えた境界、準備で省いた処理、観測した最終結果を対応付け、保証を実行した範囲に限る。
  E2Eなどの名称だけで保証を決めず、内部サービスの直接呼出し、状態遷移の全面スタブ、失敗入力を確かめない等値比較はその境界までの保証とする。
- 文書化された仕様の条件は、送信側と受信側の主体・入力値・前提条件・後続の操作を当てはめる試行か、本文と参照先の精読で、渡す値と受理できる値の一致を確かめる。
- 画面を持つ成果物では、ロジックは単体テスト、操作への画面の反応はjsdomなどのコンポーネントテスト、レイアウトと実ブラウザ固有の挙動と画面をまたぐ遷移は実ブラウザのE2Eで確かめる。
  E2Eでモックしてよいのは検証対象の外のAPIだけであり、前後端の接続を要する重要なシナリオと重要な異常系は実APIのE2Eで確かめる。
- 複雑な処理の変更では、計算量、遅延・資源消費、失敗率・分布、並行性、状態の不変条件、部分失敗から観点を選び、エラーを出さない劣化や低頻度の失敗を観測できるか確かめる。

差分検証は同じ入力に対する2つの実装の観測結果を比べる方法である。
目的に応じて比較先を選ぶ。

- 基準版との回帰比較: 性能の変更、動作を保つリファクタリング、変えた契約と保つ契約が混在する修正で、重要な回帰を既存の試験や読解で判断しにくい時に選べる。
  要求と承認済みの仕様から、基準版から保つ動作と意図した変更を分ける。
- 独立実装との比較: 変更の無い既存実装でも新規実装でも、独立に開発された別実装と契約の共通部分があり、期待値を手で書きにくい時に選べる。
  公式の参照実装が使えるパーサーでは、期待値を手で書ける場合も、適合を確かめるために出力を比べる（努力目標）。

どちらも要求と仕様から比較範囲を決め、同じ生成入力・初期状態・操作列を与えて、成功値・エラー・順序・更新後の状態・副作用・並行更新を比べる。
時刻・乱数・IDなど、契約上意味を持たない観測値の正規化の範囲を明確にする。
差だけで欠陥と確定せず、許容された契約の差、環境差、非決定の値、準備の失敗を区別する。
仕様などから独立に判定した共通の期待値に反する差は欠陥候補とし、許容された契約差は欠陥とせず、共通の期待値を独立に判定できない差は未判定とする。
結果が一致しても両者に共通する欠陥は見つからないため、仕様由来の期待値も使い、基準版の既知の不良を正解から除く。

例ベースで固定した重要な受入シナリオに、検出したい問題と使える材料に合う探索を組み合わせる。
仕様から状態・操作・許可条件を表せる時は`testing.md`「状態遷移の性質確認」で反例を探し、障害の履歴があれば失敗しやすい入力からエラー処理と復旧を探り、材料が乏しい時はランダムな操作でクラッシュを探す（業務上の正しさの判定基準が無い部分は保証から除く）。
使用性は想定する人の知識・状況とゴールを与え、到達の成否と手数・迷い・誤操作を分けて観測し、大きな画面変更では手順を渡さないブラウザーの試行も選べる。
AIが操作する場合も独立した期待値と合否判定を分け、決定論的に比べられる結果はAIの判定に置き換えない。
AIの判定には画面などの証拠と具体的な期待結果を渡し、操作担当の完了申告や判定不能は成功の証拠から外す。
契約に応じて、同件数で異なる明細、画面とダウンロード内容の相違、別のエンドユーザーや作業領域の混入まで最終成果で識別する。
探索の結果は候補として扱い、再現と仕様の確認を経て回帰の試験へつなぐ（回帰の試験と再発防止の区別は`agent-basics:bugfix/references/prevention.md`「言葉の区別」）。

### 削除・統合の類型

試験を削除・置き換え・統合する前に、候補を1本ずつ、消す類型に当たるかより先に、セキュリティ、認可、法令上の義務、安全性の契約を確かめるための試験（保護対象）かで分ける。
分けるのは試験が確かめるべき契約であり、今その違反を検出できるかではない（認可処理を経由するだけで別の契約を確かめる試験は保護対象に当たらない）。
保護対象は実装の内部の形も固定している場合も、同じ違反を検出する上位の試験（結合試験、E2E、モデル）がある場合も、削除・置き換え・統合の対象から外して残す。
保護対象に欠陥（実装から写した期待値、契約違反を検出できないなど）があれば、契約基準の入力・期待値へ直す。
この判定は本節の類型と、本書と `testing.md` の他の節で試験を消す・置き換える・統合する全ての規定（「試験を書く前の確認」「検証単位の優先順位」「検証単位の選定」「状態遷移の性質確認」など）より先に行う。
消す基準だけを読むと、守るべき試験まで整理の対象に入るためである。

試験の追加や整理では、消した時に現実的に見逃す不具合を明確にし、保証の価値（害の大きさと発見後に直す容易さ）を実行時間・不安定さ・保守の負担と比べる。
件数やカバレッジの数値は残す理由から外し、エンドユーザーが気付いてからの修正で十分な細かな挙動（一時的な表示の文言、表示が戻る時機など）は対象から外す。
変更作業中に次の類型の試験に触れ、固有の公開契約違反を検出できないと分かった試験は、期待値を更新せず削除する。
守る契約があれば、契約基準の入力・期待値へ直すか、利用シナリオ全体を確かめる試験へ統合する（統合は保護対象に適用しない）。
製品コードへ試験専用のexportや分岐、ラッパーを足さない。
試験の削除で不要になった専用処理も削る。
内部の呼出回数・作業量は通常の機能試験で固定しない。
性能契約で必要な計数は機能試験から分ける。

- 実装や実行結果から期待値を写した試験（本書「期待値の出所」の独立した期待値へ置き換える）
- 状態遷移関数だけに遷移表と同じ入力を並べた試験（利用側の操作列へ移し、直接書込や呼び出しの漏れも確かめる）
  外部イベントが直接届く入力境界の試験は、境界で起きる結果を確かめるために残す
- モックに設定した戻り値そのものを確かめる試験（その戻り値を消費した結果の検証へ置き換える）
- 型システムや利用ライブラリが既に保証する性質だけを確かめる試験
- 観点・入力・期待値が重複する試験や、同じ失敗パターンだけを検出する過剰なケース分け（代表値と境界値へ集約する）
- 公開契約でない内部の定数、内部関数の呼出順序、引数の受け渡しを固定する試験（外から観測できる最終結果の検証へ置き換える）

### 期待値の出所

実装と仕様が異なる時は試験を実装に合わせず、期待値と出力を保全して `agent-basics:bugfix` で原因を確かめ、認可内で是正して同じ試験を再実行し、結果または未回復の影響・試行・再開条件を伝える。

期待値は要求仕様と入力条件から独立に導き、実装と同じ計算式や実行して得た出力を貼った期待値は実装の不具合まで固定する。
人が後から外部仕様を変えた時は最新の仕様を出所にし、以前の完了条件との差を既存の決定事項や変更履歴へ結び付ける。
実利用環境で反例や暗黙の仕様判断が見つかった時は、要求と認可を確かめて仕様を明文化し、再現できる入力と状態を回帰の試験へ反映し、観測した挙動を正しい期待値とするかは要求と比べて決める。
要求と認可はユーザー原文に基づいて判断し、AIの意図推定と変更説明は補助資料に限定する。
契約が定める空の結果、例外、外部への送信内容や未送信も保つべき振る舞いであり、アサーションの種類やfixture内の呼出しという形だけでは消さない。
否定側の試験では誤った存在や副作用を検出できるかを確かめ、観測手段が働くことは対応する肯定側でも確かめる。

- テスト対象のコード自身の記述（文字列リテラル、定数、固定のテキストファイル）から期待値を写し、出力に含まれるかだけを確かめる試験は書かない（努力目標）。
  CLIのヘルプ、MCPツールの説明文、UIの表示テキストの一部の有無を確かめる試験が典型である。
  型が保証する範囲、定数の設定値、省略時の値、単純な委譲、分岐の全網羅そのものは読解で確かめる。
- 次は有用な試験として保つ。
  実装のロジックを経由した振る舞い（`--help`の指定で予期しない副作用が起きないことなど）。
  コード内の記述と、実装とは独立して更新される別の定義元（エージェント向けの規約文書、公式スキーマ、外部ツールの公開仕様など）との一致（ヘルプに書いた待機秒数と、タイムアウト上限を計算する関数の戻り値の一致など）。
  全てのコマンドやツールに課す共通の構造的制約と、省略時の値を解釈・解決する処理（フォールバックの優先順、未設定時の補完、不正な値の拒否など）。
- スナップショット試験は、初回に記録した値が仕様に合うことを仕様側の根拠で確かめてから採用する。

### 失敗様態の列挙とテストレイヤー

- 契約に沿った主な失敗パターン（境界値、空データ、異常系、状態遷移の不整合、二重実行、並行の競合など）を先に洗い出し、それぞれを検出できる単位と層を選ぶ（努力目標。手薄になりやすい異常系を厚くするため）。
- 生成器と生成物の両方に同じ契約の試験を置く時は、生成物側だけが検出できる差（生成の未実行、一部の同期ずれなど）を明確にし、原本をそのまま埋め込むだけの生成器では生成物側の試験を増やさずに済ませる（努力目標。重複を避けるため）。

## private関数の直接テスト禁止

段3（単一関数の内部処理）は公開インターフェース経由で確かめ、private関数（モジュールやクラスの内側だけで参照する関数）を直接呼ぶ試験は書かない。
Rustの`#[cfg(test)] mod tests`は同じモジュールに閉じた言語標準の機構で外部との結合を生まないため、この制限の対象外とする。
private関数のロジックは次の順で手段を選び、既存の直接テストを直す時も同じ順に従う（同じファイルに直接テストがあることは選ぶ根拠から外す）。

1. 公開インターフェースを経由した結合テスト（呼出元や同等の機能を持つ他の公開関数も使う）
2. 関数の引数による依存の注入での制御
3. 単独で公開する再利用価値がある場合の関数のpublic化（テストの都合だけの公開は避ける）
4. いずれも使えない場合に限る、最小範囲の直接テスト

試験のリファクタリング、移行、共通ヘルパーへの共通化では検証の内容を保ち、特定の処理を確かめる試験は`testing.md`「分岐条件の効果の裏付け」の無効化で働くことを確かめ、粒度を下げる時は意図した設計変更として行う。

## 簡潔さ

- テストダブルは外部サービス、乱数、グローバル状態、ランタイムの内部機構など決定論的に確かめにくい依存に限り、引数経由の注入（省略時は本番の実装）を優先する。
  時刻を渡す設計は[日時処理](implementation-time.md#日時処理)に従う。
- ホスト、外部CLI、外部APIなどが生成するログ、hookの入力、応答を模した試験データは、対象版の実際の出力か公式スキーマから構造と値を写し、参照した版と出所をテストコードに記録する。
  推測で手作りしたデータは実装と同じ誤った前提を共有するため、入力は生産処理の実出力、実ログや公式スキーマから最小化した標本、手書きの合成入力の順に、確かめる境界へ対応付ける。
  形式と生成手順の同等性は`agent-basics:writing-standards/references/investigation.md`「根拠と主張の一致」で判断し、外部ホストの起動が重い網羅ケースは同等性を確かめた標本で軽い試験へ置く。
- 既存のクラスやモジュールへ試験を足す前に、共通のfixtureやヘルパーが作る入力と、同種の既存の試験が渡す値の構造を確かめる（前提の違う入力では対象の機構が発動しない場合がある）。
