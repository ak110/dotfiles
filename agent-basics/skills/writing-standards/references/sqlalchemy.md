# SQLAlchemy

対象のバージョン: SQLAlchemy 2.0系のORM。
本書は、SQLAlchemyのORMでクエリと更新を書く時に読み、autoflushで入力の検証エラーより先にDBの制約違反の例外が送出される誤りを防ぐ処理の順序を示す。
一般知識で導けない固有の挙動だけを書くのは`agent-basics:writing-standards/references/quality-principles-subtraction.md`の適用である。

## 問い合わせの書き方

- NULLの判定は`== None`ではなく`.is_(None)`で書く。

## 成立条件

初期設定の`Session`は、ORMのクエリを発行する直前に、保留中の変更をデータベースへ送る（autoflush）。
次の条件が全て成り立つ処理では、アプリケーションの入力検証で捕まえるべき不正が、DBの制約違反の例外として先に起きる。

- autoflushが有効である。
- 永続化済みのインスタンスの属性を更新している途中か、新しい行のインスタンスを`session.add`した後である。
- 保留中の変更に、一意性、`NOT NULL`、外部キーなどの制約に反しうる値がある。
- 呼び出し元が、入力の検証の例外とDBドライバーの例外（`IntegrityError`など）を区別して扱う。

最初の属性の代入（新しい行では`Session`への追加）から、入力の検証と必要な全ての代入が終わるまでを「属性代入区間」と呼ぶ。

## 問い合わせと属性代入の順序

- DBへの問い合わせ（設定値の取得や一意性の事前確認など）は属性代入区間の前に終え、結果を変数に持ってから代入する（代入の途中でクエリを発行するとautoflushが起きるため）。
- DBへの問い合わせは、DBを使わない単純な入力検証の後に置く（努力目標。検証エラーだけで終わる場合に、`Session`の開始と問い合わせの費用を省けるため）。
- 同じトランザクションの保留中の変更を反映した結果を期待する処理では、その前提を保ち、問い合わせの前に`Session.flush()`を明示して送る時点を決める。
  クエリで`no_autoflush`を使って避けると、追加・更新した最新のデータを前提とする呼び出し元が古い状態を読む。
