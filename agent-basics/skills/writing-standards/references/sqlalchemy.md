# SQLAlchemy

本書は、SQLAlchemy 2.0系のORMを使用するコードを作成するエージェントに向けて、クエリの記述方法や、autoflushによって入力バリデーションエラーがDB制約違反例外として誤って先行送出されるのを防ぐ処理順序をまとめたものである。

## 問い合わせの書き方

- NULLを判定するクエリでは、`== None`ではなく`.is_(None)`を使用する。

## 成立条件

デフォルト設定の`Session`は、ORM対応のクエリを発行する直前に、保留されている変更内容をデータベースへ自動的に送信（flush）する。
以下の条件がすべて満たされる処理では、本来はアプリケーション側の入力バリデーションで捕捉すべき入力不正が、意図せずデータベースの制約違反例外として先に発生してしまう。

- autoflush機能が有効になっている。
- 既存の永続化インスタンスの属性を更新している最中であるか、または新規行のインスタンスを`Session`へ追加（`session.add`）した後である。
- 保留中の変更内容に、一意性制約、`NOT NULL`制約、外部キー制約などのDB制約に違反し得る値が含まれている。
- 呼び出し元が、ユーザー入力エラー（バリデーション例外）とDBドライバー由来の例外（IntegrityErrorなど）を区別して処理している。

最初の属性代入（新規行の場合は`Session`への追加）から、入力値の検証と必要なすべての属性代入が完了するまでの区間を「属性代入区間」と呼ぶ。

## 問い合わせと属性代入の順序

- DBへの問い合わせ（設定値の取得・判定や一意性の事前確認など）は属性代入区間を開始する前に完了させ、取得した結果を変数に保持してから属性へ代入する（原則。代入途中の不完全な状態でクエリが走り、autoflushが発動するのを防ぐため）。
- DBへの問い合わせは、DBアクセスを伴わない単純な入力バリデーションの後に配置する（努力目標。バリデーションエラーのみで終了するケースにおいて、不要な`Session`の開始やDB問い合わせのコストを削減できるため）。
- 同一のトランザクション内で保留中の変更内容を反映したクエリ結果を期待する処理フローでは、その前提契約を維持し、必要な箇所で`Session.flush()`を明示的に呼び出して、問い合わせの前に変更を送信する時点を確定させる。クエリ実行時にautoflushを無効化（`no_autoflush`）して回避することは避ける（原則。同一トランザクション内で追加・更新した最新データを前提とする呼び出し元が、古い状態のデータを取得してしまうため）。
