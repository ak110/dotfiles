# ドキュメント品質：文章の共通規定

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

## 文章の共通規定

エージェントが作成する文章は、結論または目的、主要な関係性、理解・判断・行動を促す詳細情報の順序で構成する。
全ての文章を極力簡潔に書き、読み手が文脈から容易に補える情報は書かない（努力目標。内容を増やさない装飾は本題から注意を逸らす）。
語は文字数の少なさで選ばず、`writing.md`「日本語の書き方」の呼び名と動詞の規定に従う。
正確性、安全性、認可、監査証跡、および所定のフォーマットが要求する必須情報は漏れなく維持する。
件数や文字数の一律な上限は設けず、読み手が判断や行動をするために必要な情報量に基づいて記述する。
タイトル、件名、CLIヘルプの要約、本文の冒頭文では、目的や最も重要な結果を簡潔な文で提示する。
理解に必要な主語、助詞、接続語を残し、長い修飾や条件は主体、対象、条件、動作、結果の関係が順に分かるよう整理する。
英語の生成文の理解しにくさを調べた[研究](https://arxiv.org/abs/2610.29162v1)を参考にした判断であり、日本語への効果は同研究の実証対象外である。
対象の名前や手段を列挙する場合であっても、読み手が何を実行できるか、何が変化するかを最初に把握できる構成にする。

結論、条件、例外、理由を組み立ててから、意味を保って重複と修飾を削る。
短縮後も、読み手が主体、対象、条件、結果を一意に読み取れるようにする。
説明順序と詳しさは、読者が理解・判断したいことから決める（努力目標。短さだけを優先すると説明のつながりが失われるため）。
文体を整える推敲では、現行原稿の主張、理由、根拠、条件、確度、拘束力、重点を比較の基準とし、元の理由を別の理由へ差し替えない。
同じ役割の重複を整理し、理解を進める接続文や総括はその役割に応じて残す（努力目標）。

本節の規定は、人間とエージェントの双方が読む、エージェントが記述するすべての文章に適用する。
これには委譲プロンプトや追加の連絡文、作業項目の本文、計画ファイル（進捗ログを含む）、Issueやプルリクエスト（PR/MR）の説明文、レビューへの返信、コミットメッセージ、作業報告などが含まれる。
各スキル文書では成果物の種別に固有の事項のみを扱い、同一の観点に関する規定が重複しないように配慮する（努力目標。重複した規定が存在すると、改訂時に不整合の原因となる）。

- 情報を追加する前の判断: 文章を書く前に読者と読まれる場面を明確にし、その読者が判断、操作、再取得をするために実際に必要とする情報だけを記述する。
  他の規範が記載を求めている項目であってもこの判断を適用し、読者が必要とする粒度で書く。
  情報を追加する基準は「省略すると読者が判断や操作を行えなくなるかどうか」とし、書き手だけが把握している修正前の症状、調査過程で生じた疑問、担当エージェントの誤認などは読者の前提から除外する。
  利用方法、実在する制約、意図的な仕様差、維持すべき設計判断は、読者の判断や操作に必要な範囲で漏れなく残す
- 書き手が調査・検証した過程（検索した範囲や語句、観点ごとの結論、0件や非該当の理由、突き合わせた記録の保存場所、中間出力のファイルパスなど）は、読者が実際に参照する場合を除き、証拠ファイルや委譲元への返却記録にのみ残す。
  本文には結論と、読者が再取得に用いる保存場所のみを記述する
- 委譲プロンプトや追加の連絡には、委譲先がタスクの実行に直接使う情報だけを記載する。
  委譲先が自身で読み込む規範やスキルの再掲、および作業に影響しない経緯の説明は省く
- コミットの示し方は読み手に合わせて使い分ける。
  人間向けには日付、コミットメッセージの件名、PR/MR番号、タグを用い、再取得が必要な場合に限って一意な短縮OIDを添える。
  エージェント向けには一意な短縮OIDを用い、操作を実行する直前に完全なOIDへ解決する
- 既知の概念を起点として新しい事項との関係性を示してから詳細な説明へ進む
- 1つの段落では1つの話題だけを扱い、先頭文で結論・規定・結果のいずれかを述べる。
  後続の文は先頭文の根拠、条件、または具体例とし、総括は説明を受けて理解や次の判断を進める場合に置く。
  手順や並列するデータは箇条書きや一覧表にまとめ、因果関係や判断理由は段落でつなぐ。
  箇条書きの1つの項目の中で説明や理由が長く続く場合は、独立した段落へ分ける（努力目標）
- コミットメッセージの本文やPR/MRの説明文では、その変更が必要になった背景、理由、および達成したい目的を明記する
- 作業者の手元で管理する作業項目の記録は個人記録であるため、外部に公開する成果物からはその内部ファイル名や状態などの識別子を除外する。
  作業項目の記録や個人のセッション記録が事実の出所や再検証手段を保持している場合は、公開されている実装、テスト、参考資料と、検証時の観測条件や結果を本文へ転記し、読者が後から追跡できるようにする。
  個人記録の識別子や行番号は直接書かず、転記できない一次記録についてはリポジトリ外部に存在することのみを記す。
  ただし、計画ファイル、作業項目の記録自体の本文、およびレビュー指摘管理表は例外とする
- 個人記録にアクセスできない第三者と共有する文書（Gitの管理対象ドキュメントなど）には、バージョン管理外の個人用メモ（`CLAUDE.local.md`、作業中の計画ファイル、一時ディレクトリ内のファイルなど）を出典や参照先として記載しない。
  代わりに、読者が実際に参照可能な実装コード、設定ファイル、公式ドキュメントへの参照へ置き換える。
  計画ファイル、作業項目の記録の本文、レビュー指摘管理表は前項と同様に例外とする
- 変更の由来（ユーザーの指示によるものか、エージェントの自律的な判断によるものか）は、読者の判断に必要な場合に限定して記載する
- 失敗パターンを説明する場合（テスト、設計書、障害報告、診断メッセージなど）は、エラーが発生した観測地点の事象と、後段の処理で引き起こされる結果とを（入力の種類によって挙動が異なる場合は種類ごとに）対応付けて記述し、説明内容と実際のエラー判定やシステムの挙動を一致させる。
  両者が食い違うと、保証されていない動作を読者が保証済みと誤認する原因になる
- 操作手順、設定方法、対処方法を案内する場合（手順書、ツールの出力、委譲プロンプトなど）は、実行すべきコマンド、ツール名、引数を、読者がそのまま実行できる実在の名称と構文で記述する。
  さらに、実装の処理フローや実際の実行結果に基づき、実行後に説明どおりの状態へ確実に到達することを確認する。
  設計書上の記述は、手段が実在することの裏付けにとどまる
- 条件分岐に応じて語句を前置したり連結したりして動的に組み立てる文章（CLIのステータス表示、ログメッセージ、生成プロンプトなど）は、分岐ごとの完成した出力全体を1つの文として通読し、主語、目的語、述語が正しく対応しているかを確認する
- 行為の主体、前提条件、適用範囲、確実性の度合いは、その文章が成り立つ根拠に合わせて正確に記述する。
  「〜の場合」「〜に限り」「〜では」といった条件や限定表現は、その文の成立に真に必要な範囲で記載し、要求事項や認可の範囲は書く前に確定する。
  観測した事例の対象、工程、識別子、原因の分類などは、それ単体では限定を設ける十分な根拠にならない。
  完成後に各文の限定条件を反証する手順は、`review-only-criteria.md`の「限定の反証」に従う
- 確定している事実と未確認の可能性を明確に区別し、因果関係や推奨事項を述べる際は、成立条件と客観的な根拠を添える
- 既存の要素を指す際は、規範や対象の成果物に実在する正式な名称（画面名、UI文言、コマンド名、規範で定義された用語など）を用い、固有の名称が存在しない対象は客観的な説明文で表現する。
  その場で独自に考案した呼称や、会話ログ、コミットメッセージ、過去の障害記録などで使われていた定義のない俗称は、正式名称または説明的な表現に置き換える。
  事物の名称や動詞の選定は`writing.md`「日本語の書き方」に従う。
  新しい概念を導入する場合は、その文書内で明確に定義してから使用する。
  別文書の節名、用語、用例の略号を引用する際は、同じ文の中、あるいは同じ段落や箇条書きの冒頭で文書名を明示し、読者が参照元を確実に特定できるようにする。
  完成時に各名詞句の定義元と参照可能性を確認する手順は、`review-only-criteria.md`の「名前の到達性」に従う
- 強調表現、一般論、前置き、結びの言葉は、読者が判断を下す上で実際に役立つ情報に限定する。
  対比フレーミングの禁止と必要な否定文の扱いについては、`writing.md`「日本語の書き方」に従う

- 例示する対象が全体の一部にすぎない場合は、上位の概念と対象範囲を明記する。
  閉じた網羅的な一覧のように記述すると、読者が例示以外の適切な選択肢を除外してしまう恐れがある
- 文書が完成した段階で、各記述が読者の判断、操作、再取得に実際に役立つか、識別子の粒度が読者に合っているかを改めて通読して確認する。
  複数の節をまたぐ重複記述のうち不要なものは削除する。
  ただし、必須の構造、要件の原文、根拠、適用範囲の具体例は維持する

表記の自動チェックは、口語表現チェック、textlint、ダッシュチェック、およびプロジェクトが用意する表記チェックが担当する。
