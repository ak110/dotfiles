# 機械チェックスクリプトの設計原則

エージェントが繰り返し実行する機械チェックスクリプト（`check_*.py`など、計画ファイルやエージェント向け文書に対するチェック全般）は、実行時の出力がエージェントのコンテキストに蓄積される。そのため、出力ノイズの抑制と起動回数の削減を設計段階から考慮する。

自動チェックを新たに追加するのは、入力が構造化されており、期待値が一意に定まり、判定結果が安定していて、違反時の修正方法を明確に示せる場合に限定する。
自然言語の意味解釈、責務分担の妥当性、表現の適切さなど、文脈によって複数の解釈が成り立ちうる対象は、作成規範や人間・エージェントによるレビューで扱う。
新しいチェック項目を追加する前には、正常例、違反例、および引用や識別子などの例外・許容例を用いて判定の安定性を確認し、誤検出時の対応コストや将来の保守費用を比較検討する。
自然言語の文脈上の意味や必要性は、単純な単語の一致判定ではなく、レビューによって評価する。

## 出力の簡潔さ

- チェックに成功した場合（違反なし）はexit 0で終了し、標準出力を抑制する（出力を抑制する部分は努力目標）。
- `error`相当の重大な違反は、該当箇所、要点、具体的な修正方法のみを`stderr`に出力してexit 1で終了する。`warning`区分は`[warn]`などのプレフィックスを付けて`stderr`に出力し、終了コード（exit code）には反映させない。修正方法の書き方や、対応が必要な警告における次のアクションの提示方法は、`writing.md`「読み手別の追加注意点」の「プログラムが出力するメッセージ」の項目に従う。
  - 複数の条件を複合して判定する違反では、どの条件が満たされなかったのかと、比較対象となった値（期待値と実際の値）を要点に含める。
  - 複数種類の違反を検出するスクリプトでは、違反を出力する処理側で種類ごとの修正方法を保持し、実際に出力された種類の修正方法のみを1回ずつ表示する。共通の修正方法を表示する場合も、検出された違反の種類に対応する対処法のみを示す。
- 引数の指定ミス、対象ファイルの不在、権限不足、不正なエンコーディングなど、チェック自体を開始できない事前エラーはexit 2とし、チェック結果の違反（exit 1）と明確に区別する（努力目標）。
- 外部コマンド（textlintなど）の未加工の出力（生出力）をそのまま流し込まず、JSONなどの構造化出力をパースして、違反件数と該当箇所を簡潔に要約して表示する。

## 起動の統合

- 同一のタイミングで繰り返し実行される複数の独立したスクリプトは、1つのプロセスに集約して実行できるように設計する（努力目標）。

## 構造化文書の解析

Markdownなどの構造化文書を検証する場合は、見出しやリストなどの文書構造の解析と、生の記法（インラインマークアップなど）の検証処理を明確に分離する。

## チェック項目のerror・warning区分

- `error`区分は、成果物として成立しなくなる致命的な問題（指定されたパス、スキル名、節見出しの実在確認の失敗など）に限定する。
- 表記揺れやスタイルなどの体裁面（textlint、markdownlint、typos、口語表現の指摘など）は`warning`区分にとどめる（細かな体裁修正のために、すでに成立している成果物の確定プロセスがブロックされるのを防ぐため）。
- 新しく設けたチェック項目について、`error`または`warning`に設定した判定根拠をスクリプトのdocstringに記載する（努力目標）。
