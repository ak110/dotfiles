# 機械チェックスクリプトの設計原則

エージェントが繰り返し実行する機械チェックスクリプト（計画やエージェント向け文書の検査など）を新設・改修する時の基準を定める。
出力はエージェントの文脈に蓄積されるため、出力の量と起動の回数を設計の段階で抑える（原則9、`agent-basics:writing-standards/references/quality-principles-subtraction.md`）。
自動チェックを足すのは、入力が構造化され、期待値が一意に定まり、判定が安定し、違反の直し方を示せる場合に限る。
意味の解釈や表現の適否など解釈が分かれる対象は作成規範とレビューで扱い、足す前に正常例・違反例・例外（引用、識別子）で判定の安定性を確かめて、誤検出と保守の費用を比べる。

## 出力の簡潔さ

- 違反なしはexit 0で終え、標準出力を抑える（出力の抑制は努力目標）。
- `error`は該当箇所・要点・直し方だけを`stderr`へ出してexit 1で終え、`warning`は`[warn]`などの接頭辞を付けて`stderr`へ出し、終了コードへの反映から除く。
  複合条件の違反は満たさなかった条件と期待値・実際値を要点に含め、複数種類の違反は出力した種類の直し方だけを1回ずつ示す。
  直し方の書き方は`agent-basics:writing-standards/references/program-messages.md`「出力の基準」に従う。
- 引数の誤り、対象の不在、権限不足、不正な文字コードなど、検査を始められない事前エラーはexit 2とし、違反（exit 1）と分ける（努力目標）。
- 外部コマンド（textlintなど）の生出力はそのまま出さず、構造化出力を解析して件数と該当箇所を要約する。

## 起動の統合

同じ時点で繰り返し実行する独立したスクリプトは、1つのプロセスへ集約できる形にする（努力目標）。

## 構造化文書の解析

Markdownなどの構造化文書は、見出しやリストの構造の解析と、生の記法の検証を分ける。

## チェック項目のerror・warning区分

- `error`は成果物が成立しなくなる問題（パス、スキル名、節見出しの実在確認の失敗など）に限る。
- 体裁（textlint、markdownlint、typos、口語表現の指摘など）は`warning`にとどめ、成立済みの成果物の確定を止めずにおく。
- 新しい項目の区分の根拠は、スクリプトのdocstringに書く（努力目標）。
