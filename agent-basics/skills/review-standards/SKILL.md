# レビュー担当とレビューイーの心得

成果物をレビューする担当と、指摘・是正要求を受けて採否と修正を確定する担当者（レビューイー）の判断基準である。
原則6（作る者と確かめる者を分ける。`agent-basics:writing-standards/references/quality-principles-verification.md`）を中心に、原則3（観測したことだけを事実として言う）と原則5（逸脱は情報である）を適用する。
判定の観点は本スキルへ集め、役割文書や他のスキルで独自の観点を足さない（観点が分散すると判定が分かれ、修正と再レビューが収束しなくなるため）。
「実行レビュー」は、実装後の変更差分を独立した文脈で確かめるレビューを指す。

## レビューの中心

- 作る側は最初からできるだけ正しく作る。
- 1回目のレビューで指摘が出るのはある程度避けられない（作る側の先入観を外から確かめることがレビューの意味である）。
- 2回目以降のレビューで指摘が残る、または新しく出るのは、修正の不足・不正確さか、レビューの不足・不正確さのどちらか（または両方）である。
  出た時点でどちらの欠陥かを特定し、その原因を処置する（レビュー担当は`references/reviewer.md`、レビューイーは`references/reviewee.md`）。

## 判断の初動

原要求から必要な結果と対象集合を定め、成果物・提出証拠・提案とは独立に期待結果を確定する。
是正要求などは事象と修正案を分け、現物・契約・観測結果で裏付けてから、目的・要件、硬い制約、QCDの順に採否を決める（`agent-basics:writing-standards/references/design-heuristics.md`「設計の判定順」）。
目的上の必要性を仕様適合より先に判定し、契約・テスト・計画に書いたこと自体を必要性の根拠にしない。
指摘の受領を追加要件や変更の認可とせず、確認済みの成果と未完了の作業を保つ。
裏付けが不足する範囲は未確認として扱い、影響しない作業は続ける。
欠陥や期待からの逸脱への対処は`agent-basics:bugfix`を起動して始める。
レビュー担当とレビューイーの間で原要求の解釈が分かれた場合は、原文、これまでの発話、実際の回答、現物の成果物を比べる。
ユーザー固有の意図の確認が必要なら、双方の解釈と結果をまとめてユーザーへ確認できる担当者へ返し、回答までその解釈に依る採否と修正を保留する。

## 役割ごとの着手

- コード・文書・計画・作業項目の差分を独立して検収するか、提案・自己判断・他の担当の出力を点検する: 原要求からユーザーが得る結果と対象を決める。
  成果物や提出証拠を読む前に、`references/reviewer.md`の「初回レビュー」で期待を定める。
  実行レビューでは `references/reviewer-execution.md` も初めに使い、要求と観測を分けて照合する。
- 指摘・是正要求・想定外の発見・外部資料に基づく改善案の採否を決める: 指摘された事象、手段の提案、ユーザー自身が決める事項を分ける。
  `references/reviewee.md` で根拠と元の要件から採否を確定する。
  追加の認可が要らない範囲は、自分で直して検証する。

役割が変わった時は次の役割の着手へ進み、同じ版の取得済み本文は再利用する。
個別条件の資料は、次の操作に当たる場合だけ使う。

## 索引

条件が成立したら、判断の前に資料の全文を読む。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 起動時 | `agent-basics:writing-standards/references/quality-principles.md` |
| いずれの役割でも、判定を始める前 | 対象成果物に対応する作成規範 |
| 画面のユーザビリティを判定する前 | `references/reviewer-usability.md` |
| ロゴ、ワードマーク、ブランドマークとそのアイコン展開をレビューする前 | `agent-basics:writing-standards/references/logo-quality.md` |
| 設計に異論がある変更か重要な変更の出荷前に、通常のレビューへ追加して複数のモデルに壊させる時 | `agent-basics:adversarial-review/SKILL.md` |
| 規範の追記を含む案の必要性を判定する前 | `agent-basics:writing-standards/references/agent-documents-additions.md` |
| 初回レビューで作成規範を点検する時 | `agent-basics:writing-standards/references/review-only-criteria.md` |

## 手順

1. 役割と判定を決め、「判断の初動」を行う。
   役割が変われば決め直す。
2. 「索引」の該当資料と役割の手順を適用する。
   同じ版の読了済み資料は再利用する。
3. 報告には適用した本文と原則、根拠を得た指摘、追加の観測が必要な範囲を区別して書く。

## 解決案の比較

同じ問題を解く案が複数ある時の、役割を問わない比べ方である（レビューイーの手順7・9・11でも使う）。

- 各案で失われる観測情報、対象となる入力と状態の範囲、仕様が許す入力が将来増えた後も保てる性質を比べる。
- 数値の閾値を含む基準を提案か改訂する時は、境界の前後に2例以上の値を当てはめ、閾値を上下させた時の判定の変化を確かめてから推奨の理由を書く。
- 概念を新設か変更する時は、主体・出来事・状態とその対応を表せる境界を先に決め、その内側で単純で直接的な実装を選ぶ。
  既存の概念の特殊な場合として扱う案と新しい概念として分ける案は、下流への影響と保守コストを含めて同じ階層で比べる。
  概念と機構の分離や新設は観測した要件と現実を表す範囲に限り、足すこと自体を品質の向上とは評価しない。

## 検収手段の到達可能性

実機の検証、完了条件、待機の手順で合否を決める時と、修正で待機や同期を足す時の、役割を問わない確かめ方である。

- 求められた行為、必要な入力と通知、許された機能、禁止された行為を整理し、それを満たす実行方法を探す。
  同じ対象で成功済みの方法、認可された隔離環境での同等の再現、対象が公開する別の起動方法も探す。
- 方法が1つでも成り立てば到達できると判断する。
  到達できないと判断するのは、探した具体的な方法と、各方法が成り立たなかった観測を全て示せる時に限り、それを応答に書く。
- 要求された検収を文面の比較などへ置き換えず、成り立つ別の検収手段も確定できない時だけ採否を保留する。
- 到達できないと確定した要求は成果物の未達として扱わず、その要求を定めた計画か規範の維持・修正・置換・撤去を比べる。
  レビュー担当はその矛盾を計画か規範の問題として扱い、同じ到達できない完了条件への指摘は1回にとどめる。
- 未達が繰り返す時、同じ害が再発する時、工程が収束しない時は、要求の到達可能性と、その要求を入れた規範の前提を先に見直す。

## 対象成果物の作成規範

作成規範とは対象成果物の種類ごとに適用する作成時の品質基準で、`agent-basics:writing-standards`の該当資料と、対象リポジトリに実在する`AGENTS.md`、`CLAUDE.md`、`.claude/rules/`配下の文書を指す。
変更要求・方針・作業項目・計画を検収する時は、その文書自体と、要求が変更する成果物の双方にそれぞれの作成規範を適用する。
規範の追記案は、案が成立するかと追記自体が必要かを分け、既存の記述の削除・集約で目的を満たせるかを採用前に判断する（`agent-basics:writing-standards/references/agent-documents-additions.md`「規範追記時の判定」）。
レビュー担当は初回レビューで作成規範と`agent-basics:writing-standards/references/review-only-criteria.md`を一括して適用し、レビューイーは指摘が同資料に言及した時に全文を読み、言及された基準を適用する。

## 実害の判定

指摘・推奨は目的・要件、硬い制約、QCDの順に当てはめ、プロダクトの価値を良くするかを原則1〜4から判断する。
通常の利用結果を基に、誰が何を失うか、発生条件と頻度、回復と対処のコストを比べる。
処置が問題に見合うかは、`agent-basics:writing-standards/references/design-heuristics.md`「問題と手段の比例性」に従って判定する。
途中の出力は、最終的な利用結果の裏付けと区別する。

例えば対象外の入力、前提の異なる脅威モデル、仕様上起きない応答の追加検査は、通常運用と公開契約に当てはめる。
配布元と対象が承認済みのフック更新では、手動の信頼操作を残す案が新たな本人判断を得るのか、同じ承認の反復にすぎないのかを比べる。

ユーザー自身とエージェントだけが使うCLIでは、観測した不具合、公開インターフェースの破壊、データの損失を優先する。
複数条件が同時にそろわないと起きない競合と、それを防ぐロック・lease・状態管理の新設は、条件のどれかを観測した時に扱う。
第三者や外部サービスが利用する成果物には、この限定のない実害の判定を適用する。
ロック、書き込み所有権、排他、復旧、移行の指摘では、要件の出所、行う主体と競合する主体、同時に起きる操作と条件を個別に確かめる。

データや作業の消失・重複、私的情報の露出、無認可で取り消せない外部作用、認可の迂回、公開契約どおりに回復できない障害は重大な害の例である。
他の害も生じる条件と結果から重大さを判定する。
重大でない場合は、修正のほか、限界の記録、入力や状態の拒否、変更せずに受け入れる案を比べる。

## 文章成果物の実害

共通の判定軸は本書「実害の判定」に従う。
文章成果物の実害は、読者が本文から行為者、対象、条件、結果を一意に読み取れず、判断、操作、検証を誤るか作業を進められなくなる状態を指す。
文章への指摘の採否は、作成規範やレビュー限定基準の条文への違反か、この実害が生じるかで判定し、機能面の問題と完了条件の充足は独立に確かめる。
エンドユーザー向け文書の誤記と、適用対象のスタイルへの違反は、品質に影響する指摘として直す。
後続作業へ要求を渡す作業項目の起草・投入前の検収では、意味の正確さと引き継ぎ可能性を品質水準とし、要求・認可・対象・必要事項の欠落、事実と仮説の混同、方式の不成立、完成判定の不足、意味を取り違える曖昧さを検収する。
不具合対応では、`原因:`が観測の所在を持つこと、`処置:`が足す案ならその前に検討する3案（無くす・単純にする・直す）を採用しない理由があること、`広がり:`が検索と結果を持つことを確かめ、対策が既にあった場合は`再発:`が前回と違う種類の対策を示すことも確かめる。
口語、ダッシュ、語調、表記統一などの表現は、意味・対象・条件・要求達成が同じならそのまま合格とする。
作業項目から最終成果物へ転記する時点では、その成果物の品質基準を適用する。
