# レビュー担当側心得：初回レビュー

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| 変更した状態の散在表現と遷移の分散を走査する前 | `../../writing-standards/references/implementation-time-data.md` |
| 変更した状態の不変条件と保証箇所を比較する前 | `../../writing-standards/references/design-time-state.md` |

## 初回レビュー

1. 元のユーザー目的、公開契約、適用する規範、前提とする入力、非目標、およびレビュー範囲を確定する
2. 成果物のコードや文章を読む前に、`../../writing-standards/references/quality-principles-qcd.md`「QCDと3段判定」にある「消費主体・利用場面から仕様と設計を導く原則」を用い、採用案やテストとは独立した期待結果をあらかじめ確定する。
   要求や公開契約から最も近い既存の実装を特定し、入力値、時間、操作順序、保持する状態、繰り返しの境界条件を選定する
3. 依頼内容や成立済みの承認事項、および`../../writing-standards/references/quality-principles-qcd.md`「QCDと3段判定」に基づいて許容される対象と操作を確定し、許容性→必要性→実装品質の順序で指摘を組み立てる
4. 詳細な適合性の確認に入る前に、採用案の前提を検証する視点から、その箇所が責務を担う必要性、既存の仕組みへの統合、上流のツールや共有設定への移管、削除や簡素化の可否を比較する。
   差分が計画外の新しい概念・構造を持ち込むなどの兆候があれば、`../../writing-standards/references/design-heuristics-necessity.md`「存在意義の点検」で対象自体の要否を比べる。
   提出物に記録された不採用案と理由も比較対象に含め、不採用理由が現物と要件に照らして成立するかを確かめる。
   独自に代替案を立てる比較も維持する。
   観測された不具合への対策は、問題が発生した入力や操作順序に当てはめて実害が解消するかを確認し、表面的な症状だけを変えるような案は退ける。
   呼び出し側の使い方が引き金になっている場合は、呼び出される側に新たな仕組みを追加する案と呼び出し側を修正する案を比較し、呼び出し側の修正で防止できるならそちらを優先する。
   ただし、呼び出し側に実行のたびの手作業（引数やパスの組み立て、確認用コマンドの連結、定型の後処理など）が残る場合は、呼び出される側のデフォルト動作、出力形式、公開契約を変更して手作業そのものを不要にする案も合わせて比較する。
   比較には`../../writing-standards/references/design-heuristics-decisions.md`「案の採否と実施順の判定」にある実行ごとのコストの考え方を用いる。
   新設または改訂する安全対策、検収用の記録・宣言・ハッシュ、例外処理やフォールバック、変更の成立に必要な既存機構については、`../../writing-standards/references/design-heuristics-mechanisms.md`「自作機構の兆候と自問」を適用する。
   必要性が認められない手段は種類6として採否の再選定へ差し戻し、ユーザーの要件と必要な原因分析は維持する。
   変更が進行を止める判定（遮断、終了コード1、保存の拒否など）を加える場合は、止められた主体がその場で解消できる条件か硬い制約かを`../../writing-standards/references/design-heuristics-mechanisms.md`「進行を止める判定の条件」で確かめる
5. 対象の成果物を、最も近い既存実装と責務、入力契約、状態遷移、失敗時の挙動の観点で比較し、要求や適用規範に対応付けられない差異を問題の候補とする
6. 独立した要求単位と変更面の各単位を、正常系、手順2で選定した境界条件、状態遷移や失敗からの復旧、外部入力や永続化の不変条件、および消費主体への影響の観点から走査する。
   方式全体の不変条件をすべての工程、状態分岐、想定される最大規模に対応付け、入力時点で判断できる論点を同じレビューラウンドにまとめる。
   公開処理と配信状態の保存が分かれている場合は、公開前、公開後かつ保存前、保存後の各停止タイミングにおけるデータの欠落、重複、処理済み判定を確認する。
   変更によって導入または変更された条件分岐については、判定を左右する入力条件の組み合わせも走査対象に加える
   - 変更で導入・変更した状態は、`../../writing-standards/references/implementation-time-data.md`「データと計算」の適用場面に照らして走査する
   - 同じ対象を表す複数フラグ、型上は表せる不正な組合せ、資源の有無、操作順序、複数モジュールからの書換えから、暗黙の状態と遷移の分散を確認する
   - 不変条件を成立させる主体と実際の保証箇所を、`../../writing-standards/references/design-time-state.md`「状態と業務ルールの条件」に従って対応付ける。
     通常操作・中断・再試行の操作列を比較して保証の成立を確かめ、前提の列挙と成立の証拠を区別する。
     独立した軸・外部の一次状態・結果整合・軽微変更の扱いを保つ
   - 取り消し: 変更をrevertや再配布で取り消したときに元の状態へ戻せるかを確かめる。
     永続データの形式変更・移行、外部への公開・送信、データの削除など、コードを戻しても状態が戻らない変更を含む場合は、戻す手順か、戻せない理由と事前の保護（バックアップ、段階的な移行など）が成果物か計画にあるかを確かめる
   - 障害検知: 変更した処理が本番で失敗したときに、終了コード、エラー出力、ログ、エラー監視への送信などで失敗を観測できるかを確かめる。
     例外を無視する処理や、デフォルト値・空の値を返して失敗を隠す処理がないかを確かめる
7. 候補として挙がった問題を根拠に基づいて検証し、通常運用で実害が生じる問題だけを指摘として確定する。
   文章成果物には`SKILL.md`「文章成果物の実害」の基準を適用し、作成規範とレビュー限定基準を同じラウンドで一括して点検する

未走査の領域、根拠のない`確認済み`、理由のない`非該当`が残っている間は走査を継続する。
初回の通常の走査で見つかったレビュー範囲外の実在する不良も、根拠と対象を添えて受領側へ報告する。
元のレビューの合否から分けることと、是正が不要であることを区別し、作業全体の処置へ引き渡す。
この報告のために全リポジトリを無制限に探索する工程は加えない。
説明文の追記が必要かどうかは、利用場面から期待される結果と`../../writing-standards/references/writing-common.md`「文章の共通規定」にある必要性判定を用い、完了条件への機械的な適合確認よりも先に判断する。
