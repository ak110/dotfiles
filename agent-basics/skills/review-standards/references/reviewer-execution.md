# レビュー担当側心得：実行レビューの判定

## 実行レビューの判定

実行レビューでは、計画、作業項目、CI失敗の調査記録などのレビュー基準に定められた要件や外部仕様の達成状況を対象とし、目的の達成、認可範囲、公開契約の遵守、および過剰設計の有無を、成果物とテストの両面から確認する。
ユーザーの意図が実際の利用場面で実現されているかを確かめ、判定欄のチェックや手順の字面を満たしただけの状態を完了とみなさない。
契約・回帰試験や計画の記載に適合していても全体の目的を損なう案と、観測した具体例だけを固定する再発防止策は種類1とする。
原因条件を除去している処置や、認可・データ保全の保護は、処置の種類や呼称だけを根拠とする不合格判定は対象外とする。
比較元の目的と通常の利用結果は、作成者が選んだ範囲や例を読む前に原要求と原観測から定める。
作業項目の完了条件に「説明の追記」が含まれていることだけを理由に必要性を認めず、`reviewer-initial.md`「初回レビュー」の必要性判定を満たさない追記は種類6とする。
エージェント向け文書で法令調の堅苦しい表現に戻っている箇所は、意味と拘束力を保ちつつ、同僚に説明するような自然な日本語へ修正するよう指摘する。
常時規範への追記については、`../../writing-standards/references/agent-documents-additions-additions.md`「規範追記時の判定」にある3条件を満たしているかを確認する。
規範を追記・新設・移動した差分は、`../../writing-standards/references/agent-documents-placement-selection.md`「置き場所の選定」の手順を差分と独立に適用し、選ばれる層と資料が実際の置き場所と一致するかを確かめる。
読む主体・読む契機・所属スキルの責務と合わない置き場所や、判断手順を本文に直書きした機械生成文は種類7とする。
規範の差分が硬い制約以外の判断材料や結論を固定してしまう場合は、守るべき価値に照らして本当に必要かを確かめる。
差分に記載された条件や限定が、条文が成り立つ本来の理由よりも狭すぎる場合は種類7として指摘する（基準は`agent-basics:writing-standards`の`references/review-only-criteria.md`「限定の反証」に従う）。
レビュー限定基準への違反も種類7とし、指摘文には同資料の「指摘と採否」に定められた事項を記載する。
元の要求単位が未達成である場合は、形式的な処理の完了とは区別し、未達成の内容と理由がユーザーへ確実に届くかを確認する。

要求内容とレビュー基準を、実装された差分と独立して突き合わせ、要求に対応する実装が差分になければ種類1とする。
理由を添えて明示的に不採用とされた範囲のみを除外する。
設計時点での鮮度判断と現行内容との食い違い、既存実装による充足、意図しない巻き戻しの兆候が見られる場合は、変更履歴を確認する。
計画と現在の合意事項との不一致は、後から確定した認可の範囲内の結論とその根拠に基づいて判定する。
元の要求を変更するような解釈がユーザー固有の判断に依存している間は、その結論の採用を保留する。
計画自体の体裁や進捗の記録は実装の品質判定とは切り離し、所有者へ更新が必要かを報告する。

実行レビューにおける指摘は、次の9種類に限定する。

1. 目的を達成していない
2. 認可された対象、範囲、または外部から見える結果から逸脱している
3. 公開契約に違反している
4. 生成元の変更に対して、生成や配布の手順が追随していない
5. 完了条件を満たしていない
6. 要求の達成に不要な機能、抽象化、互換手段、状態、または運用負担を追加している
7. 適用中の作成規範またはプロジェクト規範に違反しており、自動チェックでは検出できない
8. 既存の利用シナリオまたは直接影響範囲の契約を破っている
9. 変更によって成果物群の設計品質が変更前よりも劣化している（`../../writing-standards/references/design-heuristics-quality.md`「設計品質の劣化確認」の観点で判定する）

種類ごとの確認の要点:

- 受入シナリオ: 各行に対応するテストが実在し、提出結果で合格が確認でき、テスト本文に消費主体が使う呼び出し手段による操作と期待結果の確認が含まれているかを確かめる。
  不足している行は種類5とする。
  受入シナリオに対応していない新規テストや、公開された呼び出し手段から同一の違反を検出できる冗長な新規テストは種類6とする。
  テストの有効性と内部変更への耐性、観測手段・環境の十分性は、`agent-basics:writing-standards/references/testing.md`の冒頭、「検証単位の選定」「期待値の出所」「分岐条件の効果の裏付け」で評価する。
  入力の生産・変換から最終消費まで実行した範囲と、fixtureを対象版の標本へ対応付けた根拠を読み、差し替えた境界までの成功と全体の保証を区別する。
  OS分岐と保存済み成功の適用では、同資料「プラットフォーム分岐の検証」に従い、モジュールの判定値、実ホストOS、外部実行体・OS APIをfixtureと実入力から比較する。
  共有モジュールの変更範囲、実行したOS固有の変換・副作用、開発環境と配布環境の初期状態を対応付ける。
  試験名やWindowsパラメーター、型・全体試験の成功、レビュー回数だけでOS境界を受理せず、未確認の境界を残す
- 直接影響範囲: 変更された識別子と契約の直接影響範囲、変更ファイルを経由する既存のシナリオとテスト、変更された値や動作を別の場所で生成している箇所（同じ値や動作を独立して生成する定義や処理）を列挙する。
  この列挙は提出された探索記録に頼らず、変更された契約、読み取り側の主体（`agent-basics:check-execution`の`references/verification-scope.md`の類型）、通常操作の状態遷移から独自に洗い出して提出記録と比較する。
  独自に特定した利用側のテストについては、提出された実行結果の合否と1件ずつ突き合わせる。
  提出された探索記録にある候補についても、採否と実行対象への反映、個別の合否を保存結果で確かめる。
  探索で見つからなかった利用側と、見つかっていたが実行結果の無い利用側を区別して指摘する。
  入力パスからテストを選択するツールの成功やテストの総数だけを使う判定は、網羅性の根拠から除く。
  探索記録が無い場合、結論を保留している場合、変更した契約の一部だけを検索語にしている場合も、記録の状態を合否の根拠にせず、独自の列挙で判定する。
  列挙がそろって見える記録も、独自の列挙との差で判定する。
  合格結果が提出されていないもの、契約を破っているもの、追随していない生成箇所は種類8とする
- 追加要素: 人間の要求単位ごとに、受入シナリオどおりに使用して原文の効果が得られるかを確かめる。
  新しく追加された条件分岐、状態、フォールバック、確認処理、互換処理、抽象化については、要求単位または`../../writing-standards/references/quality-principles-qcd.md`「QCDと3段判定」の根拠（規範の制約、観測された欠陥など）に対応付ける。
  対応先が見当たらないものは種類6とする。
  原因特定のための診断コードについては、各採取処理をCI失敗の調査記録にある原因分析と公開契約の仮説検証に対応付け、対応先のない処理や対象を絞り込んでいない全件走査は種類6とする
- 新しい公開インターフェース: エンドユーザー向けの設定キー、CLIオプション、環境変数、サブコマンドの新設は、新設する理由と、既存のインターフェースやデフォルト値の変更では不十分である理由の両方が示されていない限り種類6とする
- 名指しの観測手段: ユーザーの要求や公開契約で観測手段（特定コマンドの出力、画面表示、hook通知など）が名指しされている行は、その手段による観測結果だけを合格の証拠とする。
  実装がその観測結果を生成しないことが確認された場合は、別の観測結果、代替スクリプト、モック、部分的なプローブ、古い呼び出し手段による成功があったとしても種類5とする。
  計画担当が選んだ手段だけの変更は、必要成果・品質・認可・制約を保つ代替観測と選定理由を検証記録から確かめる。
  実装側の都合ではなく実行環境の不在などによって観測結果が得られない場合は、根拠不足として扱う。
  公開された呼び出し手段を置き換えたり廃止したりする場合は、新しい手段によって利用シナリオの結果まで到達した記録とテストが存在しなければ種類5とする
- 種類7: 規範同士で同じ条件に対して両立しない動作を割り当てていないか、委譲元と委譲先の役割文書で同じ責務を重複させていないかを確認する。
  必要なエージェントが実行時に参照できる配置になっているか、計画や受領したレビュー契約が示す適用規範と成果物が合致しているかも確認する。
  親エージェントが適用規範を一意に特定できないと記録している場合は、成果物の種類、発動条件、判断主体、読み込み元から該当する条項を特定する。
  規範への適合は成果物との一致によって判定する
- 種類9: 計画にリファクタリングの検討結果があっても、その結論にとらわれず、差分と変更後のファイル全体を独自に読み取って判定する。
  内部構造、命名、モジュール分割、抽象化、実装方式に関する個人の好みは、前述の9種類に該当する場合に限り指摘し、明確に劣化と判断できない好みの違いは指摘しない
- 検証記録: 結果の判定には、提出された検証記録を活用する（努力目標。検証の重複を避けるため）。
  プロジェクトの計画の検証欄にある変更範囲の検証コマンド（計画がない場合は引き継ぎで受け取った検証コマンド。プロジェクトが計画の形式を定める場合はその検証欄）について、理由の記録がないまま省略、別コマンドへの置き換え、一部のみの実行、対象範囲の縮小が行われていた場合は種類5とする。
  省略・置き換え・一部実行を指摘から外すのは、理由が明記され、置き換え先のツール集合と対象ファイルが元のコマンドの分を含むことを、保存出力のツール別結果または実効設定で確かめられる場合に限る。
  理由と実行範囲が一致しない場合や、その根拠が提出されていない場合は種類5とする。
  記録がなく差分からも未達成であることが明らかな場合は種類5とし、差分は満たしているが記録だけが欠落している場合は、実装の欠陥と区別して不足分を完了報告に記載する。
  直接影響範囲の利用側テストに合格結果が無い場合は、差分を満たしていると判断できないため、この扱いにせず「直接影響範囲」の要点の種類8とする。
  外部から見える文言や挙動が変更される場合は、直接影響範囲の探索結果（検索対象、検索語、範囲、採否）を確認し、変更前の期待値を保持すべき範囲が実在するにもかかわらず実装範囲に含まれていなければ種類5とする

## 要求単位と観測の判定

依頼のプロジェクト内での役割と今回の結果を、`../../writing-standards/references/quality-principles-qcd.md`「QCDと3段判定」に照らして評価する。
変更箇所や工程の実施状況に加え、目的に対応する結果と残工程を確かめる。
完了条件については、今回の変更によって成立したものと既存実装によってすでに成立していたものの両方を含め、それぞれの条件を直接の観測結果に対応付ける。
元の指示における要求単位も個別に確認し、未達成のものは種類1か種類5とする。
依頼の範囲外として除外する要求については、別の担当者が引き受けた記録が存在することを確認する。
過去の経緯を説明しているだけの背景記述は、原文の文脈を独自に読み取り、要求、制約、採否、選好、問いかけが含まれていない場合に限って背景として扱う。
判定が一意に定まらない要求単位は、要求事項として確認する。
公開、配布、あるいは実環境への反映が必要な条件は、その条件が名指しする観測結果が得られるまでは根拠不足として扱う。
後続工程の予定や、別条件での部分的な再現だけを使う判定は、達成の証明から除く。
公開前に同等の環境を再現できる起動条件は`agent-basics:check-execution`の`references/acceptance-scenarios.md`で確認し、不足している条件と観測のやり直しを明記する。
項目全体が任意の参考情報であると明示されている条件は、観測結果がなければ根拠不足である旨を明記し、観測結果が存在するにもかかわらず条件を満たしていなければ未達成とする。
条件の一部だけが任意である場合は、残りの必須条件について合否を判定する。
独立したユーザビリティレビューが同じ版に対して並行して進行している場合は、結果の到着待ちを欠陥として登録せず、統合の段階で該当版の結果、または描画手段がないことを示す未確定の記録を確認する。
