# 実行レビューの判定基準

実装後の変更差分を独立した文脈で確かめる実行レビューで、要求単位と完成条件の達成・提出された証拠・直接影響範囲・設計と認可を判定する基準を定める。
原則6（`agent-basics:writing-standards/references/quality-principles-verification.md`）を独立した確認へ適用する。
原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）を判定の根拠へ適用する。
本書の節を上から順に判定する。
指摘・推奨を出すかの判断、書き方、レベル、根拠は`agent-basics:review-standards/references/reviewer.md`「指摘内容」「判定根拠の品質」に従う。

## 実行レビューの判定

### 原要求と利用結果

- 計画・作業項目・CI失敗の調査記録などにある要件と外部仕様について、目的の達成・認可の範囲・公開契約・過剰設計を、成果物とテストの両方で確かめる。
- 要求ごとに対応する実装を差分と独立に探し、無ければ種類1とし、理由を添えて明示的に不採用とした範囲だけを除く。
- 契約・回帰テスト・計画に合っていても全体の目的を損なう案と、観測した具体例だけを固定する再発防止策は種類1とする。
  原因の条件を除く処置と、認可・データ保全の保護は、処置の種類や呼び名でなく原因の条件への作用で判定する。
- 設計時の鮮度の判断と現行の食い違い・既存の実装による充足・意図しない巻き戻しの兆候がある時は、変更の履歴を確かめる。
- 計画と現在の合意の不一致は後から確定した認可の範囲の結論で判定し、要求を変える解釈がユーザー固有の判断に依る間は採用を保留する。
- 判定欄や手順の充足は中間の状態とし、完了は実際の利用結果と残る工程で判定する。
  完了条件は、今回の変更で成り立ったものと既存の実装で成り立っていたものの両方を直接の観測へ対応付ける。
- 元の指示の要求単位も個別に確かめて未達は種類1か種類5とし、範囲外として除く要求は別の担当者が引き受けた記録を確かめる。
  経緯だけを述べる記述は、要求・制約・採否・選好・問いを含まない時に限って背景とし、一意に定まらない単位は要求として確かめる。
  疑問符、過去形、注記だけを根拠に背景としない。
- ユーザーの入力が一般の方針を含む時は、その場の要求の達成と、将来の判断主体が読む成果物への保存を分けて確かめる。

### 提出された実動作の証拠

実行で確かめられる論点は保存済みの結果を先に読み、不足は許可された入力と操作で再現し、意図・認可・設計・セキュリティは契約と構造の根拠で判定する。

- 受入シナリオ: 各行の必要な結果と、提出されたテスト・手動の観測・読解の確認箇所・条件・合否の対応を確かめ、不足する行は種類5とする。
  受入シナリオに対応しない新しいテストと、公開された呼び出し手段で同じ違反を検出できる冗長な新しいテストは種類6とする。
  診断の採取は設定の存在と終了後の取得を分け、後始末とCIの回収の後にもテスト名・失敗内容・traceが対応するかを確かめる。
- 名指しの観測手段: 要求や公開契約が名指しした観測手段（コマンドの出力、画面表示、hookの通知など）の観測だけを合格の証拠とする。
  実装がその観測を生成しない時は、別の観測・モック・部分的なプローブ・古い呼び出し手段の成功があっても種類5とし、実行環境の不在で得られない時は根拠不足とする。
  計画担当が選んだだけの手段の変更は、必要な成果・品質・認可・制約を保つ代替の観測と選んだ理由を検証記録で確かめる。
  公開された呼び出し手段の置換・廃止は、新しい手段で利用シナリオの結果まで届いた記録とテストが無ければ種類5とする。
- 検証記録: 計画の検証欄（計画が無ければ引き継いだ検証コマンド）の検証が理由の記録なく省略・置換・一部の実行・範囲の縮小をされていれば種類5とする。
  外すのは、置換先のツールの集合と対象が元の分を含むことを、保存出力のツール別の結果か実効の設定で確かめられる時に限る。
  差分は満たして記録だけが欠ける時は、実装の欠陥と分けて不足を完了報告に書く。
  直接影響範囲の利用側のテストに合格の結果が無い時は、この扱いにせず本書「変更の直接影響」の種類8とする。
  外部から観測できる文言や挙動の変更は直接影響範囲の探索結果（検索対象、検索語、範囲、採否）を確かめ、変更前の期待値を持つ範囲の欠落を種類5とする。
- 通知の本文: エージェント宛ての通知の変更は、入力・対象版・ホスト・生成元に対応する最終の配送本文を保存記録から開いて読む。
  基準は`agent-basics:writing-standards/references/claude-hooks-block-warn.md`「通知本文の整形」とし、コードのリテラル・テスト名・合格の総数・途中の段階の本文は根拠から除く。

公開・配布・実環境への反映が要る条件は名指しの観測が得られるまで根拠不足とし、後続の工程の予定や別の条件での部分的な再現を証明から除く。
公開前に同等の環境を再現する起動条件は`agent-basics:check-execution/references/acceptance-scenarios.md`「常駐サービスの公開前の観測」で確かめる。
全体が任意の参考と明示された条件は、観測が無ければ根拠不足、観測があって満たさなければ未達とし、一部だけが任意なら残りの必須の条件で判定する。

### コードとOS境界の受入試験

コードの実行・OS分岐・テストの層を検収する時に使い、文書の変更が公開契約や実行経路を変える時も影響に応じて含める。

- テストの有効性・内部変更への耐性・観測の手段と環境は、`agent-basics:writing-standards/references/testing.md`の「試験を書く前の確認」「検証単位の選定」「期待値の出所」「分岐条件の効果の裏付け」で評価する。
- 入力の生成から最終の利用まで実行した範囲と、fixtureを対象版の標本へ対応付けた根拠を読み、差し替えた境界までの成功と全体の保証を分ける。
- 競合の順序を確かめるテストは、途中の前提の状態を通った証拠も確かめる（`agent-basics:writing-standards/references/testing.md`「安定性: flakyテスト防止」）。
- OS分岐と保存済みの成功は`agent-basics:writing-standards/references/testing.md`「プラットフォーム分岐の検証」で判定し、共有モジュールの変更範囲と開発環境・配布環境の初期状態を対応付ける。
  テスト名・Windowsのパラメーター・型や全体のテストの成功・レビューの回数だけでOSの境界を受理せず、未確認の境界を残す。

### 変更の直接影響

原要求から対象の集合・軸・必要な組合せを導いて提出された一覧の欠落を確かめ、各対象を適合・不適合・未確認・非該当として根拠へ対応付ける。

- 変更した識別子と契約の直接影響範囲、変更したファイルを経由する既存のシナリオとテスト、変更した値や動作を独立に生成する箇所を列挙する。
  列挙は提出された探索記録に頼らず、変更した契約・読む側の主体（`agent-basics:check-execution/references/verification-scope.md`「直接影響範囲の類型」）・通常の操作の状態遷移から導く。
- 自分で特定した利用側のテストは、提出された実行結果の合否と1件ずつ比べ、提出記録の候補も採否・実行対象への反映・個別の合否を保存結果で確かめる。
  探索で見つからなかった利用側と、見つかったのに実行結果が無い利用側を分けて指摘する。
- 入力のパスからテストを選ぶツールの成功やテストの総数は網羅性の根拠にせず、探索記録の有無や体裁によらず自分の列挙との差で判定する。
- 差分が`agent-basics:formal-verification`「当てるかの判定」の対象に触れるのに、計画か処理記録に`形式検証の判定:`の行が無いものは、提出された結果の不足として扱う。
  対象コードを検証する既存のスキル（frontmatterの`verifies`か本文の名指しで探す）の再実行の記録が無いものも同じに扱う。
- 合格の結果が提出されていないもの、契約を破るもの、追随していない生成箇所は種類8とする。

### 設計・認可・規範

- 追加要素: 人間の要求単位ごとに、受入シナリオどおりに使って原文の効果が得られるかを確かめる。
  新しい条件分岐・状態・フォールバック・確認処理・互換処理・抽象化は、要求単位か`agent-basics:writing-standards/references/design-heuristics.md`「設計の判定順」の根拠へ対応付け、無ければ種類6とする。
  診断コードの各採取は、CI失敗の調査記録の原因分析と仮説の検証へ対応付け、対応先の無い採取と対象を絞らない全件の走査は種類6とする。
- 新しい公開インターフェース: エンドユーザー向けの設定キー・CLIオプション・環境変数・サブコマンドの新設は、新設の理由と、既存のインターフェースやデフォルト値の変更で足りない理由が無ければ種類6とする。
- 説明の追記: 完了条件にあることだけで必要性を認めず、`agent-basics:writing-standards/references/writing.md`「文章の共通規定」の必要性を満たさない追記は種類6とする。
- 規範の差分: 常時規範への追記は`agent-basics:writing-standards/references/agent-documents-additions.md`「規範追記時の判定」で確かめる。
  追記・新設・移動した規範は、`agent-basics:writing-standards/references/agent-documents-basics.md`「置き場所の選定」で差分と独立に選んだ置き場所と比べる。
  読む主体・契機・スキルの責務と合わない置き場所と、判断の手順を直書きした機械生成文は種類7とする。
  硬い制約以外の判断材料や結論を固定する差分は、守る価値に照らして必要かを確かめる。
  狭すぎる限定（`agent-basics:writing-standards/references/review-only-criteria.md`「限定の反証」）とレビュー限定基準への違反は種類7とし、指摘には同資料「指摘と採否」の事項を書く。
- 種類7: 規範どうしの両立しない動作の割当と、委譲元と委譲先の役割文書の責務の重複を確かめる。
  必要なエージェントが実行時に参照できる配置か、計画や受領したレビュー契約が示す適用規範と成果物が合うかも確かめる。
  委譲元が適用規範を特定できないと記録した時は、成果物の種類・発動条件・判断主体・読み込み元から条項を特定する。
- 種類9: 計画のリファクタリングの検討の結論に依らず、差分と変更後のファイル全体を読んで判定し、好みの違いは明確な劣化に当たる時だけ指摘する。

### 未達・未確認の返却

- 元の要求単位の未達は形式的な処理の完了と分け、未達の内容と理由がユーザーへ届くかを確かめる。
- 計画の体裁や進捗の記録は実装の品質の判定と分け、更新の要否を所有者へ報告する。
- 同じ版の独立したユーザビリティレビューの結果待ちは欠陥にせず、統合の段階で該当版の結果か描画手段が無いことを示す記録を確かめる。

### 指摘の分類

実行レビューにおける指摘は、次の9種類に限定する。

1. 目的を達成していない
2. 認可された対象、範囲、または外部から観測できる結果から逸脱している
3. 公開契約に違反している
4. 生成元の変更に対して、生成や配布の手順が追随していない
5. 完了条件を満たしていない
6. 要求の達成に不要な機能、抽象化、互換手段、状態、または運用負担を追加している
7. 適用中の作成規範またはプロジェクト規範に違反しており、自動チェックでは検出できない
8. 既存の利用シナリオまたは直接影響範囲の契約を破っている
9. 変更によって成果物群の設計品質が変更前よりも劣化している（`agent-basics:writing-standards/references/design-heuristics.md`「設計品質の劣化確認」の観点で判定する）
