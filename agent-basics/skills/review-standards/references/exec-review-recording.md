# 判定根拠の品質

要求ごとに、原文とその出所、判定結果、判定に直接必要な観測内容と適用理由、確認した版を対応付ける。
原文の内容を保持し、古くなった説明や別要求の経緯は現在の状況に合った根拠へ置き換える。
複数の要求で同じ記録を使い回す場合でも、該当する観測結果を要求ごとに個別に確かめる。
過去の観測結果を再利用するときは、取得した時点の版と条件を確認し、対象、依存関係、入力、実行環境のうち結果に影響する条件が同一であるかを確かめる。
Gitの祖先関係や差分の見た目だけで同一とみなすことは避け、同一性を確認できない範囲は根拠不足として扱う。
履歴そのものを検証対象とするテストは、改めて実行して取り直す。
過去に受理された判定であっても、今回の変更において結果に影響する内容や条件が同一である行だけを参照する。
必要な根拠を後から再度たどれるように参照先と適用理由を記録し、再確認できない場合は今回の実行による観測へ立ち返る。
記録した根拠が原文の要求単位を過不足なく網羅しているかを、読み手が確認する。
着手時に対象と適用観点の組合せを既存の条件表や進捗記録へ準備し、各項目を順に確認済み・不適合・非該当・未確認へ判定する。
確認済みには観測や読解の根拠、非該当には理由を対応付け、空欄や一括の確認済み宣言は根拠不足として扱う。
完了・引き継ぎ時は全項目に結果が対応するか確かめ、項目の消化とは別に原要求から対象集合を導いて一覧の漏れやリスト外の反例も探す。
途中の要求追加・新事実・修正、再開・会話圧縮後は現行集合へ更新し、条件不変の確認結果を再利用する。
組合せの整理と全組合せのテスト実行は区別し、単純な変更には短い箇条書きや既存の差分・記録を用い、少数の対象も確認を終えてから完了とする。
ログの最低行数や成功件数の多さだけで条件を満たしたとみなすことは避ける。
指摘が成立するかどうかの判定基準は`reviewer.md`に従い、指摘の採否と修正方針は`reviewee.md`に従う。

報告・レビューへの引き渡し前に、主張、確認済みの根拠と対象版、未確認範囲、判断した時点を既存の検証記録・進捗ログ・引き継ぎ記録などへ保存する。
指摘を受けた担当はこの事前記録と新しい反例・要求を比較し、応答の採否と必要な再調査の範囲を決める。
専用の台帳や確信度の数値閾値の追加は対象外とする。
事前記録が無い場合は未記録と示し、指摘後の調査で得た根拠は、指摘後に得たものとして区別する。
版や条件が変わった部分は現在の観測で補い、確認済みの範囲との区別を保つ。
