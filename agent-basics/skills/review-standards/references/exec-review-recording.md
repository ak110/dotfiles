# 判定根拠の品質

要求ごとに、原文とその出所、判定結果、判定に直接必要な観測内容と適用理由、確認した版を対応付ける。原文の内容を保持し、古くなった説明や別要求の経緯は現在の状況に合った根拠へ置き換える。複数の要求で同じ記録を使い回す場合でも、該当する観測結果を要求ごとに個別に確かめる。
過去の観測結果を再利用するときは、取得した時点の版と条件を確認し、対象、依存関係、入力、実行環境のうち結果に影響する条件が同一であるかを確かめる。Gitの祖先関係や差分の見た目だけで同一とみなすことは避け、同一性を確認できない範囲は根拠不足として扱う。履歴そのものを検証対象とするテストは、改めて実行して取り直す。
過去に受理された判定であっても、今回の変更において結果に影響する内容や条件が同一である行だけを参照する。必要な根拠を後から再度たどれるように参照先と適用理由を記録し、再確認できない場合は今回の実行による観測へ立ち返る。
記録した根拠が原文の要求単位を過不足なく網羅しているかを、読み手が確認する。ログの最低行数や成功件数の多さだけで条件を満たしたとみなすことは避ける。指摘が成立するかどうかの判定基準は`reviewer.md`に従い、指摘の採否と修正方針は`reviewee.md`に従う。

報告・レビューへの引き渡し前に、主張、確認済みの根拠と対象版、未確認範囲、判断した時点を既存の検証記録・進捗ログ・引き継ぎ記録などへ保存する。指摘を受けた担当はこの事前記録と新しい反例・要求を比較し、応答の採否と必要な再調査の範囲を決める。専用の台帳や確信度の数値閾値は設けない。
事前記録が無い場合は未記録と示し、指摘後の調査で得た根拠を指摘前に確認済みとしない。版や条件が変わった部分は現在の観測で補い、確認済みの範囲と混ぜない。
