# レビュー担当側心得

本書は、レビューを実施するエージェントが従うべき確認の契約、指摘の確定基準、および完了報告の形式を定める。

## 名指し参照の読込方法

名指し参照は`agent-basics:writing-standards/references/read-method.md`に従う。

| 時点または条件 | 全文読む資料 |
| --- | --- |
| OS分岐の試験や保存済み成功を適用判定する前 | `../../writing-standards/references/testing-selection.md`、`../../writing-standards/references/testing-platforms.md` |

## 適用契約

- コード・ドキュメントのレビュー: 「基本方針」「指摘内容」に加え、再レビューの指定があれば「再レビューの場合」、指定がなければ「初回レビュー」
- 提案、自身の判断、サブエージェント出力の妥当性評価: 「基本方針」および`judgment-details.md`の該当節
- 画面のユーザビリティレビュー: 「基本方針」「指摘内容」「ユーザビリティレビューの判定」

レビュー結果には「指摘内容」で定める根拠と未確認の範囲を含め、評価を依頼した工程が指定する形式で返す。

## 基本方針

- 文章の冒頭の1文が、読者の最初の疑問に答えているかを確認する。
  題名や主語の適切さは、`agent-basics:writing-standards`の`references/writing.md`にある共通基準に沿って判定する
- 文章成果物の日本語表現は、`../../writing-standards/references/writing.md`「日本語の書き方」を執筆時と共通の基準とする。
  読者像と利用場面ごとに、想定読者や各役割に適しているかを確かめる。
  作業項目の起草・投入前検収では、`../SKILL.md`「文章成果物の実害」の意味と引き継ぎ可能性に関する適用範囲を用いる
- 成果物には何らかの課題があるという前提に立ち、目的、主張、前提、結論を反証する視点から確認を始める。
  表現の推敲や局所的な点検は、目的そのものが成立していることを確かめた後に進める
- 元のユーザー目的、公開契約、適用する規範、入力を生成する主体、信頼境界、通常の入力、および非目標（スコープ外事項）を確認し、指定されたレビュー範囲を独立した要求単位と変更面に分解する。
  実行可能な検証手段を持つ独立要求と直接影響範囲を同じレビューラウンドで網羅し、通常運用において実害が出る契約違反だけを指摘する。
  文章成果物の実害や作成規範違反の採否は、本スキルの`SKILL.md`「文章成果物の実害」に従って判断する
- ファイルの読み取り時に出力の切り詰めが通知された場合は、分割取得によって全量を読み取ってから判定する。
  取得できなかった範囲は証拠不足として指摘に記録し、未走査の領域として扱う
- lint、format、textlint、型チェック、スペルチェック、補助スクリプト、構文チェック、および機械的に算出できる数値によって検出できる事項は、レビューの指摘に含めず自動チェックツールに委ねる
- 同じ規定に違反している箇所はすべて確認し、1件の指摘としてまとめる。
  探索範囲（母集団）は`agent-basics:bugfix`の`references/root-cause-remediation.md`「類似見直し」に沿って決定する。
  提出された類似見直しについては、同資料の基準に基づき、母集団の導出根拠と各対象の選定・除外理由を規定や現物と照らして独自に確認し、修正処置が母集団全体をカバーしているかを検証する。
  提出された母集団の範囲を無条件で全体とみなさない
- 指摘に必要な根拠を取得できない場合は、証拠不足の範囲、取得できなかった根拠、および必要な検証内容をそのレビューの指摘として記録し、該当範囲を未検証として扱う
- 実機検証、完了条件、待機手順によって合否を判定する指摘は、指摘を確定する前に、対象成果物に許可されたツール、禁止事項、前提とする入力、通常の状態遷移の範囲内だけでその検証が成立するかを、`judgment-details-feasibility.md`「検収手段の到達可能性」に沿って判定する。
  到達不能と判明した要求は、計画や規範の再設計が必要な問題として依頼元へ判断を仰ぎ、到達を阻んでいる条文、不足している入力や実行権限、試行した検証方法と成立しなかった観測事実を記録する。
  契約が成立している証拠として認められるのは、契約内で許容された入力、権限、操作を通じて得られた観測結果に限る

### 指摘範囲を消費主体別に区切る基準

指摘を確定する前に、対象成果物を利用する主体（消費主体）を特定し、その主体に合わせて指摘の範囲を調整する。
読者が異なる文書では、読者像と利用場面を区別し、読者ごとに結果をまとめる。
読者適合性の品質基準は、確認する担当の分け方によらず適用する。
別担当の要否はプロジェクトのレビュー契約が定める場合はそれに従い、直接確認でも対象・読者・判定・根拠を対応付ける。
消費主体の本来の目的と利用条件に基づいて、必要とされるセキュリティ対策や競合対策の範囲を決める。

消費主体がユーザー自身とエージェントに限定されるコマンドラインツール（個人用のCLIやその補助スクリプトなど）では、実際に実行して観測された不具合、公開インターフェース（コマンド名、オプション、入出力形式、終了コード）の破壊、データの損失への対処を優先する。
複数の条件が同時に揃わなければ起きない競合や、それを防ぐためのロック、lease、状態管理といった機構の新設は、実際にいずれかの条件が観測された場合に対処する。
観測を確定できない場合は未観測として扱う。
消費主体にユーザー以外の第三者や外部サービスが含まれる成果物には、本節の基準を適用しない。

## 指摘内容

各指摘には、違反している目的や契約の原文、対象へ適用される条件、通常運用で発生する実害とその裏付け、その事象が全体の結論を覆すものか・修正が必要なものか・条件付きで成立するものかの判定結果、および到達可能な検収手段を明記する。
これらを確定できない指摘候補は、「基本方針」に沿って証拠不足として扱う。
指摘文では満たすべき契約と解消に向けた方向性を示し、具体的な実装方法はレビューイー側で確定する。
現行の方式では契約を満たせないと確認された場合は、方式の撤去または置換が必要であることを明確に伝える。
許容性や必要性が認められない変更に対しては、縮小、撤去、再選定を改善の方向として提示し、仕組みの追加や堅牢化はそれらの手段が成立しない場合の選択肢とする。

指摘を記録する際は、各指摘に`指摘レベル`を付与する。
起草者が問題の性質を最もよく把握しており、レビューイーが着手後に想定以上の範囲であることに気づくような手戻りを防ぐため、レベルの判定はレビュー担当が行う。

- `要件`: 要求の解釈、採否の範囲、採用案そのものの成否（許容性と必要性に関わるもの）
- `仕様`: 外部から見える振る舞い、公開契約、外部公開要件（必要性に関わるもの）
- `詳細`: 確定済みの設計範囲内における構成、記述の不足、整合性の修正（実装品質に関わるもの）
- `実装`: コードの具体的な書き方、テストの不足、自動チェックへの追随（実装品質に関わるもの）
