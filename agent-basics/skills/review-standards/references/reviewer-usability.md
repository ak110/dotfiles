# ユーザビリティレビューの手順

変更された画面を実際に描画・操作し、エンドユーザーが画面の意味を迷わず理解して作業を完了できるかを評価する手順を定める。
対象は、E2Eテスト、VRT（ビジュアルリグレッションテスト）、lintなどの自動テストでは判定できない、エンドユーザーから見た使いやすさである。
原則6（`agent-basics:writing-standards/references/quality-principles-verification.md`）を画面のレビューへ適用する。

## ユーザビリティレビューの判定

画像はファイル名でなく表示された状態を検収する。

1. 実装者の画面説明・成功手順を読む前に、原要求と通常利用から代表作業、開始データ、入力手段、主となる表示環境を決める。
   刷新では入口から到達する表示・共通部を自分でたどり、作業と対応付ける。
2. `agent-basics:writing-standards/references/ui-ux-topics.md`「完了前の実描画確認」に従い、Webはブラウザー、ネイティブGUIは対象OSで変更後の画面を描画・操作する。
   Web画面では`agent-basics:writing-standards/references/ui-ux-web-rules.md`と該当するModern Web Guidanceを使う。
   文言は文章の基準で判定する。
   この実機の観測で、`references/reviewer.md`「初回レビュー」の最初の合否を決める。
   対象の一部だけが使いやすい、見た目だけが揃うなど、原要求に足りない場合はここで不合格とする。
3. `agent-basics:writing-standards/references/ui-ux.md`「判断の順序」「用途と参考例の調査」「操作と情報」「状態と内容」「視覚と構造」に照らして判定する。
   `agent-basics:writing-standards/references/ui-ux-topics.md`「アクセシビリティと性能」も使う。
   実画面で最小の文字の計算値、主要な文字と背景のコントラスト比、キーボードだけでの代表作業の完遂、操作対象の大きさを観測する。
   同書「ユーザーの作業から画面を分ける」「判断と観測に使う一次資料」の判定を使い、入口の発見から結果確認まで、観点ごとに観測した手掛かりと合否の理由を記録する。
   画面の分け方がユーザーの目的で説明できず、不要な往復や文脈の喪失がある場合は、共通部品が揃っていても不合格とする。
   入力の記載とは独立に、同じ機能・資源・目的の画面や部品を探す。
   比較条件・項目と障害注入の要否は手順2の「完了前の実描画確認」に従う。
   主ラベルと配置だけで意味が通るか、補足がある場合は何を新たに伝えるかを判定する。
   対象内で見出し・操作・状態を言い直す補足と、通常の待機を説明する可視の文は、操作を完了できても不合格とする。
   同じ操作で、処理前・待機中・完了後・失敗時に何が分かり、何ができるかを確かめる。
   待機の表示が届かない場合は操作箇所の進捗や必要な非活性化を求め、説明文を合格条件にしない。
   操作・入力の識別、対象範囲・不可逆性・入力形式・回復など判断に必要で配置から分からない情報や、色以外の手掛かり、必要なアクセシブル名・状態通知は言い直しと区別する。
   無関係な画面まで差し戻しの対象にしない。
   比較相手があるのに入力が「なし」の場合と、理由のない相違は不合格とする。
   共通部品や数値への適合と、画面全体の読みやすさを別に判定する。
   設計意図を読む前に画像から先に目に入る場所と読む順を記録し、後で主目的と突き合わせる。
   補助が主役より目立つか面積を奪う、本文・操作・結果へ視線を運べない、判断を左右する変更後の状態が未観測なら、部品が揃っていても該当場面を合格にしない。
   一般的な水準を求められた場合は用途の近い外部類例とも比べ、対比・まとまり・文字・行間・密度の合否を記録する。
   他製品の手数は合格基準にしない。
   初期表示から完了まで、判断の順に情報がたどれ、長さの違う行でも比較する列が揃うか、空値や反復が主役を隠さず、不要な入力や画面往復が残っているかを判定する。
   事前知識のないエンドユーザーとして、変更画面だけから操作を見つけ、候補と既定値を理解し、必要な確認を経て保存後の結果を確かめられるかを見る。
   反復操作でも、選択肢やヘルプを前画面の記憶に頼らず見つけられるかを確かめる。
4. 機能の正しさ（受入シナリオの期待結果との一致、データの反映、操作の成否）は判定の対象から外し、自動テストと実行レビューへ任せる。
   同じ確認を重ねると、使いやすさを評価する目的が損なわれるためである。
   提出されたテストの開始状態・操作・結果が観測の対象と一致するかは確かめて不足を明示し、テストが足りない受入シナリオは実行レビューの種類5とする。
   機能上の停止に当たった時は、開始状態・操作・停止箇所・未検証の部分・証拠を機能の担当へ渡し、到達していない操作の流れは未検証として扱う。
5. 各指摘には、観測した画面の状態と保存したキャプチャーの参照、エンドユーザーが誤解するか操作を中断する具体的な場面、`agent-basics:writing-standards/references/ui-ux.md`の該当する基準を示す。
   指摘の該当箇所は、外観、要素名、DOM構造の表面的な類似だけで限定せず、同じ発生機構を持つ変更画面、表示幅、操作後の状態の全体から探す。
