# verifyスキルの生成と保守

アプリを起動し、使う人と同じ操作で機能を動かし、証拠を残して後始末する手順を、プロジェクトのスキルとして生成・保守する。
生成したスキルは、変更の挙動をテストの成功や型の確認でなく実際の操作で確かめる時に、アプリを知らない次の担当者が読んで使う。
使うかどうかはプロジェクトが選ぶ。
隔離は原則4（`agent-basics:writing-standards/references/quality-principles-constraints.md`）の適用である。
証拠は原則3（`agent-basics:writing-standards/references/quality-principles-facts.md`）の適用である。
後始末は原則7（`agent-basics:writing-standards/references/quality-principles-ownership.md`）の適用である。

## 生成の手順

1. リポジトリを調べ、自分では確認できないことだけをユーザーに尋ねる。
   - 入口（使う人が触る画面、CLI、API、ライブラリなど）: 全て挙げて主な1つを選び、残りは生成するスキルに記す。
   - 起動: プロジェクトの正規の起動手順（タスクランナー、READMEなど）と、必要な設定、データ、ポート。
   - 操作: 既存のテストの枠組みと操作の補助を先に探す。
     無ければ入口の種類で手段を選ぶ（CLIは実プロセス、HTTPはリクエスト、Web画面は既存のブラウザー操作の手段、ネイティブGUIは対象OSでの描画、OSに固有の動作は対象OSの実行環境）。
     画面の手順では、同じ操作の画像・要素構造・キーボード操作を証拠として対応付ける。
     WebはPlaywrightのrole照会か部分的なARIA snapshot、WindowsネイティブはInspectなどのUI Automationを使う。
     詳細は`agent-basics:writing-standards/references/ui-ux-topics.md`「完了前の実描画確認」に従う。
     別のテストの枠組みは、既存の手段で操作できない時だけ足す。
   - 観測: 取れる証拠（出力、終了コード、応答、画面、ログ、保存された状態）。
   - 隔離: データ、設定、ホーム、ポート、依存環境の置き場所を、コードと既存のテストの隔離から確かめる。
2. 空のデータから起動できることを確かめ、隔離は`agent-basics:writing-standards/references/investigation.md`「エージェントCLIを検証で起動する時の隔離」に従う。
   起動できなければ出力を保持し、`agent-basics:bugfix` で原因を確かめ、認可内の是正後に同じ方法で起動する。
   直せなければ誤った手順を残さず、影響・試行・再開条件を伝える。
   操作に無関係な欠けた素材が起動を妨げる時は、検証用の足場と明記して作り、後始末で消す。
3. スキルを書く。
   置き場所は`<対象のディレクトリ>/.claude/skills/verify/SKILL.md`とする。
   対象のディレクトリは対象のコードに最も近いディレクトリで、リポジトリ全体が対象ならrootとする。
   Claude Codeに同梱の`/verify`は同じ置き場所のスキルを使い、無ければ作る。
   frontmatterに`name: verify`と、アプリ、入口、使う時を書いた`description`を置く。
   `disable-model-invocation`を付けるとモデルが起動できなくなるため、モデルから起動できる形で置く。
   本文は本書「生成するスキルの節」と「機能一覧」の形で、調べた実物の値だけで書く。
4. 生成したスキルの手順のとおりに、1つの機能を起動から後始末まで実行する。
   後始末の後に、本書「生成するスキルの節」の証拠の引き渡しを確かめる。
   失敗した反復の後も後始末を実行してから直す。
   代用の環境（コンテナー、ローカルの構成など）で確かめた時は、本来の対象で行われない準備を列挙し、本来の対象では未確認とする。

## 生成するスキルの節

- 起動: 起動のコマンドと、使える状態になったことの判定（応答するだけでなく、初期化とデータの投入が終わったこと）。
  空のデータから使える状態まで進める。
  短時間で終わるCLIでは、準備を1回行い、操作ごとに隔離した実行とする。
- 状態確認: 操作する価値がある状態かを答える読み取り専用の確認を1つ（対象の版か、データと設定が隔離先か、ポートの持ち主が自分か）。
- 操作: このリポジトリの実際のコマンドとセレクター。
  座標や順番より安定した手掛かり（アクセシビリティの名前、データ属性、表示文字列、URLのパス）を使う。
- 証拠: 何を取り、どこへ保存し、どう引き渡すか。
  - 使う人と同じ公開操作で動かし、内部関数やテスト専用の手段で得た結果は証拠から外す。
  - 操作と、その結果の状態の両方を取る。
  - 表示された結果に加え、副作用（書かれたファイル、保存された記録、送った内容）を別の手段で確かめる。
  - 代用の対象は、本番でも境界で切り離されている外部サービスに限る。
    端から端までの操作には、実サービスの検証用環境と、利用する範囲のAPI・画面・状態・エラーを再現するエミュレータを比べる。
    既存の偽サーバーや偽CLIを先に使い、隔離して起動し、実際のアプリをつないで操作と副作用を確かめる。
    機能が複数のユーザーやアカウント切替を使うなら、その状態も再現する。
    応答は実際の応答か公式のスキーマから写し、出所と版を記録する（`agent-basics:writing-standards/references/testing-design.md`「簡潔さ」）。
    実サービスとの差が残る範囲は「生成の手順」4に従って未確認として書く。
  - dry-runやテストモードは、名前を信じずに、実際に省くものを観測する。
  - 証拠はプロジェクト指定の一時領域に保存し、後始末でも残す。
    読者が同じ領域を開けるなら報告にそのパスを書く。
    開けないなら、文字の証拠は必要な範囲を報告に写し、添付が要る証拠は既存の認可済みの場所へ渡す。
    渡す場所は生成するスキルに記し、秘匿値や実ユーザーのデータを含む証拠は渡さない。
    プロジェクトの課題管理が添付を扱え、履歴へ保存してよい場合は、証拠の添付も選べる（第三者・実ユーザーのデータや秘匿値が無いことを添付前に確かめる）。
    自動で中身を確認できない形式では、添付する担当が保存前に内容を確かめる。
    認可済みの場所が無ければ新設せず、証拠のホスト名とパス、読者が開けないこととその理由を書く。
  - 後始末の後、報告の読者の立場で、報告に書いた所在から証拠を開けることを確かめる。
    渡せなかった証拠は、保存したホストの記載先に残ることと、報告に閲覧の制約を書いたことを確かめる。
- 後始末: 起動した時の識別子で、起動した資源だけを止めて消す（名前で止めると他者のプロセスに及ぶ）。
- 補助スクリプト: 同梱するスクリプトは実行可能にし、呼び方を本文に書く。

## 機能一覧

使う人から見た機能ごとに、何をする機能か、どこから到達するか、どう操作するか、動いていることを示す観測、誤りやすい点を書く。
最初は、URLのパス、コマンド、メニュー、文書から主な3〜5機能を選ぶ。
データの前提不足は診断を保全して `agent-basics:bugfix` で原因を確かめ、操作を弱めず認可内のデータ修復後に再試行する。
結果か残る影響・試行・再開条件を伝え、理由を誤りやすい点に書く。
複数の入口を持つ機能は、入口ごとに確かめた結果を記す（1つの入口の結果で他の入口を確かめたことにはしない）。

## 保守の手順

1. 起動と操作の節と機能一覧を持つ`.claude/skills/verify/`を探す。
   無ければ本書「生成の手順」へ進む。
   編集はverifyスキルの配下（本文、機能一覧、補助スクリプト）に限る。
2. 機能一覧の索引と実物の過不足を直す。
3. 機能ごとにソースを読み、記述とのずれの候補を所在付きで挙げる（読み取りだけで、機能ごとに並行してよい）。
   最近の変更から一覧に無い入口を探し、ソースの所在を示せるものだけを欠落とする。
4. ソースにずれを確認できなくても、全ての機能を少なくとも1回実際に操作する。
   - 最初の操作の前と、操作が失敗した後と、想定外の結果の後に、状態確認をやり直す。
     状態確認で捉えられない異常は、既知の状態へ戻すか起動し直す。
   - 後始末の後に、本書「生成するスキルの節」の証拠の引き渡しを確かめる。
   - 失敗した反復で起動した資源は、その場で後始末する。
   - 到達できない機能は、欠けた前提（認可、OS、外部の状態など）と試した操作を添えて到達不能とする。
5. 食い違いを分ける。
   - 文書のずれ: 機能の説明や操作の誤りと欠落。
     verifyスキルを直す。
   - 操作手段の不足: 機能は動くが、スキルの手段では操作できない状態。
     補助を直し、直した操作を実際に動かし直す。
   - 製品の不具合: アプリの挙動が実際に誤っている状態。
     報告に回し、文書は実際の挙動に合わせずに元の記述を保つ。
6. 結果を「問題なし」「修正あり」「中断」のいずれかとし、修正は確かめたものだけを1つの変更にまとめる。

## 返す報告

生成では、置き場所、選んだ入口と残した入口、最後まで実行した機能と証拠の所在（開けない場合はその制約）、代用の環境で未確認の準備を含める。
保守では、結果、操作した機能と到達不能の前提、文書のずれ、操作手段の不足、製品の不具合を含める。
