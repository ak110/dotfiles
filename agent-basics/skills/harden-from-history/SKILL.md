# 履歴からの再発防止

1件ずつの修正では、同じ仕組みから出る誤りが別々の不具合に見え、再発防止がその1件の対策で止まりやすい。
本スキルは履歴全体から誤りの型を見つけ、「最初から作り直すなら何がそれらを起こりえなくするか」を問い、型ごとの対策を過去の実際の誤りで確かめて1段階ずつ入れる手順を定める。
対策を比べる順と効果の確かめ方は`agent-basics:bugfix/references/prevention.md`「案を比べる順」に従い、本スキルは対象の集め方、型へのまとめ方、作り直す視点、段階ごとの出荷、置き換えた物の削除を加える。
作業中に見つけた個別の欠陥は`agent-basics:bugfix`で扱う。

## 手順

1. 範囲と材料を決める。
   範囲は依頼が示した期間と領域とし、無ければ修正のcommitを数十件含む直近の期間から始める。
   材料は次から、取得できるものを集める。
   - `git log`: 修正を表すcommitの説明、revert、同じ箇所への短い間隔での修正の繰り返し。
   - レビューの指摘: PRやMRのコメント（取得手段がある時。読み取りだけを行う）。
   - 障害の記録、issue、事後の振り返り。
   - 後から追加された注意書き（規範、コメント、レビューの確認項目）。
     注意書きは、その誤りが過去に起きた痕跡である。
2. 誤りを型へまとめる。
   修正ごとに、誤っていた内容、それを書けてしまった理由、見つかった機会（作成時の検査、レビュー、テスト、公開後）を1行で書く。
   書けてしまった理由が同じものを1つの型に束ね、型ごとに件数と害の大きさを書く。
   件数が1件でも、回復できない害（データの破損、セキュリティ、認可の境界）の型は残す。
   原因を確かめていない型は推測と書く（原則3、`agent-basics:writing-standards/references/quality-principles-facts.md`）。
3. 作り直す視点で型ごとの案を作る。
   「このプロジェクトを最初から作り直すなら、どの設計判断か機能の調整が、この型の誤りを起こりえなくするか」を問う。
   案は設計（誤りを招く構造を無くす）、型（誤った値を表せなくする）、lint、テストの順に比べ、型の誤りを防げる最初の案を採用する。
   lintは違反の位置と直し方を示すエラーを出す形にする（`agent-basics:writing-standards/references/check-script-design.md`）。
   機能、仕様、外部の契約を変える案は、ユーザーが観測する結果が変わるため、違いと利害を示して決める権限を持つ人の判断を得てから実施する。
4. 採用する対策が過去の実際の誤りを捕まえることを確かめる。
   型に属する過去の修正ごとに、修正の直前の版（または誤りを再現した入力）で対策が失敗し、修正後の版と正常な入力で成功することを確かめる。
   確かめられない対策は採用せず、確かめた範囲だけを効果として書く。
   並行する更新、再試行、状態遷移、認可の境界の型は`agent-basics:formal-verification`で、過去の不具合の操作列を反例として再現するモデルか網羅検査を作り、CIで実行する。
5. 1つの型への1つの対策を、独立にレビューと検証ができる1つのPR（PRを使わないプロジェクトでは1つのcommit）にして順に出し、複数の段階を1つのPRに混ぜない。
   先に入れると他の段階が小さくなる対策と、害の大きい型を先にする。
   各変更で、既存の成果物に残る同じ型の誤りも全て直す（後の作業者は規範より既存の実例を手本にするため、残すと同じ誤りが再生産される）。
   各変更の説明に、防ぐ型、確かめに使った過去の誤り（commit）、確かめた結果を書く。
6. 置き換えた物を同じ変更で消す（原則9、`agent-basics:writing-standards/references/quality-principles-subtraction.md`）。
   - 構造か検査が防ぐようになった型について、同じ注意を述べる文書、コメント、レビューの確認項目。
   - コードを言い換えるだけのコメント。
     意味のあるコメントが述べる制約は、型、検査、名前へ移せる時に移す（`agent-basics:writing-standards/references/implementation-time.md`「コメントの記述粒度」）。
   - 実装の内部を固定する単体テストは、同じ契約をモデル、実際のデータベースなどを使うテスト、E2Eで保証できる時に置き換える（保護対象の判定を先に行う。`agent-basics:writing-standards/references/testing.md`「削除・統合の類型」）。

## 失敗例

- 型にまとめずに修正を1件ずつ見直し、同じ理由で書けてしまう誤りへの対策が、件ごとの注意書きの追加に分かれた。
- 追加したlintが過去の誤りを入力にして失敗するかを確かめず、実際には過去の誤りの書き方を検出しない検査を効果があると報告した。
- 作り直す視点で出た機能の削除を、ユーザーの判断を得ずに実施した。

返す報告に含める項目: 範囲と材料、型ごとの件数と害、採用した対策と出した変更、各対策が捕まえた過去の誤り（commit）と確かめた結果、判断を待つ機能や仕様の変更案、見送った型と理由。
