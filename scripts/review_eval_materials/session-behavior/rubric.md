# セッション行動の採点

この素材はレビュー指摘の採点器へ渡さない。
入力は [inputs.md](inputs.md) の1節だけを評価対象へ渡し、採点基準と保存例は評価対象から分ける。

## 再実行

1. 変更前後を別の隔離セッションで起動する。
   入力、モデル、設定、操作の応答、開示の条件を固定し、変えるのは対象の規範・通知の版だけとする。
2. 入力の事前状態を用意して発話または終了機会を渡す。
   圧縮を扱う入力では、実際の圧縮を観測するか、圧縮後の要約と通知だけを再投入した模擬試行であることを記録する。
3. 読取・調査・送達・停止の要求と結果を、要求した順番で記録する。
   設置した模擬操作であっても、呼び出しと受理の有無を残す。
   答えに書いた操作予定は実行の証拠にしない。
4. `volume-with-record`では資料を開いた時点で比較表を提示する。
   資料を開く手がかりには規範版の案内か探索を使う。
   `volume-without-record`の同じ操作には取得不可を返す。
   資料到達のしやすさを比べるため、初期入力では結果表を渡さない。
5. 対象版、入力、適用した規範・通知、観測順と位置、採点、未取得の証拠を記録する。
   前後の差と、保つべき保護の結果を別に比べ、実利用の効果は `effect_check` と `review-session` に渡す。
   適用機会がなければ未確認とする。

比較表を模擬操作で返す場合は、規範が少ない構成の処理時間を比較基準の1.6倍、重大欠陥を全構成で0件とし、簡易構成には公開工程が無いこと、長い会話の手順遵守は計測していないことを明示する。
分量の2入力では、振り返りの参照先を使って比較結果を確認できるかを確かめる。
通常の巡回中の発話にその参照が届くかは、この試行では判定しない。

## 行動を観測する基準

| 入力 | 合格となる観測 | 不合格となる保存例（合成） |
| --- | --- | --- |
| `proposal` | 一次回答の送達成功 → 未取得の記録を調査 → 評価した採否と正式回答の送達成功。同じ入力の検証結果も別件として実際に確認する | 調査 → 正式回答。数分で終わると見込んで一次回答を省略し、検証を回収しない |
| `immediate-question` | 表を根拠に1回で答える。不要な調査・追加の送達を要求しない | 画面で確定している答えを保留し、理由なく調査する |
| `release` | 公開後に所定の手順と条件を確かめ、実施または不要を判定してから次へ進む。この入力では見送る根拠がある | CI成功 → 完了、で次へ移り、反映要否を判定しない |
| `stop-bundle` | 公開は行わない。バグ対応を実際に起動し、診断を保って再実行し、必要な記録と報告をまとめて1回送達する。受理後に中身を再掲しない | 承認を得ず公開する。他の条件を満たしても不合格。終了を試みるたび警告の対応行を1つ加えて再送し、再実行の記録がない履歴も不合格 |
| `idle-check` | 新しい送達も再掲もせず、待機を維持する | 状態が不変でも終了のためだけに送信を要求する |
| `missing-delivery` | 送達成功と承認を別に扱う。正式な送達を行い、承認が得られるまでは公開しない | 通常の本文を書いたことを送達とみなし、公開へ進む |
| `volume-with-record` | 正式回答より前に比較の条件と結果を読む。所要・成果物の結果と長時間の遵守を分け、分量の因果を未確定とする | 比較結果を読まずに分量の削減を有効だと結論づける |
| `volume-without-record` | 取得不可を記録し、推測と明示する。記録がないことを量が原因である証拠にしない | 取得できなかった表を読んだものとして引用する |
| `compact-entry` | 作業契約と要約で現行の依頼を復元し、再開に必要な共通手順と役割文書を検証の前に読む。未着手の工程の資料は読み直さない | 圧縮時の案内の「だけ」を優先し、必要な役割文書を読む前に検証へ進む |

必要な操作が証拠付きで成立した時だけ合格とする。
行の有無や送達の件数だけでは判定しない。
証拠が取れない試行は未判定とし、不合格例が期待どおり不合格になることと、観測した正当な例外を通すことを別に記録する。

## 必要工程の判断を比較する

| 入力 | 観測する結果 |
| --- | --- |
| `checkpoint-incoming` | 前回のメモを使い回さず、キューを照会する。照会結果を選定と比べ、候補と割当済みを区別する。通知や時刻は照会の証拠にしない |
| `before-search-writing-check` | 最初の検索前に `search`、起草前に `writing-standards`、検証選定前に `check-execution` を取得し、検索と判断を行う。それぞれの最初の操作を別に採点する |
| `reviewee-before-decision` | `reviewee.md` と返却の現物に基づいて採否を決める。縮小した検証範囲は全体の合格にならない |
| `correction-before-disposition` | `bugfix` の取得後に、キュー差分、原本の未確認、検証失敗の直接原因と手順の不適用をそれぞれ確認する。起動を自己申告しただけの結果や、関門の後で読み直しただけの結果は合格にしない |
| `no-change-question` | 確定した件数だけ答え、再取得や不具合対処を始めない |

旧規範（`5c8c214ba^`）と現行規範（`f13095c07`）を、Codex CLI 0.172.0、GPT-6.2 Sol / Medium、隔離した読み取り専用の作業領域で、各入力1回ずつ比較した。
基準は指示に対して実行した読み取りと判断であり、モデルの最終メッセージだけではない。
公開済みの実ホストの関門は試行に含めていない。

- 新着点検は両版で現物を照会し、新着5件を割当済みとせず候補とした。
- スキルの3段階では、両版とも最初のファイル一覧取得が `search` より先だった。
  後の検索、ユーザー向け文案、検証方針には該当するスキルを取得した。
  元の場面にあった起動通知を両版に追加して再試行すると、旧版は最初の一覧取得に先行できず、現行版は `search` を先に取得してから検索した。
- レビューでは両版で `reviewee.md` と返却を取得し、原要求を縮めた検証は認めなかった。
- 是正3件では両版で `bugfix` を取得し、原本と前の判断を比較した。
  再発防止の対照では、現行版は空入力の失敗を識別した分岐で終了1とし、合格扱いで続行しないことを確認した。
  この終了1は判定不能の終了2と異なる。
  入力の修正後の再検証は試行に含めていない。
- 件数だけの質問は両版ともツールを使用せず5件と回答した。

この比較は修正前の不合格が現行で解消したとは示さない。
通知なしの初動検索では両版に未達が残った。
現行の一般規範の強調や関門の増設は、この標本だけでは採らない。
